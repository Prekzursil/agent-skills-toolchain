## Findings

### F1 — UNVERIFIED on Windows: `codex` promises a blocking foreground adapter while global fork mode forces subagents into the background

**Agent text, verbatim.** `/local_disk0/codexwork/bundle/claude/agents/codex.md:3`:

> `description: Synchronous cross-vendor work-unit executor. Blocks until Codex finishes and returns a schema-valid result or a terminal FAILED line. Use for fan-out work units that must produce artifacts; never for fire-and-forget exploration.`

`codex.md:8-11`:

> `# codex — synchronous Codex work-unit adapter`
>
> `You dispatch ONE work unit to the Codex CLI, BLOCK until it truly finishes, verify what it`
> `claims, and return a terminal state. You are a work-unit executor, not a forwarder.`

`codex.md:101-102`:

> `- Never --background, &, nohup, detached, or run_in_background.`
> `- Never return a job id, a "Check /codex:status" string, or a [codex] … progress log as a result.`

**Conflicting provider text, verbatim.** `/local_disk0/codexwork/bundle/claude/settings.json:4-7`:

> `"env": {`
> `  "CLAUDE_CODE_FORK_SUBAGENT": "1",`
> `  "CLAUDE_CODE_USE_POWERSHELL_TOOL": "1",`
> `  "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1",`

The current official subagent documentation says: when `CLAUDE_CODE_FORK_SUBAGENT=1`, every subagent spawn runs in the background and the `background` field has no effect; `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` takes precedence and keeps subagents foreground ([official runtime contract](https://code.claude.com/docs/en/sub-agents)).

**Concrete collision.** A parent delegates a work unit to named agent `codex` because its description promises the Agent call will block until the artifact and terminal receipt exist. With the global environment shown above, Claude Code schedules that subagent in the background. The inner `codex exec` can still be foreground *inside the worker*, but the parent-side delegation boundary is no longer blocking. The parent can continue before the work-unit receipt exists—the exact semantic distinction the description uses for routing.

**Which side wins at runtime.** The host's execution-mode environment wins over prose in an agent prompt. This is **very likely (80-90%)**, based on the exact enabled environment variable and the current official runtime contract. It is **UNVERIFIED on the pinned Windows installation**; settle it by running `claude --version`, starting a fresh session, invoking `@agent-codex` with a harmless 10-second probe, and recording whether the Agent tool returns a background task immediately or blocks through `SUCCESS:`. That experiment also determines whether the installed version predates the documented fork behavior.

**Minimal resolution — UNVERIFIED pending that experiment.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** If synchronous parent-side semantics remain load-bearing, remove `CLAUDE_CODE_FORK_SUBAGENT=1` or set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`; then run the probe above. If global backgrounding is more valuable, edit `codex.md:3,8-11` to say that the *worker* runs `codex exec` synchronously but the parent receives a later completion notification, and remove the parent-blocking routing promise. The former is the smaller semantic repair but has global effects; the latter is the smaller file diff but changes the contract. It is **likely (55-80%)** that removing the stale fork override is preferable, because this specific adapter was created to prevent severed/fire-and-forget work, but that choice depends on other units' concurrency findings and therefore is not asserted as final here.
