**Unit:** L03, partner dimension / anti-slop and quality-perfection enforcement  
**Date:** 2026-07-19  
**Scope:** read-only audit and design. I changed no harness subject file. The only write is this artifact.  
**Remote-node constraint:** the Windows paths in the brief do not exist on this Linux worker. ## Executive verdict

Do **not** add another guard or another semantic store. Replace the current `dup-guard` decision rule while keeping its existing PreToolUse slot, and replace the internals of the current Stop-time `wire-check` while keeping that slot. Add outcome receipts through the already-wired PostToolUse dispatcher and existing event-ledger/open-loop buses. Net new hook processes: **zero**.

The current `dup-guard` is configured as a pre-write, inject-only, fail-open check. It catches exact source basenames and the first class/function-like symbol (`guard.py:2-22,241-315`), is listed under the existing local dispatcher (`_dispatch/manifest.json:182-225`), and the enclosing PreToolUse dispatcher is registered in settings (`settings.json:251-259`). Its seven direct fixture expectations passed on this node. Those are two mechanically independent signals—configuration/source inspection and subprocess execution—after the subprocess detector first found its known-positive `alpha.py` collision.

That is not a quality record. The corpus explicitly says its hook detector failed a known-positive control and that the whole hook section is no data (`inputs/corpus.json:13260-13263`). Therefore the existing guard's historical true-positive rate, false-positive rate, acceptance rate, and prevented-duplicate count are **UNVERIFIED**; the experiment that settles them is a shadow replay over labeled historical Write payloads plus prospective candidate/outcome receipts (Finding 1). Reporting “no false positives” or “no fires” would be false.

The implementation already exposes both sides of the quality problem:

* It can false-alert on use-versus-mention. `_symbol_defined_elsewhere` searches every matching text file without a source-extension restriction (`dup-guard/guard.py:206-226`). In a throwaway known-negative control, a line `class MentionOnly:` in `docs/architecture.md` caused a duplicate warning for a new Python class. This execution result and the unrestricted search code are mechanically independent signals. The wider harness has already recorded 8+ use-versus-mention false fires across multiple detectors and identified the missing semantic-role discriminator (`inputs/INPUT-known-harness-defects.md:9-50`).
* It misses renamed copies. Its only two features are basename and primary symbol (`dup-guard/guard.py:263-294`). A throwaway new function with a different basename and symbol but the same `return sum(...)` implementation stayed silent; code-path inspection independently confirms there is no body/token comparison. This is a demonstrated scope miss, not a measured historical false-negative rate.
* It fires only for `Write` and only for a nonexistent target (`dup-guard/guard.py:241-255`), while the corpus contains 28,964 Edit calls and 12,845 Write calls (`inputs/corpus.json:31-52`). Thus it does not cover duplication introduced by editing an existing file. This is a scope fact, not an inference about how many duplicates edits caused.
* The post-write dead-code check is text-reference counting, not reachability. `wire-check` filters definition-looking lines from ripgrep hits and calls zero remaining hits “referenced 0x” (`wire-check/check.py:218-232,259-287`), while its own message acknowledges intentional public APIs (`wire-check/check.py:341-347`). Its fixtures deliberately treat an unreferenced exported function and an endpoint literal appearing once as fires (`wire-check/test_wire_check.py:73-125`); they do not label public API, framework-registration, reflection, generated-code, or runtime-entrypoint controls.
* The quality tests and manifest are inconsistent. `test_wiring.py` declares ten expected PreToolUse checks including `dup-guard` (`_dispatch/test_wiring.py:39-51`), while the manifest presently contains four (`_dispatch/manifest.json:182-225`). `test_manifest_presence.py` requires `test-tamper-guard` and `dark-surface` in Stop (`_dispatch/test_manifest_presence.py:21-65`), while the manifest Stop list is `bg-registry/done_marker`, `heartbeat`, `wire-check`, `honest-signal`, `stub-ledger/report`, `forge/todo-surfacer`, and `journey-coverage` (`_dispatch/manifest.json:72-142`). A direct JSON comparison first found the known-present controls `dup-guard` and `wire-check`, then found those expected entries missing. Pytest itself was unavailable on this worker, so an actual Windows test-run result is **UNVERIFIED**; installing/running the repository's declared test environment on Windows settles execution.

The corpus is large enough to ground priorities but not to manufacture labels: 11,633 transcript files / 10.62 GB were distilled with zero failed files and one bad line (`inputs/corpus.json:2-11`); the correction miner itself warns that 41/41 unfiltered smoke candidates were false positives (`inputs/corpus.json:10371-10374`). A real owner example says an allowlist was already correct while five requested columns were never built (`inputs/corpus.json:11566-11570`), exactly the distinction this design must preserve: do not rebuild the correct surface, and do not let deduplication distract from missing scope. Another owner message says “already told you ... finish it” (`inputs/corpus.json:11338-11342`), and another explicitly says not to forget durable findings (`inputs/corpus.json:11578-11582`). These are recall-biased candidates, not population rates; I use them only as concrete preference evidence, never as counts.

## Design invariants and hook budget

1. Every verdict closes on an external signal: filesystem/search output, language analyzer, dependency graph, build/test/coverage execution, a different model in a separate context, or explicit owner adjudication. Same-context agent reflection never labels its own result.
2. Zero new hook processes. Pre-mutation work folds into the existing `dup-guard` entry in `_dispatch/manifest.json:206-215`; post-mutation correlation folds into the existing PostToolUse dispatcher (`manifest.json:144-180`); final reachability folds into the existing `wire-check` Stop entry (`manifest.json:97-105`). This remains under the ~6-hook ceiling by replacement/folding, not addition.
3. Every detector is fail-open: outer `try/except`, exit 0, bounded work, and silent failure, matching the current guard (`dup-guard/guard.py:229-315`) and dispatcher (`_dispatch/dispatch.py:286-329`). A detector failure is separately observable in the existing ledger/shadow sink; it never blocks the edit.
4. Owner attention is a scarce resource. Weak evidence is logged silently; medium evidence produces at most one compact inline candidate; only irreversible/high-impact ambiguity asks once. No per-candidate popup, no mandatory explanation, and no “confirm this is intentionally new” on basename alone.
5. No thread is dropped. Any accepted `replace` or unresolved `possible duplicate` decision becomes an existing event-ledger/open-loop record until an external closure receipt arrives. The current open-loop layer already exists specifically for durable triggers and derived unresolved failures/goals (`open-loops/_common.py:1-26`), and `event-ledger/note.py` already records decisions and tombstones superseded failures (`event-ledger/note.py:1-13,25-43`).
6. Anti-overfit gate: every proposal below uses existing dispatch, ledger, capability catalog/router, native analyzers, and tests. None introduces a second runtime, vector database/KG, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Findings — inferred surprises first

### Finding 1 — **UNVERIFIED historical premise: make the guard earn the right to interrupt via a candidate/outcome ledger**

**Improvement:** Turn duplicate detection from an unmeasurable warning into a calibrated, falsifiable intervention policy.  
**What it is:** Every candidate receives a stable `candidate_id`, the proposed path/symbol, candidate path/symbol, evidence features, detector version, intervention lane (`shadow|inline|ask`), and timestamp. A separate later event records `reuse_existing`, `extend_existing`, `replace_existing`, `intentional_new`, `dismissed_false_positive`, or `unresolved`. This is not self-correction: labels come from the subsequent git diff/import graph/test result, a separate reviewer context, or the owner.  
**Why inferred:** The corpus cannot measure hooks because its detector failed its control (`corpus.json:13260-13263`), while the correction miner's 41/41 smoke false positives show that unlabeled heuristic counts are dangerous (`corpus.json:10371-10374`). The owner also pushes back on already-completed work (`corpus.json:11338-11342`). The inferred desire is not “more warnings”; it is warnings whose reliability is knowable without spending owner focus.  
**How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a small JSON event emitter to `dup-guard` using the existing event-ledger schema or shadow sink; do not make a new database. Fold a resolver into the existing PostToolUse dispatcher: hash the pre-write candidate, inspect the actual changed path/import choice, and leave uncertain cases unresolved. Once per week or 50 candidates, the existing background digest emits only a compact calibration row: `TP/FP/unresolved`, stratified by evidence class. Sample 20 resolved and 20 unresolved candidates to a separate reviewer context; owner adjudication is requested only for disagreements that affect promotion. Include detector version so threshold changes do not mix populations.  
**External signal that verifies it:** (1) a mechanically generated before/after git/import receipt, (2) a separate-context reviewer label on the stratified sample, and (3) owner labels only on reviewer disagreement. Promotion requires a predeclared lower precision bound and no regression in task completion; **UNVERIFIED** thresholds must be chosen after the first 100 labeled candidates—the shadow replay experiment settles them.  
**SOTA citation:** A preregistered CHI 2025 experiment found that explanations can increase reliance on correct and incorrect LLM answers, while sources and inconsistencies reduce reliance on incorrect answers; evidence, not fluent rationale, is the useful trust signal: [Kim et al., Fostering Appropriate Reliance on LLMs](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies/). Microsoft’s broader initiative defines both over- and under-reliance as harmful: [Appropriate Reliance Research Initiative](https://www.microsoft.com/en-us/research/articles/appropriate-reliance-research-initiative/).  
**Confidence:** **almost certain (90-99%)** that this is necessary to claim a true/false-positive record, because the corpus explicitly marks hook data unusable and the present guard writes only throttle state, not outcomes (`dup-guard/guard.py:130-163`). **Likely (55-80%)** that it reduces owner interruption without losing useful catches; evidence is the shadow-first design and HAI results, but the local acceptance effect remains **UNVERIFIED** until the prospective A/B shadow experiment compares interventions per completed task.  
**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for shadow recording; confirm-first before promoting any class to owner-facing `ask`.

### Finding 2 — use two independent code signals; basename alone becomes silent retrieval

**Improvement:** Replace “same basename or first symbol ⇒ warn” with an evidence ladder that distinguishes a mention from an implementation.  
**What it is:** Lane A retrieves cheaply: exact basename, exact defined symbol, normalized imports, and sibling tests. Lane B corroborates independently: source-only token/body similarity or a language-native symbol/dependency result. Only A+B can interrupt; A alone is a silent candidate. Documentation, test fixtures, vendored/generated files, public entrypoints, and intentionally recurring module layouts are typed contexts, not a growing exception word list.  
**Why inferred:** The live-defect input shows 8+ false use-versus-mention fires and says rewording followed the prose rather than fixing the discriminator (`INPUT-known-harness-defects.md:9-50`). The current guard's symbol search has no source-file filter (`dup-guard/guard.py:206-226`), and the known-negative documentation fixture actually fired. The owner wants the harness to protect quality without taxing focus.  
**How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** In the existing guard: (a) restrict candidate definitions to language-compatible source globs; (b) parse only declaration positions with stdlib `ast` for Python and use installed language analyzers where already available; (c) normalize comments/whitespace/identifier names into a token fingerprint; (d) require compatible project/module boundary or shared tests/imports as corroboration; (e) emit reason codes such as `same_symbol+body_similarity`, never a generic “duplicate.” Keep a bounded `rg --files` fallback, but pass explicit excludes rather than relying on implicit ignore behavior.  
**External signal that verifies it:** A golden fixture matrix in a separate subprocess: known-positive same implementation; known-negative documentation mention; legitimate `index.ts` recurrence; same class name in independent packages; test fixture; generated file; same symbol with materially different body. A separate language parser/analyzer must agree with the text candidate before an inline warning. The acceptance test is 100% silence on the recorded prose false fires while retaining the known-positive collision.  
**SOTA citation:** Microsoft’s validated HAI guideline set says to time services based on context, show contextually relevant information, support efficient correction, and update cautiously: [Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/). Clone research also warns against equating lexical shortcuts with semantic equivalence: [Xu et al., Semantic Code Clone Detection: Are We There Yet?](https://arxiv.org/abs/2606.25272).  
**Confidence:** **very likely (80-90%)** that source typing plus a second independent signal eliminates the demonstrated documentation false positive, based on the exact failing search code and executed negative control. **Likely (55-80%)** that it preserves useful recall; lexical/structural clone detectors degrade under distribution shift, so the held-out replay—not same-context judgment—must decide.  
**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it in shadow; confirm-first for any blocking behavior. This design recommends no blocking behavior.

### Finding 3 — detect renamed/reshaped duplication before mutation with a local token index, not an embedding service

**Improvement:** Cover the important false-negative class the present guard cannot see: different filename and symbol, duplicated behavior.  
**What it is:** At PreToolUse for new `Write` and duplication-relevant `Edit`, fingerprint only the changed function/class blocks, query a repository-local inverted token index, and return at most the top three existing blocks with file:line and shared tests/callers. The agent chooses reuse/extend/new, but that choice is verified later by Finding 1.  
**Why inferred:** The existing guard examines only basename and first symbol (`dup-guard/guard.py:263-294`); a renamed identical-body control stayed silent. The corpus shows far more edits than writes (`corpus.json:31-52`), so Write-only coverage omits the dominant mutation surface. The owner's “output allowlist is ALREADY fine” correction (`corpus.json:11566-11570`) is a concrete demand to find existing behavior before changing it.  
**How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Adapt SourcererCC's minimal idea, not its full system: tokenise blocks, discard ubiquitous tokens, use an inverted index and Jaccard/containment score, and rebuild lazily from git-tracked source files when `HEAD` changes. Store the small index under the existing cache convention, not Basic Memory and not a vector DB. Fold Edit into the existing local PreToolUse dispatch matcher; do not add a hook. Limit analysis to the proposed changed block and a strict time budget. Treat semantic-only model similarity as nomination, never proof.  
**External signal that verifies it:** Mutation/injection fixtures produce renamed, reordered, and lightly edited clones plus non-clone same-domain blocks. A separate execution signal then runs the candidate's existing tests against the proposed reuse/adapter path or performs a differential test on both implementations. No test equivalence means `possible`, never `duplicate`.  
**SOTA citation:** SourcererCC demonstrated that an inverted token index can scale clone candidate retrieval and evaluated recall with both BigCloneBench and mutation/injection benchmarks: [Sajnani et al., SourcererCC](https://arxiv.org/abs/1512.06448). A replication found large recall drops on unseen functionality, supporting nomination plus external verification rather than model authority: [CodeBERT replication study](https://ink.library.smu.edu.sg/sis_research/10175/).  
**Confidence:** **likely (55-80%)** that a bounded token index catches materially more renamed copies than basename/symbol matching; the executed identical-body miss and published clone results support the direction, but local recall is **UNVERIFIED** until the mutation/injection and held-out historical replay run. **Very likely (80-90%)** that the design stays within the anti-overfit gate because it is a local cache and existing hook entry, not a service/runtime.  
**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it in shadow; confirm-first before deleting or replacing an existing implementation.

### Finding 5 — make replacement a transaction with a supersession receipt and open-thread closure

**Improvement:** Allow radical replacement without leaving `v1`, `v2`, dead buttons, or a forgotten migration halfway complete.  
**What it is:** A duplicate decision has four typed terminal choices: `reuse`, `extend`, `replace`, `intentional_parallel`. `replace` opens a supersession record with old surface, new surface, consumers, tests, docs/config references, and rollback point. It closes only when independent signals prove the old surface is removed/redirected, all consumers moved, and verification passed.  
**Why inferred:** The owner explicitly places full replacement on the table but forbids duplicated v2 with no v1 and never permits discussed-then-forgotten threads. The corpus contains the concrete reminder “do not forget to update basic memory with our findings” (`corpus.json:11578-11582`). Current `wire-check` flags suffixes only after writing and only when it thinks no base is live (`wire-check/check.py:289-317`); that does not manage a real migration where both versions temporarily exist.  
**How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Use `event-ledger/note.py --kind decision` for the supersession decision and the existing open-loop store for unresolved closure; do not create another workflow engine. The existing Stop `wire-check` reads active supersession records and reports only failed postconditions. Close with a milestone/tombstone after: old imports/references zero by analyzer, new entrypoint reachable, build/tests green, and declared docs/config migrated. An intentional compatibility shim is explicit and time-bounded, not “dead.”  
**External signal that verifies it:** `git diff --name-status` or equivalent proves removal/redirect; a language dependency analyzer proves consumer migration; the exact build/test command produces a fresh receipt after the last mutation. For user-visible surfaces, a journey/interaction test—not a self-review—proves the button/route is live.  
**SOTA citation:** The July 2026 ProACT work models forgotten constraints, ambiguous goals, underspecified plans, and discussion loops as collaboration breakdowns and evaluates whether intervention is appropriate and non-interruptive: [Yang et al., ProACT](https://arxiv.org/abs/2607.03730). This is frontier evidence, not yet a local causal result.  
**Confidence:** **very likely (80-90%)** that typed terminal states prevent silent `v1/v2` ambiguity when used, because closure is based on external postconditions and the existing open-loop bus persists unresolved work. **Likely (55-80%)** that it lowers owner stress from forgotten migrations; the owner reminder is direct but recall-biased, and the effect is **UNVERIFIED** until supersession-age and owner-reminder rates are compared prospectively.  
**Value × effort:** transformative × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for recording/verification; confirm-first when `replace` changes a public API, deletes data, or removes a capability.

### Finding 7 — personalize the interruption budget from observed outcomes, not inferred personality

**Improvement:** Preserve owner focus by making proactive warnings rarer as evidence weakens and by learning only from explicit or mechanical feedback.  
**What it is:** Per reason-code, maintain counts for accepted reuse/extend, intentional-new, ignored, and owner-dismissed. Use three lanes: `shadow` for weak/uncalibrated, one-line `inline` for calibrated high-likelihood reversible guidance, and `ask` only for irreversible or expensive ambiguity. One candidate appears once per session and again only if evidence changes. No persona model and no trained critic.  
**Why inferred:** Prompt fatigue is a hard constraint, and the existing guard asks the agent to “confirm this is intentionally new” on any finding (`dup-guard/guard.py:296-312`). The corpus contains 41,809 Write+Edit opportunities (`corpus.json:31-52`), so even a modest uncalibrated fire rate can become noisy; this arithmetic is a risk bound, not an observed fire rate. The owner correction “already told you ... finish it” (`corpus.json:11338-11342`) argues for remembering decisions rather than asking again.  
**How to build:** **NATIVE-vs-BUILD: CONFIG (settings/JSON only)** after Finding 1 supplies labeled outcomes. Store thresholds, cooldown, max inline notices per session, and irreversible-action classes in the existing detector config/manifest. Default every new reason code to shadow. Automatically demote to shadow when the rolling lower precision bound misses its target; never auto-promote. Persist an `intentional_new` decision keyed by scope so repeated warnings stay silent.  
**External signal that verifies it:** Mechanical outcome receipts and explicit owner dismissals drive the counts. A prospective alternating-session experiment compares completed-task rate, guard acceptance, owner corrections, and interruptions per hour between calibrated and current policy. The agent's same-context statement “helpful” is not a metric.  
**SOTA citation:** The HAI guidelines explicitly call for context-timed services, efficient dismissal/correction, remembering interactions, cautious adaptation, granular feedback, and global controls: [Amershi et al.](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/). ProACT evaluates non-interruptiveness and judged intervention quality rather than proactivity alone: [ProACT](https://arxiv.org/abs/2607.03730).  
**Confidence:** **likely (55-80%)** that calibrated triage lowers interruption load without losing high-confidence catches; HAI evidence and the bounded policy support it, but the owner-specific effect is **UNVERIFIED** until the alternating-session experiment runs. **Very likely (80-90%)** that persistent intentional-new decisions prevent exact repeat nags, because the key and cooldown are deterministic.  
**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for demotion/silencing; confirm-first for any threshold promotion that increases owner-facing asks.

### Finding 8 — **UNVERIFIED historical premise: a mutation/replay gold set and contract test must precede enforcement**

**Improvement:** Give duplication and dead-code changes a release gate that cannot pass by merely agreeing with their own heuristics.  
**What it is:** A versioned, owner-adjudicated fixture/replay set with positive controls, negative controls, adversarial use-versus-mention cases, framework entrypoints, renamed clones, intentional forks, public APIs, generated/vendor code, and supersession migrations. Expected outcomes are authored outside the detector implementation and include dissent/provenance.  
**Why inferred:** Current direct tests prove only seven hand-written guard behaviors (`dup-guard/test_dup_guard.py:61-171`) and eight wire-check behaviors (`wire-check/test_wire_check.py:73-147`). The dispatcher tests and manifest are mutually inconsistent (`_dispatch/test_wiring.py:39-51` versus `manifest.json:182-225`; `test_manifest_presence.py:21-65` versus `manifest.json:72-142`). The known-defect file records a detector that reported zero skills/agents/hooks until a positive control showed only hooks were broken (`INPUT-known-harness-defects.md:111-129`).  
**How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing harness-bench/test directories, not a new evaluation service. Use two sets: deterministic synthetic mutation/injection fixtures and a privacy-redacted historical replay sampled across languages/projects. Freeze the holdout labels before threshold tuning. Run both standalone guard invocation and the real existing dispatcher path.
