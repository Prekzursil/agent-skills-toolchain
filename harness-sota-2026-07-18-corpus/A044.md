## Collision register

### C01 — client-build secret delivery conflicts with the always-on secret floor

**Class: CONTRADICTION**

**Artifacts and exact lines:**

* `claude/rules/kotlin/security.md:12-15` says never hardcode credentials, then prescribes `local.properties`, CI-generated `BuildConfig` fields, and platform storage; `:21-22` labels `BuildConfig.API_KEY` “GOOD.”
* `claude/rules/common/security.md:40-42` says always use environment variables or a secret manager and validate required secrets at startup.
* `claude/AGENTS.md:93-98` makes “Never hardcode secrets; use environment variables and validate presence at startup” always-on.

The rule conflates configuration, build-time injection, and secrecy. A secret compiled into a client artifact is still client-distributed material; changing the source of the value from a literal to CI/`local.properties` does not make the resulting `BuildConfig` field confidential. The target’s own “never hardcode” statement and “GOOD — from BuildConfig” example therefore conflict semantically. Precedence resolves this in favor of `AGENTS.md:95`; `rules/README.md:95` cannot authorize a language rule to weaken an always-on security floor because `AGENTS.md:122-126` explicitly forbids that.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** replace `:13-22` with a three-way distinction: (1) `local.properties` may hold local *inputs* but must be ignored and never copied into an artifact as a confidential value; (2) `BuildConfig` is for non-secret build configuration/public client identifiers only; (3) service credentials remain server-side in an environment-backed secret manager. Device-bound/user tokens belong in platform keystore/keychain-backed storage. This resolution is **almost certain (90-99%)**, because it directly satisfies the higher-precedence lines and removes the target’s internal contradiction.

### C03 — 403 is incorrectly grouped with refreshable authentication failure

**Class: CONTRADICTION**

**Artifacts and exact lines:**

* `claude/rules/kotlin/security.md:67` requires “token refresh with proper 401/403 handling.”
* `claude/rules/common/security.md:34` requires authentication/authorization to be verified, without collapsing the two failure classes.
* RFC 6750 distinguishes `invalid_token` (normally 401; the client may obtain a new token) from `insufficient_scope` (normally 403). [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)

If interpreted as “refresh on either status,” the Kotlin line can turn an authorization denial into a retry/refresh loop. The common line does not settle the operational behavior, so precedence alone does **not** resolve this; the protocol semantics do.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** say “refresh once only for an authentication challenge/`invalid_token` response (typically 401); treat 403/`insufficient_scope` as authorization failure unless the API contract explicitly defines otherwise; prevent concurrent refresh storms and cap retry at one.” This is **almost certain (90-99%)**, based on RFC 6750’s distinct status/error guidance.
