# G004 — Failure-mode inventory: use-versus-mention guards

**Unit:** G004  
**Date:** 2026-07-19  
**Scope:** five detector families, their observed false fires, the shared precondition, a common discriminator, and a regression suite  
**Subject policy:** read-only. I wrote only this artifact.

## Executive verdict

The defect is not “regexes need tuning.” It is a type error at the hook boundary: detectors receive a structured event, erase the structure by flattening some or all of it to text, and then interpret a lexical match as if it proved an action, an unfinished implementation, or a failed result. A string can be an executable command, a path, a status value, an identifier, source code, quoted evidence, documentation, or negated prose. The current detectors often discard exactly that role information before deciding.

The highest expected-damage member is the PostToolUse tool-result sentinel. A false warning tells the agent to discard a successful observation and not build on it, corrupting every downstream inference. The live defect record gives the concrete successful Databricks result whose field was `"user_cancelled_or_timedout": false` and the prior episode in which every WebFetch HTTP 200 was marked failed (`inputs/INPUT-known-harness-defects.md:63-76`). A pure probe against the unpacked current sentinel found a related still-live ordering defect: `{'status_code': 200}` is classified `FAILED`, while `{'exit_code': 0, 'success': False}` and `{'exit_code': 0, 'error': 'transport failed'}` are classified `SUCCESS`; that follows directly from treating every numeric status as a process exit code and returning at the first zero (`claude/hooks/tool-result-sentinel/sentinel.py:218-269`). Audit F08 independently recorded the same three outputs and confirmed the file was deployed behind the all-tools matcher (`inputs/audit-findings/F08.md:7-13`).

The shared repair is a small typed discriminator on the existing hook bus, not a new guardrail framework:

> **Decide what field and semantic role a match occupies before evaluating the match. Never search a serialized event.**

For commands, inspect executable command nodes, not strings or here-string bodies. For write scanners, interpret the target file and Markdown/source region before recognizing a directive. For results, use native failure events and fail-dominant structured fields, never arbitrary keys or prose. For credentials, require a source-to-outbound-sink flow, not the mere name of a file or token-like string.

The design is **very likely (80-90%)** to eliminate the recorded use-versus-mention cases because every recoverable false fixture differs from its positive control on a structural field (tool/field, target/region, key/value, or source/sink), not on subtle natural-language meaning. Evidence: the live cases at `inputs/INPUT-known-harness-defects.md:14-22,43-50,63-72`; the existing partial regression at `agents/harness/tests/test_modules.py:212-250`; and Claude’s hook schema, which supplies `tool_name`, structured `tool_input`, and structured PostToolUse data ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)). It is **unlikely (20-45%)** that one generic negation regex would solve the class, because two failures do not involve negation at all (a field name with boolean `false`, and an HTTP 200 treated as a nonzero process exit code), while the stub rewording chased three different words (`inputs/INPUT-known-harness-defects.md:39-41,65-72`).

## Failure-mode inventory

### 1. Tool-result sentinel — successful data represented as failure

**Mechanism.** The sentinel mixes six incompatible notions of status in one classifier: process exit codes, HTTP status codes, boolean success fields, status strings, error fields, and arbitrary MCP text (`claude/hooks/tool-result-sentinel/sentinel.py:218-289`). Numeric keys are tested in a fixed loop containing both `exit_code` and `status_code`; any nonzero integer is declared failed, so HTTP 200 becomes “exit code 200.” Conversely, an early `exit_code == 0` returns success before a sibling `success:false` or `error` can be considered (`sentinel.py:223-253`). For MCP text it flattens selected values and searches failure phrases without knowing whether the text is tool data, documentation, or an error (`sentinel.py:163-196,273-278`).

**Observed instances.** 

1. Databricks success: result contained `"user_cancelled_or_timedout": false`, call had `ok: true`, but the sentinel matched `timedout` and injected FAILED (`inputs/INPUT-known-harness-defects.md:63-69`). The independent signals are the semantically false boolean value and the top-level success value.
2. Prior WebFetch regression: a memory note records the same hook marking every WebFetch 200 as FAILED (`inputs/INPUT-known-harness-defects.md:69-72`). This is aggregate evidence; the number of calls is not in the bundle.
3. Current related reproduction: my no-write pure-function probe returned `{'status_code':200} => ('FAILED','exit code 200')`, `{'exit_code':0,'success':False} => ('SUCCESS','')`, and `{'exit_code':0,'error':'transport failed'} => ('SUCCESS','')`. The source branch independently predicts all three (`sentinel.py:223-269`), and audit F08 reports the same probe outputs (`inputs/audit-findings/F08.md:7-13`).
4. Current mention reproduction: an MCP result with `ok:true` and content text “documentation says connection refused is an expected example” returned FAILED in my pure-function probe. `_gather_text` deliberately collects `content` and `text`, and `_INFRA_FAIL` includes `connection refused` (`sentinel.py:77-92,163-196,273-278`). This is a synthetic regression candidate, not an observed owner incident.

**Precondition.** A successful structured response contains a failure-looking token in a non-status role, or carries two status fields whose meanings/precedence differ. The detector must flatten or mis-type the field before matching.

**Detection signal.** A lexical phrase such as `timed out`, any nonzero number in a key named `status_code`, or the first encountered zero exit field. None proves the application-level outcome without a schema contract.

**Structural fix.** Consume native PostToolUseFailure for host-detected failure; on PostToolUse, classify only documented structured fields with fail-dominant precedence: explicit `isError:true`, `success:false`, `ok:false`, or error status wins over transport success; process `exit_code` is distinct from HTTP `status_code`; HTTP 2xx is success; arbitrary keys and data text are never status. Tool-specific application status belongs in a small registry keyed by exact tool family, defaulting to UNKNOWN rather than FAILED.

### 2. Destructive-command/lifecycle guard — data text represented as an invoked command

**Mechanism.** The historical guard scanned a serialized tool payload, so a PowerShell `Set-Content` invocation that wrote a Markdown body containing `Remove-Item` was indistinguishable from invoking `Remove-Item`. The current shared module documents this exact root cause and has partially repaired it by selecting a whole-string input or a `command` field before applying `_is_irreversible` (`agents/harness/modules.py:764-790`). Current tests protect Write, memory-note, and Edit payloads (`agents/harness/tests/test_modules.py:212-250`).

That partial fix does not fully solve use-versus-mention inside a real shell `command` string. `Set-Content -Value @'... Remove-Item ...'@`, `printf 'rm -rf /' > notes.md`, `rg 'rm -rf' docs`, comments, and quoted arguments all occupy the command field but do not execute the quoted token. `_is_irreversible` still regexes the entire command string (`modules.py:659-723`).

**Observed instances.** Two of two live blocks were PowerShell `Set-Content` writes whose Markdown body quoted `Remove-Item`; the actual tool-use verb was `Set-Content` (`inputs/INPUT-known-harness-defects.md:14-18,58-61`). A separate behavioral rule retains this as the canonical known-positive control for the “single signal” lesson (`claude/rules/common/single-signal-verification.md:14-19`). The corpus has multiple Remove-Item block fingerprints, including six for system path `/`, but their truth labels are not recoverable from the distillation (`inputs/corpus.json:6925-6935`).

**Precondition.** The shell tool is genuinely invoked, but a dangerous command token occurs only in a string literal, here-string/heredoc body, comment, search pattern, or data argument to a writer.

**Detection signal.** A regex over the raw command string sees the dangerous token and flags it without proving that the token is an executable command node.

**Structural fix.** Extract executable command nodes and their arguments from the shell syntax tree, then evaluate policy on those nodes. For the two recorded cases the outer command node is `Set-Content`, so `Remove-Item` remains data. Preserve an explicit fallback: if parsing fails and a catastrophic token is present, return ASK/UNKNOWN, not a false claim that the operation is destructive and not silent ALLOW.

### 3. Credential/secret input guards — names or entropy represented as credential access/exfiltration

**Mechanism.** The standalone hook is better than total serialization for direct file tools, but its shell lane searches a read verb followed by a secret-name fragment on the same segment (`claude/hooks/deny-credential-reads/deny.py:19-55,86-101`). The shared module scans all string values for credential-looking paths and serializes all input for token patterns (`agents/harness/modules.py:641-643,746-798`; `agents/harness/redaction.py:11-42`). Neither requires an outbound sink. Thus legitimate local inspection, documentation, workflow definitions, session UUIDs, and hashes can be treated as raw credential exposure.

**Observed instances.** The owner directive embedded in both implementations records setbacks from inspecting the owner’s own `.ssh`, `.env`, and config and from workflows merely naming a credential file (`deny.py:73-80`; `modules.py:50-56`). The shared literal guard records UUID paths, Workflow scripts, and hex digests as false-positive shapes that hard-blocked legitimate calls across sessions (`modules.py:84-93,748-754`). Audit E15 independently groups the same concrete shapes and notes that all three blocker branches were disabled as a result (`inputs/audit-findings/E15.md:58-64`). Corpus fingerprints establish at least 15 shared credential blocks, seven literal-secret blocks, and three standalone blocks (`inputs/corpus.json:5336-5345,6743-6751,8166-8171`), but do not adjudicate individual truth.

**Precondition.** A tool input names a credential-like path or contains a high-entropy/token-shaped value even though the operation is local inspection, documentation, or another non-egress action.

**Detection signal.** Filename fragments (`.env`, `credential`, `auth.json`) or token regexes, with no source/sink relation.

**Structural fix.** Split privacy from exfiltration:

* keep literal redaction on persisted/displayed text;
* permit local reads under normal native permission policy, with the existing declarative deny rules used only in profiles that intentionally forbid context exposure (`claude/settings.json:64-71`);
* hard-block only a demonstrated flow from a sensitive source/literal to an outbound sink in the same structured tool call or shell AST (for example, `Get-Content .env | Invoke-WebRequest ...`);
* ask on unparseable mixed read/network commands rather than globally disabling the security lane.

This source-to-sink boundary matches audit F02’s independently proposed narrowing (`inputs/audit-findings/F02.md:23-29`).

### 4. Stub ledger — prose represented as unfinished implementation

**Mechanism.** `record.py` extracts Write/Edit content and sends the text to `stubscan.find_stubs` after only a target-path “test file” exclusion (`claude/hooks/stub-ledger/record.py:50-65,80-99`). `stubscan` applies comment, phrase, weak-word, and pass-body regexes line by line without parsing the target document or source language (`stubscan.py:18-50,65-97`). The report then re-runs the same detector, so a false record remains “confirmed” by the same non-independent predicate (`report.py:120-170`).

The source comments claim the scanner is tight enough not to flag prose (`stubscan.py:9-11`), but a pure no-write probe against the current function returned a hit for `# This is not a placeholder; production implementation follows.` and for the Markdown table row `| finding | no extension point exists; nothing is TBD |`. That behavior is predicted by `_COMMENT_INTRO + _WEAK` and `_PHRASE` (`stubscan.py:25-36,80-89`).

**Observed instances.** The live record counts five false fires while the operator successively used “stub,” “test double,” and “placeholder”; the source does not preserve separate text for all five occurrences (`inputs/INPUT-known-harness-defects.md:14-18,39-41`). The sixth was `F9-live-control-integration.md:400`, whose sentence says there is **no** extension point and nothing needs adding (`INPUT-known-harness-defects.md:17-22,94-98`). Writing the defect input itself then triggered the scanner because it quoted the prior trigger, making the class self-amplifying (`INPUT-known-harness-defects.md:24-38`).

**Precondition.** A non-test Markdown/documentation target contains a marker word or phrase in prose, a table, a blockquote, a quoted incident, or a negated assertion.

**Detection signal.** Bare lexical occurrence, optionally after a comment-like Markdown delimiter. The exact language role and polarity are discarded.

**Structural fix.** Define “unfinished work” by representational role, not vocabulary:

* source files: recognize syntax-valid directive comments (`TODO`, `FIXME`) and structural placeholder bodies (`pass`, `...`, `raise NotImplementedError`) using language-aware regions;
* Markdown: recognize only unchecked task items when the ledger’s purpose is work tracking, and placeholder code only inside fenced/indented code blocks with a source-language info string;
* paragraphs, tables, blockquotes, inline code, and quoted evidence are mentions and cannot create ledger entries;
* require an exact directive shape, not weak words such as “stub” or “placeholder”; negated prose then needs no general NLP negation detector.

CommonMark explicitly distinguishes paragraphs, block quotes, lists, inline code, and fenced code blocks, so this boundary has a standard grammar rather than local punctuation guesses ([CommonMark 0.31.2 specification](https://spec.commonmark.org/current/)).

### 5. Stop marker scanner — a marker name represented as the marker event

**Mechanism.** The live record says the Stop scanner matched a marker named inside a sentence explaining that naming markers trips scanners (`inputs/INPUT-known-harness-defects.md:52-62`). This is the canonical use-versus-mention shape: substring presence was substituted for an exact protocol token.

**Observed instance.** One false Stop fire, and only one, is individually recorded (`INPUT-known-harness-defects.md:54-62`).

**Precondition.** An assistant response discusses the marker protocol and includes the marker spelling in ordinary prose rather than emitting a protocol record.

**Detection signal.** Marker substring anywhere in final assistant text.

**Structural fix.** A protocol marker must be a whole record with an exact grammar—preferably a typed hook/result field; if text compatibility is unavoidable, anchor the marker to a line, require the expected value grammar, and parse only the designated terminal region. Text that merely contains the token in a sentence is a mention.

## Shared discriminator design

### Proposal 1 — Typed occurrence boundary (**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**)

Add one provider-neutral module, conceptually `occurrence.py`, imported by the existing shared dispatcher and local hooks during migration. It does not decide every policy. It preserves semantic role and gives policy detectors only eligible spans.

```python
@dataclass(frozen=True)
class OccurrenceContext:
    event: str                 # PreToolUse, PostToolUse, Stop
    tool_name: str
    field: str                 # command, file_path, content, status, data, final_text
    role: str                  # executable, source_code, directive, status, prose, data, identifier
    target_path: str = ""
    language: str = ""

@dataclass(frozen=True)
class Occurrence:
    verdict: Literal["ACTIVE", "MENTION", "UNKNOWN"]
    reason_code: str
    span: str = ""
```

The API is intentionally not `is_real_occurrence(text, context) -> bool`. A boolean forces parse failure, unknown schemas, and contradictory status fields into either a false block or a silent miss. `UNKNOWN` lets security gates ask and advisory gates remain silent while logging a canary.

The pipeline is ordered:

1. **Schema select.** Choose an allowlisted field from the native event. Never call `json.dumps(event)` for detection. `Bash.command`, `Write.content`, `Write.file_path`, and structured result fields remain distinct. Claude already provides these fields natively ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)).
2. **Role parse.** Commands yield executable AST nodes and data/string/comment nodes. File content yields target format plus block/source regions. Results yield status fields separately from data and identifiers. Final text yields exact protocol records separately from prose.
3. **Contract evaluate.** Each detector declares eligible roles. `destructive-command` accepts only `executable`; `stub-ledger` accepts `directive`/`source_code`; sentinel accepts only `status`; marker scanner accepts only an exact terminal record; credential guard accepts `sensitive_source -> outbound_sink`.
4. **Reasoned verdict.** Emit `ACTIVE`, `MENTION`, or `UNKNOWN` with a stable reason code such as `non_executable_string`, `markdown_paragraph`, `boolean_false_key`, `http_2xx`, `source_without_sink`, or `parse_failed`.

This proposal is **very likely (80-90%)** to fit below roughly 200 lines for the schema/role router and Markdown/exact-record handling, because it is a dataclass plus small field/extension tables and rides the already-normalized event bus (`agents/harness/schemas/hook-event.schema.json:22-54` is cited by audit C11 at `inputs/audit-findings/C11.md:90-94`). Shell AST adapters are excluded from that line estimate and addressed separately below.

### Proposal 2 — Native failure lane plus fail-dominant typed receipts (**NATIVE (Claude Code already does this; we just enable it)**)

Register failure handling on PostToolUseFailure and stop guessing host failure from successful PostToolUse prose. Claude documents PostToolUseFailure as carrying `tool_name`, `tool_input`, and top-level error information, while PostToolUse supplies structured tool output ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)). Keep application-level classification in the existing shared receipt bus, but use one precedence table:

1. explicit application failure (`isError:true`, `success:false`, `ok:false`, error status, nonempty error) wins;
2. process failure (`exit_code != 0`) next;
3. HTTP failure (`status_code` outside 200-299) next;
4. explicit success only if no failure sibling exists;
5. unknown schema -> UNKNOWN, never phrase-derived FAILED.

It is **almost certain (90-99%)** that this ordering fixes the reproduced HTTP-200 and exit-0-plus-error contradictions because those outputs are direct consequences of the current early-return order (`sentinel.py:223-269`; `inputs/audit-findings/F08.md:7-21`). UNVERIFIED: which MCP servers return application failure only as free text. The settling experiment is to sample sanitized response shapes for the top 20 MCP tools from raw transcripts, then add exact tool contracts only where structured status is absent.

For Bash, use an already-installed syntax parser if present; Tree-sitter builds concrete syntax trees and queries can select node types ([Tree-sitter introduction](https://tree-sitter.github.io/tree-sitter/), [query syntax](https://tree-sitter.github.io/tree-sitter/using-parsers/queries/1-syntax.html)). The PowerShell adapter is **very likely (80-90%)** to distinguish the two recorded `Set-Content` incidents because a here-string/string argument and a `Remove-Item` command are different AST node roles; evidence is the recorded outer verb (`INPUT-known-harness-defects.md:14-18`) and PowerShell’s exposed parser premise, which remains to be host-verified. The Bash adapter’s deployment feasibility is **roughly even (45-55%)** until the Windows dependency probe runs.

### Proposal 4 — Markdown/source directive grammar (**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**)

Replace weak prose words with explicit constructs:

* `.md/.mdx`: unchecked task items are work; fenced code regions are delegated to a source scanner; paragraphs/tables/blockquotes/inline code are not ledger work.
* `.py`: tokenize comments for exact TODO/FIXME directives and use `ast` for placeholder bodies where parseable.
* other source types: retain exact directive comments by extension/comment grammar; weak phrases remain shadow-only until language parsing exists.

The first migration may use a bounded CommonMark fence/block tokenizer rather than a full Markdown dependency, but its fixtures must come from the CommonMark spec. It is **very likely (80-90%)** to silence all six recorded stub-ledger incidents because all are Markdown prose/negation/quoted evidence, while the retained known-positive is a real Python TODO/pass body (`stub-ledger/test_stub_ledger.py:86-129`).

### Proposal 5 — Credential source-to-sink gate (**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**)

Keep `redact_text` for persistence, remove global `contains_secret(serialized_input) -> block`, and recognize only same-event exfiltration:

* source: exact credential path argument or literal-secret node;
* sink: executable network/upload/email/message command, or an MCP field documented as outbound content/local upload;
* active only when source reaches sink in the parsed command/tool schema;
* sensitive source without sink -> allow/ask according to native file permission profile;
* unknown mixed command -> ASK in unattended/bypass mode, advisory in interactive mode.

This proposal is **likely (55-80%)** to restore useful security coverage with far fewer false blocks because the observed false shapes have a source-like token but no demonstrated sink, and audit F02 independently recommends narrowing to outbound sinks (`inputs/audit-findings/F02.md:23-29`). UNVERIFIED: coverage of multi-step exfiltration split across separate tool calls. The settling experiment is a red-team suite with single-call and two-call read/egress sequences; if cross-call coverage is required, use the existing per-turn ledger with a short-lived taint bit rather than introducing durable execution or a new memory service.

### Proposal 6 — Shadow migration and reason-code telemetry (**CONFIG (settings/JSON only)**)

Wire the new discriminator in shadow mode before enforcement. For every legacy decision record `{legacy_verdict, new_verdict, reason_code, detector, tool_family}` without raw content. Promote per detector only after replaying the recorded false fixtures and known-positive controls, then observing a bounded live window with adjudicated samples.

It is **very likely (80-90%)** that reason codes make future regressions diagnosable because the current corpus can count block messages but cannot tell which field/role produced them (`inputs/corpus.json:5336-5345,6743-6751`; broken hook section is explicitly excluded). Existing shared staging already supports OFF/SHADOW/ADVISE/ENFORCE and shadow reason codes (`agents/harness/modules.py:118-143,311-417`), so this proposal is configuration of an existing mechanism, not another observability system.

## Regression suite design

### Suite architecture

Create one table-driven fixture file consumed by every migrated detector. Each row contains:

```json
{
  "id": "SENT-KEY-FALSE-001",
  "event": "PostToolUse",
  "tool_name": "mcp__databricks__...",
  "input": {},
```

The invariant is: changing only representational role must change the verdict exactly where the policy’s eligible-role contract says it should. This suite is **very likely (80-90%)** to catch future keyword regressions because it systematically crosses token and role instead of adding one test per bug; evidence is that the five detector families fail on four distinct role boundaries despite different keywords.

### Property checks

* **No serialized-event scanning:** monkeypatch/spy the serializer and fail if a detector invokes it for policy matching.
* **Key/value separation:** arbitrary JSON keys never influence result status; toggling a recognized boolean value may.
* **Failure dominance:** adding an explicit failure sibling cannot turn FAILED into SUCCESS.
* **HTTP/process separation:** 2xx HTTP codes are not process exit codes.
* **Mention invariance:** inserting a dangerous token into prose/data/comment regions cannot change ALLOW/SUCCESS.
* **Parse uncertainty:** malformed shell/document input yields UNKNOWN with a reason, never an unsupported “safe” or “dangerous” claim.
* **Known-positive controls:** actual recursive delete, real source TODO/pass body, explicit MCP `isError:true`, exact terminal marker, and source-to-outbound-sink credential flow remain detectable.
* **Round-trip:** provider adapters preserve tool name, selected field, target path, structured result values, and event kind into `OccurrenceContext`.

## Anti-overfit gate

All counted proposals ride the existing hook/dispatcher/receipt bus. None introduces a second orchestration runtime, vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, or external guardrail framework.

Rejected alternatives:

1. **More regex exceptions.** Rejected because “stub” -> “test double” -> “placeholder” produced repeated false matches and because key/value and HTTP/exit failures are not lexical-negation problems (`INPUT-known-harness-defects.md:39-41,65-72`).
2. **A model-based use/mention classifier.** Rejected as a trained/LLM critic on a deterministic hot path: it adds latency, nondeterminism, and another false-positive surface when native structure already settles the recorded cases.
3. **One full multi-language parsing service.** Rejected as BUILD-LARGE and a second runtime. Use native/available parsers only at the two shell adapters; default unknown rather than building a parser platform.
4. **Disable all guards.** Rejected because the sentinel, destructive-command, and credential lanes cover real high-damage failures. The problem is mistyped evidence, not lack of need.
5. **General natural-language negation detection.** Rejected because exact role contracts eliminate the need for broad NLP in the recorded cases and avoid brittle scope rules (“not only,” double negation, quotations).

## Final recommendation

Adopt the typed occurrence boundary and migrate in expected-damage order: native failure event plus fail-dominant receipt classification first, then stub/marker roles, then shell AST and credential source-to-sink policy. Do not implement a universal “smart regex,” and do not wait for a BUILD-LARGE framework.

The strongest design invariant is simple enough to review mechanically:

> A detector may match only fields and roles declared by its contract; serialized events, arbitrary keys, prose regions, and unparsed unknowns are never silently promoted to active occurrences.

This is **very likely (80-90%)** to prevent recurrence across new guards because new detectors inherit a closed set of eligible semantic roles and must supply positive/mention metamorphic pairs before promotion. Evidence: five independently written detector families converged on the same flattening error, while the current partial field gate already fixes non-shell Write/Edit payloads (`agents/harness/tests/test_modules.py:212-250`). Remaining uncertainty is concentrated in shell AST availability and raw-fixture recovery, with explicit experiments above.
