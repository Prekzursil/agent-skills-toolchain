# H06 — Summarising without burying the lede

**Unit:** H06, partner-dimension / communication and human-likeness  
**Question:** Put the correction or material risk first, never in paragraph four; audit real assistant messages and design the check.  
**Date:** 2026-07-19  
**Scope:** read-only analysis of the supplied Linux bundle; this file is the only write.

## Executive lede

**Correction first:** the supplied `corpus.json` does **not** contain assistant response bodies, so a defensible retrospective rate or set of real lede-burying examples cannot be produced from this artifact. Calling its 2,268 recall-biased owner-message candidates “assistant messages” would invert the schema and repeat the detector error this program is meant to stop. The corpus itself says samples are capped (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`), labels the correction detector recall-biased with a 41/41 false-positive smoke sample (`corpus.json:10371-10374`), and represents sessions with file metadata rather than messages (`corpus.json:13868-13877`; another metadata-only example is at `corpus.json:15981-15987`).

Two mechanically independent signals establish that limitation, after proving both detectors on known-present controls:

1. A recursive JSON-schema walk found the known-present `owner_correction_candidates.samples[].text` bodies, but found no `role` values and no assistant/message/content body path outside those owner-candidate `text` fields. The same walk found the six known-present session fields `file, kind, lines, mb, first_ts, last_ts`, proving it was traversing session objects rather than an empty document.
2. `rg` found the known-present owner sample “Call the tool b3_probe_gamma…” at `corpus.json:10865-10873`, while a separate search for `"role":"assistant"`, `assistant_message`, and `last_assistant_message` returned no match. This second detector is demonstrably capable of finding a known body string and is independent of the schema walk.

The missing Windows raw transcript root is `C:\Users\Prekzursil\.claude\projects`, named by the distillation at `corpus.json:3`; it is not present on this Linux node. **GAP:** the requested real-message audit therefore remains **UNVERIFIED; the settling experiment is Finding 1’s privacy-safe raw-transcript export followed by the blinded annotation protocol.** This is a data-availability boundary, not evidence that lede-burying is absent.

The best design is not another generic writing reminder. It is a small, externally grounded **critical-information channel** folded into the existing consolidated Stop bus: typed receipts from owner corrections, tool failures, and unresolved blocking threads determine what is load-bearing; a fresh-context checker compares those receipts with only the response lede; and the existing event ledger plus owner next-turn behavior measure misses and nuisance. It adds **zero top-level hooks**, fails open, never trusts same-context self-review, and does not create a second runtime or memory store.

The value claim is **very likely (80-90%)**, because (a) the owner made lede priority an explicit task, (b) locally observed single-detector and use-versus-mention failures make a naïve prose lint unsafe (`INPUT-known-harness-defects.md:9-22,52-82,111-129`), and (c) current field evidence finds workflow-boundary proactive messages receive more engagement and require less interpretation than mid-task interventions (Kuo et al., IUI 2026, https://doi.org/10.1145/3742413.3789148). The exact local effect size is **UNVERIFIED; the settling experiment is the shadow and stepped-wedge evaluation in Finding 8.**

## Design invariants and acceptance contract

The check’s unit of truth is a **receipt**, never the assistant’s opinion of its prose. A receipt is a small typed record with `kind`, `severity`, `source_event_id`, `source_locator`, `state`, and `owner_action_needed`. Allowed sources are: an owner correction turn; a tool execution result; an event-ledger failure/milestone/open-loop event; a task state transition; or a fresh-context verifier verdict. A sentence merely containing a scary word is not a receipt.

“Lede” means the first non-heading prose block, capped at the smaller of 80 words or 600 characters. The initial default is intentionally testable, not claimed optimal. A material receipt is covered when that block states its changed truth/risk and the immediate consequence or next action. Evidence and chronology may follow. If no correction, material risk, blocker, or changed completion state exists, the check stays silent.

The rollout acceptance contract is:

- zero new top-level hook invocations; fold one check entry into the existing local Stop dispatcher or extend the shared Stop module;
- all exceptions, missing transcripts, model timeouts, malformed receipts, and store errors exit 0 and emit nothing;
- `stop_hook_active` suppresses continuation loops;
- no owner prompt, confirmation, or extra question is generated by the checker;
- no keyword-only verdict and no same-context self-critique;
- every “miss” label names an external receipt and the response span where it should have appeared;
- every “pass” in evaluation requires a known-positive and known-negative control plus an independently labelled held-out pair;
- “never drop a thread” is enforced by the existing open-loop/event-ledger identity, not by asking the model to remember;
- shadow mode precedes any visible intervention; visible intervention remains a single compact correction, not a stack of detector nags.

## Findings — inferred surprises first

**What it is:** An offline exporter that joins each real owner turn to the next final assistant text plus typed nearby tool/ledger events. It outputs hashes/locators, first paragraph, full-response paragraph boundaries, preceding owner text, and redacted receipts—not secrets or entire 10.62 GB transcripts. Stratify by: owner-correction-like turn, preceding failed tool, unresolved ledger failure, completion claim, response length, and ordinary negative controls. Sample at least 200 pairs for development and 200 held out; oversample rare high-impact risks but report prevalence-weighted metrics.

**Why inferred:** The owner asked for real-message auditing, but the provided artifact preserves only capped owner-candidate text and session metadata. The correction candidate stream is unsafe as ground truth because its own smoke sample was 41/41 false positive (`corpus.json:10371-10374`). The owner’s insistence on grounding and detector controls implies that admitting “not measurable yet” is preferable to synthetic certainty.

**How to build:** Add an offline `export_lede_pairs.py` beside the existing corpus miner, not in a live hook. Parse transcript role/content using the already proven shapes in `truth-verify/check.py:68-127`; identify the next terminal assistant text; join tool events since the last human turn; join ledger events by session/project/time; redact credential-like spans and cap text. The known-positive control is a hand-built fixture where a correction is in paragraph four; the known-negative control mentions “risk” in quoted prose but has no receipt. **UNVERIFIED whether the remote owner will permit a raw-message export; the settling experiment is a read-only 20-file dry run on the Windows box that reports only schema/counts and five owner-approved redacted pairs.**

**SOTA:** Potluri et al. evaluate concise QA summaries with human annotations and release a 1,000-answer dataset, supporting a human-labelled rather than self-scored evaluation plane (ACL 2023, https://aclanthology.org/2023.acl-long.541/). ### Finding 2 — Compile a “critical receipt” before judging prose, so the checker knows what deserves the lede

**Improvement:** Replace generic “be concise / lead with risk” prompting with a deterministic priority input assembled from external state.

**What it is:** At Stop, build at most one lede obligation from receipts in this order: `(1) owner correction that changes the working truth; (2) safety/data-loss/security risk; (3) blocker or failed requested outcome; (4) incomplete/open thread that invalidates “done”; (5) completion outcome; (6) ordinary summary`. Within a class, prefer higher severity and more recent non-superseded state. The assistant cannot promote its favorite accomplishment over an owner correction because the priority is computed outside its context.

**Why inferred:** The exact owner requirement is about salience, not merely length. Local live defects show that prose-only scanners confuse mention with use and can corrupt the agent’s state (`INPUT-known-harness-defects.md:52-82`). The event ledger already separates objective events from narrative summaries (`claude/AGENTS.md:28-34`), which is the right substrate for salience.

**How to build:** Extend the existing shared Stop projection or add one `lede-priority` check entry to the local Stop manifest—**folded into the existing dispatcher, not a new hook**. Implement a pure `select_receipt(events) -> receipt|None`. Owner correction receipts originate from a typed UserPromptSubmit classifier only after a fresh-context classifier agrees that the owner is revising a prior assertion or priority; tool risks originate from actual nonzero/error outcomes; open-thread receipts originate from non-superseded ledger/open-loop IDs. Store only receipt ID/type/severity/source locator. Emit nothing in shadow mode. Test ordering permutations, supersession, quoted prose, negation, successful results containing failure-like field names, and empty/malformed input.

**External signal that verifies it:** The selected item must equal the independently labelled highest-priority receipt in the held-out set, and its source locator must resolve to an owner turn, execution result, or ledger event. Known-positive controls include the live `"user_cancelled_or_timedout": false` case, which must remain non-risk because the result was `ok: true` (`INPUT-known-harness-defects.md:63-72`).

**SOTA:** Vicente and Matute’s three 2026 experiments found that framing information as AI error risk, rather than accuracy, reduced following incorrect recommendations and bias acquisition (https://doi.org/10.1186/s41235-026-00726-w). NIST says monitoring should weight failures by harm and prioritize negative impacts (https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/).

**Confidence:** **very likely (80-90%)** that receipt-first prioritization produces fewer false alarms than lexical lint, because the four locally observed failures all arose from ignoring semantic role/value and the proposed controls key from execution/event type. **likely (55-80%)** that a six-class order generalizes across this owner’s work; evidence is the explicit owner brief plus the event types already present, but the ordering is **UNVERIFIED; the settling experiment is blinded owner ranking of 30 conflicting-receipt pairs.**

**Tag:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.  
**Value × effort:** **transformative × medium**.  
**Novelty:** **inferred-surprise**.  
**Autonomy:** **just-do-it** in shadow mode; visible enforcement follows Finding 8’s gate.

### Finding 3 — Use a fresh-context entailment judge only on receipt-bearing turns; never let the writer grade itself

**Improvement:** Detect semantic lede burial without reintroducing the known keyword false-positive class.

**What it is:** A bounded second-context adjudicator receives only: the typed critical receipt, the first prose block, and a strict schema: `covered`, `changed_truth`, `consequence_or_action`, `evidence_span`, `reason_code`. It never sees the rest of the authoring conversation and cannot rewrite. A cheap deterministic prefilter invokes it only when a critical receipt exists and the lede is nonempty. Its verdict is advisory/shadow until held-out precision is established.

**Why inferred:** Same-context self-correction is forbidden by this unit’s law and contradicted by the live record of six wrong conclusions plus a seventh detector-control incident (`INPUT-known-harness-defects.md:111-129`). Yet a keyword checker cannot understand whether “no risk remains” covers or merely mentions a risk. The existing harness already uses a separate Codex channel and the corpus records 47 `mcp__codex__codex` calls (`corpus.json:13515`); the concrete configured tools are allowed at `claude/settings.json:27-30`, so this does not require a new orchestration service.

**How to build:** Add a small adapter called by the existing Stop check. Prefer an already-running second-provider/fresh-context tool with a 1–2 second budget and a closed JSON schema; if unavailable or malformed, log `judge_unavailable` and exit 0. Hash prompt/version/model and attach the receipt locator. Never pass full transcripts. Require a literal evidence span from the lede, then mechanically verify that span exists before accepting `covered=true`. Cache by `(receipt_hash, lede_hash, judge_version)`. Do not ask the authoring model to “reconsider” unless the external judge returns a high-confidence miss; the continuation message should name the missed receipt and request one compact first-paragraph correction. **UNVERIFIED whether an existing second-provider call can reliably complete inside the current 35-second Stop budget; the settling experiment is 100 shadow calls measuring p50/p95 latency, timeout rate, schema validity, and cost.**

**External signal that verifies it:** A different model/context supplies the semantic verdict; a deterministic span checker supplies a mechanically independent second signal; held-out human annotation supplies the final precision/recall signal. No completion claim rests on self-review.

**SOTA:** Behzad et al. find that communicating model strengths/weaknesses improves team performance and trust calibration (2026, https://doi.org/10.1007/978-3-032-13187-4_8). Li et al. show both overconfident and underconfident AI impair collaboration, so the judge must test calibrated coverage rather than reward maximal alarm (https://arxiv.org/abs/2402.07632).

**Confidence:** **likely (55-80%)** that a receipt-conditioned fresh judge outperforms rules alone, because the task is narrow entailment and has an external source of truth; exact gain is **UNVERIFIED; the settling experiment is a paired comparison against deterministic-only and writer-self-critique baselines on Finding 1’s held-out set.** **very likely (80-90%)** that conditional invocation has lower latency/cost than judging every response, because only receipt-bearing turns invoke it by construction.

**Tag:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — an adapter on the existing Stop and second-provider buses, not a daemon.  
**Value × effort:** **high × medium**.  
**Novelty:** **inferred-surprise**.  
**Autonomy:** **confirm-first** before enabling a paid/remote judge; shadow fixtures and local adapter work are **just-do-it**.

### Finding 4 — Make “changed truth → consequence → action” the first-block contract, not a ceremonial TL;DR

**Improvement:** Give corrections and risks a minimal, actionable shape that cannot be satisfied by burying the substance under a heading.

**What it is:** When a critical receipt exists, the first block must communicate three slots in natural prose: **what changed or is at risk**, **why it matters now**, and **what happens next / what the owner must decide**. Example: “Correction: the export did not complete; 37 files remain because the API timed out. I have preserved the partial output and the next safe action is to resume from cursor X.” A bare `TL;DR`, “there are some risks,” apology, or chronology does not cover the receipt.

**Why inferred:** The owner explicitly says “the correction or risk goes first,” while prompt fatigue makes a long mandatory template a regression. A three-slot block preserves human conversational flow and actionability without making every response look like an incident report.

**How to build:** Add the contract as a short CONFIG rule and as rubric fields in Finding 3; do not add another detector. Cap the block rather than the whole answer. Skip labels on ordinary turns; allow “Correction:” or “Risk:” only when a corresponding receipt exists. For completion, first state outcome and any material limitation, then evidence. Regression fixtures include apology-first, success-first-then-risk, chronology-first, quoted-risk prose, true correction-first, and no-receipt conversational answers.

**External signal that verifies it:** Receipt-to-span entailment from the fresh judge plus the mechanical presence of all three rubric fields; owner next-turn behavior distinguishes whether action was understood (e.g., immediately acts/answers versus asks “so did it work?”). The owner’s answer is an external signal, not assumed satisfaction.

**SOTA:** Potluri et al. found that many long-form answers can be adequately compressed, while complex/implicit answers are harder and benefit from decontextualized extracts (https://aclanthology.org/2023.acl-long.541/). “Lost in the Middle” demonstrates strong position effects for relevant information in long model contexts, supporting explicit positional evaluation rather than mere inclusion (https://arxiv.org/abs/2307.03172). This second citation concerns model readers, not humans; applying it to owner-facing prose is an inference, not direct human evidence.

**Confidence:** **very likely (80-90%)** that this contract catches “paragraph four” failures better than “include a summary,” because position and semantic slots are explicit. **likely (55-80%)** that three slots are the right cognitive-load point; evidence is the owner’s lede instruction and concise-answer research, but the optimum is **UNVERIFIED; the settling experiment is owner-ranked A/B/C variants with one-, three-, and five-slot ledes on 20 real examples.**

**Tag:** **CONFIG (settings/JSON only)** for the response contract; its verification is provided by the adapter in Finding 3.  
**Value × effort:** **high × low**.  
**Novelty:** **user-asked**.  
**Autonomy:** **just-do-it** after the shadow scorer meets Finding 8’s precision gate.

### Finding 5 — Use progressive disclosure: one-screen truth first, evidence second, chronology last

**Improvement:** Preserve exhaustive technical detail without forcing the owner to excavate the outcome.

**What it is:** A response has up to three layers: (1) a self-contained lede; (2) compact evidence/changes and verification; (3) deeper chronology, alternatives, and gaps only when the task warrants it. The first layer must stand alone if the owner reads nothing else. This is not an automatic summarizer and does not replace the ledger; it is response composition.

**Why inferred:** The owner requests exhaustive research artifacts but also says prompt fatigue tracks focus. Those requirements are compatible only if information is layered. The corpus demonstrates extremely long, tool-heavy work at scale, while its own distillation uses capped samples and metadata, illustrating the usefulness—and danger—of intentional compression (`corpus.json:2-11`).

**How to build:** CONFIG the default response shape for long/research/build handoffs: maximum one short lede paragraph; then “Evidence / Changes / Verification”; then “Details / Gaps” only if useful. Do not require headings for short answers. The checker evaluates only the first layer against the receipt, so extra detail cannot buy a pass. Preserve raw evidence locators in the ledger/artifact rather than copying it all into chat. Use response-length buckets learned in Finding 8, never a universal word quota.

**External signal that verifies it:** Held-out human labels test lede sufficiency with layer 2/3 hidden; then reveal full text and test factual completeness. Owner follow-up categories (“what happened?”, “what remains?”, action taken, no clarification) measure whether layering reduced excavation without dropping content.

**SOTA:** Potluri et al.’s human study supports multiple answer granularities and finds over 90% of ELI5 long-form answers adequately summarizable by at least one tested system, while warning that complex implicit answers remain challenging (https://aclanthology.org/2023.acl-long.541/). This supports layered evaluation, not blind truncation.

**Confidence:** **likely (55-80%)** that layered responses reduce owner search effort while retaining audit depth, based on the explicit competing owner constraints and human-evaluated concise-answer evidence. The local cognitive-load reduction is **UNVERIFIED; the settling experiment is a randomized comparison measuring clarification turns, time-to-correct-action, and owner preference on matched outputs.**

**Tag:** **CONFIG (settings/JSON only)**.  
**Value × effort:** **high × low**.  
**Novelty:** **user-asked**.  
**Autonomy:** **just-do-it**.

### Finding 6 — Put the blocking open thread in the lede and carry its stable ID; never trust a prose recap to remember it

**Improvement:** Connect lede priority to the existing never-drop-a-thread machinery.

**What it is:** If an open thread blocks completion or requires owner action, its stable ledger/open-loop ID becomes a critical receipt. The first block names it and its state. Nonblocking threads remain in a bounded “Still open” tail with IDs. A response cannot say “done” while a non-superseded blocking ID exists unless it says what remains in the lede.

**Why inferred:** “Never drop a thread” is a hard owner constraint, and a beautifully written summary still fails if it omits a discussed commitment. The local open-loop system already distinguishes contextual, standing, and ledger loops and caps resurfacing (`open-loops/resurface.py:4-15,69-95`); the missing improvement is binding blocking state to outgoing-message priority, not another memory store.

**How to build:** Extend existing loop records with optional `blocking`, `owner_action_needed`, and `source_event_id`; default old records to nonblocking. At Stop, join live blocking IDs into Finding 2’s receipt selector. The checker compares IDs/state with the lede and completion language. Closing or superseding a thread requires an external ledger event or owner instruction, not the assistant saying it is closed. Render at most three nonblocking tail items; persist the rest without nagging.

**External signal that verifies it:** Independent ledger state before/after the turn plus the owner’s explicit close/supersede action or an execution receipt. A chaos test injects a known blocking loop, asks for an unrelated summary, and confirms the checker identifies omission; a known nonblocking loop confirms silence.

**SOTA:** The 2026 interruption benchmark finds strong LLMs still struggle to adapt efficiently to updated intents in long-horizon tasks, making external state preferable to conversational memory alone (https://arxiv.org/abs/2604.00892). NIST recommends ongoing monitoring and human intervention where a system cannot detect or correct its own errors (https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/).

**Confidence:** **very likely (80-90%)** that stable-ID coverage reduces silent thread drops, because the check is a set comparison against existing external state rather than a generative recollection. **likely (55-80%)** that a three-item visible cap balances continuity and fatigue; the cap is **UNVERIFIED; the settling experiment is a replay of sessions with 1–10 open loops measuring omission, nuisance, and owner dismissal.**

**Tag:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — schema extension and join on the existing open-loop/event-ledger bus.  
**Value × effort:** **transformative × medium**.  
**Novelty:** **user-asked**.  
**Autonomy:** **just-do-it** in shadow mode; schema migration should preserve old rows.

### Finding 7 — Time communication at workflow boundaries and reserve interruption for imminent harm

**Improvement:** Make lede quality improve focus instead of creating another mid-task nag.

**What it is:** The lede checker runs at the response/Stop boundary. It does not interrupt tool work, ask the owner to restate priorities, or emit mid-task suggestions. Only an imminent irreversible risk belongs on a pre-action safety rail; this communication unit does not add one. Nonurgent insights wait for the final lede or existing open-loop resurfacing. Repeated visible lede corrections are gated through the existing calibrated-silence reaction model.

**Why inferred:** Prompt fatigue is a hard constraint, and the owner’s focus is part of system quality. Current field data on proactive developer assistance shows receptivity depends strongly on timing. Locally, the consolidated Stop dispatcher is already the response boundary (`settings.json:484-504`), and calibrated-silence already models nuisance from external next-turn reactions (`calibrated_silence.py:2-53`).

**How to build:** Mark `lede_miss` as one interjection type or reuse `nudge` with a subtype; pass current intervention density and recent owner dismissal. Emit at most one combined Stop correction even if multiple checks fire; the dispatcher already aggregates outputs (`_dispatch/dispatch.py:267-283,306-321`). Rank lede correction ahead of low-value style nudges. If the gate suppresses a visible correction, retain the shadow event for evaluation. Never suppress a genuine dangerous-operation guard; communication salience and safety authorization remain separate.

**External signal that verifies it:** Workflow event type (Stop/post-commit/task complete) is external to the response text; the next owner turn supplies acted/ignored/annoyed feedback; tool continuation and correction rates supply behavioral outcomes. A known workflow-boundary fixture and a mid-tool fixture validate timing classification.

**SOTA:** In a five-day field study of 15 developers and 229 interventions, post-commit interventions reached 52% engagement, mid-task interventions were dismissed 62% of the time, and well-timed proactive suggestions took 45.4 seconds to interpret versus 101.4 seconds for reactive suggestions (Kuo et al., IUI 2026, https://doi.org/10.1145/3742413.3789148). ProMemAssist similarly balances assistance value against interruption cost and reported more selective, higher-engagement assistance in a 12-person study (https://arxiv.org/abs/2507.21378).

**Confidence:** **very likely (80-90%)** that boundary-only communication is less disruptive than mid-task lede policing, based on direct developer field evidence and the existing Stop seam. **likely (55-80%)** that the current reaction model transfers cleanly to lede corrections; its external signal and fatigue logic already exist, but subtype calibration is **UNVERIFIED; the settling experiment is a shadow replay followed by a two-week capped live trial.**

**Tag:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — implement the subtype field and timing/ranking inside the existing reaction and Stop-dispatch paths; do not create a new hook.  
**Value × effort:** **high × low**.  
**Novelty:** **inferred-surprise**.  
**Autonomy:** **just-do-it** in shadow mode; visible notification policy is **confirm-first**.

### Finding 8 — Personalize the lede budget from owner behavior, and ship only after a dual miss/nuisance gate — **UNVERIFIED premise: enough clean owner reactions; experiment named below**

**What it is:** Maintain per-task-class response preferences such as lede word bucket (`<=30`, `31–60`, `61–90`), preferred explicit labels, and desired evidence density. ## Proposed checker algorithm (buildable reference)

This is deliberately a small bus extension, not a second orchestration runtime:

1. On `UserPromptSubmit`, the existing shared dispatcher records the owner event. A fresh-context classifier may propose `correction_receipt`; it is not trusted until its quoted owner span resolves and the schema validates.
2. Tool/Task/ledger events generate objective receipts from exit status, structured error/success, supersession, and open-thread state. Prose keywords never create a receipt.
3. At `Stop`, `select_receipt` chooses at most one lede obligation by severity/order. No receipt means silence.
4. Extract the first non-heading block from the final assistant text using the already proven transcript parser pattern in `truth-verify/check.py:68-152`.
5. Run deterministic checks: nonempty lede, bounded span, source ID available, quoted evidence-span validation. These checks may flag a candidate but cannot deliver the semantic verdict.
6. Invoke a different-context judge only for that candidate. It sees receipt + lede, not the full authoring context. Timeout/malformed/unavailable means fail-open and shadow `unknown`.
7. In shadow mode, append the receipt, hashes, verdict, latency, and later owner reaction to the existing event/reaction bus. Do not alter the response.
8. After Finding 8’s gates pass, emit one compact additional-context correction through the existing consolidated Stop response. `stop_hook_active` makes the second Stop silent. If provider semantics do not permit safe continuation, keep the system shadow-only and use CONFIG guidance; do not bolt on a new delivery runtime.

Pseudo-interface:

```text
receipt = select_receipt(external_events_since_last_human)
if receipt is None: PASS_SILENT
lede = first_prose_block(final_assistant_text, max_words=80, max_chars=600)
candidate = deterministic_candidate(receipt, lede)
if not candidate: PASS_SILENT
verdict = fresh_judge(receipt, lede, timeout=budget)
if verdict unavailable/malformed: PASS_SILENT + shadow_unknown
if verdict.covered and literal_span_exists(verdict.evidence_span, lede): PASS_SILENT
else: shadow_miss OR one aggregated fail-open Stop correction
```

The 80-word/600-character values are **UNVERIFIED defaults; the settling experiment is Finding 8’s bucketed preference trial.** They are parameters, not policy truths.

## Failure modes and rejected alternatives

1. **Same-context “check your lede before answering” as the only control — rejected by construction.** It violates the unit law and the local record of confident single-context errors (`INPUT-known-harness-defects.md:111-129`). CONFIG guidance is allowed only as composition help; the verdict remains external.
2. **Keyword lint for “risk/correction/error” — rejected.** It repeats the documented use-versus-mention, negation, and JSON-field defects (`INPUT-known-harness-defects.md:9-22,52-82`). Keywords may cheaply route a candidate only when a typed receipt already exists.
3. **Always call a large judge on every answer — rejected.** It adds latency/cost and would penalize ordinary conversation. Conditional receipt-bearing calls preserve the minimal architecture.
4. **Ask the owner “is this important?” every time — rejected.** It transfers classification work to the owner, violates prompt-fatigue, and reduces autonomy. Owner input is reserved for rollout policy, disputed labels, and raw-data approval.
5. **Create `communication-v2`, another memory database, or a separate observability service — rejected.** The Stop dispatcher, event ledger, open loops, truth-verification pattern, and calibrated-silence reaction ledger already provide the buses and state.
6. **Block Stop on every miss — rejected.** Lede order is not an irreversible danger; the local behavior contract says inject rather than block and fail open (`claude/AGENTS.md:64-70`). Visible correction is contingent on provider-safe continuation and measured precision.
7. **Force every answer into headings and fixed bullets — rejected.** That makes human-like dialogue mechanical and increases prompt fatigue. The semantic three-slot contract applies only when a critical receipt exists.
8. **Summarize away raw evidence — rejected.** The lede is navigation, not ground truth. Raw locators and objective receipts remain on the ledger/artifact bus.
9. **Treat owner silence as satisfaction — rejected.** Silence is `unknown`, not `acted`; explicit action, clarification, correction, or rating supplies the external learning label.
