# T019 — Competitive teardown: Lovable

**Unit:** T019  
**Research date:** 2026-07-19  
**Subject:** Lovable's agent harness, compared with the owner's Claude/Codex harness  
**Scope:** agent loop, context management, memory, tool/MCP handling, permissions, customization, multi-agent support, verification, and self-checking  
**Method:** current first-party Lovable documentation and first-party engineering posts, cross-checked against the unpacked subject tree and the pinned corpus/defects. No Lovable account or private source was available, so internal implementation details not disclosed by Lovable are explicitly UNVERIFIED.

## Executive judgment

Lovable is not a generally stronger agent harness than the owner's. It is a narrower, vertically integrated web-app-building product whose strongest ideas are disciplined **product surfaces around a small agent core**: separate read-only planning from mutation; serialize writes through one main agent; use read-only fresh-context subagents for discovery; keep always-on knowledge separate from on-demand skills; retrieve a small, curated failure resolution before the main loop; expose task/tool progress; and attach verification to the running preview. Its first-party docs describe the main loop as intent interpretation → codebase exploration → edits → issue resolution → summary, with Build mode owning execution end to end ([Build mode](https://docs.lovable.dev/features/agent-mode)).

The owner's harness is broader and more programmable. It has lifecycle hooks at SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, failure, compaction, subagent, task, and Stop events (`/local_disk0/codexwork/bundle/claude/settings.json:81-492`); 18 visible custom agent definitions in the bundle; cross-vendor Claude↔Codex fan-out and live-peer mechanisms (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:15-77`); a semantic memory MCP plus an objective event ledger (`/local_disk0/codexwork/bundle/claude/AGENTS.md:28-34,85-91`); and hundreds of installed skills/MCPs. The corpus shows actual use of 78 named skills, 22 agent types, and 93 MCP server names (`/local_disk0/codexwork/bundle/inputs/corpus.json:1`, `capability_use`). Lovable's public surface does not approach that raw extensibility.

The harness's problem is not missing machinery. It is that machinery's reliability, selection, and legibility. The corpus measures a dead Tavily MCP continuing to receive calls (532 calls, 25.8% errors, including 135 “not connected”), only 78 of roughly 355 installed skills ever invoked, and high failure rates in StructuredOutput (22.9%), Glob (13.3%), PowerShell (10.6%), and Bash (6.0%). The live defects also establish that hook telemetry is currently unmeasurable in transcripts and that several guards confuse mentioning text with executable action (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:1-162`). Lovable's best lesson is therefore **not “add more capabilities”; it is “make a small relevant set discoverable, permissioned, observable, and empirically prunable.”**

My overall assessment is **very likely (80-90%)** that evolving the existing harness with four small bus-level mechanisms is better than replacing it with a Lovable-like runtime. Evidence: the required native buses already exist in `settings.json`; memory, skills, subagents, browser tools, and MCP are already present and used in the corpus; Lovable's differentiators can mostly ride UserPromptSubmit, PostToolUse, Stop, and existing skills. The remaining uncertainty is whether the Windows-installed live tree differs materially from the unpacked snapshot; the settling experiment is to compare hashes and active settings on the Windows host before implementation.

The four worthwhile ports are:

1. a curated, measured “known resolution” injector over the existing memory/recall bus;
2. an agent-friction/vent event with rate limiting and trajectory pointers;
3. capability health/quarantine and per-capability policy metadata;
4. a verification receipt that records which independent checks actually ran and whether their evidence is fresh.

All four are BUILD-SMALL and pass the anti-overfit gate. None requires a second orchestration runtime, vector database/KG, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 1. Agent loop

### What Lovable concretely exposes

Lovable has two user-visible modes:

* **Plan mode** is read-only. It can inspect files, logs, and context, ask clarifying questions, compare approaches, and create an editable plan; it “never modifies your code.” Approval switches to Build mode, and the latest approved plan is persisted to `.lovable/plan.md` ([Plan mode](https://docs.lovable.dev/features/plan-mode)).
* **Build mode** is the single mutating loop. It interprets intent, explores code, applies coordinated edits, inspects logs/network activity, fetches external material, fixes issues, verifies, and returns diffs/summaries. The UI shows current task, modified files, tools, and progress ([Build mode](https://docs.lovable.dev/features/agent-mode)).
* Incoming user work is serialized through a visible prompt queue. Users can pause/resume, reorder, edit, remove, copy, and repeat a prompt up to 50 times. Lovable explicitly says it processes one task at a time ([Build mode — Prompt queue](https://docs.lovable.dev/features/agent-mode)).
* Stopping preserves edits already made; undo can revert to the prior state. This is checkpoint-like user control, but the docs do not describe transaction boundaries or atomic rollback.

Lovable's 2025 launch description gives the coarse loop: interpret request, explore codebase, uncover missing context, change files, auto-fix emerging issues, summarize ([Agent Mode beta](https://lovable.dev/blog/agent-mode-beta)). A 2026 infrastructure post adds that the agent generally explores and retrieves state on initial calls and uses prompt caching with short-window project-to-provider affinity ([Routing Billions of Tokens per Minute](https://lovable.dev/blog/routing-billions-of-tokens-per-minute)).

**UNVERIFIED:** the private loop's exact planner/executor state machine, termination test, retry budget, model routing rules, compaction algorithm, and rollback semantics are undisclosed. The experiment that settles this is a controlled Lovable project with instrumented prompts and repository commits: induce build, tool, test, and network failures; export every visible trajectory/diff; compare call ordering and retry counts across at least 30 matched runs. Until then, “ReAct,” “planner-executor,” or any exact architecture label would be invention.

### Comparison

The owner's loop has more programmable event interception and stricter written behavioral invariants. The behavior contract requires front-loaded clarification, an assumption ledger, goal reinjection, two-strikes pivot, structured handoffs, and evidence-calibrated claims (`AGENTS.md:7-83`). Lovable's public loop has a cleaner operator experience but fewer exposed invariants.

Lovable is better at:

* making the plan/mutate boundary explicit and visible;
* persisting the approved plan in the repo;
* serializing writes while still accepting queued intentions;
* making progress and tool selection inspectable without reading raw traces.

The owner is better at:

* hook-level interception before and after tools;
* explicit anti-loop/two-strikes behavior;
* cross-provider delegation;
* user-controlled specialist agents;
* terminal-state evidence contracts.

Lovable's prompt queue is **worse as an orchestration primitive** than the owner's parallel fan-out: it deliberately runs one user task at a time, while the owner can run independent Claude/Codex work in parallel. It is better only as a human-facing inbox.

### Ports

#### NATIVE (Claude Code already does this; we just enable it) — use native Plan mode for read-only investigation

Make Plan mode the default for ambiguous architecture/debug requests and switch to mutation only after the user approves the approach. This matches Lovable without new code. **Very likely (80-90%)** to reduce unwanted edits because Lovable's documented boundary and Claude's native permission mode enforce non-mutation independently; evidence is the product semantics, while the uncertainty is the owner's tolerance for an extra approval step. Settle with a 20-task crossover comparing owner corrections and reverted edits.

#### CONFIG (settings/JSON only) — persist approved plan as a small repo artifact only for long work

Add an instruction that long-horizon approved plans are written to a conventional `.agent/plan.md` (or the repository's existing plan location) and re-read before mutation. Do not create a plan file for routine work. **Likely (55-80%)** to improve resume/compaction continuity because Lovable makes the plan inspectable and the current harness already reinjects goals, but redundant plan artifacts can become stale. Settle with replay tests across compact/resume and score plan-to-diff divergence.

#### BUILD-LARGE (new daemon/service/runtime -- needs its own justification) — visible editable prompt queue — REJECT

A true cross-session queue with pause/reorder/repeat and UI needs a durable scheduler and operator surface. That is a second orchestration runtime, explicitly rejected by the anti-overfit gate. The owner's current task/background mechanisms already cover long operations and fan-out. **Very unlikely (5-20%)** that the productivity benefit would repay the reliability surface for a single owner; evidence is Lovable's queue being primarily collaboration UX and the owner's existing `longrun`/Task/Monitor contract (`AGENTS.md:41-49`). The settling experiment is a no-build paper log: for two weeks, record how often the owner actually needs reorderable pending prompts rather than a task list.

## 2. Context management

### Lovable's context layers

The documented sources form a clear hierarchy:

1. recent conversation and current prompt;
2. current project code, logs, and tool results read on demand;
3. workspace knowledge, always included;
4. project knowledge, always included and generally more specific;
5. root `AGENTS.md`/`CLAUDE.md`, with root `AGENTS.md` promised to be read regardless of session length;
6. on-demand skills selected by description or explicitly invoked;
7. connected-service/integration context;
8. explicit file (`@file`) and cross-project references;
9. subagent summaries returned into the main context rather than raw exploration traces.

Lovable documents workspace and project knowledge as separate 10,000-character plain-text fields. It warns that always-included instructions may be followed inconsistently in long conversations. Project knowledge is generally prioritized when it conflicts with workspace knowledge ([Knowledge](https://docs.lovable.dev/features/knowledge)). This warning is valuable honesty: inclusion is not enforcement.

Cross-project referencing can read file trees, source, chat history, assets, and implementation patterns from projects the user can access, but is read-only, same-workspace only, permission-aware, and can be disabled at workspace or project level ([Cross-project referencing](https://docs.lovable.dev/features/cross-project-referencing)). Large results may be truncated.

Subagents provide context isolation: each starts fresh, sees only its task briefing, cannot see the full chat automatically, and returns findings rather than its full work. Lovable says this keeps discovery noise out of the main window ([Subagents](https://docs.lovable.dev/features/subagents); [engineering announcement](https://lovable.dev/blog/subagents-in-lovable)).

### Comparison

The owner already has global and repo-scoped instructions, proactive semantic recall, compaction checkpoints, goal reinjection, and structured subagent handoffs. The owner's contract explicitly forbids feeding raw subagent output as prefix context (`AGENTS.md:59-62`), aligning with Lovable's summary boundary. The owner is more explicit about temporal validity (`CLAUDE.md:5-13`) and objective-versus-semantic memory (`AGENTS.md:85-91`).

Lovable is better at permission-aware, user-visible cross-project reference selection and at making the “always-on knowledge vs on-demand skill” distinction obvious. The owner's skill router does lexical IDF overlap across skills, agents, commands, memories, and MCP families (`hooks/skill-router/route.py:113-120,157-215`), which is more general but also one more bespoke routing layer with unmeasured precision.

Lovable is worse for deep technical work because its project boundary is product-controlled, references may truncate, existing repositories cannot be imported into Git sync, and the supported application stack is narrower. The owner's direct filesystem/repository tools do not impose a one-project/one-synced-branch abstraction.

### Ports

#### CONFIG (settings/JSON only) — formalize context tiers and budgets

Keep global rules minimal; place repo invariants in root `AGENTS.md`; load task workflows as skills; inject at most three compact memory hits; summarize subagent research into typed findings. Most of this exists; the port is to make it a single precedence/budget table and delete redundant copies. **Very likely (80-90%)** to reduce instruction collision because both Lovable's docs and the owner's own precedence contract identify specificity and context volume as load-bearing (`AGENTS.md:115-131`). Verify by measuring duplicated instruction tokens and conflict corrections before/after.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — permission-aware cross-repo reference helper

Add a skill that accepts `@repo`/path references, proves access with a known-positive file, uses read-only `rg`/`git show`, caps returned bytes, and emits a structured summary plus source paths. Do not add an index or vector store. **Likely (55-80%)** to improve deliberate reuse because Lovable demonstrates useful same-workspace reuse and the owner already works across many repos, but direct filesystem access may already be adequate. Settle with ten reuse tasks comparing time, wrong-repo reads, and copied-code regressions.

## 3. Memory and continuous learning

### Lovable has three different things called or functioning as memory

1. **User-authored persistent knowledge:** workspace and project knowledge, always injected ([Knowledge](https://docs.lovable.dev/features/knowledge)).
2. **Project history:** chat history and the latest approved plan; cross-project references can read relevant chat history ([Cross-project referencing](https://docs.lovable.dev/features/cross-project-referencing)).
3. **Platform-curated failure memory:** Lovable Stack Overflow (LSO), described in a first-party engineering post. An LSO entry has a retrieval description and a resolution body. Before the agent loop, a lightweight model classifies the recent conversation for stuckness, selects relevant human-reviewed entries, synthesizes a narrow knowledge file, and skips injection if nothing matches. Lovable reports an early version reduced stuck rates 5% and increased publish rate 2% on internal benchmarks. It continually A/B drops entries and removes neutral/harmful ones because stale and model-specific advice degraded the first version ([Vent/LSO engineering post](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool)).

LSO is Lovable's most portable frontier mechanism. The key is not retrieval alone; it is **curation, narrow synthesis, outcome measurement, stochastic dropout, and deletion**. Lovable explicitly found automatic frequent AI rewriting degenerates into “AI slop” and that knowledge goes stale.

### Comparison

The owner has a richer personal semantic store: `basic-memory` supports search/write/edit and temporal supersession, and corpus counts show 1,332 server uses, including 408 writes, 357 searches, 353 reads, and 156 edits. The recall injector already performs high-precision lexical selection, per-session dedup, at-most-three notes, and a calibrated-silence gate (`hooks/recall-inject/inject.py:1-23,44-50,203-260`).

The missing Lovable capability is **measured retirement**. The owner's memory system can supersede notes, but this snapshot does not show a mechanism that randomly withholds a retrieved note and attributes downstream success/stuckness to the injection. Absence claim scope: no such mechanism appears in the directly inspected recall injector, its design contract, or the corpus fields. **UNVERIFIED** across every installed plugin because the bundle omits most skill bodies; the settling experiment is an `rg` over the live Windows hook/skill tree for `dropout|ab_test|counterfactual|memory.*outcome` plus inspection of any hit.

### Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED: counterfactual curated-resolution injector

Extend the existing recall path, do not replace it:

* Only notes tagged `known-resolution` are eligible.
* Each entry has `trigger`, `resolution`, `valid_as_of`, affected model/tool/version, and one falsifiable success signal.
* On a high-confidence match, randomly withhold the entry in a small control fraction; log only entry ID, assignment, and session ID in the event ledger.
* At Stop, attach objective outcomes already available: same-error retry count, owner correction, terminal success/failure, and tool error fingerprint. Never infer success from the agent's prose.
* A weekly report retires stale/neutral/harmful entries; a human approves promotions and deletions.
* Inject the smallest synthesized excerpt, capped by bytes/tokens. Never load the whole memory note.

This recommendation is **likely (55-80%)** to reduce repeat failures. Evidence: Lovable reports controlled internal improvement; the owner has 5,692 error fingerprints and retry-loop data; the hook already exists. It remains UNVERIFIED because the live hook telemetry path is broken and causal attribution cannot work until D3 is fixed. The settling experiment is a four-week shadow A/B on the top ten stable error fingerprints with known-positive event controls. Stop if the confidence interval includes a material increase in correction or retry rate.

Anti-overfit: passes. It reuses basic-memory and the event ledger; no new vector DB/KG or learning daemon.

## 4. Tools and MCP

### Lovable's tool surface

Build mode visibly reports use of code search/read/edit, web fetch/search, logs/network inspection, image/video generation, tests, browser actions, and backend calls ([Build mode](https://docs.lovable.dev/features/agent-mode)). Subagents can search/read/browse but cannot mutate ([Subagents](https://docs.lovable.dev/features/subagents)).

Lovable calls MCP connections “chat connectors.” It offers prebuilt connectors and custom remote MCP servers on all plans. A custom server can use OAuth (default), bearer token/API key, or no authentication. MCP connections are per-user; Business/Enterprise admins can disable MCP globally or allow/deny individual servers ([MCP chat connectors](https://docs.lovable.dev/integrations/mcp-servers)). Some connector tools can make limited writes, such as updating tickets.

For application connectors, Lovable also operates a credential gateway: encrypted tokens cannot be read back by users, admins, or the agent; the project and agent receive opaque keys; OAuth refresh is handled behind the gateway; deletion revokes access; stable egress IP ranges can be allowlisted ([Integration security](https://docs.lovable.dev/integrations/security)). This app-runtime gateway is adjacent to, but not identical with, agent MCP.

### Comparison

The owner's tool breadth is much larger: 93 MCP server names were actually touched. This is an advantage only when healthy and discoverable. The measured dead Tavily calls prove an absent capability lifecycle: a broken connector remained selectable. The allow-list in `settings.json:26-63` also grants broad families, and `defaultMode` is `bypassPermissions` (`settings.json:64-75`).

Lovable is better at:

* per-user MCP identity;
* OAuth-first onboarding;
* workspace-level server disable controls;
* opaque credential brokering for app connectors;
* presenting a curated connector catalog rather than exposing an undifferentiated fleet.

The owner is better at:

* local stdio MCPs and specialist binary/science tooling;
* custom funnels and cross-vendor agents;
* tool-level hooks and preflight repair;
* avoiding a hosted vendor gateway and its trust boundary.

Lovable's docs do not describe health-based automatic MCP quarantine. It should therefore not be credited with solving the owner's dead-server defect. **UNVERIFIED** whether Lovable has an internal circuit breaker; settle by connecting a controlled MCP that alternates success, timeout, and “not connected,” then observing selection across repeated prompts.

### Ports

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — health-scored capability registry and quarantine

Add fields to the existing capability table: owner, transport, auth mode, mutability, last known-positive probe, consecutive failures, error fingerprint, cooldown, and enabled state. The router must exclude quarantined servers before the model sees them. A known-positive control must validate the detector, satisfying D2. After cooldown, permit one canary probe; success restores selection, failure extends cooldown. Make alias families collapse to one canonical backend to prevent Tavily duplicates.

This is **almost certain (90-99%)** to stop the exact dead-MCP retry class because exclusion occurs before selection and the corpus contains 135 “not connected” calls to the dead backend. It will not fix semantic failures from a healthy server. Verify by replaying recorded Tavily prompts against a fake failing server and asserting zero post-quarantine selections while a healthy control remains discoverable.

Anti-overfit: passes; it extends the current router/preflight bus, not a new service.

#### CONFIG (settings/JSON only) — capability policy metadata and least privilege

Split MCP permissions into read-only, mutating-with-confirmation, and prohibited-secret scopes. Default unknown MCPs to unavailable; explicitly enable only servers with a current known-positive probe. **Very likely (80-90%)** to reduce blast radius because Lovable's per-user/admin controls and the owner's current broad bypass setting provide independent evidence of the gap. The settling experiment is a dry-run policy report over one month of corpus calls: count calls that would change permission class and inspect false blocks before enforcement.

#### BUILD-LARGE (new daemon/service/runtime -- needs its own justification) — hosted opaque connector credential gateway — REJECT for this owner

Generalizing Lovable's gateway would require a secret broker, OAuth refresh service, egress policy, audit store, and availability engineering. That is BUILD-LARGE and resembles a new platform. **Unlikely (20-45%)** to improve a single-owner local harness enough to justify its attack surface; OS credential stores and MCP-native OAuth already cover most needs. Reconsider only if multiple untrusted users share connectors or apps require hosted runtime credentials. The settling experiment is a credential inventory proving at least three connectors currently expose refresh tokens to the model despite available native OAuth/keychain support.

## 5. Permission model

### Lovable's layers

Lovable combines several permission boundaries:

* Plan mode cannot change code; Build mode can.
* Only the main agent mutates; subagents are read-only.
* Cross-project references are read-only and limited to projects the user can access.
* MCP connections are per-user and inherit the external account's rights.
* Workspace/project roles control who can create skills, edit knowledge, connect repositories, and access projects.
* Project editor access and published-site access are independent; restricted projects can be limited to invited users ([Project access](https://docs.lovable.dev/features/project-visibility)).
* Security scans can be configured to block publishing with critical findings, although Lovable otherwise permits publishing with unresolved critical findings and warns against it ([Security overview](https://docs.lovable.dev/features/security)).

This is a product/workspace RBAC model, not a documented per-shell-command approval system. Public docs do not expose arbitrary shell access, user-authored allow/deny glob rules, or lifecycle permission callbacks. That public-surface conclusion is supported by the documentation index control described above, but hidden internals remain UNVERIFIED; a product test with destructive-looking file, dependency, database, and network operations would settle the actual prompts/blocks.

### Comparison

The owner's harness has finer tool/path rules and safety hooks, but its snapshot is materially less safe by default: `defaultMode: bypassPermissions`, `ask: []`, access to `C:` and `D:`, and broad Bash/PowerShell/MCP allows (`settings.json:26-75`). It does deny `.env`, PEM, and credential reads (`settings.json:64-68`) and has guards for force push, credential reads, file scope, tests, and dangerous operations (`settings.json:139-280`).

Lovable is better at a simple invariant: **research delegates cannot write**. The owner supports isolated agents/worktrees, but custom agents and cross-vendor paths have heterogeneous permissions, and the corpus records nine Write failures from agents attempting the shared checkout instead of their isolated worktree.

Lovable is worse in expert control: it hides shell-level permissions and offers fewer user-defined enforcement hooks. Its security scan can still be overridden unless an admin enables the stricter publishing rule.

### Ports

#### CONFIG (settings/JSON only) — remove blanket bypass and tier tools

Change the default from blanket bypass to ordinary permission evaluation; keep deterministic allows for read-only filesystem/search tools, ask for external writes and unknown MCP mutations, and block only irreversible/dangerous operations as the existing contract requires (`AGENTS.md:64-70`). **Very likely (80-90%)** to reduce accidental external mutation and secret exposure because the current setting mechanically bypasses prompts; evidence is direct config plus Lovable's narrower role/capability boundaries. It may increase friction, so settle with a one-week shadow policy that logs would-ask/would-block without enforcing.

#### NATIVE (Claude Code already does this; we just enable it) — read-only discovery subagents

Route exploration/research/review agents through native read-only isolation and reserve file mutation for the main owner agent or explicit implementation agents. **Very likely (80-90%)** to reduce concurrent-write conflicts because Lovable's design serializes mutation and the corpus already records shared-checkout/worktree errors. Verify with a stress suite of parallel agents trying to edit the same fixture; all delegate writes must be denied and the main agent must still succeed.

Do not copy Lovable's role hierarchy wholesale. This is a single-owner harness; workspace RBAC would be ceremonial complexity unless additional humans join.

## 6. Customization: rules, skills, hooks equivalents

### Lovable's supported surface

* **Knowledge** is always-on workspace/project plain text.
* **Skills** are on-demand markdown playbooks with name, trigger description, and instructions. They can auto-trigger or be invoked as `/skill-name`; admins can disable automatic use while preserving manual invocation.
* Skills follow the portable `SKILL.md` shape, can bundle files, import from public GitHub or ZIP, download, and can be drafted from a successful chat (“save that as a skill”). Admins/owners manage them; editors invoke/download; Enterprise logs skill changes ([Skills](https://docs.lovable.dev/features/skills)).
* Root `AGENTS.md` and `CLAUDE.md` are read as repository instructions; root `AGENTS.md` is promised to stay included regardless of session length ([Knowledge](https://docs.lovable.dev/features/knowledge)).
* MCP supplies external context/actions.

Lovable's public surface does not document user-authored lifecycle hooks, arbitrary executable skill scripts, custom agent definitions, or custom tool interception. The validated docs-index probe supports that narrow conclusion. **UNVERIFIED** whether Enterprise/private APIs expose additional callbacks; settle by obtaining the Enterprise API schema and searching for lifecycle/webhook/tool-policy endpoints.

### Comparison

The owner already has all of the open, code-native pieces Lovable lacks: executable hooks, custom agents, commands, portable skills, MCP, and repository rules. The owner is therefore decisively better on extensibility.

Lovable is better on governance and usability:

* one obvious place to manage skills;
* automatic vs manual toggle per skill;
* role restrictions;
* import validation;
* saving a successful interaction as a reviewed skill;
* audit trail for changes.

The corpus's 78-used/~355-installed ratio suggests that raw inventory is not translating into selection. The current lexical router is a useful attempt but its own output is merely “invoke if apt, else ignore” (`route.py:214-215`), and no precision/recall figures are present.

### Ports

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — skill registry with auto/manual/disabled state and receipts

Extend the current skill index with `mode: auto|manual|disabled`, owner, last validation time, known-positive trigger, known-negative trigger, invocation count, success receipt count, and supersession. Auto routing may only surface `auto`; explicit invocation can use `manual`; disabled skills never enter model context. Record the selected skill ID in the event ledger and expose a compact `skill status` report.

This is **very likely (80-90%)** to reduce irrelevant skill context and zombie inventory because selection state is enforced before prompting, and Lovable's same distinction is simple and legible. Evidence is the low observed coverage and the existing router/index. Verify every skill state with one known-positive and one known-negative control, then measure owner overrides and successful receipts.

#### NATIVE (Claude Code already does this; we just enable it) — reviewed “save this as a skill” workflow

Use the existing skill-creator capability after a successful interaction: extract only the reusable procedure, require the owner to approve its trigger and content, add fixtures, and publish through the existing skill directory. Do not automatically learn from every session. **Likely (55-80%)** to capture valuable workflows with less authoring cost; Lovable demonstrates the UX, while its engineering post warns that automated rewriting degenerates. Settle by tracking how many saved skills are invoked successfully within 60 days.

#### Do not copy: replace executable hooks with prompt-only skills

Lovable's simpler surface cannot enforce the owner's platform-specific invariants. Prompt-only rules would regress deterministic force-push, credential, file-scope, and verification checks. Preserve the hook bus, but reduce and test its occupants.

## 7. Multi-agent support

### Lovable

Lovable's main agent decides when to spawn temporary subagents. Several may run in parallel. Two documented types are generic research/review agents and “Explore,” which uses the most capable available model for evidence-traceable investigation. They can search files, inspect code, perform read-only lookups, browse the web, and review against the prompt. They start with fresh context, receive only a bounded briefing, cannot change files, do not communicate with each other, and report to the main agent. Activity cards show files, searches, tools, status, and findings ([Subagents](https://docs.lovable.dev/features/subagents)).

This is a star topology:

```text
                         +-- read-only subagent A --+
user -> serial main agent+-- read-only subagent B --+-> summarized findings -> main edits/verifies
                         +-- read-only Explore -----+
```

It is deliberately minimal and anti-overfit: parallelize context-heavy discovery, not mutation or peer coordination.

### Comparison

A debug agent monitors the stream; Lovable reports about 20% of vents warranted a mergeable PR and about 10 fixes/day, but auto-PR false positives hover around 50%. One agent emitted 43 recursive apology vents, leading to a hard cap of one vent per message. Lovable keeps human review and says automated eval gates/progressive rollouts are future work ([Vent/LSO post](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool)).

## 9. Git, rollback, and collaboration

Lovable automatically commits platform edits to a linked GitHub/GitLab repository and syncs commits from one selected branch back into the project. This gives nontechnical users backup and interoperability. However, it cannot import an existing repository; linking creates a new repo; one project maps to one repository and one active branch; reconnecting creates another new repository; moving/renaming may break sync ([Git sync](https://docs.lovable.dev/integrations/git-sync-overview)).

For this owner, Lovable is worse. The owner already works in real repositories, branches, worktrees, PRs, and CI without a proprietary mirror. Copying automatic two-way sync would add a failure-prone state reconciler and risks surprise commits.

#### NATIVE (Claude Code already does this; we just enable it) — keep native Git/worktree rollback

Use explicit diffs, commits/checkpoints when authorized, and worktree isolation. Do not build a Lovable-style sync layer. **Almost certain (90-99%)** that native Git remains superior for this expert owner because it supports arbitrary existing repos, branches, merge bases, and offline recovery; Lovable documents all four corresponding limitations.

## 11. Recommended implementation order

### Phase 0 — repair measurement before adding intelligence

1. Fix D3 by giving every hook invocation a durable JSONL record containing hook name, event, version, outcome, elapsed time, and a correlation ID linked to tool/session. Validate with one known-present hook and one deliberately absent hook.
2. Build regression fixtures for D1: prose mention, negation, JSON field name with `false`, real executable occurrence, and real tool failure. All guards consume structured verb/result fields first.
3. Do not use the corpus `hooks` section until its detector passes known-positive controls.

This phase is prerequisite. **Almost certain (90-99%)** that optimization without it will be unfalsifiable because the pinned defect explicitly says hook behavior across 1,964 sessions is currently unmeasurable.

### Phase 1 — capability health and verification receipt

Implement quarantine/canary selection and the PostToolUse/Stop receipt. These address the highest-confidence correctness/reliability gaps: dead MCP calls, false tool verdicts, stale verification, and unmeasured completion.

### Phase 2 — skill governance and curated-resolution experiment

Add auto/manual/disabled state and known-positive/negative fixtures. Then run the known-resolution injector only in shadow/control mode on a small set of stable fingerprints. Do not expand inventory during this phase.

### Phase 3 — agent friction event

Enable one-per-turn friction reports locally. Review clusters weekly. A report becomes a confirmed defect only after trajectory evidence plus an independent reproduction/probe. Do not send to Slack or open PRs automatically.

### Phase 4 — only then consider cross-repo reference UX

Build the bounded helper only if logs show repeated manual cross-repo lookup cost. It is useful, but lower leverage than reliability.

## Bottom line

Lovable's frontier contribution is a coherent minimal architecture, not a magical loop: one mutating agent, fresh read-only research delegates, narrowly selected context, visible state, permission-aware external data, and verification against a live artifact. The owner's harness already has the buses and more raw capability. Replacement would discard valuable hooks, specialist tools, cross-vendor work, and direct repository control.

The ambitious answer is therefore a **subtractive evolution**: retain the native core, make read-only delegation the default, quarantine unhealthy capabilities, turn verification into a fresh evidence receipt, and evaluate/prune retrieved knowledge and skills with real outcomes. **Very likely (80-90%)** this beats both the current sprawling configuration and a Lovable-style replacement for this owner; evidence is the corpus's concentration of failures and low capability utilization, the direct presence of all required buses, and Lovable's own empirical account that narrow curated retrieval plus aggressive pruning outperformed uncontrolled automatic memory growth. The settling experiment is a staged replay and four-week shadow deployment with predeclared metrics: dead-capability calls, same-fingerprint retries, owner corrections, false blocks, verification freshness, skill-selection precision, and terminal success receipts.
