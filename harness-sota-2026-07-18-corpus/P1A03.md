# P1A03 — corpus axis: read-before-write

## Question and answer

The question is whether the recurring Claude Code error

> `File has not been read yet. Read it first before writing to it.`

is a real safety feature or friction with no safety value, and how often the agent recovers versus abandons the intended write.

**Answer: keep the safety invariant, change the harness behavior around it, and do not remove it.** The feature has demonstrated safety value: in a decisive raw case, it stopped a whole-file `Write` to an existing YAML file; after reading the file, the agent discovered a pre-existing schema and replaced the overwrite with two surgical `Edit`s. At the same time, the current interaction is materially noisy: among 938 unique tool-use attempts reconstructed from raw transcripts, 725 (77.3%) read and then achieved a native same-path write, and 289 successful retries (30.8% of all unique attempts) repeated the exact same native tool input. Those 289 are direct evidence of a tax with no observable decision change.

The expensive tail is real as an *observed workflow interruption* but is not measurable as literal task abandonment from this corpus. A strict detector found 202/938 unique attempts (21.5%) with neither a later native same-path success nor a successful shell command containing the literal full target path. That is an upper bound on expensive abandonment, not a count of abandoned tasks. The raw transcripts contain counterexamples in which an apparent native-tool abandonment is actually completion through PowerShell. **UNVERIFIED whether any of the remaining 202 attempts abandoned the owner-level objective; the settling experiment is a stratified manual audit of those 202 attempts joined to parent-agent completion and final filesystem/git state.** It is **likely (55-80%)** that the true expensive-abandonment rate is below 21.5%, because the strict detector already recovered eight shell bypasses and misses variable-composed paths, relative paths, renamed outputs, and parent-agent completion.

The numerical headline supplied to this unit, “934 across Write+Edit,” is also slightly incomplete. The corpus records 939 error lines globally, attributes 568 to `Edit` and 366 to `Write` (934), and attributes five to tool `?`. Rejoining those five raw errors by `tool_use_id` resolves all five as one `Write` plus four `Edit`s; all five then read and succeeded. The true corpus axis is therefore 939 error lines, while the cleaner behavioral denominator is 938 unique tool-use IDs because transcript replay duplicated at least one error line. This report shows both facts rather than silently choosing the more convenient count.

## Scope

The only subject-side operations were reads. The only durable write is this artifact; the required event-ledger milestone was written by the harness's own `note.py` mechanism.

## Outcome definitions

The classifications are deliberately narrower than conversational terms such as “finished” or “abandoned”:

- **Read + native success:** a successful `Read` of the same normalized path occurs after the error and before a later successful `Write` or `Edit` on that path.
- **Native success without prior successful Read:** a later same-path `Write`/`Edit` succeeds, but the transcript has no successful same-path `Read` before it. This can occur because transcript ordering/replay is imperfect or because another action satisfied state.
- **Strict shell success:** no later native same-path write is present, but a later successful `Bash` or `PowerShell` tool input contains the full literal target path.
- **Read, no detected success:** a successful same-path Read exists, but neither a native same-path write nor strict shell success is found.
- **No detected success:** neither native same-path success nor strict full-path shell success is found.

“No detected success” is not called “abandonment.” The detector cannot see a command that constructs the path from variables, uses only a basename or relative path, writes a renamed target, delegates completion to a parent agent, or intentionally drops obsolete work after learning from the read. The direct PowerShell example below proves this distinction matters.

## Safety value versus friction

### Safety value is real, not hypothetical

The YAML case demonstrates actual overwrite prevention. The 48 `Write`→`Edit` transitions provide population-level corroboration: 48/367 unique failed `Write` attempts (13.1%) later succeeded first through `Edit`, meaning the agent changed from whole-file replacement semantics to targeted replacement semantics. Not every transition is necessarily safety-motivated, but the mechanism is exactly the one visible in the decisive YAML case.

It is **very likely (80-90%)** that removing the guard entirely would increase accidental overwrites of existing files; evidence is the concrete YAML counterfactual and 48 `Write`→`Edit` transitions. The band is below “almost certain” for the population-wide claim because the corpus does not execute counterfactual no-guard runs.

The guard also composes with the separate “file modified since read” check recorded elsewhere in the corpus (`corpus/corpus.json:8942-8945` for Edit and `corpus/corpus.json:9066-9069` for Write). Together they implement an optimistic-concurrency pattern: establish a snapshot, then reject stale mutations. That is a sound invariant for shared workspaces.

### Friction is also real and substantial

The guard produced at least:

- 289 exact retries after the failed call and intervening read;
- 725 canonical read/retry recoveries overall;
- eight directly detected shell bypass completions;
- 202 unique attempts whose completion is not observable under the strict detector.

The error is especially wasteful when the agent already inspected content using Grep, Bash `cat`, or another tool that native state does not count as `Read`. The `.claude.json` transcript explicitly says “Grep doesn't satisfy the gate” at line 5852. This is a demonstrated state-accounting mismatch in that case: Grep supplied content to the agent, while the native mutation tool did not recognize it as a qualifying Read.

The strict shell detector found 78 successful later shell commands containing the full target path across all unique attempts, but only eight were cases with no later native success. The other 70 co-occurred with native completion and therefore are not classified as bypass outcomes. This is why the report uses eight, not 78, in the outcome table.

### The corpus cannot answer literal abandonment

The distillation has counts and 12 capped sample file names, but no per-error successor events. Even raw same-transcript sequencing cannot prove owner-level abandonment because:

1. The detector does not follow subagent work into a parent transcript.
2. A later command can build the target path dynamically.
3. The detector does not treat a renamed or replacement target as the same path.
4. Reading can legitimately reveal that no write is needed.
5. Transcript replay/forking duplicates and reorders some events; the five unknown cases even have originating tool-use lines serialized after their error lines in the current raw file, although their IDs join correctly.

Accordingly, “202 no detected success” is the strongest evidence-supported statement. Any exact “202 abandoned” statement would violate the evidence contract.

## Recommendation

### 1. KEEP the existing-file safety invariant — NATIVE (Claude Code already does this; we just enable it)

Retain the requirement that a mutation of an existing file must be grounded in current file state, and retain stale-read rejection. Do not remove or globally bypass it.

Why:

- The existing YAML overwrite case demonstrates concrete prevented data loss.
- 48 `Write`→`Edit` transitions show the same safety-shaped adaptation at nontrivial scale.
- The workspace is shared by agents and external formatters, making stale or assumed file state materially risky.
- It is **very likely (80-90%)** that removal would trade a measurable workflow tax for increased overwrite risk; evidence is the prevented YAML overwrite, 48 `Write`→`Edit` transitions, and the shared-workspace setting.

This rides the native tool bus and introduces no second runtime, database, durable-execution layer, critic, SaaS, or guardrail framework. It passes the anti-overfit gate.

### 2. CHANGE first-attempt behavior: read before mutation — CONFIG (settings/JSON only)

Add one concise, high-priority harness rule at the provider instruction layer:

> Before the first native `Edit` or a `Write` that may target an existing file, issue native `Read` for the smallest sufficient region in the current session. Grep, shell `cat`, and prior-session knowledge do not satisfy Claude Code's mutation ledger. After a read-before-write rejection, do not switch to shell writing merely to evade the gate.

This converts most of the 725 read/retry sequences from “failed mutation → Read → retry” to “Read → mutation,” eliminating the failed tool turn while preserving the safety invariant. It is **very likely (80-90%)** to reduce this fingerprint materially; evidence is that 725/938 attempts already follow the required recovery path after the error. It is not “almost certain” because adherence to an instruction is model-dependent and some writes race with other actors.

Keep the rule short. A large workflow framework is not justified by a single native precondition.

### 3. CHANGE the fallback rule: never evade with shell writes — CONFIG (settings/JSON only)

When the native guard fires, require the agent to Read and retry natively unless the user explicitly asked for a shell-specific mechanism. The translation transcript shows the current failure mode: friction caused a direct PowerShell bypass, which discards native read-state and stale-write protections.

This is **likely (55-80%)** to reduce unsafe bypasses; evidence is the explicit “I'll use PowerShell” response and eight detected strict-path shell completions. The uncertainty reflects that some shell writes are legitimate and some bypasses use indirect paths not measured here.

### 4. UNVERIFIED — distinguish absent-path creation from existing-file overwrite before any product-level change

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** only if the controlled experiment below shows native `Write` rejects genuinely absent paths.

Run a matrix in a temporary directory:

1. `Test-Path` proves target absent; native `Write` without prior `Read`.
2. `Test-Path` proves target exists; native `Write` without prior `Read`.
3. Existing target after native `Read`; native `Write`.
4. Existing target modified externally after native `Read`; native `Write`.

The desired safety semantics are: allow (1), reject (2), allow (3), reject (4). **UNVERIFIED whether current Claude Code already behaves this way; this exact four-cell experiment settles it.** If only (1) is wrong, a small PreToolUse diagnostic can check path existence and inject precise guidance, but it must not authorize an existing-file shell overwrite. A hook's ability to satisfy Claude Code's internal read ledger is **UNVERIFIED; the settling experiment is a hook that reads the target followed by a native Write retry in a disposable file.**

Because these premises are unverified, no implementation is recommended yet. This report does not propose a daemon or alternate mutation runtime.

### 5. Do not build auto-read orchestration now

An auto-read hook sounds attractive but has two problems. Whether the native tool counts hook-side file I/O as a model-visible `Read` is **UNVERIFIED; the disposable-file hook experiment above settles it.** Silently hydrating arbitrary files also injects their content without an explicit model action and can consume the context budget. The small CONFIG rule captures most of the value with less machinery. A new orchestration runtime violates the anti-overfit gate and is not justified by this axis.

## Expected impact and how to verify it

After the CONFIG rule is deployed, measure the exact fingerprint for a fixed window and compare against a prior matched window using both rates:

1. Errors per 1,000 `Write`+`Edit` calls.
2. Errors per 1,000 unique tasks that perform a mutation.

Also track:

- `Write`→shell-write transitions after this error;
- whole-file `Write` attempts against existing files;
- stale-read rejections, which must not increase due to bypasses;
- task completion and latency, not only error suppression.

Success criterion: at least a 70% reduction in the fingerprint rate without an increase in shell write bypasses or stale-write errors. The 70% threshold is **likely (55-80%)** to be achievable because 77.3% of current unique attempts already recover through Read + native success, but it is a forward-looking estimate; the settling experiment is an A/B or before/after matched workload run.

## Alternatives considered

### Remove the read requirement

Rejected. It optimizes away one visible failure class by deleting the protection that prevented a real overwrite. That is metric gaming, not harness improvement.

### Treat Grep or shell `cat` as equivalent to Read

Not recommended locally without native support. Those tools expose content to the model but do not establish a guaranteed complete native file snapshot: their commands permit truncation, filtering, and transformation. Extending the native ledger to recognize cryptographically identified complete snapshots requires a product-level mechanism, not a small harness rule.

### Automatically retry the blocked mutation

Rejected. Retrying without exposing current content preserves neither safety nor agent reasoning. The useful operation is Read, reconsider, then mutate.

### Automatically read the whole file in a hook

Deferred. Ledger satisfaction is **UNVERIFIED; the disposable-file hook experiment above settles it.** Automatic whole-file hydration consumes context and hides the state transition from the model. The targeted native Read instruction is smaller and inspectable.

### Normalize everything to shell writes

Rejected. The raw translation case shows this “works,” but it bypasses both read-before-write and modified-since-read protections. It is worse harness design even if its immediate tool-call error rate is lower.

## Gaps

1. **UNVERIFIED task-level abandonment.** The corpus and strict raw detector cannot establish which of the residual 202 attempts failed the owner objective. Settling experiment: stratified manual review joined to parent transcripts, final filesystem state, and git diff.
2. **UNVERIFIED absent-path behavior.** One agent says a new file was blocked, but there was no pre-call `Test-Path` for that exact file. Settling experiment: the four-cell disposable-path matrix above.
3. **UNVERIFIED causal value of changed inputs.** The 439 changed native retries are consistent with learning from the Read but do not prove it. Settling experiment: diff failed/successful inputs against returned Read content on a random stratified sample.
4. Shell bypass count is a lower bound. The strict detector requires the literal full target path in a successful shell tool input. Variables, relative paths, aliases, and renamed targets are missed.
5. Transcript serialization is not a perfect causal order. Replayed blocks duplicate tool IDs, and some origin lines occur after result lines in raw file order. Joining by stable tool ID and deduplicating IDs reduces but does not eliminate this issue.
6. The current raw tree is live and has one more duplicated error line than the pinned corpus snapshot. Aggregate corpus counts remain the authoritative snapshot; unique-ID analysis is the behavioral view.

## Final verdict

The read-before-write check is a **real safety feature with poor current ergonomics**, not friction with zero safety value.

- **Keep** its existing-file and stale-state safety invariant.
- **Change** provider instructions so native Read precedes first mutation and shell fallback is prohibited as a mere bypass.
- **Do not remove** the guard.
- **Do not build** a second mutation/orchestration runtime.
- **Experiment before changing** absent-path creation semantics.

The best evidence-supported summary is: 77.3% of unique blocked attempts read and then succeeded natively; 78.5% have some directly observed same-target completion under a conservative detector; up to 21.5% have no detected completion, but literal abandonment is UNVERIFIED. The safety benefit is demonstrated by a prevented whole-file overwrite, while the friction is demonstrated by 289 exact retries and explicit migration to shell bypasses.
