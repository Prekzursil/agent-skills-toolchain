# X110 — Cross-domain borrow: reliability engineering → finite-context management

**Unit:** X110  
**Lens:** reliability engineering (FMEA/FMECA, fault trees, importance measures, redundancy/diversity, common-cause failure) applied to long-horizon context selection and eviction  
**Research date:** 2026-07-19  
**Scope discipline:** External research and design only. Per the unit brief, I did not inspect or characterize the local harness. Therefore this artifact makes no claim that a named local mechanism is present, absent, broken, or complete.

## Executive conclusion

The borrow transfers, but only in a deliberately narrow form.

The useful mechanism is **fault-tree minimal cut sets plus counterfactual importance measures, corrected for common-cause failure**. Reliability engineering starts from a precisely defined undesirable *top event*, decomposes it through Boolean relationships into combinations of basic failures, reduces those combinations to *minimal cut sets*, and uses importance/sensitivity measures to decide where scarce inspection, maintenance, or design resources matter most. It also refuses to count nominally redundant components as independent when one cause can defeat all of them. NASA's aerospace fault-tree handbook defines a minimal cut set as a combination sufficient for the top event in which every member is necessary; it defines Fussell–Vesely importance, Risk Reduction Worth (RRW), Risk Achievement Worth (RAW), and Birnbaum importance; and it warns that ignoring common-cause failure can significantly underestimate top-event probability ([NASA Fault Tree Handbook with Aerospace Applications, pp. 58, 90–91, 157–160](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

The concrete translation is a small **context failure-path guard**. For each active goal or imminent decision, the harness maintains a tiny typed dependency structure over already-existing context episodes. Before evicting an episode, a deterministic policy asks: “Would this removal complete a known minimal cut set for losing a required constraint, decision rationale, unresolved observation, or recovery path?” It also groups representations by provenance so that a raw observation and two summaries generated from that same observation/compressor are not falsely treated as three independent backups. Only episodes that remain outside every protected failure path are eviction candidates. Offline counterfactual replay—not invented online probabilities—then estimates how much task failure rises when each class of episode is forcibly unavailable.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The recommended first implementation is an ephemeral adjacency list plus a pre-compaction/pre-eviction hook and JSONL audit output. It is not a second orchestration runtime, vector database, knowledge graph, durable-execution system, trained critic, observability SaaS, or guardrail framework. The adjacency list is a per-session control structure, not semantic long-term memory.

**Verdict:** it is **very likely (80-90%)** that this guard would catch structurally predictable catastrophic evictions that recency, token size, or per-item “relevance” scoring misses. Evidence: minimal cut sets explicitly represent multi-failure combinations; RAW explicitly measures the effect of forcing an event to occur; and common-cause analysis explicitly corrects false independence among redundant copies (NASA handbook, cited above). This remains **UNVERIFIED for this harness; the settling experiment is the paired long-session replay and fault-injection protocol in §8**. I do **not** claim that it will improve aggregate task success until that experiment runs.

The analogy must stop there. MTBF is a poor eviction clock; FMEA risk-priority numbers are not trustworthy token scores; Boolean fault trees do not prove semantic sufficiency; and diversity does not mean “make more summaries.” These disanalogies are material, not caveats to wave away.

## 1. What reliability engineering solved in its own field

### 1.1 FMEA/FMECA: enumerate failure modes, trace effects, prioritize treatment

IEC 60812 describes FMEA as a systematic method for identifying how items or processes may fail, tracing local and global effects, optionally identifying causes, and prioritizing modes for treatment. When ranking includes at least consequence severity and often other importance measures, it becomes FMECA. IEC states that the method applies to hardware, software, processes, human action, and interfaces ([IEC 60812:2018 publication summary](https://webstore.iec.ch/en/publication/26359)). NASA describes software FMEA as bottom-up: examine how each component can fail, propagate that effect through the system, consider likelihood and severity, and identify detection and compensation methods ([NASA Software Engineering Handbook, “Software Failure Modes and Effects Analysis”](https://swehb.nasa.gov/pages/viewpage.action?pageId=103776712)).

The essential achievement is not the familiar severity × occurrence × detection arithmetic. It is the discipline of stating:

1. the function an item must perform;
2. each distinct way that function can fail;
3. the local and mission-level effect;
4. the cause, existing detection, and compensation;
5. the action and evidence needed to reduce the risk.

NASA's current GSFC handbook further treats FMECA as a **living risk assessment** updated as design, operations, and knowledge change ([GSFC-HDBK-8004, 2024](https://standards.nasa.gov/standard/GSFC/GSFC-HDBK-8004)). That “living” property matters to a changing task, although the full worksheet does not belong in every model turn.

### 1.2 Fault-tree analysis: reason about combinations, not isolated parts

Fault-tree analysis (FTA) proceeds top-down from a defined undesirable event. NASA's procedural summary says to define the top event and analytical boundary, develop the paths to initiating failures, and connect contributors with Boolean gates. Minimal cut sets are the smallest combinations of failures that cause the top event ([NASA NPR 8621.1, Appendix I-3.5](https://nodis3.gsfc.nasa.gov/displayCA.cfm?Internal_ID=N_PR_8621_0001_&page_name=AppdxI35)).

Formally, if the top event is

`T = A OR (B AND C)`,

then `{A}` and `{B,C}` are its minimal cut sets. `A` is a single-point failure. Neither `B` nor `C` is individually fatal, but losing both is. The NASA handbook explains that an n-component cut set requires all n members, and uses Boolean expansion plus absorption to remove non-minimal combinations ([NASA Fault Tree Handbook, pp. 157–160](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

This solves an allocation problem that per-component scores cannot: an individually low-ranked item may be indispensable because it is the last surviving member of a success path, while two individually high-ranked items may be redundant. Context eviction has exactly this combinatorial shape.

### 1.3 Importance measures: allocate finite resources by counterfactual consequence

The NASA handbook lists four relevant measures ([pp. 90–91](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)):

- **Fussell–Vesely importance:** the share of top-event probability contributed by cut sets containing an event.
- **Risk Reduction Worth (RRW):** how much top-event probability falls if that failure is assured not to occur.
- **Risk Achievement Worth (RAW):** how much top-event probability rises if that failure is forced to occur.
- **Birnbaum importance:** sensitivity of top-event probability to changing that basic-event probability, computed from the difference between forcing it to 1 and forcing it to 0.

The handbook explicitly connects importance measures to allocating finite testing, inspection, maintenance, upgrade, repair-time, and diagnostic resources. That is the direct source-field analogue for allocating tokens: retain or make recoverable the items whose forced absence most increases mission failure, rather than items that merely look salient in isolation.

### 1.4 Redundancy is not diversity; common causes defeat duplicate backups

Reliability calculations become dangerously optimistic when redundant components are assumed independent but share a design, environment, maintenance process, or other cause. NASA defines common-cause failures as two or more failures close in time due to a common cause and says neglecting them can significantly underestimate top-event probability ([Fault Tree Handbook, pp. 58–59](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). Its worked seal example shows three identical O-rings whose independent-failure calculation is overwhelmed by a common-cause term; the design then adds different seal types, geometry, and contamination mitigation rather than merely adding a fourth identical ring ([pp. 140–143](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

The U.S. NRC reaches the same operational conclusion through a mechanically different signal: actual operating experience found that inspection of one component often disclosed a condition also present in its redundant peer, and NRC calls common-cause failures a major concern in highly redundant systems ([NRC Regulatory Issue Summary 99-003](https://www.nrc.gov/reading-rm/doc-collections/gen-comm/reg-issues/1999/ri99003)). Thus the “redundancy can share a hidden cause” claim is supported by both a formal NASA model and NRC operating-event review, not by two repetitions of the same detector.

## 2. Translation: define context failure before scoring context

The unit's target is not “remember everything.” It is deciding what belongs in a finite working context and what may be evicted over a long horizon. The reliability translation begins by defining top events. A useful default set is:

- `T_goal`: at the next irreversible or expensive action, the agent cannot state the active user goal and acceptance condition.
- `T_constraint`: the agent acts without an applicable owner constraint, safety boundary, or explicit correction.
- `T_decision`: the agent cannot reconstruct a still-active decision and the evidence or rationale needed to apply/revise it.
- `T_observation`: an unresolved error, failed probe, contradictory result, or promised follow-up becomes unavailable before resolution.
- `T_recovery`: supposedly evicted information cannot be recovered at required fidelity when needed.

These are *availability* failures, not mere textual deletion. An episode may leave the prompt safely if its effect is persisted and a valid recovery path exists. Conversely, an episode may remain literally inside a huge prompt yet be practically unavailable. Liu et al. found a U-shaped position effect in multi-document QA and key-value retrieval: relevant material in the middle was often used less reliably than material at the beginning or end, including within nominal context limits ([“Lost in the Middle,” 2023](https://arxiv.org/abs/2307.03172)). That paper does not establish the behavior of every current model, but it demonstrates that “present in the window” and “reliably usable” are not equivalent.

For a required fact `f`, a simple qualitative tree could be:

```text
T_f: fact f unavailable when demanded
  OR
  ├─ P_f: no usable prompt representation remains
  └─ AND
     ├─ R_f: exact/raw representation has been evicted
     └─ X_f: every recovery channel fails
        OR
        ├─ pointer missing or invalid
        ├─ source changed without version identity
        └─ required tool/channel unavailable
```

If the only surviving prompt representation is a summary, add `S_f: summary omits or distorts the decision-relevant property`. If both “backups” are generated by the same summarizer from the same truncated source, add a shared `C_summary` common-cause event rather than multiplying independent success probabilities.

The point is not to compute a grand numeric probability from invented numbers. The point is to expose single-point losses and dangerous combinations before an eviction commits them.

## 3. Recommended design — UNVERIFIED: Context Failure-Path Guard

**Recommendation status:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**UNVERIFIED premise:** a pre-eviction or pre-compaction interception point can receive the candidate episode list and return a protected set. **Settling experiment:** connect a no-op hook that marks one known-present synthetic episode as protected, force the normal compaction threshold, and verify both (1) hook audit output and (2) the episode's presence in the next actual model request. If that interception is unavailable, use the same algorithm at episode creation to maintain a protected capsule; the policy remains small, but the integration classification must be reassessed rather than silently assumed.

### 3.1 Minimal episode metadata

Each episode receives only fields needed for the failure analysis:

```json
{
  "id": "e173",
  "kind": "user_constraint | correction | decision | evidence | action | result | error | plan",
  "state": "active | unresolved | resolved | superseded | persisted",
  "goal_ids": ["g4"],
  "supports": ["d12"],
  "depends_on": ["e161"],
  "supersedes": ["e044"],
  "persisted_ref": {"uri": "...", "version": "...", "readable": true},
  "provenance_family": "raw:tool-call-882 | summary:compressor-A/source-set-19",
  "token_cost": 143
}
```

This is an ephemeral adjacency list. It must not accumulate a global semantic ontology, embeddings, or cross-session graph. The model or existing harness already creates episodes; the added burden is a small number of typed edges and states.

### 3.2 Deterministic protection rules

Before eviction, protect an episode if any rule holds:

1. It is the sole usable prompt representation of an active user goal, explicit constraint, owner correction, or acceptance condition.
2. It is the sole support for an active decision and the decision is not both persisted and independently recoverable.
3. It is unresolved error/evidence or a promised follow-up on an active branch.
4. Its removal, combined with already-unavailable episodes, completes a registered minimal cut set for `T_goal`, `T_constraint`, `T_decision`, `T_observation`, or `T_recovery`.
5. The apparent remaining redundancy is entirely within one provenance family. At least one representation from a different failure family must survive for high-criticality items.
6. A `supersedes` edge exists and eviction would leave an older, contradicted representation more prominent than the correction. Prefer removing or clearly tombstoning the stale item, not the correction.

Among unprotected episodes, use a simple eviction order: successful action chatter whose effects are persisted; duplicate derived representations; resolved branches; then old recoverable evidence. Token cost breaks ties. Do not ask a second model to rank every episode.

This policy is intentionally structural. It can be compiled into ordinary sets and adjacency maps. For small active contexts, cut-set checking is set containment, not a general probabilistic-risk engine.

### 3.3 Offline empirical importance, not fictional online probabilities

At runtime, apply qualitative protection. Offline, calibrate importance through counterfactual replay:

`empirical_RAW(class c) = failure_rate(forcibly hide c) / failure_rate(baseline)`

`empirical_Birnbaum(c) = failure_rate(hide c) - failure_rate(force-retain c)`

These names are analogical; the measured quantities are agent-task deltas, not component failure probabilities. Stratify by task phase, episode kind, model, and recovery availability. Use bootstrap intervals and retain “unknown” when sample size is inadequate.

**Likely (55-80%)**, this replay-derived ranking will be more stable than asking the acting model to assign importance to its own context, because the replay observes downstream task outcomes and counterfactual absence while self-scoring observes only current salience. Evidence for the direction is the reliability field's use of RAW/Birnbaum counterfactuals and the demonstrated mismatch between context presence/position and actual use. **UNVERIFIED; settle with rank-correlation and held-out policy-performance tests in §8.**

### 3.4 Diverse recovery, not duplicate summaries

For the highest-criticality facts, maintain two *failure-diverse* forms when affordable:

- a concise prompt capsule containing the operative fact, and
- a versioned pointer to exact persisted evidence that can be read through an already-existing tool path.

The capsule covers tool/retrieval unavailability; the exact source covers summary lossiness. Two summaries produced by the same compaction call count as one family. Two pointers accessed through the same dead service count as one family. A summary and a pointer to a mutable unversioned source may also share a staleness cause.

**Very likely (80-90%)**, provenance-family accounting will expose false redundancy that a simple “number of copies” rule misses. Evidence is the formal common-cause model and NRC's independent operating experience. **UNVERIFIED in agent-context workloads; settle by injecting compressor omission, source mutation, and recovery-tool outage separately and jointly (§8).**

## 4. What this catches that ordinary eviction policies miss

These are predicted detections, not claims about the current harness.

| Failure pattern | Why recency/relevance/size can miss it | Failure-path guard response |
|---|---|---|
| An old user constraint is the only surviving boundary on a new action | Old and rarely repeated looks low-value | Single-member cut set for `T_constraint`; protect until superseded or task closes |
| A small error message is the sole evidence for an unresolved diagnosis | Short text receives little token-weight or semantic salience | `unresolved` state plus support edge protects it |
| Decision summary survives but its only cited observation is evicted | Summary appears self-contained even when its rationale must later be audited or revised | Protect the support path or require exact recoverable evidence |
| Three summaries all omit the same qualifier | Copy count mistakes correlated derivatives for redundancy | One provenance family; common-cause event prevents independence assumption |
| Raw output is evicted because a file pointer exists, but that pointer is mutable or requires a failing tool | “Persisted” is treated as binary | `T_recovery` requires version identity and a tested recovery channel |
| A correction is compacted while the older instruction remains | Per-item ranking does not encode supersession direction | `supersedes` edge protects the correction and tombstones/deprioritizes stale text |
| Two individually expendable snippets jointly form the only proof of an acceptance condition | Independent relevance scores cannot represent conjunction | Two-member minimal cut set catches joint loss |
| Context is below the token limit but decisive evidence is buried in the middle | Byte/token occupancy treats presence as accessibility | Position-aware capsule placement for protected facts; supported by “Lost in the Middle” as a risk signal, not a universal law |

It is **very likely (80-90%)** that the mechanism detects the first six patterns mechanically once their metadata is correct, because they reduce to deterministic state/edge/set predicates. Evidence is the stated Boolean formulation. It is only **likely (55-80%)** that the metadata will be correct without unacceptable annotation burden; evidence is that a 2026 preprint independently reports typed, dependency-linked episodes with deterministic eviction, but its results do not validate this proposed failure-tree annotation or this harness ([Semenov and Dorofeev, “Beyond Compaction,” arXiv:2606.11213](https://arxiv.org/abs/2606.11213)). **UNVERIFIED; settle with annotation precision/recall against human-labeled replay episodes and measure added tokens/latency.**

## 5. Adversarial transfer analysis

### 5.1 Structural assumptions that do transfer

1. **Finite resource allocation:** maintenance/inspection budgets and context tokens are both scarce resources allocated among candidates. NASA explicitly uses importance measures for resource allocation; the target problem explicitly has a finite window.
2. **Combinatorial failure:** mission failure can require one omission or a conjunction of omissions. Context examples include losing both a summary and its recovery path, or losing two complementary pieces of evidence.
3. **Single-point criticality:** one old constraint can be more important than thousands of recent action tokens, just as a single-member cut set can dominate a system.
4. **Correlated backups:** derived summaries, indexes, and retrieval paths can share a compressor, source, or service and therefore fail together. This is structurally the same independence error addressed by common-cause analysis.
5. **Counterfactual prioritization:** “what if this component certainly fails?” maps cleanly to “what if this episode is unavailable?” and is empirically testable by replay ablation.

These points establish a structural homomorphism at the level of *availability paths*, not at the level of physical lifetime statistics.

### 5.2 Structural assumptions that do not transfer

1. **Failure probabilities are not given.** Hardware reliability may use component rates, mission times, and operating data. A context episode's relevance changes with the next subgoal, and episode failures are dependent on the same model that chooses and consumes the context. Assigning `P(episode failure)=0.02` without replay data would be numerology.
2. **Semantic sufficiency is graded, not Boolean.** Two differently worded summaries may partially preserve a constraint. A fault-tree leaf treats its state as defined; an LLM can misunderstand text that is present. The guard can protect known paths but cannot certify comprehension.
3. **The system boundary moves.** Agents revise plans, discover new goals, and change the external environment. A static tree goes stale. Only active goals and near-term decisions should have small living trees.
4. **Unforeseen top events remain unseen.** NASA itself states that FTA presumes the undesirable events and contributors were foreseen and cannot guarantee identification of all failures ([NPR 8621.1 Appendix I-3.5](https://nodis3.gsfc.nasa.gov/displayCA.cfm?Internal_ID=N_PR_8621_0001_&page_name=AppdxI35)). The guard cannot protect a dependency nobody annotated.
5. **Eviction can improve performance.** Removing distractors may make the remaining evidence easier to use; physical component failure rarely improves the component's mission. Therefore “retain every contributor” is wrong. Minimal protection must coexist with aggressive eligible eviction.
6. **Recovery latency matters.** A pointer may preserve information but fail the decision deadline. Availability must include fidelity, channel health, version identity, and latency, not mere storage existence.
7. **The consumer is stochastic and position-sensitive.** Identical context can yield different action trajectories. A deterministic invariant reduces structural risk but does not make task success deterministic.

The borrow therefore supports a **guardrail on catastrophic combinations**, not a complete optimizer of semantic relevance.

### 5.3 Why MTBF does not transfer

MTBF invites a superficially attractive policy: estimate how long a fact remains useful, then evict it at its “failure age.” Reject it. Context value is not a stationary lifetime process; a fact can be dormant for 100 turns and become decisive when a branch reopens. “Repair” by retrieval has task-dependent cost and may be impossible after source mutation. Recency can be one feature, but no time-to-live derived from MTBF should govern constraints, corrections, unresolved evidence, or decision rationale.

**Almost certain (90-99%)** that a literal MTBF/TTL policy would be unsound for these protected classes. Evidence: their requirement is event/goal-dependent rather than age-dependent by definition, and the target literature shows that access depends on position and task, not merely elapsed tokens. This is a logical applicability judgment, not an empirical performance claim.

### 5.4 Why full FMEA/RPN does not transfer as the runtime scorer

Full per-episode FMEA would impose worksheet overhead proportional to trajectory size. Multiplying ordinal severity, occurrence, and detectability ranks into a Risk Priority Number also creates false precision and can assign equal products to very different risk shapes. IEC 60812 supports multiple prioritization methods rather than establishing one universal token-ranking formula ([IEC 60812:2018](https://webstore.iec.ch/en/publication/26359)). Use FMEA offline to build the small failure-mode taxonomy and tests; do not run a ceremonial FMEA for every tool response.

### 5.5 Why “more copies” is not a safe reading of redundancy

Duplicate generated summaries consume the very resource being protected and can preserve identical omissions. Reliability engineering's lesson is **independent success paths**, not copy count. In context, diversity means different failure mechanisms: concise operative capsule versus exact versioned evidence, or current in-window constraint versus independently readable owner-authored source. Diversity that adds another LLM-generated paraphrase from the same source and call path is cosmetic.

## 6. Frontier overlap and the actual incremental contribution

The newest directly relevant source found in this unit is the May 2026 CWL preprint. It describes typed, dependency-linked episodes, deterministic priority eviction, preservation of user turns and active exploration, and aggressive removal of persisted action episodes. It reports 89 sequential tasks over 80 million cumulative tokens without measurable degradation relative to isolated sessions ([arXiv abstract and submission record](https://arxiv.org/abs/2606.11213)). Treat those results as author-reported preprint evidence, not independently replicated fact.

This means “typed episode graph + deterministic structured eviction” is not a novel result of this cross-domain exercise. The reliability borrow adds three narrower ideas:

1. define explicit context-loss top events and protect minimal cut sets rather than only priority classes;
2. estimate episode-class importance through forced-unavailability replay analogous to RAW/Birnbaum sensitivity;
3. model provenance families and recovery-channel coupling as common-cause failures, so correlated summaries/pointers do not masquerade as independent backups.

I did not establish publication-level novelty for those three ideas. Novelty is unnecessary for adoption, but any novelty claim is **UNVERIFIED; settle with a systematic literature/code search over context pruning, cache eviction, provenance-aware RAG, and agent memory, plus expert review**. The recommendation rests on testable utility, not novelty.

## 7. Anti-overfit gate

The proposal passes the required anti-overfit gate:

- **Existing bus:** one pre-eviction/pre-compaction hook, or a context-assembly hook if interception is unavailable.
- **Small state:** per-session JSON/adjacency maps and a bounded active-goal capsule.
- **Deterministic hot path:** no extra model call, training loop, or probabilistic solver during normal eviction.
- **No rejected architecture:** no second orchestration runtime; no vector database or semantic knowledge graph; no durable-execution engine; no trained critic; no observability SaaS; no guardrail framework.
- **Graceful fallback:** if metadata is missing, protect only invariant classes (current goal, explicit constraints/corrections, unresolved errors) and use the existing eviction policy for the rest. Do not invent edges.

**Likely (55-80%)**, the runtime portion can remain below roughly 200 lines if episode boundaries and an interception hook already exist; evidence is that the core operations are field checks, adjacency lookups, provenance grouping, and set containment. **UNVERIFIED premise and experiment:** implement the no-op integration probe described in §3, then a spike supporting the five top events on a synthetic 50-episode trace; count non-generated source lines and profile p95 hook latency. If integration requires reconstructing episodes from raw transcripts or adding a new service, the BUILD-SMALL classification fails and this recommendation must return for architectural review.

## 8. Verification program

No recommendation should ship based on analogy. The following experiment directly tests the transfer.

### 8.1 Policies compared

Use identical models, tools, task seeds, and token ceilings:

- A: existing/baseline context policy;
- B: simple recency/size eviction;
- C: typed structured eviction without failure-path/common-cause logic;
- D: C plus the proposed failure-path guard;
- E: D minus provenance-family/common-cause accounting (ablation).

If C cannot be implemented independently, compare A, B, D, and E and state that the structured-policy contribution is confounded.

### 8.2 Workloads

1. Replays of long, real tasks with owner corrections, branch changes, unresolved errors, and persisted tool effects.
2. Synthetic “needle” tasks where the decisive constraint is old, middle-positioned, or jointly supported by two innocuous snippets.
3. Recovery tasks in which exact evidence is needed after its raw transcript has left the prompt.
4. Adversarial common-cause tasks where all summaries share one planted omission.
5. Distractor-heavy tasks to ensure the guard does not prevent beneficial eviction.

### 8.3 Fault injections

Inject individually and jointly:

- remove the only goal/constraint representation;
- remove one then both members of a two-item support set;
- corrupt every summary produced by one provenance family with the same omitted qualifier;
- invalidate a pointer or mutate its unversioned target;
- make the recovery tool unavailable;
- retain a stale instruction while removing its correction;
- bury protected material in middle positions while remaining under token limit.

### 8.4 Outcome measures

- end-to-end task and acceptance-test success;
- owner-correction/rework rate;
- violations of explicit constraints;
- exact recovery success and recovery latency;
- protected-token fraction and total input tokens;
- compaction/eviction latency;
- false protection rate (episode protected but never needed);
- catastrophic false-eviction rate (episode removed and causally required later);
- annotation edge precision/recall against a blinded human label set.

### 8.5 Mechanically independent completion signals

Do not declare the guard “working” from its own logs alone.

1. **Structural signal:** the hook audit records the candidate set, protected cut set, provenance groups, chosen evictions, and invariant result. First prove the detector can identify a known-present planted single-point constraint and planted two-member cut set.
2. **Behavioral signal:** inspect the independently captured next model-request payload and execute the downstream task. Confirm that the protected item is usable and that the injected removal causes the predicted behavioral failure in a positive control.

These signals are mechanically independent: one examines the policy's internal decision; the other examines actual prompt delivery and task behavior. Re-running the audit parser is not a second signal.

### 8.6 Decision thresholds — UNVERIFIED until preregistered and run

Adopt D only if it reduces catastrophic false evictions and constraint violations versus A/C without a statistically or operationally unacceptable reduction in task success, token efficiency, or latency. Threshold values must be preregistered from workload cost—not chosen after seeing results. A plausible initial engineering gate is zero planted single-point misses, zero planted common-cause false-redundancy passes, and bounded p95 overhead, but the numeric overhead bound is **UNVERIFIED; settle by measuring baseline context-assembly latency and setting a budget before the trial**.

Expected outcomes:

- **Likely (55-80%)**, D will beat B on old-but-critical constraints and conjunctive evidence. Evidence: these are direct counterexamples to recency and independent per-item scoring. **UNVERIFIED by the A–D replay.**
- **Likely (55-80%)**, D will beat C on correlated-summary and failed-recovery injections. Evidence: D uniquely models provenance coupling and recovery cut sets. **UNVERIFIED by the C–D–E fault injection.**
- **Roughly even (45-55%)** whether D improves aggregate end-to-end success on unselected natural workloads. Evidence is mixed in structure: preventing rare catastrophic loss helps, while extra protection can retain distractors and metadata can be wrong. **UNVERIFIED by held-out long-session replay.**
- **Very unlikely (5-20%)** that full quantitative fault-tree probability calculations are justified in the first version. Evidence: no calibrated basic-event rates have been established and task-conditioned dependencies violate naïve independence. The replay should gather data before any quantitative extension.

## 9. Failure modes of the proposed guard itself

A reliability-derived mechanism should undergo its own FMEA:

| Guard failure mode | Effect | Detection/mitigation |
|---|---|---|
| Missing dependency edge | Critical episode appears evictable | Conservative invariant classes; labeled replay recall test |
| Spurious dependency edge | Context bloat/distractors | False-protection metric; expire edges when goals resolve |
| Stale active-goal state | Old tree dominates new task | Explicit goal close/supersede events; bounded active trees |
| Wrong provenance grouping | False diversity or needless protection | Record source IDs, compressor/run ID, and recovery channel mechanically |
| Pointer marked recoverable but unreadable | Latent `T_recovery` | Cheap read/version probe before relying on pointer; cache only result metadata |
| Hook log says protected but assembly drops item later | Silent policy bypass | Independent request-payload capture and positive controls |
| Guard protects too much | Window pressure and lost-in-middle effects | Hard protected-budget alarm; fail visibly; resolve/supersede state rather than silent eviction |
| Acting model fabricates metadata | False assurance | Derive persistence/version/tool-result fields from tool bus; treat model-declared edges as lower-confidence hints |

The most dangerous guard failure is false assurance: a green invariant computed over an incomplete graph. Therefore policy output should say “no known cut set completed,” never “context is safe.”

## 10. Alternatives considered and rejected

### Literal MTBF/decay cache — reject

Age is not mission importance; dormant constraints can reactivate. Suitable only as a tie-breaker among already-safe candidates.

### Full FMEA worksheet for every episode — reject

It adds token and annotation burden on the hot path and risks turning ordinal guesses into false precision. Use FMEA offline to define failure classes and injection tests.

### Numeric RPN as eviction score — reject

No calibrated occurrence/detectability scales exist for episode classes, and one scalar erases cut-set structure. Two items with equal scores can have radically different joint criticality.

### Replicate every important fact three times — reject

This consumes context and ignores common causes. Require diversity of failure path, not copy count.

### LLM critic that re-ranks the whole transcript — reject

It adds model cost, latency, nondeterminism, and a shared-model common cause. It also approaches the explicitly rejected trained-critic/second-runtime direction. Use offline model assistance for labels if desired, never as the sole runtime protection.

### Vector database or knowledge graph — reject

Neither is required for active-session cut sets. A bounded adjacency list over episode IDs supplies the needed structure without a new memory subsystem.

### Static global fault tree — reject

Long-horizon tasks change. Maintain small trees per active goal/decision and retire them explicitly.
