# A068 — Coherence audit: `~/.claude/rules/swift/patterns.md`

Date: 2026-07-19  
Unit: A068  
Mode: read-only audit of the unpacked Linux-job-node bundle  
Subject rule: `/local_disk0/codexwork/bundle/claude/rules/swift/patterns.md`

## Executive result

The 66-line Swift patterns rule is not coherent with the installed harness as written. I found **seven reportable collisions**:

1. Three `CONTRADICTION`s between simultaneously applicable rule files:
   - actors are required to mutate isolated storage while the common rule says never mutate;
   - Swift asks for small focused repository protocols while the common rule prescribes a five-operation CRUD interface;
   - Swift patterns categorically says models are structs while Swift coding style permits classes when identity/reference semantics are required.
2. One `REDUNDANCY`: actor/`Sendable` guidance is repeated in two Swift rules without a single canonical owner.
3. One `UNENFORCED` cluster: the active per-edit checker has no Swift branch, the Swift LSP plugin is disabled, and no active settings command runs the formatter, linter, or compiler promised by the Swift hook rule.
4. Two `UNRULED` hook criteria that apply to Swift: reachability/version-suffix checking and the still-open-placeholder completion gate are implemented in hooks but are not stated in the rule corpus.

The measured corpus cannot answer whether generated Swift code follows the architectural rules. Its distillation contains tool/capability aggregates and session metadata rather than edited source or final diffs, and its hook detector is explicitly broken. Treating that lack of evidence as compliance or noncompliance would violate the program's honesty requirements.

The highest-confidence conclusion is **almost certain (90-99%)**, because the conflicting imperatives and active dispatch branches are directly present in the cited files. The remaining 1-10% accounts for runtime behavior or project-local instructions not present in the unpacked bundle, not ambiguity in the quoted text.

## Collision register

### C1 — `CONTRADICTION`: actor-isolated mutation versus “NEVER mutate”

**Artifacts and exact lines**

- `rules/swift/patterns.md:36-46`: “Use actors for shared mutable state instead of locks or dispatch queues,” followed by `private var storage` and a setter that mutates the dictionary.
- `rules/common/coding-style.md:23-33`: “ALWAYS create new objects, NEVER mutate existing ones.”
- `rules/common/coding-style.md:61-68`: completion checklist requires “No mutation.”
- Both apply to `**/*.swift`: `rules/swift/patterns.md:1-5` and `rules/common/coding-style.md:1-20`.

**Why this collides**

The actor example is not merely discussing mutable state; it performs it at `patterns.md:42-45`. An agent can obey the Swift actor pattern or the universal no-mutation checklist, but cannot literally obey both. Replacing the actor's dictionary with a newly allocated dictionary on every setter still assigns to actor state and therefore remains mutation under the common rule's categorical wording.

**Precedence**

AGENTS §10 does not resolve two same-level rule files. The unloaded rules README explicitly states that Swift-specific instructions override common defaults (`rules/README.md:93-105`), but the common text calls itself “CRITICAL,” “ALWAYS,” and “NEVER,” and contains no language-exception note. Silent specificity is therefore unsafe.

**Diagnosis**

This is a badly written universal rule, not evidence that actor isolation is wrong. Confidence: **almost certain (90-99%)**, supported by the direct mutation example and simultaneous Swift path scopes.

**Specific resolution**

Change the common rule from categorical immutability to a value-semantics default: avoid externally observable shared mutation; prefer immutable values, but permit encapsulated mutation behind language-native synchronization/isolation such as a Swift actor. Add an explicit Swift override sentence immediately before the actor example: “This is the Swift exception to common/coding-style's immutability default; actor-isolated internal mutation is permitted, while values crossing isolation boundaries remain `Sendable`.” Remove “No mutation” as a universal completion gate or qualify it identically.

NATIVE-vs-BUILD: **NATIVE (Claude Code already does this; we just enable it)** — keep the native path-scoped rule loader; reconcile the two inputs it loads. The resolution is **very likely (80-90%)** to remove contradictory agent instructions because both imperatives become one scoped policy; evidence is the exact overlap above. It adds no runtime component.

### C2 — `CONTRADICTION`: small focused protocols versus mandatory CRUD repository surface

**Artifacts and exact lines**

- `rules/swift/patterns.md:10-19`: “Define small, focused protocols,” with `Repository` exposing only `find(by:)` and `save(_:)`.
- `rules/common/patterns.md:35-43`: repository interfaces must define standard operations `findAll, findById, create, update, delete`.
- Both common and Swift pattern files apply to Swift (`common/patterns.md:1-20`; `swift/patterns.md:1-5`).

**Why this collides**

A protocol restricted to the two capabilities a consumer needs is not the prescribed five-operation interface. Conversely, adding the five standard operations makes the example less small and focused. This is a genuine interface-segregation threshold conflict, not different wording for the same rule.

**Precedence**

AGENTS §10 does not decide the same-level conflict. The rules README's intended language-specific precedence points toward the Swift rule, but the target does not explicitly override the common CRUD prescription.

**Diagnosis**

The common rule is over-broadly written. Confidence: **very likely (80-90%)**, supported by the two incompatible operation sets; the residual uncertainty is that “standard operations” could have been intended as examples despite being written as an imperative.

**Specific resolution**

Make interface segregation canonical in `common/patterns.md`: repositories expose only capabilities required by their consumers; when an operation exists, use consistent domain-appropriate names. If a full CRUD aggregate is genuinely required, compose small protocols (for example `ReadableRepository`, `WritableRepository`, `DeletableRepository`) rather than requiring every repository to expose all five operations. Rename the target example if needed so `Repository` is not read as the mandated full CRUD abstraction.

NATIVE-vs-BUILD: **NATIVE (Claude Code already does this; we just enable it)** — retain native rule loading and make the common/Swift pair compositional. This resolution is **likely (55-80%)** to reduce oversized abstractions because the loaded text would no longer direct every consumer toward full CRUD; evidence is the current five-versus-two method mismatch. No rejected architecture is introduced.

### C3 — `CONTRADICTION`: categorical struct models versus a class exception threshold

**Artifacts and exact lines**

- `rules/swift/patterns.md:22-25`: “Use structs for data transfer objects and models.”
- `rules/swift/coding-style.md:15-18`: use `struct` by default, but use `class` when identity or reference semantics are needed.

**Why this collides**

The patterns rule is categorical for “models”; the coding-style rule is a default with an explicit exception. A domain model whose identity/reference semantics are essential receives opposite instructions from two simultaneously loaded Swift rules. This is exactly the requested “different threshold” form of collision.

**Precedence**

Both are Swift language rules at the same layer. Neither AGENTS §10 nor the rules README selects `patterns.md` over `coding-style.md`. AGENTS §10 says to surface the conflict.

**Diagnosis**

This is imprecise wording rather than a wrong preference. Confidence: **almost certain (90-99%)**, because “use structs” and “use class when identity … needed” have a concrete overlapping case.

**Specific resolution**

Make `swift/coding-style.md:15-18` the single normative choice rule. Replace `swift/patterns.md:24` with a pointer: “For DTOs and value-semantic models, use structs; models requiring stable identity/reference semantics may be classes per Swift Coding Style.” Keep the associated-value enum guidance in patterns because it describes state modeling rather than the struct/class threshold.

NATIVE-vs-BUILD: **NATIVE (Claude Code already does this; we just enable it)** — consolidate on the existing native rule surface. It is **almost certain (90-99%)** that this removes the textual threshold conflict, evidenced by making both files use the same exception.

**Specific resolution**

Keep concurrency policy—strict mode, isolation boundaries, `Sendable`, actor preference—in `swift/coding-style.md`.
