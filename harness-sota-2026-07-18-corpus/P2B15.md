# P2B15 — Competitive teardown: Factory

Date: 2026-07-18  
Unit: P2B15  
Subject: Factory Droid / Factory Missions versus the owner’s Claude Code harness  
Mode: research and design only; SUBJECT remained read-only

## Executive verdict

Factory is not a better replacement for this harness as a whole. It is a polished agent product with three genuinely valuable ideas for us: (1) explicit risk-tiered autonomy rather than the owner’s current blanket `bypassPermissions`; (2) milestone-scoped orchestration in which every milestone ends in independent validation and failures create follow-up work; and (3) a repository “agent readiness” audit that evaluates whether the environment gives agents fast, deterministic feedback. The first is already native Claude Code configuration. The second and third can ride the existing Claude task/hook/skill bus as small additions. None requires a second orchestration service.

Factory’s strongest-looking architectural feature, Missions, is also the clearest anti-overfit hazard. Factory describes a proprietary orchestrator, worker sessions, Mission Control, multi-day persistence, automatic recovery, and validation workers. Copying that literally would reintroduce the explicitly rejected “second orchestration runtime” and “durable-execution engine.” We should copy its milestone/validation *protocol*, not its runtime.

Factory is materially worse in durable semantic memory and objective continuity. Its own memory guide says Droid has no built-in cross-session memory and proposes Markdown files plus prompt-triggered append hooks. This owner already has a semantic `basic-memory` MCP and an objective event ledger with recovery replay, goal re-anchoring, bounded recall, typed tool receipts, and explicit failure/milestone records (`C:\Users\Prekzursil\.agents\harness\modules.py:933-1003`, `:1048-1077`, `:1279-1378`, `:1440-1680`). Do not replace those with `.factory/memories.md`.

The highest-value near-term change is permissions. Factory defaults to approval and exposes Off/Low/Medium/High risk levels, while this owner’s live Claude settings allow broad tools, expose all of `C:` and `D:`, and set `defaultMode` to `bypassPermissions` (`C:\Users\Prekzursil\.claude\settings.json:26-75`). Moving to Claude Code’s native `auto` mode plus sandbox/deny rules is **very likely (80-90%)** to reduce the blast radius of prompt injection or mistaken commands; evidence is the live permissive configuration and Claude’s documented OS sandbox plus permission-deny enforcement. The exact friction cost is **UNVERIFIED**; an A/B experiment over 50 representative sessions measuring prompts, blocked legitimate actions, and prevented unsafe actions would settle it.

## 1. Agent loop

### What Factory exposes

The observable single-Droid loop has two interaction paths.

In Auto mode, Droid interprets the request, reads/searches context, calls tools, edits, and reports results under the selected autonomy level. Factory does not publish enough core source to specify the actual planner state machine, stop criteria, retry budget, or reflection prompt. Any stronger claim is **UNVERIFIED**; a `droid exec --output-format stream-json` trace corpus across success, tool failure, interruption, context compaction, and permission denial would settle the state transitions.

Specification Mode is clearer: read-only analysis of code, dependencies, AGENTS.md and external context; generation of acceptance criteria, file-by-file implementation plan, testing strategy and security considerations; user review; then implementation only after approval. Factory documents this sequence explicitly in [Specification Mode](https://docs.factory.ai/cli/user-guides/specification-mode). This is a good productized surface, but not a missing primitive: Claude Code plan mode already provides read-only planning, and the owner’s contract requires clarification only before execution.

Missions adds a second loop above individual workers. Factory says an orchestrator decomposes the goal into milestones and features, gives each feature a fresh worker session, coordinates through git, ends each milestone with review/tests/regression/integration validation, and turns validation failures into follow-up work before advancing. It parallelizes only where coordination overhead is low. This is the most important transferable mechanism in the teardown ([Missions](https://factory.ai/news/missions)).

### What ours does

The owner’s live harness is a lifecycle supervisor, not a planner replacement. Its ten ordered modules are secret guard, event ledger, goal reinjection, sanitized checkpoint, bounded recall, anti-degeneration, claim warning, design reminder, subagent lifecycle, and a domain guard (`C:\Users\Prekzursil\.agents\harness\modules.py:420-431`, `:2599-2613`). It records/replays goals and failures, warns on repeated identical tools and low-information loops (`:1783-1997`), and checks thin subagent handoffs (`:2331-2420`). Claude itself supplies tasks, agents, teams, and worktrees; those are enabled in live config at `C:\Users\Prekzursil\.claude\settings.json:4-18`.

A mandatory milestone validator is not visible in the scoped harness. This absence has two mechanically independent signals: (1) the complete production module factory contains ten modules and no milestone validation/orchestration module (`modules.py:2599-2613`); (2) live hooks register `TaskCreated`, `TaskCompleted`, and `TeammateIdle` only to the generic dispatcher (`settings.json:445-479`), while the dispatcher’s concrete `TaskCompleted` path merely appends task state (`modules.py:944-962`). The detector control succeeds because the same probes find the known-present `goal_reinjection` module and `TaskCompleted` registration. This establishes absence from the scoped harness, not absence from every installed skill.

### Port recommendation — UNVERIFIED: milestone contract, not Mission runtime

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — Add a `mission-lite` skill plus a small `TaskCompleted`/`Stop` module:

1. The plan represents milestones as native Claude tasks with dependencies and explicit acceptance checks.
2. Feature workers use native subagents or agent teams; editing workers use `isolation: worktree` where file overlap is possible.
3. A milestone cannot close from an implementation worker’s assertion. Completion spawns or assigns a fresh validation agent with a read-only-first prompt.
4. The validator runs the repo-declared lint/type/test/build commands and, for UI/CLI/API behavior, invokes the relevant existing browser/computer-use/E2E skill.
5. The validator returns typed evidence: command, exit status, artifact path/hash, scoped acceptance criterion, and `SUCCESS:<id>` or `FAILED:<id> reason`.
6. On failure, the parent creates a bounded repair task linked to the failed acceptance criterion. It does not reset the whole mission or re-run unchanged probes.
7. The event ledger records milestone and failure events; no second database, queue, scheduler, or daemon is introduced.

This is **very likely (80-90%)** to improve long-horizon integration reliability because Factory’s mechanism directly addresses fresh-context and integration-boundary failure, and our harness already has the necessary native task events and typed receipt concepts. The magnitude is **UNVERIFIED**; an experiment on 20 multi-component tasks, randomized between current coordination and mission-lite, measuring acceptance pass rate, duplicate work, merge conflicts, tokens, and elapsed time would settle it.

Do not copy Factory Mission Control. A persistent multi-day coordinator is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and explicitly violates the anti-overfit rejection of a second orchestration runtime and durable-execution engine. It is **unlikely (20-45%)** to outperform a thin native-task protocol for this single-owner environment; evidence is the existing Claude agent-team/task/worktree primitives and the corpus’s already broad but failure-prone tool surface. The uncertainty would be settled only by the above mission-lite benchmark against a real Factory Mission on matched repositories.

## 2. Context management

### Factory’s Deferred Context Engine

Factory says its Deferred Context Engine starts each turn with compact discovery metadata, promotes full schemas/instructions only when needed, keeps promoted capabilities available for the rest of the work, and keeps frequently used tools warm across sessions. It applies the pattern to internal tools, MCP tools, skills, and plugins. Factory reports, over five production days, 15.1% average estimated input-token reduction on sessions that invoked MCP, 39.4% at p90, and 50.8% average for sessions with 100+ hidden deferred tools ([Deferred Context Engine](https://factory.ai/news/deferred-context-engine)). Those are vendor telemetry, not independently reproduced. Their transfer to this owner is **UNVERIFIED**; logging before/after prompt schema tokens with `ENABLE_TOOL_SEARCH=false`, `auto:5`, and default deferral across 100 matched tasks would settle it.

Claude Code already defers MCP tool definitions and loads relevant tools through ToolSearch. Official docs say only names load initially, selected schemas enter context on demand, and `alwaysLoad` can exempt hot servers. The owner has `ENABLE_TOOL_SEARCH=auto:5` and explicitly allows ToolSearch (`settings.json:17`, `:46`). Corpus evidence shows 5,091 ToolSearch calls with only four errors (0.08%). Therefore Factory’s headline MCP-context feature is already present and operational here.

**NATIVE (Claude Code already does this; we just enable it)** — Keep ToolSearch. Do not build a schema router. The only useful configuration work is curating always-hot tools and disabling dead tools. Given the dead Tavily endpoint’s measured damage, tool catalog health matters more than another deferral layer.

Factory also exposes per-server `enabledTools`, `disabledTools`, timeout overrides, user/folder/project precedence, automatic reload, OAuth discovery, keyring storage, and enterprise MCP allowlists ([MCP docs](https://docs.factory.ai/cli/configuration/mcp)). Claude supports scoped MCP, managed allow/deny policy, OAuth, and per-tool permission patterns. **CONFIG (settings/JSON only)** — express the small set of hot/allowed tools through existing Claude MCP/permission configuration and disable known-dead servers. It is **almost certain (90-99%)** that removing the dead `claude_ai_Tavily` route would eliminate its “not connected” calls; evidence is the corpus’s 532 calls / 25.8% overall error rate and 135 identical connection failures. Whether callers cleanly reroute is **UNVERIFIED**; a configuration-shadow experiment replaying 50 affected search intents through the remaining live providers would settle it.

### Compaction, rewind, and session continuity

Factory release notes show compaction retry fixes, output transformation before compaction, directory-specific sessions, resume by task ID, and rewind/fork workflows. Claude Code natively auto-compacts and checkpoints file edits; the owner adds sanitized pre-compaction checkpointing, post-compaction goal re-anchoring, and event-ledger replay (`modules.py:964-1003`, `:1362-1378`, `:1440-1680`). Ours is stronger on objective continuity because it does not trust a compacted conversational summary as the only ground truth.

Factory’s persistent Droid Computer retains filesystem, configuration, credentials, local services, and process memory and can run after the laptop closes ([Droid Computers](https://factory.ai/news/droid-computers)). That is a real capability outside the scoped local harness. **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** — do not port without an explicit requirement for remote, always-on execution. It is **unlikely (20-45%)** to provide net value for the current owner because it adds credential custody, remote attack surface, lifecycle management, and the prohibited durable runtime; evidence is the local-first owner environment and the absence of a stated remote-operations requirement. This premise is **UNVERIFIED**; a concrete owner requirement and threat/cost model would settle it.

## 3. Memory

Factory’s public memory guide is unusually candid: “Droid doesn’t have built-in memory between sessions.” It recommends personal and project `memories.md`, AGENTS.md references, `.factory/rules`, and a `UserPromptSubmit` hook that appends text after triggers such as `remember this:` ([Memory guide](https://docs.factory.ai/guides/power-user/memory-management)). Droid Computers provide persistent machine state, and Factory claims Droids can create memories/skills after solving environment problems, but that does not make the documented Markdown layer semantic, provenance-aware, conflict-aware, or automatically recalled.

This owner’s design is better:

- `basic-memory` is the canonical cross-tool semantic store; corpus records 1,332 calls, including 357 searches, 353 reads, 408 writes, and 156 edits.
- The event ledger separately stores objective goals, decisions, failures, milestones, mutations, and typed tool receipts (`modules.py:933-1077`).
- Recovery replay is limited to resume/compact/clear and excludes unrelated session goals (`modules.py:973-1003`).
- Recall is bounded and labels historical summaries untrusted (`modules.py:1572-1680`).
- The Stop gate nudges durable capture after canonical changes (`modules.py:2267-2328`), albeit the prior audit correctly notes that the current proxy is project-scoped rather than truly session-scoped.

Do not copy Factory memory. A Markdown append file is easier to inspect but scales poorly, has no semantic retrieval, and encourages stale/conflicting facts. The only useful Factory idea is human-readable checked-in project decisions; that can remain a view/export of basic-memory, not a second authority.

Factory’s memory absence is supported by two independent signals: the product guide’s explicit statement and its concrete architecture/example code, which reads flat files and appends dated bullets. A control confirms the detector can identify present persistence: the same guide names personal and project memory files and its hook writes them. Thus the conclusion is narrowly “no documented built-in cross-session memory,” not “Factory never stores session state.”

## 4. Tools and MCP handling

Factory’s tool surface is good product engineering:

- user/folder/project MCP configuration with precedence;
- stdio, HTTP, and SSE transports;
- OAuth discovery and system-keyring token storage;
- per-server and per-tool enable/disable;
- environment-variable expansion in memory without rewriting secrets to disk;
- MCP tools exposed under `mcp__<server>__<tool>` so hooks can gate them;
- custom droids with explicit tools/MCP servers;
- plugin bundles containing skills, commands, agents, hooks, and MCP servers;
- an interactive registry and status UI.

These are mostly native equivalents, not build targets. Claude MCP and plugin formats cover the same bus, and Factory explicitly advertises Claude Code plugin compatibility. **NATIVE (Claude Code already does this; we just enable it)** — keep Claude MCP, ToolSearch, skills, plugins, hooks, and custom agents as the one extension surface.

Factory is better in UI coherence: one `/mcp` surface displays status, tools, auth, enable/disable, and organization policy. Our estate is fragmented across `.mcp.json`, `.claude.json`, settings, plugin caches, and multiple bridges. The corpus demonstrates the operational cost: 93 servers touched, a dead MCP still called, and multiple duplicated provider namespaces. A replacement UI is not warranted. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — extend the existing SessionStart preflight/health inventory to emit one deduplicated, bounded status table and quarantine only mechanically confirmed dead routes. It is **very likely (80-90%)** to reduce repeated connection failures because the primary failure is static dead routing, not model reasoning. Quarantine safety is **UNVERIFIED**; require two health signals (configuration/transport plus a successful known-present control on the same provider family) and shadow for 30 sessions before enforcement.

Do not emulate Factory’s entire registry. The orphaned-plugin incident proves that more discovery/cache machinery can itself break process launch. Keep canonical manifests small and use exact versioned plugin inputs.

## 5. Permission model and security

Factory uses two dimensions: interaction mode (Auto versus read-only Spec) and Autonomy Level (Off/Low/Medium/High). Commands and MCP tools carry risk levels; denylisted patterns and sandbox boundaries can still require approval at High; organization policy can cap maximum autonomy; subagents are clamped to that cap. `droid exec` is read-only by default. Missions require High or an explicitly unsafe permission bypass ([Autonomy Level](https://docs.factory.ai/cli/user-guides/auto-run)). This is more legible than the owner’s current state.

The owner’s live settings allow Read/Edit/Write/Bash/Web/MCP/Task/Skill broadly, set `defaultMode: bypassPermissions`, and add both `C:` and `D:` as directories (`settings.json:26-75`). Deterministic pre-tool guards still block particular dangers, but they are not an OS sandbox and several hooks have known wiring/runtime defects. Factory is therefore better in default blast-radius control.

**CONFIG (settings/JSON only)** — switch the default from bypass to Claude Code `auto` permission mode, enable sandboxing with `failIfUnavailable` for high-risk autonomous runs, retain explicit deny rules, and require separate opt-in for deploy/push/credential-bearing operations. Claude documents that permissions apply across Bash/Read/Edit/WebFetch/MCP and the OS sandbox independently constrains Bash children. Roll out per project, not globally in one jump.

This change is **very likely (80-90%)** to improve safety, for the reasons in the executive verdict. Its usability impact is **UNVERIFIED**; the settling experiment is a 50-session shadow classifier log followed by 20-session auto-mode trial, reporting added approvals, false blocks, bypass requests, and prevented out-of-scope accesses.

Factory’s Droid Shield combines deterministic secret scanning at commit/push with two learned gates: a recall-oriented “risk” model for potential misses and a redacted-context “downgrade” model for scanner false positives. Factory reports repo-held-out metrics and openly notes uncertain production precision and domain shift ([Droid Shield 2.0](https://factory.ai/news/droid-shield-2-0)). We already have deterministic secret scanning (`modules.py:606-909`) and a security non-negotiable against hardcoded secrets.

Do not port the learned Shield. It is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and explicitly reintroduces a trained critic/guardrail framework rejected by the anti-overfit gate. Factory’s own article says real private repositories may not match the public benchmark and thresholds may not hold in traffic. Deterministic scanning plus native permission/sandbox controls is the smaller, auditable choice. If future corpus evidence shows a material deterministic false-negative class, evaluate the released weights offline first; currently that premise is **UNVERIFIED**, and a labeled sample of this owner’s scanner misses would settle it.

## 6. Customization: AGENTS.md, rules, skills, hooks, droids, plugins

Factory and Claude have converged strongly:

- `AGENTS.md`: Factory searches current directory, parents to repo root, subfolders being worked in, then `~/.factory/AGENTS.md`; closer instructions win. This is compatible with the owner’s cross-tool contract.
- Rules: `.factory/rules/*.md` provides scoped conventions; hooks enforce deterministic versions.
- Skills: `SKILL.md` plus supporting files, user/model invocation controls, automatic relevance loading, and slash-command compatibility.
- Custom droids: Markdown definitions with prompt, tools, model, reasoning effort, autonomy, and project/personal scope.
- Hooks: PreToolUse, PostToolUse, UserPromptSubmit, Notification, Stop, SubagentStop, PreCompact, SessionStart, SessionEnd; JSON on stdin; context injection, block/approve decisions, configurable timeout.
- Plugins: distributable bundles of skills, commands, agents, hooks, and MCP; Git-based marketplaces with commit/ref pinning.

Most are **NATIVE (Claude Code already does this; we just enable it)**. Do not create Factory-format duplicates. Factory even imports Claude agents and plugins.

Factory hooks have two attractive operational details: matching hook commands run in parallel and identical commands are deduplicated. Parallelism is not automatically better. Our dispatcher intentionally runs ordered modules and makes security blocks terminal (`dispatcher.py:267-302`), merges actions by priority, redacts/bounds context (`:280-315`), and has per-module fault isolation/circuit-breaker state (`:303-312`, `:374-478`). Factory’s parallel hooks can race when hooks mutate shared state or when one block should prevent later consumers from ingesting a payload. Ours is better on deterministic arbitration, although audit A16 found concurrency and breaker-state defects that must be fixed independently.

Do not copy parallel-all hook execution. If latency data identifies safe pure hooks, parallelize only an explicitly marked `pure/read_only` phase within the existing dispatcher. That prospective optimization is **UNVERIFIED**; per-module latency traces plus concurrency tests would settle whether it is worthwhile.

Factory’s plugin pinning is now better than an earlier superficial reading: its docs permit marketplace `ref` or full `sha` pinning. Still, the owner’s orphaned-plugin failure shows that caches must not expand process command lines or leave ambiguous “live” directories. Preserve one canonical manifest and garbage-collect only after reachability proofs.

## 7. Multi-agent support

Factory subagents are mature:

- fresh isolated context and session;
- own prompt, tools, model, autonomy;
- built-in read-only `explorer` and general `worker`;
- foreground streaming or background task IDs;
- resume with full prior transcript;
- parallel Task calls;
- explicit light/medium/heavy complexity-to-model routing;
- organization caps on model, MCP, tools, and autonomy;
- specialized validation droids used by Missions.

Factory’s normal subagents cannot ask the user and cannot spawn their own subagents; they return one final message to the parent. Claude Code subagents share the fresh-context/no-nesting pattern, while agent teams add peer messaging and a shared task list. The owner already enables experimental agent teams (`settings.json:7`) and registers Task/Teammate lifecycle events (`settings.json:445-479`). The corpus records 1,158 `general-purpose` agent invocations plus 21 other types. Factory therefore does not lead on raw agent count or delegation primitives.

Factory does lead on *productized model routing* and *mandatory mission validation*. Automatic complexity routing is **CONFIG (settings/JSON only)** if implemented through a small set of custom Claude agents (`explorer-fast`, `worker-default`, `review-heavy`) with pinned/inherited models; no runtime router is necessary. It is only **likely (55-80%)** to reduce cost without hurting quality because the task complexity labels are model-generated and may be wrong. The premise is **UNVERIFIED**; replay 100 completed delegated tasks against fixed and tiered routing, blinded on correctness and cost, to settle it.

Our subagent handoff discipline is stronger than Factory’s documented single-return contract: it injects a structured-summary requirement, requests an I-PASS-style read-back, detects hollow outputs, and detects frozen transcripts (`modules.py:2331-2420`). Audit A16 identified a loophole: any terminal prefix bypasses the minimum-length check (`modules.py:2384-2395`). Fix that local defect rather than importing Factory’s looser return contract.

## 8. Verification and self-checking

Factory has four distinct verification layers.

1. **Spec verification design.** Specification Mode generates acceptance criteria, testing strategy, security considerations, and a user approval gate before writes.
2. **Mission milestone validation.** Fresh workers review accumulated work, run tests, check regressions/integration, and create repairs. Computer-use validators launch apps and exercise UI flows alongside test/lint/build.
3. **Droid Control evidence.** An official plugin drives terminal/browser/desktop flows, returns pass/fail, screenshots, and video evidence. This is useful because it tests claimed behavior, not only code shape.
4. **Readiness and product self-improvement.** `/readiness-report` scores repository feedback infrastructure and persists history. Separately, Signals uses LLM/embedding analysis of session friction, crosses thresholds into Linear tickets, has Droid implement/review PRs, and keeps human approval before merge.

The owner’s harness is stronger in claim discipline and objective receipts: it hashes results, classifies test receipts, records failures, warns on unverified completion claims, and has domain-specific evidence requirements (`modules.py:1048-1077`, `:2000-2265`). But it lacks a general automatic “fresh validator after milestone” policy and a repository feedback-readiness score, as established by the two-signal absence check in section 1 and by the complete module factory plus absence of a readiness command in live settings. The known-present controls are the claim-warning module and registered task hooks.

### Port recommendation A — UNVERIFIED: validation receipts

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — Extend the existing typed receipt lane so each acceptance criterion has one of: deterministic test receipt, static-analysis receipt, runtime interaction receipt, or explicit `UNVERIFIED` with the exact missing experiment. A separate validation agent must produce the receipt for mission-lite milestones. UI evidence should include screenshot path/hash and asserted state; CLI/API evidence should include invocation, exit/status, and salient output hash.

This is **very likely (80-90%)** to reduce false completion because independent validators and evidence artifacts directly address self-attestation. Evidence includes the current claim-warning/receipt machinery and Factory’s milestone design.
