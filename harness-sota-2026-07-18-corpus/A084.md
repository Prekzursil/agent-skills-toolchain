# A084 — coherence audit: hooks vs commands / duplicate authority

**Unit:** A084  
**Date:** 2026-07-19  
**Subject snapshot:** `/local_disk0/codexwork/bundle/claude` (read-only)  
**Requested Windows subject mapping:** bundle `claude/` = `C:\Users\Prekzursil\.claude`  
**Scope:** every one of the 164 Python files under `hooks/**` versus every one of the 71 Markdown files under `commands/**`, with runtime reachability checked through `settings.json`, `_dispatch/manifest.json`, and the auxiliary `hooks/hooks.json`.

## Executive result

I found **two material duplicate-authority failures**:

1. **`/rollback` promises an automatic producer that is not registered anywhere in the local runtime graph.** The command and hook source both define the same checkpoint contract, but the registration layer has drifted away from both. At runtime the promise in the command loses: ordinary edits do not invoke `edit-checkpoints/checkpoint.py`, so `/rollback` normally has no automatically produced index to consume. A second, currently latent conflict in the same command ignores the saved HEAD SHA for `git-head-clean` records.
2. **`/codex-monitor` and `codex-monitor-autolaunch` independently own the monitor launch transport.** The command says the guarded wrapper deliberately uses a plain console instead of Windows Terminal because the board was observed to exit under `wt`/ConPTY; the active hook nevertheless tries `wt ... new-tab` first. Automatic and manual launches therefore follow different launch authorities.

Everything else was either additive, differently scoped, or dormant. In particular, I did **not** count matching vocabulary, a manual command plus an advisory hook, or two components that cannot execute in the same situation as a conflict.

The first result is **almost certain (90-99%) for this unpacked snapshot**, supported by two mechanically independent registration reads with known-positive controls and by a whole-bundle reference search. It is not stated as 100% because this Linux node cannot perform a live Claude Code edit on the owner’s Windows installation. **UNVERIFIED on the live Windows process; the settling experiment is a fresh Claude session in a disposable Git repo, one `Edit`, then test for `~/.claude/checkpoints/<session_id>/index.ndjson` and `refs/claude-checkpoints/*`.**

The second result’s split authority is certain from the texts and active settings. Whether the outer `wt` invocation actually kills the current wrapper-launched board is **UNVERIFIED because `C:/Users/Prekzursil/.local/bin/codexmon.ps1` is outside the unpacked subject; the settling experiment is to invoke one native Codex MCP call on Windows, capture the process ancestry/window host, and observe the board for two refresh intervals.**

## 2. Finding A084-F1 — `/rollback` has a dead automatic producer

**Severity:** High for recoverability; low steady-state overhead because it is dormant.  
**Class:** duplicate contract + registration drift.  
**Runtime status:** the command exists; the producer source exists; the producer is not reachable through either local registration bus in this snapshot.

### 2.1 Both authorities, verbatim

Command authority, `commands/rollback.md:3-7`:

> Restore files from an **edit-checkpoint** taken automatically before edits this  
> session. The `edit-checkpoints` PreToolUse hook snapshots the pre-edit state once  
> per turn (git repos: a `git stash create` object tagged under  
> `refs/claude-checkpoints/`; non-git paths: a file copy) so a botched edit run is  
> recoverable even though Claude Code has no native edit-undo.

Hook authority, `hooks/edit-checkpoints/checkpoint.py:2-19`:

> EDIT-CHECKPOINTS — snapshot-before-write undo safety.  
>  
> Claude Code has NO built-in edit-undo. This PreToolUse(Edit|Write|MultiEdit) hook  
> takes a cheap, non-intrusive snapshot of the pre-edit state ONCE PER TURN so a botched  
> edit run is recoverable (see /rollback):  
>  
> * git repo -> `git stash create` ... tagged under refs/claude-checkpoints/  
> * non-git -> copy each distinct target file once per turn into the checkpoints dir.  
> ...  
> checkpoint is appended to `<ckpt>/<sid>/index.ndjson` for `/rollback` to read.

Those texts agree with each other. The conflict is that they are both authoritative descriptions of an automatic runtime behavior that the actual registration graph does not invoke.

### 2.2 Concrete collision

1. The user edits a file using `Edit`, `Write`, or `MultiEdit`.
2. The command says a pre-edit checkpoint is automatically created.
3. The direct PreToolUse settings execute the handlers at `settings.json:139-282`; none names `edit-checkpoints/checkpoint.py`.
4. The local dispatcher invoked at `settings.json:250-259` reads `_dispatch/manifest.json`; its PreToolUse list contains only `bg-registry/register`, `memory-spool/spool`, `dup-guard`, and `monitor-autolaunch` (`hooks/_dispatch/manifest.json:182-227`) in this snapshot.
5. The user invokes `/rollback`. Its instructions read `~/.claude/checkpoints/<session_id>/index.ndjson` (`commands/rollback.md:21-24`), but the promised automatic producer did not run.

The auxiliary `hooks/hooks.json` is not a hidden rescue path: it contains no edit-checkpoint command, and the active user settings explicitly disable the ECC plugin (`settings.json:608`). The wiring test itself calls `settings.json` “the active user-level wire” (`hooks/_dispatch/test_wiring.py:2-7`).

### 2.3 Which authority wins at runtime

**The registration graph wins.** Hook source comments and slash-command prose do not schedule a process. On an ordinary edit, the checkpoint hook is not launched. When `/rollback` is invoked, the command prompt can list only records already present from an older deployment or a manual hook invocation; it cannot retroactively create the pre-edit state it promises.

This conclusion is **almost certain (90-99%) for the snapshot**, supported by the two controlled registration probes, the whole-bundle reference search, and the independent expected-route test. **UNVERIFIED on the live Windows process; run the disposable-repo edit experiment described in the executive result to close the final 1-10% deployment-state gap.**

### 2.5 Latent conflict — UNVERIFIED until activation, but fix before enabling

This is not counted as a current runtime finding because the producer is dormant, but activating it makes the following collision real.

Producer, `hooks/edit-checkpoints/checkpoint.py:133-143`, verbatim:

> Clean tree (no dirty changes) -> the restore point is just HEAD.  
> `rc2, head, _ = _run_git(repo, "rev-parse", "HEAD")`  
> `kind, restore = "git-head-clean", (head if rc2 == 0 else "")`  
> ...  
> `"restore": restore`

Consumer, `commands/rollback.md:38-39`, verbatim:

> `git-head-clean` — the tree was clean at that turn; revert edits with  
> `git -C <repo> checkout -- <path>` (or `git -C <repo> restore <path>`).

If HEAD advances after the checkpoint, the command restores from **current HEAD**, not the recorded checkpoint HEAD. The producer deliberately stores the old SHA, but the consumer ignores it. The runtime consumer would win because it issues the actual restore command.

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Change the command recipe to preview and restore explicitly from `<restore_sha>` for `git-head-clean`, e.g. `git -C <repo> diff <restore_sha> -- <path>` followed, only after confirmation, by `git -C <repo> restore --source=<restore_sha> -- <path>`. Also state that this restores file content, not remote/MCP side effects. This one-line authority repair is **very likely (80-90%)** to select the recorded state because the hook stores that exact SHA at `checkpoint.py:134-143`; **UNVERIFIED against staged/untracked edge cases, settled by a test that checkpoints clean HEAD A, commits HEAD B, dirties the file, and restores from A.**

## 3. Finding A084-F2 — Codex monitor manual and automatic launch paths disagree

**Severity:** Medium: duplicated launch policy can reproduce the exact terminal-host failure the command says was observed, and it makes manual versus automatic behavior inconsistent.  
**Class:** active split authority.  
**Runtime status:** direct settings registration is present.

### 3.1 Both authorities, verbatim

Command launch authority, `commands/codex-monitor.md:9-12`:

> Run this Bash command to open the board (new console window, live self-refreshing):  
> `powershell -NoProfile -File "C:/Users/Prekzursil/.local/bin/codexmon.ps1" --since-min 120`

Command rationale, `commands/codex-monitor.md:31-33`:

> The guard wrapper lives in `~/.local/bin/codexmon.ps1` ...  
> The wrapper launches via `Start-Process` in a plain new console rather than `wt new-tab`: the board's interactive loop was observed to exit under wt's ConPTY.

Active hook launch authority, `hooks/codex-monitor-autolaunch/check.py:57-68`:

> `def _launch() -> bool:`  
> `    """Open codex-monitor in a reusable named Windows-Terminal window; fall back to a console."""`  
> `    for cmd in (`  
> `        ["wt", "-w", "codexmon", "new-tab", "--title", "codexmon", "powershell", "-NoProfile", "-File", str(LAUNCH)],`  
> `        ["cmd", "/c", "start", "codexmon", "powershell", "-NoProfile", "-File", str(LAUNCH)],`  
> `    ):`  
> `        ... subprocess.Popen(cmd, creationflags=_DETACHED, close_fds=True)`  
> `        return True`

### 3.2 Concrete collision

When Claude calls `mcp__codex__codex`, the direct PreToolUse registration at `settings.json:272-281` runs `codex-monitor-autolaunch/check.py`. If `wt` is installed and `Popen` succeeds, the hook returns immediately after selecting the Windows Terminal branch (`check.py:59-68`). That is precisely the transport the command’s operator-facing authority says was retired because of observed ConPTY exits.

The duplicate is not theoretical: both paths address the same guarded wrapper (`commands/codex-monitor.md:11`, `hooks/codex-monitor-autolaunch/check.py:35-40`) and the automatic path is wired to a real event.

### 3.3 Which authority wins at runtime

Runtime precedence is split by trigger:

- **Automatic native-MCP launch:** the hook wins. `settings.json` runs it before the Codex tool, and its first successfully spawned command wins.
- **Explicit `/codex-monitor`:** the command wins. Its expanded prompt instructs Claude to call the wrapper directly.
- **Inside the wrapper:** **UNVERIFIED**. The wrapper is outside the subject bundle, so I cannot determine whether it detects/nests out of the outer `wt` host or whether the board inherits ConPTY. The exact Windows process-tree experiment named above settles it.

There is a second internal drift signal, not a separate command conflict: the hook docstring says it is wired through the dispatch manifest and can self-filter Bash/PowerShell `codex exec` (`check.py:4-16`), but the actual direct settings matcher is only `mcp__codex__codex` (`settings.json:272-281`) and the manifest does not contain this script. Thus automatic opening for shell `codex exec` cannot arise through this local hook in the snapshot.

### 3.4 Minimal resolution — UNVERIFIED wrapper behavior

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Remove terminal-host selection from `codex-monitor-autolaunch/check.py`; invoke the canonical wrapper directly with `powershell -NoProfile -File <LAUNCH>`, letting `codexmon.ps1` own singleton enforcement and console selection exactly once. Keep the per-session reminder lock only if it provides distinct value from the wrapper’s machine-wide guard.

This is **likely (55-80%)** to make manual and automatic launch behavior coherent because both paths will enter the same wrapper with no outer `wt` policy. The lower band reflects the missing wrapper source. **UNVERIFIED; the settling experiment is one manual `/codex-monitor` launch and one MCP-triggered auto-launch, comparing process host, singleton count, and survival after two refresh intervals.**

This proposal uses the existing hook and wrapper, adds no new runtime, and passes the anti-overfit gate.
