# F030 — Blue-team red-team: shared secrets → exfiltrate a secret

**Unit:** F030  
**Date:** 2026-07-19  
**Mode:** defensive analysis only; no credential value was printed, validated with a provider, transmitted, or used. No live control was changed.  
**Subject:** the deployed Claude/Codex/shared-harness configuration and the named shared credential stores on this Windows host.

## Executive verdict

The most plausible exposure path in this harness is an instruction—directly pasted by the owner or indirectly encountered in web/MCP/tool content—that induces an agent to read a plaintext shared credential file and transmit its contents through an already-authorized network channel. This is not a generic possibility assembled from product defaults: the local configuration combines all three required conditions:

1. **Readable secret source.** `C:\Users\Prekzursil\.codex\auth.json`, `C:\Users\Prekzursil\.claude\.credentials.json`, and both hub `accounts.json` working copies exist. `Get-Acl` and the mechanically independent `icacls.exe` both show inherited `ReadAndExecute` for `CodexSandboxUsers`; `Get-LocalGroupMember` shows that group contains both `CodexSandboxOffline` and `CodexSandboxOnline` (local probes P1–P3 below).
2. **Autonomous reader.** Codex is configured with `approval_policy = "never"` and `sandbox_mode = "danger-full-access"`; Claude grants `Read`, `Glob`, `Bash`, `WebSearch`, `WebFetch`, `SendUserFile`, many network MCPs, `C:` and `D:` access, an empty `ask` list, and `defaultMode = "bypassPermissions"` (`C:\Users\Prekzursil\.codex\config.toml:6-8`; `C:\Users\Prekzursil\.claude\settings.json:26-75`).
3. **Egress.** Codex has live web search (`C:\Users\Prekzursil\.codex\config.toml:8`), while Claude explicitly allows web, file-send, shell, and network-MCP tools (`C:\Users\Prekzursil\.claude\settings.json:27-62`). The corpus confirms these are active, not decorative: 19,181 PowerShell calls, 61,165 Read calls, 8,316 WebSearch calls, and 8,042 WebFetch calls (`corpus/corpus.json:8871-8905,9026-9045,9187-9210`).

**Feasibility assessment:** **very likely (80-90%)**, based on the convergent ACL, group-membership, settings, guard-code, regression-test, and official product-semantics evidence above. The missing 10-20% is deliberate: an end-to-end secret read plus network transmission was not and must not be tested against real credentials. The exact live exploit chain is therefore **UNVERIFIED; an isolated canary-file/local-fake-sink test under both provider identities would settle it without exposing a credential**.

**Comparative assessment:** this is **likely (55-80%)** to be the most plausible shared-secret exfiltration path, rather than Git-history theft or a novel memory attack, because it needs no new executable, persistence, privilege escalation, or remote service compromise and it uses the harness's most frequently exercised native tools. The evidence is the locally verified configuration plus Anthropic's 2026 controlled red-team report: a malicious collaboration prompt asked Claude Code to read a credential file and post it externally, and the agent completed the action in 24 of 25 retries; Anthropic concludes that filesystem and egress boundaries are the controls that hold. See [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude). That external result establishes plausibility, not that this owner has been attacked.

I found **no evidence that a real credential was exfiltrated**. This unit establishes exposure and a missing preventive boundary, not compromise.

## Threat statement and security boundary

### Attacker capability

The attacker does not begin with local code execution or Windows credentials. The realistic initial capability is control of text the agent processes: an issue, README, webpage, search result, MCP response, pasted collaboration prompt, or other model-visible content. OpenAI describes the same class as instructions embedded in external content that cause unintended agent actions, and notes that URL requests can carry private data to server logs even when the chat never prints it ([Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/); [Keeping your data safe when an AI agent clicks a link](https://openai.com/index/ai-agent-link-safety/)).

This attacker needs the model to cross two boundaries:

`untrusted content → local secret read → outbound network action`

Model refusal is useful defense in depth, but it is not a deterministic boundary. OpenAI's public agent system card reports materially lower success on active data-exfiltration resistance than on merely ignoring irrelevant text, and explicitly treats prompt injection plus tool access as the risk ([ChatGPT Agent System Card, §3.1.1–3.1.2](https://deploymentsafety.openai.com/chatgpt-agent/risk-description-1)).

## Most plausible abuse path — defensive characterization, not exploit instructions

### Phase 1: instruction enters a trusted planning loop

An agent processes attacker-controlled prose from an issue, repository, website, MCP result, or owner-pasted collaboration request. The content reframes credential access and an outbound request as a task prerequisite. This phase can exploit the fact that user intent and tool-return content are operational inputs to the same agent loop.

This is **likely (55-80%)** to be the highest-probability entry rather than malware already running locally, because the harness is explicitly a research/build system with thousands of web calls and 93 MCP servers touched, while local malware would already possess simpler credential theft options. Evidence: corpus tool counts above and the prompt-injection mechanism documented by both OpenAI and Anthropic. The relative likelihood is a reasoned comparison, not incident telemetry.

### Phase 2: the agent reaches a shared secret

The agent selects a native file-reading tool or shell. For Codex, the OS and application policy allow the operation: the file ACL grants its group read access, `danger-full-access` governs filesystem/network command execution, and `never` removes the approval pause. OpenAI's configuration reference defines `sandbox_mode` as the filesystem/network policy and `approval_policy` as when Codex pauses ([Codex configuration reference](https://developers.openai.com/codex/config-reference)).

For Claude, the permissions explicitly allow broad reads and shell access across both drives. The deny list covers `.env`, PEM, and `*.credentials*`, but it does not name `auth.json` or the hub `accounts.json` files (`.claude/settings.json:64-75`). Its shared `PreToolUse` matcher covers shell and MCP, but not `Read`, `Glob`, `WebSearch`, or `SendUserFile` (`.agents/harness/registration.py:60-72`; deployed copy at `.claude/settings.json:139-150`). Official Claude hooks documentation states that `PreToolUse` matches on tool name and can block before execution; an omitted tool therefore never reaches that hook ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)).

### Phase 3: bytes leave the host

The agent can combine local access with an existing outbound channel: a shell-launched HTTPS client, a network-capable MCP operation, a file-send action, or a URL/query whose attacker-controlled destination logs the request. A direct shell operation is especially important defensively because secret bytes may be read and transmitted inside one child process without ever appearing as literal text in the pre-tool hook input.

The exact destination and encoding are intentionally omitted. A defender does not need those details: the invariant is a process or tool invocation that has both a sensitive local source and an external sink, or two correlated invocations in one session/turn.

### Phase 4: persistence multiplies impact

If the bytes pass through model-visible tool output, `save-all` history and long Claude retention can create additional local copies. If a shell sends them directly, transcripts may record the command/path/destination but not the bytes. This distinction matters for response: a post-incident search must inspect both provider histories and OS process/network telemetry, not only chat messages.

The claim that raw transcripts contain hook telemetry is supported by two mechanically independent measurements already captured in the pinned defect input: 186 transcript files carried hook events, and a byte-stratified sample independently found 497/768 sampled records were async hook responses (`INPUT-known-harness-defects.md:133-140`). The corpus's own `hooks` section remains unusable: its live `DETECTOR_STATUS` says the detector is broken (P9). No conclusion here relies on that corpus section.

## Does an existing control stop this path?

**No.** Several partial controls exist, but none creates a complete source-to-sink boundary in the deployed state.

### 1. NTFS ACL — does not stop Codex sandbox reads

- Signal A: `Get-Acl` reports inherited `ReadAndExecute` and `Modify`-class permissions for `CodexSandboxUsers` on both auth stores and both hub stores (P2).
- Signal B: `icacls.exe`, a mechanically independent ACL renderer, reports inherited `(RX)` plus `(M,DC)` for the same group on sampled auth/hub files (P2).
- Principal expansion: `Get-LocalGroupMember` reports both Codex sandbox identities in that group (P3).

The ACL detector's known-present control was the owner ACE: both renderers also found the expected owner/administrator full-control entries. This avoids inferring absence or presence from an unvalidated detector.

### 2. Shared credential-read guard — present but deliberately inactive

The module contains a credential filename regex including `.env`, `auth.json`, credentials files, SSH keys, and AWS credentials (`.agents/harness/modules.py:641-643`). It blocks a matching inspection only when `_credential_guard_enabled()` returns true (`:791-798`). That predicate is explicitly opt-in and defaults off (`:50-62`).

Two independent signals verify the deployed inactive state:

- A Process/User/Machine name-only check found `HARNESS_CREDENTIAL_GUARD` absent at all three scopes; the same detector found `PATH` at all three scopes as its known-present control (P4).
- Regression tests intentionally remove the variable and assert credential reads are allowed, then set it and assert `credential_read` blocking (`.agents/harness/tests/test_modules.py:266-300`).

Even if enabled, Claude's deployed matcher omits the native `Read` tool, while the official hook API supports matching `Read` (`.agents/harness/registration.py:60-72`; [hooks reference](https://code.claude.com/docs/en/hooks)). The existing guard therefore does not cover every local read path.

### 3. Secret-literal guard — does not inspect runtime-generated bytes

`contains_secret(text)` is applied to the pending tool input before execution and only when `HARNESS_SECRET_GUARD` is enabled (`.agents/harness/modules.py:746-762`). The switch is also opt-in/off by default (`:84-99`), and the same name-only probe found it absent while finding `PATH` (P4). More fundamentally, a command that refers to a file does not contain the file's eventual bytes in its pre-execution input. This guard can catch an already-materialized literal in a later call, but cannot by itself prevent a single process from reading and transmitting a file.

### 4. Native permission modes — configured in the unsafe direction

Codex's no-approval/full-access/live-search settings are direct at `.codex/config.toml:6-8`. The official reference says `danger-full-access` is a filesystem/network sandbox policy, `never` is the non-interactive approval mode, and `live` permits unrestricted live retrieval ([Codex configuration reference](https://developers.openai.com/codex/config-reference)).

Claude's `bypassPermissions` setting is direct at `.claude/settings.json:71`. Anthropic's official documentation says that mode disables permission prompts and safety checks and recommends it only in isolated environments without internet access; this host is neither isolated from user data nor configured without internet ([Claude permission modes](https://code.claude.com/docs/en/permission-modes)).

### 5. Codex keyring settings — intended control is scoped incorrectly

The live TOML places `cli_auth_credentials_store = "keyring"` and `mcp_oauth_credentials_store = "keyring"` under `[tui]` (`.codex/config.toml:42-48`), while the official schema lists both as root configuration keys and defines the former as selecting `auth.json` versus the OS keychain ([Codex configuration reference](https://developers.openai.com/codex/config-reference)). `auth.json` still exists and contains credential field names (P1, P5).

It is **very likely (80-90%)** that the misplaced keys are not controlling the root credential-store setting, based on TOML table semantics, the official root-key schema, and the remaining plaintext store. Runtime resolution is **UNVERIFIED; a non-writing resolved-config diagnostic followed by a canary login in an isolated `CODEX_HOME` would settle it**.

### 6. `git-crypt` — protects repository blobs, not unlocked working copies

Both account stores have `filter=git-crypt` and `diff=git-crypt` (P8; `.gitattributes:1-13`). That is worth preserving. It does not stop a local process with NTFS read access from reading the decrypted files used by the live hubs.

### 7. Persistence redaction — useful after the fact, not a network gate

The shared ledger stores result hashes, not bodies (`.agents/harness/modules.py:1048-1077`), but a pre-execution network transfer is complete before PostToolUse persistence logic runs. Redaction reduces secondary copies; it cannot recall bytes already sent.

## Minimal mitigation

The minimum defensible change is a **two-boundary rule** on the existing provider/OS buses:

> An autonomous agent must not be able to read raw reusable credentials, and a process that can read sensitive user data must not have unreviewed arbitrary egress.

Fixing only one side leaves an easy alternate path. The following is the smallest coherent bundle; it introduces no second orchestrator, vector store, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### M1 — Move Codex authentication out of model-readable files

**NATIVE (Claude Code already does this; we just enable it)**

Move the two credential-store keys to TOML root, verify Codex resolves them as `keyring`, re-authenticate through the native client, and only then remove the obsolete plaintext `auth.json`. Preserve the existing age-encrypted MCP OAuth store if still in use. Do not copy token values through prompts, shell arguments, migration logs, or the event ledger.

This is **almost certain (90-99%)** to remove the verified `auth.json` raw-file target after successful migration, because the official setting explicitly selects file-based `auth.json` versus the OS keychain. The remaining uncertainty is Windows-client behavior in this installed version; the isolated `CODEX_HOME` canary above settles it before touching the real store.

### M2 — Deny sensitive paths at the provider filesystem boundary

**CONFIG (settings/JSON only)**

- Replace Codex `danger-full-access` with a named native permissions profile that denies reads of the credential roots/files and grants only the workspace paths needed for the task. The current official Codex reference supports absolute/glob filesystem rules with `"deny"` and documents `:read-only`/`:workspace` bases.
- In Claude, remove `bypassPermissions` as the user-wide default, remove broad drive roots where they are not necessary, and add explicit deny rules for `auth.json`, both `accounts.json` locations, credential directories, private keys, and other broker stores. A scoped allow for a specific user-authorized diagnostic can be temporary and exact.

This is **very likely (80-90%)** to block native file-tool access when rules are correctly resolved, based on official permission semantics. Shell and alternate-path coverage is **UNVERIFIED; an isolated canary matrix using path normalization, junction/symlink aliases, 8.3 names, case variants, and both providers would settle it**. The recommendation therefore requires that matrix before declaring the boundary complete.

### M3 — Make the shared guard complete and default-on for raw credential access

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Keep `SecretGuardModule` first in `build_default_modules()` (`.agents/harness/modules.py:2599-2613`), but change credential-read protection from an opt-in filename regex to a default-on canonical-path decision:

- Match every tool capable of file discovery/read or egress, including `Read`, `Glob`, `Grep`, `Bash`, `PowerShell`, `WebSearch`, `WebFetch`, `SendUserFile`, and `mcp__.*`.
- Normalize tool-specific paths before comparison; compare resolved paths against a small sensitive-path inventory. Do not scan prose bodies for filenames, which would repeat the measured use-vs-mention false-positive defect (`INPUT-known-harness-defects.md:100-107`).
- Treat a sensitive-path read as `deny` by default. Permit only exact, current-turn owner authorization for a named path and read-only purpose; never authorize egress with the same grant.
- Fail closed for this narrow high-impact class, while unrelated advisory hooks remain fail-open.

This is **very likely (80-90%)** to close the currently demonstrated hook gaps, because both provider registrations already carry `PreToolUse`, the module already emits terminal blocks, and official Claude hooks can deny before execution. Completeness is **UNVERIFIED; the isolated canary matrix in M2 plus a forced hook-timeout case would settle it**.

### M4 — Gate arbitrary egress when local secrets/user data are in reach

**CONFIG (settings/JSON only)**

- Change Codex from `approval_policy = "never"` to an interactive/granular policy for network/open-world actions and change live search to cached/indexed/disabled when work touches credential or personal-data roots.
- Remove blanket Claude allows for `SendUserFile` and open-world MCP/network tools; require an exact destination/purpose approval. Ensure the shared `PreToolUse` matcher actually includes every outbound tool.
- Prefer domain-scoped environment injection at the client/provider boundary: the agent sees a reference, and the approved provider process receives the credential only for its intended destination. OpenAI describes this design for hosted containers: centralized egress policy plus domain-scoped secret injection keeps raw values outside model/container context ([Equipping the Responses API with a computer environment](https://openai.com/index/equip-responses-api-computer-environment/)).

This is **likely (55-80%)** to materially reduce exfiltration even when model-layer prompt-injection defenses fail, based on the deterministic removal of arbitrary sinks and the vendor boundary designs. Exact usability cost and required destination set are **UNVERIFIED; a seven-day name/domain-only observation period followed by a replay of legitimate task fixtures would settle them without collecting payloads**.

### M5 — Harden decrypted account stores and reject new literal persistence

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Change the existing account-tool schema and `_op_add` validation so environment-mode accounts accept `${ENV}` references only; reject literal values before `_persist`. Remove inherited sandbox-group access from decrypted stores and grant only the specific hub service identity that requires them. Keep `git-crypt` for repository-at-rest protection.

This is **very likely (80-90%)** to prevent future MCP tool calls from creating new plaintext literals in those files, because the current schema explicitly permits literals and persistence copies the supplied map (`accounts.py:213-218,560-586`). Whether every backend can use references is **UNVERIFIED; enumerate each `AccountPolicy` and run fake-provider fixtures to settle it before migrating existing records**.

### Ordering and incident precaution

1. First establish the deny/egress boundary with canaries.
2. Then migrate stores without exposing values.
3. Then inventory copies and decide rotation based on verified exposure, validity, and provider scope.

Do not claim that all secrets must be rotated solely from this unit: exposure is proven, exfiltration is not. Rotation becomes mandatory for any credential independently verified in public/reachable history, transcripts, or an outbound event. Audit F01 makes such claims (`findings/F01.md:11-25`), but those are neighboring-unit claims and were not re-verified here.

## Detection signature

### Primary detector — sensitive-source/outbound-sink correlation

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing shared dispatcher/ledger with two redaction-safe event types:

`sensitive_access(provider, session_id, turn_id, tool, path_class, decision)`

`outbound_action(provider, session_id, turn_id, tool, destination_domain, operation_class, decision, byte_count_bucket)`

Never log file contents, exact sensitive paths, raw query strings, authorization headers, environment values, full command lines, or reversible path encodings. The small fixed `path_class` vocabulary is sufficient for correlation and avoids creating another secret key that a same-user agent could reach.

Raise:

- **Critical:** one shell/process tool input has both a sensitive source path/class and a network/file-transfer sink.
- **Critical:** a successful sensitive read is followed in the same session by `SendUserFile`, an open-world MCP mutation, a live URL fetch/search with user-derived query material, or a network-capable child process before a fresh exact owner approval.
- **High:** any denied sensitive read followed by path-discovery retries, alias/encoding transformations, or a switch from native `Read` to shell/MCP access.
- **High:** outbound requests from `pwsh.exe`, `powershell.exe`, `bash.exe`, `curl.exe`, language runtimes, or hub processes to a destination not observed in the approved domain inventory, when the parent process is Claude/Codex/harness-related.

The retry/alias signature is particularly useful for bypass attempts, but benign diagnostics can resemble it. Its precision is **likely (55-80%)** after path-class and session correlation, based on the narrow sensitive inventory and temporal relationship; the seven-day payload-free baseline and canary red-team replay would measure the actual precision.

The detector must record terminal results as `SUCCESS:<id>` or `FAILED:<id> reason`, consistent with the behavior contract, so a block is not mistaken for an incomplete action. It must also distinguish *mention* from *use*: only tool verb plus normalized source/sink fields count, never prose content.

### Existing provider telemetry to query

- Claude debug logs can report hook matcher counts, hook commands, exits, stdout, and stderr when debug logging is enabled; the official hooks reference documents `~/.claude/debug/<session-id>.txt` and verbose matcher diagnostics ([Claude hooks reference](https://code.claude.com/docs/en/hooks)).
- Raw Claude transcripts already contain abundant hook events according to two independent pinned measurements (`INPUT-known-harness-defects.md:133-140`).
- Codex has `history.persistence = "save-all"` (`.codex/config.toml:39-40`) and the local history/log files exist (P10).
- The current shared ledger records tool name, result hash, and verification status but not raw result (`.agents/harness/modules.py:1048-1077`). It needs the redaction-safe source/sink fields above for reliable correlation.

A transcript-only detector will miss a direct child-process read-and-send that never returns secret bytes to the model. Therefore provider telemetry must be correlated with OS process/network/file telemetry.

### Windows fallback telemetry — UNVERIFIED current enablement; enablement audit settles it

**CONFIG (settings/JSON only)**

If enabled and protected from agent modification:

- PowerShell Script Block Logging produces Event ID 4104. Microsoft warns that logs may contain sensitive data and recommends Protected Event Logging outside diagnostics ([Microsoft PowerShell logging](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_logging?view=powershell-5.1)).
- Windows Security Event 4688 records process creation; full command lines require both Audit Process Creation and the separate “Include command line in process creation events” policy, and Microsoft warns those arguments are plaintext to Security-log readers ([Microsoft command-line process auditing](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/component-updates/command-line-process-auditing)).
- Targeted object-access auditing can emit Event 4663 for reads of files with the required audit policy/SACL ([Microsoft file-access auditing](https://learn.microsoft.com/en-us/windows-server/identity/solution-guides/plan-for-file-access-auditing)).
- Sysmon Event 1 records process creation, Event 3 network connections, and Event 22 DNS queries; Event 3 is disabled by default and must be selectively enabled ([Microsoft Sysmon reference](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon)).

Current enablement of 4104/4688-command-line/4663/Sysmon-3/22 is **UNVERIFIED; a read-only audit of the relevant Group Policy/registry settings, `auditpol` state, target SACLs, and Sysmon configuration—each with a known-present control—would settle it**. This unit deliberately did not alter or exercise Windows audit policy.

Because command/script logs can themselves capture secrets, prefer source/sink classification and hashes in the harness detector. If full command logging is required, use protected logging, tightly restrict log readers, and define short retention plus incident hold.

### Concrete hunting logic

Within a five-minute/session window, correlate any of:

1. A `PreToolUse`/process/file-audit event touching the `codex-auth`, `claude-credentials`, `hub-accounts`, `ssh-private-key`, `cloud-credentials`, or `env-secret-store` path class.
2. A subsequent outbound event whose parent/ancestor is Claude, Codex, the shared dispatcher, PowerShell/Bash, a language runtime launched by them, or an MCP hub.
3. A destination outside the task's approved domain set, a URL/query length or entropy jump, an outbound body-size jump, or repeated DNS labels from the same process.
4. A preceding prompt/tool result from an external source followed by an unusual shift from research/edit tools to credential-path discovery.

Do not alert on entropy alone. The corpus shows the current secret heuristic false-positives on UUIDs and hashes (`.agents/harness/modules.py:84-93`); require a sensitive source, an outbound sink, or a retry sequence.

## Verification plan using only canaries

The following experiment settles every material UNVERIFIED enforcement premise without live credentials or external exfiltration:

1. Create an isolated temporary home/workspace and a fake credential file containing a unique non-secret canary.
2. Run Claude and Codex test harnesses under the real provider hook/config parsers but with a local fake network sink that cannot route externally.
3. Exercise tool classes, not exploit recipes: native read/discovery, shell read, MCP read, file send, live URL/query, one-process source+sink, and two-step source then sink.
4. Repeat with canonical path, relative path, case variant, junction/symlink, 8.3 alias, quoted path, and tool-name variations.
5. Force the shared hook to timeout and throw; the sensitive action must remain denied.
6. Assert that no fake sink receives the canary; every attempt yields a terminal block receipt; telemetry contains source/sink classes but never the canary.
7. Run legitimate fixtures that mention credential filenames in prose and use approved provider APIs through `${ENV}` references; these must pass.

Passing all seven is required before saying the surface is adequately defended. The expected outcome after M1–M5 is **very likely (80-90%)**, based on the existing hook transport and native permission primitives; only this experiment can promote that prediction to “done.”

## Anti-overfit gate and rejected alternatives

1. **A second orchestration runtime or generic “AI firewall”: rejected.** OpenAI notes that classifier-style intermediary firewalls do not reliably catch developed prompt-injection attacks ([Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)). It would also violate the brief's rejected-component list.
2. **A new vector database/knowledge graph for security state: rejected.** Sensitive source and outbound sink are small deterministic inventories plus short-window events; semantic retrieval adds attack surface without improving the boundary.
3. **A durable-execution engine: rejected.** PreToolUse deny, native filesystem permissions, OS ACLs, and native approvals already provide the necessary buses.
4. **A trained critic or model-only monitor: rejected as the primary control.** The attack manipulates the model; a deterministic filesystem/egress boundary is independently enforceable.
5. **Secret regex alone: rejected.** It misses runtime-generated bytes and has measured false positives on benign high-entropy material (`modules.py:84-93`).
6. **Git encryption alone: rejected.** It protects blobs at rest, not decrypted working copies.
7. **Environment-variable indirection alone: rejected.** A child process that inherits a broad environment can still read values. Indirection is useful only with per-process allowlists or domain-scoped injection.
8. **Observability SaaS: rejected.** Local provider hooks, Windows eventing, and the existing ledger are enough; a new SaaS creates another secret-bearing egress destination.

The recommended architecture stays deliberately small: native permission/keyring settings plus a sub-200-line canonical source/sink guard on the already-deployed hook bus.

## Final defender decision

This surface is **not adequately defended**. The conclusion is **almost certain (90-99%)**, supported by two ACL renderers, group expansion, direct active settings, guard code, guard regression tests, official provider semantics, and real capability-use counts. The residual 1-10% reflects the deliberately unexecuted end-to-end chain, not uncertainty about the deployed absence of a complete source-to-sink control.

The best response is evolution on the existing buses, not replacement: native keyring and permission primitives, corrected ACLs, one canonical-path/source-sink module on the shared hook dispatcher, and redaction-safe correlation with Windows telemetry. It satisfies the anti-overfit gate and directly addresses the failure mode that both Anthropic's controlled red-team and OpenAI's current agent-security guidance identify: raw secret reachability combined with arbitrary egress.
