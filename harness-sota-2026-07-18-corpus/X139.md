## Executive result

The borrow **does transfer, but only in a deliberately narrow form**. The useful mechanism is not “make the agent safer,” nor is it the Swiss-cheese picture by itself. It is STPA’s method of treating resource allocation as a **context-dependent control action in a feedback loop**, enumerating how that action can be wrong, deriving constraints, and monitoring the assumptions that make those constraints valid. NASA’s risk-informed safety-case practice contributes a second useful idea: a decision at a milestone is justified by an explicit claim, argument, and evidence, and that case is evaluated before risk is accepted. HSE’s ALARP practice contributes proportional depth: analysis rigor grows with the risk, while established good practice can suffice at the low end. These are mechanisms for directing scarce analytic attention rather than spreading it evenly ([MIT STPA Handbook, pp. 35–46, 100–114](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf); [NASA System Safety Handbook Vol. 2 record](https://ntrs.nasa.gov/citations/20150015500); [HSE ALARP guidance, paras. 8–20](https://www.hse.gov.uk/foi/internalops/hid_circs/permissioning/spc_perm_37/)).

The concrete translation is a **Compute Control Case**: a small controller on the existing hook/rule bus that grants compute in increments. Each increment is tied to (1) a consequential unresolved claim, (2) a named evidence gap, (3) the cheapest action capable of discriminating between live alternatives, and (4) a stop condition. It also preserves a task/global reserve and stops repeated actions that do not change the evidence state. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**, not a scheduler service, model router daemon, trained critic, or second orchestration runtime.

**Bottom-line confidence:** **very likely (80-90%)** that the STPA control-loop framing will expose allocation errors missed by flat token/tool/time caps, because the official STPA procedure systematically tests omission, commission, timing/order, and duration in a specified context, while a cap tests only amount ([MIT STPA Handbook, pp. 35–38](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). **UNVERIFIED—Experiment E1 (retrospective counterfactual replay) must establish how many real task outcomes or costs it would have changed.** It is only **likely (55-80%)** that the proposed lightweight runtime will improve answer-change-per-unit-cost in this owner’s workload, because adaptive-compute research supports non-uniform allocation but does not validate this rule set, this harness, or open-ended agent tasks ([Damani et al., ICLR 2025](https://openreview.net/forum?id=6qUUgw9bAZ); [CATS, 2026](https://openreview.net/forum?id=mXuUomGc0I)). **UNVERIFIED—Experiment E2 (shadow-mode randomized budget trial) must settle that efficacy claim.**

## 1. The mechanism in its own field

### 1.1 STAMP: safety is a control problem, not merely a component-failure count

STAMP models safety as an emergent system property maintained by constraints in a hierarchical control structure. A controller acts on a controlled process through control actions and receives feedback; its internal process model can be wrong even when every component is operating as designed. The official handbook explicitly motivates STPA with losses caused by unsafe component interactions in which no component failed, and it includes software, humans, organizations, feedback, and process-model flaws in the analysis ([MIT STPA Handbook, pp. 3–10](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

This matters in systems safety because a component reliability decomposition can miss an accident produced by individually “correct” components interacting in the wrong state. The handbook’s braking examples show the controller issuing or withholding a command because its model of touchdown, wheel speed, or stopping state is wrong; the unsafe result depends on context and feedback, not simply whether the brake component failed ([MIT STPA Handbook, pp. 35–46](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

The specific STPA procedure used by this borrow is:

1. Define unacceptable losses and system-level hazards.
2. Model the control structure: controllers, control actions, controlled processes, feedback, and relevant process-model variables.
3. For every control action, enumerate four ways it can become unsafe:
   - it is not provided when needed;
   - it is provided when unsafe;
   - it is provided too early, too late, or in the wrong order;
   - it lasts too long or stops too soon.
4. State the **context** that makes the action unsafe. The handbook emphasizes that a control action cannot be judged without this context.
5. Derive causal scenarios, constraints, design requirements, and feedback needed to prevent the unsafe action ([MIT STPA Handbook, pp. 14–53, especially pp. 35–46](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

This is more than a four-cell checklist. The controller’s process model is part of the causal analysis: delayed, absent, misinterpreted, or out-of-order feedback can leave the controller believing the process is in the wrong state ([MIT STPA Handbook, pp. 45–46](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). That feature is the heart of the cost-control transfer.

### 1.2 Assumption-based leading indicators: monitor why the control was believed adequate

STPA’s operational-risk extension does not merely count incidents. It identifies the assumptions under which a design and its controls were expected to work, then creates indicators that warn when an assumption is broken, weakening, or changing. The handbook distinguishes assumptions that were wrong initially, implementation/operation that departs from design, and later environmental or system changes that invalidate once-correct assumptions. It also requires a management response; detection without an action process is explicitly described as insufficient ([MIT STPA Handbook, pp. 100–114](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf); [Leveson, “A Systems Approach to Risk Management through Leading Safety Indicators”](https://sunnyday.mit.edu/leadingindicators-published.pdf)).

In its own field, an indicator is therefore not just a generic dashboard metric such as “maintenance backlog.” It is traceable to a particular hazard, control, and assumption. “This interlock remains effective if sensor latency stays below X” yields an indicator for latency and a predefined response. The handbook calls future events that trigger assumption checking “signposts,” and distinguishes preventive shaping actions from hedging/contingency actions ([MIT STPA Handbook, pp. 111–114](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

### 1.3 Risk-informed safety cases: allocate rigor at decision gates

NASA’s System Safety Handbook Vol. 2 describes a risk-informed safety case (RISC) at major milestone reviews: objectives define adequate safety, integrated safety analysis informs decisions, the case argues that objectives are satisfied, and evaluators assess both claims and supporting evidence before accepting risk ([NASA System Safety Handbook Vol. 2 record and download](https://ntrs.nasa.gov/citations/20150015500)). A NASA technical memorandum distinguishes an **assurance argument**—reasoning from premises to a conclusion—from the fuller **assurance case**, which also contains test plans, analysis reports, configuration/change material, and other support. It cautions that small argument fragments are not complete safety cases ([NASA/TM-20250001849, Appendix B](https://ntrs.nasa.gov/citations/20250001849)).

The useful cost-control mechanism is the gate, not the ceremonial document: before accepting residual uncertainty or spending the next tranche of scarce analysis, expose the claim, evidence, assumptions, and defeaters. NASA’s own research is cautious about the effectiveness of assurance cases; a year-long study organized claimed benefits alongside evidence, counter-evidence, and caveats rather than assuming the artifact “works” by definition ([NASA/CR-2017-219582](https://ntrs.nasa.gov/citations/20170003806)). That caution is important for the translation: a compute case must be a tiny runtime decision record, not paperwork mistaken for epistemic progress.

### 1.4 ALARP: proportional depth, with an important asymmetry

HSE’s ALARP guidance separates intolerable, tolerable-if-ALARP, and broadly acceptable regions. It says assessment depth should be proportionate to the scale and nature of hazards and should range from qualitative at the low end through semi-quantitative to quantitative at the high end. For tolerable risks, the operator asks what more could reduce risk and why it has not been done; a reasonable measure is expected unless its cost is grossly disproportionate to the benefit. Significant hazards must still receive authoritative good-practice controls, and controls must be reviewed as knowledge and techniques change ([HSE ALARP guidance, paras. 8–20 and 45–47](https://www.hse.gov.uk/foi/internalops/hid_circs/permissioning/spc_perm_37/)).

This is **not** ordinary cost-benefit optimization. In safety law the burden is intentionally asymmetric toward risk reduction, and “gross disproportion” does not mean equal dollars on both sides. The translation may borrow “depth proportional to consequence and uncertainty,” but it may not borrow HSE’s legal thresholds or pretend answer quality is commensurable with loss of life.

### 1.5 Swiss cheese and normal accidents: useful constraints, not the selected allocator

Reason’s Swiss-cheese model represents defenses, barriers, and safeguards as layers with weaknesses; harm occurs when weaknesses align along a trajectory. The original healthcare exposition distinguishes active failures near the event from latent conditions in the system ([Reason, “Human error: models and management,” BMJ 2000](https://www.bmj.com/content/320/7237/768)). It contributes one useful warning: “verification exists” is not enough if all verification layers share the same hole—for example, the same model, prompt, source, or stale state.

But Swiss cheese is **not selected as the allocation mechanism**. It is a descriptive barrier metaphor with no native rule for pricing another sample, deciding when evidence is saturated, or reserving quota. A later study found that even safety professionals interpreted elements of the picture inconsistently, illustrating the danger of treating the diagram as an executable theory ([Perneger, “The Swiss cheese model of safety incidents: are there holes in the metaphor?”, 2005](https://pmc.ncbi.nlm.nih.gov/articles/PMC1298298/)).

Normal-accident theory contributes an architectural constraint. Perrow’s two relevant properties are interactive complexity—unanticipated interactions—and tight coupling—failures cascading before they can be isolated. The National Academies applies those definitions to software-intensive dependable systems ([National Academies, *Software for Dependable Systems*, Observation 4](https://www.nationalacademies.org/read/11923/chapter/3)). For this unit, the implication is not “agent cost overruns are inevitable.” It is: do not answer an allocation problem by adding a tightly coupled orchestration stack whose own hidden interactions consume the savings. This directly supports the mandatory anti-overfit gate.

## 2. Structural mapping: what genuinely corresponds

| Systems-safety element | Cost-control analogue | Why the relation is structural rather than rhetorical |
|---|---|---|
| Unacceptable loss | A materially wrong high-consequence answer; quota exhaustion that prevents later priority work; runaway spend with no answer change | Both define what the controller exists to prevent before choosing metrics. |
| Hazardous system state | High-stakes claim remains unresolved at stop; low-value branch consumes reserve; repeated failures consume budget without new evidence | A hazard is a system state that can lead to loss, not the loss itself. |
| Controller | Harness policy plus runtime hook/rule | It selects model effort, tool calls, verification, branching, continuation, or stop. |
| Controlled process | The live task trajectory and evidence state | Resource grants change the trajectory; outcomes and tool results change what is known. |
| Control actions | Start, escalate, verify, branch, retry, downgrade, stop, reserve | These are discrete decisions whose safety/value depends on state and timing. |
| Feedback | Tests, source support, answer stability, branch disagreement, tool errors, spend, remaining reserve | Without these, “continue” is open-loop spending. |
| Process model | Stakes, reversibility, unresolved claims, evidence independence, tool health, budget remaining | Wrong state estimates produce wrong allocation even if the hook executes perfectly. |
| Constraint | “Do not stop while a consequential claim lacks its required evidence”; “do not retry unchanged”; “preserve reserve” | Constraints specify behavior to prevent hazards rather than predicting every failure chain. |
| Leading indicator | Repeated no-change actions, correlated verifiers, rising error rate, reserve breach, unstable conclusion | Each is tied to an assumption behind the allocation policy. |
| Milestone safety case | Micro-case for another compute tranche or for stopping | Both expose the claim, evidence, residual uncertainty, and decision at a gate. |

**Transfer judgment:** **very likely (80-90%)** that this mapping preserves the essential controller/action/feedback/process-model structure, because resource allocation in an agent is literally a sequential control decision under partial state feedback, and STPA is defined around those elements ([MIT STPA Handbook, pp. 10–13 and 24–31](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). This is an analytic judgment, not an empirical performance claim.

The key change of objective is explicit: in safety, the controlled variable is constraint satisfaction against unacceptable loss; here, it is **marginal answer change per unit resource, subject to consequence-sensitive evidence floors and a global reserve**. The translation is valid only after changing that objective. Calling tokens a “hazard” without doing so would be category error.

## 3. Adversarial analysis: where the analogy breaks

### 3.1 Human harm and token cost are not commensurable

Safety engineering often addresses irreversible injury, death, environmental damage, and public risk. Compute expenditure is usually reversible financial/latency loss. Therefore ALARP’s burden of proof, tolerability regions, and gross-disproportion doctrine cannot be copied. A task may rationally accept a greater probability of a wrong answer to save cost when the answer is advisory and reversible; that would be unacceptable in some safety contexts. This is an almost certain (90-99%) disanalogy because it follows from the different loss functions, with HSE’s legal framing as direct evidence of the safety side ([HSE ALARP guidance, paras. 3–17](https://www.hse.gov.uk/foi/internalops/hid_circs/permissioning/spc_perm_37/)).

### 3.2 Safety constraints are often one-sided; useful agent work is exploratory

An agent may discover that the user’s framing is wrong, explore a branch with uncertain payoff, or create novel alternatives. A rigid predeclared hazard list can suppress exactly the exploration that changes the answer. STPA can analyze organizational and emergent properties beyond component failure, but it still begins by defining losses and boundaries ([MIT STPA Handbook, pp. 14–24 and 86–100](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). Thus the proposed controller must permit a bounded exploration tranche and revise its task model when evidence changes; it must not require every useful tool call to be predictable at admission.

**Confidence:** **likely (55-80%)** that an overly rigid claim/evidence gate would underfund productive exploration, based on the open-ended nature of research and software tasks rather than a harness trial. **UNVERIFIED—Experiment E3 (exploration-ablation study on discovery tasks) must compare a hard gate, a bounded exploration lane, and baseline.**

### 3.3 Failure probability is poorly calibrated for open-ended answers

Safety cases may draw on reliability tests, physical models, and domain-specific rates. For open-ended agent outputs, “probability this answer is correct” is often unavailable, model self-confidence can be misleading, and task-level success may be judged only later. The design therefore must not multiply guessed likelihood by guessed impact and call the result risk. It uses ordinal consequence classes, observable evidence gaps, and measured marginal changes instead.

**Confidence:** **very likely (80-90%)** that a universal numerical expected-loss score would create false precision across heterogeneous agent work, because no cited adaptive-compute study establishes calibrated success probabilities over such a workload; CATS supplies a statistical guarantee only under its own calibration and task assumptions ([CATS, 2026](https://openreview.net/forum?id=mXuUomGc0I)). **UNVERIFIED—Experiment E4 (calibration and selective-risk evaluation by task family) must test whether any proposed score is sufficiently calibrated before it controls spend.**

### 3.4 More defenses can cost more and fail dependently

Swiss cheese can invite “add another reviewer.” In agent systems, repeated generations from the same model and context are correlated, and reviewers consume the quota being protected. The metaphor does not tell us when layers are independent or cost-effective. The proposed design therefore records the evidence mode/source and asks whether a new action can discriminate a live alternative; it never mandates N reviewers merely because a task is “high risk.”

**Confidence:** **likely (55-80%)** that same-model repeated review has enough correlated failure to make layer count a poor proxy for assurance; the structural concern follows from Reason’s aligned-hole model, but the size of correlation in this owner’s tasks is unknown. **UNVERIFIED—Experiment E5 (paired independent-vs-correlated verifier trial) must measure defect yield per token for same-context review, fresh-context review, executable tests, and external-source checks.**

### 3.5 The controller itself spends compute and can become the accident

A full safety-case engine, optimizer, classifier, event bus, and dashboard could consume more than it saves and introduce interactive complexity. NASA cautions that an argument fragment is not a full assurance case, while normal-accident theory warns about complex interaction and tight coupling ([NASA/TM-20250001849](https://ntrs.nasa.gov/citations/20250001849); [National Academies, Observation 4](https://www.nationalacademies.org/read/11923/chapter/3)). The translation deliberately uses a micro-case and a small state machine, not a safety-case platform.

**Conclusion of adversarial gate:** the analogy survives at the **control-analysis and assumption-monitoring level**. It fails as a quantitative safety-risk model, a legal proportionality rule, or a justification for layered bureaucracy. The surviving borrow is useful precisely because the implementation can remain small.

## 4. Recommendation — UNVERIFIED pending E1/E2: Compute Control Case

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Build one per-task state record plus one pre-action/post-action policy hook. The record is a compact “compute control case,” not a prose report. The controller grants small tranches of model/tool effort and uses task feedback to continue, redirect, downgrade, or stop.

**Expected-value claim:** **likely (55-80%)** that this will increase consequential defect discovery per unit cost relative to uniform effort, because input-adaptive computation has outperformed fixed allocation in controlled language-model tasks and STPA adds consequence/evidence state that difficulty-only routing omits ([Damani et al., ICLR 2025](https://openreview.net/forum?id=6qUUgw9bAZ); [CATS, 2026](https://openreview.net/forum?id=mXuUomGc0I)). **UNVERIFIED—Experiment E2 (shadow-mode randomized budget trial) must test cost, quality, and reserve outcomes on the owner’s workload.**

### 4.1 Losses, hazards, and constraints

The initial STPA worksheet for the compute controller should be:

| ID | Unacceptable loss / hazardous state | Derived control constraint |
|---|---|---|
| L1 / H1 | A consequential, hard-to-reverse action is recommended while a decisive claim is unsupported or contradicted. | CC-1: Before stop or external action, every consequence-critical claim must have the evidence mode named by the task policy, or the uncertainty must be surfaced to the owner. |
| L2 / H2 | Quota or wall-clock reserve is exhausted on earlier low-value work, preventing later priority work. | CC-2: Preserve a configurable reserve; only the owner or an explicit priority class may consume it. |
| L3 / H3 | Additional reasoning, branches, or reviews consume material cost without changing the answer, evidence set, or uncertainty. | CC-3: Every continuation tranche must name the live alternative it can discriminate and its stop condition. Stop after the no-change threshold. |
| L4 / H4 | Repeated tool failures or unchanged retries consume budget and crowd out a different method. | CC-4: Do not repeat an action with the same failure fingerprint and materially identical inputs; redirect, repair, or surface the block. |
| L5 / H5 | The controller underfunds a deceptively simple but high-consequence task because it predicts “easy.” | CC-5: Consequence/evidence floors override predicted difficulty. |
| L6 / H6 | The controller overfunds an intrinsically hard but low-consequence task after the user’s decision is already stable. | CC-6: Difficulty alone never authorizes escalation; expected decision change must remain live. |
| L7 / H7 | Multiple checks appear independent but share the same source, model context, assumption, or stale state. | CC-7: Verification credit is based on failure-mode independence and discriminating power, not check count. |
| L8 / H8 | A once-effective allocation rule drifts as models, prices, tools, or task mix change. | CC-8: Every allocation assumption has an observable indicator and a recalibration trigger. |

These are design hypotheses, not claims about the local harness. Their completeness is **unlikely (20-45%)** on a first pass because STPA normally refines hazards and scenarios with system stakeholders and a concrete control structure ([MIT STPA Handbook, pp. 14–53](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). **UNVERIFIED—Experiment E1 plus a structured owner review must discover missing loss classes before enforcement.**

### 4.2 Control actions and contextual unsafe-control-action table

The controller has six actions: **grant initial lane, grant another tranche, escalate method/model, launch verification, retry, and stop**. Applying STPA’s four categories catches errors that “maximum tokens = N” cannot express:

| Control action | Not provided when needed | Provided when unsafe/unhelpful | Wrong time/order | Too long / stopped too soon |
|---|---|---|---|---|
| Initial compute | High-consequence task starts below its evidence floor. | Trivial/reversible task gets deep reasoning by default. | Expensive synthesis starts before cheap environment/source checks. | Probe consumes most of task budget, or ends before stakes/evidence mode are known. |
| Extra tranche | Conflicting decisive evidence receives no resolution budget. | No live alternative or answer-change path remains. | Granted before prior tool result is incorporated, or after the decision deadline. | Continuation loops after evidence saturation, or stops while a critical contradiction remains. |
| Escalation | Cheap method demonstrably cannot resolve a critical claim, but no stronger method is allowed. | Strong model/multi-branch search is used merely because the task looks hard. | Escalation precedes cheap discriminating tests. | High-cost lane persists after uncertainty collapses, or is cut before the planned discriminator returns. |
| Verification | Irreversible/high-impact recommendation has only one fragile evidence mode. | Reviewer repeats generator assumptions and adds no independent signal. | Verification occurs before there is a concrete claim/artifact to test, or only after external action. | Endless review after stable independent evidence, or one superficial check stops too early. |
| Retry | A transient failure blocks a decisive source/tool and no bounded retry occurs. | Same fingerprint and same inputs are repeated. | Retry happens before fixing malformed input or checking tool health. | Retry loop consumes reserve, or stops before a known transient backoff policy is exhausted. |
| Stop | — | Stop is issued while CC-1 or a promised deliverable remains open. | Stop precedes incorporation of pending feedback. | Agent continues after acceptance criteria close, or terminates exploratory work before its bounded tranche completes. |

The strongest novel point is contextuality. “Use high reasoning” is neither good nor bad in isolation. It is unsafe-for-cost when the conclusion is already stable and no new evidence channel is available; it is unsafe-for-quality not to use it when a high-consequence contradiction is unresolved. That is exactly the distinction the STPA UCA form forces ([MIT STPA Handbook, pp. 35–38](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

### 4.3 Minimal process model

The state record should contain only variables that change an allocation decision:

```yaml
task:
  consequence: low | medium | high
  reversibility: easy | costly | hard
  acceptance_test: <named check or owner criterion>
budget:
  spent: {tokens_or_cost, tool_calls, wall_time}
  task_cap: <value>
  protected_reserve: <value>
epistemic_state:
  decision: <current answer/action>
  critical_claims_open: [ids]
  live_alternatives: [ids]
  evidence_modes_seen: [execution, primary_source, independent_context, user]
  contradiction_count: <n>
trajectory:
  last_action: <kind>
  answer_changed: true | false
  evidence_changed: true | false
  repeated_failure_fingerprint: <id|null>
  no_change_streak: <n>
next_tranche:
  claim: <claim id>
  discriminator: <cheapest action that could alter choice>
  stop_when: <observable condition>
  maximum: <small increment>
```

Do not ask an LLM for a single numeric “difficulty” or “confidence” and treat it as ground truth. The process model separates consequence, reversibility, evidence closure, failure state, and reserve because each produces a different control action. A low-confidence but inconsequential stylistic choice need not receive more compute; a high-confidence irreversible command may still require an executable preflight check.

### 4.4 Runtime policy

The policy can be implemented as a small deterministic state machine:

```text
ADMIT:
  assign consequence/reversibility class and acceptance evidence floor
  reserve quota before any optional work
  grant a cheap probe tranche

AFTER EACH MATERIAL ACTION:
  update spend, evidence modes, open critical claims, decision, failure fingerprint
  record whether decision/evidence changed

IF critical evidence floor is unmet:
  choose cheapest action that can discriminate a live alternative
  grant one bounded tranche, unless reserve policy forbids it
ELSE IF decision changed recently and a consequential contradiction remains:
  grant one bounded resolution tranche
ELSE IF same failure fingerprint + materially same input:
  forbid identical retry; require repair, alternate path, or block report
ELSE IF no-change streak reaches threshold:
  stop optional work and produce result with residual uncertainty
ELSE IF acceptance test is satisfied:
  stop

ALWAYS:
  do not spend protected reserve without explicit priority authorization
  log why the tranche could change the answer and the stop condition
```

The fixed evidence floor is intentionally modest. Examples: a code-changing task may require the relevant executable test; a current factual claim may require a primary source; an irreversible external operation may require an exact target preflight plus explicit authority; a brainstorming task may require no independent verifier. These examples are policy templates, not universal truth.

### 4.5 Micro-case at each escalation or stop gate

At a gate, the record should answer five short questions:

1. **Claim:** What decision or output are we trying to justify?
2. **Consequence:** What changes if it is wrong, and how reversible is that change?
3. **Evidence/defeater:** What evidence supports it, and what live fact would reverse it?
4. **Next discriminator:** What is the cheapest action capable of resolving that defeater?
5. **Decision:** Spend one tranche, redirect, ask the owner, or stop with stated residual uncertainty?

This is a deliberately incomplete assurance-case analogue. Calling it a full “safety case” would violate NASA’s distinction between an argument fragment and a complete case ([NASA/TM-20250001849](https://ntrs.nasa.gov/citations/20250001849)). “Compute Control Case” is therefore a functional name, not a certification claim.

### 4.6 Assumption-based indicators and predefined responses

| Allocation assumption | Indicator that it is weakening | Predefined response |
|---|---|---|
| Extra compute usually changes evidence before it changes prose only. | Rolling answer/evidence-change rate per tranche falls. | Shorten tranche or stop optional continuation; review lane thresholds. |
| Verifiers add independent information. | Same model/context/source repeatedly agrees but executable or external checks later disagree. | Reduce credit for correlated review; prefer a different evidence mode. |
| Tool retries are transient. | Same error fingerprint recurs with identical effective input. | Trip retry breaker and require input repair or alternate tool. |
| Admission classification predicts required effort. | High-consequence post-hoc corrections cluster in “low” lane, or cheap tasks routinely escalate. | Recalibrate rules by task family; preserve consequence floor. |
| The reserve is sufficient for later priority work. | Reserve breach or priority task blocked by earlier spend. | Raise reserve or lower optional caps; never hide breach in average cost. |
| No-change streak predicts saturation. | Later audit finds missed defects immediately after forced stops. | Increase threshold for that task/evidence class; add the missed signpost. |
| Prices/model behavior remain stable. | Model/version/price/tool capability changes. | Invalidate old thresholds and run E2 canary before re-enforcement. |

This is the direct borrow from assumption-based leading indicators: each metric exists because a named assumption supports a control, and each has an action. Generic token dashboards without a linked response do not qualify ([MIT STPA Handbook, pp. 101–114](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).

## 5. What it would catch that flat budgeting misses

The following are design-level detection claims, not observations about this harness.

1. **Easy-looking, high-consequence tasks.** Difficulty routing can allocate little compute to a short command even when the cost of a wrong target is high. The consequence/evidence floor catches this before predicted difficulty is consulted. **Confidence: very likely (80-90%)**, because consequence and difficulty are independent fields in the proposed state model. **UNVERIFIED—E1 must measure real instances and false escalations.**

2. **Hard but decision-irrelevant rabbit holes.** A difficult subproblem may be intellectually hard yet unable to change the user-facing choice. The “live alternative + cheapest discriminator” gate withholds further work. **Confidence: likely (55-80%)**, because the gate directly asks marginal decision value, but an agent may misidentify what can change the answer. **UNVERIFIED—E2 must measure quality regressions and saved spend.**

3. **Open-loop retries.** A numerical retry limit permits several identical failures; a fingerprint-plus-input constraint blocks the second materially identical attempt and forces repair or redirection. **Confidence: very likely (80-90%)** for detecting identical retry loops by construction. **UNVERIFIED—E1 must determine whether fingerprint normalization is accurate enough on real traces.**

4. **Verification theater.** Counting reviewers or samples treats correlated agreement as assurance. Recording evidence mode and live defeater reveals when another check cannot discriminate anything new. **Confidence: likely (55-80%)**, grounded in Swiss-cheese dependence logic but without workload-specific correlation data. **UNVERIFIED—E5 must quantify independence and defect yield.**

5. **Premature stop after a locally successful action.** A tool can succeed while a critical claim remains unresolved; CC-1 checks evidence closure rather than tool exit status. **Confidence: very likely (80-90%)** that the state machine can distinguish these states if claims are correctly registered. **UNVERIFIED—E1 must measure claim-registration recall.**

6. **Late expensive verification.** Timing/order analysis catches an expensive branch or synthesis that begins before a cheap source lookup, environment check, or executable test. A pure cap cannot encode order. **Confidence: very likely (80-90%)** as a detection category, directly supported by STPA’s timing/order UCA ([MIT STPA Handbook, pp. 35–38](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). **UNVERIFIED—E1 must determine prevalence and achievable savings.**

7. **Quota externality across tasks.** Per-task caps do not protect future work if many individually compliant tasks consume the pool. A protected reserve makes global depletion an explicit hazard. **Confidence: very likely (80-90%)** that explicit reserve accounting detects a breach earlier than task-local accounting. **UNVERIFIED—E2 must determine the right reserve policy and opportunity cost.**

8. **Allocation-policy drift.** A once-effective rule silently degrades after a model, price, tool, or task-mix change. Signposts invalidate the threshold rather than assuming permanent validity. **Confidence: very likely (80-90%)** that version/price/task-mix signposts can detect changed premises; whether recalibration pays for itself is unknown. **UNVERIFIED—E6 (threshold drift canary) must compare old and refreshed policy after each signpost.**

9. **Overlong successful trajectories.** Error-only monitoring misses a run in which every call succeeds but none changes evidence or the decision. Answer/evidence-change streaks make “successful waste” visible. **Confidence: likely (55-80%)**, because change detection is feasible but semantic equivalence can be noisy. **UNVERIFIED—E7 (human-labeled semantic change benchmark) must set precision/recall before enforcement.**

10. **Underthinking caused by a misleading process model.** A controller may believe a source is current, a test covers the changed behavior, or a tool action completed merely because it issued the command. Explicit feedback fields expose the missing confirmation. **Confidence: likely (55-80%)**, based on STPA process-model scenarios ([MIT STPA Handbook, pp. 45–46 and 178–187](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)). **UNVERIFIED—E1 must find analogous trace cases and evaluate detector recall.**

## 6. Why not simpler or more radical alternatives?

### 6.1 Uniform caps only

**Alternative tag: CONFIG (settings/JSON only).** Uniform token/tool/time caps are cheap and remain useful as containment, but they conflate low- and high-consequence work and cannot represent omission, order, evidence closure, or quota reserve. Keep a hard cap as the final boundary; do not mistake it for an allocator.

### 6.2 Prompt-only “be efficient” rule

**Alternative tag: CONFIG (settings/JSON only).** A prompt can request a cheapest-discriminator plan and stop condition, but it cannot reliably meter cumulative spend, protect cross-task reserve, or trip on repeated external failure fingerprints without feedback. It is a suitable E1 prototype, not the final enforcement point.

### 6.3 Learned difficulty router

**Rejected alternative tag: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Input-adaptive allocation is empirically promising: Damani et al. predict reward distributions across compute budgets and allocate more computation where useful; CATS estimates success at reasoning levels and uses conformal risk control ([Damani et al., ICLR 2025](https://openreview.net/forum?id=6qUUgw9bAZ); [CATS, 2026](https://openreview.net/forum?id=mXuUomGc0I)). But a trained router requires labeled outcomes, calibration, serving, monitoring, and retraining. It also focuses primarily on input difficulty/success, whereas this target includes consequence, reversibility, tool state, reserve, and evidence independence. It fails the anti-overfit gate at present. Reconsider only if E2 shows the small rule controller leaves substantial, stable, learnable regret.

### 6.4 Full assurance-case platform or durable workflow runtime

**Rejected alternative tag: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** This would reintroduce a second orchestration/durable-execution layer explicitly disallowed by the anti-overfit gate. NASA’s distinction also shows why a tiny runtime record should not impersonate a complete assurance case ([NASA/TM-20250001849](https://ntrs.nasa.gov/citations/20250001849)). The governance overhead and coupling are contrary to the target.

### 6.5 Mandatory multi-agent panel / N-way review

**Rejected alternative tag: CONFIG (settings/JSON only).** It uniformly multiplies compute and assumes reviewer independence. Use a second perspective only when it is the cheapest discriminating evidence mode. Executable tests, primary sources, exact-target preflights, or owner clarification may be both cheaper and more independent.

### 6.6 Pure expected-value optimizer

**Rejected alternative tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A formula such as probability-of-error × impact − cost looks precise but is not grounded when correctness probabilities and impacts are heterogeneous and poorly calibrated. Ordinal consequence floors plus measured answer-change yield are more honest until E4 proves calibration.

## 7. Anti-overfit gate

The selected proposal passes the gate as designed:

- It rides the existing hook/rule/skill/MCP bus.
- It adds a bounded state record and deterministic policy, not a second runtime.
- It uses no vector database, knowledge graph, durable-execution engine, trained critic/router, observability SaaS, or guardrail framework.
- It preserves the simple baseline: hard cap, cheap probe, cheapest discriminating action, and stop.
- It can run first in shadow mode and be deleted without migrating task data.
- Its metrics are tied to explicit assumptions and actions, avoiding a new dashboard platform.

**Size feasibility:** **likely (55-80%)** that the core metering/state-transition logic fits below roughly 200 lines if the host bus already exposes pre/post action events and usage. **UNVERIFIED—Experiment E0 (bus capability spike) must confirm available event fields and produce a line-counted prototype; if the bus lacks usage/failure/action feedback, the BUILD-SMALL classification must be withdrawn rather than silently expanded.** This unit did not inspect the local repo by instruction.

## 8. Verification program and falsification criteria

### E0 — Bus capability spike

**Purpose:** settle whether BUILD-SMALL is honest.  
**Method:** in a throwaway prototype, prove that existing events expose task identity, action kind, usage/cost or a defensible proxy, tool outcome/fingerprint, and a way to inject/deny the next tranche. Use one known-present event as a positive control and a second mechanically independent signal (event payload plus externally observed action count) before claiming a field absent.  
**Pass:** deterministic state update and stop/escalate injection in <~200 lines excluding tests/fixtures.  
**Fail:** any required daemon, separate queue, durable runtime, or model-serving component. On failure, retain only the CONFIG prototype or stop.

### E1 — Retrospective counterfactual replay

**Purpose:** establish prevalence and detector opportunity without changing live behavior.  
**Method:** stratify historical trajectories by task family and consequence. Human-label the decision points where another action did or did not change evidence/answer. Replay the UCA rules over traces. For “would catch,” require two independent signals: rule firing plus human-labeled counterfactual opportunity; validate the detector on known-present seeded cases before reporting absences.  
**Metrics:** precision/recall for identical retry, premature stop, no-change continuation, wrong-order expensive action, reserve breach, and evidence-floor miss; potential spend saved; consequential misses introduced.  
**Falsifier:** if false positives dominate or most spend has no observable decision boundary, do not enforce.

### E2 — Shadow-mode randomized budget trial

**Purpose:** test the recommendation’s core value claim.  
**Method:** run baseline policy and Compute Control Case on matched/randomized tasks. Shadow mode first records decisions without acting. Enforcement follows only after review. Blind outcome graders to policy where feasible. Stratify by task family and consequence rather than reporting one average.  
**Primary metric:** consequential defect-free completion per unit token/cost and wall time.  
**Guardrails:** high-consequence miss rate, owner corrections, incomplete promised work, reserve breaches, and tail latency.  
**Success:** a preregistered material cost reduction with non-inferior high-consequence outcomes, or a material quality gain at matched cost.  
**Falsifier:** savings come mainly from stopping work owners later request, or high-consequence misses increase beyond the non-inferiority margin.

### E3 — Exploration ablation

**Purpose:** prevent the gate from suppressing discovery.  
**Method:** compare hard “name the discriminator” enforcement, one bounded exploration tranche, and baseline on research/design/debug tasks with hidden useful branches.  
**Metric:** novel decision-relevant findings per unit cost, plus missed-find rate.  
**Falsifier:** the bounded exploration lane cannot recover baseline discovery at lower or equal cost.

### E4 — Calibration/selective-risk study

**Purpose:** decide whether any numeric confidence may control allocation.  
**Method:** by task family, compare predicted success/confidence with delayed owner judgment, executable checks, and independent expert labels. These are mechanically different outcome signals.  
**Falsifier:** calibration error or distribution shift is too large for the proposed thresholds; retain ordinal policy.

### E5 — Evidence independence trial

**Purpose:** test Swiss-cheese dependence rather than assuming it.  
**Method:** seed known defects and compare same-context same-model review, fresh-context review, different model, primary-source verification, and executable tests at matched cost.  
**Metric:** unique consequential defects found per unit cost and pairwise overlap.  
**Falsifier:** recorded “evidence mode” does not predict independent defect yield.

### E6 — Threshold drift canary

**Purpose:** verify signposts.  
**Method:** after model/version/price/tool/task-mix changes, route a small canary set through old and recalibrated thresholds.  
**Falsifier:** recalibration produces no stable benefit; simplify signposts rather than adding machinery.

### E7 — Semantic change benchmark

**Purpose:** validate “answer/evidence changed” detection.  
**Method:** human-label paired intermediate states, including paraphrases, new citations with no decision effect, and small facts that reverse a recommendation. Compare a cheap structural detector and model-assisted detector.  
**Falsifier:** neither reaches preregistered precision/recall at a cost below the savings it gates.

## 9. Rollout decision rule

1. Start with **CONFIG (settings/JSON only)**: require a critical-claim/evidence-gap/cheapest-discriminator/stop-condition note for optional escalation on a small task sample.
2. Run E0 and E1. Do not describe missing bus fields or missed trace classes without a known-present positive control and a second independent signal.
3. If E0 confirms the small-bus premise, deploy **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** in shadow mode.
4. Enforce only retry deduplication and reserve protection first; they have the most objective state. Keep semantic no-change stopping advisory until E7 passes.
5. Run E2 stratified by consequence/task family. Roll back on the high-consequence non-inferiority guardrail, even if mean cost improves.
6. Reconsider a learned allocator only after the simple controller’s measured regret is large, stable, and supported by enough labeled outcomes. Until then, a learned router remains outside the anti-overfit gate.

**Rollout confidence:** **likely (55-80%)** that staged shadow-first deployment will reveal useful rule failures before they affect many tasks, because the decisions can be compared against baseline without initially denying actions. **UNVERIFIED—E2’s shadow-to-enforcement transition is the settling experiment.**

## 10. Evidence quality, gaps, and claims deliberately not made

### Evidence strengths

- The STPA mechanism and four unsafe-control-action categories come from the official MIT handbook, not a secondary analogy ([MIT PSASS handbook index](https://psas.scripts.mit.edu/home/books-and-handbooks/); [STPA Handbook PDF](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).
- The milestone case/evidence/evaluation description comes from NASA’s official technical-report system ([NASA System Safety Handbook Vol. 2](https://ntrs.nasa.gov/citations/20150015500)).
- Proportional analysis and ALARP boundaries come from HSE’s official regulatory guidance ([HSE guidance](https://www.hse.gov.uk/foi/internalops/hid_circs/permissioning/spc_perm_37/)).
- Normal-accident definitions are supported by a National Academies review, not used as an empirical claim about this harness ([National Academies](https://www.nationalacademies.org/read/11923/chapter/3)).
- The non-uniform compute premise has direct contemporary ML evidence, but only on bounded evaluation settings ([Damani et al., ICLR 2025](https://openreview.net/forum?id=6qUUgw9bAZ); [CATS, 2026](https://openreview.net/forum?id=mXuUomGc0I)).

### Gaps

- **UNVERIFIED—E1:** No local-trace prevalence or counterfactual savings estimate was made, because this ideation unit was explicitly told not to ground in the local repository/corpus.
- **UNVERIFIED—E0:** No claim is made that the present hook bus exposes the fields required for a <~200-line controller.
- **UNVERIFIED—E2:** No claim is made that a no-change threshold, reserve fraction, consequence classifier, or evidence floor is calibrated for the owner.
- **UNVERIFIED—E5:** No claim is made that different models, agents, or prompts are mechanically independent evidence sources.
- **UNVERIFIED—E7:** No claim is made that semantic “answer changed” can be detected cheaply and reliably.
- The STPA Handbook’s statement that its four control-action categories are complete is accepted as a property of its control-action taxonomy, not proof that this first compute-control model includes every relevant action or hazard ([MIT STPA Handbook, pp. 37–38](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_Handbook.pdf)).
- Safety-case literature contains caveats about argument quality and effectiveness. This proposal does not infer that recording a case makes a decision correct ([NASA/CR-2017-219582](https://ntrs.nasa.gov/citations/20170003806); [NASA/TM-20250001849](https://ntrs.nasa.gov/citations/20250001849)).

## Final recommendation

Adopt the **STPA-shaped Compute Control Case**, not “safety engineering” wholesale. The transferable unit is:

> allocate compute as a contextual control action; make its process model explicit; grant it incrementally against a named evidence gap and live decision alternative; preserve reserve; stop on evidence saturation; and monitor the assumptions that made the allocation rule reasonable.

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence:** **likely (55-80%)** that this is a better cost-control research direction than uniform effort, generic “be efficient” prompts, mandatory multi-agent review, or a new learned routing service, because it covers consequence, timing, duration, feedback, reserve, and evidence independence while staying on the existing bus. **UNVERIFIED—E0, E1, and E2 jointly settle feasibility, detector value, and outcome value; failure of any one blocks rollout beyond CONFIG/shadow mode.**

The analogy should be rejected if E1 shows few contextual allocation errors, if E0 requires a second runtime, or if E2 saves cost by increasing consequential misses. That falsifiability is part of the borrow: a safety argument is not evidence that its own premises are true.
