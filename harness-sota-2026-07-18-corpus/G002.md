## Executive verdict

The earlier claim that hook telemetry is absent is false and remains retracted. Hook telemetry is abundant, structured, and sufficiently rich to recover event, handler, host duration, hook-payload duration, cancellation, blocking, error, tool-use correlation, and (often) agent identity. The failure was the miner's schema assumption, not the host.

The attachment-aware parser in this report was executed against the 616,652,882-byte control transcript `C:\Users\Prekzursil\.claude\projects\C--Users-Prekzursil\3cd9445a-ab17-4eec-ad05-c1d1bf411c40.jsonl`. It read 104,103 JSONL rows and recovered 38,599 hook records across seven attachment shapes and seven event types, including 50 blocks, 585 cancellations, and 49 non-blocking/error records. It found zero hook records missing both event and name. The parser's known-positive control therefore passed. The pinned independent full-tree result remains 125,902 `hook_event_name` occurrences in one transcript and 186 files carrying hook events (`INPUT-known-harness-defects.md:133-158`).

This produces two immediate corrections:

1. Hook telemetry must be parsed from the nested `attachment` object, not from a top-level `hookName` key. `async_hook_response` is important but is not the only shape. A parser that accepts only `async_hook_response` would have silently omitted 21,037 of the 38,599 control records (54.5%). The other observed types were `hook_success`, `hook_cancelled`, `hook_additional_context`, `hook_blocking_error`, `hook_non_blocking_error`, and `hook_system_message`.
2. Timing telemetry is also present. The control contained 19,473 host `durationMs` values and 12,179 payload `duration_ms` values. Consequently, the corpus's `p50_ms=0` / `p95_ms=0` tool rows are an analyzer gap, not evidence that the runtime emits no timing. `mine.py:320-326` looks only inside `toolUseResult`, whereas host timing appears on hook attachments (for example the `hook_non_blocking_error` at control transcript line 1,985) and payload timing appears inside the attachment response.

Confidence that these two corrections are true is **almost certain (90-99%)**: the evidence is a successful streaming parse of a 616.7 MB known-positive transcript, direct raw examples at transcript lines 31, 40, 43, 47, 1,985, 5,907, and 40,639, plus the mechanically independent pinned `rg` result in `INPUT-known-harness-defects.md:133-158`.

The genuinely unmeasured surfaces are elsewhere. In priority order:

1. Exact instruction/rule loads and direct slash-command/skill expansions are not recorded by the live shared bus.
2. Claude terminal API failures (`StopFailure`) have no live hook or ledger path.
3. The local consolidated dispatcher exposes only aggregate handler completion; individual check crashes, timeouts, elapsed time, and suppressed outputs are invisible.
4. The telemetry sinks are fail-silent and carry no sequence/config provenance; a failed write can erase evidence of its own failure.
5. Hook/gate observations are not joined to delivery, later verification, owner acceptance, or configuration version, so efficacy cannot be estimated.
6. The shared ledger discards agent identity and parent/task lineage that is partly present upstream; worker contribution and overlap are not measurable.
7. Shell, MCP, and external side effects are recorded as calls/results but not as authoritative before/after environment state; the mutation ledger recognizes only direct write tools and shell redirection.
8. Session completion and owner correction are not labeled outcomes. The corpus stores timestamps and regex candidates, not task success or adjudicated correction.
9. Codex negative/lifecycle parity is absent from the configured shared bus, but native support for the missing event names is **UNVERIFIED** and must not be invented from Claude semantics.

No proposal below adds a second runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Every accepted proposal rides the existing native hook/JSONL/ledger bus. That satisfies the anti-overfit gate.

### 1.4 Parser

This parser is intentionally streaming, emits no raw prompt/tool/hook content, treats every `hook_*` attachment plus `async_hook_response` as telemetry, and refuses to report absence unless it observes a known-positive event. It therefore fixes the exact detector failure without building another telemetry system.

```python
#!/usr/bin/env python3
import argparse, collections, json, math, sys
from pathlib import Path

def json_objects(text):
    if not isinstance(text, str):
        return
    for line in text.splitlines():
        try:
            obj = json.loads(line)
        except Exception:
            continue
        if isinstance(obj, dict):
            yield obj

def payload_of(att):
    response = att.get("response")
    if isinstance(response, dict) and (
        response.get("hook_event_name") or response.get("hookEventName")
    ):
        return response
    for obj in json_objects(att.get("stdout")):
        if obj.get("hook_event_name") or obj.get("hookEventName"):
            return obj
    return response if isinstance(response, dict) else {}

def blocked(att):
    if att.get("type") == "hook_blocking_error" or att.get("exitCode") == 2:
        return True
    response = att.get("response") if isinstance(att.get("response"), dict) else {}
    specific = (
        response.get("hookSpecificOutput")
        if isinstance(response.get("hookSpecificOutput"), dict)
        else {}
    )
    decision = specific.get("decision") if isinstance(specific.get("decision"), dict) else {}
    return (
        response.get("decision") == "block"
        or response.get("continue") is False
        or specific.get("permissionDecision") == "deny"
        or decision.get("behavior") == "deny"
    )

def percentile(values, p):
    if not values:
        return None
    values = sorted(values)
    return values[min(len(values) - 1, math.ceil(p * len(values)) - 1)]

def input_paths(raw_paths):
    for raw in raw_paths:
        path = Path(raw)
        if path.is_dir():
            yield from path.rglob("*.jsonl")
        else:
            yield path

def main(argv):
    parser = argparse.ArgumentParser(
        description="Mine Claude hook attachments without emitting payload text."
    )
    parser.add_argument("paths", nargs="+")
    args = parser.parse_args(argv)

    counts = collections.Counter()
    types = collections.Counter()
    events = collections.Counter()
    names = collections.Counter()
    missing = collections.Counter()
    host_ms, payload_ms = [], []

    for path in input_paths(args.paths):
        counts["files"] += 1
        try:
            handle = path.open(encoding="utf-8", errors="replace")
        except OSError:
            counts["files_failed"] += 1
            continue
        with handle:
            for line in handle:
                counts["lines"] += 1
                try:
                    row = json.loads(line)
                except Exception:
                    counts["bad_json"] += 1
                    continue
                att = row.get("attachment")
                kind = str(att.get("type") or "") if isinstance(att, dict) else ""
                if not isinstance(att, dict) or not (
                    kind == "async_hook_response" or kind.startswith("hook_")
                ):
                    continue

                counts["records"] += 1
                types[kind] += 1
                payload = payload_of(att)
                event = (
                    att.get("hookEvent")
                    or payload.get("hook_event_name")
                    or payload.get("hookEventName")
                )
                name = att.get("hookName") or event
                if event:
                    events[str(event)] += 1
                else:
                    missing["event"] += 1
                if name:
                    names[str(name)] += 1
                else:
                    missing["name"] += 1
                if row.get("timestamp"):
                    counts["timestamped"] += 1
                if att.get("toolUseID") or payload.get("tool_use_id"):
                    counts["tool_correlated"] += 1
                if payload.get("agent_id"):
                    counts["agent_identified"] += 1
                if kind == "hook_cancelled":
                    counts["cancelled"] += 1
                if kind in {"hook_error", "hook_non_blocking_error"} or (
                    isinstance(att.get("exitCode"), int)
                    and att.get("exitCode") not in (0, 2)
                ):
                    counts["errors"] += 1
                if blocked(att):
                    counts["blocks"] += 1
                if isinstance(att.get("durationMs"), (int, float)):
                    host_ms.append(att["durationMs"])
                if isinstance(payload.get("duration_ms"), (int, float)):
                    payload_ms.append(payload["duration_ms"])

    valid = bool(counts["records"] and sum(events.values()))
    report = {
        "detector_status": "VALID" if valid else "BROKEN_NO_KNOWN_POSITIVE",
        "counts": dict(counts),
        "attachment_types": dict(types),
        "events": dict(events),
        "top_hook_names": names.most_common(20),
        "missing": dict(missing),
        "host_duration_ms": {
            "n": len(host_ms),
            "p50": percentile(host_ms, 0.50),
            "p95": percentile(host_ms, 0.95),
            "max": max(host_ms) if host_ms else None,
        },
        "payload_duration_ms": {
            "n": len(payload_ms),
            "p50": percentile(payload_ms, 0.50),
            "p95": percentile(payload_ms, 0.95),
            "max": max(payload_ms) if payload_ms else None,
        },
    }
    print(json.dumps(report, indent=2, sort_keys=True))
    return 0 if valid else 3

if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1:]))
```

The parser is **very likely (80-90%)** to recover all currently observed Claude attachment-based hook shapes because it keys on the stable `hook_*` family rather than enumerating only today's seven variants, and it passed the large control. It is not claimed to cover future schema families that do not use either `hook_*` or `async_hook_response`; the experiment that settles a future version is a known-event fixture for every attachment type emitted by that version, with `detector_status=VALID` and expected type/event counts.

## 3. Severity-ranked findings and proposals

### F1 — High: instruction, rule, and direct skill activation are dark

Claude's current config registers SessionStart, UserPromptSubmit, Pre/PostToolUse, failure, compaction, config, subagent, task, teammate, Stop, and worktree hooks (`settings.json:82-501`), but parsed JSON-key enumeration found no `InstructionsLoaded` or `UserPromptExpansion`. This is not a grep artifact: the same enumerator found known-present `PreToolUse`, and the runtime terminal parser found 126,989 shared events.

The shared module already contains an `_append_instructions` branch (`modules.py:944-955,1196-1216`), but `registration.py:17-33` never registers the event. Across 135 project ledgers and 77,140 valid records, `kind=instructions` occurred zero times; the known controls in the same data were 61,406 tool results and 6,112 subagent lifecycle records. That is the second independent signal.

The direct activation gap is distinct. The corpus can count explicit `Skill` tool calls, but Claude's official hook reference states that a directly typed `/skillname` bypasses PreToolUse and is exposed through `UserPromptExpansion`: https://code.claude.com/docs/en/hooks#userpromptexpansion. The same reference states that `InstructionsLoaded` reports `file_path`, `memory_type`, `load_reason`, and lazy/compact triggers: https://code.claude.com/docs/en/hooks#instructionsloaded. Without those events, the owner cannot answer “which instruction/skill was actually active for this turn?”, diagnose conflicting rules, or measure the activation cost of the 82-rule/75-skill surface.

Confidence: **almost certain (90-99%)**, based on live config parsing, zero typed ledger records after two known-positive controls, the unreachable implemented branch, and the native event contract.

#### Proposal F1a — activate instruction-load auditing

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Register native Claude `InstructionsLoaded`, normalize `file_path`, `memory_type`, `load_reason`, `globs`, and trigger/parent paths, and write only redacted path identity plus scope/reason—never instruction contents—to the existing ledger. The existing `_append_instructions` call site can be reused, but its current `source/prompt` abstraction is too lossy for the documented fields.

It is **very likely (80-90%)** that this will close the Claude rule-load blind spot because the native event exists expressly for observability, the bus and append branch already exist, and the required change is registration plus field normalization. The remaining uncertainty is Windows/current-version payload fidelity; a fixture that launches one disposable session with an eager CLAUDE.md, one `paths:` rule, and one nested CLAUDE.md, then expects three reason-coded ledger events, settles it.

#### Proposal F1b — record direct skill/command expansion

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Register `UserPromptExpansion`; persist a privacy-bounded activation tuple (`command_name`, expansion type, command source, argument hash, session hash, turn ID) through the existing selection/ledger bus. Do not store expanded prompt text.

It is **very likely (80-90%)** that this will make direct Claude skill/command activation measurable because the native event explicitly covers the path PreToolUse misses. A disposable `/known-skill test` followed by one model-invoked Skill call should produce one expansion record and one tool record, respectively; this experiment also prevents double-counting.

### F2 — High: terminal Claude API failures bypass the harness record

Parsed live settings contain no `StopFailure`; the registration tuple omits it (`registration.py:17-33`); and the lifecycle ledger module has no corresponding branch (`modules.py:944-962`). The official native contract says `Stop` does not run for API errors and `StopFailure` instead carries categories such as rate limit, authentication failure, billing error, server error, and max-output-token exhaustion: https://code.claude.com/docs/en/hooks#stopfailure.

This means a session can end at precisely the point where continuity/reliability evidence matters while producing no terminal shared-bus record. A visible error may still exist in the raw conversation or provider debug log; the scoped absence is the durable normalized harness event.

Confidence: **almost certain (90-99%)**, based on two absent registration surfaces and the native mutually exclusive Stop/StopFailure contract.

#### Proposal F2 — add the terminal failure channel

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Register native `StopFailure` and append a sanitized category, optional detail hash, last-assistant-message hash, session hash, and turn ID to the existing ledger/terminal sink. It must be notification/logging only because the native event has no decision control.

It is **very likely (80-90%)** to close the normalized terminal-failure gap: the event and fields are native, and the dispatcher already handles adjacent failure events. A disposable invalid-credential or mocked API-error fixture, not a production credential change, should assert one StopFailure record and zero Stop records for the failing turn.

### F3 — High: the local consolidated dispatcher can report outer success while inner checks fail or time out

The local dispatcher imports checks and catches every import exception (`_dispatch/dispatch.py:242-252`), catches every worker exception (`:182-190`), starts daemon threads (`:256-265`), drops any timed-out worker's incomplete output (`:267-281`), and returns only newline-joined additional context (`:283`). Its manifest includes stateful checks that write sidecars, registries, state, spools, ledgers, and launch monitors (`manifest.json:11-234`).

The host transcript does record the outer handler's command/duration/exit/cancellation, which is valuable. It does not carry the internal manifest check name, matched/not-matched decision, start/end, exception class, timeout, or whether a late stateful action occurred. The raw attachment parser validated this by enumerating all observed attachment keys; none contains per-check identity. Thus `hook_success` for the consolidated command does not establish that its constituent checks ran successfully.

Confidence: **almost certain (90-99%)**, based on explicit fail-silent source paths plus independent enumeration of the host record envelope.

#### Proposal F3 — add bounded per-check receipts inside the existing dispatcher

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** For each selected check, append a compact record to the existing local/shared terminal sink: event ID, check ID, matched, started, terminal (`success|exception|timeout|import_error`), elapsed milliseconds, output-present bit, and side-effect class. Never store hook input or output text. Use one append after aggregation, not one process or hook per check.

It is **very likely (80-90%)** to make internal failure attribution possible because all required state already exists inside `run()`. It is **likely (55-80%)** to remain below the hot-path noise/latency budget if records are buffered and written once; the settling experiment is an injected fixture with one success, one exception, and one timeout, benchmarked for p50/p95 overhead across 1,000 no-op dispatches.

### F4 — High: the observer can lose its own records silently

The shared terminal writer wraps directory creation, serialization, append, and write in one broad `try/except` and silently passes (`dispatcher.py:494-515`). The shadow writer does the same (`modules.py:357-385`). The terminal sink contains 126,989 valid JSON records and six malformed rows. Its complete observed key set is only `ts`, `terminal`, `provider`, `event`, `action`, `reason_code`, `elapsed_ms`, and `failed_modules`; there is no sequence, session hash, turn ID, event ID, config hash, or previous-record hash.

Therefore, a sharing violation, disk-full error, concurrent partial append, or serialization failure can be indistinguishable from an event that never occurred. Six malformed rows prove corruption is not merely theoretical, though they do not reveal the mechanism.

Confidence: **almost certain (90-99%)** for the fail-silent/loss-detection gap, based on source and record schema. The cause of the six malformed rows is **UNVERIFIED**; byte-level inspection under a read lock plus concurrent-writer stress in a disposable sink would settle whether they came from interleaving, truncation, or historical schema damage.

#### Proposal F4 — make telemetry loss visible without a new telemetry system

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add event UUID, monotonic per-process sequence, session hash, turn ID, and resolved config hash to terminal records. On terminal-sink failure, emit one sanitized `FAILED:telemetry-write <error-class>` line to stderr so the native host attachment becomes the independent fallback. Use locked/atomic line append consistent with the existing ledger rather than a new daemon.

It is **very likely (80-90%)** that this makes gaps and sink failures detectable because sequence discontinuity and host-captured stderr are mechanically independent of the primary JSONL write. It is **likely (55-80%)** that a config hash will materially improve historical attribution; evidence is that current records span changing settings but contain no version identity. A forced sharing-lock failure against a disposable sink must yield both a missing sequence and one native hook error attachment.

### F5 — High: the harness records interventions, not their effects

Shadow decisions contain only timestamp, gate, tier, event, reason code, and session hash (`modules.py:373-380`). Terminal records contain only aggregate action/reason/duration/failing modules (`dispatcher.py:496-507`). The hook-result schema has only status/action/reason/additional context/continuation (`hook-result.schema.json:7-36`). No record says:

- what action was proposed versus delivered;
- whether the mixer truncated or suppressed it;
- which model turn received it;
- which later tool/verification/owner outcome followed;
- which config/hook/skill version produced it;
- whether recurrence fell after intervention.

Raw transcripts do preserve hook additional context and later turns, so a bespoke forensic join is sometimes possible. The durable shared bus does not preserve the identifiers needed to perform that join reliably. This is the central reason current “shadow precision”, gate promotion, or hook efficacy claims are not derivable from runtime data.

Confidence: **almost certain (90-99%)**, based on exhaustive key enumeration of 126,989 terminal records, the exact shadow writer fields, and the restrictive result schema.

#### Proposal F5 — correlated intervention receipts, not a tracing platform

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing record with one event/correlation ID, predicted action, final delivered action, emitted-character count, saturation/suppression reason, session/turn hash, config hash, and optional later objective receipt ID. Join only to existing deterministic receipts (test exit, diff, file existence, task completion) and explicitly leave subjective quality unscored.

It is **very likely (80-90%)** to make delivery and deterministic downstream outcomes measurable because the mixer and receipt ledger already see those transitions. It is **unlikely (20-45%)** that this alone establishes causal efficacy, because observational before/after association remains confounded; paired shadow/enforce trials on the same task cohort would be required. This proposal deliberately does not introduce OpenTelemetry, SaaS, a trained critic, or a second runtime.

### F6 — Medium-high: cross-agent identity is observed upstream and discarded downstream

The normalized hook-event schema contains agent ID, type, and transcript path (`hook-event.schema.json:45-53`). The control parser found `agent_id` in 16,104 hook payloads. Yet `_append_subagent` persists only provider, turn ID, agent type, and output hash (`modules.py:1257-1276`). ### F7 — Medium-high: call telemetry does not equal state-change telemetry

The shared ledger records 61,406 tool-result hashes and 6,572 mutation events. Its mutation classifier treats built-in write tools as mutations and treats Bash/PowerShell as mutations only when the command matches a redirection regex (`modules.py:1090-1108`). It will therefore miss state changes made through commands such as `git apply`, `sed -i`, `cp`, `mv`, `Remove-Item`, package installers, database clients, remote APIs, and most MCP calls unless another explicit receipt captures the result.

This gap is independently consistent with the native checkpoint boundary: Claude's official documentation says Bash modifications and external changes are not tracked by checkpointing, and remote systems cannot be checkpointed: https://code.claude.com/docs/en/checkpointing and https://code.claude.com/docs/en/how-claude-code-works#stay-safe-with-checkpoints-and-permissions.

The raw transcript still records the requested command/tool and textual result. What is absent is authoritative before/after environment state and complete mutation inventory. A successful textual tool result is not proof that the intended state changed, nor that no unintended state changed.

Confidence: **almost certain (90-99%)**, based on the explicit classifier and independent native boundary documentation.

#### Proposal F7 — widen mutation receipts conservatively; do not add process surveillance

## 8. Final verdict

The harness's largest observability problem is no longer “hook telemetry does not exist.” It is that rich raw host telemetry, a lossy shared terminal record, a typed but selectively populated project ledger, and a broken corpus miner are not joined into an auditable causal record. The raw host already measures the hook boundary. What can live indefinitely in darkness is: which instructions and direct commands activated, terminal API failure, which inner check silently died, whether telemetry itself was lost, which intervention reached which turn, which worker contributed to which outcome, what state actually changed, and whether the task or owner accepted the result.

The radical replacement option fails the evidence and anti-overfit gates. A new telemetry daemon would duplicate abundant host records while leaving the semantic joins unresolved. The ambitious evidence-backed design is smaller: parse the source correctly, enable three native dark events, make the existing dispatcher self-report its inner checks and write failures, preserve correlation/config/agent identity, and join only to objective receipts. That is **very likely (80-90%)** to yield a materially more falsifiable harness with low architectural risk; the evidence is that every required observation point already exists on the current bus, while the remaining work is bounded registration, normalization, and correlation rather than a new runtime.
