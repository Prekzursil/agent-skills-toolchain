# X114 — Cross-domain borrow: reliability engineering → agent tool design

## Executive verdict

The analogy transfers, but only partially. The useful borrow is **failure-mode analysis plus common-cause-aware fault containment**: enumerate interface failure modes and their effects, identify which protections share the same cause, then remove the dominant failure mode from the normal execution path instead of adding identical retries. The concrete translation is an argv-native process tool for ordinary program invocation, a clearly separate shell-script tool for operations that actually require shell semantics, parser preflight on the latter, and stage-specific structured errors on both.

This is not a claim that an agent harness is a safety-critical plant, nor that physical-component MTBF mathematics can be copied. Shell-quoting mistakes are predominantly systematic interaction failures, not independent random component failures. The valid structural correspondence is narrower: repeated attempts through the same stringly shell boundary are exposed to one shared failure mechanism, so retry count is not redundancy. NASA explicitly warns that treating redundant components as independent can yield “wildly optimistic” reliability estimates, and the NRC’s diversity/defense-in-depth method looks for credible common-mode failures left uncompensated by genuinely different defenses ([NASA Fault Tree Handbook, pp. 117–118](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf); [NUREG/CR-6303 abstract](https://www.nrc.gov/reading-rm/doc-collections/nuregs/contract/cr6303/index.html)).

The brief supplies 1,631 unmatched-quote EOF failures as measured ground truth. I did not inspect the local corpus by design: this unit is explicitly an ideation lens and says not to ground it in the local repository. Thus the count is accepted as a pinned input, not presented as an independently reproduced measurement. No conclusion below depends on the corpus’s broken `hooks` detector.

## 1. The mechanism in its own field

### 1.1 FMEA: analyze failures at the interface, not merely failed components

NASA describes software Failure Modes and Effects Analysis (SFMEA) as a bottom-up method: examine each component, enumerate how it can fail, trace propagation to system effects, consider likelihood and severity, identify detection and compensating provisions, take corrective design action, and examine whether the correction creates new failure modes ([NASA Software Engineering Handbook, “SW Failure Modes and Effects Analysis”](https://swehb.nasa.gov/spaces/SWEHBVD/pages/140640400/8.5%2B-%2BSW%2BFailure%2BModes%2Band%2BEffects%2BAnalysis)). Its listed procedure explicitly includes “item and interface failure modes,” detection methods, compensation, corrective action, and the impact of the correction. This matters: the shell itself may be functioning perfectly while the *interface contract*—one text string interpreted by multiple grammars—fails.

FMEA’s useful unit is therefore not “Bash failed.” It is a precise failure mode such as:

| Item/interface | Failure mode | Local effect | End effect | Existing detection | Compensating/design provision |
|---|---|---|---|---|---|
| Agent → shell command string | quote opened but not closed | parser reaches EOF | requested work does not start | shell parse diagnostic, often after the call | syntax preflight; return source span; prefer argv path |
| Harness → platform launcher | executable and arguments ambiguously serialized | wrong token boundaries | wrong executable/arguments or launch failure | platform-dependent error | separate `program` from `args`; resolve executable explicitly |
| Agent → shell string | data accidentally interpreted as syntax | expansion, redirection, or injection | wrong or unsafe side effect | often only downstream evidence | literal argv transport; shell opt-in |
| Retry policy → same shell boundary | same malformed command regenerated | same parser failure repeats | wasted turns and misleading “redundancy” | identical error fingerprint | stop identical retry; switch execution mode or repair at exact span |
| Preflight parser → runtime shell | parser/version differs | check passes, execution fails | false confidence | runtime parse failure | run the actual selected shell’s parser/version |

The final row is required by FMEA’s “impact of changes” step: adding a validator is not automatically a complete defense.

### 1.2 Fault trees: reason backward from the failed outcome

Fault Tree Analysis complements the bottom-up view. It defines a top undesired event and decomposes combinations of causes with OR/AND logic. NASA’s handbook illustrates an OR gate where a valve can be closed by hardware failure, human error, or testing, and an AND gate where loss of both fuel cells *and* the battery removes bus power ([NASA Fault Tree Handbook, pp. 48–50](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

For this target, a useful top event is **“intended external operation was not correctly performed.”** A compact qualitative tree is:

```text
TOP: intended operation not correctly performed
  OR
  ├─ command never launched
  │    OR
  │    ├─ malformed shell syntax (including unmatched quote)
  │    ├─ executable resolution failed
  │    └─ launcher/OS serialization failed
  ├─ command launched with wrong meaning
  │    OR
  │    ├─ token boundary changed
  │    ├─ expansion/redirection interpreted unintended data
  │    └─ wrong shell grammar selected
  ├─ program ran and failed semantically
  └─ result was misclassified or recovery repeated the same cause
```

This prevents one seductive but wrong simplification: “non-zero exit means the program failed.” A syntax rejection before process launch, a spawn failure, and a child-program exit are different stages, effects, and recovery actions.

### 1.3 Common-cause failure: identical retries are not diverse redundancy

NASA’s fault-tree handbook states that probabilistic analysis can become wildly optimistic if redundant components are assumed independent. It models a common-cause fraction that threatens all components in the common-cause set and distinguishes transient restoration, covered faults, and uncovered faults ([NASA Fault Tree Handbook, pp. 117–118](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). The NRC’s NUREG/CR-6303 similarly analyzes digital protection systems to find credible common-mode failures not compensated by diversity or defense-in-depth ([NRC publication page](https://www.nrc.gov/reading-rm/doc-collections/nuregs/contract/cr6303/index.html)).

In its native field, redundancy improves reliability only to the extent that redundant trains do not share the initiating cause. Diversity changes implementation, principle, signal, or failure response so one defect is less able to defeat every path. Coverage asks whether a fault is detected and successfully handled; an uncovered fault can bypass the intended redundant structure.

The harness translation is direct at the structural level: asking the same model to emit another shell string, feeding it through the same tool schema, same grammar boundary, and same opaque error is not an independent protection train. It is one common-cause set. A process/argv path is diverse with respect to *shell lexical quoting* because there is no shell lexer on that path. Rust’s standard `Command` API documents exactly this property: arguments are passed separately and literally, so shell quoting, word splitting, globbing, variable substitution, and escaping have no effect ([Rust `std::process::Command`](https://doc.rust-lang.org/std/process/struct.Command.html)). Python’s subprocess documentation likewise recommends argument sequences and defaults `shell=False` ([Python `subprocess`](https://docs.python.org/3/library/subprocess.html)).

## 2. Concrete harness translation

## Recommendation — UNVERIFIED until the corpus replay experiment below: split process execution from shell execution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement a thin executor adapter behind the existing tool bus; do not add an orchestration runtime, daemon, durable workflow engine, or external observability system.

Expose two intentionally different contracts:

```json
{
  "tool": "process_exec",
  "program": "git",
  "args": ["show", "origin/main:path with spaces/file.txt"],
  "cwd": "C:\\work\\repo",
  "env": {},
  "stdin": null,
  "timeout_ms": 30000
}
```

```json
{
  "tool": "shell_exec",
  "shell": "pwsh",
  "script": "Get-ChildItem | Where-Object Length -gt 1MB",
  "cwd": "C:\\work\\repo",
  "timeout_ms": 30000
}
```

Contract rules:

1. `process_exec` has no `command` string and no implicit shell. `program` and each `args[]` element remain distinct through the adapter. On Windows, pass an explicit application name and use the runtime’s documented argv serializer; Microsoft documents that leaving the application name null makes the first whitespace-delimited token determine the executable and warns about ambiguous spaced paths ([Microsoft `CreateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessa)).
2. `shell_exec` is an explicit escape hatch for pipelines, redirection, compound statements, shell built-ins, expansion, or scripts. The adapter writes/pipes the script as a script unit rather than nesting it inside another generated `-c "..."` layer. The selected shell and version are part of the result.
3. Route ordinary single-program calls to `process_exec` by tool description and examples. Never silently reinterpret shell metacharacters in an argv element. If the agent places `|`, `>`, `$()`, or a shell compound expression where a program is expected, return a mode-mismatch error with examples of both tools rather than guessing intent.
4. Before execution, run the *actual selected shell’s* syntax parser: for Bash, `bash -n` over the same script bytes; for PowerShell, its parser API over the same script bytes. Parse failure prevents execution and returns the precise location when available. A second, generic quote-balancing heuristic may improve the explanation but must not be the authority because quoting is grammar- and context-sensitive.
5. Do not automatically migrate arbitrary failing shell scripts into argv: that transformation can change semantics. Recommend `process_exec` only when the parser or a simple command classifier establishes that the intent is one external program with literal arguments.

It is **very likely (80-90%)** that the argv path eliminates unmatched *shell-lexing* quote failures for eligible single-program calls, because no shell parser consumes those arguments and both Rust and Python document literal/sequential argument transport; this is **UNVERIFIED in this harness until replay test E1** measures eligible historical failures through the prototype. It is only **likely (55-80%)** that a large fraction of the supplied 1,631 failures are eligible for that path, because the brief supplies the fingerprint count but not the failed command shapes; this premise is **UNVERIFIED until E0 classifies those commands**.

The under-200-line estimate is **roughly even (45-55%)**, because a thin adapter using host runtime process APIs and native parsers is small, but robust Windows argument serialization, timeout/process-tree cleanup, output limits, and error normalization can exceed that size; this estimate is **UNVERIFIED until E3 produces a spike with line count and platform tests**. If it exceeds the threshold, keep it on the existing bus and reclassify honestly rather than hiding complexity. No BUILD-LARGE component is justified by this lens.

## Recommendation — UNVERIFIED until diagnostic-recovery experiment E2: return a failure-stage envelope, not prose alone

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Normalize results into machine-readable fields while preserving raw stderr:

```json
{
  "ok": false,
  "stage": "shell_parse",
  "code": "UNTERMINATED_SINGLE_QUOTE",
  "shell": "bash",
  "shell_version": "...",
  "location": {"line": 4, "column": 17},
  "message": "Single quote opened here reaches end of script.",
  "raw_stderr": "...",
  "retryable_same_input": false,
  "recovery": [
    "Close or remove the quote at line 4, column 17.",
    "If this is one external program, use process_exec with args[]."
  ],
  "attempt_fingerprint": "sha256(normalized tool + input + stage + code)"
}
```

Required `stage` values should distinguish at least `tool_validation`, `shell_parse`, `process_spawn`, `child_exit`, `timeout`, and `output_decode`. The raw native error remains available; the normalized code must not overwrite evidence. Mark malformed syntax as `retryable_same_input: false`. After a repeated identical fingerprint, the existing hook bus can refuse a blind third execution and return the two valid recovery choices: change the input or change execution mode.

This is “diagnostic coverage” translated from reliability engineering: detect the fault, locate it, and place the system in a recovery path that does not share the same cause. It is **likely (55-80%)** to reduce identical quote-error loops, because exact stage/location and a non-retryable marker supply information absent from a generic non-zero exit; this is **UNVERIFIED until E2 compares recovery behavior with raw stderr alone**. It is **unlikely (20-45%)** to prevent first-attempt semantic shell mistakes, because an error envelope acts after or immediately before formulation and does not understand user intent; E2 should separately score first-attempt prevention and post-error recovery.

## Recommendation — UNVERIFIED until routing experiment E1: make shell use an explicit hazard-bearing choice

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** The tool descriptions and examples should state:

- `process_exec`: default for an executable plus literal arguments; filenames with spaces and quote characters are data, not syntax.
- `shell_exec`: use only when shell composition is the intended operation; name the target grammar explicitly.
- Never recommend “add more escaping” as the first recovery for an eligible argv call.
- Examples must include Windows paths with spaces, JSON text containing quotes, Git revisions containing colons/slashes, and literal `$`, `*`, `;`, and `|` arguments.

This configuration is **likely (55-80%)** to move eligible calls to the safer interface when both tools are exposed, because the schema makes the default affordance concrete, but agent tool-selection behavior may ignore descriptions; this is **UNVERIFIED until E1 performs randomized prompt replays against the old and split schemas**.

## 3. What this catches that the current string boundary misses

Subject to the experiments, the design has distinct coverage:

| Failure | New detection/containment | Residual limitation |
|---|---|---|
| Unmatched shell quote in a script | actual-shell parser rejects before side effects and reports stage/location | parser diagnostics may not identify the human-intended repair |
| Quotes/spaces/metacharacters that are intended as literal program arguments | argv tool never exposes them to shell lexing | the target program can still interpret its own mini-language |
| Executable path ambiguity on Windows | separate explicit `program`/application identity from arguments | Windows ultimately transports a command-line string to many programs; child decoders vary |
| Wrong recovery by identical retry | fingerprint plus `retryable_same_input:false` blocks blind repetition | a superficially changed but equivalent malformed command evades exact fingerprints |
| Shell parse failure mislabeled as program failure | stage taxonomy distinguishes parse, spawn, child exit, timeout | child programs can themselves launch shells |
| Wrong shell selected | explicit `shell` field and returned version make grammar observable | valid syntax can still have cross-version semantic differences |

The Windows caveat is material, not fine print. Microsoft documents a single `lpCommandLine` boundary, and Rust warns that `cmd.exe` and `.bat` files use non-standard decoding and can interpret malicious input ([Microsoft `CreateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessa); [Rust `Command`](https://doc.rust-lang.org/std/process/struct.Command.html)). Therefore the argv tool must not claim universal quote immunity. It removes the shell lexer for conventional executables; it does not normalize every possible child parser.

## 4. Adversarial analysis: where the analogy breaks

### Disanalogy 1: random failure rates versus systematic generation defects

Hardware MTBF and independent-event multiplication assume stochastic structure that is not established here. An agent can repeatedly produce the same malformed pattern because its policy, prompt, examples, and error feedback are shared causes. There is no defensible conversion from 1,631 observed quote errors to an MTBF without exposure time, opportunity counts, censoring rules, and stationarity. Therefore this unit proposes no MTBF target and no numerical reliability gain.

This actually strengthens the common-cause lesson while invalidating naive reliability arithmetic: same-input retries are correlated, but the magnitude of correlation is **UNVERIFIED until E4 measures conditional recurrence after the first fingerprint**.

### Disanalogy 2: diversity of interfaces is not diversity of decision-maker

One model chooses both `process_exec` and `shell_exec`; its mistaken intent can defeat both. The paths are diverse only against the specific shell-lexing failure mode, not against misunderstanding the task, choosing the wrong executable, destructive intent, or a target program’s argument grammar. It is **very likely (80-90%)** that this limits total end-to-end reliability gains, because those failure branches remain in the fault tree; their prevalence is **UNVERIFIED until E0 labels a representative error sample by top-event branch**.

### Disanalogy 3: diversity adds interfaces and can create new failures

Two tools introduce mode-selection errors, schema surface, documentation load, and different platform behavior. FMEA requires analyzing the correction itself, not assuming a net win. It is **roughly even (45-55%)** whether a split interface beats a single backwards-compatible tool with a tagged union (`mode: process|shell`) for model selection accuracy; no evidence here settles that UI question, so it is **UNVERIFIED until E1 compares both variants**. The implementation should prototype both schemas before freezing names.

### Disanalogy 4: parse validity is not operational correctness

`bash -n` or a PowerShell AST parser proves only that the script parses under that parser. It cannot prove paths exist, commands mean what the owner intended, quoting inside nested `ssh`, `python -c`, regex, SQL, JSON, or template languages is correct, or side effects are safe. Parser preflight is fault detection for one layer, not a guardrail framework.

### Disanalogy 5: shell-free is not universally possible

Pipelines, redirection, compound control flow, built-ins, and environment expansion legitimately require a shell or equivalent programmatic composition. Forcing them into argv would merely relocate complexity and may produce a home-grown shell—precisely the overfit architecture to avoid. The escape hatch must remain first-class and well diagnosed.

### Disanalogy 6: an error fingerprint is not root-cause identity

Two identical parser messages can arise from different intended repairs; two different messages can share one underlying construction defect. A fingerprint is a retry-loop brake and measurement key, not a causal proof. Semantic clustering may be useful later, but this proposal does not require a vector database, knowledge graph, trained critic, or new service.

## 5. Experiments that settle the UNVERIFIED premises

### E0 — Failure-mode census

Sample and label the historical unmatched-quote fingerprints by: selected shell, single external command versus true shell composition, nested-language involvement, parser stage, retry sequence, and eventual successful repair. Use two mechanically independent signals for each classification where feasible: recorded tool input plus native stderr/exit metadata; for “eventual repair,” compare both the later command structure and successful result. First validate the detector on known-present examples for Bash and PowerShell.

Output: eligibility fraction for argv migration, top fault-tree branches, and recurrence conditional on first failure. This settles the largest premise behind expected benefit.

### E1 — Randomized replay of interface variants

Replay a stratified set of tasks, not merely failed command strings, across:

1. current string-only tool;
2. one tagged-union tool with `mode`;
3. two tools (`process_exec`, `shell_exec`).

Hold model, prompt budget, task, and environment constant; randomize ordering. Measure first-attempt completion, shell-parse failure, wrong-mode selection, total tool calls, semantic correctness, and side effects. Include adversarial literal arguments containing spaces, unmatched quote characters as data, `$`, backticks, semicolons, pipes, wildcards, newlines, and Windows paths. Run on PowerShell 7 and Git Bash because grammar portability is part of the claim.

Success gate: choose the smallest schema whose upper confidence bound on new wrong-mode failures is below the reduction in quoting failures and whose overall correct-completion rate improves. Do not ship based only on parse-error reduction.

### E2 — Diagnostic recovery A/B test

After inducing the same parse errors, compare raw native stderr against the structured stage/location/recovery envelope. Measure probability of correct next action, identical retry rate, turns to recovery, and semantic completion. Include cases where parser location is misleading due to an earlier opening delimiter. This tests diagnostic coverage rather than merely message pleasantness.

### E3 — Cross-platform implementation spike

Implement only the thin adapter and tests. Verify literal argument round trips with a helper executable that prints length-prefixed argv; test empty arguments, Unicode, trailing backslashes, embedded quotes, spaces, newlines, and long inputs. Independently compare the helper’s received argv with the adapter’s structured invocation log. Exercise `.exe`, PowerShell scripts, Bash scripts, `.cmd`, and `.bat` separately; the latter two must remain documented exceptions. Record production line count including error normalization and cleanup.

### E4 — Common-cause/retry measurement

For every first quote failure, compute whether the next attempt uses the same mode and normalized structure, then measure conditional failure probability. Compare it with attempts that switch from shell string to argv or materially repair the cited span. This does not prove statistical independence, but it can falsify the assumption that repeated same-path attempts behave like independent redundancy.

## 6. Anti-overfit gate and rejected alternatives

All three proposals ride the existing tool/hook bus. They add one small adapter, schema/configuration, native parser calls, and structured error fields. They do not add a second orchestrator, vector database/knowledge graph, durable execution engine, trained critic, observability SaaS, or guardrail framework.

Rejected alternatives:

- **Retry N times.** Rejected because it treats a systematic/common-cause interface failure as independent transient noise. Retry remains appropriate for explicitly transient stages such as selected network failures, not `shell_parse`.
- **Teach the model a larger quoting handbook.** Useful as documentation but insufficient containment; every call still crosses the same grammar boundary, and Bash/PowerShell/Windows child decoding differ.
- **Auto-escape every command.** Rejected because there is no grammar-independent escaping transform for arbitrary nested languages and intended shell syntax.
- **Replace the shell with a bespoke command DSL.** Rejected as an overfit second language/runtime. A literal argv API already exists at host-runtime level, while real shell composition should remain native.
- **Use multiple agents to vote on quoting.** Rejected: expensive, still potentially common-model/common-prompt failure, and disproportionate to a parser/interface defect.
- **Build a reliability daemon and calculate MTBF.** Rejected: the needed exposure model is absent, failures are systematic, and a new service violates the minimal-architecture gate.
- **Silently fall back from malformed shell to argv.** Rejected because a parser cannot reliably infer whether shell operators were intended; silent semantic changes are worse than an explicit mode error.

## 7. Final assessment

The transfer is valid for one narrow but important reason: reliability engineering has already learned that duplicated paths do not buy reliability when a common cause defeats all of them, and that useful protection combines explicit failure-mode analysis, coverage, containment, and genuinely different failure paths. A shell string retried through the same parser is common-mode repetition; an argv-native process boundary is structurally diverse against shell lexical quoting.

It is **very likely (80-90%)** that the proposed split is technically capable of eliminating shell-lexer quote failures on eligible ordinary process invocations, supported by the documented literal-argument behavior of standard process APIs; harness-specific benefit remains **UNVERIFIED until E0/E1**. It is **likely (55-80%)** that parser preflight plus structured stage errors improves recovery from remaining shell syntax failures, supported by FMEA’s detection/compensation logic but **UNVERIFIED until E2**. It is **almost certainly not (1-5%)** a complete solution to tool misuse, because the fault tree retains intent, program semantics, nested interpreters, platform decoders, and side-effect branches; that conclusion follows from the explicitly documented API caveats and the scope of syntax parsing.

The correct build posture is therefore a measured, bus-native prototype with full replacement of the *default stringly process-invocation path* on the table, not replacement of shells or orchestration. Ship only if replay shows a net completion improvement after counting new mode-selection failures.
