# X056 — Cross-domain borrow: control theory → failure recovery

**Unit:** X056  
**Lens:** control theory (observability/controllability, feedback stability, anti-windup, dead-band design) applied to resuming useful work after a worker, session, or machine dies mid-task  
**Date:** 2026-07-19  
**Scope constraint honored:** this is an external-research and ideation unit. I did not inspect or make claims about the local harness. Concrete local integration points are therefore deliberately left to the implementation/grounding units.

## Executive result

The strongest transferable control-theory mechanism is **conditioned, bumpless transfer**, reinforced by **anti-windup**. It transfers because both a controller handoff and an agent restart have (1) an active process that continues to exist outside the controller/worker, (2) latent internal state that can become inconsistent while that controller/worker is absent or ineffective, and (3) a dangerous first action when authority returns. Control engineering handles that transition by making the inactive/new controller track the actually applied plant input, initializing its state consistently, and preventing integral state from accumulating commands that the actuator cannot realize. The control literature explicitly treats anti-windup, bumpless transfer, and reliable multi-controller designs in one framework: Zaccarian and Teel generalize an anti-windup method to saturated multi-controller bumpless transfer and hardware-redundant reliable control ([Automatica paper and abstract, DOI 10.1016/S0005-1098(02)00072-9](https://www.sciencedirect.com/science/article/pii/S0005109802000729)). Peng, Vrančić, and Hanus review these methods for PID controllers and describe conditioning around a “realizable reference” ([IEEE Control Systems Magazine, DOI 10.1109/37.526915](https://doi.org/10.1109/37.526915)).

Translated to an agent harness, the mechanism is a **Recoverable Control Envelope (RCE)**: a small durable event stream plus a compact recovery capsule that records the task reference, the observed work state, the last actually applied external effects, unresolved effect intents, retry/saturation state, and the next safe transition. On restart, a recovery gate first observes and reconciles the real environment, conditions the new worker on that observed state, and only then gives it actuation authority. Retries stop integrating while an actuator is unavailable; uncertain non-idempotent effects are reconciled rather than replayed; recovery exits through hysteretic health thresholds so a flapping dependency does not repeatedly resume and abort the task.

This is **likely (55-80%)** to reduce duplicate side effects, blind retries, and “resume from an obsolete narrative” failures, because the proposed invariants follow the same structural mismatch addressed by bumpless transfer and are independently supported by distributed snapshot, write-ahead recovery, and HTTP idempotency results cited below. The wide band reflects the absence of a harness-specific fault-injection result. This efficacy claim is **UNVERIFIED; the settling experiment is the crash-matrix evaluation in §11**, which must compare current recovery with RCE under kill-at-every-boundary injection.

It is **almost certainly not (1-5%)** valid to import Kalman observability matrices, pole placement, or Lyapunov stability proofs literally into a general language-agent harness. Those results require a defined state, dynamics, measurements, inputs, and usually linearity or other precise model assumptions. Agent tasks are open-world, partially specified, non-stationary, and can execute irreversible actions. The evidence for the control-side assumptions is Åström and Murray’s definitions: observability is recovery of a model state from input/output measurements, with a full-rank observability matrix for the linear case ([Feedback Systems, Chapter 8 summary](https://fbswiki.org/wiki/index.php/Output_Feedback)); reachability is steering a specified state-space model to a desired state, with a rank test for a linear system ([Chapter 7 summary](https://fbswiki.org/wiki/index.php/State_Feedback)). The artifact uses these concepts as **design tests**, not borrowed guarantees.

## 1. The source-field problem, in its own terms

### 1.1 Observability: can internal state be reconstructed from available signals?

For a linear state-space system

\[
\dot{x}=Ax+Bu, \qquad y=Cx+Du,
\]

observability asks whether the internal state can be determined from measured inputs and outputs over a time interval. For the linear case, the observability matrix

\[
W_o=[C; CA; \ldots; CA^{n-1}]
\]

must be full rank. An observer then propagates a model-based estimate and corrects it using the innovation, the mismatch between predicted and measured output. Åström and Murray give both the definition, rank condition, and observer form \(\dot{\hat{x}}=A\hat{x}+Bu+L(y-C\hat{x})\) ([Feedback Systems, Output Feedback, summary points 1–4](https://fbswiki.org/wiki/index.php/Output_Feedback)).

What control theory has solved here is not “log more.” It has separated three things:

1. latent state that matters to future behavior;
2. signals actually available to infer it; and
3. an explicit test for whether those signals distinguish states that require different control actions.

If two distinct internal states generate the same observed history but demand different actions, no estimator can reliably choose between them without another measurement or assumption. That negative result is the useful borrow.

### 1.2 Controllability/reachability: can the actuators drive the state where it needs to go?

Reachability asks whether some input can steer a modeled system from one state to another over a finite interval. For a linear model, the reachability matrix \(W_r=[B,AB,\ldots,A^{n-1}B]\) supplies a rank test; if reachable, feedback can place closed-loop eigenvalues under the stated assumptions ([Åström and Murray, State Feedback, summary points 1–5](https://fbswiki.org/wiki/index.php/State_Feedback)).

The transferable lesson is again a precondition, not a formula: a supervisor should not issue a target state unless its available actuators can actually realize that transition. Integral control is particularly hazardous when the target is not reachable because the controller continues accumulating error.

### 1.3 Anti-windup: stop hidden controller state diverging when actuation saturates

Integral action accumulates tracking error to remove steady-state offset. When an actuator hits a limit, requested control and applied control diverge. The integrator can keep accumulating as though the impossible request were being applied; when the actuator becomes effective again, the stored state creates overshoot, oscillation, sluggish recovery, or even divergence. Åström and Murray’s PID chapter explicitly treats actuator saturation, integral windup, avoiding windup, tracking, and general-controller anti-windup ([Feedback Systems, PID Control](https://fbswiki.org/wiki/index.php/PID_Control)). Zaccarian and Teel’s treatment catalogs windup manifestations as sluggish, oscillatory, or diverging response and notes that persistent saturation can instead require a more capable actuator or redesign ([Modern Anti-windup Synthesis, chapter DOI 10.23943/princeton/9780691147321.003.0001](https://doi.org/10.23943/princeton/9780691147321.003.0001)).

Two common families matter here:

- **conditional integration/clamping:** stop integrating in the direction of saturation;
- **back-calculation/conditioning:** feed the discrepancy between requested and actually applied control back into controller state so internal state tracks what the plant received.

Hanus, Kinnaert, and Henrotte frame conditioning generally as handling any discrepancy between actual process inputs and desired controller outputs, including nonlinear multi-input/multi-output controllers ([Automatica, DOI 10.1016/0005-1098(87)90029-X](https://doi.org/10.1016/0005-1098%2887%2990029-X)). This general “requested versus realized” discrepancy is the key transferable variable.

### 1.4 Bumpless transfer: align latent controller state before switching authority

In manual/automatic or multi-controller systems, the incoming controller can hold internal state inconsistent with the current plant and applied control. Switching it in directly causes a discontinuity—a bump. Bumpless transfer makes the latent controller track the active controller/actual plant input or selects an initial controller state consistent with observed signals, then switches authority after alignment. Peng et al. connect anti-windup, bumpless transfer, and conditioned transfer, with good post-switch tracking as the objective ([IEEE review, DOI 10.1109/37.526915](https://doi.org/10.1109/37.526915)). Zaccarian and Teel show these are not merely verbal neighbors but can share a formal compensation framework ([Automatica 38(10), 1735–1744](https://www.sciencedirect.com/science/article/pii/S0005109802000729)).

This is the closest source-field analogue to session recovery: the replacement worker must not merely load an old controller snapshot; it must be conditioned against what the world is now.

### 1.5 Dead-band and hysteresis: avoid chatter near a switching boundary

A switching controller driven by a noisy signal can rapidly toggle when the signal hovers near one threshold. Positive hysteresis uses separate entry and exit thresholds; a dead-band suppresses action over a neighborhood. In relay feedback autotuning, Lee, Sung, and Edgar state that positive hysteresis is often used to avoid chatter under noisy measurements ([AIChE 2008 proceedings paper](https://skoge.folk.ntnu.no/prost/proceedings/aiche-2008/data/papers/P131477.pdf)). The trade-off is real: a wider dead-band reduces switching and noise sensitivity but tolerates more error and delay. Åström and Murray similarly identify small-signal measurement noise/quantization and large-signal actuator limits as fundamental nonlinear limits, not defects eliminated by gain alone ([Feedback Systems, Fundamental Limits](https://fbswiki.org/wiki/index.php/Fundamental_Limits)).

### 1.6 Feedback stability: feedback can amplify delay, noise, and model error

Feedback is not inherently stabilizing. Stability claims depend on a defined closed-loop model and margins; time delay and right-half-plane dynamics impose performance limits, while measurement noise and constraints introduce further nonlinear limits ([Åström and Murray, Fundamental Limits](https://fbswiki.org/wiki/index.php/Fundamental_Limits)). For an agent harness, recovery supervision adds delay, extra state, switching, and possibly correlated retry behavior. Without a model, “closed-loop stable” is not a defensible claim. The safe import is a validation discipline: perturb the loop, measure whether deviations decay, and retain escape paths.

## 2. Structural correspondence—and the boundary of the analogy

| Control-system structure | Failure-recovery structure | Transfer judgment |
|---|---|---|
| Plant state exists independently of the controller | Repository, remote services, files, messages, job status, and owner intent can outlive a worker | Strong correspondence for externally inspectable state |
| Controller has latent dynamic state | Agent has task narrative, plan frontier, evidence, retry history, tool results, and assumptions | Strong correspondence, but agent state is symbolic and open-ended |
| Commanded input can differ from actuator-applied input | Tool request can time out, be rejected, partly execute, or succeed without a returned response | Strong correspondence; this is the central recovery hazard |
| Inactive controller can track active plant input before handoff | Replacement worker can reconcile durable records with the current environment before gaining write authority | Strong correspondence where effects are observable |
| Sensor map and dynamics are specified | Harness observations and task dynamics are incomplete and can change | Weak correspondence; rank tests and state estimators do not transfer literally |
| Actuation is often continuous/reversible within known limits | Agent actions can be discrete, semantic, externally visible, and irreversible | Major disanalogy; reconciliation/idempotency is required, not feedback alone |
| Disturbances/noise have modeled bounds or statistics | Human edits, service drift, nondeterministic model outputs, and hidden external actions may be unbounded | Major disanalogy; no general Kalman/Lyapunov guarantee |
| Controller switching time and authority are explicit | Multiple workers may overlap, lose leases, or act through independent tools | Correspondence only if the harness introduces explicit epochs/authority fencing |

### Verdict

The **mechanism transfers**, but the **theorems do not**. It is **very likely (80-90%)** that requested-versus-realized actuation mismatch is structurally present in any tool-using agent system because timeout-after-apply is a standard distributed-systems ambiguity and RFC 9110 explicitly allows automatic retry only for idempotent operations or when the client can know the original was not applied ([RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)). The remaining uncertainty is whether a particular harness exposes enough pre/post-tool events to implement the mechanism uniformly; that premise is **UNVERIFIED; inspect the actual hook event contract and inject a timeout after a known side effect to settle it**.

It is **almost certain (90-99%)** that a snapshot of the agent transcript alone is insufficient for safe recovery when there are in-flight external effects. Chandy and Lamport show that a meaningful distributed snapshot must include process and channel state, and demonstrate how independently timed local snapshots can fabricate unreachable global states such as duplicated or missing tokens ([original 1985 paper, pp. 63–75](https://lamport.azurewebsites.net/pubs/chandy.pdf)). RFC 9110 independently identifies the response-lost ambiguity for retrying requests ([§9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)). These are mechanically independent signals: a distributed-state proof and an Internet protocol standard.

The correspondence fails for hidden external state. If a worker sent a non-queryable message through a service with no idempotency key and died before recording the response, neither an observer nor a checkpoint can reconstruct the truth. The correct result is an explicit **UNKNOWN_EFFECT** state requiring reconciliation or owner decision. Pretending the state is inferable would force the analogy past its assumptions.

## 3. Proposal: Recoverable Control Envelope (RCE)

### Proposal classification

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The core is a local append-only event writer, capsule reducer, and recovery gate. External-effect adapters may require separate small mappings; they must remain on the existing tool/hook bus. If the available hook contract cannot fence writes or durably record pre/post-tool events, the classification becomes **UNVERIFIED; the settling experiment is a hook-contract spike that implements one file-write and one HTTP-like tool adapter in ≤200 source lines**. Do not silently promote this into a daemon.

**Anti-overfit gate:** pass. The proposal does not introduce a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. It is an event/capsule convention and a recovery-mode hook around the existing execution bus. The event stream is bounded/compacted and is not a general workflow engine.

### 3.1 The minimal durable state

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is the data contract consumed by the core event writer/reducer; it is not a separate memory service.

Persist an append-only stream per task. Each record has a monotonic task sequence, a worker epoch, timestamp, event type, and a hash chaining it to the preceding record. A compact capsule is a deterministic reduction of that stream, not an independently edited narrative.

```json
{
  "task_id": "opaque-stable-id",
  "worker_epoch": 7,
  "seq": 184,
  "goal": {"text": "...", "acceptance": ["..."]},
  "mode": "RECOVERING",
  "frontier": {
    "done": [{"claim": "...", "evidence_ref": "..."}],
    "next": [{"action": "...", "preconditions": ["..."]}],
    "blocked": []
  },
  "environment": {
    "repo_head": "...",
    "dirty_fingerprint": "...",
    "remote_versions": {"resource": "etag/version"}
  },
  "effects": [{
    "intent_id": "stable-idempotency-key",
    "class": "READ|REVERSIBLE|IDEMPOTENT|NON_IDEMPOTENT",
    "target": "canonical-resource-id",
    "precondition": "version/hash",
    "intent": "normalized operation",
    "status": "INTENDED|APPLIED|REJECTED|UNKNOWN_EFFECT",
    "receipt": "provider-result-or-observation-ref"
  }],
  "retry_state": {
    "actuator": "tool-or-dependency",
    "consecutive_failures": 0,
    "last_error_fingerprint": null,
    "saturated_since": null,
    "next_probe_after": null
  },
  "handoff": {
    "last_observed_output": "what actually changed",
    "next_safe_action": "one bounded action",
    "must_revalidate": ["facts whose truth can drift"]
  }
}
```

Not every thought belongs here. The state is limited to facts that can change the next safe action: reference/goal, completion evidence, action frontier, external state fingerprint, effect ledger, retry state, and uncertainty. This avoids turning the event stream into a memory platform.

### 3.2 Authority fencing: one active controller epoch

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Epoch validation belongs in the same pre-dispatch hook as intent recording.

Each recovery increments `worker_epoch`. Every mutating tool intent contains `(task_id, worker_epoch, intent_id)` where the bus permits metadata. A worker with a stale epoch is read-only or rejected. This mirrors explicit controller authority: a latent controller may track but cannot actuate.

This is **likely (55-80%)** to prevent overlapping old/new workers from both applying effects because epoch fencing is a standard comparison-based exclusion mechanism and the harness can check its own epoch before dispatch. It cannot fence a tool call already accepted by an external service, so the claim is bounded. It is **UNVERIFIED; settle it by pausing an old worker before dispatch and after provider acceptance, starting a new epoch, then releasing the old worker in both cases**.

### 3.3 Write-ahead intent/effect ledger: observe applied control, not requested control

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The common ledger/reducer is core code; individual tool mappings remain small adapters on the current bus.

Before a mutating action:

1. Canonicalize target and operation.
2. Record and durably flush `INTENDED` with an `intent_id`, effect class, and precondition/version.
3. Dispatch with the same idempotency key where supported.
4. Record `APPLIED` plus a provider receipt or an independent postcondition observation; otherwise record `REJECTED` or `UNKNOWN_EFFECT`.

This borrows anti-windup’s requested-versus-applied distinction and database write-ahead recovery’s ordering. ARIES uses write-ahead logging, log sequence numbers, and “repeating history” before undoing loser transactions after failure ([Mohan et al., original paper](https://cs-people.bu.edu/mathan/reading-groups/papers-classics/aries.pdf)); the IBM publication record says ARIES was implemented across multiple IBM and research systems and applies beyond databases to recoverable filesystems and transaction-based operating systems ([IBM Research](https://research.ibm.com/publications/aries-a-transaction-recovery-method-supporting-fine-granularity-locking-and-partial-rollbacks-using-write-ahead-logging)). RCE borrows only intent-before-effect ordering and correlation IDs—not ARIES’s locking, page recovery, or transaction runtime.

On recovery:

- `APPLIED`: do not repeat; verify postcondition if drift matters.
- `REJECTED`: retry only under the retry policy and unchanged precondition.
- `INTENDED` with no dispatch evidence: reconcile target state before deciding.
- `UNKNOWN_EFFECT`: never automatically replay if non-idempotent. Query by idempotency key/provider receipt if possible; otherwise request owner resolution or take a compensating action explicitly authorized by the task.

RFC 9110 supplies the decisive boundary: an idempotent method may be retried after communication failure because repeated intended effect equals one application, while a client should not automatically retry a non-idempotent request unless it knows the semantics are idempotent or can detect that the original was never applied ([RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)).

### 3.4 Bumpless restart gate: track, align, then actuate

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is a startup mode in the event reducer and dispatch hook, not another orchestrator.

The new worker begins in `RECOVERING`, with mutation disabled. It performs:

1. **Validate capsule integrity:** sequence continuity/hash chain and task identity.
2. **Observe the plant:** current repository/worktree state, job/process status, remote object versions, and provider receipts relevant to unresolved intents.
3. **Compute innovation:** explicit diff between capsule predictions and observations: `expected → observed`, with provenance.
4. **Reconcile unresolved effects:** classify each as applied, not applied, or unknowable.
5. **Condition internal state:** revise the frontier and next action to match the observed world; discard stale commands and transient retry pressure.
6. **Prove one-step safety:** ensure the proposed next action’s preconditions hold, its effect class is known, and its intent can be recorded before dispatch.
7. **Switch authority:** enter `ACTIVE` only after health hysteresis in §3.6.

This is controller tracking translated concretely: the replacement worker’s “output” is aligned with the actual task/environment trajectory before the switch. It catches the case where an old transcript says “next: create PR” but the PR was already created before the crash; it also catches a human edit during downtime, a changed remote version, and a file change that succeeded although its tool response was lost.

It does **not** guarantee semantic continuity. Two language models may choose different decompositions even from the same capsule, and the goal itself may be ambiguous. “Bumpless” here has an operational definition: no duplicate or precondition-invalid first mutation and no contradiction with the durable evidence/frontier. Broader behavioral equivalence is **UNVERIFIED; settle it with blinded human comparison of pre-crash intended next steps and post-recovery first three actions across diverse tasks**.

### 3.5 Anti-windup retry controller: do not integrate failure into urgency

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The state transitions are part of the same reducer; numeric thresholds are CONFIG after measurement.

Treat each tool/service as an actuator with a finite operating region. Maintain a per-dependency error fingerprint, consecutive failure count, last success, and saturation state.

- On a transient and novel failure, permit a bounded retry with jitter.
- On repeated same-fingerprint failure or explicit unavailable/not-connected/rate-limited response, enter `SATURATED`; freeze retries that would issue the same command.
- While saturated, replace work-producing calls with sparse health probes or choose an independently useful alternative action.
- “Back-calculate” from realized behavior: clear speculative claims based on the failed call, set the capability state from the actual response, and revise the next action.
- Exit saturation only after the recovery hysteresis condition, not one lucky probe.
- Never accumulate a backlog of deferred identical retries. At most one intent remains pending per canonical `(actuator,target,operation)` unless the operation is explicitly batchable and idempotent.

This catches retry loops against a dead dependency, quota exhaustion amplified by urgent retries, and burst replay after service recovery. It also forces the plan to reflect the actual actuator rather than the command the agent wished had succeeded.

This is **very likely (80-90%)** to reduce same-fingerprint retry storms because conditional integration mechanically suppresses the repeated dispatch after the saturation threshold. It is only **likely (55-80%)** to improve end-to-end completion time because a false saturation classification can delay a recoverable action. Both claims are **UNVERIFIED; settle them by replaying recorded error sequences through current versus anti-windup policy and then running live fault injection with transient, permanent, and alternating faults**.

### 3.6 Dead-band/hysteresis for recovery mode

Use separate thresholds rather than one Boolean “dependency healthy” signal:

- `ACTIVE → DEGRADED`: e.g. two equivalent failures or one authoritative terminal failure.
- `DEGRADED → RECOVERING`: required dependency probe succeeds once and unresolved-effect reconciliation is possible.
- `RECOVERING → ACTIVE`: two successes separated by a minimum dwell time **and** the one-step safety check passes.
- Any terminal or same-fingerprint failure during recovery returns to `DEGRADED`; the probe interval backs off to a cap.

The exact counts and dwell time are parameters, not researched constants. The recommended `2` successes and a short dwell are **UNVERIFIED; settle them by minimizing a cost function over task delay, duplicate calls, and mode switches on a fault trace corpus**, then validate on held-out traces. The recommendation inherits that uncertainty:

#### UNVERIFIED recommendation: tune two-threshold recovery hysteresis from held-out fault traces

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Put entry/exit counts, backoff bounds, and dwell intervals in policy data once the event reducer exists. Keep a hard maximum delay and a manual/owner override. Positive hysteresis reduces chatter in noisy relay systems ([Lee, Sung, and Edgar](https://skoge.folk.ntnu.no/prost/proceedings/aiche-2008/data/papers/P131477.pdf)), but too much hysteresis delays useful recovery; therefore this parameter must be measured, not copied from physical control.

### 3.7 Bounded checkpoints: event-triggered, not transcript-every-token

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Checkpoint emission/compaction extends the same event writer and does not add a scheduler.

Emit/compact a capsule at semantic boundaries:

- goal/acceptance change;
- plan frontier change;
- before and after any mutating external effect;
- acquisition/release of worker authority;
- transition into/out of `SATURATED`, `DEGRADED`, or `RECOVERING`;
- verified completion evidence.

Periodic checkpoints may supplement these during long computation, but a timer alone misses the most important boundary: effect intent versus effect completion. Chandy–Lamport’s snapshot algorithm records process state plus in-transit channel messages to form a meaningful consistent global state without a global clock ([original paper](https://lamport.azurewebsites.net/pubs/chandy.pdf)). RCE does not implement their algorithm; it borrows the requirement that channel/in-flight state cannot be omitted.

## 4. Recovery state machine

```text
                      authoritative failure /
                      repeated same fingerprint
          +----------------------------------------------+
          |                                              v
      +--------+     crash/lease loss              +-----------+
      | ACTIVE | ------------------------------->  | DEGRADED  |
      +--------+                                   +-----------+
          ^                                              |
          | two separated health successes               | probe success +
          | + reconciled effects + safe next step         | capsule readable
          |                                              v
          |                                        +------------+
          +----------------------------------------| RECOVERING |
                                                   +------------+
                                                     |        |
                                       unknown       |        | integrity or
                                       non-idempotent|        | precondition failure
                                       effect        v        v
                                                 +------+  +---------+
                                                 | HOLD |  | ABORTED |
                                                 +------+  +---------+
                                                    |
                                               owner/provider
                                                reconciliation
```

`HOLD` is not failure; it is the only honest state when the measurements cannot distinguish “effect happened” from “effect did not happen” and replay could harm. `ABORTED` means capsule corruption, task cancellation, or an invariant violation that makes automatic continuation unsafe.

## 5. The observability and controllability audits, translated without fake mathematics

### 5.1 Recovery-observability audit

For each pair of plausible crash states, ask:

> If these states require different next safe actions, what durable observation distinguishes them after loss of worker memory?

Examples:

| Distinct states | Different safe action | Required durable signal | If signal absent |
|---|---|---|---|
| tool call never reached provider vs provider applied it but reply was lost | retry vs do not repeat | provider idempotency lookup, receipt, or independently queryable postcondition | `UNKNOWN_EFFECT`; hold non-idempotent replay |
| file edit applied vs not applied | continue vs reapply | content hash plus intent target/precondition | inspect file; conditional reapply |
| task completed vs worker merely claimed completion | stop vs continue verification | acceptance criterion linked to evidence artifact | rerun bounded verifier |
| old worker still able to mutate vs fully stopped | permit new writer vs prevent overlap | durable epoch/fencing check at dispatch | new worker remains read-only |
| dependency transiently healthy vs actually recovered | resume workload vs keep probing | separated probe successes and work-path check | remain `RECOVERING` |

This audit catches currently easy-to-miss “hidden states”: unrecorded in-flight effects, completion assertions without evidence, and latent workers without fenced authority. A state is “recovery-observable” only relative to the next-action distinctions the harness cares about; this avoids pretending to enumerate an agent’s entire mental state.

### 5.2 Recovery-controllability audit

For each recovery target, ask:

> Do available and authorized actions actually reach this target from every admitted recovery state?

Examples:

- “Exactly one message exists” is not controllable if the provider lacks lookup/idempotency/delete and the send result is unknown. Do not automate.
- “Repository matches the post-edit content” is controllable if content is observable and a conditional write is authorized.
- “Old worker cannot mutate” is not controllable merely by writing a new capsule if the dispatch bus does not enforce epoch fencing.
- “Resume on another machine” is not controllable if the capsule lives only on the failed machine.
- “Continue with a dead required MCP” is not controllable; choose a genuinely independent actuator, wait, or surface a blocker.

This audit prevents recovery goals that the harness cannot enforce. It also makes authorization part of controllability: technically possible but unauthorized compensation is not an available actuator.

## 6. Failure classes the mechanism catches—and those it cannot

### Caught or converted into a safe explicit state

1. **Crash between external apply and response receipt.** The pre-flushed intent remains unresolved; recovery queries the target/idempotency record rather than blind replay.
2. **Crash after response but before narrative/checkpoint update.** Provider receipt or observed postcondition advances the effect to `APPLIED` even though the transcript is stale.
3. **Human or automation changes the environment during downtime.** Innovation diff invalidates stale preconditions before the first mutation.
4. **Old and replacement workers overlap.** Epoch fencing prevents stale dispatch where the bus enforces it.
5. **Repeated retries against a saturated/dead dependency.** Conditional retry integration freezes and sparse probes replace workload calls.
6. **Dependency flaps around healthy/unhealthy.** Separate exit threshold and dwell prevent immediate workload re-entry.
7. **False completion after restart.** Completion must reduce from acceptance-linked evidence, not a prose status alone.
8. **Checkpoint with only process/transcript state.** The in-flight effect ledger plays the role of channel state and exposes incompleteness.
9. **Corrupted/truncated checkpoint.** Sequence/hash continuity makes corruption detectable; the prior compacted capsule plus trailing valid events can be used if available.
10. **Restart on a different machine.** This works only if the small stream/capsule is stored on an already-authorized durable shared substrate. That durability premise is **UNVERIFIED; settle it by power-cutting the writer immediately after each flush boundary and restarting on another machine**.

### Not solved

1. **Unobservable irreversible side effects.** No mechanism can infer whether they happened; RCE holds.
2. **Wrong goal or wrong semantics recorded durably.** Durable error is still error.
3. **Provider violates its idempotency contract or query result is stale.** Require provider-specific verification and retain uncertainty.
4. **Correlated destruction of task state and target state.** A shared failure domain defeats recovery; storage selection is outside this ideation unit.
5. **Malicious or Byzantine worker/provider.** Hash chaining detects some accidental corruption, not a signer allowed to write false events.
6. **Arbitrary equivalence of model reasoning across sessions.** The capsule preserves operational state, not hidden activations or identical reasoning.
7. **Global distributed snapshot for arbitrary concurrent workers.** RCE uses a single-writer epoch and effect ledger to avoid needing a general snapshot service. If the harness requires unconstrained multi-writer continuation, this BUILD-SMALL design is insufficient.

## 7. Why not import a Kalman filter, PID controller, or formal pole placement?

### Kalman filter: reject as default

A Kalman estimator presumes a specified stochastic state model and noise structure; Åström and Murray present it for a discrete-time linear process with white Gaussian process/measurement noise and covariances ([Output Feedback, summary point 6](https://fbswiki.org/wiki/index.php/Output_Feedback)). General agent tasks do not supply such a model. A learned or hand-tuned hidden “task state vector” would likely encode designer assumptions and hide categorical uncertainty such as unknown external effects behind a numeric confidence. Use an explicit reducer and evidence links instead.

### PID retry control: borrow anti-windup, reject continuous error integration

There is no scalar task error whose integral reliably represents progress. Retries are discrete and often non-idempotent. Import the saturation-state discipline—requested versus realized, clamping, back-calculation—not PID gains.

### Formal stability claims: reject without a task-specific transition model

Language-agent behavior is stochastic and semantic; the environment may change adversarially. No eigenvalue or Lyapunov argument is established. Empirical boundedness properties are the appropriate target: maximum duplicate effects, maximum consecutive identical retries, maximum time to safe first mutation, and probability of correct continuation under a specified fault distribution.

### Full distributed-snapshot or durable-execution service: reject for this harness

Chandy–Lamport and ARIES show what correctness can require in their domains, but importing a general runtime would violate the anti-overfit gate and reintroduce a previously rejected durable-execution/orchestration component. The single-writer epoch, pre/post effect records, and compact capsule capture the subset needed for an agent harness. If experiments show genuinely concurrent multi-writer tasks are dominant and cannot be serialized, that would be evidence for revisiting the gate—not permission to assume it now.

## 8. Invariants for an implementation unit

These are testable requirements, not aspirations:

1. **Intent-before-effect:** no mutating dispatch occurs before its durable `INTENDED` record is acknowledged.
2. **One authority epoch:** at most one epoch can issue new mutating dispatches through the harness bus.
3. **No blind replay:** a non-idempotent `INTENDED`/`UNKNOWN_EFFECT` record is never automatically reissued.
4. **Observed-over-requested:** capsule state records what an independent observation or provider receipt says happened, not merely what the worker requested.
5. **Preconditioned first mutation:** after restart, the first mutation must cite a fresh observation satisfying its precondition.
6. **Bounded identical retry:** no canonical operation may produce more than the configured consecutive identical retries without entering `SATURATED`.
7. **Hysteretic exit:** `RECOVERING → ACTIVE` uses a stricter/different condition from `ACTIVE → DEGRADED`.
8. **Evidence-linked completion:** `COMPLETE` requires all acceptance entries to reference verifier output or inspectable effects.
9. **Honest unknown:** indistinguishable states that demand different actions remain `UNKNOWN_EFFECT`/`HOLD`.
10. **Deterministic reduction:** the same valid event prefix produces the same capsule, independent of model output.
11. **Bounded growth:** compaction retains unresolved effects, goal/acceptance, evidence indexes, and the current frontier; routine old events can be summarized or expired according to a declared policy.
12. **Fail closed only for mutations:** capsule/recovery failure blocks writes but should still permit diagnostic reads and artifact production where authorized.

## 9. Alternatives considered

### A. Periodic transcript snapshots only — rejected

They are useful for prose context but omit in-flight external effects and can capture a globally inconsistent state. Chandy–Lamport’s token example demonstrates the structural error ([paper, example around pp. 69–70](https://lamport.azurewebsites.net/pubs/chandy.pdf)). A transcript also records requested calls more readily than independently observed effects.

### B. Replay the entire tool log — rejected

Replay duplicates non-idempotent effects and assumes determinism. RFC 9110’s retry constraint directly contradicts universal replay ([§9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)). Selective reconciliation is necessary.

### C. Ask the model to write a handoff summary — useful but insufficient

A narrative handoff is valuable semantic compression, but it is not mechanically authoritative. It can omit failed calls, confuse requested and applied effects, or claim completion without evidence. Keep `handoff` as one capsule field derived alongside the mechanical ledger, not as the recovery source of truth.

### D. General workflow/durable-execution engine — rejected by anti-overfit gate

It could provide timers, retries, and persisted steps, but it creates a second orchestration runtime and is disproportionate to the minimal recoverability invariants. It also risks coupling task decomposition to a runtime schema that stronger future models do not need.

### E. Vector database or knowledge graph of all state — rejected

Recovery needs exact recent state, ordering, effect identity, and preconditions. Approximate retrieval is the wrong primitive for `did side effect X happen?`, adds a rejected memory component, and cannot solve unobservable effects.

### F. OS/process checkpoint-restart — rejected as primary mechanism

Transparent checkpoint/restart can restore process state, but multi-process recovery requires globally consistent state and preservation of dependencies; filesystem, network, and device state remain separate concerns ([Laadan and Hallyn, USENIX 2007](https://www.usenix.org/legacy/event/usenix07/tech/full_papers/laadan/laadan_html/paper.html)). Restoring a language-model client process does not reconcile external APIs or human changes. It may supplement RCE for expensive local computation, not replace semantic recovery.

### G. Always require owner confirmation after any crash — safe but unnecessarily disabling

This throws away automatically observable/idempotent cases. RCE reserves owner intervention for genuine ambiguity or authorization boundaries, while permitting read-only reconciliation and safe continuation elsewhere.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A plausible core breakdown—not a measured implementation—is:

It is **UNVERIFIED; settle it with the hook-contract spike described in §3 and count non-generated source lines including tests separately**. ## 11. Decisive experiment: crash matrix with controls

### 11.1 Research question

Does RCE reduce unsafe or wasteful recovery without materially delaying successful tasks, relative to the current harness recovery and a narrative-handoff baseline?

### 11.2 Workloads

Use at least these effect types:

1. read-only repository research;
2. conditional local file edit;
3. idempotent remote create/update with provider key;
4. non-idempotent message/send with queryable receipt;
5. non-idempotent effect without query/receipt (expected `HOLD`);
6. long-running job with independently queryable job ID;
7. dependency returning transient, permanent, alternating, and response-lost-after-apply failures;
8. concurrent human edit during downtime.

### 11.3 Fault injection boundaries

Kill the worker at every event boundary and at targeted sub-boundaries:

- before intent flush;
- after intent flush, before dispatch;
- after provider accepts, before response;
- after response, before effect record;
- during capsule compaction;
- after recovery observation, before authority switch;
- immediately after authority switch;
- while old worker is paused before and after provider acceptance;
- machine power loss after each durability acknowledgement.

Chandy–Lamport provides the reason to vary in-flight communication states, not merely process checkpoints ([original paper](https://lamport.azurewebsites.net/pubs/chandy.pdf)). RFC 9110 provides the idempotent/non-idempotent retry split ([§9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)).

### 11.4 Baselines

- B0: current harness recovery behavior;
- B1: periodic full transcript + model-written handoff;
- B2: intent/effect ledger without bumpless observation gate;
- B3: full RCE;
- ablation: RCE without anti-windup;
- ablation: RCE without hysteresis;
- ablation: RCE without epoch fencing.

### 11.5 Primary metrics

- duplicate irreversible effects per 1,000 injected crashes;
- incorrect omission (effect needed but never completed) per 1,000 crashes;
- invalid first mutations after restart;
- percent of ambiguous non-idempotent cases correctly entering `HOLD`;
- time and tool calls from restart to first safe useful action;
- repeated same-fingerprint calls per fault episode;
- recovery-mode switches per flapping episode;
- human interventions, separated into necessary ambiguity versus false hold;
- capsule bytes and hook latency at p50/p95/p99;
- task success under no-fault control, to detect recovery machinery harming normal work.

### 11.6 Acceptance thresholds

Thresholds must be chosen before evaluation. Suggested starting gates are **UNVERIFIED; the settling experiment is this preregistered crash matrix**:

- zero blind replay of classified non-idempotent unknown effects;
- ≥90% reduction in duplicate effects versus B0;
- ≥50% reduction in identical retry calls during permanent faults;
- ≤5% increase in no-fault task elapsed time at p50 and ≤10% at p95;
- ≤1 false `HOLD` per 100 recoveries where target state is queryable;
- no increase in task failure on held-out no-fault workloads.

The ≥90% duplicate-effect target is **likely (55-80%)** achievable where providers offer idempotency/lookup and **very unlikely (5-20%)** where they offer neither; the evidence is the protocol distinction in RFC 9110 and the explicit unobservability analysis above. The latency gates are **roughly even (45-55%)** because flush and provider-query costs are deployment-specific.

### 11.7 Mechanical independence and detector validation

Before claiming a duplicate, omission, or successful recovery:

1. Validate each detector on a known-present seeded case and a known-absent control.
2. Require two mechanically independent signals for outcome claims—for example provider-side receipt plus target-state query; or file content hash plus tool/effect ledger. Re-reading the same log twice is one signal.
3. For `COMPLETE`, use acceptance-specific verifier output plus an independent artifact/effect inspection.
4. Preserve injected fault timing and provider state as ground truth separate from the harness event stream.

This directly prevents a recovery log from “verifying” itself.

## 13. Final recommendation

Build and test the **Recoverable Control Envelope** as a small existing-bus protocol, not a new runtime:

1. durable, hash-chained semantic events and a deterministic compact capsule;
2. pre-flushed effect intents paired with observed outcomes/idempotency receipts;
3. single active worker epoch with stale-worker write fencing;
4. a mutation-disabled recovery phase that observes the real environment, computes innovation, resolves effects, and conditions the first next action;
5. anti-windup retry saturation and hysteretic recovery;
6. explicit `UNKNOWN_EFFECT/HOLD` for states that cannot be observed safely.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is **UNVERIFIED as an end-to-end recommendation; the prerequisite experiment is the hook-contract spike, and the decision experiment is the preregistered crash matrix in §11**. Proceed to broader rollout only if it clears both safety and no-fault overhead gates.

The control-theory borrow is valuable precisely because it says when **not** to recover automatically. Observability asks whether the replacement can distinguish states requiring different actions. Controllability asks whether authorized tools can reach the recovery target. Anti-windup prevents an unavailable actuator from turning accumulated error into a retry burst. Bumpless transfer aligns the replacement with the world before granting authority. Dead-band/hysteresis prevents noisy health signals from chattering the harness between work and recovery. None of these makes an open-world agent a linear plant, and no stability theorem is claimed.
