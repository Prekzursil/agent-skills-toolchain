# F032 — red team: shared secrets → corrupt a conclusion

## Executive verdict

The most plausible concrete chain is **credential capture followed by upstream evidence poisoning**: a low-privilege local subprocess inherits a shared GitHub credential, uses it to alter the private repository or an evidence-bearing branch, and a later agent treats the authenticated remote plus a fresh successful command as objective proof. This chain is **likely (55-80%) conditional on the captured PAT having repository-write or owner-bypass authority**: the harness is demonstrably configured for broad execution, the prior audit recorded machine-wide GitHub credential names and an owner-bypass-capable GitHub caller, and the conclusion gate checks freshness/status rather than source identity. The PAT's actual scopes and whether the bypass-capable caller is the identity behind `GH_TOKEN` are **UNVERIFIED; the settling experiment is a name-only, non-mutating Windows probe of `gh auth status`, `gh api user`, and `gh api repos/Prekzursil/agent-skills-toolchain --jq '{viewerPermission:.viewerPermission}'` under each agent-facing GitHub credential, plus a comparison to the ruleset bypass actor—never print a token**. Audit claims are leads, not facts; this unit does not promote that unverified scope premise to fact.

No existing deployed control adequately stops the end-to-end chain:

1. The credential-read controls are present but opt-in and default off. A synthetic known-positive read returned no decision with the flag unset and a deny decision with it set; the implementation and its tests independently specify that default (`claude/hooks/deny-credential-reads/deny.py:73-101`; `agents/harness/modules.py:50-62,791-798`; `agents/harness/tests/test_modules.py:266-300`).
2. Even when enabled, the read guard covers model-issued read operations. It does not stop a child process from inheriting a credential through its environment. The local Claude setting does not set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (`claude/settings.json:4-20`), while an earlier audit's name-only Windows check also reported the variable absent from Process, User, and Machine scopes (`inputs/audit-findings/A28.md:64-70`). Those are mechanically independent config and runtime-scope signals, and the settings detector finds known-present neighboring variables such as `CLAUDE_CODE_FORK_SUBAGENT` at `settings.json:5`.
3. The claim/evidence gate can be satisfied by successful evidence downstream of the compromised authority. Receipt status becomes `pass` from exit code zero (`agents/harness/ledger.py:322-359`), freshness requires only a later passing receipt (`agents/harness/ledger.py:1093-1117`), and the regression test proves that an arbitrary `pytest -q` result with exit code 0 changes a completion warning to allow (`agents/harness/tests/test_modules.py:823-846`). No authenticated principal, repository identity, remote URL, or immutable commit identifier appears in that receipt decision. This is not a claim that such fields are absent everywhere; it is the narrower, directly shown fact that the decision path cited above does not consume them.

The minimal durable mitigation is to make every credential reachable by an agent **incapable of mutating the evidence the agent later verifies**: rotate/revoke exposed GitHub secrets, remove owner/write/bypass credentials from agent and Machine environments, and give GitHub research/read tools separate repository-scoped read-only credentials from a native secure store. That prevention is smaller and stronger than teaching a claim checker to recognize every possible poisoned result.

## Scope and safety

This is an analysis-only attack design. I did not open `auth.json`, `.credentials.json`, `accounts.json`, a private environment bundle, the OS keyring, or any secret-bearing registry value; did not test token validity; did not start an MCP; and did not contact or mutate GitHub. The only dynamic probe fed a made-up path, `C:/synthetic/.credentials.json`, to the guard with and without its enable flag. The subject remained read-only.

The remote job bundle is a selected, unpacked subject rather than the complete Windows host. It contains the Claude/Codex configuration, shared harness, corpus, defects, and audit claims, but it does not contain the live Windows registry, `.mcp.json`, `.claude.json`, repository checkout, keyring, or actual credential stores. Therefore, any statement that depends on current token validity, scopes, ACLs, or remote state is marked **UNVERIFIED** inline and names its settling experiment.

## Grounded attack-surface map

### A. Shared credential material and delivery paths

- Codex uses a core-only shell environment (`codex/config.toml:21-22`) and explicitly configures native keyring storage for CLI auth and MCP OAuth (`codex/config.toml:47-48`). It also passes selected names to individual MCPs, for example `CONTEXT7_API_KEY`, `FIRECRAWL_API_KEY`, and `TAVILY_API_KEY` (`codex/config.toml:504-522`). This is a real containment control for the Codex MCP lane.
- Claude permits Bash, web, task, and broad MCP families, uses `bypassPermissions`, and exposes both Windows drives as additional directories (`claude/settings.json:26-75`). These settings make a won model/tool interaction high consequence; they do not by themselves prove compromise.
- The prior secret audit claims that 13 MCP credential names, including `GH_TOKEN` and `GITHUB_MCP_PAT`, had identical nonempty User and Machine values, and that `BUILTIN\Users` could read the Machine environment registry key (`inputs/audit-findings/A28.md:16-22`). It also claims ten current values, including `GH_TOKEN`, exactly matched values in seven remote-reachable plaintext revisions (`A28.md:8-14`). These are **UNVERIFIED on this Linux node; the settling experiments are (1) a name/equality-only PowerShell scope inventory plus ACL read on the Windows machine and (2) an equality-only comparison between current secrets and historical blobs without printing either value**. Both experiments were reportedly performed by A28, but this unit cannot independently reproduce them from the bundle.
- The prior audit also structurally classified nine Exa keys and one Databricks token as plaintext literals in decrypted `accounts.json` worktrees and traced a model-visible account-add path that persists literals (`inputs/audit-findings/A28.md:32-38`). This is **UNVERIFIED here; the settling experiment is a value-free classifier that emits only field name, literal-vs-environment-reference, and count, plus static tracing of `_op_add` to `_persist` on the Windows repository checkout**.
- Corpus evidence shows this is an exercised surface, not merely unused code: direct credential-file blocks occur 15 times (`inputs/corpus.json:5337-5345`), secret-literal blocks seven times (`corpus.json:6744-6750`), the standalone no-raw-credential message three times (`corpus.json:8167-8171`), and PAT access errors eight times (`corpus.json:6633-6640`). The corpus metadata says it processed 11,633 files with zero file failures but one bad line and 32 oversized lines (`corpus.json:2-11`); those counts establish observed messages, not present-day control effectiveness. The corpus hooks section is intentionally treated as no data.

### B. What conclusions depend on the credentialed authority

This program explicitly instructs agents to treat some `origin/main` paths as the readable source of truth. A GitHub credential can therefore influence conclusions through two ordinary paths:

1. a remote API/MCP answer about PRs, checks, issues, releases, or repository state; and
2. a fetched Git object later read with `git show origin/main:path`.

Those probes are mechanically different commands but not independent authorities when both resolve to the same compromised repository. The known-defect file explains why detector independence matters and records seven wrong absence conclusions caused by unvalidated probes (`inputs/INPUT-known-harness-defects.md:111-129`). The same principle applies here: `gh api` plus `git show origin/main` is not an independent pair if the attacker controls the remote both consume.

### C. The conclusion gate's trust model

The shared claim module recognizes completion families such as tests passing, fixed, builds, coverage, and healthy (`agents/harness/modules.py:2000-2040`). It prefers a fresh passing receipt and falls back to legacy verification (`modules.py:2092-2109`; `ledger.py:1178-1184`). A receipt is classified from tool name, tool input, and tool result (`modules.py:1080-1088`); the pass/fail decision is based on result counters or exit code (`ledger.py:322-359`), and freshness is sequence ordering after the last mutation (`ledger.py:1065-1117`). This is useful protection against stale or entirely untested success claims. It is not an authority-integrity control.

The conclusion-corruption path is therefore semantic: the attacker does not need to forge a hook receipt. They make the command genuinely return success against poisoned evidence, so the existing receipt accurately records the wrong-world observation.

## Concrete attack chain

### Preconditions

1. A malicious or compromised local subprocess runs under the owner's Windows session. The most plausible entry is an already-authorized hook or stdio MCP dependency, because Claude starts many local components and permits broad MCP/Bash use (`claude/settings.json:26-75,81-103,239-259`). A supply-chain compromise of a floating `npx ...@latest` MCP is **likely (55-80%) as an attack class but UNVERIFIED for any installed package; the settling experiment is to resolve every live stdio MCP executable/package to a version and digest, compare it to a trusted lock or publisher signature, and perform no package execution**. Codex visibly floats Firecrawl and Codacy packages (`codex/config.toml:511-515,540-545`); that proves drift exposure, not maliciousness.
2. The subprocess can obtain an agent-use GitHub credential through inheritance or a shared on-disk store. The Machine/User inheritance path and historical-current equality are **UNVERIFIED but likely (55-80%) given A28's independently described registry ACL and history comparisons (`A28.md:8-22`); the settling experiments are the value-free Windows probes specified above**.
3. That credential can write to the evidence-bearing repository or exercise the current caller's ruleset bypass. This is **UNVERIFIED and roughly even (45-55%)**: audit A34 reports that the current GitHub caller had `viewerPermission` sufficient to inspect an active ruleset and `current_user_can_bypass=always` (`inputs/audit-findings/A34.md:83-89`), but the audit does not establish that this caller is the same token exposed to agent subprocesses. The settling experiment is the non-mutating principal/scope/ruleset-actor comparison in the executive verdict.

### Step-by-step chain

1. **Credential acquisition without a credential-file read.** The compromised subprocess reads `GH_TOKEN`/`GITHUB_MCP_PAT` from its inherited process environment. It never asks the model to issue `Get-Content auth.json`; consequently neither the standalone filename/verb matcher (`claude/hooks/deny-credential-reads/deny.py:19-55,86-101`) nor the shared PreToolUse credential matcher (`agents/harness/modules.py:641-643,735-798`) sees a read operation.

2. **Durable reuse.** The attacker uses the captured token outside the original agent turn. This defeats turn-scoped prompt-injection banners and makes the credential a reusable authority. Whether the actual PAT is reusable and unexpired is **UNVERIFIED; the settling experiment is provider-side token inventory/last-used metadata performed by the owner, without attempting authentication from this unit**.

3. **Poison the exact evidence channel.** The attacker adds a small, plausible change to an evidence-bearing remote object: for example, alter a harness test so a dangerous default is asserted as intended, modify a finding/source file on a branch agents are instructed to inspect, or create a green check on an attacker-controlled commit. The least noisy variant is a change whose content agrees with the false conclusion and whose commit metadata resembles normal autonomous work. The attacker does not need to alter the local harness or hook ledger.

4. **Exploit branch/ruleset authority.** If the token can bypass rules, the attacker lands the poison without the seven required checks; if it only has ordinary write authority, they target a non-default remote branch or other authenticated evidence object that the task is likely to query. A34 reports seven required check contexts but also an always-bypass role for the current caller (`inputs/audit-findings/A34.md:83-89`). Whether the agent token has that path is the **UNVERIFIED** prerequisite above.

5. **Trigger an ordinary evidence request.** Later, an agent is asked whether the control exists, whether a defect is fixed, or what `origin/main` contains. The agent runs `gh api`, an authenticated GitHub MCP query, `git fetch`, and/or `git show origin/main:path`. These operations can all return internally consistent, successful results because the upstream object was changed rather than the response being syntactically forged.

6. **Collapse fake independence.** The agent may believe that GitHub API output and a Git object are two mechanically independent signals. They are two mechanisms over one compromised authority. A known-present control can still pass if the attacker preserved it, so the absence detector appears healthy while a targeted object is missing or changed.

7. **Mint valid-but-misleading evidence.** Successful commands produce exit code 0. The receipt classifier maps that to `pass` (`agents/harness/ledger.py:322-359`), and a sufficiently fresh receipt satisfies the claim gate (`ledger.py:1093-1117`). The test at `agents/harness/tests/test_modules.py:823-846` mechanically proves that one zero-exit verification result changes the module from warning to allow.

8. **Corrupt the conclusion.** The agent confidently reports the planted falsehood, cites the fetched file/API response and ledger receipt, and may propagate it to fan-out prompts. Known defect D4 shows that an orchestrator-authored false constraint propagated to about 15 agents because recipients had no way to falsify it (`inputs/INPUT-known-harness-defects.md:151-160`). The exact number of downstream agents in this hypothetical attack is **UNVERIFIED; the settling experiment would be a harmless canary fact with a probe ID in a disposable offline fan-out fixture, measuring whether recipients challenge it**.

### Concrete false conclusion

> “The credential-read guard is enforced by default across both providers, and the protected branch proves the fix is deployed.”

An attacker could plant a test/config fragment asserting the enabled behavior and a green status tied to that poisoned revision. The real bundled implementation says the opposite: the standalone control exits immediately when the toggle is unset (`deny.py:73-101`), the shared implementation uses the same opt-in toggle (`agents/harness/modules.py:50-62,791-798`), and tests explicitly expect credential reads to be allowed by default (`agents/harness/tests/test_modules.py:274-286`). This makes the target falsehood both consequential and locally falsifiable—if the agent remembers to compare the immutable unpacked subject rather than trusting only the credentialed remote.

### Why the controls can all “work” while the conclusion is false

The read guard can correctly block explicit file reads, the injection scanner can correctly see no prompt grammar, branch APIs can correctly return 200, Git can correctly verify object hashes, and the receipt ledger can correctly record a passing command. None of those observations establishes that the credentialed upstream authority was allowed only to read. This is an authority-separation failure, not primarily a detector bug.

## Minimal mitigation

### 1. Remove mutation authority from all agent-reachable GitHub credentials — **UNVERIFIED rollout premise**

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Rotate/revoke every GitHub token that is in plaintext history, User/Machine environment scope, or a shared account file; then provision distinct repository-scoped **read-only** credentials for agent research/query lanes. Keep the owner/bypass/write credential exclusively in a native secure credential store outside hook, shell, and stdio-MCP inheritance. Delete Machine-scope copies after verifying each consumer has a narrow replacement. Do not merely move the same owner-capability PAT from JSON to a keyring: secure storage reduces theft probability, while least privilege prevents conclusion poisoning after theft.

This recommendation's current-token premise is **UNVERIFIED; the settling experiment is a provider-side, name-only credential inventory that records principal, repository allowlist, permissions, expiry, and last-used time, then proves every agent-facing credential lacks Contents/Actions/Administration write and bypass authority**. The recommendation remains appropriate if A28's history claim is confirmed. If it is falsified, apply it only to credentials actually reachable by agent processes.

Expected effect: **very likely (80-90%)** to break steps 3-4 for repository evidence, because a stolen read-only token cannot push commits, forge checks, alter rules, or use an owner bypass. Evidence is the attack's required write-authority precondition and the current config's existing ability to bind named credentials to individual servers (`codex/config.toml:504-522`). It does not protect non-GitHub conclusions or an upstream provider compromise.

Although provider permission/rotation operations extend beyond literal JSON editing, this is categorized `CONFIG` rather than a build because it changes credential and client configuration only; it introduces no code or runtime. A deployment unit must perform it on the Windows/provider side—this analysis unit did not.

### 2. Enable native Claude subprocess credential scrubbing and remove Machine-scope duplicates — **UNVERIFIED coverage**

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it)**

Set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` in the Claude settings environment, then run a presence-only canary test for `GH_TOKEN`, `GITHUB_MCP_PAT`, and representative provider keys in Bash, hooks, and stdio MCP children. Remove Machine-scope copies once narrow consumers are confirmed. A28 names this native control and reports it currently unset (`inputs/audit-findings/A28.md:64-70`); the bundle's Claude env block confirms it is not configured there (`claude/settings.json:4-20`).

Coverage is **UNVERIFIED; the settling experiment is the two-mode child presence-boolean probe above**, because A28 explicitly warns that the native scrub covers known classes rather than every third-party key. Expected effect is **likely (55-80%)** to prevent opportunistic inheritance in Claude child processes, based on the stated native behavior and the hypothesized acquisition step. It is defense in depth, not a substitute for read-only credentials.

### 3. Bind remote-evidence claims to principal and immutable object only if least privilege cannot be completed — **UNVERIFIED need**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

If an agent must retain a write-capable credential, extend the existing receipt bus with one `remote_evidence` receipt containing only nonsecret fields: provider, authenticated principal, normalized repository, immutable commit SHA/object ID, command digest, and result status. A claim about branch/check/repository state is fresh only when the principal is allowlisted and the object ID is cited; an absence claim additionally requires a known-present control under the same principal and a second authority that does not derive from that remote. Never store the token, headers, or credential-store path.

Need is **UNVERIFIED; the settling experiment is to complete mitigations 1-2 and then enumerate workflows that genuinely require an agent-visible write/bypass credential**. If that inventory is empty, do not build this. If needed, expected effect is **likely (55-80%)** against accidental confused-identity and mutable-branch conclusions, because it exposes which principal/object produced the receipt. It is **unlikely (20-45%)** to stop a stolen allowlisted owner credential that can mutate the upstream before attestation; least privilege remains the real control.

### Acceptance test for the minimal mitigation

Use disposable local fixtures and provider read-only metadata only:

1. Prove the detector: a synthetic credential path is denied when the unattended profile is enabled, and a benign neighboring config read is allowed.
2. For every agent/hook/MCP child, emit booleans for whether forbidden credential names exist; all forbidden names must be false, explicitly allowlisted per-server names true only in that server.
3. Under every agent-facing GitHub principal, query identity and repository permission; expected identity must match and write/admin/bypass permissions must be false.
4. Attempt no real mutation. Instead, validate denial through provider permission metadata or a disposable private test repository owned for this acceptance test.
5. Run an offline false-conclusion fixture: a mutable branch points at a poisoned commit while a pinned clean commit disagrees. The claim must remain unconfirmed unless it cites the immutable object and correct principal.

Completion is **UNVERIFIED until those five acceptance checks pass; the checks themselves are the settling experiment**. Do not mark the mitigation done from config inspection alone.

## Anti-overfit gate

The recommended architecture passes the gate:

- Proposals 1 and 2 use provider/native credential controls and existing configuration.
- Conditional proposal 3 rides the existing receipt/claim hook bus (`agents/harness/modules.py:2000-2137`; `agents/harness/ledger.py:1053-1184`) and is bounded below roughly 200 lines.
- Nothing adds a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
- A secret broker daemon is deliberately rejected. A broker would be BUILD-LARGE, add a high-value always-on authority, and still fail if it dispensed an owner-capability token to an untrusted child. Native keyrings plus least-privilege per-client credentials solve the relevant problem more directly.

## Alternatives considered and rejected

### Turn on `HARNESS_CREDENTIAL_GUARD` everywhere

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

This is useful for unattended sessions, and the synthetic probe proves its known-positive behavior. It is not the minimal durable answer to this attack because it detects model-issued credential-file reads, while the concrete chain uses inherited environment material. It also previously caused legitimate false blocks, which is why both implementations say it is opt-in (`deny.py:73-89`; `agents/harness/modules.py:50-62`). Enabling it without fixing inheritance would create a comforting but incomplete signal.

### Add more secret regexes

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Rejected. The known-defect file documents a shared use-versus-mention failure across multiple prose/payload scanners and says the false-positive class is self-amplifying (`inputs/INPUT-known-harness-defects.md:9-48,52-87`). More patterns do not address a subprocess reading a normal environment variable and risk repeating the same detector defect.

### Require two tools for every conclusion

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Rejected as a sufficient control. Two commands are not mechanically independent if both consume the same credentialed repository. The right unit of independence is authority/provenance, not tool name.

### Replace the whole harness with a durable security runtime

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Rejected. The attack is stopped more directly by removing write authority and narrowing credential delivery. A new runtime would violate the anti-overfit boundary, expand trusted code, and become another secret-bearing process.

### Focus on `accounts.json` key-pool poisoning

Rejected as the primary chain. The structurally reported Exa and Databricks literals demonstrate exposure, but possession or replacement of an Exa key does not by itself let an attacker control Exa's search corpus. It more naturally causes quota exhaustion, invalid-key failures, account confusion, or denial of service. The corpus indeed records invalid Exa keys (`inputs/corpus.json:9455-9465`), but that does not prove conclusion corruption. A malicious endpoint/URL field in an account record would change the analysis, but such a field is **UNVERIFIED; the settling experiment is a schema-only inspection of account records and resolution code without reading values**.

### Focus on replacing `.claude/.credentials.json` or `.codex/auth.json`

Rejected as the primary chain because the live files are not in this bundle and were intentionally not inspected. Credential substitution could create a lower-privilege confused deputy that turns private resources into apparent absences, but current file presence, format, ACLs, atomic-write behavior, and provider error mapping are **UNVERIFIED; the settling experiment is metadata-only file existence/ACL/owner inspection plus a disposable two-account fixture that observes whether denied access is surfaced as error or empty result**. Codex's bundled config points auth to keyring (`codex/config.toml:47-48`), which makes a plaintext Codex credential-file chain less plausible for this host.
