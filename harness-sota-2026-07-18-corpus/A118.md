## Executive result

The minimal repair is a configuration-text edit to the `codex` agent: preserve synchronous *semantic* completion (the adapter must not return until a terminal result exists), but implement it as a `longrun` runner plus Monitor/poll-to-terminal-state. Remove the direct-foreground alternative and change “never background” to “never detach without monitored fan-in.” This rides the existing agent/rule/`longrun` bus and introduces no new runtime. **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Although the edited file is Markdown rather than JSON, it is native Claude Code agent configuration, not executable harness code.

No other available agent/contract pair met all three tests: explicit X versus NOT-X, the same situation, and a reachable collision. I recorded the strongest near-misses below so later units do not have to re-walk them.

## Method and finding threshold

For each agent I compared imperatives, prohibitions, ordering requirements, permission behavior, completion authority, output/handoff behavior, memory behavior, long-operation behavior, and mutation expectations against both contracts. I required all of:

1. one text says X and the other says NOT X (not merely different emphasis or specificity);
2. both statements govern the same concrete situation;
3. the situation is reachable for that agent rather than ruled out by its own role, tools, or observed usage;
4. runtime precedence or native enforcement is established as far as the supplied Linux bundle and current primary documentation allow.

I also searched imperative vocabulary across all files (`must`, `never`, `always`, `only`, `do not`, `block`, `ask`, `write`, `commit`, `push`, `run`, `done`, and related forms), then read surrounding sections to avoid treating isolated keywords as rules.

### Which side wins at runtime

There are two distinct meanings of “wins,” and conflating them would overclaim:

1. **Native hard enforcement:** neither Markdown side deterministically wins. Claude Code’s current documentation says CLAUDE.md instructions shape behavior but “are not a hard enforcement layer”; client settings enforce denials regardless of model choice ([Claude Code memory documentation](https://code.claude.com/docs/en/memory), lines 323-332 in the fetched page). The bundled settings route Bash through hooks (`~/.claude/settings.json:139-180,229-245`), but a validated search for `longrun` found no long-operation enforcement in `/local_disk0/codexwork/bundle/agents/harness`; the detector did find known-present `longrun` references in `compute-confidence-gate/gate.py:4,130-144`, `bg-registry/register.py:14-25`, and the cross-vendor rule. A separate settings-to-hook inspection showed no dedicated Bash hook that rewrites or blocks a direct long Codex command. It is therefore almost certain (90-99%) that this bundle has no deterministic “must use longrun” gate, based on both an implementation-wide symbol search with positive controls and independent settings/wiring inspection.

2. **Model instruction resolution:** the **agent’s direct-foreground rule is very likely (80-90%) to win**, because Claude Code documents that a custom agent’s Markdown body becomes that subagent’s own system prompt (`~/.claude/agents/*.md` body), while CLAUDE.md files load separately into its initial context ([custom subagent documentation](https://code.claude.com/docs/en/sub-agents), “Write subagent files” and “What loads at startup,” especially page lines 290-305 and 756-765). Anthropic’s platform documentation explicitly states that when system and user instructions conflict, system instructions take precedence ([mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)). The agent repeats foreground/never-background at its description, opening directive, procedure, and final NEVER list, making accidental contract compliance less likely.

The exact Windows Claude Code choice is nevertheless UNVERIFIED because this Linux bundle has no runnable owner session or raw `codex` subagent transcript. A controlled Windows experiment would settle it: invoke `@agent-codex` on a harmless `codex exec` stub that sleeps 65 seconds, capture the subagent JSONL plus PreToolUse hook input, and record whether the emitted Bash command uses direct foreground or `longrun`/Monitor. Until that experiment, “agent wins” is a well-supported precedence prediction, not fabricated observation.

At a still higher layer, a user denial or native permission denial would win over both texts. Official subagent documentation states that custom subagents inherit permissions and that only the permission system or the user can grant approval ([custom subagent documentation](https://code.claude.com/docs/en/sub-agents), page lines 128-143 and 782-783). That does not resolve this collision because both command shapes may be permitted; it only bounds the agent prompt’s authority.

## Runtime-precedence synthesis

1. a custom agent body becomes the agent’s system prompt;
