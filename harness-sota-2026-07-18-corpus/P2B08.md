## Executive verdict

Aider is not a better replacement harness. It is a deliberately narrow, single-agent pair-programming loop whose strongest ideas are (1) a task-conditioned, token-budgeted symbol map; (2) deterministic edit parsing with bounded corrective feedback; (3) edit-adjacent lint/test feedback; and (4) continuous end-to-end benchmarking of model/edit-format combinations. Its narrowness is an advantage: its core loop is legible, bounded, and empirically tuned.

Our harness is materially stronger in the areas that make a general agent harness a harness: MCP/tool breadth, policy permissions, lifecycle hooks, durable semantic memory, cross-provider continuity, multi-agent orchestration, typed receipts, and prompt-injection/secret/destructive-operation controls. Aider has no native MCP, no subagents or agent teams, no lifecycle extension bus comparable to hooks/skills, no policy sandbox, and no semantic cross-session memory. Those are not minor omissions; they make wholesale replacement a regression.

The correct extraction is small and selective. **Very likely (80-90%)**, based on Aider's implemented mechanisms plus the local absence probes below, the highest-value experiments are a bounded repo-context preflight and an edit-batched lint/test feedback hook. **UNVERIFIED whether either improves current Opus/GPT-5.6 work on this owner's tasks; the settling experiment is a repeated local A/B over representative tasks measuring file-selection precision, held-out acceptance, tokens, cost, and wall time.** Importing Aider itself would violate the anti-overfit gate by adding a second orchestration/edit runtime.

## 1. Agent loop

### What Aider actually does

Aider's `Coder.run_one()` preprocesses a user message, sends it, and repeats only when the previous response generated a `reflected_message`. The retry budget is explicitly three reflections ([base coder lines 98-101, 924-944](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L98-L101)). A reflection can be caused by malformed edit syntax, an edit that cannot be applied, a referenced file that needs approval/addition, lint failure, or test failure. Malformed edits are caught, diagnosed to the model, and turned into the next corrective message ([base coder lines 2296-2328](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2296-L2328)). This is a compact state machine, not an open-ended autonomous planner.

Aider supports several interaction modes. `ask` is read-only discussion, `code` produces edits, and `architect` makes one model propose a solution and a fresh editor coder translate that prose into file edits ([chat modes](https://aider.chat/docs/usage/modes.html)). In source, architect output is passed directly as the editor's message after an optional approval; the editor gets a fresh message history, the configured editor model/edit format, no repo map, and no shell-command suggestions ([architect coder lines 6-44](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/architect_coder.py#L6-L44)). This isolates reasoning from edit-format production, but it is not multi-agent collaboration and the handoff is untyped free-form prose.

The new `context` coder on main iteratively asks the model to name relevant files, replaces the editable file set with those mentions, and retries until stable or nearly out of reflections ([context coder](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/context_coder.py#L5-L50)). This is a focused file-selection loop.

### Comparison

Claude Code and Codex already have native tool-use loops: tool failures are returned to the model, it can search/read before editing, and the lifecycle harness detects repeated identical actions and unverified completion claims (`~/.agents/harness/modules.py:1812-1862,2000-2136`). The owner harness also has explicit plan mode, role agents, structured handoff rules, and subagent lifecycle validation (`~/.claude/settings.json:40-41,699`; `~/.agents/harness/modules.py:2331-2393`). We do not lack reasoning/editing separation; ours is more flexible and has stronger handoff controls.

Aider is better at one narrow point: the edit failure is converted into a specific, local corrective turn with a hard retry cap. Native Claude/Codex usually do this themselves, while the harness's anti-degeneration layer is more general and indirect.

**Port disposition — NATIVE (Claude Code already does this; we just enable it).** Keep native tool-error feedback and the existing repeated-action gate; do not import Aider's textual edit protocol. The concrete Aider lesson is to ensure write/edit failures preserve the native error, nearby mismatch context where available, and a bounded retry count. **Likely (55-80%)** this improves recovery from the corpus's 934 unread-before-write failures because those failures are deterministic and locally correctable (`corpus/corpus.json:4299`), but **UNVERIFIED for a new adapter change; replaying the top write/edit fingerprints through native tools with and without enriched corrective context would settle it.**

### Where Aider is worse

Its model must emit one of several textual edit formats (`whole`, search/replace `diff`, `diff-fenced`, unified diff, or editor variants), creating a failure class native structured editing tools avoid ([edit formats](https://aider.chat/docs/more/edit-formats.html)). Its own leaderboard separately measures malformed/well-formed edits; for example, the published GPT-5 high run was 91.6% well formed, not 100% ([leaderboard](https://aider.chat/docs/leaderboards/)). The architect/editor handoff is raw prose with no schema, evidence receipt, scope check, or reviewer. Copying its format zoo or raw architect packet would regress this harness.

## 2. Context management

### Aider's differentiator: the repository map

Aider parses the repository with tree-sitter tag queries, extracts definitions and references, builds a weighted directed multigraph, personalizes it using chat-file and task mentions, runs PageRank, and renders the highest-ranked definition lines under an adaptive token target ([repo map docs](https://aider.chat/docs/repomap.html); [source lines 366-553](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L366-L553)). Mentioned identifiers receive extra weight; references from files already in chat receive a large boost. It binary-searches the number of ranked tags to approach the token budget ([source lines 635-704](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L635-L704)) and caches parsed tags. The map is sent on each request, while editable files are included in full and reference-only files are separated.

This is the clearest capability Aider has and the live harness does not. The local harness has bounded lexical recall for Basic Memory (`~/.agents/harness/README.md:21-29,40-44`) and configured Repomix/Serena tools (`~/.claude/settings.json:47-51`), but no automatic, task-conditioned dependency-ranked symbol slice. Repomix is installed (`Get-Command repomix` resolved `...\npm\repomix.ps1`), so a cheaper approximation is available without importing Aider.

Aider also offers explicit `/add`, `/read-only`, `/drop`, `/tokens`, `/clear`, `/reset`, `/map`, `/map-refresh`, and `/save` controls ([commands](https://aider.chat/docs/usage/commands.html)). It summarizes old chat history in a background thread after a soft token limit while keeping a recent tail; the summarizer recursively compresses older messages and can fall back from the weak model to the main model ([history source lines 7-137](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/history.py#L7-L137)). It can arrange stable prompt prefixes—system prompt, read-only files, repo map, editable files—for provider prompt caching ([prompt caching](https://aider.chat/docs/usage/caching.html)). Claude Code already auto-compacts and exposes context visualization; the harness additionally replays an objective ledger and semantic memory, so these are not gaps.

### UNVERIFIED recommendation — CONFIG (settings/JSON only): try a Repomix MCP context preflight

Use Claude Code's native JSON `mcp_tool` hook type to call the already-configured Repomix packer at `SessionStart` or `SubagentStart`, with tree-sitter compression and a strict output cap, injecting only structure/signatures rather than full files. Claude's hook reference confirms MCP tools can be hook handlers and their output becomes hook context ([Claude hooks](https://code.claude.com/docs/en/hooks)). **UNVERIFIED whether the Repomix tool input can interpolate the hook `cwd` in this host's current JSON schema; a disposable project hook that prints the resolved MCP input and returns a 1 k-token pack would settle it before any live configuration change.**

**Likely (55-80%)**, based on Aider's mechanism and the existing local tools, that a bounded map helps fresh subagents choose files; the lack of a local A/B prevents a stronger claim. The experiment must compare no map versus compressed Repomix on at least 20 representative tasks and record first-choice file precision, files read, tokens, acceptance result, and wall time. If it does not win, remove it.

### UNVERIFIED fallback — BUILD-LARGE (new daemon/service/runtime -- needs its own justification): exact PageRank map

Only if the CONFIG experiment loses specifically on file selection should a task-conditioned def/ref ranker be considered. Port Aider's mechanics: cache tree-sitter tags by content/mtime; build file edges from shared identifiers; personalize on mentioned files/symbols; exclude files already present in full; boost root manifests and current chat files; render definition context; enforce a hard token ceiling; expose it through the existing hook/MCP bus. This is BUILD-LARGE because Aider's implementation is roughly 868 source lines plus parsers, graph ranking, caches, and renderers—not an honest sub-200-line hook.

**UNVERIFIED recommendation premise:** no controlled result shows Aider's PageRank layer beats compressed Repomix or native Claude exploration on this owner's repos. The same A/B above, followed by PageRank as a third arm, settles it. **Unlikely (20-45%)** that building the exact map is justified before that evidence, because models already search code natively and elaborate context scaffolding risks overfitting. This proposal is an explicit anti-overfit exception candidate, but it still rides the existing bus and must not become a second orchestration runtime, vector database, knowledge graph, or daemon.

### Where Aider is worse

Aider warns that large repos can be slow and that repo maps can distract weaker models; its map token setting is a suggested target that may expand, especially with no files in chat ([repo map optimization](https://aider.chat/docs/repomap.html#optimizing-the-map); [large-repo FAQ](https://aider.chat/docs/faq.html#can-i-use-aider-in-a-large-mono-repo)). It supports one git repository at a time ([FAQ](https://aider.chat/docs/faq.html#can-i-use-aider-with-multiple-git-repos-at-once)). Our native agents can traverse multiple authorized roots, selectively invoke Serena/Repomix, and avoid paying a map cost on tasks that do not need one.

## 3. Memory and continuity

Aider has conversation persistence, not semantic memory. It writes input/chat/LLM history files, optionally restores the last chat, summarizes old turns, and can save a list of `/add` and `/read-only` commands that reconstruct file context ([options](https://aider.chat/docs/config/options.html#history-files); [commands](https://aider.chat/docs/usage/commands.html)). It can manually include recent git diffs via `/run git diff ...` ([FAQ](https://aider.chat/docs/faq.html#how-do-i-include-the-git-history-in-the-context)). There is no cross-session retrieval, durable decision model, supersession, scoped auto-memory, or semantic note store in the verified source snapshot.

Our harness is decisively better: the lifecycle layer records an event ledger, replays goals and relevant milestones, performs bounded recall from a local Basic Memory index, and keeps raw secrets/identifiers out of checkpoints (`~/.agents/harness/README.md:17-29`; `~/.agents/harness/modules.py:944-1002,1572-1660`). Claude Code also has native CLAUDE.md/rules and auto memory ([Claude memory docs](https://code.claude.com/docs/en/memory)). No Aider memory mechanism should be ported.

**Port disposition — NATIVE (Claude Code already does this; we just enable it).** Preserve native auto-compaction and auto memory, plus the existing Basic Memory and objective ledger separation. Aider's history restore is strictly weaker and risks replaying stale conversational assumptions without typed validity or supersession.

## 4. Tool and MCP handling

Aider is not a general tool-using agent. Its built-ins are a fixed application surface: file edit formats, git, shell-command suggestions, `/run`, `/test`, `/lint`, webpage scraping, images/PDFs, voice, and clipboard/IDE watch flows. Suggested shell commands require an explicit yes and can remember “don't ask again”; direct `/run` commands execute because the user invoked them ([base coder lines 2434-2485](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2434-L2485); [commands lines 993-1053](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/commands.py#L993-L1053)). It uses LiteLLM to reach many hosted or local models, but model-provider breadth is not tool breadth.

The verified CLI has no MCP client/server or dynamic tool discovery. The upstream request for both remains open ([issue #4506](https://github.com/Aider-AI/aider/issues/4506)). Our settings allow numerous MCP namespaces (`~/.claude/settings.json:27-63`), the shared hook bus can match MCP tool events, and the corpus records 93 MCP servers touched. The corpus also proves breadth alone is not reliability: the dead `claude.ai Tavily` endpoint produced 135 “not connected” failures and is the highest-error named tool in the pinned ground truth. Aider avoids that class by having fewer tools, but loses the capabilities altogether.

**Do not port Aider wholesale — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Using Aider as an additional runtime to gain LiteLLM/model breadth would reintroduce the explicitly rejected second orchestration runtime. **Very unlikely (5-20%)** to be net-positive, because it would discard native MCP, hooks, permissions, subagents, and structured tools while adding another edit parser and dependency stack. Evidence: the source/documentation absences above and the owner's anti-overfit exclusions.

## 5. Permission model

Aider's permission model is conversational and file-scope-oriented:

* files explicitly added to chat are editable;
* read-only files are context only;
* ignored files are skipped;
* creating a new file or editing a file not in chat prompts for approval;
* LLM-suggested shell commands require explicit yes;
* `--dry-run` suppresses writes;
* `--yes-always` bypasses all confirmations.

The concrete edit checks are in [`allowed_to_edit`](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2191-L2240). This is understandable and useful for pair programming, but it is not an OS sandbox, tool policy engine, network policy, secret guard, or protected-path model.

Our harness has granular allow/deny rules, permission modes, path restrictions, reversible-operation policy, secret/credential handling, and PreToolUse/PermissionRequest hooks (`~/.claude/settings.json:26-74`; `~/.agents/harness/modules.py:725-903`). One important local weakness is configuration: the live default is `bypassPermissions` and allows `C:` and `D:` (`~/.claude/settings.json:71-74`), which official Claude documentation recommends only for isolated containers/VMs ([permission modes](https://code.claude.com/docs/en/permission-modes)). That is a local risk, but Aider is not the cure; it has less policy control, not more.

Aider is also worse by default on git verification: it auto-commits edits and defaults `--git-commit-verify` to false, which means it uses `--no-verify` unless enabled ([git integration](https://aider.chat/docs/git.html#disabling-git-integration)). This directly conflicts with the owner's non-negotiable “never `--no-verify` without explicit instruction.” Its `--yes-always` is similarly coarser than our per-tool/path policies.

**Port disposition — NATIVE (Claude Code already does this; we just enable it).** Aider's read-only/editable file distinction maps to native plan mode, Read versus Edit permissions, and protected paths. Do not copy `--yes-always` or default `--no-verify` behavior.

## 6. Customization: rules, skills, and hooks equivalents

Aider has a broad configuration surface but a shallow extension surface:

* CLI flags, `.aider.conf.yml`, environment variables, and `.env` are equivalent ways to set most options ([configuration](https://aider.chat/docs/config.html));
* `.aiderignore` and `--subtree-only` bound repository scope;
* conventions files are loaded read-only and can be cached ([conventions](https://aider.chat/docs/usage/conventions.html));
* `--load` executes a file of slash commands at startup ([options](https://aider.chat/docs/config/options.html#load-load-file));
* model settings/metadata files, aliases, edit formats, weak/editor models, reasoning effort, and thinking tokens tune provider behavior ([advanced settings](https://aider.chat/docs/config/adv-model-settings.html));
* custom system/edit backends require modifying coder source, and upstream says this path is not well documented ([FAQ](https://aider.chat/docs/faq.html#can-i-change-the-system-prompts-that-aider-uses)).

Conventions are analogous to CLAUDE.md/rules. Startup command files are crude macros analogous to commands/skills. Neither is equivalent to our lifecycle hooks, scoped skills, MCP tools, custom subagents, provider-neutral adapters, or module result contract (`~/.agents/harness/README.md:3-27`). Aider has no hook equivalent that can observe every tool, inject context, block a dangerous operation, validate a subagent handoff, or write a typed receipt.

**Port disposition — NATIVE (Claude Code already does this; we just enable it).** Use CLAUDE.md, path-scoped rules, skills, agents, plugins, and hooks. Aider's conventions pattern reinforces the current discipline of keeping global instructions short and moving procedures into scoped skills; it adds no missing mechanism.

## 7. Multi-agent support

Aider has none in the harness sense. Architect mode makes two serial model calls with a one-way prose handoff. There is no task fan-out, concurrent worker, mailbox, team state, role lifecycle, worktree isolation, structured receiver read-back, stalled-worker detector, or synthesis protocol. The official scripting API can launch multiple independent Aider processes, but that is shell-level composition, not coordinated multi-agent support ([scripting](https://aider.chat/docs/scripting.html)).

Our harness exposes native `Task`/agent capabilities and `teammateMode`, then adds SubagentStart/SubagentStop handling, structured handoff instructions, I-PASS read-back, and hollow-output detection (`~/.claude/settings.json:40-41,699`; `~/.agents/harness/modules.py:2331-2396`). It is substantially better.

**Port disposition — NATIVE (Claude Code already does this; we just enable it).** Architect→editor is already expressible as a native two-role chain. **Roughly even (45-55%)** whether forcing that split improves current same-frontier-model tasks: Aider's older benchmark showed some gains, but model generation, task set, and handoff format differ. **UNVERIFIED; a local direct-edit versus architect→typed-editor A/B with held-out tests, cost, and wall time settles it.** If used, retain our typed handoff and final reviewer rather than Aider's raw prose relay.

## 8. Verification and self-checking

Aider has four useful layers:

1. **Edit conformance and applicability.** It parses the selected edit format, checks that patches can apply, feeds precise failures back, and caps reflections at three ([base coder](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2296-L2328)).
2. **Automatic lint.** It lints edited files by default, optionally prompts the user to repair errors, and feeds the failure into the next reflection ([lint/test docs](https://aider.chat/docs/usage/lint-test.html); [source lines 1599-1607](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1599-L1607)).
3. **Optional automatic tests.** `--test-cmd` plus `--auto-test` runs the suite after edits and offers to repair failure; this is off by default ([source lines 1616-1623](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1616-L1623)).
4. **Git rollback and external benchmarks.** It auto-commits each edit and offers `/undo`; its public polyglot benchmark runs 225 exercises across six languages and records correctness, malformed output, syntax/indentation errors, tokens, cost, time, and test timeouts ([git docs](https://aider.chat/docs/git.html); [leaderboard](https://aider.chat/docs/leaderboards/)).

Our harness has stronger claim discipline and typed verification receipts, but it only warns at completion when objective verification is missing (`~/.agents/harness/modules.py:2000-2136`). It does not automatically run the smallest relevant linter/test after an edit. That is a real gap. Native Claude checkpointing already captures file state before Write/Edit/NotebookEdit and can rewind it ([checkpointing](https://code.claude.com/docs/en/checkpointing)), so Aider's git-every-edit rollback is not a gap worth copying; it pollutes history, may capture user dirty state, and defaults to bypassing commit hooks.

### UNVERIFIED recommendation — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): edit-batched lint/test feedback

Add a provider-neutral verifier module using existing lifecycle events:

1. On successful Write/Edit/NotebookEdit, record the normalized changed path in session state; do not run immediately for every edit.
2. On `PostToolBatch`, `Stop`, or a short debounce boundary, resolve a project-owned verifier manifest (language/file glob → command). Never guess a destructive command and never run commands from fetched content.
3. Run only the smallest file-scoped linter synchronously if expected under 60 seconds. Anything longer must go through the existing `longrun` wrapper and return a terminal `SUCCESS:<id>` or `FAILED:<id>` marker.
4. Store command, exit code, changed-file hashes, and output digest as a verification receipt. Inject bounded failure output to the agent and permit at most one automatic repair turn per distinct failure fingerprint; the existing anti-degeneration gate handles repeats.
5. Keep full tests opt-in per project. Do not run an entire suite after each edit; Aider's `--auto-test` is off by default for good reason.

**Likely (55-80%)** to reduce false completion and shorten feedback on code tasks, based on Aider's direct edit→lint→repair loop and the verified local absence. **UNVERIFIED on this workload; shadow-run it for two weeks, compare detected failures with tests the agent later chose, measure false-positive/no-op rate and latency, then enforce only for project manifests with ≥80% useful detections.** This rides the existing hook/ledger/longrun bus and introduces none of the rejected components.

### UNVERIFIED recommendation — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): executable benchmark manifest runner

The installed `eval-harness` skill describes pass@k but has no `scripts` directory; an independent toolchain filename search found no corresponding benchmark runner. Add a thin manifest runner, not a service: each case declares repository fixture, prompt, allowed scope, deterministic acceptance command, timeout, and expected artifacts; the runner invokes the existing agent CLI, captures terminal receipts, and emits JSONL with success, attempts, tokens/cost where available, wall time, changed files, and failure fingerprint. Use held-out private cases to reduce leaderboard contamination.

**Likely (55-80%)** to improve harness design decisions because it turns claims about architect splits, repo maps, and verifier hooks into comparable measurements. **UNVERIFIED that fewer than 200 lines cover all three providers; a five-case Claude-only spike with a stable JSONL schema settles the sizing before expanding.** Aider's benchmark is evidence for the measurement categories, not evidence that its public task scores transfer here.

7. **Do not build the PageRank map on reputation alone.** Aider documents the mechanism and whole-system results, not a controlled map-on/map-off causal gain on current models.
