# X107 — Cross-domain borrow: reliability engineering → use-versus-mention guards

**Unit:** X107  
**Lens:** reliability engineering (fault trees, false trips, redundancy/diversity, common-cause failure)  
**Target:** guards that act on payload text even when the text only mentions or documents the guarded operation  
**Scope:** external research and design translation only. Per the unit brief, I did not inspect or make claims about the local harness implementation. The supplied problem statement is the evidence for “5 detectors, 12+ false fires”; this unit does not independently verify that count.

## Executive result

The borrow transfers, with an important restriction. The specific reliability-engineering mechanism is **qualified actuation**: model the lexical hit as a sensor indication, place an **INHIBIT gate** before actuation so that the indication can cause an action only under a separately established operating condition, and use **diverse—not merely redundant—evidence** when the cost of a false trip warrants confirmation.

NASA's *Fault Tree Handbook with Aerospace Applications* defines the INHIBIT gate as a special AND gate: one input can produce the output only when a qualifying condition is satisfied; in its example notation, output Q occurs only when input A occurs under conditional input B (Chapter 4, p. 40 of the handbook's printed pagination) ([NASA handbook PDF](https://extapps.ksc.nasa.gov/reliability/Documents/Fault_Tree_Handbook_with_Aerospace_Applications_August_2002.pdf)). In a protection system, this separates “the sensor observed a trip-like signal” from “the plant is in the state in which that signal means trip.” The IAEA describes majority voting such as two-out-of-three or two-out-of-four as a means of preventing spurious signals from causing unnecessary trips, and immediately distinguishes **diversity**—different physical or functional means—from repetition of the same design; diversity protects against design or maintenance errors that can defeat identical channels (sections 14.4.1–14.4.2) ([IAEA Technical Reports Series No. 387 PDF](https://www-pub.iaea.org/MTCD/Publications/PDF/TRS387_scr.pdf)). The NRC likewise treats latent design defects as common-cause risks requiring defense-in-depth and diversity, rather than assuming duplicated digital channels are independent ([NRC Digital I&C research](https://www.nrc.gov/about-nrc/regulatory/research/digital); [NRC BTP 7-19 index](https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr0800/ch7/index)).

Translated to this harness, the actuation equation is:

```text
guard_action = hazard_signal(payload) AND operational_role(event)
```

The first term may remain the existing pattern/semantic detector. The second must come from a different information path: the hook event type, typed tool arguments, message provenance, parser span, or action plan—not another search over the same untyped payload. A quoted command in a document can satisfy `hazard_signal` but not `operational_role`; an actual tool invocation can satisfy both.

**Confidence: very likely (80-90%)** that this structural translation is valid. Evidence: both systems have (1) an observation that is insufficient by itself, (2) a context that changes the observation's operational meaning, and (3) a consequential actuation. The confidence is not “almost certain” because natural-language role boundaries can be ambiguous, unlike many engineered plant modes, and some harness events may not expose trustworthy typed provenance.

**Effectiveness is UNVERIFIED; the settling experiment is a labeled replay of every supplied false-fire transcript plus a stratified sample of genuine positive guard events through the proposed two-input gate, reporting false-positive and false-negative confusion matrices per detector.** Therefore the implementation recommendation below inherits UNVERIFIED in its heading.

## What reliability engineering solved in its own field

### 1. An indication is not automatically an actuation condition: the INHIBIT gate

Fault-tree analysis starts from a defined undesirable top event and decomposes the combinations of events that can produce it. An INHIBIT gate is not a generic “be smarter” instruction. It records a precise logical dependency: an input is causally effective only while a named conditioning event is true. NASA's handbook says the gate's output occurs only when the input occurs under the specified condition ([NASA handbook, Chapter 4, p. 40](https://extapps.ksc.nasa.gov/reliability/Documents/Fault_Tree_Handbook_with_Aerospace_Applications_August_2002.pdf)).

That matters because the same physical indication can have different meanings in different system states. NASA's software fault-protection guidance says variations in fault-protection behavior should be based directly on system mode or activity, and gives mission phase as the example; it also explicitly requires tolerance of false alarms because false alarms are inevitable ([NASA Software Engineering Handbook, “Fault Detection and Response,” §4.9.1.5–4.9.1.6](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695798/9.07%2BFault%2BDetection%2Band%2BResponse)). This is the closest source-field analogue to distinguishing text used as a control input from identical text carried as inert documentary content.

The key engineering move is to specify the condition, not merely tune the sensor threshold. Raising a lexical threshold may suppress some mentions, but it leaves “is this text being acted upon?” implicit. An inhibit/conditioning input makes that missing predicate part of the architecture and part of testing.

### 2. Coincidence logic controls false trips, but redundancy alone is not independence

Protection systems often use `k-out-of-n` coincidence: an actuation is emitted only when enough channels agree. The IAEA describes two-out-of-three voting concretely: the voted signal is true only when at least two of three redundant trip-unit inputs are true ([IAEA-TECDOC-973, §2.2.4.4](https://www-pub.iaea.org/MTCD/Publications/PDF/te_973_prn.pdf)). Another IAEA report explains the purpose in reliability terms: majority voting keeps a spurious signal from initiating an unnecessary trip ([IAEA TRS 387, §14.4.1](https://www-pub.iaea.org/MTCD/Publications/PDF/TRS387_scr.pdf)).

However, voting pays off only to the extent that channel failures are sufficiently independent. Three regexes trained or written around the same words are three nominal channels with one common cause. The IAEA defines common-cause failures as multiple items failing from a single event or cause—including design deficiency, maintenance error, environmental condition, signal saturation, or cascading effects—and prescribes redundancy, diversity, and independence as distinct countermeasures ([IAEA-TECDOC-1570, Annex III.5–III.9](https://www-pub.iaea.org/MTCD/Publications/PDF/TE_1570_web.pdf)). Its TRS 387 definition of diversity is two or more physically or functionally different ways of performing the same function, including using different measured physical parameters ([IAEA TRS 387, §14.4.2](https://www-pub.iaea.org/MTCD/Publications/PDF/TRS387_scr.pdf)). The UK Health and Safety Executive makes the same distinction operationally: redundancy addresses random failure, while diversity and lifecycle independence address systematic and common-mode failures ([HSE, “Control systems”](https://www.hse.gov.uk/comah/sragtech/techmeascontsyst.htm)).

For use-versus-mention, the common cause is loss of semantic role at the detector boundary. A pattern matcher and an LLM prompt that both receive only the flattened text are not meaningfully diverse with respect to that loss: both must reconstruct role from the same impoverished evidence.

**Confidence: almost certain (90-99%)** that duplicating lexical detectors does not remove this common cause. Evidence: by construction, once role metadata has been discarded, every downstream detector sees the same role-erased representation; model diversity can change error rates but cannot recover authoritative provenance that is absent from its input.

### 3. FMEA and MTBF are supporting tools, not the transferable control

FMEA would usefully enumerate failure modes such as “guard trips on mention,” “guard misses indirect use,” and “role metadata is wrong,” with effects and mitigations. Fault trees would expose the false-trip top event as `lexical hit AND role misclassification`. Neither FMEA nor an MTBF estimate itself prevents a trip. MTBF is especially ill-fitted before a stable exposure unit exists: per message, per byte, per hook event, and per operational action produce different rates.

**Confidence: very likely (80-90%)** that an MTBF target would be misleading at this design stage. Evidence: the supplied unit provides counts of detectors and false fires but no exposure denominator or stationary event definition; reliability rates cannot be compared without both. This is a scoped methodological conclusion, not a claim that MTBF is never useful.

## Concrete harness translation

### Proposal — UNVERIFIED: typed role-qualified guard envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Introduce a small adapter on the existing hook bus that presents every guarded event in a typed envelope. It does not orchestrate work and does not store long-term memory.

```json
{
  "event_kind": "tool_request | user_instruction | assistant_plan | document_content | tool_result",
  "authority": "control | data | observation",
  "destination": "tool-name-or-null",
  "content_spans": [
    {"role": "executable_argument | instruction | quotation | code_example | document | result", "text": "..."}
  ],
  "role_source": "native_event | typed_tool_schema | parser | inferred",
  "role_confidence": "authoritative | structural | heuristic"
}
```

The guard evaluates two separate inputs:

1. **Hazard channel:** Does normalized content describe the guarded operation or artifact?
2. **Demand/role channel:** Is the matched span on a control path that can cause that operation now?

Automatic blocking requires both. A mention-only span may be logged for test coverage but does not actuate. If native event metadata says “tool request” and the hit is in that tool's executable argument field, the role channel is authoritative. If the event is an edit/write whose body contains an example command, the body is data unless a separate event will execute it. Markdown parsing can label quotations and fenced examples structurally, but parser output is weaker than native provenance: code fences can contain scripts that a tool is explicitly asked to run.

This is an INHIBIT-gate translation, not a majority vote. `operational_role` is the conditional input. For high-impact guards, a limited two-channel confirmation can be layered on top, but the channels must be diverse:

```text
lexical/semantic hazard hit
    AND
native control-plane evidence (event kind + typed destination/argument)
```

Do **not** count “regex agrees with LLM classifier” as independent if both see the same flattened string. If authoritative role metadata is unavailable, preserve uncertainty explicitly. A low-consequence guard can warn; a high-consequence operation can request confirmation or apply a narrowly scoped deny rule to the actual tool argument. The precise fail-open/fail-closed policy must be chosen per guard consequence, not globally.

**Confidence: likely (55-80%)** that a thin adapter fits under roughly 200 lines for a small set of existing event shapes. Evidence: the data model and Boolean gate are small, and the proposal rides an existing hook bus named in the unit constraints. The lower bound reflects an **UNVERIFIED premise: that current hook events expose stable event kinds and typed tool arguments; settle it by capturing and schema-diffing one real event of each relevant hook type.** If they do not, this proposal may exceed BUILD-SMALL or require upstream event changes.

### What it catches or distinguishes that payload matching misses

The design expands the observable state from “which tokens occurred?” to “where can this span cause an action?” It is intended to distinguish:

| Event | Hazard text | Operational-role evidence | Result |
|---|---:|---:|---|
| A document explains a prohibited shell command | yes | no; span is document/example | no actuation |
| An edit writes that command into a tutorial | yes | no; edit body is data | no actuation |
| A shell-tool request invokes that command | yes | yes; typed executable/arguments | actuation |
| A user asks the agent to execute it, before a tool call exists | yes | yes, but lower authority; instruction/plan control path | policy-dependent warn/block |
| Tool output echoes the command | yes | no; observation channel | no actuation |
| A command is assembled without the detector's exact phrase | possibly no | yes, but hazard channel still no | still missed unless normalization/action inspection recognizes it |

The last row is deliberately included: role qualification solves false actuation caused by mention; it does not magically solve lexical evasion. A complementary action-normalization step may inspect parsed executable plus arguments at the actual tool boundary, but that is a separate detector improvement, not evidence that the inhibit gate catches everything.

**Confidence: very likely (80-90%)** that authoritative tool-request metadata can separate actual tool invocation from tool output or ordinary document content when those are distinct event types. Evidence: the distinction is supplied by the execution bus rather than inferred from words. **The mapping for user instructions and assistant plans is UNVERIFIED; settle it with adversarial labeled cases containing quoted requests, negation, hypothetical discussion, and instructions embedded in retrieved documents.**

## Adversarial transfer analysis

### Where the analogy holds

1. **Same logical shape.** A lexical hit is an indication; a guard response is an actuator; semantic role is a conditioning state. The NASA INHIBIT gate directly represents `indication AND condition → actuation` ([NASA handbook, Chapter 4, p. 40](https://extapps.ksc.nasa.gov/reliability/Documents/Fault_Tree_Handbook_with_Aerospace_Applications_August_2002.pdf)).
2. **False actuation has a cost.** Reliability engineering explicitly designs against spurious trips, not only missed trips ([IAEA TRS 387, §14.4.1](https://www-pub.iaea.org/MTCD/Publications/PDF/TRS387_scr.pdf)). A guard that interrupts benign documentation is structurally a false trip.
3. **Common-cause reasoning transfers.** Multiple detectors do not supply redundancy if all fail because role was erased before detection. Reliability guidance explicitly separates redundancy from diversity and independence ([IAEA-TECDOC-1570, Annex III](https://www-pub.iaea.org/MTCD/Publications/PDF/TE_1570_web.pdf)).
4. **Mode-aware behavior transfers.** NASA fault-protection guidance ties behavior directly to system mode/activity rather than scattered enable/threshold manipulation ([NASA SWE Handbook, §4.9.1.6](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695798/9.07%2BFault%2BDetection%2Band%2BResponse)). Semantic role is the harness analogue of mode, provided it is explicit and trustworthy.

### Where the analogy breaks

1. **Plant modes are often finite and engineered; discourse roles are compositional and adversarial.** A Markdown code block can be a mere example, a patch destined for later execution, or the exact script requested for immediate execution. Syntax alone does not determine causal role.
2. **Sensor-channel independence can be physically engineered; software evidence often shares a pipeline.** Event type, parser labels, and an LLM classifier may all originate from the same incorrectly tagged message. Calling them “three channels” would overstate diversity.
3. **Voting assumptions are not free.** A two-out-of-three scheme reduces independent single-channel false trips but can increase missed detections and gives little protection against a common design defect. The IAEA's reason for diversity is precisely that identical means share design errors ([IAEA TRS 387, §14.4.2](https://www-pub.iaea.org/MTCD/Publications/PDF/TRS387_scr.pdf)). Therefore I do not recommend generic majority voting over classifiers.
4. **The safety asymmetry varies by guard.** A reactor trip policy is tuned to physical hazard consequences. In a harness, blocking benign work, allowing a destructive action, and pausing for confirmation have different costs. There is no defensible universal `k-of-n` threshold without per-guard loss estimates.
5. **An inhibit input can itself fail.** Mis-tagging executable content as documentation creates a false negative. The proposed architecture relocates risk into role classification; it does not eliminate it.

**Overall transfer judgment: very likely (80-90%)** that the INHIBIT-gate abstraction transfers and is useful, because its claim is only that actuation needs an explicit qualifying condition. **It is unlikely (20-45%)** that protection-system majority voting transfers as a default implementation, because natural-language channels are not demonstrably independent and the loss asymmetry varies. Evidence for both judgments is the contrast between NASA's conditional-gate definition and IAEA/NRC warnings that redundancy without diversity is vulnerable to common cause.

## Validation and fault-tree test plan

The proposal must not be declared “done” from unit tests over hand-written examples. Use two mechanically independent signals for each role boundary: event provenance from the bus and an observable downstream capability to act. The second signal is not a second reading of the same metadata.

1. **Build a labeled replay set.** Include all supplied false fires, all known true fires, and counterfactual pairs where identical hazard text appears once in an executable argument and once in a document/result. Preserve detector identity and guard consequence.
2. **Prove detectors before measuring absence.** Include a known-present executable event for each event type and verify the replay captures it. Separately verify capture through a downstream tool-request record or dry-run actuator trace. Only then interpret zero fires in a class.
3. **Measure both top events.** Report false-trip rate (`mention → actuation`) and missed-demand rate (`use → no actuation`) per guard. Do not collapse them into accuracy; class imbalance would hide the rarer, costly error.
4. **Common-cause injection.** Corrupt or remove role metadata, flatten an event, mislabel a code span, and embed instruction-like text in retrieved content. Verify that the guard degrades to its declared policy rather than silently treating heuristic role as authoritative.
5. **Boundary/adversarial cases.** Test negation, quotation, nested quotations, documentation edits, generated scripts, commands split across variables, user requests to “show but do not run,” tool output containing instructions, and data later passed into an interpreter.
6. **A/B shadow run.** Run old and new decisions without changing actuation, then have a human label disagreements. Promotion requires predeclared per-guard false-positive and false-negative limits.

**Success thresholds are UNVERIFIED; settle them by attaching owner-valued costs to false interruption, confirmation delay, and unsafe allowance, then selecting per-guard operating points before the shadow run.** A raw “fewer fires” target is invalid because a detector that never fires has zero false trips and zero utility.

## Anti-overfit gate

This recommendation passes the stated anti-overfit gate conditionally:

- It rides the existing hook/tool bus.
- It is a typed envelope plus Boolean qualification, not a second orchestration runtime.
- It introduces no vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
- It keeps learned inference off the authoritative path when native provenance exists.
- Its complexity can be removed locally if the bus later becomes role-typed natively.

**Confidence: likely (55-80%)** that the minimal version remains net simpler than repeatedly patching five payload matchers. Evidence: one shared conditioning primitive replaces detector-specific attempts to reconstruct role. **This comparison is UNVERIFIED; settle it by counting changed lines, branches, and event-shape adapters in a spike implementation versus the current five-detector maintenance surface.** If the adapter requires a new daemon or cross-session state, reject this proposal under the anti-overfit gate rather than upgrading it to BUILD-LARGE.

## Rejected alternatives and dead ends

### “Add a negative regex for phrases such as ‘example’ or ‘do not run’”

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Rejected as the primary solution. It encodes a few documentary modes lexically and remains vulnerable to paraphrase, nesting, other languages, and malicious content. It is another sensor threshold, not a qualifying state.

### “Ask a second LLM whether this is use or mention”

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Rejected as an authoritative gate if the model sees only the same flattened payload. It may be useful as a non-authoritative fallback, but it is not diverse against provenance loss and adds latency/nondeterminism.

### “Use three classifiers and majority vote”

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Rejected as a default. It borrows the surface form of reliability voting while violating the independence assumption. IAEA and NRC common-cause guidance is a warning against exactly this reasoning ([IAEA-TECDOC-1570](https://www-pub.iaea.org/MTCD/Publications/PDF/TE_1570_web.pdf); [NRC diversity research](https://www.nrc.gov/reading-rm/doc-collections/nuregs/contract/cr7007/index)).

### “Build a semantic policy daemon with durable memory”

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected. It reintroduces a prohibited second runtime/durable component, adds failure modes, and is unnecessary for an event-local predicate. No evidence found in this research justifies that complexity.

### “Compute MTBF and optimize it”

No proposal tag applies because this is rejected as a premature metric, not a build. Without a stable exposure denominator and separate accounting for false trips versus missed demands, MTBF would compress unlike failures and obscure the design decision.

## Bottom line

Borrow the **logic**, not the industrial ceremony: treat a payload match as a sensor indication; require an explicit, independently sourced operational-role condition before the guard actuates; and regard multiple text-only detectors as common-cause-correlated rather than diverse. This is a defensible cross-domain transfer because the causal shape matches. Generic classifier voting does not transfer cleanly and should not be smuggled in under the language of redundancy.
