# E009 — Ecosystem survey: sandboxing runtimes (Modal, E2B, Daytona, microVMs)

**Unit:** E009  
**Research date:** 2026-07-19 UTC  
**Subject:** the owner's Claude Code / Codex harness on Windows 11, with the subject tree represented by the read-only bundle at `/local_disk0/codexwork/bundle`  
**Write scope:** this artifact only; no subject/config/install mutation was performed

## Executive verdict

Do not add E2B, Daytona, OpenSandbox, Cloudflare Sandbox, or a self-operated Firecracker/Kata stack to this harness now. The harness already has the right remote execution substrate—Modal—and its immediate problem is not missing sandbox technology but a broken and unsafe-by-default path to the technology it already owns. The local corpus records only three named Modal MCP calls: two `modal_estimate_cost` calls with one error and one `modal_volume_ls` call with one error (`corpus.json:3079-3084`, `4215-4220`). That sample is too small to estimate general Modal reliability, but it is enough to reject any claim that the current MCP path is production-proven.

The best evidence-backed architecture is a two-rung execution substrate, not a second agent harness:

1. keep provider-native/local sandboxing for ordinary workspace work (outside this unit's design scope); and
2. use the existing Modal cloud-hub MCP as an explicit escalation target for untrusted, Linux-only, dependency-heavy, GPU, or high-blast-radius execution.

Repairing and hardening that Modal rung is **very likely (80-90%)** to deliver more value per unit of complexity than adding a second hosted sandbox provider. Evidence: Modal already rides this owner's MCP bus according to audit claim C14 (`audit-findings/C14.md:48-70`); its official Sandbox API now has gVisor isolation, default denial of access to other Modal resources, block/allowlist egress controls, filesystem snapshots, and a Beta full-VM runtime; and this owner's recall index contains repeated Modal workload records (`recall_index.json:7753-8160`, with additional Modal entries later in the file). The residual uncertainty is harness-path readiness: the full Windows source paths cited by C14 are absent from this Linux bundle, so the reproduced cold-start defect remains an audit claim rather than independently re-run fact in this unit.

Docker Sandboxes is the one new candidate that merits a controlled bake-off. Version 0.35.0 was released on 2026-07-10 and its local microVM design provides deny-by-default networking, a private Docker daemon, host-side credential injection, and clone-mode workspace isolation. It is **likely (55-80%)** to be the best local microVM product for this Windows owner if it preserves required harness behavior, based on those official controls and first-party Claude/Codex templates. However, its docs explicitly say user-level `~/.claude` and `~/.codex` configuration is not inherited. A wholesale switch would therefore discard user-level hooks, skills, and settings unless deliberately repackaged. That is why this report recommends an experiment, not adoption.

E2B is high quality and active, but redundant here. Daytona's hosted service is active, yet its formerly open-source core is explicitly unmaintained as of June 2026 and its new production core is closed source. Raw Firecracker, Kata Containers, and gVisor are excellent building blocks for infrastructure operators; they are the wrong ownership layer for a personal Windows harness that already has Modal and can trial Docker Sandboxes. Building or self-hosting them would add a service/runtime with patching, image, networking, lifecycle, and credential-broker responsibilities for no measured local gain.

## 2. Taxonomy: products that look similar are not interchangeable

| Layer | Examples | What it supplies | What it does not automatically supply |
|---|---|---|---|
| Isolation engine | Firecracker, gVisor | VM or userspace-kernel boundary | Images, egress policy, credentials, file transfer, lifecycle, MCP |
| OCI-compatible isolated runtime | Kata Containers | VM-backed container runtime for containerd/Kubernetes | A personal-agent workflow or Windows-native host integration |
| Managed sandbox API | Modal, E2B, Daytona, CodeSandbox | Lifecycle, exec/files, images/snapshots, hosted isolation | Preservation of this harness's hooks/skills/rules |
| Serverless sandbox application stack | Cloudflare Sandbox | Worker + Durable Object + per-sandbox VM/container | A drop-in shell boundary for existing local Claude/Codex sessions |
| Local packaged agent microVM | Docker Sandboxes (`sbx`) | MicroVM, policy proxy, secret broker, agent templates | Automatic inheritance of user-level Claude/Codex harness config |
| Self-hosted sandbox control plane | OpenSandbox, E2B Infra | Scheduling/API/lifecycle over Docker/Kubernetes/microVMs | Low operational burden |

This distinction matters to the anti-overfit gate. A remote `exec/files/terminate` MCP is an execution tool on the existing bus. A new long-lived agent scheduler, Durable Object application, Kubernetes control plane, or self-hosted E2B deployment is a new runtime/control plane and must justify its ownership cost.

## 4. Deep findings

### 4.1 Modal: the incumbent is **very likely (80-90%)** still the best remote fit

Modal's current standard Sandbox is explicitly designed for untrusted user/agent code. Its security guide says Sandboxes run on gVisor and are not authorized to access other Modal workspace resources by default. The networking guide is precise: inbound access is absent by default, while outbound access to public IPs is allowed by default; `block_network=True`, CIDR allowlists, and Beta TLS domain allowlists can constrain it ([Modal networking and security](https://modal.com/docs/guide/sandbox-networking)). This means “secure by default” is not synonymous with “exfiltration-safe by default.” A sandbox that receives a model/API token and public egress can still leak that token.

The product is materially broader in July 2026 than the earlier audit framing:

- standard sandboxes support exec, filesystem access, volume/cloud-bucket mounts, timeouts up to 24 hours, and filesystem/directory/memory snapshots ([Sandboxes](https://modal.com/docs/guide/sandboxes), [Snapshots](https://modal.com/docs/guide/sandbox-snapshots));
- filesystem and directory snapshots default to 30-day retention; memory snapshots default to seven days ([Snapshots](https://modal.com/docs/guide/sandbox-snapshots));
- official docs include a Claude Code-in-Sandbox example ([Claude Code example](https://modal.com/docs/examples/sandbox_agent));
- a Beta VM runtime gives each sandbox a real Linux kernel and is recommended for Docker-in-Sandbox, but currently lacks GPUs and memory snapshots ([VM Sandboxes](https://modal.com/docs/guide/vm-sandboxes)); and
- the Apache-2.0 client supports Python 3.10 through 3.14 ([modal-client repository](https://github.com/modal-labs/modal-client), [license](https://raw.githubusercontent.com/modal-labs/modal-client/main/LICENSE)).

Pricing is transparent but not free execution: Starter has $30 monthly credit; Sandbox CPU is listed at $0.00003942 per physical core-second and memory at $0.00000667 per GiB-second ([Modal pricing](https://modal.com/pricing)). The service also retains Sandbox logs for one day on Starter and 30 days on Team, while files/images persist until deletion and snapshot TTLs vary ([Modal security and retention](https://modal.com/docs/guide/security)). Those retention properties rule out silently sending sensitive proprietary data merely because execution is isolated.

The local integration evidence is mixed:

- C14 claims a 41-tool cloud-hub surface and Claude registration (`C14.md:48-54`).
- The corpus confirms named Modal MCP visibility but only three calls, two of which error (`corpus.json:3079-3084`, `4215-4220`).
- PowerShell error fingerprints contain Modal's Python client and a Python 3.14 event-loop deprecation (`corpus.json:4916`, `5348`, `5366`), but the capped fingerprint alone does not prove Modal service failure; it may describe local CLI/warning handling.
- The recall index contains numerous real workload summaries, including account migration, FEP+, and a per-edge GPU parallelization lesson (`recall_index.json:7753-8160`, `8514-8575`). These are evidence of Modal use outside the three named MCP tools, not evidence that the current MCP wrapper is reliable.

Conclusion: Modal the service is high quality; Modal-through-this-harness is not yet demonstrated reliable.

### 4.2 Docker Sandboxes: **likely (55-80%)** the strongest expansion candidate, with a harness-continuity trap

Docker Sandboxes packages the missing local microVM control plane instead of asking this owner to operate Firecracker. The official security model gives each sandbox a VM, network, filesystem, and private Docker daemon. Default policy blocks outbound HTTP/HTTPS unless explicitly allowed, blocks raw TCP/UDP/ICMP and private/link-local ranges, and keeps API credentials in a host proxy that overwrites outbound headers ([security model](https://docs.docker.com/ai/sandboxes/security/), [default posture](https://docs.docker.com/ai/sandboxes/security/defaults/), [credentials](https://docs.docker.com/ai/sandboxes/security/credentials/)).

Workspace behavior must be selected deliberately. Default direct mode mounts the live host workspace read-write, so malicious edits to Git hooks, CI, package scripts, or other auto-executed files cross the VM boundary. `--clone` instead mounts the host repository read-only and works in a private in-VM clone ([usage](https://docs.docker.com/ai/sandboxes/usage/)). For untrusted tasks, direct mode is not an adequate filesystem containment policy.

The product is current: 0.35.0 released 2026-07-10; 0.33.0 closed DNS and ICMP exfiltration paths; 0.34.0 restricted kit installation sources; and 0.35.0 added policy inspection/checking ([release notes](https://docs.docker.com/ai/sandboxes/release-notes/)). It supports Claude Code, Codex, Gemini, Cursor, and other agents out of the box ([supported agents](https://docs.docker.com/ai/sandboxes/agents/)). Windows 11 is supported via the `sbx` distribution, and Docker's product page gives `winget install Docker.sbx` ([product page](https://www.docker.com/products/docker-sandboxes/)); release notes say older Windows is blocked.

The continuity trap is explicit. Sandboxed Claude/Codex instances do not inherit host user configuration such as `~/.claude` or `~/.codex`; only project-level configuration is visible ([Docker Sandbox FAQ](https://docs.docker.com/ai/sandboxes/faq/), [Codex template](https://docs.docker.com/ai/sandboxes/agents/codex/)). Therefore running the whole primary agent inside `sbx` would replace this harness's user-level hook/skill/config plane unless it were repackaged into project configuration or a custom kit. Repackaging hundreds of capabilities would recreate the exact catalogue and configuration burden this program is trying to reduce.

The lower-risk integration is to keep the existing outer harness and expose a named `sbx shell` sandbox as a bounded execution tool (`sbx exec`/copy/status/remove) through one existing skill or MCP wrapper. That preserves the hook/skill bus outside the VM and treats the VM as execution substrate only. Whether `sbx exec` can robustly carry the owner's Windows paths, quoting, long-running output, and clone-mode result handoff is **UNVERIFIED**; the settling experiment is the bake-off in §7.2.

License terms require precision. Docker says the `sbx` CLI is free for personal and commercial work and charges separately for organization governance ([FAQ](https://docs.docker.com/ai/sandboxes/faq/)). Docker Desktop, if required in the chosen Windows deployment, is governed by the Docker Subscription Service Agreement and is free only for personal/education/non-commercial OSS and qualifying small businesses; larger professional/government use requires a paid subscription ([Docker Desktop license](https://docs.docker.com/subscription/desktop-license/)). This unit did not establish an OSI source license for the `sbx` binary; treat it as a proprietary/free-to-use product, not open source.

### 4.3 E2B: excellent product, no demonstrated marginal value here

E2B is a mature Firecracker-style cloud sandbox product with unusually strong persistence. Its docs now support pause/resume of both memory and filesystem, indefinite paused retention, one-second resume, and snapshots that can fork new sandboxes ([persistence](https://e2b.dev/docs/sandbox/persistence), [snapshots](https://e2b.dev/docs/sandbox/snapshots)). SDK v2 secures controller access by default ([secured access](https://e2b.dev/docs/sandbox/secured-access)). It has first-party Claude Code/Codex guides and an MCP gateway ([Claude Code](https://e2b.dev/docs/agents/claude-code), [MCP quickstart](https://e2b.dev/docs/mcp/quickstart)).

Its security default has the same important caveat as Modal: `allow_internet_access` defaults to true, though the API supports blocking all egress and network allow/deny lists ([Python SDK reference](https://e2b.dev/docs/sdk-reference/python-sdk/v2.12.2/sandbox_sync), [create API](https://e2b.dev/docs/api-reference/sandboxes/create-sandbox)). Secure controller transport does not constrain what sandboxed code can exfiltrate.

Maintenance and openness are strong. The main SDK repository is Apache-2.0 and showed a 2026-07-17 release ([E2B repository](https://github.com/e2b-dev/E2B), [license](https://raw.githubusercontent.com/e2b-dev/E2B/main/LICENSE)). The separate Apache-2.0 infrastructure repository supports Terraform deployment to GCP, Azure, AWS Beta, or a general Linux machine and showed release `2026.28` on 2026-07-09 ([E2B Infra](https://github.com/e2b-dev/infra)). Hosted pricing is Hobby free plus usage or Pro at $150/month plus usage; the default public service bills per second ([pricing](https://e2b.dev/pricing)).

E2B's strongest differentiator over Modal is persistent memory-state pause/resume. That feature is **unlikely (20-45%)** to justify another provider here because this harness has no measured requirement for indefinite process-memory continuation, while Modal already supplies filesystem/directory snapshots and a cloud compute path. Evidence: no named E2B use in either corpus field, an existing Modal integration claim, and the anti-overfit bar against durable-execution machinery. If a future task demonstrably needs forkable live process state, a same-task E2B-vs-Modal experiment could revise this conclusion.

Self-hosting E2B fails here even more clearly: Terraform infrastructure, KVM/Firecracker hosts, scheduler/control-plane patching, networking, images, and secrets turn a managed tool into an owned platform. It is **very unlikely (5-20%)** to outperform hosted Modal or local Docker Sandboxes for this single owner after operational cost, based on E2B's own multi-component self-hosting architecture and the absence of a data-residency requirement in the pinned inputs.

### 4.4 Daytona: active hosted product; abandoned open core; poor strategic fit

Daytona's hosted product is active and capable. Its current docs claim per-sandbox dedicated kernel/filesystem/network resources, sub-90ms startup, snapshots, SDKs in five languages, CLI support, and outbound firewall controls (`networkBlockAll`, CIDR, or domains) ([docs](https://www.daytona.io/docs/), [network limits](https://www.daytona.io/docs/en/network-limits/)). It also offers proxy-injected secrets that are not placed in the sandbox ([secrets](https://www.daytona.io/docs/en/secrets/)) and an official agent skill ([agent skills](https://www.daytona.io/docs/en/agent-skills/)).

The licensing/maintenance break is decisive. Daytona's public `daytonaio/daytona` repository states: “This repository is no longer maintained”; as of June 2026 core development moved private and there will be no further updates, fixes, or releases ([repository](https://github.com/daytonaio/daytona)). The frozen public code is AGPL-3.0, whose network-use source provision matters to a modified hosted deployment ([license](https://raw.githubusercontent.com/daytonaio/daytona/main/LICENSE)). The hosted product continues from a closed production codebase ([Daytona announcement](https://www.daytona.io/dotfiles/updates/daytona-is-going-closed-source)). Thus:

- calling Daytona itself “abandoned” would be false;
- calling the public core abandoned by upstream is directly supported by both the repository banner and vendor announcement—two independent first-party signals; and
- self-hosting the frozen core as a security boundary is unacceptable because upstream has promised no fixes.

Daytona's Claude Managed Agents integration explicitly requires the user to run a long-lived orchestrator that watches a work queue and manages one sandbox per session ([Managed Agents guide](https://www.daytona.io/docs/en/guides/claude/claude-managed-agents/)). That exact mode fails the anti-overfit gate by adding a second orchestration runtime and durable session lifecycle. Direct CLI/SDK use would avoid that specific failure, but would still duplicate Modal with no local evidence of a win. Daytona hosted is **unlikely (20-45%)** to add net value here; evidence is the existing Modal surface, zero named Daytona use in two corpus fields, closed-core vendor dependence, and the redundant capability set.

### 4.5 Firecracker, Kata, and gVisor: excellent engines, not harnesses

**Firecracker.** Firecracker is **very likely (80-90%)** the strongest raw microVM building block surveyed for secure multi-tenant Linux execution, based on its minimal device model, seccomp+jailer defense in depth, AWS Lambda/Fargate production use, and regular security releases. It uses Linux KVM and v1.15.1 shipped 2026-04-07 with a CVE fix ([repository](https://github.com/firecracker-microvm/firecracker), [releases](https://github.com/firecracker-microvm/firecracker/releases)). It is Apache-2.0, with some crosvm-originated portions BSD-3-Clause ([FAQ](https://github.com/firecracker-microvm/firecracker/blob/main/FAQ.md)). The remaining uncertainty is comparative rather than factual: no common local benchmark or escape study across every surveyed engine was run.

Firecracker is not secure merely because its binary starts. Its own docs require KVM access, a hardened Linux host, and the jailer or equally restrictive constraints for production ([getting started](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md), [production host setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md)). It has no Windows-native execution or agent/MCP policy plane. Operating it here would mean building the image, snapshot, network, resource, credential, file-transfer, lifecycle, garbage-collection, and patch layer that Modal/E2B/Docker already provide.

**Kata Containers.** Kata is a high-quality Apache-2.0 OCI/CRI runtime that makes containers run in lightweight VMs and integrates with containerd/Kubernetes. Version 3.31.0 released 2026-05-19, and its release stream visibly includes 2026 CVE fixes ([repository](https://github.com/kata-containers/kata-containers), [architecture](https://github.com/kata-containers/kata-containers/blob/main/docs/design/architecture/README.md), [releases](https://github.com/kata-containers/kata-containers/releases)). That is excellent for a Kubernetes operator; it is unnecessary control-plane weight for this personal harness.

**gVisor.** gVisor is an Apache-2.0 application kernel, not a VM. It intercepts the guest System API through the Sentry and minimizes the Sentry's host-kernel surface; systrap is the default platform and KVM is optional. It depends on external cgroups for resource denial-of-service protection and external network policy ([security introduction](https://gvisor.dev/docs/architecture_guide/intro/), [security model](https://gvisor.dev/docs/architecture_guide/security/), [platforms](https://gvisor.dev/docs/architecture_guide/platforms/), [repository](https://github.com/google/gvisor)). The project is active. Only its older ptrace platform is unsupported and expected to be removed; the project itself is not abandoned.

For this owner, gVisor already arrives as part of Modal's managed security boundary. Re-operating it locally adds compatibility and policy work without changing the outer harness.

### 4.6 Adjacent frontier: useful reference points, not adoption targets

**Alibaba OpenSandbox** is the most architecturally relevant open-source newcomer. It is Apache-2.0, has SDKs in five language families, a built-in stdio MCP server, Docker/Kubernetes backends, egress controls, and support for gVisor/Kata/Firecracker ([OpenSandbox repository](https://github.com/alibaba/OpenSandbox)). It therefore passes the interface half of the anti-overfit gate. It fails the minimality/value half here: `opensandbox-server`, exec daemon, ingress, egress, runtime backends, and optionally Kubernetes form a new control plane. With Modal already on the bus and Docker Sandboxes packaging a local microVM, no measured gap justifies that BUILD-LARGE surface.

**Cloudflare Sandbox SDK** became GA on 2026-04-13. Each sandbox runs in its own VM and exposes command/file/process APIs, snapshots, PTYs, tunnels, and code interpreters ([GA announcement](https://developers.cloudflare.com/changelog/post/2026-04-13-containers-sandbox-ga/), [security](https://developers.cloudflare.com/sandbox/concepts/security/)). It is not a drop-in remote shell: its architecture requires a Worker, Durable Object, and Container ([architecture](https://developers.cloudflare.com/sandbox/concepts/architecture/)). It also removed/deprecated HTTP, WebSocket, desktop, and port-exposure features in June/July 2026 ([deprecation notice](https://developers.cloudflare.com/changelog/post/2026-06-09-deprecating-sandbox-sdk-features/)), showing meaningful early-life API churn. Billing spans Workers, Durable Objects, containers, and optional logs ([pricing](https://developers.cloudflare.com/sandbox/platform/pricing/)). Adopting it would be a new application/runtime, not a small bus adapter.

**CodeSandbox SDK** supplies managed VM sandboxes and persistent developer environments, but its current Scale plan starts at $170/month and no unique local control was found that beats Modal or Docker Sandboxes for this owner ([CodeSandbox pricing](https://codesandbox.io/pricing)). It remains active after joining Together AI; it is not abandoned.

## 5. Anti-overfit gate

## 6. Recommendations

### Recommendation 1 — **UNVERIFIED** repair and harden the existing Modal MCP rung

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Repair the cloud-hub cold-start path, then add one explicit `untrusted` create preset to the existing Modal wrapper. The preset must:

- use `block_network=True` unless a bounded domain/CIDR list is supplied;
- reject secrets, environment credentials, Volumes, network filesystems, and cloud bucket mounts by default;
- set CPU, memory, disk, wall-time, and idle-time bounds;
- forbid GPU unless the caller explicitly acknowledges billable execution;
- emit the sandbox ID, effective policy, resource ceiling, expiry, and cleanup status in a compact receipt;
- terminate on failure and expose idempotent status/terminate operations; and
- avoid transparent rerouting: an agent/user must choose the remote billable rung.

This recommendation inherits **UNVERIFIED** because the current wrapper signature and cold-start defect were verified only by audit C14, not from source available on this node. The settling Windows experiment is: (1) cold-launch the configured cloud-hub interpreter with `--print-plan`; (2) inspect the live MCP schema for create/exec/status/terminate; (3) create one CPU-only, no-secret sandbox with network blocked; (4) independently prove both a denied public egress request and a known-allowed loopback operation; (5) prove no mounts/secrets in the create receipt; and (6) terminate and confirm absence through both `Sandbox.list()` and the wrapper's status result.

This is **very likely (80-90%)** to be the highest-value sandbox change here. Evidence: it fixes the only locally claimed remote-sandbox bus, uses Modal's current native controls, and avoids another provider/control plane. The remaining 10-20% uncertainty is live Windows wrapper/account behavior and whether the implementation remains under the BUILD-SMALL bound.

### Recommendation 2 — **UNVERIFIED** expose the same proven Modal surface to Codex

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

After Recommendation 1's smoke passes, register the already-running cloud-hub endpoint for Codex rather than build a Codex-specific sandbox implementation. Restrict discovery to the small sandbox subset (`create_untrusted`, exec, file transfer, status, terminate, cost estimate) instead of all 41 Modal tools; this avoids adding catalogue tax to a harness that already activates only 78 of roughly 355 skills.

This recommendation inherits **UNVERIFIED** because C14's claim that Modal is Claude-only and absent from Codex was not re-probed against the full Windows configs. The settling experiment is two independent schema probes—Claude and Codex—against the same server build/hash, followed by the same no-network smoke in both clients. It is **likely (55-80%)** to reduce provider drift, based on a shared MCP endpoint and identical tool semantics; uncertainty comes from Codex MCP configuration/credential behavior and the current cloud-hub deployment model.

### Recommendation 3 — **UNVERIFIED** run a Docker Sandboxes execution-lane bake-off; do not migrate the whole harness

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Prototype one skill/wrapper that keeps Claude/Codex on the host and uses a named `sbx shell` sandbox only for bounded execution. The wrapper should cover create-in-clone-mode, exec with argv rather than shell interpolation, copy/fetch result, status, and remove. It should use local default-deny policy, host-proxied credentials only when necessary, and the existing `longrun` bus for operations over 60 seconds. Do not repack the full user-level harness into the VM during this experiment.

The proposal is **UNVERIFIED** because `sbx` availability, Windows 11 compatibility on this exact machine, nested virtualization, WSL/Docker conflicts, path mapping, and performance have not been tested. The experiment in §7.2 settles it. Adoption is **roughly even (45-55%)** after accounting for both its strong security design and the harness-continuity risk. Evidence favoring it: dedicated microVM, deny-default egress, proxy credentials, private Docker, Windows distribution, and current releases. Evidence against it: no user-level harness inheritance, a new proprietary CLI/daemon, direct-mode workspace risk, and the owner's prior microVM deferral.

### Recommendation 4 — do not add E2B or Daytona now

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Do not register either provider merely because an SDK/MCP exists. An addition should require a held-out task class where it beats hardened Modal on success rate, isolation policy, total elapsed time, and cost by a predeclared margin. E2B's plausible qualifying class is forkable memory-state continuation; Daytona currently has no unique qualifying class found here.

It is **likely (55-80%)** that adding either now would create provider and catalogue tax without task-value gain. Evidence: zero named use in two controlled corpus fields, overlapping exec/files/snapshot/network features, an existing Modal bus claim, E2B's separate billing/control plane, and Daytona's closed production core. This is reversible: a future measured task need can reopen the decision.

### Recommendation 5 — do not self-host a microVM/control plane

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Reject self-hosted Firecracker, Kata, E2B Infra, and OpenSandbox for the present harness. This recommendation deliberately names BUILD-LARGE because those choices require new daemons/runtime ownership. None supplies a measured capability unavailable from Modal or Docker Sandboxes, and each moves security-critical patching and network/credential correctness onto the owner.

It is **very likely (80-90%)** that self-hosting would be net-negative here. Evidence: Firecracker's own production-host/jailer obligations, Kata's containerd/Kubernetes orientation, E2B's Terraform infrastructure, OpenSandbox's server/execd/ingress/egress components, the Windows host, and the pre-existing Modal surface. A future legal data-locality mandate or provider outage SLO could justify re-evaluation; neither appears in the pinned inputs.

### Recommendation 6 — **UNVERIFIED** canary Modal VM Sandboxes only for workloads that gVisor cannot run

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Once the standard Modal rung is healthy, expose the Beta `vm_runtime` option only as a named canary for Docker-in-Docker, loop devices, kernel-dependent tooling, or other workloads that fail under gVisor. Do not make it the default and do not claim a stronger security boundary until Modal documents the VM threat model in enough detail for comparison.

This recommendation is **UNVERIFIED** because the Beta VM runtime has not been exercised through the local wrapper, and the public page does not name the hypervisor or give a detailed boundary analysis. The settling experiment is a paired standard-gVisor vs VM run of one Docker-dependent task, checking functionality, egress denial, secret absence, cleanup, elapsed time, and cost. It is **likely (55-80%)** that the option will eliminate a narrow class of gVisor incompatibilities because Modal explicitly positions it for Docker and full-kernel behavior; it is **unlikely (20-45%)** to justify default use while Beta, based on its missing GPU/memory-snapshot support and unspecified security implementation.

## 7. Experiments and acceptance gates

### 7.1 Modal repair acceptance gate

Use a credential-free image and a task that needs no public network. Record both the wrapper receipt and an independent Modal SDK/account listing.

Required assertions:

1. cold start succeeds from a new client process, not an old resident hub;
2. the detector proves a known-present tool (`create_untrusted`) before reporting any missing tool;
3. create returns an ID and effective network/resource/expiry policy;
4. public HTTPS and raw TCP both fail, while an in-sandbox loopback operation succeeds;
5. environment contains no owner API keys and no unexpected mounted paths;
6. CPU/memory/time limits are observed;
7. exec returns argv-safe stdout/stderr/exit code without `sh -c` unless explicitly requested;
8. failure triggers termination;
9. terminate is idempotent; and
10. both wrapper status and independent SDK listing agree that the sandbox ended.

Do not infer “terminated” from one status field. The two mechanically independent completion signals are wrapper status and Modal SDK/account listing.

### 7.2 Docker Sandboxes bake-off

Run five representative, non-secret tasks in three lanes: current native sandbox, repaired Modal gVisor, and Docker `sbx shell --clone`. Use the same repository snapshot and task instructions. Candidate tasks:

- dependency install + unit test;
- Docker build and test;
- malicious repository containing `.claude`, `.codex`, `AGENTS.md`, Git hooks, and package lifecycle scripts;
- attempted host-path read/write outside workspace; and
- attempted egress to one allowed and one denied endpoint.

Measure:

- task success and deterministic test result;
- cold/warm elapsed time;
- tool-call/error count;
- host filesystem diff including `.git/hooks`, not just `git diff`;
- network decision log and independent endpoint receipt;
- secret visibility inside the VM;
- cleanup agreement between `sbx ls --json` and process/VM state;
- disk left behind after removal; and
- operator steps and new persistent components.

Predeclare the adoption rule: Docker must pass all containment assertions, preserve result handoff, and improve at least one high-value task class without requiring a second agent/orchestration runtime. A performance win alone does not override a failed containment or harness-continuity assertion.

### 7.3 Alternative-provider admission gate

E2B or Daytona may enter only when a task requires a feature hardened Modal and Docker cannot supply. Run the same task 20 times per provider with fixed images and network policy, then compare completion rate, p95 start+exec latency, cleanup failures, policy violations, operator effort, and total billed cost. Twenty runs are not enough for a universal reliability claim, but they are enough to reject a provider that cannot pass basic smoke and cleanup consistently.

## 10. Final decision record

1. **Keep Modal as the remote sandbox provider.** Harden and prove its existing MCP path before expanding.
2. **Do not add a provider merely for feature parity.** E2B and Daytona have no measured local task win.
3. **Evaluate Docker Sandboxes as a narrow local execution lane, not a replacement harness.** Its controls are frontier-quality; its failure to inherit user-level harness configuration is the central risk.
4. **Use Modal's Beta VM runtime only as a canary for gVisor-incompatible tasks.** Do not infer undocumented security properties.
5. **Do not own Firecracker/Kata/gVisor/OpenSandbox infrastructure.** These are excellent foundations for vendors and platform teams, not the minimal personal harness.
6. **Never adopt Daytona's frozen AGPL core as a security boundary.** Hosted Daytona is active, but it still lacks a marginal case here.

The radical option was considered: replace the host execution model with Docker's local microVM product. Evidence does not yet support full replacement because that move drops the user-level hook/skill/config plane by design. The ambitious evidence-backed move is therefore a measured two-rung architecture—existing harness outside, hardened Modal remote execution, and a narrowly tested Docker microVM lane—rather than another orchestration stack.
