# D007 — HARNESS-BENCH: what public agent benchmarks measure, what a personal harness needs, and what to reuse

**Unit:** D007, `bench: existing-benchmarks`  
**Date researched:** 2026-07-19  
**Subject access:** read-only. This unit wrote only this artifact.  
**Scope boundary:** survey SWE-bench, Terminal-Bench, and successors; identify transfer and non-transfer to this owner's personal harness; specify a benchmark design that can run this week. The neighboring lifecycle-evaluation unit already designed low-level dispatcher/ledger traces; I cite rather than recreate that work.

## Executive verdict

The best answer is **not** “run SWE-bench” and not “build a grand unified eval platform.” Public suites are useful external thermometers for a model-plus-scaffold, but none is a release test for this personal harness. They mostly grade an end state in an artificial repository, container, database, or desktop. This owner needs the harness itself tested: routing around a dead MCP; recovery from real tool failures; Windows and PowerShell correctness; hook precision and benign utility; skill selection; owner-correction retention; compaction/resume; cross-provider parity; cost; and repeated reliability. The pinned corpus directly shows why: `StructuredOutput` failed 846/3,694 calls (22.9%), a dead Tavily extraction route failed 137/532 calls (25.75%), `Glob`'s `ENAMETOOLONG` fingerprint occurred 592 times, and read-before-write failures occurred 939 times (`/local_disk0/codexwork/bundle/inputs/corpus.json:103-108,175-180,4299-4318,8964-9006`). Public coding success can stay flat while every one of those harness pathologies improves—or rise while owner experience gets worse.

The recommended design is a **small, versioned Personal Harness Challenge Set** running through the existing `/eval` + dispatcher + event-ledger bus, with three layers:

1. deterministic lifecycle/guard traces already scoped by audit D10;
2. paired, model-in-loop personal work tasks derived from corpus failure and owner-correction families;
3. a tiny, explicitly non-gating public calibration slice.

The reusable frontier ideas are task manifests, isolated state, executable final-state verifiers, oracle/no-op/mutation validation, milestones plus minefields, paired with/without treatment trials, `pass^k` reliability, benign-utility/security separation, continuous drift checks, and versioned trajectories. The runtime should remain the existing bus. Harbor's task anatomy is worth copying; Harbor itself is a second orchestration/evaluation runtime and should not become the harness core.

**Confidence:** **very likely (80-90%)** that this layered design will produce a more decision-relevant harness regression signal than any single public suite. Evidence: the owner's measured failures are harness-specific (`corpus.json` lines cited above); SWE-bench's own successor audits expose substantial oracle defects; Terminal-Bench 2.1 changed 28/89 tasks; and public suites do not exercise this harness's hooks or owner corrections. The settling experiment is the preregistered two-revision A/B described in §8: current harness versus one known behavior-changing patch on identical cases, models, budgets, and graders. If the local suite detects the intended change without unrelated regressions while a five-task public slice does not, the premise is confirmed.

## 2. SWE-bench family: what it measures, and the limits now demonstrated

### 2.1 SWE-bench, Lite, and Verified

The original SWE-bench contains 2,294 problems from resolved GitHub issues and pull requests in 12 popular Python repositories. The agent receives the pre-fix repository and issue description, edits the repository, and is graded by fail-to-pass tests plus pass-to-pass regression tests. It therefore measures repository navigation, issue comprehension, code modification, test use, and patch correctness under a prepared environment—not generic coding in isolation. Sources: https://arxiv.org/abs/2310.06770 and the official schema at https://www.swebench.com/SWE-bench/guides/datasets/.

SWE-bench Verified reduced the set to 500 examples reviewed by professional developers; OpenAI says three experts independently reviewed each candidate during the 2024 curation. That materially improved the original, but did not make it a timeless oracle: https://openai.com/index/introducing-swe-bench-verified/.

In February 2026 OpenAI reported two severe current limits:

- In 138 hard, repeatedly audited Verified tasks, at least 59.4% had material test/design or description problems capable of rejecting functionally correct solutions.
- All frontier models tested showed some task-specific contamination signal, unsurprising for public historical repositories and fixes.

Source: https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/.

**What to reuse:** the immutable base commit, hidden fail-to-pass plus pass-to-pass tests, clean container, patch artifact, and task-level result. For this owner, the analogous unit is “fresh copied state + hidden behavioral verifier + forbidden deltas,” not “did the agent say it succeeded?”

**What not to infer:** a SWE-bench improvement does not establish hook precision, Windows shell correctness, research quality, skill routing, cross-session continuity, tool-provider resilience, owner preference adherence, or safety/utility balance. It also cannot isolate model from harness unless model, prompt, tools, budget, retries, and environment are fixed.

### 2.2 SWE-Bench Pro

SWE-Bench Pro expanded toward long-horizon enterprise-like work: 1,865 problems over 41 repositories, public/held-out/commercial partitions, multi-file changes, and tasks described as hours to days of professional work. Source: https://arxiv.org/abs/2509.16941.

This is directionally closer to a personal developer harness than classic SWE-bench because it includes larger features and held-out repositories. But the newest available audit is decisive. On July 8, 2026, OpenAI reported 200/730-ish tasks flagged by its datapoint pipeline (27.4%) and 249 (34.1%) identified in human annotation, concluding roughly 30% are broken. Failure classes were overly strict tests, underspecified prompts, low-coverage tests, and misleading prompts. Source: https://openai.com/index/separating-signal-from-noise-coding-evaluations/.

**Conclusion:** use Pro only as a noisy external calibration with task-level inspection, never as this harness's promotion gate. A score delta can be task-oracle movement rather than harness movement.

## 3. Terminal-Bench, Harbor, and terminal successors

### 3.1 Terminal-Bench 1.x → 2.0 → 2.1

Terminal-Bench evaluates agents that operate a real terminal to complete end-to-end tasks such as compiling code, configuring servers, processing data, and training models. Each task has an English instruction, environment, test script, and oracle solution. The original repository describes a dataset plus a harness connecting an agent to a terminal sandbox: https://github.com/laude-institute/terminal-bench.

Terminal-Bench 2.0 increased difficulty and manual/LM-assisted verification, and moved execution to Harbor: https://www.tbench.ai/news/announcement-2-0. Terminal-Bench 2.1 is the stronger lesson for this owner. It fixed 28 of 89 tasks because of external drift, resource mismatches, and misspecification and added continuous validation. Representative score changes included Claude Code/Opus 4.6 rising from 58.0% to 70.1%—12.1 points—from benchmark repair, not agent improvement. Source: https://www.tbench.ai/news/terminal-bench-2-1.

This is more general than SWE-bench and directly stresses shell planning, environment manipulation, tool recovery, and end-to-end verification. It is the closest public ancestor of a personal terminal harness bench.

It still misses:

- Windows host semantics in the actual owner environment unless tasks explicitly target Windows containers;
- provider-native hooks, skills, MCP catalog, permissions, compaction, and shared ledger;
- long-lived personal state and owner preferences;
- real interactive approval/correction cost;
- benign false blocks and advisory spam;
- whether the harness picked a dead tool despite a healthy alternative.

### 3.2 Harbor: reuse the contract, not the runtime

Harbor is now a general evaluation/RL environment framework. Its current task format supplies exactly the good parts to copy:

- `instruction.md`;
- `task.toml` with timeouts, resources, OS, network policy, and metadata;
- isolated `environment/`;
- optional oracle `solution/solve.sh` or Windows `solve.bat`;
- `tests/test.sh` or `test.bat` writing a numeric reward;
- separate verifier environments;
- logs and trajectories;
- custom dataset metrics.

Sources: https://www.harborframework.com/docs/tasks, https://www.harborframework.com/docs/datasets/metrics, and Windows support at https://www.harborframework.com/docs/tasks/windows-container-support.

Harbor can run Terminal-Bench 2.1 immediately after installation; its official smoke test is:

```text
harbor run -d terminal-bench/terminal-bench-2-1 -a oracle -l 5
```

and its agent form accepts built-in Claude Code or a custom agent import path: https://www.tbench.ai/docs/run-terminal-bench-2-1.

That does **not** make Harbor the right installed core here. It is a second orchestration/evaluation runtime, one of the explicitly rejected anti-overfit components. Adopting its daemon/cloud/RL features would duplicate the existing dispatcher/ledger and add dependencies, caching, images, and failure modes.

**Rejected proposal — install Harbor as the canonical personal evaluator.**  
**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**  
This violates the anti-overfit gate by adding a second runtime. It is also unnecessary: the existing bus already has a test path, dispatcher, and ledger according to audit D10/E02. If a one-off Terminal-Bench calibration is desired later, run Harbor outside the deployed harness and import only a signed summary; do not put it on the critical path.

## 4. Adjacent benchmarks that fill the important gaps

No single successor spans personal harness quality. The following supply mechanics, not a ready-made answer.

### 4.1 SkillsBench and SWE-Skills-Bench: marginal value of installed skills

SkillsBench 1.1 currently lists 87 real engineering tasks with deterministic verifiers, up to three trials, and paired with-skills/without-skills results across Claude Code, Codex, Gemini CLI, and OpenHands. The public leaderboard explicitly reports both conditions and confidence intervals: https://www.skillsbench.ai/; paper: https://arxiv.org/abs/2602.12670.

That paired design is essential here because only 78 of roughly 355 installed skills were invoked in the pinned measurement. Raw skill count or invocation count is not value. A skill earns promotion only if the same model/harness/task does better with it than without it, including routing negatives where it must stay silent.

SWE-Skills-Bench goes closer to coding and reports that specialized skills can help or hurt when guidance is mismatched to project versions: https://arxiv.org/abs/2603.15401. Its main transferable lesson is to grade *incremental skill utility*, not skill package quality in the abstract.

### 4.2 τ-bench → τ²/τ³: state, policy, conversation, reliability

τ-bench simulates a user conversing with a tool agent under domain policy and grades final database state, not wording. It introduced `pass^k`: the fraction of tasks that succeed in all `k` repeated trials, distinct from pass@k (“at least one succeeds”). Source: https://arxiv.org/abs/2406.12045.

τ² adds dual control: the user also acts with tools in the shared world, so the agent must guide and coordinate rather than monopolize execution. It uses compositional task generation and fine-grained reasoning versus communication ablations: https://arxiv.org/abs/2506.07982.

The official repository now directs evaluators to τ³, which fixes 75+ tasks and adds banking knowledge retrieval and voice while retaining airline/retail/telecom domains: https://github.com/sierra-research/tau2-bench. The very fact that 75+ task fixes were needed reinforces continuous oracle validation.

Transfer here: grade final state; preserve flexible valid trajectories; run critical cases three times and report `pass^3`; include cases where the owner must perform or authorize a step; keep policy adherence separate from task success.

### 4.3 ToolSandbox: milestones and minefields

ToolSandbox evaluates stateful conversational tool use with implicit dependencies, a user simulator, and dynamic grading of intermediate/final milestones across arbitrary valid trajectories: https://machinelearning.apple.com/research/toolsandbox-stateful-conversational-llm-benchmark.

This is the right answer to “the agent can solve a task many ways.” A local grader should not demand one golden tool sequence. It should require milestones (e.g., proved dead route, selected healthy route, wrote expected artifact) and forbid minefields (e.g., claimed absence before known-positive control, mutated live state, leaked a secret, retried the identical failing call beyond budget).

### 4.4 AgentDojo: security and benign utility must be paired

AgentDojo combines normal user tasks with indirect prompt injection tasks and reports utility, utility under attack, and attack success/security separately: https://arxiv.org/abs/2406.13352 and https://agentdojo.spylab.ai/.

This directly maps to live defect D1. A guard that blocks attacks but also flags prose descriptions or successful JSON is not “safer”; it has destroyed benign utility and can corrupt downstream reasoning. Every malicious or dangerous fixture needs a semantically matched benign mention/negation/false-valued-field control.

### 4.5 GAIA/GAIA2, OSWorld, and LongMemEval

- **GAIA** has 466 human-simple but tool-heavy questions spanning web browsing, multimodal inputs, reasoning, and files, with exact answers and a held-out leaderboard. It is useful for general research/tool calibration but is final-answer centric and static. https://arxiv.org/abs/2311.12983 and https://huggingface.co/gaia-benchmark.
- **Gaia2**, covered above, adds asynchronous environments and write-action verification.
- **OSWorld** supplies reproducible setup/evaluation for 369 real desktop tasks across Ubuntu, Windows, and macOS; OSWorld 2.0 expands long-horizon realism. https://osworld-v1.xlang.ai/ and https://arxiv.org/abs/2606.29537.
- **LongMemEval** separately tests extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention. It is valuable taxonomy for memory, but a synthetic chat-history score does not establish recall of this owner's repository decisions, aliases, compaction boundaries, or correction style. https://proceedings.iclr.cc/paper_files/paper/2025/hash/d813d324dbf0598bbdc9c8e79740ed01-Abstract-Conference.html.

## 6. What the Personal Harness Challenge Set must measure

### 6.1 Outcome vector—never one vanity number

Each run should publish this vector, with raw numerators/denominators:

1. **Task success:** deterministic final-state reward on first attempt.
2. **Critical reliability:** `pass^3`, all three clean-state repeats successful, for guards, persistence, and recovery.
3. **Recovery:** same-fingerprint fail → behaviorally successful alternative or corrected retry within budget.
4. **Benign utility:** matched near-miss task completes without false block/advisory corruption.
5. **Attack/unsafe-effect rate:** forbidden side effect occurred / attack cases.
6. **Skill marginal utility:** paired with-skill minus without-skill success; invocation precision/recall on routing positives and negatives.
7. **Owner burden:** approval requests, corrections, repeated questions, and manual rescue steps per successful task.
8. **Efficiency:** wall time, model tokens/cost, tool calls, retries, and injected context bytes per successful task.
9. **Grounding integrity:** unsupported “fact” count and known-positive-control compliance.
10. **Benchmark health:** oracle pass rate, no-op rejection, mutation kill rate, invalid/infrastructure rate, and drift status.

Do not average security, utility, success, and cost into one number. A weighted average permits a catastrophic block or leak to be hidden by cheap easy wins. Macro-average task families only as a navigation aid and always show the vector.

### 6.2 Case families derived from real owner evidence

The first version should be 24 cases—small enough to author and inspect in a week, broad enough to expose the dominant harness pathologies:

| Family | Cases | Concrete first fixtures | Oracle |
|---|---:|---|---|
| **R: route/recover** | 4 | dead Tavily route with healthy search alternative; WebFetch refusal then alternate source; transient tool timeout; same error repeated twice requiring strategy change | expected final artifact + selected route; minefield on dead-route third call |
| **S: schema/structured output** | 3 | missing required field repair; fan-out partial result aggregation; one invalid child without discarding valid siblings | schema + content assertions; partial-invalid count |
| **P: path/shell/platform** | 4 | orphan-inflated plugin lookup without long argv; Bash unmatched quote; PowerShell `.cmd` discovery via `Get-Command`; safe git revision with forward slashes and `--` | command exit + exact filesystem state + command-shape minefields |
| **W: read/write/edit** | 2 | edit unseen file requiring read; concurrent unrelated user edit that must be preserved | target diff only; forbidden unrelated diff |
| **G: guard precision** | 4 | destructive verb true positive; Markdown merely mentioning it; negated marker; JSON field name containing failure token with false value and `ok:true` | block true execution; allow three benign controls; downstream use of successful result |
| **V: verification integrity** | 2 | detector returns zero but known-positive exists; orchestrator supplies false constraint with/without probe ID | known-positive check occurs; unsupported fact is challenged, not propagated |
| **K: skill routing/value** | 2 | one task where a selected high-use skill helps; one close negative where it must not invoke | paired deterministic task outcome + invocation decision |
| **M: memory/continuity** | 2 | compact between discovery and edit; new session must honor a superseding owner correction | final state + cited source decision; stale decision is a minefield |
| **C: coordination** | 1 | two independent evidence slices, deduplicated integration, no false “done” from subtask completion | both unique required findings + no duplication/contradiction |

These case counts are a v0.1 engineering allocation, not an empirically optimal weighting.

**Confidence:** **likely (55-80%)** that 24 cases will catch the highest-damage harness regressions while remaining runnable this week. Evidence: every family maps either to a ranked corpus failure or a confirmed live defect, and deterministic fixtures can reuse the existing test/dispatcher boundary identified in audit D10. **UNVERIFIED** whether the two skill and two memory cases can obtain stable deterministic end-state graders in one week; the settling experiment is to prototype one of each on day 1 and demote them to `provisional` if oracle/no-op/mutation validation fails.

### 6.3 Case contract, borrowed from the frontier

Each case should be a directory or manifest entry with:

```yaml
id: G-03-negated-marker
suite_version: phcs-v0.1
family: guard_precision
owner_evidence:
  - INPUT-known-harness-defects.md:9-28
profile: interactive
provider: [claude, codex]
initial_state_fixture: sha256:...
instruction: instruction.md
budget:
  max_wall_sec: 120
  max_tool_calls: 12
  max_cost_usd: 1.00
faults: []
milestones:
  - artifact_written
  - terminal_success_record
minefields:
  - false_block
  - unrelated_mutation
verifier:
  command: test.ps1
  revision: sha256:...
oracle:
  command: solve.ps1
trials: 3
```

This copies Harbor's explicit instruction/environment/solution/tests discipline, SWE-bench's base/test hashes, ToolSandbox's milestones/minefields, τ-bench's repeats, and AgentDojo's paired controls without importing their runtimes.

### 6.4 Benchmark admission gates

A case cannot affect promotion until all of these pass:

1. **Oracle succeeds** from a fresh isolated state three times.
2. **No-op fails** deterministically.
3. **Malformed or known-bad candidate fails** for the intended reason.
4. **At least one alternative valid trajectory succeeds** when multiple approaches are legitimate.
5. **Verifier mutation check:** remove/invert one required assertion and demonstrate the meta-test catches the weakened grader; seed one intended defect and ensure it is killed.
6. **Known-present detector control:** the grader proves it can find a seeded success and a seeded failure before interpreting zero findings.
7. **No hidden live dependencies** unless the task is explicitly a drift canary; network allowlist and captured versions are part of the manifest.
8. **Independent review of new critical cases:** one author, one blinded reviewer, or two mechanically independent signals where the claim is absence/broken/done.
9. **Expiry/revalidation date** and owner-evidence reference.

Terminal-Bench's 28/89 repair and SWE-Bench Pro's roughly 30% broken estimate make these gates first-class product requirements, not benchmark housekeeping.

## 9. Experimental design details that prevent self-deception

### 9.1 Control model/harness confounding

To compare harness revisions, fix model, provider, reasoning mode, system/project rules, skills available, tools, MCP health fixture, budget, retries, environment, and grader. To compare models, fix the harness. To compare a skill, change only skill availability. Never compare a new model+new harness to an old model+old harness and attribute the delta to either.

### 9.2 Use paired tasks and randomized order

Run the identical case under A and B. Randomize order to reduce provider-time and cache effects. Start from fresh fixture hashes. Record invalid runs rather than silently retrying until success. A deployment that actually retries may report pass@k; reliability reports `pass^k`.

### 9.3 Separate infrastructure failures

Container build failure, provider outage, rate limit before agent action, missing fixture, verifier crash, and task drift are `INVALID/INFRA`, not task failures. But harness failure to recover from a *deliberately injected and in-contract* timeout is a scored failure. The manifest must distinguish ambient infrastructure from experimental fault.

### 9.4 Avoid trajectory overfit

Grade required/forbidden state and actions, not a single sequence. Search, direct read, or a skill helper may all be valid. Over-specific tool-order tests recreate the SWE-bench “correct solution rejected” pathology.

### 9.5 Keep hidden tests actually hidden

Store verifiers outside agent-visible task state; expose requirements, not expected implementation. Salt task variants and rotate owner-derived nouns/paths. Public benchmark canaries are insufficient for a local model that may have read prior trajectories. Record whether the agent could access gold patches, tests, or prior results.

### 9.6 Grow from escaped defects, retire stale cases

Every real escaped regression becomes a minimized case with a provenance pointer. Every case has a revalidation date. Remove or repair cases whose oracle no longer passes, whose requirement changed, or whose outcome no longer matters to the owner. Preserve retired manifests for historical score interpretation.
