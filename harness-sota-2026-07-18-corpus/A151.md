## Executive verdict

The single verified silent override is the force-push policy. The behavior contract permits a force-push to `main`/`master` after explicit user approval and does not prohibit force-pushing another branch. The active settings register a blocking Bash hook whose predicate ignores both branch and approval and exits 2 for every command matching literal `git push ... -f|--force`, including `--force-with-lease`. In the collision, the hook wins before Bash runs. The apparently load-bearing contract qualification “to main/master without explicit user approval” is therefore dead text on Claude for the command forms the hook recognizes.

Confidence: **almost certain (90-99%)**, based on (1) complete settings and contract reads; (2) direct predicate execution; (3) a separate end-to-end execution of the actual hook process with positive and negative controls; (4) implementation tracing from the registered command to exit 2; and (5) the earlier Windows audit’s independent end-to-end hook probes (`inputs/audit-findings/F05.md:24-30`). The residual 1-10% is the remote-node limitation: this unit could not start the owner’s Windows Claude Code process, so it could not observe the native host dispatch the hook in a new live session.

The four declarative credential-read denies are also ineffective while `defaultMode` is `bypassPermissions`, according to Claude Code’s current native permission-mode contract. That is genuine settings-on-settings dead text, but it is **not counted as a settings-versus-behavior-contract conflict**: the prose contract never says ordinary credential-file reads must always be mechanically denied, and a permission bypass does not itself command the model to violate the fetched-content rule. Treating an enforcement gap as a deterministic instruction collision would overclaim.

## 2. Finding F1 — the active force-push hook silently overrides the contract’s branch and approval conditions

Severity: high coherence defect; narrow command-recognition coverage.  
Proposal tag: **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.

### 2.1 Both texts, verbatim

**Settings side — active registration** (`/local_disk0/codexwork/bundle/claude/settings.json:151-160`):

```json
{
  "matcher": "Bash",
  "hooks": [
    {
      "type": "command",
      "command": "python \"C:/Users/Prekzursil/.claude/hooks/no-force-push/hook.py\"",
      "timeout": 8,
      "statusMessage": "no-force-push: protect remote history"
    }
  ]
}
```

**Contract side — conditional prohibition** (`/local_disk0/codexwork/bundle/claude/AGENTS.md:93-98`):

```markdown
## 9. Security non-negotiables (all tools) — ALWAYS ON

- Never hardcode secrets; use environment variables and validate presence at startup.
- Never `--no-verify` on commits without explicit user instruction.
- Never `git push --force` to main/master without explicit user approval.
- Validate all user inputs at system boundaries; sanitize before HTML output.
```

The contract’s own precedence list also says, verbatim, `1. The user's explicit in-session instruction and the permission system.` at `/local_disk0/codexwork/bundle/claude/AGENTS.md:121`, above the security floor at line 122. This reinforces that explicit approval is intended to be operationally meaningful rather than decorative.

The registered implementation supplies the decisive semantics. `/local_disk0/codexwork/bundle/claude/hooks/no-force-push/tripwire.py:15-18` says:

```python
KIND = "command"
FIELD = "tool_input.command"
ACTION = "Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1."
_PATTERN = re.compile("git\\s+push\\b[^\\n]*(--force\\b|-f\\b)", re.IGNORECASE)
```

`tripwire.py:39-47` returns `True` solely from that regex. It does not inspect the destination branch, transcript, permission decision, or an approval artifact. `/local_disk0/codexwork/bundle/claude/hooks/no-force-push/hook.py:45-56` parses the hook payload, calls that predicate, writes the reason, and returns exit 2 on a match.

### 2.2 Concrete collision

Situation A: the owner explicitly says, “Force-push my rewritten `feature/a151` branch,” and Claude proposes:

```text
git push --force origin feature/a151
```

The contract permits this: it is not `main` or `master`, and it has explicit approval. The hook blocks it.

Situation B: the owner explicitly approves rewriting `main` after reviewing the exact command. The contract’s `without explicit user approval` condition is now false, so the prohibition no longer applies. The hook still blocks it because approval is not an input to the predicate.

This is not merely hypothetical regex reasoning. I executed the pure predicate and separately the registered hook process from the unpacked snapshot with bytecode writes disabled:

```text
git push --force origin feature/a151 => (True, 'Tripwire: refusing ...')
git push origin feature/a151 => (False, '')
git push --force-with-lease origin main => (True, 'Tripwire: refusing ...')

actual hook process:
approved_feature_exit=2
ordinary_feature_exit=0
```

The positive and negative cases validate that the detector distinguishes ordinary push from forced push. The earlier Windows audit gives a mechanically independent host-side signal: `/local_disk0/codexwork/bundle/inputs/audit-findings/F05.md:24-30` records end-to-end stdin probes returning exit 2 for both `git push --force origin main` and `git push --force-with-lease origin main`.

### 2.3 Which side wins at runtime

**The settings-registered hook wins.** Claude Code’s official hook contract says PreToolUse exit code 2 blocks the tool call; see [Hooks reference — Exit code 2 behavior per event](https://code.claude.com/docs/en/hooks#exit-code-2-behavior-per-event). The hook returns 2 before Bash executes (`hook.py:52-56`). Thus the model cannot realize the behavior allowed by the Markdown contract for recognized command forms.

Multiple-hook precedence does not rescue the contract: Claude’s current hook reference states that the most restrictive PreToolUse decision wins (`deny > defer > ask > allow`) and a matching blocking hook cancels the call; see [PreToolUse decision control](https://code.claude.com/docs/en/hooks#pretooluse-decision-control). No model-side interpretation of `AGENTS.md` can override an exit-2 cancellation after the model has emitted the command.

The hook’s stated escape hatch is also silently misleading for a normal retry. I tested the obvious interpretation:

```text
tool_input.command = "FORGE_NO_FORCE_PUSH_OFF=1 git push --force origin feature/a151"
inline_optout_exit=2
```

The inline assignment belongs to the not-yet-executed Bash command, so it is not in the separately spawned hook process environment. Only launching the hook process itself with `FORGE_NO_FORCE_PUSH_OFF=1` returned 0. Therefore “If approved, re-run with `FORGE_NO_FORCE_PUSH_OFF=1`” does not describe a usable same-session command retry.

### 2.4 Minimal edit that resolves it

The strict minimum by line count is this one-line contract edit — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. Replace `AGENTS.md:97` with:

```markdown
- Claude's gate unconditionally blocks literal `git push` commands containing `-f` or `--force` (including `--force-with-lease`) on every branch; in-session approval does not override it. The owner must set `FORGE_NO_FORCE_PUSH_OFF=1` in Claude's process environment before session launch to opt out.
```

That edit resolves the silent contradiction immediately by making the contract describe the actual predicate and usable opt-out boundary. I do **not** recommend it as the final policy: it discards the contract’s deliberate approval and protected-branch semantics and still leaves alternate Git spellings uncovered.

Recommended minimal coherent fix — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**:

1. Keep the existing PreToolUse registration at `settings.json:151-160`.
2. Change `tripwire.py` so it blocks only a forced update whose resolved destination is `main` or `master` **and** lacks a native, session-bound approval fact.
3. Obtain that approval through an existing hook event (PermissionRequest/UserPromptSubmit) and store a one-shot, command-fingerprint approval scoped to `session_id`; consume it on the matching PreToolUse. Do not infer approval from prose with a regex, and do not accept a self-authored inline environment variable.
4. Add four regression cases: unapproved main blocks; approved identical main command passes once; approved feature force-push passes; a modified command cannot reuse approval.

This remains on the existing hook bus and needs no second runtime, database, critic, or observability service. It passes the anti-overfit gate and reintroduces none of the rejected components.

The one-shot approval design is **very likely (80-90%)** to resolve the semantic collision, because the current hook payload already carries session-scoped event data in Claude’s documented schema and the hook bus supports permission decisions. **UNVERIFIED:** whether the owner’s installed Claude Code 2.1.214 exposes the exact approval/command fingerprint needed to this particular user hook without another adapter. The settling experiment is a read-only schema capture of one PermissionRequest and its subsequent PreToolUse in a disposable repository, followed by a replay test showing the same `session_id` and stable normalized command. Until that experiment passes, do not implement the state handoff.

If the schema experiment fails, the minimal truthful fallback is **CONFIG (settings/JSON only)**: remove the standalone hook entry and use native `auto` mode plus a narrowly scoped `ask` permission rule for force-push commands. This fallback is **likely (55-80%)** to preserve the intended approval flow, based on Claude’s documented auto-mode conversation boundaries and permission rules, and on the earlier live audit claim that the installed build exposes auto mode (`inputs/audit-findings/D23.md:3-12`). **UNVERIFIED:** exact Windows rule matching for all Git spellings and whether this account currently satisfies auto-mode eligibility. The settling experiment is `claude auto-mode defaults`, `/permissions` inspection, and side-effect-free attempts against a local bare test remote. Because broad shell allow rules are treated specially in auto mode, this fallback must not be promoted from documentation alone.
