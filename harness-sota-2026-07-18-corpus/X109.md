# X109 — Cross-domain borrow: reliability engineering → agent memory

## Scope and method

This unit asks one question: what has reliability engineering already solved that can help an agent decide what to remember across sessions, when to forget it, and how to notice that a memory has become stale? Per the unit brief, this is an ideation lens. I did **not** inspect or characterize the local harness, corpus, audit, or subject tree. “Current miss” below therefore means a failure class that a conventional append/retrieve/update/delete memory design misses, not a claim that a particular local component has that defect.

Evidence is restricted to cited external primary or institutional sources. Design claims are separated from facts. Confidence words use the mandated bands. `UNVERIFIED` appears at the exact premise it qualifies and names a settling experiment.

## Executive result

The borrow transfers, but only as a **qualitative control method**, not as a literal lifetime model.

The useful mechanism is a three-part package:

1. **Reliability-Centered Maintenance (RCM):** define the function and functional failures; classify the consequence; then deliberately choose condition-directed maintenance, time-directed maintenance, failure-finding/proof testing, redesign, or run-to-failure. The key idea is not “maintain everything periodically”; it is “spend maintenance where failure consequences justify it.” NASA explicitly says failure frequency alone is too simplistic to select tasks and that a task must be evaluated against the consequence it prevents ([NASA RCM Guide, §4.1.4](https://www.nasa.gov/wp-content/uploads/2023/02/nasa_rcmguide.pdf)). NASA also defines RCM task outcomes as time-directed, condition-directed, failure-finding, or a conscious run-to-failure decision, and requires each task to be applicable and effective ([NASA Lesson 891](https://llis.nasa.gov/lesson/891)).
2. **FMECA plus fault trees:** analyze memory records bottom-up by failure mode, but analyze harmful behavior top-down as a top event. NASA describes FMEA as bottom-up analysis of how a component can fail and how the effect propagates ([NASA Software FMEA guidance](https://swehb.nasa.gov/spaces/SWEHBVD/pages/140640400/8.5%2B-%2BSW%2BFailure%2BModes%2Band%2BEffects%2BAnalysis)); its active FMECA handbook treats the analysis as a living risk document updated as design, operation, and knowledge change ([GSFC-HDBK-8004](https://standards.nasa.gov/standard/GSFC/GSFC-HDBK-8004)). NASA’s fault-tree handbook defines minimal cut sets as the smallest combinations of basic events sufficient for the top event and uses them to enumerate distinct failure paths ([NASA Fault Tree Handbook, §§3.8 and A.2](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).
3. **Common-cause failure (CCF) discipline:** do not count two checks as independent if they share the same stale source, extraction model, cache, clock, or upstream event. NRC practice increases the modeled common-cause probability when an observed deficiency could affect every member of a redundant component group ([NUREG-2225](https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr2225/index)). NRC’s diversity work distinguishes different technologies, different approaches within one technology, and different architectures within one technology ([NUREG/CR-7007](https://www.nrc.gov/reading-rm/doc-collections/nuregs/contract/cr7007/index)).

The package maps to an agent-memory **maintenance policy attached to each durable assertion**, with risk-based revalidation, explicit invalidation conditions, proof tests for hidden failures, and a common-cause ledger for validators. It is **very likely (80-90%)** to reduce harmful use of stale high-consequence memories, because it moves validation to the point where consequences and dependency paths are known; the evidence is the direct structural match between latent component failure and latent assertion invalidity, plus the newly reported agent-memory gap between retrieving an update and acting on it. The 2026 STALE paper’s authors report that their best evaluated system achieved only 55.2% overall on state resolution, premise resistance, and downstream adaptation ([STALE](https://arxiv.org/abs/2605.06527)). That empirical result is not independent replication.

It is **unlikely (20-45%)** that generic TTLs, MTBF estimates, or a “memory health score” derived from age would improve this problem reliably, because semantic facts do not share the physical wear assumptions behind an age-dependent hazard rate; the evidence is NASA’s own distinction among multiple age/failure patterns and its warning that aggregate failure frequency does not select a maintenance task ([NASA RCM Guide, §§4.1.4–4.1.5](https://www.nasa.gov/wp-content/uploads/2023/02/nasa_rcmguide.pdf)). Those literal imports should be rejected.

## 1. What the source field actually does

### 1.1 RCM starts from function and consequence, not component age

Reliability engineering distinguishes a component’s physical existence from its required function. A pump can still run and yet have functionally failed if it no longer supplies required flow; NASA’s RCM guide uses this exact distinction ([NASA RCM Guide, §4.1.3](https://www.nasa.gov/wp-content/uploads/2023/02/nasa_rcmguide.pdf)). The analysis asks:

- What function must be preserved?
- In what ways can that function fail?
- What are the consequences?
- Is there a detectable degradation interval or condition?
- Is a proactive task applicable and effective?
- If not, is redesign, redundancy, or conscious acceptance preferable?

This yields different policies for different assets. Condition-directed work monitors evidence of degradation. Time-directed work is reserved for a credible age relationship. Failure-finding tests expose a hidden failure that would otherwise become visible only when a protective function is demanded. Run-to-failure is a deliberate economic/safety decision, not neglect. NASA describes RCM as an integrated mix of proactive and reactive strategies and warns that unnecessary maintenance can itself introduce failures ([NASA NPR 8831.2E, Chapter 7](https://nodis3.gsfc.nasa.gov/displayAll.cfm?Internal_ID=N_PR_8831_002E_&page_name=all)).

That last point matters. Testing is not free: the NRC records cases where test and maintenance downtime accounted for a substantial share of unavailability, so optimizing intervals could mean **less** frequent invasive testing when test-induced unavailability dominated ([NRC Item B-61](https://www.nrc.gov/sr0933/0167_0005_item_b-61_allowable_eccs_equipment_outage_periods_%28rev._1%29.html)). The transferable principle is therefore an inspection-cost/risk tradeoff, not “validate every memory every session.”

### 1.2 FMECA and fault trees cover opposite directions

FMECA is inductive and bottom-up: for each item, list recognizable failure modes, local effects, higher-level effects, existing detection, and compensation. Fault-tree analysis is deductive and top-down: name one unacceptable outcome, then decompose the combinations that can produce it. They are complementary.

For a top event `unsafe action justified by invalid durable memory`, a small qualitative tree could be:

```text
TOP: agent performs a consequential action using invalid durable memory
  AND
  ├─ invalid assertion reaches the decision context
  │    OR
  │    ├─ old assertion remains ACTIVE after an invalidating event
  │    ├─ newer evidence exists but retrieval ranks the old assertion
  │    └─ user/query premise reactivates a superseded assertion
  ├─ action path treats the assertion as authoritative
  └─ every applicable barrier fails
       OR
       ├─ no revalidation policy exists
       ├─ validator repeats the same common source
       ├─ validation failure is silently treated as validation success
       └─ conflict is retrieved but not propagated to the action
```

The value is the cut set, not the diagram. If `old assertion remains ACTIVE` plus `no revalidation policy` plus `consequential action` is a minimal path to harm, the design can break that path at the cheapest barrier. If `validator` and `memory writer` both depend on the same cached API result, adding a second LLM judgment does not break the path.

Fault trees have an important limitation even in their home field: the undesired event and its contributors must first be foreseen. NASA calls these presumptions the primary limitation ([NASA NPR 8621.1 appendix on FTA](https://nodis3.gsfc.nasa.gov/displayCA.cfm?Internal_ID=N_PR_8621_0001_&page_name=AppdxI35)). A memory design must therefore feed observed surprises back into the tree rather than treating the initial taxonomy as complete.

### 1.3 Common-cause failure separates redundancy from diversity

Two identical pumps protect against one random pump failure; they may not protect against contaminated shared fuel. Two validators that both ask the same model to inspect the same retrieved passage protect against some sampling error; they do not protect against a stale passage, incorrect system clock, shared extraction bug, or misleading user premise.

The IAEA describes diversity as using different physical variables, principles, technologies, logic, or actuation methods, while cautioning that apparent diversity may conceal common materials, processes, principles, or support systems ([IAEA Safety of Nuclear Power Plants: Design, Appendix II](https://www-pub.iaea.org/MTCD/Publications/PDF/Pub1099_scr.pdf)). The NRC similarly treats a deficiency affecting one redundant component as evidence that the common-cause group may be at higher risk ([NUREG-2225](https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr2225/index)).

The memory translation is precise: every “independent” freshness signal needs a dependency signature, such as source authority, origin event, transport, cache, timestamp authority, extraction code/model, and adjudicator. Checks sharing a critical dependency belong to one common-cause group.

## 2. Structural transfer test

### What matches

| Reliability structure | Memory structure | Why the mapping is real |
|---|---|---|
| Component has a required function | Durable assertion exists to guide a future decision | Correctness is relative to intended use, not mere retrievability |
| Latent failure remains hidden until demand | Stale memory looks normal until a relevant task retrieves it | Ordinary operation may supply no failure signal |
| Degradation indicator precedes functional failure | Invalidation event, source change, contradiction, or scope drift precedes harmful use | A condition-directed check can act before the demand |
| Protective component needs proof testing | Infrequently used critical memory needs an on-demand source check | “No observed error” is not evidence of validity when unused |
| Maintenance can introduce failure and downtime | Rewriting/summarizing/revalidating can corrupt provenance, cost tokens, or block work | More maintenance is not monotonically better |
| Redundant identical channels share CCF | Multiple agents/checks share model, source, cache, or prompt assumptions | Count of checks overstates independence |
| Critical item list focuses controls | High-consequence memory class focuses validation budget | Uniform treatment wastes budget and misses consequences |

The qualitative transfer is **very likely (80-90%)** sound. Evidence: both systems contain latent state, a future demand, nonzero inspection cost, consequence variation, and dependency-correlated detectors. The claim is bounded to control logic; it does not include numerical failure prediction.

### What does not match

1. **Semantic invalidity is often externally caused.** Hardware wear evolves in the component; a memory can become false because the world changes while the stored bytes remain perfect. “Age” is at most a proxy for exposure to change.
2. **Truth is scoped and partly normative.** “Owner prefers concise answers” can be context-dependent, revocable, or ambiguous. It is not equivalent to a bearing being above a vibration threshold.
3. **Demand changes validity.** A rough location can be adequate for restaurant suggestions and inadequate for emergency dispatch. The same record can be functionally valid for one use and failed for another.
4. **Observations are not independent components.** Many web pages copy one source; two memories can be paraphrases of one session; two model reviewers can share training and prompt-induced blind spots.
5. **Repair is not always deletion.** A superseded assertion may remain important evidence about what was believed, promised, or authorized at an earlier time.
6. **Failure distributions are nonstationary.** Tool versions, projects, owners, and environments change. A global MTBF can mix incomparable regimes.

Therefore the following literal imports fail:

- **Reject memory MTBF as a per-record expiry rule.** Mean time to invalidity averages away relation type, environment, and consequence. It is **very unlikely (5-20%)** to set defensible expiry intervals without per-class stationarity data; evidence is the disanalogy above and NASA’s warning that failure frequency is insufficient to select maintenance tasks ([NASA RCM Guide](https://www.nasa.gov/wp-content/uploads/2023/02/nasa_rcmguide.pdf)).
- **Reject the bathtub curve as a universal memory-aging curve.** A birth date, a historical decision, a current API endpoint, and a user preference have different temporal semantics. It is **almost certainly not (1-5%)** valid as one shared curve; evidence is that even physical complex assets display several conditional-failure patterns rather than one universal pattern ([NASA RCM Guide, Figure 4-5](https://www.nasa.gov/wp-content/uploads/2023/02/nasa_rcmguide.pdf)).
- **Reject naive RPN arithmetic.** Multiplying ordinal severity, occurrence, and detectability scores creates false numerical precision. Use ordered consequence classes and explicit decision rules unless calibrated outcome data exists.
- **Reject “two LLM votes = redundancy.”** It is **very likely (80-90%)** that same-model, same-context votes retain important common causes; evidence is the shared dependency structure and the source field’s insistence on diversity attributes, not merely channel count ([NUREG/CR-7007](https://www.nrc.gov/reading-rm/doc-collections/nuregs/contract/cr7007/index)).

## 3. Concrete harness translation

### Proposal A — UNVERIFIED: Memory assurance envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Attach an assurance envelope to each durable assertion, stored beside the assertion in the existing memory format rather than in a new database:

```yaml
memory_id: stable-id
assertion: "..."
kind: observation | preference | authorization | environment | procedure | historical
scope: project/user/machine/task constraints
source_ref: immutable event or document pointer
source_class: owner-direct | authoritative-system | derived | inferred
observed_at: timestamp
valid_from: timestamp-or-null
valid_to: timestamp-or-null
status: active | suspect | superseded | quarantined | retired
invalidators: [owner-revokes, project-switch, version-change, conflicting-authority]
consequence: critical | high | medium | low
volatility: event-driven | condition-driven | stable-history | unknown
proof_test: source/tool/question used to re-establish validity
validator_dependencies: [origin, transport, cache, extractor, adjudicator]
last_validated_at: timestamp-or-null
supersedes: [memory-id]
```

The write hook need only require a few fields for high-consequence durable memories and may default low-consequence observations to a cheap policy. Retrieval remains the existing mechanism; the hook alters eligibility and labels, not semantic search infrastructure.

It is **likely (55-80%)** that this envelope can be implemented under the `BUILD-SMALL` ceiling if the current memory bus already permits metadata and pre-use hooks; evidence is the small schema and deterministic policy, but that bus capability is **UNVERIFIED — experiment E0, “bus-fit spike,” would add one synthetic record with metadata, intercept one retrieval, and measure changed eligibility without modifying the store**. Because this premise is unverified, the proposal inherits `UNVERIFIED` in its heading.

What it catches that raw text plus timestamp misses:

- an old fact whose age is harmless because it is historical;
- a young fact already invalidated by a version change;
- a preference that applies only to one project;
- an inference presented later as owner-provided fact;
- a superseded record retrieved without its successor;
- a critical record whose only validator shares the writer’s source and cache.

### Proposal B — RCM decision table for remembering and forgetting

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Use explicit policies, not a global TTL:

| Memory class | Consequence if wrong | Maintenance mode | Retrieval behavior | Forgetting behavior |
|---|---:|---|---|---|
| Authorization, credentials state, destructive-operation target, legal/financial/medical constraint | critical | proof-test at every consequential use against owner or authoritative system | block or ask if not verified | quarantine from use; preserve audit pointer unless deletion policy requires erasure |
| Tool/API/project environment fact | high/medium | condition-directed on version/config/repo/environment event; proof-test when context changed | retrieve with source and validation state | supersede old active value; retain compact tombstone |
| Owner preference | medium | event-driven on correction; contextual confirmation when scope changes | show scope; premise resistance if query assumes old preference | demote/supersede, do not erase history by default |
| Learned procedure/lesson | medium | validate on outcome; raise suspicion after failure or distribution shift | retrieve with applicability predicates | retire from default retrieval after repeated non-applicability; retain evidence pointer |
| Historical event/decision | varies | no age maintenance; integrity/provenance check | retrieve by event time, not “current truth” | retain according to audit/privacy policy |
| Ephemeral task detail | low | run-to-failure / session-bound | exclude after task boundary | expire physically if no audit/privacy reason to retain |

This is the most important answer to “when to forget.” Reliability engineering says preservation of function, not preservation of every component, is the objective. For memory, “forget” should be split into four operations:

1. **Stop serving** — remove from default retrieval.
2. **Supersede** — preserve temporal evidence but mark a successor authoritative.
3. **Quarantine** — preserve for inspection while preventing action.
4. **Erase** — physically delete because retention is unauthorized or no longer useful.

Conflating those operations makes either safety or privacy lose. The recommended default is supersession/quarantine for operational invalidity and physical deletion for an explicit retention/privacy rule. It is **likely (55-80%)** that this separation reduces both stale-action errors and accidental loss of provenance; evidence is the source-field distinction between loss of function and physical state plus current memory research reporting that append-only temporal histories and temporal filtering are useful. For example, APEX-MEM’s authors describe append-only temporal evolution with query-time conflict resolution ([APEX-MEM](https://aclanthology.org/2026.acl-long.749/)). The magnitude is **UNVERIFIED — experiment E2, “forgetting-semantics ablation,” would compare delete-only versus four-state lifecycle on stale-answer rate, audit reconstruction, privacy-deletion completion, and retrieval cost**.

### Proposal C — UNVERIFIED: Proof test at the point of consequential use

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Before an action uses a `critical` or context-changed `high` memory, execute the stored proof test:

1. Resolve the exact assertion and intended use.
2. Obtain a fresh signal from the authority named in the envelope.
3. Compare the authority’s current value and scope with the stored assertion.
4. If confirmed, update `last_validated_at` and use it.
5. If contradicted, mark suspect/superseded and propagate the conflict to dependent memories.
6. If unreachable, return “unknown/unverified”; never turn validation failure into validity.

This is failure-finding maintenance: a rarely demanded safety function can be failed silently, so it is exercised before reliance. It differs from periodic refresh because demand and consequence determine whether the cost is justified.

It is **very likely (80-90%)** to catch “retrieved the new state but acted on the old premise” when the authority is available and the assertion is machine-checkable; evidence is that the barrier is placed immediately before action, after retrieval and premise formation. It is only **roughly even (45-55%)** for implicit, normative, or commonsense invalidations, because the comparison itself may require fallible interpretation; evidence is the STALE benchmark’s implicit-conflict category and reported gap between updated evidence and behavior ([STALE](https://arxiv.org/abs/2605.06527)).

### Proposal D — Common-cause ledger and validator diversity rule

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Define independence mechanically. A second signal counts as diverse only when it differs on a dependency relevant to the hypothesized failure:

| Suspected failure | Signal 1 | Signal 2 that is actually diverse | Fake diversity |
|---|---|---|---|
| Stored version is stale | memory record | live package/tool version | another summary of the same record |
| Owner preference changed | old session | current owner confirmation | another model interpreting the old session |
| Source page changed | cached extraction | fresh authoritative page with cache bypass | second retriever over same cache |
| Extractor corrupted a value | extracted assertion | raw immutable source span/hash | another agent reading extracted assertion |
| Clock/time anchor wrong | host timestamp | authoritative event/version identifier | second process using same host clock |
| Claimed capability absent | validated detector with known-positive control | independent registry/file/runtime signal | rerunning the same detector |

The rule should be fail-closed only for critical actions; lower classes can proceed with a visible uncertainty label. Every validation result records its dependency signature. If two checks share the suspected common cause, the policy counts them as one.

It is **very likely (80-90%)** that this catches false reassurance from same-source multi-agent review; evidence is the exact common-cause structure and institutional diversity guidance cited above. It is **likely (55-80%)** that a small dependency taxonomy is sufficient for most harness checks; this is **UNVERIFIED — experiment E3, “CCF replay,” would label dependencies in 100 historical validation episodes, then test whether the taxonomy predicts pairs that fail together better than raw validator count**.

### Proposal E — Qualitative memory fault trees for a short critical-item list

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Do not build a general fault-tree engine. Maintain five to ten top events as review templates, for example:

- consequential action uses superseded authorization;
- agent discloses information after retention/consent state changed;
- project-specific instruction leaks into another project;
- failed procedure is replayed because similarity outranks applicability;
- correction is stored but not propagated to derived memories;
- all validators agree because they share one stale source.

For each top event, write qualitative AND/OR paths and identify single-point cut sets. Feed actual incidents and near misses back into the templates. NASA’s 2024 FMECA guidance explicitly characterizes FMECA as a living document updated with operational and knowledge changes ([GSFC-HDBK-8004](https://standards.nasa.gov/standard/GSFC/GSFC-HDBK-8004)).

It is **likely (55-80%)** that this reveals end-to-end gaps which record-level validation misses, because harmful behavior requires a chain from write through retrieval to use and FTA exposes barrier combinations. It is **unlikely (20-45%)** that maintaining exhaustive trees would pay for itself, because the source handbook notes combinatorial growth in large trees and because semantic failure contributors are open-ended ([NASA Fault Tree Handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). Keep the list short and qualitative.

### Proposal F — Living FMECA generated from incidents, not imagined exhaustively

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Seed a small table and update it when a correction, near miss, or stale-memory incident occurs:

| Failure mode | Local effect | End effect | Detection | Compensation |
|---|---|---|---|---|
| Omission | relevant memory unavailable | repeated work or missed constraint | known-item recall probes | reconstruct from authoritative source |
| Commission/staleness | invalid assertion remains active | wrong action | invalidation event, proof test, contradiction | suspect → supersede/quarantine |
| Scope leak | valid assertion applied outside scope | cross-project/user error | scope mismatch at retrieval | require scope predicate |
| Corruption | summary changes meaning/source | false confidence | raw-source comparison/hash | rebuild derived record |
| Conflict non-propagation | parent corrected, derivative unchanged | old policy survives indirectly | dependency traversal | mark descendants suspect |
| Provenance laundering | inference later appears owner-stated | unjustified authority | source-class mismatch | preserve derivation chain |
| Over-retention | memory survives authorization/purpose | privacy or distraction harm | retention sweep against purpose | erase and verify deletion |
| Under-retention | evidence erased with operational value | no audit/reconstruction | tombstone-pointer audit | separate serve state from retention state |
| Common-cause validation | multiple checks share defect | correlated false confirmation | dependency signature | require diverse authority/check |

Do not assign pseudo-precise RPN products. Sort first by consequence class, then by observed recurrence, then by lack of detection. A new observed failure mode updates the taxonomy and relevant fault tree.

It is **likely (55-80%)** that an incident-fed table remains useful with lower overhead than an exhaustive prospective catalogue; evidence is NASA’s living-risk-document model and the anti-overfit constraint, but maintenance cost is **UNVERIFIED — experiment E4, “30-day FMECA upkeep trial,” would measure minutes per new incident, duplicate categories, and number of resulting policy changes**.

## 4. End-to-end operating policy

The proposals combine into one lifecycle:

### On write

1. Store the source pointer and distinguish observed fact, owner statement, inference, and derived procedure.
2. Assign scope, consequence, volatility trigger, and invalidators.
3. For high/critical records, define a proof test and validator dependencies.
4. Link supersession and derivation; never silently overwrite the only provenance.
5. If the assertion is low-value and session-bound, choose run-to-failure/expiry deliberately.

### Between sessions

1. Consume cheap invalidation events already present on the bus: project switch, repo revision, tool/version change, correction, owner revocation, source update.
2. Mark affected records `suspect`; do not eagerly ask an LLM to rewrite every descendant.
3. Run periodic tests only for a class with evidence that age predicts invalidity and the test cost is justified.
4. Sample low-consequence records to estimate failure modes, not to pretend every record is certified.

### On retrieval

1. Filter `retired`, `quarantined`, and out-of-scope records before semantic ranking.
2. Return current assertion together with source class, scope, status, and supersession links.
3. Retrieve conflicts/updates as a set; do not let embedding similarity pick authority.
4. Resist query premises that contradict the active state.

### Before consequential action

1. Identify which durable assertions are load-bearing.
2. Apply the consequence-specific proof test.
3. Require mechanically diverse evidence for claims of absence, breakage, completion, authorization, or irreversible state.
4. On unreachable authority, surface uncertainty and follow the configured fail-open/fail-closed policy.

### After outcome

1. Record whether the memory was useful, inapplicable, contradicted, or harmful.
2. Update failure-mode recurrence and the relevant top-event path.
3. Suspect derivatives when a parent is corrected.
4. Reassess whether the maintenance task itself caused excessive latency, corruption, or false alarms.

This closed loop is **likely (55-80%)** to outperform periodic “memory cleanup” on stale-action rate per validation call, because it targets validation by consequence, condition, and demand rather than uniform age. The evidence is RCM’s task-selection logic and the NRC example showing surveillance itself can add unavailability. The effect size is **UNVERIFIED — experiment E1 below settles it**.

## 5. What this would catch that simpler memory designs miss

1. **Young-but-stale memory.** A package version changes minutes after storage. A 30-day TTL says fresh; the version-change invalidator marks suspect immediately.
2. **Old-but-valid memory.** A historical decision remains true as history years later. A TTL deletes it; functional classification retains it without treating it as current authorization.
3. **Retrieved correction, unchanged behavior.** The update is in context, but the query embeds the old premise. A point-of-use proof test and premise-resistance barrier stop reliance.
4. **Derived-memory zombie.** The owner corrects a parent preference, while a procedure inferred from it remains active. Derivation links propagate suspicion.
5. **False two-signal assurance.** Two agents agree because both read the same cached summary. Dependency signatures classify one common-cause group.
6. **Maintenance-induced corruption.** Repeated consolidation changes meaning. Raw-source comparison detects drift, and RCM treats the rewrite task itself as a possible failure source.
7. **Wrong kind of forgetting.** A stale authorization should stop being served but may need an audit trail; an unauthorized secret may need physical erasure. Four lifecycle operations distinguish these cases.
8. **Silent detector failure.** A validator has not run successfully for months, but no action demands it. A failure-finding probe with a known-positive control exposes the hidden failure.
9. **Scope-dependent truth.** “Use tool X” was valid for one repo and is harmful in another. Scope is checked before ranking.
10. **Validation outage laundered into confidence.** The authority is unreachable. The proof-test state becomes unknown, not success.

## 6. Experiments that decide whether to adopt

### E0 — Bus-fit spike

Purpose: settle whether the existing memory/hook/skill/MCP bus can carry the envelope and enforce retrieval eligibility within `BUILD-SMALL`.

- Add one synthetic assertion with scope, status, invalidator, proof test, and dependency fields.
- Trigger one matching retrieval before and after invalidation.
- Pass only if enforcement changes without a new daemon, database, orchestration runtime, or model training.

### E1 — Risk-based maintenance versus TTL

Create a replay set with at least these transitions: explicit contradiction, implicit invalidation, version change, scope change, authority outage, unchanged historical fact, and query-premise trap. Randomize age independently of validity.

Compare:

- append-only retrieval;
- global TTL;
- newest-wins;
- consequence/condition/demand-based policy;
- the same policy without the point-of-use proof test.

Measure stale-action rate, valid-memory suppression, validation calls, latency, token/tool cost, and recovery after correction. The proposal passes if it materially reduces critical/high stale actions without unacceptable valid-memory suppression and does so with fewer checks than validate-everything. “Materially” must be set before seeing results.

### E2 — Forgetting-semantics ablation

Replay cases requiring supersession, quarantine, historical audit, and actual privacy deletion. Compare hard-delete-only with the four-state lifecycle. Verify physical deletion through two mechanically independent signals: storage enumeration with a known-present control and an attempted retrieval/raw-object lookup.

### E3 — Common-cause replay

Construct validator pairs sharing or differing in source, cache, timestamp authority, extractor, and model. Inject one defect at each layer. Compare raw vote count with dependency-aware independence. Measure correlated false confirmation and extra check cost.

### E4 — Maintenance-induced failure test

Repeatedly summarize, consolidate, and revalidate fixed provenance-rich records. Compare assertion meaning, source attribution, scope, and confidence to the raw source after each cycle. This tests whether the maintenance policy damages the item it is maintaining.

### E5 — Hidden-function proof test

Plant critical memories whose validators silently stop executing or always return a default. Ensure a known-positive control first proves detector sensitivity, then measure time-to-detection with and without scheduled/on-demand failure finding.

Adoption is **likely (55-80%)** warranted if E1 reduces high/critical stale-action rate, E3 reduces correlated false confirmation, and E4 shows bounded maintenance-induced corruption at acceptable cost. This is a forward decision rule, not a result; all three experiments are currently unrun in this unit.

## 7. Anti-overfit gate and alternatives rejected

All retained proposals ride an existing memory/hook/skill/MCP bus and require metadata, deterministic policy, and small review templates. They do **not** introduce a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Rejected alternatives:

- **New memory daemon/service — BUILD-LARGE (new daemon/service/runtime -- needs its own justification): rejected.** The policy does not require one, and a daemon creates its own liveness and consistency failure modes.
- **Vector database or knowledge graph:** rejected by the anti-overfit gate. Supersession and dependency links can be IDs in existing records; scale has not been demonstrated to require graph infrastructure.

## 8. Risks, counterarguments, and boundary conditions

### The schema may become bureaucracy

If every casual memory requires a complete FMECA envelope, agents will either stop writing useful memories or populate meaningless defaults. Mitigation: require full fields only for high/critical durable assertions; infer or omit low-risk metadata; measure write latency and null/default rates. It is **likely (55-80%)** that tiering avoids most overhead, but this is **UNVERIFIED — E0 plus a 100-write usability trial would settle completion time and field quality**.

### “Authoritative source” can still be wrong

Reliability proof tests work because a measurable function exists. Semantic authority may be contradictory, delayed, or compromised. The design must represent “unknown” and source hierarchy, not convert fresh into true. For owner preferences, the owner is the authority; for system state, the live system often outranks remembered dialogue; for historical claims, immutable source evidence may outrank current summaries.

### Invalidation propagation can explode

A broadly scoped parent can mark many descendants suspect. Eager LLM rewriting would be expensive and risky. Use lazy suspicion: record that the dependency changed and adjudicate descendants only when retrieved. It is **likely (55-80%)** to bound routine cost because work is demand-driven; evidence is the explicit lazy algorithm, but workload distribution is **UNVERIFIED — E1 should report descendant fan-out and adjudications per action**.

### Fault trees can give false completeness

A neat tree is not proof that all semantic failure modes are known. This is the most serious analogy risk and is explicitly recognized in NASA’s FTA guidance. Treat trees as incident-fed barrier maps, never as exhaustive truth. Unknown/other must remain a first-class incident category.

### Diversity costs complexity

The IAEA cautions that diversity can add operational, maintenance, and test complexity and may even use lower-reliability equipment ([IAEA design guidance](https://www-pub.iaea.org/MTCD/Publications/PDF/Pub1099_scr.pdf)). Therefore require diverse proof only where the consequence warrants it. Two different sources are not automatically better if one is unauthoritative.

### Privacy may require non-recoverable forgetting

Quarantine and tombstones are not substitutes for deletion when retention is prohibited. The design must let retention/privacy policy override reliability’s instinct to preserve failure evidence. Completion of erasure must use two mechanically independent, validated detectors as specified in E2.

## 9. Final judgment

The cross-domain borrow succeeds in a bounded form:

- Borrow **RCM’s function/consequence/task-selection logic**.
- Borrow **failure-finding proof tests** for latent high-consequence memory invalidity.
- Borrow **FMECA as a living incident-fed taxonomy**, not an exhaustive worksheet.
- Borrow **fault trees/minimal cut sets** as short end-to-end barrier maps.
- Borrow **common-cause groups and real diversity**, not validator counts.
- Do **not** borrow MTBF, a universal age curve, naive RPN arithmetic, or physical-component independence assumptions.

The recommended first move is **very likely (80-90%)** to be the assurance envelope plus a point-of-use proof test for only high/critical memories, because those two changes break the most consequential cut sets while preserving the minimal architecture; evidence is the qualitative fault tree, RCM consequence discipline, and current temporal-memory failure reports. Feasibility in this harness is **UNVERIFIED — E0 “bus-fit spike” must pass before implementation**, and effectiveness is **UNVERIFIED — E1 “risk-based maintenance versus TTL” must beat the preregistered baselines before rollout**.

If E0 requires a new daemon or E1 does not reduce stale consequential actions per unit cost, stop. That negative result would show that the structural analogy is intellectually valid but not operationally valuable in this harness.
