# A023 — coherence audit: rules versus commands / duplicate authority

Date: 2026-07-19  
Subject: unpacked read-only copy of `C:\Users\Prekzursil\.claude` at `/local_disk0/codexwork/bundle/claude`  
Scope: every regular file under `rules/**` and `commands/**`; no subject file was changed

## Executive result

I found **eleven verified conflict families** in which a rule and one or more command definitions independently govern the same runtime decision and have drifted. The highest-risk cluster is cross-vendor dispatch: the unconditional rule requires foreground work units, file-backed prompt transport, and a 30-minute Bash timeout, while the `multi-*` command templates require background work, embed prompts in heredocs, and set a one-hour Bash timeout. These are not hypothetical overlaps: invoking `/multi-plan`, `/multi-execute`, or `/multi-workflow` on a Codex/Gemini task exercises the contradictory instructions in the same turn.

The other verified families are vendor-output trust, model tier selection, the implementation lifecycle, coverage thresholds, review verdicts, Windows CLI detection, checkpoint commit gates, and durable session claims. I found no cross-tree verbatim duplicate line of 25 or more normalized characters; the dangerous duplication is semantic, not copy/paste duplication.

Confidence in the conflict inventory is **almost certain (90-99%)** because (a) all 154 regular files were included in deterministic manifests, hashes, directive extraction, and cross-document similarity comparison; (b) every promoted finding below has opposing literal text and an executable collision case; and (c) absence claims were checked with known-positive controls. The remaining uncertainty is the missing live Windows runtime and missing `codeagent-wrapper`/DevFleet implementations, which I tag inline rather than turning into conclusions.

### Runtime precedence, verified rather than assumed

Claude Code's official memory documentation states that rules are behavioral context, not enforced configuration, and warns that when instructions conflict Claude may choose arbitrarily: <https://code.claude.com/docs/en/memory>. The official skills documentation states that legacy `.claude/commands/*.md` files work as skills and that a skill body is a prompt handed to Claude: <https://code.claude.com/docs/en/slash-commands>. Therefore a loaded rule and an invoked custom command do **not** have a deterministic hard precedence relation. They are simultaneously visible behavioral instructions.

For every advisory conflict below, the verified runtime winner is consequently: **neither is guaranteed to win; Claude may follow either**. This conclusion is **almost certain (90-99%)** because it is stated by the vendor's current documentation. A local A/B execution could not add a second empirical signal because `claude` is not installed on this Linux job node (`claude: command not found`); I do not fabricate a Windows run. The settling experiment for model-specific adherence, if desired, is a temporary-config `/memory` load check followed by repeated contradictory command invocations on the Windows host, recording the expanded prompt and chosen action.

This lack of precedence is itself why duplicate authority is dangerous. The `rules/README.md:93-104` “language-specific overrides common” convention does not resolve rule-versus-command conflicts; official Claude Code documentation does not provide a corresponding command-over-rule or rule-over-command priority.

## Findings

### F1. Background dispatch is simultaneously banned and mandatory

**Confidence: almost certain (90-99%).** Evidence is the literal opposing imperatives and explicit barrier waits in the same command templates.

Rule text, verbatim (`rules/common/cross-vendor-dispatch.md:7-14`):

> ## 1. A work-unit dispatch MUST block. Fire-and-forget is banned.
>
> - NEVER `--background`, `&`, `nohup`, `spawn(detached)`, or `run_in_background` for a dispatch
>   whose result a barrier is waiting on. Foreground is already the DEFAULT in
>   `codex-companion.mjs:788` (it backgrounds only `if (options.background)`).
> - NEVER return a job id, a `"started in the background as task-…"` string, or a
>   `"Check /codex:status"` receipt as a work-unit result.

Command texts, verbatim:

* `commands/multi-plan.md:11-15`: “`**Mandatory Parallel**: Codex/Gemini calls MUST use \`run_in_background: true\` (including single model calls, to avoid blocking main thread)`”. Its concrete template sets `run_in_background: true` at line 33, and lines 51-60 wait on `TaskOutput`.
* `commands/multi-execute.md:21-35`: “`**Call Syntax** (parallel: use \`run_in_background: true\`):`” and the template contains “`run_in_background: true,`”. The same directive occurs in the second prototype and audit calls at lines 49 and 74.
* `commands/multi-workflow.md:34-48`: “`**Call syntax** (parallel: \`run_in_background: true\`, sequential: \`false\`):`” and “`run_in_background: true,`”. Lines 81-92 explicitly wait for all results via `TaskOutput`.

Concrete collision: `/multi-plan` launches Codex and Gemini analysis that the phase-2 fan-in must consume. The command says the dispatch **MUST** background; the unconditional rule says the very same barrier-bound dispatch must **NEVER** background.

Runtime winner: neither is guaranteed, per the verified runtime model above. If the command wins, the ledger-proven lost-result class described at `cross-vendor-dispatch.md:3-17` is re-enabled. If the rule wins, the command's “mandatory parallel” protocol is violated but results remain reachable.

Minimal edit: make `cross-vendor-dispatch.md` the single authority. In `multi-plan`, `multi-execute`, and `multi-workflow`, replace background calls with foreground calls (`run_in_background: false`) and delete their `TaskOutput` job-ID fan-in instructions. If parallelism is later required, parallelize native Claude subagents, each of which performs one foreground external dispatch; do not background the external work unit itself. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This edit is **very likely (80-90%)** to remove the contradiction because every explicit `run_in_background: true` authority in the five-file comparison is in those three commands; the remaining uncertainty is whether a referenced role skill injects background execution dynamically, settled by one expanded-prompt trace.
