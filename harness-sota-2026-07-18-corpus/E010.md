# E010 — Ecosystem survey: evaluation and tracing SaaS (and why we rejected them)

Date: 2026-07-19 UTC  
Unit: E010  
Scope: evaluation/tracing products, their current status and licensing, and whether any should be adopted in this owner's Claude/Codex harness.

## Executive verdict

Do **not** adopt an evaluation or tracing SaaS for this harness. This is not a claim that the category is poor. Braintrust, LangSmith, Langfuse, Arize Phoenix, and W&B Weave are the strongest general-purpose products in the surveyed set; Opik, Laminar, HoneyHive, Galileo, Patronus, Parea, and Helicone are credible active alternatives with different emphases. The rejection is architectural and owner-specific: a hosted trace/eval control plane is exactly the previously rejected **observability SaaS**, while a self-hosted edition still adds a second trace database, ingestion service, UI, retention system, and operational lifecycle beside a harness that already has a dispatcher, ledger, hook events, tests, and an `/eval` workflow.

It is **very likely (80-90%)**, based on the existing normalized hook schema, ledger append points, native Claude Code OpenTelemetry export, Codex runtime-metrics flag, and local `/eval` contract cited below, that the useful 80% of this category can ride the existing hook/test/ledger bus with a small amount of local work. The remaining uncertainty is runtime coverage: this read-only unit did not execute Claude or Codex with a disposable collector, so cross-provider field completeness is **UNVERIFIED; experiment E1 (one sanitized synthetic session per provider, exported into a temporary directory and joined by episode ID) would settle it**.

The concrete adoption package is therefore:

1. enable redacted native telemetry on demand, locally;
2. add an episode/case/trial correlation envelope to the existing ledger;
3. make the existing `/eval` convention executable with deterministic outcome graders first;
4. retain raw/model-content capture as opt-in and short-lived;
5. use OTLP as an interchange boundary, not a reason to buy or self-host a platform;
6. reconsider SaaS only if a future multi-person organization demonstrates collaboration, retention, annotation, or compliance needs that the local bus cannot meet.

No subject files were changed. The only write is this artifact.

## 2. What the category contains

The market has converged on five overlapping layers:

1. **Capture:** decorators, provider wrappers, proxies, or OpenTelemetry/OpenInference spans collect prompts, completions, tool calls, timing, tokens, costs, errors, and parent/child relationships.
2. **Trace store and UI:** searchable span trees, sessions/threads, flame graphs, dashboards, and annotations.
3. **Offline evaluation:** versioned datasets, tasks, repeated experiments, code scorers, model judges, human review, and comparisons.
4. **Online evaluation:** sampling and asynchronous scoring of production traces, alerts, drift/error monitoring, and promotion of failures into datasets.
5. **Control plane:** prompt registries/playgrounds, release gates, gateways, guardrails, optimization agents, or production routing.

Layer 5 is where scope expansion becomes dangerous here. Helicone adds an AI gateway; Galileo advertises real-time protection; Patronus includes guardrails and proprietary evaluator models; Opik includes prompt optimization; Braintrust now advertises an optimization agent. Those may be valuable for product teams, but adopting them here would expand from evidence capture into routing, enforcement, or another agent runtime. That violates the anti-overfit boundary even more directly than a trace store alone.

## 5. Why the category is attractive—and why that is still insufficient here

### 5.1 What the best products get right

The frontier pattern is consistent across Braintrust, Langfuse, Phoenix, HoneyHive, and Weave:

- a trial is a first-class trace, not an undifferentiated collection of tool logs;
- input, expected outcome, configuration, model, dataset revision, scorer revision, costs, latency, and outputs are comparable across experiments;
- code, model, and human scores coexist rather than collapsing into one judge;
- production failures can be promoted into a regression dataset;
- trace/session/thread hierarchy preserves parent-child context;
- standards-based ingestion and export reduce instrumentation lock-in.

Anthropic's current agent-evaluation guide independently supports the substance: tasks contain repeated trials, complete trajectories and environment outcomes; code-based graders should be preferred where possible; LLM judges need human calibration; pass@k and pass^k answer different questions; and graders should usually evaluate outcomes rather than brittle exact tool paths ([Anthropic, “Demystifying evals for AI agents”](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

These ideas are worth adopting. Their hosted implementation is not.

### 5.2 The local system already owns the irreplaceable parts

The value of an eval system is not its span viewer. It is the owner's task bank, success criteria, deterministic oracles, baselines, failure taxonomy, and promotion decisions. The local harness already owns:

- cross-provider lifecycle normalization (`hook-event.schema.json:7-54`);
- tool-result verification receipts (`modules.py:1048-1077`);
- task/turn/subagent lifecycle points (`modules.py:1218-1275`);
- elapsed time and terminal result capture (`dispatcher.py:485-513`);
- capability vs regression vocabulary and pass metrics (`commands/eval.md:21-31,72-96`);
- provider-native metrics capability (`config.toml:82-90` for Codex and Claude's documented native OTel export).

The missing pieces are identifiers, outcome events, a versioned case manifest, deterministic execution, and aggregation. None requires a SaaS.

### 5.3 SaaS would not fix the measured failures

A trace platform may show that Tavily returned “not connected,” that a schema retry loop repeated, or that a shell command hit quoting failure. It cannot remove the dead MCP registration, relax an over-strict schema, shorten Windows plugin command lines, or correct quoting. Those fixes belong at MCP/config/schema/command-generation boundaries. Paying to retain prettier evidence of known failures is not the highest-leverage intervention.

It is **very likely (80-90%)**, based on the failure modes supplied in the brief and the product functions documented above, that SaaS adoption alone would not materially reduce those error rates. This is a causal fit judgment, not an A/B result; **UNVERIFIED experiment E6 (instrument a fixed failure-repair suite with and without a candidate platform and measure repair success, time, retries, tokens, and new endpoint failures) would settle the incremental benefit**.

### 5.4 New failure and privacy surfaces

Native Claude telemetry documents that prompt content, tool arguments, and tool content are disabled by default; raw API bodies can include the entire conversation; and full tool content requires explicit opt-in ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)). This harness routinely touches source code, commands, MCP arguments, research content, and potentially credentials. A hosted trace store therefore creates a new sensitive-data destination and retention contract.

Self-hosting does not make the complexity disappear. Helicone explicitly lists at least web, worker, API/collector, Supabase, ClickHouse, and object storage in its self-host design ([Helicone repository](https://github.com/Helicone/helicone)); Langfuse describes web/worker, S3-first ingestion, caching, and persistence ([Langfuse self-hosting](https://langfuse.com/self-hosting)); Phoenix documents Docker/Kubernetes deployment ([Phoenix overview](https://arize.com/docs/phoenix)). Those are new services to patch, back up, migrate, monitor, and reconcile with the existing ledger.

## 6. Anti-overfit gate: explicit disposition

The mandated gate says a find counts only if it rides the existing hook/skill/MCP bus and does not reintroduce a second orchestration runtime, vector/KG memory, durable execution engine, trained critic, observability SaaS, or guardrail framework.

## 7. Proposals that pass the gate

### 7.1 UNVERIFIED — on-demand native Claude OTel capture to a temporary local sink

**NATIVE (Claude Code already does this; we just enable it)**

Claude Code can export standard metrics and log events through OTel and optional beta traces through OTLP; documented controls leave prompts, tool details, and tool content off by default ([monitoring docs](https://code.claude.com/docs/en/monitoring-usage)). Start with metrics and event logs only, console or a temporary local OTLP receiver, during explicit benchmark runs. Do not turn on raw API bodies. Do not make export a hot-path dependency for normal interactive sessions.

This is **very likely (80-90%)** to provide enough Claude-side timing, tool, error, and session evidence for benchmark diagnosis because the official schema includes identity, tool results, hooks, costs, and timing. Interactive trace allowlisting and cross-provider joinability are **UNVERIFIED; experiment E1 settles them**. If tracing is unavailable, metrics/events plus the existing hook ledger remain useful.

### 7.2 Add privacy-safe episode correlation to the existing event bus

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add an additive correlation envelope, generated by the eval launcher and propagated through available hook fields:

`episode_id`, `suite_rev`, `case_id`, `trial`, `provider`, `model_id`, `reasoning_profile`, `harness_rev`, `grader_rev`, `parent_episode_id`, and `privacy_profile`.

Persist hashed session/actor IDs where raw IDs are not required. Add these to task/turn/tool/terminal result rows without copying prompt or tool content. The need is directly visible: source receives session/agent identity but current persisted task/turn/subagent and terminal rows omit it (`modules.py:1218-1275`; `dispatcher.py:485-513`).

It is **very likely (80-90%)** that this stays below roughly 200 lines because it is an additive schema/adapter/append-field change across existing seams, based on the compact source points cited. Exact change size is **UNVERIFIED; experiment E2 (dry-run patch in a copied tree with tests and `git diff --stat`) would settle the tag before implementation**. If it exceeds 200 lines because both provider adapters need invasive propagation, reclassify rather than hiding the scope.

### 7.3 Make `/eval` executable with deterministic-first cases

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Keep `/eval define/check/report`, but back it with a versioned JSON/JSONL manifest and one thin runner that:

- creates a temporary state root;
- runs a case for one or more trials;
- captures the existing ledger/terminal artifacts;
- applies code/state graders;
- emits `eval_start` and `eval_result` rows;
- reports pass@1, pass@k only when retries are an actual policy, pass^k for reliability, latency, tool calls, retries, and invalid/missing episodes;
- never upgrades model-judge output into a release blocker without human calibration.

The current Markdown command already names the user-facing workflow and metrics (`commands/eval.md:1-119`), so this is implementation behind an existing interface, not a new evaluation framework.

It is **likely (55-80%)** that a minimal v1 runner fits under 200 lines if cases call existing pytest/dispatcher fixtures and aggregation remains simple. This size is **UNVERIFIED; experiment E3 (three-case vertical slice: deterministic lifecycle, known Bash quoting failure, dead-MCP preflight) would settle it**. A full stochastic fleet benchmark is not v1.

### 7.4 Redaction and retention profile for telemetry

**CONFIG (settings/JSON only)**

Define an explicit `benchmark-minimal` profile: no prompt bodies, no tool content, no raw API bodies, hashed actor/session IDs, temporary local destination, bounded retention, and deletion after aggregate/report creation. Define a separate, manually approved `debug-content` profile for a single disposable case with synthetic secrets only.

This is **almost certain (90-99%)** to reduce disclosure risk relative to defaulting content capture on, because Claude's documentation enumerates exactly which flags reveal prompts, tool details, tool content, and complete API bodies ([monitoring docs](https://code.claude.com/docs/en/monitoring-usage)). It does not make telemetry risk zero.

### 7.5 Use OTLP as an exit hatch, not a platform commitment

**CONFIG (settings/JSON only)**

Preserve standard trace/span IDs and GenAI attributes where native hosts provide them; keep owner-specific eval fields under a documented namespace. Export only on demand. This leaves a future path to Phoenix, Langfuse, LangSmith, Braintrust, HoneyHive, or ordinary OTel tools without binding current operation to any of them. Multiple surveyed products accept OTel/OTLP ([Phoenix](https://arize.com/docs/phoenix), [Braintrust](https://www.braintrust.dev/docs/integrations/sdk-integrations/opentelemetry), [LangSmith](https://docs.langchain.com/langsmith/trace-with-opentelemetry), [HoneyHive](https://docs.honeyhive.ai/v2/evaluation/concepts)).

It is **very likely (80-90%)** that this materially lowers later migration cost, based on the number of independent products documenting OTLP ingestion. Semantic fidelity is **UNVERIFIED; experiment E4's export/re-import round trip would settle which custom fields survive**.

## 8. Minimal evaluation architecture

The recommended flow is deliberately small:

```text
versioned case manifest
        |
        v
existing /eval command -> native Claude/Codex run
        |                         |
        |                         +-> optional native redacted OTel (temporary)
        v
existing hook dispatcher -> existing ledger + terminal rows
        |
        v
deterministic outcome graders -> eval_result event -> local report/baseline diff
        |
        +-> failed real case promoted into regression manifest after review
```

No daemon, trace UI, vector database, durable engine, trained critic, SaaS, or second agent loop is required.

The episode record should distinguish:

- **trajectory evidence:** tool calls, failures, timing, child relationships, receipts;
- **outcome evidence:** filesystem/test/database/browser state, artifact validity, or exact task-specific oracle;
- **evaluation metadata:** case/suite/grader/harness/model/provider revisions and trial number;
- **operational metrics:** tokens, seconds, tools, retries, subagents, invalid/missing status;
- **decision:** pass/fail/partial/invalid plus individual grader results, never only a composite score.

This directly follows Anthropic's task/trial/trajectory/outcome distinctions and avoids rewarding activity as capability ([agent eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## 9. Experiments that settle the remaining uncertainties

### E1 — Native cross-provider telemetry contract

Run one synthetic, credential-free case through Claude and Codex in copied state. Capture only environment-variable **names**, native event schemas, and local temporary outputs. Include one tool success, one tool failure, one subagent, and one hook block. Verify:

- session/turn/task/parent identifiers;
- model and reasoning-profile availability;
- tool/error/timing/token/cost fields;
- content redaction defaults;
- hook deadline impact;
- joinability with ledger terminal rows;
- cleanup.

Success: the known-present events appear, content can remain absent, and ≥95% of intended rows join to the synthetic episode. Failure: any secret/raw prompt appears under minimal profile, export blocks tool execution, or provider identity cannot be correlated.

### E2 — Correlation patch size and compatibility

In a copied tree, add only correlation fields, run schema/unit fixtures, and inspect diff size. Success: additive compatibility, old rows still parse, both providers preserve episode IDs, and implementation remains under the claimed BUILD-SMALL budget. This is the experiment that confirms or changes proposal 7.2's tag.

### E3 — Three-case vertical eval slice

Cases:

1. deterministic hook lifecycle with allowed and forbidden state deltas;
2. a minimized unmatched-quote Bash failure and corrected form;
3. a dead/unconnected MCP preflight case that must route away before invocation.

Run three fresh trials per provider/profile. Grade terminal state and side effects, not prose. Meta-test each grader with oracle, no-op, and malformed variants. Report raw counts, pass@1, pass^3, invalid episodes, latency, tools, and retries. This is more directly tied to measured damage than importing a generic chatbot/RAG benchmark.

### E4 — Only if SaaS reconsideration is requested

Use synthetic/redacted data and free/local trials. Shortlist Braintrust, Langfuse, Phoenix, LangSmith, and Weave. Import exactly the same 20 traces and 12 cases. Measure:

- event/span loss and parent-child fidelity;
- deterministic scorer parity;
- dataset/baseline/version semantics;
- export round-trip fidelity;
- query latency at 100k synthetic spans;
- setup and weekly maintenance time;
- content/redaction controls;
- monthly price under actual volume;
- vendor shutdown/export plan.

Hard gate: a platform must improve median failure-to-root-cause time or benchmark maintenance time by at least 30% without becoming authoritative for pass/fail and without losing any required export field. The 30% threshold is a v1 policy choice, **roughly even (45-55%)** as the correct cutoff because no local time baseline exists; E4 supplies that baseline.

### E5 — Local framework marginal-value test

Implement the same three cases in current pytest/dispatcher fixtures and one local candidate such as Promptfoo or Inspect. Compare code, dependencies, runtime, isolation, Windows behavior, output clarity, and CI wiring. Reject if the candidate executes untrusted config without a real sandbox, duplicates case metadata, or cannot write results back through the existing ledger.

### E6 — Observability causal-value A/B

For 20 seeded failures, give an agent either existing local evidence or the candidate trace UI/export. Hold model, prompt, budget, tools, and task fixed. Measure correct root cause, correct repair, time, tokens, retries, and new infrastructure failures. This tests the core premise that prettier traces improve outcomes rather than merely diagnosis experience.

## 13. Final recommendation

Reject all evaluation/tracing SaaS and all self-hosted observability platforms for the current harness. Adopt the category's data model, not its control planes:

- native redacted telemetry, on demand;
- one episode identifier spanning provider → agent → tool → outcome;
- versioned cases and grader revisions;
- deterministic outcome graders first;
- repeated trials and pass@1/pass^k reported honestly;
- local ledger as the canonical evidence store;
- OTLP as an optional export boundary;
- promotion of real failures into regression cases;
- no model judge as an uncalibrated release authority.

This package is **very likely (80-90%)** to improve diagnosability and evaluation integrity without reintroducing a rejected component, based on the verified local seams and native telemetry capability.
