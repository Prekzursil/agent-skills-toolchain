# A045 — Coherence audit of `~/.claude/rules/kotlin/testing.md`

## Scope and verdict

This unit audited the complete 128-line target rule from the read-only unpacked subject at `/local_disk0/codexwork/bundle/claude/rules/kotlin/testing.md`. It compared the target with every available rule, the active hook/configuration surfaces, `CLAUDE.md`, `AGENTS.md`, and the measured corpus. The requested live skill directories were not included in the unpacked subject, so the skill-content part of the audit is explicitly incomplete rather than inferred from an index.

The target is not internally self-sufficient. Its most serious coherence defect is that line 128 introduces a second, structurally different “minimum test coverage” after the inherited common rule already defines a percentage threshold and requires unit, integration, and E2E tests. The target also applies to `.kts`, while the common rule it says it extends does not. On the enforcement side, the active per-edit hook silently ignores Kotlin, Kotlin coverage commands are typed as generic `run` receipts rather than coverage receipts, and the only explicit test-integrity hook runs at `git commit` time and is registered only for Bash despite PowerShell being the declared primary shell.

The measured corpus does **not** preserve enough Kotlin-specific behavior to decide whether the owner’s Kotlin work followed this rule. That conclusion is not based on the broken `hooks` corpus section. It is based on the corpus schema plus a controlled term query described below. Any stronger “followed” or “violated” verdict would fabricate a denominator.

## Collision register

### C1 — Two incompatible meanings of minimum coverage

- **Artifacts and exact lines:** `rules/common/testing.md:23-28,38` says coverage is defined by `.coverage-thresholds.json`, defaults to 80%+, and requires unit, integration, and E2E test types. `rules/kotlin/testing.md:118-128` ends with “Minimum test coverage: ViewModel + UseCase for every feature” after listing KMP/Android source sets.
- **Class:** **CONTRADICTION**.
- **Why it collides:** The common file uses “coverage” as a numeric quality gate plus a required test-type set. The Kotlin file uses the same normative phrase for architectural component presence. A Kotlin feature can satisfy line 128 while having no integration/E2E test and less than 80% coverage; conversely, a non-MVVM Kotlin library can satisfy the common gate while having no ViewModel or UseCase. The Kotlin sentence is also inapplicable to Kotlin projects whose architecture legitimately has neither concept.
- **Precedence:** AGENTS §10 does not resolve two same-level rules. `rules/README.md:93-98` makes Kotlin override common, so the deployed textual result is the weaker/architecture-specific minimum. That is an explicit precedence outcome, not a silent choice.
- **Diagnosis:** badly written. The problem is semantic overloading and an architecture assumption, not evidence that numeric coverage or feature-layer tests are intrinsically wrong.
- **Specific resolution — CONFIG:** Replace line 128 with an additive requirement, for example: “Coverage thresholds and required test types remain governed by `common/testing.md` and project `.coverage-thresholds.json`. In projects that actually use ViewModel/UseCase layers, cover each feature’s meaningful state transitions and business rules.” This keeps the common SSOT and makes the architecture condition explicit. It rides the existing rule bus and introduces no new runtime.
- **Confidence:** almost certain (90-99%), because both normative minima and the rules-tree override are explicit at the cited lines; the residual uncertainty is only how Claude composes simultaneously loaded path rules.

### C2 — `.kts` claims to extend a common rule that is not scoped to `.kts`

- **Confidence:** very likely (80-90%), based on the exact frontmatter mismatch. **UNVERIFIED:** whether this Claude version follows the apparent path selector literally for a `.kts`-only turn; settle it with a clean-session instruction-context probe that edits one temporary `.kts` file and records the loaded rule list.

- **Specific resolution — BUILD-SMALL:** Extend the existing `per-edit-check` dispatch with bounded Kotlin handling: discover the nearest Gradle wrapper, prefer a project-provided ktlint/detekt task, and otherwise inject a single concise “run the project Kotlin gate” reminder rather than spawning an unbounded build after every edit. It likely (55-80%) remains under ~200 lines if task discovery is deliberately small; evidence is the existing 20-line extension dispatch at `per-edit-check/check.py:151-170`, and a design spike with line count settles the estimate.
- **Anti-overfit gate:** passes. It extends an existing hook and receipt bus; it does not add an orchestrator, vector database, durable engine, critic, SaaS, or guardrail framework.
- **Confidence:** likely (55-80%) that this bounded implementation reduces silent Kotlin breakage, because the active hook already provides immediate per-edit feedback for supported languages (`per-edit-check/check.py:2-24`) and Kotlin is mechanically an unsupported extension. The experiment is an A/B replay of representative `.kt` syntax, lint, and Gradle edits measuring latency, actionable catches, and false nags before enabling it globally.
