# N03 — Invocation transparency for capability discoverability / auto-routing

## Executive answer

The owner should not have to infer capability use from prose, remember whether a router hint was followed, or watch a stream of hook chatter. The recommended surface is a **quiet per-turn invocation receipt** with three progressively disclosed levels:

1. a persistent one-line status strip: `used 2 · affected 1 · verified 1 · open 1`;
2. an on-demand `why this turn?` view listing skill/hook/agent, trigger, reason, effect, and external evidence;
3. an exception-only inline notice for a failed-open hook, a high-confidence capability that was routed but never invoked, a newly changed capability, or an open thread about to be lost.

The critical distinction is not merely “fired.” The receipt must distinguish **suggested**, **invoked**, **affected the turn**, and **externally verified**. A hook process exiting zero proves invocation, not correctness; a skill loading proves use, not benefit; an agent returning proves completion, not that its work influenced the accepted result. This design refuses to turn self-narration into proof.

The architecture stays deliberately small: append compact `invocation.v1` records to the existing event-ledger, project the current turn into the already-configured Claude status line, and expose a bounded reader. It adds no daemon, second orchestration runtime, vector store, trained critic, durable-execution engine, observability SaaS, or guardrail framework. It adds no seventh hook: instrumentation is folded into the existing shared dispatcher and native lifecycle registrations, while the current `selection-events` registrations are replaced rather than supplemented.

**Overall confidence:** **very likely (80-90%)** that this design will answer “how do I know they are being used?” with materially less cognitive load than inline per-invocation messages. Evidence: the live configuration already has a status-line carrier (`/local_disk0/codexwork/bundle/claude/settings.json:534-537`); the ledger already provides append/replay primitives (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/ledger.py:230-305`); Claude exposes native skill-command and subagent lifecycle signals ([Claude hooks reference](https://code.claude.com/docs/en/hooks)); and a 2026 CHI study reports user demand for collapsible/toggleable multi-agent transparency rather than mandatory rationales ([Sensemaking in Multi-Agent LLM Interfaces](https://doi.org/10.1145/3772318.3791157)). The settling experiment is a two-week within-owner A/B test of exception count, receipt expansions, dismissals, correction rate, and “what fired?” questions versus the current interface.

## Grounding: what is known, and what is not

### Corpus boundary

The corpus is unusually complete for transcript-derived events: 11,633 files, 10.62 GB, 1,564,084 lines, zero file failures, one bad line, and 32 oversized lines (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). Its capability detector found a strongly long-tailed skill-use distribution—`deep-research` 70, `grill-me-extensive` 33, `grill-me` 25, `self-reflect` 18, then many skills used once or twice (`/local_disk0/codexwork/bundle/inputs/corpus.json:13265-13344`)—and 22 named/default agent types with `general-purpose` dominating at 1,158 invocations (`/local_disk0/codexwork/bundle/inputs/corpus.json:13346-13368`). This makes discoverability and routing consequential, but those counts alone cannot say whether a capability was helpful.

The corpus hook section is **NO DATA**, not negative evidence: it explicitly says its detector observed zero fires on a known-positive control and is broken (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13264`). The operational defect report supplies two mechanically independent signals for the symptom: the miner found no hook-name fields across the transcript corpus while a hook visibly injected into the mining turn (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:133-141`). The exact persistence root cause remains **UNVERIFIED**; grepping a known-fired hook name in event-ledger and independently checking transcript system-reminder blocks is the named settling experiment (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:143-147`). No finding below treats the corpus as evidence that hooks did not fire.

### Existing buses to build on, not duplicate

* Claude already registers the shared dispatcher for prompt, tool, permission, compaction, subagent, task, teammate, and stop lifecycle events (`/local_disk0/codexwork/bundle/claude/settings.json:117-149,284-320,356-505`). The native payload includes `session_id`, lifecycle event, tool identity, and subagent identity; the normalized local envelope preserves `turn_id`, tool, and agent fields (`/local_disk0/codexwork/bundle/agents/harness/models.py:10-39`).
* The shared dispatcher currently loops over named modules and receives each module's typed outcome (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:235-308`), but its terminal record projects only event-level status/action/reason/elapsed time plus failed-module names (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:485-515`). That is sufficient for coarse liveness, not a per-component causal receipt.
* The event-ledger already supports typed append, monotonic sequence recovery, atomic projection, and bounded replay (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/ledger.py:230-305`). The manual `note.py` already records decisions, failures, goals, milestones, and supersession (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/note.py:2-12,25-42`). Invocation records belong on this bus, not in a new telemetry store.
* `selection-events/emitter.py` already correlates a real user query, tool-use ID, chosen tool, and success into the ledger (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:577-606`) and fails open at every boundary (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:609-652`). However, live settings register it for prompt caching and failures, not successful `PostToolUse` (`/local_disk0/codexwork/bundle/claude/settings.json:117-137,356-378`), although its own successful path requires `PostToolUse` (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:633-640`). The recommendation replaces this partial experiment with the general receipt writer; it does not create `selection-events-v2` beside it.
* The capability catalog already injects a once-per-session catalog and project card (`/local_disk0/codexwork/bundle/claude/hooks/capability-catalog/inject.py:29-52,55-85`). The lexical router already deduplicates repeated suggestion sets per session and emits a bounded hint (`/local_disk0/codexwork/bundle/claude/hooks/skill-router/route.py:139-154,184-215`). Neither suggestion is proof of invocation.
* The local `_dispatch` plane already consolidates multiple checks behind one process, selects them by matcher, and runs them fail-open (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/dispatch.py:2-19,215-283`). Instrumenting its existing `matched`/`loaded`/timeout boundaries is cheaper and more truthful than another observer hook.

### Design law

Every status in the proposed surface is derived from an external receipt. The agent may state an intent (“I am using X”), but that statement never advances state. Only a native lifecycle event, a different process's exit/result, an artifact/test execution, a second model's independently recorded verdict, or an owner action may do so. This directly implements the operational lesson that a known-positive control separated a genuinely broken hook detector from working skill and agent detectors (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`).

## Findings — inferred surprises first

### Finding 1 — Show capability debt, not just capability activity

**improvement:** Add a quiet `expected-but-missing` lane: when the router strongly selects a skill/agent and no native invocation receipt follows by turn end, retain one open capability-debt item with `why-not` evidence. Do not nag inline on the first miss.

**what it is:** A counterfactual receipt answers the more useful question: “What relevant capability did the harness surface but the agent did not use?” Each row is one of `invoked`, `dismissed-by-owner`, `superseded-by-equivalent`, `not-invocable`, or `unresolved`. It records the router candidate ID and score/basis, the native invocation window searched, and the eventual closure. It never labels a miss from transcript absence alone.

**why-inferred:** The owner explicitly asks how to know capabilities are used, while the corpus shows a steep head and many one-off skill invocations (`/local_disk0/codexwork/bundle/inputs/corpus.json:13265-13344`). Activity-only transparency can reassure while silently hiding routing noncompliance. The existing router itself says its output is only “invoke if apt, else ignore” (`/local_disk0/codexwork/bundle/claude/hooks/skill-router/route.py:205-215`), so suggestion and use are currently different states.

**how-to-build:** Extend the router's existing emitted candidate object with a stable `route_id`, `candidate_id`, `rank`, and short rule/term evidence; append `route.proposed` to event-ledger. Close it from native `Skill` tool/command-expansion or `SubagentStart` receipts, equivalence mappings, or explicit owner dismissal. At `Stop`, fold unresolved high-score candidates into the existing open-loop/event-ledger projection; cap at one new item per turn and deduplicate by `(project, candidate, intent_hash)`. An unresolved item never ages out or disappears during compaction: only an invocation, evidenced equivalent, supersession, or explicit owner dismissal closes it. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. It adds no hook: it instruments the router and existing Stop projection. It builds on open-loop resurfacing already present in the local dispatcher manifest (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:53-59`).

**the EXTERNAL signal that verifies it:** (1) a router-produced `route.proposed` receipt; plus (2) a mechanically independent native skill/agent invocation event or owner dismissal. An absence claim is allowed only after a known-present control route in the same session is successfully matched. A seeded evaluation of 50 prompts must show that every deliberately invoked control closes and every deliberately skipped control remains open; then a second-context evaluator checks false debt against the transcript.

**SOTA citation with URL:** Lim and Dey found demand for different intelligibility questions, including why/why-not, varies with situation and criticality ([Assessing Demand for Intelligibility in Context-Aware Applications](https://www.cs.cmu.edu/afs/cs/Web/People/byl/publications/ubi205-lim.pdf)). Miller's review argues explanations are contrastive—“why P rather than Q”—and selective rather than exhaustive ([Explanation in Artificial Intelligence](https://arxiv.org/abs/1706.07269)).

**value x effort:** transformative x medium

**novelty:** inferred-surprise

**autonomy:** confirm-first — the owner should choose the score threshold and whether unresolved debt appears only on demand or also in a session-end digest.

**confidence:** **likely (55-80%)** that capability debt will expose more actionable routing failures than a fired-components list, because it compares the router's own proposal against a separate native invocation signal. The range is not higher because the semantic router's live quality is outside this unit and router false positives could create debt noise. A shadow-mode precision study over 100 turns, owner-labelled as `miss`/`correct skip`, settles promotion.

### Finding 2 — Use a four-rung proof ladder: suggested → invoked → affected → verified

**improvement:** Make every capability badge carry an evidence grade, preventing “fired” from being mistaken for “helped.”

**what it is:** Four monotonic but independent states:

| State | Meaning | Admissible evidence |
|---|---|---|
| `suggested` | router/catalog proposed it | router process receipt |
| `invoked` | native runtime or hook wrapper executed it | native lifecycle event or child-process exit |
| `affected` | it changed context, action, artifact, or accepted parent result | non-empty effect hash, changed action, artifact hash, or parent incorporation edge |
| `verified` | a different context/tool/owner confirmed the claimed effect | test/build/lint receipt, second-model verdict, owner acceptance/correction, or downstream execution result |

The UI uses neutral glyphs rather than trust-colored green for the first two states. `Verified` names the verifier; it never means “the same agent reviewed itself.”

**why-inferred:** The shared hook contract already distinguishes action, reason code, and additional context (`/local_disk0/codexwork/bundle/agents/harness/models.py:45-95`), but the terminal projection records only the aggregate winner (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:485-513`). The operational defect report shows a detector can falsely mark a successful tool result as failed and thereby corrupt downstream reasoning (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:63-76`). A binary “used” badge would repeat that category error.

**how-to-build:** Define additive `invocation.v1` fields: `event_id`, `session_hash`, `turn_id`, `kind`, `component_id`, `phase`, `trigger`, `reason_code`, `effect_type`, `effect_hash`, `verifier_type`, `verifier_event_id`, `elapsed_ms`, `status`. Instrument the shared dispatcher's existing per-module loop before/after `module.run` and after injection mixing; instrument `_dispatch` at matched/loaded/timed-out/output boundaries; map native skill and subagent events; connect existing typed execution receipts by event ID. Store no prompt, tool input, output text, or chain-of-thought. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** if implemented as one stdlib receipt helper plus small call sites.

**the EXTERNAL signal that verifies it:** A fixture module emits a known additional-context hash and a separate transcript/tool-result reader observes that hash; a fixture skill writes a test artifact and a separate test process validates it; a fixture subagent returns a unique token and the parent artifact contains it. Each ladder transition is asserted from different producers. Same-context prose is ignored.

**SOTA citation with URL:** Buçinca, Malaya, and Gajos found that explanations alone did not reliably prevent overreliance; cognitive-forcing interventions reduced overreliance but received worse subjective ratings ([To Trust or to Think](https://arxiv.org/abs/2102.09692)). The 2025 Microsoft appropriate-reliance review warns that even the presence of sources can increase trust ([Fostering Appropriate Reliance on GenAI](https://www.microsoft.com/en-us/research/wp-content/uploads/2025/03/Appropriate-Reliance-Lessons-Learned-Published-2025-3-3.pdf)). The implication is to display outcome evidence, not decorative rationale.

**value x effort:** transformative x medium

**novelty:** inferred-surprise

**autonomy:** just-do-it — additive shadow receipts are reversible and do not change agent behavior.

**confidence:** **very likely (80-90%)** that this ladder prevents at least some trust miscalibration because it makes the evidence category explicit and all promotions require external signals. Evidence is the current typed outcome contract, the aggregate-only terminal projection, and experimental literature showing that explanations can increase reliance. The remaining uncertainty is whether the owner will attend to grades; the two-week expansion/correction experiment settles that.

### Finding 3 — Personalize transparency from reveal/dismiss behavior, not from self-reported usefulness

**improvement:** Learn a tiny owner-specific attention policy from direct UI actions: expand, pin, dismiss, “show these,” and “never show routine X.”

**what it is:** A bounded local preference table keyed by component family and event class, not a learned critic. It controls presentation only, never routing or enforcement. Example: if the owner repeatedly expands failed-open hooks but never routine `truth-verify` successes, the status strip keeps the latter collapsed and immediately surfaces the former. One global `quiet | balanced | audit` control overrides all learned preferences.

**why-inferred:** Prompt fatigue is a hard constraint, and the owner’s question indicates a need for assurance, not a desire to supervise every hook. Claude's existing injection mixer already ranks safety, goal, verify, loop, and advisory output and caps injected volume (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:45-92,186-208`), so attention priority is already a local design language. Persisting presentation preferences extends it without changing decisions.

**how-to-build:** Add `receipt-view.json` with counters for `expanded`, `dismissed`, `pinned`, and last action; apply deterministic thresholds only after at least five direct actions; decay counts monthly; provide reset/export. Do not infer preference from the agent's choice, time-on-screen, or missing feedback. Feed only presentation priority into the statusline/reader. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** and uses no model, embeddings, or new memory service.

**the EXTERNAL signal that verifies it:** Owner UI actions are the sole learning signal. Offline replay predicts reveal/dismiss choices on held-out actions; a two-week crossover compares interruptions per turn and missed-important-receipt corrections. Promotion requires fewer interruptions with no increase in owner-reported missed events.

**SOTA citation with URL:** Amershi et al.'s validated guidelines call for granular feedback, cautious adaptation, global controls, efficient dismissal, and clear consequences of user action ([Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Their 49-practitioner study tested the guidelines across 20 AI products ([publication page](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**value x effort:** high x low

**novelty:** inferred-surprise

**autonomy:** confirm-first — observation and storage are low-risk, but the owner should choose defaults and retention.

**confidence:** **likely (55-80%)** that direct-action personalization will reduce noise without concealing important exceptions because it modifies display only and retains a global audit mode. The uncertainty is sparse feedback and preference drift; five-action cold start, decay, and a crossover experiment bound it.

### Finding 4 — Make the observability detector prove itself every session

**improvement:** Add a silent known-positive invocation canary and dual-source reconciliation before the UI claims a capability did not fire.

**what it is:** At session start, an already-running carrier records one `canary.invoked` receipt with a nonce. The projection reader must recover that nonce from the append-only ledger and independently see the carrier's terminal/native event. If either signal fails, the UI says `telemetry unknown`, never `0 hooks`. This tests the detector, not the agent.

**why-inferred:** The operational incident is exact: one detector reported zero skills, agents, and hooks; a known-positive control proved skills and agents were fine and only hooks were broken (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:120-129`). Invocation transparency that lacks a canary can manufacture false reassurance or false alarms.

**how-to-build:** Fold a 16-byte random canary into the existing shared `SessionStart` dispatcher; record `(session_hash, canary_hash, producer=dispatcher)`. The statusline reader checks both `terminal.jsonl` and event-ledger within a bounded window. Each component-family absence query first checks a family-specific known-present fixture from installation self-test. The canary is silent unless reconciliation fails. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** and consumes no new hook slot.

**the EXTERNAL signal that verifies it:** Signal A is the shared dispatcher's terminal append; signal B is the event-ledger canary append read by a separate statusline process. Fault-injection independently drops each sink, corrupts one line, and disables one producer; the UI must show `unknown/degraded`, never `none`. A known-present skill and agent fixture validates their detectors separately.

**SOTA citation with URL:** Adaptive trust-calibration research defines transparency around an agent's intent, performance, future plans, and reasoning and reports that continuous behavior feedback supports calibration ([Adaptive trust calibration for human-AI collaboration](https://pmc.ncbi.nlm.nih.gov/articles/PMC7034851/)). The local lesson is stricter: feedback itself needs health evidence.

**value x effort:** high x low

**novelty:** inferred-surprise

**autonomy:** just-do-it — it is silent, fail-open, and only prevents unsupported absence claims.

**confidence:** **almost certain (90-99%)** that this canary catches the already-observed detector class because it directly recreates the known-positive control that exposed it. Evidence is the confirmed incident and two independent sinks. It does not guarantee all correlation bugs; mutation tests across session/turn IDs define the remaining boundary.

### Finding 5 — Disclose capability changes once, at the moment trust assumptions become stale

**improvement:** Add a one-time delta receipt when a skill, hook, or agent is added, removed, renamed, rewired, or changes enforcement mode.

**what it is:** Instead of repeating the catalog, show `capabilities changed: +2 skills, -1 hook, truth-verify shadow→enforce` once, with drill-down. This is invocation transparency over time: the owner learns when yesterday's expectations no longer apply.

**why-inferred:** The capability catalog injects only once per session (`/local_disk0/codexwork/bundle/claude/hooks/capability-catalog/inject.py:29-39,55-69`), while Claude already registers `ConfigChange` through the shared dispatcher (`/local_disk0/codexwork/bundle/claude/settings.json:406-417`). Amershi's guideline 18 is to notify users when capabilities change; the owner’s “how do I know?” concern naturally includes whether the set being monitored is still the same.

**how-to-build:** Extend capability-catalog generation to persist a canonical manifest hash and per-component content hash. On existing `ConfigChange` or next `SessionStart`, append a redacted delta receipt; render it once until acknowledged. Include route aliases so a rename does not look like remove+add when identity is known. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**, folded into capability-catalog and shared dispatcher.

**the EXTERNAL signal that verifies it:** Signal A is the filesystem manifest/hash diff; signal B is the native `ConfigChange` event or next-session inventory. Tests add, rename, delete, and mode-flip fixture components and assert exactly one delta, then owner acknowledgement closes it.

**SOTA citation with URL:** The validated human-AI guidelines explicitly recommend cautious adaptation, conveying consequences of actions, global control, and notifying users about capability updates ([Microsoft HAI guidelines summary](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)).

**value x effort:** high x low

**novelty:** inferred-surprise

**autonomy:** just-do-it — shadow the delta for one week before enabling the one-time notice.

**confidence:** **very likely (80-90%)** that delta-only disclosure creates less fatigue than repeated catalogs because unchanged sessions emit nothing and native/config hash signals are deterministic. Whether every rename can be identified is **UNVERIFIED**; an isolated manifest migration test with ten real historical renames settles identity coverage, and unknown cases must be labelled `possible rename` rather than asserted.

## Findings — directly answering the owner's request

### Finding 6 — Put the default receipt in the status line, not in the conversation

**improvement:** Render one stable, low-entropy per-turn strip and reserve chat interruption for exceptions.

**what it is:** Default compact form:

```text
cap: used 3 · affected 2 · verified 1 · open 1
```

After a first-time or exceptional event only:

```text
cap: skill deep-research ✓ · hook truth-verify !failed-open · agent reviewer ◇verified · open 1
```

The line is a current-turn projection, not a scrolling history. It never displays reasoning text, scores, raw prompts, or all routine hooks.

**why-inferred:** Claude is already configured with a status-line command (`/local_disk0/codexwork/bundle/claude/settings.json:534-537`). Official guidance says status lines are width-limited, should stay short, and should cache slow work ([Claude status-line documentation](https://code.claude.com/docs/en/statusline)). Using the existing persistent peripheral surface protects focus better than injecting a message after every invocation.

**how-to-build:** Extend the existing statusline script to read a tiny atomic `current-turn-receipt.json` projection written by the ledger append path; no ledger scan on refresh. Enforce a hard width budget and priority order: telemetry degraded > failed-open/block > open thread > newly changed > verified > affected > invoked. Add `quiet`, `balanced`, and `audit` environment/config modes. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. The status line is a native surface, but code is needed for the projection and rendering, so the build tag is not `NATIVE`.

**the EXTERNAL signal that verifies it:** Mock statusline input plus a separately generated receipt projection verifies exact rendering; a PTY/screenshot test verifies truncation at 80/120/160 columns; owner A/B ratings and actual interruption counts verify cognitive load. The agent's opinion is not a signal.

**SOTA citation with URL:** Amershi et al. recommend timing services based on task context, showing contextually relevant information, and supporting efficient dismissal ([Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)). Iqbal and Bailey report that deferring notifications to task breakpoints reduces frustration ([Effects of Intelligent Notification Management on Users and Their Tasks](https://interruptions.net/literature/Iqbal-CHI08.pdf)).

**value x effort:** transformative x low

**novelty:** user-asked

**autonomy:** confirm-first — the owner should select the default verbosity after seeing three static mockups.

**confidence:** **very likely (80-90%)** that a statusline strip is less disruptive than inline event messages because it is persistent, bounded, and user-pulled, consistent with notification timing research and native width guidance. Actual focus impact is personal; a two-week crossover using interruption count, dismissals, and subjective focus settles it.

### Finding 7 — Make “why this turn?” an evidence drawer, not generated rationale

**improvement:** Provide one on-demand bounded view that lists exactly which skill/hook/agent fired and why, with source links and counterfactuals.

**what it is:** Each row contains:

```text
kind/name | trigger | why selected | phase | effect | external verifier | receipt id
```

Example: `skill/deep-research | Skill tool | terms: papers, primary sources | affected | 6 citations | owner-opened sources | #1842`. For hooks, “why” is the registered event/matcher plus stable reason code—not a model-written post-hoc story. For agents, it is spawn task hash, agent type, completion status, and incorporation evidence. A second section says `why not` for unresolved high-confidence routes.

**why-inferred:** The current dispatcher has stable module names and typed reason codes (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:267-295`), and native Claude hooks provide command-name and agent-type lifecycle fields ([Claude hooks reference](https://code.claude.com/docs/en/hooks)). These are faithful causal anchors. Asking the same model “why did you use it?” would violate this unit's external-signal law.

**how-to-build:** Add a bounded read-only `/why-this-turn` command or existing re-harness subcommand that reads the current turn's ledger projection and formats at most 12 rows, grouped by exceptions then verified/affected/invoked/suggested. Add `--receipt ID` for raw sanitized JSON and `--why-not NAME` for the counterfactual closure record. Keep all raw data local. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.

**the EXTERNAL signal that verifies it:** Every row must resolve to an append-only receipt and its named producer; a separate validator recomputes effect hashes and rejects dangling verifier IDs. Golden fixtures cover Skill tool invocation, direct command expansion, successful/failed-open hook, agent completion, and router skip. Owner spot-checks ten random turns against native debug/transcript evidence.

**SOTA citation with URL:** Lim, Dey, and Avrahami found why/why-not explanations improve intelligibility of context-aware systems ([CHI paper record and PDF links](https://www.semanticscholar.org/paper/Why-and-why-not-explanations-improve-the-of-systems-Lim-Dey/b062423d2c021274300e5a9f58fc66eea39d1c55)). A 2026 CHI study of multi-agent interfaces found participants wanted collapsible transparency they could inspect when doubtful ([Sensemaking in Multi-Agent LLM Interfaces](https://doi.org/10.1145/3772318.3791157)).

**value x effort:** transformative x medium

**novelty:** user-asked

**autonomy:** just-do-it — ship read-only behind an explicit command before exposing any automatic notice.

**confidence:** **very likely (80-90%)** that an evidence drawer will answer the owner's question more faithfully than generated explanation because its reasons are native triggers, matchers, and receipts. Whether 12 rows is the right bound is **UNVERIFIED**; instrument drawer depth and owner “show more” use for two weeks to settle the cap.

### Finding 8 — UNVERIFIED: replace the partial selection observer; do not add a seventh hook

**improvement:** Consolidate skill, hook, and agent receipts into the existing shared lifecycle carrier and retire the narrow selection-event registrations it supersedes.

**what it is:** A wiring rule: one receipt writer, called from existing dispatch points. Native `Skill` tool events cover model-invoked skills; `UserPromptExpansion` covers direct `/skill`/command invocation; `SubagentStart/Stop` cover agents; the shared and local dispatchers cover their internal hook modules/checks. Standalone hooks use the same tiny fail-open wrapper only when migrated into the shared bus. There is no observer that asks the model what happened.

**why-inferred:** Live settings already register the shared dispatcher broadly (`/local_disk0/codexwork/bundle/claude/settings.json:81-149,284-505`) and separately register `selection-events` twice (`/local_disk0/codexwork/bundle/claude/settings.json:128-137,368-378`). The emitter's positive tool path exists but lacks the corresponding live successful registration (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:633-640`). The local dispatcher already consolidates checks specifically to replace N process spawns (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/dispatch.py:2-19`). ## Concrete schema and rendering contract

The following is a proposed additive record, deliberately smaller than a tracing system:

```json
{
  "schema": "invocation.v1",
  "event_id": "sha256:...",
  "ts": "2026-07-19T12:34:56Z",
  "session_hash": "...",
  "turn_id": "...",
  "kind": "skill|hook|agent",
  "component_id": "truth-verify",
  "phase": "suggested|invoked|affected|verified|failed_open|dismissed",
  "trigger": "PostToolUse:Edit",
  "reason_code": "unverified_completion_claim",
  "effect_type": "inject|block|artifact|advice|none",
  "effect_hash": "sha256:...",
  "verifier_type": "test|tool_result|second_context|owner|none",
  "verifier_event_id": "...",
  "elapsed_ms": 4.2,
  "status": "ok|timeout|error|unknown"
}
```

Privacy rules: hash session/turn identifiers where cross-file joins permit it; retain stable component IDs and reason codes; never store raw prompt, hook payload, tool input/output, agent answer, chain-of-thought, secrets, or absolute transcript paths. This mirrors the existing emitter's deliberate omission of tool input/response/error text and raw session IDs (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:17-29`).

Presentation rules:

1. Routine `invoked` is statusline-only.
2. `affected` and `verified` remain collapsed unless owner-pinned.
3. `failed_open`, `telemetry unknown`, first-time capability, configuration delta, and imminent open-thread loss may appear inline once.
4. No more than one inline capability notice per turn; aggregate the rest.
5. Inline notices appear at a task breakpoint/turn boundary, never between a command and its result.
6. Every notice has `dismiss`, `details`, and `always/never show this class` semantics.
7. A failed receipt writer exits zero and cannot block the wrapped capability.
8. The display says `unknown` whenever detector health or correlation fails.

## Acceptance and rollout plan

### Phase 0 — isolated fixture, no subject mutation

Build in a temporary profile/copy. Fixtures: one skill invoked by model, one directly invoked skill, one successful hook, one failed-open hook, one agent whose result is incorporated, one agent whose result is ignored, and one routed-but-skipped skill. Required assertions:

* Every fixture produces the expected proof rung.
* Same-context narration produces no receipt.
* A missing sink produces `unknown`, never `0`.
* Writer exceptions and timeouts exit zero.
* No raw prompt/tool/agent content appears in records.
* Statusline remains within 80 columns.

### Phase 1 — shadow receipts

Run receipts without any owner-facing display for at least 100 turns. Reconcile a stratified sample against two independent sources: native debug/transcript events and terminal/artifact evidence. Required gates: known-positive recall 100%; zero unsupported `verified` promotions; p95 append overhead below 5 ms; zero hook behavior changes; every failure fail-open. These thresholds are design requirements, not predictions.

### Phase 2 — owner-facing A/B

Alternate `quiet current` and `balanced receipt` by session for two weeks. Measure: inline notices/turn, drawer expansions, dismissals, “what fired?” questions, owner corrections caused by misunderstood invocation, missed open threads, and subjective focus. Do not optimize “trust” upward; optimize correct discrimination among invoked/affected/verified/unknown.

### Phase 3 — replacement

After parity, remove superseded `selection-events` registrations and any dead consumer only with two mechanically independent absence checks and a known-present control. Keep one implementation, one schema, one reader, and one wiring test. If parity fails, retain the old path and mark the receipt experiment incomplete rather than shipping parallel v2 surfaces.

## Alternatives considered and rejected

1. **Print every firing into chat.** Rejected: it consumes attention and context, repeats routine events, and turns observability into prompt fatigue. Notification research and native statusline constraints favor a peripheral, bounded surface.
2. **Have the agent summarize which capabilities it used.** Rejected by construction: same-context self-report is not an external signal and can omit or invent invocations.
3. **Add an observability daemon/OTel SaaS dashboard.** Rejected by the anti-overfit gate: it is a second runtime for a personal harness, duplicates the event-ledger, and adds failure/privacy surfaces.
4. **Store chain-of-thought to explain routing.** Rejected: it is neither required nor a faithful causal receipt. Native event, matcher, score terms, reason code, effect, and verifier are enough.
5. **Show router confidence as truth.** Rejected: confidence can increase unwarranted reliance. The UI shows evidence phase and named verifier instead.
6. **Add one hook per capability family.** Rejected: violates the ~6-hook ceiling and reproduces fragmented detectors. Instrument existing carriers and replace the selection observer.
7. **Learn a personalized router from receipt data immediately.** Rejected: this unit is presentation/observability, and a trained critic/router violates the anti-overfit gate. Simple owner-driven display preferences are sufficient.
8. **Treat no receipt as no invocation.** Rejected: the corpus's broken hook detector is the direct counterexample. No receipt while the canary is unhealthy means `unknown`.
