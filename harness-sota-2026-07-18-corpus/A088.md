# A088 — coherence audit: hooks vs settings / stale references

## Verdict

This is **not** a clean hooks/settings pairing. The direct registrations in
`~/.claude/settings.json` all point to files that are present in the unpacked subject, but the
second-stage local dispatcher routing table has materially regressed:

1. **Fourteen dispatcher-compatible handlers required by the hook tree's own explicit census are
   absent from the runtime manifest**: seven `PreToolUse` and seven `PostToolUse` handlers.
2. **Two Stop handlers which a separate presence test says were wired are absent from the runtime
   manifest.** One surviving Stop handler explicitly defers to one of the absent handlers, making
   the collision behavioral rather than merely documentary.
3. **The live tool is `Agent`, while settings and the local manifest still route `Task`.** The
   corpus contains 1,745 `Agent` calls and no `Task` tool entry; the hook implementation already
   accepts `Agent`, but the two outer matchers prevent it from receiving one.
4. **The generalized Workflow monitor branch cannot run.** The manifest and two hook docstrings say
   the local dispatcher receives `Workflow`; settings excludes it and instead invokes an older,
   standalone Workflow-only monitor.
5. **The Codex monitor implements Bash and PowerShell launch detection, but settings invokes it only
   for `mcp__codex__codex`.** Its two shell branches are unreachable.
6. Several hook files explicitly call themselves registered or wired, while neither active
   registration document names them. The strongest instances are the prompt-time open-loop trigger,
   the semantic router, SessionStart MCP liveness, and MCP user-scope healing.
7. **UNVERIFIED current-plane finding:** the RE matchers recognize legacy direct MCP names but not
   the plugin-local-bridge and funnel names which dominate many historical calls. The corpus proves
   those names have occurred; the omitted live `~/.claude.json` / `~/.mcp.json` prevents proving
   which aliases are connected today. The settling experiment is `claude /mcp` plus a sanitized
   dump of current server names on the Windows host.

The central conclusion is **almost certain (90-99%)**, supported by four mechanically independent
signals: (a) full JSON parsing of settings and manifest, (b) a non-self-derived expected-handler
census in `_dispatch/test_wiring.py`, (c) a separate Stop presence test plus a dated manifest backup,
and (d) the prior Windows audit's recorded executable test result (`9 failed, 11 passed`). The final
1-10% uncertainty is limited to configuration sources omitted from the remote bundle; it does not
change which handlers the shown user-level dispatcher can load.

No replacement runtime is warranted. Every repair below rides the existing native hook/settings
and local-dispatch bus. This passes the anti-overfit gate and introduces none of the prohibited

### Runtime-resolution rule used

Anthropic's current hook reference says user hooks are defined under `~/.claude/settings.json`,
plugin hooks are loaded from a plugin's `hooks/hooks.json` **when the plugin is enabled**, and a
tool-event matcher filters on `tool_name`. It also says all matching hooks run; this is not a
first-match-wins chain. Source:
https://code.claude.com/docs/en/hooks (sections “Hook locations,” “Matcher patterns,” and “How a hook
resolves”). Anthropic's configuration debugger explicitly says a standalone `.claude/hooks.json`
does not load: https://code.claude.com/docs/en/debug-your-config.

For the local dispatcher, settings first decides whether `dispatch.py` is launched. The dispatcher
then loads `manifest.json` (`dispatch.py:147-150`), selects only checks in the chosen event
(`:215-237`), constructs their script paths (`:240-250`), and runs only that selected list
(`:256-283`). Therefore:

```text
tool event
  -> settings event + matcher
  -> settings command (dispatch.py EVENT)
  -> active manifest event.checks
  -> each inner matcher
  -> handler
```

At runtime, active settings wins over comments/tests/backups for the outer step, and the active
manifest wins over comments/tests/backups for the inner step. A test that says a handler must exist
does not register it.
