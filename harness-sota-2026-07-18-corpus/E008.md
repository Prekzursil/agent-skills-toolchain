This is **not** a population recall/precision result because the sample is capped, deliberately recall-biased, and contaminated. It is nevertheless a decisive fixture failure: four of the five are follow-up directives/corrections rather than initial ambiguity, so enabling this detector as an asking gate would inject clarification pressure after the owner has already clarified or asked for continuation.
5. The clarification implementation is currently unwired. Signal 1: active Claude `UserPromptSubmit` settings invoke the shared dispatcher and selection emitter only (`claude/settings.json:117-138`), and a validated bounded name search found no `inquisitiveness`, `calibrated-silence`, or `compute-confidence-gate` registration in either active settings or the local manifest. This agrees with, but does not merely repeat, audit claim A32 (`inputs/audit-findings/A32.md:39-45`).

The recommended gate is therefore a two-stage **authority + expected-value-of-sample-information** policy:

- Ask unconditionally when only the owner can grant required authority for a material external, destructive, irreversible, costly, or preference-binding action.
- Otherwise, inspect/probe first; then ask only when the expected loss avoided by a likely, resolving answer exceeds the measured cost of interrupting and stalling. If it does not, choose the most reversible option, state the load-bearing assumption, preserve a rollback point, and continue.

This is **likely (55-80%)** to reduce needless questions without increasing owner corrections, based on the autonomy-oriented samples, the mutation correction, and the current detector's fixture failures. It remains **UNVERIFIED** until the raw-transcript linkage and a shadow/active replay described below measure false asks, missed asks, correction rate, abandonment, and task success.

## 2. What an interruption costs—and what is not measured

### 2.1 Cost components the harness must model

An ask is not a free information lookup. Its cost is a vector:

1. **Owner active effort:** reading the question, reconstructing context, deciding, and typing.
2. **Wall-clock stall:** the agent may stop until the owner returns.
3. **Context resumption:** both parties reload the task state; long-running jobs or remote environments may have moved meanwhile.
4. **Autonomy/trust cost:** a needless question transfers work the agent could have resolved from code, configuration, logs, or a reversible experiment.
5. **Question-error cost:** poorly framed choices can anchor the owner to false alternatives or omit the best option.
6. **Abandonment risk:** a blocked task may receive no answer in that session.

Only qualitative evidence for items 2-4 appears in the supplied samples. There is no timestamp pair linking an agent question to the owner's response, so median/P95 wait, answer length, resumption calls, and abandonment are **UNVERIFIED**; exporting raw event sequences and applying the instrumentation in §6 would settle each one.

## 3. Diagnosis of the current mechanisms

### 3.1 The contract is directionally right but not executable

The behavior contract already says to ask 1-3 targeted questions only for material ambiguity, only in the first 1-2 actions, never mid-task, and to bypass questions when a prompt begins `*` (`claude/AGENTS.md:7-13`). It further says a low-confidence load-bearing assumption is a clarify-or-verify trigger (`claude/AGENTS.md:14-20`) and that ordinary ambiguity should inject guidance rather than block (`claude/AGENTS.md:64-70`).

These rules omit the quantities needed to choose between clarify and verify: alternatives, probability of choosing wrong, consequence of being wrong, reversibility, cost of a probe, expected response/resolve probability, and interruption cost. “Material” is therefore model intuition, not an auditable EVPI decision.

### 3.2 The lexical guard fires on the wrong axis

The guard's hard gate equates a concrete object with a settled decision (`prompt-guard.py:120-123`). Those are different concepts. “Delete the old production database and replace it with the backup” names a concrete target but may require authority and confirmation; the replay score was only 2, below the asking threshold. Conversely, “continue monitoring the subagents(do not stop them)” scored 3 even though it is an explicit continuation directive.

The five firings over supplied samples show the practical mismatch:

- “nope it still doesnt wrk” — a failure report; inspect and diagnose.
- “do not forget to update basic memory with our findings” — a direct instruction.
- “continue monitoring the subagents(do not stop them)” — a direct instruction.
- “i meant you should do that” — a correction; the clarification opportunity has already passed.
- “why did you stop?...” — a complaint about halted execution; asking again compounds the friction.

It is **very likely (80-90%)** that enabling this predicate unchanged would add low-value clarification pressure on some correction/continuation turns, because 4/5 observed fires have that shape. The population false-positive rate is **UNVERIFIED**; running it over every genuine initial human task turn in the raw corpus and manually labeling a stratified sample would settle it.

### 3.3 “Calibrated silence” learns engagement, not value of information

The existing interjection gate uses `ev = p_useful * value[type]` and compares it with a base threshold plus fatigue (`calibrated-silence/calibrated_silence.py:11-26,94-123,382-428`). This is useful infrastructure, but `question` has a fixed value of 1.0 (`calibrated_silence.py:98-107`); it does not represent the loss avoided by *this* question.

More importantly, the reaction classifier marks any non-dismissive response of at least five words as `acted` for a question (`calibrated-silence/log_reaction.py:51-52,100-115,143-151`). A five-word “you decide; please just proceed” would count as success even if the question conveyed no useful information and caused delay. The ledger row stores type, context key, session, surfaced, and reaction, but no question text, alternatives, chosen branch, counterfactual default, latency, or downstream correction (`calibrated_silence.py:198-220`).

Thus this component estimates engagement/acceptance, not EVPI or net utility. Reuse its append-only ledger and density/fatigue machinery; do not reuse `acted` as proof that asking was worthwhile.

### 3.4 The shared result bus cannot directly express “ask”

The shared `Action` type permits only `allow`, `block`, `inject`, and `continue` (`agents/harness/models.py:7-8,45-74`); its schema repeats the same enum (`agents/harness/schemas/hook-result.schema.json:18-20`). The adapter renders block/deny, continuation, or additional context, but no human-question action (`agents/harness/adapters.py:159-207`). The existing inquisitiveness code correctly describes itself as a router: a `UserPromptSubmit` hook cannot itself call the question UI, so it injects guidance for the agent (`prompt-guard.py:2-20`).

The minimal portable design is consequently to compute/log the gate on `UserPromptSubmit`, inject a short `ASK_REQUIRED` or `DECIDE` rationale, and let the provider's native agent interaction ask when required. A cross-provider wire-level `ask` action is **UNVERIFIED** and outside this unit; a real disposable-session canary on each provider would settle support. The design below does not depend on such a new action.

## 4. The EVPI/EVSI gate

### 4.1 First principle: authority is not an expected-value trade

Before computing information value, classify whether the agent has authority to choose. Ask when the missing input is consent/authorization for a material action whose permission cannot be inferred from the current instruction:

- destructive or difficult-to-recover mutation;
- external communication, publication, purchase, deployment, merge/push, or action affecting third parties;
- credential/secret disclosure or permission expansion;
- a costly commitment beyond the authorized scope;
- a subjective preference fork whose outcome will be durable/user-facing and no stated preference or established convention resolves it.

This is an `AUTHORITY_REQUIRED` result, not “high vagueness.” Cheap read-only investigation may still precede the question so the agent asks about concrete options. The gate must not use EVPI to justify unauthorized action.

If the prompt explicitly authorizes the action and names constraints, proceed within those constraints. For example, the RAM-cleanup sample authorizes a bounded cleanup but protects active sessions and forbids hard kill (`corpus.json:11291-11294`); the agent should audit first and only escalate an unclassifiable candidate.

### 4.2 For ordinary uncertainty, use EVPI as an upper-bound rejection test

Let:

- `S` be the small set of materially different states/owner preferences still plausible after reading the prompt and repository.
- `A` be the feasible actions.
- `p(s)` be the agent's calibrated probability of state `s`.
- `L(a,s)` be expected loss if action `a` is taken in state `s`: reversible rework time/cost plus task-quality loss. Irreversible harm is excluded here because it was handled by the authority gate.

Then:

```text
Loss_decide = min_a Σ_s p(s) L(a,s)
Loss_perfect_info = Σ_s p(s) min_a L(a,s)
EVPI = Loss_decide - Loss_perfect_info
```

If `EVPI <= C_ask`, decide immediately: even perfect information cannot repay the interruption. This is the key anti-rubber-stamp gate.

Human answers are not perfect and may never arrive. Therefore the actual ask decision uses expected value of sample information (EVSI):

```text
EVSI_ask = P(answer in useful window)
           × P(answer resolves the branch | answer)
           × expected loss avoided when resolved

ASK iff EVSI_ask > C_ask
```

`C_ask` is measured, not guessed:

```text
C_ask = owner_active_time
        + weighted_wall_stall
        + agent_resume/revalidation_time
        + expected_abandonment_loss
        + question_composition/processing cost
```

The weights translating wall stall and abandonment into task-cost units are **UNVERIFIED**. A shadow log plus owner-specified relative valuation, followed by the experiment in §6, would settle them. Until then, retain the components as a vector and use Pareto dominance: ask only when the expected avoided loss exceeds the interruption on every owner-designated material dimension or authority requires it.

### 4.3 Machine-obtainable information dominates interruption

Before asking, compare a probe with both deciding and asking:

```text
if a read-only/local/reversible probe is expected to resolve the branch
   and C_probe < min(EVPI, C_ask):
       probe, update probabilities, and re-run the gate
```

Examples include reading the relevant file/config, inspecting logs, checking repository conventions, running a bounded test, querying a live status endpoint, or making a reversible prototype. This directly implements the owner's recorded preference for sandboxed/live evidence without manual presence (`corpus.json:12101-12104,12257-12260`).

No fixed “two-minute probe” threshold is recommended: the corpus does not measure owner interruption time, so such a number would be fabricated.

### 4.4 Decision table

| Condition | Result | Required behavior |
|---|---|---|
| Explicit instruction already chooses the branch | `DECIDE` | Act; do not ask for confirmation. |
| Required authority/consent is absent | `ASK_REQUIRED` | Investigate enough to offer 2-3 grounded choices; ask and stop before the material action. |
| Information is available from a cheaper safe probe | `VERIFY_FIRST` | Probe; update the assumption ledger; recompute. |
| `EVPI <= C_ask` | `DECIDE` | Choose lowest expected-loss, most reversible action; state assumption; retain rollback. |
| `EVPI > C_ask` but answer/resolve probability makes `EVSI <= C_ask` | `DECIDE_REVERSIBLY` | Choose reversible default and proceed; do not stall. |
| `EVSI > C_ask` in the first 1-2 actions | `ASK` | Ask one compact question, ideally 2-3 mutually exclusive options plus a recommended default. |
| New ambiguity arises mid-task but authority is not required | `DECIDE_REVERSIBLY` | Verify or choose reversible default; log assumption. Do not perform a generic check-in. |
| New mid-task authority boundary appears | `ASK_REQUIRED` | Stop only at that boundary; summarize completed work and ask the minimum permission question. |
| Owner explicitly says “no check-ins,” `*`, or equivalent | Raise `C_ask`; do not erase authority | Continue on ordinary uncertainty; still ask for genuinely missing required authority. |

### 4.5 Question construction

An `ASK` must contain:

1. the decision that changes;
2. 2-3 mutually exclusive choices when possible;
3. the recommended choice and why;
4. the default the agent will use if the interface supports non-blocking continuation;
5. no question whose answer is already in the prompt, repository, logs, memory, or explicit owner policy.

Ask one compound decision question rather than serially discovering adjacent preferences. The current contract's 1-3 question cap remains an upper bound (`claude/AGENTS.md:9-12`), not a target.

- If both options were authorized, querying dominates because it obtains diagnostic information without mutation.

- Verify-first: decompiler, replay harness, sandbox, telemetry, or deterministic contract tests.
- Ask only for a genuinely owner-only physical observation/input after those paths fail.
- If a manual test is unavoidable, batch all needed observations into one checklist.

This policy is **likely (55-80%)** to lower interruption count in similar reverse-engineering sessions, based on two explicit owner-free-testing requests. It is **UNVERIFIED** outside those workflows; task-stratified active telemetry would settle generalization.

### 5.4 “Why did you stop?”

The same long-running session contains “why did you stop?” and later “why did you stop mr sir?” (`corpus.json:12251-12254,12359-12362`), plus a recorded instruction for sequential execution with no check-ins (`corpus.json:11836-11840`).

- Ordinary uncertainty: choose the reversible next backlog item and continue.
- Terminal condition, exhausted safe alternatives, or missing authority: summarize and ask once.
- Do not turn a status update or “continue?” confirmation into a blocking owner turn when the continuation instruction is already explicit.

It is **very likely (80-90%)** that continuation questions in that explicitly autonomous loop would be negative-value, conditional on the sampled text being genuine, because they request information already supplied and create the exact stop the owner later challenges.

## 6. Measurement plan: turn the unmeasured cost into data

### Proposal 1 — shadow ask-decision receipts. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add one provider-neutral `UserPromptSubmit` module to the existing shared dispatcher. In **shadow mode**, it must not ask or inject. It writes a bounded receipt to the existing event ledger:

```json
{
  "reason_code": "ask_evpi_shadow",
  "authority_required": false,
  "states": ["..."],
  "candidate_actions": ["..."],
  "recommended_action": "...",
  "probe_available": true,
  "evpi_components": {"rework": null, "quality": null},
  "ask_cost_components": {"owner_active": null, "stall": null, "resume": null},
  "counterfactual": "VERIFY_FIRST",
  "question_hash": "..."
}
```

Do not persist raw secrets or full prompts; store a session/turn key and bounded redacted rationale. This reuses `UserPromptSubmit`, `HookResult`, and the ledger rather than creating a new runtime. It passes the anti-overfit gate: no second orchestrator, vector database, knowledge graph, durable-execution engine, trained critic, SaaS, or guardrail framework.

It is **likely (55-80%)** that a shadow module can be kept under ~200 lines because the shared event envelope, dispatcher, module list, result contract, and ledger already exist (`agents/harness/models.py:10-74`, `modules.py:2599-2613`). The line bound is **UNVERIFIED**; an implementation spike with tests and a diff line count would settle it.

### Proposal 2 — outcome-linked question receipts. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing calibrated-silence reaction path rather than building a second learner. For each actual agent question, capture:

- question turn and decision key;
- authority versus ordinary information request;
- recommended/default action;
- owner response timestamp and non-empty-answer flag;
- whether the answer changed the action;
- first subsequent tool/action;
- time/tool calls until work resumed;
- correction within a bounded later window;
- task completion/abandonment receipt;
- explicit annoyance/“you decide”/answer-already-provided labels.

The current `acted` label must remain an engagement metric, not be renamed utility (`log_reaction.py:143-151`). Net utility requires avoided wrong-branch/rework evidence.

It is **likely (55-80%)** that the receipt extension can use the existing append-only interjection ledger and transcript parser (`calibrated_silence.py:198-220`; `log_reaction.py:154-189`) without a new service. The <200-line target is **UNVERIFIED**; a tested spike measuring added production lines would settle it.

### Proposal 3 — activate only after a labeled shadow replay. **NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

After Proposal 1 exists and the module is tested, promotion from shadow to inject can be a module-mode/settings change on the existing bus. Do **not** wire the current lexical guard unchanged.

The activation dataset and thresholds are **UNVERIFIED**. The settling experiment is:

1. Export genuine human initial-task turns, adjacent assistant turns, tools, and subsequent human turns from the raw corpus; exclude `tool_result`, task notifications, teammate envelopes, stop-hook feedback, local-command envelopes, and embedded agent-authored prompts using event provenance rather than text prefix alone.
2. Validate the detector with known-present controls for every excluded and retained event type.
3. Independently label a stratified sample by task type and consequence. Labels: `AUTHORITY_REQUIRED`, `VERIFY_FIRST`, `ASK`, `DECIDE_REVERSIBLY`, `ALREADY_ANSWERED`.
4. Replay the current lexical guard and proposed gate blind. Measure false asks, missed authority asks, missed preference asks, redundant asks, and inter-rater agreement.

## 7. Minimal implementation contract

The shared module should output one of five reason codes: `ask_authority`, `ask_evsi`, `verify_first`, `decide_reversible`, `already_answered`. It should not attempt precise arithmetic when inputs are unavailable. Unknown terms remain `null`, forcing a qualitative dominance decision and a shadow receipt rather than fake precision.

Pseudo-code:

```text
on UserPromptSubmit:
  constraints = extract explicit choices, prohibitions, autonomy preference
  if requested action is clear:
      return ALREADY_ANSWERED

  if missing authority for material action:
      return ASK_AUTHORITY with grounded alternatives

  if safe machine probe can resolve cheaper than owner interruption:
      return VERIFY_FIRST

  enumerate <=3 material states and actions
  estimate loss vector, answer probability, resolution probability, ask-cost vector

  if perfect information cannot dominate ask cost:
      return DECIDE_REVERSIBLE

  if answer-weighted information dominates ask cost:
      return ASK_EVSI

  return DECIDE_REVERSIBLE
```

The agent-facing injection, when active, should be compact:

```text
[ASK-EVPI] VERIFY_FIRST. The unresolved branch is machine-obtainable from <source>.
Do not ask the owner yet. Probe, update the assumption, then choose the reversible path.
```

or:

```text
[ASK-EVPI] ASK_REQUIRED: missing authority for <material action>.
Ask one question offering <A>/<B>, recommend <A>, and do not cross the boundary before reply.
```

This is **likely (55-80%)** to be more robust than injecting a long rubric on every prompt because it minimizes context consumption and rides the existing behavior contract and dispatcher. The comparative compliance rate is **UNVERIFIED**; a prompt replay measuring next-action adherence for compact versus long injection would settle it.

## 8. Anti-overfit gate and rejected alternatives

### Accepted architecture

The design adds one small decision module and bounded fields to an existing ledger/reaction path. It uses the native provider interaction for the actual question. It does not add a second orchestration runtime, vector/KG memory, durable execution engine, trained critic, observability SaaS, or generic guardrail framework.

### Rejected: enable `inquisitiveness` unchanged

Rejected because the predicate measures lexical vagueness, not value of information or authority, and its supplied-sample fires are mostly already-clarified follow-ups (`prompt-guard.py:108-160`; measured 5/400 replay). It would also keep the broken utility proxy that counts any substantive answer as an `acted` question (`log_reaction.py:143-151`).

### Rejected: ask on every low-confidence assumption

Low confidence is not enough. If a cheap probe resolves it or the wrong choice is reversible, interruption can cost more than perfect information is worth. The contract already says “clarify-or-verify,” not “always clarify” (`claude/AGENTS.md:14-20`).

### Rejected: never ask / always decide

This fails at missing authority, irreversible changes, external commitments, and durable subjective choices. The disable-versus-query correction is a concrete warning that proceeding can create rework (`corpus.json:11897-11900`), though its exact predecessor remains **UNVERIFIED** pending raw inspection.

### Rejected: fixed monetary/minute threshold now

No available field measures question response time or owner active effort. A numeric threshold would be false precision. Collect the components first; let the owner set the value trade once the empirical distribution exists.

### Rejected: a model-based “question critic” service

This would be a second decision runtime/trained-critic-shaped component, add latency, and violate the anti-overfit constraint. The required policy is small enough to ride the current hook/ledger bus.
