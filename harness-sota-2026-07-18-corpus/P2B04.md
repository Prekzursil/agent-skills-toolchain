# P2B04 — Competitive teardown: Roo Code

**Unit:** P2B04  
**Research date:** 2026-07-18  
**Subject under comparison:** the owner’s Claude Code / shared Agents harness, not stock Claude Code alone  
**Roo baseline:** Roo Code 3.54.0 / archived `main`, whose extension and company service were shut down on 2026-05-15

## Executive verdict

Roo Code is not a replacement candidate. It is a useful source of a handful of productized interaction patterns, but its agent architecture is mostly a less capable, VS Code-bound version of facilities that the owner already has. Roo’s own repository is archived and its extension was shut down on May 15, 2026; the final official documentation says so explicitly ([official landing page, lines 19–30](https://roocodeinc.github.io/Roo-Code/), [archived repository and shutdown notice](https://github.com/RooCodeInc/Roo-Code)). It is **almost certain (90-99%)** that adopting Roo itself would be a regression rather than a frontier upgrade: evidence is the shutdown, the read-only archive, Roo’s sequential-only in-process delegation, its lack of a documented lifecycle-hook bus, and its substantially weaker durable-memory story.

The useful extraction is much narrower:

1. **Port the diagnostic delta, not the IDE shell.** Roo snapshots VS Code diagnostics before an edit, waits for language servers, and reports only newly introduced errors. That is a concrete verification receipt, not a prompt telling the model to “check its work.”
2. **Port simple invariants as native task hooks.** Roo can require a todo list for delegated tasks and refuse completion while todos remain open. Claude Code has a richer task graph and a blocking `TaskCompleted` event already; the owner has wired that event, but the current handler verifies claims rather than enforcing the open-task invariant.
3. **Make compaction and MCP state observable.** Roo exposes before/after token counts, cost, and the retained summary for every condensation, plus per-server MCP enable/restart/timeout/tool controls. The owner’s harness has the underlying buses, but its own pinned defects say hook behavior is not durably measurable, while the corpus shows a dead MCP repeatedly called hundreds of times.
4. **Do not copy Roo’s Qdrant code index, implicit message-queue approval, auto-approved in-repo custom tools, shadow-Git checkpoint runtime, or second orchestrator.** The first violates the anti-overfit gate’s rejected vector-DB component; the next two weaken security; and the last two duplicate capabilities Claude Code already implements natively.

This conclusion is **very likely (80-90%)** to remain correct for the design phase because it is based on Roo’s final official docs and archived source plus the installed Claude Code 2.1.214 configuration. The uncertainty is that the community fork ZooCode may continue evolving independently; that fork is outside this unit’s named subject and would require a separate teardown.

## Ground truth: what “our harness” already is

This baseline prevents attributing stock-product differences to the owner’s much richer harness.

- **Task and agent substrate is live.** The corpus records 1,745 `Agent` calls at 1.15% error (`corpus.json:119-124`), 2,181 `TaskCreate` calls at 1.51% error (`corpus.json:111-116`), 3,710 `TaskUpdate` calls at 0.38% error (`corpus.json:95-100`), and 500 `SendMessage` calls at 2.0% error (`corpus.json:191-196`). This is not a theoretical capability.

Concrete examples are `settings.json:82-101`, `139-257`, `310-364`, `380-393`, and `419-523`.
- **Permissions are configured, though permissively.** There are 35 allow rules, four deny rules, zero ask rules, and `defaultMode: "bypassPermissions"` (`settings.json:27-71`). This matters when comparing Roo’s approval UI: Roo’s safer default is better than this owner setting, but Claude Code’s native permission mechanism is not missing.
- **Compaction is enabled and hooked.** `autoCompactEnabled: true` and `autoCompactWindow: 1000000` appear at `settings.json:686-697`; PreCompact and PostCompact hooks appear at `settings.json:380-405`.
- **Durable cross-tool memory exists.** `CLAUDE.md:5-15` defines proactive recall and capture through the `basic-memory` MCP and distinguishes it from the event ledger. The corpus records 1,332 basic-memory uses (`corpus.json:13370-13378`).
- **Completion checking exists.** The shared harness runs on both Stop and TaskCompleted (`modules.py:2051-2067`) and detects unsupported completion claims (`modules.py:2111-2137`). The known defect is not absence but reliability: prose is misclassified as execution, and hook telemetry is not durably measurable (`INPUT-known-harness-defects.md:9-109`, `133-149`).
- **Reliability damage is measured.** StructuredOutput fails 22.9%, with 294 instances of the dominant required-schema mismatch (`corpus.json:8964-8992`). Glob fails 13.32%, including 592 `ENAMETOOLONG` failures (`corpus.json:8995-9006`). Tavily extraction fails 25.75%, including 135 “not connected” calls (`corpus.json:9141-9148`). These defects matter more than aesthetic parity with Roo.

## 1. Agent loop

### What Roo actually does

Roo’s core loop is conventional and explicit in the docs: choose a tool, show its parameters for review, execute after approval, show the result, and repeat until the task is complete ([How Tools Work, lines 42–59](https://roocodeinc.github.io/Roo-Code/basic-usage/how-tools-work)). Its workflow tools are `ask_followup_question`, `attempt_completion`, `switch_mode`, `new_task`, and `skill`; read/edit/execute are separate tool groups ([tool reference, lines 107–126](https://roocodeinc.github.io/Roo-Code/basic-usage/how-tools-work)). Terminal shell integration observes streaming output, exit codes, working-directory changes, and allows stop from chat ([official shell integration](https://roocodeinc.github.io/Roo-Code/features/shell-integration/)).

This loop does not contain a planner, verifier, critic, or durable scheduler as a separate runtime. Planning is expressed through Architect mode and a todo tool. Verification is expressed through tool results, diagnostics, and prompt instructions. That simplicity is good and satisfies the anti-overfit principle.

### Comparison

The owner already has the same loop plus more interception points. The high-value lesson is not a new runtime; it is Roo’s insistence that task flow is represented by a few explicit terminal-state tools (`attempt_completion`, `new_task`, `update_todo_list`). The owner contract independently demands terminal outputs such as `SUCCESS:<id>`/`FAILED:<id>`, which is directionally stronger.

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Do not add a Roo-like controller around Claude. Claude’s Task/Stop events and native tool loop are the bus. A second controller would be one of the anti-overfit gate’s explicitly rejected “second orchestration runtimes.”

### Multi-provider loop — capability we lack but should reject

Roo is genuinely model-agnostic and can assign a remembered model to each mode ([Using Modes, lines 39–44](https://roocodeinc.github.io/Roo-Code/basic-usage/using-modes), [Custom Modes, lines 64–70](https://roocodeinc.github.io/Roo-Code/features/custom-modes/)). Stock Claude Code cannot switch the active conversation to Gemini, OpenAI, DeepSeek, and dozens of other providers through one native model picker.

**Port assessment: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** A faithful port requires a provider-normalization layer for tool schemas, reasoning formats, streaming, token accounting, caching, and authentication. Roo’s changelog is filled with provider-specific schema and history repairs; for example, 3.37 fixed malformed reasoning details and tool-result formatting ([3.37 release notes](https://roocodeinc.github.io/Roo-Code/update-notes/v3.37/)). The owner already spans providers by using their native agents behind a shared behavioral contract. It is **very likely (80-90%)** that a unified provider runtime would add more reliability surface than value, evidenced by Roo’s repeated compatibility fixes and the owner’s existing StructuredOutput 22.9% error rate. This proposal explicitly reintroduces a rejected second orchestration runtime, so it fails the anti-overfit gate and should not proceed.

## 2. Context management

### Roo’s mechanism

Roo combines five mechanisms:

1. **Selective context mentions.** `@file`, `@folder`, `@problems`, `@terminal`, `@commit`, `@git-changes`, URL, and slash-command mentions inject concrete context. File contents include line numbers; URLs are fetched in a headless browser and converted to Markdown ([Context Mentions, lines 37–71 and 93–149](https://roocodeinc.github.io/Roo-Code/basic-usage/context-mentions/)).
2. **Environment details.** Workspace state and task reminders are appended to the model context. Todo state appears as a `REMINDERS` table so it remains available to the model ([Task Todo List, lines 94–109](https://roocodeinc.github.io/Roo-Code/features/task-todo-list/)).
3. **Isolated subtask contexts.** A child receives only an explicit down-message and returns only its final result summary; the parent history is not inherited ([Boomerang Tasks, lines 71–93](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks/)).
4. **Intelligent condensation.** At a configurable context threshold, the active model summarizes earlier conversation; the first slash command is preserved; the user can customize the condense prompt or trigger it manually ([Context Condensing, lines 62–100](https://roocodeinc.github.io/Roo-Code/features/intelligent-context-condensing/)). Roo displays before/after token counts, cost, and the expandable retained summary ([same page, lines 105–121](https://roocodeinc.github.io/Roo-Code/features/intelligent-context-condensing/)).
5. **Error recovery.** On a provider context-window error, Roo truncates context by 25% and retries up to its retry limit. It reserves 30% of the window by default—20% output and 10% safety—and uses native token counting where possible, otherwise estimation ([same page, lines 144–184](https://roocodeinc.github.io/Roo-Code/features/intelligent-context-condensing/)).

### What is already native

Claude Code 2.1.214 already clears old tool outputs, auto-compacts, supports `/compact <focus>`, Compact Instructions in CLAUDE.md, and `/context` token attribution ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works), [context-window survival table](https://code.claude.com/docs/en/context-window)). Project-root instructions, auto memory, and invoked skill bodies are re-injected after compaction. The owner explicitly enables auto-compact and has both PreCompact and PostCompact hooks.

Therefore Roo’s basic condensing, mention, and subcontext ideas are **NATIVE (Claude Code already does this; we just enable it)**. Roo’s UI is more explicit about each condensation, but the mechanism is not missing.

### Proposal — durable compaction receipts

**Port assessment: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing PreCompact/PostCompact route to record a receipt with session id, reason, token estimate before/after, compact instruction hash, summary/checkpoint permalink when available, and success/failure. Do not create another memory service; append to the event ledger and link to basic-memory only when a semantic checkpoint already exists.

This is **likely (55-80%)** to reduce compaction regressions and make them diagnosable. Evidence: Roo found enough value to expose an audit row with token and summary deltas; the owner already has Pre/PostCompact events; and pinned defect D3 says hook behavior across 1,964 sessions is currently unmeasurable (`INPUT-known-harness-defects.md:133-149`). The benefit magnitude is uncertain because the hook payload’s exact compact-token fields have not been inspected in this unit.

**UNVERIFIED — experiment:** capture one real PreCompact and PostCompact JSON payload with redaction, prove the detector against known-present `hook_event_name`, and check whether token counts and summary identifiers are provided. If token counts are absent, use the native `/context`/status data only if it is accessible without scraping the UI; otherwise record reason, timestamps, and checkpoint identity rather than inventing counts.

### Where Roo is worse

- Roo’s official issue tracker recorded context-condensing loops even on a new conversation ([issue #8158](https://github.com/RooCodeInc/Roo-Code/issues/8158)). Claude Code now explicitly stops auto-compacting after repeated refill attempts rather than looping ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)).
- Roo always uses the active model for condensation. This avoids tool-format translation, but it can spend an expensive coding model on summarization. This is a tradeoff, not an unqualified advantage.
- Roo’s environment payload has historically been large and provider-sensitive; 3.37 changed how `environment_details` was attached because it could interrupt tool-call sequences ([3.37 release notes](https://roocodeinc.github.io/Roo-Code/update-notes/v3.37/)).

## 3. Memory

### Roo’s memory layers

Roo has persistence, but it is not a semantic long-term memory system:

- **Task history:** conversation/task data is stored in VS Code extension storage, optionally at a custom path; settings can be imported/exported, and a shared network folder can expose the same task history ([Settings Management](https://roocodeinc.github.io/Roo-Code/features/settings-management/)).
- **Task todo state:** the checklist persists in the task and is repeatedly placed into environment details ([Task Todo List](https://roocodeinc.github.io/Roo-Code/features/task-todo-list/)).
- **Checkpoints:** shadow-Git snapshots persist workspace and task rewind points but are explicitly task-scoped ([Checkpoints, lines 171–195](https://roocodeinc.github.io/Roo-Code/features/checkpoints/)).
- **Rules and skills:** global/project instructions encode durable preferences and procedures, not learned episodic facts.
- **Condensation summaries:** preserve conversation continuity within a task.

The final official feature index contains no durable recall/learning feature while successfully listing task history, skills, indexing, checkpoints, and condensation ([feature index](https://roocodeinc.github.io/Roo-Code/features/)). Searches for Roo `MEMORY.md`, “persistent memory,” and “long-term memory” returned no primary implementation documentation; the known-present control returned Task Todo and Skills. Thus Roo has **no documented cross-task semantic memory equivalent** to the owner’s basic-memory MCP. This is an absence of a public capability, not a claim that no internal persisted object ever contains prior text.

### Comparison

The owner’s basic-memory layer is strictly broader: it is cross-tool, semantically searchable, has proactive recall after compaction/resume, and requires temporal supersession metadata (`C:\Users\Prekzursil\.claude\CLAUDE.md:5-15`). The event ledger separately stores objective turn history. Claude Code also now has native auto memory and task persistence ([official memory guide](https://code.claude.com/docs/en/memory), [interactive task-list persistence](https://code.claude.com/docs/en/interactive-mode)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Nothing from Roo should replace basic-memory or the event ledger.

### Where Roo is worse

- Shared task-history storage is a coarse synchronization mechanism, not conflict-aware semantic memory.
- Task history and checkpoint state can reproduce prior conversation but do not proactively retrieve the right durable fact.
- Roo’s Qdrant index is for code blocks, not owner preferences/decisions, and it introduces a separate vector database.

## 4. Tool and MCP handling

### Built-in tools

Roo exposes read, edit, command, image, and workflow tools. It includes multi-file reads, several edit encodings, command-output recovery, `attempt_completion`, `new_task`, and skills ([How Tools Work](https://roocodeinc.github.io/Roo-Code/basic-usage/how-tools-work)). This is comparable to Claude Code’s native tools. The owner’s main issue is reliability, not breadth: Glob’s 13.32% failure rate and StructuredOutput’s 22.9% failure rate are empirical (`corpus.json:79-106`).

### MCP lifecycle

Roo’s MCP product surface is unusually concrete:

- Global `mcp_settings.json` plus project `.roo/mcp.json`, with project server names overriding global ([Using MCP, lines 54–73](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).
- STDIO, Streamable HTTP, and legacy SSE transports.
- Per-server `cwd`, environment, `disabled`, timeout from 1–3600 seconds, watched paths, and `disabledTools`; `${env:NAME}` interpolation avoids literal secrets ([Using MCP, lines 101–125 and 155–199](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).
- A global MCP enable toggle removes all MCP logic and definitions from the prompt when disabled, reducing token use ([Using MCP, lines 293–309](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).
- UI controls to restart/disable a server, adjust timeout, and independently “Always allow” each tool behind a global MCP auto-approve switch ([Using MCP, lines 335–373](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).
- Roo can scaffold a new MCP server, keep secrets in environment variables, add it to configuration, and attempt immediate connection ([Using MCP, lines 312–331](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).

### Comparison and ports

Claude Code already supports user/project/local MCP scopes, stdio and HTTP, OAuth, lazy tool-schema loading, `/mcp`, and exact MCP-tool permission rules. Per-tool allow/deny is **NATIVE (Claude Code already does this; we just enable it)**; cleaning configuration and denying dead tools is **CONFIG (settings/JSON only)**. Current Claude docs explicitly recommend disabling inactive MCPs because definitions consume context ([cost guide](https://code.claude.com/docs/en/costs)), and permissions can match individual tools ([permissions guide](https://code.claude.com/docs/en/permissions)).

The owner’s serious gap is health-state enforcement. Corpus evidence shows Tavily extraction was called 532 times, failed 137 times, and 135 failures were “not connected” (`corpus.json:9141-9148`). Roo at least surfaces a server toggle/restart/state panel; the owner’s agent could continue selecting a dead server.

#### Proposal — dead MCP quarantine

**Port assessment: CONFIG (settings/JSON only)** for immediately disabling/removing confirmed dead duplicate server entries. This must be done only in the build phase after resolving exact config provenance; this unit remains read-only.

**Port assessment: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for a generic health receipt: at SessionStart or first use, probe configured servers cheaply; mark `live/down/quota` with TTL; inject a short routing exclusion; after repeated connection-class failures, quarantine for the session and point to a live equivalent. Reuse the existing dispatcher/event ledger. Do not build an MCP manager daemon.

This is **very likely (80-90%)** to eliminate the measured “dead MCP still being called” class. Evidence is the deterministic `not connected` fingerprint repeated 135 times and the availability of SessionStart/PostToolUseFailure hooks. It will not fix schema mismatch or remote service failures.

#### Proposal — UNVERIFIED: per-server controls

**Port assessment: CONFIG (settings/JSON only)** for `disabled`/deny and environment-based startup timeout where Claude supports them. **UNVERIFIED — experiment:** inspect `claude mcp get <server>` and the current schema for whether a per-server call timeout, distinct from startup timeout, is supported in 2.1.214. If absent, use a small wrapper process only for the few servers that need a hard call timeout; do not generalize into a service.

### Where Roo is worse

- Roo had a prompt-injection-to-RCE path through project `.roo/mcp.json` when auto-approved writes could modify executable MCP configuration. It was patched in 3.20.3 by adding a separate opt-in for protected config writes ([GHSA-5x8h-m52g-5v54](https://github.com/RooCodeInc/Roo-Code/security/advisories/GHSA-5x8h-m52g-5v54)).
- Roo’s archived security page lists multiple high-severity auto-execution and command-validation advisories ([security advisories](https://github.com/RooCodeInc/Roo-Code/security)).
- Roo did not ship preinstalled servers; “marketplace” convenience did not mean verified health ([Using MCP, lines 376–383](https://roocodeinc.github.io/Roo-Code/features/mcp/using-mcp-in-roo/)).
- Roo’s own issue history includes MCP connection races after changing tool approval, illustrating that UI controls do not guarantee correct state ([issue #8468](https://github.com/RooCodeInc/Roo-Code/issues/8468)).

## 5. Permission model

### Roo’s model

By default every tool use is presented for explicit approval. Auto-approve can be toggled independently for reads, writes, allowed commands, browser use, MCP, mode switching, subtasks, and default follow-up answers ([Auto-Approving Actions, lines 99–150](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/)). Reads/writes outside the workspace require additional flags; `.roo/` and `.rooignore` are protected configuration unless separately opted in ([same page, lines 152–209](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/)). MCP auto-approval requires both a global switch and a per-tool “Always allow” ([same page, lines 227–250](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/)).

Command rules use allow and deny prefixes with longest-prefix specificity; equal or more specific deny wins. The docs enumerate dangerous defaults and add guards for parameter/process substitution ([same page, lines 273–320](https://roocodeinc.github.io/Roo-Code/features/auto-approving-actions/)). `.rooignore` blocks direct reads/writes/diffs and some known file-reading commands, hot-reloads, and cannot be edited by Roo itself ([rooignore, lines 62–115](https://roocodeinc.github.io/Roo-Code/features/rooignore/)).

### Comparison

Claude Code’s permission system is richer: deny → ask → allow precedence, path/tool/argument matching, plan/acceptEdits/auto/dontAsk/bypass modes, managed policy, and hook decisions ([official permissions](https://code.claude.com/docs/en/permissions)). The owner has deliberately set bypassPermissions, so Roo’s safe-by-default posture is better than the current local default, but the capability is not absent.

**Port assessment: NATIVE (Claude Code already does this; we just enable it)** for fine-grained tool/path permissions. **Port assessment: CONFIG (settings/JSON only)** if design chooses to replace `defaultMode: bypassPermissions` with a safer mode and explicit allow rules.

Changing the owner default is **roughly even (45-55%)** as a net productivity win without a workload replay. Evidence for safety is straightforward; evidence against is the owner’s high-autonomy intent and existing 35-rule allowlist. The settling experiment is a shadow replay of representative sessions under `auto` or `dontAsk + allowlist`, measuring prompts, blocks, task completion, and false denials. Do not change it from a teardown alone.

### Roo permission defects not to copy

1. **Queued messages implicitly approve the next pending action even when auto-approval is disabled.** Roo documents this as intentional and outside the auto-approval settings ([Message Queueing, lines 71–104](https://roocodeinc.github.io/Roo-Code/features/message-queueing/)). This violates least astonishment and collapses “I have more information” into “execute the pending mutation.” Do not copy.
2. **Experimental custom tools are automatically approved as soon as the feature is enabled.** They execute in-repo TypeScript/JavaScript with npm dependencies and no per-call approval ([Custom Tools, lines 44–60 and 99–115](https://roocodeinc.github.io/Roo-Code/features/experimental/custom-tools/)). Do not copy. Claude hooks/MCP permissions provide a safer bus.
3. `.rooignore` is not a sandbox and only recognizes a predefined set of file-reading shell commands ([rooignore, lines 107–115](https://roocodeinc.github.io/Roo-Code/features/rooignore/)). The abstraction leaks at the command boundary.
4. Direct `@file` and `@folder` mentions bypass `.rooignore` and `.gitignore` when fetching context, despite the general documentation describing `.rooignore` as affecting context mentions ([Context Mentions, lines 168–174](https://roocodeinc.github.io/Roo-Code/basic-usage/context-mentions/)). Explicit user provision may justify the bypass, but the rule is surprising.

## 6. Customization: rules, skills, modes, commands, tools, and hooks

### Rules

Roo supports global, workspace, and mode-specific rules. It recursively loads directory contents, orders them, gives workspace rules precedence, and supports AGENTS.md ([Custom Instructions, lines 64–120](https://roocodeinc.github.io/Roo-Code/features/custom-instructions/), [full combination/AGENTS.md behavior](https://roocodeinc.github.io/Roo-Code/features/custom-instructions/)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Claude Code has CLAUDE.md hierarchy, `.claude/rules` with path scoping, user/project settings, and instruction-load hooks. The owner already has an authoritative cross-tool AGENTS.md contract.

### Skills

Roo adopted the Agent Skills format. It reads only name/description for discovery, loads SKILL.md on match, and opens bundled resources on demand. Project overrides global; Roo-specific overrides cross-agent `.agents`; mode-specific overrides generic ([Skills, lines 62–89 and 245–273](https://roocodeinc.github.io/Roo-Code/features/skills/)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** This is already the owner’s strongest customization surface. The owner has 280 `.agents/skills` directories in the read-only inventory, while the pinned brief says roughly 355 installed but only 78 invoked. The problem is selection/quality/retirement, not missing skill packaging.

### Custom modes

A Roo mode packages role definition, `whenToUse`, tool groups, optional edit-file regex, custom instructions, and a sticky model. Modes can be global/project YAML, imported/exported with rules, and selected automatically by Orchestrator ([Custom Modes, lines 62–118 and 197–250](https://roocodeinc.github.io/Roo-Code/features/custom-modes/)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it)** for role, tool/model selection, isolation, and reusable definitions through custom subagents. **CONFIG (settings/JSON only)** for mapping high-value modes to existing agent definitions. Do not reproduce the mode picker in another runtime.

Roo’s sticky model per mode is convenient. Claude subagents can declare a model, which is more deterministic than “last used.” The owner already invokes planner, architect, security-reviewer, python-reviewer, and code-reviewer agents (`corpus.json:13351-13366`).

### Slash commands

Roo turns Markdown files into global/project slash commands with description, argument hint, and optional target mode ([Slash Commands, lines 62–95 and 123–166](https://roocodeinc.github.io/Roo-Code/features/slash-commands/)). `/init` performs multi-phase repository analysis and writes tailored agent rules ([Slash Commands, lines 463–489](https://roocodeinc.github.io/Roo-Code/features/slash-commands/)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Skills and native commands cover invoked workflows; Claude’s current `/init` also generates instruction configuration. Roo’s UI is pleasant, but not a new harness mechanism.

### Custom tools

Roo’s experimental `.roo/tools/*.ts` loader converts Zod to JSON Schema, transpiles with esbuild, provides mode/task context, and hot-reloads imperfectly ([Custom Tools](https://roocodeinc.github.io/Roo-Code/features/experimental/custom-tools/)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it)** through MCP, plugin tools, and hooks. A separate in-repo executable-tool loader is unnecessary and less safe. The owner already touched 93 MCP servers and has 99 enabled plugins in settings; adding another tool ABI would worsen discovery and reliability.

### Lifecycle hooks — Roo is materially worse

Roo exposes settings, rules, skills, modes, slash commands, MCP, and experimental tools, but no public general lifecycle hook bus equivalent to Claude’s SessionStart/PreToolUse/PostToolUse/Stop/TaskCompleted events. This absence is supported by both the controlled documentation index and controlled full-archive content scan described above.

Claude Code now exposes command, prompt, agent, HTTP, and MCP-tool hooks and a `/hooks` provenance browser ([hooks reference](https://code.claude.com/docs/en/hooks), [hooks guide](https://code.claude.com/docs/en/hooks-guide)). The owner config wires 18 event families. Roo therefore cannot implement the owner’s event ledger, cross-tool dispatcher, completion receipt enforcement, compaction checkpoints, goal re-injection, or guard discrimination at the same architectural layer.

No port is required; Roo is worse. The lesson is to make the existing hook bus reliable and observable, not to imitate Roo’s absence.

## 7. Multi-agent and orchestration

### Roo’s Boomerang model

Roo Orchestrator has no direct read/edit/command/MCP access. It creates a subtask in a specialized mode, **pauses**, waits for that child to finish, receives only the child summary, then resumes ([Using Modes, lines 107–113](https://roocodeinc.github.io/Roo-Code/basic-usage/using-modes), [Boomerang Tasks, lines 77–93](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks/)). Isolation protects parent context; explicit down/up handoffs are good. Approval is required for subtask creation/completion unless enabled.

This is nested task navigation, not coordinated concurrency. Roo’s worktree UI permits multiple independent Roo tasks in separate VS Code windows, but the user must create/open/manage those windows; there is no shared mailbox/task graph connecting them ([Worktrees, lines 62–70 and 127–150](https://roocodeinc.github.io/Roo-Code/features/worktrees/)).

### Comparison

Claude Code subagents and agent teams already provide separate contexts, parallel execution, automatic completion notifications, a shared task list with dependencies, and direct teammate messaging ([agents guide](https://code.claude.com/docs/en/agents), [agent teams](https://code.claude.com/docs/en/agent-teams)). Native worktree isolation supports subagents and `.worktreeinclude` ([worktrees guide](https://code.claude.com/docs/en/worktrees)). The owner’s corpus proves use, including 500 SendMessage calls.

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Roo’s explicit summary-only handoff is already reflected in the owner contract, which forbids passing raw subagent output as prefix context.

### Where Roo is worse

- The parent is idle while a child runs, so independent subtasks cannot overlap.
- Subtasks do not communicate laterally.
- There is no shared dependency graph or automatic work claiming.
- A summary is the sole returned truth, creating an evidence bottleneck. Roo’s final 3.48 release had to repair race conditions and state loss where parents became unresumable or stale after delegation ([3.48.0 release notes](https://roocodeinc.github.io/Roo-Code/update-notes/v3.48.0/)).
- Worktree parallelism is manual multi-window operation, not an orchestrator capability.

Roo’s forced isolation is nevertheless a good default: Orchestrator cannot fill itself with file reads. Our harness already achieves this through scoped agent roles and summary handoffs without sacrificing parallelism.

## 8. Verification and self-check mechanisms

### What Roo verifies mechanically

1. **Tool result/exit status.** Terminal integration observes exit codes and output.
2. **Diagnostic delta.** Before editing, Roo captures diagnostics; after editing it waits for the VS Code Problems state to update, detects only new errors, and reports them ([Diagnostics Integration, lines 62–89](https://roocodeinc.github.io/Roo-Code/features/diagnostics-integration/)).
3. **Todo completeness.** Optional `preventCompletionWithOpenTodos` blocks completion; `newTaskRequireTodos` can require a plan for delegated tasks ([Task Todo List, lines 150–186](https://roocodeinc.github.io/Roo-Code/features/task-todo-list/)).
4. **Checkpoints/diffs.** Every direct edit can be compared/restored.
5. **Debug-mode instructions.** Debug mode asks the model to narrow causes, add logs, and confirm before fixing ([Using Modes, lines 100–106](https://roocodeinc.github.io/Roo-Code/basic-usage/using-modes)). This is prompt guidance, not independent verification.
6. **Approval review.** Humans can inspect tool parameters and diffs before execution.

### What Roo does not provide

Roo does not document a mandatory test runner, evidence receipt schema, independent critic, mutation-aware verification policy, or lifecycle hook that can refuse a final answer based on missing evidence. Its completion tool signals model belief. Todo completion can still be self-reported incorrectly. The diagnostic delta covers language-server errors, not behavioral correctness, tests, security, or requirements.

The owner harness is broader: ClaimWarning runs at Stop/TaskCompleted and asks for recent objective evidence (`modules.py:2000-2137`). But it is also noisier and demonstrably wrong in some guard contexts. Pinned defect D1 shows four detector implementations confusing prose with executable occurrences; D2 records wrong conclusions from unvalidated probes; D3 says hook telemetry is unmeasurable (`INPUT-known-harness-defects.md:9-149`). Roo’s simple diagnostic delta is therefore worth copying even though Roo’s overall verifier is weaker.

### Proposal — UNVERIFIED: new-diagnostic receipt

**Port assessment: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On successful Edit/Write/MultiEdit, capture a baseline and post-edit diagnostic snapshot keyed by URI/range/code/severity; wait for a bounded IDE/LSP update; compute `introduced`, `resolved`, and `unchanged`; inject only introduced errors and write a terminal receipt. Scope it to files touched by the edit. Never infer “all clear” if the diagnostics provider was unavailable or stale.

This recommendation is headed **UNVERIFIED** because the premise that Claude Code 2.1.214 exposes VS Code diagnostics to a hook or stable local endpoint was not established. **Experiment:** in a disposable TypeScript fixture with one known compiler error, prove a detector can see the known-present diagnostic through the VS Code extension/LSP interface; edit a separate file to introduce a second known error; verify baseline vs post-edit delta and timestamps. If no stable endpoint exists, implement a language-specific command receipt (`tsc --noEmit`, linter) for selected ecosystems rather than screen-scraping Problems.

If the endpoint exists, the mechanism is **likely (55-80%)** to catch a useful class of edit regressions with low noise. Evidence is Roo’s exact before/after design and the mechanical signal from language servers. The range is not higher because diagnostics can be delayed, project-wide, or incomplete, and because the owner already has false-positive guard debt.

### Proposal — UNVERIFIED: open-task completion invariant

**Port assessment: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At TaskCompleted and final Stop, query the native TaskList. If tasks owned by the current goal remain `pending` or `in_progress`, return a typed non-complete receipt and list ids/subjects. Allow explicit cancellation/de-scope and distinguish blocked tasks from forgotten work. Do not use prose regex.

Claude Code supports blocking TaskCompleted with exit code 2 and feeding the reason back to the model ([hooks reference](https://code.claude.com/docs/en/hooks)); the owner already routes TaskCompleted at `settings.json:458-468`. This is **very likely (80-90%)** to be cheaper and more precise than completion-language regex for forgotten work because it reads structured task state. It does not replace evidence checking: a model can incorrectly mark a task completed.

**UNVERIFIED — experiment:** confirm the TaskCompleted hook input or an accessible TaskList snapshot identifies sibling/open tasks and goal ownership. If the hook sees only the completing task, maintain the task projection from TaskCreated/TaskCompleted ledger events and validate it against a known task list before enforcing.

## 9. Codebase indexing: the tempting feature to reject

Roo parses code with Tree-sitter, embeds semantic blocks, stores vectors in Qdrant, and exposes `codebase_search` ([Codebase Indexing, lines 62–75](https://roocodeinc.github.io/Roo-Code/features/codebase-indexing/)). It requires an embedding provider and Qdrant cloud or Docker; credentials may be stored in VS Code secret storage ([same guide](https://roocodeinc.github.io/Roo-Code/features/codebase-indexing/)).

This is a real capability the owner’s harness does not natively reproduce as a local universal code index.

**Port assessment: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Explicitly rejected. It reintroduces the anti-overfit gate’s forbidden vector-DB/KG memory component, adds indexing freshness, embedding compatibility, secret, daemon, and Windows lifecycle failure modes, and competes with fast lexical/symbol search plus model reasoning. The corpus already shows Glob’s failure is environmental path inflation, not insufficient semantic retrieval; fix the 592 ENAMETOOLONG cases before building a parallel search stack.

It is **very likely (80-90%)** that a universal Qdrant index would add more operational burden than measured benefit for this owner. Evidence: the anti-overfit prior, existing high use of native search, the known orphan-directory root cause, and Roo’s own need for a separate database/service. A narrowly scoped evaluation could overturn this only if a benchmark of real owner queries shows a large retrieval-quality gain after fixing native search reliability.

## 10. Checkpoints and worktrees: do not rebuild what became native

Roo’s checkpoint design is technically concrete: a separate shadow Git repository, snapshots at task start and before direct file edits, structured diffs, and restoration of files only or files plus conversation ([Checkpoints, lines 62–110 and 126–167](https://roocodeinc.github.io/Roo-Code/features/checkpoints/)). It excludes build/media/cache/secret/large files, respects `.gitignore` and LFS, and disables itself for nested Git repositories ([same guide, lines 204–243](https://roocodeinc.github.io/Roo-Code/features/checkpoints/)). It does not checkpoint before commands.

Claude Code now natively checkpoints every prompt/edit, persists checkpoints with sessions, and supports rewind of code/conversation/summary; it likewise does not capture Bash mutations ([official checkpointing](https://code.claude.com/docs/en/checkpointing)).

**Port assessment: NATIVE (Claude Code already does this; we just enable it).** Do not copy the shadow Git service. It is heavier, disables on nested repositories, can overwrite unsaved work, and uses hard reset internally. Use native checkpointing and ordinary Git/worktrees for durable branches.

Roo’s `.worktreeinclude` mechanism is now also native in Claude Code, including subagent isolation and cleanup ([Claude worktrees](https://code.claude.com/docs/en/worktrees)). The owner config already has WorktreeCreate/Remove hooks (`settings.json:506-543`). **Port assessment: NATIVE (Claude Code already does this; we just enable it).** No gap remains.

## 12. What not to copy, in one place

1. **Do not copy a discontinued runtime.** Roo’s extension was shut down and repository archived on 2026-05-15.
2. **Do not copy sequential-only orchestration.** Summary isolation is good; parent-pauses-child is weaker than native parallel subagents/teams.
3. **Do not copy implicit approvals.** A queued message must never silently approve a pending write/command.
4. **Do not copy auto-approved in-repo executable tools.** Project source is an untrusted boundary; permissions must remain explicit.
5. **Do not copy Qdrant code memory.** It violates the anti-overfit gate absent benchmark evidence.
6. **Do not copy shadow Git checkpointing.** Claude now provides native rewind; ordinary Git remains the durable history.
7. **Do not treat diagnostics as correctness.** New-error delta is one receipt, not proof of behavior, requirements, or security.
8. **Do not imitate mode proliferation.** The owner already uses only a fraction of installed skills. New personas without measured routing demand increase prompt/discovery surface.
9. **Do not copy prefix-only command safety as the main guard.** Roo’s history of shell-validation advisories shows how hard shell semantics are. Prefer native parsed permissions, exact tool identity, and narrowly scoped hooks.
