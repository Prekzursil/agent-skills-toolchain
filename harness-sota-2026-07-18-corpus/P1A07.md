# P1A07 — Owner-correction axis: triage, real clusters, and harness implications

**Unit:** P1A07  
**Date:** 2026-07-18  
**Axis:** `owner_correction_candidates` in `corpus/corpus.json`  
**Subject policy:** read-only. This unit changed no harness, repository, settings, MCP configuration, transcript, or plugin. Its only durable work product is this report (plus the event-ledger entries required by the governing `AGENTS.md`).

## Executive conclusion

The corpus's **2,268 is not a count of owner corrections**. It is the number of top-level user-role strings under 4,000 characters that contain any of about twenty broad tokens, including `no`, `stop`, `again`, `actually`, and `don't`. The detector itself says that it is recall-biased (`mine.py:56-63`, `mine.py:424-435`). Raw-record provenance proves that most hits are not human turns:

| Mutually exclusive provenance class | Pre-cutoff raw hits | Share of 2,269 rescan hits | What it means |
|---|---:|---:|---|
| `isMeta:true` | 1,074 | 47.3% | Hook feedback, scheduled monitor prompts, peer/system traffic, and other metadata turns |
| `origin.kind:"task-notification"` (not already meta) | 429 | 18.9% | Background-task notifications wearing the user role |
| `promptSource:"sdk"` (not already above) | 52 | 2.3% | Agent/SDK-authored prompts, not owner typing |
| `promptSource:"typed"` | 283 | 12.5% | Conservative human-typed stratum |
| `origin.kind:"human"` with queued source | 40 | 1.8% | Human-origin queued prompts |
| queued, origin absent | 23 | 1.0% | **Likely (55-80%)** human because `promptSource` is `queued`, but legacy origin is absent; a queued-prompt control would settle it |
| provenance fields absent | 368 | 16.2% | Legacy unknown; contains both genuine corrections and synthetic traffic |
| **Total in raw cutoff rescan** | **2,269** | **100%** | One more than the frozen corpus count; see boundary note below |

Two mechanically independent signals support the false-positive conclusion:

1. **Raw metadata:** a known genuine turn has `promptSource:"typed"`, `isSidechain:false`, and no `isMeta` (`09158d9e-...jsonl:3970`); a task notification has `promptSource:"system"` and `origin.kind:"task-notification"` (`09158d9e-...jsonl:4511`); stop feedback and a scheduled monitor turn have `isMeta:true` (`09158d9e-...jsonl:5157`; `c5980bb4-...jsonl:19299`).
2. **Content envelopes:** 1,698/2,269 hits match independently recognizable non-owner forms—`Stop hook feedback:`, `<task-notification>`, `Another Claude session sent a message:`, monitor ticks, tool probes, security-review prompts, continuation summaries, and polling prompts. The control is positive: this content detector finds the known-present 961 stop-feedback records and 428 pre-cutoff task-notification records before it is used to claim other records are absent.

The owner's most frequent **real** corrections are, in priority order:

1. **The delivered result is broken, regressed, or not actually working.**
2. **The agent acts on the wrong target, state, interpretation, or already-corrected requirement.**
3. **The agent omits scope/capabilities, drifts from the whole goal, or silently narrows effort.**
4. **The agent violates an explicit constraint, including destructive/safety-sensitive constraints.**
5. **The agent stops, defers, or asks to postpone despite an active terminal condition.**
6. **The interaction loses state across interruptions or fails to expose the operational UI/status needed to continue.**

This ordering is **very likely (80-90%)**, because it is consistent across (a) exact high-precision typed-turn rule counts, (b) a 90-interaction manual audit, and (c) decisive raw transcript excerpts. The precise population frequencies are **UNVERIFIED; a blinded adjudication of all 242 typed identities plus all 391 provenance-unknown/queued identities would settle them**. The corpus does not contain an owner-authorship label or a correction label, so it cannot support an exact number of real corrections by itself.

The central harness design implication is not “add a smarter critic.” It is much smaller: preserve the current native hook/event bus, correctly distinguish human prompts from metadata/system prompts, coalesce repeated feedback into episodes, and re-anchor explicit corrections and acceptance criteria until verified. That passes the anti-overfit gate: no second orchestration runtime, vector database, durable-execution engine, trained critic, observability SaaS, or guardrail framework is needed.

## 1. What the corpus can and cannot establish

### 1.1 Corpus coverage is strong; correction precision is not

`corpus.json` reports 11,633 files seen, zero files failed, 1,564,084 lines, one bad line, 32 oversized lines, and 10.62 GB scanned (`corpus/corpus.json:1`). This makes corpus-level *presence* evidence strong. It does not make the correction classifier accurate.

The detector implementation is explicit:

- `CORRECTION_PAT` matches `no|nope|wrong|incorrect|actually|instead|don't|do not|stop|...|again|redo|...` anywhere in a message (`mine.py:56-63`).
- It excludes list-valued tool-result envelopes, sidechains, and a short list of tag-prefixed synthetic turns (`mine.py:288-305`).
- It retains only 120 normalized repeated patterns and the first 400 samples (`mine.py:428-435`).
- The comments acknowledge that the regex “favours RECALL” and that triage is the consumer's job (`mine.py:424-427`).

The result has three separate biases:

1. **Lexical bias.** A new task saying “do not use X,” an owner changing their mind with “actually,” a pasted review containing “wrong,” or a monitor prompt saying “do not run WSL” all match.
2. **Role-envelope bias.** Claude Code stores hooks, scheduled prompts, task notifications, peer messages, and SDK prompts as user-role records. `isSidechain:false` is therefore necessary but not sufficient.
3. **Sampling bias.** The 400 samples are the first matches encountered in path-sorted traversal, not a random or stratified sample. A single hot session supplies a large tail of the sample list.

### 1.2 Frozen-corpus count versus raw rescan boundary

The frozen corpus says 2,268 candidates out of 8,441 owner-role messages (`corpus/corpus.json:1`). A read-only raw rescan completed under `longrun` with `SUCCESS:p1a07-extract` and found 2,272 current candidates. Three have timestamps after the corpus file's 2026-07-18 20:14:46 local write time (17:14:46Z), leaving 2,269 at the cutoff. The one-record difference is **almost certain (90-99%)** to be a concurrent-write boundary effect: the miner walks mutable JSONL files sequentially, while the corpus file timestamp is only the final output timestamp; the evidence is the one-record delta and three clearly post-cutoff timestamps. The experiment that would settle the last record is to snapshot the transcript tree and rerun both miners against the immutable snapshot.

For all corpus totals, this report treats **2,268 as authoritative**. For provenance and context ratios, it reports the 2,269 cutoff rescan and makes the denominator visible. Nothing material changes at a one-record delta (0.044%).

### 1.3 The 524-hit “top correction” is one runaway feedback episode, not 524 owner corrections

The corpus's largest normalized pattern is:

> “Stop hook feedback: please do it 100% with both ghidra, binary and ida, as you said for all 100% coverage and do not stop” — 524 hits (`corpus/corpus.json:1`).

Raw samples place those repeats in the same transcript, `aeb94ff3-639d-48d8-b24a-6f3ee9650c46.jsonl`, seconds apart. The raw provenance class is `isMeta:true`, not a typed human prompt. Therefore:

- **Raw detector frequency:** 524.
- **Human correction-event frequency:** 0 demonstrated by these records.
- **Distinct feedback episode:** 1 runaway episode.
- **Underlying owner preference is UNVERIFIED:** persistence/completeness is consistent with the text, but its origin is not recoverable from these repeated records alone; locating the stop-hook configuration that produced the text would settle it.

It is **almost certain (90-99%)** that counting the 524 repeats as 524 owner corrections would invert the result, because the metadata flag and the seconds-apart same-session sequence independently identify machine repetition. The hook content remains useful as weak corroboration that persistence was configured, but not as frequency evidence.

## 2. Triage method

### 2.1 Grain

I used three grains, because each answers a different question:

1. **Raw hits:** compatible with the frozen corpus count.
2. **Timestamped interaction identity:** deduplicate exact `(body, timestamp)` pairs, which removes branch/file duplication while preserving a genuinely repeated owner message at a later time.
3. **Episode:** collapse rapid identical meta feedback in one session. This prevents one feedback loop from dominating owner preferences.

The 283 typed raw hits reduce to **242 typed timestamped identities**, 239 exact bodies, across 22 transcript files. The 571 lexical-residual raw hits reduce to 510 identities. Branch duplication is real: many exact messages and timestamps appear in two transcript files.

### 2.2 Provenance tiers

The triage uses a conservative tier, not a forced binary label:

- **SYNTHETIC:** `isMeta:true`, task-notification origin, SDK source, peer/monitor/probe envelope, or another mechanically demonstrated machine form.
- **HUMAN-TYPED:** `promptSource:"typed"`; this is the conservative analysis stratum.
- **HUMAN-QUEUED:** `origin.kind:"human"` with queued source; counted separately so typed-only results remain reproducible.
- **LEGACY-UNKNOWN:** provenance fields absent. A legacy record can be a real owner correction (for example, several `why did you stop` turns in the April SWFOC transcript) or old synthetic traffic. It is not silently assigned either way.

### 2.3 Semantic adjudication

A human-authored candidate counts as a **real harness/agent correction** only when the text and preceding interaction show that the owner is correcting an agent output, behavior, interpretation, omission, or continuation decision. I excluded:

- a new task that merely contains a negative constraint;
- the owner changing their mind or supplying new facts;
- an owner answering an agent's explicit option/question;
- a report that an external website or game independently failed, unless it corrects a change or claim made by the agent;
- pasted agent prompts/reviews;
- API authentication/rate-limit interruptions that the agent did not choose;
- machine-generated feedback in the user role.

This distinction matters. “Actually, use account B” is a revision; “I meant the old toolkit, not the one you are working on” is a correction; “the website is down” is environment state; “you broke the timer and altar” is an agent-caused regression.

### 2.4 Manual audit and uncertainty

I manually reviewed 90 timestamped interactions with preceding assistant context:

- **30 high-signal/direct-rule interactions:** 20 were attributable corrections (66.7%; Wilson 95% interval 48.8-80.8%).
- **60 randomly selected typed interactions outside the direct rules:** 32 were attributable corrections (53.3%; Wilson 95% interval 40.9-65.4%).

Applying those stratum rates to 61 direct-rule typed identities and 181 other typed identities yields an **UNVERIFIED estimate of about 137 real corrections among 242 typed identities (plausible interval from the two Wilson bounds: about 104-168); a blinded full-label pass over all 242 would settle it**. This estimate is **likely (55-80%)**, not higher, because the sample is reproducible but semantic attribution remains a human judgment and several long prompts quote prior agent text.

I do **not** extrapolate that estimate into the 368 legacy-unknown records. Their provenance distribution differs, and doing so would manufacture a corpus-wide total. The corpus therefore cannot answer “exactly how many of 2,268 are real?” It can answer the ranked failure modes and provide defensible minimum counts in the typed stratum.

## 4. Cross-cluster interpretation

### 4.1 What the owner most often has to restore

Across clusters, the owner repeatedly restores four invariants:

1. **Reality:** “it does not work,” “it only copies one file,” “it crashes,” “the stages look broken.”
2. **Referent:** the correct repo, game state, account, private design system, target file, or prior decision.
3. **Completeness:** all requested scope, relevant capabilities, documentation, tests, and terminal conditions.
4. **Boundaries:** do not delete/reset/share/stop; do not silently narrow or defer.

This is more useful than treating every correction as a prompt-writing problem. The recurring failure is loss of an executable task contract: target + constraints + observable acceptance + terminal condition.

### 4.2 Where severity concentrates

The most severe corrections arise after mutation, not during planning. Battle Cats changes regressed timers/stages; file-management work prompted “do not delete the installers”; operational automation risked stopping active work. It is **very likely (80-90%)** that pre-mutation constraint checks plus post-mutation acceptance checks have more value than adding general prose reminders, because the raw corrections name concrete state transitions and observed failures. A shadow-mode A/B experiment on 50 mutation tasks would settle the effect size.

### 4.3 What not to infer

- The data does **not** prove that the owner corrected the agent 2,268 times.
- The data does **not** prove that persistence is the most frequent real correction; one runaway meta episode makes it look that way in raw counts.
- The data does **not** establish a global owner preference from a single product-heavy transcript. Candidate-bearing sessions are concentrated: 2,269 hits occur in only 87 transcript files, and typed hits in 22.
- The data does **not** distinguish an agent's chosen stop from authentication/rate limits without reading predecessor context.
- The data does **not** show that hooks did not fire. The corpus hooks section is explicitly broken/no-data, and this analysis did not use it.
- The data does **not** support a trained correction classifier. There are no gold labels; the manual labels in this unit are an audit sample, not a training set.

## 5. Proposals

### Proposal 1 — Correction miner v2 with provenance tri-state — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Change the existing corpus miner, not the runtime:

1. If `isMeta:true`, classify `synthetic_meta` and do not count it as owner-authored.
2. If `origin.kind:"task-notification"`, classify `synthetic_task_notification`.
3. If `promptSource in {"system","sdk"}`, classify `synthetic_system` unless a documented exception exists.
4. If `promptSource:"typed"` or `origin.kind:"human"`, classify `human_candidate`.
5. If provenance fields are absent, classify `legacy_unknown`; never silently count it as human.
6. Preserve `file`, physical JSONL line, timestamp, preceding assistant UUID/type, and a normalized episode fingerprint.
7. Report raw hits, human candidates, legacy unknowns, and coalesced episodes separately.

This would remove at least 1,555/2,268 (68.6%) mechanically demonstrated non-owner hits from the human-candidate headline. That effect is **almost certain (90-99%)** because it is arithmetic over raw provenance fields; an immutable-snapshot rerun is the settling test. It remains deliberately recall-preserving for legacy records.

Anti-overfit gate: passes. It is a small change to the existing miner and adds no runtime component.

### Proposal 2 — Stop-feedback episode coalescing and repeat fuse — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Fingerprint stop feedback after number/path normalization, store `(session, fingerprint, first_seen, repeats)`, and inject the same feedback at most once per assistant attempt or once per bounded time window. On repeated identical stop outcomes, emit a terminal `FAILED:<id> repeated_feedback=<n>` diagnostic instead of re-injecting indefinitely.

It is **almost certain (90-99%)** that this would collapse the observed 524-record runaway sequence to one episode plus a repeat count, because all 524 share the normalized text and session. A replay of that transcript through the coalescer settles it deterministically. This proposal does not assert that the underlying task would finish; it prevents telemetry inflation and context churn.

Anti-overfit gate: passes. This is hook-local state/fingerprinting, not durable execution or a second orchestrator.

### Proposal 3 — Typed correction re-anchor in shadow mode — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED

On a provenance-confirmed typed human turn containing high-precision correction forms (`I meant`, `not the X`, `you got that wrong`, `do not delete/reset/stop`, `still doesn't work`, `you forgot/missed`), extract a compact task-contract delta:

```text
target_changed: ...
constraint_added: ...
acceptance_failed: ...
terminal_condition_reaffirmed: ...
source: session/file/line
```

Inject that delta once on the next action/stop decision and retire it only after the agent explicitly reports the observable acceptance result. Do not block and do not infer a correction from meta/system prompts.

The premise that a hook can access the same provenance fields at prompt time is **UNVERIFIED; a two-turn control experiment with one typed prompt, one queued human prompt, one task notification, and one stop-hook injection would settle it**. The recommendation inherits the tag because routing depends on that premise. If prompt-time provenance is unavailable, record the delta in the existing event ledger after transcript persistence instead of guessing live.

It is **likely (55-80%)** to reduce wrong-target and omitted-constraint recurrences, because those clusters explicitly repeat already-supplied information across 8 and 5 typed transcript files respectively. The settling experiment is a 50-task shadow run comparing re-anchors to subsequent owner correction rate, with no blocking enabled.

Anti-overfit gate: passes. It uses the existing hook and event-ledger buses; no vector/KG memory, critic model, or new service.

### Proposal 4 — Make observable acceptance and negative constraints first-class task fields — CONFIG (settings/JSON only)

Add a concise behavior rule to the shared contract:

> Before mutating, restate the exact target and all explicit negative constraints. After mutating, verify the owner's observable acceptance condition. A unit/static pass is not evidence that a live/UI outcome works. If the owner reports a regression, stop expanding scope, preserve/recover state, form a falsifiable hypothesis, and test the failed observation.

This is not a new planner. It tightens the existing goal/terminal-condition contract around the two highest-damage fields. It is **likely (55-80%)** to reduce some broken-result and ignored-constraint corrections, based on 17 and 7 conservative typed direct identities; a shadow audit of whether agents state and verify these fields across 50 mutation turns would settle adoption and effect.

Anti-overfit gate: passes. Configuration only.

### Proposal 5 — Preserve terminal conditions across ordinary stops, but distinguish external blockers — CONFIG (settings/JSON only)

Clarify the existing terminal-condition rule with a cause split:

- Agent-chosen defer/stop while safe in-scope work remains: continue.
- Authentication, rate limit, session cutoff, missing authority, or unsafe operation: report the concrete blocker and a resumable next action; do not pretend persistence can overcome it.
- A repeated stop-hook message is not new owner input and must not reset progress.

It is **likely (55-80%)** to reduce false “why did you stop” moments without encouraging infinite retries, because raw predecessor context shows both agent-chosen deferrals and 401/rate-limit stops. A replay review of all legacy `why did you stop` episodes, labeled by predecessor cause, would settle the cause proportions.

Anti-overfit gate: passes. Configuration only; it explicitly avoids durable-execution machinery.

## 6. Rejected alternatives and dead ends

### 6.1 “Just use the top patterns” — rejected

The top 120 normalized patterns sum to only 1,120 of 2,268 hits, and their largest count is a machine loop. They are useful for locating hot forms, not estimating human frequency.

### 6.2 “The first 400 samples are enough” — rejected

They are path-order samples, not random. They overrepresent probe sessions early in traversal and the 524-repeat SWFOC feedback session late in the retained sample. The corpus warning that 41/41 smoke samples were false positives was correct, but it does not quantify the residual precision.

### 6.3 “Require `promptSource:typed` and call the rest false” — rejected

That would be precise for newer records but would erase genuine legacy corrections. The April SWFOC `why did you stop` messages have incomplete provenance. A tri-state `legacy_unknown` is the honest solution.

### 6.4 “Train a classifier/critic” — rejected by evidence and anti-overfit gate

There is no gold-label set, and provenance fields solve most of the problem mechanically. It is **almost certain (90-99%)** that a learned critic would add maintenance and opacity, because it introduces a trained component and evaluation lifecycle where deterministic provenance already removes at least 68.6% of hits; a provenance-filter benchmark against a trained classifier would settle whether the extra component adds material precision/recall.

### 6.5 Longrun invocation dead end
