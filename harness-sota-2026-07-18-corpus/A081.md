# A081 — coherence audit of `~/.claude/rules/web/security.md`

## Executive result

The audited rule is not coherent enough to remain unchanged. I found **nine harness collisions**: one contradiction, two redundancies, four unenforced policy groups, one unruled enforcement, and one stale scope claim. I also found four standards-level stale/incomplete statements that make the rule a poor enforcement specification even before hooks are considered. The highest-impact defects are:

1. `web/security.md` narrows the common rule's rate-limiting requirement from “all endpoints” to “submission endpoints,” with no risk model explaining the different threshold.
2. The rule claims to extend `common/security.md`, but five of its own file classes (`.css`, `.scss`, `.html`, `.vue`, `.svelte`) are outside the common file's frontmatter, so the claimed inherited floor is not loaded for those turns.
3. None of the active hook census, active settings registrations, shared dispatcher manifest, or per-edit implementation enforces CSP, HTML-sink safety, SRI, security headers, CSRF, endpoint throttling, or the quarterly audit cadence. This is **almost certain (90-99%)** for the unpacked configuration because two mechanically independent detectors found zero relevant controls and found known-positive controls; live Windows behavior remains **UNVERIFIED — the settling experiment is to run one instrumented Edit on a fixture containing an unsafe HTML sink and one Stop on a fixture with failing header/CSRF acceptance tests, then capture every hook decision and context injection**.
4. The current nonce-only CSP instruction is inapplicable to static HTML, and the sample confuses `frame-src` with clickjacking protection by omitting `frame-ancestors`.
5. Credential-file reads are declaratively denied even though no inherited security rule says they are forbidden and the dedicated credential hook says the block is deliberately opt-in/off by default.

The recommended direction — **CONFIG (settings/JSON only)** — is replacement of this 69-line checklist with a short, testable, risk-scoped rule: retain always-on sink/input invariants, select nonce versus hash CSP by rendering model, require project-owned security acceptance commands, and remove cadence and deployment claims that the harness cannot observe. This is **very likely (80-90%)** to improve coherence because it eliminates every verified rule-to-rule conflict and maps each remaining “must” to observable evidence; the exact effect on live compliance is **UNVERIFIED — settle it with a 20-task before/after fixture evaluation covering static SPA, SSR, API-only TypeScript, and component-library edits**.

## Standards-level stale/incomplete content

These are not additional harness-to-harness collisions, but they determine whether the rule is “badly written, wrong, or unenforceable.” They should be fixed in the same replacement.

### S1 — STALE: nonce-only CSP conflicts with static delivery

`web/security.md:21-23` mandates a per-request nonce. MDN's current CSP implementation guidance says nonces fit dynamically generated content and hashes fit static content: <https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/CSP>. OWASP likewise notes that nonces require non-static HTML: <https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html>.

**Specific resolution — CONFIG (settings/JSON only).** State “use a nonce-based strict CSP for dynamically rendered HTML; use a hash-based strict CSP for static HTML; roll out with Report-Only and project-specific sources.” This is **almost certain (90-99%)** to be more accurate because it follows the rendering distinction in both current sources.

### S2 — STALE: `frame-src 'none'` is not clickjacking protection

The sample uses `frame-src 'none'` (`web/security.md:26-36`) and separately lists `X-Frame-Options: DENY` (`:56-62`) but omits CSP `frame-ancestors`. MDN explicitly distinguishes them: `frame-src` governs frames the page loads; `frame-ancestors` governs who may embed the page: <https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors>. OWASP says `frame-ancestors` supersedes X-Frame-Options in supporting browsers: <https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html>.

**Specific resolution — CONFIG (settings/JSON only).** Add `frame-ancestors 'none'` (or a project-specific allowlist), retain X-Frame-Options only as legacy defense in depth, and keep `frame-src` only if outbound embedded frames are actually forbidden. This is **almost certain (90-99%)** to correct the semantic error because the directives control different directions of framing.

### S3 — STALE: SRI requirement omits cross-origin/CORS mechanics

`web/security.md:47-52` says to use SRI for CDN assets but does not mention immutable asset versions, the `integrity` value, or `crossorigin`. MDN states that cross-origin SRI requires CORS and the `crossorigin` attribute: <https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity>.

**Specific resolution — CONFIG (settings/JSON only).** Require pinned immutable CDN URLs plus `integrity` and `crossorigin="anonymous"` where the provider supplies appropriate CORS; otherwise self-host or use another trusted delivery path. This is **almost certain (90-99%)** to prevent a non-working/incomplete SRI prescription because it includes the browser precondition.

### S4 — STALE/badly scoped: unconditional HSTS preload boilerplate

`web/security.md:54-62` presents `max-age=31536000; includeSubDomains; preload` without a deployment precondition. MDN documents that `includeSubDomains` covers every subdomain and that preload has minimum/max-age and subdomain requirements: <https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security>. The target itself warns not to cargo-cult only the CSP block (`:38`), not the header block.

**Specific resolution — CONFIG (settings/JSON only).** Qualify HSTS by deployed domain readiness; use `includeSubDomains`/`preload` only after verifying every present and future subdomain is HTTPS-capable and the operator intentionally accepts preload lifecycle constraints. Add the same “adapt and test” warning to the header example. This is **almost certain (90-99%)** to reduce outage risk because it makes the header's domain-wide effect explicit.

## Replacement shape

### Proposal R1 — CONFIG (settings/JSON only): replace the checklist with a testable rule

The replacement should contain only:

1. **Applicability:** distinguish browser-rendered application, static site, component library, browser extension, and API-only TypeScript. Do not demand production response headers from a library file merely because it is `.ts`.
2. **Always-on sinks:** framework auto-escaping; no raw HTML bypass without a named sanitizer and a justification; contextual output encoding; server-side validation at trust boundaries. MDN confirms front-end validation is bypassable and server validation is required: <https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Input_validation>.
3. **CSP by rendering model:** strict nonce CSP for dynamic HTML, strict hash CSP for static HTML, project-specific allowlists only as fallback, Report-Only rollout, `frame-ancestors`, `form-action`, `object-src`, and `base-uri` as applicable.
4. **Third-party execution:** minimize, inventory owner/purpose, pin immutable version, SRI+CORS where applicable, self-host when risk/operations justify it; review on addition/update rather than an untracked calendar promise.
5. **Server acceptance:** project-owned checks for actual response headers, CSRF on applicable state-changing authenticated requests, server validation, and risk-based throttling.
6. **Evidence:** name the command/test/output that establishes each production claim. If the current turn cannot observe deployment, say so rather than claim completion.

This replacement is **very likely (80-90%)** to outperform incremental wording edits because the current rule mixes source-level, deployment-level, supply-chain, and operational cadence claims without applicability or evidence boundaries. It remains **UNVERIFIED — the settling evaluation is the 20-task multi-archetype A/B test named in the executive result**.

### Proposal R2 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): one adapter, project-owned checks

If mechanical enforcement is desired, add one thin adapter to the existing verification bus. It should discover only an explicit repository declaration (for example, a named security acceptance command), execute it with the existing long-operation/terminal-state conventions, and pass through structured results. It must not scan prose or invent framework policy. This is **likely (55-80%)** to provide useful enforcement without harness overfit because detection remains owned by project-native analyzers/tests, while the harness only routes evidence. **UNVERIFIED — settle it with the fixtures specified in C5/C6 and measure false positives, missed seeded defects, runtime, and abandonment.**
