**Remote constraint:** the Windows host and its live `~/.agents/state`, transcripts, scheduled tasks, and OpenTelemetry endpoint were not available. ## Verdict

Build a **session measurement spooler, not a second benchmark runtime**. The shared lifecycle dispatcher already runs on both Claude and Codex and already appends one sanitized terminal record per dispatch. Add correlation and compact per-module signals to that record, create one session row at `SessionStart`, checkpoint a summary at each main-agent `Stop`, and finalize it at Claude `SessionEnd`. Store the current summaries in a local SQLite database plus bounded JSONL diagnostic logs. Do not parse 10.62 GB again, do not put a model judge in the loop, and do not require Prometheus, an OpenTelemetry Collector, a vector database, or an observability SaaS.

This is **very likely (80-90%)** to produce a useful, current operational baseline within one implementation week because the dispatcher, normalized session/turn/tool identities, terminal latency record, atomic-write helper, hook registration generator, and shadow sink already exist at `/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:235-338,485-513`, `models.py:26-39`, `storage.py:10-24`, `registration.py:17-53,144-170`, and `modules.py:336-386`. The uncertainty is Windows concurrency and tail latency, not architectural reach; the settling experiment is the staged Windows overhead and concurrency protocol in “Acceptance tests.”

The design deliberately does **not** claim that a session was successful. Automatic telemetry can establish execution, failures, latency, retries, interventions, fresh verification receipts, and later owner corrections; it cannot establish semantic task success without a task-specific oracle or owner label. NIST’s AI RMF likewise calls for repeatable TEVV with uncertainty and benchmark comparisons, rather than an unexplained scalar score ([NIST AI RMF Core, Measure](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

## 2. Measurement contract: what one session emits

Never emit prompts, command bodies, tool arguments/results, assistant prose, file contents, absolute paths, credentials, or raw session IDs. Emit hashes and bounded categorical/numeric fields only. This matches the OpenTelemetry GenAI warning that tool arguments and results can contain sensitive content ([OpenTelemetry GenAI attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)).

Each session snapshot has these groups:

| Group | Required fields | Why it exists |
|---|---|---|
| Identity/config | `schema_version`, `bench_version`, `session_hash`, `segment`, `provider`, `start_source`, `model`, `config_hash`, `mode_hash`, `started_at`, `updated_at`, `end_reason`, `finalized` | Separate model/harness/config changes; never merge unlike profiles. `session_hash = sha256(provider + NUL + session_id)[:24]`; the source UUID is not stored. |
| Coverage/data quality | `start_seen`, `checkpoint_seen`, `session_end_seen`, `events_seen`, `parse_errors`, `spool_replays`, `terminal_offset_start/end`, `stale_open`, `detector_control_pass` | Makes missing telemetry visible. A zero with `detector_control_pass=false` is unknown, not absence. |
| Host activity | prompt count; tool calls by categorical tool name; explicit tool failures; unknown outcomes; subagent starts/stops; compactions; permission denials; total native `duration_ms` where supplied | Maintains the corpus’s high-value tool reliability baseline without content capture. Claude documents successful `PostToolUse` separately from `PostToolUseFailure`; Codex documents that Bash non-zero exits can still arrive in `PostToolUse`, so Codex ambiguous outcomes must remain `unknown`, never be coerced to success ([Claude hooks](https://code.claude.com/docs/en/hooks#posttooluse), [Codex PostToolUse](https://developers.openai.com/codex/hooks)). |
| Harness activity | dispatcher events/success/fail-open; action counts; reason counts; failed modules; per-module non-allow fires; shadow fires; injected-context characters; latency histogram | Answers “did the guard run, fire, block/inject, fail, and cost how much?” without persisting injected text. |
| Evidence/outcome proxies | fresh verification receipt count, stale/missing receipt warnings, repeated-no-progress fires, completion-claim warnings, owner-follow-up/correction label if later attached | Keeps executable evidence separate from semantic success. The correction field starts `unknown`; the pinned candidate detector warns that its smoke sample was 41/41 false positives (`corpus.json`, `owner_correction_candidates.precision_warning`). |
| Resource use | input/output/cache token and cost counters when the host supplies them; otherwise `null` plus `source_available=false` | Missing is not zero. Claude’s native OTel can supply these fields. Codex v1 leaves them `null`; establishing a Codex source is explicitly deferred to the installed-host experiment in GAPS. |

Use fixed latency buckets rather than persisting precomputed p95: `<=1, <=2, <=5, <=10, <=25, <=50, <=100, <=250, <=500, <=1000, <=2000, <=5000, >5000 ms`. Histograms preserve aggregability across sessions, whereas averaging precomputed quantiles is invalid ([Prometheus histogram guidance](https://prometheus.io/docs/practices/histograms/)). Tool names and reason codes are bounded by the installed capability/config vocabulary; MCP names must be reduced to `mcp__server__tool` with both components capped and sanitized. Unknown or excessive-cardinality names map to `other:<sha256-prefix>`.

## 3. Runnable loop

### Proposal 1 — **UNVERIFIED Windows overhead** — correlated hot-path sensor — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Modify the existing dispatch, not hook registration count:

1. After normalization, compute `session_hash`, `turn_hash`, and `tool_use_hash` from existing identifiers (`models.py:26-39`; `adapters.py:116-145`).
2. Around each `module.run(event)`, collect only a compact signal when it returns non-`allow` or fails: `[module_name, action, reason_code]`. Do not store context text. The dispatcher already has the exact per-module boundary at `dispatcher.py:267-308`.
3. Extend the existing terminal row—not a second hot-path append—with `session_hash`, `turn_hash`, sanitized `tool_name`, `tool_use_hash`, explicit `tool_outcome` (`success|failure|unknown`), native tool `duration_ms` when present, `context_chars`, and compact `signals`. Continue to record final dispatcher `elapsed_ms`.
4. Rotate terminal JSONL by day/size and retain 30 days after the summary database is proven complete. Rotation must be lock-safe and must never delete the only copy before summary reconciliation.

This is **very likely (80-90%)** to stay under the hot-path budget because it adds bounded hashing/serialization to an append that already occurs on every dispatch (`dispatcher.py:485-513`) and adds no hook process or network call. Actual Windows overhead is **UNVERIFIED**; the settling experiment is 1,000 paired dispatches against a disposable state root plus the 32-worker concurrency test below. Promotion requires incremental p95 <1 ms, max <5 ms, zero malformed rows, and no statistically material change in end-to-end dispatch p95.

Production-code budget: approximately 25–35 changed lines in `dispatcher.py`, 10–20 in `models.py`/`adapters.py` for native duration/outcome, and 25–40 for rotation—well below 200 production lines. Tests are additional. If compact signal capture pushes the implementation beyond that boundary, omit rotation from week one rather than creating a service.

### Proposal 2 — **UNVERIFIED Windows lifecycle/concurrency** — start/checkpoint/finalize spooler — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add one standard-library-only `continuous_bench.py` called **after** `_record_terminal`:

```text
SessionStart:
  insert-or-upsert session row immediately (start_seen=1, finalized=0)
  store stable terminal byte offset and config/mode hashes
  drain any prior lock-failure spool files
  mark old open rows stale; never call them successful/failed

main-agent Stop (both providers, every completed turn):
  read only complete terminal lines from saved offset to a captured EOF
  filter by session_hash; fold counts/histograms into the session snapshot
  atomically upsert the snapshot and new safe offset
  recompute the small current-baseline JSON; return no model-visible output

Claude SessionEnd:
  repeat checkpoint, set end_reason/finalized/session_end_seen
  return no output; it cannot block termination

Codex:
  keep the most recent Stop checkpoint as the current session snapshot
  SessionStart always emits a row, so a pre-Stop crash becomes stale_open rather than no data
```

Use SQLite through Python’s standard library with `journal_mode=WAL`, `synchronous=NORMAL`, a 100 ms busy timeout, and one short upsert transaction only at `SessionStart`, `Stop`, or `SessionEnd`. SQLite WAL appends changes and supports concurrent readers, but still permits only one writer; it can also grow if checkpoints are starved, so this design keeps transactions short and checks WAL size rather than pretending concurrency is free ([SQLite WAL](https://sqlite.org/wal.html)). If the lock budget expires, atomically write one uniquely named, sanitized pending snapshot under `state/harness/bench/spool/`; the next lifecycle event drains it. Fail-open for the host, fail-visible for measurement through `spool_replays` and a digest alert.

Minimal logical tables:

```sql
CREATE TABLE session_snapshot (
  session_hash TEXT PRIMARY KEY, provider TEXT NOT NULL,
  started_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  finalized INTEGER NOT NULL, end_reason TEXT,
  config_hash TEXT NOT NULL, mode_hash TEXT NOT NULL,
  start_seen INTEGER NOT NULL, checkpoint_seen INTEGER NOT NULL,
  session_end_seen INTEGER NOT NULL, stale_open INTEGER NOT NULL,
  counters_json TEXT NOT NULL, histograms_json TEXT NOT NULL,
  quality_json TEXT NOT NULL
);
CREATE TABLE schema_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

One row per session keeps the week-one implementation small. `counters_json` and `histograms_json` have a versioned, tested closed schema; do not build an entity graph. A later migration may normalize tool/gate rows only if real query latency requires it.

This is **likely (55-80%)** to meet a 75 ms Stop checkpoint target because it reads only the terminal suffix since the previous checkpoint and performs one local upsert, while the corpus sizing is 74.93 tool calls per artifact. The confidence is lower than Proposal 1 because same-session resume semantics, Windows append visibility, and concurrent hook writers were not live-tested. **UNVERIFIED** premises and settling experiments are: (a) Python append produces complete concurrent terminal lines—run the 32-worker unique-row test; (b) Claude `SessionEnd` fires for each documented reason on the installed binary—exercise `clear`, interactive resume, and normal prompt exit and reconcile against SessionStart; (c) Codex has no undocumented end callback—inspect `/hooks` and capture installed-host event fixtures. Regardless, the start row and per-Stop checkpoint provide useful data even if finalization coverage is imperfect.

Register Claude `SessionEnd` through the existing `registration.py` generator with a 2-second command timeout and no matcher. Do **not** attach measurement to a new standalone Stop hook: the active Claude Stop path already runs the shared dispatcher and a local dispatcher with 5- and 35-second timeouts (`settings.json:484-503`), and Stop can re-enter/continue. The recorder must never block or inject.

### Proposal 3 — **UNVERIFIED threshold calibration** — automatic rolling baseline and alerts — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

After each successful checkpoint, write `state/harness/bench/current.json` atomically. It is a report cache, not source of truth. It contains:

- last 50 finalized/checkpointed sessions and prior 200-session comparison, split by provider + config hash + mode hash;
- trailing 1-day, 7-day, and 28-day numerators and denominators for tool failures, harness internal errors, blocks/injections, verification receipts, repeated-no-progress, stale sessions, and data-quality loss;
- aggregatable latency buckets and derived p50/p95/max;
- top regressions by absolute harmed-event count, not percentage alone;
- `generated_at`, database max `updated_at`, schema version, and detector-control status.

Never emit a single “harness score.” Report separate reliability, utility/evidence, safety-intervention, cost, latency, and coverage panels. Aggregate numerator and denominator before division; do not average session error rates or p95s. Google’s SRE guidance favors counters, long windows, and percentiles, and stresses that an SLI shows impact but not necessarily cause ([Google SRE Monitoring](https://sre.google/workbook/monitoring/)); Prometheus gives the same numerator/denominator aggregation rule ([Prometheus recording rules](https://prometheus.io/docs/practices/rules/)).

Alert to the already-existing background digest only when:

1. **Measurement is blind:** known-positive SessionStart terminal record missing, malformed row, spool backlog, stale-open rate, or database freshness lag. This alert precedes all “zero fires” claims.
2. **Deterministic failure:** any safety-tier module internal error or explicit critical forbidden effect. Advisory module errors need a denominator and recurrence threshold.
3. **Rate regression:** at least 50 relevant events in both comparison windows, absolute worsening >=2 percentage points, relative worsening >=25%, and non-overlapping 95% Wilson intervals. Keep the raw counts beside the alert.
4. **Latency regression:** at least 100 samples and either p95 consumes >=50% of the registered event timeout or rises >=25% against the matching config/profile baseline.
5. **Dead capability:** a configured MCP/tool has >=10 attempts and >=50% explicit failure, or a known dead fingerprint recurs. This would surface the pinned Tavily case quickly without waiting for another manual 10 GB mine.

Threshold efficacy is **UNVERIFIED**; replay the historical corpus-derived daily counts through the proposed alert rules and label whether each would have surfaced the seven pinned high-damage defects without excessive noise. This recommendation is therefore **likely (55-80%)**, supported by multi-window/counter prior art and the pinned defect rates, but the exact 2%/25%/50-event thresholds are initial hypotheses, not facts. Google SRE’s burn-rate work explains why multi-window alerts improve detection/precision, but this local low-volume workload still requires replay calibration ([Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)).

If an existing receiver is present, **very likely (80-90%)** it can corroborate Claude session/hook counts because the official schema exposes exactly those signals. ### Per-session storage model

Using the corpus’s observed 74.93 calls per artifact as a rough sizing input, approximately two tool lifecycle rows per call plus prompts/lifecycle events yields about 160 enriched rows per typical artifact. At an added 120 bytes per row, incremental diagnostic storage is about **19.2 KiB/session**; one SQLite snapshot plus indexes is budgeted at **<=8 KiB/session**, for a total incremental budget of **<=28 KiB/session** before filesystem/WAL overhead. These byte sizes are **UNVERIFIED** estimates; serialize 100 real sanitized fixtures and measure `Get-Item.Length`, then measure database growth over 1,000 synthetic sessions to settle them.

At 100 main sessions/day, the <=28 KiB budget implies <=2.8 MiB/day and approximately <=1.0 GiB/year before rotation. Retain enriched terminal diagnostics for 30 days (about <=84 MiB at that assumed rate), session snapshots for 180 days, and daily aggregate rows for two years. The 100/day workload is **UNVERIFIED**; derive actual 30-day distinct main SessionStart counts on Windows before fixing retention. Retention is a disk budget, not evidence deletion: preserve aggregate numerators/denominators and schema/config hashes after raw diagnostic expiry.

The database must expose `db_bytes`, `wal_bytes`, `terminal_bytes`, oldest/newest snapshot, and spool count in `current.json`. Storage that cannot measure itself repeats the original defect.

## 5. Baseline semantics and decision use

The baseline is the rolling data, not a hand-edited golden number:

- **Operational baseline:** matching provider + config hash + mode hash, trailing 28 days, with 1/7-day early-warning windows.
- **Deployment baseline:** last known controlled deterministic trace run for the same source hash.
- **Historical pinned baseline:** the 2026-07-18 corpus rates, immutable and labeled as a one-time mine.
- **No-data state:** any detector-control failure, missing denominator, unknown tool outcome, missing provider surface, or insufficient sample count.

Use the loop to make these decisions:

- promote/shadow/prune a gate only after matched benign and harmful fixtures pass the deterministic bench **and** operational fire/error/latency data has adequate denominators;
- disable or repair a capability when explicit failure rate and harmed-event count cross the calibrated rule;
- investigate a hook when its host-native Claude count and dispatcher terminal count diverge; never infer which side is wrong from one detector;
- compare harness/model changes only within explicitly tagged cohorts;
- never claim a gate “helped” from fire count alone. A shadow fire correlated with later success is observational, not causal; a randomized or controlled replay experiment is required.

The last causal limit is **almost certain (90-99%)**: neither current terminal rows nor shadow rows encode counterfactual outcomes (`dispatcher.py:496-507`; `modules.py:373-380`), and production sessions differ in task/model/config. The settling experiment for an intervention is a preregistered replay or randomized shadow/advice trial with executable task outcomes, not another correlation query.

## 7. Anti-overfit gate and rejected alternatives

The design passes the gate:

- it rides the existing shared hook dispatcher, shadow sink, background digest, and atomic-storage helpers;
- it adds no orchestration runtime, vector DB/KG, durable-execution engine, trained critic, guardrail framework, or SaaS;
- it uses standard-library SQLite only at lifecycle boundaries and bounded JSONL already present on the hot path;
- it keeps controlled benchmarks separate from passive telemetry;
- it stores counts/histograms and explicit unknowns, not raw content or an ontology.

Rejected alternatives:

1. **Always-on OpenTelemetry Collector + Prometheus/Grafana.** Excellent general tooling, wrong first-week architecture here: it creates a new daemon/monitoring stack and does not solve custom gate outcome labeling. Reconsider only if a receiver is already live for another purpose.
2. **Observability SaaS.** Explicitly prohibited by the anti-overfit gate and unnecessary for one owner/local Windows host.
3. **Parse every transcript in `SessionEnd`.** The corpus averages roughly 1.87 MB/artifact in a crude aggregate and Codex explicitly says transcript format is not a stable hook interface ([Codex common fields](https://developers.openai.com/codex/hooks)). Incremental hook summaries are smaller and schema-controlled. A scheduled incremental miner may still enrich error fingerprints later, but it is not the keystone loop.
4. **Run D10/pytest or semantic-router eval after every session.** Too slow and workload-distorting; the existing router runner permits 1,200 seconds (`harness-bench/bench.py:41-42`).
5. **Use Stop as session end everywhere.** Claude Stop is response completion and can re-enter; Codex documents Stop as turn scope. It is a checkpoint, not a finalizer.
6. **One composite quality score.** It hides safety/utility/latency tradeoffs and makes missing data look comparable. Keep panels and raw denominators.
