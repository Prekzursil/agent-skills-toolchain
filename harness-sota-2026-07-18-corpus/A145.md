## Runtime precedence grounded from primary documentation, but not applicable to missing live definitions

Current official Claude Code documentation defines these tie-breaks:

1. For the same manually configured MCP server name in multiple ordinary scopes, the highest-precedence source wins; Claude's feature overview states `local > project > user`. See [Claude Code feature overview](https://code.claude.com/docs/en/features-overview) and [MCP installation scopes](https://code.claude.com/docs/en/mcp).
2. Plugin MCP servers start automatically only when the plugin is enabled, and plugin MCPs appear alongside manually configured servers. See [Plugin-provided MCP servers](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers).
3. An active `managed-mcp.json` has exclusive control: only its server map supplies servers, and user configuration cannot add more. Anthropic's prescribed runtime verification is that `claude mcp list` show only managed servers and `claude mcp add ...` fail with the enterprise-exclusive-control message. See [Control MCP server access](https://code.claude.com/docs/en/managed-mcp#validate-the-configuration).
4. MCP allowlists and denylists are settings filters, not registries. A server must still be supplied by a user, plugin, or managed file; denylist matches win, then allowlist rules are evaluated. See [How a server is evaluated](https://code.claude.com/docs/en/managed-mcp#how-a-server-is-evaluated).

These are authoritative generic rules. They do not identify the live Windows definitions, prove that managed mode is active, or show which project entry applies to the owner's current working directory. It is **almost certain (90-99%)** that the generic `local > project > user` order would decide a same-name ordinary-scope collision on the current documented Claude Code behavior; the evidence is Anthropic's current primary documentation. The experiment that settles it for this installed build is a three-definition sentinel server with distinct harmless `tools/list` descriptions, invoked once from the target project.

It is **very likely (80-90%)** that active managed mode would suppress user/project additions on the owner's installed build; the evidence is Anthropic's explicit exclusive-control behavior and prescribed CLI test. ## Conflict classes evaluated

### Cleared non-finding: permission allow-rules versus MCP registration

The settings file allows names such as `mcp__tavily`, `mcp__firecrawl`, and `mcp__playwright` at `/local_disk0/codexwork/bundle/claude/settings.json:54-60`, while their similarly named official plugins are disabled at `:585,596` (and Tavily has no similarly named plugin entry in the supplied map). This is not itself a precedence conflict.

Concrete reason: a permission rule answers whether a surfaced tool may execute without a prompt; MCP registration and plugin enablement answer whether the server/tool is surfaced at all. Anthropic describes allow/deny MCP policy separately from server supply, explicitly saying an allowlist is not a registry and a server must still be added by a user, a plugin, or `managed-mcp.json` ([managed MCP documentation](https://code.claude.com/docs/en/managed-mcp#policy-based-control-with-allowlists-and-denylists)). A permission allow entry cannot make a disabled or absent server connect. Conversely, a connected server still passes the permission decision.

Runtime winner: not applicable because the two texts do not claim authority over the same decision. Minimal edit: none. Removing stale allow entries may improve hygiene, but that is neighbouring fleet-curation work and is not required to resolve precedence.
