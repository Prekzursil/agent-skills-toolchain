# T012 — Competitive teardown: Gemini CLI

**Unit:** T012  
**Research date:** 2026-07-19 UTC  
**Subject:** Google Gemini CLI, compared with the unpacked Claude/Codex owner harness  
**Research posture:** read-only on the subject; only this artifact was written

## Executive verdict

Gemini CLI is not a better wholesale harness for this owner. Its strongest ideas are narrow control-plane mechanisms that can ride our existing hook, skill, and MCP buses: admission-time MCP health filtering, a mode- and agent-aware policy table, locally queryable lifecycle telemetry, semantic segmentation before pattern matching, and a human-reviewed memory/skill proposal inbox. Its event-driven TypeScript scheduler, second-model loop critic, shadow-Git checkpoint store, and non-recursive subagent runtime should not replace our harness.

The most important competitive advantage is mundane and decisive: Gemini connects to each MCP server before registering its tools; a failed connection becomes `DISCONNECTED`, and only successfully discovered tools enter the registry. Its `/mcp` display exposes connection and discovery state. That mechanism addresses our highest-damage MCP defect at its source: Tavily extract produced 137 errors in 532 calls, including 135 “not connected” results ([corpus.json lines 9141–9148](/local_disk0/codexwork/bundle/inputs/corpus.json:9141)); Gemini’s discovery sequence marks failed servers disconnected before tool discovery and registration ([official MCP architecture](https://geminicli.com/docs/tools/mcp-server/#discovery-process-deep-dive)). A port that prevents a disconnected server from being offered is **very likely (80-90%)** to eliminate this exact error fingerprint, because availability is determined before model selection rather than after a doomed call. It will not repair server outages.

The second strongest idea is semantic discrimination inside loop detection. Gemini resets or disables repetition analysis across code fences, tables, lists, headings, blockquotes, and dividers ([source, `loopDetectionService.ts` lines 351–397](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/services/loopDetectionService.ts#L351-L397)). Our live defects explicitly require distinguishing executable use from prose mention and recommend fence/path/verb context ([known defects lines 43–50](/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:43)). Reusing this *segmentation principle*, not Gemini’s entire detector, is **very likely (80-90%)** to remove the recorded prose false positives; evidence is that all recorded cases occur in prose/table/field-name contexts and the proposed regression controls include a real source occurrence.

Gemini is worse in several important respects:

* Its LLM loop detector adds one Flash judgment and, above a threshold, a second model judgment ([source lines 563–713](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/services/loopDetectionService.ts#L563-L713)). That is precisely the trained/model critic class rejected by this program’s anti-overfit gate. Our existing result-aware `(tool, args, output)` fingerprint is deterministic, polling-aware, and under 200 lines ([`fingerprint.py` lines 1–16 and 104–140](/local_disk0/codexwork/bundle/claude/hooks/anti-degen/fingerprint.py:1)).
* Gemini subagents are explicitly isolated and cannot invoke other subagents, even with `*` tool access ([official subagent docs](https://geminicli.com/docs/core/subagents/#isolation-and-recursion-protection)). That is a useful recursion fuse but a worse orchestration ceiling than the owner’s native team/fan-out use: the corpus records 1,158 general-purpose agent invocations plus specialist agents ([corpus lines 13346–13368](/local_disk0/codexwork/bundle/inputs/corpus.json:13346)), and current settings enable experimental agent teams ([settings lines 5–8](/local_disk0/codexwork/bundle/claude/settings.json:5)).
* Gemini skills request consent on every activation ([official skill management](https://geminicli.com/docs/cli/using-agent-skills/#security-and-consent)). With roughly 355 installed capabilities but only a small used subset, this treats repeated execution as the trust boundary rather than install/provenance review. Copying it literally would add prompts without fixing discovery quality.
* Gemini’s default compression threshold in current source is 50% and retains the latest 30% ([source lines 37–52](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/context/chatCompressionService.ts#L37-L52)); this owner deliberately sets Claude autocompaction to 90% and uses a 1M-context model ([settings lines 18 and 77–80](/local_disk0/codexwork/bundle/claude/settings.json:18)). Copying Gemini’s threshold would likely throw away useful context earlier.

## 1. Agent loop

### Concrete design

The current core is a streaming loop, not a planner DAG. `GeminiClient.processTurn()`:

1. increments and enforces a session turn limit;
2. renders or compresses history before the request;
3. checks estimated request size against remaining tokens;
4. runs loop detection;
5. routes/selects a model and updates tool descriptions for that model;
6. streams a `Turn` and inspects every emitted event;
7. accumulates response text for hooks;
8. returns pending tool calls to the outer loop.

Those steps are visible in [`client.ts` lines 614–855](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/core/client.ts#L614-L855). The separate `Scheduler` calls itself an “Event-Driven Orchestrator for Tool Execution,” owns a state manager, executor, modifier, message bus, abort controller, and request queue, and either enqueues or starts a tool batch ([`scheduler.ts` lines 95–138 and 191–223](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/scheduler/scheduler.ts#L95-L223)). The official changelog says the event-driven scheduler arrived in v0.27.0 ([release notes](https://geminicli.com/docs/changelogs/#announcements-v0270---2026-02-03)).

This architecture is credible source evidence for orderly lifecycle events and cancellation, but there is no published benchmark in the reviewed sources showing it produces better task completion than a smaller loop. Any claim of superior end-task quality is **UNVERIFIED; the settling experiment is an A/B run of the owner’s fixed task suite using Gemini stable versus the current Claude harness, measuring terminal postconditions, tool errors, wall time, and tokens.**

### What to copy

#### Proposal: make tool batches explicit in telemetry, not a new scheduler

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `batch_id`, `call_id`, `parent_call_id`, queue timestamp, start timestamp, terminal status, and cancellation reason to the shared event ledger for every PreToolUse/PostToolUse pair. The existing provider-neutral flow already normalizes provider input and writes terminal records ([shared harness README lines 1–15](/local_disk0/codexwork/bundle/agents/harness/README.md:1)); this is a schema/event enrichment, not orchestration.

It is **likely (55-80%)** that correlation IDs will expose cancelled sibling calls and retry batches more clearly, because the corpus already contains “Cancelled: parallel tool call … errored” fingerprints ([corpus lines 9012–9022](/local_disk0/codexwork/bundle/inputs/corpus.json:9012)) and Gemini’s scheduler makes batch and call identity first-class. It is not evidence that serialized execution will be better.

### What not to copy

Do not replace Claude/Codex native loops with Gemini’s scheduler. That would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and would reintroduce the explicitly rejected second orchestration runtime. The proposal fails the anti-overfit gate. The owner’s own Codex adapter warns that an added companion/job-store/detached-worker layer created recorded failure modes and therefore calls `codex exec` directly ([`codex.md` lines 10–15](/local_disk0/codexwork/bundle/claude/agents/codex.md:10)).

## 2. Context management

### Rules and hierarchical context

`GEMINI.md` files are automatically loaded as hierarchical instructions. `/memory show` prints the concatenated text actually supplied to the model and `/memory reload` refreshes it ([official memory tutorial](https://geminicli.com/docs/cli/tutorials/memory-management/)). This inspection surface matters: an owner can see the active instruction payload rather than infer it from the filesystem.

Gemini also records full project-scoped sessions, including prompts, responses, tool inputs/outputs, token statistics, and reasoning summaries where available; `--resume`, a searchable session browser, and retention controls operate on those records ([official session management](https://geminicli.com/docs/cli/session-management/)). `/rewind` can rewind chat, AI edit-tool changes, or both, and reconstructs history across compression points ([official rewind docs](https://geminicli.com/docs/cli/rewind/)).

### Compression mechanism

The legacy/current fallback compression service is unusually explicit:

* trigger at 50% of model context by default;
* preserve the newest 30%;
* budget preserved function responses to 50,000 tokens;
* walk tool responses newest-first and truncate older large results, preserving their tail and saving full output separately;
* summarize earlier history into a `<state_snapshot>`;
* perform a second lightweight “what was omitted?” verification turn;
* reject a summary if it is empty or has more tokens than the original.

The source implements output budgeting at [`chatCompressionService.ts` lines 124–180](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/context/chatCompressionService.ts#L124-L180), compression gating/failure fallback at [lines 239–339](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/context/chatCompressionService.ts#L239-L339), and summary self-check/inflation rejection at [lines 342–480](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/context/chatCompressionService.ts#L342-L480). Official telemetry records `tokens_before` and `tokens_after` for compression ([telemetry reference](https://geminicli.com/docs/cli/telemetry/#gemini_cli-chat_compression)).

### What to copy

#### Proposal: active-context manifest

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Provide a `/harness:context-show` skill/command that emits the ordered instruction sources, their paths, byte/token estimates, precedence, and content hash. It should validate the detector by including one known-present instruction before claiming any source is absent.

This is **very likely (80-90%)** to shorten diagnosis of fabricated or stale constraints, because D4 shows one orchestrator-authored false constraint propagated to roughly 15 prompts with no recipient-side way to falsify it ([known defects lines 150–160](/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:150)); a manifest makes origin and precedence directly inspectable. It will not by itself determine whether an instruction is true.

#### Proposal: bounded old-tool-output elision

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing command-output compressor so that, after a cumulative per-turn budget, old tool results are replaced in model context by `{digest, byte_count, first_lines, last_lines, artifact_path}` while the complete output remains local. Preserve recent results and all nonzero exit/error tails. Never rewrite the tool *arguments* or success status.

It is **likely (55-80%)** to reduce context pressure without losing the failure evidence most useful for recovery, based on Gemini’s reverse-token-budget implementation and this owner’s very high `BASH_MAX_OUTPUT_LENGTH=150000` ([settings lines 9–10](/local_disk0/codexwork/bundle/claude/settings.json:9)). **UNVERIFIED whether the current Claude PostToolUse output can replace native history rather than merely inject context; the settling experiment is a hook fixture that returns compressed output and then inspects the next model-visible transcript event.** If replacement is unavailable, keep this as a shell-wrapper optimization and do not pretend it controls history.

### What not to copy

Do not set compaction to Gemini’s 50% default. It is **likely (55-80%)** to be worse for this owner because the active Claude model is configured for 1M context and deliberate 90% compaction; the evidence is configuration intent, not an A/B quality test. Also do not copy the second LLM compression critic as a general verification layer: it spends another model call, can agree with its own omission, and approaches the rejected trained-critic pattern. The deterministic checks worth copying are “summary nonempty,” “new token count lower,” and “critical pinned fields present.”

## 3. Memory

### Concrete design

Gemini has four relevant persistence layers:

1. global personal instructions in `~/.gemini/GEMINI.md`;
2. repository/project `GEMINI.md` instructions;
3. private per-project memory;
4. model-activated Agent Skills and their resources.

The memory tool edits Markdown directly and routes durable facts to the appropriate tier ([official memory tool](https://geminicli.com/docs/tools/memory/)). This is deliberately file-native rather than a vector database or knowledge graph.

Auto Memory is experimental. At startup it scans local sessions idle for at least three hours and containing at least ten user messages, uses a lock and processed-version state, has a background extraction agent propose memory patches or `SKILL.md` drafts, validates/dry-runs patches, and holds everything in a project-local review inbox. It cannot directly edit active memory, settings, credentials, or project `GEMINI.md`; `/memory inbox` is the approval point ([official Auto Memory docs](https://geminicli.com/docs/cli/auto-memory/)). It sends selected transcript content to the configured model and uses a preview Flash model, which the docs list as a limitation.

### What to copy

#### Proposal — UNVERIFIED: reviewed improvement inbox

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Reuse the already distilled corpus/correction-candidate feed instead of rescanning 10.62 GB on every startup. A SessionEnd producer writes only candidate metadata (`session_hash`, evidence offsets, repeated fingerprint/correction cluster, proposed target type); a review skill shows the evidence and a unified patch; acceptance routes through the existing skill/config installer and tests. No candidate auto-applies. Per-project locking and a processed-version digest prevent repeat work.

**UNVERIFIED premise: the unpacked harness may already have an equivalent review inbox outside the supplied tree; the settling experiment is (1) prove a known-present `memory-spool` file is found, then (2) search user/project commands and state roots for inbox manifests containing proposed unified patches, and (3) run the relevant command-list control on the Windows host.** The heading inherits UNVERIFIED as required.

If the premise is confirmed, the narrow inbox is **likely (55-80%)** to convert owner corrections into reviewable improvements with less risk than direct self-modification. Evidence: the corpus contains 2,268 correction candidates per the pinned input, while Gemini’s safety boundary makes proposals inert until approval. The confidence is not higher because extraction precision has not been measured on this owner’s corrections.

### What not to copy

Do not create a vector DB/KG memory, durable-execution service, or always-on memory daemon. Gemini does none of those here, and each is rejected by the anti-overfit gate. Do not run a background model over every session at startup until a sampled precision evaluation exists. Auto Memory itself is experimental and admits dependence on a preview model ([official limitations](https://geminicli.com/docs/cli/auto-memory/#limitations)).

## 4. Tool and MCP handling

### Concrete design

Gemini MCP integration has separate discovery and execution layers. Discovery iterates configured servers, chooses stdio/SSE/streamable HTTP, connects, lists tools, sanitizes/validates schemas, applies include/exclude filters, registers fully-qualified tool names, discovers resources, and closes connections that yield no usable tools ([official MCP architecture](https://geminicli.com/docs/tools/mcp-server/#core-integration-architecture)). Connection failures become `DISCONNECTED`; successful servers remain connected. `/mcp` displays server status, sanitized configuration, available tools, and overall discovery state ([official status display](https://geminicli.com/docs/tools/mcp-server/#using-the-mcp-command)).

Other concrete controls include:

* server allow/exclude lists before connection;
* per-server include/exclude tool lists;
* request timeouts;
* OAuth 2.0 for remote SSE/HTTP servers;
* automatic redaction of inherited environment variables matching token/secret/password/key/auth/credential patterns, with explicit per-server opt-in overrides;
* tool and resource namespaces;
* restrictive merging: exclusions union, inclusions intersect, exclusions win;
* MCP resources addressable by `@server://resource/path` and injected only when referenced.

These are documented in the [official MCP configuration/security reference](https://geminicli.com/docs/tools/mcp-server/#configuration-properties) and [override rules](https://geminicli.com/docs/tools/mcp-server/#overriding-extension-configurations).

There is a sharp defect worth not copying: official docs warn that underscores in an MCP server name can cause wildcard security policies to fail silently because the parser splits the FQN at the first underscore ([official warning](https://geminicli.com/docs/tools/mcp-server/#tool-naming-and-namespaces)). A security naming grammar that silently misparses legal names is worse than explicit structured identity.

### What to copy

#### Proposal: disable the known-dead Tavily registration now

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Remove/disable the `claude_ai_Tavily` registration that is known disconnected, while retaining a verified live Tavily provider if one exists. Resolve the exact config key on Windows first; do not delete plugin directories. The user explicitly stopped bulk deletion because 110/169 plugins had no live sibling and one orphaned directory was read by a live skill.

This is **almost certain (90-99%)** to stop the exact disconnected-provider calls once a fresh session no longer advertises that namespace, because the error is tied to that provider name and the corpus records 135 identical extract failures. The remaining 0.2575 extract error rate includes two user rejections, so it will not make all Tavily activity error-free ([corpus lines 9141–9152](/local_disk0/codexwork/bundle/inputs/corpus.json:9141)).

#### Proposal: admission-time MCP circuit breaker

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing MCP liveness hook rather than add a service. At SessionStart, probe each configured server once with transport-appropriate connect/list-tools and store `{server_id, config_hash, state, checked_at, error_class}`. At PreToolUse, a disconnected server returns a typed `mcp_unavailable` result plus live alternatives; after a cooldown, exactly one half-open probe is allowed. A successful probe closes the circuit. Config hash changes invalidate state. Server identity must be structured fields, never parsed from underscore-delimited names.

It is **very likely (80-90%)** to prevent repeated dead-server retries in this harness, because the failure repeats 135 times and the current settings permit the broad MCP surface ([settings lines 47–60](/local_disk0/codexwork/bundle/claude/settings.json:47)). It cannot remove a tool from Claude’s native model-visible registry mid-session; therefore CONFIG removal is still the clean fix for permanently dead entries. **UNVERIFIED whether SessionStart can enumerate every native/remote plugin MCP in the Windows runtime; the settling experiment is a known-positive inventory test against one connected and one intentionally unreachable fixture, comparing hook enumeration with the native MCP list.**

#### Proposal: restrictive MCP override algebra

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** When the same MCP arrives from plugin, user, and project scopes, compute effective tools as `intersection(all specified includes) - union(all excludes)`, and log the provenance of every exclusion. Scalars use explicit precedence; credentials never merge implicitly. Add property tests for commutativity of include/exclude aggregation.

This is **likely (55-80%)** to prevent a plugin update from silently re-enabling a locally forbidden tool, based on Gemini’s documented restrictive merge. The benefit magnitude is unmeasured in our corpus because MCP policy provenance is not a corpus field.

### What not to copy

Do not use delimiter parsing for MCP identity. Do not let `trust: true` bypass every confirmation for a whole server; Gemini supports that switch ([official configuration properties](https://geminicli.com/docs/tools/mcp-server/#configuration-properties)), but this owner’s MCP estate spans 93 used servers and broad server trust magnifies one compromised/misdescribed tool. Prefer tool/action-scoped policy.

## 5. Permission model

### Concrete design

Gemini’s policy engine evaluates a set of rules with conditions, decision (`allow`, `deny`, `ask_user`), and numeric priority. Conditions include tool name, stable-JSON argument regex, interactive/headless state, approval mode, MCP identity, and subagent identity. Tiers order default, extension, workspace, user, and admin rules; admin wins. Modes are `plan`, `default`, `autoEdit`, and `yolo`, and persistent approvals are context-aware ([official policy engine](https://geminicli.com/docs/reference/policy-engine/)). Global denies can remove tools from model context, saving tokens and preventing selection. Tool sandboxing can request a one-run expansion for a specific directory or network need ([official sandbox expansion](https://geminicli.com/docs/cli/sandbox/#sandbox-expansion)). Untrusted folders ignore project settings, `.env`, MCP servers, custom commands, auto-acceptance, and automatic memory loading ([official trusted-folder behavior](https://geminicli.com/docs/cli/trusted-folders/)).

The current owner settings, by contrast, have a broad flat allow list, four read-deny patterns, an empty ask list, `bypassPermissions`, and additional access to entire `C:` and `D:` drives ([settings lines 26–75](/local_disk0/codexwork/bundle/claude/settings.json:26)). Hooks add nuanced enforcement, but the shared result contract exposes only `allow`, `block`, `inject`, and `continue` with no policy priority/mode/agent fields ([hook result schema lines 7–36](/local_disk0/codexwork/bundle/agents/harness/schemas/hook-result.schema.json:7)). Those are two mechanically independent signals of the structural gap: native config shape and provider-neutral result schema. The detector control is the clearly present `tools:` restriction in agent frontmatter, e.g. the security reviewer ([agent lines 1–9](/local_disk0/codexwork/bundle/claude/agents/security-reviewer.md:1)).

Gemini’s own documentation is inconsistent: the changelog says v0.31 added project-level policies, while the policy reference currently labels the workspace tier disabled/non-functional. The actual stable behavior is **UNVERIFIED; the settling experiment is an integration test on Gemini stable v0.50 with conflicting user/workspace rules and inspection of the resolved policy trace.** Therefore workspace policy parity is not a reason to migrate.

### What to copy

#### Proposal: typed priority policy in the existing dispatcher

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a declarative policy module to the current ordered dispatcher. Minimal rule fields: `id`, `tool`, structured `argv_prefix` or typed argument predicate, `agent`, `interactive`, `mode`, `decision`, `priority`, `expires`, and `evidence`. The module receives the actual tool verb and parsed arguments. It must never run a regex over a write payload to infer the action. Highest priority wins; equal-priority conflicts fail closed only for irreversible operations and otherwise ask/inject. Emit the winning rule ID and shadow all new heuristic rules before enforcement, using the harness’s existing OFF→SHADOW→ADVISE→ENFORCE ladder ([`modules.py` lines 118–143](/local_disk0/codexwork/bundle/agents/harness/modules.py:118)).

It is **very likely (80-90%)** to reduce policy ambiguity and the live “use versus mention” false positives, because it forces matching on verb/argv/agent rather than prose and because D1 diagnosed the shared discriminator defect with four independent detectors ([known defects lines 52–82](/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:52)). It is only **likely (55-80%)** to reduce user interruptions overall; stricter priorities can also create new blocks, so shadow precision must be measured first.

#### Proposal: untrusted-workspace safe profile

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Define a launcher/profile for unknown repositories that disables project hooks/commands/MCP, ignores project `.env`, removes broad drive access, and uses default/plan permissions until trust is explicitly granted. This is a profile, not a new sandbox runtime.

It is **very likely (80-90%)** to reduce exposure to repository-supplied execution, because it removes the configuration channels before the model can invoke them, mirroring Gemini’s trusted-folder boundary. Whether Claude’s native settings can disable every project-contributed surface is **UNVERIFIED; the settling experiment is a hostile fixture repository containing a project hook, command, MCP, instruction file, and `.env`, then a trace proving which load under the profile.**

### What not to copy

Do not copy Gemini’s `argsPattern` over stable-stringified full JSON as the primary safety discriminator. That repeats D1: dangerous words in prose payloads can match even when they are not executable. Use typed tool-specific fields and argv parsing. Do not enable an all-tools `yolo` equivalent as a persistent default; current `bypassPermissions` is already overly broad.

## 6. Customisation: rules, skills, hooks, commands, extensions

### Gemini surface

Gemini exposes:

* hierarchical context rules via `GEMINI.md`;
* TOML custom slash commands at user and project scopes, with namespacing and reload ([official custom commands](https://geminicli.com/docs/cli/custom-commands/));
* Agent Skills discovered from built-in, extension, user, and workspace tiers, including `.agents/skills` aliases and explicit precedence ([official skill tiers](https://geminicli.com/docs/cli/using-agent-skills/#discovery-tiers));
* three-stage progressive disclosure: name/description always present, `SKILL.md` on activation, bundled resources on demand ([official skill best practices](https://geminicli.com/docs/cli/skills-best-practices/#progressive-disclosure));
* extensions packaging MCP, context, commands, hooks, skills, subagents, policy, and themes in one manifest ([official extension reference](https://geminicli.com/docs/extensions/reference/));
* command hooks at `BeforeTool`, `AfterTool`, `BeforeAgent`, `AfterAgent`, `BeforeModel`, `BeforeToolSelection`, `AfterModel`, `SessionStart`, `SessionEnd`, `Notification`, and `PreCompress` ([official hook reference](https://geminicli.com/docs/hooks/reference/)).

Hook stdin includes session ID, transcript path, cwd, event name, and timestamp. `BeforeTool` receives tool name/input and can deny or rewrite arguments; `AfterTool` receives structured result and can hide/replace it, inject context, or request an immediate tail tool call; `AfterAgent` can reject a response and force a retry ([official hook schemas](https://geminicli.com/docs/hooks/reference/#tool-hooks)). Hook groups may run sequentially or in parallel.

Our harness already has extensive hooks and specialists.
