# A123 — coherence audit: commands / direct contradiction

## Scope and result

I audited the complete unpacked command surface at
`/local_disk0/codexwork/bundle/claude/commands/*.md`, corresponding to
`~/.claude/commands/**` on the subject. The bounded inventory is **71 regular Markdown files,
8,180 lines, 271,439 bytes** (`find ... -type f | wc -l`, `wc -l .../*.md`, and
`wc -c .../*.md`). The SHA-256 of the sorted 71-name inventory is
`bc68dd745f7da1ff9afe62ae833975114c4888ffafb75cbd41849ce09aee6d2a`.

Result: **four direct-contradiction families** occur in situations the commands themselves make
reachable:

1. the design gate both requires unanimous approval and offers proceeding without it;
2. `/ccg:plan` forbids the exact Y/N approval handshake that `/ccg:execute` requires;
3. two multi-model commands say both “NEVER kill” and ask whether to kill after the same timeout;
4. PR-comment handling both requires every comment type to be fixed and permits disagreement, and
   separately both requires reviewer acknowledgment and immediate resolution when declining.

No subject files were modified. This artifact is the only write.

The applicable checked-in runtime precedence contract says, verbatim:

> `1. The user's explicit in-session instruction and the permission system.`

— `~/.claude/AGENTS.md:121`

and:

> `When two SAME-LEVEL instructions genuinely conflict, surface the conflict`
> ` (§7) rather than silently picking one.`

— `~/.claude/AGENTS.md:129-131`

Therefore the **configured winner** for same-level command-text collisions is neither clause: the
agent must surface the conflict. If the user explicitly selects an offered override/kill/decline,
the user's instruction wins (`AGENTS.md:121`). This is the verified policy result, not an assumed
“later line wins” rule.

Actual model compliance on the owner's Windows Claude Code runtime is **UNVERIFIED — experiment:
run each reproducer below in a clean Claude Code session with a disposable repository and retain
the expanded prompt/transcript plus tool calls**. The Linux bundle has no `claude` executable on

here. It is **likely (55-80%)** that unresolved same-prompt contradictions produce inconsistent
choices rather than reliable line-order precedence; evidence is that the only local arbitration
rule explicitly requires surfacing rather than selecting (`AGENTS.md:129-131`), while no command
file defines intra-file priority. This likelihood is not a substitute for the named experiment.

## Findings

### F1 — Unanimous design approval vs forced override — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

**Text A (verbatim):**

> `3. Wait for all 5 review agents to approve before proceeding to planning`

— `~/.claude/commands/brainstorm.md:15`

The same invariant is repeated more strongly in the actual task router:

> `3. Wait for all 5 review agents (PM, Architect, Designer, Security, CTO) to APPROVE`
> `4. Only after ALL APPROVED, proceed to planning`

— `~/.claude/commands/start-task.md:142-143`

and in the gate itself:

> `The review gate passes when:`
> `- [ ] All five agents return APPROVED`
> `- [ ] All blocking issues resolved`

— `~/.claude/commands/review-design.md:141-144`

**Text B (verbatim):**

> `After 3 iterations, use --force-override to proceed anyway (documents technical debt).`

— `~/.claude/commands/review-design.md:166-168`

The collision is reachable, not hypothetical: `/brainstorm` automatically triggers the design
review gate (`brainstorm.md:13-15`); `/start-task` also mandates that gate before planning
(`start-task.md:138-144`); and `review-design.md:63-68` explicitly defines the state “After 3
iterations without approval” with options `Override / Defer / Cancel`. In that exact state, Text A
forbids planning while Text B says to proceed anyway.

**Runtime winner.** With no explicit user selection, neither wins: same-level conflict must be
surfaced (`AGENTS.md:129-131`). If the user explicitly chooses Override, the user instruction wins
(`AGENTS.md:121`). Actual adherence is **UNVERIFIED — experiment F1: create a disposable design
whose reviewer remains NEEDS_REVISION for three iterations, then observe whether Claude asks for
Override/Defer/Cancel or silently applies `--force-override`**.

**Minimal resolution edit.** Pick one policy and say it in all three callers. The safety-preserving
minimal edit is to replace `review-design.md:168` with:

> `After 3 iterations, surface Override / Defer / Cancel. Proceed with --force-override only after the user explicitly selects Override; record unresolved blockers as technical debt.`

Then add `unless the user explicitly chooses the documented force override after escalation` to
`brainstorm.md:15` and `start-task.md:143`. This is three prose-line edits on the existing command
bus; no new runtime is justified. It passes the anti-overfit gate: no second orchestrator, vector
store, durable-execution engine, critic, SaaS, or guardrail framework.

### F2 — Planner forbids Y/N; executor requires Y — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

**Text A (verbatim):**

> `**ABSOLUTELY FORBIDDEN**:`
> `- Ask user "Y/N" then auto-execute (execution is /ccg:execute's responsibility)`

— `~/.claude/commands/multi-plan.md:222-225`

It is restated without the auto-execute qualifier:

> `2. **No Y/N prompts** – Only present plan, let user decide next steps`

— `~/.claude/commands/multi-plan.md:262-265`

**Text B (verbatim):**

> `- **Prerequisite**: Only execute after user explicitly replies "Y" to /ccg:plan output (if missing, must confirm first)`

— `~/.claude/commands/multi-execute.md:15`

and:

> `- If cannot confirm user replied "Y" to plan: must confirm again before proceeding`

— `~/.claude/commands/multi-execute.md:121-123`

The collision occurs in the documented handoff itself. `/ccg:plan` tells the user to copy
`/ccg:execute .claude/plan/actual-feature-name.md` into a new session
(`multi-plan.md:204-220`) and then terminate. A user who follows that exact instruction has invoked
execution but has not “explicitly replied Y”; the executor must inject the confirmation the planner
categorically says not to ask. This is not the unrelated `/plan` command: both files name the same
`/ccg:plan` → `/ccg:execute` protocol.

**Runtime winner.** In the execution session, the later command's stricter prerequisite causes the
executor to ask for confirmation; there is no user instruction saying to bypass it. This is the
configured behavior at `multi-execute.md:15,121-123`. Whether the model treats the user's explicit
`/ccg:execute ...` invocation itself as approval is **UNVERIFIED — experiment F2: in a new clean
session paste exactly the handoff command emitted by `/ccg:plan`, without “Y”, and record whether
the first execution tool call is gated by confirmation**. It is **very likely (80-90%)** that the
written prerequisite adds a redundant turn; evidence is the unqualified “if missing, must confirm”
at line 15 and repeated “must confirm again” at line 123.

**Minimal resolution edit.** Make command invocation the approval token. Change
`multi-execute.md:15` to:

> `Prerequisite: an explicit /ccg:execute invocation with a saved plan path counts as approval; for direct task text or an incomplete plan, confirm first.`

Delete the reply-`Y` check at `multi-execute.md:123`, retaining its existing direct-task/incomplete-
plan gate at line 122. The planner's no-auto-execution boundary remains intact. This is a two-line
prose edit on the existing command bus and passes the anti-overfit gate.

### F3 — “NEVER kill” vs offer to kill after timeout — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

This contradiction is duplicated verbatim in two commands.

**Text A (verbatim):**

> `- If still incomplete after 10 minutes, continue polling with TaskOutput, **NEVER kill the process**`

— `~/.claude/commands/multi-plan.md:59`; identical at
`~/.claude/commands/multi-execute.md:100`

**Text B (verbatim):**

> `- If waiting is skipped due to timeout, **MUST call AskUserQuestion to ask user whether to continue waiting or kill task**`

— `~/.claude/commands/multi-plan.md:60`; identical at
`~/.claude/commands/multi-execute.md:101`

The concrete collision is a background model task still incomplete after the specified 600,000 ms
`TaskOutput` wait (`multi-plan.md:51-60`; `multi-execute.md:92-101`). Text A admits only continued
polling. Text B makes killing an offered next action for that timeout. This is not merely two modes:
both bullets are adjacent under the same `IMPORTANT` timeout section.

`multi-workflow.md:91-92` is a useful non-conflicting control: it has the same pair but appends
`Never kill directly`, which makes “do not kill without approval; a user may authorize it” explicit.
That qualifier is absent from both conflicting copies.

**Runtime winner.** Before user input, neither same-level bullet wins and the conflict should be
surfaced (`AGENTS.md:129-131`). If the user chooses Kill after the mandated question, that explicit
instruction wins (`AGENTS.md:121`). Actual compliance is **UNVERIFIED — experiment F3: use a
disposable background task that exceeds 600 seconds, choose Kill, and observe whether Claude kills
it, continues polling, or reports the contradiction**. It is **very likely (80-90%)** that different
runs can diverge before user choice; evidence is the adjacent unconditional `NEVER` and mandatory
offer, plus the absence of the qualifier that exists in `multi-workflow.md:92`.

**Minimal resolution edit.** Copy the already-clear control wording into both files:

> `If still incomplete after 10 minutes, continue polling; never kill directly. If the user does not want to keep waiting, ask whether to continue or kill, and kill only on explicit approval.`

This replaces two adjacent bullets in each file. It is a four-line documentation-only change on
the existing bus and passes the anti-overfit gate.

### F4 — PR feedback must always be fixed vs may be rejected; resolution acknowledgment vs immediate decline — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

This command contains two tightly related direct contradictions.

#### F4a — disposition

**Text A (verbatim):**

> `> **Note**: ALL comment types require fixes. See Complete PR Lifecycle Protocol - trivial/nitpicks are NOT optional.`

— `~/.claude/commands/handle-pr-comments.md:368`

The mandatory table also says Critical through Low are to be fixed
(`handle-pr-comments.md:360-365`).

**Text B (verbatim):**

> `3. For each comment: fix OR create issue OR respond with disagreement`

— `~/.claude/commands/handle-pr-comments.md:57`

The collision occurs whenever a fetched review comment is actionable but incorrect, unsafe, or
based on a false premise. Text A requires a code fix for every type; Text B explicitly allows an
evidence-backed disagreement instead. Such comments are within the loop's declared input (“For
each comment”), so this is not a conflict that never arises.

#### F4b — resolution timing

**Text A (verbatim):**

> `- Never auto-resolve without reviewer acknowledgment`

— `~/.claude/commands/handle-pr-comments.md:82`

The completion contract likewise says:

> `4. All threads are marked as resolved (after reviewer approval)`

— `~/.claude/commands/handle-pr-comments.md:24` (repeated at line 526)

**Text B (verbatim):**

> `- Resolve immediately if declining a suggestion (with explanation)`

— `~/.claude/commands/handle-pr-comments.md:81`

and:

> `6. Only resolve threads when: (a) reviewer confirms they're satisfied, OR (b) you're explicitly declining/ignoring the suggestion`

— `~/.claude/commands/handle-pr-comments.md:123`

The collision is immediate for a declined suggestion: Text B requires/permits resolution before
acknowledgment, while Text A categorically forbids resolution without acknowledgment and the final
checklist says approval is required.

**Runtime winner.** Without explicit user direction, neither contradictory same-file policy wins;
the conflict must be surfaced (`AGENTS.md:129-131`). If the owner explicitly directs an
evidence-backed decline and immediate resolution, that user instruction wins (`AGENTS.md:121`).
Actual GitHub behavior is **UNVERIFIED — experiment F4: on a disposable PR, provide a demonstrably
incorrect review suggestion, invoke `/handle-pr-comments`, and retain whether Claude fixes,
disagrees, waits for acknowledgment, or resolves immediately**. It is **likely (55-80%)** that the
repeated later exception at lines 123, 128, and 468 steers the model toward immediate resolution;
evidence is repetition, but no local rule establishes repetition or recency as precedence.

**Minimal resolution edit.** Preserve exhaustive handling without forcing bad changes:

* Change line 368 to `ALL comment types require an explicit disposition: fix, defer to a linked issue, or evidence-backed disagreement; trivial/nitpicks are not optional to process.`
* Change line 82 to `Never auto-resolve a fixed thread without reviewer acknowledgment; an explicitly declined suggestion may be resolved after posting the evidence-backed explanation.`
* Change checklist lines 24 and 526 to `All threads are resolved after reviewer approval, except explicitly declined suggestions resolved with an evidence-backed response.`

These are four prose-line edits on the existing command bus. They do not weaken the requirement to
fetch, respond to, and account for every comment. They pass the anti-overfit gate.

* `save-session.md:270` says never append to a previous session file, while lines 56-64 allow edits

* `update-docs.md:81-82` says generated sections come from code and manual sections are preserved.

* `start-task.md:11` says the router must not make the user choose, while lines 23 and 27 allow an
