## Runtime authority model (verified before deciding winners)

Claude’s current official custom-subagent documentation states that the Markdown body is the custom
agent’s system prompt, that each non-fork subagent starts in an isolated context, and that its final
message returns to the parent, which may summarize it. It also documents precedence between
*locations that define the same agent name*, but no precedence between two rules inside one agent
body and no severity arbitration between the outputs of different agents:
<https://code.claude.com/docs/en/sub-agents>.

The local runtime gives the same structural signal. `settings.json:419-440` registers generic
`SubagentStart` and `SubagentStop` dispatch, while
`hooks/subagent-lifecycle/stop.py:273-307` reads one `agent_type`, checks that one final assistant
message for degeneracy/result-contract conformance, and returns. Its decision path at
`stop.py:309-337` retries schema/contract failures; it does not compare two reviewers or reconcile
severity. A bounded search for the reviewer severity vocabulary and arbitration terms across the
hook and harness runtime found no relevant arbitration implementation; the detector control found
known-present `agent_type` and `SubagentStop` handling in the same files. Thus:

* for a conflict **within one agent file**, both texts occupy the same system-prompt layer. Neither
  has a mechanically enforced winner. Labels such as “MANDATORY” or later placement may influence
  the model, but treating that as precedence would be an assumption, not runtime verification;
* for a conflict **between distinct agents**, neither wins natively. Each returns an independent
  result and the parent/orchestration prompt decides what to do;
* the local `/orchestrate feature` prompt adds one path-specific ordering: `planner -> tdd-guide ->
  code-reviewer -> security-reviewer` at `commands/orchestrate.md:15-19`, and calls the security
  reviewer “Final approval” at `commands/orchestrate.md:91-101`. On that path, the security
  reviewer is operationally last. This is not a general Claude runtime precedence rule.

It is **very likely (80-90%)** that leaving same-layer contradictions unresolved will produce
task-to-task variation rather than a stable implicit winner, because the official runtime injects
the whole body as one prompt and the local hook validates shape rather than policy. The evidence is
the official loading model plus `stop.py:273-337`; a prospective settling experiment would run a
fixed set of paired synthetic diffs 30 times through each reviewer and measure verdict/severity
agreement.

## Findings

### F1 — HIGH-severity findings have incompatible merge effects

This is duplicate authority over the same decision: whether a HIGH finding permits merge.

**Text A, verbatim — generic reviewer:**

> “- **Warning**: HIGH issues only (can merge with caution)”  
> — `/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:212`

> “- **Block**: CRITICAL issues found — must fix before merge”  
> — `/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:213`

**Text B, verbatim — Python reviewer:**

> “- **Block**: CRITICAL or HIGH issues found”  
> — `/local_disk0/codexwork/bundle/claude/agents/python-reviewer.md:86`

**Text C, verbatim — TypeScript reviewer:**

> “- **Block**: CRITICAL or HIGH issues found”  
> — `/local_disk0/codexwork/bundle/claude/agents/typescript-reviewer.md:106`

**Concrete collision.** A changed `.py` file has a HIGH missing-type-annotation finding, or a changed
`.ts` file has a HIGH floating-promise finding. `code-reviewer` says HIGH is a warning and merge is
permitted with caution; the mandatory language reviewer says HIGH blocks. This is reachable, not
hypothetical: `code-reviewer.md:3` says it “MUST BE USED for all code changes,” while
`python-reviewer.md:3` and `typescript-reviewer.md:3` say they “MUST BE USED” for their respective
languages.

**Runtime winner.** Neither wins in Claude’s native subagent runtime. They execute in separate
contexts and return separate final messages; the parent must improvise reconciliation. No local
severity arbiter was found in the validated hook/runtime search described above. If only one agent
is explicitly invoked, that agent’s rule wins merely because the other authority was not loaded—not
because precedence was resolved.

**Minimal resolution — CONFIG.** Pick one merge taxonomy in a single shared reviewer contract and
remove the three local approval lists. The conservative minimal choice is `HIGH = block`, because it
matches both language-specific reviewers and avoids silently weakening them. Each agent should
retain only domain-specific classification examples and reference the shared taxonomy. This rides
the native agent/skill prompt bus and introduces no second runtime. It is **very likely (80-90%)**
to eliminate this collision because the only remaining authority would be the shared taxonomy;
evidence is the three quoted local lists. The settling test is a synthetic HIGH-only Python and
TypeScript diff through both reviewer routes, asserting identical envelope outcomes.

> “5. **Report findings** — Use the output format below. Only report issues you are confident about

> — `code-reviewer.md:26`

become separate typed outputs; evidence is that the existing schema already supports
`CONFIRMED|PLAUSIBLE`. The settling test is an endpoint with intentionally unavailable middleware
