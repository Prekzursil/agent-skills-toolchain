# A125 — coherence audit: commands / duplicate authority

## Executive result

I found **nine actionable duplicate-authority conflicts** inside the 71 personal command definitions. Six are internal contradictions in one command, two are conflicts between commands that participate in the same workflow, and one is an ordering collision in the `/start-task` router. I did **not** find a second commands tree to compare: the task names `~/.claude/commands/** (71)` on both sides, literally the same path. I therefore audited every pair of command authorities within that one tree rather than pretending that two copies existed.

The most consequential cluster is `/start-task`: its new deterministic router says to bypass gates for trivial or explicitly scoped work, but its legacy body subsequently says to run pre-task gates and ask for complexity confirmation before every task. The most mechanically definite defect is in `/handle-pr-comments`: prose claims REST-only operation while its executable workflow uses GraphQL twice.

Confidence in the inventory and quoted conflicts is **almost certain (90-99%)**, based on a complete whole-file scan, independent file counts, numbered source reads, and exact-text duplicate detection. Confidence is not stated as 100% because this is a read-only Linux snapshot, not a live invocation on the owner's Windows Claude Code installation.

### Runtime model used for “which wins”

Claude Code's current official documentation says that legacy `.claude/commands/<name>.md` files remain supported, that the file content defines the command, and that invocation passes the skill/command body to Claude as a prompt. It also says a skill body loads only when used. Evidence: [Claude Code — Extend Claude with skills](https://code.claude.com/docs/en/slash-commands) and [Claude Agent SDK — Slash commands](https://code.claude.com/docs/en/agent-sdk/slash-commands).

Therefore:

- Between two unrelated command files, neither normally “wins” merely by existing; the invoked command body is the active command prompt.
- Within one invoked command body, Claude Code does not compile headings into an ordered policy program. Conflicting same-level sentences are both present in the prompt. There is no documented “later line wins” rule. The runtime winner is consequently **none / undefined** unless the command text itself specifies an order or an executable shell block mechanically performs one behavior.
- `UserPromptExpansion` hooks can block expansion or add context, but they do not supply a documented line-precedence rule for contradictions inside the expanded body. Evidence: [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#userpromptexpansion).

Actual model choice under an internally contradictory prompt is **UNVERIFIED**; the settling experiment is to invoke each affected command in a disposable repository with a transcript-capturing `UserPromptExpansion` hook and a mock tool bus, repeat at least 30 times per supported model, and score which branch is taken. This does not change the verified conclusion that the platform itself defines no winner.

## Findings

### F1 — `/start-task` bypass router collides with unconditional legacy preflight

**Authority A (verbatim):**

> “Match the task top-to-bottom; **first match wins**. ~75-80% route with no extra model call. A `*`-prefix means the user already scoped it → skip to the work.”

`~/.claude/commands/start-task.md:13`

> “| read-only · <1 file · <3 tool-calls | **T0 just-do-it** (no gates) | the anti-over-engineering escape hatch — the router MUST be allowed to say "trivial" |”

`~/.claude/commands/start-task.md:17`

**Authority B (verbatim):**

> “Before starting any new task:”

`~/.claude/commands/start-task.md:37`

The ensuing unconditional checklist requires checking an active plan, running `bd prime`, checking PRs, and asking whether to handle PR comments (`start-task.md:39-57`). Later it also says:

> “Then ask the user to confirm your assessment:”

`~/.claude/commands/start-task.md:88`

**Concrete collision:** `/start-task * explain this one error` or a zero-file read-only query qualifies for immediate work/no gates, yet the same expanded command then requires multiple gates and at least two user questions.

**Runtime winner:** none. Both instructions are in the same expanded prompt; the router gives an early conceptual route but contains no explicit `return` or “skip Sections 0-4” instruction. Claude Code has no documented intra-body precedence rule.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Insert after the router: “For `*` and T0, perform the requested work immediately and stop interpreting this file; Sections 0-4 apply only to T1-T5.” Alternatively wrap the legacy body under `## T1-T5 only`. This is a two-line command edit, not a new router runtime.

### F2 — `/start-task` “first match wins” makes the high-stakes route unreachable for common high-stakes tasks

**Authority A (verbatim):**

> “Match the task top-to-bottom; **first match wins**.”

`~/.claude/commands/start-task.md:13`

> “| ≥3 files AND a spec / Definition-of-Done | **T2 metaswarm gates** | design → plan → adversarial → coverage |”

`~/.claude/commands/start-task.md:19`

**Authority B (verbatim):**

> “| high-stakes go/no-go · ship · merge · "are you sure?" | **T5 codex-council** (cross-model) | requires a 2nd CLI authed — VERIFY first, it silently no-ops otherwise |”

`~/.claude/commands/start-task.md:22`

**Concrete collision:** “Are you sure we should merge this 5-file security fix? Here is the DoD” matches both T2 and T5. Because T2 appears first, the explicitly high-stakes task never reaches T5.

**Runtime winner:** **T2**, according to the command's own mechanically explicit “top-to-bottom; first match wins” algorithm. This winner is verified from `start-task.md:13,19,22`; it is not an inference about model preference.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Move the T5 row to the top, then T4, then narrower cost/complexity routes, or state “T5 overrides all earlier shape matches.” Reordering one row preserves the minimal table router.

### F3 — `/start-task` says a complex-task issue is mandatory, then asks an optional yes/no question

**Authority A (verbatim):**

> “- For **complex tasks**: An issue is ALWAYS needed. Ask the user:”

`~/.claude/commands/start-task.md:133`

**Authority B (verbatim):**

> “> "This is a complex task. Should I create a GitHub Issue to track it?"”

`~/.claude/commands/start-task.md:134`

**Concrete collision:** the user answers “no.” One authority makes continuing without an issue invalid; the question presents “no” as a legitimate branch but defines no stop, downgrade, or override behavior.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Either change `ALWAYS needed` to “recommended” or retain the mandate and ask for permission with an explicit negative branch: “If declined, stop the complex workflow and ask whether to proceed via a user-approved no-issue exception.” The former is the smaller edit; the latter preserves the intended gate.

### F4 — `/review-design --skip-agent` cannot satisfy its own pass criterion

**Authority A (verbatim):**

> “| `--skip-agent <name>` | Skip specific agent (pm, architect, designer, security, cto) |”

`~/.claude/commands/review-design.md:43`

**Authority B (verbatim):**

> “The review gate passes when:”
>
> “- [ ] All five agents return APPROVED”

`~/.claude/commands/review-design.md:139-143`

The general APPROVED definition independently repeats “All agents approve” at `review-design.md:47-49`, providing a second source signal for the pass rule.

**Concrete collision:** `/review-design design.md --skip-agent designer` runs four agents; a fifth APPROVED verdict cannot exist, so the advertised option makes APPROVED unattainable.

**Runtime winner:** the skip option wins operationally if honored (only four agents run), while the verdict remains undefined/unreachable. There is no runtime mechanism that synthesizes an approval for a skipped agent.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Change the criterion to “All non-skipped agents return APPROVED; the report names every skipped agent and records the user-requested waiver.” This retains partial review without silently equating “not reviewed” with approval.

### F6 — `/handle-pr-comments` claims REST-exclusive operation while its required workflow uses GraphQL

**Authority A (verbatim):**

> “This command uses **REST API exclusively** to avoid GraphQL rate limit issues.”

`~/.claude/commands/handle-pr-comments.md:104`

**Authority B (verbatim):**

> “**Pattern**: Use GraphQL for thread operations (variables via -f/-F; parse with `-q` on fetch or `jq` for stored JSON) and REST for posting replies.”

`~/.claude/commands/handle-pr-comments.md:131` and duplicated independently at `:137`.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Replace line 104 with: “This command uses REST for comments/replies and GraphQL for review-thread resolution state; both rate limits matter.” Remove one of the duplicate pattern sentences at lines 131/137 so it cannot drift again.

### F7 — multi-model timeout policy says both “never kill” and “offer kill”

This duplicate authority occurs verbatim in two commands and nearly verbatim in a third.

**Authority A (verbatim):**

> “- If still incomplete after 10 minutes, continue polling with `TaskOutput`, **NEVER kill the process**”

`~/.claude/commands/multi-plan.md:59`; identical at `multi-execute.md:100`; punctuated equivalent at `multi-workflow.md:91`.

**Authority B (verbatim):**

> “- If waiting is skipped due to timeout, **MUST call `AskUserQuestion` to ask user whether to continue waiting or kill task**”

`~/.claude/commands/multi-plan.md:60`; identical at `multi-execute.md:101`.

`multi-workflow.md:92` adds “Never kill directly,” but still tells the agent to offer killing.

**Concrete collision:** a background model call remains incomplete after a ten-minute `TaskOutput` wait. Authority A permits only continued polling. Authority B presents killing as a user-selectable next action. If the user chooses kill, obeying B violates A.

**Runtime winner:** none until a user chooses. If the user explicitly selects kill, user instruction has higher general instruction precedence, but the command's own policy remains contradictory. Claude Code supplies no intra-command resolver.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Choose one canonical sentence and reference it from all three commands. Minimal safe wording: “After each 10-minute wait, continue polling; on a user status/stop request, report status and ask whether to keep waiting or cancel. Never cancel without explicit user instruction.” This reconciles persistence with user control.

**Authority A (verbatim):**

`~/.claude/commands/multi-plan.md:84`

**Authority B (verbatim):**

### F9 — configured coverage authority and `/test-coverage` hard-coded 80% authority can diverge

**Authority A (verbatim):**

> “1. **Coverage threshold** — "What test coverage threshold do you want to enforce?"”
>
> “- Options: "100% (Recommended)", "80%", "60%", "Custom"”

`~/.claude/commands/metaswarm-setup.md:226-227`

The setup then says:

> “### 4.2 — Customize .coverage-thresholds.json”

`~/.claude/commands/metaswarm-setup.md:321`, with threshold-writing instructions at `:323-347` and completion output identifying `.coverage-thresholds.json` at `:574`.

**Authority B (verbatim):**

> “Analyze test coverage, identify gaps, and generate missing tests to reach 80%+ coverage.”

`~/.claude/commands/test-coverage.md:3`

It operationalizes this as:

> “3. List files **below 80% coverage**, sorted worst-first”

`~/.claude/commands/test-coverage.md:20`.

**Concrete collision:** setup configures a project for 100% (the recommended option) or a custom threshold such as 90%, then the user invokes `/test-coverage`. The command stops prioritizing files once they reach 80%, below the configured enforcement target. A 60% configured project has the inverse mismatch: the command silently raises the target.

**Runtime winner:** there is no single winner. It is **very likely (80-90%)** that a runner configured by the setup command enforces the written project threshold while the `/test-coverage` prompt selects work using 80%; the evidence is the setup command's explicit threshold-specific runner commands at `metaswarm-setup.md:335-347` and the hard-coded selection rule at `test-coverage.md:20`. The command can therefore report/act toward one threshold while the runner fails or passes against another. Whether a current project in the snapshot has a non-80 threshold is **UNVERIFIED**; the settling experiment is to inventory project `.coverage-thresholds.json` files and invoke `/test-coverage` in disposable 60%, 80%, 90%, and 100% fixtures. The design conflict exists regardless because setup explicitly supports all four choices.

**Minimal resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** At command start, read `.coverage-thresholds.json` and native runner configuration; use the configured project threshold. Fall back to 80% only if no project authority exists, and print the selected source and value.

## Repetitions examined that are not findings

These duplicates are worth naming because they were reviewed and rejected rather than overlooked.

2. **Brainstorm/design review:** `/brainstorm` requires five approvals (`brainstorm.md:13-15`) and `/review-design` normally spawns five (`review-design.md:27-34`). They agree in the normal path. The only conflict is the explicit `--skip-agent` option reported as F4.

These are separate commands with separate terminal behaviors; neither invokes the other, so no concrete collision arises merely from their coexistence.
4. **Monitoring commands:** `/agent-monitor`, `/codex-monitor`, and `/compute-monitor` cover Claude subagents, Codex sessions, and served computations respectively (`agent-monitor.md:1-7`; `codex-monitor.md:1-7`; `compute-monitor.md:2,8-18`). Their read-only claims have different targets and do not collide.
5. **Save versus resume mutability:** `/save-session` writes a new snapshot and never appends to an old one (`save-session.md:270,274-275`); `/resume-session` treats the selected historical snapshot as read-only (`resume-session.md:152`). Different lifecycle phases make these complementary, not contradictory.
6. **Sequential versus parallel orchestration:** `/orchestrate` defines sequential chains but explicitly permits parallel independent checks (`orchestrate.md:7,39-46,140-155`). The scopes are explicit, so no collision arises.
7. **PR thread resolution:** “wait for reviewer acknowledgment” and “resolve immediately when explicitly declining” are presented as an explicit exception pair repeatedly (`handle-pr-comments.md:78-82,116-129,461-468`), not accidental drift.
8. **Learn versus learn-eval:** `/learn-eval` explicitly says it extends `/learn` with additional gates (`learn-eval.md:5-8`). Their different save-location decision depth is versioned behavior, not a situation in which both prompts are active. File-layout correctness is neighboring work, not duplicate-authority coherence.
9. **Review iteration escalation:** `/review-design` says max three iterations before escalation and separately offers override/defer/cancel (`review-design.md:55-68,166-168`). Those are successive states, not competing rules.

## Architecture and anti-overfit assessment

All nine fixes are edits to existing Markdown commands. They ride Claude Code's native command/skill prompt bus and add no second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Each proposal is tagged **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** because the change is prompt content rather than settings-only JSON; none qualifies as BUILD-LARGE.

A new policy engine would be counterproductive here. The failure mode is duplicated prose with missing scoping or exceptions. The minimal durable pattern is: one canonical rule, explicit state transitions, and thin command adapters that point to it. For the three multi-model commands in F7, centralizing the timeout paragraph in their already-shared skill/reference bus is **very likely (80-90%)** to reduce future drift, based on the existing exact duplication across three files and Claude Code's documented supporting-file mechanism. The uncertainty is whether maintainers will consistently update the shared reference; a mutation test that changes the canonical timeout sentence and asserts every command expansion contains it would settle that operational premise.
