# L05 — Executable dead-button / crash-on-edge audits for UI work

## Verdict

The best next mechanism is not another UI-review checklist, another general reviewer, or a seventh hook. It is an **executable interaction-proof lane** inside the already-built `ui-audit`/Playwright + journey-coverage + shared-ledger buses. For every enabled interactive control, it should produce a machine receipt proving either (a) a declared, user-observable effect occurred or (b) the control is intentionally inert/disabled; it should then stress the same controls under bounded failure and sequence perturbations. Before it may say “no dead buttons” or “no crash edges,” it must first catch injected known-dead and known-crashing controls.

This recommendation is **very likely (80-90%)** to find a materially different defect class from ordinary unit/build/E2E-green checks. Evidence: the current journey checker treats an exit-zero broad runner as covering every discovered journey without inspecting a control-level outcome (`/local_disk0/codexwork/bundle/claude/hooks/journey-coverage/check.py:126-141`); the corpus records only 20 Playwright clicks and four console inspections, versus 194 uses of the Playwright MCP server (`/local_disk0/codexwork/bundle/inputs/corpus.json:983-988,2327-2332,13387`); and the owner has explicitly asked for app-driving coverage rather than passive review (`/local_disk0/codexwork/bundle/inputs/corpus.json:10493-10494`). The exact incremental defect yield is **UNVERIFIED**; the settling experiment is a shadow A/B over 20 completed UI changes, comparing defects uniquely found by the interaction-proof lane against the existing project suite and existing `ui-audit` output.

No rejected component is introduced. There is no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. All findings ride Playwright, project-native test commands, the shared dispatcher/ledger, `OPEN-THREADS.md`, and the existing fresh-context/owner escalation surfaces.

### Relevant frontier, translated into this workspace

The research does not support “make the agent more proactive” as a license to interrupt more or act through ambiguity. It supports a narrower synthesis:

* **Human-AI teaming / mixed initiative:** allocate deterministic execution, enumeration, replay, and repair to automation; reserve semantic intent and irreversible authority for the owner. Horvitz defines mixed initiative as flexible contribution by human and computer at the appropriate time and foregrounds uncertainty/cost in deciding when automation should act ([Mixed-Initiative Interaction](https://www.microsoft.com/en-us/research/publication/mixed-initiative-interaction/); [Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). This maps to F2-F4 doing work autonomously and F8 escalating only ambiguity/authority.
* **Proactive and anticipatory computing:** anticipate likely failure surfaces from the changed UI and observed dependency graph, run them before the owner encounters them, and defer notification until a consolidated result is ready. Horvitz explicitly treats attention, timing, costs, benefits, and uncertainty as coupled design variables (same primary paper). This maps to silent shadow execution, bounded fault/sequence exploration, and one batched question—not a background agent that continuously nags.
* **Personalization:** learn only from explicit owner choices and verified outcomes. The local correction miner’s 41/41 false-positive smoke sample (`corpus.json:10371-10374`) is concrete evidence that raw conversational pattern mining is unsafe personalization. Amershi et al. include learning from user behavior while supporting correction and control, based on multiple evaluation rounds and 49 practitioners ([CHI 2019 primary paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). F6/F8 use explicit decisions, expiry, and correction rather than inferred personality.
* **Trust calibration:** expose bounded proof and bounded uncertainty. A “100% UI tested” confidence badge is not calibration; exact denominators, canary performance, state/fault/sequence budgets, stale hashes, and incomplete frontier are. Recent empirical/analytic work finds that discrimination between correct and wrong decisions is as important as calibration for collaborative accuracy ([Steyvers & Peters, 2026](https://www.sciencedirect.com/science/article/pii/S0022249626000192)). F1 and F7 make detector discrimination visible.
* **Executable UI QA frontier:** Playwright already supplies actionability, retrying semantic assertions, accessibility snapshots, route-level fault injection, trace replay, and event channels; fast-check supplies command preconditions, async/scheduled model runs, replay seeds, and shrinking. The frontier move is to compose these into a calibrated control-effect protocol, not add another reasoning runtime ([Playwright actionability](https://playwright.dev/docs/actionability), [ARIA snapshots](https://playwright.dev/docs/aria-snapshots), [network mocking](https://playwright.dev/docs/mock), [fast-check model-based testing](https://fast-check.dev/docs/advanced/model-based-testing/)).

## Architecture in one page

```text
UI diff / explicit UI task
        |
        v
existing skill router -> existing ui-audit / project Playwright command
        |                            |
        |                            +--> canary fixture: LIVE / DEAD / THROW
        |                                   must classify all three correctly
        v
runtime control inventory (role + accessible name + route + ordinal)
        |
        +--> single-action effect probe (clean context per control)
        +--> bounded action-sequence probe (replayable seed, shrinking)
        +--> network/browser fault matrix (allowlisted, isolated)
        +--> keyboard/viewport/lifecycle differential
        |
        v
typed ui_proof.json receipt + trace/screenshot/console/network artifacts
        |
        v
existing event ledger / TaskCompleted / journey-coverage consumer
        |
        +--> deterministic failure: agent fixes without asking owner
        +--> ambiguous intent or irreversible action: one batched owner question
        +--> clean receipt: one terse completion line; no prompt fatigue
```

Hook budget: **zero new hook registrations**. The receipt consumer folds into the existing shared `TaskCompleted` dispatcher and replaces the current command-name-only satisfaction rule in journey coverage. Every wrapper is `try/except` (or JS `try/finally` plus top-level catch), records `checker_error`, and exits 0 on its own failure. Fail-open means the hook never crashes or traps the owner; it does **not** mean a failed checker fabricates a passing UI receipt.

## Findings — inferred surprises first

### F1 — Certify the auditor with known-dead and known-crashing canaries before auditing the product

**Improvement.** Add a detector-certification prelude: every run first audits a generated local fixture containing (1) a live button that increments an externally observed counter and updates a status region, (2) an enabled dead button whose click produces no effect, and (3) a button whose handler throws. The product audit is allowed to emit absence claims only if it classifies all three correctly.

**What it is.** This turns “the test ran” into “the detector demonstrated sensitivity and specificity immediately before the test.” It directly operationalizes the workspace law that absence requires a known-positive control. The fixture should be generated under the run artifact directory, never added to the product, and served from the same browser project/config so browser/tool failures affect both canary and subject equally.

**Why-inferred.** The owner did not merely ask for more testing; the live-defect record says seven wrong calls were separated from correct calls only by known-positive controls (`INPUT-known-harness-defects.md:107-129`). The corpus also contains a `SwfocTrainer.UiTests.dll` failure fingerprint (`corpus.json:5774`), showing UI tests can fail, but a suite failure says nothing about whether a dead-button detector can recognize a known dead button. The inferred need is therefore calibration of the auditor itself.

**How-to-build.** Extend the existing `ui-audit` command with a preflight module of roughly 80-120 lines:

1. Write one self-contained HTML fixture to the run temp directory with stable `data-audit-id` attributes `canary-live`, `canary-dead`, `canary-throw`.
2. Attach `page.on('pageerror')`, `page.on('console')`, request-failure, dialog, popup, download, and filechooser listeners before navigation.
3. Inventory the three controls from the accessibility/DOM surface, click each through normal Playwright actionability (never `force`), and compute the effect vector defined in F2.
4. Require `live=effect`, `dead=no_effect`, and `throw=pageerror_or_process_failure`. Require two mechanically independent signals for the known-present live canary: its accessible status text changes **and** a separate test-side counter/network-free event log increments.
5. If any canary is misclassified, write `audit_status=DEGRADED`, include the raw trace, skip all absence conclusions, exit the command nonzero, and let the hook wrapper itself exit 0 after recording degradation.
6. Unit-test the classifier with fixed effect vectors; integration-test it in Chromium and the primary project browser.

**External signal that verifies it.** A real browser execution against code the auditing agent did not author in its same reasoning context, with known ground-truth labels embedded in the fixture; success requires the Playwright event stream plus DOM/status counter. A second process parses `ui_proof.json` and independently checks the three expected classifications.

**SOTA citation.** Playwright makes click actionability concrete—unique, visible, stable, event-receiving, enabled—and fails on unmet conditions ([official actionability documentation](https://playwright.dev/docs/actionability)). The canary goes beyond actionability by testing post-click effect. Microsoft’s human-AI guidelines were validated through multiple evaluation rounds and a 49-practitioner study, emphasizing support for efficient correction and scoped behavior rather than unearned trust ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**NATIVE-vs-BUILD.** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).

**Value x effort.** transformative x low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it; it is isolated, reversible, non-destructive, and does not involve owner preference.

**Confidence.** **Almost certain (90-99%)** that this prevents the specific “detector found nothing because detector was broken” conclusion class: the defect report supplies both the failed detector and the successful known-positive-control discrimination (`INPUT-known-harness-defects.md:120-129`). Defect-yield uplift beyond that class is **likely (55-80%)**, supported by the current journey gate’s command-level rather than oracle-level logic (`journey-coverage/check.py:126-141`).

### F2 — Replace “click succeeded” with a declared effect-vector oracle for every enabled control

**Improvement.** Exhaustively probe every reachable enabled control and require a semantically allowed, externally observable effect. This is the core dead-button detector.

**What it is.** At each declared page/state, build a runtime inventory keyed by `route + role + accessible-name + stable-test-id (if present) + ordinal fallback`. For each control, use a fresh browser context or checkpointed state, capture `S0`, perform the action, settle with web-first assertions/polling, and capture `S1`. The effect vector is:

* navigation/history/URL change;
* popup, dialog, download, file chooser, clipboard request, or focus transfer;
* network request with a declared method/endpoint class and terminal response;
* accessible state change (`pressed`, `checked`, `expanded`, `selected`, `disabled`, `invalid`);
* visible or accessibility-tree content/status change;
* declared storage/state mutation;
* an explicit validation/recovery message for rejected input.

A control is `DEAD` only when it was actionable, its contract expects an effect, no allowed effect occurs within the bounded settle window, and no crash signal supersedes it. “Some DOM changed” is insufficient; ambient clocks/spinners/telemetry must be normalized away. An intentionally inert control must be actually disabled or carry an explicit per-project exemption with a reason and expiry—not merely be ignored by the model.

**Why-inferred.** Playwright click has zero recorded tool errors across 20 calls (`corpus.json:983-988`), but the corpus separately shows the owner asking for full app automation/coverage (`corpus.json:10493-10494`). The surprise is that action delivery and product response are separate propositions. The current claim guard treats an exit-zero command containing an E2E signature as functional evidence (`claim-guard/README.md:47-54`); it does not prove each enabled control caused its promised effect.

**How-to-build.** Add a `control_probe.mjs` adapter to the current UI audit:

1. Discover controls through roles (`button`, `link`, `checkbox`, `radio`, `switch`, `tab`, `menuitem`, `option`, text inputs) plus native interactive elements not correctly exposed through accessibility. Record missing accessible names as separate quality failures, not as invisible controls.
2. Ignore disabled/hidden controls but record them in the denominator and reason. Reject `force: true` because it would bypass the receives-events check.
3. For each control, restore a clean storage state or declared setup checkpoint. Execute pointer activation and, where applicable, keyboard activation.
4. Poll the exact allowed effect for up to a small project-configured bound using Playwright web assertions. Capture all event channels from before the action.
5. Emit `controls_discovered`, `controls_actionable`, `controls_probed`, `controls_effect_verified`, `dead`, `crashed`, `skipped_with_reason`, and stable per-control records. The denominator makes “3/3” distinguishable from “3 passed, 47 never discovered.”
6. On dynamic pages, repeat inventory after each successful state transition until the control-key frontier stabilizes or a strict action/state budget is reached. Budget exhaustion is `INCOMPLETE`, never green.

**External signal that verifies it.** Browser-observed state/event deltas and process exit data, compared by the test runner to a declarative effect contract. The agent’s prose judgment is not an oracle.

**SOTA citation.** Playwright’s official assertions re-fetch and retry until a concrete state is observed, including URL, accessibility, text, value, screenshot, and response assertions ([assertions documentation](https://playwright.dev/docs/test-assertions)). ARIA snapshots expose roles and states such as checked, disabled, expanded, invalid, pressed, and selected ([ARIA snapshot documentation](https://playwright.dev/docs/aria-snapshots)). WCAG requires detected input errors to identify the item and describe the error in text, so “form stayed put” alone is not an acceptable rejection effect ([W3C WCAG 2.2, Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification)).

**NATIVE-vs-BUILD.** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus). Playwright supplies the event/action/assertion primitives; the small build is the effect classifier and receipt emitter.

**Value x effort.** transformative x medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it for read-only/idempotent controls in disposable/local state; confirm-first for controls whose contract marks payment, publication, deletion, external messaging, or other irreversible effects.

**Confidence.** **Very likely (80-90%)** that per-control effect receipts are more probative than current command-name coverage, because the current implementation explicitly promotes a bare broad runner to coverage of all specs (`journey-coverage/check.py:126-141`) while Playwright exposes the required independent event/state channels. The correct default settle time and ambient-delta normalizers are **UNVERIFIED**; settle them with a labeled 100-control corpus containing delayed valid effects and known ambient churn, optimizing false-dead and false-live rates before enforcement.

### F3 — Search crash edges as replayable, shrinking action sequences—not hand-picked “edge cases”

**Improvement.** Run bounded model-based action sequences over the real UI and automatically reduce any crash to the smallest replayable sequence.

**What it is.** Single clicks miss history-dependent failures: double submit, open-close-open, back during save, reload while modal state exists, escape during async completion, select-delete-undo, rapid filter changes, two tabs sharing storage, and focus/blur races. Represent available UI actions as commands with preconditions, run seeded sequences against clean contexts, and treat uncaught errors, browser/page closure, process nonzero exit, unhandled rejection, invariant violation, or persistent busy state as failures. Persist seed and replay path.

**Why-inferred.** The owner repeatedly asks the harness not to stop before everything is finished (`corpus.json:10425-10426`) and places a hard bar on crash-on-edge quality. The current journey implementation covers files/commands, not adjacent action pairs or histories (`journey-coverage/check.py:61-78,126-141`). Proactive sequence exploration removes the need for the owner to imagine and enumerate every edge.

**How-to-build.** Add a bounded `sequence_probe.mjs` mode:

1. Convert the current state’s actionable inventory into commands: activate, fill boundary value, clear, press Enter/Escape/Tab, back, forward, reload, open/close, resize, and duplicate activation.
2. Give every command a precondition derived from the current accessibility state so the generator does not spend its budget on impossible actions.
3. Start with deterministic pairwise sequences around changed controls, then 50-200 seeded sequences of length 2-12 under a wall-time budget. Use fresh browser contexts and fixed data fixtures.
4. After every command, assert global invariants: page/browser alive; no pageerror/unhandled rejection; no endless busy indicator; at most one destructive request per single activation unless contract says otherwise; focus remains in a valid document; and a visible/programmatic recovery status exists after expected rejection.
5. On failure, shrink by deleting commands and simplifying inputs until the shortest still-failing replay remains. Emit a Playwright test snippet, seed/path, trace, and state snapshots.
6. Promote every unique minimized escape to a permanent project regression journey; deduplicate by normalized stack + action sequence + control key.

Fast-check availability in the owner’s relevant UI projects is **UNVERIFIED**; the settling experiment is `Get-Command node`, then project-local `npm ls fast-check --depth=0` and a disposable `asyncModelRun` smoke test. If absent, start with a dependency-free deterministic pairwise generator; installing fast-check is confirm-first. The proposal does not depend on installing it.

**External signal that verifies it.** A separate test process executes the seed against the real browser and reproduces the same normalized failure twice from clean state. The minimized replay, not the originating model’s assessment, closes the loop.

**SOTA citation.** fast-check’s current model-based testing defines commands with precondition checks and real-system execution, provides async and scheduled runners, efficiently shrinks failing scenarios, and persists seed/path/replayPath ([official model-based testing guide](https://fast-check.dev/docs/advanced/model-based-testing/)). Its own warning says the model must not be a copy of the system—exactly the external-oracle constraint here.

**NATIVE-vs-BUILD.** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).

**Value x effort.** transformative x medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it within disposable/local fixtures; confirm-first before dependency installation or sequences that can cross an irreversible boundary.

**Confidence.** **Likely (55-80%)** to find history-dependent failures missed by golden journeys, supported by the formal ability to generate/shrink command sequences and the local gate’s lack of sequence coverage. Exact sequence budget and yield are **UNVERIFIED**; the settling experiment is a shadow run over 20 UI changes, reporting unique minimized failures per minute and flaky-reproduction rate.

### F4 — Inject dependency failures at the UI boundary and require observable recovery

**Improvement.** Automatically test every changed journey against a bounded network/browser fault matrix: empty, slow, rejected, malformed, stale, duplicated, and offline dependencies.

**What it is.** A button is not “working” if it works only against the one happy response used by the author. For each API call observed during the baseline journey, replay the journey while routing that endpoint through cases appropriate to its schema: 204/empty collection, empty object, malformed JSON/content type, 400 validation, 401/403 auth, 404 missing, 409 conflict, 429 with retry metadata, 500/503, connection abort, delayed response, and browser offline. Assertions require no crash, no infinite busy state, input preservation where retry is possible, a programmatically determinable error/status, and a working retry/cancel path.

**Why-inferred.** The corpus’s general WebFetch error rate is 5.57% (448/8,042; `corpus.json:71-77`), Playwright navigation has 20.45% tool errors (`corpus.json:623-628`), and the owner’s quality bar explicitly includes crash-on-edge. These do not prove product API failures, but they show dependency failure is routine enough that happy-path-only UI proof is poorly calibrated.

**How-to-build.** Reuse Playwright network routing:

1. Run one baseline journey, collect same-origin/allowlisted API requests, and classify safe read versus mutation by method plus project contract. Do not fuzz third-party or destructive endpoints live.
2. For each changed control’s dependency, generate a compact applicable fault set. Cap combinatorics by testing one fault at a time, then only pair faults for previously failing endpoints.
3. Install `browserContext.route()` before navigation; block service workers for this lane so interception is observable, unless the service worker itself is the declared subject.
4. After activation, assert `role=alert/status` or an explicit focused error dialog; retry must generate a new request and clear busy state; cancel must return focus to a stable control.
5. Record the injected fault, intercepted request, UI recovery state, console/page errors, and trace. A route not exercised is `NOT_REACHED`, not pass.
6. Test websocket-dependent controls with a small declared close/malformed/delay matrix only where the project uses websockets.

**External signal that verifies it.** The test-side route log proves the fault was actually delivered; the browser accessibility tree and event stream prove recovery; request count proves retry/dedup behavior. These are independent of the implementing agent’s explanation.

**SOTA citation.** Playwright officially supports tracking, modifying, mocking, and HAR-replaying XHR/fetch traffic ([Mock APIs](https://playwright.dev/docs/mock)); its network guide documents request routing and notes that service workers can hide events unless blocked ([Network](https://playwright.dev/docs/network)). WCAG status messages are specifically meant to expose success, waiting, results, and errors without needlessly interrupting the user ([W3C Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)).

**NATIVE-vs-BUILD.** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).

**Value x effort.** high x medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it for mocked/local endpoints; confirm-first if the only available environment can cause real external mutations or consume paid/quota-limited resources.

**Confidence.** **Very likely (80-90%)** that this mechanically distinguishes “dependency failed but UI recovered” from “dependency failed and UI crashed,” because both the injected request and browser recovery state are observable through independent native channels. The optimal per-status applicability map is **UNVERIFIED**; settle it by comparing the generated cases with each project’s OpenAPI/schema and by replaying five known historical API-failure fixtures before enforcement.

### F5 — Differentially audit pointer, keyboard, viewport, and lifecycle without multiplying owner prompts

**Improvement.** Run the same control contract across input and lifecycle variants, then compare semantic outcomes rather than screenshots alone.

**What it is.** For each high-value/changed control, execute: pointer click; Enter/Space where role semantics require it; sequential Tab navigation; narrow viewport/reflow; 200% zoom or equivalent viewport scaling; reload/back/forward after state change; and, when supported, touch emulation. Require the same semantic effect class across applicable modalities, valid focus order/return, no keyboard trap, and no offscreen/obscured actionable control. Use screenshots only as diagnostic artifacts; accessibility state, focus, URL/network, and execution errors remain the pass/fail oracles.

**Why-inferred.** The corpus shows screenshot capture more often than click or console inspection (`corpus.json:719-724,983-988,2327-2332`). A screenshot can reveal layout slop but cannot prove keyboard operability or that a control survived reload. The owner wants concrete full-functional coverage, and proactive differential execution supplies it without asking them to enumerate devices.

**How-to-build.** Add a project matrix to the existing UI-audit config:

1. Default quick lane: primary browser, desktop viewport, pointer + keyboard activation for changed controls.
2. Completion lane: installed project browsers and two viewports (mobile/narrow and desktop), keyboard traversal, reload/back state checks.
3. Compare the effect-vector class from F2, not pixel identity. A desktop dialog and mobile sheet may differ visually but must produce the same declared state transition.
4. After modal open/close, assert focus enters the modal, remains contained while open, and returns to the invoking control. After validation error, assert the erroneous item is identified and reachable.
5. Attach screenshot/trace only on failure or first baseline to control artifact noise.
6. Respect a wall-time budget; unrun variants remain explicit `INCOMPLETE` obligations in F6 rather than disappearing.

**External signal that verifies it.** Real browser actionability, focus, accessibility tree, URL/network, and process/error signals under separately configured contexts. Cross-variant agreement is computed by the runner, not visually judged by the authoring model.

**SOTA citation.** Playwright actionability checks whether the element is visible, stable, receives events, and is enabled ([official docs](https://playwright.dev/docs/actionability)). WCAG 2.2’s operable surface includes keyboard access, no keyboard trap, concurrent input mechanisms, dragging alternatives, and target size ([W3C WCAG 2.2 Understanding index](https://www.w3.org/WAI/WCAG22/Understanding/)).

**NATIVE-vs-BUILD.** CONFIG (settings/JSON only) once F2’s runner exists; projects declare applicable browsers, viewports, and control exemptions in the receipt manifest.

**Value x effort.** high x low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **Very likely (80-90%)** to expose modality-specific dead controls and lifecycle crashes when they exist, because it executes the same declared effect through mechanically different browser inputs. Prevalence in this owner’s projects is **UNVERIFIED**; settle it with a shadow matrix over the next 20 UI changes and report unique failures by modality.

### F6 — Turn UI promises and discovered controls into expiring proof obligations so no thread disappears

**Improvement.** Bind each discussed UI commitment and each newly discovered enabled control to a durable obligation that closes only on a fresh per-control receipt.

**What it is.** Extend the existing `OPEN-THREADS.md`/event-ledger convention with typed `ui_obligation` records: `control_key`, `journey`, `promised_effect`, `source` (owner request, accepted plan, changed UI diff, or runtime discovery), `risk`, `created_at`, `changed_set_hash`, `status`, and `receipt_id`. Runtime-discovered controls are automatically added as `needs_effect_contract`; owner-stated/accepted controls carry their wording and may not be silently superseded by a later model summary. Completion means every in-scope obligation is `verified`, `intentionally_disabled` with evidence, or explicitly deferred by the owner—not merely absent from the final answer.

**Why-inferred.** The owner’s “never drop a thread” constraint is reinforced by repeated corpus patterns asking the agent why it stopped (`corpus.json:10425-10426`) and to proceed until named deliverables exist (`corpus.json:10489-10490`). The event ledger is already append-only and treats failures as first-class (`event-ledger/ledger.py:10-13,61-65`), so losing UI commitments is an integration gap, not a reason to add memory infrastructure.

**How-to-build.** Use the existing note/ledger bus:

### F7 — Replace broad-run green receipts with typed, fresh, denominator-bearing UI proof

**Improvement.** Make `ui_proof.json` the only evidence class that can satisfy a “no dead buttons / UI works end-to-end” claim.

**What it is.** The existing journey checker’s externality is good, but its evidence is too weak: any successful command naming a spec covers that spec, and a bare broad E2E command covers all specs (`journey-coverage/check.py:119-141`). ### F8 — Calibrate autonomy: silently fix deterministic failures, batch only ambiguous/irreversible decisions

**Improvement.** Make the audit proactive without turning the owner into its test oracle or notification queue.

**What it is.** A three-lane response policy based on external evidence:

* **Just fix:** reproducible dead control, pageerror, duplicate submit, missing status/error semantics, focus trap, or failed known contract in a reversible local branch.
* **One batched clarification:** no declared effect for a newly discovered control, conflicting owner/plan contracts, or an action that must touch money, deletion, publication, messages, credentials, or live external state.
* **Report only:** clean receipt or degraded checker. Clean is one terse line with counts and artifact path; degraded says what was not verified and names the settling command. No repeated reminders.

This is personalization by revealed preference, not speculative psychology: the owner wants exhaustive autonomous completion, does not want threads dropped, and treats focus/prompt fatigue as a first-class constraint. The ledger may remember explicit choices such as “this control intentionally stays disabled until X,” but it must never infer permission for destructive action from prior silence.

**Why-inferred.** Corpus patterns repeatedly request continued completion (`corpus.json:10377-10394,10425-10426`), while the candidate miner itself warns against overtrusting inferred owner messages (`corpus.json:10371-10374`). The correct response is not more questions; it is better external evidence and selective escalation. AskUserQuestion already exists at meaningful volume (1,329 calls, 39 errors; `corpus.json:111-117`), so no new dialog mechanism is needed.

**How-to-build.** Configuration/policy on existing mechanisms:

1. Add `autonomy` and `risk` to each UI obligation/effect contract.
2. Deterministic failures automatically open/retain a thread and route back to implementation; after repair, a fresh browser context reruns the minimized failing replay plus impacted audit.
3. Collect all semantic ambiguities during the run. At the end, issue at most one AskUserQuestion containing 1-3 highest-impact decisions, each with control label, current behavior, observed trace, safe options, and default “leave disabled/defer.” Remaining low-impact ambiguity stays open, not forgotten.
4. Use a fresh-context second model only to summarize a trace or challenge an ambiguous classification; because intrinsic same-context checking is rejected, that model receives raw receipt/artifacts without the author’s conclusion. Its judgment never overrides execution failure.
5. Learn only from explicit owner decisions and later verified outcomes. Do not use unfiltered correction candidates as personalization facts.
6. Emit one completion capsule: `UI PROOF: 47/47 actionable controls; 12 fault cases; 100 sequences; 0 dead; 0 crashes; canaries 3/3; hash ...`, or the exact incomplete delta.

**External signal that verifies it.** Deterministic lanes close only on fresh browser receipts. Ambiguous/high-stakes lanes close only on an owner answer (or remain open). A fresh-context model is an independent challenge signal, never the sole verifier.

**SOTA citation.** Horvitz’s mixed-initiative principles call out uncertainty about user goals, the costs/benefits of automated action, and the timing of interventions with respect to attention ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). Amershi et al.’s empirically evaluated guidelines cover scoping services when uncertain, supporting correction, and learning from user behavior ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). Recent empirical work finds that useful uncertainty communication matters for human-AI collaboration, but calibration and metacognitive discrimination—not decorative confidence—drive complementarity ([Journal of Mathematical Psychology, 2026](https://www.sciencedirect.com/science/article/pii/S0022249626000192)).

**NATIVE-vs-BUILD.** CONFIG (settings/JSON only): route existing AskUserQuestion, fresh-context verification, event-ledger, and Workflow behavior by receipt/risk state. No new agent type or hook.

**Value x effort.** high x low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it for adopting the policy; the policy itself says confirm-first at irreversible/authority boundaries.

**Confidence.** **Very likely (80-90%)** to reduce owner interruption relative to per-defect questioning because it deterministically batches and suppresses prompts while retaining open obligations. The best batch size and interruption timing are **UNVERIFIED**; settle them with a four-week ledger measure of questions per UI task, owner deferrals/corrections, time-to-close, and reopened threads, with the owner choosing the acceptable prompt budget.

## Build order and acceptance tests

The smallest coherent delivery is:

1. **F1 canaries + F2 effect vector + F7 receipt** in shadow mode. Without these, later stress lanes can produce impressive but uncalibrated noise.
2. **F4 dependency faults + F5 modality/lifecycle matrix**, still on deterministic declared journeys.
3. **F3 sequence exploration/shrinking** after the single-action oracle is stable.
4. **F6 obligation join + F8 escalation policy** to close the owner loop without prompt fatigue.

Acceptance is mechanical:

* The canary fixture must produce exactly live/effect, dead/dead, throw/crash in two consecutive clean browser contexts.
* A product fixture with one enabled no-op button must yield nonzero audit exit, `dead.length=1`, a stable control key, trace, and no “clean” receipt.
* A product fixture whose click throws must be detected through `pageerror` plus either console/runner/process failure; one signal alone is diagnostic, not the final absence/broken conclusion.
* A delayed valid action must not be falsely called dead when the declared web-first assertion settles inside its bound.
* A button covered by ambient clock changes but no declared effect must still be dead.
* A 500/abort/429 route must be proven delivered by the route log; recovery must be proven in the accessibility tree; a route never reached is incomplete.
* A known four-action crash must shrink to a replay that reproduces twice from clean state.
* `probed != actionable`, failed canaries, stale changed-set hash, missing artifact, partial receipt, runner nonzero, or any `incomplete` item must prevent a verified UI claim.
* The hook wrapper must exit 0 on malformed receipt, missing Playwright, browser crash, timeout, permission error, and internal exception, while best-effort recording `checker_error`. It must never fabricate a pass.
* One UI task with ten deterministic failures must generate zero owner questions while the agent can safely repair; three semantic ambiguities generate at most one batched question; unanswered items remain in `OPEN-THREADS.md`.

## Anti-overfit gate

Each proposal passes the gate:

* It uses the existing browser/test, skill-router, dispatcher, ledger, TaskCompleted, journey-coverage, AskUserQuestion, and open-thread buses.
* The shared mechanics are small adapters and schemas; project-specific semantic effects stay declarative.
* The system does not ask an LLM to re-judge its own UI in the same context. Models may propose contracts or summarize artifacts, but only browser execution, a second context, a deterministic parser, or the owner closes a loop.
* It adds zero hooks. The existing journey-coverage classifier is folded/replaced, not duplicated.
* It is deliberately bounded: changed controls first, declared journeys, pairwise then seeded sequences, one fault at a time, strict wall-time/state budgets, artifacts mainly on failure.
* No previously rejected architecture is reintroduced.

## Alternatives rejected

1. **“Add a UI checklist to AGENTS.md.”** Rejected by construction: same-context self-attestation, no external signal, prompt fatigue, and no replayable defect.
2. **“Have the authoring model click around and visually confirm.”** Rejected by construction: action and judgment remain in one context; screenshots cannot prove effects or crash absence.
3. **“Run Playwright and accept exit 0.”** Rejected because current local logic already does the command-level version (`journey-coverage/check.py:126-141`); it lacks control denominators and per-effect proof.
4. **“Use a second model as the UI judge.”** Rejected as the primary oracle. A second context is mechanically independent, but functional outcomes are cheaper and stronger when observable through browser state/events. A second model is reserved for ambiguous intent/artifact challenge.
5. **“Exhaustively traverse every possible UI state.”** Rejected as unbounded and overfit. The proposed frontier/state/action budgets, changed-control prioritization, model preconditions, and persistent incomplete obligations are honest about finite exploration.
6. **“Install a hosted observability/visual-regression SaaS.”** Rejected: it violates the anti-overfit component list, adds credentials/cost, and is unnecessary for dead-button/crash evidence already exposed by Playwright traces and the local ledger.
7. **“Add a seventh completion hook.”** Rejected. The existing consolidated TaskCompleted/Stop paths are explicit in settings (`settings.json:458-505`); this work folds into those consumers.
