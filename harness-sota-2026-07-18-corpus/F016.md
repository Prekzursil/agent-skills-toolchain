# F016 — Frontier research: continual learning and non-stationarity as models change

**Unit:** F016  
**Research date:** 2026-07-19  
**Scope:** What an agent harness can reliably retain, test, adapt, and retire while its foundation model, provider runtime, tools, tasks, and owner preferences change. The focus is deployed, API/CLI-based language agents, not continual pre-training as an end in itself.

## Executive judgment

The important distinction is between **the model learning** and **the harness learning**. This owner does not control the weights of the Claude and Codex models used by the harness. For this system, practical continual learning therefore means changing external state—versioned instructions, skills, memories, routing, and tests—based on verified experience. Weight-level continual learning remains relevant background, but importing its infrastructure would solve the wrong layer.

What is established is comparatively modest:

1. Model endpoints and model aliases are non-stationary. Anthropic says Claude Code aliases update over time, while full model IDs pin an underlying version for that ID's lifetime; it also publishes retirement schedules and tells applications to test replacements before migration ([Claude Code model configuration](https://code.claude.com/docs/en/model-config), [Claude model IDs and versioning](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions), [Claude model deprecations](https://platform.claude.com/docs/en/docs/about-claude/model-deprecations)). OpenAI likewise says pinned model versions plus application evals are the best way to obtain consistent prompting behavior ([OpenAI API backward compatibility](https://platform.openai.com/docs/api-reference/backward-compatibility)).
2. An agent score is a property of **model + harness + tools + environment + grader**, not a model constant. Anthropic's operational eval guidance explicitly defines an evaluated agent as harness plus model, recommends multiple trials because outputs vary, distinguishes outcome from what the agent says happened, and separates capability from regression suites ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
3. Static test sets age. LiveCodeBench and LiveBench use dated, continuously refreshed, automatically graded items to limit contamination and measure performance over time windows ([LiveCodeBench paper](https://arxiv.org/abs/2403.07974), [LiveCodeBench repository](https://github.com/LiveCodeBench/LiveCodeBench), [LiveBench paper](https://arxiv.org/abs/2406.19314), [LiveBench repository](https://github.com/LiveBench/LiveBench)).
4. Retaining past text is not equivalent to useful learning. Recent agent benchmarks find that naive replay can inject irrelevant context or degrade held-out performance, and that self-feedback can recursively drift; controlled reuse and external feedback matter ([LifelongAgentBench](https://arxiv.org/abs/2505.11942), [AGENTCL](https://arxiv.org/abs/2606.02461), [SkillLearnBench](https://arxiv.org/abs/2604.20087)). The last two are recent 2026 preprints, so their individual magnitudes are not established even though their failure modes agree with older self-correction evidence ([ICLR 2024: Large Language Models Cannot Self-Correct Reasoning Yet](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)).

The harness should consequently adopt a small **model-transition/evidence loop**, not a self-improvement runtime: record exact provenance, maintain a stable regression bank plus a fresh temporal slice, replay incumbent and candidate models in matched conditions with repeated trials, promote only changes supported by executable outcomes or calibrated human review, and retain rollback. This rides the current hook/skill/ledger/basic-memory/background-bench buses. No new vector database, knowledge graph, daemon, durable execution engine, trained critic, guardrail framework, or observability service is justified.

The most urgent harness-specific mismatch is already visible. Claude is configured with the moving alias `"model": "opus[1m]"` (`/local_disk0/codexwork/bundle/claude/settings.json:77`), and many delegated agents use the moving family aliases `opus` or `sonnet` (for example `/local_disk0/codexwork/bundle/claude/agents/tdd-guide.md:5` and `/local_disk0/codexwork/bundle/claude/agents/intent-drift-sentinel.md:5`). Codex is configured with a named slug in both execution and review fields (`/local_disk0/codexwork/bundle/codex/config.toml:18-19`), but the local adapter warns that Codex self-reports its slug as unknown and requires verification from the session header (`/local_disk0/codexwork/bundle/claude/agents/codex.md:40-43`). A run can therefore change behavior without the harness possessing a trustworthy, joined model-transition record.

## Research method and evidence standard

This report distinguishes four evidence levels:

- **Established:** replicated problem class, official platform contract, peer-reviewed result with direct operational relevance, or direct local configuration/corpus evidence.
- **Promising but unproven:** positive benchmark evidence without cross-model, cross-environment, temporal, or owner-specific validation. Every such claim carries the mandated confidence band and its evidence.
- **Hype:** a stronger operational claim than the evidence licenses. The report names the diagnostic tell.
- **Recommendation:** a concrete harness change with exactly one implementation tag and an explicit anti-overfit decision.

Local corpus claims use `/local_disk0/codexwork/bundle/inputs/corpus.json`. Its `_meta` records 11,633 files seen, zero failed, 10.62 GB, 1,564,084 parsed lines, one bad line, and 32 oversized lines. Counts are usable for presence and frequency, not causal effectiveness. Its `hooks` field is deliberately excluded because the detector is marked broken in the pinned input. Hook effectiveness is not inferred from transcript silence.

The bundled audit files are treated as leads, not facts. When one supplied a useful lead—such as Agent Workflow Memory in `audit-findings/D01.md:68`—the conclusion below cites the primary publication instead ([Agent Workflow Memory, ICML 2025](https://proceedings.mlr.press/v267/wang25bx.html)).

“Post-cutoff” below means work appearing after the mature 2024 evidence base or so recently that independent replication and operational uptake are thin, especially 2026 preprints. Such items are explicitly lower-confidence even though the research date permits finding them.

## Definitions: what can drift, and what can learn

Treating every change as “model drift” produces bad diagnoses. This harness has at least six independently changing layers:

| Layer | Example | Observable discriminator |
|---|---|---|
| Model identity | `opus` resolves to a newer release; a Codex slug changes | Exact provider, resolved model ID, CLI version, session header |
| Provider/runtime | sampler, safety layer, backend routing, rate limits | Provider fingerprint if exposed; repeated identical probes; release notes |
| Harness | prompt, rule, hook, skill, routing, tool schema | Content hash and deployment receipt |
| Tool/environment | MCP availability, dependency version, Windows process limits | Tool catalog/health plus concrete external postcondition |
| Task distribution | owner moves from reverse engineering to research or new APIs | Project/task-family/time metadata |
| Stored knowledge | memory becomes stale, over-general, or contradicted | `valid_as_of`, scope, evidence, supersession, revalidation outcome |

“Continual learning” in this report means improvement over an ordered experience stream while retaining useful earlier capability and avoiding harmful interference. “Adaptation” is any change after evidence. “Non-stationarity” is a change in one or more layers above. “Drift detection” is evidence of a persistent distribution or behavior change, not merely one different stochastic output.

This decomposition matters because Anthropic reports that infrastructure allocation alone can affect agentic coding evaluation and recommends controlling resource configuration and running at multiple times/days ([Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise)). A single worse run is therefore insufficient to blame a model upgrade.

# 1. Established

## 1.1 Versioned models and moving aliases are operational facts

Anthropic's current contract says each Claude model ID pins an underlying version for that ID's lifetime, while Claude Code convenience aliases such as `opus`, `sonnet`, and `haiku` point at recommended versions and update over time ([Model IDs and versioning](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions), [Claude Code model configuration](https://code.claude.com/docs/en/model-config)). Anthropic also distinguishes active, legacy, deprecated, and retired states, gives publicly released models at least 60 days' retirement notice, and recommends thorough application testing of replacements before retirement ([Model deprecations](https://platform.claude.com/docs/en/docs/about-claude/model-deprecations)). OpenAI's API documentation independently recommends pinned versions and application evals for consistency ([OpenAI backward compatibility](https://platform.openai.com/docs/api-reference/backward-compatibility)).

Consequences that follow directly:

- A model family alias is a **channel**, not an experimental treatment identifier. Comparing June and July runs labeled only `opus` does not establish that the model was constant ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)).
- A pinned ID controls model identity but does not freeze tools, system prompts, CLI behavior, dependencies, or infrastructure. Anthropic's infrastructure study explicitly shows that environment configuration is a first-class eval variable ([Quantifying infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)).
- Pinning forever is not an availability strategy because versions retire. A controlled migration lane is necessary ([Claude deprecations](https://platform.claude.com/docs/en/docs/about-claude/model-deprecations)).

## 1.2 Agent evaluation must measure outcomes, variance, and the whole system

Anthropic's 2026 field guidance formalizes several practices that are directly applicable here: record the complete trajectory; distinguish the final environment state from an agent's claim about that state; use code-based, model-based, and human graders appropriately; run multiple trials; track pass@k when any success matters and pass^k when consistency matters; maintain capability and regression suites separately; and inspect transcripts to verify graders ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). This is official practitioner guidance rather than a randomized trial, but its core points are established by the mechanics of stochastic multi-turn agents.

Objective graders deserve priority where a postcondition exists. An agent saying “done” is not the same signal as tests passing or the requested file existing; Anthropic uses this exact outcome/claim distinction in its definitions ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The local harness already encodes the same principle: it requires a receipt and a postcondition for terminal success, and two mechanically independent signals for absence/failure claims (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:20-37`).

LLM judges are useful only as a calibrated layer, not ground truth. Peer-reviewed work documents position, verbosity, and self-enhancement limitations in LLM judging ([Judging LLM-as-a-Judge, NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/file/91f18a1287b398d378ef22505bf41832-Paper-Datasets_and_Benchmarks.pdf)); later work finds that evaluators can recognize and favor their own outputs relative to human judgments ([LLM Evaluators Recognize and Favor Their Own, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/7f1f0218e45f5414c79c0679633e47bc-Paper-Conference.pdf)). Therefore, changing the candidate model and the judge model simultaneously changes both the object and the ruler.

## 1.3 Temporal test sets address benchmark aging, not all contamination

LiveCodeBench continuously collects dated contest problems, publishes versioned releases, and supports start/end-date scoring; its paper evaluates code generation plus self-repair, execution, and output prediction ([paper](https://arxiv.org/abs/2403.07974), [repository](https://github.com/LiveCodeBench/LiveCodeBench)). LiveBench similarly refreshes objective, automatically scored tasks from recent sources across multiple domains ([paper](https://arxiv.org/abs/2406.19314), [repository](https://github.com/LiveBench/LiveBench)). These establish two useful design properties:

- Preserve a **fixed regression bank** to detect backsliding.
- Add a **fresh, time-indexed capability slice** so optimization against the fixed bank cannot masquerade as general progress.

“Contamination-free” should not be read literally as an eternal proof. New items can later enter training corpora, test-generation policies can leak, and an eval can saturate. Anthropic recommends monitoring saturation and treating an evaluation suite as a maintained living artifact ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Thus temporal separation reduces a known risk; it does not prove deployment validity.

## 1.4 Weight-level continual learning establishes the stability/plasticity problem, not this harness's solution

Sequential neural-network training can overwrite earlier capabilities; continual-learning research calls the central tradeoff stability versus plasticity. Elastic Weight Consolidation slows changes to parameters judged important to earlier tasks ([Kirkpatrick et al., PNAS 2017](https://www.pnas.org/doi/10.1073/pnas.1611835114)); Gradient Episodic Memory uses remembered examples and constraints to limit harmful interference while measuring backward and forward transfer ([Lopez-Paz and Ranzato, NeurIPS 2017](https://proceedings.neurips.cc/paper_files/paper/2017/hash/f87522788a2be2d171666752f97ddebb-Abstract.html)). A 2024 Nature study shows loss of plasticity in long-running deep supervised and reinforcement learning and reports benefit from maintaining small weights and continual reinitialization in its tested settings ([Loss of plasticity in deep continual learning](https://www.nature.com/articles/s41586-024-07711-7)).

Those results establish that “keep training on new examples” is not safely monotonic. They do not establish that EWC, replay buffers, or continual backpropagation belong in an API agent harness. This system cannot update proprietary provider weights, and adding a training stack would be a new runtime with a different safety and evaluation burden.

## 1.5 External feedback is materially different from intrinsic reflection

Reflexion showed that agents can improve on tested sequential decision, coding, and reasoning tasks by storing natural-language feedback rather than changing weights ([Reflexion, NeurIPS 2023](https://papers.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)). CRITIC showed improvement from tool-interactive critique, where external tools provide evidence during correction ([CRITIC, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)). In contrast, controlled work on intrinsic self-correction found that models often fail to improve reasoning without external feedback and can degrade correct answers ([Huang et al., ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)).

The established conclusion is not “reflection never works.” It is narrower: a reflection becomes actionable evidence when it is anchored to an independent outcome, tool result, human correction, or accepted test—not merely because a model wrote a plausible diagnosis.

## 1.6 Selective workflows can transfer, but undifferentiated replay can hurt

Agent Workflow Memory induces reusable workflows from trajectories and selectively supplies them on later tasks. In ICML 2025 experiments it improved relative success on Mind2Web and WebArena and generalized across task/website/domain splits ([Agent Workflow Memory](https://proceedings.mlr.press/v267/wang25bx.html)). This establishes that compact workflow abstractions can outperform providing no learned workflow in those web-navigation settings.

It does not establish “store every trajectory.” LifelongAgentBench reports limited effectiveness from conventional experience replay because irrelevant material and context limits interfere ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)). The very recent AGENTCL preprint goes further: controlled compositional streams distinguish memory designs better than naive streams, while naive and held-out settings often show limited gains or memory-induced degradation ([AGENTCL](https://arxiv.org/abs/2606.02461)). The robust operational lesson is selective, scoped reuse plus held-out evaluation—not maximal memory.

## 1.7 The local harness already contains pieces of a continual-learning system, but not an outcome loop

The following are direct, positive local observations:

- Durable memory instructions already require `valid_as_of` on new facts and `superseded_by` on retired facts (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-11`).
- The event ledger is explicitly designated objective turn-history ground truth, while basic-memory is semantic memory (`/local_disk0/codexwork/bundle/claude/AGENTS.md:85-91`).
- A weekly harness bench runs the semantic-router eval, compares skill/MCP recall against a baseline, logs regressions through the existing background digest, never auto-acts, and retains the higher baseline (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:1-9`; implementation at `/local_disk0/codexwork/bundle/claude/hooks/harness-bench/bench.py:150-184`). Its current baseline covers 14 skill cases, five MCP cases, and two negative-fire cases (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/baseline.json`).
- `/learn-eval` drafts reusable skills, checks overlap, and asks the user before saving (`/local_disk0/codexwork/bundle/claude/commands/learn-eval.md:18-90`).
- `/self-reflect` requires user selection before knowledge capture and contains deduplication and conflict-resolution guidance (`/local_disk0/codexwork/bundle/claude/commands/self-reflect.md:107-184`).

The missing link is also directly observable: `/learn-eval`'s quality verdict is a model synthesis of uniqueness/specificity/reusability and does not require a successful external postcondition, a counterexample, a model ID, or a held-out replay before saving (`/local_disk0/codexwork/bundle/claude/commands/learn-eval.md:54-88`). Its default says “when in doubt, choose Global” (`:23-27`), which increases the blast radius of a model-specific lesson. `/self-reflect` allows a single PR observation to be “medium” confidence (`/local_disk0/codexwork/bundle/claude/commands/self-reflect.md:174-180`) and generalizes file paths as a canonicalization rule (`:165-172`), which can erase the boundary that made a fact true. These are candidate-generation mechanisms, not validated continual learning.

The corpus confirms actual but sparse use: `capability_use.skills_invoked` records `continuous-learning-v2=2`, `learn-eval=2`, `self-reflect=18`, `prompt-optimize=2`, and `prompt-optimizer=1` in `/local_disk0/codexwork/bundle/inputs/corpus.json`; it also records 408 basic-memory write calls, 357 searches, and 353 reads in `tool_usage`. Presence is established. Improvement caused by any of them is not measurable from these counts.

# 2. Promising but unproven

Every item in this section is deliberately below “established for this harness.”

## 2.1 Outcome-gated textual skill learning

**Confidence: likely (55-80%)**, based on Reflexion's multi-domain benchmark improvements, AWM's peer-reviewed cross-distribution web-navigation gains, and this harness's existing skill/memory buses; transfer to the owner's heterogeneous Windows research/coding/reverse-engineering workload remains **UNVERIFIED — experiment:** replay at least 30 ordered, owner-derived tasks with no memory versus candidate workflow memory, using executable postconditions, a held-out later task family, and the same resolved model ID ([Reflexion](https://papers.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html), [AWM](https://proceedings.mlr.press/v267/wang25bx.html)).

The promising mechanism is not raw transcript retrieval. It is a compact candidate rule/workflow with explicit scope, evidence, failure boundary, and verification, promoted only after it helps on later work. That is close to skills the harness already understands.

## 2.2 Automated prompt compilation per model version

DSPy treats prompt and few-shot selection as compilation against an explicit metric, while GEPA evolves prompts using trajectory-level natural-language reflection and Pareto selection ([DSPy paper](https://arxiv.org/abs/2310.03714), [DSPy repository](https://github.com/stanfordnlp/dspy), [GEPA paper](https://arxiv.org/abs/2507.19457), [GEPA repository](https://github.com/gepa-ai/gepa)).

**Confidence: likely (55-80%)** that offline optimization can improve a narrow, objectively graded harness component such as schema adherence or skill routing, based on published task gains and open implementations; general improvement of full autonomous workflows is **UNVERIFIED — experiment:** optimize only on a development split, then compare the generated prompt against the human prompt over a frozen held-out regression bank and a later temporal slice, across at least two resolved model versions. GEPA is a 2025 preprint and its comparisons do not establish unattended production safety ([GEPA](https://arxiv.org/abs/2507.19457)).

**Confidence: unlikely (20-45%)** that a single optimized prompt remains best after a major model transition, because optimization targets a particular model/metric distribution and provider guidance requires application testing at migration; **UNVERIFIED — experiment:** take prompts optimized for incumbent and candidate models and run the full 2×2 prompt-by-model cross-over ([Claude deprecations](https://platform.claude.com/docs/en/docs/about-claude/model-deprecations), [OpenAI backward compatibility](https://platform.openai.com/docs/api-reference/backward-compatibility)).

## 2.3 Automatically generated skills

SkillLearnBench is directly relevant and unusually cautionary. Its recent 2026 preprint evaluates 20 tasks/100 verified instances and reports that continual skill-generation methods beat a no-skill baseline in aggregate, but no method leads across all tasks/models; open-ended tasks remain difficult; stronger backbones do not reliably yield better skills; and self-feedback alone induces recursive drift ([paper](https://arxiv.org/abs/2604.20087), [official repository](https://github.com/cxcscmu/SkillLearnBench)).

**Confidence: roughly even (45-55%)** that this harness's current `/learn-eval` candidates would beat a no-new-skill baseline on future owner work, because it has user confirmation and duplicate checks but lacks the benchmark's required outcome/trajectory evaluation; **UNVERIFIED — experiment:** run a prospective sequence of repeated task families, randomly expose later tasks to the approved candidate skill or the prior harness, and grade objective outcomes plus tool cost. The confidence is capped because SkillLearnBench is a two-month-old preprint with only 20 tasks and because the local corpus provides invocation counts rather than outcome labels ([SkillLearnBench](https://arxiv.org/abs/2604.20087), `/local_disk0/codexwork/bundle/inputs/corpus.json::capability_use`).

## 2.4 Controlled continual-learning benchmarks for agents

LifelongAgentBench, AGENTCL, Continual Learning Bench, and SkillLearnBench are converging on ordered task streams, retention/transfer measurement, verified task outcomes, and comparisons between persisted and reset memory ([LifelongAgentBench](https://arxiv.org/abs/2505.11942), [AGENTCL](https://arxiv.org/abs/2606.02461), [Continual Learning Bench](https://continual-learning-bench.com/docs/), [SkillLearnBench](https://arxiv.org/abs/2604.20087)).

**Confidence: very likely (80-90%)** that ordered-stream evaluation with a reset-memory control is more diagnostic than counting saved memories, because it directly tests whether earlier experience changes later verified outcomes and because AGENTCL finds naive streams unable to discriminate designs; owner-specific effect sizes are **UNVERIFIED — experiment:** construct paired streams from the 2,268 correction candidates, preserving chronology and hiding later cases, then compare persistent versus reset state ([AGENTCL](https://arxiv.org/abs/2606.02461), `/local_disk0/codexwork/bundle/inputs/corpus.json::owner_correction_candidates`). This claim is methodological, not a claim that the new benchmarks' leaderboards generalize here.

## 2.5 Deployment replay against a candidate model

OpenAI reported in June 2026 that it uses privacy-preserving replays of prior conversations to simulate candidate-model deployment, while acknowledging coverage and representativeness limits ([Deployment Simulation](https://openai.com/index/deployment-simulation/)). Anthropic says teams with evals can test new models and retune prompts more quickly ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

**Confidence: very likely (80-90%)** that a bounded replay set will catch more owner-specific model regressions than generic leaderboard inspection, because it executes the actual harness/task contract; **UNVERIFIED — experiment:** replay a privacy-scrubbed, stratified sample of historical tasks on incumbent and candidate model versions with matched tool snapshots, then compare objective outcomes and owner-correction proxies. Replay coverage will remain incomplete, as OpenAI explicitly notes ([Deployment Simulation](https://openai.com/index/deployment-simulation/)).

## 2.6 Black-box endpoint fingerprints and change-point detection

Behavioral probe sets and statistical change detection could detect an undocumented endpoint change. However, probabilistic outputs, prompt sensitivity, safety routing, and infrastructure noise confound attribution. Anthropic explicitly recommends multiple times/days for shared coding evals because infrastructure affects outcomes ([Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)).

**Confidence: roughly even (45-55%)** that a small behavioral canary can detect large, task-relevant drift before the owner notices, based on black-box measurability and repeated-trial eval practice; **UNVERIFIED — experiment:** pre-register a probe set, collect repeated baseline trials across days, inject a known model-ID transition as a positive control, and require both a statistical shift and a task-outcome regression. Confidence is capped because no primary evidence found demonstrates low false-alarm black-box drift detection on this exact Claude Code/Codex harness.

## 2.7 Test-time non-parametric policy adaptation

JitRL, a January 2026 preprint, stores trajectories and modulates output logits using retrieved experience, reporting gains on WebArena and Jericho without gradient updates ([JitRL](https://arxiv.org/abs/2601.18510), [repository](https://github.com/liushiliushi/JitRL)).

**Confidence: very unlikely (5-20%)** that JitRL is an appropriate near-term mechanism for this harness, because it requires output-logit control not exposed by the ordinary proprietary CLI/API agent path and would introduce a policy/runtime layer; compatibility is **UNVERIFIED — experiment:** confirm whether every target provider exposes the needed token logits and intervention point, then reproduce on an owner-derived sandbox stream. Even a positive reproduction would still fail the current anti-overfit gate unless it materially beats the small external-state loop.

# 3. Hype, and the tell that gives it away

## 3.1 “The agent learns from every interaction”

**Tell:** “learning” is measured by the number of stored reflections, instincts, vectors, or skills rather than later held-out task outcomes. LifelongAgentBench reports that conventional replay has limited effectiveness, and AGENTCL reports memory-induced degradation in naive/held-out settings ([LifelongAgentBench](https://arxiv.org/abs/2505.11942), [AGENTCL](https://arxiv.org/abs/2606.02461)). Storage is an exposure; transfer is the outcome.

Applied locally, `continuous-learning-v2=2` invocations and hundreds of memory operations prove use, not benefit (`/local_disk0/codexwork/bundle/inputs/corpus.json::capability_use` and `::tool_usage`). Any claim that this harness already “continuously improves” from those counts is unsupported.

## 3.2 “Recursive self-improvement” from model-authored reflection

**Tell:** the same model proposes the lesson, judges the lesson, and promotes the lesson, with no executable environment signal, independent reviewer, or held-out task. Intrinsic self-correction can degrade reasoning ([Huang et al., ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)); LLM judges have self-preference and other biases ([NeurIPS 2023 judge study](https://proceedings.neurips.cc/paper_files/paper/2023/file/91f18a1287b398d378ef22505bf41832-Paper-Datasets_and_Benchmarks.pdf), [NeurIPS 2024 self-preference study](https://proceedings.neurips.cc/paper_files/paper/2024/file/7f1f0218e45f5414c79c0679633e47bc-Paper-Conference.pdf)); SkillLearnBench reports recursive drift from self-feedback alone ([SkillLearnBench](https://arxiv.org/abs/2604.20087)).

The local `/learn-eval` “holistic verdict” is useful candidate triage, but calling it validation would cross this line because it does not require an independent outcome (`/local_disk0/codexwork/bundle/claude/commands/learn-eval.md:54-88`).

## 3.3 “No catastrophic forgetting” after a higher aggregate score

**Tell:** the paper or product reports only final average success, not per-task retention, backward transfer, negative transfer, or a reset-memory control. Continual-learning methods were created precisely because new-task improvement can overwrite old tasks ([EWC](https://www.pnas.org/doi/10.1073/pnas.1611835114), [GEM](https://proceedings.neurips.cc/paper_files/paper/2017/hash/f87522788a2be2d171666752f97ddebb-Abstract.html)). For a harness, a new skill that improves one task while increasing schema errors or tool retries elsewhere is not an unqualified improvement.

## 3.4 “Model X got worse” from one before/after run

**Tell:** no exact resolved model IDs, harness hashes, tool/environment snapshot, repeated trials, or confidence interval. Anthropic says model aliases move and agent trials vary; it separately documents infrastructure noise ([Claude model configuration](https://code.claude.com/docs/en/model-config), [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)). A single changed answer can be real and still fail to identify the changing layer.

## 3.5 “Contamination-free benchmark” as a permanent property

**Tell:** no item release dates, model cutoff relationship, versioned releases, or refresh policy. LiveCodeBench and LiveBench provide these mechanisms ([LiveCodeBench repository](https://github.com/LiveCodeBench/LiveCodeBench), [LiveBench repository](https://github.com/LiveBench/LiveBench)). Even then, the defensible claim is reduced contamination risk for a defined time window—not metaphysical freedom from contamination.

## 3.6 “SOTA lifelong agent” on one synthetic environment

**Tell:** one model, one domain, a handful of seeds, no cross-version replication, and no negative-transfer report. Voyager is an important proof that an executable skill library can support exploration and transfer in Minecraft, but Minecraft results do not establish a general production skill-learning policy ([Voyager](https://arxiv.org/abs/2305.16291)). JitRL's WebArena/Jericho results similarly do not establish suitability for proprietary CLI agents ([JitRL](https://arxiv.org/abs/2601.18510)).

## 3.7 “More memory is more intelligence”

**Tell:** retrieval precision, context cost, stale-fact rate, conflict handling, and held-out degradation are absent. AWM's contribution is selective workflow induction, not unlimited recall ([AWM](https://proceedings.mlr.press/v267/wang25bx.html)); LifelongAgentBench identifies irrelevant replay and context length as failure modes ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)). The owner's existing `valid_as_of`/`superseded_by` convention is directionally correct because temporal validity matters (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:7-11`).

## 3.8 “Automatic prompt optimization replaces eval design”

**Tell:** the optimizer and evaluator share the same development set; success is reported on the optimized metric only; no temporal or held-out slice exists. DSPy and GEPA optimize against a supplied metric, so a bad or saturated metric is optimized just as efficiently ([DSPy](https://arxiv.org/abs/2310.03714), [GEPA](https://arxiv.org/abs/2507.19457)). Optimization raises the value of evaluation discipline; it does not remove it.

## Final design position

The frontier does not justify a self-modifying mega-harness. It justifies a disciplined **external continual-learning loop**:

```text
experience
  -> independent outcome / owner correction
  -> scoped candidate lesson
  -> incumbent-vs-candidate replay
  -> retention + fresh-task checks
  -> human-approved promotion
  -> provenance + temporal validity
  -> rollback or revalidation at model transition
```

That loop is small enough to survive stronger future models, yet it preserves the evidence needed to exploit them. **Confidence: very likely (80-90%)** that this is a better fit than autonomous self-rewriting for the present harness, based on official model lifecycle/eval guidance, peer-reviewed external-feedback results, recent negative evidence on naive replay and self-feedback, and the harness's already-existing buses ([Claude model lifecycle](https://platform.claude.com/docs/en/docs/about-claude/model-deprecations), [Anthropic agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [AWM](https://proceedings.mlr.press/v267/wang25bx.html), [Huang et al.](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html), [SkillLearnBench](https://arxiv.org/abs/2604.20087), `/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:1-9`).
