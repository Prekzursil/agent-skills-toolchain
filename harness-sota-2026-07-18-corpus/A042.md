# A042 — Coherence audit of `~/.claude/rules/kotlin/hooks.md`

## Scope and verdict

This unit audited the complete 17-line Kotlin hook rule supplied at
`/local_disk0/codexwork/bundle/claude/rules/kotlin/hooks.md`. The rule applies to `*.kt`,
`*.kts`, and `build.gradle.kts` (`hooks.md:1-6`), says that it extends the common hook rule
(`hooks.md:7-10`), and directs three PostToolUse behaviors to be configured in
`~/.claude/settings.json`: format with ktfmt/ktlint, analyze with Detekt, and run
`./gradlew build` (`hooks.md:11-17`).

The operative result is not a subtle partial implementation: all three Kotlin-specific behaviors
are **UNENFORCED** in the supplied harness. `settings.json` does register generic PostToolUse
dispatchers and `per-edit-check` (`settings.json:310-354`), but the checker has no Kotlin dispatch
and falls through to a silent success (`hooks/per-edit-check/check.py:151-170`). The local dispatcher
manifest contains only memory-spool, tool-result-sentinel, and stub-ledger PostToolUse checks
(`hooks/_dispatch/manifest.json:144-180`). The shared harness's default module list contains no
formatter, Detekt, or Gradle runner (`agents/harness/modules.py:2599-2613`), and its PostToolUse ledger
path records results/mutations and runs an injection tripwire rather than executing project checks
(`agents/harness/modules.py:1036-1046`).

The target also collides conditionally with the higher-precedence long-operation contract, overlaps
the Java rule on `build.gradle.kts` with a different validation threshold, duplicates Kotlin style
tool selection with inconsistent roles, and omits two active cross-language enforcements that
explicitly include `.kt`. The measured corpus cannot establish whether humans/agents manually
compensated for the missing hooks. That behavioral question is **UNVERIFIED; the settling experiment
is to scan the raw transcripts for successful edits to `.kt`/`.kts`, then inspect the immediately
following tool calls and file hashes for formatter, Detekt, and Gradle executions**. The supplied
distillation does not retain that evidence, and its hook detector is explicitly broken.

## Method and detector controls

All subject-tree work was read-only. The only write is this artifact.

I used two mechanically independent signals before reporting important absences:

1. **Static registration/code signal.** I parsed `settings.json` as JSON and enumerated the four
   PostToolUse registrations; none names Kotlin tooling. I then read the registered checker and both
   dispatch paths. The known-present control was `PostToolUse` itself: the parser found the shared
   dispatcher, Bash output compressor, per-edit checker, and local dispatcher exactly as shown at
   `settings.json:310-354`. The target-negative signal was the absence of `kotlin`, `ktlint`, `ktfmt`,
   `detekt`, and `gradlew` from those registrations/manifests, plus the explicit unsupported-extension
   fallthrough at `per-edit-check/check.py:151-170`.
2. **Runtime dispatch signal.** I imported the read-only checker, replaced its Python checker with a
   sentinel, and called `_run_check` with three paths. The known-present control returned
   `known.py => (['CONTROL_PY_DISPATCH'], False)`; `target.kt` and `target.kts` both returned
   `([], False)`. This exercises the dispatch logic independently of text search and confirms the
   static reading of `per-edit-check/check.py:157-170`.
3. **Corpus detector signal.** A recursive string walk over the parsed corpus found 28 occurrences of
   the known-present control `Bash`, but zero of `kotlin`, `ktlint`, `ktfmt`, `detekt`, `gradlew`,
   `build.gradle.kts`, `.kt`, or `.kts`. An independent `rg` scan found two structured
   `"tool": "Bash"` controls and no Kotlin terms. This proves only that the *distillation* contains no
   Kotlin evidence; it does not prove no Kotlin work occurred.
4. **Missing-skills detector signal.** `test -f` found the known-present target rule and Claude
   `AGENTS.md`. Direct directory tests reported both `bundle/claude/skills` and
   `bundle/agents/skills` absent. An independent bounded `find` listed the sibling known-present
   `claude/rules`, `claude/hooks`, and `claude/agents` directories but no skills directory.

## Precedence applied

Claude `AGENTS.md` §10 is explicit: user/permissions rank first, safety second, the cross-tool
contract third, project/repo governance fourth, and third-party skill/plugin defaults fifth
(`claude/AGENTS.md:115-128`). Lower layers may add restriction but cannot relax safety, and genuine
same-level conflicts must be surfaced rather than silently resolved (`claude/AGENTS.md:129-131`).

The rules README separately says a language-specific rule overrides a common rule
(`claude/rules/README.md:93-104`). That statement is narrower than, and subordinate to, AGENTS §10.
Therefore:

- AGENTS §4a wins over the Kotlin rule whenever a Gradle build is expected to exceed 60 seconds.
- Kotlin-vs-Java and Kotlin-hooks-vs-Kotlin-style collisions are same-level rule collisions. AGENTS
  §10 does **not** select a winner; they need an explicit project-aware resolution.
- Settings and hook code are implementation, not a higher-precedence instruction. Their silence does
  not override the rule; it demonstrates non-enforcement.
- Any skill default would rank below the rule/project layer, but skill contents were not supplied, so
  no skill collision can honestly be adjudicated.

## Consolidated resolution architecture

### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Use one project-aware Kotlin/Gradle adapter on the existing hook bus, not three global hard-coded
commands:

1. On `.kt`/`.kts` edit, discover only repository-declared tooling and run a measured-fast formatter
   or file-scoped check. Emit explicit success/failure/skip status and changed-file readback context.
2. Defer project-wide Detekt and broad Gradle verification to Stop/completion unless a benchmark
   proves they fit the fast per-edit budget.

   file-extension rules independently launch overlapping task graphs.
5. Put generic duplicate/wiring policies in `common/hooks.md`; keep Kotlin rules specific to Kotlin
   tooling and point to one tool-role source of truth.
6. Add fixture tests for Java-only Kotlin-DSL, JVM Kotlin, Android, and KMP projects, including absent
   formatter/Detekt cases and a synthetic long build.

This passes the anti-overfit gate: it uses the current PostToolUse/Stop bus and `longrun`, introduces
no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained
critic, observability SaaS, or guardrail framework. It is **very likely (80-90%)** to restore rule/code
coherence because every confirmed defect is at the existing dispatch/config boundary; evidence is
