# A105 — Coherence audit: agents versus commands / silent override

## Executive verdict

The unpacked subject contains **18 agent definitions and 71 command definitions**, not the task's approximate 27 agents. I read and decoded every byte of all 89 Markdown files (112,392 agent bytes / 2,536 lines; 271,439 command bytes / 8,180 lines). The coverage limitation is real: this artifact can make conclusions about the 18 agent files present in the remote bundle, not the nine agent files implied by the task estimate but absent from that bundle.

I found **three confirmed text/runtime collision families**:

1. `/e2e` says the dispatched agent uses Playwright, while `e2e-runner` makes Agent Browser primary and Playwright fallback; its mandatory JSON-only final also supersedes the command's illustrated human report.
2. `/python-review` illustrates a human Markdown/text report and assigns inconsistent severity to missing context managers, while `python-reviewer` mandates a single JSON handoff and makes missing context managers CRITICAL.
3. `/orchestrate` requires Markdown handoffs from every agent, while the invoked `code-reviewer` and `security-reviewer` agents each require exactly one JSON block and forbid surrounding prose.

These are not same-name file resolution collisions. Current Claude Code treats legacy `commands/*.md` as skill prompts in the main conversation. A custom agent definition is loaded as the subagent system prompt only when delegation occurs. Thus there is **no universal “agents beat commands” or “commands beat agents” rule**. In the three concrete command-directed delegations above, the agent's system prompt governs the spawned worker, while the command remains the parent/task prompt. The agent therefore wins the contradictory worker-level policy. Evidence for that runtime model is the current official documentation: [Extend Claude with skills](https://code.claude.com/docs/en/slash-commands) says legacy `.claude/commands/<name>.md` files create slash-invoked skills; [Create custom subagents](https://code.claude.com/docs/en/sub-agents) says a non-fork subagent receives its agent body as the system prompt and a separate delegation task message. The same page says natural-language naming lets Claude decide whether to delegate, while an `@` mention guarantees it.

The three command files do **not** use the native deterministic binding fields `context: fork` and `agent:`. Two independent static signals establish this: (1) a frontmatter scan found `name:` only in six command files and no `context:` or `agent:` fields in any of 71; (2) an exact search for `context: fork`, `agent: e2e-runner`, `agent: python-reviewer`, `agent: planner`, and `agent: intent-drift-sentinel` returned zero command hits, while the same detector found the known-present agent names at `agents/*:2`. Consequently, the prose claims “invokes”/“dispatch” are model-mediated requests, not a deterministic runtime binding.

The best repair is consolidation, not another router: bind commands that genuinely need isolation using Claude Code's native `context: fork` + `agent:` fields, and delete duplicated behavioral/output policy from the command body. Keep one authoritative policy in the agent definition and leave only task arguments plus command-specific acceptance criteria in the command. This is **NATIVE (Claude Code already does this; we just enable it)**. It rides the existing skill/subagent bus and adds no orchestration runtime, memory store, critic, SaaS, durable engine, or guardrail framework, so it passes the anti-overfit gate.

I am **almost certain (90-99%)** that this consolidation removes the identified static contradictions, because each contradiction exists as duplicated literal policy and the proposed edit leaves one copy. Whether the owner's installed Windows Claude Code version accepts `context: fork` in legacy `commands/*.md` directly is **UNVERIFIED**; the settling experiment is to copy one affected command into a disposable project, run `claude --debug`, invoke it once, and confirm a `SubagentStart` event for the named agent. The current official docs say legacy commands and skills “work the same way,” making direct support **very likely (80-90%)**, but this Linux job node has no `claude` executable and cannot execute the owner's Windows runtime.

## Finding 1 — `/e2e`: Playwright command policy is silently overridden by Agent Browser policy

Severity: **degrading**. The command promises a specific primary execution stack and examples; the spawned agent uses a different primary stack. The difference can change setup, selectors, commands, artifacts, and debugging.

### Both texts, verbatim

Command side:

> “This command invokes the **e2e-runner** agent to generate, maintain, and execute end-to-end tests using Playwright.”  
> — `claude/commands/e2e.md:7`

> “The e2e-runner agent will:”  
> “2. **Generate Playwright test** using Page Object Model pattern”  
> “3. **Run tests** across multiple browsers (Chrome, Firefox, Safari)”  
> — `claude/commands/e2e.md:28-35`

Agent side:

> “description: End-to-end testing specialist using Vercel Agent Browser (preferred) with Playwright fallback.”  
> — `claude/agents/e2e-runner.md:3`

> “## Primary Tool: Agent Browser”  
> “**Prefer Agent Browser over raw Playwright** — Semantic selectors, AI-optimized, auto-waiting, built on Playwright.”  
> — `claude/agents/e2e-runner.md:22-24`

> “## Fallback: Playwright”  
> “When Agent Browser isn't available, use Playwright directly.”  
> — `claude/agents/e2e-runner.md:39-41`

There is a second collision in the same path. The command illustrates a long human-readable report with generated test code, console results, artifact lists, and a boxed status (`claude/commands/e2e.md:37-203`). The agent says:

> “Your FINAL message MUST be a single fenced ` ```json ` block conforming to the shared `HandoffEnvelope` schema...”  
> — `claude/agents/e2e-runner.md:112-114`

> “Emit exactly one JSON block; prose belongs in `evidence` / `openQuestions`, not around it.”  
> — `claude/agents/e2e-runner.md:132`

### Concrete collision

User runs `/e2e Test checkout across supported browsers`. The command directs dispatch of `e2e-runner`. In that worker, “use Playwright” arrives through the task/delegation context, but “Agent Browser preferred; Playwright fallback” is in the worker's agent system prompt. The worker selects Agent Browser when available and emits one JSON envelope, not the command's illustrated report. The command's Playwright-as-primary wording and prose-output illustration are dead for that spawned worker.

### Runtime winner

**`e2e-runner` wins inside the spawned worker.** This is not inferred from recency or filename: current official subagent docs explicitly identify the agent body as the subagent system prompt and the delegation as a separate task message. The parent can reformat the returned JSON afterward, but that does not make the worker follow the command's requested direct output.

Actual dispatch from the prose-only legacy `/e2e` command on the owner's installed version is **UNVERIFIED**; settle it by invoking `/e2e` under `claude --debug` and observing `SubagentStart` plus agent type. This uncertainty does not affect the documented winner *if the command performs the dispatch it explicitly orders*. The corpus has no `e2e-runner` key under `capability_use.agents_invoked`, and the corpus cannot establish absence of all historical invocations because `_meta` limits and key aggregation may omit context; therefore I make no historical-use claim.

### Minimal resolution

**NATIVE (Claude Code already does this; we just enable it)** — make the dispatch explicit and keep agent policy authoritative:

```yaml
---
description: Generate and run end-to-end tests with browser artifacts.
context: fork
agent: e2e-runner
---

Execute this E2E task: $ARGUMENTS
```

Delete the duplicated 365-line Playwright tutorial from the command or move non-conflicting reference material into a skill preloaded by the agent. If Playwright truly is the owner's intended primary tool, make the opposite one-line edit instead: change `agents/e2e-runner.md:3,15,22-24,39-41` to Playwright-primary. Do not retain two authorities.

The single-source edit is **almost certain (90-99%)** to remove this silent override because it eliminates the contradicting clause and binds the intended agent. Whether Agent Browser is actually superior for the owner's projects is **UNVERIFIED**; settle that with a held-out journey benchmark comparing setup success, pass@1, flake rate over ten reruns, runtime, and artifact usefulness. This audit recommends coherence, not a tool winner without that experiment.

> “- MEDIUM: 2”  
> “Recommendation: ❌ Block merge until CRITICAL issue is fixed”  
> — `claude/commands/python-review.md:153-158`

The command is internally inconsistent even before composition: its category list places “Not using context managers for resources” under HIGH (`claude/commands/python-review.md:37-44`), while its worked report labels the same defect MEDIUM (`claude/commands/python-review.md:139-151`).

Agent side:

> “### CRITICAL — Error Handling”  
> “- **Missing context managers**: manual file/resource management — use `with`”  
> — `claude/agents/python-reviewer.md:27-30`

> “Your FINAL message MUST be a single fenced ` ```json ` block conforming to the shared `HandoffEnvelope` schema ... with the **reviewer extension**.”  
> — `claude/agents/python-reviewer.md:125-127`

> “Emit exactly one JSON block; if `findings` is empty, still emit the envelope...”  
> — `claude/agents/python-reviewer.md:158`

### Concrete collision

User runs `/python-review` on a diff containing an opened file without a context manager. The command's own two labels compete (HIGH versus MEDIUM), and the dispatched agent supplies a third, stronger CRITICAL classification. The worker must also return JSON rather than the command's demonstrated human report.

### Runtime winner

**`python-reviewer` wins inside the spawned worker**: CRITICAL and the reviewer-extension JSON envelope. The agent-body/system-prompt versus delegation-task split is documented by the official subagent page cited above. This is also historically relevant rather than purely hypothetical: the corpus records 13 `python-reviewer` invocations (`inputs/corpus.json:13351-13360`). However, linking those 13 calls to `/python-review` is **UNVERIFIED**; the settling experiment is a session trace joining the user `/python-review` event to the following `Agent` tool call and returned agent type.

### Minimal resolution

**NATIVE (Claude Code already does this; we just enable it)** — bind `/python-review` using `context: fork` and `agent: python-reviewer`; reduce the command body to `$ARGUMENTS` plus any scope instruction. Keep the JSON schema and severity taxonomy solely in `python-reviewer.md`. If a human-readable summary is desired, make the parent render the returned envelope; do not ask the worker to emit two mutually exclusive formats.

Also choose one evidence-based severity for missing context managers. I do not recommend CRITICAL by default: an ordinary leaked file descriptor is not automatically equivalent to injection or credential exposure. Making it context-sensitive (HIGH normally; CRITICAL only when it causes a demonstrated security or availability impact) is **likely (55-80%)** to reduce severity inflation, based on the file itself grouping injection and unsafe deserialization as CRITICAL (`agents/python-reviewer.md:20-30`) while providing no impact test for the context-manager case. This forward recommendation is **UNVERIFIED**; settle it by labeling a held-out sample of owner-accepted/rejected review findings and comparing false-positive escalation rates.
