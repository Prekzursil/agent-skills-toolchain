# P1A01 — Corpus axis: tool reliability

## Scope and answer

This unit ranks every observed tool by failed-call damage (`calls × error_rate`, which is the corpus `errors` count apart from displayed-rate rounding), diagnoses the leading failure fingerprints against raw transcripts where the capped samples are decisive, and assigns each failure to one of three primary owners: **harness defect**, **agent-behaviour defect**, or **environment defect**. It does not inspect the corpus `hooks` section: the program brief marks that detector broken, so it is no evidence either way.

The corpus contains 299,724 tool calls and 15,772 calls marked as errors across 533 exact, case-sensitive tool names. There are 199 error-bearing names and 334 zero-error names. The top eight names account for 13,885 errors (88.04%); Bash alone accounts for 6,461 (40.97%). These counts come from `corpus/corpus.json:13-110`, and the concentration figures are exact recomputations from those rows.

The central result is that the error counter is **not a pure tool-reliability metric**. It mixes transport failures, invalid arguments, expected nonzero exits from commands/tests, stale external services, user or guard rejections, and normal optimistic-concurrency refusals. Therefore the ranking is a damage triage queue, not a claim that the tool implementation caused every counted error. This limitation is visible in the fingerprints themselves: the global list includes 533 user/tool-use rejections, generic `Exit code <n>`, test failures, and validation errors (`corpus/corpus.json:4279-4535`).

## Dataset and grain checks

- Source: `corpus/corpus.json`, distilled from `C:\Users\Prekzursil\.claude\projects`.
- Grain: one `tool_usage` row per exact tool-name string, not per logical capability/provider. This matters because Tavily, Exa, Firecrawl, IDA, and ChEML appear under several aliases and transports.
- Coverage: `_meta` reports 11,633 files seen, zero failed, 1,564,084 JSONL lines, one bad line, and 32 oversized lines (`corpus/corpus.json:1-11`). Thus aggregate presence/count claims are almost certain (90-99%), based on 0 failed files and only 1 bad line; content on the 32 oversized lines remains outside that confidence.
- Samples: each fingerprint retains at most 12 filenames. Counts are exact, samples are not representative (`corpus/corpus.json:10`). Root-cause claims below use samples only to falsify or confirm a concrete mechanism, never to estimate prevalence beyond the exact fingerprint count.
- Case preservation: PowerShell `ConvertFrom-Json` without `-AsHashtable` rejected the corpus because it contains case-distinct keys (`reframe` and `Reframe`). All computations used `-AsHashtable`, preserving distinct tool names.
- Reconciliation defect: `tool_usage.errors` sums to 15,772. `failures_by_tool` has 63 named buckets totaling 15,512 plus one anonymous 22-error bucket, for 15,534. The omitted named tail (ranks 64-199) totals 260 errors; subtracting the unexplained anonymous 22 yields the observed 238 net difference. The corpus therefore ranks all tools, but cannot supply per-tool fingerprints for ranks 64-199. This is a corpus-shape gap, not evidence that those tools share the anonymous failures.
- Fingerprint coverage is uneven: the listed top fingerprints cover 34.1% of Bash errors and only 8.2% of PowerShell errors, versus 94.7% of Glob and 100% of the disconnected Exa/Tavily tools. Root-cause completeness for Bash and especially PowerShell is therefore limited.
- Retry-loop data is narrow: it records 53 Read runs, 14 Bash runs, one PowerShell run, and one StructuredOutput run (`corpus/corpus.json:10297-10370`). The corpus does not define whether this detector catches only consecutive identical calls; it cannot support a general claim about total retry amplification.

## Root-cause diagnosis of the dominant failures

### 1. Bash — 108,121 calls, 6,461 errors, 5.98%; primary class: environment defect, harness boundary UNVERIFIED

The dominant fingerprint is 1,631 instances of `/usr/bin/bash: -c: line <n>: unexpected EOF while looking for matching \`'\``; a related double-quote form adds 128 (`corpus/corpus.json:4281`, `4533`). This is 27.2% of all Bash errors.

Raw evidence contradicts the simple “agent wrote invalid shell” diagnosis. In `C:\Users\Prekzursil\.claude\projects\C--Users-Prekzursil-Documents-GitHub\09158d9e-df69-4e33-8371-22a2963e3d7d.jsonl:14868`, the result is exactly:

> `Exit code 2 /usr/bin/bash: -c: line 98: unexpected EOF while looking for matching \`'\``

The parent call at line 14866 is a 2,998-character Bash command with quoted paths, Python and Git heredocs. Three more decisive cases are the same transcript at lines 18864-18866 and `C:\Users\Prekzursil\.claude\projects\C--Users-Prekzursil-Documents-GitHub\09158d9e-df69-4e33-8371-22a2963e3d7d\subagents\agent-a62c35a5ce247e762.jsonl:64-69`, including a 2,883-character heredoc script. An independent control piped each exact `input.command` string from the JSONL into `C:\Program Files\Git\bin\bash.exe -n`; all four returned exit 0 (full parent UUIDs are present at those cited lines). It is therefore very unlikely (5-20%) that agent-authored Bash grammar caused these four sampled failures; the evidence is four exact-command parser passes after transport had reported unmatched quotes.

The primary classification is **environment defect** at the Bash invocation/argument-transport boundary. It is very likely (80-90%) that the dominant fingerprint is produced after the model-authored string leaves the transcript, because exact recorded strings parse successfully and the failure comes from `bash -c`. **UNVERIFIED whether a harness hook or Claude Code’s native Bash wrapper corrupts the argument**; the settling experiment is an A/B capture of the final `argv`/stdin bytes for the same quote-rich canary with all user hooks enabled and then disabled. If hooks-on alone fails, reclassify as harness defect; if both fail, retain environment/native-wrapper ownership.

Other Bash errors cannot be assigned wholesale. **UNVERIFIED whether the 230 rejections are successful policy enforcement or an agent asking for an unwanted action; the settling experiment is to join each rejection to a persisted rejection-source field, which the current corpus lacks.** The 115 generic exits and many low-frequency fingerprints include legitimate command/test failures. The corpus is silent on the causal split for 65.9% of Bash errors not covered by its top-failure list.

## Repair design, in damage order

All proposals pass the anti-overfit gate: they ride existing configuration, hook, skill, or MCP buses and add no second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### R1 — UNVERIFIED shell-byte canary and stdin/response-file transport — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

First run the hooks-on/hooks-off argv experiment named in §1. If a user hook mutates the command, fix that hook; otherwise report the native Bash wrapper defect upstream and route multiline/quote-rich commands through stdin or a response/script file created by the existing Bash tool. It is very likely (80-90%) this targets the 1,759 dominant single/double-quote fingerprints because four exact failing commands independently parse, but causality across all 1,759 is **UNVERIFIED until the canary experiment captures final bytes**. Do not add another shell runtime.

### R2 — Live-plugin manifest plus conservative orphan quarantine — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Build the launch/search path only from enabled plugin manifests, never by expanding every cache directory. A maintenance command may quarantine an orphan only when (a) `.orphaned_at` is present, (b) no enabled manifest resolves into it, and (c) no live process/open-skill reference resolves into it; it must produce a reviewable plan before mutation. This avoids repeating the stopped unsafe bulk delete. It is very likely (80-90%) to eliminate the 709 `uv_spawn` ENAMETOOLONG failures, based on the raw plugin-root call, current 875 markers, and pinned command-line-cap diagnosis.

### R3 — Health-aware MCP exposure with per-session circuit breaker — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

At session start, probe configured providers once; remove disconnected aliases from routing context, retain a canonical healthy fallback, and after one deterministic “not connected,” suppress that exact endpoint for the session. This targets 487 global disconnected Exa/Tavily calls plus smaller expired/disconnected providers. It is very likely (80-90%) to prevent repeat dead calls because the relevant Exa/Tavily fingerprints are 100% deterministic for their failing aliases. Re-authentication remains an environment operation; suppression is the harness fix.

### R4 — UNVERIFIED minimal fan-out terminal envelope — CONFIG (settings/JSON only)

Replace bespoke high-arity required schemas with four stable required fields—`status`, `summary`, `evidence`, `gaps`—and make domain extras optional or store them inside `evidence`. Validate semantic completeness at orchestration synthesis, not at every leaf’s terminal serialization. Replay-test before rollout. It is likely (55-80%) to materially reduce StructuredOutput’s 846 errors, based on 335 explicit `kg_triples` misses and the decisive sample; the exact gain is **UNVERIFIED until the 100-output replay described above**.

### R5 — Read-size adaptive retry and path existence discipline — CONFIG (settings/JSON only)

Teach routing rules to use Grep first for unknown large files; for Read, begin with a conservative line window and halve on a size/token rejection.
