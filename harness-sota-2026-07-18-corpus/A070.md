## Collision register

### C1 — Swift Testing is mandated for test categories it does not cover

**Artifacts and exact lines**

* `~/.claude/rules/swift/testing.md:12`: “Use **Swift Testing** (`import Testing`) for new tests.”
* `~/.claude/rules/common/testing.md:25-28`: unit, integration, and E2E tests are all required; E2E uses a framework chosen per language.
* Apple’s current [Testing overview](https://developer.apple.com/documentation/xcode/testing) says Swift Testing is the modern unit-test framework and that XCTest remains for UI tests controlling apps through XCUIAutomation. Apple’s [Adding tests guide](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project?changes=_4__3) says Swift Testing is for unit/direct-code integration tests, while XCTest supports unit, integration, UI, and performance tests. Apple’s [XCTest reference](https://developer.apple.com/documentation/xctest?changes=latest_bet_6) likewise retains UI and performance facilities.

**Class:** CONTRADICTION.

**Why this is a collision:** A new UI/E2E test is literally a “new test,” so line 12 mandates Swift Testing, while the common rule requires E2E and delegates the framework choice. The available first-party framework for Xcode UI automation is XCTest/XCUIAutomation. This is not merely omitted detail: the universal quantifier in “new tests” selects the wrong framework for a required test category.

**Precedence:** `rules/README.md:93-98` makes the Swift-specific rule win over the common rule where they conflict. `AGENTS.md` §10 does not independently resolve intra-rule specificity. Applying the README literally therefore preserves the bad universal mandate; precedence identifies the winner but does not make the winning policy technically coherent.

**Specific resolution — CONFIG:** Replace line 12 with: “Use Swift Testing for new unit tests and direct-code integration tests when the project toolchain supports it. Continue to use XCTest/XCUIAutomation for UI tests and XCTest where required for performance tests. Existing XCTest and Swift Testing tests may coexist during incremental migration.” Add the toolchain/project-convention gate before changing an established suite. This rides the existing rule bus and adds no runtime. It is **almost certain (90-99%)** to remove the contradiction because Apple explicitly documents coexistence and category boundaries in the sources above.

### C4 — Test isolation is demanded but no mechanism observes it

## Consolidated replacement text

The smallest coherent replacement remains a rule-file edit plus reuse of existing validation buses:

```markdown
## Framework

Use Swift Testing (`import Testing`, `@Test`, `#expect`) for new unit tests and
direct-code integration tests when supported by the repository's toolchain and
conventions. Use XCTest/XCUIAutomation for UI tests and XCTest where required
for performance tests. Swift Testing and XCTest may coexist during migration.

## Isolation

Tests must not share mutable state. Prefer value-type suites and fresh fixtures.
Use explicit scoped cleanup for global/process resources; do not rely on `deinit`
as the only cleanup for resources requiring deterministic or asynchronous teardown.

## Coverage

Run `swift test --enable-code-coverage` for SwiftPM projects (through `longrun`
when expected to exceed 60 seconds), export the result, and verify it against
`.coverage-thresholds.json`; use 80% only when that file defines no threshold.
For Xcode projects, use the repository's scheme/test plan and the same threshold gate.

## Reference

For protocol-based dependency injection and mocks, invoke
`swift-protocol-di-testing` when the task actually involves those patterns.
```

**CONFIG** for the rule rewrite and command routing; **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** only for a missing threshold adapter or the existing per-edit `.swift` branch. No proposal needs a second orchestrator, vector database/knowledge graph memory, durable execution engine, trained critic, observability SaaS, guardrail framework, daemon, or service.
