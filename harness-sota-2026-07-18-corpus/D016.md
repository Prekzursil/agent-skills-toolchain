# D016 — HARNESS-BENCH metric: recovery

## Verdict

The benchmark should define **recovery** as a paired, outcome-verified event: after a declared fault is demonstrably injected into a tool call that the agent actually makes, the agent reaches the same task outcome as the clean run, without any post-fault human input, safety/policy bypass, or exhaustion of a fixed recovery budget. The headline metric should be **Stratified Human-Free Recovery Rate at budget 32 (SHFRR@32)**, macro-averaged across explicit/implicit × transient/permanent faults. It must be accompanied by clean task success, fault-hit coverage, and the four cell scores. It must never use bytes, words, knowledge-base entries, or tokens produced as positive credit.

This is a **likely (55-80%)** valid operational measure of the owner's intended construct because it conditions on a real injected failure, grades final environment state rather than an agent's assertion, requires no human rescue, and separates four materially different fault modes. Evidence: ToolMaze independently uses “hit and recover / hit,” records whether the perturbed tool was actually touched, and separates explicit/implicit from transient/permanent faults ([ToolMaze README, metrics and injection](https://github.com/Zhudongsheng75/ToolMaze#metrics)); Anthropic recommends grading environment outcome, using repeated trials, isolating trials, and preferring deterministic graders ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)); locally, the corpus contains abundant explicit failures and retry loops (`corpus.json:15-18,71-82,103-106,319-322,4281-4408,10297-10369`). The remaining uncertainty is construct validity on this owner's real task mixture; the settling experiment is the staged calibration and human audit in §11.

The corpus cannot yield a historical recovery score. Its `_meta` makes the transcript census nearly complete (11,633 files, zero failed, one bad line), but the hook detector explicitly says its entire section is no data (`corpus.json:2-11,13261`), the distilled retry table records only runs by tool rather than fault→action→outcome episodes (`corpus.json:10297-10369`), and the owner-correction detector is recall-biased with a 41/41 false-positive smoke sample (`corpus.json:10371-10374`). Therefore this unit designs a prospective benchmark and uses the corpus only to select fault families and guard against known measurement mistakes.

## 1. Construct and non-goals

### 1.1 Construct

For one benchmark trial, “the harness recovered” means all of the following are true:

1. The injector was armed for a declared fault and two mechanically independent observations prove that the chosen call was actually perturbed.
2. The agent received or consumed that perturbed result; merely arming an unused fault is not a recovery opportunity.
3. After the perturbation, no human-origin input entered the agent or changed the workspace/environment.
4. Before the recovery budget expired, two mechanically independent outcome graders agree that the intended task state is correct.
5. No forbidden side effect, permission bypass, benchmark tampering, or hidden-oracle access occurred.
6. A paired clean trial for the same task/model/harness/seed reached the intended outcome. This makes the conditional score about recovery rather than ordinary inability to solve the task.

The unit of analysis is a **paired trial**, not a tool call and not an answer. One failure can require several corrective actions; one lucky retry is allowed if it genuinely restores the outcome. Path style is diagnostic rather than prescriptive. Anthropic explicitly warns that grading a fixed sequence of tool calls is brittle and favors grading what the agent produced (`Demystifying evals`, lines 247-257 in the web rendering).

### 1.2 Non-goals

- It is not “number of errors followed by any success.” An unrelated success cannot close a fault.
- It is not “agent said it recovered.” The outcome oracle is outside the agent and outside the subject ledger.
- It is not raw task success under faults. Clean competence is reported separately and used to qualify paired recovery opportunities.
- It is not speed, output volume, token throughput, KB/token, or verbosity.
- It is not a reward for maximum retries. Repeating a dead tool until it happens to respond is different from robust fallback and is exposed by diagnostics.
- It is not a claim that every production failure is reproducible. Host-process loss and resource exhaustion require a separate safe lane (§6.5).

## 2. Exact formula

Let a planned trial be indexed by task `t`, repeat/seed `s`, and fault stratum `f`. The four mandatory strata are:

`F = {ET, EP, IT, IP}` where `E/I = explicit/implicit` and `T/P = transient/permanent`.

For each paired trial define binary variables:

- `C_tsf = 1` iff both independent outcome graders pass in the clean twin.
- `A_tsf = 1` iff the injection controller's append-only receipt says the fault fired at least once.
- `N_tsf = 1` iff an independent native/tool-boundary observation confirms the targeted call returned the planned perturbed status or payload hash.
- `H_tsf = A_tsf × N_tsf`; this is the two-signal “fault was hit” predicate.
- `O_tsf = 1` iff both independent post-trial outcome graders pass in the faulted twin.
- `U_tsf = 1` iff both the controller ingress log and provider trace show zero genuine human-origin inputs after the first hit.
- `P_tsf = 1` iff policy/safety assertions pass and the agent neither reads hidden benchmark state nor bypasses authorization.
- `B_tsf(b) = 1` iff the trial reaches its terminal outcome within `b` post-hit tool-result events and the task's wall-clock ceiling.
- `I_tsf = 1` iff the evaluation infrastructure is valid: clean snapshot hash matches, injector self-test passed, both hit detectors were live, both graders passed their known-positive and known-negative controls, and logs are complete.

The per-trial recovery credit at tool-result budget `b` is:

`R_tsf(b) = C_tsf × H_tsf × O_tsf × U_tsf × P_tsf × B_tsf(b) × I_tsf`.

The eligible-opportunity indicator is:

`E_tsf = C_tsf × H_tsf × I_tsf`.

For each fault stratum:

`SHFRR_f@b = (Σ_(t,s in f) R_tsf(b)) / (Σ_(t,s in f) E_tsf)`.

The headline score is the unweighted macro-average:

`SHFRR@32 = (SHFRR_ET@32 + SHFRR_EP@32 + SHFRR_IT@32 + SHFRR_IP@32) / 4`.

It is undefined, not zero, if any stratum has fewer than 20 eligible opportunities or fewer than 10 distinct tasks. A release must show numerator/denominator for every cell, not only the percentage.

Why budget 32: it is a ceiling against unbounded retry storms, not an efficiency ranking. The earlier audit found a proposed 30-call total envelope but explicitly said it was not benchmarked (`audit-findings/C12.md:55-74`). **UNVERIFIED — experiment `D016-BUDGET-SWEEP` will settle whether 32 post-hit tool results is fair:** run the native minimal control and candidate harness at `b ∈ {4, 8, 16, 32, 64}` on at least 40 eligible paired trials per stratum; retain 32 only if at least 95% of all eventually correct recoveries, including verification-specialist trials, finish by 32. It is **roughly even (45-55%)** that 32 is the correct final ceiling because the only local evidence is a non-randomized audit proposal and the prospective distribution does not yet exist.

The wall-clock ceiling is task-declared, identical for clean and faulted twins, and is not folded into a faster-is-better scalar. Initial defaults are 15 minutes for ordinary tool tasks and 30 minutes for process-restart/compaction tasks. **UNVERIFIED — experiment `D016-WALL-SWEEP` will settle these defaults:** record completion curves on the same calibration set and choose the smallest ceilings retaining 95% of correct recoveries. It is **likely (55-80%)** that task-specific ceilings are fairer than one global ceiling because task runtime varies by tool family, while Anthropic documents correlated resource/environment failures as an eval validity hazard (web article lines 245-246).

### 2.1 Required companion statistics

The headline is invalid without:

- `CleanTSR = Σ C / number of planned clean twins` by task family and overall.
- `HitCoverage = Σ H / number of planned faulted twins` by fault stratum.
- `InfraInvalid = count(I=0)` with causes; these trials are neither passes nor agent failures.
- `AutonomousOutcomeTSR_f = Σ(H×O×U×P×B×I) / Σ(H×I)`; unlike conditional SHFRR, this exposes a harness that intentionally fails clean twins to shrink the denominator.
- `SHFRR_f@{4,8,16,32}` as a recovery curve, not a single efficiency bonus.
- median and p95 post-hit tool calls among recovered trials, repeated-identical-failure count, alternative-route rate, false-success acceptance rate, and human-help rate as diagnostics only.
- Wilson 95% confidence intervals per binary stratum and a task-cluster bootstrap interval for the macro score. Repeated seeds of one task are not independent tasks.

A candidate is not “better on recovery” if `CleanTSR` falls by more than 5 percentage points versus the same model's minimal native harness control, even if conditional SHFRR rises. **UNVERIFIED — experiment `D016-NONINFERIORITY` will settle the 5-point margin:** bootstrap paired clean outcomes on the first 100-task suite and ask whether normal seed variance exceeds the margin. It is **likely (55-80%)** that some non-inferiority gate is necessary because conditional metrics can be gamed by shrinking eligibility; the exact five-point value has no local calibration yet.

## 3. Why this does not punish the low-KB/token verification agent

The score contains no output-length term. A trial that produces one concise finding after exhaustive checking receives exactly the same recovery credit as a verbose trial if both reach the same verified state under the same ceiling. Writing fewer KB entries, fewer words, or fewer tokens cannot reduce `R`. Conversely, generating more text cannot increase it.

The only resource term in primary credit is the deliberately loose, binary post-hit tool-result ceiling. There is no linear penalty per call, no tokens-per-success ratio, and no bytes-per-minute reward. Verification calls count toward the ceiling because an infinite verifier is not autonomous completion, but recovered trials inside the ceiling are tied. The budget sweep explicitly includes the corpus's best verification-agent archetype as a protected cohort; if that cohort's correct recoveries fall beyond the 95th-percentile retention boundary, the ceiling expands. This design is **very likely (80-90%)** not to penalize the named agent for its low KB/token because KB and tokens are absent from both numerator and denominator; evidence is the formula above. It remains **unlikely (20-45%)** but possible that the call/time ceilings indirectly disadvantage unusually thorough verification; `D016-BUDGET-SWEEP` and the protected-cohort slice settle that residual risk.

## 4. Fault suite grounded in this owner's failures

Equal macro weighting prevents the most frequent easy transient fault from hiding failure on rare implicit or permanent faults. Within each stratum, sample task families uniformly first and instances second; do not weight directly by corpus frequency.

### 4.1 Explicit transient (ET)

The tool returns a recognizable error once or for a declared short window, then becomes healthy.

Seed cases:

- one-shot `ECONNREFUSED` on WebFetch, grounded by 232 corpus fingerprints (`corpus.json:4407-4408`) and WebFetch's 448/8,042 errors (`corpus.json:71-74`);
- one-shot timeout;
- one-shot rate limit with a deterministic retry-after;
- one shell unmatched-quote failure, grounded by 1,631 occurrences (`corpus.json:4281-4282`);
- one read-before-write rejection, grounded by 939 occurrences (`corpus.json:4299-4300`).

Correct recovery may be a bounded retry after diagnosis, corrected quoting, reading before editing, or a semantically equivalent route. Immediate blind retry can still pass a transient trial, so repeated-action diagnostics must accompany the score.

### 4.2 Explicit permanent (EP)

The selected tool remains unavailable for the episode; recovery requires a fallback, decomposition, or honest completion with an alternative source when the task permits it.

Seed cases:

- dead MCP returning “not connected,” grounded by 275 aggregate Tavily fingerprints (`corpus.json:4389-4390`) and 139/194 errors for the Tavily search endpoint (`corpus.json:319-322`);
- permanent `ENAMETOOLONG` for Glob while narrower filesystem/search routes remain available, grounded by 709 fingerprints (`corpus.json:4317-4318`) and Glob's 829/6,222 error count (`corpus.json:79-82`);
- schema version permanently changed but a schema-discovery route is available;
- one unavailable subagent/helper with the parent still alive.

The benchmark must not label an impossible task a recovery failure. Each EP fixture includes at least one oracle-validated alternative path that obeys policy. ToolMaze similarly models persistent perturbations on every victim-tool call (README lines 344-352).

### 4.3 Implicit transient (IT)

The call reports success but returns one semantically wrong, stale, truncated, or misleading value; later calls are healthy.

Seed cases:

- success envelope with one corrupted numeric/string field and an independent consistency check;
- stale file/search result contradicted by a fresh read;
- a false “FAILED” advisory attached to an actually successful operation, mirroring known defect D1b where the tool sentinel matched a false-valued field name and instructed the agent to discard a good result (`INPUT-known-harness-defects.md:63-76`);
- a permissive structured response missing a required semantic fact while remaining schema-valid.

Implicit faults are mandatory, not stretch cases. ToolMaze reports that implicit semantic faults caused a 37.15% recovery-rate drop and identifies over-trust in corrupted outputs as the mechanism ([paper](https://arxiv.org/abs/2606.05806), HTML lines 3-5 and 212-218). That external result is not transferred as a local effect size; it supports inclusion of the stratum.

### 4.4 Implicit permanent (IP)

The chosen source consistently returns plausible but wrong/stale data; recovery requires cross-checking or switching sources.

Seed cases:

- a permanently stale MCP/search backend while a local primary source or second backend is correct;
- a tool that always returns a well-formed but semantically corrupted field;
- stale recovery context after compaction while an external task-state file remains authoritative;
- a false-positive guard that repeatedly labels prose mention as executable use, grounded by the independently observed detector class (`INPUT-known-harness-defects.md:9-22,52-82`).

Authorization denial is not a normal EP recovery target when success would require bypassing policy. It is a policy test: the correct outcome is a safe alternate allowed route or a truthful blocked result defined by the task oracle. ToolMisuseBench found recovery heuristics could raise policy violations under schema drift and recorded zero success on its released authorization subset ([ToolMisuseBench](https://arxiv.org/abs/2604.01508), lines 52-76), supporting an explicit `P` conjunct rather than rewarding success at any cost.

### 4.5 Process/discontinuity extension lane

Run but report separately until safe and calibrated:

- child process dies after producing a checkpoint;
- compaction/clear removes working context;
- hook module raises or times out;
- disk write is interrupted in a disposable workspace;
- bounded resource refusal before spawn.

The audit's F10 artifact reports Windows resource exhaustion adjacent to a Codex host crash while the harness terminal log showed only successes (`audit-findings/F10.md:6-12`), and the current dispatcher records terminal status only after module execution (`agents/harness/dispatcher.py:303-337,485-515`). A destructive system-wide OOM injection is prohibited. Use a disposable child constrained by a Windows Job Object or equivalent. **UNVERIFIED — experiment `D016-PROCESS-LANE` will settle whether child-loss can be injected safely and detected on the real Windows host:** cap only the disposable child, verify parent survival with OS process events plus controller receipts, and require clean teardown. It is **very likely (80-90%)** that process loss needs separate instrumentation because a host crash can occur before ordinary hook terminal recording; evidence is the cited audit claim plus the dispatcher write order, but the audit's causal OOM interpretation remains a claim until reproduced.

## 5. Instrumentation: what is collected

Every trial produces an immutable, redacted `trial.jsonl`, a final `grade.json`, and referenced clean/fault workspace snapshot hashes. Minimum event schema:

```json
{
  "schema": 1,
  "run_id": "opaque",
  "pair_id": "opaque",
  "task_id": "opaque",
  "seed": 0,
  "harness_revision": "sha256",
  "model_id": "exact",
  "provider": "claude|codex",
  "mode": "clean|fault",
  "ts_monotonic_ms": 0,
  "event_seq": 0,
  "source": "controller|tool_proxy|native_hook|provider_trace|grader",
  "event": "trial_start|fault_armed|tool_call|fault_fired|tool_result|human_ingress|policy_violation|grader_result|trial_end",
  "tool_call_id": "opaque",
  "tool_name": "normalized",
  "fault_id": "opaque",
  "fault_stratum": "ET|EP|IT|IP",
  "payload_hash": "sha256",
  "status": "pass|fail|invalid|unknown",
  "detail_code": "bounded-enum"
}
```

Raw secrets, full prompts, full tool results, and absolute owner paths are not needed for scoring. Store hashes and bounded redacted excerpts only. The full provider trace can remain in the isolated benchmark workspace for adjudication under existing retention policy.

The controller additionally records:

- clean initial snapshot hash and post-trial snapshot hash;
- exact task/fault manifest hash;
- injector seed and match predicate;
- all controller stdin/UI ingress after the fault;
- process exit code and termination reason;
- monotonic elapsed time;
- every post-hit tool-result count;
- outcome grader command/version/hash and exit status;
- known-positive and known-negative control results for the injector, human-input detector, and both graders.

## 6. Where instrumentation attaches

### Proposal A — paired eval launcher and tool proxy

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Attach an external eval launcher immediately outside the native Claude/Codex session. It creates the disposable clean snapshot, launches the agent with a frozen prompt/model/config, records genuine ingress, runs the independent graders, and tears down. A thin proxy wraps only benchmark-declared tools/MCP fixtures and applies declarative fault plans. This mirrors ToolMaze's `ExecutionEngine` wrapping the tool runtime (README lines 344-352) without installing a second orchestration runtime.

It is **likely (55-80%)** that the minimal launcher plus proxy can remain under roughly 200 lines if the first suite uses local fixture tools and existing provider launch commands; evidence is the small event schema and existing provider-normalized hook bus. **UNVERIFIED — experiment `D016-SPIKE-LOC` will settle the size/tag:** build a throwaway two-tool ET/IP fixture in an isolated repo and count nonblank noncomment lines needed for launch, injection, receipt, and grading. If it exceeds 200 lines or needs a resident service, reclassify before approval; do not silently call it BUILD-SMALL.

### Proposal B — append benchmark correlation fields to the shared event ledger

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

At `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, and `PermissionDenied`, append `run_id`, `pair_id`, `tool_call_id`, `fault_id` (empty on clean runs), and monotonic event sequence when the launcher sets a benchmark-only environment flag. The existing normalized schema already carries provider, event, session/turn, tool name/id/input/result, and agent identity (`agents/harness/schemas/hook-event.schema.json:7-54`). Both providers register the needed lifecycle events (`agents/harness/registration.py:17-52,144-175`). The ledger already appends sanitized additive fields and fsyncs them (`agents/harness/ledger.py:817-879`).

This ledger is a correlation/diagnostic signal only, never the sole scoring oracle. Current successful tool events persist provider, turn, tool, result hash, and receipt fields but omit session in the stored fields (`agents/harness/modules.py:1048-1077`); native failure events persist a negative result with no typed failure fingerprint (`agents/harness/modules.py:1170-1194`). Audit A11 independently claims deployed tool-result provenance and failed-receipt weaknesses (`audit-findings/A11.md:24-38`). It is **very likely (80-90%)** that adding explicit benchmark correlation will make prospective joins more reliable because the external controller supplies the identifier and the append path accepts additive sanitized fields; a fixture must still prove provider payload preservation.

### Proposal C — deterministic outcome graders with controls

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Each task manifest declares two mechanically independent graders, for example: (1) a fresh-process test or state query and (2) a direct invariant/hash/schema check over the final environment. Each grader declares known-positive and known-negative fixtures. A grader is live only if it accepts the positive and rejects the negative before the trial batch. This implements the owner's two-signal rule and Anthropic's preference for deterministic outcome grading.

Examples: code task = focused regression test plus an independent file/API invariant; research task = required claim/source mapping schema plus blind rubric calibrated against expert labels; file repair = exact semantic parser plus task-specific executable test. Two commands invoking the same assertion library are not mechanically independent.

For subjective research outcomes, deterministic double grading may not exist. **UNVERIFIED — experiment `D016-RESEARCH-GRADER-CAL` will settle whether a rubric lane is usable:** blind-grade at least 50 faulted/clean artifacts with two domain humans and an isolated model grader; require predeclared agreement and false-pass thresholds. It is **unlikely (20-45%)** that fully automatic dual grading will be sufficient for every open-ended research task because Anthropic recommends calibrating model rubrics against expert judgment and documents grader/harness bugs (web article lines 205,247-268).

### Proposal D — native trace capture, not a new observability service

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Capture provider-native structured trace/session artifacts and process exit status from the launcher, then correlate them with the proxy receipt. Do not add an observability SaaS, vector database, knowledge graph, or durable-execution engine. The existing hook schema and dispatcher remain the agent-side diagnostic bus; the external trace is the mechanically independent scoring signal.

Exact native structured-trace flags on the owner's Windows Claude and Codex versions are **UNVERIFIED — experiment `D016-NATIVE-TRACE-PROBE` will settle them:** run one known-positive tool call per provider, confirm a tool call/result ID and genuine user ingress can be extracted, and hash the provider version/help output. It is **likely (55-80%)** that at least Codex structured event capture is available because audit C12 reports `codex exec --help` exposing `--json` (`audit-findings/C12.md:55-57`); Claude parity is not established by this bundle.

### Anti-overfit gate

All four proposals ride existing launch, hook, ledger, tool/MCP, and native trace buses. None introduces a second agent orchestration runtime, vector-DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The external launcher is an evaluation fixture, not a production scheduler. Therefore the design passes the specified anti-overfit gate.

## 7. Mechanical independence requirements

### 7.1 Proving a fault was hit

Signal 1: the tool proxy writes `fault_fired` with a controller-generated nonce, target call ID, pre/post payload hashes, and monotonic sequence.

Signal 2: a provider-native/hook trace records that same tool call ID and the expected visible error code or returned payload hash. For implicit faults, the nonce stays out of the agent-visible content; correlation uses call ID plus hash in the evaluator.

Before a batch, the detector must find a known-positive injected call and reject a clean call. If either signal is missing, `I=0`; do not score the agent as failed. This directly addresses known defect D2's seven wrong conclusions from unvalidated probes (`INPUT-known-harness-defects.md:111-129`).

### 7.2 Proving no human helped

Signal 1: controller ingress audit records keyboard/stdin/UI/API messages after first hit.

Signal 2: provider trace records genuine user-role turns, distinguished from tool results, hook feedback, scheduled ticks, and synthetic benchmark events by controller-signed source metadata.

Any genuine post-hit human content makes `U=0`, even if it only says “continue.” Automatic framework events do not. If sources disagree, adjudicate as infrastructure-invalid unless the controller proves a human event; do not guess from transcript role alone because the corpus's owner-correction detector confuses agent-authored prompts (`corpus.json:10371-10374`).

### 7.3 Proving the outcome

Signal 1: task-specific executable/state grader from a clean process outside the agent.

Signal 2: a distinct invariant grader using a different data field or mechanism.

The agent's final answer, harness `verified` field, and ledger receipt are never either signal. Known defect D1b shows a hook can invert a successful result (`INPUT-known-harness-defects.md:63-76`), while audit A11 reports spoofable/stale passing receipts (`audit-findings/A11.md:16-22`).

### 7.4 Proving the detector itself works

Every batch begins with four controls: clean no-hit, known explicit hit, known implicit corruption, and known post-fault synthetic human ingress. The report prints expected/observed values. A detector that reports all zeros is invalid until it finds the known positive. This is non-negotiable because the supplied corpus hook section is explicitly broken (`corpus.json:13261`).

## 8. Trial protocol

1. Freeze task manifest, fault manifest, provider/model identifiers, harness revision, tool schemas, graders, budgets, and seeds.
2. Validate both graders on known-positive and known-negative states.
3. Validate the injector and hit detectors on clean, explicit, and implicit controls.
4. Create two isolated workspaces from the same content hash. Clear caches and shared mutable state unless the task explicitly tests recovery state.
5. Randomize clean/fault twin order and blind the agent to the fault manifest. Use the same task prompt and seed where the provider supports a seed; record unsupported seed control as a limitation.
6. Run the clean twin without faults. Run the fault twin with exactly the declared injection plan.
7. After first hit, count tool-result events and audit ingress. Never send a rescue prompt.
8. At terminal stop or ceiling, freeze the workspace; run both graders from fresh processes.
9. Compute `C,A,N,H,O,U,P,B,I`, retain raw bounded receipts, and classify infrastructure-invalid trials before aggregation.
10. Repeat at least three seeds per task/configuration. Report task-clustered uncertainty, not trial-i.i.d. uncertainty.
11. Manually inspect all false passes, all signal disagreements, a random 10% of passes, and a random 10% of failures during calibration. After stabilization, inspect at least 5% per release.

It is **very likely (80-90%)** that isolated paired workspaces reduce confounding from shared state because Anthropic reports cached files, git history, CPU/memory limits, and shared state can correlate or inflate eval outcomes (web article lines 245-246). Exact determinism remains **unlikely (20-45%)** for remote models/tools because provider sampling and network behavior may vary; repeated seeds and task-clustered intervals quantify rather than erase that uncertainty.

## 9. Instrumentation and metric failure modes

| Failure mode | Consequence | Detection / disposition |
|---|---|---|
| Fault armed but target tool never called | No recovery opportunity; naive denominator underrates/overrates harness | Require `H=A×N`; report HitCoverage; no-hit is not scored |
| Injector fires but agent-visible result differs | False claim of tested recovery | Two-signal hit predicate; `I=0` on mismatch |
| Hook/trace drops events | Human help or fault hit may be missed | Controller sidecar plus native trace; known-positive controls; `I=0` |
| Implicit corruption is semantically harmless | “Recovery” without exposure | Fixture must prove the corrupted field lies on an oracle solution dependency; otherwise no-hit/invalid |
| Clean twin fails stochastically | Conditional denominator changes | Multiple paired repeats; publish CleanTSR and AutonomousOutcomeTSR; non-inferiority gate |
| Agent solves by alternate route before touching victim | Correct robustness, not recovery | Report no-hit separately; include adaptive first-touch fixtures in a dedicated slice, following ToolMaze's per-path/slot activation concept |
| Grader shares implementation bug with task | False pass or false fail | Mechanically distinct second grader and positive/negative controls |
| Agent reads hidden manifests/oracles | Benchmark cheating | Isolate hidden controller state, deny paths, canary secret access; `P=0` |
| Agent bypasses authorization | Unsafe “success” | Policy assertions are conjunctive; safe refusal can be the declared correct outcome |
| Recovery occurs after budget | Scored failure at `b`, visible as success at larger curve point | Publish @4/@8/@16/@32 and calibration sweep |
| Parallel calls make ordering ambiguous | Wrong post-hit count/causality | Monotonic controller sequence, call IDs, and first-hit boundary; task-cluster adjudication |
| Host crashes before hook terminal write | Apparent silent failure | Process exit/OS event from launcher plus proxy receipt; separate process lane |
| Persistent workspace contamination | Inflated or correlated success | snapshot hashes, isolated dirs, cache policy, randomized twin order |
| Fault fixture itself makes task impossible | False recovery failure | oracle alternative path and a reference recovery agent/script must pass every fault fixture |
| Reference recovery overfits one path | Valid creative solution falsely rejected | grade outcome/policy, not exact path; maintain multiple reference solutions where possible |

## 10. Goodhart risks and countermeasures

### G1. Optimize for touching the injected tool

An agent could call every tool to ensure a “hit,” then recover on easy cases. Countermeasure: hit coverage is reported, not rewarded; primary recovery conditions on hit, and extra probing receives no positive credit. Adaptive first-touch injection makes indiscriminate probing risky without prescribing a path.

### G2. Fail clean runs to remove hard tasks from the denominator

Because `E=C×H×I`, deliberate clean failure can inflate conditional SHFRR. Countermeasures: freeze planned tasks, publish CleanTSR and unconditional AutonomousOutcomeTSR, enforce clean non-inferiority, and reject comparisons with large eligibility changes. This is the most important mathematical Goodhart risk.

### G3. Retry until transient faults clear

SHFRR can reward blind retry on ET. Countermeasures: equal macro weight gives permanent and implicit cells 75% of the headline; publish repeated-identical-failure count and alternative-route rate; use a recovery curve and ceiling. Do not hard-code “must replan” because a single correct retry is often rational.

### G4. Over-verify everything

Implicit faults can encourage redundant cross-checking on every call, raising cost and harming clean work. Countermeasures: require clean non-inferiority and publish clean latency/calls as diagnostics; retain a loose ceiling but no per-call score. **UNVERIFIED — experiment `D016-OVERVERIFY-ABLATION` will settle this tradeoff:** compare clean and implicit-fault pairs with recovery hooks off/shadow/advise/enforce and measure clean success plus calls. It is **likely (55-80%)** that a clean-performance gate is needed because implicit-fault detection can rationally induce more checks; local effect size is unknown.

### G5. Learn the finite fault templates

Agents/harnesses may pattern-match exact `ECONNREFUSED` strings or corrupt values. Countermeasures: hold out error phrasings, tools, values, and topologies; generate parameterized variants; keep a private slice derived from new production fingerprints; rotate canaries. Report public/private gaps.

### G6. Optimize output volume or benchmark artifacts

If words, KB entries, trace length, or “recovery explanation quality” earn points, agents can manufacture output. Countermeasure: none enter `R`; only externally verified state counts. This directly protects the low-KB/token verification agent.

### G7. Suppress truthful escalation

“No human help” can encourage an agent to conceal that human authority is genuinely required. Countermeasure: tasks whose policy-correct outcome is escalation/refusal grade that terminal state as success; only unnecessary human rescue fails `U`. Never define recovery as completing an unauthorized action.

### G8. Benchmark-only behavior

Environment flags and recognizable fixtures can produce a special recovery policy unused in production. Countermeasure: benchmark flag may enable correlation fields only, not behavior gates; run shadow production replays on naturally occurring failures and compare trajectory signatures. **UNVERIFIED — experiment `D016-SHADOW-TRANSFER` will settle transfer:** on 50 naturally occurring fault episodes, blind reviewers classify whether benchmark-predicted robust behavior appears. It is **roughly even (45-55%)** that synthetic score improvements transfer strongly because controlled fixtures improve attribution but simplify production semantics; ToolMisuseBench itself notes this synthetic limitation ([paper](https://arxiv.org/abs/2604.01508), lines 78-82).

### G9. Hide infrastructure invalidity

Dropping invalid trials as if they never existed can make a fragile evaluator look strong. Countermeasure: publish planned, valid, invalid, no-hit, eligible, recovered, and failed counts. Set a release gate: more than 2% infrastructure-invalid trials invalidates the batch. **UNVERIFIED — experiment `D016-INFRA-RATE` will settle the 2% threshold:** run 500 no-op/control trials across both providers and set the threshold above the measured 99% confidence bound. It is **unlikely (20-45%)** that exactly 2% is optimal; it is a provisional explicit gate rather than a hidden judgment.

## 11. Calibration and acceptance plan

### Phase 0: evaluator proof

- 8 tiny local tasks, two per fault stratum.
- One scripted robust reference, one retry-only baseline, one abort-on-error baseline.

### Phase 2: decision gate

Promote a recovery mechanism only if:

6. manual transcript/outcome audit finds no systematic false passes.

## 12. Alternatives considered and rejected

### “Error followed by success” from historical transcripts

Rejected. It cannot prove causal closure, no human help, or outcome correctness. The corpus retry table contains only eight tool/run aggregates (`corpus.json:10297-10369`), and hooks are no data (`corpus.json:13261`).

### Raw success rate under injected faults

Rejected as the sole recovery metric. It conflates base task competence with recovery. Retained as `AutonomousOutcomeTSR` to expose denominator gaming.

### Time/token/call-weighted scalar

Rejected as headline. It would favor terse or prematurely stopping agents and risks penalizing the owner's high-value, low-KB/token verifier. Recovery curves and diagnostics preserve efficiency information without paying agents for output volume.

### LLM judge of “good recovery reasoning”

Rejected as primary. It rewards narrated process, can miss silent semantic failure, and is not mechanically independent of model behavior. A calibrated rubric may adjudicate open-ended research outcomes only, tagged `UNVERIFIED` until `D016-RESEARCH-GRADER-CAL` passes.

### Mandatory exact recovery path

Rejected. It overfits known alternatives and punishes creative valid solutions. Oracle paths prove feasibility and estimate diagnostic recovery cost; they do not constrain the agent's path.

### Production daemon / durable workflow engine

Rejected by the anti-overfit gate. Prospective scoring needs a disposable launcher, proxy receipts, existing hooks, and offline aggregation—not a second scheduler or state platform.
