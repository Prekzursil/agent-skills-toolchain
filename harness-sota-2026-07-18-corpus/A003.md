# A003 — coherence audit: `rules/common/coding-style.md`

## Scope and result

This unit read the target rule in full and audited the read-only bundle at
`/local_disk0/codexwork/bundle`. It wrote no subject file. The target contains seven operative
clusters: universal immutability (`coding-style.md:23-33`), 200–400-line typical / 800-line maximum
files (`:35-41`), comprehensive error handling at every level (`:43-49`), system-boundary input
validation (`:51-57`), and completion checks for functions under 50 lines, files under 800 lines,
nesting no deeper than four, no hardcoded values, and no mutation (`:59-68`). Citations below use
the unpacked Linux paths because the Windows subject paths do not exist on this job node.

The decisive result is that this is not one coherent policy. It is a mixture of:

1. sound boundary principles (validate untrusted input, do not silently lose failures);
2. useful review heuristics written as universal hard limits (50/800/four);
3. an incorrect absolute (`ALWAYS` copy and `NEVER` mutate);
4. a substantially unmechanized checklist; and
5. scope metadata that omits several languages whose own files claim to extend it.

I found 17 reportable collision instances, grouped below without hiding repeated language-specific
instances. AGENTS.md §10 puts the user/permissions first, security next, the cross-tool contract
next, project/repo governance next, and third-party skills last
(`/local_disk0/codexwork/bundle/claude/AGENTS.md:115-131`). It does **not** order two files in the
same rules layer. The rules README supplies a separate specific-over-general rule at
`/local_disk0/codexwork/bundle/claude/rules/README.md:93-104`; where even that does not settle a
same-level collision, this report says so explicitly.

## Detailed analysis and resolutions

### C01–C05 — the immutability absolute is wrong as written

The common rule does not say “prefer,” “at interfaces,” “for shared state,” or “unless the language
idiom requires mutation.” It says `ALWAYS` and `NEVER` (`coding-style.md:23-30`) and repeats “No
mutation” in the completion checklist (`:68`). Five specific rules materially narrow or override
that statement, as listed above. The rules README even uses Go mutation as its canonical override
example (`rules/README.md:100-104`), while also claiming overridable common rules are marked with a
language note (`:106-110`); the target has no such note (`coding-style.md:21-68`). That missing note
is an additional STALE documentation defect within this collision family.

The harness implementation is a concrete counterexample to its own absolute. The shared dispatcher
mutates lists with `append`/`extend` (`hooks/_dispatch/dispatch.py:192-223,243-279`), and the shared
harness mutates result/state containers throughout, for example
`agents/harness/registration.py:105-121`, `agents/harness/dispatcher.py:276-307,424-430`, and
`agents/harness/ledger.py:705-733`. These are ordinary local accumulators and state machines, not
hidden alias mutation. Treating them as forbidden would make the implementation noisier without
making it safer.

**Resolution — CONFIG (settings/JSON only).** Rewrite the rule text (configuration/instruction
content, not runtime code) to: “Prefer immutable values and copy-on-write at public APIs, shared
state, and domain-state transitions. Local mutation is allowed when ownership is exclusive,
contained, idiomatic, and clearer. Never mutate caller-owned input unless the API explicitly
documents it.” Add the promised language-override note. It is **very likely (80-90%)** this will
reduce instruction conflict without reducing safety because five specific rules already encode
this boundary and the harness’s own implementation relies on contained mutation (evidence: C01–C05
and the cited dispatcher/ledger lines).

Rejected alternative: mechanically ban `.append`, `var`, `let mut`, setters, or in-place algorithms.
That would flag local builders, performance-sensitive buffers, actor-owned state, and idiomatic
language constructs. It fails the anti-overfit gate by converting a semantic ownership question
into a brittle token guard.

### C06–C07 — “handle at every level” conflicts with propagation and intentional discard

Logging at every layer and then rethrowing creates duplicate logs; translating at every layer loses
error identity; catching at every layer can make cancellation and cleanup less correct. The Java
rule correctly places broad catches at top-level handlers (`rules/java/coding-style.md:89-100`). The
static-analyzer rule has a real intentional-discard case (`rules/common/static-analyzer.md:11-19`).
At the same time, the target’s “never silently swallow errors” captures a useful requirement: an
unexpected failure must not disappear.

The harness again embodies the exception: `_disabled` and `_worker` catch and `pass` under explicit
fail-open contracts (`hooks/_dispatch/dispatch.py:134-140,182-190`). The behavior is coherent with
AGENTS.md’s requirement that hook errors fail open (`AGENTS.md:64-70`), but incoherent with the
unqualified coding-style sentence.

**Resolution — CONFIG (settings/JSON only).** Replace “at every level” with three cases: recover or
translate once at an appropriate boundary; otherwise propagate while preserving cause/context;
intentionally discard only a narrowly expected failure with an adjacent rationale. Keep UI-safe
messages and server-side structured detail, but say “log once at the owning boundary.” It is
**almost certain (90-99%)** this resolves the documented conflict because both current exception
sites become expressible without weakening the rule for unexpected errors (evidence: C06–C07 and
AGENTS.md fail-open contract).

### C08–C10 — “no hardcoded values” is not a usable invariant

The security floor is precise: never hardcode **secrets** and validate their presence at startup
(`AGENTS.md:93-98`; `rules/common/security.md:38-43`). Code review uses the same secret/credential
scope (`rules/common/code-review.md:49-55,104-107`). The target silently expands that into every
value (`coding-style.md:67`). Language examples immediately require literals: fallback strings and
validation bounds in TypeScript (`rules/typescript/coding-style.md:69-76,180-192`), and design-token
values in web code (`rules/web/coding-style.md:48-66`).

**Resolution — CONFIG (settings/JSON only).** Replace the checklist item with “No hardcoded secrets.
Extract repeated values and independently changeable domain/deployment policy into named constants
or validated config; keep obvious local literals local.” It is **very likely (80-90%)** this will
improve compliance signal because it matches both the security floor and the language examples
(evidence: C08–C10). Do not add a generic literal scanner; it would be another prose/token detector
of the class already confirmed to false-positive in
`INPUT-known-harness-defects.md:9-50,65-82`.

### C11–C12 — thresholds need one owner and named semantics

The 50/800/four values are duplicated verbatim across coding style and code review. Duplication is
already a maintenance hazard even before values drift. Kotlin’s “max two” applies only to nested
scope functions, but the unqualified numbers look like competing global nesting limits.

**Resolution — CONFIG (settings/JSON only).** Create one small “complexity review triggers” table
owned by coding style and link to it from code review. Label 50 function lines, 800 file lines, and
four control-flow nesting levels as review triggers rather than correctness failures; label Kotlin’s
two as scope-function nesting. It is **likely (55-80%)** that review-trigger language preserves the
useful decomposition nudge with fewer false positives because the current harness itself contains
legitimate modules above 800 lines (line-count evidence in the corpus section below).

### C13–C14 — path-scoped inheritance is incomplete

The common rule frontmatter lists 17 patterns but omits all Dart and Perl source patterns and
several secondary extensions (`coding-style.md:1-20`). The specific files say they extend common,
but a Markdown link is not evidence that Claude Code recursively loads the linked file. **UNVERIFIED:
whether this installed Claude Code build follows rule-file links as transitive instructions; the
settling experiment is a controlled session editing a `.dart`, `.pl`, `.csx`, `.kts`, and `.hpp`
file and inspecting the loaded-instructions trace for `common/coding-style.md`.** Until that
experiment, the safe conclusion is limited to a metadata mismatch, not a runtime non-load claim.

**Resolution — CONFIG (settings/JSON only) — inherits the UNVERIFIED premise only for runtime
impact.** Align common frontmatter with the union of installed language source extensions, or move
the genuinely universal subset into an always-loaded contract and keep path-specific examples in
language files. It is **almost certain (90-99%)** this removes the static mismatch because the union
is directly enumerated by the cited frontmatter; runtime behavior remains UNVERIFIED by the trace
experiment named above.

### C15–C17 — the enforcement surface is both incomplete and over-blocking

The live settings wire `per-edit-check` for `Edit|Write|MultiEdit`
(`settings.json:333-342`). Its own contract says Python gets Ruff/compile, JS gets syntax, TS and Rust
are skipped, JSON/YAML are parsed, and unknown extensions silently pass
(`hooks/per-edit-check/check.py:8-26,151-170`). It never measures immutability, file/function size,
nesting, hardcoded policy, error-boundary quality, or input-boundary validation. The dispatcher’s
other active edit check only records possible stubs, and Stop checks cover wiring, honesty, stubs,
TODOs, and journey coverage (`hooks/_dispatch/manifest.json:72-180`), not these style clauses.

The checker also hard-blocks syntax failures (`check.py:225-244`). That is an unruled enforcement
relative to the target and a direct conflict with the higher-precedence cross-tool contract, which
reserves exit 2 for irreversible/dangerous operations and requires ordinary guidance to inject
context (`AGENTS.md:64-70`). YAML is additionally outside the target’s path scope
(`coding-style.md:1-20`).

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Change syntax
failures from exit 2 to an exit-0 `additionalContext` nudge. Add a cheap changed-file line-count and
available-project-linter nudge behind the existing post-edit bus; do not implement semantic regexes
for mutation/error handling/input validation. It is **very likely (80-90%)** this will align hook
behavior with AGENTS §6 because it changes the explicitly conflicting exit protocol and reuses the
already wired checker (evidence: `check.py:225-244`, `settings.json:333-342`, `AGENTS.md:64-70`). Its
effect on style adherence is **UNVERIFIED; the settling experiment is an A/B replay of matched edit
turns measuring post-edit lint/size defects, false-nudge rate, and completion defects with and
without the nudge.**

Anti-overfit gate: this proposal rides the existing PostToolUse bus, stays under the small-hook
budget, and introduces none of the rejected components (no second orchestrator, vector/KG memory,
durable execution engine, trained critic, observability SaaS, or guardrail framework). The semantic
clauses remain review guidance because ownership, boundary placement, and justified literals cannot
be reliably inferred from token patterns.

## Measured behavior and corpus interpretation

### What the corpus can establish

The corpus is operational telemetry, not a snapshot of generated source. Its `_meta` says it is a
distillation of tool counts/fingerprints with capped samples (`inputs/corpus.json:1`). It has no
per-edit code body, AST metric, file-length metric, mutation detector, nesting detector, boundary
validation detector, or hardcoded-value detector. Therefore **UNVERIFIED: corpus-wide adherence to
the target’s source-style clauses; the settling experiment is to join raw transcript Edit/Write
payloads to their repository snapshots, run language-aware analyzers on changed code, and compare
violations before/after the rule was loaded.** The raw Windows transcripts named in `_meta.root`
are not present on this Linux node, so this unit cannot perform that join.

The corpus does provide one relevant boundary-validation signal. `StructuredOutput` has 3,694 calls,
846 errors, and a 22.9% error rate, with 294 occurrences of the fingerprint requiring both
`kg_triples` and `confidence` (`inputs/corpus.json:1`, fields `tool_usage` and
`error_fingerprints`). That shows schema enforcement is actively encountered; it does **not** prove
the coding-style instruction caused it. It also demonstrates why “use schema-based validation where
available” (`coding-style.md:53-56`) needs a proportionality clause for agent fan-out: the pinned
ground truth identifies over-strict fan-out schemas as the failure mode. This is a STALE rule-design
collision with measured operation, not evidence that boundary validation itself is wrong.

**Resolution — CONFIG (settings/JSON only).** Amend the validation clause to distinguish security/
data-integrity boundaries from internal agent handoffs: validate untrusted external inputs strictly;
for fan-out outputs require only fields the immediate consumer truly needs, permit additive fields,
and repair/default non-safety metadata when lossless. It is **likely (55-80%)** this will reduce
schema retries because 294 failures share the two-required-field fingerprint, but the causal effect
is **UNVERIFIED; the settling experiment is a replay of those sampled fan-out prompts with minimal
consumer-driven schemas versus current schemas, measuring first-pass validity and downstream
answer quality.**

The 939 “File has not been read yet” fingerprint and Edit/Write error rates (919/28,964 and
439/12,845 respectively) are real (`inputs/corpus.json:1`) but do not test any coding-style clause;

Classification matters:

* **Badly written:** “handle errors at every level” conflates recovery, translation, logging, and

* **Unenforced but mechanically tractable as a nudge:** changed-file line count and project-native
  formatter/linter checks.
* **Stale:** scope frontmatter, the absent override note promised by README, the documented-but-not-
  wired 800-line hook, and the unqualified schema recommendation in the face of measured strict-
  schema failures.

## Recommended final form

### P0 — make the instruction internally coherent — CONFIG (settings/JSON only)

Replace the absolutes with four concise principles:

1. Prefer immutable public/shared/domain state; allow contained, exclusively owned, idiomatic
   mutation.
2. Handle failures once at the recovery/translation boundary; otherwise propagate with cause and
   context. Intentional discard must be narrow and documented.
3. Validate untrusted external input strictly. Keep internal handoff schemas minimal and
   consumer-driven.
4. Treat 50 function lines, 800 file lines, and four control-flow nesting levels as review triggers,
   not universal correctness failures. Never hardcode secrets; extract repeated or independently
   changeable policy.

Add the language-override note promised by `rules/README.md:106-110` and align frontmatter with the
installed language union. This is **very likely (80-90%)** to remove all wording/precedence
collisions C01–C14 because each replacement directly encodes the narrower specific rules cited in
the register.

### P1 — align enforcement with AGENTS §6 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Make per-edit syntax/lint/size findings nonblocking context, project-aware, and changed-file-only.
Do not add regex enforcement for semantic clauses. This is **very likely (80-90%)** to remove C15–C17’s
static protocol conflict because exit 2 is the exact conflicting mechanism; adherence impact remains
UNVERIFIED by the A/B replay experiment specified above.

### P2 — measure rather than assume — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Extend the existing event record with the check name, outcome, latency, and stable reason code, then
evaluate false-nudge and fix-through rates. This responds to the confirmed telemetry gap
(`INPUT-known-harness-defects.md:133-147`) without introducing an observability service. It is
**likely (55-80%)** to make future rule-effect claims falsifiable because the missing fields are the
ones required to join an enforcement event to an edit, but Windows persistence is **UNVERIFIED; the
settling experiment is to emit one known hook record, restart/compact, and retrieve it through both
the event ledger and transcript path.**
