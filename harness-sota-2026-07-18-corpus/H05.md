# H05 — Communication / human-likeness: when “I noticed X; want me to Y?” helps versus annoys

**Unit:** H05  
**Family:** communication / human-likeness  
**Question:** When should an agent surface an observation with a proposed action, and what is the gating rule?  
**Date:** 2026-07-19  
**Mode:** research and design only; the unpacked subject was read-only. The only write is this artifact.

## Executive answer

The phrase is not the pattern worth preserving. The useful pattern is **mixed initiative with earned interruption**:

> **Do not ask “want me to?” when the action is already authorized, in scope, reversible, cheap, and externally verifiable. Do it, verify it, and report the receipt. Ask only when the owner must supply missing authority, preference, or information that would materially change the outcome. If the observation matters but does not deserve an interruption now, escrow it in the existing thread/ledger machinery and resurface it at a verified breakpoint.**

The proposed gating rule is:

```text
1. ADMISSIBILITY
   candidate is admissible only if:
   - it is relevant to the active goal or a user-authored open thread;
   - X is backed by an EXTERNAL signal;
   - “absent / broken / done” has two mechanically independent signals,
     including a known-positive detector control;
   - there is a concrete Y and a falsifiable done signal.

2. AUTHORITY / ACTION LANE
   A. JUST DO + RECEIPT
      if Y is in scope, reversible, low-risk, cheap, and does not consume a scarce
      owner preference. Report later: “Noticed X; did Y; receipt Z.”
   B. ASK NOW
      only if continuing would be unsafe/wasteful AND Y needs new authority,
      irreversible external change, secret/credential, or a real preference choice.
   C. QUEUE, NEVER DROP
      if valuable but non-urgent: append evidence + proposed action + trigger + expiry
      to the existing event-ledger/open-loop/OPEN-THREADS bus. Do not interrupt.
   D. DROP
      if irrelevant, unactionable, duplicate, or below value/cost threshold.

3. TIMING
   Surface B or a queued C only at an externally observable breakpoint (terminal tool
   receipt, completed subgoal, failure that prevents safe continuation, or owner turn),
   except an imminent irreversible hazard, which may interrupt immediately.

4. WORDING
   observation + evidence + consequence + one bounded action/default.
   Never append a generic “if you want” menu to completed work.
```

This is **very likely (80-90%)** to reduce annoyance without losing valuable initiative, because (a) the owner explicitly said “No check-ins between items” and corrected a re-ask with “I’ve already told you to do that” in manually inspected corpus samples (`/local_disk0/codexwork/bundle/inputs/corpus.json:11339`, `:11837`), (b) the existing behavior contract already limits questions to material ambiguity in the first 1–2 actions (`/local_disk0/codexwork/bundle/codex/AGENTS.md:5-10`), and (c) controlled notification research finds lower interruption cost at task breakpoints, while the CHI human–AI guidelines require contextual timing, efficient dismissal/correction, and scoped behavior when uncertain ([Iqbal & Bailey, Oasis](https://www.microsoft.com/en-us/research/publication/oasis-a-framework-for-linking-notification-delivery-to-the-perceptual-structure-of-goal-directed-tasks/); [Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). The owner-specific effect size is **UNVERIFIED; the experiment that settles it** is the receipt-backed, owner-approved A/B in Finding 8.

## Findings (inferred-surprise first)

### Finding 1 — Invert “fail-open” for optional chatter: fail-open execution, fail-silent interjection

**Improvement:** Make a broken proactive gate preserve execution but emit no optional suggestion. Safety-critical alerts remain outside this optional lane.

**What it is:** Today, `calibrated-silence` defines a read error, corrupt/empty ledger, disabled gate, or exception as `ALLOW` (`calibrated_silence.py:142-162`, `:385-428`), and each consumer shim also returns `True` on import/error (`inquisitiveness/prompt-guard.py:29-49`; `persist-nudge/nudge.py:28-52`; `open-loops/trigger_match.py:43-67`). Its tests explicitly require “read error -> allow” and “garbage ledger -> allow”; I ran both test files successfully, independently confirming that this is intentional executable behavior rather than a comment-only claim. This satisfies process fail-open (exit 0) by becoming **fail-noisy** for the owner: the exact time personalization is unavailable is when every optional interjection is admitted.

**Why-inferred:** Prompt-fatigue is a hard constraint, and the owner’s corpus asks for uninterrupted execution (`corpus.json:11819`, `:11837`). Optional chatter is not a safety control. A corrupt preference ledger should not spend owner attention.

**How-to-build:** In the existing `should_interject` API, return a typed result `{decision: suppress_optional, degraded: true, reason}` on ledger/import/classifier failure. Consumer shims catch all exceptions, write a compact diagnostic to the existing event ledger, exit 0, and emit nothing. Add a `mandatory` class that bypasses calibrated-silence only for externally verified imminent irreversible hazards. Queue any non-urgent observation through Finding 5 so silence does not drop the thread. Replace, do not add, the current `ALLOW` fallback. Add fixtures for missing module, corrupt ledger, permission error, and a known mandatory safety alert.

**EXTERNAL signal that verifies it:** A hermetic subprocess matrix corrupts/removes the preference ledger and imports each consumer: exit code must be 0, stdout empty for optional candidates, and an event-ledger receipt must exist. A separately seeded known mandatory hazard must still produce an alert. These are execution receipts from different components, not same-context self-review.

**SOTA citation:** Amershi et al. require easy dismissal, scoped service under uncertainty, and cautious adaptation ([CHI 2019 paper, Guidelines 8, 10, 14](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).

**Confidence:** **very likely (80-90%)** to prevent bursty nagging during gate degradation; evidence is the executable allow-on-error behavior plus the owner’s explicit no-check-in samples. The frequency of real gate degradation is **UNVERIFIED; the experiment that settles it** is a 30-day count of typed degraded receipts in the existing ledger.

**NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — modify the existing gate and consumer shims; no new registration.  
**Value × effort:** **high × low**  
**Novelty:** **inferred-surprise**

### Finding 2 — Repair the learner before letting it personalize interruptions

**Improvement:** Replace coarse next-turn inference with receipt-addressed outcomes and keep ambiguous reactions unknown.

**What it is:** Two independent signals prove that the present feedback math can reward annoying suggestions:

1. Static code: `hit_rate` includes only `acted + ignored`, omitting `annoyed` from its denominator (`calibrated_silence.py:243-266`). `apply_reactions` classifies **every** pending row in a session against the same next prompt and same tool set (`log_reaction.py:263-301`), while any substantive response counts as “acted” for a question (`:143-151`).
2. Execution probes: with 20 `annoyed` and 5 `acted` suggestion rows, the shipped function returned `p=0.782754..., acted=5, ignored=0`; with one pending question and one pending suggestion, one substantive answer resolved both rows as `['acted', 'ignored']`. Both shipped test suites passed, showing existing tests encode the current semantics but miss these cases.

Thus the learner does not yet support a trustworthy owner-specific gating policy.

**Why-inferred:** The owner wants human-like adaptation, but false learning is worse than a static conservative rule: it can convert dismissals into an apparently high hit rate and can attribute one reaction to unrelated interjections. The known-defects file independently documents seven wrong conclusions caused by unvalidated signals (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`), making coarse attribution especially contraindicated here.

**How-to-build:** Extend each existing interjection row with `candidate_id`, `source`, `target_action`, `emitted_turn_id`, `evidence_receipt_ids`, and `outcome_deadline`. Credit `acted` only when (a) the exact proposed action has a matching later tool/ledger receipt tied to `candidate_id`, or (b) the owner explicitly selects the corresponding `AskUserQuestion` option. Count `annoyed` as a negative outcome with at least the weight of `ignored`. Do not turn an unrelated next prompt into “ignored”; leave it `unknown` until deadline, then use an explicit censored outcome rather than silently equating non-response with dislike. Only one candidate may claim a tool receipt. Keep all writes append-only or atomic as today.

**EXTERNAL signal that verifies it:** A golden transcript suite with two simultaneous suggestions, an unrelated next prompt, a dismissal, an explicit selection, and one matching tool receipt must produce exactly one credited action, one negative dismissal, and censored unrelated rows. A second, mechanically independent replay reads the resulting JSONL and recomputes the confusion matrix against hand-authored labels. The gate ships only if both agree.

**SOTA citation:** Contextual-bandit systems learn from partial user feedback, but reliable offline evaluation requires carefully logged random/propensity data rather than treating unobserved outcomes as known ([Li et al., WWW 2010](https://www.microsoft.com/en-us/research/publication/a-contextual-bandit-approach-to-personalized-news-article-recommendation-3/); [Wang, Agarwal & Dudík, ICML 2017](https://www.microsoft.com/en-us/research/publication/optimal-adaptive-off-policy-evaluation-contextual-bandits/)).

**Confidence:** **almost certain (90-99%)** that the current calculation mishandles `annoyed`, because source inspection and direct execution independently reproduce it. It is **very likely (80-90%)** that receipt addressing improves attribution, based on the exact candidate/action mapping and established logged-feedback methodology; owner-level benefit magnitude remains **UNVERIFIED; the experiment that settles it** is Finding 8’s preregistered replay/A/B.

**NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — schema and classifier correction inside calibrated-silence/log-reaction.  
**Value × effort:** **high × medium**  
**Novelty:** **inferred-surprise**  
**Autonomy:** **just-do-it**

### Finding 3 — Replace fatigue folklore with observable task phase

**Improvement:** Gate timing on task breakpoints and explicit focus signals, not word count or wall-clock hour.

**What it is:** The current fatigue model assumes a prompt of four or fewer words means “the user wants less chatter” and that before 06:00/after 23:00 warrants a fatigue penalty (`calibrated_silence.py:28-37`, `:109-123`, `:289-297`, `:358-373`). Those premises are **UNVERIFIED; the experiment that settles them** is to correlate each feature with explicit owner dismissals/acceptance after repairing attribution in Finding 2. The corpus itself contains terse messages that mean urgency or recovery (“go again at it since it seems you were stuck,” `corpus.json:11801-11810`), so terseness does not uniquely indicate fatigue. Conversely, “No check-ins between items” is an explicit focus signal (`:11837`) and should dominate.

**Why-inferred:** The owner’s session quality tracks focus. Timing at semantic breakpoints preserves flow better than guessing cognitive state from style or local time, especially across a Windows owner and remote/Linux execution contexts.

**How-to-build:** Feed the existing gate a small enumerated `task_phase` derived from external lifecycle receipts: `executing` (tool/subagent active), `breakpoint` (terminal tool receipt or subgoal completed), `blocked` (verified failure prevents progress), `owner_turn`, `finalizing`. Add explicit session directives such as `no_checkins_until:<terminal-id>` to the existing goal/event ledger. Policy: queue during `executing`; surface at `breakpoint` or `owner_turn`; immediately surface only `blocked + cannot safely pivot` or an imminent irreversible hazard. Remove the late-hour term. Put terseness in shadow-only telemetry until the settlement experiment supports it. Fold this input into calibrated-silence; no lifecycle hook is added.

**EXTERNAL signal that verifies it:** Replay timestamped lifecycle events and assert that identical candidates are queued during an active tool and released only after a terminal `SUCCESS:/FAILED:` receipt. Then compare interruption-at-breakpoint versus interruption-mid-action in the owner-approved trial (Finding 8), measuring dismissals and “already told/no check-ins” corrections.

**SOTA citation:** Controlled notification work reports that aligning delivery with the perceptual structure of goal-directed tasks reduces interruption costs ([Iqbal & Bailey, Oasis](https://www.microsoft.com/en-us/research/publication/oasis-a-framework-for-linking-notification-delivery-to-the-perceptual-structure-of-goal-directed-tasks/)). Amershi et al.’s Guideline 3 is “Time services based on context” ([CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Recent proactive-agent work also separates having a potentially useful thought from finding the appropriate turn to contribute ([Liu et al., Proactive Conversational Agents with Inner Thoughts](https://arxiv.org/abs/2501.00383)). This unit adopts that separation but rejects same-context self-validation: release is keyed to external lifecycle receipts.

**Confidence:** **very likely (80-90%)** that breakpoint gating is a better default than late-hour/terse proxies, supported by controlled interruption research, the direct owner focus instruction, and the absence of local validation for the proxies. Exact weights are **UNVERIFIED; the experiment that settles them** is the explicit-feature correlation and bounded trial above.

**NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — add one context enum and ledger directive to the existing gate.  
**Value × effort:** **high × medium**  
**Novelty:** **inferred-surprise**

### Finding 4 — Make silence lossless with “thread escrow,” not repeated reminders

**Improvement:** Every suppressed but material observation becomes a triggerable, deduplicated thread; silence controls timing, not memory.

**What it is:** “Never drop a thread” and “prompt fatigue” are compatible if suppression means **queue**, not forget. The existing open-loop code already supports contextual conditions, one-shot firing, recurring throttles, a maximum of three firings, and explicit closure (`open-loops/trigger_match.py:1-28`, `:70-136`). The behavior contract already distinguishes the objective event ledger from semantic basic-memory (`codex/AGENTS.md:64-91`). Build on those rather than inventing another memory store.

**Why-inferred:** The corpus shows both sides of the problem: the owner dislikes intermediate check-ins (`corpus.json:11837`) and also calls the agent back when it appears stuck (`:11801-11810`). A quiet escrow preserves initiative without making the owner repeatedly hold the queue in working memory.

**How-to-build:** When a candidate passes admissibility but fails the timing/authority threshold, append one normalized record through existing `note.py`/open-loops:

```json
{
  "kind": "observation",
  "fingerprint": "project|object|condition|proposed_action",
  "x": "observation",
  "evidence_receipts": ["r1", "r2"],
  "y": "bounded proposed action",
  "why_now": "goal linkage",
  "trigger": {"on": "subgoal_complete|file_touch|session_start|owner_topic"},
  "authority": "just_do|confirm",
  "expires_or_supersedes": "..."
}
```

Deduplicate by fingerprint; merge stronger evidence; close on the proposed action’s external receipt; supersede stale facts rather than deleting history. At the next matching breakpoint, emit at most one compact digest ordered by consequence of forgetting. If the owner says “no check-ins,” retain the records but suppress release until the named terminal condition.

**EXTERNAL signal that verifies it:** A deterministic scenario queues three observations during execution, restarts/compacts, supplies one matching trigger, and checks two independent outputs: the ledger still contains all three, while the owner-facing output contains only the single triggered item. Applying the action’s execution receipt must close that item and prevent resurfacing on a second session start.

**SOTA citation:** Human–AI guidelines call for recent-interaction memory, contextually relevant information, and cautious adaptation ([Amershi et al., Guidelines 4, 12, 14](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Field notification research finds that users value passive awareness even while acknowledging disruption, supporting a low-interruption awareness channel rather than all-or-nothing alerts ([Iqbal & Horvitz, Notifications and Awareness](https://www.microsoft.com/en-us/research/publication/notifications-and-awareness-a-field-study-of-alert-usage-and-preferences/)).

**Confidence:** **very likely (80-90%)** that escrow reconciles the two hard constraints, because durable storage and contextual resurfacing already exist and the verification is receipt-based. The best digest cap (one versus more) is **UNVERIFIED; the experiment that settles it** is the owner-approved comparison in Finding 8.

**NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — establish the record contract and routing policy on the already-built event-ledger/open-loops bus, with only the smallest schema extension needed after a record round-trip probe.  
**Value × effort:** **high × low**

### Finding 5 — The action ladder: act, ask, escrow, or drop

**Improvement:** Replace the default binary “mention versus ask” with four lanes based on authority, reversibility, urgency, and verification.

**What it is:** The exact “want me to?” form is helpful only in the **ASK NOW** lane. It annoys when it delegates a safe implementation decision back to the owner, repeats authority already granted, or appends optional work after declaring completion. It helps when the choice changes scope, spends money/quota, sends/deletes/publishes externally, needs a credential, makes an irreversible change, or selects among genuinely different owner preferences.

**Why-inferred:** The owner directly corrected redundant asking (`corpus.json:11339`) and requested autonomous chaining (`:11819`, `:11837`). The existing contract already says questions occur only for material ambiguity in the first one or two actions, never mid-task, with `*` as an explicit bypass (`codex/AGENTS.md:5-10`). This finding generalizes that contract to observations discovered during execution.

**How-to-build:** Add the executive gating rule to the shared behavior contract and prompt templates. The decision table is:

| Externally verified observation | Proposed action | Lane | Owner-facing behavior |
|---|---|---|---|
| Relevant; action in scope, reversible, cheap | Safe to execute | JUST DO | Execute; report X/Y/receipt at breakpoint |
| Relevant; action needs new authority/preference or is irreversible | Cannot safely continue without it | ASK NOW | One focused `AskUserQuestion`, recommended default first |
| Relevant; action useful but not urgent | Can wait without compounding harm | ESCROW | Store trigger/evidence/action; no prompt now |
| Duplicate, irrelevant, unactionable, or weakly evidenced | No earned value | DROP | No owner message; optional diagnostic counter only |

If an in-scope action fails, the agent may take one externally distinguishable safe pivot without asking; repeated same-approach failure or exhausted safe pivots moves to ASK NOW. This uses terminal execution results, not same-context “I think I fixed it.”

**EXTERNAL signal that verifies it:** A policy conformance suite presents a reversible lint fix, an external publish, an unrelated gem, a duplicated suggestion, and a repeated failed action. Expected outputs are respectively execute+receipt, AskUserQuestion, escrow, drop, and ask/pivot based on terminal receipts. A fresh-context second model labels only the lane from the evidence packet; disagreement fails the case rather than letting the generating context approve itself.

**SOTA citation:** Amershi et al. recommend contextual timing, efficient invocation/dismissal/correction, and scoping when uncertain ([CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Their guideline set was validated through multiple rounds including 49 practitioners evaluating 20 AI products ([Microsoft publication page](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**Confidence:** **almost certain (90-99%)** that redundant “want me to?” prompts conflict with this owner’s explicit execution preference, based on direct samples and the current behavior contract. The four-lane policy’s net benefit is **very likely (80-90%)**, supported by the same signals and HAI guidance; exact lane thresholds are **UNVERIFIED; the experiment that settles them** is the conformance replay plus Finding 8.

**NATIVE-vs-BUILD:** **CONFIG (settings/JSON only)** — behavior-contract and prompt-template change using native AskUserQuestion, tool execution, and existing ledger.  
**Value × effort:** **transformative × low**  
**Novelty:** **user-asked**  
**Autonomy:** **confirm-first**

### Finding 6 — No naked observation: require evidence, consequence, and a done signal

**Improvement:** Surface only an “observation envelope,” never a self-certified hunch.

**What it is:** Before the owner sees “I noticed X,” the candidate must contain: (1) the active-goal link, (2) concrete evidence, (3) calibrated truth confidence, (4) consequence of doing nothing, (5) one proposed action, (6) authority/reversibility class, and (7) an external done signal. Claims of absent/broken/done additionally require two mechanically independent signals and a known-positive control. This directly enforces the law binding this unit.

**Why-inferred:** The live defects document six confident wrong calls from single unvalidated probes and a seventh detector failure caught by a known-positive control (`INPUT-known-harness-defects.md:111-129`). The corpus also shows meaningful tool failure/retry pressure (`corpus.json:10297-10369`). Proactive surfacing amplifies a false observation because it asks the owner to reallocate attention around it.

**How-to-build:** Add a typed candidate schema to the existing calibrated-silence function call, not a new detector:

```text
candidate_id, goal_id, observation, evidence_receipt_ids[],
known_positive_control_receipt?, confidence_band, consequence,
proposed_action, authority_class, reversibility, done_signal,
dedupe_fingerprint, timing_deadline
```

Reject from owner-facing lanes if required fields are missing; save only a diagnostic rejection count. For cheap factual uncertainty, run the external probe first. If no cheap probe exists and the observation still warrants asking, label uncertainty inline and ask for the missing external information—not for the owner to validate a technical fact the harness can test. Any same-context critic output is advisory only and cannot populate an evidence receipt.

**EXTERNAL signal that verifies it:** Schema fixtures include a known-present control and two distinct probes for absent/broken/done claims. Mutate each receipt independently: removing either must prevent surfacing. A real execution/test/owner-selection receipt must be required to close the action. A fresh-context verifier receives only the envelope and source artifacts; its verdict is the second-model signal, never the originating context’s opinion.

**SOTA citation:** In a preregistered CHI 2025 experiment (N=308), explanations increased reliance on both correct and incorrect answers, whereas sources or visible inconsistencies reduced reliance on incorrect responses ([Kim et al., CHI 2025](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies/)). This supports concrete source/receipt exposure rather than a fluent rationale. A separate preregistered study (N=404) found that wording of uncertainty changes reliance and trust ([Kim et al., FAccT 2024](https://www.microsoft.com/en-us/research/publication/im-not-sure-but-examining-the-impact-of-large-language-models-uncertainty-expression-on-user-reliance-and-trust/)).

**Confidence:** **almost certain (90-99%)** that this catches the documented single-signal class, because the exact missing control becomes a required external field. It is **very likely (80-90%)** to improve trust calibration rather than merely confidence, based on the controlled reliance studies and local incidents. The optimal amount of evidence displayed to the owner is **UNVERIFIED; the experiment that settles it** compares one-line receipt IDs against expanded evidence on correction rate and task-resumption time.

**NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — typed input/validation inside calibrated-silence/truth-verify, folded into an existing hook invocation.  
**Value × effort:** **high × medium**

### Finding 7 — Use three terse speech acts; ban generic post-completion menus

**Improvement:** Standardize the utterance to the lane so the owner can parse it without a conversation tax.

**What it is:**

* **Executed:** “Noticed **X** (receipt A/B); it affected **goal G**, so I **did Y**. **Z verifies it**.”
* **Needs decision:** “Noticed **X** (A/B). Continuing risks **C**. **Y** needs your approval because **R**. Proceed with **Y**? [recommended default / alternative]”
* **Escrowed:** “Noticed **X** (A/B); queued as **thread T** for **trigger K**. No action needed now.” Include this only in a breakpoint/final digest, not immediately.

Do not say “I noticed X, want me to Y?” after completed work when Y is an obvious in-scope continuation. Do not list “three possible follow-ups if you want” unless the task genuinely terminates at a preference fork. Do not anthropomorphize confidence (“I feel”) where receipts exist.

**Why-inferred:** The owner’s “finish it” correction (`corpus.json:11339`) is precisely the failure mode of handing an already-authorized continuation back as a menu. HAX requires making clear why the system acted and supporting efficient invocation/dismissal/correction, not maximizing conversational turns.

**How-to-build:** Put these templates and the prohibited generic-menu rule in the shared behavior contract/output style. AskUserQuestion gets at most one decision with 2–3 mutually exclusive choices and the recommended safe default first. Report the consequence and authority boundary, not an essay. All technical claims link to receipt IDs or path:line. The final response includes escrowed threads by stable ID so none vanish.

## Bottom line

“I noticed X, want me to Y?” helps when **X is externally grounded, Y is consequential, and the owner alone can authorize or choose Y**. It annoys when the agent already has authority, could cheaply verify or execute Y itself, interrupts mid-flow, repeats a granted instruction, or offers a generic menu after completion.

The harness should therefore be **proactive in action and memory, conservative in interruption**:

* verify X externally;
* just do safe authorized Y and show the receipt;
* ask once when authority/preference is genuinely missing;
* escrow valuable non-urgent observations so no thread disappears;
* release at a real breakpoint;
* learn only from addressed external outcomes, never same-context self-judgment.
