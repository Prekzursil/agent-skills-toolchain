# J02 — Scheduled proactive maintenance beyond drift-audit and backup

**Unit:** J02  
**Family:** background / anticipatory “dreaming”  
**Question:** What genuinely needs periodic attention, and what is make-work?  
**Date researched:** 2026-07-19

## Executive answer

The harness does need periodic attention, but not a general-purpose agent that wakes up and “looks for ways to improve things.” The defensible maintenance set is narrow: replay real failures against the current harness; reconcile durable open threads with external project state; challenge time-sensitive memories; prove backups by restoring them; measure whether gates earn their latency and interruption cost; detect statistically meaningful reliability regressions; and batch all non-urgent results into one attention-budgeted digest. Calendar-driven capability updating, routine self-reflection, repeated corpus summarization, “green” reports, and maintenance triggered only by non-use are make-work.

This conclusion is **very likely (80-90%)** to improve reliability without increasing owner load. Evidence: the corpus contains repeated, high-volume error classes and explicit persistence corrections, while its own correction detector is recall-biased and its hook detector fails a known-positive control (`/local_disk0/codexwork/bundle/inputs/corpus.json:4281-4318`, `:10297-10369`, `:10371-10426`, `:13260-13263`). The design therefore turns already-observed failures into external executable checks and surfaces only deltas. The remaining uncertainty is operational: this Linux bundle cannot inspect the live Windows Scheduled Task inventory.

The architecture is intentionally small:

```text
existing Windows scheduler / Claude Desktop local scheduled task
        |
        v
small deterministic producers (read-only or isolated-temp execution)
        |
        +--> external verifier: command/test/CI/git/API/fresh-context model/owner
        |
        v
existing BACKGROUND-DIGEST.md queue
        |
        v
existing folded SessionStart reader (one bounded, once-only summary)
```

No proposal adds a hook, MCP server, orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The existing digest reader is already folded into the dispatcher and explicitly does not consume another hook slot (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:2-10`); the existing weekly semantic-router bench already demonstrates the intended scheduler → digest pattern (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:1-9`). Every proposed scheduled entry point must wrap its whole `main` in `try/except`, return/exit `0` on its own failure, and write nothing to the digest unless an external verifier produced a valid result.

## Finding 1 — A weekly “failure replay foundry,” not another reflection pass

**improvement:** Convert newly frequent real-world failures into a rotating, executable harness replay suite, then run that suite weekly and on harness changes.

**what it is:** A scheduled producer reads the latest distilled `error_fingerprints` and a small verified set of owner-correction exemplars. It admits a case only when it can be represented as (input fixture, expected external observation, negative control). Deterministic cases run against an isolated temporary harness checkout; semantic cases run in a fresh model context and are graded by a deterministic artifact/tool assertion wherever possible. The suite keeps a holdout partition and rotates cases so it cannot merely memorize a fixed prompt. It appends one digest line only when a formerly passing case regresses or a high-volume failure has no replay coverage.

This goes beyond `/self-reflect`, continuous-learning-v2, instincts, truth-verify, and the existing semantic-router bench. Those mechanisms reflect, learn, verify a current claim, or test routing; this finding tests whether today’s harness still survives yesterday’s actual failures. Anthropic’s 2026 eval guidance explicitly recommends sourcing realistic tasks from observed failures and combining automated evals, production monitoring, and periodic human calibration ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

**why-inferred:** The owner wants failures not to recur, not more prose about them. The corpus supplies unusually strong seeds: 1,631 quoting failures, 939 read-before-write failures, 709 command-length failures, and repeated retry runs (`corpus.json:4281-4318`, `:10297-10323`). The live defect report also documents a detector bug that reproduced while its own bug report was being written (`INPUT-known-harness-defects.md:24-41`), which is precisely the kind of regression a replay fixture can catch.

**how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a stdlib-only `maintenance/replay.py` plus JSON fixtures. Reuse the existing weekly task registration pattern and `BACKGROUND-DIGEST.md`; do not register a hook. Pipeline: (1) parse only top/new fingerprint deltas; (2) require a hand-verified or mechanically derived fixture; (3) create a fresh temp directory; (4) invoke the relevant script/CLI with a timeout; (5) require both a known-positive and known-negative control; (6) compare current result with the last-known-good baseline; (7) write at most one delta line. Never mutate the live harness. For an LLM-graded semantic fixture, require agreement with an independent deterministic check or a second model; same-context self-grading is forbidden.

Start with five fixtures, not all 5,692 fingerprints: unmatched shell quoting, read-before-write, long command/plugin enumeration, StructuredOutput schema flexibility, and use-vs-mention guard discrimination. Expand only when a new fixture catches a real regression. This is **very likely (80-90%)** to pay for itself because the starting cases are high-frequency measured failures and the execution result is independent; the remaining uncertainty is how many can be reproduced without the raw Windows runtime.

**the EXTERNAL signal that verifies it:** Process exit status plus exact stdout/stderr/file-state assertions from an isolated run, with a known-positive fixture proving the detector can see a seeded failure and a known-negative fixture proving it stays silent. For semantic cases, a fresh-context model is only one signal and must be paired with a command/file assertion or owner adjudication.

**SOTA citation with URL:** ICLR 2025’s ProactiveBench labeled predicted proactive tasks as accepted/rejected and evaluated them with F1 rather than counting suggestions ([Proactive Agent, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/75c37811e830bf029584b1c6fac17726-Abstract-Conference.html)); Anthropic recommends production-derived tasks and layered evaluation ([agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)); NIST calls for objective, repeatable TEVV, independent review, production-context monitoring, and documented uncertainty ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**value x effort:** transformative x medium  
**novelty:** inferred-surprise  
**autonomy:** just-do-it

## Finding 2 — Proof-carrying thread reconciliation, beyond resurfacing OPEN-THREADS

**improvement:** Periodically reconcile every durable open thread with the external state that can actually close or block it; do not merely remind the next session that the thread exists.

**what it is:** The current open-loop mechanism already resurfaces up to three matching triggers and ledger failures/goals at SessionStart (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:1-15`, `:51-95`). The proposed next step is a background reconciler that attaches a typed closure predicate to each important thread: file exists with hash, test command passes, PR/check reaches a terminal state, scheduled job produces a receipt, or the owner explicitly cancels/defers it. A thread remains open until that external predicate is observed. Age alone never closes it.

**why-inferred:** “Never drop a thread” is a hard owner constraint. Corpus patterns include “why did you stop proceed until you finish everything” and “go again at it since it seems you were stuck” (`corpus.json:10425-10426`, `:10565-10570`), though the corpus warns these candidates require verification (`:10371-10374`). The existing event ledger is expressly designed to retain goals, failures, decisions, and superseding milestones (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/note.py:2-12`), so the least-duplicative extension is to verify closure, not create another backlog.

**how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing open-loop record schema with optional `verify.kind`, `verify.target`, and `verify.expected`, supporting a deliberately small allowlist: `file_hash`, `command_exit`, `git_ref`, `github_check`, `scheduled_receipt`, `owner_disposition`. A daily read-only producer evaluates predicates with bounded timeouts and writes only state transitions to the existing digest: `open→verified`, `open→externally-blocked`, or `verification-regressed`. It may auto-mark `verified` only for deterministic predicates with a known-positive control; it must never infer completion from an assistant message, ledger milestone, age, or its own summary. Owner-only threads remain open until an explicit owner disposition.

Fold this into the existing open-loops/event-ledger code and digest producer lane. Do not add a seventh hook or an `OPEN-THREADS-v2`. This is **very likely (80-90%)** to reduce dropped work because it changes completion from narrative state to external evidence; the evidence is the owner’s repeated persistence language plus the already-built durable thread buses.

**the EXTERNAL signal that verifies it:** The declared verifier itself: git/CI/API state, command exit and output, file hash, scheduled-task receipt, or explicit owner response. The reconciler’s detector must first identify a seeded known-open and known-closed fixture before it can update any real thread.

**SOTA citation with URL:** Microsoft’s validated human-AI guidelines emphasize efficient correction, cautious adaptation, feedback, and notifying users of changes ([CHI 2019 paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)); NIST Manage 4.1 explicitly includes user input, override, recovery, and change management in post-deployment monitoring ([AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**value x effort:** transformative x medium  
**novelty:** inferred-surprise

## Finding 3 — UNVERIFIED: a monthly memory half-life and contradiction clinic

**improvement:** Treat remembered constraints and preferences as time-sensitive claims with provenance and expiry, not permanent personalization facts.

**what it is:** Once a month, a read-only job selects only high-impact memory items whose source is old, contradicted by a later owner statement, or dependent on an external condition that changed. It produces a tiny “still true?” candidate set. It never rewrites basic-memory, instincts, rules, or prompts by itself. The proposal is conditional because the premise “material stale preference claims exist in the live vault” is **UNVERIFIED**; the experiment that settles it is to sample 50 provenance-bearing preference/constraint records, compare each with later owner turns and current referenced files/APIs, and have a fresh-context reviewer label `current / superseded / ambiguous`, followed by owner adjudication of the ambiguous high-impact subset.

**why-inferred:** The owner values personalization but is directly harmed when a fabricated constraint persists. **how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend existing memory records where possible with `source_event`, `observed_at`, `scope`, `supersedes`, and optional `recheck_after`. **improvement:** Run a weekly production-outcome delta that reports only statistically meaningful new or worsening failure classes.

## Finding 7 — One attention-budgeted maintenance digest; urgent interrupts require external harm

**improvement:** Make attention a hard budget: no more than three actionable maintenance deltas at a SessionStart, no “all green” notices, and no urgent interruption without an external signal of imminent harm.

**what it is:** All background producers already have a single queue and a once-only reader. The reader currently defaults to up to 12 surfaced entries (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:59-68`, `:138-158`). Change producer and reader policy so routine items are deduplicated and ranked by expected loss avoided, confidence, freshness, and reversibility. Show the top three; archive or defer the rest. “Urgent” means an externally observed failing recovery test, security revocation, data-loss risk, CI/release blockage tied to an open owner-authorized thread, or a deterministic corruption signal. A speculative model concern never interrupts.

**why-inferred:** Prompt fatigue is explicitly a first-class constraint. Research finds notifications alone can disrupt attention-demanding performance ([Stothart et al., 2015](https://pubmed.ncbi.nlm.nih.gov/26121498/)), and a two-week randomized field trial found evidence that three predictable batches per day improved well-being relative to an endless stream while hourly batching did not ([Fitz et al., 2019](https://www.sciencedirect.com/science/article/abs/pii/S0747563219302596)). A 92-programmer vignette experiment found proactive help reduced competence-based self-esteem and system satisfaction, with the effect stronger among AI-knowledgeable users ([When AI-Based Agents Are Proactive](https://link.springer.com/article/10.1007/s12599-024-00918-y)). This owner is an expert, so “more proactivity” is not automatically better.

**how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Set `BG_DIGEST_MAX=3`; add producer-side stable dedup keys and severity values in the existing dated line format; suppress green/unchanged results; retain the archive and FIFO protection so no thread is dropped. Fold the small metadata/dedup change into the existing reader and producers rather than creating another component. Once per quarter, and only if at least ten maintenance suggestions were surfaced, ask one batched three-choice calibration question about usefulness/noise; otherwise infer nothing. It is **very likely (80-90%)** that this reduces interruption cost because the local reader currently permits 12 items and controlled studies show batching/notification costs; whether three is the owner-optimal cap is settled by explicit quarterly feedback and can be changed as config.

**the EXTERNAL signal that verifies it:** Count of surfaced items, explicit owner accept/dismiss/defer actions, and downstream execution outcome. A lower notification count is not success unless thread closure and owner-rated usefulness remain stable or improve.

**SOTA citation with URL:** Microsoft’s CHI guidelines cover efficient dismissal/correction, cautious adaptation, feedback, and user control ([CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)); the proactive-help study recommends regular feedback and less proactive intervention for competence-central tasks ([BISE study](https://link.springer.com/article/10.1007/s12599-024-00918-y)); notification experiments are cited above.

## Finding 8 — Make-work gate: maintenance is change-triggered or evidence-triggered, never “because Tuesday”

**improvement:** Adopt a written admission rule that prevents scheduled maintenance from becoming autonomous busywork.

**what it is:** A recurring job is admitted only if all five conditions hold: (1) a real external state can drift or decay; (2) a detector has known-positive and known-negative controls; (3) a concrete action follows a failed result; (4) unchanged/green state is silent; and (5) its owner-attention and compute budget are capped. If any condition fails, use an event trigger or remove the job.

This rejects the following as scheduled work:

* periodic `/self-reflect`, prompt optimization, or re-summarization of the same history;
* weekly updating of all skills/MCPs/plugins merely because versions might exist;
* treating “not used recently” as proof a capability is obsolete;
* recurring broad web research without a named decision or source-change trigger;
* routine full harness audits when failure deltas and replay tests are green;
* green reports, health dashboards no one acts on, and owner questions whose answer cannot change the action;
* any loop where the same context proposes, grades, and approves its own change.

**why-inferred:** The corpus enumerates a broad capability portfolio but concentrated actual invocation, with `deep-research` 70, `self-reflect` 18, and many one-off skills (`corpus.json:13265-13344`). ## Trust and autonomy policy

The safe autonomy boundary is asymmetric:

* **Just do:** read-only measurement, isolated-temp replay, isolated restore drills, baseline comparison, archiving raw evidence, silent baseline ratcheting on verified improvement, and writing one proposal to the existing digest.
* **Confirm first:** changing owner preferences/memory, retiring a safety gate, deleting a capability with no live sibling, changing permissions, enabling a new external connector, modifying live configuration, or acting on an ambiguous thread.
* **Never accept as closure:** an assistant’s own completion sentence, a same-context critique, elapsed time, a ledger milestone without external corroboration, or a detector that has not first passed a known-positive control.

This is **very likely (80-90%)** to improve appropriate reliance rather than maximize trust: Lee and See’s model treats trust as dynamic and context-dependent ([PubMed](https://pubmed.ncbi.nlm.nih.gov/15151155/)), while the local defect report shows seven wrong absence/broken conclusions avoided by known-positive controls (`INPUT-known-harness-defects.md:111-129`).
