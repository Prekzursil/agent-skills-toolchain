# X098 — Cross-domain borrow: metrology → agent memory

**Unit:** X098  
**Source field:** metrology (calibration, traceability, measurement uncertainty, reference standards)  
**Target:** what an agent should remember across sessions, when it should forget, and how it should notice staleness  
**Research date:** 2026-07-19  
**Lens constraint:** external research and design only; no local-repository grounding was performed.

## Executive judgment

The useful borrow is **not “calibrate the agent’s memory to truth.”** That analogy fails because most remembered propositions have no SI-like unit, stable measurand, primary standard, repeatable measurement model, or defensible numeric uncertainty. The useful borrow is the surrounding *assurance system*: an immutable provenance chain, explicit conditions and time, separation of calibration/verification/adjustment, risk- and evidence-driven recheck intervals, intermediate checks between full checks, documented decision rules near a limit, and retrospective review when something is found out of tolerance.

**Transfer verdict:** **very likely (80-90%)** that this selective structure transfers usefully to source-backed factual memory. Evidence: the BIPM vocabulary explicitly makes traceability time-bearing, documented, branched for multiple inputs, and uncertainty-carrying, while warning that traceability neither proves fitness for purpose nor absence of mistakes; those constraints have direct structural counterparts in derived, time-varying memory claims ([BIPM VIM 2.41](https://jcgm.bipm.org/vim/en/2.41.html)). This is a design judgment, not an empirical harness result.

**Boundary verdict:** **almost certain (90-99%)** that literal metrological calibration does **not** transfer to preferences, intentions, narrative summaries, ambiguous social facts, and most qualitative judgments. Evidence: VIM calibration is specifically a relation, under specified conditions, between standards' quantity values and instrument indications, with associated measurement uncertainties ([BIPM VIM 2.39](https://jcgm.bipm.org/vim/en/2.39.html)); those required structures do not exist for “the owner likes concise answers” or “this architecture is elegant.”

The resulting design is a small **memory assurance layer**, not a second memory runtime: ordinary records plus provenance metadata, a retrieval-time gate, and a scheduled sampler riding existing hooks/skills. It explicitly rejects a vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, and guardrail framework.

## 1. What metrology actually solved

### 1.1 Metrological traceability is a documented relation, not a pedigree badge

The International Vocabulary of Metrology (VIM) defines metrological traceability as a property of a *measurement result*: the result can be related to a reference through a documented, unbroken chain of calibrations, each contributing to measurement uncertainty. The notes add several crucial constraints:

- a calibration hierarchy is required;
- the reference specification must include the time at which the reference was used;
- when a measurement model has multiple inputs, each input should be traceable, forming a branch or network, with effort proportional to each input's contribution;
- traceability does not ensure uncertainty is fit for the intended purpose and does not ensure absence of mistakes.

Source: [BIPM VIM 2.41, definition and notes 2–5](https://jcgm.bipm.org/vim/en/2.41.html).

This is more rigorous than “save the source URL.” A traceability claim is about a particular result, obtained through a documented transformation chain, under conditions, at a time, and with uncertainty accumulated along the way. A prestigious ancestor does not magically make a descendant correct.

### 1.2 Calibration, verification, validation, and adjustment are different operations

VIM calibration first establishes a relationship between reference values and indications, with uncertainty, and then uses that relationship to obtain a result from an indication. VIM explicitly says not to confuse calibration with adjustment or verification ([BIPM VIM 2.39](https://jcgm.bipm.org/vim/en/2.39.html)). Verification is objective evidence that an item fulfills specified requirements ([BIPM VIM 2.44](https://jcgm.bipm.org/vim/en/2.44.html)). Validation is verification in which the specified requirements are adequate for an intended use ([BIPM VIM 2.45](https://jcgm.bipm.org/vim/en/2.45.html)).

This separation prevents a dangerous bookkeeping collapse:

1. **Characterize** how an instrument behaves against a reference.
2. **Decide** whether that behavior meets a stated requirement.
3. **Decide** whether that requirement is adequate for this use.
4. **Adjust** only through a distinct, controlled operation, then characterize again.

The 2022 ILAC/OIML recalibration guide likewise says adjustment is distinct from calibration and that after adjustment a system usually must be recalibrated ([ILAC-G24/OIML D 10:2022, §3.2–3.3](https://ilac.org/?ddownload=124891)).

### 1.3 Uncertainty belongs to the result and has a budget

VIM defines measurement uncertainty as a non-negative parameter characterizing dispersion of values attributed to a measurand, based on the information used. It includes components from systematic effects and definition; components can be evaluated statistically (Type A) or from experience and other information (Type B) ([BIPM VIM 2.26](https://jcgm.bipm.org/vim/en/2.26.html)). For multiple inputs, combined uncertainty must account not only for individual input uncertainties but also for covariance where inputs are correlated ([ILAC-G24/OIML D 10:2022, §3.7](https://ilac.org/?ddownload=124891)).

The important mechanism is not “attach a confidence score.” It is:

- identify material uncertainty contributors;
- retain their relation to the result;
- avoid treating correlated inputs as independent corroboration;
- state the decision requirement separately from the uncertainty estimate.

### 1.4 Recalibration intervals are managed from risk and history, not a universal TTL

ILAC-G24/OIML D 10:2022 says there is no universally applicable single best practice for recalibration intervals. It calls for documented methods, retained historical results, intermediate checks, and predetermined acceptance limits. Its initial interval factors include required uncertainty, risk of exceeding limits, tendency to drift, severity and extent of use, environmental conditions, comparisons with other standards, and the frequency, quality, and results of intermediate checks ([§4.5–5.2](https://ilac.org/?ddownload=124891)).

After enough history exists, intervals can be adjusted to balance risk and cost. The guide specifically discourages fixed intervals unless normatively specified, because observed drift can justify shorter intervals and demonstrated stability can justify longer ones ([§6.1](https://ilac.org/?ddownload=124891)). It gives several concrete methods:

- **staircase:** lengthen/hold an interval after satisfactory calibration and shorten it after excessive deviation;
- **control chart:** plot significant calibration points over time, estimate dispersion and drift, and calculate an interval;
- **in-use time:** schedule by actual use rather than calendar time when wear follows use;
- **in-service/black-box checks:** frequently check a small set of critical parameters and trigger full calibration only when limits are exceeded.

Sources: [ILAC-G24/OIML D 10:2022, §6.2–6.5](https://ilac.org/?ddownload=124891).

The guide also names the black-box method's failure: unmeasured parameters may fail, and the checker can itself drift, so the checker needs periodic review ([§6.5](https://ilac.org/?ddownload=124891)). This is directly relevant to any memory “canary” or stale detector.

### 1.5 Decision rules include uncertainty and the cost of false acceptance/rejection

ILAC-G8 defines a decision rule as the rule for accounting for measurement uncertainty when declaring conformity. A guard band moves the acceptance limit inward from the tolerance limit to reduce incorrect conformity decisions. It supports non-binary outcomes—pass, conditional pass, conditional fail, fail—and stresses that conformity depends on the declared decision rule ([ILAC-G8:09/2019, §§1.7–1.9 and 4](https://ilac.org/?ddownload=122722)). The same guide distinguishes the risk of false acceptance from false rejection and notes that larger uncertainty raises decision risk ([§3](https://ilac.org/?ddownload=122722)).

This solves a general decision problem: do not turn an uncertain value near a boundary into an unjustified crisp pass/fail.

### 1.6 Discovery of drift implies retrospective consequence analysis

One stated purpose of calibration is to confirm whether equipment changed in a way that creates doubt about results delivered during the elapsed period ([ILAC-G24/OIML D 10:2022, §4.2](https://ilac.org/?ddownload=124891)). The guide warns that extremely long intervals can force withdrawal of many reported results or repetition of substantial work ([§6.2](https://ilac.org/?ddownload=124891)).

Metrology therefore treats an out-of-tolerance finding as more than “fix it now.” It raises: when was the last known-good state, which intervening results relied on it, and which must be reviewed?

## 2. Structural translation to agent memory

The closest defensible mapping is:

| Metrology | Agent memory analogue | Important non-equivalence |
|---|---|---|
| Measurement result | A retrieved factual claim used in a task | A claim is usually semantic, not a numeric quantity |
| Measurand | Precisely scoped proposition being asserted | The proposition can change because the world changes |
| Measurement standard/reference procedure | Authoritative, versioned source or explicit owner statement | Authority is contextual; there is rarely a universal primary standard |
| Calibration chain | Provenance and transformation chain from sources to stored claim | Provenance establishes lineage, not truth |
| Measurement uncertainty budget | Structured reasons the claim may be wrong or inapplicable | Usually cannot be combined into a defensible numeric probability |
| Stability/drift | Rate and pattern with which a claim ceases to remain valid | Change may be abrupt, intentional, or event-driven rather than continuous |
| Recalibration interval | Revalidation deadline or trigger | Calendar age is only one trigger |
| Intermediate check | Cheap source/version/conflict check before full re-research | A narrow check can miss semantic changes |
| Out-of-tolerance review | Quarantine and review outputs that consumed a stale claim | Causality may be hard to establish from mere retrieval logs |
| Guard band | Indeterminate zone requiring refresh or disclosure | There is no natural metric scale for many claims |

## 3. Concrete harness design

### Proposal A — Claim certificate with immutable lineage — UNVERIFIED pending E0/E1

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Persist only a scoped claim, never an unqualified prose blob. Each durable fact record should contain:

```yaml
id: mem_...
claim: "Repository X requires Node >= 22 on branch main."
scope:
  subject: repository-X
  branch: main
  environment: production
kind: external_fact | repo_fact | owner_preference | derived_summary | episode
observed_at: 2026-07-19T00:00:00Z
valid_from: 2026-07-18T14:22:00Z
source:
  locator: "..."
  immutable_locator: "commit/blob/version if available"
  content_digest: "sha256:..."
  authority_basis: "owner statement / official docs / runtime observation / inference"
parents: [mem_source_a, mem_source_b]
transform:
  procedure: "exact extraction | normalization | model synthesis"
  tool_or_model: "..."
uncertainty_factors:
  - "source can change without versioned URL"
  - "claim synthesized from two correlated pages"
refresh:
  mode: event | calendar | use_count | retrieval_gate | never_without_supersession
  due_at: 2026-07-26T00:00:00Z
  triggers: [branch_change, package_manifest_change]
state: current | due | indeterminate | quarantined | superseded
supersedes: mem_...
```

The source snapshot/digest preserves what was actually observed; a live URL alone does not. Derived records name every material parent. The transformation says whether the agent copied, normalized, or synthesized. Scope prevents a true claim from one branch/environment/user being replayed in another. The old record is never silently overwritten; a correction creates a new record linked by `supersedes`.

**Expected effect:** **very likely (80-90%)** to make stale-memory diagnosis and targeted invalidation materially easier, because time, scope, parents, and transformation are explicit—the same structural elements required by metrological traceability. Evidence is the mapping to VIM 2.41; harness effectiveness remains **UNVERIFIED pending Experiment E1 (mutation/replay benchmark)**.

**What it could catch:** a summary whose upstream source changed; a fact remembered from a different branch; two “independent” citations that descend from one parent; a memory with no recoverable observation; a correction that currently looks like an unrelated duplicate. Whether the present harness misses these cases is **UNVERIFIED pending Experiment E0 (two independent detectors: schema scan with a known-present control, plus retrieval-log replay)**.

### Proposal B — Separate check, decision, and mutation — UNVERIFIED pending E2

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Use three explicit phases:

1. **Characterize:** fetch or inspect the reference and compute what changed; do not mutate memory.
2. **Verify/validate:** decide whether the stored claim still meets the requirement for the current task and whether that requirement is adequate for this use.
3. **Adjust:** create a new version, link it to the old one, then re-run verification; never rewrite provenance in place.

A correction hook must not edit a record merely because a new source differs. It should emit a comparison result (`same`, `compatible`, `materially changed`, `scope mismatch`, `reference unavailable`) and let a decision rule choose `use`, `use with caveat`, `refresh`, or `quarantine`.

**Expected effect:** **likely (55-80%)** to prevent self-confirming updates and loss of correction history. Evidence: VIM's separation of calibration, verification, validation, and adjustment; effectiveness in semantic-memory workflows is **UNVERIFIED pending Experiment E2 (seed conflicting but scoped claims and audit mutation histories)**.

### Proposal C — Evidence-adaptive refresh intervals, not one global TTL — UNVERIFIED pending E3

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Assign an initial refresh policy by risk class, then adjust it from observed history:

| Memory class | Initial policy | Lengthen when | Shorten/trigger when | Forget/quarantine rule |
|---|---|---|---|---|
| Owner-declared stable preference | Event-driven; no calendar expiry | Repeated confirmations | Owner correction or context-specific exception | Supersede, do not erase history; do not generalize beyond stated scope |
| Volatile external fact (office-holder, price, API model list, law) | Retrieval-time verification; short calendar backstop | Repeated checks show stability | Source update, conflicting authoritative source, high-impact use | Quarantine if reference unavailable and task requires currency |
| Versioned technical fact | Keyed to exact version/commit | Immutable reference remains addressable | Version/branch/environment changes | Retain for old scope; exclude from new scope |
| Runtime/environment observation | Use-count plus event triggers | Repeated observations under same conditions | Restart, deployment, configuration or dependency change | Expire on environment transition |
| Derived summary | Earliest relevant parent deadline | Parents stable and synthesis rechecked | Any material parent superseded | Quarantine until recomputed |
| Episodic task detail | Session/task boundary by default | Explicit owner request to retain | Task completion or purpose expiry | Delete/compact according to retention policy |
| Secret or sensitive transient | Do not persist by default | Never automatically | Explicit scoped owner authorization only | Forget at boundary; metrological lineage is not a justification to retain secrets |

Use an ILAC-style staircase: if a claim repeatedly verifies unchanged, extend its interval within a class maximum; if it changes, conflicts, or causes a correction, shorten the interval. Combine calendar exposure and *use exposure*: a frequently retrieved claim deserves earlier checking even if young, while an immutable version-pinned claim need not be repeatedly fetched.

Do not infer a quantitative “half-life” until sufficient change-history exists. With sparse observations, store categorical drift evidence (`unknown`, `stable-so-far`, `event-sensitive`, `observed-changing`) and use conservative class defaults.

**Expected effect:** **likely (55-80%)** to reduce stale uses without paying to revalidate every memory on every session. Evidence: ILAC-G24's risk/history factors and adaptive methods. The cost/benefit for this harness is **UNVERIFIED pending Experiment E3 (shadow-mode refresh scheduler measuring stale catches, refresh volume, and latency)**.

### Proposal D — Two-layer staleness detection with calibrated controls — UNVERIFIED pending E4

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Run two mechanically independent signals:

- **Retrieval-time gate:** before a high-impact claim is injected, check its scope, due state, parent states, immutable version, and cheap source fingerprint/metadata.
- **Background stratified sampler:** periodically sample across claim classes, including little-used memories, and perform full semantic revalidation against the reference.

Every detector run includes controls:

- one known-present, deliberately due canary record that the due scanner must find;
- one known-current immutable record that must not be flagged;
- a separately implemented count/reconciliation over the underlying record set.

No report may claim “zero stale records” unless the run detects the due canary and the independent reconciliation agrees on coverage. This imports the ILAC warning that black-box checks can miss unmeasured parameters and can themselves drift.

**Expected effect:** **very likely (80-90%)** to expose detector blindness that a single scheduled scan would misreport as clean. Evidence: ILAC-G24 requires intermediate checks and explicitly describes black-box blind spots. Harness performance is **UNVERIFIED pending Experiment E4 (disable one detector input, mutate an unmeasured field, and verify canary/coverage alarms)**.

### Proposal E — Guard-banded retrieval decision, with an indeterminate state — UNVERIFIED pending E5

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Define the decision rule before retrieval. Do not collapse freshness into `fresh=true/false`.

- **Use:** reference is within policy, scope matches, parents are current, and uncertainty factors are acceptable for the task.
- **Conditional use:** evidence is near the task's acceptance boundary; disclose age/scope and avoid irreversible or high-impact action.
- **Refresh required:** a cheap/current reference is available and the consequence of stale use exceeds refresh cost.
- **Quarantine:** material conflict, parent invalidation, scope mismatch, failed high-impact verification, or inaccessible reference where currency is required.

The “guard band” is not a fake numeric probability. It is a conservative policy zone around risk boundaries. Example: a package-version claim can be used for brainstorming when seven days old but must be refreshed before editing a lockfile; the *same evidence* receives different decisions because validation is use-specific.

**Expected effect:** **likely (55-80%)** to reduce false acceptance of borderline memories while avoiding needless rejection of harmless ones. Evidence: ILAC-G8's non-binary decisions and explicit false-accept/false-reject tradeoff. The chosen categories and thresholds are **UNVERIFIED pending Experiment E5 (task-impact-labelled replay to tune false-use versus unnecessary-refresh rates)**.

### Proposal F — Out-of-tolerance quarantine and blast-radius review — UNVERIFIED pending E6

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

When a stored claim is found materially stale:

1. mark the version `quarantined` and create a corrected successor;
2. identify its last verified-good time and first observed-bad time;
3. follow only stored parent/consumer IDs in the existing append-only memory-use log;
4. mark derived memories as `indeterminate` or `quarantined` according to the decision rule;
5. produce a bounded review list of outputs/actions that actually consumed the record during the uncertainty window;
6. do not automatically undo external actions; request review according to impact.

Keep the consumer pointer minimal: `{timestamp, task/session, memory_id, output_or_action_id, use_role}`. This is not a knowledge graph or observability service. It is a local append-only audit line emitted by the same retrieval hook.

**Expected effect:** **likely (55-80%)** to make correction consequences visible and bound rework after late staleness discovery. Evidence: ILAC-G24 treats elapsed-period results as potentially doubtful and warns that long intervals increase withdrawal/rework. Accurate causal attribution from retrieval is **UNVERIFIED pending Experiment E6 (inject a stale claim into some but not all derived outputs and score blast-radius precision/recall)**.

### Proposal G — Correlation-aware corroboration — UNVERIFIED pending E7

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Do not count two pages, summaries, or agents as independent evidence merely because their URLs or outputs differ. Add `evidence_family` or `ultimate_parent` to each source edge. If two records quote the same press release, database, benchmark run, or owner statement, treat them as one evidence lineage for corroboration. Preserve explicit conflict instead of averaging it away.

**Expected effect:** **likely (55-80%)** to prevent duplicated-source confidence inflation. Evidence: combined measurement uncertainty must account for covariance, and VIM traceability permits branched networks rather than pretending each leaf is independent. The frequency of correlated-source inflation here is **UNVERIFIED pending Experiment E7 (cluster citation lineages in a held-out memory sample and manually adjudicate independence)**.

## 4. What this would catch that a flat memory store cannot represent

These are capability targets, not claims about the present harness:

1. **Correct fact, wrong scope:** a branch-, environment-, version-, jurisdiction-, or user-specific fact retrieved globally.
2. **Source changed in place:** the URL remains identical while its content digest or semantic claim changes.
3. **Derived-memory rot:** a synthesis remains textually unchanged after one parent is corrected.
4. **Citation laundering:** multiple apparent sources share one ultimate parent.
5. **Silent detector failure:** a scan reports no due records because it did not traverse the store; the due canary exposes it.
6. **Checker drift/blindness:** metadata stays stable while content changes, or the background sampler omits a claim class.
7. **Abrupt event invalidation:** deployment, branch switch, election, owner correction, or dependency update invalidates memories earlier than a TTL.
8. **Over-refresh:** immutable commit-pinned facts are repeatedly fetched despite unchanged scope.
9. **Borderline high-impact use:** a claim acceptable for ideation is incorrectly reused for a purchase, legal conclusion, production mutation, or external message.
10. **Unknown blast radius:** a correction updates the stored fact but leaves downstream summaries and decisions appearing current.

Whether the current harness fails any specific item is **UNVERIFIED pending Experiment E0 (validated schema inventory plus independent retrieval replay)**. This unit intentionally did not inspect the local subject tree.

## 5. Adversarial analysis: where the analogy breaks

### 5.1 No universal reference hierarchy

SI traceability ultimately relates compatible quantities to agreed references. Memory claims may have multiple legitimate authorities: current owner intent supersedes an older owner statement; deployed runtime may contradict documentation; jurisdictions differ; subjective preferences are authoritative only when scoped to the person and situation. “Official” does not automatically mean current, applicable, or true.

**Consequence:** provenance rank must never be treated as a truth score. Reference selection is part of the claim and task, and conflicts remain explicit.

### 5.2 The measurand may be ill-defined or altered by observation

A physical measurand is defined under stated conditions. Natural-language claims often conflate several propositions, omit time, or change meaning across contexts. An agent asking the owner can itself cause a preference or plan to be reformulated.

**Consequence:** only atomic, scoped propositions receive factual revalidation. Narratives and preferences use supersession and confirmation, not pseudo-calibration.

### 5.3 Drift is not necessarily gradual or stochastic

Instrument drift often supports trend estimation. Software releases, policy changes, deployments, elections, and owner decisions can invalidate a claim instantaneously. Conversely, an immutable commit fact does not drift at all within its scope.

**Consequence:** calendar/control-chart logic is secondary to event triggers and version identity. An inferred half-life is never sufficient for high-impact current-fact use.

### 5.4 Numeric uncertainty would usually be counterfeit precision

Metrological uncertainty is attached to quantity values and supported by a measurement model. A language model saying “0.82 confidence that this preference still holds” usually lacks calibration data, a well-defined event, and a stable reference class.

**Consequence:** retain named uncertainty contributors and the mandatory qualitative confidence bands; do not combine them arithmetically unless a held-out calibration experiment establishes meaning.

### 5.5 Traceability does not imply correctness

The VIM itself warns that traceability does not ensure adequate uncertainty or freedom from mistakes ([BIPM VIM 2.41 note 5](https://jcgm.bipm.org/vim/en/2.41.html)). A perfectly documented chain can carry a misquotation, invalid inference, biased authority, or wrong scope.

**Consequence:** the interface must say “source-backed and within policy,” never “true because traceable.” Independent validation remains necessary for consequential tasks.

### 5.6 The checking process can become the new stale memory

A list of “critical facts,” source-authority rankings, refresh defaults, and detector canaries can all become stale. ILAC's black-box warning applies recursively: a narrow checker can miss other parameters and itself needs review.

**Consequence:** version policies, test the detector with positive and negative controls, reconcile coverage independently, and periodically sample outside the “critical” set.

### 5.7 Forgetting has privacy and relevance goals absent from calibration

Metrology aims to preserve records sufficient for traceability. Agent memory must also minimize sensitive retention, honor owner deletion/correction, and avoid irrelevant personalization. More lineage is not always better.

**Consequence:** sensitivity and purpose limitation override provenance retention. Where deletion is required, retain at most a non-sensitive tombstone needed to prevent resurrection, if authorized.

### 5.8 Retrieval logs show use, not causation

A record being retrieved before an output does not prove that it materially affected the output. Conversely, an unlogged parametric memory could influence generation.

**Consequence:** blast-radius review is a prioritization aid, not an automatic rollback oracle. Store `use_role` when the agent explicitly relies on a fact; label causal attribution as indeterminate otherwise.

## 6. Anti-overfit gate

This design passes the stated gate:

- It rides the existing memory retrieval, hook, skill, and MCP buses.
- It adds metadata and small deterministic checks, not another orchestration runtime.
- It uses ordinary JSON/YAML/JSONL records and indexes already available to the harness; it does not require a vector database or knowledge graph.
- It does not require durable execution, a trained critic, observability SaaS, or a guardrail framework.
- Every automated decision remains inspectable and reversible through immutable versions and explicit states.

**Complexity judgment:** **very likely (80-90%)** that Proposals A–G can be implemented as several independently useful sub-200-line adapters/config changes rather than a new service. Evidence: each operation is record validation, small state transition, source fingerprinting, or append-only logging. Exact fit to the existing bus is **UNVERIFIED pending Experiment E0b (enumerate actual hook payloads and prototype one no-write shadow adapter)**.

Do not implement a universal “memory metrology platform.” Start with the certificate schema and retrieval gate; add adaptive intervals only after collecting history. This sequencing limits scaffolding that model improvements may obsolete.

## 7. Required experiments and decision gates

### E0 — Establish the current baseline without detector self-deception

Use two mechanically independent signals:

1. schema/static inventory of persistent memory records, first proving the detector finds a planted or known-present provenance field;
2. replay of retrieval events, first proving the replay finds a known retrieval.

Measure whether scope, source time, digest/version, parents, last verification, and use consumers are available. Do not conclude a field or behavior is absent from one failed query.

### E1 — Mutation/replay benchmark for trace certificates

Construct held-out cases with: source changed in place, version change, branch mismatch, owner supersession, one changed parent, correlated sources, inaccessible source, and irrelevant textual edit. Compare flat memory against Proposal A on stale-use detection and false alarms.

**Advance criterion:** **likely (55-80%)** that a certificate schema is worthwhile if it reduces material stale uses by at least 30% without increasing retrieval latency p95 by more than 100 ms when no network refresh is due. Evidence for these thresholds is pragmatic, not empirical; they are **UNVERIFIED and should be settled by E1**.

### E2 — Mutation-history integrity

Seed conflicting records where one is a scoped exception and one is a genuine correction. Verify that characterize → decide → adjust retains the comparison, never rewrites the old observation, and does not erase a valid scoped exception.

### E3 — Shadow adaptive scheduler

For several weeks, make recommendations without blocking retrieval. Record proposed recheck, actual changes, costs, high-impact uses, and owner corrections. Compare global TTL, fixed class TTL, and staircase/event policy.

**Expected result:** **roughly even (45-55%)** that staircase adaptation beats well-chosen fixed class defaults during the initial sparse-data period. Evidence: ILAC recommends history-based review but also notes methods differ by equipment; agent-memory drift may be abrupt and data sparse. This is deliberately not promoted to default until E3 settles it.

### E4 — Detector fault injection

Disable a record enumerator, corrupt a due-date parser, mutate content without metadata, and omit one claim class from sampling. Require the known-due canary, known-current control, reconciliation count, and second detection path to distinguish “clean” from “detector blind.”

### E5 — Decision-rule replay

Label past or synthetic retrievals by task consequence. Compare binary freshness, four-state guard-banded decisions, and always-refresh. Measure material stale use (false acceptance), unnecessary refresh/quarantine (false rejection), latency, and disclosure burden.

### E6 — Blast-radius precision/recall

Inject one stale parent into a controlled subset of summaries/actions. Evaluate whether consumer pointers find affected outputs without flagging outputs that merely shared a session. No automatic rollback is allowed during the experiment.

### E7 — Evidence correlation audit

Sample apparently multi-source memories. Manually trace ultimate origins and measure how often nominal corroboration is derived from the same primary document, dataset, benchmark execution, or owner statement.

## 8. Recommended build order — UNVERIFIED pending E0–E5

1. **Proposal A: claim certificate**, initially shadow-only and only for new high-impact factual memories.
2. **Proposal B: immutable correction path** so new validation evidence cannot destroy old provenance.
3. **Proposal E: explicit retrieval decision rule** with `indeterminate` and `quarantined` states.
4. **Proposal D: retrieval gate plus independently reconciled sampler and controls.**
5. **Proposal F: minimal consumer pointers and bounded blast-radius review.**
6. **Proposal G: correlated-source families.**
7. **Proposal C: adaptive intervals only after enough verification history exists.**

**Overall recommendation:** **very likely (80-90%)** that A+B+E+D form the highest-value minimal slice because they add traceability, controlled correction, non-binary decisions, and detector validation without requiring learned models or a new runtime. Evidence: these are direct translations of BIPM/ILAC mechanisms and do not depend on estimating a drift distribution. Harness-specific value remains **UNVERIFIED pending E0–E5**, so the recommendation is shadow-mode first, not immediate enforcement.

## 9. Rejected borrows

### Rejected: a single numeric “memory uncertainty” score

It would conflate source authority, age, scope fit, transformation error, and conflict without a defensible measurement model. The BIPM concept depends on a defined measurand and information model; most semantic memory lacks both.

### Rejected: one universal memory half-life

ILAC explicitly rejects one universally best recalibration method and discourages fixed intervals absent normative specification. Agent facts range from immutable commit-bound propositions to abruptly changing prices and intentions.

### Rejected: provenance depth as truth

A long chain can accumulate transformation error and correlated evidence. VIM explicitly says traceability does not guarantee adequate uncertainty or absence of mistakes.

### Rejected: a memory knowledge graph or calibration daemon

Consumer and parent IDs can be ordinary fields in existing records and JSONL events. A new service would violate the anti-overfit gate without evidence that simple hooks fail.

### Rejected: automatic rollback of actions after a stale finding

Retrieval correlation is not causation, and rollback can be destructive. The appropriate translation is quarantine plus bounded human/agent review.

## 10. Gaps and limits

- This unit did not inspect any local harness, corpus, audit finding, subject tree, or existing memory implementation, as required by the ideation-lens instruction. All “current harness” status is therefore **UNVERIFIED pending E0**.
- The external sources establish metrology practice, not effectiveness for LLM memory. Transfer-effect claims are design hypotheses carrying confidence bands and named experiments above.
- ISO/IEC 17025 full text was not used because it is not openly reproduced by ISO. ILAC's official guidance quotes and operationalizes the relevant concepts; conclusions here cite ILAC and BIPM primary publications directly.
- No empirical estimate exists here for semantic-memory change rates, detector false-positive rates, refresh costs, or the causal benefit of consumer logging. E1–E7 are the settling experiments.
- The BIPM VIM pages consulted are the online VIM3 entries. Terminology can evolve; implementations should pin the referenced entry/version rather than assume the live URL is immutable—the very failure mode this design addresses.
