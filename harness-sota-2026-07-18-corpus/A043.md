# A043 — Coherence audit of `~/.claude/rules/kotlin/patterns.md`

## Scope and verdict

This unit audited the unpacked, read-only Linux bundle at `/local_disk0/codexwork/bundle`. The subject file is `/local_disk0/codexwork/bundle/claude/rules/kotlin/patterns.md`; its complete content is 146 lines. The requested Windows paths are not present on this job node, so all path:line citations below refer to the corresponding unpacked bundle paths.

The rule is not coherent enough to retain unchanged. I found eight reportable collisions: two contradictions, two divergent redundancies, two unenforced contracts, one unruled Kotlin enforcement, and one stale/false inheritance claim. The strongest defects are:

1. the Kotlin builder example endorses mutation while the loaded common rule says `NEVER` mutate;
2. the file claims to extend `common/patterns.md` for `.kts`, but that common rule does not load for `.kts`;
3. the Kotlin hook rule promises formatter, Detekt, and Gradle validation, while the live settings contain no Kotlin validation command and the wired per-edit validator silently skips `.kt` and `.kts`;
4. the target makes a repository-wide dependency choice (`Koin` or `Hilt`) for every Kotlin file, without the project/dependency guard required elsewhere in the rules.

The measured corpus cannot determine whether these Kotlin architectural rules were followed. That is **UNVERIFIED; the settling experiment is to scan the 11,633 raw JSONL transcripts for successful `Edit`/`Write` calls whose `file_path` ends in `.kt`/`.kts`, resolve the resulting repository revisions, and classify the edited code against each rule before and after the rule's installation date**. The corpus is a behavior distillation, not a source-code snapshot: its top-level sections have no language or edited-file-path field, while `_meta` expressly describes capped samples (`inputs/corpus.json:2-11`) and `sessions` retains only filenames/times/sizes (`inputs/corpus.json:13868-13880`).

### Applicable precedence

`claude/AGENTS.md` §10 orders user/permissions, safety, the cross-tool contract, project governance, then third-party skills/plugins (`claude/AGENTS.md:115-131`). It does **not** place global rule files relative to one another. ## Collision register

### A043-C01 — false `.kts` inheritance

**Class: STALE**

**Artifacts and exact lines**

* `claude/rules/kotlin/patterns.md:2-4` scopes the Kotlin rule to both `**/*.kt` and `**/*.kts`.
* `claude/rules/kotlin/patterns.md:8` says: `This file extends common/patterns.md`.
* `claude/rules/common/patterns.md:2-19` scopes the common file to many extensions, but includes only `**/*.kt` at line 18 and no `**/*.kts`.

For a `.kts` file, the specific rule loads but the rule it claims to extend does not. This is a stale structural claim, not merely wording: the common skeleton/repository/API-response instructions at `common/patterns.md:23-51` are absent from the `.kts` instruction set.

**Precedence:** neither AGENTS §10 nor the language-specific-over-common rule resolves a rule that never loads. There is no competing instruction to rank for `.kts`.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule bus):** add `**/*.kts` to `common/patterns.md` or narrow the target's line 8 to say that common patterns apply only when their own path selector loads. Adding `.kts` is **very likely (80-90%)** to restore the intended inheritance, because path frontmatter is the only observed scope gate; evidence is the mismatched selectors at the cited lines. **UNVERIFIED: the settling experiment is a Claude Code instruction-load diagnostic in a throwaway repo with one `.kt` and one `.kts`, asserting both files report the common and Kotlin rule IDs.**

Anti-overfit gate: this is a two-line change on the native rules bus; it adds no runtime or rejected component.

### A043-C02 — mutable Kotlin DSL versus universal no-mutation rule

**Class: CONTRADICTION**

**Artifacts and exact lines**

* `claude/rules/common/coding-style.md:23-33` labels immutability `CRITICAL` and says `ALWAYS create new objects, NEVER mutate existing ones`.
* `claude/rules/kotlin/patterns.md:117-139` endorses a builder whose `baseUrl` and `timeout` are mutable `var`s (lines 121-122), whose `interceptor` mutates a `MutableList` via `add` (lines 123-127), and whose usage assigns both properties (lines 136-139).
* The nearby Kotlin style rule only says to prefer `val` and allow `var` where mutation is required (`claude/rules/kotlin/coding-style.md:15-19`), which confirms that Kotlin's intended policy is scoped mutation, not the common rule's literal prohibition.

The code is idiomatic as a localized construction DSL, but it directly violates the literal common instruction. This is primarily a badly written common rule: “never mutate” is too absolute to coexist with builders, mutable state holders, collection assembly, or controlled implementation-local mutation.

**Precedence:** `rules/README.md:93-104` resolves execution in favor of the Kotlin-specific pattern. AGENTS §10 does not mention rule specificity, so it does not independently resolve this pair. The contradiction remains a documentation/coherence defect even though the rules README supplies a winner.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule bus):** rewrite `common/coding-style.md:25` as a public-boundary/default rule (“prefer immutable values and do not mutate caller-owned objects; permit encapsulated mutation during construction or where the language-specific rule explains it”), and add one sentence before the Kotlin builder saying mutation is confined to the unshared configuration object. This is **almost certain (90-99%)** to remove the textual contradiction because it changes the universal quantifier and documents the exact exception; evidence is the literal `NEVER` at common line 25 and literal assignments/add at target lines 121-139.

Anti-overfit gate: documentation-only refinement on the existing rule bus; no new component.

### A043-C03 — two repository contracts with different operation surfaces

**Class: REDUNDANCY**

**Artifacts and exact lines**

* `claude/rules/common/patterns.md:35-43` defines the repository pattern and instructs repositories to expose `findAll`, `findById`, `create`, `update`, and `delete` (line 40).
* `claude/rules/kotlin/patterns.md:52-63` defines the repository pattern again, but its endorsed interface exposes only `getById`, `getAll`, and `observeAll` (lines 59-63), with no create/update/delete contract.

The second statement is not a clean Kotlin translation of the first. It silently narrows the operation surface and adds reactive/local-remote policy. Because the Kotlin example need not be exhaustive, this is divergent redundancy rather than a proven prohibition of CRUD. An agent following examples literally receives two different repository templates.

**Precedence:** language-specific-over-common (`rules/README.md:93-104`) favors the Kotlin version for `.kt`; AGENTS §10 does not rank these rule files. For `.kts`, C01 means only the Kotlin version loads.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule bus):** make common patterns the single definition and make Kotlin patterns a language mapping: “Expose only domain-required operations; use `suspend` for one-shot I/O and `Flow` for observation.” Remove the fixed universal CRUD list or label it illustrative. This is **very likely (80-90%)** to reduce divergent templates because only one artifact would own the operation-surface policy; evidence is the two explicit, different method lists.

Anti-overfit gate: consolidation removes instruction mass and adds no runtime.

### A043-C04 — duplicated Kotlin error-return policy

**Class: REDUNDANCY**

**Artifacts and exact lines**

**Precedence:** both are language-specific Kotlin rules at the same layer. AGENTS §10 says same-level genuine conflicts must be surfaced (`claude/AGENTS.md:129-131`) but supplies no preference; today the statements are compatible.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule bus):** keep error semantics in `kotlin/coding-style.md` and replace `patterns.md:54` with a pointer plus only repository-specific shape (`suspend` for one-shot work, `Flow` for observation). This is **almost certain (90-99%)** to eliminate duplicate ownership because one of the two normative statements would be removed; evidence is the cited duplication.

Anti-overfit gate: subtraction on the rules bus.

### A043-C05 — unconditional DI framework choice versus project-fit governance

**Class: CONTRADICTION**

**Artifacts and exact lines**

* `claude/rules/kotlin/patterns.md:10-26` says `Use Koin (KMP) or Hilt (Android-only)` after preferring constructor injection. Its path selector covers every `.kt` and `.kts`, not just Android/KMP (`patterns.md:2-4`).
* `claude/rules/README.md:59-67` says language rules must be configured according to actual project requirements and are reference configuration.
* `claude/rules/common/development-workflow.md:29-35` makes research/reuse mandatory and requires checking existing implementations, documentation, registries, and adaptable approaches before choosing an implementation.

The target pre-chooses two frameworks before project type, current dependency graph, dependency budget, or an existing DI mechanism is considered. It also has no branch for Kotlin/JVM server or desktop code. This is a rule-design defect: the constructor-injection principle is portable, while framework selection is contextual.

**Precedence:** the rules README makes Kotlin specific over common, but that only makes the unconditional framework choice win over the common workflow; it does not reconcile the README's own “actual project requirements” instruction. AGENTS §10 does not locate global rule files in its hierarchy and therefore does not resolve this collision.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule bus):** retain “prefer constructor injection”; replace the framework mandate with a decision table: preserve the project's existing DI approach; for a new Android-only app evaluate Hilt; for KMP evaluate Koin or manual DI; for Kotlin/JVM/desktop follow project constraints; do not add a framework solely to satisfy this rule. This is **very likely (80-90%)** to prevent needless dependency churn because it makes the project-fit rule and the DI rule jointly satisfiable; evidence is the current unconditional wording and universal file scope. **UNVERIFIED: the settling experiment is to replay a stratified set of Android, KMP, and Kotlin/JVM implementation prompts against old and revised rules and compare unnecessary dependency additions while holding task/repo constant.**

Anti-overfit gate: the resolution reduces forced scaffolding and remains a rule-only change. It explicitly favors manual DI when sufficient, consistent with the anti-overfit gate.
