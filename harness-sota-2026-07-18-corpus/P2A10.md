# P2A10 — MCP ecosystem: gateways, aggregators, lazy connection, tool filtering, and security

**Unit:** P2A10  
**Research date:** 2026-07-18  
**Lens:** external research only; no inspection of the owner's local harness, subject repositories, or prior audit claims  
**Question:** What in the current MCP ecosystem is actually worth adopting?

## Executive conclusion

The highest-value MCP improvements no longer require a new gateway. Claude Code now natively defers MCP tool schemas, discovers tools on demand, connects ordinary servers in the background, supports dynamic `list_changed` updates, and retries transient remote failures. It also exposes server allow/deny controls and per-tool allow/ask/deny permission rules. These are mature-enough, low-complexity controls riding the existing client and configuration bus, so they should be the first adoption layer ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [Claude Code permissions](https://code.claude.com/docs/en/permissions), [managed MCP controls](https://code.claude.com/docs/en/managed-mcp)).

Gateways are real and useful, but their value is conditional. Docker MCP Gateway, ToolHive, IBM ContextForge, Microsoft MCP Gateway, MetaMCP, and GitHub's workflow-specific gateway all implement some combination of aggregation, container isolation, authentication, filtering, namespacing, tracing, and lifecycle management ([Docker MCP Gateway](https://github.com/docker/mcp-gateway), [ToolHive](https://github.com/stacklok/toolhive), [ContextForge](https://github.com/IBM/mcp-context-forge), [Microsoft MCP Gateway](https://github.com/microsoft/mcp-gateway), [MetaMCP](https://github.com/metatool-ai/metamcp), [GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/)). What is not established is that putting a general gateway into a single-owner coding harness improves end-to-end completion rate or reliability. It introduces another process, protocol translator, credential boundary, cache, and failure domain. A gateway is therefore an optimization for a demonstrated multi-client governance or isolation need, not a default prerequisite.

Security is not supplied by MCP itself or by registry presence. The official MCP trust model says clients trust connected servers and local servers are trusted like any installed program; the official registry authenticates publisher namespaces and hosts metadata but delegates code security scanning, and its moderation policy explicitly does not remove servers merely for security vulnerabilities ([MCP security policy](https://github.com/modelcontextprotocol/modelcontextprotocol/security), [registry trust and security](https://modelcontextprotocol.io/registry/about), [registry moderation policy](https://modelcontextprotocol.io/registry/moderation-policy)). The practical security baseline is deterministic: minimize the enabled server/tool set, separate read from write authority, use native approvals, use scoped OAuth rather than token passthrough, contain local processes, bound time/output/calls, and detect tool-schema drift.

My recommendation is therefore **native client controls + a small deterministic preflight/drift layer**, not a general-purpose MCP control plane. A gateway pilot becomes justified only if direct connections fail a measured reliability threshold, several hosts truly need one canonical endpoint, or untrusted local servers require container isolation that cannot be supplied more simply.

## Method and evidence discipline

I split the question into five subproblems: protocol primitives; client-side lazy discovery/filtering; gateway/aggregator implementations; registry and authorization trust; and empirical security evidence. I searched official specifications and documentation, first-party repositories and issue trackers, standards/security guidance, and recent papers. Product existence and documented behavior count as established only for the documented implementation; vendor benchmarks do not become ecosystem-wide facts. Recent papers are treated as evidence of reproduced attacks or experimental results, not proof that every current client remains vulnerable.

The principal source set is the MCP 2025-11-25 specification, MCP security guidance and registry documentation, current Claude Code/GitHub/OpenAI documentation, gateway repositories maintained by their publishers, OWASP guidance, and recent research papers. Search snippets were not used as the sole basis for the central recommendations when a full official page or repository was available.

## 1. What is actually established

### 1.1 MCP already has the discovery primitives an aggregator needs

The protocol defines initialization, version negotiation, and capability negotiation before normal operation. A server declares whether it supports tools and whether its tool list can change; clients enumerate tools with paginated `tools/list`, and a capable server can emit `notifications/tools/list_changed` so the client refreshes the catalog ([MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). This establishes dynamic discovery, not semantic routing, lazy process startup, or authorization policy. Those remain client, server, or gateway concerns.

The protocol explicitly makes tools model-controlled but does not mandate a user-interface pattern. It recommends that applications show exposed tools, visually indicate invocations, and let a human deny calls; it also says clients must treat annotations as untrusted unless they come from trusted servers ([MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Therefore `readOnlyHint`, `destructiveHint`, and similar metadata can help route approval policy, but they cannot safely be the sole authority for it.

### 1.2 Lazy schema loading is now a native client feature, not a gateway requirement

Claude Code's current documentation says MCP tool search is enabled by default: only tool names load initially, full schemas are deferred, and relevant tools are discovered on demand. It supports an `auto:N` threshold, individual or server-wide always-load exceptions, background MCP connection, dynamic tool updates, and bounded reconnection for HTTP/SSE servers ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [Agent SDK tool search](https://code.claude.com/docs/en/agent-sdk/tool-search)). GitHub Copilot CLI independently documents default tool search on supported models and a `deferTools` setting for per-server exceptions ([GitHub Copilot CLI tool search](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/tool-search)). These are two mechanically independent implementations of the same architectural pattern.

Anthropic's published internal evaluation reported that its Tool Search Tool reduced a representative tool-definition load by 85%, improved Opus 4 tool-use accuracy from 49% to 74%, and improved Opus 4.5 from 79.5% to 88.1% on its MCP evaluations. Anthropic also identifies the trade-off: a first-use search round trip, with little benefit for small catalogs under roughly ten tools ([Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). The numbers are vendor-run, not independently replicated, but the feature's existence and mechanism are independently corroborated by Claude Code and GitHub's product documentation.

“Lazy connection” needs precise language. Claude Code documents non-blocking background connection for ordinary MCP servers and waiting only when a requested server is still connecting; `alwaysLoad` intentionally blocks startup up to the connect timeout because those tools must be in the first prompt ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp)). This is lazy/background **connection handling** plus lazy **schema disclosure**. It is not evidence that every server process is spawned only on first tool use, nor that idle remote sessions consume zero resources.

### 1.3 Tool filtering has three distinct layers

First, **availability filtering** decides whether a server or tool is exposed to the model. Claude Code supports managed server allowlists/denylists and exclusive `managed-mcp.json`; its Agent SDK also distinguishes the set of available tools from permission approval ([managed MCP controls](https://code.claude.com/docs/en/managed-mcp), [custom tools and availability](https://code.claude.com/docs/en/agent-sdk/custom-tools)). GitHub's gateway configuration supports a per-server `tools` allowlist, and OpenAI's remote MCP API accepts `allowed_tools` as names or a read-only filter ([GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/), [OpenAI API MCP tool reference](https://platform.openai.com/docs/api-reference/evals/deleteRun)).

Second, **invocation authorization** decides whether a visible tool call is allowed, denied, or requires approval. Claude Code permission rules match an MCP server or exact MCP tool and use deny-before-ask-before-allow precedence; OpenAI's remote MCP tool has a separate `require_approval` policy whose documented default is `always` ([Claude Code permissions](https://code.claude.com/docs/en/permissions), [OpenAI API MCP tool reference](https://platform.openai.com/docs/api-reference/evals/deleteRun)).

Third, **context optimization** decides which authorized schemas are loaded for a particular turn. Tool search belongs here. It reduces context pressure but is not an authorization boundary: a deferred tool may still be found and called if it is available and permitted ([Claude Code Agent SDK tool search](https://code.claude.com/docs/en/agent-sdk/tool-search)). Conflating these layers is dangerous because hiding a schema temporarily is not the same as denying execution.

### 1.4 Gateways and aggregators are implemented, but they are not interchangeable

Docker MCP Gateway provides one interface over multiple servers, containerizes catalog servers, manages secrets and OAuth, discovers tools dynamically, and includes logging/tracing ([Docker MCP Gateway repository](https://github.com/docker/mcp-gateway)). ToolHive combines an MCP runtime, gateway, registry, and Kubernetes operator; it documents container isolation, identity/policy enforcement, tool filtering, OIDC/OAuth, OpenTelemetry, and semantic tool search ([ToolHive repository](https://github.com/stacklok/toolhive)). IBM ContextForge federates MCP, A2A, REST, and gRPC services and documents authentication, rate limiting, virtual servers, filtering plugins, and encrypted per-user token storage ([ContextForge repository](https://github.com/IBM/mcp-context-forge), [ContextForge security features](https://ibm.github.io/mcp-context-forge/latest/architecture/security-features/)).

MetaMCP aggregates selected servers into namespaces/endpoints and can enable or disable tools and override their names/descriptions/annotations; its own roadmap still labels search-based selection, broader middleware, and tool-selection evaluation as future work ([MetaMCP repository](https://github.com/metatool-ai/metamcp)). Microsoft MCP Gateway is a Kubernetes-oriented reverse proxy and management layer with session-aware routing and explicit warnings that its built-in shell denylist is defense-in-depth, not a sandbox ([Microsoft MCP Gateway repository](https://github.com/microsoft/mcp-gateway)). GitHub's agentic-workflow gateway is narrower and unusually concrete: container-only stdio servers, per-server tool filters, timeouts, OIDC, call limits, integrity filtering, and explicit failure propagation ([GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/), [GitHub tool restrictions](https://github.github.com/gh-aw/reference/github-tools/)).

Aggregation creates naming and state duties that direct one-client/one-server links avoid. MetaMCP uses namespaces, ContextForge has an implemented namespaced federation design, and an active IETF Internet-Draft proposes hierarchical namespace delegation for MCP aggregators ([MetaMCP repository](https://github.com/metatool-ai/metamcp), [ContextForge namespaced federation ADR](https://ibm.github.io/mcp-context-forge/latest/architecture/adr/011-tool-federation/), [MCP-AX Internet-Draft](https://datatracker.ietf.org/doc/draft-abbott-mcp-ax/)). The existence of multiple naming schemes and a still-draft aggregation protocol establishes that cross-server naming is an active interoperability problem, not a settled protocol feature.

### 1.5 Authorization is substantially more mature than the early MCP ecosystem, but optional

The current MCP HTTP authorization specification is based on OAuth 2.1, Protected Resource Metadata, authorization-server metadata or OIDC discovery, and Client ID Metadata Documents; authorization remains optional, and stdio implementations are told to obtain credentials from the environment rather than use the HTTP flow ([MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). The security guide explicitly forbids token passthrough, requires tokens intended for the MCP server, describes confused-deputy defenses, mandates per-client consent in the vulnerable proxy pattern, and recommends progressive least-privilege scopes ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)).

The same official guide identifies SSRF during OAuth metadata discovery, session hijacking, authorization-URL injection, and privilege escalation through stdio proxy architectures; it recommends HTTPS, private-address blocking, redirect validation, non-shell URL opening, per-request authorization, secure session identifiers, and sandboxing/restriction of spawned processes ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). Cloudflare's current MCP client independently implements URL checks that block private, link-local, cloud-metadata, and IPv4-mapped private targets, illustrating that these mitigations can be implemented concretely rather than left as prose ([Cloudflare MCP client API](https://developers.cloudflare.com/agents/model-context-protocol/apis/client-api/)).

### 1.6 Registry identity is not code trust

The official registry verifies the publisher namespace and package-to-metadata linkage; it supports package types with different ownership checks and supports an artifact hash for MCPB installation ([registry authentication](https://modelcontextprotocol.io/registry/authentication), [registry package types](https://modelcontextprotocol.io/registry/package-types)). However, the registry says it focuses on namespace authentication and metadata hosting, delegates security scanning to package registries and downstream aggregators, and is still preview ([registry about page](https://modelcontextprotocol.io/registry/about), [registry FAQ](https://modelcontextprotocol.io/registry/faq)). Its moderation policy explicitly says low-quality, buggy, and security-vulnerable servers generally are not removed ([registry moderation policy](https://modelcontextprotocol.io/registry/moderation-policy)). Registry presence therefore proves a naming/publication relationship, not safe behavior.

### 1.7 Tool poisoning and cross-server risk are credible, not hypothetical

OWASP's MCP Security Cheat Sheet identifies tool poisoning, rug pulls, tool shadowing, confused-deputy behavior, excessive permissions, supply-chain attacks, and sandbox escape as key risks. It recommends least privilege, schema inspection and hashing, sandboxing, explicit confirmation for sensitive actions, input/output validation, per-server credentials, and cross-server isolation ([OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)). OWASP guidance is a consensus practice document, not an empirical incidence measurement.

A 2026 study threat-modeled MCP and experimentally compared seven clients against tool-poisoning attacks; it reported significant weaknesses in most tested clients, especially static validation and parameter visibility ([Huang et al., 2026](https://arxiv.org/abs/2603.22489), [journal version](https://www.mdpi.com/2624-800X/6/3/84)). The experiment is a second, mechanically independent signal that the OWASP-described class can manifest in real clients. It does not establish the vulnerability status of versions released after the November 2025 test window.

The MCP project's own security policy is unusually explicit that the protocol assumes connected servers are trusted, local servers are equivalent to installed software, and users/operators are responsible for selection and configuration ([MCP security policy](https://github.com/modelcontextprotocol/modelcontextprotocol/security)). That trust model explains why client-side allowlisting, process containment, and change detection remain necessary even with valid protocol conformance.

## 2. What is promising but unproven

### 2.1 Native deferred tool search is promising beyond its current vendor evidence

It is **very likely (80-90%)** that native deferred MCP tool search improves this owner's large-tool harness on context use and tool selection, because Claude Code and GitHub have shipped the mechanism, Anthropic measured large token and accuracy gains, and both vendors describe a small-catalog crossover where eager loading remains faster ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [GitHub Copilot CLI tool search](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/tool-search), [Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). The exact benefit on this owner's workload is **UNVERIFIED — settle it with an A/B replay of at least 100 representative tasks using eager loading versus default deferral, measuring task success, first-tool latency, wrong-tool calls, prompt tokens, and total wall time**.

Semantic retrieval is **likely (55-80%)** to beat regex search only when names/descriptions are weak or the catalog is very large; evidence is the shipped BM25/regex support and Anthropic's accuracy results, while ToolHive's “up to 85%” token-saving claim is vendor marketing without a public independent benchmark in the sources reviewed ([Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), [ToolHive repository](https://github.com/stacklok/toolhive)). ToolHive's optimizer advantage over the already-native Claude tool search is **UNVERIFIED — settle it with the same catalog and task set against native search, comparing recall@5, successful invocation, latency, and tokens**.

### 2.2 Schema hashing and approval-on-change are low-complexity, high-upside

It is **very likely (80-90%)** that canonical hashing of `tools/list` output catches accidental or malicious schema drift cheaply, because OWASP recommends it, an open MCP SEP proposes digest-pinned tool versioning, and registry versions are immutable metadata records even though runtime tool lists may still change ([OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html), [SEP-1766](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1766), [registry versioning](https://modelcontextprotocol.io/registry/versioning)). Whether automatic blocking creates unacceptable churn with legitimately dynamic servers is **UNVERIFIED — settle it by running warn-only hashing for 30 days and measuring stable changes, expected `list_changed` events, and false alarms before enabling a block**.

Hashing provides change evidence, not authenticity or behavioral safety; SEP-1766 says so directly ([SEP-1766](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1766)). Its value is therefore to force review of changed authority, not to certify that the approved version is benign.

### 2.3 A narrowly scoped gateway may pay off for governance or containment

It is **likely (55-80%)** that a gateway improves operations when several clients must consume the same curated server set, when per-user identity must be enforced centrally, or when local servers need container isolation. Docker, ToolHive, ContextForge, and GitHub each implement relevant parts, and Cloudflare's governance portal independently frames central identity, scope, and audit as the remote-MCP use case ([Docker MCP Gateway](https://github.com/docker/mcp-gateway), [ToolHive](https://github.com/stacklok/toolhive), [ContextForge security features](https://ibm.github.io/mcp-context-forge/latest/architecture/security-features/), [Cloudflare MCP governance](https://developers.cloudflare.com/agents/model-context-protocol/protocol/governance/)). The net reliability benefit for a single-owner Windows harness is **UNVERIFIED — settle it with a 14-day shadow pilot that compares direct and gateway paths for connection success, p50/p95 latency, startup time, tool-list correctness, authentication failures, and recovery from one dead backend**.

It is **unlikely (20-45%)** that a broad enterprise gateway is the best immediate default for this owner, because the products add databases, containers or Kubernetes, identity layers, and sometimes protocol translation while native clients already provide lazy discovery and permissions ([ToolHive architecture](https://github.com/stacklok/toolhive), [ContextForge repository](https://github.com/IBM/mcp-context-forge), [Microsoft MCP Gateway](https://github.com/microsoft/mcp-gateway), [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp)). This is an architectural inference, not a product defect; the shadow-pilot experiment above would overturn it.

### 2.4 Search-and-execute / code mode can compress huge API surfaces

It is **likely (55-80%)** that a two-tool `search`/`execute` facade is valuable for a genuinely huge, coherent API because Cloudflare now ships an experimental OpenAPI-to-MCP implementation that keeps the schema outside model context, blocks direct sandbox egress, keeps credentials host-side, and bounds final results ([Cloudflare Code Mode patterns](https://developers.cloudflare.com/agents/model-context-protocol/codemode/), [Cloudflare search-and-execute guide](https://developers.cloudflare.com/agents/model-context-protocol/guides/build-codemode-openapi-mcp-server/)). Production safety and cross-model reliability are **UNVERIFIED — settle them with adversarial path/argument tests, side-effect approval tests, and task-completion comparisons against explicit tools**. Cloudflare labels the feature experimental and warns that authorization must still be enforced in the host callback.

For heterogeneous servers, replacing explicit tools with a universal code executor is **unlikely (20-45%)** to improve safety, because it moves selection and argument construction into generated code and creates a new sandbox/approval boundary; Cloudflare itself says code execution does not replace authorization ([Cloudflare Code Mode patterns](https://developers.cloudflare.com/agents/model-context-protocol/codemode/)).

### 2.5 Trust/sensitivity annotations and message signing remain unsettled

Deterministic trust annotations are **roughly even (45-55%)** as an ecosystem-wide solution. A closed MCP proposal describes private, sensitive, open-world, malicious-activity, and attribution hints, but also acknowledges divergent definitions and assumes trust in all participating servers ([MCP issue #711](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/711)). Interoperable adoption is **UNVERIFIED — settle it with a current-spec conformance survey across the ten clients and twenty servers most relevant to the owner, then test whether clients enforce rather than merely display annotations**.

Application-layer message signing is **unlikely (20-45%)** to be worth adding to this personal harness now. OWASP recommends it, but it is not part of the cited core MCP authorization flow, requires key distribution/replay state, and mainly protects against compromised middleware after TLS termination ([OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html), [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). Its incremental value is **UNVERIFIED — settle it with a concrete threat model showing an untrusted intermediary that TLS, process isolation, and endpoint authentication do not already remove**.

## 3. What is hype, and how to tell

### “One gateway makes MCP secure”

This is hype. A gateway can enforce identity and policy, but it also receives tool schemas/results, routes credentials, translates protocols, and may spawn local processes. The official security guidance describes specific proxy-only escalation paths and confused-deputy risks, while Microsoft's gateway explicitly says its command denylist is not a sandbox ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [Microsoft MCP Gateway](https://github.com/microsoft/mcp-gateway)). The tell is an architecture diagram that labels the gateway “zero trust” without documenting token audience validation, per-request authorization, SSRF controls, process isolation, fail-open/fail-closed behavior, and redacted audit logs.

### “The official registry means vetted or safe”

This is directly contradicted by the registry. It verifies namespace ownership and metadata relationships, delegates scanning, disclaims server safety, and generally does not remove servers merely for security vulnerabilities ([registry about](https://modelcontextprotocol.io/registry/about), [registry terms](https://modelcontextprotocol.io/registry/terms-of-service), [registry moderation policy](https://modelcontextprotocol.io/registry/moderation-policy)). The tell is substituting publisher identity, stars, or registry presence for a pinned artifact, reviewed capabilities, contained runtime, and explicit permissions.

### “Up to 85% fewer tokens” as a product-selection result

Anthropic and ToolHive both publish 85% figures, but they are not comparable evidence: Anthropic describes a particular internal tool-search evaluation, while ToolHive's repository uses an “up to” product claim without an independent benchmark in the reviewed sources ([Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), [ToolHive repository](https://github.com/stacklok/toolhive)). The tell is a percentage without catalog composition, model/version, task set, baseline, latency, accuracy, and raw results. Token reduction alone can hide missed tools or extra search turns.

### “Thousands of tools” as a goal by itself

Claude's Agent SDK documents a 10,000-tool catalog limit, and vendors advertise access to thousands, but the useful metric is successful discovery and completion, not maximum catalog size ([Claude Agent SDK tool search](https://code.claude.com/docs/en/agent-sdk/tool-search)). The tell is a scale claim with no recall@k, wrong-tool rate, name/description quality analysis, or end-to-end task evaluation.

### “AI guardrails solve tool poisoning”

Static or model-based scanners may catch known suspicious text, but tool poisoning can occur throughout schemas and results, and a trusted-looking server can change later. The empirical seven-client study and OWASP guidance support layered controls, not a complete detector ([Huang et al., 2026](https://arxiv.org/abs/2603.22489), [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)). The tell is a scanner marketed without adversarial false-negative/false-positive results, schema-wide coverage, version-drift handling, or deterministic authorization underneath it.

### “Aggregation always simplifies the system”

It simplifies client configuration while centralizing naming, sessions, credentials, retries, and failure behavior. The need for product-specific namespaces and a draft aggregation protocol shows that those responsibilities do not disappear ([MetaMCP](https://github.com/metatool-ai/metamcp), [ContextForge federation ADR](https://ibm.github.io/mcp-context-forge/latest/architecture/adr/011-tool-federation/), [MCP-AX draft](https://datatracker.ietf.org/doc/draft-abbott-mcp-ax/)). The tell is counting endpoints rather than processes, trust boundaries, state stores, and independent failure modes.

## 4. Specific things this owner's harness should adopt

### 4.1 Keep native MCP Tool Search on; always-load only a tiny proven core

**Tag: NATIVE (Claude Code already does this; we just enable it)**

Adopt Claude Code's default deferred MCP tool loading. Do not globally set `ENABLE_TOOL_SEARCH=false`. Use `alwaysLoad` only for a small set of truly universal, compact tools whose extra discovery turn measurably costs more than their persistent schemas. If a proxy or alternate model host does not support `tool_reference` blocks, use `auto:N` rather than silently forcing every schema into context ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [Claude Agent SDK tool search](https://code.claude.com/docs/en/agent-sdk/tool-search)).

This is **very likely (80-90%)** to improve context efficiency without a second runtime, based on two shipped client implementations and Anthropic's internal evaluation ([GitHub Copilot CLI tool search](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/tool-search), [Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Verify with the A/B replay defined in §2.1.

**Anti-overfit gate:** passes. It is a native client behavior, adds no orchestration runtime, memory system, durable executor, trained critic, SaaS observability product, or guardrail framework.

### 4.2 Enforce server and tool allowlists separately from approvals

**Tag: CONFIG (settings/JSON only)**

Maintain an explicit approved-server set and explicit per-tool policy. In Claude Code, use `allowedMcpServers`/`deniedMcpServers` or fixed managed MCP configuration for server admission, then `permissions.deny`, `permissions.ask`, and narrowly scoped `permissions.allow` patterns for invocation. Put mutation, external communication, credential access, browser execution, shell execution, and broad filesystem operations in `ask` or `deny`; do not wildcard-allow a server merely because it is approved to connect ([managed MCP controls](https://code.claude.com/docs/en/managed-mcp), [Claude Code permissions](https://code.claude.com/docs/en/permissions)). For OpenAI remote MCP integrations, use both `allowed_tools` and `require_approval`, not either alone ([OpenAI API MCP tool reference](https://platform.openai.com/docs/api-reference/evals/deleteRun)).

This is **very likely (80-90%)** to reduce accidental authority and cross-server exposure because availability and invocation are independently enforced by current clients and least privilege is the common recommendation of MCP and OWASP guidance ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)). The owner-specific policy split is **UNVERIFIED — settle it by replaying past legitimate calls through warn-only proposed rules and counting blocks/prompts before enforcement**.

**Anti-overfit gate:** passes. This uses existing settings and permission buses.

### 4.3 Add a deterministic MCP preflight and schema-drift snapshot

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build one small script invoked at session start and on explicit audit. For each configured server, with a strict per-server timeout: initialize; record negotiated protocol/capabilities; exhaust paginated `tools/list`; canonicalize each tool's name, description, input/output schema, annotations, and server identity; hash both each tool and the whole list; record connection state and latency; and compare with the last approved snapshot. Output terminal markers such as `SUCCESS:mcp-preflight` or `FAILED:mcp-preflight <server> <reason>`. New/removed/changed tools warn by default; a changed write-capable or previously approved tool requires review before its invocation policy is broadened. Respect `list_changed` by re-snapshotting rather than treating all change as malicious ([MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [OWASP schema-integrity guidance](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)).

This is **very likely (80-90%)** to detect dead endpoints, malformed discovery, and schema drift at low complexity; whether blocking changed high-risk tools is tolerable is **UNVERIFIED — settle it with the 30-day warn-only trial in §2.2**.

Do not add semantic “malice” classification in version one. Hash/diff, timeouts, pagination correctness, and explicit policy are deterministic; a scanner can later supply advisory evidence without becoming the authorization boundary.

**Anti-overfit gate:** passes. It is a small stateless check on the existing MCP/lifecycle bus. It is not a second orchestrator, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### 4.4 Prefer scoped native OAuth for remote MCP; forbid token passthrough

**Tag: CONFIG (settings/JSON only)**

For remote servers, prefer the host's OAuth flow and HTTPS over pasted bearer headers. Require exact redirect matching, PKCE/state protections, token audience validation, minimal initial scopes, incremental elevation, and per-server credentials. Do not pass a token issued for a downstream API through an MCP server; the official MCP guidance explicitly forbids this pattern ([MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). Claude Code documents secure OAuth token storage/refresh and automatic authorization discovery for HTTP servers ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp)).

This is **almost certain (90-99%)** to be safer than plaintext, shared, or wrong-audience tokens because the OAuth requirements and token-passthrough risks are explicit and standards-based ([MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [RFC 9700 OAuth security best current practice](https://datatracker.ietf.org/doc/rfc9700/)). Interoperability with every server is **UNVERIFIED — settle it by preflighting each remote server's Protected Resource Metadata and completing one least-scope login/call/refresh/revoke cycle**.

**Anti-overfit gate:** passes. It uses the protocol and native client credential path.

### 4.5 Contain local stdio servers and pin what executes

**Tag: CONFIG (settings/JSON only)**

Treat every local MCP command as installed code. Pin package/image versions or immutable digests; avoid “latest” and unreviewed `npx -y`/equivalent execution for privileged servers; pass only required environment-variable names; restrict filesystem roots and network access; and use stdio for local-only communication. For higher-risk third-party servers, use an existing container boundary with read-only mounts, no-new-privileges, resource limits, and no network unless required ([MCP security policy](https://github.com/modelcontextprotocol/modelcontextprotocol/security), [MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)).

This is **very likely (80-90%)** to reduce supply-chain drift and blast radius because it removes mutable package resolution and limits process authority. Exact Windows containment fidelity for each selected runtime is **UNVERIFIED — settle it with a canary server that attempts forbidden file, process, and network access under the proposed profile**.

**Anti-overfit gate:** passes if implemented with the already-available OS/container runtime and only for servers that need it. It fails if used as a pretext to introduce a full Kubernetes control plane for a single workstation.

### 4.6 Bound tool calls, outputs, startup, and retries

**Tag: CONFIG (settings/JSON only)**

Set finite connection/startup and invocation timeouts, output limits, and per-run call budgets for expensive or side-effecting tools. Claude Code already has bounded MCP output warnings/limits and bounded remote retries; GitHub's gateway demonstrates per-tool call limits and explicit failure propagation rather than silently dropping a failed backend ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [GitHub tool restrictions](https://github.github.com/gh-aw/reference/github-tools/), [GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/)). Cache denied scope-elevation failures to avoid repeated auth loops, as the MCP security guide recommends ([MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)).

This is **very likely (80-90%)** to constrain retry loops, runaway output, and hung connections because each limit creates a deterministic terminal state. Optimal thresholds are **UNVERIFIED — settle them from observed p95 successful latency/output/call counts, then place limits above legitimate tails and test induced hangs/oversized responses**.

**Anti-overfit gate:** passes. These are native limits, not a durable execution system.

### 4.7 Do not adopt the official registry as an automatic installation source

**Tag: CONFIG (settings/JSON only)**

Use the registry for discovery and publisher identity only. Installation still requires a curated allowlist, pinned version/digest, capability review, schema snapshot, and containment profile. Do not auto-install or auto-enable because a server is “official registry” listed ([registry about](https://modelcontextprotocol.io/registry/about), [registry moderation policy](https://modelcontextprotocol.io/registry/moderation-policy), [registry terms](https://modelcontextprotocol.io/registry/terms-of-service)).

This is **almost certain (90-99%)** to avoid a false trust inference because the registry explicitly disclaims that inference and delegates code scanning.

**Anti-overfit gate:** passes. It is a policy on the existing registry/config path.

### 4.8 Do not install a general gateway by default; define a promotion gate

**Tag: NATIVE (Claude Code already does this; we just enable it)**

Keep direct native client-to-server connections as the baseline. Promote a gateway only if one of these is measured: (a) at least two active clients require the same curated endpoint and policy; (b) direct connection/startup failures exceed an agreed service objective and the gateway shadow path improves them; (c) central per-user identity/audit is required; or (d) several untrusted local servers need a shared container lifecycle. Then run a bounded bakeoff, not a feature checklist.

The bakeoff should compare Docker MCP Gateway and ToolHive first for workstation isolation/lifecycle, and ContextForge only if federation, legacy API virtualization, or multi-user identity is genuinely required. Score cold/warm startup, successful discovery including pagination and `list_changed`, tool-name collision handling, protocol-version preservation, OAuth login/refresh/revoke, one-dead-backend behavior, p50/p95 added latency, memory/CPU, log redaction, Windows operability, upgrade/rollback, and removal completeness ([Docker MCP Gateway](https://github.com/docker/mcp-gateway), [ToolHive](https://github.com/stacklok/toolhive), [ContextForge](https://github.com/IBM/mcp-context-forge)).

It is **likely (55-80%)** that direct native connections remain the smaller and more reliable baseline until one promotion condition is met, because lazy discovery, permissions, retries, and dynamic updates already exist natively while every gateway adds another runtime boundary ([Claude Code MCP documentation](https://code.claude.com/docs/en/mcp)). The conclusion is **UNVERIFIED — settle it with the 14-day direct-versus-shadow experiment in §2.3**.

**Anti-overfit gate:** passes because it explicitly rejects a second orchestration runtime until evidence justifies it. A full gateway deployment would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and would otherwise reintroduce a previously rejected second orchestration runtime.

### 4.9 If a gateway is promoted, require deterministic properties before optimizer features

**Tag: BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

This is a conditional proposal, not a current adoption recommendation. Require: server/tool allowlists at discovery and invocation; stable server-qualified names; protocol and schema preservation; bounded startup/call/output; healthy-backend isolation; explicit error propagation; per-server credentials with audience validation; no secret logging; localhost-only management by default; containment for spawned stdio processes; and exportable, redacted call records. Only after those pass should semantic routing, content classifiers, retries with fallback, or code mode be evaluated ([GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/), [MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices), [ContextForge security features](https://ibm.github.io/mcp-context-forge/latest/architecture/security-features/)).

It is **very likely (80-90%)** that these deterministic controls provide more safety and diagnosability than adding an unvalidated semantic optimizer first; the evidence is the protocol's explicit lifecycle/error contracts and GitHub's concrete gateway controls ([MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [GitHub MCP Gateway specification](https://github.github.com/gh-aw/reference/mcp-gateway/)). Comparative product conformance is **UNVERIFIED — settle it with the bakeoff tests in §4.8**.

**Anti-overfit gate:** currently fails for an unconditional deployment because this is a new daemon/runtime and overlaps a previously rejected second orchestration runtime. It passes only after a promotion condition and shadow benchmark provide its independent justification. Do not deploy it merely for feature breadth.

## Bottom line

Adopt what is already native and deterministic: deferred tool discovery, explicit server admission, exact tool permissions, bounded execution, standards-based OAuth, and dynamic-list support. Add one small preflight/schema-diff mechanism because it closes a real integrity and reliability gap without becoming a new runtime. Treat registry metadata as discovery, annotations as hints, scanner output as advisory, and gateway marketing as a hypothesis.

A general gateway is not rejected forever. It is rejected **until measured need beats its added boundary**. That is the anti-overfit answer: preserve the minimal client/server architecture while models and clients continue improving, and promote infrastructure only through an explicit, reproducible shadow test.
