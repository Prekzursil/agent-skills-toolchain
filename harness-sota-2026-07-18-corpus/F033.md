# F033 — Blue-team red-team: cross-session → exfiltrate-a-secret

**Unit:** F033  
**Date:** 2026-07-19  
**Mode:** defensive analysis only; no live credential was printed, validated with a provider, transmitted, rotated, modified, or deleted  
**Subject:** the live Windows harness under `C:\Users\Prekzursil`  

## Executive verdict

The most plausible path is not an exotic MCP protocol escape. It is a same-Windows-principal read of literal API credentials from the shared, live MCP account stores—especially `C:\Users\Prekzursil\source\agent-skills-toolchain\tools\mcp\search-hub\accounts.json`—followed by direct outbound transmission from an already-authorized shell or network tool. This path is **almost certain (90-99%) to be technically available** because four mechanically different observations agree:

1. A value-safe parser found nine non-empty 36-character literals under `EXA_API_KEY` at `search-hub/accounts.json:21,28,35,42,49,56,63,70,77`, plus a non-empty 36-character `DATABRICKS_TOKEN` literal at `cloud-hub/accounts.json:51`. No values were emitted.
2. The account-store implementation explicitly accepts either literals or `${ENV}` references and returns the literal unchanged: `tools/mcp/_shared/accounts.py:11-17,58-60,160-167`. The hubs layer the selected account environment into spawned backend processes: `tools/mcp/social-hub/hub.py:113-134,155` (the cloud/search hubs use the same shared account-store design).
3. File ACL inspection gives `DESKTOP-A60S9GP\CodexSandboxUsers` `ReadAndExecute` and `Modify` on both live account files, while the current owner has `FullControl`. `git ls-files` independently reports both files tracked; `git check-attr` reports `filter: git-crypt` and `diff: git-crypt`. Git encryption protects repository blobs, not the decrypted live working tree that concurrent sessions read.
4. A live process census found 12 hub processes—cloud, search, and social under each of four distinct `claude.exe` parent PIDs. Thus credentials/configuration are reused across concurrent sessions even though the stdio hub processes themselves are per-Claude-parent rather than one shared PID.

The credentials' present provider validity is **UNVERIFIED**; no live provider call was made. An owner-approved, minimally scoped identity/quota request for each credential, or rotation followed by an expected authentication failure, would settle validity. This does not weaken the finding: a non-empty value stored in a field intentionally consumed as an API credential must be handled as a secret until disproven.

The existing controls do **not** stop this path. That conclusion is **almost certain (90-99%)** because the active configuration, the guard source, a known-positive-controlled behavioral probe, and the host permission modes all agree. Even when `HARNESS_CREDENTIAL_GUARD=1` was scoped only to a harmless synthetic hook invocation, a `Read` of the live `accounts.json` path produced `decision=none`; a synthetic `PowerShell` command combining that path with `Invoke-WebRequest https://invalid.example` also produced `decision=none`. In the same run, the detector returned `decision=deny` for `C:\synthetic\credentials.json`, proving the detector was active and capable of detecting a known-positive target.

Severity is **critical** for confidentiality and **high** for likelihood. The blast radius is the set of secrets readable by the shared Windows principal, not only the ten literals found in these two files: a names-only inventory found 77 secret-looking process variables and confirmed all 77 non-empty; the User environment held 71 names/69 non-empty and the Machine environment 73 names/71 non-empty. The scan never emitted values. The Machine environment ACL grants `BUILTIN\Users` `ReadKey`, so machine-scoped environment secrets are broader than a single owner process.

## Scope and trust boundary

### In-scope principals and sessions

The relevant attacker is a compromised, prompt-injected, or simply mis-scoped autonomous Claude/Codex session running as the same Windows user or as a member of the local Codex sandbox group. It does not need administrator rights. The cross-session property matters because:

- every session inherits or can query common user/machine environment state;
- Claude and Codex load shared configuration below the same profile;
- multiple live Claude sessions use the same plaintext account-store files;
- the account stores select credentials that are then injected into session-local MCP backend children;
- the working-tree ACL expressly admits the Codex sandbox group.

There is no confidentiality boundary between two processes running with the same unrestricted Windows principal merely because they have different model thread IDs. This is **almost certain (90-99%)** from Windows ACL semantics plus the observed ACLs and effective host modes. `C:\Users\Prekzursil\.codex\config.toml:6-7` sets `approval_policy = "never"` and `sandbox_mode = "danger-full-access"`; `C:\Users\Prekzursil\.claude\settings.json:27-60,64-75` broadly allows file/shell/network/MCP tools, sets `defaultMode` to `bypassPermissions`, and adds both `C:` and `D:` as accessible directories.

## Plausible abuse narrative (non-runnable)

No exploit steps are provided. At defender level, the path is:

1. One concurrent agent session obtains an instruction—through direct malicious intent, prompt injection in repository content, a poisoned skill/hook, or cross-session task contamination—to inspect shared MCP account configuration.
2. Its file or shell capability reads the live, decrypted account store. The path is accessible under the current ACL and host policy. The literal enters either model/tool output or stays inside the shell pipeline.
3. The same tool call, or a subsequent call in the same session, sends the material to an external destination. Direct shell egress is the most dangerous variant because redaction after tool execution cannot recall bytes already transmitted.
4. The attacker reuses the credential off-box. Provider logs would see a new source IP, user agent, geography, or atypical API pattern; local logs may contain only the source-read and egress commands.

This route is more plausible than process-memory scraping because it requires only ordinary allowed capabilities, uses stable paths, avoids elevated rights, and targets intentionally parseable plaintext. Process-memory scraping remains a secondary route if file/environment cleanup is incomplete.

## Why the surface is exposed

### 1. Literal account records are a supported feature, not an accidental parser quirk

`accounts.py:11-17` documents literal values as supported. `resolve_env` at `:160-167` substitutes `${NAME}` references but passes non-reference strings through unchanged. `account_tool_defs` at `:213-238` advertises an `add` operation whose `env` values may be literals. That makes a literal-bearing account record a normal reachable state.

The implementation claims the on-disk store is gitignored and restrictive at `accounts.py:34-35,327-330`. Live reality contradicts both assurances:

- `git ls-files --error-unmatch` succeeds for both account stores, and `git check-ignore` says neither is ignored;
- the files use git-crypt in the repository, but are decrypted in the working tree;
- their inherited ACL grants the Codex sandbox group read and modify access;
- `os.chmod(..., 0o600)` is explicitly described as best effort, and the source itself notes that Windows honors only a read-only bit (`accounts.py:327-330`).

Thus the code-level “restrictive permissions” claim is not a Windows access-control guarantee.

### 2. Ambient secrets are injected at the wrong trust layer

The sanitized inventory saw 77 non-empty secret-looking variables in the current process. Config indirection such as `.mcp.json:62-67` protects the JSON from containing those values, but each autonomous session currently starts inside the credential-bearing principal and process environment. A malicious shell does not need to ask an MCP server to disclose its token; it can inspect its own inherited environment or the persistent registry environment.

This is a cross-session architectural issue: configuration and credentials are global to the user/machine, while trust decisions happen per model thread. A per-thread instruction boundary cannot protect a per-user credential namespace.

### 3. Read and egress controls are permissive

Claude's live permission policy allows `Read`, `Grep`, `Bash`, `WebFetch`, multiple remote MCPs, and whole-drive additional directories (`settings.json:27-75`). Codex runs with no approval prompts and full access (`config.toml:6-8`). These settings are intentional autonomy choices, but together with ambient credentials they collapse read plus send into one trust domain.

The owner-provided corpus quantifies that these channels are heavily exercised: Bash 108,121 calls, PowerShell 19,181, and WebFetch 8,042. Those figures do not prove abuse; they establish that malicious credential reads/egress can hide inside high-volume normal channels. The corpus hook section is intentionally not used because its own `_meta` marks that detector broken.

## Existing-control verification

### Declarative Claude deny list: does not match the live account store

`C:\Users\Prekzursil\.claude\settings.json:64-69` denies only `.env`, `*.pem`, and `*.credentials*` through the `Read` tool. `accounts.json` matches none of those patterns. It also does not constrain shell reads of the registry or arbitrary paths.

### Standalone credential-read hook: registered, off by default, and path-incomplete

The standalone hook is actually registered for `Read|Edit|MultiEdit|Grep|Bash|PowerShell` at `settings.json:240-247`, so this is not an absent-hook inference. Its implementation says the credential-read block is opt-in and off by default at `deny-credential-reads/deny.py:73-89`. Process, user, and machine checks all found `HARNESS_CREDENTIAL_GUARD` absent.

More importantly, enabling it does not cover the primary path. The safe behavioral matrix was:

| Synthetic input to the live hook | Scoped flag | Result |
|---|---:|---|
| `Read` of live `...\search-hub\accounts.json` path | `HARNESS_CREDENTIAL_GUARD=1` | rc 0, empty output, no decision |
| `PowerShell` text containing that path plus an invalid `.example` outbound sink | `HARNESS_CREDENTIAL_GUARD=1` | rc 0, empty output, no decision |
| `Read` of `C:\synthetic\credentials.json` | `HARNESS_CREDENTIAL_GUARD=1` | rc 0, JSON deny |

The third row is the required known-positive control. Therefore “no decision” for `accounts.json` is a detector-validated finding, not a failed probe.

### Shared `SecretGuardModule`: same default-off and incomplete pattern

`C:\Users\Prekzursil\.agents\harness\modules.py:50-61` makes credential blocking opt-in. Its credential regex at `:641-643` recognizes `.env`, `auth.json`, `credentials(.json)`, SSH private-key names, and `.aws/credentials`, but not `accounts.json`, Windows environment registry paths, environment enumeration APIs, or keyring reads. The module blocks only when the flag is enabled at `:791-798`.

The existing unit tests affirm rather than contradict the default: `tests/test_modules.py:266-300` expects credential reads to be allowed when the flag is absent and blocked when set. A targeted run produced `8 passed, 167 deselected`. That validates the feature's intended state but does not cover the primary file name.

The literal-secret input block is also opt-in at `modules.py:748-762`. In any case, a PreToolUse literal scanner sees command text before execution, not the secret produced by reading a file inside the command. Post-execution redaction cannot prevent direct shell egress.

### Storage redaction: useful, but not preventive

The event ledger redacts string values and paths before persistence (`ledger.py:68-84,1019-1024`) and fingerprints commands (`ledger.py:374-400`). This is a valuable control against secondary leakage into durable memory. It is not an egress control. A shell pipeline can transmit bytes before the dispatcher receives a result to sanitize.

### Native subprocess scrubbing: available, not enabled here

Claude Code now exposes `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, which strips Anthropic and cloud-provider credentials from Bash, hook, and stdio MCP child environments while keeping them in the parent; official documentation states this explicitly. No process/user/machine definition of that variable was observed in this unit. Codex officially supports `shell_environment_policy` with default exclusion of names containing `KEY`, `SECRET`, or `TOKEN`, plus `include_only` and `inherit = core|none`; the live `config.toml` contains no `shell_environment_policy` section and instead selects `danger-full-access` at `:6-7`.

These native controls materially reduce accidental child-process inheritance but do not by themselves prevent a same-user PowerShell process from querying HKCU/HKLM environment registry values or reading the literal account files. Treating them as the complete fix would be unsafe.

## Minimal mitigation

### M1 — credential-free autonomous-session principal — **CONFIG (settings/JSON only)**

This is the minimum mitigation that actually closes the identified trust-boundary failure:

1. Treat the ten discovered literals as exposed candidates: rotate them without first validating by live use, because validation itself is unnecessary risk. Replace the account-store entries with non-secret disabled placeholders until a protected capability path exists.
2. Remove long-lived API credentials from both User and Machine environment storage. This matters because Machine environment values are readable by `BUILTIN\Users`; merely removing them from the current shell leaves registry persistence available.
3. Launch autonomous Claude/Codex sessions under a dedicated, non-admin Windows principal whose profile, HKCU environment, Credential Manager vault, and readable filesystem contain no reusable owner credentials. Give that principal only its task workspace. Do not add it to ACLs for the owner profile or the plaintext MCP account stores.
4. Disable credentialed cloud/search/social MCP registrations for that principal until the service can be exposed as a capability that never returns or injects reusable secret material into the agent-side process tree.

This may temporarily reduce capability. It is still the minimal honest fix: security boundaries come from principals/capabilities, not filenames or model instructions. It rides Windows ACLs and existing provider configuration and introduces no new daemon, memory system, orchestration runtime, or guardrail framework.

M1 is **very likely (80-90%) to prevent this exact file/environment route** because the agent principal would neither read the owner stores nor inherit the owner registry environment. Evidence: the current exposure is wholly explained by same-principal ACL and environment access. The remaining uncertainty is whether any credential is duplicated in a task workspace, shell profile, CLI auth file, browser store, or globally readable location. The settlement experiment is a fresh-session canary matrix under the dedicated principal: prove a known-safe workspace file is readable, then prove synthetic canary credentials in owner-only file, owner HKCU environment, owner keyring, and sibling process environment are unreadable, while outbound access is separately tested. Use canaries only—never real secrets.

### M2 — enable native child-environment minimization as immediate defense in depth — **NATIVE (Claude Code already does this; we just enable it)**

- Claude: set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` in managed launch policy, then restart every session. Official docs say it scrubs Bash, hooks, and MCP stdio children.
- Codex: configure `[shell_environment_policy] inherit = "core"`, leave `ignore_default_excludes = false`, and use `include_only` for the smallest safe variable set. Official Codex config documents that default exclusions remove `KEY/SECRET/TOKEN`, `include_only` is a whitelist, and inheritance can be reduced to `core` or `none`.

M2 is **very likely (80-90%) to shrink routine inheritance exposure** based on vendor-documented behavior, but **unlikely (20-45%) to close the whole route alone** because the same Windows principal can still read persistent registry values and plaintext account files. It must accompany M1, not substitute for it.

### M3 — deny the exact source classes on the existing hook bus — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing `SecretGuardModule` and standalone guard with semantic source classes rather than one more loose substring list:

- exact canonical account-store paths under `tools/mcp/*-hub/accounts.json`;
- environment enumeration APIs and `Env:` / `set` / registry environment queries;
- Windows Credential Manager, DPAPI/keyring extraction APIs, and process-environment/memory inspection;
- file-tool reads and actual shell command fields only—never markdown prose or Write/Edit bodies.

Fail closed for these source classes in unattended sessions, and require explicit owner approval in interactive sessions. Add hermetic positive/negative tests, including the live basename `accounts.json`, registry syntax variants, quoted paths, aliases, PowerShell AST forms, and prose mentions. This directly addresses the known D1 use-vs-mention defect in `INPUT-known-harness-defects.md:1-78` rather than reintroducing it.

M3 is **likely (55-80%) to stop ordinary model-generated attempts** because they traverse registered PreToolUse hooks, but **unlikely (20-45%) to be a complete security boundary** against compromised same-user code or an unhooked execution path. The settlement experiment is a hermetic provider matrix across Claude and Codex with canary sources and sinks, plus a bypass suite using indirect shell/process forms.

### Rejected as the minimal answer

- **`${ENV}` substitution alone:** rejected. It removes literals from JSON but the current environment/registry is itself broadly exposed.
- **Same-user OS keyring alone:** rejected. It protects at rest against casual file reads but does not isolate arbitrary code running as that user.
- **Redaction alone:** rejected. It acts after execution and cannot undo network transmission.
- **A new general secret-broker daemon — BUILD-LARGE (new daemon/service/runtime -- needs its own justification):** not proposed as the minimal fix. It would reintroduce a new service/runtime, explicitly disfavored by the anti-overfit gate, and would require authentication, authorization, audit, update, and availability design. If the owner later requires credentialed MCP access from an otherwise credential-free principal, a capability broker may become justified; that premise is **UNVERIFIED**, and a capability inventory showing which required providers cannot use native remote OAuth/connector auth would settle it.
- **Windows Sandbox as the sole solution:** not selected. It provides strong hypervisor isolation and can disable networking or use read-only mapped folders, but Microsoft documents that only one instance can run at a time, while this harness demonstrably runs four concurrent Claude parents. It is a useful high-risk single-session mode, not the general concurrent-session answer.
- **Claude native Bash sandbox on this host:** not selected as the immediate Windows-native fix. Official Claude documentation says native Windows is unsupported; it requires WSL2. A WSL2 migration could be valuable, but it is not smaller than the dedicated-principal configuration and does not cover non-Bash tools by itself.

## Detection signature

### D1 — cross-session credential-source → egress correlation — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Emit a value-free event at PreToolUse whenever an actual read-capable tool invocation touches one of these source categories:

```text
source_class in {
  mcp_account_store,       # canonical */tools/mcp/*-hub/accounts.json
  persistent_environment, # HKCU/HKLM Environment, Env:, GetEnvironmentVariables
  os_credential_store,    # Credential Manager/keyring/DPAPI retrieval
  process_environment     # sibling PID environment or process-memory access
}
```

Emit a second value-free event for an egress-capable action:

```text
sink_class in {
  shell_http, raw_socket, dns, upload, send_user_file,
  webfetch_external, remote_write_mcp, clipboard_or_browser_paste
}
```

Generate a critical alert when either:

1. one actual command contains both a source and sink; or
2. the same session/agent/PID touches a source and then any non-owner-approved sink within 120 seconds; or
3. a child spawned after a source touch creates the sink connection.

Log only timestamp, provider, session hash, agent hash, PID/PPID, normalized source class, canonical path hash, sink class, destination eTLD+1/IP, rule version, and command fingerprint. Never log command bodies, file contents, environment values, HTTP bodies, headers, query strings, or clipboard data. The current ledger already provides redaction and argv fingerprinting primitives at `ledger.py:68-84,374-400`; reuse them.

High-signal lexical/AST indicators include:

- `accounts.json` beneath an MCP hub, not every generic `accounts.json` in a project;
- `Get-ChildItem Env:`, `$env:*` enumeration, `[Environment]::GetEnvironmentVariables`;
- `Get-ItemProperty` / registry APIs against HKCU/HKLM environment keys;
- `cmd /c set`, `reg query` of environment locations;
- keyring/Credential Manager enumeration or retrieval;
- process-open/read APIs targeting `claude.exe`, `codex.exe`, `python.exe`, or `node.exe` followed by network activity;
- outbound `Invoke-WebRequest`, `Invoke-RestMethod`, `curl`, `wget`, Python HTTP/socket libraries, base64/hex compression immediately before network use, or a remote-write MCP call.

To resist trivial encoding, normalize PowerShell ASTs and argv before matching; join aliases to canonical cmdlets; resolve paths without opening targets; and correlate process lineage. Do not match prose or a Write/Edit payload that merely describes these strings. This follows the measured D1 discriminator requirement in `INPUT-known-harness-defects.md:1-78`.

### D2 — native Windows telemetry supplement — **CONFIG (settings/JSON only)**

Use existing PowerShell Operational logging for Script Block event 4104 and add process/network telemetry through native Windows facilities. Correlate:

- PowerShell 4104 containing a source indicator and an outbound sink;
- process creation for shell/interpreter children of Claude/Codex;
- network connection from the same PID or descendant within 120 seconds;
- process-access telemetry against credential-bearing sibling processes.

Current host evidence:

- `Microsoft-Windows-PowerShell/Operational` exists, is enabled, and held 1,441 records at inspection time; 20 event-4104 records were retrievable in a capped seven-day sample.
- A broader value-safe seven-day query saw 260 event-4104 records and 211 outbound lexical matches. Its source matcher returned zero, but that is **UNVERIFIED as an absence** because the probe did not demonstrate a known-positive source event in that channel; replay a canary source script block and confirm it appears before using zero as a baseline.
- Sysmon is **absent with almost certain (90-99%) confidence**: `Get-Service Sysmon,Sysmon64` returned zero after the same detector found known-present `WinDefend` running; independently, the Sysmon Operational log was absent after the same log detector found the known-present enabled System log.

Enabling native process/network telemetry is **very likely (80-90%) to make the described source→sink sequence observable** when the abuse uses PowerShell or a logged child process. It is **unlikely (20-45%) to catch all MCP-internal or in-process exfiltration without the hook correlation**, because TLS payloads are opaque and some tools may not create a separately visible shell child.

### Provider-side corroboration — **CONFIG (settings/JSON only)**

For each rotated provider credential, enable available audit logs and alert on:

- first use from a new ASN/geography/IP;
- user-agent or client fingerprint change;
- calls outside the owner's normal time window;
- sudden endpoint mix or quota slope changes;
- one token used concurrently from the workstation and a new source;
- authentication success immediately after a local source→sink alert.

Provider audit support and exact event fields are **UNVERIFIED per provider**; the settling experiment is a names-only capability inventory of EXA and Databricks account/audit controls, followed by one owner-authorized canary alert test. This recommendation does not depend on provider logs for prevention; they are bypass detection.

The harness currently combines reusable plaintext/ambient credentials, same-principal concurrent sessions, whole-drive or full-access execution, and unrestricted outbound-capable tools. The nominal credential guard is both disabled by default and blind to the actual account-store basename even when enabled. The shortest correct mitigation is to remove credentials from the autonomous session's principal entirely, rotate the exposed candidates, disable credentialed MCPs for that principal, then add native child-environment scrubbing and a value-safe source→sink detector on the existing hook/Windows telemetry buses.
