# K02 — Patterns, preferences, and idioms: what the owner says vs. what they mean

**Partner-dimension:** user-model depth / grows-with-you  
**Unit date:** 2026-07-19  
**Subject access:** read-only; this artifact is the only write.  
**Design law:** no same-context self-correction is accepted as verification. Every proposed loop below terminates in an execution receipt, a different model/context, a durable artifact comparison, or the owner.

## Executive verdict

The highest-value expansion is **not another memory store and not a longer owner profile**. The harness already has a durable preference note, a “Signature prompts + overarching intent” memory, semantic routing, Basic Memory, continuous-learning machinery, an event ledger, open-loop resurfacing, truth/claim verification, and monitor infrastructure. **very likely (80-90%)**, the missing layer is a small, typed **utterance-to-intent delta** between the owner's language and those existing consumers: the evidence is the direct omission/correction samples below plus the independently existing memory/router/ledger substrates, while the proposed shadow evaluation would settle comparative value.

**Local citation aliases used below:** `corpus.json` = `/local_disk0/codexwork/bundle/inputs/corpus.json`; `recall_index.json` = `/local_disk0/codexwork/bundle/claude/hooks/recall-inject/index/recall_index.json`; other shortened hook paths are relative to `/local_disk0/codexwork/bundle/claude/hooks/`. Every alias is followed by an exact line number.

These mappings are useful **hypotheses**, not a license to psychologize the owner. The newest personalization benchmarks find that explicit memory can improve recall without guaranteeing aligned use, that latent-trait extraction and updates remain difficult, and that persistent preferences are often misapplied outside their proper context ([AlpsBench 2026](https://arxiv.org/abs/2603.26680), [BenchPreS 2026](https://arxiv.org/abs/2603.16557)). The design below therefore stores scoped, falsifiable intent rules and measures their use; it does not create a global persona.

## Grounding and method

### What the corpus can and cannot establish

The corpus covers 11,633 files / 10.62 GB / 1,564,084 transcript lines, with zero failed files, one bad line, and 32 oversized lines (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). This supports corpus-level presence claims. It does **not** make every correction candidate human-authored: the miner itself says it is recall-biased and that 41/41 items in an unfiltered smoke sample were agent-authored false positives (`corpus.json:10371-10374`).

I used three safeguards:

1. I treated `Stop hook feedback`, task notifications, teammate messages, and repeated identical loop prompts as clustered/system-shaped evidence, never as independent preference votes.
2. I favored distinct-session owner text and the rare `after_tool_use:true` samples. A read-only Node probe over `owner_correction_candidates.samples` returned `after_tool_use 13 false 387`; concrete examples and their flags are visible at `corpus.json:11201-11204`, `11897-11900`, `11927-11930`, `11987-11990`, `12101-12110`, `12203-12206`, and `12257-12260`.
3. I cross-checked inferred preferences against a mechanically different signal when available: existing curated-memory index entries. The index already contains “User preferences and working style” (`recall_index.json:1260-1271`), “autonomous-testing-preference” (`recall_index.json:1434-1450`), the progress-monitor preference (`recall_index.json:4913-4939`), and “Signature prompts + overarching intent” (`recall_index.json:13235-13260`). This proves the topic is not new; it does not prove those summaries are current or always retrieved.

### Dedup and architectural boundary

No finding below adds a memory database, orchestration runtime, trained critic, durable-execution engine, observability SaaS, or guardrail framework. Every build rides an existing path:

- The semantic router is already designed as a single fail-open UserPromptSubmit router with content gating and per-session dedup (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/route.py:1-22`).
- Selection events already correlate real user text with later tool results while excluding tool/system-shaped messages and bounding/redacting content (`selection-events/emitter.py:1-29`, `131-162`).
- The event ledger already accepts agent annotations for goals, decisions, failures, and milestones, including supersession (`event-ledger/note.py:1-12`, `25-42`), while its Stop writer records objective git state and is fail-open (`event-ledger/stop-hook.py:1-8`, `76-100`).
- Open-loop resurfacing is already folded into the existing SessionStart dispatcher (`open-loops/_common.py:18-26`; `_dispatch/manifest.json:52-60`) and derives unresolved failures plus a standing goal (`open-loops/_common.py:465-493`).
- Truth verification is already a fail-open Stop check for RE anchors (`truth-verify/check.py:1-22`, `163-208`), and persist-nudge is already a once-per-session, strong-signal persistence check (`persist-nudge/nudge.py:1-15`, `125-186`).

The hook ceiling is therefore respected: **zero new hook registrations**. UserPromptSubmit work folds into the existing shared dispatcher/semantic-router lane; Stop-time evidence work folds into truth/claim verification; continuity work extends the existing ledger/open-loop representation; monitor work reads those artifacts out of band.

## Findings — inferred surprises first

### 1. UNVERIFIED — Compile utterances into typed intent deltas, not replacement prompts

- **improvement:** Add an `intent_delta.v1` record to the existing UserPromptSubmit path. It represents `speech_act` (`new_root|add|replace|cancel|order|status|evidence_demand|explore`), `target_thread`, `preserve[]`, `add[]`, `remove[]`, `sequence`, `proof_level`, `autonomy`, `terminal_condition`, `source_prompt_hash`, `confidence_band`, and `expires/supersedes`. A short utterance such as “actually instead of codex fan out after this workflow ends proceed with tdd metaswarm” becomes a **future executor replacement** on one child step, not a new root goal.
- **what it is:** A deterministic phrase/structure lane handles high-precision forms (`also`, `meanwhile`, `after`, `instead`, `do not`, `make sure`, `why`, `continue`). Ambiguous cases are sent—only in shadow initially—to a **fresh-context different model** that sees the root contract, newest prompt, and candidate deltas, not the originating agent's reasoning. The record is appended to the existing ledger; the rendered model context is a compact three-line “root / current delta / preserved threads” envelope.
- **why-inferred:** The owner's additive requests have demonstrably been dropped (`corpus.json:11453-11456`), narrow post-tool corrections exist (`corpus.json:11201-11204`, `11897-11900`), and temporal executor substitutions appear without abandoning the task (`corpus.json:11591-11600`). The existing goal-stability audit independently claims that ordinary follow-ups overwrite the root goal and recommends separate `root_goal` / `latest_delta` fields (`/local_disk0/codexwork/bundle/inputs/audit-findings/E11.md:35-41`); that audit is a claim, but the code experiment below can settle it.
- **how-to-build:** Extend the existing shared UserPromptSubmit module or semantic router; do not register another hook. Keep the high-precision parser under ~120 lines plus schema/tests. Store deltas through `event-ledger/note.py` semantics, adding `parent_goal_id`, `thread_id`, and `operation`. Render at most 500 characters. If deterministic and fresh-model parses disagree, preserve the root and all threads, take only reversible preparatory action, and ask the owner **only when** the difference changes scope, destroys state, sends externally, or changes a high-cost route. Every parser exception returns no delta and exit 0.
- **the EXTERNAL signal that verifies it:** Build a frozen, human-reviewed set of at least 100 real adjacent prompt pairs, stratified across the eight speech acts and including the post-tool examples above. A separate model labels candidates; the owner adjudicates only disagreements/high-impact examples. Pass gates: ≥95% preservation recall for additive constraints, 0 destructive cancellations from an `add/status` utterance, and fewer owner “you ignored X” corrections in a shadow-vs-active matched-session evaluation. **UNVERIFIED:** whether the existing shared dispatcher exposes the full previous root and prompt without truncation; inspect its normalized UserPromptSubmit fixture and run one sanitized controlled trace to settle this before implementation.
- **SOTA citation with URL:** Horvitz's mixed-initiative principles explicitly call for representing uncertainty about user goals, efficient dialog for key uncertainty, low-cost rejection, and precision scoped to uncertainty ([CHI 1999 paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). PrefEval finds preference following can degrade sharply even in long context, supporting an explicit evaluated delta rather than assuming “the model remembers” ([PrefEval, ICLR 2025](https://arxiv.org/abs/2502.09597)).
- **value x effort:** transformative x medium
- **novelty:** inferred-surprise
- **autonomy:** confirm-first
- **NATIVE-vs-BUILD:** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)
- **confidence:** **very likely (80-90%)** that root-vs-delta representation addresses a real failure class, based on two corpus correction forms plus the existing audit's code-level overwrite claim. **likely (55-80%)** that the proposed parser thresholds reduce owner corrections; the labeled shadow experiment above is required.

### 2. UNVERIFIED — Turn the user model into scoped hypotheses with counterexamples, not global persona facts

- **improvement:** Upgrade the existing preference notes to a small `preference_hypothesis.v1` envelope: `rule`, `scope`, `anti_scope`, `positive_examples`, `counterexamples`, `source_kind` (`explicit|correction|inferred`), `valid_from`, `last_supported`, `supersedes`, `confidence_band`, and `application_budget`. For example, “high effort / broad capability coverage” can apply to substantial research/build tasks while “quickly audit RAM; no hard kill” remains a task-local constraint, not a personality contradiction (`corpus.json:11291-11294`).
- **what it is:** Metadata on the **existing Basic Memory/event-ledger artifacts**, not a new store. Retrieval must select both a rule and its nearest counterexample/anti-scope. Explicit current-turn instructions always outrank inferred memories; scoped newer corrections outrank older broad rules; an expired hypothesis is silent rather than auto-renewed.
- **why-inferred:** The corpus contains both expansive requests and tightly bounded/reversible ones. It also shows proposal language that authorizes alternatives (`corpus.json:12257-12260`) and direct prohibitions immediately after tool use (`corpus.json:11201-11204`). Treating all of these as global traits would overfit. The existing recall index proves preference summaries already exist (`recall_index.json:1260-1271`, `13235-13260`), so the missing value is selectivity and lifecycle, not collection.
- **how-to-build:** Extend the existing memory-note template and recall rendering. On promotion by continuous-learning-v2 or `/self-reflect`, require at least two distinct-session supporting examples for an inferred durable rule, or one explicit “always/never” statement plus scope. Store one counterexample whenever a later correction narrows the rule. On retrieval, emit at most two hypotheses whose `scope` matches the task classifier, plus the strongest anti-scope. Never persist sensitive personal traits, credentials, health inference, or third-party attributes from implication alone. Fail open: malformed metadata degrades to an ordinary note and is not applied automatically.
- **the EXTERNAL signal that verifies it:** Create a held-out selectivity suite with four cells: apply, suppress, update, and conflict. The expected label comes from explicit owner text or owner adjudication, never the generating model. Compare current recall vs typed recall on appropriate-application rate, misapplication rate, task completion, and owner correction rate. **UNVERIFIED:** whether current Basic Memory note bodies support frontmatter consistently; inspect ten known preference notes and the active recall builder schema to settle the serialization choice.
- **SOTA citation with URL:** BenchPreS reports a trade-off between stronger preference adherence and misapplication, motivating scope and suppression ([BenchPreS 2026](https://arxiv.org/abs/2603.16557)). PersonaMem reports frontier systems around 50% overall on evolving profiles under its benchmark, arguing against direct-prompt profile trust ([PersonaMem 2025](https://arxiv.org/abs/2504.14225)). AlpsBench uses human-verified structured memories and separately evaluates extraction, update, retrieval, and use ([AlpsBench 2026](https://arxiv.org/abs/2603.26680)).
- **value x effort:** transformative x medium
- **novelty:** inferred-surprise
- **autonomy:** confirm-first
- **NATIVE-vs-BUILD:** CONFIG (settings/JSON only)
- **confidence:** **very likely (80-90%)** that scope/counterexample metadata is safer than a flat global profile, based on the corpus's conflicting task-local forms and BenchPreS. **likely (55-80%)** that it improves this harness's personalization accuracy; the four-cell held-out evaluation settles it.

### 3. UNVERIFIED — Learn from corrections as versioned patches with negative training cases

- **improvement:** When the owner says “no/don't/actually/instead”, capture a candidate **patch** against the immediately preceding intent/action, not a standalone positive memory. Preserve the rejected interpretation as a negative example: `before_interpretation -> correction -> accepted_delta -> external_outcome`.
- **what it is:** A correction lifecycle riding selection-events + event ledger + the existing memory spool. It distinguishes `scope correction`, `method correction`, `fact correction`, `timing correction`, `stop/cancel`, and `accidental message`. The “I sent you the msg by mistake” sample (`corpus.json` sample identified by the read-only probe) must cancel learning rather than become a preference. The owner-facing behavior changes immediately only for the current task; durable promotion waits for either explicit confirmation or recurrence across distinct contexts.
- **why-inferred:** The strongest post-tool samples are surgical: do not delete installers (`corpus.json:11201-11204`), query rather than disable (`corpus.json:11897-11900`), use stronger RE plus autonomous testing (`corpus.json:12101-12104`), and diagnose abnormal test duration before proceeding (`corpus.json:12203-12206`). A positive-only memory would retain both the rejected and corrected routes and leave retrieval to chance.
- **how-to-build:** Extend the existing selection event with a bounded `preceding_action_hash` and add `correction_candidate` / `correction_resolved` ledger kinds. A different-context model classifies the patch from only the previous user turn, action summary, tool result, and correction; deterministic cues gate obvious cancellation. Resolution requires one of: owner explicit acceptance, a changed external execution result, or a later owner message that proceeds without re-correcting the same dimension. On resolution, update the existing note via `supersedes`; do not create “v2” beside “v1”. Memory-spool failure leaves the old preference marked `pending_verification` and resurfaces once through existing open loops. Every error exits 0.
- **the EXTERNAL signal that verifies it:** Replay all human-verified post-tool corrections through a fresh model and compare the next action against the historical accepted path where observable. For fact/method corrections, require the corresponding command/test/MCP result. For subjective scope, require owner adjudication. Track false promotion, stale-rule retrieval, and repeated same-dimension correction. **UNVERIFIED:** the corpus does not include a resolved-intent field or complete adjacent assistant/tool context in the distilled samples; a privacy-bounded join against raw transcript IDs for these 13 samples would settle the initial gold set.
- **SOTA citation with URL:** Amershi et al.'s validated human-AI guidelines include supporting efficient correction, learning from user behavior, updating cautiously, and providing control; the paper synthesizes 150+ recommendations into 18 guidelines and validates them across products ([CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). AlpsBench's separate “updating” task and observed update ceiling reinforce that correction capture and correct later use must be measured separately ([AlpsBench 2026](https://arxiv.org/abs/2603.26680)).
- **value x effort:** high x medium
- **novelty:** inferred-surprise
- **autonomy:** confirm-first
- **NATIVE-vs-BUILD:** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)
- **confidence:** **very likely (80-90%)** that corrections should supersede rejected interpretations rather than coexist, based on the surgical post-tool examples and existing ledger supersession support. **likely (55-80%)** that automatic classification can reach safe precision after deterministic gating; the raw-context replay is required before active promotion.

### 4. UNVERIFIED — Treat “perhaps / better idea?” as delegated optimization, not specification

- **improvement:** Add an `optionality` field to the intent delta: `binding`, `example`, `candidate`, or `outcome_delegation`. “How about X, or perhaps you have a better idea?” records X as a candidate and the desired outcome as binding. The agent may select a better route without asking, but must preserve the outcome and produce comparative evidence.
- **what it is:** A tiny decision protocol: (1) extract outcome, (2) list at most three viable routes, (3) use read-only probes to eliminate dominated routes, (4) autonomously take the best reversible route, or ask only if the remaining choice changes cost, risk, external effects, or user experience materially. The final handoff says which candidate was chosen and what external result justified it.
- **why-inferred:** The owner explicitly couples a concrete suggestion with “perhaps you have a better idea” and the real objective of closer-to-live autonomous validation (`corpus.json:12257-12260`). “Perhaps” also appears in a request for SOTA research and capability discovery (`corpus.json:11297-11300`). Literal execution would underuse the invitation; treating it as mere brainstorming would drop the outcome.
- **how-to-build:** Add four optional fields and a rendering rule to Finding 1's schema—no separate component. Extend `/prompt-optimizer` or the semantic router's high-precision intent table with modal markers. Require an external comparison artifact: benchmark result, dry-run, compatibility check, source evidence, or owner choice. If no comparison signal exists, label the selection provisional and reversible. No self-scored “best”.
- **the EXTERNAL signal that verifies it:** In the held-out intent suite, measure candidate-vs-binding classification and whether the selected route satisfies owner-labeled outcome constraints. For executable tasks, compare tests/benchmarks; for preference residue, ask the owner in a batched calibration review. **UNVERIFIED:** the precision of modal markers on this owner's broader history; label 30 “perhaps/maybe/how about” examples from distinct sessions to settle it.
- **SOTA citation with URL:** Horvitz recommends choosing among act, ask, and wait based on inferred probability plus expected costs/benefits, and degrading service precision under uncertainty ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).
- **value x effort:** high x low
- **novelty:** inferred-surprise
- **autonomy:** just-do-it
- **NATIVE-vs-BUILD:** CONFIG (settings/JSON only)
- **confidence:** **very likely (80-90%)** that the cited “better idea” construction delegates method choice while binding the outcome. **likely (55-80%)** that a four-way optionality field generalizes across sessions; the 30-example calibration set settles it.

### 5. UNVERIFIED — Calibrate silently, then ask in a bundled “preference diff” only when information value is high

- **improvement:** Replace opportunistic clarification with a low-frequency calibration queue. The system silently collects uncertain, consequential hypothesis diffs and surfaces at most three at a natural checkpoint: “I inferred A in scope S from examples E1/E2; keep, narrow, or discard?” Routine, reversible work continues without interruption.
- **what it is:** An extension to `/self-reflect` or a `/calibrate-me` command, backed by existing Basic Memory metadata. It is **not** a hook and never opens a modal automatically. Queue priority is `expected future reuse × consequence of misapplication × uncertainty`; low-value style details expire. A current-turn material ambiguity still uses native AskUserQuestion, but only after cheap probes cannot resolve it.
- **why-inferred:** Prompt fatigue is an explicit hard constraint, while the corpus shows the owner already spends messages repairing omissions and misinterpretations (`corpus.json:11453-11456`, `11927-11936`). The right target is fewer high-value questions, not zero questions. The installed corpus also shows `grill-me-extensive` invoked 33 times and `grill-me` 25 (`corpus.json:13267-13271`), indicating that deep elicitation is welcome when deliberately invoked, not as ambient friction on every task.
- **how-to-build:** Add a JSONL queue beside existing learning artifacts with prompt hashes and no raw sensitive text. `/self-reflect` reads the top three, shows evidence and scope, and writes owner decisions through the existing note path with supersession. Deduplicate by normalized rule+scope. TTL 30 days. AskUserQuestion remains native for irreversible/high-stakes ambiguity. Malformed queue entries are skipped; the task continues.
- **the EXTERNAL signal that verifies it:** Randomize eligible low-risk sessions between current behavior and silent queue; measure interrupt count, time-to-first-action, owner correction count, accepted/narrowed/rejected hypothesis rate, and task outcome. Owner ratings are collected only in the deliberate calibration command. **UNVERIFIED:** whether three items and a 30-day TTL match the owner's attention pattern; an A/B of 1 vs 3 items and 7 vs 30 days settles it.
- **SOTA citation with URL:** Attention-sensitive alerting explicitly balances the context-sensitive cost of deferral with interruption cost ([Horvitz, Jacobs & Hovel, UAI 1999](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/)). Mixed-initiative design likewise recommends dialog only for key uncertainties while considering the cost of needless bother ([Horvitz 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).
- **value x effort:** high x low
- **novelty:** inferred-surprise
- **autonomy:** just-do-it
- **NATIVE-vs-BUILD:** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)
- **confidence:** **very likely (80-90%)** that batching reduces ambient interruption relative to per-turn questioning, based on the interaction-cost literature and the no-new-hook design. **roughly even (45-55%)** that three items / 30 days is optimal for this owner; only the A/B can determine it.

Additive phrases create a child thread; ordering phrases set a dependency; completion automatically returns the parent to `active`. Nothing disappears merely because the conversation focus changed.

The canonical state is the ledger's compact thread records plus external task/artifact status. The UI/model sees only the active thread, its parent, and up to three blocked siblings—never the whole backlog.
- **why-inferred:** The owner explicitly says requested research and a clipboard upgrade were ignored (`corpus.json:11453-11456`), uses “after this workflow ends” for sequence (`corpus.json:11591-11600`), “while we wait” to branch (`corpus.json:11885-11888`), and “continue monitoring the subagents (do not stop them)” to preserve a parallel thread (`corpus.json:11999-12002`). - **how-to-build:** Add fields to `note.py` and ledger state; update open-loop rendering to show `active / blocked / resume-to`. Derive closure only from an external signal: task completion record, expected artifact existence+hash, test receipt, owner cancellation, or a superseding ledger milestone. A final answer may not silently close a thread. If a detector fails, leave the thread open and exit 0. Fold all reading into the current SessionStart dispatcher; add no hook.
- **the EXTERNAL signal that verifies it:** Replay 50 multi-thread prompt sequences, including the explicit omission example, against current and typed state. Score thread survival, correct ordering, false resurrection, owner “forgot/ignored” corrections, and verified closure. Use task/file/test events—not the agent's prose—to mark done. **UNVERIFIED:** whether every provider exposes sufficiently stable task IDs; inspect sanitized Claude and Codex task-event fixtures, falling back to artifact/receipt identity where IDs are missing.

## Kill criteria and failure containment

- Kill or keep shadow-only any classifier with additive-constraint preservation recall below 95%, any destructive false cancellation, or >2% high-impact misapplication in the owner-reviewed set.
- Do not promote an inferred durable preference from one ambiguous utterance. One explicit instruction may govern the current task; durable inference needs recurrence or owner confirmation.
- Do not let remembered preferences override current explicit scope, safety policy, permissions, or third-party context.
- Do not equate tool invocation success with outcome success. Evidence must point to the obligation it settles.
- Do not close a thread from assistant prose. Close from owner cancellation, external task/artifact/test state, or a superseding milestone.
- Every hook-path addition is wrapped in `try/except`, emits no block on internal failure, and exits 0. “Fail open” means the harness yields control; it does not authorize a false success claim.
- If consolidated dispatcher latency crosses the existing budget, disable fresh-model adjudication first and retain deterministic parsing plus manual calibration. No seventh hook is an allowed fallback.

## Alternatives considered and rejected

1. **A new vector-profile or knowledge-graph memory:** rejected. It violates the anti-overfit gate, duplicates Basic Memory/recall, and AlpsBench shows explicit memory does not itself guarantee preference-aligned use.
2. **A trained personalized critic:** rejected. It would be a new model/runtime, risks learning the corpus miner's false positives, and violates the same-context/external-signal law unless separately evaluated.
3. **Inject the full owner profile every turn:** rejected. It increases context and prompt fatigue, encourages context-insensitive preference application, and competes with the actual task.
4. **Ask the owner to clarify every modal phrase:** rejected. It makes owner attention the hot path and contradicts mixed-initiative value-of-information guidance.
5. **Treat “all tools / ultracode” literally:** rejected. The correct measurable target is missing-lens coverage and outcome evidence; raw invocation count rewards ceremony and increases error/latency exposure.
6. **Add a Stop hook for each idiom:** rejected. It breaches the ~6-hook ceiling, duplicates existing verification/open-loop machinery, and detects meaning too late.
7. **Let the generating agent revise its interpretation until it agrees with itself:** rejected by construction. Every proposed adjudication uses a frozen label, a different context/model, an execution result, durable state, or the owner.
