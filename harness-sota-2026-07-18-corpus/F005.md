# F005 — Frontier research: execution-grounded verification and test synthesis

**Unit:** F005  
**Research date:** 2026-07-19  
**Scope:** What is actually established, merely promising, or hype in execution-grounded verification and automated test synthesis; and the smallest high-value mechanisms this harness should adopt. This is research and design only. I made no changes to the unpacked subject tree.

## Executive verdict

The frontier does **not** justify a second orchestration runtime, a learned verifier, or an autonomous test-generation daemon. The most defensible design is much smaller: make every material “done” claim produce an execution receipt; validate the verifier itself with a known-positive control; require a defect-specific test to demonstrate the expected state transition; and use targeted mutation, property-based, metamorphic, differential, or fuzz testing only where each supplies a genuinely independent oracle.

This conclusion rests on three unusually consistent bodies of evidence:

1. Mature testing systems already establish that generation becomes useful when it is closed around **real execution feedback**: coverage-guided fuzzers preserve inputs that reach new paths; property-based systems shrink actual counterexamples; mutation systems measure whether tests detect seeded semantic changes; and search-based generators execute candidates and optimize measurable criteria. These are deployed tools with public implementations, not only model claims: [LLVM libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html), [Hypothesis documentation](https://hypothesis.readthedocs.io/en/latest/reference/api.html), [PIT](https://pitest.org/), [Stryker mutation states](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/), and [EvoSuite repository](https://github.com/EvoSuite/evosuite).
2. Repository-level test-generation benchmarks increasingly use execution transitions rather than prose grading. SWT-Bench defines a useful bug-reproduction test as one that fails on the buggy state and passes on the fixed state; TDD-Bench-Verified publishes executable infrastructure and generated tests; TestGenEval measures pass rate, coverage improvement, and mutation-score improvement in repository containers. Sources: [SWT-Bench](https://swtbench.com/), [IBM TDD-Bench-Verified](https://github.com/IBM/TDD-Bench-Verified), [TestGenEval repository](https://github.com/facebookresearch/testgeneval).
3. Execution is necessary but not sufficient. Even a human-screened benchmark with hidden fail-to-pass and pass-to-pass tests later proved to have major oracle/specification problems in a targeted audit. OpenAI reports that, among 138 SWE-bench Verified problems audited because o3 did not solve them consistently, at least 59.4% had material test-design and/or problem-description issues. This is a selected failure subset, not an estimate for all 500 tasks, but it decisively falsifies “the tests ran, therefore the verdict is correct.” Sources: [original SWE-bench Verified construction](https://openai.com/index/introducing-swe-bench-verified/), [2026 audit and retirement rationale](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/).

The local harness makes this research immediately relevant. Its testing rule mandates unit, integration, and end-to-end tests for every covered language and an 80% default coverage threshold (`/local_disk0/codexwork/bundle/claude/rules/common/testing.md:23-38`), but it contains no equivalent requirement that a new test discriminate buggy from fixed behavior, kill a targeted negative control, or prove that its assertion can fail. Meanwhile, live operation recorded false success/failure classifications caused by semantically blind detectors (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-82`) and seven wrong conclusions from detectors that lacked a known-positive control (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`). The harness already has the correct two-signal principle in prose (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:20-37`); the missing frontier step is to make the critical parts mechanical and artifact-producing.

# 1. Established

## 1.1 Execution feedback is a real, mature search signal

**Established claim:** candidate generation coupled to actual execution can systematically explore behavior that unguided one-shot generation misses. This is **almost certain (90-99%)**, supported by multiple mechanically different, mature systems rather than one model family.

- Coverage-guided fuzzing instruments program execution, mutates concrete inputs, and retains inputs that discover new coverage. libFuzzer also persists crash/timeout artifacts and can replay saved inputs as regression tests. It is explicitly designed for fast, deterministic targets and is commonly combined with AddressSanitizer or UndefinedBehaviorSanitizer. [Official LLVM libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html).
- Property-based testing executes generated cases against developer-specified invariants and shrinks a failing case to a smaller counterexample. Hypothesis exposes shrinking, targeted search, stateful testing, and reproducible failure data, while warning that a poorly chosen target metric can steer search away from bugs. [Official Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html).
- Search-based unit-test generation predates current LLMs. EvoSuite generates and minimizes executable JUnit suites using evolutionary search and can optimize branch, output, and mutation criteria; its generated assertions characterize observed behavior, which is useful for regression but not automatically a specification of correctness. [EvoSuite repository](https://github.com/EvoSuite/evosuite), [EvoSuite project description](https://www.evosuite.org/evosuite/).
- Mutation testing executes a test suite against systematically changed program variants. PIT defines the mutation-kill percentage as a gauge of test quality, while Stryker distinguishes killed, survived, no-coverage, timeout, compile-error, and ignored states rather than collapsing all outcomes into “pass/fail.” [PIT official site](https://pitest.org/), [Stryker official metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

What is established is the **feedback mechanism**, not universal superiority of any generator. Execution makes candidate quality measurable. It does not manufacture a correct oracle.

## 1.2 The fail-to-pass transition is a strong minimum standard for defect reproduction

**Established claim:** for a bug-fix task, a proposed reproduction test is materially stronger if it fails on the original buggy revision and passes on the corrected revision. This is **almost certain (90-99%)**, because it is definitionally discriminating and is used by multiple executable repository benchmarks.

- SWT-Bench explicitly evaluates whether a generated test fails on the original codebase and passes after the issue is fixed; it also rejects suites containing tests that fail on the fixed state. [SWT-Bench methodology](https://swtbench.com/).
- SWE-bench constructs `FAIL_TO_PASS` tests that fail before the solution and pass afterward, plus `PASS_TO_PASS` tests for regression behavior. The Verified subset used three independent human annotations and conservatively removed cases flagged for underspecification or tests that reject valid solutions. [SWE-bench Verified construction](https://openai.com/index/introducing-swe-bench-verified/).
- TDD-Bench-Verified is dedicated to generating tests from issues before resolution and publishes benchmark code and generated Otter outputs. [Official IBM repository](https://github.com/IBM/TDD-Bench-Verified).

This transition is necessary for a reproduction test but not sufficient for correctness: a test may fail for an irrelevant import error, environment error, or overfitted assertion. The observed failure must therefore be classified, and a fixed-state pass must be accompanied by broader regression evidence.

## 1.3 Passing tests, coverage, and compilation are different signals

**Established claim:** compilation/collection, test pass rate, structural coverage, and fault-detection strength measure different things. This is **almost certain (90-99%)**, supported by tool semantics and benchmarks that report them separately.

TestGenEval deliberately reports `pass@k`, coverage improvement, and mutation-score improvement separately, using Dockerized repository environments. Its benchmark contains 1,210 code/test file pairs from 11 repositories. [Official TestGenEval repository](https://github.com/facebookresearch/testgeneval), [ICLR 2025 paper page](https://proceedings.iclr.cc/paper_files/paper/2025/hash/26ded5c8ee8ec1bc4caced4e1c9b1584-Abstract-Conference.html). CoverUp likewise executes generated Python tests and uses line/branch coverage feedback iteratively; its repository repeats tests for flakiness and isolates test pollution. [CoverUp repository](https://github.com/plasma-umass/coverup), [FSE paper](https://doi.org/10.1145/3729398).

Therefore:

- Compile/collection proves the test can be loaded, not that it asserts anything useful.
- A passing test proves compatibility with the observed implementation, not correctness against intent.
- Coverage proves execution reached a location, not that an assertion would detect a defect there.
- A killed, carefully selected mutant or reverted fix is stronger evidence that the test is behaviorally discriminating, though equivalent mutants and unrealistic mutations create noise.

This directly challenges the local blanket coverage policy at `/local_disk0/codexwork/bundle/claude/rules/common/testing.md:23-38`. A numeric threshold can remain a project-specific regression constraint, but it is not a universal completion oracle.

## 1.4 The oracle problem survives execution

**Established claim:** a real execution can yield a wrong verdict when the asserted behavior is underspecified, overfitted, or tests the implementation rather than intent. This is **almost certain (90-99%)**, with both benchmark audits and mature testing methodology supporting it.

The strongest recent signal is the 2026 SWE-bench Verified audit: OpenAI stopped using the benchmark as a frontier measure after finding substantial flawed-test/specification incidence in a targeted set of model failures. The source carefully states the sampling frame, so its 59.4% number must not be generalized to the whole benchmark. [OpenAI audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/). The live SWE-bench tracker also contains current reports involving gold patches, collection failures, image/tag leakage, and issue/test inconsistencies; issue reports are claims until resolved, but they show that executable infrastructure itself remains an active failure surface. [Official SWE-bench issues](https://github.com/swe-bench/SWE-bench/issues).

Metamorphic and differential testing are established responses when an exact expected output is unavailable: metamorphic tests assert relations between executions, while differential tests compare independent implementations or configurations. These are valuable only when the relation or reference is independently justified. A study of metamorphic source-test strategies describes the approach as addressing the oracle problem and evaluates fault-finding differences; compiler-testing work has independently found real commercial compiler bugs through differential/EMI methods. [Metamorphic-testing study](https://arxiv.org/abs/1802.07361), [PLDI 2015 many-core compiler fuzzing](https://pldi15.sigplan.org/details/pldi2015-papers/3/Many-Core-Compiler-Fuzzing).

## 1.5 Test isolation and replay are part of verification, not polish

**Established claim:** a generated test must survive isolated replay and suite interaction before it is accepted. This is **very likely (80-90%)**, supported by implemented behavior in CoverUp and the deterministic-target requirements of libFuzzer, though optimal repetition counts vary by repository.

CoverUp only admits tests that pass alone and increase coverage, provides clean-state isolation to address in-memory test pollution, and supports repeated execution to detect flaky generated tests. [CoverUp repository](https://github.com/plasma-umass/coverup). libFuzzer warns that nondeterminism makes fuzzing inefficient and persists concrete artifacts for later replay. [LLVM libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html). These do not prove that three repeats or any fixed count detects all flakiness; they establish that isolation, repeatability, and artifact replay are first-class acceptance dimensions.

## 1.6 A simple execution loop remains a serious baseline

**Established claim:** sophisticated agent topology must be compared against a strong, simple model-plus-tools execution loop. This is **very likely (80-90%)**, supported by SWE-agent/Agentless results and a recent replication warning, but exact rankings decay rapidly with model versions.

SWE-agent showed that an agent-computer interface enabling repository navigation, editing, and test execution materially affected performance; its paper reported 12.5% pass@1 on the then-current SWE-bench and 87.7% on HumanEvalFix. [SWE-agent paper](https://arxiv.org/abs/2405.15793), [official repository tutorial](https://github.com/SWE-agent/SWE-agent/blob/main/docs/usage/cl_tutorial.md). Agentless showed that a simpler staged workflow could be competitive without a large autonomous runtime. [FSE 2025 Agentless analysis](https://lingming.cs.illinois.edu/publications/fse2025.pdf).

A **recent/post-cutoff** 2026 replication reports that a plain current-LLM baseline outperformed four previously proposed LLM test-generation systems on line coverage, branch coverage, and mutation score across its experimental subjects. This is **likely (55-80%)** evidence that scaffolding gains can vanish as base models improve; it is one recent study and needs independent reproduction. [Primary preprint](https://arxiv.org/abs/2601.09695). The anti-overfit implication is strong: any harness component must beat the simplest bounded execution loop on this owner’s actual tasks, not an outdated paper baseline.

# 2. Promising but unproven

## 2.1 LLM-generated reproduction tests from issue text

**Confidence: likely (55-80%).** Evidence: TDD-Bench-Verified and SWT-Bench provide executable task definitions; Otter was accepted at ICML 2025; and e-Otter reports execution-feedback-driven gains. [TDD-Bench-Verified repository](https://github.com/IBM/TDD-Bench-Verified), [SWT-Bench](https://swtbench.com/), [e-Otter ICSE 2026 paper](https://hirzels.com/martin/papers/icse26-eotter.pdf).

The appealing use is to turn a natural-language issue into a regression test before editing production code. The unresolved risk is oracle circularity: the same model interprets the issue, writes the test, writes the fix, and judges the result. Self-consistency across those stages is not mechanical independence. The generated test becomes trustworthy only after it demonstrates a meaningful fail-to-pass transition, passes on the fixed state, survives isolation/replay, and ideally kills a reverted-fix or targeted mutant.

The reported e-Otter++ average fail-to-pass rate of 63% on TDD-Bench Verified is **UNVERIFIED outside the authors’ experiment; the settling experiment is to run its released generator on a preregistered sample of this owner’s historical issues, blind-review semantic failure reasons, and compare against a strong single-prompt baseline at equal model/cost budget**. The paper is a **recent/post-cutoff** 2025/2026 frontier item, so it is promising evidence rather than an established harness requirement. [e-Otter++ arXiv record](https://arxiv.org/abs/2508.06365), [ICSE 2026 paper](https://hirzels.com/martin/papers/icse26-eotter.pdf).

## 2.2 Iterative coverage-guided LLM test generation

**Confidence: likely (55-80%).** Evidence: CoverUp is peer-reviewed, open source, executes candidates, reports ablations, and substantially improved coverage over its named baselines in the reported benchmark. [FSE paper](https://doi.org/10.1145/3729398), [repository](https://github.com/plasma-umass/coverup).

The uncertainty is whether coverage-directed prompting adds value over a strong current-model prompt and targeted human/agent reasoning. The 2026 replication cited above reports that a plain newer-LLM baseline beat several older scaffolded techniques, including CoverUp, under its setup. [Primary preprint](https://arxiv.org/abs/2601.09695). Thus the reusable idea is “execute, locate uncovered behavior, retry narrowly,” not necessarily the full CoverUp implementation.

General superiority for this owner is **UNVERIFIED; the settling experiment is an equal-budget A/B test on 30 representative Python modules comparing (a) one-shot current-model generation, (b) two-turn execution repair, and (c) coverage-guided iteration, scored by compile/pass, changed-line branch coverage, targeted mutation kills, flake rate, maintenance review, elapsed time, and token cost**.

## 2.3 Mutation-guided LLM test synthesis

**Confidence: likely (55-80%).** Mature mutation engines establish the feedback signal, and recent LLM systems report gains when surviving mutants guide new tests. [PIT](https://pitest.org/), [Stryker](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/), [MUTGEN preprint](https://arxiv.org/abs/2506.02954).

The promising form is **targeted**: mutate changed conditions, boundary operators, return values, or reverted patch hunks, then ask the model for the smallest test that distinguishes the intended behavior. Whole-repository mutation on every turn is slow and produces equivalent/noisy mutants. MUTGEN’s reported benchmark advantage is **UNVERIFIED by an independent replication; the settling experiment is a stratified, equal-model comparison against vanilla prompting and existing human tests, with equivalent mutants adjudicated blind and wall-clock cost reported**.

## 2.4 LLM-authored properties and metamorphic relations

**Confidence: roughly even (45-55%).** Evidence for property/metamorphic execution is established, but evidence that an LLM can reliably invent correct, non-vacuous relations for arbitrary repository code is limited.

This is attractive for parsers, serializers, transformations, numerical code, query normalizers, and protocol state machines: round-trip, idempotence, permutation invariance, monotonicity, conservation, and reference-equivalence relations can generate many discriminating executions. Hypothesis can then search and shrink counterexamples. [Hypothesis documentation](https://hypothesis.readthedocs.io/en/latest/reference/api.html). The danger is a plausible but false invariant or a vacuous property that never constrains output.

Correct relation synthesis for this owner is **UNVERIFIED; the settling experiment is to have the model propose relations with explicit preconditions for 20 known modules, then require an owner/domain review plus mutation score against seeded relevant faults before any property enters the permanent suite**.

## 2.5 Execution-trace-assisted debugging

**Confidence: likely (55-80%) for bounded use; unlikely (20-45%) for a large always-on trace agent.** Evidence: self-debugging research shows execution state can help, but self-generated post-execution tests can bias the model and sometimes fail to improve basic tasks. [ACL 2025 paper](https://aclanthology.org/2025.acl-long.881.pdf).

The useful bounded pattern is to capture the smallest failure evidence—exception, assertion diff, relevant stack, local values, and command—then let the same agent make at most a small number of repairs. Unlimited “reflect until green” loops invite test weakening and repeated wrong hypotheses. The best retry budget for this harness is **UNVERIFIED; the settling experiment is replay of corpus-derived repair episodes with fixed 1-, 2-, and 3-repair budgets, measuring resolution, regression, and loop cost**.

## 2.6 Visual and external-effect verification

**Confidence: roughly even (45-55%).** Browser screenshots, accessibility trees, database reads, message-queue inspection, API GET-after-write, and file hashes can provide execution evidence when unit tests cannot observe the real user effect. The method is strong when the second signal reads the effect through a mechanically independent interface; it is weak when the agent merely looks at its own success banner.

Broad automation is **UNVERIFIED; the settling experiment is a task-family pilot in which each UI/external-effect task declares one action-path probe and one independent state/readback probe, followed by injected failures to confirm that each detector actually turns red**. This recommendation derives primarily from the local two-signal rule (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:22-37`) and live false-positive history (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:65-76`), not from a claim that screenshot judging is solved.

# 3. Hype, and the tell that gives it away

## 3.1 “Tests pass, therefore the patch is correct”

**Verdict: almost certainly not (1-5%) as a universal claim.** The tell is reporting only a green test command without showing baseline state, the specific fail-to-pass transition, broader pass-to-pass/regression behavior, or oracle provenance. SWE-bench Verified’s later audit is a concrete counterexample to treating an executable suite as infallible. [OpenAI 2026 audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/).

## 3.2 “High coverage means high-quality tests”

**Verdict: almost certainly not (1-5%) as a universal claim.** The tell is a coverage percentage with no assertions, mutation score, failure injection, or defect detection. TestGenEval reports coverage and mutation score separately; mature mutation systems exist precisely because execution reach and fault detection differ. [TestGenEval repository](https://github.com/facebookresearch/testgeneval), [PIT](https://pitest.org/).

## 3.3 “The agent wrote tests first, so the work is TDD and therefore safe”

**Verdict: very unlikely (5-20%).** The tell is process compliance substituted for behavioral evidence. A test written first can encode the wrong interpretation, pass vacuously, or fail for an irrelevant reason. The local rule mandates RED→GREEN and all three test types (`/local_disk0/codexwork/bundle/claude/rules/common/testing.md:25-38`) but does not demand semantic failure classification or a negative-control kill. TDD can be useful discipline; it is not a correctness proof.

## 3.4 “Self-generated tests make self-debugging autonomous”

**Verdict: unlikely (20-45%) in open-ended repository work.** The tell is one model producing the specification, oracle, implementation, and final judgment, followed by claims of independent verification. The ACL 2025 study finds bias from self-generated tests and differing outcomes between post-execution and in-execution paradigms even on self-contained Python problems. [ACL paper](https://aclanthology.org/2025.acl-long.881.pdf).

## 3.5 “A leaderboard score establishes a production harness”

**Verdict: very unlikely (5-20%).** The tell is no released raw trajectories, no environment failure accounting, no contamination analysis, no confidence intervals/repeated runs, or comparison against current simple baselines. SWE-bench’s official issue tracker shows continuing infrastructure/data disputes, while the benchmark maintainers’ FAQ distinguishes empty patches, evaluation errors, completions, and resolutions. [Official issues](https://github.com/swe-bench/SWE-bench/issues), [official FAQ](https://www.swebench.com/SWE-bench/faq/).

## 3.6 “More agents/verifiers inevitably improve verification”

**Verdict: unlikely (20-45%).** The tell is counting votes from agents that share the same prompt, model, source, or faulty detector as independent signals. The local harness has already documented that multiple agents sharing one lens do not constitute mechanical independence (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:34-37`) and that a false orchestrator-authored constraint propagated to roughly 15 agents (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160`). A second agent is useful only when it supplies a genuinely different oracle or probe.

## 3.7 “Environment-free learned verification can replace execution”

**Verdict: unlikely (20-45%) for this harness today.** The tell is calling model-scored plausibility “verification,” especially when the method is evaluated on a benchmark derived from familiar public patches. Static review is valuable triage but is not execution-grounded. Any recent claims that an environment-free verifier matches execution should remain lower-confidence until independently reproduced on contamination-controlled, owner-specific tasks with injected faults. The settling experiment would compare verifier ranking against actual clean-environment test outcomes and independent effect readbacks on a blinded historical set. This proposal is not adopted below.

# 4. Specific things this harness should adopt

## Adoption 1 — Replace blanket test ceremony with an evidence ladder

**Tag: CONFIG (settings/JSON only)**  
**Anti-overfit gate:** PASS. This changes rules on the existing instruction bus; it adds no runtime and explicitly removes universal scaffolding.

Replace `ALL required` unit/integration/E2E and default 80% coverage language at `/local_disk0/codexwork/bundle/claude/rules/common/testing.md:23-38` with a task-conditioned evidence ladder:

1. **Baseline:** identify the repository’s existing verification commands and run the smallest relevant known-positive control.
2. **Static/load:** compile, type-check, lint, or collect only where configured by the repository.
3. **Defect discriminator:** for a bug, show a test that fails on the pre-fix state for the expected semantic reason and passes on the candidate fix. For a new feature, show the closest equivalent negative control: reverted hunk, disabled implementation, contract violation, or targeted mutant.
4. **Focused verification:** run affected tests in a clean process.
5. **Regression verification:** run the repository-prescribed broader suite in proportion to risk.
6. **Independent effect:** for stateful/external work, read back the effect through a second interface.
7. **Receipt:** report commands, revisions, exit status, counts, duration, and artifact paths; report `UNVERIFIED` for skipped/unavailable stages.

It is **very likely (80-90%)** this improves signal per unit cost because it directly addresses the local mismatch between ceremony and semantic verification, and every step maps to mature execution mechanisms. The exact task-family routing is **UNVERIFIED; the settling experiment is a 50-task shadow run comparing current rules with the evidence ladder on defect escape, elapsed time, false completion, and owner corrections**.

## Adoption 2 — Make fail-to-pass plus patch-kill the default bug-fix protocol

**Tag: CONFIG (settings/JSON only)**  
**Anti-overfit gate:** PASS. It is an instruction/acceptance protocol using existing shell and test tools.

For every bug fix where a test harness exists:

- Save the proposed test before production edits when feasible.
- Execute it against the original revision/worktree and retain the exact failure signature.
- Reject failures caused only by collection, missing dependency, timeout, or unrelated exception unless that is the reported defect.
- Execute it against the candidate fix.
- Then revert/disable the relevant fix hunk or introduce one targeted semantic mutant and confirm the test becomes red again.
- Restore the patch and rerun focused plus broader regression tests.

The patch-kill stage guards against tests that happen to change state for irrelevant reasons. It is **very likely (80-90%)** to be more discriminating than RED→GREEN alone, based on the combination of SWT-Bench’s transition criterion and mature mutation semantics. [SWT-Bench](https://swtbench.com/), [PIT](https://pitest.org/). Whether automated hunk reversion is safe on dirty multi-agent worktrees is **UNVERIFIED; the settling experiment is to implement the protocol only in disposable worktrees first and inject interrupted runs to prove restoration**. Until settled, agents should use a separate temporary worktree/container or a semantic mutant that does not touch the owner’s live worktree.

## Adoption 3 — Emit a machine-readable verification receipt — UNVERIFIED hook fit; run the dual telemetry-path experiment first

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**  
**Anti-overfit gate:** PASS. A small hook/helper writes a bounded JSON/Markdown receipt; no daemon, database, or observability service.

Define one tolerant receipt schema:

```json
{
  "task_id": "...",
  "revision_before": "...",
  "revision_after": "...",
  "checks": [
    {"kind":"baseline|f2p|patch_kill|focused|regression|effect_readback",
     "command":"...", "cwd":"...", "exit":0, "duration_ms":0,
     "result":"pass|fail|unverified", "artifact":"..."}
  ],
  "known_positive_control":"pass|fail|unverified",
  "unverified":["reason..."],
  "verdict":"verified|partially_verified|not_verified"
}
```

The schema must allow partial results instead of recreating the corpus’s over-strict StructuredOutput failure mode: 846 errors in 3,694 calls, including 294 missing-field schema mismatches (`/local_disk0/codexwork/bundle/inputs/corpus.json:8964-8992`). Do not fan out strict required fields that turn an unavailable check into malformed output. Store raw stdout/stderr separately and hash/link it from the receipt.

It is **likely (55-80%)** that a receipt reduces unsupported “done” claims and makes later mining possible, because the present hook telemetry gap leaves behavior unmeasurable (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:133-147`). Hook payload fields and durable event locations are **UNVERIFIED; the settling experiment is exactly the pinned defect’s proposed dual probe: search the event ledger for a known-fired hook and independently search transcript system-reminder blocks, after first proving both detectors on known-present controls**.

## Adoption 4 — Mechanize known-positive controls for every load-bearing verifier

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**  
**Anti-overfit gate:** PASS. This is a shared fixture runner on the existing hook bus.

Each verifier/guard gets a small golden set containing at least:

- one true positive it must detect;
- one true negative;
- one use-versus-mention case;
- one negated case;
- one successful tool result whose field name contains failure-like text;
- one malformed/partial input that must fail closed only where safety requires it.

Run the relevant control after verifier changes and periodically before trusting a zero-result/absence finding. This directly operationalizes `/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:22-37` and replays the live false fires at `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-107`. It is **almost certain (90-99%)** to catch the already observed detector class because the known failures are concrete regression fixtures. Generalization to unknown semantic matcher failures is **UNVERIFIED; the settling experiment is mutation-testing the detector predicates and measuring whether the golden set kills seeded verb/payload, negation, key/value, and prose/code confusions**.

## Adoption 5 — Add targeted mutation/negative-control verification, not global mutation gates

**Tag: CONFIG (settings/JSON only)**  
**Anti-overfit gate:** PASS. Invoke a repository’s existing mutation tool or a minimal reversible hunk mutant through configured commands; do not build a general mutation service.

Routing:

- Java/JVM with PIT configured: mutate only changed classes. [PIT](https://pitest.org/).

## Bottom line

The best harness does not ask an agent to “be more certain.” It makes certainty expensive to fake. A completion claim should carry a compact chain of executable evidence: verified detector, baseline, discriminating transition, restored good state, focused and regression execution, independent effect readback where relevant, and an honest list of what was not run. Test synthesis is valuable when it strengthens one link in that chain; it is hype when generated volume, coverage, agent votes, or a green command substitutes for the chain.
