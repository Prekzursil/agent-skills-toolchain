# L06 — Anti-slop / quality-perfection enforcement: the “v2 with no v1” class

## Executive conclusion

The requested detector is not missing. The unpacked subject already contains two complementary checks: `dup-guard` searches before a new file is written for basename or primary-symbol collisions (`/local_disk0/codexwork/bundle/claude/hooks/dup-guard/guard.py:2-21`), while `wire-check` scans the session diff at Stop for unreferenced additions and names ending in `_v2`, `_new`, `_copy`, `_2`, or `V2` whose base appears absent (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/check.py:2-17,98-102,289-318`). Both are already folded into the local dispatcher: `dup-guard` is a PreToolUse check and `wire-check` is a Stop check (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:97-105,182-215`). Re-proposing either check would therefore fail the deduplication requirement.

The important defect is the loop closure. `wire-check` emits an advisory asking the same agent to decide whether the item is dead, wire it, delete it, or “confirm” it is intentional (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/check.py:321-359`). That is intrinsic same-context self-correction, rejected by the law of this unit. The upgrade below changes the output from a self-reflection prompt into a typed candidate that can be cleared only by an external receipt: a different mechanical analyzer, a clean execution, a fresh-context verifier, or the owner for genuinely ambiguous/high-impact retirement.

The existing detector is **almost certain (90-99%)** to detect its narrow synthetic class: its direct-invocation suite creates disposable Git repositories and includes both known-positive and known-negative controls (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/test_wire_check.py:24-61,73-147`), and I independently executed `python /local_disk0/codexwork/bundle/claude/hooks/wire-check/test_wire_check.py`; all eight cases passed, including `coupons_v2 with no v1 -> fires` and `coupons_v2 WITH live v1 -> silent`. This does **not** establish fleet precision or semantic correctness. It only validates the detector against its own explicit fixture contract.

The highest-value design is an evidence ladder inside the existing dispatcher slot, not a stronger suffix regex. A version-looking name becomes a *candidate*, never a defect. It advances through lineage, identity, reachability, behavior, and retirement checks. A candidate can be called an absurd duplicate/orphan only when two mechanically independent signals agree and each detector has passed a known-positive control. No automatic deletion is proposed.

## Scope and evidence discipline

### What was inspected

- Corpus tool counts show the environment is large and noisy: 108,121 Bash calls with 6,461 errors, 6,222 Glob calls with 829 errors, and 3,694 StructuredOutput calls with 846 errors (`/local_disk0/codexwork/bundle/inputs/corpus.json:13-20,79-84,103-108`). This supports cheap deterministic checks and tolerant receipts, not more agent-authored schema fan-out.
- The corpus reports 2,268 owner-correction *candidates* but explicitly warns that the detector is recall-biased and that 41/41 in a smoke sample were false positives (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10375`). I therefore use individual owner messages only as preference signals, never as verified correction counts.
- Owner-language candidates include “why did you stop proceed until you finish everything” (`/local_disk0/codexwork/bundle/inputs/corpus.json:10421-10426`), “you havent found any OCR? ... before you proceed with the main task” (`/local_disk0/codexwork/bundle/inputs/corpus.json:10709-10714`), a report that a reassigned task was already a duplicate, and another that a reassigned task was already completed (`/local_disk0/codexwork/bundle/inputs/corpus.json:10845-10854`). These are evidence that forgotten work and duplicate effort are painful, but their exact prevalence is not established.
- The corpus’s hooks section is unusable by construction: it says its known-positive control produced zero fires and that the whole section is NO DATA (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13264`). No conclusion below relies on hook-fire counts.
- Capability-use data itself exhibits names that look related but cannot safely be merged by spelling: `self-reflect` is recorded 18 times, `continuous-learning-v2` twice, `prompt-optimize` twice, and `prompt-optimizer` once (`/local_disk0/codexwork/bundle/inputs/corpus.json:13266-13314`). This is direct evidence that aliases, commands, and implementation identities must be reconciled before calling anything a duplicate.
- The live-defect input independently records four prose scanners confusing mention with use, including a tool sentinel treating a successful response as failure (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:52-82`), and seven wrong absence conclusions caused by unvalidated single probes (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`). This is the empirical reason every proposed closure below uses an external signal.

### Mechanically independent signals used for present-state claims

1. **Known-present control:** the existing `wire-check` fixture suite has positive `_v2` and unwired-symbol cases and negative live-v1, clean-repo, non-Git, and opt-out cases (`test_wire_check.py:73-147`). I ran it and obtained eight PASS results.
2. **Independent implementation signal:** the dispatcher manifest actually registers both `wire-check` and `dup-guard` (`_dispatch/manifest.json:97-105,182-215`), while the implementations describe distinct detection phases (`dup-guard/guard.py:10-21`; `wire-check/check.py:19-29`). This establishes presence without relying on test names alone.
3. **Independent operational limitation signal:** source code says `wire-check` analyzes only working-tree-versus-HEAD unless an external base is supplied (`wire-check/check.py:27-29,168-200`), while the dispatcher invokes it at Stop (`_dispatch/manifest.json:72-105`). A committed-earlier-in-session change can therefore fall outside its default window; this is a direct source limitation, not an inferred fleet failure.

## Findings, inferred-surprise first

### Finding 1 — Replace the self-verdict with a receipt state machine; do not replace the detector

**Improvement.** Convert `wire-check` output from “Is it dead ... confirm it” into `version_anomaly_candidate` records with states `suspect -> corroborated -> quarantined -> resolved|retired|accepted_exception`. The candidate may be created by the existing same-context hook, but it may advance only on an external receipt.

**What it is.** A small adjudication layer over the current checker. Each record contains `candidate_id`, `repo_id`, `session_start_ref`, `path`, `symbol`, parsed `base`, `suffix`, `detector_version`, `signal_a`, `signal_b`, `controls`, `authority`, `status`, and `next_probe`. The hook itself never says “duplicate”, “orphan”, “done”, or “safe to delete.”

**Why inferred.** The owner asked for mechanical detection and imposed the stronger rule that intrinsic self-correction fails. The present implementation expressly delegates the final judgment back to the agent that produced the work (`wire-check/check.py:343-347`). The defect input shows why that is unsafe: six initial wrong conclusions plus a seventh control-caught detector failure (`INPUT-known-harness-defects.md:111-129`). This is an inferred surprise because the capability superficially exists and its tests are green; the missing part is independent adjudication, not pattern coverage.

**How to build.** Extend `wire-check/check.py` rather than add a hook. On candidate creation, write one bounded event through the existing event-ledger/note bus; enqueue a deterministic `next_probe`. Accept only these closure receipts: (a) `git_lineage` plus `authority_resolution`; (b) `static_reachability` plus a clean consumer/entrypoint execution; (c) content/API equivalence plus a fresh-context reviewer verdict; or (d) explicit owner decision. Preserve the existing top-level try/except and exit 0 behavior (`wire-check/check.py:321-360`). Fold the work into the existing Stop dispatcher entry, so hook count remains unchanged. The dispatcher already runs checks in isolated threads and fail-opens per check (`_dispatch/dispatch.py:9-19,182-189`).

**EXTERNAL signal that verifies it.** A separate process reads the candidate file/event, performs the named probe from a clean context, and appends a signed/hash-linked receipt. Acceptance test: a candidate cannot transition when only the originating session emits “intentional”; it can transition when a disposable-repo command, fresh verifier, or owner receipt supplies the required second signal. A known-positive fixture must reach `corroborated`, and a known-negative `coupons_v2` with a documented migration must reach `accepted_exception`.

**SOTA.** Microsoft’s 18 human-AI guidelines say systems should make capability limits clear, support efficient dismissal/correction, scope service when uncertain, and explain why they acted ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/); [guideline summary](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)). NIST likewise treats validity/reliability as foundational and calls for ongoing test/monitoring and human intervention where a system cannot detect or correct errors ([NIST AI RMF trustworthiness](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This modifies the registered `wire-check` and ledger interface; it adds no hook or runtime.

**Value x effort:** transformative x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for candidate/receipt plumbing and shadow evaluation; confirm-first before any retirement or deletion.

**Confidence.** It is **very likely (80-90%)** that external receipts will remove the construction-level defect without losing the current narrow recall: the present controlled suite already validates candidate generation, while the live-defect input independently demonstrates the failure of same-context verdicts. Exact precision improvement is **UNVERIFIED**; the settling experiment is the seeded 40-case shadow evaluation specified in Finding 8.

### Finding 2 — Make “v2 with no v1” a lineage query, not a filename assertion

**Improvement.** Add provenance-aware lineage resolution to the existing `_VERSUF` branch.

**What it is.** For every version-looking path or symbol, resolve the predecessor across: current tree, rename/copy history, deleted paths, manifest/registry aliases, imports/exports, package entrypoints, and explicit `supersedes` metadata. Emit `NO_PREDECESSOR_OBSERVED` only when two independent channels fail after their known-positive controls pass; never emit “v1 does not exist” from `rg` alone.

**Why inferred.** Current `_base_is_live` searches changed-file stems and then accepts any word occurrence as liveness (`wire-check/check.py:239-248`); its `_v2` conclusion is therefore neither a real Git-history check nor a semantic predecessor check (`wire-check/check.py:289-315`). The canonical skills audit illustrates the danger of one-direction inventories: it found 35 skills missing from a manifest but zero orphan manifest entries and zero duplicate names (`inputs/audit-findings/A21.md:10-17,37-44`). That audit is a claim, not independently re-run here, but its evidence design—set equality in both directions—is the right template.

**How to build.** Record the session-start commit once (the existing `WIRE_CHECK_BASE` seam already exists at `wire-check/check.py:27-29,168-195`). For each candidate run: `git log --follow --name-status -- <path>` for history; a language-neutral authority resolver over known manifests/settings; and an import/registration graph. Store each command, exit code, bounded output hash, and detector control. Treat `v2` whose first Git appearance is the initial implementation as `MISLEADING_VERSION_NAME`, not an orphan; treat a rename with removed predecessor as `MIGRATION_WITH_LINEAGE`; treat two simultaneously authoritative implementations as `PARALLEL_VERSION_CANDIDATE`.

**EXTERNAL signal that verifies it.** Signal A is Git object/history output; signal B is the independently parsed authority/import registry. The test repo contains known rename, delete-and-replace, initial-v2, live-v1/live-v2, generated artifact, and false suffix (`sha256`, `base64`) controls. Absence may be reported only if the history probe first finds a known renamed fixture and the registry probe first finds a known registered fixture.

**SOTA.** Research on backward compatibility in human-AI teams found that an update can improve model accuracy while disrupting users’ learned understanding of prior behavior, harming team performance; version transitions therefore need continuity evidence rather than “newer is better” assumptions ([Bansal et al., *A Case for Backward Compatibility for Human-AI Teams*](https://arxiv.org/abs/1906.01148)). Horvitz’s mixed-initiative principles similarly require reasoning about uncertainty and the costs of poor guesses ([CHI 1999 paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a helper called by `wire-check`; retain its Stop slot.

**Value x effort:** high x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it in report/shadow mode; confirm-first for renames or consolidation.

**Confidence.** It is **very likely (80-90%)** that Git lineage plus authority resolution will distinguish important classes the current word search conflates, because they observe different substrates and the source exposes the current bounded heuristic. Coverage of reflection-heavy languages is **UNVERIFIED**; the settling experiment is the per-language fixture matrix in Finding 4.

### Finding 3 — Canonical identity before similarity: aliases are not duplicates

**Improvement.** Give every skill, command, hook check, MCP, schema, and deployed module a stable capability ID plus an alias/supersession table before performing content similarity.

**What it is.** A generated `capability-identity.json` derived from existing catalogs and registrations, with `id`, `kind`, `authority`, `aliases`, `implementation_path`, `deployment_paths`, `schema_version`, `supersedes`, and `compatibility_contract`. It is a reconciliation artifact, not another discovery system.

**Why inferred.** The corpus counts both `prompt-optimize` and `prompt-optimizer`, and separately counts `continuous-learning-v2` (`corpus.json:13300-13314`); spelling alone cannot establish whether these are command-to-skill aliases, parallel implementations, or duplicates. The harness already solved a similar identity problem for project memory: it documents that cwd-based IDs fragmented one logical repository and centralizes identity on remote/toplevel/pin (`claude/hooks/_shared/projid.py:2-25,218-250`). Reusing that design lesson is safer than adding fuzzy matching.

**How to build.** Extend the existing capability-catalog generator/installer input, not the semantic router. Normalize provider prefixes and explicit command-to-skill references, but never infer identity solely from embeddings or name distance. A proposed merge requires: same declared capability ID or explicit alias, equivalent authority role, and the behavioral evidence of Finding 4. Cross-provider deployed copies retain one ID with multiple materializations.

**EXTERNAL signal that verifies it.** Mechanically reconcile three independent views: generated identity inventory, provider registration/config, and a runtime `tools/list`/skill-resolution snapshot in a disposable session. Controls: a known command-to-skill alias must collapse; two deliberately same-named fixtures of different kinds must remain separate. A fresh-context verifier reviews only unresolved clusters, with artifact paths rather than raw transcript prefixes.

**SOTA.** Amershi et al. recommend making what an AI can do and how well it can do it clear, remembering recent interactions, and updating cautiously over time ([CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). The local project-identity resolver is concrete evidence that stable identity prevents fragmentation (`projid.py:4-18`).

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Generate an identity table from existing catalogs and registrations; no new execution plane.

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for identity/report generation; confirm-first for alias merges that change user-visible names.

**Confidence.** It is **likely (55-80%)** that explicit identity will eliminate a meaningful share of false duplicate candidates, based on observed alias-like corpus names and the already documented project-fragmentation fix. The actual share is **UNVERIFIED**; the settling experiment is a blinded manual label of every candidate produced across one week, compared with and without the identity table.

### Finding 4 — Require behavioral equivalence and consumer reachability before consolidation

**Improvement.** Separate “looks duplicated” from “can safely replace.” Use two orthogonal checks: semantic/API equivalence and consumer behavior.

**What it is.** A verifier adapter selected by artifact kind: Python/JS/etc. export/API extraction, JSON-schema comparison, hook stdin/stdout contract replay, skill frontmatter/routing checks, and MCP `tools/list` plus smoke calls. Text hashes catch exact duplicates; structural signatures catch equivalent wrappers; execution receipts determine whether consumers still work.

**Why inferred.** The current checker counts textual references and excludes definition lines (`wire-check/check.py:218-248`), but a public plugin entrypoint, reflection-loaded class, config-discovered skill, or subprocess command may be live without a source reference. Conversely, two wrappers may be textually different but behaviorally redundant. The audit found three incompatible “original goal” implementations across deployed harness, repo copy, and dormant hook (`inputs/audit-findings/B13.md:63-69`); this is an audit claim, so it motivates a verifier but is not treated here as independently proven fleet state.

**How to build.** Add adapter functions behind `wire-check`; unsupported kinds abstain. For source artifacts: extract exports with the language’s parser where available, otherwise emit `UNSUPPORTED`, never infer safety. For hooks: replay the same seeded payloads in separate processes against old/new targets and compare action, context, state delta, exit code, and timeout. For skills/MCP: resolve through the existing router/catalog and run a bounded contract probe. Consolidation is eligible only when (1) authority/lineage says one should supersede the other, (2) contract equivalence passes, and (3) a clean consumer journey passes after the candidate removal is simulated in a temporary worktree.

**EXTERNAL signal that verifies it.** A temporary worktree or disposable directory runs the consumer journey with one implementation masked, producing a command/test receipt. A different static parser produces the API/reachability receipt. Each lane has known-live and known-dead controls. Same-context prose is never a verification signal.

**SOTA.** Bansal et al. found explanations can increase acceptance whether the AI recommendation is correct or not, and did not by themselves improve complementary team performance; persuasive rationale is not a substitute for outcome evidence ([*Does the Whole Exceed its Parts?*](https://arxiv.org/abs/2006.14779)). NIST identifies ongoing testing/monitoring as the basis for validity and reliability ([NIST AI RMF](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement a narrow adapter registry and reuse existing tests/router; abstain outside supported artifact kinds.

**Value x effort:** transformative x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for temporary simulation and reporting; confirm-first before real consolidation.

**Confidence.** It is **very likely (80-90%)** that external contract replay prevents a class of unsafe “unused” conclusions that reference counting cannot settle, because it observes the consumer outcome directly. A universal cross-language adapter within 200 lines is **almost certainly not (1-5%)**, based on the number of supported source extensions in `wire-check` (`wire-check/check.py:53-74`); the design deliberately abstains and covers only the dominant verified kinds.

### Finding 5 — Detect source/deployment version skew as a first-class anomaly

**Improvement.** Add `DEPLOYMENT_SKEW` to the candidate taxonomy: canonical source, deployed copy, registry, and persisted data schema must agree on identity and compatibility.

**What it is.** A read-only parity receipt produced by the existing installer/SessionStart carrier: expected content fingerprint and schema version versus deployed module fingerprint, registration target, and persisted artifact header. This detects the more dangerous “v2 exists, but v1 still runs” class.

**Why inferred.** The source index builder declares schema version 2 and adds `mtime`, `importance`, `superseded_by`, `is_failure_head`, and `poisoned` (`agents/harness/recall_index.py:40-46,283-324`), while its consumer accepts the first JSON containing a `notes` list without checking schema (`agents/harness/modules.py:1583-1606`) and intentionally degrades missing fields to neutral values (`agents/harness/modules.py:1693-1710`). Audit units report that a live schema-v1 index was being served beside v2 code (`inputs/audit-findings/D05.md:5,30-31`; `E05.md:36-44`), but that runtime observation is **UNVERIFIED on this Linux bundle**; the settling experiment is to inspect the Windows deployed index header and run a controlled rebuild/read-back. The recommendation does not depend on that runtime claim: source permissiveness alone makes skew mechanically possible.

**How to build.** Fold a parity module into the existing shared SessionStart dispatcher or installer verification; do not create a new hook. Read only small headers/fingerprints. Emit one digest item only on mismatch, with exact expected/observed version, authority, and rebuild command. Fail open on parse/read errors but log `PROBE_ERROR`, never `MATCH` or `MISSING`. Include a known schema-v1 fixture and a known schema-v2 fixture.

**EXTERNAL signal that verifies it.** Signal A: deployed file hash/schema header read by the installer/parity process. Signal B: a clean consumer process loads a canary artifact and proves which fields affect output. The checker must recognize the seeded old fixture before it can declare a live artifact current or stale.

**SOTA.** Backward-compatibility research shows that updates need to preserve the user’s learned model of system behavior, not merely improve the new component in isolation ([Bansal et al.](https://arxiv.org/abs/1906.01148)). NIST’s AI RMF organizes risk work as Govern, Map, Measure, and Manage, emphasizing measurable lifecycle controls rather than undocumented inference ([NIST AI RMF Playbook](https://www.nist.gov/itl/ai-risk-management-framework/nist-ai-rmf-playbook)).

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold into the existing shared SessionStart/installer parity path; it replaces no component and adds no hook invocation.

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for read-only mismatch receipts; confirm-first for rebuild/migration when user data is involved.

**Confidence.** It is **almost certain (90-99%)** that schema/header parity can detect the seeded skew class, because both expected and observed values are deterministic. It is **likely (55-80%)** to catch materially harmful real drift in this harness, based on permissive consumer code and the audit’s independently described runtime observation; the Windows experiment above settles whether that instance is still live.

### Finding 6 — Quarantine with a tombstone and rollback receipt; never auto-delete

**Improvement.** Replace delete recommendations with a reversible retirement protocol that cannot drop a thread.

**What it is.** After two independent corroborating signals, move the candidate only in a temporary worktree for verification. If the clean consumer journey passes, propose a retirement patch containing an alias/redirect or explicit tombstone, `superseded_by`, reason, evidence receipts, and rollback command. The durable candidate remains open until post-change verification and a later fresh-session resolution check both pass.

**Why inferred.** The owner explicitly warns that bulk deletion of orphaned plugin directories was stopped because 110/169 had no live sibling and an allegedly orphaned directory was still read by a live skill. Locally, the open-loops system already exists specifically to resurface forgotten threads, limits output to 1-3 relevant loops, and suppresses duplicate replay on resume/compact/clear (`claude/hooks/open-loops/resurface.py:2-25,38-80`). Its store is fail-open and derives unresolved failures/dangling goals from the event ledger (`claude/hooks/open-loops/_common.py:2-26`). Building a separate retirement tracker would be duplication.

**How to build.** Represent the candidate as an event-ledger/open-loop item with `next_probe` and `rollback`. The existing open-loop resurfaces it only at a relevant boundary. Retirement execution uses edit-checkpoints/rollback already named in the brief. Generated files, caches, plugin installations, and user-authored assets default to `confirm-first`. Nothing is physically removed merely because a suffix or zero-reference check fires.

**EXTERNAL signal that verifies it.** Before retirement: consumer journey in a temporary worktree with the candidate masked. After retirement: the same journey in a fresh process plus a later SessionStart parity receipt resolving the open loop. Rollback is tested by restoring the checkpoint and reproducing the pre-change fingerprint.

**SOTA.** Microsoft’s human-AI guidance calls for efficient dismissal and correction and cautious updates over time ([Amershi et al.](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)). NIST’s human-AI appendix says oversight roles should be explicitly differentiated according to context and risk ([NIST AI RMF Appendix C](https://airc.nist.gov/airmf-resources/airmf/appendices/app-c-ai-risk-management-and-human-ai-interaction/)).

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Reuse event-ledger, open-loops, edit-checkpoints, and rollback; add a typed candidate kind/status convention.

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for quarantine simulation and evidence capture; confirm-first for deleting, retiring, or changing public names.

**Confidence.** It is **very likely (80-90%)** that reversible quarantine lowers deletion risk while preserving progress, because the verification occurs before mutation and rollback is an explicit receipt. The later SessionStart closure rate is **UNVERIFIED**; the settling experiment is ten seeded retirements across restart, compact, and resume, with zero silently dropped candidate IDs.

### Finding 7 — Deliver one boundary-timed digest, not another interrupting guard

**Improvement.** Surface only evidence-complete anomalies at a task/phase boundary; keep raw candidates silent in the ledger/digest.

**What it is.** A three-line maximum report: `candidate`, `why it matters`, and `next action`, with `dismiss`, `accept exception`, and `inspect evidence` affordances. No repeated warning for the same candidate/version unless evidence changes. Owner attention is reserved for irreversible or authority-ambiguous choices.

**Why inferred.** The owner makes prompt fatigue a first-class regression criterion. The existing dispatcher already consolidates many checks into one invocation and aggregates contexts (`_dispatch/dispatch.py:2-19`); adding another hook violates both architecture and the ~6-hook ceiling. The corpus contains repeated “why did you stop” candidates (`corpus.json:10421-10426`) and duplicate/completed task reassignment reports (`corpus.json:10845-10854`), suggesting that an interrupt that derails the main thread would trade one owner stressor for another.

**How to build.** Keep candidate creation silent. At existing Stop/TaskCompleted/SessionStart boundaries, have the current dispatcher emit only newly corroborated/high-value items. Use the existing background-digest reader and open-loop resurface entries already present in the SessionStart manifest (`_dispatch/manifest.json:53-69`). Record dismissal/correction as structured receipts; throttle by `(candidate_id, evidence_hash)`. Never ask the owner to adjudicate low-risk exact duplicates whose disposable consumer test passed and whose retirement is still only simulated.

**EXTERNAL signal that verifies it.** Shadow for one week and compare intervention timing against objective user behavior: dismissal, evidence-open, explicit correction, and task continuation, all correlated by candidate ID. The owner is asked only whether to promote the policy after receiving aggregate results. The report is successful only if it adds no mid-task interventions and no candidate thread disappears from terminal state.

**SOTA.** A 2026 five-day field study of proactive developer assistance observed 52% engagement at workflow boundaries, while mid-task interventions were dismissed 62% of the time; well-timed proactive suggestions also required less interpretation time ([Kuo et al., 2026](https://arxiv.org/abs/2601.10253)). This is a small 15-developer study, so transfer to this owner is **likely (55-80%)**, not certain. Horvitz’s mixed-initiative principles explicitly model user attention, uncertainty, and the cost of interruption ([CHI 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Change emission policy within existing dispatcher/digest/open-loop carriers; add no hook.

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for shadow telemetry and throttling; confirm-first to promote owner-visible policy.

**Confidence.** It is **very likely (80-90%)** that deduplicated boundary delivery creates fewer interruptions than the current per-Stop self-adjudication message, by construction and supported by the field study. Whether it improves this owner’s felt focus is **UNVERIFIED**; the settling experiment is the one-week shadow comparison above plus one explicit owner rating at promotion time.

### Finding 8 — Promote only after a seeded, independently graded anti-slop benchmark

**Improvement.** Turn the detector into an evaluated capability with a confusion matrix, abstention rate, and deletion-safety score.

**What it is.** A fixed 40-case suite: exact duplicate; near duplicate; alias; generated file; public entrypoint; reflection/config-loaded component; initial implementation unfortunately named v2; rename migration; deleted predecessor; two live versions; source/deployed drift; schema drift; dormant-but-supported compatibility shim; unused junk; built-but-not-wired UI; prose mention; negative sentence; test fixture; vendor/cache file; and interrupted work awaiting completion. Each case has expected candidate class, required probes, allowed autonomy, and forbidden mutation.

**Why inferred.** Current tests are necessary but self-authored and narrow: eight cases cover basic source references, `_v2`, route, clean repo, non-Git, and opt-out (`wire-check/test_wire_check.py:73-147`). The known-defect file shows pattern detectors repeatedly failed on prose, negation, and JSON field semantics (`INPUT-known-harness-defects.md:9-82`). The corpus owner-correction detector’s 41/41 false-positive smoke sample (`corpus.json:10371-10375`) shows why recall-biased metrics cannot justify promotion.

**How to build.** Extend the existing direct-invocation suite and harness eval bus, not StructuredOutput fan-out. ## Recommended mechanical decision procedure

This is the concrete algorithm the existing `wire-check` should implement. It is intentionally conservative:

1. **Candidate generation (same-context allowed, verdict forbidden).** Parse changed paths/symbols for version suffixes and collision hints. Snapshot the session-start ref. Emit `SUSPECT`, never “duplicate/orphan.”
2. **Detector control.** In the separate verifier process, prove the lineage detector can find a seeded rename and the authority detector can find a seeded registered entry. If either control fails, emit `PROBE_ERROR` and stop; fail open.
3. **Canonical identity.** Resolve explicit capability ID, alias, materialization, generated/vendor status, and authority. If two names share an explicit identity, classify `ALIAS_OR_MATERIALIZATION`; do not delete.
4. **Lineage.** Query Git history and explicit `supersedes`. Classify initial-v2, rename, replacement, parallel version, or unknown.
5. **Reachability.** Compute static import/config/registry reachability using the relevant adapter. Unsupported/reflection-heavy targets abstain.
6. **Behavior.** In a temporary worktree, mask the candidate (or predecessor) and run the smallest consumer journey. Preserve command, exit, timeout, output hash, and state delta.
7. **Independent adjudication.** Exact mechanical cases close from the two receipts. Ambiguous cases go to a fresh-context verifier. Only irreversible/high-impact ambiguity reaches the owner.
8. **Quarantine and continuity.** Simulate retirement, attach rollback and tombstone, and create an open-loop item. Nothing is deleted.
9. **Post-change proof.** Fresh process reruns the consumer journey; a later SessionStart parity check confirms resolution. Only then mark `resolved`.

Terminal classes should be explicit: `EXACT_DUPLICATE`, `BEHAVIORAL_DUPLICATE`, `ALIAS_OR_MATERIALIZATION`, `MIGRATION_WITH_LINEAGE`, `INITIAL_MISLEADING_VERSION_NAME`, `PARALLEL_SUPPORTED_VERSION`, `DEPLOYMENT_SKEW`, `UNREACHABLE_CANDIDATE`, `INTERRUPTED_INCOMPLETE_WORK`, `ACCEPTED_EXCEPTION`, `UNSUPPORTED`, and `PROBE_ERROR`. “No v1” is evidence text, not a terminal class.

## Hook-ceiling, prompt-fatigue, fail-open, and anti-overfit compliance

- **Hook ceiling:** zero new hook invocations. Findings 1, 2, and 4 extend the existing `wire-check` Stop check. Finding 5 folds into the existing shared SessionStart/installer carrier. Findings 6 and 7 reuse event-ledger, open-loops, background-digest, edit-checkpoints, and rollback.
- **Prompt fatigue:** raw candidates are silent; only corroborated items appear once at a workflow boundary, keyed by evidence hash. Low-risk work stays autonomous and reversible.
- **Never drop a thread:** every nonterminal candidate has `next_probe`, owner, terminal-state enum, and an open-loop/event-ledger identity. Restart/compact/resume fixtures must prove survival.
- **Fail open:** checker/probe exceptions produce `PROBE_ERROR`, never absence, success, block, or deletion. Production hooks retain try/except and exit 0. Quality enforcement occurs through evidence-gated promotion/retirement, not a blocking hook.
- **Anti-overfit gate:** all proposals ride existing hook/dispatcher, event-ledger/open-loop, installer/catalog, test, and rollback buses. This report explicitly rejects a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, and guardrail framework. A deterministic fixture suite and small verifier adapters are sufficient.
- **No reimplementation:** `dup-guard`, `wire-check`, capability catalog, semantic router, event ledger, `note.py`, open loops, and rollback remain authoritative. The new work is independent closure and evidence typing.
