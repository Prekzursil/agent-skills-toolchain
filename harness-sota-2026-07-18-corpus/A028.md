## Runtime authority model

The phrase “which one wins” needs precision because rules and settings are not peers in a merge algorithm:

- User rules under `~/.claude/rules/` enter model context. User-level rules load before project rules, and path-scoped rules load when matching files are read. Claude's official documentation says these are context, not strict enforcement, and contradictory instructions may be followed arbitrarily ([Memory/rules documentation](https://code.claude.com/docs/en/memory)).
- `~/.claude/settings.json` is parsed by the host. Its permission mode determines whether the host prompts, and its hook registrations determine which lifecycle commands execute. A prose rule cannot synthesize an unregistered hook or force a permission prompt the host has skipped ([Permissions](https://code.claude.com/docs/en/permissions), [Hooks](https://code.claude.com/docs/en/hooks)).
- Consequently, **settings win for host behavior**. Rules can still cause the model to invoke a formatter manually or avoid a dangerous action voluntarily, but that is not equivalent to a permission boundary or lifecycle hook.
- Other settings scopes can override this user file: project/local/managed settings and runtime flags may change the effective value. That does not erase the user-level duplicate-authority defect; it means a live `/permissions` or resolved-settings probe is required to describe a particular project session. Official settings documentation describes hierarchical sources and project/local precedence ([Settings](https://code.claude.com/docs/en/settings)).

### Runtime winner

The change is **very likely (80-90%)** to restore coherence because it directly makes the host's default match the prose rule and preserves explicit allow/deny rules; evidence is the documented permission-mode table and the two literal settings keys. An alternative is to rewrite the rule to endorse permanent bypass. I reject that resolution because it would make the two authorities coherent by deleting the safety intent, while official documentation limits this mode to isolation and this snapshot grants both drive roots.

## Finding 3 — Rule-published hook JSON conflicts with the active/native schema

### Dart: object matcher versus string matcher

Rule authority, `rules/dart/hooks.md:19-33`, verbatim core:

> `"PostToolUse": [`  
> `  {`  
> `    "matcher": { "tool_name": "Edit", "file_paths": ["**/*.dart"] },`  
> `    "hooks": [`  
> `      { "type": "command", "command": "dart format $CLAUDE_FILE_PATHS" }`  
> `    ]`  
> `  }`  
> `]`

Active settings authority, representative working group at `settings.json:334-342`:

> `{`  
> `  "matcher": "Edit|Write|MultiEdit",`  
> `  "hooks": [`  
> `    {`  
> `      "type": "command",`  
> `      "command": "python \"C:/Users/Prekzursil/.claude/hooks/per-edit-check/check.py\"",`  
> `      "timeout": 12,`  
> `      "statusMessage": "Per-edit validation"`  
> `    }`  
> `  ]`  
> `}`

Claude's current official hook reference defines `matcher` as a string matched against `tool_name`; narrow path filtering belongs in the handler `if` field (for example `Edit(*.ts)`) or inside the command using `tool_input.file_path` ([Hooks reference](https://code.claude.com/docs/en/hooks)). The Dart object-valued matcher is not the documented settings schema.

### Web: handler fields placed at matcher-group level

The four web PostToolUse examples repeat this shape. For example, `rules/web/hooks.md:25-36` says:

> `"PostToolUse": [`  
> `  {`  
> `    "matcher": "Write|Edit",`  
> `    "command": "pnpm prettier --write \"$FILE_PATH\"",`  
> `    "description": "Format edited frontend files"`  
> `  }`  
> `]`

The lint, type-check, CSS-lint, PreToolUse file-size, and Stop examples at `rules/web/hooks.md:43-123` likewise put `command` directly on the matcher group and omit the inner `hooks` handler array and handler `type`.

The active settings use the documented three levels: event, matcher group, then one or more typed handlers (`settings.json:81-529`). Official documentation explicitly defines those three levels and provides the same nested shape as the active settings ([Hooks reference](https://code.claude.com/docs/en/hooks), [Hooks guide](https://code.claude.com/docs/en/hooks-guide)).

### Concrete collision and runtime winner

During Dart or frontend work, follow the rule's “Recommended Hook Configuration” by copying its object into user or project settings. That puts a second representation of the `hooks` key beside the known-working active representation. The host parser, not the prose, controls runtime. The malformed handler structure cannot register the intended command under the documented schema; the Dart matcher cannot perform the documented match.

**UNVERIFIED:** whether the owner's exact future Windows CLI rejects these shapes at load, silently ignores the unknown fields, or tolerates a backward-compatibility form cannot be tested on this Linux snapshot. The settling experiment is to place each sample in an isolated temporary project `.claude/settings.local.json`, start the installed Windows Claude Code, inspect `/hooks`, and edit a disposable matching file while recording whether the handler executes. This UNVERIFIED detail does not weaken the conflict: the samples contradict both the active known-working structure and the current official schema; it only affects the failure mode.

Confidence that the examples conflict with the supported schema is **almost certain (90-99%)**, based on two independent signals: the active 449-line hook configuration consistently uses nested typed handlers, and official documentation specifies the same three-level shape. Confidence about reject-versus-ignore behavior is **roughly even (45-55%)** because no live fixture was run.

### Minimal resolution — BUILD-SMALL

Rewrite the Dart and web examples into the current nested handler schema:

- string matcher `"Edit|Write"` at group level;
- inner `"hooks": [{ "type": "command", "command": "..." }]`;
- file filtering via handler `"if": "Edit(*.dart)|Write(*.dart)"` where supported, or robust parsing of `tool_input.file_path` from stdin;
- project-local executables, as the web rule already sensibly requires.

This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. It changes documentation/config examples only, uses Claude's native hook bus, and passes the anti-overfit gate.

The corrected samples are **very likely (80-90%)** to register on current Claude Code because they match both the active settings and official examples. The exact `if` expression for all Dart tool/path variants is **UNVERIFIED** until the isolated Windows `/hooks` fixture above executes it; omit `if` and filter stdin in the script if that fixture fails.
