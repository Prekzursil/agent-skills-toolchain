# P2B11 — Competitive teardown: OpenAI Codex CLI

**Unit:** P2B11  
**Research date:** 2026-07-18  
**Subject:** OpenAI Codex CLI, with the installed stable build `codex-cli 0.144.5` as the local reference point  
**Question:** What does current Codex CLI do that this owner's cross-tool harness does not, what is worth porting, and what is worse and must not be copied?

## Executive verdict

Codex CLI is no longer merely a thin terminal loop around shell and patch tools. In the current stable line it is a coherent local agent runtime: a model/function-call loop, automatic history compaction, persistent rollouts and goals, optional two-stage local memory, MCP and plugin loading, OS-enforced sandboxing, structural command policy, lifecycle hooks, native subagent threads, machine-readable automation, and a read-only review mode. The official configuration reference marks persisted goals and multi-agent collaboration stable and on by default, while local memories remain off by default [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). The installed `0.144.5` exactly matches the latest stable GitHub release published 2026-07-16; the release page identifies newer `0.145.0-alpha.*` builds as prereleases [OpenAI Codex releases](https://github.com/openai/codex/releases).

The central finding is not “replace our harness with Codex.” This owner already runs Codex as one provider inside a stronger cross-tool system, and the local Codex configuration has enabled nearly every experimental feature while simultaneously setting `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`C:\Users\Prekzursil\.codex\config.toml:6-7,82-126`). Claude is likewise configured with `defaultMode: "bypassPermissions"` and drive-wide `C:`/`D:` access (`C:\Users\Prekzursil\.claude\settings.json:26-75`). The best Codex ideas therefore divide into three groups:

1. **Adopt now on existing native buses:** enforced sandbox boundaries, destination-scoped network policy, least-privilege subagent profiles, and required-MCP startup semantics.
2. **Port as small deterministic mechanisms:** hash-bound hook trust, structurally tested command rules, a persisted goal state machine, bounded structured fan-out, hook-output truncation/spill, and durable hook telemetry.
3. **Do not copy:** autonomous second-model approval review, a second auto-generated memory authority, deep recursive delegation, and a general durable-execution runtime. Those are exactly the elaborate components excluded by the anti-overfit gate.

It is **almost certain (90-99%)** that enabling native sandboxing and fixing permissions posture will reduce blast radius without requiring a new runtime: both Codex and Claude documentation describe OS-level filesystem/network enforcement, while the two live configurations independently prove it is disabled/bypassed here. It is **very likely (80-90%)** that structural command rules and hook telemetry will reduce actual harness error and false-conclusion rates: Codex supplies mechanically testable rule examples and typed JSONL lifecycle events, while the pinned defects independently show prose/command confusion and absent hook observability (`INPUT-known-harness-defects.md:D1-D3`). Exact effect size is UNVERIFIED; the settling experiment is the replay matrix specified in “Experiments before rollout.”

## 1. Agent loop

### Codex mechanism

Codex's current loop is explicit in source. `run_turn()` builds skill/plugin injections, runs session and prompt hooks, prepares normalized history, sends a sampling request, and interprets the model response as either function calls requiring another sampling step or an assistant message completing the turn. Tool calls are routed through a `ToolRouter`; follow-up is driven by model requests, queued user input, and context-window state [current `session/turn.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/session/turn.rs). This is a conventional ReAct/function-call loop, not a planner/executor graph.

That minimality is a strength. It rides one loop and adds capabilities through tools, hooks, skills, and configuration. This aligns with the anti-overfit gate and with the brief's reminder that a roughly 100-line loop can score strongly. The evidence assembled for this unit does not establish a benefit from copying a second orchestration runtime; such a benefit is **unlikely (20-45%)** because the proposed deltas all fit existing tools, hooks, skills, configuration, and ledger buses. The exact comparison is UNVERIFIED; a matched benchmark of the existing bus against an app-server replacement would settle it, but building that replacement merely to test it fails the anti-overfit gate.

Codex also exposes stable persisted goals with automatic continuation (`features.goals`) [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). The current session tool surface independently includes create/get/update goal operations, and the live config enables goals at `C:\Users\Prekzursil\.codex\config.toml:111`. A goal is distinct from a plan: it persists the objective and terminal condition, while plan items are turn-local progress structure.

### Our comparison

Our behavior contract already has stronger anti-loop semantics than stock Codex: terminal `SUCCESS/FAILED` markers, a two-strikes pivot, goal reinjection, structured handoff, and a generator-critic honesty check (`C:\Users\Prekzursil\.claude\AGENTS.md:22-83`). Codex's core loop does not replace these.

The gap is mechanical goal state. Our goal is model-followed text plus a hook injection, not a provider-neutral object with one active objective, explicit status, and automatic continuation. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): persisted goal record.** Add `{goal_id, objective, created_at, status, blocker, terminal_evidence}` to the existing event ledger. SessionStart loads it; PreToolUse re-injects a compact form; Stop refuses a false “complete” transition unless terminal evidence exists. This is **very likely (80-90%)** to reduce goal drift because the current contract already relies on goal reinjection and Codex demonstrates the state model; the improvement magnitude is UNVERIFIED, settled by an A/B replay of 50 long sessions measuring owner corrections for abandoned objectives.

### What not to copy

Do not replace the loop with the Codex app-server as a second orchestration runtime. App Server is useful as a protocol surface, but a provider-neutral harness already exists. A second runtime violates the explicit anti-overfit exclusion and would duplicate lifecycle, persistence, and tool routing.

## 2. Context management

### Codex mechanism

Codex retains ordered response items, normalizes unsupported media before prompts, keeps tool-call/output pairs coherent, estimates tokens, and tracks world-state diffs [current context history](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/context_manager/history.rs). Its compactor replaces history with a summary while deliberately reinjecting initial context at the correct position; the source caps the compacted user message at 20,000 tokens and runs PreCompact/PostCompact hooks [current `compact.rs`](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs). The config exposes both an auto-compact threshold and whether it counts total context or the body after the carried prefix [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

The subagent system is also a context-management feature: independent exploration, tests, and logs stay in child threads and only summaries return to the parent. Official guidance explicitly names context pollution/rot and recommends read-heavy parallel work while warning about parallel writes [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Codex adds three pragmatic controls worth retaining conceptually:

- skill metadata is injected separately from full skill content;
- oversized hook output is reduced to roughly 2,500 model-visible tokens while full text is saved to a temporary file and represented by head/tail plus path [Hooks](https://learn.chatgpt.com/docs/hooks);
- noninteractive mode separates progress on `stderr` from final output on `stdout`, and can emit every lifecycle item as JSONL [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

### Our comparison and port

Our harness already uses compaction hooks, structured subagent handoffs, basic-memory recall after compaction, and output compression hooks (`C:\Users\Prekzursil\.claude\settings.json:313-399`; `C:\Users\Prekzursil\.codex\AGENTS.md:43-46,62-85`). It is better than stock Codex at preserving explicit decisions across providers.

The missing useful piece is a single deterministic output-budget contract for hooks and monitors. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): bounded hook envelope.** For every hook output, store the full sanitized payload as a ledger artifact; inject at most a fixed token/byte budget using head + tail + hash + path; include `truncated=true`. This is **very likely (80-90%)** to prevent a verbose guard from polluting context because Codex implements the same bounding pattern and the corpus shows large tool/error payloads. UNVERIFIED whether every Claude hook event accepts an artifact path in model-visible context; a 5 KB/50 KB/500 KB synthetic output probe settles it.

### Where Codex is worse

Compaction still has a source-level TODO: pre-turn compaction does not yet estimate pending context diffs and new user input before deciding whether they cross the threshold [current `session/turn.rs`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/session/turn.rs). An upstream report on 0.117.0 described context overflow when custom limits were set, but that reproduction is not proof against installed 0.144.5 [issue #16033](https://github.com/openai/codex/issues/16033). **UNVERIFIED on 0.144.5;** the settling experiment is a disposable 0.144.5 session with a small explicit limit and one turn that accumulates tool output across many calls, asserting that auto-compaction fires and the task continues. Do not tune production thresholds until that passes.

## 3. Memory

### Codex mechanism

Local memories are off by default and independently controllable for “use old memories” and “generate future memories.” Eligible idle, non-ephemeral root sessions are extracted in parallel into structured raw memory and rollout summaries; generated fields are secret-redacted; failures use leases and retry backoff. A serialized second phase ranks memories by usage/recency, writes `raw_memories.md` and per-rollout summaries, then launches a no-network/no-approval local consolidation subagent [memory pipeline README](https://github.com/openai/codex/blob/main/codex-rs/core/src/memories/README.md). The user can exclude sessions polluted by MCP/web/tool-search context and require a minimum remaining rate-limit percentage [Memories](https://learn.chatgpt.com/docs/customization/memories).

This is a sophisticated implementation, but sophistication is not automatically an advantage. Codex's memory is local to `~/.codex`; official docs explicitly advise keeping required guidance in AGENTS.md rather than memory. Our basic-memory vault is intentionally cross-tool canonical and separates semantic facts from the objective event ledger (`C:\Users\Prekzursil\.codex\AGENTS.md:62-85`). The live config nevertheless enables Codex memory generation and use (`C:\Users\Prekzursil\.codex\config.toml:103,404-406`), creating two authorities.

### Selective port, not wholesale adoption

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): memory provenance gate.** Add three fields to every proposed basic-memory write: `external_context_used`, `secret_scan_passed`, and `evidence_refs`; suppress automatic capture when external content influenced the session unless the user/agent explicitly confirms it. Also gate any background capture on current quota. This is **likely (55-80%)** to reduce contaminated or stale memory because Codex independently treats external context as pollution and redacts generated fields; exact benefit is UNVERIFIED, settled by replaying known prompt-injection/tool-result fixtures through the write path and checking zero unauthorized durable facts.

**CONFIG (settings/JSON only): disable Codex auto-generation after the canonical policy is enforced.** Set `memories.generate_memories = false` and preferably `memories.use_memories = false`, retaining `/memories` only for deliberate experiments. It is **very likely (80-90%)** this removes contradictory memory writers without reducing canonical recall because basic-memory and the ledger already own those roles; a 30-session recall comparison settles any quality loss.

### What not to copy

Do not port the two-phase database/lease/consolidation-agent pipeline. It is both a second memory system and a durable execution engine, two explicitly rejected components. It also spends model quota invisibly and introduces a trained/model critic-like consolidation step. Our smaller provenance gate captures the useful safety lessons without importing the machinery.

## 4. Tools and MCP handling

### Codex mechanism

Codex supports built-in shell, unified exec, `apply_patch`, web/image tools, plans, local functions, MCP tools, apps/connectors, and plugin-supplied surfaces. MCP supports STDIO, Streamable HTTP, bearer auth, OAuth, server instructions, and shared configuration across CLI/IDE/desktop [MCP documentation](https://learn.chatgpt.com/docs/extend/mcp). Project MCP configuration is loaded only for trusted project layers. Noninteractive runs can mark an MCP server `required = true`; failed initialization then aborts instead of silently continuing [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

Tool calls share a router and hook path. PreToolUse/PostToolUse cover shell, unified exec, apply_patch, MCP, and other local functions, but hosted WebSearch is excluded and specialized paths may opt out [Hooks](https://learn.chatgpt.com/docs/hooks). MCP/app tools can advertise destructive or open-world behavior; Codex can require approval per app/tool and always requires approval for a destructive annotation under the documented security model [Agent approvals](https://learn.chatgpt.com/docs/agent-approvals-security).

### Our comparison and ports

Our MCP breadth is larger, but reliability is worse. The corpus records a dead Tavily connector still being called, schema mismatches, connection refusals, and tool timeouts; the current Codex config also carries many static servers (`C:\Users\Prekzursil\.codex\config.toml:132-147,480-630`). Breadth without liveness is not an advantage.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): required-capability preflight.** A task declares zero to three required capabilities, resolves each to one server, performs MCP initialize + tools/list, and fails before model work if none is live. Optional servers stay fail-open. This is **almost certain (90-99%)** to prevent the exact “dead MCP still called” class because successful handshake is a direct precondition; the remaining uncertainty is only operational overhead. Settle overhead with 100 cached and uncached preflights.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): annotation-aware approval adapter.** Normalize MCP `readOnlyHint`, `destructiveHint`, and `openWorldHint` into the existing PermissionRequest event; destructive always asks/blocks, read-only may run inside policy, missing annotations remain conservative. It is **likely (55-80%)** to reduce both unsafe auto-approval and needless prompts; many existing servers may omit or misuse annotations, so the recommendation remains conditional on an inventory experiment.

Do not port more MCP servers. ToolSearch is already enabled in Claude (`C:\Users\Prekzursil\.claude\settings.json:17,46`) and is extremely reliable in the corpus—5,091 calls, four errors (`corpus/corpus.json:87-92`). The right move is liveness-weighted discovery and smaller active loadouts.

### Where Codex is worse

- `codex mcp list` establishes configured state, not successful backend handshakes. Required initialization helps only when explicitly set.
- Local STDIO MCP processes can multiply with subagent fan-out; this is resource coupling, not free parallelism.
- Hosted tools can bypass the local hook path. Codex itself warns that hooks are a useful guardrail, not a complete enforcement boundary [Hooks](https://learn.chatgpt.com/docs/hooks).
- Code mode is under development and off by default upstream, yet enabled locally (`C:\Users\Prekzursil\.codex\config.toml:104`). Do not depend on it for safety enforcement.

## 5. Permission model

### Codex mechanism

Codex cleanly separates technical sandbox boundaries from approval policy. The default local posture is workspace write, no network, and approval for crossing boundaries. Commands and subprocesses inherit OS-level restrictions; native Windows, WSL2/Linux bubblewrap, and macOS Seatbelt are supported [Sandbox](https://learn.chatgpt.com/docs/sandboxing). The network proxy can allow/deny individual domains and restrict local binding, upstream proxies, and Unix sockets [Agent approvals](https://learn.chatgpt.com/docs/agent-approvals-security).

Codex's experimental `.rules` language is the most transferable mechanism in this teardown. A `prefix_rule` operates on argv, combines overlapping rules by the most restrictive result, accepts inline `match` and `not_match` cases validated at load time, and uses tree-sitter to split safe shell chains so `git add . && rm -rf /` cannot inherit the allow decision for `git add` [Rules](https://learn.chatgpt.com/docs/agent-configuration/rules). `codex execpolicy check` produces the effective decision and matching reasons without executing the command.

Hook definitions themselves are trust-scoped: Codex hashes each non-managed command hook, skips new/changed definitions until reviewed, and exposes `/hooks` to inspect sources and trust/disable them. Managed hooks can be pinned and user/project/plugin hooks excluded [Hooks](https://learn.chatgpt.com/docs/hooks).

### Our comparison and ports

The effective local posture is worse than Codex defaults on both providers: Codex grants full access with no approvals, and Claude bypasses permissions with both drives mounted (`C:\Users\Prekzursil\.codex\config.toml:6-7`; `C:\Users\Prekzursil\.claude\settings.json:26-75`). This conclusion has two mechanically independent signals. It does not depend on reading model instructions.

**NATIVE (Claude Code already does this; we just enable it): sandbox first.** Claude Code natively provides OS-enforced filesystem and domain-scoped network isolation through Seatbelt/bubblewrap/WSL2, while its documentation says native Windows support is planned rather than present [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing). On this Windows owner, use Codex's native Windows sandbox and run Claude's shell lane through WSL2. A native-Windows Claude sandbox would be **UNVERIFIED and cannot be claimed**; the settling experiment is upstream release support plus a deny-write/deny-network probe. It is **almost certain (90-99%)** the documented WSL2 path enforces a smaller blast radius; compatibility with this owner's Windows-native reverse-engineering tools is **roughly even (45-55%)** because those tools intentionally cross the Windows/WSL boundary. Use per-tool exclusions rather than abandoning the sandbox.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): structural execpolicy core.** Port only argv normalization, safe-chain splitting, most-restrictive-wins, inline positive/negative fixtures, and a dry-run checker. This directly addresses D1's use-versus-mention defect: markdown payload text is never argv execution. It is **very likely (80-90%)** to eliminate the recorded command-guard false positives because the discriminator changes from substring payload matching to executable structure. The settling regression suite is all D1 fixtures plus true destructive controls.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): hook trust manifest.** Hash `{event, matcher, command, script_sha256}` at install/reconcile; unknown hashes do not execute for project/plugin scope; managed user-level hooks remain policy-trusted. This is **likely (55-80%)** to prevent silent execution of changed cloned-repo hooks. The exact benefit is UNVERIFIED until a trusted hook is modified and an untrusted repository hook is introduced in a disposable checkout.

### Auto-review: capable but rejected

Codex can route eligible sandbox escalation requests to a separate reviewer agent that sees a compact transcript and exact action, may perform read-only checks, and returns allow/deny rationale without widening the sandbox [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review). This is a trained/model critic at the permission boundary. **CONFIG (settings/JSON only): keep `approvals_reviewer = "user"`.** Do not copy or enable auto-review. It violates the explicit trained-critic exclusion, consumes capacity, and can only probabilistically review a decision that structural sandbox/rules can enforce deterministically. The live config already keeps the user reviewer (`C:\Users\Prekzursil\.codex\config.toml:16`).

## 7. Multi-agent support

### Codex mechanism

Current Codex releases enable subagents by default. The root can spawn, steer, interrupt, wait for, inspect, and close child threads; `/agent` switches among them. Custom TOML agents can select model, reasoning effort, sandbox, MCP servers, and skills. Defaults are six open threads and depth one; children inherit the parent turn's live sandbox/approval overrides. A dedicated experimental CSV path creates one worker per row, requires exactly one `report_agent_job_result`, enforces concurrency/runtime, and exports status/error/result metadata [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Claude is not simply behind. It has isolated subagents and agent teams with peer communication; custom agents support tools, disallowed tools, model, permission mode, MCP, hooks, max turns, skills, memory, effort, background execution, and worktree isolation [Claude subagents](https://code.claude.com/docs/en/sub-agents). Stock Claude subagents cannot recursively spawn other subagents, whereas Codex can raise `agents.max_depth`.

### Our comparison and port

The owner already uses fan-out heavily, and the corpus shows Agent itself is reliable: 1,745 calls and 1.15% errors (`corpus/corpus.json:119-124`). The weak point is structured aggregation: StructuredOutput fails 22.9%, with repeated mandatory-field mismatch (`corpus/corpus.json:103-108,8964-8992`). Codex's best idea is not “more agents”; it is the terminal row-result protocol.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): ephemeral batch contract.** Input is CSV/JSONL; one row equals one bounded child task; each child must emit one terminal envelope `{item_id,status,result,error,evidence}`; missing result becomes an explicit error; parent writes one aggregate artifact. Use existing Task/Agent tools and `longrun`, with no new daemon and no SQLite requirement. This is **very likely (80-90%)** to reduce ambiguous partial completion because every row has a terminal state. It is **likely (55-80%)** to reduce schema errors if the envelope stays minimal and `result` is free-form; settle both with a 100-row replay against the corpus's failure-producing schemas.

### What not to copy

The live Codex config raises `max_depth` to 8 (`C:\Users\Prekzursil\.codex\config.toml:77-80`), far beyond upstream's cautious default of 1. This is worse. Recursive fan-out multiplies context, MCP processes, permissions, and coordination, while the user's own brief warns against elaborate scaffolding. **CONFIG (settings/JSON only): restore `agents.max_depth = 1` unless a task explicitly proves recursive delegation is necessary.** It is **very likely (80-90%)** this reduces runaway fan-out and resource multiplication; the cost to task quality is UNVERIFIED and settled by comparing bounded benchmark tasks at depth 1 versus 2, never 8.

Do not build a durable job engine. The ephemeral adapter deliberately omits leases, retries across restarts, and a database. If a batch needs durable execution, use CI or an existing scheduler rather than turning the harness into one.

## 8. Verification and self-check

Codex has five concrete verification surfaces:

1. `/review` inspects uncommitted changes or a branch against a base and reports prioritized findings without modifying the working tree [Code review](https://learn.chatgpt.com/docs/code-review).
2. `codex execpolicy check` mechanically evaluates command rules and their justifications without executing them [Rules](https://learn.chatgpt.com/docs/agent-configuration/rules).
3. Rule files embed known-match and known-non-match fixtures validated at load time.
4. `codex exec --json` emits typed thread/turn/item events and usage; `--output-schema` requests a final JSON schema [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).
5. Hooks can run deterministic validation on PostToolUse and Stop, including continuation feedback.

Our harness is stronger at explicit behavioral honesty and terminal evidence, but weaker at mechanical observability. D2 proves agents repeatedly trusted detectors without a known-positive control, and D3 says hook behavior is unmeasurable in mined transcripts. Codex's typed JSONL event stream is therefore a meaningful advantage.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): provider-neutral event envelope.** Normalize existing Codex JSONL and Claude hook events into `{timestamp,provider,session,turn,event,tool,status,input_hash,output_hash,hook,decision,duration_ms}`. Store sanitized summaries in the existing ledger; retain raw references separately. This is **almost certain (90-99%)** to make future hook firing countable because event and hook identity become explicit fields. Whether it improves agent outcomes is **likely (55-80%)**, settled by the next corpus miner demonstrating known-present hooks and correlating decisions with retries.

**CONFIG (settings/JSON only): use `/review` explicitly, not a mandatory Stop review gate.** Read-only review is useful when change risk warrants it, but a hidden second-model review on every stop repeats the trained-critic and capacity problems. The owner's contract already requires a fresh-context internal critic; keep external review explicit.

Do not expand schema strictness. Codex's `--output-schema` is useful for stable automation, but this corpus proves over-strict schemas are the second-worst measured tool surface. The ported batch envelope must require only `item_id` and `status`; everything domain-specific belongs under a permissive `result` object/string. This is **very likely (80-90%)** to avoid the observed missing-field class because absent domain fields cannot invalidate the terminal envelope.

## Anti-overfit gate

Every accepted proposal rides an existing bus:

- sandbox and network controls: provider-native configuration;
- structural policy, hook trust, bounded outputs, MCP preflight: existing hook dispatcher;
- goals and telemetry: existing event ledger;
- fan-out: existing Task/Agent + longrun path;
- memory provenance: existing basic-memory write path.

No accepted proposal introduces a second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The Codex features that would violate the gate—auto-review, autonomous two-stage memory consolidation, and SQLite-backed durable job semantics—are explicitly rejected or reduced to stateless adapters.

## Experiments before rollout

1. **Sandbox compatibility matrix:** in disposable workspaces on native Codex Windows and Claude WSL2, prove allowed workspace write succeeds, parent-drive write fails, denied-domain egress fails, allowed-domain egress succeeds, and each required Windows RE tool works only through an explicit exclusion. This settles the UNVERIFIED compatibility concern.
2. **Structural policy regression:** feed all D1 false-positive payloads, a real destructive command, a mixed safe/destructive shell chain, quoted prose, fenced code, variables, redirection, and PowerShell AST cases. Require zero false blocks and zero missed destructive controls.
3. **Hook telemetry control:** emit one known hook event and one fake name; run the miner; require exactly the known event and zero fake events. This follows D2's mechanically independent known-positive rule.
4. **Hook-output budget:** return 5 KB, 50 KB, and 500 KB sanitized payloads; verify model-visible bounds, full artifact hash/path, and no secret leakage.
5. **MCP preflight:** test live, auth-required, dead, slow, and schema-invalid servers; verify required failures stop before work while optional failures degrade with a terminal marker.

7. **Compaction on 0.144.5:** one disposable long turn with explicit low thresholds and many tool outputs; require automatic compaction and continued completion. Until this passes, the current-version behavior is UNVERIFIED.
8. **Memory authority A/B:** 30 sessions with Codex memory disabled versus enabled, while basic-memory remains canonical; score recall accuracy, contradictions, secret false positives, and hidden model usage.
