# X130 — systems-safety borrow for use-vs-mention guards

## Executive conclusion

The borrow transfers, but only in a narrow and useful form. The specific mechanism is STAMP/STPA's **context-qualified unsafe control action (UCA), backed by a controller process model and feedback**. STPA does not ask whether a dangerous-looking word exists somewhere in the system. It asks whether a controller provided (or failed to provide) a particular control action, in a particular operational context, with hazardous timing, duration, order, or parameters. The STPA Handbook defines a UCA as a control action that leads to a hazard “in a particular context and worst-case environment,” and requires five fields: source, UCA type, control action, context, and linked hazard ([MIT STPA Handbook, pp. 34–36](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). That is the systems-safety answer to use-versus-mention: **constrain an act at its control boundary, not a string that can represent the act**.

My verdict is **very likely (80-90%)** that this structural idea transfers to an agent harness, because the target has the same minimum structure: a controller (agent/user/runtime), a control action (tool invocation, permission grant, file mutation, shell execution), a controlled process, and observable context. The evidence is the STPA control-loop definition and the target brief's explicit failure mode—detectors consuming payload text rather than semantic role. This is not a claim that the whole STAMP ontology transfers.

The concrete design is a small **role-gated guard adapter** on the existing hook bus. It evaluates action guards only on provenance-assigned, typed control events; passes the structured action and trusted context to guard logic; treats quoted/document/evidence payloads as non-actions for action-only guards; and retains separate content guards where the hazard genuinely is carriage or disclosure of content. It also turns each guard rule into a small UCA contract and tests all four STPA guideword classes. This rides the existing hook/skill bus and introduces none of the rejected orchestration, memory, durable-execution, critic, SaaS, or guardrail-framework components.

This conclusion is an ideation result. Per the unit instruction, I did not inspect or infer the local harness implementation. **UNVERIFIED: whether the present hook events expose enough trusted provenance and action context to implement the adapter without changing an upstream event producer; settle this with an event-envelope capture across one known tool execution and one document-only mention.** Consequently, the implementation recommendation that depends on that premise is marked UNVERIFIED below.

## 1. The mechanism in its own field

### 1.1 STAMP: safety as enforcement of behavioral constraints through control and feedback

STAMP models safety as a control problem in a sociotechnical control structure. A controller issues control actions to a controlled process, receives feedback, and uses a process model to decide which action is appropriate. MIT describes the STPA Handbook as the definitive guide and lists its sequence as defining the analysis, creating a control structure, identifying unsafe control actions, building scenarios, and developing constraints and requirements ([MIT PSASS handbook index](https://psas.scripts.mit.edu/home/books-and-handbooks/)).

This matters because an item of information is not automatically a control action. In a control diagram, a brake command on the control path has a different functional role from a display that reports or describes a brake command on a feedback path. The handbook explicitly advises that diagram labels describe the *functional information sent*, avoid vague “Command” or “Feedback” labels, and check that required control actions and feedback are present ([MIT STPA Handbook, p. 33](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). The field therefore starts from channel, source, destination, and function—not lexical resemblance.

The controller's process model is equally important. For an automated controller, the handbook says decision-making can depend on the state of the controlled process, other controllers, the automation mode, and (in some systems) the human controller. It warns that a correct control algorithm can still issue an unsafe action if these contextual models are wrong ([MIT STPA Handbook, pp. 180–183](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). The general lesson is not “classify the text more cleverly”; it is “provide the controller with the state variables needed to distinguish safe from unsafe issuance.”

### 1.2 STPA: a control action is unsafe only in context

STPA applies four guideword categories to every control action:

1. a required action is not provided;
2. an action is provided when providing it is hazardous;
3. a potentially safe action is provided too early, too late, or out of order; or
4. a continuous action lasts too long or stops too soon.

The handbook supplies exactly those categories and then insists that context is critical: a brake command cannot be judged unsafe without knowing whether the aircraft is landing or in normal takeoff. Relevant context can include process state, controller state, previous and simultaneous actions, other controllers, parameters, and environmental conditions ([MIT STPA Handbook, pp. 35–38](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

The formal writing template is especially portable:

`<Source> <UCA type> <Control action> <Context> <Link to hazard>`

This template forces the analyst to distinguish these two propositions:

- “A document contains the text `delete account`.”
- “Controller A provides the `DeleteAccount(account_id=…)` action to actuator B while approval state is absent.”

Only the second is an unsafe control action as written. The first may be feedback, evidence, an instruction awaiting authorization, malicious data, or harmless quotation. It becomes safety-relevant only through a separately stated causal scenario—for example, if a parser mistakes that payload for a control event.

### 1.3 STPA: analyze both unsafe decisions and faulty execution paths

After finding UCAs, STPA works backward into loss scenarios. The handbook requires consideration of both why a controller would issue or omit an unsafe action and why a nominally correct action would be improperly executed or not executed. Its causal prompts include flawed control algorithms, unsafe input from another controller, missing/delayed feedback, incorrect interpretation, and nonexistent necessary feedback ([MIT STPA Handbook, pp. 41–43](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

This is important to use-versus-mention because “payload matched a token” is only a symptom. The systemic causal scenario is closer to: the guard receives a lossy observation in which control-channel role and data-channel role have been collapsed, then its process model assumes every representation is an attempted action. The remedy is to restore the missing state and boundary, not to grow an exception list of quoting patterns.

### 1.4 Swiss cheese: useful supporting constraint, not the primary solution

Reason's Swiss-cheese model says complex systems employ successive engineered, human, procedural, and administrative defenses; each has changing weaknesses, and loss occurs when weaknesses align across layers ([Reason, “Human error: models and management,” BMJ 2000](https://www.bmj.com/content/320/7237/768)). This contributes one design constraint: defenses should not all make the same use-versus-mention error from the same raw string. A keyword pre-hook, keyword post-hook, and keyword audit check are three nominal layers but one correlated sensing hole.

However, Swiss cheese does **not** itself tell us how to identify semantic role. It is a model of how defenses fail and align, not a classifier or interface specification. Later analysis records common criticisms: the metaphor is simplistic, nonspecific about slices and holes, static relative to dynamic systems, and open to divergent interpretation; Reason cautioned that it is a symbolic simplification requiring tailoring ([Li & Thimbleby, “Gating the holes in the Swiss cheese,” 2014/2018 open-access review](https://pmc.ncbi.nlm.nih.gov/articles/PMC5901035/)). Therefore, “add another detector” is not a justified borrow. The useful borrow is to make the second signal mechanically different: control-plane provenance or actuator-side observation, rather than another scan of the same payload.

### 1.5 Safety cases: an assurance wrapper, not a runtime guard

A safety case makes the relationship among claim, argument, evidence, and context explicit. The UK Ministry of Defence's Manual of Air System Safety Cases says an argument without evidence is unfounded, evidence without argument is unexplained, and safety cannot be argued without the context of use ([MASSC Issue 3, pp. 12–13](https://assets.publishing.service.gov.uk/media/642283502fa848000cec0c63/MASSC_Issue_3.pdf)). This maps to acceptance discipline: “false fires fell” is a claim; a role-stratified replay, live boundary trace, and adversarial mutation set are evidence; the argument explains why they cover intended operating contexts.

Safety cases do not solve runtime classification. Their transferable role is to prevent a redesigned guard from being declared done merely because documents exist or a happy-path test passes. MASSC itself warns that document existence can produce false reassurance and emphasizes operating context and continuing evidence ([MASSC Issue 3, pp. 12–13](https://assets.publishing.service.gov.uk/media/642283502fa848000cec0c63/MASSC_Issue_3.pdf)).

## 2. Translation to the agent harness

### 2.1 The control-structure mapping

| Systems-safety element | Harness counterpart | Required trusted fact |
|---|---|---|
| Controller | agent runtime, user approval component, scheduler, hook | stable producer identity |
| Control action | tool invocation, permission decision, mutation request, external send | typed event kind and action schema |
| Actuator/control path | tool dispatcher, shell runner, filesystem/API client | destination/capability handle |
| Controlled process | workspace, machine, account, remote service | target identity and pre-state |
| Feedback | tool result, exit status, diff, approval response | correlation to the initiating action |
| Process model | hook-visible mode, authorization, provenance, action lifecycle | state from control plane rather than payload text |
| Hazard | unauthorized effect, data release, destructive mutation, denied legitimate workflow | explicit rule-specific consequence |

The pivotal translation is that **semantic role is provenance at the boundary, not a linguistic property inferred from bytes**. A document containing a JSON object that looks like a tool call remains a document payload if it arrived on a document/evidence channel. A real tool request remains an action even if its dangerous parameter is obfuscated or contains no banned verb. The event producer assigns the role; payload text cannot promote itself to a control action.

Candidate envelope fields are:

```text
event_id, correlation_id
producer, principal
channel_role: action_request | action_result | instruction | evidence | quoted_data
action_kind, destination, capability
parameters (structured)
authorization_state
lifecycle: proposed | approved | dispatched | completed | failed
parent_event_id, timestamp
```

These are not all universally mandatory. A guard contract declares which fields it requires. Unknown or missing role is not silently treated as harmless: the adapter uses a rule-specific policy such as “do not run this action-only lexical detector, but require approval / emit a diagnostic because provenance is unknown.” Treating all unknowns as documents would create an obvious bypass; treating all unknowns as executable recreates the false-fire problem.

### 2.2 Proposal — UNVERIFIED role-gated guard adapter

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Insert a thin adapter before the five affected detectors:

1. Accept the existing hook event.
2. Validate trusted envelope fields supplied by the hook dispatcher, outside the scanned payload.
3. Select guards by declared applicability (`channel_role`, `action_kind`, lifecycle phase, destination).
4. Pass structured parameters plus trusted context to applicable guards.
5. Emit a structured decision: `allow | deny | require_approval | diagnostic`, with rule ID, UCA contract ID, evidence fields, and correlation ID.
6. Never allow content inside `payload`, a quoted code block, or a fetched document to override the outer role.

**UNVERIFIED: the “<~200 lines” size and availability of an authoritative outer envelope; settle with a one-hour spike that consumes captured hook fixtures and reports changed producers, adapter LOC, and fields unavailable before dispatch.** It is **roughly even (45-55%)** that every affected detector can be migrated within 200 lines, because the conceptual adapter is small but the unit deliberately did not inspect current event schemas. If upstream producers need modification, split the work into small producer patches rather than introduce a daemon.

It is **very likely (80-90%)** that boundary role gating would prevent the stated class of document-only false fires, provided roles are assigned outside payloads, because action-only rules would never receive `evidence` or `quoted_data` events; the evidence is the control-path/data-path separation in STPA and the deterministic envelope rule. This confidence does not extend to guards whose actual hazard is content transport, such as secret disclosure or prompt injection. Those must explicitly subscribe to relevant content roles.

### 2.3 Proposal — UCA contracts for every guard

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Represent each guard's purpose in a compact manifest:

```json
{
  "id": "G-delete-without-approval",
  "source": ["agent-runtime"],
  "uca_type": "provided",
  "control_action": ["filesystem.delete", "account.delete"],
  "context": {"authorization_state": ["missing", "denied"]},
  "hazard": "irreversible-or-unapproved-loss",
  "applies_to_roles": ["action_request"],
  "unknown_context": "require_approval"
}
```

The manifest makes “match text” insufficient as a rule definition. Review fails if source, action, context, or hazard is absent. Content-oriented guards use a different contract; for example, the hazardous action may be `external_send`, while secret-shaped text is a parameter condition. A prompt-injection detector may legitimately inspect `evidence`, but its response should constrain a later control action rather than pretend the evidence itself executed something.

It is **likely (55-80%)** that this manifest would expose guards that conflate data with control during review, because reviewers can see an `applies_to_roles`/`control_action` mismatch; the evidence is STPA's required five-part UCA structure. Effectiveness is not certain because a manifest can be populated mechanically without improving semantics. The settling experiment is blinded review: give maintainers a mixed set of current-style and UCA-style rules and measure whether they identify planted use-versus-mention defects.

### 2.4 Proposal — generate tests from all four UCA guidewords

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For each guard contract, generate or require fixtures for:

- **provided, hazardous:** a real action in the forbidden context must be blocked;
- **provided, nonhazardous:** the same action in an authorized/safe context must pass;
- **mentioned:** identical dangerous tokens in instructions, quoted code, fetched pages, logs, test fixtures, and reports must follow the contract's content-role policy;
- **not provided:** a required safety action or approval omitted from a sequence must be detected where the rule claims to cover omission;
- **timing/order:** approval after dispatch, stale approval, result before request, or action outside its permitted phase;
- **duration/repetition:** a monitor stopped early, repeated action, or capability retained too long;
- **parameter transformation:** aliases, encoded parameters, indirect paths, and benign prose containing exact trigger tokens.

The first three cells directly measure use versus mention. The remaining cells are what the STPA borrow catches that raw payload matching misses **by construction**: absence has no token to match, order is a relationship between events, duration is lifecycle state, and hazardous context may be entirely outside the action string. This is a logical coverage statement derived from the four UCA categories, not a claim that the local five detectors promise all these functions.

It is **likely (55-80%)** that a small fixture generator plus existing test runner can cover these transformations without a new framework, because the generator only expands declarative contracts into hook events; evidence is the finite STPA guideword set. **UNVERIFIED: whether the current test runner can replay ordered hook events; settle by implementing one three-event approval→dispatch→result fixture.** If it cannot, keep the generator as a fixture producer and use the existing runner's nearest native sequence facility; do not add a durable-execution engine.

### 2.5 Proposal — two independent runtime signals for “this was an action”

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Use two mechanically independent observations in verification and high-risk policy:

- **Control-plane signal:** the dispatcher emits a typed pre-action event with producer, capability, destination, and correlation ID.
- **Execution/feedback signal:** the actuator or tool-result boundary emits a correlated dispatch/result record, exit status, or observed target-state transition.

A second regex over the same payload is not independent. Nor is replaying the same parser twice. For document-only tests, the detector control is a known-present tool invocation that both signals find; only after validating those detectors may a test claim that the document mention caused no action. For a blocked action, the expected evidence is a pre-action event plus an explicit non-dispatch/denial record—not mere absence of a result.

It is **very likely (80-90%)** that correlation between control-plane and feedback events would detect at least the STPA scenario “decision issued but action not executed” and distinguish it from mere text, because those observations occur at different boundaries; the handbook explicitly requires analysis of both unsafe controller decisions and improper/non-execution on the actuator path ([MIT STPA Handbook, pp. 41–43 and 180–181](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). **UNVERIFIED: whether actuator-side feedback exists for every tool; settle with a tool-by-tool event matrix and known-present controls.** Lack of a second signal must be recorded as unknown coverage, not “no action.”

### 2.6 Proposal — claim/argument/evidence acceptance record

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

For each migrated guard, record:

- claim: the precise hazard constrained and roles covered;
- argument: why envelope provenance plus guard logic distinguishes action from representation;
- evidence: role-stratified replay, known-present detector control, live boundary trace, adversarial payload mutations, and false-negative cases;
- context and defeaters: unsupported producer, missing role, nested agent event, forged inner envelope, stale correlation, content-hazard exception;
- residual risk and owner.

This is a lightweight safety-case pattern, not a new assurance platform. It is **likely (55-80%)** to prevent premature “done” claims when used as a merge criterion, because it requires an explicit bridge from evidence to a context-bounded claim; MASSC identifies precisely that bridge as the role of the safety argument. It is **unlikely (20-45%)** to help if treated as passive documentation, because the same source warns that document existence can create false reassurance. The settling experiment is process-level: sample migrations after one month and test whether every claim's cited fixture and trace can still be reproduced.

## 3. What this catches beyond the stated false fires

Subject to the envelope and correlation premises above, the design broadens detection in specific ways:

1. **Actual action without trigger vocabulary.** A typed `filesystem.delete` or `external_send` action remains guardable when parameters use aliases, IDs, encoded values, or indirect paths. It is **very likely (80-90%)** to outperform lexical action detection for known typed tools, because dispatch identity is explicit rather than inferred from wording.

2. **Unsafe omission.** Missing approval, missing confirmation, or missing required safety action can be detected as an absent predecessor in an event sequence. It is **likely (55-80%)** for bounded request lifecycles, because correlation IDs and state transitions make the expected predecessor enumerable; it is less certain for open-ended conversational obligations.

3. **Unsafe order and timing.** Approval after dispatch, reuse of stale approval, or action in the wrong mode becomes expressible. It is **likely (55-80%)** where lifecycle timestamps and parent IDs are authoritative; the evidence is STPA's explicit timing/order UCA category.

4. **Controller/process-model mismatch.** A guard can diagnose `unknown authorization_state` or an unsupported producer rather than silently infer state from prose. It is **very likely (80-90%)** to make missing context visible because missing structured fields are mechanically enumerable.

5. **Decision/execution divergence.** Correlated pre-action and actuator feedback can reveal a nominal allow that never executed or an execution with no authorized request. It is **likely (55-80%)** for instrumented actuators; **UNVERIFIED for uninstrumented/native tools, settled by the tool event matrix experiment.**

6. **Correlated defense holes.** A role gate plus actuator feedback can identify cases that several keyword layers all mishandle. It is **likely (55-80%)** to reduce common-mode use-versus-mention failures because the signals are structurally different, while Swiss cheese alone gives no quantitative guarantee.

These are design capabilities, not measured claims about the current harness. The only local condition taken as a premise is the unit brief's “5 detectors, 12+ false fires”; this lens intentionally did not duplicate repository-grounding work.

## 4. Adversarial analysis of the analogy

### 4.1 Where the structure really matches

The analogy is not based on superficial language. Both domains contain:

- controllers that decide whether to act;
- controlled processes affected through bounded interfaces;
- data/feedback that can describe actions without being actions;
- safety constraints dependent on operating context;
- hazards caused by provision, omission, timing, duration, and faulty feedback;
- process-model errors where a controller acts on the wrong understanding of state.

The strongest isomorphism is the control boundary. A shell tool call or API mutation is causally different from bytes in a report, just as an actuator command is causally different from a display or maintenance record describing that command. Therefore the transfer is not “aircraft are like agents”; it is “both expose control actions and feedback through interfaces.”

### 4.2 Where it does not match

First, natural-language roles are not always fixed. A user's sentence may be documentation in one workflow and an instruction in another; an agent may quote an instruction and later adopt it. Physical control systems usually have engineered channels and enumerated actuators, whereas an LLM collapses data and instruction into a shared token stream. It is **very likely (80-90%)** that provenance gating alone cannot resolve every conversational intent, because channel role and intended illocutionary force are different facts. The remedy is not to claim otherwise: use deterministic roles for actual harness boundaries, and require approval or a separate intent decision where the action has not yet reached a typed boundary.

Second, “mention” can itself be hazardous. A secret in a document sent externally, malicious instructions entering an agent context, or illegal content in storage may create a hazard without tool-like execution. A global “documents are safe” exemption would be unsound. The UCA contract must identify the actual controlled action and hazard: for exfiltration, `external_send(payload)` is the action and secret-bearing content is relevant context; for ingestion risks, admitting untrusted text into an instruction-capable context may itself be the action.

Third, an LLM may transform text into an action later. A benign evidence event at time T does not prove that no later unsafe action will be derived from it. STPA handles this only if the later action and feedback loop are modeled. This is why the design gates every consequential action at dispatch rather than granting a durable “safe document” label.

Fourth, STPA is an analysis method, not a proof of classifier correctness. Research on STPA validation notes that validation of hazard-analysis applications remains challenging and that expert practices have often been informal or ad hoc ([Sadeghi et al., 2023 interview study abstract](https://www.sciencedirect.com/science/article/abs/pii/S0950423023000943); [proposed validation framework](https://www.sciencedirect.com/science/article/abs/pii/S092575352300022X)). Therefore a UCA worksheet does not establish completeness. Replay, mutation, live traces, and operational feedback remain necessary.

Fifth, the STPA four-category completeness statement applies to ways a defined control action can be unsafe, not to completeness of our chosen action inventory, hazards, context variables, or producer instrumentation. It would be invalid to say “all guard hazards are covered” merely because all four columns have tests. Unknown action types and missing control boundaries remain gaps.

Sixth, safety systems often tolerate conservative shutdown; developer harnesses pay a high productivity cost for false positives. The acceptable response therefore varies by consequence. A destructive external effect may justify `require_approval` on unknown provenance; a style warning may justify diagnostic-only behavior. STPA helps state the constraint but does not choose the owner's utility tradeoff.

### 4.3 Final transfer judgment

The analogy survives these objections because the proposal borrows only the part supported by a genuine structural match: context-qualified control actions at typed boundaries with feedback. It rejects the overreach that natural-language semantic role is always knowable, that documents are intrinsically harmless, or that more defensive layers automatically help.

The transfer is **very likely (80-90%)** to solve the narrow false-fire class when an authoritative action boundary exists, based on deterministic role separation and STPA's context-qualified action model. It is **unlikely (20-45%)** to solve use-versus-mention purely inside an undifferentiated prompt before any typed action exists, because provenance cannot decide speaker intent or later model adoption. In that region, the appropriate result is uncertainty plus action-boundary enforcement—not another confident payload classifier.

## 5. Anti-overfit gate and rejected alternatives

The retained design passes the anti-overfit gate:

- it rides the existing hook/skill/MCP event bus;
- it adds a thin adapter, declarative contracts, fixtures, and structured evidence;
- it does not add a second orchestration runtime;
- it does not add vector/KG memory;
- it does not add a durable-execution engine;
- it does not add a trained critic;
- it does not add observability SaaS;
- it does not add a general guardrail framework.

Rejected alternatives:

1. **A larger LLM semantic classifier before every guard.** Rejected because it infers role from the same ambiguous payload, adds latency and nondeterminism, and can reproduce the common-mode failure. It may be useful for triage but not as the authority for whether an actuator event exists.

2. **More quote/code-block/document regex exceptions.** Rejected because representation forms are open-ended and adversarial; the rule remains attached to syntax instead of causal role.

3. **A new policy daemon or workflow runtime.** Rejected because the needed mechanism is local to the existing event boundary. A BUILD-LARGE component lacks justification and violates the explicit architecture gate.

4. **Swiss-cheese layering of several payload scanners.** Rejected because the layers share the same sensing hole. Independence comes from control-plane provenance and actuator feedback, not detector count.

5. **Blanket suppression for all documents.** Rejected because content transport and instruction-ingestion hazards can make document content relevant. Applicability must be hazard-specific.

6. **Safety-case paperwork as the primary control.** Rejected because assurance artifacts cannot mediate runtime effects; they only structure the claim and evidence for the actual control.

## 6. Minimal experiment sequence

No experiment was run in this ideation-only unit. The recommended sequence is designed to settle every material UNVERIFIED premise without local architecture expansion:

1. Capture one known tool action and one document containing identical action text. Confirm whether the bus exposes distinct, trusted event roles.
2. Validate two mechanically independent action detectors using the known-present tool call: dispatcher event and actuator/result event.
3. Prototype the adapter on one detector in shadow mode; do not change enforcement.
4. Replay a balanced set: hazardous use, authorized use, quoted mention, code example, log, fetched malicious page, missing approval, stale approval, reordered lifecycle, transformed parameter.
5. Compare old and new decisions, with false positives and false negatives separated by role and hazard—not one aggregate accuracy number.
6. Attempt envelope forgery inside payloads and nested quotations. The outer producer-assigned role must remain unchanged.
7. Run one live deny case and prove both the decision and non-dispatch record. Do not infer non-execution merely from missing output.
8. Migrate further detectors only if the evidence supports the bounded claim and the adapter remains small. If role is not available at the existing bus, patch event producers individually; do not create a parallel runtime.

Success criteria should be stated before the replay. A defensible starting claim is: “For action-only rules and instrumented producers, document/evidence mentions do not invoke the rule; hazardous typed actions still do; unknown provenance produces an explicit non-allow decision or diagnostic according to the contract; dispatcher and actuator records correlate.” Numeric thresholds require a representative labeled corpus and are therefore **UNVERIFIED; settle them by labeling a stratified sample of real false-fire and true-action events before choosing thresholds.**

## 7. Gaps

- **UNVERIFIED: existing event fields, producer trust boundaries, detector APIs, and replay facilities.** Settling experiment: the event-envelope capture and ordered replay spike described above. This unit was explicitly prohibited from duplicating local grounding.
- **UNVERIFIED: whether all five stated detectors are action-only guards.** Settling experiment: write a UCA contract for each and identify whether its hazard is action, content transport, ingestion, or another category. The role exemption must not be applied until this is known.
- **UNVERIFIED: representativeness of the “12+ false fires” across channels and payload forms.** Settling experiment: label each incident by outer event role, intended role, detector, hazard, and eventual actuator effect.
- **UNVERIFIED: coverage of actuator-side feedback.** Settling experiment: a tool-by-tool matrix with a known-present control for each detector. No absent/broken conclusion is permitted from a single unvalidated trace.
- **UNVERIFIED: performance cost.** Settling experiment: shadow-mode p50/p95 overhead on real hook events. The adapter is structurally simple, but no latency claim is made without measurement.
- **UNVERIFIED: whether role metadata can be forged by nested agents or plugins.** Settling experiment: attempt to set envelope fields from payloads and lower-trust producers; verify the dispatcher overwrites or rejects them.
