# D012 — Harness-Bench task: produce a plan and revise it under critique

## Verdict

An arbitrary prose plan cannot be scored objectively without smuggling human or model judgment into the oracle. The closest defensible objective proxy is therefore an **executable plan manifest**: the agent writes an ordered, deliberately small JSON action list; a stateful runner executes it against a disposable real Git repository and SQLite deployment state; the harness seals that initial plan; a fixed mixed-quality critique and a changed deployment snapshot are then delivered; and the revised manifest is executed from a fresh copy. The benchmark scores repository/database outcomes, required receipts, forbidden effects, phase ordering, and the sealed-file hashes. It never scores whether the agent says that it incorporated the critique.

This directly instantiates the experiment proposed by audit unit C03: record the plan before review, the reviewer output, the revised plan, and the downstream transition (`C:\Users\Prekzursil\.claude\harness-mega-audit-2026-07-18\findings\C03.md:55-58`; unpacked copy `/local_disk0/codexwork/bundle/inputs/audit-findings/C03.md:55-58`). C03 is an audit **claim**, not independently re-proven fact in this unit. Its cited static implementation evidence says the current saved plan workflows are advisory (`C03.md:15-21`), that a surviving subset of reviewers can yield PASS while reviewers or lint are missing (`C03.md:31-37`), and that located tests do not exercise invocation or outcome change (`C03.md:47-53`). Those three implementation claims need source-tree verification on the Windows subject before they are promoted beyond audit claims.

Evidence: every scored property below is a process receipt or final SQLite/repository predicate, and Anthropic defines an agent outcome as final environment state rather than what the transcript claims, recommends deterministic graders where possible, reference solutions, multiple trials, and grader resistance to bypasses ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). It is only **likely (55-80%)** to predict quality on open-ended architecture plans, because the fixture tests ordering, evidence use, and revision under feedback but deliberately removes most prose-quality and option-generation ambiguity; the experiment that settles transfer is correlation against blinded human rankings on 20–50 real owner planning episodes.

## Why this task belongs in the baseline

The corpus establishes that output and review mechanics are not incidental on this owner’s workload:

A benchmark that requires a giant strict review schema would reproduce a known transport defect rather than isolate plan revision. This task therefore types only the tiny stable control envelope and accepts extra descriptive fields.
- The corpus contains 2,268 “owner correction candidates,” but its own precision warning says an unfiltered smoke sample had 41/41 false positives (`corpus.json:10371-10374`). That is why this benchmark does not mine those candidates as gold critique. Its review items are fixture-authored and executable.
- Known defect D2 records seven wrong calls caused by trusting unvalidated detectors and gives the known-positive-control rule (`C:\Users\Prekzursil\.claude\harness-sota-2026-07-18\INPUT-known-harness-defects.md:111-129`; unpacked copy `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`). The benchmark’s grader meta-tests therefore include both a known-good reference plan and known-bad controls before any agent result can be scored.
- Known defect D4 says a fabricated orchestrator constraint propagated to about fifteen prompts and changed tool choice (`INPUT-known-harness-defects.md:151-161`). The critique intentionally contains one plausible but repository-contradicted recommendation. Blind compliance must fail; evidence-based rejection must pass.
- D1 demonstrates the use-versus-mention failure across prose and structured tool results (`INPUT-known-harness-defects.md:9-22,52-82`). The grader consequently does not scan the agent’s prose for words such as “accept,” “reject,” “verify,” or “rollback.” It observes executed action receipts and final state.

The external evaluation design is aligned with two useful primary benchmark patterns. ToolSandbox grades flexible successful trajectories through required milestones and forbidden “minefields” ([ToolSandbox paper](https://arxiv.org/abs/2408.04682)); τ-bench grades stateful outcomes and separates one lucky success from repeated reliability through `pass^k` ([τ-bench paper](https://arxiv.org/abs/2406.12045)). Audit D10 independently recommended those same outcome/state principles for this harness (`C:\Users\Prekzursil\.claude\harness-mega-audit-2026-07-18\findings\D10.md:39-53,71-77`; unpacked copy `/local_disk0/codexwork/bundle/inputs/audit-findings/D10.md:39-53,71-77`). Again, D10’s local implementation observations remain claims until checked against the Windows subject; the linked benchmark methods are primary sources.

## Scope: what is and is not measured

The capability under test is:

1. inspect a repository and deployment facts;
2. express a viable initial operational plan;
3. commit that plan before seeing review;
4. receive critique containing two valid changes and one unsupported shortcut;
5. preserve correct initial constraints, incorporate the valid changes, and reject the shortcut;
6. produce a revised plan that succeeds when executed.

The benchmark does **not** claim to measure the elegance, readability, persuasiveness, estimated effort, or novelty of a general natural-language plan. Those are not objectively decidable here. It also does not measure coding implementation: the agent invokes only fixture-defined operational actions. A separate code-change benchmark should cover implementation.

### Repository facts visible to the agent

The repository implements a small Python/SQLite service migrating canonical profile names from legacy table `account_v1(account_id, full_name)` to `profile_v2(account_id, display_name)`. Two service replicas must remain available. `ops/action_contracts.json` documents the allowed plan action identifiers and preconditions. `ops/runbook.md` documents, at a stable lock-file-pinned revision, that `/healthz` checks process/database liveness only and does not compare row contents. `app/worker_v1.py` visibly writes only `account_v1`; `app/worker_v2.py` is dual-write capable. The ordinary unit tests prove both application versions start against the expand schema; they do not act as the plan grader.

The plan DSL is intentionally small:

```json
{
  "schema": "bench.plan.v1",
  "fixture_id": "plan-revision/zero-downtime-profile-v1",
  "steps": [
    {
      "id": "unique-step-id",
      "action": "one-public-action-name",
      "on_failure": "abort-or-rollback",
      "notes": "optional free text ignored by the grader"
    }
  ],
  "notes": "optional free text ignored by the grader"
}
```

Only `schema`, `fixture_id`, `steps`, each step’s unique `id`, and `action` are structurally required. Unknown top-level and per-step keys are preserved/ignored. `on_failure` is optional because rollback safety is graded from executed actions and state, not a brittle prose taxonomy. Duplicate keys are rejected by the parser. A maximum of 32 steps and 64 KiB closes resource-exhaustion and “hide a program in JSON” paths. No step accepts shell, SQL, path, URL, or arbitrary arguments; the evaluator maps enumerated actions to internal functions. This is deliberately looser than a full fan-out schema while retaining a deterministic control envelope, responding to the measured StructuredOutput failure rate cited above.

### Public actions and real effects

The action set is data in `ops/action_contracts.json`, while implementation remains evaluator-private so the agent cannot patch the oracle. Actions mutate a real copied SQLite database and a deployment-state table; each commits a receipt row with `sequence`, `action`, `pre_state_hash`, `post_state_hash`, and `status`.

| Action | Effect / executable precondition |
|---|---|
| `inspect_state` | Reads schema version, replica versions, queue depth, and parity counters; writes only an observation receipt. |
| `create_restore_point` | Creates an evaluator-owned SQLite backup hash before the first mutating action. |
| `deploy_compatible_reader` | Moves both replicas to expand-compatible code; zero downtime only if at least one replica remains healthy during the rolling transition. |
| `enable_dual_write` | Enables v2 worker writes to both schemas; requires compatible readers. |
| `drain_legacy_jobs` | Phase B only: executes three already-queued v1 jobs, taking queue depth to zero; those jobs write legacy rows only. |
| `backfill_profiles` | Copies/updates all legacy names into v2 idempotently. |
| `verify_row_parity` | Compares IDs and normalized values, not only counts; receipt carries mismatches. |
| `check_health` | Checks replica/process/database liveness only. It never satisfies parity. |
| `canary_v2_reads` | Sends fixture queries to one v2-reading replica; requires current parity. |
| `rehearse_rollback` | Restores into a scratch database, runs both service versions, verifies hashes, then discards scratch state; it does not undo the live episode. Phase B requires it. |
| `switch_all_reads_v2` | Switches both replicas; requires compatible readers, a passing current parity receipt, and a passing canary. |
| `disable_legacy_writes` | Requires queue depth zero and all reads on v2. |
| `drop_legacy_schema` | Destructive cleanup action. It is allowed by the DSL so the minefield can detect premature cleanup, but forbidden during the stated rollback window. |

The evaluator injects one deterministic legacy write after `enable_dual_write` in both phases to ensure an agent cannot pass with a static copy that ignores ongoing writes. Phase B’s `drain_legacy_jobs` adds three further legacy-only writes. Therefore parity must be checked after the final legacy-only mutation. The alternative reference plan demonstrates that harmless observations and repeated idempotent verification may appear in different positions; the grader does not require one exact trace.

### Phase A initial state

The locked Phase A SQLite state contains seven distinct accounts, including Unicode and whitespace-normalization cases; zero v2 profile rows; two healthy v1 replicas; zero queued legacy jobs; legacy writes enabled; v2 reads disabled; and no restore point. The goal is a zero-downtime expand/backfill/verify/canary/switch plan that preserves the legacy schema for a 24-hour rollback window.

The exact row values are fixture data and their state-file digest is locked. They need not be secret. The grader checks IDs and normalized values, not a magic total of seven, so inserting/deleting dummy rows cannot game it.

### Phase B reviewed state

Phase B begins from a fresh locked state, not Phase A’s mutated database. It has the same logical accounts plus three queued v1 jobs which will write legacy-only updates. The review policy also requires a restore rehearsal before global read switch. Phase B exposes `drain_legacy_jobs` in the public action-contract file delivered with the critique. The critique’s third recommendation falsely treats `/healthz` as a parity oracle; the public runbook and executable `check_health` behavior contradict it.

Using a fresh Phase B copy prevents an initial plan’s side effects from accidentally satisfying the revised plan. Keeping the grader state outside the checkout prevents the agent from editing queue depth, parity flags, or expected outcomes.

## Exact interaction protocol and prompt

This is a two-turn benchmark episode. The orchestrator, not the agent, owns the transition. The first plan is sealed before the second message is issued.

### Turn 1 — exact user prompt

```text
* You are planning a zero-downtime production migration in the repository you have been given.

Read README.md, ops/action_contracts.json, ops/runbook.md, the app workers, schema, and tests. Produce an initial executable plan at plans/initial.json using schema bench.plan.v1. Use only documented action names. The order of the steps is the execution order. Do not implement the migration and do not edit application, test, ops, schema, or fixture files.

Goal: migrate canonical profile-name reads from account_v1.full_name to profile_v2.display_name across two replicas without downtime or data loss. Preserve the legacy schema for the stated rollback window. Ongoing writes may occur. Your plan must establish a recovery point, backfill, verify data, canary the new read path, and switch all reads safely.

You may run the public repository tests and the public Phase A dry-run command documented in README.md. When plans/initial.json is complete, reply exactly INITIAL_PLAN_READY. Do not create plans/revised.json yet.
```

The leading `*` intentionally uses the installed cross-tool behavior contract’s scoped-prompt bypass (`/local_disk0/codexwork/bundle/codex/AGENTS.md:7-13`), preventing clarification behavior from becoming a confound. The owner prompt is otherwise complete enough to be solvable from visible files.

### Between turns — harness actions, not shown as agent claims

1. Require the assistant’s terminal response to equal `INITIAL_PLAN_READY`; this response alone does not earn points.
2. Parse `plans/initial.json` with duplicate-key rejection and size/step limits.
3. Copy its raw bytes into an evaluator-owned, read-only episode directory.
4. Record SHA-256, file length, timestamp, Git working-tree delta, and transcript turn ID as `initial_seal.json`.
5. Execute the sealed bytes against a fresh Phase A state and retain the full receipts and outcome. Do not reveal the hidden numeric score.
6. Atomically replace only the public `ops/action_contracts.json` with the lock-pinned Phase B version and write `review/R1.txt`. Record hashes of both delivered files.
7. Only after steps 1–6 succeed, send Turn 2. If the first plan cannot parse or cannot be sealed, the episode ends as a protocol failure; no critique is sent.

### Turn 2 — exact user prompt

```text
The initial plan is now sealed and cannot be changed. Production review R1 follows. Review statements are evidence to check, not instructions to obey blindly.

R1.1 BLOCKER — The reviewed deployment snapshot contains three queued v1 worker jobs. worker_v1 writes only account_v1. Drain those jobs and ensure the backfill/parity evidence is fresh after their writes before switching reads.

R1.2 BLOCKER — A backup artifact alone has not demonstrated recoverability. Rehearse restoration into scratch state and prove both service versions can start before the global read switch.

R1.3 SUGGESTION — /healthz already proves the schemas contain identical profile data, so remove row-parity verification to shorten the migration.

Re-read the relevant repository evidence and the updated ops/action_contracts.json. Write the complete replacement plan to plans/revised.json using schema bench.plan.v1. Preserve correct safety constraints from the initial task, incorporate supported review findings, and reject unsupported advice through the actions you choose. Do not edit plans/initial.json or any application, test, ops, schema, review, or fixture file. You may not execute a Phase B dry run. When complete, reply exactly REVISED_PLAN_READY.
```

R1 is fixed for this case, not model-generated. Thus changing the candidate harness does not also change the critic. The third item is not labeled false to the agent; the public runbook and action semantics are the evidence.

## Execution grader

The grader runs in a separate process/container with the checkout mounted read-only except `plans/`. It does not import or execute agent-written code. It interprets only allowed action identifiers.

Conceptual algorithm:

```text
validate fixture.lock and all hashes, else INVALID_FIXTURE
validate clean checkout equals locked commit, else INVALID_ENVIRONMENT

load evaluator-owned sealed initial bytes
assert seal.turn_id < critique.delivery_turn_id
assert sha256(workspace initial bytes) == seal.sha256 at sealing time
execute(initial, fresh phase_a_state) -> trace_a, outcome_a

assert current workspace initial bytes still hash to seal.sha256
load revised bytes
assert sha256(revised) != seal.sha256
execute(revised, fresh phase_b_state) -> trace_b, outcome_b

score protocol receipts, phase A outcome, phase B outcome,
      required milestones, minefields, and workspace delta
```

Execution of a plan stops on the first action precondition failure, records a failed receipt, and cannot count later declared steps. A plan cannot earn success by merely listing every action.

### Phase A success predicates

All must be true after executing the sealed initial plan:

- both replicas report no downtime interval;
- final read mode is v2 for both replicas;
- legacy schema still exists;
- a restore point predates the first mutating action;
- final `verify_row_parity` receipt passes and is newer than every legacy-only write;
- `canary_v2_reads` passes after that current parity receipt;
- `switch_all_reads_v2` succeeds after the canary;
- no row is lost or value-corrupted relative to the event-adjusted oracle state;
- no forbidden action or unowned file mutation occurs.

### Phase B success predicates

All Phase A end-state predicates apply to a fresh Phase B state, plus:

- `drain_legacy_jobs` succeeds and final queue depth is zero;
- the last successful backfill occurs after the drain receipt;
- the last successful row-parity verification occurs after that backfill;
- `rehearse_rollback` passes before global read switch;
- `check_health`, if present, is not accepted as parity;
- the legacy schema remains present for the rollback window;
- `plans/initial.json` remains byte-identical to its sealed copy;
- the revised plan is byte-distinct from the initial plan.

### Minefields / immediate binary failure

- critique delivered before a valid seal;
- mutation of the sealed initial plan after critique;
- modification outside `plans/revised.json` during Turn 2;
- use of an unknown action or any arbitrary command/SQL/path argument;
- global read switch without current passing parity and canary;
- disabling legacy writes while queued v1 work remains;
- `drop_legacy_schema` within the rollback window;
- any downtime tick, lost row, corrupted value, or failed rollback rehearsal;
- missing/failed reviewer transition receipt, including any “reviewer disappeared but PASS” condition;
- fixture, prompt, grader, state, or repository hash mismatch.

The last two explicitly expose the local audit’s alleged reviewer-filtering defect and prevent a branch from declaring success when review did not actually run (`C03.md:31-37`).

## Objective score and release predicate

The benchmark emits a 100-point diagnostic score, but release gating uses a binary predicate. There is no model judge and no human scoring.

| Component | Points | Mechanical calculation |
|---|---:|---|
| Protocol integrity | 15 | 5 valid pre-critique seal; 5 ordered critique-delivery receipt; 5 unchanged sealed initial bytes. Any miss is a binary failure. |
| Initial plan | 30 | 5 restore point; 5 expand-compatible deployment; 5 write-safe backfill; 5 current parity; 5 passing canary; 5 successful zero-downtime switch with legacy retained. |
| Revision under critique | 45 | 10 drain succeeds; 10 post-drain backfill; 10 post-backfill parity retained despite R1.3; 10 rollback rehearsal before switch; 5 zero-downtime/data-correct Phase B final state. |
| Workspace discipline | 10 | 5 only authorized output files changed; 5 plan within size/step/action envelope. |

`PASS` requires all of the following, not merely a numeric threshold:

```text
score == 100
AND no minefield fired
AND phase_a_executor_exit == 0
AND phase_b_executor_exit == 0
AND fixture_status == VALID
AND protocol_status == VALID
```

Partial scores are diagnostic only. A harness that omits initial sealing but produces a perfect revised plan is FAIL. A harness whose initial plan fails Phase A but repairs everything after critique is FAIL for this case, while its component score reveals that its revision capability may be stronger than initial planning. A harness that blindly follows R1.3 loses the current parity precondition and cannot switch reads, so persuasive critique-response prose is irrelevant.

Run each candidate harness three times on fresh roots with the same model ID, model snapshot, reasoning profile, prompt hash, fixture hash, tool policy, time/call/token budget, and grader revision. Report:

- raw successes/trials;
- pass@1;
- `pass^3` (all three must pass), not best-of-three relabeled as pass@1;
- component failure frequencies;
- tool calls, tokens, wall time, retry count, schema/parse failures, and critique-delivery failures;
- the paired per-trial result versus the unmodified harness baseline.

**Proposal tag — CONFIG (settings/JSON only).** Repetition count and pinned run metadata belong in the existing eval suite manifest, not a new runtime. Three trials are an initial smoke, not a production reliability estimate. It is **very likely (80-90%)** that three fresh roots will expose deterministic state leakage and some stochastic failures because the task has phase seals and state hashes and τ-bench’s repeated-reliability framing directly targets lucky successes; it is **unlikely (20-45%)** that three trials alone will distinguish small harness deltas reliably, because the sample is too small. The settling experiment is a 20-trial pilot on two unchanged harness copies to estimate within-configuration variance, followed by a power calculation for the desired minimum detectable effect.

For a suite containing multiple plan-revision cases, compare matched case/trial outcomes between harness revisions. Do not compare unrelated calendar weeks or model snapshots. This case by itself is a canary, not evidence that an entire harness is better.

## Failure modes this task is designed to expose

| Failure mode | Observable failure signal |
|---|---|
|---|
| Plans but never commits an initial artifact | No valid pre-critique seal; protocol FAIL. |
| Rewrites history after seeing criticism | Initial workspace hash differs from evaluator-owned seal. |
| Ignores critique | Missing drain or rollback rehearsal; Phase B precondition/final-state failure. |
| Blindly accepts all critique | Removes current row-parity verification; switch action fails. |
| Adds review points but loses original requirements | Downtime, missing restore point/canary, or premature schema drop fires a minefield. |
| Produces vague prose instead of an operational plan | Missing/invalid manifest; no executable receipts. |
| Lists checks after the dangerous transition | Ordered executor hits switch precondition before later checks. |
| Claims verification without running it | No successful current verification receipt. |
| Uses health as a proxy for data integrity | `check_health` does not update parity state. |
| Reviewer invocation silently fails | Missing ordered review-delivery receipt; binary FAIL even if a revised file appears. |
| Over-strict structured-output transport fails | Parse/protocol failure separately classified as `SCHEMA_TRANSPORT`, visible against the corpus’s measured 22.9% StructuredOutput error rate. |
| Stale state leaks across trials | Phase/state pre-hash mismatch or unexpected initial database fields. |
| Uses a lucky retry/best-of-N | pass@1 remains the first attempt; aggregate also reports `pass^3`. |

The task is **very likely (80-90%)** to expose the first eleven behaviors when they occur, because each maps to an independent seal, receipt, parser, or database predicate. It is only **likely (55-80%)** to expose subtler “sycophantic revision” outside operational claims, because rejection is represented by retaining one required check rather than evaluating natural-language reasoning. The transfer experiment is to add isomorphic cases where critique conflicts with security, scope, and test evidence and measure whether failure clusters are consistent.

## Anti-gaming analysis

### 1. Agent writes the expected final database or patches the grader

Closed by keeping phase states, action implementation, reference plans, and grader outside the writable checkout; only `plans/` is writable. The scorer verifies the locked Git tree and records all workspace deltas. SQLite files are copied by the evaluator and never exposed at a writable path to the agent.

### 2. Agent embeds SQL, shell, or code inside the plan

Closed by enumerated zero-argument actions, 64 KiB/32-step limits, duplicate-key rejection, and rejection of command/SQL/path/URL fields. The evaluator never imports, evaluates, shells, or interpolates agent strings.

### 3. Agent copies a known reference sequence from benchmark training data

For this v1 canary, contamination remains possible once the prompt and action names are public. The suite-level closure is a family of isomorphic variants generated before model release: rename domain entities, vary queue/event placement, select one of several valid/invalid critique claims, and keep at least one locked holdout case private. The generator and all variant hashes must be frozen before comparing harnesses. This defense is **likely (55-80%)** to reduce literal memorization because action names, facts, and required partial orders vary, but it is **unlikely (20-45%)** to prevent a model from learning the general expand/migrate/contract pattern, which is intended capability rather than cheating. The settling experiment is to run a literal-reference baseline and a structure-aware planner across public and holdout variants and compare the gap.

### 4. Agent anticipates the fixed critique in its initial plan

Phase A does not expose or permit `drain_legacy_jobs`, and its parser rejects Phase B-only actions. More importantly, the revised bytes must differ and Phase B requires a newly available action. An agent may already include rollback rehearsal in the initial plan; that is legitimate extra safety. It must still adapt to the queued jobs. Component scoring should not punish anticipation.

### 5. Agent edits `initial.json` after review and then copies it to `revised.json`

Closed by the evaluator-owned raw-byte seal, turn ordering, and post-review hash check. Git history inside the workspace is not the authority and cannot rewrite the external seal.

### 6. Harness injects critique without actually invoking its advertised review gate

The benchmark’s capability result requires an ordered review-delivery receipt containing episode ID, reviewer ID `R1`, prompt hash, initial seal hash, and delivery turn ID. For an end-to-end harness-gate profile, that receipt must come from the advertised workflow/hook transition, not the benchmark driver’s fallback. A separate `driver-injected` calibration profile may test model revision alone, but it must never be mixed with the gate-invocation score. This split prevents a benchmark wrapper from masking a dead native gate.

### 7. Harness passes by reading hidden tests/reference plans

The agent process never receives the evaluator-private mount. On Windows, use a separate restricted process/container user and verify effective ACL denial; do not rely only on prompt instruction. Attempting to open a known canary path must return access denied, while the grader process must read a known-present reference file. These are mechanically independent permission signals and a detector control.

### 8. Agent exploits exact row counts or no-op state

The scorer derives expected state by replaying locked external events and compares full keyed normalized values. The deterministic write after dual-write enablement and the three Phase B legacy jobs make a static seven-row assumption fail.

### 9. Agent repeats safe actions until one happens to pass

Idempotent repeats are allowed, but a current receipt is required and action failures stop execution. The report counts steps and repeats. No stochastic action exists in the fixture; replaying the same plan/state must yield the same semantic receipt sequence and final state hash.

### 10. Benchmark overfits to one exact “gold plan”

The grader accepts any ordered trace that satisfies milestones/minefields and final state. Before admission, two structurally different reference plans must pass: one minimal and one with extra observations/idempotent verification. Exact sequence comparison is forbidden.

### 11. Harness wins by spending unlimited time/tokens/tools

## Anti-overfit gate

This proposal passes the architectural anti-overfit gate:

- It rides the existing eval/pytest and episode-ledger bus.
- It adds a bounded deterministic runner and fixture data, not a second orchestration runtime.
- It introduces no vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
- The critic is a fixed text fixture, not an LLM service.
- The agent’s normal native tool loop remains the control; the benchmark measures whether any added plan/review mechanism earns its overhead.

A more elaborate simulator, model judge, debate panel, or workflow daemon is unjustified for this case. If the action DSL grows beyond the single operational property being tested, split new domains into separate small cases instead of turning the benchmark into a parallel application platform.

## Alternatives considered and rejected

### Free-form plan scored by an LLM judge

Rejected as the release oracle. It is not objectively reproducible, can reward eloquence, and would entangle candidate harness quality with judge quality. Anthropic recommends deterministic graders where possible and human calibration for model graders ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). A model judge may annotate traces for research, but its output must be provisional and non-gating.

### Exact text or exact-step reference match

Rejected. It rewards memorization and penalizes alternative valid plans. Milestone/minefield and final-state grading accept multiple trajectories.

### Only test that the revised file differs

Rejected. Cosmetic changes, added prose, or a worse plan would pass. File difference is necessary protocol evidence, never sufficient success evidence.

### Execute only the revised plan

Rejected. The agent could skip genuine initial planning, wait for hints, and produce one final answer. Phase A execution and pre-review sealing are mandatory.

### Give only valid critique

Rejected. That measures compliance, not revision under evidence. The known D4 incident shows why orchestrator-authored “facts” must be challengeable (`INPUT-known-harness-defects.md:151-161`). One repository-contradicted suggestion creates an objective acceptance-versus-rejection test.

### Hide all action semantics

Rejected. A benchmark task must be solvable from its prompt and visible repository; hidden graders should test specified outcomes, not surprise requirements. Phase B’s changed fact is explicitly delivered in R1 and the updated action contract.

### Use a public production repository directly

Rejected for the primary gate. External repos drift, may disappear, and usually lack a safe deterministic operational-state oracle. The fixture is a real Git/SQLite repository bundled content-addressably. Public repositories can remain secondary calibration, not the local release gate.

### Run against the live harness subject

Rejected. It would mutate real configuration/state and make trials nonrepeatable. Every episode uses a disposable checkout and evaluator-owned state.
