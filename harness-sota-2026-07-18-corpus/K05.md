## The few-words-suffice target: measuring context re-establishment and designing the reduction

**Unit:** K05

## Executive answer

The exact number of owner turns currently spent re-establishing context is **not recoverable from the supplied distillation**. This is not an inference from a zero-result detector. Two mechanically independent signals establish the measurement limitation: (1) the corpus says it is distilled, that samples are capped at 12, and that only aggregate counts are exact (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`); (2) its correction-candidate field explicitly says its unfiltered smoke sample was **41/41 false positives**, because agent-authored prompts were counted as owner corrections (`corpus.json:10372-10374`). A known-positive control succeeds: the detector retained the explicit first-person repair “ask me again since we got intrrupted” (`corpus.json:11171`) and the aggregate table retained repeated “Continue … read … state” patterns (`corpus.json:10413`). Therefore the detector can find context-repair-shaped messages, but it cannot attribute them reliably to the owner or distinguish a new instruction from a restatement.

What can be measured now is a conservative, reproducible proxy:

* The corpus contains **8,441 nominal owner messages** and **2,268 recall-biased correction candidates** (`corpus.json:10372-10374`). The raw candidate fraction is 26.87%, but it is **not a correction rate** and must never be presented as one.
* Five narrowly selected aggregate patterns account for **60 context-continuity-shaped occurrences**: 25 “Continue … per the brief,” 16 “Continue … read [persistent state] first,” 12 “why did you stop,” 5 “why did you stop” plus a persistent-state handoff, and 2 plain “why did you stop” (`corpus.json:10397`, `10413`, `10425`, `10461`, `10569`). This is **0.71 proxy occurrences per 100 nominal owner messages**, not 60 verified owner turns. Some are demonstrably stop-hook feedback, so even this narrow figure is an upper bound on owner labor for those patterns, not a lower bound.
* The capped samples nevertheless contain unmistakable examples of the target failure: an interrupted question sequence had to be requested again (`corpus.json:11171`); the owner said a previously assigned item had already been given (`corpus.json:11339`); the owner named two ignored prior threads (`corpus.json:11453`); a compaction handoff explicitly warned not to trust the summary and supplied a multi-command state reconstruction (`corpus.json:12197`); and the owner challenged an autonomous loop stopping (`corpus.json:12251`). These examples prove the phenomenon is present, but the capped/non-random sample cannot estimate prevalence.

**Baseline conclusion:** it is **almost certain (90-99%)** that owner attention is being spent on context repair; evidence is the five explicit first-person examples above plus 60 aggregate continuity-shaped occurrences. The proposition that the true rate is “about 0.71% of turns” is **very unlikely (5-20%)**, because system-generated stop feedback contaminates the numerator and the distillation does not retain an origin label that separates owner, hook, and agent-authored messages. The exact rate remains **UNVERIFIED — the settling experiment is Finding 1’s stratified transcript adjudication plus prospective typed continuity receipts.**

The recommended target is not “more memory.” There are already two memory roles: basic-memory for semantic durable facts and the event ledger for objective turn history (`/local_disk0/codexwork/bundle/claude/AGENTS.md:85-91`). The target is a **small, evidence-bearing continuity packet** that lets “continue,” “that one,” “again,” or a project noun resolve to one live thread, while ambiguity triggers at most one high-value choice. The system should silently prove the packet against current files, git state, task events, and tool receipts before acting. It should learn preferences only from repeated cross-session behavior or explicit owner choices, expire weak inferences, and budget proactive suggestions by observed interruption cost.

I recommend seven findings, ordered with inferred-surprise items first. All ride the existing shared lifecycle harness, event ledger, basic-memory, Workflow/AskUserQuestion, typed receipts, OPEN-THREADS.md, and existing hook dispatcher. **No proposal adds a hook.** The architecture stays under the ~6-hook ceiling by folding all runtime behavior into the already-registered shared `UserPromptSubmit`, `SessionStart`, `PostToolUse`, `TaskCompleted`, `PostCompact`, and `Stop` paths. The deployed settings already route these events through the shared dispatcher (`/local_disk0/codexwork/bundle/claude/settings.json:90-103`, `117-126`, `310-320`, `393-404`, `445-468`), and the local dispatcher explicitly consolidates many checks into one fail-open process (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/dispatch.py:2-19`, `41-45`).

## Measurement protocol and honesty constraints

### Operational definition

A **context re-establishment turn** is an owner-authored turn whose information was already available before that turn in one or more of: the active goal, an unresolved conversational thread, a prior owner preference, a task/workflow state, a file/artifact state, or a prior answer/question sequence—and whose purpose is materially to make that prior information active again. It includes “continue the plan,” “I already told you,” “you forgot X,” and re-supplying a lost handoff. It excludes genuinely new scope, ordinary corrections of a new factual error, system/hook feedback, teammate messages, repeated test probes, and owner messages reporting a recurring external-world failure (“it crashed again”) when the recurrence itself is new evidence.

This definition deliberately separates **owner repair labor** from **agent recovery work**. A silent agent read of the ledger is recovery latency, not an owner context-repair turn. Both should be measured, but only the first is the headline target.

### Existing architecture that must be extended, not duplicated

* Global guidance already says basic-memory does not auto-load and must be queried proactively after compaction/resume or when prior work is referenced (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-11`).
* The shared harness describes its fixed module order as event ledger → goal reinjection → checkpoint → bounded recall and states that module errors fail open (`/local_disk0/codexwork/bundle/agents/harness/README.md:17-27`).
* Recovery replay currently happens only for resume/compact/clear and explicitly gives a brand-new session a clean context (`/local_disk0/codexwork/bundle/agents/harness/modules.py:964-989`). This protects against cross-session bleed, but it also means a fresh session cannot resolve “continue” from the project ledger without another mechanism.
* The goal module deliberately retains the current goal for very short acknowledgements such as “yes” or “continue” (`modules.py:1318-1338`). It retains a goal but does not resolve a short cue to a concrete open thread or next action.
* The shared bounded-recall module does nothing for prompts shorter than 40 characters or fewer than four tokens (`modules.py:1608-1614`). The older recall injector likewise rejects prompts shorter than 15 characters and uses lexical overlap (`/local_disk0/codexwork/bundle/claude/hooks/recall-inject/inject.py:269-303`, `343-369`). Thus the exact target phrase class is structurally disadvantaged by both recall paths.
* The shared ledger already records tool-result hashes and whether a result looks externally verified (`modules.py:1036-1077`), mutations (`modules.py:1103-1142`), native task completion (`modules.py:1218-1238`), and turn hashes (`modules.py:1240-1255`). Those are the external closure signals this unit needs.
* New heuristic gates already have a mandatory OFF→SHADOW→ADVISE→ENFORCE staging rail and anti-zombie metric contracts (`modules.py:118-149`). Every design below uses that rail rather than inventing a second evaluation framework.

### The governing verification rule

No “the agent re-read its answer and agreed” check appears below. Interpretation, continuity, preference promotion, thread closure, and autonomy promotion must close against one of: a later owner action/correction; a native task event; a tool execution result; a git/file-system observation; a different-context model blinded to the original reasoning; or a time-split replay ground truth. Same-context self-critique is rejected even if it produces a plausible explanation.

## 1. Inferred surprise — Continuity Tax Meter with typed repair receipts **[UNVERIFIED — experiment: stratified transcript adjudication + 30-day prospective receipt audit]**

**Improvement.** Turn the vague complaint “we keep having to re-establish context” into a calibrated metric: verified owner repair turns per 100 owner turns, median repair turns per resumed task, and words retyped per repaired thread. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add fields to the existing event-ledger module and one offline report command; add no hook and no daemon.

**What it is.** On `UserPromptSubmit`, record only a redacted prompt digest, token count, origin class from the native envelope, and deterministic cue flags (`already_told`, `ignored_prior`, `continue_prior`, `reask_after_interrupt`, `forgotten_thread`, `deictic_short_cue`). On the next `PostToolUse`, `TaskCompleted`, `Stop`, or owner prompt, attach a **continuity receipt** containing: candidate prior event/thread IDs, resolution chosen, external evidence type, whether the owner corrected that resolution, and words the owner had to restate. Do not store a self-awarded “correct” bit.

An offline `continuity-report` command draws a stratified sample from flagged and unflagged prompts. A fresh-context evaluator receives only the prior ledger tail, the candidate owner turn, and subsequent objective events—not the original agent’s reasoning—and labels `repair / new-scope / external-recurrence / system-generated / uncertain`. A small owner audit of uncertain cases estimates evaluator precision. Report a Wilson interval, not a point estimate masquerading as truth. Keep the 2,268 historical candidates as a discovery pool only; the corpus itself warns that 41/41 unfiltered candidates were false positives (`corpus.json:10372-10374`).

**Why inferred / owner signal.** The owner supplied a question explicitly asking to measure turns, and the corpus shows the measurement is currently impossible rather than merely uncomputed. The stronger inferred need is **trustworthy instrumentation that does not ask the owner to annotate every interaction**. The explicit “already told you” and “you ignored…” samples (`corpus.json:11339`, `11453`) show that the harm is not just elapsed time; it is the burden of proving a thread existed. The live defect report shows seven wrong conclusions caused by unvalidated detectors and demands known-positive controls (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`), so a raw regex counter would repeat a known failure class.

Reuse the existing module staging function and anti-zombie contract with metric `verified_context_repairs_per_100_owner_turns`. Implement the report as a normal command/skill that reads ledger JSONL and transcript slices. Historical backfill must first validate origin classification on known-positive owner messages (`corpus.json:11171`, `11339`) and known-negative controls such as task notifications and the “continued from previous conversation” system message (`corpus.json:10445`). Fail open: any parser/evaluator/report error records no verdict and returns zero.

**EXTERNAL signal that verifies it.** Two independent signals are mandatory: (1) blinded, different-context adjudication on a stratified sample; (2) subsequent behavior—owner correction/override, native task continuation, or tool actions that match the referenced thread. Promotion out of shadow requires ≥0.90 precision on owner-origin classification and ≥0.80 precision on repair-vs-new-scope classification with confidence intervals, plus a known-present control found in every run. The proposition that this will yield a defensible baseline within 30 days is **very likely (80-90%)**, because all needed native events are already dispatched and the explicit repair samples provide positive controls; evidence is settings wiring at `settings.json:117-126`, `310-320`, `445-468` and typed ledger events at `modules.py:1036-1077`, `1218-1255`.

NIST’s 2026 evaluation guidance warns that benchmarks need explicit assumptions and uncertainty estimates rather than unqualified point claims: https://www.nist.gov/publications/expanding-ai-evaluation-toolbox-statistical-models .

**Value × effort.** **high × low.** Measurement alone does not solve continuity, but it prevents optimizing a false detector and supplies the fitness signal for every later finding.

**Novelty.** **inferred-surprise.** The user asked for a measurement; the surprising part is treating “repair” as a typed, externally closed lifecycle event rather than another correction regex.

**Autonomy.** **just-do-it.** It is shadow-only, local, reversible, and creates no owner prompt. Ask the owner only to adjudicate a small uncertain calibration sample after the system has demonstrated that the sample changes a decision.

## 2. Inferred surprise — Thread escrow: every discussed item receives a lifecycle, not a reminder **[UNVERIFIED — experiment: 100-session shadow comparison against owner “forgot/ignored” corrections]**

**Improvement.** Make “never drop a thread” a state invariant: every owner-requested deliverable, unresolved choice, promised follow-up, interrupted question set, and explicitly deferred item is either open, completed with an external receipt, superseded, or intentionally dropped by the owner. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This extends the existing OPEN-THREADS.md + event-ledger projection and native Task/Workflow events; it does not create OPEN-THREADS-v2 or another task system.

**What it is.** A `thread` projection joins four already-existing sources: active goal, OPEN-THREADS.md entries, native TaskCreated/TaskCompleted/Workflow state, and ledger decision/failure/milestone events. Each thread has `thread_id`, `owner_words_hash`, short title, parent/child links, state, `last_external_receipt`, `next_action`, and `superseded_by`. “Discussed” does not mean every idea becomes a task. In shadow mode a deterministic candidate extractor looks for list structure, explicit commitments (“I’ll also…”, “after X…”), owner imperatives, unresolved AskUserQuestion options, and interrupted question sequences. Ambiguous candidates remain `candidate`, invisible to the owner.

The essential difference from a reminder is **escrow**: closure requires an event outside the proposing context. A file-deliverable thread closes only after file existence/readback plus relevant test/build receipt; a research thread closes after the artifact exists and citations resolve; a decision thread closes only after owner choice or an explicitly authorized default; a Task thread closes on native TaskCompleted plus its required receipt. An assistant sentence saying “done” cannot close it.

**Why inferred / owner signal.** The corpus contains an owner message naming two ignored requests in one turn (`corpus.json:11453`), another saying an assigned item had already been requested (`corpus.json:11339`), and a manual compaction handoff that reconstructs files, tests, and unfinished state (`corpus.json:12197`). Those are signals that the owner wants not merely recall but assurance that parallel/subordinate threads survive. Existing event-ledger annotations already recognize decisions, failures, goals, and milestones and tombstone superseded failures (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/note.py:2-12`, `25-42`); the missing design step is projecting those facts into conversational thread lifecycle.

**How to build.** Add `thread_opened`, `thread_linked`, `thread_external_progress`, `thread_closed`, and `thread_superseded` event shapes to the shared ledger, plus a deterministic projection that can render/update the canonical OPEN-THREADS.md. Fold extraction into the existing `UserPromptSubmit`/`Stop` module path. On `TaskCreated`, link the task to the highest-overlap open thread; on `TaskCompleted`, wait for the typed result receipt already recorded by the ledger. At `PostCompact`/resume, inject at most three lines: active thread, next externally grounded action, and count of sibling threads—not the full backlog. At natural completion, mention only remaining blocking threads; never nag about candidates. Use the existing shadow ladder (`modules.py:118-149`), fail open, and cap all injected continuity context.

**EXTERNAL signal that verifies it.** Run 100 sessions in shadow. A fresh-context auditor compares owner prompts + objective events to projected threads, with known-positive controls seeded from `corpus.json:11453` and known-negative controls from system task notifications. Independently count subsequent owner “forgot/ignored/already told” corrections whose referenced item had no open thread. Ship advisory injection only if candidate precision ≥90%, verified thread recall ≥95%, and owner repair turns decrease without increased AskUserQuestion count. The claim that thread escrow will reduce discussed-then-forgotten stress is **likely (55-80%)**, supported by explicit ignored-thread samples and by native task/receipt availability, but remains UNVERIFIED until that shadow comparison.

**SOTA.** LongMemEval identifies information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention as distinct long-term-memory abilities and reports a large sustained-interaction accuracy drop in existing systems: https://arxiv.org/abs/2410.10813 . LoCoMo-Plus targets the harder cue/constraint disconnect where latent goals or values must apply even when the later wording does not overlap: https://arxiv.org/abs/2602.10715 . Thread escrow operationalizes those abilities without adding a vector database or knowledge graph.

**Value × effort.** **transformative × medium.** It directly addresses the hard “never drop a thread” constraint, while reusing present storage and events.

**Novelty.** **inferred-surprise.** The owner named OPEN-THREADS.md as existing; the new move is to make it a receipt-closed projection of conversation, tasks, and tools rather than another manually maintained note.

**Autonomy.** **just-do-it.** Open candidates in shadow, link tasks, and close against deterministic receipts without prompting. Intentionally dropping or materially reprioritizing an owner-requested thread remains outside this autonomous proposal and uses the existing AskUserQuestion surface once, with the impacted threads named.

## 3. Inferred surprise — Short-cue intent compiler (“continue”, “that one”, “again”) **[UNVERIFIED — experiment: time-split short-cue replay against actual next actions]**

**Improvement.** Make a few words sufficient when—and only when—the current state contains one externally supported interpretation. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `GoalModule` and `RecallModule` in the shared dispatcher; replace neither memory store and add no hook.

**What it is.** A short cue is compiled against a bounded `continuity packet`:

1. the session’s active goal;
2. one active thread plus up to two sibling thread titles;
3. the last owner-selected option;
4. the last externally verified tool/task receipt;
5. explicit negative constraints/preferences with valid provenance;
6. a live-state checksum from Finding 4.

Resolution is deterministic where possible. “Continue” selects the unique active, unblocked thread. “Again” selects the most recent failed/interrupted action only if a failure/interrupt event exists. “That one” selects the most recent owner-visible option only if exactly one candidate is salient. A project noun selects a thread by exact alias/title match. If there are multiple materially different candidates, do not guess: use one compact AskUserQuestion with 2–3 choices and consequences. If the choice is reversible and cheap, act on the top interpretation in a reversible sandbox/worktree and state the interpretation in the normal progress update, not in a new confirmation prompt.

**Why inferred / owner signal.** Current code explicitly preserves the goal for short acknowledgements (`modules.py:1326-1338`) but bounded recall rejects prompts under 40 characters (`modules.py:1608-1614`), while the older recall hook rejects under 15 characters (`recall-inject/inject.py:343-369`). This is a structural mismatch with the target. Corpus samples include “go again at it since it seems you were stuck” (`corpus.json:10565`) and “why did you stop…” (`corpus.json:12251`), showing that short continuation cues already occur. The owner’s real need is not more verbose summaries; it is reliable reference resolution that preserves focus.

**How to build.** Add `ShortCueResolver` as a function inside the existing goal/recall module, gated on ≤12 tokens or deictic/continuation terms. It reads the thread projection and typed receipts locally. Emit `resolved_thread_id`, `resolution_basis` (event IDs, never chain-of-thought), `ambiguity_count`, and an injection capped around 400 characters. Never call semantic/vector/network/model search from the hook; the shared harness already promises recall is local lexical only (`README.md:23-29`). Add a `short_cue_resolution` shadow event. Preserve the current high-precision bounded recall for longer prompts. All exceptions return success/no injection.

**EXTERNAL signal that verifies it.** Build a time-split replay set: for each historical short cue, hide all events after the cue, give a fresh-context evaluator the proposed continuity packet, and compare its selected thread/next action against (a) the actual next native task/tool sequence and (b) whether the owner corrected the interpretation in the next two owner turns. Use explicit ambiguous cases to test abstention. Require ≥90% top-1 accuracy on unique-thread cases, ≥95% abstention on materially ambiguous cases, and no increase in owner clarification turns. The claim that this will make “continue” reliably sufficient is **very likely (80-90%)** for unique active-thread cases because the selection is deterministic and externally grounded; it is **roughly even (45-55%)** for deictic cues across multiple parallel threads because salience is not fully represented in the current ledger. Both claims are UNVERIFIED until replay.

**SOTA.** LoCoMo-Plus specifically evaluates cue–trigger semantic disconnect rather than surface factual overlap: https://arxiv.org/abs/2602.10715 . Microsoft’s 2025 CHI proactive-programming study emphasizes a shared workspace as the context that enables relevant proactive suggestions: https://www.microsoft.com/en-us/research/publication/need-help-designing-proactive-ai-assistants-for-programming/ . Google’s AAC study found that less typing can reduce effort but that generated language must reflect the user’s own style/preferences: https://research.google/pubs/the-less-i-type-the-better-how-ai-language-models-can-enhance-or-impede-communication-for-aac-users/ .

**Value × effort.** **transformative × medium.** This is the direct mechanism for the stated few-words-suffice target.

**Novelty.** **inferred-surprise.** Semantic recall already exists; the new capability is an abstaining reference compiler tied to thread and receipt state.

**Autonomy.** **just-do-it.** Act when one reversible interpretation is externally supported. Multiple interpretations that produce materially different or irreversible actions fall outside this autonomous proposal and use one bounded existing AskUserQuestion; this replaces broad re-explanation rather than adding a routine prompt.

## 4. Inferred surprise — Live-state checksum before memory is trusted **[UNVERIFIED — experiment: resume fault-injection with stale summaries and changed worktrees]**

**Improvement.** Prevent memory from confidently restoring a state that the files, git tree, task runtime, or tool endpoint no longer support. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold live probes into the existing SessionStart/PostCompact recovery module and reuse MCP-liveness, capability-catalog, event-ledger, and typed receipts.

**What it is.** Before injecting the continuity packet after resume/compact—or before resolving a fresh-session “continue”—compute a cheap checksum from independent facts: canonical project identity, git HEAD/branch/dirty count, existence+mtime/hash of thread-linked artifacts, current native Workflow/Task state, and liveness only for the named tool endpoint. Compare it to the last ledger checkpoint. Inject deltas, not a narrative: `HEAD changed`, `artifact missing`, `task stopped`, `endpoint unavailable`, `receipt stale`. The historical memory remains context, never ground truth for current state.

This is not another truth-verify hook. It is recovery input validation inside the existing ledger replay. It specifically builds on the B1 MCP-liveness self-heal+alert, capability catalog, edit checkpoints, and truth-verify named in the brief. It calls those current sources or their receipts; it does not reimplement them.

**Why inferred / owner signal.** The corpus preserves a manual handoff saying “Do not trust the compaction summary for completion status—read the actual files” and then listing file/test probes (`corpus.json:12197`). Existing recovery replay labels stored text as sanitized historical data (`modules.py:973-1003`), but its injected state is drawn only from ledger entries. The older stop hook already records git HEAD, branch, and dirty count and fails open (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/stop-hook.py:76-100`), proving these probes are available cheaply. The owner’s unasked need is for memory that knows when it is stale.

**How to build.** Extend recovery replay with a `recovery_checksum` helper that has a strict 500–800 ms aggregate budget and parallel stdlib subprocess/file probes. Use only thread-linked paths; no recursive glob. Read liveness from the existing liveness/capability receipt rather than calling every MCP. Store the checksum as a ledger event. If a probe fails, mark that field `unknown` and continue; never treat unknown as absent. Validate the detector with a known-present fixture file and a known-live mock tool before drawing absence conclusions. The injection should remain under the current 4,000-character replay cap (`modules.py:999-1003`) and preferably much smaller.

**EXTERNAL signal that verifies it.** Fault-inject resumes where summaries claim (a) a file exists but it was renamed, (b) tests are green but the source changed afterward, (c) a task is running but emitted a stopped event, and (d) an endpoint is down while another known-live endpoint proves the liveness detector. A fresh-context agent must choose the externally correct next action without seeing the fault setup. Require 100% detection on deterministic fixtures, no false “absent” report, and p95 added recovery latency below one second. The claim that the checksum will prevent stale-completion replays is **very likely (80-90%)**, because deterministic file/git/task probes are independent of the stored narrative; evidence is existing git capture at `stop-hook.py:85-94` and native receipt recording at `modules.py:1036-1077`.

**SOTA.** LongMemEval makes knowledge updates and abstention first-class memory abilities rather than treating recall alone as success: https://arxiv.org/abs/2410.10813 . NIST defines validation as confirmation through objective evidence and recommends continuous assurance after deployment: https://csrc.nist.gov/pubs/conference/2022/10/03/ai-assurance-for-the-public/final .

**Value × effort.** **high × low.** It sharply improves trust in recovered context with a small deterministic extension.

**Novelty.** **inferred-surprise.** The harness already stores memory and verification receipts; the new move is to make recovery conditional on a live-state checksum.

**Autonomy.** **just-do-it.** All probes are read-only and local. Confirm only if a mismatch implies a destructive reconciliation choice; merely reporting and adapting to a mismatch requires no prompt.

## 5. Inferred surprise — Evidence-weighted preference ledger with expiry and counter-evidence **[UNVERIFIED — experiment: prospective preference prediction with owner overrides]**

**Improvement.** Let the harness grow with the owner without turning one frustrated correction into a permanent personality rule. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing basic-memory note schema and shared recall-index fields; do not build another user-profile store, vector DB, KG, trained critic, or continuous-learning-v3.

**What it is.** Add a small `user-preference` frontmatter contract to basic-memory/continuous-learning-v2 records:

`scope`, `behavior`, `polarity`, `source_event_ids`, `evidence_types`, `first_seen`, `last_confirmed`, `confidence_band`, `counterevidence_ids`, `expires_at`, `superseded_by`, and `stakes_limit`.

Promotion rules are mechanical. One explicit owner instruction may create an `explicit` scoped preference. An implicit behavior becomes active only after the same choice is observed in at least two different sessions or two different external action types. A correction is negative evidence, not automatically a universal rule. Conflicts lower confidence or create a narrower scope; weak preferences decay. Only explicit, current preferences may steer high-stakes/irreversible choices. The owner can inspect/edit the markdown record directly.

**Why inferred / owner signal.** The corpus contains both repeated style/effort instructions and task-specific corrections, but its candidate detector confuses agent-authored prompts with owner speech (`corpus.json:10372-10374`). Naively learning all 2,268 candidates would personalize to the harness’s own echoes. The current index already retains importance, superseded-by, failure-head, and poisoning fields (`/local_disk0/codexwork/bundle/agents/harness/recall_index.py:40-44`, `283-298`), and global guidance already requires temporal validity via `superseded_by` and `valid_as_of` (`CLAUDE.md:9-11`). The owner signal implies a preference model is wanted, but also that provenance and forgetting are essential.

**How to build.** Update the basic-memory note template and recall-index schema to recognize `type: user-preference`; reuse current importance/supersession logic. continuous-learning-v2 may propose candidates, but promotion consumes external ledger event IDs and cross-session separation. Inject at most the top three in-scope preferences in the continuity packet. Never surface a “please rate this preference” prompt. When two live preferences materially conflict, use one AskUserQuestion naming the conflict and write the answer as explicit evidence. A nightly/local report can list expiring or contradicted preferences for optional review, but silence is the default.

**EXTERNAL signal that verifies it.** For each active preference, predict an observable owner choice on the next eligible task before seeing it; score against owner override/correction, chosen AskUserQuestion option, rollback, or explicitly requested style. A second, fresh-context evaluator checks whether cited source events actually entail the scoped preference. Promote only when both provenance precision and prospective prediction exceed thresholds; expire when counter-evidence accumulates. The claim that this will reduce repeated preference restatement without fossilizing transient frustration is **likely (55-80%)**, supported by existing temporal-validity fields and cross-session signals, but UNVERIFIED until prospective prediction.

**SOTA.** PerMemBench argues that what is worth storing differs by user and reports that personalized retention helps under perfect gating while accurate gating remains an open problem: https://arxiv.org/abs/2605.25535 . COLING 2025’s evolving conditional-memory work studies plug-and-play memory that preserves user knowledge/preferences over time: https://aclanthology.org/2025.coling-main.254/ . Google’s steerable-chatbot user study reports heterogeneous preferences for control, transparency, and usability in personalization interfaces: https://research.google/pubs/personalizing-llms-with-preference-based-activation-steering/ . These findings support explicit provenance/control and argue against a hidden monolithic persona.

**Value × effort.** **high × low.** The storage and recall fields mostly exist; the work is schema/promotion policy and evaluation.

**Novelty.** **inferred-surprise.** continuous-learning and instincts already exist; the new part is preference-specific evidence, negative evidence, scope, and expiry rather than another learning subsystem.

**Autonomy.** **just-do-it.** Create shadow candidates and apply externally supported preferences to low-stakes reversible behavior. Consequential/irreversible changes and conflicts between explicit preferences remain outside this autonomous proposal and use the existing confirmation path.

## 6. Inferred surprise — Attention-priced proactivity: suggestions spend a learned interruption budget **[UNVERIFIED — experiment: randomized shadow/advice trial at natural breakpoints]**

**Improvement.** Become anticipatory without becoming noisy: prefetch/read/check proactively, but speak only when expected benefit exceeds the owner’s observed interruption cost. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing calibrated-silence/staging configuration and selection-event ledger; add no hook, model, daemon, or UI.

**What it is.** Every possible proactive contribution receives a simple deterministic score:

`expected avoidable repair turns × confidence × urgency − interruption_cost − action_risk`.

Use four delivery modes: `silent prefetch`, `fold into next normal update`, `one-line interjection at a breakpoint`, and `AskUserQuestion`. Signals for low interruption cost include a completed tool/task, an owner question, a session start/resume, a detected stall, or an already-required status update. High-cost signals include rapid owner steering, active multi-turn clarification, recent dismissal, and repeated hook feedback. The default proactive action is a silent, reversible read/check. Recommendations queue until a meaningful breakpoint. Per-session caps and per-category cooldowns prevent prompt fatigue.

**Why inferred / owner signal.** The hard constraints state the owner’s session quality tracks focus and that prompt fatigue is a regression. The live defect report documents 8+ false flags and a workaround that raised failure rate (`INPUT-known-harness-defects.md:94-102`), while the older recall and persist hooks already attempt calibrated-silence gating and once-per-session dedup (`recall-inject/inject.py:203-237`, `379-389`; `/local_disk0/codexwork/bundle/claude/hooks/persist-nudge/nudge.py:9-15`, `156-183`). The missing capability is a shared, outcome-updated attention price across all proactive behaviors.

**How to build.** Add JSON weights/caps to the existing staging/calibrated-silence state: `max_visible_interjections_per_session`, cooldown, breakpoint kinds, and rolling outcomes. Reuse selection events and continuity receipts to classify an interjection as `accepted` (owner follows it / relevant tool succeeds), `dismissed` (owner says no/returns to prior thread), `ignored`, or `repair_prevented` (thread resolved without restatement). These outcomes are external to the proposing context. Keep the policy transparent and editable; do not train a critic or add reinforcement-learning infrastructure. Silent prefetch may use existing capability-catalog/MCP-liveness results but must not spend metered services.

**EXTERNAL signal that verifies it.** Randomize eligible shadow events between “would surface now,” “would defer,” and “silent only,” then compare acceptance, owner steering/correction, AskUserQuestion count, time-to-next-progress receipt, and context-repair turns. Only enable visible advice when deferral at breakpoints reduces interruptions without reducing useful acceptance. The claim that breakpoint delivery will lower disruption is **likely (55-80%)**, supported by interruption research and existing owner false-nudge evidence, but remains UNVERIFIED in this owner’s workflow. The claim that more proactive messages by themselves improve outcomes is **unlikely (20-45%)**, because prompt-fatigue evidence and mixed-initiative research both show timing and relevance dominate raw suggestion count.

**SOTA.** The CHI 2025 proactive-programming study experimentally evaluates design elements of automatically offered suggestions and highlights shared-workspace context: https://www.microsoft.com/en-us/research/publication/need-help-designing-proactive-ai-assistants-for-programming/ . BusyBody models personalized interruption cost from current/recent activity and context: https://www.microsoft.com/en-us/research/publication/busybody-creating-fielding-personalized-models-cost-interruption/ . Classic mixed-initiative principles explicitly trade the value of service against attention/timing: https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/ .

**Value × effort.** **high × low.** It protects focus while allowing the other findings to become more proactive.

**Novelty.** **inferred-surprise.** calibrated-silence already exists; the advance is a single measured interruption budget driven by subsequent owner/tool outcomes, not per-hook heuristics.

**Autonomy.** **just-do-it.** Score in shadow, prefetch silently, and fold information into an already-required update. An underlying action that independently requires confirmation remains governed by its existing permission path; the predicted suggestion creates no new confirmation.

## 7. Inferred surprise — Evidence-earned autonomy ladder with compact trust receipts **[UNVERIFIED — experiment: per-action-class shadow policy against rollbacks and owner interventions]**

**Improvement.** Grow from “ask often” to “few words suffice” by earning autonomy separately for each action class from real outcomes, while making failures legible enough to calibrate trust. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Configure policy over the existing Workflow, AskUserQuestion, edit-checkpoint/rollback, truth-verify, typed receipt, and shadow-staging mechanisms; build no guardrail framework.

**What it is.** Maintain a transparent action-class table, not a global trust score:

* **A0 observe:** read/search/status—just do it.
* **A1 reversible local:** scoped edit with checkpoint, local test, easy rollback—just do it when intent resolution is unique.
* **A2 reversible but broad/costly:** multi-file change, long workflow, paid/metered call—act under an existing explicit goal; otherwise one bounded confirmation.
* **A3 externally consequential:** publish, message, merge/push, spend, secrets/credentials, destructive/nonrecoverable—confirm first unless a current explicit standing authorization covers the exact class.

For each class, track external success receipts, owner overrides, rollbacks, correction turns, and unverified completion claims. Promotion changes only prompt policy within the class and only after a minimum evidence count; one severe failure demotes it. At completion, show a compact receipt (“changed X; test Y passed; thread Z remains”) rather than a persuasive explanation. Sources and inconsistencies matter more than fluent rationale.

**Why inferred / owner signal.** Repeated “why did you stop”/continue patterns (`corpus.json:10425`, `10461`, `10569`, `12251`) signal under-autonomy in long-running authorized work; the live defect report’s fabricated Write constraint propagated to ~15 prompts and forced a worse workaround (`INPUT-known-harness-defects.md:151-160`), showing that static global restrictions can create systematic under-use. At the same time, the law for this unit forbids same-context assurance. The shared ledger already records verified tool results (`modules.py:1048-1077`) and the edit-checkpoint system is explicitly in the dedup list, so earned autonomy can be outcome-based rather than confidence-based.

**How to build.** Add an editable `autonomy-policy.json` keyed by action class with `mode`, `minimum_receipts`, `max_override_rate`, `max_rollback_rate`, `standing_authorization_source`, and `last_demoted`. Reuse typed receipts and thread IDs. AskUserQuestion occurs only when the action class and authorization state require it. For A1, checkpoint → edit → external test → rollback on failure is the closed loop. For A2/A3, the owner is the external signal. Keep any natural-language model confidence out of promotion decisions. Fail open here means a policy-reader error falls back to the platform’s native permission behavior; it must never silently expand authority.

**EXTERNAL signal that verifies it.** Shadow-log the action the ladder would choose and compare it to actual owner approvals/rejections, rollbacks, tool receipts, and later corrections. Promote one class at a time only if intervention/rollback does not worsen and context-repair/confirmation turns fall. A different-context reviewer audits a sample of receipt-to-action mappings. The claim that action-class-specific autonomy will reduce unnecessary questions without increasing consequential errors is **likely (55-80%)**, supported by existing checkpoint/receipt mechanisms and observed under-autonomy, but UNVERIFIED until the per-class trial.

**SOTA.** NIST states that trustworthiness is contextual, requires balancing criteria, and that human judgment should set metrics/thresholds for the use context: https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/ . A CHI 2025 preregistered experiment found that explanations increase reliance on both correct and incorrect LLM answers, while sources and inconsistencies reduce reliance on incorrect answers: https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies/ . A 2025 Microsoft technical report warns that overreliance mitigations can backfire and should be user-tested: https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-genai-lessons-learned-from-early-research/ . These results favor compact external receipts and per-class outcome calibration over more self-explanation.

**Value × effort.** **transformative × low.** The mechanism largely configures existing buses and turns verified history into less owner friction.

**Novelty.** **inferred-surprise.** Permissions and checkpoints already exist; the advance is evidence-earned, per-action prompt policy rather than a static autonomy setting or agent self-confidence.

**Autonomy.** **confirm-first.** This proposal changes confirmation policy and therefore requires owner approval before activation. Once approved, A0/A1 within a uniquely resolved goal run autonomously; A3 and any A2 lacking explicit scope retain confirmation. The ladder may reduce confirmation frequency but never manufacture authority.

## Integrated architecture

The minimal architecture is deliberately one loop over the existing bus:

```text
owner cue
   |
   v
existing UserPromptSubmit dispatcher
   |-- ledger candidate flags (Finding 1, silent)
   |-- thread projection (Finding 2, shadow)
   |-- short-cue resolver (Finding 3, bounded/abstaining)
   |-- scoped preferences (Finding 5, evidence-bearing)
   `-- attention/autonomy policy (Findings 6–7)
            |
            v
       continuity packet (small)
            |
            v
       existing tools / Workflow / Task
            |
            v
PostToolUse + TaskCompleted + git/files + owner next turn
            |
            v
external receipts close threads, score resolution, update preference/proactivity/autonomy
```

SessionStart/PostCompact first runs the live-state checksum (Finding 4), so the packet is a delta against current external state rather than a replayed self-narrative. The offline continuity report reads the resulting ledger and transcript slices. No runtime calls a second model; different-context evaluation is a batch/skill action during shadow evaluation, avoiding latency and keeping the steady-state harness simple.

### Hook-ceiling accounting

There is **no seventh hook**. Runtime changes fold into shared events already registered in `settings.json`: SessionStart (`90-103`), UserPromptSubmit (`117-126`), PostToolUse (`310-320`), PostCompact (`393-404`), and TaskCompleted (`458-468`). The local dispatcher’s explicit purpose is to replace many process spawns with one event invocation and wrap each check fail-open (`_dispatch/dispatch.py:2-19`, `41-45`). If implementers discover the provider-neutral dispatcher cannot expose one required native field, the proposal becomes **UNVERIFIED — run the hook-input-schema capture experiment before code; do not add a hook as a workaround.**

### Prompt-fatigue accounting

The visible-interjection budget is non-increasing:

* Findings 1, 2, and 5 are silent in shadow.
* Finding 4 silently probes and injects only actual recovery deltas.
* Finding 3 asks only when two materially distinct interpretations remain; otherwise it removes a re-explanation turn.
* Finding 6 caps proactive output and defers it to natural breakpoints.
* Finding 7 reduces confirmations only after external evidence.

The primary regression metric is not “number of features enabled”; it is owner repair turns + clarifying prompts + proactive interjections per 100 owner turns. A capability that improves task accuracy but raises this combined attention tax is not promoted without an explicit owner decision.

### Never-drop accounting

Thread candidates cannot disappear silently. They either remain candidates, become open, close on an external receipt, are superseded by a named thread, or are dropped by owner choice. “Done” text is not a receipt. A rendering failure in OPEN-THREADS.md leaves the append-only ledger authoritative and returns success/no block. The thread projector must be rebuildable from ledger events.

### Fail-open accounting

Every runtime function is `try/except → HookResult.success()` or exit 0. Unknown probe state is `unknown`, never “absent.” A failed preference/autonomy configuration read falls back to native platform permissions, never expanded authority. Timeouts drop optional context rather than blocking the owner. This matches the shared harness invariant that unexpected module errors fail open (`agents/harness/README.md:17-27`) and the local dispatcher contract (`_dispatch/dispatch.py:41-45`).

## Anti-overfit gate

All seven proposals pass the anti-overfit gate:

* They ride the existing lifecycle dispatcher, event ledger, basic-memory, OPEN-THREADS.md, Workflow/Task/AskUserQuestion, edit checkpoints, and typed receipt bus.
* They introduce no second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
* The runtime logic is deterministic and bounded. The only second-model use is offline evaluation in a fresh context; it is an external verifier, not a new runtime service.
* Every heuristic starts in existing shadow mode and has a falsifiable metric/deadline. If it does not reduce verified attention tax, it is removed rather than tuned indefinitely.
* The design prefers one small continuity packet to ever-growing instructions. This is important because the current recall index already supports recency, importance, supersession, and contradiction-first ranking (`recall_index.py:283-298`; `modules.py:1693-1705`); another memory architecture would duplicate capability and increase failure surface.

## Alternatives considered and rejected

### A new vector DB / user knowledge graph

Rejected. basic-memory already supplies semantic durable memory and the shared harness already indexes it; the brief explicitly rejects vector-DB/KG memory. The target failure is reference resolution, provenance, and lifecycle, not storage capacity. Engrama-style structured retrieval may improve some cross-space reasoning, but the proposed thread projection captures only operational lifecycle and does not introduce a graph runtime.

### A second orchestration or durable-execution service

Rejected. Native Workflow/Task events and the event ledger already expose task lifecycle. Adding a daemon would violate the anti-overfit gate and need independent operations/health management. Thread escrow is a projection, not an executor.

### Injecting a full summary on every prompt

Rejected. It would worsen prompt fatigue, increase context competition, and retain the same self-narrative failure mode. Existing bounded recall already caps results and performs high-precision lexical selection (`modules.py:1623-1681`). The correct extension is a tiny continuity packet for short cues plus live-state deltas.

### Asking the owner to confirm every inferred preference or thread

Rejected. It moves labeling cost onto the owner and directly violates the focus constraint. Shadow candidates, cross-session evidence, and prospective behavior provide lower-cost signals. Ask only where ambiguity changes a consequential action.

### Same-context self-reflection as verification

Rejected by construction. /self-reflect and prompt optimization may improve reasoning, but they cannot certify continuity interpretation or completion here. Every promotion/closure rule above uses owner behavior, a fresh context, native events, or execution results.

### A learned critic or online reinforcement learner for proactivity

Rejected. A transparent deterministic score with per-category observed outcomes is sufficient for the initial design. A trained critic would add an ungrounded component, obscure why the system interrupted, and violate the anti-overfit exclusion.
