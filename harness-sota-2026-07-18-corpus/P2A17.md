# P2A17 — Cost/latency engineering for large fan-outs

**Unit:** P2A17  
**Lens:** external research only  
**Research date:** 2026-07-18  
**Question:** Caching, model routing, batching, and when a cheaper model is genuinely sufficient for large agent fan-outs.

## Executive conclusion

The best-supported design is not a universal “smart router.” It is a short stack of increasingly speculative optimizations:

1. Make repeated prompt prefixes byte-stable and use the provider's native prefix cache. OpenAI, Anthropic, Azure OpenAI, and Amazon Bedrock all document prefix caching; their TTLs, minimum prefix sizes, price multipliers, and batch interactions differ, so cache behavior must be observed from returned usage fields rather than assumed. OpenAI's current guide says caching begins at 1,024 tokens, exposes `cached_tokens` and `cache_write_tokens`, and recommends static content first; Anthropic exposes separate write/read counters and currently prices 5-minute writes at 1.25×, 1-hour writes at 2×, and reads at 0.1× base input price. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing) [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) [Azure OpenAI prompt caching](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/prompt-caching)
2. Put deadline-free independent work onto a provider-native asynchronous batch lane. OpenAI and Anthropic both advertise a 50% discount and completion/expiry within 24 hours; OpenAI also assigns Batch a separate, larger rate-limit pool. This is a real cost mechanism, not “send N synchronous requests at once.” [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch) [Claude batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
3. Route by a small, explicit task-class/model eligibility matrix, starting with only two tiers. Current large comparative work finds that several sophisticated routers do not reliably beat simple baselines, gains often come from coarse domain structure, larger model pools have diminishing returns, and careful model selection matters more than pool size. [LLMRouterBench](https://arxiv.org/abs/2601.07206) RouteLLM itself says thresholds must be calibrated on queries resembling the deployment workload. [RouteLLM repository](https://github.com/lm-sys/RouteLLM)
4. Call a cheaper model “sufficient” only when replacing the expensive call preserves the **end-to-end task outcome** on held-out, repeated trials at an explicit risk bound. One-shot public benchmarks and LLM-judge preferences are not enough for an agent. TwinRouterBench's central criticism is precisely that older router tests do not test whether a cheaper intermediate call preserves downstream agent success; its live track measures official task resolution and realized spend. [TwinRouterBench](https://arxiv.org/abs/2605.18859) Anthropic's agent-eval guidance likewise distinguishes transcript from final environment outcome and recommends multiple trials because agent behavior is nondeterministic. [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
5. Bound concurrency and measure fan-out completion p50/p95/p99, not only individual-call latency. In a fan-out/fan-in stage, the slowest required child controls completion; classic “tail at scale” work shows rare component delays become dominant at scale. Hedging can reduce tails in some systems, but independent research also identifies realistic regimes where hedging provides no benefit over good load balancing and adds load, so paid LLM calls should not be hedged by default. [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) [When to Hedge in Interactive Services](https://www.usenix.org/conference/nsdi21/presentation/primorac)

This ordering passes the anti-overfit gate: it rides provider APIs and the existing hook/skill/script bus; it does not require a second orchestration runtime, vector-DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Method

I investigated four sub-questions: provider-native caching/batching economics; empirical cache behavior in long-horizon agents; model-routing evidence and failure modes; and fan-out/tail-latency mechanics. Sources were prioritized in this order: current official provider documentation, original papers/conference publications, and real open-source repositories. Vendor performance claims are identified as such. No claim about this owner's current implementation is made, because this unit was explicitly external-only.

The most important source limitation is temporal volatility: API prices, model names, TTLs, and feature compatibility can change. The linked provider pages are the authority at deployment time. The architectural findings—measure cache hits, separate offline from interactive work, validate routing on end outcomes, and control tail latency—are less volatile than any quoted price.

## 1. What is actually established

### 1.1 Large fan-outs multiply token cost and expose tail latency

Anthropic reports that, in its research product data, agents used about 4× the tokens of chat interactions and multi-agent systems about 15× the tokens of chats. This is an observational result from one production system, not a universal constant, but it establishes that fan-out can multiply token use enough to dominate optimization priorities. [Anthropic, “How we built our multi-agent research system”](https://www.anthropic.com/engineering/multi-agent-research-system)

Fan-out completion latency is governed by the slowest child whose result is required at the join. Dean and Barroso's original “Tail at Scale” article establishes that occasional component-level high-latency episodes can dominate whole-service latency as system size and utilization rise. That finding predates LLMs but directly applies to any required-all-results fan-out/fan-in graph. [Google Research, “The Tail at Scale”](https://research.google/pubs/the-tail-at-scale/)

Therefore, average per-call latency is not a sufficient harness metric. At minimum, an orchestration run needs stage-level wall time, time-to-first-token (TTFT), full completion time, queue delay if observable, and fan-out p50/p95/p99. Anthropic's latency guide distinguishes baseline latency from TTFT and recommends shorter inputs/outputs and streaming for perceived responsiveness. [Anthropic latency guidance](https://docs.anthropic.com/en/docs/test-and-evaluate/strengthen-guardrails/reduce-latency)

### 1.2 Provider prefix caching is real, useful, and exact-prefix sensitive

OpenAI currently enables prompt caching automatically for eligible recent models. Its guide says the default minimum is 1,024 tokens; requests are routed using a hash of an initial prefix; `prompt_cache_key` can improve co-location; and static/repeated material should precede dynamic/user-specific material. Returned usage distinguishes `cached_tokens`, and newer model families also report billable `cache_write_tokens`. OpenAI also warns to shard high-volume traffic rather than drive one cache key far beyond roughly 15 requests/minute. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

Anthropic supports automatic caching and explicit breakpoints. Its official pricing page currently gives 1.25× base input for a 5-minute cache write, 2× for a 1-hour write, and 0.1× for a hit; it explicitly calculates that a 5-minute cache pays back after one read and a 1-hour cache after two reads. Its prompt-cache guide says too-short marked prefixes are processed without caching and recommends verifying the result through `cache_creation_input_tokens` and `cache_read_input_tokens`. [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing) [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Amazon Bedrock documents the same core semantic—static contiguous prefixes and explicit checkpoints—but with model-dependent minimum token counts, checkpoint limits, and TTL support. It says changes in earlier sections invalidate later cache segments, recommends stable `tools` and `system` before variable `messages`, and reports `cacheReadInputTokens` and `cacheWriteInputTokens`. Bedrock also states that its prompt cache is not supported by its batch inference API. [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)

Azure OpenAI documents automatic prefix reuse, typical eviction after 5–10 minutes of inactivity and removal within an hour, and billing discounts that depend on deployment type. It also states caches are not shared between Azure subscriptions. [Azure OpenAI prompt caching](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/prompt-caching)

The cross-provider conclusion is established: prompt caching is a KV/prefix reuse mechanism, not an answer cache. It preserves model behavior while avoiding repeat processing of an exact reusable prefix. The operational details are provider- and model-specific, so a harness must record actual read/write token fields instead of applying a guessed discount. The provider documentation above independently supports the common mechanism and the differing details.

### 1.3 Cache-aware prompt structure has agent-specific empirical support

The 2026 “Don't Break the Cache” study evaluated more than 500 long-horizon research-agent sessions with 10,000-token system prompts across OpenAI, Anthropic, and Google. It reports 41–80% API cost reduction and 13–31% TTFT improvement, and finds that explicit cache-boundary control—especially keeping dynamic material after stable content and excluding dynamic tool results—was more consistent than naïvely caching full evolving context. It also reports cases in which naïve full-context caching increased latency. These numbers are specific to its models, benchmark, and prompt shape, but the comparative result directly concerns agent loops. [“Don't Break the Cache”](https://arxiv.org/abs/2601.06007)

This aligns with provider mechanics: OpenAI recommends static content first; Bedrock says changing `tools` can invalidate later `system` and `messages` segments; Anthropic's cache is organized around reusable prefixes and breakpoints. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

### 1.4 Asynchronous Batch is an economic lane, not an interactive latency optimization

OpenAI's Batch API offers 50% lower cost than synchronous APIs, a separate pool with higher rate limits, and completion within 24 hours; the official examples include evaluations, classification, embeddings, and offline rendering. A file may currently contain up to 50,000 requests and 200 MB. [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch)

Anthropic's Message Batches API charges 50% of standard prices. Its current documentation allows up to 100,000 requests or 256 MB, says most batches finish within an hour but expire after 24 hours, and notes results can arrive out of order and must be correlated by `custom_id`. The current batch path supports tool use, system messages, multi-turn inputs, and extended thinking, but requests are independent; the docs list several unsupported stateful/routing parameters. [Claude batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) [Claude Batches API](https://platform.claude.com/docs/en/api/messages/batches)

OpenAI Flex is a separate synchronous-looking lower-priority service tier: it is priced at Batch rates but explicitly trades cost for slower responses and occasional resource unavailability. OpenAI calls it suitable for evaluations, enrichment, and asynchronous or lower-priority work. [OpenAI Flex processing](https://developers.openai.com/api/docs/guides/flex-processing)

Consequently, “batch everything” is wrong for a human-blocking agent turn. Batch is established for deadline-free, independent work; it increases allowed completion latency to buy price and capacity. Client-side concurrency of ordinary API calls is not the same product and does not automatically receive the discount.

### 1.5 Routing can save cost, but no router is universally reliable

FrugalGPT demonstrated the basic cascade idea and reported up to 98% cost reduction while matching the best tested individual model on its selected tasks, or a 4% accuracy improvement at the same cost. Those are paper-specific maxima from 2023 model pools, not portable promises. [FrugalGPT](https://arxiv.org/abs/2305.05176)

HybridLLM reported up to 40% fewer large-model calls without a quality drop in its evaluated setting by predicting query difficulty and allowing a test-time quality/cost trade-off. Again, this establishes feasibility, not universal performance. [HybridLLM, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/file/b47d93c99fa22ac0b377578af0a1f63a-Paper-Conference.pdf)

RouteLLM provides an OpenAI-compatible implementation and advertises up to 85% savings while retaining 95% GPT-4 benchmark performance. More importantly for practice, its own documentation says routing thresholds depend on the router and actual query distribution, and recommends calibrating with a representative sample of incoming queries. [RouteLLM repository](https://github.com/lm-sys/RouteLLM)

The strongest recent caution comes from LLMRouterBench: more than 400,000 instances, 21 datasets, 33 models, and 10 routing baselines. It confirms model complementarity, but finds many routing methods broadly similar, several recent/commercial methods unable to reliably beat a simple baseline, diminishing returns from larger ensembles, and a remaining gap to an oracle due in part to missing rare correct experts. It reports up to 31.7% cost reduction while matching the best single model in its evaluated setting—not the much larger maxima often used in routing marketing. [LLMRouterBench](https://arxiv.org/abs/2601.07206)

The established engineering conclusion is narrower than the hype: routing is useful when the workload contains stable, learnable heterogeneity and candidate models have complementary cost/quality profiles. A small domain- or task-conditioned policy can capture much of the gain. A generic router trained on chat preference data is not evidence of success in a long-horizon coding/research harness.

### 1.6 “Cheaper is sufficient” is an end-to-end, workload-specific claim

TwinRouterBench argues that one-shot routing benchmarks miss the central agent question: whether substituting a cheaper model at an intermediate step preserves downstream task success. It publishes a static step-level track and a dynamic agent track; the latter locks the model pool and measures official task resolution and realized API spend on live agent execution. [TwinRouterBench](https://arxiv.org/abs/2605.18859) This is the correct evaluation shape even if its particular datasets are not adopted.

Anthropic's agent-evaluation guidance independently says the transcript is not the outcome: an agent may claim it booked a flight, while the environment state determines whether a reservation exists. It recommends multiple trials, distinguishes capability from regression evaluations, and describes code-based, model-based, and human graders. It also explains pass@k versus pass^k; for dependable automation, consistency across trials (pass^k or per-task failure bounds) matters more than obtaining one lucky success. [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

A cheaper tier is therefore genuinely sufficient for a task class only if all of the following hold on held-out owner-representative tasks:

- The agent's externally verifiable final outcome is non-inferior within a predeclared tolerance, not merely preferred by an LLM judge.
- Safety/integrity regressions are bounded separately from average quality; rare severe failures cannot be averaged away by cheap easy wins.
- Multiple trials characterize nondeterminism.
- Realized total cost includes retries, escalations, router calls, tool calls, and longer cheap-model outputs—not only nominal input-token price.
- Realized wall time includes the routing decision and any failed cheap-first cascade, not only the winning model call.
- The test set is temporally and task-wise held out, and the policy is re-evaluated when model snapshots, prompts, tools, or schemas change.

These requirements follow from the execution-outcome emphasis of TwinRouterBench and Anthropic's eval definitions; the exact non-inferiority margin is a product-risk choice, not something the literature can choose for this owner.

### 1.7 Throughput batching and application batching are different

For self-hosted inference, vLLM's PagedAttention work reports 2–4× throughput improvement at comparable latency over the evaluated serving baselines, enabled by more efficient KV-cache memory management and batching. [vLLM paper](https://arxiv.org/abs/2309.06180) Sarathi-Serve addresses the throughput/latency trade-off through chunked prefills and stall-free scheduling. [Sarathi-Serve](https://arxiv.org/abs/2403.02310)

Those are server-side inference results, not evidence that an API client should concatenate unrelated prompts into one giant prompt or deploy GPUs. Provider-native Batch is an application/API economic contract; continuous batching is a model-server scheduler. Conflating them is a category error. For an API-based personal harness, self-hosted serving is only relevant if a separate model-hosting decision has already been justified.

## 2. Promising but unproven

### 2.1 A two-tier, task-class router is likely useful

**Confidence: likely (55-80%).** Evidence: HybridLLM, FrugalGPT, and RouteLLM demonstrate substantial savings in selected settings, while LLMRouterBench shows that coarse domain structure captures much of the available routing gain and that carefully curated small model pools outperform indiscriminate expansion. The uncertainty is whether this owner's real agent calls separate into stable cheap-safe and frontier-required classes, and whether retries erase savings. [HybridLLM](https://proceedings.iclr.cc/paper_files/paper/2024/file/b47d93c99fa22ac0b377578af0a1f63a-Paper-Conference.pdf) [FrugalGPT](https://arxiv.org/abs/2305.05176) [RouteLLM](https://github.com/lm-sys/RouteLLM) [LLMRouterBench](https://arxiv.org/abs/2601.07206)

**UNVERIFIED — settling experiment:** replay a stratified sample of real task trajectories with each eligible call downgraded one tier, then run full end-to-end tasks under candidate policies. Compare outcome failures, severe-failure count, total dollars, total tokens, retries, and p50/p95/p99 wall time against “always strong” and “always cheap” baselines. Do not train a router until an explicit task-class table beats both baselines on held-out tasks.

### 2.2 Confidence-triggered cascades are promising for objectively gradable subtasks

**Confidence: likely (55-80%).** Evidence: selective-routing and cascade papers show that uncertainty or difficulty gates can reduce expensive-model calls; conformal routing work offers distribution-free violation guarantees in closed-form benchmark settings. However, the published guarantee cited here is demonstrated on GSM8K/MMLU routing, not open-ended agent work. [Conformal LLM Routing](https://aclanthology.org/2026.acl-srw.70/) [HybridLLM](https://arxiv.org/abs/2404.14618)

The strongest candidates are tasks with mechanical acceptance checks: schema validation, exact classification, compilation, tests, or bounded extraction. They permit cheap-first execution followed by escalation on an observable failure. Open-ended research synthesis and architectural judgment lack a reliable local acceptance signal and are worse cascade candidates.

**UNVERIFIED — settling experiment:** on a held-out set, measure calibration curves for the cheap model's proposed confidence/acceptance signal and the actual mechanical outcome. Compare cheap-first-plus-escalation with direct-strong on total latency and cost. A cascade that saves token price but fails first often enough to increase wall time is rejected.

### 2.3 Cache-conscious fan-out launch ordering may increase hit rates

**Confidence: very likely (80-90%).** Evidence: providers route/cache exact prefixes with short or bounded retention, and OpenAI specifically documents key-based routing and a per-key traffic recommendation. Launching sibling calls that share a stable prefix close together should improve the chance they land inside the cache TTL, while stable-prefix sharding should avoid hot-key misses. The uncertainty is provider scheduling and whether this harness's sibling prefixes are actually identical. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)

**UNVERIFIED — settling experiment:** A/B 100+ identical fan-out families under current ordering versus cache-affinity ordering, using the provider's returned cache-read/write fields. Predeclare hit-rate and TTFT deltas; do not infer success from request timing alone.

### 2.4 Delayed hedging may help only a narrow interactive tail

**Confidence: unlikely (20-45%) as a default; likely (55-80%) only for demonstrated transient stragglers with idempotent/cancelable calls.** Evidence: “The Tail at Scale” shows delayed redundancy can mask stragglers, but NSDI 2021 demonstrates realistic regimes where hedging gives no benefit over optimal load balancing. Paid LLM generation also makes duplicate work directly billable and cancellation may arrive after substantial tokens are consumed. [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) [When to Hedge in Interactive Services](https://www.usenix.org/conference/nsdi21/presentation/primorac)

**UNVERIFIED — settling experiment:** only after collecting per-provider TTFT distributions, shadow-simulate a hedge at the rolling p95 TTFT and estimate duplicate-call rate, canceled-token spend, and p99 improvement. Then run a capped live trial on idempotent, human-blocking calls. Do not hedge full fan-outs or state-changing tool calls.

### 2.5 Semantic answer caching is promising in repetitive FAQ workloads, not general agents

**Confidence: unlikely (20-45%) for this general harness.** Evidence for upside exists: GPT Semantic Cache reported up to 68.8% fewer API calls and positive-hit rates above 97% on its query categories. [GPT Semantic Cache](https://arxiv.org/abs/2411.05276) But semantic-cache correctness is task dependent, and 2026 security research demonstrates collision attacks against embedding-key caches, including response hijacking in agent workflows. [CacheAttack](https://arxiv.org/abs/2601.23088) A cache hit also freezes a past answer that may depend on current files, tool state, time, credentials, or model policy.

**UNVERIFIED — settling experiment:** label a real repeated-query set with “response safely reusable” versus “must recompute,” test false-hit rate under adversarial near-neighbor queries, and include state/version/time in the key. Unless the false-hit risk is acceptably near zero for a narrow read-only task class, use exact content hashes or provider prefix caching instead.

### 2.6 Small-model best-of-N can sometimes beat one expensive sample

**Confidence: unlikely (20-45%) for latency-sensitive agent steps; roughly even (45-55%) for offline mechanically graded steps.** BEST-Route reports that adaptive model-and-sample-count selection can cut cost while keeping performance close in its benchmark, exploiting the fact that several small-model samples may cost less than one large-model call. [BEST-Route](https://proceedings.mlr.press/v267/ding25d.html) But N-way sampling is itself fan-out, requires a reliable selector, and worsens tail latency if all samples are awaited.

**UNVERIFIED — settling experiment:** compare one strong call against N cheap calls plus a mechanical selector on a narrow test-generation or candidate-patch task. Count selector cost and time. Do not use an expensive LLM judge, because that can erase the economic advantage.

## 3. What is hype, and how to tell

### 3.1 “Up to 85–98% savings with no quality loss” is not a deployment forecast

FrugalGPT's 98%, RouteLLM's 85%, and vendor “up to” cache figures are maxima under particular model prices, workloads, prompts, and metrics. [FrugalGPT](https://arxiv.org/abs/2305.05176) [RouteLLM](https://github.com/lm-sys/RouteLLM) [Claude prompt-caching announcement](https://claude.com/blog/prompt-caching) LLMRouterBench's unified comparison reports a materially smaller 31.7% maximum cost reduction while matching the best single model in its evaluated cost setting, and finds several routers fail to beat a simple baseline. [LLMRouterBench](https://arxiv.org/abs/2601.07206)

**How to tell:** reject a savings number that lacks the denominator, price date, candidate model set, routing overhead, retry/escalation cost, end-to-end outcome metric, and held-out evaluation. “Maintains 95% of model X” is not the same as a non-inferiority bound on the owner's tasks.

### 3.2 “AI-powered router” is not automatically better than a table

LLMRouterBench finds many leading routing methods broadly comparable and attributes much of the gain to coarse domain structure; lightweight clustering can perform competitively, larger pools show diminishing returns, and pool curation matters. [LLMRouterBench](https://arxiv.org/abs/2601.07206) RouteLLM itself requires workload-specific threshold calibration. [RouteLLM](https://github.com/lm-sys/RouteLLM)

**How to tell:** require comparisons against four baselines: always strong, always cheap, fixed task-class table, and random routing at the same strong-model fraction. If a learned router does not beat the explicit table on held-out end outcomes after its own latency/cost is charged, it is decorative complexity.

### 3.3 Public benchmark parity does not prove intermediate-call substitutability

Agent mistakes propagate across turns. TwinRouterBench was created because existing router benchmarks generally evaluate one-shot prompts rather than whether a downgraded intermediate call preserves downstream success. [TwinRouterBench](https://arxiv.org/abs/2605.18859) Anthropic's eval guidance distinguishes transcript claims from actual environment outcomes. [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**How to tell:** demand call-position-aware replay and live end-to-end trials. A model that classifies a standalone prompt correctly may still choose the wrong tool, corrupt context, or create recovery work when placed inside an agent loop.

### 3.4 “Batching makes the agent faster” conflates throughput, turnaround, and perceived latency

Provider Batch products explicitly allow up to 24 hours in exchange for price and capacity. [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch) [Claude batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) Server-side continuous batching can raise inference throughput, but it is a serving-engine optimization. [vLLM paper](https://arxiv.org/abs/2309.06180)

**How to tell:** ask which metric improved: aggregate tokens/sec, cost/request, TTFT, time-to-last-token, or full job makespan. An optimization can improve throughput and worsen an individual user's wait.

### 3.5 A cache hit ratio without correctness and dollar accounting is vanity

Provider prefix caches and semantic answer caches are different. Prefix caching avoids repeated computation while still generates a fresh continuation; semantic caching returns a previous answer. The latter can be wrong or attacked even at a high hit rate. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [GPTCache paper](https://aclanthology.org/anthology-files/pdf/nlposs/2023.nlposs-1.24.pdf) [CacheAttack](https://arxiv.org/abs/2601.23088)

**How to tell:** for prefix caching, require cache-read tokens, cache-write tokens, dollars saved net of writes, and TTFT. For answer caching, additionally require false-hit rate, stale-hit rate, tenant isolation, invalidation correctness, and adversarial collision tests.

### 3.6 “More agents/models improve quality” ignores coordination cost and tail amplification

Anthropic's observed token multipliers show multi-agent systems can be far more expensive than chat, and “Tail at Scale” shows more required children expose more latency tails. [Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)

**How to tell:** require marginal value per extra child: incremental end-outcome improvement divided by incremental dollars and p95 makespan. If a child rarely changes the final decision or produces redundant evidence, it should not exist merely to increase “coverage.”

## 4. Specific concrete things this owner's harness should adopt

### 4.1 Stable-prefix compiler and cache telemetry — **CONFIG (settings/JSON only)**

Adopt a canonical prompt order for every fan-out worker:

1. immutable provider/system policy;
2. stable harness rules;
3. deterministically sorted tool schemas;
4. stable task-family rubric/examples;
5. shared corpus/document context;
6. dynamic per-unit assignment;
7. evolving tool results and conversation state.

Use provider-native automatic caching first. Where the active API exposes it, use explicit breakpoints or a stable `prompt_cache_key`; shard cache keys according to provider guidance. Never add timestamps, random IDs, unordered JSON, or unit-specific prose before the cache boundary unless semantically required. Record cache-write tokens, cache-read tokens, uncached input tokens, output/reasoning tokens, model snapshot, TTL/mode if known, TTFT, and completion time per call. OpenAI and Anthropic both expose the required usage counters, and Bedrock exposes analogous fields. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)

**Confidence: almost certain (90-99%) that this is the highest-value low-complexity mechanism for repeated long fan-out prefixes.** Evidence: native support from multiple providers plus the cross-provider long-horizon agent experiment showing 41–80% cost and 13–31% TTFT improvements. The residual uncertainty is the owner's actual repeated-prefix length and hit rate. [“Don't Break the Cache”](https://arxiv.org/abs/2601.06007)

**UNVERIFIED — settling experiment:** a 100-family A/B test must show nonzero cache-read tokens and net dollar/TTFT gains. If common prefixes are below provider minimums or diverge early, the recommendation's benefit for that task family is unverified and it should remain telemetry-only.

**Anti-overfit gate:** passes. This is configuration on native provider behavior and the existing invocation path. It introduces no runtime, daemon, memory system, or trained component.

### 4.2 Two service lanes: interactive and offline — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add one thin submission script or skill with an explicit `latency_class`:

- `interactive`: synchronous request; bounded concurrency; human-visible progress/streaming where available; strict wall-time budget.
- `offline`: provider Batch API, or OpenAI Flex only where supported and acceptable; durable correlation ID in the existing artifact/event record; completion notification/poll through the existing long-operation mechanism.

Eligible offline work: large eval sweeps, corpus classification, embeddings, independent research units whose join is hours away, nightly audits, and bulk summarization. Ineligible: a child on the critical path of the current user turn, stateful dependent steps, or work whose batch API lacks a required feature. OpenAI and Claude document the 50% discount and 24-hour completion/expiry semantics; their feature limits differ and must be checked per request. **Confidence: very likely (80-90%) to halve provider token charges for qualifying deadline-free work.** Evidence: both providers explicitly price Batch at 50% of standard. It will not halve total program cost if tool fees, storage, retries, or non-batched work dominate.

**UNVERIFIED — settling experiment:** run one representative 100-item workload through synchronous and Batch paths, verify identical request semantics and output grading, and compare billed usage plus makespan. The recommendation inherits UNVERIFIED for any provider/model combination until that compatibility test passes.

**Anti-overfit gate:** passes only if implemented as a thin adapter over provider-native APIs and the existing longrun/event path. A new durable-execution service or queue daemon is explicitly rejected.

### 4.3 Explicit two-tier eligibility matrix before learned routing — **CONFIG (settings/JSON only)**

Define a small versioned table, initially with only `cheap` and `strong`, keyed by task class and risk:

| Task class | Initial eligibility | Acceptance/escalation signal |
|---|---|---|
| deterministic classification/extraction | cheap-first | schema + exact invariants; escalate on failure |
| formatting, deduplication, ranking candidates | cheap-first | programmatic checks |
| test generation with executable oracle | cheap-first | tests compile/run; sample strong audits |
| repository-wide design, ambiguous diagnosis | strong | no reliable local oracle |
| final synthesis crossing many child reports | strong | downstream impact and error propagation |
| security/destructive decision | strong | risk floor; never average severe failures away |

The table must identify concrete model snapshots, maximum reasoning effort/output budget, allowed tools, and the eval suite/version that authorized the route. Default to strong for unknown classes. Start with two models; LLMRouterBench finds diminishing returns from larger ensembles and emphasizes model curation. [LLMRouterBench](https://arxiv.org/abs/2601.07206)

**Confidence: likely (55-80%) to capture most safe routing gains with far less complexity than a learned router.** Evidence: LLMRouterBench finds coarse domain structure explains much of leading-router performance; HybridLLM and RouteLLM establish that task difficulty can support a two-tier choice. [HybridLLM](https://arxiv.org/abs/2404.14618) [RouteLLM](https://github.com/lm-sys/RouteLLM)

**UNVERIFIED — settling experiment:** the matrix is not enabled for production decisions until held-out replay and live canaries satisfy Recommendation 4.4. This heading is UNVERIFIED with respect to which exact task classes and models qualify.

**Anti-overfit gate:** passes. It is versioned configuration, not a new router service. A learned neural router is intentionally deferred.

### 4.4 Downgrade-and-cascade qualification harness — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build a small evaluator around the existing run/event interfaces:

1. Sample representative completed tasks by task class and call position.
2. Lock prompts, tools, model snapshots, and environment fixtures where possible.
3. Replace one candidate strong call with the cheap tier; replay the remainder or run the full task.
4. Grade final environment/artifact outcomes mechanically first; use calibrated rubric grading only where no deterministic outcome exists.
5. Run multiple trials and retain full trajectories.
6. Report paired outcome delta, severe failures, dollars, tokens, retry/escalation rate, p50/p95/p99 wall time, and confidence interval.
7. Promote a route only if the upper confidence bound on unacceptable regression is below a predeclared risk tolerance and total cost/latency improves.
8. Canary the route on a small live fraction and auto-revert to the strong tier on drift, schema/tool version change, or budget breach.

This adopts TwinRouterBench's static-then-live, execution-verified shape and Anthropic's outcome/trial distinctions without importing another framework. [TwinRouterBench](https://arxiv.org/abs/2605.18859) [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Confidence: very likely (80-90%) that this method can distinguish many genuinely safe downgrades from benchmark-only ones, provided tasks have meaningful graders.** Evidence: the two independent sources agree that end outcomes and multiple trials are required. Open-ended research quality remains harder to grade.

**UNVERIFIED — settling experiment:** validate the evaluator itself with known-good reference solutions and injected known-bad trajectories, then confirm two independent graders detect them. Anthropic explicitly recommends reference solutions and transcript inspection to expose broken tasks/graders. [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Anti-overfit gate:** passes if it remains a stateless evaluator over existing traces and commands. It must not become a durable-execution engine, trained critic, or observability platform.

### 4.5 Concurrency governor with budgeted joins — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

At every fan-out site, require:

- a per-provider semaphore informed by rate limits and observed overloads;
- a maximum child count and token/dollar budget;
- an explicit join policy: `all`, `quorum(k)`, `first_valid`, or `deadline_then_synthesize`;
- cancellation of unneeded children where the API supports it;
- independent accounting for queue time, TTFT, completion, and join makespan;
- bounded retry with jitter only for transient errors, charged to the same budget;
- no automatic duplicate/hedged paid calls.

The join policy is the important latency lever. If synthesis needs only three independent corroborations, waiting for ten adds tail exposure without necessarily adding value. “The Tail at Scale” supplies the systems rationale; Anthropic's measured token multiplier supplies the agent cost rationale. [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) [Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

**Confidence: very likely (80-90%) to prevent cost explosions and reduce avoidable tail waiting in large fan-outs.** Evidence: fan-out tail amplification is established; exact gains depend on current join semantics and redundancy.

**UNVERIFIED — settling experiment:** replay or simulate recorded child latency distributions under alternative caps/join rules, then run a live canary. Quality must be graded to prove that early stopping did not discard unique necessary evidence.

**Anti-overfit gate:** passes as a small library/hook on the existing dispatcher. A new orchestration runtime is explicitly prohibited.

### 4.6 Exact content-addressed cache only for pure preprocessing — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Use a local exact cache only where the operation is demonstrably pure: token counting, parsing, deterministic corpus transforms, immutable file summarization under a pinned prompt/model for eval replay, or provider-independent preprocessing. Key on the full normalized dependency envelope: input content hashes, operation version, prompt version, model snapshot if an LLM output is cached, tool/schema versions, and relevant policy flags. Use explicit TTL or immutable-version invalidation. Do **not** reuse cached outputs for current web results, mutable repository state, permissions, security decisions, or state-changing tool calls.

This recommendation is deliberately not semantic caching. Semantic caches can improve hits, but published integrity attacks exploit embedding-key collisions in agent workflows. [CacheAttack](https://arxiv.org/abs/2601.23088) Exact content addressing also avoids adding the vector-DB/KG memory component rejected by the anti-overfit gate.

**Confidence: likely (55-80%) to save repeated preprocessing work with low correctness risk in narrowly declared pure functions.** The benefit depends on repeat rate; provider prefix caching may already capture most LLM-side value.

**UNVERIFIED — settling experiment:** instrument miss/hit/recompute-shadow for one month; on a sample of hits, recompute and byte/grade compare. Remove any cache whose hit savings do not exceed complexity or whose dependency key produces a mismatch.

**Anti-overfit gate:** passes only as a bounded file/SQLite content-hash cache on the existing bus. Vector similarity search, semantic reuse, and a memory service are rejected.

### 4.7 Cost-per-success and tail-latency scorecard — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For each task class/model/service tier, aggregate:

- attempted, successful, escalated, retried, and severe-failure counts;
- input, cached-read, cache-write, output, and reasoning tokens;
- provider tool-call fees where applicable;
- dollars per attempt and **dollars per successful end outcome**;
- TTFT, completion, queue, and full fan-out/join p50/p95/p99;
- cache hit rate and **net cache savings after writes**;
- route distribution and model snapshot;
- batch expiry/error rate and time-to-result.

Cost per raw call rewards cheap models that create recovery work; cost per successful end outcome prices the entire cascade. Tail percentiles expose the fan-out behavior hidden by averages. These metrics follow the endpoint/outcome distinction in Anthropic's eval guidance and the realized-spend/live-execution method of TwinRouterBench. [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) [TwinRouterBench](https://arxiv.org/abs/2605.18859)

**Confidence: almost certain (90-99%) that these measurements are necessary to make defensible routing and batching decisions.** Evidence: provider billing fields differ, routing overhead can reverse apparent savings, and agent outcomes require full trajectories; the remaining uncertainty is only which subset can be collected from each provider.

**UNVERIFIED — settling experiment:** reconcile aggregated dollars against provider billing for a fixed interval and inject a known cache hit, retry, escalation, batch error, and failed outcome. Do not declare the scorecard complete until two independent signals—event totals and provider billing/usage—agree within a declared tolerance.

**Anti-overfit gate:** passes if rendered from existing event data to local Markdown/JSON. No observability SaaS or new telemetry daemon.

**Confidence: very likely (80-90%) that these defaults have the best present evidence/risk balance.** LLMRouterBench undermines claims that complicated routers reliably beat simple baselines; CacheAttack demonstrates semantic-cache integrity risk; NSDI hedging work shows hedging can be useless in realistic regimes. **Anti-overfit gate:** passes. These are explicit non-adoptions of components most likely to create complexity without demonstrated owner-specific value.

## 5. Concrete decision rules

These rules convert the evidence into an operational policy.

### Caching decision

Use provider prefix caching when the identical stable prefix exceeds the provider/model minimum and is expected to be read enough times within its TTL to beat write cost. For current Anthropic pricing, the provider calculates break-even after one 5-minute read or two 1-hour reads. Always decide from usage counters. [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing) For OpenAI, confirm `cached_tokens`/`cache_write_tokens` and the active model's rates; caching rules changed for GPT-5.6-family models, demonstrating why hard-coded assumptions are unsafe. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

Use exact output caching only for pure, versioned operations. Do not deploy semantic answer caching for general agent work.

### Batch decision

Use provider Batch when all are true: requests are independent; results can arrive out of order; the task tolerates up to 24 hours; the required tools/features are supported; and correlation/retry semantics are explicit. [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch) [Claude batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

Use synchronous bounded concurrency when a human or downstream critical path waits. Use OpenAI Flex only for lower-priority work that tolerates slower responses and resource unavailability. [OpenAI Flex](https://developers.openai.com/api/docs/guides/flex-processing)

### Cheap-model sufficiency decision

Approve a cheaper model for a task class only when:

1. It has a workload-representative held-out suite.
2. Final outcomes are mechanically graded wherever possible.
3. Multiple trials cover nondeterminism.
4. The paired quality regression confidence bound is inside the declared tolerance.
5. No severe-risk floor is breached.
6. Total dollars per success improve after retries, escalation, routing, tools, and output length.
7. p95/p99 makespan does not violate the class SLO.
8. A small live canary confirms the offline result.
9. Model, prompt, tool, schema, or environment changes invalidate qualification and trigger re-evaluation.

This is a synthesis of TwinRouterBench's execution-verified downgrade/live tracks and Anthropic's outcome/multiple-trial eval method. [TwinRouterBench](https://arxiv.org/abs/2605.18859) [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### Fan-out decision

Before adding a child, state which unique evidence or capability it contributes and how the join uses it. Prefer quorum/first-valid/deadline joins where correctness permits. Add children only while marginal end-outcome gain justifies incremental dollars and tail latency. Never infer that parallelism makes total work free: Anthropic's production observation shows multi-agent token use can be roughly 15× chat, and tail-at-scale mechanics make required-all joins increasingly sensitive to stragglers. [Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)

## 6. Rejected alternatives and dead ends

### New universal routing gateway/runtime — rejected

This would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and fails the anti-overfit gate because it creates a second orchestration runtime. Current comparative evidence does not justify it: simple baselines remain competitive and model-pool curation dominates much of the gain. [LLMRouterBench](https://arxiv.org/abs/2601.07206) A two-tier configuration plus a small qualification evaluator can test the premise first.

### Vector-DB semantic cache — rejected

This would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** in many deployments and reintroduces the specifically rejected vector-DB/KG memory component. It also adds correctness, isolation, invalidation, and collision-attack surfaces. [CacheAttack](https://arxiv.org/abs/2601.23088) Exact hashing plus provider KV caching covers the low-risk portions.

### Self-hosted vLLM solely to make fan-outs cheaper — rejected for now

This would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**. vLLM's server-side throughput evidence is strong for self-hosting, but it does not establish that operating GPUs is cheaper or more reliable for this owner's volume, model requirements, or Windows environment. [vLLM paper](https://arxiv.org/abs/2309.06180) This unit found no owner-specific utilization, hardware, or staffing economics that would justify crossing the anti-overfit gate.

### LLM-as-router on every call — rejected as default

An LLM router consumes latency and tokens before the useful call. LLMRouterBench indicates lightweight/coarse routers can match sophisticated ones in many cases. [LLMRouterBench](https://arxiv.org/abs/2601.07206) Until an explicit table loses on held-out end outcomes, paying a model to choose a model is unjustified.

### Best-of-N everywhere — rejected

BEST-Route establishes that adaptive multi-sampling can help selected tasks, but universal best-of-N multiplies calls, requires selection, and worsens join tails. [BEST-Route](https://proceedings.mlr.press/v267/ding25d.html) It belongs only in offline, objectively graded experiments.

## 8. Recommended adoption sequence

1. Add token/cost/TTFT/completion/cache telemetry and cost-per-success reporting.
2. Canonicalize stable prefixes and verify real cache hits.
3. Label work `interactive` or `offline`; batch one mechanically graded offline class.
4. Establish always-strong and always-cheap end-to-end baselines.
5. Build the downgrade evaluator and qualify an explicit two-tier task table.
6. Add bounded concurrency and explicit join policies.
7. Only then test a cascade on mechanically gradable subtasks.
8. Reconsider learned routing, best-of-N, semantic caching, or hedging only if the simple architecture leaves a measured, valuable gap.

This sequence is **very likely (80-90%)** to capture most available value without overfitting the harness, because each step either uses a provider-native mechanism or adds a small measurement/policy layer, and LLMRouterBench finds diminishing returns from routing complexity beyond coarse task/model structure.
