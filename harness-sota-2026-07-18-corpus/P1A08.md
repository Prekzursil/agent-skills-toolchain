# P1A08 — corpus axis: session shape

## Scope and verdict

This unit analyzes only the `sessions` array in `corpus/corpus.json`, then reads raw transcripts where the summary cannot distinguish a normal terminal state from a mid-task death. It does not assess neighboring axes, modify the harness, or treat the corpus `hooks` section as evidence.

The central result is that the array mixes at least three unlike populations:

1. **Top-level launch attempts dominated by immediate access failures.** Of 1,857 rows labeled `session`, 1,361 end with either “organization has disabled Claude subscription access” (491) or “session limit” (870). Of those 1,361, 1,297 contain exactly nine JSONL lines; their median wall span is 1.594 seconds. This explains the top-level medians of nine lines and 1.809 seconds. These are front-door rejections, not tasks that exhausted context mid-work.
2. **Subagents that usually run for minutes.** The 2,143 `subagent` rows have a median of 54 lines and 458.205 seconds, versus nine lines and 1.809 seconds for top-level `session` rows.
3. **A tiny number of persistent, repeatedly resumed containers.** One top-level transcript is 4,392.11 MiB, 261,708 lines, and spans 82.7 days wall-clock. It alone contributes 61.61% of the bytes and 36.80% of the lines in the 4,000-row array. It survived at least 20 compactions and ended with an ordinary `end_turn`, `stop_hook_summary`, and `turn_duration`; it did not “die because it was 4.4 GB.”

The decisive outlier mechanism is **very likely (80-90%)** transcript amplification by hook-result attachments, based on two mechanically different signals: (a) a 64-window byte-stratified sample found attachments in 497/768 sampled records and 49,825,690/51,038,667 sampled bytes (97.62%); and (b) individual sampled `async_hook_response` attachments are up to 1,035,241 bytes because the same full PostToolUse/Edit hook input is retained twice, once under `response` (~510,395 characters) and once under `stdout` (~510,751 characters). This remains **UNVERIFIED** as a whole-file byte attribution; an exact streaming sum of bytes by top-level record type over the 4.4 GB JSONL would settle it.

Compaction itself is not the enemy. In this corpus it is both the reason very long work can continue and a failure point when the compacted/resumed payload immediately refills or exceeds a request limit. The raw evidence includes:

- a continuation prompt of 200,686 tokens rejected against a 200,000-token maximum;
- one subagent terminated after context refilled within three turns of the preceding compact, three times in a row;
- four `agent-acompact-*` transcripts ending at the 20 MB request limit;
- the 4.4 GB parent successfully crossing at least 20 compact boundaries, then later ending normally.

The survival design is therefore bounded and unglamorous: retain native compaction, make the existing PreCompact/SessionStart checkpoint path provably effective, cap and de-duplicate hook/tool payloads before they enter transcripts, refuse oversized Task payloads before launch, and keep task state plus long-running process identity outside the conversation. A second orchestration runtime or durable-execution engine is not justified by this evidence.

### What “duration” means

Duration here is `last_ts - first_ts`, not active compute time. The outlier demonstrates the difference: its raw tail jumps from activity on 2026-05-21 to activity on 2026-06-25, and then resumes normally (`aeb94ff3-...jsonl:261436` to `:261594`). A multi-day duration can mean a reopened session with long idle gaps. The array contains no per-turn active time, maximum gap, suspend/resume count, or process lifetime, so it cannot answer “how many hours of work happened.”

The raw terminal evidence supports a conservative answer to “what makes work die mid-task”:

1. **Explicit cancellation.** A sidechain can end with `[Request interrupted by user for tool use]`; 159 validated subagents have an explicit interrupt terminal. This is a cause, not a heuristic.
2. **Service/API loss.** Fifty-seven validated subagents end in explicit API failures, including socket closure, rate limiting, overload, and policy refusal. Example terminal strings appear in the raw remap output and are represented in corpus error fingerprints, but the sessions array itself carries none of them.
3. **Payload/context exhaustion.** Nineteen validated subagents end `Prompt is too long`; four more compact agents end at the 20 MB request ceiling; one ends after repeated autocompact refill. These are direct raw errors.
4. **Unresolved tool boundary.** Sixteen subagents and 43 top-level sessions stop at an assistant tool-use record without a subsequent result. It is **likely (55-80%)** that this class contains real abrupt deaths, because a tool call is an incomplete protocol boundary; however, it is **UNVERIFIED** which cases are crashes versus detached/async work or transcript truncation. Checking tool-use IDs against process/background registries and subsequent sibling transcripts would settle each case.
5. **Access rejection before work.** This dominates top-level row count but is not mid-task death.

No honest aggregate “task completion rate” can be computed from this array. Completion is not encoded; `end_turn` can be a progress update, `StructuredOutput` ends on a tool result, an API error can occur after artifacts were already written, and a pending tool may have continued outside the transcript.

- kind: `session`;
- 261,708 lines;
- 4,392.11 MiB (live file: 4,605,459,524 bytes);
- first timestamp: 2026-04-04T05:30:11.394Z;
- last timestamp: 2026-06-25T22:53:40.837Z;
- wall span: 7,147,409.443 seconds (~82.72 days).

It is not a single uninterrupted task. It contains a large autonomous-loop phase, many resumed turns, and an inactivity gap of more than a month. Its final substantive turn says housekeeping is done and summarizes the Ralph loop as stopped; then the transcript records `stop_hook_summary`, `turn_duration`, and `away_summary`.

Therefore the proposition “large transcript = dead session” is almost certainly not (1-5%) true for this outlier, because both semantic and protocol terminal records show a normal end.

This is not just “many turns.” It is a payload-amplification shape. The whole-file dominance claim remains **UNVERIFIED**, but **very likely (80-90%)**: the 64 byte-stratified windows are distributed through the full file, 97.62% of their measured bytes are attachments, and individual attachments expose the exact duplication mechanism. A full byte-by-type pass is the settling experiment.

## What would make work survive session death

### 1. Keep native compaction; do not replace it

**NATIVE (Claude Code already does this; we just enable it)**

Retain native manual/automatic compaction as the primary context-pressure mechanism. It is **almost certain (90-99%)** to be necessary for this owner’s long-lived work, because the outlier crossed at least 20 compact boundaries and later produced normal completed turns; without context reduction, those same near-million-token boundaries could not remain in one live context.

Do not interpret this as permission to preserve 4.4 GB transcripts forever. Context compaction and transcript retention are separate concerns.

### 2. UNVERIFIED — prove the already-configured checkpoint/replay path end to end

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

The desired architecture mostly exists already:

- `settings.json:82-101` routes SessionStart to the shared and local dispatchers;
- `settings.json:380-400` routes PreCompact and PostCompact to the shared dispatcher;
- `modules.py:1458-1528` writes a bounded, redacted checkpoint containing ledger pointer, goal, decisions, failures, and `.remember/now.md`;
- `modules.py:1362-1378` constructs a post-compact goal re-anchor;
- `event-ledger/sessionstart-replay.py:2-4,72-83` replays objective ledger state on `resume|compact|clear` rather than trusting the lossy summary;
- `event-ledger/stop-hook.py:2-7,90` records objective turn state before compaction.

Static configuration and tests do not prove a live compacted session receives the intended state. The known defect explicitly says transcript hook behavior is currently unmeasurable (`INPUT-known-harness-defects.md:133-147`). Runtime effectiveness is therefore **UNVERIFIED**; the settling experiment is a canary task with a unique goal, decision, falsifiable failure, dirty file, and background operation, followed by manual compact, auto compact, `/clear`, process kill, and resume. Each recovery must independently demonstrate the goal, decision, unresolved failure, changed file, and operation/log identity without reading the pre-compact conversation.

The recommended small build is the canary/receipt harness, not another memory system. It is **very likely (80-90%)** to expose continuity failures if present, because it checks the exact fields needed after death and uses both injected context and durable files as independent signals.

### 3. Cap and de-duplicate hook outputs before transcript persistence

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Introduce one shared output-budget adapter for every hook result:

- never echo the full hook input payload;
- never retain identical `response` and `stdout` bodies twice;
- cap inline hook stdout/additional context (for example 8-16 KiB, selected by a measured canary);
- for larger diagnostic content, persist a content-addressed sidecar and emit only `{status, digest, byte_count, path, first/last bounded excerpt}`;
- omit unchanged or empty fields;
- attach the tool-use/session identifiers needed for provenance.

It is **very likely (80-90%)** that this would sharply reduce outlier transcript growth, based on the 97.62% sampled attachment-byte share and the observed 1.035 MB duplicated hook line. The exact reduction is **UNVERIFIED**; replay a representative large Edit through the current and bounded adapters and compare transcript bytes, context tokens, hook diagnostics retained, and recovery success.

This proposal also directly attacks compaction refill: a compacted context cannot immediately refill from a megabyte-scale hook echo that was never admitted.

### 4. Preflight Task/continuation payloads and chunk large reads/results

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Before Task/subagent dispatch or continuation submission, measure both serialized bytes and estimated tokens. If either crosses a conservative fraction of the host limit, return a terminal `FAILED:payload-budget` with the largest contributors and a bounded remedy: write state to disk, pass paths/digests, split the task, or start fresh after checkpoint.

The preflight must budget the full rendered request, not just the user text: system prompt, skill catalog, MCP definitions, continuation summary, attachments, and tool results all count. A separate byte gate is required because the raw evidence contains both `200686 tokens > 200000` and `Request too large (max 20MB)`.

It is **very likely (80-90%)** that a dual token/byte preflight would prevent the observed immediate context deaths, because all 24 validated context-size terminals expose deterministic limit errors (19 prompt-too-long, four 20 MB requests, one thrash diagnostic). Its false-positive rate is **UNVERIFIED**; settle it by replaying those raw payload shapes plus successful near-limit controls.

### 5. Make external work identity part of every checkpoint

**CONFIG (settings/JSON only)**

Require long operations to run through the existing `longrun`/background registry path and require checkpoints to carry operation ID, PID or provider task ID, log path, start time, last heartbeat, expected terminal marker, and reconciliation command. This lets the conversational process die while the operation remains observable and resumable.

It is **likely (55-80%)** to preserve useful progress across abrupt session loss, because process/log identity is external to context and the corpus contains pending-tool and explicit-interrupt terminals. It cannot preserve an in-memory reasoning chain; only disk artifacts, ledgers, and external operations survive. The settling experiment is to start a 2-5 minute canary operation, kill the session at a tool boundary, resume in a fresh session, and reconcile it without re-running.

### 6. Add session terminal and active-time fields to the corpus miner

**BUILD-SMALL (<~200 lines, rides the existing corpus-mining bus)**

Extend each session row with bounded fields already available during the single scan:

- `final_semantic_role`;
- `final_stop_reason` and normalized terminal class;
- final error type/message fingerprint;
- pending tool-use ID and whether a later result exists;
- count of explicit interrupts;
- compact-boundary count, triggers, last pre/post tokens, maximum compact duration;
- count/bytes by top-level record type;
- largest record type/bytes;
- maximum timestamp gap and an “active span” estimate under a declared idle threshold;
- terminal timestamp and whether the raw file later grew.

This would have prevented the core ambiguity of this unit. It is **almost certain (90-99%)** to make future session-shape analysis more valid, because the current six fields (`file, kind, lines, mb, first_ts, last_ts`) mechanically cannot encode death cause, completion, compaction, payload amplification, or active time. The experiment is a labeled fixture suite containing normal end, StructuredOutput end, user interrupt, API error, prompt too long, pending tool, compact/resume, and background continuation.

Do not infer completion from `last_role` alone; the 382 subagents ending in a StructuredOutput tool result are the counterexample.

### 7. Admission circuit breaker for quota/subscription failure storms

**BUILD-SMALL (<~200 lines, rides the existing dispatcher/breaker bus)**

After a deterministic subscription-disabled or session-limit response, open a TTL breaker keyed by provider/account/reset time. Subsequent dispatch attempts should fail fast with one terminal status and the reset/repair action instead of generating another transcript and initializing another session.

This is **very likely (80-90%)** to remove most of the nine-line session storm if the same conditions recur, because 1,361/1,857 top-level rows end in those two explicit states and 1,297 are exactly nine lines. The runtime savings are **UNVERIFIED**; replay a controlled rejected dispatch burst with and without the breaker and measure attempts, transcript rows/bytes, hook startups, and time to actionable status.

## Anti-overfit gate

Every proposal above either uses a native Claude mechanism or rides an existing hook, dispatcher, ledger, background registry, or corpus-mining path. None adds:

- a second orchestration runtime;
- a vector database or knowledge graph;
- a durable-execution engine;
- a trained critic;
- an observability SaaS;
- a guardrail framework.

The evidence does not justify any of those rejected components. The failures are payload budgeting, terminal classification, admission control, and recovery verification. A new runtime would add another lifecycle to survive without fixing the byte echo that currently refills context.

## Alternatives considered and rejected

### “Delete or rotate every large transcript”

Rejected as the primary fix. Retention may be necessary, but deletion does not prevent hook stdout from being duplicated into the next transcript or context. It also risks destroying the only forensic evidence before the hook pipeline emits durable telemetry. First stop amplification; then set retention from measured recovery/forensic needs.

### “Compact more aggressively”

Rejected alone. One sidechain explicitly refilled within three turns three times, and four compact agents exceeded 20 MB. More frequent compaction can increase latency and summary loss while failing to bound the next hook/tool payload.

### “Treat all tool-result-last transcripts as dead”

Rejected. In the validated raw set, 382/391 subagent tool-result-last rows and 111/287 top-level tool-result-last rows follow `StructuredOutput`, which is normally the successful handoff boundary.

### “Treat `end_turn` as task complete”

Rejected. The outlier contains many `end_turn` progress updates (“Next tick…”, “3 of 4 in…”) before later work. `end_turn` is a turn terminal, not a task terminal.

### “Replace native sessions with a durable workflow engine”

Rejected by the anti-overfit gate. Native compaction demonstrably carried one session through at least 20 boundaries. The smaller fixes address the observed failures without introducing another orchestration/lifecycle surface.

## Gaps: what this corpus cannot answer

1. **No census of session shape.** The array is capped to the first 4,000 sorted paths; it omits 7,633 scanned files from per-session metadata (`mine.py:331-339,362-375`).
2. **No task outcome field.** The array cannot say whether an artifact was written, verified, committed, or accepted before the final record.
3. **No active-time field.** `first_ts`/`last_ts` measures wall span and includes month-long idle gaps.
4. **No death cause.** Terminal errors, stop reasons, pending tool IDs, and explicit interrupts exist only in raw JSONL.
5. **No compact metadata.** The array omits compact count, trigger, pre/post tokens, duration, and dropped-token totals.
6. **No payload attribution.** It cannot distinguish user/assistant prose from attachments, snapshots, hook stdout, or duplicated responses.
7. **No reliable hook-effect telemetry.** The corpus hook detector is explicitly broken, and the known defect says runtime hook behavior is unmeasurable (`corpus/corpus.json` hooks `DETECTOR_STATUS`; `INPUT-known-harness-defects.md:133-147`). Static wiring is not execution proof.
8. **One bad and 32 oversized lines.** The miner increments line counts but skips semantic parsing for lines over `MAX_LINE_BYTES` (`mine.py:213-224`). A terminal error or compact boundary inside such a line would be invisible to its global semantic counters.
9. **Raw-tree drift.** Two uniquely mapped files grew after mining and 152 rows have ambiguous basenames. Future corpora need full relative paths plus a content/size digest, not basename alone.
10. **No full outlier type census.** The distributed sample is strong but not an exact whole-file byte sum. The failed full scan is documented rather than converted into a claim.
11. **No causal proof that a checkpoint was consumed.** Checkpoint files and configuration can prove writers exist; only controlled compact/kill/resume can prove the recovered model received and used the right state.

## Bottom line for the next design unit

Do not optimize “average session length.” There is no single average session:

- the row-count mode is a rejected launch;
- normal subagents live for minutes and often terminate through StructuredOutput rather than `end_turn`;
- a few resumed containers dominate bytes and wall span;
- the largest container survived compaction and died normally, but its transcript was inflated by duplicated hook payloads;
- context death happens when the next rendered request or tool/hook output is too large, not merely when historical conversation is long.

The minimal high-value architecture is: **admission breaker → bounded payloads → native compaction → verified checkpoint/replay → external operation registry → explicit terminal classification**. That architecture uses the existing buses and directly matches the observed death points.
