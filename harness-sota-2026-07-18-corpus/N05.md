# N05 — Capability discoverability / auto-routing: owner overrides, harness selects

## Executive answer

The owner must not be the orchestration router. The harness should silently classify the work, choose **plain execution, native subagents, Workflow, metaswarm, or DevFleet**, begin every reversible step, and expose a one-line route receipt that the owner can override in ordinary language. Complexity and authority must be separate axes: choosing DevFleet does not grant permission to auto-merge, and choosing plain execution does not require asking whether the task is “simple.”

The best design is evolution, not a replacement runtime. The snapshot already contains (a) a semantic capability router, (b) a deterministic `/start-task` topology table, (c) an event ledger and selection-event emitter, (d) an external-reaction/fatigue gate, (e) open-loop resurfacing, and (f) native orchestration surfaces. The missing layer is a small **delegation-policy compiler** that turns task evidence into an executable route envelope, attaches an external verifier and thread owners, and learns from verified outcomes rather than from whether the model happened to invoke its own suggestion.

This conclusion is **very likely (80-90%)**, based on two local signals and the current agent-scaling literature: the local router emits “invoke if apt, else ignore” suggestions rather than taking responsibility for the route (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/route.py:361-402`), while `/start-task` already says “pick the flow FIRST” and “never make the user choose” but is only a manually invoked command and later asks the user to confirm complexity (`/local_disk0/codexwork/bundle/claude/commands/start-task.md:11-29,76-90`). Google Research’s controlled 180-configuration study reports that architecture choice depends on measurable task properties and predicts the best architecture on 87% of held-out configurations; it also finds multi-agent penalties on sequential and tool-heavy tasks ([Google Research, 2026](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). A shadow replay and live canary, specified below, must settle whether this local policy improves completion and owner focus.

No proposal below adds a hook, daemon, vector database, knowledge graph, trained critic, durable-execution engine, observability SaaS, or guardrail framework. Every proposal rides the existing semantic-router / shared-dispatch / event-ledger bus. Every correctness loop terminates in an external signal: an execution result, a fresh context/model, a durable artifact, or the owner.

## Finding 1 — UNVERIFIED: Learn route quality from verified task outcomes, not “suggested → invoked”

**Improvement.** Add an outcome-aware shadow policy behind the existing router. It estimates which topology succeeds for a task shape, but it learns only after an external completion receipt. This is the leading inferred surprise: the current personalization loop optimizes *compliance with a suggestion*, which can reinforce a bad route merely because the model obeyed it.

**What it is.** Each route decision logs a compact tuple:

`{route_id, task_features, chosen_topology, shadow_topology, health_snapshot, authority_level, verifier_kind}`

At terminal state, a separate event resolves it with externally observed fields:

`{acceptance_pass, verifier_source, owner_override, reopened_within_window, wall_time, tool_errors, threads_open}`

The policy begins in shadow mode: the existing route executes while the candidate policy predicts an alternative. Only after offline replay and a canary beat the baseline does it influence routing. No model grades its own route.

**Why inferred.** The semantic router’s durable signal is `used/(suggested+2)` (`semantic-router/success.py:113-122`), and PostToolUse credits a use as soon as the suggested capability is invoked (`semantic-router/observe.py:52-66`). Neither observes whether the work passed tests, satisfied acceptance criteria, stayed complete, or prompted an owner correction. The corpus’s 78-skill skew and 1,158 `general-purpose` agent uses (`corpus.json:13266-13368`) make an invocation-only reward especially vulnerable to popularity reinforcement. It is **likely (55-80%)** that outcome learning will choose better routes than invocation learning, because the reward is closer to the owner’s actual goal and the contextual-bandit literature shows value from context plus behavioral feedback; the local effect size is **UNVERIFIED — settle it with the 200-task replay plus 30-task canary below**.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing selection-event/event-ledger schema with `route_decision` and `route_outcome`; do not create a new store. Add a deterministic feature extractor to the semantic router: estimated file count bucket, read/write, dependency width/depth, tool count bucket, cross-repo, isolated-worktree need, fixed-DAG presence, risk tier, and liveness flags. Start with a five-arm Beta-Bernoulli Thompson sampler or simpler per-bucket Wilson score; reward is 1 only when the external verifier passes and no unresolved thread remains, 0 on verified failure/reopen/owner override, and unresolved otherwise. Never treat silence as success. Cap exploration to reversible routes with the same authority level. The actual ledger wiring on the Windows host is **UNVERIFIED — run one known-positive `selection.v1` tool success and verify both the source hook receipt and a ledger row before implementing route events**.

**External signal that verifies it.** First, replay 200 stratified historical tasks hand-labeled by a fresh context or owner against baseline `/start-task` and the candidate policy; require a known-present control task for every topology. Second, canary 30 live reversible tasks and compare two mechanically independent measures: (1) executable acceptance/test receipts and all-thread closure, and (2) owner override/reopen rate. Promotion requires no regression in either and a preregistered improvement in at least one. A same-context “looks good” verdict is inadmissible.

**SOTA citation.** Contextual bandits select actions from context and update from observed user feedback; Li et al. evaluated LinUCB on 33 million logged events and reported a 12.5% lift over a context-free bandit ([WWW 2010 paper](https://arxiv.org/abs/1003.0146)). Implicit feedback can be misleading unless examination and relevance are modeled separately ([Qi et al., NeurIPS 2018](https://papers.neurips.cc/paper_files/paper/2018/hash/d8c9d05ec6e86d5bbad7a2f88a1701d0-Abstract.html)); that directly motivates not equating “invoked” with “successful.”

**Value × effort.** transformative × medium.

**Novelty.** inferred-surprise.

**Autonomy.** confirm-first — confirmation is for promoting the learned policy out of shadow mode once, not for individual route choices.

## Finding 2 — Split “how to execute” from “what requires permission”

**Improvement.** Make topology and authority orthogonal. The router chooses the execution machinery; an independent authority policy decides whether the next action is reversible, externally consequential, or destructive.

**What it is.** A route envelope contains two independent fields:

* `topology`: `plain | subagents | workflow | metaswarm | devfleet`
* `authority`: `execute_reversible | checkpoint_before_external | confirm_before_irreversible`

Thus, the harness can announce “DevFleet selected for isolated parallel worktrees; planning and probes started; auto-merge is held for confirmation” without asking the owner to choose DevFleet. Conversely, plain execution cannot use “simple” as permission for an external write.

**Why inferred.** `/start-task` says autonomy defaults to auto-handling reversible/obvious steps and stopping only at genuine forks or irreversible actions (`commands/start-task.md:25-29`), yet its later flow asks the owner to validate the harness’s complexity assessment (`commands/start-task.md:76-90`). DevFleet couples route approval to dispatch and enables auto-merge (`commands/devfleet.md:37-45`). The owner’s complaint implies that these are different decisions. It is **very likely (80-90%)** that separating them reduces micro-management without weakening control, because it removes topology questions while preserving action-level approval; evidence is the explicit owner requirement, the local contradiction, and mixed-initiative research’s emphasis on weighing costs/benefits under uncertainty and providing user control ([Horvitz, CHI 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).

**How to build.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Put a declarative authority matrix beside the route policy: read/search/test/local temp writes are reversible; modifying in-scope workspace files follows task authorization; install, publish, message, merge, push, delete, credential/security changes, and other material external effects require the existing confirmation rules. Route selection cannot raise authority. Existing PreToolUse enforcement remains the external action boundary; do not add a guard. Add a route-envelope field consumed by existing Workflow/Task/DevFleet launch instructions so auto-merge is disabled unless authority permits it.

**External signal that verifies it.** Run a fixed matrix of 30 synthetic task/action pairs through the route classifier and the existing PreToolUse boundary as separate mechanisms. Required invariants: all five topologies are selectable without owner input; every known irreversible control is caught by the action boundary; a known reversible control proceeds. Then measure owner questions per completed live task and audit actual tool calls for unauthorized external effects. Both signals must remain green.

**SOTA citation.** The 18 validated human-AI interaction guidelines include scoping services under uncertainty, efficient correction/dismissal, global controls, and cautious adaptation ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Horvitz’s mixed-initiative principles frame automation as a utility decision under uncertainty about goals and attention, rather than as a single fixed autonomy level ([CHI 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)).

**Value × effort.** transformative × low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

## Finding 3 — Route hysteresis with execution-triggered escalation and de-escalation

**Improvement.** Stop re-deciding architecture from prose each turn. Select once, hold the route while evidence is healthy, and change only when an external event crosses a threshold.

**What it is.** A route state machine:

`PROPOSED → ACTIVE → {COMPLETE | ESCALATE | DEESCALATE | FALLBACK}`

Examples: plain → subagents after discovery proves three independent read-only lanes; subagents → plain after two workers contend on the same files; Workflow → plain after the first sequential phase shows the remaining steps share one stateful tool loop; metaswarm → Workflow when a stable DAG and executable phase postconditions emerge. Route changes produce one terse receipt; they do not ask the owner unless the authority axis changes.

**Why inferred.** The corpus records retry runs for Read (53), Bash (14), TaskOutput (6), deep-research polling (3), and other tools (`corpus.json:10297-10369`), so external stall signals exist. A recall-biased sample also records a mid-course owner switch from Codex fan-out to metaswarm (`corpus.json:11591-11598`), which is a hypothesis that the harness did not own route adaptation. It is **likely (55-80%)** that hysteresis reduces thrash and catches genuinely changed task shape, based on those external signals and research showing architecture performance varies sharply with sequentiality, tool density, and parallelizability; the precise thresholds are **UNVERIFIED — settle them via replay of tasks with timestamped tool/error sequences and a live canary**.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Store route state as an event-ledger projection keyed by task/goal. Transition only on: executable dependency graph changes; file-overlap evidence from worker reports; two identical tool-error fingerprints; verifier failure; worker terminal status; or owner override. Do not use the current model saying “this is harder than expected.” Add a minimum dwell of one completed step and a maximum of one automatic topology change before a fresh external probe. Existing loop-recovery and monitor events supply failure/terminal signals; fold evaluation into the existing dispatcher rather than adding a hook.

**External signal that verifies it.** For every transition, persist the exact triggering tool result, worker status, file-overlap report, or owner utterance. A separate replay process recalculates the transition from the ledger and must match. Success requires both fewer repeated identical failures and no increase in unfinished threads. A known transition fixture and known no-transition fixture validate the detector before any absence claim.

**SOTA citation.** Google Research’s controlled study found centralized multi-agent execution +80.9% on parallelizable tasks, all multi-agent variants -39% to -70% on sequential reasoning, and disproportionate coordination cost for tool-heavy tasks ([Google Research, 2026](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). The result supports dynamic architecture selection; it does not supply local thresholds.

**Value × effort.** high × medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

## Finding 4 — UNVERIFIED: Health- and reliability-aware routing with automatic topology fallback

**Improvement.** Treat an orchestrator as a capability that must be live and empirically reliable, not as a name the model can confidently select. A dead DevFleet or unhealthy Workflow lane should fall back automatically to the next valid topology while preserving the task and verifier.

**What it is.** The delegation policy intersects `task fit × live health × local reliability prior`. A topology is eligible only if its known-positive probe passes. The first real invocation result is a second independent signal. Failure yields a single receipt such as: “DevFleet fit the DAG, but its live probe failed; using native subagents with the same four threads.”

**Why inferred.** The corpus demonstrates why semantic fit alone is unsafe: Tavily remained heavily used even with severe failure (`mcp__claude_ai_Tavily__tavily_search` shows 194 calls and 71.65% error in the tool table at `corpus.json:319-324`; the family-level measured ground truth supplied to this unit reports 135 “not connected” failures). StructuredOutput is 22.9% error (`corpus.json:103-108`), so a strict-schema Workflow cannot receive a neutral reliability prior. ToolSearch, by contrast, is 0.08% error (`corpus.json:87-92`) and is a safe discovery fallback. DevFleet’s live server is **UNVERIFIED on this Linux snapshot — settle it on Windows with `Get-Command`/MCP discovery plus a documented no-op health call; do not infer liveness from `commands/devfleet.md` existing**. It is **very likely (80-90%)** that excluding known-dead substrates prevents avoidable route failures, based on the local Tavily failure evidence; relative ranking among live topologies remains **UNVERIFIED until route-outcome receipts exist**.

**How to build.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Consume the existing B1 `mcp-liveness` state and capability catalog; do not recreate either. Add topology requirements and fallback order to the policy JSON. Example: `devfleet → native subagents → plain`; `workflow → plain staged execution`; `metaswarm → native subagents + TDD skill`. Reliability priors come from the corpus initially, decay with time, and are updated only by actual tool success/failure. Never suppress all routes on telemetry error: fail open to plain execution and native tools. Structured-output routes use a minimal permissive envelope plus deterministic field validation because the local strict schema path is unreliable.

**External signal that verifies it.** Require two mechanically independent signals before marking a substrate dead: (1) its known-positive health/discovery control fails while another known-present capability is detected, and (2) the first bounded no-op or real call returns an unavailable/connection failure. Verify the fallback by completing the same acceptance fixture through the fallback topology. The original route is restored only after both health and call controls recover.

**SOTA citation.** The Google scaling study explicitly models efficiency, overhead, error amplification, redundancy, tool count, and task parallelism and reports 87% held-out architecture prediction ([paper](https://arxiv.org/abs/2512.08296)). Human-AI guidelines also recommend making capability/reliability clear and gracefully degrading under uncertainty ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).

## Finding 5 — Make thread custody a route invariant, not a memory reminder

**Improvement.** Every selected topology must accept custody of every discussed thread before execution and return external evidence for each thread’s terminal state. A route cannot be “complete” while a thread silently disappears.

**What it is.** The route envelope carries a compact `threads[]` array:

`{id, source_turn, acceptance_signal, owner_worker, depends_on, state, evidence_ref}`

Plain execution owns all threads in the main context. Subagents/Workflow/metaswarm/DevFleet assign exactly one accountable worker per thread; multiple workers may contribute, but custody is singular. Terminal states are `verified_done | explicitly_deferred | owner_cancelled | externally_blocked`, never “probably handled.”

**Why inferred.** The hard requirement is never to drop a thread. The snapshot already has an open-loop system that surfaces at most three relevant loops (`open-loops/resurface.py:38-40,69-95`) and an event ledger that records goals/failures/milestones (`event-ledger/note.py:1-12,25-42`), but neither source establishes that every route decomposes its current request into owned acceptance threads. The corpus includes the candidate sample “do not forget to update basic memory” only as recall-biased evidence (`corpus.json:11579-11582`), while the owner’s explicit constraint is decisive. It is **very likely (80-90%)** that explicit custody reduces discussed-then-forgotten work, because completion becomes impossible without a terminal evidence reference; the magnitude is **UNVERIFIED — settle it with injected-thread chaos tests and live reopen counts**.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing event-ledger/open-loop projection; do not add a task database or OPEN-THREADS v2. On task start, extract candidate threads once, attach their source turn, and allow the owner to override by ordinary correction. Before dispatch, require an owner worker and external acceptance signal for every thread. Worker reports can update state only when they include an artifact/test/tool-result reference. At Stop, the existing dispatcher folds a projection check into its current Stop invocation; it emits unresolved thread IDs but exits 0 on its own error. Because intrinsic extraction can miss threads, validate extraction against a fresh-context transcript parser or owner-labeled fixtures—never let the originating context certify its own completeness.

**External signal that verifies it.** Create 25 transcripts with 1-8 known seeded threads, including later additions, negations, explicit deferrals, and interruptions. A separate parser/context must recover the seed IDs; then run each topology and require a durable terminal row plus artifact/test receipt for every non-cancelled seed. In live use, independently compare ledger-open count with a fresh-context transcript audit and owner reopen/correction events. Do not claim zero dropped threads unless both detectors find the known-present control.

**SOTA citation.** Amershi et al. recommend remembering recent interactions, supporting efficient correction, and making adaptation consequences visible ([CHI 2019 guidelines](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Microsoft’s situated-interaction program frames human-AI collaboration as coordinated, mixed-initiative work requiring awareness of goals, attention, and turn-taking ([Situated Interaction](https://www.microsoft.com/en-us/research/project/situated-interaction/)).

**Value × effort.** transformative × medium.

## Finding 7 — Natural-language override grammar with scope, TTL, and immediate consequence

**Improvement.** Let the owner correct a chosen route in one phrase—“plain only,” “fewer agents,” “switch to metaswarm,” “no auto-merge,” “use DevFleet for this repo”—without opening a chooser or editing configuration.

**What it is.** Overrides compile into one of four scopes:

* `this_step`
* `this_task`
* `this_repo_until <expiry>`
* `global_until_revoked`

The default scope is `this_task`; broad/global changes require a brief consequence echo. Route-specific preferences decay or are explicitly revoked; they do not become permanent “owner truth” from one correction.

**Why inferred.** The corpus contains recall-biased candidate evidence of explicit topology changes (`corpus.json:11591-11598`) and a request to use fewer agents is present among candidates but cannot be treated as verified without raw transcript validation. The owner’s present instruction establishes the interaction model: override rather than selection. ## Integrated decision design

### Route calculation

The compiler uses a cheap deterministic pass before any model call:

1. **Content gate:** ignore pleasantries and non-task turns.
2. **Override lane:** apply a live explicit owner override with scope/TTL.
3. **Task evidence:** compute boundedness, read/write, dependency width and depth, likely file overlap, tool density, fixed DAG, isolated-worktree need, risk, and externally visible acceptance signals.
4. **Eligibility:** intersect with capability catalog, B1 liveness, and reliability priors.
5. **Topology:** choose the first policy match; unknowns get bounded plain discovery, not an owner menu.
6. **Authority:** independently compute what may start and where confirmation is required.
7. **Verifier:** attach an external signal before work begins. If none exists, use a fresh context/model or owner review; the same context cannot certify itself.
8. **Threads:** assign every thread to one custodian and acceptance signal.
9. **Receipt:** emit once, begin reversible work, and accept ordinary-language override.
10. **Outcome:** resolve from external receipts and update shadow policy; never reward self-approval.

This design is **very likely (80-90%)** to be implementable without a seventh hook because the existing dispatcher is explicitly designed to aggregate checks behind one invocation (`hooks/_dispatch/manifest.json:1-4`) and the semantic router already emits UserPromptSubmit context (`semantic-router/route.py:361-405`). Actual Windows wiring is **UNVERIFIED — trace a known-positive prompt from UserPromptSubmit to the semantic-router output and event ledger before implementation**.

### External verifier matrix (law compliance)

| Work class | Minimum external close-loop signal |
|---|---|
| code change | actual tests/build/lint in a separate process; high-risk changes also get a fresh reviewer context/model |
| research | source retrieval/citation resolution plus independent claim audit or owner review |
| UI | rendered screenshot/browser interaction plus deterministic accessibility/console checks |
| reverse engineering | second tool/disassembler/runtime observation, never the originating narrative alone |
| infrastructure | provider/API status plus an independent observable effect/read-back |
| route quality | acceptance receipt + owner override/reopen/thread outcome |
| absence/broken claim | known-positive detector control + mechanically independent second signal |

If the external verifier is unavailable, the route fails open in execution but cannot claim verified completion. It records `externally_blocked`, preserves the thread, and asks the owner only if no safe work remains.

The external-verification rule is supported by local live defects: six wrong conclusions from single unvalidated probes and a seventh detector caught by a known-positive control (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`). It also aligns with the TACL survey finding that self-correction works reliably when reliable external feedback is available, while prompted intrinsic correction lacks general evidence ([Kamoi et al., TACL 2024](https://aclanthology.org/2024.tacl-1.78/)).

### Hook-ceiling accounting

* New settings-level hook entries: **0**.
* New daemon/service/runtime: **0**.
* Delegation classification and override parsing fold into the existing semantic-router UserPromptSubmit carrier.
* Route state/outcomes ride the existing selection-event/event-ledger path.
* Thread projection and terminal checks fold into the existing local dispatcher invocations.
* Receipt timing reuses calibrated silence.

Therefore, none of the findings consumes a seventh hook or requires replacing an existing hook. If implementation discovers that the semantic router is not live, do not add a new entry immediately: fold the classifier into the already-wired shared `UserPromptSubmit` dispatcher (`settings.json:117-137`) and prove the known-positive receipt.

### Anti-overfit gate

The proposal stays deliberately small. It does not introduce a second orchestration runtime; it selects among already native/installed runtimes. It does not add vector/KG memory; it uses the event ledger and existing semantic index. It does not add durable execution; DevFleet/Workflow already own their native persistence. It does not add a trained critic; external tests/tools/fresh contexts/owner close loops. It does not add observability SaaS or a guardrail framework.

The only adaptive component is a bounded topology bandit in shadow-first mode. If the deterministic table matches or beats it on verified outcomes, retire the bandit and keep the table. That kill criterion prevents personalization machinery from surviving merely because it is sophisticated.
