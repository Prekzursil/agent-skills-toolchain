## Wrong-path failure chain

The following is a defensive failure model, not exploit code.

1. A task contains, derives, or copies a filesystem path. Sources include owner prose, an artifact path, fetched/repository text, a shell variable, or model-generated cleanup logic. The harness itself recognizes that fetched and cloned-repository content may be hostile (`C:\Users\Prekzursil\.claude\AGENTS.md:99-106`).
2. String/path composition loses the intended directory and produces `/`. The adapter states that a prior agent's recursive PowerShell cleanup “collapsed to `/`” (`C:\Users\Prekzursil\.claude\agents\codex.md:108-109`). The actual historical command, variable state, and deletion receipt were not recovered in this unit, so the incident mechanism and whether deletion began are **UNVERIFIED — settle by locating the originating transcript/tool receipt or replaying its exact composition logic in a disposable VM**. This report does not convert the adapter's warning into a verified historical deletion.
3. PowerShell interprets `/` as the current drive root. On this live machine both PowerShell's provider resolver and .NET's path resolver returned `C:\`; Microsoft documents the same root-relative behavior.
4. The model submits a recursive delete. Codex does not request approval and does not sandbox the shell. The shared hook receives the call, but the only broad destructive classifier is conditional on an environment flag which is currently absent/off (`modules.py:65-81,765-790`).
5. Windows performs deletions allowed by the elevated token until it encounters locks, ACL denials, special objects, or errors. Partial failure is not safety: user data, repositories, harness state, credentials, and installed tools can be damaged before a protected object stops one branch. This breadth is **very likely (80-90%)**, based on High Administrator integrity plus the recursive semantics; exact reach is the VM experiment noted above.
6. A post-hoc check runs only after the side effect. It may discover missing files, but it cannot restore uncommitted work, rotate exposed credentials, retract a network request, undo a registry/device operation, or guarantee that every outside-workspace mutation was enumerated.

The key security invariant is consequently violated: an untrusted or simply wrong path reaches a high-authority system boundary without canonicalization, root rejection, containment validation, or an approval/capability gate.

## Remediation design, in priority order

### R1 — Fail closed on sandbox preflight — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Replace the adapter's unconditional bypass fallback with a version- and environment-keyed preflight in the existing dispatcher/adapter bus:

1. Create a disposable test root and an outside sibling canary.
2. Under the exact CLI binary, version, config/profile, environment-size class, and intended sandbox mode, prove: a child command executes; an in-root write succeeds; an outside-sibling write is denied and absent; `/status` reports the expected writable roots.
3. Cache only a signed/digested receipt keyed by CLI executable hash, version, effective config hash, sandbox-helper hash, Windows build, and environment-length bucket. Invalidate on any key change.
4. If any control fails, return `FAILED:sandbox-preflight` and do not launch on the host. Never substitute the bypass flag.

This is **very likely (80-90%)** to prevent silent sandbox-label drift, because it tests the boundary's observable postconditions with both known-positive and known-negative controls before real work. It will not by itself fix the native helper; it correctly turns that defect into a safe refusal. The design rides the existing hook/adapter bus, adds no daemon, vector store, trained critic, durable-execution engine, observability SaaS, or guardrail framework.

### R2 — Restore least-privilege invocation after the preflight passes — CONFIG (settings/JSON only)

For local unattended work, select `--sandbox workspace-write`; use explicit `--add-dir` only for a small resolved root list; use `on-request` for interactive risky work; remove `--dangerously-bypass-approvals-and-sandbox`; and change the base profile away from `danger-full-access`/`never`. These are the modes OpenAI currently recommends.

This remediation is **very likely (80-90%)** to reduce ordinary host blast radius once R1 proves enforcement, based on vendor semantics and the inside/outside controls. Without R1 it is **UNVERIFIED — the same disposable preflight must pass on 0.144.6 before the profile is described as contained**. Merely changing the status label is not completion.

### R3 — Add a path-capability gate for destructive filesystem operations — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Keep this as defense in depth, not a sandbox replacement. On the existing PreToolUse bus, block raw recursive deletion by default and route legitimate cleanup through one small safe-delete helper which:

- rejects null, empty, whitespace, `/`, `\`, drive roots, UNC share roots, the workspace root itself, wildcards, and unresolved paths;
- accepts separate, literal `allowed_root` and `target` arguments rather than a composed shell string;
- canonicalizes both to fully qualified final targets, resolves reparse points/junctions, and requires the target to be a strict descendant of the allowed root using path-segment-aware comparison;
- re-checks the opened target immediately before mutation to reduce time-of-check/time-of-use substitution;
- moves to a same-volume quarantine with a manifest by default; permanent deletion requires an explicit, one-shot, command-fingerprinted approval;
- emits `SUCCESS:<id>`/`FAILED:<id>` receipts with the resolved root and target, never secret contents.

This is **likely (55-80%)** to prevent the observed wrong-root class for operations routed through it, based on canonical root rejection and strict-descendant checks. Comprehensive shell-language coverage is **very unlikely (5-20%)** from regex alone, because Python, cmd, native utilities, MCP tools, and encoded scripts can express equivalent effects; R1/R2 remain the true boundary.

### R4 — Repair error 206 without bulk-deleting plugin state — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

The pinned program evidence says orphaned plugin directories inflate the Windows command line, but also says one apparently orphaned directory was serving a live skill and 110/169 candidates lacked a live sibling. Extend the existing plugin/config reconciliation bus to inventory references, prove a known-live control, quarantine candidates to a bounded same-volume holding directory, launch the exact sandbox preflight, and only retire a quarantined directory after a soak period and a zero-reference proof.

It is **likely (55-80%)** that reducing the effective launch environment/argument expansion below the Windows limit will let the native helper start, based on repeated error 206 and the pinned orphan-inflation diagnosis. Exact candidate safety and whether helper launch then yields correct enforcement are **UNVERIFIED — settle with reference tracing plus R1's preflight before and after quarantine**. ## Acceptance tests

No remediation is “done” until all of these pass on the installed binary and launch path:

1. **Known-positive execution:** a harmless child process runs inside the selected sandbox.
2. **Allowed write:** an in-workspace canary is created and contains the expected nonce.
3. **Denied sibling write:** an absolute path to a sibling directory remains absent and the tool reports denial.
4. **Root-collapse fixture:** empty, whitespace, `/`, `\`, `C:\`, and a composed path that normalizes to a drive root are all rejected before the mutation API is called.
5. **Traversal/reparse fixture:** `..`, a junction, a symlink, a UNC root, and case/alternate-separator forms cannot escape the allowed root.
6. **Race fixture:** replacing the checked directory with a junction between validation and mutation fails safely.
7. **Alternate-effect fixture:** raw PowerShell, cmd, Python, and an MCP-shaped deletion request are blocked or constrained by the real sandbox; this proves the path helper is not the sole boundary.
8. **Hook failure fixture:** a timed-out/crashed PreToolUse hook does not grant destructive host execution; the launcher fails closed for high-risk operations.
9. **No-network fixture:** a sandbox profile that claims network-off cannot reach a controlled test endpoint, while the known-positive endpoint is reachable from the harness outside that sandbox.
10. **Receipt and recovery:** quarantine emits a terminal receipt and restore succeeds; permanent deletion requires the one-shot approval and cannot reuse it for a changed target.

The expected result is **very likely (80-90%)** to distinguish real containment from status-text theater, because it combines independent positive/negative filesystem, process, path, race, hook, and network postconditions. The exact Windows Sandbox/0.144.6 results are **UNVERIFIED — executing this acceptance suite in disposable fixtures is the settling experiment**.
