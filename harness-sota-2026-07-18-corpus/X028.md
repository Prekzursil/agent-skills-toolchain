# X028 — Cross-domain borrow: aviation safety → agent memory

## Executive finding

The aviation analogy transfers, but only at the level of **information lifecycle controls and verification protocols**. It does not justify turning an agent harness into an airline-style safety bureaucracy.

The best borrow is a small “memory airworthiness envelope”: every durable memory is treated as controlled operational information with a declared source, scope, effective time, expiry/review trigger, supersession relation, and accountable origin; expired or contradicted memories are quarantined from silent use; a compact phase-specific brief exposes which memories are active; and consequential use of mutable memories invokes challenge–verification–response against current evidence. Near misses and corrections enter a non-punitive candidate queue, not durable memory automatically.

This is **likely (55-80%)** to reduce stale-memory and wrong-context errors because three independent aviation mechanisms address the same proximate failure modes: AIRAC/NOTAM controls address changing information, checklist redundancy addresses omission and false completion, and mode-awareness research addresses hidden automation state. The evidence is strong in aviation but transfer effectiveness in an agent harness is **UNVERIFIED; the “Memory AIRAC Replay” experiment in §9 would settle it**.

This is not a recommendation for a second runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The design rides ordinary session-start/session-end hooks, the existing memory files/store, and tool-call interception. It therefore passes the anti-overfit gate.

## 1. Scope and method

This unit is intentionally an ideation lens. Per the assignment, it does not inspect or make claims about the local harness. All factual claims about aviation below cite an external primary or original source. Recommendations are translations, not claims that aviation evidence directly proves agent-harness outcomes.

The question was decomposed into three memory problems:

1. **Admission:** what deserves to persist across sessions?
2. **Retirement:** when should a memory stop influencing behavior?
3. **Surprise detection:** how does the operator or agent notice that retrieved memory is stale, conflicting, or being applied in the wrong context?

Four aviation mechanisms were evaluated: controlled aeronautical information (AIRAC and NOTAM), normal checklists and crew cross-checking, automation mode awareness, and confidential/non-punitive occurrence learning. The result is a partial transfer, with explicit disanalogies in §8.

## 2. Mechanism A: AIRAC and NOTAM as lifecycle-managed operational memory

### 2.1 How it works in aviation

Aeronautical facts change: routes, navigation aids, procedures, runways, and taxiways. ICAO’s AIRAC system does not treat a newly published fact as timeless or immediately active. It distinguishes **publication date**, **latest reception date**, and **effective date**, and coordinates important changes on a predetermined schedule so pilots, dispatchers, controllers, flight-management systems, and charts work from the same information base ([ICAO, AIRAC](https://www.icao.int/airnavigation/airac)). ICAO’s Aeronautical Information Management description states that establishment, withdrawal, and significant changes use common effective dates at 28-day intervals ([ICAO, AIM](https://www.icao.int/airnavigation/aeronautical-information-management)).

NOTAM handling adds explicit validity and supersession semantics for temporary or exceptional information:

- A NOTAM states a start of activity and end of validity.
- An estimated end is marked `EST` and must be canceled or replaced before that end; otherwise it expires.
- The accountable organization validates whether an approaching end-of-validity item may expire; if the condition remains valid, the item is canceled and reissued with new times.
- A permanent condition is marked `PERM`, but the originator remains responsible for cancellation after incorporation into a publication.
- Except for `PERM`, notices auto-cancel at end of validity.
- A correction/change is issued as a new notice and the prior notice is canceled.

Those are operational rules, not a loose metaphor; see the FAA’s [Preparing NOTAMs for Dissemination](https://www.faa.gov/air_traffic/publications/atpubs/notam_html/chap4_section_2.html), [Cancellation/Expiration](https://www.faa.gov/air_traffic/publications/atpubs/notam_html/chap7_section_2.html), and [NOTAM responsibilities](https://www.faa.gov/air_traffic/publications/atpubs/notam_html/chap3_section_1.html). The last source also assigns responsibility for accuracy, currency, and validity to a certified source.

The important safety idea is not merely “add a TTL.” It is that operational knowledge has a lifecycle, an effective interval, an originator, and a replacement path. Temporary information is not allowed to drift silently into permanence.

### 2.2 Translation: typed memory records with validity envelopes — UNVERIFIED

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a small schema and admission/selection hook around the existing memory store. Do not replace the store.

Each persisted item would carry:

```yaml
id: mem-...
kind: invariant | preference | operational_notice | open_loop | incident_hypothesis
statement: ...
source: user-message/session/tool-result/path-or-url
recorded_at: ...
effective_from: ...
review_or_expire_at: ...
scope: owner | workspace | repository | branch | task
authority: owner | verified-tool-result | agent-inference
confidence: observed | inferred | contested
supersedes: [mem-...]
revalidate_on: [source_changed, branch_changed, tool_missing, contradiction, owner_correction]
```

Concrete policy:

- `operational_notice` and `open_loop` require a review/expiry condition. They never silently become permanent.
- `preference` and `invariant` may omit wall-clock expiry, but require provenance and a revalidation trigger.
- `incident_hypothesis` cannot enter the active prompt as a fact; it remains a candidate until corroborated or explicitly accepted.
- A replacement creates a new record and marks the old record superseded. History is retained for audit, but only the current record is eligible for normal retrieval.
- Expiry means **quarantine from silent retrieval**, not deletion. An expired item can be shown as historical context and explicitly revalidated.
- A generic `PERM` value is disallowed for agent-generated inferences. Only an explicit owner statement or a stable, versioned source may produce a non-expiring record.

This is **very likely (80-90%)** to prevent temporary task facts from silently becoming durable because mandatory expiry/review and non-destructive quarantine directly constrain that transition; the evidence is the explicit FAA validity/reissue/cancel lifecycle above. Its actual error reduction is **UNVERIFIED; “Memory AIRAC Replay” in §9 tests it against later corrections and changed source state**.

It is **likely (55-80%)** to catch memories such as “this service is down,” “work is on branch X,” “file Y is authoritative,” “awaiting review,” or “use this temporary workaround” after their condition changes. The causal evidence is that these are scoped, mutable conditions, exactly the class bounded by start/end/supersession fields; whether those fields are populated accurately is **UNVERIFIED; the admission-completeness arm of Memory AIRAC Replay tests missing or incorrect metadata**.

It will not prove truth. A current, well-formed record can still be wrong. The mechanism controls currency and use, not epistemology.

## 3. Mechanism B: the checklist is a redundant verifier, not an encyclopedia

### 3.1 How it works in aviation

NASA’s *Human Factors of Flight-Deck Checklists: The Normal Checklist* describes two distinct redundancies: the checklist backs up initial aircraft configuration, and pilots supervise one another while conducting it. In challenge–verification–response, one pilot calls the item, both verify the actual setting, and the other calls the verified status. A do-list instead directs the action step by step. The report warns that a do-list error can pass unnoticed after interruption and that overlong detailed checklists risk poor or non-use. It frames item selection as a tension between completeness and human usability ([NASA/FAA report, pp. 19–21](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)).

FAA CRM guidance separately says crew members must monitor the aircraft’s path and systems and actively cross-check one another; it calls effective monitoring and cross-checking a possible last line of defense that can break an accident chain ([FAA AC 120-51E, §16(a)](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_120-51e.pdf)).

The transferable mechanism is therefore not “write everything down.” It is:

1. perform the work using the live environment;
2. select only critical checks for the current phase;
3. challenge a claimed state;
4. inspect the actual indicator/source;
5. respond with observed state, not intention;
6. use mutual redundancy where consequences justify it.

### 3.2 Translation: phase briefs and challenge–verification–response — UNVERIFIED

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At session start and before consequential transitions, render a compact “memory brief” from eligible records rather than injecting the whole memory archive.

Suggested phases and critical items:

| Phase | Memory brief | Verification action |
|---|---|---|
| Session start | owner constraints, repository scope, unresolved open loops, quarantined conflicts | confirm workspace/branch and whether open loops are still live |
| Before external/state-changing action | authorization, exact target, current environment, last known precondition | re-read current source or query system state |
| Before declaring done | requested outcomes, tests/evidence, remaining open loops | compare each claim with a fresh result |
| Session end | durable decisions, unresolved items, candidate lessons | assign scope and expiry/revalidation trigger before admission |

For a mutable record used in a high-impact decision, the protocol is:

> **Challenge:** “Memory says dependency/service/path/branch/requirement X.”  
> **Verify:** inspect a current authoritative source.  
> **Response:** “Observed X at time T from source S,” or “conflict—memory quarantined.”

The “verifier” must be mechanically independent of the memory record. Re-reading the memory, asking the same model to reconsider it without new evidence, or paraphrasing it is not verification. Examples of acceptable independence are a current tool query versus a stored session note, a repository digest versus a remembered path, or an explicit owner correction versus an agent inference.

This is **likely (55-80%)** to catch false carry-over claims before consequential use because the protocol compares memory to live state and because aviation evidence supports redundant verification of critical configuration. Effectiveness and latency cost are **UNVERIFIED; the “Challenge Gate A/B” experiment in §9 would measure caught contradictions, false alarms, and added tool calls**.

This is **very unlikely (5-20%)** to remain useful if implemented as a comprehensive checklist on every tool call, because the NASA/FAA report documents the non-use/poor-use risk of long lists and the harness would impose substantially more repetitions than a phase checklist. The transfer therefore requires sparse, consequence-gated checks.

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Define a short allowlist of memory classes that require live verification before destructive, external, credentialed, publish, or “done” actions. This configuration is **likely (55-80%)** to capture most value with low overhead because it limits checks to state transitions analogous to critical flight phases; that distribution is **UNVERIFIED; the Challenge Gate A/B experiment stratified by action class would settle it**.

## 4. Mechanism C: automation surprise and mode annunciation

### 4.1 How it works in aviation

Sarter and Woods studied mode error in highly automated “glass cockpit” systems. Their central finding is structural: as automation gains modes and autonomy, supervisors must track which mode is active, what it is doing, and how modes interact. Their studies combined experienced-pilot reports, transition-training observations, and a field experiment; gaps in mode awareness and understanding contributed to automation surprises and supervisory-control difficulty ([Sarter & Woods, 1995, DOI 10.1518/001872095779049516](https://doi.org/10.1518/001872095779049516); accessible author copy [here](https://www.researchgate.net/publication/258138719_How_in_the_World_Did_We_Ever_Get_into_That_Mode_Mode_Error_and_Awareness_in_Supervisory_Control)).

Agent memory has a comparable hidden-mode risk. It is **likely (55-80%)** that an operator sometimes cannot tell whether an answer came from the current conversation, a persistent owner preference, a repository-scoped memory, a stale task note, or an inferred “lesson,” because those sources can be merged into one context without a source-level display. The incidence in this harness is **UNVERIFIED; the baseline arm of the Memory Surprise Study in §9 would settle it**.

### 4.2 Translation: a memory annunciator — UNVERIFIED

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Whenever persistent memory materially shapes a plan, tool target, refusal, or completion claim, show one compact annunciation:

```text
MEMORY ACTIVE: 3 records
  owner preference (non-expiring; explicit; 2026-07-01)
  repo constraint (review on branch/source change; verified now)
  open loop (expires 2026-07-20; not reverified)
QUARANTINED: 1 superseded record
```

Do not dump record bodies unless requested. Annunciate transitions—memory loaded, record quarantined, scope changed, conflict detected—not a constantly scrolling dashboard.

This is **likely (55-80%)** to make hidden memory influence diagnosable because it exposes the active mode and transitions, matching the cognitive problem identified by Sarter and Woods. Whether users notice and correctly interpret the annunciation is **UNVERIFIED; the “Memory Surprise Study” in §9 would compare detection of deliberately seeded wrong-scope memories with and without the annunciator**.

It is **unlikely (20-45%)** that annunciation alone prevents stale-memory errors because aviation’s evidence concerns awareness demands, not guaranteed corrective action, and operators can miss or misunderstand displays. That is why annunciation supplements lifecycle and verification controls rather than replacing them.

## 5. Mechanism D: non-punitive occurrence learning without automatic belief

### 5.1 How it works in aviation

NASA’s Aviation Safety Reporting System is voluntary, confidential, non-punitive, and independent. Reports are de-identified; qualifying unintentional violations receive enforcement-related incentives under defined limits ([NASA ASRS confidentiality and incentives](https://asrs.arc.nasa.gov/overview/confidentiality.html)). Its database contains sanitized narratives plus coded information added by expert analysts. Crucially, NASA states that ASRS **does not verify or validate reports** and cannot confirm their details ([ASRS Database Online](https://asrs.arc.nasa.gov/search/database.html)).

ICAO Annex 13 makes prevention—not blame or liability—the objective of accident and incident safety investigation ([ICAO Annex 13 description](https://store.icao.int/en/annex-13-aircraft-accident-and-incident-investigation); historical explanation [here](https://www.icao.int/sites/default/files/postalhistory/annex_13_aircraft_accident_and_incident_investigation.htm)). FAA describes Safety Management Systems as a structured learning culture that seeks and analyzes information and turns it into risk mitigation before unwanted events ([FAA SMS and voluntary programs](https://www.faa.gov/licenses_certificates/airline_certification/air_carrier/cert_volun_safety_program)).

The subtle lesson for memory is separation of stages:

1. make weak signals easy to report;
2. preserve enough context to learn why;
3. separate safety learning from blame;
4. analyze and code the report;
5. do **not** equate a report with a verified fact;
6. promote a lesson only after evidence or accountable acceptance.

### 5.2 Translation: candidate lessons, not automatic durable rules — UNVERIFIED

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On owner correction, repeated tool failure, rollback, or near miss, append a compact `incident_hypothesis` candidate containing event, context, observed consequence, suspected contributing factors, and a proposed prevention check. Do not inject it as an active rule. Promote it only when one of these gates is met:

- an explicit owner acceptance;
- the same fingerprint recurs in a distinct session and the candidate predicts it;
- an independent authoritative source supports the rule;
- a controlled replay shows the rule prevents the failure without material regressions.

This is **likely (55-80%)** to preserve useful weak signals without canonizing one-off explanations because NASA ASRS explicitly separates rich incident reporting from verification. Harness benefit is **UNVERIFIED; the “Candidate Promotion Replay” in §9 would compare automatic promotion, gated promotion, and no learning on later sessions**.

“Blamelessness” does not transfer as concern for the model’s feelings. The agent has no employment, license, or fear of discipline. It transfers only to the human/system incentive structure: if telemetry is used to shame the owner or silently punish workflows, reporting becomes selected and incomplete. This claim about selection effects in this specific harness is **UNVERIFIED; an opt-in reporting experiment comparing capture rates under identifiable versus de-identified summaries would settle it**.

        no                        +--> confirm or quarantine/conflict

        |

This integrated design is **likely (55-80%)** to outperform undifferentiated “remember everything” memory on stale-state errors because each control has a distinct function: validity bounds retirement, scope controls context, provenance supports revalidation, supersession prevents competing current versions, annunciation exposes hidden influence, and challenge-response checks consequential use. ## 7. Forgetting policy: suppress first, delete later

Aviation’s NOTAM model supports operational expiry, but agent memory has a stronger audit and reversibility need. Therefore the translation deliberately diverges:

1. At expiry or contradiction, remove the item from silent active retrieval.
2. Keep a tombstone and provenance so a later session can explain why it disappeared.
3. Permit explicit renewal only after revalidation; renewal creates a new version rather than editing history invisibly.
4. Garbage-collect quarantined content only under an owner-approved retention policy, while retaining a minimal tombstone where appropriate.

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Default to quarantine on expiry and define retention by memory class. This is **very likely (80-90%)** to be safer than immediate deletion because quarantine is reversible and preserves diagnosis; evidence is the direct difference in recoverability, not an aviation outcome. The best retention periods are **UNVERIFIED; a storage-growth and resurrection-rate study over 90 days would settle them**.

**Proposal — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a session-end review that lists only items newly admitted, nearing review, conflicted, or still-open—not the entire archive. This is **likely (55-80%)** to prevent forgotten temporary records while limiting checklist fatigue, based on the NASA/FAA warning about long checklists. Actual completion and renewal quality are **UNVERIFIED; log review abandonment and incorrect-renewal rates in Memory AIRAC Replay**.

## 8. Adversarial transfer analysis

### 8.1 Structural similarities that support transfer

- Both domains use changing external facts to guide later consequential actions.
- Both can suffer when an old but once-correct state is silently treated as current.
- Both involve automation whose active state and source of behavior may be opaque to its supervisor.
- Both benefit from separating an observation/report from a verified operational rule.
- Both face an attention budget: excessive notices and checklists can hide critical items. The checklist report’s warning about long lists is direct aviation evidence ([NASA/FAA checklist report, pp. 20–21](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)).

These similarities make transfer of lifecycle metadata, sparse phase gates, and state annunciation **likely (55-80%)** to be structurally sound. Agent-specific effectiveness remains **UNVERIFIED; §9 provides the experiments**.

### 8.2 Disanalogies that prohibit wholesale transfer

1. **Bounded versus open world.** Aviation procedures operate inside a highly specified aircraft, airspace, operator, and regulatory envelope. General agents encounter novel tools, repositories, and goals. A checklist cannot enumerate every correct action. Therefore checklist borrowing must be limited to critical state transitions and verification shape, not task content.

2. **Certified sources versus heterogeneous evidence.** FAA NOTAMs have accountable/certified originators and standardized formats. Agent memories may originate from a user, an unreliable web page, a tool error, or the model’s inference. Merely adding an `authority` field cannot manufacture certification. The design must preserve source class and refuse to promote inferences as permanent facts.

3. **Coordinated effective dates versus asynchronous software change.** AIRAC synchronizes participants on scheduled cycles. Software dependencies, branches, services, and owner intentions can change at any time. The transferable element is explicit effectiveness and revalidation—not a 28-day cadence.

4. **Human crew independence versus correlated model checks.** Two pilots can provide mutual redundancy, although they too share training and biases. Two calls to the same model over the same context are more strongly correlated and are not mechanically independent. The harness must verify against a different data source or measurement, not spawn rhetorical “reviewers.”

5. **Safety severity and economics.** Aviation accepts procedure, training, and delay costs against catastrophic risk. Most agent actions are lower stakes and high frequency. It is **very likely (80-90%)** that applying flight-deck rigor everywhere would produce alert/checklist fatigue and material cost, based on the NASA/FAA checklist report's documented risk of poor or non-use as lists lengthen. Harness-specific magnitude is **UNVERIFIED; Challenge Gate A/B would settle it**. Consequence gating is therefore part of the proposal.

6. **Blame incentives.** ASRS confidentiality addresses career, legal, and enforcement incentives for humans. An agent does not experience those incentives. The transferable target is honest human reporting and unbiased incident capture, not being kind to a model.

7. **Expiry can erase valid preferences.** A runway closure naturally ends; a stable owner preference may not. It is **almost certain (90-99%)** that uniform finite TTLs would eventually suppress at least some still-valid non-expiring preferences by construction; the direct evidence is that expiry depends on elapsed time rather than truth change. Review triggers and source-change events are therefore preferable for invariants and preferences; their relative performance is **UNVERIFIED and would be tested in Memory AIRAC Replay**.

8. **Aviation mechanisms also fail operationally.** The sources specify intended controls, not infallibility. ASRS explicitly does not validate reports; checklist literature acknowledges interruption and usability problems; mode annunciations themselves create monitoring demands. The harness must test outcomes rather than invoke aviation prestige.

### 8.3 Verdict

The analogy **does transfer** for four narrow mechanisms: validity-bounded records, supersession, sparse challenge–verification–response, and visible retrieval state. It **does not transfer** as an argument for exhaustive procedures, a regulatory organization, blanket multi-agent review, or automatic incident-to-rule learning.

The confidence in this boundary is **very likely (80-90%)**, supported by the explicit limitations in the original aviation sources: checklist length/non-use risk, ASRS non-validation, and mode proliferation/monitoring burden. The exact optimal boundary in this harness is **UNVERIFIED; the staged experiments below would settle whether each additional control earns its cost**.

## 9. Settling experiments

### 9.1 Memory AIRAC Replay

Build an offline benchmark of cross-session facts whose later ground truth is independently observable: changed files/digests, branch/workspace changes, service recovery, explicit owner supersession, closed open loops, and still-valid stable preferences. Detector validation must include known-present positive controls for each change type.

Compare:

- baseline memory retrieval;
- schema only;
- schema + quarantine/supersession;
- full design with phase brief and challenge gate.

Primary metrics: stale-memory precision/recall, harmful stale uses, valid-memory suppression, missing-metadata rate, extra tool calls, prompt tokens, and task completion. A claim of “caught” requires two mechanically independent signals: the lifecycle detector plus later authoritative state/correction. A claim of “no stale memory” requires a known-present seeded stale item to prove detector sensitivity.

Go criterion: the full design must reduce harmful stale uses materially without suppressing more valid memories than it saves; the threshold must be selected before evaluation. Until this experiment runs, the integrated recommendation remains **UNVERIFIED**.

### 9.2 Challenge Gate A/B

Seed mutable memories before tasks requiring destructive, external, publish, and completion actions. Randomize live verification by action class. Measure contradiction catches, false alarms, added calls, latency, and whether the action changes appropriately. Include a sham “self-review” arm that only asks the same model to reconsider; this tests the requirement for mechanical independence.

The prediction that live-source verification beats sham self-review is **very likely (80-90%)**, because only the former adds independent evidence. Its magnitude is **UNVERIFIED; this A/B settles it**.

### 9.3 Memory Surprise Study

Deliberately seed one correct, one stale, and one wrong-scope memory. Compare no disclosure, full memory dump, and transition-only annunciation. Ask operators to identify which persistent memories influenced the result and intervene when inappropriate. Measure detection, time, false suspicion, and notification dismissal.

Transition-only annunciation is **likely (55-80%)** to beat both silence and full dumps because it exposes mode changes while limiting attention load; this premise is **UNVERIFIED, and this study settles it**.

### 9.4 Candidate Promotion Replay

From incident/correction narratives, compare no learning, immediate automatic rule creation, and gated candidates. Replay later similar and dissimilar tasks. Score recurrence prevented, regressions introduced, false generalizations, and owner overrides.

Gated promotion is **likely (55-80%)** to outperform immediate promotion because it separates reports from validated facts, as ASRS explicitly does. Transfer performance is **UNVERIFIED; this replay settles it**.

## 11. Alternatives considered and rejected

### Copy all aviation checklists into agent procedures

Rejected. Task content is open-ended, and the aviation source itself warns that long lists invite poor or non-use. Only checklist structure and critical-phase selection transfer.

### Give every memory a fixed TTL

Rejected. It confuses temporary operational notices with stable preferences/invariants, guarantees periodic amnesia, and does not detect a change that occurs before the TTL. Typed review triggers are more faithful to the underlying validity problem.

### Delete expired memories immediately

Rejected. Aviation operational notices can disappear because controlled publications and accountable organizations maintain continuity. It is **likely (55-80%)** that an agent harness will need history to explain some decisions or recover some mistakenly expired preferences, because provenance and erroneous-expiry diagnosis require the prior record. The incidence is **UNVERIFIED; the storage-growth and resurrection-rate study in §7 would settle it**. Quarantine first preserves reversibility.

### Use several agents as a “crew” to vote on memory truth

Rejected. Same-model agents are not mechanically independent evidence. It is **very likely (80-90%)** that a voting design would add fan-out cost, by construction, and it could introduce a second orchestration layer depending on implementation; that implementation premise is **UNVERIFIED and would be settled by a line-count/architecture review before prototyping**. A live source check supplies a mechanically independent signal with a smaller proposed surface.

### Automatically convert every correction/error into a permanent rule

Rejected. ASRS explicitly distinguishes reports from validated facts. Immediate promotion overfits one incident and can preserve an incorrect causal story.

### Build a vector database or knowledge graph for provenance and supersession

Rejected. The required relations are small and explicit (`scope`, `supersedes`, dates, triggers). A human-readable record file and deterministic scan ride the existing bus and avoid a previously rejected memory subsystem.

### Treat non-punitive reporting as “never assign responsibility”

Rejected. Aviation separates prevention-oriented learning from blame proceedings; it does not erase accountable originators or validity responsibilities. Agent memory likewise needs accountable provenance while avoiding premature blame-based suppression of incident data.

## 12. Gaps and evidence limits

## 13. Bottom line

Aviation’s useful answer to cross-session memory is not “remember more.” It is: **publish deliberately, declare when information becomes effective, bound temporary information, identify its origin, supersede rather than silently overwrite, expose active automation state, verify critical claims against the world, and learn from incidents without mistaking reports for facts.**

A minimal memory envelope implementing those controls is **likely (55-80%)** to catch meaningful stale- and wrong-context-memory failures with less overfit than a richer memory platform, based on the direct structural match among controlled aeronautical information, checklist redundancy, and mode awareness.
