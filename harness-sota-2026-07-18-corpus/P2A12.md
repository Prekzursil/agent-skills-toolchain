# P2A12 — Prompt programs: optimization, structured generation, and constrained decoding

**Unit:** P2A12  
**Date:** 2026-07-18  
**Research lens:** external evidence only. I did not inspect or characterize the local harness, repository, configuration, or session corpus.  
**Question:** Do DSPy-style optimization, structured generation, or constrained decoding fit a personal agent harness without becoming a second runtime?

## Executive conclusion

Yes, but only after separating three ideas that are often bundled together.

1. **Provider-native structured output fits directly.** Claude's API now compiles JSON Schemas into grammars for constrained sampling, while Claude Code and the Agent SDK expose schema-shaped final output for agent runs. These are existing execution paths, not a new orchestration layer. The API mechanism constrains generation; the Agent SDK mechanism validates and re-prompts. They solve related but different problems ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Claude Code headless mode](https://code.claude.com/docs/en/headless), [Agent SDK structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs)).
2. **Prompt optimization fits only as an offline compiler/laboratory.** DSPy, MIPROv2, and GEPA have credible benchmark results, but they require task examples and a metric, can be expensive, can overfit, and show model/task-dependent gains. The deployable artifact should be a reviewed plain-text prompt plus an evaluation manifest; DSPy or GEPA should not own the live agent loop ([MIPRO paper](https://arxiv.org/abs/2406.11695), [GEPA paper](https://arxiv.org/abs/2507.19457), [DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md), [negative replication study](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)).
3. **Third-party constrained-decoding runtimes do not fit unless local inference already exists for another reason.** Outlines, Guidance, XGrammar, vLLM guided decoding, and LMQL are useful inference/programming systems, but introducing one solely to format hosted Claude output duplicates a native capability and creates another compatibility surface. Maintainer issue trackers show model/backend-specific failures even where structural guarantees are the product's purpose ([Outlines repository](https://github.com/dottxt-ai/outlines), [XGrammar repository](https://github.com/mlc-ai/xgrammar), [vLLM structured-output failure](https://github.com/vllm-project/vllm/issues/13260), [LMQL repository](https://github.com/eth-sri/lmql)).

The architectural answer is therefore: **native constraints at narrow machine boundaries; ordinary prose for reasoning; an offline, evidence-gated prompt tournament for a few repeated tasks; no prompt framework in the live control plane.**

## Method and evidence discipline

I decomposed the question into five tests: demonstrated quality gain, generalization, structural guarantee, operational footprint, and fit with an existing hook/skill/MCP bus. Sources were restricted to primary papers, official documentation, real repositories, and maintainer issue trackers. I deep-read the core DSPy/MIPRO, GEPA, LMQL, JSONSchemaBench, Claude structured-output, and Claude Code/Agent SDK materials and used issue reports as counter-signals to project claims.

The configured multi-provider research harness described by the selected research skill was not exposed in this unit's tool surface. Web search/open was live; Firecrawl, Exa, Tavily, Perplexity, scholarly-access, Hugging Face, Context7, and SearXNG preflights could not be run. This limits index-level corroboration, not access to the primary URLs cited below.

Claims from a framework's own paper or repository are treated as evidence that the result or feature was reported, not independent proof that it generalizes. Recent 2026 preprints are explicitly marked **UNVERIFIED** where peer review, replication, or applicability to this owner's workload is unsettled.

## 1. What is actually established

### 1.1 Automatic prompt optimization is real, measurable, and task-bound

DSPy formalizes an LM program as modules with typed-ish signatures and treats instructions, demonstrations, or model weights as optimizable parameters. Its optimizer contract requires a program, a scoring metric, and examples. MIPRO bootstraps traces, proposes data- and program-aware instructions, and searches combinations of instructions and demonstrations using minibatch evaluation and a surrogate model ([DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md), [MIPRO paper](https://arxiv.org/abs/2406.11695)).

The MIPRO paper reports improvement over baseline optimizers on five of seven multi-stage programs using Llama-3-8B, with gains as high as 13 percentage points. This establishes that joint prompt optimization can outperform the compared baselines in some controlled programs; it does not establish universal improvement or transfer to a general coding agent ([MIPRO paper](https://arxiv.org/abs/2406.11695)).

OPRO independently demonstrated the basic search pattern—feed an optimizer LM previous candidate prompts and scores, ask it for new candidates, evaluate, repeat—and reported best-candidate gains up to 8% on GSM8K and up to 50% on selected Big-Bench Hard tasks. A later study found OPRO much less effective with smaller Llama-2 and Mistral models and emphasized compute cost and strong direct-instruction baselines ([OPRO paper](https://arxiv.org/abs/2309.03409), [OPRO limitations study](https://arxiv.org/abs/2405.10276)). This pair is important: automatic prompt search is an optimization method, not a property that guarantees lift.

TextGrad implements a PyTorch-like computation graph whose “gradients” are natural-language critiques. Its paper reports improvements across QA, code, molecules, and radiotherapy, including GPT-4o GPQA accuracy from 51% to 55% and a 20% relative gain on LeetCode-Hard solution optimization ([TextGrad paper](https://arxiv.org/abs/2406.07496)). These are author-reported results across diverse demonstrations; they establish breadth of the mechanism, not that a textual autograd runtime is necessary for a personal harness.

GEPA uses execution traces, natural-language reflection, mutation, and Pareto selection. Its paper reports an average 6% advantage over GRPO across six tasks, up to 35 times fewer rollouts, and more than 10% over MIPROv2 in reported comparisons ([GEPA paper](https://arxiv.org/abs/2507.19457)). Its standalone repository accepts a dictionary of text candidates and a caller-supplied evaluator, so it can optimize a prompt without rewriting the live system as DSPy ([GEPA repository](https://github.com/gepa-ai/gepa)).

The counter-evidence is equally concrete. A recent study across 72 optimization runs on Claude Haiku 4.5—six methods, four tasks, three repeats—found 49% of runs below the zero-shot baseline; on three tasks, average gains were negative or near zero. It used only 20 training questions and observed train/test gaps up to 5.6 points, so its scope is deliberately representative of low-data practice rather than a definitive upper bound. Its one consistent positive task had a clear structured-output gap ([Prompt Optimization Is a Coin Flip](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)).

**Established synthesis:** prompt optimization is worthwhile to test where (a) a task repeats, (b) success is executable or otherwise measurable, (c) enough representative cases exist, and (d) the optimized artifact is evaluated on data the optimizer never saw. The literature does not establish automatic optimization as a safe default for a broad, heterogeneous system prompt.

### 1.2 Optimization cost and data discipline are part of the mechanism

DSPy's own FAQ gives an illustrative compilation run of 3,200 API calls, 2.7 million input tokens, 156,000 output tokens, about six minutes, and then-current cost of USD 3. Its current optimizer guide says a typical simple run may take roughly ten minutes and cost around USD 2, with real runs ranging from cents to tens of dollars depending on model and data ([DSPy FAQ](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/faqs.md), [DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)). The dollar values age; the established point is that compilation spends many inference calls before deployment.

DSPy's current guidance suggests BootstrapFewShot around ten examples, random-search few-shot optimization from roughly 50 examples, and MIPROv2 with 40 or more trials and around 200 or more examples to reduce overfitting risk ([DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)). Those are maintainer heuristics, not universal sample-complexity laws.

Optimized DSPy programs can be saved as readable JSON and reloaded later ([DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)). That capability makes an offline compiler/deployment split possible, but loading the serialized DSPy program still retains DSPy as a runtime dependency. Exporting and reviewing the resulting prompt text avoids that dependency more completely.

### 1.3 Structured output has three distinct guarantee levels

**Provider constrained decoding.** Claude's API `output_config.format` compiles a JSON Schema into a grammar and constrains sampling; `strict: true` similarly constrains tool names and inputs. Anthropic documents schema-compliant JSON and typed required fields, plus native Pydantic, Zod, Java, Ruby, PHP, C#, and Go helpers ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). OpenAI likewise describes dynamic constrained decoding and distinguishes strict JSON Schema output from JSON mode, which only ensures valid JSON ([OpenAI structured outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)).

**Agent-run validation and repair.** Claude Code accepts `--output-format json --json-schema ...` and returns the result in `structured_output`; its Agent SDK documentation says the SDK validates against the schema and re-prompts on mismatch, returning an error if validation still fails within the retry limit ([Claude Code headless mode](https://code.claude.com/docs/en/headless), [Agent SDK structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs)). That is a final-output contract around a multi-turn tool-using agent, not token-by-token grammar control over every intermediate turn.

**Client-side validation/retry.** Instructor wraps provider clients with Pydantic models and retries failed validation with the validation error ([Instructor repository](https://github.com/567-labs/instructor)). This is useful when provider-native facilities are absent or inconsistent; it is not constrained decoding and it duplicates the Agent SDK's documented repair loop for this use case.

These levels must not be described by the same “guaranteed” shorthand. A grammar can guarantee syntactic membership in the supported schema language; it cannot guarantee factual truth, correct reasoning, safe intent, or that a string field contains the intended value. OpenAI explicitly notes that Structured Outputs does not prevent mistakes inside values ([OpenAI structured outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)).

### 1.4 Native constraints have explicit limits and failure exits

Anthropic documents first-use grammar compilation latency, 24-hour grammar caching, added system-prompt tokens, prompt-cache invalidation when the output format changes, and JSON Schema feature limitations ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

Anthropic also documents non-schema exits: a refusal can return HTTP 200 with `stop_reason: "refusal"` and nonconforming output; a token-limit stop can truncate the object; and string enum/const capitalization can differ despite a normal completion. Callers therefore still need stop-reason and transport handling even with constrained output ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

Schema complexity is operational, not aesthetic. Anthropic currently caps strict tools at 20, optional parameters at 24, and union-typed parameters at 16 across the request; it also has an internal grammar-size limit and a 180-second compilation timeout. Its mitigation order is to make only critical tools strict, reduce optional fields, and flatten nesting ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

### 1.5 Open-source constrained decoding is substantive but belongs to the inference layer

Outlines converts choices, regexes, JSON Schemas, and grammars into constraints and integrates with local Transformers/llama.cpp and serving systems such as vLLM/Ollama, as well as some hosted APIs ([Outlines repository](https://github.com/dottxt-ai/outlines)). XGrammar compiles grammars and token-vocabulary state into masks and is integrated into vLLM, SGLang, TensorRT-LLM, and MLC-LLM ([XGrammar repository](https://github.com/mlc-ai/xgrammar), [XGrammar paper](https://arxiv.org/abs/2411.15100)). Guidance is another Python library that interleaves generation with constraints over supported backends ([Guidance repository](https://github.com/guidance-ai/guidance)). These are real systems, not merely prompt templates.

JSONSchemaBench contains 10,000 real-world schemas, combines them with the official JSON Schema Test Suite, and evaluates Guidance, Outlines, llama.cpp, XGrammar, OpenAI, and Gemini along efficiency, coverage, and output-quality dimensions ([JSONSchemaBench paper](https://arxiv.org/abs/2501.10868), [JSONSchemaBench repository](https://github.com/guidance-ai/jsonschemabench)). The existence of separate coverage and quality axes is evidence against equating “valid JSON” with “good answer.”

Issue trackers expose real edges: Outlines users have reported valid but poor string values under broad string regexes ([Outlines issue 994](https://github.com/dottxt-ai/outlines/issues/994)); vLLM users have reported endless whitespace/generation and crashes in guided modes for particular models and backends ([vLLM issue 13260](https://github.com/vllm-project/vllm/issues/13260), [vLLM issue 13683](https://github.com/vllm-project/vllm/issues/13683)); and XGrammar had a nondeterministic grammar that caused an infinite loop before a fix ([XGrammar issue 127](https://github.com/mlc-ai/xgrammar/issues/127)). These do not show that the projects are generally broken. They show that a self-hosted grammar stack creates a tokenizer/model/grammar/engine compatibility matrix that a personal hosted-model harness would otherwise not own.

### 1.6 LM programming languages are execution runtimes, not neutral prompt files

LMQL is a Python-superset language with its own query semantics, control flow, constraint evaluation, decoding strategies, async execution, and playground. Its paper reports 26–85% cost savings on evaluated tasks, while its repository's latest listed release is 0.7.3 from October 2023 and warns that `main` is not continuously tested ([LMQL paper](https://arxiv.org/abs/2212.06094), [LMQL repository](https://github.com/eth-sri/lmql)). Regardless of quality, adopting LMQL means adopting a second language/runtime for prompts. That fails this unit's architectural constraint.

## 2. What is promising but unproven

### 2.1 Offline GEPA for narrow, repeated harness tasks

It is **likely (55-80%)** that a dev-only GEPA experiment will find a better prompt than the current hand-written baseline for at least one repeated, objectively scored harness leaf task. Evidence for the upper side is GEPA's reported gains across six tasks, trace-based feedback, standalone adapter, and comparatively low rollout counts; evidence against certainty is the small task suite, author affiliation overlap with DSPy, and the 2026 study in which prompt optimizers frequently failed to beat zero-shot ([GEPA paper](https://arxiv.org/abs/2507.19457), [GEPA repository](https://github.com/gepa-ai/gepa), [negative replication study](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)).

This premise is **UNVERIFIED; the settling experiment is a preregistered prompt tournament on three owner tasks with chronological train/dev/frozen-test splits, three run seeds, identical model/version/tool access, and bootstrap confidence intervals against the current prompt**. Candidate tasks should have executable outcomes such as correct routing, valid patch classification, or faithful failure fingerprinting—not holistic “be a better agent” judging.

It is **unlikely (20-45%)** that GEPA optimization of one global system prompt will improve the owner's full task distribution without meaningful regressions. Evidence: recent studies find task- and model-specific prompt effects, iterative overfitting, and poor cross-task transfer ([Prompt Optimization Is a Coin Flip](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf), [Why Prompt Optimization Works](https://arxiv.org/abs/2605.26655)). The settling experiment would require a representative multi-domain frozen test set with safety, autonomy, coding, research, and interaction outcomes; no cited study supplies that owner's distribution.

### 2.2 “Can but does not” headroom screening

It is **likely (55-80%)** that a cheap candidate-spread screen will prevent wasted optimizer runs: generate 10–20 materially different prompt candidates, evaluate them on a small development sample, and stop if score differences are within resampling noise. Evidence is the recent negative study's finding that optimization worked on the task with an exploitable structured-format gap and its proposed score-spread screen ([Prompt Optimization Is a Coin Flip](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)).

This is **UNVERIFIED; the settling experiment is to compare the screen's go/no-go prediction against full optimizer outcomes on at least ten task/model pairs**. The paper's fixed “greater than two points” rule should not be copied literally; the harness should use uncertainty from repeated runs or bootstrap resampling because metric scales differ.

### 2.3 Hybrid free reasoning plus constrained final state

It is **very likely (80-90%)** that allowing ordinary agent reasoning/tool use and constraining only the final state-update or handoff object will outperform constraining every intermediate response operationally. Evidence: Anthropic explicitly scopes API grammar to direct output rather than thinking/tool results, while the Agent SDK supports multi-turn tool use followed by validated final output; schema complexity and compile costs grow with the constrained surface ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Agent SDK structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs)). The settling experiment is an A/B test of final-only versus per-step structured responses on completion rate, semantic correctness, latency, tokens, and retries.

### 2.4 Schema wording as an instruction channel

It is **roughly even (45-55%)** that deliberately descriptive property names and field descriptions materially improve semantic correctness in this harness after structural validity is guaranteed. A 2026 preprint reports that schema-key wording can alter reasoning performance and that effects differ by model family ([Schema Key Wording as an Instruction Channel](https://arxiv.org/abs/2604.14862)). This is **UNVERIFIED; the settling experiment is a counterbalanced A/B test of semantically rich versus neutral keys on the same schemas, prompts, model versions, and inputs, scored on value correctness rather than parse validity**.

### 2.5 Local constrained decoding if local inference becomes independently justified

It is **unlikely (20-45%)** that installing XGrammar/Outlines plus a local inference server solely for this personal harness will provide net value today. Native hosted constraints already exist, whereas local stacks add model weights, GPU/runtime management, tokenizer coupling, and backend-specific failures ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [XGrammar repository](https://github.com/mlc-ai/xgrammar), [vLLM issue 13260](https://github.com/vllm-project/vllm/issues/13260)).

If private/offline inference is independently adopted later, it is **likely (55-80%)** that XGrammar through the already-selected inference server would be preferable to a hand-written parser/retry loop, because XGrammar is integrated into major engines and reports low decoding overhead ([XGrammar repository](https://github.com/mlc-ai/xgrammar), [XGrammar paper](https://arxiv.org/abs/2411.15100)). This is **UNVERIFIED; the settling experiment is JSONSchemaBench plus the owner's actual schemas on the exact model/tokenizer/server versions, including semantic accuracy, timeout, whitespace-loop, and concurrency tests**.

## 3. What is hype, and how to tell

### 3.1 “Programming, not prompting” does not remove specification work

DSPy replaces hand-editing strings with program signatures, metrics, examples, search, and compilation. That is a valuable change in engineering method, but the user must still choose the task boundary, training distribution, metric, evaluator, optimizer, and deployment threshold ([DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)). If those are weak, the optimizer faithfully optimizes a weak proxy. The tell is simple: a claim of automatic improvement that omits the metric, baseline, held-out set, model version, and optimization budget is marketing, not a reproducible result.

### 3.2 “Guaranteed output” commonly slides from syntax into semantics

Constrained decoding guarantees only membership in a supported formal language, subject to documented exits such as refusal and truncation. It does not make a plausible string factually correct or a tool action appropriate. OpenAI states this limitation directly, Anthropic documents exception exits, and JSONSchemaBench evaluates output quality separately from schema coverage ([OpenAI structured outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/), [Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [JSONSchemaBench paper](https://arxiv.org/abs/2501.10868)). The tell is a 100% number whose denominator is schema conformance rather than end-task correctness.

### 3.3 “Works with any model/schema” hides a compatibility matrix

Outlines advertises broad model portability and XGrammar advertises universal deployment; both are serious projects. Yet maintainers and users document backend-, grammar-, whitespace-, tokenizer-, and model-specific edge cases ([Outlines repository](https://github.com/dottxt-ai/outlines), [XGrammar repository](https://github.com/mlc-ai/xgrammar), [Outlines issue 994](https://github.com/dottxt-ai/outlines/issues/994), [XGrammar issue 127](https://github.com/mlc-ai/xgrammar/issues/127), [vLLM issue 13260](https://github.com/vllm-project/vllm/issues/13260)). The tell is whether a project publishes schema coverage, unsupported keywords, model/backend versions, semantic-quality evaluation, and failure behavior—not its star count or structural demo.

### 3.4 “Up to N% better” is not an expected-value estimate

MIPRO, OPRO, TextGrad, and GEPA all report large best-case gains, while controlled negative evidence finds many no-gain or negative-gain conditions ([MIPRO paper](https://arxiv.org/abs/2406.11695), [OPRO paper](https://arxiv.org/abs/2309.03409), [TextGrad paper](https://arxiv.org/abs/2406.07496), [GEPA paper](https://arxiv.org/abs/2507.19457), [negative replication study](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)). The tell is whether a report gives all tasks, all seeds, zero-shot and strong manual baselines, held-out performance, token/call budget, and failures. Best-task deltas are existence proofs, not forecasts.

### 3.5 “Optimize anything” is dangerous when the evaluator is incomplete

GEPA's repository explicitly exposes optimization of prompts, code, architectures, configurations, and other text artifacts against caller-supplied evaluation ([GEPA repository](https://github.com/gepa-ai/gepa)). That flexibility is technically real. It also increases Goodhart risk: an optimizer can discover brittle shortcuts, evaluator-specific wording, or verbose exception lists. Recent work reports prompt distributional overfitting as prompts lengthen and accumulate sample-specific rules ([TextReg preprint](https://arxiv.org/abs/2605.21318)). The tell is whether the proposed workflow includes immutable safety constraints, a frozen test set, prompt-length/complexity penalties, human diff review, and rollback.

### 3.6 Continuous self-improvement is a runtime proposal in disguise

An optimizer continuously consuming production traces, mutating system prompts, judging itself, and promoting winners is no longer an offline compiler. It is a second orchestration/control runtime with write authority. None of the cited benchmark results establishes that such autonomous promotion is safe for a broad personal agent. The tell is whether optimized prompts can reach production without an explicit, reproducible evaluation gate and owner-visible diff.

## 4. Specific things this owner's harness should adopt

Every item below includes the required implementation class and an explicit anti-overfit decision.

### 4.1 Use native structured final outputs at narrow machine boundaries — **NATIVE (Claude Code already does this; we just enable it)**

Adopt `claude -p --output-format json --json-schema ...` (or the corresponding Agent SDK `outputFormat`) for bounded headless operations whose result is consumed by code: routing decisions, hook decisions, task handoffs, defect classifications, and terminal status records. Use the direct Claude API's `output_config.format` or strict tool use when the harness makes a direct single-call API request and token-level constrained sampling is required ([Claude Code headless mode](https://code.claude.com/docs/en/headless), [Agent SDK structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs), [Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

Do **not** force the entire conversational answer or every intermediate tool step into JSON. The schema should describe only the state transition that code must consume. Always branch explicitly on SDK error, API `stop_reason`, missing `structured_output`, refusal, and truncation.

It is **very likely (80-90%)** that this reduces parse/schema retry failures at those boundaries. Evidence is the native constraint/validation mechanism and the platform's documented purpose; residual uncertainty concerns this harness's exact calling paths and semantic errors, which schemas cannot fix. The settling experiment is a canary comparison over 100 representative calls measuring parse failures, retries, latency, tokens, and value correctness.

**Anti-overfit gate:** passes. It enables a native feature on the existing Claude Code/API bus, creates no daemon or runtime, and does not reintroduce any rejected component.

### 4.2 Establish a “schema austerity” policy — **CONFIG (settings/JSON only)**

For every machine-facing schema:

- keep a small required core and represent optional narrative detail as one free-text field rather than many optional branches;
- avoid deeply nested objects, case-only enum distinctions, and unions unless they change executable behavior;
- separate `status`/`error` envelopes from success payloads;
- place semantic constraints in field descriptions but validate critical values in ordinary code;
- use strictness only for tools whose malformed arguments cause real failure;
- version schemas and keep stable structures to preserve grammar/prompt caches.

These rules follow Anthropic's documented complexity caps, failure modes, cache invalidation, and mitigation order ([Claude API structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

It is **very likely (80-90%)** that austere schemas will be more reliable and cheaper to compile/cache than a universal fan-out envelope. Evidence is the platform's explicit optional/union/tool limits and recommendation to flatten/reduce; uncertainty is the magnitude for the owner's schemas. The settling experiment is to compile and execute both minimal and expanded variants on the same workload.

**Anti-overfit gate:** passes. This is a schema/configuration convention on the existing bus and adds no software component.

### 4.3 Add a schema preflight and semantic canary — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build one stateless script, invoked by an existing test skill or hook, that:

1. validates each schema against the supported subset;
2. counts strict tools, optional fields, union fields, maximum nesting, and schema bytes;
3. rejects case-colliding enums and flags unconstrained strings at executable boundaries;
4. runs a small fixed canary set through the actual Claude Code/API path;
5. checks both schema validity and domain assertions on values;
6. emits one terminal `SUCCESS:<id>` or `FAILED:<id> reason` result.

Use JSONSchemaBench's separation of coverage, efficiency, and quality as the test model, but do not import its full benchmark into routine harness execution ([JSONSchemaBench paper](https://arxiv.org/abs/2501.10868), [JSONSchemaBench repository](https://github.com/guidance-ai/jsonschemabench)).

It is **likely (55-80%)** that this catches schema regressions before they enter live fan-out. Evidence is the documented platform complexity/failure modes and cross-framework benchmark methodology; uncertainty is the current rate of schema-change defects in this harness. The settling experiment is prospective defect capture over the next 20 schema changes.

**Anti-overfit gate:** passes. It is stateless, under roughly 200 lines, runs only on demand/on change, and uses the current test/hook path. It is not a guardrail framework, service, or observability product.

### 4.4 UNVERIFIED — Add an offline prompt headroom probe and tournament — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Create a dev-only command/skill for a *single named prompt and model version*. It should:

1. require a baseline prompt, executable metric, immutable invariants, and chronological train/dev/frozen-test files;
2. generate 10–20 diverse candidates with one existing model call;
3. run at least three seeds and estimate score uncertainty;
4. stop if candidate spread is indistinguishable from noise;
5. only then optionally invoke standalone GEPA with a hard call/token budget;
6. penalize prompt length and reject changes to safety/authority invariants;
7. evaluate once on the frozen test set after selection;
8. output a plain-text prompt, unified diff, scores, model IDs, dataset hashes, cost, and rollback pointer;
9. never edit or promote the live prompt automatically.

This recommendation is **UNVERIFIED; the settling experiment is the three-task preregistered tournament described in §2.1**. It is **likely (55-80%)** to produce a useful improvement on at least one narrow task, based on the positive optimizer papers and negative evidence that emphasizes screening and held-out evaluation ([MIPRO paper](https://arxiv.org/abs/2406.11695), [GEPA paper](https://arxiv.org/abs/2507.19457), [negative replication study](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf)).

**Anti-overfit gate:** passes only with the stated boundary. The runner is an offline skill, GEPA is an optional development dependency, and deployment is plain text on the existing prompt bus. If GEPA begins owning live calls, trace ingestion, promotion, or rollback, the proposal becomes **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and fails this brief's anti-overfit gate.

### 4.5 Make optimized prompts model/task-scoped, reviewable, and reversible — **CONFIG (settings/JSON only)**

Store each accepted prompt beside a small manifest containing: task ID, target model and version, baseline hash, train/dev/test hashes, metric version, invariant checks, candidate budget, mean/variance or confidence interval, test delta, token length, acceptance decision, date, and previous version. Promotion is a human-reviewed pointer change; rollback is the inverse pointer change.

It is **very likely (80-90%)** that model/task scoping is safer than one global “best prompt.” Evidence is the model-dependent reversal and task-conditioned transfer failures reported in recent studies ([Prompt Optimization Is a Coin Flip](https://openreview.net/pdf/72f120a7e51905dcd82355757a28fe47ff13c6a5.pdf), [Why Prompt Optimization Works](https://arxiv.org/abs/2605.26655)). The settling experiment is longitudinal: re-evaluate accepted prompts after model upgrades and on adjacent task families.

**Anti-overfit gate:** passes. These are versioned text/JSON artifacts and review rules, not a registry service or durable-execution engine.

### 4.6 Do not install a prompt-programming framework in the live agent loop — **CONFIG (settings/JSON only)**

Record an architectural rule: production prompts, tool schemas, and handoff schemas remain native Claude Code/API artifacts. DSPy/GEPA may be invoked only by the offline experiment lane and must export plain text plus evidence. Do not rewrite the live harness as DSPy modules, a TextGrad graph, or LMQL programs.

It is **very likely (80-90%)** that this preserves most attainable optimization benefit while avoiding a second runtime. Evidence: optimizers ultimately emit prompt parameters, DSPy can serialize readable results, standalone GEPA can optimize text dictionaries, and LMQL explicitly supplies its own language/runtime ([DSPy optimizer documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md), [GEPA repository](https://github.com/gepa-ai/gepa), [LMQL repository](https://github.com/eth-sri/lmql)). The residual uncertainty is whether a future multi-module task genuinely needs joint runtime optimization; that would require its own measured case.

**Anti-overfit gate:** passes. This proposal actively excludes a second orchestration runtime and the rejected durable/critic/guardrail/observability components.

### 4.7 Do not add Instructor where native schema output is available — **NATIVE (Claude Code already does this; we just enable it)**

Use Claude Code/Agent SDK schema output or Claude API structured output directly. Instructor's Pydantic abstraction and retry feedback are useful for cross-provider application code, but for this Claude-centered harness they overlap the native SDK's validation/re-prompt path and introduce another provider compatibility layer ([Instructor repository](https://github.com/567-labs/instructor), [Agent SDK structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs)).

It is **likely (55-80%)** that native use will have fewer integration failure modes than adding Instructor for the same boundary. Evidence is feature overlap; uncertainty is whether the owner has a substantial cross-provider typed-extraction workload outside this unit's evidence. The settling experiment is unnecessary unless such a workload is identified; then compare adapter code, retries, and provider portability directly.

**Anti-overfit gate:** passes. It chooses the existing native bus and declines a duplicative wrapper.

### 4.8 Do not add Outlines, Guidance, XGrammar, vLLM, or LMQL solely for formatting — **NATIVE (Claude Code already does this; we just enable it)**

Provider-native Claude structure covers this harness's hosted-model output boundary. Outlines/Guidance/XGrammar require or integrate with an inference/API layer, vLLM is a serving runtime, and LMQL is a language/runtime. Their own documentation and issue trackers show both sophisticated capability and additional compatibility surfaces ([Outlines repository](https://github.com/dottxt-ai/outlines), [Guidance repository](https://github.com/guidance-ai/guidance), [XGrammar repository](https://github.com/mlc-ai/xgrammar), [vLLM issue 13683](https://github.com/vllm-project/vllm/issues/13683), [LMQL repository](https://github.com/eth-sri/lmql)).

It is **very likely (80-90%)** that installing any of them solely for hosted Claude formatting has negative net value. Evidence is native feature equivalence plus added runtime surfaces; uncertainty is any unstated local-inference requirement. The settling condition is architectural, not speculative: revisit only when local inference is independently selected.

**Anti-overfit gate:** passes by rejection. Adding these solely for format control would be a second runtime and fail the gate.

### Recommended adoption order

1. Enable native final-output schemas on one bounded headless path.
2. Apply schema austerity and add stop/error handling.
3. Add the small schema preflight/canary.
4. Select three repeated tasks with executable metrics.
5. Run the offline headroom probe; use GEPA only where candidate spread shows measurable headroom.
6. Promote only plain-text, model/task-scoped prompts with frozen-test evidence and rollback.

This sequence is deliberately reversible. No step requires replacing the agent loop, adding a daemon, or entrusting an optimizer with production writes.

2. **Claude Code implementation detail beneath `--json-schema`.** Official Agent SDK documentation explicitly says validation and re-prompting, while the Claude API documents grammar-constrained sampling. 3. **Independent GEPA replication on personal coding harnesses.** I found the author paper, repository, integrations, and a recent negative optimizer study, but no mature independent multi-model replication on a heterogeneous personal coding/research agent. This is **UNVERIFIED; settle it with preregistered owner-task trials and publication of all candidates/seeds**.
4. **Longitudinal prompt durability across silent model updates.** Recent work reports model-specific reversals, but I found no authoritative estimate of optimized-prompt half-life for hosted Claude Code models. This is **UNVERIFIED; settle it by scheduled re-evaluation keyed to reported model/version changes and a stable frozen set**.
5. **Semantic effects of constrained decoding on this workload.** Formal validity is well supported; semantic quality can improve, remain flat, or degrade depending on schema/model/task. 6. **Whether local inference has an independent requirement.** This unit was instructed not to inspect the local system, so I did not determine privacy, offline, latency, GPU, or cost requirements that might independently justify vLLM/XGrammar. If such a requirement exists, the rejection in §4.8 must be revisited against that requirement, not against formatting alone.
7. **Provider coverage beyond the live web route.** The research skill's Firecrawl/Exa/Tavily/Perplexity/scholarly/context providers were not exposed for preflight. The cited primary sources were accessible through web search/open, but I could not compare provider index recall or record cache hit/miss data.
