# T021 — Competitive teardown: AutoCodeRover

**Unit:** T021  
**Date:** 2026-07-19  
**Subject:** AutoCodeRover (public repository `AutoCodeRoverSG/auto-code-rover`)  
**Research snapshot:** public `main` at commit [`585d3e639aeda58ef0b6a151dd1cc2721a94d267`](https://github.com/AutoCodeRoverSG/auto-code-rover/commit/585d3e639aeda58ef0b6a151dd1cc2721a94d267), checked out read-only in a temporary research directory; owner harness inspected only in the supplied read-only bundle. The only written deliverable is this artifact.

## Executive verdict

AutoCodeRover (ACR) is not a general agent harness competitor in the Claude Code/Codex sense. It is a compact, fixed program-repair pipeline: generate a reproducer when possible; optionally run spectrum-based fault localization (SBFL); let a search agent iteratively call eight Python/AST-aware retrieval functions; hand selected `BugLocation` records to a patch agent; optionally execute the reproducer and ask a reviewer agent to judge both test and patch; run regression validation; retry; and select among candidate patches. Its public README accurately reduces the original design to two main stages, context retrieval and patch generation ([README lines 53–63](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L53-L63)); the current source adds reproducer, reviewer, validation, and selection stages around that spine ([`app/inference.py` lines 263–340](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L263-L340)).

The best idea to port is **not ACR itself**. It is the deliberate coupling of model-directed navigation to program structure and execution evidence. Specifically:

1. Search classes/methods as code entities, return small structurally complete units, and let results seed the next search stratum.
2. When tests exist, feed a short ranked list of suspicious methods from coverage contrast into retrieval—not directly into editing.
3. For repair-shaped work, make reproducer execution, independent review, regression comparison, bounded retry, and candidate selection a first-class lane.

Those three ideas ride our existing skill/hook/MCP and native subagent buses. They do not justify replacing the owner’s harness or adding a second orchestration runtime.

ACR is worse than the owner’s harness on nearly every general-harness axis: there is no MCP, no dynamically extensible tool registry, no rules/skills/hooks surface, no interactive permission policy, no durable semantic memory, no compaction or token-budget strategy, no collaborative agent team, and no safe treatment of a user’s working tree. Its local-issue setup performs hard reset/clean operations, and its patch context includes untrusted repository/issue/tool output without an explicit prompt-injection boundary. These are design warnings, not features to copy.

**Bottom line:** adopt the repair-specific epistemic mechanisms; reject the runtime and safety model. This conclusion is grounded in the public implementation, the paper, and two independently validated owner-side absence probes described below.

## System anatomy at a glance

```text
issue + checked-out Python repository
              |
              v
   reproducer agent (optional path)
       | execute; keep stderr/test
       v
   SBFL (optional, test-suite based)
       | top suspicious methods
       v
   retrieval agent <----+
       | choose up to several AST/search APIs
       v                |
   local SearchBackend --+
       | code results + analysis, bounded rounds
       v
   validated BugLocation[] + intended behavior
       |
       v
   patch agent -> syntactic/applicability check
       |
       +--> reproducer execution -> reviewer agent --feedback--+
       |                                                    |
       +--> regression evaluation --------------------------+
       |
       v
   repeat overall attempts; selector chooses candidate patch
```

This is a static workflow, not a model-authored plan and not an agent graph runtime. The orchestration is ordinary Python functions and generators in [`app/inference.py`](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py) and [`app/api/review_manage.py`](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/api/review_manage.py).

## 1. Agent loop

### Retrieval loop

The search agent’s system prompt assigns a single narrow role: gather sufficient code context, which will later be sent to a colleague for patch writing ([`agent_search.py` lines 16–22](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_search.py#L16-L22)). The prompt advertises eight callable-looking APIs:

- `search_class`
- `search_class_in_file`
- `search_method_in_file`
- `search_method_in_class`
- `search_method`
- `search_code`
- `search_code_in_file`
- `get_code_around_line`

The list and multi-call instruction are literal prompt text, not a provider-neutral tool registry ([`agent_search.py` lines 25–37](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_search.py#L25-L37)). Each stratum is two LLM decisions:

1. choose API calls;
2. after receiving results, analyze code purpose, bug relation, and intended behavior, then either request more APIs or emit bug locations ([`agent_search.py` lines 41–63](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_search.py#L41-L63), [`agent_search.py` lines 122–162](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_search.py#L122-L162)).

A proxy LLM converts the free-form response to JSON. The program validates that tools exist, invocations parse as Python expressions, and argument counts match; it retries the proxy up to five times ([`agent_proxy.py` lines 16–45](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_proxy.py#L16-L45), [`agent_proxy.py` lines 45–70](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_proxy.py#L45-L70), [`agent_proxy.py` lines 90–131](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_proxy.py#L90-L131)). The manager then executes each named `SearchBackend` method and records `func_name`, arguments, and `call_ok` ([`search_manage.py` lines 162–191](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L162-L191)).

The default conversation limit is 15 rounds, although the example experiment uses 10 ([`config.py` lines 8–15](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/config.py#L8-L15), [`conf/example.conf` lines 8–14](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/conf/example.conf#L8-L14)). If the loop exhausts the limit, it continues to patch generation with an empty bug-location list rather than failing closed ([`search_manage.py` lines 193–196](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L193-L196)).

### Patch/review loop

The patch agent does not edit files through tools. It receives the issue and selected code locations, emits exact-match `<original>`/`<patched>` blocks, and a deterministic postprocessor turns these into a diff. Its prompt insists on minimal changes, no test edits, exact continuous original snippets, and preservation of existing functionality ([`agent_write_patch.py` lines 29–80](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_write_patch.py#L29-L80)). Non-applicable output is retried up to three times ([`agent_write_patch.py` lines 130–161](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_write_patch.py#L130-L161)).

With `reproduce_and_review` enabled and a successful reproducer, the review manager:

1. executes the test on original and patched states;
2. gives issue, test, patch, and both executions to a reviewer;
3. asks separately whether the test is correct and whether the patch is correct;
4. feeds advice back to patch or test generation;
5. yields reviewer-approved patches for external regression evaluation.

The loop is explicit in [`review_manage.py` lines 78–139](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/api/review_manage.py#L78-L139). The reviewer’s JSON has six required semantic fields (`patch-correct`, `patch-analysis`, `patch-advice`, `test-correct`, `test-analysis`, `test-advice`) and allows up to five formatting retries ([`agent_reviewer.py` lines 59–111](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_reviewer.py#L59-L111), [`agent_reviewer.py` lines 155–200](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_reviewer.py#L155-L200)).

The outer workflow permits three overall attempts and can cycle across configured model names. After attempts, it gathers every extracted diff, favors regression-passing candidates, honors an approved final patch, or invokes a selector agent ([`inference.py` lines 98–139](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L98-L139), [`inference.py` lines 144–240](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L144-L240)). The selector itself performs root-cause and resolution analysis, samples three responses per call across three calls, then majority-votes a patch index ([`agent_select.py` lines 15–92](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_select.py#L15-L92)).

### Assessment

**Better than ours:** A repair-specific task has a bounded, mechanically enforced evidence loop rather than relying on the main agent to remember a testing rule. This directly addresses the owner harness’s general problem that rules can be forgotten (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md`, D2).

**Worse than ours:** the loop is rigid. It cannot represent a documentation task, architecture design, interactive clarification, browser work, release process, or a task whose correct next action is not one of its fixed stages. Search exhaustion silently degrades into patch generation. The proxy adds LLM calls merely to transform free form to JSON, which is especially unattractive given the owner corpus’s 22.9% `StructuredOutput` error rate and 294 repeated schema mismatches (`/local_disk0/codexwork/bundle/inputs/corpus.json`, `tool_usage` and `failures_by_tool.StructuredOutput`).

**Do not copy:** a second fixed orchestration runtime. Port the repair lane as a skill/workflow on the existing bus, invoked only for issue-repair tasks.

## 2. Context management

### What ACR does well

ACR retrieves code at method/class granularity rather than reading whole files by default. `SearchBackend` builds indexes from Python ASTs: class → ranges, class+method → ranges, top-level function → ranges, and a partial inheritance map ([`search_backend.py` lines 25–72](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_backend.py#L25-L72), [`search_backend.py` lines 74–123](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_backend.py#L74-L123)). Searching a method yields the complete syntactic unit; code-string search returns small windows. When a method belongs to a class, bug-location expansion can also retrieve inherited implementations and whole-class context ([`search_backend.py` lines 713–757](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_backend.py#L713-L757), [`search_backend.py` lines 797–879](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_backend.py#L797-L879)).

The paper articulates the key design principle: class search returns signatures rather than full definitions, allowing the model to choose methods in the next iteration instead of truncating arbitrary text ([paper §4.2, lines 172–179](https://arxiv.org/html/2404.05427)). It also explains the tension that motivates stratification: one search is incomplete; all searches at once create distracting or over-limit context; iterative structure-aware retrieval navigates between those extremes ([paper §4.3, lines 182–188](https://arxiv.org/html/2404.05427)).

The patch stage gets a deliberately lossy handoff when localization succeeds: a list of `BugLocation` objects containing exact code plus intended behavior, not the entire discovery transcript ([`agent_write_patch.py` lines 206–236](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_write_patch.py#L206-L236)). This is a strong separation of discovery from editing and resembles the owner’s structured-handoff rule at `/local_disk0/codexwork/bundle/claude/AGENTS.md:59-63`.

### What ACR does poorly

`MessageThread` is an append-only list passed wholesale to the model; `to_msg()` returns every message without token accounting, pruning, summarization, or compaction ([`data_structures.py` lines 67–137](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/data_structures.py#L67-L137)). The only clear runtime truncation is reproducer stderr: first 50 plus last 50 lines after a 100-line threshold ([`task.py` lines 447–453](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L447-L453)). The README explicitly warns that some Groq models can exceed context limits even on simple issues ([README lines 326 onward](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L326)).

There is no context-budget controller, message priority, compact/resume strategy, or relevance eviction. Whole-file retrieval exists and can return an entire file ([`search_backend.py` lines 655–683](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_backend.py#L655-L683)). The public implementation is Python-specific: `_build_python_index` enumerates and parses Python files, so its headline AST mechanism does not generalize across the owner’s languages without another parser layer.

**Compared with ours:** our durable basic-memory plus event ledger survives compaction (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13`; `/local_disk0/codexwork/bundle/claude/AGENTS.md:85-91`), and native Claude/Codex context handling is broader. ACR’s advantage is precision of *code retrieval*, not general context lifecycle.

## 3. Memory

ACR has three kinds of ephemeral run state:

1. in-memory `MessageThread` conversation lists;
2. in-memory patch/test maps and feedback histories held by `PatchAgent`, `TestAgent`, and `ReviewManager`;
3. serialized run artifacts such as search rounds, proxy conversations, patch conversations, reviews, regression JSON, tool-call layers, costs, and the selected patch.

`MessageThread` can save/load JSON ([`data_structures.py` lines 131–160](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/data_structures.py#L131-L160)), and search state is saved before each round ([`search_manage.py` lines 67–80](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L67-L80)). This is excellent experimental provenance, but it is not autonomous memory: the main workflow contains no resume-from-artifact path, semantic recall, cross-task learning, owner preference memory, or mechanism to turn prior failures into future constraints.

The owner harness is decisively stronger. It separates semantic memory (`basic-memory`) from objective event history and replays the latter on resume (`/local_disk0/codexwork/bundle/claude/AGENTS.md:28-34,85-91`). The shared lifecycle harness also has sanitized checkpoints and bounded local lexical recall (`/local_disk0/codexwork/bundle/agents/harness/README.md:17-29`). Corpus evidence shows actual use: `basic-memory` 1,332 server uses, including 408 writes, 357 searches, and 353 reads.

**Do not copy:** ACR has no memory capability we lack. Its one useful property—saving every phase artifact in machine-readable form—is already conceptually covered by our ledger/artifacts, though our pinned defect D3 says hook telemetry itself is currently unmeasurable. ACR’s phase artifact discipline is a useful benchmark for that separate telemetry fix, not a replacement memory architecture.

## 4. Tool and MCP handling

### ACR mechanism

ACR has no MCP client/server integration. Its “APIs” are Python methods on one local `SearchBackend`. Tools are declared in prompt prose, extracted by a proxy model, parsed with Python `ast`, reflected with `getattr`, checked against function signatures, and invoked in process ([`search_manage.py` lines 71–95](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L71-L95), [`search_manage.py` lines 162–183](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L162-L183)). `catch_all_and_log` converts backend exceptions into a failed `(output, summary, False)` tuple ([`utils.py` lines 339–351](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/utils.py#L339-L351)). Each retrieval layer logs tool name, arguments, and `call_ok` ([`search_manage.py` lines 198–215](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L198-L215)).

Tests, installs, git, and Docker are not LLM-callable tools. They are deterministic workflow code. This sharply limits the model’s action space during retrieval and patch generation.

### Relative assessment

**Better than ours:** phase-specific least capability. The retrieval model cannot edit or execute arbitrary shell; the patch model cannot browse or run shell. Deterministic code owns application and test execution. This reduces accidental action surface and avoids the owner corpus’s high-error tools (Glob 13.3%, PowerShell 10.6%, Bash 6.0%).

**Worse than ours:** no dynamic discovery, no MCP, no external research, no browser, no database, no language-server abstraction, no user tools, no health checks, no liveness/fallback routing, and no capability lifecycle. The owner has 93 MCP servers observed and a shared adapter/dispatcher contract (`/local_disk0/codexwork/bundle/agents/harness/README.md:1-29`). ACR cannot respond to a dead server because it has no servers; that simplicity is not transferable to the owner’s broad workload.

**Important caveat:** ACR’s proxy is an avoidable structured-output fan-out. The owner’s measured `StructuredOutput` failure rate makes copying this interface inappropriate. Native function calls or a single permissive schema with deterministic validation would be safer.

## 5. Permission and safety model

### What exists

The model is implicitly constrained by workflow phase: search is read-only; patch generation emits text; actual patch application, test execution, installs, git reset/clean, and Docker validation are host code. The README recommends Docker for running ACR ([README lines 106–131](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L106-L131)). Reproducer execution has a 120-second timeout, and general test execution defaults to 300 seconds ([`task.py` lines 420–453](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L420-L453), [`config.py` lines 39–40](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/config.py#L39-L40)).

### What is missing or dangerous

There is no user approval system, allow/deny/ask policy, filesystem scope policy, network policy, secret boundary, command-risk classification, hookable permission event, or per-action audit decision. Docker is recommended, not enforced, and local mode explicitly operates on a supplied local repository ([README lines 174–188](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L174-L188)).

Most importantly, `PlainTask.setup_project()` and `reset_project()` call `repo_reset_and_clean_checkout()` ([`task.py` lines 501–527](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L501-L527)). That helper executes `git reset --hard <commit>`, `git clean -fd`, checkout, and submodule deinit/update; it also deletes coverage files first ([`utils.py` lines 125–172](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/utils.py#L125-L172)). `Task.apply_patch()` cleans the repository in `finally`, again using hard reset and `git clean -fd` ([`task.py` lines 76–98](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L76-L98)). A local user with uncommitted or untracked work can lose it without an interactive approval boundary.

The issue statement and retrieved repository content are interpolated directly into model messages. There is no explicit instruction that fetched/repository content is untrusted data. The owner’s contract has precisely that boundary and warns that cloned repos can auto-load agent configuration (`/local_disk0/codexwork/bundle/claude/AGENTS.md:93-106`).

**Compared with ours:** the owner config has explicit allowed/denied tool classes and credential-read denials (`/local_disk0/codexwork/bundle/claude/settings.json:26-76`), plus PreToolUse/PermissionRequest hooks (`settings.json:139-149,284-295`) and “block only dangerous” semantics (`AGENTS.md:64-70`). The owner’s hooks have confirmed false-positive defects, but a defective permission layer is still a layer that can be repaired; ACR has no equivalent control surface.

**Do not copy:** direct operation on a user checkout. Any ACR-inspired lane must use native isolated worktrees/ephemeral clones and preserve the owner’s existing approval and hook path.

## 6. Customisation surface: rules, skills, hooks equivalents

ACR’s supported customization is operational rather than compositional:

- CLI/config fields select model(s), temperature, conversation limit, tasks, validation/SBFL flags, output paths, and process count ([`conf/example.conf` lines 1–15](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/conf/example.conf#L1-L15); [`EXPERIMENT.md` lines 89–103](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/EXPERIMENT.md#L89-L103)).
- Provider adapters support several named OpenAI, Claude, Bedrock, Gemini, Groq, Ollama, Azure, and LiteLLM models; the README’s update history records those additions ([README lines 28–35](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L28-L35)).
- Extending roles, prompts, stages, tools, languages, or validation requires editing Python source.

There are no repository-level instruction files, path-scoped rules, installable skills, prompt commands, lifecycle hooks, plugin manifests, MCP registration, or user-defined agents. There is also no declarative way to bind a different tool subset to a custom phase; phase scope is hard-coded.

This is much worse than the owner’s surface: agents, skills, commands, rules, shared native hook dispatch, MCP servers, settings, and provider-neutral adapters are all present in the supplied bundle. The owner’s challenge is curation/reliability (78 of roughly 355 skills invoked, dead MCP calls, orphan inflation), not lack of extensibility.

**Do not copy:** hard-code more prompts and roles into another runtime. Implement an ACR-inspired feature as one narrowly routed skill plus, at most, small hook/MCP helpers.

## 7. Multi-agent support

ACR uses multiple *roles*, sequentially:

- context retrieval agent;
- proxy/formatter agent;
- reproducer agent;
- patch agent;
- reviewer agent;
- candidate selector agent.

They do not run as a communicating team. They share state through orchestrator-owned data structures and files. The context agent’s prompt literally says the collected context will be sent to a colleague ([`agent_search.py` lines 16–22](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_search.py#L16-L22)), but there is no mailbox, delegation, shared task board, agent lifecycle API, worktree ownership, mid-turn steering, or asynchronous result collection.

ACR can run independent SWE-bench tasks in parallel processes. The documentation warns against separately launching multiple experiment scripts because task instances can share a codebase and instead exposes `num_processes` inside one script ([`EXPERIMENT.md` lines 78–86](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/EXPERIMENT.md#L78-L86)). That is batch parallelism, not within-task multi-agent collaboration.

The owner is much stronger: native Task/Workflow/Agent tools are observed in the corpus; `CLAUDE.md` documents native MCP fan-out and live peer dialogue (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:15-77`); the settings enable experimental Agent Teams (`settings.json:5-8`). The pinned audit finding C19 shows monitoring/recovery defects, so the owner’s multi-agent system is not fully reliable, but ACR offers no remedy—the competitor has no long-lived children to monitor.

One idea worth preserving is **role-separated epistemics**: the patch author and reviewer are different calls with different prompts, and the reviewer judges the test as well as the patch. That separation can be implemented with our native subagent bus and does not require ACR’s runtime.

## 8. Verification and self-check mechanisms

ACR has an unusually dense repair-specific verification stack:

1. **Invocation validation:** proxy output must be JSON; tools must exist; arguments must parse and match arity ([`agent_proxy.py` lines 90–131](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_proxy.py#L90-L131)).
2. **Bug-location grounding:** model locations are resolved back to actual AST/file snippets; imprecise locations cause another search round ([`search_manage.py` lines 112–157](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/search/search_manage.py#L112-L157)).
3. **Patch applicability:** exact original snippets must match and the patch must convert/apply before registration ([`agent_write_patch.py` lines 191–204](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_write_patch.py#L191-L204)).
4. **Generated reproducer:** ACR asks for a standalone Python test only when the issue contains reproduction steps, executes it, and treats a nonzero result containing `AssertionError` as reproduction ([`data_structures.py` lines 163–187](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/data_structures.py#L163-L187)).
5. **Independent joint review:** a reviewer sees original/patched executions and judges both test validity and patch correctness ([`agent_reviewer.py` lines 125–200](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/agents/agent_reviewer.py#L125-L200)).
6. **Regression delta:** validation runs pre-existing tests on no-op and candidate patch, then rejects only additional failures ([`task.py` lines 223–254](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L223-L254)).
7. **Execution-guided localization:** optional SBFL ranks suspicious methods using passing/failing coverage and feeds at most five into retrieval ([`manage.py` lines 36–105](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/manage.py#L36-L105); paper §4.4 [lines 191–197](https://arxiv.org/html/2404.05427)).
8. **Bounded retries and candidate selection:** three overall attempts, per-phase retry caps, regression filtering, reviewer approval, and a selector vote ([`inference.py` lines 28–95](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L28-L95), [`inference.py` lines 144–240](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L144-L240)).

### Weaknesses in those checks

- The reproducer predicate is brittle: any nonzero run with `AssertionError` is “reproduced,” without proving correspondence to the issue. The LLM reviewer mitigates but does not eliminate this.
- Reviewer and producer generally use the currently selected model; independence is prompt/role separation, not model-family or evidence independence.
- Regression validation only checks *additional* pre-existing failures in the shown Docker path. A patch can pass that check without fixing the issue unless the reproducer/reviewer path is sound.
- `enable_validation` and `enable_sbfl` default false; `reproduce_and_review` also defaults false ([`config.py` lines 14–18,36–40](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/config.py#L14-L40)). The richer loop is not guaranteed for ordinary invocation.
- Plain/local tasks cannot validate at all: `PlainTask.validate` raises `NotImplementedError` ([`task.py` lines 501–527](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/task.py#L501-L527)).
- Candidate selection catches selector exceptions and can fall back to the last candidate (`index = -1`), including when none pass regression ([`inference.py` lines 188–225](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/app/inference.py#L188-L225)).
- The paper’s failure taxonomy found that even after choosing all correct method-level locations, 29.3% of tasks still had a wrong patch; another 20.0% used the right file but wrong methods, 18.0% the wrong files, and 6.7% no applicable patch ([paper §6.3, lines 291–317](https://arxiv.org/html/2404.05427)). Those historical numbers are not current leaderboard claims; they explain failure modes.

**Compared with ours:** our agent-as-judge, verification skills, testing agents, and generator-critic rule provide analogous components, but ACR composes them mechanically for repair. Our checks cover far more task types and richer security boundaries. The right synthesis is ACR’s repair-lane composition on our existing bus.

## Capabilities to port (only genuine gaps)

### 1. CONFIG — Enable and route structure-aware code retrieval (UNVERIFIED equivalence of existing server)

**Capability gap:** ACR gives the model class/method/inheritance-aware retrieval and complete syntactic units. Owner-side probes found no first-class equivalent, but an enabled generic code-navigation MCP may expose comparable tools under different names. **UNVERIFIED equivalence; settle by inventorying the live Serena/code-navigation MCP schemas and running a benchmark that asks for a class signature, method body, inherited implementation, and code-around-line in Python, TypeScript, C#, Java, and Dart.**

**Port mechanism:** do not build an AST daemon first. Configure a narrowly curated code-navigation server already on the MCP bus (the owner settings permit `mcp__plugin_serena_serena` at `/local_disk0/codexwork/bundle/claude/settings.json:51`) and add one repair/repository-navigation skill that:

1. starts with issue identifiers and failing-test symbols;
2. requests a class outline/signature rather than whole-file content;
3. follows method definitions, references, implementations, and inheritance one stratum at a time;
4. admits at most N complete code entities per round;
5. emits `[{path, symbol, range, exact_code_hash, intended_behavior, evidence_source}]`;
6. falls back to `rg`/native reads when the language server is absent or stale.

Keep schemas shallow: one permissive list of locations, optional fields, and deterministic post-validation. This avoids reproducing ACR’s proxy agent and our 22.9% structured-output failure mode.

**Expected value:** **very likely (80-90%)** to reduce irrelevant whole-file reads and improve localization on symbol-rich issues; evidence is ACR’s mechanism, the paper’s rationale, and the owner corpus’s 384 oversized-token Read failures. It is **roughly even (45-55%)** to improve end-to-end fix rate across the owner’s heterogeneous workload without a pilot; evidence is ACR’s Python/benchmark specialization and the unknown live server quality.

**Anti-overfit gate:** passes. It is configuration plus a skill on existing MCP/native tool buses; no vector database, knowledge graph, or second runtime.

### 2. BUILD-SMALL — Add execution-guided suspicious-method ranking

**Capability gap:** no first-class SBFL capability was found by two static signals plus the corpus capability signal.

**Port mechanism:** a language/test-adapter helper under roughly 200 lines for the first Python pilot:

1. run a known failing test and a bounded sample of passing tests with coverage contexts;
2. map per-test executed lines to enclosing symbols using the existing code-navigation service or Python `ast`;
3. compute one transparent Ochiai score per symbol;
4. return only the top five `{path, symbol, score, failing_hits, passing_hits}`;
5. inject the result as *hints* into the retrieval skill, never as an edit command;
6. record the command, test selection, coverage hashes, and baseline/failing outcome in the event/artifact ledger;
7. skip cleanly when there is no reproducible failing test or coverage support.

Do not port ACR’s broad coverage setup code wholesale. Begin with pytest/coverage.py, which already exists in typical Python test stacks, and add other language adapters only after measured wins.

**Expected value:** **likely (55-80%)** to improve localization on reproducible Python bugs with mixed passing/failing tests. Evidence: ACR uses method-level SBFL only as a cross-referenced hint ([paper lines 191–197](https://arxiv.org/html/2404.05427)) and reports cases where it revealed relevant methods absent from issue text ([paper lines 289–290](https://arxiv.org/html/2404.05427)). General value is lower because SBFL quality depends on test quality, explicitly acknowledged by the paper.

**Anti-overfit gate:** passes. Small helper on the skill/hook bus; no durable execution engine or learned critic.

### 3. BUILD-SMALL — Add a mechanically enforced repair-verification lane

**Capability gap:** our pieces exist, but the fixed composition is **very likely (80-90%)** absent. Evidence: the validated static composition search and the independent corpus capability-key search described under “Owner-side lack detector validation”; a live task trace is the settling experiment.

**Port mechanism:** one `repair-evidence-loop` skill/workflow using native agents and worktrees:

1. create an isolated worktree and record its baseline commit/status;
2. generate or extract the smallest reproducer, but first run it on the baseline and require an issue-specific oracle, not merely `AssertionError`;
3. localize with normal structure search; add SBFL hints only when its preconditions hold;
4. have an implementer produce a patch in the worktree;
5. run the exact reproducer on baseline and patch, then targeted tests and a bounded regression suite;
6. dispatch a fresh-context reviewer with only the issue, diff, test source, baseline/patched terminal outputs, and location evidence;
7. require separate verdicts for oracle validity, patch causality, regression evidence, and scope minimality;
8. feed concrete failed evidence back for at most two repair retries, respecting the existing two-strikes rule;
9. return a patch plus evidence manifest, or an explicit non-completion.

Use optional, shallow review fields. Never require ACR’s six-field schema on every branch; the owner’s schema mismatch data argues against it.

**Expected value:** **very likely (80-90%)** to reduce false completion on repair-shaped tasks. Evidence: deterministic baseline/patched execution is mechanically stronger than prose-only completion, and the owner already has all component buses. End-to-end throughput impact is **likely (55-80%)** positive because extra calls/tests add cost but are bounded and task-routed.

**Anti-overfit gate:** passes. This is a skill/workflow over native subagents, worktrees, tests, and event artifacts—not a second orchestrator.

### 4. NATIVE — Use native fan-out for candidate diversity and fresh selection

**Capability gap:** ACR produces multiple overall attempts and selects candidates; the owner has native parallel agents but does not mechanically require candidate diversity in the proposed repair lane.

**Port mechanism:** for high-value or still-ambiguous repairs after localization, dispatch two isolated implementers with the same evidence but no access to each other’s reasoning. Validate both identically. If more than one passes, use a fresh reviewer to select by issue coverage, regression evidence, diff scope, and maintainability. If none passes, do not select “last candidate” as ACR can; return failure evidence.

**Expected value:** **likely (55-80%)** to improve robustness on ambiguous repairs, because independence creates real alternative hypotheses and the owner already supports fan-out. It is **unlikely (20-45%)** to be cost-effective for routine one-line fixes; route it only when confidence is low or the first validated attempt fails.

**Anti-overfit gate:** passes. Native agent/worktree support only.

## What not to port

1. **No full ACR replacement.** It would discard general tools, MCP, rules, skills, hooks, durable memory, interactive permissions, and cross-domain work to gain a Python repair pipeline.
2. **No second orchestration runtime.** ACR’s stages map onto one existing skill/workflow. A separate daemon would violate the anti-overfit gate and duplicate lifecycle/monitoring responsibilities already defective in C19.
3. **No proxy LLM for JSON cleanup.** Use native tool calls or permissive parsing plus deterministic validation. The owner has direct evidence that strict structured fan-out is unreliable.
4. **No direct hard reset/clean of a user checkout.** Always isolate in a worktree/clone and preserve existing permission hooks.
5. **No Python-only AST service as a universal foundation.** Start with existing language-server/code-navigation buses; prove value per language.
6. **No “AssertionError means reproduced” oracle.** Require a task-specific assertion and baseline/patched contrast.
7. **No reviewer approval as proof by itself.** Reviewer output is advisory evidence alongside terminal results, not a completion certificate.
8. **No fallback to an unvalidated last patch.** If no candidate meets the evidence contract, return failure.
9. **No whole conversation as unbounded memory.** Preserve structured location/evidence records and let native context management handle the rest.
10. **No claim that batch multiprocessing is multi-agent collaboration.** It is useful throughput machinery for independent tasks, nothing more.

## Proposed pilot and falsification plan

### Phase A — retrieval-only benchmark

Select 20 completed owner repair tasks: five Python, five TypeScript/JavaScript, five C#/Java, five Dart or other. For each, replay localization from issue text without revealing the final diff. Compare current tool use against structure-aware retrieval on:

- top-1 and top-5 changed-symbol recall;
- tokens/read bytes before first correct location;
- number of failed search/read calls;
- wall time;
- contamination by irrelevant files.

Promotion gate: retain the route only if changed-symbol recall improves without materially increasing wall time or tool failures. **UNVERIFIED threshold values; the settling experiment is the replay itself. Fix thresholds before looking at results.**

### Phase B — SBFL ablation

Use only tasks with a reproducible failing test and at least five passing tests. Run retrieval with and without top-five Ochiai hints, holding model/prompt fixed. Measure correct-symbol recall, wrong-location rate, and time. Reject SBFL if it merely overweights test infrastructure or produces no localization lift.

### Phase C — repair-evidence loop

On 20 new repair tasks, compare normal workflow versus the composed lane. Primary metrics:

- baseline reproducer validity;
- patch fixes reproducer;
- no new targeted/regression failures;
- fresh reviewer agreement;
- owner correction within the next session;
- tool error count and total cost.

Include negative controls: misleading reproducer, flaky test, incorrect issue hint, multi-file fix, and feature request with no failing baseline. The lane must abstain or downgrade confidence instead of forcing a patch.

### Phase D — safety regression

Verify the lane never runs `reset --hard`/`clean -fd` on the shared checkout, never reads denied credentials, preserves existing untracked files, emits permission events through the native bus, and treats issue/repository text as untrusted data. Run the nine recorded prose-scanner false positives from the pinned defects as a separate harness regression; do not let the new lane worsen D1.

## Research dead ends and limitations

- The supplied bundle contains only audit finding `C19.md`, not all 140 Windows audit artifacts described in the brief. I did not invent unavailable findings. This teardown uses C19 only for the established warning that a new runtime would worsen live-agent monitoring complexity.
- `corpus.json.hooks` was not used as evidence because the brief explicitly marks that detector broken. Hook claims come from static wiring and the known-defects file, not the corpus hook section.
- GitHub REST API calls hit an unauthenticated shared-IP rate limit during research. Release dates were therefore obtained from local signed/ref metadata and public commit pages rather than REST release JSON. Tags visible locally are `v1.0.0`, `v1.1.0`, and `v2.0.0`; no release-body claim is made.
- `pdfinfo`/`pdftotext` were unavailable on the job node. The official arXiv HTML and repository source supplied the paper evidence.
- No ACR task was executed. Running it would require dependencies, model credentials, and writes to a target repository, beyond this read-only research unit. Source-level control flow and published evaluation are distinguished from live behavior throughout.
- **UNVERIFIED whether the current owner’s permitted Serena MCP is installed, live, or exposes the required multi-language symbol operations; settle with a live tool-schema inventory and the Phase A benchmark.** This is why proposal 1 is headed `UNVERIFIED` and classified CONFIG rather than claiming an already working solution.
- **UNVERIFIED whether a private/commercial post-2025 ACR includes MCP, permissions, hooks, durable memory, or new multi-agent mechanisms; settle with authorized current product docs/build.** None of the negative public-implementation findings should be projected onto an unseen private system.
- Benchmark efficacy numbers in the README/paper are historical and version/model/environment-specific. The README reports 46.20% on SWE-bench Verified for `v20240620` ([README lines 28–32](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/585d3e639aeda58ef0b6a151dd1cc2721a94d267/README.md#L28-L32)); this teardown does not treat that as a 2026 frontier comparison.

## Final recommendation

Do not replace the owner harness with AutoCodeRover. Build a narrow, evidence-heavy **repair lane** inside the existing harness:

1. CONFIG pilot of existing structure-aware navigation;
2. BUILD-SMALL Python SBFL hint generator;
3. BUILD-SMALL repair evidence loop using native worktrees, tests, reviewer, and ledger;
4. NATIVE candidate fan-out only for ambiguous/high-value cases.

This is **very likely (80-90%)** to capture nearly all of ACR’s transferable value with far less risk, because each proposal maps to an existing bus and the discarded parts are precisely where ACR is weaker: extensibility, safety, memory, and generality. The residual uncertainty is concentrated in whether the existing code-navigation MCP is good enough and whether SBFL improves the owner’s real task mix; the proposed ablations settle both before broad rollout.
