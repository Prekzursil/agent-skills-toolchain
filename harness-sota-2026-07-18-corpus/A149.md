# A149 — coherence audit: `settings.json` versus the behavior contract

## Verdict

I found **three direct contradictions** in the supplied Claude-side runtime configuration:

1. Native permission mode is configured to bypass prompts and safety checks while the contract requires explicit user authorization for two shell actions.
2. The configured reverse-engineering auto-launch hook denies ordinary, retryable tool calls while the contract says non-dangerous guidance must inject context and must not block.
3. The configured `WorktreeCreate` replacement deliberately exits nonzero on ordinary hook errors while the contract says any hook error exits 0 (fail-open).

These are not merely different degrees of strictness. In each case the settings-selected runtime path performs the opposite control action from the contract in the same concrete situation. The first has split runtime behavior (native permission bypass wins unless a separate hook preempts it); the second is won by the hook's JSON `deny`; the third is won by `WorktreeCreate`'s special nonzero-exit semantics.

I found no other proven direct contradiction after reading all 964 relevant lines (`settings.json` 703, Claude `CLAUDE.md` 121, Claude `AGENTS.md` 140). In particular, broad capability enablement is not itself an instruction to use a capability, and a timeout ceiling is not itself an instruction to block for that long.

## Finding 1 — blanket permission bypass contradicts explicit-authorization rules

### Both texts, verbatim

Settings:

> `"ask": [],`
>
> `"defaultMode": "bypassPermissions",`

— `/local_disk0/codexwork/bundle/claude/settings.json:70-71`

The setting also broadly permits shell execution:

> `"Bash",`

— `/local_disk0/codexwork/bundle/claude/settings.json:35`

and suppresses the dangerous-mode warning:

> `"skipDangerousModePermissionPrompt": true,`

— `/local_disk0/codexwork/bundle/claude/settings.json:693`

Contract:

> `- Never \`--no-verify\` on commits without explicit user instruction.`
>
> `- Never \`git push --force\` to main/master without explicit user approval.`

— `/local_disk0/codexwork/bundle/claude/AGENTS.md:96-97`

The contract also ranks the user's explicit instruction and permission system first (`AGENTS.md:115-123`), so this is not a case where permission semantics can be ignored as irrelevant implementation detail.

### Concrete collision

The collision occurs if Claude emits `git commit --no-verify` without the user having instructed that exception, or emits `git push --force ... main` without explicit approval. The contract says the action must not occur. The native settings say not to ask and to execute tool calls immediately. This is a same-situation allow/not-allow contradiction, not merely “the tool exists.”

### Which wins at runtime

There are two runtime stages:

* **Model/action selection:** the loaded prose contract can prevent Claude from proposing the call. That is behavioral guidance, not a native permission decision (`AGENTS.md:93-102`).
* **Tool authorization:** if such a call reaches the Bash tool, `bypassPermissions` wins at the native permission layer; official semantics say it disables prompts and safety checks and executes immediately. The empty `ask` list provides no declarative exception (`settings.json:64-71`; [permission modes](https://code.claude.com/docs/en/permission-modes)).

For force-push specifically, a separately configured PreToolUse tripwire usually wins over bypass: settings wires it on every Bash call (`settings.json:151-160`), its predicate matches `git push ... --force|-f` (`hooks/no-force-push/tripwire.py:15-18,39-47`), and its entry point returns exit 2 (`hooks/no-force-push/hook.py:45-59`). The shipped self-test independently records that the positive case halts and the override allows (`hooks/no-force-push/SELFTEST-RESULT.txt:1-9`). Thus the effective force-push path is **contract-compatible because of the hook, despite contradictory native permission mode**.

For `--no-verify`, a `block-no-verify` hook text exists at `claude/hooks/hooks.json:4-13`, but that file is not referenced by the 38 user-settings hook groups, while the relevant `ecc@everything-claude-code` plugin is explicitly false at `settings.json:608`. The settings detector was validated on the known-present `no-force-push` command (`settings.json:151-160`) before this negative comparison. A second, mechanically different signal was a complete source read of the shared `SecretGuardModule`: its Git predicates cover reset/clean/push/restore/checkout/branch/stash and destructive filesystem/registry operations but contain no commit/`--no-verify` predicate (`agents/harness/modules.py:606-723,764-798`); its default assembly is at `modules.py:2588-2613`. An exact recursive string search independently found `--no-verify` only in the unwired `claude/hooks/hooks.json`, its backup, and explanatory test-tamper prose. Thus the supplied user-settings plus shared-dispatcher paths do not mechanically gate `--no-verify`. **UNVERIFIED** whether an exact loaded plugin version adds a separate gate; the settling experiment is `claude --debug hooks` with a non-executing synthetic payload in a disposable repository. I therefore do not claim every possible plugin-composed path is unguarded; I do claim the native permission layer contradicts the prose requirement.

### Minimal resolution — UNVERIFIED targeted permission rule

**NATIVE (Claude Code already does this; we just enable it).** Change `permissions.defaultMode` from `bypassPermissions` to `auto`, and add targeted `permissions.ask` entries for the force-push and `--no-verify` Bash forms. `ask` is evaluated before `allow`, so targeted rules can override the broad `"Bash"` allow under normal permission modes ([Claude Code configuration, permission rules](https://code.claude.com/docs/en/configuration#permission-settings)). Keep the force-push hook as defense in depth until the rule is proven.

The exact Bash-rule strings are **UNVERIFIED** because Claude's Bash specifier matching is command-prefix-oriented and multiple flag positions/aliases must be covered; the settling experiment is a disposable Windows repository with a fake `git` executable that logs argv, testing `commit --no-verify`, `commit -n`, `push --force`, `push -f`, `push --force-with-lease`, flags before/after the remote/ref, and benign controls under `claude --permission-mode auto`. It is **very likely (80-90%)** that native `auto` plus validated ask rules eliminates this contradiction, because official settings precedence is ask-before-allow and the current installed-host audit independently recorded that `auto` exists with classifier rules (`inputs/audit-findings/D23.md:1-14`); the remaining uncertainty is pattern coverage, not mode semantics.

Changing only `defaultMode` is not sufficient evidence of explicit approval because `"Bash"` remains broadly allowed at `settings.json:35`. Changing only `ask` while leaving bypass active is also not sufficient because bypass mode disables ordinary prompting. Those tempting one-line edits were rejected.

Anti-overfit gate: this uses Claude's native permission bus and existing hook. It adds no orchestration runtime, memory store, durable-execution system, critic, SaaS, or guardrail framework.

## Finding 2 — RE auto-launch blocks an ordinary retryable condition

### Both texts, verbatim

Settings selects the auto-launch hook for all configured reverse-engineering MCP calls:

> `"matcher": "mcp__ida-pro-mcp__.*|mcp__ghidra-mcp__.*|mcp__binary-ninja-mcp__.*",`
>
> `"command": "python \"C:/Users/Prekzursil/.claude/hooks/re-autolaunch/autolaunch.py\" pretool",`

— `/local_disk0/codexwork/bundle/claude/settings.json:196-201`

Contract:

> `- **Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code,`
>
> `  force-push to main without explicit approval.`
>
> `- **Exit 0 + additionalContext (inject):** all other guidance (routing, reminders, goal`
>
> `  injection). Never block on ambiguity; inject a clarifying route instead.`

— `/local_disk0/codexwork/bundle/claude/AGENTS.md:66-70`

The effective settings-selected backend configuration is also explicit:

> `"deny_while_starting": true,`
>
> `"deny_when_unlaunchable": true,`

— `/local_disk0/codexwork/bundle/claude/hooks/re-autolaunch/backends.json:12-13`

### Concrete collision

When Claude calls IDA, Ghidra, or Binary Ninja while its local backend is still starting, cannot be launched, is below the RAM threshold, or requires a manual GUI start, the condition is retryable/environmental—not irreversible or dangerous. The contract requires an exit-0 context injection. The configured hook instead emits `permissionDecision: "deny"` (`autolaunch.py:397-412`) on those branches (`autolaunch.py:465-539`). For the common cold-start branch it says “retry this call shortly” while denying it (`autolaunch.py:488-496`); for an already-starting backend it again denies and says retry (`autolaunch.py:499-514`). This is the exact same situation and opposite control action.

This is not hypothetical dead code. The two controlling booleans default true in the supplied live backend config (`backends.json:12-13`), the settings matcher invokes the script on the three MCP namespaces (`settings.json:196-203`), and the hook state machine reaches these decisions whenever the port probes are down (`autolaunch.py:441-457`). An earlier independent audit traced the same live state machine and recorded the deny/retry path at `inputs/audit-findings/C17.md:47-53`; that audit remains a claim, but agrees with the primary implementation.

### Which wins at runtime

The **hook wins**. It exits 0 with structured JSON containing `permissionDecision: "deny"` (`autolaunch.py:397-408,645-674`). Official Claude Code semantics say JSON deny prevents the call, and among multiple PreToolUse results the precedence is `deny > defer > ask > allow` ([Claude Code hooks](https://code.claude.com/docs/en/hooks#pretooluse-decision-control)). Thus neither broad MCP allow entries (`settings.json:47-60`) nor `bypassPermissions` can rescue the call. The contract's instruction to inject is not the runtime winner.

### Minimal resolution

**CONFIG (settings/JSON only).** Set these two existing fields in `hooks/re-autolaunch/backends.json`:

```json
"deny_while_starting": false,
"deny_when_unlaunchable": false
```

No Python change is needed. `_disposition()` already selects `emit_context` when its boolean is false (`autolaunch.py:397-412`), and every affected branch already passes one of those booleans (`autolaunch.py:481-539`). It is **almost certain (90-99%)** this minimal edit converts these non-dangerous denies into exit-0 `additionalContext`, because the complete branch selection is visible in source and the only residual uncertainty is host/plugin version parity. Settle that residual with table-driven synthetic PreToolUse payloads against a temporary copied config for states `up`, `launch`, `wait`, `lowram`, and `manual`, asserting no `permissionDecision` key while preserving the guidance text.

This may allow the underlying MCP call to fail once while a backend is unavailable; that is the intended cost of contract coherence. The hook still launches/probes and gives a concrete retry route, while normal tool failure supplies terminal evidence. If avoiding that first failure is desired later, Claude's native `defer` could be evaluated, but it is not the minimal fix and has batch-call constraints documented in the official hook reference.

Anti-overfit gate: this is a two-value change on the existing hook bus. It introduces none of the rejected components.

## Finding 3 — `WorktreeCreate` is intentionally fail-closed on hook error

### Both texts, verbatim

Settings:

> `"WorktreeCreate": [`
>
> `  {`
>
> `    "hooks": [`
>
> `      {`
>
> `        "type": "command",`
>
> `        "command": "powershell -NoProfile -ExecutionPolicy Bypass -File \"C:/Users/Prekzursil/.claude/hooks/create-worktree.ps1\"",`
>
> `        "timeout": 60,`

— `/local_disk0/codexwork/bundle/claude/settings.json:506-513`

Contract:

> `- All hook code wrapped in try/except; any hook error exits 0 (fail-open).`

— `/local_disk0/codexwork/bundle/claude/AGENTS.md:70`

The selected script states the opposite behavior verbatim:

> `# stdout (on exit 0): absolute path of the created worktree. Non-zero exit aborts creation.`

— `/local_disk0/codexwork/bundle/claude/hooks/create-worktree.ps1:3`

and implements it:

> `catch {`
>
> `    [Console]::Error.WriteLine("WorktreeCreate hook error: $_")`
>
> `    exit 1`
>
> `}`

— `/local_disk0/codexwork/bundle/claude/hooks/create-worktree.ps1:157-160`

### Concrete collision

Malformed JSON, no candidate Git repository, or a failed `git worktree add` are ordinary hook/runtime errors. The contract says they exit 0 and fail open. The script exits 1 for each (`create-worktree.ps1:114-160`). This collision has an executed independent signal: the earlier hook audit fed malformed JSON and recorded `WorktreeCreate malformed JSON -> rc=1`, while the paired `WorktreeRemove` returned 0 (`inputs/audit-findings/A08.md:40-46`). The implementation is the primary signal; the differently constructed process probe is the second.

### Which wins at runtime

The **settings-selected script wins and creation aborts**. Official semantics make `WorktreeCreate` the exception to ordinary hook nonzero handling: any nonzero status causes worktree creation to fail ([Claude Code hooks, exit codes](https://code.claude.com/docs/en/hooks#exit-code-output)). The script itself documents the same host contract at line 3 and reaches `exit 1` at lines 130, 149, and 157-160. Therefore the prose promise “any hook error exits 0” is false for this active event.

This is also a contract-design mismatch, not merely a missing catch: a successful custom `WorktreeCreate` hook must print a valid created directory, so blindly converting the catch to `exit 0` would produce no path and would not constitute a meaningful fail-open result. The official host replaces native creation entirely when this hook is configured ([WorktreeCreate](https://code.claude.com/docs/en/hooks#worktreecreate)).

### Minimal resolution

**NATIVE (Claude Code already does this; we just enable it).** Remove the `hooks.WorktreeCreate` group at `settings.json:506-517` and let Claude Code use its documented native `git worktree` default. Keep `WorktreeRemove` only if it is still needed; it already catches failures and exits 0 at `remove-worktree.ps1:1-28`.

It is **almost certain (90-99%)** that removing the replacement restores native worktree creation because the official documentation explicitly says native `git worktree` is the default and configuring this hook replaces it. The 1-10% residual covers this owner's nonstandard global launch wrapper and Windows-version behavior; settle it with `claude --worktree` in a disposable repository after removing the group from a temporary settings scope, then verify the returned directory and source ref.

Trade-off: removing the custom hook also removes its rules-vault junction/compile side effect (`create-worktree.ps1:9-17,42-112`). If that side effect remains required, the alternative is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**: move it to a post-create setup path that cannot replace native creation, or narrow `AGENTS.md:70` to say that decision/guidance hooks fail open while replacement lifecycle hooks may report an operation failure. The native removal is the minimal coherence edit; preserving the extra wiring requires a separate design decision and is not silently assumed here.

Anti-overfit gate: the preferred edit removes a custom replacement and uses native behavior. The fallback reuses the existing lifecycle bus and adds no second runtime.
