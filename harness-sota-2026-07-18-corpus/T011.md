# T011 — Competitive teardown: OpenAI Codex CLI

**Research date:** 2026-07-19 UTC  
**Subject:** OpenAI Codex CLI, with the owner’s cross-provider Claude/Codex harness as the comparison baseline  
**Current upstream checked:** official Codex manual refreshed 2026-07-19; official changelog through Codex CLI 0.144.6 (2026-07-18); open-source `openai/codex` main; unpacked owner snapshot and pinned corpus dated 2026-07-18  
**Write scope:** this artifact only. The unpacked subject tree was read-only. No subject configuration, install, repository, or external system was mutated.

## Executive verdict

Codex CLI is no longer merely a terminal prompt wrapped around shell and patch tools. It is an open-source, event-driven agent runtime with: a repeated model/tool continuation loop; automatic and manual context compaction; durable resumable/forkable rollouts; optional generated local memories; OS-enforced sandboxing plus a separate approval layer; lifecycle hooks with hash-based trust; hierarchical `AGENTS.md`; progressively disclosed skills; plugins; first-class MCP; typed noninteractive output; native subagent threads; and app-server/MCP-server embedding surfaces. The core turn source explicitly performs pre-sampling compaction, records model-visible context, runs prompt hooks, repeatedly samples, dispatches tool calls, records results, and resumes the loop until the response is terminal ([turn loop source](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs#L141-L365)). The tool orchestrator separately resolves approval, sandbox, network approval, execution, escalation, and retry ([tool orchestrator source](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/orchestrator.rs#L136-L505)).

For this owner, however, the competitive conclusion is **not “replace our harness with Codex.”** The unpacked Codex profile already enables `multi_agent`, memories, hooks, code mode, goals, plugins, and fan-out (`/local_disk0/codexwork/bundle/codex/config.toml:82-130`), while the cross-tool contract already supplies structured handoffs, an event ledger, semantic memory, terminal-state outputs, anti-grind, and safety rules (`/local_disk0/codexwork/bundle/codex/AGENTS.md:14-85`). The valuable frontier is to consume a small set of native Codex controls correctly and remove duplicated or unsafe scaffolding.

The recommended architecture is **very likely (80-90%)** to improve reliability without overfitting because it adds no second runtime and directly targets measured failures: native typed output addresses the 22.9% StructuredOutput failure surface (`corpus.json:103-108,8964-8993`); native MCP fail-closed and allowlists address continued calls to dead MCPs (`corpus.json:9141-9149`); strict config and Doctor address configuration drift; prompt inspection and hook receipts address unverifiable composition. The evidence is the official mechanisms plus the owner’s exact error distributions. The percentage is not a claim of measured uplift; that remains **UNVERIFIED — settle with an A/B replay of the top 100 schema failures, dead-MCP calls, and prompt-composition fixtures.**

Full replacement is **unlikely (20-45%)** to outperform an evolution centered on native Codex rails, because the owner already operates richer cross-provider memory, ledger, correction, long-run, and provider-neutral hook semantics than Codex supplies, and replacement would strand that evidence. This is supported by the cross-tool contract (`AGENTS.md:20-68`) and live defects which require semantic discriminators and independent controls, not a new orchestration engine (`INPUT-known-harness-defects.md:9-107,111-129`). This forward-looking conclusion is **UNVERIFIED — settle with the same 30 representative tasks run under (a) lean Codex-native-only and (b) native Codex plus the minimal shared dispatcher, scoring terminal success, intervention count, tokens, and false blocks.**

## Evidence discipline and boundaries

1. The pinned corpus is accepted as measured ground truth, not recomputed. Its own metadata says 11,633 files, 10.62 GB, zero file failures, one bad line, and that corpus absence is conditional (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). Its hook section explicitly says the detector is broken, so this teardown draws **no** negative hook-use conclusion from it (`corpus.json:13260-13264`).
2. Audit findings were treated as leads. A finding is used as a conclusion only where the unpacked snapshot, current official docs/source, or a second independent field supports it.
3. Windows live behavior could not be re-run on this Linux job node. Any statement requiring the Windows host is labeled **UNVERIFIED** inline and names a settling experiment.
4. “We lack” means a missing or incorrectly consumed mechanism in the owner’s end-to-end harness, not merely a missing flag. This matters because many Codex features are already enabled in the owner snapshot.
5. Every proposal below uses one owner-side port tag with its required value. No proposal adds a second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 1. Agent loop

### What Codex actually does

Codex’s local core is a stateful loop, not a one-shot code generator:

1. It builds a turn from session state and per-turn configuration.
2. Before sampling, it checks whether compaction is needed.
3. It records context updates and the exact model-visible state.
4. It runs input/lifecycle hooks and records injected context.
5. It constructs a step view of tools, MCP, skills/plugins, permissions, world state, and pending user steering.
6. It calls the model.
7. It converts function-call response items into routed tool calls.
8. It executes those calls through approval and sandbox orchestration, records results, and loops back into sampling.
9. It can compact mid-turn and continue.
10. It terminates when the model produces a final assistant result or the turn is aborted/fails.

The source signals are mechanically independent: `run_turn` contains the pre-sampling compact and outer continuation loop ([source](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs#L141-L365)); `ToolRouter::build_tool_call` parses response function calls and its dispatch methods route them ([source](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/router.rs#L99-L241)); and the orchestrator applies approval/sandbox/retry outside the sampling loop ([source](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/orchestrator.rs#L136-L505)).

Interactive CLI, IDE, desktop app, `codex exec`, app-server, and `codex mcp-server` are surfaces over this core rather than separately invented agents. `codex exec` is the headless automation lane, while app-server exposes threads, streamed items, approvals, configuration, and review to clients ([noninteractive docs](https://developers.openai.com/codex/noninteractive), [app-server source protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)).

### Strengths

- The control loop is centralized. Tools do not each invent approval, sandbox, retry, and result-recording semantics.
- Session/turn IDs and item lifecycle make UI, resume, subagent, and noninteractive consumers share a common state model.
- User messages can steer a run or queue for the next turn; the loop is not fire-and-forget.
- Tool calls can run in parallel where the router marks them safe, while runtime cancellation remains explicit.
- Goal mode adds a persistent objective with pause/resume/edit/clear controls, but it remains inside the existing thread rather than creating a durable-execution service ([CLI slash commands](https://developers.openai.com/codex/cli)).

### Weaknesses and what not to copy

- The loop’s competence still depends on model prompting. The official best-practices page tells users to ask for tests and review; it does not claim universal automatic verification ([Codex best practices](https://developers.openai.com/codex/learn/best-practices)). Our contract’s explicit terminal-state, two-strikes, and generator-critic rules are stronger behavior-level safeguards (`AGENTS.md:28-60`).
- Context compaction is model-generated and lossy; source itself warns that long threads and multiple compactions can reduce accuracy ([compact source](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs#L329-L374)). Do not treat a compacted rollout as an objective ledger.
- Under-development features are mixed into the same config namespace as stable ones. The owner snapshot suppresses unstable warnings and enables many feature flags (`config.toml:14,82-130`), which makes silent drift more likely.
- Codex exposes powerful “bypass everything” modes. That flexibility is useful inside an externally isolated environment but unsafe as a global default; the owner snapshot currently has `approval_policy="never"` plus `sandbox_mode="danger-full-access"` (`config.toml:6-7`).

## 2. Context management

### Instruction and context assembly

Codex composes context from base/developer instructions, prompt/thread input, environment context, `AGENTS.md`, skill metadata and selected skill bodies, plugin/app instructions, MCP server instructions/tools, memory injection, hooks, tool outputs, and prior rollout items. Its configuration reference exposes explicit context controls such as `model_context_window`, `model_auto_compact_token_limit`, `model_auto_compact_token_limit_scope`, `tool_output_token_limit`, and custom compaction prompts ([configuration reference](https://developers.openai.com/codex/config-reference)).

`AGENTS.md` is hierarchical: global guidance in `~/.codex/AGENTS.md`, repository guidance, and closer nested files, with closer guidance winning. The instruction chain is built at session start, so a restart is required for changed files to be reliably reloaded ([AGENTS.md docs](https://developers.openai.com/codex/agent-configuration/agents-md)). This is comparable to the owner’s cross-tool contract, which already uses a global file and task-specific pointers (`AGENTS.md:1-18`).

Skills use progressive disclosure: metadata first, full `SKILL.md` only when selected, then references/scripts as needed. Codex caps the initial skill listing at 2% of the context window or 8,000 characters when the window is unknown, shortening descriptions and potentially omitting skills with a warning ([skills docs](https://developers.openai.com/codex/skills)). This is already mirrored in the owner’s Claude settings via `skillListingBudgetFraction: 0.02` (`/local_disk0/codexwork/bundle/claude/settings.json:3` in the unpacked file), so it is not a missing capability.

### Compaction and persistence

Codex supports automatic compaction and `/compact`. Compaction replaces older history with a summary, preserves selected user messages and canonical initial context, increments a compaction window, records a compaction item, and resumes the turn ([compact source](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs#L221-L374)). Hooks exist immediately before and after compaction. The configured prompt can be replaced inline or by file.

Sessions are stored under `CODEX_HOME` by default, can be resumed, forked, archived, unarchived, renamed, or permanently deleted, and `codex exec resume` supports multi-stage automation ([CLI reference](https://developers.openai.com/codex/cli/reference), [noninteractive docs](https://developers.openai.com/codex/noninteractive)). `--ephemeral` suppresses rollout persistence for disposable runs.

The owner is already stronger on objective continuity: its Stop hook records objective turn data and SessionStart replays the event ledger after resume/compact/clear (`AGENTS.md:20-26`), while semantic memory is explicitly distinct (`AGENTS.md:62-68,79-85`). Codex compaction should therefore remain a working-set reducer, not become canonical history.

### Context proposal

#### CONFIG — set explicit tool-output and compaction budgets

Set `tool_output_token_limit` and a deliberate `model_auto_compact_token_limit`; keep raw logs as addressable files with terminal status plus bounded head/tail. This rides Codex’s native context bus and mirrors the owner’s long-run pointer model. It is **likely (55-80%)** to reduce context pollution because the owner permits very large outputs (`BASH_MAX_OUTPUT_LENGTH=150000` and 64,000 assistant tokens in the Claude settings) and Codex natively truncates stored tool output. Exact limits are **UNVERIFIED — settle by replaying long tests, RE dumps, and research tasks at 4k/8k/12k tool-output caps and measuring terminal success plus forced rereads.**

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — composed-prompt regression receipt

Add a background validation job using native `codex debug prompt-input` to store only item kinds, sizes, ordering, and hashes—never raw secrets—and compare them against fixtures after AGENTS/skills/hooks/config changes. This is **very likely (80-90%)** to catch precedence and bloat regressions because Codex exposes model-visible prompt composition and the owner’s behavior is spread across several layers. It is **UNVERIFIED — settle by inserting one known canary instruction in each layer, confirming the detector finds all controls, then deliberately reversing a precedence edge.** This satisfies the owner’s known-positive-control requirement (`INPUT-known-harness-defects.md:111-129`).

## 3. Memory

### Codex native memory mechanism

Local Codex memories are optional and off by default. When enabled, Codex turns useful context from eligible prior chats into local memory files in the background; it skips active or short-lived sessions, redacts secrets from generated fields, and can defer generation near rate limits. Generated artifacts live under `~/.codex/memories/`; controls separate `generate_memories` from `use_memories`, and `disable_on_external_context` can keep MCP/web-using chats out of generation ([memories docs](https://developers.openai.com/codex/customization/memories)).

This is a useful native design for an otherwise stateless personal CLI: delayed idle extraction avoids summarizing live work, generation and injection can be controlled separately, and memory can be disabled per chat.

### Why it is worse for this owner

The owner already declares `basic-memory` the cross-tool canonical semantic store, uses explicit `valid_as_of`/`superseded_by` semantics, and keeps the event ledger as objective history (`AGENTS.md:62-68,79-85`). The Codex snapshot simultaneously enables native memories (`config.toml:103`) and the canonical Basic Memory contract. That creates two semantic writers with different authority, provenance, supersession, and cross-tool visibility.

Codex’s secret redaction is defense-in-depth, not a proof that extracted memory is safe or correct. Generated summaries can preserve stale or adversarial external claims, especially if external-context sessions are allowed. The owner’s hard rule treats fetched/MCP content as untrusted; native memory must not silently promote it.

#### CONFIG — disable the duplicate native memory writer, or at minimum exclude external-context sessions

Preferred: set native `generate_memories=false` and `use_memories=false`, retaining Basic Memory and the event ledger. If the owner deliberately wants native personal-preference recall, first set `disable_on_external_context=true`, restrict it to preferences that do not overlap project truth, and evaluate it. Pruning the duplicate plane is **very likely (80-90%)** to reduce stale/conflicting recall because both configured writers target durable semantic context and only one has the owner’s supersession contract. The actual conflict rate is **UNVERIFIED — settle by sampling 100 native memory entries, joining them to Basic Memory by topic, and scoring duplicates, contradictions, source provenance, and temporal freshness.**

Do **not** copy the internal SQLite/claim pipeline into the shared harness. That would be a rejected second memory/durable-execution plane. The existing bus already has the needed durable store.

## 4. Tool and MCP handling

### Native local tools

Codex has a registry/router/runtime split. Tool specs exposed to the model are separated from runtime handlers; the router parses model function calls; the tool orchestrator applies approval/sandbox/network policy; lifecycle events record started/completed results. Shell/unified PTY execution, patch application, plan updates, images, time, user input, plugin install requests, MCP resources, MCP tools, web tools, and multi-agent controls use this common path. This architectural separation is stronger than payload-scanning guards because it retains typed tool identity and arguments.

That exact distinction matters to the owner’s confirmed defect: four detectors confuse mention with use and can label a successful result failed (`INPUT-known-harness-defects.md:9-107`). Codex hooks receive `tool_name` plus `tool_input` for local function calls, so a shared semantic discriminator can branch first on typed verb/tool and target path instead of scanning arbitrary prose ([hooks docs](https://developers.openai.com/codex/hooks)). Hosted tools are not universally visible to local hooks, however, so hooks are explicitly not a complete enforcement boundary.

### MCP

Codex supports stdio and streamable HTTP MCP; environment forwarding, bearer tokens, OAuth, ChatGPT-session auth for trusted first-party servers, server instructions, resources, prompts, and tools. Config can set startup/tool timeouts, `enabled`, `required`, `enabled_tools`, `disabled_tools`, OAuth scopes, and per-tool approval behavior ([MCP docs](https://developers.openai.com/codex/mcp)). `/mcp` exposes status, and the CLI provides add/list/get/remove/login/logout operations.

The important competitive mechanism is not “supports MCP”—the owner has touched 93 servers—but **typed health and least privilege at the server boundary**:

- `required=true` turns a canonical dependency’s initialization failure into startup/resume failure.
- Optional servers can remain non-required.
- Tool allow/deny lists prevent the entire server catalog from entering the model’s capability surface.
- Startup and tool timeouts are per server.
- MCP/app tools can advertise read-only, destructive, and open-world annotations that drive approval.
- MCP server instructions communicate cross-tool constraints without repeating them in every tool description.

The measured contrast is severe: `mcp__claude_ai_Tavily__tavily_extract` failed 137/532 calls, including 135 “not connected” errors (`corpus.json:9141-9149`), while ToolSearch itself failed only 4/5,091 calls (`corpus.json:87-92`). Discovery is reliable; the fleet is not being retired or gated correctly.

#### CONFIG — MCP required/optional policy and tool allowlists

Mark only the canonical memory dependency required; disable dead servers; add explicit `enabled_tools`/`disabled_tools` to broad enabled servers; retain bounded startup/tool timeouts; and use tool annotations/approval modes for side-effecting tools. This is **almost certain (90-99%)** to eliminate repeated “server not connected” calls once the dead server is disabled because a disabled tool cannot be selected; the settling experiment is a model-visible tool inventory plus replay of the 135 recorded Tavily-not-connected prompts. It is **likely (55-80%)** to improve tool selection more broadly because fewer irrelevant tools reduce routing ambiguity; that broader effect is **UNVERIFIED — settle with paired tool-choice evals over 100 historical prompts.**

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — MCP health retirement loop

Use `codex doctor --json` or MCP status in the existing periodic health/longrun path, not per turn. Emit a redacted terminal receipt and propose—not automatically perform—disablement after a repeated deterministic initialization failure. This is **very likely (80-90%)** to catch dead/config-drifted servers before model use because Doctor examines configured runtime state and the corpus already exposes repeat failures. Automatic retirement without owner review is **unlikely (20-45%)** to be safe because transient OAuth/network failures can mimic dead servers; therefore the proposal stops at a reviewed config change. The precise Doctor JSON contract on the Windows install is **UNVERIFIED — settle with a redacted `codex doctor --json --all` background capture and a known-good plus intentionally invalid disposable MCP config.**

### Tool behavior worse than ours

- Codex’s local hook bus does not cover hosted tools such as WebSearch. The owner’s cross-provider safety model must therefore keep a non-hook trust rule for fetched content.
- Multiple matching hook commands launch concurrently, so one hook cannot prevent another hook from starting. Do not assume hook ordering or use one hook as a prerequisite for another.
- Async hook handlers, prompt handlers, and agent handlers are parsed but currently skipped; only command hooks execute. Do not port designs that depend on those parsed forms.
- Oversized hook output is truncated in-model and written to disk. This is useful, but it can create a new secret-bearing artifact if a hook emits sensitive data.
- Tool schema enforcement can itself be over-strict. The owner measured 846 StructuredOutput errors in 3,694 calls, including 294 failures for two required properties (`corpus.json:8964-8992`). Copy typed schemas only at machine boundaries; do not require irrelevant fan-out fields.

## 5. Permission model

### Codex’s two-layer model

Codex separates technical containment from decision policy:

- **Sandbox mode:** `read-only`, `workspace-write`, or `danger-full-access` determines what the process can technically touch. Local clients use OS enforcement. Workspace-write defaults to no network and limited writable roots; protected paths can remain unwritable.
- **Approval policy:** `untrusted`, `on-request`, `never`, or granular categories determines when execution pauses for permission.

Network policy is allowlist-first and supports domain and socket rules, DNS-rebinding protections, and local/private destination controls. `deny` wins. Shell environment inheritance can start from none/core and filter secret-like variables. App/MCP destructive annotations can force approval separately from shell/file changes. Managed `requirements.toml` can constrain allowed sandbox/approval/web-search modes and lock hook policy ([approvals and security](https://developers.openai.com/codex/agent-approvals-security), [managed configuration](https://developers.openai.com/codex/enterprise/managed-configuration)).

Codex also has an automatic approval reviewer. Eligible interactive approvals can be routed to `auto_review`, which sees a compact transcript and exact proposed action, applies policy, and approves/denies; prompt/session parsing failures fail closed. The sandbox remains the hard boundary. The open-source config schema describes the reviewer as a context-gathering, risk-based subagent ([config schema](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json)).

### Owner-specific finding

The snapshot uses the least contained global combination: approval never plus danger-full-access (`config.toml:6-7`), and user-level trust spans broad roots (`config.toml:151-170` and later project entries). This is worse than Codex’s documented default and worse than the owner’s stated “block only dangerous” contract (`AGENTS.md:48-54`).

The earlier audit’s Windows probe reported `codex sandbox` failing before child execution with Windows error 206, consistent with the pinned orphan-plugin/CreateProcess root cause. That runtime claim is **UNVERIFIED on this Linux node — settle with two mechanically independent Windows signals after safe orphan quarantine: (1) `codex sandbox read-only` attempts a write to a disposable file and must deny it; (2) a separately launched child reports its token/ACL identity or a ProcMon trace shows the sandbox boundary. First prove both detectors on known-present allowed behavior.** Until then, the label `workspace-write` is not evidence of containment on this machine.

#### CONFIG — make native profiles the only launcher policy surface

Set the global default to workspace-write/on-request (or read-only/on-request for audit work); keep danger-full-access/never only in an explicitly named externally isolated profile; ensure every wrapper passes `--profile`; and add `--strict-config`. This is **very likely (80-90%)** to reduce accidental broad authority because current global values are maximally permissive and native profile layering is supported. Effective enforcement on Windows remains **UNVERIFIED — settle with the two-signal sandbox test above and an effective-config receipt from each wrapper.**

#### CONFIG — use granular approvals, not prompt-only prohibitions

Keep sandbox escape, rule, MCP elicitation, permission-request, and skill-script categories explicitly interactive or explicitly denied. Keep destructive git and credential egress in executable policy/rules. This is **likely (55-80%)** to reduce both interruptions and unsafe auto-execution because Codex can distinguish approval categories; the optimal category split is **UNVERIFIED — settle by replaying 200 historical approvals and scoring false prompts/false permits against owner labels.**

#### CONFIG — automatic approval review only behind sandbox and canary

If used, enable `auto_review` only in workspace-write/read-only profiles and supply the owner’s policy. Never treat it as containment. It is **roughly even (45-55%)** whether it improves this owner’s workflow because it could reduce routine prompts but introduces another model judgment on a harness already harmed by semantic false positives. **UNVERIFIED — settle with shadow-mode review of 200 historical proposed actions, measuring agreement, dangerous false approvals, and benign false denials; require zero dangerous false approvals before enforcement.**

## 6. Customization: rules, skills, hooks, prompts, plugins

### `AGENTS.md` and config layers

Codex has a clear scope ladder: one-off prompt; global/repo/nested `AGENTS.md`; global/project/profile `config.toml`; skill; plugin; MCP/app; hook. Project config/hooks are trust-gated. This is a good separation of guidance, reusable workflow, external capability, and lifecycle enforcement.

The owner already uses `AGENTS.md` well, including cross-tool precedence and a compact pointer model (`AGENTS.md:1-18,43-85`). Codex’s closest-file precedence is not a gap.

### Rules / execpolicy

Codex rules are executable command policy. They match command prefixes, attach decisions, and can be amended from an approval. This is more appropriate than scanning arbitrary payload prose for dangerous command substrings ([rules docs](https://developers.openai.com/codex/rules)). It directly supports the known defect’s required discriminator: tool identity/argv first, content only when semantically relevant (`INPUT-known-harness-defects.md:43-50,78-87`).

### Skills

Skills are portable folders with `SKILL.md`, optional scripts, references, assets, and optional MCP dependencies. Global and repo scopes are supported, discovery is metadata-first, and a skill can be explicitly selected or implicitly matched. This is broadly equivalent to the owner’s installed skill system; the problem is utilization, not primitive availability. The corpus shows a long tail with only a subset repeatedly invoked (`corpus.json:13265-13310` excerpt), and the prompt pins 78 used of roughly 355 installed.

### Hooks

Codex currently documents ten lifecycle events: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, and `Stop`. Hooks can inject context, block or rewrite supported local tool calls, issue warnings, and request continuation/stop on supported events. Definitions can live in user/project config, `hooks.json`, managed requirements, or plugins. Non-managed hook trust is pinned to the exact definition hash; new/changed definitions are skipped until reviewed through `/hooks` ([hooks docs](https://developers.openai.com/codex/hooks)).

This trust mechanism is a Codex advantage over a naive installer that equates “file written” with “hook active.” It also exposes a deployment requirement: hook reconciliation must report pending trust rather than silently declaring success.

Codex hooks are weaker than the owner’s Claude surface in event breadth: there is no documented `PostToolUseFailure`, `PermissionDenied`, `ConfigChange`, task-created/completed, or teammate-idle event. Do not generate a shared superset and assume unknown Codex events work. Absence is established with two independent signals: the current official event table and the open-source hook/tool paths; the owner snapshot also enables hooks but does not prove unsupported events (`config.toml:105`).

### Custom prompts and plugins

Markdown custom prompts under `~/.codex/prompts/` can expand placeholders, but only top-level files are scanned. Plugins are the distribution unit: a manifest can bundle skills, MCP config/apps, hooks, assets, and marketplace metadata; local or Git-backed marketplaces can pin sources. This is useful packaging, but the owner’s 1,293 orphaned plugin directories demonstrate that cache lifecycle is an operational hazard. Do not expand plugin use until installation/cache cleanup is safe and reference-aware.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — provider capability matrix for hook registration

Generate only events supported by each provider; reject unknown events during validation; and require a known-present event canary. This is **almost certain (90-99%)** to remove false “drift” pressure for non-native Codex events because official docs enumerate the Codex surface and provider-specific generation is deterministic. Runtime firing remains **UNVERIFIED — settle with a disposable Codex home that fires one controlled event in each supported coordinate and emits a receipt.**

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — hook trust receipt in deployment

After writing/reconciling Codex hooks, compare definition hashes to Codex trust state and end with `ACTIVE`, `PENDING_TRUST`, or `REJECTED`, never generic success. This is **very likely (80-90%)** to prevent silent inactive hooks because Codex explicitly skips untrusted changed definitions. The trust-state read interface is **UNVERIFIED — settle with `/hooks` or an official structured status command in a disposable profile; do not parse unstable transcripts if no supported structured interface exists.**

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — shared typed semantic discriminator

Implement the already-pinned fix once on the existing dispatcher: inspect event, typed tool name, argv/target path, file role, JSON field value, and markdown fence/prose position before matching content. Migrate destructive-command, marker/stub, and tool-result sentinels to it; replay all recorded false fires plus true positive controls. This is **very likely (80-90%)** to eliminate the confirmed use-versus-mention class because all recorded cases differ on typed role/value/context. Input sufficiency is **UNVERIFIED — settle by capturing redacted hook payload schemas from Claude and Codex for Bash, write/patch, MCP, and Stop before implementation.** This stays below ~200 lines only if those fields are present; if not, stop rather than expanding into BUILD-LARGE.

## 7. Multi-agent support

### Mechanism

Codex has native agent threads. The root can spawn specialized children, send follow-up input, interrupt, wait, inspect, resume, and close them; supported clients surface thread activity. Built-ins include general/default, worker, and explorer. Custom agents are TOML layers in user or project `.codex/agents/`, with required name/description/developer instructions and optional model, reasoning effort, sandbox mode, MCP servers, skills config, and nicknames ([subagents docs](https://developers.openai.com/codex/subagents)).

The defaults are intentionally bounded: maximum six open threads and depth one, so the root may spawn children but children do not recursively fan out. Subagents inherit the parent’s live permission overrides; noninteractive children cannot conjure a new approval and fail the action back to the parent. Read-heavy exploration/test/log analysis is recommended for parallelism; parallel writes risk conflicts.

The owner snapshot enables stable and v2 multi-agent surfaces, sets eight concurrent threads, **and sets depth eight** (`config.toml:77-80,101,125-130`). The owner contract wisely requires structured summaries and goal re-anchoring instead of raw subagent output (`AGENTS.md:43-46`). Native Codex already embodies the context-isolation benefit but does not replace that handoff contract.

### Better than ours

- Agent work is a first-class thread with lifecycle, inspectability, steer/interrupt/wait/close controls, not opaque fire-and-forget subprocess output.
- Each role can have a distinct model, effort, sandbox, MCP set, and skill set.
- Parent live permission overrides are reapplied to children, preventing a stale role file from silently broadening a child.
- Subagent activity is summarized back into the main context, reducing raw log pollution.

### Worse / risks

- Recursive depth eight is a multiplicative token/latency/resource risk. The official default and recommendation are depth one.
- All agents share a workspace unless worktrees or file-scope discipline isolate writes. Native threads do not solve write conflicts.
- More agents consume more tokens; Ultra plus high concurrency is explicitly warned about in CLI 0.144.0 ([Codex changelog](https://developers.openai.com/codex/changelog)).
- Custom agent TOML is described by the manual as heavier than a dedicated manifest and may evolve.
- A summarized child handoff can conceal omitted evidence. The owner’s requirement for typed sections and file references should remain.

#### CONFIG — return recursion depth to one; keep concurrency separate

Set `agents.max_depth=1`; retain a bounded direct-child concurrency limit; require an explicit per-run exception for recursive delegation. This is **very likely (80-90%)** to prevent runaway fan-out while preserving nearly all useful parallelism because the owner’s documented workload is one root coordinating independent audit units, not recursively self-replicating work. Any quality loss is **UNVERIFIED — settle by replaying representative 8-, 32-, and 140-unit audits at depth one versus current depth, comparing completion, duplicates, wall time, and tokens.**

#### CONFIG — role-specific least privilege

Keep explorer/reviewer read-only, worker workspace-write, and give production/log MCP only to roles that need it. This is **very likely (80-90%)** to reduce blast radius because custom agent layers natively override sandbox and MCP and the work types have distinct needs. Exact role inventories are **UNVERIFIED — settle by logging model-visible tools per role against 30 historical tasks and removing tools never needed.**

Do not build a second multi-agent coordinator. Native Codex threads plus the existing shared dispatcher satisfy the anti-overfit gate.

## 8. Verification and self-check mechanisms

Codex provides several distinct verification surfaces, but no single universal “correctness critic”:

1. **`/review` / `codex review`:** review uncommitted changes, a commit, or a branch/base comparison; review can use custom instructions or a review-specific model ([CLI docs](https://developers.openai.com/codex/cli)).
2. **Tests/commands:** the normal loop can run repository-defined validation. `AGENTS.md` is the durable place for exact commands.
3. **Typed noninteractive output:** `codex exec --output-schema` constrains the final response; `--json` streams events; `-o` stores the last message; `--ephemeral` prevents history persistence ([noninteractive docs](https://developers.openai.com/codex/noninteractive)). These are different channels and should not be conflated.
4. **Strict config:** `--strict-config` rejects unknown configuration instead of silently accepting drift ([CLI reference](https://developers.openai.com/codex/cli/reference)).
5. **Doctor:** current releases expose `codex doctor --json` for redacted machine-readable health; the current changelog is the release authority ([changelog](https://developers.openai.com/codex/changelog)).
6. **Prompt inspection:** debug prompt input exposes what the model actually receives, enabling composition regression tests.
7. **Diff/status:** `/diff` includes untracked files; `/status` exposes model, permission, writable roots, and remaining context.
8. **Hook gates:** Pre/Post tool and Stop hooks can inject validation or continue a turn.
9. **Approval auto-review:** a separate model review can evaluate proposed actions but is a safety reviewer, not a code-correctness proof.
10. **Open-source tests/source:** behavior can be audited down to loop and config schema, reducing black-box ambiguity.

### Typed output: the most valuable port

The owner’s StructuredOutput tool fails 22.9% of calls; the largest fingerprint is over-strict missing `kg_triples` plus `confidence` (`corpus.json:8964-8992`). Native Codex output schema is valuable at true machine boundaries, but only if the schema is minimal and caller validation remains independent.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — typed Codex consultation envelope

For every machine-consumed Codex peer, invoke `codex exec --json --output-schema <minimal-schema> -o <result> --ephemeral`; validate the result again in the caller; distinguish event JSONL from final payload; return a typed failure rather than reparsing arbitrary prose. Use optional fields for non-universal content and a discriminated status union (`ok` with result, `blocked` with blocker, `failed` with error). This is **very likely (80-90%)** to eliminate malformed-final-payload handling failures because both producer and consumer validate the same small boundary. It will **not** fix bad schema design. The net error reduction is **UNVERIFIED — settle by replaying the 846 StructuredOutput failures against a minimal envelope and comparing schema rejection, semantic completeness, and retries.**

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — verification receipt, not completion prose

At task end, record changed files, diff hash, commands run, exit codes, test counts, unresolved failures, and explicit unverified claims. Feed this through the current event ledger/Stop hook and optionally compare with `/review`. This is **likely (55-80%)** to reduce false completion because it converts claims into checkable evidence and fits the existing ledger. It is **UNVERIFIED — settle by scoring 100 owner-correction candidates with and without receipts for false “done” claims.**

### What not to copy

- Do not use a trained critic or perpetual review swarm. A bounded `/review` after meaningful diffs rides the native bus; an always-on critic would violate the anti-overfit gate.
- Do not make schema richness a proxy for quality. The corpus directly falsifies that approach.
- Do not accept “Doctor green” as task correctness; it is environment/config health.
- Do not accept a review model’s approval as independent proof unless it uses different evidence or a fresh execution signal. The owner’s two-independent-signals rule remains stronger.

## 12. Anti-overfit gate

Every counted proposal uses Codex config, the existing shared hook/skill/MCP dispatcher, or a small wrapper around an existing native command. None introduces:

- a second orchestration runtime;
- a new vector database or knowledge graph;
- a durable-execution engine;
- a trained critic;
- an observability SaaS;
- a guardrail framework.

The radical option considered was replacing the shared harness with Codex app-server as the sole owner runtime. It was rejected because app-server would replace a transport/orchestration surface but not the cross-provider canonical memory, objective ledger, known-positive controls, Windows-specific rules, or Claude/Antigravity integration. This minimal hybrid is **very likely (80-90%)** to dominate either extreme for this owner because it retains unique cross-provider assets while deleting duplicated control planes.
