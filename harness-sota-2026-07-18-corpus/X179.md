# X179 — Cross-domain borrow: experimental design → tool design

**Unit:** X179  
**Source field:** experimental design (preregistration, power analysis, blinding, negative controls)  
**Target:** tool interfaces and error messages that induce agent misuse, especially the pinned 1,631 unmatched-quote/EOF shell failures  
**Lens constraint:** external research and cross-domain translation only; no local-repository audit  
**Date:** 2026-07-19

## Executive conclusion

One experimental-design mechanism transfers strongly, but only after narrowing the analogy: **a prospectively declared protocol paired with concurrent positive and negative controls**. In the source field, the protocol fixes the intended intervention, outcome, exclusions, and analysis before outcomes can influence those choices; controls exercise the same assay while omitting the target or supplying a known target. In a tool interface, the corresponding objects are (1) a machine-readable declaration of the intended executable and argument boundaries, made before execution, and (2) an independent observation of what the shell/parser/launcher would actually receive. The harness compares intent with observation before allowing side effects.

The resulting design is an **intent-registered, control-checked execution interface**:

1. Direct program invocations use a structured `argv` tool, not a shell string.
2. Commands that genuinely need shell grammar use an explicit `shell_program` mode.
3. Before execution, the native shell parser checks syntax, a deterministic extractor records the resulting command/argument structure, and the tool compares that structure with the prospectively supplied intent contract.
4. The tool emits a diagnostic diff—expected argument boundaries versus parsed boundaries—instead of forwarding only the shell's downstream EOF message.
5. A small conformance probe runs at harness startup and after shell/runtime changes. Its positive control contains a known parse error and must be detected; its negative control contains adversarial but valid literal arguments and must pass unchanged through the launch path. This validates the detector as well as the serializer.

It is **very likely (80-90%)**, based on the GNU Bash definition of quoting, Python's official recommendation to pass an argument sequence, and the fact that an unmatched quote is a deterministic parse error, that structured `argv` plus native pre-parse would prevent the large majority of simple unmatched-quote EOF calls from reaching execution. This is **UNVERIFIED for this owner's actual 1,631 fingerprints; the settling experiment is a replay of a redacted, stratified sample through the proposed preflight, scored against the original shell outcome**. It is only **likely (55-80%)**, based on the proposed intent-versus-AST comparison and the known limits of static shell analysis, that the design will also catch syntactically valid but semantically wrong argument grouping. This is **UNVERIFIED; the settling experiment is a mutation suite that removes, moves, and changes quote types while preserving syntactic validity, with expected `argv` recorded by an oracle helper**.

This is a bounded transfer, not a claim that commands are scientific experiments. Preregistration alone does not make execution correct; controls alone do not reveal the user's intended argument boundaries; and neither mechanism can safely simulate every effectful shell program. Their useful shared structure is narrower: **an intended protocol exists before an observation, the transport can distort it, and a separately specified control can expose distortion**.

## 1. What experimental design has already solved

### 1.1 Preregistration: make the intended protocol inspectable before outcomes

In its own field, preregistration is a time-ordering and disclosure mechanism. The Open Science Framework defines it as posting a time-stamped, read-only study plan before data collection or analysis. Its guidance calls for explicit hypotheses, variables, decision criteria, exclusion rules, outcome reporting, and prospective if/then contingencies ([OSF, “Welcome to Registrations & Preregistrations”](https://help.osf.io/article/330-welcome-to-registrations)). NIST's design-of-experiments handbook similarly describes experimental design as laying out a detailed plan in advance and selecting factors and responses so the resulting data support valid, objective conclusions ([NIST/SEMATECH, “What is experimental design?”](https://www.itl.nist.gov/div898/handbook/pri/section1/pri11.htm)).

The mechanism is not mystical commitment. It creates two inspectable records:

- what was intended before results were available; and
- what was actually done, including deviations.

That separation makes undisclosed outcome-driven changes visible. OSF explicitly recommends recording anticipated contingencies and unplanned work, so preregistration is not equivalent to forbidding adaptation. The important property is that adaptation becomes a named deviation rather than being silently rewritten into the original plan ([OSF](https://help.osf.io/article/330-welcome-to-registrations)).

The closest tool-design analogue is **not** “make the agent write a plan paragraph.” Natural-language plans are too ambiguous to serve as an oracle. The transferable unit is a small, typed execution protocol established before the launcher interprets it:

```json
{
  "mode": "argv",
  "program": "git",
  "args": ["show", "origin/main:path with spaces/file.md"],
  "cwd": "<workspace>",
  "stdin": {"kind": "none"},
  "expected": {
    "command_count": 1,
    "argument_count": 2,
    "literal_args": [1]
  }
}
```

The declaration gives the harness an expectation against which it can compare the actual transport. It also eliminates quoting from the model-facing interface for the common case. Python's official subprocess documentation says that providing a sequence is generally preferred because the library handles the required escaping and quoting, including spaces in filenames; it also warns that `shell=True` requires a correctly formatted shell string ([Python 3 subprocess documentation](https://docs.python.org/3/library/subprocess.html)). GNU Bash explains the underlying hazard: shell metacharacters have special meaning and quoting removes that meaning when a character must represent itself ([GNU Bash, “Quoting”](https://www.gnu.org/software/bash/manual/html_node/Quoting.html)).

Preregistration contributes something that a plain `argv` API does not: it asks the caller to state a few invariants—argument count, literal positions, pipeline stage count, and permitted expansions—before parsing. Those invariants let the tool catch a syntactically valid command whose quote boundary moved. A parser alone will accept that command; an intent/observation mismatch can reject it.

### 1.2 Negative and positive controls: test the whole path, not only the nominal operation

Controls in experimental work identify whether a signal can arise without the target and whether the assay can detect a target that is known to be present. FDA guidance for nucleic-acid diagnostic devices is unusually concrete: a blank/no-template control contains the assay components except target nucleic acid and rules out contamination or background; a negative sample control evaluates the complete procedure, including extraction; and a positive control is designed to exercise the entire assay process from extraction through detection ([FDA, nucleic-acid diagnostic controls](https://www.fda.gov/medical-devices/guidance-documents-medical-devices-and-radiation-emitting-products/nucleic-acid-based-in-vitro-diagnostic-devices-detection-mycobacterium-tuberculosis-complex-respiratory)). Another FDA assay guideline requires negative controls to be treated the same way as treatment groups except for the test substance ([FDA, Bacterial Reverse Mutation Test](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/redbook-2000-ivc1a-bacterial-reverse-mutation-test)).

The essential source-field mechanism is **path equivalence**. A control that bypasses extraction cannot establish that extraction works. A harness analogue must therefore exercise the same serializer, shell selection, quoting layer, process launcher, and operating-system boundary as real calls. Merely calling a string library's `escape()` function in isolation is not an adequate control.

Translate the controls as follows:

- **Positive detector control:** submit a known malformed specimen such as an unclosed Bash single quote and a known malformed PowerShell string. The preflight must reject each with the correct source span. If it does not, the detector is unhealthy and cannot support claims that other commands are clean.
- **Negative transport control:** send a set of valid literal arguments containing spaces, apostrophes, double quotes, trailing backslashes, wildcard characters, dollar signs, Unicode, newlines where supported, and empty strings through the real launch path to a tiny `argv` recorder. The observed argument vector must byte-for-byte (or documented Unicode-normalization-for-normalization) equal the registered vector. A mismatch means the transport, not the called program, is broken.
- **Non-target control:** include shell metacharacters as data in structured `argv` mode. They must remain literal and must not create a pipeline, redirect, expansion, or second command.
- **Known-effect control:** in explicit shell mode, run a harmless fixed pipeline and verify that the AST reports the expected number of stages and redirections. This distinguishes “shell syntax disabled” from “syntax parser healthy.”

The control suite is intentionally tiny and deterministic. It is not run by substituting values into the user's effectful command. It validates the shared transport at startup, after upgrades, and on demand. Per-call validation then checks the specific command's parse and intent invariants without executing it.

### 1.3 Power analysis: useful for the rollout experiment, not the runtime call

In experimental design, sample-size/power analysis is prospective: choose a sample large enough to detect an effect of interest with specified error rates, rather than collecting until the result looks favorable. NINDS asks rigorous studies to justify sample size, for example with a power calculation, and to plan blinding, randomization, and reporting of null as well as non-null results ([NINDS, “Rigorous Study Design and Transparent Reporting”](https://www.ninds.nih.gov/funding/preparing-your-application/preparing-research-plan/rigorous-study-design-and-transparent-reporting)). NIST gives worked methods in which significance, desired power, and effect size determine required sample size ([NIST/SEMATECH, sample sizes for testing proportions](https://www.itl.nist.gov/div898/handbook/prc/section2/prc242.htm)).

Power analysis does **not** sensibly run before each deterministic parser call. There is no population sample in a single invocation, and repeating a deterministic parse does not create independent evidence. Its valid translation is to the evaluation of the interface across stochastic agent generations and heterogeneous tasks.

Using the pinned count only as a planning anchor, 1,631 unmatched-quote failures among 108,121 Bash calls is approximately 1.51%. A simple, independent two-proportion calculation suggests roughly 3,100 calls per arm for 80% power to distinguish 1.51% from 0.755% at two-sided 5% significance; about 4,100 per arm gives 90% power under the same assumptions. These figures are **UNVERIFIED because calls within sessions and tasks are unlikely to be independent and the fingerprint denominator may not represent a stable prospective rate; the settling experiment is a pilot estimating task/session intraclass correlation, followed by a cluster-aware power calculation**. The numbers are therefore a floor for planning, not an acceptance criterion.

The rollout experiment must pre-register:

- primary endpoint: unmatched-quote/EOF failures per eligible shell call;
- secondary endpoints: syntactically valid argument-boundary defects, task completion, latency, extra tool calls, and false blocks;
- eligible calls and exclusions;
- unit of randomization (prefer session or task, not individual call, to limit contamination);
- stopping rule and analysis model;
- minimum worthwhile effect; and
- treatment of agent retries after a blocked call.

This guards against declaring success merely because the wrapper relabels a shell failure as a preflight failure. The primary engineering outcome should count **attempted malformed commands**, while a separate operational outcome counts **malformed commands that reach execution**.

### 1.4 Blinding: little runtime transfer, legitimate evaluation transfer

Blinding in its own field keeps investigators or assessors unaware of group assignment so expectations cannot bias treatment or outcome assessment. NIH's training material defines blinding as keeping sample designations hidden until after the experiment and, where possible, analysis ([NIH, “Blinding and Randomization”](https://grants.nih.gov/policy/reproducibility/training/blinding-randomization.pdf)).

That structure mostly does not exist inside a deterministic shell parser. A parser has no expectation to bias, and hiding the requested operation from the launcher would make validation worse. “Blind the error generator to agent intent” is therefore a failed borrow: intent is exactly what is needed to diagnose an argument-boundary mismatch.

Blinding does transfer to evaluation. Human adjudicators comparing old and new diagnostics can receive randomized, de-identified outputs without treatment labels; a deterministic rubric can score whether the diagnostic identifies the bad span, preserves intended arguments, and suggests a valid repair. This prevents preference for a polished new error format from becoming evidence of correctness. The interface's automated replay oracle should remain primary because it is more objective.

## 2. Adversarial transfer test

### 2.1 Structural correspondences that hold

| Experimental-design structure | Tool-design structure | Why the relation is real |
|---|---|---|
| Protocol exists before outcome | Typed invocation intent exists before parsing/execution | Both establish a prospective reference that later deviations cannot silently overwrite. |
| Sample preparation/assay may distort the target | Templating, quoting, shell parsing, and OS launch may distort argument boundaries | In both cases, the transport/process is a causal part of the observation. |
| Negative control follows the same assay without target | Literal metacharacter specimen follows the same launch path without shell semantics | Unexpected activation exposes contamination/interpolation. |
| Positive control contains a known target | Known malformed quote must trigger the parser | Failure to detect it invalidates “no error found” conclusions. |
| Pre-specified endpoint prevents outcome switching | Pre-specified error taxonomy prevents relabeling a blocked failure as success | Both preserve the meaning of the measured outcome. |

### 2.2 Disanalogies that constrain the design

1. **A command is an intervention, not a passive measurement.** An experiment can often run a control alongside treatment. A destructive shell command cannot safely be “control-run” with substituted data because substitution can change semantics or still cause effects. Therefore per-call controls stop at parsing and intent comparison; transport controls use a separate inert recorder.

2. **There is usually no stochastic sampling in parsing.** Power and randomization are not runtime safety mechanisms. They belong in evaluation across tasks and sessions.

3. **The agent supplies both hypothesis and specimen.** In science, researchers can also make both, but external reality constrains results. Here an agent could register an incorrect intent that exactly matches an incorrect command. The mechanism catches transport and representation mismatch, not mistaken goals. Independent task-level verification remains necessary.

4. **Shell semantics can be undecidable or environment-dependent in practice.** Expansions, command substitutions, generated code, `eval`, sourced files, aliases, functions, and runtime filesystem state can determine final behavior. Static extraction cannot promise exact future `argv` for arbitrary shell programs.

5. **Preregistration is normally an accountability device, not an automatic validator.** The translation adds a machine comparison that the source mechanism does not inherently provide. The borrow supplies the temporal separation; tool engineering supplies the typed schema and parser.

6. **Controls validate a path only within their coverage.** A Bash control does not validate PowerShell, `cmd.exe`, WSL boundary behavior, or every target program's private argument parser. Controls must be shell/runtime-specific and report their coverage explicitly.

The analogy therefore survives, but only for commands with either direct `argv` execution or statically parseable shell structure. It does not justify claiming arbitrary shell scripts safe before execution.

## 3. Concrete harness design

### Proposal A — make direct structured execution the default

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Expose a tool schema with `program`, `args[]`, `cwd`, `stdin`, `timeout`, and narrowly scoped environment additions. The backend launches without a shell. Keep a separate explicit tool/mode for shell programs.

This is the highest-leverage part because it removes the need for the model to serialize an argument vector into a quote-sensitive language and for the harness to reconstruct it. The official Python interface already models this distinction and prefers sequences for escaping/quoting ([Python subprocess](https://docs.python.org/3/library/subprocess.html)). On Windows, the boundary still needs careful serialization because `CreateProcess` accepts a command-line string and executable/path ambiguity is affected by quoting; Microsoft documents that an unquoted path containing spaces can be interpreted multiple ways ([Microsoft `CreateProcessA`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessa)). The negative transport control must therefore run on each supported Windows launcher, not only POSIX.

Minimum schema:

```json
{
  "program": "string",
  "args": ["string"],
  "cwd": "absolute-or-workspace-relative path",
  "stdin": {"kind": "none|text|file-ref", "value": "..."},
  "timeout_ms": 30000,
  "intent": {
    "literal_arg_indexes": [0, 2],
    "expected_arg_count": 3
  }
}
```

Do not accept a single `command` string in this mode. Do not expose a “helpful” automatic fallback to `shell=True`, because fallback would erase the interface invariant precisely when quoting becomes hard. If launch requires a `.cmd`, PowerShell script, or shell builtin, the tool should return a typed `SHELL_REQUIRED` diagnostic and an explicit repair template.

It is **very likely (80-90%)**, based on removal of shell parsing for direct invocations and the official subprocess guidance, that this change reduces unmatched-quote failures for eligible calls. It is **UNVERIFIED what fraction of the owner's failed calls are eligible; the settling experiment classifies a random fingerprint sample into direct-exec, genuine pipeline/redirection, nested interpreter, and unknown categories**.

### Proposal B — explicit shell-program mode with an intent contract

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Preserve shell expressiveness, but require the caller to identify the dialect (`bash`, `pwsh`, or `cmd`) and state compact invariants before execution:

```json
{
  "dialect": "bash",
  "script": "git show 'origin/main:path with spaces/file.md' | sed -n '1,20p'",
  "intent": {
    "commands": ["git", "sed"],
    "pipeline_stages": 2,
    "redirections": 0,
    "literal_fragments": ["origin/main:path with spaces/file.md", "1,20p"],
    "allows": ["pipeline"],
    "forbids": ["command-substitution", "eval", "background"]
  }
}
```

Preflight stages:

1. Parse with the selected native parser without execution. Bash's `-n` option reads commands without executing them and is expressly documented for syntax checking ([GNU Bash Reference Manual](https://www.gnu.org/software/bash/manual/bash.html)); PowerShell exposes `System.Management.Automation.Language.Parser.ParseInput`, which returns tokens and parse errors ([Microsoft PowerShell SDK, `Parser.ParseInput`](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.language.parser.parseinput)).
2. Reject any parse error with its exact span and dialect.
3. Build a shallow AST summary: command names where statically known, pipeline count, redirections, quote spans, expansions, substitutions, and dynamic/effectful constructs.
4. Compare the summary with the intent contract.
5. If the script is too dynamic to establish an invariant, return `CANNOT_VERIFY_STATICALLY`, name the construct, and offer either a structured-exec decomposition or an explicit override. Do not call it safe.
6. Execute only after the comparison passes or a policy-authorized override is recorded.

This catches unmatched quotes before side effects. More importantly, it catches some valid-but-wrong strings: an accidentally unquoted space changes the apparent argument count; a quote swallowing `|` changes pipeline count; an unexpected `$()` violates the allowed-construct list; and a redirection accidentally placed inside or outside quotes changes the AST summary.

It will not determine the final values of arbitrary expansions or substitutions. It is **likely (55-80%)**, based on ShellCheck's documented ability to identify word-splitting/globbing errors and the additional caller-supplied invariants, that the shallow check catches useful defects beyond parser errors without becoming a full shell runtime. ShellCheck explains that unquoted expansions can split on IFS and then glob, while arrays preserve intended argument boundaries ([ShellCheck SC2086](https://www.shellcheck.net/wiki/SC2086)). This effectiveness forecast is **UNVERIFIED; the settling experiment is a labeled corpus of real and mutation-generated Bash/PowerShell quote defects, measured separately for syntax errors, static semantic errors, false blocks, and unclassifiable dynamic constructs**.

### Proposal C — concurrent conformance controls for every launcher/dialect

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a tiny `argv-recorder` helper and a manifest of control cases. Run them at installation/startup, after detected runtime-version changes, and when a launcher produces an impossible result.

Required outcome matrix:

| Control | Expected result | Failure interpretation |
|---|---|---|
| Valid empty argument | Recorder sees one zero-length argument | Serializer collapsed an argument |
| Valid path with spaces | Recorder sees one argument | Quote/launch boundary split it |
| Literal `*`, `$()`, `|`, `>` in direct mode | Recorder sees literal characters; no shell effect | A shell or interpolation layer was unexpectedly introduced |
| Trailing backslashes before a quote (Windows) | Recorder matches manifest exactly | Windows serialization mismatch |
| Known unclosed Bash quote | Native preflight rejects at known span | Bash detector unavailable/misconfigured if it passes |
| Known unclosed PowerShell quote | Native preflight rejects at known span | PowerShell detector unavailable/misconfigured if it passes |
| Known harmless pipeline in shell mode | Two stages reported and command succeeds | Shell grammar disabled, wrong dialect, or AST extractor broken |

Report control health as typed capability state, for example `direct.windows-crt: PASS`, `bash.parse: PASS`, `pwsh.parse: FAIL_CONTROL`. A failed control disables only the affected claim/mode where feasible. It must not be converted into “no defect detected.”

It is **very likely (80-90%)**, based on the FDA whole-procedure control principle and deterministic byte comparisons, that these controls detect regressions in serialization and detector wiring that ordinary happy-path unit tests can miss. It is **UNVERIFIED whether startup overhead is negligible on the owner's Windows environment; the settling experiment measures cold and warm control-suite latency on PowerShell 7, Git Bash, native executables, and any supported WSL path**.

### Proposal D — change errors from shell prose to an intent/observation diff

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The error message is part of the corrective control loop. Returning only `unexpected EOF while looking for matching quote` tells the agent that parsing failed but not which intended argument boundary was lost or which interface avoids the failure.

Use a stable machine-readable envelope plus concise rendered text:

```json
{
  "code": "QUOTE_UNCLOSED",
  "dialect": "bash",
  "phase": "preflight.parse",
  "span": {"start": 9, "end": 47},
  "expected": {"arg_count": 2, "literal_arg_indexes": [1]},
  "observed": {"parse": "incomplete", "open_quote": "single"},
  "executed": false,
  "retry_class": "repair-input",
  "repairs": [
    {"kind": "use-structured-exec", "program": "git", "args": ["show", "origin/main:path with spaces/file.md"]}
  ]
}
```

Rendered form:

> **Not executed — Bash parse failed.** A single-quoted argument begins at column 10 and never closes. Intended argument 2 was `origin/main:path with spaces/file.md`. Prefer structured execution: `program="git"`, `args=["show", "origin/main:path with spaces/file.md"]`. Do not retry the unchanged string.

Design requirements:

- State whether side effects occurred (`executed: false`) before diagnostic detail.
- Name phase and dialect; “quote error” without dialect is under-specified on a mixed-shell host.
- Give source span, quote type, and expected-versus-observed structure.
- Supply a structured repair when direct execution is possible; do not synthesize another nested shell string.
- Assign retry semantics: unchanged retry forbidden, corrected input allowed, environment retry irrelevant.
- Preserve raw native-parser text as a secondary field for debugging, not as the primary agent instruction.
- If intent is missing, say `INTENT_UNAVAILABLE`; never invent what the argument was supposed to be.
- If more than one repair is valid, distinguish safe structural repair from behavior-changing alternatives.

It is **likely (55-80%)**, based on the tighter causal information and explicit no-unchanged-retry signal, that this format reduces blind retry loops after quote errors. This is **UNVERIFIED; the settling experiment randomly assigns agents the legacy versus structured diagnostic on held-out malformed commands and measures unchanged retries, repair success, new defects introduced, and tokens/tool calls to recovery**.

### Proposal E — preregister and power the interface evaluation

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Before rollout, freeze a small evaluation protocol beside the benchmark manifest. Randomize at task/session level, keep benchmark authors from scoring their own cases where human judgment is required, and publish all primary and secondary outcomes including false blocks and latency.

The protocol should include four strata:

1. exact syntax faults (unclosed single/double/ANSI-C quotes, escaped terminators, nested substitutions);
2. valid but wrong grouping (spaces, empty args, wildcard expansion, quote-swallowed operators);
3. genuinely dynamic scripts that the verifier should decline to certify; and
4. clean, difficult commands that must not be blocked.

Use held-out real fingerprints only after redaction and mutation-generated cases whose oracle `argv` is independently recorded. Mutation cases prevent the benchmark from being only a memorized replay of yesterday's errors. Real cases prevent a synthetic grammar suite from standing in for agent behavior.

Blinded human scoring applies only to ambiguous repair quality; exact parse detection and `argv` equality are automatically scored. This proposal is **very likely (80-90%)**, based on established prospective design and blinding principles from OSF and NIH, to make the rollout conclusion more credible than an unregistered before/after dashboard. Whether it changes the product decision is **UNVERIFIED; the settling experiment is the registered A/B evaluation itself**.

## 4. What this catches that a conventional parser/error pipeline misses

| Failure | Native syntax parse only | Intent + controls design |
|---|---:|---:|
| Unclosed quote / EOF | Yes | Yes, before execution, with intended boundary and structured repair |
| Wrong shell dialect selected | Sometimes confusingly | Control health and explicit dialect identify it |
| Quote closes, but a path splits into two args | Usually no | Expected argument count/literal invariant can detect it |
| Pipe or redirection accidentally quoted | Usually no syntax error | Pipeline/redirection invariant can detect it |
| Metacharacter interpreted although caller intended data | Usually no | Direct `argv` mode plus non-target control prevents/detects it |
| Launcher changes argument serialization after an upgrade | No, script parses | End-to-end recorder control detects it |
| Detector silently unavailable | Absence may look clean | Known-positive control must fail if detector is unhealthy |
| Agent retries identical malformed text | Not necessarily | Typed retry class says unchanged retry is invalid |
| Agent's overall goal is wrong | No | No; outside the analogy and requires task-level verification |
| Runtime-dependent `eval`/sourced/generated code defect | Usually no | Often only `CANNOT_VERIFY_STATICALLY`; no false safety claim |

The strongest improvement is epistemic: the harness distinguishes **passed**, **failed**, and **not verifiable**, and it validates that its detector can find a known-present defect before reporting a clean state.

## 5. Alternatives considered and rejected

### “Just improve the prompt with shell quoting rules”

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Rejected as the primary mechanism. Prompt guidance leaves the agent responsible for serializing structured intent through a context-sensitive grammar. GNU Bash's quoting rules and ShellCheck's examples show why seemingly simple expansions can split and glob ([GNU Bash](https://www.gnu.org/software/bash/manual/html_node/Quoting.html); [ShellCheck SC2086](https://www.shellcheck.net/wiki/SC2086)). Guidance can remain as defense in depth, but it provides neither a transport oracle nor detector-health control.

### “Run ShellCheck and nothing else”

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Rejected as a complete answer, even where a native hook can invoke it. ShellCheck is useful Bash static analysis and recognizes quoting problems, but it does not represent the caller's intended `argv`, validate Windows process serialization, cover PowerShell with Bash semantics, or prove that the detector itself is wired correctly. It belongs inside Proposal B for supported dialects, not in place of structured execution and controls.

### “Dry-run every command in a sandbox”

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected. Faithful shell behavior depends on filesystem, environment, credentials, network, processes, and time. Reproducing those in a sandbox becomes a second execution runtime, one of the explicitly rejected architecture classes, while an unfaithful sandbox provides false reassurance. This proposal would violate the anti-overfit gate without evidence that the small parser/transport mechanisms are insufficient.

### “Use an LLM critic to review every command”

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected. A model critic is stochastic, shares failure modes with the command-generating model, needs its own calibration, and is a trained-critic-like layer explicitly disfavored by the anti-overfit gate. Deterministic parsers, typed arrays, and exact byte comparisons are better matched to quote transport.

### “Blind the parser to the agent's intent”

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Rejected because the source-field purpose of blinding—preventing expectancy bias in subjective treatment or assessment—does not apply to deterministic parsing. Hiding intent removes the oracle needed to detect syntactically valid mis-grouping. Blind only evaluation labels from human raters.

### “Apply power analysis to each command”

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Rejected as a category error. Repeated deterministic parsing is not independent sampling. Power analysis belongs to the population-level A/B evaluation.

## 6. Minimal implementation sequence and acceptance gates

The proposals deliberately ride the existing tool/hook bus. They add no orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

1. **Structured direct-exec schema.** Implement `program + args[]`; refuse silent shell fallback. Acceptance: adversarial literal arguments arrive at the recorder exactly on every supported OS/runtime path.
2. **Dialect preflight.** Native parse, shallow AST summary, intent comparison. Acceptance: every known syntax-positive control is rejected, every valid negative control passes, and unsupported dynamics are labeled unverified rather than safe.
3. **Typed errors.** Add phase, dialect, span, expected/observed, execution state, retry class, and structured repair. Acceptance: deterministic schema tests plus blinded repair-quality evaluation.
4. **Controlled shadow deployment.** Run preflight without blocking, recording would-block decisions and oracle outcomes. Acceptance thresholds must be preregistered after a pilot and before the confirmatory sample.
5. **Randomized blocking rollout.** Randomize by task/session, use cluster-aware power, measure attempted defects separately from defects reaching execution, and report false blocks/latency.

The ordering matters: a control suite must exist before “no errors observed” becomes evidence, and shadow mode must estimate false blocks before enforcement.

## 7. Anti-overfit gate

All retained runtime proposals are either **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** or **CONFIG (settings/JSON only)**. They exploit stable operating-system and language boundaries: typed arguments, native parsing, AST summaries, and equality checks. They do not attempt to out-reason an improving model with a parallel reasoning scaffold.

The proposal remains minimal in three ways:

- It removes a representation problem for common calls instead of adding a repair agent.
- It uses native parsers and one tiny recorder rather than emulating shells.
- It declines to certify dynamic programs instead of building a second runtime.

The only potentially expanding element is multi-dialect AST summarization. Keep it shallow and invariant-driven. If PowerShell or `cmd` extraction cannot remain under the small-build boundary, ship syntax preflight plus structured direct execution first; do not grow a universal shell analyzer. It is **likely (55-80%)**, based on the narrow schema and existing native parser APIs, that a useful first implementation fits the stated small-build bound per integration surface. ## 9. Bottom line

The experimental-design borrow is valid, but its value is not “treat every command like a clinical trial.” The transferable mechanism is **prospective intent plus a control that traverses the same causal path**. Applied narrowly, it yields a practical tool design: represent direct calls as typed argument vectors; require an explicit dialect and intent contract for true shell programs; compare native parse structure with declared invariants; validate both transport and detector with concurrent positive/negative controls; and return an intent/observation diff that forbids unchanged retries.

This design directly addresses the class represented by unmatched-quote EOF failures and extends coverage to some syntactically valid argument-boundary defects that a parser alone misses. It also states its boundary honestly: it cannot infer a correct goal from an incorrect declaration, cannot statically certify arbitrary dynamic shell code, and should report those cases as not verifiable. That boundedness is why the analogy transfers instead of becoming decorative metaphor.
