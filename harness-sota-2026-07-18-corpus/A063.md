# A063 — Coherence audit of `~/.claude/rules/rust/patterns.md`

## Executive result

The audited file is not a coherent enforceable Rust contract. It mixes examples with unconditional architectural commands, duplicates the common rules with different interfaces, contradicts the common API-envelope shape, and points to a `rust-patterns` skill that cannot be inspected in this bundle and is absent from the supplied router index. Its only crisp code-level invariant—no wildcard arm for business-critical enums—is not checked by the configured hook path. The configured per-edit validator explicitly skips `.rs` files.

## Collision C1 — repository contract is duplicated with a different CRUD vocabulary

**Class: REDUNDANCY**

### Artifact A: Rust rule

- `B/claude/rules/rust/patterns.md:9-11`: “Repository Pattern with Traits” and “Encapsulate data access behind a trait.”
- `B/claude/rules/rust/patterns.md:14-19`: the purported standard trait exposes `find_by_id`, `find_all`, `save`, and `delete`.
- `B/claude/rules/rust/patterns.md:22`: storage-specific concrete implementations.

### Artifact B: common rule

- `B/claude/rules/common/patterns.md:35-43`: repository pattern, abstract interface, storage-specific implementations, and mockability.
- In particular, `B/claude/rules/common/patterns.md:40` declares the standard operations to be `findAll`, `findById`, `create`, `update`, and `delete`.

### Why this collides

The conceptual instruction is duplicated on the same `.rs` scope. The examples disagree about whether the normative write surface is `save` or the separate `create` and `update` operations. That difference matters: an agent applying both cannot know whether `save` is an upsert, insert-only operation, or a replacement for two operations. Neither artifact conditions its interface on domain semantics, existing repository conventions, sync versus async I/O, or the selected persistence library.

The Rust rule wins under `B/claude/rules/README.md:93-104`, but the precedence policy only selects a winner; it does not remove the contradictory vocabulary from model context. `AGENTS.md` section 10 adds no further resolution because these are two first-party rule files, a tier it does not name.

### Specific resolution

**Proposal — NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it):** keep the common file as a one-sentence, explicitly optional decision heuristic and make the Rust file the sole Rust example. Replace “standard operations” with “operations follow domain semantics and existing project conventions”; label the shown trait illustrative, not mandatory. Avoid prescribing CRUD when a repository is not already part of the project architecture.

It is **very likely (80-90%)**, based on the duplicate same-scope text and the differing operation names at the cited lines, that this consolidation will reduce ambiguous architecture generation without losing useful Rust syntax guidance. The residual uncertainty is how Claude weights two simultaneously loaded rule files; a controlled prompt evaluation comparing 20 Rust repository tasks before/after would settle the effect size.

Anti-overfit gate: pass. This is a text change on the existing native rule bus; it adds no component.

## Collision C2 — API response contracts require incompatible shapes

**Class: CONTRADICTION**

### Artifact A: Rust rule

- `B/claude/rules/rust/patterns.md:151-164`: “Consistent API responses using a generic enum.”
- The enum is internally tagged by `status`; the `Ok` variant contains only `data`, and the `Error` variant contains only `message` (`B/claude/rules/rust/patterns.md:156-163`).

### Artifact B: common rule

- `B/claude/rules/common/patterns.md:45-51`: all API responses must include status/success, a nullable data payload, a nullable error-message field, and pagination metadata (`total`, `page`, `limit`) for paginated responses.

### Why this collides

The Rust enum represents success and failure as mutually exclusive variant fields. It cannot simultaneously satisfy the common requirement that every envelope include both nullable `data` and nullable error fields. It also has no pagination metadata field or paginated variant. This is a structural contradiction, not harmless elaboration.

The Rust rule wins under `B/claude/rules/README.md:93-104`. `AGENTS.md` section 10 does not rank these two first-party rules, so the narrower README is the only stated resolver. Selecting the Rust rule still leaves the common mandatory shape misleading for Rust turns.

### Specific resolution

**Proposal — NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it):** remove the universal wire-format mandate from both global rule files. Replace it with: preserve the repository/API specification's existing response contract; use a typed success/error representation only when the protocol does not already define one; model pagination in the success payload or protocol-specific metadata. Keep the enum only as an explicitly non-normative Serde illustration.

This is **almost certain (90-99%)**, based on the mutually exclusive enum fields versus the four-field common requirement, to eliminate the direct contradiction. Whether the enum remains a useful default is **roughly even (45-55%)**, because no project/API evidence is present; a benchmark across representative Axum/Actix library and application tasks would settle that design question.

Anti-overfit gate: pass. Existing native rule bus only.

## Collision C3 — absolute immutability versus the consuming builder mutation

**Class: CONTRADICTION**

### Artifact A: Rust rule

- `B/claude/rules/rust/patterns.md:88-90`: use a builder for structs with many optional parameters.
- `B/claude/rules/rust/patterns.md:115-119`: the setter takes `mut self`, assigns `self.max_connections = n`, and returns `self`.

### Artifact B: common and Rust coding-style rules

- `B/claude/rules/common/coding-style.md:23-33`: “ALWAYS create new objects, NEVER mutate existing ones.”
- `B/claude/rules/common/coding-style.md:61-68`: completion checklist includes “No mutation.”
- The Rust-specific coding-style rule instead permits mutation when required and merely prefers returning new values (`B/claude/rules/rust/coding-style.md:16-22`).

### Why this collides

The builder mutates its owned `self` before returning it. That is idiomatic value-consuming construction and does not mutate an object observable through an alias, but it still violates the common rule's literal “NEVER” and its literal completion checklist. The Rust coding-style rule already expresses the nuanced rule, so the absolute common instruction is the defective artifact.

The language-specific rules win under `B/claude/rules/README.md:93-104`. This collision is therefore precedence-resolved for execution, but the common wording remains internally false and unnecessarily consumes instruction budget. `AGENTS.md` section 10 does not add a ranking for these rule files.

### Specific resolution

**Proposal — NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it):** rewrite the common principle as “avoid unnecessary or externally observable mutation; prefer value-returning updates where idiomatic.” Delete the absolute “No mutation” checkbox. In the Rust builder, add one sentence that `mut self` consumes the builder and does not mutate a shared value.

It is **almost certain (90-99%)**, based on the literal assignment at Rust lines 115-119 and the common “NEVER” at lines 23-25, that this rewrite removes the textual contradiction while preserving the intended concurrency/aliasing benefit.

Anti-overfit gate: pass. Existing native rule bus only.

## Collision C4 — newtype invariant advice is duplicated in two Rust rules

**Class: REDUNDANCY**

### Artifact A: Rust patterns

- `B/claude/rules/rust/patterns.md:48-60`: distinct `UserId` and `OrderId` wrappers prevent argument swaps.

### Artifact B: Rust security

- `B/claude/rules/rust/security.md:45-50`: validate at boundaries, use the type system to enforce invariants via the newtype pattern, and “parse, don't validate.”
- `B/claude/rules/rust/security.md:52-73`: a validated `Email(String)` newtype example.

### Why this collides

Both files match `**/*.rs` (`B/claude/rules/rust/patterns.md:1-4`; `B/claude/rules/rust/security.md:1-4`) and both teach newtypes as the way to prevent invalid or confused values. The security file adds validated construction while the patterns file exposes tuple-struct construction directly. They are not logically incompatible for identifier wrappers, but the duplicated instruction blurs an important distinction: nominal argument separation versus construction-time validation.

These are same-level Rust rules. Neither `AGENTS.md` section 10 nor `rules/README.md:93-104` says which Rust file wins, so precedence does not resolve this collision.

### Specific resolution

**Proposal — NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it):** keep nominal newtype mechanics in `patterns.md`; keep boundary parsing and private/validated constructors in `security.md`; cross-link them with one sentence defining the distinction. Remove one full duplicate code block if instruction-budget measurements show both files load together.

It is **likely (55-80%)**, based on the same-scope duplicate examples and their different invariant strength, that separating nominal typing from validated construction will prevent accidental public constructors for validated values. The uncertainty is whether Claude currently conflates the two examples; a prompt suite asking it to implement both IDs and validated email/domain types would settle that.

Anti-overfit gate: pass. Existing native rule bus only.
