# A062 — Coherence audit: `~/.claude/rules/rust/hooks.md`

## Verdict

The Rust hook rule is not an operational contract. It is a six-line recommendation whose three promised PostToolUse actions are not configured, and the only active per-edit checker deliberately and testably skips Rust. The clearest collision is therefore not subtle: `rules/rust/hooks.md:14-16` says Rust edits are formatted, linted, and compilation-checked after editing, while `hooks/per-edit-check/check.py:16,168-169` says `.rs` is skipped because Cargo checking is too heavy. `settings.json:333-342` wires that skipping checker under the user-facing label “Per-edit validation.”

I found five material collision records:

1. one **CONTRADICTION** between the Rust rule and the active per-edit implementation;
2. two **UNENFORCED** promises (the entire three-command policy, plus uncovered mutation paths);
3. one **REDUNDANCY** with an unresolved Clippy severity/cadence difference inside the Rust rules;
4. one **STALE** path-scope promise for `Cargo.toml` that has no corresponding behavior.

There is no evidence in the supplied bundle that any Rust-specific hook enforces an extra Rust check omitted by this rule. This statement is limited to the unpacked bundle, not the Windows subject: the active settings command list and both local/shared dispatcher code were searched, with known-present PostToolUse hooks as controls. Skills cannot be audited from this job node because neither requested skill tree was included in the bundle. I do not infer that those trees are absent on the Windows owner machine.

The measured corpus cannot answer whether owners/agents manually follow the commands. Its hook detector is explicitly marked broken (`inputs/corpus.json:1`, top-level `hooks.DETECTOR_STATUS`), and its retained `tool_usage` and `sessions` rows have no command, edited-path, language, or hook-result fields. The independently supplied live-defect report reaches the same measurement conclusion at `inputs/INPUT-known-harness-defects.md:133-147`. Accordingly, runtime adherence is **UNVERIFIED; the settling experiment is to mine raw transcript Bash/PowerShell command payloads and edited `.rs`/`Cargo.toml` paths, then correlate each mutation with subsequent command receipts, while separately reading the event ledger for a known-positive hook fire**.

## Collision ledger

### C01 — Rust validation is promised but the active hook deliberately skips it

**Class: CONTRADICTION**

**Artifacts and exact lines**

- `claude/rules/rust/hooks.md:10-16`: declares PostToolUse hooks and says `cargo fmt`, `cargo clippy`, and `cargo check` act after Rust edits/changes.
- `claude/hooks/per-edit-check/check.py:2-6`: describes the active hook as a fast per-edit syntax/lint checker.
- `claude/hooks/per-edit-check/check.py:16`: explicitly documents `.rs` as skipped because Cargo check is too heavy per edit.
- `claude/hooks/per-edit-check/check.py:151-170`: dispatch returns `([], False)` for `.rs`.
- `claude/hooks/per-edit-check/test_check.py:283-293`: treats `.rs` as an intentionally silent skipped extension.
- `claude/settings.json:333-342`: registers that checker for `Edit|Write|MultiEdit` as “Per-edit validation.”

**Why this is a collision**

This is not merely absent implementation. The executable artifact contains an explicit design decision opposite to the rule’s cadence: the rule says Cargo checks happen after editing; the checker says Cargo check is too heavy for per-edit and guarantees silence. The black-box invalid-Rust/invalid-JSON control reproduced that distinction.

AGENTS §10 does not resolve policy-versus-hook precedence. Both are owner-level harness artifacts rather than a third-party skill default, and neither is a security non-negotiable.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Replace the single cadence with two explicit stages on the existing PostToolUse/Stop bus:

- R0 after an `.rs` edit: run only a bounded changed-file formatter/syntax-capable action if the repo exposes one, or mark Rust validation as due; never report the silent skip as validation success.
- R1 after a coherent edit batch and before a completion/commit claim: run the repository’s declared Rust verification entrypoint, with Cargo defaults only as fallback. At minimum distinguish format, lint, and compile receipts.
- Change the hook result from silent success on `.rs` to an explicit non-green state such as `unsupported/deferred -> R1 required`; keep ordinary edits non-blocking, consistent with `AGENTS.md:64-70`.
- Add black-box tests for invalid Rust, absent Cargo, workspace Cargo, and a passing minimal crate.

It is **very likely (80-90%)**, based on the existing hook’s explicit “too heavy” decision (`check.py:16,168-169`) and AGENTS’ long-operation rule (`AGENTS.md:41-49`), that tiering is more coherent than three synchronous Cargo commands after every edit. Exact latency and the best debounce boundary are **UNVERIFIED; the settling experiment is to time fmt/check/clippy separately in a disposable copy of every active Rust workspace at cold and warm cache, recording p50/p95 and timeout rates**.

The proposal uses the existing bus and adds no orchestrator, vector memory, durable engine, critic, SaaS, or guardrail framework; it passes the anti-overfit gate.

### C03 — Clippy’s failure threshold and cadence have two same-level definitions

**Class: REDUNDANCY**

## Recommended replacement text and mechanism — UNVERIFIED benchmark-dependent details

The best resolution is replacement of this rule’s vague three bullets, not preservation of their unconditional per-edit cadence. The following contract is deliberately minimal and rides the current bus.

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

6. Operations expected over 60 seconds use existing `longrun`; no new daemon or scheduler.
7. Test invalid/pass `.rs`, invalid/pass `Cargo.toml`, missing toolchain, single crate, workspace, timeout, and every mutation path from C04.
