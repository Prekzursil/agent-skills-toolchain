# F019 — Frontier research: agent observability, tracing, and telemetry standards

**Unit:** F019  
**Research date:** 2026-07-19  
**Scope:** what is actually established, what is merely published, what is hype, and what this specific Claude/Codex harness should adopt.  
**Method:** primary specifications, official documentation, official repositories/issue trackers, and the supplied read-only harness bundle. The 140-unit audit is treated as a claim index, not ground truth. The corpus `hooks` section is treated as no data because it explicitly says its detector failed a known-positive control (`/local_disk0/codexwork/bundle/inputs/corpus.json:13261`). Sources first published or materially changed in 2026 are post-cutoff relative to common pretrained-model knowledge and are treated as lower-transfer-confidence frontier evidence even when they are primary; current official status fields and repository state are used only for what they directly establish.

## Executive verdict

There is an established observability substrate, but there is not yet an established end-to-end **agent observability semantic standard**.

The established substrate is:

1. W3C Trace Context for causal correlation across process/protocol boundaries;
2. OpenTelemetry's trace/log/metric data model and stable OTLP transport;
3. ordinary distributed-tracing structure: trace, parent/child spans, span links, events, status, resource identity, and explicit sampling;
4. MCP's finalized convention for propagating W3C `traceparent`, `tracestate`, and `baggage` through `_meta`.

The agent-specific layer is still moving. The new official OpenTelemetry GenAI semantic-conventions repository covers inference, agents, tools, evaluation, and MCP, but its manifest is explicitly `development`; its README still says `Schema URL: TODO`; GitHub reports no published releases. The release absence has two mechanically independent signals: the GitHub release panel says “No releases published,” and a 2026-07-19 `git ls-remote --tags https://github.com/open-telemetry/semantic-conventions-genai.git` returned no refs after the same detector found `v1.41.1`, `v1.42.0`, and `v1.43.0` in the known-present `open-telemetry/semantic-conventions` control. That is publication and active standardization work, not a stable compatibility promise ([official repository](https://github.com/open-telemetry/semantic-conventions-genai), [development manifest](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/model/manifest.yaml)). OpenInference is a useful OTel-compatible ecosystem convention, but its own repository describes it as a complementary convention/plugin set and it remains governed by one vendor-led project, not a cross-industry standards body ([OpenInference repository](https://github.com/Arize-ai/openinference)).

For this harness, the winning move is not a new observability platform. It is a thin, typed causal envelope and outcome join on the already-built hook/ledger bus, plus a bounded native Claude Code OTel canary. The harness already has the expensive pieces: a closed normalized hook schema (`/local_disk0/codexwork/bundle/agents/harness/schemas/hook-event.schema.json:1-56`), an append-only sequence/fsync ledger (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:817-880`), and terminal timing records (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:485-515`). What it lacks is correlation: the terminal record drops session, turn, tool, module, parent, and outcome-receipt identity even though the normalized input has session/turn/tool IDs (`hook-event.schema.json:7-39`).

The highest-value design rule is therefore: **preserve a complete low-cardinality causal skeleton for every lifecycle operation; collect high-risk content only by explicit, bounded, redacted opt-in; join interventions to independently verified outcomes.** A trace that only says a hook or model claimed success is telemetry, not truth.

### What already exists and must be reused

The normalized hook event is schema-versioned and closed, with provider, event, session, turn, tool name/ID/input/result, and agent ID/type/transcript path (`hook-event.schema.json:7-54`). The ledger allocates a monotonically increasing per-ledger sequence, UTC timestamp, optional deduplicated event ID, sanitized additive fields, append, flush, fsync, and state reduction (`ledger.py:841-880`). This is already an event spine. Replacing it with a second event store, graph database, durable workflow runtime, or hosted observability product would duplicate capability and violate the stated anti-overfit gate.

The design must also preserve the distinction between:

* **observation:** a tool or hook emitted a result;
* **decision:** the harness allowed, advised, or blocked;
* **effect:** a file/process/network/external state actually changed;
* **task outcome:** a verifier or owner accepted the result.

This distinction is grounded locally: the known defects show a tool sentinel labeling a successful result as failed by matching `timedout` in a JSON field name whose value was false (`INPUT-known-harness-defects.md:50-68`), and a fabricated orchestrator constraint propagated to roughly 15 agents and drove use of a materially less reliable write path (`INPUT-known-harness-defects.md:151-160`). Self-reported event status therefore cannot be the outcome oracle.

## 1. Established

### 1.1 W3C Trace Context is the stable cross-boundary correlation standard

W3C Trace Context is a W3C Recommendation, published 23 November 2021. It standardizes the `traceparent` and `tracestate` HTTP headers, including a 16-byte trace ID, 8-byte parent/span ID, flags, parsing rules, mutation rules, and privacy/security considerations. Its purpose is explicitly multi-vendor propagation and correlation across distributed components ([W3C Recommendation](https://www.w3.org/TR/trace-context/)). This is standards-track, consensus-backed, and implementation-oriented—not an agent-observability marketing schema.

Established implication: use W3C-format IDs and propagation at process/MCP boundaries. Do not invent UUID-shaped “trace IDs” with incompatible semantics, and do not put arbitrary user or task content into trace context.

W3C Baggage standardizes a separate distributed key/value context carrier ([W3C Baggage](https://www.w3.org/TR/baggage/)). Baggage is not a substitute for span attributes or a secret-bearing state channel; it propagates downstream and therefore expands disclosure and cardinality risk.

### 1.2 OTLP is stable for traces, metrics, and logs

The OpenTelemetry Protocol specification explicitly marks OTLP stable for trace, metric, and log signals, while profiles remain development. It defines protobuf payloads and gRPC/HTTP export behavior between telemetry sources, intermediaries, and backends ([OTLP specification](https://opentelemetry.io/docs/specs/otlp/)). This establishes a vendor-neutral export format. It does **not** establish that every GenAI/agent attribute name carried inside a span is stable.

OpenTelemetry's specification status page separately tracks API, SDK, data-model, and implementation maturity by signal ([status summary](https://opentelemetry.io/docs/specs/status/)). “Uses OTel” is therefore too coarse: an implementation can use a stable transport while emitting development semantic conventions.

### 1.3 Conventional distributed-tracing structure is established and sufficient for the causal skeleton

Trace IDs, span IDs, parent IDs, start/end times, status/error fields, events, and links are established OTel concepts. Parent/child describes execution nesting; links associate related operations that do not have a single nesting relationship. This is enough to represent a prompt/turn, agent invocation, tool execution, hook decision, retry attempt, subagent handoff, and verifier receipt without inventing an “agent graph database” ([OpenTelemetry specification overview](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/overview.md)).

Sampling is also established as a necessary cost control, but no single universal sampling algorithm is established. The W3C recommendation explicitly describes probability, delayed, and deferred decisions and notes the tradeoff between broken traces and prohibitive full recording ([W3C Trace Context sampled flag](https://www.w3.org/TR/trace-context/#sampled-flag)); OpenTelemetry documents head and tail sampling separately ([OpenTelemetry sampling](https://opentelemetry.io/docs/concepts/sampling/)). For a local harness, this supports an unsampled minimal skeleton plus sampled detail; it does not justify silently dropping error/block/receipt records.

### 1.4 MCP trace-context propagation is now finalized and has multiple implementation signals

MCP SEP-414 is Final Standards Track. It specifies `traceparent`, `tracestate`, and `baggage` as unprefixed `_meta` keys using W3C formats and lists existing C#, Python, OpenInference, Envoy AI Gateway, Logfire, and ToolHive implementations ([MCP SEP-414](https://modelcontextprotocol.io/seps/414-request-meta)). This meets a stronger “established” test than a lone proposal: final protocol decision plus multiple independently named implementations.

This matters directly to a harness that touched 93 MCP servers. It gives an interoperable correlation carrier for a tool call even when the MCP client, server, and telemetry backend are different products.

### 1.5 MCP-native logging is a useful negative result: publication did not equal establishment

MCP did publish structured server-to-client logging with RFC 5424 severity, `logging/setLevel`, and `notifications/message` ([MCP logging specification](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/logging)). But Final Standards Track SEP-2577 now deprecates that feature, citing low adoption and overlap with mature stderr/OpenTelemetry infrastructure ([MCP SEP-2577](https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging)). This is unusually strong evidence for the anti-overfit gate: do not build a second protocol-level logging plane merely because an agent protocol once exposed one.

### 1.6 Native vendor traces are established product capabilities, not common standards

Claude Code officially exports OTel metrics, log/events, and beta traces. Its current trace model links prompts to API requests and tool executions, uses W3C `TRACEPARENT`, redacts prompt/tool content by default, and provides separate opt-ins for tool details and content. It also documents `hook_execution_complete`, MCP connection events, tool duration, permission wait, execution success/error, token/cost metrics, and cardinality controls ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)). These are real native capabilities.

OpenAI's Agents SDK likewise automatically traces runner tasks, turns, agents, generations, tools, guardrails, and handoffs, with trace/group/span/parent IDs and custom processors. It defaults to including sensitive generation and function data unless configured otherwise, and its default exporter targets OpenAI's backend ([OpenAI Agents SDK tracing](https://openai.github.io/openai-agents-python/tracing/)). This demonstrates convergence on a trace/span hierarchy, but the proprietary span data and export defaults are not a portable standard.

Established implication: treat provider traces as adapters into the harness evidence model, not as the harness's source of truth.

### 1.7 Privacy and cardinality controls are first-class observability requirements

OpenTelemetry publishes explicit guidance for handling sensitive telemetry, including data minimization, filtering, redaction, hashing, and access control ([OTel sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/)). Claude Code separately warns that tool details may contain commands, paths, URLs, and arguments; full content can include raw file contents and tool output, and raw API bodies contain the conversation history ([Claude monitoring security notes](https://code.claude.com/docs/en/monitoring-usage)).

This is established enough to reject “capture everything and decide later.” In this owner’s corpus, 10.62 GB of transcripts already shows that raw payload retention is operationally expensive; it also makes repeated whole-transcript Stop scans pathological (`/local_disk0/codexwork/bundle/inputs/audit-findings/A07.md:15-21`).

## 2. Promising but unproven

### 2.1 OpenTelemetry GenAI semantic conventions

The official GenAI repository now models client inference, agent creation/invocation, tool execution, evaluation events, MCP spans/metrics, and provider-specific fields ([repository](https://github.com/open-telemetry/semantic-conventions-genai)). Its direction is **likely (55-80%)** to become the best long-term portable vocabulary because it sits under the OpenTelemetry organization, extends the stable OTel model, includes MCP, and ships reference compliance reports. The lower bound is warranted because the repository manifest is `development`, the README's schema URL remains TODO, breaking-change fragments are active, and GitHub shows no published release ([manifest](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/model/manifest.yaml), [repository release panel](https://github.com/open-telemetry/semantic-conventions-genai)).

It is **very likely (80-90%)** that pinning one development version behind a local mapping boundary will reduce later migration cost; evidence is the repository's explicit dependency/schema machinery and the previous GenAI transition guidance requiring stability opt-in rather than silently changing emitted conventions ([GenAI metrics transition guidance](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-metrics/)). It is **unlikely (20-45%)** that copying the current attribute set directly into the harness's canonical schema without a version field will remain migration-free; evidence is the active development status and breaking-change queue. The experiment that would settle compatibility is a three-exporter fixture that emits one agent/tool/MCP trace and compares accepted fields across two consecutive GenAI convention versions plus the chosen local reader.

### 2.2 OpenInference as an interoperability bridge

OpenInference provides OTel-compatible conventions and instrumentation across multiple languages/frameworks and says its output can go to any OTel-compatible collector ([OpenInference repository](https://github.com/Arize-ai/openinference)). It is **likely (55-80%)** to remain useful as an adapter when a library already emits it, supported by the breadth of instrumentations and OTLP compatibility. It is **unlikely (20-45%)** to be the right canonical schema for this harness, because it is a parallel convention family while the official OTel GenAI work now covers agents, tools, evaluation, and MCP. The settling experiment is schema-diff and query-portability testing on identical Claude/Codex/MCP traces emitted as OpenInference and pinned OTel GenAI.

Recommendation consequence: accept OpenInference at an import/export edge if encountered; do not rewrite the local ledger around it.

### 2.3 Automatic trace diagnosis and LLM-as-judge observability

The TRAIL benchmark contributes 148 human-annotated real agent traces and a failure taxonomy, which is useful research infrastructure. Its strongest evaluated long-context model achieved only 11% trace-debugging accuracy ([TRAIL paper](https://arxiv.org/abs/2505.08638)). It is **likely (55-80%)** that deterministic fingerprints plus structured causal joins will outperform a free-form judge on this harness's known repeated errors, because 5,692 existing fingerprints and exact retry loops provide direct, low-ambiguity signals while TRAIL demonstrates poor general trace-debugging accuracy. The settling experiment is a blinded sample of 100 owner-corrected failures comparing exact fingerprint/receipt rules, an LLM judge, and their combination on step localization and false accusations.

Newer projects such as AgentTelemetry, AgentTrace, AgentRx, and trace-evaluation frameworks are promising research but lower-confidence for this owner until independently replicated on long coding-agent traces. It is **roughly even (45-55%)** that their fault-localization gains transfer to this harness; evidence for promise is their released benchmark/tooling claims, while evidence against immediate adoption is recency, small or self-constructed datasets, and the mismatch between benchmark traces and this 10.62-GB Windows/Claude/Codex corpus ([AgentTelemetry OpenReview entry](https://openreview.net/forum?id=owdmAYFk6k), [AgentRx project description](https://www.microsoft.com/en-us/research/blog/systematic-debugging-for-ai-agents-introducing-the-agentrx-framework/)). The settling experiment is frozen, owner-labeled replay on the harness’s 2,268 correction candidates with exact model/version/budget and a deterministic baseline.

### 2.4 Causal graphs reconstructed from spans

Explicit parent IDs, tool-call IDs, subagent handoff IDs, `derived_from` receipts, and span links are **very likely (80-90%)** to improve blast-radius investigation because the local terminal stream presently discards those join keys while the ledger already supports additive provenance fields (`ledger.py:860-866`), and W3C/OTel make the identifiers interoperable. This does not mean a graph database is needed.

It is **unlikely (20-45%)** that temporal parent/child structure alone proves semantic causality. A parent span shows execution context, not that its content caused a later wrong decision; shared state, stale memory, owner intervention, and external side effects can be omitted. The settling experiment is a labeled set of failures with known causal edges, scored separately for structural reachability and actual root-cause precision.

### 2.5 Native Claude Code beta traces

Native traces are **very likely (80-90%)** to expose tool/API/permission wall time more accurately than the current internal dispatcher timer, because official docs define tool duration as wall-clock including permission wait/execution, while the local timer begins inside the imported dispatcher (`dispatcher.py:251`; [Claude monitoring](https://code.claude.com/docs/en/monitoring-usage)). It is **roughly even (45-55%)** that detailed hook spans are usable on the owner’s installed Windows build without special backend assumptions: the documentation labels tracing beta and describes extra gating for detailed hook spans, while no live effective telemetry configuration or trace was available in this Linux bundle. The settling experiment is the disposable canary in Recommendation 5.

## 3. Hype, and the tell that gives it away

### 3.1 “Full-fidelity observability” that captures only model and tool messages

**Tell:** the product diagram ends at emitted messages and does not join to an independent state/receipt/verifier signal.

Calling that “full fidelity” is **very likely (80-90%)** misleading for this harness. Evidence: the local tool sentinel produced a false failure on a successful result, and an orchestrator-authored false constraint propagated to many agents (`INPUT-known-harness-defects.md:50-68,151-160`). A perfectly recorded false statement remains false. Required counter-evidence is an outcome join showing that claimed mutations, tests, external sends, and final acceptance occurred.

### 3.2 “Automatic root cause” from an LLM reading the trace

**Tell:** the evidence is a few demonstrations, a self-created synthetic dataset, or judge agreement—not independently labeled production failures with calibrated abstention and false-accusation cost.

Unqualified root-cause claims are **very likely (80-90%)** ahead of evidence. TRAIL's best reported result is 11% on 148 annotated traces ([TRAIL](https://arxiv.org/abs/2505.08638)). A useful assistant may rank suspects; it should not overwrite deterministic error fingerprints or verified receipts. “Explanation generated” is not “cause established.”

### 3.3 “Causal graph” where every edge is merely timestamp order or span parentage

**Tell:** no edge type distinguishes execution nesting, data derivation, control decision, shared-state read, or verified effect.

The causal label is **likely (55-80%)** overstated because W3C/OTel parentage describes trace position, not counterfactual causation. The harness should name edges (`parent`, `link`, `derived_from`, `supersedes`, `verified_by`) and reserve “cause” for a supported diagnosis.

### 3.4 “Open standard” meaning “exports OTLP”

**Tell:** transport is standard, but attribute names, span hierarchy, IDs, and privacy defaults are proprietary or undocumented.

This conflation is **almost certain (90-99%)** to cause portability surprises; evidence is that OTLP is stable while the official GenAI semantics remain development, and OpenAI/Claude expose different native span vocabularies ([OTLP](https://opentelemetry.io/docs/specs/otlp/), [OTel GenAI repository](https://github.com/open-telemetry/semantic-conventions-genai), [OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/), [Claude monitoring](https://code.claude.com/docs/en/monitoring-usage)). Ask two separate questions: “Can it transport OTLP?” and “Which versioned semantic convention does it emit?”

### 3.5 “Replay” that is only a trace viewer

**Tell:** it cannot reconstruct exact tool versions, filesystem/repository snapshot, environment, approvals, network responses, model/version, sampling seed where available, and side effects.

Calling a viewer replay is **very likely (80-90%)** misleading for coding agents. A trace can support analysis or fixture construction; deterministic re-execution needs captured dependencies and controlled side effects. The harness should say “trace replay” only for synthetic/disposable fixtures, never for reissuing historical side effects.

### 3.6 “Capture all prompts and chain-of-thought for safety”

**Tell:** content collection is default-on, retention is indefinite, and the pitch lacks a threat model, access boundary, or measured diagnostic lift.

This is **very likely (80-90%)** net harmful here because tool output can contain source, credentials, URLs, and personal data; official OTel and Claude docs explicitly require minimization/redaction controls. It also recreates the transcript-size pathology already measured. Extended thinking is not a dependable or necessary operational signal; typed decisions, actions, results, and receipts are.

### 3.7 Dashboard count as evidence of maturity

**Tell:** screenshots, stars, span counts, and integration logos replace retention tests, schema migration tests, dropped-event accounting, overhead measurements, and incident-resolution outcomes.

A dashboard-only evaluation is **likely (55-80%)** to optimize visibility rather than reliability. MCP's structured logging feature was fully specified yet later deprecated for low adoption and overlap ([SEP-2577](https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging)); publication and UI polish do not prove a mechanism earns its cost.

## 4. Specific things this harness should adopt

### Recommendation 1 — UNVERIFIED: add a W3C-compatible causal envelope to the existing normalized event and terminal record

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add schema-versioned, sanitized fields to the existing event/terminal shapes:

* `trace_id` (32 lowercase hex), `span_id` (16 lowercase hex), optional `parent_span_id`;
* `event_id` (stable dedupe identity), `ts_wall`, `duration_ms_monotonic`;
* `session_id`, `turn_id`, `tool_call_id`, `agent_id`, `provider`;
* `origin` enum (`host`, `hook`, `agent`, `tool`, `mcp`, `verifier`, `owner`);
* `operation` low-cardinality enum and `outcome` enum;
* typed `links[]` for non-parent associations, capped and ID-only.

Map provider IDs into these fields; never replace an available native ID with a content hash. Generate W3C IDs only at roots/boundaries that lack one. Keep the existing ledger sequence because ordering and correlation solve different problems.

**Confidence: very likely (80-90%)** to deliver high diagnostic value. Evidence: the upstream schema already carries session/turn/tool IDs (`hook-event.schema.json:7-39`), terminal records discard them (`dispatcher.py:496-507`), MCP SEP-414 standardizes W3C propagation, and the ledger accepts sanitized additive fields (`ledger.py:860-866`). **UNVERIFIED:** exact native IDs available on every Claude and Codex hook event; settle with one captured, redacted fixture for every registered event on each provider before making any field required.

**Anti-overfit gate:** passes. It extends the existing schema/ledger and introduces no store, daemon, queue, graph database, orchestration runtime, or SaaS.

### Recommendation 2 — UNVERIFIED: measure the host envelope and each module/check, not only dispatcher interior time

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Record both host-observed start/end duration and internal module timings. At minimum emit `queue_or_startup_ms`, `dispatch_ms`, `module_ms`, `permission_wait_ms` when native, `tool_execution_ms`, and `export_ms` when measurable. Name missing phases `unknown`; do not back-calculate them as zero. Store one terminal event per dispatch and bounded child timing events only for slow/error/block paths.

**Confidence: very likely (80-90%)** to correct prioritization. Evidence: source proves the current timer starts inside `dispatch()` (`dispatcher.py:251`), while audit A07 provides an independent native-host timing versus import-timing discrepancy (`A07.md:39-45`). The benefit magnitude is **UNVERIFIED** until a seven-day before/after host trace records p50/p95/p99 under ordinary and audit-concurrency workloads.

**Anti-overfit gate:** passes. This is instrumentation in the current dispatcher, not a parallel tracer runtime.

### Recommendation 3 — UNVERIFIED: make intervention-to-outcome joins the primary harness observability feature

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For every advise/block/rewrite/retry/quarantine event, emit an `intervention_id`; later attach one independently observable outcome:

* `accepted`, `ignored`, `overridden_by_owner`, or `unknown`;
* `verified_by` receipt/test/mutation/event ID;
* `same_error_recurred` with fingerprint ID;
* `task_terminal` only when an existing verifier/receipt establishes it;
* `false_positive_label` only from owner correction or deterministic contradiction, never inferred from silence.

No trained critic is required. Exact fingerprints, tool status, mutation receipts, test receipts, and owner corrections are enough for the first version.

**Confidence: very likely (80-90%)** to be more useful than richer raw spans. Evidence: audit D27 traces the open-loop claim to the shadow and terminal producer schemas (`/local_disk0/codexwork/bundle/inputs/audit-findings/D27.md:1-13`), the local terminal source independently confirms the missing correlation (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:485-513`), and the known defects show that detector outputs can be wrong. The exact percentage of interventions that can be automatically labeled is **UNVERIFIED**; settle by joining a stratified 500-event week against existing receipts and reporting coverage, unknown rate, precision, and owner-disagreement rate.

**Anti-overfit gate:** passes. It uses the existing ledger/receipt/fingerprint bus and explicitly avoids a trained critic, guardrail framework, and observability SaaS.

### Recommendation 4 — UNVERIFIED: use a two-tier retention contract: complete skeleton, sampled detail

**Tag: CONFIG (settings/JSON only).**

Define a versioned telemetry policy:

* retain 100% of low-cardinality lifecycle skeletons, errors, blocks, permission decisions, retries, hook failures/timeouts, MCP connection failures, owner corrections, and verification receipts;
* deterministically sample ordinary successful detail by stable trace hash;
* default raw prompts, tool input/output bodies, source contents, full shell commands, secrets, emails/account IDs, and arbitrary baggage to **off**;
* store normalized error fingerprints and content hashes instead of raw bodies where diagnostic value survives;
* cap attribute length, array count, link count, and retention days;
* put schema version, sampling decision, redaction version, and truncation indicator on every retained event.

**Confidence: very likely (80-90%)** to preserve corpus-level reliability analysis while controlling privacy and volume. Evidence: W3C/OTel explicitly recognize sampling tradeoffs; Claude offers separate detail/content gates; this corpus already derives useful error fingerprints without requiring all raw payloads. The optimum success-detail sample rate is **UNVERIFIED**; settle by replaying current corpus queries against 1%, 5%, 10%, and 100% deterministic samples and measuring confidence intervals plus missed rare fingerprints.

**Anti-overfit gate:** passes. This is policy on the existing sink, not tail-sampling infrastructure or a Collector deployment.

### Recommendation 5 — UNVERIFIED: run a bounded native Claude Code OTel canary, then enable only the signals that close measured gaps

**Tag: NATIVE (Claude Code already does this; we just enable it).**

In a disposable, non-sensitive session, enable native metrics/events and beta traces with content capture off. Exercise one known-success tool, one known-failure tool, one hook that allows, one hook that blocks in a safe fixture, one MCP connection success/failure, one subagent, and one permission wait. Export only to a disposable local test endpoint or console capture isolated from the normal interactive stream. Compare native trace IDs, durations, hook labels, tool/MCP outcomes, and dropped fields against the local causal envelope. Do not enable `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_CONTENT`, or raw API bodies.

Promote native logs/metrics only if the canary provides fields the ledger cannot get more cheaply and measured overhead is acceptable. Treat beta trace/hook attributes as adapter input, not canonical schema.

**Confidence: likely (55-80%)** that the canary will close the transcript hook-visibility and host-wall-time gaps. Evidence: official Claude docs list `hook_execution_complete`, tool spans, MCP connection events, W3C propagation, and wall duration; the known defect shows those signals are absent from transcript mining. **UNVERIFIED:** installed-version feature availability, exact hook-span gates, Windows behavior, exporter overhead, and whether a safe local receiver already exists. Settle with the named canary and two detector controls: prove the capture finds the known-success tool and known-fired hook before interpreting any zero count.
