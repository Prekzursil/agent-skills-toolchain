# H02 — Reading the moment: adaptive terse-vs-thorough communication

## Executive answer

The central finding is that **prompt length is not response-length intent**. The owner’s short messages frequently encode *interaction mode*—continue executing, repair a mistake, report status, or obey an exact output contract—while long messages often encode a durable mission whose next reply still ought to be compact. The harness must infer five separate variables and only then select an answer envelope:

1. **literal output contract** (`ONLY`, `quickly`, `in detail`, `describe`, `briefly`);
2. **speech act / task phase** (execute, status, explain, decide, hand off, repair);
3. **epistemic and consequence risk** (routine receipt versus uncertain or irreversible claim);
4. **owner attention state** (active rapid steering versus a natural breakpoint);
5. **domain expertise** (how much scaffolding is useful, independent of length).

The inference order is important. An explicit output contract wins. Task phase comes next. Risk can force evidence but not filler. Learned per-mode preference is a prior, and raw word count is only the last tie-breaker. I am **very likely (80-90%)** that this hierarchy will outperform the current ≤4-word proxy because (a) the local corpus contains short continuation/repair commands that do not specify answer length, (b) the current code explicitly equates a ≤4-word prompt with wanting less chatter, and (c) response-length research finds that length preference is query-context dependent. The settling experiment is Finding 6’s silent, pre-registered, next-turn evaluation.

The design adds **zero hooks**. BUILD-SMALL changes fold into the existing `UserPromptSubmit` semantic-router/calibrated-silence path; continuity uses the existing event ledger/open-loop/heartbeat surfaces. CONFIG changes are additions to the existing cross-tool behavior contract. Everything remains fail-open. No second orchestrator, vector database, knowledge graph, durable-execution runtime, trained critic, observability SaaS, or guardrail framework is proposed.

## Signal hierarchy to implement

| Priority | Signal | Inference | Counter-signal / safeguard |
|---|---|---|---|
| 1 | Exact form: `ONLY`, `YES/NO`, “one sentence,” “in detail,” “describe for Claude” | Literal response envelope | Never infer beyond the specified turn |
| 2 | Continuation verbs: `proceed`, `continue`, `do it yourself`, `monitor` | Act with minimal conversational interruption | Do not infer shallow execution or omit terminal proof |
| 3 | Status/latency language: `quickly`, `still running`, “what state” | Outcome-first snapshot | Include blocked/manual-input needs even in terse mode |
| 4 | Repair language: `no`, `I meant`, `why did you stop`, corrected fact | Short repair receipt plus changed action | Persist displaced work; do not defend at length |
| 5 | Deliverable is a plan/audit/handoff/research artifact | Thorough artifact, compact chat wrapper | Artifact completeness never licenses chat spam |
| 6 | High uncertainty, high consequence, destructive action, disagreement | Evidence-rich but tightly structured | Length is not evidence; cite external receipts |
| 7 | Dense technical identifiers and correct domain vocabulary | High expertise; omit elementary exposition | Expertise does not imply preference for terse output |
| 8 | Prompt word count, punctuation, message cadence, hour | Weak attention-state tie-breaker only | Never override priorities 1-7 |

## Findings — inferred-surprise first

### 1. Replace “short prompt → short answer” with an interaction-mode envelope

- **improvement:** Introduce a five-field `response_envelope`: `mode`, `length`, `evidence_depth`, `interrupt_policy`, and `thread_receipt`. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold it into the existing semantic-router `UserPromptSubmit` check; it is not a seventh hook.
- **what it is:** A deterministic first-pass classifier gives explicit phrases precedence, then derives `mode ∈ {execute,status,explain,decision,handoff,repair}`. The injected context is one line, for example: `[response-envelope mode=execute length=compact evidence=terminal interrupt=defer thread_receipt=on]`. Raw token count can break a tie but cannot choose the mode. Every exception returns no envelope and exit 0, preserving fail-open behavior.
- **why-inferred:** The current implementation explicitly treats ≤4 words as “the user wants less chatter” (`calibrated_silence.py:289-297`), yet corpus examples show short messages whose primary content is continuity or repair: “why did you stop?” (`corpus.json:12251-12254`, again at `12359-12362`), “I meant you should do that” (`12227-12230`), and “don’t do commits … proceed with implementation” (`12395-12398`). Conversely, the owner explicitly requests a detailed handoff at `11987` and exact-text-only responses at `10985-11069`. These are counterexamples to a one-dimensional word-count rule, not estimates of their frequency.
- **how-to-build:** Add `response_envelope.py` beside `semantic-router/route.py`; use an ordered, unit-tested phrase/speech-act table; call it after prompt parsing and before the router’s existing JSON emission; concatenate its compact line with the router’s current context. Reuse `session_id` and store the chosen fields alongside the calibrated-silence ledger row. Do not infer emotion. Do not persist a global “terse user” persona.
- **the EXTERNAL signal that verifies it:** (1) A frozen fixture suite containing the cited short-continuation, exact-output, quick-status, detailed-handoff, and known negative controls must produce the pre-registered envelope; a separately launched fresh-context verifier adjudicates fixture labels. (2) In live use, the next owner turn is scored as `continue`, `expand`, `compress`, `correct`, or `manual_input`; only that later turn updates the policy. Same-context self-review has no vote.
- **SOTA citation:** Bu et al. find that legitimate length preference varies with query context and that context-adaptive length modeling reduces unnecessary verbosity without treating shortness as universally desirable ([NAACL Findings 2025](https://aclanthology.org/2025.findings-naacl.169/)). Horvitz’s mixed-initiative principles frame dialog/intervention as a decision under uncertainty rather than a fixed interface behavior ([CHI 1999](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/)).
- **confidence:** **very likely (80-90%)** — direct code inspection plus mutually incompatible local speech acts and context-adaptive length research support the classifier; the live next-turn experiment above settles owner-specific benefit.
- **value x effort:** **transformative x medium**
- **novelty:** **inferred-surprise**
- **autonomy:** **just-do-it**

### 2. Make terse communication lossless: compress prose, never state

- **improvement:** Require a tiny continuity receipt in every nonterminal compact answer: `Done | Now | Parked(n)`; on terminal answers use `Outcome | Proof | Open(n)`. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This extends the existing event-ledger/open-loop/heartbeat renderer; it does not create a memory system or hook.
- **what it is:** Terse mode becomes a rendering choice, not permission to omit pending work. `Parked(n)` is generated from external ledger/open-loop state and expands only when `n>0`, when a thread changed, or when the user asks. Each item is referenced by stable ID; it can disappear only after a ledger close/supersede event.
- **why-inferred:** The owner repeatedly had to reassert continuation after stopping (`corpus.json:12251-12254,12359-12362`) and explicitly delegated monitoring while asking to be told only when manual input is necessary (`12377-12380`). The local behavior contract already makes event-ledger replay the ground truth across resume/compact/clear (`/local_disk0/codexwork/bundle/claude/AGENTS.md:28-34`), and open-loop resurfacing already caps user-visible items while retaining the store (`open-loops/resurface.py:4-21,69-95`). The opportunity is to make compactness preserve these IDs, not to rebuild continuity.
- **how-to-build:** Add a pure `render_receipt(turn_state, open_loop_ids, max_chars=220)` function to the existing heartbeat/open-loop package. Derive `Done` and `Now` from the event ledger’s latest milestone/goal; derive `Parked` from unresolved IDs. Inject the receipt instruction through the response envelope. If ledger read fails, emit no invented counts and leave normal generation untouched. Append/close remains owned by existing `note.py` and open-loop tools.
- **the EXTERNAL signal that verifies it:** (1) A transcript parser outside the generation context compares every response receipt against the event-ledger projection and fails on a missing, fabricated, or silently vanished ID. (2) A fresh session after forced compaction must reconstruct the same unresolved ID set from SessionStart replay. Completion requires both equality checks, not the agent saying it remembered.
- **SOTA citation:** Interruption research found that early interruptions can make users forget the primary goal ([Cutrell, Czerwinski & Horvitz, INTERACT 2001](https://www.microsoft.com/en-us/research/publication/notification-disruption-and-memory-effects-of-messaging-interruptions-on-memory-and-performance/)). Bounded deferral balances awareness and interruption rather than deleting deferred information ([Achlioptas & Horvitz 2005](https://www.microsoft.com/en-us/research/publication/principles-of-bounded-deferral-for-balancing-information-awareness-with-interruption/)).
- **confidence:** **almost certain (90-99%)** that stable external IDs prevent the specific “terse therefore forgotten” failure class, because the emitted set is mechanically compared with the existing ledger; **likely (55-80%)** that the three-field receipt reduces owner stress, with the live rate of “what happened to X?” corrections as the settling outcome.
- **value x effort:** **transformative x low**
- **novelty:** **inferred-surprise**
- **autonomy:** **just-do-it**

### 3. Defer explanations to task breakpoints, not arbitrary clock intervals

- **improvement:** During active execution, queue nonurgent explanation detail and emit one compact digest at externally observed breakpoints: command terminal state, plan phase transition, failure/pivot, manual-input requirement, or final completion. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold into the existing background-digest/heartbeat checks.
- **what it is:** “Terse now, thorough at the right moment.” The owner sees immediate exceptions and decision needs, while routine tool narration accumulates in an append-only digest. A bounded timer prevents indefinite silence, but task state—not elapsed minutes—is the primary release signal.
- **why-inferred:** The owner asks the agent to monitor autonomously and surface manual input needs (`corpus.json:12377-12380`), asks why work stopped (`12251-12254`), and sometimes explicitly requests a detailed state handoff (`11987`). The existing digest already archives before truncation and surfaces once (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:2-25,138-178`); the heartbeat already distinguishes steady state from noteworthy conditions (`/local_disk0/codexwork/bundle/claude/hooks/heartbeat/heartbeat.py:2-21,150-162`). This proposal changes release policy, not storage.
- **how-to-build:** Extend digest entries with `task_id`, `severity`, and `release_on`; accept terminal markers already mandated by `AGENTS.md:36-39`; heartbeat emits one line for running state and immediately releases failure/manual-input entries. At phase completion, reader groups entries by task, emits outcome/evidence/open-thread counts, archives them, and preserves overflow. Wrap every reader/writer path in the module’s existing fail-open pattern.
- **the EXTERNAL signal that verifies it:** (1) Command/process terminal markers and ledger phase transitions trigger releases in an integration test; wall-clock polling alone cannot pass. (2) The digest archive and live queue are mechanically reconciled so every queued entry is either still pending or archived/surfaced exactly once. A later owner request for status is checked against both files.
- **SOTA citation:** Notifications are less disruptive when relevant to the current task or queued until key operations complete ([Czerwinski, Cutrell & Horvitz 2000](https://www.microsoft.com/en-us/research/publication/instant-messaging-effects-of-relevance-and-timing/)). BusyBody modeled interruption cost from current and recent activity rather than applying one fixed policy ([Horvitz, Koch & Apacible 2004](https://www.microsoft.com/en-us/research/?p=316172)).
- **confidence:** **very likely (80-90%)** — the existing queue/archive and terminal-state convention make the mechanism concrete, and controlled interruption studies support breakpoint timing; owner-specific fatigue reduction remains measured by fewer mid-run dismissals and fewer status requests.
- **value x effort:** **high x medium**
- **novelty:** **inferred-surprise**
- **autonomy:** **just-do-it**

### 4. Allocate words by trust risk, not by how much work the agent performed

- **improvement:** Use a three-level evidence envelope: `receipt` for routine verified actions, `evidence-summary` for uncertain/high-impact conclusions, and `full-audit` only for requested artifacts, disputes, or irreversible/high-stakes decisions. **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Encode this in the existing cross-tool behavior contract and response-envelope phrase table; reuse truth-verify receipts.
- **what it is:** A ten-command task can end in three lines if terminal receipts settle it. A one-sentence high-risk conclusion can require citations, uncertainty, alternatives, and a stop condition. “Thorough” means decision-relevant evidence, not a chronological tool diary.
- **why-inferred:** The owner asks for quick action in one corpus sample (`corpus.json:11291`) and detailed reliability state in another (`11987`); the distinction follows task purpose, not prompt length. Local defects show why prose volume is unsafe as proof: six conclusions were wrong after single unvalidated probes (`INPUT-known-harness-defects.md:111-129`). The owner’s mandated law for this unit likewise rejects same-context self-correction.
- **how-to-build:** Add a contract table: routine+verified → outcome and receipt; uncertain or consequential → claim, calibrated band, two independent external signals, next experiment; artifact/handoff → full evidence. Explicit owner form always overrides. Ban “I checked” as a receipt. A full audit must cite tool output, file line, second model, or owner confirmation.
- **the EXTERNAL signal that verifies it:** (1) `truth-verify`/terminal tool receipts mechanically validate every completion claim. (2) A fresh-context verifier receives only the evidence bundle and must reproduce the verdict; disagreement forces `UNVERIFIED` and names the settling experiment. The original context cannot certify itself.
- **SOTA citation:** Longer LLM explanations increased human confidence even when accuracy did not improve; matching explanation to actual confidence narrowed calibration gaps ([Steyvers et al., Nature Machine Intelligence 2024](https://www.nature.com/articles/s42256-024-00976-7)). NIST emphasizes that trust varies with the task and its risk, not merely system characteristics ([NIST user-trust overview](https://www.nist.gov/news-events/news/2021/05/nist-proposes-method-evaluating-user-trust-artificial-intelligence-systems)).
- **confidence:** **almost certain (90-99%)** that evidence-level gating avoids treating verbosity as proof, because verification is external and the cited experiment directly identifies explanation-length inflation; **likely (55-80%)** that it improves subjective trust calibration for this owner, settled by correction and expand/compress rates.
- **value x effort:** **high x low**
- **novelty:** **inferred-surprise**
- **autonomy:** **just-do-it**

### 5. Infer expertise separately from desired length

- **improvement:** Add a query-local expertise axis (`novice`, `working`, `expert`) that changes terminology and omitted prerequisites without directly changing the token budget. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing project-card/semantic-router context; no new profile database.
- **what it is:** The same owner can be expert in reverse engineering and unfamiliar with a deployment seam. Dense correct identifiers, tool names, offsets, constraints, and direct correction of a mechanism support higher expertise *for that query*. “Nobody told me how” or a request for operational instructions supports more scaffolding for that seam. Confidence decays by domain and session; it is never a permanent persona label.
- **why-inferred:** The corpus includes highly specific tool/offset/task language (`corpus.json:12371-12409`) alongside an explicit statement that the owner did not know how to restart an installed funnel (`12221-12224`). A single global “technical owner” setting would under-explain the latter; using verbosity as a proxy would over-explain the former.
- **how-to-build:** Add a small feature table to the response-envelope classifier: known technical entities used correctly, correction specificity, and prior successful actions raise query-local expertise; explicit “I don’t know how” lowers it for that operation. Inject `expertise=<level>` plus a rule: omit elementary definitions at expert, include prerequisites and exact commands at working/novice, but preserve the independently chosen `length` field. Persist only domain-level evidence with timestamp and source event in basic-memory if the owner explicitly states it; otherwise keep it session-local.
- **the EXTERNAL signal that verifies it:** (1) A fresh-context domain reviewer labels held-out prompts without seeing the classifier output; agreement and confusion-request rates are measured. (2) The next owner turn supplies behavioral evidence: executing the instruction without a “how?” request supports adequacy; correcting elementary exposition or requesting missing setup changes only that domain’s evidence. No same-turn model judgment updates expertise.
- **SOTA citation:** A study of 25,000 Bing Copilot conversations found that expertise misalignment, especially responding below the user’s level on complex tasks, harmed experience and that matched expertise correlated with more engagement ([Palta et al., IJCNLP-AACL 2025](https://aclanthology.org/2025.ijcnlp-short.5/)). LaMP demonstrates gains from retrieving relevant user-history items across multiple personalized tasks rather than relying on a universal response style ([ACL 2024](https://aclanthology.org/2024.acl-long.399/)).
- **confidence:** **very likely (80-90%)** that expertise and verbosity must be separate variables, supported by opposite local domain examples and the large conversational study; **likely (55-80%)** that the proposed lexical features infer the correct level, settled by the held-out labels and next-turn confusion rate.
- **value x effort:** **high x medium**
- **novelty:** **inferred-surprise**
- **autonomy:** **just-do-it**

## Concrete minimal architecture

```text
UserPromptSubmit (existing raw hook)
    |
    +-- semantic-router (existing)
          |
          +-- response_envelope.py (new pure BUILD-SMALL library)
          |     explicit form > mode > risk > expertise > learned prior > word count
          |
          +-- calibrated-silence ledger (extend existing rows)
                chosen envelope + later external reaction

Tool/command/event results (existing buses)
    |
    +-- event ledger / open loops ---- stable Done|Now|Parked receipt
    +-- background digest ----------- defer detail until external breakpoint
    +-- truth-verify receipts -------- evidence floor and completion proof
```

This architecture is deliberately small. It changes one injected context line and two existing ledgers/renderers. It does not make an LLM call in a hook. It does not ask the owner to configure a personality survey. It uses later behavior, execution results, independent validators, and durable state—the external signals permitted by this unit’s law.

## Implementation order and acceptance gates

1. **CONFIG first:** explicit-form precedence, mode templates, and evidence-depth rules. Acceptance: byte/schema fixtures plus a fresh-context reviewer.
2. **BUILD-SMALL envelope classifier:** pure function, frozen fixtures, fail-open injection through semantic-router. Acceptance: known-positive and known-negative controls; no additional raw hook.
3. **BUILD-SMALL lossless receipt:** external ledger projection into `Done|Now|Parked`. Acceptance: transcript-to-ledger set equality before and after forced compaction.
4. **BUILD-SMALL breakpoint digest:** extend existing archive/heartbeat release rules. Acceptance: terminal-event integration tests and live/archive reconciliation.

## Alternatives rejected

- **Always terse:** rejected because it loses evidence, handoff utility, and open threads; local requests explicitly include detailed state transfer (`corpus.json:11987`).
- **Always thorough:** rejected because it taxes attention during autonomous execution and can inflate trust without improving accuracy (Steyvers et al. above).
- **Mirror prompt length:** rejected by the local continuation/repair counterexamples and query-context length research.
- **Ask “how detailed?” every turn:** rejected as a first-class prompt-fatigue regression and contrary to the existing EVPI-gated clarification contract (`AGENTS.md:7-12`).
- **One permanent owner verbosity profile:** rejected because mode and domain vary within one owner; query-local expertise and explicit form are stronger signals.
- **A second model judging every answer:** rejected for latency and because an evaluator’s verbosity bias is not the owner’s preference. A second model is used only as an independent verifier on frozen evidence, never as the reward signal.
- **A new personalization service/vector store:** rejected by the anti-overfit gate. The event ledger, basic-memory, calibrated-silence JSONL, semantic router, and open-loop store already provide the required bus and state.
