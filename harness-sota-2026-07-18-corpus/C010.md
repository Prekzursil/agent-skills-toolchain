# C010 — Context lifecycle: long-horizon drift and goal reinjection

**Unit:** C010  
**Date:** 2026-07-19 (Europe/Bucharest)  
**Scope:** Read-only investigation of the deployed Claude/Codex harness, the pinned corpus, raw
Claude transcripts, the shared harness state, and the canonical basic-memory vault. The only file
written by this unit is this artifact.

## Executive verdict

The goal-reinjection transport is real, active, and frequent. It is **almost certain (90-99%)** that
the deployed unified harness successfully delivers goal text into at least many Claude turns: a
snapshot scan of the real transcript tree found **609 actual `hook_success` attachments** containing
`ACTIVE GOAL (authoritative re-anchor)` in eight parent-session transcripts, while the mechanically
independent shared terminal ledger contained **1,301 successful `goal_reinjection` records** (788
Claude, 513 Codex). The two signals are raw host transcripts and the harness's own terminal sink,
respectively. This is not an inference from the corpus's broken hook detector.

The mechanism nevertheless does **not preserve the original long-horizon goal**. It preserves the
latest qualifying prompt, after prefix-only redaction/truncation. The current store had **728/728
parseable session goals; 630 (86.5%) contained `[TRUNCATED]`**. The raw delivered-anchor snapshot
contained **194/609 truncated anchors (31.9%)**, **49 anchors reduced to `[PATH]` or `do [PATH]`**,
and **21 unmistakably harness/system-shaped anchors** (14 `<task-notification>`, three stop-review
tasks, four `<agent-message>` payloads). The source explains the mechanism: every non-filtered prompt
of at least 12 characters replaces the active goal (`modules.py:1318-1338`), storage keeps at most
500 redacted characters (`ledger.py:1019-1028`), and reinjection simply reads that slot
(`modules.py:1345-1360`).

It is therefore **very likely (80-90%)** that the present lifecycle permits and sometimes amplifies
long-horizon drift, based on four independent observations: destructive latest-prompt overwrite in
source, 86.5% live truncation, delivered malformed/system anchors in transcripts, and a real
long-running session whose anchor changed from a 100-200-agent program to polling/status fragments
and finally `check on progress`. This confidence is about the existence of the failure mode, not its
population incidence.

**UNVERIFIED whether reinjection reduces or increases net task drift in aggregate; the settling
experiment is the prospective shadow A/B described under “Effectiveness experiment.”** There is no
counterfactual in the transcripts, no drift label, and no randomized no-injection/control cohort.
Counting delivery is not measuring behavioral benefit.

The correct design direction is evolution on the existing hook/ledger bus, not replacement with a
second runtime: keep native hook delivery, but store a durable **root objective plus steering
events**, make reinjection cadence lifecycle-based rather than write-tool-based, retain goal head and
tail (or a compact typed envelope), and add an outcome experiment. This passes the anti-overfit gate:
no new daemon, vector database, knowledge graph, durable-execution engine, critic model,
observability SaaS, or guardrail framework is proposed.

## 1. Questions and operational definitions

The unit separates three questions that are easy to conflate:

1. **Transport:** did the hook run and did its `additionalContext` reach a persisted host
   transcript?
2. **Anchor fidelity:** was the injected text a faithful statement of the active long-horizon
   objective rather than a status request, system notification, fork sibling's goal, or truncated
   prefix?
3. **Behavioral effectiveness:** did the injection causally reduce subsequent off-goal actions or
   improve completion?

For this report, “drift” means a material mismatch between the still-open root objective and later
agent behavior. A legitimate user replacement task is not drift. An additive correction, status
request, monitoring instruction, or system notification replacing the only stored root objective is
a **continuity defect** because the harness can no longer distinguish steering from replacement;
whether the agent subsequently goes off-goal is a separate behavioral question.

This distinction matters because the implementation's label, `ACTIVE GOAL (authoritative
re-anchor)`, makes a stronger promise than its data model supports.

## 5. Anchor fidelity results: what does it reinject?

### 5.1 Prefix truncation is the dominant measured defect

Read-only parse at this unit's snapshot:

```text
SESSION_GOALS files 728 parsed 728 bad 0 truncated 630 pct 86.5
short_lt20 15 maxlen 496
```

This reproduces and updates the earlier audit claim in `findings/E03.md:26-32` (then 565/657,
86.0%). Source and state are mechanically independent signals: `ledger.py:1019-1028` applies
`redact_text(..., max_chars=500)`, and current files contain the marker.

The impact is not cosmetic. Owner prompts routinely put output paths, stop conditions, corrections,
and “after X” requirements near the end. Prefix-only retention makes the injected anchor a lossy
summary selected by position, not importance.

### 5.2 “Original goal” is overwritten by routine steering

The module has no root-vs-steering representation. Any non-system prompt of length >=12 becomes the
sole active goal (`modules.py:1326-1338`). A concrete shared-ledger sequence shows system bridge
messages stored as goals at
`C:\Users\Prekzursil\.agents\state\harness\ledger\project-8cca8fd173dd\events.jsonl:1624`,
`:1626`, and `:1628`, followed by the 19-character `continue monitoring` at `:1630`.

One real long-running parent transcript makes the lifecycle visible:

- `30bd50d4-...jsonl:852` injects the broad 100-200-agent objective.
- By line 2,256 the anchor is only `Poll the detached 140-unit codex mega-audit at ~[PATH]`.
- By line 3,655 it has become a quoted choice asking whether to run an audit now or wait.
- By line 6,883 it is `okay go with 60`.
- By line 8,158 it is `check on progress`.

These later prompts may all be legitimate steering. The defect is that the data model cannot retain
them **and** the still-open root completion condition. A re-anchor to `check on progress` is faithful
to the latest prompt but not to the original goal.

### 5.3 Redaction can erase the target

At the 609-delivery snapshot, 49 anchors matched only `[PATH]` or `do [PATH]`. Examples of path-only
goal transitions appear in `30bd50d4-...jsonl:1175` and `:4450`. Redaction is necessary, but replacing
the entire semantic object with `[PATH]` leaves no actionable goal.

It is **likely (55-80%)** that preserving a non-sensitive basename, role label, or typed target
(`artifact_path`, `repo`, `remote_host`) would materially improve these anchors, based on the 49
observed path-only deliveries. Exact privacy/utility trade-offs are **UNVERIFIED; replay the 49 raw
prompts through candidate redactors and have a blinded reviewer score goal recoverability while a
secret fixture suite verifies zero disclosure.**

### 5.4 System and orchestration payloads have become goals

The snapshot contained at least 21 unambiguous system-shaped delivered anchors:

- 14 beginning `<task-notification>`;
- three stop-review task prompts;
- four beginning `<agent-message>`.

Example: `4ac44ee8-...jsonl:15030` injects a killed background-command task notification as the
authoritative goal. Example: `d219bc39-...jsonl:55644` injects a stop-gate review task.

The current source filters only four prefixes (`<task-notification`, `[SYSTEM NOTIFICATION`,
`<system-reminder`, `<local-command`) at `modules.py:1282-1290`. Some observed contamination predates
the current filter, while `<agent-message>`, `<task>`, bridge `<channel ...>`, and other host payloads
remain outside it. Therefore the historical count should not be projected unchanged onto the
current build, but the class is still structurally open.

### 5.5 Fork/session identity is inconsistent

The raw snapshot found 114/609 attachment records where transcript metadata `session_id` differed
from `sessionId`. All 44 fires in `d99b3484-...jsonl`, 33 in `5c615def-...jsonl`, and 29 of 80 in
`dea94f05-...jsonl` were mismatched. At `dea94f05-...jsonl:33`, for example, the attachment's
`session_id` is the parent `09158d9e-...`, while `sessionId` is `dea94f05-...`.

The adapter selects only lowercase `session_id` (`adapters.py:116-127`), and goal isolation hashes
that value (`ledger.py:996-1039`). It is **very likely (80-90%)** that forked sessions can therefore
share the parent's goal/counter identity, based on the metadata mismatch plus the exact adapter/key
path. **UNVERIFIED whether Claude's stdin hook payload itself contains both fields or the extra
`sessionId` is attached only by transcript persistence; capture a redacted hook-input schema from a
disposable fork and compare it to the transcript attachment to settle this.**

### 5.6 Cadence is write-operation cadence, not turn cadence

The contract says “Every N turns,” but the module advances only on
`Bash|PowerShell|Edit|Write|MultiEdit|apply_patch` (`modules.py:1279-1316`). Read-, search-, web-,
MCP-, and monitoring-heavy work can consume arbitrarily many turns without advancing the counter.
This is an exact implementation mismatch, not a statistical inference.

## 6. Does the agent actually drift?

### What can be claimed

The transcripts demonstrate that:

- long sessions carry many different active anchors (for example, 64 deliveries and 29 distinct
  goals in `30bd50d4-...` at the earlier bounded scan);
- corrections such as `you misunderstood me...` became the active goal and were reinjected many
  times in `09158d9e-...`;
- transient status prompts and system payloads replace the root slot;
- the agent continues operating after goal-module failure because failure is fail-open.

These are direct continuity and risk signals. They support the **very likely (80-90%)** conclusion
that drift occurs in some long sessions, but they do not supply a defensible fleet-wide drift rate.

### What cannot be claimed

**UNVERIFIED: a percentage of long sessions that drift.** The settling experiment is to define a
root-objective/steering label schema, blind-label a stratified sample of sessions with >=50 parent
turns, and score each later action against the latest unresolved root plus steering events.

**UNVERIFIED: the causal benefit of the existing injection.** The settling experiment is a
prospective randomized shadow A/B with identical telemetry: current latest-prompt anchor versus
root+steering anchor, measuring owner corrections, reopened requirements, off-goal tool streaks,
and terminal acceptance.

**UNVERIFIED: whether the 609 visible injections were read or acted upon by the model.** The
settling experiment is to add a non-burdensome structured `goal_anchor_id` to context and require no
verbal acknowledgment; subsequent tool/turn receipts should carry the active ID so alignment can be
measured without training the model to parrot the hook.

It would be dishonest to substitute lexical similarity for these labels. Commands can serve a goal
without sharing its words, and a fluent status paragraph can repeat the goal while making no
progress.

## 8. Design recommendations

### R1 — Root objective plus steering log

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Replace the single session-goal value with:

```json
{
  "root_objective": "...",
  "steering": [{"kind":"constraint|status|correction|replacement", "text":"...", "ts":"..."}],
  "completion_state": "open|complete|superseded",
  "source_turn_id": "..."
}
```

Do not infer replacement merely from length. A prompt prefixed `*` is already an explicit scoped
signal in the behavior contract; reuse it as one replacement signal, while explicit phrases such as
“new task”/“we solved that, now” and terminal completion can be conservative additional signals.
Ambiguous follow-ups append steering and preserve the root.

This change is **very likely (80-90%)** to improve anchor fidelity because it directly removes the
observed destructive overwrite while staying on the existing `EventLedger` and hook bus. It does
not claim outcome improvement without R6's experiment.

### R2 — Preserve goal head and tail, with typed critical fields

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Keep a bounded head and tail rather than the first 484 characters only, and extract explicit fields
already present in the unit/fan-out prompt style: objective, constraints, output path, stop
condition, and unit ID. Preserve the full redacted hash so changes are auditable.

It is **very likely (80-90%)** this will reduce loss of late constraints, based on 630/728 live
goals being truncated and the owner's consistent long-form prompt structure. Whether 500, 800, or
1,200 characters is the best budget is **UNVERIFIED; replay the current 728 stored goals plus a
raw-transcript sample through candidate budgets and measure blinded recoverability and hook token
cost.**

### R3 — Advance cadence on parent lifecycle turns

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Count parent `UserPromptSubmit`/assistant turn completion or another existing lifecycle receipt,
not only write-capable tools. Keep delivery on an existing injection-capable hook event. Exclude
subagents and host/system messages with typed origin data rather than an expanding prefix list.

This is **likely (55-80%)** to cover the currently missed research/monitoring lanes because those
lanes are demonstrably tool-heavy but can be write-light; the best cadence is **UNVERIFIED and should
be selected by replaying long sessions for token cost and maximum turns-between-anchor.**

### R4 — Normalize fork identity before goal lookup

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Capture the actual provider hook schema in parent and fork sessions, then choose one canonical
session identity with explicit lineage (`session_id`, `parent_session_id`) rather than silently
reusing a parent ID. Add regression fixtures for fork, resume, clear, compact, and missing ID.

This is **very likely (80-90%)** to prevent cross-fork goal/counter bleed if the stdin schema exposes
a distinct child identifier; that premise is **UNVERIFIED pending the disposable fork schema
capture** named above.

### R5 — Surface continuity degradation once, fail-open

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Retain fail-open execution, but persist sanitized exception class and emit a once-per-session
`HARNESS DEGRADED: goal continuity unavailable` advisory through the current dispatcher/breaker.
Add a correlation ID and host transcript receipt. Do not add a monitoring service.

It is **likely (55-80%)** this will reduce silent operation without creating wallpaper because only
25 goal-module failures occurred in the measured terminal history; cap it at one advisory per
session and expose the rest in terminal state.

### R6 — Effectiveness experiment — UNVERIFIED

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

The recommendation to prefer root+steering over latest-prompt reinjection inherits an unverified
outcome premise. Settle it prospectively:

1. Randomize eligible long sessions at session start into current-anchor and root+steering shadow
   arms; do not change permissions or orchestration.
2. Log redacted anchor ID, root/steering hashes, delivery receipt, turn number, compaction boundary,
   and terminal state.
3. Pre-register outcomes: owner correction rate after turn 25, reopened-requirement count,
   longest off-goal action streak from blinded labels, completion acceptance, time/tool calls per
   accepted task, and false re-anchor rate.
4. Stratify by interactive build, research, monitoring, and multi-agent orchestration; the current
   write-op cadence disproportionately samples build work.
5. Stop or roll back if false re-anchors or user corrections worsen materially.

The experiment is **very likely (80-90%)** to distinguish delivery from benefit because it creates a
counterfactual and records host receipt; it remains lightweight and uses existing state files.

### R7 — Keep PostCompact advice enabled, but feed it the repaired anchor

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Retain `postcompact_reanchor=advise`. Once R1/R2 land, render root objective plus the newest bounded
steering/correction rather than the single lossy goal string. The present five delivered records
prove the route is live; no new mechanism is required.

### R8 — Raise the shared PreToolUse timeout only after latency attribution

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

One 2,598-ms success exceeded the configured 2,000-ms budget, but most successful goal records were
fast (15.23-ms mean). A blanket increase may hide unrelated dispatcher latency. First add per-module
timing/correlation on the existing terminal sink; then raise to a measured percentile if host loss
is confirmed.

It is **roughly even (45-55%)** that increasing the timeout alone improves delivered continuity,
because the over-budget event is certain but host discard is UNVERIFIED; the correlation-ID canary
settles it.

## 9. Anti-overfit gate and rejected alternatives

The recommendations all ride the existing Claude/Codex lifecycle hook, shared dispatcher,
EventLedger, flat JSON/JSONL state, and transcript telemetry.

Rejected:

- **Second orchestration runtime:** adds another source of session/goal identity and violates the
  explicit anti-overfit gate.
- **Vector DB / knowledge graph for goals:** retrieval is not the measured bottleneck; selection and
  overwrite are. Basic-memory already exists for semantic memory.
- **Durable-execution engine:** unnecessary for a root+steering record and lifecycle counter.
- **Trained critic or always-on LLM drift judge:** expensive, difficult to calibrate, and would turn
  a deterministic continuity defect into another probabilistic dependency.
- **Observability SaaS / guardrail framework:** the raw host transcript and terminal JSONL already
  contain enough substrate; they need correlation, not replacement.
- **More prompt prose alone:** cannot repair destructive storage, truncation, session identity, or
  write-only cadence.

## 10. Acceptance tests for the replacement data model

These tests should run on the existing harness test suite and a disposable host canary:

1. Root objective + `continue monitoring` => root remains; steering appends.
2. Root objective + `check on progress` => injected text contains root and status steering.
3. Explicit new-task/reset => old root becomes superseded; new root is active.
4. `<task-notification>`, `<task>`, `<agent-message>`, `<channel source=...>`, local command output,
   stop-hook review prompts => never become owner goals.
5. A 2,000-character prompt with unit ID/output path at the tail => bounded anchor retains those
   fields without secrets.
6. Path-only goal => retains a safe semantic target or refuses to replace a meaningful root.
7. Parent plus fork => distinct counters and goals, explicit lineage.
8. Missing/unknown session ID => no shared fallback goal.
9. Fifty read/search/MCP-heavy parent turns with no writes => cadence still re-anchors.
10. Subagent task => parent goal never injects into child.
11. PostCompact => root plus newest correction is delivered in advise mode.
12. Module exception => operation continues, sanitized failure is recorded, one degraded advisory is
    visible.
13. Correlation ID => every terminal inject can be classified delivered/not-delivered/unknown from
    transcript receipt.
14. Redactor fixture suite => no literal credentials, tokens, full sensitive paths, or private
    coordinates survive.

   misunderstandings and later reinjection, not that reinjection fixed or caused them.
8. **Basic-memory semantic MCP search was unavailable to this unit.** Direct vault search covered
   618 Markdown notes with a known-positive control, but an MCP semantic search might retrieve notes
   lacking literal drift terms. The settling experiment is `search_notes`/`build_context` with
   `goal reinjection long horizon drift` when the connector is exposed.

## 12. Bottom line for the next design/build unit

Do not remove goal reinjection: the existing native hook transport is working and provides a useful
control point. Do not call the current output “the original goal”: it is a lossy, latest-prompt
prefix whose fidelity is measurably poor in this owner's long sessions.

The smallest high-leverage replacement is the **data model**, not the runtime: root objective +
steering/corrections + explicit supersession on the current ledger; lifecycle cadence on the current
hook bus; bounded head/tail or typed critical fields; session lineage; and correlated outcome
measurement. That is ambitious enough to fix the actual failure while remaining minimal enough not
to overfit the next generation of models.
