**Unit:** X117  
**Source field:** reliability engineering (FMEA/FMECA, fault trees, reliability demonstration, diagnostic coverage, redundancy/diversity, common-cause failure)  
**Target problem:** knowing how much to believe a given agent output, conditional on agent and task type

## Executive determination

The analogy **partly transfers, but only if “reliability” means probability of an unacceptable output on a particular demand under a stated operating regime—not MTBF, uptime, or a permanent reputation score.** This conclusion is **very likely (80-90%)**, because NIST explicitly analyzes reliability at the individual failure-mode level and warns that models generally only make sense at that level, while agent tasks are discrete demands whose correctness can be judged as success/failure or by mode ([NIST, “Based on failure mode”](https://www.itl.nist.gov/div898/handbook/apr/section2/apr211.htm); [NIST, binomial proportion model](https://www.itl.nist.gov/div898/handbook/prc/section2/prc24.htm)). The remaining uncertainty is structural: agent outputs are adaptive, task mixtures shift, labels are frequently missing, and “correct” is sometimes contestable.

The specific borrow I recommend is a **failure-mode-conditioned reliability case with measured diagnostic coverage and an explicit common-cause model**. It combines four established reliability mechanisms:

1. FMEA supplies the failure-mode/effect vocabulary and makes severity distinct from frequency.
2. Fault-tree analysis supplies a top-event model and minimal combinations by which bad output becomes harmful reliance.
3. Reliability demonstration supplies samples, uncertainty intervals, and the discipline that “no observed failures” is not “perfect.”
4. Common-cause analysis prevents correlated agent/verifier agreement from being multiplied as if it were independent evidence.

This combination is **likely (55-80%)** to calibrate routing and review decisions better than a single global success rate, because the cited engineering methods explicitly separate failure mechanisms, uncertainty, detection, and dependence. That benefit for agents is **UNVERIFIED; settle it with a prospective, pre-registered comparison on held-out tasks between (a) global agent score, (b) agent-by-task score, and (c) the proposed failure-mode/coverage/common-cause score, measuring Brier score, selective-risk curves, and escaped-material-error rate.**

The borrow must not become an autonomous “trust oracle.” It should emit an **evidence card**: estimated failure probability or conservative success bound, sample size, task cell, failure-mode mix, audit coverage, drift status, and dependence warnings. A user or router can then choose a review tier. It is **very likely (80-90%)** that exposing sample size and uncertainty prevents more false confidence than showing a point estimate alone, because NIST calls for interval estimates and notes that precision depends critically on observed failures ([NIST, exact intervals for small samples](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm); [NIST, lack of failures](https://www.itl.nist.gov/div898/handbook/apr/section1/apr132.htm)).

## 1. What reliability engineering actually solved

### 1.1 FMEA/FMECA: reason by failure mode and consequence, not by an undifferentiated average

In its own field, Failure Mode and Effects Analysis starts with a subject or process step, identifies ways it can fail, and records the effects of each failure. NIST describes FMEA as a method and information model for quality management and risk analysis; its process includes selecting the at-risk subject and listing the effect when each failure mode occurs ([NIST AMS 300-7 landing page](https://www.nist.gov/publications/proposed-expansion-quality-information-framework-qif-standard-schema-potential-failure); [NIST AMS 300-7 PDF, §2](https://nvlpubs.nist.gov/nistpubs/ams/NIST.AMS.300-7.pdf)). NIST’s reliability handbook goes further: root-cause analysis should characterize incidents by failure mode; each mode normally has its own model; and bottom-up composition comes only after mode-level analysis ([NIST, “Based on failure mode”](https://www.itl.nist.gov/div898/handbook/apr/section2/apr211.htm)).

This matters because a component can have an excellent aggregate success rate yet fail disproportionately in a rare, catastrophic mode. FMEA also keeps **effect/severity**, **occurrence**, and **detectability** conceptually separate. Multiplying ordinal rankings into a pseudo-precise “risk priority number” is not needed for this borrow; the useful mechanism is the structured inventory and the separation of dimensions.

**Translation:** treat an agent response as the item on demand. Classify both the task and the unacceptable outcome. A first harness taxonomy could be:

| Dimension | Concrete values (initial, revisable) |
|---|---|
| Task family | code change; diagnosis; factual research; synthesis; planning; high-stakes advice; external action |
| Failure mode | false factual claim; stale claim; missed explicit requirement; invalid inference; incomplete coverage; wrong artifact/state mutation; unsafe action; fabricated citation/evidence; unverifiable completion claim |
| Effect severity | cosmetic; recoverable rework; material wrong decision; irreversible/external harm |
| Detection opportunity | deterministic test; source check; independent review; owner correction; no practical detector |
| Outcome | pass; fail by mode; indeterminate; not audited |

The exact taxonomy is **likely (55-80%)** to need task-domain variants, because reliability models are normally mode-specific and agent error semantics differ across code, research, and action tasks ([NIST, failure-mode modeling](https://www.itl.nist.gov/div898/handbook/apr/section2/apr211.htm)). It is **UNVERIFIED whether the proposed initial values cover this owner’s workload; settle it by dual-coding a stratified random sample of 300 historical outcomes, measuring uncodable cases and inter-rater agreement, then revising the codebook before scoring agents.**

What this catches beyond an average score:

- an agent that is strong on code implementation but weak on current-fact research;
- an agent whose failures are rare but disproportionately irreversible;
- a verifier that catches syntax/test failures but routinely misses requirement omissions;
- “successful” tasks whose deliverable exists but whose completion claim is unsupported.

Those detections are **likely (55-80%)** if outcomes are independently and consistently labeled; the evidence is the failure-mode resolution principle above. The qualification is important: mislabeled or selectively labeled outcomes can manufacture the appearance of calibration.

### 1.2 Fault trees: model how an erroneous output becomes harmful reliance

Fault-tree analysis works top-down from an undesirable **top event**, decomposing it through logical gates into contributing events. The NRC’s NUREG-0492 handbook codifies construction and evaluation of fault/event trees ([NRC, Fault Tree Handbook NUREG-0492](https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr0492/index)). NASA’s aerospace fault-tree handbook also explains that probabilistic treatment of redundant components becomes wildly optimistic when failures assumed independent are actually subject to common causes ([NASA, Fault Tree Handbook with Aerospace Applications](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf), especially chapters 5 and 8).

For trust calibration, use this top event:

> **Top event: the owner or harness relies on an agent output that contains a material error.**

A compact qualitative tree is:

```text
MATERIAL WRONG RELIANCE
  AND
  ├── MATERIAL OUTPUT FAILURE
  │     OR
  │     ├── false/unsupported claim
  │     ├── missed controlling requirement
  │     ├── invalid artifact or state claim
  │     └── unsafe/irreversible action recommendation
  └── FAILURE ESCAPES OR BYPASSES CONTROL
        OR
        ├── no check selected
        ├── check lacks coverage for that failure mode
        ├── check fails independently
        └── producer and check fail from a common cause
```

The important result is not a made-up numerical top-event probability. It is the identification of **cut sets**: for example, `{missed requirement, verifier reuses the same summary}` or `{stale fact, no web/source check}`. These identify where an apparently strong workflow has a single epistemic point of failure.

This transfer is **very likely (80-90%)** to be structurally sound at the qualitative level: both domains have an undesirable system outcome produced by combinations of component failure and protection failure, and NASA explicitly relates uncovered faults to failures that propagate across a computer system ([NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). Quantitative gate probabilities are **unlikely (20-45%)** to be trustworthy initially, because agent events are not stationary and the dependencies are poorly observed. Therefore the first implementation should use the tree for coverage gaps and routing, not calculate six-decimal “risk.”

### 1.3 Reliability demonstration: evidence includes exposure and uncertainty

Reliability engineering does not infer reliability merely from a streak of success. It plans tests, records failure exposure, and attaches uncertainty to estimates. NIST states that reliability assessment normally needs failure data and frames test planning around duration, sample size, and test conditions ([NIST, Reliability Data Collection](https://www.itl.nist.gov/div898/handbook/apr/section3/apr3.htm)). For binary outcomes, NIST models the defect count with a binomial distribution and provides confidence intervals; it warns that symmetric normal approximations can be inaccurate with small samples or few failures ([NIST, proportion defective](https://www.itl.nist.gov/div898/handbook/prc/section2/prc24.htm); [NIST, exact/small-sample intervals](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm)). NIST also notes that failure-estimate precision varies roughly with the inverse square root of the **number of observed failures**, not merely units or test duration ([NIST, lack of failures](https://www.itl.nist.gov/div898/handbook/apr/section1/apr132.htm)).

Bayesian reliability analysis offers the same discipline in posterior form: prior knowledge combines with current data, and the Beta distribution is conjugate to a binomial success probability ([NIST, Bayesian methodology](https://www.itl.nist.gov/div898/handbook/apr/section1/apr1a.htm)). NIST explicitly says historical test data is the most credible prior information and describes weakening prior data when transferability is doubtful ([NIST, Bayesian reliability assumptions](https://www.itl.nist.gov/div898/handbook/apr/section2/apr25.htm)).

**Translation:** for each sufficiently supported `(agent configuration, task family, risk tier, evaluation regime)` cell, report at minimum:

- audited successes, failures, and indeterminate outcomes;
- the sampling policy (random audit, triggered review, owner correction, benchmark);
- a conservative one-sided success bound or posterior credible bound;
- age/version range of evidence;
- failure-mode counts and severity-weighted escaped failures;
- fraction of production demands independently audited;
- an explicit “insufficient evidence” state.

The denominator must be **audited eligible demands**, not all invocations. Unaudited success must not count as success. Trigger-only samples (only disputes, retries, or owner corrections) must be displayed separately, because their selection process differs from random audits.

For routing, a lower bound is preferable to a point estimate: `observed pass rate 100%, n=3` must not look equivalent to `observed pass rate 99%, n=2,000`. This is **almost certain (90-99%)** as a mathematical statement under the binomial sampling model, because interval width is sample-dependent and NIST’s small-sample guidance explicitly treats those estimates differently ([NIST confidence intervals](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm)). Whether a binomial model fits agent demands is only **likely (55-80%)**, because demands within a task cell can remain heterogeneous and temporally dependent. The model card must state this assumption.

### 1.4 Diagnostic coverage: confidence in the checker is itself empirical

Reliability and functional-safety practice distinguishes component failure from the probability that a diagnostic will detect it. NASA’s aerospace fault-tree handbook treats imperfect coverage as an uncovered fault that can directly affect the system, and explicitly relates diagnostic coverage to common-cause failure modeling ([NASA, Fault Tree Handbook with Aerospace Applications](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf), §8.2.1.1 in the indexed PDF text). NASA’s IV&V guidance similarly makes objective examination a risk-reduction mechanism and defines independence along technical, managerial, and financial dimensions ([NASA Software Engineering Handbook, SWE-141](https://swehb.nasa.gov/spaces/SWEHBVB/pages/32604595/SWE-141%2B-%2BSoftware%2BIndependent%2BVerification%2Band%2BValidation); [NASA IV&V overview](https://www.nasa.gov/ivv-overview/)).

**Translation:** every checker—tests, citation validation, critic agent, schema validator, human review—gets a **coverage matrix**, not a badge saying “verified”:

`coverage(checker, failure_mode, task_family) = detected known failures / known failures presented`

Estimate it from two sources kept separate:

1. **seeded faults** with known ground truth, for controlled sensitivity;
2. **naturally occurring adjudicated failures**, for ecological validity.

Also measure false alarms and “abstain/indeterminate,” because a checker that flags everything has high sensitivity and no practical discrimination. A checker may be credited only for the failure modes it had a realistic opportunity to detect.

This mechanism is **very likely (80-90%)** to expose hollow verification—such as a test suite being treated as evidence about factual freshness—because it forces the detector/failure-mode mapping. Its numeric coverage will be **UNVERIFIED until fault-seeding is performed; settle it with a blinded mutation suite containing at least 30 examples per high-severity failure mode and a held-out natural-failure set.**

### 1.5 Redundancy versus diversity: agreement is not independent evidence

Reliability engineering distinguishes redundant channels from independent or diverse channels. NASA warns that redundant-system probability can be wildly optimistic when nominally redundant components are assumed independent despite common-cause failures; its beta-factor treatment assigns a fraction of component failure rate to a shared threat ([NASA, Fault Tree Handbook with Aerospace Applications](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf), chapters 5 and 8). NASA safety requirements say use of redundancy must include a verifiable requirement that common causes do not invalidate failure tolerance ([NASA NPR 8715.3, Chapter 1, redundancy requirement](https://nodis3.gsfc.nasa.gov/displayCA.cfm?Internal_ID=N_PR_8715_0003_&page_name=Chapter1)). The NRC describes diversity and defense-in-depth as part of preventing and mitigating inadvertent digital failures ([NRC, Digital Instrumentation and Control](https://www.nrc.gov/reactors/digital)). NASA IV&V guidance defines technical independence as analysis by personnel not involved in development ([NASA Software Engineering Handbook, IV&V Surveillance](https://swehb.nasa.gov/spaces/SWEHBVC/pages/72024974/8.06%2B-%2BIV%2BV%2BSurveillance)).

**Translation:** “Agent B agrees with Agent A” adds little confidence when both share the same model family, prompt framing, supplied context, source, tool result, or evaluator. Record an **independence vector** for every assurance signal:

- model/provider and model family;
- prompt author and whether the producer’s reasoning/output was visible;
- context/evidence provenance;
- verification method (execution, source retrieval, recomputation, rubric review);
- toolchain/runtime;
- adjudicator identity or process;
- shared upstream summaries.

Do **not** multiply error probabilities unless conditional joint-failure data support independence. Initially, treat identical-family self-review as one channel plus possible incremental diagnostic coverage, not two independent votes. Give strongest credit to method diversity: for example, code generation checked by execution against hidden tests, or a web claim checked against independently retrieved primary sources.

It is **very likely (80-90%)** that same-context agents have meaningful common-cause errors; the engineering evidence establishes the general danger, while the specific magnitude for agents is **UNVERIFIED; settle it by a factorial benchmark varying model family, prompt visibility, context provenance, and verification method, then estimate pairwise and conditional joint failure rates by task/failure mode.** A literal NASA beta factor should not be imported without those data.

### Proposal B — BUILD-SMALL: append-only demand/outcome recorder on the existing hook bus

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one small hook that appends a JSONL record when a task is delegated/completed/adjudicated. It should store identifiers and hashes, not full sensitive content by default. Required event types:

- `demand_started`: task family, agent configuration, risk tier, version/time;
- `output_produced`: output/artifact hash and assurance signals claimed;
- `audit_selected`: selection probability and selection reason, recorded before outcome;
- `audit_result`: outcome, failure modes, severity, checker, independence vector;
- `owner_correction`: linked outcome, with later adjudication rather than automatically treating every correction as agent failure;
- `configuration_changed`: closes the evidence epoch.

The hook should be deliberately dumb: append validated events and reject malformed records. It should not orchestrate agents, infer truth, or maintain a knowledge graph.

This event spine is **very likely (80-90%)** to make later estimates reproducible if the hooks observe the relevant lifecycle transitions, because it preserves denominator, selection, version, and outcome provenance. Hook completeness in the target harness is **UNVERIFIED; settle it with two mechanically independent signals: inject a known-present synthetic lifecycle event and confirm both (1) its JSONL record and (2) an independently observed terminal/artifact marker, then reconcile hook counts against task ledger counts.**

### Proposal C — BUILD-SMALL: offline reliability-card scorer with conservative uncertainty

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A batch script reads the append-only events and emits cards by cell. Minimum behavior:

1. never mix agent-configuration epochs by default;
2. separate random/stratified audits from triggered and benchmark samples;
3. report `n`, failures, indeterminate count, audit fraction, and a one-sided Wilson/Jeffreys or exact-binomial bound;
4. suppress quantitative routing below a configured effective sample size;
5. report failure modes and high-severity escapes separately;
6. flag cells whose recent window differs materially from the earlier window;
7. refuse to aggregate cells when their failure-mode distributions or selection regimes differ materially.

NIST lists Wilson and Jeffreys intervals among methods with good small-sample coverage and cautions against the naive normal approximation ([NIST Dataplot, proportion confidence limits](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/propconf.htm)). The choice between a frequentist bound and a Bayesian credible bound is less important than declaring it, exposing assumptions, and not hiding `n`.

It is **likely (55-80%)** that a lightweight scorer can fit under 200 lines if classification and adjudication occur elsewhere. That line-count premise is **UNVERIFIED; settle it with a spike implementing parsing, stratification, Wilson bounds, and card emission against a frozen event schema, excluding tests but counting all runtime dependencies.** If it exceeds the bound, split recorder and scorer into two small bus consumers rather than creating a service.

### Proposal D — CONFIG: risk-based routing by conservative bound and effect severity

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Routing policy should use the card, not the agent’s self-confidence:

| Condition | Route |
|---|---|
| irreversible/high-severity effect | independent method check regardless of historical score |
| insufficient evidence or drift suspected | review or bounded trial; no autonomous external action |
| known weak failure mode matches task | attach a checker with demonstrated coverage for that mode |
| conservative bound exceeds task threshold and no dependence warning | normal acceptance path |
| disagreement or checker outside demonstrated coverage | abstain/escalate, not majority vote |

Thresholds should be expressed as policy decisions tied to consequence, not discovered from the same evaluation set. This is **very likely (80-90%)** to preserve the engineering distinction between occurrence and effect, because FMEA explicitly represents effects while reliability testing estimates occurrence ([NIST AMS 300-7 PDF](https://nvlpubs.nist.gov/nistpubs/ams/NIST.AMS.300-7.pdf); [NIST reliability assessment](https://itl.nist.gov/div898/handbook/apr/apr.htm)). The actual thresholds are **UNVERIFIED; settle them with owner utility elicitation plus shadow-mode replay measuring false accepts, unnecessary reviews, latency, and cost before enforcement.**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines per task-domain adapter, rides the existing skill/hook bus).** Maintain a small, versioned set of fault mutations per high-value failure mode. Run each checker blind against them and publish:

This suite is **likely (55-80%)** to reveal common-cause weaknesses that ordinary pass-rate evaluation misses, based on NASA’s warning that redundancy without common-cause treatment is optimistic ([NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). ### Proposal F — CONFIG: random assurance sampling and label-provenance separation

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Preselect a small random or stratified fraction of completed tasks for independent adjudication, with higher fractions for rare/high-severity task cells. ## 3. What the design catches that a conventional harness can miss

Because this unit intentionally did not inspect the local harness, the phrase “currently miss” cannot be asserted as a fact. **UNVERIFIED whether the current harness already implements any item below; settle it by demonstrating two independent signals for each claimed capability—(1) a known-present control that proves the detector and (2) a live end-to-end event/card—before declaring it present or absent.** The proposed design would catch these failure patterns if they are otherwise unmodeled:

1. **The high average hiding the bad cell.** A 98% aggregate performer may be materially worse on current legal research or multi-repository edits. Failure-mode/task conditioning surfaces the cell. This is **very likely (80-90%)** under heterogeneous task performance; the mechanism follows NIST’s requirement to analyze modes separately ([NIST failure-mode analysis](https://www.itl.nist.gov/div898/handbook/apr/section2/apr211.htm)).

2. **The perfect streak with almost no evidence.** Three audited successes produce “100%” but a weak lower bound. This is **almost certain (90-99%)** under binomial interval mathematics ([NIST small-sample intervals](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm)).

3. **The checker that tests the wrong property.** Unit tests may cover execution behavior but not source freshness or requirement completeness. Coverage matrices make the mismatch explicit. Detection is **very likely (80-90%)** if checker claims are mode-scoped and fault-seeded; NASA’s coverage treatment supports the structural mechanism ([NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

4. **Correlated consensus.** Producer and reviewer repeat the same wrong framing from shared context. An independence warning prevents “two votes” from being counted naively. Detection is **likely (55-80%)** from provenance alone; proving the error correlation still requires outcome data, as NASA’s common-cause warning does not quantify agents ([NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

5. **Silent drift after model/prompt/tool change.** Configuration epochs prevent old evidence from automatically certifying a new system. Detection is **likely (55-80%)** if all consequential changes are hashed; completeness is **UNVERIFIED and must be settled by deliberately changing each configuration surface and confirming a new epoch plus an independent configuration diff.**

6. **The severe rare escape drowned by minor failures.** Severity remains separate from occurrence, so one unsafe irreversible action is not averaged with formatting defects. This is **very likely (80-90%)** to improve risk visibility, following FMEA’s effect-oriented representation ([NIST AMS 300-7](https://www.nist.gov/publications/proposed-expansion-quality-information-framework-qif-standard-schema-potential-failure)).

7. **Selective labels masquerading as production reliability.** Random audits, triggered failures, benchmarks, and owner corrections remain separate evidence regimes. This is **very likely (80-90%)** to make selection bias visible because the binomial/random-sample assumption can be checked rather than silently violated ([NIST binomial proportion model](https://www.itl.nist.gov/div898/handbook/prc/section2/prc24.htm)).

8. **“Done” supported only by the producer’s assertion.** The fault tree treats completion error and failed/bypassed detection as a cut set; a material completion claim can require an independent artifact/state signal. This is **likely (55-80%)** to reduce false completion if the second signal is method-independent. NASA IV&V’s technical-independence rationale supports the direction ([NASA SWE-141](https://swehb.nasa.gov/spaces/SWEHBVB/pages/32604595/SWE-141%2B-%2BSoftware%2BIndependent%2BVerification%2Band%2BValidation)).

## 4. Adversarial transfer analysis: where the analogy breaks

### 4.1 Agents are not stationary components

Classical MTBF/exponential models often assume a homogeneous Poisson process and a constant failure rate. NIST states those assumptions explicitly for its gamma/exponential Bayesian reliability model ([NIST, Bayesian reliability assumptions](https://www.itl.nist.gov/div898/handbook/apr/section2/apr25.htm)). Agent behavior changes with model version, system prompt, context length, tool state, upstream summaries, and task distribution. A single timeless “agent reliability” is therefore **almost certainly not (1-5%)** defensible; evidence is the mismatch between the cited constant-rate assumptions and the configuration-sensitive demand process.

**Consequence:** use version-bounded demand probabilities, rolling/shadow evaluation, and explicit drift flags. Never call the number MTBF.

### 4.2 Agent demands are not identically distributed

Two “research” tasks can differ radically in novelty, source availability, ambiguity, and consequence. A binomial model assumes a common success probability for trials in the modeled population ([NIST, proportion defective](https://www.itl.nist.gov/div898/handbook/prc/section2/prc24.htm)). Even task-family cells can be mixtures. Thus confidence intervals quantify sampling uncertainty **conditional on the cell definition**; they do not repair a bad taxonomy or distribution shift.

**Consequence:** show the operational/task profile and refuse aggressive pooling. Hierarchical shrinkage may eventually help sparse cells, but is **UNVERIFIED; settle it by temporal held-out calibration against unsmoothed cell estimates and a global baseline.** No hierarchical model is recommended for the first build.

### 4.3 Ground truth is often partial or socially constructed

Hardware failure usually has an operational definition; many agent outputs are open-ended and multi-dimensional. Human adjudicators can disagree, and a later owner correction is not automatically proof the earlier output was wrong.

**Consequence:** allow `indeterminate`, preserve rubrics and adjudicator provenance, measure inter-rater agreement, and separate objective checks from judgment. A binary pass/fail score without this escape hatch is **likely (55-80%)** to create label noise; this is an inference from the target domain rather than a claim supplied by the reliability sources. It is **UNVERIFIED; settle it with blinded duplicate adjudication of a stratified sample.**

### 4.4 The agent can adapt to the measurement

Physical components do not normally optimize prose to satisfy a visible evaluator. Agents can learn or be prompted to game rubrics, over-abstain, or emit citations that look checkable. This breaks a passive-monitoring analogy.

**Consequence:** use hidden/rotating faults, held-out adjudication, and monitor abstention/cost as well as correctness. It is **likely (55-80%)** that static public evaluator suites invite evaluator-specific optimization; this is **UNVERIFIED for this harness and would be settled by comparing performance on disclosed versus sequestered fault sets over successive prompt revisions.**

### 4.5 Failures are not independent, and “diversity” is hard to observe

Agent replicas can share training data, provider infrastructure, retrieval sources, system prompts, and user framing. Different model names do not prove independent failure. Reliability engineering already warns about precisely this logical error for redundant systems ([NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

**Consequence:** record provenance, estimate joint error, and prefer diverse methods over nominally diverse personas. Do not import a beta factor until measured.

### 4.6 Detection changes the system

Extra reviewers increase latency, cost, context volume, and opportunities for new error. A checker can overwrite a correct answer with a wrong critique. Unlike a passive sensor, an agent reviewer may be an actuator.

**Consequence:** log checker-induced regressions and evaluate the whole route’s escaped-error rate, not only checker recall. It is **likely (55-80%)** that some checkers have nonzero harmful false-positive rates; the exact magnitude is **UNVERIFIED and would be settled by blinded paired evaluation of producer-only versus producer-plus-checker outputs.**

### Bottom line on transfer validity

The **structural** borrow—failure modes, effects, diagnostic coverage, uncertainty, and common-cause dependence—transfers. The **physical lifetime mathematics and assumptions of stationary independent components do not.** This boundary is **very likely (80-90%)** correct, based on the explicit assumptions in NIST’s reliability models and NASA’s common-cause treatment ([NIST Bayesian assumptions](https://www.itl.nist.gov/div898/handbook/apr/section2/apr25.htm); [NASA aerospace fault-tree handbook](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

## 6. Anti-overfit gate and rejected expansions

The recommended architecture passes the brief’s anti-overfit gate: it rides existing hooks/skills/configuration, consists of append-only events plus small offline scoring, and does not introduce a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Explicitly rejected:

- **A permanent “agent trust score.”** Rejected because it erases task type, evidence age, and failure mode.
- **A new reliability daemon/control plane.** Rejected because batch cards and configuration routing suffice; a service adds a second operational failure surface.
- **A learned trust predictor or trained critic.** Rejected because it adds another opaque, drifting model before basic labels and coverage are established.
- **Majority vote among agent personas.** Rejected because nominal redundancy does not establish independence; common-cause failures can dominate.
- **A vector DB/KG of reliability incidents.** Rejected because structured append-only events and small aggregate tables answer this problem without retrieval infrastructure.
- **Literal FMEA risk-priority-number multiplication.** Rejected because ordinal severity/occurrence/detection ranks do not justify cardinal multiplication and would create fake precision.
- **Literal MTBF.** Rejected because agent outputs are demand-based, heterogeneous, and configuration-sensitive rather than constant-rate physical lifetimes.

The minimal design outperforming a large trust-control runtime is **likely (55-80%)**, because it directly tests the needed claims while minimizing new components; that comparative claim is **UNVERIFIED and would be settled only if a concrete larger alternative is implemented and compared on the Phase 3 endpoints.** No such large alternative is recommended here.

## 7. Decision rules and invariants

These are the non-negotiable invariants the borrow contributes:

1. **No reliability without a stated demand population.** Always name agent configuration, task family, risk tier, and evidence epoch.
2. **No success without adjudication.** Invocation/completion is exposure, not proof of correctness.
3. **No point estimate without uncertainty and `n`.** Sparse perfect records remain uncertain.
4. **No verifier badge without mode-specific coverage.** A checker is evidence only for demonstrated failure modes.
5. **No confidence multiplication without dependence evidence.** Same model/context/source is a common-cause warning.
6. **No mixing of label-selection regimes.** Random audits, benchmarks, triggered reviews, and owner corrections are reported separately.
7. **No old evidence silently crossing a configuration change.** Transfer, if allowed, is explicit and discounted.
8. **No low-severity volume drowning a high-severity escape.** Report occurrence and effect separately.
9. **No “broken,” “absent,” or “done” from one detector.** Validate the detector on known-present control and use a mechanically independent second signal.
10. **No autonomous trust decision when evidence is unknown.** Unknown routes to bounded trial, method-diverse verification, or owner judgment according to consequence.

These rules are **very likely (80-90%)** to make trust claims more auditable, because every rule corresponds to an assumption or failure mechanism made explicit in the cited reliability guidance. Their net productivity effect is **UNVERIFIED; settle it in the prospective routing trial with cost and latency as co-primary constraints rather than correctness alone.**
