# A089 — coherence audit: hooks versus settings / duplicate authority

## Executive result

I found **three real settings↔hook authority conflicts** in the supplied read-only snapshot:

1. `codex-monitor-autolaunch` says and implements detection for native Codex MCP calls **and** `codex exec` / `codex mcp` shell calls, but its outer settings matcher permits only the native MCP tool. The Bash and PowerShell branches are unreachable.
2. The local dispatch manifest and generalized monitor hook say the dispatcher receives `Workflow`; the active settings matcher excludes `Workflow`. A separately wired legacy Workflow-only launcher masks part of this regression, but the generalized successor's Workflow path is unreachable.
3. Credential-file access has two policy owners with different states and scopes: unconditional native `permissions.deny` rules and an opt-in hook which is explicitly off by default. Consequently, turning the hook off does **not** implement its stated owner directive for `Read(.env)`-class access.

The first two are invocation-boundary drift. The third is policy-state drift. All three arise in concrete calls, not merely in comments.

The runtime conclusions are **almost certain (90-99%)**, based on (a) exact active settings and hook source, (b) controlled matcher/hook probes with known-positive controls, and (c) Claude Code's official contracts that tool-event matchers decide whether a hook spawns and that PreToolUse/native deny decisions block calls. A live Windows Claude process was unavailable on this Linux job node, so the end-to-end Windows observation is **UNVERIFIED**; the settling experiment is the `/hooks` plus `claude --debug` smoke matrix specified under “Final verification.” This does not make the source-level reachability defects contingent on an unverified premise.

## Finding 3 — credential access is simultaneously unconditional and opt-in

### The two authorities, verbatim

Native settings unconditionally declare:

> `"Read(./.env)",`
>
> `"Read(**/.env)",`
>
> `"Read(**/*.pem)",`
>
> `"Read(**/*.credentials*)"`

— `claude/settings.json:65-68`

The hook explicitly acknowledges this authority:

> `The declarative permissions.deny in settings.json already blocks the Read tool`
>
> `on .env/*.pem/*credentials*; this ALSO closes the Bash/Grep gap (e.g. \`cat .env\`,`

— `claude/hooks/deny-credential-reads/deny.py:6-8`

but declares a different state policy:

> `Owner directive 2026-07-11: this credential-file-READ block is OPT-IN and`
>
> `OFF by default.`

— `claude/hooks/deny-credential-reads/deny.py:74-75`

and enforces that state as:

> `return os.environ.get("HARNESS_CREDENTIAL_GUARD", "").strip().lower() in {`
>
> `    "1", "true", "yes", "on",`
>
> `}`

— `claude/hooks/deny-credential-reads/deny.py:81-83`

The settings environment block at `claude/settings.json:4-20` does not set `HARNESS_CREDENTIAL_GUARD`. This absence was checked with two signals: direct complete inspection of the env object, and an exact-key search across settings plus all hook Python that found the key only in `deny.py:77,81`. The search's ability to find a known-present settings env key was controlled using the listed settings keys; none of those keys are consumed by hook Python.

### Concrete collision and runtime winner

Call: `Read({"file_path":".env"})` in the default profile.

Synthetic hook results:

```text
HARNESS_CREDENTIAL_GUARD unset: Read .env -> rc=0, no output
HARNESS_CREDENTIAL_GUARD=1:     Read .env -> rc=0, permissionDecision=deny
HARNESS_CREDENTIAL_GUARD=1:     Read client.key -> permissionDecision=deny
HARNESS_CREDENTIAL_GUARD=1:     Edit .env -> permissionDecision=deny
HARNESS_CREDENTIAL_GUARD=1:     Bash "cat .env" -> permissionDecision=deny
```

**Runtime winner for `Read(.env)` / matching PEM / credentials paths: native `permissions.deny`.** The hook's default silence cannot relax a native deny. Claude Code documents permission evaluation as deny → ask → allow, with deny winning; it also documents that deny rules remain evaluated regardless of a PreToolUse hook result. Therefore the stated “OFF by default” owner directive does not hold for the overlapping native `Read` cases. This is **almost certain (90-99%)**, supported by settings, executable hook behavior, and the official permissions contract.

Outside the overlap, authority flips with the environment. With the variable unset, `Edit(.env)`, `Bash(cat .env)`, and hook-only patterns such as `Read(client.key)` receive no hook denial; with it enabled, the hook denial blocks them even under `bypassPermissions` (official hooks guide). The scope difference is visible in the hook's broader `SENSITIVE_GLOBS` at `deny.py:19-24`, tool routing at `deny.py:90-100`, and the narrow native list at settings lines 65-68.

### Minimal resolving edit — CONFIG (settings/JSON only)

Honor the recorded owner directive and establish one state owner: remove the four native `permissions.deny` entries at `claude/settings.json:65-68`; keep the existing hook registration and `HARNESS_CREDENTIAL_GUARD` toggle. When protection is desired, set the one toggle so the same hook governs Read/Edit/Grep/Bash/PowerShell consistently.

This recommendation is **very likely (80-90%)** to make credential-file protection genuinely opt-in, based on the native deny precedence and executable hook matrix. It deliberately follows the explicit owner directive embedded at `deny.py:73-80`; if that directive is obsolete, the alternative coherent edit is to set `HARNESS_CREDENTIAL_GUARD=1` and retain native denies as defense in depth, while rewriting “OFF by default” and documenting that the native overlap is always on. The owner-intent choice cannot be inferred beyond the dated directive.

Anti-overfit gate: passes. This consolidates policy on the existing hook bus and adds no machinery.

## Design conclusion

The best repair is not a replacement runtime. These defects are produced by **outer registration predicates duplicating inner predicates without a single enforced source**. The existing bus and existing `_dispatch/test_wiring.py` are enough:

- Keep outer standalone matchers as broad transport filters and inner scripts as semantic filters where standalone blocking/output behavior requires it (Codex monitor).
- For consolidated hooks, mirror the manifest's declared outer matcher exactly and enforce it with the already-written wiring test.
- Do not express policy enablement twice. Credential enforcement gets one toggle owner; native denies cannot serve as a second, silently unconditional mode.

This minimal architecture is **very likely (80-90%)** to prevent recurrence of the two observed reachability drifts if the existing exact-equality test is run in CI or the harness validation command, because the test directly compares settings to manifest at `_dispatch/test_wiring.py:208-234`. Merely possessing the test is insufficient—the current snapshot proves that—so its routine execution is necessary. The actual CI wiring is **UNVERIFIED**; the settling experiment is to search the repository's test workflow for this file and introduce no new framework if it is not already included.
