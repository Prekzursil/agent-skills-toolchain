## Authority model used for adjudication

The following distinctions prevented false positives:

1. An agent `tools:` list is a native **availability allowlist**. Anthropic documents that omitted tools are not exposed to that subagent. It is not the same operation as `permissions.allow`, which controls automatic approval for tools that exist.
2. `permissions.deny` is enforcement, not advice. Deny is evaluated before ask and allow, and prompt text cannot override it. Anthropic explicitly says prompts shape what Claude tries, while permission configuration controls what Claude Code allows.
3. The subagent's `model:` frontmatter normally outranks the main-session model, below only `CLAUDE_CODE_SUBAGENT_MODEL` and a per-invocation model. The audited settings do not set `CLAUDE_CODE_SUBAGENT_MODEL`.
4. Enabling a plugin makes its components available; it does not order a local agent to invoke them. Plugin agents are exposed under scoped names such as `plugin-name:agent-name`, so mere semantic overlap with a local unscoped agent is not a name collision.
5. `CLAUDE_CODE_FORK_SUBAGENT=1` is different: current official subagent documentation says it makes **every** subagent spawn run in the background and overrides the agent's `background` field. It therefore controls the same foreground/background fact that the `codex` prompt declares.

Those are documented product semantics. Exact behavior on the owner's installed Windows binary is **UNVERIFIED inline**; the version-and-trace experiment above is the settlement test.

### Concrete collision

The collision occurs whenever the main session delegates a work unit to the named `codex` subagent and expects the Agent call to block until the adapter returns its schema-valid terminal result. The global environment variable forces the subagent spawn onto the fork/background path. The `codex` agent may still run its internal `codex exec` child in that background subagent's foreground, but the **caller-to-subagent edge** is asynchronous. The parent can continue before the artifact and terminal receipt exist, exactly contrary to “Blocks until Codex finishes.”

This situation is not hypothetical configuration overlap: the setting applies to every subagent spawn, while the agent is defined specifically to be spawned for work units. Whether an actual historical `codex` dispatch lost a result for this exact reason is **UNVERIFIED inline**; querying session transcripts for `agent_type=codex` and joining Agent start, immediate tool result, and `SubagentStop` timestamps would settle historical incidence. Historical incidence is not needed to establish the live contradictory control surfaces.

### Which one wins at runtime

**Settings wins for the caller/subagent scheduling mode.** Anthropic's current subagent documentation states: when `CLAUDE_CODE_FORK_SUBAGENT` is `1`, every subagent spawn runs in the background regardless of the `background` frontmatter field. A Markdown system prompt can direct the model, but it cannot change how the host schedules the Agent call. This is independently consistent with Anthropic's permission documentation at lines 111-116 of the current page: prompt instructions shape attempted behavior, while Claude Code configuration supplies enforcement.

The installed binary's exact observed result is **UNVERIFIED inline** due the remote Linux override; launch one disposable `@codex` task whose only child action waits for a pre-created marker, then observe whether the Agent call returns before the marker is released. That separates caller scheduling from the Codex CLI child's own foreground behavior.

### Minimal edit

**NATIVE-vs-BUILD: CONFIG.** Remove this one user-global entry:

```json
"CLAUDE_CODE_FORK_SUBAGENT": "1",
```

Then use native `background: true`, `run_in_background`, or skill `context: fork` only on workloads whose contract is asynchronous. Do not add `background: false` to `codex.md` while retaining the environment variable: official documentation says global fork mode overrides that field, so that apparent one-line fix is inert.

This edit is **very likely (80-90%)** to preserve the adapter's synchronous contract, based on the documented override behavior and the absence of any `background:` field in the 18 supplied agents. It is **roughly even (45-55%)** that it would alter at least one workflow that silently relied on globally forced forking, because the setting is global but skill definitions were outside this unit's comparison; that impact is **UNVERIFIED inline**, and a pre-edit inventory of skill frontmatter containing `context: fork`, saved Agent-call timing receipts, and a disposable post-edit smoke matrix would settle it. Because this unit is read-only, I did not make the edit.

### Anti-overfit gate

The correction removes a global override and returns control to Claude Code's native agent/skill bus. It adds no runtime, daemon, store, memory system, critic, SaaS, durable-execution layer, or guardrail framework. It therefore passes the anti-overfit gate.

### Tool allowlists versus permissions: two layers, not duplicate authority

Settings allows common tools at `/local_disk0/codexwork/bundle/claude/settings.json:27-62` and sets `defaultMode` to `bypassPermissions` at line 71. Every supplied agent has a `tools:` field. The official subagent documentation defines that field as a tool-availability allowlist. Official permission documentation separately defines allow entries as auto-approval rules and says a prompt cannot alter enforcement. Thus, for example, global `Write` approval does not expose Write to `architect`; `architect.md:4` limits it to Read/Grep/Glob. The agent allowlist wins availability, then permissions evaluate attempted calls among available tools.

The apparent omission of `AskUserQuestion` and `ReportFindings` from settings' allow array is also not a deny. `AskUserQuestion` is documented as unavailable in subagent context for a different native reason; `ReportFindings` remains available if the host supplies it and the agent lists it.
