## Executive verdict

Windsurf's strongest contribution is not a fundamentally better autonomous agent loop. It is an unusually coherent product surface around familiar primitives: a persistent plan and visible Todo list, codebase retrieval, local workspace memories, conditionally activated rules, Agent Skills, MCP, permission tiers, worktree-isolated parallel sessions, hooks, checkpoints, linter repair, and review. The current product adds Arena, a local/cloud agent command center, Spaces, and Quick Review. The official Windsurf documentation index now redirects the native-editor pages to Devin Desktop while retaining `.windsurf` compatibility paths; this product-continuity interpretation is **almost certain** because the Windsurf index names the pages and their Windsurf paths while the English pages redirect to the corresponding Devin documentation, and the redirected pages explicitly retain legacy `.windsurf` paths ([Windsurf documentation index](https://docs.windsurf.com/llms.txt), [Memories & Rules](https://docs.devin.ai/desktop/cascade/memories)).

For this owner, most attractive Windsurf features are already **NATIVE (Claude Code already does this; we just enable it)** or are present in the live harness: plan mode and tasks, checkpoint/rewind, path-scoped instructions, auto memory, Skills, MCP Tool Search, hooks, granular permissions, subagents, agent teams, isolated worktrees, parallel desktop sessions, browser verification, and code review. The live configuration proves that agent teams, Tool Search, tasks, subagent lifecycle hooks, and worktree hooks are already enabled (`C:\Users\Prekzursil\.claude\settings.json:4-20`, `:445-470`; `C:\Users\Prekzursil\.agents\harness\registration.py:17-34,122-140`).

The high-value gaps are narrower:

1. Canonical Basic Memory recall is global rather than workspace-isolated. Windsurf's local memories are workspace-bound; our lexical index contains known-present quality fields (`superseded_by`, `poisoned`) but no project/workspace field, and recall gates on injection, path exclusions, poison and relevance but not workspace (`C:\Users\Prekzursil\.agents\harness\recall_index.py:300-324`; `C:\Users\Prekzursil\.agents\harness\modules.py:1623-1650`). This absence has two mechanically independent signals and a known-positive detector control.
2. Instruction activation telemetry is implemented but not registered. The event module handles `InstructionsLoaded`, while the registration tuple omits it (`C:\Users\Prekzursil\.agents\harness\modules.py:944-962`; `C:\Users\Prekzursil\.agents\harness\registration.py:17-34`). This directly compounds pinned defect D3, which says hook behavior is currently unmeasurable in the corpus (`INPUT-known-harness-defects.md:110-124`).
3. Immediate verification skips TypeScript/TSX and Rust even though Windsurf auto-detects and repairs generated lint errors. The deployed post-edit hook is wired (`C:\Users\Prekzursil\.claude\settings.json:333-342`) but explicitly returns no check for those extensions (`C:\Users\Prekzursil\.claude\hooks\per-edit-check\check.py:8-24,151-170`).

The recommended import is therefore small: workspace-gate canonical recall, register instruction-load telemetry, and close the measured per-edit diagnostic gaps. Do not clone the hidden planning agent, the trained SWE-grep retrieval service, an Arena runtime, a second durable memory, or a new command-center service. Those exact copies fail the anti-overfit gate because they would introduce large machinery beside a host that already provides the core primitives.

## 1. Agent loop

### What Windsurf does

Cascade exposes Code, Plan, and Ask modes. Code has all tools and mutates the repository; Plan explores, asks structured questions, writes an external Markdown plan, and can hand off to Code; Ask is read-only ([Cascade modes](https://docs.devin.ai/desktop/cascade/modes)). A separate planning agent continuously refines the long-term plan while the selected action model executes short-term steps. A visible Todo list tracks complex tasks and can change as new information, including a Memory, arrives. Users can queue messages during execution. The loop is explicitly bounded to 20 tool calls per prompt, after which Continue or Auto-Continue resumes at additional prompt cost ([Cascade overview](https://docs.devin.ai/desktop/cascade/cascade)).

Plan files live under `~/.windsurf/plans`, can be mentioned into a fresh conversation, and let the user discard a failed implementation while retaining the plan. That is good context hygiene: preserve a compact intent artifact, not the entire failed trajectory ([Cascade modes](https://docs.devin.ai/desktop/cascade/modes)).

### Comparison

Our harness already has an authoritative goal state, ignores system-noise prompts, re-injects the goal every N mutating actions, and re-anchors after compaction (`C:\Users\Prekzursil\.agents\harness\modules.py:1279-1365`). Claude Code provides native plan mode, tasks, background agents and resumable sessions. The live configuration enables forked subagents and agent teams (`C:\Users\Prekzursil\.claude\settings.json:4-20`). This is more explicit and inspectable than a hidden planner.

Windsurf is worse in three ways:

1. The 20-call prompt boundary is an arbitrary commercial/trajectory boundary. Auto-Continue consumes another prompt credit rather than representing verified completion.
2. A continuously running planner can create a second source of intent. The documentation says it may rewrite the plan when a Memory appears, but it does not document conflict resolution between the original user goal, the planner and retrieved memory.
3. “Continue” is recovery from a cap, not a terminal-state protocol. Our behavior contract demands `SUCCESS:<id>` / `FAILED:<id>` outcomes and the harness records terminal receipts (`C:\Users\Prekzursil\.agents\harness\README.md:8-24`).

### Proposal: keep native plan/task/goal state; do not clone the continuous planner

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Port the useful mechanism as an operating pattern: create or update a visible native task/plan artifact; keep the event-ledger goal authoritative; after compaction or resume, re-anchor from that goal and the compact plan. Do not run a second always-on planning model. It is **very likely** that this preserves most of Windsurf's focus benefit with less drift, because the local goal module already persists and re-injects the user goal while Claude exposes native plan/tasks; no controlled benchmark compares the hidden Windsurf planner against this design, so relative performance remains **UNVERIFIED** until the same long-horizon task suite is run on both and scored for goal retention, corrections and cost.

### Proposal: persistent plan file import — UNVERIFIED need

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

The exact Windsurf convenience—an automatically saved, @-mentionable plan file that seeds a fresh context—may not be available in the CLI surface used by this owner. **UNVERIFIED** whether the installed Claude Desktop/CLI version already persists plan-pane documents in an equivalent reusable form; settle by creating a native plan, ending the session, and checking whether a fresh session can select it without manually copying text. If absent and the owner repeatedly reuses plans, a small `plan-artifact` skill can save the approved plan plus goal hash under the project, with no daemon. Do not build it preemptively: the existing goal module and checkpoint mechanism may make it redundant.

## 2. Context management

### What Windsurf does

Windsurf indexes the full local codebase and combines retrieved snippets with the current/open files and pinned items. Team/Enterprise can index remote repositories and add up to 50 Google Docs to a team Knowledge Base. The documentation explicitly warns that team-added Google Docs do not preserve individual Drive ACLs once an admin exposes them to the team ([Context Awareness](https://docs.devin.ai/desktop/context-awareness/overview)).

Fast Context is a specialized retrieval subagent powered by trained SWE-grep models. It automatically triggers for code search, uses up to eight parallel grep/read/glob calls per turn for up to four turns, and returns targeted snippets to conserve the primary model's context ([Fast Context](https://docs.devin.ai/desktop/context-awareness/fast-context)). This is a concrete architecture: a narrow retrieval model, restricted toolset, bounded parallel search, and summarized handoff.

### Comparison

Claude Code has native Explore/subagent search, path-scoped rules, compacting, desktop context/session management and MCP Tool Search. Our shared recall hook deliberately uses a bounded local lexical index and never performs semantic/network/model search (`C:\Users\Prekzursil\.agents\harness\README.md:21-29`). That makes it predictable and cheap, but not equivalent to a trained code retrieval model.

Fast Context is **likely** to reduce time and primary-context pollution on some large-repository searches because its mechanism is specifically bounded and delegated, and the official page describes parallel targeted retrieval. The magnitude is **UNVERIFIED** marketing evidence: settle with a fixed large-repo query set measuring relevant-file recall, wall time, tool errors, tokens returned, and downstream task success against native Explore/rg.

The local corpus makes a blind port especially risky: Glob is the worst core tool at 13.3% errors, with 592 `ENAMETOOLONG` failures caused by the orphaned plugin-path expansion described in the pinned brief. A retriever that fans out grep/read/glob calls could amplify the existing Windows launch defect before that substrate is fixed.

### Proposal: do not build a SWE-grep service now

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).**

An exact port requires a trained retrieval model, serving path, parallel search controller, evaluation set and lifecycle. It fails the minimal-architecture gate today. Use native Explore agents, `rg`, MCP Tool Search and bounded handoffs; first remove the measured plugin-path launch failure. Revisit only if a benchmark shows native retrieval is a dominant residual bottleneck after that fix. It is **very likely** that fixing the known Windows execution substrate has higher near-term value, because it already causes hundreds of measured failures whereas no local benchmark shows retrieval quality as a top defect.

### Proposal: optional team-doc context without a new knowledge base

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

If project work genuinely needs shared Google Docs, connect a Drive/Docs source through the existing connector/MCP bus and retrieve on demand. Do not ingest another vector store. Apply source ACL and provenance at retrieval because Windsurf's own Knowledge Base deliberately broadens admin-selected Docs to the whole team. This is **likely** sufficient for this single-owner harness because Basic Memory already provides cross-tool durable notes and the missing function is source access, not another persistence engine; settle by measuring whether document retrieval succeeds with the connector and whether answers preserve document identity and access scope.

## 3. Memory

### What Windsurf does

Cascade automatically creates local memories when it judges context useful, also accepts explicit “create a memory” requests, stores them under `~/.codeium/windsurf/memories/`, and retrieves them when relevant. Generated memories are workspace-specific, machine-local, not committed, and free of prompt credits. Windsurf recommends Rules or `AGENTS.md` instead for durable/team-shareable knowledge ([Memories & Rules](https://docs.devin.ai/desktop/cascade/memories)).

That separation is sound:

- ephemeral learned facts: local auto memory;
- durable behavioral instructions: versioned rules / `AGENTS.md`;
- repeatable manual trajectories: Workflows;
- complex model-selected procedures with assets: Skills.

### Comparison

Our setup has three memory surfaces already: Claude auto memory, Codex native memories, and canonical cross-tool Basic Memory, plus the objective event ledger. Adding Windsurf-style auto memory would create another authority. Basic Memory is richer than Windsurf's local memories for cross-tool continuity and supersession, and the event ledger is explicitly objective history rather than semantic memory.

The real delta is scope. The canonical lexical index includes path, title, summary, permalink, keywords, recency, importance, supersession, failure-head and poison state (`C:\Users\Prekzursil\.agents\harness\recall_index.py:300-324`). The recall loop proves it can detect known-present fields—permalink suppression, excluded paths and poison—but has no project/workspace key or gate (`C:\Users\Prekzursil\.agents\harness\modules.py:1623-1650`). This satisfies the two-signal absence rule: independent producer schema and consumer selection logic, with known-positive controls in each.

### Proposal: workspace-gate canonical recall

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Mechanism:

1. At index time, derive a stable workspace/project scope from note metadata or its vault folder; retain `global` only for deliberately cross-project notes.
2. At recall time, derive the current repository identity using the same stable project hash already used by pre-compaction checkpoints (`C:\Users\Prekzursil\.agents\harness\README.md:28-29`).
3. Filter candidates to `{current_scope, global}` before relevance scoring.
4. Preserve explicit cross-project recall through the Basic Memory MCP search, not automatic hook injection.
5. Add known-positive tests: a current-project note must be recalled; an equally relevant foreign-project note must not; an explicitly global note must be recalled.

This is **very likely** to reduce cross-project contamination because the missing field and missing gate are directly observed, and Windsurf's workspace isolation demonstrates a simple safety boundary. The behavioral improvement magnitude is **UNVERIFIED** until the three-control test is followed by a replay over owner-correction candidates involving stale or foreign context.

### Do not copy Windsurf auto-memory generation

Windsurf's memory generator is worse for this harness because relevance, promotion and conflict behavior are undocumented, memories are not cross-tool, and the product itself recommends versioned rules for reliable reuse. The correct import is isolation, not another generator.

## 4. Tool and MCP handling

### What Windsurf does

Windsurf supports MCP over stdio, Streamable HTTP and SSE, with OAuth. It offers a marketplace, one-click deeplinks, raw `mcp_config.json`, individual tool toggles, secret interpolation from environment variables or files, and a hard limit of 100 enabled tools. Teams can replace the marketplace with custom registries or enable an allowlist; adding the first allowlist entry blocks all non-allowlisted servers. Matching is anchored and applies to server configuration fields ([MCP integration](https://docs.devin.ai/desktop/cascade/mcp)). Hooks can inspect and block `pre_mcp_tool_use` with server, tool and arguments, then observe results in `post_mcp_tool_use` ([Cascade hooks](https://docs.devin.ai/desktop/cascade/hooks)).

### Comparison

The corpus records 93 MCP servers touched and a dead `claude_ai_Tavily` still receiving calls: 532 calls, 25.8% errors, including 135 “not connected” failures. This is an operational lifecycle failure, not a lack of MCP breadth.

Claude Code's Tool Search is stronger than Windsurf's fixed 100-tool ceiling for a large fleet: it defers MCP schemas and discovers only relevant tools on demand. The live setting uses a 5% threshold (`C:\Users\Prekzursil\.claude\settings.json:17`). Claude permissions and hooks can gate individual MCP tools, and native MCP supports project/user scopes and OAuth ([Claude MCP Tool Search](https://code.claude.com/docs/en/mcp), [Claude permissions](https://code.claude.com/docs/en/permissions)).

Windsurf's marketplace and per-tool toggles are better UX for a small fleet, but they do not document health checks, circuit breaking, error-rate retirement, or schema relaxation—the exact problems measured here. A marketplace clone would not fix the dead-server loop or StructuredOutput's 22.9% error rate.

### Proposal: keep deferred Tool Search; curate through existing configuration

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Retain Tool Search, disable/remove known-dead servers after the separate MCP-lifecycle unit proves the canonical registration target, and use per-tool permission rules for dangerous mutators. Use environment interpolation rather than literal secrets. It is **almost certain** that disabling a confirmed dead endpoint eliminates its “not connected” calls because the corpus fingerprint is endpoint-specific; which configuration file is authoritative is outside this unit and must be settled by the MCP-grounding unit before any write.

### Do not copy the hard 100-tool cap or marketplace

The cap fails open-world capability discovery and turns capacity into manual toggling. The marketplace adds supply without health or quality scoring, which is the wrong direction for a fleet already calling a dead MCP. Tool Search rides the host's existing bus and avoids another aggregation layer.

## 5. Permission model

### What Windsurf does

Terminal execution has four tiers: Disabled, Allowlist Only, Auto (model judges risk), and Turbo (everything except denylisted commands auto-runs). Team admins can cap the maximum tier and merge team/user allow/deny lists; deny takes precedence but means “require approval,” not unconditional prohibition. `.codeiumignore` prevents Cascade from viewing, editing or creating matching files. Enterprise admins can govern MCP registries/allowlists and deploy read-only system rules/hooks ([Terminal](https://docs.devin.ai/desktop/terminal), [Cascade overview](https://docs.devin.ai/desktop/cascade/cascade), [MCP integration](https://docs.devin.ai/desktop/cascade/mcp)).

### Comparison

Claude Code's native model is more granular: deny → ask → allow across Bash, file, web and MCP tools; managed settings; sandbox filesystem/network enforcement; and PreToolUse decisions that cannot override a native deny ([Claude permissions](https://code.claude.com/docs/en/permissions)). Windsurf's documented denylist only prevents auto-execution, so a user may still approve the command. Claude deny rules actually prevent the tool call.

The host is stronger, but the live posture is weaker: all read/write/search/shell tools are broadly allowed, `defaultMode` is `bypassPermissions`, and both `C:` and `D:` are additional directories; only a short secret-file deny list remains (`C:\Users\Prekzursil\.claude\settings.json:26-75`). This is a configuration choice, not an architectural absence.

### Proposal: adopt Windsurf's tiered UX intent through native Claude policy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Map ordinary sessions to Claude `auto` or `default`, plan/research sessions to `plan`, and reserve bypass for explicitly isolated environments. Keep deny-first rules for secret paths and genuinely destructive operations; use sandbox boundaries for Bash rather than string-only command interpretation. It is **likely** to reduce accidental mutation exposure because the current mode bypasses prompts across two drives while native policy and sandbox supply enforcement. The productivity/security tradeoff is **UNVERIFIED** for this owner's workflow; settle with a shadow log of commands that would prompt or deny under `auto` over representative sessions before changing the default.

### Windsurf hook examples are actively worse—do not copy

The official dangerous-command example scans substrings such as `rm -rf`, `sudo rm`, `format`, and `del /f` in the command string ([Cascade hooks](https://docs.devin.ai/desktop/cascade/hooks)). That repeats pinned defect D1's exact semantic error: matching payload text without distinguishing use from mention or parsing shell structure. The docs also warn that hooks run with the user's full permissions. Our replacement must use parsed tool verb/arguments and sandbox/permission boundaries, not copy these examples.

## 6. Customization: rules, skills, workflows, hooks

### Rules and `AGENTS.md`

Windsurf supports global, workspace, directory-derived `AGENTS.md`, and Enterprise system rules. Workspace rule frontmatter selects `always_on`, `model_decision`, `glob`, or `manual`. Only a model-decision rule's description stays in the prompt until selected; glob rules load when matching files are touched; manual rules load by @mention. Workspace files are limited to 12,000 characters and global rules to 6,000 ([Memories & Rules](https://docs.devin.ai/desktop/cascade/memories)).

Claude already provides root and path-scoped rules, lazy-loaded nested instructions, Skills with progressive disclosure, and `/memory` to inspect loaded instruction sources ([Claude memory](https://code.claude.com/docs/en/memory)). Windsurf's model-decision and manual modes map cleanly to a Skill description plus auto/manual invocation. No new rule engine is justified.

Windsurf is worse for hard enterprise policy because its system rules are merged “without overriding” user rules. A non-overriding prompt rule is guidance, not enforcement. Claude managed settings and deny rules provide stronger policy precedence.

### Skills and Workflows

Windsurf Skills follow the Agent Skills format: `SKILL.md` frontmatter, progressive disclosure, workspace/global/system scope, supporting scripts/templates, automatic model selection or manual @mention ([Skills](https://docs.devin.ai/desktop/cascade/skills)). Workflows are Markdown step sequences invoked only by slash command; they can call other workflows and are versionable ([Workflows](https://docs.devin.ai/desktop/cascade/workflows)).

This is native parity. The local environment already exposes hundreds of Skills and the corpus shows only 78 invoked, so importing another directory of templates would worsen discoverability rather than close a mechanism gap. Claude's skill/command surface already rides the same standard.

### Hooks

Windsurf documents 12 events: before/after read, write, command and MCP; before prompt; after response; after response with transcript; and after worktree setup. Inputs include stable trajectory/execution IDs and model name. Pre-hooks block on exit 2. System, user and workspace hooks merge in order. The transcript hook writes structured JSONL with file contents, command output, tool arguments, search results and applied rules, protects files with mode `0600`, retains 100 files, and warns that schemas may change ([Cascade hooks](https://docs.devin.ai/desktop/cascade/hooks)).

Claude's native hook surface is broader, including compaction, permission, subagent, task, teammate, instruction, config, worktree and batch events ([Claude hooks](https://code.claude.com/docs/en/hooks)). Our live registration includes most of those (`C:\Users\Prekzursil\.agents\harness\registration.py:17-34`). The missing value is observability of instruction activation, not event breadth.

### Proposal: register instruction-load telemetry

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Add `InstructionsLoaded` to the existing registration tuple and timeout map, regenerate native registrations through the harness installer, and test with two controls: a known always-loaded root instruction and a known path-scoped instruction triggered by reading a matching file. The consumer already exists at `C:\Users\Prekzursil\.agents\harness\modules.py:952-954`; the producer registration is absent at `C:\Users\Prekzursil\.agents\harness\registration.py:17-34`. This is **almost certain** to make instruction activations ledger-visible because the native event is documented and the local handler is already implemented. Whether it fully resolves D3 for every hook is **UNVERIFIED**; settle by grepping both the ledger and one transcript for a known fired hook and the known fired instruction event after registration.

### Proposal: structured hook receipts, only if D3's experiment still fails — UNVERIFIED

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

If known-fired hooks remain absent from both transcript and ledger, append a compact receipt `{event, trajectory/session hash, execution/turn hash, module verdict, reason_code, timestamp}` to the existing event ledger. Never log raw prompt, file contents or MCP results. The recommendation is **UNVERIFIED** until D3's specified two-location grep establishes that the data is genuinely absent. ## 7. Multi-agent support

### What Windsurf does

- Multiple Cascade sessions may run simultaneously, but edits can race unless isolated.
- Worktree mode creates one session/worktree, offers a Merge action, copies only tracked files by default, supports a post-setup hook, caps each workspace at 20 worktrees, and prunes least-recently-used worktrees ([Worktrees](https://docs.devin.ai/desktop/cascade/worktrees)).
- Arena runs the same prompt independently across selected models, gives each a worktree, lets the user continue each trajectory, and converges after the human selects “X is better.” Battle groups can conceal model identity until selection ([Arena](https://docs.devin.ai/desktop/cascade/arena)).
- Agent Command Center places local Cascade and cloud Devin agents in a status Kanban. Spaces group agent sessions, PRs, files and context for a task/project ([Agent Command Center](https://docs.devin.ai/desktop/agent-command-center)).

### Comparison

Claude Code agent teams provide full independent sessions, shared dependency-aware tasks, file-locked claiming, peer/lead messaging, lifecycle hooks and direct teammate interaction ([Claude agent teams](https://code.claude.com/docs/en/agent-teams)). Claude Desktop supplies parallel local/remote/SSH sessions, status filtering, visual diffs and previews ([Claude Desktop](https://code.claude.com/docs/en/desktop)).

Therefore Windsurf does not lead on orchestration semantics. It leads on integrated comparison and portfolio UX. Arena also has a serious verification weakness: the user/model preference decides the winner. It does not execute distinguishing tests or account for correlated model failures. Our `execution-grounded-bon` explicitly selects from multiple worktree candidates using deterministic execution, cross-vendor consensus, knockout on hard failures and surfaced discrimination (`C:\Users\Prekzursil\.claude\skills\execution-grounded-bon\SKILL.md:6-28,90-109`).

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Use Claude Desktop when the owner wants a visual session portfolio; use CLI agent teams for dependency-aware collaboration; use isolated worktrees for overlapping edits. Do not add a second orchestrator. This is **almost certain** to cover the operational core because the official Claude documentation explicitly lists parallel worktree sessions, status filtering and agent teams, and the live configuration enables teams/worktree hooks.

An exact Arena clone needs synchronized multi-model session creation, worktree lifecycle, diff viewers, blind identity handling, convergence/discard semantics and cost accounting. It fails the anti-overfit gate. Retain cross-vendor fan-out and execution-grounded selection on the existing bus. ## 8. Verification and self-check

### What Windsurf does

Cascade supports prompt-level checkpoints and named snapshots, Problems-panel transfer, Explain-and-Fix, and default auto-fix of generated lint errors without additional credits. It can consume editor state in real time and retrieve relevant summaries/checkpoints from prior conversations instead of injecting the entire history ([Cascade overview](https://docs.devin.ai/desktop/cascade/cascade)). Current Devin Local adds Quick Review: a separate agent examines the diff for correctness, style and issues using SWE-check or a selected frontier model ([Quick Review](https://docs.devin.ai/desktop/quick-review)).

### Comparison

Claude Code natively checkpoints before edits and supports rewind across sessions ([Claude checkpointing](https://code.claude.com/docs/en/checkpointing)). Claude Code/Chrome and Desktop provide browser verification and live previews ([Claude Chrome](https://code.claude.com/docs/en/chrome), [Claude Desktop](https://code.claude.com/docs/en/desktop)). Hooks can prevent Stop, task completion or teammate idle until quality gates pass. The local harness already runs post-edit validation and has stronger execution-grounded multi-candidate selection.

Windsurf's integrated zero-friction lint repair is better than the live hook for polyglot edits. The hook handles Python, JS syntax, JSON and optionally YAML, but explicitly skips TS/TSX and Rust (`C:\Users\Prekzursil\.claude\hooks\per-edit-check\check.py:8-24,151-170`). This absence is proven by two independent signals: the documented dispatch table and executable branch logic, with Python/JS as known-present controls.

Quick Review is useful as a second opinion but is not a proof. A model reviewing another model's diff can share blind spots, and the Windsurf page does not document execution-based validation or false-positive filtering. Our execution-grounded mechanism is superior for candidate selection because it makes confidence a mechanical function of observable behavior and explicitly caps indistinguishable results (`C:\Users\Prekzursil\.claude\skills\execution-grounded-bon\SKILL.md:90-109`).

### Proposal: close TypeScript/Rust per-edit gaps with bounded project-aware checks

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Mechanism:

1. For TS/TSX, prefer the project's fast configured linter/type command scoped to the changed file when supported (for example ESLint/Biome); do not invoke full-project `tsc` after every edit.
2. For Rust, use `rustfmt --check` on the changed file per edit; reserve `cargo check` for task/Stop verification or an explicit batch gate.
3. Preserve the existing 12-second hook budget and fail-open behavior on missing tools.
4. Emit structured diagnostics tied to the changed file; never auto-mutate in the checker itself. Let the agent perform and explain the repair.
5. Test known-valid, known-invalid, missing-tool and timeout controls for each language.

It is **likely** this captures much of Windsurf's fast lint-feedback value without hidden auto-mutation because the current hook and event are already deployed. Exact command choices are **UNVERIFIED** until the target repositories' package/config files are inventoried and median per-file runtime is measured; that experiment must precede implementation.

### Proposal: checkpoint/review/previews through native host

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Use native rewind, Desktop visual diff/preview, Chrome for web-flow verification, and a separate review subagent when risk warrants it. Do not rebuild named checkpoints or preview plumbing. Prefer executable acceptance signals over a universal review model.

## Final assessment

Windsurf is best understood as a product-integration benchmark, not a blueprint for another harness runtime. Its most valuable ideas—workspace isolation, context-cost-aware activation, worktree-by-default parallelism, visible plans, bounded hooks and immediate diagnostics—fit the existing Claude/skill/hook/MCP bus. Its most distinctive internals—continuous planner and trained retrieval agent—are not supported by local evidence as the next bottleneck. Its most polished multi-agent features—Arena and the command center—are UI advantages, while our agent-team semantics and execution-grounded verification are stronger.

The evidence supports evolution at three seams, not replacement: register native telemetry, scope canonical recall, and extend bounded diagnostics. Full replacement with Windsurf's architecture would be a regression against the owner's measured failures and anti-overfit constraints.
