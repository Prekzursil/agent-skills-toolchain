# A026 — Coherence audit of `~/.claude/rules/dart/coding-style.md`

## Executive verdict

The audited rule is not coherent with the harness around it. I found **eight reportable collisions**: two STALE wiring/scope statements, one REDUNDANCY, three direct CONTRADICTIONS in the companion Dart examples, one broad UNENFORCED policy surface, and one UNRULED hard enforcement. The most consequential defect is not a disputed Dart preference: the file says formatting is “enforced in CI,” while the live user settings do not register a Dart formatter or analyzer and the only directly registered per-edit validator explicitly has no `.dart` dispatch. The next most actionable defects are executable examples that teach the opposite of the rule: non-`const` constructors, mutable collections returned from public APIs, and an `async` function with no `await` that forwards a Future despite an absolute “Always await” sentence.

The measured corpus cannot establish whether agents followed this Dart rule. It contains no Dart/Flutter/path markers in the fields that can carry behavioral evidence, while its `sessions` records are metadata only. Calling the rule followed, violated, or unused from this corpus would therefore exceed the detector. This is a **GAP**, not evidence that Dart work did not occur.

The skill-content comparison is also incomplete for a concrete packaging reason. The bundle has a router index naming 1,341 skills, including five Dart/Flutter-adjacent skills, but it does not contain `~/.claude/skills/` or `~/.agents/skills/` content. I do not convert that missing input into “no skill collision.”

All proposed changes below ride the existing rule/settings/hook/analyzer bus. None introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The anti-overfit gate is therefore satisfied.

Repository CI remains **UNVERIFIED:** settle it per repository by locating its workflow and running the exact format gate on a deliberately misformatted disposable branch.

### C5 — CONTRADICTION: public collection-return examples are mutable despite the target's unmodifiable-public-API rule

**Artifacts and exact lines**

- `claude/rules/dart/coding-style.md:19-22`, specifically `:21`, requires public APIs to return `List.unmodifiable` / `Map.unmodifiable`.
- `claude/rules/dart/patterns.md:13-18` makes `getAll()` part of a public repository interface; its implementation returns the data source's `remote` list directly at `:37-43`.
- `claude/rules/dart/testing.md:111-140` presents a public fake repository. Its `getAll()` returns `_users.values.toList()` at `:122-125`, and `watchAll()` exposes `Stream.value(_users.values.toList())` at `:127-128`; both lists are mutable snapshots.
- `claude/rules/dart/patterns.md:77-82` exposes `CartState.items` publicly and accepts/stores an arbitrary caller-supplied list without an unmodifiable wrapper.

**Why this collides**

The examples are precisely where an agent will learn how to implement the target's repository and state APIs. Returning a fresh mutable list avoids aliasing the backing map but does not satisfy the literal requirement to return an unmodifiable collection. Returning `remote` can additionally preserve a data-source alias. The `CartState` constructor likewise allows callers holding the original list to mutate state behind its back.

**Resolution — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL.** Choose and state one policy. If the strict target is intended, wrap repository/state outputs (`List.unmodifiable(remote)`, `List.unmodifiable(_users.values)`) and defensively copy/wrap constructor inputs; update all canonical examples together. If performance-sensitive APIs may return owned mutable snapshots, weaken line 21 to say so explicitly and define ownership. The strict repair is **very likely (80-90%)** to eliminate accidental external mutation, based on the direct mutable-return sites. Whether the owner wants strict wrappers on every public collection is **UNVERIFIED:** settle it with a Dart design review plus microbenchmarks on the affected hot APIs; until then, do not silently weaken the target.

AGENTS precedence does not decide this same-level conflict.

### C6 — CONTRADICTION: the target's absolute Future wording rejects valid forwarding and conflicts with its own canonical Riverpod example

**Artifacts and exact lines**

- `claude/rules/dart/coding-style.md:133-138` says “Always `await` Futures or explicitly call `unawaited()`” and “Never mark a function `async` if it never `await`s anything.”
- `claude/rules/dart/patterns.md:99-103` defines `Future<List<User>> users(Ref ref) async`, contains no `await`, and `return`s `repo.getAll()` directly.
- The same patterns file intentionally forwards Futures from expression-bodied repository methods at `:46-54` and use cases at `:174-189` (some are direct returns and some await).

**Why this collides**

The Riverpod example violates both literal bullets at once. More importantly, the first bullet is badly written: returning/forwarding a Future is neither dropping it nor fire-and-forget. Requiring `await` in a direct forwarding function can add an unnecessary async boundary and makes the second bullet impossible to follow if the function is already marked `async` only to satisfy the first.

This collision indicates a **badly written rule**, not necessarily bad runtime behavior. That distinction determines the remedy: repair the normative sentence rather than forcing every forwarding expression through `await`.

**Resolution — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL.** Rewrite line 135 to: “Never discard a Future: `await` it, return/forward it, or use `unawaited()` for intentional fire-and-forget.” Remove `async` from the Riverpod example and use `Future<List<User>> users(Ref ref) => ref.watch(...).getAll();`, unless Riverpod code generation requires `async` in the installed version. The wording repair is **almost certain (90-99%)** to remove the logical contradiction because it explicitly covers the existing direct-return form. The exact Riverpod generated-signature edit is **UNVERIFIED:** settle it by running `dart analyze` and `build_runner` against a minimal project pinned to the owner's Riverpod version.

AGENTS precedence does not decide between same-level Dart artifacts; this resolution makes them consistent.

### C8 — UNRULED: YAML syntax is hard-blocked for files in this rule's scope, and that hard block violates higher-precedence hook policy

**Artifacts and exact lines**

- The target explicitly scopes itself to `pubspec.yaml` and `analysis_options.yaml` (`dart/coding-style.md:2-5`) but contains no YAML-syntax enforcement statement in `:7-159`.

**Why this collides**

On either YAML file named by the target, a parse error triggers enforcement that the rule never declares. That is an UNRULED enforcement under the unit taxonomy. It is also a direct precedence violation: invalid YAML is usually reversible editing feedback, not an irreversible/dangerous operation, so AGENTS §6 outranks and forbids the exit-2 behavior. PostToolUse cannot undo the edit anyway; the “hard block” terminology in `per-edit-check.py:18-24,225-231` is misleading about what can be blocked after the tool completes.

**Resolution — NATIVE-vs-BUILD: BUILD-SMALL.** Keep YAML parsing but emit exit 0 plus `additionalContext`, matching the existing soft-lint path, and document syntax validation once in the generic rule/hook contract rather than in every language rule. Add a regression test that feeds invalid `analysis_options.yaml` and asserts nonblocking feedback. This is **almost certain (90-99%)** to restore AGENTS §6 compliance because it changes the exact exit protocol at issue while preserving detection.

Precedence resolves this collision: `claude/AGENTS.md` is level 3 and the hook/target are level 4, so the hook must yield.
