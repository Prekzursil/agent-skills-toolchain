## Executive finding

The useful borrow is **STPA's context-dependent Unsafe Control Action analysis plus explicit feedback/process-model analysis**. The structural match is strong: an agent issues a tool call as a controller issues a control action; the tool adapter and shell actuate it; the operating system and repository are the controlled process; and tool results are feedback that updates the agent's internal model. STPA asks not only whether a component fails, but whether a valid control action is absent, present in a hazardous context, mistimed/misordered, or sustained for the wrong duration. It then works backward from each unsafe action to inadequate control logic, a flawed controller process model, bad feedback, and action-path failures. That is exactly the level at which an apparently reasonable `command: string` interface can convert an agent's intention into a malformed shell program.

The transfer conclusion is **very likely (80-90%)**, based on the direct correspondence between STPA's controller/action/actuator/process/feedback loop and an agent/tool/shell/OS/result loop, and on STPA's explicit treatment of software and human controllers. The remaining uncertainty comes from an important disanalogy: ordinary shell quoting is deterministic language processing, while STPA was designed for broader sociotechnical hazards; STPA identifies where constraints and feedback belong but does not itself synthesize a correct command or prove an interface usable.

The proposed intervention is deliberately small:

1. Replace the single ambiguous shell-string lane with two explicit lanes: an **argv-first program invocation** for ordinary commands and a **dialect-declared script invocation** for actual shell programs.
2. For the script lane, run the declared shell's own non-executing parser before execution, then return a stable, structured error envelope with parser stage, dialect, source span, and an explicit `executed: false` fact. Do not auto-rewrite the command.
3. Admit the change only through a compact claims–argument–evidence record backed by corpus replay and shadow traffic, including false-block and capability-loss tests.

It is **very likely (80-90%)** that the argv-first lane would prevent a large fraction of quoting failures in simple program invocations, because the shell grammar is removed from that path and official subprocess documentation explicitly prefers an argument sequence so the runtime handles escaping and quoting. This is **UNVERIFIED** until experiment **E1, quote-fingerprint replay**, classifies and replays the supplied 1,631 failures. It is **almost certain (90-99%)** that exact-dialect parser preflight would catch syntactically unterminated quotes before execution when the submitted script and runtime dialect match, because Bash exposes a read-without-execute syntax-check mode and PowerShell exposes its parser with returned parse errors. This is **UNVERIFIED** until experiment **E2, parser differential**, compares preflight results with execution-parser results on the same scripts and shell versions.

This is not a recommendation for a second orchestration runtime, a vector store, a trained critic, a guardrail framework, or observability infrastructure. Every proposed control rides the existing tool schema/adapter/test bus. The design removes a grammar boundary from common calls and adds one native-parser check at the remaining boundary.

## 1. The mechanism in its own field

### 1.1 STAMP: safety as enforced constraints in a control loop

STAMP treats safety as a control problem: losses can arise when safety constraints are inadequately enforced across a control structure, including through interactions rather than only through failed components. The official MIT STPA Handbook is presented as the definitive guide and explicitly covers complex systems containing software and human elements ([MIT PSASS, “Books and Handbooks”](https://psas.scripts.mit.edu/home/books-and-handbooks/)).

The central control-loop vocabulary is:

- A **controller** selects control actions using a control algorithm and an internal **process model**.
- A **control action** travels through an action/actuation path to a **controlled process**.
- Sensors and other channels return **feedback**, which updates the controller's process model.
- A controller can behave unsafely even when every component is nominal if its process model does not match reality, its algorithm is inadequate, or the feedback is missing, late, incorrect, or misinterpreted.

The handbook expressly states that a process-model mismatch can follow from incorrect feedback, correct feedback that is misinterpreted or ignored, feedback that is delayed or absent, or necessary feedback that does not exist. It also warns that a controller may incorrectly assume that an issued action was executed and update its process model accordingly ([STPA Handbook, especially pp. 22 and 42–47, and appendix discussion around p. 181](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

This matters because “operator error” is not the terminal explanation. The method asks what system design, feedback, assumptions, and constraints made that action reasonable or recoverable from the controller's perspective.

### 1.2 STPA's specific mechanism: enumerate Unsafe Control Actions by context

The handbook defines an Unsafe Control Action (UCA) as a control action that, in a particular context and worst-case environment, leads to a hazard. It requires the context because the same action may be safe in one state and unsafe in another. STPA systematically considers four ways an action can be unsafe:

1. a required control action is not provided;
2. providing the action causes a hazard;
3. a potentially safe action is provided too early, too late, or out of order; or
4. a continuous action lasts too long or stops too soon.

Each UCA records the source/controller, UCA type, action, hazardous context, and trace to a hazard. The next STPA step constructs loss scenarios by asking both why the controller would issue or omit the unsafe action and why an otherwise adequate action would be improperly executed or not executed. The official handbook documents all four categories, contextual construction, and these two scenario families ([STPA Handbook, pp. 34–47](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

The crucial systems-safety move is therefore:

> Do not begin with “how do we make the operator stop making syntax mistakes?” Begin with “which control actions become hazardous under which observable contexts, what constraint should hold there, what process-model fact does the controller need, and what feedback proves what actually happened?”

That move transfers more productively than merely adding a shell-syntax reminder to a prompt.

### 1.3 Swiss cheese: layered defences, active failures, and latent conditions

James Reason's system approach places defences, barriers, and safeguards between local hazards and losses. Engineered controls, human operators, and procedures are distinct defensive layers. Each layer has weaknesses; harm occurs when weaknesses align across layers. Reason distinguishes active failures at the operational “sharp end” from latent conditions created earlier in design and organization ([Reason, “Human error: models and management,” BMJ 2000](https://www.bmj.com/content/320/7237/768)).

The useful lesson is not “add many checks.” It is that a local unsafe act and a latent interface condition can combine, and that no single defence should be presumed perfect. The model is a metaphor, not a method for demonstrating independence. A later empirical study found that safety professionals interpreted parts of the diagram differently and noted that the simplified rendering removed causal pathways; this is direct reason not to treat the picture as a complete causal model ([Perneger, “The Swiss cheese model of safety incidents: are there holes in the metaphor?”](https://pmc.ncbi.nlm.nih.gov/articles/PMC1298298/)). EUROCONTROL likewise describes the model as useful but not accepted uncritically and explicitly frames its publication as a review of pros, cons, and limits ([EUROCONTROL, “Revisiting the Swiss Cheese model of accidents”](https://www.eurocontrol.int/publication/revisiting-swiss-cheese-model-accidents)).

For this unit, Swiss cheese contributes one design test: **are the controls mechanically different, or are they correlated holes produced by the same agent and same textual representation?** A prompt that says “quote carefully,” an LLM self-review, and an LLM critic all share the same representation and reasoning source. Calling them three layers would exaggerate independence.

### 1.4 Normal-accident theory: interactive complexity plus tight coupling

Perrow's normal-accident theory argues that systems combining interactive complexity with tight coupling are vulnerable to unexpected failure interactions and fast cascades. “Interactive complexity” concerns unfamiliar or unplanned interactions that are not immediately comprehensible; “tight coupling” leaves little slack, few alternatives, and little time to intervene. Perrow's own later abstract recommends decomposing systems into units connected by monitored links, designing robustness in from the start, and warns that add-on safety measures can themselves become disproportionate sources of accidents ([Perrow, “Organizing to Reduce the Vulnerabilities of Complexity”](https://doi.org/10.1111/1468-5973.00108)). The theory's core dimensions and original book provenance are also summarized in the NIOSH-hosted research report on operationalizing normal-accident theory for embedded systems ([CDC/NIOSH report](https://stacks.cdc.gov/view/cdc/8538/cdc_8538_DS1.pdf)).

This provides a negative constraint on our design: reduce interpretive stages and separate “describe” from “execute” where useful; do not respond to one grammar problem with an elaborate cascade of generated validators, critics, and retry policies.

It would be an overreach to label the 1,631 quote failures “normal accidents.” Shell parsing is deterministic, many invocations are loosely coupled and reversible, and the supplied outcome is usually task interruption rather than catastrophic loss. Normal-accident theory transfers here only as an architectural caution about nested grammars, immediate actuation, opaque interactions, and add-on complexity.

### 1.5 Safety cases: make the claim and its evidence inspectable

A safety case is a structured argument that demonstrates adequate safety and links the argument to supporting evidence. UK HSE guidance emphasizes consistency, hazard coverage, assessability, lifecycle maintenance, monitoring, and management of change ([HSE Research Report RR1170, pp. 39–41](https://www.hse.gov.uk/research/assets/docs/rr1170.pdf)). The UK NCSC's current software assurance guidance decomposes top-level claims into lower-level claims that can be objectively evidenced and says that inability to evidence a claim should expose remediation or additional testing ([NCSC, “Assurance Principles and Claims”](https://www.ncsc.gov.uk/guidance/software-security-code-of-practice-assurance-principles-claims)).

The transferable mechanism is modest: do not accept “the wrapper is safer” as a free-floating assertion. State exactly which failure class is controlled, why the mechanism addresses it, what counter-hazards it introduces, and what replay/shadow evidence supports the claim.

## 2. Structural translation to an agent harness

| Systems-safety element | Agent-tool analogue | Quoting-specific example |
|---|---|---|
| Controller | Model/agent selecting a tool call | Agent chooses Bash or PowerShell and constructs a command |
| Control algorithm | Model policy, prompt, examples, tool affordances | “Use a shell for this task” plus learned quoting habits |
| Process model / mental model | Agent's beliefs about OS, shell dialect, current directory, interpolation, and prior execution | Agent believes a quote is balanced or believes PowerShell escaping applies in Bash |
| Control action | Structured tool invocation | `exec_script(dialect="bash", script=...)` |
| Actuator/action path | Tool adapter, transport, shell launcher, command parser | JSON decoding → adapter → `bash -c` → Bash parser |
| Controlled process | Shell, child process, filesystem, repository, network | Command mutates or reads the workspace |
| Feedback | Tool result: parse status, execution status, exit code, stdout/stderr, changed state | `stage=preflight`, `executed=false`, unmatched quote span |
| Hazard | System state that can cause an owner-defined loss | malformed command blocks progress; incorrect repair changes the wrong file |
| Safety constraint | Context-specific invariant on tool behavior | A script with a fatal parser error must not be executed |
| Loss | Owner-level unacceptable outcome | wasted autonomous loop, unintended mutation, false belief that work completed |

This mapping is **very likely (80-90%)** to be useful for interface design, based on the one-to-one functional correspondence and STPA's explicit inclusion of software and human controllers. It is **unlikely (20-45%)** that the complete rigor or vocabulary of safety-critical STPA is cost-effective for every harness tool call, because most calls have low consequence and a full hazard analysis would add process weight; the evidence is the mismatch in consequence scale and the anti-overfit constraint in the unit brief.

### 2.1 Mini-STPA for shell invocation

Define losses narrowly for this lens:

- **L1:** task progress is lost through a malformed invocation and retry loop.
- **L2:** the agent acquires a false belief that a command ran, partly ran, or did not run.
- **L3:** a repair attempt changes semantics or causes unintended state change.
- **L4:** a safety control blocks a legitimate command or removes needed shell expressiveness.

Corresponding hazards:

- **H1:** syntactically invalid text is sent to an executing shell.
- **H2:** text is parsed by a different dialect/version than the agent assumed.
- **H3:** execution outcome and side effects are ambiguous in feedback.
- **H4:** a validator rejects valid input or a restricted interface cannot express the task, causing bypass or deadlock.
- **H5:** retry logic repeats an unchanged malformed action without incorporating new state.

Contextual unsafe control actions:

| STPA category | Agent-tool UCA | Constraint derived from it | What a quote-only linter misses |
|---|---|---|---|
| Not provided | Adapter refuses a valid script because a heuristic mistakes a legal quote construct for an error | Native-parser failure, not heuristic suspicion, gates execution; escape path remains explicit | False positives and capability loss (H4/L4) |
| Provided | Adapter executes a script whose declared dialect parser reports an unterminated quote | Fatal parser errors must return before actuation | Prevents the supplied failure class before shell execution (H1/L1) |
| Provided | Adapter accepts `dialect=bash` while launcher actually resolves another interpreter | Result must report requested and resolved dialect/version; mismatch must fail closed for script mode | Process-model mismatch and configuration drift (H2/L2) |
| Too early / wrong order | Retry executes before the agent receives or incorporates the prior parse span | A rejected call returns `executed=false`, stable code, and source span before any retry is eligible | Retry-loop coupling (H5/L1) |
| Too late | Syntax feedback arrives only after an execution attempt | Parse-stage feedback precedes actuation | Ambiguity about partial execution (H3/L2) |
| Applied too long | A malformed multiline construct leaves an interactive or wrapper path waiting for completion | Script lane is non-interactive and has bounded parse/execute time | Hangs rather than immediate EOF failures |
| Stopped too soon | Wrapper truncates script content or transport drops a suffix that closes a quote | Hash/length of accepted script is echoed in result metadata | Action-path corruption rather than controller-generation error |

This table exposes why “run a quote counter” is inadequate. Quotes can be legal or illegal depending on dialect, context, escaping, here-documents/here-strings, and interpolation. The system must know which interpreter is authoritative and must distinguish controller-generation defects from transport, resolution, parser, execution, and feedback defects.

## 3. Proposed design

### Proposal 1 — Dual-lane execution contract — **UNVERIFIED**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

**Unverified premise and settling experiment:** The premise that most quoting failures occur in calls that do not intrinsically need shell syntax is **UNVERIFIED**; experiment **E1, quote-fingerprint replay**, must label all 1,631 supplied cases as simple program invocation, shell composition, embedded-language quoting, transport corruption, or indeterminate. The recommendation inherits this marker because its expected coverage depends on that mix.

Expose two semantically different calls rather than one overloaded command string:

```json
{
  "tool": "exec_program",
  "program": "rg",
  "args": ["-n", "owner's intent", "docs/Design Notes.md"],
  "cwd": "/workspace",
  "env": {},
  "stdin": null,
  "timeout_ms": 10000
}
```

and:

```json
{
  "tool": "exec_script",
  "dialect": "bash",
  "script": "set -euo pipefail\nrg -n \"owner's intent\" 'docs/Design Notes.md' | head -20",
  "cwd": "/workspace",
  "env": {},
  "timeout_ms": 10000
}
```

Contract rules:

1. `exec_program` invokes an executable with an argument array and does not perform shell expansion, pipelines, redirection, command substitution, glob expansion, or tilde expansion.
2. `exec_script` requires an explicit dialect from a small supported set such as `bash` and `pwsh`; there is no `auto` dialect.
3. A call that needs a pipeline, redirection, compound statement, variable expansion, or shell builtin uses `exec_script`; normal single-program calls use `exec_program`.
4. The adapter returns the resolved executable/interpreter identity and version in result metadata.
5. Legacy raw-string execution, if retained during migration, is named `exec_legacy_shell` and emits a measurable deprecation code; it is not silently selected.

Python's official subprocess documentation says a sequence of arguments is generally preferred because the module can handle necessary escaping/quoting, and warns that explicit shell use makes the application responsible for whitespace and metacharacter quoting. It also documents Windows batch-file caveats, which is why this proposal does not pretend that argv eliminates every Windows parsing layer ([Python `subprocess` documentation](https://docs.python.org/3/library/subprocess.html)). POSIX itself models program arguments as an argument list of strings ([The Open Group `exec` specification](https://pubs.opengroup.org/onlinepubs/9799919799/functions/exec.html)).

Expected catches:

- It is **very likely (80-90%)** that the argv lane prevents unmatched shell quotes for simple native executable calls, because quote characters are data inside an argument rather than shell syntax; this is **UNVERIFIED** until E1 replay demonstrates coverage on the supplied cases.
- It is **likely (55-80%)** that the majority of the 1,631 supplied failures can migrate to either argv without quoting or a clearly declared script dialect, based on the high frequency of ordinary search/build/file commands in agent work described by the unit context; this is **UNVERIFIED** until E1 classifies the actual calls.
- It is **very unlikely (5-20%)** that this eliminates all quoting failures, because genuine scripts, nested languages, remote-shell commands, `.cmd` behavior, and data passed to programs can retain quoting semantics; this is supported by the Python documentation's platform caveat and is to be measured in E1/E4.

Counter-hazard: loss of shell expressiveness could push the model into awkward workarounds. The explicit script lane and an audited legacy escape hatch control that risk. There must be no rule that mechanically translates arbitrary scripts into argv; such translation changes semantics.

Why this is not overfit: it reduces one overloaded representation into two existing process-launch semantics. It introduces no planner, daemon, memory layer, critic, or durable workflow engine.

### Proposal 2 — Exact-dialect native-parser preflight — **UNVERIFIED**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

**Unverified premise and settling experiment:** The premise that the launch-time parser and the preflight parser will be the same executable/version/configuration is **UNVERIFIED**; experiment **E2, parser differential**, must record the resolved interpreter identity for both stages and compare their accept/reject result on valid and malformed scripts.

For `exec_script` only:

1. Resolve the declared interpreter once.
2. Parse without executing using that interpreter's supported facility.
3. If the parser reports a fatal syntax error, return before the actuation path with `executed=false`.
4. If parsing succeeds, execute the exact same bytes with the same resolved interpreter and non-interactive mode.
5. Echo a content digest and byte length in both the preflight and execution record so transport truncation can be distinguished from authoring error.

Use the shell's parser, not a custom quote counter. Bash documents `-n`/`noexec` as reading commands without executing them for syntax checking ([GNU Bash Reference Manual](https://www.gnu.org/software/bash/manual/bash.html)). PowerShell exposes `System.Management.Automation.Language.Parser.ParseInput`, returning an AST, tokens, and parse errors for supplied input ([Microsoft `Parser.ParseInput`](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.language.parser.parseinput?view=powershellsdk-7.4.0)).

Preflight result example:

```json
{
  "ok": false,
  "stage": "preflight",
  "code": "SHELL_PARSE_UNTERMINATED_QUOTE",
  "dialect_requested": "bash",
  "interpreter_resolved": "/usr/bin/bash",
  "interpreter_version": "...",
  "executed": false,
  "script_bytes": 83,
  "script_sha256": "...",
  "diagnostics": [
    {
      "severity": "fatal",
      "message_native": "...",
      "start_line": 2,
      "start_column": 7,
      "end_line": 2,
      "end_column": 28
    }
  ],
  "retry": {
    "retryable": true,
    "required_change": "script"
  }
}
```

The wrapper may normalize a stable top-level code, but it must retain the native diagnostic. It must not invent a closing quote or submit a repaired command automatically: the parser establishes invalidity, not author intent.

Expected catches:

- It is **almost certain (90-99%)** that an unterminated-quote script rejected by the same Bash or PowerShell parser at execution would be rejected at preflight, because the same parser sees the same bytes; this is **UNVERIFIED** until E2 establishes interpreter identity and differential equivalence.
- It is **likely (55-80%)** that source spans plus `executed=false` improve first-repair success versus a raw EOF fingerprint, because they reduce ambiguity in the agent's process model; this is **UNVERIFIED** until experiment **E3, blinded repair A/B**, compares otherwise identical agents given the old and new envelopes.
- It is **unlikely (20-45%)** that syntax preflight alone prevents semantic misuse, expansion surprises, command injection, wrong working directory, or a valid command with dangerous effects; the evidence is the parser's scope—it checks syntax, not owner intent or runtime state.

Counter-hazards:

- Native syntax checking may perform startup/configuration work or differ from execution mode. E2 must use non-interactive, startup-suppressed modes where supported and compare identities and modes.
- Some syntax depends on runtime dialect version or dynamically generated code. The result must not claim “safe”; it claims only “accepted by parser under recorded interpreter and mode.”
- Parse latency can tax high-volume calls. Measure it; do not cache results without binding the cache to content digest and interpreter identity.

Why this is not overfit: it delegates syntax to parsers already authoritative for execution and adds one pre-actuation hook. It does not build another language parser or policy framework.

### Proposal 3 — Stage-aware, state-repairing feedback contract — **UNVERIFIED**

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

**Unverified premise and settling experiment:** The premise that agents currently cannot reliably distinguish parser rejection from partial execution is **UNVERIFIED** because this ideation unit did not inspect present result schemas; experiment **E3, blinded repair A/B**, must first snapshot the actual envelope and then compare repair behavior.

Standardize the result schema across both lanes:

- `stage`: one of `validation`, `resolution`, `preflight`, `spawn`, `execution`, `timeout`, `collection`;
- `executed`: `false`, `true`, or `unknown`—never infer `false` merely from nonzero exit;
- `side_effect_status`: `none_by_contract`, `possible`, or `unknown`;
- requested and resolved dialect/program identity;
- stable machine code plus native diagnostic;
- source span when supplied by the native parser;
- retryability and what input/state must change before retry;
- content digest/length for script-mode action-path integrity.

This is a direct STPA feedback/process-model control. The agent needs to know which action it issued, whether it reached the process, how the process responded, and what state remains uncertain. The STPA Handbook specifically treats missing, delayed, incorrect, and misinterpreted feedback as causes of flawed process models and unsafe control actions ([STPA Handbook, pp. 42–47](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

Expected catches:

- It is **likely (55-80%)** that a required-change field reduces unchanged quote-error retries, because the controller is explicitly told that resubmission without script change cannot alter a deterministic parse result; this is **UNVERIFIED** until E3 measures identical-fingerprint retry loops.
- It is **likely (55-80%)** that `executed` and `side_effect_status` reduce unsafe “repair after unknown partial execution” behavior by improving the agent's process model; this is **UNVERIFIED** until E3 includes commands with controlled partial effects.

The contract does not claim that a nonzero exit implies no side effects. It also does not ask the adapter to infer whether owner intent was fulfilled.

Why this is not overfit: this is a JSON result-schema refinement on the existing bus. It adds no service and no learned critic.

## 4. What this catches that the measured path missed

The supplied 1,631 unmatched-quote EOF failures prove that those malformed calls were not arrested before reaching the shell parser. The proposals add earlier and more diagnostic control at four distinct points:

1. **Representation prevention:** simple arguments never enter shell grammar in `exec_program`.
2. **Context declaration:** actual scripts declare the dialect instead of relying on an implicit or inferred shell.
3. **Pre-actuation detection:** the resolved interpreter's native parser rejects fatal syntax before execution.
4. **Process-model repair:** feedback says where failure happened, whether execution occurred, what bytes were parsed, and what must change before retry.

The design also surfaces adjacent failure modes that a bare unmatched-quote detector misses:

- requested-versus-resolved interpreter mismatch;
- transport truncation, through digest/length mismatch;
- false rejection of valid shell constructs, through E4 compatibility testing;
- unchanged deterministic retry, through required-change feedback;
- ambiguous partial execution, through stage and side-effect status;
- silent loss of capability when argv cannot express a shell composition, through explicit script/legacy lanes and bypass metrics.

It is **very likely (80-90%)** that these controls catch more of the causal chain than a prompt reminder or quote-count heuristic, because they act at representation, native parsing, and execution-feedback boundaries rather than asking the same generator to self-judge the same string; this is **UNVERIFIED** until E1–E3 compare those baselines directly.

## 5. Adversarial evaluation of the analogy

### 5.1 Why STPA transfers

1. **Control, not component reliability, is the problem shape.** A shell may be perfectly reliable when it rejects malformed text; the unsafe system behavior is that the interface allowed ambiguous textual control to reach it and returned feedback too late or too vaguely. This matches STPA's focus on inadequate control and interaction.
2. **Context determines safety.** A quote is not intrinsically wrong. Its correctness depends on Bash versus PowerShell, syntactic position, interpolation, here-document rules, nested language boundaries, and transport. STPA forces context into each UCA.
3. **The agent has a process model.** It reasons about platform, cwd, prior effects, dialect, and command semantics. Feedback defects can therefore produce the same category of controller/reality mismatch STPA analyzes.
4. **Both controller and action path can fail.** The model may generate malformed text; the transport may truncate it; the adapter may select the wrong shell; the result may imply the wrong execution state. STPA explicitly separates why a UCA was selected from why an adequate action was improperly executed.
5. **Constraints become interface requirements.** “Fatal native parse error must precede actuation” and “simple argument boundaries must not be re-parsed as shell syntax” are enforceable design constraints, not exhortations.

The transfer is **very likely (80-90%)** to remain valid for other agent tools with stateful execution and structured feedback, based on these functional properties; that broader generalization is **UNVERIFIED** until experiment **E6, second-tool transfer**, applies the same UCA method to one non-shell high-error tool without changing the categories.

### 5.2 Where STPA does not transfer cleanly

1. **Loss severity differs.** Safety engineering often addresses death, injury, environmental damage, or mission loss. Many quote failures cost only a tool call and time. Heavyweight analysis would be disproportionate.
2. **The controller is stochastic and general-purpose.** Traditional automated controllers usually operate over bounded state variables and specified algorithms. A language model's process model is implicit, high-dimensional, and not directly inspectable.
3. **The controlled process is unusually heterogeneous.** The same text field can transit JSON, a host language, a Windows process API, Bash/PowerShell, SSH, and an embedded language. A single neat control diagram can hide rather than clarify these boundaries.
4. **STPA is a hazard-discovery method, not a parser or usability test.** It does not tell us that argv is usable, that native parse mode matches execute mode, or what error wording produces the best repair. Those require experiments.
5. **Worst-case reasoning can overblock.** Treating every possible shell effect as a safety-critical hazard could eliminate useful autonomy and create H4/L4. The unit's anti-overfit gate requires proportional controls.

Therefore this report borrows the UCA/context/feedback mechanism, not the whole safety-engineering institution.

### 5.3 Why Swiss cheese transfers only weakly

The active-failure/latent-condition distinction transfers: an unmatched quote is the active manifestation; an overloaded string interface, implicit dialect, or ambiguous feedback can be latent conditions. The demand for multiple defences also transfers only if the defences fail differently.

The metaphor fails if used to count correlated LLM checks as independent slices. Prompting, self-reflection, and a same-model critic can all miss the same construct. Even argv selection and script preflight share a tool adapter and could share a dialect-resolution defect. The controls must therefore be tested for common-mode failure rather than pictured as independent.

It is **roughly even (45-55%)** whether explicitly teaching the Swiss-cheese metaphor adds decision value beyond STPA plus tests, because the metaphor is memorable but underspecified and has documented interpretation problems. The evidence is Perneger's interpretation study and EUROCONTROL's qualified treatment. Accordingly, no standalone “Swiss-cheese layer manager” is proposed.

### 5.4 Why normal-accident theory is a warning, not the primary mechanism

Nested shell strings can exhibit interactive complexity: JSON escaping, model-generated quoting, host-language interpolation, shell expansion, and embedded commands interact nonlinearly from the author's perspective. Immediate execution tightly couples description to actuation. The theory supports simplifying the representation and inserting a monitored pre-actuation boundary.

But deterministic parser behavior, replayability, low typical consequence, and the ability to stop after an error are major disanalogies. It is **very unlikely (5-20%)** that quoting failures are inherently unavoidable in the strong normal-accident sense, based on the availability of argv interfaces and deterministic native parsing. The theory therefore vetoes elaborate add-on stacks; it does not justify fatalism.

### 5.5 Why safety cases transfer only as a micro-gate

Claims–argument–evidence structure transfers because “safer” is otherwise easy to assert from a single success metric. It becomes counterproductive if it grows into a large static dossier divorced from executable evidence. The harness needs a one-page/machine-readable release gate with live links to replay and shadow results, not a certification program.

It is **likely (55-80%)** that a compact evidence gate is net-positive for a high-volume core tool, while a full safety-case process would be net-negative, based on HSE's own allowance for simpler safety narratives and this brief's anti-overfit requirement; this is **UNVERIFIED** until E5 measures maintenance effort and whether the gate changes a release decision.

## 6. Experiments required before adoption

### E1 — Quote-fingerprint replay

**Question:** What proportion of the 1,631 supplied failures is preventable by argv, native parser preflight, both, or neither?

**Method:**

1. Build a replay set from the exact failed payload, declared/current shell metadata where available, and fingerprint. Preserve secrets by deterministic placeholders that retain quote and whitespace structure.
2. Prove the detector on known-present controls: one intentionally unterminated Bash quote and one intentionally unterminated PowerShell quote.
3. Classify each payload independently by (a) structural feature extraction and (b) replay result against the recorded dialect/version. Disagreement is “indeterminate,” not forced.
4. Test argv migration only where the intended operation can be represented as a single executable plus arguments without changing shell semantics.
5. Report numerator/denominator for prevented-before-execution, still-invalid, semantically nonmigratable, dialect unknown, and nonreplayable.

**Acceptance:** Do not set a threshold in advance from intuition. Establish baseline coverage, then require that prevented failures materially exceed introduced false blocks in E4 and that no semantic-equivalence failures are accepted as successes.

### E2 — Parser differential

**Question:** Does preflight agree with the execution parser without executing user code?

**Method:** Cross product of supported interpreter versions with malformed quotes, valid quoting, here-documents/here-strings, nested substitutions, multiline strings, comments, escaped newlines, and Unicode. Record requested/resolved interpreter path, version, mode, bytes, digest, parse disposition, and execution-parser disposition in an isolated no-side-effect fixture.

**Independent completion signals:** (1) native parser result and (2) actual interpreter parse result in a disposable fixture. Re-running the native parser is not a second signal.

**Acceptance:** zero known false negatives for the supplied unmatched-quote class on supported versions; every disagreement blocks rollout for that interpreter/mode until explained. This acceptance target is a design criterion, not a forecast.

### E3 — Blinded repair A/B

**Question:** Does structured feedback improve recovery without prompting semantic drift?

**Method:** Give otherwise identical agent runs either the current error or the stage-aware envelope. Blind the agent to condition. Measure first-repair success, unchanged-payload retry rate, number of tool calls to recovery, semantic equivalence of repaired intent, and unsafe actions after deliberately ambiguous partial execution.

**Acceptance:** pre-register thresholds after baseline variance is measured; require improvement in recovery and no worsening in semantic drift or side-effect handling.

### E4 — Valid-command compatibility and capability test

**Question:** What does the control wrongly reject or make inexpressible?

**Method:** Use successful production scripts plus adversarial valid constructs. Prove the detector can identify known-valid and known-invalid controls. Compare old and new execution outputs/exit/side-effect fixture state. Track fallback to the explicit script or legacy lane.

**Acceptance:** no silent semantic translation; false rejects and fallback rates reported with confidence intervals; any owner-critical construct receives a documented supported path.

### E5 — Shadow traffic and micro-case gate test

**Question:** Does the intervention reduce total failures in live-like traffic, and can the assurance gate detect incomplete evidence?

**Method:** Run new classification/preflight in shadow mode without blocking. Compare predicted catches to actual outcomes. Inject one evidence package missing false-positive results and one complete synthetic package. The gate must reject the former and admit the latter.

**Rollout:** canary by lane and interpreter version, with automatic rollback on false-block or latency budget breach. The proposition that a canary will preserve user capability is **likely (55-80%)**, based on limiting exposure and keeping explicit fallback, but is **UNVERIFIED** until E5 exercises rollback end to end.

### E6 — Second-tool transfer (optional boundary test)

Apply the same four UCA categories and feedback analysis to one non-shell tool with a known high error rate. If the analysis merely renames generic error handling and yields no new constraint, stop claiming broad harness applicability. This experiment is optional for the shell decision but required for broader generalization.

## 7. Mechanically independent signals and detector discipline

The safety borrow itself implies a validation rule for the harness:

- **Prevention signal:** structured argv makes shell parsing inapplicable, demonstrated by captured child `argv` in a fixture.
- **Detection signal:** the native parser rejects malformed script bytes before actuation.
- **Outcome signal:** an isolated execution fixture confirms that no controlled-process side effect occurred for rejected input.
- **Feedback signal:** the tool result independently records `executed=false`, stage, interpreter identity, and content digest.

No “done” claim may rely only on the wrapper's own status bit. For a rejected command, use at least native-parser rejection plus an independently observed absence of the fixture side effect; first prove the fixture observer detects a known-present side effect. For correct argv boundaries, compare adapter-captured serialized arguments with a child process that independently prints length-prefixed arguments.

It is **very likely (80-90%)** that this two-signal discipline catches adapter self-reporting bugs that a status-only test misses, because the signals observe different mechanisms (parser result versus controlled-process state; adapter serialization versus child-observed argv). This is **UNVERIFIED** until E2/E4 include seeded lying-status and truncation faults.

## 8. Alternatives considered and rejected

### Prompt-only quoting rules

Rejected as the primary control. They operate in the same stochastic controller that generated the malformed string and do not change the action path or feedback. They may remain educational context, but counting them as a defence would be weak Swiss-cheese reasoning.

### Custom quote-count linter

Rejected. Counting delimiters is not equivalent to parsing Bash or PowerShell, and legal constructs vary by dialect and syntactic context. It risks both false negatives and H4 false blocks. Native parsers already define the accepted language.

### Automatic quote repair

Rejected. An unmatched delimiter identifies malformed syntax but not intended grouping, interpolation, or literal content. Automatic insertion can turn a nonexecuting failure into a valid but wrong state-changing command, converting L1 into L3.

### Same-model critic or trained command critic

Rejected. It reintroduces a previously rejected trained-critic/guardrail pattern, shares common-mode representation failures with the generator, adds latency, and cannot provide parser authority. No exception is justified for deterministic syntax.

### Universal shell AST or new command DSL

Rejected. A universal Bash/PowerShell/Windows/remote-shell AST is a BUILD-LARGE second language/runtime with substantial semantic surface. It violates the anti-overfit gate when argv plus declared native script mode covers the relevant boundary.

### Multiple safety layers managed by a daemon

Rejected. This would be a BUILD-LARGE guardrail framework/second runtime, explicitly disallowed by the anti-overfit gate absent extraordinary justification. The proposed adapter and schema checks fit the existing bus.

### Ban shell use

Rejected. Pipelines, redirections, builtins, and short compound scripts are legitimate capabilities. Removing them would create H4, induce awkward substitutes, and likely drive bypass.

### Full formal verification of commands

Rejected for this failure class. Syntax validity is decidable by the native parser, but owner intent and arbitrary command side effects are not captured by quote correctness. A formal layer would be disproportionate and would not solve the semantic specification problem.

## 10. Final judgment

**Borrow STPA; constrain Swiss cheese; use normal-accident theory as a complexity veto; use a micro safety case as an evidence gate.**

The core STPA transfer is **very likely (80-90%)** sound because the agent-tool interaction is functionally a feedback control loop and the failure is contextual inadequate control rather than shell unreliability. The most concrete design consequence is to stop representing every process launch as an undifferentiated shell program: preserve argument boundaries for ordinary commands, declare dialect for actual scripts, preflight with the exact native parser, and report execution state in feedback.

The predicted reduction is **likely (55-80%)** to be material across the supplied 1,631 unmatched-quote failures, based on removing shell grammar from simple calls and detecting fatal syntax in true scripts, but this remains **UNVERIFIED** until E1–E5 establish case mix, parser equivalence, repair benefit, compatibility, and shadow results. A claim that all 1,631 would disappear is **very unlikely (5-20%)**, because nested languages, Windows launch behavior, genuine scripting, and non-syntax causes remain.

The analogy should not be stretched into a safety bureaucracy or layered guardrail product. Its best contribution is a sharper question: **what unsafe control action did the interface permit, under what context, which process-model fact was missing, and what mechanically independent feedback would have prevented or repaired it?** For unmatched shell quotes, that question leads to a small and testable interface change rather than another autonomous subsystem.
