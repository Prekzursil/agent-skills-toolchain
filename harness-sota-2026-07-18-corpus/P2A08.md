# P2A08 — Deterministic guardrails around probabilistic agents

**Unit:** P2A08 — external research: hooks-and-guards  
**Date:** 2026-07-18  
**Scope:** Hook systems, policy engines, and the use-vs-mention failure mode. This is an external-evidence lens. I did not inspect or derive claims from the owner's local harness, repository, corpus, or earlier audit.

## Executive answer

The known-good pattern is not “find dangerous words in agent text.” It is a small reference monitor on the **structured action path**: intercept every effectful tool call after arguments exist but before execution; validate a typed, canonical request; combine policy with deny-first precedence; require user approval where policy cannot decide; execute under least privilege; and log the decision and outcome. This is the direct application of complete mediation, fail-safe defaults, and least privilege from Saltzer and Schroeder, and of NIST's reference-monitor requirement that the mechanism be always invoked, tamper-resistant, and small enough to verify ([Saltzer & Schroeder](https://www.cs.virginia.edu/~evans/cs551/saltzer/), [NIST SP 800-53 Rev. 5, AC-25](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53r5.pdf)).

The use-vs-mention bug is a type error. `rm -rf /` as the command position of an executable shell AST is an attempted use; the same bytes inside `Write.content`, a quoted `echo` argument, a Markdown example, or a policy test fixture are mentions. A substring scanner discards those types and therefore cannot reliably tell the cases apart. Claude Code's current permission system already parses compound Bash commands and the PowerShell AST, checks subcommands independently, and warns that argument-constraining wildcard rules are fragile ([Claude Code permissions: compound commands and PowerShell AST](https://code.claude.com/docs/en/permissions#bash)). More generally, security research on data confusion recommends parsing into normalized, unambiguous forms rather than scanning raw rich content ([Samuel and Erlingsson, “Let's Parse to Prevent Pwnage”](https://research.google/pubs/lets-parse-to-prevent-pwnage/)).

Prompt-based or classifier-based guards can help triage ambiguous cases, but they are not deterministic enforcement. Static evaluations have repeatedly overstated their robustness: adaptive attacks bypassed eight indirect-prompt-injection defenses at over 50% attack success, and a later scaled study bypassed 12 recent defenses above 90% for most ([Zhan et al.](https://arxiv.org/abs/2503.00061), [Nasr et al.](https://arxiv.org/abs/2510.09023)). The deterministic boundary should therefore constrain what an injected or mistaken agent can do even when the model-level detector fails.

The recommended architecture is deliberately small: use native permission parsing, native pre-tool hooks, native sandboxing where supported, and one small pure policy adapter plus tests. Do **not** add an OPA daemon, a second orchestration runtime, a guardrail framework, or a CaMeL-style interpreter now. Those violate the anti-overfit gate for this owner unless a measured policy-complexity threshold is later crossed.

## Research method and source quality

I divided the question into four lanes: (a) lifecycle interception and hook failure semantics; (b) mature policy-engine properties; (c) parsing/provenance and use-vs-mention; and (d) empirical agent-guardrail results. I searched official vendor documentation, specifications, primary papers, peer-reviewed proceedings, and authors' repositories. I deep-read the key hook, permission, sandbox, MCP, OPA/Cedar, AgentDojo, Spotlighting, CaMeL, and adaptive-attack sources rather than relying only on snippets.

The available provider was the web search/open interface. The optional Firecrawl, Exa, Tavily, scholarly-access, and Context7 providers named by the research skill were not exposed in this session; provider-diverse result comparison was therefore unavailable. Source diversity instead comes from independent publishers and mechanisms: Anthropic and MCP specifications for runtime behavior, NIST and classic security literature for reference-monitor principles, OPA/Cedar for policy design, and multiple independent research groups for empirical attack/defense results.

## 1. What is actually established

### 1.1 Enforce at the effect boundary, with complete mediation

Saltzer and Schroeder's established principles remain the right baseline: access should be based on permission rather than exclusion (fail-safe defaults), **every** access to **every** object should be checked (complete mediation), and each program should run with only the privileges needed (least privilege) ([original paper](https://www.cs.virginia.edu/~evans/cs551/saltzer/)). NIST's AC-25 reference-monitor control restates the engineering properties: the reference validation mechanism is always invoked, tamper-proof, and verifiable ([NIST SP 800-53 Rev. 5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53r5.pdf)). These properties are independent of LLMs.

For an agent, the security-relevant moment is a proposed tool invocation, not the prose that preceded it. Claude Code's `PreToolUse` event runs after the model has produced `tool_name` and `tool_input` but before the call executes, and can allow, deny, ask, defer, or replace the input ([hooks reference](https://code.claude.com/docs/en/hooks#pretooluse)). OpenAI's Agents SDK makes the same workflow distinction: agent input/output guardrails cover only the first/final agent, whereas tool guardrails run around every custom function-tool invocation; blocking input guardrails must run before the agent if side effects must not begin ([OpenAI Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/)). Two independent implementations thus expose the same architectural seam.

Complete mediation includes alternate paths. Claude's documentation explicitly notes that a `PreToolUse` hook on `Skill` does not cover direct `/skillname` invocation, so `UserPromptExpansion` exists for that path; likewise, `@file` inclusion does not issue a `Read` tool call, so a `Read` deny rule—not a pre-tool hook—is required ([Claude hooks: UserPromptExpansion and `@` references](https://code.claude.com/docs/en/hooks)). This is a concrete example of why “a hook exists” is not proof that a policy is complete.

### 1.2 Typed requests and real parsing solve use-vs-mention at the right layer

MCP tools have a unique name and a JSON Schema for input, and may declare a schema for structured output. Servers must validate inputs; clients should validate results, show sensitive tool inputs before execution, use timeouts, and log use ([MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). Cedar likewise treats a schema as a contract between requests and policy; its validator's soundness is formally proved for the documented error classes, with differential testing between the Lean and Rust implementations ([Cedar validation](https://docs.cedarpolicy.com/policies/validation.html)). The established lesson is to make policy decisions over a validated record, not over an undifferentiated transcript.

Claude Code's current shell permission matcher is syntax-aware. It recognizes `&&`, `||`, `;`, pipes, background operators, and newlines and requires each Bash subcommand to match independently. For PowerShell it canonicalizes aliases, parses the PowerShell AST, and checks compound commands separately. The same documentation cautions that wildcard patterns intended to constrain command arguments are fragile under option reordering, variables, redirects, and whitespace ([permissions reference](https://code.claude.com/docs/en/permissions#bash)). This directly supports three rules:

1. classify the tool and operation from typed fields;
2. for shell tools, inspect parser nodes/command positions rather than raw substrings;
3. if parsing or canonicalization is incomplete, escalate (`ask`) instead of guessing.

Tree-sitter provides a maintained Bash grammar, but Tree-sitter describes itself as a concrete-syntax-tree parser for programming tools, not a shell security oracle ([Tree-sitter](https://github.com/tree-sitter/tree-sitter), [Bash grammar listing](https://github.com/tree-sitter/tree-sitter/wiki/List-of-parsers)). ShellCheck is useful for supported Bourne-family syntax and quoting errors but explicitly does not support PowerShell ([ShellCheck SC1071](https://www.shellcheck.net/wiki/SC1071)). Therefore parser choice must follow the actual execution language; one regex or one parser cannot faithfully cover Bash, PowerShell, `cmd.exe`, Python wrappers, and nested interpreters.

### 1.3 Deny-first composition and explicit failure semantics are known-good

AWS IAM provides a mature example of fail-safe composition: requests are implicitly denied until allowed, and any applicable explicit deny overrides an allow ([AWS IAM evaluation logic](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)). Claude Code follows a similar restrictive lattice: permission rules are evaluated deny, then ask, then allow; hook decisions do not bypass deny/ask rules; among multiple pre-tool hooks, the more restrictive decision wins ([Claude permissions](https://code.claude.com/docs/en/permissions), [hooks guide](https://code.claude.com/docs/en/hooks-guide#combine-results-from-multiple-hooks)).

Failure behavior must be designed, not assumed. In Claude Code, exit 2 blocks on block-capable events, but ordinary nonzero hook exits generally report an error and let the action proceed. JSON output is processed only on exit 0. Multiple matching hooks run in parallel, and a denying hook does not prevent a sibling hook's side effect ([Claude hooks reference](https://code.claude.com/docs/en/hooks), [hooks guide](https://code.claude.com/docs/en/hooks-guide)). OpenAI's input guardrails run in parallel by default, which lowers latency but can allow token consumption and tool activity before cancellation; blocking mode completes the guard first ([OpenAI Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/)). A security gate must therefore choose blocking mode for irreversible actions and must translate its own crash/timeout into a defined `deny` or `ask`, rather than inheriting a framework's convenience default.

### 1.4 Separate policy decision, enforcement, and audit

OPA's established architecture separates policy decision-making from enforcement and evaluates structured JSON against declarative Rego policy ([OPA overview](https://www.openpolicyagent.org/docs)). Its decision logs can include the decision ID, queried policy, input, result, bundle revision, and trace identifiers; it also provides policy-controlled masking for sensitive fields ([OPA decision logs](https://www.openpolicyagent.org/docs/management-decision-logs)). OPA supports unit tests and coverage, and its bundle mechanism supports revisions, validation, and signatures ([OPA policy testing](https://www.openpolicyagent.org/docs/policy-testing), [OPA bundles](https://www.openpolicyagent.org/docs/management-bundles)). Cedar demonstrates that schema validation, formal specification, and differential/property testing are practical in a production policy language ([Cedar policy organization](https://github.com/cedar-policy), [Cedar validation](https://docs.cedarpolicy.com/policies/validation.html)).

The harness does not need either engine to adopt their good properties. The portable minimum is:

- a versioned structured request;
- a pure, deterministic decision function;
- a small set of outcomes (`deny`, `ask`, `allow`, and optionally `defer`);
- a reason code and policy version;
- a separate enforcement adapter;
- redacted decision/outcome records;
- table-driven tests, negative tests, and coverage of alternate paths.

### 1.5 Capability and provenance beat content-based notions of danger

MCP's risk annotations—`readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`—are useful vocabulary, but the specification community is explicit that they are untrusted hints unless the server is trusted ([MCP tool-annotations analysis](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)). Thus, they may raise risk but cannot safely grant permission by themselves.

The deeper prompt-injection problem is code/data confusion. Spotlighting states that an LLM receives a boundary-less token stream and can mistake untrusted document instructions for trusted commands ([Hines et al.](https://arxiv.org/abs/2403.14720)). CaMeL instead extracts control and data flow from the trusted query and attaches capabilities to prevent unauthorized data flows; it reports 67% of AgentDojo tasks completed with its stated security guarantee ([CaMeL paper](https://arxiv.org/abs/2503.18813)). These results support a system-level principle: untrusted text may supply **data values**, but it must not silently acquire the authority to choose a privileged operation or destination.

### 1.6 Sandboxing limits consequences even when the decision layer is wrong

Claude Code's sandbox uses OS-level filesystem and network isolation for Bash and descendants on macOS, Linux, and WSL2. Its documentation recommends `failIfUnavailable: true` when sandboxing is a hard gate and allows disabling the unsandboxed escape hatch; it also documents important limitations, including no native-Windows sandbox, risks from Unix sockets, broad write paths, and hostname-only network controls without TLS inspection ([Claude sandboxing](https://code.claude.com/docs/en/sandboxing), [configuration keys](https://code.claude.com/docs/en/configuration#sandbox-settings)). This is defense in depth, not a substitute for action policy, because built-in file tools and computer use have separate boundaries.

## 2. What is promising but unproven

### 2.1 Provenance-tainted values and capability-carrying plans — UNVERIFIED

**very likely (80-90%)**, based on the classic complete-mediation model, CaMeL's control/data-flow construction, and the fact that content-only defenses repeatedly fail under adaptive attack, that provenance labels on tool results plus capability checks at privileged sinks will reduce a broad class of indirect prompt-injection failures ([CaMeL](https://arxiv.org/abs/2503.18813), [adaptive evaluation](https://arxiv.org/abs/2510.09023)). This is not established for this owner's coding harness. **UNVERIFIED — settle with an experiment that labels web/MCP/file-derived values, then runs benign and adversarial tasks where those values populate shell commands, file destinations, URLs, git refs, and outbound messages; measure unsafe-action rate and benign task completion against the current harness.**

The important scope limit is that provenance does not decide user intent. A value from a web page may legitimately become a package version or filename. The defensible rule is narrower: untrusted provenance cannot by itself mint authority for a new high-risk operation, principal, destination, or secret-bearing flow.

### 2.2 A task-alignment critic isolated from untrusted content — UNVERIFIED

**likely (55-80%)**, based on Task Shield's reported 2.07% attack success rate and 69.79% utility on its AgentDojo evaluation, that a narrowly scoped critic seeing only trusted user intent plus canonical action metadata can improve decisions at ambiguous high-risk sinks ([Task Shield, ACL 2025](https://aclanthology.org/2025.acl-long.1435/)). However, this remains probabilistic and benchmark-dependent. **UNVERIFIED — settle with a defense-aware red team that can adapt to the critic, plus a false-positive suite containing quoted dangerous text, security research, deletion tests in disposable directories, and legitimate release/deploy actions.** It must advise `ask`, never autonomously convert denial to allow.

### 2.3 Spotlighting/datamarking as an input-hygiene layer — UNVERIFIED

**likely (55-80%)**, based on the original experiments reducing attack success below 2% in some settings with little measured task loss, that provenance marking of external text will reduce casual injection attempts ([Spotlighting](https://arxiv.org/abs/2403.14720)). The same paper says simple delimiter-only defenses can be subverted and encoded text can harm weaker models. Strong adaptive attacks later broke most tested prompt defenses above 90% ([Nasr et al.](https://arxiv.org/abs/2510.09023)). **UNVERIFIED — settle with an adaptive attack against the exact models, prompt templates, and tool surface used by this harness.** Treat marking as context hygiene, never as authorization.

### 2.4 System-level agent defenses such as CaMeL and information-flow control — UNVERIFIED

**likely (55-80%)** to become an important architecture for agents operating on untrusted content, based on CaMeL's 67% secure task completion and multiple independent information-flow-control proposals ([CaMeL](https://arxiv.org/abs/2503.18813), [AgentDojo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html)). For this owner today, a wholesale adoption is **UNVERIFIED — settle with a side-by-side prototype on at least 50 representative coding-agent tasks, including dynamic discovery and underspecified tasks, measuring completion, intervention rate, latency, and bypasses.** The authors' released repository warns that the interpreter likely contains bugs, may not be fully secure, and is an unsupported research artifact ([CaMeL repository](https://github.com/google-research/camel-prompt-injection)).

### 2.5 Formal policy languages for a personal harness — UNVERIFIED

**unlikely (20-45%)** to provide net value now, because the owner's required decisions appear small enough for a typed table and because OPA/Cedar introduce language, packaging, and integration surface. The engines' benefits are real—structured policy, tests, schemas, decision logs, and in Cedar's case formal validation—but OPA itself documents memory/performance tradeoffs and deployment choices ([OPA performance](https://www.openpolicyagent.org/docs/policy-performance), [Cedar validation](https://docs.cedarpolicy.com/policies/validation.html)). **UNVERIFIED — settle with a threshold experiment: implement the same policy matrix as a pure local function and as embedded OPA Wasm or Cedar; compare lines, dependencies, cold-start latency, test clarity, auditability, and change-defect rate over ten policy revisions.**

## 3. What is hype, and how to tell

### 3.1 “Regex blocks dangerous commands”

This is category error, not a security boundary. It confuses bytes with syntax and authority. A claim is hype when its examples test only direct execution strings and omit: quoted strings, here-documents, comments, Markdown/code fixtures, encoded commands, variables, aliases, compound commands, wrappers, nested interpreters, and parser failure. Claude's own documentation says Bash argument patterns are fragile and uses AST parsing for PowerShell ([permissions reference](https://code.claude.com/docs/en/permissions#bash)); parsing research identifies data confusion as a recurring source of injection bugs ([Samuel and Erlingsson](https://research.google/pubs/lets-parse-to-prevent-pwnage/)).

### 3.2 “Deterministic hooks” implemented with an LLM judge

Claude supports prompt and agent hooks specifically for judgments that deterministic rules cannot make, and those hooks call a model ([hooks guide](https://code.claude.com/docs/en/hooks-guide#prompt-based-hooks)). Calling that layer deterministic because the surrounding lifecycle is deterministic is hype. A useful test is replay: if identical structured input and policy version can yield different decisions, it is not the deterministic reference monitor. LLM judgment can route to `ask`; it cannot be the sole authorization source for destructive or externally visible actions.

### 3.3 “Near-zero attack success” on a static benchmark

The red flags are a fixed attack corpus, no defense-aware adaptation, no benign false-positive set, and no action-open/underspecified tasks. AgentDojo is a valuable extensible benchmark with 97 tasks and 629 security cases, but its authors themselves frame it as an evolving environment ([AgentDojo paper](https://arxiv.org/abs/2406.13352)). Adaptive work bypassed eight defenses over 50%, and scaled attacks bypassed 12 defenses above 90% for most despite many originally reporting near-zero rates ([Zhan et al.](https://arxiv.org/abs/2503.00061), [Nasr et al.](https://arxiv.org/abs/2510.09023)). AgentDyn further reports that almost all ten evaluated defenses were either insufficiently secure or over-defensive on its newer open-ended tasks ([AgentDyn](https://arxiv.org/abs/2602.03117)). **UNVERIFIED — AgentDyn is a 2026 preprint; settle its claims through independent reproduction on the released benchmark.**

### 3.4 “Provable security” without a threat-model boundary

Proofs can be valuable, but the guarantee is only about the formalized system. CaMeL's 67% refers to tasks for which its control/data-flow and capability model can enforce the stated property, while its repository explicitly warns that the implementation may be buggy and not fully secure ([paper](https://arxiv.org/abs/2503.18813), [repository](https://github.com/google-research/camel-prompt-injection)). Cedar carefully lists errors its validation proof does not preclude ([Cedar validation limitations](https://docs.cedarpolicy.com/policies/validation.html)). Hype drops these qualifiers and turns “proved under assumptions” into “safe in production.”

### 3.5 “Tool annotations make a tool safe”

MCP annotations are intentionally hints and untrusted unless the server itself is trusted ([MCP tool annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)). A server-provided `readOnlyHint: true` cannot grant authority. Hype can be detected by whether the design verifies server identity and maintains a local override/risk registry, or simply trusts self-description.

### 3.6 “Install a policy platform for governance”

OPA and Cedar are serious systems, but adding a daemon, control plane, SaaS, or policy language before policy complexity warrants it is platform-shaped overfitting. OPA explicitly separates the decision engine from a control plane and does not ship the latter out of the box ([OPA management architecture](https://www.openpolicyagent.org/docs/management-introduction)). For this owner's minimal harness, a pitch that does not first show a policy count, change rate, multi-process need, or measured defect that a typed local function cannot handle is hype.

## 4. Specific things this owner's harness should adopt

Each proposal includes the mandatory implementation tag and an explicit anti-overfit decision.

### A. Replace prose scanning with a typed pre-action policy envelope

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: almost certain (90-99%)**, because typed tool inputs already exist in Claude hooks and MCP, and established reference-monitor principles require policy at the action boundary ([Claude PreToolUse](https://code.claude.com/docs/en/hooks#pretooluse), [MCP tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [NIST AC-25](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-53r5.pdf)).

Define one normalized record:

```json
{
  "schema": 1,
  "event": "pre_tool_use",
  "tool": "PowerShell",
  "operation": "Remove-Item",
  "resource": "C:/resolved/target",
  "effect": "delete",
  "provenance": "model_tool_input",
  "parse_status": "complete",
  "risk": ["destructive", "local"],
  "policy_version": "<content hash>"
}
```

The adapter must read only the event's typed action fields. It must never scan `prompt`, `additionalContext`, assistant prose, file content, `Write.content`, or arbitrary transcript text for command keywords. Policy returns `{decision, reason_code, explanation, policy_version}`. Keep decision pure; logging and user display are separate.

**Anti-overfit gate:** passes. It is one small adapter on the existing pre-tool hook bus. No second runtime, database, daemon, trained critic, SaaS, or guardrail framework.

### B. Use native shell parsing; parser uncertainty becomes `ask` — UNVERIFIED

**Tag: NATIVE (Claude Code already does this; we just enable it).**  
**Confidence: very likely (80-90%)**, because current Claude Code documentation says Bash compound commands are split and PowerShell commands are AST-parsed before permission matching ([permissions reference](https://code.claude.com/docs/en/permissions#bash)). The residual uncertainty is version/platform behavior. **UNVERIFIED — settle with a version-pinned acceptance test on this Windows host containing direct use, quoted mention, comments, here-strings, pipelines, aliases, variables, `Invoke-Expression`, `powershell -Command`, `bash -lc`, and malformed input.**

Use native `deny`/`ask` permission rules for broad command families and hook `if`/tool matchers where available. Do not reimplement shell tokenization with regex. For an execution language not parsed natively, call its real parser (PowerShell's parser API; a maintained Bash parser for Bash) and treat parse failure, dynamic evaluation, nested interpreters, or unresolved command position as `ask`. A quoted dangerous string passed to `echo`, `rg`, a test runner, or `Write.content` remains data unless an actual interpreter sink consumes it.

**Anti-overfit gate:** passes. It preferentially removes custom mechanism. A small parser adapter is permitted only for an uncovered native gap; building a universal shell parser fails the gate.

### C. Install a four-outcome, deny-first decision lattice

**Tag: CONFIG (settings/JSON only).**  
**Confidence: almost certain (90-99%)**, from AWS's deny-by-default/explicit-deny precedence and Claude's documented `deny > defer > ask > allow` hook merge ([AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html), [Claude hooks](https://code.claude.com/docs/en/hooks)).

Use:

- `deny`: invariant violation or dangerous action outside authorized scope;
- `ask`: syntactically valid but materially risky/ambiguous action;
- `defer`: external UI or asynchronous approval is required;
- `allow`: validated low-risk operation inside explicit scope.

Only irreversible/dangerous actions should hard-block. Ordinary mistakes should inject precise corrective context, matching the owner's existing behavior contract. A sibling hook may log but must not mutate state before the final decision, because matching hooks run in parallel ([hooks guide](https://code.claude.com/docs/en/hooks-guide#combine-results-from-multiple-hooks)).

**Anti-overfit gate:** passes; this is configuration of the native decision bus.

### D. Make hook crash/timeout behavior risk-sensitive and explicit

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: very likely (80-90%)**, because Claude normally proceeds on nonzero exits other than 2 and OpenAI's parallel guardrails may permit work before cancellation ([Claude hooks](https://code.claude.com/docs/en/hooks), [OpenAI guardrails](https://openai.github.io/openai-agents-python/guardrails/)).

Wrap the policy evaluator so an internal exception, invalid JSON, timeout, missing parser, or schema mismatch produces:

- `ask` for destructive, secret-bearing, externally visible, privilege-changing, or open-world operations;
- a nonblocking error plus telemetry for low-risk local reads and reversible workspace edits;
- never silent allow.

Return valid structured JSON on exit 0 for normal decisions; reserve exit 2 for hard blocks. Emit a stable terminal marker such as `SUCCESS:<decision-id>` or `FAILED:<decision-id> <reason-code>`.

**Anti-overfit gate:** passes; this is a thin reliability wrapper, not durable execution.

### E. Add a trusted local risk registry; treat MCP annotations as untrusted hints

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: very likely (80-90%)**, because MCP explicitly labels tool annotations as hints that clients must not trust absent a trusted server ([MCP tool annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)).

Key by canonical tool identity and optionally operation. Record local facts: trusted server identity, read/write/destructive/open-world/secret-bearing, idempotence, user-interaction requirement, and approved resource scopes. Server annotations can only raise risk or populate an unknown field; they cannot reduce locally assigned risk or auto-allow. Unknown tools default to `ask`, not deny, so expansion remains usable.

**Anti-overfit gate:** passes. A small versioned JSON registry is enough; no service or knowledge graph.

### F. Bind approval to the canonical action, not to a prose description — UNVERIFIED

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: likely (55-80%)**, based on MCP's recommendation to show tool inputs before sensitive calls and established authorization practice, but the best receipt format for this harness is not externally established ([MCP tools security considerations](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). **UNVERIFIED — settle with a replay test that changes one canonical field after approval and confirms re-approval is required.**

Hash `{tool, normalized operation, resolved resources, effect, destination, policy_version}` and bind approval to that hash, one session, a short TTL, and preferably one execution. Any mutation, redirect target change, symlink resolution change, wrapper insertion, or policy-version change invalidates it. Display the canonical fields, not the agent's friendly summary.

**Anti-overfit gate:** passes if implemented as an ephemeral hook receipt. Durable workflow execution or a new approval service would fail.

### G. Add a use-vs-mention and alternate-path conformance suite

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: almost certain (90-99%)**, because the failure class follows directly from parsing ambiguity and because OPA/Cedar demonstrate policy unit, coverage, property, and differential testing ([OPA testing](https://www.openpolicyagent.org/docs/policy-testing), [Cedar project](https://github.com/cedar-policy)).

Every dangerous pattern needs paired fixtures:

- **use:** actual executable/operation node must deny or ask;
- **mention:** same bytes in prose, a quoted argument, file content, fixture, comment, or expected-error string must allow;
- **obfuscated use:** aliases, case changes, option reorder, variables, compound commands, pipelines, wrappers, nested interpreters, encoded commands;
- **parser failure:** malformed/unsupported input must ask;
- **alternate path:** direct skill expansion, `@file`, built-in file tools, shell subprocess, MCP tool, and computer-use route where applicable;
- **known-present control:** each detector test first proves it sees a safe known-present action and a dangerous known-present action.

Add metamorphic properties: quoting an argument as data must not turn it into a command; adding whitespace must not change effect classification; changing a write target outside scope must never reduce risk; wrapping an operation must not erase the inner effect. Report false-positive and false-negative rates separately.

**Anti-overfit gate:** passes. This is a compact regression corpus on the existing test bus.

### H. Log decision facts and execution outcomes locally, with redaction

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**  
**Confidence: very likely (80-90%)**, based on OPA's decision-log fields and MCP's audit recommendation ([OPA decision logs](https://www.openpolicyagent.org/docs/management-decision-logs), [MCP tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)).

Record decision ID, timestamp, event/tool, canonical operation/effect, redacted resource class, decision, reason code, policy hash, parser version/status, approval receipt ID, execution success/failure, and duration. Never log raw secrets or full untrusted documents. Separate “policy allowed” from “tool succeeded”; neither implies task completion. Use shadow mode only when introducing new non-safety rules; hard invariants remain enforced.

**Anti-overfit gate:** passes. Append-only local JSONL is sufficient. Observability SaaS, vector storage, and a new telemetry service fail the gate.

## 5. Concrete reference design

```text
trusted user request / managed policy
                 |
                 v
       probabilistic planner/model
                 |
        typed proposed tool call
                 |
                 v
  native parser + canonicalizer ---- parse incomplete ----> ASK
                 |
        structured policy envelope
                 |
                 v
      pure local decision function
       DENY | ASK | DEFER | ALLOW
                 |
       approval bound to action hash
                 |
                 v
 native permission layer + sandbox / scoped credential
                 |
                 v
              execution
                 |
      redacted decision + outcome log
```

Untrusted web/file/MCP/subprocess text may inform the planner and fill data fields, but it never bypasses the structured policy envelope. The model can propose; the reference monitor disposes. Hard policy remains deterministic; probabilistic critics may only increase scrutiny or recommend `ask`.

## 6. Acceptance criteria for “done”

A later build unit should not call this complete until two mechanically independent signals agree for each property:

1. **Lifecycle coverage:** configuration inspection shows the gate attached to every relevant action path, and black-box canaries demonstrate it fires on known-present tool, direct-skill, `@file`, and subprocess cases.
2. **Use-vs-mention:** table tests pass paired use/mention fixtures, and transcript-level replay shows no block on prose-only mentions while direct executable nodes are blocked.
3. **Failure semantics:** unit injection makes the evaluator throw/timeout and yields `ask`/deny according to risk; a black-box attempted action confirms no side effect occurred for high-risk cases.
4. **Decision precedence:** unit tests prove deny-first combination; an integration case with simultaneous allow and deny confirms the native runtime blocks.
5. **Approval binding:** receipt-unit tests reject mutated action hashes; integration replay with a changed target prompts again.
6. **Audit:** schema validation proves required fields and redaction; an independent correlation check joins decision ID to the actual tool outcome.
7. **Sandbox:** configuration reports sandbox active with hard failure, and forbidden filesystem/network probes fail from a child process. A tool-level check separately verifies built-in file permissions.
8. **Utility:** benign completion and intervention rates are measured, including security research and documentation tasks rich in dangerous-looking mentions.

## Bottom line

Adopt a small reference monitor, not a prose censor. Parse the actual action, keep mentions typed as data, make deny/ask/allow semantics explicit, mediate every path, bind approvals to canonical actions, run with least privilege, and test both false positives and bypasses. Use model-based guards only to raise scrutiny. Preserve the minimal harness by riding native permissions, hooks, schemas, and sandboxing; defer OPA/Cedar and full information-flow runtimes until measurements justify their cost.
