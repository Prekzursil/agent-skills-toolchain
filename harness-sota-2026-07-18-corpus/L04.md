# L04 — Anti-slop / quality-perfection enforcement

## The build-then-prove-it-works loop: evidence required for a `done` claim, by artifact type

**Unit:** L04, partner-dimension / anti-slop family  
**Date:** 2026-07-19  
**Scope:** research and design only. The subject bundle was read-only. The only file written is this artifact.

## Executive answer

`Done` must mean **the stated acceptance claims are covered by fresh, artifact-specific proof sets, and every proof set contains at least two mechanically independent external signals**. A same-context critique, an agent's prose saying it ran a check, a command exit without its result, and a stale green result are not proof. The smallest workable implementation is not another guard or orchestration layer: extend the existing typed-receipt lane in `EventLedger`/`ClaimWarningModule` from its present **ANY-of one-green** semantics to **AND-of proof sets**, bind receipts to an artifact/dependency digest and the current mutation sequence, and make the existing `truth-verify` Stop lane summarize only missing obligations.

This is a targeted evolution, not full replacement. The static subject already has receipt classes and freshness (`ledger.py:98-121`, `1093-1117`), a claim-warning module (`modules.py:2000-2137`), a same-fingerprint green rerun gate (`modules.py:2167-2195`), and journey coverage (`hooks/journey-coverage/README.md:6-32`). Replacing those would create a duplicated v2. The defect is narrower but consequential: current `has_fresh_receipt` explicitly uses ANY-of, so one fresh result can substantiate a broad claim (`ledger.py:109-121`, `1101-1116`).

The recommended default evidence matrix is:

| Artifact / claim | External signal A | Mechanically independent signal B | `done` only when |
|---|---|---|---|
| Code fix / feature | execution of the exact failing reproduction or acceptance test | diff/static/type/build check over the changed scope, or independent CI at the exact SHA | acceptance criteria pass; original fingerprint is green; no later mutation invalidates either receipt |
| UI / interaction | browser-driven golden journey with observable assertions | screenshot/accessibility-tree review from a fresh visual context; owner only for unresolved taste | all declared journeys ran, controls work, and no critical accessibility/visual defect remains |
| Config / hook / MCP integration | parser/schema/load check with known-positive and known-negative fixtures | the real consumer reports the new behavior/state through a different interface | configured value is loaded and behavior changes as intended; config text alone never proves wiring |
| Research / factual report | URL/DOI resolves and extracted source span supports each atomic claim | independent verifier (different model/tool) checks entailment and counterevidence; owner/domain expert for high stakes | every load-bearing claim has support, citations resolve, and uncertainty/gaps are explicit |
| Data / generated report / scientific result | independent recomputation from recorded inputs/environment | invariant, benchmark, cross-method, or domain-validity check | provenance, counts/checksums and domain validity agree; file existence or job exit alone is insufficient |
| Autonomous workflow / multi-agent deliverable | terminal receipt plus actual artifact/postcondition read from the target system | reconciliation of the original acceptance criteria and `OPEN-THREADS` against ledger state | every thread is closed, explicitly deferred with owner/reason, or blocked with evidence; no silent omission |
| External side effect (deploy, issue, email, upload) | mutation API/provider receipt with stable ID | read-after-write through the destination's independent read/list/health surface | intended recipient/environment can observe the exact result; high-impact/irreversible actions still require prior confirmation |

The predicted effect is **very likely (80-90%)** to reduce false `done` claims materially because the design directly closes the two observed gaps: seven wrong conclusions arose from unvalidated single signals (`INPUT-known-harness-defects.md:111-129`) and the existing receipt query accepts one green class (`ledger.py:109-121`, `1101-1116`). The exact reduction is **UNVERIFIED — settle it with a 30-day shadow experiment comparing unsupported-done rate, owner reopen rate, and verification latency against the prior 30 days**.

## Grounding and limits

### Local evidence used

* The corpus covers 10.62 GB, 11,633 files and 1,564,084 parsed lines, with zero file failures and one bad line; its own warning says capped samples cannot prove global absence (`inputs/corpus.json:2-11`). I therefore use aggregate counts as measurements, not sample absence as fact.
* Tool reliability makes proof acquisition itself fallible: Bash is 6,461/108,121 errors, PowerShell 2,031/19,181, WebFetch 448/8,042, Glob 829/6,222, and StructuredOutput 846/3,694 (`inputs/corpus.json:13-20`, `39-44`, `71-84`, `103-108`). The receipt protocol must preserve raw exit/result evidence, tolerate partial fields, and never depend on a rigid completion schema.
* The largest relevant fingerprints include 1,631 unmatched-quote shell failures, 939 read-before-write errors, 709 `ENAMETOOLONG` failures, 294 instances of one schema mismatch, and 232 `ECONNREFUSED` results (`inputs/corpus.json:4281-4300`, `4317-4319`, `4371-4373`, `4407-4409`). A check that fails to execute is `unknown`, not pass and not automatic proof of product failure.
* The corpus reports 2,268 owner-correction *candidates* among 8,441 messages but warns that an unfiltered smoke sample was 41/41 false positives (`inputs/corpus.json:10371-10374`). I use the high-frequency owner language only as an intent clue, never as a correction count. The repeated phrases include “nothing left out or skipped” and “why did you stop … finish everything” (`inputs/corpus.json:10389-10398`, `10421-10426`), which supports completeness and thread reconciliation as owner preferences.
* The corpus hook section is **NO DATA**, not evidence of no fires: its detector failed a known-positive control (`inputs/corpus.json:13260-13263`). No proposal below relies on corpus hook-frequency claims.
* The operating-defects input supplies two independent-signal diagnoses: prose/code confusion caused false guard fires and could instruct the agent to discard successful results (`INPUT-known-harness-defects.md:9-82`); six wrong conclusions plus the capability-detector incident were corrected by independent controls (`INPUT-known-harness-defects.md:111-129`); and a fabricated orchestrator constraint propagated to about 15 prompts (`INPUT-known-harness-defects.md:150-160`).

## SOTA synthesis: why external, calibrated, low-friction proof is the frontier

* **External feedback beats intrinsic review.** Huang et al. report that intrinsic self-correction can fail or degrade reasoning without external feedback ([paper](https://arxiv.org/abs/2310.01798)); Kamoi et al.'s critical survey finds reliable external feedback is the condition under which correction works well ([paper](https://arxiv.org/abs/2406.01297)). This independently supports the unit's binding law.
* **Trust must be calibrated, not maximized.** Buçinca et al. found cognitive forcing reduced AI overreliance but received worse subjective ratings, exposing the accuracy/effort trade-off ([paper](https://doi.org/10.1145/3449287)). Google PAIR recommends communicating system limits, using feedback for co-learning, and balancing control with automation ([Mental Models](https://pair.withgoogle.com/guidebook-v2/chapter/mental-models/), [Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)). The resulting design choice is autonomous proof work with owner interruption only where human judgment is the irreducible signal.
* **Proactive help must remain context-sensitive and controllable.** The validated Microsoft human-AI guidelines cover proactive action, contextual relevance, correction, and user control ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Here, proactive means anticipating the correct proof at mutation time, not delivering another generic Stop lecture.
* **Independent evaluation is a process, not a model persona.** NIST AI RMF calls for objective, repeatable TEVV, deployment-representative tests, documented metrics, and independent assessors ([AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). LLM judges themselves exhibit misinformation, authority and presentation biases ([Chen et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.474/)) and self-preference bias ([Chen et al., EMNLP 2025](https://aclanthology.org/2025.emnlp-main.86/)); hence a second model is useful but not sufficient alone.
* **Evidence is bound to the artifact version.** GitHub required checks attach to the latest commit SHA and external CI processes ([required checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks), [status checks](https://docs.github.com/en/enterprise-server%403.19/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks)). SLSA likewise says provenance has value only when a consumer verifies the artifact and provenance against expectations ([SLSA verification](https://slsa.dev/spec/v1.2/verifying-artifacts)). This motivates evidence leases, not timeless badges.

## Findings (inferred-surprise first)

### Finding 1 — Replace “one green receipt” with mutation-bound proof leases

**improvement** — Make a `done` claim a query over an **AND-of proof set** whose receipts are bound to `(artifact_digest, dependency_digest, mutation_seq, acceptance_claim_ids)`. Any later relevant mutation expires the lease automatically. This builds on, rather than replaces, the existing typed receipt/freshness lane.

**what it is** — A proof lease is a compact ledger record, not a new service:

```text
proof_id, artifact_kind, claim_ids[], signal_kind, producer,
artifact_digest, dependency_digest, mutation_seq, status, observed_at,
command_or_uri_digest, result_excerpt_or_artifact_path
```

For each artifact kind, `proof_sets.toml` defines alternatives such as `code = (repro_pass AND scope_gate_pass)` or `ui = (journey_pass AND visual_or_owner_pass)`. Unknown/missing fields yield `unknown`, never pass. Receipts produced before the last relevant mutation or for a different digest do not count. A final message cites only `proof_id`s and gaps; it does not ask the model to narrate its own correctness.

**why-inferred** — The owner repeatedly demands “nothing left out or skipped” and continuation to actual completion (`corpus.json:10389-10398`, `10421-10426`). More importantly, the present implementation explicitly treats receipt classes as ANY-of and one pass as substantiation (`ledger.py:109-121`, `1101-1116`), while the local verification law requires success corroboration by independent probes (`rules/common/single-signal-verification.md:20-37`). A generic green badge is therefore structurally weaker than the owner's stated bar.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add optional digest/signal/claim fields to `Receipt`; replace `has_fresh_receipt(required_classes)` at the new call site with `satisfied_proof_set(kind, claims, digest, min_seq)` while retaining the old shim for compatibility; put the small artifact matrix in config; have existing PostToolUse classification stamp deterministic receipts; fold the summary into the current `ClaimWarningModule`/`truth-verify` Stop lane. Ship OFF → SHADOW → ADVISE using the already-coded staging ladder (`modules.py:118-143`). Do not add a seventh hook. Parser/evidence errors are caught and exit 0, matching the existing fail-open pattern (`modules.py:2080-2089`) and cross-tool contract (`AGENTS.md:64-70`).

**the EXTERNAL signal that verifies it** — (A) table-driven unit tests feed a stale pass, mutate the artifact, and prove the resolver returns unsatisfied; (B) a fresh process performs an end-to-end canary in a temporary repo and reads the resulting ledger/digest without importing the test process's in-memory state. The detector must also find one seeded known-positive and reject one seeded known-negative. Only those two signals justify “proof leasing works.”

**SOTA citation with URL** — GitHub binds required checks to the latest commit SHA ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)); SLSA requires consumer-side verification of artifact provenance against expectations ([SLSA v1.2](https://slsa.dev/spec/v1.2/verifying-artifacts)); NIST calls for objective, repeatable TEVV ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**value x effort** — **transformative x medium**. It is **very likely (80-90%)** to prevent stale-green and one-green false completion because it directly changes the two permissive predicates visible in `ledger.py:109-121` and `1101-1116`; magnitude is **UNVERIFIED — settle with shadow replay over 200 historical done-claim turns, hand-labeling false blocks and false passes**.

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** (shadow-only implementation and tests); confirm before promotion to enforce.

### Finding 2 — Prove claim coverage, not merely that “some tests passed”

**improvement** — Compile the original request/plan into stable acceptance-claim IDs and require each `done` clause to point to a proof set. This is a coverage map, not another checklist prompt.

**what it is** — At task start, extract only explicit deliverables and hard constraints into a small ledger object (`C1…Cn`, source quote/digest, artifact kind, risk). At completion, mechanically compute `covered`, `failed`, `blocked`, `deferred-with-owner`, and `unmentioned`. The agent cannot mark `deferred` merely by omitting a claim. New discoveries become child claims linked to their originating claim. The owner sees a one-line summary only when gaps remain.

**why-inferred** — “Never drop a thread” is a hard constraint, and the corpus's strongest owner-intent patterns emphasize 100% coverage and nothing skipped (`corpus.json:10377-10398`). The existing journey hook covers declared E2E specs (`journey-coverage/README.md:6-23`) but does not cover non-UI deliverables, research assertions, configuration wiring, or external side effects. The cross-tool contract already records goals and milestones in the event ledger (`AGENTS.md:22-34`), so coverage belongs there.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend event-ledger goal records with optional claim IDs and status; add a pure `reconcile_claims(goal_digest, proof_ids, open_threads)` function; call it inside existing `truth-verify` at Stop/TaskCompleted. Reuse `OPEN-THREADS.md` as an input, not a second source of truth, and write no new memory store. Keep extraction tolerant: plain records, optional fields, no `StructuredOutput` dependency, because StructuredOutput's measured 22.9% error rate (`corpus.json:103-108`) makes rigid schemas a poor completion dependency.

**the EXTERNAL signal that verifies it** — (A) a fixture task with a known omitted acceptance criterion must produce `unmentioned=C3`; (B) an independent fresh-context reviewer receives only the original brief, artifacts and generated coverage map and must locate no additional uncovered explicit criterion. Reviewer disagreement keeps status partial, not done.

**SOTA citation with URL** — NIST asks that targeted capabilities, goals, criteria and deployment-representative performance be documented and measured ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)); Microsoft’s human-AI guidance emphasizes remembering recent interactions and supporting efficient correction ([Amershi et al.](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).

**value x effort** — **transformative x medium**. It is **likely (55-80%)** to reduce discussed-then-forgotten deliverables, based on the explicit owner pattern and deterministic reconciliation; the extraction accuracy is **UNVERIFIED — settle with a blinded 100-task benchmark against owner-authored acceptance labels**.

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** in shadow mode; owner confirmation only to resolve a genuinely ambiguous/deferred criterion.

### Finding 3 — Code, repair, and package claims require reproduction closure plus scope integrity

**improvement** — Define code `done` as two different questions answered externally: “does the intended behavior now work?” and “did the change preserve the surrounding contract?”

**what it is** — For a bug, signal A is a green rerun of the exact original failing fingerprint or a newly added failing-first regression; for a feature, it is an executable acceptance test. Signal B is selected by scope: type/lint/build for local edits, broader CI for cross-cutting edits, consumer install/import smoke for packages, and a blast-radius/wire check for confirmed defects. Test modification cannot be its own proof unless an independent behavior oracle remains.

**why-inferred** — The harness already has the right seed: a same-fingerprint rerun gate (`modules.py:2167-2195`) and a blast-radius rule (`AGENTS.md:108-113`). But the generic `/verify` command runs a fixed pipeline (`commands/verify.md:7-32`) and the receipt map allows `fixed = test OR run`, `builds = build OR typecheck` (`ledger.py:112-120`), leaving one-green and wrong-scope gaps. The corpus's 939 read-before-write errors and 1,631 quoting errors (`corpus.json:4281-4300`) also mean a claimed edit or test command needs observed output, not intent.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `code_fix`, `code_feature`, and `package` proof-set recipes to Finding 1's config; reuse the current repro fingerprint; derive changed scope from `git diff --name-only` and project manifests; select the smallest native project commands; preserve raw exit code, counts and SHA/digest. If no executable oracle exists, status is `PARTIAL/UNVERIFIED`, not a model-generated pass. Never auto-edit tests merely to satisfy the gate.

**the EXTERNAL signal that verifies it** — (A) the real test/runtime produces the expected observable output for the original repro; (B) an independent CI/build/type/static tool runs against the exact artifact digest/SHA. For packages, replace B with install/import/use from a clean temporary environment. Both must post-date the last mutation.

**SOTA citation with URL** — GitHub status checks are produced by external CI and gate the current commit ([GitHub status checks](https://docs.github.com/en/enterprise-server%403.19/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks)); recent SWE-bench re-evaluation found erroneous patches could pass insufficient tests, reinforcing that a green suite alone is not an oracle ([UTBoost](https://arxiv.org/abs/2506.09289)).

**value x effort** — **high x low** after the proof-set substrate. It is **very likely (80-90%)** to reject “command ran” and wrong-fingerprint fixes because exact-fingerprint matching is deterministic and already present; preservation coverage remains **likely (55-80%)**, limited by the repository's available tests. Evidence: `modules.py:2167-2195`, `commands/verify.md:7-32`.

**novelty** — **user-asked**.  
**autonomy** — **just-do-it** (implementation and ordinary tests/checks). Costly, destructive, billable, or production verification is outside this autonomy rating and still requires confirmation.

### Finding 4 — UI claims need behavioral, accessibility, and visual evidence; a rendered page is not a finished product

**improvement** — Require the actual declared journey to be driven in a browser and pair it with a different representation of the UI. Separate objective interaction/accessibility from subjective taste.

**what it is** — Signal A drives every declared user journey, asserts navigation/state/persistence/error recovery, and fails on dead controls. Signal B is either (i) accessibility tree plus automated ACT/WCAG checks for semantic quality, and a screenshot reviewed in a fresh visual context for layout quality, or (ii) the owner for a genuinely subjective design decision. A screenshot alone cannot prove a button works; a DOM assertion alone cannot prove visual finish.

**why-inferred** — The pinned quality bar explicitly forbids dead buttons and built-but-not-wired work. Existing journey coverage already discovers E2E specs and checks that each ran (`journey-coverage/README.md:13-23`) but it only names successful commands; it does not attest to visual finish or accessibility. The owner values full workflow closure, reflected by the corpus's repeated 100%/finish patterns (`corpus.json:10377-10398`, `10421-10426`).

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a small proof-set recipe plus the receipt adapter that records the project-native Playwright/Cypress report, screenshot path/digest and accessibility result. Fold it into journey-coverage/truth-verify, not a new hook. Run at representative viewport(s); require zero broken journeys and zero critical accessibility violations. Ask the owner only when the fresh visual reviewer identifies a preference fork that cannot be decided from requirements.

**the EXTERNAL signal that verifies it** — (A) browser execution report with assertions and trace for each journey; (B) accessibility-tree/ACT result plus screenshot evaluated by a fresh multimodal context that did not build the UI. For a subjective brand/taste claim, owner approval replaces—not supplements—a pretending model verdict.

**SOTA citation with URL** — W3C publishes WCAG 2.2 and ACT rules for automated, semi-automated and manual conformance testing ([WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/), [ACT rules](https://www.w3.org/WAI/standards-guidelines/act/rules/)); cognitive-forcing research shows accuracy interventions can increase user burden, supporting selective rather than routine owner review ([Buçinca et al.](https://doi.org/10.1145/3449287)).

**value x effort** — **high x medium**. It is **very likely (80-90%)** to catch dead/unwired UI when journeys assert outcomes, and **likely (55-80%)** to improve finish when paired with accessibility and fresh visual review; visual-taste agreement is **UNVERIFIED — settle with 20 blinded owner ratings comparing accepted/rejected screenshots and reviewer verdicts**.

**novelty** — **inferred-surprise** (the split between behavioral proof, semantic accessibility, and taste).  
**autonomy** — **just-do-it** (implementation and browser/accessibility checks). Unresolved subjective choices and irreversible publishing remain confirm-first actions outside the implementation proposal.

### Finding 5 — Config, hooks, and MCPs are done only when the live consumer changes behavior

**improvement** — Make “wired and live” a distinct artifact type. A valid JSON file, existing script, or successful process start is only construction evidence, never operational proof.

**what it is** — Signal A validates the artifact syntactically and exercises the detector against one known-positive and one known-negative fixture. Signal B queries or stimulates the real consumer through a different interface: Claude hook canary appears in durable ledger output; MCP tool is rediscovered and invoked; service health/read endpoint reports the loaded version/config digest; capability catalog sees the installed item from a fresh session. If the consumer cannot expose loaded-state evidence, the honest status is partial.

**why-inferred** — D2 records a detector reporting zero skills/agents/hooks until a known-positive control proved only the hooks half broken (`INPUT-known-harness-defects.md:120-129`). D4 records a fabricated constraint propagated to about 15 prompts because recipients could not re-probe it (`INPUT-known-harness-defects.md:150-160`). The corpus records 275 dead-Tavily connection fingerprints and 232 `ECONNREFUSED` results (`corpus.json:4388-4409`). These are direct evidence that existence/configuration and availability diverge.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `integration` proof recipes and consumer adapters to the existing mcp-liveness/capability-catalog/truth-verify bus. Require `parse_pass AND live_consumer_canary_pass`; record the config digest and observed consumer version. Reuse B1 MCP liveness rather than proposing another health hook. Canary failures advise and remain fail-open; they do not repeatedly nag. Promotion requires shadow precision data because D1 shows prose-blind detectors can corrupt state (`INPUT-known-harness-defects.md:52-82`).

**the EXTERNAL signal that verifies it** — (A) parser plus known-positive/known-negative detector fixtures; (B) fresh-process consumer readback or same-session live tool invocation that returns a unique canary value. For absence claims, B must first demonstrate it can discover a known-present control.

**SOTA citation with URL** — NIST calls for deployment-context evaluation and production monitoring, not development-only validation ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)); Google PAIR recommends setting expectations about system adaptation and using logs to detect confusion/failure ([PAIR Mental Models](https://pair.withgoogle.com/guidebook-v2/chapter/mental-models/)).

**value x effort** — **transformative x low** after proof sets. It is **almost certain (90-99%)** to distinguish “file exists” from “consumer loaded it” when a canary endpoint/tool exists, because the signals query different layers; universal applicability is **likely (55-80%)** because some consumers may lack introspection. Evidence: D2 and D4 above.

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** (implementation and read-only canaries). A mutating canary remains confirm-first and is outside this implementation proposal.

### Finding 6 — Research and advice require atomic citation entailment plus counterevidence search

**improvement** — Treat a research report as a graph of atomic claims, each with resolvable source evidence, rather than equating “has citations” with “is verified.”

**what it is** — Signal A resolves each URL/DOI and extracts the source span/metadata that supports a claim. Signal B gives the claim and evidence—not the draft's rationale—to a different model/tool for entailment, relevance, recency and strongest-counterevidence checks. Deterministic fields (dates, titles, identifiers, quotes) are compared mechanically. A second model may flag, never single-handedly certify. Medical/legal/financial or novel scientific recommendations require owner/domain-expert confirmation before consequential action.

**why-inferred** — The unit law rejects same-context self-review, and D4 demonstrates how an unsupported orchestrator premise can propagate (`INPUT-known-harness-defects.md:150-160`). WebFetch itself fails 5.57% (`corpus.json:71-76`), so a drafted link is not proof it resolved. The user's honesty instrumentation demands inline `UNVERIFIED` and concrete evidence, making atomic support coverage the natural externalization.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `truth-verify` with a research adapter: parse Markdown links and adjacent claim IDs; HTTP/DOI-resolve them; store retrieved-title/date/span digest; dispatch only unsupported/high-impact claims to a different-vendor verifier; emit a coverage report and inline `UNVERIFIED` for failures. Use primary sources by default. Do not introduce a vector DB/KG, trained critic, or durable research runtime.

**the EXTERNAL signal that verifies it** — (A) URL/DOI resolution plus source-span extraction confirms identity and content; (B) a different-vendor fresh context labels support/contradiction/insufficient and searches for counterevidence. For high-stakes conclusions, a domain expert/owner is the second decisive signal even if the model agrees.

**SOTA citation with URL** — ALCE evaluates citation correctness and completeness and found even its best systems lacked complete citation support 50% of the time on ELI5 ([Gao et al.](https://arxiv.org/abs/2305.14627)); LLM-judge bias studies warn against model-only certification ([EMNLP 2024](https://aclanthology.org/2024.emnlp-main.474/), [EMNLP 2025](https://aclanthology.org/2025.emnlp-main.86/)).

**value x effort** — **high x medium**. It is **likely (55-80%)** to reduce unsupported factual claims because link resolution and entailment target distinct failure modes; exact precision is **UNVERIFIED — settle on 300 atomic claims with blinded expert labels, measuring support precision/recall and counterevidence yield**.

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** (implementation and read-only verification). High-stakes or costly downstream action remains confirm-first and is not authorized by this proposal.

### Finding 7 — Data, reports, and scientific outputs require reproducibility and domain validity

**improvement** — Separate “the pipeline produced a file” from “the result is reproducible and means what the claim says.”

**what it is** — Signal A records inputs, tool/environment version, command digest, output checksum, row/record counts and an independent recomputation or clean rerun. Signal B applies a domain oracle: invariants and reconciliation totals for data; source-to-table spot checks for reports; benchmark/cross-method/physical-validity checks for scientific work. For stochastic work, record seed and tolerance and compare distributions or convergence, not byte equality.

**why-inferred** — The corpus has long-running scientific workflows and a compchem-specific claim detector in the current harness (`modules.py:2230-2240`), but that detector accepts validity words in assistant text—still same-context narration—not necessarily a referenced external result. Tool exit alone is unreliable given Bash/PowerShell/WebFetch error rates (`corpus.json:13-20`, `39-44`, `71-76`) and retry loops across Read, Bash, task output and research polling (`corpus.json:10297-10369`).

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `data`, `report`, and `scientific` proof recipes. Store a minimal provenance sidecar in the event ledger or beside the output (input/output digests, command, versions, seed/tolerance); invoke project-native validators; require `recompute_or_reconcile AND domain_validity`. For compchem, parse PoseBusters/redock RMSD/convergence artifacts rather than scanning assistant prose. No KG/vector DB or new scientific daemon.

**the EXTERNAL signal that verifies it** — (A) a clean process recomputes the output or independently reconciles checksums/counts from source inputs; (B) a different domain tool, benchmark, invariant suite or expert reviews physical/statistical validity. File existence, timestamp, and the generating job's `SUCCESS` marker are all one lineage and cannot be the pair.

**SOTA citation with URL** — W3C PROV defines interoperable provenance around entities, activities and agents and explicitly supports derivation, versioning and reproducibility ([PROV-O](https://www.w3.org/TR/prov-o/), [PROV Overview](https://www.w3.org/TR/prov-overview/)); NIST requires documented test sets, tools, uncertainty and deployment-representative validation ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**value x effort** — **high x medium**. It is **very likely (80-90%)** to catch truncated/wrong-input/non-reproducible artifacts when recomputation is feasible; scientific semantic validity is **likely (55-80%)** because domain oracles vary. **UNVERIFIED — settle per domain with seeded corruptions (wrong input, truncated rows, unit mismatch, unconverged run) and measure detector recall/false alarms.**

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** (implementation and cheap validators/reconciliation). Expensive compute or expert review remains confirm-first and is outside the implementation proposal.

### Finding 8 — Autonomous workflows and external side effects require destination readback and zero unowned threads

**improvement** — Finish the loop at the system that consumes the work, then reconcile every thread. A worker terminal receipt is necessary but never sufficient.

**what it is** — For multi-agent/long-run work, require terminal receipt + artifact/postcondition, then compare acceptance claims and `OPEN-THREADS` to ledger state. For deploys/issues/uploads/messages, require provider mutation receipt + independent destination read-after-write. Every remaining thread must be `closed`, `blocked` with two signals, or `deferred` with owner, reason and resumption condition; “not mentioned” is a failing state.

**why-inferred** — The local rule already says terminal `DONE` needs receipt AND postcondition and treats subagent output as one signal (`single-signal-verification.md:20-37`). Long operations use terminal markers and log readback (`AGENTS.md:36-57`). The corpus contains TaskOutput and polling retry loops (`corpus.json:10325-10339`) plus owner language asking why the agent stopped before everything finished (`corpus.json:10421-10426`). The hard constraint “never drop a thread” makes reconciliation part of correctness, not project-management decoration.

**how-to-build** — **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend claim reconciliation with `destination_receipt` and `thread_status`; reuse event-ledger, note.py, longrun terminal markers and `OPEN-THREADS.md`. Add provider-specific readback adapters only as small functions: deployment health/version, issue GET by ID, upload list/hash, sent-message/thread GET. Existing `truth-verify` reports only unresolved items once; no new hook, notification daemon or owner checklist. Any adapter exception records `unknown` and exits 0.

**the EXTERNAL signal that verifies it** — (A) worker/provider terminal mutation receipt with stable run/object ID; (B) independent target read/list/health query returns the expected artifact digest, version, recipient, or state. Separately, a fresh-context acceptance reconciliation must find zero unowned claims/threads. For absence or failure, the readback detector must first find a known-present control.

**SOTA citation with URL** — Google PAIR recommends feedback/control that explains impact and timing while balancing automation with user effort ([PAIR Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)); Microsoft’s guidelines address proactive action, correction and user control ([Amershi et al.](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)); NIST calls for post-deployment monitoring, feedback, incident handling and change management ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**value x effort** — **transformative x medium**. It is **very likely (80-90%)** to eliminate false completion caused by worker exit without delivered state when a read API exists, and **likely (55-80%)** to reduce dropped threads through explicit reconciliation. The prompt-fatigue effect is **UNVERIFIED — settle by measuring owner interruptions, reopen messages, and unresolved-thread age during a 30-day shadow trial**.

**novelty** — **inferred-surprise**.  
**autonomy** — **just-do-it** (implementation and read-only readback/reconciliation). Sending, deploying, publishing, deleting, or other irreversible/public/costly/human-facing mutations remain confirm-first and are not authorized merely because their proof adapters exist.

## Unified build plan (no seventh hook)

1. **Instrument in shadow, inside the existing dispatcher/truth lane.** Add proof-set evaluation and adapters to `EventLedger`/`ClaimWarningModule`; do not register a new hook. Preserve the existing stage ladder (`modules.py:118-143`) and fail-open exception handling (`modules.py:2080-2089`).
2. **Start with four high-yield recipes:** `code_fix`, `integration`, `research`, `workflow`. They cover the live defect classes and require no new runtime. Add UI/data/science/provider adapters only when their artifact type appears.
3. **Use tolerant records, not strict fan-out StructuredOutput.** Optional fields plus explicit `unknown` avoid turning the corpus's 22.9% schema failure (`corpus.json:103-108`) into a new inability to finish. Validate required semantics inside the small resolver.
4. **Shadow replay before advice.** Seed known-positive/negative controls; replay historical turns where possible; hand-label a sample. A detector that cannot find its seeded positive has no authority to report absence.
5. **Advise once, never nag.** If proof is missing, one compact line lists `C3 integration: missing live-consumer canary`; otherwise remain silent. Never ask the owner to execute routine proof. Escalate only subjective, high-stakes, costly or irreversible judgments.
6. **Promote by measured precision and burden.** Proposed thresholds are **UNVERIFIED — settle in shadow**: at least 95% precision on unsupported-done warnings, known-positive recall ≥99%, p95 added Stop latency <250 ms excluding the checks themselves, zero hook crashes that block work, and no increase in owner interruptions per completed task. Promotion to enforce requires owner confirmation because false positives have already caused correctness damage (`INPUT-known-harness-defects.md:65-82`).

## Anti-overfit gate and rejected alternatives

All eight proposals ride existing buses: dispatcher hooks, event-ledger/note.py, truth-verify, journey coverage, project-native test tools, current MCP liveness/capability catalog, and owner confirmation. None needs a second orchestration runtime, vector DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Rejected alternatives:

* **A universal “LLM reviewer says PASS.”** Rejected by construction: it is a single fallible external lens, judge studies show bias, and it cannot replace execution/readback.
* **A seventh Stop hook per artifact type.** Rejected: it violates the hook ceiling, increases latency and repeats the D1 false-fire surface. All recipes fold into existing truth-verify/dispatcher logic.
* **Owner approval on every task.** Rejected as a prompt-fatigue regression. Human judgment is reserved for subjective/high-stakes/irreversible forks.
* **One giant mandatory test suite.** Rejected as overfit and high latency. Select the smallest proof set that actually entails the claim, then bind it to the artifact digest.
* **StructuredOutput as the proof transport.** Rejected as the only transport because its measured error rate is 22.9% (`corpus.json:103-108`). Plain tolerant receipts with semantic validation are safer.
* **File existence, process exit, screenshot, citation, or agent handoff as sole proof.** Rejected because each observes only one layer. The second signal must interrogate behavior, destination state, entailment, or domain validity through a mechanically different path.
