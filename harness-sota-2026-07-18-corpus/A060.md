# A060 — Coherence audit of `~/.claude/rules/python/testing.md`

Date: 2026-07-19  
Unit: A060  
Mode: read-only subject audit; the only written file is this artifact.  
Remote subject root: `/local_disk0/codexwork/bundle`.

## Executive conclusion

The effective Python testing policy is not just the 38-line leaf rule. The leaf explicitly says it extends the common testing rule (`claude/rules/python/testing.md:8`), so its effective contract is: pytest; a hard-coded `--cov=src` example; pytest marks; all unit, integration, and E2E test types; mandatory RED/GREEN/IMPROVE ordering; a threshold from `.coverage-thresholds.json` or 80% by default; and proactive use of `tdd-guide` (`claude/rules/python/testing.md:8-38`; `claude/rules/common/testing.md:23-49`).

That contract is incoherent in four different ways:

1. It contains internally incompatible or scope-insensitive instructions: `--cov=src` versus `--cov=app`; “all” E2E versus “critical paths”; and a metaswarm-aware threshold SSOT versus a generic agent that declares 80% as required (`claude/agents/python-reviewer.md:63-71`; `claude/agents/tdd-guide.md:36-48`).
2. It is contradicted by this harness's own Python test assets: 16 hook tests explicitly advertise running without pytest, two use `unittest` as the runner, none of the 71 supplied Python test files uses either prescribed category mark, and the supplied subject has no directory named `src` (command evidence in “Behavioral ground truth”).
3. Its principal requirements are not mechanistically enforced. No configured hook checks pytest choice, RED-before-GREEN chronology, unit/integration presence, pytest category marks, or the threshold SSOT. The only live testing-specific guard scans staged test weakening at commit time (`claude/settings.json:162-171`; `claude/hooks/test-tamper-guard/guard.py:224-320`).
4. The one registered E2E-completeness hook depends on a claim ledger whose writer is not registered in either settings or the local dispatcher. On a missing ledger, its code returns an empty successful-command list (`claude/hooks/journey-coverage/check.py:35-41,144-162,218-234`; `claude/hooks/journey-coverage/README.md:34-42`; `claude/hooks/_dispatch/manifest.json:133-141`). This is an ineffective enforcement chain, not evidence that hooks did or did not fire; `corpus.json:1` explicitly marks its entire hooks section broken.

Overall diagnosis: the rule is **badly written** where it hard-codes repository layout or states categorization unconditionally; **wrong at the universal level** where every change is said to require all three test layers; and **unenforceable as currently wired** where it demands chronology, thresholds, and proactive routing without corresponding evidence-producing mechanisms. It is not wrong to prefer pytest or to require risk-appropriate tests.

The highest-value resolution is a small replacement of the leaf/common policy contract plus configuration of existing hook buses. This is **very likely (80-90%)** to improve coherence because every observed collision comes from ambiguous scope, duplicated SSOT text, or missing/incorrect wiring documented below; the band is not higher because the actual Windows skill trees and raw successful command stream were not included in the remote bundle.

## Detailed findings and diagnosis

### 1. The effective rule has three different sources of truth

`python/testing.md` owns the framework, package-root example, and marks. `common/testing.md` owns test layers, chronology, and thresholds. `tdd-guide.md` restates chronology, thresholds, metrics, and test layers. `development-workflow.md` and `code-review.md` restate parts again. This is not merely verbose documentation: the copies have already diverged at E2E scope and metaswarm threshold behavior (C2-C3).

Resolution architecture: one normative testing contract; language leaves choose runners and idioms; project configuration chooses package roots and numeric gates; agents and hooks consume those values. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is **almost certain (90-99%)** to eliminate the currently enumerated textual contradictions because no new runtime is required—only references and one resolver contract.

### 2. “Use pytest” is a preference masquerading as a universal invariant

The supplied harness deliberately contains bootstrap-friendly tests that run with plain Python. The two clearest framework-level contradictions are `mvt-patch-leaving/test_check.py:13-16,640` and `selection-events/test_emitter.py:14-16,527`; many other modules explicitly advertise no-pytest execution. Pytest can collect many unittest-style tests, so the existence of `unittest.mock` alone is not a contradiction; the audit counted only explicit direct-run claims and `unittest.main` for the strong signal.

Diagnosis: **badly written**, not simply “pytest is wrong.” The rule fails to state whether it means authoring API, primary suite runner, or compatibility. The resolution in C4 preserves pytest as the default while admitting a bounded zero-dependency exception.

### 3. Coverage has no executable SSOT contract

The common rule names `.coverage-thresholds.json`, but the remote bundle contains no such file and no `pyproject.toml`, `pytest.ini`, `tox.ini`, or `setup.cfg`. That does not prove those files are absent on the Windows subject or in individual project repositories; it proves they were not included in this bundle. The target command does not read a threshold, enforce a minimum, request branch coverage, or adapt its package root (`python/testing.md:14-18`). The Python reviewer gives a different root (`python-reviewer.md:63-71`). The dormant claim checker then treats any successful `pytest` substring as coverage evidence (`claim-check.py:232-240,340-343`).

Diagnosis: **badly written** command example plus **unenforced** threshold. The rule can only be reliable if “resolve configuration → run declared command → persist machine-readable result → compare” is explicit.

### 4. Mandatory TDD is not observable with present hooks

The configured `test-tamper-guard` observes only staged diffs immediately before `git commit`; it cannot know whether a failing test preceded implementation (`guard.py:224-274`). The corpus capability detector records no `tdd-guide` invocation despite complete reconciliation of 1,745 named Agent calls with the Agent tool total. The corpus distillation does not retain the full successful Bash/Edit command chronology, so it cannot independently prove whether humans or agents followed RED/GREEN without the named agent.

Diagnosis: **unenforceable as currently instrumented**, not proven universally ignored. The owner-mandated distinction matters: rewriting “MANDATORY” more emphatically will not create chronology evidence. C6 proposes a receipt on the existing event ledger instead of a second orchestration runtime.

### 5. Universal all-layer testing is overbroad

The rule applies to every listed source extension and says all three layers are required (`common/testing.md:1-28`). That makes integration and E2E mandatory even for a pure helper, a schema-only change, or a hook parser with no user interface. The TDD agent itself narrows E2E to critical paths (`tdd-guide.md:42-48`).

Diagnosis: **wrong at universal scope**. Risk-tiering is preferable to weakening all projects to unit-only. This resolution passes the anti-overfit gate: it reduces scaffolding, rides existing rule/CI buses, and does not add a critic, database, daemon, durable execution engine, SaaS, or guardrail framework.

### 6. Testing hooks are both under-ruled and under-wired

`test-tamper-guard` has concrete policy not stated in rules (C10). `journey-coverage` has a same-turn completeness policy not stated in rules (C11). Yet neither implements threshold or TDD requirements, and journey coverage lacks its producer wiring (C12). Thus “more hooks” is not the remedy; policy, producer, consumer, and mode must be a single declared contract.

The missing producer conclusion uses two mechanically independent configuration signals: exact search of `settings.json` and exact search of `_dispatch/manifest.json` found no `claim-guard` or `ledger-write`. Detector controls succeeded in the same files: `settings.json:167` finds `test-tamper-guard`, and `_dispatch/manifest.json:134-135` finds `journey-coverage`. This establishes that the searches can detect known registrations.

## Recommended replacement contract

### P0 — Replace the rule text and remove duplicate literals

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Suggested normative content:

1. Use the repository's declared Python test command. Prefer pytest for project suites. Permit documented stdlib direct tests for zero-dependency bootstrap/recovery components, while keeping them collectible by the project gate where practical.
