# X050 — control theory → use-vs-mention

## Executive result

The borrow transfers, but only partially and only at structural boundaries.

Control theory's useful answer is **port-aware supervision**: a feedback design does not decide whether a waveform is a command, measurement, disturbance, or reference by inspecting the waveform's values. The signal's role is established by the port through which it enters the interconnection. A reference governor therefore sits on the reference/command channel, observes the relevant plant state, and modifies the reference only when predicted constraints require it. This is a strong match for an agent harness at the moment a proposed tool action becomes a canonical executor request. It is a weak match for an undifferentiated natural-language message that can contain instructions, quotations, examples, and retrieved data at once.

The central design conclusion is:

> Do not make an enforcement decision from payload text alone. Carry trusted, out-of-band role and provenance from the harness route, and put hard guards on the canonical proposed-action port. Treat content detection and action authorization as separate planes.

This conclusion is **almost certain (90-99%)** at structured tool-call boundaries because (1) classical feedback diagrams assign different closed-loop effects to reference, disturbance, measurement-noise, and actuator channels even when their numerical traces could be identical, and (2) reference governors explicitly operate by modifying the reference supplied to an already controlled system, rather than by scanning every signal for reference-like values. Sources: Åström and Murray's *Feedback Systems*, especially the feedback architecture and state-estimation chapters ([book site and full text](https://fbswiki.org/wiki/index.php/Feedback_Systems:_An_Introduction_for_Scientists_and_Engineers)); Garone, Di Cairano, and Kolmanovsky's survey, whose abstract defines reference/command governors as add-on schemes that modify the reference when needed ([MERL publication page](https://www.merl.com/publications/TR2016-102)); and Bemporad, Casavola, and Mosca's predictive reference-governor formulation ([DOI/article page](https://doi.org/10.1016/S0166-3615(97)00098-5)).

The same conclusion is only **likely (55-80%)** for free-form prompt ingress because control systems normally obtain role from distinct wires/ports, whereas language multiplexes roles within one string. The evidence for the lower band is the structural disanalogy itself: an identical sentence can be an owner's instruction, a quoted attack specimen, or text inside a file, and no extra payload feature is guaranteed to distinguish those cases. The experiment that would refine this band is the mixed-role corpus experiment specified below.

This unit does not inspect or make claims about the local harness implementation. The unit brief explicitly makes this an external ideation lens and supplies the target observation—five payload-text detectors and at least twelve false fires—as commissioning evidence. No Windows-only subject path is required for this analysis.

## 1. What control theory solved in its own field

### 1.1 Signal role is topology, not waveform semantics

A standard feedback interconnection distinguishes at least:

- a reference or command `r`, expressing desired behavior;
- a control input `u`, which the controller sends to the plant;
- an output or measurement `y`, returned through feedback;
- disturbances and sensor noise, injected at different points in the loop.

Those labels are not classifications inferred from the samples. They are part of the system model and wiring. In a linear feedback loop, the transfer from reference to output is different from the transfer from disturbance or sensor noise to output precisely because each signal enters at a different summing junction. Åström and Murray explicitly analyze reference tracking, load-disturbance rejection, and measurement-noise attenuation as different closed-loop paths, including two-degree-of-freedom architectures in which reference response can be shaped separately from feedback response ([*Feedback Systems*, book site/full text](https://fbswiki.org/wiki/index.php/Feedback_Systems:_An_Introduction_for_Scientists_and_Engineers)).

This is the first transferable mechanism: **role is carried by the interconnection**.

An important corollary follows. Suppose two signals have exactly the same numerical sequence, for example a unit step. If one is connected to the reference port and one to a load-disturbance port, the controller treats them differently and they have different closed-loop consequences. A content-only rule—“if the samples look like a step, treat it as a command”—would erase information the architecture already knows.

The mapping to use-vs-mention is direct at structured boundaries:

| Control field | Harness analogue |
|---|---|
| reference/command port | canonical proposed tool action |
| plant actuator input | executor invocation actually issued |
| measured plant output | tool result and postcondition evidence |
| disturbance/noise | retrieved/file/tool text that may influence reasoning but is not itself an action |
| controller state | agent/harness workflow state |
| reference governor | pre-execution policy hook that allows, transforms, requests confirmation, or denies a proposed action |

The analogy does **not** say “documents are harmless disturbances.” Untrusted text can alter the agent's later proposal, just as a disturbance can alter plant state. It says the document's literal characters are not themselves an actuator command. If they induce a dangerous tool proposal, that proposal crosses the action port and is governed there.

### 1.2 Reference/command governors supervise the command channel

A reference governor is an add-on supervisory component for a pre-stabilized system. It uses the current state, desired set-point, and constraints to modify the reference when necessary so that constraints remain satisfied. Bemporad, Casavola, and Mosca describe the device as acting on the current state, set-point, and constraints, computing an admissible modified reference online ([1998 article](https://doi.org/10.1016/S0166-3615(97)00098-5)). The later survey describes reference and command governors as add-on schemes that enforce state/control constraints by modifying the reference and covers uncertainty, unmeasured disturbances, and networked variants ([MERL survey page and open PDF link](https://www.merl.com/publications/TR2016-102)).

The specific architectural property worth borrowing is not the quadratic program. It is the **placement and contract**:

1. The primary controller/system continues to operate.
2. The governor is placed on a known command path.
3. It receives state relevant to constraint prediction.
4. It passes, reshapes, or holds the command.
5. It does not reinterpret every observed signal as a command candidate.

That placement makes the mechanism compositional. The governor can protect a system without becoming a second controller for the entire plant.

### 1.3 Observability gives an impossibility test, not a semantic classifier

In control theory, observability asks whether internal state can be reconstructed from available inputs and outputs. If distinct internal states generate indistinguishable observations, no observer using only those observations can determine which state is present. Villaverde's tutorial explains observability in terms of distinguishing states from model outputs and notes that even a local observability condition may leave distant states indistinguishable ([open-access tutorial](https://doi.org/10.1155/2019/8497093)). Åström and Murray develop state estimation from a model, known inputs, and measured outputs—not from output samples in isolation ([state-estimation material in *Feedback Systems*](https://fbswiki.org/wiki/index.php/Feedback_Systems:_An_Introduction_for_Scientists_and_Engineers)).

For use-vs-mention, construct two histories:

- `H_use`: the owner says `delete build-cache` as an operative instruction.
- `H_mention`: a test report quotes the exact bytes `delete build-cache` as an example of text a detector matched incorrectly.

If a detector observes only those bytes, its observation is identical under both histories. The latent role differs, but the measured output does not. The role is therefore unobservable from that detector's input. More regular expressions, a larger keyword list, or a confidence threshold cannot make the missing variable observable.

This transfer is **almost certain (90-99%)** as an information argument: identical detector inputs cannot deterministically yield two correct different labels. Evidence is the standard distinguishability definition above plus the explicit equal-payload construction. The residual 1-10% is not doubt about the logic; it covers cases where the production detector secretly receives additional context, in which case the premise “payload only” would be false.

The remedy implied by observability is to add a measurement: trusted route/role metadata, a canonical action object, or an explicit user confirmation. Observability does not tell us how to infer pragmatic meaning inside arbitrary prose, and it supplies no reason to pretend that a heuristic semantic classifier is ground truth.

### 1.4 Anti-windup contributes a secondary rule: feed back realized actuation

Integrator windup occurs when a controller continues integrating error while the actuator is saturated and cannot realize the requested control. A practical anti-windup method detects saturation and disables or adjusts integration; the University of Illinois control handbook states the mechanism plainly: detect saturation and turn the integrator off ([ECE 486 handbook](https://courses.grainger.illinois.edu/ece486/sp2025/documentation/handbook/lec09.html)). Tracking/back-calculation variants feed the difference between requested and saturated actuator output back into controller state; MIT's feedback-control notes describe feedback of `sat(u) - u` and note that the anti-windup path has no effect when there is no saturation ([MIT 16.30/31 lecture notes](https://mitocw.ups.edu.ec/courses/aeronautics-and-astronautics/16-30-feedback-control-systems-fall-2010/lecture-notes/MIT16_30F10_lec23.pdf)).

The transferable secondary rule is: **persistent enforcement state must be updated from what the actuator actually did, not merely what some upstream text resembled**.

For example, a harness may accumulate strikes, latch a “dangerous workflow” state, or escalate repeated violations. A mention in a document is analogous neither to commanded actuation nor to realized actuation. It should not wind up enforcement state. A denied proposed action may update a denial counter; an executed action should update the audit record from the executor's result; a passive mention should update only content-analysis telemetry.

This mapping is **likely (55-80%)** to reduce cascaded false escalation if any of the five detectors maintain counters, latches, cooldowns, or retry state. That premise is **UNVERIFIED; the experiment that settles it is to inspect each detector's state transition table and replay a repeated-mention sequence while recording state before and after each event**. If all detectors are stateless, anti-windup adds no value to this target problem.

### 1.5 Why dead-bands and hysteresis are not the primary answer

Control uses dead-bands to ignore sufficiently small deviations and hysteresis/dwell time to prevent rapid switching near a boundary. Hespanha and Morse describe hysteresis switching as preventing chatter ([HSCC paper](https://doi.org/10.1007/3-540-48983-5_13)); Liberzon's switched-systems notes similarly present hysteresis as a standard way to avoid chattering around a switching surface ([lecture notes](https://liberzon.csl.illinois.edu/teaching/Liberzon-LectureNotes.pdf)).

This does not solve use-vs-mention. The false fire is not necessarily a small-amplitude signal near a threshold. A quoted destructive command can be lexically “stronger” than a vague real instruction. Adding a keyword score dead-band would suppress some mentions and some real uses without restoring the missing role variable. Hysteresis could reduce repeated UI flapping after role has already been estimated, but it cannot make an unobservable role observable.

Using dead-band/hysteresis as the principal safety fix is **very unlikely (5-20%)** to dominate explicit channel metadata because its cited control purpose is suppression of boundary chatter, while the supplied defect is a category error between semantic roles. The experiment that could overturn this assessment is a labeled replay showing that false and true fires separate cleanly by a scalar score with stable margins across detector families and adversarial paraphrases. Until that result exists, no dead-band belongs on a hard safety decision.

## 2. Concrete harness translation

## Proposal — UNVERIFIED: Role-Routed Guard Governor

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

The proposal is **UNVERIFIED; a shadow-mode replay followed by an interventional canary, both specified in Section 4, would settle whether it reduces false fires without increasing unsafe executions**.

Build one small event-envelope adapter and change each affected guard to declare which semantic ports it consumes. Do not build a new orchestration runtime.

### 2.1 Trusted event envelope

The hook bus supplies an envelope separate from payload bytes:

```text
GuardEvent {
  transition_id     // stable ID across proposal -> decision -> execution -> result
  phase             // ingress | proposed_action | pre_execute | post_execute
  role              // instruction | proposed_action | observation | artifact | diagnostic
  origin            // owner | agent | tool | local_file | network
  trust_domain      // trusted_control | untrusted_content
  tool_name?        // present for action phases
  canonical_args?   // parsed executor arguments, never regex-extracted from prose
  payload?          // raw text, available to content analyzers
}
```

The critical property is that `phase`, `role`, `origin`, and `tool_name` are assigned by the harness adapter from the route and call frame. Untrusted content must not be able to self-assert `role=proposed_action` or `trust_domain=trusted_control` by embedding JSON-like text. Metadata is out-of-band, just as a physical signal does not choose which controller port its voltage is wired into.

`role` need not claim a perfect interpretation of arbitrary prose. At minimum, `proposed_action` is structurally exact when the agent emits a tool-call object, and `observation`/`artifact` is structurally exact when bytes arrive as tool output or file contents. Mixed user prose remains `instruction` with optional spans; it is not falsely advertised as solved.

### 2.2 Two planes, with different authority

1. **Content-analysis plane.** Scanners may inspect any payload and emit labels such as “contains command syntax,” “possible prompt injection,” or “secret-like token.” These are observations. On their own they do not authorize or deny an executor operation.
2. **Action-authorization plane.** Hard guards consume `proposed_action`/`pre_execute` events and evaluate `tool_name + canonical_args + workflow state`. They may allow, transform, ask for confirmation, or deny. They do not search surrounding documents for command-looking substrings to decide whether an action occurred.

The separation matters for prompt injection. An untrusted document can still be scanned and marked suspicious. If it influences the agent to emit an unsafe tool call, the canonical action is independently checked. Content suspicion can reduce trust or require confirmation, but the audit record must say “suspicious content observed,” not “dangerous action attempted,” unless the action transition actually happened.

This two-plane design is **very likely (80-90%)** to eliminate the class of false fires in which a hard action guard is invoked solely by mention text, because passive events never enter the action guard's declared port. Evidence is architectural exclusion, analogous to reference-governor placement. This is **UNVERIFIED for the supplied 12+ cases; replaying those exact cases through the adapter and asserting zero action-guard decisions would settle it**.

It is **likely (55-80%)** to catch a class the current design can miss: a dangerous action whose canonical arguments are assembled without containing the detector's trigger phrase in any single upstream text fragment—for example, a shell executable and arguments composed across steps. Evidence is that the proposed guard examines the final parsed action object rather than relying on phrase occurrence. This is **UNVERIFIED; mutation tests that split, quote, encode, and incrementally construct equivalent commands, then compare canonical executor requests, would settle it**.

It is also **likely (55-80%)** to improve audit attribution by linking content observation, proposal, decision, execution, and result with `transition_id`. Evidence is the explicit event contract. This is **UNVERIFIED; a trace-completeness test requiring exactly one terminal result or explicit cancellation per admitted transition would settle it**.

### 2.3 Role-specific policy table

| Event | Content scanner | Hard action guard | Persistent violation state |
|---|---:|---:|---:|
| owner instruction | yes, if useful | no action decision yet | no |
| retrieved/file text quoting a command | yes | no | no |
| agent's canonical tool proposal | optional | yes | update only on decision |
| executor invocation | audit only | already decided; fail closed if decision missing | update “attempted/executed” |
| tool result | scan as untrusted observation | no retrospective action decision | reconcile with realized result |

The executor-side invariant is more important than perfect ingress labeling:

```text
no executor invocation without an allow/transform decision
for the same transition_id and canonical action digest
```

If the action changes after approval, the digest changes and the guard runs again. A document that merely prints a serialized `GuardEvent` cannot satisfy the invariant because it lacks an adapter-issued transition and decision record.

### 2.4 What this catches and what it intentionally does not claim

Expected catches, all pending experiment:

- **likely (55-80%)**: canonical dangerous commands assembled from multiple benign-looking fragments, because enforcement sees the fully assembled action. Evidence: enforcement placement after assembly; **UNVERIFIED; settle with composition mutations**.
- **likely (55-80%)**: action/tool mismatches, such as destructive semantics hidden behind an unexpected executable or argument form, if canonicalization exposes the executable and operands. Evidence: parsed arguments are available; **UNVERIFIED; settle with platform-specific alias and wrapper fixtures**.
- **very likely (80-90%)**: documents, test fixtures, logs, and error reports that merely contain detector keywords will cease generating hard action decisions when routed as artifact/observation. Evidence: declared-port exclusion; **UNVERIFIED on production fixtures; settle with the known false-fire replay**.
- **likely (55-80%)**: false persistent escalation from repeated passive mentions, if such state exists, because only decision/execution transitions update enforcement state. Evidence: anti-windup-style realized-actuation feedback; **UNVERIFIED; settle with the state-transition inspection/replay**.

Non-claims:

- It does not perfectly separate use from mention inside one free-form user message.
- It does not prove that untrusted content cannot influence an agent.
- It does not replace semantic policy for determining whether a canonical action is dangerous.
- It does not guarantee safety when an executor bypasses the governed hook path.
- It does not infer intent from payload alone.

## 3. Adversarial transfer analysis

### 3.1 Structural assumptions that do transfer

**Known ports.** Tool proposal and executor invocation are discrete harness transitions, analogous to a command/actuator path. This transfer is **almost certain (90-99%)** for any harness that exposes pre-execution hooks; evidence is the proposal's required integration point, not an assertion that a particular local hook exists. If no such hook exists, the proposed BUILD-SMALL classification fails and the design must be re-scoped.

**Constraint supervision before actuation.** A guard can evaluate the canonical action before execution, like a reference governor constraining a command before it reaches a pre-stabilized plant. This transfer is **very likely (80-90%)** where hooks can deny or transform calls. Evidence: the reference-governor placement in the cited literature and the explicit harness contract; **UNVERIFIED locally; a no-op deny canary on a harmless fixture would settle hook controllability**.

**Realized-output feedback.** Tool results can reconcile proposed versus executed behavior, analogous to anti-windup tracking the constrained actuator. This transfer is **likely (55-80%)**, because tool APIs vary in whether they expose reliable completion/postconditions. Evidence: anti-windup theory supplies the pattern, while API variability limits confidence; **UNVERIFIED locally; terminal-event coverage measurement would settle it**.

### 3.2 Structural assumptions that do not transfer

**Physical port separation.** A plant's reference and sensor wires are distinct. A language message is a multiplexed symbolic object. A user can say “run `x`,” “do not run `x`,” or “the manual says ‘run `x`’” in one payload. Routing metadata identifies origin and phase but not every speech act.

**Low-dimensional dynamics.** Classical governor guarantees assume an explicit plant model, constraints, and often bounded uncertainty. Agent behavior and tool semantics are not captured by a trustworthy low-dimensional dynamics model. Importing a predictive optimizer or Lyapunov guarantee would be decorative mathematics unless such a model were established.

**Scalar proximity.** Dead-band and hysteresis assume a meaningful switching coordinate and neighborhood. Lexical detector scores do not automatically supply a safety-calibrated coordinate.

**Stable primary loop.** Reference governors are normally added to a pre-stabilized system. An agent workflow is not proven stable in that technical sense. The useful borrow is architectural placement, not a stability theorem.

Therefore, the analogy supports a typed routing and feedback contract, but **does not support claiming control-theoretic stability or safety guarantees for the agent harness**. That boundary is **almost certain (90-99%)** because the cited governor results require mathematical plant/constraint assumptions not supplied here.

### 3.3 Failure modes of the proposed borrow

1. **Metadata laundering.** If payload authors can set role/trust fields, the design collapses. Metadata must be assigned by trusted adapters.
2. **Bypass paths.** If even one executor route omits the pre-execution guard, a dangerous action can evade the governor. The detector must enumerate executor entry points using two mechanically independent signals before claiming coverage: static registration/configuration plus dynamic canary traces.
3. **Canonicalization gaps.** Shell aliases, wrappers, encoded scripts, platform quoting, and indirection can hide semantics after parsing. Canonicalization must preserve the exact bytes eventually executed as well as a parsed view.
4. **TOCTOU/action drift.** Approval of one digest must not authorize a mutated action.
5. **Mixed-role prompts.** Route-level labels are too coarse for arbitrary user prose. When policy genuinely depends on pragmatics rather than an action object, require clarification/confirmation or use a semantic classifier whose result is explicitly probabilistic.
6. **Content-plane overreach.** A suspicious-content label must not silently become an “attempted action” counter through a downstream aggregator.
7. **Postcondition blindness.** A zero exit status may not mean the intended state transition occurred; realized-actuation feedback needs domain-appropriate postconditions where stakes justify them.

## 4. Falsification and verification plan

### 4.1 Detector calibration controls

Before any absence/broken/done claim, validate each detector with a known-present control. For every affected detector, use:

- a positive operative action that must fire;
- the byte-identical text embedded in a quoted document that must not produce a hard action decision;
- a benign negative control;
- a mixed-role message containing both a quotation and a genuine request;
- a composed/encoded action whose final canonical request is equivalent to the positive action.

This is designed to prevent the known class of invalid “zero detections” conclusions. A detector is not declared inactive unless (a) its positive control is seen and (b) an independent trace at the executor/decision boundary confirms no relevant transition.

### 4.2 Shadow replay — experiment that settles the main UNVERIFIED proposal

Replay, without execution:

1. all supplied 12+ false-fire cases;
2. a balanced set of true operative cases for each of the five detectors;
3. mutation families: quotation, negation, code fences, logs, JSON serialization, split construction, aliases, encoding, and nested tool output;
4. adversarial metadata-looking strings inside payloads.

Record old decision, content-plane label, new action-plane decision, event role, canonical action digest, and expected label.

Primary acceptance criteria:

- 100% of known false-fire fixtures generate no hard action decision unless the fixture also contains a real canonical proposal.
- 100% of known true canonical proposals reach the relevant hard guard.
- Payload-embedded fake metadata never changes routing.
- Every executor canary has one matching pre-execution decision with the same digest.

The 100% thresholds are fixture acceptance criteria, not claims of population-wide perfection.

### 4.3 Interventional canary — mechanically independent signal

On a non-destructive fixture tool:

- submit an allowed proposal and observe both the hook decision record and fixture-side receipt;
- submit a denied proposal and observe both the denial record and absence of fixture-side receipt;
- mutate arguments after a recorded allow and confirm digest mismatch causes re-evaluation;
- emit identical command text as artifact output and confirm it creates a content label, if configured, but no fixture invocation.

Static route enumeration and dynamic fixture receipt are mechanically independent. Only their agreement justifies a coverage claim.

### 4.4 Stability/anti-windup replay

If detectors have state, replay 100 repeated mentions followed by one real proposal. Measure counter/latch state after each event. The desired result is no enforcement-state accumulation from mentions and exactly one proposal transition. Then replay repeated denied proposals and verify that any escalation is bounded and explicitly reset. If there is no detector state, record anti-windup as non-applicable rather than manufacturing one.

## 5. Anti-overfit gate and rejected alternatives

**Existing bus:** pass. The proposal is a small adapter plus guard subscription changes on the existing hook/tool bus.

**No rejected architecture reintroduced:** pass. It adds no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

**Model-improvement robustness:** pass in principle. Better models may reduce unsafe proposals, but canonical action gating and provenance remain useful because they are interface invariants rather than compensatory reasoning scaffolds. This is **very likely (80-90%)**, supported by the fact that reference-governor placement is independent of the internals of the primary controller; **UNVERIFIED for future agent APIs, and the settling experiment is an adapter compatibility test on each supported API version**.

Rejected alternatives:

- **Bigger regex/keyword lists:** rejected because they cannot recover an unobserved role from byte-identical payloads.
- **LLM classifier as sole gate:** rejected as the sole authority because it changes an information deficit into a probabilistic guess and remains vulnerable to mixed-role text. It may provide a content-plane label.
- **Dead-band on detector confidence:** rejected for hard safety because lexical strength is not semantic role.
- **Global “ignore code blocks” rule:** rejected because real operative instructions and attacks can be placed in code blocks.
- **New policy daemon or orchestration runtime:** rejected by the anti-overfit gate; the mechanism fits a small existing-bus adapter.
- **Predictive-control optimizer:** rejected because no validated plant dynamics or constraint model exists. The useful reference-governor borrow is placement, not optimization machinery.

## 6. Final verdict

Control theory has already solved the architectural half of use-vs-mention: preserve the identity of signal channels, supervise the command/reference path before actuation, and reconcile controller state with realized actuation. Observability explains why a payload-only detector cannot solve the remaining ambiguity when use and mention present identical bytes.

The best borrow is therefore a **Role-Routed Guard Governor**, **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**, with hard enforcement on canonical action transitions and separate content-analysis telemetry. Its production benefit is **very likely (80-90%)** for structurally passive artifacts versus canonical tool calls, based on the control-theoretic channel distinction and the architectural exclusion it enables. That benefit remains **UNVERIFIED; the exact known-false-fire replay plus the independent executor canary in Section 4 is the experiment that settles it**.

The analogy stops at mixed natural language. There, port metadata adds evidence but does not create semantic observability. Any claim that control theory has supplied a universal use-vs-mention classifier would be false.
