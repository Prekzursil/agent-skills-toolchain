# F009 — Red-team: Databricks cloud-job security

**Unit:** F009  
**Date:** 2026-07-19 UTC  
**Scope:** The live Databricks batch path that stages a harness bundle, reads Codex authentication from a Databricks secret scope, and runs autonomous Codex units on a corporate AWS job node with an IAM instance profile.  
**Authorization and restraint:** Defensive review of the owner's system. I used read-only local inspection, metadata-only permission probes, a role-name-only IMDSv2 request, and official primary documentation. I did not retrieve an AWS access key, secret key, or session token; did not read the contents or even the JSON keys of `/root/.codex/auth.json`; did not enumerate IAM permissions; did not alter the runner, job, bundle, manifest, secret scope, or AWS resources; and did not develop or execute an exploit. The only write is this artifact.

## Executive verdict

**Verdict: do not treat the present Databricks path as a security boundary.** It is a high-throughput trusted-input runner operating as root, not a safe executor for autonomous agents that inspect potentially adversarial material.

The most important end-to-end chain is **VERIFIED in all of its enabling conditions** and **REASONED, not exploited, as a complete attack**:

1. The batch manifest, bundle, result tree, and prior summary are in DBFS root and appear locally as mode `0777`; Databricks independently documents that DBFS root is accessible to all workspace users ([Databricks, “Recommendations for working with DBFS root”](https://docs.databricks.com/aws/en/dbfs/dbfs-root)).
2. The runner reads the manifest without a digest/signature, extracts the bundle without an integrity or member-safety gate, and accepts IDs and prompts without schema/path validation (`/Workspace/Users/costin.ionescu@bolt.eu/codex-batch/batch_runner.py:82-90,93-122,164-169`).
3. Each prompt is executed by `codex exec` with `--dangerously-bypass-approvals-and-sandbox`, web search enabled, MCPs disabled, and no OS privilege drop (`batch_runner.py:117-122`). A live process inventory counted **121 Codex launcher processes owned by root**.
4. One secret-scope value is materialized at `/root/.codex/auth.json`, mode `0600`, before all units run (`batch_runner.py:72-79,169-180`). Every unit is the same UID 0, so the `0600` boundary does not separate the units from the credential. A live `namei -l` check showed every path component and the file owned by root, and five sampled Codex processes all had UID 0.
5. The host can obtain the attached IAM role through IMDSv2. My role-name-only probe returned `datascience-databricks-ec2-role`; independently, `/databricks/common/conf/deploy.conf:223,298` records `arn:aws:iam::287845475429:instance-profile/datascience-instance-profile` and `instanceProfileUsed = "true"`. AWS documents that applications on an instance retrieve the role's temporary security credentials from this same metadata branch ([AWS, “Retrieve security credentials from instance metadata”](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-security-credentials.html)).
6. Host egress is not deny-by-default: `ip route` showed a default route and `iptables -S OUTPUT` returned `-P OUTPUT ACCEPT`. The runner intentionally downloads Node and an unpinned Codex release from the public internet (`batch_runner.py:55-65`).

It is **almost certain (90-99%)**, given the verified same-UID file access, reachable IMDS role, unrestricted agent shell, and outbound route, that a hostile unit which reaches execution could read the restored Codex credential and obtain role credentials. This is a capability assessment, not a claim that any unit did so. Whether a workspace user can modify this exact run's DBFS objects through the control plane is **very likely (80-90%)**, because Databricks says all workspace users can access DBFS root and the live objects are `0777`; the remaining uncertainty is the workspace's cloud/storage overlays and any undocumented account restriction. The settling experiment is to use a disposable file under this prefix from a non-admin test principal and test list/read/create/replace via the DBFS API, never against the live bundle.

The authorization/authenticity premise is the decisive issue. The current 180 manifest prompts appear owner-programmed, and I found no proof of malicious modification. **UNVERIFIED: no compromise is claimed.** The settling experiment is to compare uploader-side signed digests and creation audit events with the hashes measured on-node, then review OpenAI account activity, Databricks audit logs, VPC flow logs, and CloudTrail for the run window.

## Pipeline reconstruction and trust boundaries

The job runs the workspace source `/Workspace/Users/costin.ionescu@bolt.eu/codex-batch/batch_runner.py`. The secret is retrieved before `main()` validates or even reads the batch.

The current cluster is a single-node automated job cluster, not a service-principal cluster. `/databricks/common/conf/deploy.conf` recorded:

- `clusterUnityCatalogMode = "LEGACY_SINGLE_USER_STANDARD"` at line 227;

Databricks recommends running production jobs as a service principal and explains that jobs otherwise default to the creator's Run-as identity ([Databricks, “Manage identities, permissions, and privileges for Lakeflow Jobs”](https://docs.databricks.com/aws/en/jobs/privileges)). **UNVERIFIED: the exact Run-as principal, job ACL, notebook ACL, secret-scope ACL, policy JSON, and who may override notebook parameters were not available in the unpacked subject or safely derivable from local POSIX modes.** The settling experiment is an administrator export of Jobs API `2.1/jobs/get`, `permissions/jobs/<id>`, workspace object permissions, secret-scope ACLs, and compute policy `0F61EF4EEC0002D6`, with principal IDs mapped but secret values omitted.

### Stage B — bootstrap and mutable supply chain

`setup()` downloads Node `v22.11.0` from a constructed nodejs.org URL into `/tmp/n.tar.xz`, extracts it as root into `/opt/n`, then runs `npm install -g @openai/codex` without a version (`batch_runner.py:43-69`). The previous completed summary reports `codex-cli 0.144.6`; the live command line requests model `gpt-5.6-sol`.

There are three separate integrity gaps:

1. Node is version-pinned but no expected SHA-256/signature is verified before root extraction.
2. Codex is not version-pinned, so a re-run resolves whatever the registry tag provides at that time. npm documents that install resolves packages and that lock files/`npm ci` are the reproducible mechanism ([npm install documentation](https://docs.npmjs.com/cli/install/)).
3. The npm command is piped to `tail` without `set -o pipefail`; its return code is discarded, and the runner only asks whether some `codex` binary can subsequently print a version (`batch_runner.py:63-68`). On a reused node, that can accept a stale pre-existing executable.

No supply-chain compromise was observed. It is **unlikely (20-45%)** that these official distribution endpoints are malicious in an ordinary run, based on HTTPS transport and established publishers, but the impact is host-root execution and the job is intentionally reproducible security work. The risk is therefore material despite lower probability.

### Stage C — shared bundle shipment and extraction

The bundle is fixed at `/dbfs/tmp/codex-batch/harness-bundle.tar.gz`; SHA-256 measured during this review was `34db6a7998b886fe48230d829a83db4ba010deda648d486f31312c8779b95e48`. The runner never possesses or checks an expected digest (`batch_runner.py:9,25,82-90`). It extracts directly into an existing `/local_disk0/codexwork/bundle` directory with `tar -xzf` and does not clear it first, use a staging directory, validate members, reject links, enforce ownership/modes, or make the result immutable.

The current archive itself had 617 listed paths, zero absolute/`..` traversal names, and zero non-regular/non-directory member types under the bounded probes used here. That is a **VERIFIED clean-current-archive result**, not proof that the extractor is safe. The archive's regular files are stored as mode `0666`; umask `0022` made extracted files generally `0644`.

The live extracted tree later contained 628 regular files—11 more than the archive—consisting of Python bytecode caches under the shared bundle. The runner's earlier summary recorded 617 immediately after extraction. Together with `test -w /local_disk0/codexwork/bundle` succeeding as root, these are two mechanically independent signals that the “subject tree is unpacked read-only” text appended at `batch_runner.py:107-115` is behavioral instruction only, not enforcement. No harmful bundle edit was detected; the extra files are ordinary `__pycache__` outputs. The general consequence is still that one concurrent unit can contaminate what another unit subsequently reads.

### Stage D — manifest to root command

The batch JSON SHA-256 measured during this review was `e263ed7d9cef9dd872c23db8489b219205fd64e6d663de89bf530b96578c31b4`. It contains 180 unique unit IDs and about 1.396 MB of prompt text. The runner performs `json.load`, takes `batch["units"]`, and does no schema, size, count, string, timeout, path, or dependency validation (`batch_runner.py:166-175`).

For each unit it:

- joins the unvalidated `id` beneath `/local_disk0/codexwork` (`batch_runner.py:95-100`);
- writes the unvalidated prompt into that work directory (`:100-103`);
- joins the same ID into a DBFS result filename (`:104-105`);
- appends a remote override containing the result path (`:107-115`);
- interpolates `wd` and `pf` unquoted into a shell string and runs `bash -lc` (`:117-122`).

The current IDs are unique; 38 include punctuation (principally the legitimate `expansion.A...` form). I did not construct a malicious ID. Static data flow is sufficient to establish that shell metacharacters and path separators are not rejected before shell and filesystem use. It is **almost certain (90-99%)** that a purpose-built malicious ID could change shell parsing or escape an intended path, because this is direct unquoted string interpolation into `bash -lc`; the evidence is `batch_runner.py:95-121`. This is a defensive conclusion; no payload is supplied here.

Prompt replacement is even simpler than command injection: because the prompt is the program for an autonomous root agent, modifying a prompt requires no shell-parser trick. The manifest's DBFS placement and lack of authentication are therefore the primary exposure.

### Stage E — secret restoration and agent execution

The code comment says a token “never lands on shared storage” (`batch_runner.py:11-13`). Narrowly, that is true: I found no auth file in DBFS and did not inspect credential values. But the stronger security implication is false. `restore_auth()` writes the entire secret-scope string to `/root/.codex/auth.json` and chmods it `0600` (`:72-79`). The summary writes the credential file's byte length, 4938, to the shared `_summary.json` (`:169,187-188`); length leakage is minor but unnecessary.

The restored file is protected from a different Unix UID. It is not protected from these agents:

- all sampled agents and the runner are UID 0;
- 121 live Codex launcher processes were owned by root at the observation point;
- `test -w /root/.codex/auth.json` succeeded from a unit process;
- the runner launches Codex with sandbox and approvals bypassed (`:117-122`);
- all units share `/root/.codex`, whose session databases, WALs, shell snapshots, configuration, caches, and sessions are also visible to the same UID.

The `--ignore-user-config` flag reduces configuration injection from the installed user config, and `mcp_servers={}` removes MCP exposure. These are good controls. They do not isolate credentials, processes, filesystem, network, or other units.

Databricks explicitly warns that secret redaction cannot prevent authorized code from deliberately transforming or indirectly referencing a secret and says ACLs must limit who can run commands ([Databricks secret management](https://docs.databricks.com/aws/en/security/secrets/)). Once the secret is copied to a normal file and the agent has root shell access, notebook-output redaction is not a confidentiality boundary.

**UNVERIFIED: I found no evidence that a unit opened or exported the auth file.** A metadata-only scan found no process currently holding the file open, but that cannot establish historical absence. The settling experiment is OpenAI account/session audit plus egress logs correlated to unit process times; absence may only be concluded if those detectors first find a known control event.

### Stage F — AWS identity and egress

The instance profile is not merely configured; its metadata endpoint is reachable from unit code. I requested an IMDSv2 token and queried only the role-name collection endpoint. It returned `datascience-databricks-ec2-role`. I immediately discarded the metadata token and did not request the role document containing credentials.

Independent Databricks signals are `/databricks/common/conf/deploy.conf:223` (instance-profile ARN), `:298` (`instanceProfileUsed=true`), and `/databricks/driver/conf/spark-branch.conf:334` (the Databricks instance-profile credential provider). Databricks warns that once compute launches with an instance profile, anyone with attach permission can access the resources controlled by that role ([Databricks compute configuration reference](https://docs.databricks.com/aws/en/compute/configure)). AWS says applications on the instance can retrieve temporary credentials for exactly the actions/resources assigned to the role ([AWS EC2 IAM role documentation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html)). IMDSv2 prevents trivial unauthenticated remote SSRF patterns; it does not separate arbitrary local root code from the role.

**UNVERIFIED: the IAM policy, permission boundaries, session policy, S3 bucket policies, KMS grants, SCPs, and CloudTrail events were not inspected.** Therefore this report does not claim access to any particular S3 bucket, database, secret, or AWS API beyond the verified role-name endpoint. The settling experiment is IAM Access Analyzer plus `iam simulate-principal-policy` over a defensively enumerated action set, followed by a disposable denied-action canary; use CloudTrail to confirm the observed session's actual API calls.

Given the role name, profile ARN, corporate account, and cluster log bucket, the role may be data-capable, but the magnitude is **roughly even (45-55%)** until its policy is examined. This band reflects direct proof of credential reachability but no permission enumeration. Impact was conservatively scored 5 because a broad role is plausible and the missing policy is precisely the control that would reduce it.

### Stage G — results, replay, and cleanup

Results are written to a caller-selected DBFS directory, one `<id>.md` file per unit (`batch_runner.py:104-105`). Success requires only:

- an artifact exists;
- its size is at least 1024 bytes;
- the substring `UNIT-COMPLETE` occurs somewhere in its last 600 characters;
- Codex exits zero (`:124-140`).

The owner's required exact terminal line is not enforced. The result is not hashed, signed, exclusively created, atomically finalized, bound to the prompt digest/model/runner digest, or re-read after the summary is committed. Any post-check replacement is invisible.

More seriously, the result path is reused across executions and not cleaned. Two independent live signals establish stale mixing:

1. `/dbfs/tmp/codex-batch/results/batch-01/_summary.json` was timestamped 2026-07-18 23:17 UTC and describes a previous 20-unit `X001`…`X020` batch, while the current `/dbfs/tmp/codex-batch/batch-01.json` contains 180 different units.
2. The same directory simultaneously contained old `X*.md` artifacts and newly arriving `expansion.A*.md` artifacts. The runner creates directories but never removes or namespaces prior output (`batch_runner.py:99,104-105,124-140,186-188`).

If a rerun uses an existing ID and Codex returns zero without producing a new file, the stale file can satisfy the current checks. This is **almost certain (90-99%)** from the source's existence-only check and lack of pre-run unlink/freshness binding; a disposable replay test would settle the remaining platform-specific detail. The current summary itself is stale during execution and is overwritten only at the end, so downstream consumers that poll it can ingest the wrong run.

There is also no `finally` cleanup for `/root/.codex/auth.json`, per-unit prompts, last-message files, Codex state, or the bundle. `autoTerminationMinutes=1440` is not a cleanup guarantee during a long or failed job. `subprocess.run(... timeout=...)` kills/waits for its direct child, but `sh()` creates no new session or process group and performs no descendant sweep (`batch_runner.py:32-40,117-123`). **UNVERIFIED: orphaned Codex descendants after timeout were not induced.** The settling experiment is a disposable unit that spawns a benign long-lived child, reaches timeout, and then checks the process tree and credential cleanup before cluster termination.

The cluster tag says local disk encryption is disabled (`deploy.conf:180`). Databricks documents that enabling local disk encryption gives each compute node a unique local key for data stored on local disks ([Databricks compute configuration reference](https://docs.databricks.com/aws/en/compute/configure)). **UNVERIFIED: the underlying AWS volume encryption state and whether `/root` is backed by a volume separately encrypted by AWS were not established.** The settling experiment is a compute configuration export plus EC2 `DescribeVolumes`/KMS metadata for this instance, with no snapshot or credential access. Do not infer plaintext physical media solely from the Databricks tag.

## Detailed findings and remediations

### F1 — Critical: unauthenticated shared inputs become unsandboxed root actions

**Status:** VERIFIED primitives; REASONED end-to-end hostile use.  
**Evidence:** `batch_runner.py:82-90,93-122,164-169`; live DBFS modes; Databricks DBFS documentation; root process inventory.  
**Exploit prerequisite:** ability to replace the manifest or bundle, alter the job's batch parameter, modify the workspace runner, or introduce adversarial content that the model follows. Exact current job ACL is UNVERIFIED; export the APIs listed in Stage A to settle it.

The runner crosses four trust boundaries without authentication: shared storage → parser, parser → prompt, ID → shell/path, and prompt → root/network. Any one of manifest signature verification, strict schema/path handling, non-root sandboxing, or removal of cloud identity would reduce risk. None is present.

#### Remediation F1a — authenticated, per-run staging — CONFIG

Move input/output from DBFS root to a Unity Catalog Volume or workspace file tree governed by a dedicated job service principal. Create a fresh cryptographically random run directory; grant the uploader write, the job read on inputs and create-only/write on that run's outputs, and no access to ordinary workspace users. Disable legacy DBFS root after migration. Databricks recommends UC volumes/workspace files and documents that DBFS root lacks this governance ([disable DBFS root and mounts](https://docs.databricks.com/aws/en/dbfs/disable-dbfs-root-mounts)).

It is **very likely (80-90%)** this removes the current workspace-wide read/replace path, based on Databricks' documented UC governance; the uncertainty is the owner's exact metastore and service-principal setup. The acceptance experiment is an unprivileged workspace-principal matrix proving deny for list/read/create/overwrite on the run prefix while the job principal can perform only its required operations.

#### Remediation F1b — signed manifest and bundle gate — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Before secret retrieval or extraction, verify a detached signature or a trusted uploader-supplied SHA-256 manifest covering: runner version, batch JSON, bundle archive, every unit ID, prompt digest, expected model, timeout, and output run ID. Copy verified inputs to a newly created local staging directory and re-hash after copy. Abort closed on mismatch. Never take the “expected” hash from the same writable directory as the objects.

It is **almost certain (90-99%)** this detects post-signing input replacement, because the check is content-addressed and occurs before privilege/secret acquisition. It does not make maliciously signed owner input safe; the evidence is the direct mutable-storage gap at `batch_runner.py:82-90,166-169`.

#### Remediation F1c — strict schema, path containment, and argv execution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Use a closed JSON schema; cap units, prompt bytes, and timeout; require unique IDs matching a narrow pattern such as ASCII letters/digits plus `._-` with a short maximum; resolve every path and assert it remains under the fresh run root; reject pre-existing targets and links; and invoke Codex with an argv list and an opened stdin file rather than `bash -lc`. Treat `result_dir`, `batch_json`, and `scope` as fixed job configuration, not general run parameters.

It is **almost certain (90-99%)** this removes the identified ID-to-shell and path traversal class, because no untrusted string reaches a shell parser and containment is checked. Tests must include separators, Unicode confusables, duplicate IDs, oversized prompts, links, and boundary timeouts; this statement is grounded in the direct interpolation at `batch_runner.py:95-121`.

### F2 — Critical: Codex auth and AWS role are inside the agent's trust domain

**Status:** VERIFIED exposure; no unauthorized use observed.  
**Evidence:** `batch_runner.py:13,72-79,117-122,169`; auth path mode/ownership; UID inventory; IMDSv2 role-name probe; `deploy.conf:223,298`; AWS and Databricks official documentation.

Secret scope storage solves transport-to-runner and at-rest management. It does not solve secrets exposed to arbitrary code at the same UID. Likewise, IMDSv2 solves classes of remote metadata theft but intentionally serves local workloads. A model-generated root shell is a local workload.

#### Remediation F2a — immediate credential and role containment — CONFIG

Terminate this class of job cluster after the run; rotate/revoke the Codex auth material used by the batch; detach the corporate data instance profile from agent compute; and inspect OpenAI activity, CloudTrail, VPC flow logs, Databricks audit logs, and S3 data events for the run window. Whether theft occurred is **UNVERIFIED; the settling experiment is that correlated audit review**. Rotation is recommended because access by every autonomous root unit is verified, not because theft was observed.

It is **very likely (80-90%)** detaching the instance profile prevents future units from obtaining that role through the verified metadata path, provided no other AWS credentials are injected. The acceptance experiment is role-name and STS calls from an agent sandbox returning denied/no-credentials while required staging remains available through a narrower governed mechanism.

#### Remediation F2b — least-privilege job identity — CONFIG

Run the job as a dedicated Databricks service principal; grant it only read access to immutable inputs, create-only/write access to the current output prefix, and read access to one purpose-specific secret scope. Use UC storage credentials/external locations instead of a node-wide legacy instance profile where AWS data access is genuinely necessary. Databricks recommends both service principals for production jobs and Unity Catalog rather than instance profiles ([job permissions](https://docs.databricks.com/aws/en/jobs/privileges), [compute configuration](https://docs.databricks.com/aws/en/compute/configure)).

It is **likely (55-80%)** this materially lowers blast radius on the current platform, but it cannot hide a Codex credential that the same OS process must consume. The lower band reflects that distinction; acceptance requires IAM/UC negative tests, not just configuration review.

#### Remediation F2c — credential-brokering execution boundary — BUILD-LARGE (new daemon/service/runtime -- needs its own justification)

For genuinely untrusted autonomous execution, do not place a reusable OpenAI credential in the agent's filesystem or environment. Put Codex API access behind a narrow egress proxy/broker outside the unit's OS trust domain; allow only the required OpenAI API surface, inject upstream credentials at the broker, bind short-lived capability tokens to one run/unit/model/budget, and deny arbitrary destinations. Run units in ephemeral sandboxes with no corporate IAM role and destroy them after output finalization.

This intentionally crosses the anti-overfit gate's presumption against a second runtime/service. The exception is justified: a filesystem mode or prompt rule cannot hide a credential from arbitrary same-UID root code. The proposed boundary addresses a verified security impossibility, not model-quality orchestration, memory, observability, critics, or durable workflow. It introduces no vector database/KG, trained critic, observability SaaS, guardrail framework, or durable-execution engine.

It is **very likely (80-90%)** a correctly isolated broker plus deny-by-default egress prevents direct credential-file theft and arbitrary AWS egress; the remaining risk is broker implementation, API-level abuse within the delegated budget, and sandbox escape. Settle it with adversarial canaries that attempt file/env/proc/IMDS reads and off-allowlist connections, plus broker-side budget and destination assertions.

### F3 — Critical: concurrent units are one root security principal

**Status:** VERIFIED.  
**Evidence:** 121 root Codex launchers; common `/root/.codex`; writable shared `/local_disk0/codexwork`; source `batch_runner.py:27,93-122,178-180`.

Units can inspect or modify one another's prompts, local outputs, process state, common Codex databases, and common subject tree. The per-unit working directory is organization, not isolation. One unit can also consume node resources or kill peers because all are root. The current workload intentionally invites red-team and security analysis, increasing the chance that inspected content contains adversarial strings.

#### Remediation F3a — sandbox and unique OS identity per unit — BUILD-LARGE (new daemon/service/runtime -- needs its own justification)

Run each unit in an ephemeral container/VM or an equivalent hardened sandbox with a unique UID, private HOME, private process namespace, read-only verified input snapshot, bounded scratch, no host root, no Docker socket, no `/proc` visibility into peers, resource quotas, and a narrow output channel. Keep the runner outside unit namespaces. Batching trusted units per sandbox is an explicit transitional risk-acceptance option; security-sensitive/red-team units need one trust domain each.

This also crosses the anti-overfit gate, justified by verified cross-unit root equivalence. It is isolation infrastructure, not a competing orchestration framework. It is **very likely (80-90%)** to block ordinary cross-unit file/process interference if namespaces and mounts are correctly configured; sandbox escape remains. Acceptance requires unit A being unable to stat/read/write unit B's HOME, prompt, process, result staging, or broker token.

#### Remediation F3b — transitional least privilege — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Until stronger isolation exists, create a dedicated unprivileged local user for the batch, make the verified bundle owned by a supervisor and read-only to that user, use private `0700` per-run/per-unit directories, set a restrictive umask, cap concurrency, and remove `--dangerously-bypass-approvals-and-sandbox`. This does not hide a shared auth token from units under that same UID; it only reduces host and accidental cross-tree damage.

It is **likely (55-80%)** this reduces accidental mutation and host takeover, but **unlikely (20-45%)** to stop a deliberately hostile unit from stealing a credential still readable by its own principal. The evidence is the current same-UID design.

### F4 — Critical: sensitive harness history and results are workspace-wide

**Status:** VERIFIED storage placement and platform behavior.  
**Evidence:** DBFS paths/modes; tar inventory; official DBFS documentation.

The shared tar contains at least `inputs/corpus.json` and `claude/hooks/recall-inject/index/recall_index.json`, which by the pinned description summarize extensive owner session history and memory metadata. Results contain detailed security findings and local path/configuration evidence. Both input and outputs sit under DBFS root. Databricks states that all workspace users can access DBFS root and recommends not storing sensitive or production data there ([DBFS root recommendations](https://docs.databricks.com/aws/en/dbfs/dbfs-root)).

No claim is made that a workspace user actually read these objects. **UNVERIFIED: access events require Databricks audit/S3 data-event review; that experiment would settle historical access.**

#### Remediation F4 — governed storage, minimization, retention — CONFIG

Move the bundle and results to a UC Volume with explicit grants, exclude memory indexes and corpus fields not required by a unit, encrypt governed storage with the account's required keys, set a short retention policy, and disable DBFS root after dependent workflows migrate. Separate raw artifacts from a sanitized summary intended for broader circulation.

It is **very likely (80-90%)** explicit UC grants and minimization reduce unauthorized workspace disclosure, based on Databricks' documented migration path. Prove it with the principal matrix and audit events; do not infer protection from POSIX mode alone.

### F5 — Critical: stale, replayable, replaceable results can be called successful

## Replacement versus evolution

### Evolution option

Keep Databricks only as the batch coordinator, but remove DBFS root, remove the corporate instance profile, use a job service principal, verify signed inputs, run a fixed immutable Codex version, create fresh result namespaces, and place each unit in a genuine least-privilege sandbox. This reuses the current job and storage buses.

It is **roughly even (45-55%)** that Databricks classic job compute can deliver the required per-unit OS and credential isolation without awkward custom infrastructure. Evidence for the positive side is job compute, policies, UC volumes, and network controls; evidence for the negative side is the current single-user/root runtime and the need to give Codex network authentication while hiding it from model-generated shell.

### Replacement option — BUILD-LARGE (new daemon/service/runtime -- needs its own justification)

Replace the execution plane—not the catalog/orchestration logic—with an ephemeral sandbox service purpose-built for hostile code: no AWS role, brokered OpenAI access, deny-by-default egress, immutable input snapshot, unique identity per unit, output-only channel, strict CPU/memory/time budget, and destruction after receipt. Two integration choices to test are Databricks submitting jobs and collecting receipts, or the existing local orchestrator doing so. Do not add memory databases, trained critics, durable workflow engines, or an observability SaaS.

This is the radical recommendation if the units will continue to inspect untrusted repos, fetched web content, or security artifacts. It is **very likely (80-90%)** better than attempting to make same-root Databricks subprocesses safe, because it places the security boundary below the model-generated shell. It costs more engineering and operational ownership, which is why it is not the default for trusted analysis-only batches. A short bake-off should decide: run the acceptance suite below on both a hardened Databricks evolution and the isolated executor, then compare containment, throughput, cost, and operator burden.

## Acceptance tests before another sensitive run

Every test uses synthetic secrets and disposable resources. No production credential should be used as a canary.

1. **Storage ACL test:** a non-admin workspace principal cannot list/read/create/replace inputs or outputs; the job principal has only the required directional grants.
2. **Tamper-before-start test:** change one byte in manifest, bundle, runner, or expected model; the job aborts before secret retrieval and before starting any unit.
3. **TOCTOU test:** replace a verified object after the first hash; re-hash/copy binding aborts.
4. **Schema/path test:** separators, metacharacters, Unicode confusables, duplicates, links, absolute paths, oversized prompts, and out-of-range timeouts are rejected without creating files outside the run root.
5. **Archive test:** traversal, absolute names, links, device entries, mode/owner tricks, decompression bombs, duplicates, and stale destination entries all fail closed.
6. **Auth isolation test:** unit code cannot read/stat the real credential store, environment, supervisor memory, peer state, or broker upstream secret. A synthetic credential read attempt is logged and denied.
7. **IAM test:** IMDS role-name and STS calls from unit code fail; required object access succeeds only through the intended narrow identity.
8. **Egress test:** OpenAI/API allowlist succeeds; arbitrary HTTP(S), DNS tunneling canaries, metadata IP, private RFC1918 ranges, and S3 direct endpoints fail and are audited.
9. **Cross-unit test:** unit A cannot observe or modify B's prompt, HOME, process, scratch, result, logs, or budget.
10. **Replay test:** pre-create an old valid artifact and summary; the new run refuses the prefix and cannot report success from it.
11. **Finalize test:** partial/crashed outputs never appear final; exact sentinel and receipt digests are mandatory; post-finalization replacement is detected by consumers.
12. **Timeout test:** a benign descendant survives the direct shell unless the new containment works; after timeout, assert no unit process remains.
13. **Log canary test:** literal and transformed synthetic secrets do not appear in artifacts, failure tails, driver logs, cluster-log S3, Codex state, or notebook results.
14. **Cleanup test:** after success, failure, cancellation, and runner exception, no auth file, prompt, unit state, temporary archive, or process remains; the compute terminates on schedule.
15. **Supply-chain test:** the run makes no Node/npm installation requests; binary and image digests match the signed receipt.
16. **Authorization test:** a CAN VIEW principal cannot run or parameterize; a CAN MANAGE RUN test principal cannot override fixed security parameters; only narrowly trusted principals can edit job/source/policy.

It is **very likely (80-90%)** this suite detects the concrete classes found here because each test maps directly to a verified boundary. It cannot prove absence of sandbox escapes or provider compromise; retain patching and periodic independent red-team review.

## Bottom line

The Databricks path successfully moved the credential out of DBFS, but then placed it inside the same root trust domain as 121 unsandboxed autonomous processes and an attached corporate AWS role. The shared DBFS input/output design additionally permits unauthenticated replacement and stale replay, while runtime dependencies are fetched mutably as root. These are not theoretical style issues; the enabling primitives were observed on the live node. No exploit or compromise was observed.

The immediate safe course is: quarantine and hash the current outputs; audit/rotate the exposed Codex auth; audit and detach the instance profile from agent compute; move staging off DBFS root; bind every run to signed immutable inputs and fresh outputs; and do not resume sensitive autonomous runs until auth/IMDS/cross-unit isolation tests pass. It is **very likely (80-90%)** that those changes eliminate the concrete paths documented here, with the residual risk concentrated in sandbox/broker implementation and provider supply chain.
