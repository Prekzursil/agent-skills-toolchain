# M04 — Honest capability signalling: an externally grounded check against real overclaims

## Executive result

The harness does not need another generic honesty prompt or a seventh hook. It already has `honest-signal`, `truth-verify`, `claim-guard`, the capability catalog, MCP liveness, an event ledger, and open-loop machinery. The highest-leverage change is **very likely (80-90%)** to be turning `honest-signal` from a **tool-presence lint** into a **claim-to-relevant-receipt checker**, because it directly closes the independently observed implementation and test-contract gap while reusing the existing Stop dispatcher. Today, any substantive tool call suppresses `honest-signal`, irrespective of whether that call bears on the asserted fact (`hooks/honest-signal/check.py:24-30,173-190,233-247`); its test suite verifies only the favorable case where `grep timeout config.py` actually relates to the timeout claim (`hooks/honest-signal/test_honest_signal.py:83-113`). Those are two mechanically independent signals (implementation and test contract) for the same gap.

The proposed check is:

> **A load-bearing capability/status claim may be stated as observed only when a typed, fresh, claim-relevant receipt exists outside the prose that makes the claim. Otherwise say `unknown`, `registered but unprobed`, `observed unavailable`, or use an evidence-paired confidence band. Negative claims require a known-positive detector control plus a second independent signal.**

This unit proposes eight findings, ordered with inferred-surprise items first. Every runtime change folds into an existing carrier; no proposal adds a hook invocation. No proposal adds a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Grounding and epistemic limits

All local citations below are paths relative to the concrete unpacked subject root `/local_disk0/codexwork/bundle/`; each includes source line numbers.

### What the corpus establishes

The distilled corpus covers 11,633 transcript files / 10.62 GB / 1,564,084 lines, with zero failed files, one bad line, and 32 oversized lines; it also warns that samples are capped (`inputs/corpus.json:2-11`). The tool reliability data therefore provide strong operational priors. They do **not** by themselves preserve enough claim/result adjacency to label every assistant overclaim.

Concrete capability-signalling pressure is visible:

* A nominally available Tavily MCP tool was invoked 532 times and failed 137 times (25.75%) (`inputs/corpus.json:175-180`); the corpus independently records 275 `MCP server "claude.ai Tavily" is not connected` fingerprints (`inputs/corpus.json:4388-4404`). Thus “registered”, “used historically”, and “available now” are observably different states.
* ToolSearch had only 4 errors in 5,091 calls (`inputs/corpus.json:87-92`), while the capability-use section records many MCP server and tool names (`inputs/corpus.json:13370-13464`). This makes ToolSearch/tool schema a useful *visibility* signal, not proof of liveness or authorization.
* The corpus records explicit same-turn dynamic-tool probes and asks for `TOOL_NOT_AVAILABLE` when a newly registered tool is not visible (`inputs/corpus.json:10857-10872`). Dynamic visibility must therefore be tested in the context making the claim.
* Background work can have no completion record; the preserved notification explicitly says to inspect partial output rather than assume completion (`inputs/corpus.json:11230-11234`). “Started”, “stopped”, and “completed” must be distinct capability/status states.
* Verification skills were invoked, but sparsely relative to the corpus: `fresh-context-verify` 5 times and `verification-before-completion` 3 times (`inputs/corpus.json:13291-13296`). This is evidence of use, not proof of effectiveness.
* The corpus hook section is unusable by its own known-positive control and explicitly says to treat it as no data (`inputs/corpus.json:13260-13264`). No conclusion below uses empty hook telemetry as evidence of non-firing.
* The owner-correction miner reports 2,268 candidates but calls itself recall-biased and says an unfiltered smoke sample produced 41/41 false positives (`inputs/corpus.json:10371-10374`). Candidate count is not an overclaim count.

### Two higher-confidence live incidents

The operating-defects input supplies the strongest directly diagnosed overclaims. Six wrong conclusions in one session came from single unvalidated probes, and a known-positive control later separated a genuinely broken hooks detector from working skills/agents detection (`inputs/INPUT-known-harness-defects.md:111-129`). Separately, an orchestrator invented “Write is blocked for `~/.claude`” and propagated it into about 15 prompts; the resulting PowerShell workaround was measured as 13.6% failure versus 0.0% for Write (`inputs/INPUT-known-harness-defects.md:151-160`). These are direct targets for Findings 2 and 4.

### Limitation that materially shapes the design

The unpacked Linux bundle does not contain the raw transcript tree named by `_meta.root`; it contains the 1.3 MB distillation. Therefore, **UNVERIFIED: the prevalence, precision, and recall of each proposed overclaim class are unknown here; the settling experiment is the two-stage raw-transcript benchmark in Finding 6, run on the Windows subject where the JSONL files exist.** I do not turn the 2,268 recall-biased candidates into a prevalence claim.

## Architecture in one page

The minimal data model is a typed receipt, stored through the existing event ledger rather than a new service:

```json
{
  "receipt_id": "r_...",
  "ts": "...",
  "claim_type": "capability.live|capability.visible|result.complete|fact.value|absence",
  "subject": "mcp__claude_ai_Tavily__tavily_extract",
  "scope": {"session": "...", "cwd": "...", "target": "..."},
  "signal": {"kind": "tool_result|exit_code|file_hash|remote_state|owner|fresh_model", "ok": true},
  "probe": "exact tool name or normalized command",
  "expires_at": "...",
  "source_event": "tool_use_id / ledger event id"
}
```

At Stop, the existing `honest-signal` dispatcher check extracts only load-bearing claims and maps each to an evidence predicate. It does not decide truth from its own prose. Examples:

| Claim | Required external receipt |
|---|---|
| “I can call tool X” | X is visible in this context **and** the action is authorized; if “now/live”, a fresh successful health/no-op call |
| “X is unavailable” | validated detector finds a known-present control **and** an independent probe fails for X |
| “Task X is complete” | terminal task/workflow state plus expected output/artifact/test receipt |
| “The fix works” | existing claim-guard E2E/acceptance receipt |
| “Value is Y” | read/query result whose target and extracted key match the claim subject |
| “I cannot do X” because of policy | cited policy/config receipt plus, when safe, a non-mutating authorization probe |

If evidence is missing, the check injects one compact repair instruction into the same Stop carrier: **“Change `available` to `registered but unprobed`, or run probe P.”** It exits 0 on all errors. It never asks the owner merely to repair the agent’s uncertainty.

## Finding 1 — Replace “any tool ran” with claim-relevant evidence receipts

**Improvement.** Upgrade the existing `honest-signal` check into a typed claim/evidence join. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold it into the already registered `honest-signal` entry in `_dispatch/manifest.json`; add no hook invocation.

**What it is.** Normalize a narrow set of load-bearing claim frames (`can/cannot`, `available/unavailable`, `connected`, `authorized/blocked`, `started/running/stopped/completed`, exact factual values, and generic “done/works” delegated to claim-guard). Normalize tool events into receipts. Require subject, scope, freshness, and evidence-kind compatibility. A `Read README.md` receipt cannot support “Tavily is connected”; a successful `grep timeout config.py` can support the timeout claim only if the command output contains the asserted value and the target matches. If no compatible receipt exists, rewrite the epistemic status instead of merely adding “probably”.

**Why inferred.** The owner did not ask for more hedging; they asked never to overclaim capability. The present check says any substantive tool suppresses it (`hooks/honest-signal/check.py:24-30,233-247`), while the harness honesty rule already requires a band paired with evidence (`claude/AGENTS.md:72-83`). The owner’s live D2 incidents show that “a probe happened” is not equivalent to “a valid probe supported this conclusion” (`inputs/INPUT-known-harness-defects.md:111-129`).

**How to build.**

1. Add `claim_frames.py` beside `honest-signal/check.py`: deterministic patterns produce `{type, subject, polarity, asserted_state, span}`. Reuse the shared use-vs-mention discriminator required by D1 before matching prose; do not grow more independent regex scanners.
2. Add `receipt_from_event(event)` that recognizes tool result IDs, normalized target path/tool name, exit/status, output digest, and timestamp. Prefer event-ledger records; fall back to the current transcript only when a real tool result is present.
3. Add a small compatibility table: claim type -> allowed receipt kinds + TTL + target match. Default is no match, not “any ok command”.
4. Keep existing delegation: RE anchors stay with `truth-verify`; test/build/functional claims stay with `claim-guard` (`hooks/honest-signal/check.py:11-22,93-109`).
5. Emit at most one message with at most two offending claims. Maintain current `try/except`, anti-loop, and exit 0 (`hooks/honest-signal/check.py:216-264`).
6. Add adversarial tests: unrelated successful tool, stale success, wrong target, output lacking claimed value, mentioned/quoted claim, negative sentence, safe hedge, matching live probe, and owner-supplied fact.

**External signal that verifies it.** A tool result/exit code/file read/remote query external to the generated sentence and relevant by typed subject. The implementation passes only if a held-out raw-transcript set shows the unrelated-tool examples fire and matched-receipt examples stay silent. **UNVERIFIED: D1’s shared discriminator is not yet confirmed to expose sufficient fence/role context; experiment: dump the Stop payload and replay the nine recorded D1 false fires plus a real source-code marker before wiring claim extraction.**

**SOTA.** Tian et al. found that verbalized confidence from RLHF models can be better calibrated than token probabilities, but calibration is benchmark-dependent and is meant to enable deferral—not to substitute for evidence ([Just Ask for Calibration, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.330/)). MiniCheck frames grounding as checking each claim against potential evidence, which supports claim-level joins rather than response-level “some tool ran”; this proposal uses deterministic receipt matching rather than MiniCheck’s trained checker, because trained critics are excluded by the anti-overfit gate ([MiniCheck, 2024](https://arxiv.org/abs/2404.10774)).

**Value x effort.** value(transformative) x effort(medium).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **very likely (80-90%)** to catch the live D2/D4-shaped overclaims without owner input, because the gap is independently visible in code and test contract and the deciding evidence already exists in tool events. The remaining uncertainty is semantic extraction precision, settled by Finding 6.

**Anti-overfit gate.** Passes: it replaces logic inside an existing dispatched check and reads the existing ledger. It introduces none of the rejected components.

## Finding 2 — Capability is a state vector, not a Boolean

**Improvement.** Extend the existing capability catalog and MCP-liveness data with explicit `registered / visible / live / authorized / task-proven` state and freshness. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This builds on capability-catalog and mcp-liveness; it does not add a catalog v2 or another liveness hook.

**What it is.** Separate five questions that agents currently collapse:

1. **Registered:** a config/catalog entry exists.
2. **Visible:** the tool schema is present in this exact model context.
3. **Live:** a fresh external probe succeeded.
4. **Authorized:** policy/credentials permit the intended operation.
5. **Task-proven:** an operation representative of the requested task succeeded on the actual target.

Render only the smallest truthful phrase: `registered, not visible here`; `visible, liveness unknown`; `observed live 4m ago`; `live but write authorization untested`; `task-proven on repo X at commit Y`. “I can do X now” requires the relevant conjunction, not merely an installed skill.

**Why inferred.** The catalog is intentionally a static, curated SessionStart injection (`hooks/capability-catalog/inject.py:2-13,42-52`) and its footer says to name a daemon rather than “no access” when an MCP is disconnected (`hooks/capability-catalog/catalog.json:2-4`). Yet Tavily’s historical tool presence coexists with 25.75% errors and 275 not-connected fingerprints (`inputs/corpus.json:175-180,4388-4404`). The owner’s dynamic gamma probes further show that registration and same-context visibility differ (`inputs/corpus.json:10857-10872`).

**How to build.**

1. Add optional state fields to existing catalog entries, not a second catalog file: `visibility_source`, `liveness_probe`, `auth_probe`, `ttl_seconds`, `last_observation`.
2. Have existing MCP-liveness write its successful/failed probe receipt to the event ledger. Capability-catalog reads that sidecar at SessionStart and annotates only routed capabilities; do not dump all 355 skills.
3. For native tools, ToolSearch/schema presence supplies `visible`. For binaries on Windows, use `Get-Command` rather than Git Bash `which`; for MCPs, use the existing health/no-op call. For authorization, use a non-mutating identity/whoami/list call when available.
4. Expire `live` rapidly for process-backed MCPs; retain `registered` until config changes. A stale observation becomes `unknown`, never silently remains `live`.
5. On failure, route to an already catalogued alternative when semantically equivalent and label the degradation (`Tavily unavailable; used Exa`). Do not say “no web access” while WebSearch/Exa remains visible.

**External signal that verifies it.** Same-context tool-schema visibility plus a distinct liveness/identity probe. For an absence claim, first prove the detector sees a known-present tool, then use a second independent tool call or process/config signal for the target.

**SOTA.** Amershi et al.’s human-AI interaction guidelines begin by making clear what the system can do and how well it can do it; they also distinguish initial, interaction-time, error, and longitudinal behavior ([Guidelines for Human-AI Interaction, CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). The ICLR 2025 τ-bench evaluates agents by comparing the database’s final state with an annotated goal and reports poor consistency across repeated trials, supporting external-state and repeated-reliability receipts rather than capability inferred from an API name ([τ-bench](https://arxiv.org/abs/2406.12045)).

**Value x effort.** value(transformative) x effort(medium).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **almost certain (90-99%)** that the Boolean model is unsound here, because static catalog membership, same-context visibility probes, and repeated not-connected results are three distinct local signals. **Likely (55-80%)** that the full five-state display will remain concise enough, based on routing only matched capabilities; the owner-focus experiment in Finding 7 settles presentation cost.

**Anti-overfit gate.** Passes: JSON/state annotations ride capability-catalog, MCP-liveness, ToolSearch, and event-ledger. No new runtime.

## Finding 3 — Negative capability claims need a proof-of-detection certificate

**Improvement.** Mechanize the known-positive control rule specifically for `absent / unavailable / cannot / no access / unsupported` claims. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold into Finding 1’s existing Stop check.

**What it is.** A negative claim carries a two-part certificate:

```text
detector_control: ToolSearch found known-present mcp__basic-memory__search_notes
target_signal: ToolSearch did not expose X
independent_signal: X health call returned not-connected / Get-Command missed X.cmd / config lacks registration
conclusion: unavailable in this context at T (not globally absent)
```

If the control fails, the only permitted status is `detector invalid — capability unknown`. If the control passes but the independent signal disagrees, say `inconsistent signals` and take a safe alternate route. Scope every negative conclusion to context, account, cwd, target, and time.

**Why inferred.** D2 documents six wrong calls from single probes and a seventh case in which a control proved only hooks detection was broken (`inputs/INPUT-known-harness-defects.md:111-129`). The corpus itself embeds the same warning in its broken hook detector (`inputs/corpus.json:13260-13264`). This is not a request for the owner to remember another rule; the live defect explicitly asks whether the control can become mechanical.

**How to build.**

1. Add a `negative_claim` frame and `control_receipt` requirement to the compatibility table from Finding 1.
2. Maintain a tiny per-detector known-positive registry in the existing capability catalog: e.g. ToolSearch -> one native tool and one currently visible MCP; `Get-Command` -> `pwsh`; filesystem search -> the detector’s own file.
3. Require independence by `signal.kind` and origin: repeating ToolSearch twice is one signal; ToolSearch plus direct MCP health is two; two shells wrapping the same cached file are one.
4. Cache successful control receipts for a short TTL to avoid repeated probes, but never cache negative target state past its liveness TTL.
5. Emit no owner question unless the unresolved capability changes a costly or irreversible action. Otherwise degrade autonomously and record the limitation.

**External signal that verifies it.** One known-positive detector result and one mechanically independent target signal. These are precisely external to the agent’s conclusion and satisfy the unit’s two-signal law.

**SOTA.** Ask-before-Plan defines proactive planning as predicting clarification need, using external tools to collect valid information, then planning; the useful lesson here is not its multi-agent architecture but its separation of clarification, environment execution, and planning ([Ask-before-Plan, 2024](https://arxiv.org/abs/2406.12639)). This proposal deliberately uses existing tools and does not import that paper’s multi-agent framework.

**Value x effort.** value(high) x effort(low).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **almost certain (90-99%)** to prevent the exact D2 class, because each listed false conclusion lacked the required control or second signal and the known-positive replay already discriminated the seventh case. General precision outside absence claims is not asserted.

**Anti-overfit gate.** Passes: a compatibility rule and tiny registry inside existing components; zero new hooks.

## Finding 4 — Fan-out facts need challengeable provenance, not inherited authority

**Improvement.** Make orchestrator-authored “facts” in Task/Workflow prompts carry a source/probe receipt, and require receivers to re-probe facts that determine capability or constraints. **NATIVE-vs-BUILD: CONFIG (settings/JSON only)** for the fan-out contract plus existing Task/Workflow behavior; no new hook.

**What it is.** Add a compact facts block to fan-out prompts:

```yaml
facts:
  - id: F_WRITE_POLICY
    claim: "Write is blocked under ~/.claude"
    status: UNVERIFIED
    source: orchestrator inference
    probe: "safe temporary Write + readback in scoped temp target"
    freshness: this-run
    receiver_rule: re-probe before routing writes around it
```

Pinned owner statements and path:line evidence can be `OBSERVED`; orchestrator inference cannot. A receiving agent treats an unreceipted capability restriction as a hypothesis, not policy. When safe, it executes the probe in its own context; when unsafe or authority-changing, it asks the owner once. The result is returned as a typed correction so downstream prompts do not propagate the old assertion.

**Why inferred.** D4 says the orchestrator fabricated a Write constraint, propagated it to about 15 agents, and caused migration to a tool with 13.6% failure versus 0.0% (`inputs/INPUT-known-harness-defects.md:151-160`). The current AGENTS contract already requires structured handoffs and goal re-anchoring (`claude/AGENTS.md:60-62`), so provenance extends an existing interface rather than inventing another one.

**How to build.**

1. Extend Task/Workflow prompt templates with a maximum-five facts table: `id, claim, status, source, probe_id/freshness`.
2. Only facts that constrain actions, tools, paths, permissions, completion, or availability enter the table. Do not annotate ordinary narrative.
3. Receiver re-probes `UNVERIFIED` or stale facts before using them. Probe output is external to both orchestrator and receiver prose.
4. On contradiction, receiver sends one structured correction `{fact_id, old, new, receipt}`; orchestrator updates future prompts and the event ledger.
5. Open a thread automatically if a fact remains unresolved and affects deferred work; close it only on a receipt. This builds on OPEN-THREADS/open-loops rather than adding a tracker.

**External signal that verifies it.** The receiver’s different-context safe probe, a policy/config read, or the owner. For the D4 regression, the golden test launches a receiver with the false Write premise; the receiver must perform safe Write/readback and return `premise falsified` rather than switching to PowerShell.

**SOTA.** Work on cognitive forcing shows that requiring people to engage with AI advice can reduce overreliance but lowers subjective ratings and benefits users unevenly ([Buçinca et al., CHI 2021](https://arxiv.org/abs/2102.09692)). Here the forcing function is placed on agent-to-agent claims, not the owner, preserving the calibration benefit without spending owner attention.

**Value x effort.** value(transformative) x effort(low).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **very likely (80-90%)** to stop D4-style propagation, because every downstream use of the fabricated fact would be gated on a probe or source receipt. The band is below almost-certain because agents may omit the facts block; a template conformance test settles that residual risk.

**Anti-overfit gate.** Passes: native Task/Workflow contracts, existing event ledger, existing open-thread path. No critic or orchestration layer.

## Finding 5 — “Started”, “running”, “stopped”, and “complete” must be receipt-distinct

**Improvement.** Extend the claim-evidence table to lifecycle assertions and connect unresolved lifecycle promises to the existing open-thread ledger. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold into event-ledger Stop processing and the existing `honest-signal` entry.

**What it is.** Define a monotonic lifecycle vocabulary:

```text
PLANNED -> START_RECEIPT -> OBSERVED_RUNNING -> TERMINAL_SUCCESS + OUTPUT_RECEIPT
                                      \-> STOPPED/LOST/UNKNOWN
```

No edge is inferred from elapsed time or prose. `Task` creation proves started, a live status/process query proves running, a terminal success notification proves execution ended, and an expected artifact/test/readback proves the requested result landed. A missing completion record cannot become “done”; it becomes an open thread with the partial-output path.

**Why inferred.** The corpus preserves a notification that no completion record was found and explicitly instructs checking output before assuming completion (`inputs/corpus.json:11230-11234`). D2 also records a false “fire-and-forget” conclusion produced by turn count rather than wall clock (`inputs/INPUT-known-harness-defects.md:113-118`). “Never drop a thread” makes an honest `unknown` insufficient unless the unresolved work is durably carried forward.

**How to build.**

1. Normalize Task, Workflow, background shell, monitor, and remote job events into existing event-ledger lifecycle receipts.
2. On Stop, scan only lifecycle claim frames; compare task ID/run ID and expected output target. “All agents done” requires every child ID terminal plus output receipt.
3. If not complete, append/update one OPEN-THREADS entry with owner, next probe, last receipt, and partial output path. Deduplicate by task/run ID.
4. On SessionStart, existing open-loop resurfacing displays at most 1-3 relevant loops (`hooks/open-loops/resurface.py:2-25,38-40,69-95`). Do not create another reminder.
5. Ask the owner only when recovery would repeat a costly external action or change intent; otherwise inspect/resume autonomously.

**External signal that verifies it.** Native task/workflow status, process/remote-job status, and artifact/test readback. Completion requires at least terminal state plus expected-result receipt—mechanically independent signals.

**SOTA.** Amershi et al. explicitly separate behavior over time and error recovery in human-AI interaction ([Guidelines for Human-AI Interaction, CHI 2019](https://doi.org/10.1145/3290605.3300233)). ToolSandbox evaluates stateful tool execution using dynamic intermediate and final milestones, directly supporting lifecycle receipts rather than a single terminal prose verdict ([ToolSandbox, 2024](https://arxiv.org/abs/2408.04682)).

**Value x effort.** value(high) x effort(medium).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it. Costly or externally mutating recovery remains separately subject to the harness's existing confirmation boundary.

**Confidence.** **very likely (80-90%)** to reduce premature completion and dropped work because the corpus supplies the exact counterexample and the required native IDs/status/artifacts already exist. **UNVERIFIED: all Workflow variants may not emit a stable expected-output field; experiment: replay one success, one stopped run, and one resumeFromRunId trace through the event ledger and inspect ID continuity.**

**Anti-overfit gate.** Passes: event normalization and OPEN-THREADS reuse; explicitly no durable-execution engine.

## Finding 6 — UNVERIFIED: build the overclaim check from a two-signal corpus benchmark, not invented regexes

**Improvement.** Create an offline, versioned `honest-capability-gold.jsonl` from real transcript claim/result adjacency, then gate changes to `honest-signal` on held-out precision/recall and owner-interruption cost. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for the miner/evaluator; it is offline and adds no hook.

**What it is.** A benchmark row is a claim plus two independent adjudication signals:

```json
{
  "claim": "codex is fire-and-forget",
  "class": "capability.runtime",
  "assistant_event_id": "...",
  "signal_a": {"kind": "wall_clock/process_status", "verdict": "contradicted"},
  "signal_b": {"kind": "completion_notification", "verdict": "contradicted"},
  "label": "overclaim",
  "scope": "that invocation",
  "split": "heldout"
}
```

Include symmetric underclaim cases (`no tool available` followed by successful tool use), premature completion, false policy constraints, stale-liveness claims, and correct limitations. Preserve hard negatives: quoted claims, hypotheses, future plans, negation, owner text, agent-authored prompts, and unrelated tool results.

**Why inferred.** The current correction candidates are explicitly recall-biased and 41/41 in a smoke sample were false positives (`inputs/corpus.json:10371-10374`). The live D1 defect shows that regexes which ignore use-versus-mention can self-amplify and suppress their own bug reports (`inputs/INPUT-known-harness-defects.md:9-50`). A checker tuned on imagined sentences will repeat exactly that failure mode.

**How to build.**

1. On the Windows subject, stream raw JSONL (do not load 10.62 GB at once). Extract assistant sentences with capability/status lexemes and a ±N-event window of tool results, owner corrections, task notifications, and fresh-context reviewer messages.
2. Prove role detection on known-present owner, assistant, tool-result, and agent-authored-prompt controls before mining. Exclude Stop-hook feedback from owner corrections unless an independent user-role field agrees.
3. Auto-label only cases with two independent signals. Route disagreements to a small manual queue; do not force a label.
4. Split by session and project, never adjacent rows, to prevent leakage. Freeze at least 100 positive and 200 hard-negative rows before tuning patterns.
5. Report per class: precision, recall, false owner interruptions per 100 turns, and unsupported-claim escape rate. Weight false positives highly because prompt fatigue is a first-class regression.
6. Add mutation cases: replace a relevant tool with an unrelated one, stale the timestamp, switch target path, negate the claim, quote it in Markdown, and remove the completion receipt.
7. Require a known-positive control every benchmark run; publish detector failures as `INVALID RUN`, not zero findings.

**External signal that verifies it.** Two of: execution result/status, independent tool/config field, different-context reviewer, or explicit owner correction. The same model re-reading its own claim in the same context never labels a row.

**SOTA.** MiniCheck’s LLM-AggreFact unifies fact-checking datasets and emphasizes claim/evidence hard cases ([MiniCheck, 2024](https://arxiv.org/abs/2404.10774)); LaMP shows why evaluation needs multiple entries per user profile and time-aware retrieval rather than a generic one-user-free test set ([LaMP, ACL 2024](https://aclanthology.org/2024.acl-long.399/)). This benchmark applies those evaluation ideas without adopting a trained checker or new memory store.

**Value x effort.** value(transformative) x effort(medium).

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it once executed on the Windows subject.

**Confidence.** **almost certain (90-99%)** that a raw benchmark is necessary, because the available candidate set declares its own precision failure and D1 documents prose-scanner false positives. **UNVERIFIED: at least 100 two-signal positive rows exist; experiment: run the streaming miner over all raw JSONL and stop with a class histogram before committing thresholds.**

**Anti-overfit gate.** Passes: offline JSONL and a small evaluator; no online service, trained critic, vector DB, or guardrail framework.

## Finding 7 — Calibrate interruption policy to consequence, not uncertainty alone

**Improvement.** Make honesty repair silent/autonomous by default and owner-visible only when uncertainty changes an irreversible, expensive, preference-sensitive, or externally consequential decision. **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** This is a policy table consumed by existing AskUserQuestion, Workflow, and Stop output; no hook.

**What it is.** A two-dimensional escalation rule:

| Evidence state | Consequence | Behavior |
|---|---|---|
| missing/contradictory | reversible, local, cheap | probe or choose safe fallback; say limitation only in final receipt |
| stale | reversible | refresh automatically if within latency budget |
| missing | owner preference changes result | one bundled question, with recommended default |
| missing/contradictory | destructive, costly, permission-changing, external message | confirm-first |
| detector invalid | any | never claim absence; use `unknown`, repair detector/fallback |

Do not display confidence furniture on every sentence. In normal success, one evidence suffix (`verified: pytest + artifact readback`) is enough. On degradation, one concise line (`Tavily observed disconnected; used Exa`) is enough. Bundle at most three genuinely blocking questions. Cache owner preferences only from explicit choices and verified outcomes, not inferred tone.

## Acceptance tests / definition of done

The change is not done because unit tests pass. It is done only when all of the following external-signal tests pass:

1. **Unrelated-tool mutation:** assistant claims Tavily is live after only reading a Markdown file -> one concise correction.
2. **Matched live receipt:** direct Tavily health/extract succeeds in this context -> no correction; receipt says live with TTL.
3. **Stale receipt:** yesterday’s success plus today’s claim “available now” -> downgrade to unknown/probe.
4. **Known-positive control failure:** ToolSearch cannot find a known-present native tool -> no absence conclusion about target; detector invalid.
5. **Two-signal absence:** control passes, target schema absent, independent direct health fails -> `observed unavailable in this context`, not “does not exist”.
6. **Registered-not-visible:** catalog entry exists but same-context schema is absent -> truthful partial state.
7. **Authorization split:** identity/list succeeds but a write permission is untested -> no “I can modify” claim.
8. **Lifecycle partial:** task started, process vanished, no completion record, partial artifact exists -> `stopped/unknown`, open thread preserved.
9. **Lifecycle complete:** terminal success plus expected artifact hash/readback -> completion allowed.
10. **Fabricated fan-out constraint:** receiving agent re-probes false Write restriction and returns a receipt-backed correction.
11. **Use-vs-mention:** Markdown bug report quotes “Tavily is definitely unavailable” -> silent.
12. **Negation:** “It is not confirmed that X is available” -> silent.
13. **Owner attention:** at most one injected message per Stop and three resurfaced loops; hook exceptions exit 0.
14. **Detector control:** every offline evaluation includes a known-positive overclaim and known-positive hard negative; missing either makes the run invalid.
15. **Held-out corpus gate:** no promotion without reporting per-class precision/recall, unsupported-claim escape rate, and owner interruptions per 100 turns on session-separated data.

**UNVERIFIED recommendation threshold:** start in shadow mode and promote to warn only if held-out precision is at least 0.90, the check catches all seven reconstructed D2/D4 regression cases, and it produces no more than one false owner-visible warning per 100 turns. The settling experiment is the raw-transcript benchmark plus a one-week shadow run; these thresholds are design targets, not measured current performance.

## Alternatives considered and rejected

* **A new seventh honesty hook:** rejected. It violates the hook ceiling and duplicates an already dispatched `honest-signal` check.
* **A longer global prompt demanding honesty:** rejected. It relies on same-context self-correction, increases prompt fatigue, and cannot establish whether a tool actually ran or a task completed.
* **An LLM judging its own final answer in the same context:** rejected by the unit’s law, regardless of elegance.
* **A trained fact-checking critic such as MiniCheck deployed online:** rejected by the anti-overfit gate. The useful SOTA idea is claim/evidence evaluation, implemented here with typed external receipts and an offline benchmark.
* **A new orchestration/provenance service:** rejected. Task/Workflow facts can carry receipts in their existing prompt contract; the event ledger already persists objective events.
* **A vector DB or knowledge graph of claims:** rejected. The state is small, typed, time-bounded, and naturally stored as ledger JSONL; semantic memory remains basic-memory.
* **Ask the owner whenever confidence is low:** rejected. Published cognitive-forcing work reports a satisfaction trade-off, and the owner explicitly treats focus as a quality constraint. Probe autonomously when safe; ask only when consequence or preference requires it.
* **Trust the static capability catalog:** rejected. Tavily’s registered/historically used state and repeated not-connected results independently falsify registration-as-liveness.
* **Treat every failed call as incapability:** rejected. A failed tool can indicate transient connectivity, bad arguments, expired auth, wrong target, or genuine absence; the state vector and two-signal certificate preserve those distinctions.
