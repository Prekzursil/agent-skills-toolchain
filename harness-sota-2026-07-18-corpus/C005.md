## Executive verdict

The production vault that this unit was assigned to audit was **not included in the Linux bundle**. The brief says the Windows vault contains 319 files / 3.1 MB, but the unpacked subject contains only nine implementation/test files under `claude/hooks/event-ledger` and contains zero production `events.jsonl` and zero production `state.json` files. Consequently, I cannot truthfully inventory the 319 files, count their event kinds, test their JSON integrity, reconstruct their time range, or grep them for a known-fired hook. This is a hard evidence boundary, not an empty-vault finding.

Two mechanically independent signals establish the bundle omission:

1. A typed filesystem inventory found exactly the nine source/test files and `production_events_jsonl_count=0`, `production_state_json_count=0`. The same detector found the known-present `claude/settings.json` (`known_present_settings_count=1`), which validates that it can find an expected file in the bundle.
2. The bundle's supplied file catalog is a list of batch-unit descriptions, not a vault manifest; its event-ledger entry merely repeats the Windows assignment. A content search finds source references and prior audit claims, but no serialized production event rows. In particular, the bundle-wide `find` result contains no `events.jsonl` at all.

This unit therefore gives two different outputs:

* a **verified implementation and live-wiring audit** from the unpacked subject, plus isolated execution tests; and
* a clearly separated **GAPS / required Windows experiment** for the missing production population.

On the narrow question “can `~/.claude/event-ledger` answer ‘did this hook fire?’”, the verified answer is **no, not in general**. Its base event schema records event kind and arbitrary payload fields, not a required hook identity, hook event, invocation ID, start/completion pair, matcher/config revision, duration, exit status, timeout, or emitted action. A positive row can sometimes prove that a particular writer reached its append call; an absent row cannot distinguish “hook did not run” from “matcher did not select it”, “hook returned early”, “append failed and was swallowed”, “host killed it”, “writer is no longer registered”, or “the row is in another shard.” This is **breaking for hook-firing telemetry**, while the same store can still be useful as a semantic continuity log.

The best replacement for custom “did it fire?” inference is now a native Claude Code facility: current official monitoring documentation describes `hook_registered`, `hook_execution_start`, and `hook_execution_complete` events, including hook event/name, matching-hook count, completion counts, blocking/errors/cancellation, duration, session correlation, and sequence. That native surface did not exist in the legacy ledger design and directly models the question being asked. It should be validated locally before any custom receipt layer is built.

## 2. Intended physical model

### 2.1 Paths and project identity

The legacy root is `EVENT_LEDGER_ROOT` when set, otherwise `~/.claude/event-ledger` (`claude/hooks/event-ledger/ledger.py:17-24`). Each project maps to a directory and stores:

* `events.jsonl`, one JSON object per line (`ledger.py:10-12,105-116`);
* `state.json`, a mutable projection (`ledger.py:115-130`);
* `.append.lock`, the one-byte OS-lock file used around append and projection update (`ledger.py:133-192,230-287`);
* possibly `captured.json`, written by the old Stop hook after it mirrors milestones into `.beads/knowledge/decisions.jsonl` (`stop-hook.py:40-73`);
* possibly root-level `oats-centroids.json`, written by the OATS scaffold (`oats.py:54-60,92-108,192-243`); and
* possibly `stopfailures.log` from a separate fallback logger, as indicated by `claude/hooks/stopfailure-notify/notify.py:26-64`.

The actual distribution of those file types among the 319 production files is **UNVERIFIED — the settling experiment is the read-only Windows inventory in §9**.

Project slugging prefers the shared `projid` resolver, retains a pre-existing cwd-hash shard until migration, and otherwise falls back to basename plus the first eight hex characters of SHA-256 over the path (`ledger.py:40-102`). That continuity rule deliberately preserves legacy shards, but it also means one repository can have more than one historical directory until migration.

### 2.2 Append mechanics

`append()` acquires a per-shard OS lock, accepts one of seven kinds, recovers the next sequence from both projection and the last valid JSONL tail, appends/flushed the event first, then atomically replaces the projection (`ledger.py:194-287`). It does not call `os.fsync()` after the event flush, whereas the newer shared ledger does (`agents/harness/ledger.py:868-879`). The legacy code therefore orders event before projection but does not itself demonstrate power-loss durability.

The implementation's own description says malformed fields never raise, but lock acquisition explicitly raises `TimeoutError` (`ledger.py:230-241`). Callers often swallow that error. This matters for telemetry: no row is not evidence that the hook never began.

### 2.3 Isolated execution verification

I copied the nine files to `/tmp/c005-ledger-eu1wwR` and ran all three self-contained test programs with `PYTHONDONTWRITEBYTECODE=1`. This did not touch the subject or production data. Results:

```text

test_concurrent_append.py: SUCCESS:event-ledger-concurrency 24/24 unique monotonic appends + stale-projection recovery
test_prune_oats.py: PASS (0 failures)
```

The tests verify monotonic append/replay, projection, milestone supersession, project isolation, non-serializable field fallback, Stop re-entry suppression, SessionStart injection, 24-process serialization, stale-projection recovery, synthetic prune ranking, and OATS scaffold math (`test_ledger.py:25-97`; `test_concurrent_append.py:18-101`; `test_prune_oats.py:43-205`). They do **not** verify Windows locking, the production 319-file population, active host wiring, host timeouts, or whether emitted context reached a model.

Health verdict for physical mechanics: **healthy in the isolated Linux tests, production status UNVERIFIED — the settling experiment is to run the same tests against a temporary Windows `EVENT_LEDGER_ROOT`, then separately perform the read-only population audit.**

## 3. What the implementation can record

### 3.1 Base envelope and allowed kinds

Every legacy event has only three mandatory fields created by `append()`:

```text
seq: integer
ts: local wall-clock string, second precision, no timezone suffix
kind: turn | decision | failure | goal | milestone | selection | note
```

The envelope is constructed at `ledger.py:243-257`. Every caller-provided key/value is admitted if JSON-serializable; otherwise `repr(value)` is stored. There is no schema version, reserved-key protection, redaction layer, required provenance, event hash, predecessor hash, or event ID requirement in this writer. Because caller fields are copied after the base envelope, a caller can overwrite `seq`, `ts`, or `kind` (`ledger.py:250-257`). The isolated tests do not cover reserved-key override.

The timestamp is produced by `time.strftime("%Y-%m-%dT%H:%M:%S")` (`ledger.py:250-251`). The newer shared ledger uses timezone-aware UTC and merges legacy and shared rows by timestamp/sequence (`agents/harness/ledger.py:850-907`), while interpreting a timezone-free legacy timestamp as UTC for one comparison path (`agents/harness/ledger.py:944-968`). Prior audit B15 claims this causes a roughly three-hour skew on the UTC+03 owner host (`inputs/audit-findings/B15.md:41-47`); that host/timezone observation is not reproducible on this UTC Linux node, so it remains a prior claim rather than this unit's measurement.

### 3.2 Objective `turn` rows

The old Stop writer attempts to append:

```text
kind=turn
cwd=<full cwd>
head=<short git HEAD or null>
branch=<branch or null>
dirty_files=<porcelain line count or null>
session=<first 12 characters of session_id>
```

This is exact at `stop-hook.py:76-94`. The writer does not record assistant content, user goal, tool call, hook event name, hook command, start time, completion status, host timeout, or whether its output was consumed. It also skips all writing when `stop_hook_active` is true (`stop-hook.py:81-83`).

`turn` is not exclusive to this hook: the generic CLI permits `--kind turn`, and any importer can call `ledger.append(..., "turn", ...)` (`note.py:25-42`; `ledger.py:230-257`). Therefore a `turn` row with the exact Stop field shape is evidence that a compatible writer appended; it is not cryptographic or schema-enforced proof that Claude Code invoked `stop-hook.py`.

The `prune-report.py` documentation says Stop writes a `tool` field, then ranks that field (`prune-report.py:1-11,65-90`). The actual Stop append has no `tool` or `skill` field (`stop-hook.py:84-91`). Therefore ordinary Stop rows cannot feed that capability ranking. Synthetic tests pass only because they seed `tool=` manually (`test_prune_oats.py:35-41`). This is **breaking for the prune report's advertised production data path**, though not for ledger append/replay.

### 3.3 Semantic annotations

`note.py` lets an agent or human append any allowed kind with `text`; it optionally adds `preconditions` and integer `supersedes_failures` (`note.py:25-42`). The projection stores:

* latest goal text;
* latest non-null turn HEAD;
* up to 25 open failures, keeping sequence, text, and preconditions; and
* up to 50 path aliases (`ledger.py:263-284`).

A milestone carrying `supersedes_failures` removes those failure sequences from the mutable projection but does not delete the authoritative historical failure row (`ledger.py:276-284`). This is appropriate event-sourcing behavior.

These annotations preserve “why” only when an agent explicitly calls the CLI. They contain no required session/provider/worker/scope fields. In a shared project with concurrent units, a decision or failure cannot be reliably attributed to one session from the base schema.

### 3.4 Selection rows

The separate selection emitter writes a richer `selection.v1` row after correlating a hook payload to a real user prompt. Its fields are `schema`, `event_id`, bounded/redacted `query`, `query_hash`, `query_source`, `query_evidence`, `chosen_tool`, boolean `success`, `session_hash`, and `tool_use_id` (`selection-events/emitter.py:577-606`). It maps `PostToolUse` to `success=true` and `PostToolUseFailure` to `false` (`emitter.py:609-645`).

This is the one legacy row shape that can strongly support a writer-specific statement: a valid `selection.v1` event with its correlated tool-use ID proves that the emitter reached a successful append for a success/failure hook payload. It still does not prove what Claude did with any hook output, and an absent row is ambiguous because correlation, claim, append, and top-level errors all fail open (`emitter.py:577-645`).

Current live settings register the emitter only at UserPromptSubmit and PostToolUseFailure (`claude/settings.json:117-137,356-378`), although its positive path requires PostToolUse (`emitter.py:4-15,633-640`). Thus the present configuration can cache prompts and record some failures, but cannot record successful selections. OATS `rank()` remains a pass-through and its update stores raw grouped queries rather than embeddings (`oats.py:192-262`). Health verdict: **degrading telemetry skew plus no ranking effect**.

### 3.5 Session-end notes and other consumers

`session-end/end.py` can append `kind=note`, `reason`, truncated `session`, and `hook="session-end"`, plus a second note for unflushed memory spools (`session-end/end.py:79-122`). That is writer provenance embedded by one caller, not a ledger-wide contract. No active registration for this Python writer appears in the supplied live settings or local manifest; a separate plugin-style `hooks/hooks.json` contains a different Node SessionEnd command (`claude/hooks/hooks.json:283-296`).

Several local components read the legacy store (loop recovery, open-loops, capability cards, goal reinjection, subagent context), while the newer cross-provider `EventLedger` explicitly bridges it during replay/state projection (`agents/harness/ledger.py:468-480,882-941,1217-1280`). This makes the legacy vault still behaviorally relevant even after its automatic Stop/SessionStart writers were removed from live registration.

## 5. Can it answer “did this hook fire?”

### 5.1 Evidence ladder

| Question | Legacy ledger answer | Reason |
|---|---|---|
| Did some compatible writer append this row? | Yes, for a valid row. | JSONL existence is direct evidence of an append; sequence/projection mechanics are verified in isolation. |
| Did old `stop-hook.py` append a turn? | Often inferable from the exact field shape, not guaranteed. | The writer shape is known, but `turn` is not reserved and the CLI/API can create it. |
| Did the selection emitter complete its append? | Strongly supportable for a valid `selection.v1` row. | Its schema/event fields are writer-specific (`emitter.py:577-606`). |
| Did a named arbitrary hook such as `codex-monitor-autolaunch` begin? | No. | There is no general hook identity/start schema and no reference from that hook to this ledger. |
| Did a hook finish, time out, error, block, inject, or get cancelled? | No in general. | Those outcome fields are absent from the base contract. |
| Did the host accept/deliver the hook's output? | No. | A hook-owned append occurs inside the process and cannot attest to subsequent host processing. |
| If no row exists, did the hook not fire? | No. | Fail-open writers, matchers, early returns, host kills, lock failures, stale wiring, and shard splits are observationally equivalent. |

### 5.2 The known-positive proposed by defect D3

The defect report proposed grepping for `codex-monitor-autolaunch` (`INPUT-known-harness-defects.md:143-146`). Static source settles the interpretation of that experiment before the missing-vault scan:

* the hook is registered for `mcp__codex__codex` at `claude/settings.json:271-279`;
* no production code in `codex-monitor-autolaunch/check.py` writes this legacy ledger; and
* a bounded search across event-ledger source, selection emitter, live settings, and local manifest finds the name only in its registration.

Therefore a zero grep result in the vault would **not** be evidence that this hook did not fire; the ledger has no designed telemetry path for it. A positive string might be an annotation mentioning the hook rather than a host invocation. The correct known-positive control must target a writer that is designed to emit a uniquely shaped receipt, or use host-native telemetry.

### 5.3 Severity

* **Breaking for global hook auditability:** the store cannot answer the general question its hook-audit consumer needs.
* **Degrading for continuity:** two write stores, stale legacy shards, project-global annotations, timezone-free timestamps, and current removal of the old automatic writers can make replay incomplete or misordered. The newer shared bridge remains active (`agents/harness/ledger.py:882-941`).
* **Healthy in a narrower role:** explicit semantic decisions/failures/milestones and append mechanics are useful when interpreted as annotations, not authenticated host telemetry.

## 6. Frontier: native hook lifecycle telemetry

Current official Claude Code monitoring documentation describes native OpenTelemetry log events that map directly to this audit:

* `claude_code.hook_registered`, once per configured hook at session start, with event/type/source and optional matcher;
* `claude_code.hook_execution_start`, with event/name, number of matching hooks, source, and session/event sequence; and
* `claude_code.hook_execution_complete`, with success, block, non-blocking-error, cancellation counts and total duration.

The same documentation describes a hook span with `hook_event`, `hook_name`, counts, definitions, and duration under detailed beta tracing. See the primary source: https://code.claude.com/docs/en/monitoring-usage . The hook input contract also natively provides `session_id`, `transcript_path`, `cwd`, and `hook_event_name`: https://code.claude.com/docs/en/hooks .

This is materially better evidence than asking each hook to log itself: host-owned start/complete telemetry can observe cancellation and non-completion that an in-hook final write cannot. It also distinguishes registered, matched/started, and completed—three states the legacy ledger collapses.

Native event availability in the owner's installed interactive build and an acceptable local persistence path are **UNVERIFIED — the settling experiment is Recommendation 1 below**. The official documentation notes extra gating for detailed hook spans in interactive sessions, but presents the registration/start/complete log events in the normal monitoring event catalog.

### Recommendation 2 — add bounded per-module receipts to the existing shared dispatcher only if native retention fails

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

It must never store raw prompts, hook input/output, commands, or secrets. Start-without-finish must be interpreted as “incomplete/host termination possible,” never success.

Confidence: **likely (55-80%)** that a bounded implementation fits under roughly 200 lines, because the dispatcher already times modules and appends a terminal record; uncertainty is the exact current module-loop seams and concurrency locking. A temporary-root test with parallel provider events and forced timeout/error/kill settles the size and correctness.

Limit: this fallback proves only modules running behind the shared dispatcher. Standalone direct hooks remain outside its observation boundary. Do not wrap them in a third runtime; port only independently valuable ones onto the shared bus, then retire duplicates in the owning hook-consolidation unit.

### Recommendation 5 — define an explicit evidence contract for “did it fire?”

**CONFIG (settings/JSON only)** for the schema/policy declaration once either Recommendation 1 or 2 supplies events.

Use four non-collapsible states:

```text
REGISTERED  host loaded the hook definition/config revision
MATCHED     host selected at least one hook for the lifecycle opportunity
STARTED     execution began, with invocation/session/event identity
COMPLETED   terminal outcome and duration were recorded
```

Never translate missing evidence into `false`. Report `NO-OPPORTUNITY`, `NOT-MATCHED`, `STARTED-NO-FINISH`, or `UNKNOWN/TELEMETRY-GAP` as appropriate. “Injected” or “blocked” additionally requires the host-owned outcome, not a hook's self-report. The native event model in Recommendation 1 already supplies the first four distinctions at group granularity.

Confidence: **almost certain (90-99%)** that this eliminates the specific false inference in defect D3, because it makes detector health and incomplete execution explicit and is directly aligned with the native registered/start/complete event sequence. It does not by itself measure whether model behavior improved.

Anti-overfit gate: passes. This is a small contract over an existing event bus, not a new framework.

## 8. Alternatives considered and rejected

### Keep using `turn` rows as a firing proxy

Rejected. The automatic writer is no longer registered in either supplied live plane; the kind is not exclusive; errors are swallowed; and the row lacks hook/outcome fields. This would recreate the exact single-detector mistake in known defect D2.

### Add `hook=<name>` at the end of every hook

Rejected as the primary mechanism. A final self-write cannot observe host cancellation, timeout after output, failure before the write, or whether output reached Claude. It also requires touching every hook and creates inconsistent adoption. Host-owned native start/complete events are the stronger boundary.

### Expand the legacy ledger into a universal observability database

Rejected by the anti-overfit gate. It would duplicate the native telemetry surface, preserve the Claude-only store, and compete with the existing cross-provider ledger. No vector DB, KG, durable-execution runtime, trained critic, SaaS, or guardrail framework is justified here.

### Deploy a new local OpenTelemetry collector solely for hooks

Rejected for this unit. It is a new daemon/service and is unnecessary until the console-export experiment proves native event utility but also proves that no existing approved sink can retain it. Even then, that decision requires BUILD-LARGE justification from the architecture owner, not an implicit expansion by C005.
