## Executive result

I found **three genuine runtime conflicts** in which a behavioral rule is stated both in the prompt contract and in a live hook, but the two authorities implement different outcomes:

1. The contract permits a force-push to `main`/`master` after explicit user approval; the live `no-force-push` hook still blocks the approved command unless a separate environment-variable bypass is added.
2. The contract places an explicit in-session user instruction above lower-layer governance and permits hard blocking only for danger; the live Ulysses hook can block an ordinary direct edit of its own JSON policy file despite an explicit user instruction, until a separate override command is logged.
3. The contract requires non-dangerous routing/readiness guidance to inject context and continue; the live RE auto-launch hook denies the MCP call while a backend is starting, unavailable, manual-only, or held back for RAM.

For all three, the hook wins on the affected call. This is not an inference from comments: the files are wired in `settings.json`, direct-process tests exercised the relevant decision paths, and Claude Code's official hook reference says a `PreToolUse` exit 2 or `permissionDecision: "deny"` cancels the tool call before normal permission evaluation.

The strongest conclusion is **almost certain (90-99%)**, supported by (1) exact live-wiring entries, (2) exact hook branches, (3) direct subprocess/acceptance-test results, and (4) the official runtime protocol. The residual 1-10% is the remote-snapshot limitation: the actual Windows process environment and a live `--debug-file` trace were unavailable on this Linux node. The Windows-instance firing status is therefore **UNVERIFIED; the settling experiment is to invoke one fixture per finding in Claude Code on Windows with `claude --debug-file <path>` and inspect the matched-hook decision and exit code**.

No replacement runtime is justified. Each fix is a small change on the existing native hook bus. None introduces a second orchestrator, vector database/knowledge graph, durable-execution runtime, trained critic, observability SaaS, or guardrail framework.

### Concrete collision

Claude calls a read-only Ghidra/IDA/Binary Ninja MCP inspection tool while its local backend is cold-starting, down, or held back to avoid OOM. This is **almost certain (90-99%)** to resolve the authority conflict because the shipped test already proves `deny_while_starting=False -> inject not deny`, and all affected branches route through those two booleans. Whether users prefer that extra native tool error is **UNVERIFIED; the settling experiment is an A/B Windows fixture with a closed backend, measuring retries and user-visible noise for deny=true versus inject-only, while requiring identical successful recovery**.
