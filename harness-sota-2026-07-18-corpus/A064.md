# A064 — Coherence audit: `~/.claude/rules/rust/security.md`

## Scope and verdict

This unit audited the complete 141-line Rust security overlay at
`/local_disk0/codexwork/bundle/claude/rules/rust/security.md` (logical live path
`~/.claude/rules/rust/security.md`). The unpacked tree is the read-only subject supplied by the
remote override. I wrote only this artifact.

The rule is directionally sound, but it is not a coherent executable contract. It repeats four
always-on/common policies, uses unconditional words for checks with no defined trigger, points to
skills whose source trees were not included in this bundle, and is largely disconnected from the
registered enforcement path. The strongest confirmed defect is the secret-control split brain:

* The Rust rule says “Never hardcode” (`rust/security.md:11`).
* AGENTS.md also makes that an always-on security floor (`AGENTS.md:93-98`).
* The shared secret-literal hard block is explicitly opt-in and off by default
  (`~/.agents/harness/modules.py:84-99,748-762`), and its tests require literal secrets to be
  allowed by default (`~/.agents/harness/tests/test_modules.py:303-338`).
* The registered `per-edit-check` has tests for a write-path secret gate
  (`hooks/per-edit-check/test_secrets.py:1-6,136-151`), but the live implementation has no
  `_scan_secrets` function and routes `.rs` to an unconditional clean result
  (`hooks/per-edit-check/check.py:151-170`). A runtime import independently returned
  `runtime_has_scan_secrets=False` and `runtime_rs_dispatch=([], False)`.

Thus “never hardcode” is **UNENFORCED**, not wrong. The target behavior is appropriate; the current
heuristic enforcement was intentionally relaxed after false positives. The resolution must restore
a high-precision write-path check, not merely turn the old broad payload heuristic back on.

No collision found below is silently resolved by choosing a lower layer. AGENTS.md section 10 is
controlling: user/permission instructions rank first; the security floor ranks second and cannot be
relaxed; the cross-tool contract ranks third; project governance may only add restrictions; and
third-party skill/plugin defaults rank last (`AGENTS.md:115-131`).

## Collision register

### C1 — Security-floor duplication: secrets — REDUNDANCY

**Artifacts and exact lines**

* `~/.claude/rules/rust/security.md:11-14`: never hardcode keys/tokens/credentials, use environment
  variables, fail fast when missing, and ignore `.env`.
* `~/.claude/AGENTS.md:93-98`: never hardcode secrets; use environment variables and validate at
  startup.
* `~/.claude/rules/common/security.md:28-43`: pre-commit secret checklist; never hardcode; use an
  environment variable **or secret manager**; validate at startup; rotate exposure.

The Rust overlay repeats the security floor almost verbatim. It is slightly narrower than common
security because it mentions only environment variables, whereas common security also permits a
secret manager (`common/security.md:40-42`). This is not a permission to forbid secret managers:
AGENTS.md section 10 makes the security floor controlling, and the Rust file supplies no explicit
reason to narrow it.

**Specific resolution — NATIVE (Claude Code already does this; we just enable it):** replace
`rust/security.md:11-13` with one sentence inheriting AGENTS/common policy and retain only the Rust
API example. Keep `.env` ignore guidance as a Rust-project operational detail. This reduces context
without reducing protection. It rides native path-scoped rules and introduces no new runtime.

### C2 — Input-validation duplication with different boundary wording — REDUNDANCY

**Artifacts and exact lines**

* `~/.claude/rules/rust/security.md:47-50`: validate all user input “at system boundaries,” use
  newtypes, parse into typed structs, and reject clearly.
* `~/.claude/AGENTS.md:98`: validate all user inputs at system boundaries.
* `~/.claude/rules/common/coding-style.md:51-57`: validate all input “before processing,” prefer
  schema validation, fail clearly, and distrust external data.
* `~/.claude/rules/common/security.md:28-36`: “all user inputs validated” before commit.

“At system boundaries” is the more precise threshold; “before processing” could be read as repeated
validation inside the system. Section 10 does not resolve this same-level wording drift because both
common rule files are at the same layer. The Rust file’s typed-boundary guidance is additive and is
the valuable part.

**Specific resolution — NATIVE (Claude Code already does this; we just enable it):** make
“validate once at each trust boundary, then operate on typed values” the canonical common wording;
remove the repeated first and fourth bullets from the Rust overlay, retaining newtypes and
parse-to-type guidance. This is a rule-only consolidation on the existing native rule bus.

### C3 — SQL policy repeated in three places — REDUNDANCY

**Artifacts and exact lines**

There is no contradictory threshold. The duplication is costly because the common checklist and

**Specific resolution — NATIVE (Claude Code already does this; we just enable it):** retain only

### C4 — Error-disclosure policy duplicated, with an unresolved audience ambiguity — REDUNDANCY

**Artifacts and exact lines**

* `~/.claude/rules/rust/security.md:118-120`: do not expose paths, traces, or DB errors in API
  responses; log detail server-side; return generic client messages.
* `~/.claude/rules/common/security.md:36`: error messages must not leak sensitive data.
* `~/.claude/rules/common/coding-style.md:43-49`: provide user-friendly UI messages, log detailed
  server context, never swallow errors.
* `~/.claude/rules/rust/coding-style.md:74-100`: add detailed path context to propagated internal
  errors.

The Rust coding-style example includes `failed to read {path}` (`rust/coding-style.md:95-100`), while
the security rule forbids paths in **API responses**. These can coexist only if internal errors are
mapped at the API boundary. That mapping is shown in `rust/security.md:123-135`, so this is
redundancy/audience ambiguity rather than a contradiction.

**Specific resolution — NATIVE (Claude Code already does this; we just enable it):** state the
boundary explicitly once: preserve detailed typed/internal errors and logs, but map them to stable,
non-sensitive public error codes/messages at external response boundaries. Keep the axum mapping
example; remove repeated generic policy.

### C5 — Rule precedence can wrongly relax the security floor — CONTRADICTION

**Artifacts and exact lines**

README’s unconditional “specific overrides general” rule is incompatible with section 10 for a

**Specific resolution — NATIVE (Claude Code already does this; we just enable it):** amend

relax, AGENTS sections 6/9/9b or common security. This makes the documented rule loader semantics
coherent without another mechanism.

### C6 — Unconditional credential-file read denial is not stated by the rule and conflicts with the owner toggle — UNRULED

**Artifacts and exact lines**

## Measured corpus: is the rule followed?

### What it cannot establish

failure fingerprints and capped samples. Session rows contain filename/kind/line/size/timestamps,

The corpus also supplies no Rust-work denominator: it does not state how many `.rs` edits, Cargo
dependency changes, SQL queries, unsafe blocks, or Rust API response boundaries occurred. Without a
denominator, neither compliance nor violation rate can be calculated.

Finally, the corpus `hooks` object explicitly says its detector is broken. Per the pinned input, it
is NO DATA. I make no claim that hooks did or did not fire from that field.

### Behavior verdict

Compliance with the Rust rule is **UNVERIFIED**; the settling experiment is to re-mine raw

The rule itself falls into three remedy classes:

1. **Badly written:** dependency commands lack cadence/pass criteria (`rust/security.md:96-113`),

2. **Wrong:** no target requirement was proven substantively wrong. The only confirmed contradiction

3. **Unenforceable:** none is inherently unenforceable. Semantic SQL/input/error adequacy cannot be
   soundly regex-blocked, but it can be reviewed; comments and dependency receipts are mechanically
   checkable. The live state is **unenforced**, not intrinsically unenforceable.

## Consolidated architecture resolution and anti-overfit gate

The minimal coherent design is one short normative Rust overlay plus two existing-bus seams:

* native path-scoped prose for Rust-specific techniques and boundary semantics;
* the already registered per-edit hook for cheap, local, high-confidence checks only (secret shapes
  and missing `SAFETY` markers), warn-first;
* the existing reviewer/router and event receipt path for semantic review and heavy dependency
  commands.

All proposals above are NATIVE, CONFIG, or BUILD-SMALL and ride current rule/settings/hook/reviewer/
ledger buses. None introduces a second orchestration runtime, vector DB/KG memory, durable-execution
engine, trained critic, observability SaaS, or guardrail framework. BUILD-LARGE is unjustified here.
The design deliberately avoids running heavy Cargo commands after every edit, consistent with the
existing hook’s explicit latency rationale (`per-edit-check/check.py:13-17`).

5. **External correctness/currentness:** this coherence unit did not re-research current Rust tool or
   lint semantics. Any eventual implementation must test the actual installed Cargo/rustc versions
   and project configuration rather than assume every named command/lint is universally available.
