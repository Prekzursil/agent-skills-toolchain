# E011 — ecosystem survey: prompt/context management libraries

**Research date:** 2026-07-19 UTC  
**Scope:** prompt assets and templating, deterministic context budgeting/packing, prompt compression, prompt optimization/evaluation, agent-framework context systems, long-term memory, and prompt-management platforms. The decision target is this owner's Claude Code + Codex harness, not a greenfield LLM application.  
**Subject handling:** read-only. I wrote only this artifact. The Linux bundle at `/local_disk0/codexwork/bundle` is a snapshot of the Windows subject; no Windows path was assumed to exist on this node.

## Executive verdict

Do **not** replace the harness with a prompt framework. The best ecosystem result is a narrow three-part evolution:

1. provisionally adopt Repomix as an on-demand, skill-routed code-context packer (**UNVERIFIED** owner-specific benefit; the paired 20-task experiment in R1 settles it);
2. borrow Prompt Poet/Priompt's deterministic *priority-and-budget* primitive for context emitted by existing hooks and handoffs, without adopting either as the universal prompt runtime;
3. run a bounded Promptfoo bakeoff as an offline prompt-regression backend, never as a production orchestrator or guardrail service.

This conclusion is **very likely (80-90%)**, based on (a) the existing shared hook bus and its goal/compaction implementations at `/local_disk0/codexwork/bundle/agents/harness/modules.py:1279-1378,1458-1528`, (b) live Claude PreCompact/PostCompact wiring at `/local_disk0/codexwork/bundle/claude/settings.json:380-403`, (c) a host policy that already standardizes non-blocking context injection at `/local_disk0/codexwork/bundle/codex/AGENTS.md:48-54`, and (d) the external libraries' documented architectures cited below. The remaining 10-20% is integration uncertainty: this unit could not execute the Windows hosts or measure whether model-visible hook injection preserves the proposed envelopes.

The radical replacement candidates are high-quality *for application development*, but wrong here. LangChain/LangGraph, LlamaIndex, Haystack, Semantic Kernel, PydanticAI, DSPy, Prompt Flow, Guidance, and LMQL all want to own model calls, conversation state, control flow, or generation. Installing one under Claude Code/Codex would create the explicitly rejected second orchestration runtime. Memory products (Mem0, Letta, Zep/Graphiti) recreate the explicitly rejected vector/KG/durable memory plane. Prompt-management/observability platforms (Langfuse, LangSmith, PromptLayer, Braintrust, Helicone, Agenta) recreate the explicitly rejected observability service/SaaS.

No wholesale library adoption passes the anti-overfit gate. Two libraries pass in bounded roles (Repomix and optional Promptfoo), and two more are worth mining for a small algorithm (Prompt Poet and Priompt). That negative result is **almost certain (90-99%)** because each rejected project's own documentation explicitly describes the forbidden runtime/service it supplies; this is not an inference from popularity or code size.

## Evaluation method and honesty controls

I scored candidates on five axes:

1. **Function:** prompt asset, templating, selection/budgeting, compression, optimization/evaluation, orchestration, memory, or management/observability.
2. **Maintenance:** current release/activity where primary sources expose it. “Dormant/unmaintained” is claimed only with two mechanically different signals (for example, stale release plus stale push/activity, or stale release plus obsolete runtime constraint).
3. **Quality evidence:** documented primitives, test/release posture, adoption only as a weak corroborating signal, and fit to the measured failure modes. Star counts never decide adoption.
4. **License:** repository-declared SPDX/license. “MIT/BSD/Apache-2.0” means permissive use with preservation of copyright/license notices; Apache-2.0 additionally includes an express patent grant and NOTICE obligations where applicable. “Open core/proprietary service” means the repository and hosted product must be evaluated separately. This is an engineering survey, not legal advice.
5. **Anti-overfit gate:** a candidate counts only if it can ride the existing hook/skill/MCP bus and is not a second orchestrator, vector/KG memory plane, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Survey A — prompt assets and deterministic templating

### Prompt Poet — best directly relevant design; selective adoption

[Prompt Poet](https://github.com/character-ai/prompt-poet) represents prompts as YAML/Jinja2 parts with roles and truncation priorities. It exposes per-section token statistics, tokenizer injection, and cache-aware step truncation; its own docs explicitly state the tradeoff that stable cache boundaries can discard more tokens than strictly necessary. The latest PyPI release is 0.0.52 dated 2026-02-12, requires Python >=3.10, and declares MIT ([PyPI](https://pypi.org/project/prompt-poet/)).

Quality is **very likely (80-90%)** for the narrow primitive, based on deterministic priority semantics, section accounting, a current release, and a small 35 KB source distribution. It is only **likely (55-80%)** as a universal prompt authoring dependency here, because the harness already uses Markdown skills/rules and host-native role construction; migrating those assets would create a second representation without evidence of improved outcomes.

**Gate:** PASS only for the priority/section/truncation primitive inside a hook or skill. FAIL as the canonical prompt runtime.  
**License:** MIT; preserve the notice.  
**Verdict:** mine the design and, only if a direct dependency is simpler than a small native implementation after a spike, use the library for *generated context envelopes*, never for host conversation history.

### Priompt — excellent idea source, wrong runtime shape

[Priompt](https://github.com/anysphere/priompt) uses JSX scopes with absolute/relative priorities, reserves response tokens, supports fallback/ejection callbacks, isolates token sub-budgets, and builds sourcemaps. Its renderer chooses the minimum priority cutoff that fits a token limit. Its documentation also candidly says that adding priorities everywhere is an anti-pattern, overuse harms cacheability, the renderer can miss the mathematically perfect cutoff, and no GitHub releases are published. The repository is MIT.

The concept quality is **very likely (80-90%)**, supported by explicit budget semantics and unusually honest caveats. Direct adoption is **unlikely (20-45%)** to beat a small Python primitive here because it imports JSX/TypeScript into a Python hook bus, has no published GitHub releases, and its last API-observed push was 2025-10-15. The package is not called abandoned: the repository is not archived and that date alone is insufficient.

**Gate:** PASS as an algorithm/reference; FAIL as a new prompt runtime.  
**License:** MIT; preserve the notice.  
**Verdict:** borrow “mandatory scopes + prioritized optional scopes + reserved output budget + explicit ejection receipt.” Do not adopt JSX.

### Microsoft Prompty — promising asset format, unstable and redundant here

[Prompty](https://github.com/microsoft/prompty) is a Markdown-plus-YAML prompt asset supporting role markers, Jinja2/Mustache, scoped file references, Python/TypeScript runtimes, VS Code preview, and provider invocation. It declares MIT. The current main README explicitly says v2 is alpha and the API/file format/tooling may change; GitHub shows the latest listed release as `0.2.3-beta` from 2025-07-24, while the repository API showed a 2026-07-17 push.

Prompty is **likely (55-80%)** to become a high-quality interoperable prompt asset for application code, based on Microsoft's active development and cross-language spec. It is **unlikely (20-45%)** to add net value to this harness now because `.prompty` duplicates `SKILL.md`, commands, agent Markdown, hook messages, and provider-native model configuration. Its full runtime would also own provider invocation.

**Gate:** PASS only as a file-format experiment inside one evaluation fixture; FAIL as runtime or harness-wide migration.  
**License:** MIT.  
**Verdict:** watch, do not adopt while v2 is alpha. Revisit when v2 is stable and a concrete cross-provider prompt asset cannot be represented as an existing skill.

### Jinja2 / Mustache / Liquid — mature tools, but templating is not the bottleneck

[Jinja](https://github.com/pallets/jinja) is a mature BSD-3-Clause Python template engine with inheritance, macros, async support, compilation, and a sandbox. GitHub lists release 3.1.6 (2025-03-05). Mustache/Liquid implementations offer intentionally weaker logic and broad language portability. Jinja's general-purpose flexibility includes arbitrary functions when a host exposes them; Prompt Poet documents that capability explicitly.

Jinja quality is **almost certain (90-99%)**, based on its mature release history and widespread standalone use. Net harness benefit is **unlikely (20-45%)** because most assets are static Markdown and dynamic content already comes from Python hook code. Rendering untrusted retrieved text as a template would enlarge the injection/execution surface; retrieved text must remain data.

**Gate:** PASS as a library within an existing hook/skill, but no demonstrated need.  
**License:** Jinja BSD-3-Clause; individual Mustache/Liquid implementations vary and require a separate check.  
**Verdict:** keep direct Python formatting for tiny messages. Use Jinja only when a specific generated asset needs loops/includes and templates remain trusted code.

### PromptSource — research corpus, effectively unmaintained for this use

[PromptSource](https://github.com/bigscience-workshop/promptsource) is a dataset-prompt toolkit and P3 collection, not an agent-context manager. Two mechanically independent signals support the maintenance verdict: its latest release is 0.2.3 from 2022-07-02, and its setup still requires Python 3.7 for the authoring interface. It declares Apache-2.0.

It is **very likely (80-90%)** effectively unmaintained for modern harness integration based on those two signals. This does not claim the prompt dataset is valueless.

**Gate:** PASS technically as static data, but irrelevant to the owner's harness.  
**License:** Apache-2.0; dataset-level licenses may differ and must be checked per source.  
**Verdict:** do not adopt.

## Survey B — token counting, context selection, and packing

### Repomix — strongest ready-made adoption candidate

[Repomix](https://github.com/yamadashy/repomix) packs selected repository files to XML/Markdown/JSON/plain text, respects ignore files, reports per-file/tree token counts, can include diffs/history, scans for secrets, and offers experimental Tree-sitter signature compression. It supports `--stdout` and explicit include/ignore patterns, so it can be a pure subprocess under an existing skill rather than a daemon. Remote repository config is untrusted by default. The repository API showed a 2026-07-18 push and MIT license.

Repomix is **very likely (80-90%)** high quality for deterministic code packing based on its current activity, explicit selection controls, token accounting, security defaults, and composable CLI/library surfaces. It is **likely (55-80%)** to reduce repeated file-discovery/context assembly here, supported by the audit's same conclusion (`inputs/audit-findings/D15.md:46-50,63-66`) and Aider's independent evidence that bounded repo maps expose important symbols. The exact owner-specific gain is **UNVERIFIED**; a 20-task paired trial measuring time-to-first-relevant-file, read calls, input tokens, and task success would settle it.

**Gate:** PASS. It rides a skill/MCP subprocess, has no durable store, and does not own agent execution.  
**License:** MIT.  
**Verdict:** adopt on demand, not automatically in every session. Never pack the whole 10+ GB history or plugin tree. Quarantine packed external text as untrusted, keep source comments unless an explicit compression experiment proves safe, and retain file paths/line provenance.

### Aider repo map — best algorithmic benchmark, not a harness replacement

[Aider's repository map](https://aider.chat/docs/repomap.html) uses Tree-sitter tags and dependency-graph ranking to fit important definitions into a dynamic token budget (normally about 1k map tokens). It is part of the Apache-2.0 Aider application.

The repo-map approach is **very likely (80-90%)** high quality for code navigation, based on explicit symbol extraction, graph ranking, dynamic budgets, and Aider's long-running coding-agent use. Directly adopting Aider is **almost certainly not (1-5%)** the right integration because Aider is another coding-agent runtime and edit loop. Extracting its internal map code is **unlikely (20-45%)** to be cheaper than Repomix first because it brings language grammars, graph ranking, and chat-state relevance logic.

**Gate:** FAIL for Aider runtime; PASS only as a benchmark/design reference.  
**License:** Apache-2.0.  
**Verdict:** benchmark Repomix packs against Aider-style maps; do not install Aider as a second agent.

### tiktoken — excellent OpenAI counter, not a cross-provider authority

[tiktoken](https://github.com/openai/tiktoken) is OpenAI's MIT-licensed fast BPE tokenizer and maps known OpenAI model names to encodings. Its README reports 3-6x speed over a historical comparison; that benchmark is informative but not re-run here. The API showed a 2026-05-24 push.

Quality for OpenAI tokenization is **almost certain (90-99%)** because it is the provider's maintained tokenizer. Cross-provider accuracy is **almost certainly not (1-5%)**: Claude and other providers do not use OpenAI's tokenizer.

**Gate:** PASS inside a small estimator; no runtime ownership.  
**License:** MIT.  
**Verdict:** use only for OpenAI/Codex estimates when the exact model encoding is known. Label every byte/character fallback as an estimate; never let an estimated count silently truncate mandatory instructions.

### Prompt Poet/Priompt budgeting versus generic token counters

Counting alone does not decide *what to lose*. Prompt Poet's named sections/truncation priorities and Priompt's mandatory/optional scopes solve that policy question deterministically. Their best transferable properties are:

- mandatory goal/latest-delta/safety/receipt scopes;
- priority-ranked optional context;
- reserved completion budget;
- stable ordering for prompt caching;
- explicit list of ejected sections and original provenance;
- no semantic rewriting.

This primitive is **very likely (80-90%)** safer than LLMLingua-style semantic compression for harness controls because deletion is explicit/reversible and core sections can be non-ejectable; evidence is the libraries' deterministic semantics versus LLMLingua's learned compression described below. Owner-specific outcome improvement remains **UNVERIFIED**; replaying representative long handoffs with seeded “needle” facts and exact retention assertions would settle it.

## Survey C — semantic prompt compression

### LLMLingua / LongLLMLingua / LLMLingua-2 — serious research, wrong default

[Microsoft LLMLingua](https://github.com/microsoft/LLMLingua) uses small language models to compress prompts; the project cites EMNLP 2023 and ACL 2024 papers, supports JSON compression, and claims up to 20x compression with limited loss. It is MIT. GitHub lists release 0.2.2 from 2024-04-09; the repository API showed a 2026-04-08 push, and a maintainer answered an issue in 2025, so it is not accurate to call the project abandoned.

Research quality is **very likely (80-90%)**, supported by peer-reviewed papers and continued repository activity. Safe harness benefit is **unlikely (20-45%)** because the compressor is a trained model, adds heavyweight inference/model downloads, and can remove qualifiers, negation, paths, exact commands, or honesty tags. This corpus already documents detectors mishandling negation and quoted prose (`INPUT-known-harness-defects.md:8-87`); lossy rewriting upstream would make forensic provenance worse.

**Gate:** FAIL for automatic hook/compaction use. Although the rejected list names a trained *critic* rather than every trained model, LLMLingua adds a learned decision component on the highest-value context path and does not preserve byte-exact evidence. It also does not solve source selection.  
**License:** code MIT; model weights/dependencies require separate license checks before use.  
**Verdict:** no production adoption. An offline research bakeoff is permissible only after deterministic packing is measured, with exact must-retain assertions and zero control-instruction loss.

### Selective Context and similar entropy compressors — dormant/fragile class

Selective/entropy-based compressors remove low-information tokens without a full LLM. They are cheaper but still rewrite evidence and often target older model/tokenizer assumptions. I did not verify a current, maintained cross-provider implementation suitable for this harness; therefore no absence claim is made. **UNVERIFIED:** a PyPI/GitHub census of releases since 2025 plus a needle-retention benchmark would settle whether a maintained candidate exists.

**Gate:** generally PASS as a small library in theory, but FAIL in this survey because no verified maintained candidate and no evidence it preserves paths/negation/commands.  
**Verdict:** do not adopt from this unit's evidence.

## Survey D — prompt programming, optimization, and constrained generation

### DSPy and PromptWizard — high-quality optimization systems that fail the gate

[DSPy](https://github.com/stanfordnlp/dspy) programs LM modules and optimizes prompts/weights against examples and metrics; it is active and MIT. [PromptWizard](https://github.com/microsoft/PromptWizard) is an agent-driven prompt optimization framework using datasets and iterative LLM calls.

DSPy is **very likely (80-90%)** high quality for building and optimizing an LLM application, based on active 2026 development, a large research/community footprint, and explicit optimizer abstractions. It is **unlikely (20-45%)** to improve this personal harness without a labeled task/evaluation set, and its optimizer/model-call loop would become another runtime. PromptWizard has the same fit problem with more agent-driven optimization.

**Gate:** FAIL. Both introduce a second model-execution/optimization loop; an optimizer-selected prompt can also overfit a narrow eval. They are not merely template libraries.  
**Licenses:** DSPy MIT; PromptWizard's repository license must be rechecked at adoption time because this unit did not capture its license file.  
**Verdict:** do not adopt. Extract the principle “optimize only against held-out, outcome-grounded evals,” not the runtime.

### Guidance, Outlines, Instructor, and LMQL — solve output control, not host context

[Guidance](https://github.com/guidance-ai/guidance) is an active MIT library for regex/CFG-constrained generation and interleaving Python control with model generation; GitHub lists release 0.3.2 from 2026-03-18. [Outlines](https://github.com/dottxt-ai/outlines) similarly constrains token generation/structured outputs. [Instructor](https://github.com/instructor-ai/instructor) wraps provider clients with validation/retry for typed outputs. [LMQL](https://github.com/eth-sri/lmql) is an Apache-2.0 LLM programming language with control flow, constraints, decoding, batching, and its own runtime.

Guidance/Outlines quality is **very likely (80-90%)** for local or controllable generation backends. Relevance here is **unlikely (20-45%)** because Claude Code/Codex own decoding and tool schemas. Instructor's validation/retry approach could actually amplify this corpus's 22.9% StructuredOutput error surface when schemas are over-strict (`corpus.json:103-110,8964-9020`) unless schemas are simplified first.

LMQL is **very likely (80-90%)** dormant: its latest release is 0.7.3 from 2023-10-14 and GitHub activity shows the last push on 2025-05-22—two independent GitHub fields. “Dormant” is more accurate than “abandoned” because the repository is not archived.

**Gate:** FAIL for all as harness integrations because they require owning/wrapping model calls or decoding, i.e. a second execution layer.  
**Licenses:** Guidance MIT; LMQL Apache-2.0; Outlines and Instructor license files must be rechecked at adoption time (their current repository pages, not copied snippets, are authoritative).  
**Verdict:** do not adopt. Prefer provider-native structured output with smaller, tolerant schemas and typed repair receipts.

### Promptfoo — useful offline evaluator if tightly bounded

[Promptfoo](https://github.com/promptfoo/promptfoo) is an MIT CLI/config-driven prompt, agent, and RAG test tool with CI integration and optional red teaming. The repository API showed a push on 2026-07-18.

Quality is **very likely (80-90%)** for offline prompt comparison based on active releases/development, declarative fixtures, provider breadth, and CI orientation. Fit here is **roughly even (45-55%)** until compared with the existing eval skill and scripts; adding it could either fill an execution gap or duplicate a runner. The red-team/guardrail surface is explicitly out of scope for adoption.

**Gate:** PASS only as an offline subprocess invoked by the existing eval skill; FAIL as a hosted service, runtime proxy, or always-on red-team guardrail framework.  
**License:** MIT for the repository; hosted/enterprise terms are separate.  
**Verdict:** bounded bakeoff, not immediate fleet-wide adoption.

## Survey G — prompt management and observability platforms (explicit gate failures)

Representative current products include [Langfuse](https://github.com/langfuse/langfuse), LangSmith, [PromptLayer](https://github.com/promptlayer/promptlayer), Braintrust, Helicone, [Agenta](https://github.com/Agenta-AI/agenta), Portkey, and Humanloop-style hosted prompt registries. They provide some combination of prompt versioning, labels, playgrounds, traces, datasets, evals, gateways, cost/latency dashboards, and collaboration.

- Langfuse is active and broad. Its core is MIT while some self-hosted enterprise features are commercially licensed ([official self-hosting license explanation](https://github.com/langfuse/langfuse-docs/blob/main/pages/faq/all/self-hosting-langfuse.mdx)).
- LangSmith is a proprietary hosted/service product tied to the LangChain ecosystem; terms must be read from the service agreement, not inferred from LangChain's MIT license.
- PromptLayer/Braintrust/Helicone/Agenta/Portkey mix open-source SDKs or cores with hosted offerings; repository licenses do not grant rights to hosted services. Exact current license boundaries must be rechecked before any adoption.

**Gate:** FAIL for all production adoption here because the forbidden list explicitly excludes observability SaaS. Self-hosting does not fix the architectural issue: it adds a service/database/control plane. Prompt registries also create split-brain authority versus versioned skill/rule files in Git.

## Recommended design

### R1 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED: on-demand Repomix `context-pack` skill

Create one front-door skill that calls a pinned Repomix CLI/library in a subprocess and returns a typed, bounded pack. Do not auto-run it at SessionStart or inject a whole repository into every agent.

Required contract:

```text
CONTEXT-PACK v1
goal: <re-anchored exact goal>
selection_basis: explicit paths | changed files | search hits
budget: <declared estimate/encoding>
files: [path, source hash/mtime, included lines or signature mode]
omitted: [path, reason: ignore|budget|binary|secret|parse-failure]
untrusted: true when any source is external/retrieved
body: <pack>
```

Defaults: local repository only; explicit include roots; `.gitignore` honored; secrets scan on; remote config off; `--stdout`; no comments removed; no semantic compression; hard byte ceiling before returning through the hook/tool channel. Tree-sitter `--compress` is opt-in and must preserve file/symbol provenance. Never scan plugin caches/session history by default, both because they are irrelevant and because the measured Windows command-line/plugin pathology makes broad enumeration risky.

Adoption value is **likely (55-80%)**, supported by Repomix's feature fit and Aider's independent repo-map success. **UNVERIFIED:** exact improvement; settle with a paired 20-task trial. Promotion criteria: at least 20% fewer discovery Read/Grep/Glob calls or lower time-to-first-relevant-file, no lower completion rate, zero secrets, zero required-file omissions, and no increase in prompt-injection compliance. If it misses, remove the skill; there is no daemon or migration.

Anti-overfit gate: PASS. It is a bounded tool on the existing skill bus, not an orchestrator, database, memory service, critic, SaaS, or guardrail framework.

### R2 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED: deterministic context-envelope budgeter

Implement a small pure function in the shared harness, inspired by Prompt Poet/Priompt, for *harness-generated additionalContext and typed handoffs only*. The recommendation inherits **UNVERIFIED** because the hosts' exact injection limits and model-visible delivery are not captured; a live sanitized hook fixture at 50%, 80%, and 95% context usage would settle it.

Input parts: `{id, text, priority, mandatory, min_chars, provenance}`. Output: stable-order concatenation under a declared budget plus an ejection receipt. Mandatory parts are: active root goal, latest user delta, dangerous-operation policy, unresolved failures/verification receipts, and honesty tags. Optional parts include repeated routing hints, older background, verbose examples, and generated maps. The function may *drop a whole optional part* but may not semantically summarize or cut the middle of a mandatory part.

Use the provider's native count if the hook payload exposes it; otherwise use a clearly labelled conservative byte estimate. tiktoken is permitted only for known OpenAI encodings. Every output must say which method was used. Maintain a stable prefix/order to preserve caching. Record what was ejected so failures are diagnosable.

Expected value is **likely (55-80%)**, supported by deterministic library designs and the existing fixed 500-character goal truncation (`modules.py:1357-1359,1374-1376`). Harm and benefit are **roughly even (45-55%)** if it is applied to host-owned conversation history, because deterministic ejection would then compete with native compaction without a model-visible delivery measurement; therefore scope is intentionally narrow. Do not use it to rewrite the user prompt, native system prompt, raw tool evidence, or host conversation history.

Anti-overfit gate: PASS. It is one pure helper on the existing injection/handoff bus. No new runtime or store.

### R3 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED: Promptfoo offline bakeoff

Add no production dependency yet. Create the same 10-20 prompt/hook fixtures in (a) the existing eval runner and (b) Promptfoo, then compare setup lines, Windows reliability, provider coverage, deterministic assertions, artifact provenance, runtime, and failure readability. The experiment settles the premise that Promptfoo fills rather than duplicates the current eval gap.

If Promptfoo wins materially, invoke it only through the existing eval skill/CI lane with pinned version and local files. Disable hosted sharing, tracing, proxying, and red-team runtime features. If it does not win, retain the fixtures and discard the dependency.

The probability of net value is **roughly even (45-55%)**, because Promptfoo is mature but the local eval surface already exists in part (`inputs/audit-findings/D15.md:15-19`).

Anti-overfit gate: PASS only in this offline, subprocess form. It becomes FAIL if used as an always-on proxy, hosted observability service, or guardrail framework.

### R4 — NATIVE (Claude Code already does this; we just enable it) — UNVERIFIED: preserve host compaction and validate the existing PostCompact route

Do not replace native compaction with LLMLingua, a LangChain summary memory, or a second transcript manager. Preserve native compaction and the shared PreCompact/PostCompact hooks already wired at `claude/settings.json:380-403`; validate the existing `postcompact_reanchor` mode before adding anything.

Benefit is **very likely (80-90%)** because the code already captures exact goal/decision/failure state and avoids a new runtime. **UNVERIFIED:** live delivery/obedience; the experiment is a session with a unique root goal, a deliberate compact, and a captured first post-compact model-visible context plus continuation. Promote only after two independent signals: dispatcher receipt and model-visible/behavioral retention.

Anti-overfit gate: PASS. This is the native host plus existing hook bus.

## What not to build

1. No universal prompt DSL migration. Markdown skills/rules remain the source assets; generated envelopes can be structured without rewriting hundreds of files.
2. No automatic whole-repo pack on every turn. Context selection is task-triggered and bounded.
3. No semantic compressor in the control path. Exact instructions, negation, paths, and evidence remain intact.
4. No second agent runtime, DAG, graph, or provider wrapper under Claude Code/Codex.
5. No vector database, temporal KG, stateful-agent server, or self-editing memory.
6. No prompt-observability SaaS or self-hosted observability stack.
7. No trained prompt optimizer/critic selecting live harness policy.
8. No new guardrail framework disguised as prompt evaluation.

These exclusions are **almost certain (90-99%)** correct under the supplied gate because they rest on explicit forbidden-component text, not a forecast about model progress.

## Adoption order and stop conditions

1. First validate the existing live PostCompact path (R4). If it already preserves the goal and failures, do not add a summary/compression layer.
2. Run Repomix in an isolated 20-task trial (R1). Stop on any secret disclosure, provenance loss, or worse completion rate.
3. Replay long generated handoffs through the pure budgeter (R2). Stop if any mandatory needle, negation, command, path, confidence band, or UNVERIFIED experiment is lost.
4. Run the Promptfoo bakeoff (R3). Adopt only if it beats the existing runner on measured owner-relevant criteria.
5. Reassess after host/model upgrades. It is **likely (55-80%)** that larger effective context and better native selection reduce the marginal value of packing, based on the anti-overfit premise that model capability improves while scaffolding persists; deterministic selection remains removable and does not own state.

This order is **very likely (80-90%)** to minimize iatrogenic risk because each stage is reversible, rides an existing bus, and has a measured stop condition. The exact numeric trial thresholds are a design choice, not an empirical truth; they are deliberately explicit so later units can amend rather than silently reinterpret them.
