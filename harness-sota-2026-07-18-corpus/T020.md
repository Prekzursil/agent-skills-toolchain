# T020 — Competitive teardown: SWE-agent

**Unit:** T020  
**Research date:** 2026-07-19 UTC  
**Upstream snapshot inspected:** `SWE-agent/SWE-agent` `main` at commit [`3ea751c087f32b16e039a2233dd6eefecef325d5`](https://github.com/SWE-agent/SWE-agent/commit/3ea751c087f32b16e039a2233dd6eefecef325d5), committed 2026-07-16  
**Latest release tag independently enumerated:** `v1.1.0` (`0f3acafacabc0def8cc76b4e48acb4b6cf302cb9`); the package still declares version 1.1.0 at the inspected `main` commit ([source](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/__init__.py#L15))  
**Subject baseline:** unpacked read-only trees under `/local_disk0/codexwork/bundle`; no Windows-only path was assumed present  

## Executive verdict

Do **not** replace the owner's harness with SWE-agent. This is not a conservative preference; it follows from upstream's own product direction and a mechanism-by-mechanism comparison. The project says that mini-SWE-agent has superseded SWE-agent, recommends mini-SWE-agent going forward, and marks SWE-agent maintenance-only ([README lines 19–24](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/README.md#L19-L24), [FAQ lines 145–149](https://swe-agent.com/latest/faq/)). The newest published changelog entry is 1.1.0 from 2025-05-22 and describes a mostly-fix release ([changelog](https://swe-agent.com/latest/installation/changelog/)). A wholesale move to it would introduce a second Python orchestration/runtime stack, SWE-ReX, while losing or rebuilding the owner's native MCP ecosystem, cross-provider lifecycle bus, durable semantic/event memory, permission hooks, and genuine collaborating agents.

The best extraction is much smaller:

1. Port a **typed, replay-oriented per-step receipt**, including the exact model query hash, proposed action, executed action, observation outcome, relevant state, hook decisions, and configuration hash.
2. Port **syntax-aware corrective requery** for Bash and PowerShell, targeted directly at the corpus's 1,631 unmatched-quote EOF failures.
3. Port SWE-agent's **staged review-on-submit** idea, but as a non-blocking, semantic finalization check on the existing hook bus—not as its literal shell command.
4. Keep **best-of-N / reviewer selection** as an opt-in escalation for high-uncertainty work, implemented through native agents. Do not make per-step sampling the default.
5. Use Claude Code's native sandbox in a WSL2 pilot if the owner has WSL2; do not import SWE-ReX merely to obtain isolation.

This extraction is **very likely (80-90%)** to improve debuggability and recovery without degrading the harness's breadth. Evidence: SWE-agent persists the exact query/action/observation/state/config needed for replay, while the pinned live defect D3 says the owner's hook behavior is currently unmeasurable; all proposed changes ride existing hooks, settings, or native agents rather than adding a rejected runtime. The remaining uncertainty is whether Claude's current Windows hook payload can rewrite or suppress a malformed command without violating the harness's “block only dangerous” contract; the settling experiment is specified under GAPS.

## 1. Agent loop

### SWE-agent mechanism

SWE-agent's default loop is deliberately conventional:

1. `RunSingle` constructs `SWEEnv` and an agent, starts the environment, invokes hooks, runs the agent, saves predictions, and closes the environment ([run_single.py lines 164–207](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/run/run_single.py#L164-L207)).
2. Agent setup installs tools, sets the problem statement in the environment, inserts system prompt, demonstrations, and instance prompt, and reads structured environment state ([agents.py lines 561–606](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L561-L606)).
3. Each step processes message history, queries the model or action sampler, parses thought/action, checks the action blocklist, executes it in a persistent shell, records output and state, and recognizes a submission marker ([agents.py lines 1006–1052](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L1006-L1052), [agents.py lines 936–1004](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L936-L1004)).
4. Format errors, blocked actions, content policy errors, and Bash syntax errors enter a bounded correction loop. Context, cost, repeated timeout, API, environment, and unknown errors instead terminate through patch autosubmission ([agents.py lines 1106–1218](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L1106-L1218)).
5. The action/observation loop continues until `done`, saving the trajectory after every step ([agents.py lines 1235–1294](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L1235-L1294)).

The strongest detail is not the loop itself but its failure partition: recoverable model-interface mistakes get bounded requery with specific corrective context; terminal infrastructure failures attempt to preserve the patch. `max_requeries` defaults to three ([agents.py lines 149–161](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L149-L161)). Commands have per-action, total-execution, and consecutive-timeout ceilings ([tools.py lines 139–152](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L139-L152)).

### Better than ours

The syntax-specific corrective path is a concrete advantage over the current measured Bash behavior. The owner has 1,631 unmatched-quote EOF failures; SWE-agent catches `BashIncorrectSyntaxError`, supplies the shell-check output, and requests a corrected action without polluting normal history with the failed temporary exchange ([template source](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L102-L120), [correction source](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L789-L821)). The trajectory still retains the mistake for diagnosis.

### Worse than ours

- It is a task-specific second runtime rather than a cross-tool behavior layer. Replacing our native provider loops with this wrapper would duplicate lifecycle, tools, execution, retry, telemetry, and permission semantics.
- It executes one model action at a time. The owner's native tools already support richer file operations, web/MCP calls, notebooks, interactive steering, and multi-agent coordination.
- By default, shell non-zero exit codes are ignored (`check="ignore"`) unless an internal flag is set ([agents.py lines 958–967](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L958-L967)). That makes textual output—not terminal status—the default truth source. Our behavior contract's terminal `SUCCESS:`/`FAILED:` convention is stronger.
- Autosubmitting a patch after context, cost, runtime, or unknown failure preserves work but can relabel an unverified patch as a submission. SWE-agent records the qualified exit status, which mitigates but does not remove that semantic risk ([agents.py lines 823–868](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L823-L868)).

### Port proposal: syntax-aware correction — UNVERIFIED hook rewrite support

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one shared `command_preflight` module to the existing provider-neutral PreToolUse dispatcher:

1. Inspect only the actual command field for `Bash` or `PowerShell`; never scan a Write/Edit body. This inherits the D1 use-vs-mention discriminator.
2. Bash: pass command bytes on stdin to `bash -n`, never interpolate them into a wrapper command. PowerShell: parse with `[System.Management.Automation.Language.Parser]::ParseInput` and collect parser errors without executing.
3. On valid syntax, emit no context and a terminal success receipt.
4. On invalid syntax, emit a typed reason (`shell_syntax`, offsets, parser message, command hash), increment a per-hash counter, and ask for one corrected command. Cap at two corrections, then require a different mechanism (script file or argument-array execution).
5. Persist both the original and corrected command hashes in hook telemetry, not raw commands containing secrets.

UNVERIFIED whether the installed Claude Windows PreToolUse contract can replace/cancel an invalid command while returning exit 0. The settling experiment is to dump the real hook input/output schema, submit a harmless known-invalid `printf '`, and test whether `updatedInput`, a permission decision, or another native field suppresses execution. The recommendation is **very likely (80-90%)** to reduce unmatched-quote retries if suppression or rewrite is supported; evidence is the exact corpus fingerprint class and SWE-agent's bounded syntax correction. If only exit-2 blocking is available, it is **roughly even (45-55%)** that this remains worth deploying because it would conflict with the owner's “block only dangerous” invariant; the experiment above settles that branch.

## 2. Context management

### SWE-agent mechanism

SWE-agent stores full history, then derives the messages sent to the model by chaining configured processors ([agents.py lines 540–551](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L540-L551)). Available processors include:

- `LastNObservations`: preserve messages but replace older observation bodies with an explicit line/image omission marker; the first observation is never removed, and tagged outputs can be forced kept or removed ([history_processors.py lines 85–176](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/history_processors.py#L85-L176)).
- `ClosedWindowHistoryProcessor`: keep the newest displayed window for each file and replace older windows with a short omission message ([history_processors.py lines 215–258](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/history_processors.py#L215-L258)).
- `CacheControlHistoryProcessor`: move ephemeral cache-control marks to the last N user/tool messages ([history_processors.py lines 261–302](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/history_processors.py#L261-L302)).
- `RemoveRegex`: delete configured regex-matched regions from all but the newest K messages ([history_processors.py lines 305–337](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/history_processors.py#L305-L337)).
- Observation-level clipping at a configurable character threshold, with an explicit count and instruction to use narrower commands ([agents.py lines 69–82](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L69-L82)).

The current default does **not** use classic last-N elision; it only applies cache control to the last two messages ([default config lines 67–69](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/config/default.yaml#L67-L69)). The source itself says modern state-of-the-art models often fit enough context that `LastNObservations` is not always needed and notes that it breaks prompt caching ([history processor lines 104–111](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/history_processors.py#L104-L111)).

### Better than ours

SWE-agent exposes deterministic, tool-aware context transforms that are replayable from configuration. Our harness has strategic compaction, goal reinjection, and memory, but the model/provider controls the main transcript compaction. We do not have an equivalent supported transform over arbitrary native history.

### Worse than ours

- `RemoveRegex` is the same architectural family as the owner's confirmed D1 defect: regex over content without semantic role. It can silently erase negated prose, quoted evidence, or payload fields. Do not copy it.
- Last-N output removal is recency, not relevance. It can retain five redundant failures and elide the one older result that settles the task. The keep/remove tags help only when tools or hooks assign them correctly.
- SWE-agent context is trajectory-local. It has no durable semantic recall, temporal supersession, event-ledger replay, or compaction checkpoint equivalent.
- The default 100,000-character observation ceiling is far above a useful “small evidence packet” and counts characters rather than model tokens.

### Capability we lack: arbitrary history rewriting

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** A faithful port would require interposing on every model request and owning the canonical conversation, because the current native provider—not our hook bus—owns message history. That is precisely a second orchestration runtime. Reject it under the anti-overfit gate. The benefit is **unlikely (20-45%)** to exceed the regression risk, because SWE-agent itself has moved away from last-N in its default and our owner already uses 1M-context Claude plus durable recall; the evidence is the current default and the source's caching warning.

### Small substitute: explicit observation receipts

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Do not rewrite history. Instead, after large terminal output, inject a compact receipt: tool, exit status, total bytes/lines, retained head/tail sizes, omitted count, artifact/log path, and a command hash. Preserve the raw result at its native transcript/log path. This is **likely (55-80%)** to reduce re-fetching and false “empty output” assumptions; evidence is SWE-agent's explicit omission counts and the owner's terminal-marker/longrun contract. UNVERIFIED whether native tool results expose pre-truncation byte counts; the settling experiment is a known 200,000-byte command output compared across hook payload, transcript, and terminal log. Until that experiment, do not claim the receipt can report total bytes.

## 3. Memory

### SWE-agent mechanism

SWE-agent has three persistence forms, none of which is semantic long-term memory:

1. In-run history and trajectory.
2. `.traj` JSON containing thought/action/observation/state and the exact model `query` for every step ([trajectory docs lines 7–30](https://swe-agent.com/latest/usage/trajectories/)).
3. A saved `config.yaml`, logs, predictions, and replay configuration; the documented config can repeat the instance, and completed trajectories can be converted to demonstrations and replayed ([trajectory docs lines 51–100](https://swe-agent.com/latest/usage/trajectories/), [demonstration docs](https://swe-agent.com/latest/config/demonstrations/)).

Demonstrations are manually chosen successful trajectories inserted at run start. That is few-shot procedural guidance, not learned retrieval or owner memory.

### Better than ours

The trajectory is a substantially better single-run forensic record than today's hook telemetry. It keeps the exact query visible at each step, distinguishes parsed thought/action from raw response, stores the resulting state, saves after every step, and carries replay configuration. The owner corpus can measure tool calls but, per live defect D3, cannot currently measure hook behavior. SWE-agent's “query at the current step” change was explicit in 1.1.0 ([changelog lines 10–15](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/docs/installation/changelog.md#L10-L15)).

### Worse than ours

- There is no cross-session semantic recall, temporal validity, supersession, bounded lexical recall, or objective-vs-semantic separation.
- Full raw trajectory logging can retain secrets, private code, model thought text, and propagated environment values. The tool configuration warns that propagated API-key values can appear in debug logs ([tools.py lines 86–92](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L86-L92)). Our shared harness explicitly redacts and hashes session/project identifiers (`/local_disk0/codexwork/bundle/agents/harness/README.md:23-30`).
- A demonstration selected from a successful old run can fossilize obsolete tool usage. There is no supersession metadata comparable to the owner's memory contract.

### Port proposal: typed trajectory and hook receipts

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing `terminal.jsonl`/ledger receipt, not the transcript runtime. One JSON object per lifecycle transition:

```json
{
  "schema": 1,
  "run_hash": "...",
  "seq": 42,
  "event": "PreToolUse",
  "tool": "Bash",
  "input_hash": "...",
  "decision": "allow|inject|block|error",
  "reason_code": "shell_syntax|goal_reinject|secret_path|none",
  "module": "command_preflight",
  "latency_ms": 8,
  "output_status": "SUCCESS|FAILED",
  "config_hash": "...",
  "prev_receipt_hash": "..."
}
```

Raw commands, outputs, prompts, absolute paths, and secrets stay in their already-governed stores; receipts use hashes and stable reason codes. `prev_receipt_hash` makes dropped/reordered records detectable without creating a durable-execution engine. A tiny manifest at SessionEnd records provider version, model, worktree commit, installed harness version, receipt head hash, and native transcript/log pointers.

This is **very likely (80-90%)** to close D3's observability gap because the dispatcher already sees events and writes terminal receipts; evidence is `/local_disk0/codexwork/bundle/agents/harness/README.md:3-15,19-29`. UNVERIFIED whether every registered local hook bypasses the shared dispatcher; the settling experiment is to enumerate settings registrations and generate one known event per hook family, then reconcile expected vs receipt module IDs. The recommendation does not claim complete hook coverage until that test passes.

## 4. Tools and MCP handling

### SWE-agent mechanism

Tools are executable bundles copied into the runtime. A bundle contains `bin/`, `config.yaml`, optional `install.sh`, README, and optional Python packaging; its config declares signatures, descriptions, and arguments ([tool docs](https://swe-agent.com/latest/config/tools/), [custom-tool tutorial](https://swe-agent.com/latest/usage/adding_custom_tools/)). SWE-agent:

- Can expose a built-in Bash function-calling tool plus commands from bundles.
- Rejects duplicate tool names at configuration construction ([tools.py lines 168–191](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L168-L191)).
- Uploads bundles into `/root/tools`, installs them, prepends their `bin` directories to PATH, and checks every declared command is available ([tools.py lines 252–312](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L252-L312)).
- Supports function-calling, JSON, or thought/action parsing; the default is function calling ([FAQ lines 120–122](https://swe-agent.com/latest/faq/)).
- Runs each bundle's state command after every action, merging JSON state such as working directory/open file into the next prompt ([tool docs lines 46–78](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/docs/config/tools.md#L46-L78)).
- Has no first-class MCP client or server, with **almost certain (90-99%)** confidence from the two independent signals in “Evidence and detector discipline.”

### Better than ours

- Duplicate tool definitions fail at startup with both source paths, rather than becoming ambiguous routing.
- Installation includes an availability check before the agent loop. This is exactly the shape missing from the dead Tavily case: declared is not assumed healthy.
- Per-action structured state is a clean ACI concept. The paper's central result is that agent-specific interfaces materially affect performance, though its reported benchmark numbers are historical and should not be transferred to this harness ([paper](https://arxiv.org/abs/2405.15793)).

### Worse than ours

- Tool bundles are local executable packaging, not a protocol ecosystem. They lack MCP discovery, remote capabilities, resources/prompts, auth/lifecycle standards, and dynamic tool search.
- `install.sh` executes inside the runtime and can install arbitrary dependencies. That is acceptable in a disposable container but expensive and risky as a general skill mechanism.
- The owner already has roughly 355 installed skills but uses 78; importing another tool packaging system worsens capability sprawl.
- SWE-agent's static tool list does not solve dead-service routing. A copied executable can pass `which` and still fail at runtime; its availability check is necessary but not sufficient.

### Port proposal: health-qualified capability routing

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Before exposing or recommending an MCP/tool family, maintain a session-start capability record with `declared`, `launchable`, `live`, `last_error`, and TTL. `launchable` must resolve the Windows command with PowerShell `Get-Command`, not Git Bash `which`; `live` must use a tool-specific harmless probe. A failed live probe removes the tool from agent-facing recommendations for the TTL and injects the healthy substitute. Include a known-positive control in every detector run.

This is **very likely (80-90%)** to prevent the recorded dead-Tavily repeat calls, because 135 failures were “not connected” and a live probe directly discriminates declaration from service availability. Evidence is the pinned corpus and D2's known-positive-control requirement. UNVERIFIED which Claude MCP servers expose a side-effect-free health/list operation; the settling experiment is to enumerate each server's native list/capabilities method and classify probes before any automatic call. Servers without a harmless probe remain `declared/unknown`, never falsely `dead`.

Do not port SWE-agent's bundle runtime. Our existing skill/plugin/MCP buses are broader and already installed.

## 5. Permission and isolation model

### SWE-agent mechanism

The default deployment is a Docker container (`python:3.11`); SWE-ReX can execute locally, in Docker, Modal, or AWS/Fargate-style remote deployments ([hello-world docs lines 72–82](https://swe-agent.com/latest/usage/hello_world/), [architecture](https://swe-agent.com/latest/background/architecture/)). A persistent Bash session runs inside the deployment. The repository is copied/cloned and reset between RetryAgent attempts ([swe_env.py lines 109–166](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/environment/swe_env.py#L109-L166)).

Inside that boundary, permission is not user-mediated. A prefix/equality/regex blocklist rejects interactive or unsupported commands such as editors, `nohup`, `tail -f`, bare shells, and some debugger forms ([tools.py lines 29–72](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L29-L72), [matching implementation](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/tools/tools.py#L350-L367)). Environment variables must be explicitly propagated, but the docs warn their values may appear in logs.

### Better than ours

The disposable container is a materially stronger default blast-radius boundary than the subject's current `defaultMode: bypassPermissions` plus additional access to `C:` and `D:` (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`). It also makes arbitrary bundle installation and hard reset tractable.

### Worse than ours

- The blocklist is syntactic and trivially incomplete: it checks `startswith`, exact strings, or a small command-name regex map. Aliases, absolute paths, wrappers, and semantically equivalent commands can bypass it. Conversely, `startswith("make")` also catches unrelated prefixes. It is an unsupported-operation filter, not an authorization model.
- There is no per-tool ask/allow/deny policy, path-scoped file permission, MCP permission, approval provenance, or human escalation flow.
- Container isolation does not itself constrain network egress, credential propagation, or destructive actions inside a mounted/copied repository. The SWE-agent docs call the environment sandboxed but the inspected SWE-agent layer does not declare a domain allowlist.
- Exact SWE-ReX replacement is a new runtime and conflicts with the anti-overfit gate.

### Port proposal — UNVERIFIED WSL2 availability: native sandbox profile

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** If the Windows owner already uses WSL2 for an eligible repository, create an opt-in Claude sandbox profile with `sandbox.enabled: true`, `failIfUnavailable: true`, minimal filesystem writes, an explicit network-domain allowlist, and `allowUnsandboxedCommands: false`. Claude Code natively applies OS-level filesystem and network isolation on Linux/WSL2; native Windows support is only planned, and WSL2's sandbox cannot invoke Windows binaries such as PowerShell or programs under `/mnt/c/` ([official sandbox docs](https://code.claude.com/docs/en/sandboxing)).

The profile is **likely (55-80%)** to reduce blast radius for Linux-compatible coding work if those prerequisites hold; evidence is Claude's OS-level enforcement and the subject's broad bypass mode. ## 7. Multi-agent support

### What SWE-agent actually has

SWE-agent has two ensemble-like mechanisms, neither a collaborating team:

1. `RetryAgent` runs attempts sequentially. It rotates among configured DefaultAgent configs, hard-resets the environment between attempts, applies a shared cost limit, reviews each submission, and selects a best attempt ([agents.py lines 257–383](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L257-L383), [loop lines 390–440](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/agents.py#L390-L440)). Reviewer loops can score attempts or choose among them under maximum-attempt and cost thresholds ([reviewer configs](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/reviewer.py#L157-L237)).
2. Action samplers can request N completions from the same model as “colleagues,” feed their proposed thought/actions back to the model, or tournament-compare sampled actions. They do not execute tools independently, own files, communicate asynchronously, or retain separate contexts ([action sampler](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/action_sampler.py#L40-L94), [binary comparison](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/action_sampler.py#L96-L314)).

It has no first-class cooperating-agent delegation/mailbox/handoff with **almost certain (90-99%)** confidence, based on the two independent signals above.

### Better than ours

The retry/reviewer loop provides explicit aggregate cost ceilings, hard environment reset, per-attempt artifacts, and deterministic best-attempt selection plumbing. The owner's fan-out is stronger in agency but more dependent on prompt discipline and handoff structure.

### Worse than ours

- Sequential full retries pay repeatedly for discovery and setup and do not share verified facts.
- Same-model “colleagues” are samples, not mechanically independent reviewers. They share model biases and the same context.
- The reviewer generally judges patches/trajectories using an LM; that is not an independent correctness signal. It can rank plausible-looking wrong patches above tested ones.
- Per-step tournament sampling multiplies model calls on every decision and is the kind of elaborate scaffolding likely to overfit as base models improve.
- The owner already has native Claude agents, Codex MCP fan-out, live peer dialogue, and remote fleet workflows. SWE-agent would be a regression in coordination.

### Capability we lack: automatic cost-bounded best-of-N escalation

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Implement this as an opt-in orchestration recipe using existing native agents, not a new runtime:

1. Trigger only for an explicit high-cost/high-uncertainty class (security-sensitive patch, architecture choice with two viable designs, or repeated failed implementation), never every tool step.
2. Spawn two fresh-context agents with identical objective/evidence packet but different roles: implementer and falsifier, or two implementers if alternatives are genuinely distinct.
3. Require each to return a typed packet: patch/worktree, tests run and exit codes, remaining gaps, confidence with evidence.
4. Have the primary verify both in the real target environment; test evidence dominates an LM judge.
5. Enforce attempt count, token/cost proxy, and wall-clock ceiling; keep all attempts, select one only after independent verification.

This is **likely (55-80%)** to help on explicitly gated hard tasks and **unlikely (20-45%)** to help as a default. Evidence: SWE-agent exposes the cost/attempt controls, while the owner's native team is more capable than sampled completions; the anti-overfit evidence in the brief says a ~100-line loop remains highly competitive. The uncertain benefit must be settled by an A/B evaluation on at least 30 previously failed tasks, stratified by failure class, comparing single-agent versus two-agent escalation on resolution, wall time, tool errors, and owner corrections.

No trained critic, durable workflow engine, second orchestrator, or agent-mail replacement is proposed.

## 8. Verification and self-check

### SWE-agent mechanisms

SWE-agent combines four verification layers:

1. **Prompted reproduce/fix/reproduce.** The default instance template asks the model to create a reproduction script, confirm failure, fix source, rerun, and consider edge cases ([default config lines 18–27](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/config/default.yaml#L18-L27)).
2. **Staged review on submit.** The default `submit` bundle captures the staged diff. On the first call, it returns a configurable checklist plus diff; only after the configured review stages does it emit the submission marker ([submit source](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/review_on_submit_m/bin/submit#L13-L46)). The default checklist asks to rerun reproduction after final edits, remove the temporary reproduction, revert test-file modifications, and submit again ([default config lines 47–63](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/config/default.yaml#L47-L63)).
3. **Format/action self-correction.** Bounded requery handles parser errors, invalid Bash syntax, and blocked actions.
4. **Optional attempt review and selection.** A reviewer samples scores or a chooser ranks multiple patches; failure exits may receive a score penalty ([reviewer source](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/sweagent/agent/reviewer.py#L157-L224)).

Trajectory replay and testing models provide harness self-tests; demonstrations can be replayed to ensure their actions still execute ([demonstration docs lines 27–38](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/docs/config/demonstrations.md#L27-L38)).

### Better than ours

The staged submit command is a simple and powerful “second look at the actual diff” mechanism. It is stateful, deterministic, and tied to the final artifact rather than a vague “review your work” prompt. Our subject has verify/quality-gate commands and Stop checks, but the inspected baseline does not show a universal semantic first-finalization diff review across providers.

### Worse than ours

- The checklist is generic and model-attested. It does not mechanically prove the reproduction was run or passed.
- It tells the model to revert test modifications wholesale. That is benchmark contamination policy, not a generally correct software-engineering rule; real tasks often require legitimate test updates.
- The submit tool uses `shell=True` for a fixed Git command. The string is fixed, so injection is not the issue, but it reinforces reliance on shell text rather than argument arrays.
- LM reviewer scores are not independent verification. The owner contract's fresh-context critic principle is better only when backed by actual test/tool signals.
- Autosubmission after infrastructure failure weakens the meaning of “submitted.”

### Port proposal: evidence-backed staged finalization

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a shared finalization state machine keyed by `(session_hash, repo_hash, diff_hash)`:

- Detect only actual finalization verbs/actions (`gh pr create`, `git push`, explicit PR skill finalization, or Stop with modified files), never prose mentioning them.
- First encounter: compute `git diff --stat`, changed paths, test-file change classification, latest relevant test receipt, and whether code changed after that receipt. Inject a checklist containing only falsifiable missing evidence. Exit 0.
- If the diff changes, invalidate prior review state.
- Second encounter with unchanged diff: allow finalization and record the reviewed diff hash.
- Dangerous actions retain existing permission policy. This module must not block ordinary stopping or use regex over assistant prose.
- Never auto-revert tests. If tests changed, ask whether the task requires them and run tamper checks already present.

This is **very likely (80-90%)** to improve final-patch review quality at low architecture cost. Evidence: SWE-agent's staged diff review is deterministic and the owner's existing hook bus already has Git/test-tamper/Stop surfaces. UNVERIFIED whether all provider finalization actions can be observed through the shared dispatcher; the settling experiment is a matrix of Claude/Codex actions (`gh pr create`, `git push`, ordinary Stop, user-cancel) with known-positive receipts. Deploy initially as inject-only and measure owner corrections and repeated finalization rate before any stronger enforcement.

## 11. What explicitly not to copy

1. **Do not adopt SWE-agent or SWE-ReX as the owner harness.** That is a second orchestration/execution runtime, explicitly disallowed by the anti-overfit gate absent extraordinary evidence. Upstream recommends a simpler successor.
2. **Do not copy regex history deletion.** It recreates D1's use-vs-mention defect and silently modifies evidence.
3. **Do not copy the shell prefix blocklist as security.** Container boundaries are useful; string matching is neither complete nor semantically precise.
4. **Do not copy raw full-trajectory logging.** Keep hashes, reason codes, pointers, and governed native records. Propagated secret values can appear in SWE-agent debug logs.
5. **Do not make LM reviewer scores correctness gates.** Treat them as proposal ranking at most; executable tests and independent environment checks dominate.
6. **Do not make per-step best-of-N the default.** It multiplies inference on every action and overfits the harness around weaknesses that stronger base models may remove.
7. **Do not auto-revert all test changes.** That policy is benchmark-specific and wrong for normal development.
8. **Do not interpret autosubmitted-on-error as verified completion.** Preserve patches with a distinct `salvaged_unverified` status.
9. **Do not add SWE-agent tool bundles beside skills/plugins/MCP.** The owner already has capability sprawl and low utilization; a fourth packaging surface worsens routing.

## 12. Anti-overfit gate

All counted recommendations ride an existing bus:

- Shared hook dispatcher: receipts, command preflight, staged finalization, health routing.
- Settings/JSON: optional native sandbox and schema/config hashes.
- Native agents: gated best-of-N.

No second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is proposed. The receipt hash chain is append-only telemetry, not workflow state or retry scheduling. The staged finalization state is session-scoped and reconstructible from diff hash, not durable execution.

The one capability whose faithful port would require a rejected component—arbitrary model-history rewriting—is tagged **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and explicitly rejected. Exact Docker/SWE-ReX parity is likewise rejected rather than smuggled in as “sandboxing.”

## Bottom line

SWE-agent's enduring lesson is not “build a bigger agent framework.” It is that the model-facing interface, failure taxonomy, and final artifact review matter. Its best mechanisms are compact: parse and correct malformed actions, expose structured state, persist exact step evidence, and force a second look at the actual diff. Its weaker mechanisms—string blocklists, raw trajectory retention, sequential retries, LM-only judging, and a dedicated execution runtime—are actively mismatched to this owner.

The owner should evolve the current minimal shared bus with typed receipts and two targeted state machines. Full replacement with SWE-agent is **almost certainly not (1-5%)** the best architecture. Evidence: upstream has superseded it with a simpler system; our harness already exceeds it in MCP, memory, permissions, hooks, and real collaboration; and replacement would reintroduce a specifically rejected second runtime. Extracting the four narrow mechanisms above is **very likely (80-90%)** the higher-value path, with the evidence and settling experiments stated inline.
