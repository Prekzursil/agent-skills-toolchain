# N06 — capability discoverability / auto-routing: naming and findability

## Executive verdict

The catalog's main discoverability failure is not merely that some names are cute or obscure. It is that the compiled routing surface is not a trustworthy representation of the skill sources. Six of the 240 skill entries in the available semantic index have a literal YAML block-scalar marker (`>` or `>-`) as their entire description; the lexical index consequently reduces several of them to a name alone, and one generic name (`blueprint`) resolves to Airflow vocabulary while the decision router uses the same public name for a multi-session construction plan. These are externally observable compilation and identity failures, not subjective copy-editing disagreements.

The corpus then shows the user repeatedly having to act as the missing capability router: “weren't there skills…”, “you haven't found any OCR?”, and “use all information…tools, research, MCPs, plugins” occur among the correction candidates (`/local_disk0/codexwork/bundle/inputs/corpus.json:10493`, `:10713`, `:10745`). The correction miner is explicitly recall-biased and reported 41/41 false positives in an unfiltered smoke sample (`corpus.json:10373-10374`), so I use those sentences only as owner-intent signals, not as counts of confirmed routing failures. The stronger usage signal is exact: only 78 distinct skill labels were observed, 403 total invocations, while `deep-research` alone accounts for 70 (`corpus.json:13265-13267`; read-only parse command below).

The best replacement is therefore **not** another router. Keep progressive disclosure and the already-built semantic router, capability catalog, event ledger, and weekly harness bench. Turn catalog publication into a tested compilation pipeline: parse YAML correctly, assign collision-proof identities, compile task-language trigger cards, and admit a description only after held-out prompts retrieve the intended skill and reject its nearest confounders. Then personalize aliases from real owner language, but promote them only on future held-out interactions. This is **very likely (80-90%)** to improve findability because the local compiler defects are directly observed and independent ToolRet results show that retrieval quality controls downstream tool-task pass rate; the exact effect size here is **UNVERIFIED — the experiment is the chronological shadow A/B in Finding 1**.

No proposal adds a seventh hook. No proposal adds a second orchestration runtime, vector DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Runtime routing continues to fail open; publication/evaluation runs out of band and can fail closed without blocking a user turn.

### What “bad name/description” means in this unit

A description is not condemned merely for omitting the words “use when.” Of 240 excerpts, 174 contain “when,” 167 match a direct “use … when” form, and only 27 state an explicit negative/boundary phrase. These are screening counts, not quality verdicts. A capability is a demonstrated findability defect only when at least two independent signals agree: compiled metadata plus parser behavior; identity plus conflicting routing vocabulary; or held-out prompt retrieval plus an execution/owner signal. This prevents the same-context self-approval prohibited by the unit law.

## Findings — inferred-surprise first

Compile each source into `{stable_id, public_name, positive_intents, negative_intents, prerequisites, side_effect, source_hash}` and refuse to publish a new index unless its held-out retrieval contract is non-regressing.
- **what it is:** For every skill, create three to five task-language positives, two nearest-confounder negatives, and one “no capability needed” case in a sidecar fixture. Split chronologically: author/derive cases from older corpus prompts, freeze them, tune descriptions on the middle slice, and score exactly once on a later slice. Report Recall@5, reciprocal rank, wrong-sibling rate, no-route false-fire rate, prompt tokens, and p95 router latency. Keep the prior index atomically if parsing or evaluation fails. Runtime routing remains `try/except`, silent, and exit 0.
- **why-inferred:** The current bench has only 16 cases and accepts any member of broad clusters (`semantic-router/eval.py:9-13,33-146`); it therefore cannot tell whether `security-review` beats six neighboring security skills or whether a renamed skill remains individually findable. ToolRet independently shows conventional retrievers can perform poorly on tool retrieval and that retrieval errors reduce downstream pass rate ([Shi et al., ACL 2025](https://aclanthology.org/2025.findings-acl.1258/)). The owner asks for completeness but experiences forgotten tools; a publish gate removes the need to notice misses manually.
- **how-to-build:** Add `catalog_contracts.jsonl` beside the semantic index; update `build_index.py` to emit a temporary index with a complete source manifest; add a `--catalog-contracts` lane to the existing eval; have the existing weekly `harness-bench/bench.py` compare per-skill and aggregate metrics before `os.replace`. Use deterministic lexical/semantic rank outputs, not the model judging its own answer. Fold notification into the existing background digest only on a regression; no seventh hook.
- **EXTERNAL signal that verifies it:** A fresh process runs the frozen chronological test set against old and candidate indexes, then a real tool/skill invocation or owner correction in the later holdout settles selection success. Same-context model opinion never counts. Promotion requires no aggregate regression, no high-value skill regression, and lower wrong-sibling/no-route error with confidence intervals.
- **SOTA citation:** ToolRet supplies the retrieval/task-success link and a 7.6k-task/43k-tool evaluation design ([ACL 2025](https://aclanthology.org/2025.findings-acl.1258/)); NIST says accuracy needs realistic test sets, human-AI teaming measures, and external validity ([NIST AI RMF](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).

- **novelty:** inferred-surprise

### 2. UNVERIFIED — Learn the owner's task vocabulary without asking the owner to become the catalog

- **improvement:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — add a personalized alias lane to the semantic router's existing index builder and selection-event analysis, not a new memory store or hook.
- **what it is:** Compile privacy-preserving phrases from confirmed successful prompt→capability pairs into aliases attached to the canonical capability. Examples of owner language already visible are “weren't there skills…fully automatize apps,” “haven't found any OCR,” and “use all information…tools…MCPs…plugins” (`corpus.json:10493,10713,10745`). Do not save full prompts. Store normalized n-grams only after an external successful invocation/receipt, decay them, and keep global descriptions portable.
- **why-inferred:** The owner naturally describes outcomes, not product names. Existing descriptions often lead with vendor nouns (`010-editor`, `rtv-pdr`, `gateguard`) while the router indexes name and description language. Proactive-personalization research argues productivity, proactivity, and preference adaptation must be optimized jointly, not task completion alone ([Sun et al., 2025](https://arxiv.org/abs/2511.02208)). This gives the owner personalization without repeated preference interviews or prompt fatigue.
- **how-to-build:** Read already-recorded selection events and invocation receipts; for a successful selection, extract bounded, redacted 2-5 grams from the initiating owner turn, excluding paths, secrets, IDs, and stop words. Add aliases only when they recur in two separate sessions or receive explicit owner use; write them to the existing catalog data file with support count and last-seen timestamp. The semantic/lexical router consumes aliases as low-weight text. Never let aliases change permission or side-effect boundaries.
- **EXTERNAL signal that verifies it:** Backtest on future, chronologically later owner prompts that were never used to form aliases; count rank lift for the actually invoked capability and owner “wrong/missed tool” corrections. A tool execution receipt is one signal; an owner accept/override or independent later-session replay is the second.
- **SOTA citation:** UserVille/PPP evaluates agents on productivity, proactivity, and personalization and reports gains on software-engineering and deep-research tasks ([arXiv 2511.02208](https://arxiv.org/abs/2511.02208)); NIST requires metrics representative of expected-use conditions ([NIST AI RMF](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).
- **value x effort:** high x medium
- **novelty:** inferred-surprise
- **autonomy:** just-do-it
- **confidence:** **likely (55-80%)**, because real owner language and exact invocation telemetry exist, but causal attribution of current misses is unavailable. This recommendation is **UNVERIFIED — the future chronological rank-lift plus correction-rate experiment settles it**.

### 4. UNVERIFIED — Treat proactive suggestions as scarce interruptions, not free context

- **improvement:** **CONFIG (settings/JSON only)** for thresholds and quiet policy, plus a small data change in the existing router output; no new hook.
- **what it is:** Use a three-band intervention policy: high-confidence, low-risk route silently; ambiguous high-value route shows at most one terse “using X because Y” line; low-confidence route abstains. Never ask the owner to choose among near-duplicate skills unless choice changes side effects, cost, or artifact. Keep the current per-session dedup (`skill-router/route.py:139-154,205-215`) but add an interruption budget and negative-query calibration.
- **why-inferred:** Prompt fatigue is explicitly a hard constraint, and the capability catalog already says its `WHEN` clause is load-bearing (`capability-catalog/catalog.json:2-4`). Research on proactive support finds timing matters: help delivered at actual struggle is more beneficial than help too early, too late, or misaligned ([CHI 2026](https://doi.org/10.1145/3772318.3791191)). The 2026 confirmation-frequency study reports 81% preferred intermediate confirmation and a 13.54% completion-time reduction, but only when checkpoints were placed decision-theoretically rather than everywhere ([Georgia Tech / CHI 2026](https://tail.cc.gatech.edu/publications/zhou-chi-2026/)).
- **how-to-build:** In the existing router JSON/config, define `auto_use_threshold`, `explain_threshold`, `abstain_threshold`, `max_visible_nudges_per_session`, and a risk override. Calibrate on positive prompts plus mundane acknowledgements, side questions, and already-in-progress threads. Route explanations name the external match evidence (trigger phrase/path/tool availability), not a model confidence monologue. Errors catch and return no injection/exit 0.
- **EXTERNAL signal that verifies it:** A frozen negative suite measures false visible nudges; event-ledger reactions measure accept/dismiss/override; later task receipts measure whether silent high-confidence routing invoked the right capability. Owner focus cost is measured as visible nudge count and interruption/override rate, not inferred by the same model.
- **SOTA citation:** Timing/personalization evidence comes from the CHI 2026 proactive-support study ([DOI](https://doi.org/10.1145/3772318.3791191)); confirmation burden versus recovery cost comes from the CHI 2026 decision model ([project page](https://tail.cc.gatech.edu/publications/zhou-chi-2026/)); NIST recommends calibrating controls with HCI/human-AI teaming expertise ([NIST Measure playbook](https://airc.nist.gov/airmf-resources/playbook/measure/)).
- **value x effort:** high x low
- **novelty:** inferred-surprise
- **autonomy:** just-do-it
- **confidence:** **likely (55-80%)**, because external timing studies and the local fatigue constraint align, but optimal thresholds are user-specific. This is **UNVERIFIED — the shadow interruption-budget experiment settles thresholds before enabling visible changes**.

## Priority and architecture decision

1. Fix block-scalar parsing and publish a source-complete manifest (Findings 5 and 8).
2. Introduce stable IDs/collision reporting before any rename (Finding 3).
3. Add per-skill frozen contrast tests to the existing weekly bench (Finding 1).
4. Rewrite only descriptions that fail exact-sibling tests, preserving aliases (Finding 6).
5. Add receipt-backed personalized aliases and a calibrated interruption budget in shadow mode (Findings 2, 4, and 7).

This sequence is **very likely (80-90%)** to avoid treating compiler bugs as prose problems because parsing/identity are verified before wording changes. The evidence is the observed scalar-marker outputs, first-wins dedup, and the broad-family eval acceptance. It also satisfies the anti-overfit gate: a small compiler/linter and fixtures ride the existing buses; there is no new retrieval service or runtime.

## Alternatives considered and rejected

- **Inject all 355 descriptions every turn:** rejected. It worsens prompt fatigue and contradicts progressive disclosure; the prior audit claims Codex already degraded to names-only under its skill budget (`audit-findings/B03.md:8-22`).
- **Add another proactive hook:** rejected. The existing UserPromptSubmit router and SessionStart catalog are the right bus, and the ~6-hook ceiling prohibits gratuitous expansion. Every runtime change above folds into those paths.
- **Train a critic or bespoke retriever:** rejected. ToolRet shows retrieval is hard, but the local catalog first has deterministic parse, identity, and evaluation defects. A trained component would violate the anti-overfit gate before simpler causes are removed.
- **Put `triggers:` into shared skill frontmatter:** rejected. The earlier audit found the current shared validator permits only portable AgentSkills keys and would reject provider-specific trigger fields (`audit-findings/D14.md:55-62`). Use descriptions plus sidecar test contracts.
- **Automatically rename opaque skills from an LLM review:** rejected. Names are API-like public identifiers; changing them without reference search and redirects can break explicit invocations. A second model can draft, never certify.
- **Use invocation count as proof a skill is useless:** rejected. Non-use can mean poor discovery. The corpus supports use counts, not causal reasons for non-use.

## Bottom line

Naming is currently a reliability surface, not cosmetics. Six descriptions are mechanically mistranslated; at least one public name denotes two incompatible capabilities; broad-family evaluation hides wrong-sibling selection; and catalog counts cannot be reconciled without provenance. The ambitious but minimal answer is a tested catalog compiler with collision-proof IDs, contrastive trigger contracts, receipt-backed owner-language aliases, and a strict interruption budget. It builds on what exists, creates no new hook/runtime, fails open during user work, and closes every correction on evidence outside the context that made the mistake.
