# G010 — Failure-mode inventory: tool-result detector regression

**Unit:** G010  
**Question:** Why did `tool-result-sentinel` return to false `FAILED` verdicts after it had already been patched for that class?  
**Snapshot inspected:** unpacked read-only subject at `/local_disk0/codexwork/bundle`; the live Windows paths were not available on this Linux job node. SHA-256 of the inspected sentinel was `f42d80e3f28ccdc66e259a419118772edcf2fd63713e9bacbbcc83301224b790`; its direct test file was `7fbe4a9a3b96a584653cb36fe8c2189f7be6700e3c3e62ea9002b2755ef3734c` (command output, 2026-07-19 UTC).

## Executive verdict

This is not two unrelated bad regular expressions. The recurring failure is a missing **typed outcome contract** at the tool-result boundary.

The sentinel accepts heterogeneous process, HTTP, MCP, and application envelopes, then tries to infer one three-valued verdict from (a) overloaded field names and (b) a flattened text blob. The prior WebFetch repair reportedly distinguished HTTP status from process exit status, but it did not remove the underlying type erasure. A later path therefore reached the same false-`FAILED` state by matching `timedout` inside the serialized JSON key `user_cancelled_or_timedout` even though its value was `false` and the surrounding call said `ok: true` (`inputs/INPUT-known-harness-defects.md:63-72`). The inspected implementation still contains both routes: it treats `status_code` as a process exit code (`claude/hooks/tool-result-sentinel/sentinel.py:218-239`) and searches flattened MCP result text with an unanchored failure-phrase regex (`sentinel.py:77-92,163-196,271-278`).

The reason these failures come back is therefore structural:

1. No canonical typed result model says which producer owns each field and what that field means.
2. No explicit evidence-precedence lattice handles contradictory signals.
3. Text fallback scans serialized representation rather than semantic values.
4. The regression suite tests examples, not invariants; it has no HTTP-200, false-valued failure-key, contradiction, or serialization-invariance case (`test_sentinel.py:59-171`).
5. The warning throttle is keyed only by `(session, tool, args)`, not the classified response. A false positive can consume the warning slot and suppress a later real failure for the same call shape (`sentinel.py:110-121,316-320`). I reproduced exactly that sequence; details are in rank 1 below.

The structural replacement is a small, typed normalizer and verdict algebra on the existing hook bus, plus invariant/property tests and a response-aware dedupe key. It does not require another orchestration runtime, database, daemon, trained critic, SaaS, durable-execution engine, or guardrail framework.

## Ranked inventory by expected damage

Ranking is by how badly the failure can corrupt decisions, not by how often it occurred. “Observed” means the live-operations defect record or a historical operational note records an actual event. “Reproduced” means this unit demonstrated the current pure/hook behavior without claiming it occurred in production.

### 1. False `FAILED` consumes the throttle key, then a genuine failure is silent

**Status:** current mechanism reproduced; no production occurrence claimed.  
**Expected damage:** CRITICAL — a visible false alarm primes a later invisible miss.  
**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

#### Mechanism

The fingerprint is SHA-256 of `tool_name + NUL + args_hash`; response, verdict, reason, and tool-use ID do not participate (`sentinel.py:110-121,316-320`). `_already_warned` suppresses any later non-success verdict sharing that key (`sentinel.py:132-160,318-320`). Consequently, a false `FAILED` and a true `FAILED` with the same session/tool/arguments collide.

#### Reproduction

I invoked the bundled hook twice with session `g010`, tool `mcp__databricks__run`, and input `{"job": 7}`:

1. Response: `ok: true` plus text `{"user_cancelled_or_timedout": false, "ok": true}`. Output contained a `FAILED` warning for reason `infra-failure text: 'timedout'`.
2. Response: `isError: true` plus text `actual authentication failure`. Output was the empty string.

The temporary warning-state file contained one fingerprint. This is mechanically independent of the source read: it exercised the subprocess entrypoint, stdout protocol, filesystem throttle, and a changed second response.

#### Preconditions

All are required:

- same `session_id`;
- same tool name and normalized arguments;
- first response is falsely classified non-success;
- a later response for that call shape is genuinely non-success;
- warning state persists and has not aged out of the 400-entry list.

This sequence is **likely (55-80%)** to occur eventually on retryable/polling APIs because retries deliberately reuse tool and arguments, while the current false-positive route is proven on a Databricks result. The evidence does not establish a production rate, so a narrower band would be unjustified.

#### Detection signal

Join sentinel decisions by session/tool/args and compare successive normalized response hashes. Signal a defect when a suppressed response has a different authoritative failure tuple (`isError`, `success`, `ok`, `status`, exit status, HTTP status) from the response that created the warning key. A direct regression test is: false-positive fixture first, true `isError` fixture second, and assert the second warning is emitted.

#### Structural fix

Key deduplication by `(session_id, tool_use_id when present, verdict, canonical_reason_code, canonical_failure_signature)`. If `tool_use_id` is absent, include a stable hash of only authoritative outcome fields, not the whole potentially sensitive output. Do not allow an `AMBIGUOUS`/legacy-text warning to suppress an authoritative `FAILED` warning.

This fix is **very likely (80-90%)** to prevent cross-response suppression because the reproduced collision disappears when the changed outcome signature participates; evidence is the exact current key construction and the two-call reproduction. A shadow replay of real repeated calls is still required before claiming no unacceptable warning amplification.

### 2. Transport success overrides explicit application failure: silent false `SUCCESS`

**Status:** current mechanism reproduced; independently reported by audit F08.  
**Expected damage:** CRITICAL — the detector stays silent and downstream completion logic can build on a failed result.  
**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

#### Mechanism

`_structural_failed` iterates numeric fields first. On the first numeric zero it immediately returns `False`, before checking `isError`, `success`, `ok`, `status`, or `error` (`sentinel.py:218-253`). Thus transport/process success is not merely evidence of success; it vetoes stronger application-failure evidence.

#### Instances and evidence

- This unit reproduced `{"exit_code": 0, "success": false} => ("SUCCESS", "")`.
- This unit reproduced `{"exit_code": 0, "error": "application failed"} => ("SUCCESS", "")`.
- Audit F08 independently recorded the same two pure-function outcomes and cites the active deployed copy (`inputs/audit-findings/F08.md:7-13`).

These are reproduced code paths, not claimed live user-visible events. The adjacent shared receipt bus can persist contradictory verified/pass evidence according to F08 (`F08.md:15-21`), but that is neighbouring work and is not reinvestigated here.

#### Preconditions

- A response carries an explicit numeric zero in one of the recognized numeric keys.
- A sibling or later-recursed field carries explicit failure.
- The zero is encountered before the failure in the sentinel’s fixed field-precedence routine.

#### Detection signal

For every envelope, collect all authoritative signals before deciding. Emit a contradiction counter when both success and failure signals occur. Golden cases must include exit-0 plus each of `isError=true`, `success=false`, `ok=false`, `status=error`, and nonempty `error`.

#### Structural fix

Use fail-dominant aggregation rather than early returns:

`authoritative failure > contradiction/unknown > authoritative success > no evidence`.

An exit code of zero is process-layer success only; it cannot erase application-layer failure. Contradiction should be represented explicitly in telemetry and injected as `AMBIGUOUS` unless a specified layer-precedence rule resolves it. MCP `isError=true` is authoritative for MCP execution errors under the official MCP tool-result contract, which also provides typed `structuredContent`; see the [MCP tool-result specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

This change is **almost certain (90-99%)** to fix the listed contradiction fixtures because it directly removes the early success return; evidence is the exact branch ordering and pure-function reproductions. It is only **likely (55-80%)** to cover every producer envelope until a captured production-envelope corpus is replayed, because vendor-specific wrappers are not fully inventoried on this job node.

### 3. Successful Databricks result declared `FAILED` from a false-valued field name

**Status:** observed live on 2026-07-18 and reproduced against the bundled classifier.  
**Expected damage:** HIGH — direct corruption of the agent’s world model; the warning explicitly orders it not to build on successful output.  
**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

#### Observed instance

The live-operations defect record says a Databricks API result contained `"user_cancelled_or_timedout": false`, the call also returned `ok: true`, and the sentinel matched `timedout` in the field name. Its injected instruction told the agent to discard the successful result and not build on its output (`INPUT-known-harness-defects.md:63-76`). That input states the four defects were observed during real operation and diagnosed with two independent signals (`INPUT-known-harness-defects.md:1-5`).

#### Mechanism

For MCP names, `_gather_text` recursively collects selected strings and concatenates them (`sentinel.py:163-196`). `_INFRA_FAIL` then searches this untyped blob (`sentinel.py:77-92,271-278`). MCP’s compatibility contract explains why this route is normal rather than exotic: typed `structuredContent` may also be returned as serialized JSON in text content for backward compatibility ([MCP tool-result specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). Once JSON becomes text, keys, values, negation, and prose all become indistinguishable substrings.

I reproduced:

- JSON serialized in `content[].text` with the false-valued key: `FAILED`, reason `timedout`.
- The semantically equivalent typed nested dictionary: `SUCCESS`.

That pair proves a serialization-dependent verdict. The classifier judges representation, not outcome.

#### Preconditions

- MCP tool name starts with `mcp__`.
- Result includes a selected text-bearing path or serialized JSON string.
- A key, value, or prose mention contains a regex phrase such as `timedout`.
- No earlier structural branch returns first.

#### Detection signal

A metamorphic test must assert **serialization invariance**: a typed object and its canonical JSON text representation yield the same verdict. A polarity test must assert that changing `user_cancelled_or_timedout` from `false` to `true` is outcome-relevant, while the key alone is not. Production telemetry should record a non-sensitive reason code and the JSON path of the deciding value; a decision attributed only to `text-regex` is a degraded-confidence signal.

#### Structural fix

Never regex-search raw serialized JSON for `FAILED`. Prefer, in order:

1. Native hook event outcome and typed host fields.
2. MCP `isError` and typed `structuredContent`.
3. Tool-family adapter for documented typed fields.
4. If text parses as JSON, parse it and classify semantic values/paths.
5. Only for genuinely unstructured legacy text, map strong infrastructure phrases to `AMBIGUOUS`, not `FAILED`, unless the producer contract explicitly makes that text authoritative.

This is **very likely (80-90%)** to eliminate the observed false verdict because the deciding key name is excluded and its boolean value is preserved; evidence is the typed-vs-serialized reproduction and MCP’s dual representation contract. It is not “almost certain” until the exact captured live payload is in the fixture corpus.

#### Preconditions

- Result contains a numeric `status_code`.
- Value is any nonzero integer, including successful HTTP 2xx.
- That key is reached before another numeric zero causes early success.

#### Detection signal

Field-domain matrix tests: process `exit_code/returncode` use zero/nonzero semantics; HTTP `http_status/status_code` use HTTP classes; ambiguous `code` must not be interpreted without a producer adapter. A wire check should hash-compare the canonical implementation and deployed hook rather than merely checking that a file is registered.

Delete generic numeric-field interpretation. Require a typed adapter to map a raw field to `ProcessExit`, `HttpStatus`, `RpcErrorCode`, or `UnknownNumericCode`. HTTP 2xx is transport success, 4xx/5xx transport/application failure, and redirects require tool-contract-specific handling. A bare `code` remains unknown absent a schema.

This change is **almost certain (90-99%)** to stop HTTP 200 from becoming “exit code 200” because the domains can no longer alias; evidence is the exact current alias list and reproduction. Deployment drift prevention is separately required or an older copy can return.

### 5. Phrase scanning can classify mention, negation, or data as infrastructure failure

**Status:** class observed via the Databricks field-name instance; additional triggers are current reachable code paths, not individually observed.  
**Expected damage:** HIGH when output is decision-bearing, otherwise MEDIUM noise.  
**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

#### Mechanism and reachable instances

The regex includes phrases such as `not connected`, connection errors, timeout forms, `tool not found`, `no tools available`, `503`, `internal server error`, and `failed to execute/invoke/call` (`sentinel.py:77-92`). `_gather_text` does not preserve whether a phrase is:

- a JSON key;
- a false-valued flag;
- a quoted log line;
- a statement that a test correctly detected such text;
- documentation returned by a search/read tool;
- a negated statement;
- the actual producer error.

Only the Databricks key-name route is an observed sentinel instance. The broader “use versus mention” class is independently observed across other guards in the defect input (`INPUT-known-harness-defects.md:9-62`), supporting the architectural diagnosis but not proving each sentinel phrase fired.

#### Preconditions

- MCP name prefix;
- matching text in one of the selected text paths;
- no earlier structural decision;
- phrase regex match regardless of semantic role.

#### Detection signal

Counterexample suite for every phrase family: actual error, quoted error, negated error, false-valued key, documentation paragraph, and successful diagnostic result. The detector must expose the deciding JSON path and evidence type (`authoritative-field`, `parsed-structured`, `legacy-text`) so field-name/prose decisions are detectable.

#### Structural fix

Demote legacy phrase matching to an `AMBIGUOUS` compatibility adapter, after JSON parsing and only on explicitly human-message fields. Do not scan `data`, `body`, arbitrary `result`, or tool-returned documents for definitive failure. Producers that repeatedly return plain-text failures should get a narrow named adapter or be repaired to emit MCP `isError=true`, not expand a global regex.

This is **likely (55-80%)** to reduce false alarms materially because the observed false key and the cross-guard mention failures all bypass definitive failure; evidence is the selector/regex source and live defect roster. Exact reduction is **UNVERIFIED; experiment to settle it:** replay a redacted sample of successful and failed MCP envelopes through old and proposed classifiers and adjudicate disagreements.

### What it does not cover

## Structural replacement design

### Proposal A — Canonical typed `OutcomeEvidence` normalizer

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Replace `_structural_failed` and `_gather_text`-driven definitive classification with a pure normalizer that returns evidence records, for example:

```text
OutcomeEvidence {
  layer: host | process | http | mcp | application | legacy_text
  polarity: success | failure | unknown
  authority: authoritative | adapter | heuristic
  code: stable non-sensitive reason code
  path: JSON path or native event field
}
```

Adapters are selected by native event and tool family. Unknown fields remain unknown. Do not infer semantics from a generic key named `code` or `status` without an adapter.

For Claude, use the native lifecycle as one transport-layer signal: the official hooks reference defines `PostToolUse` as after a tool call succeeds and `PostToolUseFailure` as after it fails, and the bundled settings register the shared dispatcher for both (`claude/settings.json:310-320,356-364`; [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)). This does not replace application-result parsing, because a transport-successful MCP call can still carry typed `isError=true`; it supplies the missing layer identity.

This design is **very likely (80-90%)** to prevent field-domain aliasing and serialization-dependent outcomes because type and source path become mandatory evidence; the two current reproductions directly exercise those missing distinctions.

### Proposal B — Explicit verdict lattice and contradiction state

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Reduce collected evidence only after the full envelope is traversed:

```text
authoritative failure
  > contradictory authoritative signals (AMBIGUOUS + telemetry)
  > authoritative success
  > adapter evidence
  > legacy-text heuristic (AMBIGUOUS only)
  > no evidence (SUCCESS only for a native-success event; otherwise AMBIGUOUS)
```

No success branch may return before failure evidence is collected. Preserve `SUCCESS / FAILED / AMBIGUOUS` at the hook output boundary so callers need not change immediately.

This is **almost certain (90-99%)** to fix exit-0 masking explicit failure because failure aggregation replaces the exact early return that causes it. The correct treatment of every contradictory vendor envelope remains **UNVERIFIED; experiment to settle it:** capture and adjudicate at least one real fixture per active high-volume tool family before enforcement.

### Proposal C — Parse structured content; quarantine global text regex from definitive verdicts

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Read MCP `isError` and `structuredContent` first. If TextContent is valid JSON, parse it and run the same typed adapter, giving typed and serialized forms identical decisions. Restrict unstructured fallback to explicit message/text leaves and return `AMBIGUOUS`; record `legacy_text` as evidence authority. Do not scan arbitrary documents, data bodies, keys, or serialized payloads for `FAILED`.

This is **very likely (80-90%)** to fix the observed `user_cancelled_or_timedout=false` case because it makes the boolean, not the key spelling, outcome-bearing. A replay experiment is still required for legacy MCPs that violate the official `isError` contract.

### Proposal D — Response-aware warning dedupe

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Fingerprint the normalized failure signature and tool-use ID where available. Maintain precedence so a prior heuristic/ambiguous warning can never suppress a later authoritative failure. Keep the existing bounded per-session store; no new service is needed.

This is **very likely (80-90%)** to eliminate the reproduced throttle poisoning; the remaining uncertainty is acceptable noise under high-frequency identical but differently worded failures, measurable during shadow rollout.

### Proposal E — Invariant and mutation regression gate

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add table-driven and property/metamorphic tests to the existing test file or shared harness quality lane:

1. **Failure dominance:** adding `exit_code=0`, HTTP 200, or `ok=true` cannot turn authoritative failure into success.
2. **Serialization invariance:** typed JSON and canonical JSON TextContent have the same verdict.
3. **Boolean polarity:** a failure-named key with `false` does not fail; the documented true form does according to its adapter.
4. **Irrelevant-field invariance:** adding unknown fields or prose does not change authoritative verdict.
5. **Domain separation:** process exit, HTTP status, RPC code, and application code cannot alias.
6. **Contradiction preservation:** contradictory authoritative signals become explicit, never order-dependent.
7. **Throttle monotonicity:** a heuristic/false fixture cannot silence a later authoritative failure with the same tool/args.
8. **Native-event coherence:** PostToolUseFailure cannot normalize to success; PostToolUse plus MCP `isError=true` remains application failure.

Seed the fixture corpus with the two observed regressions and the F08 contradiction probes. Run mutation tests that swap field order, wrap/unwrap `result` and `output`, and serialize/parse JSON. Registration tests remain separate from semantic tests.

This gate is **very likely (80-90%)** to stop the same semantic class from re-entering through another field/order/serialization route because it constrains laws rather than remembered spellings; evidence is that the current example suite passes while all listed invariants have counterexamples.

### Proposal F — UNVERIFIED: canonical ownership and deploy hash parity

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The small wire-check also reads a settings/JSON declaration of the canonical path and expected hash; that declaration does not create a second proposal or runtime.

The current bundle proves registration but cannot establish why an `_http_status` fix recorded in memory is absent from the inspected source. A semantic test on the deployed file plus hash parity is stronger than a file-presence check. Fail the quality gate on mismatch; at SessionStart, inject a bounded degraded-protection notice rather than silently choosing a copy.

This proposal is **likely (55-80%)** to prevent old-copy resurrection because it detects byte drift across known deployment locations. The benefit depends on provenance being part of the actual recurrence, which is **UNVERIFIED; experiment to settle it:** the Windows history/hash comparison named above.

## Rollout experiment and acceptance criteria

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Use the existing PostToolUse dispatcher; do not add a daemon.

1. Build a redacted fixture corpus from actual envelopes for WebFetch, Databricks, basic-memory, shell, and the highest-volume MCP families. Preserve field names/types and outcome flags; redact content.
2. Run old and new classifiers in shadow on the same events. Persist only verdict, reason code, evidence layer/path, response-shape hash, and disagreement category.
3. Manually adjudicate every disagreement in the seeded observed fixtures and a stratified production sample.
4. Require all invariant tests above to pass.
5. Canary only injection, not blocking; the sentinel is already inject-only (`sentinel.py:42-44,335-346`).
6. Promote after zero known false `FAILED`, zero authoritative false `SUCCESS`, and zero throttle-poisoning failures in the adjudicated set. Do not claim a universal zero-error detector from a finite sample.
7. Keep legacy-text decisions `AMBIGUOUS` until each producer either emits typed failure or receives a named adapter.

The shadow comparison is **very likely (80-90%)** to reveal schema gaps before user-visible promotion because both verdicts see identical envelopes and every disagreement carries a typed reason. It cannot prove correctness without adjudication; that is why adjudication is an acceptance gate, not optional telemetry.

## Anti-overfit gate

All counted proposals ride the existing Claude/shared PostToolUse/PostToolUseFailure bus and are a small pure classifier, tests, or configuration. None adds a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The design replaces heuristic complexity with fewer concepts: typed adapters, evidence aggregation, and invariants.

A per-tool adapter registry can itself sprawl. Constrain it to fields backed by a producer contract or captured fixture; unknown producers fall back to `AMBIGUOUS` rather than acquiring speculative rules. This keeps the hot path and conceptual surface small as models and tool fleets change.

## Alternatives considered and rejected

### Tune `_INFRA_FAIL` boundaries or add a negative lookbehind

Rejected. A word boundary could suppress `timedout` in one key spelling but not JSON keys such as `timeout`, quoted error documentation, negation, or the next status alias. It preserves representation-dependent classification and repeats the failed patch pattern.

## Final answer to “why do these come back?”

They come back because the harness patched symptoms in an untyped, open-world classifier. HTTP status, process exit, MCP status, application flags, JSON keys, JSON values, and prose still share one heuristic decision surface. The tests memorialize examples rather than enforce semantic laws, and deployment parity is not proven. A different field or representation can therefore recreate the same wrong verdict without touching the prior patched branch. The current throttle then compounds that false verdict by letting it suppress a later real failure.

Replace the decision surface with typed evidence, fail-dominant aggregation, serialization invariance, and response-aware dedupe; enforce those as properties on the existing bus. That is the smallest structural fix that addresses recurrence rather than the latest spelling.
