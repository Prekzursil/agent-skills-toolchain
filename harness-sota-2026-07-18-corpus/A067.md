## Executive result

The Swift hook rule is not a description of the deployed harness. It is a 20-line recommendation copied into a path-scoped rule, but none of its four observable behaviors is implemented for Swift by the active user-level hook registrations:

1. no Swift formatter is registered;
2. no SwiftLint invocation is registered;
3. no `swift build` invocation is registered; and
4. the registered per-edit validator silently treats `.swift` and `Package.swift` as unsupported and therefore never flags `print()`.

That conclusion is **almost certain (90-99%)**, based on two mechanically independent signals: (a) parsed `settings.json` and the local dispatcher manifest contain no Swift command or Swift-specific route (`settings.json:310-354`; `_dispatch/manifest.json:144-180`), and (b) the implementation's extension dispatcher ends with an empty success for unknown extensions (`per-edit-check/check.py:151-170`), reproduced by a read-only import probe returning `([], False)` for both `Probe.swift` and `Package.swift`. This is an absence in the *deployed configuration represented by the bundle*, not a claim that no plugin outside the bundle could ever add a hook.

More importantly, wiring the prose literally would recreate a design the harness has already rejected. `hooks.md:14-16` asks for three checks “after edit,” while the installed validator's postmortem says per-edit validation caused a degenerate wake loop and was replaced by one validation pass at the Stop boundary (`hooks/edit-validate/README.md:1-18`; `validate-stop.py:1-21`). The measured corpus also contains 132 occurrences of “File has been modified since read, either by the user or by a linter” (`corpus.json:4514-4521`), 125 attributed specifically among Edit failures (`corpus.json:8937-8945`). It is **likely (55-80%)** that mutating post-edit formatters are one contributor to that broad error class, because the error explicitly names a linter and the proposed formatter changes a just-read file; this is **UNVERIFIED for Swift**. The settling experiment is to correlate raw transcript Edit tool-use IDs and file paths with immediately preceding/following formatter hook receipts, split by extension and formatter, then compare stale-read failures with the formatter disabled in an A/B session.

The best resolution is therefore not to add three literal commands to `settings.json`. It is to replace this rule with a small, project-aware, once-per-turn Swift validation policy on the existing hook bus: record touched Swift files on PostToolUse; at Stop or through the existing `longrun` wrapper, run the repository-declared formatter in check/lint mode, SwiftLint on touched files, and one package-root build; emit typed pass/fail/skip receipts; keep actual formatting an explicit edit or project opt-in. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This does not add a second orchestration runtime, vector store, durable-execution engine, trained critic, SaaS, or guardrail framework, and therefore passes the anti-overfit gate.

```markdown
# Swift validation hooks

This file extends the common hook policy. AGENTS.md §4a and §6 govern timeouts,
background execution, fail-open behavior, and block-vs-inject semantics.

## Lifecycle

- PostToolUse(Edit|Write|MultiEdit): record the touched Swift file only.
- Stop: group touched files by owning project/package root and validate each root once.
- If a validation is expected to exceed 60 seconds, use `longrun`; never block the
  foreground tool call.

## Project-native tool selection

- Use the formatter and linter already pinned/configured by the repository.
- Prefer non-mutating formatter check/lint mode. Auto-format is project opt-in; after
  mutation, tell the agent the file must be re-read.
- Run SwiftLint on touched production files when the project declares SwiftLint.
- For SwiftPM, run one `swift build --package-path <root>` per affected package. For
  Xcode-only projects, use the repository's existing build entrypoint instead.
- Emit typed PASS / FAIL / SKIP_NO_TOOL / SKIP_NO_CONFIG / ERROR receipts. Ordinary
  format, lint, or build findings inject guidance; hook faults fail open.

## Logging calls

Treat `print()` as advisory unless a repository policy identifies production targets
and supplies an AST/linter-backed rule. Do not regex-scan comments, strings, docs,
tests, or CLI targets as production logging violations.
```
