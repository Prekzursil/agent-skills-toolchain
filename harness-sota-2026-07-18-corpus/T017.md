# T017 — Competitive teardown: Replit Agent

**Unit:** T017  
**Research date:** 2026-07-19 UTC  
**Subject:** Replit Agent 4, with Agent 3 engineering disclosures where they describe still-relevant internals  
**Scope:** agent loop, context, memory, tools/MCP, permissions, customization, multi-agent execution, verification, and porting implications for the owner's Claude/Codex harness  
**Write boundary:** the unpacked subject was read-only; this artifact is the only subject-adjacent output.

## Executive verdict

Replit Agent is not a generally better replacement for this owner's harness. It is a vertically integrated software-building product whose best behavior comes from owning the editor, compute sandbox, browser, Git history, development database, credential broker, and deployment surface together. The owner's harness is much broader: its corpus records 78 invoked skills, 22 agent types, and 93 MCP servers, while its Claude configuration exposes a real event-hook bus and cross-tool behavior contract (`/local_disk0/codexwork/bundle/inputs/corpus.json:13265-13395`; `/local_disk0/codexwork/bundle/claude/settings.json:81-520`; `/local_disk0/codexwork/bundle/codex/AGENTS.md:1-85`). Replit is the cleaner product; ours is the more programmable harness.

The parts worth porting are narrower and more consequential than copying Replit wholesale:

1. **Selective decision-time guidance — BUILD-SMALL.** Replit classifies the live trajectory and injects one ephemeral micro-instruction only when relevant. This is a direct answer to our overgrown static rules and noisy hooks. The mechanism belongs in the existing `PreToolUse`/`PostToolUseFailure` bus, not in a second runtime.
2. **A fresh-context behavioral verifier — CONFIG first, BUILD-SMALL only for a persistent browser notebook.** Replit splits testing from coding, passes a high-level test plan into a separate subagent, lets it manipulate a real browser through Playwright code, and returns only a compact verdict. Ours already has agents and Playwright; the missing piece is a standard verifier contract and automatic trigger.
3. **MCP connection health and circuit breaking — BUILD-SMALL.** Replit tests a custom MCP before saving it and exposes connection status. Our corpus shows a dead Tavily endpoint repeatedly called and failing “not connected” 135 times (`corpus.json:9141-9149`). A tiny health registry that removes failed servers from routing until a successful probe would address measured damage.
4. **Isolated, review-before-apply task branches — NATIVE plus CONFIG.** Claude/Codex already support agents/worktrees; standardize Replit's Draft → Active → Ready → Done contract, explicit definition of done, test evidence, and human apply/dismiss decision. Do not build a Kanban service.
5. **Risk-tiered approval — CONFIG.** Replit reserves human confirmation for deploys, secret changes, outbound calls, and tools that declare confirmation. Our current Claude settings use `defaultMode: "bypassPermissions"` with an empty `ask` list (`settings.json:26-75`). Keep low-risk autonomy, but reinstate explicit approval at trust-boundary crossings.

The exact Replit snapshot engine is **not** a good port. Exact parity would be **BUILD-LARGE**: copy-on-write block storage, append-only Git recovery, versioned PostgreSQL, isolated compute, and synchronized conversation state. That violates the anti-overfit gate by introducing platform-scale durable execution/storage machinery. Use Git worktrees and application-native database snapshots where available; do not create a Replit clone around the harness.

Overall assessment: **very likely (80-90%)** that adopting the first three small mechanisms will reduce real harness failure and rework, because each targets a measured local defect and each has a directly corresponding Replit production mechanism. The remaining uncertainty is effectiveness on this owner's Windows traces; settle it with a 100-task shadow evaluation comparing retry-loop count, false guidance, verification catches, latency, and tokens against the current harness.

## 1. Agent loop

### What Replit actually runs

At the product level, the loop is goal → plan/tasks → tool-mediated build → run/test → diagnose → repair → checkpoint → present for review. Plan mode is read-only and requires “Start building” approval; Build mode writes files and changes the app ([Plan vs. Build](https://docs.replit.com/learn/plan-vs-build-mode)). In Agent 4, planning no longer blocks all building: separate planning threads can create tasks while other tasks execute. Each background task receives an isolated project copy and does not touch main until explicitly applied ([Agent 3 → 4](https://replit.com/blog/whats-changed-agent3-to-agent4); [Task system](https://docs.replit.com/core-concepts/agent/task-system)).

Within a task, Replit's verification disclosure describes the usual action → observe → repeat loop. The main agent can start a testing subagent with a high-level plan; that subagent explores and manipulates the browser, decides when testing is complete, and summarizes what works and what broke back to the main agent ([REPL-based self-testing](https://replit.com/blog/automated-self-testing)). App Testing then permits automatic self-correction before handoff ([App Testing](https://docs.replit.com/features/agent/app-testing)).

Agent modes are explicit cost/capability routing controls: Lite, Economy, Power; High effort selectively invokes more capable frontier models for hard portions; Turbo trades cost for latency. Replit states that code review now happens automatically rather than through the former Code Optimizations toggle ([Agent modes](https://docs.replit.com/features/agent/agent-modes)). **UNVERIFIED** whether mode selection changes only models or also prompts, tool budgets, and loop limits; settle it by replaying an identical instrumented task in every mode and comparing tool trace, context size, stopping condition, and resulting diff.

### The frontier mechanism: decision-time guidance

Replit's most important harness disclosure is its January 2026 decision-time control layer. Static rules degrade on long trajectories, so a cheap multi-label classifier examines user messages, recent tool results, and error patterns on every iteration. It selects zero or a few short micro-instructions from a reusable bank. Examples include “new browser console log; pull it” and “consult a different model” when a doom loop is detected. Guidance is advisory, ephemeral, and not retained in conversation history. Replit reports that moving a parallel-tool nudge to decision time produced 15% more tools per loop, and that keeping the core prompt stable preserved caching and reduced cost relative to dynamic prompt rewriting ([Decision-Time Guidance](https://replit.com/blog/decision-time-guidance)). Those numbers are Replit's own experiments, not independent evaluation.

This is recognizably hook-like internally even though Replit offers no public hook API. It is also better shaped than our current fleet in one crucial respect: it treats a false positive as a disposable suggestion. Our observed guards can block or corrupt the agent's interpretation of a successful tool result. The known-defects file documents four implementations matching prose/field names without semantic role, including a sentinel that treated `"user_cancelled_or_timedout": false` as a failure and instructed the model to discard a successful result (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-87`).

### Port proposal P1 — selective ephemeral guidance

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Mechanism:

1. Reuse the existing dispatcher at `PreToolUse`, `PostToolUse`, and `PostToolUseFailure`; do not add a daemon.
2. Normalize only recent typed events: tool name, outcome boolean, error fingerprint, retry count, changed paths, and current task state. Never classify raw prose as an executable action.
3. Start with deterministic labels tied to measured failures: `dead_mcp`, `repeat_same_failure`, `quote_risk`, `read_before_write`, `unvalidated_absence`, `browser_console_error`. A model classifier is unnecessary until deterministic labels plateau.
4. Select at most one short nudge per iteration. Emit it as non-blocking `additionalContext`; make it expire after the next decision and never write it into durable chat/memory.
5. Reserve exit/block only for irreversible operations, matching our existing contract (`/local_disk0/codexwork/bundle/codex/AGENTS.md:48-54`).
6. Log label, evidence fields, nudge ID, whether the agent followed it, and downstream result to the event ledger. The current hook telemetry gap is documented at `INPUT-known-harness-defects.md:133-147`; observability is part of the mechanism, not a later add-on.

**very likely (80-90%)** to reduce prompt clutter and false blocking because the mechanism is local, advisory, and directly addresses four live false-positive detectors. Evidence: Replit's controlled placement result and our confirmed use-vs-mention defect. Settle the residual uncertainty with a shadow mode that logs recommendations but does not inject them for 50 tasks, followed by 50 injected tasks; compare applicable-nudge precision, retries, blocks, and tokens.

### Where Replit is worse

- Product modes expose only coarse user control. The owner cannot inspect or alter the loop, guidance bank, classifier, merge policy, or stopping policy. Ours exposes source-level hooks, rules, skills, agent definitions, and cross-provider behavior.
- Replit bills Plan interactions and longer conversations based on effort; a read-only planning request is still charged ([Plan Mode](https://docs.replit.com/references/agent/plan-mode)).
- Replit's “Agent can run for 200+ minutes” is a first-party Agent 3 claim, enabled partly by verification; it is not evidence that every run is productive or that longer is better ([Agent 3 launch](https://replit.com/blog/introducing-agent-3-our-most-autonomous-agent-yet)). Our anti-overfit gate correctly prefers success criteria and terminal states over runtime as a capability metric.

## 2. Context management

### Replit's layers

Replit documents these context sources: current prompt, earlier messages, files/code, errors/logs, screenshots/design references, `replit.md`, and previous tool results. Its own guidance says long conversations drift and advises a fresh thread with a hand-written relevant summary when switching features or when old constraints leak forward ([Context management](https://docs.replit.com/learn/foundations/context-management)).

Persistent project context has three forms:

- `replit.md` in the project root is automatically generated, automatically read, editable by the user, and may be updated by Agent as the project evolves. It holds architecture, conventions, stack, coding preferences, and communication style. It does not auto-detect nested copies and extremely large files may not be fully processed ([`replit.md`](https://docs.replit.com/features/project-setup/replit-dot-md)).
- Project skills expose only name/description every chat and load the full `SKILL.md` plus support files on demand. They live in `/.agents/skills`, conform to the open Agent Skills specification, persist across sessions, and can be versioned ([Agent Skills](https://docs.replit.com/features/agent/skills)).
- Workspace custom instructions are always injected in every project/session, while workspace skills remain on-demand. Replit warns that long instructions can reduce performance and that every skill description is still read on each task ([Agent Customization](https://docs.replit.com/features/agent/agent-customization)).

The testing subagent is a strong context-separation pattern. Replit says the main coding context often reaches 80k–100k tokens; browser exploration would pollute it, so only a test plan crosses into the verifier and only a summary crosses back ([REPL-based self-testing](https://replit.com/blog/automated-self-testing)). This is exactly the structured-handoff principle already present in our contract (`/local_disk0/codexwork/bundle/codex/AGENTS.md:43-46`).

### Port proposal P2 — context tiering and thread-reset packet

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Standardize four tiers using existing surfaces:

1. **Always-on:** only security invariants, owner preferences, and routing rules; impose a hard line/token budget.
2. **Metadata-on:** skill/agent names plus discriminative trigger descriptions.
3. **On-demand:** full skill bodies, references, MCP tool schemas, and memory notes.
4. **Task-local:** logs, browser trace, experimental output, and retry history; discard or summarize at handoff.

Add a deterministic fresh-thread packet with `goal`, `accepted constraints`, `current state`, `changed files`, `failed attempts with fingerprints`, `next probe`, and `definition of done`. This is configuration/documentation on native session and agent surfaces, not a memory service.

**likely (55-80%)** to improve long-horizon attention because both Replit and our contract independently converge on selective loading and typed summaries. It is not more certain because the owner's installed-skill metadata alone may already be large. Settle it by measuring injected tokens and task success on 30 long tasks before/after, with the exact same model and tools.

### Where Replit is worse

- `replit.md` is root-only and Agent may edit it. Automatic mutation can turn a context file into an unreviewed, self-reinforcing belief store. Our versioned rules and explicit memory validity fields are more auditable (`/local_disk0/codexwork/bundle/codex/AGENTS.md:79-85`).
- Replit's own recommended response to drift is manual thread reset and summary; no public compaction contract or inspectable context manifest is documented.
- Workspace custom instructions are a paid-plan surface and are centrally editable only under plan-dependent roles. Our project files are portable and vendor-neutral.

## 3. Memory

### What “memory” means in Replit

Replit uses the word in two distinct ways:

1. Durable declarative memory: `replit.md`, project/workspace skills, and workspace custom instructions.
2. Opaque Agent state: checkpoints preserve “the AI's understanding of your project architecture, preferences, and patterns,” along with conversation context, files, environment configuration, and optionally database contents ([Checkpoints](https://docs.replit.com/features/version-control/checkpoints-and-rollbacks)).

Checkpoint rollback restores the conversation to that point as well as code/config; future checkpoints after a rollback form an alternate history once new changes occur. Each checkpoint also creates a Git commit. This is coherent time-travel, not semantic retrieval.

### Port proposal P3 — do not replace our semantic memory

Replit does **not** demonstrate a better semantic-memory design for this owner. Our contract distinguishes objective event ledger from semantic `basic-memory`, supports proactive recall after compaction, and requires temporal invalidation via `superseded_by`/`valid_as_of` (`/local_disk0/codexwork/bundle/codex/AGENTS.md:62-68,79-85`). Replit's public project memory is less inspectable.

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Keep concise versioned project rules and on-demand skills; ensure the existing event-ledger replay and basic-memory recall are actually wired and measured. Do not introduce a vector DB/KG: that component is explicitly rejected by the anti-overfit gate and the corpus already shows StructuredOutput failures driven by `kg_triples` fan-out schemas (`corpus.json:8964-8992`).

**very likely (80-90%)** that retaining the current two-store distinction is better than copying Replit's opaque memory because ours supports provenance and supersession while Replit documents neither. The remaining uncertainty is whether our recall is dependable in live sessions; settle it with seeded recall tests across Claude/Codex, compaction, and 7/30-day age, recording precision and stale-fact rate.

### Exact whole-state time travel (UNVERIFIED recommendation threshold)

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Exact Replit parity would require coordinated filesystem snapshots, append-only off-volume Git, dev-database copy-on-write snapshots, runtime configuration snapshots, conversation/agent state serialization, and atomic restore. Replit implements immutable 16 MiB storage chunks and manifest-copy snapshots, restricts Agent to a development database, and synchronizes DB checkpoints with Git ([Snapshot engine](https://replit.com/blog/inside-replits-snapshot-engine)).

Do **not** build this now. It reintroduces a durable-execution/storage engine specifically rejected by the anti-overfit gate. **UNVERIFIED** whether the owner's workloads ever require coordinated code+database+conversation rollback often enough to justify it; settle with a 60-day incident ledger counting cases where Git/worktree rollback was insufficient and estimating recovery time saved. Only revisit BUILD-LARGE if at least five high-cost incidents require atomic non-code rollback and no application-native snapshot exists.

## 4. Tool and MCP handling

### Replit's surface

Replit offers built-in editor/runtime tools plus remote MCP. Users can one-click OAuth into a curated catalog or add an arbitrary HTTPS MCP endpoint, optional custom headers, and OAuth. Custom servers must pass “Test & save”; the UI records status. Agent automatically fetches the connected server's tool list and makes it available across projects, selects tools from the request, and prompts before any tool declaring confirmation ([Connect via MCP](https://docs.replit.com/build/connect-via-mcp)).

Workspace connector management adds central setup, app/member visibility, per-app consent and revocation, and platform-managed credentials. Enterprise adds group access, custom OAuth scopes/clients, API-key controls, and audit/governance ([Managing Connectors](https://docs.replit.com/replitai/managing-connectors)).

Skills and MCP are correctly separated: skills are lazy instructional context; MCP exposes executable capability. Replit's skills docs note that full skill content is lazy, while the MCP page says the tool list is fetched and made available. **UNVERIFIED** whether Replit lazily exposes MCP schemas or injects every connected tool schema; settle by connecting servers with 1, 100, and 1,000 synthetic tools and reading token/latency diagnostics for a no-tool prompt.

### Port proposal P4 — connection admission and circuit breaker

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a registry keyed by canonical server ID with `configured`, `last_probe`, `last_success`, `consecutive_failures`, `cooldown_until`, and `auth_required`. On session start, probe only stale/previously failed servers with a cheap list/capability call. On a definitive “not connected”/auth failure, open the circuit immediately; remove the server from routing and inject one concise alternative. Retry only after cooldown or explicit user request. A successful independent capability-list probe closes it. Log state transitions.

This directly targets measured ground truth: Tavily extract made 532 calls with 137 errors, 135 of them “not connected” (`corpus.json:175-180,9141-9149`); a separate Tavily search endpoint failed 139/194 calls (`corpus.json:9130-9138`).

**almost certain (90-99%)** to eliminate repeat calls to definitively disconnected MCP endpoints because circuit breaking mechanically prevents selection during cooldown. Settle the 1-10% operational uncertainty with replay of all recorded “not connected” fingerprints plus live known-good and known-bad control servers; acceptance is zero second calls to the bad server and no suppression of the good control.

### Port proposal P5 — schema-light tool results

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Prefer terminal-state envelopes (`ok`, `id`, `summary`, optional artifact path) over task-specific compulsory knowledge-graph fields. Put large results in artifacts and return pointers. Our contract already prefers `SUCCESS:<id>`/`FAILED:<id>` terminal results (`AGENTS.md:28-31`), while StructuredOutput currently fails 846/3,694 calls and its top mismatch is missing `kg_triples` and `confidence` 294 times (`corpus.json:8964-8992`). Replit's task review similarly presents work log, tests, and preview instead of requiring a universal research schema.

**almost certain (90-99%)** to eliminate the measured missing-`kg_triples` mismatch class if those fields cease being universally required; verify by replaying all 294 fingerprints against the relaxed envelope and checking downstream consumers.

### Where Replit is worse

- “Available across all projects” risks global tool noise and blast radius. Ours can scope MCP and skills by project/provider.
- Custom MCP trust is largely user-vetting: Replit explicitly warns users to trust the server. No public per-tool allow/deny policy language is documented beyond confirmation prompts and enterprise connector RBAC.
- Central OAuth brokerage is excellent for organizations but overbuilt for one local owner. Exact parity would be **BUILD-LARGE** and would add a credential service; do not build it. Existing MCP OAuth/secret stores plus explicit scoping are enough.
- Replit's proprietary platform can hide tool failures and routing choices; ours has raw config and can log exact tool fingerprints—once the telemetry defect is fixed.

## 5. Permission model

### Replit

Replit layers permissions rather than presenting a raw shell approval matrix:

- Plan mode reads but does not modify code/data; the user explicitly approves transition to Build.
- Background tasks mutate isolated copies and require apply/dismiss before main changes, unless user-configured auto-merge/auto-approve settings are used.
- MCP tools may request confirmation.
- The shared-responsibility model explicitly identifies human approval for deploys, secret changes, and outbound calls.
- Enterprise connector access can be granted by group with least-privilege OAuth scopes.
- Agent sees only the development database, not production, and production database rollback is separate.
- Workspaces provide RBAC/audit controls; Secrets are platform-managed instead of pasted into prompts.

Sources: [Shared responsibility](https://docs.replit.com/references/security/shared-responsibility-model), [Task system](https://docs.replit.com/core-concepts/agent/task-system), [MCP](https://docs.replit.com/build/connect-via-mcp), and [Snapshot engine](https://replit.com/blog/inside-replits-snapshot-engine).

### Ours

The subject's Claude configuration broadly allows file, shell, web, task, skill, and many MCP categories; denies direct reads of `.env`, PEM, and credential-like files; leaves `ask` empty; and sets `defaultMode` to `bypassPermissions` (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`). Hooks add fine-grained policy, including a credential-read guard and dangerous-operation contract, but observed semantic-role bugs make those guards noisy (`INPUT-known-harness-defects.md:9-87`).

### Port proposal P6 — trust-boundary approval

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Preserve auto-approval for read, local edit, test, and reversible worktree operations. Require explicit approval for production deploy/publish, secret creation/rotation/export, outbound write calls, force push, destructive database operations, and writes outside declared workspace roots. Bind approval to structured tool verb + resolved target + account/environment, never raw payload text.

**likely (55-80%)** to reduce high-impact mistakes without restoring approval fatigue because the gate is narrow and aligns with Replit's trust boundaries. Confidence is not higher because the available Claude permission schema may not express every outbound-write distinction without a hook. Settle it by schema inspection followed by a table-driven test of 30 operations; approval precision must exceed 95% and all irreversible controls must fire.

### Where Replit is worse

- Replit's permission implementation is not inspectable. Users cannot author arbitrary policy code comparable to our hook bus.
- Product-level confirmation is not a substitute for semantic validation; Replit itself places code correctness, licensing review, and business-logic specification on the user.
- Plan and task approval toggles can be auto-approved/auto-merged per user. Convenience may erase the safety boundary if enabled without risk classification.

## 7. Multi-agent support

### Replit Agent 4

Agent 4 supports three multi-agent patterns:

1. **Parallel independent tasks.** Pro supports up to 10 concurrently, Core one. Each works in an isolated current-project copy; main remains unchanged until apply. Extra tasks queue.
2. **Automatic decomposition.** Large work can be broken into smaller pieces and executed concurrently by subagents, then recombined.
3. **Specialized conflict resolution.** When parallel changes conflict, specialized subagents assist resolution.

Tasks have explicit Drafts, Active, Ready, Done states, dependency detection, work logs, test results, live previews, apply/dismiss, cancellation, and AI-assisted merges ([Agent 4](https://replit.com/blog/introducing-agent-4-built-for-creativity); [Task system](https://docs.replit.com/core-concepts/agent/task-system)). Multiple humans can create separate planning chats into one shared board.

This is multi-agent execution, but not an open society of arbitrary roles. Users do not publicly configure subagent prompts/tools/context budgets or direct agent-to-agent messages. The `build-an-agent` tutorial describes Claude Agent SDK multi-agent programs that users can create *as apps*, but that is not the same as customizing Replit Agent's own harness ([Build an agent](https://docs.replit.com/build/build-an-agent)).

### Our position

Our corpus already records 1,745 Agent tool calls at 1.15% errors (`corpus.json:119-124`) and 22 invoked agent types (`corpus.json:13346-13368`). Our orchestration rule explicitly prefers parallel subagents for independent work (`/local_disk0/codexwork/bundle/claude/rules/common/agents.md:1-3`). Therefore “add multi-agent” is not the gap. Isolation, review/apply semantics, and dependency-aware admission are.

### Port proposal P8 — task envelope over native worktrees

## 8. Verification and self-check

### Replit's verification stack

Replit combines several levels:

1. Build/run feedback, language diagnostics, console/server logs.
2. Automatic code review and simplification.
3. Unit/API tests where available.
4. Real-browser App Testing for Full Stack JavaScript and Streamlit Python.
5. A separate browser verifier with persistent REPL state.
6. Security scanning that combines deterministic analysis/dependency data with LLM reasoning.
7. Checkpoint creation at stable/tested milestones and review artifacts (logs, tests, preview).

The distinctive browser mechanism is “code use,” not one click tool call at a time. The verifier writes Playwright JavaScript in a sandbox/notebook. Variables and browser sessions persist; loops/conditionals compress repeated actions; stripped DOM plus ARIA/test attributes, read-only DB queries, and incremental client/server logs provide causal evidence. The verifier is a subagent to prevent main-context pollution. Replit reports median $0.20 per testing session and multi-hundred-step tests, but these are first-party numbers ([REPL-based self-testing](https://replit.com/blog/automated-self-testing)).

App Testing is selective rather than after every message. It can ask the human to take over for login/CAPTCHA and otherwise times out the takeover after ten minutes. Results include replay and section navigation ([App Testing](https://docs.replit.com/features/agent/app-testing)).

This is materially better than “agent wrote tests and says they pass.” It attacks Potemkin UIs: visible controls backed by mocks, missing handlers, dead links, or non-persistent data.

### Port proposal P9 — independent behavioral verifier

**NATIVE-vs-BUILD: CONFIG (settings/JSON only) for the baseline.** Define a `behavior-verifier` agent using the existing agent surface and allowed Playwright MCP (`settings.json:47-60`). Trigger after changes to UI routes, forms, auth, data persistence, or integration boundaries. Pass only: user-visible acceptance criteria, base URL/run command, critical flows, allowed test data, and changed areas. The verifier must return:

```text
VERDICT: PASS | FAIL | BLOCKED
FLOW: action -> observed state -> independent corroboration
EVIDENCE: screenshot/video/log/test artifact paths
DEFECTS: minimal reproduction + likely layer
COVERAGE_GAPS: untested acceptance criteria
```

Require two mechanically independent signals before PASS for load-bearing flows—for example browser-visible confirmation plus DB/API state, or UI state plus server log. This operationalizes the owner's rule rather than leaving it in prose (`single-signal-verification.md:20-37`).

**very likely (80-90%)** to catch failures missed by code-only tests because Replit identifies UI/backend seams and Potemkin interfaces as the motivating failure class, and our rules already require E2E critical flows (`/local_disk0/codexwork/bundle/claude/rules/common/testing.md:21-38`). Settle with 25 seeded bugs across missing handlers, mocked data, auth cookies, stale caching, failed persistence, and dead navigation; compare verifier recall, false positives, time, and tokens.

### Port proposal P10 — persistent browser code-use (UNVERIFIED need)

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** If baseline Playwright MCP traces are too token-heavy, expose one existing-browser tool that accepts short Playwright JavaScript snippets against a persistent context and returns only stdout, assertions, stripped DOM deltas, and new logs. Keep it in the existing MCP process/plugin model; do not create a general computer-use daemon. Provide read-only database query helpers and require explicit test-data namespace.

Settle it by running the same ten 20+ action flows with current Playwright MCP versus generated Playwright scripts and comparing tokens, wall time, recovery after selector failure, and defect recall. Proceed only if code-use cuts median tokens by at least 40% without lowering recall.

### Port proposal P11 — deterministic security baseline

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Run existing static analyzer, dependency audit, and secret scan deterministically before asking an LLM for business-logic review. Replit's security research reports AI-only scans vary with syntactic form/prompt and miss dependency vulnerabilities, recommending hybrid deterministic + model reasoning ([security white paper summary](https://replit.com/blog/securing-ai-generated-code)).

**very likely (80-90%)** to provide more repeatable baseline coverage than LLM-only review because the conclusion follows both established scanner mechanics and Replit's controlled experiments. ### Where Replit is worse

- App Testing officially supports only Full Stack JavaScript and Streamlit Python web apps. Our harness spans far more languages and non-web work.
- Replit chooses when to test; missing coverage must be requested explicitly. There is no documented acceptance-criteria coverage ledger.
- Automatic self-review is not independent if the same model/context reviews its own code. Replit's browser subagent improves this, but model identity is **UNVERIFIED**; settle by inspecting trace/model metadata or controlled self-preference tests.
- Replit tells users they remain responsible for correctness, security, licensing, and business logic. Its automation is evidence, not assurance.

## 12. Bottom line: replace, evolve, or ignore

**Do not replace the harness with Replit Agent.** Replit's advantages depend on platform ownership and a much narrower software-building product boundary. Replacement would lose programmable hooks, cross-provider operation, broad specialist skills/agents, arbitrary local tooling, and inspectable policy.

**Evolve the harness using three Replit principles:** guide only at the decision point, verify behavior in fresh context, and isolate work before review/apply. Those principles are model-agnostic and ride existing buses.

**Do not copy Replit's infrastructure moat.** Its snapshot engine is excellent platform engineering, but it is exactly the kind of durable runtime/storage scaffolding this harness should not acquire without repeated, measured need.

The radical move here is subtraction plus sharper control, not a larger framework: retire dead tools and over-strict schemas, shrink always-on context, convert noisy blockers into ephemeral typed nudges, and make a separate browser verifier prove user-visible behavior. **very likely (80-90%)** this is a better frontier direction than either safe incremental patching or wholesale Replit imitation, because it preserves our stronger extensibility while importing Replit's best verified loop mechanisms.
