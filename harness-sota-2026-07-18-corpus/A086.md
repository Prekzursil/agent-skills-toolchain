## Executive result

I found **one real policy-coherence conflict** between the Python hook tree and `settings.json`: the credential hook records an owner directive that the credential-file read block is opt-in and **off by default**, while `settings.json` unconditionally denies the same reads. At runtime, the settings deny wins after the hook passes the call onward. This remains true in `bypassPermissions` mode under the current documented evaluation order.

This is not merely duplicate defense-in-depth. The two texts express opposite default policies, and there is no harness-local tie-break or shared toggle. The minimal resolution is to remove the four `Read(...)` deny rules from `permissions.deny` and leave the broader hook as the single conditional authority controlled by `HARNESS_CREDENTIAL_GUARD`. Proposal tag: **CONFIG (settings/JSON only)**.

I found **no other demonstrated hooks-versus-settings precedence ambiguity** in the supplied scope. Broad tool allows and `bypassPermissions` do overlap with several hook blocks, but Claude Code defines the tie-break: hooks run first; hook denies block; settings deny/ask rules are evaluated after hooks; and a settings deny also defeats a hook allow. Those overlaps are deliberate layered enforcement, not ambiguous precedence.

The conclusion above is **almost certain (90-99%)**, based on (1) the verbatim settings and hook source, (2) an executable probe of the hook in both default and enabled states, (3) a complete binding/decision census, and (4) Anthropic's current documented runtime evaluation order. The remaining uncertainty is that the actual Windows Claude Code executable and its version were unavailable on this Linux job node.

## Finding 1 — opposite defaults for credential reads

### Both authoritative texts, verbatim

The declarative settings authority says:

> `/local_disk0/codexwork/bundle/claude/settings.json:64-71`
>
> ```json
> "deny": [
>   "Read(./.env)",
>   "Read(**/.env)",
>   "Read(**/*.pem)",
>   "Read(**/*.credentials*)"
> ],
> "ask": [],
> "defaultMode": "bypassPermissions",
> ```

The hook's owner-policy text says:

> `/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:73-80`
>
> ```python
> def _guard_enabled():
>     """Owner directive 2026-07-11: this credential-file-READ block is OPT-IN and
>     OFF by default. It created setbacks in interactive sessions (inspecting one's
>     OWN ~/.ssh keys / .env / config, and workflows that merely NAME a credential
>     file). Set HARNESS_CREDENTIAL_GUARD=1 (or true/yes/on) to re-enable. Mirrors the
>     gate in ~/.agents/harness/modules.py SecretGuardModule so both credential
>     mechanisms share ONE toggle. The secret-LITERAL input block and the
>     irreversible-op (disk-wipe / history-rewrite) gate are separate and unaffected."""
> ```

The executable hook then implements that policy:

> `/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:81-101`
>
> ```python
> return os.environ.get("HARNESS_CREDENTIAL_GUARD", "").strip().lower() in {
>     "1", "true", "yes", "on",
> }
> ...
> if not _guard_enabled():
>     sys.exit(0)  # credential-file block DISABLED BY DEFAULT (owner directive 2026-07-11)
> ...
> sys.exit(0)  # no decision -> normal permission flow
> ```

The same file also acknowledges the other authority, but without reconciling it:

> `/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:4-8`
>
> ```text
> Enforces the no-raw-credentials rule STRUCTURALLY (not by trusting the model):
> a confused/jailbroken agent still cannot pull a literal secret into context.
> The declarative permissions.deny in settings.json already blocks the Read tool
> on .env/*.pem/*credentials*; this ALSO closes the Bash/Grep gap
> ```

Thus the file simultaneously says that the **credential-file-READ block** is off by default and that settings already block the same reads. The claim that the two credential mechanisms share one toggle is false for the supplied `settings.json`: the settings deny array has no conditional relationship to `HARNESS_CREDENTIAL_GUARD`.

### Concrete collision

1. Start Claude Code with the supplied user settings. `HARNESS_CREDENTIAL_GUARD` is absent from the complete environment object (`settings.json:4-21`).
2. Claude requests `Read` with `file_path` `./.env` (or a path matching the other three settings rules).
3. The registered PreToolUse hook applies because its matcher includes `Read` (`settings.json:239-248`). It observes that the toggle is unset and exits 0 without a decision (`deny.py:86-101`). This is the hook authority saying “normal flow / no hook block.”
4. The declarative `Read(./.env)` deny then applies (`settings.json:64-69`) and blocks the request.

This collision arises under the configured `defaultMode: "bypassPermissions"`; bypass does not bypass explicit deny rules. It also arises under other modes.

### Which wins at runtime

**`settings.json permissions.deny` wins.** Anthropic's current permission-evaluation contract is explicit:

* Hooks run first, and a hook that passes or returns allow does not skip later rules: <https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated>, lines 106-119 in the retrieved page.
* A matching deny rule blocks **even in `bypassPermissions` mode**: the same page, lines 118-130.
* The hooks guide independently states that exit 0 does not approve a PreToolUse call and normal permission flow still applies, while a hook `allow` cannot override a settings deny: <https://code.claude.com/docs/en/hooks-guide>, retrieved lines 560-585.
* The non-SDK permissions reference independently states deny → ask → allow precedence and says permission rules are enforced by Claude Code rather than the model: <https://code.claude.com/docs/en/permissions>, retrieved lines 107-116.

The hook half was also executed locally with exactly the collision payload:

```json
{"hook_event_name":"PreToolUse","tool_name":"Read","tool_input":{"file_path":"./.env"}}
```

With the normal inherited environment, it produced no stdout and exited 0. With `HARNESS_CREDENTIAL_GUARD=1`, it emitted the documented `permissionDecision: "deny"` JSON and exited 0. This executable control confirms that the hook's default gate behaves as its source says.

The exact end-to-end behavior of the owner's installed Windows binary is **UNVERIFIED (experiment: on the Windows subject, record `claude --version`, run a disposable session with the supplied user settings, invoke `Read` on a synthetic `.env` in both unset and `HARNESS_CREDENTIAL_GUARD=1` states, and inspect `/hooks`, `/permissions`, and the debug trace)** because no `claude` executable exists on this Linux node. The current official runtime contract plus the executable hook probe make the stated winner **almost certain (90-99%)**; the missing Windows smoke test accounts for the residual uncertainty.

### Minimal edit that resolves the conflict

**Proposal tag: CONFIG (settings/JSON only).** Delete these four entries from `settings.json.permissions.deny`:

```json
"Read(./.env)",
"Read(**/.env)",
"Read(**/*.pem)",
"Read(**/*.credentials*)"
```

Then `deny-credential-reads/deny.py` becomes the single user-level credential-file authority:

* unset/false `HARNESS_CREDENTIAL_GUARD` means off, honoring the owner directive;
* true means the hook blocks `Read`, `Edit`, `NotebookEdit`, `MultiEdit`, `Grep`, `Bash`, and `PowerShell` paths covered at `deny.py:86-100`, which is broader and more internally coherent than the four Read-only settings rules;
* externally managed deny rules, if any, remain authoritative and cannot be weakened by this user-level edit.

This resolution is **very likely (80-90%)** to make the default policy coherent, based on the documented evaluation chain and the hook probe. It does not claim to remove managed/project/local denies not present in the bundle; the Windows smoke experiment above settles the remaining host-scope uncertainty.

Alternative if the owner's current intent has changed back to “always block”: add `"HARNESS_CREDENTIAL_GUARD": "1"` to `settings.json.env` and revise `deny.py:73-80` to remove the stale “off by default / one toggle” directive. That is also **CONFIG (settings/JSON only)**, but it contradicts the most recent explicit owner directive in the supplied source and therefore is not the recommended resolution.

Anti-overfit gate: pass. This edit uses the existing native permission/hook bus, adds no runtime, and reintroduces none of the rejected architectures.

Sources: <https://code.claude.com/docs/en/hooks-guide> (retrieved lines 580-585) and <https://code.claude.com/docs/en/hooks> (PreToolUse decision-control section). Minimal edit: none.
