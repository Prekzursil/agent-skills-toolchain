# P2B16 — Competitive teardown: Continue

**Unit:** P2B16  
**Research date:** 2026-07-18  
**Subject:** Continue final 2.0.0 codebase, CLI, VS Code extension, and published documentation  
**Comparison target:** the owner's Claude Code + Codex harness, not stock Claude Code alone

## Executive conclusion

Continue is no longer a moving frontier competitor. Its repository says that it is read-only, that the project received a final 2.0.0 release, and that the final release removed authentication and anonymous telemetry; GitHub dates the latest VS Code 2.0.0 release to 2026-06-19. This matters because several currently served docs still describe login, Hub agents, and a beta CLI as if they were live. The final source is therefore authoritative whenever it conflicts with the docs. Sources: [repository status and final-release notice](https://github.com/continuedev/continue#what-is-continue), [v2.0.0 release](https://github.com/continuedev/continue/releases/tag/v2.0.0-vscode), [stale CLI quickstart still describing login](https://docs.continue.dev/cli/quickstart).

Continue's core architecture is a conventional single-session tool loop with automatic context compaction, MCP tools, three-state permissions, rules/prompts/skills, and—late in its life—a Claude Code-compatible lifecycle-hook layer. It also contains a beta subagent tool and a separate parallel `cn review` fan-out. The most important competitive finding is not that Continue has a better general harness. It does not. The owner's harness already has native subagents/teams, cross-vendor delegation, durable semantic memory, a richer lifecycle bus, worktree hooks, many more skills, and explicit deterministic verification mechanisms. Local evidence: `C:\Users\Prekzursil\.claude\settings.json:5-18,26-75,310-525`; `C:\Users\Prekzursil\.claude\CLAUDE.md:5-11,15-82`; `C:\Users\Prekzursil\.agents\harness\README.md:3-29`.

Two Continue mechanisms are worth porting:

1. **A privacy-tiered, schema-versioned local lifecycle-event sink — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This recommendation is **UNVERIFIED** because the exact telemetry gap in our harness has not yet passed the prescribed two-signal experiment. The experiment is: grep `~/.claude/event-ledger/` for the known-fired `codex-monitor-autolaunch` hook and independently grep transcripts for its injected `system-reminder`; only if neither contains durable hook execution data should the sink be built. Continue's `data` destination design—event allowlist, schema version, local JSONL or HTTP, and `noCode` privacy level—is the useful part. Sources: [Continue config reference, `data`](https://docs.continue.dev/reference#data); local defect evidence `INPUT-known-harness-defects.md:133-147`.
2. **A turnkey, isolated, parallel diff-review command — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Port the protocol, not Continue's unsafe implementation: compute one diff, run independent local review agents in worktrees, scope every reviewer to changed lines, collect plain terminal-state findings/patches, dry-run patch application, and return a nonzero status on findings/errors. Do not copy its `--no-verify` commit or its full-auto tool permissions. Sources: [review orchestrator](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review.ts), [review worker](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/reviewWorker.ts), [worktree helper](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/worktree.ts).

The first port is **likely (55-80%)** to make hook benefit/harm measurable because Continue's event sink exposes exactly the missing dimensions—event type, local destination, schema, and code-redaction tier—and our defect file records a known-fired hook that the transcript miner could not see (`INPUT-known-harness-defects.md:133-147`). The wide band reflects the still-UNVERIFIED possibility that equivalent data is already in the event ledger. The second port is **very likely (80-90%)** to reduce the friction of repeatable multi-perspective review because all underlying primitives already exist locally (native Task/Agent, worktree create/remove hooks, reviewer agents), while Continue demonstrates that only a thin orchestration layer is needed; evidence is `settings.json:419-525`, corpus Agent use at `corpus/corpus.json:119-124`, and Continue's roughly 300-line review implementation. Neither port adds a second orchestration runtime, vector database, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Full replacement by Continue is **almost certainly not (1-5%)** the right direction. Evidence: the project is frozen/read-only; its final subagent executor temporarily grants every tool; its review worker uses auto mode; its worktree snapshot bypasses commit hooks; its prompt/agent hook types are declared but not implemented; and its native long-term memory is only session history unless an external MCP is added. By contrast, our corpus records 1,745 Agent calls at 1.15% error and 500 inter-agent messages at 2.0% error (`corpus/corpus.json:119-124,191-196`), and the live harness has native subagent, task, teammate, compaction, and worktree lifecycle registrations (`settings.json:382-525`).

## 1. Agent loop

### What Continue does

Continue's public description is accurate at the high level: send available tool schemas with the user request, accept a tool call, apply policy, execute the built-in or MCP tool, append its result, and call the model again. Source: [How Agent Mode Works](https://docs.continue.dev/ide-extensions/agent/how-it-works).

The final CLI source makes the loop concrete. `streamChatResponse()` runs `while (true)`, refreshes session history, recomputes the system message and tool list every iteration (so a mid-stream permission-mode change takes effect), performs pre-request compaction, streams the response, executes tool calls, validates post-tool context size, and performs another normal auto-compaction check. Source: [final stream loop](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/stream/streamChatResponse.ts).

Continue also catches most tool errors and returns them to the model, which can choose a recovery action. Source: [Agent quick start](https://docs.continue.dev/ide-extensions/agent/quick-start#how-to-view-tool-responses).

### Comparison

This is not a gap. Our providers own mature native loops, while our harness intercepts lifecycle events rather than replacing those loops. The local shared harness normalizes provider input, runs ordered modules, emits a closed `HookResult`, and fails unexpected module errors open with terminal markers (`C:\Users\Prekzursil\.agents\harness\README.md:3-29`). That is the minimal architecture the anti-overfit gate calls for.

**Port decision — NATIVE (Claude Code already does this; we just enable it).** Do not build a Continue-like agent runtime. A second loop would be a previously rejected second orchestration runtime. It would also create another parser and tool schema boundary adjacent to our largest measured fan-out defect: StructuredOutput failed 846/3,694 calls (22.9%), including 294 identical required-field mismatches (`corpus/corpus.json:103-108,8964-8972`).

### What Continue does worse

- Its compatibility claim for system-message tools is broader than its reliability evidence. A documented issue shows multi-action gpt-oss MCP sequences stopping after the first action because generated tool text did not parse as JSON; maintainers called it backlog work. Source: [Continue issue #7429](https://github.com/continuedev/continue/issues/7429).
- The fallback converts tools to XML in the system message and parses XML emitted by the model. Source: [system-message tools](https://docs.continue.dev/ide-extensions/agent/model-setup#how-system-message-tools-work). That is another prompt/parser protocol. Given our measured schema/quoting failures, importing it is **unlikely (20-45%)** to improve reliability; evidence is Continue's parsing incident and our 22.9% StructuredOutput error rate. The range is not lower because it could still help a future non-native local model in a controlled eval.
- Continue recomputes and exposes the full tool list each iteration. Our `ENABLE_TOOL_SEARCH=auto:5` (`settings.json:17`) and corpus ToolSearch result—5,091 calls with only four errors (`corpus/corpus.json:87-92`)—provide a more scalable path for a large MCP fleet.

## 2. Context management

### Context acquisition

Continue can attach highlighted code, the active file, named files, open/pinned files, terminal contents, git diff, URLs, OS information, repo maps, and provider-returned context. Agent tool results automatically become context items. Sources: [chat context selection](https://docs.continue.dev/ide-extensions/chat/context-selection), [context providers](https://docs.continue.dev/customize/custom-providers), [agent context selection](https://docs.continue.dev/ide-extensions/agent/context-selection).

For autocomplete, it can include imports, recently edited files, and recently opened files. It supports distinct model roles for autocomplete, apply, embedding, and reranking. Sources: [config reference](https://docs.continue.dev/reference#models), [model roles](https://docs.continue.dev/customize/models).

**Port decision — NATIVE (Claude Code already does this; we just enable it)** for selections, files, diffs, terminal, URLs, and autonomous search. **CONFIG (settings/JSON only)** for any project-specific path rule or context source already reachable by MCP. There is no case here for a new context service.

### Compaction

Continue's final compactor is one of its cleaner mechanisms. It counts chat history, system message, tool definitions, model context length, and reserved output tokens. Its threshold uses 80% of available input with an additional buffer capped at 15,000 tokens. Before summarizing, it removes whole user/assistant-tool pairs until the summary request fits; it stores the result as a `conversationSummary`, retains the system message, and supports both manual `/compact` and auto-compaction. Source: [final compaction source](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/compaction.ts), [TUI commands](https://docs.continue.dev/cli/tui-mode).

Our live Claude setting uses `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=90` and registers both PreCompact and PostCompact events (`settings.json:18,382-401`). This proves compaction exists, not that 90% is optimal.

**Port decision — CONFIG (settings/JSON only).** If later evaluation shows context-overflow or summary-quality failures, compare the current 90% threshold against 80% on the same long-session suite. The claim that 80% would be better is **UNVERIFIED**; the settling experiment is an A/B replay measuring completed tasks, overflow errors, compaction count, and post-compact correction rate. It is **roughly even (45-55%)** that lowering the threshold improves end-to-end quality: Continue's explicit output/tool reservation supports earlier compaction, while the owner's current 90% setting preserves more raw history and no pinned metric attributes failures to late compaction.

### Semantic code indexing — do not copy

Continue historically indexed code with local embeddings plus keyword search, stored the index in SQLite, retrieved `nRetrieve` candidates, and optionally reranked to `nFinal`. Its own docs now mark `@Codebase` deprecated and point users toward agentic codebase awareness. Source: [deprecated @Codebase](https://docs.continue.dev/reference/deprecated-codebase), [reranking role](https://docs.continue.dev/customize/model-roles/reranking).

This is a capability we do not provide as a general code vector index.

**Port decision — BUILD-LARGE (new daemon/service/runtime -- needs its own justification). Reject.** It reintroduces the explicitly rejected vector-DB/KG memory component, while Continue itself deprecated the user-facing retrieval path. Agentic `rg`/read plus repo maps ride the current bus and improve as models improve. A code index is **very unlikely (5-20%)** to clear the anti-overfit gate for this owner; evidence is Continue's deprecation, our highly reliable ToolSearch (0.08% errors), and the brief's explicit vector-DB/KG exclusion. The remaining probability covers a future measured large-monorepo retrieval failure that search/repo maps cannot solve.

### What Continue does worse

- Its old index can become stale and sometimes requires a complete rebuild; the FAQ explicitly recommends rebuilding persistent failures. Source: [Continue FAQ, indexing issues](https://docs.continue.dev/faqs#indexing-issues).
- Documentation indexes do not automatically re-index and require manual refresh. Source: [deprecated @Docs management](https://docs.continue.dev/reference/deprecated-docs#how-to-manage-your-documentation-indexes).
- Continue's compaction summary is a single model-generated message. It does not have our separate sanitized PreCompact checkpoint plus durable Basic Memory recall (`CLAUDE.md:5-11`; shared harness invariant at `README.md:28-29`).

## 3. Memory and continuity

Continue persists chat sessions, supports `/resume`, restores full history, allows `/fork`, and summarizes history with `/compact`. Sources: [TUI session management](https://docs.continue.dev/cli/tui-mode#resume-previous-sessions), [CLI quickstart](https://docs.continue.dev/cli/quickstart).

I found no first-party durable semantic memory mechanism distinct from chat/session persistence. This absence claim is **UNVERIFIED** despite two signals: the current config reference's complete top-level property list has no memory property, and the docs' memory example is an external `@modelcontextprotocol/server-memory`. The decisive experiment is to run final 2.0.0 in an empty profile, finish a session containing a unique decision, start an unrelated new session without resuming it, and query that decision with all MCP servers disabled. Sources: [complete config properties](https://docs.continue.dev/reference), [external memory MCP example in troubleshooting](https://docs.continue.dev/troubleshooting#mcp-server-connection-issues).

Our harness has canonical cross-tool Basic Memory with proactive recall, semantic vault storage, temporal supersession, and PreCompact checkpoints (`CLAUDE.md:5-11`). The corpus records 1,332 Basic Memory uses (`corpus/corpus.json:13370-13374`).

**Port decision — CONFIG (settings/JSON only).** We already have the stronger external-memory pattern. Do not create another memory database, graph, or daemon. Continue contributes no missing mechanism here.

Continue's explicit `/fork` UI is useful ergonomically, but session branching is provider-native rather than a harness component. **Port decision — NATIVE (Claude Code already does this; we just enable it).** If one provider lacks a visible fork shortcut, document its native command; do not synthesize branching in the shared harness.

## 4. Tool and MCP handling

### Continue mechanism

Continue supports stdio, SSE, and streamable HTTP MCP transports; remote servers, request options, connection timeouts, OAuth flows, and secret interpolation; and direct import of Claude/Cursor/Cline JSON MCP files placed under `.continue/mcpServers`. Sources: [MCP deep dive](https://docs.continue.dev/customize/deep-dives/mcp), [MCP config reference](https://docs.continue.dev/reference#mcpservers), [JSON import](https://docs.continue.dev/customize/deep-dives/mcp#using-json-mcp-format-from-claude-cursor-cline-etc).

Every tool is described by a name and arguments schema. Results, including most errors, are appended to model context. The user can exclude a tool entirely so it is not sent to the model. Sources: [agent handshake](https://docs.continue.dev/ide-extensions/agent/how-it-works), [tool policies](https://docs.continue.dev/ide-extensions/agent/how-to-customize#how-to-configure-tool-policies).

The final built-in registry includes read, write, multi-edit, search, fetch, diff, background-job status, question, checklist, failure reporting, status, artifact upload, skills, and the beta subagent tool. The IDE core also exposes rule creation and experimental repo-map/codebase tools. Sources: [final CLI tool directory](https://github.com/continuedev/continue/tree/main/extensions/cli/src/tools), [IDE tool registry](https://raw.githubusercontent.com/continuedev/continue/main/core/tools/index.ts).

### Comparison and port classification

Our harness already uses MCP at much greater breadth: 93 servers were touched according to the pinned program input; the corpus excerpt shows ToolUniverse, Basic Memory, Firecrawl, Ghidra, browser automation, Cheat Engine, Exa, search-hub, Tavily, paper search, Playwright, Hugging Face, and others (`corpus/corpus.json:13370-13400`). The live config enables tool search (`settings.json:17`).

**Port decision — NATIVE (Claude Code already does this; we just enable it)** for MCP transports, OAuth-capable servers, tool results, and discovery. **CONFIG (settings/JSON only)** for per-server timeouts and registration. Continue's direct `.claude` JSON import is interoperability, not a missing capability, because `.mcp.json`, `.claude.json`, and provider configs are already subjects of this harness.

### What Continue teaches us not to do

- Continue's tool-fallback layer adds XML parsing. Do not introduce that adapter between native Claude/Codex tool calls and MCP.
- The `Skills` tool is marked `readonly: false` even though reading a skill is non-mutating. Source: [final skills tool](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/tools/skills.ts). This needlessly expands approval friction and is a caution against classifying by tool family rather than actual effect.
- Continue injects every discovered skill name and description into the Skills tool description. Source: [same skills tool](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/tools/skills.ts). With the owner's roughly 355 installed skills, copying this is **likely (55-80%)** to waste context and worsen selection; evidence is the source's eager string construction and our deliberate `skillListingBudgetFraction: 0.02` (`settings.json:3`). The uncertainty is whether Continue applies an upstream tool-description truncation not visible in this file.
- Continue's final docs recommend `which` when troubleshooting executable paths. Source: [troubleshooting](https://docs.continue.dev/troubleshooting#mcp-server-connection-issues). That advice is wrong for this Windows harness because Git Bash `which` misses `.cmd` shims; the pinned contract requires PowerShell `Get-Command`.
- Continue had its own `ENAMETOOLONG` MCP spawn issue and recommends full executable paths. Source: [troubleshooting](https://docs.continue.dev/troubleshooting#mcp-server-connection-issues). The workaround is relevant, but it does not solve our root cause: approximately 1,293 orphaned plugin directories inflate the Windows process command line. Continue supplies no safe orphan-cleanup design.
- Continue exposes all configured tools each loop unless policies exclude them. Our dynamic ToolSearch is demonstrably reliable: four errors in 5,091 calls (`corpus/corpus.json:87-92`). Do not regress to an eager 93-server tool list.

### Dead-server lesson

Continue's `/mcp` UI and per-server visibility are convenient, but I found no source-backed automatic circuit breaker that removes a repeatedly dead server after a known connection failure. That absence is **UNVERIFIED**; the experiment is to configure a server whose command deterministically exits, run three model turns that request it, and observe whether final 2.0.0 suppresses it or repeatedly reoffers it. Our need is nevertheless measured: `claude_ai_Tavily` produced 135 “not connected” failures on extract and 139 on search (`corpus/corpus.json:9130-9148`). Any future circuit breaker should be designed from that measured defect, not claimed as a Continue port.

## 5. Permission model

Continue has three tool decisions: `allow`, `ask`, and `exclude`. Read tools default to allow; writes and Bash default to ask; headless mode excludes tools that remain `ask`. CLI flags can match the entire tool or its primary argument, including `Write(**/*.ts)` and `Bash(npm install*)`. Mode policies outrank CLI flags, which outrank persistent `~/.continue/permissions.yaml`, which outranks defaults. Plan and auto modes are absolute overrides. Sources: [Tool Permissions](https://docs.continue.dev/cli/tool-permissions), [final ToolPermissionService](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/services/ToolPermissionService.ts).

Our settings already express allow, deny, tool/path patterns, an explicit default mode, and permission lifecycle hooks (`settings.json:26-75,286-305`).

**Port decision — NATIVE (Claude Code already does this; we just enable it).** Continue's policy grammar is not a missing capability. The safe lesson is configuration hygiene: keep irreversible/credential access blocked, allow routine reversible work, and do not proliferate regex payload guards.

### Continue is materially worse for child agents

The final beta subagent executor saves the main permission state, then replaces it with a single `* → allow` policy for the child, with a comment saying “allow all tools for now.” It restores the parent state afterward. Source: [subagent executor](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/subagent/executor.ts).

The review worker similarly initializes every reviewer in `auto` mode with full tool access, relying on prompt text to constrain it to changed files. Source: [review worker](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/reviewWorker.ts).

This violates least-privilege inheritance. Do not copy it. Our subagent definitions can restrict tools and our shared harness receives SubagentStart/SubagentStop events (`settings.json:419-440`). A ported review command must give each reviewer only read/search/diff plus an isolated patch-writing path when `--fix` is explicitly selected.

The worktree snapshot helper makes an internal commit with `--no-verify`. Source: [worktree helper](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/worktree.ts). That directly violates this owner's security non-negotiable. It also means Continue's reviewer can see a state that repository hooks would have rejected. The port must either create a worktree and apply a patch without committing, or commit normally with hooks; it must never bypass verification.

## 6. Customisation: rules, skills, prompts, hooks, and agents

### Rules and prompts

Continue rules can be global or workspace-local, can be shared as Hub blocks, and can carry globs that activate when matching files are in context. Rules are joined into the system message. Agent mode can create a new `.continue/rules` file. Invokable Markdown prompts become slash commands and can run in Chat, Plan, Agent, TUI, or headless CI. Sources: [rules deep dive](https://docs.continue.dev/customize/deep-dives/rules), [prompts deep dive](https://docs.continue.dev/customize/deep-dives/prompts), [configuration blocks](https://docs.continue.dev/guides/configuring-models-rules-tools).

**Port decision — CONFIG (settings/JSON only).** Our `AGENTS.md`, `CLAUDE.md`, path-scoped `rules/`, skills, commands, agents, and plugin system already cover this. Continue's UI “notch” for toggling rules/prompts/tools is useful ergonomics, but Claude's native `/permissions`, `/hooks`, `/mcp`, skill invocations, and settings views are the correct bus. Do not build another control plane.

### Skills

Final Continue loads one-level skill directories from `<cwd>/.continue/skills`, `<cwd>/.claude/skills`, and the global Continue directory. It requires `name` and `description` frontmatter, captures auxiliary files, and exposes skill contents through a tool. Source: [skill loader](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/util/loadMarkdownSkills.ts), [skill tool](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/tools/skills.ts).

This is explicit convergence on Claude's skill format. It does not exceed our harness. Our corpus observes 78 distinct invoked skills, including deep research, fresh-context verification, verification-before-completion, Codex review, orchestration, and domain skills (`corpus/corpus.json:13265-13344`). The utilization ratio is low relative to roughly 355 installed, but Continue's eager listing is not the cure.

**Port decision — NATIVE (Claude Code already does this; we just enable it).** Improve selection/evaluation on the native skill bus; do not adopt Continue's parallel skill directory or importer as another source of truth.

### Hooks

Continue's final CLI implemented a Claude Code-compatible hook layer. It loads and merges global/project/local `.continue/settings*.json` and `.claude/settings*.json`; recognizes 17 lifecycle event names; passes Claude-shaped JSON; allows command and HTTP handlers; supports blocking, input rewriting, and additional context; deduplicates handlers; runs synchronous handlers in parallel; and fails hook errors open. ### Parallel `cn review`

This is Continue's genuinely distinct multi-agent mechanism:

1. Compute a diff against an auto-detected or specified base.
2. Resolve reviewer definitions from flags or local `.continue/agents/*.md` / `.continue/checks/*.md`.
3. Create one detached temporary worktree per reviewer and mirror committed, staged, unstaged, and untracked state.
4. Fork one worker process per reviewer (parallel by default, sequential with `--fail-fast`).
5. Prompt each worker to inspect only changed lines and allow surrounding reads only for context.
6. Capture each reviewer's patch and textual output.
7. Mark pass when no patch exists, fail when a patch exists, error on worker failure; render text/JSON/patch and use a nonzero exit status.
8. With `--fix`, dry-run `git apply --check` then apply patches to the real working tree.

Sources: [review orchestrator](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review.ts), [diff-scoped worker](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/reviewWorker.ts), [review resolution](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/resolveReviews.ts), [worktrees](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review/worktree.ts).

Our harness has all primitives but I found no single local command evidenced in the pinned inputs that performs this complete deterministic review fan-out and aggregation. This absence is **UNVERIFIED** because the search was limited to live rules/agents/skills and pinned audit inputs, not every repository script. The settling experiment is: run a known-positive search for the existing `codex-review` skill, then search all harness/toolchain scripts for a command that computes one diff, launches multiple isolated reviewers, aggregates patches, and returns an exit code. If found, this recommendation becomes CONFIG rather than a build.

### Recommendation 1 — UNVERIFIED turnkey parallel diff review — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Build only if the preceding known-positive search confirms the absence.

Concrete port design:

- A skill or thin PowerShell/Python helper accepts `--base`, `--reviewers`, `--fail-fast`, `--patch`, and explicit `--fix`.
- It computes the diff once and bounds/truncates it with a visible marker.
- It invokes existing native reviewer agents in isolated native worktrees; it does not fork another agent runtime.
- Each reviewer receives a plain-text contract: changed-lines scope, surrounding reads allowed, no unrelated findings, terminal `SUCCESS:<review-id>` or `FAILED:<review-id> reason` marker, optional unified patch path.
- Avoid StructuredOutput fan-out. That mechanism has a 22.9% measured error rate and 294 repeated required-field mismatches (`corpus/corpus.json:8964-8972`). Parse only terminal markers and patch files.
- Reviewer permissions are a subset of the parent: read/search/diff by default; isolated edits only when the user selected `--fix`; no network or broad Bash unless the reviewer definition explicitly requires it.
- Never use `--no-verify`. Never force-remove an unresolved worktree path. Validate every temporary path is under the chosen temp root before cleanup.
- Re-run deterministic repository tests/lint after patch application; reviewer opinion alone does not grant “done.”
- Emit a compact aggregate with reviewer, terminal state, evidence locations, patch applicability, and deterministic test receipt.

This is **very likely (80-90%)** to be implementable under 200 lines because native agents, worktree hooks, reviewer definitions, terminal markers, and longrun already exist (`settings.json:419-525`; shared README `:14-25`). It is **likely (55-80%)** to improve repeatable review coverage without overfitting because it standardizes an already-used native fan-out rather than adding a critic model; evidence is 1,745 successful Agent invocations and existing reviewer/TDD agents. The lower outcome band reflects possible reviewer correlation and patch conflicts.

Anti-overfit result: passes. It rides the existing Task/Agent/worktree bus. It is not a durable engine, trained critic, SaaS, second runtime, or new memory system.

## 8. Verification and self-check mechanisms

Source: status derivation in [review orchestrator](https://raw.githubusercontent.com/continuedev/continue/main/extensions/cli/src/commands/review.ts). This is a correctness flaw; do not copy that oracle. A port must let explicit `FAILED:<id>` findings fail even without a patch.

Our harness is stronger in intent and breadth: PostToolUse runs per-edit validation (`settings.json:334-340`); PreToolUse has credential and test-tamper guards (`settings.json:240-257` and earlier live hook registrations); rules and agents cover TDD, language tests, security review, fresh-context verification, and advisory agent-as-judge. Our implementation is not uniformly better in reliability. D1 confirms four detector implementations confuse mentions with uses and can discard successful tool results; D2 records seven wrong conclusions from unvalidated probes (`INPUT-known-harness-defects.md:9-129`). Continue's matcher design—match `tool_name` for tool events, not arbitrary payload text—is the right discriminator principle. The proposed shared semantic discriminator in the defects file remains the correct BUILD-SMALL repair; Continue does not justify replacing the bus.

**Port decision — CONFIG (settings/JSON only)** for invoking existing deterministic tests and reviewer agents. The only new build is the diff-review front end above. Do not create a trained critic or guardrail framework.
