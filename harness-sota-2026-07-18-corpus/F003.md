# F003 — Red-team: guard-bypass false negatives

## Unit boundary and verdict

This unit defensively reviewed the owner-controlled implementations of four guards named in the brief: the shared destructive-command/lifecycle guard, `stub-ledger`, `tool-result-sentinel`, and `dup-guard`. I did not execute a destructive operation, change the subject harness, install anything, or test against a real secret/remote. Dynamic probes invoked pure classifier functions or hooks over temporary fixtures. The only persistent write is this artifact. The pre-existing dirty files reported by `git status --short --untracked-files=no` in `C:\Users\Prekzursil\source\agent-skills-toolchain` were `hooks/_dispatch/manifest.json`, `hooks/stub-ledger/stubscan.py`, and two account JSON files; this unit did not touch them.

Bottom line: the most important false negative is not an exotic parser bypass. The shared lifecycle guard is deliberately **off by default**, and its own tests prove that recognized catastrophic commands are allowed in that state. When enabled, it is still a command-string recognizer rather than a containment boundary. The result sentinel has several verified schema-level fail-open cases, including contradictory envelopes where an explicit zero exit code masks `isError: true`. Stub and duplicate guards have broad, verified mutation-surface and language-grammar gaps; those are primarily completion/correctness risks, but become security-relevant when the missed code is an authorization, validation, cleanup, or credential-handling implementation.

I found no defensible basis for replacing the harness with another runtime. Every remediation below rides the existing Claude hook/shared-dispatch bus and avoids a second orchestrator, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. That is the anti-overfit result, not merely an omission.

The run path only blocks when `_lifecycle_guard_enabled()` is true (`modules.py:764-790`). On this unit's live process, PowerShell reported the environment variable absent; a mechanically independent Python import reported both absence and `_lifecycle_guard_enabled() == False`.

Most importantly, this is not inferred from configuration alone. The harness tests explicitly feed recognized catastrophic commands into `SecretGuardModule.run()` with the flag unset and assert `result.action != "block"` (`C:\Users\Prekzursil\.agents\harness\tests\test_modules.py:150-163`). The shared dispatcher is live for `PreToolUse` and its matcher includes `Bash` and `PowerShell` (`C:\Users\Prekzursil\.claude\settings.json:139-149`), so this is not a wiring absence: the module runs and intentionally allows. The implementation's comment says prose/operator judgment is the remaining floor (`modules.py:65-75,764-775`). A behavioral instruction is valuable, but it is not enforcement against an autonomous tool call.

Defense-in-depth qualification: a separate blocking `no-force-push` hook is wired for `Bash` (`settings.json:151-158`) and detects the ordinary `git push ... --force/-f` string (`C:\Users\Prekzursil\.claude\hooks\no-force-push\tripwire.py:15-47`). That separate predicate does not cover local disk/partition/registry destruction, and its regex is itself narrower than the shared lifecycle grammar. The rank remains Critical because recognized local catastrophic operations are proven allowed by the shared guard's own tests.

Confidence: it is **almost certain (90-99%)** that the present interactive shared lifecycle module will allow any recognized catastrophic input when the flag remains absent. Evidence is the enabling predicate, live two-probe environment state, run-path condition, and 39 passing branch tests. The residual 1-10% is for process-specific environment injection outside this unit and independent hooks that might separately block a particular command.

### 2. High — result-sentinel schema precedence creates false SUCCESS verdicts (VERIFIED)

`_structural_failed()` scans a fixed list of numeric code keys first. If it sees a numeric zero, it immediately returns success from the structural scan (`C:\Users\Prekzursil\.claude\hooks\tool-result-sentinel\sentinel.py:222-239`). It therefore never reaches a later `isError: true`, `success: false`, or error status in the same envelope (`sentinel.py:240-253`). A direct probe produced:

```text
SENTINEL control_isError ('FAILED', 'isError=true')
SENTINEL success_code_conflicts_with_isError ('SUCCESS', '')
```

Three additional schema misses were dynamically verified against the same known-positive control:

```text
SENTINEL boolean_error_true ('SUCCESS', '')
SENTINEL nested_content_error ('SUCCESS', '')
SENTINEL http_statusCode_500 ('SUCCESS', '')
```

Those outputs follow directly from the code: a boolean `error` value is excluded (`sentinel.py:249-253`); structural recursion visits only `output` and `result`, not `content`, `data`, or `body` (`sentinel.py:254-261`); and `statusCode` is not one of the six numeric spellings (`sentinel.py:223-230`). MCP text fallback only recognizes infrastructure phrases (`sentinel.py:77-92,271-278`), so a domain error such as permission denial inside an unvisited wrapper remains SUCCESS.

This is security-relevant when a state-changing MCP returns a heterogeneous/contradictory failure envelope and the agent proceeds as if the write succeeded. The prevalence of these exact shapes in the 93-server population counted by the pinned corpus (`C:\Users\Prekzursil\.claude\harness-sota-2026-07-18\corpus\corpus.json:13370`; independent PowerShell hashtable count output `MCP_SERVER_COUNT=93`) is **UNVERIFIED — the settling experiment is a redacted sample of real PostToolUse result schemas grouped by server/tool and field path**. Consequently, prevalence is **likely (55-80%)**, not certain; evidence is the deliberately generic all-tools sentinel (`sentinel.py:2-35`) facing a heterogeneous MCP estate, while no local schema census was available to this unit.

### 3. High — an enabled command regex is not an execution boundary (SOURCE-VERIFIED; dynamic end-to-end UNVERIFIED)

When enabled, `_is_irreversible()` recognizes a finite set of direct textual forms: two catastrophic regex families, selected Git subcommands, recursive PowerShell/cmd/shell deletions, and force-push forms (`C:\Users\Prekzursil\.agents\harness\modules.py:609-640,659-723`). The run path extracts only a string input or the dictionary's exact `command` field (`modules.py:764-782`).

This necessarily leaves composed execution surfaces outside the grammar. One concrete source-level case is a PowerShell pipeline that recursively enumerates targets before a non-recursive `Remove-Item -Force`: the recurse flag occurs before the matched deletion verb, while the implementation searches only the deletion verb's trailing arguments (`modules.py:698-704`). Interpreter-encoded commands, dynamically assembled cmdlet names, arbitrary language runtimes that call filesystem APIs, and shell aliases/functions are also outside the listed patterns.

These are not weaponized payloads and were not executed. Dynamic predicate replay for this family is **UNVERIFIED — the settling experiment is to add inert pure-predicate fixtures for composed pipelines, encoded-interpreter envelopes, aliases/functions, and library-level deletion calls, then assert a policy verdict without invoking a shell**. The source-level conclusion that the listed grammar does not parse those execution mechanisms is exact; the end-to-end conclusion that no other live hook blocks every such mechanism is **likely (55-80%)**, supported by the narrow separate force-push predicate (`no-force-push/tripwire.py:15-47`) and the shared lifecycle source, but not by a full syscall-level sandbox audit.

The finding is not “add more dangerous strings forever.” That would reproduce the false-positive failure already measured in `INPUT-known-harness-defects.md:9-50` and still remain incomplete.

## Remediation design

### R1. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — separate high-confidence catastrophic enforcement from advisory shell-risk detection

Keep a tiny always-on blocker for only high-confidence, typed catastrophic operations; move opaque/indirect shell-risk recognition to an approval/advisory lane. The blocker must consume the typed tool name and exact executable field, normalize direct Git/shell option forms, and retain the separate force-push tripwire until parity tests pass. It must not scan Write/Edit bodies. Target scope should be resolved where the tool API exposes paths; opaque interpreter or encoded-command invocation should request approval rather than pretending a denylist is complete.

This is **very likely (80-90%)** to restore meaningful coverage without recreating the documented prose false fires, because the live false positives were caused by scanning non-executable content (`INPUT-known-harness-defects.md:14-50`) and the current module already extracts the exact `command` field (`modules.py:764-782`). The settling experiment is a replay matrix containing all recorded benign mentions, current positive tests, and inert composed/indirect command fixtures. Promotion requires zero benign blocks and explicit verdicts for every catastrophic fixture. This proposal rides the existing PreToolUse dispatcher and introduces no new runtime.

An immediate blanket **CONFIG (settings/JSON only)** `HARNESS_LIFECYCLE_GUARD=1` change is rejected as the end state: it would re-enable known false-block behavior documented by the implementation itself (`modules.py:65-75`). It can be used only for an explicitly unattended, tightly scoped session after the owner accepts that tradeoff.

### R2. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — make failure evidence monotonic and schema-aware

Change sentinel precedence so any explicit high-confidence failure dominates success metadata: inspect all recognized structural fields before returning; recurse through bounded dictionaries/lists; recognize common camel/snake status variants; and treat boolean `error: true` as failure only where that field is a declared status field. Prefer per-server/tool schema adapters for ambiguous domain keys, with the generic fallback remaining conservative. Preserve the native `PostToolUseFailure` event as authoritative when present rather than re-inferring it from text; that event is already wired in `settings.json:356-377`.

This is **very likely (80-90%)** to eliminate the five verified classifier misses because each has a deterministic structural discriminator in the probe. It is only **likely (55-80%)** to improve all-server precision until real schemas are sampled; the settling experiment is a redacted stratified replay of success, domain-failure, transport-failure, and contradictory envelopes from each active MCP family. No enforcement promotion should occur for an unrecognized key solely because its English name contains “error,” preserving the lesson from `INPUT-known-harness-defects.md:63-76`.

### R3. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — throttle on state transition, not arguments alone

Key warning state by `(tool, args, verdict, reason-class)` and clear/supersede it after a successful result. This continues to suppress a literal retry loop while warning when failure class changes or a recovered call later regresses.

This is **almost certain (90-99%)** to fix the verified same-arguments/new-failure miss because the missing dimensions are exactly those omitted at `sentinel.py:316-320`; the settling experiment is a short state-machine test: failure A → identical failure A (one warning), failure B (new warning), success (clear), failure A (new warning). It is a local change to the existing hook state file.

### R4. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — normalize mutation events once for stub and duplicate consumers

Add a shared mutation adapter that emits `{operation, paths, inserted_text, is_new_file, repo_root}` for `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, and `apply_patch`, then feed both guards. Do not infer incompleteness from prose. Add high-precision language markers such as explicit Rust incompleteness macros, while leaving semantically ambiguous empty/constant bodies to a completion-claim verification lane instead of hard classification.

This is **very likely (80-90%)** to close the verified tool-route gaps because the excluded tool names are the direct cause. Language recall improvement is **likely (55-80%)** without a precision regression if additions are limited to explicit incompleteness constructs; settle it with production/test/prose fixtures per language and the existing false-positive corpus. The shared adapter reduces duplicated parsers and stays on the existing dispatcher.

### R5. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — anchor dup search at the repository root and surface bounded-search uncertainty

Resolve `git rev-parse --show-toplevel` with a timeout, fall back to `cwd` only outside Git, extend symbol forms through small language-specific patterns, and emit a one-shot “search incomplete” advisory when the file cap or search timeout is hit. Include alternate new-file mutation tools through R4. Do not hard-block duplicates.

This is **very likely (80-90%)** to fix the verified nested-`cwd` miss because the control repository already demonstrated that root choice is decisive. Coverage beyond 15,000 files is **likely (55-80%)** to improve if the cap is replaced by targeted basename/symbol queries rather than full enumeration; settle it with temporary repositories above/below the cap and ignored-file fixtures. This remains an advisory existing-bus hook, not an index service.

## Rejected alternatives and dead ends

1. **Expand a universal regex denylist.** Rejected. The current grammar is already incomplete (`modules.py:609-723`) and the measured false-positive defect came from untyped text scanning (`INPUT-known-harness-defects.md:9-50`). More strings increase both evasion surface and mention fires.
2. **Claim shell hooks are a sandbox.** Rejected. This unit verified string classification, not OS containment. Encoded/dynamic/library execution means a string predicate cannot establish syscall-level safety.
3. **Disable every guard.** Rejected. The sentinel and completion guards have passing positive controls and useful scope; the correct response is typed evidence and explicit uncertainty, not removing the safety/correctness lane.
4. **Add a daemon, guardrail framework, or second orchestrator.** Rejected by the anti-overfit gate. All identified fixes fit the existing event bus and small adapters/state machines.
5. **Dynamically execute destructive fixtures.** Rejected as unnecessary and unsafe. Pure predicates, temporary data, source-path controls, and existing tests establish the relevant branches without changing real state.
6. **Bypass the pre-execution block on the combined probe.** Rejected. Splitting non-destructive classifier probes preserved policy and itself provided evidence of the mention problem.
