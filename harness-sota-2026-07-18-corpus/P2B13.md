# P2B13 — Competitive teardown: JetBrains Junie

**Unit:** P2B13  
**Date researched:** 2026-07-18  
**Subject:** JetBrains Junie (IDE, CLI, and documented headless surfaces)  
**Comparison target:** the owner's live Claude/Codex/shared harness, not stock Claude Code  

## Executive verdict

Do **not** replace the current harness with Junie and do **not** add Junie as a second orchestration runtime. The evidence supports a much narrower import: connect the JetBrains IDE's existing MCP server to Claude/Codex, admit IDE build/inspection/debugger results as typed verification receipts, and actually use Claude Code's now-native per-subagent capability envelope. This is **very likely (80-90%)** to capture most of Junie's differentiated value for this owner because JetBrains explicitly exposes the same IDE semantics to external clients, including Claude Code and Codex, while the local harness already has the stronger dispatcher, hook, event-ledger, skill, memory, and multi-agent substrates ([JetBrains MCP documentation](https://www.jetbrains.com/help/ai-assistant/mcp.html), lines 168-230 and 417-447 in the fetched page; local `C:\Users\Prekzursil\.agents\harness\registration.py:17-34`; local `C:\Users\Prekzursil\.agents\harness\modules.py:2092-2118`).

Junie's genuinely useful ideas are:

1. IDE-indexed symbol understanding, inspections, build/test workflows, and real debugger control.
2. A visible plan-to-implementation approval boundary.
3. Per-worker tools, MCP servers, model, reasoning level, turn cap, and skills.
4. Default-deny/ask treatment of sensitive actions, with a user-editable action allowlist.
5. MCP installation and health UX that verifies startup and makes failed servers visible.
6. Completion gates with a bounded retry loop and explicit API-failure lifecycle events.

Items 2, 3, much of 4, MCP health visibility, and the Stop retry cap are already native in Claude Code 2.1.214. The owner's live configuration simply does not use all of them. Junie's agent loop itself is not frontier architecture: it is the familiar plan → tool use/edit → test/inspect → report loop. Its advantage comes from JetBrains' semantic IDE tools and coherent product UX, not a demonstrably superior reasoning runtime.

The highest-value ports are therefore:

| Priority | Port | Our-side classification | Verdict |
|---|---|---|---|
| P0 | Enable a narrow JetBrains IDE MCP toolset for Claude/Codex | **CONFIG (settings/JSON only)** | Do, conditional on live IDE readiness |

| P0 | Stop using global `bypassPermissions` for interactive/research workers | **NATIVE (Claude Code already does this; we just enable it)** | Do by launch profile, not by weakening unattended jobs indiscriminately |
| P1 | Register and ledger `StopFailure` and `SessionEnd` | **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** | Do |

| P2 | Add a persistent plan artifact convention for large tasks | **NATIVE (Claude Code already does this; we just enable it)** | Use native editable Plan mode; no new planner |
| Reject | Add Junie as an orchestrator or automatic model-routing runtime | **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** | Reject under the anti-overfit gate |

## Capability teardown

## 1. Agent loop

### What Junie does

Junie Code mode decomposes a prompt into a multistep plan, executes it with terminal/file/MCP/IDE tools, runs tests, verifies changes, and reports progress. Ask mode is read-only. CLI Plan mode performs read-only exploration, writes a structured design document, pauses for refinement or confirmation, and only then switches to implementation. The plan commonly separates requirements, technical design, testing, and delivery steps ([IDE plugin](https://junie.jetbrains.com/docs/junie-ide-plugin.html), code/ask modes; [Plan mode](https://junie.jetbrains.com/docs/junie-cli-plan-mode.html), sections “How Plan mode works” and “Plan view”).

Junie also accepts real-time follow-ups while working; queued clarifications are appended to the task and considered immediately ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html), “Real-time follow-ups”). It can run headless in CI and exposes local review workflows for branch/commit/unstaged diffs.

### Comparison

This loop is parity, not a reason to replace the harness. Claude Code has native read-only Plan mode, an editable plan (`Ctrl+G`), explicit approval into selected permission modes, background subagents/forks, mid-task steering, and headless execution ([Claude permission modes](https://code.claude.com/docs/en/permission-modes); [Claude subagents](https://code.claude.com/docs/en/sub-agents)). The local harness adds front-loaded EVPI clarification, goal re-injection, long-operation monitoring, terminal-state results, event-ledger evidence, and claim gates.

Junie's plan-as-document UX is cleaner. However, the capability is already **NATIVE (Claude Code already does this; we just enable it)**. It is **very likely (80-90%)** that using Claude's native Plan mode for non-trivial changes captures the value without a new planner because both products enforce read-only exploration and a user approval boundary; the evidence is the two first-party Plan-mode contracts. The remaining difference—Junie's `.junie/plans` location and tabbed IDE view—is presentation, not a new reasoning mechanism.

**UNVERIFIED:** JetBrains' GA post says users can plan on a powerful model and implement on a cheaper one, but the public Plan-mode page does not specify an auditable model-switch contract. A controlled Junie run with `/usage` before and after plan confirmation would settle whether the switch is automatic, manually selected, or marketing shorthand. Do not build a model router on this premise.

### What not to copy

Do not add a second plan state machine or durable-execution runtime. That would violate the anti-overfit gate and recreate state already represented by native Plan mode, the task plan, the event ledger, and artifacts. **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** is the honest classification for a separate Junie-style orchestration runtime, and the evidence does not justify it.

## 2. Context management

### What Junie does

Junie's IDE connection supplies project-index awareness: symbol-aware search, project structure, inspections, test discovery, refactorings, product-specific actions, open-file context, and `@` completion for classes and symbols ([IDE integration](https://junie.jetbrains.com/docs/junie-cli-jetbrains-ide-integration.html), lines 44-64 in the fetched page). In the IDE, automatic context attaches the active file and selected text; other open or recently edited files are not automatically included ([JetBrains AI Junie help](https://www.jetbrains.com/help/ai-assistant/junie-agent.html), “Collect IDE context”). CLI users can explicitly attach files/folders/images with `@`.

For long conversations, Junie uses a helper model for context summarization. The selected primary model handles main reasoning/code, while an automatically selected same-provider helper handles summarization, routing, memory extraction, and capability filtering ([model selection](https://junie.jetbrains.com/docs/junie-cli-model-selection.html), “How Junie uses models internally”).

### Comparison and gaps

Claude Code's JetBrains plugin already supplies selection context, native diffs, and diagnostic sharing, so those are **NATIVE (Claude Code already does this; we just enable it)**, not Junie-only ([Claude JetBrains integration](https://code.claude.com/docs/en/jetbrains), lines 115-119 and 301 onward). The owner's config does not prove that plugin is live; absence cannot be claimed from JSON because the plugin's hidden `ide` MCP server is intentionally not shown in `/mcp`.

The real gap is the broader JetBrains semantic tool surface: explicit builds, IntelliJ inspections, symbol documentation, modules/dependencies, run configurations, and debugger state. JetBrains' bundled MCP server exposes these to external clients, including Claude Code and Codex. This is **CONFIG (settings/JSON only)** from our side: enable the bundled MCP server, expose a narrow tool list, and auto-configure the existing client.

**UNVERIFIED recommendation — local readiness:** Enable `build_project`, `get_file_problems`, and `get_symbol_info`, plus the debugger toolset only for active debugging tasks. This is **likely (55-80%)** to improve grounded diagnosis and post-edit verification because the official tool schemas return compiler errors, inspection severity/location, symbol declarations, and runtime stack/frame values. Local readiness is UNVERIFIED because no current JetBrains MCP config exists and this unit did not launch the IDE. The settling experiment is: open the actively used JetBrains IDE, inspect Settings → Tools → MCP Server and Exposed Tools, then make one successful read-only call to each selected tool from Claude and capture its exact result shape.

Automatic helper-model summarization is not worth porting. Implementing a hidden router/summarizer would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and would reintroduce orchestration complexity. Claude already auto-compacts; the harness has explicit compaction checkpoints and basic-memory. Junie's opaque helper calls are worse for auditability.

## 3. Memory

### What Junie does

Junie's public “Guidelines and memory” documentation primarily describes persistent instruction files: project `.junie/AGENTS.md`, root `AGENTS.md`, legacy `.junie/guidelines*`, and global `~/.junie/AGENTS.md`. It merges global and project guidelines, gives project instructions precedence, and deduplicates identical content ([Guidelines and memory](https://junie.jetbrains.com/docs/guidelines-and-memory.html)). The model-selection page additionally says a helper model performs “extracting information for memory,” but it does not document the memory store, schema, retention, retrieval, provenance, user controls, or conflict resolution.

Junie CLI retains full context for the last ten sessions and preserves prompt history; sessions can be resumed from task history ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html)).

### Comparison

There is no demonstrated Junie memory advantage. The owner has cross-tool basic-memory, compaction checkpoints, a lexical recall index, injection defenses, and an event ledger. Historical corpus use proves that this is live rather than aspirational. The harness also nudges a memory write when canonical configuration changed without one (`modules.py:2267-2314`).

**UNVERIFIED:** Junie's “extracting information for memory” may indicate an undocumented learned-memory layer, but the public docs do not establish one. A settling experiment is to run two fresh Junie sessions against a novel, non-AGENTS preference, inspect all files under `~/.junie` before/after, and test whether the preference is recalled without transcript resumption. Until then, no recommendation may depend on that premise.

If the experiment proves automatic durable extraction, a narrow opt-in memory-extraction Stop hook would be **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**, not a new database: emit candidate facts with source session/turn, require owner confirmation for preferences, then call the existing basic-memory MCP. It is **unlikely (20-45%)** to outperform the current explicit nudge enough to justify its false-memory risk; evidence is the current 408 successful memory writes and D4's warning that orchestrator-authored “facts” can spread unchecked.

### What not to copy

Do not replace basic-memory with Junie's opaque mechanism or a vector/KG store. That would reintroduce an explicitly rejected component and lose cross-tool continuity and provenance. Junie's ten-session retention is materially weaker than the local all-session corpus plus semantic store.

## 4. Tools and MCP handling

### What Junie does

Junie supports built-in file/search/shell/web tools and local or remote MCP servers. Its MCP Installation Assistant searches the official registry, collects parameters and secrets, writes project/user configuration, supports OAuth for remote servers, starts the server, verifies startup, and displays `Starting`, `Active`, `Inactive`, `Disabled`, `Failed`, or `Authorization required` states ([MCP configuration](https://junie.jetbrains.com/docs/junie-cli-mcp-configuration.html)). Junie can enable/disable servers interactively and show their tools. The IDE limits the effective MCP surface to 100 tools.

Custom subagents can specify an MCP-server allowlist; other configured servers are hidden. Junie also bundles skills, subagents, commands, MCP configs, and guidelines into installable extensions that can hot-load in a running session ([Extensions](https://junie.jetbrains.com/docs/junie-cli-extensions.html)).

### Comparison and gaps

Claude Code already has `claude mcp add/list/get/remove`, `/mcp` status, OAuth, project approval, server deduplication by precedence, tool search, `/doctor`, plugin-bundled MCP lifecycle, and per-agent `mcpServers` ([Claude MCP](https://code.claude.com/docs/en/mcp); [Claude troubleshooting](https://code.claude.com/docs/en/troubleshooting)). Therefore the installation/health surface is mostly **NATIVE (Claude Code already does this; we just enable it)**. The harness also has skills for MCP troubleshooting/curation and a drift monitor.

What is missing operationally is *enforcement of the live roster*. The corpus's 135 “not connected” calls to a dead Tavily server prove that available health signals did not prevent selection. Junie's UI alone would not guarantee that either; the transferable mechanism is per-worker MCP exposure.

Use each agent definition's native `mcpServers` and `disallowedTools: mcp__*`/specific server patterns so a worker sees only task-relevant, live servers. This is **NATIVE (Claude Code already does this; we just enable it)**. It is **very likely (80-90%)** to reduce dead-server selection and tool-schema/context fan-out because hidden servers cannot be selected and Claude's docs explicitly say inline per-agent servers connect only for that worker. Evidence: zero of 18 local agents uses `mcpServers`; the corpus has 93 servers touched and the highest-error surface is dead MCP.

Do not copy Junie's fixed 100-tool ceiling. Tool search and scoped server exposure are better than a global truncation threshold, especially for a catalog this large. A fixed cap could silently hide the only relevant tool.

### MCP setup assistant assessment

Junie's assistant is better UX than hand-editing JSON, but building another registry installer would be **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** only if implemented as a thin wrapper over `claude mcp add`, `/doctor`, and the official registry. It is **unlikely (20-45%)** to be higher leverage than fixing roster exposure because the current failure is not lack of installation tooling; it is continued calls after a server is known dead. Prefer native tools plus preflight.

## 5. Permission model

### What Junie does

By default, Junie asks before terminal commands, MCP tools, outside-project reads/writes, build-script edits, builds/tests/previews, and other sensitive actions. Its allowlist supports exact/pattern terminal rules and action categories. CLI rules are ordered first-match `allow`/`ask` entries for file editing, executables, MCP tools, and outside-project reads. Brave mode has Off, Auto (safety classifier), and On. Plan/Ask modes are read-only. `.aiignore` protects file contents behind explicit approval, though file names remain visible and Brave mode or allowlisted commands can bypass that protection ([Action Allowlist](https://junie.jetbrains.com/docs/action-allowlist.html); [CLI allowlist](https://junie.jetbrains.com/docs/action-allowlist-junie-cli.html); [IDE plugin](https://junie.jetbrains.com/docs/junie-ide-plugin.html)).

### Comparison and actual gap

The live owner configuration is materially less safe for interactive work: `bypassPermissions`, allow `Bash`, `Edit`, `Write`, broad MCP families, and additional directories `C:` and `D:` (`settings.json:26-75`). There are explicit denies for `.env`, PEM, and credentials, but bypass mode skips the ordinary permission layer.

Claude Code already has `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, and `bypassPermissions`, plus allow/ask/deny rules and per-agent modes. This is **NATIVE (Claude Code already does this; we just enable it)**. It is **almost certain (90-99%)** that an interactive/research launch profile using `default`, `plan`, or `dontAsk` is safer than global bypass because the native contract explicitly gates writes/sensitive tools and the current config explicitly bypasses those gates. The uncertainty is only workflow cost, not security direction.

Concrete port:

1. Keep `bypassPermissions` only for explicitly isolated/unattended contexts.
2. Launch interactive code work in `acceptEdits` or `auto`; launch audit/research agents in `plan` or `dontAsk` with read-only `tools`.
3. Put `permissionMode`, `tools`, and `disallowedTools` in user/project agent files, not plugin agent files (Claude ignores these security fields for plugin agents).
4. Use `mcpServers` to restrict external authority per worker.
5. Add `isolation: worktree` for mutating parallel workers.

Important native limitation: Claude documents that a parent in `bypassPermissions` or `acceptEdits` can override a subagent's stricter `permissionMode`. Therefore simply adding `permissionMode: plan` to local agents while the parent remains bypassed is not an enforcement boundary. A separate safe parent launch profile is required.

Junie's `.aiignore` is a small real gap because Claude's JetBrains integration does not consume that file as a universal privacy boundary. Port only secrecy/privacy patterns into Claude `permissions.deny`; this is **CONFIG (settings/JSON only)**. It is **likely (55-80%)** to reduce accidental sensitive-file ingestion because deny rules also block IDE selection sharing, but the mapping is not semantically identical. Test with one known-denied canary file through Read, IDE selection context, and a shell command before broad rollout.

### Where Junie is worse

- In the IDE allowlist, an MCP rule currently authorizes *all* MCP tools; it cannot scope an individual server/tool. Claude can scope exact MCP tool patterns and per-agent servers.
- `.aiignore` can be bypassed by Brave mode and by an allowlisted command that reads the ignored path. It is not a sandbox.
- “Allow similar commands” generates regex rules. D1 shows this owner's regex/prose detectors already suffer semantic-role false positives; generated regex permissions require a check-command test and adversarial chained-command fixtures before trust.

## 6. Customization: rules, skills, commands, extensions, hooks

### Rules and skills

Junie reads standard `AGENTS.md`, supports global/project precedence and deduplication, discovers open Agent Skills, and can import compatible instructions/skills/commands/MCP configs/agents from Claude Code, Codex, or Cursor. Extensions bundle these artifacts for marketplace distribution.

The harness is already stronger here: about 355 installed skills, 78 observed invoked skills, cross-tool AGENTS behavior, 85 rule files, 18 live custom agent files, and plugins. Agent Skills are portable across Junie, Claude, and Codex ([JetBrains Agent Skills article](https://blog.jetbrains.com/idea/2026/03/ai-assisted-java-application-development-with-agent-skills/)). No new rules format should be created. Use root `AGENTS.md`; do not create `.junie/guidelines.md` copies.

Hot-loaded extension bundles are **NATIVE (Claude Code already does this; we just enable it)** through Claude plugins and `/reload-plugins`. Junie's marketplace is not a capability gap. Given the measured 1,293 orphaned plugin directories and Windows command-line overflow, copying another extension cache is actively contraindicated.

### Hooks

Junie's EAP hooks support `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `Stop`, `StopFailure`, `PermissionRequest`, and `SessionEnd`. PreToolUse can allow/ask/block, rewrite input, and inject context. Stop can gate submission, retry with feedback, or hard-halt. An eight-consecutive-block cap bounds runaway loops. Project-local hooks are ignored unless explicitly passed, which is a sound trust boundary ([Junie hooks](https://junie.jetbrains.com/docs/junie-cli-hooks.html)).

The local harness already has broader hooks: `PostToolUse`, `PostToolUseFailure`, compaction, config, subagent, task, teammate, worktree, and permission-denied events (`registration.py:17-34`). It also already suppresses re-entrant Stop nudges after the first continuation (`modules.py:2054-2067`) and Claude itself has an eight-continuation cap. Junie's cap is parity.

The actual local gap is `StopFailure` and `SessionEnd`. Claude Code 2.1.214 natively emits both, but the shared registration does not subscribe. Porting requires adding event fields (`error`, `error_details`, `reason`, optional duration/message), adapter normalization, registration/timeouts, and event-ledger records. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. It is **very likely (80-90%)** to improve failure attribution and cleanup because the corpus has 5,692 error fingerprints while the current dispatcher receives neither API-stop classes nor session termination; the native wire contracts are documented.

Do not infer this will fix D3. **UNVERIFIED:** hook outputs may still not appear in transcripts. The settling experiment is to trigger a known `StopFailure` against a test endpoint, then independently check (a) the event ledger for the classified error and (b) the transcript for the hook event/system message. Success requires both a ledger event and a known-positive detector control; transcript absence is acceptable only if the ledger is durable.

### Where Junie hooks are worse

- Hooks are EAP.
- Junie lacks `PostToolUse` and `PostToolUseFailure`; its own docs say tool-error coverage is future work.
- ACP and server hosts do not invoke hooks.
- Hook stdout/stderr is logged but not stored in session history.
- Hooks inside one entry run sequentially.
- Stop does not run for chat-type tasks.
- Only command hooks are supported, while Claude supports command, HTTP, prompt, agent, and MCP-tool hooks across appropriate events.

These are decisive reasons not to move harness authority into Junie.

## 7. Multi-agent and parallel work

### What Junie does

Junie CLI custom subagents are Markdown/YAML definitions selected automatically by name/description. Each gets an independent context and returns its result to the main agent. Fields include `tools`, `disallowedTools`, `mcpServers`, `model`, `reasoningLevel`, `maxTurns`, `skills`, and prompt arguments. SameModelOnly uses same-model parallelism; Auto may also select cheaper model tiers. This feature is EAP ([Custom subagents](https://junie.jetbrains.com/docs/junie-cli-subagents.html)).

The CLI can keep several live top-level sessions running in one terminal and switch through task history. Parallel sessions share files unless the user creates/switches a Git worktree. `/worktree` can create sibling worktrees and optionally transfer uncommitted changes using `git stash` ([Parallel sessions and worktrees](https://junie.jetbrains.com/docs/junie-cli-worktrees.html)).

### Comparison

Claude Code 2.1.214 now exceeds Junie on core multi-agent mechanics: explicit and automatic invocation, foreground/background workers, nested subagents, forks with inherited context, resumable subagent transcripts, direct steering, agent teams, per-agent persistent memory, native worktree isolation, and a configurable per-session spawn cap. The owner's corpus shows heavy real use: 1,158 `general-purpose` invocations, 124 forks, 101 Explore, and 22 observed agent types (`corpus.json#/capability_use/agents_invoked`).

The capability gap is not multi-agent support; it is failure to use the full native worker envelope. All 18 local agents have tools/model, but none has `disallowedTools`, `permissionMode`, `mcpServers`, `maxTurns`, `skills`, or `isolation`. Enable those fields. This is **NATIVE (Claude Code already does this; we just enable it)** and **very likely (80-90%)** to reduce capability leakage and context/tool fan-out because Claude enforces the fields at launch and refuses an agent whose tool allowlist resolves to nothing.

Concrete profile examples to encode in existing agent frontmatter:

- Audit/research: `tools: [Read, Glob, Grep, WebSearch]`, `disallowedTools: [Edit, Write, Bash, PowerShell, mcp__*]`, `permissionMode: plan`, `maxTurns: 20`, selected research skills.
- Code reviewer: read/grep plus build/inspection MCP only; no writes; `memory: project` only if its outputs are explicitly curated.

## 8. Verification and self-checking

### What Junie does

Junie combines several verification layers:

1. Code mode runs tests and verifies changes before reporting completion.
2. IDE-backed builds and inspections return compiler/semantic diagnostics.
3. Debug mode drives a real debugger: start/attach, breakpoints, stepping, stack/thread/frame inspection, and expression evaluation ([Junie agent help](https://www.jetbrains.com/help/ai-assistant/junie-agent.html); [JetBrains MCP debugger tools](https://www.jetbrains.com/help/ai-assistant/mcp.html)).
4. The Done panel provides diffs and file-by-file reversion.
5. Local `/review` reviews branch/main, last commit, or unstaged changes.
6. Stop hooks can block completion until tests/checks pass, with the eight-continuation limit.

### Comparison and real gap

The harness has a stronger abstract verification design: typed receipts, freshness relative to mutation, claim families, known-positive controls, and a completion-language gate. But the classifier accepts command-shaped tools only (`ledger.py:262-280,383-403`). JetBrains IDE results therefore cannot currently satisfy it.

Add an IDE receipt adapter. This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. The concrete mechanism:

1. Match exact MCP tool identities for `build_project`, `get_file_problems`, and selected test/debug tools.
2. Parse only documented structured fields; never treat prose summaries as proof.
3. Emit receipt classes such as `build`, `inspection`, `test`, and `runtime-debug` with `pass|fail|unknown`, counts where available, project/file scope, tool/server identity, timestamp, and a hash of normalized input+result.
4. Require project path and file scope to match the current task/worktree.
5. Treat timeout, partial result, missing status, or schema drift as `unknown`, never pass.
6. Add one successful and one failing fixture captured from the live IDE for each tool.
7. Feed receipts through the existing `has_fresh_receipt` path; do not create a second verifier.

It is **very likely (80-90%)** that this improves verification quality for JetBrains-supported projects because it converts semantic compiler/inspection evidence into the exact ledger signal the claim gate already trusts. Evidence is the official structured tool contract plus the proven local command-only classifier gap.

**UNVERIFIED:** Exact live JSON result shapes may differ by IDE/language/plugin version. The recommendation heading therefore inherits UNVERIFIED until one pass and one fail result are captured. The settling experiment is the three-tool probe described under Context, followed by classifier fixtures that assert fail-closed behavior on missing/changed fields.

### Where Junie verification is worse

- “Runs tests and verifies” is an agent behavior claim, not a typed proof contract. Public docs do not document receipt freshness, mutation ordering, or what constitutes a passing task.
- IDE build/test allowlist support is explicitly concentrated on JVM IntelliJ and C# Rider in the Action Allowlist docs; coverage is product/language dependent.
- Junie has no documented known-positive-control requirement before declaring absence.
- Its hook output is not preserved in session history, and ACP/server hooks do not run.
- Vendor claims that Junie “makes sure every change meets your standards” are marketing language, not evidence of complete verification.

## Risks and falsification tests

1. **IDE integration may not be usable on the active installation — UNVERIFIED.** Open the IDE and inspect the MCP Server plugin/status. Known-positive: verify an exposed `get_symbol_info` tool appears. Negative claim is allowed only after that control.

## Final assessment

Junie is a strong integrated product whose best feature is the JetBrains semantic environment. It is not evidence for a better standalone harness architecture. The owner already has a richer and more auditable agent substrate; the problem is that native controls and IDE evidence are not consistently connected to it.

The radical option—full replacement—is therefore considered and rejected on evidence, not conservatism. Replacement would trade away broad hooks, typed proof freshness, event-ledger continuity, cross-tool memory, a much larger skill catalog, and mature multi-agent control to gain IDE semantics that JetBrains already exports over MCP. It is **very likely (80-90%)** that this is a dominated trade because the unique value is available as a configuration/adapter layer without taking Junie's runtime.

The ambitious path is compositional: keep one orchestration authority, make workers capability-minimal, admit semantic IDE evidence as first-class proof, and observe every failure/termination in the same ledger. That expands into runtime debugging and IDE-indexed verification without adding a second brain.
