# F035 — red team: cross-session → persist

## Executive verdict

The most plausible harness-specific persistence chain is **untrusted MCP/web content in session A → autonomous edit of the shared user settings → attacker-controlled `SessionStart` command hook → execution in session B and again after a Claude restart**. This is not a generic “prompt injection might be bad” scenario: this installation combines (1) a heavily used MCP ingestion surface, (2) a silent-by-default injection detector with incomplete tool-name coverage, (3) `bypassPermissions`, broad `Edit`/`Write`/`Bash` permission, and both drives in scope, and (4) a global user settings file whose hooks execute at session start.

**Likelihood:** **very likely (80-90%)** that a model-followed injection could place a syntactically valid persistent hook once it decides to do so. Evidence: the live snapshot grants `Edit`, `Write`, and `Bash`, uses `defaultMode: "bypassPermissions"`, and adds `C:` and `D:` at `C:\Users\Prekzursil\.claude\settings.json:26-75` (bundle: `/local_disk0/codexwork/bundle/claude/settings.json:26-75`); the canonical-edit guard deliberately excludes `~/.claude/settings.json` at `C:\Users\Prekzursil\.agents\harness\modules.py:835-862`; and Claude documents that user settings are global to every project and that hooks are lifecycle commands ([settings scope](https://code.claude.com/docs/en/settings), [hooks reference](https://code.claude.com/docs/en/hooks)). This is a feasibility estimate, not evidence that compromise has occurred.

**Impact:** **almost certain (90-99%)** execution in later Claude sessions if a valid malicious `SessionStart` command is admitted and no higher-priority managed policy excludes user hooks. Evidence: this snapshot already registers command handlers on every `SessionStart` at `settings.json:82-115`, and Claude documents `~/.claude/settings.json` as machine-local, all-project scope and `SessionStart` as firing when a session begins or resumes ([hooks, lines 186-215 and 321-331](https://code.claude.com/docs/en/hooks); [settings, “When edits take effect”](https://code.claude.com/docs/en/settings)). The remaining managed-policy condition is **UNVERIFIED**; reading `C:\Program Files\ClaudeCode\managed-settings.json` and checking `/status` “Setting sources” would settle it.

No exploit was run. No payload, executable command, credential value, or exfiltration endpoint is included below.

## Assets and trust boundary actually crossed

Session A and session B run as the same Windows owner and consume the same `~/.claude/settings.json`. The settings file is therefore a cross-session control plane, not session state. A hook stored there is persistent data plus an execution trigger.

The attack does not require stealing credentials to persist. Credentials increase post-trigger impact, but the chain succeeds at its stated goal as soon as later-session code execution occurs. This distinction keeps the finding grounded and avoids claiming exfiltration that was never tested.

The pinned corpus shows the ingress is exercised rather than hypothetical: 93 MCP servers were touched; examples include `tooluniverse` 1,864 uses, `firecrawl` 1,259, `claude-in-chrome` 1,067, and `search-hub` 630 (`corpus.json:capability_use.mcp_servers_used`). Core mutation tools are also routine: Bash 108,121 calls, Edit 28,964, and Write 12,845 (`corpus.json:tool_usage`). These counts establish exposure frequency, not compromise frequency.

## Concrete attack chain

### Step 1 — attacker controls content returned through a normal ingestion lane

The attacker places instruction-like text in a page, repository document, MCP response, or MCP initialization instructions that session A is asked to inspect. The most plausible concrete lane for this harness is a generic MCP result whose qualified tool name is not in `_INGEST_TOOLS`, because the installed fleet is broad and routinely used.

The harness scans results only if the tool name contains one of the fragments at `modules.py:912-930`; the branch at `modules.py:1150-1158` otherwise returns success without scanning. Prior audit F04 independently exercised representative names and reported that `mcp__deepwiki__read_wiki`, `mcp__context7__query-docs`, `web__run`, `Bash`, and `Read` all returned `allow` for the same canonical test string while `WebFetch` was detected (`audit-findings/F04.md:F2`).

Even on a covered tool, the result is not isolated by default. `injection_quarantine` is heuristic, and heuristics resolve to shadow at `modules.py:138-142`; `stage()` logs and returns success in shadow mode at `modules.py:389-417`. The actual quarantine is only an added warning at `modules.py:1144-1168`, not output replacement. Official Claude hooks support `PostToolUse.updatedToolOutput`, but the shared result model/adapter does not expose it (verified in `audit-findings/F04.md:F4`).

**Likelihood:** **likely (55-80%)** that an attacker can arrange delivery through an uncovered or nonmatching lane, given 93 historically touched MCP servers and the exact allowlist structure. Whether a particular remote server currently returns attacker-controlled content is **UNVERIFIED**; an inert integration test that returns a fixed canary through every live MCP/tool envelope and records names would settle it.

### Step 2 — injected content reframes a global-settings mutation as harness repair

The content instructs session A to make a “required compatibility/security repair” in the owner’s global Claude settings and to verify that a startup helper is registered. This framing matches the harness’s genuine maintenance vocabulary and is more plausible than an overt malware request.

The agent does not need a permission escalation:

- `Edit`, `Write`, and `Bash` are allowed at `settings.json:26-63`.
- `defaultMode` is `bypassPermissions` at `settings.json:71`.
- `additionalDirectories` includes both drives at `settings.json:72-75`.
- `PreToolUse` does invoke the shared harness for Edit/Write/Bash at `settings.json:139-149`, but the relevant guard is not a deny for this target.

The write may be a structured edit after reading the file, so the common “File has not been read yet” tool interlock is not a security boundary. It only changes the attacker’s sequencing.

### Step 3 — session A adds a persistent startup handler without touching the guarded hook tree

The mutation adds one `SessionStart` command handler directly to the `hooks` object in `~/.claude/settings.json`. To keep this report non-operational, the handler’s command and payload are intentionally omitted. The command could reference an already reachable attacker-influenced executable path or encode its behavior in the declaration; therefore writing a second script under `~/.claude/hooks` is not required.

This target is a deliberate blind spot in the canonical-edit guard. `_canonical_config_edit_guard()` classifies only the deployed harness, skills, and hooks trees, and its own comment names `~/.claude/settings.json` as an ordinary hand-maintained file that must stay silent (`modules.py:835-862`). The dedicated regression test forces the gate to enforce and still asserts `allow` for this exact path (`tests/test_modules.py:2162-2175`). Those are mechanically independent implementation and test signals.

**Likelihood:** **very likely (80-90%)** that this mutation passes the bundled PreToolUse harness once proposed, because both the predicate and its positive regression test explicitly allow the target. A separate local `file-scope` hook is registered for Edit/Write at `settings.json:218-226`, but its code was not included in the bundle; whether it independently blocks this path is **UNVERIFIED**. A safe fixture invocation with a temporary fake user-settings path would settle that without changing live configuration.

### Step 4 — current drift detection observes too late and does not prevent the write

`ConfigChange` fires after the configuration file changes; the live snapshot routes it to the shared dispatcher at `settings.json:406-417`. Anthropic documents that a `ConfigChange` hook can block the new setting from being applied to the **running session**, but this does not make the filesystem write a pre-write transaction ([ConfigChange decision control](https://code.claude.com/docs/en/hooks)).

The bundled implementation supplies even less protection:

1. `_config_drift()` reads the already-written settings and an install receipt (`modules.py:864-880`).
2. The deployed `installed.json` contains `installed_at`, hashes, deploy metadata, and file hashes, but no `settings` object (`installed.json:1-49`).
3. With no `settings` object, `_config_drift()` explicitly returns success (`modules.py:882-889`). The regression test explicitly requires silence on this receipt shape (`tests/test_modules.py:1431-1455`). This is a second independent signal.
4. Even if a fresh baseline existed, the gate is heuristic/shadow by default (`modules.py:138-142`, `:906-909`). Its test asserts the changed MCP settings return `allow` by default (`tests/test_modules.py:1367-1386`).
5. Even when manually promoted to enforce, `_config_drift()` creates `action="inject"`, not `block` (`modules.py:897-909`); the test expects `inject`, not denial (`tests/test_modules.py:1400-1428`). Thus promotion would warn after mutation rather than veto application.

The conclusion that **this bundled drift control does not stop the chain** is **almost certain (90-99%)**, supported by the deployed receipt shape, the fail-open branch, the mode ladder, and two regression-test expectations. The residual 1-10% is host behavior outside this bundle, particularly a managed policy or an omitted local hook.

### Step 5 — another concurrent or later session consumes the shared change

Claude watches settings and reloads most keys, including hooks, during a running session; the official settings documentation says changes trigger `ConfigChange` and that user settings apply to every project ([settings, lines 173-194 and 226-230](https://code.claude.com/docs/en/settings)). A concurrent session B can therefore encounter the new global handler without sharing A’s transcript or cwd. At minimum, a newly started B loads it.

No cooperation bus is required. Shared filesystem identity is the cross-session bridge.

### Step 6 — restart re-triggers persistence

After Claude exits, `~/.claude/settings.json` remains. On the next start or resume, the admitted `SessionStart` command executes. Existing snapshot entries demonstrate this lifecycle in use (`settings.json:82-115`), and official documentation identifies `SessionStart` as firing when a session begins or resumes ([hooks lifecycle](https://code.claude.com/docs/en/hooks)). The handler can then restore other files if they were cleaned, act under the new session’s environment, or simply execute again. Those possible follow-on actions are not needed to establish persistence and were not tested.

**Persistence confidence:** **almost certain (90-99%)** conditional on the handler being admitted by effective policy. The effective managed-policy condition remains **UNVERIFIED**; a cold-start canary using a harmless marker handler in an isolated Windows test profile would settle exact reload/restart behavior.

## Does an existing control stop it?

### Control 1: PreToolUse canonical-edit gate — no

It intentionally ignores `~/.claude/settings.json` (`modules.py:845-850`), and the exact regression test asserts allow even in enforce mode (`tests/test_modules.py:2162-2175`). This is verified with two independent signals.

### Control 2: ConfigChange/config-drift — no

It is post-write, the deployed receipt has no baseline, the no-baseline path is fail-open, the default is shadow, and “enforcement” yields only an injection. Implementation evidence is `modules.py:864-909`; independent receipt evidence is `installed.json:1-49`; independent behavioral-contract evidence is `tests/test_modules.py:1367-1386,1400-1455`.

### Control 3: injection quarantine — not reliably

It is silent in default shadow mode and tool-name gated (`modules.py:138-142,389-417,912-930,1144-1168`). Prior audit F04’s pure probes provide an independent behavioral signal. It might warn for some exact English patterns on covered tools if explicitly promoted, but a warning is not isolation or a mutation deny.

### Control 4: native permission system — no in this snapshot

The owner configuration gives the needed tools broad permission and chooses `bypassPermissions` (`settings.json:26-75`). Claude’s native setting `disableBypassPermissionsMode` exists specifically to prevent this mode ([settings reference, permission settings](https://code.claude.com/docs/en/settings)), but it is not present in the bundled user snapshot. This statement is limited to the bundle; an overriding managed source is **UNVERIFIED**.

### Control 5: managed-hooks-only policy — potentially decisive, effective state UNVERIFIED

Claude natively supports `allowManagedHooksOnly: true` in managed settings. Official documentation says it excludes user, project, and ordinary plugin hooks while retaining managed hooks and hooks from plugins force-enabled by policy ([hook locations](https://code.claude.com/docs/en/hooks), [hook configuration](https://code.claude.com/docs/en/settings)). That would stop the malicious user `SessionStart` declaration from loading.

I cannot honestly say whether this control is already active. The Linux bundle does not contain `C:\Program Files\ClaudeCode\managed-settings.json`, but that is not evidence of absence. Same-day audit claims conflict: `A25.md:F1`/`A29.md:F1` recorded the file missing earlier, while `E06.md:F3` later cites `managed-settings.json:1-4`. Neither reproduced those lines in the provided bundle. The settling experiment is two-part: (1) read that exact Windows path without values beyond relevant policy keys, and (2) run `/status` to verify the active managed source and then use an isolated harmless user-hook canary to confirm it is ignored. Until then, the overall live-host result is **UNVERIFIED**.

## Minimal mitigation — UNVERIFIED effective-state prerequisite

### NATIVE (Claude Code already does this; we just enable it)

Place the vetted lifecycle hook registrations in administrator-controlled Windows managed settings and set `allowManagedHooksOnly: true`; remove the equivalent executable registrations from user settings only after a test profile proves parity. The prerequisite—whether a managed settings file already exists and what it contains—is **UNVERIFIED**; the read + `/status` + harmless canary experiment above settles it.

Why this is the minimum:

- It directly severs this chain at the persistence trigger. Session A may still write a malicious user hook declaration, but Claude will not load it in session B or after restart.
- It uses Claude’s existing policy and hook buses. It adds no daemon, MCP, memory substrate, orchestration runtime, trained critic, observability service, or guardrail framework.
- It preserves the owner’s existing hooks by moving the reviewed set to the higher-trust source rather than disabling all hooks.
- Managed policy cannot be overridden by user/project settings, and official documentation says `policy_settings` changes cannot be blocked by lower-level hooks ([settings precedence](https://code.claude.com/docs/en/settings), [ConfigChange](https://code.claude.com/docs/en/hooks)).

**Expected effectiveness:** **almost certain (90-99%)** against this exact user-hook persistence chain, because the vendor contract explicitly excludes user hooks when the flag is true. The remaining uncertainty is version/effective-source deployment on this Windows host; an isolated cold-start test settles it.

Deployment acceptance tests, all harmless and names-only:

1. `/status` reports the administrator/file managed source.
2. A managed `SessionStart` canary fires once in a test profile.
3. A user-settings `SessionStart` canary does not fire in the same profile.
4. A restart repeats (2) and continues to suppress (3).
5. Existing reviewed hook inventory matches the intended managed inventory; do not infer parity from process exit alone.

Rollback is a managed-policy file restore performed with Claude closed. Do not first delete the current user hook block: that risks removing protections before managed parity is proven.

### CONFIG (settings/JSON only)

After the managed-hooks-only canary is green, disable bypass mode with managed `disableBypassPermissionsMode: "disable"` and replace broad mutation permission with exact, owner-approved rules. This reduces the chance that session A can modify other persistence surfaces even though `allowManagedHooksOnly` already neutralizes this hook lane.

**Expected effectiveness:** **very likely (80-90%)** as a general reduction in autonomous persistence opportunities, based on the native permission contract and this snapshot’s current maximum-autonomy settings. Exact workflow friction and bypasses through allowed shell forms are **UNVERIFIED**; replay a frozen set of ordinary Edit/Write/Bash tasks plus inert attempts targeting user config to settle both security and false-positive rates.

### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

If the owner intentionally retains user hooks, change the existing ConfigChange lane to compare a signed/reviewed hook allowlist and return native `decision: "block"` for unapproved user hook changes. Also make the deploy receipt include the settings baseline. This is second-best because ConfigChange blocks application to the running session but does not clearly roll back bytes already written; restart behavior after a blocked change is **UNVERIFIED**, and an isolated profile edit/restart experiment must settle it before treating this as persistence prevention.

This proposal rides the existing dispatcher and avoids all rejected architecture classes, but it is less minimal and less authoritative than managed-hooks-only policy.

## Alternatives considered and rejected

1. **“Promote config_drift to enforce.”** Rejected: its raw action is `inject`, so enforce mode still does not block (`modules.py:897-909`; `tests/test_modules.py:1400-1428`).
2. **“Guard writes under `~/.claude/hooks`.”** Insufficient: the settings declaration itself can carry or invoke the behavior, and the current guard deliberately excludes the settings file (`modules.py:845-850`).
3. **“Rely on restart to clear it.”** Rejected: restart is the trigger, not remediation; user settings persist and `SessionStart` fires on start/resume.
4. **“Disable all hooks.”** Rejected as disproportionate: it would also remove the reviewed safety/lifecycle bus. `allowManagedHooksOnly` retains a vetted managed set.
5. **“Build a security daemon/EDR/guardrail framework.”** Rejected by the anti-overfit gate and unnecessary for this chain. Native managed hook policy already supplies the correct trust boundary.
6. **“Use the event ledger to detect it later.”** Rejected as prevention. The ledger stores digests for tool results and provides useful sanitized replay (`modules.py:1048-1077`), but detection after a global executable config mutation is too late.
7. **“Treat managed-mcp.json as sufficient.”** Rejected: managed MCP controls the server catalog, not user lifecycle hooks. Prior audit F06 further reports that administrator-owned MCP entries can still point at user-writable code (`audit-findings/F06.md:F1`), a neighboring supply-chain surface outside this unit’s chosen chain.

## Blast radius and cleanup implications

The direct blast radius is all future Claude projects for this Windows user because `~/.claude/settings.json` is all-project scope. Concurrent sessions share it even when their transcripts, goals, and worktrees differ. The trigger runs with the hook process environment; exact credential inheritance is **UNVERIFIED** and would require a names-only child-environment canary. Prior A28/F01 audits report broad ambient credentials, but this unit does not reuse those claims as proof of what one future hook receives.

If a real incident is suspected, cleanup must not consist only of deleting one handler. A safe response would close Claude, preserve a forensic copy, compare the complete user settings and referenced executable paths against a reviewed baseline, rotate any credentials shown by independent evidence to have been read or transmitted, install the managed-policy boundary, and then cold-start with names-only observation. These are incident-response recommendations, not actions authorized or performed by this unit.

## Final determination

The bundled harness is **not an adequate stopping control** for this cross-session persistence chain. That conclusion is supported independently by the path predicate, its regression test, the deployed receipt shape, the drift-mode ladder, and the drift tests. Whether a separate administrator-managed policy already stops user hooks on the actual Windows host is **UNVERIFIED**, with a specific non-destructive experiment supplied.

The right minimal architecture is native managed hook provenance, not another detector: keep reviewed `SessionStart` hooks in administrator-controlled managed settings and admit no user/project/plugin executable hooks by default. This preserves the existing bus while moving its root of trust outside the autonomous agent’s writable user plane.
