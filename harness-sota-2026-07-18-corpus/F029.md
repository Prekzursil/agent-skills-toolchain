# F029 — defensive red team: hook-scripts → disable-a-guard

**Unit:** F029  
**Date:** 2026-07-19  
**Mode:** defensive analysis only; live hook/config subjects were read but not mutated and no guard-disable action was executed  
**Surface:** Claude Code user hooks in `C:\Users\Prekzursil\.claude\hooks`, their registrations in `C:\Users\Prekzursil\.claude\settings.json`, and the shared dispatcher in `C:\Users\Prekzursil\.agents\harness`

## Executive verdict

The most plausible guard-disable path in this harness is not a sophisticated code-injection exploit. It is a same-user trust-boundary failure: an agent-controlled shell process can create the explicit `.disabled` marker beside a blocking safety hook, or alter the hook implementation/registration, because Claude and its hooks run under the same Windows user token and the hook tree grants that token (and `CodexSandboxUsers`) modify rights. The clearest concrete target is the independently registered force-push guard:

- `C:\Users\Prekzursil\.claude\hooks\no-force-push\hook.py:25-38` checks `no-force-push\.disabled` before loading its predicate and returns success/allow if the marker exists.
- The same file documents that a broken/missing predicate or any exception also fails open (`hook.py:11-15,39-58`).
- Its registration is a blocking `PreToolUse` Bash hook in `C:\Users\Prekzursil\.claude\settings.json:151-160`.
- The live settings globally allow Bash, Edit, and Write (`settings.json:26-42`), select `defaultMode: bypassPermissions` (`settings.json:70-75`), and add all of `C:` and `D:` (`settings.json:72-75`).
- Two independent ACL readers showed the hook implementation is mutable: `Get-Acl` reported inherited `Modify` for `DESKTOP-A60S9GP\CodexSandboxUsers` and `FullControl` for `DESKTOP-A60S9GP\Prekzursil`; `icacls C:\Users\Prekzursil\.claude\hooks\no-force-push\hook.py` independently reported `(M,DC)` for the sandbox group/SID and `(F)` for the owner.

It is **almost certain (90-99%)** that a tool-capable process running under this current token can silence this guard without first defeating the guard's force-push predicate: the explicit opt-out is checked before the predicate, the containing directory is writable, and the pre-tool safety logic does not classify creation of the marker as an irreversible operation. I did not perform the disabling action. End-to-end success from a hostile fetched-page instruction is **UNVERIFIED**; an isolated throwaway Windows account/VM test in which a synthetic untrusted tool result attempts a marker write and then submits a synthetic forbidden command would settle the complete prompt-injection chain without touching the live harness.

The existing controls do **not** stop this path. They provide, at most, an advisory for some direct Write/Edit calls, and current file-integrity telemetry cannot reliably reveal the bypass. This is a high-severity defense-in-depth defect because it removes the control immediately before the protected action; it is not evidence that any attacker has used it.

## Threat model and trust boundaries

### Defender's protected property

For the representative guard, the protected property is: a history-rewriting push identified by `tripwire.should_halt()` must cause exit code 2 before the Bash tool runs (`no-force-push\hook.py:35-56`). Claude's official hook contract confirms that a `PreToolUse` exit code 2 blocks the pending tool call even when an allow rule or bypass permission mode would otherwise permit it ([Claude Code permissions](https://code.claude.com/docs/en/permissions), [hooks guide](https://code.claude.com/docs/en/hooks-guide)).

### Plausible attacker position

The relevant attacker is untrusted content that has gained influence over the agent's next tool selection—for example, a prompt injection in fetched content—or a malicious/compromised local skill. It does not need a second account, kernel privilege, or an RCE vulnerability after the model has decided to invoke a permitted shell/file tool. The shared harness already recognizes external tool results as an injection surface (`C:\Users\Prekzursil\.agents\harness\modules.py:912-920` begins its content-ingesting tool list), so this actor model is specific to the harness rather than hypothetical generic malware.

### Files, processes, and handoffs in scope

1. **Policy registration plane:** `C:\Users\Prekzursil\.claude\settings.json:81-283`, especially the force-push registration at `:151-160` and shared dispatcher at `:139-149`. Editing/removing an entry, or setting Claude's native `disableAllHooks`, changes which user hooks are loaded. Claude documents that user settings are watched and hook changes are normally picked up automatically; it also documents `disableAllHooks` as a supported user setting ([hooks reference](https://code.claude.com/docs/en/hooks)).
2. **Blocking hook execution plane:** `no-force-push\hook.py` and sibling `tripwire.py`. `hook.py` is the process entry point; it imports `tripwire` only after the opt-out check (`:35-53`). Corrupting either file degrades to allow (`:39-58`).
3. **Explicit disable plane:** `no-force-push\.disabled` and environment variable `FORGE_NO_FORCE_PUSH_OFF` (`hook.py:25-32`). The marker is especially plausible because it is a documented, one-file, persistent opt-out requiring no parsing of JSON and no code modification.
4. **Agent tool process:** Claude's Bash/PowerShell subprocess runs before the target safety-sensitive command and with the same effective filesystem authority as the hook process. The ACL probes above establish the write authority; the settings establish tool availability.
5. **Shared pre-tool handoff:** Claude invokes `C:\Users\Prekzursil\.agents\harness\dispatcher.py` for Bash/PowerShell/Edit/Write (`settings.json:139-149`). That dispatcher calls `SecretGuardModule._canonical_config_edit_guard`, but this handoff does not close the boundary (details below).
6. **Consolidated local dispatcher:** `C:\Users\Prekzursil\.claude\hooks\_dispatch\dispatch.py` has its own master `.disabled` and `HOOK_DISPATCH=off` opt-outs (`dispatch.py:41-45,61-63,134-140,286-323`). Silencing this dispatcher would disable the manifest's consolidated SessionStart/Stop/PostToolUse/PreToolUse checks (`_dispatch\manifest.json:5-239`) but not the independently registered force-push gate. A targeted per-guard marker is therefore quieter and more plausible for attacker goal “disable one guard.”
7. **Protected policy plane already present but unused for guards:** `C:\Program Files\ClaudeCode\managed-settings.json:1-4` exists and is owned by Administrators; `Get-Acl` and `icacls` both report only read/execute for ordinary Users and full control for SYSTEM/Administrators. It currently contains only MCP settings, not hooks.

### Exposure sequence (defender-level, deliberately non-operational)

The most plausible sequence is: untrusted instructions influence an allowed shell call; that call places the documented opt-out marker beside the selected guard; subsequent Bash events still launch `hook.py`, but its first predicate observes the marker and returns allow; the dangerous command then reaches the tool because the only dedicated blocker has self-disabled. This description intentionally omits commands, quoting, and runnable payloads.

This path is **very likely (80-90%)** to be preferred over editing `settings.json`: it changes one guard rather than all hooks, uses an interface intentionally supported by that guard, avoids JSON validity/file-watcher behavior, and produces no guard error because the disabled state is treated as successful allow. Evidence is the early-return ordering in `hook.py:29-38`, compared with Claude's documented automatic reload for settings changes and `ConfigChange` visibility ([hooks reference](https://code.claude.com/docs/en/hooks)). The preference claim is predictive, not evidence of observed abuse.

## Does an existing control stop it?

**No.** Four candidate controls were checked rather than assumed.

### 1. The target guard does not self-protect

The force-push hook's only blocking predicate is `tripwire.should_halt(payload)` (`hook.py:42-56`). The `.disabled` check precedes payload parsing and predicate loading (`:35-43`). Therefore a tool call whose purpose is to affect the marker is not evaluated by the force-push predicate in any protective way; once the marker is present, all future inputs allow.

The current marker is absent, so this finding is exposure rather than evidence of compromise. That absence was checked with two mechanically independent detectors, each first proving a known-present control: PowerShell returned `manifest.json=True` and `_dispatch\.disabled=False`; Git Bash independently returned `GITBASH_CONTROL_MANIFEST=PRESENT` and `GITBASH_TARGET_DISABLED=ABSENT`. No marker was created.

### 2. Shared canonical-config protection is advisory and misses shell-mediated writes

`SecretGuardModule._canonical_config_edit_guard` only considers tool names `Edit`, `Write`, `MultiEdit`, and `NotebookEdit` (`C:\Users\Prekzursil\.agents\harness\modules.py:835-850`). It does not inspect Bash or PowerShell filesystem side effects. When it does match a direct edit under the live hook tree, it returns an **inject**, not a block (`modules.py:851-862`). The live mode file explicitly sets `canonical_config_edit` to `advise` (`C:\Users\Prekzursil\.agents\state\harness\module-modes.json:5-7,15-18`). Thus:

- a shell-mediated marker/file mutation is not classified; and
- a direct Write/Edit receives advice but is still authorized.

Existing tests confirm this is deliberate behavior, not an inference: `C:\Users\Prekzursil\.agents\harness\tests\test_modules.py:2126-2132` expects default shadow/allow and enforced mode to inject; `:2191-2203` verifies non-write tools are no-ops.

### 3. ConfigChange drift control cannot protect this path, and is inert in the current deployment

Claude's native `ConfigChange` event covers settings, policy settings, and skills, not arbitrary hook implementation files or `.disabled` markers ([hooks reference](https://code.claude.com/docs/en/hooks)). The live shared registration exists at `settings.json:406-417`, but the module compares only `hooks`, `mcpServers`, and `disabledMcpServers` inside `settings.json` (`modules.py:864-909`). A marker beside `hook.py` is out of scope.

Even for a registration edit, the current detector is inert for two independent reasons:

- `modules.py:878-889` returns allow unless `installed.json` has a dictionary-valued `settings` baseline. The live `C:\Users\Prekzursil\.agents\harness\installed.json:1-48` has keys `installed_at`, `backup`, `sha256`, deploy metadata, and `files`, but no `settings` node; a `ConvertFrom-Json` structural probe independently reported `SETTINGS_NODE=ABSENT`.
- `config_drift` is a heuristic gate whose default is shadow (`modules.py:133-143,156-160,906-909`), and it has no override in the live `module-modes.json:1-37`. A search of all six live shadow logs found zero `config_drift` records while known-present controls returned two `canonical_config_edit` and fourteen `failed_modules_spike` records. This is a validated detector, not “zero means absent” without controls.

It is **almost certain (90-99%)** that current ConfigChange logic will allow a settings-hook drift event rather than block it, because the live baseline shape forces the explicit early return before staging. An isolated unit test using a copy of the exact live `installed.json` plus a modified temporary settings file would settle the remaining 1-10% without touching production.

### 4. Current Windows file audit is not a compensating detector

`auditpol /get /subcategory:"File System"` returned `No Auditing`. Independently, `Get-Acl -Audit` reported `AUDIT_COUNT=0` for `no-force-push`, `_dispatch`, and the managed settings file. The detector itself successfully read the same objects' DACLs and owners in the ACL probes above. Consequently, current Windows Security logs should not be expected to contain file-write events for this surface.

Microsoft documents that event 4663 records use of a file access right only when Audit File System is enabled and the object has a matching SACL; event 4670 records permission changes when the relevant SACL is configured ([event 4663](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4663), [event 4670](https://learn.microsoft.com/pt-pt/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4670), [audit policy guidance](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/advanced-audit-policy-configuration)).

## Minimal mitigation — **UNVERIFIED launch-path coverage** — **NATIVE (Claude Code already does this; we just enable it)**

Move only the genuinely blocking safety guards—not all 164 local scripts—into Claude's managed-policy trust plane, and execute them from an administrator-owned, user-read-only directory. On this machine, the plane already exists at `C:\Program Files\ClaudeCode\managed-settings.json`, and its ACL already provides the needed separation. The minimal change set is:

1. Put the force-push hook entry in managed settings and point it to a protected copy of `hook.py` plus `tripwire.py` under an administrator-owned directory (for example, beneath `C:\Program Files\ClaudeCode`).
2. Preserve the hook's exit-2 behavior, but locate any emergency opt-out only in that protected directory. Do not rely on a mutable environment flag for a mandatory safety gate.
3. Keep ordinary advisory/productivity hooks in the user hook tree. Do **not** enable `allowManagedHooksOnly` until there is a deliberate migration plan; enabling it now would suppress the large existing user-hook fleet.
4. Add the managed hook registration and protected-script hashes to the existing deploy receipt. Changes must go through the current `install.py --deploy`/backup/CAS path rather than a second deployer (`C:\Users\Prekzursil\.agents\harness\install.py:22-32`).

Claude officially states that managed settings have highest precedence, cannot be overridden by user/project settings or command-line arguments, and that user `disableAllHooks` cannot disable managed hooks ([settings precedence](https://code.claude.com/docs/en/configuration), [hooks reference](https://code.claude.com/docs/en/hooks)). It also supports managed-only `allowManagedHooksOnly` and disabling bypass permission mode, although neither is required for this narrow fix ([permissions](https://code.claude.com/docs/en/permissions)).

This mitigation is **very likely (80-90%)** to prevent the identified same-user marker/configuration bypass: the live managed file's ACL gives ordinary Users read/execute only, Claude resolves managed hooks above user settings, and the guard code already implements the correct blocking result once its entry point and predicate remain intact. The remaining uncertainty is administrator-equivalent compromise and whether the exact Claude binary used by every launch path reads this managed file. The latter is **UNVERIFIED** for every launch path; the settling experiment is an isolated, harmless managed SessionStart canary registered from the existing file, followed by CLI, VS Code, and any scheduled launch, checking `/hooks` source attribution and canary receipts before migrating a safety guard.

This proposal passes the anti-overfit gate: it uses Claude's native managed-hook bus, the already-present Windows ACL boundary, and the existing deploy/receipt path. It adds no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### Why not the superficially smaller alternatives?

- **A second pre-tool regex that blocks references to `.disabled`:** rejected. It lives in the same writable hook plane, can be bypassed through shell side effects or alternate spellings, and repeats the measured use-vs-mention false-positive class in `INPUT-known-harness-defects.md:9-107`.
- **Remove only the `.disabled` branch:** rejected as insufficient. A same-user writer can still alter `hook.py`, `tripwire.py`, or its user registration, all of which fail open.
- **Promote `canonical_config_edit` to enforce:** rejected as insufficient. Its enforced action is injection, not block, and its tool allowlist omits shell-mediated writes (`modules.py:835-862`).
- **Turn on `allowManagedHooksOnly` immediately:** rejected as excessive. It would replace/suppress the user hook fleet and is not required to make a managed safety hook non-disableable by user settings.
- **New daemon/service/guardrail framework:** rejected by the anti-overfit gate. The native managed-policy and ACL planes already provide the missing trust boundary.

## Detection signature — **UNVERIFIED alert delivery** — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add a small integrity/audit step to the existing installer/deployer, not a daemon. It should configure a narrow SACL on only the protected guard directory and managed settings file, record expected SHA-256 values in the existing deployment receipt, and provide a read-only check consumed by the existing scheduled self-maintenance/hook telemetry path. The abuse signature is the following OR-set:

1. **Disable artifacts:** creation of any `.disabled` under a blocking safety-guard directory; introduction/change of `FORGE_NO_FORCE_PUSH_OFF`, `HOOK_DISPATCH`, or Claude's `disableAllHooks`; or disappearance/change of a managed safety-hook registration.
2. **Implementation drift:** SHA-256 mismatch, rename, delete, truncate, or parse/import failure for the protected entry point and predicate; a change in expected owner/DACL/SACL; or a managed hook command resolving outside the protected directory.
3. **Windows Security events after SACL enablement:** event 4663 where `Object Name` is the managed settings/guard path and `Accesses` includes `WriteData/AddFile`, `AppendData`, `DeleteChild`, `DELETE`, `WRITE_DAC`, or `WRITE_OWNER`; event 4670 on the same object; or a failed 4656 request. Alert particularly when `Process Name` is a Claude-spawned shell/interpreter or is not the approved deployer. Microsoft explicitly recommends these access masks for critical file objects ([event 4663](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4663)).
4. **Lifecycle divergence:** a current-session `PreToolUse:Bash` stream without the expected managed safety-hook receipt, while the independently registered shared dispatcher continues writing `SUCCESS:hook-pretooluse` to `C:\Users\Prekzursil\.agents\state\harness\terminal.jsonl`. The terminal schema is visible in `dispatcher.py:317-328,483-529`; current samples contain timestamp, provider, event, action, reason code, elapsed time, and failed modules. This must be a positive per-hook receipt, not inference from silence, because `no-force-push` normally emits nothing when it allows (`hook.py:4-6,59`).
5. **Config event mismatch:** a native `ConfigChange` event for `user_settings` followed by a hook-set/hash delta, or a managed-policy change event not paired with an approved deploy receipt. Claude documents `source` and `file_path` on ConfigChange and states that the event can block non-policy changes ([hooks reference](https://code.claude.com/docs/en/hooks)).

The detector needs a **known-positive control**: each scheduled integrity pass must confirm it can read and hash the protected `hook.py` and find its managed registration before evaluating absence. A monthly harmless audit canary in a sibling protected test file should generate a 4663 event, proving both Audit File System and the SACL are active. Without that canary, “no tamper events” is not evidence of safety—the exact detector failure class documented in `INPUT-known-harness-defects.md:111-129`.

It is **almost certain (90-99%)** that configured SACL write auditing will expose a same-user attempted mutation of these exact protected paths as 4656/4663 and expose ACL changes as 4670, provided the audit policy and matching SACL remain enabled; Microsoft documents both prerequisites and event meanings. Delivery of an alert to the owner's preferred UI is **UNVERIFIED**; the settling experiment is a harmless write attempt against a protected canary file from a non-privileged test account, followed by querying the local Security log and the existing monitor consumer for the correlated event.

### What current telemetry would show today

- The shared dispatcher continues producing terminal records (`terminal.jsonl` currently has `SUCCESS:hook-pretooluse` and `SUCCESS:hook-posttooluse` records), but those prove only the shared dispatcher ran; they do not prove the standalone force-push hook ran.
- Raw Claude transcripts contain abundant hook attachments according to the corrected measured finding in `INPUT-known-harness-defects.md:133-162`, but this particular hook's normal allow path is intentionally silent. Absence of hook output is therefore not a reliable disable signature.
- The consolidated dispatcher has no unconditional durable per-invocation receipt and catches exceptions with silence (`_dispatch\dispatch.py:182-189,226-283,286-329`). Its local heartbeat always emits only at SessionStart and is itself under the mutable dispatcher (`heartbeat\heartbeat.py:13-21,201-236`). It cannot serve as an independent tamper detector.
- Windows File System auditing is currently off and the target paths have no SACL audit entries, as verified above. Until configured, filesystem tamper may leave only timestamps/hash drift, not Security events.

## Residual risk and scope limits

- An administrator/SYSTEM compromise can alter managed settings and protected scripts. This mitigation targets the actual same-user agent/tool boundary, not host compromise.
- A malicious actor may seek a different allowed path to the protected operation. Managed placement preserves the force-push predicate but does not prove its regex/predicate has complete semantic coverage; that is a neighboring guard-quality unit, not F029.
- `FileChanged` might provide a native watch for named guard files, but whether it reliably watches user-hook paths and a newly created dot-marker on this Windows build is **UNVERIFIED**; the settling experiment is a temporary project-local canary registered in a managed `FileChanged` hook and modified only inside an isolated test profile. This recommendation does not rely on it.
- The phrase “164 Python hooks running on every tool call” comes from the unit brief; the live settings show different matchers and consolidated event-specific checks, so not every script literally runs on every call (`settings.json:81-523`, `_dispatch\manifest.json:5-239`). This finding deliberately targets one proven blocking safety guard rather than extrapolating uniform behavior to the whole fleet.
- I did not execute the guard, create a marker, change an environment variable, edit settings, alter ACLs, or run a forbidden operation. Verification used source/control-flow inspection, independent ACL readers, independent filesystem probes with known-present controls, current mode/manifest structure, current read-only telemetry, and primary vendor documentation.

## Final assessment

The surface is **not adequately defended**. The blocking safety guard is mutable and explicitly self-disableable by the same principal that invokes tools. Existing shared controls either miss shell side effects, advise rather than block, cover settings rather than hook files, or currently no-op because their baseline is absent. The smallest durable correction is to promote only mandatory safety hooks into the already-present managed-policy + administrator-owned filesystem trust plane, then add narrow OS file auditing and positive receipts through the existing deploy/telemetry bus.

After that change and a successful isolated launch-path/canary test, it is **very likely (80-90%)** that the specific same-user disable-a-guard path will be closed and bypass attempts will be attributable. It would be dishonest to call the control “done” before those two experiments because neither managed-hook loading across every launch path nor Security-log alert delivery has yet been exercised on this live installation.
