# A078 — coherence audit of `~/.claude/rules/web/hooks.md`

## Scope and result

This unit audited the complete unpacked copy of the target rule at
`/local_disk0/codexwork/bundle/claude/rules/web/hooks.md:1-132` against the rule tree, the active
hook wiring and implementations, `settings.json`, `CLAUDE.md`, `AGENTS.md`, and the measured
corpus. The Windows subject paths named by the program do not exist on this Linux worker; all
subject evidence below is therefore from the mandated read-only unpack at
`/local_disk0/codexwork/bundle`.

The result is not a recommendation to install the examples as written. The file currently mixes
three incompatible roles: a path-scoped behavioral rule, project-local setup documentation, and
copy/paste JSON. The six JSON examples use a shape different from the live hook configuration;
the four edit-time commands are not extension-routed; the 800-line exit-2 gate violates the
higher-precedence block policy; and the active harness does not wire the advertised formatter,
ESLint, TypeScript, Stylelint, or build commands. The clean resolution is to keep a short
declarative web-quality rule and move executable recipes into one validated, project-aware hook
implementation.

That resolution is **very likely (80-90%)** to reduce contradictions and edit churn because the
active configuration and two independent hook implementations agree on stdin JSON and nested
hook entries, while the corpus records 132 edit failures explicitly attributed to an intervening
user or linter modification (`corpus.json:8943-8944,9075-9076`). The remaining uncertainty is
project diversity: the unpack contains no representative web repositories on which to benchmark
the proposed router.

No subject file was modified. This unit wrote only this artifact.

### How precedence was applied

`AGENTS.md` gives explicit global precedence: user/permissions, then safety §6/§9/§9b, then the
cross-tool contract, then project governance, then third-party defaults
(`AGENTS.md:115-127`). It also says same-level conflicts must be surfaced rather than silently
resolved (`AGENTS.md:129-131`). The rule-tree README separately says language-specific rules
override common rules (`rules/README.md:93-99`). That latter statement can resolve a
web-vs-common disagreement only when it does not relax the higher AGENTS safety floor. It does not
establish precedence between the sibling `web/` and `typescript/` rule sets. Consequently:

* AGENTS §6 wins over the web file-size block.
* `web/hooks.md` may specialize `common/hooks.md`, but it cannot redefine exit-2 policy.
* `web/hooks.md` and `typescript/hooks.md` are same-level overlapping rules for `.ts/.tsx/.js/.jsx`;
  neither wins. Their overlap must be consolidated or explicitly scoped.
* Active `settings.json` is mechanism, not a higher behavioral instruction. A mismatch between it
  and a demanded rule is reported as UNENFORCED or STALE, not silently resolved in favor of either.

## Collision ledger

### C01 — Non-dangerous 800-line hard block violates the global exit-2 policy

**Artifacts and exact lines**

* `rules/web/hooks.md:91-102`: “Guard File Size,” “Block oversized writes,” and a Write hook that
  calls `process.exit(2)` when `lines > 800`.
* `AGENTS.md:64-70`: exit 2 is for “irreversible/dangerous only”; all other guidance must use exit 0
  plus `additionalContext`; hook errors must fail open.
* Reinforcing, not overriding, threshold rules: `rules/common/coding-style.md:35-40,61-64` calls
  200-400 lines typical and 800 maximum; `rules/common/code-review.md:47-52,113-117` treats a file
  over 800 lines as a review/refactoring concern.

**Class:** CONTRADICTION.

**Precedence:** Resolved by AGENTS §10. Safety §6 is layer 2 and the web rule is lower. The 800-line
quality preference survives, but hard-block semantics do not.

**Diagnosis:** The threshold itself is coherent across three rule files; the enforcement severity
is not. File length is maintainability guidance, not inherently irreversible or dangerous. It is
also possible to have legitimate generated, vendored, migration, grammar, schema, fixture, or
single-file deliverables over 800 lines. The hook checks only Write content and therefore does not
enforce the alleged maximum against Edit/MultiEdit growth, existing files, or other writers. That
makes it both over-strict on one path and incomplete overall.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Replace
exit 2 with exit 0 plus a structured warning containing file path, measured lines, and the 200-400
typical/800-review threshold. Exempt generated/vendor/lock/snapshot artifacts by repository-owned
patterns. Enforce the threshold as a completion/review check over changed deliverable files, not as
an irreversible tool gate. This is **almost certain (90-99%)** to restore AGENTS §6 compliance
because it directly removes the prohibited exit 2; whether 800 remains the best threshold is
**UNVERIFIED — experiment: sample changed hand-authored web files from 20 owner repositories,
compare defect/review rates by file-size bucket, and set a project override where the distribution
justifies it**.

### C02 — All six JSON examples use a stale/incompatible hook-entry shape

**Artifacts and exact lines**

* Target examples put `matcher`, `command`, and `description` in one event-array object:
  `web/hooks.md:25-36,43-54,59-70,75-86,95-106,113-123`.
* Live settings put `matcher` on the group and commands under a nested `hooks` array with
  `type: "command"`: `settings.json:310-354,484-504`.
* The harness's own recipe uses the same nested live shape:
  `hooks/README.md:161-169,174-182`.

**Class:** STALE.

**Precedence:** AGENTS §10 does not choose between a documentation example and runtime schema. The
runtime parser contract settles operability, while the rule remains responsible for matching it.

**Diagnosis:** A mechanical parser accepted all six JSON blocks as JSON, so this is not a JSON
syntax defect. A structural probe then showed every block lacks both nested `hooks[]` and `type`.
The examples therefore do not match either independent, known-live configuration exemplar. This
is an **unenforceable-as-written** rule defect: copying the advertised snippet does not create the
same shape the active harness uses.

**Specific resolution — CONFIG (settings/JSON only):** Rewrite every example to
`{ "matcher": ..., "hooks": [{ "type": "command", "command": ..., "timeout": ... }],
"description": ... }`, validate fenced examples in CI against the same schema used for
`settings.json`, and include a failing fixture for the old flat shape. Corrected snippets are
**almost certain (90-99%)** to pass the current structural check because two independent harness
artifacts use that structure. Host acceptance is **UNVERIFIED — experiment: on the Windows host,
install each corrected snippet in an isolated project settings file, run `claude --debug`, and
observe one known-positive event per hook**.

### C05 — The advertised four-step edit pipeline is not file-type routed

**Artifacts and exact lines**

**Class:** CONTRADICTION.

by the missing raw transcripts.

### C10 — A full build on every Stop conflicts with the long-operation contract and lacks loop guards

**Artifacts and exact lines**

**Class:** CONTRADICTION.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus),

deduplication is deterministic. The premise that owner web builds commonly exceed 60 seconds is
**UNVERIFIED — experiment: collect clean/incremental build durations for the owner’s active web
repos and enable foreground execution only below the measured threshold**.

## Recommended coherent end state

### 1. Separate policy from recipes — CONFIG (settings/JSON only)

Keep `rules/web/hooks.md` short and normative:

* use repository-owned scripts;
* validate only relevant changed files during the edit loop;
* do not mutate behind the agent between reads;
* perform full project verification at a bounded checkpoint;

* use the canonical frontend hook contract linked from TypeScript rules.

Move copy/paste JSON to hook documentation and schema-test every fence. This is **very likely
(80-90%)** to reduce drift because policy will have one owner and executable configuration another.

### 2. One project-aware changed-file router — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Use one existing PostToolUse/Stop bus, not a second runtime. The router should:

1. parse stdin JSON and normalize `file_path` without shell interpolation;
2. ignore unsupported/generated/vendor files using repo configuration;
3. discover the owning workspace and repo-defined scripts;
4. run formatter/linter in read-only mode per edit with strict timeouts;
5. queue a once-per-change-set typecheck/build for a checkpoint;
6. emit one terminal `SUCCESS:<id>` or `FAILED:<id> reason` result;
7. fail open on hook errors and never exit 2 for quality guidance;
8. record tool absence/skip as evidence rather than silently claiming success.

This proposal passes the anti-overfit gate: it rides the current native hook bus, stays under the
BUILD-SMALL boundary, and introduces none of the rejected second orchestration runtime, vector/KG
memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. It is
**likely (55-80%)** to be net-positive after shadow validation; confidence is capped because the
skill trees, raw transcripts, and representative web repositories are unavailable on this worker.
