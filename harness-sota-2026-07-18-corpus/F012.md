# F012 — Frontier research: DSPy-style prompt optimisation for agent systems

**Research date:** 2026-07-19  
**Scope:** automatic prompt optimisation (APO) for compound LLM programs and tool-using agents, with emphasis on what transfers to this owner's Claude/Codex harness.  
**Operating constraint:** the subject was read-only. I wrote only this artifact. The Windows paths in the brief were unavailable on this Linux job node; the supplied read-only bundle at `/local_disk0/codexwork/bundle` was used for local evidence.

## Executive verdict

The established core is narrower than the branding. Treat a prompt as a versioned parameter, score candidate variants on a task-specific metric, and promote only a candidate that improves a separate held-out set. That is ordinary black-box optimisation over text. DSPy makes this workflow programmable; MIPRO/MIPROv2 searches instructions and demonstrations; GEPA uses execution traces plus natural-language reflection to mutate candidates; TextGrad propagates textual critiques through a computation graph. Author-run studies show that all of these mechanisms can improve particular benchmarked programs, and AutoPDL shows that selecting among prompting patterns can improve some agent-like tasks. Primary sources: [DSPy paper](https://arxiv.org/abs/2310.03714), [MIPRO paper](https://arxiv.org/abs/2406.11695), [GEPA paper](https://arxiv.org/abs/2507.19457), [TextGrad/Nature](https://www.nature.com/articles/s41586-025-08661-4), and [AutoPDL/PMLR](https://proceedings.mlr.press/v293/spiess25a.html).

What is **not** established is the leap from “an optimiser improved a frozen benchmark” to “a production agent harness should continuously rewrite its own system prompts, tools, routing, or architecture.” A recent controlled study found that 49% of 72 optimisation runs on Claude Haiku 4.5 fell below zero-shot and that the only task on which every method helped had exploitable output structure; the paper itself warns that its causal explanation is based on one positive task ([Zhang et al. 2026, abstract, Tables 2/4, and caveat](https://arxiv.org/html/2604.14585)). Independent GEPA evidence is deliberately two-sided: a medical-note workshop paper reports gains from 0.669 to 0.785 on GPT-5 and 0.578 to 0.690 on Qwen3-32B ([Myles et al. 2026](https://aclanthology.org/2026.healing-1.20/)), while an ACL 2026 Student Research Workshop paper reports a defective seed falling from 23.81% to 13.50% ([Liu et al. 2026](https://aclanthology.org/2026.acl-srw.8/)). Both are recent 2026 publications and therefore lower-confidence frontier evidence, not settled general law.

**Recommendation:** do not replace this harness with DSPy and do not add a live self-modification service. Build one small, offline, framework-optional optimisation lane around the existing evaluation/receipt bus. Its first job is not to optimise; it is to decide whether a target prompt has measurable headroom. Start with generate-and-rank and a frozen promotion contract. Allow a GEPA adapter only after the simple baseline wins. This is **very likely (80-90%)** to yield a better risk-adjusted result than importing a second runtime, because the strongest cross-paper agreement is on metric/data/version discipline, whereas algorithm rankings vary by task and model ([DSPy optimisation guidance](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/overview.md), [MIPRO results and variance discussion](https://arxiv.org/html/2406.11695), [2026 compound-system diagnostic](https://arxiv.org/html/2604.14585)). The experiment that would move this confidence is a paired local pilot described in Proposal 4.4.

## Method and evidence standard

I prioritised peer-reviewed papers and proceedings, then official framework documentation/repos, then recent preprints. A paper being published establishes that the experiment was reported; it does not establish transfer to this harness. “Independent” below means different authors and a different experiment, not an exact replication unless explicitly stated.

## 1. Established

### 1.1 The durable abstraction is “program + metric + examples,” not a magic rewriting algorithm

DSPy's official optimiser interface takes a program, a metric, and training inputs; optimiser families then synthesize demonstrations, propose instructions, or fine-tune weights ([official optimiser documentation](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/optimizers.md)). The 2024 MIPRO paper formalises multi-stage prompt optimisation as maximising a downstream metric without module-level labels or gradients, and factorises the search into free-form instructions and few-shot demonstrations ([MIPRO paper, §§2–4](https://arxiv.org/html/2406.11695)). OPRO independently uses an LLM to propose new text solutions based on prior candidates and their scores ([OPRO paper](https://arxiv.org/abs/2309.03409)). TextGrad frames textual feedback as an analogue of gradients over a computation graph ([Nature paper](https://www.nature.com/articles/s41586-025-08661-4)).

What is established across these systems is the optimisation loop:

1. define a parameterised text/program surface;
2. define executable examples and a score;
3. generate candidates;
4. evaluate candidates;
5. retain/promote based on evidence.

The proposal strategy differs; the need for a scoreable task does not. This matters for the owner because the difficult part is not installing `dspy`. It is producing faithful local tasks, graders, failure traces, and promotion rules. DSPy's own current guidance says to build training and held-out test sets, warns that prompt optimisers often overfit small training sets, and says norms for complex program optimisation are still emerging ([official optimisation overview](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/overview.md)).

### 1.2 Automatic search can beat a given prompt on bounded tasks

This is established as an existence claim, not a universal effect:

- The original DSPy work reports improvements over standard few-shot and expert-created demonstrations across math, retrieval, question answering, and an agent loop ([DSPy paper](https://arxiv.org/abs/2310.03714); [ICLR paper PDF](https://openreview.net/pdf?id=PFS4ffN9Yx)).
- MIPRO reports beating baseline optimisers on five of seven evaluated multi-stage programs with Llama-3-8B, with gains up to 13 percentage points ([paper abstract](https://arxiv.org/abs/2406.11695)). Its full results also state that few-shot-set performance varies substantially, which is direct evidence that one compilation is not a stable estimate ([paper §6](https://arxiv.org/html/2406.11695)).
- OPRO reports up to +8% on GSM8K and up to +50% on Big-Bench Hard versus human-designed prompts, but these are maxima across the authors' tasks/models, not expected gains ([OPRO paper](https://arxiv.org/abs/2309.03409)). Its official repository warns that API optimisation/evaluation can incur unexpectedly large cost ([OPRO repository](https://github.com/google-deepmind/opro)).
- TextGrad was published in Nature and demonstrates optimisation across science QA, radiotherapy, molecules, coding, and agentic systems; the article reports five random seeds for at least its code-optimisation extended result ([Nature article and extended figures](https://www.nature.com/articles/s41586-025-08661-4)). Publication and breadth establish that textual-feedback search is a serious research method, not that its “backpropagation” metaphor grants mathematical gradient properties.
- AutoPDL, published at AutoML 2025, searches over zero-shot, chain-of-thought, ReAct, ReWOO, prompt content, and demonstrations using successive halving. Across three tasks and six 3B–70B models it reports a mean gain of 9.06 ± 15.3 percentage points and a maximum of 68.9 points; the very large dispersion and model/task-dependent winners are part of the result ([PMLR paper page](https://proceedings.mlr.press/v293/spiess25a.html)).

Thus “search sometimes finds a materially better prompt/configuration” is established. “The expected gain is large” is not.

### 1.3 Joint instruction-and-demonstration search is a real capability; its necessity is not established

MIPROv2 actually implements joint instruction and few-shot-example optimisation using bootstrapping, grounded instruction proposals, and Bayesian optimisation ([official MIPROv2 documentation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/api/optimizers/MIPROv2.md); [paper](https://arxiv.org/html/2406.11695)). DSPy also exposes simpler baselines—labeled few-shot, bootstrap few-shot, random search, COPRO—and its docs recommend different choices by sample count and budget rather than naming one universal winner ([official optimiser guide](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/optimizers.md)).

The distinction is crucial. Multi-component search is available, but a recent 18,000-grid-evaluation study found no statistically significant prompt interaction in six model×task conditions and recommends testing coupling before paying for joint optimisation ([Zhang et al. 2026](https://arxiv.org/html/2604.14585)). That study is a recent workshop-accepted preprint with only two-agent pipelines, four tasks, and two executor models; it weakens a blanket joint-search requirement but does not prove all agent prompts are independent.

### 1.4 Model and task specificity are first-order facts

AutoPDL explicitly reports that selected prompting strategies vary across models and tasks ([PMLR 2025](https://proceedings.mlr.press/v293/spiess25a.html)). The 2026 “coin flip” study reports that which agents, tasks, and methods benefit changes with executor model; on HelpSteer2 all six methods beat zero-shot on Haiku, while only one of six did on Nova Lite ([paper §§4–5](https://arxiv.org/html/2604.14585)). A separate revisit of OPRO found limited effectiveness on smaller Llama-2 and Mistral models and recommends accounting for optimiser-model capability and compute cost ([Revisiting OPRO](https://arxiv.org/abs/2405.10276)).

Accordingly, an “optimised prompt” is properly identified by at least target model/version, tool/schema version, evaluator version, dataset split, optimiser/configuration, seed(s), and date. Portability without re-evaluation is not established.

### 1.5 Held-out evaluation and repeated trials are requirements, not polish

DSPy's official guide recommends a distinct held-out test set and, for most prompt optimisers, allocates more examples to validation because small-train-set overfitting is common ([official optimisation overview](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/overview.md)). The MIPRO paper reports high variation from different few-shot sets ([MIPRO §6](https://arxiv.org/html/2406.11695)). GEPA's own FAQ distinguishes training and validation overfitting and advises separate sets ([GEPA FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)). The 2026 compound-system study reports three repeats per method/task and still finds near coin-flip aggregate outcomes ([Zhang et al. 2026](https://arxiv.org/html/2604.14585)).

LLM judges are usable but not neutral. The NeurIPS 2023 MT-Bench/Chatbot Arena paper reports position, verbosity, self-enhancement, and limited-reasoning biases even while strong judges achieve over 80% agreement with human preferences ([Zheng et al. 2023](https://arxiv.org/abs/2306.05685)). Therefore a prompt optimiser can optimise judge quirks unless objective graders and human-calibrated slices constrain it.

### 1.6 The framework is active, but framework maturity is not evidence of optimiser efficacy

DSPy's repository shows a current 3.x release line, 36k+ stars, active issues/PRs, and a 3.3.0 beta adding experimental ReActV2/native tool history; the release notes also document optimizer and adapter fixes ([DSPy releases](https://github.com/stanfordnlp/dspy/releases)). MIPROv2 has had real integration failures, including multi-hop index errors and example-input assertion failures ([issue #1390](https://github.com/stanfordnlp/dspy/issues/1390), [issue #1506](https://github.com/stanfordnlp/dspy/issues/1506)). GEPA has an independent package and adapter interface ([GEPA repository](https://github.com/gepa-ai/gepa)); DSPy consumes that implementation ([GEPA FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)).

Those signals establish that DSPy/GEPA are real, maintained software with nontrivial integration surfaces. Star count, publication venue, and release cadence do not establish local value.

### 1.7 What the local harness already has—and does not yet demonstrate

The installed `/prompt-optimize` command is an advisory six-phase rewrite: project detection, intent, scope, component matching, missing-context detection, and workflow/model recommendation. It outputs full and quick prompt versions but explicitly refuses execution (`/local_disk0/codexwork/bundle/claude/commands/prompt-optimize.md:5-38`). This is manual meta-prompting, not DSPy-style optimisation, because no dataset, candidate trials, task execution, metric, holdout, or promotion test appears in that command.

The corpus count of two command invocations and one skill invocation (`/local_disk0/codexwork/bundle/inputs/corpus.json:13265-13329`) establishes low observed use in the mined corpus, not why use was low or whether another prompt workflow substituted for it. The corpus's correction candidates cannot yet seed optimisation labels because its own precision control failed 41/41 (`corpus.json:10371-10374`). The existing harness ledger can classify test/build/lint/typecheck/coverage/run/e2e/health receipts and retain pass/fail/unknown (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:98-152,383-403`), which is a concrete bus an offline evaluator can reuse. However, receipt status can fall back to lexical words such as “success,” “healthy,” or “ok” (`ledger.py:354-371`), so those heuristic receipts are not automatically safe objective labels for optimisation.

## 2. Promising but unproven

### 2.1 UNVERIFIED — GEPA-style trace reflection for tool-using agents

GEPA consumes trajectories—including reasoning, tool calls, and tool outputs—then reflects in natural language to propose and combine prompt changes ([GEPA paper](https://arxiv.org/abs/2507.19457)). This is a better conceptual fit for tool failures than score-only search because the optimiser can see error messages and constraint violations; GEPA's official FAQ explicitly says score-only mode limits optimisation and recommends actionable side information ([GEPA FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)).

It is **likely (55-80%)** that trace-conditioned proposals will produce more relevant candidate edits than blind paraphrasing for this harness's recurrent, semantically clear failure classes (for example unmatched quoting or schema mismatch), because the corpus contains concrete tool error fingerprints and GEPA's mechanism consumes exactly that side information. This is **UNVERIFIED** locally; the settling experiment is to compare a fixed-budget APE/generate-and-rank baseline against GEPA on the same labelled local train/validation/hidden-test split, scoring task completion plus per-failure-class non-regression. Relevance of proposals is not the same as final held-out improvement.

GEPA's headline evidence remains mixed. Its authors report a mean score of 54.85 versus 48.91 for GRPO and 47.84 for MIPROv2 across six tasks, with fewer rollouts ([GEPA paper](https://arxiv.org/abs/2507.19457)). Independent medical-note results support cross-task usefulness ([Myles et al. 2026](https://aclanthology.org/2026.healing-1.20/)); the defective-seed result demonstrates a severe failure mode ([Liu et al. 2026](https://aclanthology.org/2026.acl-srw.8/)). Exact six-task, same-model, same-budget independent replication was not located.

### 2.2 UNVERIFIED — a cheap headroom test before optimisation

Zhang et al. propose generating 10–20 candidate prompts and proceeding only when the best candidate beats zero-shot by more than two points; in their setup, flatter landscapes did not benefit reliably from six optimisers ([paper §6](https://arxiv.org/html/2604.14585)). The paper explicitly says its two-point threshold is calibrated to its setup and its “exploitable structure” explanation comes from one positive task ([paper caveat](https://arxiv.org/html/2604.14585)).

A local headroom gate is **very likely (80-90%)** to save evaluation cost and prevent needless prompt churn, because candidate spread can be measured with the same runner and imposes no runtime architecture. **UNVERIFIED** is the useful local threshold; the settling experiment is a retrospective calibration across at least three prompt surfaces and two model versions, relating cheap candidate spread to subsequent held-out gains. Use a confidence interval/minimum detectable effect, not the paper's literal two-point constant.

### 2.3 UNVERIFIED — optimising examples before rewriting global rules

DSPy provides labeled few-shot, bootstrap few-shot, and random-search optimisers, and its guide recommends starting with simpler example-based methods at small data sizes ([official optimiser guide](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/optimizers.md)). MIPRO's results state that demonstration-set choice has high performance variation ([MIPRO §6](https://arxiv.org/html/2406.11695)).

It is **likely (55-80%)** that selecting a few representative, verified examples will be safer than letting an optimiser rewrite the entire global `CLAUDE.md`/`AGENTS.md`, because examples can be scoped to one skill while global prose affects unrelated tasks. **UNVERIFIED** is whether examples help current frontier models on this owner's tasks; the settling experiment is a three-arm comparison—baseline, example selection only, instruction mutation only—on the same hidden set and token budget. This does not imply adding examples when they increase context cost without gain.

### 2.4 UNVERIFIED — source-to-source search over a small set of native agent patterns

AutoPDL treats zero-shot, CoT, ReAct, and ReWOO selection plus prompt content as an AutoML problem and returns human-readable PDL programs; it reports gains but with 15.3-point standard deviation and only three tasks ([AutoPDL/PMLR](https://proceedings.mlr.press/v293/spiess25a.html)).

It is **roughly even (45-55%)** that selecting among a few already-supported harness templates (single agent, parallel independent workers, reviewer) will outperform today's explicit routing after controlling cost, because the search space is meaningful but agent topology is strongly task-dependent and the evidence is narrow. **UNVERIFIED** locally; settle it with paired same-task trials and repeated seeds, not a new PDL runtime. The result should select existing native templates, not synthesize arbitrary orchestration code.

### 2.5 UNVERIFIED — contrastive, regression-aware prompt repair

A June 2026 preprint proposes selecting failure slices, adding nearby successes, generating targeted edits, and accepting only validation improvements with optional regression checks. It reports HotpotQA held-out exact match moving from 51.4% to 60.4%, with failure-only and random evidence variants improving less and breaking more previously correct examples ([Contrastive Reflection](https://arxiv.org/abs/2606.30840)). This is post-cutoff/recent preprint evidence and has no independent replication located.

The mechanism is **likely (55-80%)** to be more inspectable than wholesale reflective rewriting for known local regressions, because every edit is tied to a failure/success contrast and a regression set. **UNVERIFIED** locally; settle it by replaying labelled corrections plus matched successful tasks and measuring newly fixed cases versus newly broken cases. The tree-based slice selector is unnecessary for the first pilot; explicit error-fingerprint strata already exist in the corpus.

### 2.6 UNVERIFIED — prompt regularisation and brevity constraints

TextReg argues that iterative textual-gradient methods grow longer, sample-specific prompts and reports out-of-distribution gains over TextGrad and REVOLVE after regularisation ([TextReg preprint](https://arxiv.org/abs/2605.21318)). GEPA's own docs expose length/custom proposal constraints ([GEPA FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)). This is recent 2026 preprint evidence without independent replication located.

It is **likely (55-80%)** that a prompt-size/nonlocal-change penalty will reduce instruction accretion in this harness, because every extra global token is paid across sessions and narrow exceptions invite collisions. **UNVERIFIED** is the optimal penalty and whether brevity harms needed detail; settle it by placing token delta and semantic edit scope on the Pareto report, while requiring non-inferior hidden-set quality. Do not optimise “shortest” as a primary objective.

### 2.7 UNVERIFIED — optimiser-assisted model migration

GEPA's official FAQ recommends re-running optimisation when switching model families ([GEPA FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)); AutoPDL and the 2026 compound-system study both show model-dependent winners ([AutoPDL](https://proceedings.mlr.press/v293/spiess25a.html), [Zhang et al.](https://arxiv.org/html/2604.14585)).

It is **likely (55-80%)** that an offline optimiser can reduce manual retuning during a model upgrade when a stable eval suite exists. **UNVERIFIED** is whether it is cheaper than simply using the new model's baseline prompt; settle it by including that zero-shot/native baseline and full optimisation cost in every migration trial. Never assume the old optimised prompt is the fair baseline.

## 3. Hype, and the tell that gives it away

### 3.1 “Self-improving agent” without an immutable external evaluator

**Hype:** a running agent learns from every success/failure and continuously rewrites its own prompt or memory.

**Tell:** the same model/system proposes the change, judges it, chooses it, and deploys it; there is no hidden holdout, objective receipt, version pin, rollback, or human promotion boundary. This is selection on self-generated feedback, not evidence of improvement. GEPA itself requires a metric and distinguishes train from validation ([GEPA docs](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)); DSPy's official guide asks for a held-out test set ([DSPy optimisation overview](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/overview.md)). The defective-seed GEPA regression is the concrete counterexample to “reflection corrects itself” ([ACL SRW 2026](https://aclanthology.org/2026.acl-srw.8/)).

### 3.2 “35× fewer rollouts” presented as “35× cheaper” or universal

**Hype:** GEPA is 35× more efficient than reinforcement learning, therefore it is cheap for any agent harness.

**Tell:** a best-case “up to” rollout ratio is silently converted into expected dollars, latency, or engineering cost. The paper compares against GRPO and reports task-dependent results; GEPA also pays for reflection/proposal tokens, program executions, validation, and potentially merges ([GEPA paper](https://arxiv.org/abs/2507.19457)). The official OPRO repo independently warns that optimisation/evaluation API costs can be unexpectedly large ([OPRO repo](https://github.com/google-deepmind/opro)). Require total task-model calls, proposer/judge calls, input/output tokens, wall time, and failures—not rollout count alone.

### 3.3 “Backpropagation for text” interpreted literally

**Hype:** TextGrad makes arbitrary compound AI optimisation as reliable or principled as differentiable neural-network training.

**Tell:** the analogy substitutes for a convergence guarantee, stable gradient, or unbiased credit assignment. TextGrad uses LLM-generated textual critiques ([Nature paper](https://www.nature.com/articles/s41586-025-08661-4)); it is powerful search machinery, but discrete prompt edits and stochastic LLM judgments are not mathematical derivatives. The 2026 compound-system study's failure rates are direct adverse evidence against assuming turnkey monotonic improvement ([Zhang et al.](https://arxiv.org/html/2604.14585)).

### 3.4 “Optimise the whole agent architecture” before showing prompt headroom

**Hype:** co-evolve prompts, tool schemas, routing, code, and control flow because the optimiser supports arbitrary text.

**Tell:** the search space expands before any ablation proves that individual prompt changes matter or components interact. GEPA's FAQ claims it can evolve whole architectures and tools ([official FAQ](https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/faq.md)); capability is not evidence that this is the right local search space. The recent 18,000-grid study found no significant interaction in its tested two-agent systems and recommends a coupling/headroom diagnostic ([Zhang et al.](https://arxiv.org/html/2604.14585)). For this harness, arbitrary architecture evolution would also violate the anti-overfit gate by creating a second orchestration runtime.

### 3.5 “Prompt optimisation replaces prompt engineering”

**Hype:** the framework eliminates human task definition and prompt expertise.

**Tell:** the benchmark supplies labelled examples, curated splits, a metric, program boundaries, tool sandbox, and compute budget—precisely the hard engineering inputs. DSPy's interface literally requires program/metric/examples ([official docs](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/optimizers.md)). A 2026 linguistic study notes the asymmetric comparison: GEPA searches over gold-standard splits while expert prompts may use no labelled data ([To Write or to Automate Linguistic Prompts](https://arxiv.org/abs/2603.25169)). Automation relocates prompt engineering into eval and search-space engineering.

### 3.6 Benchmark maxima without distributions, strong baselines, or hidden tests

**Hype:** “up to +50%,” “up to +68.9 points,” or a single best seed is treated as the normal outcome.

**Tell:** “up to,” no per-task table, no variance, no repeated seeds, no cost-matched random/generate-and-rank baseline, or candidate selection and reporting on the same set. AutoPDL's own mean ± standard deviation (9.06 ± 15.3) shows why the maximum is misleading ([PMLR](https://proceedings.mlr.press/v293/spiess25a.html)). MIPRO reports high few-shot-set variation ([MIPRO §6](https://arxiv.org/html/2406.11695)).

### 3.7 LLM-judge gains without judge calibration

**Hype:** a higher semantic/judge score is equated with owner value.

**Tell:** no judge-vs-human confusion matrix, no swapped-order test, no blinded pairwise review, and the optimiser can see judge rationales. Known judge biases include position, verbosity, and self-enhancement ([MT-Bench/Chatbot Arena paper](https://arxiv.org/abs/2306.05685)). An optimiser is unusually capable of exploiting a stable evaluator quirk, so judge calibration is part of the training system, not optional reporting.

### 3.8 Repository popularity or a polished dashboard as efficacy evidence

**Hype:** thousands of stars, many optimiser names, or visual trace dashboards prove production readiness.

**Tell:** adoption metrics replace same-task held-out comparisons. DSPy is clearly active ([releases](https://github.com/stanfordnlp/dspy/releases)), yet its issue tracker documents real MIPRO integration failures ([#1390](https://github.com/stanfordnlp/dspy/issues/1390), [#1506](https://github.com/stanfordnlp/dspy/issues/1506)). Software maturity and algorithmic value are separate axes.

## 4. Specific things this harness should adopt

### 4.1 Adopt an optimisation-candidate manifest and immutable promotion contract

**Tag: CONFIG (settings/JSON only)**

Add a versioned manifest schema for every candidate run:

- target prompt/skill path and content hash;
- target model/provider/version and sampling settings;
- tool/schema/harness commit or content hashes;
- train, validation, hidden-test dataset hashes and provenance;
- optimiser name/version/config and random seed;
- primary metric plus hard safety/reliability gates;
- total calls, tokens, wall time, failures, and estimated cost;
- baseline/candidate scores with per-stratum results and uncertainty;
- exact candidate diff, rollback target, and promoter identity.

**Why:** model/task specificity and overfitting are established ([AutoPDL](https://proceedings.mlr.press/v293/spiess25a.html), [DSPy split guidance](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/optimization/overview.md)). The owner already requires falsifiable receipts, and the harness has typed verification classes (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:98-152`).

**Confidence:** **almost certain (90-99%)** that provenance plus rollback improves the interpretability and reversibility of any future optimisation, because it does not depend on an optimiser winning; it records what was actually compared. The remaining uncertainty is schema integration ergonomics, settled by validating one hand-authored manifest against one baseline/candidate replay.

**Anti-overfit gate:** passes. It is JSON on the existing eval/ledger bus; it adds no runtime, memory system, critic, SaaS, or orchestration layer.

**Kill criterion:** if the manifest cannot represent a run without provider-specific executable logic, keep the schema as a report artifact and do not make it a hook.

### 4.2 UNVERIFIED — replace “optimise this prose” with “optimise this typed target”

**Tag: CONFIG (settings/JSON only)**

Retain the current `/prompt-optimize` advisory path for human drafting, but add a distinct offline contract that requires:

`target + mutable_regions + invariants + trainset + valset + hidden_test + metric + hard_gates + budget`.

Mutable regions should default to one skill/agent instruction block, not global `CLAUDE.md`, tool schemas, hooks, or routing. Invariants should include owner hard rules, security boundaries, output contracts, and maximum prompt-token delta.
