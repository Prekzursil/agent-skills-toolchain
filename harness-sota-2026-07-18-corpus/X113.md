# X113 — Reliability engineering borrowed into failure recovery

**Unit:** X113  
**Source field:** reliability engineering (FMEA, fault trees, maintainability/availability, fault containment, redundancy/diversity, common-cause failure)  
**Target:** resuming useful work after a worker, session, or machine dies mid-task  
**Lens constraint:** external research and design only. I did not inspect the local harness, repo, settings, skills, agents, or MCP configuration. That is deliberate: the unit brief assigns local grounding to other units.

## Executive verdict

The borrow transfers, but only in a deliberately narrow form.

The useful mechanism is a **fault-contained recovery block**:

1. define a bounded unit of useful work and its allowed effects;
2. preserve a recoverable entry state;
3. execute a primary method;
4. evaluate the result with an acceptance test expressed in terms visible outside the failed worker;
5. on failure, isolate the failed attempt, restore or reconcile state, and run a meaningfully different alternate;
6. if the state of an external effect is ambiguous, stop automatic replay and reconcile it first;
7. measure time to restored useful service, not merely time between crashes.

This is not a new orchestration runtime. It is a small recovery protocol riding the existing task, hook, tool, filesystem, and session buses.

The transfer is **very likely (80-90%)** to reduce lost local work and blind same-path retries, because the original recovery-block mechanism explicitly couples checkpointing, restoration, alternates, and an externally stated acceptance test, while NASA fault-management guidance couples detection, isolation, recovery, containment regions, escalation, and fault injection. The uncertainty is whether the present harness exposes durable pre/post-tool boundaries with enough information to implement the protocol under roughly 200 lines; that premise is **UNVERIFIED; settle it by instrumenting one representative task runner and counting which required recovery fields can be captured at existing hook events without patching the runtime**.

The transfer is **unlikely (20-45%)** to make arbitrary external side effects transparently replayable, because the original recovery-block assumptions require that outputs from a failed attempt be suppressible and external influences be reproducible. A sent message, submitted form, charge, remote mutation, or partially accepted API call violates that assumption. The evidence is Randell's explicit “side firewall” requirement in the original recovery-block paper. In such cases, the correct recovery state is `UNKNOWN/RECONCILE`, not `retry`.

The central recommendation is therefore:

## Recommendation — BUILD-SMALL fault-contained recovery cells

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Implement an append-only, human-readable **Recovery Cell Record** for bounded task phases, plus a resume procedure that verifies rather than trusts the last worker's claims. Use recovery blocks as the execution semantics, FMEA/fault trees as the design and test-selection method, NASA-style containment/escalation as the operational policy, and common-cause analysis to prevent “backup” paths that share the failed dependency.

This proposal passes the anti-overfit gate: it uses existing hooks, tool calls, task workspaces, and session startup; it does not add a second orchestration runtime, vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. A plain append-only record and a small recovery skill/hook are sufficient for the experiment. If the experiment shows that the existing bus cannot give atomic append or stable task identity, the proposal should fail rather than expand automatically into a daemon.

## 1. What reliability engineering already solved

### 1.1 Availability makes recovery time a first-class design variable

Reliability engineering distinguishes avoiding failure from restoring service after failure. NASA's Kennedy Space Center material defines maintainability as the probability that a failed item is restored within a given interval, and availability as a function of reliability and maintainability. NASA's availability note gives inherent availability as:

`A = MTBF / (MTBF + MTTR)`

and calls repair time an inherent design feature of the item. Sources: [NASA KSC Reliability definitions](https://extapps.ksc.nasa.gov/Reliability/) and [NASA, “Availability — What is it?”](https://extapps.ksc.nasa.gov/Reliability/Documents/Availability_What_is_it.pdf).

In its own field, this changes the engineering question from “How do we make a component never fail?” to two coupled questions: “How often does it fail?” and “How quickly and correctly can it be restored?” The same availability target may be reached by improving either side, subject to cost and safety constraints. The older but still clear DoD maintainability handbook makes the same relationship explicit and notes that lower reliability requires better maintainability to preserve availability: [MIL-HDBK-470A, section 2.2.1.1](https://quicksearch.dla.mil/Transient/735248C985CC4686BDCFC2CE29384599.pdf).

**Translation:** for an agent harness, the service is not “a process is alive.” The service is **the owner is receiving useful, verified progress on the intended task**. The relevant recovery metric is therefore `time-to-useful-work-restored` (TTUWR), beginning when durable useful progress stops and ending when a replacement actor has reconstructed intent, classified outstanding effects, and produced the next accepted increment. Session restart time alone is an invalid proxy.

This reframing is **very likely (80-90%)** to expose recovery defects hidden by ordinary uptime or task-completion metrics, because a process can restart quickly yet spend a long time rediscovering context, repeat an already-completed mutation, or confidently continue from corrupted state. The evidence is the maintainability/availability distinction above; the remaining uncertainty is whether task-level “useful work” can be operationalized consistently. **UNVERIFIED; settle it with blinded human labeling of 50 post-restart traces, comparing a proposed TTUWR detector against owner judgments of the first genuinely useful accepted increment.**

### 1.2 FMEA and fault trees connect local failure modes to system-level loss

NASA describes software FMEA as a bottom-up technique: examine how each component can fail, trace propagation through the system, and determine whether it can lead to a hazard. It considers likelihood, severity, redundancy, and single points of failure: [NASA Software Engineering Handbook, “Software Failure Modes and Effects Analysis”](https://swehb.nasa.gov/spaces/SWEHBVD/pages/140640400/8.5%2B-%2BSW%2BFailure%2BModes%2Band%2BEffects%2BAnalysis). NASA's active 2024 GSFC handbook describes FMECA as a living risk assessment updated as designs, operating parameters, processes, and knowledge change: [GSFC-HDBK-8004](https://standards.nasa.gov/standard/GSFC/GSFC-HDBK-8004).

Fault-tree analysis works in the other direction: start with an unwanted top event and deductively decompose combinations of contributing events. The NRC's Fault Tree Handbook exists to codify construction and evaluation of fault trees: [NUREG-0492](https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr0492/index).

In its own field, the value of using both is their different direction of attack:

- FMEA asks, “If this component or function fails in this way, what happens next?”
- FTA asks, “What combinations can produce this unacceptable system outcome?”

They are complementary, not redundant measurements. Neither proves exhaustiveness; both are structured ways to reveal propagation, single points, and combinations that casual happy-path design misses.

**Translation:** define the top event as `useful work cannot be resumed safely after actor loss`. Work downward into at least these branches:

`no durable intent` OR `no trustworthy progress state` OR `outstanding effect is ambiguous` OR `replacement cannot access dependencies` OR `replacement repeats the same fault` OR `two replacements act concurrently` OR `acceptance test blesses a bad state`.

Then run a bottom-up recovery FMEA over worker, session, machine, workspace, credentials, tools, network, remote services, checkpoint writer, recovery reader, acceptance test, and human handoff. This catches failure *propagation*: for example, a machine loss becomes task loss only if the latest accepted state and task intent share that machine's failure domain.

Using both analyses is **likely (55-80%)** to find materially different recovery gaps, because their inductive and deductive directions are mechanically distinct and authoritative guidance assigns them different purposes. The breadth of additional findings in this particular harness is **UNVERIFIED; settle it by having two people independently perform a one-hour FMEA and one-hour FTA on the same five chaos traces, then compare unique actionable failure modes and inter-rater agreement.**

### 1.3 Fault detection, isolation, and recovery is a chain, not a restart button

NASA's current fault-recovery guidance states that catastrophic faults should be isolated to the smallest containment region allowed by the design before recovery begins. It distinguishes detection, isolation, and recovery, aims for safe or degraded-but-stable operation, and explicitly warns that not all faults are detectable or recoverable: [NASA SWEHB HR-37, “Fault Recovery”](https://swehb.nasa.gov/spaces/SWEHBVD/pages/171508207/HR-37%2B-%2BFault%2BRecovery).

NASA's fault-detection and response guidance says fault-management architectures commonly escalate responses to persistent failures; gives a progression such as notify, precautionary action, then shutdown; says fault protection need only isolate down to defined fault-containment regions; and warns that lack of containment compromises redundancy and complicates diagnosis and recovery. It also requires tolerance of false alarms: [NASA SWEHB 9.07, “Fault Detection and Response”](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695798/9.07%2BFault%2BDetection%2Band%2BResponse).

In its own field, a detector is therefore not allowed to jump directly from “I did not hear a heartbeat” to “rerun everything.” It must consider the containment boundary, the system mode, the possible cost of a false alarm, and whether recovery action can itself create a hazard.

**Translation:** worker/session/machine death detection should yield a classified recovery event, not an automatic replay:

- `CONFIRMED_DEAD`: lease expired and the execution substrate independently reports termination;
- `SUSPECTED_DEAD`: heartbeat absent but substrate state is unavailable or contradictory;
- `ALIVE_STALLED`: actor alive but no useful progress;
- `OUTCOME_UNKNOWN`: the actor died across an effect boundary and remote outcome is not known;
- `STATE_CORRUPT`: durable record fails validation;
- `COMMON_CAUSE_SUSPECTED`: replacement exhibits the same fingerprint or depends on the same failed support system.

This classification is **very likely (80-90%)** to reduce harmful false failovers compared with heartbeat-only replay, because NASA explicitly treats false alarms as inevitable and recovery actions as potentially harmful. The magnitude is **UNVERIFIED; settle it by injecting delayed heartbeats, partitioned status queries, and slow-but-live tools, then comparing duplicate ownership and duplicate side-effect rates with heartbeat-only takeover.**

### 1.4 Recovery blocks supply the concrete execution mechanism

Brian Randell's 1975 recovery-block structure was designed for residual software design faults, not just hardware malfunction. Its essential operation is:

1. save the entry state;
2. execute a primary alternate;
3. run a side-effect-free acceptance test;
4. if execution times out, raises an error, or fails the test, restore the entry state;
5. execute the next alternate;
6. if all alternates fail, fail the enclosing block so recovery can occur at a higher level.

The paper also supplies the decisive constraints. The acceptance test observes state meaningful to the caller rather than alternate-local variables. The block acts as a firewall only if it is isolated from external influences that cannot be recreated and does not emit results that cannot be suppressed after failure. For interacting processes, uncoordinated rollback causes a domino problem; processes must coordinate within a common recovery structure (“conversation”). Source: Brian Randell, [“System Structure for Software Fault Tolerance,” IEEE Transactions on Software Engineering, 1(2), 220–232 (1975)](https://www.inf.pucrs.br/~zorzo/cs/system-structure-for-software.pdf); bibliographic DOI record: [10.1145/390016.808467](https://doi.org/10.1145/390016.808467).

This is stronger than checkpoint-and-resume. A checkpoint merely preserves state. A recovery block additionally defines:

- the containment boundary;
- an acceptance predicate;
- restoration semantics;
- one or more alternate ways to achieve the function;
- escalation if no alternate is accepted.

**Translation:** an agent task phase becomes a recovery cell. Its primary may be the normal tool/path/model strategy. Its alternate must be simpler or meaningfully diverse: a different tool family, direct local documentation instead of a failed remote service, a narrower task slice, a clean workspace on another machine, or a human-assisted reconciliation. Repeating the identical call with identical dependencies is time redundancy, not diversity.

The recovery-block structure is **likely (55-80%)** to fit bounded research, code-edit, and artifact-production phases because those phases often have inspectable workspace state and executable acceptance checks. It is **unlikely (20-45%)** to fit long, free-form conversations or side-effectful workflows as a literal transaction because intent changes, external inputs arrive, and emitted effects cannot always be suppressed. Both estimates follow directly from Randell's firewall assumptions; actual fit is **UNVERIFIED; settle it by classifying 200 historical task phases against four prerequisites: stable intent, capturable entry state, suppressible/reconcilable effects, and an external acceptance predicate.**

### 1.5 Redundancy is not diversity; common-cause failure dominates naive failover

Reliability engineering does not treat two identical channels as independent merely because there are two of them. The European space reliability handbook states that identical redundant components can share development, manufacturing, installation, environmental, procedural, and support-system causes. It recommends coupling redundancy with technical diversity and physical separation, and notes that defeating coupling factors can be easier than eliminating root causes: [Space Product Assurance digital handbook, “Modelling of common cause failure”](https://handbook.reliability.space/en/stable/system/handbook/reliability_prediction/modelling_common_cause_failure.html).

The NRC likewise reports that dependent failures defeat redundancy or diversity and that operating experience shows simultaneous failures of apparently independent components due to common causes; those dependencies can be subtle and data sparse: [NUREG-1150, Appendix C.2, “Common-Cause and Dependent Failures”](https://www.nrc.gov/sites/default/files/doc_library/cdn/legacy/reading-rm/doc-collections/nuregs/staff/sr1150/v2/sr1150v2appc.pdf).

**Translation:** a replacement worker on the same machine, using the same session state, same credential, same dead MCP, same quoting path, same over-strict schema, or same corrupted checkpoint is not a diverse alternate. A recovery record must name the failed path's **coupling factors** so the alternate can change at least the implicated dimension.

A coupling-factor check is **very likely (80-90%)** to prevent some futile failovers where the second worker inherits the first worker's environment or dependency, because this is precisely the common-cause pattern described in both space and nuclear reliability sources. Which coupling factors dominate this harness is **UNVERIFIED; settle it by clustering paired primary/alternate failures by machine, workspace, credential, tool, endpoint, prompt/schema, and checkpoint lineage, then compute conditional alternate-failure rates.**

## 2. Concrete harness design

### 2.1 Recovery Cell Record

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

At each explicitly bounded phase, append a compact record in the task workspace. JSON Lines is preferable for atomic append and easy inspection, but the semantic contract matters more than the encoding.

Minimum fields:

```text
recovery_cell_id
task_id
intent_version
objective
acceptance_contract[]
containment_boundary:
  allowed_paths[]
  allowed_external_systems[]
  prohibited_effects[]
entry_state:
  workspace_identity
  revision_or_snapshot_ref
  dirty_state_digest
  input_refs[]
worker_lease:
  actor_id
  machine_id
  session_id
  acquired_at
  last_heartbeat_at
effect_ledger[]:
  effect_id
  idempotency_key_if_any
  target
  intent_digest
  state = PREPARED | CONFIRMED | REJECTED | UNKNOWN
checkpoint:
  sequence
  durable_artifacts[]
  evidence_refs[]
  next_safe_action
  digest
failure:
  fingerprint
  suspected_containment_region
  coupling_factors[]
alternate_plan:
  changed_dimensions[]
  next_method
status = OPEN | ACCEPTED | RECOVERING | RECONCILE | ABANDONED
```

The record should contain references and digests, not transcript dumps. The durable source of truth remains ordinary files, version control state, tool receipts, and external-system reads. This keeps the layer small and inspectable.

The record is **likely (55-80%)** to be sufficient for reconstructing bounded work without a full transcript when objective, accepted artifacts, outstanding effects, evidence, and next safe action are present. That sufficiency is **UNVERIFIED; settle it by giving recovery records—but not transcripts—to fresh agents for 30 killed tasks and measuring correct intent reconstruction, safe next action, and owner-rated continuity.**

### 2.2 Phase protocol: PREPARE → EXECUTE → VERIFY → ACCEPT

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For each recovery cell:

1. **PREPARE.** State the objective, acceptance contract, containment boundary, entry-state reference, and intended external effects before execution.
2. **EXECUTE.** Run the primary. Before each non-local or irreversible effect, append an effect intent with a stable effect ID and idempotency key if the target supports one.
3. **VERIFY.** Evaluate acceptance using evidence visible outside the actor: file digest, parser, test, target-system read, receipt, or human decision. The worker's prose assertion is not sufficient.
4. **ACCEPT.** Append the accepted checkpoint and next safe action. Only accepted checkpoints are eligible for automatic continuation.

On death before `PREPARE`, restart from the prior accepted cell. On death during local reversible execution, restore the entry state or discard the isolated attempt and run an alternate. On death across an external effect, mark `UNKNOWN` until a target-system read or idempotency result proves whether it committed. On death after verification but before acceptance, rerun the acceptance test against durable state rather than rerunning the work.

This protocol is **very likely (80-90%)** to distinguish “work absent” from “work completed but acknowledgement lost” when the target provides a readable receipt, idempotency lookup, or authoritative state query. It is **very unlikely (5-20%)** to resolve that ambiguity automatically when the target offers none; the experiment is a kill between remote commit and local confirmation across each supported connector, checking whether a second independent read can establish outcome.

### 2.3 Acceptance contracts, not self-reported completion

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Require each recoverable phase to declare one or more caller-visible acceptance checks. Examples:

- artifact: path exists, expected format parses, required terminator exists, digest recorded;
- code change: expected diff predicate plus targeted test/lint result;
- research: required question coverage and resolvable source URLs, with claims linked to evidence;
- remote mutation: authoritative target read matches intended postcondition and effect ID;
- handoff: fresh reader can identify objective, completed work, unresolved risks, and next action from durable state.

The acceptance check must not depend only on ephemeral worker memory and should not merely ask the same actor “did you finish?” Randell emphasizes that the strength of the firewall is only as good as the rigor of its acceptance test. An acceptance test need not prove total correctness; it establishes the range of results the caller can safely continue from.

Configuration-only enforcement is **likely (55-80%)** to improve recovery-point quality for structured tasks, based on the caller-visible acceptance-test property in recovery blocks. It is **unlikely (20-45%)** to detect subtle semantic wrongness in open-ended research or design, because economical predicates are necessarily incomplete. **UNVERIFIED; settle it with mutation testing: inject syntactically valid but semantically wrong artifacts and measure escape rates for each contract class.**

### 2.4 Diverse alternate selection

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Define alternate selection as a change in a recorded coupling dimension, not just a new actor ID. The recovery policy should choose the cheapest alternate that does not share the suspected cause:

| Suspected cause | Invalid “alternate” | Meaningfully diverse alternate |
|---|---|---|
| worker process crash | same process loop | new process from accepted record |
| session/context corruption | continuation in same context | fresh session reconstructed from durable record |
| machine/workspace loss | new session on same machine-only state | new machine using remotely durable artifacts and verified revision |
| tool-specific fault | same tool with identical arguments | different tool/path or simpler direct operation |
| endpoint/MCP outage | another worker calling same endpoint | cached/local authoritative source, different provider where allowed, or defer that branch |
| schema/prompt design fault | same schema through another model | relaxed staged schema or plain artifact plus validator |
| malformed shell quoting | same generated command in another shell | argument-array/native API or a script file with validator |
| checkpoint corruption | reread same checkpoint | prior accepted checkpoint plus replay of verified increments |
| credential/support-system loss | replica using same credential | separately supported read path or explicit human reconciliation |

The policy should log `changed_dimensions[]` and reject an alternate with an empty set after the same fingerprint recurs.

This is **likely (55-80%)** to reduce repeated identical failure loops because it operationalizes the reliability distinction between redundancy and diversity. It may increase latency when a transient retry would have succeeded, so the first low-cost retry can remain identical for failures classified as transient; escalation should require persistence. **UNVERIFIED; settle it with an A/B chaos run comparing unrestricted retries against one same-path retry followed by coupling-aware alternates, measuring success, tool calls, elapsed time, and repeated fingerprints.**

### 2.5 Escalating recovery response

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Adopt a bounded escalation ladder patterned on NASA's persistent-failure response:

1. record and retry once only when the operation is read-only or demonstrably idempotent;
2. restart the smallest failed containment region;
3. run a diverse alternate that changes an implicated coupling factor;
4. rehydrate a fresh session from the last accepted recovery cell;
5. rehydrate on another machine if machine or workspace is implicated;
6. enter degraded mode: narrow the objective, preserve verified output, and defer the failed branch;
7. require human reconciliation for ambiguous irreversible effects, conflicting intent versions, corrupt trusted state, or exhaustion of independent alternates.

Nested recovery is important: a failed tool call should not discard an accepted research phase; a failed phase should not discard accepted task output. Conversely, if the acceptance test or checkpoint itself is suspect, recovery must move outward to a prior trust boundary.

The ladder is **very likely (80-90%)** to bound runaway recovery work if every rung has an attempt budget and an explicit terminal condition; NASA's guidance supports escalating responses to persistence rather than uniform reaction. Whether these exact seven rungs are optimal is **UNVERIFIED; settle it by replaying historical failure fingerprints and chaos traces through candidate ladders, optimizing safe recovery rate subject to call and latency budgets.**

### 2.6 Recovery-start procedure

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

On a replacement session or machine:

1. identify the task and highest recovery-cell sequence;
2. validate record syntax, digest chain, referenced artifact existence, and workspace identity;
3. independently read the last accepted artifact/revision rather than trusting summary prose;
4. compare intent version with the latest owner instruction;
5. acquire a lease with fencing token; if another non-expired owner exists, do not execute;
6. reconcile every `PREPARED` or `UNKNOWN` effect against the target system;
7. rerun the acceptance contract for the last claimed accepted state;
8. choose an alternate whose changed dimensions address the suspected cause;
9. append a recovery decision with evidence;
10. resume at the smallest safe containment boundary.

A fencing token is necessary because a “dead” worker can revive after a partition. Every state-changing append or remote effect mediated by the harness should carry the current token where possible; a stale actor must be refused or detected. Where targets cannot accept a token, the effect ledger and target read become the weaker fallback.

Split-brain prevention is **likely (55-80%)** to be necessary in real machine/session recovery because failure detection in asynchronous systems cannot reliably distinguish a dead process from a delayed or partitioned one. The exact incidence in this harness is **UNVERIFIED; settle it by pausing rather than killing the original worker, starting a replacement after lease expiry, then resuming the original and measuring concurrent mutations with and without fencing.**

### 2.7 Fault-injection qualification

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

NASA HR-37 calls for fault-injection evidence showing detection, isolation, recovery, and absence of cascading failure, including hardware disconnection, software exceptions, redundant failover, boundaries, and overload. Translate that into a repeatable recovery qualification suite rather than assuming the mechanism works because records exist.

Inject termination at these boundaries:

- before phase preparation;
- after preparation, before work;
- midway through local file changes;
- after durable output, before verification;
- after verification, before checkpoint acceptance;
- immediately before remote effect submission;
- after remote acceptance, before local acknowledgement;
- during checkpoint append;
- after lease expiry while the original actor is merely paused;
- during recovery itself;
- simultaneous machine loss and dependency outage;
- corrupted latest checkpoint;
- stale intent after a new owner instruction.

For each injection, assert:

- the detector classifies it correctly or conservatively;
- damage remains inside the declared containment boundary;
- no irreversible effect is duplicated;
- the replacement identifies the last accepted useful state;
- the replacement does not inherit the known common cause;
- the acceptance contract is rerun;
- TTUWR and lost accepted work are recorded;
- recovery failure escalates rather than looping indefinitely.

Fault injection is **very likely (80-90%)** to reveal defects not found by static review because it exercises boundary timing, false death, partial write, and recovery-of-recovery paths; NASA explicitly requests simulated-fault evidence. The expected number and severity are **UNVERIFIED; settle it with the matrix above on at least three task classes and two machines.**

## 4. Fault tree for the top event

Top event: **safe useful work is not resumed after actor loss**.

```text
TOP occurs if ANY:

A. No usable recovery basis
   A1. objective/intent not durable
   A2. no accepted checkpoint
   A3. checkpoint corrupt AND prior checkpoint unavailable
   A4. referenced artifacts share failed machine/storage domain

B. Recovery basis exists but cannot be trusted
   B1. acceptance test absent/weak
   B2. checkpoint is stale relative to owner intent
   B3. effect ledger incomplete
   B4. recovery reader trusts worker prose without independent evidence

C. Takeover is unsafe
   C1. false death AND no fencing
   C2. remote effect outcome unknown AND automatic replay
   C3. workspace has unrelated/user-owned state AND blanket rollback

D. Alternate is not actually independent
   D1. same failed tool/endpoint
   D2. same machine/workspace/storage domain
   D3. same credential/supporting service
   D4. same faulty acceptance test/schema/prompt assumption

E. Recovery cannot terminate successfully
   E1. every alternate fails
   E2. recovery mechanism itself fails AND no simpler outer fallback
   E3. escalation has no bounded terminal state
   E4. human reconciliation required but unavailable
```

Minimal-cut-set reasoning changes design priority. For example, adding more checkpoints does not prevent `C2`; faster worker replacement does not prevent `D1`; a second machine does not prevent `A4` if both machines rely on the same unavailable durable store; and a perfect lease does not prevent `B1`. The architecture needs a thin chain with no obvious single-point omission: durable intent, accepted state, effect knowledge, independent verification, exclusive takeover, and a changed failure dimension.

This fault tree is **likely (55-80%)** to be a useful first decomposition because every branch corresponds to a known recovery-block or fault-management assumption. It is not demonstrated complete. **UNVERIFIED; settle it by coding every failure from the chaos campaign and 100 real interrupted sessions to a leaf, adding leaves for uncodable cases, and measuring the uncodable fraction.**

This heading inherits `UNVERIFIED` because the assigned lens prohibits inspecting the local harness, and the pinned corpus does not state recovery behavior. The phrase “currently misses” cannot honestly be asserted from the supplied evidence. The following are **candidate miss classes**, not findings. The settling experiment is the baseline chaos campaign in section 7, run against the current harness before enabling the proposal.

1. **Completed effect, lost acknowledgement.** A worker dies after a remote system accepts a mutation but before local confirmation. Restart-only replay duplicates it; the effect ledger forces a target read or idempotency lookup.

2. **False death and split brain.** A paused or partitioned worker is replaced, then returns. Heartbeats alone create two owners; lease fencing exposes stale ownership.

3. **Syntactically valid but semantically stale checkpoint.** A record parses but reflects an older owner instruction. Intent-version comparison blocks continuation.

4. **Checkpoint and worker in the same failure domain.** A machine dies and takes the “durable” recovery file with it. The containment analysis requires accepted state outside the machine's failure domain.

5. **Repeated common-cause failure.** A new worker calls the same dead dependency or uses the same bad schema/quoting path. Coupling-factor fields make the lack of diversity visible and prevent an empty-dimension alternate.

6. **Bad state accepted because the worker said “done.”** The acceptance contract requires caller-visible evidence and reruns it after takeover.

7. **Good durable output exists but acceptance append was lost.** Recovery reruns verification rather than recomputing the output.

8. **Recovery damages unrelated dirty state.** A blanket reset crosses the containment boundary. The entry-state and allowed-path records require targeted isolation or human reconciliation.

9. **Recovery loop has no outer fallback.** The recovery procedure itself fails repeatedly. Nested escalation moves to a prior trust boundary and terminates in degraded/human mode.

10. **Fast restart but slow return to useful work.** Process uptime looks healthy while a replacement rereads large context or reproduces work. TTUWR exposes the actual owner-visible outage.

It is **very likely (80-90%)** that at least one of these classes appears in a sufficiently broad kill campaign, because they arise at generic distributed-state boundaries documented by recovery-block constraints and NASA's false-alarm/containment guidance. Whether any is missed by the current harness is **UNVERIFIED; settle it by proving the baseline detector on known-present injected cases, then testing the current harness with the same injections and two independent outcome signals (local recovery record plus authoritative workspace/remote-system state).**

## 6. Adversarial transfer analysis

### 6.1 Structural assumptions that do transfer

**Bounded failure propagation transfers.** Agent work already touches separable resources—workspace regions, tools, endpoints, tasks—even when natural-language reasoning is fluid. A declared containment boundary can limit what a failed phase is allowed to damage. This is **likely (55-80%)** for code/artifact tasks and **roughly even (45-55%)** for broad exploratory work; the evidence is the existence of caller-visible artifacts in the former and the weaker phase boundaries in the latter. **UNVERIFIED; settle it by asking independent reviewers to mark recovery-cell boundaries in 50 traces and measuring agreement.**

**External acceptance transfers.** Tests, parsers, digests, target reads, and owner acceptance are state visible outside a worker. This maps directly to the recovery-block acceptance test. It is **very likely (80-90%)** to work for structural properties and **unlikely (20-45%)** to prove open-ended semantic quality. Evidence: Randell explicitly says acceptance need not establish absolute correctness, only caller acceptability.

**Diversity/common cause transfers strongly.** Workers can be nominally separate while sharing machine, context, tool, endpoint, credentials, prompt, or schema. These are direct analogues of shared environment, support system, design, and procedure. The transfer is **very likely (80-90%)**, supported by both the space reliability and NRC common-cause sources.

**Maintainability transfers.** Time to recover useful work is an owner-visible availability component. The transfer is **very likely (80-90%)**, supported by NASA's MTBF/MTTR availability relation; only the operational definition of “useful” remains task-specific.

### 6.2 Structural assumptions that do not transfer cleanly

**Agent state is not just program state.** A checkpoint cannot serialize all latent model reasoning, salience, tacit hypotheses, or the exact effect of a long context. Reconstructing from durable evidence is a new computation, not restoration of an identical internal state. Therefore the design promises **safe continuation from accepted external state**, not preservation of the same mind. It is **almost certain (90-99%)** that exact cognitive restoration is unavailable under ordinary session recovery, because no cited mechanism serializes a model's transient internal activations; this proposal deliberately does not attempt it.

**External side effects violate rollback isolation.** Randell's side firewall requires that failed outputs be suppressible and external influences reproducible. Email, messages, purchases, form submissions, deployments, and many remote mutations escape the block. The analogy fails unless the target supplies idempotency, a receipt, compensation, or authoritative reconciliation. It is **very likely (80-90%)** that some useful integrations lack a complete combination of those properties; this prevalence is **UNVERIFIED; settle it by capability-testing every state-changing connector for idempotency key support, status lookup, postcondition read, and compensation.**

**Failure detectors are epistemically weaker.** Physical systems may have multiple sensors; distributed sessions face delay/partition ambiguity. A missing heartbeat is not death. The design must tolerate false alarms and fence stale actors rather than claim perfect diagnosis.

**Acceptance tests can share the design fault.** If the same prompt, schema, assumptions, or worker produces both output and validator, “independence” is weak. Reliability engineering warns that redundant channels share design faults. A different model instance with the same instructions is not automatically diverse. It is **likely (55-80%)** that shared-assumption false passes will dominate simple syntactic failures after basic checks are added; this is **UNVERIFIED; settle it with adversarial mutations derived independently from the producer prompt and compare same-prompt versus independently specified validators.**

**Task intent can legitimately change.** Engine requirements usually do not change midway because an operator sends a new preference; agent tasks do. A recovery record can version intent but cannot decide which conflicting instruction reflects the owner's present choice. That requires a stop/replan boundary.

**Rollback may be destructive.** A workspace can contain unrelated owner changes. “Restore entry state” cannot mean resetting an entire repository. Recovery is permitted only inside explicitly owned paths or an isolated worktree/sandbox; otherwise preserve and reconcile. This is an important disanalogy from a recovery cache that owns all variables it restores.

**Common-cause probabilities are not available.** Nuclear/space reliability sometimes quantifies common-cause factors from operating data and models. The present artifact has no calibrated conditional failure rates for task alternates. It would be false precision to assign beta factors or compute recovery reliability now.

### 6.3 Rejected borrows

**N-version agent voting — rejected.** Running several agents and majority-voting their answers looks like redundant channels, but common prompts, training, tools, evidence, and blind spots create strong dependence. Natural-language outputs also lack a generally valid voter. It adds cost and orchestration complexity without solving acceptance. A narrowly diverse validator may be useful, but universal N-version execution fails the anti-overfit gate unless independently evidenced.

**Full durable-execution engine — rejected.** Workflow engines offer checkpoints, retries, leases, and idempotency patterns, but the brief's anti-overfit gate explicitly rejects a durable-execution engine. The small recovery record tests the valuable semantics on the existing bus first.

**Continuous full-session snapshotting — rejected.** It preserves large quantities of stale or misleading context, can share the failed machine's domain, and does not classify ambiguous effects. The recovery unit should be accepted external state, not an indiscriminate transcript image.

**Retry-until-success — rejected.** It is time redundancy without diversity, can amplify persistent/common-cause faults, and is unsafe across unknown effect outcomes.

**MTBF-only optimization — rejected.** Preventing crashes is valuable but cannot answer how much accepted work is lost or how safely it resumes. Availability/maintainability supplies the missing dimension.

**Quantitative fault-tree probabilities now — rejected.** No occurrence or conditional-dependence data are supplied for recovery events. The tree is qualitative until chaos and real-event data populate it.

## 7. Experiment that settles the recommendation

### 7.1 Baseline detector validation

Before claiming the current harness misses anything, prove each detector can find a known-present case.

Create controlled tasks containing:

- a known accepted local artifact;
- a known committed remote effect with receipt;
- a known uncommitted remote effect;
- a deliberately corrupt checkpoint tail;
- a paused-but-live worker;
- two alternates sharing a labeled dependency;
- a stale intent version.

Use two mechanically independent signals for every “absent/broken/done” judgment:

- local state: record/digest/process or lease state;
- external state: authoritative artifact/revision/remote target/substrate query.

Re-running the same query is not independence. For example, prove remote effect absence with both a target-system lookup by effect ID and a postcondition/list query through a different API surface, after first demonstrating that both probes find a known-present control.

### 7.2 Comparative chaos campaign

Run the same task corpus in two conditions:

- **baseline:** current harness recovery behavior;
- **treatment:** recovery cells enabled.

Use at least three task classes: local code/artifact, read-only research, and remote side-effect workflow. Use at least two machines or failure domains. Randomize kill points across the twelve boundaries in section 2.7. Include pauses/partitions as well as hard kills.

Primary outcomes:

- safe recovery rate;
- duplicate irreversible effects (must be zero for automatic recovery qualification);
- accepted work lost, in accepted-cell units;
- TTUWR median and 95th percentile;
- false takeover rate;
- wrong-intent continuation rate;
- acceptance false-pass and false-fail rates;
- repeated-fingerprint count after failover;
- fraction requiring human reconciliation;
- recovery overhead during failure-free work;
- record bytes and hook latency per accepted cell.

Qualification gates:

1. no automatic replay from `UNKNOWN` without reconciliation evidence;
2. no destructive rollback outside the declared containment boundary;
3. no stale actor mutation after fenced takeover in targets that support fencing;
4. every accepted recovered state passes its caller-visible contract when rerun;
5. treatment materially improves TTUWR or accepted-work loss without increasing semantic escape or irreversible duplication;
6. the implementation remains BUILD-SMALL and on the existing bus.

The treatment is **likely (55-80%)** to beat baseline on accepted local work lost and repeated same-path failure, based on recovery-block restoration/alternate semantics and common-cause controls. It is **roughly even (45-55%)** whether it improves median TTUWR for short tasks, because record/verification overhead may exceed recomputation. It is **very likely (80-90%)** to improve diagnosability even when it does not improve latency, because it creates explicit states for prepared, confirmed, unknown, accepted, and recovering; all predictions are **UNVERIFIED until this comparative chaos campaign is run**.

### 7.3 Stop conditions

Stop and reject the build if any of these occurs:

- existing hooks cannot provide stable task identity and durable phase append without runtime replacement;
- the record becomes a shadow transcript or second source of task truth;
- reliable implementation exceeds the BUILD-SMALL boundary and pressures adoption of a daemon/durable engine;
- acceptance contracts cannot be stated for the target task class;
- recovery increases duplicate external effects;
- operators routinely bypass `RECONCILE` because it is too costly;
- recovery records contain secrets or materially expand sensitive-data retention;
- the same failure domain holds worker, record, artifacts, and lease, making apparent durability fictitious.

These stop conditions prevent a valid narrow analogy from becoming an invalid general platform claim.

## 8. Metrics and feedback loop

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)**

Record task-level maintainability metrics:

- `TTD`: time to detect loss of useful progress;
- `TTI`: time to isolate the failed containment region;
- `TTRC`: time to reconstruct trusted context;
- `TTE`: time to reconcile outstanding effects;
- `TTUWR`: time to first new accepted useful increment;
- accepted-cell loss count;
- duplicate-effect count;
- false-takeover count;
- recovery-attempt count and changed coupling dimensions;
- recovery success by failure fingerprint and alternate;
- fraction of cells with runnable acceptance contracts;
- checkpoint corruption/staleness rate;
- recovery overhead in failure-free runs.

Do not collapse these prematurely into a single score. A fast recovery that duplicates a purchase or resumes the wrong intent is a failure. Once enough observations exist, plot TTUWR distributions by failure mode and compute conditional alternate success by changed dimension. That supports maintainability design without pretending failures are independent.

This metric set is **likely (55-80%)** to identify whether delay comes from detection, isolation, reconstruction, effect reconciliation, or execution, because the timestamps partition the recovery path. The usefulness of every field is **UNVERIFIED; settle it after 100 recovery events by testing whether each metric changes a design or operating decision, and remove fields that do not.**

## 10. Final answer to the cross-domain question

Reliability engineering has already solved the *shape* of this problem: service availability depends on recovery time as well as failure frequency; FMEA and fault trees expose propagation paths and single/common cuts; fault management separates detection, isolation, and recovery inside declared containment regions; recovery blocks restore a caller-visible state, try a diverse alternate, and admit success only through an acceptance test; common-cause analysis warns that duplicated workers are not independent when they share dependencies or design assumptions.

The concrete harness translation is a small, append-only recovery-cell protocol with accepted checkpoints, effect states, leases/fencing, caller-visible acceptance contracts, coupling-aware alternates, and bounded escalation. It catches candidate failure classes that restart-only logic cannot distinguish: acknowledgement-lost effects, false death, split brain, stale-but-valid state, same-cause failover, lost acceptance acknowledgements, and recovery that crosses unrelated state.

The analogy does **not** authorize transparent rollback of arbitrary agent work. Exact cognitive state is not serializable; owner intent changes; acceptance tests are incomplete; and external effects escape rollback. The design is valid only where it can recover from accepted external state and reconcile every ambiguous effect. Else it must stop for human resolution.

The overall design value is **likely (55-80%)**, supported by the close structural match between bounded agent phases and recovery blocks plus NASA's containment/recovery guidance. It is not yet a harness finding or an implementation result. The proposition remains **UNVERIFIED; the decisive experiment is the detector-validated comparative chaos campaign in section 7, with zero duplicate irreversible effects as a hard gate**.
