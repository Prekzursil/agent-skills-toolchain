### Runtime rules used

Claude’s current official documentation states that:

* user command files under `~/.claude/commands` continue to work as commands; if a same-named skill exists, the skill wins ([Extend Claude with skills](https://code.claude.com/docs/en/slash-commands));
* plugin components and plugin `bin/` executables are supplied while the plugin is enabled, and plugin scripts should be addressed through `${CLAUDE_PLUGIN_ROOT}`; scripts needing plugin-root working directory must explicitly `cd` there ([Plugins reference](https://code.claude.com/docs/en/plugins-reference));
* plugin enable/disable changes are applied by `/reload-plugins` or session reload ([Discover and install plugins](https://code.claude.com/docs/en/discover-plugins)); and
* `bypassPermissions` skips the permission layer, so `permissions.allow` omissions do not block tool calls in this configured mode ([Choose a permission mode](https://code.claude.com/docs/en/permission-modes)).

These are the runtime precedence signals. Where the exact live Windows outcome also depends on an unbundled cache, project setting, or current working directory, I mark that dependency inline as UNVERIFIED.

### Collision and runtime winner

The collision occurs whenever the owner invokes `/context-budget` without explicitly supplying a window size. At runtime, **settings wins for the model/context capacity; the command wins for the report’s denominator**. This is not a speculative precedence choice: Claude Code selects the configured model before expanding the prompt, while the expanded command text explicitly tells the model which denominator to use. The resulting report can therefore disagree with the runtime it is describing.

### Minimal resolution
