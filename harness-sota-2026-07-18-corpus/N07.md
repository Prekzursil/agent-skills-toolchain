# N07 — capability discoverability / auto-routing: installed-but-dead

## Executive verdict

The most damaging capability-discovery defect is not low use. It is **positive routing confidence attached to an endpoint that has no recent successful execution receipt**. The corpus records a working Tavily route (`mcp__tavily__tavily_search`, 459/459 successful) beside a dead Claude.ai Tavily route (`tavily_search`, 139/194 errors, all 139 “not connected”; `tavily_extract`, 137/532 errors, 135 “not connected”) at `/local_disk0/codexwork/bundle/inputs/corpus.json:175-180,215-220,9130-9154`. The current semantic router credits a capability merely because it was invoked, not because its external result succeeded (`semantic-router/observe.py:20-64`; `semantic-router/success.py:66-122`). That is a trust-calibration inversion: repeated selection can raise a broken route’s rank.

The installed-but-dead set has four evidence grades:

1. **Operationally broken:** Claude.ai Tavily and three skill names that actually returned `Unknown skill` are corpus-proven (`corpus.json:9130-9154,9669-9688`).
2. **Dangling:** `council` routes correctness checking to absent `santa-method`; the earlier audit used two independent absence signals—`Test-Path` across all three roots after validating the detector on present skill roots, and bounded `rg` that found only references (`audit-findings/C08.md:74-80`).
3. **Wired but inert:** the scheduled skill/MCP regression job reports scheduler success while its producer emits text, its consumer expects JSON, and tests replace the producer with fake JSON (`audit-findings/E01.md:47-53`). Homunculus and Claude Reflect have separate code/wiring and artifact signals showing that their future-behavior loops do not close (`audit-findings/E08.md:44-60`).
4. **Cold/unknown, not dead:** only 78 skill names were observed in a near-complete transcript corpus, but non-use does not establish failure or lack of value. The corpus detector’s positive control finds `deep-research` 70 times and reports 11,633 files seen, zero failed, and one bad line (`corpus.json:5-11,13265-13315`). The installed denominator (~355) comes from the pinned measured ground truth. Every never-seen capability must remain **UNVERIFIED**, not “dead,” until the paired certification experiment in Finding 2 executes it in a disposable context.

The design recommendation is evolution, not replacement. Extend the already-built semantic router, capability catalog, MCP liveness, scheduled harness bench, and event ledger. Add **zero hooks**. A seventh hook is neither needed nor justified. All proposed runtime paths remain fail-open; failures alter ranking/quarantine metadata or create a ledger thread but never block the owner’s task.

## Evidence discipline and detector validation

The remote bundle contains the corpus, known defects, 140 audit claims, and a curated subject snapshot. It does not contain the raw Windows transcripts, the full skill/plugin trees, or the live Windows process/config state. I therefore treated audit findings as claims unless they include two mechanically independent signals, and I did not infer live absence from omission in the bundle.

Known-positive controls:

- The JSON parser found `_meta.files_seen=11633`, `files_failed=0`, `lines_bad=1`; the same branch warns that absence is corpus-only (`corpus.json:5-11`).
- The capability detector finds known-present `deep-research=70` (`corpus.json:13265-13268`) and `general-purpose=1158` (`corpus.json:13347`). This validates skills/agents detection, but **not hooks**.
- The corpus explicitly labels its hooks detector broken and says to treat the branch as no data (`corpus.json:13260-13263`). No finding uses hook-fire counts.
- The error detector independently agrees with capability-use on the three bad skill names: `verification-before-completion`, `gcloud-auth-verification`, and `simplest-probe-first` appear as attempted invocations (`corpus.json:13291-13315`) and as `Unknown skill` failures (`corpus.json:9679-9688`). These are different data fields derived from invocation and result events.

Important local architecture facts used for deduplication:

- The existing semantic router supersedes the lexical router, imports its precision lanes, validates intent suggestions against the live index, caps suggestions, deduplicates per session, and fails open (`claude/hooks/semantic-router/route.py:1-22,153-161,203-225,273-358,361-405`).
- Its observer says “invoked” means “success,” but does not inspect a result or error field (`claude/hooks/semantic-router/observe.py:1-9,20-66`). Its store increments `used` and boosts by `used/(suggested+2)` (`success.py:66-122`).
- The B1 capability catalog is a static JSON list injected once per session and already rides a fail-open SessionStart carrier (`capability-catalog/catalog.json:1-37`; `capability-catalog/inject.py:1-13,55-86`).
- B1 MCP liveness performs an external TCP plus MCP `initialize` handshake, but its critical automatic path is Basic Memory and registered RE daemons (`mcp-liveness/liveness.py:9-28,99-224`). This unit does not propose another liveness hook.
- The local dispatcher already multiplexes checks behind existing event invocations (`_dispatch/manifest.json:1-4`), and the scheduled regression net already exists but is false-green (`audit-findings/E01.md:47-53`).

## Findings — inferred surprises first

### Finding 1 — Rank verified outcomes, not invocations

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Make the semantic router’s learning signal outcome-aware. Replace `suggested → invoked` credit with `suggested → externally successful result`, and record negative receipts for resolution failure, connection failure, schema failure, timeout, or user rejection as distinct outcomes.

**What it is.** Extend the existing `observe.py`/`success.py` row from `{suggested, used}` to a bounded record such as `{suggested, attempted, succeeded, failed_by_class, last_success, last_failure}`. `observe.py` must parse the host’s PostToolUse result only when a real successful result is available; a PostToolUseFailure/failed result updates failure class instead. Ranking uses a confidence-smoothed success rate and freshness, never invocation count alone. A capability with no receipt gets a neutral prior, not a boost. A capability with repeated external connection failures becomes temporarily ineligible until the liveness/certification path supplies a new success receipt.

**Why inferred.** The owner wants capabilities to appear proactively but says a failed first invocation burns trust. The corpus proves that one Tavily endpoint is dead while another is perfect (`corpus.json:175-180,215-220,9130-9154`). The current observer can credit any invocation (`observe.py:20-64`), and the boost is strictly positive for credited use (`success.py:113-122`). This is almost certain (90-99%) to miscalibrate at least some rankings because the code has no outcome predicate and the corpus contains failed invocations; the exact number of falsely credited failures is **UNVERIFIED** until the experiment replays 100 sampled PostToolUse/Failure payloads through the observer and compares its credits with their external result status.

**How to build.** Add a versioned row schema and migration in `success.py`; normalize result status in `observe.py`; preserve atomic writes and fail-open exception handling. Add fixtures for success, not-connected, unknown-skill, schema mismatch, timeout, user rejection, and malformed payload. Do not inject new prose. Feed the negative/positive score into the existing `_succ.boost` call in `route.py:193-195`. Store only capability ID, coarse failure class, timestamps, and counts—no tool payloads.

**External signal that verifies it.** A held-out replay of real tool-result envelopes must show: (a) every known success increments `succeeded`; (b) all `Unknown skill` and “not connected” fixtures increment the right failure class and never `succeeded`; (c) the working Tavily route ranks above Claude.ai Tavily for a frozen web-search prompt; and (d) a real successful canary reverses quarantine. This closes on recorded execution results, not same-context model judgment.

**SOTA citation.** Appropriate reliance means accepting correct advice and rejecting incorrect advice case by case, not maximizing generic trust ([Schemmer et al., “Should I Follow AI-based Advice?”](https://arxiv.org/abs/2204.06916)). NIST calls for deployment-context measurement, uncertainty, benchmarks, independent review, and recalibration or removal when needed ([AI RMF Core, Measure and Manage](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it (non-destructive scoring migration with rollback fixture).  
**Anti-overfit gate:** passes—two existing files and the current observer bus; no critic, daemon, vector store, SaaS, or second runtime.

### Finding 2 — Turn the false-green weekly bench into a paired capability certification authority

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Repair the existing `ClaudeHarnessBench`, then make each certification test contain a known-positive control and a target probe. Its output becomes the sole source for states `CERTIFIED`, `DEGRADED`, `QUARANTINED`, and `UNVERIFIED` in a small JSON receipt consumed by the catalog/router.

**What it is.** This is not another health daemon or hook. It is the already-scheduled regression command, repaired so `semantic-router/eval.py --json` really emits versioned JSON and the consumer treats parse failure/missing control as `BENCH_INVALID`, never green. Skills get schema/load plus one positive trigger and one negative trigger in a disposable session. MCPs get `tools/list` plus the cheapest non-mutating data probe. Agents/commands get native resolution plus a bounded dry-run or fixture. Every target probe is paired with a known-present control of the same class.

**Why inferred.** The audit found the weekly job exits 0 even though producer and consumer formats disagree; its tests use fake JSON (`audit-findings/E01.md:47-53`). The corpus shows only 78 skills used from ~355 installed, yet non-use cannot safely classify the other ~277. A repaired external certification authority is very likely (80-90%) to distinguish cold-but-valid from dead without consuming owner attention, because its verdict comes from native resolution/execution plus a paired control; the remaining uncertainty is whether every capability has a safe non-mutating probe.

**How to build.** First add a real `--json` integration test spawning the producer executable—no monkeypatch/fake output. Define `capability-cert/v1` with `id`, `kind`, `source_digest`, `control`, `probe`, `state`, `checked_at`, `expires_at`, and coarse failure. Abort the run’s classifications if the class control fails. Partition probes by cost and run only changed/expired capabilities. Write atomically to the capability catalog’s directory; have the existing router read it fail-open. Create one event-ledger open thread only for persistent high-value failures; a later passing receipt supersedes it. No owner prompt is emitted unless repair needs credentials, destructive cleanup, or an explicit product choice.

**External signal that verifies it.** The repaired scheduler must produce parseable JSON from the real producer, fail a seeded dead skill/MCP while its paired known-positive passes, and return non-green when the producer emits text/empty output. A second fresh process must load one newly certified capability by native name. Those are independent producer-contract and runtime-resolution signals.

**SOTA citation.** Google’s People + AI guidance recommends staged introduction, explaining capability limits, and relevant “inboarding” only when needed—not interrupting users with unrelated features ([PAIR Mental Models](https://pair.withgoogle.com/guidebook-v2/chapter/mental-models/)). NIST recommends testing before deployment and regularly in operation with benchmarks and uncertainty reporting ([AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for repair and non-mutating probes; confirm-first for any probe requiring credentials, cost, write access, or a live external side effect.  
**Anti-overfit gate:** passes—repairs an existing scheduled script and writes a small JSON receipt; adds no hook or runtime.

### Finding 3 — Route capability families through a health-aware canonical alias, not provider names

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add canonical `capability_id` families and ordered providers to the existing catalog, then make the semantic router select a certified provider and automatically fall through on a typed availability failure.

**What it is.** “Web search,” “Tavily search,” and “IDA decompile” are capabilities; `claude_ai_Tavily`, `tavily`, plugin bridges, and funnel routes are provider endpoints. The corpus currently exposes at least three Tavily surfaces and three IDA decompile surfaces (`corpus.json:13377,13386,13470-13494,13497,13543`). Encode aliases in static JSON, e.g. `web.tavily.search → [mcp__tavily__, mcp__plugin_local-mcp-bridge_tavily__, mcp__claude_ai_Tavily__]`, with certification state, last-success freshness, cost/risk, and provider-specific invoke spelling. The router surfaces one canonical choice, not three brands.

**Why inferred.** The owner wants the harness to use powerful tools autonomously, but duplicate brands make tool choice a lottery. One Tavily search route is 459/459 successful while Claude.ai Tavily search is 55/194 successful and failed “not connected” 139 times (`corpus.json:215-220,9130-9139`). It is almost certain (90-99%) that canonical family routing would have avoided many of those connection failures because a simultaneously observed provider delivered 459 successes; whether it can substitute for every extract/search call is **UNVERIFIED** until the experiment runs semantic-equivalence fixtures for search and extract separately.

**How to build.** Extend `capability-catalog/catalog.json` rather than create another catalog. Teach the existing `capabilities.py` labels and semantic index builder to emit canonical IDs. At selection, filter `QUARANTINED`, then order by recent certified success, task fit, and lowest interaction cost. On `not connected`/resolution failure only, retry once through the next certified equivalent; do not retry semantic/schema/data errors blindly. Record both attempts in Finding 1’s receipts. Batch any persistent “all providers down” condition into the event ledger; do not ask the owner to choose among equivalent brands.

**External signal that verifies it.** A frozen prompt suite must resolve to a single canonical family; with Claude.ai Tavily seeded down and Tavily seeded up, a live non-mutating search must succeed through the latter and produce one fallback receipt. Equivalence tests must independently compare required output fields before providers may share an alias.

**SOTA citation.** Horvitz’s mixed-initiative framework says automated action must account for uncertainty, costs, benefits, and the user’s attention; dialog is a third option between action and inaction ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). Here the low-cost action is selecting a verified equivalent automatically; owner dialog is reserved for non-equivalent or consequential choices.

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for proven equivalents and availability-only fallback; confirm-first when providers differ in cost, privacy, side effects, or semantics.  
**Anti-overfit gate:** passes—static aliases plus current router/liveness/receipt paths; no new orchestrator.

### Finding 4 — Lease orphaned plugin directories from real loads before reclaiming them

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace “`.orphaned_at` means deletable” with a two-phase, receipt-backed lease collector: mark candidates, observe actual load paths in an external fresh session, then offer a precise recoverable reclaim set.

**What it is.** The pinned measured ground truth says ~1,293 orphan-marked plugin directories inflate process arguments past Windows’ 32,767-character limit, but 110/169 plugin families lack a live sibling and one marked directory is actually read by a live skill; bulk deletion was correctly stopped. The corpus independently records 592 `ENAMETOOLONG: name too long, uv_spawn` Glob failures (`corpus.json:4317,9001`) and Codex’s separate native sandbox probe hit Windows error 206 (`audit-findings/D24.md:25-26`). Treat marker files as candidates, not truth.

**Why inferred.** The owner explicitly values both reliability and loss avoidance. A lease collector is very likely (80-90%) to recover most command-line headroom without deleting the live-read exception because its keep/delete decision is based on native load receipts, sibling/provenance reachability, and a quarantine interval. The exact reclaimable count is **UNVERIFIED** until a fresh Claude session plus representative skill invocations emit resolved cache paths and a second filesystem walk recomputes the candidate set.

**How to build.** Add a manual/maintenance command to the existing plugin/fleet curation path, not a hook. Phase A inventories marker age, canonical manifest reachability, settings enablement, marketplace/version provenance, and size/argument contribution. Phase B starts a disposable fresh session with file-access tracing or loader debug output and invokes known-present controls plus every enabled plugin front door; resolved cache paths receive leases. Candidates without a lease, live sibling, or manifest reference move to a dated quarantine directory on the same volume. Only after a second fresh-session control and a soak period does the command propose deletion. Moving is recoverable; permanent deletion is separate.

**External signal that verifies it.** Before/after measurements must include actual constructed command-line length, a successful `Glob` and `codex sandbox cmd.exe /d /c ver` control, and fresh-session loading of every enabled plugin. Restore one quarantined directory and repeat if any control regresses. The loader trace and OS process result are mechanically independent.

**SOTA citation.** NIST’s Manage guidance includes recalibration, mitigation, removal, and recovery controls rather than treating one detector as authoritative ([AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). Google PAIR likewise emphasizes accurate capability/limit models and graceful failure over confident hidden automation ([PAIR Mental Models](https://pair.withgoogle.com/guidebook-v2/chapter/mental-models/)).

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first (moving or deleting plugin caches is destructive/material even with rollback).  
**Anti-overfit gate:** passes—maintenance command and receipts only; no watcher/daemon. The collector must not become a seventh hook.

## Cross-finding build order and acceptance contract

1. **Repair the bench contract first** (Finding 2). Until a real producer/consumer integration test goes green, it cannot certify or retire anything.
2. **Make routing receipts outcome-aware** (Finding 1). Historical invocation counts remain descriptive, never promotion evidence.
3. **Repair native plugin provenance** (Finding 6), then compile referential integrity (Finding 5).
4. **Add family aliases and availability-only fallback** (Finding 3).
5. **Run certification and tier the catalog** (Finding 8). Cold capabilities remain `UNVERIFIED`, never dead by non-use.
6. **Run the lease collector** (Finding 4) and retirement experiments (Finding 7); both require confirmation before material removal.

Global acceptance rules:

- **External-loop law:** no capability changes state because the same model says it worked. State transitions require native resolution, process/tool output, a fresh context, a different detector, or owner confirmation.
- **Two-signal absence:** a target’s negative result is meaningful only if a known-positive control of the same class passes. “No transcript invocation” is never an absence/broken signal.
- **Never drop a thread:** persistent failures create one deduplicated event-ledger item with capability ID, evidence, owner/action requirement, and expiry. A passing external receipt supersedes it. Do not create a new OPEN-THREADS system.
- **Prompt-fatigue budget:** background certification and routing metadata remain silent. One route line at most through the existing calibrated-silence gate; one batched owner alert only when credentials, destructive action, cost/privacy equivalence, or an unresolved product choice requires the owner.
- **Fail-open:** every reader/writer catches its own error and returns the last known-good catalog or neutral ranking. A broken cert file cannot block work or erase the catalog.
- **Hook ceiling:** zero new hooks. Extend `semantic-router/observe`, the scheduled bench, catalog/index build, MCP liveness data, and the existing event ledger. If implementation discovers a need for another event, fold it into the existing local/shared dispatcher invocation rather than registering a seventh hook.
- **No forbidden architecture:** no second orchestration runtime, vector-DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The only new durable structures are small versioned JSON receipts on current buses.
