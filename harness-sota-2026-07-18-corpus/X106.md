# X106 — Cross-domain borrow: reliability engineering → reliable agent conclusions

## Executive determination

The analogy transfers, but only in a deliberately narrow form. The useful reliability-engineering mechanism is **fault-tree-derived, common-cause-qualified diverse redundancy, with a proof test of each diagnostic path**. That phrase is a synthesis of several established mechanisms rather than the title of one standard: fault-tree analysis (FTA) defines the undesired top event and its minimal cut sets; common-cause failure analysis (CCFA) tests whether nominally redundant channels are actually coupled; diversity removes selected shared failure modes; and a built-in or injected test exposes a detector that is silently incapable of detecting anything.

Translated to an agent harness, this becomes an **evidence qualification gate** for high-risk categorical claims such as “absent,” “broken,” and “done.” The gate does not accept two tool outputs merely because there are two. It requires (1) a precise claim and scope, (2) a successful known-present control for every negative detector, (3) two agreeing evidence channels with materially different failure paths, (4) an explicit common-cause check, and (5) abstention on disagreement or detector failure. This is **very likely (80-90%)** to catch a substantial class of the observed single-probe false conclusions, because the stated incident pattern is exactly a single latent diagnostic failure propagating directly to a categorical conclusion, while NASA and FAA guidance identify latent detection faults and shared coupling as the mechanisms that defeat nominal redundancy. The actual catch rate is **UNVERIFIED; the experiment that settles it is a blinded replay of the measured correction cases against baseline and gated harnesses, scored for false categorical claims, abstentions, tool cost, and latency**.

This borrow does **not** justify multiplying guessed probe error rates, claiming a numerical reliability improvement, using majority vote among copies of the same model, or building a second orchestration runtime. Those are the parts of the analogy that fail.

## 1. What reliability engineering has already solved

### 1.1 Redundancy is conditional on independence

The elementary reliability result is not “more copies are safer”; it is “more independently failing copies can be safer.” NIST’s reliability handbook states the assumption explicitly: the parallel/redundant model assumes all components operate independently, and its system failure distribution is the product of the component failure distributions ([NIST, “Parallel or redundant model,” §8.1.8.3](https://www.itl.nist.gov/div898/handbook/apr/section1/apr183.htm)). The multiplication is invalid when failures are dependent.

NASA’s aerospace FTA handbook shows why this matters. In its worked example, three components with individual failure probability \(10^{-3}\) appear to have an independent joint failure probability of \(10^{-9}\). Adding a 1% common-cause fraction yields a common-cause contribution of \(10^{-5}\), 10,000 times the independent estimate. The handbook says the common-cause contribution must be modeled separately rather than hidden below the redundancy AND gate ([NASA, *Fault Tree Handbook with Aerospace Applications*, version 1.1, chapter 5, PDF pp. 70–72](https://extapps.ksc.nasa.gov/reliability/Documents/Fault_Tree_Handbook_with_Aerospace_Applications_August_2002.pdf)). A later NASA summary states the limiting principle even more directly: no amount of redundancy can reduce total failure probability below the common-cause failure probability ([NASA NTRS, “Common Cause Failures Dominate and Defeat Redundancy”](https://ntrs.nasa.gov/citations/20240013667)).

In its own field, the mechanism works as follows:

1. Define the system-level failure (“top event”).
2. Decompose it into combinations of basic failures with AND/OR logic.
3. Reduce the tree to minimal cut sets: the smallest combinations sufficient to cause the top event.
4. Inspect supposedly independent events for shared design, environment, location, operations, maintenance, or support dependencies.
5. Represent those common causes explicitly, then redesign or add diversity where their contribution is unacceptable.

The FAA’s current CCFA description makes steps 3–4 operational: analysts examine primary events in minimal cut sets using matrices to find coupling through environment, location, secondary causes, human error, or quality control, specifically to determine whether redundancy is “real” ([FAA, *Safety Risk Management Guidance*, June 2024, appendix C.2.4, PDF p. C-13](https://www.faa.gov/media/80661)). This is stronger than “independent review” as a slogan because it demands an account of shared failure paths.

### 1.2 Diversity addresses identified common causes; duplication does not

NASA’s human-spaceflight guidance says redundancy should eliminate or mitigate common-cause failures and gives identical components, a common adverse environment, common incorrect maintenance, and operation outside specification as examples. It recommends dissimilar systems performing the same function as one reduction method ([NASA NPR 8705.2A, appendix C.6.8](https://nodis3.gsfc.nasa.gov/displayCA.cfm?Internal_ID=N_PR_8705_002A_&page_name=AppendixC)).

The aerospace FTA handbook contains a concrete physical example. Three identical O-ring seals protect well against independent failures but remain vulnerable to a single temperature or contamination cause. NASA’s redesigned example uses different seal types, different geometry, and separation; it still models residual shared dust exposure rather than declaring diversity perfect ([NASA, *Fault Tree Handbook with Aerospace Applications*, chapter 12, PDF pp. 152–154](https://extapps.ksc.nasa.gov/reliability/Documents/Fault_Tree_Handbook_with_Aerospace_Applications_August_2002.pdf)). Two lessons matter for the harness translation:

- “Different instances” are not necessarily diverse.
- Diversity is relative to named failure modes, never an all-purpose certificate of independence.

### 1.3 A detector is itself a component that can fail latently

NASA’s 2024 failure-tolerant avionics guidance distinguishes masking from detection and assigns two desired properties to failure detection: completeness (identify every failed component) and correctness (do not identify a healthy component). It warns that real systems trade these properties, asks designers to state assumed failure signatures and how false positives are avoided, and calls for strategies to detect latent faults in the detection mechanism itself. It defines integrity as ensuring service is correct **or detectably incorrect** and lists built-in self-tests among integrity techniques ([NASA NESC-IB-24-01986, *Failure-Tolerant Avionics for Crewed Space Systems*, pp. 15–16](https://ntrs.nasa.gov/api/citations/20240009366/downloads/20240009366.pdf?attachment=true)).

In reliability engineering, a warning channel that has never demonstrated sensitivity can be a hidden failed component. A proof or built-in test supplies a known stimulus and verifies that the end-to-end diagnostic path responds. It does not prove the detector covers every real failure; it proves something narrower and essential: the channel was capable of detecting its control under the conditions of the test.

The agent analogue is exact enough to be useful. A command that returns zero matches may mean “target absent,” but may also mean “wrong root,” “unsupported syntax,” “permission-filtered view,” “stale index,” “parser discarded output,” or “detector never ran.” A known-present control exercises the path from query construction through tool execution and parsing to evidence receipt. Without it, “zero” is not evidence of absence.

### 1.4 FMEA supplies the bottom-up complement

FTA begins with the bad outcome and works downward. Failure Modes and Effects Analysis (FMEA/FMECA) begins with components or functions and asks how each can fail and what follows. NASA’s active 2024 GSFC handbook describes FMECA as a uniform, living risk-assessment method updated as designs, operations, and knowledge change ([NASA GSFC-HDBK-8004, scope and status](https://standards.nasa.gov/standard/GSFC/GSFC-HDBK-8004)). For this transfer, a compact probe-FMEA is valuable because novel tool failures will not all be anticipated in a static fault tree.

## 2. Structural mapping to agent verification

| Reliability-engineering object | Agent-harness object | Concrete example |
|---|---|---|
| Top event | A categorical conclusion is asserted but false | “No skills are installed” when the detector saw the wrong directory |
| Component/channel | One evidence-producing probe and its interpretation | `rg` search, API enumeration, direct file read, behavioral invocation |
| Latent failure | Probe path is incapable but appears quiet | missing mount, bad quoting, swallowed stderr, stale cache |
| Proof/built-in test | Known-present control through the same diagnostic path | search for a fixture or item already proven present before accepting zero target matches |
| Redundancy | More than one evidentiary route to the same proposition | namespace listing plus direct read/invocation |
| Diversity | Different mechanisms and failure dependencies | text search versus structured API; static existence versus behavioral exercise |
| Common cause | Shared upstream reason both channels can agree wrongly | same stale index, same wrong root, same parser, same model assumption |
| Minimal cut set | Smallest set of failures that permits the false claim | one untested detector; or two false channels; or one common cause defeating both |
| Safe state | Detectably uncertain rather than confidently wrong | “Unknown: detector control failed” or “evidence disagrees” |

The proposed top-event tree is intentionally qualitative:

```text
FALSE CATEGORICAL CONCLUSION
  OR
  ├─ synthesis/semantic error after sound evidence
  ├─ common cause makes all accepted channels wrong
  ├─ primary channel wrong AND corroborating channel wrong
  └─ qualification gate bypassed or misclassifies channel independence
```

This tree exposes something a bare “two signals” rule misses: the common-cause branch reaches the top event without two independent probe failures. It also preserves a synthesis-error branch. Evidence can be correct while the language model overgeneralizes from “not in this directory” to “does not exist.”

## 3. Proposed harness change — UNVERIFIED pending replay experiment

### Proposal A — UNVERIFIED: Evidence Qualification Gate

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement a small policy hook plus a compact verification skill/template. It should consume ordinary tool results and emit an evidence receipt; it is not a new agent, planner, database, or runtime.

Trigger the gate only when the agent is about to make a high-consequence categorical claim of one of these forms:

- **absence:** no file, capability, hook, record, configuration, or behavior exists;
- **broken:** a component cannot perform its promised function;
- **done:** an output exists and satisfies its acceptance condition;
- optionally, **safety/security invariant:** a protection is enabled or a prohibited state is impossible.

The receipt should contain:

```yaml
claim: "No X exists in scope S"
claim_class: absence
scope: "explicit path, revision, account, host, and time if relevant"
channel_a:
  mechanism: "recursive text search"
  raw_evidence_ref: "tool-call/output identifier"
  positive_control: "known-present K was found through the same path"
  dependencies: [filesystem_view, root_resolution, shell_quoting, rg, output_parser]
channel_b:
  mechanism: "structured enumeration plus direct item read"
  raw_evidence_ref: "tool-call/output identifier"
  positive_control: "known-present J was enumerated and read"
  dependencies: [enumeration_api, credentials, response_parser]
common_cause_review:
  shared_dependencies: [host, authorization_scope]
  disposition: "shared items do/do not invalidate corroboration, with reason"
decision: permit | abstain | escalate
```

Decision rule:

1. Normalize the proposition: object, predicate, scope, revision/time, and acceptance criterion.
2. For a negative detector, run a known-present control through the same execution and parsing path. A failed control forces `abstain`; the agent must report the detector failure inline.
3. Obtain a second signal by a materially different mechanism.
4. Compare dependency labels. Re-running the same command, changing only the spelling, using two wrappers over the same index, or asking the same model twice does not qualify.
5. If both qualified signals agree and no identified common cause invalidates them, permit the scoped claim.
6. If signals disagree, a control fails, scope is unresolved, or independence cannot be justified, emit `unknown` plus the next discriminating experiment. Do not majority-vote uncertainty away.

It is **very likely (80-90%)** that a receipt can be implemented within the BUILD-SMALL bound because it needs phrase/claim classification, a schema, dependency labels, and policy evaluation over existing tool calls, not a persistent service. That size estimate is **UNVERIFIED; the settling experiment is a spike implementation with physical line count, integration test, and measurements of false trigger rate**.

It is **likely (55-80%)** that automatic dependency classification will be good enough for common routine probes, because tool type, working root, data source, parser, and credential context are often available in call metadata; this is **UNVERIFIED, and the settling experiment is to have two reviewers label dependencies for 100 historical probe pairs, then measure the classifier’s precision/recall and inter-reviewer agreement**. For unfamiliar probes, the correct behavior is “independence unestablished,” not invented confidence.

### Proposal B — UNVERIFIED: Probe-FMEA library as a small, revisable table

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Maintain a short table keyed by probe family, not an encyclopedic rules engine:

| Failure mode | Effect on conclusion | Control or diverse evidence |
|---|---|---|
| Wrong scope/root/revision | false absence or false completion | record resolved scope; enumerate root; read a known-present object |
| Quoting/glob expansion error | query differs from intended query | literal sentinel/control; structured API or direct read |
| Permission or connector filtering | incomplete universe appears complete | explicit identity/capability check; second authority/data plane |
| Stale cache/index/snapshot | old state reported as current | direct source read; timestamp/version comparison |
| Parser/output truncation | matches disappear or success is misread | raw-output receipt; count/checksum; alternate parser/mechanism |
| Behavioral failure hidden by static presence | “exists” mistaken for “works” | minimal behavioral invocation with expected output |
| Semantic overreach | scoped evidence becomes universal claim | machine-check that conclusion repeats scope and predicate |
| Shared model assumption | two probes answer the wrong question | explicit proposition normalization; adversarial counterexample prompt |

Update the table from correction cases. NASA’s FMECA framing supports a living document rather than a one-time checklist. It is **likely (55-80%)** that a small table will outperform a large taxonomy in actual compliance because the owner’s anti-overfit constraint favors a minimal bus-riding mechanism, but this is **UNVERIFIED; settle it with an A/B replay comparing a 10-row table against a fuller taxonomy on catch rate, false blocks, and token/tool overhead**.

### Proposal C — UNVERIFIED: Calibrated rollout and fail-safe response

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Start in shadow mode on all claims, then enforce only absence/broken/done claims whose consequences exceed a configured threshold. Log four outcomes: `qualified`, `caught-control-failure`, `evidence-disagreement`, and `bypass/unknown`. Never present abstention as proof of failure.

This limited rollout is **very likely (80-90%)** to avoid the dominant usability failure of demanding two probes for every ordinary statement, because enforcement is claim-class and consequence scoped. The threshold calibration is **UNVERIFIED; settle it by shadowing 200 real tasks and measuring gate frequency, additional tool calls, latency, user corrections, and prevented false categorical claims before enforcement**.

## 4. What this catches that a single-probe policy misses

1. **Dead detector reported as absence.** A search returns zero because it ran against the wrong or unmounted root. The known-present control also returns zero, so the harness reports detector failure rather than absence.
2. **Syntactically successful but semantically malformed query.** Quoting or glob expansion changes the query. A literal control and a structured enumeration channel expose the mismatch.
3. **Two nominal signals with one source.** `find` and `rg` both inspect the same stale checkout or wrong revision. The dependency matrix marks the shared filesystem view/root/revision; they are not accepted as diverse evidence.
4. **Static presence mistaken for operability.** A file or registration exists, but a minimal behavioral invocation fails. The evidence channels disagree, producing `broken within tested scope` or `unknown`, not “working.”
5. **Successful write mistaken for completion.** A write call returns success, but independent readback plus acceptance test fails. “Done” is blocked.
6. **Scope inflation by the model.** Evidence establishes “not found under path P at revision R”; proposition normalization prevents rewriting that as “does not exist.”
7. **Shared parser failure.** Two upstream tools produce evidence, but the same postprocessor truncates both. Dependency labels reveal the common parser, while retaining raw evidence permits a second parser/readback.
8. **Disagreement concealed by majority rhetoric.** With only two qualified channels, disagreement is diagnostic information. The policy escalates rather than allowing the model to choose the convenient answer.

The gate will **almost certainly not (1-5%)** catch every false conclusion, because a wrong proposition, a novel common cause, deceptive but mutually consistent sources, or a synthesis error after sound evidence can bypass probe redundancy; the evidence is the explicit top-event branches above and NASA’s warning that diversity still retains residual shared vulnerabilities. This is a boundary, not a reason to discard the mechanism.

## 5. Adversarial transfer test: where the analogy holds

### Shared structure

- **Latent diagnostic failure exists in both domains.** A quiet detector can be failed while the protected system appears normal. Agent probes likewise can return an empty or plausible result despite an invalid path.
- **The harmful inference is conjunctive.** A reliable categorical conclusion depends on the proposition being well formed, the detector being sensitive, the observed result being interpreted correctly, and corroboration not sharing the same failure cause.
- **Common-cause failure is central.** Identical commands, copies of one model, common caches, common credentials, and common parsers create the same structural error as redundant components exposed to common design or environment.
- **A safe degraded state is available.** Unlike a hard real-time actuator, a research agent can usually say “unknown” and run another experiment. That makes fail-safe abstention cheaper and strengthens the transfer.
- **Minimal cut sets are actionable without precise probabilities.** “One unvalidated negative detector” is a single-point cut set; requiring a working control removes it. “Two channels plus one shared stale index” reveals a common-cause cut set; diversity targets it.

On those structural points, transfer is **very likely (80-90%)** valid: the claim is supported by the direct mapping and by FAA/NASA treatments of coupling, independence, latent detection failure, and detectably incorrect service.

## 6. Adversarial transfer test: where the analogy breaks

### 6.1 No defensible MTBF arithmetic

Physical reliability models often use stable populations, time-to-failure data, and independence assumptions. Agent probe failures are conditional on task, prompt, tool version, host, permissions, data freshness, and model behavior. They are also repaired or changed continuously. Therefore multiplying historical marginal error rates to announce a false-conclusion probability would be pseudoprecision. A controlled replay could estimate conditional catch rates, but even those may drift.

Numerical MTBF transfer is **almost certainly not (1-5%)** defensible without a carefully stratified operational dataset and dependency model; the evidence is NIST’s explicit independence premise for parallel reliability and the many state-dependent common causes identified by FAA CCFA.

### 6.2 Evidence channels are not interchangeable components

Two physical components can have a crisp success function. Two epistemic probes may observe different slices of reality or answer subtly different propositions. Disagreement can mean one failed, both are correct in different scopes, or the question is underspecified. Thus 2-out-of-3 voting is not a truth oracle. The harness must normalize scope and treat disagreement as a request for a discriminating experiment.

Majority voting among same-model agents is **unlikely (20-45%)** to provide meaningful independence, because they share training, prompt framing, available tools, and often the same source; NASA’s redundancy guidance specifically requires showing that one condition cannot fail multiple redundant components ([NASA NESC-IB-24-01986, p. 15](https://ntrs.nasa.gov/api/citations/20240009366/downloads/20240009366.pdf?attachment=true)). The exact residual benefit of separately sampled agents is **UNVERIFIED; settle it by correlated-error measurement on blinded correction cases, comparing same-model resampling, different tools, and different data planes**.

### 6.3 A positive control proves sensitivity only to the control

Finding a known-present fixture does not prove that the detector can find every target. The fixture may use a different encoding, namespace, permission, file type, or lifecycle state. Controls must resemble the target’s detection path, and a diverse channel remains necessary. Treating one control as complete validation would recreate the original overconfidence one level higher.

### 6.4 Diversity has cost and can create new faults

Every additional tool call adds latency, token use, transient failures, and more interpretation. Diversity can also make scopes diverge. Therefore this is not a universal “always use two tools” rule; it is a consequence-weighted gate for categorical claims. The optimal threshold is **roughly even (45-55%)** between a narrow three-class gate and a somewhat broader invariant gate because no operational experiment has yet measured the workload; this is **UNVERIFIED, and the shadow-mode experiment in Proposal C settles it**.

### 6.5 FTA completeness is not guaranteed

FTA is only as good as its top-event definition and modeled causes. The aerospace handbook emphasizes that top-event definition changes the tree structure and that common causes must be identified and represented. A novel agent/tool failure can remain outside the model. The FMEA table, correction feedback, raw evidence, and abstention state reduce this risk but do not eliminate it.

## 7. Anti-overfit gate

This proposal passes the stated anti-overfit gate:

- It rides existing tool results and the existing hook/skill/MCP bus.
- It needs a small policy evaluator, a schema, and a compact table.
- It introduces no second orchestration runtime.
- It introduces no vector database or knowledge graph memory.
- It introduces no durable-execution engine.
- It introduces no trained critic or standing critic agent.
- It introduces no observability SaaS or guardrail framework.
- It makes the agent do extra work only at a narrow epistemic boundary and defaults to a safe linguistic state (`unknown`) rather than elaborate recovery machinery.

A BUILD-LARGE implementation would be unjustified here. The mechanism’s value comes from changing the acceptance rule for evidence, not from persistent infrastructure.

## 8. Verification plan

The recommendation inherits **UNVERIFIED** status until this experiment is run:

1. Assemble a blinded test set from the measured owner-correction cases involving false absence, brokenness, or completion claims. Include matched correct categorical claims so a system that always abstains cannot score well.
2. Freeze task context and available tools. Run the current harness and the proposed gate on the same cases with repeated seeds.
3. Label each evidence pair’s dependencies independently by two reviewers; adjudicate disagreements before scoring automatic dependency labels.
4. Primary metrics: false categorical conclusion rate and severe false categorical conclusion rate.
5. Secondary metrics: true-claim completion, correct abstention, unnecessary abstention, additional calls, latency, tokens, and new tool errors.
6. Ablate the mechanism: baseline; positive control only; second signal only; diversity labels only; full gate. This determines which part earns its cost.
7. Inject known failures: wrong root, stale snapshot, permission-filtered enumeration, swallowed stderr, truncated parser, same-source wrappers, and a static-present/behaviorally-broken component. Verify each expected gate state.
8. Predeclare a deployment criterion. A reasonable initial criterion is a material reduction in severe false claims with no more than a modest regression in correctly completed tasks, but the numerical thresholds are **UNVERIFIED; settle them with owner-selected loss weights before reading experiment outcomes**.
9. Shadow in live use, review new minimal cut sets from escapes, and update the small FMEA table. Do not silently widen enforcement.

The full gate is **likely (55-80%)** to outperform “two signals” without qualification, because it specifically addresses the common-cause branch that redundant probes otherwise leave open. This comparative claim is **UNVERIFIED; the ablation in step 6 is the settling experiment**.

## 9. Rejected alternatives and dead ends

### “Just retry the probe” — rejected

Retry is useful for transient failure but does not address a deterministic wrong root, bad query, stale index, missing permission, or shared parser. It repeats the same failure domain and therefore is not reliability-qualified redundancy.

### “Ask two or three agents and vote” — rejected

Agents sharing model, prompt, tools, and sources have strong common causes. Voting also collapses legitimate scope disagreement into a spurious answer. It could be studied as one channel among others, but not accepted as independent merely because sampling differs.

### “Require two different shell commands” — rejected

Different executables can share the same checkout, mount, authorization, revision, environment, and semantic assumption. Mechanical difference is necessary in some cases but not sufficient; the dependency matrix is the important object.

### “Build a probabilistic reliability service” — rejected

There is no defensible stationary failure model, and a service would violate the minimal-architecture/anti-overfit constraint. Qualitative cut sets and empirical replay provide the decision value without false precision.

### “Use FMEA severity × occurrence × detectability scores as truth” — rejected

Ordinal products can create a misleading rank, and occurrence/detectability estimates for evolving agent behavior are not grounded. Use FMEA to enumerate failure modes and controls; use replay data for measured prioritization.

### “Positive control alone proves absence” — rejected

A control validates only the tested path and stimulus. It cannot prove universe completeness or target equivalence. The second diverse signal and explicit scope remain required.

## 10. Bottom line

The transferable reliability-engineering insight is not redundancy in the abstract. It is **qualified redundancy**: define the failure, expose single-point cut sets, prove diagnostic sensitivity, examine shared causes, and introduce diversity against named couplings. In an agent harness, that means a small evidence gate that refuses to turn one quiet probe—or two coupled probes—into a universal categorical claim.

The best next action is **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for a shadow-mode evidence receipt and replay evaluation, paired with **NATIVE-vs-BUILD: CONFIG (settings/JSON only)** for the probe-FMEA table and consequence threshold. The expected reliability gain is **likely (55-80%)**, based on the structural match to the measured single-probe failure pattern and the primary-source engineering evidence above; it remains **UNVERIFIED until the blinded replay, failure injection, and ablation experiments specified in §8 are completed**.
