# B004 — Groundedness: confidence calibration

## Executive verdict

The harness's Sherman–Kent vocabulary is **not empirically calibrated on the evidence supplied to this unit**. That does not mean it is empirically miscalibrated. It means the calibration question is unanswerable from the available retrospective sample: there are **zero outcome-adjudicable banded forecasts** (`n = 0`) after de-duplication and eligibility screening. Consequently, the requested statistic for “very likely” is `0/0 = undefined`, not 0%, 100%, or an inferred 80–90%.

The strongest current-state conclusion is narrower and fully evidenced: the harness enforces *controlled vocabulary*, not calibration. The Claude contract calls the bands “calibrated” (`/local_disk0/codexwork/bundle/claude/AGENTS.md:80-83`), while the shared hook only searches for a hedge and then accepts any percentage, the word `confidence`, `[verified]`, `[plausible]`, `receipt`, `proven`, or `cited` anywhere in the entire assistant message (`/local_disk0/codexwork/bundle/agents/harness/modules.py:2044-2049`). It neither binds a probability to a proposition nor records an outcome (`/local_disk0/codexwork/bundle/agents/harness/modules.py:2251-2265`). The only bundled test proves that the string `~80% confidence, tests cited` suppresses the warning; it does not test whether 80% forecasts resolve true 80% of the time (`/local_disk0/codexwork/bundle/agents/harness/tests/test_modules.py:1839-1853`).

The correct immediate label is therefore **“Sherman–Kent controlled estimative language — calibration pending.”** Calling it calibrated now manufactures assurance unsupported by outcomes.

Hallucination cannot be eliminated. The design below catches a bounded set of detectable failures: malformed explicit forecasts, post-hoc probability changes, objectively resolvable forecasts whose outcomes were not settled, and cohort-level over/under-confidence after enough outcomes. It does **not** catch an untagged hallucination, a false premise backed by mutually dependent sources, a badly specified resolution rule, or a confidently wrong claim that never becomes objectively decidable.

### Detector and controls

I used the exact mandated lexicon, longest phrase first, with word boundaries and case-insensitive matching:

```regex
\b(almost certainly not|almost certain|very unlikely|very likely|roughly even|unlikely|likely)\b
```

This deliberately does not treat “almost certainly” as “almost certain”; the mandate gives those as different strings and recognizes only `almost certainly not`. It also does not promote audit `confidence: high|medium|low` fields into Sherman–Kent bands. Those are analytic-confidence labels, not the required likelihood vocabulary.

Two mechanically different scans agreed on the material result:

1. `rg -n -i` over the raw serialized JSON and 136 Markdown files found every textual occurrence with file and line.

## Audit of the current mechanism

### What exists

1. The Claude behavior contract asks for a band on every forward-looking or uncertain claim, maps verbal hedges to numeric ranges, and requires an evidence tag (`claude/AGENTS.md:80-83`).
2. The shared lifecycle harness receives normalized `Stop` and `TaskCompleted` messages (`agents/harness/modules.py:2054-2089`; normalized assistant text is a first-class field at `agents/harness/models.py:26-39`).
3. `wep_hedge` searches for a small hedge lexicon (`likely`, `should work`, variants) and suppresses its nudge if `_BAND` matches (`agents/harness/modules.py:2044-2049`, `2251-2265`).
4. The event ledger already supports arbitrary sanitized additive fields and event kinds, appends JSONL under a file lock, timestamps and sequences entries, flushes and fsyncs, and offers bounded replay (`agents/harness/ledger.py:817-907`). This is the correct existing bus for forecast records; no second store is needed.

### What it catches today

The code catches only messages containing one of `_HEDGE`'s phrases and none of `_BAND`'s permissive tokens. It produces an advisory/injection through the staged gate (`modules.py:2251-2265`). The test demonstrates one positive and one suppressed case (`tests/test_modules.py:1839-1853`).

### What it does not catch

- A claim using an unlisted hedge, including the corpus's “almost certainly,” because `_HEDGE` contains neither “certain” nor “certainly” (`modules.py:2044-2046`).
- A confident bare prediction with no hedge, such as “the deploy will overwrite it.”
- Multiple claims in one message where one unrelated percentage or evidence word satisfies the global `_BAND.search(message)`.
- A “likely” claim accompanied only by the bare word `confidence`; `_BAND` treats that as sufficient (`modules.py:2047-2049`).
- A probability with no proposition, resolution criterion, horizon, or outcome.
- Miscalibration. There is no settlement or cohort scoring in this path (`modules.py:2251-2265`).

The prior D29 audit independently made the same core distinction: it says WEP conflates likelihood with analytic confidence and recommends binding probability to a proposition and horizon (`audit-findings/D29.md:32-38`); it also says an existing Brier helper was not wired to an outcome loop (`D29.md:64-70`). Those remain audit claims rather than ground truth because the helper file is not present in this bundle. The shared hook and ledger observations above are grounded directly in bundled code.

### False-positive rate and cost today

No empirical WEP false-positive denominator is present in the supplied corpus; the `hooks` data must not be used, per the pinned detector warning. Therefore the WEP false-positive rate is **UNVERIFIED**. A shadow run that logs every WEP match, then has a blinded human label at least 200 consecutive firings as `actionable hedge`, `mention/quotation`, or `wrong claim association`, would settle it.

The broader use-versus-mention hazard is confirmed elsewhere: the live-defect input records guards matching command names and stub markers inside prose, including a defect report that flagged itself (`INPUT-known-harness-defects.md:9-50`), then records a tool-sentinel matching `timedout` in a false-valued JSON field despite `ok: true` (`INPUT-known-harness-defects.md:52-76`). That evidence does not prove WEP has fired falsely, but it establishes why a prose-wide confidence regex must not be promoted to blocking without its own labeled shadow sample.

Runtime cost is also **UNVERIFIED**. The existing path performs two regex searches over `last_assistant_message`, so algorithmic work is linear in message length, but no latency telemetry was provided. Replay a fixed suite of 10,000 representative Stop payloads through the module with and without WEP and compare p50/p95 wall time to settle the marginal cost.

## Design: measurable calibration without a new runtime

### P1 — Rename the present guarantee (CONFIG)

Change the contract phrase from “Attach a calibrated band” to:

> Use controlled estimative language. Calibration is PENDING until the prospective ledger reports enough objectively resolved forecasts for this task cohort.

Keep three concepts separate:

- `likelihood`: probability that a binary proposition resolves true;
- `analytic_confidence`: high/medium/low confidence in the reasoning and evidence basis, not a probability;
- `source_quality`: provenance/reliability of supporting evidence, not either of the above.

This proposal rides the existing instructions bus and adds no component. It catches semantic overclaim in the contract itself: agents can no longer cite vocabulary compliance as evidence of empirical calibration. It does not catch wrong forecasts.

Cost: a small prompt/config change. False-positive rate: not applicable; this is terminology, not a detector.

### P2 — Explicit prospective forecast record (BUILD-SMALL)

Add one exact, line-oriented record format to consequential claims that have a later typed outcome:

```text
FORECAST id=<uuid> proposition="<binary claim>" band="very likely" p=0.85
  resolves_by=<ISO-8601|event> criterion="<objective true/false rule>"
  cohort=<task/domain> evidence=<receipt/source ids>
  analytic_confidence=<high|medium|low> basis="<why>"
```

On `Stop`/`TaskCompleted`, parse only lines beginning exactly `FORECAST `; validate the allowed band, `0 <= p <= 1`, that `p` falls inside the band's interval, a nonempty criterion/horizon, and a unique id. Append `kind=forecast` using the existing `EventLedger.append`, which already accepts arbitrary sanitized fields and writes ordered JSONL (`ledger.py:817-880`). The original event is immutable; revisions append `kind=forecast_revision` and refer to the prior id.

This is deliberately not an NLP classifier. It catches:

- malformed **explicit** records;
- band/probability mismatch;
- duplicate ids;
- a revision made after a resolution event, if the validator rejects it;
- loss across compaction, because the event is in the existing ledger.

It does not catch:

- omitted forecasts or untagged uncertainty;
- a proposition constructed to be vague despite a syntactically present criterion;
- incorrect evidence;
- correlated claims copied by many agents;
- any hallucination that is never tagged.

**UNVERIFIED — BUILD-SMALL:** it is **likely (55-80%)** that the complete parser, append call, resolver, report, and tests can fit below approximately 200 new lines if implemented as one small module using the existing ledger API; evidence is the small explicit grammar and existing generic append interface. A patch-size count plus the existing harness test suite would settle the size class. The integration is **very likely (80-90%)** to require no new daemon because `HookEvent` already exposes the assistant message (`models.py:26-39`) and `EventLedger.append` already accepts new kinds/fields (`ledger.py:817-880`); this confidence is about bus compatibility, not correctness of an unbuilt implementation.

Parser false-positive rate: for inputs without an exact start-of-line `FORECAST ` marker, it is 0% by construction. For marked lines, semantic false-positive rate is **UNVERIFIED**; shadow-log every rejection for two weeks and have a human label whether the record was intentionally a forecast. A test fixture must include quoted documentation, Markdown code fences, negation, and a literal example so the self-flagging class in `INPUT-known-harness-defects.md:24-50` is exercised. The parser must ignore fenced/quoted examples or require a provider field that marks generated control records.

Cost is **UNVERIFIED**. It is **very likely (80-90%)** that per-event computational work consists of one bounded line scan plus one existing locked JSONL append per explicit forecast, because that is the specified parser and current append path (`ledger.py:817-880`); actual latency remains unmeasured. Benchmark 10,000 Stop events and report p50/p95 latency and ledger bytes/forecast before rollout. It is **likely (55-80%)** that manual cost dominates runtime cost because the agent must write a criterion and a resolver must settle it; a timed prospective pilot would settle that comparison.

### P3 — Typed settlement, never self-scored prose (BUILD-SMALL)

Allow:

```text
OUTCOME forecast_id=<uuid> y=<0|1|void> evidence=<typed receipt ids|human adjudication id>
```

Settlement rules:

1. Accept automatic `y=0/1` only from deterministic task-native evidence already represented as a typed receipt: exit code, parsed test count, exact file/config readback, or other claim-specific artifact. The ledger already has claim-to-receipt classes (`ledger.py:109-120`) and the claim gate checks freshness (`modules.py:2197-2228`), although D30 warns that current receipt authentication can be gamed (`audit-findings/D30.md:15-21`). Forecast settlement must therefore name a claim-specific criterion and must not accept generic positive output.
2. Accept subjective/open-world outcomes only as explicit human adjudication; do not silently convert later model prose into ground truth.
3. Use `void` for impossible/ambiguous resolution, but report void rate and reasons. Never delete difficult forecasts from the denominator after seeing their direction.
4. Preserve the forecast timestamp, original probability, resolver actor/type, and evidence id. A later correction appends; it does not overwrite.
5. Collapse cloned propositions to a shared `canonical_question_id` for calibration or use clustered standard errors. Thirty copies of one template must never count as 30 independent successes.

This catches ungrounded settlement attempts, missing outcome evidence, and retrospective rewriting when the event order is checked. It does not prove that a test tests the right thing, and it cannot adjudicate open-ended truth without external evidence.

**UNVERIFIED — BUILD-SMALL:** the semantic false-positive rate for rejecting valid settlements is unknown. Run a preregistered replay set with at least 50 clear deterministic outcomes, 50 ambiguous outcomes, 25 quoted/example payloads, and 25 adversarial generic-`ok` receipts; report a confusion matrix before advise mode. This experiment settles the rate rather than guessing one.

### P4 — Calibration report and promotion gate (BUILD-SMALL)

For each band and cohort, report:

- `n_created`, `n_due`, `n_resolved`, `n_void`, `n_overdue`;
- empirical truth frequency `sum(y)/n_resolved`;
- a 95% Wilson interval for that frequency;
- mean Brier score `mean((p-y)^2)` using the committed point probability;
- reliability table by band and task cohort;
- duplicate/cluster count and human-versus-automatic resolver count.

Do not report “calibrated” merely because point accuracy lies inside the verbal interval. Report the interval, sample size, and cohort. A broad `likely` band (55–80%) is unsuitable as a Brier input by itself, so require `p` inside the display band and score that point value.

For “very likely,” approximately 196 independent resolutions near `p=.85` produce a normal-approximation 95% half-width near five percentage points (`1.96*sqrt(.85*.15/196) ≈ .05`). This is a planning calculation, not a magical sufficiency threshold; use the exact Wilson interval in the report. Until the interval is informative, retain “calibration pending.” Do not pool coding-test forecasts with medical, legal, research, or human-behavior forecasts merely to increase `n`.

Promotion rule: keep any outcome-derived nudging advisory until there is a preregistered cohort, a nontrivial resolved denominator, a reported void/overdue rate, and stable out-of-sample performance. Never make an agent's permissions, tool access, or reputation depend on a Brier score; that creates incentives to choose easy questions and avoid resolution.

This report catches systematic overconfidence or underconfidence in cohorts with enough resolved forecasts. It does not catch individual hallucinations reliably: a well-calibrated forecaster can still be wrong 15% of the time on 85% claims.

### P5 — UNVERIFIED: replace, do not promote, the current prose-wide WEP regex (BUILD-SMALL)

Keep a lightweight advisory linter, but scope it to exact forecast records and local fields. Do not let one `%`, `confidence`, `receipt`, or `cited` token anywhere in a message satisfy every claim. Near-miss vocabulary such as “almost certainly” can receive an advisory that either asks for the exact band or asks the agent to verify the claim now.

The current regex is useful only as a shadow discovery signal. It is **likely (55-80%)** that promoting it as-is would create unacceptable mention/association errors, based on its message-global matching (`modules.py:2044-2049`) and the independently observed use-versus-mention defect class (`INPUT-known-harness-defects.md:9-76`), but the WEP-specific premise is **UNVERIFIED**. The settling experiment is a 200-fire blinded shadow review with controls for prose, code fences, negation, multiple claims, and evidence words unrelated to the hedge. This recommendation inherits the tag in its heading because no WEP-specific false-positive sample exists.

The replacement catches malformed records and local band mismatches. It intentionally accepts false negatives outside explicit records; deterministic low-noise coverage is preferable to another prose scanner that claims semantic understanding it does not have.

### Anti-overfit gate

All five proposals ride existing buses: instruction/config, provider-normalized Stop/TaskCompleted, and the append-only event ledger. They add no second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The only persistent data is two new event kinds in the existing JSONL ledger. If implementation cannot remain a small module plus tests, defer it rather than introduce a service.

## Rollout and acceptance experiment

1. Change terminology to “controlled estimative language; calibration pending.”
2. Implement forecast/outcome schemas in shadow-only mode.
3. Unit-test exact parsing, invalid bands, point outside band, duplicated ids, revision after outcome, fenced examples, quotations, negation, and the generic-`ok` counterfeit-receipt case described at `audit-findings/D30.md:15-21`.
4. Replay a labeled retrospective fixture only to test extraction. Do not call that calibration because probabilities were not committed before outcomes.
5. Collect prospective claims. Prefer naturally consequential, objectively resolvable decisions; do not ask the model to generate trivial forecasts merely to fill bins.
6. Settle outcomes from task-native receipts or explicit human judgments.
7. Publish all due forecasts, including overdue and void counts, to prevent survivorship bias.
8. Compare band frequencies by cohort with Wilson intervals and Brier scores.
9. Adjust vocabulary mappings only on a held-out later window. Never tune and declare success on the same resolutions.

Acceptance criteria:

- Every stored forecast predates its outcome and has a proposition, point probability, exact band, horizon/event, criterion, cohort, and evidence basis.
- Every outcome has a typed evidence or human-adjudication id and resolver type.
- Duplicate propositions do not inflate independent `n`.
- The report renders `undefined / calibration pending`, not 0%, for empty bands.
- Shadow parser confusion matrix and p50/p95 overhead are published.
- No gate claims to eliminate hallucination.

## Alternatives considered and rejected

### Retrospectively label the 30 “very likely” messages

Rejected. The raw spawn context is unavailable; “working on behalf” has no binary criterion; and the 30 messages are repeated boilerplate, not independent judgments. A later artifact delivery would not independently prove authorization or owner alignment.

### Treat audit mechanisms as known outcomes

Rejected. A causal mechanism is not an observed outcome. “Would overwrite on a future deploy” and “would make stale advice win if activated” are counterfactuals. Labeling them true because code inspection supports the mechanism is circular.

### Score every uncertain sentence with an LLM judge

Rejected by the anti-overfit gate and by epistemic circularity. A model judge creates another uncertain claim, introduces correlated model error, adds cost, and still needs human/objective calibration. It can annotate candidates, never mint outcomes.

### Use owner corrections as negative outcomes

Rejected. The corpus says the correction detector is recall-biased and 41/41 in an unfiltered smoke sample were false positives (`corpus.json` structured `owner_correction_candidates.precision_warning`). A correction can also target scope, tone, or preference rather than factual truth.

### Add a separate forecasting database/service

Rejected. The existing ledger already sequences, timestamps, sanitizes, fsyncs, and replays arbitrary event fields (`ledger.py:817-907`). A new service would violate the anti-overfit constraint without adding an outcome source.

### Report only Brier score

Rejected. Brier score mixes calibration and resolution and is sensitive to question difficulty. The owner asked whether verbal bands are calibrated, which requires reliability frequencies and uncertainty intervals by band/cohort. Brier is complementary, not sufficient.
