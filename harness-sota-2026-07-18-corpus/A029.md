# A029 — coherence audit of `~/.claude/rules/dart/security.md`

Date: 2026-07-19  
Unit: A029

Subject root used: `/local_disk0/codexwork/bundle`

## Executive verdict

The Dart/Flutter security rule is not coherent with the rest of the deployed harness. I found ten reportable collisions spanning contradiction, staleness, unenforced requirements, unruled enforcement, and duplicated thresholds; several collisions legitimately have more than one class. The highest-impact issue is not wording: the always-on contract says secrets in code are block-worthy, while both shared secret gates are ineffective in the deployed default path. The generic post-edit hook has no Dart checker and the shared literal-secret guard is opt-in and absent from `settings.json`.

The most important resolution is a small consolidation, not a second security runtime: make the cross-tool contract distinguish server/build secrets from client runtime credentials; make the Dart rule say that client-bundled configuration is public; add Dart and manifest/build-file coverage to the existing post-edit/CI bus; and use one context-aware secret scanner. This is **very likely (80-90%)** to remove the identified incoherence because every proposed change targets a directly observed rule, matcher, or branch; the remaining uncertainty is real Windows hook wiring, which the unpacked Linux snapshot cannot execute.

No proposal below introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Every proposal rides the existing rule, hook, settings, or CI bus and therefore passes the anti-overfit gate.

## Detailed collisions

### C1 — server-style environment-only rule conflicts with mobile runtime credential storage

**Artifacts and exact lines**

- `claude/rules/dart/security.md:15-17`: compile-time configuration is passed with `--dart-define`; runtime secrets are stored in `flutter_secure_storage`.
- `claude/rules/dart/security.md:74-78`: tokens and credentials go to secure storage and must not be logged.
- `claude/AGENTS.md:93-98`: “Never hardcode secrets; use environment variables and validate presence at startup.”
- `claude/rules/common/security.md:38-43`: “ALWAYS use environment variables or a secret manager” and validate at startup.

**Class: CONTRADICTION.** A mobile app cannot treat a user session token acquired after login as a startup environment variable. Conversely, a secret embedded with `--dart-define`, an asset, or obfuscation is recoverable from the client and is not a server secret. The Dart file partly understands this at lines 15 and 23, but the higher always-on contract does not name the client/runtime exception.

**Precedence.** `AGENTS.md` §9 is higher and formally wins. That formal result is operationally harmful because blindly applying it would replace appropriate OS-backed runtime storage with an inapplicable process-environment rule. Section 10 does not provide a semantic exception mechanism; it only tells us which text wins. The two files therefore need reconciliation rather than silent obedience.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Amend the security floor to distinguish: (a) server/build/deployment secrets, which use environment references or a secret manager and are validated by the process that consumes them; (b) public client configuration, which may use Dart defines or bundled config but must be treated as extractable; and (c) user/session credentials obtained at runtime, which use platform secure storage with lifecycle clearing. Mirror those three categories in the Dart rule. This is **almost certain (90-99%)** to remove the textual contradiction because the categories directly cover both existing instructions; evidence is the conflicting lines above and the current package description of OS-specific secure storage at <https://pub.dev/packages/flutter_secure_storage>.

### C2 — “extends common/security.md” is false for Dart-triggered context

The always-loaded `CLAUDE.md` imports `AGENTS.md` at `CLAUDE.md:1-3`, so the four-line §9 floor survives; the detailed common checklist at `common/security.md:26-52` does not.

**Precedence.** None. This is a reachability defect, not a disagreement that ordering can solve.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Either add Dart/YAML/XML/plist/build-file patterns to `common/security.md`, or make common security unscoped and keep only language details scoped. Prefer one unscoped, concise non-negotiable floor plus scoped implementation details; official documentation also warns that path-scoped rules are lost after compaction until another matching read (<https://code.claude.com/docs/en/context-window>). It is **very likely (80-90%)** that unscoping the concise floor improves availability; the uncertainty is adherence cost from additional always-on tokens, settled by `/context` and `/memory` before/after measurements.

### C4 — “all PII only in key-value secure storage” conflicts with the canonical local repository pattern

**Artifacts and exact lines**

- `claude/rules/dart/security.md:72-78`: “Store tokens, PII, and credentials only in `flutter_secure_storage`” and clear cached user data on logout.
- `claude/rules/dart/patterns.md:21-55`: `UserRepositoryImpl` reads and writes `User` objects through `_local`, caches every remote user locally, and gives no encryption, minimization, retention, or logout constraint.
- `claude/rules/dart/patterns.md:207-227`: the data layer explicitly owns local datasources and DTO persistence.

**Class: CONTRADICTION.** Both are same-level Dart rule files. One forbids PII anywhere except a secure key-value store; the other makes generic local user-object persistence the recommended pattern. `flutter_secure_storage` describes itself as secure key-value storage, not a bulk relational/object store (<https://pub.dev/packages/flutter_secure_storage>). OWASP separately treats unencrypted PII in SharedPreferences, Room databases, DataStore, and ordinary files as risks (<https://mas.owasp.org/MASWE/MASVS-STORAGE/MASWE-0006/>), so the correct distinction is protection and minimization, not forcing every PII object into one plugin.

**Precedence.** Unresolved by §10 because both are language-rule peers. This collision must remain explicit until the files are edited.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Change the target to: store small credential material (refresh/access tokens, private keys) in OS-backed secure storage; minimize locally retained PII; place required structured/bulk sensitive data in an encrypted database/file protected by platform data-protection and backup rules; never put sensitive values in plaintext preferences/files. Add a one-line security qualifier to the `_local` repository example. This is **very likely (80-90%)** to resolve the mismatch and improve implementability; uncertainty is project-specific threat model and data volume, which must be decided in each project's security design.

### C7 — `.env` is presented as secret management although it is public client configuration, and enforcement is asymmetric

**Artifacts and exact lines**

This is **almost certain (90-99%)** to correct the factual guidance because it matches the package's own current security contract.

### C8 — Android secure-storage implementation description is stale

**Artifacts and exact lines**

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the parenthetical implementation claim with version-neutral language (“platform-backed encrypted storage; verify the pinned major version's Android cipher/migration/backup requirements”) and add a dependency-upgrade migration check. This is **almost certain (90-99%)** to age better because it removes an implementation detail already invalidated by a major release while retaining a verifiable package-level requirement.

### C10 — indiscriminate sanitization conflicts with boundary- and sink-specific handling

**Artifacts and exact lines**

- `claude/rules/dart/security.md:47-52`: says to “validate and sanitize all user input” before API or storage, then separately requires parameterized SQL and structured deep-link validation.
- `claude/AGENTS.md:93-98`: requires validation at system boundaries and names sanitization specifically for HTML output.
- `claude/rules/common/coding-style.md:51-57`: requires validation at system boundaries and says external data is untrusted.
- OWASP's input-validation guidance distinguishes syntactic/semantic validation from context-aware output encoding and warns that generic denylist filters reject legitimate input: <https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html>.

**Class: CONTRADICTION / REDUNDANCY.** The target restates the higher boundary-validation requirement but changes its threshold to mutation/sanitization of *all* input before ordinary API transmission or storage. That conflates validation, normalization, output encoding, and safe sink APIs. Its own SQL example correctly uses parameterization rather than trying to sanitize an email string.

**Precedence.** The higher `AGENTS.md` boundary rule is the floor. The Dart rule may add stricter controls under §10, but an indiscriminate transform is not a coherent specialization; it must specify the trust boundary and sink.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the first bullet with: validate untrusted data syntactically and semantically at entry boundaries; normalize only where the protocol defines a canonical form; use context-specific output encoding; use parameterized/safe APIs for interpreters; and validate server-side even when Flutter performs client validation for UX. This is **very likely (80-90%)** to preserve the intended security outcome without corrupting legitimate input because it matches both the higher harness rule and the cited OWASP distinctions.
