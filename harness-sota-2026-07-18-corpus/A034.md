# A034 — Coherence audit: `~/.claude/rules/golang/security.md`

## Verdict

The Go security rule is short, mostly compatible with the always-on security floor, and not itself in direct conflict with another language rule. Its principal defect is that its three obligations do not have a coherent enforcement path:

1. secret indirection/startup validation repeats stronger common and cross-tool rules but the current write path does not check Go files for hardcoded secrets;
2. `gosec ./...` is prescribed but is absent from the configured hook graph; and
3. `context.Context` timeout control is prescribed in language too broad to verify mechanically and has no checker.

The corpus proves that credential/secret guards blocked calls historically, but it does **not** retain enough successful command or source-diff content to establish whether Go code followed `gosec` or timeout guidance. Treating those historical blocks as proof of current Go-rule compliance would be wrong: the current shared guards explicitly say they are opt-in and off by default, while the corpus covers earlier sessions.

I found seven reportable collisions: one REDUNDANCY, three UNENFORCED gaps, one UNRULED enforcement, one STALE test/implementation contract, and one latent precedence CONTRADICTION. I found no verified skill collision because the supplied bundle omits both requested skill trees; that result is a GAPS finding, not an absence claim.

## Collision register

### C1 — REDUNDANCY: Go secret example duplicates two stronger rules

**Artifacts and exact lines**

- `claude/rules/golang/security.md:11-18`: `os.Getenv("OPENAI_API_KEY")` and fatal startup validation when it is empty.
- `claude/rules/common/security.md:38-43`: never hardcode; always use environment variables or a secret manager; validate required secrets at startup; rotate exposure.
- `claude/AGENTS.md:93-98`: never hardcode secrets, use environment variables, and validate at startup.

**Collision.** The Go file adds only syntax, not a different policy. Three copies create drift risk: the Go example omits the common rule's secret-manager alternative and rotation response. It does not contradict them, because an example using one allowed mechanism does not prohibit the other.

**Precedence.** §10 resolves substance: the AGENTS security floor controls; common and Go files may only add detail. It does not resolve whether duplicate text should remain.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the Go “Secret Management” prose with one explicit sentence that the AGENTS/common policy governs, retain only a Go-specific helper example, and make the example accept a variable name or typed configuration rather than canonizing one provider key. This consolidation is **very likely (80-90%)** to reduce future policy drift because the stronger obligations already exist verbatim at the cited common and AGENTS lines, while the language file needs only idiomatic implementation detail.

### C2 — UNENFORCED: hardcoded-secret/startup-validation rule has no working Go write gate

**Artifacts and exact lines**

- Demand: `claude/rules/golang/security.md:11-18`, extended common requirements at `claude/rules/common/security.md:38-43`, and the always-on floor at `claude/AGENTS.md:93-96`.
- Hook wiring: `claude/settings.json:333-342` invokes `hooks/per-edit-check/check.py` after Edit/Write/MultiEdit.
- Hook implementation: `hooks/per-edit-check/check.py:151-170` has no `.go` branch and silently passes unknown extensions; `:211-214` returns success when the dispatcher finds no issues.
- Shared guard state: `agents/harness/modules.py:84-99` says literal-secret blocking is opt-in and off by default; `:738-755` never blocks a user prompt and only scans tool input when `HARNESS_SECRET_GUARD` is enabled.
- Local credential hook state: `hooks/deny-credential-reads/deny.py:74-89` says the credential-file block is opt-in and exits 0 by default. This hook prevents reads, not hardcoded-secret writes, even when enabled.

**Collision.** An agent can write a `.go` file containing a credential-shaped literal; the configured edit hook will take the unknown-extension path and return 0. Startup presence validation is semantic and is likewise unchecked. The behavioral rule remains in force, but “ALWAYS ON” is not structurally true for this write path.

Add `.go` integration fixtures. This is **very likely (80-90%)** to cover Go writes because the hook is already wired to all Edit/Write/MultiEdit events (`settings.json:333-342`) and a pre-dispatch scan is extension-independent. False-positive safety remains important: the known live defect says prose-as-code scanning produced repeated false positives (`inputs/INPUT-known-harness-defects.md:9-48`), so Markdown and test samples must be discriminated by semantic role.

### C3 — UNENFORCED: `gosec ./...` is demanded but absent from the hook graph

**Artifacts and exact lines**

- Actual edit hook: `hooks/per-edit-check/check.py:8-17` documents supported/skipped languages and omits Go; `:151-170` confirms the executable dispatch.

Neither includes gosec. `claude/settings.json:602-603` also disables the generic security-guidance and Semgrep plugins; neither would be evidence of gosec in any event.

**Collision.** The rule does not define when `gosec` must run, while the aspirational Go hooks document and the active graph both omit it. This is both badly written (no trigger/scope/failure semantics) and unenforced. It is not evidence that gosec was never run manually.

**Precedence.** No higher layer contradicts gosec. Precedence therefore does not resolve the missing trigger or enforcement.

**Specific resolution [UNVERIFIED] — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Rewrite the obligation to “before a completion claim that changes Go code, run `gosec` on changed packages or the repository's canonical security target; report unavailable/failed scans explicitly.” Extend the existing validation hook with a changed-Go-package lane or a Stop-time advisory receipt. Do not launch a daemon or new orchestration runtime. This is **likely (55-80%)** to provide useful enforcement because the existing bus already receives edit and Stop events, but package resolution and acceptable scan duration are **UNVERIFIED — the experiment is to replay the hook against three representative Go repositories (small module, multi-module workspace, generated-code-heavy module) and measure path resolution, runtime, and false-positive rate before choosing per-edit versus Stop-time execution.**

### C4 — UNENFORCED: absolute timeout wording is mechanically unverifiable and underspecified

**Artifacts and exact lines**

- Demand: `claude/rules/golang/security.md:27-34` says always use `context.Context` “for timeout control” and shows `context.WithTimeout(ctx, 5*time.Second)`.
- The active post-edit validator has no Go parsing/checking branch (`hooks/per-edit-check/check.py:151-170`).
- Settings contain tool/hook operational timeout values (`claude/settings.json:9-14`, `:81-529`), but those govern Claude tools and hook commands, not timeouts inside Go programs.
- `claude/rules/common/cross-vendor-dispatch.md:62-65` requires a 30-minute timeout for agent-runtime shelling; that is a different operational layer and is not a conflicting five-second Go threshold.

**Collision.** “Always” does not say which operations require a deadline, whether the function should accept a caller context, whether a caller deadline is sufficient, or whether five seconds is normative. A textual hook cannot reliably distinguish an outbound operation that needs cancellation from pure computation or a function whose caller already supplies a deadline. This rule is therefore badly written first and unenforceable second. I found no contradictory timeout threshold: five seconds is inside an example, while the 30-minute rule addresses cross-vendor runtime calls.

**Precedence.** No higher layer resolves the semantic scope.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the absolute wording with a reviewable contract: boundary functions performing cancellable I/O accept and propagate a caller `context.Context`; entry points establish a workload/configuration-appropriate deadline where none exists; all derived contexts call `cancel`; do not replace an earlier caller deadline with a fixed constant. Keep the checker advisory: use `go vet`/static analysis plus review prompts, not a regex block. This is **likely (55-80%)** to be more enforceable because each clause corresponds to reviewable call-boundary behavior, whereas the current universal sentence supplies no scope. Whether a lightweight analyzer can enforce all clauses is **UNVERIFIED — the settling experiment is to run candidate analyzers against a labeled set of Go call sites with and without propagated deadlines and report precision/recall before adding any hard gate.**

**Collision.** The permission configuration enforces a broader policy than the rule set states. It can prevent diagnosing or migrating the very configuration that supplies environment values. The local hook's owner-directed opt-in policy and the unconditional-looking settings deny also express different operational defaults.

**Precedence.** §10 places the permission system first, so settings win at runtime. That resolves what happens, but not the coherence defect: an enforcement with no articulated rule is still UNRULED.

**Specific resolution [UNVERIFIED] — CONFIG (settings/JSON only).** Choose one documented policy and make both mechanisms share it. Given the explicit owner directive in `deny.py:74-89`, narrow the settings deny to true private-key material and make `.env`/credential-file inspection an opt-in guarded mode, while retaining output redaction and literal-secret write scanning. This is **likely (55-80%)** to reduce legitimate-work blocks because the hook records that exact motivation, but the effect of `defaultMode: bypassPermissions` on deny semantics is **UNVERIFIED — the settling experiment is a Windows Claude Code permission matrix with four harmless fixture paths (`.env`, `.pem`, `credentials.json`, ordinary `.go`) under default and opt-in guard modes, recording whether settings or hooks block each operation.**

### C7 — CONTRADICTION: blanket language-rule precedence can purport to override the security floor

**Artifacts and exact lines**

**Collision.** The target currently does not relax common security, so this is latent rather than an active bad Go behavior. But the README's unqualified override rule would authorize a future Go security relaxation that §10 explicitly forbids.

**Precedence.** §10 resolves the present decision: AGENTS security wins. It does not make the contradictory README safe to leave in place.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Amend `rules/README.md:93-99` to say language files may specialize implementation details and add stricter requirements, but cannot relax AGENTS §6/§9/§9b or another same-level security requirement without surfacing the conflict.
