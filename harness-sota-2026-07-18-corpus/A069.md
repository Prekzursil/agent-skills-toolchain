## Executive verdict

The Swift security rule is not coherent enough to remain unchanged. I found **eight reportable collisions**: two contradictions, two redundancies with materially different wording, two unenforced groups, one unruled enforcement, and one stale platform prescription. The highest-risk defect is not missing prose; it is that the rule explicitly presents `.xcconfig` as a build-time **secret** channel while the higher security floor says secrets must come from environment variables or a secret manager and must be checked at startup. The next highest-risk defect is the unconditional certificate-pinning instruction, which conflicts with current Apple guidance to avoid pinning in most cases and use it only when absolutely necessary.

The operational answer is also asymmetric. There is real historical evidence that generic credential/secret guards blocked work (15 + 7 + 3 normalized error fingerprints), but there is no usable evidence that the Swift-specific requirements were followed. The corpus's own hook detector is broken, its samples are capped, and no Swift security term appears in the distilled fields. Consequently, any claim that Keychain, ATS, URL validation, certificate trust, or pasteboard/deep-link validation was followed is **UNVERIFIED; the settling experiment is to query raw transcripts and changed Swift/Info.plist files for sessions that edited `.swift` or `Package.swift`, then inspect the resulting diffs and hook events**.

The recommended architecture stays minimal. All resolutions are rule/config edits or one small PostToolUse checker on the existing hook bus. No second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is proposed.

## Collision register

### C1 — `.xcconfig` is called a secret channel while the higher floor forbids shipped/hardcoded secrets

**Class: CONTRADICTION**  
**Artifacts and exact lines:**

- `rules/swift/security.md:13`: “Use environment variables or `.xcconfig` files for build-time secrets.”
- `rules/swift/security.md:14`: “Never hardcode secrets in source — decompilation tools extract them trivially.”
- `AGENTS.md:95`: “Never hardcode secrets; use environment variables and validate presence at startup.”
- `rules/common/security.md:40-43`: never hardcode; use environment variables or a secret manager; validate at startup; rotate exposures.

An `.xcconfig` is a plain build-settings file, not a secret manager. Apple describes it as a text file whose settings are deliberately easy to inspect and edit, and warns to deselect targets to avoid embedding the file as a resource: [Apple, Adding a build configuration file](https://developer.apple.com/documentation/xcode/adding-a-build-configuration-file-to-your-project/). Calling `.xcconfig` a place for **secrets** also collides internally with `security.md:14`: a client build that consumes a credential can expose the resulting value even if the source `.xcconfig` itself is ignored.

**Precedence:** AGENTS §9 wins. The `rules/README.md:95` “specific overrides general” rule is lower than AGENTS §10 and cannot relax the security floor.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Rewrite line 13 to distinguish nonsecret build configuration from secrets: `.xcconfig` may hold public endpoints, feature flags, and identifiers; deployable client apps must not contain server-side secrets. Use CI/secret-manager injection only for build operations whose values do not ship, and use Keychain for user/runtime credentials. Keep startup validation only where an environment-provided value is legitimately runtime-required. This wording change is **almost certain (90-99%)** to remove the policy contradiction because the evidence is the target's own adjacent lines plus the higher AGENTS/common floor; whether any existing Swift project relies on shipped `.xcconfig` credentials is **UNVERIFIED; the settling experiment is a secret scan of tracked/untracked `.xcconfig`, generated Info.plist, build settings output, and a release archive**.

### C2 — the language-rule precedence statement conflicts with the security precedence contract

**Class: CONTRADICTION**  
**Artifacts and exact lines:**

- `rules/README.md:93-98`: language-specific rules take precedence over common rules when they conflict.
- `AGENTS.md:121-131`: security is higher precedence; lower layers may be stricter, never laxer; same-level conflicts must be surfaced.

The README supplies an unrestricted override rule, while AGENTS supplies a security exception to precisely that behavior. The target's word “extends” does not resolve whether its alternatives replace or supplement common security. This ambiguity is what permits C1.

**Precedence:** AGENTS §10 resolves the immediate decision in favor of the higher security floor. It does **not** repair the contradictory README text for future readers.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Amend `rules/README.md:93-98` to say language rules may override ordinary idiom defaults, but security/safety non-negotiables can only be strengthened. Add the same one-sentence guard to the Swift file's extension preface. This is **almost certain (90-99%)** to make precedence deterministic because both conflicting policies are explicit at the cited lines.

### C3 — unconditional certificate pinning is stale and differs from the harness's other mobile threshold

**Class: STALE**  
**Artifacts and exact lines:**

- `rules/swift/security.md:26`: “Use certificate pinning for critical endpoints.”
- `rules/dart/security.md:36`: “Consider certificate pinning for high-security endpoints.”
- `rules/swift/security.md:27`: “Validate all server certificates.”

The two language rules are path-scoped and therefore do not directly compete on one source file, so AGENTS precedence does not select one. They nevertheless state different harness-wide risk thresholds: mandatory for “critical” Swift endpoints versus conditional consideration for “high-security” Dart endpoints. Current Apple guidance says pinning is not required, should be deployed cautiously only when absolutely necessary, and in most cases should be avoided because default TLS already performs system trust evaluation: [Apple, Identity Pinning](https://developer.apple.com/news/?id=g9ejcf8y). Apple separately documents ATS and default server trust: [Apple, Identifying blocked connections](https://developer.apple.com/documentation/security/identifying-the-source-of-blocked-connections).

**Precedence:** unresolved by AGENTS because these are same-level, non-overlapping language addenda. Current authoritative platform guidance breaks the technical tie; it does not create a harness precedence rule.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Replace lines 26-27 with: rely on platform server-trust evaluation; never accept-all or bypass challenges; pin identities only for an explicit threat model, with backup pins, rotation, expiry monitoring, and a tested recovery path. Align Dart wording to the same decision rule in its own audit rather than modifying it in this unit. The claim that the unconditional instruction is stale is **almost certain (90-99%)**, supported by Apple's explicit “most cases” guidance. The appropriate pinning decision for any particular owner endpoint is **UNVERIFIED; the settling experiment is a threat-model review plus a staged certificate-rotation/failure-recovery drill**.

### C4 — input validation is redundantly restated with a different action and threshold

**Class: REDUNDANCY**  
**Artifacts and exact lines:**

- `rules/swift/security.md:31`: sanitize **all** user input **before display**.
- `rules/swift/security.md:33`: validate APIs, deep links, and pasteboard data before processing.
- `AGENTS.md:98`: validate inputs at system boundaries; sanitize before HTML output.
- `rules/common/coding-style.md:51-57`: validate all user input before processing and never trust external data.
- `rules/common/security.md:30-32`: all user inputs validated; sanitized HTML for XSS prevention.

The Swift text conflates validation, output encoding, and sanitization. It is broader at display time (“all” displayed text) but narrower about the sink (it does not name HTML/WebKit, SQL, file paths, or commands). The higher floor is clearer: validate at the boundary and sanitize/encode for the actual sink. Apple specifically treats incoming URL parameters as an attack surface and requires malformed values to be discarded: [Apple, Supporting universal links](https://developer.apple.com/documentation/Xcode/supporting-universal-links-in-your-app).

**Precedence:** AGENTS §9 controls. Swift may add platform examples but should not redefine the general action.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Replace line 31 with sink-aware language: validate external data against an allowlisted schema at ingress; encode plain text with native UI APIs; sanitize only when intentionally rendering rich HTML in WebKit; parameterize SQL and validate file/URL components for their respective sinks. Keep line 33 as Swift examples, adding scheme/host/path/action allowlists for deep links. This rewrite is **very likely (80-90%)** to reduce misapplication because it maps actions to sinks and matches three higher-layer lines; the remaining uncertainty is project UI composition. **UNVERIFIED; the settling experiment is to run adversarial unit tests through each actual input-to-sink path, including malformed and destructive deep links.**
