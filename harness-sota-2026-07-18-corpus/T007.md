# T007 — Competitive teardown: Goose

**Unit:** T007  
**Research date:** 2026-07-19 UTC  
**Subject:** Goose, the AAIF/Linux Foundation open-source agent formerly hosted by Block  
**Comparison target:** the owner's Claude Code + Codex + shared harness, using only the read-only bundle available on this Linux job node

## 0. Bottom line

Goose is not a better wholesale replacement for this owner's harness. Its core loop is clean and unusually inspectable, its cross-provider surface is broad, and several recent mechanisms are worth porting. But its default security posture is materially weaker, its memory is less governed, its generic loop prevention is effectively inactive in the inspected constructor, and its multi-agent verification can silently turn a failed reviewer into an empty finding set. The owner's harness is more epistemically ambitious and has stronger cross-provider memory, verification rules, and fan-out contracts; Goose is better at packaging a few of those ideas as concrete runtime primitives.

The highest-value Goose ideas to port are:

1. executable postconditions and bounded retries attached to a reusable workflow;
2. a hard cap on consecutive Stop-hook vetoes;
3. typed hook payloads whose matcher is the semantic field (tool name, path, or command), not an arbitrary serialization;
4. explicit session identity propagated into extension processes;
5. bounded, per-file and per-check review fan-out with model/tool/turn overrides;
6. session/subagent-scoped extension sets and per-subagent turn limits;
7. a first-class structured final-output tool that gives validation feedback in-loop—only with permissive schemas, because this owner's measured strict-schema failure rate is already severe.

The strongest recommendation is evolutionary, not replacement: port those primitives onto the existing native agent/hook/skill/MCP buses. This is **very likely (80-90%)** to produce more value per unit of complexity than adopting Goose as a fourth agent runtime, because every proposed mechanism below rides an existing bus, while the measured corpus already shows that tool proliferation, dead MCP routing, schema strictness, and Windows process inflation are major failure modes (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11,13-118,175-182`; owner's pinned ENAMETOOLONG ground truth). The remaining uncertainty is integration behavior on the actual Windows subject; a shadow replay of the corpus's recorded failures through each proposed mechanism would settle it.

**Do not replace Claude/Codex with Goose.** That recommendation is **almost certain (90-99%)**, based on four independent facts: (a) the owner already has native multi-agent, hooks, goals, memories, tool search, and MCP apps enabled (`/local_disk0/codexwork/bundle/codex/config.toml:77-130`); (b) Claude already has native fan-out, tool search, hooks, and auto-compaction configured (`/local_disk0/codexwork/bundle/claude/settings.json:4-20,81-180`); (c) Goose defaults to full autonomy and uses best-effort/LLM permission classification; and (d) adding another orchestration runtime is explicitly rejected by the anti-overfit gate. A controlled same-task benchmark across Goose, Claude, and Codex on this owner's Windows error corpus would settle the residual 1-10% uncertainty.

## 2. Architecture snapshot

Goose is a Rust agent runtime with CLI, desktop/ACP, provider adapters, session persistence, an MCP-centric extension manager, platform extensions, recipes, plugins, hooks, skills, custom agents, and subagents. The current README advertises 15+ providers and 70+ MCP extensions: <https://github.com/aaif-goose/goose/tree/8e78960e535ab7f34630e7c5921a42f146cbc9f4#goose>.

Its architectural center is one provider-driven loop in `Agent::reply` / `reply_internal`. The loop persists conversation state through `SessionManager`, prepares the system prompt and current tool set, streams a provider response, classifies tool calls, runs inspectors/permissions, executes approved tool calls concurrently, appends tool responses, and calls the provider again until the model returns without tools or another terminal condition fires. Source: [`agent.rs:1553-1846`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1553-L1846), [`agent.rs:1932-2051`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1932-L2051), and [`agent.rs:2165-2277`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2165-L2277).

This is a valuable design property: recipes, structured output, hooks, compaction, goal checks, permissions, and tool execution are integrated into the same loop instead of being independent prompt conventions. The owner already has the same native-loop advantage in Claude and Codex; the shared Python dispatcher should remain an adapter/control plane, not become a second loop.

## 3. Agent loop teardown

### 3.1 Exact loop behavior

1. `reply` resolves elicitations, emits `SessionStart` on the first agent turn, emits `UserPromptSubmit`, handles slash commands, persists the user message, and checks proactive compaction before entering the loop ([`agent.rs:1553-1846`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1553-L1846)).
2. `reply_internal` prepares the conversation, tools, toolshim tools, system prompt, context cutoff, mode, and model configuration; it then loads project instructions ([`agent.rs:1849-1874`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1849-L1874)).
3. Each iteration checks cancellation and queued steering messages, increments a turn counter, enforces `max_turns`, injects top-of-mind context, then streams a provider completion with the current tools ([`agent.rs:1932-2045`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1932-L2045)).
4. Tool requests are separated into frontend and ordinary tools. In non-chat modes, Goose runs security, egress, adversary, permission, and repetition inspectors before dispatch ([`agent.rs:2194-2277`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2194-L2277); [`agent.rs:659-687`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L659-L687)).
5. Tool futures are multiplexed, results are persisted, newly enabled extensions refresh the prompt/tool set, and the loop continues. A no-tool response enters final-output, goal/grind, recipe-retry, empty-turn-retry, or terminal handling ([`agent.rs:2662-2818`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2662-L2818)).
6. A blocking Stop hook can inject a reason and continue the loop, but consecutive vetoes are capped; after the cap Goose ends the turn ([`agent.rs:2894-2918`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2894-L2918)).

### 3.2 Strong points

- **Empty-turn recovery is explicit and bounded.** v1.43.0's changelog calls out retrying empty provider turns rather than stopping silently, and source drops empty assistant messages before bounded retry ([release v1.43.0](https://github.com/aaif-goose/goose/releases/tag/v1.43.0); [`agent.rs:2681-2795`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2681-L2795)).
- **Human steering is drained between iterations.** Pending user messages can alter an active run without creating a second runtime ([`agent.rs:1951-1975`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1951-L1975)).
- **Maximum turns is a runtime invariant.** Main sessions default to 1,000 turns, subagents to 25, and the user can override both. Docs: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/sessions/smart-context-management.md#L163-L172> and <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/subagents.mdx#L267-L300>.
- **The same loop owns structured output and postcondition retry.** That is more reliable than hoping a prompt remembers to self-check.

### 3.3 Weak points / do not copy

- **The generic repetition inspector is wired with `None`.** `RepetitionInspector` only blocks when `max_repetitions` is `Some`; the default agent registers `RepetitionInspector::new(None)`. These are two mechanically independent positive source fields: behavior at [`tool_monitor.rs:41-80`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/tool_monitor.rs#L41-L80), wiring at [`agent.rs:659-687`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L659-L687). The owner's two-strikes rule is conceptually better because it fingerprints approach/failure and requires a pivot, whereas Goose only compares exact tool name+arguments when enabled (`/local_disk0/codexwork/bundle/claude/AGENTS.md:51-57`).
- **`/grind` is deliberately anti-pivot.** It reinjects “keep working” until `max_turns`, even after the model has tried to finish ([`agent.rs:2742-2758`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2742-L2758)). Do not copy this into the owner harness; it conflicts directly with the measured two-strikes discipline.
- **`/goal` is a self-report, not proof.** It gives the same model one extra chance to check whether its goal is met ([`agent.rs:2723-2740`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2723-L2740)). The owner already requires a receipt plus postcondition and two independent signals for “done” (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:20-37`), which is stronger.

## 4. Context management

### 4.1 What Goose does

Goose uses two layers:

- proactive auto-compaction at 80% by default, configurable through `GOOSE_AUTO_COMPACT_THRESHOLD`;
- overflow strategies `summarize`, `truncate`, `clear`, or `prompt`, with summarization as headless default.

Docs: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/sessions/smart-context-management.md#L19-L50> and <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/sessions/smart-context-management.md#L87-L161>.

Compaction preserves the most recent eligible user text, marks old messages user-visible but agent-invisible, inserts an agent-only summary plus continuation instruction, and persists the replacement conversation ([`context_mgmt/mod.rs:67-169`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L67-L169)). If exact usage is absent, the threshold check estimates tokens from agent-visible messages; provider-managed context bypasses Goose compaction ([`context_mgmt/mod.rs:172-224`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L172-L224)).

Separately, Goose summarizes older tool request/response pairs in batches while protecting current-turn calls. The cutoff scales with effective context, is clamped to 10-500 calls, and each selected pair is summarized asynchronously ([`context_mgmt/mod.rs:432-473`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L432-L473), [`context_mgmt/mod.rs:510-595`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L510-L595)). Large single tool responses can be written to a temporary file instead of injected inline; default threshold is 200,000 characters: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/environment-variables.md#L270-L310>.

### 4.2 Comparison

The owner's Claude threshold is 90%, and Codex has request compression enabled (`/local_disk0/codexwork/bundle/claude/settings.json:17-18`; `/local_disk0/codexwork/bundle/codex/config.toml:82-87`). Goose's 80% leaves a larger recovery margin but compacts earlier. Neither threshold is intrinsically superior without a workload test.

Goose's per-tool-pair summarization is more concrete than anything visible in the reduced owner bundle. However, it spends model calls to replace exact evidence with lossy summaries. For this owner—whose work includes audits and reverse engineering—copying it globally would risk deleting decisive details. The right port is selective and native-provider-first, not another summarization service.

### 4.3 Proposal: selective oversized-result externalization — UNVERIFIED benefit

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add one post-tool adapter that, for results above a configured byte threshold, writes the full result to a session-scoped artifact and returns a bounded header plus path/hash, while exempting already-structured small outputs and tools whose exact inline output is required. This is **likely (55-80%)** to reduce context pressure without the fidelity loss of LLM summarization, because Goose demonstrates the same basic externalization mechanism and the owner's corpus has very large tool traffic; the exact benefit is UNVERIFIED. A replay measuring tokens, task success, and later evidence retrieval on the 100 largest corpus tool outputs would settle it.

Do not add a vector store, context daemon, or second memory system. This passes the anti-overfit gate because it is a small adapter on the current result bus.

## 5. Memory and continuity

### 5.1 Goose memory surfaces

Goose has at least four different continuity mechanisms:

1. **Session history** stored by `SessionManager` and searchable through Chat Recall. Chat Recall searches previous conversation content and loads session summaries: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/mcp/chatrecall-mcp.md#L11-L90>.
2. **Memory MCP extension** with global and project scopes. Files live under `~/.config/goose/memory/` and `.goose/memory/`; tools remember, retrieve, remove category, and remove a matching memory: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/mcp/memory-mcp.md#L53-L99>.
3. **Global-memory prompt injection.** At Memory extension initialization, all global memories are loaded into instructions ([`memory/mod.rs:105-144`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose-mcp/src/memory/mod.rs#L105-L144)).
4. **Top of Mind**, a platform extension that injects persistent instructions every turn; it is listed as a built-in platform extension: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/getting-started/using-extensions.md#L34-L47>.

### 5.2 Where Goose is worse

- Memory files are category-based plaintext append stores, not a governed semantic memory. `remove_specific_memory` filters entries with substring containment ([`memory/mod.rs:272-295`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose-mcp/src/memory/mod.rs#L272-L295)). That is a fragile deletion identity.
- All global memories are injected into extension instructions at initialization. This scales poorly and has no visible temporal supersession, contradiction resolution, provenance ranking, or retrieval budget in the inspected implementation ([`memory/mod.rs:105-144`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose-mcp/src/memory/mod.rs#L105-L144)).
- Project memory is a separate `.goose` namespace, creating another cross-agent store. The owner already declares Basic Memory canonical and distinguishes semantic memory from objective event history (`/local_disk0/codexwork/bundle/codex/AGENTS.md:79-85`; `/local_disk0/codexwork/bundle/claude/AGENTS.md:85-91`).

**Do not copy Goose Memory or Top of Mind — UNVERIFIED local-overlap premise.** This is **almost certain (90-99%)** to worsen duplication and precedence ambiguity, because the owner's audit claim already reports overlapping native Claude, Basic Memory, remember-plugin, and Codex memory streams (`/local_disk0/codexwork/bundle/inputs/audit-findings/E08.md:26-39,71-82`), while Goose would add yet another store and always-injected stream. The local-overlap premise is UNVERIFIED on this reduced node; a startup-prompt capture across both providers would settle it. The further uncertainty—whether Goose memory retrieval quality would exceed Basic Memory on this owner's notes—would be settled by a blinded retrieval benchmark, but it does not justify adding the store first.

## 6. Tool and MCP handling

### 6.1 Goose mechanisms

- Extensions can be built-in, platform, stdio, Streamable HTTP, frontend, or recipe-defined inline Python. Recipes can restrict `available_tools` and set per-extension timeouts: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/recipes/recipe-reference.md#L152-L235>.
- MCP Roots automatically expose the active session working directory to roots-aware servers: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/getting-started/using-extensions.md#L120-L125>.
- The Extension Manager can dynamically discover, enable, and disable extensions during a session; this built-in is enabled by default: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/getting-started/using-extensions.md#L34-L45>.
- Goose caches the aggregate tool set and attaches owning-extension metadata. It also attempts to recover provider-mangled names such as `extension.tool` back to `extension__tool` ([`extension_manager.rs:185-205`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/extension_manager.rs#L185-L205), [`extension_manager.rs:257-305`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/extension_manager.rs#L257-L305)).
- Before launching `npx` or `uvx` stdio extensions, Goose queries OSV and blocks advisories whose IDs begin `MAL-`; unknown commands, network failures, HTTP failures, and JSON failures fail open ([`extension_malware_check.rs:31-67`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/extension_malware_check.rs#L31-L67), [`extension_malware_check.rs:188-268`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/extension_malware_check.rs#L188-L268)).
- Goose docs warn it performs best with fewer than 25 enabled tools (<https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/managing-tools/tool-permissions.md#L11-L27>). This is much smaller than the owner's catalog, but the owner already uses native deferred tool search at 5% and measured ToolSearch at 0.08% errors (`/local_disk0/codexwork/bundle/claude/settings.json:17`; `/local_disk0/codexwork/bundle/inputs/corpus.json:87-94`).

### 6.2 Comparison

Goose's extension scoping is cleaner than globally exposing every MCP to every recipe/subagent. That directly addresses the owner's dead-MCP and Windows process-forest problems: `claude_ai_Tavily` was called 532 times with 25.8% errors, including 135 “not connected” errors, and orphaned plugin directories inflate Windows command lines (pinned ground truth; corpus tool entry begins at `/local_disk0/codexwork/bundle/inputs/corpus.json:175`).

However, dynamically enabling an extension during a run still risks mutating tool state mid-session, and Goose's own historical design discussion documented shared-agent/session interference before the session-aware execution work: <https://github.com/aaif-goose/goose/discussions/4389>. The current source has moved materially since that 2025 discussion, so it is background, not current proof.

### 6.3 Proposal: task-scoped MCP profiles with dead-end suppression

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Define a small set of task profiles that eagerly enable only the native core plus the MCPs required for that task; keep all other tools discoverable through native Tool Search, and mark known-dead endpoints disabled until an independent health probe passes. This is **very likely (80-90%)** to reduce dead calls and process pressure because native deferred Tool Search is already live and highly reliable, while the worst MCP is demonstrably dead yet callable. Settlement: A/B 100 representative sessions, comparing enabled process count, tool-selection accuracy, startup latency, dead calls, and task completion.

This is configuration on existing provider/MCP buses, not a router service. Do not adopt Goose's “<25 tools” as a literal universal threshold; native tool search changes the active-schema economics.

### 6.4 Proposal: session identity in every extension/tool environment — UNVERIFIED local gap

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Goose exports `AGENT_SESSION_ID` to stdio extensions and Developer shell commands, enabling isolated handoff paths: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/environment-variables.md#L540-L625>. The earlier local audit claims objective receipts can lose session identity and allow sibling receipts to satisfy another session (`/local_disk0/codexwork/bundle/inputs/audit-findings/B15.md:5-52`), but that premise is **UNVERIFIED** on this reduced node. Before building, capture one Claude and one Codex tool-hook envelope from two simultaneous sessions and prove whether provider/session/turn IDs survive into ledger receipts. If the audit claim reproduces, add the already-available session/thread ID to the shared envelope and extension environment.

Conditional on reproduction, this is **almost certain (90-99%)** to eliminate the specific cross-session wildcard class because it changes the receipt key from project/global scope to provider+session+turn; the concurrency regression suite named in B15 would settle it.

## 7. Permission model

### 7.1 Goose permission layers

Goose exposes four modes:

- Autonomous: all tools execute;
- Manual approval;
- Smart approval;
- Chat only.

Autonomous is documented as the default: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/managing-tools/goose-permissions.md#L25-L36>.

Manual and Smart modes support per-tool `Always Allow`, `Ask Before`, and `Never Allow`: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/managing-tools/tool-permissions.md#L29-L40>. Permission precedence in source is: explicit user rule; MCP read-only annotation; force approval for extension management; LLM read-only detection in Smart mode; otherwise ask. Unknown tools therefore ask unless Auto is selected ([`permission_inspector.rs:155-193`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/permission/permission_inspector.rs#L155-L193)).

The LLM judge prompt explicitly treats request IDs, names, and arguments as untrusted and tells the judge not to obey embedded instructions ([`permission_judge.rs:40-88`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/permission/permission_judge.rs#L40-L88)). This is thoughtful, but the classification is still probabilistic.

### 7.2 Comparison and verdict

The owner's live modes are also effectively autonomous: Claude uses `bypassPermissions` over both drives, and Codex uses `approval_policy="never"` plus `danger-full-access` (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`; `/local_disk0/codexwork/bundle/codex/config.toml:6-7`). Goose is therefore not uniquely weak relative to current configuration, but it is worse as a product default because full autonomy is the documented default.

Do not copy LLM-based read/write classification as a security boundary. The owner's confirmed D1 defect is exactly semantic misclassification from inspecting payload text without role/context (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:7-85`). A second probabilistic classifier would create another detector, not fix the discriminator.

### 7.3 Proposal: use MCP annotations and explicit rules, never Smart classification

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

For tasks that need approvals, use native Claude/Codex permission controls and explicit per-tool allow/ask/deny rules; consume MCP `readOnlyHint` only as an allow hint for known tools, with explicit deny rules winning. This is **likely (55-80%)** to reduce approval noise without introducing Goose's LLM judge; the uncertainty is whether all high-volume MCPs publish trustworthy annotations. Inventory annotations across enabled servers and replay 200 read/write calls to settle it.

## 8. Customisation surface: rules, skills, hooks, plugins, agents, recipes

### 8.1 Rules / persistent instructions

`.goosehints` provides global and hierarchical project instructions. Local instructions override global ones; nested files load when Goose accesses nested directories; hints are added to the system prompt on every request. Goose can also load `AGENTS.md`, `CLAUDE.md`, and custom filenames through `CONTEXT_FILE_NAMES`: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/using-goosehints.md#L33-L43> and <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/using-goosehints.md#L73-L114>.

The owner is already stronger here: shared behavior contracts, language rules, project rules, and measured fan-out prompt requirements exist. Goose's cross-compatibility paths are useful confirmation that `.agents/` is becoming a portable convention, but there is nothing to port.

### 8.2 Skills

Goose skills are progressive-disclosure `SKILL.md` packages with name/description indexed at session start and full instructions loaded on match or explicit request. It discovers global, project, plugin, Goose, and Claude paths and supports scripts/templates: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/using-skills.md#L7-L43> and <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/using-skills.md#L92-L109>.

The owner already has approximately 355 installed skills but only 78 invoked (pinned corpus ground truth). Goose does not solve that discovery/quality problem; it uses the same description-based loading model. Do not add more skills merely for Goose parity.

### 8.3 Hooks

Goose implements the Open Plugins hook convention. Plugins supply `hooks/hooks.json`; commands receive JSON on stdin. Supported events include session start/end, Stop, prompt submit, pre/post/failure tool use, before read, after edit, before/after shell. The matcher target is explicitly the tool name, prompt text, path, or shell command: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/hooks.md#L97-L169>.

The payload includes `session_id`, `matcher_context`, `tool_name`, `tool_input`, message, assistant text, and working directory. For built-in write/edit tools it documents separate `path` and content fields: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/hooks.md#L156-L230>. That separation is precisely the semantic input needed to avoid the owner's “use vs mention” false positives.

Only PreToolUse and Stop can block. PreToolUse blocks on exit 2/stderr or a JSON block decision. Broken hooks fail open. Stop vetoes are capped: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/hooks.md#L232-L251>.

#### Proposal: shared semantic hook envelope + discriminator

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Normalize every provider hook into `{provider,event,session_id,turn_id,tool_name,target_path,command,content_role,success}` and make all guards call one `is_real_occurrence` discriminator. Matcher input must be the semantic field; document bodies must never be command-guard input. This is **almost certain (90-99%)** to prevent the nine recorded D1/D1a/D1b false fires because each was caused by matching the wrong field, and Goose demonstrates that the required fields can be separated. First dump actual Claude and Codex hook schemas—the pinned defect explicitly marks field availability UNVERIFIED—then replay all recorded false fires plus known-positive executable commands (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:28-95`).

This directly follows the pinned defect and introduces no new runtime.

#### Proposal: cap consecutive Stop vetoes

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a session-scoped consecutive-veto counter to the existing dispatcher; after a small cap, persist a warning receipt and allow termination. Reset on a real tool action or user input. This is **very likely (80-90%)** to prevent a broken finalizer from creating an infinite model/hook loop because Goose uses the same invariant and tests it in-loop ([`agent.rs:2894-2918`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2894-L2918)). A hermetic hook that always vetoes, alternates veto/allow, and fails to spawn would settle local correctness.

### 8.4 Plugins

Goose plugins bundle skills and hooks, install from Git, namespace imported skill names, support disable lists, and optionally auto-update before skill loading. Failed update continues with the installed copy: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/plugins.md#L7-L24>, <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/plugins.md#L118-L169>.

Do not copy auto-update-on-load. The owner's Windows installation already contains roughly 1,293 orphaned plugin directories whose path expansion causes ENAMETOOLONG/os error 206, and one apparent orphan was live (pinned ground truth). Automatic replacement without reference-aware garbage collection would aggravate that class.

### 8.5 Custom agents and recipes

Custom agents are Markdown role files in `.agents/agents`, with optional model, which can be loaded into the current context or delegated into an isolated session. Goose also discovers Claude-compatible paths: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/custom-agents.md#L7-L29> and <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/custom-agents.md#L81-L105>.

Recipes are the richer workflow primitive: YAML/JSON packages instructions, prompt, extension set, parameters, structured response, retry checks, model settings, and subrecipes: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/recipes/recipe-reference.md#L37-L56>.

The owner has skills, commands, and agents, but the reduced bundle does not show one portable manifest that binds **instructions + exact tools + model + postcondition + retry**. That integrated recipe contract is Goose's clearest capability lead.

#### Proposal: “verified workflow” manifest

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add an optional manifest beside a skill/command containing: `instructions`, `allowed_tools`, `model_class`, `max_turns`, `success_checks[]`, `max_retries`, `on_failure`, and a permissive `response_schema`. A Stop/finalizer hook executes shell postconditions with mandatory timeouts, injects failures for one bounded retry, and emits a typed terminal receipt. This is **very likely (80-90%)** to improve completion truthfulness because Goose's mechanism makes postconditions executable and the owner's own contract already requires receipt+postcondition; a 30-task A/B with seeded incomplete outputs would settle effect size.

Important divergence from Goose:

- preserve failure history instead of resetting the entire conversation to initial state; resetting is source behavior in [`retry.rs:99-161`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/retry.rs#L99-L161) and risks re-walking the same dead end;
- after two matching failures, invoke the owner's pivot rule instead of blind retry;
- shell checks run through the existing Windows-aware command rail, not Goose's `cmd /C` default ([`retry.rs:225-277`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/retry.rs#L225-L277));
- schemas must be minimal because StructuredOutput is already 22.9% errors with 294 schema mismatches (`/local_disk0/codexwork/bundle/inputs/corpus.json:103-110` plus pinned fingerprint count).

## 9. Multi-agent support

### 9.1 Goose capabilities

Goose's `summon` platform extension can delegate sequential or parallel internal subagents, use reusable recipes/custom agents, restrict extensions, override working directory/model/provider/temperature/max turns, run background tasks, and load results later. The docs state subagents are independent temporary instances and expose their tool calls live: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/subagents.mdx#L10-L72>.

Defaults are 25 turns, five-minute timeout, inherited extensions, and full return details. Subagents may use enabled extension tools but cannot spawn subagents, manage extensions, or manage schedules: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/context-engineering/subagents.mdx#L263-L359>.

The 2026 v1.41 changelog added background peek, explicit context, working-directory override, structured load metadata, and subagent instructions: <https://github.com/aaif-goose/goose/releases/tag/v1.41.0>.

### 9.2 Where the owner is better

- The owner already supports deeper and broader native fan-out: Codex config permits depth 8 and eight concurrent threads, while Claude experimental teams are enabled (`/local_disk0/codexwork/bundle/codex/config.toml:77-80,125-130`; `/local_disk0/codexwork/bundle/claude/settings.json:4-8`).

Goose's standard subagent result contract does not encode those epistemic gates.
- Goose deliberately blocks recursive subagent spawning. That is safer and simpler, but less capable than the owner's configured depth 8.

### 9.3 Where Goose is better

- Per-delegation extension scoping is first-class. This reduces context, permissions, and process cost.
- Model/provider/temperature/max-turn/working-directory overrides are part of the delegation mechanism rather than prose alone.
- Background tasks return structured metadata and can be peeked without waiting.

### 9.4 Proposal: enforce subagent capability envelopes — UNVERIFIED local resource premise

Extend each agent definition/launch contract with an enforceable `allowed_tools`, `max_turns`, `max_runtime`, `working_dir`, and `may_spawn` envelope using native agent configuration where available; default verification agents to read-only tools and `may_spawn=false`. This is **likely (55-80%)** to reduce resource pressure and accidental cross-scope mutation because Goose demonstrates the mechanism and the owner's live host has experienced system-wide resource exhaustion according to the earlier audit claim (`/local_disk0/codexwork/bundle/inputs/audit-findings/F10.md:3-15,38-48`). The local resource premise is UNVERIFIED on this node; a live Windows controlled fan-out recording of commit, process count, and tool exposure would settle it.

## 10. Verification and self-check mechanisms

### 10.1 Structured final output

Recipes can attach a JSON schema. Goose adds a required `recipe__final_output` tool; the model must call it, validation errors are returned with paths and expected format, and valid JSON becomes the terminal output ([`final_output_tool.rs:8-91`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/final_output_tool.rs#L8-L91), [`final_output_tool.rs:94-147`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/final_output_tool.rs#L94-L147)). This is a good feedback loop, but Goose panics if the schema is absent/empty/invalid at construction. The owner already experiences over-strict schema failures, so copy only the validation-feedback pattern, not the rigidity.

### 10.2 Executable postconditions and retry

Recipe retry runs ordered shell checks, requires exit 0, optionally runs `on_failure`, resets conversation to initial messages, and retries until `max_retries`: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/recipes/recipe-reference.md#L439-L518> and [`retry.rs:115-161`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/retry.rs#L115-L161). This is Goose's strongest verification primitive.

### 10.3 Goal and grind

`/goal` triggers one self-check before finishing; `/grind` forces continued effort. The first is weaker than an independent receipt, and the second is worse than the owner's two-strikes pivot. Preserve the owner's stronger policy.

### 10.4 Stop hooks

Stop hooks can veto completion and force another model turn, but are capped. This is useful for mechanical checks if the check result is based on real state, not prose scanning.

### 10.5 MAIN-ONLY / UNVERIFIED IN STABLE: `goose review`

The inspected main source and docs contain a first-class `goose review` command. The stable v1.41 changelog says the local review command was added, but the richer current implementation may postdate the release tag. Installing v1.43.0 and running `goose review --help` plus a two-file dry run would settle exact stable parity.

Current main behavior:

Docs: <https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/documentation/docs/guides/goose-cli-commands.md#L469-L510>. #### Proposal: portable `.agents/checks` review skill, with typed failure receipts — UNVERIFIED stable parity

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Adopt only the declarative check format and deterministic fan-out pattern as a shared skill/script: enumerate changed files, launch bounded native read-only reviewers, require each to return either `SUCCESS` with structured findings or `FAILED` with a reason, and refuse a clean verdict when any required reviewer lacks a receipt. ## 13. Anti-overfit gate

Every accepted proposal rides an existing bus:

- hook envelope/discriminator: existing shared hook dispatcher;
- postconditions/retry: existing Stop/finalizer hook plus skill/command manifest;
- task profiles: existing provider MCP configuration and native Tool Search;
- Stop cap: existing dispatcher state;
- capability envelopes: native subagent config or existing PreToolUse fallback;
- review checks: existing native fan-out plus a shared skill/script;
- oversized outputs: existing post-tool/artifact path.

None introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The one Goose component that is itself an orchestration runtime (`goose review` subprocess fan-out) is deliberately not copied; only its file/check manifest pattern is ported to native agents.
