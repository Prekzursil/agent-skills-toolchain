# F026 — Red team: `hook-scripts` → `exfiltrate-a-secret`

## Executive verdict

**The most plausible chain is a same-path compromise of an already registered Python hook (or of the local dispatch manifest/module it loads), followed by ambient-environment credential collection and a one-shot outbound HTTPS transmission on the next ordinary lifecycle event. The deployed harness does not stop that chain.**

This is **very likely (80-90%)** to succeed *if an attacker first obtains write influence over a registered hook byte-path or its canonical source and an outbound-capable process is permitted*, because five concrete properties compose:

1. the active Claude configuration launches Python hook commands automatically (`bundle/claude/settings.json:81-529`);
2. official Claude documentation says command hooks run with the system user's full permissions, inherit Claude Code's environment, and receive the hook event on stdin ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks));
3. this owner's prior equality-safe audit found 73 nonempty secret-named values in the audit process environment and many persistent user/machine variables (`bundle/inputs/audit-findings/F01.md:27-33`);
4. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is not set in the unpacked user settings environment (`bundle/claude/settings.json:4-20`), while current official documentation says setting it to `1` strips Anthropic and cloud-provider credentials from hooks, Bash, and stdio MCP subprocesses ([Claude Code environment variables](https://code.claude.com/docs/en/env-vars)); and
5. the existing credential controls either inspect model-visible tool calls rather than hook-process behavior, are disabled by default, or protect deployment-time consistency rather than execution-time script identity (`bundle/claude/hooks/deny-credential-reads/deny.py:73-108`; `bundle/agents/harness/modules.py:50-99,725-815`; `bundle/agents/harness/install.py:748-817`).

The confidence is not “almost certain” because this unit ran on a Linux job node against a read-only unpacked snapshot. **UNVERIFIED: effective Windows Defender Firewall/AppLocker/WDAC/EDR rules, the environment of a live Claude child, and current ACLs on `C:\Users\Prekzursil\.claude\hooks`; the settling experiment is an owner-controlled Windows canary test that gives a copied hook a fake environment token and an owned loopback/deny-by-default sink, records process environment *names only*, and proves whether network and file policy block the attempted canary transfer.** No such call was made here.

The checked snapshot itself does **not** establish present compromise. A bounded active-hook AST inventory found only local socket use and process spawning, not an obvious hard-coded remote sink. That clean-snapshot statement is **likely (55-80%)**, not stronger: the detector proved it could find known-present `socket.create_connection` in `heartbeat/heartbeat.py` and `re-autolaunch/autolaunch.py`, while an independent textual detector found the same calls plus the known `urlopen` in the currently unreferenced `mcp-liveness/liveness.py`; however, static scans cannot exclude obfuscation, runtime imports, compromised dependencies, or files missing from the bundle. The exact settling experiment is a clean-room Windows execution trace plus hash comparison against a reviewed source commit and dependency lock.

## Scope and safety boundary

This is analysis only. I did not read a secret value, identify a recipient controlled by an attacker, create an exfiltration payload, make an outbound request, alter a hook, weaken a permission, install anything, or touch the Windows host.

The only write is this artifact. All subject inspection was against `/local_disk0/codexwork/bundle`, which is the remote override's read-only unpacked subject. The Windows paths in the brief do not exist on this node. Consequently, claims about *deployed files represented by the bundle* cite the corresponding bundle path; claims about *live process state, ACLs, firewall, key validity, or currently selected plugin versions* remain UNVERIFIED inline.

The corpus `hooks` telemetry is deliberately not used. The pinned brief says that detector is broken and therefore supplies no evidence of firing or non-firing. The known-defects input independently confirms that zero hook records in transcripts is an unverified telemetry symptom rather than proof that hooks did not run (`bundle/inputs/INPUT-known-harness-defects.md:133-147`).

## What the attack surface actually is

The brief describes “164 python hooks running on every tool call.” The bundle contains exactly **164 `*.py` files** under `bundle/claude/hooks`, but it would be inaccurate to say all 164 execute on every call.

A settings-plus-local-manifest resolver found **36 currently referenced script paths**: 34 Python files and two PowerShell worktree scripts. All 36 exist in the bundle. A specific tool event runs only matching direct hooks plus matching checks in `_dispatch/manifest.json`:

- the shared dispatcher runs before selected shell/write/task/web/MCP tools (`bundle/claude/settings.json:139-149`);
- direct Bash guards and rewrites are separately registered (`bundle/claude/settings.json:151-183`);
- the credential reader is registered for `Read|Edit|MultiEdit|Grep|Bash|PowerShell` (`bundle/claude/settings.json:239-249`);
- the local dispatcher runs selected pre-tool checks (`bundle/claude/settings.json:250-259`), every post-tool event (`bundle/claude/settings.json:344-353`), and Stop/SessionStart checks (`bundle/claude/settings.json:94-104,495-503`);
- its manifest currently lists 6 SessionStart, 7 Stop, 3 PostToolUse, and 4 PreToolUse checks (`bundle/claude/hooks/_dispatch/manifest.json:5-228`).

This correction matters defensively: the attack does not need to poison 164 files. It needs one high-frequency registered path, one dispatcher, or one manifest-selected module.

Two mechanically independent signals establish that hooks are genuinely present rather than a detector artifact:

1. **Configuration signal:** `settings.json` names concrete absolute commands such as the shared dispatcher and standalone credential guard (`bundle/claude/settings.json:139-149,239-249,310-353`).
2. **Filesystem/loader signal:** those files exist, and `_dispatch/dispatch.py` reads its manifest, resolves `hooks_root + script`, and executes module top-level code with `exec_module` (`bundle/claude/hooks/_dispatch/dispatch.py:147-164,226-277`).

The known-positive controls for the inventory were the explicitly configured `deny-credential-reads/deny.py` and the manifest-listed `heartbeat/heartbeat.py`; both were found. Therefore, a resolver returning 36 is evidence about active references in the provided user configuration, not a repeat of the broken transcript hook detector.

## Attacker model and precondition

The attacker does not begin with arbitrary host code execution—that would make the hook surface irrelevant. The selected precondition is narrower: attacker-controlled bytes reach a path Claude already executes as a hook. There are several candidate routes, whose live feasibility remains UNVERIFIED pending the ACL, plugin-provenance, and disposable-deploy experiments named below:

- a malicious or compromised enabled plugin ships a lifecycle hook;
- a poisoned skill/instruction persuades an autonomous agent to edit canonical hook source and run the normal deployer;
- a same-user/sandbox process replaces a user-owned same-path hook;
- `_dispatch/manifest.json` is changed to point at another Python file.

The last route is concrete in this bundle: `hooks_root` and each `script` are manifest data (`bundle/claude/hooks/_dispatch/manifest.json:4,10-18`); the dispatcher joins them without a containment or byte-digest check and executes the resolved module before starting its timeout-governed worker (`bundle/claude/hooks/_dispatch/dispatch.py:147-164,240-264`). Earlier audit F06 made the same source-flow claim and separately found all checked live artifacts clean at audit time (`bundle/inputs/audit-findings/F06.md:34-48,82-88`). I verified the source flow here rather than accepting the audit claim as fact.

**UNVERIFIED: the live Windows ACL permits a Claude-driven or sandbox-driven write to the hook tree. The settling experiment is `Get-Acl` on the hook root and one registered file, expanded to effective rights for the owner, `CodexSandboxUsers`, `CodexSandboxOnline`, and `CodexSandboxOffline`, followed by a harmless create/rename probe in a disposable ACL-equivalent directory—not the live hook tree.** The prior F01 audit found broad modify rights on several adjacent Claude/Codex data and config surfaces (`bundle/inputs/audit-findings/F01.md:59-73`), but that is not a substitute for a hook-tree ACL measurement.

The chain below therefore begins at the first hook-byte compromise. It does not assert which initial route has occurred.

## Concrete attack chain

### Step 1 — Land below the registered command string

The attacker preserves the command in `settings.json` and changes the bytes at a referenced Python path, or changes one local-dispatch manifest entry while leaving the configured dispatcher command unchanged.

This is the least noisy placement because configuration-level trust continues to see the same handler command. It also avoids having to add a new visible hook group. The existing deploy receipt hashes files only at deploy time and writes their hashes after parity succeeds (`bundle/agents/harness/install.py:748-817`). Nothing in `settings.json` invokes a receipt checker before each hook execution (`bundle/claude/settings.json:81-529`).

The local dispatcher magnifies the placement: imported module top-level code runs in the dispatcher process during `_load_module`, before the module's `main()` and before the worker thread's join timeout (`bundle/claude/hooks/_dispatch/dispatch.py:154-164,242-277`). A malicious top-level side effect therefore does not need to emit hook JSON and is not constrained by the hook's intended inject-only semantics.

### Step 2 — Wait for a normal trigger

No suspicious model tool call is required after the bytes land. A new session triggers the shared and local SessionStart dispatchers (`bundle/claude/settings.json:82-115`); ordinary selected tool calls trigger PreToolUse; every completed tool triggers the shared PostToolUse dispatcher and the local post-tool dispatcher (`bundle/claude/settings.json:310-353`).

A PostToolUse or SessionStart placement is **very likely (80-90%)** to be preferable to an attacker because the cited settings prove it runs after benign activity and does not have to pass a model-visible approval decision. This is a threat-analysis observation, not an instruction to implement one.

### Step 3 — Read an ambient credential inside the hook process

The malicious hook enumerates inherited environment *inside its own process* and selects one provider token already present there. It does not ask Claude to call `Read`, `Bash`, `PowerShell`, or an MCP tool.

This is concrete for this owner: the earlier redaction-safe Windows audit counted 73 process-scope nonempty secret-named variables and reported representative names present at user, machine, and process scopes (`bundle/inputs/audit-findings/F01.md:27-33`). Official Claude documentation states that hook handlers run with Claude Code's environment and that a hook process inherits the parent environment ([hooks reference](https://code.claude.com/docs/en/hooks)).

**UNVERIFIED: a chosen provider credential is still valid and is present in the effective environment of a currently running Claude hook. The settling experiment is a sanitized hook trace that emits only a Boolean for a fake canary variable and a count of names matching a secret-name classifier—never values—followed by provider-side validity checks performed by the owner for already planned rotation.** Equality with a current environment value in F01 proves exposure and duplication, not provider validity (`bundle/inputs/audit-findings/F01.md:83-89`).

### Step 4 — Send one outbound request from below the tool bus

The malicious hook makes a direct outbound HTTPS request containing the selected credential, or launches a child capable of doing so. No operational endpoint, payload format, or command is included here.

Why this route is **likely (55-80%)** given the following local and vendor evidence:

- official documentation says hooks run with full user permissions ([hooks reference](https://code.claude.com/docs/en/hooks));
- the unpacked active hooks already demonstrate that this process class can import sockets and spawn child processes: `heartbeat` opens a loopback socket (`bundle/claude/hooks/heartbeat/heartbeat.py:118-133`); `re-autolaunch` opens sockets and spawns a child (`bundle/claude/hooks/re-autolaunch/autolaunch.py:135-153,298-327`); and monitor hooks spawn detached processes (`bundle/claude/hooks/monitor-autolaunch/check.py:70-78`, `bundle/claude/hooks/codex-monitor-autolaunch/check.py:57-68`);
- `memory-spool/replay.py` explicitly clones `os.environ` into a child process (`bundle/claude/hooks/memory-spool/replay.py:115-130`), illustrating that ambient authority can propagate to descendants.

**UNVERIFIED: this Windows host permits outbound Internet access from the exact Python interpreter and its descendants. The settling experiment is a fake canary sent only to an owner-controlled local listener and a separate connection-only probe to an owner-controlled public endpoint, with zero secret data, while collecting Windows Filtering Platform/AppLocker/EDR decisions.** Prior audit F06 explicitly left those controls unverified (`bundle/inputs/audit-findings/F06.md:82-88`).

### Step 5 — Return a normal hook result and persist

The malicious path can then return no output or an ordinary allow/inject result. Many harness components deliberately fail open:

- the local dispatcher catches `BaseException` at import, worker, and top-level boundaries and returns success (`bundle/claude/hooks/_dispatch/dispatch.py:182-190,242-252,322-329`);
- the standalone credential guard catches any exception and exits zero (`bundle/claude/hooks/deny-credential-reads/deny.py:104-108`);
- the shared dispatcher catches module errors and can still produce an allow result, as summarized and evidenced in audit F02 (`bundle/inputs/audit-findings/F02.md:63-69`).

Fail-open behavior is good for advisory reliability but supplies no evidence that an already-running hook was benign. The attacker needs only one successful outbound side effect before the normal return.

### Step 6 — Recur at high frequency

The attacker can repeat on each matching event or self-throttle to one send per session. Repetition is not required to meet the goal. It merely increases opportunity while blending into a hook plane already invoked on SessionStart, PreToolUse, PostToolUse, and Stop (`bundle/claude/settings.json:81-529`).

## Does an existing control stop this chain?

### Control 1 — Declarative `permissions.deny`: **No**

The declarative denies cover Claude's `Read` tool for `.env`, PEM, and credential-shaped filenames (`bundle/claude/settings.json:64-69`). The malicious code reads its own inherited process environment. It never submits a `Read` tool call, so the deny rules are outside the path.

The broad `defaultMode: bypassPermissions` and drive grants make the overall posture worse (`bundle/claude/settings.json:26-75`), but the decisive point is architectural: tool permission rules mediate tool calls, not code already executing as a trusted hook.

### Control 2 — Standalone credential-read guard: **Present but does not stop it**

The guard is wired for selected model tools (`bundle/claude/settings.json:239-249`), but `_guard_enabled()` is opt-in and returns false unless `HARNESS_CREDENTIAL_GUARD` is explicitly truthy (`bundle/claude/hooks/deny-credential-reads/deny.py:73-89`). When enabled, it scans `tool_name` and `tool_input` (`bundle/claude/hooks/deny-credential-reads/deny.py:86-101`), not the Python hook's own environment reads or network calls.

I verified the default-off branch with a synthetic, non-secret input. With `HARNESS_CREDENTIAL_GUARD` removed, the script exited 0 and emitted no deny. With `HARNESS_CREDENTIAL_GUARD=1`, the same synthetic credential-filename read produced `hookSpecificOutput.permissionDecision="deny"` and exited 0. This execution signal is independent of the static source signal and proves the detector can recognize a known-positive input when enabled.

The bundled shared-harness tests independently encode four default allows and four enabled blocks for credential-read commands (`bundle/agents/harness/tests/test_modules.py:266-300`), but **UNVERIFIED: those tests pass in this artifact environment; the settling experiment is to run the named cases in the repository's pinned Python environment.** This job node's current Python reported `No module named pytest`, so I do not count the tests as executed evidence.

Even if this flag were enabled, the attack still bypasses it because no model tool input contains the read.

### Control 3 — Shared `SecretGuardModule`: **Present but does not stop it**

Both the credential-read and secret-literal hard blocks are opt-in/off by default (`bundle/agents/harness/modules.py:50-99`). The run path inspects normalized hook-event `tool.input`, conditionally blocks a literal or credential-looking input, and otherwise allows (`bundle/agents/harness/modules.py:725-815`). It does not sandbox sibling hook scripts, scrub their environment, or proxy their network.

The source tests intentionally assert literal-secret inputs are allowed when unset and blocked when enabled (`bundle/agents/harness/tests/test_modules.py:303-339`). Again, those are source assertions, not executed test results on this node.

### Control 4 — Redaction: **Useful for persistence, irrelevant to direct egress**

`redact_text()` replaces recognized patterns before selected text is persisted or reinjected (`bundle/agents/harness/redaction.py:40-56`). The malicious hook does not pass the value through `redact_text`; it reads and transmits below the ledger path. F01 also found a current token shape missed by the redactor in a durable goal (`bundle/inputs/audit-findings/F01.md:43-49`), so redaction must not be promoted into an execution-boundary claim.

### Control 5 — Config drift sentinel: **Does not cover hook-script bytes**

`_config_drift()` compares only `settings.json` sections `hooks`, `mcpServers`, and `disabledMcpServers` against an installed snapshot (`bundle/agents/harness/modules.py:864-909`). Same-path replacement leaves the `hooks` JSON unchanged. Moreover, the provided `installed.json` has no `settings` key (`bundle/agents/harness/installed.json:1-48`), which drives `_config_drift()` through its fail-open `baseline` check (`bundle/agents/harness/modules.py:878-889`).

Two independent signals support that “does not cover bytes” conclusion: the compared data fields are configuration objects, while the deployment receipt's per-file hashes live in a different `files` map (`bundle/agents/harness/installed.json:11-46`) that `_config_drift()` never reads.

### Control 6 — CAS-lite deploy receipt: **Strong at deployment, not consulted at execution**

The deployer hashes candidate and live files, stages and atomically replaces them, verifies post-write parity, restores on mismatch, and writes a receipt (`bundle/agents/harness/install.py:516-534,748-817`). That is a meaningful existing control against partial/concurrent deployment.

It does not authenticate bytes immediately before `settings.json` or `_dispatch` executes them. The active settings commands invoke Python files directly (`bundle/claude/settings.json:81-529`), and `_dispatch` calls `exec_module` without reading `installed.json` (`bundle/claude/hooks/_dispatch/dispatch.py:147-164`). A post-deploy same-path edit is therefore outside the receipt's enforcement window.

### Control 7 — Current scripts appear non-malicious in a bounded scan: **Not a preventive control**

The active-reference AST scan found socket use only in `heartbeat` and `re-autolaunch`, plus several process-spawn calls; the socket targets shown in source are loopback (`bundle/claude/hooks/heartbeat/heartbeat.py:128-133`; `bundle/claude/hooks/re-autolaunch/autolaunch.py:144-153`). An independent text scan found the known local HTTP targets in the broader hook tree. This reduces evidence of *present compromise in the provided files* but does nothing to prevent later replacement.

## Minimal mitigation

### P0 — Enable native subprocess credential scrubbing now

**NATIVE (Claude Code already does this; we just enable it)**

Set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` in the Claude launch environment or managed/user settings environment, restart Claude Code, and verify a hook sees a fake canary variable but does not see representative Anthropic/cloud-provider credential *names or values*. Current official documentation explicitly says this native switch strips Anthropic and cloud-provider credentials from Bash, hooks, and stdio MCP server subprocess environments ([Claude Code environment variables](https://code.claude.com/docs/en/env-vars)). The current bundled `settings.json` environment does not include it (`bundle/claude/settings.json:4-20`).

This is the minimum change that breaks the **exact ambient-environment chain above**, and it rides the native hook bus without a new runtime. It is **very likely (80-90%)** to prevent the chosen hook from obtaining the provider tokens Claude classifies for scrubbing, because the official documentation names hooks explicitly and F01 establishes that ambient process inheritance is the chosen source. It is not “almost certain” until a Windows canary confirms which credential categories this Claude version scrubs.

**UNVERIFIED: the native scrub includes every one of this owner's 73 secret-named variables, including non-cloud application tokens. The settling experiment is a name-only before/after inventory inside a disposable hook process using synthetic canaries in each category.** Therefore this control must not be described as a complete secret sandbox.

Expected compatibility cost is **likely (55-80%)** to be low for the 36 active references because their visible source primarily uses local paths, state files, loopback sockets, and child launchers; evidence is the active AST/string inventory described above. Some child tools may currently depend on ambient provider variables, so the canary rollout must record hook failures and explicitly pass only required non-secret variables. That compatibility claim is forward-looking and cannot be stronger without a Windows replay.

### P1 — Close same-path replacement with receipt verification at the loader boundary

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing deploy receipt and dispatcher—not a second orchestrator—so the loader resolves every selected script under the canonical hook root, rejects traversal/absolute redirection, and verifies the script SHA-256 against `hooks/installed.json` immediately before `exec_module`. Direct settings hooks should be routed through the same tiny verified launcher or receive equivalent byte checks. On mismatch, this *security* predicate must fail closed before import and emit a short recovery instruction; advisory checks may remain fail open.

This mitigation is **likely (55-80%)** to stop accidental or lower-privilege same-path replacement, based on the already implemented SHA-256/CAS deploy machinery (`bundle/agents/harness/install.py:571-598,748-817`) and the single loader seam (`bundle/claude/hooks/_dispatch/dispatch.py:154-164`). Its confidence is capped because a verifier and receipt writable by the same attacker can be changed together.

**UNVERIFIED: the hook tree and receipt can be made non-writable to the model/sandbox identities while remaining maintainable by the owner. The settling experiment is an effective-rights ACL matrix plus a disposable install/update/read/run test under the exact Claude and Codex execution identities.** Without that independent trust boundary, byte verification is tamper evidence, not strong containment.

### P2 — If admin-managed policy is available, move hook trust there

**CONFIG (settings/JSON only)** for the policy switch itself; migrating the curated scripts to an administrator-owned path is separate operational work and is not mislabeled as JSON-only.

Set managed `allowManagedHooksOnly: true`, define only reviewed managed hooks, and force-enable only pinned reviewed plugins. Official settings documentation says this blocks user, project, and ordinary plugin hooks while retaining managed hooks and managed force-enabled plugin hooks ([Claude Code settings](https://code.claude.com/docs/en/configuration)).

This is **very likely (80-90%)** to remove the untrusted project/plugin registration routes because the native setting explicitly names them. It does not protect a managed command that still points to a user-writable script; the reviewed command targets must live under an admin-owned path or use the verified launcher described above.

This is not the immediate minimum for the current personal 36-reference setup: enabling it before migration would block the user's own global hook layer. It is the clean durable trust boundary if managed settings are available.

### P3 — UNVERIFIED: native network sandbox as defense in depth

**NATIVE (Claude Code already does this; we just enable it)**

Claude's current admin documentation says its OS-level sandbox plus `sandbox.network.allowedDomains` closes shell-level `curl`/`wget` bypasses ([Claude Code admin setup](https://code.claude.com/docs/en/admin-setup)). **UNVERIFIED: command-hook processes on Windows are inside that same network sandbox; the settling experiment is a disposable hook that makes a connection-only request to one allowed and one denied owner-controlled domain and inspects Windows Filtering Platform decisions.** Do not claim hook egress is blocked, or make this the primary mitigation, until that experiment passes.

## Anti-overfit gate

All counted recommendations ride existing native settings, the existing dispatcher, or its existing SHA-256 deploy receipt. None introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

The immediate fix is one native environment switch. The small integrity extension reuses the loader and receipt already paid for. The managed-policy option replaces soft user/plugin trust with Claude's native policy plane. This is consistent with the deliberate minimal architecture constraint; a new daemon would add a second privileged process without removing the ambient-authority problem.

## Verification plan and acceptance criteria

No live mitigation should be declared done until all of the following pass with fake canaries only:

1. **Known-positive detector control:** a disposable hook sees an ordinary fake variable and a deliberately allowed non-secret variable, proving the environment detector works.
2. **Scrub negative:** the same hook does not see fake canaries named for each documented scrub category after `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`; record names/Booleans only.
3. **Execution identity:** record executable path, parent/child identity, and permission mode, but no environment values.
4. **Integrity positive:** an unchanged reviewed module hash loads and produces its expected benign hook output.
5. **Integrity negative:** one-byte modification in a disposable copied hook tree is denied before module import; a top-level marker file must remain absent, proving no code ran.
6. **Traversal negative:** absolute and parent-relative manifest paths are denied before read/import.
7. **Receipt trust:** the Claude/Codex execution identities can read but not modify the protected receipt/verifier in the disposable ACL-equivalent tree.
8. **Network policy:** an allowed local endpoint connects; a denied public canary endpoint does not; inspect WFP/EDR logs as the independent signal.
9. **Compatibility replay:** replay sanitized hook envelopes for SessionStart, PreToolUse, PostToolUse, and Stop; all required local hooks still return within their configured deadlines (`bundle/claude/settings.json:82-529`).
10. **No real secret:** the fixture contains only generated canaries, and the owned receiver asserts it never received a value from the machine's real secret-name inventory.

Completion confidence after those checks would be **almost certain (90-99%)** for the tested Claude version and hook set, because loader-before-import state, OS policy state, and receiver state are mechanically independent. It would still not prove safety after future hook, plugin, interpreter, or Claude updates; pin the test to version/hash and rerun on those changes.

## Alternatives considered and rejected

### Merely enable `HARNESS_CREDENTIAL_GUARD` / `HARNESS_SECRET_GUARD`

**CONFIG (settings/JSON only)**

Useful for model-originated tool calls, but rejected as the primary fix for this unit. Both inspect `tool_input`; malicious hook code operates below that boundary (`bundle/agents/harness/modules.py:725-815`). They also were disabled because of measured false positives (`bundle/agents/harness/modules.py:50-99`; `bundle/inputs/INPUT-known-harness-defects.md:9-107`). Enabling them does not stop the constructed chain.

### Add another regex looking for network calls in hook source

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Rejected. A lexical scanner is trivially bypassed by imports, helpers, subprocesses, or encoded destinations and repeats the harness's demonstrated “use versus mention” defect (`bundle/inputs/INPUT-known-harness-defects.md:9-107`). Byte identity plus environment/network confinement addresses behavior boundaries rather than syntax.

### Rely on the deployer's clean parity result

No new proposal. Rejected as a runtime control because parity is checked during deployment, while settings and the local dispatcher later execute paths without rechecking the receipt (`bundle/agents/harness/install.py:748-817`; `bundle/claude/hooks/_dispatch/dispatch.py:147-164`).

### Block all Python networking globally

This would require OS policy and covers legitimate MCP/research Python processes as well as hooks, making it overbroad relative to native subprocess scrubbing and a verified hook loader. It also fails if a malicious Python hook launches a different allowed executable. No recommendation is made.

### Build a hook-security daemon or observability service

Explicitly rejected by the anti-overfit gate. A daemon would be another privileged runtime and would still need an OS trust boundary. Existing native settings, managed policy, the current dispatcher, and the receipt are sufficient buses.

## Gaps

- **UNVERIFIED live state:** The remote bundle cannot establish Windows ACLs, EDR/AppLocker/WDAC rules, WFP outbound policy, live hook environment, active plugin cache selection, credential validity, or runtime hook inventory. The specific experiments are named inline above.
- **UNVERIFIED plugin route:** The bundle's `settings.json` shows several enabled plugins (`bundle/claude/settings.json:538-637`), and audit F06 claims enabled executable plugin hooks lack usable active-version provenance (`bundle/inputs/audit-findings/F06.md:66-72`), but the plugin cache is absent from this unpacked subject. Repairing/exporting the plugin registry without updating it, then hashing the selected hook files, would settle this route.
- **UNVERIFIED pytest pass:** Source tests encode the expected security-toggle behavior, but pytest is not installed in this job environment. Run the named tests in the pinned repository environment.
- **No outbound exploit:** By design, no exfiltration or remote canary was executed. The owned-canary integration test described above is the only acceptable end-to-end settlement.
- **Static-clean limitation:** The active AST/text scan is bounded and does not analyze transitive Python imports, PowerShell bodies, dynamically generated code, installed packages, or interpreter startup hooks. A clean-room process trace plus reviewed dependency hashes would settle those layers.

## Final answer to the unit question

An existing control does **not** stop the concrete chain. The configured file and literal guards are either default-off or inspect model tool inputs; declarative denies also mediate model tools; redaction protects selected persistence; config drift hashes hook declarations rather than script bytes; and the CAS receipt is not consulted at execution. A malicious registered hook therefore runs below every one of those checks.

The minimal immediate mitigation is **NATIVE (Claude Code already does this; we just enable it): `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`**, verified with fake canaries. That breaks the exact inherited-provider-token chain with the smallest compatibility and architecture cost. The minimal durable follow-up is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): enforce receipt-backed containment and byte verification immediately before import, anchored in an ACL-protected or managed trust root**. Anything less leaves same-path replacement able to execute with full user authority; anything substantially larger fails the anti-overfit gate unless the named Windows canary experiments disprove the native/small options.
