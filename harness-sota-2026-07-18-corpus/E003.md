# E003 — Ecosystem survey: MCP gateways and aggregators

**Unit:** E003  
**Research date:** 2026-07-19 UTC  
**Scope:** MCP gateways, aggregators, transport proxies, and adjacent managed portals; suitability for this owner's Claude Code/Codex harness.  
**Write policy:** The unpacked subject at `/local_disk0/codexwork/bundle` was read-only. This artifact is the only file written.

## Executive decision

Do **not** replace the harness's MCP control plane with a general-purpose gateway now. The evidence says the first problem is control-plane convergence, not lack of a gateway: a coherent 24-server daily projection already exists, but it is not deployed; two legacy tasks still rewrite the live user fleet; the repository registry and staged registry disagree; and the existing drift sentinel exits before comparing anything. Those facts are recorded in `/local_disk0/codexwork/bundle/inputs/audit-findings/A25.md:9-31,132-170,213-219`. A gateway imported before those are reconciled is **almost certain (90-99%)** to become a fifth source of truth, because four mutually inconsistent configuration/control surfaces are already evidenced there.

The best ecosystem candidate **for a bounded experiment here** is **Docker MCP Gateway**, specifically a small profile containing two or three stateless, presently-stdio servers. It uniquely combines a single native MCP attachment with per-server container isolation, credential handling, catalogs, profiles, and lifecycle management. This assessment is **very likely (80-90%)**, based on Docker's official architecture and CLI documentation, the active MIT repository, and the owner's existing use of Docker-backed MCP entries; it is still **UNVERIFIED for this Windows host** until experiment `DG-P1` measures Docker Desktop availability, incremental private commit, cold/warm startup, handshake success, tool/schema fidelity, and Claude reconnect behavior. Do not enable Docker Dynamic MCP or Code Mode in that pilot: those reproduce the already-rejected search/describe/execute meta-tool pattern.

The best lightweight non-container alternative is **1MCP**, but only its MCP-native `serve` plus `proxy`/streamable-HTTP path. Its new CLI-mode `instructions -> inspect -> run` surface is a meta-tool protocol, not a reason to replace native MCP namespaces. A 1MCP pilot is **likely (55-80%)** to reduce duplicated client configuration and initial tool-schema exposure, based on its documented presets, filters, lazy loading, template servers, and 2026-07-17 release; benefit here is **UNVERIFIED** until experiment `1MCP-P1` imports a sanitized projection and compares token/schema surface, name stability, OAuth, failure isolation, and RAM with direct native servers.

Everything heavier—IBM ContextForge, agentgateway, Microsoft MCP Gateway, TrueFoundry, Kong, Cloudflare portals, and the full MetaMCP stack—either targets a team/cluster problem this single-owner Windows harness has not demonstrated, or bundles a rejected component such as a second agent/LLM routing runtime, guardrail framework, observability platform, database-backed control plane, or Kubernetes lifecycle layer. They may be high-quality products; they are poor fits **here** under the anti-overfit gate.

### Quality rubric

“High quality” below means: (a) live upstream maintenance; (b) explicit licence; (c) MCP-native client-facing transport; (d) server/tool selection rather than only blind forwarding; (e) credible authentication or secret story; (f) documented deployment and failure model; and (g) an architecture proportional to this owner's single-machine problem. **NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it)**

## Risks and alternatives considered

### “One endpoint” is not automatically more reliable

An aggregator reduces client configuration edges but concentrates failure. It is **likely (55-80%)** that a single gateway-process crash, bad catalog parse, credential-store failure, or incompatible protocol translation can hide every upstream behind that gateway; this follows from the shared endpoint/process architecture documented by Docker, 1MCP and MCPJungle. This owner already has a concrete example of a stdio MCP rail that did not automatically reconnect (`/local_disk0/codexwork/bundle/inputs/audit-findings/B11.md:8-26`). Therefore a gateway recommendation without crash/reconnect testing is evidence-free.

### Tool renaming can invalidate skills and telemetry

MCPJungle uses `server__tool` naming; MetaMCP and 1MCP can filter/rename or front tools through generic execution. The current harness has skills and hooks matching server/tool names, and the corpus is aggregated by those identities. Renaming is **very likely (80-90%)** to require mapping changes, based on those documented gateway naming layers and local name-based matchers. `DG-P1`/`1MCP-P1` must emit a before/after name map.

### Gateway retries can make non-idempotent writes worse

Enterprise gateways advertise retries/circuit breakers. Automatic retry of a tool call is safe only when its side-effect/idempotency contract is known. MCP tool annotations can help but are provider-declared, not proof. It is **likely (55-80%)** that blanket retries would duplicate at least some writes in a 65-server heterogeneous fleet; evidence is the mix of GitHub, Linear, Notion, Figma, cloud and RE mutation tools in `A25.md:35-128`. Do not enable tool-call retries globally.

### Security value is real but must be scoped

Container isolation and centralized secrets can reduce direct host exposure. A gateway also becomes a high-value credential and tool-confusion boundary. Docker's signed catalog and restricted containers are the most relevant local security mechanisms; enterprise DLP/RBAC does not address the measured local failures. A security improvement from Docker is **likely (55-80%)**, supported by its documented isolation/signature features, but **UNVERIFIED** against custom local servers until `DG-P1` inspects mounts, networks, privileges, secret exposure and image digests.

### Native configuration remains the smallest architecture

Anthropic managed MCP and Codex's enabled/disabled server configuration already provide native inventory and tiers; the owner also has an MCP liveness hook. A small renderer plus validated projections is proportional to the problem. This is consistent with the anti-overfit reminder that simple loops age better as models improve: gateways should earn adoption through measured process/security value, not architectural neatness.

## Gaps and experiments not performed

- **UNVERIFIED Windows execution:** E003 ran on Linux and did not have the live Windows paths. `DG-P1`, `1MCP-P1`, and `MJ-P1` on the owner host settle installability, PowerShell quoting, `.cmd` resolution, command-line length, Docker mode and resource cost.
- **UNVERIFIED current OAuth matrices:** documentation changes quickly. Each pilot must test the owner's actual OAuth remote(s), token refresh after restart, and multi-client token separation. Reading a feature list does not settle interoperability.
- **UNVERIFIED protocol fidelity:** no candidate was run through the official Inspector/conformance suite here. Run initialize, capability negotiation, cancellation, progress, elicitation if used, structured output, resource/prompt operations, tool-list notifications and error mapping.
- **UNVERIFIED production error reduction:** repository activity and architecture do not prove improvement on this corpus. A shadow comparison with at least 200 representative calls, forced failures and 20 cold starts settles it.
- **UNVERIFIED commercial terms:** Cloudflare uses service terms; Kong explicitly requires AI Gateway Enterprise; TrueFoundry's exact price, data retention, subprocessors and licence rights require written vendor terms. Do not infer them from marketing docs.
- The unpacked bundle did not include the live Windows `.mcp.json` or `.claude.json`; conclusions about their counts use the cited A25 audit claim plus pinned brief, not a fresh E003 parse. A sanitized exported projection is **almost certain (90-99%)** to permit independent structural verification because both files are JSON and the prior audit describes exact name/definition comparisons.
- GitHub metrics are a point-in-time signal and can be gamed. They were used only alongside licences, releases, code push dates and primary documentation.
- The survey is broad, not a proof that no other gateway exists. The known-present control found Docker, IBM, Microsoft, 1MCP, MCPJungle and MetaMCP; absence claims were deliberately avoided for unsearched projects.

## Bottom line

The frontier has split into three product shapes: lightweight aggregation/lazy discovery (1MCP, MCPJungle), local isolated lifecycle/catalogs (Docker), and enterprise agent/API governance platforms (ContextForge, agentgateway, Microsoft, Cloudflare, Kong, TrueFoundry). This owner needs the second shape only if a small measured pilot beats a reconciled native baseline. The third shape is impressive but violates the explicit architecture gate; the first risks recreating a meta-tool already rejected here.

The ambitious answer is therefore not “install the biggest gateway.” It is to make the canonical fleet portable enough to render both native and gateway profiles, then force Docker and 1MCP to beat native configuration on measured memory, isolation, schema fidelity and failures. That keeps full replacement genuinely available while refusing a replacement with no evidence.
