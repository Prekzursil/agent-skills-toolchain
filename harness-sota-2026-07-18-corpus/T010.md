# T010 — Competitive teardown: Devin / Cognition

**Research date:** 2026-07-19 (UTC)  
**Unit scope:** Devin Cloud, Devin CLI, and the Devin-facing parts of Devin Desktop. This is a competitive teardown, not an implementation. The harness subject was read-only; the only write is this artifact.  
**Owner constraint:** Windows, PowerShell 7 + Git Bash. That matters because Devin CLI's strongest local isolation feature explicitly does not support Windows.

## Executive verdict

Devin is no longer just a single cloud coding agent. Cognition now exposes a three-layer system:

1. **Cloud Devin:** a long-running agent session whose “brain” is a stateless Cognition-cloud service and whose shell/browser/editor run in a per-session Linux Devbox. It can plan, edit, run commands, browse, test, open PRs, sleep/wake, and spawn managed child Devin sessions on separate VMs. [Enterprise deployment architecture](https://docs.devin.ai/enterprise/deployment/overview), [first session](https://docs.devin.ai/get-started/first-run).
2. **Devin platform:** indexed repositories, Knowledge, Playbooks, Skills, snapshots/blueprints, secrets, schedules, integrations, session APIs, Session Insights, Devin Review, and an authenticated Devin MCP that exposes the platform to other agents. [Knowledge](https://docs.devin.ai/product-guides/knowledge), [Devin MCP](https://docs.devin.ai/work-with-devin/devin-mcp), [environment configuration](https://docs.devin.ai/onboard-devin/environment).
3. **Devin CLI/Desktop:** a local harness with AGENTS/rules, Agent Skills, plugins, lifecycle hooks, fine-grained allow/ask/deny permissions, MCP, OS sandboxing, and foreground/background subagents. [CLI docs index](https://docs.devin.ai/llms.txt), [rules](https://docs.devin.ai/cli/extensibility/rules), [permissions](https://docs.devin.ai/cli/reference/permissions), [subagents](https://docs.devin.ai/cli/subagents).

The important conclusion is not “replace our harness with Devin.” Our harness already has a wider and in places more rigorous local control surface: multi-agent depth eight and eight concurrent threads (`/local_disk0/codexwork/bundle/codex/config.toml:77-80,125-130`), pre/post-compaction and subagent lifecycle hooks (`config.toml:409-440`), a shared semantic memory plus objective event ledger (`/local_disk0/codexwork/bundle/codex/AGENTS.md:20-26,62-85`), and explicit completion/evidence gates. Devin's best advantage is **product coherence**: clean sessions from reproducible snapshots, scoped secrets, a searchable event history, post-session analysis, one-click visual QA evidence, and isolated cloud child agents are integrated rather than assembled.

The radical replacement option is **not recommended**. It is **very likely (80-90%)** to lose owner-specific capabilities while adding a second orchestration runtime: evidence is the subject's 355-ish installed skills, 93 MCP servers touched, cross-tool memory, custom hooks, and Windows/reverse-engineering/media workflows in the supplied corpus and bundle, versus Devin Cloud's Linux Devbox and closed cloud brain. Full replacement also fails the anti-overfit gate because it introduces the explicitly rejected second orchestration runtime. A bounded evaluation against real owner tasks could settle the remaining product-quality uncertainty, but it would not remove the architectural mismatch.

The highest-value ports are:

* session evidence/insights built on the existing ledger and transcripts;
* safer configured permission defaults and per-skill capability scopes;
* short, annotated E2E proof recordings for UI work;
* scoped secret attachment using the OS credential store;
* MCP default-disable/quarantine controls that prevent a dead server from remaining selectable.

These ride existing buses and do not require a vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, guardrail framework, or second orchestration runtime.

## Evidence discipline and limitations

### What was directly verified

* Primary Cognition documentation and release notes were read at the URLs cited inline. The documentation index explicitly enumerates current pages for hooks, sandbox, subagents, rules, skills, MCP, RBAC, Session Insights, Review, Knowledge, and releases: [docs index](https://docs.devin.ai/llms.txt).
* The live 2026 changelog was checked directly through July 15, 2026, rather than relying on the search engine's older May crawl. July additions relevant to this teardown include skill-based session filtering, Git-backed blueprints, per-domain network access requests, MCP read-only secure mode, enterprise Skills Analytics, MCP usage by organization/session, and stale MCP-install warnings. [2026 release notes](https://docs.devin.ai/release-notes/2026).
* The unpacked subject was inspected at `/local_disk0/codexwork/bundle`. The configured Claude permission mode is `bypassPermissions`, with broad drives `C:` and `D:` added, although selected credential reads are denied (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`). Codex likewise sets `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`/local_disk0/codexwork/bundle/codex/config.toml:1-19`).
* Two independent local signals establish that isolation is available in product configuration but not the harness's normal posture: Claude is configured to bypass permissions across two drives (`claude/settings.json:26-75`), while Codex separately runs danger-full-access (`codex/config.toml:6-7`). This is a configured-posture claim, not a claim that the underlying products lack sandbox features.
* The known live defects are treated as higher-confidence than static audit claims. In particular, detectors confuse mention with use (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-87`), detectors were trusted without positive controls (`:111-129`), hook telemetry was absent from the mined transcripts even though hooks visibly fired (`:132-147`), and an orchestrator-authored false constraint propagated into roughly 15 prompts (`:150-160`).
* The corpus's `hooks` section was not used. The pinned input says its detector is broken; zero detected hooks is therefore no data, not an absence.

### What cannot be known from public material

**UNVERIFIED:** Cognition does not publish the cloud agent's controller prompt, exact model-routing policy, context-window allocation, compaction algorithm, retry policy, or internal planner state. The settling experiment is a controlled Devin account run with event export: submit identical instrumented tasks at increasing context lengths, inspect the full session-event timeline, and compare actions, retrieval, compaction-visible discontinuities, retries, and costs. Accordingly, this report describes the observable loop, not a fabricated internal architecture.

**UNVERIFIED:** marketing statements such as “subagents improve performance and reduce cost” are not accepted as owner-specific facts. The settling experiment is paired evaluation of 30 representative owner tasks under fixed budgets with subagents disabled versus enabled, scored by deterministic task verifiers and total cost. [Devin CLI subagents](https://docs.devin.ai/cli/subagents).

**UNVERIFIED:** no live Devin tenant was available, so reliability, latency, knowledge-retrieval precision, MCP connection health, and Review false-positive rates were not measured. The settling experiment is a two-week shadow trial on non-sensitive repositories with exact success, tool-error, retry-loop, review precision, cost, and wall-clock metrics.

## 1. Agent loop

### Observable cloud loop

The defensible external model is:

1. **Bootstrap a clean machine.** Every session boots a fresh copy of a frozen environment snapshot containing cloned repositories, tools, and dependencies. Session changes do not persist back into the snapshot. Blueprint changes rebuild it. [Environment configuration](https://docs.devin.ai/onboard-devin/environment).
2. **Retrieve and scope.** Connected repositories are indexed. Ask Devin can answer with code citations or work in Plan mode and produce a context-rich prompt for an Agent session. [Ask Devin](https://docs.devin.ai/work-with-devin/ask-devin).
3. **Plan.** Cognition's 2025 release notes say the interactive planner rapidly scans relevant files, cites snippets, emits an initial plan, and allows an approval wait. Confidence is expressed at session start, after planning, and in code answers; lower-confidence plans wait for approval. [2025 release notes](https://docs.devin.ai/release-notes/2025).
4. **Act.** Agent mode can write code, execute shell commands, browse, and operate the editor/browser. The Devbox exposes a shell, browser, and editor controlled by the cloud brain. [First session](https://docs.devin.ai/get-started/first-run), [deployment architecture](https://docs.devin.ai/enterprise/deployment/overview).
5. **Verify and deliver.** It can run lint/build/tests, inspect CI, create a PR, and optionally enter testing mode: derive a focused E2E plan from the diff, wait for green CI/comments, interact with the application, annotate a screen recording, and attach the processed video. [Testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings).
6. **Reflect.** After completion, a user can generate Session Insights: issue timeline, improved prompt, configuration action items, and useful/misleading Knowledge attribution. Insights are post-hoc and manually triggered, not an always-on completion gate. [Session Insights](https://docs.devin.ai/product-guides/session-insights).

This is an effective product loop because it separates environment reproducibility, context planning, execution, evidence, and after-action learning. It is not evidence of a novel internal reasoning loop.

As of July 2026, blueprints can be Git-backed and enterprise snapshot builds can be scheduled with drift warnings. [2026 release notes](https://docs.devin.ai/release-notes/2026).

### Reject: local snapshot image service

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Faithfully porting Devin snapshots would require image builds, storage, boot orchestration, secret injection, drift reconciliation, and garbage collection. This reintroduces infrastructure rather than improving the existing agent bus and therefore fails the anti-overfit gate.

It is **very likely (80-90%)** that deterministic version-controlled setup and preflight checks deliver most of the owner value at much lower complexity because the normal workspace is persistent and local, unlike disposable cloud Devboxes. The settling experiment is 30 fresh-worktree task starts measuring setup failures and time-to-first-test before considering any image layer.

### Where ours is better

Our cross-tool contract requires terminal-state tool outputs, explicit long-operation monitoring, structured subagent handoffs, a fresh-context critic pass, and semantic plus objective continuity (`/local_disk0/codexwork/bundle/codex/AGENTS.md:14-68`). Devin's public guidance instead admits that performance can degrade in long sessions and recommends splitting complex work into multiple sessions. [Prompting advice](https://docs.devin.ai/learn-about-devin/prompting). That is worse than having compaction replay and objective state continuity as first-class invariants.

Our completion controls also act before a claim is accepted: the bundle contains `claim-guard`, `fresh-verify`, `test-tamper-guard`, `wire-check`, and related hooks. Devin Session Insights is useful but runs only after a completed session and only when triggered, according to its documentation. Do not replace pre-completion evidence gates with post-hoc AI analysis.

### Port: evidence-shaped planning, not a new planner

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a planning skill that emits four typed fields—goal, affected surfaces, verification commands, and uncertainty/approval gate—and persist that record in the existing event ledger. Reuse the existing plan tool and goal-reinject hook; do not build a planner service. The planner record becomes an input to Stop-time verification so the plan and proof correspond.

This is **very likely (80-90%)** to reduce “finished the wrong thing” failures because the current contract already re-injects goals and records decisions (`AGENTS.md:14-26`), while Devin's public planner demonstrates a concise file-grounded plan/approval interface. A settling experiment is 40 historical tasks replayed with and without the typed plan, scored on requirement coverage and correction turns.

## 2. Context management

### Devin's mechanisms

* **Repository index:** repositories are indexed for Ask Devin/DeepWiki-like code search; answers cite code, and Plan mode can hand a high-context prompt to an Agent session. [Ask Devin](https://docs.devin.ai/work-with-devin/ask-devin).
* **Selective durable context:** Knowledge has a trigger description and is retrieved only when relevant; it may be pinned to one repo or all repos. The docs explicitly advise small, specific notes because full note contents are read when selected. [Knowledge](https://docs.devin.ai/product-guides/knowledge).
* **CLI lazy rule discovery:** root AGENTS/rules load at session start; subdirectory rules are discovered when files in that directory are accessed, avoiding unrelated context. It imports AGENTS, Claude, Cursor, and Windsurf formats. [CLI rules](https://docs.devin.ai/cli/extensibility/rules).
* **CLI skills:** only metadata is initially visible and full content is invoked when relevant. Skills support arguments, dynamic shell content, tool scopes, model overrides, and subagent execution. [Creating skills](https://docs.devin.ai/cli/extensibility/skills/creating-skills).
* **Compaction lifecycle:** CLI exposes `PostCompaction` with the generated summary, enabling reinjection after compaction. [Lifecycle hooks](https://docs.devin.ai/cli/extensibility/hooks/lifecycle-hooks).
* **Session references:** prompts can `@`-mention prior sessions for context. [First session](https://docs.devin.ai/get-started/first-run).

### Comparison

Our harness already uses the strongest ideas: a 2% skill-listing budget (`/local_disk0/codexwork/bundle/claude/settings.json:1-4`), 90% auto-compaction threshold (`:15-19`), explicit pre/post-compaction hooks (`/local_disk0/codexwork/bundle/codex/config.toml:412-431`), and the rule that objective event replay—not an in-context summary—is ground truth (`/local_disk0/codexwork/bundle/codex/AGENTS.md:20-26`). The latter is stronger than Devin CLI's public `PostCompaction.summary` contract.

Devin's cleanest idea is lazy directory-scoped rule loading. **UNVERIFIED:** whether our Claude/Codex providers already implement equivalent lazy hierarchical rule loading consistently across all three toolchains cannot be established from the bundle alone. The settling experiment is a three-provider fixture with a root rule, two conflicting subdirectory rules, and file access traces proving exactly when each enters context.

### Port: cross-provider hierarchical-rule conformance [UNVERIFIED]

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** If the fixture proves each provider's native directory-scoped instructions behave consistently, standardize on `AGENTS.md` plus narrow subdirectory files and delete duplicated always-on language rules. If one provider fails, do not emulate it with a daemon; keep provider-specific adapters in the existing installer.

This is **likely (55-80%)** to lower context tax because Devin explicitly recommends small rules and relevant skills, and only 78 of roughly 355 installed skills were invoked in the supplied corpus. It inherits **UNVERIFIED** status until the hierarchical-rule fixture above runs.

## 3. Memory

### Devin Knowledge

Knowledge is an organization/enterprise collection of short triggered notes. It supports macros, per-user enable/disable, folders, repo/all-repo pinning, automatic suggestions from feedback, and suggestions to update existing entries. Multiple relevant items may be retrieved. Session Insights labels Knowledge as useful or misleading and explains its application. [Knowledge](https://docs.devin.ai/product-guides/knowledge), [Session Insights](https://docs.devin.ai/product-guides/session-insights).

Cloud Skills are separate: repository-committed `SKILL.md` procedures are automatically indexed, rescanned after clone, and can be invoked automatically or by `@skills:name`. Only one cloud skill may be active at once; invoking another replaces it. Org-wide cloud skills require a dedicated repository workaround. [Cloud Skills](https://docs.devin.ai/product-guides/skills).

### Comparison and what not to copy

Our memory separation is better designed for truth maintenance. The event ledger stores objective turn state; `basic-memory` stores semantic knowledge; the contract requires `valid_as_of` and backward `superseded_by` links when facts change (`/local_disk0/codexwork/bundle/codex/AGENTS.md:62-85`). Devin documents folders, triggers, enable/disable, and misleading-note analysis, but not an equivalent temporal supersession contract.

**UNVERIFIED:** public docs may omit hidden Knowledge versioning. The settling experiment is to create/update a note in a Devin tenant, inspect the v3 notes API and UI history, then retrieve it from a session to determine whether superseded text remains addressable and whether retrieval honors effective dates. Do not conclude that versioning is absent until then.

Do not copy automatic skill creation into the live skill directories. Devin proposes skills via PR after testing, which is safer than silent installation, but the pinned audit cites SkillsBench evidence that one-shot generated skills can regress performance (`/local_disk0/codexwork/bundle/inputs/audit-findings/E09.md:26-45`; paper URL recorded there: https://arxiv.org/pdf/2602.12670). Our foundry/incubation approach is the better boundary.

### Port: Knowledge-use receipts and stale-note review

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing memory recall path so each injected note writes `{note_id, query_hash, timestamp, session_id}` to the event ledger. At SessionEnd, join those receipts with later explicit corrections, failed commands, and completion status; emit a small review artifact listing “used,” “possibly misleading,” and “not enough evidence.” Never auto-edit or delete notes. Require a human or a dedicated maintenance skill to add `superseded_by`.

This is **likely (55-80%)** to improve memory quality because Devin's Session Insights demonstrates actionable note attribution, while our live D3 defect proves hook behavior is currently hard to measure (`INPUT-known-harness-defects.md:132-147`). The lower band reflects attribution ambiguity: a used note is not necessarily causal. The settling experiment is manual review of 100 attributed notes, measuring precision of “misleading” flags before enabling any notification.

## 4. Tool and MCP handling

### Devin

Devin Cloud offers an MCP marketplace and supports stdio, SSE, and HTTP transports. Devin CLI supports `add/list/get/remove/login/logout/enable/disable`, project/local/user scopes, Streamable HTTP with SSE fallback, OAuth tokens stored locally and refreshed, headers, environment variables, and tool-level permissions using `mcp__server__tool`. [Cloud MCP marketplace](https://docs.devin.ai/work-with-devin/mcp), [CLI MCP configuration](https://docs.devin.ai/cli/extensibility/mcp/configuration), [CLI permissions](https://docs.devin.ai/cli/reference/permissions).

The June/July 2026 platform adds operational governance that is easy to miss in older summaries: a dedicated enterprise MCP page reports per-server organization/session usage; stale installations show an “out of date” warning with marketplace refresh; secure mode can restrict MCPs to read-only; and automations warn when a user-scoped MCP would run without the creator identity. [2026 release notes](https://docs.devin.ai/release-notes/2026). This does not prove automatic liveness quarantine, but it is a substantially better inventory and scope surface than a flat server list.

The official Devin MCP reverses the direction: any MCP-compatible client can create and gather sessions, inspect/search session events, manage playbooks/Knowledge/schedules, search private/public repositories, and list installed integrations. It uses authenticated Streamable HTTP. [Devin MCP](https://docs.devin.ai/work-with-devin/devin-mcp).

### Comparison

Our fleet is far larger and more specialized, but reliability is demonstrably worse. The pinned corpus measured `claude_ai_Tavily` at 25.8% error, including 135 “not connected” failures, yet it remained callable. The subject config broadly allows `mcp__tavily` (`/local_disk0/codexwork/bundle/claude/settings.json:47-60`). This is a two-signal broken-path conclusion: observed calls fail in the corpus, and static permission configuration continues to expose the server. In contrast, Devin CLI gives an explicit disabled state and enable/disable commands.

Devin does not publicly document automatic MCP health quarantine. **UNVERIFIED:** marketplace UX may perform liveness checks not described in docs. The settling experiment is to configure a deliberately dead stdio server and a dead HTTP endpoint, restart CLI/cloud sessions, and observe tool exposure, retry behavior, warnings, and audit logs. Do not attribute self-healing to Devin without that test.

The official Devin MCP's session-event search is more coherent than our telemetry: it explicitly searches shell, file, browser, git, and MCP activity, while our D3 live defect found hook telemetry absent from transcripts (`INPUT-known-harness-defects.md:132-147`). However, adopting Devin MCP as a controller would be a second orchestration runtime and fails the anti-overfit gate.

### Port: evidence-driven MCP quarantine

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Render the active MCP set from the existing canonical fleet with `enabled=false`/omission for any endpoint that fails two mechanically independent checks: (1) transport handshake and tool listing; (2) a provider-native resolved-config/list command confirming the same entry and launch target. Re-enable only after both pass. The runtime hook may warn, but config rendering owns exposure. Never retry “not connected” more than once per session.

This is **almost certain (90-99%)** to eliminate calls to the known-dead Tavily entry because removing/disablement makes the tool unselectable; evidence is the 135 “not connected” fingerprint and the still-allowed config entry. The settling experiment is a canary session that asks explicitly for Tavily and proves it cannot be selected, followed by a known-live MCP control that is still listed and callable.

### Port: tolerant child result envelopes, not strict schemas

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Devin can request structured JSON from child sessions, including a schema. Our corpus shows `StructuredOutput` at 22.9% error with 294 schema mismatches. Do not copy strict fan-out schemas. Use a tolerant envelope with required `status` and free-form `summary`, optional `evidence[]`, `artifacts[]`, and `gaps[]`; preserve unknown fields; accept a plain-text fallback and normalize it at the parent boundary.

This is **very likely (80-90%)** to reduce schema-caused fan-out failures because it directly relaxes the measured mismatch point while retaining machine-readable terminal state. The settling experiment is replay of the 294 schema-mismatch fingerprints through strict and tolerant parsers, requiring no false “success” promotion.

## 5. Permission model

### Cloud and enterprise

Every cloud session runs on an isolated machine. Enterprise Cloud uses multi-tenant Cognition infrastructure; Customer Dedicated Deployment uses a customer-isolated single-tenant VPC connected by PrivateLink or IPSec. The brain remains in Cognition Cloud. [Deployment](https://docs.devin.ai/enterprise/deployment/overview).

Devin Enterprise has custom RBAC for sessions, Knowledge, playbooks, secrets, snapshots, MCP, API keys, metrics, repository indexing, and other resources; API endpoints are permission-gated. [Custom roles](https://docs.devin.ai/enterprise/security-access/custom-roles), [API RBAC](https://docs.devin.ai/api-reference/v3/overview).

GitHub permissions are organization-level, not the initiating user's individual permissions. The app requests read/write access to repository contents, checks, statuses, discussions, issues, PRs, projects, and workflows. Cognition recommends branch protection. [GitHub integration](https://docs.devin.ai/integrations/gh). This is convenient but broad; a dedicated bot identity plus branch protection is essential.

### CLI

Devin CLI's design is precise:

* normal mode auto-allows reads but prompts for fetch, shell, and writes;
* accept-edits auto-allows workspace edits;
* bypass auto-allows everything unless an org rule blocks it;
* autonomous mode auto-allows shell/fetch inside the OS sandbox, while direct edit/write tools still prompt;
* decisions resolve `deny > ask > allow > default prompt`;
* scopes include `Read(glob)`, `Write(glob)`, `Exec(prefix)`, `Fetch(pattern)`, named tools, and named MCP tools;
* organization policy is highest precedence; session, project-local, project, and user layers follow;
* skills and custom subagents can narrow tools and permissions. [Permissions](https://docs.devin.ai/cli/reference/permissions), [configuration precedence](https://docs.devin.ai/cli/reference/configuration/global-vs-local), [creating skills](https://docs.devin.ai/cli/extensibility/skills/creating-skills).

Cloud secure mode now adds a read-only MCP toggle, and network-restricted sessions can request a specific domain for user approval instead of requiring every domain to be preconfigured. These July 2026 controls are narrower and more usable than either blanket network access or a static global allowlist. [2026 release notes](https://docs.devin.ai/release-notes/2026).

### Where Devin is worse

The OS sandbox is not currently supported on Windows; requesting it hard-fails. Linux requires `bubblewrap` and `socat`. Network filtering is explicitly documented as unstable. [Sandbox](https://docs.devin.ai/cli/sandbox). For this owner, this makes Devin CLI's “autonomous with isolation” mode unavailable on the primary OS. Our Codex config at least exposes a Windows `sandbox = "elevated"` setting (`/local_disk0/codexwork/bundle/codex/config.toml:459-460`), although the active top-level posture remains danger-full-access (`:6-7`).

Background Devin subagents automatically deny any tool not previously approved; they cannot request new permissions. That is safe but can fail legitimate work and then require foreground resumption. [Subagents](https://docs.devin.ai/cli/subagents). Our explicit agent messages can grant a bounded task scope directly, which is more flexible, though less uniformly enforced.

### Port: least-privilege configured defaults

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Change the harness baseline from broad bypass to: reads auto-approved; edits only in the workspace; shell allowlisted for known read/test/build prefixes; fetch scoped by domain; MCP scoped by server/tool; destructive and external-write operations ask or deny. Add per-skill `allowed-tools`/permission metadata for high-risk skills. Organization/user policy remains the ceiling; a skill may narrow but never widen it.

This is **very likely (80-90%)** to reduce blast radius because both active provider configs currently auto-approve broadly (`claude/settings.json:26-75`; `codex/config.toml:6-7`), and Devin's precedence model shows a concrete configuration-only design. The settling experiment is a permission conformance suite with known-positive read/test cases and known-negative credential, outside-workspace, force-push, and destructive-command cases on PowerShell and Git Bash.

This port must not reuse the current lexical command guards as the security boundary. D1 proves four detectors conflate mention with execution and can even label a successful result failed (`INPUT-known-harness-defects.md:9-87`). Native structured tool/path scopes should decide permissions; semantic hooks may add context but should not parse prose payloads as executable commands.

### Port: scoped secret attachment

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Mirror Devin's personal/org/repo/session secret scopes without building a secret vault: store values only in Windows Credential Manager/provider keyrings; keep a non-secret manifest mapping secret IDs to allowed repo hashes, tools, and duration; resolve selected IDs at SessionStart or explicit user attachment into the child process environment; scrub at SessionEnd; never expose values to prompts or config files. Devin's create-session API already models `secret_ids` and ephemeral `session_secrets`. [Create session](https://docs.devin.ai/api-reference/v1/sessions/create-a-new-devin-session), [Secrets](https://docs.devin.ai/product-guides/secrets).

This is **likely (55-80%)** to reduce ambient credential exposure because the mechanism narrows scope and lifetime while reusing the native credential store. The lower band reflects Windows child-process/env leakage risks. The settling experiment is a red-team fixture proving an allowed tool can use the secret, an unrelated tool/repo cannot observe it, logs/transcripts redact it, and teardown removes it.

## 6. Customization: rules, skills, hooks, plugins

### Devin's surface

* **Rules:** global and project AGENTS/CLAUDE/Windsurf/Cursor files; lazy subdirectory discovery; always-on, glob, model-decided, and manual activation depending on imported format. [Rules](https://docs.devin.ai/cli/extensibility/rules).
* **Skills:** `SKILL.md`, args, dynamic command substitution, model override, subagent execution, allowed tools, permissions, user/model triggers. Cloud Skills are repo-indexed and can be suggested via PR after testing. ### Comparison

Our surface is at least as broad and demonstrably more specialized. The bundle includes dozens of active hook directories and a shared dispatcher, while corpus capability use records 78 invoked skills and 22 agent types. Devin's advantage is not raw extensibility; it is a comprehensible resolution model and migration compatibility.

Our worse point is operational complexity. One audit unit measured a synchronous plugin SessionStart hook around 51 seconds p50 and the local Stop dispatcher around 10.4 seconds p50 (`/local_disk0/codexwork/bundle/inputs/audit-findings/A07.md:1-18`). Those are audit claims, not independently reverified by this unit, so they must not be treated as measured fact here. They are strong enough to justify a benchmark gate, not a conclusion.

### Port: resolved customization inventory and latency budget

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Produce one provider-neutral `/harness status` artifact from the installer/dispatcher: resolved rules, skills metadata, hooks by lifecycle event/source, MCP enabled/disabled/health state, agent profiles, and configuration precedence. Include load/exec latency from actual receipts. Validate detection with a known-present rule, skill, hook, MCP, and agent before reporting zeros.

Record skill activation and terminal outcome in the same receipt so usage/adoption can be counted as Devin now does. Do not label raw completion rate “skill performance”: task selection is confounded. A paired same-task evaluation is required for causal performance claims.

This is **very likely (80-90%)** to prevent another false “0 skills/0 agents/0 hooks” conclusion because D2 records exactly that detector failure and the positive control that separated working skills/agents from broken hook detection (`INPUT-known-harness-defects.md:111-129`). The settling experiment is a golden fixture containing one known-present item of every kind and one deliberately malformed item.

## 7. Multi-agent support

### Devin CLI subagents

The parent can spawn foreground or background workers. Each has its own conversation/context window and does not inherit parent history, but shares tools and codebase context. Foreground waits and can ask permission; background runs in parallel, inherits only already approved permissions, and reports completion. Built-ins are a read-only explore profile on a cheaper routed model and a general profile on the parent's model. Custom `AGENT.md` profiles specify prompt, tools, permissions, model, and optional nesting. Default nesting is disabled; custom profiles opt in with a maximum depth. Completed/failed/cancelled agents can resume in foreground. [Subagents](https://docs.devin.ai/cli/subagents).

This is almost exactly the minimal architecture favored by the anti-overfit gate: separate context windows plus bounded delegation, not a durable workflow engine.

### Cloud managed Devins

Since March 2026 a main Devin can create child sessions, each a full Devin with an isolated VM; coordinate, monitor, resolve conflicts, and compile results; and give child sessions playbooks plus structured output. Parent/child sessions are grouped in the UI, and child status/todos/PRs appear in an Agents tab. [2026 release notes](https://docs.devin.ai/release-notes/2026), [Advanced Capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities).

Our local model uses shared filesystem/worktree infrastructure, with depth eight and eight threads configured (`codex/config.toml:77-80,125-130`). The contract already requires structured, re-anchored handoffs rather than raw history (`codex/AGENTS.md:43-46`). Therefore Devin CLI supplies little we lack. Full VM-per-child isolation is genuinely absent from the supplied local architecture, established by two independent signals: agent configuration describes threads/depth but no machine allocator (`codex/config.toml:77-80,125-130`), and the behavior contract describes shared task/workflow execution and structured handoffs but no per-agent VM boundary (`codex/AGENTS.md:33-46`). Both detectors find known-present agent controls, so this is not a zero-result detector error.

### Reject: cloud VM-per-child orchestration

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Porting this faithfully requires image building, VM scheduling, secrets/network policy, repository synchronization, artifact/result gathering, cost control, cleanup, and conflict resolution. It reintroduces a previously rejected second orchestration runtime and therefore fails the anti-overfit gate.

It is **very likely (80-90%)** that this would cost more operational complexity than it returns for the owner's normal local tasks: evidence is the explicit BUILD-LARGE surface above, existing native concurrency, and the Windows-local environment. The settling experiment—if unusually high-risk untrusted code becomes common—is a hosted disposable-worker pilot for only those tasks, comparing containment and operator time against native worktrees. Do not generalize it to the default harness.

### Port: profile-level permissions and cheap explore routing [UNVERIFIED]

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Preserve the existing 22 agent types but classify each as `explore-readonly` or `general-write`, set allowed tools and maximum depth, and route read-only research to a cheaper model only when the task has a deterministic evidence contract. Keep concurrency at the existing eight rather than increasing fan-out.

This is **likely (55-80%)** to reduce cost without reducing correctness because focused read-only work does not need write-capable premium agents, but the owner-specific benefit is **UNVERIFIED**. The settling experiment is paired replay of 30 research subtasks on the primary and cheap model, scoring citation/file-line correctness and total cost. The recommendation inherits that UNVERIFIED premise and must remain opt-in until the experiment passes.

## 8. Verification and self-check

### Devin mechanisms

1. **Planning confidence:** confidence at start/after plan/in code answers; low confidence pauses for approval. Cognition says its internal data correlates confidence with success, but publishes no calibration curve in that release note. [2025 releases](https://docs.devin.ai/release-notes/2025).
2. **Build/test/CI:** environment configuration is explicitly necessary so Devin can build and verify; GitHub integration reads actions/checks and sets statuses. [Environment](https://docs.devin.ai/onboard-devin/environment), [GitHub integration](https://docs.devin.ai/integrations/gh).
3. **Interactive E2E proof:** testing mode reads the diff, selects one important flow, waits for CI/comments, records the UI interaction, annotates, zooms, compresses idle time, and returns the video. It explicitly calls this a quick sanity check, not exhaustive coverage. [Testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings).
4. **Devin Review:** groups changes, detects bugs/security issues/copied code, offers chat, and can be triggered from CI/API. The local Bug Catcher is restricted to repository-scoped read operations and a limited read-only shell vocabulary. [Devin Review](https://docs.devin.ai/work-with-devin/devin-review), [2026 releases](https://docs.devin.ai/release-notes/2026).
5. **Session Insights:** post-hoc issue timeline, repeated-issue detection, improved prompt, configuration actions, and Knowledge usefulness/misleadingness. [Session Insights](https://docs.devin.ai/product-guides/session-insights).
6. **Merge conflict/status visibility:** release notes document conflict notifications, PR statuses, and Review commit checks. [2026 releases](https://docs.devin.ai/release-notes/2026).

### Where ours is better

Our fresh-context verification, claim guard, test-tamper guard, and ledger-backed completion policy aim to prevent unsupported completion, not merely analyze it afterward. The cross-tool contract says a conclusion receives an internal fresh-context critic and durable failures retain falsifiable preconditions (`codex/AGENTS.md:20-26,56-60`). Keep that.

Devin's confidence gating is weaker as evidence unless calibrated. A model's self-reported confidence can become presentation theater. **UNVERIFIED:** Cognition's claim of correlation may be true on its distribution but no public calibration/reliability diagram was found. The settling experiment is to record pre-task and post-plan confidence on 100 blinded owner tasks, then plot reliability, Brier score, and selective accuracy before using confidence to auto-approve anything.

Devin Review is a separate reviewing agent/product. Copying it as a mandatory trained critic would violate the anti-overfit gate's rejected trained-critic component. Use existing linters/tests plus occasional fresh agents, not an always-on learned reviewer.

### Port: session evidence index and retry-loop report

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At SessionEnd, normalize existing event-ledger and transcript receipts into a bounded artifact: goal, changed files, commands with exit status, tests, MCP failures, retries by normalized fingerprint, final artifacts, open gaps, and note IDs used. Do not ask an LLM to decide facts. Optionally run a model only to rewrite the next prompt, clearly labeled as a suggestion. Add a known-positive test event and hook event to validate the detector before any absence claim.

This is **almost certain (90-99%)** to improve diagnosability because D3 identifies missing hook visibility, D2 identifies unvalidated zero detectors, and the corpus already contains 5,692 error fingerprints and retry loops. The settling experiment is to generate ten instrumented sessions containing known tool, hook, failure, retry, and success events and require exact event recall before deployment.

### Port: annotated E2E proof recording

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a `ui-proof` skill using the already configured browser/Playwright path (`/local_disk0/codexwork/bundle/claude/settings.json:47-60`) and existing video tooling in the skill catalog. Inputs: affected route, one golden flow, expected observable, credentials by secret ID. Steps: start screen capture, run the deterministic browser script, overlay timestamps/step labels, stop, attach video plus Playwright trace and test exit code. It must never substitute for automated tests.

This is **likely (55-80%)** to shorten review for UI changes because a short visual proof exposes interaction/layout failures that a terminal log does not. The settling experiment is 20 UI PRs randomized to logs/screenshots versus annotated video, measuring reviewer time and escaped visual defects. The lower band reflects the production/maintenance cost of reliable Windows capture.

### Do not port: automatic confidence approval

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Keep confidence advisory until calibrated; do not let green self-confidence bypass tests, permissions, or human approval for consequential actions. If the 100-task calibration experiment above passes predeclared thresholds, confidence may decide whether to ask a scoping question, never whether to skip evidence.

This restriction is **very likely (80-90%)** safer than auto-approval because confidence is not proof and our corpus contains many confidently wrong single-signal conclusions (`INPUT-known-harness-defects.md:111-129`).

## 9. Specific things Devin does worse — do not copy

1. **Windows sandbox gap.** `--sandbox` hard-fails on Windows and network filtering is unstable. This directly conflicts with the owner's platform. [Sandbox](https://docs.devin.ai/cli/sandbox).
2. **Cloud dependence and closed brain.** Even the customer-dedicated deployment keeps the brain in Cognition Cloud, and Cognition does not support customer-provided model API keys. [Deployment](https://docs.devin.ai/enterprise/deployment/overview). Do not make the harness dependent on a single closed control plane.
3. **Linux-only Cloud Devbox.** Desktop applications must have a Linux build for Devin's computer-use testing. [Computer use](https://docs.devin.ai/work-with-devin/computer-use). This is materially worse for Windows-only reverse engineering, WinDbg, Visual Studio, and native desktop tasks represented in our skill/MCP fleet.
4. **Broad org-level GitHub identity.** Integration permissions are shared at organization level rather than inheriting the initiating user's exact GitHub rights. [GitHub](https://docs.devin.ai/integrations/gh). Our default should be task-scoped credentials, not ambient organization write authority.
5. **One active cloud skill.** Cloud Devin replaces the previous active skill when another is invoked; composition is explicitly a limitation. [Cloud Skills](https://docs.devin.ai/product-guides/skills). Our orchestrated skills and agent roles should remain composable.
6. **Long-session degradation acknowledged.** Cognition advises separate sessions for particularly complex work because performance can degrade with session length. [Prompting](https://docs.devin.ai/learn-about-devin/prompting). Our event-ledger/compaction continuity is the better direction.
7. **Post-hoc insights are manual.** Session Insights is free but not automatic; a user must trigger it after completion. [Session Insights](https://docs.devin.ai/product-guides/session-insights). Our deterministic receipts should be automatic and cheap.
8. **Visual testing is deliberately shallow.** Testing mode chooses one principal flow and says exhaustive coverage belongs in CI. [Testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings). Copy the evidence artifact, not the idea that one recorded happy path proves correctness.
9. **Background permission starvation.** Unapproved background-subagent tools are denied and require a foreground resume. [Subagents](https://docs.devin.ai/cli/subagents). Prefer explicit task capability manifests at spawn time.
10. **Structured schemas can become the same trap.** Devin supports structured child outputs, but our measured `StructuredOutput` mismatch rate proves that strict schemas are dangerous under fan-out. Use tolerant envelopes.
11. **Automatic Knowledge/Skill suggestions need quarantine.** Suggestions are useful candidates, not verified truth. Devin partly mitigates this through edit/dismiss flows and skill PRs. Keep our temporal validity and incubation gates.
12. **Full platform adoption violates minimal architecture.** Sessions, schedules, VM workers, indexed repos, cloud Knowledge, Review, and MCP management together form a second orchestration/runtime platform—the exact class the anti-overfit gate rejects.

## 11. Anti-overfit gate result

All recommended ports use an existing bus:

* rules/config renderer;
* hook dispatcher and event ledger;
* skill/agent metadata;
* existing MCP fleet;
* existing browser and artifact/video tooling;
* native OS credential store.

No recommended port adds a second orchestration runtime, vector DB/KG, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The one proposal that would—VM-per-child managed orchestration—is explicitly rejected. The evidence/insights design keeps facts deterministic and confines any model-generated “improved prompt” to a labeled suggestion.

This is important because the owner's measured harness already suffers from elaborate control-plane failure: noisy semantic guards, broken detector telemetry, strict schema mismatches, fleet drift, and propagated false constraints. Devin's frontier lesson is not “add more agents.” It is “make the state transitions, evidence, permissions, and learning surfaces coherent.”
