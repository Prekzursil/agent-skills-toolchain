There are **seven real textual conflict classes**. They affect 15 unique command files. The highest-risk conflicts are (1) explicit one-hour foreground multi-model calls versus mandatory `longrun`, (2) command-level vendor “authority” versus the evidence-independent critic rule, and (3) importing a URL directly into an instruction store despite the fetched-content rule.

The important architectural fact is that this harness has **no deterministic command-versus-contract precedence mechanism**. Claude Code's official documentation says `CLAUDE.md` is added as a user message after the system prompt, while an invoked command/skill enters the conversation as a rendered prompt message and remains in context. It also documents `UserPromptExpansion` as the hook event that can block or add context to a user-typed command before Claude receives it ([skills/commands documentation](https://code.claude.com/docs/en/slash-commands), [hooks reference](https://code.claude.com/docs/en/hooks), [output-style/context comparison](https://code.claude.com/docs/en/output-styles)). In the unpacked live configuration, parsed hook keys contain `UserPromptSubmit` and `PreToolUse` but not `UserPromptExpansion`; independently, the shared adapter recognizes `UserPromptSubmit` and `PreToolUse` at `agents/harness/adapters.py:15-16` and contains no `UserPromptExpansion`. Both absence probes had known-present controls.

Therefore, “which wins” is not a hard runtime property in this snapshot. On direct `/command` invocation, the command is **very likely (80-90%)** to dominate at the contradictory step because it is the current user-triggered prompt, the contract itself ranks “The user's explicit in-session instruction” first (`AGENTS.md:121`), and Anthropic documents direct invocation as a user-typed command expanded into a prompt. This is **UNVERIFIED; settle it with experiment E1 below on the Windows host**. For a model-auto-invoked command, the winner is **roughly even (45-55%)**, because both texts are prompt guidance at comparable user-message level and no enforcement hook resolves the collision; this is **UNVERIFIED; the auto-invocation arm of E1 settles it**.

That limitation does not make the static conflicts hypothetical: every finding below gives a concrete invocation in which both instructions apply and cannot both be followed. It only prevents an honest claim that a particular model build always chooses the same loser.

## Apparent conflicts investigated and rejected

These were not counted because the two texts can both execute, the situation is outside the contract clause, or the collision depends on unavailable implementation evidence.

1. **Structured subagent handoffs:** `/orchestrate` is compliant, not conflicting. `commands/orchestrate.md:41-69` explicitly collects a structured handoff with Context, Findings, Files Modified, Open Questions, and Recommendations. The multi-model commands refer to “analysis results” or plan content, but do not explicitly demand raw-output prefixing. Without evidence that the implementation passes raw output, absence of compliance is not a finding.
2. **Review/merge blocking:** `/code-review`, `/python-review`, and `/review-design` use “block” as a workflow verdict. `AGENTS.md:64-70` defines exit-code behavior for hooks. A review recommendation to block a merge is not an Exit-2 hook, so the axes differ.
3. **Approval questions:** `/plan`, `/devfleet`, `/rollback`, and most selection prompts ask for authorization at a task boundary or before a destructive/external action. Those are permission/decision gates, not necessarily clarifying questions. I therefore did not inflate Finding 1 with every occurrence of “ask” or “approval.”
4. **Test-suite duration:** `/verify`, `/test-coverage`, `/refactor-clean`, `/e2e`, and `/python-review` name suites that might exceed 60 seconds. Duration is repository-dependent, and the contract only applies when an operation is expected to exceed 60 seconds. **UNVERIFIED; timing each suite on its real target repo would settle it.** They are gaps, not conflicts. By contrast, Finding 2 includes explicit one-hour waits, ten-minute blocking polls, four-hour monitoring, and `--watch`, which the contract itself names.
5. **BEADS versus basic-memory:** `/prime` loads project facts and execution context, while basic-memory is semantic memory and the ledger is objective history. Those can be additive. I only counted `/save-session` and `/resume-session`, which explicitly claim full/exact continuity and omit reconciliation with the named ground truths.
6. **`command -v` probes:** `external-tools-health.md:15-16` and `start-task.md:65-66` use `command -v`, not the specifically forbidden `which`. Whether Git Bash `command -v` resolves the owner's `.cmd` shims is **UNVERIFIED; E3 settles it**. I did not call those broken.
7. **Dispatcher argument validation:** `/compute-monitor` and `/cs` say they pass `$ARGUMENTS` through to PowerShell. The dispatcher implementations referenced by those commands are not in the unpacked subject. Whether they validate/allowlist verbs is **UNVERIFIED; inspect `mon.ps1` and `cs.ps1` plus adversarial argv tests to settle it**. No absence claim was made.
