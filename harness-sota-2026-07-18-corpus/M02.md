# M02 — Durable authorization tracking: remember permission without inventing it

**Unit:** M02, partner-dimension / trust and autonomy calibration  
**Date:** 2026-07-19  
**Mode:** research and design only; the unpacked subject was read-only and no harness/config was changed.

Unless an absolute path is shown, every local `path:line` citation below is relative to the verified bundle root `/local_disk0/codexwork/bundle`.

## Executive verdict

The harness needs a **typed authorization receipt layer inside the existing shared event-ledger and dispatcher**, not a new memory service, policy daemon, hook, or model-based judge. The layer should remember only authority that came from the owner through an externally observable approval event, match later actions by exact or subset scope, and make a new owner interruption only when the requested action is outside that scope. The expected reduction in repeated permission questions is **very likely (80-90%)**, because the local system already has the required lifecycle events, durable append path, recall surface, and native permission response shape; the remaining uncertainty is the distribution of real authorization prompts, which the distilled corpus does not measure (`/local_disk0/codexwork/bundle/agents/harness/registration.py:17-34`; `/local_disk0/codexwork/bundle/agents/harness/ledger.py:817-880`; [native Claude hook decision fields](https://code.claude.com/docs/en/hooks)).

This is not “trust the model more.” It is **remember the exact boundary the owner set, prove the present action is inside it, and otherwise stop**. That distinction is the core calibration mechanism.

The live Databricks premise is only partly recoverable on this Linux bundle. The recall index proves that a Databricks SSO recovery verdict note exists and carries a stable permalink, title, and project path (`claude/hooks/recall-inject/index/recall_index.json:6467-6492`). The full note body and original approval turn are **UNVERIFIED; the settling experiment is to read the indexed basic-memory note and its source transcript on the Windows box, then compare the proposed action/resource/effect fields to the owner's exact words**. Therefore this unit does not state what the owner authorized for Databricks. The user's unit brief supplies the operational observation that the authorization was re-litigated because memory was not checked; the artifact uses that incident as a required test case, not as permission to reconstruct an unknown grant.

## Grounding: what exists, what the corpus establishes, and what it does not

### Verified local substrate

1. The behavior contract already says to record durable decisions through `note.py`, to treat the event ledger as objective turn-history ground truth, and to query basic-memory proactively after compaction or when prior work is referenced (`claude/AGENTS.md:30-33,85-89`). This design builds on those roles instead of duplicating them.
2. `note.py` currently records decisions, failures, goals, and milestones, including supersession, but has no authorization-specific schema (`claude/hooks/event-ledger/note.py:2-12,25-42`). Free-text `decision` is therefore durable but not safely matchable as authority.
3. The newer shared `EventLedger.append()` accepts a sanitized additive `kind` and arbitrary additive fields, uses an append lock, fsyncs the JSONL event, and deduplicates by an event id (`agents/harness/ledger.py:817-880`). A typed `authorization_*` event family can ride this exact bus. The older local event-ledger constrains kinds to seven values and downgrades unknown values to `note` (`claude/hooks/event-ledger/ledger.py:61-65,230-285`); implementation must use the shared ledger as canonical and provide a compatibility projection rather than patching both stores independently.
4. `PermissionRequest` and `PermissionDenied` are already registered native events (`agents/harness/registration.py:17-53`), and the live Claude settings route both to the same shared dispatcher (`claude/settings.json:284-308`). The normalized event already carries provider, session, cwd, permission mode, tool name/id/input, result aliases, and the denial reason (`agents/harness/adapters.py:44-62,73-146`).
5. The dispatcher already runs ten modules in a fixed order, with `secret_guard` before `event_ledger`, and is fail-open per module (`agents/harness/modules.py:420-431`; `agents/harness/dispatcher.py:267-308`). `LedgerModule` presently records denials as negative tool results but does not record approvals or reusable grants (`agents/harness/modules.py:944-962,1170-1194`). This is the precise extension seam.
6. Claude's native hook protocol can let a `PermissionRequest` hook answer `allow`, optionally return a complete `updatedInput`, and apply `updatedPermissions`; native deny/ask rules still take precedence ([Claude hooks reference](https://code.claude.com/docs/en/hooks), [permissions precedence](https://code.claude.com/docs/en/permissions)). This is a native actuation surface, not a reason to write settings JSON ourselves.
7. The recall-inject hook is high-precision, bounded to three notes, per-session deduplicated, fail-open, and tells the agent to retrieve the full note from basic-memory (`claude/hooks/recall-inject/inject.py:8-23,44-50,240-263,269-321,327-392`). It is useful for semantic context, but its lexical match is not an authorization evaluator.
8. The recall index contains a second, unusually clear authorization precedent: a Claude Design note summary says the user authorized `/design-login` with `user:design:read+write` (`claude/hooks/recall-inject/index/recall_index.json:6575-6588`). It also contains explicit “do not re-suggest” and “deferred” decisions (`claude/hooks/recall-inject/index/recall_index.json:6726-6747,6858-6869`). Those examples show that authority and negative preferences already reach semantic memory; they do not prove that agents retrieve or scope them correctly.
9. Open-loop/prospective memory is already implemented. Its durable trigger records include conditions, TTL, fired state, recurrence, and source, and it evaluates cheap cwd/branch/file/prompt predicates (`claude/hooks/open-loops/_common.py:1-26,41-58,109-198`). SessionStart resurfaces at most three matching or standing loops and deliberately avoids duplicating event-ledger replay (`claude/hooks/open-loops/resurface.py:1-25,38-40,51-108`). Authorization work blocked on owner input should attach to this mechanism, not create another thread tracker.
10. The consolidated hook dispatcher already folds multiple checks behind one invocation (`claude/hooks/_dispatch/manifest.json:1-4`). This unit adds **zero hook registrations**. It proposes one module on the existing shared dispatcher and, where necessary, one check folded into the existing consolidated event entry.

### Corpus evidence and its limits

The corpus is a trustworthy coverage source for its captured fields: 11,633 files were read, none failed, only one line was bad, and 32 lines were oversized (`inputs/corpus.json:2-11`). It shows that owner interruption is not hypothetical: `AskUserQuestion` ran 1,329 times with 39 errors (`inputs/corpus.json:134-140`). It also shows substantial use of the existing semantic memory bus: basic-memory was touched 1,332 times at the server level (`inputs/corpus.json:13370-13379`), including 408 writes, 357 searches, 353 reads, and 156 edits (`inputs/corpus.json:13466-13485`). Reads were reliable at 0.85% error, but writes, searches, and edits had 4.41%, 3.64%, and 11.54% error respectively (`inputs/corpus.json:238-284,334-340`). Concrete failures include disconnected transport, missing tools, and lost responses (`inputs/corpus.json:9592-9638,9807-9831`). Consequently, basic-memory is valuable evidence and a human-readable mirror, but it is **not reliable enough to be the sole enforcement store**.

The correction detector reports 2,268 candidates but explicitly warns that it is recall-biased and that 41/41 in an unfiltered smoke sample were false positives (`inputs/corpus.json:10371-10375`). Those candidates cannot be counted as authorization mistakes. The hooks section is detector-broken by the pinned input and is treated as no data. The known-defects file independently shows why model interpretation and single detectors cannot close the loop: seven wrong calls were separated from correct calls only by known-positive controls (`inputs/INPUT-known-harness-defects.md:115-129`), while a successful Databricks response was misclassified from a field-name substring even though the response said `ok: true` (`inputs/INPUT-known-harness-defects.md:58-76`).

**GAP:** The number of repeated authorization prompts, their action classes, and the exact Databricks grant are absent from the distilled fields. Claiming a measured prompt-fatigue reduction from this corpus would be false. The settling experiment is a read-only transcript miner that pairs permission questions by normalized `(action, resource, effect)` fingerprint and counts owner approvals followed by equivalent later questions; it must validate against one known repeated pair and one known distinct-scope pair before reporting counts.

## Store and matching contract

The findings below refer to one concrete minimal design. Its canonical event shapes are:

```json
{
  "kind": "authorization_proposed",
  "grant_id": "authz-<random>",
  "principal": "owner",
  "provider": "claude",
  "session_id_hash": "...",
  "turn_id_hash": "...",
  "request_tool": "mcp__cloud-hub__dbx_jobs_run_now",
  "action": "execute",
  "effect": "external_mutation",
  "resource": {"scheme": "databricks", "authority": "workspace-id", "path": "job/123"},
  "environment": "production",
  "data_classes": ["job-metadata"],
  "limits": {"uses": 1, "max_cost_usd": 0},
  "delegation": {"subagents": false, "providers": ["claude"]},
  "expires_at": "2026-07-19T18:00:00Z",
  "request_fingerprint": "sha256:...",
  "status": "pending"
}
```

```json
{
  "kind": "authorization_granted",
  "grant_id": "authz-...",
  "proposal_event_id": "...",
  "scope_fingerprint": "sha256:...",
  "owner_signal": {"type": "native_permission_choice", "evidence_hash": "sha256:..."},
  "status": "active",
  "granted_at": "..."
}
```

```json
{
  "kind": "authorization_used",
  "grant_id": "authz-...",
  "tool_use_id": "...",
  "request_fingerprint": "sha256:...",
  "match": "subset",
  "result_event_id": "...",
  "result_status": "success|failure|unknown"
}
```

Revocation, expiry, denial, supersession, and migration are new append-only events referencing `grant_id`; earlier records are never edited. The current projection is derived by folding events in sequence order. Secrets and raw credentials never enter this store. Resource identifiers needed for matching are normalized before the existing path redactor, while a keyed or salted digest preserves equality for sensitive IDs. The salt belongs in the OS credential store, not in the ledger.

The evaluator implements set containment, not semantic similarity:

```text
deny/revocation match?             -> DENY / do not reuse
no active grant?                   -> ASK once; create pending proposal
requested principal != owner?      -> ASK (peer cannot grant)
requested action/effect not subset -> ASK with scope delta only
resource not subset                -> ASK with scope delta only
environment/data/destination drift -> ASK with scope delta only
limits or expiry exceeded          -> ASK with scope delta only
delegation exceeds caveat          -> ASK with scope delta only
otherwise                          -> ALLOW and append authorization_used
```

No branch asks an LLM whether a grant “basically covers” the action.

## Findings — inferred-surprise first

### Finding 1 — Authority is an attenuating capability, never a remembered vibe

**Improvement:** Add typed, append-only authorization receipts with explicit negative space. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

**What it is:** Store the smallest reusable unit of authority as `(principal, action, effect, resource, environment, data class, destination, limits, delegation, time, provenance)`. Later requests may consume a grant only when every requested dimension is equal to or narrower than the grant. Missing fields default to the restrictive value: `environment=unknown`, `delegation=false`, `external_mutation=false`, `duration=once`, `resource=exact`. A grant can be attenuated for a child task; it can never be widened automatically.

**Why-inferred:** The owner asked for less re-asking and simultaneously prohibited overreach. Local memory contains the explicit authorization scope string `user:design:read+write` and durable negative decisions (“do not re-suggest”), while the Databricks note's actual scope is unavailable (`claude/hooks/recall-inject/index/recall_index.json:6467-6492,6575-6588,6726-6747`). Treating these as a single free-text preference would erase exactly the boundaries the owner cares about. The known-defects incident also proves that model-level interpretation of a successful Databricks response can be confidently wrong (`inputs/INPUT-known-harness-defects.md:65-76`).

**How-to-build:**

1. Add pure `normalize_request(event) -> Scope` adapters for Bash/PowerShell, file tools, MCP tools, external messages, deploys, spending jobs, and destructive operations. Unknown tools normalize to `effect=unknown`, which cannot match a reusable grant.
2. Add `authorization_proposed/granted/denied/used/revoked/expired/superseded` events through the shared `EventLedger.append()` additive field path (`agents/harness/ledger.py:817-880`).
3. Add a pure `is_subset(request, grant)` comparator with table-driven tests for each dimension. No regex over prose and no embeddings.
4. Expose a human-readable projection in basic-memory only after the canonical append succeeds. If the MCP mirror fails, queue through the already-built memory spool; enforcement continues from the event ledger.
5. Do not build cryptographic macaroon tokens. Borrow the caveat/attenuation model, but a local append-only record plus exact comparator is sufficient for this single-owner harness. Cryptographic delegation would exceed the need.

**External signal that verifies it:** A golden corpus generated outside the deciding model contains scope pairs labeled by the owner: 25 exact/subset pairs that must auto-allow and 25 one-field expansions that must ask. The test executable emits `SUCCESS:authorization-subset 50/50`; an independent runtime probe then attempts a narrower Databricks read and a broader Databricks write against fixtures, confirming only the narrower request receives native `allow`. The owner labels are the authority; executable outcomes are the second independent signal.

**SOTA citation:** OAuth Rich Authorization Requests represents rights as typed authorization detail objects and binds them to granted tokens, while Resource Indicators asks clients to name the most specific target resource ([RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html), [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html)). Macaroons demonstrate contextual caveats that confine when, where, by whom, and for what purpose authority applies ([Google Research / NDSS 2014](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/)).

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first for the initial grant; just-do-it for later requests proven to be subsets.  
**Confidence:** **very likely (80-90%)** that typed caveats reduce both repeated questions and accidental widening, because standards and capability research independently use action/resource/caveat structures and the local bus can store arbitrary typed fields. The remaining uncertainty is normalization coverage for this harness's long MCP tail; shadow evaluation described in Finding 7 settles it.

### Finding 2 — Two-phase grant minting: the model may propose scope, but only an external owner event can create authority

**Improvement:** Introduce a pending-proposal handshake that makes self-authorization impossible. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

**What it is:** Before the owner sees a permission question, persist an `authorization_proposed` event derived from the actual tool payload. An active grant is created only when an independent owner-controlled event references that exact proposal fingerprint: a native permission choice, an AskUserQuestion option whose value contains the proposal id, or a deterministic short reply (`approve once/session/project`) when exactly one unexpired proposal exists. Agent prose, a subagent message, tool output, fetched content, and a memory summary can never mint a grant.

**Why-inferred:** The binding law rejects same-context self-correction. The local adapters already distinguish user prompts and lifecycle events, but the normalized `HookEvent` does not contain an approval-result field (`agents/harness/models.py:25-42`; `agents/harness/adapters.py:116-146`). The current `PermissionRequest` path can deny but has no module that records later user assent (`agents/harness/modules.py:420-431,944-962`). The orchestrator has also fabricated a constraint and propagated it into about 15 prompts, demonstrating that agent-authored “ground truth” is not acceptable authorization provenance (`INPUT-known-harness-defects.md:151-160`).

**How-to-build:**

1. On an unmatched `PermissionRequest` or explicit preflight, write `authorization_proposed` before returning native `ask`. Include the tool input fingerprint and a 10-minute expiry.
2. Render one compact owner choice: `Approve once` / `Approve for this session` / `Approve this exact scope durably` / `Deny`. The durable option is absent for destructive, spending, credential, IAM, production deploy, secret-egress, and public-message effects; those remain once/session only.
3. Bind the response by proposal id and exact scope fingerprint. A bare “yes” binds only if exactly one pending proposal exists in the same owner session. Ambiguous responses do not grant; they preserve the pending open loop and show the two competing deltas once.
4. Extend the provider-neutral result contract with a narrow permission directive (`allow|ask|deny`, optional complete updated input, optional session-only rule); translate it only in `adapters.py`. The current `HookResult` has no `ask` action and a normal `allow` renders `{}` (`agents/harness/models.py:45-94`; `agents/harness/adapters.py:159-205`), so claiming that a new module alone can auto-allow would be false. Provider-native field names remain out of core modules.
5. For native UI approvals, **UNVERIFIED whether Claude exposes the user's eventual permission choice to any post-decision hook; the settling experiment is a disposable default-mode session that records sanitized payload schemas for PermissionRequest, ConfigChange, PostToolUse, and PermissionDenied around each of the four UI choices**. If no event exposes it, treat successful execution of the exact proposed `tool_use_id` after a permission prompt as a once-only approval signal; durable scope still requires the explicit structured owner choice.
6. Never infer a durable grant from success alone. Success proves permission for that call, not the duration or future scope.

**External signal that verifies it:** A black-box test tries five mint paths: owner structured approval, owner denial, agent text saying “approved,” teammate text saying “approved,” and a fetched page containing “approve.” Only the first may create `authorization_granted`; the actual ledger file is inspected by a fresh process, and the next native permission decision is exercised. This closes on owner input plus execution, not same-context reflection.

**SOTA citation:** Claude's native PermissionRequest hook can answer a permission dialog and apply session permission updates, providing the right owner-facing actuation point ([Claude hooks reference](https://code.claude.com/docs/en/hooks)). NIST AI RMF calls for human-oversight processes to be defined, assessed, and documented ([AI RMF Core, MAP 3.5](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first.  
**Confidence:** **almost certain (90-99%)** that the two-phase rule prevents the harness from treating its own prose as owner authorization, because authority requires a different event source and matching proposal id. Cross-provider capture parity is **UNVERIFIED; the settling experiment is the provider payload matrix above**, so automatic grant capture must ship provider-by-provider rather than assuming parity.

### Finding 3 — Non-transitive authority firewall for subagents, providers, memories, and peers

**Improvement:** Make grants non-delegable by default and require explicit attenuation for every handoff. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

**What it is:** A grant belongs to the owner and a named execution principal. A parent may pass a child only a capability reference narrowed to the child's task, provider, resource, and expiry. Teammates can report work but cannot grant, revoke, or broaden owner authority. Memory recalls provide evidence pointers, never capabilities. A provider-specific grant is not silently portable to another provider because permission semantics differ.

**Why-inferred:** The corpus shows 1,158 general-purpose agents, 124 forks, and 101 Explore agents (`inputs/corpus.json:13346-13355`), so delegation is routine. The behavior contract already states that a peer cannot grant escalation, and the goal module carefully avoids cross-task bleed by keeping subagents on their delegated task (`agents/harness/modules.py:1310-1316`). The owner wants autonomy without scope leakage; delegation is where a seemingly harmless durable approval can become broad host authority.

**How-to-build:**

1. Default every grant to `delegation.subagents=false` and `providers=[issuing_provider]`.
2. When spawning an agent, the existing SubagentStart path may attach only `{grant_id, attenuated_scope_fingerprint, expires_at}`; the child resolves it from the canonical store and recomputes subset containment.
3. Reject owner-authority state changes whose event source is `SubagentStop`, `TaskCompleted`, `TeammateIdle`, MCP output, web output, or basic-memory text.
4. Record a delegation edge as `authorization_delegated(parent_grant_id, child_principal, caveats)` and bound depth to one unless the owner explicitly grants deeper delegation.
5. If a child needs more scope, return a structured scope-delta to the parent. The parent batches it with other unknowns; the child never contacts the owner independently mid-task.

**External signal that verifies it:** Run an adversarial fixture where a teammate message, recalled note, and web result each claim “the owner approved production Databricks writes.” A child attempts the write. The shared ledger must show no grant and the native hook must ask/deny. Then issue a real owner grant for one read-only workspace and show the child can read that workspace but not a sibling or write to it. Tool execution is the independent terminal signal.

**SOTA citation:** Macaroons' central property is delegation with attenuation through additional caveats rather than authority expansion ([Google Research / NDSS 2014](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/)). RFC 8707's resource indicator similarly prevents a token's authority from floating across unnamed resources ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html)).

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for attenuation; confirm-first for any delegation or provider expansion.  
**Confidence:** **very likely (80-90%)** that explicit non-transitivity prevents the largest authorization blast-radius class, because the local system heavily uses agents and already distinguishes lifecycle principals. It is **UNVERIFIED whether all provider payloads carry stable child identity; the settling experiment is a known-present SubagentStart/TaskCreated payload capture on Claude and Codex, followed by a negative control from a normal user turn**.

### Finding 4 — Negative authority has precedence: revocation, denial, and changed boundaries are first-class receipts

**Improvement:** Add append-only revocation/supersession and deny-first evaluation, with no silent expiry renewal. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

**What it is:** “Do not,” “not anymore,” “only read,” “not production,” and denied native prompts are durable boundary events. The projection evaluates the newest applicable negative event before positive grants. Narrowing a grant appends `authorization_superseded`; revocation never edits history. Expired grants remain evidence of a past decision but confer no current authority.

**Why-inferred:** The recall index already preserves “do not re-suggest” and reversed/deferred decisions (`recall_index.json:6726-6775,6858-6869`). Claude's native permission system is explicitly deny → ask → allow ([permissions documentation](https://code.claude.com/docs/en/permissions)). Remembering approvals but forgetting revocations would optimize prompt fatigue at the cost of overreach—the opposite of calibrated trust.

**How-to-build:**

1. Add `authorization_denied`, `authorization_revoked`, and `authorization_superseded` events. Each references an exact grant or a scoped deny fingerprint.
2. Fold projection in sequence order, but evaluate any matching active deny before allow. Store `supersedes` edges so audit can explain why a once-valid grant no longer applies.
3. Parse revocation only through the same two-phase source rules as grants: direct owner/native denial events. A model-authored summary cannot revoke either.
4. Add a low-friction `/permissions`-style view backed by a CLI (`authz list`, `authz revoke <id>`, `authz explain <request-fingerprint>`). Reuse native `/permissions` for native rules; do not build a second graphical settings panel.
5. On ambiguity between a broad old allow and a narrow new deny, deny/ask and surface one sentence naming both event ids. Never resolve by semantic recency guesses.

**External signal that verifies it:** Grant read+write for a test resource, exercise both, then have the owner narrow it to read-only. A fresh process must allow the read and prompt on the write; ledger replay must show the supersession chain. A second test reorders events to confirm sequence and deny precedence deterministically.

**SOTA citation:** Claude's permission engine evaluates deny before ask and allow ([Claude permissions](https://code.claude.com/docs/en/permissions)). RFC 9396 requires the token response to carry the authorization details actually granted, rather than treating the original request as the final authority ([RFC 9396 §7](https://www.rfc-editor.org/rfc/rfc9396.html#section-7)).

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for recording an explicit denial/revocation; confirm-first if natural-language scope is ambiguous.  
**Confidence:** **almost certain (90-99%)** that deny-first supersession is necessary for safe durable grants, because both the native permission model and local durable decisions already encode negative boundaries. The exact natural-language revocation detector's recall is **UNVERIFIED; the settling experiment is an owner-labeled set of real revocation phrasings, so the first release should accept only native denials and explicit structured commands**.

### Finding 5 — Trust promotion is evidence-based and one-way safe: outcomes may suggest a wider lease, never create it

**Improvement:** Add a shadow “promotion candidate” calculation based on externally verified uses; do not auto-broaden authority. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

**What it is:** Exact repeated owner approvals and successful outcomes can justify offering a compact scope promotion—for example, from one-use to session scope—but cannot themselves widen the grant. Failures, owner corrections, denials, and rollback events lower or reset the candidate. Promotions are suggestions attached to the next otherwise-necessary prompt, never unsolicited interruptions.

**Why-inferred:** Prompt fatigue calls for learning from repeated choices, while trust calibration rejects equating success with permission. The corpus contains 1,329 AskUserQuestion calls (`inputs/corpus.json:134-140`) but does not identify their topics. The event ledger already records verified tool outcomes and failures (`agents/harness/modules.py:1048-1077,1170-1194`). This allows reliance to be calibrated from external results without installing a trained critic.

**How-to-build:**

1. For each exact scope fingerprint, count owner approvals, successful terminal receipts, denials, failures, rollbacks, and corrections.
2. In shadow mode, mark a promotion candidate only after a conservative configurable threshold such as three owner approvals and three successful executions with no deny/correction. **UNVERIFIED whether three is the right threshold; the settling experiment is offline replay over owner-labeled repeated-grant sequences comparing false-promotion rate across thresholds 2-10**.
3. Never show a separate promotion notification. If a future ask is already required, add one option: “You approved this exact scope N times; approve for this project?”
4. Never promote across action, effect, resource authority, environment, destination, data class, cost, or delegation dimensions. Only duration/use-count can be proposed automatically.
5. A promotion remains confirm-first and produces a new granted event superseding the shorter lease.

**External signal that verifies it:** Offline replay computes candidates from immutable ledger events; a separately written owner-labeled oracle grades true/false promotions. Live canary then exposes suggestions without auto-allowing and measures owner acceptance/rejection. No model judges its own reliability.

**SOTA citation:** Appropriate reliance is outcome-graded: accept correct assistance and reject incorrect assistance; explanations alone often increase acceptance regardless of correctness ([Bansal et al., CHI 2021](https://www.microsoft.com/en-us/research/publication/does-the-whole-exceed-its-parts-the-effect-of-ai-explanations-on-complementary-team-performance/)). The 2024 synthesis argues explanations help only when they support verification ([Fok & Weld, AI Magazine 2024](https://onlinelibrary.wiley.com/doi/full/10.1002/aaai.12182)).

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for shadow scoring; confirm-first for every promotion.  
**Confidence:** **likely (55-80%)** that promotion suggestions reduce repeated prompts without widening authority silently, because they piggyback on already-required asks and use terminal outcomes. The benefit magnitude is uncertain because authorization-specific ask counts are absent; the A/B experiment in Finding 7 settles it.

### Finding 6 — Permission decisions happen before action and produce one compact scope delta, not a mid-task interrogation

**Improvement:** Put authorization lookup at task preflight and native PermissionRequest, batch unknown scopes, and explain only the delta. **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The owner UI and allow/ask actuation are native; the typed lookup and batching policy are the small built portion.

**What it is:** Use the native `PermissionRequest`/PreToolUse decision point and existing front-loaded clarification policy. At the first actionable boundary, collect all currently foreseeable unmatched scopes and ask one question with 2-3 mutually exclusive scope choices. Later equivalent actions reuse receipts silently. A changed request says only what changed: “Prior grant: read job 123 in workspace A. New request adds run + production. Approve once?”

## Anti-overfit gate and architecture decision

All eight proposals ride existing buses:

- Shared dispatcher events: `UserPromptSubmit`, `PermissionRequest`, `PermissionDenied`, `PreToolUse`, `PostToolUse`, and task/subagent lifecycle.
- Shared append-only event ledger for canonical typed receipts.
- Native Claude permission decision output for actuation.
- Existing basic-memory + memory spool for readable semantic mirroring, never enforcement.
- Existing open-loops/OPEN-THREADS behavior for pending authorization threads.
- Existing terminal/shadow sink and known-positive controls for evaluation.

No proposal introduces a second orchestration runtime, vector DB/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. No proposal requires a seventh hook. The `AuthorizationModule` folds into the existing shared dispatcher; the open-loop linkage folds into the existing consolidated manifest. This passes the anti-overfit gate.

The radical alternative—an external authorization daemon issuing cryptographic capabilities—was rejected. It would be **BUILD-LARGE**, duplicate the shared ledger/dispatcher, add a runtime failure mode, and solve multi-party decentralized trust that this single-owner local harness does not currently have. Macaroon-style caveats are retained as a data-model insight without importing their runtime.

The incremental alternative—write “the owner trusts Databricks” to basic-memory and tell agents to search first—was also rejected. Search is fallible (13/357 failures; `inputs/corpus.json:271-276,9807-9831`), recall matching is lexical (`recall-inject/inject.py:269-303`), and free text cannot prove subset containment. It would reduce some re-asking but create unbounded overreach risk.

The native-only alternative—persist broad Claude allow rules—was rejected as the full solution. Native rules are an excellent enforcement endpoint and deny-first backstop, but they are tool/command oriented, provider-specific, and do not by themselves carry owner provenance, effect/data/destination caveats, supersession history, task linkage, or cross-provider audit. Use native rules only for narrow derived session updates, never as the source of truth.
