# A097 — coherence audit: hooks versus behavior contracts / silent override

Date: 2026-07-19 (UTC)  
Subject: unpacked read-only bundle at `/local_disk0/codexwork/bundle/claude`  
Unit scope: all `~/.claude/hooks/**/*.py` versus `~/.claude/CLAUDE.md` and the imported `~/.claude/AGENTS.md` behavior contract  
Mutation policy: subject remained read-only; only this artifact was written

## Executive result

**One confirmed runtime conflict exists.** The live reverse-engineering backend auto-launch hook denies an ordinary MCP analysis call while its backend is starting, down, low on RAM, or intentionally manual-only. The behavior contract says non-dangerous guidance must be injected and must not block. The hook wins at runtime because it returns Claude Code's `PreToolUse` `permissionDecision: "deny"` before the tool executes. The result is a true silent override: in exactly those states, the model never gets an opportunity to obey the contract for that attempted call.

Confidence in this finding is **almost certain (90-99%)**, based on four independent signals: the active `settings.json` registration, the enabled deny flags in `backends.json`, an executable repository test that exercised the deny branch successfully, and the official Claude Code hook reference defining `permissionDecision: "deny"` as cancellation of the tool call. The residual 1-10% is version/environment risk: this Linux bundle cannot launch the owner's installed Windows Claude Code binary to observe a real interactive transcript.

No second current conflict met the bar. I found several superficially similar blockers, but they either protect dangerous actions, implement an explicit permission boundary, default to warning-only, are not live-wired, or run at an event where exit 2 cannot undo/block the action. Those rejected candidates are documented below so a later unit does not repeat the work.

### Runtime semantics: independent external reference

The current official [Claude Code hooks reference](https://code.claude.com/docs/en/hooks) states that `PreToolUse` runs before a tool call and can block it; it also states that a nested `hookSpecificOutput.permissionDecision` of `"deny"` cancels the call and returns the reason to Claude. The same reference states that `PostToolUse` cannot block because the tool has already run. This is mechanically independent of both the hook source and its tests.

## Finding 1 — active RE auto-launch denial silently overrides inject-only contract

### Contract text, verbatim

`/local_disk0/codexwork/bundle/claude/AGENTS.md:64-70`:

> ## 6. Block only dangerous; inject for everything else
>
> - **Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code,
>   force-push to main without explicit approval.
> - **Exit 0 + additionalContext (inject):** all other guidance (routing, reminders, goal

The precedence section reinforces rather than weakens this. `AGENTS.md:121-127` ranks the user's instruction/permission system first, safety rules second, and this cross-tool contract third; no project governance or plugin rule is identified here that reclassifies a down analysis backend as a safety hazard.

### Concrete collision

1. Claude attempts a matched ordinary analysis call such as `mcp__ghidra-mcp__list_methods`, `mcp__ida-pro-mcp__...`, or `mcp__binary-ninja-mcp__...`.
2. The relevant backend port is down. For IDA/Ghidra the hook launches it; for Binary Ninja `auto_launch` is false and the hook routes to manual startup.
3. If the port is not ready during the brief wait, the hook emits `permissionDecision: "deny"` and asks for a later retry.
4. The contract requires non-dangerous routing/readiness guidance to use `additionalContext`, not a denial. The attempted MCP call is analysis/readiness work, not a destructive git operation, secret write, force-push, or other irreversible mutation.
5. Claude Code cancels that attempt before execution. Thus the hook's decision wins; the contract's inject-only instruction cannot affect that call.

The collision is deterministic once the backend-down condition is true. Whether the owner's backend was down at the exact instant of this remote audit is **UNVERIFIED; experiment to settle it:** on the Windows host stop one configured RE backend, start `claude --debug-file <path>`, invoke one matched MCP analysis tool, and inspect the debug record for the hook output and canceled tool call. That environmental fact is not required for the code/config conflict: the repository test exercises the exact state transition without launching a real backend.

### Which side wins at runtime — verified, not assumed

**The hook wins.** Evidence is mechanically independent:

1. **Live registration:** `settings.json:195-203` registers `re-autolaunch/autolaunch.py pretool` for the three RE MCP namespaces. This is not a dormant source file.
2. **Enabled configuration:** `re-autolaunch/backends.json:12-13` sets both `"deny_while_starting": true` and `"deny_when_unlaunchable": true`. IDA and Ghidra are configured launchable at `:16-31`; Binary Ninja has `auto_launch: false` at `:33-39`.
3. **Executable behavioral test:** running `python hooks/re-autolaunch/test_autolaunch.py` produced `ALL PASS`, including `run down+still-starting -> spawn + DENY with retry msg`, `run BN down -> deny + NO spawn`, `low-RAM -> NO spawn + OOM-avoid deny`, and `wait-branch ... -> deny`. The assertions for the first case require `permissionDecision == "deny"` at `test_autolaunch.py:317-329`; the manual backend assertions require the same at `:359-379`.
4. **Provider runtime specification:** the official [Claude Code hooks reference](https://code.claude.com/docs/en/hooks) defines nested PreToolUse `permissionDecision: "deny"` as canceling the tool call and feeding the reason back to Claude. It also says PreToolUse runs before permission evaluation, so an allow rule does not rescue a denied call.

Confidence that the hook, rather than the prose contract, controls the attempted call is **almost certain (90-99%)**, based on those four signals. This is stronger than inferring behavior from a return code or comment.

### Minimal resolving edit

Change only these two values in `re-autolaunch/backends.json:12-13`:

```json
"deny_while_starting": false,
"deny_when_unlaunchable": false
```

No Python edit is needed: `_disposition()` already emits `additionalContext` when each flag is false (`autolaunch.py:411-412`), and the test already covers that behavior at `test_autolaunch.py:337-357`.

This edit is **almost certain (90-99%)** to resolve the coherence conflict because it selects an existing tested inject path and changes neither backend launch logic nor MCP wiring. The remaining risk is whether allowing the original call to proceed while cold-start is incomplete produces a noisy connection failure; the current tool-result sentinel is live at `_dispatch/manifest.json:160-168` and can report such a failure without converting readiness guidance into a permission gate.

Anti-overfit gate: **passes**. This is a two-value edit on the existing hook/config bus. It adds no second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
