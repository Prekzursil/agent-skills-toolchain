# T006 — Competitive teardown: Zed

**Unit:** T006  
**Research date:** 2026-07-19 UTC  
**Subject:** Zed's native agent, external-agent/ACP shell, context, tools, permissions, customization, multi-agent operation, and verification surfaces  
**Scope:** competitive teardown only. No subject configuration or code was changed. The only written file is this artifact.

## Executive judgment

Zed is not a better replacement agent runtime for this owner. It is a better *interactive control plane around an agent runtime* in four specific ways: it makes tool availability and approval separate concepts; gives terminal commands an OS-enforced filesystem/network boundary; binds agent edits to visible restore checkpoints and hunk-level review; and treats independent threads/worktrees as first-class, recoverable UI objects. Zed's actual native loop is deliberately conventional: compact if required, stream a model completion, execute parallel tool calls, put their results back into the conversation, repeat until no tool results remain, with retry/cancel/refusal handling around that loop. Current source implements exactly that sequence in `Thread::run_turn_internal` ([source, lines 2702-3048](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2702-L3048)).

The right conclusion is therefore **evolution, not replacement**. This is **very likely (80-90%)**, because (1) the owner already has the stronger parts Zed lacks—cross-session semantic memory, hundreds of skills, a broad lifecycle hook bus, and deeper provider-native multi-agent machinery—and (2) the valuable Zed ideas can ride existing Claude/Codex settings, hooks, worktree events, and the shared dispatcher. The residual uncertainty is operational: the live Windows subject was unavailable on this Linux node, so config-presence and static bundle evidence could not be paired with live behavior for every proposed setting.

The most important anti-copy finding is that Zed does not mechanically verify task correctness. Its diagnostics and terminal tools make verification easy, but no documented turn-end gate requires a fresh test/diagnostic receipt before declaring completion. Copying Zed wholesale would discard the owner's richer verification ambitions while retaining model discretion at the decisive point.

## 1. System shape and agent loop

Zed now exposes three “agent paths”:

* **Zed Agent:** Zed owns model configuration, native tools, agent profiles, tool permissions, Skills, Instructions, MCP, thread persistence, and review UI.
* **External Agent:** an ACP process such as Claude, Codex, OpenCode, Copilot, Cursor, or Pi owns its runtime/auth/model/native configuration; Zed hosts the session UI and may forward MCP.
* **Terminal Thread:** a CLI/TUI owns everything and Zed organizes its terminal-backed thread.

This boundary is explicit in [Agents](https://zed.dev/docs/ai/agents) and [External Agents](https://zed.dev/docs/ai/external-agents). It is a strong design choice: Zed is willing to be the control plane without pretending that a hosted external agent obeys Zed Agent settings. External-agent profiles and Zed Skills do not automatically apply; MCP and tool permission behavior depends on the bridge.

### Native loop, concretely

The native Zed loop is a streaming tool loop, not a planner/executor graph:

1. `Thread::send` appends a user message and starts a turn ([thread source, lines 2470-2505](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2470-L2505)).
2. The turn cancels any prior in-flight generation, captures enabled tools, and spawns `run_turn_internal` ([lines 2638-2699](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2638-L2699)).
3. Every loop iteration first runs automatic compaction if the threshold says so; compaction itself is a separate streamed model request ([lines 2712-2786](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2712-L2786), [lines 3082-3217](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L3082-L3217)).
4. It re-reads model and enabled tools between tool-call rounds, meaning a mid-turn model/profile/tool toggle affects the next boundary ([lines 2788-2801](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2788-L2801)).
5. It streams completion events and races model events, tool completions, and cancellation. Tool tasks are collected in `FuturesUnordered`, so independent calls can execute concurrently ([lines 2815-2905](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2815-L2905)).
6. It drops the model stream before waiting for tools, explicitly releasing a concurrency permit so a tool-spawned subagent cannot deadlock waiting for a model permit ([lines 2920-2937](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2920-L2937)). This small resource-lifecycle detail is excellent and worth testing in our provider bridges.
7. It records every tool result and loops with `CompletionIntent::ToolResults`; if there are no results, the turn ends ([lines 2993-3048](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2993-L3048)). Tool uses and results are serialized back as assistant tool-use plus user tool-result messages; empty tool output is normalized to a sentinel string to satisfy provider APIs ([lines 650-710](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L650-L710)).

Errors are retried through a specific completion-error path, cancellations are raced throughout, and configured refusal fallback can switch the model once ([lines 2940-2990](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L2940-L2990)). There is no evidence here of a trained critic, graph scheduler, or durable-execution engine. That restraint is a feature under the anti-overfit gate.

### Compared with ours

The basic loop is not a capability gap. Claude Code and Codex already run provider-native tool loops, and replacing them with Zed Agent would lose native provider features while adding another agent runtime. Zed itself acknowledges this by offering ACP and terminal paths instead of forcing its runtime ([Agents](https://zed.dev/docs/ai/agents)).

Zed's resource-permit release before subagent execution is a possible edge we have not verified. **UNVERIFIED — experiment: run eight parent completions that each spawn model-using children under the configured Codex concurrency cap, capture semaphore/queue timings, and test whether parents retain a scarce completion permit while awaiting children.** A recommendation based on it appears below with the same tag.

## 2. Context management

### What Zed does

Zed combines explicit, model-driven, and compressive context:

* `@` mentions can add files, directories, symbols, previous threads, Skills, diagnostics, branch diffs, and fetched URLs. Buffer/terminal selections can be attached, pasted multiline buffer code becomes file-aware context, and supported models accept images ([Agent Panel, Adding Context](https://zed.dev/docs/ai/agent-panel#adding-context)).
* Each thread has its own context window and conversation history. Zed advises a new thread per distinct task ([Zed-hosted models, Context Windows](https://zed.dev/docs/ai/subscription#context-windows)).
* Automatic compaction defaults to 90% and accepts a percentage, absolute token count, or negative remaining-token threshold. `/compact` forces it ([Agent Settings, Automatic Compaction](https://zed.dev/docs/ai/agent-settings#automatic-compaction)).
* A compaction summary replaces earlier messages in model context but remains inspectable as a “Context Compacted” entry. Small-context models under 80,000 tokens receive a warning instead of automatic compaction ([Agent Panel, Token Usage and Compaction](https://zed.dev/docs/ai/agent-panel#token-usage-and-compaction)).
* Thread token use is visible, archived threads remain searchable/restorable, and a prior thread can be mentioned into a new one ([Agent Panel](https://zed.dev/docs/ai/agent-panel), [Parallel Agents](https://zed.dev/docs/ai/parallel-agents)).

Zed's implementation inserts a `Message::Compaction(Summary)` into the message sequence and sends “The previous conversation was compacted. Use this summary as context” when building a request ([thread source, lines 199-234](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L199-L234)). This is ordinary lossy summarization with visible provenance, not memory.

### Compared with ours

Our Claude config already sets 90% compaction and a one-million-token window (`/local_disk0/codexwork/bundle/claude/settings.json:18,686,697`); Codex already exposes detailed context/token fields in its status line (`/local_disk0/codexwork/bundle/codex/config.toml:42-63`) and enables request compression (`:82-87`). We also have PreCompact/PostCompact hook lanes (`claude/settings.json:380-401`; `codex/config.toml:412-447`). Zed's threshold is not a gap.

Zed is better at **context provenance UX**: explicit chips/mentions, visible compacted summaries, and easy cross-thread references. A CLI harness cannot port the UI literally. It can port the invariant: every injected context block declares type, source, scope, and freshness, and compacted summaries stay inspectable. This aligns with the known defect where an orchestrator-authored false constraint propagated to ~15 agents (`INPUT-known-harness-defects.md:150-161`).

## 3. Memory and continuity

Zed persists threads, detailed summaries, token usage, project snapshots, profiles, subagent context, and sandbox grants in its thread store ([thread-store source](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread_store.rs#L62-L170)). It can archive, fuzzy-search, restore, and import supported external-agent sessions; worktree-backed archived threads can reconstruct their worktree ([Parallel Agents, Thread History](https://zed.dev/docs/ai/parallel-agents#thread-history)). That is good *episodic continuity*.

The controlled absence test above found no first-party cross-thread semantic retrieval or autonomous durable fact memory. Users can emulate durable knowledge with always-on `AGENTS.md`, Skills, project files, or an MCP memory server, but those are instruction/context mechanisms, not a built-in learned memory plane.

Our harness is stronger here: `/local_disk0/codexwork/bundle/codex/AGENTS.md:62-85` names `basic-memory` as the cross-tool canonical semantic store and explicitly distinguishes it from Codex native memories; Claude has `basic-memory` allowed at `claude/settings.json:47`. The audit claim that a second native Codex memories plane is also active is supported by `codex/config.toml:103` (`memories = true`). Copying Zed would be a regression in semantic continuity; copying its restraint would be useful. One canonical semantic store plus objective event history is less ambiguous than multiple writers.

Zed's thread/worktree restoration is **likely (55-80%)** to reduce “where did that agent's changes go?” recovery time if adopted as a presentation invariant, based on its persisted thread↔worktree association and automatic restore behavior. The exact magnitude is **UNVERIFIED — experiment: sample 30 interrupted or resumed multi-agent tasks, compare time-to-locate transcript and worktree before/after adding stable thread/worktree IDs to the existing monitor/ledger.**

## 4. Tools and MCP

### Built-in tool set

Zed Agent provides purpose-specific project tools—read/list/grep/path search, diagnostics, edit/write/move/copy/delete/create-directory, terminal, fetch/search web, Skills, and `spawn_agent` ([Tools](https://zed.dev/docs/ai/tools)). The `diagnostics` tool queries editor/LSP errors and warnings for one file or the project. The terminal opens a fresh shell process per invocation. Narrow file APIs reduce quoting and shell dependence compared with expressing all mutations in Bash.

This is relevant to the corpus: Bash has 108,121 calls and 6.0% errors, including 1,631 unmatched-single-quote EOF fingerprints; PowerShell has 19,181 calls and 10.6% errors; Glob has 13.3% errors, 592 of them `ENAMETOOLONG`. Zed's path/search tools do not prove immunity to Windows length limits, but avoiding plugin-expanded command lines and reducing shell serialization attacks the measured failure modes directly.

### MCP lifecycle

Zed supports extension-installed, custom local, and remote MCP servers, including standard OAuth for remote servers ([MCP, Installing Servers](https://zed.dev/docs/ai/mcp#installing-mcp-servers)). Its Settings UI shows a per-server status dot: active servers are green; other states carry diagnostic tooltips ([MCP, Configuration Check](https://zed.dev/docs/ai/mcp#configuration-check)). Profiles can expose only selected servers/tools; MCP permissions use `mcp:<server>:<tool>` keys. Zed can forward configured MCP servers over ACP, while external agents may also read their native MCP config ([MCP, Agent Path Support](https://zed.dev/docs/ai/mcp#agent-path-support)). Server errors are returned directly to the agent and shown to the user ([MCP, Error Handling](https://zed.dev/docs/ai/mcp#error-handling)).

This is materially better than our observed admission behavior. The corpus records 532 Tavily calls at 25.8% error, including 135 “not connected” calls to a dead MCP. A green dot alone would not stop a model from calling a dead server, but Zed's enable toggle, status, profile tool selection, and visible error state form a concrete admission surface. Our Codex config declares 25 servers in the inspected audit and the live config excerpt shows disabled-server fields are possible, yet the dead server remained callable in Claude history.

Zed is not immune to MCP/schema trouble. Its release history fixed Gemini invalid-JSON failures caused by incompatible MCP schemas and incomplete schemas ([v1.4.2 release notes on GitHub](https://github.com/zed-industries/zed/releases)), and the current stable release says Zod/Pydantic-generated MCP schemas were corrected ([latest stable release](https://zed.dev/releases/stable/latest)). This is a reason to copy compatibility testing, not evidence that Zed has solved schemas universally. Our `StructuredOutput` rate—846/3,694, 22.9%, including 294 one-schema fingerprint instances—is substantially worse than Zed's disclosed qualitative bug reports, but the two datasets are not comparable enough to claim a ratio.

### Where Zed is worse

* MCP health is primarily presented to a human. The docs do not describe circuit breaking, exponential quarantine, or automatically removing an unhealthy tool from the next model request. **UNVERIFIED whether current source has an undocumented backoff policy — experiment: run a local MCP fixture that alternates initialize/tool failures, record consecutive `tools/list` exposure and reconnect timing.**
* Error text is sent directly back into model context. That is useful diagnostically but is an injection boundary; Zed's privacy page acknowledges tools/MCP can reach external systems but does not document an output-provenance quarantine ([AI Privacy](https://zed.dev/docs/ai/privacy-and-security)). Our memory-guard ambitions are stronger, though current known defects show heuristic scanners can themselves corrupt truth.
* Zed's built-in `fetch` is not inside the terminal OS sandbox; it is governed only by profiles, permissions, and trust ([Tools](https://zed.dev/docs/ai/tools), [Sandboxing](https://zed.dev/docs/ai/sandboxing)).

## 5. Permission and trust model

Zed separates three layers that our deployed posture currently collapses:

1. **Availability:** an Agent Profile selects model, built-in tools, and MCP tools. Built-ins are Write, Ask, and Minimal; custom profiles can fork these ([Agent Profiles](https://zed.dev/docs/ai/agent-profiles)). A disabled tool cannot be called.
2. **Invocation decision:** `agent.tool_permissions` yields allow, deny, or confirm globally, per tool, and by regex over the relevant input—terminal command, path, URL, query, or Skill path ([Tool Permissions](https://zed.dev/docs/ai/tool-permissions)). Source makes precedence explicit: hardcoded security rule, `always_deny`, `always_confirm`, `always_allow`, tool default, global default. Terminal commands are parsed into subcommands before aggregation; deny on any subcommand wins, confirm on any wins next, and allow requires every subcommand to match ([tool-permission source, lines 208-429](https://github.com/zed-industries/zed/blob/main/crates/agent/src/tool_permissions.rs#L208-L429)).
3. **Execution containment:** terminal actions can run in an OS sandbox that restricts writes and outbound network, keeps Git metadata read-only, and supports one-call, thread, or persistent grants for hosts and paths ([Sandboxing](https://zed.dev/docs/ai/sandboxing)).

The tool-permission source explicitly warns that a bare `rm` regex also matches “storm” and “arms” and recommends word boundaries ([source, lines 241-251](https://github.com/zed-industries/zed/blob/main/crates/agent/src/tool_permissions.rs#L241-L251)). This is directly relevant to our prose-as-code defect. What Zed gets right is the discriminator: terminal rules inspect executable command strings parsed into commands, while file rules inspect paths. It does not scan an arbitrary markdown body for shell substrings. Our four defective detectors instead conflate mention and use (`INPUT-known-harness-defects.md:9-82`).

Current ours is worse by configuration: Claude uses `bypassPermissions`, permits Bash/PowerShell/Edit/Write/Task and broad MCP families, and grants `C:` plus `D:` (`claude/settings.json:26-75`); Codex uses never-approve plus danger-full-access (`codex/config.toml:6-8`). Neither deployed default provides an independent containment boundary.

Zed's Windows story is also weak: OS sandboxing works only inside WSL; native Windows falls back to Git Bash, PowerShell, or `cmd.exe` without equivalent confinement. WSL grants are all-network or no-network, not host-specific ([Sandboxing, Windows](https://zed.dev/docs/ai/sandboxing#windows)). Do not copy the assumption that Zed's sandbox solves this owner's native Windows work.

Project-local Skills load only from trusted worktrees, and the agent cannot edit Skill files/resources without explicit authorization ([Skills, Project Trust and Editing](https://zed.dev/docs/ai/skills#project-local-skills-and-trust)). This is a useful instruction-supply-chain boundary.

## 6. Customization: Instructions, Skills, profiles, tasks, and hooks

### Instructions

Zed supports a personal `AGENTS.md` plus one matching project instruction file from a compatibility list including `.rules`, `.cursorrules`, `.windsurfrules`, `.clinerules`, Copilot instructions, `AGENT.md`, `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`; project instructions override personal conflicts ([Instructions](https://zed.dev/docs/ai/instructions)). Choosing only the first matching project file is simple but can silently ignore other valid instruction files. Our multi-provider harness is stronger when it deliberately composes provider-specific and shared instructions with provenance.

### Skills

Zed adopted the Agent Skills directory format: `SKILL.md` plus optional scripts/references/assets. The system prompt sees only name and description, and the `skill` tool loads the body on demand; user slash invocation is also supported. Project skills override same-named global Skills. Catalog metadata is capped at 50 KB, `SKILL.md` is advised under 500 lines, and project Skills require trust ([Skills](https://zed.dev/docs/ai/skills)). `disable-model-invocation: true` makes deploy/release-type skills manual-only. Skill changes live-reload; catalog changes invalidate prompt cache.

The progressive-disclosure mechanism is good. Our installed-to-used gap—about 355 installed and only 78 invoked—shows that *more Skills* is not the answer. Zed's flat two-root lookup is worse than our richer catalog and plugin ecosystem, but its explicit budget and model/manual invocation bit are valuable governance primitives. Zed's share links embed `SKILL.md` and require the recipient to review and save; no silent install occurs ([Skills, Sharing](https://zed.dev/docs/ai/skills#sharing-skills)).

### Profiles

Profiles put model and tool bundle together, allowing a read-only Ask thread, no-tool Minimal thread, or narrowly MCP-specific thread. This is better than our global bypass/full-access defaults. Profiles do not apply across the ACP boundary unless an external agent implements an equivalent, a limitation Zed documents rather than hides ([Agent Profiles](https://zed.dev/docs/ai/agent-profiles)).

### Tasks and hooks

Tasks live globally or in `.zed/tasks.json`, take structured `command` plus `args`, environment/cwd/reveal policy, and can interpolate editor variables. The docs specifically recommend argv arrays for space-containing paths rather than shell-quoted strings ([Tasks](https://zed.dev/docs/tasks)). That is directly applicable to 1,631 Bash unmatched-quote failures.

Zed's documented native hook bus is far weaker than ours: only `create_worktree` is supported, and it launches matching tasks after a linked worktree is made with `ZED_WORKTREE_ROOT` and `ZED_MAIN_GIT_WORKTREE` ([Tasks, Hooks](https://zed.dev/docs/tasks#hooks)). Our Claude settings alone register SessionStart, UserPromptSubmit, PreToolUse, Pre/PostCompact, and many other hook families (`claude/settings.json:81-401`), with a shared dispatcher plus local dispatcher. Zed cannot replace that lifecycle bus.

## 7. Multi-agent support

Zed has two distinct multi-agent mechanisms.

### Parallel first-class threads

The Threads Sidebar can run multiple independent Zed Agent, ACP external-agent, and terminal threads. Each has its own context and history, can use a different agent, and can be grouped by project. Threads can share a checkout or be manually placed in linked Git worktrees. New worktrees start detached; archiving can save Git state, remove the worktree from disk, and restoration recreates it ([Parallel Agents](https://zed.dev/docs/ai/parallel-agents)). Multi-root projects let one thread span repositories.

This is excellent operator ergonomics, but it is not automatic conflict avoidance. The user must choose isolation if two threads might edit the same files. Our harness already has worktree event machinery and native provider isolation, though the pinned audit claim says the current WorktreeCreate adapter is stale (`audit-findings/D22.md:7-18`). Because audit findings are claims, the settling experiment is to create one disposable native worktree and capture the adapter payload plus target resolution before enabling wider automation.

### Model-spawned subagents

`spawn_agent` gives the child a separate context window and the parent's tools. Source instructions state that a new child does **not** see parent conversation history, so the parent must send a self-contained task; it should use disjoint write sets and returns only the child's final message plus a reusable `session_id` ([spawn-agent source, lines 13-46](https://github.com/zed-industries/zed/blob/main/crates/agent/src/tools/spawn_agent_tool.rs#L13-L46)). The implementation creates or resumes a subagent, sends one message, awaits completion, records telemetry, and returns `{session_id, output}` ([lines 128-220](https://github.com/zed-industries/zed/blob/main/crates/agent/src/tools/spawn_agent_tool.rs#L128-L220)). Zed shipped this in March 2026 specifically for parallelism and context management ([0.227.1 release](https://zed.dev/releases/stable?b=71)).

Current source also defines independent sibling-thread requests with optional agent, model, new-worktree flag/name, and base ref ([thread source, lines 776-824](https://github.com/zed-industries/zed/blob/main/crates/agent/src/thread.rs#L776-L824)).

Compared with ours, Zed is better at visible thread/worktree lifecycle and heterogeneous agent selection. Ours is stronger at hierarchical collaboration: Codex config enables depth 8 and eight concurrent V2 threads (`codex/config.toml:77-80,101,125-130`), and the shared harness supports messages, waits, interrupts, and richer hook events. Zed's documented child API is essentially spawn/follow-up/final-output, not a team mailbox or deep hierarchy.

Zed's “child receives no parent transcript” default is a useful anti-context-bloat rule. It also makes orchestrator-fabricated premises more dangerous unless delegated facts carry provenance. This owner's D4 incident demonstrates that risk (`INPUT-known-harness-defects.md:150-161`).

## 8. Verification, self-check, and reversibility

Zed offers four strong *affordances*:

1. **Diagnostics:** language-server errors/warnings for a file or project; docs explicitly suggest running it after edits ([Tools, diagnostics](https://zed.dev/docs/ai/tools)).
2. **Terminal verification:** tool docs give `cargo test` and `git diff --stat` as examples ([Tools, terminal](https://zed.dev/docs/ai/tools)).
3. **Edit checkpoints:** every edit-bearing prompt exposes “Restore Checkpoint,” including interrupted generations ([Agent Panel, Checkpoints](https://zed.dev/docs/ai/agent-panel#checkpoints)).
4. **Review:** a multibuffer shows all changed files and allows accept/reject per hunk or whole set; inline file review can do the same ([Agent Panel, Reviewing Changes](https://zed.dev/docs/ai/agent-panel#reviewing-changes)).

Checkpoint reliability is real enough to be a maintained subsystem, not proof of perfection: the current stable release fixed comparison errors that silently hid the restore button ([latest stable release](https://zed.dev/releases/stable/latest)).

Zed does **not** document a mandatory fresh-verification receipt at turn end. The two-signal absence test is: (A) the Tools page describes diagnostics/test invocations as examples (“useful,” “after editing”), not enforced transitions, with the detector control finding the diagnostics tool; (B) Agent Panel completion/review docs describe stop, checkpoint, and hunk review but no test gate, with the detector control finding checkpoint/review. Therefore the scoped conclusion is that Zed's native agent makes self-check possible but leaves it model/user-discretionary.

Our intended design is stronger: the shared dispatcher/ledger and verification skills can bind mutation to evidence. Actual deployment is not yet trustworthy enough to claim victory: the known defects show detectors can invert successful results, and hook telemetry is currently unmeasurable (`INPUT-known-harness-defects.md:63-76,133-147`). Zed's UI reversibility is better than a hidden, fail-open checkpoint hook. Claude Code already has native `/rewind`; an audit claim says the custom edit-checkpoint source incorrectly asserts otherwise and is not wired (`audit-findings/D18.md:42-43,69`), while the bundled custom file indeed says “NO built-in edit-undo” at `claude/hooks/edit-checkpoints/checkpoint.py:2-19`. The official Claude checkpoint documentation linked by the audit is [Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing).

## 10. Things not to copy

1. **Do not replace Claude/Codex with Zed Agent.** This is **very likely (80-90%)** to be a net regression because provider-native hooks, memory, agent hierarchies, and current harness integrations would move behind a less capable native lifecycle surface, while Zed itself treats external agents as first-class.
2. **Do not copy Zed's one-hook customization ceiling.** Our event bus is materially richer; fix telemetry and detector semantics instead.
3. **Do not copy regex rules without semantic field selection.** Zed source itself documents substring hazards. The portable mechanism is command/path-role discrimination plus parsed subcommands, not a larger denylist.
4. **Do not treat checkpoint restore as verification.** Restore is reversibility, not proof. A green diagnostic/test receipt and reviewed diff answer different questions.
5. **Do not adopt Zed's lack of semantic memory.** Retain one canonical `basic-memory` plane. Conversely, copy Zed's restraint by pruning duplicate native/lexical memory writers after parity tests.
6. **Do not assume the Windows sandbox exists.** Zed documents WSL-only containment. Native Windows fallback is unconfined.
7. **Do not trust MCP status UI as a circuit breaker.** A visible red dot helps a person; automated admission must suppress/deny unhealthy tools.
8. **Do not build Zed's editor UI into the harness.** Context chips, review panes, and thread sidebars are product surfaces. Port their data invariants into existing status, ledger, provider UI, and Git workflows.
9. **Do not add any previously rejected architecture.** Nothing here justifies a second orchestration runtime, vector DB/KG, durable-execution engine, trained critic, observability SaaS, or general guardrail framework.

## 11. Recommended sequence

1. Run the P1 native sandbox/profile matrix and change no defaults until Windows behavior is measured.
2. Dump hook schemas, then implement P2 only if the semantic fields exist. Replay all recorded false positives and known-positive destructive cases.
3. Put the dead-MCP admission fixture around the existing liveness lane and implement P3.

This order is **very likely (80-90%)** to address more measured damage per unit of harness complexity than a replacement project: it attacks current broad privileges, false guard decisions, dead MCP calls, and worktree ambiguity before cosmetic UI parity. Evidence is the pinned failure ranking and the fact that every step rides an existing provider/config/hook/MCP/worktree bus.

## 12. Gaps and dead ends

* The Windows subject paths do not exist on this Linux job node. I could inspect only the unpacked bundle. No live Zed installation/version/config was available, so this is a product teardown, not a live bake-off.
* GitHub's recursive-tree API returned HTTP 403. I did not treat that as absence. I instead streamed the public source archive without writing it, validated a known-present `crates/agent/src/thread.rs`, and searched agent/assistant paths for `memory`; this supplied the second controlled source signal described above.
* GitHub HTML rendering of the 8,284-line `thread.rs` obscured some source matches. I fetched the official raw source to stdout for bounded line inspection and cite the corresponding GitHub blob anchors.
* No Zed eval establishes task success, tool reliability, or security versus this owner's harness. Product docs and source establish mechanisms, not comparative outcome rates. Any quantified benefit above is confidence-banded and paired with an experiment.
* Zed's exact MCP reconnect/backoff internals were not exercised. The P3 recommendation therefore does not claim Zed has a circuit breaker; it combines Zed's admission/status concept with our measured dead-server defect.
* Audit findings conflict on the desired custom edit-checkpoint action (restore it versus prune it). I resolved the design direction only provisionally using native Claude checkpoint documentation and the bundled custom source; the parity experiment in P5 is the deciding gate.
* Zed's source contains richer sibling-thread types than the public docs fully explain. I cited only fields visible in current source and did not claim universal availability across agent paths.

## Bottom line

Zed's frontier contribution is a clean control-plane decomposition: **thread-scoped context + explicit tool availability + execution-aware permission decision + OS containment + reversible/reviewable edits + recoverable worktree identity**. Port those invariants selectively. Keep our provider-native loops, one canonical semantic memory, deep agent collaboration, and lifecycle event bus. The ambitious move is not a wholesale rewrite; it is to make the existing minimal architecture enforce the few boundaries Zed gets right, while deleting duplicate checkpoint/memory scaffolding that native facilities have superseded.
