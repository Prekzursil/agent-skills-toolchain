# A037 — coherence audit of `~/.claude/rules/java/hooks.md`

## Executive verdict

The 18-line Java hook rule is not an executable contract in the bundled harness. It names three outcomes—format Java, run Checkstyle, and compile—but the active user settings, the local dispatcher manifest, and the directly wired per-edit checker contain no Java implementation. This is a confirmed configuration/code mismatch, not a conclusion drawn from the corpus hook detector: that detector is explicitly broken and therefore supplies no hook evidence (`inputs/corpus.json:13260-13263`).

The most important defects are:

1. The rule's own load scope includes generic Maven/Gradle build files, so it activates Java-specific advice even where no Java source is in scope (`claude/rules/java/hooks.md:2-6`). That conflicts with the rules architecture's statement that language directories contain language-specific material (`claude/rules/README.md:28-29`).
2. It says to configure both `google-java-format` and Checkstyle (`claude/rules/java/hooks.md:14-18`), while the adjacent Java coding-style rule says `google-java-format` **or** Checkstyle (`claude/rules/java/coding-style.md:9-13`). The same-level rules do not define which meaning wins.
3. `build.gradle.kts` activates both Java and Kotlin hook rules, but the two prescribe different verification thresholds: Java says `compileJava`; Kotlin says full `build` (`claude/rules/java/hooks.md:4-6,18`; `claude/rules/kotlin/hooks.md:3-5,13-17`). AGENTS.md precedence does not resolve two same-level language rules; it requires the collision to be surfaced (`claude/AGENTS.md:115-131`).
4. None of the three named Java checks is wired. Active PostToolUse settings route only the shared dispatcher, Bash output compression, generic per-edit validation, and the local dispatcher (`claude/settings.json:310-355`). The generic per-edit checker handles Python, JavaScript, JSON, YAML, and explicit TS/Rust skips, then silently skips every unknown extension; `.java` has no branch (`claude/hooks/per-edit-check/check.py:151-170`). The local PostToolUse dispatcher manifest likewise has only memory-spool, result-sentinel, and stub-ledger checks (`claude/hooks/_dispatch/manifest.json:144-180`).
5. The rule puts compilation under PostToolUse without defining duration, debounce, project/module selection, failure semantics, or fallback when a wrapper/tool is absent. That is badly specified against the higher-level requirements to send operations expected to exceed 60 seconds through `longrun` (`claude/AGENTS.md:41-49`) and to reserve exit 2 for dangerous operations (`claude/AGENTS.md:64-70`).

The correct disposition is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): replace this rule's current prose and add a small implementation on the existing hook bus**, not a second runtime. A project-aware Java check can reuse the existing Edit/Write PostToolUse route and run consolidated validation once at Stop or explicit verification. This is **likely (55-80%)** to fit within BUILD-SMALL because the current per-edit dispatcher and edit ledger already expose the required event/path primitives (`claude/hooks/per-edit-check/check.py:176-212`; `claude/hooks/edit-validate/record.py:18-36`); the evidence does not establish Windows command discovery, wrapper behavior, or real-project runtime, so the canary experiment in “Resolution design” must settle the remaining size/risk.

## Detailed findings and resolutions

### C1 — STALE: build-file frontmatter over-selects the Java rule

**Exact conflict.** The target's path list includes every `pom.xml`, `build.gradle`, and `build.gradle.kts` (`claude/rules/java/hooks.md:2-6`). The rules design says the language directories contain language-specific tools and examples (`claude/rules/README.md:28-29`). A Maven POM is not proof of Java, and a Gradle Kotlin DSL file is explicitly also selected by the Kotlin hook rule (`claude/rules/kotlin/hooks.md:3-5`).

This is a rule-selection defect, not merely a missing hook. It causes advice to load based on build-system syntax rather than the language actually edited. It is **very likely (80-90%)** that narrowing the rule to `.java` reduces false activation without losing executable discovery, because the hook can inspect nearby `pom.xml`/Gradle files after receiving the edited `.java` path; the evidence is the existing hook input path extraction at `claude/hooks/per-edit-check/check.py:189-212`. The remaining uncertainty is multi-module root discovery; settle it with fixtures for Maven parent/child modules, Gradle multi-project builds, and mixed Java/Kotlin modules.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Change frontmatter to `**/*.java`. In the Java hook implementation, walk upward within the repository boundary to the nearest authoritative wrapper/build root and determine the affected module. Do not infer Java merely from a build file.

### C2 — CONTRADICTION: formatter-or-linter versus formatter-and-linter

**Exact conflict.** The coding-style rule states “`google-java-format` or `Checkstyle` … for enforcement” (`claude/rules/java/coding-style.md:9-13`). The hook rule gives separate formatter and Checkstyle bullets under a configuration directive (`claude/rules/java/hooks.md:14-17`). One permits either tool to satisfy enforcement; the other reads as requiring both behaviors after every edit.

These tools also represent different outcomes in the target prose: mutation (“Auto-format”) versus analysis (“Run style checks”). Treating them as interchangeable in one file and cumulative in another makes compliance untestable. AGENTS.md §10 has no same-level tie-breaker and tells the harness to surface the conflict (`claude/AGENTS.md:129-131`).

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace both tool-centric statements with a single outcome contract:

> After a Java edit, use the repository's canonical formatter when configured. Run the repository's configured Java style/lint task when distinct. Never impose a global style or install a tool. Record FORMAT, STYLE, and COMPILE as separate terminal receipts; an unavailable, unconfigured outcome is `SKIPPED:<reason>`, not `SUCCESS`.

This does not silently choose between the existing same-level rules; it removes the false equivalence and makes both outcomes independently observable.

### C3 — REDUNDANCY: Java and Kotlin rules overlap with different build thresholds

**Exact conflict.** Both frontmatters match `build.gradle.kts` (`claude/rules/java/hooks.md:4-6`; `claude/rules/kotlin/hooks.md:3-5`). The Java rule asks for `compileJava`, while Kotlin asks for `build` (`claude/rules/java/hooks.md:18`; `claude/rules/kotlin/hooks.md:17`). Full Gradle `build` is a broader threshold than Java compilation. The Java rule supplies no evidence that `compileJava` is relevant in a Kotlin-only module; running both prescriptions after the same script edit is redundant fan-out.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Select checks from changed source paths and the project task graph, not from instruction-file overlap. One debounced validator should merge Java/Kotlin changes into one affected-module plan. In a mixed project, run both compile tasks only when discovered project tasks and changed source sets require both.

### C4/C5/C6 — UNENFORCED: every promised Java outcome is missing from the active path

The active user-level registration proves only that generic routes are invoked (`claude/settings.json:310-355`). It does not confer Java behavior on them. Following each route establishes:

- the local dispatcher manifest's PostToolUse list contains only memory spool, tool-result sentinel, and stub ledger (`claude/hooks/_dispatch/manifest.json:144-180`). None formats, lints, or compiles Java.
- its wiring test's independently enumerated expected PostToolUse set likewise contains no Java quality check (`claude/hooks/_dispatch/test_wiring.py:52-63,99-125`).

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the current edit ledger plus consolidated Stop path, or add one Java-aware local check, with these behaviors:

## Resolution design

### Recommended replacement contract

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the current file with a precise, project-aware contract along these lines:

> **Java edit validation**
>
> On an Edit/Write/MultiEdit of a `.java` file, record the changed path and affected build module. Use only repository-declared tooling; never install or impose a formatter.
>
> 1. FORMAT: if the repository defines a canonical formatter/task, format the edited Java file and report its diff/receipt; otherwise `SKIPPED:FORMAT no-project-formatter`.
> 2. STYLE: if the affected module defines a Java style task, run it once per turn; otherwise `SKIPPED:STYLE no-project-style-task`.
> 3. COMPILE: run the affected module's canonical compile/check entrypoint once per turn or before completion. Prefer an existing wrapper. If expected duration exceeds 60 seconds, use `longrun`.
> 4. Emit `SUCCESS:<stage>`, `FAILED:<stage> reason`, or `SKIPPED:<stage> reason` with cwd, argv, duration, and affected module. Ordinary failures inject context; only dangerous actions may block. Hook-internal errors fail open but emit an observable error receipt where the host contract permits.

This replacement resolves tool ambiguity without weakening the three intended outcomes. It also aligns terminal receipts with AGENTS.md §4 (`claude/AGENTS.md:36-39`), long operations with §4a (`claude/AGENTS.md:41-49`), and failure semantics with §6 (`claude/AGENTS.md:64-70`).

### Project discovery order

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Discovery should be evidence-driven and stop at repository boundaries:

1. project-documented or repository script/task explicitly designated as formatter/style/build authority;
2. existing Maven/Gradle wrapper plus configured plugin/task in the affected module;
3. direct executable only if the repository config names it and the executable is already present;
4. otherwise an explicit `SKIPPED` receipt—never installation, network fetch, or invented global defaults.

The exact Maven/Gradle task map is **UNVERIFIED** because no Java project fixtures or skill bodies are in the bundle. The experiment is to build a fixture matrix covering Maven wrapper/non-wrapper, Gradle Groovy/Kotlin DSL, multi-module builds, mixed Java/Kotlin, Spotless/Checkstyle present/absent, and Windows paths with spaces. Only tasks proven by fixture discovery belong in code.

### Cadence and failure semantics

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Do not run full compile after every transient edit. PostToolUse should record/deduplicate and perform only a measured file-local format fast path. Consolidated style/compile should run once at Stop or explicit verification. This follows the existing edit recorder's loop-avoidance rationale—record cheaply, validate once (`claude/hooks/edit-validate/record.py:2-10`)—without copying its current lack of Java support.

It is **likely (55-80%)** that once-per-turn consolidation materially lowers redundant process cost compared with three per-edit commands, because one turn may contain many edits and the existing recorder was explicitly designed to avoid one validation wake per edit (`claude/hooks/edit-validate/record.py:5-8`).
