# E001 — ergonomics/friction triage of the 2,268 owner-correction candidates

## Executive result

The dominant measured pattern is not an owner-friction cluster. It is detector contamination and replay amplification.

The corpus contains 2,268 `owner_correction_candidates`, but its own warning says the detector is recall-biased and that an unfiltered smoke sample produced **41 false positives out of 41**. The 120 published normalized patterns account for 1,120/2,268 candidates (49.38%). A conservative prefix/type classification finds **1,037/1,120 (92.59%) of that published pattern mass is mechanically recognizable as hook feedback, agent/task notifications, monitor prompts, capability probes, tool-output envelopes, continuation summaries, or agent-authored review/research prompts**. Those records may contain useful evidence about harness behavior, but they are not 1,037 independent owner corrections. Evidence: `/local_disk0/codexwork/bundle/inputs/corpus.json:1`, JSON pointers `/_meta`, `/owner_correction_candidates/precision_warning`, `/owner_correction_candidates/top_patterns`.

The largest recognizable class is **Stop-hook feedback replay: 808/1,120 published occurrences (72.14%; 35.63% of all 2,268 candidates)**. One retained exact-text sample appears **141 times in one transcript file over 2h33m05s**; a second appears **16 times in one transcript file over 6h16m43s**. That is the strongest measured ergonomics defect in this unit: repeated stop-time instructions flood the interaction and the correction miner. Evidence: `/local_disk0/codexwork/bundle/inputs/corpus.json:1`, pointers `/owner_correction_candidates/top_patterns/0`, `/owner_correction_candidates/top_patterns/5`, and the matching objects in `/owner_correction_candidates/samples`.

## Measured friction cluster 0: the correction detector confuses provenance

### Measured pattern

At least 1,037 of the 1,120 published pattern occurrences have explicit machine-origin wrappers. Examples include `Stop hook feedback:`, `<task-notification>`, `Another Claude session sent a message:`, exact MCP capability probes, and `<bash-stdout>...`. The detector nonetheless placed them under `owner_correction_candidates`. The retained samples additionally show 387/400 candidates have `after_tool_use: false`, so that boolean does not isolate actual corrections. Evidence: `/local_disk0/codexwork/bundle/inputs/corpus.json:1`, pointers `/owner_correction_candidates/top_patterns` and `/samples`.

### Root cause

The root cause is **role/provenance collapse**: synthetic messages serialized into a user-like stream are treated as owner-authored based on correction-like lexical triggers. This is **almost certain (90-99%)**, because (1) explicit wrappers identify the producing subsystem, (2) 41/41 smoke records were independently labeled false positive by the corpus author, and (3) the top-pattern and sample aggregations independently show the same contamination. The remaining uncertainty is whether the miner had inaccessible provenance fields that it ignored or whether the transcript schema itself loses provenance.

### Specific change — provenance-aware correction miner

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Change the miner's candidate record from `{text,file,ts,after_tool_use}` to at least:

```text
source_kind = direct_owner | stop_hook | teammate | task_notification |
              monitor | capability_probe | continuation | tool_output | unknown
source_event_id
quoted_owner_message_id (nullable)
session_id
normalized_text_hash
preceding_assistant_turn_id
preceding_tool_error_ids[]
```

Only `source_kind=direct_owner` enters the owner-correction denominator. Hook/agent/task records remain in separate operational-friction tables. Apply exact-wrapper classification before lexical correction matching; quarantine `unknown` rather than silently counting it as owner. Keep a manually labeled validation set and report precision/recall by source kind.

### Predicted effect size

On the already published table this change deterministically reclassifies **1,037/1,120 (92.59%)** explicit synthetic occurrences out of the direct-owner ranking, leaving 83 owner-like occurrences in that table. Relative to the complete 2,268 candidate set, the proven floor is **1,037/2,268 (45.72%)** reclassified. It is **very likely (80-90%)** that the full re-mine will reclassify more than 1,037, because 1,148 candidates lie outside the published top-pattern table and the independent retained-sample slice is 71.25% explicitly synthetic. The amount above 1,037 is **UNVERIFIED; the settling experiment is to run the new source classifier across all 2,268 records and manually audit a stratified 200-record sample**.

This proposal passes the anti-overfit gate: it is a bounded modification to the existing corpus miner/data schema, not a second orchestrator, vector database, durable runtime, trained critic, observability SaaS, or guardrail framework.

## Measured friction cluster 1: Stop feedback is replay-amplified

### Measured pattern

Stop feedback contributes 808 occurrences across 26 normalized patterns. The largest normalized payload occurs 524 times:

> `Stop hook feedback: please do it <n>% with both ghidra, binary and ida, as you said for all <n>% coverage and do not stop`

The retained exact text with `100%` occurs 141 times, all in `aeb94ff3-639d-48d8-b24a-6f3ee9650c46.jsonl`, from `2026-04-26T15:18:06.565Z` through `2026-04-26T17:51:11.318Z`. A second exact Ralph-loop continuation text occurs 16 times in that same file between `2026-04-23T06:14:25.109Z` and `2026-04-23T12:31:08.915Z`; one closely related retained sample raises the keyword match to 17. Evidence: `/local_disk0/codexwork/bundle/inputs/corpus.json:1`, pointer `/owner_correction_candidates/samples`; normalized counts at `/owner_correction_candidates/top_patterns/0` and `/5`.

The top-pattern row for stop-time Codex review failure contributes 39 more occurrences, while edit-validation Stop messages contribute 26 occurrences across 13 two-count rows in the published table. Those are operational failures/guard outputs, not owner corrections. Evidence: same file and pointer `/owner_correction_candidates/top_patterns` rows 3 and 78, 91, 94–98, 103–104, 108, 110–111, 113, 116–117 (1-based row numbering).

### Root cause

It is **very likely (80-90%)** that the Stop path lacks effective per-session duplicate suppression or progress-sensitive latching: an identical payload is observed 141 times in one transcript identifier within 2h33m, and another identical continuation payload 16 times in the same identifier. The exact hook implementation and whether every replay blocked a stop are **UNVERIFIED; the settling experiment is to inspect the missing raw JSONL around these timestamps and join each Stop attempt to the event ledger by session/event ID**.

This pattern has two ergonomic costs even if the hook is semantically correct: repeated context/window consumption and repeated forced continuation without a changed, testable acceptance condition. The corpus does not include token cost per replay, so no token estimate is claimed.

### Specific change — progress-sensitive Stop coalescing — UNVERIFIED

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

On Stop feedback, compute a key of `(session_id, normalized_feedback_hash, acceptance_criteria_hash)`. Persist only a tiny latch on the existing hook ledger:

1. First occurrence: emit the full feedback and record the current progress fingerprint (changed artifacts, completed checklist IDs, last successful verification, and last tool-error ID).
2. Repeated key with changed progress: emit a short delta—what remains—not the full historical instruction.
3. Repeated key with no changed progress: do not blindly replay. Emit one bounded diagnosis request containing the last distinct blocker/error and a choice of retry, alternate route, or explicitly blocked handoff.
4. Clear the latch when acceptance criteria change, the owner sends a new direct message, or the criteria are evidenced complete.
5. Never coalesce safety or destructive-action denials; this change is for continuation/quality feedback only.

### Predicted effect size

For the retained Ghidra/IDA exact-text run, simple same-session exact-hash suppression after the first occurrence would remove **140/141 (99.29%)** duplicate full-text emissions. For the retained exact Ralph payload it would remove **15/16 (93.75%)**. These are observed sample counterfactuals, not extrapolated population effects.

The claim that the same rule removes 523 of the 524 normalized Ghidra/IDA occurrences is **UNVERIFIED; the settling experiment is to group the missing raw occurrences by real session ID and acceptance-criteria changes**. It is **likely (55-80%)** that progress-sensitive coalescing will eliminate at least half of the 808 published Stop-feedback messages as full replay, because the retained decisive examples show extreme within-file duplication, but the corpus does not expose session distribution for all 808.

This proposal passes the anti-overfit gate: it adds a small dedupe/progress latch to the existing Stop/event-ledger bus, not another execution runtime or memory system.
