# C003 — checkpoint economics and context lifecycle

## Scope and answer

This unit asks one economic question: **what does a context checkpoint cost to write, compared with the cost of not having recoverable state when work is interrupted or context recovery fails?** It grounds the answer in the pinned corpus, decisive raw transcripts, the live shared-harness terminal ledger, and the real `D:\basic-memory` vault. It does not modify the harness or configuration.

The answer is:

1. **The currently deployed sanitized checkpoint is cheap.** The real vault contains 96 checkpoint files totaling 224,893 bytes: 2,342.6 bytes mean, 1,364 bytes median, 6,532 bytes maximum. The corresponding 96 real `PreCompact` dispatcher records have 107.482 ms median end-to-end latency, 304.155 ms p95, 1,591.265 ms maximum, and 13.998 seconds total. All 96 records say `SUCCESS:hook-precompact` and have an empty `failed_modules` list. This is the cost of the whole shared `PreCompact` dispatch, so it is an upper bound on the checkpoint writer alone, not a falsely precise component benchmark. Evidence: `D:\basic-memory\compaction-checkpoints\checkpoint-*.md`; `C:\Users\Prekzursil\.agents\state\harness\terminal.jsonl`; writer implementation at `C:\Users\Prekzursil\.agents\harness\modules.py:1458-1528`.
2. **The corpus shows material terminal-loss incidence, but not a task-death rate.** In 1,990 validated subagent transcripts, 253 (12.71%) end in an explicit interrupt, API error, prompt-too-long error, or other explicit stop sequence. Adding 16 unresolved pending-tool boundaries produces a 269/1,990 (13.52%) terminal-risk indicator. Neither number is a task-loss rate: an error may occur after an artifact was saved, and a pending tool may continue outside the transcript. Evidence and detector controls: `out/P1-ground/P1A08.md:115-156` and the raw paths cited there.
3. **Context-specific failures are directly observed.** Nineteen validated subagents end `Prompt is too long`; four compact agents end at the 20 MB request limit; one ends after context refilled within three turns of the previous compact three times. Including the one top-level prompt-too-long terminal gives 25 explicit context/payload terminal failures in the validated sample. Evidence: `out/P1-ground/P1A08.md:131,144-152,158-194`.
4. **Observed failed recovery is orders of magnitude more expensive than checkpoint writing in latency and transcript volume.** One continuation spent 33.892 seconds and reached one tool boundary before its 200,686-token continuation prompt was rejected against a 200,000-token maximum. Another spent 147.697 seconds, crossed three compact boundaries, and ended in autocompact-thrash without a report. Four failed `agent-acompact-*` attempts retain 7,472 JSONL lines and 21.03 MiB. Their wall spans are 43.19, 11.50, 11.68, and 11.59 hours; the latter three overlap and wall span includes idle time, so summing them as labor would be dishonest. Evidence: raw transcripts named in §5 and their rows in `corpus/corpus.json`.
5. **The exact counterfactual value of a checkpoint is UNVERIFIED; the settling experiment is a randomized kill/compact/resume canary with and without checkpoint injection, measuring reorientation turns, duplicate tool calls, time-to-first-correct-action, artifact reuse, and final acceptance.** Current telemetry proves checkpoints were written, but does not join a checkpoint ID to a recovery event or outcome. It is **very likely (80-90%)** that a bounded checkpoint is economically positive for interrupted multi-step work because the observed median full-dispatch write cost is 0.107 seconds while even the smallest decisive failed continuation consumed 33.892 seconds; the uncertainty is causal attribution, not the direction of the raw cost ratio.

The design implication is not a new durable-execution platform. Keep native compaction, keep the existing small local checkpoint, and add a receipt joining `checkpoint_id → recovery event → first correct action → terminal outcome`. That rides the existing hook/ledger bus and makes the next economics analysis causal rather than inferential.

## 1. Evidence contract and detector controls

### 1.1 What the corpus can and cannot measure

`corpus/corpus.json` says it scanned 11,633 files, 10.62 GB, and 1,564,084 lines, with zero files failed, one bad line, and 32 oversized lines (`corpus/corpus.json` `_meta`). Those global counts are strong coverage evidence.

The `sessions` list is not a census. `mine.py:331-339` stops appending after 4,000 rows and stores only basename, kind, line count, rounded MiB, first timestamp, and last timestamp. It does not store task identity, completion, terminal reason, recovery link, compact count, checkpoint ID, active time, or artifacts produced. Consequently:

- session-shape rates describe the first 4,000 lexically selected rows, not all 11,633 scanned files;
- `first_ts → last_ts` is wall span, not active compute or owner time;
- a transcript terminal is not automatically a task terminal;
- a task can retain useful disk work despite an API/context terminal;
- no checkpoint causal effect can be derived from the six session fields.

These limitations are demonstrated mechanically by the miner schema (`mine.py:331-339`) and by raw transcripts containing terminal causes and compact boundaries absent from that schema (`out/P1-ground/P1A08.md:402-414`).

The corpus `hooks` section is not used. Its detector is explicitly marked broken. Real hook execution is measured instead from the live shared terminal ledger and checkpoint files.

### 1.2 Known-positive controls for the live checkpoint detector

The live terminal ledger contains 123,542 parseable records and six malformed records. The detector finds known-present event types in large numbers: 58,587 `PostToolUse`, 52,734 `PreToolUse`, 1,145 `SessionStart`, 96 `PreCompact`, and 82 `PostCompact` records. This proves the event detector is not a universal-zero probe.

The checkpoint side has an independent known-positive: 96 markdown files in `D:\basic-memory\compaction-checkpoints`. Their frontmatter contains provider, project, timestamp, session hash, and permalink; their bodies contain a ledger pointer, goal, decisions, unresolved failures, and bounded `.remember/now.md` content. Example: `D:\basic-memory\compaction-checkpoints\checkpoint-20260719-015025-625510-54b7876e014d7839.md`.

The two surfaces reconcile:

- 60 vault files say provider `claude`; 36 say `codex`.
- The terminal ledger has 60 Claude and 36 Codex `PreCompact` records.
- 90 checkpoint timestamps equal a `PreCompact` terminal timestamp to the second; all 96 match within one second. The one-second difference is consistent with the writer taking its timestamp before dispatch terminal logging (`modules.py:1474,1515-1517`; `dispatcher.py:496-513`).

That timestamp/provider/count agreement is a mechanically independent second signal that the 96 terminal records and 96 vault files represent the same real writes. It is **almost certain (90-99%)** that every retained checkpoint corresponds to one recorded shared `PreCompact` dispatch, based on exact counts/providers and ≤1-second nearest timestamp agreement for all 96. “Every `PreCompact` ever emitted a retained file” is not claimed: the writer retains only the newest 100 (`modules.py:1518-1527`), and historical terminal/log retention may differ.

### 1.3 What “checkpoint cost” means here

There are three distinct costs:

1. **Checkpoint serialization/write cost:** ledger reads, bounded redaction, atomic local write, and retention scan.
2. **Whole `PreCompact` dispatch cost:** all registered shared modules plus checkpoint writing. This is what `terminal.jsonl.elapsed_ms` measures (`dispatcher.py:485-513`).
3. **Native model compaction cost:** the model-generated summary/context reduction. In the large raw session, observed compact boundaries take roughly 58–230 seconds (`out/P1-ground/P1A08.md:221-240`). This is not checkpoint-writing cost.

The implementation invokes no model and no MCP call in `SanitizedCheckpointModule.run`; it reads local ledger/remember state and calls `atomic_write_text` (`modules.py:1458-1517`). Therefore the deterministic checkpoint writer itself incurs no additional model-token charge. The measured 107 ms median is deliberately reported as the whole-dispatch upper bound because no per-module timer exists.

### 2.3 Information carried

The checkpoint is not a conversation dump. It captures:

- provider, project hash, timestamp, and session hash;
- current ledger pointer;
- session-private goal;
- last ten redacted decisions;
- last ten redacted open failures;
- up to 4,096 redacted characters of `.remember/now.md`;
- a bounded total payload.

Evidence: `modules.py:1462-1517`. This design directly follows the anti-overfit gate: it persists compact task state on the existing file/hook bus rather than introducing a second orchestration runtime or a new vector/KG store.

Quality is uneven. All 96 files have a nonempty `goal` field, but samples show that a goal can be a transient task notification or the owner’s latest narrow prompt rather than a complete task plan. For example, `checkpoint-20260711-010906-471193-2424e0c9edfb4371.md` captures a stopped background-workflow notification as the goal; `checkpoint-20260719-025519-789493-a832eeaa71ad5f03.md` captures a narrow browser instruction while `.remember/now.md` carries broader project state. It is **likely (55-80%)** that the present fields are enough to reduce reorientation for many tasks, based on 27 decision-bearing and 13 failure-bearing files plus the consistent ledger pointer; it is **UNVERIFIED** that they are sufficient for correct recovery, and the settling experiment is the checkpoint-consumption canary in §8.

## 3. How often work appears to die mid-task

### 3.1 Top-level sessions are a misleading denominator

Among 1,854 validated top-level rows, 1,361 end in subscription-disabled or session-limit messages (`out/P1-ground/P1A08.md:117-133`). These are front-door rejections, generally before task work. Including them in a “mid-task death rate” would inflate the rate with failures a checkpoint cannot solve.

Top-level validated rows also contain 43 pending-tool terminals, 14 API/auth/overload errors, two explicit interrupts, and one prompt-too-long error. The 43 pending-tool cases are ambiguous. It is **likely (55-80%)** that some represent abrupt work loss because the protocol ends after a tool request with no corresponding result, but this is **UNVERIFIED**; the settling experiment is to join tool-use IDs to background/process registries and sibling transcripts (`out/P1-ground/P1A08.md:153`).

### 3.2 Subagents provide the cleaner operational population

The 1,990 validated subagents end as follows (`out/P1-ground/P1A08.md:135-146`):

| Terminal shape | Count | Share of 1,990 | What can be claimed |
|---|---:|---:|---|
| Ordinary `end_turn` | 1,085 | 54.52% | Strong normal-turn terminal, not proof of whole-task acceptance |
| Tool result last | 391 | 19.65% | Mostly StructuredOutput handoff; not a death class |
| Assistant text/no stop reason | 245 | 12.31% | Often a report; schema-dependent |
| Explicit interrupt | 159 | 7.99% | Direct cancellation terminal |
| API error | 57 | 2.86% | Direct service/policy/network terminal |
| Prompt too long | 19 | 0.95% | Direct request/context terminal |
| Other explicit stop sequence | 18 | 0.90% | Includes 10 expired logins, four 20 MB limits, one compact-thrash terminal, and quota variants |
| Pending tool use | 16 | 0.80% | Incomplete boundary; cause unknown |

The explicit non-success terminal indicator is `(159 + 57 + 19 + 18) / 1,990 = 12.71%`. Adding pending tool boundaries gives 13.52%. These are the most honest frequency measures available, but neither is “work died”:

- interrupts can be deliberate reprioritization;
- API errors can happen after useful files were written;
- a transcript can stop while an external process continues;
- `end_turn` can be an interim update;
- no artifact or acceptance field exists.

Therefore the true task-loss frequency is **UNVERIFIED; the settling experiment is to add task ID, artifact receipt, terminal class, resume link, and accepted/rejected outcome to the miner, then label a stratified sample by raw transcript plus filesystem/git evidence.** It is **likely (55-80%)** that the task-loss rate is below the 12.71% explicit-terminal indicator because durable artifacts can precede a terminal and some interrupts are intentional; the corpus does not quantify how far below.

### 3.3 Context/payload-specific incidence

Direct context/payload terminals in the validated rows are:

- 19 subagent `Prompt is too long` terminals;
- one top-level `Prompt is too long` terminal;
- four 20 MB compact-request terminals;
- one autocompact-thrash terminal.

That is 25 observed terminals in the validated 3,844 top-level-plus-subagent classified rows, or 0.65%. This is a terminal incidence in a path-biased, capped session sample—not a population rate and not a checkpoint-preventable fraction. ## 5. Can the current data prove checkpoint benefit?

No causal benefit can currently be proved. This is an evidence gap, not a negative result.

Two mechanically independent surfaces expose the missing join:

1. Checkpoint files contain session hash, project, timestamp, ledger pointer, goal, decisions, failures, and `.remember/now.md`, but no checkpoint ID consumption record, recovery event ID, or outcome (`modules.py:1488-1517`; real vault samples).
2. Terminal records contain timestamp, terminal marker, provider, event, action, reason code, elapsed time, and failed module names, but no session hash or checkpoint ID (`dispatcher.py:496-513`).

Known-present controls validate both detectors: the vault/terminal probes join 96 writes within one second, and the terminal probe finds 1,145 `SessionStart` plus 82 `PostCompact` records. Therefore it is valid to say **these telemetry surfaces cannot causally join write to recovery**. It would be invalid to say “checkpoints are never read” or “recovery does not work.”

The broader corpus records 1,332 basic-memory MCP calls, including 408 `write_note`, 357 `search_notes`, 353 `read_note`, 156 `edit_note`, 30 `recent_activity`, and 11 `build_context` uses (`corpus/corpus.json` `capability_use.mcp_tools_used`). These are known-positive evidence that the vault is actively used. They cannot be divided by the 96 retained checkpoints to make a recall rate because the corpus and retained-vault windows differ and no call carries the checkpoint ID in the distillation.

A direct local `basic-memory tool search-notes "compaction checkpoint recovery" --local` query exceeded 60 seconds without output during this unit. This failure is recorded rather than silently converted to “no matching notes.” The filesystem inventory remains authoritative for retained checkpoint files; semantic-search latency is a separate operational issue. The search result is **UNVERIFIED; rerun through `longrun` with daemon health, request timing, and a terminal marker to settle it.**

## 6. Economic interpretation

### 6.1 Break-even arithmetic

Let:

- `Cw` = checkpoint write cost;
- `Pr` = probability that a checkpoint is needed and usable;
- `Sr` = recovery cost saved when usable;
- `Cr` = extra recovery/recall overhead caused by the mechanism.

Checkpointing is positive when `Pr × Sr > Cw + Cr`.

Measured `Cw` is at most the whole-dispatch median, 0.107482 seconds, plus 1,364 median bytes. Using the smallest decisive failed-continuation wall cost, 33.892 seconds, and temporarily setting `Cr=0`, latency break-even is `0.107482 / 33.892 = 0.317%`: one successful save in roughly 315 checkpoints. Using the 147.697-second thrash episode gives 0.073%, or roughly one successful save in 1,374 checkpoints.

Those are sensitivity calculations, not empirical benefit rates. `Pr`, causal `Sr`, and `Cr` are **UNVERIFIED; the experiment in §8 measures them.** It is **very likely (80-90%)** that the present local write clears the economic bar for multi-step work because observed explicit terminal-risk indicators are percent-scale while latency break-even is sub-percent; the evidence does not show what fraction of those terminals a checkpoint can actually rescue.

### 6.2 Why “checkpoint every turn” does not follow

The favorable economics apply to **lifecycle boundaries**, not arbitrary high-frequency snapshots. The current writer fires on `PreCompact`, carries bounded ledger state, and retains 100 files. Writing on every tool call would multiply I/O and retention churn without evidence that every tool boundary needs a full semantic checkpoint.

It is **likely (55-80%)** that `PreCompact` plus explicit long-operation/task milestones is the right cadence, because 96 real compactions cost only 14 seconds total and the decisive failures cluster at compaction, interruption, and pending-tool boundaries. The optimal cadence is **UNVERIFIED; a settling experiment should compare PreCompact-only against PreCompact+milestone checkpoints on matched kill points, measuring saved work and write amplification.**

### 6.3 What checkpoints cannot buy

A checkpoint cannot by itself:

- make a 200,686-token prompt fit a 200,000-token limit;
- make a >20 MB request fit a 20 MB transport limit;
- stop a large tool result from refilling context;
- keep an in-memory subprocess alive;
- prove that a restored model understood or obeyed the state;
- recover unsaved reasoning that was never externalized.

These need admission budgeting, bounded outputs, external operation identity, and a recovery receipt. Treating checkpointing as a universal cure would overfit the mechanism to failures it cannot address.

## 8. Experiment that settles the economics

### UNVERIFIED — randomized checkpoint recovery canary

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Run at least 30 matched multi-step canaries across Claude and Codex. Each canary creates:

1. a unique goal and acceptance test;
2. one durable decision with rationale;
3. one falsifiable unresolved failure;
4. one modified-but-uncommitted artifact;
5. one 2–5 minute background operation with terminal marker;
6. a known next action that must not be repeated.

Randomize recovery mode at matched interruption points:

- native summary only;
- native summary + current checkpoint injection;
- fresh session + current checkpoint injection;
- fresh session with neither checkpoint nor old conversation (negative control).

Rejected. This reintroduces a previously rejected durable-execution/runtime component. Native compaction demonstrably survives at least 20 boundaries, and the checkpoint writer is already cheap. Rejected as a standalone remedy. One sidechain refilled within three turns three times, and four compact agents crossed a separate 20 MB ceiling. More compactions could add 58–230 seconds each without bounding the next payload.

Rejected. Lack of a receipt means benefit is unmeasured, not absent. Real write cost is low, real terminal/recovery failures are present, and disabling the only bounded external lifecycle state would remove the mechanism before measuring it. Instrument first.

### Checkpoint every tool call

Rejected pending evidence. The present `PreCompact` boundary already maps 96 events to 96 writes with 14 seconds total dispatch time.
