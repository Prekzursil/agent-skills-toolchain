# X040 — Cross-domain borrow: nuclear operations → agent memory

## Scope and answer in one paragraph

This unit asks whether nuclear-operations mechanisms can improve what an agent remembers across sessions, when it forgets, and how it detects stale memory. I did not inspect or characterize the local harness: the unit is explicitly an external ideation lens, and claims about current local implementation would duplicate neighboring units. The useful transfer is **partial**. Nuclear operations has not solved semantic memory, but it has developed a coherent answer to a structurally similar control problem: an operator must act using fallible information in a changing system where a single unchecked error may propagate. The transferable pattern is a layered, consequence-sensitive **claim lifecycle**: preserve provenance; classify consequence; require independent verification only for consequential irreversible actions; assume uncertainty conservatively; perform a use-time Stop–Think–Act–Review check; and retain multiple independent detection/recovery layers. It is **very likely (80-90%)**, based on the direct structural match between “stored claim → consequential action” and “indication/procedure → plant action,” that this pattern is worth a shadow-mode experiment. It is **UNVERIFIED** for this owner until a replay experiment compares stale-memory acceptance, repeated-owner-correction rate, token cost, and latency against the present harness.

The headline caveat is equally important: the nuclear “two-person rule” is not a general truth-validation method. NRC describes it in material access areas as preventing anyone from being alone, and a Commission paper describes its principal value as reducing malevolent insider acts involving special nuclear material. That is separation-of-custody/security, not epistemic peer review. The closer analogue for memory validation is DOE **independent verification**, which requires a qualified person other than the performer to check conformance to established criteria. Conflating these mechanisms would produce performative multi-agent ceremony rather than independence.

## What nuclear operations actually solved

### 1. Two-person controls and independent verification are different mechanisms

**In the source field.** NRC’s material-access-area two-person rule is a physical/security control: no one is allowed alone where specified special nuclear material is accessible (source 1). The Commission’s notation vote is unusually clear about the threat model: the rule is useful primarily in reducing potential malevolent acts by an insider (source 3). COMSECY-12-0026’s proposed formulation adds authorization and qualification: two qualified, authorized people are present, with sufficient knowledge to tell whether the proper procedure was followed (source 2). Presence provides mutual surveillance, response capacity, and division of control. It does not, by itself, make either person’s belief true.

DOE independent verification has a different error model. DOE’s operating-experience summary defines it as a check against established criteria by a qualified person other than the performer, and explains the intended benefit: the same mistake is less likely to be made independently by two workers (source 5). The important word is **independently**. If the verifier merely accepts the performer’s framing, shares the same erroneous display, or repeats the same procedure path, correlated failure defeats the control. DOE places independent verification and self-checking as a last defensive barrier in its wrong-valve discussion, not as substitutes for good design, training, or procedures (source 5).

**Problem actually solved.** These controls reduce two different single-point failures: malicious or unauthorized conduct (two-person presence) and an individual’s unnoticed execution error relative to explicit criteria (independent verification). They do not solve ambiguous criteria, shared bad evidence, or systemic design errors.

**Memory translation.** Do not require “two agents agree” for ordinary memories. Require an **independent evidence check** only before a high-consequence memory is promoted to durable/authoritative status or before a high-consequence deletion becomes irreversible. The verifier receives the candidate assertion, scope, and raw evidence references, but not the writer’s rationale or verdict. It independently returns `supported`, `contradicted`, or `insufficient`, with evidence locations. Same-model agreement is not enough if both calls share a summary or retrieval results.

This would catch: a preference inferred from one ambiguous exchange; a constraint copied with the negation lost; a “resolved” incident recorded from the fixer’s assertion but not the verification output; and a destructive “forget” request whose target is broader than the cited evidence. It would not catch two runs retrieving the same poisoned source, a bad criterion, or facts changed after verification.

### 2. Conservative decision-making is a burden-of-proof rule under uncertainty

**In the source field.** NRC’s safety-culture component says decisions affecting nuclear safety should be systematic, particularly under unexpected or uncertain plant conditions. It describes conservative decisions as using conservative assumptions and rejecting options unless the action is demonstrated safe, rather than requiring proof that it is unsafe. It also calls for risk/consequence consideration, contingencies, design margins, interdisciplinary input for risk-significant decisions, communication, and later effectiveness reviews (source 7). This is not “always do nothing.” It is a burden-of-proof allocation: when evidence is incomplete and consequences are asymmetric, uncertainty does not license the riskier action.

**Problem actually solved.** The mechanism prevents production pressure or motivated reasoning from converting “not proven dangerous” into “safe.” It deliberately trades some availability or schedule for a larger safety margin when the downside is consequential.

**Memory translation.** A stale or weakly sourced memory must not silently become an action premise merely because nothing contradicts it. The use gate chooses the conservative state according to consequence:

- For a potentially destructive or externally visible action, `unknown`, expired, contradicted, or out-of-scope memory means pause and re-establish the fact from an authoritative source or ask the owner.
- For a reversible low-impact action, the agent may proceed while explicitly treating the claim as tentative and retaining rollback information.
- For retention of credentials, private data, or one-time secrets, “conservative” reverses direction: uncertainty about continued need favors forgetting/quarantine, not indefinite retention.
- For owner preferences, ambiguity favors asking at the next material decision, not repeatedly asserting a guessed preference as identity.

Thus “conservative” must be consequence-relative. A blanket “keep everything just in case” policy would be anti-conservative for privacy and would make stale recall more likely.

This would catch: an old deployment target used after a migration; an expired approval treated as standing authority; an obsolete API constraint driving a workaround; and a transient secret retained because no deletion instruction arrived. It will also create false pauses if consequence classification is too broad.

### 3. Defence in depth assumes prevention will fail

**In the source field.** IAEA’s defence-in-depth account begins from a sober premise: prevention is the first safety priority, but component, system, and human failures remain possible, so further levels must prevent escalation and mitigate consequences (sources 9 and 10). NRC’s plain-language reactor-risk backgrounder illustrates the resulting diversity of protections: multiple physical barriers, safety systems, trained staff, testing, maintenance, and inspection (source 11). The conceptual value is not merely “many checks”; it is **successive barriers with different functions**, so one failed layer does not erase protection.

**Problem actually solved.** Defence in depth limits propagation. It recognizes that perfect components and perfect operators are unavailable, and it places prevention, detection, control, and mitigation at different points in an accident sequence. Independence matters because cloned layers fail together.

**Memory translation.** The memory system must not bet everything on perfect writing, a single TTL, or a clever retrieval score. Use four functionally different barriers:

1. **Admission prevention:** no durable claim without typed scope, provenance, observation time, retention basis, and invalidation conditions.
2. **At-rest detection:** contradictions, supersession links, elapsed review dates, and source-change triggers move claims to `needs-review`; they do not silently rewrite truth.
3. **Use-time control:** STAR checks identity/scope/freshness and consequence immediately before the claim affects a tool call or answer.
4. **Outcome mitigation and learning:** compare the observed result with the expected result; on mismatch, quarantine the memory, preserve the event, and open a correction candidate rather than compounding the old claim.

These layers address different failure moments. A malformed memory can be rejected at admission; a once-valid fact can age at rest; an apparently fresh fact can be misapplied to the wrong repository at retrieval; and a bad premise that escapes all earlier barriers can still be detected from action outcome.

This would catch more than a TTL-only scheme: scope drift, contradictions, wrong-entity retrieval, stale facts without predictable expiration, and evidence that becomes bad only after action. It cannot guarantee safety if all layers consume the same corrupt evidence or if no observable outcome exists.

### 4. STAR is a point-of-action attention protocol, not a memory database

**In the source field.** DOE describes self-checking as a risk-management tool that focuses attention on task detail and positive identification of the correct unit/train/component. STAR is the mental sequence Stop, Think, Act, Review before, during, and after a task (source 5). DOE’s later operating-experience summary makes the prompts concrete: pause; consider what response is expected; confirm the correct component; act; then ask whether the result matched expectation (source 6). The cited incident—an operator opened a wrong valve roughly half an inch from the intended valve—shows the class of capture error the technique targets (source 5).

**Problem actually solved.** STAR interrupts automatic action at the last responsible moment, forces identity and expected-outcome checks into working attention, and closes the loop after action. It is intentionally small enough to use at point of work.

**Memory translation.** At the moment a retrieved memory is about to alter a consequential answer or tool action:

- **Stop:** identify the exact durable claim being relied on and its consequence class.
- **Think:** confirm owner/project/entity scope, provenance, age, invalidation triggers, contradictions, and expected result if the claim is still valid.
- **Act:** use it, revalidate it, ask, or choose a reversible alternative according to the conservative gate.
- **Review:** compare actual result to the predicted result; record support, contradiction, or non-diagnostic outcome. Never treat task completion alone as confirmation of the memory.

This would catch the memory equivalent of the adjacent wrong valve: a correct instruction for the neighboring repository, similarly named owner, old environment, or predecessor tool. It would also turn action results into staleness signals rather than leaving memory maintenance to periodic cleanup.

## Concrete harness design

### Proposal A — UNVERIFIED: typed claim ledger with expiry and invalidation triggers

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add an append-only, human-readable claim ledger (JSONL or equivalent) and a small admission/transition helper on the existing memory write/read bus. Do not add a daemon or database.

Minimum record:

```json
{
  "id": "stable-id",
  "claim": "single falsifiable or preference assertion",
  "kind": "fact|preference|authorization|decision|lesson|secret",
  "subject_scope": ["owner", "project/repo", "environment"],
  "evidence": [{"type": "session|file|url|tool-output", "locator": "..."}],
  "observed_at": "timestamp",
  "valid_from": "timestamp-or-null",
  "review_by": "timestamp-or-null",
  "invalidate_on": ["source changed", "project migration", "owner correction"],
  "consequence": "low|material|high",
  "retention_basis": "why cross-session retention is needed",
  "status": "active|needs-review|quarantined|superseded|forgotten",
  "supersedes": [],
  "contradicts": [],
  "writer": "run-id",
  "verifier": null,
  "last_used_at": null,
  "last_checked_at": null
}
```

Rules:

- Store one scoped assertion per record; summaries may point to claims but are not themselves authoritative evidence.
- `review_by` is a review trigger, not a magical truth deadline. Passing it changes `active → needs-review`; it does not delete history or assert falsehood.
- New contradictory evidence creates a linked record and quarantines the actionable claim until resolution. Never silently overwrite.
- Supersession preserves lineage. The retriever returns only the active head plus explicit conflict state.
- Forget secrets and one-time authorization at end of need unless an explicit retention basis exists. Forget low-value episodic detail after a short horizon. Preserve durable owner decisions/preferences while their scope is valid, but schedule review when they materially affect action.
- “Forgotten” removes the claim from retrieval and triggers the system’s actual privacy deletion path where one exists; a tombstone may retain only non-sensitive ID, deletion time, and reason so deleted content is not reconstructed.

Expected benefit is **likely (55-80%)**, because typed scope/provenance directly addresses known classes of stale and cross-context retrieval errors, but no owner-specific baseline is available in this ideation unit. **UNVERIFIED experiment:** replay a stratified sample of sessions containing owner corrections, environment migrations, revoked approvals, preferences, and secrets. Compare stale-claim acceptance, false quarantine, correction recurrence, tokens, and latency with and without the ledger.

### Proposal B — UNVERIFIED: consequence-gated memory STAR hook

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a pre-action hook that runs only when a retrieved durable claim is both action-relevant and `material/high` consequence. It evaluates the four STAR stages using ledger fields. Add a post-action hook that accepts an expected-result predicate and records `supported`, `contradicted`, or `non-diagnostic`.

The hook must be deterministic where possible. Scope equality, status, review date, contradiction links, and evidence availability are checks; a model may explain ambiguity but must not waive a failed hard check. For high-consequence actions, `needs-review`, missing provenance, scope mismatch, or unresolved contradiction blocks silent use and routes to authoritative re-fetch/owner question/reversible fallback. For low consequence, do not invoke the hook.

Expected benefit is **likely (55-80%)**, based on DOE’s mechanism targeting point-of-action capture errors and on the direct analogue between component identity and memory subject scope. Generalization to agent behavior is **UNVERIFIED**. **Experiment:** inject wrong-repository, old-endpoint, superseded-preference, and adjacent-entity memories into replay tasks. Measure detection before tool action, incorrect blocks, and added latency. Require improvement over a simple scope+TTL gate to justify STAR’s extra prompts.

### Proposal C — UNVERIFIED: independent promotion/deletion check for high-consequence claims

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At promotion of a high-consequence claim (authorization, destructive target, durable security constraint) or irreversible deletion of such a claim, launch one fresh-context verification call through the existing agent bus. Provide raw evidence locators and explicit criteria, not the original author’s chain of thought, summary, or verdict. Require evidence-addressed output. On disagreement or insufficiency, quarantine and ask/research; do not majority-vote.

Do not apply this to routine facts. Two calls on every memory would waste cost and normalize rubber-stamping. Do not call it a “two-person rule”: it borrows DOE independent verification, while the actual two-person rule supplies only the narrower lessons of qualification, authorization, and separation of control.

Expected benefit is **roughly even (45-55%)**, because second checks can catch transcription and scope errors but same-model, same-source errors are highly correlated. **UNVERIFIED experiment:** blind the verifier to the writer’s conclusion; seed negation loss, over-broad deletion targets, ambiguous preferences, poisoned common sources, and correctly written controls. Compare fresh-context verification, same-context critique, and no verifier. Retain this proposal only if fresh-context verification materially improves high-consequence defect detection without unacceptable false blocks.

### Proposal D — UNVERIFIED: independent absence/staleness detector with a canary

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A claim that memory is absent, stale, or successfully forgotten must meet the owner’s two-signal rule. First prove detector sensitivity by retrieving a known-present canary of the same class and scope. Then use two mechanically independent signals:

1. the active retrieval/index view; and
2. the append-only ledger/source-event audit path (or authoritative source re-fetch for staleness).

Examples: “no active authorization exists” needs a negative active-index result plus ledger lineage showing expiry/revocation, after the canary is found. “This endpoint is stale” needs a memory review failure plus an authoritative live configuration/API signal, not two model judgments over the same cached text. “The secret was forgotten” needs absence from the retrievable store plus the deletion backend’s acknowledgement/audit record; absence in two queries to the same index is one signal, not two.

Expected benefit is **very likely (80-90%)**, because the mechanism directly guards detector failure and the owner’s brief records multiple false conclusions from single unvalidated probes. Local implementation feasibility is **UNVERIFIED** because this unit did not inspect memory backends. **Experiment:** fault-inject a disabled index, stale cache, failed deletion, and broken source connector; require the detector to refuse all false “absent/stale/done” declarations while still finding known-present controls.

## Retention and forgetting policy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** This policy is the declarative classification consumed by Proposal A; it does not require a separate service.

The nuclear borrow suggests not “remember more,” but “retain claims according to consequence and revalidation cost.” Proposed default classes:

| Memory class | Admission | Review/expiry | Forget behavior | Use gate |
|---|---|---|---|---|
| Secret, token, one-time code | Avoid durable admission; explicit need only | End of task/need | Delete content; minimal non-sensitive tombstone | Never silently reuse |
| Authorization/approval | Exact scope, action, grantor, evidence | Explicit expiry; otherwise next materially distinct action | Quarantine on expiry/revocation | Re-establish for high consequence |
| Environment fact (path, endpoint, version, branch) | Authoritative source and project scope | Source-change trigger plus short review horizon | Supersede; retain lineage briefly | Re-fetch when stale/material |
| Owner preference | Direct owner evidence; distinguish preference from one-off instruction | Event-driven correction; review when high-cost choice depends on it | Supersede, do not erase correction lineage | Ask when ambiguous/material |
| Durable decision/rationale | Decision, alternatives, scope, date, evidence | Project phase/change trigger | Archive after project; retain decision lineage | Surface contradiction |
| Operational lesson | Concrete incident and observable trigger | Effectiveness review after uses | Retire if non-predictive or harmful | Apply only in matching scope |
| Episodic task detail | Minimal admission | Short horizon/end of project | Forget by default | No high-consequence reliance |

This table is a design hypothesis, not an established nuclear standard. Its effectiveness is **UNVERIFIED**; Proposal A’s replay experiment settles whether these classes reduce stale use without destroying helpful continuity.

Two subtleties prevent naive expiration:

1. **Age is evidence, not verdict.** A ten-year-old birth date may remain true; a ten-minute-old deployment status may be stale. Review horizons should follow volatility, invalidation signals, and consequence.
2. **Forgetting and superseding differ.** If a preference changes, the current value should supersede the old one while enough non-sensitive lineage remains to prevent oscillation and explain conflict. If a secret’s purpose ends, its content should be deleted rather than “archived for history.”

## Adversarial analysis: where the analogy breaks

### Disanalogy 1: physics supplies stronger state and criteria than language memory

Plant components have engineered identities, procedures, instrumentation, and often measurable expected responses. Agent memories include vague preferences, inferred intentions, social context, and open-world facts. “Conformance to established criteria” may not exist. Therefore independent verification transfers well to exact claims with raw evidence, and poorly to taste or latent intent. It is **very likely (80-90%)**, based on this difference in observability, that verifier agreement on ambiguous preferences would create false confidence unless the owner is the authority.

### Disanalogy 2: nuclear loss functions are unusually asymmetric

Nuclear conservative decision-making prioritizes public and worker safety over production pressure. Agent tasks span radically different stakes. Pausing on every uncertain memory could make the harness unusable and could itself cause harm (missed deadlines, loss of autonomy, needless owner interruption). The correct transfer is consequence-gated burden of proof, not universal caution.

### Disanalogy 3: two humans can have genuinely separate perception; cloned agents often do not

Two model calls may share weights, retrieval, prompt assumptions, and source defects. Fresh context gives partial procedural independence, not cognitive or evidentiary independence. It is **likely (55-80%)**, based on shared-model/shared-source correlation, that naive multi-agent agreement will overstate confidence. Only the proposed blinded fault-injection experiment can quantify the effect here.

### Disanalogy 4: nuclear barriers are engineered against bounded hazards; knowledge is open-world

Defence-in-depth layers can be designed around physical release paths and defined safety functions. No finite memory schema enumerates all ways a fact can change or be misapplied. The translated layers improve detection and containment; they cannot establish truth completeness.

### Disanalogy 5: plant operators and agent owners have different authority relationships

An operating procedure can prescribe an approved safe state. An agent often needs the owner’s current preference, and a historical memory cannot overrule a current instruction. The owner’s present statement is authoritative for preferences and authorization; a verifier should check transcription/scope, not vote against the owner.

### Disanalogy 6: adding checks can create its own common-mode failure

If admission, staleness detection, STAR, and verification all rely on the same model summary, they are four labels on one barrier. Independence requires different signals: raw evidence at admission, deterministic metadata at rest/use, authoritative re-fetch for dynamic state, and observable post-action outcome. Otherwise the design is theatre.

## What this catches that a typical “save and retrieve notes” memory misses

Without claiming anything about the owner’s current implementation, the design targets these generic blind spots:

1. **Once-true but now false:** review dates and invalidation triggers quarantine rather than silently serve the claim.
2. **True in the wrong scope:** STAR checks repository/environment/person identity at point of action.
3. **Contradictory memories:** append-only links expose conflict; last-write-wins does not erase it.
4. **Unsupported inference hardened into identity:** admission requires evidence and distinguishes direct preference from inferred behavior.
5. **False completion:** post-action review and two independent deletion signals prevent “forgotten” from meaning merely “not returned by one query.”
6. **Repeated bad workaround:** expected-vs-observed review quarantines the premise that generated it and creates a correction candidate.
7. **Over-retained sensitive data:** retention basis and asymmetric conservative treatment favor deletion at end of need.
8. **Over-forgetting durable rationale:** supersession lineage preserves why a decision changed without keeping every episodic detail.
9. **Verifier rubber-stamping:** blinded raw-evidence review tests criteria independently and records `insufficient` rather than forcing agreement.
10. **Detector blindness:** known-present canaries validate the detection path before negative claims.

## Anti-overfit gate and rejected alternatives

All four proposals ride an existing memory/hook/skill/agent bus and can be evaluated independently. They do not require a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The ledger is a small append-only artifact, not a new memory platform. STAR is consequence-gated, not a prompt ceremony on every retrieval. Independent verification is rare and criterion-bound.

Rejected alternatives:

- **A second “nuclear-grade” orchestration runtime:** rejected. It violates the anti-overfit gate and adds a larger common-mode failure surface without evidence that scheduling, rather than claim quality, is the bottleneck.
- **Vector DB or knowledge graph for all memory:** rejected. Better retrieval does not establish freshness or scope; semantic similarity can make the adjacent-wrong-component problem worse.
- **Two-agent vote on every write:** rejected. It mistakes presence/agreement for independent verification, adds cost, and is vulnerable to correlated error.
- **Global TTL:** rejected. Volatility is claim-specific; TTL both preserves fast-changing facts too long and discards stable facts unnecessarily.
- **Never delete, only append:** rejected. It conflicts with privacy and increases stale/secret exposure. Non-sensitive lineage and sensitive content need different treatment.
- **Nightly model-based memory cleanup:** rejected. It is one opaque judgement over an accumulated store, can silently rewrite history, and lacks use-time context.
- **Trained staleness critic:** rejected. It is a previously rejected trained-critic component and would need its own data and calibration program.

Run in shadow mode before blocking actions. This is **NATIVE-vs-BUILD: CONFIG (settings/JSON only)** for enabling/disabling and sampling the proposed BUILD-SMALL hooks once they exist.

1. Build a labeled replay set stratified by memory class and consequence: still-valid, expired, superseded, wrong-scope, contradictory, ambiguous, sensitive-end-of-need, and genuinely absent.

3. Compare: baseline retrieval; typed ledger only; ledger + simple scope/TTL gate; ledger + STAR; and high-consequence independent verification.

6. Promote a layer only if it improves its targeted failure class over the simpler preceding layer. If STAR does not beat deterministic scope/status checks, omit it. If a fresh verifier does not beat same-context critique enough to justify cost, omit it.

## Final judgment

The analogy transfers, but only after removing its most seductive interpretation. “Use two agents because nuclear uses two people” does **not** transfer: the nuclear two-person rule principally addresses custody/insider threat, and two correlated model calls do not create truth. The defensible borrow is the combined operating discipline:

- independent, criterion-based checks for selected high-consequence transitions;
- a conservative burden of proof that changes with consequence and privacy direction;
- independent prevention/detection/control/mitigation layers;
- a tiny use-time STAR loop that identifies the exact claim and closes the expected/actual outcome loop.

The resulting design is intentionally small. It changes memory from an undifferentiated pile of remembered prose into scoped claims with provenance, invalidation, consequence, lifecycle, and outcome feedback. It knows three states beyond “remembered”: `needs-review`, `quarantined`, and `superseded`; and it treats “forgotten” as a result requiring independent evidence, not a retrieval impression.

Recommendation: run Proposals A, B, and D in replay/shadow mode; test Proposal C skeptically and retain it only on measured high-consequence gains. This recommendation is **likely (55-80%)** to improve stale-memory detection with tolerable complexity, based on the direct mechanism mapping and the small bus-native implementation, but it remains **UNVERIFIED until the specified replay, fault-injection, ablation, and shadow-mode experiments are run**.
