# C009 — Context lifecycle: handoff quality across session boundaries

## Executive verdict

The corpus supports a narrower and more useful conclusion than “write better summaries”:

> A good handoff is a bounded index into independently inspectable state. A bad handoff is a narrative that asks the next context to trust claims about state it could cheaply verify.

The decisive real example is an owner continuation message that begins, “Do not trust the compaction summary for completion status — read the actual files,” then names the scratch state, three deliverables, and concrete verification commands (`corpus.json`, JSON pointer `/owner_correction_candidates/samples`, sample in `aeb94ff3-639d-48d8-b24a-6f3ee9650c46.jsonl` at `2026-04-08T01:46:17.290Z`). That is not an abstract preference: the owner explicitly demoted the summary and supplied an evidence-first recovery procedure. A second family of real samples reports background work from a prior session as having no completion record, with in-process state lost or ambiguous; the better variants include a workflow `resumeFromRunId` and say completed agent calls will be cached (`corpus.json`, same JSON pointer, samples at `2026-07-12T02:19:02.825Z` and `2026-07-17T15:02:12.257Z`). Together they identify the two handoff failure classes that matter here: **epistemic loss** (the next context cannot tell what is actually done) and **execution loss** (the next context cannot identify or resume volatile work).

The current harness has many of the right primitives but joins them incompletely. It has native continuous transcript persistence; Claude Code can resume a saved session. It has a per-session goal, a durable project ledger, a sanitized PreCompact checkpoint, lexical Basic Memory recall, and structured handoff templates. However, the automatic ledger replay intentionally fires only for `resume|compact|clear`, not a genuinely fresh session; the checkpoint directory is intentionally excluded from automatic lexical recall; and Stop records only an assistant-message hash, not a recoverable handoff body. These facts are directly visible at `/local_disk0/codexwork/bundle/agents/harness/modules.py:973-1003,1240-1255,1440-1528,1600-1643`. The result is a lifecycle split: same-session recovery has automatic rails, while a replacement session or cross-provider handoff still depends on manual capture/search or project memory.

The best design is therefore not another memory service or orchestration runtime. It is one small, typed **evidence manifest** on the existing hook/ledger/file bus, generated at PreCompact/explicit handoff and read at recovery. Its job is not to retell the conversation. Its job is to identify the objective, authoritative artifacts, verified claims and their receipts, unresolved work, volatile executions, ownership, and one exact next action. Native session resume remains the primary same-session mechanism; Basic Memory remains semantic memory; the event ledger remains objective history. The manifest is the missing bridge between them.

The proposed local benefit is **very likely (80-90%)**, because the fields are derived from three independent real signals: the owner’s evidence-first recovery prompt, prior-session task-loss notifications, and the harness’s own current split between summaries and inspectable state. The exact reduction in owner corrections or failed resumptions is **UNVERIFIED; the settling experiment is the paired 30-boundary replay described in “Evaluation gate,” comparing current behavior against the manifest on completion accuracy, duplicate work, time-to-first-correct-action, and volatile-task recovery.**

## What the real examples say

### Example 1 — The summary was explicitly not evidence

At `2026-04-08T01:46:17.290Z`, the owner supplied this continuation:

> “CONTINUE. Do not trust the compaction summary for completion status — read the actual files. First, establish ground truth (5 minutes max): …”

The message then identifies `.remember\now.md`, three knowledge-base deliverables, `python -m verifier lint`, a bridge test harness, and a filtered `dotnet test` command. The corpus sample truncates at 600 characters, so the remainder is unavailable on this node (`corpus.json`, `/owner_correction_candidates/samples`; file key `aeb94ff3-639d-48d8-b24a-6f3ee9650c46.jsonl`, timestamp above).

This example yields six observed handoff properties without appealing to principle:

1. **Authority is assigned.** Files and command output outrank the summary.
2. **The recovery set is bounded.** It names a scratchpad, three deliverables, and targeted gates rather than “read the whole repo.”
3. **Completion is falsifiable.** Missing files and failing commands can disprove it.
4. **The first action is explicit.** “Establish ground truth” precedes new implementation.
5. **The cost is bounded.** The owner specifies five minutes.
6. **The handoff distinguishes state from prose.** A narrative may orient, but it cannot certify completion.

It would be an overclaim to say the compaction summary was objectively wrong: the raw summary and ensuing tool trace are not in the bundle. The supported statement is that the owner considered it insufficiently trustworthy for completion status and replaced it with readbacks. Whether the summary contained a false completion claim is **UNVERIFIED; retrieve the raw transcript around `2026-04-08T01:46:17.290Z` and compare each summary claim with the named artifacts and gate results.**

### Example 2 — Volatile work crossed the boundary without terminal state

Four individually read corpus samples mention work from a previous process/session:

- `2026-06-15T07:25:12.716Z`: background agent “Build memory-regression benchmark” was running when the previous Claude Code process exited; “in-process state was lost”; the notification directs the new session to inspect worktree/output before assuming the task landed.
- `2026-06-27T01:27:05.752Z`: a background shell command has no completion record; it may have been stopped or still running when the prior process exited; the notification again directs inspection of the output file.
- `2026-07-12T02:19:02.825Z`: workflow `pra-export-build-e2e` has no completion record, but supplies `resumeFromRunId: "wf_50774366-898"` and says completed agent calls will return cached.
- `2026-07-17T15:02:12.257Z`: the same resumable pattern appears for `primariro-e2e-build` with run ID `wf_5993ee65-662`.

Source: `corpus.json`, `/owner_correction_candidates/samples`, file/timestamp keys above. These are sample counts only; the corpus does not expose an exhaustive previous-session-task-loss field.

The contrast is concrete. The weak form has identity plus ambiguity (“no completion record”), and recovery requires forensic inspection. The stronger form adds an execution handle and reuse semantics. A handoff for volatile work is therefore materially better when it carries:

- execution kind and human label;
- task/tool-use ID;
- terminal state if known;
- output/worktree locator;
- last observed timestamp;
- resumable run ID and exact resume operation, when supported;
- warning not to infer completion from process disappearance;
- readback needed before relaunch, so duplicate work is avoided.

The claim that these fields would recover all background jobs is **almost certainly not (1-5%)**, because two samples explicitly describe UI stop, monitor timeout, agent teardown, or process exit paths that leave no completion marker. The more defensible claim is that they make ambiguity explicit and make resumable workflows cheaper to recover.

The following contract is derived from the examples above. Fields marked “direct” are present in at least one real corpus example; “harness-supported” fields are already available in source; “new join” means the data exists in separate channels but is not currently emitted as one handoff.

| Field | Why it matters in the real examples | Status in this harness |
|---|---|---|
| Objective and why | Repeated SWFOC continuation re-anchors the work and method | Harness-supported: per-session goal in `GoalModule`, `modules.py:1318-1338` |
| Lifecycle kind | Compact, process exit, same-session resume, fresh session, and subagent transfer have different recovery needs | Available as `event.source` for `resume|compact|clear`, `modules.py:973-978`; fresh replacement remains distinct |
| Authoritative state locators | The owner explicitly points to `.remember`, deliverables, worktrees, and output files | Direct; no single typed manifest |

### Minimal typed handoff

The smallest useful representation is not another prose document. It is a Markdown file with machine-readable frontmatter and short human sections, for example:

```yaml
schema: handoff-v1
handoff_id: <stable id>
lifecycle: compact | resume | fresh-session | provider-transfer | subagent
project: <stable project key>
session_hash: <redacted hash>
created_at: <UTC>
objective: <bounded redacted text>
runbook:
  path: <relative path>
  content_hash: <hash>
workspace:
  cwd_key: <redacted project key>
  branch: <name>
  worktree: <bounded locator>
  diff_hash: <hash>
verified:
  - claim: <claim>
    receipt_ids: [<ledger seq/id>]
    evidence: [<relative path or output locator>]
unfinished:
  - item: <item>
    state: in_progress | blocked | unverified
volatile_runs:
  - kind: workflow | shell | agent
    id: <task/run id>
    state: <last observed state>
    output: <bounded locator>
    resume: <exact operation or null>
failed_attempts:
  - failure_seq: <ledger seq>
next_action:
  command_or_readback: <one exact bounded step>
```

The prose body should explain only decisions and exceptions that are not derivable from those locators. Raw tool output should not be copied into the manifest; use hashes and bounded locators. That preserves the current contract’s “no raw-output prefix” rule at `/local_disk0/codexwork/bundle/codex/AGENTS.md:43-46` and the existing untrusted-data treatment at `modules.py:990-1003`.

## Current lifecycle, mapped precisely

### 1. Same-session continuation

Claude Code natively saves sessions continuously and offers `--continue`, `--resume`, named resume, and `/resume`; official documentation states this at <https://code.claude.com/docs/en/sessions> (retrieved lines 85-100). This is stronger than the local `/save-session` command for faithful same-session history because the local command asks the model to synthesize a separate file manually (`save-session.md:18-64`).

The local command is nevertheless a good handoff **schema**: it requires objective, evidence-backed worked items, exact failures, untried approaches, per-file state, decisions, blockers, next step, and environment (`save-session.md:68-180`). Its weak point is transport and trust, not field selection. It is manual, duplicates native persistence, and asks the same context that did the work to assert its own completion. The receiving `/resume-session` command reads the file, summarizes it again, and deliberately waits for user confirmation before acting (`resume-session.md:49-91`).

### 2. Compaction inside a session

Official Claude Code behavior re-injects project-root `CLAUDE.md`, unscoped rules, auto memory, and invoked skill bodies after compaction, with documented exceptions for path-scoped rules and nested `CLAUDE.md` files (<https://code.claude.com/docs/en/context-window>, retrieved lines 87-99). The local harness adds:

- active-goal re-anchor on PostCompact (`modules.py:1362-1378`);
- sanitized checkpoint on PreCompact with goal, ledger pointer, ten decisions, ten unresolved failures, and `.remember/now.md` (`modules.py:1440-1528`);
- same-session ledger replay of decision/failure/milestone on a compact recovery source (`modules.py:973-1003`).

This is a sensible defense against summary loss. But it does not bind a “done” statement to file state or verification receipt, and it does not capture volatile runs. The owner’s April 8 recovery prompt supplies exactly those missing readbacks.

### 3. Fresh replacement session

The automatic ledger path intentionally refuses to replay shared project state into a fresh startup (`modules.py:973-978`). That prevents cross-session goal bleed, a real concurrency hazard. It also means a fresh replacement session does not automatically receive the previous session’s active goal or compact checkpoint from this module.

The semantic recall lane can inject indexed Basic Memory notes on sufficiently long, overlapping prompts (`modules.py:1608-1621`), but it explicitly excludes paths containing `compaction-checkpoints` (`modules.py:1631-1643`). The global contract instead tells the model to manually search for `compaction checkpoint <project>` after compaction/resume (`/local_disk0/codexwork/bundle/codex/AGENTS.md:79-85`; Claude copy at `/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-11`). Thus the checkpoint is written automatically but recovery of it depends on a model following a rule and invoking Basic Memory.

This is not necessarily a bug: unconditional latest-checkpoint injection can select a sibling-session goal because project state is shared, and it can surface a stale checkpoint when no predecessor identity is checked. It is a missing **selection policy** for a true fresh-session handoff. The handoff manifest should only auto-surface when an explicit predecessor relation, matching project plus recent boundary marker, or user-provided handoff ID establishes intent.

### 4. Process exit with background work

The real notifications show that process exit can leave background work without a completion record. Current sanitized checkpoints have no `volatile_runs` section. Orchestration documentation has an operator control-plane block containing sessions, worktrees, diffs, approvals, and telemetry (`orchestrate.md:181-208`), but that is a prompt template, not demonstrated automatic capture.

### 5. Subagent/provider handoff

The cross-tool contract requires a structured summary with the original goal re-anchored (`codex/AGENTS.md:43-46`). `/orchestrate` specifies Context, Findings, Files Modified, Open Questions, and Recommendations (`orchestrate.md:48-69`) and optionally a control-plane block. This is orientation-rich but evidence-light: it has no required receipt IDs, claim status, artifact freshness, or execution resume handle.

## Proposals

### P0 — NATIVE (Claude Code already does this; we just enable it): make native resume the default for same-session continuation

Use `claude --continue`, `claude --resume`, or `/resume` when the intent is to continue the same saved conversation. Retain `/save-session` only for deliberate replacement-session/provider handoff or human-audited archival transfer. Official session persistence and resume semantics are documented at <https://code.claude.com/docs/en/sessions> (lines 85-100); the local manual command’s duplication is visible at `save-session.md:5-64`.

Expected benefit is **very likely (80-90%)** for fidelity of same-session continuation because native persistence retains the actual transcript rather than a model-authored re-summary. It will not recover missing external process state; the real task-loss samples show that limitation.

Anti-overfit gate: passes. This uses the native runtime and adds nothing.

### P1 — UNVERIFIED event-field availability — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): emit `handoff-v1` from existing state

Extend `SanitizedCheckpointModule` or a sibling module on the same dispatcher bus to emit the minimal manifest above. Populate only fields already available from the goal store, event ledger, receipt ledger, project key, relative workspace metadata, and registered task/workflow notifications. Preserve redaction and character bounds. Do not scrape or summarize the entire transcript.

The implementation is **likely (55-80%)** to fit below roughly 200 net new lines because checkpoint serialization, redaction, bounded retention, atomic write, and session hashing already exist at `modules.py:1440-1528`; the uncertain part is where task/workflow resume IDs are durably exposed. **UNVERIFIED implementation size and event availability; settle by dumping normalized hook payloads for a known running shell, Workflow run, and subagent, then sketching the field adapter before patching.**

Expected quality improvement is **very likely (80-90%)** for epistemic handoff checks because the April 8 example already demonstrates that locators plus commands allow completion claims to be falsified. Expected background-run recovery is only **likely (55-80%)**, because resumable workflow IDs exist in some samples but ordinary shell/agent exits may have no resume mechanism.

Anti-overfit gate: passes. It adds no runtime, database, daemon, trained critic, SaaS, or general guardrail framework. It is one bounded file on the current hook/ledger bus.

### P2 — UNVERIFIED live gate mode — CONFIG (settings/JSON only): promote lifecycle re-anchor rails after a controlled replay gate

Anti-overfit gate: passes. Existing module, existing event.

### P3 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): require evidence pointers for “done” in a handoff

When a handoff claims a file/task is complete, serialize ledger receipt IDs and relative artifact locators. If none exist, mark the claim `unverified`; do not block the handoff. At recovery, render verified and unverified items separately. This operationalizes the owner’s “read actual files” instruction without asking the next model to rediscover which claims lack proof.

The existing checkpoint already has a ledger pointer (`modules.py:1502`), and the ledger already sequences and fsyncs events (`ledger.py:851-879`). The missing join is from a handoff claim to a receipt/exhibit. Do not embed raw outputs.

Expected reduction in false completion carryover is **likely (55-80%)**, based on the owner’s explicit distrust of completion status and the current checkpoint’s absence of claim-bound evidence. The exact base rate of false completion across boundaries is **UNVERIFIED; settle with the 30-boundary labeled replay, because the distillation does not include summary-to-artifact joins.**

Anti-overfit gate: passes. This is deterministic serialization and display on the ledger bus, not a critic.

### P4 — UNVERIFIED provider event-field availability — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): add volatile-run terminality and resume handles

Capture task/workflow/subagent identity, last observed state, output/worktree locator, and resume handle when the provider supplies one. On SessionStart, state one of `completed`, `failed`, `stopped`, `unknown-at-boundary`, or `resumable`; never translate disappearance into success. If the state is unknown, the exact next action is readback, not relaunch.

Provider delivery of all these fields to the shared dispatcher is **UNVERIFIED; settle it by capturing redacted normalized hook payloads for one known background shell, one Workflow with a resume ID, and one subagent at their boundary events, then map which fields survive each adapter.**

This proposal is directly grounded in the four previous-session samples. It is **very likely (80-90%)** to improve the clarity of ambiguous exits, because ambiguity becomes a typed state rather than being buried in prose. It is **unlikely (20-45%)** to make arbitrary shells resumable, because the samples demonstrate resume IDs only for Workflow executions and explicitly say other teardown paths can lack completion markers.

Anti-overfit gate: passes if it consumes existing provider task notifications. If implementation instead requires a durable-execution engine, reject it: that would violate the anti-overfit gate and is not justified by these samples.

### P5 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): select a fresh-session predecessor explicitly

Do not broaden current project-ledger replay to every fresh session. Add an explicit handoff ID/predecessor token to `/save-session`, the handoff file, or startup prompt. SessionStart may inject the matching recent manifest only when project key and handoff ID agree; otherwise it should show at most a one-line “recent handoff available” locator.

This preserves the source’s deliberate fresh-session isolation (`modules.py:973-978`) and concurrency warning (`modules.py:1005-1033`). It addresses a replacement session without importing another session’s active goal by pathname coincidence alone.

Expected reduction in cross-session bleed is **very likely (80-90%)** relative to an unconditional “latest checkpoint” policy, because identity matching is deterministic. Expected usability is **likely (55-80%)**, because explicit IDs add a small operator step; a native session resume needs no such step.

Anti-overfit gate: passes. It is a selector on an existing SessionStart hook and file store.

### P6 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): make the handoff self-checking, not self-judging

Add a deterministic linter for required fields, bounded lengths, valid state enums, existing relative artifact locators, receipt IDs that resolve, and exactly one `next_action`. It must not judge whether prose is “good,” and must not block ordinary stopping. The linter returns missing/stale fields and lets the model repair the manifest or leave them explicitly `unverified`.

The owner’s example benefits from commands that mechanically settle status; the local `/save-session` template already insists no section be silently skipped (`save-session.md:50-64`). A schema linter makes that property falsifiable without another model.

Expected schema-completeness gain is **almost certain (90-99%)** for synthetic malformed fixtures because deterministic required-field validation is exact. Downstream task-success gain is **UNVERIFIED; settle in the paired replay rather than treating schema compliance as outcome quality.**

Anti-overfit gate: passes. It is a small validator, not a guardrail framework or trained critic.

### P7 — NATIVE (Claude Code already does this; we just enable it): keep project-root instructions and auto memory for stable cross-session knowledge

Stable conventions and recurring learnings belong in Claude Code’s native project-root `CLAUDE.md` and auto memory, which reload at session start and after compaction; volatile task state belongs in the handoff manifest. Official behavior and limits are documented at <https://code.claude.com/docs/en/memory> and <https://code.claude.com/docs/en/context-window> (memory lines 403-425; context lines 87-99).

This is a classification rule, not a demand to duplicate Basic Memory. The owner’s cross-provider semantic store remains Basic Memory per `codex/AGENTS.md:62-68,79-85`. Native Claude auto memory is provider-local; the handoff manifest must remain shareable and evidence-oriented.

## What not to build or copy

1. **No second orchestration runtime.** Native session resume, the shared dispatcher, ledger, hooks, and Basic Memory already cover transport and storage. The gap is a bounded join.
2. **No vector database or knowledge graph for handoffs.** Handoff selection needs exact identity, freshness, and provenance; similarity search is appropriate only for semantic background.
3. **No durable-execution engine.** Some Workflow runs are resumable; arbitrary lost shells are not. Capturing terminality and locators is justified, replacing process supervision is not.
4. **No trained handoff critic.** Required fields, receipt resolution, hashes, and artifact existence are deterministic. A model judge is **very likely (80-90%)** to be costlier and less reproducible for these exact checks, because it adds inference while the proposed predicates have deterministic oracles.
5. **No transcript dump as successor prefix.** It obscures authority, imports untrusted tool content, and violates the existing structured-handoff rule.
6. **No unconditional “latest checkpoint” injection.** Concurrent sessions share a project; latest-by-mtime can select a sibling objective. Use an explicit predecessor.
7. **No automatic assertion that a disappeared job failed or succeeded.** The real notifications preserve uncertainty; the manifest must do the same.

These exclusions satisfy the anti-overfit gate and preserve the deliberate minimal architecture.

- **completion recall:** fraction of truly done items surfaced as done;

- **time/tool calls to authoritative state:** bounded recovery cost;
- **unresolved uncertainty honesty:** unknown work remains `unknown-at-boundary`;
- **injected tokens/characters:** handoff overhead;
- **secret/path leakage:** redaction regression;
- **determinism:** same fixture produces the same selected manifest and field verdict.

## Frontier check and why it does not change the architecture

Claude Code’s current official context documentation says compaction replaces conversation history with a structured summary, then re-injects root instructions and auto memory, while path-scoped rules and nested instruction files wait for a matching file read (<https://code.claude.com/docs/en/context-window>, lines 84-105). This validates the local decision to persist task-specific state outside conversational history, but it also means a root instruction should contain only the stable recovery rule, not the changing task body.

LongMemEval-V2 (May 2026) evaluates 451 questions across static state, dynamic state, workflow, gotcha, and premise-awareness memory. Its strongest reported method, AgentRunbook-C, stores trajectories as files and gives a coding agent workflow documents, manifests, and helper scripts to assemble compact evidence; it reports 72.5% average accuracy versus 69.3% for an off-the-shelf coding agent and 48.5% for the strongest RAG baseline, with latency tradeoffs (<https://arxiv.org/abs/2605.12493>, abstract and §§1,4–5; retrieved lines 4-7, 48-52). The transfer to this owner’s software handoffs is **likely (55-80%)**, because both settings require targeted evidence from file histories, but the benchmark is web-agent memory, not cross-session coding continuation.

The useful frontier lesson is structural, not a mandate to import the system: files plus a manifest plus helper operations can outperform a heavier retrieval baseline while remaining inspectable. The local proposal adopts only that small pattern. It does not add a memory runtime, embeddings, graph, or agent controller. Local superiority over current Basic Memory is **UNVERIFIED and not claimed; the real-vault benchmark is required.**

## Alternatives considered

### Evolve the current checkpoint — selected

This reuses redaction, bounded retention, atomic writes, project/session keys, event ledger, receipts, and native lifecycle events. It directly fills every field exposed by the corpus examples without adding another runtime.

### Replace everything with native session resume — rejected as incomplete

Native resume is the right default for same-session history, but the real corpus shows process-exit ambiguity and cross-session/provider handoff needs. A transcript cannot prove external job terminality or select a replacement-session predecessor safely.

### Use `/save-session` unchanged — rejected as the primary path

Its schema is strong, but it is manual, narrative, self-asserted, and duplicates native session persistence. It has no receipt binding or volatile-run identity. Preserve it as an explicit UI over `handoff-v1`, not as an independent truth source.

### Inject the latest sanitized checkpoint on every SessionStart — rejected

The current code deliberately isolates fresh sessions and warns about sibling sessions. Latest-by-time is not predecessor identity.

### Put everything into Basic Memory and recall semantically — rejected

Semantic memory answers “what prior knowledge is relevant?” A handoff must also answer “which exact execution and workspace state should I resume?” The latter requires identity and readback, not similarity.

### Store raw transcripts and let a large-context model reconstruct state — rejected

Raw history is not authoritative external state; the April 8 example explicitly demands file/test readback. It also increases context and prompt-injection exposure. LongMemEval-V2’s file approach still uses manifests/helper retrieval to assemble compact evidence rather than blindly passing all trajectories.

## Final design decision

Adopt a three-layer context lifecycle:

1. **Native session transcript** for faithful same-session continuation.
2. **`handoff-v1` evidence manifest** for a bounded boundary state: authoritative locators, receipts, unresolved work, volatile executions, ownership, and next action.
3. **Basic Memory / native auto memory** for durable semantic knowledge and stable conventions, not execution terminality.

Generate layer 2 on PreCompact and explicit handoff; select it by explicit predecessor identity on a fresh session; lint it deterministically; keep stored prose untrusted; and verify external state before implementation resumes. This design is **very likely (80-90%)** to improve handoff correctness because it directly instantiates the recovery behavior the owner already wrote by hand and adds the execution identifiers shown in stronger prior-session notifications. Its effect size is **UNVERIFIED until the fixed 30-boundary replay and mounted-vault study are run.**

Full replacement is not justified by the available evidence. The current architecture already has the native and existing-bus primitives; its defect is an incomplete join and ambiguous authority, not a missing runtime. A radical replacement would discard working resume, hook, ledger, and file-memory mechanisms without evidence that it solves either observed loss class.
