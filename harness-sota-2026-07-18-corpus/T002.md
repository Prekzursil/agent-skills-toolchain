# T002 — Competitive teardown: GitHub Copilot / Copilot Workspace

**Research date:** 2026-07-19 UTC  
**Unit:** T002  
**Subject:** the retired GitHub Copilot Workspace technical preview, its surviving design ideas, and the current GitHub Copilot cloud agent / Copilot CLI / VS Code agent system that replaced its practical role.

## Executive verdict

GitHub Copilot Workspace itself is not a current competitor to copy wholesale. GitHub's own GitHub Next page says the technical preview was sunset on **2025-05-30**. Its durable contribution was a highly inspectable, editable chain—task → current/desired-state specification → per-file plan → implementation → validation—rather than a novel autonomous loop. The current competitor is a family of surfaces: Copilot cloud agent for isolated background pull-request work, Copilot CLI/VS Code for a local tool loop, Copilot Memory for cross-session facts, and GitHub-native validation/review controls. Sources: [GitHub Next: Copilot Workspace](https://githubnext.com/projects/copilot-workspace/), [2024 launch description](https://github.blog/news-insights/product-news/github-copilot-workspace/), and [current cloud-agent overview](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent).

The best ideas to port are narrow and bus-compatible:

1. a mechanically inspectable “what customizations actually loaded” manifest with known-positive controls;
2. tool exposure separated from tool approval, with deny-overrides-allow and per-agent least privilege;
3. repository memories carrying source coordinates/content hashes and being revalidated at recall;
4. a default, configurable validation bundle whose results are visible and attributable;
5. an editable current-state/desired-state/per-file plan contract for genuinely large changes.

The strongest things **not** to copy are GitHub's hosted orchestration plane as a second runtime, its managed semantic index as a new vector-memory dependency, cloud-agent MCP's silent autonomous invocation model, and automatic `/fleet` use as a default. Those would violate the anti-overfit gate or enlarge the failure surface without targeting this owner's measured defects.

The comparative conclusion is **very likely (80-90%)**, because it is supported by current first-party documentation for every named Copilot mechanism, the pinned 10.62 GB corpus for the owner's dominant reliability failures, and direct reads of the unpacked harness configuration; the remaining uncertainty is whether undocumented GitHub internals materially outperform the documented controls. A settlement experiment would run the same 30-task, mutation-and-verification suite through Copilot CLI/cloud agent and this harness, scoring success, false completion, tool-error rate, human interventions, latency, and credits.

## 1. Scope, product lineage, and evidence discipline

### 1.1 “Workspace” is historical; “cloud agent” and CLI are current

Copilot Workspace's public architecture was a sequence of specialized experiences: brainstorm, specification, plan, implementation, integrated build/test, and repair. Its specification contained editable bullet lists for the current and desired state; its plan listed every file to create, change, or delete and the actions for each; editing an upstream artifact regenerated downstream work. The implementation diff was itself editable. GitHub also versioned workspace context/history and let collaborators fork their own iterations. Source: [GitHub Next: Copilot Workspace](https://githubnext.com/projects/copilot-workspace/) and the [December 2024 technical-preview changelog](https://github.blog/changelog/2024-12-30-expanding-access-to-the-github-copilot-workspace-technical-preview/).

GitHub later added automatic build-and-test after implementation, with a repair path on failures. Source: [Copilot Workspace auto-validation changelog, 2025-01-31](https://github.blog/changelog/2025-01-31-copilot-workspace-auto-validation-go-to-definition-and-more/). GitHub's product page now explicitly records the 2025-05-30 sunset: [GitHub Next: Copilot Workspace](https://githubnext.com/projects/copilot-workspace/).

Current Copilot cloud agent retains the repository research → plan → branch changes → tests/linters → review/PR shape, but runs in an ephemeral GitHub Actions environment and integrates with normal GitHub branches, commits, logs, checks, and pull requests. Copilot CLI adds plan mode, an iterative tool loop, autopilot continuation, subagents, hooks, skills, plugins, MCP, compaction, and memory. Sources: [cloud-agent overview](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent), [Copilot CLI overview](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli), and [Copilot customization cheat sheet](https://docs.github.com/en/copilot/reference/customization-cheat-sheet).

Accordingly, this teardown treats Workspace as the design ancestor and current Copilot agents as the operational competitor. It does not attribute current CLI/cloud capabilities retroactively to the sunset Workspace preview.

## 3. Agent loop

### 3.1 What Copilot does

The original Workspace loop was unusually legible. It first generated an editable representation of “how the code works now” and “what it should do,” then an editable per-file plan, then a diff. A change to specification or plan regenerated downstream artifacts. That design reduced the reviewer's need to infer intent from a large diff. Source: [GitHub Next: Copilot Workspace](https://githubnext.com/projects/copilot-workspace/).

Current cloud agent is less stage-rigid. It evaluates the prompt, explores a single repository in an ephemeral Actions-powered environment, plans, modifies a dedicated branch, runs tools, and exposes progress in session logs. The user can research/plan/iterate before creating a PR on GitHub.com, or delegate directly to a PR from other entry points. Source: [About Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent).

Copilot CLI separates:

- **plan mode**, which asks clarifying questions and creates a structured plan without editing;
- **normal interactive execution**, which stops at model decision points;
- **autopilot**, which autonomously continues model turns until it calls `task_complete`, optionally capped by `--max-autopilot-continues`;
- **`/fleet`**, which has a main agent decompose and coordinate parallel subagents.

Sources: [Copilot CLI overview](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli), [autopilot](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/autopilot), and [`/fleet`](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/fleet).

### 3.2 What to port

#### Proposal A — editable intent contract

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** For long-horizon code mutations, add a plan template with three required fields: `current_state` (claims with paths), `desired_state` (acceptance conditions), and `file_operations` (create/modify/delete plus reason). Keep it editable and require re-rendering downstream plan items after a load-bearing change. This rides the existing plan/rule surface; it is not a new planner service.

Expected benefit is **likely (55-80%)**, because Workspace's public design makes misunderstandings visible before code generation and this owner's D4 shows that a fabricated orchestrator constraint propagated to about 15 agents (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160`). The uncertainty is whether a mandatory form adds more friction than error reduction on this owner's task mix. Settlement experiment: randomly assign 40 comparable long-horizon tasks to the current plan format or the three-field template; measure owner corrections before first edit, downstream rework, tokens, and completion rate.

What not to copy: do not force the Workspace stage chain on small tasks. A mandatory spec/plan/regenerate sequence would conflict with the anti-overfit gate and the owner's own brief that minimal agent loops remain competitive.

#### Proposal B — bounded autonomous continuation

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Retain existing native agent continuation, but expose a per-run continuation/tool-call budget and a visible stop reason, analogous to `--max-autopilot-continues`. Do not create a durable-execution engine.

Expected benefit is **likely (55-80%)**, supported by the corpus's retry-loop/error fingerprints and Copilot's explicit cap mechanism. It is not more certain because the current harness already has two-strike prose and anti-degeneration machinery. Settlement experiment: replay the top 50 retry-loop patterns with and without a 10-continuation cap plus two-strike pivot; compare wasted calls and false early stops.

### 3.3 Where ours is better

The owner harness explicitly re-anchors the original goal, distinguishes terminal success/failure, requires structured subagent handoffs, and calls for a fresh-context check after the second failure (`/local_disk0/codexwork/bundle/claude/AGENTS.md:22-70`). Workspace's public materials describe steerability and repair but not error fingerprints, an anti-grind state machine, or claim-bound receipts. Copilot's current `task_complete` is an agent-declared terminal condition; its docs do not state that the call is mechanically tied to a fresh relevant verification receipt.

The conclusion that Copilot lacks receipt binding is **UNVERIFIED**: public docs do not describe it, but absence from docs is not proof of implementation absence. A settlement experiment would intentionally make an unrelated test pass after a target failure, then inspect whether Copilot can declare completion and whether the session log contains a task-bound validator.

## 4. Context management

### 4.1 Retrieval and repository understanding

GitHub automatically builds a semantic code-search index and lets cloud agent search by meaning when exact identifiers are unknown. Index creation is automatic; GitHub says a large repository's initial index can take up to 60 seconds and is refreshed around the start of later conversations. Source: [Indexing repositories for GitHub Copilot](https://docs.github.com/en/copilot/concepts/context/repository-indexing).

VS Code also uses workspace indexing and accepts explicit files, folders, symbols, source-control changes, terminal output, URLs, and `#codebase` as context. Source: [VS Code context management](https://code.visualstudio.com/docs/chat/copilot-chat-context). This is a useful interface distinction: automatic retrieval is inspectable and the user can pin load-bearing sources.

### 4.2 Window management and large outputs

Copilot CLI's `/context` command breaks usage down into system prompt, custom instructions, built-in tools, MCP tools, messages, buffer, and free space. Tool output over 20 KiB is written to a temporary file by default, with only a preview and path sent to the model; this applies to MCP results too. Around 80% usage, background compaction begins; near 95%, execution may wait for it. Compaction preserves original user instructions and plan/todo state, creates a checkpoint, and explicitly loses fine detail. Source: [Managing context in Copilot CLI](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-cli/context-management).

The owner harness already has a large auto-compact window (`/local_disk0/codexwork/bundle/claude/settings.json:686-697`), saved Codex history (`/local_disk0/codexwork/bundle/codex/config.toml:39-40`), and the stronger rule that objective ledger replay—not an in-context summary—is ground truth (`/local_disk0/codexwork/bundle/claude/AGENTS.md:28-35`). That objective/semantic split is better than treating a lossy compaction summary as history.

### 4.3 What to port and reject

#### Proposal C — context bill of materials — UNVERIFIED full field availability

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At session start/resume and on demand, emit a bounded manifest containing: active instruction files and hashes, selected skills, agents, hook configurations, MCP servers and enabled tool counts, context bytes by category, and detector-control results. Include one known-present control for each discovery lane. This is the Copilot `/env` and `/context` idea adapted to the owner's D2/D3 detector failures.

Expected benefit is **very likely (80-90%)**, because the local defect file records seven false absence conclusions caused by unvalidated probes (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`), while Copilot exposes `/env` and `/context` in its [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference). Uncertainty remains around hook payload availability. **UNVERIFIED** whether every Claude/Codex discovery API exposes a stable source path and enabled state; the settlement experiment is to capture one real SessionStart payload per provider, enumerate a known instruction/skill/agent/hook/MCP, and compare the manifest to direct filesystem/config reads.

#### Proposal D — uniform large-result spill

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Normalize any tool or MCP result above a configurable byte threshold into `{preview, artifact_path, sha256, byte_count, truncation=false}` and require explicit ranged reads. Preserve the raw file until session end. This should be one adapter behavior, not per-tool wrappers.

Expected benefit is **likely (55-80%)**, based on Copilot's 20 KiB mechanism and this corpus's large, failure-prone tool population. The exact benefit is **UNVERIFIED**; settlement experiment: replay the 100 largest available result samples, measuring context consumption, downstream factual accuracy, and extra read calls with thresholds of 20, 64, and 256 KiB.

#### Rejected — semantic index as a new harness service

A new vector database or managed semantic-index service fails the explicit anti-overfit gate. GitHub can amortize a hosted index across its platform; this owner already has exact search, model-native exploration, and semantic memory. The 2026 Copilot changelog reports semantic search made agent tasks only 2% faster with no quality change: [semantic search changelog](https://github.blog/changelog/2026-03-17-copilot-coding-agent-works-faster-with-semantic-code-search/). That evidence does not justify a new local memory/runtime dependency.

## 5. Memory

### 5.1 Copilot Memory's concrete mechanism

Copilot Memory is a public-preview managed store with two lanes:

- repository facts such as architecture, build commands, conventions, and project rules;
- user preferences tied to the initiating user and billing entity.

Repository facts carry citations to supporting code. At use time, Copilot checks those citations against the current branch and uses only validated facts. Repository owners can inspect and delete facts. User preferences can include direct user-quote citations and can be viewed/deleted; enterprise administrators can export/delete them. Unused entries expire after 28 days, with the timer resetting after successful validation/use. Memories learned in cloud agent can be used in code review and CLI, subject to feature-specific scope. Source: [About GitHub Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory).

This is materially different from merely retrieving semantically similar prose: the remembered assertion is attached to evidence and checked against current code.

### 5.2 Our position

The owner harness has a better conceptual split—semantic basic-memory versus objective append-only event history—but its contract says basic-memory does not auto-load and tells the model to query and write it manually (`/local_disk0/codexwork/bundle/codex/AGENTS.md:79-85`). A bounded search across the unpacked harness found the known-present memory and ledger mechanisms, but no 28-day/TTL, source-citation, current-branch-validation terms in the memory path. The second independent signal is the explicit memory contract, which documents manual supersession via permalinks rather than automatic source validation (`/local_disk0/codexwork/bundle/codex/AGENTS.md:83-85`). Therefore the packaged subject does not demonstrate Copilot-style source-validated facts.

### 5.3 What to port

#### Proposal E — cited, revalidated semantic facts

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing basic-memory write/read wrapper, not the store, with a compact provenance envelope:

```json
{
  "claim": "Tests use pytest markers from pyproject.toml",
  "repo": "<stable repo id>",
  "ref_at_capture": "<commit>",
  "path": "pyproject.toml",
  "line_anchor": "tool.pytest.ini_options",
  "evidence_sha256": "<normalized supporting span hash>",
  "captured_at": "<UTC>",
  "last_validated_at": "<UTC>",
  "status": "candidate|validated|stale|superseded"
}
```

On recall, resolve the path on the current branch, locate the semantic anchor, recompute the normalized span hash, and inject only validated facts. A changed/missing span is returned separately as stale evidence, never silently injected. Keep current manual review and supersession. Use a configurable stale-candidate cleanup window; do not blindly copy GitHub's 28 days.

Expected benefit is **very likely (80-90%)**, because it directly addresses stale durable knowledge while preserving the existing memory bus, and Copilot documents exactly this validation design. The line-anchor relocation success rate is **UNVERIFIED**; settlement experiment: capture 100 facts, apply rename/move/edit/delete mutations, and measure correct validation, stale detection, false invalidation, and latency. The recommendation does not depend on the unverified relocation mechanism: a strict path+hash first version can conservatively stale out moved facts.

### 5.4 Where Copilot is worse

- Its memory implementation is managed and public preview, so the owner cannot audit the full selection, extraction, or relevance algorithm from the cited docs.
- A fixed 28-day unused expiry can delete rare but valuable operational knowledge. The owner's explicit supersession and event-history split is more suitable for long-lived personal knowledge.
- User preferences are validated by Copilot's “best judgment,” not the current-branch citation rule used for repository facts. That is a weaker evidentiary contract.
- Do not copy autonomous promotion of inferred preferences into high-authority rules. Keep candidates reviewable and lower priority than explicit user instructions.

## 6. Tools and MCP handling

### 6.1 Copilot's model

Copilot separates three decisions that are too often conflated:

1. whether the model can see a tool (`--available-tools`, `--excluded-tools`, or a custom agent's `tools` list);
2. whether a visible tool may execute without asking (`--allow-tool`, `--deny-tool`, saved approvals);
3. whether a server/tool is installed/configured at all.

Deny rules override allow rules and even `--allow-all`. Rules can target tool kinds, exact commands/subcommands, paths, URLs, MCP servers, and MCP tools. Source: [Allowing and denying tool use](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools).

Cloud agent configures local/stdio/http/SSE MCP servers at repository or custom-agent scope. The `tools` array is an explicit allowlist; secrets exposed to MCP must use the `COPILOT_MCP_` prefix. GitHub and Playwright servers are defaulted with narrow access: GitHub's token is read-only to the current repo; Playwright can reach only the agent's localhost by default. Sources: [MCP and cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/mcp-and-cloud-agent), [repository MCP configuration](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers), and [custom agent configuration](https://docs.github.com/en/copilot/reference/custom-agents-configuration).

### 6.2 Capability gaps to port

#### Proposal F — dead-server admission and circuit state

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Before exposing MCP tools to the model, perform one bounded initialize/list-tools health probe; expose tools only for servers in `HEALTHY`. After a deterministic “not connected” response, open a per-server circuit for the session and inject one actionable status, not another callable schema. Allow an explicit user retry or cooldown probe to close it. Persist no new service state beyond the existing session/harness state.

Expected benefit is **almost certain (90-99%)**, because the pinned ground truth records 532 Tavily extract calls at 25.8% error and 135 “not connected” responses from a dead MCP, and the same fingerprints appear in `/local_disk0/codexwork/bundle/inputs/corpus.json:4389` and `:9130-9147`. The remaining uncertainty is the fraction of calls made before a health signal was observable. Settlement experiment: replay all “not connected” sequences and calculate calls avoided after the first deterministic failure, with a known-healthy MCP as the detector control.

#### Proposal G — per-agent least-privilege tool bundles — UNVERIFIED cross-provider parity

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Continue the existing Claude agent `tools:` allowlists, but make them provider-neutral and generated from one manifest. Define explicit bundles (`read-research`, `code-edit`, `test-run`, `review`, `external-read`) and deny unlisted MCP tools. A docs agent should not see edit/destructive tools; a reviewer should not see write tools; an MCP server should expose named read tools rather than `*`.

Expected benefit is **very likely (80-90%)**, supported by Copilot's separation of exposure/approval and the owner's dead-server/tool-schema error rates. The current Claude profiles prove the mechanism is already present for named agents—examples at `/local_disk0/codexwork/bundle/claude/agents/planner.md:4-5` and `docs-lookup.md:4-5`—but cross-provider parity is **UNVERIFIED**. Settlement experiment: render the same four bundle profiles into Claude and Codex, invoke each agent, and compare the actually visible tool set via a known-present/known-absent matrix.

### 6.3 Where Copilot is worse

- Cloud agent supports MCP **tools only**, not MCP resources or prompts, and does not support OAuth-based remote MCP authentication. Source: [MCP and cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/mcp-and-cloud-agent).
- Once repository MCP tools are configured, cloud agent uses them autonomously without per-call approval. That is unsafe for write-capable tools; GitHub itself recommends allowlisting read-only tools.
- Repository MCP settings apply to both cloud agent and code review. This convenient convergence can overgrant a reviewer tools intended for an implementation agent.
- A configured custom agent with no `tools` field gets all available tools; omission is permissive. The owner harness should prefer an explicit bundle or empty-by-default behavior.

## 7. Permission model and isolation

### 7.1 Local CLI permissions

Copilot CLI allows read-only exploration automatically and asks for modifying commands, file changes, URLs, and other risky tools. Approvals can be one-shot, session-scoped, or saved for a repository/location. It separately verifies filesystem paths and URLs. Deny rules win over all allows. Enterprise/device policy can suppress bypass modes. Source: [Allowing and denying tool use](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools) and the [CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference).

Autopilot does **not** silently turn limited permission into broad permission: with limited permissions it automatically denies approval-requiring calls. However, GitHub's UI recommends enabling all permissions for best results, and `--allow-all`/`--yolo` grants all tools, paths, and URLs. This is a sharp edge, not a best practice to copy. Source: [Copilot autopilot](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/autopilot).

### 7.2 Cloud rail

Cloud agent uses a non-interactive ephemeral environment with constrained network. Only users with repository write access can trigger it; untrusted commenters are not passed to it. It can push only to its one working branch with limited credentials, cannot approve/merge its PR, cannot mark it ready for review, and is subject to branch protection. By default, Actions workflows wait for a write-authorized human to click “Approve and run.” Commits are signed and link to session logs; administrators receive audit events. Hidden HTML-comment input is filtered. Source: [Risks and mitigations](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/cloud-agent/risks-and-mitigations).

### 7.3 What to port

#### Proposal H — safe base posture

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Change the default local posture from blanket `never` + `danger-full-access` to workspace-scoped writes and approval for network, credential, destructive, and out-of-scope filesystem actions. Preserve explicit per-run escalation for genuinely autonomous work. This proposal concerns native sandbox/approval configuration, not another guardrail framework.

Expected safety benefit is **almost certain (90-99%)**, because the current configuration explicitly disables approval and enables full access (`/local_disk0/codexwork/bundle/codex/config.toml:6-7`), while Copilot demonstrates granular approval and deny precedence. Productivity cost is **likely (55-80%)** if applied without durable narrow approvals, supported by GitHub's own warning that limited autopilot may fail. Settlement experiment: run 30 representative tasks under current mode and workspace-write/network-ask mode; compare prompts, blocked legitimate calls, destructive attempts prevented, and completion time.

#### Proposal I — branch/PR isolation for unattended repository mutation — UNVERIFIED cross-provider attribution

## 8. Customization surface: rules, skills, hooks, agents, plugins

### 8.1 Instructions and rules equivalents

Copilot supports personal, organization, repository-wide, path-specific, and agent instruction files. It reads `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md`, nested `AGENTS.md`, and root `CLAUDE.md`/`GEMINI.md`; CLI also discovers user-level modular instructions and can show/disable them with `/instructions`. Path-specific frontmatter uses `applyTo`; cloud agent/code review exclusions can use `excludeAgent`. Sources: [CLI custom instructions](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions) and [repository custom instructions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions).

This is now close to the owner's cross-tool `AGENTS.md` plus language/path rules. Copilot's compatibility with `AGENTS.md`, `CLAUDE.md`, `.claude/agents`, `.claude/settings`, and `.claude/skills` is strategically good: it lowers migration cost and makes customization assets portable rather than vendor-exclusive.

### 8.2 Skills, agents, hooks, and plugins

Copilot skills use the same progressive-disclosure shape: a folder with `SKILL.md`, optional scripts/resources, selected when the description is relevant. Project skills can live under `.github/skills`, `.claude/skills`, or `.agents/skills`; personal skills under `~/.copilot/skills` or `~/.agents/skills`. Source: [customization cheat sheet](https://docs.github.com/en/copilot/reference/customization-cheat-sheet) and [adding skills](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills).

Custom agents are Markdown/YAML profiles with instructions, model/tool selection, MCP servers, and configuration precedence. Git commit SHA versions the profile; a PR session continues using the same version. An explicit empty tool list disables all tools. Source: [custom agent configuration](https://docs.github.com/en/copilot/reference/custom-agents-configuration).

Hooks cover session start/end, prompt submitted, pre/post tool, main/subagent stop, and errors. `preToolUse` can allow/deny/ask or modify arguments; main/subagent stop can block and force another turn; post-tool can modify the result or inject context. CLI policy hooks can be machine-wide, administrator-owned, and non-disableable. Cloud hooks run in the ephemeral sandbox and local files disappear at job end. Source: [hooks concepts](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/hooks) and [hooks reference](https://docs.github.com/en/enterprise-cloud@latest/copilot/reference/hooks-reference).

Copilot plugins package agents, skills, commands, hooks, MCP, LSP, and extensions under one manifest and marketplace cache. Source: [CLI plugin reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference).

### 8.3 Comparative judgment

The owner harness has more domain-specific agents, rules, hooks, and provider normalization than the public Copilot defaults. Claude agent profiles already restrict tools (`/local_disk0/codexwork/bundle/claude/agents/*.md`, known-present examples above), and shared dispatch spans more lifecycle events than Copilot cloud hooks (`/local_disk0/codexwork/bundle/claude/settings.json:81-523`). The owner's low skill utilization—78 of roughly 355 installed—and broken hook telemetry mean breadth is not translating reliably into selection or measurement.

#### Proposal J — one customization manifest and cachebuster

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Define a provider-neutral manifest for each installable package: id, version/source commit, agent/skill/hook/MCP/LSP assets, supported providers, required tools, declared hook events, and health checks. At session start, render only the chosen provider surface and expose the resolved manifest through Proposal C. Invalidate discovery caches when the source commit or manifest hash changes.

Expected benefit is **very likely (80-90%)**, because Copilot's plugin packaging/versioning directly addresses asset discoverability while the corpus records only 78/~355 skill use and the pinned orphan directories inflate process command lines. Exact reduction in ENAMETOOLONG is **UNVERIFIED**, because this unit did not inspect Windows plugin loader argv construction; settlement experiment: render a clean manifest-only install in a disposable Windows profile, measure CreateProcess command length and Glob spawn success against the current profile.

### 8.4 What not to copy

- Do not create a second marketplace/runtime. A manifest may describe and render existing buses; it must not own execution.
- Do not add embeddings-based skill retrieval as a new vector service. First repair deterministic inventory, descriptions, health, and selection telemetry.
- Do not copy cloud hook persistence semantics: local log files are discarded at job end. The owner needs objective, durable, redacted telemetry.
- Do not copy blanket fail-closed hook behavior. Copilot fails closed for a crashed `preToolUse` command but fails open on timeout; the owner's D1 false positives show that a faulty detector can become a correctness/productivity outage. Enforce only validated, narrow, dangerous-action rules and shadow-test new detectors.

## 9. Multi-agent support

### 9.1 Copilot mechanism

Copilot CLI `/fleet` asks the main agent to decompose a task, run independent subtasks concurrently, and aggregate their results. Each subagent has its own context window. Custom agents can be selected automatically or named explicitly. The main agent manages the workflow. Source: [`/fleet`](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/fleet).

CLI supports `list_agents`/`write_agent` sibling communication and enforces depth and concurrency caps; current documentation lists default maximum depth 6 and plan-dependent concurrency, overridable within clamps. Source: [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference).

GitHub cloud can run multiple **independent sessions** in parallel, but the customization matrix marks subagents unsupported on GitHub.com. Source: [customization cheat sheet](https://docs.github.com/en/copilot/reference/customization-cheat-sheet). This distinction matters: a dashboard of concurrent PR agents is not a cooperating agent tree.

### 9.2 Comparison

The owner already has depth 8, concurrency 8, agent identity, fanout, and multi-agent v2 (`/local_disk0/codexwork/bundle/codex/config.toml:77-80`, `:101-106`, `:125-130`), plus a structured-handoff rule (`/local_disk0/codexwork/bundle/claude/AGENTS.md:59-63`). Claude has explicit SubagentStart/SubagentStop/Task/Teammate lifecycle hooks (`/local_disk0/codexwork/bundle/claude/settings.json:419-477`). These are at least as rich as documented Copilot CLI coordination.

Copilot's advantage is productized visibility and explicit isolated context; the owner's advantage is governance: no raw-output prefix, original-goal re-anchor, and fresh-context verification. Copilot's own docs warn that `/fleet` increases credits and does not help sequential tasks.

#### Proposal K — make fanout opt-in by task graph — UNVERIFIED causal benefit

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Preserve the existing agent tree, but allow parallel fanout only when the plan declares at least two write-disjoint or read-only independent subtasks, an integration owner, and a verification join. Record per-child context sources and changed paths in the handoff. Do not add an orchestration runtime.

Expected benefit is **likely (55-80%)**, supported by Copilot's explicit warning about sequential tasks and this owner's structured-handoff rules. The benefit is not more certain because the corpus does not provide clean causal multi-agent outcome telemetry. **UNVERIFIED** multi-agent success/cost delta; settlement experiment: take 20 naturally decomposable and 20 sequential tasks, randomize current fanout versus declared-task-graph fanout, and measure merge conflicts, duplicated reads, credits/tokens, wall time, and acceptance.

### 9.3 What not to copy

- Do not make `/fleet` the default for “large” prompts. Complexity is not the same as independence.
- Do not majority-vote free-form results. Separate context windows reduce shared anchoring but do not make signals mechanically independent if agents consume the same flawed premise.
- Do not copy GitHub's hosted multi-session dashboard as a BUILD-LARGE control plane. The current native agent tree and worktree rail already cover execution; a new runtime is explicitly rejected.

## 10. Verification and self-check

### 10.1 Copilot's verification stack

The original Workspace let users build, run, and test in an integrated environment or Codespace, and later automatically ran build/test after implementation with a repair agent reacting to failures. Sources: [Workspace launch](https://github.blog/news-insights/product-news/github-copilot-workspace/) and [auto-validation changelog](https://github.blog/changelog/2025-01-31-copilot-workspace-auto-validation-go-to-definition-and-more/).

As of 2026, Copilot cloud agent automatically runs project tests and lint plus a default security/quality suite:

- CodeQL;
- secret scanning;
- new-dependency checks against GitHub Advisory Database malware and High/Critical CVSS entries;
- a second opinion from Copilot code review.

When findings occur, the agent attempts repairs before stopping and requesting review. Repository administrators can disable individual validators. Sources: [validation-tools changelog, 2026-03-18](https://github.blog/changelog/2026-03-18-configure-copilot-coding-agents-validation-tools/) and [cloud-agent risks and mitigations](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/cloud-agent/risks-and-mitigations).

Human review remains a real gate: the agent cannot approve or merge, and the initiating user cannot approve the agent PR under required-approval rules. Session logs show analyses/actions; signed commits link back to logs.

### 10.2 Our stronger primitive and its defects

The owner's typed receipts are more epistemically precise than “some tests ran”: they classify command results, fingerprint argv, require fresh receipts after mutation, and can demand a passing rerun of the exact command that previously failed (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:374-400`, `:1093-1163`; `/local_disk0/codexwork/bundle/agents/harness/modules.py:2093-2212`). The contract also demands a fresh-context critic (`/local_disk0/codexwork/bundle/claude/AGENTS.md:72-83`).

But this advantage is not fully realized. The pinned defects show false failure verdicts from payload/prose substring matching and unvalidated absence detectors (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-87`, `:111-147`). The corpus also records a high StructuredOutput schema mismatch rate and unread-before-write failures. A theoretically stronger receipt system that misclassifies the event is worse than a simpler reliable check.

### 10.3 What to port

#### Proposal L — default validation bundle, bound to receipts — UNVERIFIED BUILD-SMALL sizing

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a repo-configured validation manifest, not a new framework:

```yaml
validate:
  target: ["<project test command>", "<project lint command>"]
  security: ["secret-scan", "dependency-audit", "static-analysis"]
  require_after_last_mutation: true
  exact_failed_argv_must_turn_green: true
  independent_review: "risk-triggered"
```

The existing Stop/completion hook launches only configured existing tools, captures argv/exit/result hashes as typed receipts, checks freshness, and emits a single validation summary. Security scanners are optional by repository and risk; they do not become an observability SaaS or guardrail framework.

Expected benefit is **very likely (80-90%)**, because it combines Copilot's default breadth with the owner's existing receipt binding. The claim that it fits under 200 lines is **UNVERIFIED**; settlement experiment: implement a disposable prototype against two repos and count non-test logical lines while proving test/lint/secret/dependency/static receipt ingestion. If it exceeds 200 lines, reduce scope rather than promote it to BUILD-LARGE.

#### Proposal M — detector qualification before enforcement

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Every detector manifest must ship known-positive, known-negative, mention-vs-use, negation, structured-field, success-with-failure-word, and timeout/crash fixtures. New detectors run shadow-only until the recorded suite passes on both provider adapters. The enforcement loader refuses a detector without its controls.

Expected benefit is **almost certain (90-99%)**, because D1 and D2 record multiple independent false positives and seven false absence conclusions caused by precisely these missing controls (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-87`, `:111-129`). The remaining uncertainty is only the number of future detector classes not represented in the fixtures. Settlement experiment: replay all recorded D1 fires plus real dangerous controls and require zero false blocks and detection of every known real occurrence.

### 10.4 Where Copilot is worse

- GitHub's docs say validators run and the agent attempts repairs; they do not document claim-to-receipt freshness, exact failing-command identity, or binding a validator to the acceptance criterion. This absence is **UNVERIFIED**; use the unrelated-green settlement experiment in §3.3.
- Copilot code review is another model-based signal, not mechanically independent proof. It is useful dissent, not an oracle.
- Administrators can disable validators. That configurability is necessary, but a UI toggle can silently weaken assurance unless logs identify the actual enabled set. The owner should always record validator identity/version/config in the receipt bundle.
- GitHub's PR metrics—created/merged counts and median time-to-merge—measure throughput, not correctness. Source: [cloud-agent overview, metrics section](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent).

## 15. Bottom line

Copilot's frontier advantage is not “more agents.” The owner already has deep agents, skills, hooks, MCP, memory, and receipts. Copilot's advantage is that several mundane control surfaces are now productized together: the system can say what it loaded, narrow what the model can see, narrow what it may execute, isolate unattended writes, revalidate remembered repository facts, and run a visible default validation suite before a human merge.

The owner harness remains stronger in three important ways: provider-neutral behavior, explicit objective-versus-semantic memory, and verification receipts tied to mutation freshness and failing-command identity. Its problem is reliability of the control plane: dead tools remain callable, detectors confuse mention with use, capability measurement lacks validated controls, and the default Codex permission posture is broad.

The best replacement strategy is therefore **not** full replacement. It is a selective transplant into the existing buses: Copilot-style admission, visibility, provenance, and least privilege; retain the owner's ledger, handoff, fresh-context, and exact-receipt semantics. That conclusion is **very likely (80-90%)**, grounded in the source comparisons and the measured defect ranking; only the paired benchmark in §14 can raise it toward almost certain.
