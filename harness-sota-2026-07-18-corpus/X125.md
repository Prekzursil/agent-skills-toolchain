# X125 — Cross-domain borrow: forensic science → failure recovery

## Executive conclusion

The forensic-science analogy transfers, but only as a **quality-assurance pattern for recovery**, not as a claim that agent state is analogous to physical evidence. The strongest borrow is a three-part **Recovery Assurance Triad**:

1. run positive and negative controls through the recovery path so that the harness can distinguish a bad task state from a bad recovery mechanism;
2. make the successor form a small, independently recorded assessment before it sees the predecessor's interpretation, then reveal information in a deliberate sequence; and
3. test recovery with realistic, undeclared fault-injection exercises and score those exercises against externally held facts.

The transfer is **likely (55-80%)** to expose recovery defects that ordinary checkpoint/restore happy-path tests miss, because forensic controls detect process-introduced contamination, blind verification prevents simple agreement from masquerading as corroboration, and blind proficiency tests exercise the routine system rather than test-aware behavior. The evidence is the NIST/OSAC treatment of controls and contamination, NIST's definition of blind verification, and the U.S. Subcommittee on Forensic Science's distinction among declared, blind, and random-reanalysis proficiency tests. The exact effect size in an agent harness is **UNVERIFIED; the settling experiment is the controlled kill/restart study specified in “Evaluation protocol” below**.

This is deliberately not a second orchestration runtime. Every proposed mechanism rides an existing event-hook, filesystem-artifact, and worker-launch bus. It introduces no vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or general guardrail framework.

## Mechanism 1: process controls and contamination localization

### How it works in forensic science

Forensic DNA laboratories do not infer process integrity solely from the evidentiary sample. They process controls alongside it:

- A **negative control** contains the process materials but no sample. An unexpected signal indicates that the assay, consumables, reagents, or handling introduced something that did not originate in the evidence.
- A **positive control** contains a known sample expected to produce a known response. Failure says that the process may not be capable of producing a valid result even if the evidentiary sample itself is sound.
- Controls are associated with a batch and travel through relevant stages. This is what gives a failed control localization value: it links a defect to a process window and to other samples sharing that window.
- A failed control is not treated as an automatic binary discard. The laboratory documents the likely cause, affected results, impact, suitability for interpretation, and the risk of interpretation versus retesting. NIST/OSAC explicitly recognizes that some data associated with a failed control may remain scientifically useful, provided the impact is evaluated and reported ([NIST/OSAC PDF](https://www.nist.gov/system/files/documents/2021/02/26/2020-S-0004_Standard%20for%20interpreting%20and%20reporting%20failed%20controls_Final.pdf), pp. 6-10).

The important mechanism is not “take backups.” It is **carry known-empty and known-good comparators through the same process as the unknown**, then reason about differential outcomes.

### Translation to failure recovery — UNVERIFIED; settling experiment: differential-control fault matrix

#### Proposal A — Recovery control envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

At each recoverable checkpoint, write a compact, immutable recovery envelope containing:

- task/run/checkpoint IDs and parent checkpoint ID;
- owner request and explicit acceptance tests or a pointer plus digest;
- repository/workspace identity and observed revision, without claiming the tree is clean;
- a manifest of task-owned artifacts with size and digest;
- last completed externally visible action and next intended action;
- outstanding side-effect intents, each with an idempotency key and one of `not-started`, `attempted-unknown`, `confirmed`, or `compensated`;
- tool/runtime version identifiers needed to interpret the journal;
- the positive-control specification and negative-control specification used for that checkpoint;
- append-only evidence references, never only a prose “state summary.”

The **positive recovery control** is a tiny deterministic operation known to succeed in the checkpoint's declared environment, such as reading a harness-owned fixture and checking its digest, parsing a fixed structured record, and round-tripping an artifact manifest. It answers: “Can this resumed worker read, interpret, and validate the recovery substrate?”

The **negative recovery control** is a clean, task-empty recovery envelope processed through the same parser, hook chain, policy loader, and tool-discovery path. Its expected result is an empty task artifact set and no inherited pending side effects. It answers: “Did the recovery path itself inject stale task identity, artifacts, permissions, pending actions, or context?” It must be read-only and run in an isolated temporary workspace; a “null task” that can mutate production is not a valid control.

The recovered task proceeds only after the harness records the four-way differential:

| Positive control | Negative control | Task envelope | Recovery interpretation |
|---|---|---|---|
| pass | clean | valid | resume candidate |
| fail | clean | any | recovery substrate/runtime defect; do not blame task state |
| pass | contaminated | any | cross-run leakage or recovery-path contamination |
| pass | clean | invalid/incomplete | task checkpoint defect; reconstruct or roll back to parent |

This proposal is **likely (55-80%)** to localize defects more accurately than checking only whether a checkpoint file exists, because the three inputs vary process capability, process contamination, and task evidence independently; this is a direct structural match to positive control, negative control, and unknown sample. The effect on this harness is **UNVERIFIED; the settling experiment is to inject parser corruption, stale-run context, missing artifact, tool-version drift, and an ambiguous external side effect, and require the differential table to identify the correct fault domain**.

#### What it would catch that checkpoint-only recovery misses

- A syntactically valid checkpoint interpreted by an incompatible parser or policy version: the positive control fails too.
- Stale context from a prior run, a reused environment, or a leaky hook: the task-empty negative control unexpectedly contains task identity or artifacts.
- A missing or silently replaced artifact: its manifest digest disagrees even though the prose summary appears plausible.
- An external action that was attempted immediately before death but whose acknowledgement was lost: the side-effect intent is `attempted-unknown`, preventing an unexamined duplicate.
- A predecessor summary that says “done” while acceptance evidence is absent: the envelope cannot elevate prose to confirmed state without the referenced evidence.
- A recovery mechanism that works in a toy smoke test but fails on the current runtime/tool schema: the checkpoint-specific positive control uses the declared interpretation path.

These are **likely (55-80%)** to be real failure classes in multi-worker agent systems because each follows from a distinct crash boundary—before persistence, after persistence, or between external action and acknowledgement—but whether the current harness misses any one of them is **UNVERIFIED; the settling experiment is the named injection for that class plus two independent outcome signals: envelope/control verdict and externally observed final state**.

### Adversarial disanalogy

A forensic reagent blank is materially parallel to a sample batch. There is no universal “blank task” that exercises the same semantic reasoning as an arbitrary software task. A negative recovery envelope can test parsing, identity isolation, hook loading, and side-effect emptiness; it cannot prove that the successor understood the owner's intent. Treating it as an end-to-end semantic control would be a category error.

The control-envelope transfer is therefore **very likely (80-90%)** valid for mechanical recovery-path contamination and **unlikely (20-45%)** to validate semantic task understanding. The evidence for the first judgment is the shared pipeline/differential-control structure; the evidence for the second is the absence of a known expected semantic answer for open-ended tasks. The semantic boundary is **UNVERIFIED; the settling experiment is to compare control verdicts with blinded human scoring across open-ended resumed tasks and measure false reassurance**.

## Mechanism 2: blind independent verification and staged unmasking

### How it works in forensic science

Forensic verification is not merely a second signature. NIST defines it as comparison by a second, independent examiner so that the first result can be corroborated or corrected; NIST further states that blind verification is more robust than open verification ([NIST OSAC Lexicon](https://www.nist.gov/glossary-term/41106)). Independence is degraded when the verifier sees the first examiner's conclusion before examining the underlying material, because agreement can reflect anchoring rather than a second evidentiary path.

LSU-E generalizes context management. Information is classified by relevance, objectivity, and biasing power; relatively objective and task-relevant material is examined first; potentially biasing context is disclosed later; initial observations and subsequent revisions are recorded. It is not simply “hide all context.” The implementation literature stresses a managed sequence and transparency about changes ([Dror & Kukucka, 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8385162/); [Quigley-McBride et al., 2022](https://doi.org/10.1016/j.fsisyn.2022.100216)).

The evidence is deliberately mixed. Langenburg et al. found that contextual prompts changed fingerprint experts' response patterns but did not make experts more erroneous in that experiment ([study](https://doi.org/10.1111/j.1556-4029.2009.01025.x)). A later critique/evaluation says sequencing is not always effective ([Dror, 2026](https://doi.org/10.1016/j.fsisyn.2025.100657)). Therefore, “blindness always improves accuracy” is not supported.

### Translation to failure recovery — UNVERIFIED; settling experiment: randomized staged-context takeover trial

#### Proposal B — Two-pass takeover, not a second full execution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

When a new worker resumes a task after an unclean death, reveal information in two passes:

**Pass 1 — independent state examination**

Give the successor only:

- the owner's original request and explicit constraints;
- immutable or directly observable evidence: workspace status, artifact manifest, command/tool receipts, external acknowledgements, acceptance-test definitions, and control results;
- the fact and approximate boundary of the interruption.

Temporarily withhold:

- the predecessor's “done/not done” conclusion;
- speculative root-cause prose;
- confidence language;
- the proposed next action;
- evaluator or owner reaction that is not needed to interpret the evidence.

Require a short structured record: `observed facts`, `inferred state`, `unknowns`, `next read-only discriminator`, and `unsafe-to-repeat actions`. This is not permission to redo the task; it is a bounded reconstruction capped by time or tool-call count.

**Pass 2 — controlled unmasking**

Reveal the predecessor's recovery note and withheld context. Record agreements, disagreements, and any revision with its new evidence. If the two assessments disagree on a destructive action, an irreversible external effect, or completion status, require a read-only discriminator or escalation. Otherwise resume normally.

This proposal is **likely (55-80%)** to catch inherited false completion claims, anchoring on a wrong next step, and duplicate side effects at ambiguous crash boundaries, because the successor must commit an evidence-based state estimate before seeing the predecessor's interpretation. Its net value is **UNVERIFIED; the settling experiment is to randomize seeded recovery cases between full-context-first and staged-context conditions, then compare correct resumption, duplicated side effects, unnecessary rework, latency, and token cost**.

#### What it would catch

- The predecessor asserted success but the expected artifact or acceptance receipt is absent.
- The predecessor misidentified which substep failed; the successor independently localizes the last confirmed boundary.
- The predecessor proposed repeating an action whose acknowledgement was merely lost.
- A stale summary conflicts with current observable workspace state.
- The successor agrees only after seeing the prior conclusion; staged records make that non-independence visible.

Whether the present harness fails to catch these is **UNVERIFIED; the settling experiment is to seed each contradiction into a replay fixture and compare the current recovery outcome with the two-pass outcome using artifact digest and side-effect ledger as mechanically independent signals**.

### Adversarial disanalogy

Full blinding is a poor transfer. A forensic verifier can often inspect the same relatively stable item; a successor agent must reconstruct a dynamic task whose intent, decisions, and external state may exist only in the predecessor's history. Hiding too much creates amnesia, duplicated work, or unsafe action. Also, successor and predecessor may be instances of the same model with correlated failure modes; “different worker” is not automatically an independent examiner.

The safe transfer is **staged exposure plus an independent micro-assessment**, not a fully blind restart and not a second end-to-end agent run. It is **likely (55-80%)** that this preserves more independence than immediate summary exposure while avoiding most full-blind duplication, based on the LSU-E sequencing principle and the bounded scope; the cost/benefit in agent recovery is **UNVERIFIED; the settling experiment is the randomized trial above, stratified by task type and crash boundary**.

Independence should be measured behaviorally, not declared. Useful measures are: proportion of facts derived from direct evidence before unmasking, rate of changed state classification after unmasking, correlated error rate, and disagreement resolution by external evidence. A different prompt to the same model is **unlikely (20-45%)** to provide examiner-level independence when the underlying model, tool trace, and prior summary are identical; the evidence is the shared failure substrate, while the exact correlation is **UNVERIFIED; the settling experiment is repeated paired recovery trials across model/prompt combinations**.

## Mechanism 3: blind proficiency testing and random re-examination

### How it works in forensic science

Declared proficiency tests tell participants they are being tested. Blind tests do not. Random case re-examination selects completed work for another examiner to analyze. The Subcommittee on Forensic Science describes all three and notes both the comparative value of externally generated tests and an unresolved cost-effectiveness debate ([NIJ/OJP report](https://www.ojp.gov/pdffiles1/NIJ/251422.pdf), pp. 23-25). BJS uses the same operational definitions ([BJS report](https://bjs.ojp.gov/document/pffclqap14.pdf), p. 3).

The mechanism addresses a measurement problem: people and systems behave differently on obvious test specimens, and a declared exercise may cover the analyst while failing to cover intake, routing, ordinary queues, reporting, and handoffs. A realistic blind specimen samples more of the operational chain. Random re-examination samples real work but has no planted ground truth; it detects disagreement and process drift rather than providing a perfect accuracy oracle.

### Translation to failure recovery — UNVERIFIED; settling experiment: hidden-fixture crash campaign

#### Proposal C — Recovery proficiency fixtures with undeclared kill points

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Maintain a small suite of synthetic but routine-looking tasks with externally held truth:

- expected artifacts and digests;
- allowed and forbidden external actions;
- explicit acceptance checks;
- a side-effect simulator that supports idempotency keys and acknowledgement loss;
- safe fault points before intent logging, after intent logging, after the side effect but before acknowledgement, during artifact write, and after apparent completion but before final receipt.

Periodically route one fixture through the ordinary worker path. The worker may know that reliability exercises exist, but not which task or which crash boundary is an exercise. A scheduler injects a process death, session loss, or simulated machine loss. A fresh worker resumes through the normal path. A deterministic evaluator scores final artifacts, duplicate/missing effects, evidence preservation, recovery latency, and whether the system correctly localized the fault.

“Double-blind” should be used precisely. The worker is blind to fixture identity and kill point; the first-pass successor is blind to the predecessor conclusion; the scorer is a deterministic oracle or an evaluator given only acceptance evidence, not the seeded narrative. The scheduler necessarily knows the injection. Calling the entire organization double-blind would overstate the design.

The campaign is **very likely (80-90%)** to reveal defects that declared “restore this checkpoint” tests can mask, because it exercises ordinary routing and crash boundaries without allowing a special test-aware recovery path. This confidence concerns defect revelation in the fixture system, not production benefit. Production benefit is **UNVERIFIED; the settling experiment is to compare unique recovery defects per 100 declared exercises versus per 100 undeclared fixture exercises, with severity and false-positive review**.

#### Proposal D — Sampled recovery re-examination

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Sample a small fraction of completed recovered runs for evidence-only re-examination. Give a reviewer the request, pre-crash evidence, post-recovery artifacts, and acceptance checks, but initially hide the recovery narrative. Record whether the reviewer independently reaches the same completion and side-effect classification. This is a sampling policy over artifacts already produced, not a new runtime.

Random re-examination is **likely (55-80%)** to find drift and correlated “looks done” judgments in real workloads that synthetic fixtures omit, because it samples ecological task diversity. It is **unlikely (20-45%)** to provide a clean error rate by itself, because most real tasks lack an externally known ground truth and reviewer disagreements may be ambiguous. Both estimates follow from the distinction between real case sampling and planted proficiency truth. The value in this harness is **UNVERIFIED; the settling experiment is a 30-case pilot with adjudication based only on external acceptance evidence and a report of unresolvable cases rather than forced labels**.

### Adversarial disanalogy and safety boundary

Secretly killing arbitrary owner work is not justified by forensic blind-testing practice. Live agent tasks may involve expensive computation, scarce credentials, customer-visible messages, or irreversible side effects; forensic blind specimens are designed and controlled before submission. Therefore blind recovery drills must initially use synthetic tasks, isolated credentials, and simulated side effects. Expansion to production shadow traffic would be **UNVERIFIED and requires an explicit owner decision; the settling experiment is a risk review plus a zero-external-effect canary proving isolation with both the simulator ledger and independent external-system query**.

Blind fixtures can also become recognizable, producing benchmark overfit. Rotate surface form, crash boundary, and tool path while keeping a small set of invariant capabilities. Hold back some fixtures from harness developers. The claim that rotation will prevent recognition is **unlikely (20-45%)** without empirical evidence, because capable models may infer a test from subtle regularities; the settling experiment is a classifier-style audit asking workers to predict fixture status and measuring discrimination above chance.

## Integrated design — UNVERIFIED; settling experiment: controlled kill/restart study

### Recovery Assurance Triad

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

The three mechanisms fit into one minimal flow:

1. Existing lifecycle hooks append compact evidence and side-effect intents to the recovery envelope.
2. On unclean termination, the launcher starts a fresh worker and runs checkpoint-specific positive and task-empty negative controls.
3. If controls localize a recovery-substrate failure, stop automatic semantic recovery and select a parent checkpoint or escalate.
4. If controls pass, give the successor Pass 1 evidence and collect its bounded independent state assessment.
5. Reveal the predecessor note, record revisions, and resume from the last externally confirmed boundary.
6. Existing acceptance checks decide completion; prose never decides completion alone.
7. Separately, the same path is exercised by hidden synthetic proficiency fixtures and sampled real-run re-examination.

The append-only envelope and small gate are the only build. The evaluator can initially be deterministic fixture checks plus existing acceptance tests. There is no always-on daemon and no general workflow engine.

### Minimal schema

```json
{
  "run_id": "...",
  "checkpoint_id": "...",
  "parent_id": "...",
  "request_ref": {"uri": "...", "sha256": "..."},

  "artifacts": [{"path": "...", "sha256": "...", "bytes": 0}],
  "receipts": [{"action_id": "...", "idempotency_key": "...", "state": "attempted-unknown", "evidence_ref": "..."}],
  "acceptance": [{"check": "...", "state": "not-run", "evidence_ref": null}],
  "controls": {"positive_spec": "...", "negative_spec": "..."},
  "last_confirmed": "...",
  "next_intended": "..."
}
```

This schema is illustrative, not a settled contract. Its adequacy is **UNVERIFIED; the settling experiment is to encode every fault-matrix case, reject fields not used in a recovery decision, and add only fields whose absence prevents correct classification**.

### Recovery decision rule

Automatic continuation is allowed only when:

- the positive control passes;
- the negative control is clean;
- required artifact digests match;
- the next action does not repeat an `attempted-unknown` or `confirmed` side effect without an idempotency-safe read;
- successor and predecessor do not have an evidence-unresolved disagreement about completion, destructive action, or external effect.

This rule is **likely (55-80%)** to reduce unsafe duplicate work at the cost of some conservative stops, because it makes ambiguity explicit at the side-effect boundary. The magnitude and false-stop rate are **UNVERIFIED; the settling experiment is to sweep decision thresholds over the fault corpus and report both missed hazards and unnecessary escalations**.

## Evaluation protocol

### Hypotheses

H1: Differential controls improve fault-domain localization versus checkpoint-exists/checkpoint-parses checks. This is **likely (55-80%)**, supported by the known-good/known-empty/unknown separation in forensic controls; agent-harness effect is **UNVERIFIED; settle with Experiment 1**.

H2: Staged context reduces acceptance of seeded predecessor errors without excessive duplicated work. This is **roughly even (45-55%)**, because forensic research supports context effects but also shows that blinding does not invariably improve expert accuracy and task context is operationally necessary; **UNVERIFIED; settle with Experiment 2**.

H3: Undeclared exercises find more operational-chain defects than declared exercises. This is **very likely (80-90%)**, supported by the difference between test-aware and routine processing and the broader components exercised by blind proficiency testing; effect size is **UNVERIFIED; settle with Experiment 3**.

### Experiment 1 — differential-control fault matrix

Use at least these seeded faults:

1. corrupt envelope syntax;
2. valid syntax but incompatible schema version;
3. missing artifact;
4. substituted artifact with same filename;
5. stale run identity injected by the recovery path;
6. stale tool/policy configuration;
7. death before side effect;
8. death after side effect but before acknowledgement;
9. death after acknowledgement but before checkpoint;
10. false predecessor completion statement;
11. positive-control fixture unavailable;
12. negative-control isolation breach.

For every case, collect two mechanically independent signals: (a) the recovery envelope/control verdict and (b) direct observation of the final artifact or simulator/external-system ledger. A detector is not credited with an absence until it also finds a known-present planted item. Score localization accuracy, missed unsafe continuation, false stop, duplicate effect, and time to useful resumption.

### Experiment 2 — randomized staged-context takeover

Create paired replay cases with identical evidence and seeded predecessor narratives, half correct and half wrong. Randomize successor workers to:

- full predecessor narrative first;
- evidence first, then staged unmasking;
- evidence only, as a diagnostic upper-cost condition rather than proposed production mode.

Measure correct last-confirmed-boundary identification, duplicate side effects, acceptance correctness, revisions after seeing predecessor context, tool calls, tokens, and wall time. Stratify by mechanical tasks, ambiguous debugging tasks, and owner-intent-heavy tasks. Do not pool them: the analogy predicts the most benefit in judgment-heavy, directionally biased cases, while intent-heavy work may suffer from hidden context.

### Experiment 3 — declared versus undeclared proficiency

Run matched synthetic fixtures through the same recovery bus. In the declared arm, tell the worker and recovery mechanism the crash test and fault point. In the undeclared arm, expose only normal task metadata. Hold acceptance truth outside the worker context. Compare unique defects, severity-weighted defects, recovery success, and false alarms. Rotate fixture form and include held-out fixtures.

### Adoption thresholds

Threshold values are **UNVERIFIED; the settling experiment is the three-experiment pilot followed by a cost-sensitive threshold selection using observed baseline rates**. Before measurement, adopt only directional gates:

- no statistically or operationally meaningful increase in duplicated external effects;
- fewer unsafe resumptions than baseline;
- staged unmasking retained only for task strata where its error reduction exceeds its rework/latency cost;
- negative controls retained only for surfaces they genuinely exercise;
- blind exercises confined to isolated synthetic work until isolation is proven by two independent signals.

## Failure modes of the proposed borrow

1. **Control theater.** A positive control that only parses JSON can pass while the substantive tool path is broken. Mitigation: bind each control to the exact recovery surfaces it claims to cover and never generalize beyond them.
2. **Blank non-equivalence.** A task-empty negative envelope cannot exercise task-specific semantics. Mitigation: report its scope as identity/isolation/parser/hook contamination only.
3. **Correlated examiners.** Two instances of the same model can reproduce the same error. Mitigation: measure disagreement and paired error; use external evidence, not agreement, as the decision criterion.
4. **Information starvation.** Withholding intent or safety constraints can itself cause bad recovery. Mitigation: never blind the successor to the owner request, constraints, acceptance tests, or directly observed safety-relevant evidence.
5. **Proficiency gaming.** Repeated fixtures become recognizable. Mitigation: held-out fixtures, surface rotation, and explicit fixture-detection audits.
6. **Over-conservative recovery.** Every ambiguity can become an escalation, defeating useful resumption. Mitigation: calibrate by consequence; an ambiguous read-only local computation is not equivalent to an ambiguous customer-visible side effect.
7. **Journal contamination.** A compromised predecessor may write false “evidence.” Mitigation: receipts and artifacts carry independent digests or external queries; predecessor prose remains an interpretation.
8. **Non-idempotent external systems.** Some actions lack queryable status or idempotency keys. Mitigation: classify them as unsafe-to-repeat and require owner/external coordination rather than inventing certainty.

The first four failure modes are **very likely (80-90%)** to appear in an uncalibrated implementation because they arise directly from the disanalogies above; the evidence is structural rather than measured in this harness. Their observed prevalence is **UNVERIFIED; the settling experiment is to label their incidence during the three pilots and retain the design only where mitigations succeed**.

## What this cross-domain lens adds

The distinctive forensic-science contribution is not another checkpoint format. It changes the recovery question from:

> “Did we save enough state to continue?”

to three separately testable questions:

> “Did the recovery process work on a known-good input?”  
> “Did the recovery process inject anything into a known-empty input?”  
> “Did an independently formed interpretation of the unknown agree with the inherited interpretation after controlled disclosure?”

It then tests those questions under routine-looking crash conditions, not only when every component knows it is in a recovery test.

This reframing is **very likely (80-90%)** to improve diagnostic clarity even if it does not improve end-task success, because it separates process capability, process contamination, and semantic disagreement into independently observable records. Improvement in owner-visible completion is **UNVERIFIED; the settling experiment is the end-to-end pilot with success, duplicate-effect, rework, and latency metrics**.
