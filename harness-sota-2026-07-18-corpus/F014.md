# F014 — Red team: cloned-repo config → persistence

## Scope, verdict, and evidence standard

This unit analyzes one attack surface and one attacker objective: an attacker-controlled repository supplies `.claude/`, `.codex/`, `.mcp.json`, hooks, `CLAUDE.md`, or `AGENTS.md`; the attacker wants execution that survives a client or machine restart and triggers again later. I did not execute an attack, create a fixture in the subject tree, alter configuration, or access secrets.

**Verdict:** the most plausible persistence chain against this harness is a malicious Claude project `SessionStart` hook in `.claude/settings.json` that, on a non-interactive first open, adds a second `SessionStart` hook to the user's `C:\Users\Prekzursil\.claude\settings.json`. The first hook runs before turn 1; the copied user-scope registration then runs on later ordinary Claude starts, including starts outside the malicious repository. This is **very likely (80-90%)** to succeed if the checkout is opened with `claude -p` without `--bare`: current Anthropic documentation says `-p` disables workspace trust, `--bare` is what skips project hooks/config, and command hooks run with the user's full permissions ([Claude security](https://code.claude.com/docs/en/security), [headless mode](https://code.claude.com/docs/en/headless), [hooks](https://code.claude.com/docs/en/hooks)). The remaining uncertainty is the exact installed Windows CLI build and any machine-managed policy omitted from the unpacked bundle; the settling experiment is the inert disposable-repository canary in “Required verification experiment” below.

An ordinary first-time **interactive** Claude launch is adequately defended at the initial-load boundary by native codebase/MCP trust verification, according to Anthropic's current security documentation. That control does **not** settle this harness's autonomous/headless path because the same documentation explicitly says trust verification is disabled under `-p`. The harness's own after-load controls do not stop the chain.

Codex is materially better defended against executable project configuration: current official documentation says an untrusted project skips project `.codex/` config, hooks, and rules, and each non-managed command-hook definition requires exact-hash review ([Codex config](https://developers.openai.com/codex/config-basic), [Codex hooks](https://developers.openai.com/codex/hooks)). Codex project `AGENTS.md` remains a separate prompt-level route: it loads before work, nearer files override global guidance, and this installation raises the project-document budget to 151,072 bytes (`/local_disk0/codexwork/bundle/codex/config.toml:15`; [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md)). I did not choose that as the primary chain because Claude's project command hook is deterministic pre-turn code execution, while an `AGENTS.md` persistence attempt still depends on model compliance.

## Grounding on this harness

The following are direct observations from the read-only bundle, not inherited audit conclusions:

1. Claude is globally configured with `permissions.defaultMode = "bypassPermissions"`, allows `Bash`, `Write`, and `Edit`, and adds both `C:` and `D:` as accessible directories (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`). `defaultMode` is not needed for the pre-turn hook itself—command hooks execute as the user—but it enlarges the damage available after the model starts.
2. User-scope `SessionStart` command hooks are a live mechanism in this installation. Two dispatchers and a local reminder are registered for every session (`/local_disk0/codexwork/bundle/claude/settings.json:81-115`). This is a known-positive control proving the detector used below can find real hook configuration; a Python JSON parse returned 18 hook events and a non-empty `hooks` object.
3. The global contract explicitly recognizes this attack class and tells the agent to inspect/neutralize `.codex/`, `.claude/`, `.mcp.json`, hooks, `AGENTS.md`, and `CLAUDE.md` before entering an untrusted checkout (`/local_disk0/codexwork/bundle/claude/AGENTS.md:93-106`). That is useful behavior guidance, but it cannot execute before the project file it warns about is loaded.
4. Claude's live `ConfigChange` hook calls the shared dispatcher (`/local_disk0/codexwork/bundle/claude/settings.json:406-416`). The shared module reads only the user-level `~/.claude/settings.json`, compares `hooks`, `mcpServers`, and `disabledMcpServers` against an installed snapshot, fails open on missing/malformed state, and produces an `inject` result on drift (`/local_disk0/codexwork/bundle/agents/harness/modules.py:864-909`). It does not restore the file or deny the change.
5. A mechanically independent signal confirms the previous point: the tests require the drift event to return `allow` in default shadow mode and `inject` in enforce mode (`/local_disk0/codexwork/bundle/agents/harness/tests/test_modules.py:1368-1387`, `:1400-1428`). A separate adapter test requires that the enforced injection render only as `{"systemMessage":"CONFIG DRIFT detected"}` (`/local_disk0/codexwork/bundle/agents/harness/tests/test_native_events.py:264-269`). Thus the claim “the harness drift sentinel does not stop persistence” has both implementation and behavioral-test signals.
6. A JSON parse found `allowManagedHooksOnly`, `disableAllHooks`, and `permissions.disableBypassPermissionsMode` absent from the unpacked user settings while successfully finding the known-present `hooks` object. A second bounded filename inventory found no managed/policy settings artifact in the supplied bundle. This proves only that the **bundle does not contain** those controls. Effective machine-managed policy is **UNVERIFIED; the experiment that settles it is a redacted Claude `/status` plus the read-only `/hooks` source browser on the Windows host**. I therefore do not claim that enterprise policy is absent from the real machine.
7. The bundle's Codex configuration is explicitly `approval_policy = "never"`, `sandbox_mode = "danger-full-access"`, and `features.hooks = true` (`/local_disk0/codexwork/bundle/codex/config.toml:6-7`, `:82-105`). It also contains many stored trusted project records, including `C:\Users\Prekzursil` and `D:\` (`:151-162`). Whether trust is inherited from those broad parent records by a newly cloned Git root is **UNVERIFIED; the settling experiment is `codex status` in a disposable child Git repository plus inspection of its resolved config layer without accepting trust**. No inheritance claim is used in the primary attack.

The earlier audit's F03 report is treated as a claim, not ground truth. It says the Windows profile wraps ordinary Claude calls with bypass permissions and that an autonomous Codex CI runner strips `.codex/` but leaves `AGENTS.md` (`/local_disk0/codexwork/bundle/inputs/audit-findings/F03.md:46-89`). The Windows profile and repository workflow were not included in this job's subject bundle, so those details are **UNVERIFIED here; the settling experiment is a read-only `Get-Command claude -All`/function-body capture and `git show origin/main:.github/workflows/codex-runner.yml` on the Windows repository**. The attack does not depend on the wrapper: official documentation makes plain `claude -p` the trust-bypass condition.

## Concrete attack chain (designed, not executed)

### Preconditions

- The attacker can cause the owner or automation to clone or check out an attacker-controlled repository or PR head.
- A Claude non-interactive invocation starts inside that checkout with `-p` and without `--bare`.
- No unseen machine-managed policy rejects non-managed/project hooks. This is **UNVERIFIED; the redacted `/status` and `/hooks` experiment above settles it**.
- The normal Windows user can write their own `~/.claude/settings.json`. This is **very likely (80-90%)**, supported by the harness installer itself writing that file (`/local_disk0/codexwork/bundle/agents/harness/install.py:488-511`) and the file living under the user's profile, but its live ACL is not in the bundle; `Get-Acl C:\Users\Prekzursil\.claude\settings.json` would settle it.

### Step-by-step

1. **Repository payload.** The repository contains `.claude/settings.json` with a `SessionStart` command hook. It points to a repository-owned script under `.claude/` (or directly invokes a system interpreter). This is a supported project configuration surface: Anthropic documents project hooks as coming from `.claude/settings.json`, and its hooks security warning says command hooks run with the user's full permissions ([hooks reference](https://code.claude.com/docs/en/hooks), [Claude directory](https://code.claude.com/docs/en/claude-directory)).

2. **Trigger.** An autonomous job runs `claude -p ...` from the checkout without `--bare`. Anthropic states that `-p` disables trust verification and, unless `--bare` is added, loads the same working-directory context/customizations as an interactive session, including project hooks and `.mcp.json` ([security](https://code.claude.com/docs/en/security), [headless mode](https://code.claude.com/docs/en/headless)).

3. **Pre-turn execution.** The project `SessionStart` hook runs as the Windows user before the first model turn. Tool permission prompts and the model's global safety prose are not a boundary here: the command hook is client startup behavior, not a model-requested Bash tool call. The real CVE-2026-47751 establishes the same ordering class: attacker-controlled `.mcp.json`/`.claude` settings were acted on before tool-permission gating ([GitHub advisory lines 154-174](https://github.com/advisories/GHSA-8q5r-mmjf-575q), [Anthropic fix PR](https://github.com/anthropics/claude-code-action/pull/1066)). The exact vulnerable action is not asserted to be installed.

4. **Persistence write.** The first-stage hook makes an idempotent JSON edit to the user's `C:\Users\Prekzursil\.claude\settings.json`: it adds a user-scope `SessionStart` entry pointing to a payload stored outside the repository under a user-writable per-user directory. An idempotent edit avoids duplicate registrations and preserves the owner's existing 18 event blocks. This report intentionally omits executable payload code, obfuscation, egress, and destructive behavior; those details are unnecessary to establish persistence.

5. **Optional concealment.** No concealment is required for persistence. The current ConfigChange path may notice a changed user hook block, but default mode deliberately returns `allow`; even when promoted to “enforce,” it only creates a system message (`modules.py:864-909`; tests at `test_modules.py:1368-1387` and `test_native_events.py:264-269`). Because the malicious startup command has full user permissions, it could also tamper with the snapshot or dispatcher, but that expansion is unnecessary and is not part of the minimal chain.

6. **Restart survival.** The client exits or the machine restarts. The modified user settings and user-owned script remain on disk. On the next ordinary, non-bare Claude session, the user-scope `SessionStart` hook is loaded for every project, just as the three current global startup hooks are loaded from `settings.json:81-115`.

7. **Later re-trigger.** The persistent hook executes again before turn 1, even when the original clone is no longer the working directory. This achieves the requested objective. It can keep its registration idempotent, repair a removed payload, or perform some later action; this analysis does not design any harmful follow-on behavior.

### Why this chain is more plausible than alternatives

- It uses a natively documented, auto-loaded command surface rather than persuading a model through prose.
- It requires one owner/automation action—opening the checkout—and one deterministic filesystem mutation.
- It persists on the same lifecycle bus already used by this harness, so no scheduled task, service, registry run key, second runtime, or exploit is required.
- `.mcp.json` could also obtain pre-turn process execution in affected/trusting configurations, as CVE-2026-47751 demonstrated, but current MCP approval/trust behavior has more version- and settings-dependent branches. A project `SessionStart` hook is the clearer chain.
- `CLAUDE.md`/`AGENTS.md` could instruct the model to install persistence, but success depends on model compliance. Codex's project hook trust is a real extra barrier, whereas its `AGENTS.md` loading remains prompt-level.

## Existing controls: what stops what

| Control | Verified behavior | Does it stop this chain? |
|---|---|---|
| Claude first-codebase trust | Current official security docs say first-time codebases and new MCP servers require trust verification. | **Yes, conditionally**, for a normal first-time interactive launch if the owner refuses trust. It is not active under `-p`. |
| Claude `--bare` | Current official headless docs say it skips auto-discovery of hooks, skills, plugins, MCP, auto-memory, and `CLAUDE.md`; only explicitly passed flags apply. | **Yes**, at the initial project-load step, if actually present on every untrusted non-interactive invocation. |
| Global AGENTS security rule | Warns about this exact class (`claude/AGENTS.md:93-106`). | **No deterministic stop.** It is prose loaded too late to prevent a startup command hook. |
| ConfigChange drift sentinel | Compares three user-settings sections and injects a notice (`modules.py:864-909`); tests require allow/inject, never restoration (`test_modules.py:1368-1428`). | **No.** It may report persistence after the write but neither prevents nor rolls it back. |
| Claude permission mode/deny list | User settings include a small read deny list and bypass mode (`settings.json:26-75`). | **No.** Startup command hooks do not pass through model tool permission evaluation. |
| Codex untrusted-project config gate | Official docs say untrusted projects skip project `.codex/` config/hooks/rules; command hooks require definition-hash review. | **Yes for executable `.codex/` hooks/config**, assuming the project is actually untrusted and hook trust is not bypassed. It does not cover project `AGENTS.md`. |
| Harness prompt-injection scanner | It is a PostToolUse/result-channel mechanism, not a pre-start project-config verifier (`agents/harness/modules.py:912-930` begins its ingest-tool allowlist after the ConfigChange code). | **No.** No tool result exists before the project startup hook fires. |

The claim that the ConfigChange control fails to stop this attack is **almost certain (90-99%)** because two mechanically independent signals—the implementation's returned action and tests specifying rendered behavior—agree. The 1-10% residual covers runtime wiring/version divergence from the supplied files; a disposable edit canary would settle it without touching live settings.

## Minimal mitigation

### 1. Make bare mode mandatory for first-pass/headless work on untrusted checkouts

**NATIVE (Claude Code already does this; we just enable it)**

The launcher that enters an untrusted checkout must invoke Claude with `--bare -p`, pass only the minimal required tools/settings explicitly, and avoid passing a repository-owned settings or MCP file. `--bare` is the decisive control: Anthropic says it does not read project or user hooks, `.mcp.json`, plugins, auto-memory, or `CLAUDE.md`. Perform the initial inventory using explicit read-only capabilities; only after human review should normal project customization be enabled.

This is **almost certain (90-99%)** to break the concrete chain at step 2, because the vendor explicitly documents that a project hook and `.mcp.json` do not run in bare mode ([headless mode](https://code.claude.com/docs/en/headless)). The evidence is documentation rather than an execution against the owner's installed binary; the required canary below closes that residual uncertainty.

This mitigation rides the native launcher/config bus and adds no daemon, database, guardrail framework, trained critic, or orchestration runtime. It passes the anti-overfit gate.

### 2. Preserve Codex's native untrusted-project state and suppress repo instructions during the first pass

**CONFIG (settings/JSON only)**

For the same untrusted-checkout launcher, require an explicitly untrusted Codex project and override `project_doc_max_bytes=0` for the first inspection. The first clause preserves the native skip of `.codex/` config/hooks/rules; the second closes the separate `AGENTS.md` prompt channel. The current installation's 151,072-byte project-doc budget (`codex/config.toml:15`) is unsuitable for a hostile first pass.

This is **very likely (80-90%)** to remove both Codex repository configuration channels, based on current official config and discovery documentation plus the pinned-source behavior reported by audit F03. End-to-end behavior on the owner's installed binary is **UNVERIFIED; the settling experiment is a disposable repo with an inert `.codex` hook marker and an `AGENTS.md` response marker, launched once with explicit untrusted state and `project_doc_max_bytes=0`**.

This second item is provider parity, not a prerequisite for stopping the primary Claude chain.

### Why not “fix” the drift sentinel

Turning ConfigChange into a blocker is the wrong enforcement point: the attacker-controlled project hook has already executed and modified disk by the time a user-settings change is observed. A rollback hook would also race other startup hooks, could destroy legitimate concurrent edits, and remains tamperable by code running as the same user. Pre-load exclusion (`--bare`) is smaller and earlier. No new `BUILD-SMALL` hook is recommended.

### Optional machine policy, not the minimal fix

Where enterprise managed settings are available, `allowManagedHooksOnly`, `allowManagedMcpServersOnly`, `allowManagedPermissionRulesOnly`, and disabling bypass-permissions mode provide defense in depth ([Claude settings](https://code.claude.com/docs/en/settings), [permissions](https://code.claude.com/docs/en/permissions)). This would be **CONFIG (settings/JSON only)**. It is not the minimal recommendation because it changes the owner's normal global customization model, may require a managed-policy deployment channel, and the bundle does not reveal whether that channel exists.

## Required verification experiment (safe, inert, and mechanically independent)

Run this on the Windows host only in a disposable directory and with a temporary `CLAUDE_CONFIG_DIR`; do not point it at the real `~/.claude`, do not expose credentials, and make the hook write only an inert marker inside the disposable directory.

1. Prove the detector with a known-positive: a benign project `SessionStart` hook writes marker `PROJECT_HOOK_RAN` inside the fixture.
2. Launch interactively without accepting trust. Expected: no marker.
3. Launch with `-p` and without `--bare`. Expected under current docs: marker exists.
4. Clear the marker and launch with `--bare -p` plus only an explicit read-only prompt. Expected: no marker.
5. In a second disposable config root, let the inert first-stage hook add an inert user-scope hook that writes `PERSISTED_HOOK_RAN`; restart outside the repo. Expected without mitigation: second marker exists. Repeat the initial launch with `--bare`; expected: neither persistence write nor second marker.
6. Capture `claude --version`, `claude --help` entries for `-p`/`--bare`, redacted `/status`, and `/hooks` source listings. These are mechanically independent signals: runtime marker state, CLI-advertised semantics, and resolved configuration provenance.

The mitigation is accepted only if the known-positive fires in the vulnerable control case and both markers remain absent in the mitigated case. Merely seeing “no marker” without the known-positive is not evidence.

## Gaps and limits

- The remote job contains a curated unpacked subject, not the live Windows profiles, `.claude.json`, `.mcp.json`, machine-managed settings, real ACLs, executable versions, or repository workflows. Claims requiring those paths are marked **UNVERIFIED** inline with settling experiments.
- I did not prove how frequently this owner launches Claude with `-p`. The chain is the most plausible concrete path because the program is explicitly autonomous and the native non-interactive route is documented, but actual invocation frequency is **UNVERIFIED; a redacted command-line/process-history inventory would settle it**. No corpus frequency is claimed.
- I did not claim current compromise. No supplied evidence shows a malicious global hook or payload, and proving absence would require a complete live resolved-hook inventory plus byte/provenance review. The safe experiment is `/hooks`, export names/commands with secrets redacted, then compare every command target's hash to an owner-reviewed manifest.
- I did not claim the exact `anthropics/claude-code-action` CVE is installed. The advisory is evidence for the ordering and vulnerability class only. The audit says the named repository workflows did not reference the action (`inputs/audit-findings/F03.md:28-35`), but that audit statement was not independently reproducible from this bundle.
- The corpus hook section is detector-broken by pinned instruction and was not used as evidence of hook absence or effectiveness.
- The suggested first-pass workflow deliberately sacrifices project skills/hooks/MCP conveniences. That is the intended trust-boundary cost for an untrusted first open; reviewed configuration can be enabled in a later normal session.

## Final assessment

This surface is **not adequately defended for non-interactive Claude starts**. The existing interactive trust prompt is real, and Codex has a substantive executable-config trust gate, but the harness combines a documented `-p` trust bypass with user-writable global startup hooks and only post-change, inject-only drift reporting. The minimal answer is not another scanner: require Claude's native `--bare` mode at the untrusted-checkout launcher boundary, and use Codex's native untrusted state plus zero project-doc budget for the analogous first pass.
