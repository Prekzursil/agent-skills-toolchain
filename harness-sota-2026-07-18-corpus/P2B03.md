## Executive verdict

Cline 4.0 is no longer merely a VS Code sidebar around a model/tool loop. It is becoming a general local agent platform: one SDK-backed runtime shared by the VS Code extension and CLI, a hub/spoke daemon for persistent sessions, tools and lifecycle hooks as extension points, persistent multi-agent teams, scheduled agents, and a separate Kanban/worktree product. The most valuable ideas for this owner are nevertheless the small ones, not that platform runtime.

The three ideas worth porting are:

1. **Operational context admission, not advisory context hygiene.** Cline enforces `.clineignore`, deduplicates file reads, chunks reads, and budgets tool-result ingestion. Our harness has offset/limit-capable native reads and a good `context-sandbox` skill, but the skill explicitly says it is “Markdown guidance only, not an automated guarantee” (`C:\Users\Prekzursil\.agents\skills\context-sandbox\SKILL.md:3`), while the live output compressor mainly summarizes large `git status` output and strips ANSI (`C:\Users\Prekzursil\.claude\hooks\cmd-rewrite\compress-output.py:20-30`, `:265-289`). The corpus makes this concrete: Read has 384 over-token failures, Glob has 592 `ENAMETOOLONG` failures, and WebFetch has 232 `ECONNREFUSED` failures (`C:\Users\Prekzursil\.claude\harness-sota-2026-07-18\corpus\corpus.json:1`, `failures_by_tool`). **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** very likely (80-90%) to reduce avoidable context/tool failures because the gap is an enforcement gap with direct matching corpus failure classes; a replay experiment over the 384 oversized Read cases and 53 detected repeated-Read runs would settle the effect size.
2. **Make the already-written result-aware loop detector operational.** Cline 4.0 includes repeated identical-tool-call detection and a consecutive-mistake budget in the core runtime ([loop detector source](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/safety/loop-detection.ts#L61-L153), [mistake tracker source](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/safety/mistake-tracker.ts#L80-L153)). Our implementation is actually more discriminating because it hashes `(tool, args, output)` and treats a changed result as progress (`C:\Users\Prekzursil\.claude\hooks\anti-degen\fingerprint.py:2-13`, `:36`, `:104-168`), but it is not present in either live hook registry; `rg` found only the dependent `loop-recovery` PreToolUse hook in settings, while a known-present control found `stub-ledger/record` in the dispatcher manifest (`C:\Users\Prekzursil\.claude\settings.json:228-237`; `C:\Users\Prekzursil\.claude\hooks\_dispatch\manifest.json:171-177`). **CONFIG (settings/JSON only).** almost certain (90-99%) that wiring the PostToolUse fingerprint will make the existing loop-recovery path receive its intended primary signal, because `verdict.py` explicitly reads the file that fingerprint writes (`C:\Users\Prekzursil\.claude\hooks\loop-recovery\verdict.py:5-8`, `:243-250`); a fixture replay plus one disposable live three-call test settles runtime delivery.
3. **Make path-conditional global rules reliable.** Cline activates rule files from the paths in current prompt/editor/edited-file context and can toggle each rule ([Cline conditional rules](https://docs.cline.bot/customization/cline-rules#conditional-rules)). Our vault already contains `paths:` frontmatter (for example `C:\Users\Prekzursil\.claude\rules\typescript\testing.md:1-7`), but the worktree hook documents that user-level path-scoped rules silently ignore it and compensates only by symlinking rules into project scope (`C:\Users\Prekzursil\.claude\hooks\create-worktree.ps1:9-16`). **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** likely (55-80%) to improve relevance and reduce rule dilution because the mechanism is deterministic, but the impact on answer quality is UNVERIFIED; replay prompts across TypeScript, Python, prose, and mixed-language worktrees while logging `InstructionsLoaded` to settle it.

Do **not** copy Cline’s hub, durable teams, scheduler, or Kanban runtime into this harness. They are real capabilities, but each is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and directly reintroduces components the anti-overfit gate rejects: a second orchestration runtime and a durable-execution engine. Claude Code already supplies native subagents, worktree isolation, checkpoints, permissions, sessions, hooks, and skills; the owner already has a cross-tool event ledger, semantic `basic-memory`, an agent monitor, and 22 exercised agent types. Cline’s larger platform would divide authority and state rather than repair the measured failure modes.

The earlier audit claim that “Cline mostly validates architecture this setup already has” (`C:\Users\Prekzursil\.claude\harness-mega-audit-2026-07-18\findings\D13.md:1-3`) is now incomplete. Conversely, its recommendation to “restore” a custom edit-checkpoint hook is obsolete: Claude Code now natively supports code-only, conversation-only, and combined rewind, persisting checkpoints across resumed sessions ([Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing)).

## 3. Cline’s agent loop

### 3.1 Concrete mechanism

Cline 4.0 routes the VS Code extension through the same SDK session runtime used elsewhere. The current changelog explicitly names agent turns, tools, Plan/Act coordination, MCP, checkpoints, telemetry, provider changes, compaction, mistake limits, and task history as shared SDK responsibilities ([4.0 migration](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L1-L32)).

The core flow is a familiar model/tool loop:

1. Append the user turn to the conversation store.
2. Compose a system prompt from registered rules.
3. Merge built-in/config tools with extension-contributed tools and apply per-tool policies.
4. Seed the runtime with the full prior transcript.
5. Run or continue the agent runtime.
6. Stream model/tool events, record each tool’s input/output/error/duration, update mistake and loop trackers, and persist the resulting full transcript.

Those operations are visible in the current orchestrator source ([system prompt and run setup](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L640-L846), [persistence and hook setup](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L850-L951), [per-tool records](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L1027-L1100)). ClineCore built-ins are `bash`, `editor`, batch `read_files`, `apply_patch`, ripgrep `search`, `fetch_web`, and `ask_question` ([tool reference](https://docs.cline.bot/tools-reference/all-cline-tools#built-in-tools-clinecore)).

Cline has Plan and Act phases. Plan is documented as read/search/discuss only; Act inherits the conversation and enables edits/commands ([Plan/Act docs](https://docs.cline.bot/core-workflows/plan-and-act)). Different models can be selected for each phase. Cline also supplies `/deep-planning`, which investigates, discusses, writes an implementation plan, and creates a new implementation task ([commands](https://docs.cline.bot/core-workflows/using-commands#deep-planning)).

The Plan story is not fully stable. The current docs say Plan cannot execute commands, while the changelog says strict plan mode was disabled by default in 3.56 and 4.0 reworked Plan/Act through SDK coordinators. UNVERIFIED whether the exact current 4.0 VS Code Plan policy prevents every state-changing extension/plugin/MCP tool; a controlled task offering one write tool, one command tool, and one MCP mutator in Plan mode would settle it. This uncertainty means no recommendation rests on Cline’s Plan enforcement.

### 3.2 What is better than ours

#### Automatic tool-result budgets and read deduplication — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Cline 3.74 added a file-read deduplication cache, 3.77 added chunked targeted reads, and 4.0 applies default truncation/budgets to bash, file-read, search, assistant text, and media while batching outdated-read rewrites to preserve provider prefix caches ([changelog 3.74-3.77](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L483-L528), [4.0 budgets](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L264-L276)).

Our native Read already supports offset/limit and refuses giant files, but the operational pattern is reactive: 384 oversized Read errors and 53 repeated-Read runs were still mined. Port the useful mechanism as a PostToolUse/PreToolUse state file keyed by `(session, canonical path, mtime/size, requested range)`:

- If unchanged bytes/range were already returned, inject a compact pointer to the prior read instead of repeating them.
- If the file is above a configured size, convert an unbounded read into a bounded head plus an instruction to search or request ranges.
- Apply byte/line budgets to search, WebFetch, and MCP output; store overflow in a task-local spool and return a digest/path plus a retrieval recipe.
- Invalidate on mtime/size/content-hash change so the feature never creates stale-read confidence.

very likely (80-90%) to reduce repeat/oversize waste; evidence is Cline’s concrete implementation history plus matching corpus failures. UNVERIFIED whether Claude’s PostToolUse `updatedToolOutput` path covers every MCP result shape; replay one known large result from each of Read, Grep, WebFetch, and MCP to settle provider coverage before enabling broadly.

#### Queued prompts during a running turn — no port recommendation

Cline 4.0 queues messages submitted while a turn streams and permits cancellation before execution ([4.0 changelog](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L1-L32)). This is useful UI behavior, but the owner’s Codex surface already supports steering during active work, and Claude Code’s current host behavior was not tested in this unit. I therefore do not claim a harness-wide absence and assign no proposal tag.

### 3.3 Where Cline is worse

- Its core is a much larger runtime surface than the owner’s preferred thin host-native loop. The 4.0 migration centralizes many concerns cleanly, but it also creates a platform that this harness would have to track across Claude, Codex, and Antigravity. very likely (80-90%) that cloning it would raise maintenance and drift cost because it duplicates three host runtimes; the direct evidence is Cline’s own list of responsibilities in the 4.0 changelog and our existing cross-provider dispatcher.
- Cline’s repeated-call detector compares identical tool name plus input signature before execution. Our dormant fingerprint waits for results and only fires when name, arguments, **and output** repeat (`fingerprint.py:2-13`). That distinction avoids breaking legitimate polling whose output changes. Do not copy Cline’s simpler pre-result criterion.
- Cline exposes `--retries` as “maximum consecutive mistakes,” defaulting to six in current source (`session-runtime-orchestrator.ts:401-440`). A fixed count is useful as a circuit breaker, but it does not know whether a retry used a materially new hypothesis. Our failure ledger’s falsifiable preconditions and supersession are a better reasoning substrate; the right action is to wire the result-aware detector, not replace it.

## 4. Context management

### 4.1 Concrete Cline mechanisms

Cline manages context at several layers:

- Auto Compact monitors token use, summarizes the conversation near the limit, replaces history with the summary, and continues. LLM summarization is documented for Claude 4, Gemini 2.5, GPT-5, and Grok 4; other models fall back to rule-based truncation ([Auto Compact](https://docs.cline.bot/features/auto-compact)).
- `/smol` or `/compact` manually compresses the current task; `/newtask` packages a developer handoff into a fresh task, with user refinement before creation ([commands](https://docs.cline.bot/core-workflows/using-commands)).
- `.clineignore` prevents matching files from being accessed/analyzed and recommends excluding dependencies, build output, environment files, large data, maps, and minified files ([`.clineignore`](https://docs.cline.bot/customization/clineignore)).
- Conditional rules only load when current prompt paths, open/visible tabs, previously edited files, or pending edits match rule globs ([conditional rules](https://docs.cline.bot/customization/cline-rules#conditional-rules)).
- Task history stores full local conversations, token/cost/time metadata, fuzzy-searches prompts/responses/snippets/files, and resumes across sessions while checking file state against checkpoints ([task history](https://docs.cline.bot/core-workflows/task-management#task-history)).
- Focus Chain maintains a todo list and persists it across Auto Compact. The public changelog documents its addition, but the current 4.0 implementation path was not found under that name after the SDK migration ([3.25 changelog](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L900-L940)). UNVERIFIED whether all 4.0 clients preserve the legacy Focus Chain behavior; enable it in CLI and VS Code, force compaction, and compare task state to settle it.

### 4.2 What is better than ours

#### Enforced context exclusions — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Our harness lacks one provider-neutral, operational “do not auto-admit these paths/results” layer. It has native ignore behavior in individual tools, a context-sandbox skill, and a `glob-argv-guard`, but the pinned D13 audit correctly observed that the active compressor is narrow (`D13.md:46-53`). Cline’s `.clineignore` is valuable because it is simple, local, visible, and applies before bytes enter the model.

Port it without inventing a new memory store:

1. Define one `.agentignore`/existing-ignore precedence contract, preferably reusing `.gitignore` plus a small explicit sensitive/generated overlay rather than adding tool-specific formats.
2. At PreToolUse for Read/Grep/Glob, normalize the target and consult ignore patterns. Deny secret paths; for generated/large paths, ask or inject an override instruction rather than hard-blocking explicit user requests.
3. At PostToolUse for WebFetch/MCP/search, budget bytes and spool overflow.
4. Emit the matched pattern and source file so false exclusions are diagnosable.
5. Regression-test the orphan-plugin/Windows argv case: ignored plugin cache trees must never be expanded into process argv.

very likely (80-90%) to reduce context and spawn failures because the measured worst Glob fingerprint is caused by enormous orphan-plugin expansion, while Read oversize is the top Read failure. It will not by itself fix `uv_spawn` if the native host expands paths before PreToolUse; that part is UNVERIFIED and requires replaying a known failing Glob against the hook to see whether the hook receives a still-compact pattern or an expanded argv.

#### Reliable global conditional rules — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Mechanism: compile the existing `paths:` frontmatter into a small index at SessionStart/InstructionsLoaded; on UserPromptSubmit and before a file edit, resolve mentioned/open/pending paths and inject only matching rule bodies plus always-on common rules. Preserve project rules’ native behavior and use this only to repair user-vault/global parity. Cache by file mtimes.

likely (55-80%) to reduce irrelevant rule context. The gap is certain in the documented home-level case, but quality gain is UNVERIFIED; a blinded prompt suite with rule-load telemetry and token counts settles it.

### 4.3 Where ours is better

- Cline Auto Compact is summary-authoritative. Its own task guide concedes very long tasks may lose earlier details ([task context window](https://docs.cline.bot/core-workflows/task-management#context-window)). Our event ledger persists compact objective state and replays the active goal/open failures/decisions, while `basic-memory` stores semantic knowledge. almost certain (90-99%) that retaining those two roles is more robust than replacing them with a generated summary, because one is append-only objective history and the other is explicitly queryable semantic memory (`modules.py:934-1001`; cross-tool contract sections 3 and 8).
- Cline’s Memory Bank is not an automatic memory engine. It is a manual Markdown methodology: create six project files, instruct Cline to read all files at task start, and explicitly request updates before a fresh conversation ([Memory Bank](https://docs.cline.bot/best-practices/memory-bank)). That is worse than prompt-relevant semantic recall plus an objective ledger for this owner. Reading all memory files every task is exactly the context tax the harness is trying to avoid.
- Cline’s task-history fuzzy search is a useful UI, but it is conversation retrieval, not knowledge lifecycle. It has no documented temporal supersession equivalent to the owner’s `superseded_by`/`valid_as_of` convention. UNVERIFIED whether a plugin supplies such semantics; installing/searching the current Customize catalog for memory plugins and testing an update-conflict query would settle it. No recommendation depends on this absence.

## 5. Memory

### 5.1 What Cline actually calls memory

Cline has four persistence forms, which should not be conflated:

1. Full task transcripts and metadata in local session storage.
2. Auto-compact summaries inside a task.
3. `/newtask` distilled handoffs between tasks.
4. The optional project “Memory Bank” Markdown convention.

Persistent teams add a fifth form—task board, mailbox, and mission log—but that is coordination state, not semantic memory.

There is no need to port any of these as a new memory layer. The harness already has transcripts, handoff skills, an objective event ledger, and heavily exercised `basic-memory`. **NATIVE (Claude Code already does this; we just enable it)** covers session persistence, checkpoint resume, `/compact`, `/context`, `/clear`, and rewind ([Claude sessions](https://code.claude.com/docs/en/sessions), [Claude checkpoints](https://code.claude.com/docs/en/checkpointing)). The installed `handoff` skill covers the fresh-task pattern (`C:\Users\Prekzursil\.agents\skills\handoff\SKILL.md:1-15`).

Cline is worse here for this owner: its documented Memory Bank begins with the instruction that memory “resets completely” and therefore all bank files must be read at every task ([Memory Bank custom instructions](https://docs.cline.bot/best-practices/memory-bank#memory-bank-custom-instructions)). That is manual, unranked, and likely to go stale. very likely (80-90%) that replacing `basic-memory` with it would reduce retrieval precision and increase prompt cost; evidence is the mandatory all-file load versus the corpus’s 357 searches/353 targeted reads. A direct memory benchmark could settle the magnitude, but replacement has no evidentiary case.

## 6. Tool and MCP handling

### 6.1 Concrete Cline mechanisms

Cline tools are registered into a contribution registry, filtered by global and per-tool policies, and wrapped by before/after model and tool hooks. Hook layers may stop, skip, mutate tool input, or replace results ([runtime hook merge](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L114-L225)).

MCP supports local STDIO and remote Streamable HTTP/SSE servers, enable/disable, restart, timeouts, server-specific `autoApprove`, resources, and rich responses. The CLI has a wizard for list/add/edit/toggle/delete; 4.0 moved MCP state into shared settings with lock/atomic updates and refreshes the MCP hub after marketplace installs ([MCP docs](https://docs.cline.bot/mcp/mcp-overview), [4.0 changelog](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L255-L276)).

Cline can also install plugins from a raw HTTPS TypeScript/JavaScript file, Git, npm, or local path; plugins register tools, hooks, commands, rules, skills, and MCP capabilities ([plugin docs](https://docs.cline.bot/customization/plugins)). The 4.0 Customize marketplace brings Skills, MCP, and Plugins into one UI.

### 6.2 What is better than ours

#### Atomic MCP settings writes and immediate health refresh — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

The owner has a cross-plane manager, which is broader than Cline’s single ecosystem, but the live state is unreliable: a dead Tavily plane was called 532 times with a 25.8% error rate, and the prior audit found the drift sentinel early-returns because its installed receipt lacks the expected settings baseline (`D13.md:60-68`). Cline 4.0’s settings lock/atomic update and post-install hub refresh are the right small ideas.

Port mechanism:

- Add a compare-and-swap/lockfile around each MCP config write in the existing manager.
- Write to a same-volume temporary file, parse/validate it, fsync/replace atomically, and retain a recoverable previous version.
- Immediately run the existing status probe; if a server is “not connected,” mark it unhealthy in the manager’s inventory and suppress recommendation/routing until a successful probe or explicit override.
- Fix the installed receipt to hash the actual `.mcp.json`, `.claude.json`, and Codex TOML server sections, not only `settings.json`.
- Do not hot-restart host processes by inventing a daemon; expose “restart required” when the native host cannot refresh.

very likely (80-90%) to prevent config truncation/races and dead-server routing because the current failure is directly observed and Cline’s atomic-write design matches it. UNVERIFIED whether each host exposes a non-destructive live MCP refresh command; test Claude `/mcp`, Codex MCP reload, and Antigravity independently before promising hot refresh.

### 6.3 What not to copy

- **Dynamic MCP creation/install from natural language.** Cline advertises that it can clone/build or create MCP servers. For this owner, fetched repository instructions are untrusted input and enabled launchers have already drifted. Keep deterministic admission: immutable revision/version, digest, declared tools, env-var names, transports, risk, and exact approval list. Cline’s public plugin install supports `@main` and raw file URLs ([plugin installation](https://docs.cline.bot/customization/plugins#installing-plugins-via-cli)); that is weaker supply-chain hygiene than the desired manifest.

- **Direct in-process TypeScript plugins.** They are expressive, but they expand trusted code inside the runtime. Skills, hooks, and MCP already cover the required extension shapes with clearer process boundaries. almost certain (90-99%) that no large plugin runtime is justified here because every useful identified port rides an existing hook/MCP/skill bus.
- **Treating per-server `autoApprove` as sufficient risk policy.** Approval belongs to the host’s deny/ask/allow layer and tool semantics, not a server-owned list.

## 7. Permission model

### 7.1 Cline

The IDE’s Auto Approve is category-based: project/all-file reads, project/all-file edits, safe/all commands, browser, MCP, and notifications. Cline’s docs state that the **model** marks a command `requires_approval`; there is no fixed safe-command allowlist ([Auto Approve](https://docs.cline.bot/features/auto-approve#safe-vs-approval-required-commands)). YOLO approves every file operation anywhere, all terminal commands, browser actions, MCP tools, and Plan→Act transitions ([YOLO](https://docs.cline.bot/features/auto-approve#yolo-mode)).

The CLI adds deterministic `CLINE_COMMAND_PERMISSIONS` with allow/deny glob lists, deny precedence, and redirects disabled by default; however, the CLI reference also says default invocation starts in Act with auto-approve enabled and `--auto-approve` defaults true ([CLI reference](https://docs.cline.bot/cli/cli-reference#cline-command-permissions)). The 4.0 changelog separately says command auto-approval is disabled by default for new/reset VS Code configurations. These statements can both be true for different surfaces, but the surface split is easy to misunderstand.

### 7.2 Comparison

Nothing should be ported. Claude Code already provides the stronger mechanism: host-enforced deny → ask → allow precedence, tool/input/domain/MCP patterns, compound-command parsing, process-wrapper normalization, managed settings, worktree-aware persistence, and hooks that cannot override deny/ask policy ([Claude permissions](https://code.claude.com/docs/en/permissions)). **NATIVE (Claude Code already does this; we just enable it).**

Cline is worse in four ways:

1. Model-declared command risk is circular: the actor proposes the command and supplies the risk bit. Claude Code explicitly says permission rules are enforced by the host, not the model.
2. YOLO disables the safety checks Cline otherwise presents as the user-control boundary.
3. CLI auto-approve defaults are more permissive than the 4.0 VS Code defaults, creating cross-client surprise.
4. Broad “use MCP” approval does not express per-server/tool/data-boundary risk as precisely as Claude’s canonical MCP permission names.

Our problem is not a missing permission model; it is faulty custom guards layered on top. D1/D1b shows guards matching prose, field names, and negation, including a successful result with `"user_cancelled_or_timedout": false`. The port lesson is to simplify and repair semantic discrimination, not add Cline policy.

## 10. Verification and self-check mechanisms

### 10.1 What Cline does

1. **Human approval and diff preview** before edits/commands unless auto-approved.
2. **Checkpoints** after tool use with compare and three restore modes; shadow Git captures untracked files and command-caused workspace changes ([checkpoints](https://docs.cline.bot/core-workflows/checkpoints)).
3. **Repeated-call loop detector** with a soft recovery notice and hard stop.
4. **Consecutive-mistake tracker** for invalid tool calls/no tool calls/tool failures, default max six in current SDK source.
5. **Focus Chain** warns when completion occurs with checklist items remaining; telemetry has `task.focus_chain_incomplete_on_completion` ([OTel event reference](https://docs.cline.bot/enterprise-solutions/monitoring/opentelemetry-events)).
6. **Terminal exit-code/error feedback**, browser automation, and ordinary model-driven build/test commands.
7. **Historical experimental “double-check completion.”** Version 3.58 added it, but current 4.0 docs/source discovery did not expose a stable public mechanism ([3.58 changelog](https://github.com/cline/cline/blob/557d725690024b7c12dfad7672c476de74bd1eac/CHANGELOG.md#L680-L720)). UNVERIFIED whether it survived the 4.0 SDK migration; toggle discovery plus a controlled false-completion task would settle it. No recommendation rests on it.

### 10.2 What is better than ours

#### Selective recovery for command-caused local file changes — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Claude native checkpointing covers Write/Edit/NotebookEdit but explicitly not Bash changes. Cline’s shadow Git captures project file state after commands too. Our old custom checkpoint source is stale (“Claude Code has NO built-in edit-undo,” `checkpoint.py:2-6`), ignores Bash entirely (`:185-193`), and is unwired.

Do not re-enable it wholesale. Refactor the small existing code into a **selective pre-command snapshot** only for commands classified as locally file-mutating and not already recoverable through direct edit checkpoints. Use `git stash create`/reachable refs without touching the index, record affected worktree/repo, and preview before restore. Never imply it can undo databases, APIs, deployments, package registries, or sibling worktrees.

likely (55-80%) to close the narrow Bash-local-file rollback gap, but performance/concurrency safety is UNVERIFIED. A disposable worktree experiment must cover new/untracked/ignored files, nested repos, concurrent sibling edits, large repositories, and commands that mutate outside the repo before any live wiring.

### 10.3 Where ours is better

- `verification-before-completion` requires fresh command output, exit code, and claim-specific evidence (`C:\Users\Prekzursil\.agents\skills\verification-before-completion\SKILL.md:3`, `:31-50`). Cline’s generic completion tool/checklist is model-in-loop and therefore weaker evidence.

The weakness is invocation reliability: corpus capability counts show `verification-before-completion` only three times and `fresh-context-verify` five times, so these strong mechanisms are sparsely exercised.
