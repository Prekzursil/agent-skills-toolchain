# C001 — Context lifecycle: what actually survives Claude Code compaction

## Executive verdict

Claude Code compaction on this machine is not one mechanism. It is a four-layer continuity stack:

1. Claude Code replaces old message history with a generated `isCompactSummary` message.
2. Claude Code also retains a host-selected exact message tail, including text, thinking, tool calls, tool results, system records, and attachments.
3. Startup-class material is reloaded according to native Claude Code rules: the system prompt, project-root `CLAUDE.md`, unscoped rules, auto memory, and a bounded set of invoked skill bodies return; path-scoped rules and nested `CLAUDE.md` content do not return until a matching file is read again.
4. This harness writes an external PreCompact checkpoint to basic-memory and, only since promotion on 2026-07-18, can inject the session goal after compaction.

The generated narrative summary is useful but not authoritative. In the measured corpus, only 664 of 7,521 literal direct-user strings between boundaries (8.8%) appeared verbatim in the next summary; only 41 of 341 measurable last-user strings (12.0%) appeared verbatim. This does **not** measure semantic retention, so it is a floor on exact wording, not an estimate of meaning lost. A concrete recent boundary contains a factual summary error: the summary says the #92 finisher was not dispatched, while the exact preserved tail contains the dispatch text, `Agent` call, and `async_launched` result. The first new assistant turn correctly says both coders are running. Exact-tail preservation therefore caught a narrative-summary distortion in real operation.

The basic-memory layer is durable but not presently an automatic replay of working state. The vault contains 99 retained sanitized checkpoints (63 Claude, 36 Codex), all with a nonempty goal, but 70/99 have no decisions, 69/99 have no `.remember/now.md` content, and 71/99 are truncated. The automatic lexical recall index explicitly excludes `compaction-checkpoints`; only 3 of 392 unique compactions were followed by an explicit basic-memory recall within five assistant records. The checkpoint is recoverable by direct basic-memory search, but it normally sits out-of-band.

It is **very likely (80-90%)** that evolution on the native hook bus is better than replacement with another memory/orchestration runtime, because the measured native exact tail already corrected the one verified summary contradiction, while the measured external ledger and vault already supply durable storage: keep the native summary plus exact tail, add a short session-scoped typed continuity capsule, inject it through the existing PostCompact event, and deterministically overlay terminal task facts when they contradict prose. This directly addresses the observed failure without reintroducing a vector/KG store, durable-execution engine, trained critic, or second orchestrator.

## Detector design and validation

### Boundary signatures

The real transcript representation has two adjacent records:

- a top-level system record with `"subtype":"compact_boundary"`, and
- the immediately following user record with `"isCompactSummary":true`.

A recent example is `C:\Users\Prekzursil\.claude\projects\C--Users-Prekzursil\30bd50d4-5a72-4c19-8fd5-85b6430c7b7d.jsonl:8-9`. Line 8 contains trigger, pre/post token counts, duration, discovered tools, preserved-segment UUIDs, and preserved-message UUIDs. Line 9 contains the generated structured summary and points back to source session `3cd9445a-ab17-4eec-ad05-c1d1bf411c40`.

### Two mechanically independent all-corpus signals

Signal A used forced-text ripgrep across every JSONL file:

```text
rg -a -n --no-heading --glob *.jsonl \
  '"subtype":"compact_boundary"|"isCompactSummary":true' ~/.claude/projects
```

It found 435 boundary rows and 435 summary rows. Every boundary was immediately followed at physical line `N+1` by a compact summary. UUID deduplication yielded 392 unique boundary UUIDs in 194 files; 43 physical duplicates are fork/copy reuse, not new summarization operations.

Signal B was a separate Python binary-line walker over all 11,908 JSONL files and 1,604,092 lines. It prefiltered byte strings, parsed only candidates with `json.loads`, and tested the top-level fields. It independently found 435 boundaries, 435 summaries, 392 unique UUIDs for each, zero candidate parse failures, and a known-present control UUID five times.

The first ripgrep pass without `-a` produced 434/434 and warned that two files became “binary” after NUL bytes. Forced-text ripgrep and the independent Python walker both found the missing event. This is a concrete example of why single-probe absence claims are unsafe on this corpus.

### Measurement units

- **Physical pair:** a boundary/summary pair stored in a file; N=435.
- **Unique event:** boundary UUID deduplicated across forks/copies; N=392.
- **Modern-metadata event:** unique event with `preservedMessages`; N=329. Sixty-three older events lack that field.
- **Literal-user segment:** unique event with at least one preceding string-valued user message in the same physical segment; N=341. Fifty-one cross-session/line-one/empty cases cannot support this literal comparison.

## What the native runtime preserves

### 1. The structured compact summary

All 392 unique events have a generated summary. Summary length was 1,548–24,871 characters, median 14,358.5. The full nine-section template (`Primary Request`, concepts, files, errors, problem solving, user messages, pending tasks, current work, optional next step, plus transcript pointer) appeared in 381/392 unique events; 11 older/alternate summaries were shorter.

The summary is inserted as a user-role record that is transcript-visible only. In the recent example, it is the `anchorUuid` named by boundary metadata (`...30bd50d4...jsonl:8-9`). New-generation summaries also carry both the source session (`session_id`) and current continuation session (`sessionId`): among unique events, 68 were same-session, nine explicitly crossed sessions, and 315 older summaries did not serialize a source-session field. Therefore source provenance is exact for 77 recent events and UNVERIFIED for 315 legacy events; the settling experiment is to reconstruct each legacy boundary’s parent chain from UUIDs and compare it to every basename-matched source transcript.

### 2. An exact selected message tail

Modern boundary metadata identifies an `anchorUuid` for the summary and a separate ordered `preservedMessages.uuids` list. Across 329 unique modern events:

- selected UUIDs: 25,131 total;
- selected per event: median 6, p90 111, maximum 1,883;
- candidate `allUuids`: 37,412 total, median 6, p90 147, maximum 3,320;
- 70/316 nonempty candidate sets selected fewer UUIDs than `allUuids`; 246/316 selected all candidates.

The selected records are not just prose. Top-level types verified in the raw continuation files include 9,266 attachments, 3,366 user tool results, 3,353 assistant tool calls, 3,197 assistant text records, 2,708 thinking records, 1,577 system records, and 983 string-valued user messages, plus smaller mixed classes. At least 111 physically present omitted records were assistant thinking records. Thus the exact tail can retain operational receipts and tool state, while some thinking is discarded.

The metadata-to-disk verifier found 25,889 of 25,978 unique `(continuation path, selected UUID)` pairs as top-level transcript records. The other 89 UUIDs occur only inside boundary metadata and not as top-level records; e.g. `87dc9800-...` is listed as preserved at `C:\Users\Prekzursil\.claude\projects\C--Users-Prekzursil-Documents-GitHub\09158d9e-df69-4e33-8371-22a2963e3d7d.jsonl:9789` but has no top-level record in that file. Whether those 89 records existed transiently in the model request is UNVERIFIED; capture the post-compaction API message array or run a nonce-bearing canary message immediately before compaction to settle it. They must not be called “lost” or “preserved” from transcript evidence alone.

For same-session compaction the preserved records generally remain physically before the boundary and are referenced into the new logical segment. For a cross-session continuation they can be copied after the summary. Physical line order is therefore not model-context order; the UUID metadata is the authoritative structural signal.

### 3. Reloaded startup-class context

Official Claude Code documentation states that after compaction:

- system prompt and output style are unchanged;
- project-root `CLAUDE.md` and unscoped rules are re-injected from disk;
- Claude Code auto memory is re-injected from disk;
- path-scoped rules and nested `CLAUDE.md` files are absent until a matching file is read again;
- invoked skill bodies are re-injected subject to 5,000 tokens per skill and 25,000 tokens total, with oldest skills dropped first.

These are native host behaviors, not visible as ordinary transcript messages, so this unit did not pretend the JSONL could re-measure them. The documented behavior is current at the cited official page. Note that “auto memory” here is Claude Code’s native memory; it is not this owner’s basic-memory MCP. The owner’s own `C:\Users\Prekzursil\.claude\CLAUDE.md:5-11` explicitly says basic-memory does not auto-load and must be queried.

The official docs also state that older tool outputs are cleared first, then conversation history is summarized. That matches the transcript evidence that exact preservation is selective rather than a replay of all messages.

### 4. Tools and external processes are not conversation memory

Boundary metadata serializes `preCompactDiscoveredTools`, sometimes dozens of names (`...30bd50d4...jsonl:8`). Tool schemas/names are host-managed startup/tool-search context rather than old conversation turns. Whether a particular deferred tool schema remains loaded in the first post-compact API request is UNVERIFIED; run `/context` before and after a canary tool discovery, or capture the request’s tool definitions, to settle it.

External jobs and subprocesses can continue independently, but knowledge of them must come from the summary, exact tail, task registry, or a fresh status probe. The latest-20 audit repeatedly showed the first post-compact action rechecking live state rather than assuming it: for example the compute campaign continuation explicitly verified that the box was up and measured upload progress. This is good operational behavior, not evidence that process state itself was “remembered.”

## What is lost or distorted

### Literal wording is mostly not retained in the narrative summary

The all-boundary literal test accumulated string-valued user messages between successive physical boundaries, excluded compact summaries and list-valued tool results, and checked whether each full stripped string occurred in the next summary:

- 7,521 direct strings across 341 measurable segments;
- 664 exact full strings in the summary: 8.83%;
- 146/341 summaries contained at least one complete preceding string;
- 2/341 contained every preceding string;
- 41/341 contained the complete last string: 12.02%;
- direct strings per segment: median 9, p90 56, maximum 544.

This is deliberately a literal metric. Paraphrase can preserve a requirement without preserving its exact wording, and copied preserved-tail messages can appear in later physical segments. Semantic-loss percentage is UNVERIFIED; a blinded, atomic-obligation annotation benchmark over a stratified sample of boundary/source pairs would settle it. No plausible-sounding semantic-retention estimate is substituted here.

### One verified summary contradiction, corrected by exact tail

At `...\30bd50d4-5a72-4c19-8fd5-85b6430c7b7d.jsonl:9`, the generated `Current Work` says only the four-small-drafts coder was dispatched and that the #92 finisher “was NOT yet dispatched”; `Optional Next Step` says to dispatch it.

But the exact tail immediately shows:

- assistant text “Dispatching the #92 finisher” at line 11;
- an `Agent` tool call at line 12;
- a user tool-result with `toolUseResult.status:"async_launched"` at line 13.

Those records are timestamped 02:11:59–02:12:17, before the summary at 02:14:46 and boundary at 02:15:38. The first genuinely new assistant text, line 33 at 02:16:31, says “Both coders are running.” This proves three things:

1. the summary can be stale or factually wrong about the terminal action;
2. exact preserved records can overrule it;
3. continuation can remain correct when the host includes the decisive receipt.

A deterministic latest-20-boundary review compared parsed `Current Work`/`Optional Next Step`, preserved tail, and first new assistant action. Thirteen used the parsed modern sections: 12 continued consistently and the case above had a demonstrable contradiction neutralized by the exact tail. Seven alternate-template cases were not scored. This sample is evidence of a failure mode, not a population error rate.

## The real vault and ledger layer

### What gets written

`SanitizedCheckpointModule` runs only on `PreCompact` (`modules.py:1440-1460`). It writes to `D:/basic-memory/compaction-checkpoints` (`modules.py:1451`) and includes:

- session-scoped goal (`modules.py:1463`);
- the last ten decisions and open failures from project-wide ledger state (`modules.py:1462,1475-1482`);
- up to 4,096 redacted characters of `.remember/now.md`;
- a pointer into the event ledger;
- a session hash and project key.

It prunes after the newest 100 matching files (`modules.py:1519-1525`). The current vault contains 621 Markdown files, 126 tagged/type-marked compaction checkpoints, and 99 sanitized automatic checkpoints in the capped directory. The 99 providers divide exactly into 63 Claude and 36 Codex.

Mechanically independent dispatch evidence agrees: `terminal.jsonl` contains 63 successful Claude PreCompact records, all `action:"allow"` with no failed modules. All 63 retained Claude checkpoint timestamps exactly match a Claude PreCompact terminal timestamp to the second. The basic-memory CLI successfully returned a specific retained note by searching `checkpoint-20260719-034333`, proving the detector can retrieve a known-present checkpoint.

Checkpoint content quality:

- nonempty goal: 99/99;
- nonempty decisions: 29/99; none: 70/99;
- nonempty `.remember/now.md`: 30/99; none: 69/99;
- marked `[TRUNCATED]`: 71/99;
- file length: median 1,328 characters, range 626–6,466.

### Cross-session contamination inside the checkpoint

The implementation obtains `state = self.ledger.state(event.cwd)` but obtains `goal = self.ledger.goal(event.cwd, event.session_id)` (`modules.py:1462-1463`). Therefore the goal is session-scoped while decisions/failures are cwd/project-scoped. A real checkpoint for the OOM-drain session, `D:\basic-memory\compaction-checkpoints\checkpoint-20260719-034333-147179-f66b6a4b78472ca9.md:15-36`, contains decisions and failures from unrelated parallel audit units P1A05, P2A03, D009, F010, B002, A072, A073, A106, C007, F004, A053, and D017. This is not hypothetical: concurrent-unit state is already mixed into a session checkpoint.

It is **very likely (80-90%)**, based on the direct code path and the mixed real checkpoint, that using this note wholesale for recovery can distract or mis-anchor a resumed session. It is not certain to harm the model because the note is not normally auto-injected.

### What gets replayed

The deployed `GoalModule` has a PostCompact path (`modules.py:1303-1307`) that looks up the session goal and can emit `POST-COMPACT RE-ANCHOR` (`modules.py:1362-1378`). However, gate history matters:

- the current `module-modes.json` says the gate was observe-only before promotion and records 39 shadow fires across 20 sessions;
- live terminal records contain 49 Claude PostCompact successes: 44 `action:"allow"`, five `action:"inject"`;
- the five delivered injections occurred at 2026-07-18 22:50:43 and 2026-07-19 01:54:31, 02:59:27, 03:47:45, and 04:09:26 UTC.

Thus the claim “the ledger always survives compaction by injection” would be false historically. The goal was externally durable, but only five measured Claude events actually delivered the promoted injection.

The richer checkpoint is not automatically recalled. The lexical index excludes the entire `compaction-checkpoints` directory twice: at index build (`recall_index.py:46`) and at injection filtering (`modules.py:1634-1643`). `RecallModule` only runs on a substantial `UserPromptSubmit`, not PostCompact (`modules.py:1603-1613`). Across all 392 unique events, explicit basic-memory `build_context/search_notes/recent_activity/read_note` appeared at some later point before the next compaction in 56 events, but within five assistant records in only three; median first explicit recall among the 56 was assistant record 123. Therefore checkpoint existence is not equivalent to recovery use.

## Design recommendations

### R1 — NATIVE (Claude Code already does this; we just enable it): add a compact-instructions contract

Add a short `## Compact Instructions` section near the top of root `CLAUDE.md`, using the official native facility. It should require the summary to preserve, in this order:

1. exact active goal and latest owner correction;
2. terminal task states keyed by task/agent/run ID;
3. completed versus pending actions (never infer one from a promise);
4. irreversible/safety constraints;
5. changed paths, branch/commit/worktree identifiers;
6. live external-job identifiers plus “last observed at” timestamp;
7. failed approaches and falsifiable retry preconditions;
8. the single next action.

This is **very likely (80-90%)** to improve narrative-summary consistency because it directly targets the verified #92 “not dispatched” error and uses a documented native control point. It will not make prose authoritative; exact receipts still win.

### R2 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): session-scoped typed continuity capsule

Change the existing PreCompact module, not the runtime architecture. Write a bounded JSON/Markdown capsule keyed by session hash with fields such as:

```text
goal
owner_corrections[]
completed[{id, receipt, observed_at}]
pending[{id, next_action, blocker}]
live_external[{id, kind, last_status, observed_at}]
changed_refs[{path, commit_or_hash}]
constraints[]
open_failures[{fingerprint, retry_preconditions}]
```

Populate only session-attributable events. Do not copy `ledger.state(cwd)` last-ten lists across concurrent sessions. Preserve the existing redaction, bounded size, atomic write, and hook timing.

This is **very likely (80-90%)** to eliminate the measured cross-session checkpoint contamination because the defect is a direct keying mismatch in `modules.py:1462-1463`. It is **likely (55-80%)** to improve recovery beyond the narrative summary because it preserves terminal facts; the latter requires an A/B continuity benchmark to verify.

### R3 — CONFIG (settings/JSON only): retain `postcompact_reanchor=advise`, add a delivery canary before any wider promotion

Keep the recently promoted goal re-anchor in advisory/inject mode, never enforcement. Add a temporary, non-secret canary identifier to the payload/log and verify three independent surfaces for the next ten compactions: terminal `action:"inject"`, post-compact model-visible context, and first-action goal alignment. Remove the canary after validation.

It is **likely (55-80%)** that the current five successful injection terminal records represent real model-visible delivery, because the native PostCompact hook supports context output and the terminal action is `inject`; model visibility remains UNVERIFIED until the canary experiment inspects the actual post-hook context or elicits the nonce.

### R4 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): deterministic terminal-fact overlay using native `compact_summary`

Official PostCompact input includes `compact_summary`. The existing module ignores it. On PostCompact, parse only high-stakes typed statements from the capsule/ledger—not arbitrary semantic prose—and inject a short overlay:

```text
TERMINAL FACTS OVERRIDE SUMMARY:
- agent #92: async_launched at 02:12:17 (receipt ...)
- PR #88: merged at commit ...
- pending: review #92; do not redispatch
```

The summary can be logged/diffed for contradiction candidates, but no model judge, trained critic, or blocking guard is justified. Exact typed receipts take precedence; ambiguous prose is left alone.

This is **very likely (80-90%)** to prevent recurrence of the measured duplicate-dispatch class when the receipt exists, because the #92 contradiction is exactly a typed terminal-state disagreement. Coverage for untyped work is **unlikely (20-45%)** without better receipt capture; that limitation is acceptable because the mechanism should stay small and deterministic.

### R5 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): exact-session checkpoint replay, not broad memory search

At PostCompact, read the newest checkpoint whose session hash matches the current session and inject only the typed capsule plus ledger pointer. Do not add `compaction-checkpoints` to general lexical recall: those notes are high-churn, frequently truncated, and currently contain project-wide contamination. Keep ordinary basic-memory search for durable semantic notes.

This is **likely (55-80%)** to improve first-turn continuity because only 3/392 events explicitly recalled basic-memory within five assistant records, while exact-session lookup is deterministic. The effect size is UNVERIFIED; score first-action alignment and redundant-work rate on a held-out set of real compactions.

### R6 — UNVERIFIED — CONFIG (settings/JSON only): A/B natural-boundary compaction timing before changing the 90% threshold

Do not immediately lower `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`. Official docs recommend manual compaction at natural breaks, and the observed median compaction lasts 173 seconds, but earlier compaction also increases summary count and repeated-loss opportunities. Run an owner-specific A/B:

- A: current 90% of 1M auto threshold;
- B: manual `/compact` at a declared task boundary with the compact contract;
- measure wall time, number of compactions, first-action alignment, duplicate actions, literal/atomic obligation retention, and total tokens over matched long tasks.

It is **roughly even (45-55%)** whether a lower automatic threshold alone improves total task performance; the evidence supports better timing, not a particular threshold. The named A/B experiment settles the premise.

## Anti-overfit gate

All recommendations use Claude Code’s native compaction, `PreCompact`/`PostCompact`, the existing event ledger, the existing markdown basic-memory vault, and current dispatcher. None adds a second orchestration runtime, vector database/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

It is **very likely (80-90%)** that full replacement would be net-negative, because the native exact tail already prevented one verified summary error from changing behavior and the external ledger/vault already provide the needed durable substrate. Replacement would duplicate working buses while leaving the actual defect—untyped or cross-session-mixed terminal state—unsolved.
