# D013 — HARNESS-BENCH metric: correctness

## Executive decision

Define correctness as **Verified Correctness Yield, VCY-v1**: the fraction of a frozen,
versioned set of first-attempt cases for which an independent executable oracle proves every
required outcome and proves that no forbidden outcome occurred. Missing, corrupt, ungrounded,
or invalid runs receive no correctness credit, but remain visibly labelled `INVALID` or `MISSING`
rather than being falsely called incorrect.

The exact primary score is:

\[
\boxed{\operatorname{VCY\text{-}v1}(S)=100\times\frac{\sum_{i=1}^{N}P_{i,1}}{N}}
\]

where `S` is one immutable suite manifest, `N` is the number of planned cases in that manifest,
`1` is the first attempt, and `P[i,1]` is exactly `1` only when the case is valid and all of its
executable acceptance conditions pass; it is `0` for `FAIL`, `INVALID`, or `MISSING`. The score
therefore means “percentage of planned work proved correct on the first attempt,” not “percentage
of observed valid runs that happened to pass.”

This metric contains **no output bytes, tokens, KB/token, tool-call count, subagent count, test
count, or wall-clock term**. A terse verification agent that produces one decisive receipt earns
the same `1` as a verbose agent reaching the same proved state. A verbose agent that produces no
valid proof earns `0`. This directly satisfies the unit constraint that the low-KB/token
verification agent must not be penalised. The pinned brief states that this agent is near the
bottom on KB/token; that particular ranking is **UNVERIFIED in the supplied bundle — the settling
experiment is to join the original per-agent token/output table to its human-verified outcomes**.
The design does not depend on that ranking because output volume is absent from the formula by
construction.

The recommendation is **very likely (80-90%)** to distinguish “the harness actually worked” from
“the harness emitted plausible success text,” because (1) final-state execution is the outcome
oracle used by τ-bench, (2) milestone/minefield execution supports multiple valid trajectories in
ToolSandbox, (3) the local ledger already records executable receipts and mutation order, and (4)
the local execution probe below reproduced a lexical false-green that VCY-v1 refuses to credit.
The residual uncertainty is oracle adequacy, not score arithmetic.

## Scope and definition of the construct

“Correctness” here is **task outcome correctness attributable to one harness configuration**, under
a fixed provider/model/reasoning profile and a frozen case manifest. It is not:

* fluency, completeness of prose, or apparent confidence;
* raw test pass rate;
* hook uptime, latency, fire count, or false-positive rate;
* number of errors avoided, retries performed, tools called, skills invoked, or agents spawned;
* general intelligence; or
* proof that behavior outside the declared oracle boundary is correct.

Harness operational health is a sidecar because a faster or more talkative hook is not necessarily
a more correct agent. Verification adequacy is also a sidecar because a weak test can be green
while the implementation remains wrong. VCY gives no credit without an admitted oracle, but it
does not pretend that an admitted oracle is logically complete.

The suite compares harness revisions only while the tuple
`(suite_version, case_id, attempt, provider, model_id, reasoning_profile, grader_revision,
environment_revision, budget)` is held fixed. A manifest change creates a new series; scores from
different manifest versions are displayed separately and are never differenced.

### 5. Frontier evidence changes the design, but not into a second runtime

τ-bench compares final database state with an annotated goal state and separates repeated-trial

forbidden events, not one canonical action trace.

## Exact operational formula

### Case manifest

Every case `i` in immutable suite manifest `S` declares:

```text
suite_version, case_id, family, critical
task_prompt_hash, fixture_hashes, initial_state_hash
provider, model_id, reasoning_profile, harness_revision, environment_revision
budget, timeout_class
R_i = required requirement families
F_i = forbidden predicates (minefields)
A_i = allowed state boundary
G_i = grader executable + grader hash + grader revision
```

Each required family `r` contains one or more explicitly equivalent oracle alternatives. This is
important for platform-neutral outcomes: `ANY` is allowed only among alternatives inside one
requirement family, while `AND` applies across families.

For attempt `a`, let:

* `O[i,a,r,k]` be `1` when deterministic oracle alternative `k` for required family `r` passes;
* `M[i,a,f]` be `1` when forbidden predicate `f` occurred;
* `D[i,a]` be `1` when final state/artifact hashes are inside `A_i` and match the declared final
  predicates;
* `Q[i,a]` be `1` only when the run passes every validity condition below.

Then:

\[
R_{i,a}=\prod_{r\in R_i}\max_{k\in r}O_{i,a,r,k}
\]

\[
X_{i,a}=\prod_{f\in F_i}(1-M_{i,a,f})
\]

\[
P_{i,a}=Q_{i,a}\times D_{i,a}\times R_{i,a}\times X_{i,a}
\]

All terms are binary. There are no partial points. One missing requirement, one minefield, an
out-of-bound side effect, or invalid instrumentation makes `P=0`.

### Validity predicate

`Q[i,a]=1` if and only if all of these hold:

1. the planned `eval_start` exists once and its episode, suite, case, attempt, configuration, and
   hashes equal the manifest;
2. the actual initial-state hash equals `initial_state_hash`;
3. the grader executable and fixtures equal their pinned hashes;
4. the case's oracle-admission record is current for the same grader/fixture hashes;
5. the agent process reaches a terminal state within the declared timeout, and the grader itself
   exits normally;
6. the final boundary snapshot is complete and parseable;
7. every required event/receipt used by the grader has the same `episode_id` and is deduplicated;
8. no unknown lexical receipt is used as an oracle; accepted sources are explicit process exit,
   parsed structured count tied to that process, exact state query, content hash, protocol/API
   status with schema validation, or recorded human adjudication identity;
9. the final `eval_result` is written once with the same manifest and grader hashes; and
10. no infrastructure fault, environment drift, grader self-test failure, or missing planned event
    is present.

The four external labels are mechanically derived:

```text
PASS     := Q=1 and D=1 and R=1 and X=1
FAIL     := Q=1 and (D=0 or R=0 or X=0)
INVALID  := Q=0 for an attempted case
MISSING  := no eval_start for a planned case, or no terminal result by collection close
```

`INVALID` and `MISSING` count as zero in VCY's planned denominator but are never relabelled `FAIL`.
This prevents deleting failures or breaking telemetry from improving the number, while preserving
the epistemic distinction between “proved wrong” and “not measured.” Always publish the raw vector
`PASS/FAIL/INVALID/MISSING/N` next to VCY.

The conditional rate
`100*PASS/(PASS+FAIL)` may be shown only as the diagnostic label
`valid-case pass rate`; it is never the headline and is undefined when `PASS+FAIL=0`.

### Repeat reliability and critical veto

VCY-v1 is first-attempt correctness. It does not grant correctness credit for retries. If the
deployed policy genuinely permits up to `k` retries, publish `pass@k` separately; do not substitute
it for VCY.

For deterministic release-critical cases, run three fresh roots and define:

\[
\operatorname{CriticalPass^3}=\prod_{i\in C}\prod_{a=1}^{3}P_{i,a}
\]

where `C` is the manifest's fixed critical set. `CriticalPass^3` is either `1` or `0`; any invalid,
missing, or failed critical trial vetoes promotion. Report each trial, because three successes do
not establish a production failure probability. Inspect's evaluation framework likewise keeps
`pass_at_k` and all-k `pass_k_k` distinct and supports sample/grouped uncertainty
([Inspect metrics](https://inspect.aisi.org.uk/metrics.html)).

### Why the quiet verification agent is not penalised

For any two trajectories `t1` and `t2` with the same validity, final state, required oracle values,
and minefield values:

\[
P(t1)=P(t2)
\]

regardless of `tokens(t1)`, `bytes(t1)`, `tool_calls(t1)`, `subagents(t1)`, or duration. Therefore a
near-zero-output verifier and a long-report verifier are score-equivalent when their proved outcome
is equivalent. Efficiency metrics such as seconds per pass, tool calls per pass, and tokens per
pass may be reported as non-gating diagnostics; they do not enter VCY and must not be used to rank
verification quality.

## Oracle admission: verify the verifier before scoring an agent

A case cannot enter the scored manifest until its oracle passes all admission checks:

1. **Known-good positive control.** A trusted reference or independently constructed valid
   trajectory must pass.
2. **Known-bad negative control.** A no-op plus at least one defect-seeded implementation must fail.
   For an “absence” predicate, inject a known-present forbidden event and prove the detector finds
   it before accepting a clean absence.
3. **Alternative-valid control.** At least one semantically valid non-reference trajectory must
   pass whenever the task admits multiple implementations. This catches tests coupled to a gold
   patch.
4. **Metamorphic control.** A semantics-preserving variation such as irrelevant file order,
   platform-normalised path, or equivalent API ordering must not change the outcome.
5. **Determinism control.** Two grader runs over the same frozen evidence bundle must produce
   byte-identical labels and reason codes.
6. **Tamper control.** Changing the agent-visible success text without changing final state must
   not change the grade.
7. **Boundary control.** A deliberately out-of-scope write must trigger the side-effect predicate.

These checks implement the owner's known-positive rule mechanically. The source's current schema
is closed and exposes tool name, ID, input, and result
(`/local_disk0/codexwork/bundle/agents/harness/schemas/hook-event.schema.json:5-55`), while the
result schema exposes status/action/reason/context but no benchmark identity
(`/local_disk0/codexwork/bundle/agents/harness/schemas/hook-result.schema.json:5-37`). The admission
bundle therefore belongs beside the case manifest, not inside agent prose.

The admission protocol is **very likely (80-90%)** to catch the observed detector class because it
requires both known-present and known-absent controls and because the live defect arose precisely
from detectors that had no semantic-role discriminator
(`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-22,111-129`). It cannot prove
coverage of unseeded defects.

## Instrumentation and attachment points

### Proposal 1 — CONFIG (settings/JSON only): immutable suite and case manifests

Store the fields above in versioned JSON. Hash canonical JSON bytes. The manifest defines the
planned denominator before execution, preventing case deletion, easy-case injection, or post-hoc
weight changes. It also defines the state boundary and which cases are critical.

Confidence: **almost certain (90-99%)** that a frozen manifest prevents denominator edits within a
run, because the collector recomputes and compares its hash; it does not prevent a maintainer from
publishing a new easier suite version, which is handled by never comparing across versions.

### Proposal 2 — UNVERIFIED live child propagation — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): provider-common episode wrapper

Attach at an explicit `/eval run` or benchmark launcher, before the provider is invoked. Do not use
native `TaskCreated`/`TaskCompleted` as the canonical boundary: registrations declare those events

normalised event contract lacks suite/case/attempt fields
(`/local_disk0/codexwork/bundle/agents/harness/models.py:25-42`).

The wrapper:

1. loads and hashes the manifest;
2. creates `episode_id = SHA256(run_id || suite_version || case_id || attempt)`;
3. creates a fresh temporary state root and declared task sandbox;
4. snapshots initial state;
5. appends `eval_start` to the existing `EventLedger`;
6. exports only the opaque episode ID to the existing dispatcher/ledger path;
7. invokes the pinned provider/model/profile/budget; and
8. invokes the independent grader after termination or timeout.

The existing CLI already accepts provider, event, and a redirected state root

The ledger already offers locked, deduplicated, additive append semantics (`ledger.py:817-880`).

Confidence: **likely (55-80%)** that the wrapper itself stays below roughly 200 lines, based on
those existing seams. **UNVERIFIED whether both live Windows providers preserve an exported episode
ID through every child/subagent — the settling experiment is a copied-state Claude/Codex trace that
asserts one episode ID on parent, tool, mutation, and subagent events**. Until that passes, subagent

### Proposal 4 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): independent final-state grader

Attach after the agent process, outside the model context. The grader reads only the pinned
manifest, isolated final state, and episode-filtered evidence. It performs exact state queries,
content hashes, executable acceptance commands, and minefield checks; then emits one signed/hash-
anchored evidence bundle and `eval_result`. It ignores assistant claims and positive words.

For code repair, a required family normally contains baseline reproducer failure, candidate
reproducer pass, and regression-suite pass as three separate `AND` families; for a behavior-
preserving refactor, add differential behavior and state-boundary predicates; for research, use
deterministic source/identifier/schema checks and explicit human adjudication for semantic claims;
for tool/state tasks, query final world state plus minefields. These are manifest policies, not
free-form model judgments.

Confidence: **likely (55-80%)** that a small grader core can support exact/hash/exit/schema
predicates below 200 lines if domain-specific predicates remain case-owned executables. Open-ended
semantic correctness without human adjudication is **UNVERIFIED — the settling experiment is a
blinded calibration set with two independent human labels and disagreement adjudication**; such
cases remain `INVALID` rather than using an uncalibrated LLM judge.

### Proposal 5 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): streaming scorer and report

The scorer reads planned cases from the manifest, streams all `eval_start`/`eval_result` events for

Confidence: **very likely (80-90%)** that this remains a bounded small component because the
formula is binary and the ledger is JSONL. Performance on the full Windows ledger is **UNVERIFIED —
the settling experiment is a timed streaming scan of the largest live shard with peak RSS and
elapsed time recorded**.

### Proposal 6 — CONFIG (settings/JSON only): promotion policy

Promotion requires all of:

* candidate VCY is not lower than the paired baseline VCY on the identical manifest;
* `CriticalPass^3 == 1`;
* `INVALID + MISSING == 0` for the critical set;
* no new minefield violation; and
* oracle-admission records match the active grader and fixture hashes.

For non-critical stochastic cases, raw paired outcomes and confidence intervals accompany the
point estimate; this unit does not set an effect-size threshold before a baseline exists.

Confidence: **likely (55-80%)** that this conservative policy prevents obvious correctness
regressions because a critical failure is a veto and all comparisons are paired. The useful
non-critical regression threshold is **UNVERIFIED — two complete paired baseline/candidate suite
runs plus bootstrap/Wilson uncertainty would settle the variance before choosing it**.

## Failure modes and exact score behavior

| Failure mode | How it creates a wrong score | Detection / treatment |
|---|---|---|
| Lexical false-green | Tool output contains “ok” or “success” without proving the task | `oracle_source=text_heuristic` is forbidden; case is `INVALID` if no independent oracle. Reproduced in this unit. |
| Weak or low-coverage tests | Incomplete implementation passes | Negative defect seeds, alternative valid implementation, boundary checks; residual risk remains and is reported as oracle adequacy. |
| Overly strict tests | Correct alternative implementation fails | Alternative-valid and metamorphic admission controls; failing admission excludes the case. |
| Underspecified prompt | Hidden grader enforces unstated behavior | Human admission checks requirement-to-oracle traceability; ambiguous case excluded or explicitly adjudicated. |
| Gold-patch coupling | Grader rewards one implementation rather than behavior | At least one independent valid trajectory must pass. |
| Stale green | Tests passed before later mutation | Final-state grader runs after termination and binds evidence to candidate/final-state hash. Existing ledger ordering is a supporting signal only. |
| Untracked shell mutation | Freshness floor misses formatter, `git apply`, or in-place rewrite | Full declared-boundary before/after snapshot is independent of hook mutation classification. |
| Wrong episode attribution | One agent/session borrows another's receipt | Exact episode join; blank/mismatched IDs make the case `INVALID`. |
| Dropped telemetry | Easy failures disappear from observed denominator | Planned manifest denominator; missing result is `MISSING` and receives zero credit. |
| Duplicate event | One success is counted twice | Event-ID dedupe; conflicting duplicates make the case `INVALID`. |
| Hook fail-open | CLI exit zero looks healthy while modules failed | Hook exit code never grades correctness; terminal/failed modules are health sidecars. |
| Flaky oracle/environment | Same evidence alternates labels | Admission determinism fails; scored trial is `INVALID`; preserve raw reruns. |
| Network/service drift | External dependency failure looks like agent failure | Pinned replay fixture when possible; otherwise explicit environment revision and `INVALID`, never silent exclusion. |
| Agent tampers with tests | Modified grader makes its own patch pass | Grader/fixture hashes checked from outside agent-writable boundary. |
| Prose/action confusion | Mentioning a dangerous command trips a guard | Matched benign/malicious controls and semantic-role predicates; grade actual forbidden effect, not payload substring. Live examples are at `INPUT-known-harness-defects.md:9-76`. |
| Correct outcome through a different path | Exact-trace grader false-fails | Grade final state and partial-order milestones/minefields, not a single call sequence. |
| Side effect outside target | Main tests pass but unrelated state is damaged | Declared boundary snapshot plus minefields; any forbidden delta makes `FAIL`. |
| Human semantic grader disagreement | Subjective result becomes false certainty | Retain labels/adjudicator IDs and disagreement; unresolved case is `INVALID`. |
| Verifier process crash | No grade | `INVALID` if start exists; `MISSING` if no result by collection close; zero credit either way. |
| Easy-case suite inflation | Aggregate rises without improvement | Manifest frozen; new version is a separate series; publish per-family cases. |

The false-positive and false-negative directions both matter. The newest primary evidence is
especially sobering: the July 2026 audit found both overly strict tests and low-coverage tests in a
major coding benchmark. Therefore VCY is **likely (55-80%)** to be a substantially better local
release signal than raw “tests passed,” but **almost certainly not (1-5%)** a proof of complete
semantic correctness beyond its admitted oracle boundary; both bands are grounded in the same
external audit plus the local lexical false-green execution.

## Goodhart analysis

Optimising VCY can still perversely encourage:

1. **Teaching to the manifest.** The harness may special-case known fixtures. Controls: keep a
   rotating held-out tranche, hash and version it, and review suspicious case-specific branches.
2. **Avoiding hard work.** Maintainers may remove or invalidate difficult cases. Controls: fixed
   planned denominator, `MISSING/INVALID` count as zero, case deletion changes suite version, and
   family counts are always visible.
3. **Narrow fixes that satisfy the oracle.** An agent may overfit visible tests. Controls: hidden
   boundary tests, defect seeds, differential/metamorphic cases, regression families, and
   out-of-bound minefields.
4. **Suppressing instrumentation.** If telemetry failure excluded cases, breaking the detector
   would increase score. VCY instead gives missing/invalid runs zero credit and reports them
   separately.
5. **Retry farming.** Unlimited attempts can turn luck into apparent correctness. VCY uses first
   attempts; `pass@k` is separate and only matches an actual retry policy.
6. **Excessive conservatism.** A harness may refuse valid actions to avoid minefields. Paired benign
   cases and required positive milestones make refusal fail utility cases.
7. **Test-only artifacts.** The agent may leave production behavior untouched while altering test
   state. External grader hashes and final boundary state detect this.
8. **Verifier verbosity gaming.** If explanation length entered the score, verbose agents would
   win. It does not. This is the explicit anti-KB/token safeguard.
9. **Verifier silence gaming.** If absence of a detected violation counted as success, disabling a
   detector would win. Known-positive controls and required positive milestones prevent this.
10. **Critical-set neglect.** A high mean can hide one catastrophic regression. `CriticalPass^3`
    is a non-compensatory veto.
11. **Case-family flooding.** Adding many nearly identical easy cases can dominate a micro-average.
    Frozen manifests prevent within-version flooding; per-family results expose imbalance. A later
    macro-average may be added only after the owner approves domain weights.
12. **Human-adjudication drift.** Reviewers may learn expected harness identity. Blind the harness
    revision and randomise ordering; preserve disagreements.

The held-out tranche's marginal benefit is **likely (55-80%)** because fixture special-casing is a
standard consequence of repeated benchmark exposure, but the appropriate rotation frequency is
**UNVERIFIED — the settling experiment is to compare public-case versus held-out deltas over three
harness revisions**.

## Anti-overfit gate and rejected alternatives

Every proposal above rides the existing JSON/dispatcher/EventLedger/test bus. None adds a second
orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic,
observability SaaS, or guardrail framework.

Rejected:

* **LLM-as-final-judge:** nondeterministic and weaker than execution for executable cases; retain
  only as non-gating triage or as a tool for a human adjudicator.
* **Rewarding number of tests/receipts:** makes test splitting and receipt spam profitable.
* **Rewarding tool or agent count:** makes fan-out and retries profitable.
* **Output volume or KB/token:** directly violates the owner constraint and confuses explanation
  with truth.
* **One giant weighted quality number:** permits latency or hook uptime to compensate for wrong
  outcomes.
* **Exact action-trace matching:** false-fails alternate valid trajectories.
* **Historical score from transcript volume:** lacks stable episodes and labels in the supplied
  corpus.
* **BUILD-LARGE benchmark service:** unjustified; append-only events, isolated runners, and a
  streaming scorer suffice for this metric.

Avoiding a new runtime is **almost certain (90-99%)** to reduce implementation surface relative to
a new service, because the necessary append, dedupe, state-root redirection, provider dispatch,
and executable tests already exist in the supplied harness. It does not establish that each small
component meets the line budget; the experiments under Proposals 2–5 settle that.

## Acceptance tests for the metric implementation

The metric is not “done” until these execute green from fresh temporary roots:

1. gold trajectory -> `PASS`, VCY `100` for a one-case manifest;
2. no-op -> `FAIL`, VCY `0`;
3. known-bad mutation -> `FAIL`, VCY `0`;
4. valid alternative trajectory -> `PASS`;
5. success prose with unchanged bad state -> `FAIL`, never `PASS`;
6. green test then mutation without rerun -> `FAIL` or `INVALID`, never `PASS`;
7. green baseline reproducer -> repair case `FAIL` because fail-before is missing;
8. baseline fail + candidate pass + regression fail -> `FAIL`;
9. all required checks pass plus minefield hit -> `FAIL`;
10. hook CLI returns zero but terminal records failed module -> task grade follows final state, and
    health sidecar is red;
11. delete `eval_result` -> `MISSING`, primary denominator unchanged;
12. corrupt grader hash -> `INVALID`, primary denominator unchanged;
13. duplicate identical result -> one deduped result; conflicting duplicate -> `INVALID`;

17. verbose and terse transcripts with identical evidence -> identical score;
18. three critical passes -> `CriticalPass^3=1`; any one fail/invalid/missing -> `0`;

## Gaps and limits

  specified correctness, not proof of all possible behavior.

## Final recommendation

Adopt VCY-v1 as the correctness metric and keep verification coverage, operational health,
reliability, and efficiency beside it rather than inside it. A case gets credit only for a valid,
independently executed, final-state-and-minefield proof on the first attempt. This makes quiet,
high-value verification score correctly; makes missing telemetry unable to improve the number; and
makes a lexical “ok,” a callback, a hash, or a large report incapable of masquerading as success.

The overall design choice is **very likely (80-90%)** to be the best fit for this harness because it
combines three independent signals: the local executable receipt/state spine, the locally
reproduced false-green, and frontier final-state/milestone benchmark practice. Its principal risk
is the benchmark oracle itself, which is why oracle admission is part of the metric rather than a
trailing caveat.
