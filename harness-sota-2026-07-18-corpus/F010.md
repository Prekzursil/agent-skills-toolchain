# F010 — Red-team: `mcp_agent_mail` local attack surface

Date of review: 2026-07-19 (Europe/Bucharest)  
Unit: F010  
Scope: defensive review of the owner's own `mcp_agent_mail` installation, configuration, scheduled supervisor, HTTP/MCP surface, data store, and local reachability.  
Subject root: `C:\Users\Prekzursil\.local\opt\mcp_agent_mail` at Git commit `35e774fa9ae636c6e1662ab7925d7e68938bb718` (`pyproject.toml:7` identifies package version `0.3.4`).

## Executive verdict

The socket is genuinely configured to bind only IPv4 loopback when the supervisor starts it, but “local-only” is not an adequate security boundary here. It is host-local, not caller-authenticated, and the installed controls deliberately turn localhost into a full writer. More importantly, sandbox principals can modify the executable supervisor/source/config and the datastore that the owner's scheduled task consumes.

The highest-risk verified weakness is therefore a sandbox-to-owner trust-boundary break, not LAN exposure:

1. The Windows group `DESKTOP-A60S9GP\CodexSandboxUsers` has `Modify` and `DeleteSubdirectoriesAndFiles` on the repository root, `.env`, `supervisor\agentmail_supervisor.ps1`, `storage.sqlite3`, and `store\`. `Get-LocalGroupMember CodexSandboxUsers` independently showed that the enabled `CodexSandboxOffline` and `CodexSandboxOnline` accounts are members.
2. The enabled `MCPAgentMailSupervisor` scheduled task executes that writable supervisor as `DESKTOP-A60S9GP\Prekzursil` at owner logon. The checked-in installer constructs exactly that task and action at `supervisor/install_service.ps1:59-80`; the live `Export-ScheduledTask` output independently showed `InteractiveToken` and the same script path.
3. Consequently, code executing as either sandbox account can persistently alter what later runs in the owner's non-sandboxed context. This control-flow claim is **VERIFIED statically and by live ACL/task inspection**; no payload was written and no execution was attempted.

The second critical cluster is unauthenticated authority while the server is up:

- The historical live startup output says `Environment development`, `Auth disabled`, and `Uvicorn running on http://127.0.0.1:8812` at `logs/agentmail_server.err.log:22,26,74`. The `.env` contains only host/port/path among the relevant HTTP settings (`.env:1-3`), so the code defaults apply: no bearer token, rate limiting off, JWT off, and localhost unauthenticated at `src/mcp_agent_mail/config.py:393-430`.
- The middleware skips RBAC for a localhost peer and elevates it to writer at `src/mcp_agent_mail/http.py:988-1018`. This is transport-level authorization by source address, not by client identity.
- A new name can be registered without an existing project credential, receives a freshly minted token, and binds the session (`src/mcp_agent_mail/app.py:5998-6024`; token generation at `:3640-3657`). A session-bound agent is accepted as project administrator (`:5249-5258`). Thus the registration token protects an existing agent identity but does not protect membership in, or administration of, an existing project.
- The unauthenticated Web UI exposes all-project inbox/project metadata and has state-changing endpoints (`src/mcp_agent_mail/http.py:2085-2135,2221-2315,2325-2350`). Its “overseer” endpoint creates or reuses a `HumanOverseer` identity, inserts a message, and prepends instructions stating that the human's guidance supersedes other priorities (`:3592-3617,3622-3745`). This is a concrete local prompt-injection/impersonation primitive whenever an agent consumes that mailbox.

At the exact audit instant the daemon was **not listening**, despite the “always-on” description. Two mechanically independent probes established this: `netstat -ano -p TCP` returned no `:8812` row, while `.NET IPGlobalProperties.GetActiveTcpListeners()` successfully found known-present listeners but none on 8812; separate bounded `TcpClient` connects to `127.0.0.1:8812` and `::1:8812` both failed. The live scheduled task was `Ready`, not `Running`, and `Get-ScheduledTaskInfo` returned `LastTaskResult=3221225786` (`0xC000013A`). Therefore no finding below claims that the endpoint was exploitable at the audit instant; findings describe the verified installed surface during its documented up periods.

### F010-1 — Critical: sandbox-writable scheduled-task code

**What is verified**

- Live `Get-Acl` output gave `DESKTOP-A60S9GP\CodexSandboxUsers` both `ReadAndExecute` and `Modify`/`DeleteSubdirectoriesAndFiles` on the application directory, `.env`, the exact scheduled supervisor script, the database, and the archive root.
- Live local-group enumeration showed two enabled sandbox users in that group: `CodexSandboxOffline` and `CodexSandboxOnline`.
- Live task export showed an owner-logon trigger and action `powershell.exe ... -ExecutionPolicy Bypass -File "...\supervisor\agentmail_supervisor.ps1"`, using the owner's interactive token. The source installer corroborates the path, trigger, principal, and registration at `supervisor/install_service.ps1:59-80`.
- The supervisor launches repository-controlled Python with `-m mcp_agent_mail.cli` at `supervisor/agentmail_supervisor.ps1:152-154`. Both the script and module tree are within the sandbox-modifiable directory.

**Security consequence**

A compromised or prompt-injected sandboxed agent does not need to defeat HTTP authentication. It can modify code or launch configuration that the owner task later executes. Run level `Limited` avoids an administrative UAC token, but it does not preserve the intended Codex filesystem/process sandbox: the process runs as the owner account and inherits the owner's ordinary file and credential reach.

The persistence/execution consequence is **almost certain (90-99%)**, because the writable action target and owner-logon trigger are both directly verified; the remaining uncertainty is only whether the owner logs on or manually starts the task after tampering. A safe experiment that would settle the final 1–10% is to point a cloned task at a canary script in an isolated test account, alter only the canary as a sandbox user, and verify the resulting identity—never use the production task for this test.

### F010-2 — Critical: unauthenticated `HumanOverseer` impersonation

**What is verified**

- HTTP auth was disabled in the recorded live startup (`logs/agentmail_server.err.log:26`), and the relevant `.env` has no bearer/JWT/localhost-bypass override (`.env:1-3`; defaults at `src/mcp_agent_mail/config.py:393-430`).
- Localhost bypass explicitly skips the security check (`src/mcp_agent_mail/http.py:723-733`) and RBAC (`:988-1018`).
- `POST /mail/{project}/overseer/send` accepts recipients, subject, body, and thread from request JSON with no agent token or CSRF field (`src/mcp_agent_mail/http.py:3592-3617`).
- It prepends an authoritative-looking block saying the message is from a human operator and “supersedes all other priorities” (`:3622-3639`), creates/reuses `HumanOverseer` (`:3658-3735`), and inserts the message (`:3737-3745`).

**Security consequence**

Any process that can connect locally while the service is up can plant instructions that the product itself labels as owner guidance. This bypasses per-agent registration-token checks entirely because it is a separate Web UI route.

It is **likely (55-80%)** that an active agent which is instructed to poll Agent Mail would treat such a message as high authority, because the server supplies the explicit priority preamble and both Claude and Codex are currently mounted (`C:\Users\Prekzursil\.claude.json:1997-2000`; `C:\Users\Prekzursil\.codex\config.toml:632-634`). It is not “almost certain” because the corpus records only three Agent Mail capability uses (`corpus/corpus.json:13448`) and no live consumer was invoked in this defensive test. A fixed benign canary message to a disposable agent, followed by an inbox poll with action execution disabled, would settle actual consumer behavior.

### F010-3 — Critical: self-registration defeats project administration boundaries

**Verified control flow**

1. `register_agent` accepts an arbitrary new name and optional `registration_token` (`src/mcp_agent_mail/app.py:5897-5908`).
2. It authenticates only when that name already exists (`:5998-6008`).
3. For a new name it creates the agent, mints a 32-byte URL-safe token, returns it, and binds the MCP session (`:6009-6024`; token creation `:3640-3657`).
4. `_authenticate_project_admin` accepts any session-bound agent without a separate administrator role or capability (`:5249-5258`).
5. Project archive/unarchive and hard-delete call that project-admin helper (`:6156-6213,6396-6432`). Hard delete physically removes the database records and archive after only a literal confirmation string (`:6396-6428` and subsequent deletion body).

The control flow is **VERIFIED**. The irreversible final call was not made. This is an authorization-design flaw: a random registration token proves possession of a newly created identity, while the code incorrectly treats that as authorization over the pre-existing project.

The impact is **almost certain (90-99%)** if the service is reachable and an attacker knows or learns a project key, because all state transitions are explicit in the cited code. The small uncertainty covers hidden runtime defects and database state. A safe experiment is to create a completely isolated temporary database/archive, pre-create a dummy project, self-register a new identity, and assert that a non-destructive `archive_project` call succeeds; production data must not be used.

### F010-4 — High: direct datastore confidentiality and integrity bypass

The same live ACL probe that established F010-1 grants sandbox users Modify rights over `storage.sqlite3` and `store\`. The archive currently contains project/message artifacts, while recorded startup statistics reported six projects, fifteen agents, and fourteen messages (`logs/agentmail_server.err.log:31-43`). The database and Git archive are therefore not protected from the sandbox principals that HTTP-level tokens are supposed to constrain.

Consequences are direct mail disclosure, message alteration, token/database manipulation, reservation tampering, and destruction, all without using MCP. Integrity and confidentiality loss are **almost certain (90-99%)** for any code already running as one of the two sandbox users, because filesystem authorization itself grants the access; a non-destructive `icacls` effective-access check executed under a disposable sandbox token would settle any token-deny nuance without opening mail content.

### F010-5 — High: unauthenticated Web UI exposes and mutates all-project data

This exposure also supplies the identifiers needed for subsequent project-level actions. The claim is **VERIFIED statically** and corroborated by the startup record showing auth disabled. No mailbox content was fetched during this unit.

### F010-6 — High, UNVERIFIED: browser DNS rebinding may cross the “local-only” boundary

The source contains no `TrustedHostMiddleware`, allowed-host check, CSRF token, or Origin/Referer enforcement in the live HTTP application. This absence used two signals: (1) an exact source search for `TrustedHostMiddleware|allowed_hosts|csrf|Origin|Referer` returned no live-app control while the same detector found known-present Origin test fixtures; (2) the inspected middleware stack at `src/mcp_agent_mail/http.py:1534-1565` contains request logging, security/rate limiting, optional bearer, and CORS only. CORS is enabled by default in development but has an empty origin list (`src/mcp_agent_mail/config.py:453-458`); CORS alone does not validate Host or authenticate same-origin traffic after DNS resolution.

The MCP project's own current security guidance identifies insecure localhost servers reachable via DNS rebinding as a local-server compromise risk: [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices). OWASP's Host-header testing guidance likewise begins by sending a non-canonical Host and checking whether it is accepted: [OWASP WSTG Host Header Injection](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/17-Testing_for_Host_Header_Injection).

The end-to-end browser exploitability is **UNVERIFIED — experiment to settle it: run the server against a disposable datastore, use an owned test domain whose DNS is switched to `127.0.0.1`, and verify in each installed browser whether Private Network Access/preflight policy blocks a harmless GET and harmless canary POST**. Until that test, the claim that an arbitrary website can reach the route is only **likely (55-80%)**, based on the missing Host/Origin controls and the upstream MCP threat model; browser-version and Private Network Access behavior are the major uncertainty.

This finding does not include exploit code. It is important because a successful browser route would remove the “attacker already has local process execution” precondition from F010-2/F010-5.

### F010-7 — Medium: no rate limit on a demonstrably fragile service

The supervisor log records repeated health failures, recycle attempts, and long failure streaks; the final observed recovery was at `logs/agentmail_supervisor.log:369-372`. Request throttling is **very likely (80-90%)** to reduce trivial accidental or hostile request floods because the existing middleware already implements per-kind token buckets (`src/mcp_agent_mail/http.py:1020-1028`); it is not claimed to fix the underlying server instability. A bounded load test against a disposable datastore comparing p95 latency, error rate, and recovery time with the flag off/on would settle the effect.

## What the service can do

The installed source exposes 48 MCP tools (mechanically extracted from `@mcp.tool(name=...)` decorators). The material authority groups are:

- Project/identity lifecycle: ensure projects; register, deregister, retire, unretire, and hard-delete agents; archive, unarchive, and hard-delete projects (`src/mcp_agent_mail/app.py:5789-6432`).
- Messaging: send, reply, search, summarize, fetch, acknowledge, and purge messages (`:6975-11077`). Sender calls have agent-token checks, but the unauthenticated Web UI bypasses that model.
- Coordination: contact policy/handshakes, file reservations including forced release, and build-slot lifecycle (`:8851-12145`).
- Repository mutation: install or uninstall pre-commit guards at a caller-supplied resolved repository path (`:11079-11132`). This path is currently gated by `WORKTREES_ENABLED`; the installed `.env` has no enabling entry, so the default makes install a no-op. If enabled later, it becomes another reason HTTP authorization must be mandatory.
- Product-wide linking/search/inbox/summarization (`:12226-12607`).
- Web administration: all-project inbox/search, archive browsing/download, message deletion, agent/project lifecycle, marking read, and overseer composition (`src/mcp_agent_mail/http.py:2085-4147`).

Two potential primitives were checked and are **not current findings**:

- Absolute attachment paths are disabled by default (`src/mcp_agent_mail/config.py:441-450`), and attachment processing rejects them when disabled (`src/mcp_agent_mail/storage.py:1808-1819`). The installed `.env` does not override this. Therefore this unit found no current arbitrary owner-filesystem read through attachments.
- The canonical supervisor binds `127.0.0.1`, not `0.0.0.0` (`supervisor/agentmail_supervisor.ps1:152-154`; `logs/agentmail_server.err.log:74`). Therefore this unit found no current direct LAN listener. This conclusion has two independent signals, not merely configuration text.

## Remediation, ordered

### R1 — Remove sandbox write access from executable/config/task paths

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** This is Windows ACL/task configuration, not a new runtime.

Remove `CodexSandboxUsers` Modify/Delete rights from the repository code, `.venv`, `.env`, and `supervisor\`; allow owner/SYSTEM read/execute as appropriate. Move mutable database/archive/logs to a separate directory with the narrowest needed ACL, and do not let a sandbox principal modify the code or configuration that an owner-context scheduled task executes. Prefer running the daemon under a dedicated non-admin service identity that owns only its data directory; clients should use MCP, not direct files.

This will **almost certainly (90-99%)** close the verified persistence/control-flow path because the path exists solely through the live ACL plus owner-executed action. Verify with two signals: `Get-Acl`/`icacls` effective access for both sandbox users, then a canary write-denial test on a non-production file under the protected code directory. Confirm the service can still read code and write only its data/log directories.

### R2 — Require transport authentication even on localhost

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** The implementation already has bearer/JWT middleware and both clients already support HTTP MCP configuration.

Set a strong bearer or audience-bound JWT, set `HTTP_ALLOW_LOCALHOST_UNAUTHENTICATED=false`, and require authentication for `/mcp` **and every `/mail` read/write route**. Do not hardcode the secret in tracked config; inject it from an environment variable or OS credential store and validate presence on startup. Split read/write/admin scopes; do not treat a generic authenticated token as administrator.

The current MCP authorization specification says protected HTTP servers must validate access tokens before processing and return no data to unauthorized parties: [MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization). This change is **very likely (80-90%)** to block untrusted local processes that cannot read the credential, based on the existing tested middleware (`tests/test_http_auth.py:50-205`) and explicit bypass control. It will not protect against sandbox users until R1 removes their ability to read/alter `.env` and the database.

### R3 — Close open membership and create a real project-admin capability

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the current registration-token checks; do not add another identity service.

Allow unauthenticated creation only for a brand-new project, and require an invite/project-admin capability to add a new identity to an existing project. Mint a distinct admin token or admin role at project creation; do not define “any session-bound agent” as administrator. Gate archive/unarchive, hard delete, retention purge, product linking, Web UI lifecycle actions, guard installation, and overseer sends by explicit capabilities. Disable irreversible tools by default and require a server-side policy flag in addition to a confirmation phrase.

This is **very likely (80-90%)** to break the verified self-registration-to-admin chain because its exact weak link is `app.py:5249-5258`. A disposable-database authorization matrix—anonymous, new member, existing member, admin—covering every mutating tool/route would settle completeness.

### R4 — Authenticate and de-weaponize the `HumanOverseer` route

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Reuse the transport/admin identity from R2/R3.

Require an owner/admin capability, log the authenticated subject, and cryptographically or structurally label owner-authored messages so agents can distinguish them from ordinary mail. Remove the unconditional prose claiming that mailbox content supersedes higher-level instructions; an MCP message must never elevate itself above system/developer policy. Add a client-side rule that mail is untrusted data unless a verified owner signature/capability is present.

This will **very likely (80-90%)** eliminate the verified impersonation primitive because the current route has no identity input and manufactures authority at `http.py:3622-3739`. A disposable canary test should assert 401/403 for anonymous and ordinary-agent callers and success only for the owner/admin principal.

### R5 — Add loopback Web hardening; browser premise remains UNVERIFIED

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing HTTP middleware bus).**

Allowlist only canonical Host values (`127.0.0.1:8812`, `[::1]:8812` if IPv6 is intentionally enabled, and an explicitly chosen localhost name), reject all other Hosts before routing, enforce an exact Origin allowlist for browser API calls, add CSRF tokens or same-site double-submit protection for state changes, and disable CORS unless a named UI origin needs it. Keep this even after bearer auth as defense in depth.

The recommendation inherits the **UNVERIFIED** browser premise—settle it with the disposable DNS-rebinding/PNA experiment in F010-6—but Host/Origin validation is independently supported by the MCP local-server threat model. It is **very likely (80-90%)** to block classic DNS-rebinding access when correctly configured; browser-specific PNA behavior remains outside the server's control.

### R6 — Prefer per-client stdio if shared always-on HTTP is not essential

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Both installed clients already demonstrate stdio MCP configuration (`C:\Users\Prekzursil\.claude.json:1685-1704`; `C:\Users\Prekzursil\.codex\config.toml:136-137,496-528`); no new orchestration runtime is proposed.

If the measured three Agent Mail uses do not justify a shared HTTP daemon, replace the always-on listener with on-demand stdio processes or retire the integration. Stdio removes host-wide TCP and browser reachability, but only if concurrent instances can safely share SQLite/archive state. That concurrency premise is **UNVERIFIED — experiment to settle it: run two authenticated stdio clients against a disposable shared datastore and measure locking, delivery consistency, and shutdown behavior**. Therefore full stdio replacement is only **roughly even (45-55%)** as the best operational choice today; authentication and ACL repair remain mandatory regardless.

This proposal passes the anti-overfit gate: it removes a runtime and rides native MCP transport. It does not introduce a second orchestrator, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### R7 — Enable bounded rate limiting and fail closed on missing auth

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** The token-bucket middleware already exists.

Enable separate tool/resource limits with conservative bursts, and make startup fail if an HTTP listener is configured without bearer/JWT auth or if localhost bypass is enabled outside an explicit disposable-development mode. Keep health endpoints minimal and unauthenticated only if required by the supervisor.

This is **very likely (80-90%)** to reduce trivial request floods and configuration regression, based on the existing limiter branch at `http.py:1020-1028` and strict parsing in `config.py:297-318`. It is **unlikely (20-45%)** to cure the existing health/recycle failures by itself; only a controlled load/recovery experiment can attribute those failures.

### R8 — Make supervision state observable without adding a platform

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing scheduled-task/log bus).**

Have the existing supervisor emit a terminal `SUCCESS:<id>`/`FAILED:<id> reason`, rotate its stale PID atomically, and expose a bounded status command that compares task state, actual listener PID, PID file, and health. Alert locally after the restart budget is exhausted. Do not add an observability SaaS or durable-execution engine.

This is **very likely (80-90%)** to prevent the present “task Ready + stale PID + no listener” state from being misreported as always-on, because those are exactly the four independently observable fields. It improves detection, not confidentiality or authorization, and must follow R1–R5.

## Recommended acceptance gates

1. ACL gate: both sandbox users are denied write/delete on executable/config/task paths; the dedicated service identity can write only data/log locations.
2. Network gate: when healthy, listeners show only the intended loopback address; LAN probes fail; sandbox/other-user/browser probes receive 401/403 without credentials.
3. Authentication gate: anonymous `initialize`, `tools/list`, all `/mail` pages/APIs, and all mutations return 401/403 except minimal health endpoints.
4. Authorization matrix: anonymous/new member/member/admin are tested for every mutating MCP tool and Web route; self-registration to an existing project fails without invite/admin authority.
5. Overseer gate: only a verified owner/admin principal can create owner-labeled mail; arbitrary mail cannot claim higher instruction priority.
6. Browser gate: noncanonical Host is rejected; non-allowlisted Origin is rejected; CSRF canary fails; disposable DNS-rebinding test fails in every installed browser.
7. Destructive-tool gate: irreversible tools are disabled by default and require both explicit server policy and admin authorization; tests run only on disposable state.
8. Reliability gate: task Running/listener/PID/health agree after logon, after a forced harmless child crash, and after the configured restart budget is exhausted.

Each proposed gate is **very likely (80-90%)** to detect regression in its named control because it asserts the security boundary directly rather than inferring it from configuration. The remaining uncertainty is integration behavior across the installed Claude/Codex client versions; the full two-client canary suite settles that.
