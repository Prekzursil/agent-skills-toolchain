# T024 — Competitive teardown: Sourcegraph Amp

**Research date:** 2026-07-19 UTC  
**Subject:** Amp (the coding agent originally launched by Sourcegraph; current product documentation is at `ampcode.com`)  
**Unit scope:** agent loop, context management, memory, tools/MCP, permissions, customization, multi-agent operation, and verification/self-checking. This is a competitive teardown, not an installation recommendation.

## Executive judgment

Amp's most transferable advantage is not a larger orchestration system. It is a small set of context-economy mechanisms that ride the agent's existing buses:

1. skill bodies are loaded only after selection, while only name and description are continuously visible;
2. a skill can own an MCP server and keep that server's tools hidden until the skill is loaded;
3. repository guidance is included progressively by subtree and file globs;
4. old threads are durable, searchable work records, but a dedicated retrieval subagent extracts only task-relevant evidence and checks whether later work superseded an earlier result;
5. review criteria are plain Markdown, path-scoped, and fanned out one check per read-only review subagent;
6. the plugin event bus can modify or synthesize tool outcomes and can append a guarded continuation after an agent tries to stop.

Those mechanisms attack failures measured in our corpus: a dead Tavily MCP was still called 532 times with 25.8% errors; only 78 of roughly 355 installed skills were invoked; StructuredOutput failed 22.9%; and thousands of globally accumulated plugin directories caused `ENAMETOOLONG`. Amp's answer is selective exposure and aggressive deletion of obsolete surfaces, not another coordinator.

**Recommendation:** selectively port the context and review primitives; do not replace our harness with Amp wholesale. This is **very likely (80-90%)** to improve reliability per unit complexity because the ports below are configuration or small hooks on buses we already operate, while Amp's weaker default permission posture and isolated subagents would discard capabilities we already have. Evidence: Amp's selective skill/MCP loading is documented in the [Owner's Manual](https://ampcode.com/manual); our global MCP allowlist and bypass mode are visible at `/local_disk0/codexwork/bundle/claude/settings.json:26-75`; our native team feature flags are enabled at that file's lines 5-7; and our shared harness already registers tool, compaction, subagent, and team lifecycle events at `/local_disk0/codexwork/bundle/agents/harness/registration.py:17-53`.

The strongest radical option—full Amp replacement—is **unlikely (20-45%)** to be better for this owner. Evidence: Amp offers cleaner selective context, searchable threads, and a polished plugin API, but its documented built-in subagents cannot communicate or be guided mid-task, and by default it runs tools without approval. The owner uses cross-provider agents, experimental agent teams, numerous domain-specific MCPs, and custom pre/post-tool guards. A replacement trial could change this probability; the settling experiment is the controlled bake-off specified in §11, not an immediate migration.

## 2. Agent loop

### 2.1 What Amp concretely does

Amp defines an agent as a model plus system prompt plus tools. A thread contains the user messages, model responses, tool calls, tool inputs, and results. The client sends prompt and accumulated context to Amp Server/model inference; when the model requests a tool, the client executes it and returns the result for the next inference step. This is the familiar model → tool → observation loop, not a separate planner/executor runtime. See [Context Management in Amp](https://ampcode.com/guides/context-management) and the interaction description in the [Security Reference](https://ampcode.com/security).

The loop has four current capability/cost modes—`low`, `medium`, `high`, `ultra`—rather than exposing a stable model taxonomy. As of 2026-07-09, Amp maps those tiers to different models/reasoning effort and assigns every tier an Oracle; the mapping is explicitly expected to change while the tier semantics remain stable. See [The Dial](https://ampcode.com/news/the-dial). This separates the user's decision (“how hard/costly is this?”) from model churn.

Plugins observe a lifecycle:

`session.start → agent.start → (tool.call → tool.result)* → agent.end`

At `tool.call`, a plugin can allow, reject-and-continue, modify arguments, or synthesize a result without executing. At `tool.result`, it can replace the status/output before the model sees it. At `agent.start`, it can append context. At `agent.end`, it can append a user message and continue, provided the plugin uses a marker to prevent infinite loops. See the [Owner's Manual plugin event examples](https://ampcode.com/manual) and [Plugin API](https://ampcode.com/manual/plugin-api).

This event model is unusually useful because it makes enforcement and recovery transformations first-class rather than forcing every policy helper to communicate via unstructured stdout. Its documented warning is also important: execute mode can begin before plugins are ready unless `--plugin-ready-timeout` is used, in which case lifecycle events can be skipped. That is an Amp defect surface, not a feature to copy.

### 2.2 Comparison

Our harness already has a richer named native lifecycle than Amp's five public plugin stages, including failure, permission, compaction, subagent, task, and teammate events (`registration.py:17-53`). Amp is better at the *typed response contract* for `tool.call`/`tool.result`: modification and synthesis are explicit return variants. Our defect D1 shows several guards pattern-match prose or field names rather than semantic tool/result fields, causing false blocks and even false “FAILED” observations (`INPUT-known-harness-defects.md:9-87`).

### 2.3 Port

#### Typed tool intervention contract — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Normalize each pre/post-tool module response to one of `allow`, `reject_continue(message)`, `modify(input)`, `synthesize(status, output)`, or `observe`. Validate the discriminated union in the shared dispatcher; reject ambiguous free text. Carry structured tool name, target, arguments, status, and output separately. This ports Amp's mechanism without its runtime.

This is **very likely (80-90%)** to reduce false interpretations because Amp's contract preserves semantic fields and our confirmed D1 failures arose from treating payload prose or a JSON key as execution/result truth. Evidence: known defects lines 9-87; current dispatcher registration already intercepts pre/post events at `registration.py:17-53`. The remaining uncertainty is whether every Claude/Codex hook payload exposes enough structured fields. **UNVERIFIED — experiment:** capture one sanitized native payload for Bash, Write-to-Markdown, successful MCP JSON containing `false`, and failed MCP; map available fields before implementation.

#### Capability dial routing — CONFIG

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Present four stable task tiers in the harness rules/router: low = precisely specified/local; medium = normal default; high = subtle cross-cutting/high miss cost; ultra = broad unknown-path research/migration. Map tiers to currently installed Claude/Codex models and reasoning settings behind one table; do not expose vendor model names in task templates.

This is **likely (55-80%)** to reduce model-route churn because Amp's stable semantic dial directly addresses under/over-spending, and our settings already define a primary and fallback model (`settings.json:77-80`). The settling experiment is an A/B replay of 100 stratified historical tasks comparing current routing with tier routing on completion, retries, wall time, and token cost. Do not accept Amp's model mapping as evidence for ours.

## 3. Context management

### 3.1 Current mechanisms

Amp's context model is deliberately legible: the visible thread is roughly the context window, plus system prompt, tool definitions, `AGENTS.md`, and environment data. Tool calls and outputs consume context like any other text. Amp's guide explicitly warns that more context generally worsens results. Files mentioned with `@` are truncated at 500 lines and 2 KB per line; the agent can read more if needed. See [Context Management in Amp](https://ampcode.com/guides/context-management).

Four progressive-disclosure layers matter:

1. **Hierarchical guidance.** Amp always includes `AGENTS.md` in cwd/workspace roots and parents up to home, plus system/user guidance. A subtree `AGENTS.md` is included only after the agent reads a file in that subtree. It falls back to `AGENT.md` or `CLAUDE.md` where appropriate.
2. **Conditional referenced guidance.** `AGENTS.md` can reference other files and globs. Referenced Markdown can carry YAML `globs`; it is included only after Amp reads a matching file. The manual's example activates TypeScript conventions only after a `.ts`/`.tsx` file is read.
3. **Lazy skill bodies.** Skill name and description are always visible for routing; the rest of `SKILL.md` and bundled resources load only when invoked.
4. **Lazy tool definitions.** MCP tools bundled with a skill stay hidden until that skill loads, reducing system-prompt tool bloat.

Amp currently auto-compacts long threads. The most concrete evidence is [Read Bigger Threads](https://ampcode.com/news/read-bigger-threads): Amp reports a thread compacted more than 68 times and an uncompacted equivalent exceeding 21 million tokens. This is vendor-reported operational evidence, not independently reproduced.

The chronology is instructive. Amp first judged summary compaction too lossy and replaced it with goal-directed Handoff ([Handoff](https://ampcode.com/news/handoff)); later Neo restored compaction and removed Handoff as unnecessary complexity ([Neo](https://ampcode.com/news/neo)). The transferable lesson is not “compaction good” or “handoff good”; it is to measure context mechanisms against current models and delete obsolete scaffolding.

### 3.2 Where Amp is better

Our harness has `skillListingBudgetFraction=0.02` and `ENABLE_TOOL_SEARCH=auto:5` (`settings.json:1-20`), so it already attempts bounded discovery. But our canonical MCP design broadly promotes/synchronizes servers: source comments describe canonical `~/.mcp.json` propagation in `/local_disk0/codexwork/bundle/claude/hooks/mcp-canonical-sync/sync.py:1-11`, while the settings allowlist names many MCP families at lines 47-60. The measured dead Tavily calls and plugin-directory command-line inflation show that discovery alone has not supplied lifecycle hygiene.

Amp's skill-owned, hidden-until-selected MCP is a capability not shown in our snapshot by two independent signals described in §1.2. **UNVERIFIED whether current Claude Code natively honors `mcp.json` inside a skill directory — experiment:** create a disposable skill with a one-tool no-op MCP on the Windows box, restart, inspect tool search before and after skill load, then delete the fixture. Until that test, the proposal inherits UNVERIFIED status.

### 3.3 Ports

#### UNVERIFIED: Skill-scoped MCP exposure — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add optional `mcp.json` to a skill; index only server/tool metadata; expose tool definitions only after skill selection; support `includeTools` globs; unload/hide after the turn or task. If the native experiment passes, most of this BUILD-SMALL allowance collapses to configuration and fixture tests; otherwise the implementation is a SessionStart index plus Skill-selection activation table, not a new MCP broker.

This is **very likely (80-90%)** to reduce irrelevant tool exposure and dead-server calls because Amp documents the exact context-bloat rationale, our corpus contains 135 “not connected” Tavily failures, and only 78/~355 skills were invoked. It will not by itself fix servers that are dead *after* selection; pair it with health/circuit breaking from the neighboring reliability work.

#### Conditional rule loading — CONFIG

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Convert broad language rule packs into referenced files with path/language globs, using the host's native path-scoped rules if available. Keep a short global safety core. Activate domain rules only once a matching file or tool is touched.

This is **very likely (80-90%)** to improve context precision because Amp's mechanism is deterministic, the bundle contains multiple language-specific rule trees, and model-visible irrelevant guidance consumes context. Evidence: `/local_disk0/codexwork/bundle/claude/rules/{java,dart,cpp,php,swift,kotlin,golang}/`; Amp manual's granular guidance section. **UNVERIFIED host parity — experiment:** known-positive prompt in a fixture with nested guidance, inspect injected context before and after reading a matching file.

#### Context ledger visible to the operator — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At SessionStart and after skill/tool activation, emit a compact manifest: global guidance files, conditional guidance now active, skill bodies loaded, MCP tool families exposed, and approximate token cost. Do not log content or secrets.

This is **likely (55-80%)** to catch context pollution because Amp exposes an `agents-md list` command and its design makes inclusion inspectable, while our corpus demonstrates low capability use amid a large installed surface. The settling experiment is whether operators can correctly identify seeded irrelevant-context faults faster with the manifest than without it.

## 4. Memory and durable work context

### 4.1 What Amp calls memory

Amp does not advertise an autonomous vector-memory or knowledge-graph subsystem. Its durable memory is mostly explicit, inspectable artifacts:

- threads retain messages, responses, tool calls/results, attachments, and partial code context;
- threads can be searched by words plus filters such as file, project, repository, ref, author, date, label, and archive state;
- another thread can be referenced by ID/URL;
- `read_thread` receives a question and retrieves only relevant information;
- the July 2026 implementation is a retrieval subagent that searches a large/compacted thread, reads candidate messages, checks for later revisions/reverts/contradictions, treats tool calls as attempts rather than outcomes, uses compaction only for orientation, and inspects original messages for exact facts.

See the [Owner's Manual thread sections](https://ampcode.com/manual) and [Read Bigger Threads](https://ampcode.com/news/read-bigger-threads).

That last mechanism is the standout. It directly encodes two epistemic rules our known defects demand: do not trust the first plausible hit, and do not treat an attempted action as a successful outcome.

Amp threads are also team-visible by default inside a workspace unless visibility is changed; workspace admins can see private threads. Thread visibility can be unlisted, workspace, group, or private. The [Security Reference](https://ampcode.com/security) says stored thread data includes prompts, model responses, code snippets/files in context, tool results, and attachments, and documents retention/security controls. This makes thread memory collaborative but also increases governance and privacy burden.

### 4.2 Comparison

Our explicit `/save-session` creates a new flat file and `/resume-session` reads the entire file before briefing (`resume-session.md:26-87`; `save-session.md:268-275`). Basic Memory is allowlisted (`settings.json:47`), but the corpus says hook telemetry is absent from transcripts and the root cause is unverified (`INPUT-known-harness-defects.md:133-147`). Our supplied snapshot/corpus show no `read_thread` equivalent by the two-signal test in §1.2.

Amp is better at task-directed retrieval from an audit trail and at checking temporal supersession. Our manual session file is better in one respect: it is local, directly inspectable, owner-controlled, and does not implicitly expose all work to a hosted workspace.

### 4.3 Port

#### Task-directed session retrieval — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing session store, not a new database. Store an append-only JSONL/Markdown event index keyed by session, timestamp, repo, branch, file paths, tool status, and message offsets. A `read_session(question, session?)` skill/tool should: search metadata/text; read candidate original spans; scan later spans for supersession/revert; require a successful result before reporting a tool action as done; return citations to session/message offsets. Compaction summaries may orient search but cannot substantiate exact claims.

This is **likely (55-80%)** to improve cross-session correctness because it ports the exact safeguards Amp added after its first retrieval version stopped at the first plausible hit, and our current resume command consumes a whole summary file. The uncertainty is whether local transcript formats offer stable offsets and complete tool outcomes. **UNVERIFIED — experiment:** index 20 historical sessions with known later reversions; measure exact-answer accuracy against full-file resume and a first-hit baseline.

This proposal intentionally avoids a vector DB/KG memory, one of the rejected components. Start with SQLite FTS5 or even `rg` over JSONL only if already available in the runtime; if SQLite would constitute a new durable service, use file indexes. No daemon is justified.

#### Do not copy hosted-by-default workspace memory — no proposal

Amp's collaborative thread feed is worse for this owner's privacy/control unless consciously opted in. Amp documents that workspace threads are generally shared and workspace admins can see private threads. We should keep local/private by default and export a selected, redacted thread artifact explicitly. No new component is needed.

## 5. Tools and MCP handling

### 5.1 Amp's surface

Amp has built-in tools, shell access, plugin-registered tools, MCP, and specialist subagent tools. `amp tools list` enumerates built-ins. Plugins register a tool with name, description, JSON input schema, and execute function. MCP can be local (`command`, `args`, `env`) or remote (`url`, `headers`), with OAuth support.

Important controls from the [Owner's Manual](https://ampcode.com/manual):

- `includeTools` accepts tool names/globs and is recommended;
- skill-scoped MCP is preferred over globally configured MCP;
- loading precedence is CLI flags, then user/workspace config, then skills;
- workspace `.amp/settings.json` MCP servers require explicit approval; global config and CLI MCP do not;
- `amp mcp doctor` reports approval state;
- the manual warns that too many tools reduce model performance;
- tools can be disabled by exact name or glob;
- remote OAuth tokens are refreshed and stored under `~/.amp/oauth/`.

Specialist tools include Oracle for a different-model second opinion, Librarian for public/private GitHub cross-repository search, Painter for image generation/editing, and the review agent. Librarian needs a configured GitHub connection; see [The Librarian](https://ampcode.com/news/librarian).

### 5.2 Better and worse

Better than ours:

- coherent precedence and per-project MCP trust;
- explicit `includeTools` filtering;
- lazy skill ownership of MCP tools;
- one diagnostic surface (`mcp doctor`);
- a code-search subagent that gives the main agent a compact answer rather than exposing a large search API surface.

Worse than ours:

- globally configured or CLI-provided MCP does not require approval, so a compromised user config remains powerful;
- servers start when Amp launches even when skill tools remain hidden, so lazy visibility is not lazy process startup;
- the public docs do not describe automatic circuit breaking after repeated connection failures. **UNVERIFIED absence — experiment:** configure a disposable MCP that always refuses connections, invoke it repeatedly, and inspect whether Amp quarantines it. Until tested, do not claim Amp lacks a breaker.

### 5.3 Ports

#### MCP admission manifest and doctor — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Define per server: scope, origin, command/URL fingerprint, allowed tool globs, auth type, last health, failure count, and activation owner skill. Require explicit trust for repository-supplied MCP. Add a read-only doctor that validates configuration, command resolution with PowerShell `Get-Command`, endpoint reachability, and tool count without starting every heavy server.

This is **very likely (80-90%)** to prevent recurring dead-server use because the corpus records 135 Tavily “not connected” failures and our current design broadly synchronizes canonical MCP configuration. Keep it a CLI/hook view over existing config; do not build a broker daemon.

#### Cross-repository search specialist — CONFIG

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Route cross-repo/library-source questions through one existing search skill/MCP with a compact contract: query, repositories/scope, cited files/commits, answer. Hide low-level search tools behind the skill. Prefer existing Sourcegraph/DeepWiki/GitHub facilities already configured rather than adding Librarian as another provider.

This is **likely (55-80%)** to reduce context and tool-choice errors because Amp's Librarian demonstrates the specialist pattern and our allowlist already includes DeepWiki and GitHub (`settings.json:49-53`). The settling experiment is a 30-question cross-repo benchmark comparing current free selection with the routed specialist on citation correctness, calls, tokens, and failures.

## 6. Permission and security model

### 6.1 Amp's behavior

Amp states plainly: by default, it does not ask for approval before running tools. The manual warns that repositories, MCP servers, and external inputs can influence actions and suggests isolated environments or a custom policy plugin.

Configured permissions are granular. The first matching rule for a tool plus argument conditions can `allow`, `reject`, `ask`, or `delegate` the decision to an external command. SDK rules can be scoped to the main thread or subagent. MCP server permissions separately allow/reject servers by URL or command/args. Repository MCP configuration requires initial trust approval. See [Tool-Level Permissions](https://ampcode.com/news/tool-level-permissions), [SDK permissions](https://ampcode.com/manual/sdk/typescript), and the [Owner's Manual](https://ampcode.com/manual).

Plugins can implement richer policy: the official example extracts a shell command from a tool call, uses deterministic safe patterns, then asks a small AI classifier whether an unrecognized git command is destructive and prompts the user. AI policy is a fallback, not the only gate.

The [Security Reference](https://ampcode.com/security) describes automatic secret redaction before content reaches the LLM/cache/server, thread audit trails, provider-mediated web prompt-injection defenses, enterprise zero-data-retention for inference, SSO, and retention controls. These are vendor claims, not tested by this unit.

### 6.2 Comparison and warning

Amp's permission rule language is better than our current broad string allowlist because it matches structured arguments and includes external delegation. But Amp's no-prompt default is not safer than ours—and ours is already risky: `defaultMode` is `bypassPermissions`, `ask` is empty, `additionalDirectories` includes entire `C:` and `D:`, and most tools/MCPs are allowed (`settings.json:26-75`). Copying Amp's default would cement that exposure.

Our hook suite has more domain-specific invariants, but confirmed defects show string/prose matching can corrupt decisions. Amp's sample AI classifier also has a potential false-positive/false-negative surface; it is acceptable only behind deterministic parsing and a user confirmation, not as an autonomous allow decision.

### 6.3 Port

#### Structured permission rules with external delegation — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Compile a small ordered rule list over structured tool, argument fields, path scope, repository trust, and agent context. Actions: allow, reject-and-continue, ask, delegate to existing policy helper. Default repository-origin MCP to ask; default destructive or external side effects to ask; keep common read-only local operations allowed. Log rule ID and semantic fields, not secrets.

This is **very likely (80-90%)** to reduce D1-class false blocks while improving blast-radius control because the defect is confirmed across multiple text scanners and the current bypass setting is concrete. **UNVERIFIED native matcher expressiveness — experiment:** run fixtures for a Markdown body mentioning `Remove-Item`, an actual destructive command, a JSON field named `timedout` with false value, and a true failed result through native permission hooks before choosing CONFIG versus the BUILD-SMALL adapter.

#### Automatic secret redaction at the transport boundary — UNVERIFIED, BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** If the hosts do not already redact secrets before persistence/transmission, add a lowest-common transport adapter that redacts known token formats and values loaded from credential stores before event logging or external MCP/model calls. Preserve a keyed digest for correlation, never the secret.

This is **likely (55-80%)** to reduce leakage if the premise is true; Amp explicitly places redaction below thread storage and model transmission, whereas our visible deny rules only prevent reads of a few filename patterns. **UNVERIFIED premise — experiment:** on an isolated account, inject synthetic canary-shaped secrets through tool output, file read, and MCP result; inspect local transcript, event ledger, and outbound debug capture. Do not implement until native behavior is known.

## 7. Customization: rules, skills, hooks, plugins, agents

Amp's customization stack has unusually clear separation:

- `AGENTS.md`: durable repository/user/organization guidance;
- skills: task-specific instructions and resources, selected by model-visible metadata;
- plugins: TypeScript event handlers, tools, commands, UI, AI classifiers, and agent definitions;
- MCP: external tool integration;
- checks: path-scoped review criteria;
- custom agent modes/subagents: model, appended instructions, included/excluded tools, reasoning effort, label/color.

Project plugins live in `.amp/plugins/*.ts`; system plugins live in a user config directory; global workspace plugins are an experimental enterprise surface. Plugins can reload without restarting, list their registered events/commands/tools, and mirror UI across TUI and web. See the [Owner's Manual](https://ampcode.com/manual) and [Plugin API](https://ampcode.com/manual/plugin-api).

Custom agents may use a public model ID, appended instructions, tool include/exclude selection, and reasoning effort. Plugins can run them once or create a continued thread; `parentThreadID` associates child and parent; execution can be local, an Amp Orb, or a named live Runner. A plugin can also register a mode visible alongside built-ins. Some of this agent-mode API is explicitly experimental and unstable.

### Better than ours

- One typed, hot-reloadable plugin surface spans events, commands, tools, UI, AI helpers, and child agents.
- Each customization mechanism has a documented purpose, reducing the chance that rules, commands, hooks, and MCP duplicate one another.
- Tool and custom-agent schemas use ordinary TypeScript types and JSON Schema.
- Plugins can synthesize a tool result or append a guarded continuation.

### Worse than ours

- TypeScript/Bun plugins are a broader in-process code-execution surface than isolated command hooks.
- Global policy plugins are experimental, which is weak for organization-wide enforcement.
- Execute mode can skip lifecycle events without a readiness flag.
- Amp explicitly removes compatibility and obsolete features quickly. That keeps its surface small but makes it a poor fit for owner workflows that require stable long-lived domain integrations unless pinned and regression-tested.

### Port

#### Customization decision table — CONFIG

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Enforce this routing rule in contributor guidance and skill creation templates: durable always-relevant facts → AGENTS/rules; task procedure/resources → skill; deterministic lifecycle reaction → hook; external system → MCP; review invariant → check; genuinely different model/tool policy → agent. Reject new additions that duplicate an existing layer.

This is **very likely (80-90%)** to reduce surface sprawl because Amp's taxonomy is explicit, our installed-to-used skill ratio is 355:78, and orphaned plugin directories already caused a platform failure. This is governance on the existing bus, not a registry service.

#### Do not port a Bun/TypeScript plugin runtime — no proposal

That would be a second extension runtime and violates the anti-overfit gate. Our native hooks already cover more lifecycle events. Port the discriminated response semantics into the dispatcher, not Amp's runtime.

## 8. Multi-agent support

### 8.1 Amp's built-ins

Amp automatically spawns subagents for complex tasks, particularly in `medium` mode. Each has its own context and file-edit/terminal tools. The manual recommends them for independent work, high-output tasks whose details need not pollute the parent, parallel code areas, and context isolation.

The limitations are explicit and substantial: subagents cannot communicate with each other, the user cannot guide them mid-task, they start without the accumulated parent conversation, and the parent sees only the final summary rather than step-by-step work. See the [Owner's Manual subagents section](https://ampcode.com/manual).

Specialists mitigate some weaknesses:

- Oracle is a different high-capability model used for debugging/review/analysis; in top tiers Amp deliberately pairs different frontier model families for writer and second opinion ([The Dial](https://ampcode.com/news/the-dial)).
- Librarian searches remote GitHub code.
- Review creates a review-specialized agent/toolset.
- Each custom review check gets a separate subagent.
- Plugins can define custom subagents and parent-linked threads, and run them on local, cloud Orb, or runner execution.

### 8.2 Comparison

Amp's automatic, context-isolated fan-out is cleaner for simple independent tasks. Its cross-model Oracle is a good diversity mechanism. But Amp is worse than our intended native team operation: our settings explicitly enable agent teams and forked subagents (`settings.json:5-7`), and the shared harness registers `TaskCreated`, `TaskCompleted`, and `TeammateIdle` (`registration.py:28-32`). Amp's built-ins cannot communicate or be steered and only return summaries, which makes them unsuitable for contested evidence, long monitoring, or tasks where a worker must challenge an orchestrator's false premise—the exact D4 failure in `INPUT-known-harness-defects.md:150-160`.

### 8.3 Ports

#### Cross-model Oracle role — CONFIG

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Define one optional `oracle` agent that is read-only, uses a different provider/model family from the main worker, receives a focused question plus cited evidence, and returns risks, contradictory evidence, and a recommended next probe. Invoke on high-cost misses: architecture, debugging after one failed fix, security, or pre-ship review—not every turn.

This is **likely (55-80%)** to catch correlated model errors because model-family diversity is a concrete Amp design and our harness already exposes Codex lanes. Evidence: Amp's Oracle docs; `/local_disk0/codexwork/bundle/claude/settings.json:27-30` permits Codex MCP calls. The settling experiment is a stratified replay comparing same-model review, cross-model review, and no review on defect recall, false positives, latency, and cost.

#### Preserve communicative, steerable teams — NATIVE

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Keep the native team/task surface and its lifecycle hooks. Use isolated summary-only subagents only when work is actually independent and disposable. Require evidence paths/results in the completion message and permit workers to challenge briefed facts.

This is **very likely (80-90%)** to outperform Amp-style isolation for interdependent work because our D4 shows false orchestrator facts propagate when recipients cannot falsify them, while our host already exposes team flags/events. No second orchestration runtime is warranted.

## 9. Verification and self-check mechanisms

Amp uses four layers:

1. **Model behavior.** Vendor evaluation says Opus 4.8 used a tighter write→test loop and ran tests/code 15% more often than its predecessor; this is vendor-reported and model/version-specific, not a durable harness guarantee. See [Opus 4.8](https://ampcode.com/news/opus-4.8).
2. **Prompt/repository affordance.** The manual recommends putting build/test/review commands in `AGENTS.md` and giving the agent something concrete to verify against.
3. **Second opinions.** Oracle provides another model for debugging/review; the main agent may invoke it but is not forced to because of cost.
4. **Review system.** `amp review` or the review panel analyzes a diff with a review-specialized agent. It pre-scans a large changeset, recommends review order, summarizes, and returns actionable findings. User-defined Markdown checks are path-scoped, carry severity/tool restrictions, and each executes in a separate subagent. See [Agentic Review](https://ampcode.com/news/agentic-code-review) and the [Owner's Manual](https://ampcode.com/manual).

Plugins add a fifth mechanism: an `agent.end` handler can detect an attempted finish and append “run the relevant tests” once, guarded by a marker against loops.

### Better than ours

Amp checks are a small, composable review primitive that does not require a trained critic, guardrail framework, or new service. Path precedence lets a specific subtree override a global check. One-check-per-subagent keeps each rubric focused and permits tool restriction.

Our `/verify` is comprehensive but operator-invoked (`verify.md:1-59`); `/quality-gate` explicitly says it is operator-invoked (`quality-gate.md:20-23`). The supplied snapshot/corpus show no `.agents/checks` equivalent by two signals. **UNVERIFIED whether an installed external skill outside the bundle implements equivalent automatic per-check fan-out — experiment:** enumerate live skill manifests for `check`, `review criterion`, and `severity-default`, then invoke a known candidate in a fixture.

### Worse than ours

- Amp does not document a mandatory test/evidence gate on every code-changing completion; the default relies partly on model judgment. **UNVERIFIED actual frequency — experiment:** run 50 code-edit tasks with clear tests and record whether Amp executes them before completion.
- Separate check agents can multiply cost and produce duplicate/noisy findings.
- The review loop still requires feeding findings back to the main agent; the December 2025 UI describes this as a human action.
- An `agent.end` “continue” hook can loop if the marker is wrong; Amp explicitly warns about this.

### Port

#### Path-scoped Markdown review checks — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `.agents/checks/*.md` (or the host-native equivalent) with `name`, description, default severity, path globs, and allowed tools. At explicit review or pre-ship gate, select only checks matching changed paths. Run independent read-only agents, deduplicate findings by file/line/root cause, and require each finding to cite evidence and a falsifying test. Start with 3-5 high-value invariants, not a catalog.

This is **likely (55-80%)** to improve review recall without bloating the main prompt because Amp's mechanism is focused and uses existing subagents. It may increase false positives; the settling experiment is a seeded-defect benchmark with precision/recall and cost, compared against the current `/verify` and reviewer agent.

#### Guarded completion verification — BUILD-SMALL

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On Stop/agent end after file-changing tools, inspect structured evidence ledger for a relevant successful test/build/repro after the last edit. If absent, append one continuation asking for the cheapest relevant verification or an explicit reason verification is impossible. Include a per-turn marker and hard maximum of one continuation.

This is **very likely (80-90%)** to reduce unverified completion because our host already exposes Stop/PostToolUse and Amp demonstrates the continuation mechanism. It must use structured result status to avoid D1's false-result corruption. **UNVERIFIED evidence-ledger completeness — experiment:** replay successful, failed, skipped, and irrelevant-test sequences through the shared harness and compare hook judgment with ground truth.

## 10. What not to copy

1. **No-approval-by-default execution.** Amp and our current bypass mode are both too permissive for a harness consuming untrusted repositories and MCP. Port structured permissions, not the default.
2. **Summary-only isolated subagents as the universal model.** They are good for independent disposable work and bad for contested, interdependent, or monitorable work.
3. **A hosted thread feed as implicit memory.** It is convenient but changes privacy, retention, and admin visibility. Keep local-first storage.
4. **A new plugin runtime.** We already have lifecycle buses. A Bun/TypeScript runtime would violate the anti-overfit gate and add readiness/order failures.
5. **Blind model-chasing.** Copy the stable task-difficulty dial, not Amp's July 2026 model names.
6. **Automatic compaction as truth.** Amp itself reversed course twice. Compactions orient retrieval; original events substantiate exact claims.
7. **One review agent per rule without selection.** Select checks by changed paths and cap fan-out.
8. **Aggressive removals without compatibility tests.** Amp can reject backcompat because it owns a hosted product. This owner has rare domain workflows; remove only after corpus/use and live known-positive controls agree.
9. **Lazy visibility mistaken for process health.** Amp starts skill MCP servers at launch while hiding tools until skill load. We need activation plus health/circuit breaking and safe orphan cleanup.
10. **AI classifier as permission authority.** Use AI to escalate uncertainty to a person, never to silently authorize destructive operations.

## 12. Anti-overfit gate

Every positive proposal above rides an existing rule, skill, hook, MCP, session-file, or native agent bus. None requires:

- a second orchestration runtime;
- a vector database or knowledge graph;
- a durable-execution engine;
- a trained critic;
- observability SaaS;
- a guardrail framework.

The only persistent addition proposed is a small file/optional SQLite FTS index for existing local session artifacts, not a daemon. If even that cannot remain local and dependency-free, omit it and use `rg` plus sidecar metadata. BUILD-LARGE is not justified anywhere in this teardown.

Amp's own evolution reinforces the gate: it removed Handoff, user-invokable skills, toolboxes, rollback behavior, themes, and other surfaces when newer models made them unnecessary ([Neo](https://ampcode.com/news/neo)). The portable principle is deletion after measurement, not copying every frontier feature.

## Bottom line

Port Amp's **selective exposure, temporal thread retrieval, typed tool intervention, scoped review checks, and stable capability dial**.
