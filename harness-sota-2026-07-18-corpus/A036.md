## Collision register

### C1 — Absolute common immutability versus Java's conditional mutability

**Artifacts and exact lines**

- `~/.claude/rules/common/coding-style.md:23-33`: “ALWAYS create new objects, NEVER mutate existing ones”; the rule calls immutability critical.
- `~/.claude/rules/java/coding-style.md:18-21`: fields are final “by default,” mutable state is permitted “when required,” and copy-on-write is prescribed.

**Class:** CONTRADICTION.

“Never” and “when required” cannot both govern the same `.java` file. Both rules are path-scoped to Java (`common/coding-style.md:1-20`; `java/coding-style.md:1-4`). AGENTS §10 does not resolve this same-level collision. The common wording is badly written as a universal coding law: Java has useful, bounded mutation in builders, collections under encapsulation, framework entities, local algorithms, and performance-sensitive internals. The target's “by default/when required” formulation is the more coherent intent, but precedence does not authorize silently choosing it.

**Specific resolution — CONFIG (settings/JSON only):** replace the common absolute with a boundary-oriented rule: “Prefer immutable values and do not mutate caller-owned inputs; permit localized mutation when it is encapsulated, required by a framework, or measurably clearer/faster.” In the Java rule, define the exceptions and require no mutable collection escape from public APIs. This resolution is **very likely (80-90%)** to remove the contradiction without weakening the valuable public-boundary invariant because it preserves defensive copies (`java/coding-style.md:20,32-34`) and makes the exception explicit. Evidence is the already-shipped builder collision in C2.

### C2 — Copy-on-write versus the shipped mutable Builder

**Artifacts and exact lines**

- `~/.claude/rules/java/coding-style.md:20-21`: defensive copies and “return new instances rather than mutating existing ones.”
- `~/.claude/rules/java/patterns.md:98-109`: every builder setter assigns to `this` (`this.query = query`, etc.) and returns the same mutable builder instance.

**Class:** CONTRADICTION.

This is not hypothetical: the harness simultaneously labels copy-on-write as the Java rule and teaches in-place builder mutation as the Java pattern. Both are same-level Java rules; precedence does not resolve it. The copy-on-write sentence is overbroad, not the builder pattern inherently wrong.

**Specific resolution — CONFIG (settings/JSON only):** scope copy-on-write to externally observable domain/application state and caller-owned objects; explicitly exempt construction-phase mutation confined to a builder that does not escape across threads. Add “builders may be mutable; built objects should satisfy their declared immutability contract” beside `patterns.md:80-109`. This is **almost certain (90-99%)** to make these two artifacts logically compatible because it directly separates the lifecycle phases exhibited by the exact example.

### C3 — Selectable Google enforcement versus 2-or-4 indentation and fixed member order

**Artifacts and exact lines**

- `~/.claude/rules/java/coding-style.md:11`: permits `google-java-format` or Checkstyle with Google or Sun style.
- Same file, `:13-14`: permits 2 or 4 spaces based on project standard and mandates one fixed order: constants, fields, constructors, public, protected, private.
- The official [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html) specifies +2 block indentation and states there is no single correct recipe for class-member order; it requires a logical, explainable order and contiguous overloads.
- The official [`google-java-format` README](https://github.com/google/google-java-format) says its formatting algorithm is deliberately non-configurable and distinguishes the normal 2-space formatter from the 4-space AOSP formatter.

**Class:** CONTRADICTION (and consequently UNENFORCED for the fixed member order when Google formatting is selected).

Selecting ordinary `google-java-format` cannot implement an arbitrary project 4-space standard, and Google Style directly rejects the target's single universal member recipe. Checkstyle can check configured policies but is a checker, not interchangeable with an autoformatter. The word “or” collapses different responsibilities.

**Specific resolution — CONFIG (settings/JSON only):** make project configuration authoritative in this order: existing Maven/Gradle formatter and Checkstyle tasks; repository formatter config; only then a documented default. Replace line 11 with separate “format” and “lint” duties. If Google Style is selected, use 2 spaces and logical member grouping/contiguous overloads; mention `--aosp` only when the repository explicitly chooses AOSP. Remove the universal member-order recipe or encode it in project Checkstyle and name that configuration. This is **very likely (80-90%)** to prevent formatter/rule fights because the official formatter is non-configurable and project build tasks are the only reliable place to pin the selected dialect.

## Recommended coherent end state

### 1. One canonical Java policy — CONFIG (settings/JSON only)

Rewrite `java/coding-style.md` around stable intent:

- repository formatter/build configuration outranks defaults;
- detect effective Java version before choosing syntax;
- immutable value/API boundaries by default, with explicit encapsulated construction/framework/performance exceptions;
- no mutable collection escapes;
- `Optional`, exceptions, streams, and member organization are review guidance unless a project-pinned tool enforces them;
- every bullet is marked `AUTO`, `BUILD`, or `REVIEW`;
- mechanism details live only in `java/hooks.md`; examples live only in skills/patterns.

This is **very likely (80-90%)** to remove the identified prose collisions because it resolves C1-C3 and C8-C9 at their source. It rides the existing rules bus and adds no rejected architecture.

### 2. Project-native Java validation adapter — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Add a bounded `.java` branch to the current validation bus. It should discover the nearest project wrapper/config, run fast check-only validation, cache project detection, exclude generated/build trees, and defer slow compile/test work to Stop or `longrun`. It must fail open on internal errors but emit a visible “not checked” receipt rather than silently treating unsupported Java as clean.

This is **likely (55-80%)** to fit in the small-build class; the uncertainty is multi-module Maven/Gradle resolution. Settle it with fixture tests for Maven wrapper, Gradle wrapper, multi-module roots, Android, no-build-file, generated sources, Java 8/17/21, timeout, and missing executable cases.

### 3. Govern existing reachability warnings — CONFIG (settings/JSON only)

Add the language-neutral static-reachability review rule from C7 and keep `wire-check` inject-only. Require the warning to cite the detected symbol and allow evidence of reflection/framework registration.

This is **very likely (80-90%)** to turn the current unruled enforcement into a coherent review prompt because it codifies the hook's own admitted uncertainty without escalating it to a block.

### 4. Do not add another runtime

No daemon, service, parser service, vector/KG memory, durable engine, trained critic, observability SaaS, or guardrail framework is justified. Compiler/formatter/linter truth already exists in each Java repository; the missing component is a thin adapter and coherent rules. This conclusion is **almost certain (90-99%)** under the anti-overfit gate because every identified defect is a text/config/dispatch defect, not a scheduling or memory-runtime deficit.
