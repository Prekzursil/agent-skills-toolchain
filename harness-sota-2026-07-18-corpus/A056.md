# A056 — Coherence audit: `~/.claude/rules/python/coding-style.md`

## Scope and verdict

This unit audited the unpacked, read-only subject at `/local_disk0/codexwork/bundle`. The canonical Windows subject paths do not exist on this Linux job node; every path below therefore names the corresponding file under the bundle. I wrote only this artifact.

The rule is not coherent as installed. Its useful intent is split across five incompatible levels of strictness:

1. the common rule makes immutability absolute (`ALWAYS`/`NEVER`);
2. the Python rule weakens that to a preference;
3. the sibling Python patterns rule demonstrates a mutable dataclass without an exception note;
4. the Python reviewer only treats missing annotations on **public** functions as a problem, whereas the rule requires annotations on **all** signatures; and
5. current hook wiring enforces Ruff lint findings after edits, but does not enforce Black, isort, type annotations, or immutability.

The overall diagnosis is **badly written plus incompletely enforced**, with one part of the policy probably wrong for this harness rather than merely missing enforcement. It is **almost certain (90-99%)**, based on the literal rule text, current settings wiring, hook source, a mechanically counted 1,628 unannotated function definitions in the two Python-heavy harness trees, and repeated Ruff violations captured in the corpus. “Probably wrong” applies specifically to the unqualified “all function signatures” rule: the unpacked hooks tree has 890/1,649 definitions not fully annotated and the shared harness has 738/869, while the reviewer consistently scopes its type-hint concern to public functions (`claude/agents/python-reviewer.md:32-35`).

The best resolution is evolution, not full replacement: reduce the Python file to a precise, project-aware policy; reconcile the common immutability language; and use the already-wired per-edit hook plus repository-native quality commands. That recommendation is **very likely (80-90%)** to improve coherence because every defect is on an existing rule/reviewer/hook bus and none requires a second runtime. It does not prove downstream project compatibility; the compatibility experiment is to run the proposed rule and checks against a stratified sample of active Python repositories before promotion.

## Collision register

### C01 — Absolute common immutability versus preferred Python immutability

- **Artifacts and exact lines:** `claude/rules/common/coding-style.md:23-33` says “ALWAYS create new objects, NEVER mutate existing ones”; the target says only “Prefer immutable data structures” at `claude/rules/python/coding-style.md:15-17` and supplies frozen examples at lines 19-32.
- **Class:** CONTRADICTION.
- **Precedence:** resolved operationally by `claude/rules/README.md:93-99`: the Python rule overrides common for `.py`. AGENTS.md §10 does not itself resolve two rule-pack files.
- **Why this is a defect:** a soft preference and an absolute prohibition produce different outcomes for ordinary Python operations such as appending to a private local list or updating a stateful object. Loading both wastes context and makes reviewer severity unpredictable.
- **Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** change common lines 23-33 to “prefer immutability at shared/state boundaries; local mutation is allowed when clearer and contained,” and make the Python rule the concrete language interpretation. This is **very likely (80-90%)** to eliminate the collision because the rule pack already declares language overrides (`rules/README.md:93-99`) and the sibling general review rule already uses the non-absolute wording “prefer immutable operations” (`rules/common/code-review.md:113-120`).

## Recommended replacement text — UNVERIFIED against active repositories

```markdown
---
paths:
  - "**/*.py"
  - "**/*.pyi"
---
# Python Coding Style

This file specializes the common coding-style rule. For Python, contained local
mutation is allowed when it is clearer; prefer immutable values at API, shared-
state, DTO, cache, and concurrency boundaries.

## Source of truth

- Follow the repository's checked-in Python configuration and quality command.
- Where the repository is silent, use PEP 8 and Ruff as the default lint baseline.
- Do not introduce Black, isort, Ruff format, mypy, pyright, or basedpyright into
  an established project unless its existing configuration or the user selects it.

## Types

- Annotate public and cross-module function parameters and returns.
- Annotate private helpers when the types are not obvious or the repository's
  configured checker requires it.
- Project-local strict typing may add stronger requirements.

## Data and mutation

- Prefer frozen dataclasses, NamedTuple, tuples, and read-only interfaces for value
  objects and shared data.
- Mutable dataclasses and collections are allowed when mutation is intentional,
  locally owned, and clearer than replacement.
- Do not mutate caller-owned inputs unless the API explicitly documents it.

## Verification

- After edits, use the existing fast syntax/lint nudge.
- Before completion, run the repository's configured formatter, linter, type checker,
  and tests for the changed scope; report unavailable or skipped checks explicitly.
- Python review may use `python-reviewer`; load `python-patterns` only when its live
  content has been reconciled with this rule.
```

This replacement is **very likely (80-90%)** to be more coherent because it resolves C01-C03, makes project configuration authoritative for C05-C08/C11, and gives immutability a reviewable scope for C10. It is **UNVERIFIED** against all active repositories; settle that premise with a dry-run matrix over representative strict-typed, untyped legacy, Black/isort, and Ruff-format projects before installation.
