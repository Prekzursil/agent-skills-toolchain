# A104 — coherence audit: agents vs commands / precedence ambiguity

**Unit:** A104  
**Date:** 2026-07-19  
**Subject snapshot:** `/local_disk0/codexwork/bundle/claude`  
**Scope:** every regular file under `agents/` and `commands/`, with the comparison limited to cases where an agent definition and a command can both govern the same execution and disagree without an explicit tie-break.

## Executive result

I found **six actionable precedence ambiguities in five overlap families**:

1. `/e2e` says Playwright; `e2e-runner` says Agent Browser first.
2. `/build-fix` says stop and ask before installing a missing dependency; `build-error-resolver` says adding missing dependencies is allowed.
3. `/refactor-clean` says one deletion at a time and no refactoring while cleaning; `refactor-cleaner` says remove by category/batch, commit each batch, and consolidate duplicates in the same workflow.
4. `/update-codemaps` requires approval before an overwrite when the generated diff exceeds 30%; `doc-updater` contains no such approval boundary and directs the agent to generate/update the codemap set.
5. `/code-review` blocks on HIGH findings; `code-reviewer` says HIGH is warning/can-merge and that reviewer judgments are advisory, not blocking.
6. `/python-review` and `/orchestrate` turn reviewer outputs into block/final-approval/SHIP decisions, while `python-reviewer`, `code-reviewer`, and `security-reviewer` say reviewer reasoning is advisory and deterministic verification gates decide merge/block.

This is **not** a flat “which Markdown file has priority?” problem. Claude Code creates two actors. A custom command loads into the **parent conversation** as a prompt message; a custom agent runs in a fresh context whose Markdown body is its **system prompt**, plus a delegation task message. The agent prompt therefore governs actions taken *inside the subagent*, while the parent command remains able to interpret the returned result and govern the parent’s outward decision. That split is the missing tie-break. It explains why tool-choice and mutation conflicts resolve toward the agent, while aggregation/gating conflicts resolve toward the command-owning parent.

The exact model completion for each collision is **UNVERIFIED; the settling experiment is the disposable fixture described under “Runtime verification protocol,” run with the owner’s installed Claude Code version on Windows**. The structural precedence above is verified from two mechanically independent official documentation surfaces and the local configuration, but this Linux node has no `claude` executable (`command -v claude` returned no path; `claude --version` returned `/bin/bash: claude: command not found`).

## Runtime precedence: what actually wins

### Verified composition model

Signal 1 — the official Claude Code skills/commands documentation says legacy `.claude/commands/<name>.md` files use the skills mechanism and that, when invoked, their rendered content enters the conversation as a single message: <https://code.claude.com/docs/en/slash-commands>.

Signal 2 — the official custom-subagents documentation says a file’s Markdown body becomes the subagent’s system prompt; a non-fork subagent receives its own system prompt and a separate delegation task message, not the parent conversation; the parent receives the subagent’s final message as the Agent tool result: <https://code.claude.com/docs/en/sub-agents>. The SDK version independently states that the only parent-to-subagent channel is the Agent tool prompt and lists “its own system prompt” plus “the Agent tool’s prompt” as separate inputs: <https://code.claude.com/docs/en/agent-sdk/subagents>.

Signal 3 — Anthropic’s system-prompt documentation states that instructions in a user message carry less weight than the same text in a system prompt: <https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts>.

Local corroboration — `settings.json:419-440` wires distinct `SubagentStart` and `SubagentStop` events, while `settings.json:117-135` wires `UserPromptSubmit`; this confirms that this harness treats the parent prompt and subagent lifecycle as separate runtime surfaces. It does not itself prove model-role priority, so it is corroboration rather than the primary signal.

Therefore:

```text
/command invocation
    -> command Markdown becomes a parent-conversation prompt
    -> parent decides/executes or delegates
        -> agent Markdown is the subagent SYSTEM prompt
        -> delegation is the subagent TASK prompt
        -> agent system prompt wins conflicts inside that subagent
    -> result returns to parent
    -> parent command still governs aggregation, gating, and user-facing next action
```

This is the runtime tie-break the files fail to state. It is **almost certain (90-99%) that an explicitly dispatched agent follows its own system-level tool/mutation rule over a contradictory command-derived delegation task**, based on the two official context-composition descriptions and Anthropic’s explicit system-vs-user weighting. The remaining 1-10% is model non-determinism and version-specific prompt assembly; exact completions are **UNVERIFIED; run the fixture protocol below to settle them on the owner’s version**.

Automatic delegation is weaker. Official docs say Claude delegates based on the task, the agent description, and context, but do not promise delegation for a plain slash command. Thus it is **likely (55-80%) that exact semantic pairs such as `/build-fix`, `/refactor-clean`, `/update-codemaps`, and `/code-review` auto-select their counterpart agents**, based on near-identical task descriptions and observed historical use of several corresponding agents. That co-activation is **UNVERIFIED; capture `SubagentStart.agent_type` while invoking each command to settle it**. These are still actionable ambiguities because the configuration advertises `Use PROACTIVELY`/`MUST BE USED` and grants the agents mutation tools; but their severity is below the explicit `/e2e`, `/python-review`, and `/orchestrate` paths.
