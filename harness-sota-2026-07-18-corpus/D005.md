# D005 — HARNESS-BENCH: regression detection under noisy agent runs

## Executive verdict

A harness regression gate must make a three-way decision—**regression**, **non-inferior**, or **inconclusive**—from paired, contemporaneous baseline/candidate runs. It must not turn “not statistically significant” into “no regression.” The practical design is a thin Python scorer over immutable JSONL results, task-level paired bootstrap/permutation inference, an explicit power calculation, and exact zero-tolerance checks for deterministic safety invariants. This rides the existing pytest/eval/scheduled-task/ledger buses and does not require another orchestration runtime, model judge, vector database, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

The concrete sample-size answer is:

* If “10% effect” means a **10 percentage-point absolute change** in a binary pass rate, with two independent equal-sized arms, two-sided `alpha=0.05`, and 80% power, the normal two-proportion calculation requires **388 runs per arm at 50%→40%, 356 per arm at 70%→60%, or 195 per arm at 90%→80%** (776, 712, or 390 total trajectories respectively).
* If it means a **10% relative decline**, the absolute effect depends on the baseline. The same calculation requires **1,565 per arm for 50%→45%, 712 per arm for 70%→63%, or 445 per arm for 80%→72%**.
* A paired design is usually much cheaper, but its answer depends on the fraction `q` of pairs for which baseline and candidate disagree. For a 10-point absolute change, the large-sample McNemar calculation needs about **84, 155, 234, 312, or 469 independent pairs** when `q` is respectively 0.11, 0.20, 0.30, 0.40, or 0.60. For a 70%→63% relative decline, it needs **110–1,071 pairs** as `q` ranges from its theoretical minimum 0.07 to 0.67. The discordance must come from a pilot; choosing it after seeing the candidate is invalid.

These values were mechanically recomputed on this job node with `statsmodels.stats.proportion.proportion_effectsize`, `statsmodels.stats.power.NormalIndPower.solve_power`, and the two-sided McNemar power equation documented by Stata. Statsmodels documents `NormalIndPower` as a two-independent-sample z-test power calculator ([official API/source](https://www.statsmodels.org/stable/_modules/statsmodels/stats/power.html#NormalIndPower)); Stata defines the paired binary problem in terms of discordant proportions and gives the test and power equations ([official `power pairedproportions` manual, pp. 20–21](https://www.stata.com/manuals/pss-2powerpairedproportions.pdf)).

**Bottom line:** three repeats are a useful smoke test, not a powered regression claim. A release claim about a 10% effect needs a pilot, paired design, and usually hundreds—not three—of independent task/run pairs. It is **almost certain (90-99%)**, given the analytic calculations above and the 60,000-trajectory agent-eval study discussed below, that treating 3/3 as evidence of production reliability would materially overstate confidence.

### 4. Real agent runs are noisy even at temperature zero

The 2026 paper *On Randomness in Agentic Evals* reports 60,000 SWE-bench Verified trajectories across three models and two scaffolds. ## What “a run” means

Confusion between tasks, epochs, and trajectories is a primary source of fake sample size. This design uses the following vocabulary:

* **Task**: a versioned input/environment/grader unit. Tasks are the sampling units for claims about future work.
* **Epoch**: one independent attempt by a variant on a task from fresh state.
* **Trajectory**: the complete recorded attempt. Total cost is `tasks × epochs × variants` trajectories.
* **Pair**: baseline and candidate on the same task and epoch index, with order randomized. A pair is not independent of other epochs on the same task.
* **Case family**: a predeclared stratum such as quoting, schema, path/plugin, network, edit freshness, safety false positive, recovery, or provider parity.
* **Benchmark run**: one execution of the complete manifest. This term is never used as the statistical sample size.

Repeated epochs reduce uncertainty about a fixed task. More distinct tasks reduce uncertainty about the task population. Ten epochs on one task are not ten independent task samples; treating them that way is pseudoreplication. Inspect explicitly supports clustered standard errors when observations share a cluster ([official documentation](https://inspect.aisi.org.uk/metrics.html#clustered-stderr)).

### P4 — Paired task bootstrap plus randomization test

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing result JSONL bus).**

For each task `i`, compute baseline epoch mean `b_i`, candidate epoch mean `c_i`, and paired difference `d_i=c_i-b_i`. The reported effect is `mean(d_i)`.

Inference:

1. Resample **tasks**, not individual trajectories, with replacement 10,000 times; carry all epochs and both variants for each selected task. Stratify by the predeclared case family if the manifest fixes family proportions. Use the percentile or BCa 95% interval for `mean(d_i)`.
2. Independently compute a paired randomization test by swapping baseline/candidate labels within each task with probability 0.5 and recomputing the mean. SciPy documents `permutation_type="samples"` for paired-sample label exchange and defaults to 9,999 resamples ([official API](https://scipy.github.io/devdocs/reference/generated/scipy.stats.permutation_test.html)).
3. Report both the interval and p-value, plus the raw vector of task effects. If they disagree near the boundary, return `INCONCLUSIVE`; do not choose the favorable method.

Bootstrap uncertainty is established prior art for finite-run agent evaluation: RLiable recommends stratified bootstrap confidence intervals because every finite-run aggregate is a random variable ([Google Research overview](https://research.google/blog/rliable-towards-reliable-evaluation-reporting-in-reinforcement-learning/); [paper](https://arxiv.org/abs/2108.13264)).

This method is **likely (55-80%)** to have well-calibrated coverage once there are at least roughly 100 diverse tasks because it preserves task clustering and pairing, but the coverage for this owner's skewed task mix is **UNVERIFIED; the settling experiment is a simulation calibrated from a baseline A/A pilot, checking empirical Type-I error over at least 2,000 synthetic null experiments**. A bootstrap library is not a substitute for that calibration.

### P5 — Three-way decision rule

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing scheduled digest and ledger bus).**

Let `Δ = candidate - baseline`, and let `m=0.10` be the predeclared maximum tolerable absolute regression for the primary metric. Use the paired 95% confidence interval `[L,U]`:

* `REGRESSION` when `U < 0`. Add severity `observed_material` when the point estimate `Δ <= -m`, and the stronger severity `confidence_bound_material` only when `U < -m`. Keeping the statistical decision separate from materiality makes the 80%-power calculation for a true `-m` alternative valid.
* `NON_INFERIOR` when the result is not `REGRESSION`, `L > -m`, no hard constraint fails, and benchmark integrity is green. This rules out a regression as large as the tolerance; it does not prove equality.
* `INCONCLUSIVE` otherwise. Run the predeclared additional task block if budget remains; never silently pass.
* `INVALID` when the benchmark self-test, manifest hash, grader hash, sample accounting, environment preflight, or result parser fails. Invalid is not green and must page/log separately from a candidate regression.

For a stricter claim that the true regression is at least ten points, require `U < -0.10`; note that this is a different estimand and needs a larger observed decline to clear. For detecting a true ten-point decline against zero, the power tables in this document use the conventional two-sided null `Δ=0` with 80% power. A narrow interval such as `[-0.08,-0.02]` is therefore `REGRESSION` but not materially bounded at ten points; promotion policy may treat that as a warning or block, but the statistical record must preserve both facts.

This decision rule is **very likely (80-90%)** to prevent the most damaging current failure mode—silent invalid evaluation—because parse failure becomes a separate terminal state rather than `return 0` (`bench.py:158-160,185-190`). ## Power and sample size in detail

### Define the effect before calculating power

“Detect a 10% effect” has at least four incompatible meanings:

1. ten **percentage points**, e.g. 70%→60%;
2. ten percent **relative**, e.g. 70%→63%;
3. a standardized continuous effect, e.g. Cohen's `d=0.10`;
4. a ten-percent increase in cost/latency, usually analyzed on a log scale.

This design defaults to a **10 percentage-point absolute pass-rate regression** because it maps directly to owner-visible failed tasks. Every manifest must spell out `practical_regression_margin_abs: 0.10`; the word “10%” alone is rejected by schema validation.

### Independent-arm reference calculation

For binary pass rates `p0` and `p1`, equal arms, two-sided `alpha=.05`, and power `.80`, the reproducible calculation is:

```python
from math import ceil
from statsmodels.stats.proportion import proportion_effectsize
from statsmodels.stats.power import NormalIndPower

def n_per_arm(p0, p1, alpha=0.05, power=0.80):
    h = abs(proportion_effectsize(p0, p1))
    return ceil(NormalIndPower().solve_power(
        effect_size=h, alpha=alpha, power=power,
        ratio=1, alternative="two-sided"))
```

Mechanically reproduced results:

| Baseline → candidate | Meaning | Absolute delta | Runs per arm | Total trajectories |
|---|---:|---:|---:|---:|
| 50% → 40% | 10 points | -0.10 | 388 | 776 |
| 70% → 60% | 10 points | -0.10 | 356 | 712 |
| 90% → 80% | 10 points | -0.10 | 195 | 390 |
| 50% → 45% | 10% relative | -0.05 | 1,565 | 3,130 |
| 70% → 63% | 10% relative | -0.07 | 712 | 1,424 |
| 80% → 72% | 10% relative | -0.08 | 445 | 890 |

These are independent Bernoulli observations. They are not valid if repeated epochs from the same task are counted as independent.

### Paired binary calculation

Pairing changes the variance. Let `p12` be the probability baseline passes/candidate fails, `p21` candidate passes/baseline fails, `d=p21-p12`, and `q=p12+p21`, the total discordant fraction. McNemar's statistic uses only discordant pairs. Stata's official manual gives `χ²=(n12-n21)²/(n12+n21)` and the corresponding two-sided power equation ([manual, pp. 20–21](https://www.stata.com/manuals/pss-2powerpairedproportions.pdf)).

For a ten-point decline, `|d|=.10`, but `q` remains unknown:

| Pilot discordance `q` | Example discordant probabilities | Independent pairs for 80% power | Total trajectories (two variants) |
|---:|---:|---:|---:|
| 0.11 | 0.105 vs 0.005 | 84 | 168 |
| 0.20 | 0.15 vs 0.05 | 155 | 310 |
| 0.30 | 0.20 vs 0.10 | 234 | 468 |
| 0.40 | 0.25 vs 0.15 | 312 | 624 |
| 0.60 | 0.35 vs 0.25 | 469 | 938 |

For a 70%→63% relative decline (`|d|=.07`), the required independent pairs are 110 at `q=.07`, 238 at `.15`, 479 at `.30`, 799 at `.50`, and 1,071 at `.67`. This is why no honest universal number exists.

The paired table can be reproduced without Stata as follows; it directly implements the documented two-sided normal power equation and searches the first integer `n` reaching the target:

```python
from math import sqrt
from scipy.stats import norm

def mcnemar_power(n, p12, p21, alpha=0.05):
    d = p21 - p12
    q = p12 + p21
    z = norm.ppf(1 - alpha / 2)
    den = sqrt(q - d*d)
    return (norm.cdf((d*sqrt(n) - z*sqrt(q)) / den)
            + norm.cdf((-d*sqrt(n) - z*sqrt(q)) / den))

def paired_n(discordance_q, abs_delta=0.10, power=0.80):
    p12 = (discordance_q + abs_delta) / 2
    p21 = (discordance_q - abs_delta) / 2
    assert 0 <= p21 <= p12 <= 1
    return next(n for n in range(2, 100_000)
                if mcnemar_power(n, p12, p21) >= power)
```

These McNemar figures use a large-sample approximation and are **likely (55-80%)** accurate enough for planning once expected discordant counts are comfortably above 25; exact or simulation-based power is preferable near sparse boundaries. The evidence is Stata's documented large-sample method and its example obtaining 82 pairs for approximately a 10.1-point effect at `q=.109` ([official manual, pp. 12–15](https://www.stata.com/manuals/pss-2powerpairedproportions.pdf)), which closely matches this unit's 84-pair reproduction at `q=.11`.

### Clustered task/epoch design

The production estimator averages epochs within task and resamples tasks. There is no closed-form sample count that is trustworthy before observing task heterogeneity and within-task variance. Use a two-stage prospective design:

1. **Variance pilot:** 50 tasks × 3 epochs × 2 variants = **300 trajectories**. Include all benchmark families and randomize A/B order. The pilot estimates task-effect standard deviation, epoch intraclass correlation, binary discordance, invalid-run rate, and family variance. It is not a ship/no-ship test.
2. **Power simulation:** resample pilot tasks, simulate candidate regressions of exactly -0.10 without changing task/family composition, and find the smallest task count in `{75,100,150,200,300,400}` whose complete planned decision procedure detects the effect in at least 80% of 2,000 simulations while its A/A false-regression rate is at most 5%.
3. **Lock `N`:** write that task count and max exclusions into the manifest before looking at candidate outcomes. Run the fixed sample. If the available task pool cannot reach the required `N`, report `UNDERPOWERED/INCONCLUSIVE`; do not weaken the claim.

The 50×3 pilot size is **UNVERIFIED and therefore not a recommendation for final power; the experiment that settles it is the pilot itself followed by the specified simulation**. It is a deliberately affordable variance-estimation starting point. Three epochs follow the existing local regression vocabulary (`pass^3`) and recent agent-eval evidence that multiple independent runs are necessary; they do not independently justify an 80%-powered claim.

As a sanity check for continuous task-level differences, the paired-normal approximation is `N ≈ ((1.96+0.842) × SD(d_i) / 0.10)^2`. It gives approximately 49 tasks if `SD(d_i)=0.25`, 97 at `0.35`, 126 at `0.40`, and 197 at `0.50`. These are diagnostics, not the final binary clustered calculation.

### Precision is different from power

Power asks whether the gate detects a prespecified effect under repeated experiments. Confidence-interval width asks how precisely this one experiment estimates the effect. Report both. A test can have `p<.05` yet an interval too wide to rule out an operationally important regression; conversely, a narrow interval around a tiny negative delta can be statistically significant but practically irrelevant.

No `N` can justify “zero risk.” For zero observed critical violations in `N` independent opportunities, the rough 95% upper bound is `3/N` (the rule of three): 3% at 100, 1% at 300, and 0.1% at 3,000. Because agent opportunities are clustered within tasks, those are optimistic unless the unit of exposure is defined correctly. Hard safety gates should therefore combine zero observed violations with explicit exposure counts and a stated upper bound, not the phrase “100% safe.”

Fix or log all of the following before comparison:

* exact task manifest and family proportions;
* baseline/candidate source hash and dependency lock/image hash;

* environment/preflight failure distinct from agent failure.

Use the same task and epoch index for each pair. If a provider honors seeds, use matched seeds as a variance-reduction device but still randomize pair order; matched seeds do not make runs deterministic. Re-run baseline contemporaneously rather than comparing a July candidate to a June point estimate.

These controls are **very likely (80-90%)** to reduce nuisance variance without changing the intended harness comparison because they hold non-harness factors constant. The exact gain is **UNVERIFIED; the experiment is to compare paired versus deliberately unpaired A/A standard errors on the pilot**.

Do not eliminate real operational variance that belongs in the target: network failure/recovery, Windows quoting, plugin-path size, and provider differences are part of this owner's harness. Instead, represent them as declared strata and report both controlled-core and operational-stress results.

## Sequential testing, peeking, and multiple comparisons

Do not repeatedly inspect `p<.05` after every task and stop when convenient. That inflates false positives. The simplest runnable-this-week rule is fixed `N` from the pilot. One optional blinded checkpoint may check only invalid rate and variance—not arm labels—and may increase `N` according to a prewritten formula capped by `max_tasks`.

If cost later demands true sequential testing, use a predeclared alpha-spending or always-valid procedure. Adding one ad hoc is not part of this minimal design. A second experimentation service would fail the anti-overfit gate.

One primary metric avoids most multiplicity. Safety constraints are contracts, not p-value fishing. Family slices are diagnostic unless a small set is preregistered as co-primary and Holm-adjusted. Every exploratory result must be labeled exploratory and reproduced on a held-out task refresh before promotion.

Repeatedly tuning against one frozen suite wears it out. Google’s ML guidance notes that validation/test sets can wear out through repeated use and recommends representative, nonduplicated held-out data ([official guidance](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)). Maintain:

* a visible development suite for fast iteration;
* a sequestered promotion suite used only for release decisions;
* a quarterly refresh queue drawn from new corpus fingerprints/owner corrections, with old tasks retained for longitudinal reporting.

It is **likely (55-80%)** that this split will reduce benchmark overfitting because candidate authors cannot directly optimize every promotion task; the magnitude is **UNVERIFIED, settled by tracking visible-suite versus sequestered-suite effect gaps across at least ten candidate evaluations**.

## Rejected alternatives and dead ends

### “Run each version three times and require 3/3”

Rejected as a confidence claim. Three fresh roots can reveal deterministic state leakage and make `pass^3` meaningful as an observed reliability metric, but 3/3 has a very wide binomial interval and cannot detect a ten-point pass-rate change with 80% power. The recent 60,000-trajectory study directly finds meaningful run-to-run variation even at temperature zero ([paper](https://arxiv.org/abs/2602.07150)).

### Compare a candidate point estimate to the historical maximum

Rejected. The current ratchet selects positive noise, does not preserve the raw comparison distribution, and confounds time/provider drift. Freeze and rerun the baseline contemporaneously.

### Bootstrap individual trajectories

Rejected. Epochs from one task share prompt, environment, difficulty, and grader; trajectory-level resampling destroys clustering and yields intervals that are too narrow. Resample tasks and carry their epochs/pairs together.

### One giant weighted score

Rejected. It allows cheap utility gains to compensate for a secret leak or destructive side effect and hides family regressions. Keep one primary utility metric, hard safety constraints, and visible family slices.

### Treat missing/timeout/parse error as candidate pass because the hook is fail-open

Rejected. Runtime fail-open and benchmark validity are different contracts. The host may continue, while the experiment must be `INVALID`. The present silent-zero path proves the danger (`bench.py:158-160,185-190`).

### Adopt an experiment SaaS, durable workflow system, or model-judge service

Rejected by the anti-overfit gate. None is needed for paired JSONL scoring, and each would add a second control plane. Revisit only if the small scorer fails a measured requirement that the existing bus cannot meet.

### Automatically stop when significance appears

Rejected without a predeclared sequential method. Optional stopping inflates false positives. Fixed `N` from a pilot is simpler and runnable this week.

## Acceptance tests for the regression detector itself

The detector is done only when two mechanically independent signals support every status:

1. **Producer validity:** real subprocess emits schema-valid JSON; independent parser self-test finds the known-positive case.
2. **Regression sensitivity:** seeded -10-point synthetic data returns `REGRESSION`; independent label-swap returns the opposite-signed effect.
3. **Null calibration:** A/A simulation has no more than 5% false regressions at two-sided alpha .05; independent real A/A pilot interval includes zero.
4. **Non-inferiority:** synthetic effect above `-m` returns `NON_INFERIOR` only when the lower interval bound exceeds `-m`; independent hard-constraint injection overrides it.
5. **Inconclusive behavior:** small/noisy sample returns `INCONCLUSIVE`; independent added predeclared sample block can resolve it without changing prior rows.
6. **Invalid behavior:** malformed output returns `INVALID`; independent scheduler exit/digest check proves invalid is surfaced rather than swallowed.
7. **Accounting:** manifest says `N×epochs×2`; independent row counter and unique `(task,epoch,variant)` constraint agree.
8. **Reproducibility:** rerunning the scorer on frozen rows yields byte-identical decision JSON; independent implementation (small reference notebook/script) matches effect and interval within declared tolerance.

The design will be **very likely (80-90%)** fit for promotion decisions when all eight controls pass, because they cover data validity, sensitivity, Type-I error, power semantics, terminal states, accounting, and reproducibility. That is a forward-looking assessment, not a completed implementation claim; the experiments above are the settling evidence.
