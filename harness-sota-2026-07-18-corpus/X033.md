# X033 — Cross-domain borrow: aviation safety → agent tool design

**Unit:** X033  
**Source field:** aviation safety (checklists, crew resource management, incident reporting, and automation-surprise research)  
**Target:** tool interfaces and error messages that induce agent misuse, especially the 1,631 measured unmatched-quote/EOF shell failures stated in the unit brief  
**Lens boundary:** external research and design only. Per the task, I did not inspect or make claims about the local harness implementation.

## Executive finding

The analogy **does transfer, but only after a crucial substitution**. Aviation's useful mechanism is not “add a checklist” or “ask another agent to agree.” It is **challenge–verification–response against independently observable state**, combined with explicit automation-mode annunciation, error-tolerant controls, and a reporting loop that drives interface redesign. The transferable structure is:

1. an operator expresses an intended action;
2. a mechanistically different channel observes the action or system state;
3. the system returns a concrete readback of what it actually understood;
4. disagreement blocks or redirects the action before consequences propagate;
5. failures and near misses are classified as system-design evidence, not merely operator incompetence.

For shell tools, the independent observer can be the **target shell's own parser** (and, where no shell semantics are needed, an argv-native process launcher). It must not be another natural-language self-check by the same model. This narrowed transfer is **very likely (80-90%)** to eliminate the unmatched-quote/EOF subclass before execution because Bash itself exposes a syntax-only mode and the aviation source explicitly requires review of constructed commands before activation; evidence is the GNU Bash definition of `-n` and FAA AC 25.1302-1 §5-6/§5-7 ([GNU Bash `set -n`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html), [FAA AC 25.1302-1](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf)). The exact reduction on this owner's workload is **UNVERIFIED; the experiment that settles it is a shadow-mode replay of the 1,631 supplied unmatched-quote fingerprints through the proposed preflight contract, followed by a randomized live canary comparing failures per 1,000 shell calls**.

The broader claim that this will reduce all quoting failures is only **likely (55-80%)**, because syntactically valid but semantically wrong quoting, expansion, interpolation, and cross-shell assumptions survive a syntax check; evidence is that Bash `-n` is documented only to read without executing and check syntax, while Bash `-c` still treats one string as shell input ([GNU Bash invocation](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html)). The proposed interface therefore makes **argv execution the default** and explicit shell interpretation the exception.

The analogy fails in three places and those failures shape the design:

- Two pilots can provide partly independent perception, physical access, and expertise. Two samples from the same model and prompt are correlated. A “critic agent” reciting the command is not CRM-grade redundancy. No second orchestration runtime or trained critic is proposed.
- Aviation checklists rely partly on professional discipline and social coordination. Agents can ritualistically emit “checked” without observing anything. The verifier must return parsed facts, not an attestation.
- Aviation incident reporting needs confidentiality and limited immunity to overcome human fear. An agent has no career, shame, or punishment avoidance. The transferable part is structured capture and system-level causal analysis, not the incentive regime.

## Research method and evidence quality

I prioritized primary or first-party sources: FAA advisory circulars and research reports, NASA technical reports and ASRS program material, and the GNU Bash manual for the concrete parser capability. The central sources are:

- FAA-hosted NASA report, Degani and Wiener, *Human Factors of Flight-Deck Checklists: The Normal Checklist*. It defines challenge–verification–response, discusses mutual/configuration redundancy, ambiguity, interruption recovery, and checklist length ([report PDF](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). This is an older report, and some examples concern paper flight decks; I use its mechanisms only where later FAA design guidance independently agrees.
- FAA AC 25.1302-1, *Installed Systems and Equipment for Use by the Flightcrew*. It requires operationally relevant behavior to be predictable and unambiguous, recommends review and confirmation of constructed commands before activation, specifies unambiguous feedback, and assumes trained crews still make errors ([AC 25.1302-1 PDF](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf)).
- FAA AC 25.1322-1, *Flightcrew Alerting*. It specifies condition-identifying, corrective, prioritized, consistent alerts while minimizing false/nuisance alerts ([AC 25.1322-1 PDF](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_25.1322-1.pdf)).
- NASA research on automation surprise and mode awareness. It defines surprise as designed behavior diverging from operator expectation, and reports mode/data-entry/coordination categories from 184 ASRS cases ([NASA TM 1998-112217](https://humanfactors.arc.nasa.gov/publications/20051025132410_aiding_vg_understanding_tm.pdf)); the related NASA record frames mode awareness as knowledge of current and future automation status ([NASA NTRS record](https://ntrs.nasa.gov/citations/20040112190)).
- FAA controller/pilot communication research describing the readback/hearback loop and distinguishing a bad readback from the originator's failure to correct it ([FAA report DOT/FAA/AM-06/25](https://www.faa.gov/sites/faa.gov/files/data_research/research/med_humanfacs/oamtechreports/200625.pdf)). The FAA glossary separately defines “READ BACK” as repeating the message ([FAA Pilot/Controller Glossary, R](https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/glossary-r.html)).
- NASA ASRS documentation for voluntary, confidential, de-identified reporting and limited enforcement protections ([ASRS confidentiality and incentives](https://asrs.arc.nasa.gov/overview/confidentiality.html), [ASRS immunity policies / AC 00-46F](https://asrs.arc.nasa.gov/overview/immunity.html)).
- FAA maintenance human-factors guidance, which says person-centered “blame-and-train” does not effectively reduce failure to follow procedure and recommends a systematic response across organizational levels ([FAA Procedural Non-Compliance](https://www.faa.gov/about/initiatives/maintenance_hf/procedural_non-compliance)).

These are normative guidance and observational/experimental research, not proof about LLM tool use. Every effectiveness projection below is therefore marked **UNVERIFIED** and names its settling experiment.

## Mechanism 1: challenge–verification–response, not checkbox theater

### How it works in aviation

Degani and Wiener distinguish a do-list (“call–do–response”) from the more redundant challenge–response method, more precisely **challenge–verification–response**. In the latter, the aircraft is first configured; one pilot reads the item; both pilots verify the actual setting; the responding pilot states the verified status. This provides two different redundancies: the checklist backs up configuration, and crew members cross-monitor each other ([NASA/FAA checklist report, §3.1.4](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)).

The response is not supposed to be a generic ritual. The same report documents ambiguity from responses such as “set,” “check,” and “completed,” and recommends stating the actual value or desired status. Its example contrasts “checked and set” with reading actual airspeed/EPR values; the latter creates an observable comparison rather than a content-free assertion ([NASA/FAA checklist report, §6.2.3 and guidelines 4-6](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). FAA readback/hearback similarly requires the receiver to repeat the instruction and the sender to actively verify it; the FAA study calls a receiver's wrong repetition a readback error and the sender's failure to correct it a hearback error ([FAA DOT/FAA/AM-06/25, discussion](https://www.faa.gov/sites/faa.gov/files/data_research/research/med_humanfacs/oamtechreports/200625.pdf)). Safety therefore depends on the **closed loop**, not merely producing an echo.

### Why the structure transfers

A shell command has the same relevant topology: intent is encoded into a compact command; a parser interprets that encoding; the actual interpretation may diverge from intent; and an error can emerge late as a generic EOF or at execution as unintended arguments. The analogy is strongest because the tool can obtain an independent, exact observation from the interpreter. Unlike a cockpit switch check, shell syntax is deterministic and cheap to parse before execution.

The structural match is **very likely (80-90%)**, supported independently by (1) aviation's requirement that automated systems let crews review and confirm constructed commands before activation in FAA AC 25.1302-1 §5-6, and (2) Bash's documented `-n` parse-without-execution behavior ([FAA AC 25.1302-1](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf), [GNU Bash `set -n`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)). It is not “almost certain” because intent cannot always be inferred from a syntactically valid program.

### Proposal 1 — Typed command envelope and parser readback — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Put a small adapter on the existing tool bus. Replace the single overloaded command string with an explicit envelope:

```json
{
  "mode": "argv | bash | powershell",
  "cwd": "/absolute/path",
  "executable": "rg",
  "argv": ["--fixed-strings", "owner's text", "file.md"],
  "script": null,
  "timeout_ms": 10000,
  "intent": "find the literal text in one file"
}
```

Contract rules:

1. `mode=argv` accepts `executable` plus an argument array and rejects `script`. It performs no shell interpolation. This is the normal route for single commands.
2. `mode=bash|powershell` accepts `script`, requires an explicit interpreter, and rejects simultaneous `argv`. Shell use is reserved for pipelines, redirection, control flow, or expansions that actually require it.
3. Before executing shell mode, the adapter sends the exact script to the target interpreter's parser-only facility. For Bash, `-n` reads commands without executing and is explicitly documented for syntax checking ([GNU Bash `set -n`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)). A PowerShell implementation should use the native PowerShell parser and its parse-error extent; that PowerShell-specific API detail is **UNVERIFIED; the experiment that settles it is a 20-case spike on the deployed PowerShell 7 version comparing parser error extents with real invocation errors**.
4. The adapter returns a machine-readable **readback receipt** before/with execution: `invocation_id`, selected mode, interpreter identity/version, cwd, executable resolution, argv as a JSON array, parse status, and source extent for any parse failure. It does not ask the model to say “looks good.”
5. Syntax rejection returns `executed:false`. The model repairs the retained envelope by replacing only the faulty field; it does not reconstruct the entire command from a flattened error string.

This proposal is **very likely (80-90%)** to catch unmatched quotes, unclosed command substitutions, and syntactically unfinished shell programs before process execution because those are parser-level defects and Bash exposes a no-execute syntax pass; evidence is the GNU Bash manual. This projection is **UNVERIFIED; settle it with the shadow replay and canary described in the executive finding**. It is only **likely (55-80%)** to reduce the total retry-loop burden, because retry behavior depends on how agents consume the structured error; **UNVERIFIED; settle it by measuring same-fingerprint recurrence within the next three calls, not merely first-call rejection**.

What this catches that a conventional string tool misses:

- an unmatched quote before the command reaches normal execution;
- accidental use of PowerShell syntax under Bash, or vice versa, because mode is explicit;
- argument-boundary drift (`"a b"` becoming two arguments) in `argv` mode because the receipt exposes actual array elements;
- an agent “repair” that changes unrelated command text, because patch-on-envelope preserves stable fields;
- empty or unresolved executables before running;
- cross-platform ambiguity such as a command whose meaning depends on an implicit default shell.

It does **not** prove the command's semantic intent, path correctness, authorization, glob cardinality, environment-variable value, or destructive impact. Claiming otherwise would force the analogy past its evidence.

### Anti-overfit gate for Proposal 1

This is a thin adapter on the existing tool bus, not a second planner, runtime, durable executor, vector database, knowledge graph, trained critic, observability SaaS, or guardrail framework. Its state lasts only for the invocation and immediate repair. It therefore passes the anti-overfit gate. The default `argv` route is also an intentional reduction in representational power: most commands should not pay the shell-language failure surface when they need only process arguments.

## Mechanism 2: automation-mode awareness and command preview

### How it works in aviation

NASA describes an automation surprise as automation behaving differently from what the pilot expects even when it behaves as designed. Its study of 184 ASRS mode-awareness reports attributed cases to categories including data-entry mistakes, failure to detect or anticipate a mode transition, insufficient avionics knowledge, and crew coordination; categories overlapped ([NASA TM 1998-112217, “Automation Surprises”](https://humanfactors.arc.nasa.gov/publications/20051025132410_aiding_vg_understanding_tm.pdf)). NASA's A-320 research record defines mode awareness as understanding the automation's current and future status and behavior ([NASA NTRS 20040112190](https://ntrs.nasa.gov/citations/20040112190)).

FAA AC 25.1302-1 turns that research into interface criteria: operationally relevant behavior should be understandable, predictable, and unambiguous; the crew should know what a system is doing and why; feedback should distinguish commanded state, in-process state, initiated action, and actual state. If input is not accepted, that fact should be clearly indicated ([FAA AC 25.1302-1 §§5-2, 5-4, 5-6](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf)).

### Why the structure transfers

Implicit execution mode is an agent-tool version of mode confusion. A text such as `$x`, `^`, quotes, glob characters, or command substitution has different behavior depending on interpreter, invocation style, and operating system. A generic “command failed” reports neither what mode was selected nor what the system actually accepted. Making mode and state visible is a direct structural match.

### Proposal 2 — Mode annunciator and phase-state receipt — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Extend the Proposal 1 receipt with a compact, always-machine-readable state record:

```text
MODE=bash  PHASE=preflight  PARSER=bash-5.x  CWD=/work
RECEIVED=184_bytes  PARSE=failed  EXECUTED=false
ERROR_CLASS=syntax.unclosed_single_quote  SPAN=line:1,col:47..end
NEXT_SAFE_ACTION=replace script span or switch to argv mode
```

State transitions are fixed: `received → preflight → launched → running → exited|timed_out|cancelled`; failures must name the phase. The tool must separately report **commanded** content (the submitted envelope), **accepted** content (parser/launcher receipt), and **actual** outcome (exit, signal, timeout, side-effect verification if the caller requested one). This maps directly to FAA's distinction between commanded state, action-in-process, initiated action, and actual state ([FAA AC 25.1302-1 §5-4.f](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf)).

This is **likely (55-80%)** to reduce wrong-shell retries and “automation surprise” loops because the error names the active interpreter and phase rather than making the agent infer them; evidence is NASA's mode-awareness classification and FAA's predictable/unambiguous behavior requirement. The harness effect is **UNVERIFIED; settle it with an A/B evaluation containing paired Bash/PowerShell traps, scored on correct first repair and absence of same-class recurrence within three calls**.

What it catches or exposes beyond ordinary stderr:

- parse failure versus executable-not-found versus runtime nonzero exit;
- timeout versus a command that never launched;
- caller belief that argv was passed directly when a shell actually reparsed it;
- wrong cwd or wrong interpreter as first-class causal facts;
- a rejected input that otherwise looks like an executed failure.

## Mechanism 3: alert design that supports correction rather than error-code archaeology

### How it works in aviation

FAA AC 25.1322-1 says alerts should occur only for conditions requiring awareness, provide information needed to identify the condition and determine corrective action, use consistent presentation, prioritize the most urgent condition, and minimize false/nuisance alerts because they increase workload and can cause real alerts to be ignored. Its recommended visual format contains a general heading, specific subsystem/location, and nature of condition; voice information should be descriptive, concise, and consistent with the visual message ([FAA AC 25.1322-1 §§5, 8, 12 and appendices](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_25.1322-1.pdf)).

FAA AC 25.1302-1 adds a particularly relevant rule: an alert after operator error is insufficient if it does not directly relate to the error or if it leaves error indistinguishable from other causes; additional information must enable identification and correction ([FAA AC 25.1302-1 §5-7](https://www.faa.gov/documentlibrary/media/advisory_circular/ac_25_1302-1.pdf)).

### Proposal 3 — Three-part causal error contract — UNVERIFIED — NATIVE-vs-BUILD: CONFIG (settings/JSON only)

Standardize tool errors on the existing bus as:

```json
{
  "severity": "error",
  "phase": "preflight",
  "system": "bash.parser",
  "condition": "syntax.unclosed_single_quote",
  "location": {"line": 1, "column": 47, "end": "eof"},
  "actual_state": {"executed": false, "cwd": "/work"},
  "correction": {
    "preferred": "use argv mode for this single executable",
    "alternative": "close or remove the quote at the reported span"
  },
  "invocation_id": "...",
  "fingerprint": "..."
}
```

The three human-factors fields are **system/location**, **condition**, and **corrective route**—the direct translation of the FAA alert format. Raw stderr remains available as evidence but is not the primary interface. Only the highest-priority causal error is placed first; cascading consequences are nested under it. Duplicate alerts within one invocation are coalesced, while a still-active critical condition remains visible. This applies the FAA's warning against nuisance alerts rather than producing a verbose “safety” banner on every call.

This contract is **likely (55-80%)** to improve first-repair accuracy for parser failures because it disambiguates operator input error from system fault and supplies an exact extent; the support is FAA AC 25.1302-1's error-detectability criterion and AC 25.1322-1's condition/correction criterion. It is **UNVERIFIED; settle it by replaying a stratified sample of quote, executable-resolution, permission, timeout, and runtime failures to blinded agents, comparing correct causal classification and calls-to-recovery against raw stderr**.

Configuration-only is appropriate because the parser adapter in Proposal 1 already produces the facts; Proposal 3 only standardizes their schema, ordering, and rendering. If the existing bus cannot transform errors declaratively, this proposal's tag must be revised to BUILD-SMALL rather than silently expanding its scope; that implementation premise is **UNVERIFIED; settle it by a schema-capability inspection before scheduling work**.

## Mechanism 4: interruption-resilient checklist state

### How it works in aviation

The NASA/FAA checklist report documents that interruptions displace the operator's working-memory “pointer.” A verbal “hold on…item” was rarely used in practice; paper checklists did not visibly distinguish completed from incomplete items. One safe recovery was restarting a short checklist from the beginning. The report recommends explicit completion calls, smaller chunks, critical items early, and buffers that decouple checklist completion from external pressure ([NASA/FAA checklist report §§5.4.2, 7.1 and final guidelines](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). It also warns that long lists may be skipped or performed poorly and that checklist responses should state actual values, not “checked” ([same report §§3.1.5 and 6.2.3](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)).

### Proposal 4 — Stable repair pointer, not a universal agent checklist — UNVERIFIED — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

On a rejected shell call, retain the validated envelope under a short-lived invocation ID and return the exact faulty span plus allowed patch fields. A retry can say, conceptually, “replace `script[47..EOF]`” or “convert this envelope to argv mode,” while cwd, timeout, and already-validated arguments remain stable. Expire the state at turn/task boundary; do not create durable workflow state.

For commands crossing a high-risk boundary, run a **machine checklist**, not a prose checklist:

1. execution mode explicit;
2. parser accepted exact content;
3. cwd/executable resolved;
4. argument boundaries recorded;
5. execution begins only after the above state is complete.

This is **likely (55-80%)** to reduce repair-induced regressions because it externalizes the interrupted state pointer and prevents whole-command reconstruction; evidence is aviation interruption research plus the supplied observation that failures occur in retrying shell commands. It is **UNVERIFIED; settle it by measuring how often a repair changes fields unrelated to the diagnosed span and by comparing recurrence rates with stateless retry**.

A universal natural-language preflight checklist is rejected. It would be long, frequent, easy to ritualize, and would consume attention on low-risk calls—the exact failure modes identified in checklist and nuisance-alert research ([NASA/FAA checklist report](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf), [FAA AC 25.1322-1](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_25.1322-1.pdf)).

## Mechanism 5: system-centered incident learning (the useful part of “blameless”)

### How it works in aviation

NASA's ASRS makes reporting voluntary, confidential, de-identified, and protected from enforcement use within defined limits. It does not provide blanket immunity for accidents or criminal conduct. NASA states that more than one million reports have been submitted and describes removing names and generalizing identifying details ([ASRS confidentiality](https://asrs.arc.nasa.gov/overview/confidentiality.html), [ASRS immunity policies](https://asrs.arc.nasa.gov/overview/immunity.html)). The FAA's maintenance program independently says “blame-and-train” responses do not effectively reduce failure to follow procedures and instead calls for systematic countermeasures across organizational levels; it provides a Maintenance Error Decision Aid for structured investigation ([FAA Procedural Non-Compliance](https://www.faa.gov/about/initiatives/maintenance_hf/procedural_non-compliance)).

The lesson is not “nobody is accountable.” Aviation uses a **just** rather than blanket no-blame boundary. The relevant tool-design move is to stop encoding every repeated error as “the agent failed to follow instructions” and ask which interface, mode, feedback, workload, and environmental conditions made the error likely.

### Proposal 5 — Local incident/near-miss card and interface feedback loop — UNVERIFIED — NATIVE-vs-BUILD: CONFIG (settings/JSON only)

For each parser rejection or repaired preflight near miss, emit a local structured card through the existing event/corpus path:

- tool and interface version;
- mode, parser, OS family, and phase;
- normalized error class and source extent shape;
- whether argv mode was available/suggested;
- repair action and whether the same fingerprint recurred within three calls;
- eventual outcome;
- secrets removed before persistence.

Aggregate by **interface condition → repair → recurrence**, not by agent blame. A weekly design review should promote repeated patterns into one of three changes: eliminate an ambiguous input affordance, improve a causal error, or add a narrowly triggered automatic preflight. Do not add prompts merely saying “be careful with quotes.”

This is **likely (55-80%)** to identify high-leverage interface defects that aggregate error counts alone miss, because near misses and repair recurrence expose where recovery support fails; evidence is ASRS's use of incident reports for corrective system action and FAA's structured/systematic maintenance-error approach. The harness benefit is **UNVERIFIED; settle it with an eight-week prospective test in which the top weekly interface fingerprint must produce a shipped interface change, then compare its exposure-adjusted recurrence before and after**.

This proposal is CONFIG only if an existing local telemetry/corpus channel already accepts additional JSON event fields. That premise is **UNVERIFIED; the experiment is a read-only capability check by the implementation unit**. If no such channel exists, stop: do not introduce an observability service or daemon. A small emitter could be considered separately as BUILD-SMALL, but that is outside this proposal's authorized configuration scope.

### What does not transfer from ASRS

Confidentiality, immunity, and voluntary incentives solve fear and organizational retaliation among people. Agents do not possess those motivations, so copying an anonymous reporting portal would be cargo cult. De-identification still matters for owner privacy and secret handling, but that is a data-governance reason, not a motivational analogue. “Blameless” also must not suppress deterministic attribution: if the parser says the submitted script has an unclosed quote, the incident record should say so. The system-centered question is why the interface accepted a fragile representation and why its first error did or did not enable recovery.

## Rejected borrows and disanalogies

### Rejected: a second agent as the “other pilot”

The apparent CRM translation is to launch a verifier agent for every command. I reject it. The two outputs share model priors, prompt context, and often the same mistaken shell mental model; agreement is not an independent observation. It adds a second orchestration path and violates the anti-overfit gate. A parser result is cheaper and mechanically independent.

A second-agent verifier outperforming parser readback for semantic quoting errors is **roughly even (45-55%)** because it might catch intent mismatches but can also confidently share them; there is no evidence in the aviation sources about correlated LLM sampling. This premise is **UNVERIFIED; a settling experiment would compare same-model critique, different-model critique, and parser/argv enforcement on a held-out semantic-quoting suite**. Because the architecture cost is high and the evidence weak, it is not proposed.

### Rejected: a long “before every tool call” checklist

Aviation's own research warns that long checklists invite poor performance or nonuse, that more items can increase omission probability, and that critical items should be early and lists chunked ([NASA/FAA checklist report §§3.1.5, 7.1 and guidelines](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). Tool calls are far more frequent than flight-phase transitions. A verbose checklist on every call would become a nuisance alert and compete with the task. Automatic, risk-triggered machine checks are the transferable mechanism.

### Rejected: “standard phraseology” as prompt vocabulary alone

FAA standardized phraseology and readback reduce ambiguity in a noisy human radio channel; the Pilot/Controller Glossary exists to promote common understanding ([FAA Pilot/Controller Glossary purpose](https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/index.html)). But reserving words like “execute” and “confirm” in a prompt does not force correct argument boundaries. The useful translation is a typed vocabulary (`mode`, `argv`, `script`, `phase`, `condition`, `executed`) enforced by schema. Natural-language phraseology without a parser contract is rejected.

### Rejected: treating syntax acceptance as flightworthiness

`bash -n` proves only that Bash can read the script without a syntax error; GNU documents it as reading commands without execution ([GNU Bash `set -n`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)). It does not expand variables, prove files exist, establish correct intent, or make destructive actions safe. The receipt must say `PARSE=accepted`, never `SAFE=true`.

### Rejected: reproducing cockpit authority gradients

CRM addresses interpersonal hierarchy and assertiveness. A model/tool pair has no captain/first-officer employment hierarchy. The transferable part is the right of the independent verifier to stop progress on concrete disagreement. Anthropomorphic role assignments add ceremony without the human social structure that made CRM necessary.

## Integrated minimal design

The five proposals compose into one small path rather than five subsystems:

```text
agent intent
    ↓
typed envelope (argv by default; explicit Bash/PowerShell only when needed)
    ↓
native parser / launcher preflight  ← independent verification
    ↓
mode + phase + parsed-state readback
    ├─ disagreement → causal error + exact repair pointer → patched retry
    └─ agreement    → execution → actual outcome receipt
                         ↓
                local normalized incident/near-miss event
```

No component reasons about the task. No component stores long-term agent memory. No component schedules work. No component trains a critic. The design puts deterministic checks at the representation boundary where deterministic evidence exists.

Implementation priority:

1. **Typed argv default plus explicit shell mode.** Highest leverage because it removes quoting from calls that never needed a shell.
2. **Native parser preflight and `executed:false` readback.** Directly catches the measured unmatched-quote/EOF class.
3. **Causal error schema with exact span and phase.** Makes recovery measurable and reduces error-code archaeology.
4. **Stable invocation repair pointer.** Targets retry-loop recurrence.
5. **Near-miss aggregation.** Only after the execution contract emits reliable structured facts.

This ordering is **very likely (80-90%)** to produce more diagnostic value per line than starting with dashboards or richer prompting, because each earlier step generates the structured facts required by the next and all remain on the existing bus. The comparative efficiency is **UNVERIFIED; settle it by separately feature-flagging each layer and estimating marginal reduction in failures and calls-to-recovery per implementation line**.

## Acceptance experiments and falsification criteria

The borrow should be abandoned or narrowed if it fails these tests. Success cannot be claimed from implementation existence alone.

### Experiment A — historical syntax shadow replay

Input: all available unmatched-quote/EOF fingerprints plus a matched sample of successful shell commands. Run the exact requested interpreter preflight without execution.

Metrics:

- recall on true syntax failures;
- false rejection rate on historically successful commands;
- correct interpreter selection rate;
- fraction eligible for argv conversion.

Gate: advance only if recall is high and false rejection is low enough not to create a nuisance-alert regime. A reasonable numeric threshold is **UNVERIFIED; the experiment should plot the full error tradeoff before choosing one**, because no workload severity distribution was supplied.

### Experiment B — held-out first-repair trial

Construct failures spanning unmatched single/double quotes, nested substitution, whitespace in paths, literal metacharacters, wrong-shell syntax, unresolved executable, permission error, timeout, and syntactically valid semantic misquoting. Randomize agents to raw stderr versus causal receipt.

Primary outcome: correct first repair. Secondary outcomes: calls to recovery, unrelated-field mutation, same-fingerprint recurrence within three calls, and total tool-call overhead. ## Bottom line

The defensible aviation borrow is **not more procedural prose**. It maps well because shell interpretation is deterministic and externally observable. It must stop where intent becomes semantic: no amount of parser readback proves the command is the command the owner wanted.
