# G006 — Blind-spot analysis: capability gaps

**Unit:** G006  
**Date:** 2026-07-19  
**Scope:** What the captured Claude/Agents/Codex harness cannot currently do that a frontier agent system can do; static subject inspection plus the pinned historical corpus and current primary-source research.  
**Subject mutation:** none. The unpacked subject at `/local_disk0/codexwork/bundle` was read only.  
**Remote constraint:** the live Windows host and the original `C:\Users\Prekzursil\...` paths do not exist on this Linux job node. Live-process, entitlement, Windows sandbox, Task Scheduler, MCP-handshake, and transcript follow-up probes could not be run. Every conclusion below is limited accordingly.

## Executive verdict

This is not a capability-poor harness. It has already exercised browser/computer control, scheduled wakeups, dynamic tool search, durable memory, scientific tools, reverse-engineering tools, and multi-agent execution. The honest frontier gap is therefore not “add more tools.” It is that the harness cannot reliably **bound**, **discover**, **measure**, and **learn from** the capabilities it already has.

Four gaps survive the required paired-probe gate:

1. **Enforced contained autonomy:** the harness runs both primary providers with host-wide bypass/full-access defaults and the Codex wrapper explicitly says containment is post-hoc rather than sandbox-enforced. A frontier harness can run high-autonomy work inside an OS-enforced filesystem/network boundary.
2. **Live capability assimilation:** the proactive semantic router exists, but is not registered on either of the two inspected hook-registration surfaces; its snapshot predates the corpus by 19 days and indexes only 240 skills against the pinned approximately 355 installed. A frontier harness discovers current tools on demand and refreshes when the surface changes.
3. **Outcome-linked self-improvement:** the harness has strong local receipts, a shadow ladder, a narrow router regression benchmark, and taint primitives, but the general fitness reader is explicitly out of scope, shadow records have no outcome/cost/candidate link, and production never creates the provenance edges the taint query needs. A frontier system can turn reviewed failures into isolated eval targets, compare candidates against targeted and regression outcomes, and promote only measured improvements.
4. **Complete lifecycle sensing:** the shared registration captures 16 events and proves lifecycle hooks work, but omits current native `InstructionsLoaded`, `StopFailure`, and `SessionEnd`. Consequently, instruction provenance, API-terminal failure, and definitive session finalization fall outside the provider-neutral state machine.

A fifth, lower-priority gap is **causal multi-agent economics**: 1,745 historical Agent calls prove orchestration exists, but the declared `sibling_overlap` contract has no implementation and the ledger does not say whether a worker contribution affected the accepted result. The harness can fan out; it cannot establish when fan-out was worth its cost.

The highest-leverage replacement is not a new orchestration runtime. It is a small, measured control plane on the buses already present: native sandbox/permission boundaries, one live catalog, outcome-bearing receipts, and lifecycle-complete telemetry. It is **very likely (80-90%)** that this will improve trustworthy autonomy more than installing another large skill or MCP tranche, because the corpus already shows 93 MCP servers touched but only 78 of roughly 355 skills invoked, while the current router is unwired and the two providers default to unrestricted execution. The settling experiment is a fixed, repeated local task suite comparing current versus bounded+fresh-catalog+outcome-linked profiles on task success, pass^3, calls, wall time, false blocks, and operator interventions.

## 2. Current capability envelope: what is not a blind spot

The harness already covers much of the 2026 frontier surface:

- **Long-horizon execution:** background monitoring, scheduled wakeups, remote fleet descriptions, persistent goals, and compaction recovery are present (`claude/AGENTS.md:32-49`; `claude/CLAUDE.md:79-100`; `agents/harness/modules.py:1362-1528`).
- **Cross-vendor orchestration:** Claude can fan out to Codex over native MCP and use a live peer mailbox (`claude/CLAUDE.md:15-77`).
- **GUI/browser action:** historical calls prove real use, not merely installation.
- **Memory:** Basic Memory is canonical and actively used (`claude/CLAUDE.md:5-13`; corpus `basic-memory=1332`).
- **Verification:** typed receipt classes, mutation freshness, exact failed-command rerun matching, a claim warning, and fresh-context review substrate exist (`agents/harness/ledger.py:1054-1184`).
- **Risk hooks:** secret paths, destructive actions, force pushes, test tampering, prompt injection, stale anchors, and more have implementations. Their precision is a separate problem: the live defects file proves several use-versus-mention false positives.
- **Capability breadth:** the historical tool list includes scientific literature, chemistry, cloud execution, reverse engineering, browser automation, Figma, GitHub/GitLab, code quality, and OCR.

This matters because the correct design target is **reliable composition**, not feature-count maximization. OpenAI's April 2026 Codex product announcement shows the frontier moving toward computer use, image generation, memory, repeatable work, and more than 90 plugins (https://openai.com/index/codex-for-almost-everything/). This harness already has evidence for most of those categories. Its bottleneck is making that breadth trustworthy and legible.

## 3. Gap 1 — no enforced, verified containment for high-autonomy host work

### Falsifiable claim

The captured default profiles do not provide an OS-enforced least-privilege boundary for autonomous shell/tool work. This is **almost certain (90-99%)** for the captured configuration because Claude explicitly bypasses permissions across both drives (`claude/settings.json:26-75,693`), Codex selects never-approve plus danger-full-access (`codex/config.toml:6-7`), and the Codex wrapper explicitly bypasses sandboxing after finding workspace-write inert (`claude/agents/codex.md:32-47`). The remaining 1-10% uncertainty is whether an unbundled outer VM, AppContainer, WSL policy, or launcher constrains the whole process; the settling experiment is a disposable canary attempting one workspace write, one out-of-workspace write, one denied-secret read, and one disallowed network connection under every actual launcher, while observing from outside the sandbox.

This is a capability gap, not just a safety preference. Without containment the system cannot safely take the class of frontier actions “download/inspect/run untrusted code, execute long autonomous evals, or let multiple workers mutate isolated candidates” at maximum autonomy. It can still do those actions, but only by accepting host-wide blast radius or relying on model/hook judgment.

### Frontier comparison

Anthropic documents filesystem and network sandbox enforcement as complementary to permission rules: permissions govern tools; the sandbox constrains Bash and children even if hostile content affects model decisions (https://code.claude.com/docs/en/permissions). Its sandbox supports auto-allow within boundaries and `sandbox.failIfUnavailable=true`; on Windows it requires WSL2 (https://code.claude.com/docs/en/sandboxing). Anthropic's native auto mode adds a separate classifier for actions that exceed the request, target unknown infrastructure, or appear driven by hostile content, while explicitly warning it is not a safety guarantee (https://code.claude.com/docs/en/permission-modes).

OpenAI likewise describes native sandbox execution and controlled workspaces as a frontier Agents SDK primitive (https://openai.com/index/the-next-evolution-of-the-agents-sdk/). The exact product is less important than the architectural capability: the “hands” operate inside an enforceable boundary.

### Why existing hooks do not close it

The shared harness blocks selected dangerous actions and secret reads (`agents/harness/README.md:17-30`), but hooks are semantic policy checks in the same host trust domain. The known live defect D1 shows that several guards confuse mention with use, including a tool-result sentinel that told the agent to discard a successful result. A fallible classifier/pattern layer is not equivalent to an OS boundary.

### Proposal 1.1 — native Claude WSL2 sandbox profile — UNVERIFIED

**NATIVE (Claude Code already does this; we just enable it).** UNVERIFIED whether WSL2 and its required sandbox dependencies are ready on this host; the experiment is the outside-observer four-boundary canary plus representative builds. If ready, create a bounded profile using the native Claude sandbox with workspace-only writes, explicit network domains, `allowUnsandboxedCommands=false`, and `failIfUnavailable=true`; keep the interactive host profile separate. Do not claim success until the canary passes.

It is **very likely (80-90%)** that this enables materially safer unattended non-RE coding/eval work, because the official implementation enforces filesystem/network restrictions and the local `/start-task` policy already identifies WSL2 as the strongest available isolation for non-RE work (`claude/commands/start-task.md:25`). The uncertainty is WSL2 readiness and compatibility on this host; the settling experiment is the four-boundary canary plus representative build/test workloads.

### Proposal 1.2 — restore least-privilege interactive permissions

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace ordinary Claude `bypassPermissions` with native auto mode if the account/model is entitled, or a normal permission mode otherwise; remove the PowerShell launcher's forced bypass, remove whole-drive grants from the default, and keep narrowly scoped allow/deny rules. For Codex, make the non-elevated workspace-write profile the ordinary launcher only after its enforcement canary passes.

This is **likely (55-80%)** to reduce prompt-injection blast radius without reintroducing intolerable prompt friction, because auto mode is designed for that tradeoff and the current ask list is empty. The wide confidence band reflects account entitlement and classifier false-positive latency; settle with a one-week canary measuring approvals, false blocks, task success, and operator overrides against the current profile.

### Proposal 1.3 — containment attestation before autonomous lanes

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a read-only preflight to the existing dispatcher/profile launcher that emits a terminal receipt only after benign inside/outside/network canaries demonstrate the claimed boundary. Autonomous eval/fan-out skills require a fresh receipt; if unavailable, they fail closed or downgrade to propose-only.

This is **very likely (80-90%)** to prevent “sandbox by label” errors because it tests behavior, not configuration names, and directly addresses the observed Codex mode mismatch. The experiment is mutation testing: deliberately misconfigure each profile and confirm the attestation turns red while a correct profile remains green.

### Anti-overfit gate

These proposals reuse native sandboxing and the existing dispatcher/receipt bus. They add no second runtime, vector store, durable executor, trained critic, SaaS, or guardrail framework. A generic Docker/microVM control plane is explicitly not proposed: the recall index records `projects/learnings/microVM-OS-sandbox for autonomous loops — DEFERRED (do not re-suggest)` at `claude/hooks/recall-inject/index/recall_index.json:6858-6889`. Native WSL2 and verified profiles are the smallest un-rejected path.

## 4. Gap 2 — no live, trustworthy capability assimilation

### Falsifiable claim

The proactive semantic capability router is not active on either inspected Claude registration bus. This is **almost certain (90-99%)** for the captured files: `route.py` says it supersedes the lexical router “as the registered UserPromptSubmit router” (`claude/hooks/semantic-router/route.py:1-22`), but parsed `settings.json` and `_dispatch/manifest.json` independently contain zero route registrations while both detect their known-positive controls. A live host could have plugin/managed registration not captured here; `claude hooks` or a disposable UserPromptSubmit trace is the settling experiment.

The router snapshot is stale relative to pinned ground truth: `index/meta.json:1` says it was built 2026-06-29 with 240 skills, 39 MCPs, 16 agents, and 65 commands, whereas the July 18 corpus brief says roughly 355 skills installed and 22 agent types used. This does not prove every difference is a missing live item—the counts use different notions—but it proves the snapshot is not a current, complete representation. Audit A20's live name-aware comparison reported 54 live skills missing and 14 stale entries; because that is an earlier audit claim, a current name-aware rebuild/diff must settle the exact set.

### Frontier comparison

Anthropic's Tool Search Tool dynamically discovers deferred tools instead of loading all definitions. Its vendor-reported internal MCP evaluation improved Opus 4 from 49% to 74% and Opus 4.5 from 79.5% to 88.1%, while sharply reducing definition tokens (https://www.anthropic.com/engineering/advanced-tool-use). Those figures are vendor results, not a guaranteed local effect.

MCP itself provides `tools/list`, pagination, and `notifications/tools/list_changed` when a server's tool surface changes (https://modelcontextprotocol.io/specification/2024-11-05/server/tools and https://modelcontextprotocol.io/docs/learn/architecture). A frontier catalog can therefore be current by protocol event rather than a manually dated snapshot.

OpenAI's Codex app similarly lets installed skills be automatically selected based on the task and reports internal use of hundreds of skills (https://openai.com/index/introducing-the-codex-app/). Again, the relevant capability is automatic, current routing—not the number of files installed.

### What is and is not missing

Native `ToolSearch` is working: 5,091 calls with four errors. The gap is the layer that makes the whole local surface legible before the model knows which server/skill to search. With 78 skills invoked out of roughly 355 installed, the system cannot infer that the unused 277 are useless. It is **likely (55-80%)** that routing/discovery explains part of the unused tail because the proactive router is unwired and stale; the settling experiment is a randomized prompt suite comparing explicit-skill, native ToolSearch-only, and fresh-router conditions on correct skill selection. Conversely, the stale router can recommend removed names.

The current semantic implementation has valuable substrate:

- content-aware skill/agent/command indexing (`build_index.py:40-48,129-193`);
- MCP enrichment hooks (`build_index.py:196-225`);
- fail-open semantic plus lexical lanes (`route.py:18-22,164-225`);
- a success observer (`observe.py:1-71`);
- a narrow regression bench (`harness-bench/bench.py`).

The correct move is to make that existing path live and fresh, not add a trained router.

### Proposal 2.1 — wire one router and one observer

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** After the current payload tests pass, register exactly one `UserPromptSubmit` semantic router and update/register its success observer for current `Agent` as well as legacy `Task`; remove/supersede any duplicate lexical hook registration. Use native ToolSearch as the final tool-definition loader.

It is **very likely (80-90%)** that this restores proactive suggestions because the route code already emits provider-native additional context and the current absence is registration-level. The settling experiment is a disposable session with positive prompts for known current skills, paraphrase prompts, and pleasantry negatives, plus an observer check using current `Agent` rather than legacy `Task` names.

### Proposal 2.2 — atomic catalog refresh with known-positive gates

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing build/bench path so install/config-change events produce a candidate catalog outside the live path, then promote atomically only when: all four kinds are nonzero; named known-present controls are found; deletion/addition deltas are reported; vectors and rows agree; negative routing stays below threshold; and the candidate is at least as fresh as sources. A failed rebuild preserves the last known-good catalog.

It is **very likely (80-90%)** to eliminate silent stale-snapshot deployment because every stated failure is mechanically testable and the current builder already supports incremental reuse (`build_index.py:229-276`). The remaining risk is the embedding backend's live instability reported by A20; settle with cold/warm latency and failure injection while confirming lexical/native ToolSearch fallback.

### Proposal 2.3 — consume MCP list changes where the native host exposes them — UNVERIFIED

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** UNVERIFIED whether the installed Claude/Codex clients expose MCP `tools/list_changed` to hooks; the experiment is a disposable MCP server that advertises `listChanged`, adds a canary tool, sends the notification, and records whether either host refreshes or emits an observable event. If exposed, invalidate only that server's cached tool document. If not exposed, refresh on config/install changes and bounded SessionStart age instead.

This is **likely (55-80%)** to reduce catalog drift if the event is exposed, because MCP defines the notification semantics; local host plumbing is the unresolved premise.

### Anti-overfit gate

The plan reuses native ToolSearch, MCP, existing semantic/lexical files, the dispatcher, and the existing bench. It explicitly rejects a trained router: there is insufficient local outcome data to train or validate one, and the anti-overfit brief forbids a trained critic/router-like second intelligence layer without exceptional proof.

## 5. Gap 3 — no general causal loop from failure to measured harness improvement

### Falsifiable claim

The harness cannot currently demonstrate that a rule, skill, hook, memory, or orchestration change caused better end-to-end outcomes without regressions. This is **very likely (80-90%)**, supported by three independent implementation facts:

1. shadow events omit candidate, source-failure, receipt, outcome, and cost links (`agents/harness/modules.py:368-384`);
2. the fitness forcing function is explicitly out of scope (`agents/harness/modules.py:145-149`);
3. provenance/taint production edges are not written by captured production code even though the query and tests exist (`agents/harness/ledger.py:817-880,1186-1215`; test-only writers at `tests/test_ledger_receipts_and_taint.py:461-505`).

UNVERIFIED whether unbundled scheduled tooling or Basic Memory workflows join these records externally; this accounts for the 10-20% uncertainty. The settling experiment is to enumerate scheduled harness-fitness commands and schemas, then replay one known failure through candidate, targeted eval, regression eval, promotion, and recurrence query while requiring the same candidate ID at every edge.

This claim does not erase existing strengths. Typed receipts can prove a fresh test/build/lint/run after mutation (`ledger.py:1093-1184`). The router bench can detect recall regression. `/eval` defines useful vocabulary. What is missing is the causal join across a **general task outcome** and a **specific harness candidate**.

### Frontier comparison

Anthropic's January 2026 eval guidance defines a full eval harness as running tasks concurrently, recording trajectories, grading final outcomes, and aggregating results. It recommends isolated clean environments, repeated trials, balanced positive/negative tasks, reference solutions that validate graders, deterministic outcome graders where possible, and pass@k/pass^k rather than single lucky runs (https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

OpenAI's May 2026 Tax AI account shows a bounded deployed loop: reviewed recurring corrections become structured eval targets; Codex inspects trace, eval, repo, and skills; targeted and broader regression evals gate a candidate PR; ambiguous cases go back to humans (https://openai.com/index/building-self-improving-tax-agents-with-codex/). This is first-party case-study evidence, not an independent causal ablation, but it is a concrete frontier capability.

Google DeepMind's AlphaEvolve goes further in evaluator-rich algorithm domains by generating programs, scoring them with objective automated evaluators, and evolving promising candidates (https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/). That architecture is evidence that bounded evaluator-driven exploration can exceed one-shot editing; it is not evidence for unattended mutation of a general personal harness.

### Proposal 3.1 — outcome-bearing candidate receipt

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one additive event shape to the existing ledger:

`candidate_id, source_failure_id, surface_hash, task_suite_hash, profile_hash, trial, outcome, grader_hash, receipt_refs, calls, elapsed_ms, token_or_cost_if_available, regression_outcome, reviewer_decision, supersedes`.

No prose is treated as success. Candidate promotion requires a deterministic final-state or test receipt when the task permits it; model graders are optional and calibrated separately. This is additive to `ledger.append`, not a new database.

It is **very likely (80-90%)** to make harness changes causally auditable because it supplies the missing join keys while preserving the existing receipt and supersession model. The experiment is a deliberately good and deliberately bad candidate: the good candidate must link fail→pass plus regression pass; the bad candidate must be rejected and remain queryable.

### Proposal 3.2 — small deterministic lifecycle trace suite

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a pytest parameter table that drives the existing dispatcher against fresh temporary roots for the highest-damage lifecycle traces: benign/malicious use-versus-mention pairs; malformed input; stale-green then exact rerun; compact/resume goal isolation; hollow/substantive handoff; repeated failure/recovery; provider render parity; concurrent append; and a module exception followed by later-module execution. Grade action, reason, context, and final state—not prose trajectory.

This is **very likely (80-90%)** to catch harness regressions that 511 unit tests can miss, because the proposed cases cross event boundaries while reusing deterministic APIs. The settling test for the benchmark itself is mandatory: a known-good reference trace passes, and no-op/malformed mutants fail. Audit D10 independently reached the same design from the dispatcher/test surface; the local direct evidence is `dispatcher.py:235-338,518-556`, `registration.py:17-53`, and the existing pytest suite.

### Proposal 3.3 — reviewed failure-to-eval promotion

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `/eval` or a skill—not a daemon—to convert an owner-confirmed repeated fingerprint into a versioned target fixture. Require recurrence or explicit nomination, a falsifiable precondition, a known failing reference, targeted fail→pass, broader pass^3, and human approval before a canonical hook/rule/skill changes. Candidate changes first run shadow/advice where applicable.

It is **likely (55-80%)** to reduce recurring harness failures over months because it follows the bounded loop in the OpenAI case study and uses this harness's existing 5,692 error fingerprints and 2,268 correction candidates. The wide band reflects the unlabeled/noisy nature of those candidates; settle by sampling and labeling 100 candidates, then tracking precision, recurrence reduction, false promotion, reviewer minutes, and rollback for a quarter.

### Proposal 3.4 — evaluator-rich optimization lane, not general self-editing

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Encode in the existing optimization skill that `autoresearch`/benchmark optimization is permitted only for surfaces with cheap objective metrics and isolated candidate worktrees: router rank@k, hook precision on labeled fixtures, latency, test coverage, compression ratio, or algorithm benchmarks. Freeze criteria within a run and require regression receipts. Do not allow the lane to rewrite core safety policy or its own graders.

It is **likely (55-80%)** to produce useful improvements in those narrow domains because AlphaEvolve demonstrates evaluator-driven search in quantifiable problems and the index already contains `autoresearch` and `benchmark-optimization-loop` skills (`semantic-router/index/meta.json:1`). It is **unlikely (20-45%)** to safely improve qualitative general policy without human grading, because the evaluator can be gamed or encode the wrong target; the settling experiment is a held-out benchmark plus manual review of top candidates and evaluator exploits.

### Anti-overfit gate

This design intentionally does not add a durable-execution engine, trained critic, observability SaaS, vector/KG store, or second orchestrator. It uses pytest, the dispatcher, JSONL ledger, existing `/eval`, worktree isolation, and human review. The general self-improvement mechanism is a small promotion protocol, not recursive self-rewriting.

## 6. Gap 4 — lifecycle-incomplete provider-neutral state

### Falsifiable claim

The captured shared harness cannot observe three current Claude lifecycle facts: which instructions were loaded, when a turn ended due to API failure, and why a session ended. This is **almost certain (90-99%)** for the captured registration because two independent local registration surfaces omit `InstructionsLoaded`, `StopFailure`, and `SessionEnd` while containing validated known-positive events (`agents/harness/registration.py:17-34`; `claude/settings.json:81-533`). Anthropic documents those events in the current hook guide (https://code.claude.com/docs/en/hooks-guide). The settling experiment is a disposable live Claude session that fires one nested instruction load, one safely induced API/invalid-model failure, and one exit/clear, then captures raw hook input.

Why this is a frontier capability gap rather than mere telemetry polish:

- dynamic nested instructions can change agent policy without entering the ledger;
- Stop-only completion accounting misses a terminal class when the model/API fails;
- background/task cleanup has no definitive provider-neutral session boundary;
- a self-improving harness cannot attribute failures to policy/version/context if it cannot observe which instructions were actually loaded.

### Proposal 4.1 — register the three native events

## 7. Gap 5 — fan-out without causal contribution or marginal-cost evidence

### Falsifiable claim

The harness can fan out but cannot determine from its own records whether a sibling worker was redundant or changed the accepted result. This is **very likely (80-90%)** because:

- the corpus proves substantial orchestration (`Agent=1,745`, `SendMessage=500`), establishing the known-positive;
- `sibling_overlap` occurs once in active harness Python, only as a declared contract at `agents/harness/modules.py:222-227`, with no stage/module implementation;
- shadow records lack worker, overlap, contribution, accepted-result, call, token, and elapsed fields (`modules.py:368-384`);
- structured handoff enforcement exists (`modules.py:2331-2418` per audits D08/D25), so the missing feature is outcome linkage rather than handoff text.

The 10-20% uncertainty is external Workflow/Agent View telemetry not bundled here. A settling experiment dispatches fixed tasks under single-worker, two-independent, and duplicated-worker prompts; it then asks whether existing logs alone can attribute accepted evidence and total cost to workers without transcript interpretation.

### Frontier comparison

The Codex app is explicitly designed to supervise coordinated teams and parallel long-running agents (https://openai.com/index/introducing-the-codex-app/). Anthropic's eval guidance requires calls, turns, tokens, latency, repeated trials, and final outcomes to interpret an agent system (https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). The frontier capability is not “spawn N”; it is selecting an architecture based on measured reliability and cost.

### Proposal 5.1 — contribution receipts at structured handoff

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At SubagentStop/TaskCompleted, record worker ID hash, task/template hash, evidence hashes, parent acceptance/rejection, accepted evidence hashes, elapsed time, and available call/token counts. Compute exact evidence-hash reuse first; do not introduce embeddings. The parent explicitly names which evidence it used in the existing structured handoff contract.

It is **likely (55-80%)** that this will identify a meaningful redundant-worker tail, because many workloads use homogeneous general-purpose workers and the current system has no diversity gate. It is **roughly even (45-55%)** that pruning based on it will improve net task success; independent workers may be valuable witnesses even when their text overlaps. Settle with paired repeated trials reporting pass^3, total cost, wall time, and unique accepted evidence.

### Proposal 5.2 — static policy before adaptive routing

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Encode in the existing orchestration skill that, until contribution data exists, one worker is the default; use explicit parallel templates only for independent file/domain partitions, genuinely independent verification, or high-stakes select@N where visible tests reject candidates. Report select@N/pass@N honestly with total cost.

It is **likely (55-80%)** to reduce waste without losing much capability because the existing corpus is dominated by general-purpose agents and independent decomposition remains available. The settling experiment is the same stratified single-versus-parallel suite; no adaptive selector should be built before it produces enough labeled outcomes.

### Anti-overfit gate

This proposal adds scalar/hash fields to the existing lifecycle ledger. It explicitly avoids a multi-agent scheduler, learned router, semantic overlap service, or observability platform.

## 8. Prioritized replacement/evolution decision

### Recommended architecture

Keep the minimal provider-native execution loops and replace the current **implicit trust/control story** with four explicit contracts:

```text
native Claude/Codex loop
        |
        +-- verified execution profile receipt (boundary proven, not named)
        |
        +-- one current catalog -> native ToolSearch / MCP call
        |
        +-- existing dispatcher + complete lifecycle events
        |
        +-- additive outcome/candidate/contribution receipts
        |
        `-- pytest + /eval promotion gate -> reviewed config/rule/skill candidate
```

This is evolution of the execution plane but a genuine replacement of three weak abstractions:

- replace “bypass plus regex guards equals safe” with proven native containment plus narrow guards;
- replace “installed inventory plus dated embedding snapshot equals discoverable” with one fresh catalog plus native ToolSearch;
- replace “more hooks/lessons means improvement” with candidate-linked outcomes and regression gates.

It is **very likely (80-90%)** that full replacement of the agent loop itself would be worse than this control-plane replacement, because the corpus proves broad successful use of native tools, multi-agent calls, MCP, memory, scheduling, and browser control, while the strongest gaps sit at their boundaries. The settling experiment is an ablation: same model/tasks/budgets under (A) current native loop, (B) proposed bounded/fresh/measured loop, and (C) any replacement runtime candidate; require C to beat B on pass^3 and cost without losing capability coverage before migration.

### Order of operations

1. **Containment canaries and profiles.** Do not increase autonomous scope before the boundary is behaviorally proven.
2. **Wire/freshen the catalog.** This unlocks installed capability without installing more.
3. **Complete lifecycle events.** Outcome evidence needs complete terminal/context facts.
4. **Add candidate/outcome receipts and deterministic traces.** Establish a trustworthy hill-climbing signal.
5. **Measure multi-agent contribution.** Optimize fan-out only after success measurement exists.
6. **Then consider new frontier modalities/plugins.** A new capability must enter the same catalog, boundary, receipt, and eval contracts.

## 12. Final answer to the AGI-ambition question

What can this harness not do that a frontier system can?

It cannot yet take its enormous action surface and turn it into **trustworthy compounding autonomy**. Specifically, it cannot prove that autonomous actions are contained; it cannot keep its proactive view of available capabilities current; it cannot causally connect a failure, a harness change, and a later outcome; it misses native lifecycle facts needed for that connection; and it cannot tell whether additional agents added value.

Those are falsifiable statements with settling experiments, not claims that the harness lacks intelligence. In fact, the breadth already present makes these control gaps more important: 93 MCP servers, unrestricted host access, and 1,745 agent calls amplify both upside and failure radius.

The ambitious design is therefore not maximal scaffolding. It is a harness that can say, with evidence:

1. **I know what I can use now.**
2. **I know where my actions are physically bounded.**
3. **I know what outcome occurred, not merely what I said occurred.**
4. **I know which change and which worker caused the improvement.**
5. **I can reject my own proposed harness change when held-out evidence says it made things worse.**

Achieving those five properties on the existing native buses is **very likely (80-90%)** to move this owner closer to a frontier harness than adding another orchestration layer, because each property directly addresses a proven boundary failure while remaining model-agnostic as models improve. Only a controlled ablation can settle the magnitude; the artifact deliberately does not invent one.
