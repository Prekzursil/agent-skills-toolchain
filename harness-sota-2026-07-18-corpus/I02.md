# I02 — Anticipating the next need: initiative / anticipation calibration

## Executive answer

The useful frontier is not “guess the owner's next request and do it.” It is **selective anticipation**: predict quietly, prepare only the cheap/reversible parts, preserve every discussed thread, and surface or execute a prediction only when its expected benefit exceeds its asymmetric error cost. A wrong prediction can cost more than wasted compute here: it can interrupt focus, create unauthorized state, steer work onto an unreliable tool, or crowd a real thread out of context. The system therefore needs separate decisions for **predict**, **prepare**, **ask**, **surface**, and **act**.

The strongest local signal is repeated demand for continuation and completeness: the corpus detector groups 524 instances of “do not stop,” 77 of implementing opportunities found along the way, 34 of proceeding with everything required, 30 of taking all logical steps, and 12 of “why did you stop” (`/local_disk0/codexwork/bundle/inputs/corpus.json:10377-10426`). These are useful hypotheses, not verified counts of owner corrections: the same corpus warns that its correction miner is recall-biased and that 41/41 items in an unfiltered smoke sample were agent-authored false positives (`corpus.json:10371-10374`). I therefore infer a preference for momentum from the repeated normalized language, but do not infer carte-blanche authority from the counts.

The harness already contains most of the right substrate. `calibrated_silence.py` treats interjection as a learned signal-detection decision, uses the owner's later behavior as the signal, includes fatigue and density, is fail-open, and exposes only a small importable bus (`/local_disk0/codexwork/bundle/claude/hooks/calibrated-silence/calibrated_silence.py:2-53,94-124,381-428`). Its reaction logger explicitly resolves outcomes from the next user turn or a matching tool execution rather than same-context self-assessment (`.../calibrated-silence/log_reaction.py:2-27,118-151`). The event ledger is append-only, typed, hook-written, and replayed rather than trusting a self-summary (`.../event-ledger/ledger.py:2-13,61-65`); recovery already replays goals, open failures, decisions, and live Git HEAD drift (`.../event-ledger/sessionstart-replay.py:31-63`). `persist-nudge` is one-shot and fail-open (`.../persist-nudge/nudge.py:2-15,131-186`). Consequently, this unit proposes **no new hook, no new agent runtime, and no new memory store**.

My central forecast is **very likely (80-90%)**, based on the repeated continuation language, the owner's hard “never drop a thread” constraint, and mixed-initiative/proactive-agent evidence below: the owner wants the harness to arrive at the next decision with evidence and reversible preparation already in hand, while remaining quiet when the prediction is weak. It is only **likely (55-80%)**, based on the unreliable intent labels and the lack of a historical prediction-outcome field, that any particular next-need category can initially be predicted accurately enough to surface. That distinction drives the shadow-first design.

## Findings — inferred surprises first

### 1. UNVERIFIED — Shadow next-need forecasts before any proactive behavior

**improvement:** Add a silent, falsifiable “next need” forecast lane to the existing event ledger.

**what it is:** At a task boundary, record at most three typed candidates such as `verify_result`, `continue_declared_plan`, `diagnose_failure`, `compare_alternative`, `package_handoff`, `live_test`, or `return_to_thread:<id>`. Each row contains `prediction_id`, `context_key`, `need_type`, `horizon` (next turn / next task), `p_need`, `evidence_refs`, `expires_at`, and `mode=shadow`. It is not injected into the prompt and cannot trigger a tool. The next UserPromptSubmit or objective tool/receipt resolves it as `hit`, `miss`, `superseded`, or `unobservable`.

**why-inferred:** The owner asks for opportunities found along the way and logical next steps, while also making prompt fatigue and wrong inference first-class. The normalized corpus patterns support momentum (`corpus.json:10381-10394`), but the correction detector's 41/41 false-positive warning makes immediate enforcement reckless (`corpus.json:10371-10374`). The harness currently scores only interjections that were surfaced; `record_interjection` stores type/context/reaction (`calibrated_silence.py:198-223`), so it cannot measure counterfactual predictions that correctly stayed silent.

**how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the event-ledger `KINDS`/fields rather than create a store. Invoke the predictor inside the existing Stop/TaskCompleted dispatcher lane; write only shadow rows. Extend the existing UserPromptSubmit reaction pass to match the future owner turn and external receipts. Start with deterministic transition templates, not another model: completed code edit → likely verification; failed tool → diagnosis/retry alternative; explicit numbered plan → next incomplete item; mentioned/deferred thread → later resurface candidate. Cap at three, TTL one task/24h, and store hashes or typed keys rather than raw sensitive prompts.

**the EXTERNAL signal that verifies it:** The subsequent owner turn, a subsequently invoked tool keyed to the predicted need, a task-state transition, or an executable receipt. Same-context “looks right” never labels a hit. Offline, replay predictions against later events. The premise that these seven need types cover useful transitions is **UNVERIFIED; the experiment that settles it is a 100-session shadow replay with a manually verified stratified sample and per-type precision/recall**. Benefit is **likely (55-80%)**, because real-work history helps proactive prediction in ProAgentBench, but this owner's available labels are noisy.

**SOTA citation with URL:** [ProAgentBench](https://arxiv.org/abs/2602.04482) separates “when to assist” from “how to assist,” uses 28,000+ events from 500+ hours of real sessions, and reports gains from long-term/history context; it also argues synthetic data misses real decision patterns. [PRISM](https://arxiv.org/abs/2602.01532) frames proactivity as cost-sensitive selective intervention and reports a 22.78% false-alarm reduction and 20.14% F1 gain on ProactiveBench.

**value x effort:** high x low  
**novelty:** inferred-surprise

### 2. UNVERIFIED — A prediction may prepare evidence, but authority is a separate gate

**improvement:** Split anticipation into a five-rung action ladder: observe → prefetch → stage → ask → commit.

**what it is:** A likely next need earns preparation proportional to reversibility, not permission to execute it. `observe` records only; `prefetch` performs bounded read-only discovery or liveness checks; `stage` may create an explicitly temporary/diffable artifact or checkpoint; `ask` uses AskUserQuestion only for a material branch; `commit` performs the owner-authorized mutation. Prediction confidence never widens task scope.

**why-inferred:** The owner repeatedly requests momentum, but the local live-defect record shows how a fabricated constraint spread to about 15 prompts and diverted writes into a 13.6%-failure workaround (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-161`). A confident anticipation can propagate the same way. Existing edit checkpoints and rollback make staging cheaper than committing; the corpus also shows read/write paths are materially more reliable than PowerShell and Glob (`corpus.json:23-50,79-84`).

**how-to-build:** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Add an action-class table consumed by calibrated-silence/Workflow: `read_local`, `search_docs`, `health_probe` = prefetch; `temp_patch`, `draft_plan`, `checkpoint` = stage; `edit_in_scope` = commit only when already authorized by a build/change request; `send/publish/install/delete/expand_scope` = ask. Bounded speculative budget: ≤2 read-only calls or ≤10 seconds; no metered MCP; no owner-visible question unless the branch changes outcome. Staged work receives `prediction_id`, TTL, and exact discard path.

**the EXTERNAL signal that verifies it:** Tool result/liveness response verifies prepared evidence; checkpoint/diff plus a disposable replay verifies reversibility; the owner's explicit response verifies any branch or expanded authority. The claim that this ladder reduces latency without increasing unwanted state is **UNVERIFIED; settle it with an A/B shadow replay measuring time-to-first-useful-action, discarded staging, and unauthorized-mutation count**. It is **very likely (80-90%)**, based on the cost asymmetry and existing checkpoint bus, that read-only preparation is safer than speculative mutation.

**SOTA citation with URL:** Horvitz's [Principles of Mixed-Initiative User Interfaces](https://erichorvitz.com/uiact.htm) grounds mixed initiative in goal recognition, user modeling, probability, and decision theory while coupling automation with direct manipulation. The validated [Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/) call for contextual timing, efficient dismissal/correction, scoping service under uncertainty, cautious adaptation, and global controls.

**value x effort:** transformative x low  
**novelty:** inferred-surprise  
**autonomy:** just-do-it for observe/prefetch; confirm-first for expanded scope or irreversible/external action

### 3. UNVERIFIED — Price a wrong prediction by action and context, not a global hit rate

**improvement:** Upgrade calibrated silence from `p_useful × type_value` to asymmetric expected regret.

**what it is:** Retain its learned reaction rate and fatigue proxy, but add `false_alarm_cost`, `miss_cost`, `execution_cost`, `reversibility`, `focus_state`, and `p_accept`. The same prediction can silently prefetch at low confidence, surface at higher confidence, and mutate only under authorization. A false “run tests next” prediction is cheap if it merely locates the command; a false “change architecture next” prediction is expensive even if dismissed.

**why-inferred:** The existing gate has per-interjection values but one base threshold and a cold-start allow policy (`calibrated_silence.py:94-124,401-426`). That is good for avoiding total silence, but it does not distinguish a one-line suggestion from an expensive tool run or state mutation. The corpus's tool error rates differ by more than two orders of magnitude—ToolSearch 0.08% versus StructuredOutput 22.9% (`corpus.json:87-106`)—so execution cost is not interchangeable. The owner's prompt-fatigue constraint makes a false visible alarm costlier than an unseen miss in ordinary contexts.

**how-to-build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `should_interject(itype, context)` rather than add a hook. Compute `EU(surface)=p_need*p_accept*benefit - (1-p_need)*false_alarm_cost - execution_cost`; compare with `EU(silent)=-p_need*miss_cost`. Near the boundary, do not ask the same model to reconsider; request an external cheap probe, a different-context verifier, or owner confirmation depending on stakes. Cold start defaults to silent shadow/prefetch, not visible interjection, except safety/thread-loss cases.

**the EXTERNAL signal that verifies it:** Next-turn owner behavior, actual tool use, executable result, and discard/rollback events populate separate regret terms. Weekly calibration reports expected calibration error/Brier score plus realized cost, never a model's self-grade. Exact cost weights are **UNVERIFIED; settle them by fitting on shadow outcomes and then a reversible two-week canary with an owner-visible global off switch**. A cost-sensitive gate is **very likely (80-90%)** to beat a global threshold for this harness because local action costs are demonstrably heterogeneous.

**SOTA citation with URL:** [PRISM](https://arxiv.org/abs/2602.01532) explicitly derives the intervention threshold from asymmetric false-alarm/miss costs and reserves slow reasoning for near-boundary cases. [To Trust or to Think](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml) found cognitive forcing reduced overreliance in an N=199 experiment but received the worst subjective ratings when strongest, directly demonstrating that correctness interventions themselves impose user-experience cost.

**value x effort:** transformative x medium  
**novelty:** inferred-surprise  
**autonomy:** confirm-first (cost weights change visible behavior)

## What history can and cannot predict

The most defensible initial predictions are structural rather than personal:

1. After a mutation, verification or live-use evidence is likely next. This is **very likely (80-90%)**, based on the owner's quality law, existing truth/checkpoint buses, and the corpus's heavy Read/Bash/Edit sequence opportunity; the exact transition rate is UNVERIFIED until raw event replay is run.
2. After a failed tool, diagnosis plus a healthy fallback is likely next. This is **very likely (80-90%)**, based on measured tool error heterogeneity and the dead-MCP ground truth.
3. After an explicitly numbered plan, the next incomplete step is likely next. This is **likely (55-80%)**, based on repeated “all logical steps/nothing skipped” patterns, weakened by the correction miner's false positives.
4. A discussed/deferred item will need resurfacing at its declared condition. This is **almost certain (90-99%)** as a normative owner requirement (“never drop a thread”), but predicting *when* without a recorded condition is **roughly even (45-55%)**; therefore capture the condition instead of guessing the time.
5. Communication style or domain preference transferred across unrelated projects is **unlikely (20-45%)** to be safe without scoped evidence, because the observed continuation patterns mix autonomous loops, research, and ordinary tasks.

The corpus does not provide a trustworthy direct measure of wrong-prediction cognitive cost. It provides technical errors, repeated normalized language, and noisy correction candidates. **UNVERIFIED whether raw transcripts contain enough owner accept/dismiss outcomes to estimate that cost; the experiment is a read-only labeled sample of actual owner turns joined to immediately preceding proactive suggestions, with two independent reviewers or owner adjudication for disagreements.** Until then, use an ordinal cost matrix:

| Wrong prediction action | Default cost | Rationale / safe response |
|---|---:|---|
| silent shadow record | very low | storage/compute only; expire it |
| bounded local read or health probe | low | small latency; cache with TTL |
| visible optional suggestion | medium | attention/trust cost; batch or suppress |
| unnecessary AskUserQuestion | medium-high | interrupts focus and transfers work to owner |
| speculative in-scope reversible stage | medium-high | creates cleanup/review burden; checkpoint + TTL |
| unauthorized mutation, metered run, external send, install, or deletion | unacceptable | confirm first; prediction never grants authority |
| silently dropped real thread | unacceptable | reconcile typed thread state and require resolution receipt |
