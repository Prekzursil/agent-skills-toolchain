## Executive verdict

The Java testing rule is not a coherent, enforceable extension of the common testing contract. Its Java examples are useful, but its normative layer has three distinct problems:

1. It replaces the common repository-owned coverage threshold with a fixed `80%+` target. Because the rules' own priority document says language-specific rules override common rules, this can lower a metaswarm project's required 100% threshold. This is a real **CONTRADICTION**, not harmless duplication (`claude/rules/java/testing.md:122-126`; `claude/rules/common/testing.md:23,38`; `claude/rules/README.md:93-98`).
2. The prescribed TDD helper is internally Java-incoherent. The Java rule selects JUnit 5, AssertJ, Mockito, Testcontainers, and JaCoCo, while the globally prescribed `tdd-guide` agent gives `npm test`, `npm run test:coverage`, JavaScript null/undefined cases, Supabase examples, and Playwright as its concrete workflow (`claude/rules/java/testing.md:9-14,122-126`; `claude/agents/tdd-guide.md:20-40,42-59,61-80`). The agent also says external dependencies must be mocked while the Java rule requires real-database integration through Testcontainers (`claude/agents/tdd-guide.md:61-67`; `claude/rules/java/testing.md:83-112`).
3. Almost every observable demand is unenforced. The configured PostToolUse validator deliberately has no Java branch, the dispatch manifest contains no Java test check, the journey checker recognizes web/Python runners but no Maven/Gradle/JUnit runner, and the only configured test-specific hook runs only at `git commit` and only for Bash (`claude/settings.json:163-170,310-354`; `claude/hooks/per-edit-check/check.py:8-17,151-170`; `claude/hooks/_dispatch/manifest.json:72-180`; `claude/hooks/journey-coverage/check.py:61-79`). It does not establish test-first order, run Java tests, measure coverage, or verify the named libraries.

The corpus cannot establish whether Java projects followed JUnit/Testcontainers/JaCoCo or achieved 80% coverage because the distillation contains aggregate tool/capability counts rather than command arguments, changed-file extensions, dependency graphs, or coverage results (`inputs/corpus.json:2-11,13-60,13868+`). It does establish that the supposedly proactive `tdd-guide` agent was recorded zero times while other custom agents were recorded: `code-reviewer` 29, `planner` 28, `python-reviewer` 13, and `build-error-resolver` 2 (`inputs/corpus.json:13346-13368`). **UNVERIFIED:** whether there were Java feature/bug/refactor turns to which `tdd-guide` should have applied; the settling experiment is to query the raw JSONL transcripts for `.java`, `pom.xml`, or Gradle edits, then reconstruct per-turn agent invocation and test-command order. ## Collision register

### C01 — Fixed Java coverage overrides the repository SSOT

**Class:** CONTRADICTION  
**Artifacts:** `claude/rules/java/testing.md` and `claude/rules/common/testing.md`, with `claude/rules/README.md` determining which currently wins.

**Exact conflicting lines**

- Java: “Target 80%+ line coverage” and “Use JaCoCo” (`claude/rules/java/testing.md:122-126`).
- Common: “per `.coverage-thresholds.json` (100% on metaswarm; 80%+ where none is defined)” and verify the SSOT at the end of TDD (`claude/rules/common/testing.md:23,30-38`).
- Priority: language-specific rules override common rules (`claude/rules/README.md:93-98`).

**Why this collides**

For a repository whose `.coverage-thresholds.json` requires 100%, Java's more-specific fixed 80% text is laxer. AGENTS §10 puts project/repository governance above skill/plugin defaults and says restrictions add downward (`claude/AGENTS.md:121-130`), so an implementation cannot legitimately use Java's 80% to lower a project gate. The collision is nevertheless live in the instruction text because the rule package explicitly makes Java win over common.

**Specific resolution — BUILD-SMALL:** Replace lines 122-126 with: “Meet the repository's `.coverage-thresholds.json`; if absent, use 80%+ line coverage. Use the repository's configured coverage engine; for JaCoCo projects, preserve and run the existing JaCoCo gate. Exclude generated/trivial code only through repository-owned exclusions.” Keep the threshold in one artifact. This is **almost certain (90-99%)** to remove the contradictory instruction because both files will point to the same key and the evidence is the current literal mismatch plus the explicit specificity rule. This rides the existing rules bus and adds no runtime.
