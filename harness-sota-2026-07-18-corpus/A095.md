# A095 — Coherence audit: hooks versus behavior contract, direct contradictions

Date: 2026-07-19  
Unit: A095  
Scope: all 164 Python files under the unpacked `~/.claude/hooks/**`, compared with the complete unpacked `~/.claude/CLAUDE.md` and `~/.claude/AGENTS.md` behavior contract. Runtime wiring was resolved through `~/.claude/settings.json` and `~/.claude/hooks/_dispatch/manifest.json`. The subject was read-only; this report is the only artifact written.

## Executive result

I found **four direct contradictions that have a reachable runtime path**:

1. The force-push gate still blocks after explicit user approval unless a separate process-environment opt-out was arranged; the contract makes the user's explicit instruction highest-precedence and prohibits force-push only *without* explicit approval.
2. The RE auto-launch hook denies a confirmed-down backend call, while the contract says every non-dangerous case must inject guidance and must not block.
3. The per-edit syntax checker deliberately exits 2 for a non-dangerous syntax error even though the contract requires exit 0 plus context. Because this is a `PostToolUse` hook, Claude Code cannot undo or block the edit; the result is a hook error/feedback path, not the “hard block” the hook claims.
4. Loop recovery explicitly tells the agent to call `AskUserQuestion` after a repeated mid-task failure; the contract says “Never ask mid-task.”

The conclusion that these are the only reachable direct contradictions is **almost certain (90-99%)**, supported by (a) a successful AST parse and behavior census of all 164 Python files/41,183 lines, (b) independent searches for every hard-decision mechanism (`return 2`, `permissionDecision`, and top-level `decision:"block"`), (c) a second wiring pass through both `settings.json` and the dispatcher manifest, and (d) isolated executable probes of each finding. It is not stated as 100% because the unpacked Linux snapshot cannot expose an environment variable set only in the live Windows parent process, and the shared `~/.agents/harness/dispatcher.py` is a neighboring runtime rather than one of the 164 local hook files.

The corpus is not used as negative evidence about hook frequency. Its own known-positive control says: `"DETECTOR_STATUS": "BROKEN -- zero fires observed on a known-positive control. Treat this whole section as NO DATA, never as 'hooks did not fire'."` (`inputs/corpus.json:13260-13261`). The live-defects input independently says hook telemetry is absent from the transcripts and names the experiment needed to locate it (`inputs/INPUT-known-harness-defects.md:133-147`). Therefore this unit makes code-path and runtime-protocol claims, not historical fire-count claims.

## Finding 1 — explicit force-push approval cannot satisfy the gate

### The two contradictory texts, verbatim

Contract:

> “1. The user's explicit in-session instruction and the permission system.”  
> — `claude/AGENTS.md:121`

and:

> “Never `git push --force` to main/master without explicit user approval.”  
> — `claude/AGENTS.md:97`

Hook:

> `ACTION = "Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1."`  
> — `claude/hooks/no-force-push/tripwire.py:15-18`

The enforcement wrapper unconditionally returns 2 whenever that predicate fires:

> `halt, reason = tripwire.should_halt(payload)`  
> `if halt:`  
> `    ...`  
> `    return 2  # BLOCK: exit-2 path; reason -> model`  
> — `claude/hooks/no-force-push/hook.py:52-56`

The predicate considers only `tool_input.command`; it does not consume an approval field (`tripwire.py:21-47`). Its regex covers every `git push ... --force`/`-f`, not only main/master (`tripwire.py:18`). The standalone PreToolUse registration is live for every Bash call (`claude/settings.json:151-160`).

### Concrete collision

The user explicitly says, in the active session, “force-push this approved main rewrite,” and Claude attempts `git push --force origin main`. The contract ranks that explicit instruction first and its force-push prohibition is conditioned on approval. The hook has no access to that approval and exits 2 solely from the command text.

The advertised override does not repair that same call. `FORGE_NO_FORCE_PUSH_OFF` is read from the hook process environment before the pending Bash command executes (`hook.py:29-38`). Prefixing the *pending command* with an environment assignment changes only the future shell process, not the already-spawned PreToolUse hook's parent environment. Creating `.disabled` is also a global state change, not evidence that this one operation was approved (`hook.py:25-32`).

An isolated executable probe added an approval-shaped field to the payload and still returned:

```text
NO_FORCE_RC=2
Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1.
```

That synthetic field is not claimed to be a native Claude field; it demonstrates the code's approval-blindness independently of the source read. The official hooks reference supplies the second runtime signal: PreToolUse exit 2 blocks before permission rules can allow the call. The permissions reference is even more explicit: <https://code.claude.com/docs/en/permissions> says an exit-2 PreToolUse hook stops the call before permission rules are evaluated.

### Runtime winner

**The hook wins mechanically.** The force-push does not run. This is **almost certain (90-99%)**, supported by the live settings registration, the unconditional return-2 path, the executable `RC=2` probe, and official Claude Code exit semantics. The remaining 1-10% is the remote-snapshot limitation: this unit could not inspect whether the live Windows Claude parent process already had the global opt-out set. Such an opt-out would disable the safety gate entirely; it would not make the hook understand approval.

### Minimal resolution — UNVERIFIED native prompt under bypass mode — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Replace the exit-2 wrapper with native structured `permissionDecision:"ask"` for a detected force-push, with the reason “Force-push rewrites remote history; approve only if the user explicitly requested this exact ref.” On confirmation, Claude Code proceeds; on rejection, it does not. Keep the pure predicate and tests, add one test for the structured ask shape, and remove the process-environment instruction from `ACTION` and `SKILL.md:17-25`.

This is **very likely (80-90%)** to preserve the structural safety property while honoring approval, because the official hook reference defines `ask` as prompting the user and the existing hook is only 63 lines. The evidence is the native `PreToolUse` decision protocol and the current standalone wiring. **UNVERIFIED under this owner's `defaultMode:"bypassPermissions"` combination; settle it by launching Claude with a temporary debug file, triggering a harmless test predicate that emits `permissionDecision:"ask"`, and verifying that the approval dialog appears and the debug log records the decision.** Until that experiment passes, the safe fallback is to keep exit 2 and change the block reason to request a one-shot, externally created approval token rather than claiming the command can simply be rerun.

## Finding 2 — RE backend unavailability is blocked although it is non-dangerous guidance

### The two contradictory texts, verbatim

Contract:

> “**Exit 0 + additionalContext (inject):** all other guidance (routing, reminders, goal injection). Never block on ambiguity; inject a clarifying route instead.”  
> — `claude/AGENTS.md:68-69`

Hook:

> “A deliberate deny on a confirmed-down backend (`deny_while_starting` / `deny_when_unlaunchable`, both config-toggleable) is a controlled decision, not an error -- it replaces a guaranteed ‘connection refused’ with an actionable retry message.”  
> — `claude/hooks/re-autolaunch/autolaunch.py:28-33`

The emitted object is an actual deny:

> `"permissionDecision": "deny",`  
> `"permissionDecisionReason": "[re-autolaunch] " + msg,`  
> — `claude/hooks/re-autolaunch/autolaunch.py:397-408`

Both deny switches are true in the shipped config (`claude/hooks/re-autolaunch/backends.json:12-13`). The down/starting, low-RAM, failed-launcher, and manual-launch paths all select those switches (`autolaunch.py:456-539`). The hook is a standalone PreToolUse command for IDA, Ghidra, and Binary Ninja MCP tools (`claude/settings.json:195-204`).

### Concrete collision

Claude calls an IDA/Ghidra/BN MCP tool while its local GUI/headless backend is down, still starting, cannot be launched, or is held back for low RAM. That is an unavailable capability, not an irreversible or dangerous operation. The contract says to inject the route; the hook cancels the call.

The probe on the unpacked snapshot, with its state redirected to a temporary directory, produced:

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"[re-autolaunch] ida-pro-mcp: backend down and the re-harness launcher could not be started ..."}}
```

and returned 0, the exact structured-deny protocol Claude parses. This probe used the Linux node's necessarily absent Windows launcher; reachability of the branch is independently established by shipped config defaults and the branch logic, so the conclusion does not depend on claiming that the Windows launcher is absent.

### Runtime winner

**The hook wins mechanically:** Claude Code cancels the pending MCP tool call and feeds the reason to the model. This is **almost certain (90-99%)**, supported by the structured deny output, official `permissionDecision:"deny"` semantics, true shipped switches, and standalone settings registration.

### Minimal resolution — CONFIG (settings/JSON only)

Set:

```json
"deny_while_starting": false,
"deny_when_unlaunchable": false
```

The existing `_disposition` function will then emit `additionalContext` rather than deny (`autolaunch.py:411-412, 481-539`). No code or new runtime is needed. This is **almost certain (90-99%)** to reconcile the hook with contract §6, because both false branches already call `emit_context` and the official runtime treats that as advisory context. A still-down backend is **almost certain (90-99%)** to return the expected connection error, supported by the hook's own port-probe and bridge description (`autolaunch.py:2-21`); that visible tool result is coherent with the contract and measurable by the existing failure machinery.

## Finding 3 — per-edit syntax errors use a blocking protocol that cannot block PostToolUse

### The two contradictory texts, verbatim

Contract:

> “**Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code, force-push to main without explicit approval.”  
> “**Exit 0 + additionalContext (inject):** all other guidance ...”  
> — `claude/AGENTS.md:66-69`

Hook:

> “`py_compile / node / JSON syntax errors → exit 2 + decision:block JSON (hard nudge)`”  
> — `claude/hooks/per-edit-check/check.py:18-24`

The actual branch writes the diagnostic to stderr and returns 2:

> “`# Hard block: Claude Code reads STDERR on exit 2`”  
> `print(msg, file=sys.stderr)`  
> `return 2`  
> — `claude/hooks/per-edit-check/check.py:225-231`

It is registered as `PostToolUse` for `Edit|Write|MultiEdit` (`claude/settings.json:333-342`).

### Concrete collision

An Edit or Write succeeds but leaves malformed Python, JavaScript, JSON, or YAML. A syntax error is reversible and the write has already happened. The contract requires an injected correction. The hook calls its return-2 response a “hard block.”

An isolated write to a temporary malformed JSON file produced:

```text
PER_EDIT_RC=2
[per-edit-check] found 1 issue(s) in broken.json:
Expecting property name enclosed in double quotes: line 1 column 3 (char 2)
```

The official hooks reference independently states that `PostToolUse` **cannot block**; exit 2 only shows stderr to Claude because the tool already ran. It also states that stdout JSON is ignored on exit 2.

### Runtime winner

**The contract wins with respect to state:** the edit remains applied; the hook cannot block or undo it. **The hook wins only in choosing a noisier error channel:** Claude receives stderr as a hook error/feedback rather than a normal `additionalContext` injection. This is **almost certain (90-99%)**, supported by the active event registration, executable return code, and the official per-event exit-2 table.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Delete the syntax-special `return 2` path. Emit the already-built `msg` through the same `hookSpecificOutput.additionalContext` shape used for lint findings and return 0. Update lines 18-24 and the corresponding assertions in `per-edit-check/test_check.py` that currently require exit 2 (`test_check.py:1-10`).

This is **almost certain (90-99%)** to preserve immediate feedback and eliminate the contract/protocol mismatch, because PostToolUse cannot prevent the completed edit anyway and the hook already has a tested exit-0 injection branch at `check.py:233-244`.

## Finding 4 — loop recovery orders a mid-task question

### The two contradictory texts, verbatim

Contract:

> “Ask 1-3 targeted questions ONLY when material ambiguity remains, and only in the first 1-2 actions. **Never ask mid-task.**”  
> — `claude/AGENTS.md:9-12`

Hook:

> “`STOP and present these options to the user via AskUserQuestion:`”  
> ...  
> “`3. Ask the user directly: 'I am stuck on [specific blocker] — what should I try next?'`”  
> “`(This is a proven repeated action/failure, not mid-task ambiguity. Escalating to the user is warranted — do not continue grinding.)`”  
> — `claude/hooks/loop-recovery/handler.py:169-181`

The collision is intentional rather than accidental wording: the hook distinguishes the case from ambiguity but still instructs an interactive question. It emits that text in its `LOOPING` branch (`handler.py:252-265`). The verdict becomes `LOOPING` after three identical tool/input/output fingerprints or two identical failure preconditions (`loop-recovery/verdict.py:28-32, 84-109, 140-159, 244-264`). The handler is a live standalone PreToolUse hook on every Bash call (`claude/settings.json:228-237`).

### Concrete collision

Midway through work, the same Bash call produces the same output three times. Immediately before the next Bash call, the hook tells the agent to call `AskUserQuestion`. The contract categorically says never to ask mid-task. Contract §4b does allow escalation after two strikes (`AGENTS.md:51-57`), but it does not repeal §1's ban or define escalation as an interactive question; the hook supplies that extra, contradictory instruction.

With three identical temporary anti-degeneration records, the actual handler emitted:

```text
FAILED:d34161539794ef2d — detected a repeating action/failure ...

STOP and present these options to the user via AskUserQuestion:
...
3. Ask the user directly: 'I am stuck on [specific blocker] — what should I try next?'
```

and returned 0. That is independent confirmation of the source branch. The handler does not itself invoke `AskUserQuestion`; it adds text to model context (`handler.py:147-157, 259`).

### Runtime winner

**The pending Bash call is not mechanically blocked, and neither behavioral instruction has a deterministic runtime winner.** The hook exits 0 and the official hook protocol adds `additionalContext` to Claude's context. The model then sees both “Never ask mid-task” and “present ... via AskUserQuestion.” The contract declares itself the shared higher-precedence floor (`claude/AGENTS.md:115-131`), so a contract-compliant model ought to avoid the question, but that is not a mechanical enforcement mechanism.

The claim that the model will consistently honor the contract over the later injected text is **UNVERIFIED; settle it with a Windows Claude Code canary that seeds the three-record loop, enables `--debug-file`, attempts a harmless Bash call, and records whether the next tool is `AskUserQuestion` across at least 20 fresh sessions.** It is **roughly even (45-55%)** without that experiment: evidence for the contract is its explicit precedence text, while evidence for the hook is the later, imperative additional context. This uncertainty does not weaken the direct-contradiction finding; it is the consequence of the finding.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Edit `_looping_message` so it says: stop the repeated approach; enumerate at least two materially different alternatives; choose the cheapest falsifiable one and continue; if no safe progress is possible, stop and report the concrete blocker in the final response. Remove all three `AskUserQuestion`/“ask the user” imperatives. Keep `FAILED:<id>`, backoff, and the existing injected delivery.

This is **very likely (80-90%)** to preserve the anti-grind benefit while resolving §1, supported by the fact that contract §4b already requires alternatives or escalation and the hook's only conflicting portion is its message text. No orchestration behavior or state schema changes.
