# A074 — coherence audit: hooks (internal), duplicate authority

**Unit:** A074  
**Date:** 2026-07-19 (UTC job node)  
**Subject audited:** `/local_disk0/codexwork/bundle/claude/hooks/**`  
**Requested Windows subject:** `C:\Users\Prekzursil\.claude\hooks\**`

## Executive result

This is **not** a clean “nothing found” result. I found four runtime-relevant coherence failures caused by duplicate authority inside the hook system:

1. `_dispatch/manifest.json`, `_dispatch/test_wiring.py`, and `settings.json` independently state the PreToolUse/PostToolUse membership and routing policy. The executable manifest currently omits **14 handlers** which the explicit, non-derived wiring contract says must be dispatched, and it contains one newer handler absent from that contract.
2. The Stop-time stub rule is deliberately partitioned between `stub-ledger/report.py` and `dark-surface/check.py`, but only the first is in the runtime manifest. The live first half explicitly suppresses itself on completion claims and defers to the absent second half. That creates a deterministic blind spot on the exact `completion claim + still-open stub` case.
3. Two Workflow monitor hooks claim authority over the same action. The generalized successor is listed in the inner dispatcher manifest, but the outer live settings matcher prevents the dispatcher from running on `Workflow`; the legacy standalone hook is what actually runs.
4. Installation and self-wiring documentation repeatedly describes a different live registration than the executable registration. The most concrete examples say `no-force-push` and `todo-surfacer` are “NOT WIRED IN” even though both are wired, while six Python docstrings direct maintainers to nonexistent standalone settings entries or claim a missing MCP-liveness wire.

The first three are operational, not cosmetic. Runtime authority is held by the live `settings.json` outer matcher followed by `_dispatch/manifest.json` inner selection. Tests, docstrings, `INSTALL.md`, `spec.json`, and `hooks.json` do not override that chain. I verified that precedence from the actual call chain rather than assuming that a file named “manifest” or “test” wins.

Confidence in the findings is **almost certain (90-99%)**, based on (a) a complete AST-readable census of all 164 Python files, (b) parsed live registration and manifest data, (c) direct execution of the actual dispatcher selection function over representative tool names, and (d) independent static comparison to explicit test contracts. The missing 1-10% is because this Linux bundle cannot run the Windows Claude Code host or inspect its already-loaded in-memory settings; a native Windows restart-and-trace experiment would close that final gap.

## Design recommendation: one owned projection, no new runtime

The minimal architecture is deliberate. All repairs above ride the existing native settings/hook bus and local dispatcher. They do **not** add a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

The durable direction is:

```text
one reviewed local hook manifest
    -> settings contains only one dispatcher registration per supported event
    -> dispatcher consumes the manifest
    -> tests validate reachability, contracts, and critical flags
       without cloning path/matcher/timeout tables
    -> module docs point to the authority instead of embedding registration JSON
```

**CONFIG (settings/JSON only)** for routing cutovers, and **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for the manifest validation/doc-pointer checks. This is **very likely (80-90%)** to reduce independent drift because it removes the exact duplicated fields that are presently inconsistent, while retaining the existing 334-line dispatcher rather than introducing another service. The evidence is internal: every operational conflict found here crosses `settings.json`, `manifest.json`, a cloned test table, or hand-copied documentation.

I do not recommend full harness replacement from this unit. The evidence here supports replacing duplicate authority, not replacing the hook bus. A radical new runtime would fail the anti-overfit gate: none of these defects requires it, and the existing dispatcher already provides the necessary execution point.
