# T009 — Competitive teardown: OpenHands

**Unit:** T009  
**Research date:** 2026-07-19 UTC  
**Subject:** OpenHands, with emphasis on the current Software Agent SDK rather than the retiring V0 monolith  
**OpenHands source snapshot inspected:** `OpenHands/software-agent-sdk` commit [`4fe565663af2b4f1130a6e0dac7566b002bfe9b4`](https://github.com/OpenHands/software-agent-sdk/commit/4fe565663af2b4f1130a6e0dac7566b002bfe9b4), committed 2026-07-17  
**Product-shell snapshot inspected:** `OpenHands/OpenHands` commit [`11d4ecf21fc144d10a614ddba63b84de5c90bfd4`](https://github.com/OpenHands/OpenHands/commit/11d4ecf21fc144d10a614ddba63b84de5c90bfd4), committed 2026-07-17

## Executive verdict

OpenHands is not a better wholesale replacement for this owner's harness. It is a useful donor of a few sharply bounded mechanisms.

The decisive architectural difference is that OpenHands owns an event-sourced agent runtime. Its `Conversation` repeatedly calls a stateless `Agent.step()`, persists typed action/observation/hook events, applies condensation, risk analysis, confirmations, stuck detection, and optional completion judging inside that runtime. The owner's harness instead rides Claude Code/Codex native runtimes through rules, skills, MCP, and hooks. OpenHands therefore gets stronger end-to-end state semantics, but only by introducing the exact second orchestration runtime that the anti-overfit gate says not to add. The current OpenHands README itself now describes the old repository as Agent Canvas and points agent/runtime source to the separate SDK, while positioning the canvas as a control center that can host OpenHands, Claude Code, Codex, Gemini, or ACP agents ([current README](https://github.com/OpenHands/OpenHands/blob/11d4ecf21fc144d10a614ddba63b84de5c90bfd4/README.md)).

The parts worth taking are smaller:

1. OpenHands' new action-boundary security discriminator separates *executable fields* from thought/prose fields and gives every detector a stable ID. This is an unusually direct answer to the owner's confirmed D1 “use versus mention” failure. Port it, not the OpenHands runtime.
2. OpenHands persists a first-class `HookExecutionEvent` containing hook type, command, tool, exit code, result, stdout/stderr, injected context, IDs, and the exact hook input. The owner's current shared dispatcher records an aggregate terminal result and some event-ledger facts, but the pinned live evidence shows historical hook effectiveness was not recoverable. Port a bounded per-module receipt into the existing hook ledger.
3. OpenHands has an isolated MCP preflight that connects, lists tools, optionally invokes a caller-selected read-only tool to exercise credentials, returns structured failure kinds, and tears the connection down. This is directly relevant to the dead Tavily MCP that still received 532 calls at 25.8% error.
4. OpenHands gives run outcomes typed states (`FINISHED`, `ERROR`, `STUCK`; goal outcomes `complete` versus `capped`) rather than relying only on prose. The owner's harness already has typed verification receipts and terminal markers, so only the missing status distinctions should be borrowed.

The parts not worth taking are equally important. Do not adopt the OpenHands daemon/runtime as the default harness; do not adopt its experimental trained critic; do not enable render-time shell execution embedded in skill markdown; and do not copy its default-permission ambiguity. OpenHands' source currently initializes `ConversationState.confirmation_policy` to `NeverConfirm`, while its security architecture documentation calls `ConfirmRisky` the default. That contradiction is a warning, not a model.

**Replacement decision:** wholesale replacement is **very unlikely (5-20%)** to improve this owner's harness, because it would discard proven native Claude/Codex features, introduce a second orchestration runtime forbidden by the anti-overfit gate, and still require the same external skills/hooks/MCP configuration. Evidence: OpenHands' loop is implemented in its own `Conversation.run()` and `Agent.step()` ([run loop source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L1725-L1871), [step source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/agent/agent.py#L613-L772)); the owner's anti-overfit rule explicitly rejects a second orchestration runtime; and the local owner harness already enables native Agent Teams, ToolSearch, skills, hooks, MCP, cross-vendor fan-out, event receipts, and semantic memory (`/local_disk0/codexwork/bundle/claude/settings.json:5-18,26-81`; `/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-47`; `/local_disk0/codexwork/bundle/claude/AGENTS.md:28-90`).

**Selective-port decision:** taking the three small mechanisms above is **almost certain (90-99%)** to be higher value per line than replacing the runtime. Evidence: each rides an existing hook/MCP/ledger bus, each maps to a measured owner defect, and none requires a daemon, vector database, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 1. Agent loop

OpenHands uses a conventional but well-factored reason/action loop. The conversation is the mutable state owner; the agent is intended to be stateless between steps. The official architecture describes `step()` as: execute previously confirmed pending actions; build the current event view and condense if needed; query the LLM; parse text or tool calls; pause if confirmation is required; execute actions and emit observations ([agent architecture](https://docs.openhands.dev/sdk/arch/agent)). Current source matches that description: pending actions are handled first; blocked user prompts terminate; the view is transformed into LLM messages; a `Condensation` event causes an early return; malformed function calls become feedback; malformed history and context overflow request condensation ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/agent/agent.py#L613-L772)).

`Conversation.run()` supplies the outer loop. It changes `IDLE`/`PAUSED`/`ERROR`/`STUCK` to `RUNNING`, checks Stop hooks on finish, applies stuck detection before each step, handles confirmation waits, enforces budget and iteration limits, and emits a typed `ConversationErrorEvent` when the limit is reached ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L1725-L1871)). Atomic steps make pause/resume and event replay tractable.

What is better than ours: terminal state is an enum, action and observation correlation is structural, and errors are events. The owner has `SUCCESS:/FAILED:` markers and a ledger contract, but the provider-native loop still owns execution. OpenHands can therefore prove internally whether an action lacks an observation and can reconstruct a branch.

What is worse: adopting this advantage wholesale requires OpenHands to become the runtime. That duplicates Claude Code/Codex scheduling, permissions, tool discovery, compaction, and native agent teams. The anti-overfit gate explicitly rejects this component class. OpenHands' 500-iteration default (`ConversationState.max_iterations`) also permits far more grind than the owner's two-strikes pivot unless stuck detection catches the exact pattern ([state source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/state.py#L108-L126)).

**Proposal — typed provider terminal distinctions — UNVERIFIED. NATIVE (Claude Code already does this; we just enable it).** Preserve provider-native lifecycle events in the shared ledger as `finished`, `waiting_confirmation`, `stuck`, `error`, `interrupted`, and `limit_reached`; do not emulate OpenHands' loop. This is **likely (55-80%)** to prevent “done versus stopped” ambiguity because the owner already normalizes provider events and emits typed results, while the remaining work is mapping native lifecycle fields rather than orchestrating turns (`models.py:25-62`; `adapters.py:90-190`). The uncertainty is provider event coverage. **UNVERIFIED** whether every Claude and Codex terminal path exposes a distinct native event; settle it with a six-case fixture capture (normal finish, denial, interrupt, max-turn limit, tool failure, process loss) on both providers before adding schema-required values.

## 2. Context management

OpenHands keeps an append-only raw event history and derives an LLM-facing `View`. Condensation does not rewrite history. It emits a `Condensation` event naming forgotten event IDs, a summary, and an insertion offset; the next view filters the named events and inserts the summary. The rolling strategy preserves a head and recent tail and summarizes the middle ([condenser architecture](https://docs.openhands.dev/sdk/arch/condenser)). `LLMSummarizingCondenser` is configurable by maximum view size and number of first events to keep ([guide](https://docs.openhands.dev/sdk/guides/context-condenser)). Context-window and malformed-history errors can also generate `CondensationRequest` events, so recovery is explicit rather than a silent retry.

This is better than opaque compaction in one respect: the original event ledger remains available and the summary's exact coverage is machine-readable. It is not automatically better at retaining truth. An LLM summary can omit a constraint, and the guide's performance/cost claims are OpenHands' own claims rather than a result reproduced in this unit.

The owner already has stronger continuity semantics outside the prompt: SessionStart replays an objective ledger; PreCompact checkpoints semantic memory; goal reinjection occurs after compaction (`AGENTS.md:22-34,85-91`; `CLAUDE.md:5-13`). Replacing these with a single rolling summary would collapse objective history and semantic memory into one lossy channel.

**Proposal — compaction coverage receipt — UNVERIFIED. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On PreCompact/PostCompact, append `{session, pre_token_count, checkpoint_id, active_goal_hash, summary_or_resume_event_id, timestamp}` and test that the goal and checkpoint are replayed after compaction. This is **very likely (80-90%)** to improve auditability because the owner already has both hooks and event storage, and the pinned D3 problem is missing durable observability rather than missing summarization. Evidence: OpenHands' explicit condensation events demonstrate the useful invariant; the owner's contract already treats ledger replay as ground truth. **UNVERIFIED** exact post-compaction event fields; settle with one captured Claude compaction and one Codex compaction fixture, with known-present goal markers, before fixing the schema.

**Do not copy:** an LLM condenser as a new default service. It adds an extra inference call and another summary that can conflict with the owner's event ledger/basic-memory split. The native context window is already one million tokens in current settings (`settings.json:77-80`, model `opus[1m]`), reducing the case for aggressive summarization.

## 3. Memory

OpenHands' durable memory is primarily episodic conversation persistence. With a `persistence_dir` and conversation ID, it automatically persists message history, actions, tool outputs, execution status, statistics, activated skills, secrets/agent state, and workspace context; events are append-only individual JSON files while base state is overwritten on state change ([persistence guide](https://docs.openhands.dev/sdk/guides/convo-persistence)). Current `EventLog` is file-backed, indexed, locked for concurrent writes, and supports parent-linked branches and bounded path-to-root reads ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/event_store.py#L30-L126), [append source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/event_store.py#L184-L223)).

This gives OpenHands excellent same-conversation resume and makes subagent resumption straightforward. It is not a semantic memory system: the documented retrieval key is conversation/task identity, not meaning. The owner's `basic-memory` explicitly supports semantic cross-project notes, supersession, and proactive recall (`CLAUDE.md:5-13`). OpenHands' event tree is complementary, not a replacement.

OpenHands is worse in two concrete ways for this owner. First, its source warns that `flock()` is unreliable on NFS/network filesystems ([event log source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/event_store.py#L30-L41)); the owner's environment spans Windows and remote job nodes. Second, persisting complete tool observations increases sensitive-data and storage exposure. OpenHands supports secret encryption/redaction, but the owner already has a sanitizer and separate objective/semantic stores with narrower payloads.

**No new memory proposal.** A vector/KG memory would be a previously rejected component. Keep basic-memory for semantics and the event ledger for objective receipts. The only useful OpenHands idea—append-only typed events—is already substantially present in the shared harness.

## 4. Tool and MCP handling

OpenHands wraps native and MCP tools behind one `ToolDefinition` interface. MCP initialization connects, calls `tools/list`, converts JSON Schema to dynamic Pydantic action types, registers tools, then routes calls through an executor that converts results into observations ([MCP architecture](https://docs.openhands.dev/sdk/arch/mcp)). MCP annotations such as read-only/destructive can inform security decisions. Current execution code uses a 300-second default timeout, masks secrets in observations, and attempts one reconnect when a live client's session is lost ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/mcp/tool.py#L39-L169)).

The strongest feature for this owner is not schema conversion—it is isolated preflight. `POST /api/mcp/test` takes a candidate config, connects and lists tools without persisting anything, optionally calls one chosen read-only tool because listing alone may not exercise credentials, returns `timeout`/`connection`/`unknown`, and always tears down the temporary client ([source contract](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-agent-server/openhands/agent_server/mcp_router.py#L1-L18), [probe implementation](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-agent-server/openhands/agent_server/mcp_router.py#L563-L674)). This implements the owner's missing known-positive-control discipline: “connected and listed a tool” is not confused with “credentials work.”

OpenHands still does not solve the complete dead-tool problem. Its runtime reconnects once on a lost session, but the preflight endpoint is an add/configuration-time API; the source does not show automatic quarantine based on repeated call failures. The owner already has a per-module circuit breaker in the hook dispatcher, but not a demonstrated MCP availability gate. Therefore the port should combine OpenHands preflight with the owner's existing breaker rather than copy either in isolation.

**Proposal — MCP admission test plus availability lease — UNVERIFIED. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Before an MCP server becomes callable, run protocol handshake + `tools/list` + one configured known-positive read-only probe; store `{server, config_hash, tool_names_hash, credential_probe, tested_at, expires_at}`. On two connection-class failures, mark the lease unhealthy and remove/inject-disable the server until a bounded background re-probe succeeds. Never infer credential validity from `tools/list`. This is **almost certain (90-99%)** to reduce dead-Tavily calls because the corpus records 532 calls, 25.75% errors, and 135 “not connected” failures for Tavily extract (`/local_disk0/codexwork/bundle/inputs/corpus.json:9141-9149`), while OpenHands' code explicitly explains why listing alone is insufficient. The remaining uncertainty is which native Claude/Codex configuration surface can dynamically hide an MCP without restart. **UNVERIFIED** dynamic removal; settle by mounting a disposable MCP, killing it, and testing ToolSearch/tool availability before and after a config refresh in both providers. If dynamic removal is unavailable, the fail-safe variant is an injected “unavailable until re-probed” routing rule plus a SessionStart health refresh.

**Proposal — schema normalization only at the boundary — UNVERIFIED. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** For StructuredOutput's measured 3,694 calls, 22.9% error rate, and 294 instances of the top missing-field schema fingerprint (`/local_disk0/codexwork/bundle/inputs/corpus.json:8964-8975`), accept provider/MCP nullable and optional schema variants into a permissive internal envelope, validate the minimal discriminant and required payload only at the consumer, and retain raw output for diagnosis. This is **likely (55-80%)** to reduce schema-mismatch fan-out failures because OpenHands explicitly normalizes arbitrary MCP schemas into a generic action boundary and its v1.24.0 changelog includes an MCP Responses schema fix. The evidence does not prove it fixes the owner's 294 fingerprints. **UNVERIFIED** fingerprint overlap; settle by replaying the 294 schema-mismatch corpus samples against the permissive adapter and measuring acceptance plus downstream semantic correctness.

## 5. Permission model and security

OpenHands separates *risk assessment* from *confirmation policy*. `AlwaysConfirm`, `NeverConfirm`, and `ConfirmRisky` map risk levels to approval; `ConfirmRisky` has a threshold and can require confirmation for `UNKNOWN` ([security guide](https://docs.openhands.dev/sdk/guides/security), [policy source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/security/confirmation_policy.py#L9-L61)). File-based subagents can set `always_confirm`, `never_confirm`, or `confirm_risky`, or inherit the parent ([file-agent docs](https://docs.openhands.dev/sdk/guides/agent-file-based)). This is cleaner than a global bypass plus scattered hook blocks.

The newest source contains the most valuable security idea in this teardown. `PatternSecurityAnalyzer` constructs two corpora: shell-destructive/code-execution/network patterns inspect only executable tool fields, while prompt-injection patterns may inspect all fields. It says explicitly that an agent merely thinking about a dangerous command must not be treated as executing it, normalizes text, anchors/bounds patterns, and emits stable detector IDs ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/security/defense_in_depth/pattern.py#L1-L14), [analyzer source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/security/defense_in_depth/pattern.py#L140-L244)). A shared tree-sitter-bash parser is also present as substrate for AST-aware security detection ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/security/shell_parser.py#L1-L75)). This directly answers D1's required discriminator.

OpenHands also supports ensembles that take worst-case concrete risk and fail a throwing child analyzer closed to HIGH ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/security/ensemble.py#L22-L101)). That policy is suitable inside a confirmation system but should not be copied blindly into this owner's fail-open hooks: a broken advisory analyzer must not freeze all work. The owner's rule correctly reserves blocking for irreversible/dangerous operations (`AGENTS.md:64-70`).

There is a serious default contradiction. Current source sets `ConversationState.confirmation_policy = NeverConfirm()` ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/state.py#L119-L127)), while official architecture documentation labels `ConfirmRisky` the default ([security architecture](https://docs.openhands.dev/sdk/arch/security)). **UNVERIFIED** effective default in the packaged CLI/Canvas; the settling experiment is to launch a clean current release with no permission setting, request a HIGH and an UNKNOWN action, and record whether it pauses. No security conclusion should use the word “default” until that experiment passes.

**Proposal — semantic-role discriminator shared by all guards. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement `extract_executable_surface(event)` once: switch on tool verb; for shell tools return the command/argv field; for edits return operation + target path and never body prose; for structured responses inspect values by typed field, not field-name substrings; for prose/source scanners classify file type and Markdown fence position. Return `(surface, semantic_role, detector_id)` and make guards consume only allowed roles. This is **almost certain (90-99%)** to eliminate the nine recorded D1 false positives because OpenHands independently implements the same two-corpus distinction and the pinned defect analysis identifies the same root cause. Regression gate: all nine recorded false fires silent; real destructive command blocked; real source marker found; `{"user_cancelled_or_timedout": false}` accepted; known injection in fetched text quarantined as data. Hook schema availability is no longer merely speculative in the unpacked shared harness: normalized `HookEvent` contains tool name/input/result (`models.py:14-43`; schema `schemas/hook-event.schema.json:1-52`).

**Proposal — safer owner permission baseline. CONFIG (settings/JSON only).** Replace global `bypassPermissions` with provider-native “allow safe/read, ask destructive/external mutation,” leaving narrowly enumerated autonomous workflows explicit. This is **likely (55-80%)** to reduce blast radius because current settings allow Bash, Write, MCP and broad drives under bypass (`settings.json:26-75`), while the owner contract itself says block dangerous and inject everything else. The productivity cost on Windows automation is uncertain. **UNVERIFIED** prompt frequency; settle with a one-week shadow classification of existing calls, reporting how many would ask and their false-positive rate before enforcement.

**Do not copy:** LLM self-reported risk as the sole security signal. OpenHands' documented `LLMSecurityAnalyzer` adds a `security_risk` field to tool schemas for the same model to fill. That is not mechanically independent from the action generator and can increase structured-output burden—the owner's second-worst measured tool class.

## 6. Customisation: rules, skills, hooks, and plugins

### Rules and skills

OpenHands supports always-on `AGENTS.md` plus model variants, AgentSkills `SKILL.md` progressive disclosure, legacy markdown skills, user/project/organization scopes, and keyword/task/path triggers ([skills overview](https://docs.openhands.dev/overview/skills), [SDK guide](https://docs.openhands.dev/sdk/guides/skill)). AgentSkills are advertised by description and loaded on demand; legacy untriggered skills are inserted as repository context. Current source tracks activated and invoked skills separately and deduplicates path rules (`ConversationState` [source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/state.py#L129-L150)).

The owner is already at least equivalent: it has AGENTS.md, hundreds of installed skills, progressive skill loading, a 2% listing budget, and path-scoped rule guidance. OpenHands' strongest differentiator is declarative path-trigger activation with a persisted “already injected” set. That could reduce relying on the model to remember to read a language-specific rule.

**Proposal — path-trigger manifest — UNVERIFIED. CONFIG (settings/JSON only).** Express existing path-scoped rules as `{glob, rule_or_skill, once_per_session}` entries and use the native skill/hook router to inject when a matching path is first read or edited. ## 7. Multi-agent support

## 8. Verification and self-check

OpenHands has several layers:

1. deterministic stuck detection over the last 20 active-branch events for repeated action/observation, repeated action/error, monologue, alternating patterns, and context-window error loops ([source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/stuck_detector.py#L18-L139));
2. max iterations and max budget in the run loop;
3. Stop hooks that can reject finishing and feed a reason back into the conversation;
4. an experimental critic that scores actions/final answers and can automatically retry below a threshold ([critic guide](https://docs.openhands.dev/sdk/guides/critic));
5. current-main goal control that sends the objective, runs to finish, asks a second LLM to judge transcript evidence, and distinguishes `complete` from `capped` ([controller source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/goal/controller.py#L25-L133), [runner](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/goal/runner.py#L30-L57)). A malformed judge response conservatively returns incomplete ([judge source](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/goal/judge.py#L43-L69), [parse fallback](https://github.com/OpenHands/software-agent-sdk/blob/4fe565663af2b4f1130a6e0dac7566b002bfe9b4/openhands-sdk/openhands/sdk/conversation/goal/judge.py#L89-L120)).

The deterministic stuck detector is useful but cruder than the owner's two-strikes rule: identical-event comparison catches repetition after several events, while the owner pivots after the second failed hypothesis and requires an independent re-derivation (`AGENTS.md:51-57`). OpenHands' fixed 20-event window can miss slow loops and can label intentional repeated polling as stuck. Its explicit `STUCK` terminal state is still better than an advisory message that the model may ignore.

The critic/goal judge is not recommended. The owner's anti-overfit gate explicitly rejects a trained critic. Even the generic goal judge is not mechanically independent if configured with the same provider/model and only reads the transcript: it may agree with unsupported agent claims. The owner's typed verification receipts, exact failing-command rerun fingerprint, mutation freshness, and known-positive controls are stronger where completion is mechanically testable (`ledger.py` receipt code; `modules.py:2051-2228`).

**Proposal — typed `stuck` and `capped` receipts — UNVERIFIED. BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Promote the existing repeated-no-progress detector from injected prose to a typed ledger terminal only after its shadow precision threshold passes; distinguish `stuck`, `budget_capped`, `iteration_capped`, `interrupted`, and `complete_with_fresh_receipt`. **Do not copy:** `APIBasedCritic` or any trained critic service. ## Where OpenHands is worse and what not to copy

1. **Second runtime:** its advantages depend on owning scheduling, event state, tools, permissions, and persistence. This is precisely the rejected second-orchestrator component.
2. **Permission ambiguity:** source says `NeverConfirm`; docs say `ConfirmRisky` default. A security default that cannot be named consistently is not a reference design.
3. **Skill-time ambient code execution:** untrusted markdown can carry render-time shell commands if loaded as trusted. The owner has already identified cloned agent configuration as an attack surface.
4. **Experimental critic:** adds a model/service and confuses predicted success with proof.
5. **Loop tolerance:** default maximum 500 iterations is permissive relative to the owner's two-strikes pivot.
6. **Parallel mutation risk:** concurrency is experimental and relies on tool resource declarations/model behavior; shared file writes can race.
7. **Memory narrower than ours:** strong event replay, but no verified cross-project semantic memory equivalent to basic-memory.
8. **Network-filesystem caveat:** file locking is explicitly unreliable on NFS/network stores, relevant to mixed Windows/remote operation.
9. **MCP preflight is not automatic quarantine:** valuable admission primitive, incomplete availability control.
10. **Plugin cache risk:** remote fetch/update and bundle execution would compound the owner's orphan-directory/command-line problem unless content is referenced from one reconciled store.
