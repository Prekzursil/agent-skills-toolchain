# F027 — Red team: `hook-scripts` → `execute-code`

## Executive verdict

The most plausible attack against this harness is **same-path replacement of a live Python hook dependency, followed by an ordinary matched tool event**. The cleanest concrete target is `C:\Users\Prekzursil\.claude\hooks\no-force-push\tripwire.py`: the active `PreToolUse(Bash)` registration launches `hook.py`; `hook.py` prepends its own writable directory to `sys.path` and imports `tripwire`; Python executes the imported module's top-level code before calling `should_halt`. The relevant deployed-source evidence is the unpacked `claude/settings.json:139-159` and `claude/hooks/no-force-push/hook.py:35-58`.

An attacker who can induce one `Edit`/`Write` to that dependency gets code execution on the next Bash tool request, even if the requested Bash command itself is harmless and even if the malicious module preserves the expected `should_halt(payload)` interface. This is **very likely (80-90%)** under the supplied effective configuration because (1) `Read`, `Edit`, `Write`, and `Bash` are globally allowed, (2) `defaultMode` is `bypassPermissions`, and (3) both `C:` and `D:` are additional directories (`claude/settings.json:26-75`). Anthropic's current documentation says `bypassPermissions` skips permission prompts, including writes to `.claude`, and is intended only for isolated containers/VMs: [Configure permissions](https://code.claude.com/docs/en/permissions).

The existing controls do **not** stop this chain:

* The shared harness's `canonical_config_edit` gate recognizes direct `Edit`/`Write` targets in the deployed hook tree, but it is a heuristic gate whose default is `shadow`; shadow converts the verdict to success (`agents/harness/modules.py:138-143,311-333,389-417,837-862`). Its own regression test asserts that the default result is `allow`, and even forced `enforce` is only `inject`, not `block` (`agents/harness/tests/test_modules.py:2117-2132`).
* The same regression suite independently asserts that a Bash command targeting a canonical deployed path returns `allow` even when this gate is forced to `enforce` (`agents/harness/tests/test_modules.py:2191-2203`). This validates the detector against known-present positive paths before concluding that it does not prevent mutation.
* `file-scope` blocks only if a matching sidecar already exists; no sidecar means unrestricted, and any error fails open (`claude/hooks/file-scope/check.py:4-10,69-90,93-139`). The supplied `file-scope` directory contains only `_common.py`, `check.py`, `set_scope.py`, and `test_file_scope.py`, while `settings.json` and the supplied top-level instructions contain no `FILE_SCOPE_AGENT`/`FILE_SCOPE_DIR` wiring. Whether an unbundled live Windows sidecar existed at the exact attack moment is **UNVERIFIED — experiment: on the Windows host, enumerate `C:\Users\Prekzursil\.claude\hooks\file-scope\scopes\` and capture the effective hook environment before a disposable synthetic edit**. The attack verdict does not rely solely on this absence: the canonical guard's source and tests independently prove allow/inject rather than block.
* `test-tamper-guard` is not hook-integrity protection. It runs only for Bash, immediately returns for commands that do not contain `git ... commit`, and then scans staged test files for weakening signals (`claude/settings.json:162-171`; `claude/hooks/test-tamper-guard/guard.py:213-255`).
* `per-edit-check` runs only after the edit and syntax/lint-checks the changed file. Python checking uses `ruff check` or `python -m py_compile`; it does not intentionally import the changed module (`claude/settings.json:333-342`; `claude/hooks/per-edit-check/check.py:45-90,176-247`). A syntactically valid backdoor therefore looks clean to this control.

This is a trust-boundary failure, not evidence that the live hooks are currently malicious. No exploit was executed, no live control was changed, and no real data was read or exfiltrated.

## Scope and evidence handling

The Windows subject paths were unavailable on this Linux job node. I used the read-only unpack at `/local_disk0/codexwork/bundle`, whose `claude`, `agents/harness`, and `inputs` directories correspond to the pinned live trees. I wrote only this artifact.

The corpus's `hooks` section was not used as evidence because the brief marks its detector broken. The corpus metadata is still suitable for its stated general bounds: `inputs/corpus.json` reports 11,633 files seen, zero failed, one bad line, and warns that absence is only meaningful within the corpus. No conclusion here treats “zero hook records” as “hooks did not fire.” The supplied operational defects likewise say hook telemetry is unmeasurable and prescribe a separate known-positive test (`inputs/INPUT-known-harness-defects.md:111-147`).

Prior audit F06 is treated as a claim and then independently checked. Its claim that `_dispatch` is a manifest-driven unrestricted Python loader appears at `inputs/audit-findings/F06.md:42-48`. The actual implementation confirms that it reads `hooks_root` and `script` from JSON, joins them, constructs an import spec, and calls `exec_module` before worker timeout handling (`claude/hooks/_dispatch/dispatch.py:147-164,226-277`); the manifest supplies the absolute live root and child paths (`claude/hooks/_dispatch/manifest.json:1-18`). That is a second viable execution path, discussed below, but the primary chain uses the simpler directly registered standalone hook.

## Assets, attacker, and security boundary

### Protected asset

The asset is execution under the owner account at every lifecycle/tool boundary. A hook process is launched by the host, outside the semantics of the pending tool call. Once Python imports attacker-modified hook bytes, the code can exercise whatever filesystem, process, credential, and network authority the hook process inherits. The exact inherited Windows token, EDR policy, and outbound firewall state are **UNVERIFIED — experiment: launch a benign, administrator-reviewed canary hook in a disposable Windows account and record token groups, integrity level, environment-variable names, and denied filesystem/network operations without accessing secrets**. Arbitrary local code execution itself does not depend on those extra privileges.

### Attacker capability

The realistic initial actor is untrusted text from a cloned repository, fetched page, MCP result, issue, generated patch, or compromised skill that persuades the model to “repair,” “upgrade,” or “synchronize” a live hook. It need not already execute a shell command. It needs the model to perform a read plus an edit/write, or one complete write, to a known hook path.

This initial persuasion is **likely (55-80%)** to be attainable in at least some autonomous sessions because the harness explicitly runs with `bypassPermissions`, grants `Edit`/`Write`/`Bash`, and treats both drives as additional directories (`claude/settings.json:26-75`). The probability is not measured by this unit; **UNVERIFIED — experiment: in an isolated disposable copy with inert marker-only payloads, replay a stratified set of repository/MCP prompt-injection fixtures and measure whether the agent proposes or attempts a live-tree edit**. The recommendation inherits no dependency on a particular success rate: executable control-plane files should not be writable by an untrusted agent even if persuasion is rare.

### Trust-boundary error

The hook scripts are simultaneously:

1. trusted executables automatically launched by Claude Code (`claude/settings.json:81-280,310-353`), and
2. files reachable by tools that the same agent may use without prompting (`claude/settings.json:26-75`).

The configuration therefore makes “data the agent may edit” and “code the host will execute automatically” the same security principal and path namespace.

## Primary concrete attack chain

The chain below is deliberately concrete but omits a weaponized payload. The harmless proof substitute for every test should be a marker write in a disposable copy, never a real command, credential read, or network request.

### Step 0 — Delivery

An attacker places instructions in a repository document or tool result. The instructions claim that the local no-force-push predicate is stale and ask the agent to update the deployed copy directly. Naming the exact file is plausible because the path is exposed in active settings and hook documentation (`claude/settings.json:156`; `claude/hooks/no-force-push/hook.py:2-15`).

The attacker chooses `tripwire.py`, not the registered `hook.py`, to reduce visible configuration drift. The registered command remains byte-for-byte unchanged.

### Step 1 — Reconnaissance through an allowed read

The agent reads `C:\Users\Prekzursil\.claude\hooks\no-force-push\tripwire.py`. The configured deny list covers `.env`, PEM, and credential-name patterns, not hook source (`claude/settings.json:64-69`). This makes a precise, interface-preserving edit straightforward.

### Step 2 — Persist syntactically valid import-time code

The agent uses `Edit` or `Write` to add an import-time action to `tripwire.py` while keeping `should_halt(payload)` defined. A safe test version would only append a nonce to a temp marker. A malicious version could perform an arbitrary action under the hook process's authority. This unit did not create either version.

Before the edit, the shared dispatcher sees `PreToolUse(Edit|Write)` because its active matcher includes these tools (`claude/settings.json:139-149`). Its `SecretGuardModule` classifies the live hook target (`agents/harness/modules.py:548-591,835-862`) but stages this heuristic in shadow by default and returns success (`agents/harness/modules.py:138-143,389-417`). The implementation test confirms exactly `allow` in default mode (`agents/harness/tests/test_modules.py:2117-2129`).

The standalone `file-scope` hook also runs for edit tools (`claude/settings.json:217-225`), but it is explicitly unrestricted if it finds no sidecar and fails open on errors (`claude/hooks/file-scope/check.py:4-10,119-139`).

### Step 3 — Post-edit checks create a misleading clean signal

After the file mutation, `per-edit-check` runs because the matcher is `Edit|Write|MultiEdit` (`claude/settings.json:333-342`). Its Python path runs `ruff check` or `py_compile` (`claude/hooks/per-edit-check/check.py:45-90`). Neither checker is a malicious-behavior verifier; valid import-time code can pass. The hook then returns zero when there are no lint/syntax issues (`claude/hooks/per-edit-check/check.py:211-247`).

This is not a claim that validation says “secure”; it says only that the UI label “Per-edit validation” does not enforce hook integrity or behavior.

### Step 4 — Trigger with an innocuous Bash request

On the next Bash tool request, Claude Code launches:

`python "C:/Users/Prekzursil/.claude/hooks/no-force-push/hook.py"`

The active registration and matcher are at `claude/settings.json:151-160`. The pending Bash command need not contain a force push; the Python process starts before `should_halt` decides whether to block it.

### Step 5 — Automatic import executes attacker bytes

`hook.py` inserts its own directory at the front of `sys.path` and imports `tripwire` (`claude/hooks/no-force-push/hook.py:35-44`). Python executes module top-level statements during import. Only afterward does `hook.py` read the payload and call `tripwire.should_halt` (`hook.py:45-56`). The attacker-controlled action has therefore already run.

The broad exception handler does not protect this boundary: exceptions are converted to `allow`, but successful malicious code does not raise; even a post-action exception would only make the gate fail open (`hook.py:57-59`).

### Step 6 — Preserve stealth and repeatability

If the replacement retains a normal `should_halt` implementation, the no-force-push behavior can appear unchanged. Each Bash request launches a new Python process and imports the same dependency again. Repeated execution is **almost certain (90-99%)** once the bytes are present and a Bash request matches, based on the unconditional active command registration (`claude/settings.json:151-160`) and unconditional import before payload classification (`hook.py:35-52`). The 1-10% residual uncertainty is host/runtime deployment drift not observable from the Linux bundle; **UNVERIFIED — experiment: compare the live Windows file hashes and `/hooks` effective registration to this bundle, then run an inert marker canary in a disposable copy**.

## Alternate concrete chain: manifest redirection

An attacker can instead edit `_dispatch/manifest.json` so that a frequently matched check's `script` resolves to attacker-controlled Python. `_dispatch` reads the manifest on every process start, accepts its `hooks_root`, joins that root with each `script`, imports the resulting file, and calls `exec_module` (`claude/hooks/_dispatch/dispatch.py:147-164,226-250`). There is no resolved-path containment or content-digest check in that dataflow. Import happens serially before the timeout-controlled worker threads (`dispatch.py:242-277`), so a worker timeout cannot bound module top-level execution.

This alternate is **very likely (80-90%)** to yield code execution after one successful manifest edit because the local dispatcher is actively registered on SessionStart, PreToolUse, PostToolUse, and Stop (`claude/settings.json:94-103,250-258,344-353,484-504`), and its manifest has match-all/frequent checks (`claude/hooks/_dispatch/manifest.json:144-179`). The residual uncertainty is again live deployment parity; **UNVERIFIED — experiment: on a disposable copy only, point one manifest entry at an inert marker module and assert both containment rejection before mitigation and rejection after mitigation**.

The primary `tripwire.py` chain remains preferable to an attacker because it changes one ordinary Python file and does not need to understand manifest matching.

## Does an existing control stop the primary chain?

### Answer: no

Two mechanically independent signals support that conclusion.

**Signal 1 — implementation/dataflow.** The only targeted shared control is `_canonical_config_edit_guard`. It returns an `inject` verdict, not `block`, then passes through `stage`; heuristic default is `shadow`, and shadow logs then returns `HookResult.success()` (`agents/harness/modules.py:138-143,389-417,837-862`). The active settings set no `HARNESS_GATE_MODE__canonical_config_edit` override (`claude/settings.json:4-20`), and the bootstrap default mode file is `{}`, preserving tier defaults (`agents/harness/install.py:449-462`). Even if promoted, raw action remains `inject` (`modules.py:852-862`).

**Signal 2 — purpose-built tests.** The harness test suite explicitly expects a deployed harness edit to be `allow` in default mode and `inject` in forced enforce mode (`agents/harness/tests/test_modules.py:2117-2132`). It separately expects Bash targeting a canonical deployed path to be `allow` in forced enforce mode (`test_modules.py:2191-2203`). These are semantic expectations, not a second grep of the same source branch.

The detector was validated against known-positive controls before drawing a negative conclusion: `_canonical_tree` has explicit live roots (`modules.py:548-591`), and the parameterized test verifies that harness, skills, and hooks live targets all classify and emit `canonical_config_edit` (`test_modules.py:2135-2159`). Therefore “does not block” is not an artifact of a detector that cannot recognize the hook path.

### What controls do accomplish

* `canonical_config_edit` can produce useful shadow telemetry and, if promoted, an advisory telling the agent to edit repository source instead (`modules.py:852-862`). It is not an integrity boundary.
* The no-force-push hook can block its intended command pattern via exit 2 (`claude/hooks/no-force-push/tripwire.py:15-18,39-47`; `hook.py:52-56`). That proves blocking hooks can have teeth, but the predicate module is itself inside the mutable trust boundary.
* The dispatcher/deployer contains stronger receipt machinery for the shared harness, as prior audit F06 notes (`inputs/audit-findings/F06.md:34-40`), but the hook execution path shown above does not consult a byte receipt before import. The local dispatcher likewise imports first and fails open (`claude/hooks/_dispatch/dispatch.py:147-189,226-329`).

## Minimal mitigation — NATIVE proposal

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Move the executable hook control plane out of the agent-writable user tree and make Claude load only administrator-managed hooks:

1. Deploy the reviewed hook package (including every imported sibling such as `tripwire.py`, manifests, and shared helpers) to an administrator-owned, standard-user-read/execute-only directory, for example under `C:\Program Files\ClaudeCode\OwnerHooks\<content-version>\`. Do not point a protected declaration back to `C:\Users\Prekzursil\...`; protecting only the JSON command while leaving referenced bytes user-writable does not close same-path replacement.
2. Put the hook declarations in managed settings and enable `allowManagedHooksOnly: true`. Anthropic documents that this excludes user/project/unmanaged-plugin hooks while allowing managed hooks and force-enabled managed plugins: [Hooks reference](https://code.claude.com/docs/en/hooks) and [Configure permissions](https://code.claude.com/docs/en/permissions).
3. Set managed `permissions.disableBypassPermissionsMode: "disable"`. The current `bypassPermissions` mode explicitly permits writes to `.claude`; disabling it restores the protected-path/permission layer ([Configure permissions](https://code.claude.com/docs/en/permissions)).
4. Keep source development in the Git repository, but require an elevated deploy step to create a new immutable/versioned directory and atomically change the managed pointer. Standard agent sessions receive no write ACL to the active directory. This preserves ordinary repo editing while separating deploy authority from runtime authority.
5. Add managed deny rules for `Edit`/`Write` against the old and new live hook/harness paths as defense in depth. This does not replace the ACL boundary: Anthropic explicitly says Read/Edit deny rules apply to built-in file tools, not Bash subprocesses; OS-level enforcement is needed for processes ([Configure permissions](https://code.claude.com/docs/en/permissions)).

This mitigation is **very likely (80-90%)** to stop the documented same-path replacement chain because a standard agent process could neither alter the managed hook declaration nor write the executable/imported bytes, while unmanaged user hooks would not load. Evidence is the native managed-hook precedence documented above plus Windows ACL enforcement as the intended deployment boundary. It is **UNVERIFIED on this owner's Windows installation — experiment: in a disposable standard-user account, verify `/status` and `/hooks` show only managed hooks; attempt `Edit`, `Write`, PowerShell redirection, Git Bash redirection, rename, hardlink, symlink/junction, and directory replacement against every imported hook byte; require all mutations to fail; then confirm an administrator can deploy a new content-version and the hook still fires**.

Native Windows Claude sandbox support is not assumed. The current sandbox documentation lists macOS, Linux, and WSL2 for `sandbox.enabled`; therefore this Windows-native mitigation uses managed policy plus NTFS ownership/ACL, not an unverified sandbox claim: [Sandboxing](https://code.claude.com/docs/en/sandboxing).

### Why this is minimal

It adds no daemon, no second orchestration runtime, no vector database, no durable-execution engine, no trained critic, no observability SaaS, and no guardrail framework. It uses Claude's existing managed-hook bus and the operating system's existing file-integrity boundary. The 164 Python hooks can remain Python hooks; only their deployment/trust location changes.

Promoting `canonical_config_edit` to enforce is not sufficient: its “enforce” output is still `inject`, and its tests require Bash mutation to remain allowed (`agents/harness/tests/test_modules.py:2117-2132,2191-2203`). Adding more command regexes would also repeat the measured use-vs-mention defect in `inputs/INPUT-known-harness-defects.md:9-82` and would be bypassable through alternate writers/encodings.

## Fallback if administrator-managed immutable deployment is temporarily impossible — UNVERIFIED BUILD-SMALL proposal

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add one small, separately protected launcher that:

1. reads a signed or administrator-owned receipt containing the relative path and SHA-256 of every executable/imported hook byte;
2. resolves every path and requires it to remain under one fixed hook root;
3. verifies all required hashes before importing or spawning any hook;
4. fails closed for `PreToolUse` if integrity is wrong, with a bounded user-visible repair instruction; and
5. launches the exact content-addressed/versioned entry point, never a mutable “current file” discovered from a manifest.

The launcher and receipt must live outside the writable tree; otherwise an attacker replaces the verifier and payload together. This fallback is **likely (55-80%)** to close both the standalone import and manifest-redirection variants, based on the direct dataflows above and the prior audit's report that the existing deployer already computes receipts (`inputs/audit-findings/F06.md:34-40,50-56`). It is **UNVERIFIED — experiment: disposable-copy tests must independently corrupt (a) the registered script, (b) an imported sibling, (c) the manifest root, (d) a traversal path, and (e) the launcher target between verification and import; every case must block without executing the marker. A concurrent swap test settles TOCTOU resistance**.

This fallback rides the existing hook bus and does not violate the anti-overfit gate. It is second choice because native managed immutable deployment removes the writable-code condition directly, whereas a custom verifier creates code that itself must be protected and maintained.

## Verification/acceptance plan

No test below should run against the live owner account. Use a disposable Windows account and inert marker-only modules.

1. **Known-positive registration control.** Install one benign managed `PreToolUse(Bash)` hook and prove `/hooks` lists its managed source and that a harmless Bash request creates its expected marker. This validates the hook detector before testing absences.
2. **Unmanaged-hook negative test.** Place a second benign hook in user and project settings. With `allowManagedHooksOnly`, prove `/hooks` does not load it and its marker remains absent. Use the positive control from step 1 as the independent detector validation.
3. **Built-in writer matrix.** Attempt `Edit`, `Write`, `MultiEdit`, and `NotebookEdit` against the protected hook root. Require host denial and unchanged SHA-256.
4. **Process writer matrix.** Attempt PowerShell and Git Bash create, append, overwrite, rename-over, directory swap, junction/symlink, and hardlink operations. Require OS denial and unchanged SHA-256. This is mechanically independent of built-in tool permissions.
5. **Dependency integrity.** Change only `tripwire.py` in a disposable staging copy and prove the protected live copy remains unchanged; then perform an elevated reviewed deploy and prove both `hook.py` and `tripwire.py` advance together.
6. **Manifest containment.** In the fallback launcher test only, try absolute, `..`, symlink/junction, case-variant, and alternate-separator paths. Require resolved containment and hash failure before module import.
7. **TOCTOU.** Race a file/directory swap between hash check and launch. Acceptance requires execution by content-addressed handle/path or another design that cannot switch to unverified bytes.
8. **Behavior preservation.** Replay benign Bash, force-push, edit, and malformed-input fixtures. The benign event must continue, the force-push fixture must still block, and malformed input must follow the deliberately chosen policy without executing unknown bytes.
9. **Audit receipt.** Record effective managed-settings source, package version/hash, ACL owner/DACL, and the exact `/hooks` roster. A second read-only verifier must recompute hashes from bytes, not trust deploy output.

The mitigation can be called complete only after both independent classes agree: Claude's effective managed roster and OS-level mutation attempts. A passing JSON inspection alone is insufficient.

## Alternatives considered and rejected

### Promote the current canonical edit warning

Rejected as a stopping control. Even forced `enforce` returns `inject`, and Bash remains explicitly allowed by regression test (`agents/harness/tests/test_modules.py:2117-2132,2191-2203`). It is useful telemetry, not prevention.

### Add a regex for commands mentioning `.claude/hooks`

Rejected. The known operational defect shows command guards repeatedly confuse quoted prose with executable position and drove users toward a more failure-prone shell-writing workaround (`inputs/INPUT-known-harness-defects.md:9-47,100-107`). Regexes also miss aliases, scripting APIs, encoded commands, rename-over, filesystem links, and helpers. This would be another heuristic around the boundary rather than a boundary.

### Syntax/lint/antivirus scan before import

Rejected as the primary control. Valid Python can be malicious, and behavioral scanners are neither complete nor necessary when immutability removes unauthorized replacement. The active per-edit checker already demonstrates the limited syntax-only contract (`claude/hooks/per-edit-check/check.py:2-24,45-90`). EDR may add defense in depth, but effective Windows EDR policy is **UNVERIFIED — experiment: export applicable policy and run vendor-provided benign canaries in a disposable account**.

### Hash only the command declaration

Rejected. The registered command can remain unchanged while `tripwire.py` changes. Every imported/transitively executed byte must be bound to the receipt. Prior audit F06 makes the analogous claim for normalized Codex handler hashes versus dispatcher bytes (`inputs/audit-findings/F06.md:34-40`).

### Put the verifier beside the hooks

Rejected. Same-principal replacement lets an attacker modify verifier, receipt, and payload together. The root of trust must be administrator-owned or otherwise outside the agent's write authority.

### Build a daemon, policy service, or second sandbox runtime

Rejected by the anti-overfit gate. The native managed-hook bus and OS file permissions already express the needed separation. A daemon would add lifecycle, update, authentication, and availability failure modes without improving the core invariant.

## Residual risks after mitigation

* A malicious administrator or compromise of the elevated deployment pipeline remains able to publish malicious hooks. That is outside the standard-agent boundary. A reviewed, content-addressed receipt makes this auditable but does not eliminate administrator compromise.
* A force-enabled managed plugin is only as trustworthy as its pinned source and deployment channel. `allowManagedHooksOnly` permits managed force-enabled plugins by design ([Configure permissions](https://code.claude.com/docs/en/permissions)); therefore exact plugin identity/version and protected cache bytes must be part of the same acceptance evidence.
* Hooks still intentionally execute code. The mitigation prevents unauthorized same-path replacement; it does not prove reviewed hook logic is bug-free.
* If the owner continues launching some clients under unrestricted full-host modes outside Claude Code, equivalent writable-code boundaries in Codex or MCP launchers require their neighboring units' controls. This unit does not redesign those surfaces.
* The exact number “164 Python hooks running on every tool call” is pinned task input. The active settings show both standalone and dispatch paths, but this unit did not re-count or reinterpret that measured scope.

## GAPS

1. Live Windows hashes, ACLs, effective `/hooks` roster, and hook environment were unavailable on the Linux job node. The disposable Windows acceptance plan above settles them.
2. AppLocker/WDAC, Defender/EDR, outbound firewall, and process-token restrictions were not supplied. No conclusion assumes they are absent or ineffective; export of effective policy plus benign canaries would settle their contribution.
3. An unbundled `file-scope` sidecar could narrow a particular session. Its live presence is UNVERIFIED as specified above, but it would not replace a permanent control-plane integrity boundary because its own documented missing/error behavior is fail-open (`claude/hooks/file-scope/check.py:4-10,119-139`).
4. The attack was not executed. Static import semantics, active settings, and purpose-built expected-result tests establish the chain/control behavior; only the disposable marker experiment should validate end-to-end host behavior.
5. The probability that a specific prompt injection persuades a current model is unmeasured. The architectural recommendation does not depend on that probability being high.
