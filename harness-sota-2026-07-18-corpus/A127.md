Date: 2026-07-19

## Executive verdict

I found **one confirmed, degrading command/settings conflict**: `/context-budget` tells the model to assume a 200K Sonnet window while the user settings select `opus[1m]` and a 1,000,000-token compaction window. Both instructions apply during the command: settings select the runtime model/window, while the command prompt controls the report's arithmetic. There is no tie-break in the command. The result can therefore be a 1M session analyzed as though it were 200K.

This conclusion is **very likely (80-90%)**, based on four independent signals: the exact command text (`commands/context-budget.md:22-27`), the exact settings (`settings.json:77,684-686`), Anthropic's current model documentation defining the `[1m]` suffix, and two recorded `context-budget` invocations in the distilled corpus (`inputs/corpus.json:13265,13309`). The confidence is below 90% only because this Linux job node cannot run the owner's Windows Claude Code instance and therefore cannot recover the effective model/status from those two historical invocations.

I did **not** promote two reachable hazards to findings: `/pm2` versus `.env` denies, and legacy Metaswarm bootstrap/update commands versus the enabled marketplace plugin. Their collisions require project/runtime state that is absent from the remote bundle. Each is marked **UNVERIFIED inline** below with the exact experiment that settles it.

No full replacement is justified by this unit. A one-line dynamic-capacity correction rides the existing command/skill bus and resolves the confirmed defect. Adding another runtime, memory system, daemon, critic, SaaS, or guardrail framework would fail the anti-overfit gate for this evidence.

## Finding F1 — `/context-budget` hard-codes 200K over an active 1M configuration

Severity: **degrading**. It does not prevent invocation, but it can scale every percentage, threshold, and optimization conclusion by a factor of five.

### Both authority texts, verbatim

Command (`C:\Users\Prekzursil\.claude\commands\context-budget.md:22-27`):

> Run the **context-budget** skill (`skills/context-budget/SKILL.md`) with the following inputs:
>
> 1. Pass `--verbose` flag if present in `$ARGUMENTS`
> 2. Assume a 200K context window (Claude Sonnet default) unless the user specifies otherwise
> 3. Follow the skill's four phases: Inventory → Classify → Detect Issues → Report
> 4. Output the formatted Context Budget Report to the user

Settings (`C:\Users\Prekzursil\.claude\settings.json:77-80`):

> "model": "opus[1m]",
> "fallbackModel": [
>   "claude-sonnet-5"
> ],

Settings (`C:\Users\Prekzursil\.claude\settings.json:684-686`):

> "outputStyle": "Honest",
> "effortLevel": "xhigh",
> "autoCompactWindow": 1000000,

Related setting (`C:\Users\Prekzursil\.claude\settings.json:18`):

> "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "90",

### Concrete collision

The collision occurs whenever `/context-budget` is invoked without an explicit window argument in this user configuration. That situation is not hypothetical: the corpus records two `context-budget` invocations (`inputs/corpus.json:13265,13309`). The command passes a 200K assumption into its analysis, while Claude Code is configured to select the 1M Opus variant. For example, 100K tokens of fixed harness overhead is 50% under the command assumption but 10% under a 1M window. Ranking “context overflow” remedies from the former number can materially overstate urgency and favor deletion of useful capabilities.

The prior audit claim that the delegated `skills/context-budget/SKILL.md` is absent (`inputs/audit-findings/D13.md:39-41`) is **not** used to establish this finding. If that claim is true, it is a separate dangling-dependency defect; if false, the contradictory input still reaches the skill.

### Which wins at runtime

Two different planes win simultaneously:

1. **Settings win model selection and the real context ceiling.** Anthropic's current model documentation explicitly says `opus[1m]` selects the 1M context variant and distinguishes it from standard 200K models. A legacy command body is injected as instructions; it does not rewrite the persisted `model` field. Anthropic's skills documentation likewise says a command/skill `model` frontmatter field would be the turn-local override; this command has no such field (`context-budget.md:1-3`).
2. **The command wins the report's stated assumption.** Its imperative line 25 is loaded when the command runs, so absent user correction or model disobedience, the analysis is told to calculate against 200K.

That split authority is the defect: the runtime does not reconcile the report denominator with the selected model.

**UNVERIFIED:** whether the owner's account accepted `opus[1m]` rather than falling back during each of the two historical invocations cannot be established on this Linux node. Settle it on Windows by starting a clean Claude Code session, recording `/status` and `/model`, invoking `/context-budget --verbose` without adding a window, and comparing the report denominator with the status-reported context capacity. This uncertainty does not remove the defect: even a legitimate fallback should be detected dynamically rather than always called “Claude Sonnet default.”

### Minimal resolution

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Edit only `commands/context-budget.md:25` to replace the hard-coded assumption with:

> Determine the effective context capacity from the active model/status. Treat a model with the `[1m]` suffix as 1,000,000 tokens and a standard model as 200,000. If effective capacity cannot be determined, state the assumption explicitly in the report; a user-supplied capacity wins.

This is a one-paragraph prompt edit, not a new component. It is **almost certain (90-99%)** to remove this ambiguity because the report would name and derive its denominator, supported by the command's existing four-phase reporting structure and Anthropic's documented `[1m]` semantics. The remaining 1-10% covers future model aliases with other capacities; reading effective status rather than enumerating aliases is the durable part.

A still smaller but less robust edit—changing `200K` to `1M`—was rejected because `fallbackModel` exists (`settings.json:78-80`) and sessions can change models. It would merely invert the same hard-coded defect.

## Conditional hazards examined but not counted as findings

### H1 — `/pm2` wants `.env`; settings deny built-in reads — UNVERIFIED

Command (`commands/pm2.md:29`) says verbatim:

> **Port Detection Priority**: User specified > .env > config file > scripts args > default port

Settings (`settings.json:64-69`) say verbatim:

> "deny": [
>   "Read(./.env)",
>   "Read(**/.env)",
>   "Read(**/*.pem)",
>   "Read(**/*.credentials*)"
> ]

If a project has its only port declaration in root `.env`, `/pm2` claims that source outranks config/scripts, while a built-in `Read` call is denied. Anthropic's permission documentation says a deny at any level cannot be overridden by allow and explicitly uses `.env` as the sensitive-file example. Thus, for a `Read` tool attempt, settings win at runtime even though `defaultMode` is `bypassPermissions` (`settings.json:71`).

This is not a confirmed finding because the command does not prescribe the tool used to obtain the port. Anthropic documents that `Read` deny rules do not block Bash subprocesses. The local Bash-closing hook is registered at `settings.json:240-247`, but its implementation is opt-in and exits without a decision unless `HARNESS_CREDENTIAL_GUARD` is true (`hooks/deny-credential-reads/deny.py:73-100`); that environment variable is not set in `settings.json:4-20`. Also, the remote bundle contains no selected project whose root `.env` is known to be the only port source.

**UNVERIFIED:** settle reachability on Windows with a disposable project containing `.env` with `PORT=4321`, no other port declaration, and invoke `/pm2`; capture whether Claude uses `Read`, is denied, falls back to Bash, or uses the documented default. Do not expose a real secret. If it is reproduced, the minimal **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** edit is to replace `.env` with “non-secret metadata (`.env.example`, package/config args); ask the user for a port when only `.env` may contain it.” It is **very likely (80-90%)** to prevent the collision, based on the explicit deny and official permission semantics.

## Precedence model derived from evidence

The local behavior contract already gives a general instruction hierarchy at `AGENTS.md:115-131`: explicit user/permission system, security non-negotiables, cross-tool contract, project governance, then third-party defaults. That resolves safety collisions but does not solve F1 because the command and settings govern different runtime planes rather than occupying one comparable instruction level.

For this audit, the mechanically supported resolution rules are:

1. Persistent settings and supported turn-local frontmatter select runtime configuration. Anthropic documents `model` frontmatter as a current-turn override; absent that frontmatter, the session model resumes/continues. Command prose that merely recommends or assumes a model does not mutate settings.
2. Explicit permission denies win over allows and hook allows. Anthropic documents deny-first evaluation and says denies remain effective across settings levels. Bash file access is a documented exception unless sandbox/hook policy closes it.
3. Marketplace enablement loads plugins from the Claude-managed cache, not from arbitrary project-local legacy paths. An npm bootstrap command can still write local files, so without an explicit migration/deprecation branch both planes may act rather than one cleanly winning.
4. Workflow approval prose and tool permission mode are orthogonal. “Bypass permissions” is not evidence that a user approved a plan, merge, reviewer response, or architecture change.
