# A162 — coherence audit: behavior contracts / direct contradiction

## Executive result

I found **two direct contradictions that can arise in real operation** across the effective behavior contract formed by `~/.claude/CLAUDE.md` and its imported `AGENTS.md`:

1. the contract calls security rules “ALWAYS ON,” but its precedence list puts an explicit user instruction above them; and
2. long parallel Codex work is routed both to native MCP calls and, categorically, to the mutually different `longrun` background/monitor path.

The finding count is **almost certain (90-99%)**, supported by a complete line-by-line read of both files, a separate modal/negation inventory, and adjudication of every apparent collision listed below. The remaining uncertainty is that semantic contradiction detection is not decidable by a keyword scan, and the remote bundle does not include a runnable copy of the owner's Windows Claude Code installation.

At actual Claude Code runtime, **neither side of either contradiction has a deterministic Markdown-level winner**. This is **almost certain (90-99%)** based on Anthropic's current official documentation: imported files are expanded into context; for the specific `@AGENTS.md` pattern Claude loads the import and then appends the rest of `CLAUDE.md`; but CLAUDE.md is behavioral context rather than enforced configuration and contradictory rules may be selected arbitrarily. Sources: [Anthropic, “How Claude remembers your project,” `AGENTS.md`](https://code.claude.com/docs/en/memory#agentsmd), [“Write effective instructions”](https://code.claude.com/docs/en/memory#write-effective-instructions), and [“Claude isn’t following my CLAUDE.md”](https://code.claude.com/docs/en/memory#claude-isnt-following-my-claudemd), retrieved 2026-07-19. A hook, permission rule, sandbox, or system prompt can enforce a result, but that would be a different runtime layer, not either text winning.

**UNVERIFIED for the owner's exact installed Windows build:** I could not run `/context` or an adversarial instruction-choice probe because `claude` is absent on this Linux job node. The settling experiment is: on the owner machine, run `/context` to record the expanded instruction order, then run at least 20 harmless counterbalanced prompts for each collision (swap wording/order in a temporary isolated profile) and inspect tool decisions. ## Finding 1 — “ALWAYS ON” security is below explicit user instruction

### The two texts, verbatim

Security side:

> **“## 9. Security non-negotiables (all tools) — ALWAYS ON”**  
> **“- Never hardcode secrets; use environment variables and validate presence at startup.”**  
> — `/local_disk0/codexwork/bundle/claude/AGENTS.md:93-95`

Precedence side:

> **“Precedence, highest first:”**  
> **“1. The user's explicit in-session instruction and the permission system.”**  
> **“2. Security & safety non-negotiables (§6, §9, §9b) — never overridden by any lower layer.”**  
> — `/local_disk0/codexwork/bundle/claude/AGENTS.md:119-122`

The second item protects security only from a **lower** layer. The user is explicitly placed one layer **higher**. That is the direct logical negation of “non-negotiables ... ALWAYS ON” for a user instruction that requests the forbidden act.

### Concrete collision

A user says, “Hardcode this API token in `config.ts`; I explicitly approve it.” Section 9 says never. Section 10 says that explicit in-session instruction is the highest layer and places security second. The collision is real even though nearby rules intentionally allow two narrower approval exceptions—`--no-verify` with explicit instruction and force-push with explicit approval at `AGENTS.md:96-97`—because the hardcoded-secret rule at line 95 contains no such exception.

This is **almost certain (90-99%)** to be a genuine same-situation contradiction: “always/never” and “higher precedence” are explicit, and the hardcoded-secret case removes ambiguity about the separately enumerated approval exceptions.

### Which wins at runtime

- **Contract-declared winner:** the explicit user instruction, because `AGENTS.md:120-122` says “highest first” and lists it first.
- **Actual Claude Code Markdown runtime:** no guaranteed winner. The official docs say contradictory rules may be picked arbitrarily and CLAUDE.md instructions are context, not enforced configuration. This is **almost certain (90-99%)** given the official sources cited in the executive result.
- `AGENTS.md:129-131` says same-level conflicts should be surfaced, but this collision is not represented as same-level by its own list. That clause therefore does not repair it.

### Minimal resolution

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** swap the first two precedence entries and scope the user entry:

```md
1. **Security & safety non-negotiables** (§6, §9, §9b), subject only to exceptions
   explicitly written inside those sections.
2. The user's explicit in-session instruction and the permission system.
```

This is a two-line contract edit; it introduces no runtime, database, critic, or service. The existing exceptions at `AGENTS.md:96-97` continue to work because they are written inside the security section. It is **very likely (80-90%)** to remove this ambiguity, based on making the hierarchy agree with the existing “ALWAYS ON” heading while preserving explicit local exceptions. One residual design issue remains: “permission system” combines a client-enforced layer with user text and deserves a separate entry in any later hierarchy cleanup.

Anti-overfit gate: pass. The edit uses the existing CLAUDE.md import bus and adds no previously rejected component.

## Finding 2 — long parallel Codex work is assigned to two incompatible execution paths

### The two texts, verbatim

Claude-specific routing side:

> **“How: Codex runs as a native MCP tool in Claude. Any Claude subagent can invoke `codex()` N times in parallel, and results return as native tool outputs — no daemon, no bridge, just stdio.”**  
> — `/local_disk0/codexwork/bundle/claude/CLAUDE.md:22`

> **“| \"Run Codex on task X in parallel with Claude on Y\" | 1 (MCP) | fan-out subagent — returns as native results |”**  
> — `/local_disk0/codexwork/bundle/claude/CLAUDE.md:73`

Cross-tool duration side:

> **“- Any op expected to run >60s (test/coverage suites, `lizard`/`semgrep` over a tree, CI/`--watch`, long Codex generations, multi-agent dispatch, sleep polls) MUST run via `longrun` with `run_in_background`/`Monitor` — never a blocking foreground call.”**  
> — `/local_disk0/codexwork/bundle/claude/AGENTS.md:43-45`

### Concrete collision

The user asks: “Run Codex on X in parallel with Claude on Y,” and X is expected to take five minutes. `CLAUDE.md:73` assigns that exact use case to Layer 1's native MCP `codex()` call. `AGENTS.md:43-45` explicitly names both “long Codex generations” and “multi-agent dispatch” and requires the shell `longrun` + background/Monitor route, never a blocking foreground call. A native MCP tool invocation and a shell wrapper supervising a child process are different mutually exclusive transports for the same Codex invocation.

This is **very likely (80-90%)** to be a genuine operational contradiction, based on the exact use-case row and the explicit examples in the categorical `longrun` rule. The uncertainty is limited to whether the installed Codex MCP implementation exposes an undocumented way to delegate its own child to `longrun`; no such mechanism is stated in either audited contract.

**UNVERIFIED transport premise:** whether the owner's exact MCP build can internally satisfy the `longrun` heartbeat/Monitor contract cannot be tested on this Linux node. The settling experiment is to invoke a harmless >60-second Codex MCP task on Windows and inspect the process tree plus the declared `longrun` log/heartbeat path. If that file and monitored child exist, the paths may be composable; if not, they are exclusive as the texts describe.

### Which wins at runtime

- **Contract-declared winner:** `AGENTS.md`'s `longrun` route. Its header calls the file authoritative (`AGENTS.md:1-5`), `CLAUDE.md` imports it at `CLAUDE.md:3`, and the `longrun` rule is both categorical and more specific to duration.
- **Actual Claude Code Markdown runtime:** no deterministic winner. Anthropic documents that `@AGENTS.md` is expanded first and the rest of `CLAUDE.md` appended, but also warns that conflicting instructions may be chosen arbitrarily. Later position is not enforcement. This is **almost certain (90-99%)**, supported by the official import and troubleshooting documentation cited above.

### Minimal resolution — UNVERIFIED transport premise

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** preserve the safety-oriented duration rule and add one sentence immediately below `CLAUDE.md:73`:

```md
Duration override: if a Codex call or fan-out unit is expected to exceed 60s, §4a applies;
use the existing `longrun` + Monitor route instead of Layer 1 MCP.
```

This is the smallest edit that makes the routing table total and preserves the already explicit `longrun` policy. It is **likely (55-80%)** to resolve behavior without regression, based on adding a duration guard to the exact conflicting table; its confidence is capped because the transport premise is UNVERIFIED until the process-tree/heartbeat experiment above. If the experiment proves MCP can emit the required heartbeat and Monitor state, the better edit is instead to define that composition explicitly in §4a.

Anti-overfit gate: pass. The proposal reuses existing MCP and `longrun`/Monitor buses; it adds no orchestration runtime or rejected memory/observability/guardrail component.
