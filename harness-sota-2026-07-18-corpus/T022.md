# T022 — Competitive teardown: TRAE

**Unit:** T022  
**Research date:** 2026-07-19 UTC  
**Subject:** TRAE IDE, TRAE Work (the July 2026 successor name for SOLO), and the separately published `bytedance/trae-agent` research harness  
**Required lens:** agent loop; context management; memory; tool/MCP handling; permissions; rules/skills/hooks equivalents; multi-agent; verification/self-check; concrete ports into the owner's Claude/Codex harness

## Executive verdict

TRAE is not a better underlying harness than the owner's system across the board. It is a **better product shell around several harness primitives**: users can see and trim context, manage skills and commands in one surface, inspect MCP logs, configure agents and their least-privilege toolsets visually, run several agents in a common workspace, and invoke a first-class source-control review flow. The owner's harness is materially stronger in lifecycle programmability, cross-provider operation, explicit evidence rules, hook-time enforcement, durable semantic memory, and depth of specialist capability.

The highest-value thing to copy is therefore not TRAE's IDE or cloud runtime. It is its **control-plane legibility**: one view of active context, active tools, MCP health, agent progress, review evidence, and recoverable changes. That conclusion is **very likely (80-90%)**, supported independently by (1) TRAE's official documentation for visible context, MCP logs, editable per-agent tools, and review panels, and (2) this owner's measured failures, where a dead MCP continued to receive calls and hook telemetry could not be measured (`corpus.json:9130-9148,13260-13264`; `INPUT-known-harness-defects.md:133-148`).

The recommended response is evolution on the existing Claude/Codex/hook/MCP buses, not wholesale replacement. Full replacement with TRAE is **unlikely (20-45%)** to improve this owner's end-to-end outcomes: official TRAE documentation exposes a substantially weaker command permission boundary, the product is closed, TRAE Work's cloud path transmits or retains code, and its advertised multi-agent shared-context mechanics are not specified well enough to audit. Evidence: [TRAE auto-run and security](https://docs.trae.ai/ide/auto-run-and-security), [TRAE privacy mode](https://docs.trae.ai/solo/privacy-mode), and [TRAE SOLO GA](https://www.trae.ai/blog/product_solo_1112).

### Bottom line

1. **Port now:** a health-aware MCP catalog with a circuit breaker and local log links; a compact context manifest; a unified trajectory/receipt envelope; an integrated evidence-first review summary. All ride existing buses.
2. **Enable or consolidate rather than build:** native isolated subagents, per-agent tool restrictions, on-demand skills, manual/automatic compaction, and recoverable worktrees already exist in the owner stack.
3. **Do not copy:** outside-sandbox command auto-run, a fourth memory authority, silent all-MCP exposure to a primary agent, cloud continuity as a prerequisite, or a permanent candidate-generation/pruning/selector runtime.
4. **Experiment only:** test-time candidate diversity on a narrow class of expensive, objectively testable defects. The evidence is a benchmark paper, not proof for this owner's task mix.

## 4. Agent loop teardown

### 4.1 Closed product loop

Official IDE documentation describes `Agent` as the primary development agent. Its sequence is:

1. analyze requirements;
2. generate a PRD and technical solution;
3. ask the user to confirm;
4. generate code and add context-dependent actions such as file reads, scope confirmation, to-do organization, subagent calls, runtime checks, or key-decision questions;
5. preview and summarize after validation.

Source: [built-in Agent](https://docs.trae.ai/ide/built-in-agent) and [agent overview](https://docs.trae.ai/ide/agent-overview).

This is a plan-act-observe loop with a deliberate pre-edit approval boundary. The useful detail is not “it plans”—all modern coding agents do—but that the plan, context, terminal, browser/preview, diff, and subagent activity are presented in a common workspace. The GA post says users can redirect during execution and review changes in DiffView, while Plan mode precedes execution. Source: [TRAE SOLO GA, lines 21-40 and 83-107 in the rendered page](https://www.trae.ai/blog/product_solo_1112).

The product docs do not publish the loop's exact termination logic, retry policy, prompt, context-ranking function, or model/tool error recovery. Any assertion that the production IDE uses the open-source CLI's state machine would be **UNVERIFIED; the experiment is a controlled TRAE run with exported diagnostic logs plus source-map inspection or an official architecture disclosure**. Therefore this report does not make that assertion.

### 4.2 Open-source loop: useful but separate

The public CLI config exposes a model, `max_steps`, a short tool list, and an explicit `task_done` tool. It records a full trajectory and can run in Docker. Sources: [`trae-agent` README/config and CLI](https://github.com/bytedance/trae-agent#configuration), [tools documentation](https://github.com/bytedance/trae-agent/blob/main/docs/tools.md), [trajectory recording](https://github.com/bytedance/trae-agent/blob/main/docs/TRAJECTORY_RECORDING.md).

The OSS tool surface is intentionally small: a persistent exact-replacement editor, persistent bash, sequential thinking, a completion signal, and a JSON editor. `task_done` is documented as callable only after proper verification and encourages tests/reproduction scripts. This is a good minimal-loop invariant, though the documentation shows an instruction-level requirement rather than a mechanically proven verifier.

Relative to ours:

* TRAE's explicit `max_steps` is easier to audit than open-ended “continue” behavior, but Codex already has bounded job runtime and goals (`codex/config.toml:77-80`), and native Claude subagents can be bounded. No new loop is justified.
* TRAE's exact-string editor has the same collision/read-before-write class already visible in our corpus; exact replacement is not a cure (`corpus.json:8938-8960`).
* Persistent bash preserves state and reduces repeated setup, but it also amplifies quoting/state surprises; our dominant Bash errors include a quoted-command class in the pinned summary. Do not infer reliability from persistence.
* A dedicated completion tool is sound, but ours has an even stronger goal-status contract plus verification hooks. The gap is receipt integrity and telemetry, not the absence of a completion verb.

### 4.3 Port verdict

**NATIVE (Claude Code already does this; we just enable it).** Keep provider-native loops. Standardize a thin loop contract shared through rules/agent frontmatter:

`intent + constraints + acceptance -> plan -> smallest action -> observe typed result -> verify against acceptance -> completion receipt`.

This is **very likely (80-90%)** to outperform replacing the loop with the OSS Trae CLI for this owner, because our existing surface already has multi-agent, hooks, skills, goals, broader tools, and cross-provider routing, whereas the pinned damage is concentrated in tool reliability and telemetry rather than missing planning (`settings.json:81-150`; `config.toml:82-130`; `corpus.json:8964-9148`).

## 5. Context management teardown

### 5.1 What TRAE exposes

The strongest TRAE feature is visible, editable context:

* Official IDE docs show a per-chat context usage rate and context-window value after each round.
* The system auto-compacts once when the context exceeds the window; the user can manually compact earlier.
* Compaction claims to remove redundancy and retain task-relevant key content; a new chat clears prior chat context.
* The GA product describes static context (documentation, designs, code) beside dynamic context (browser, terminal, errors), selective retention, and a unified layer shared by parallel agents.
* The newer Work product accepts code, documents, datasets, images, and presentations in one project, and lets the user see, compact, or trim what is used.

Sources: [context compaction](https://docs.trae.ai/ide/context-compaction), [SOLO GA context discussion](https://www.trae.ai/blog/product_solo_1112), [new SOLO/Work context and file types](https://www.trae.ai/blog/new_solo_beta_0331).

The claim that “shared context” prevents conflicts is product marketing, not a published consistency protocol. Whether shared state is snapshot-isolated, last-writer-wins, event-sourced, or just retrieved summaries is **UNVERIFIED; the experiment is two parallel agents making contradictory decisions and overlapping edits while capturing each agent's visible context before and after the conflict**.

### 5.2 Relative verdict

TRAE is better at **context legibility**. Ours exposes context usage in Codex's status line and has auto-compaction plus Basic Memory checkpoints (`codex/config.toml:42-64`; `claude/settings.json:18`; `claude/CLAUDE.md:7-11`), but the evidence bundle does not show one user-visible manifest answering:

* which rule/skill/memory/file/tool result is active;
* why it was selected;
* its age/provenance/token cost;
* whether every child saw it;
* what compaction retained or discarded.

I do **not** claim that such a manifest is absent across the entire Windows installation: a second independent live-UI signal was unavailable on the Linux node. The bounded bundle signal is that Codex exposes aggregate context status and Claude config exposes hooks, while the known-defect report says transcript hook telemetry is not measurable. Thus “no unified manifest in the inspected surfaces” is **very likely (80-90%)**, supported by two mechanically different signals: config/UI fields and corpus schema (`config.toml:42-64`; `corpus.json:13260-13264`). A live Windows screenshot/export would settle product-wide absence.

### 5.3 Port: compact context manifest

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a projection, not a new memory system:

```text
context-manifest/v1
session, turn, root_goal_hash, compact_generation
active_items[]:
  kind: rule|skill|memory|file|tool-result|agent-handoff
  id/path_hash, reason, source_event, observed_at, valid_as_of
  token_estimate, trust: trusted|untrusted|mixed
compaction:
  retained_ids[], dropped_count_by_kind, summary_hash, raw_pointer
```

Mechanism:

1. Existing `InstructionsLoaded`, Skill, memory-recall, tool-result, SubagentStart/Stop, and PreCompact/SessionStart events append item metadata to the existing ledger.
2. A projection command renders the current manifest in the existing monitor/artifact surface.
3. PreCompact hashes the before-set; SessionStart-after-compact records the retained-set and summary pointer.
4. The UI/skill offers “pin for this task,” “exclude next turn,” and “show source.” Pinning is session metadata, not durable memory.
5. Never include raw secrets or full untrusted payloads; retain hashes and source pointers.

It is **likely (55-80%)** that this will reduce context drift and false “what did the child know?” debugging, because TRAE's visibility addresses exactly those operator questions and our hook telemetry cannot currently answer them. The uncertainty is whether the provider events expose retained compaction item IDs. **UNVERIFIED premise: event payload sufficiency; experiment: dump sanitized schemas for InstructionsLoaded, PreCompact, compact-resume SessionStart, Skill, and SubagentStop before implementation.** If retained IDs are unavailable, record only before/after summary hashes and label the projection incomplete.

Anti-overfit gate: passes. It is a ledger projection on the existing hook bus, not a vector database, knowledge graph, second orchestrator, durable-execution engine, critic, SaaS, or guardrail framework.

## 6. Memory teardown

### 6.1 TRAE's mechanism

Current official memory docs describe two local Markdown files:

* global: `~/.trae/memory/user_profile.md` (or Windows `%userprofile%/.trae/memory/user_profile.md`);
* project: `~/.trae/memory/projects/{project_path}/project_memory.md`.

The agent may automatically identify durable preferences/rules, update changed ones, or create/update/delete memory on explicit request. One-time instructions, vague/uncertain preferences, and sensitive data are not automatically stored. Memory is local and cannot be shared across devices. Source: [TRAE memories](https://docs.trae.ai/solo/memories).

The Work launch post says preferences, brand guidance, watchlists, and deliverable styles carry forward; that is a capability claim rather than evidence of retrieval quality. Source: [new SOLO/Work](https://www.trae.ai/blog/new_solo_beta_0331).

TRAE's strengths are inspectability and scope. Its weaknesses are equally concrete:

* docs specify no provenance fields, confidence, `valid_as_of`, supersession link, poisoning/quarantine policy, retrieval scoring, or conflict-resolution procedure;
* memory is device-local even though Work tasks synchronize across devices, creating an explicit continuity boundary;
* global/project Markdown can still become a silent instruction authority.

Those missing documented fields are not proof that internal metadata is absent. Product-level absence is **UNVERIFIED; the experiment is to create, update, contradict, and delete the same preference while inspecting the two files and any diagnostic export**. What is certain is that the public contract does not expose them.

### 6.2 Relative verdict and port

Ours is stronger in semantic recall and temporal validity: Basic Memory is declared durable, queryable, checkpoint-aware, and uses `superseded_by` plus `valid_as_of` (`claude/CLAUDE.md:5-13`). Ours is worse in authority clarity because native Claude/Codex memory features also exist; earlier audit units claim split-brain risk, but this unit does not re-verify their complete live state.

**CONFIG (settings/JSON only).** Do not add TRAE memory. Instead:

1. Keep Basic Memory as canonical durable authority.
2. Disable or demote provider auto-generation after a separately authorized config phase.
3. Generate a read-only plain-Markdown `current-profile` projection from canonical notes, grouped into owner preference, project invariant, decision, and active caveat; each row links to provenance and validity.
4. Treat automatic candidate memories as pending until they have an explicit source, scope, and confidence; do not let an agent's self-authored inference silently become a rule.

It is **very likely (80-90%)** this is safer than copying TRAE's auto-memory, because the owner's memory already has richer temporal semantics, while a new store would create another authority. Evidence: the canonical-memory contract (`CLAUDE.md:5-13`) plus TRAE's separate local global/project stores ([memory docs](https://docs.trae.ai/solo/memories)).

Anti-overfit gate: passes only as consolidation/projection. A new TRAE-like memory service would fail the prohibited-component rule.

## 7. Tool and MCP teardown

### 7.1 TRAE mechanisms

TRAE supports MCP over stdio, SSE, and Streamable HTTP. Its documented protocol coverage includes tool listing/calling/list-change notification, tool input/output schemas, structured content, timeouts, and server logging. It supports local/remote servers, a marketplace, manual raw JSON, project `.trae/mcp.json`, `${workspaceFolder}`, startup/run timeouts, and per-agent selection of servers/tools. Sources: [MCP overview](https://docs.trae.ai/ide/model-context-protocol), [add MCP servers](https://docs.trae.ai/ide/add-mcp-servers), [use MCP servers in agents](https://docs.trae.ai/ide/use-mcp-servers-in-agents).

The MCP log surface is particularly concrete: users can open a server's logs or select “MCP Server Host” in the Output panel. Source: [check MCP server logs](https://docs.trae.ai/ide/check-mcp-server-logs).

The built-in Agent receives all configured MCP servers automatically, though users can disable them on its edit page. That default is convenient but violates least-privilege-by-default. Source: [use MCP servers in agents](https://docs.trae.ai/ide/use-mcp-servers-in-agents).

TRAE advises trusting workspace content before project-level MCP config and warns that third-party MCPs are not reviewed. Good warning; weak enforcement. The docs do not expose health probes, exponential backoff, circuit states, per-tool error budgets, output trust labels, schema-relaxation strategy, or argument-length controls.

### 7.2 Relative verdict

Our MCP breadth is far larger: the prompt's ground truth reports 93 servers touched, and settings allow many specialist families (`settings.json:47-60`). Breadth has become a reliability liability:

* Tavily extract was called 532 times and failed 25.75%, with 135 “not connected” failures (`corpus.json:9141-9148`).
* Tavily search failed 71.65% (`corpus.json:9130-9138`).
* The pinned summary identifies 1,293 orphaned plugin directories as the cause of Windows command-length failures. Bulk deletion was correctly stopped because “orphaned” did not reliably mean unused.

TRAE's marketplace and project config are not cures. Automatically exposing all configured servers to the primary agent would make our dead-server problem worse.

### 7.3 Port: health-aware MCP catalog and breaker

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing dispatcher/ledger, not the MCP runtime:

```text
mcp-health/v1 per server
configured -> probing -> healthy | degraded | open | disabled
last_known_positive: timestamp + probe_id
recent_failures: typed counts in rolling window
open_reason: not_connected | auth | timeout | schema | transport | unknown
retry_after, last_log_pointer, tool_inventory_hash
```

Concrete behavior:

1. SessionStart or ToolSearch runs a cheap protocol/list-tools probe only for configured-on servers, with a known-present control server first.
2. PreToolUse checks state. `open/disabled` returns a typed routing hint before the model spends a call; it does not pretend the desired work succeeded.
3. PostToolUse/PostToolUseFailure classifies transport/auth/not-connected separately from tool/business errors.
4. Two consecutive independent signals open the breaker: e.g. list-tools transport failure plus a real call's not-connected result. A repeated identical probe is not independent.
5. Half-open after a bounded cooldown; one known-positive tool-list plus a real cheap call closes it.
6. Present the server's last log pointer, state, and alternative live server in ToolSearch/monitor output.
7. Do not delete plugin directories from state labels. Directory cleanup is a separate inventory/ownership workflow with live-reference checks.

It is **almost certain (90-99%)** that suppressing calls to demonstrably disconnected MCPs will remove that failure class, because the breaker decision occurs before invocation and the corpus error is a stable “not connected” outcome. It is **likely (55-80%)** to improve task completion latency, because agents may route to healthy alternatives sooner; experiment: shadow the breaker for 200 eligible calls, measure false-open rate, avoided failures, alternative success, and latency before enforcement.

Anti-overfit gate: passes. This is a small state projection and pre-tool decision on the existing bus, not another MCP gateway or daemon.

### 7.4 Structured output lesson

TRAE's MCP docs explicitly support `outputSchema` and Structured Content, but they offer no evidence that its agents avoid over-strict schemas. Our 22.9% `StructuredOutput` failure rate means copying structured fan-out naively is harmful (`corpus.json:8964-8992`). Prefer a two-stage receipt:

1. accept a minimal envelope (`status`, `artifact_pointer`, `summary`, optional `evidence[]`);
2. validate specialized payloads after persistence, with partial results retained and exact field errors returned for repair.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is **very likely (80-90%)** to reduce schema-induced total loss because 294 observed failures share required-field mismatch signatures; the experiment is replaying the recorded StructuredOutput samples against minimal-envelope-plus-post-validation and counting retained usable payloads.

## 8. Permission model teardown

### 8.1 What TRAE gets right

Subagent Markdown frontmatter supports:

* `tools` allowlist;
* `disallowedTools` deny list, which takes precedence;
* `mcpServers` server allowlist;
* individual `mcp__server__tool` selection;
* behavioral boundaries in the system prompt, with official read-only reviewer/security examples.

Project subagents override same-name user subagents. Sources: [TRAE subagents](https://docs.trae.ai/ide/subagents), [built-in Agent tool editing](https://docs.trae.ai/ide/built-in-agent).

That is good least-privilege ergonomics and is worth matching in every provider-native agent descriptor.

### 8.2 What is worse

TRAE's “Auto Run” command mode is explicitly outside the sandbox and “bypasses all security checks.” External MCP connections require explicit authorization only the first time; automatic MCP execution can then proceed without per-call confirmation. Deleted files from the built-in deletion tool go to the OS recycle bin/trash. Source: [auto-run & security](https://docs.trae.ai/ide/auto-run-and-security).

This is not a safe permission model; it is a convenience switch plus warnings. Our live configuration is also unsafe by default: Claude uses `bypassPermissions`, Codex uses `approval_policy = never` and `sandbox_mode = danger-full-access` (`claude/settings.json:64-75`; `codex/config.toml:6-7`). TRAE should not be used to rationalize our current setting.

TRAE is better only in making recoverable deletion an explicit product behavior. It is worse in implying that first-use MCP authorization and trusted workspace warnings meaningfully contain later tool behavior.

### 8.3 Port verdict

**NATIVE (Claude Code already does this; we just enable it).** Apply tool restrictions and worktree/sandbox isolation per agent. A normalized descriptor can map:

```yaml
capabilities:
  allow: [Read, Glob, Grep]
  deny: [Write, Edit, Bash]
  mcp_servers: [github]
  mcp_tools: [mcp__github__get_issue]
isolation: worktree|sandbox|none
approval: ask-risky|never-write|provider-default
```

Provider adapters translate into Claude agent frontmatter/permissions and Codex role/sandbox config. No policy engine is required.

It is **very likely (80-90%)** that explicit least-privilege profiles reduce blast radius without material loss for read-only reviewers, because TRAE's examples and our own reviewer agents use naturally separable toolsets. ## 14. Replacement decision

### Keep and evolve the current harness

The decision is **very likely (80-90%)** correct because:

* measured failures are concentrated and mechanically addressable: MCP liveness, strict schemas, plugin-path inflation, shell quoting, fetch connectivity, and read-before-write;

* TRAE's unique advantages are mostly projections and product affordances that can ride the existing bus;
* replacement loses hook programmability and cross-provider specialization while retaining permission/context opacity;
* a Work-style cloud control plane violates the anti-overfit constraint.

This does not endorse incrementalism for its own sake. If a disposable bake-off shows TRAE achieving materially higher outcome quality on the owner's real task distribution at lower total intervention and failure cost, replacement remains on the table. The current evidence does not show that.

Run 30 sanitized tasks sampled across the actual owner distribution, including coding, research, Windows automation, reverse engineering, document work, and multi-agent coordination. Compare current harness and TRAE Work/IDE on:

Replacement becomes credible only if TRAE wins outcome quality and intervention burden without losing safety/auditability. It is **unlikely (20-45%)** on current evidence, but this bake-off is the mechanically relevant settlement experiment.
