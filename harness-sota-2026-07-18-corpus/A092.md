## Why the missing files are decisive at runtime

Anthropic's current official documentation states two distinct precedence rules:

1. If `managed-mcp.json` is deployed, Claude Code loads only servers it defines; user, project, plugin, and claude.ai MCP servers cannot be used. This makes the managed file an exclusive control plane, not merely a higher-precedence duplicate source: [Control MCP server access for your organization](https://code.claude.com/docs/en/managed-mcp).
2. Without managed-exclusive control, duplicate configured servers resolve by scope: local, then project, then user, then plugin, then claude.ai connector. Manual scopes match duplicates by name; plugin/connector duplicates are also detected by endpoint: [Connect Claude Code to tools via MCP](https://code.claude.com/docs/en/mcp#scope-hierarchy-and-precedence).

Those rules are direct primary-source evidence for the runtime algorithm, but they cannot tell us which branch this machine currently takes. A prior audit claim says a bounded `Test-Path` on 2026-07-18 found the managed file missing (`/local_disk0/codexwork/bundle/inputs/audit-findings/A25.md:9-15`). Per the program brief, audit findings are claims rather than facts; that dated observation cannot substitute for reading the current 2026-07-19 file. It is **likely (55-80%)** that the managed file was still absent when this bundle was packed, because the prior audit observed absence on the preceding day and the bundled user settings still carry user/plugin MCP-oriented permissions and plugin enablement (`/local_disk0/codexwork/bundle/claude/settings.json:26-63,539-637`); this remains **UNVERIFIED**, and `Get-Item 'C:\Program Files\ClaudeCode\managed-mcp.json'` plus `claude mcp list` in a fresh Windows session is the experiment that settles it.
