## Collision register

### C1 — unconditional immutability versus PHP-scoped preference

**Class:** CONTRADICTION

**Artifacts and exact conflicting lines:**

- `rules/common/coding-style.md:23-33`: “Immutability (CRITICAL)”; “ALWAYS create new objects, NEVER mutate existing ones.”
- `rules/common/coding-style.md:61-68`: completion requires “No mutation (immutable patterns used).”
- `rules/php/coding-style.md:16-20`: only “Prefer immutable DTOs and value objects” across service boundaries, use readonly/immutable constructors “where possible,” and retain arrays for simple maps.

The common rule forbids all object mutation without qualification; the PHP rule limits strong immutability guidance to boundary objects and explicitly uses conditional language. Both apply to `**/*.php` (`common/coding-style.md:1-20`; PHP rule `:1-5`). Treating both literally makes ordinary stateful PHP application code fail the common checklist even though the PHP layer only expresses a preference.

**Precedence:** `rules/README.md:93-104` says PHP-specific rules win over common defaults. AGENTS section 10 does not mention this rule-to-rule layer. Thus the PHP scope controls, but the intended override remains implicit and brittle.

**Specific resolution — CONFIG:** Replace the common absolute with a default principle (“avoid shared or non-local mutation; allow local mutation when idiomatic and contained”) and add an explicit PHP override sentence: “For PHP, this section replaces the common absolute no-mutation rule; immutable value/boundary objects are required when practical, while local mutation inside an encapsulated implementation is allowed.” Keep `readonly` conditional on the repository’s supported PHP version. This is **very likely (80-90%)** to remove contradictory agent behavior because it changes the two exact modal conflicts (`ALWAYS/NEVER` versus `Prefer/where possible`) and follows the package’s documented specific-over-general mechanism (`README.md:93-104`).

### C2 — DTO is mandatory before domain logic, but PHP security permits non-DTO boundary validation

**Class:** CONTRADICTION

**Artifacts and exact conflicting lines:**

- `rules/php/coding-style.md:35-36`: “Convert framework/request input into validated DTOs before it reaches domain logic.”
- `rules/php/security.md:11-15`: validate at the framework boundary using “`FormRequest`, Symfony Validator, **or** explicit DTO validation.”

The coding rule requires a validated DTO before domain entry. The security rule explicitly treats framework validation and DTO validation as alternatives. A Laravel `FormRequest` can validate input while downstream code still receives an array; that satisfies `security.md` but not `coding-style.md`. The two files are same-language, same rule-package level. AGENTS section 10 and `rules/README.md` do not resolve a same-level PHP-vs-PHP collision, so it must be surfaced rather than silently choosing one.

**Specific resolution — CONFIG:** Separate validation from mapping: “Validate at the request boundary using the project framework. Before data enters domain logic, map non-trivial/business-critical input to a typed command/DTO; simple transport-only maps may remain arrays.” Mirror the same sentence in `security.md` or leave one canonical sentence and cross-reference it. This is **very likely (80-90%)** to reconcile both artifacts because it preserves the security boundary requirement while aligning with the target’s own simple-map/business-critical distinction (`coding-style.md:20`).

### C3 — formatter/analyzer policy is duplicated with different activation thresholds

**Class:** REDUNDANCY

**Artifacts and exact overlapping lines:**

- `rules/php/coding-style.md:22-26`: use PHP-CS-Fixer or Pint; use PHPStan or Psalm; keep Composer scripts checked in for local/CI parity.
- `rules/php/hooks.md:13-19`: configure PostToolUse; auto-format edited PHP with Pint/PHP-CS-Fixer; run PHPStan/Psalm “after PHP edits in typed codebases.”

This is not merely benign repetition. The target sounds unconditional (“Use”), whereas the hooks rule conditions analysis on a typed codebase and demands post-edit execution. Neither identifies repository configuration as the source of truth or defines what happens when only one tool is installed. AGENTS section 10 offers no precedence between same-level first-party PHP rule files.

**Specific resolution — CONFIG:** Make `coding-style.md` the policy source and `hooks.md` only the execution pointer. Suggested policy: “Use the formatter and static analyzer already configured by the repository; do not introduce or switch tools without project authority. Expose canonical commands through Composer scripts.” Then make `hooks.md` say the hook discovers and invokes those canonical scripts when present. This is **very likely (80-90%)** to prevent tool-choice drift because both current alternatives and their inconsistent activation conditions occur on the cited lines.

### C4 — array-to-DTO threshold is restated differently

**Class:** REDUNDANCY

**Artifacts and exact overlapping lines:**

- `rules/php/coding-style.md:18-20`: immutable DTOs/value objects for service-boundary data; arrays remain for simple maps; business-critical structures become classes.
- `rules/php/patterns.md:15-18`: replace “shape-heavy associative arrays” with DTOs for requests, commands, and external API payloads; use value objects for constrained concepts.

The policies point in the same direction, but use three thresholds—“crossing service boundaries,” “business-critical,” and “shape-heavy”—without saying whether any one is sufficient. That creates inconsistent review findings even though it is not a direct prohibition/permission conflict. Same-level precedence is unresolved.

**Specific resolution — CONFIG:** Put one decision test in `patterns.md` and cross-reference it from style: require a DTO/value object when a shape is reused, crosses an application/domain boundary, has invariants, or is business-critical; permit arrays for local one-off maps without invariants. This is **likely (55-80%)** to reduce inconsistent reviews because it replaces three subjective thresholds with observable criteria, evidenced by the three phrasings above.
