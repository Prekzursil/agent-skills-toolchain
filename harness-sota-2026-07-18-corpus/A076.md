## Runtime precedence model — verified rather than assumed

The runtime outcome depends on the kind of hook result, not its textual intensity.

1. A custom agent body is its system prompt; the tool list removes unavailable tools. Claude Code’s official subagent documentation says the body becomes the system prompt, subagents get the specified tools, and custom agents also load normal project/user memory. Source: [Create custom subagents](https://code.claude.com/docs/en/sub-agents).
2. A settings `PreToolUse` hook runs after the model has formed a tool call but before the tool executes. Exit 2 blocks the tool. A JSON `permissionDecision: "deny"` also denies it. Therefore a real blocking hook wins mechanically over an agent’s wish to perform that call; this is control flow, not LLM instruction precedence. Source: [Hooks reference — exit code output and PreToolUse](https://code.claude.com/docs/en/hooks).
3. Exit 0 plus `additionalContext` is advisory context. It does not retract the agent system prompt or itself choose an action. When multiple hooks match, all commands run to completion and Claude Code merges their results. Source: [Automate workflows with hooks](https://code.claude.com/docs/en/hooks-guide).
4. `Stop` exit 2 prevents stopping and continues the conversation; `SubagentStop` decision `block` keeps the subagent running. Source: [Hooks reference — exit code 2 behavior](https://code.claude.com/docs/en/hooks).
5. The local dispatcher is a stricter special case. Its contract says it “Never blocks (exit 0 only)” at `~/.claude/hooks/_dispatch/dispatch.py:41-45`; it invokes child `main()` without using the return value at `~/.claude/hooks/_dispatch/dispatch.py:167-179`, catches `BaseException` at `~/.claude/hooks/_dispatch/dispatch.py:182-189`, extracts only `additionalContext` at `~/.claude/hooks/_dispatch/dispatch.py:192-212`, and always returns 0 at `~/.claude/hooks/_dispatch/dispatch.py:286-329`. Consequently no child behind this dispatcher can mechanically outrank an agent through its own `return 2`.

Two independent signals validate the blocking part of this model:

- Static: `no-force-push/hook.py` writes the reason and returns 2 at `~/.claude/hooks/no-force-push/hook.py:45-58`; its settings matcher is Bash at `~/.claude/settings.json:151-160`.
- Execution: direct hook invocation produced `rc=0` for `git push origin feature`, and `rc=2` for both `git push --force origin main` and `git push --force-with-lease origin master`, with stderr beginning `Tripwire: refusing git push --force.`

Confidence that a registered exit-2 PreToolUse gate mechanically wins on the Windows host is **almost certain (90-99%)**, supported independently by the direct process result and current official host semantics. The remaining uncertainty is only whether a particular hook process is disabled, killed by timeout, or fails open on the Windows machine.
