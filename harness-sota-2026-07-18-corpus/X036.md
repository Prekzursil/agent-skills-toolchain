# X036 — Cross-domain borrow: aviation safety → trust calibration

**Unit:** X036  
**Source field:** aviation safety (normal-operations observation, Threat and Error Management, crew resource management, challenge–verification–response checklists, protected reporting, and automation-surprise research)  
**Target:** knowing how much to rely on an agent output, conditional on the agent and task type  
**Research boundary:** external ideation only. Per the unit instruction, I did not inspect or make claims about the local subject repository. URLs below are the evidence. Sources were accessed 2026-07-19.

## Executive conclusion

The useful aviation borrow is **not a pilot-style score attached to an agent**. Aviation's stronger solution is an **operational assurance loop**: anticipate the threats of this operation; make the active automation mode visible; divide producing from monitoring; verify a short list of consequential states by challenge and response; observe ordinary operations rather than learning only from accidents; and protect reports that expose weak signals. The object being calibrated is therefore **reliance on this actor, in this operating context, under this verification regime**, not confidence in the actor as an enduring personal trait.

The transfer is **very likely (80-90%)** to be structurally sound at that level, because both domains involve a fallible actor/automation combination, context-dependent performance, hidden or misunderstood internal state, rare but costly errors, and a human who must decide when to monitor or intervene. Aviation's own mechanisms explicitly address normal-operation data, mode awareness, independent monitoring, and precursor reporting: ICAO describes LOSA as trained observation of crew behavior and situational factors on normal flights ([ICAO, LOSA Doc 9803 description](https://store.icao.int/en/line-operations-safety-audit-losa-doc-9803)); NASA identifies lack of current/future automation-state awareness as a source of automation surprise ([Sarter, Woods, and Billings, NASA NTRS](https://ntrs.nasa.gov/citations/20040112190)); and FAA checklist guidance assigns verification across two crew roles ([FAA TSWG report, §2.1.1](https://www.faa.gov/sites/faa.gov/files/Revised-HS125-Curriculum-Report-20Feb24.pdf)).

The transfer is **unlikely (20-45%)** to remain valid if implemented as one scalar “agent trust score.” Evidence for that judgment is the source field itself: Threat and Error Management distinguishes threats, errors, and resulting operational states; LOSA observes situational factors and error management, not merely actor identity ([ICAO AN-Conf/11-WP/39, §§4.1–4.4](https://www.icao.int/sites/default/files/Meetings/AMC/MA/Eleventh%20Air%20Navigation%20Conference%20%28ANConf11%29/anconf11_wp039_en.pdf)); and FAA Safety Assurance continuously reassesses controls as the operational environment changes ([FAA Order 8000.369A, Safety Assurance](https://www.faa.gov/documentLibrary/media/Order/8000.369A.pdf)). A scalar would erase task class, consequence, tool/mode, verification coverage, version, sample size, and recency—the variables that make the evidence actionable.

My recommended design is an **Operational Reliance Envelope** with five small mechanisms on the existing hook/skill/MCP bus:

1. a pre-task Threat and Verification Brief;
2. explicit Agent Mode Annunciation;
3. a consequence-weighted Challenge–Evidence–Response acceptance gate;
4. a task-stratified Normal Agent Operations Sample feeding evidence cards; and
5. a protected near-miss/correction channel used for learning, not punishment.

The predicted value of the complete loop is **likely (55-80%)**, based on the close process correspondence and authoritative aviation evidence above, but it is **UNVERIFIED; a preregistered shadow-mode trial comparing decision loss, unnecessary verification, and undetected material-error rates against the current workflow would settle it**. The recommendation headings below inherit that UNVERIFIED status and define narrower experiments.

## 1. What aviation has actually solved

### 1.1 Threat and Error Management: trust the managed operation, not an error-free operator

In its own field, Threat and Error Management (TEM) starts from the premise that threats and errors are routine parts of flight, not exceptional proof that a pilot is untrustworthy. ICAO defines threats as external events that increase complexity and risk, errors as crew actions or inactions that deviate from intentions or expectations, and the TEM framework as a quantifiable way to record both and how crews manage them ([ICAO AN-Conf/11-WP/39, §§4.1–4.4](https://www.icao.int/sites/default/files/Meetings/AMC/MA/Eleventh%20Air%20Navigation%20Conference%20%28ANConf11%29/anconf11_wp039_en.pdf)). An error can be detected and corrected before it produces an undesired aircraft state; the management response is therefore as important as raw error incidence.

That is a direct correction to naive agent calibration. “Agent A made an error” is less operationally useful than:

- what task and threat conditions were present;
- what deviation occurred;
- whether the agent disclosed, detected, corrected, or compounded it;
- whether an independent control trapped it; and
- what consequential state, if any, escaped.

Translated taxonomy:

| Aviation TEM term | Harness term | Example |
|---|---|---|
| Threat | Context that raises error likelihood but is not itself an agent error | stale source, ambiguous request, huge repository, unavailable tool, context compaction, conflicting instructions |
| Error | Deviation from task intent or acceptance criterion | unsupported claim, wrong file, malformed invocation, omitted constraint |
| Managed error | Deviation detected and contained before acceptance | agent flags uncertainty, test fails, verifier rejects claim, retry corrects output |
| Undesired state | User/workspace is placed in a materially bad state | wrong edit accepted, destructive action on wrong target, false research conclusion delivered |
| Countermeasure | Prevention, detection, or recovery control | brief, mode display, source check, test, diff review, rollback |

This reframing catches two failures a correctness-only score misses: a frequently self-correcting agent can look worse than a confidently wrong agent if every intermediate error is counted equally; and a low raw error rate can look reassuring even when the rare errors routinely escape into high-consequence states.

### 1.2 LOSA and safety assurance: measure normal work, not only crashes and complaints

LOSA uses expert, trained observers to collect data about crew behavior and situational factors on **normal flights** ([ICAO, LOSA Doc 9803 description](https://store.icao.int/en/line-operations-safety-audit-losa-doc-9803)). The ICAO conference paper explains the reason: occurrence-derived data alone miss the processes, errors, and failures visible during uneventful operations; systematic line observations reveal organizational strengths and weaknesses before an occurrence ([ICAO AN-Conf/11-WP/39, §§2–3](https://www.icao.int/sites/default/files/Meetings/AMC/MA/Eleventh%20Air%20Navigation%20Conference%20%28ANConf11%29/anconf11_wp039_en.pdf)). FAA Safety Assurance similarly combines data acquisition, analysis, system assessment, and corrective action, and continuously monitors whether controls remain effective ([FAA SMS components](https://www.faa.gov/about/initiatives/sms/explained/components); [FAA Order 8000.369A](https://www.faa.gov/documentLibrary/media/Order/8000.369A.pdf)).

This is the most important answer to “per agent and per task type.” A harness needs a denominator: not a scrapbook of memorable failures, but sampled ordinary attempts labeled by agent version, task family, threat context, outcome, and error-management result. It must retain successes, managed errors, and escaped errors. Otherwise, correction reports estimate salience, not reliability.

Aviation also supplies an important restraint. LOSA's observer is trained and applies a stable taxonomy; it is not simply the same pilot grading their own flight. An agent's prose self-confidence or self-review is not mechanically independent evidence. A harness observation counts as verified only when it is tied to an external acceptance signal such as tests, artifact inspection, source support, a deterministic checker, or later owner adjudication.

### 1.3 Challenge–verification–response: an acceptance protocol, not ceremonial checklist completion

The NASA/FAA human-factors report distinguishes a challenge–verification–response checklist from a do-list. In the former, one pilot calls the item, both pilots verify the actual configuration, and the other pilot states the verified status; this provides configuration and mutual redundancy. The report also warns that a call–do–response sequence loses that configuration redundancy and that interruption can allow mistakes to pass unnoticed ([Degani and Wiener, *Human Factors of Flight-Deck Checklists*, pp. 18–19](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). Current FAA training guidance likewise says that disagreement must be resolved before continuing and that the monitoring pilot announces checklist completion ([FAA TSWG report, §2.1.1](https://www.faa.gov/sites/faa.gov/files/Revised-HS125-Curriculum-Report-20Feb24.pdf)).

The important mechanism is not “add a checklist.” It is:

1. **challenge:** name the consequential claim or state;
2. **verification:** inspect the state or evidence, rather than echoing the producer's assertion;
3. **response:** report the observed status in constrained language; and
4. **closure:** do not declare completion while a challenge is unresolved.

For an agent harness, “tests pass” must not be accepted merely because the producing agent says it. The response should be bound to an independently captured test result, inspected diff, resolved citation, schema validation, or other task-specific evidence. The verifier can be deterministic and need not be another model.

This catches completion theater: claims of tests that were not run, citations that do not entail the claim, edits outside scope, hidden unresolved errors, and a verifier merely paraphrasing the producer.

### 1.4 CRM: formally empower monitoring and disagreement

FAA Crew Resource Management guidance makes communication, inquiry, advocacy, assertion, interactive briefings, critique, and explicit division of automation duties trainable operational behaviors. It says automation programming actions may need to be verbalized and acknowledged, and it distinguishes pilot-flying from pilot-monitoring duties ([FAA AC 120-51E, CRM behavioral markers](https://www.faa.gov/sites/faa.gov/files/2022-11/AC120-51e_0.pdf)). The earlier AC text also emphasizes debriefing the process followed, recognizing effective and ineffective team behavior, and advocating a conflicting course when necessary ([FAA AC 120-51D, §12](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-51D.pdf)).

The harness translation is a role contract, not extra agent chatter. The producer proposes and acts. The monitor is authorized to say `DISAGREE`, identify the exact challenged state, and block acceptance at a predeclared threshold. A debrief evaluates the process and control failure, not an agent persona.

This catches social and orchestration failure modes: a subordinate reviewer yielding to a confident producer, two agents assuming the other checked a claim, an owner believing “reviewed” means “verified,” and retrospective critique with no authority to stop acceptance.

### 1.5 Automation surprise: reveal current state, future behavior, and authority

Sarter, Woods, and Billings define mode-awareness trouble as lack of awareness of the automation's current and future status and behavior; pilots then encounter an unexpected automation action or failure to behave as anticipated ([NASA NTRS record 20040112190](https://ntrs.nasa.gov/citations/20040112190)). NASA's formal-methods work names invisible-effect transitions as a detectable source of mode confusion—for example, a crew input that has no visible flight-deck effect ([NASA Langley, Mode Awareness](https://shemesh.larc.nasa.gov/fm/fm-collins-mode.html)). ASRS examples describe unrecognized mode transitions and the resulting “What is it doing now?” problem ([NASA ASRS CALLBACK 456](https://asrs.arc.nasa.gov/publications/callback/cb_456.html)).

For an agent, the corresponding “mode” includes model/version, role, tool availability, write authority, sandbox/network state, active task phase, context or compaction status, source cutoff/freshness, and the next consequential action. A polished answer can conceal that the agent silently moved from sourced research to memory, from planning to mutation, from full context to a summary, or from a working tool to fallback behavior.

This catches automation surprise that output-level confidence cannot: the same surface fluency produced under materially different capabilities and constraints.

### 1.6 Protected reporting and blameless review: useful data, with a major disanalogy

NASA ASRS accepts voluntary safety reports, removes identifying details, and is institutionally separated from FAA enforcement. FAA commits not to use qualifying ASRS reports in enforcement and provides limited penalty-waiver incentives; accidents, criminal activity, deliberate violations, and other specified cases are exceptions ([NASA ASRS confidentiality](https://asrs.arc.nasa.gov/overview/confidentiality.html); [NASA ASRS immunity policy](https://asrs.arc.nasa.gov/overview/immunity.html); [NASA ASRS caveats](https://asrs.arc.nasa.gov/overview/caveats.html)). FAA's Aviation Safety Action Program similarly uses enforcement-related incentives to elicit safety information that employees might otherwise withhold ([FAA ASAP](https://www.faa.gov/about/initiatives/asap)). The system is “blameless” only in a bounded, accurate sense: it protects inadvertent reports to improve learning; it does not abolish accountability.

Only half of this transfers. Human reporters can rationally fear discipline, so confidentiality and enforcement separation change reporting incentives. A language model does not fear punishment or possess a career. Therefore, “be blameless toward the agent” is anthropomorphic and **almost certainly not (1-5%)** the operative causal mechanism, based on the absence of the human incentive that ASRS explicitly addresses. What transfers is separation of channels: a near-miss report used to discover systemic precursors should not automatically lower an agent's reliability estimate as if disclosure itself were failure. Otherwise the metric rewards silent, confidently escaped errors over disclosed and contained errors.

This catches Goodhart pressure in the harness: suppressing uncertainty, hiding retries, or treating honest `UNVERIFIED` outputs as worse than unsupported certainty. It does not justify ignoring deliberate policy violations, destructive actions, or escaped harm.

## 2. The concrete harness design: Operational Reliance Envelope

The envelope is a decision aid that answers:

> Given this agent identity/version, task family, threat context, consequence, and proposed verification regime, what evidence supports accepting this output, and what remains unknown?

It deliberately does **not** answer “How trustworthy is Agent A?”

### 2.1 UNVERIFIED proposal — Threat and Verification Brief

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Before execution, require a compact machine-readable brief:

```json
{
  "task_family": "research_claim | code_change | diagnosis | destructive_op | communication | other",
  "consequence": "low | medium | high | irreversible",
  "threats": ["ambiguous_acceptance", "stale_source", "tool_unavailable"],
  "acceptance_checks": [
    {"claim": "artifact exists at requested path", "evidence": "filesystem_stat", "required": true},
    {"claim": "material factual claims are supported", "evidence": "source_entailment_sample", "required": true}
  ],
  "abort_or_escalate_on": ["scope_conflict", "unverifiable_high_consequence_claim"]
}
```

For low-consequence work, the brief can be inferred from defaults and displayed without blocking. For high-consequence or irreversible work, unresolved acceptance criteria stop execution or require owner confirmation. The brief should name only the few states whose wrongness changes the user's decision; a long generic checklist recreates the very checklist-completion problem aviation human-factors work warns about.

**Predicted catch:** The mechanism is **likely (55-80%)** to reduce cases where an agent produces a plausible deliverable that cannot establish the user's actual acceptance criterion, because it moves verification design before production and mirrors TEM's anticipatory briefing. This is **UNVERIFIED; randomly assign comparable tasks to brief/no-brief conditions and score acceptance-criterion omissions and owner rework to settle it**.

**Anti-overfit gate:** This is a schema/prompt on the existing task path. It adds no scheduler, memory service, critic model, or policy runtime.

### 2.2 UNVERIFIED proposal — Agent Mode Annunciator

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Render a one-line, event-updated status block from facts already known to the harness:

```text
MODE research/sourced | model=<id+version> | tools=web,read | writes=artifact-only
CTX full, 61% | net=on | source-freshness=live | phase=verify | NEXT write X036.md
MODE-CHANGE tool:web→unavailable  REPLAN required
```

Required fields are current role/task phase, model/version, effective tools, authority/scope, context state, evidence mode (`sourced`, `local-observation`, `memory`, `inference`), and next consequential action. Changes must be event-driven and conspicuous. An input with no visible effect and a mode transition with no annunciation are defects, following NASA's mode-awareness framing.

**Predicted catch:** It is **very likely (80-90%)** to expose silent capability/authority transitions when the harness can observe those transitions, because those fields are direct state rather than model self-report. It is only **roughly even (45-55%)** to change user intervention behavior, because users may habituate to status displays; these are **UNVERIFIED claims, settled by fault-injection tests for detection coverage plus an A/B study measuring noticed transitions and correct interventions**.

**Anti-overfit gate:** A hook reads and displays existing runtime state. No new orchestration runtime or durable state engine is needed. If a field cannot be directly observed, show `UNKNOWN`; do not ask the model to invent it.

### 2.3 UNVERIFIED proposal — Challenge–Evidence–Response acceptance gate

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

At declared acceptance boundaries, emit one record per consequential item:

```text
CHALLENGE  requested file is present and nonempty
EVIDENCE   fs.stat /exact/path: size=18342, exit=0, captured=2026-07-19T...
RESPONSE   VERIFIED

CHALLENGE  recommendation X follows from source Y
EVIDENCE   source resolved; entailment not independently checked
RESPONSE   UNVERIFIED
```

Allowed responses are `VERIFIED`, `DISPUTED`, `UNVERIFIED`, and `NOT-APPLICABLE`, each with provenance. `VERIFIED` requires a check mechanically distinct from the producing assertion. Examples:

- code: test process output plus diff/scope inspection;
- research: source resolution plus sampled claim-to-source entailment;
- file delivery: direct filesystem metadata plus content sentinel;
- destructive operation: independently resolved explicit target plus recoverability check;
- structured output: parser/schema result, not visual plausibility.

The same model may design the challenge, but it may not supply the sole evidence for its own claim. Deterministic checks are preferred; a second model is used only for irreducibly semantic checks and must be labeled as correlated judgment, not independence.

**Predicted catch:** This gate is **very likely (80-90%)** to catch false completion claims for machine-checkable states, because acceptance becomes bound to external evidence. It is **likely (55-80%)** to catch unsupported semantic claims when only model-based entailment is available, because producer and verifier errors can correlate. Both are **UNVERIFIED; seed known false completion claims and citation non-entailments, measure recall/false-block rate separately by evidence type, and compare same-model, different-model, and deterministic verification**.

**Anti-overfit gate:** This is a small acceptance adapter dispatching existing tools. It explicitly rejects a trained critic, guardrail framework, or second orchestration runtime.

### 2.4 UNVERIFIED proposal — Normal Agent Operations Sample and task-conditional evidence cards

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Sample ordinary completed tasks—not only failures—and code them using the TEM translation. Sampling can be deterministic (for example, a hash of task ID) so agents cannot select favorable cases. The hook stores a compact event record on the existing logging path; a periodic offline reducer can generate an evidence card without a daemon.

Minimum dimensions:

- agent/model/version and configuration fingerprint;
- task family and consequence class;
- declared threats and tool/mode state;
- observable acceptance checks attempted and passed;
- errors: disclosed, externally detected, corrected, repeated, or escaped;
- resulting state: acceptable, uncertain, or materially undesired;
- human override/correction, if any;
- sample size, sampling rule, time window, and missing-outcome rate.

An evidence card should look like this:

```text
AGENT/MODEL: <versioned identity>        TASK: code-change / medium consequence
WINDOW: <dates>  N=37 sampled, 5 outcomes pending, config fingerprint=<...>
THREATS REPRESENTED: large repo 12; weak tests 9; tool outage 2; ambiguity 6
ACCEPTABLE STATE: 28/32 adjudicated
MANAGED ERRORS: 7/32                 ESCAPED MATERIAL ERRORS: 2/32
VERIFICATION COVERAGE: tests 29/32; diff-scope 24/32; semantic review 8/32
INTERVAL / ESTIMAND: <explicit method and denominator>
STATUS: EVIDENCE-SPARSE | STALE | CURRENT | CONFIG-CHANGED
DO NOT GENERALIZE TO: destructive ops, legal claims, unseen tool modes
```

Do not combine these fields into a star rating. Show a statistical interval for each declared estimand, the raw numerator/denominator, pending outcomes, and “no evidence” rather than a favorable default. A version or material configuration change starts a new stratum; old data may appear as historical context but not current assurance.

**Predicted catch:** Task stratification is **likely (55-80%)** to reveal agents that are reliable in one task/tool regime and unreliable in another, because LOSA/TEM explicitly retains situational factors and response outcomes. Normal-operation sampling is **very likely (80-90%)** to correct the denominator bias of failure-only logs if the sampling rule and outcomes are captured faithfully; the arithmetic follows directly from including sampled successes and failures. Whether the resulting cards improve owner reliance decisions is **UNVERIFIED; conduct a prospective crossover study in which decision-makers receive either aggregate history or evidence cards, then score over-reliance, under-reliance, and decision loss on held-out task/version strata**.

**Anti-overfit gate:** Event emission and an offline reducer ride existing logging/hooks. No vector database, knowledge graph, durable-execution engine, observability SaaS, or permanent evaluator service is proposed. The `<~200 lines` boundary applies to the sampler/emitter adapter; use an existing analysis path for aggregation rather than hiding a large new subsystem behind the tag.

### 2.5 UNVERIFIED proposal — protected near-miss and correction channel

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Add a structured disclosure record available to the agent, tools, and owner:

```json
{
  "kind": "near_miss | correction | uncertainty | mode_surprise",
  "task_phase": "verify",
  "observed": "source did not support the drafted claim",
  "contained_before_acceptance": true,
  "control_that_caught_it": "claim-source sample",
  "system_contributor": "search snippet overgeneralized",
  "follow_up": "narrow claim and resolve primary source"
}
```

Keep two ledgers:

- **assurance ledger:** externally adjudicated outcomes used for the evidence card;
- **learning ledger:** self-reports, corrections, surprises, and contributing conditions used to discover new threats and controls.

A self-reported near miss is not proof of correctness and does not earn reliability credit. If externally confirmed, it can be classified as a managed error. A disclosure alone must not be counted as an escaped error. Deliberate policy violations, irreversible actions, and actual escaped harm remain in the assurance ledger; this mirrors ASRS's bounded exceptions rather than a blanket “no blame” rule.

**Predicted catch:** The split is **likely (55-80%)** to preserve useful precursor detail that a pass/fail score discards, because ASRS/ASAP show why protected precursor reporting can reveal otherwise unavailable safety information. It is **unlikely (20-45%)** that “nonpunitive” wording alone will make an LLM more truthful, because the aviation incentive is human and does not transfer. These effects are **UNVERIFIED; inject hidden opportunities to disclose uncertainty and compare disclosure, silent-error, and false-alarm rates under coupled-score versus split-ledger prompts, with external adjudication**.

**Anti-overfit gate:** This is a record schema on existing event/logging paths, not a memory architecture. Retention and redaction must reuse existing policy.

### 2.6 UNVERIFIED proposal — consequence-based reliance policy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Evidence does not decide reliance without consequence. Apply the envelope as a policy matrix:

| Consequence / reversibility | Evidence condition | Default reliance |
|---|---|---|
| Low and easily reversible | sparse or stale | proceed; label uncertainty; sample verification |
| Medium | relevant/current but incomplete | require targeted acceptance checks |
| High | relevant/current and independently verified | proceed only through required gate |
| High with sparse, stale, or changed-mode evidence | any | escalate, stage safely, or require human verification |
| Irreversible | any agent history | explicit target resolution and owner-controlled authorization; history never waives the gate |

This avoids two symmetric calibration failures: over-reliance on fluent output and expensive verification of every trivial output. “Trusted agent” never bypasses a consequence-mandated check.

**Predicted catch:** A consequence-conditioned policy is **likely (55-80%)** to reduce expected harm more efficiently than uniform verification, because aviation SMS explicitly couples hazard, risk control, and continuing assurance rather than applying one control everywhere ([FAA SMS overview](https://www.faa.gov/faa-aviation-safety-outreach/safety-management-system); [FAA SMS components](https://www.faa.gov/about/initiatives/sms/explained/components)). The optimal thresholds are **UNVERIFIED; replay a labeled task set with measured verification cost and miss severity, then choose thresholds on a development slice and report held-out decision loss**.

**Anti-overfit gate:** This is a policy table evaluated at existing acceptance points. It adds no new runtime.

## 3. End-to-end operating sequence

The smallest coherent loop is:

```text
TASK ARRIVES
    |
    v
[Threat + Verification Brief] ---- consequence/acceptance criteria declared
    |
    v
[Mode Annunciator] --------------- identity, capability, authority, context visible
    |
    v
[Agent acts] --------------------- mode changes are emitted, surprises disclosed
    |
    v
[Challenge–Evidence–Response] ---- consequential states externally checked
    |                    |
  accept              dispute/unknown
    |                    |
    v                    v
[Outcome event]       recover/escalate; do not claim complete
    |
    +--> sampled normal-operation record --> evidence card by task/mode/version
    |
    +--> near-miss/correction record ------> threat/control learning ledger
```

The loop separates three questions that generic confidence collapses:

1. **Prior empirical support:** How has this version/configuration performed on comparable tasks?
2. **Present-run evidence:** Which consequential claims/states were independently checked now?
3. **Decision consequence:** What level of residual uncertainty is acceptable here?

A high historical rate cannot substitute for present-run evidence on an irreversible action. Conversely, sparse history does not require rejecting a low-consequence output whose claims can be cheaply and deterministically verified.

## 4. What this catches that conventional trust signals miss

These are target failure modes, not claims that the local harness currently exhibits; local grounding was explicitly outside this unit.

| Conventional signal | Missed failure | Aviation-derived catch |
|---|---|---|
| Agent says “high confidence” | confidence is ungrounded or miscalibrated | evidence card plus present-run evidence; self-report is not verification |
| One global success rate | strong coding performance masks weak research or destructive-operation performance | task/consequence/tool/version strata |
| Count every error against agent | honest, contained errors make an agent look worse than silent failures | TEM separation of managed error from escaped undesired state |
| Review was requested | reviewer echoed producer or checked prose rather than state | challenge–evidence–response with provenance |
| Tests passed | tests were not run, wrong tests ran, or diff exceeded scope | captured process evidence plus separate diff/scope challenge |
| No incident occurred | latent weak controls in ordinary work remain invisible | sampled normal operations and near misses |
| Same agent name | model/config/tool/context changed underneath the label | mode annunciation and evidence reset on material change |
| More automation means less monitoring | human loses current/future state awareness | visible mode, authority, and next consequential action |
| Punish disclosed uncertainty | metric selects for confident silence | learning ledger separate from outcome adjudication |
| Verify everything | cost and alert fatigue cause ritual compliance | consequence-based, short critical-item gates |

## 5. Adversarial transfer analysis

### 5.1 Structural correspondences that support transfer

**Context dependence.** Flight risk is not a stable property of the pilot; weather, airport, aircraft state, workload, and crew coordination matter. Agent performance likewise depends on task type, tool state, context, source freshness, and acceptance criteria. TEM and LOSA preserve those conditions rather than averaging them away.

**Automation surprise.** Both settings pair a human decision-maker with automation whose surface behavior can conceal a mode transition. NASA's current/future-state definition maps cleanly to an agent changing tool, evidence, authority, or context mode.

**Rare consequential outcomes.** Waiting only for disasters produces sparse, biased evidence. Normal-operation observation and precursor reports provide earlier signals, while outcome adjudication retains consequence.

**Need for independent state checks.** In both settings, a fluent verbal assertion is weaker than observing configuration. Challenge–verification–response maps from switch/indicator state to artifacts, test output, citations, and resolved targets.

**Shared need for recovery.** Error incidence alone is incomplete. Detection and containment change the resulting state, which TEM explicitly records.

Together these make process-level transfer **very likely (80-90%)**, with evidence in the cited ICAO TEM/LOSA definitions, FAA checklist method, and NASA mode-awareness research. The remaining uncertainty comes from agent-specific failure correlation and the much lower consequence/tempo of many software tasks.

### 5.2 Disanalogies that prohibit literal transfer

**A model is not a licensed pilot.** Pilots have durable identities, certification, recurrent training, embodied perception, and organizational accountability. Agent labels may front changing models, prompts, tools, and context. Therefore, personal reputation should be weak prior evidence and a configuration fingerprint should be the unit of measurement.

**Two model calls are not two crew members.** Two agents can share training data, prompting, context, and tool failures. Their agreement is not independent in the statistical or mechanical sense. Deterministic checks and direct artifact observation are stronger; model review must be labeled correlated.

**The environment is less objectively observable.** Aircraft configuration has many direct indicators. Open-ended research quality, design judgment, and user satisfaction may lack immediate ground truth. `UNVERIFIED` must remain an allowed terminal status; forcing binary closure manufactures certainty.

**Task distribution changes faster.** Aircraft types and procedures change, but agent versions, prompts, and tools can change between runs. Evidence decays faster and must be version/configuration scoped. Exact decay rates are **UNVERIFIED; a rolling holdout study measuring performance drift across model/config releases would settle them**.

**Consequences range far more widely.** Agent work spans trivial drafts to destructive infrastructure actions. Aviation's uniformly high safety orientation would overburden low-risk work. Verification must scale with consequence and reversibility.

**Humans have reporting incentives; models do not have fear.** ASRS confidentiality transfers as information architecture and organizational policy for human owners/operators, not as model psychology.

**The human may be a solo operator.** CRM assumes distributed crew roles with training and shared situational awareness. A harness may have one owner and one model. Role separation must therefore be supplied by evidence mechanisms, not a theatrical multi-agent crew.

### 5.3 Where the analogy fails outright

The analogy does **not** justify:

- treating an agent as morally blameworthy or praiseworthy;
- assigning pilot-like certification from a small benchmark;
- equating a second LLM's agreement with copilot verification;
- mandating checklists for all tasks;
- inferring real-world correctness from process compliance;
- suppressing outcome accountability in the name of “blamelessness”; or
- constructing a large safety-management bureaucracy around a lightweight agent loop.

If the proposed system requires any of those assumptions, this unit's conclusion is “do not transfer.”

## 6. Measurement plan and falsification criteria

The proposal should earn adoption by improving calibrated reliance, not by producing attractive dashboards.

### 6.1 Primary study

Run the mechanisms first in shadow mode on a preregistered, stratified stream of tasks. Include task families, model/configuration versions, consequence classes, tool outages, ambiguous requirements, and context changes. Preserve a held-out period or held-out task strata.

Compare:

- current workflow;
- evidence card only;
- present-run challenge gate only; and
- full Operational Reliance Envelope.

Primary outcomes:

- **undetected material-error rate:** material errors accepted without appropriate warning;
- **over-reliance rate:** accepted when the consequence policy says evidence was insufficient;
- **under-reliance rate:** rejected/escalated despite adequate verified evidence;
- **decision loss:** severity-weighted misses plus verification/escalation cost;
- **verification yield:** material defects found per unit verification effort;
- **coverage:** fraction of declared consequential claims with mechanically independent evidence;
- **mode-surprise detection:** injected observable transitions announced and noticed;
- **calibration by stratum:** predicted acceptable-state rate against adjudicated outcome, always with sample size and interval.

Secondary outcomes:

- owner rework;
- false blocks;
- time/latency and token/tool overhead;
- disclosure rate and false disclosure rate;
- unresolved `UNVERIFIED` rate;
- behavior after configuration change;
- missing or delayed ground truth.

### 6.2 Mechanically independent validation

For each claimed control, use two different signals where feasible:

- file delivery: filesystem metadata **and** required content/sentinel parse;
- code correctness: test process **and** diff/acceptance review;
- citation: URL/source resolution **and** claim-entailment inspection;
- mode: runtime event state **and** an injected known transition the detector must find;
- absence: first demonstrate the detector finds a known-present item, then use a second field or mechanism before claiming absence;
- task outcome: automated acceptance evidence **and** sampled owner/expert adjudication.

Re-running the same command is not independence. A second model reading the same context is also not mechanically independent.

### 6.3 Kill and rollback criteria

Reject or narrow the borrow if any of the following holds on held-out data:

- decision loss does not improve after verification cost is included;
- mode displays are frequently wrong or ignored;
- reviewers mostly echo producers and deterministic checks cannot cover consequential states;
- task strata are too sparse to support decisions, yet the UI encourages generalization;
- disclosed near misses are used as punishment and disclosure collapses;
- checklist burden raises bypass/ritual-completion behavior;
- false blocks delay high-value work more than caught errors justify; or
- maintaining the mechanism requires a prohibited second runtime, durable-execution system, vector/KG memory, trained critic, observability SaaS, or guardrail framework.

The overall architecture is **roughly even (45-55%)** to survive unchanged after a real shadow trial, because the mechanisms have different observability and cost profiles; this is **UNVERIFIED, and the factorial comparison above would identify which components merit retention**. That is not an argument against the trial. It is a reason to deploy the pieces independently and retain only measured value.

## 7. Alternatives considered and rejected

### 7.1 Universal agent trust score — reject

A universal score compresses unlike tasks and hides configuration change, sample size, verification coverage, and outcome severity. It invites threshold gaming and false precision. Aviation's TEM/LOSA structure is evidence against this abstraction, not support for it.

### 7.2 Self-reported confidence as the primary signal — reject

Self-confidence can be retained as one diagnostic feature, but it is not an acceptance check. It is produced by the same system whose correctness is in question and is therefore not mechanically independent.

### 7.3 Always use a second agent as copilot — reject

This confuses social role diversity with error independence. Correlated model failures can produce confident consensus, adds cost to low-risk tasks, and drifts toward a second orchestration runtime. Use direct evidence first; reserve model review for semantic judgments and label it correlated.

### 7.4 Full safety-management service/daemon — reject under the anti-overfit gate

FAA/ICAO SMS is an organization-wide governance system, but importing the institution would be cargo cult. The target needs a few assurance primitives on its existing bus, not a parallel runtime. The 100-line-loop anti-overfit warning in the unit brief reinforces this rejection.

### 7.5 Pure post-mortem program — reject as insufficient

Post-mortems learn after an occurrence. LOSA's specific contribution is to observe normal work and managed errors before a serious outcome. Retain debriefs for material surprises, but do not make them the only signal.

### 7.6 Checklist on every output — reject

The NASA/FAA checklist report itself distinguishes verification redundancy from step-following and warns about interruption-sensitive do-lists. The transfer is a short, consequence-selected acceptance gate, not maximum checklist volume.

## 8. Minimal adoption sequence

Each stage can be evaluated and removed independently:

1. **CONFIG (settings/JSON only):** define task family, consequence, threats, and required acceptance checks.
2. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** expose observable mode and transition events; validate with known injected transitions.
3. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** implement challenge–evidence–response for file, process, schema, and source checks.
4. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** sample normal operations and emit TEM-coded compact events.
5. **CONFIG (settings/JSON only):** split learning disclosures from externally adjudicated assurance outcomes.
6. Evaluate in shadow mode; retain only components that reduce held-out decision loss.

The adoption sequence is **likely (55-80%)** to remain within the existing bus and avoid a large runtime if each adapter stays within its stated boundary, because all stages are configuration, event emission, display, or acceptance dispatch. This is **UNVERIFIED; an implementation spike with line count, dependency, latency, and state-retention budgets would settle it before production adoption**.

## 9. Gaps and limits

- No local harness inspection was performed, by instruction. Consequently, statements above describe target failure modes and proposed mechanisms, not verified absences or defects in the current subject.
- LOSA's detailed coding manual is sold by ICAO. This unit relied on ICAO's official description and conference working paper, not an unlicensed copy. Exact LOSA observer-training and sampling procedures beyond those public descriptions are **UNVERIFIED; access to ICAO Doc 9803 and a procedure-by-procedure comparison would settle fidelity**.
- The cited checklist report is older, although current FAA training guidance independently confirms challenge/response, cross-confirmation, disagreement resolution, and explicit completion. This is two temporally distinct official signals for the core mechanism, not evidence that every checklist-design recommendation generalizes.
- ASRS data are voluntary reports, not an unbiased incidence estimator. They support the reporting-channel mechanism and illustrate automation surprises; they do not establish event prevalence. NASA's own program description identifies submissions as voluntary ([NASA ASRS confidentiality](https://asrs.arc.nasa.gov/overview/confidentiality.html)).
- No claim is made that aviation has solved LLM calibration statistically. Aviation supplies operational mechanisms and failure taxonomies. The statistical estimands, intervals, version reset rules, and decision thresholds require harness-specific validation.
- The best definition of “material error” varies by task. A stable, owner-approved adjudication rubric is a prerequisite for comparing variants. Its cross-rater reliability is **UNVERIFIED; double-blind adjudication of a stratified sample and agreement/error analysis would settle it**.
- Logging can itself expose sensitive prompts, artifacts, or identities. This unit proposes reuse of existing retention/redaction policy and does not establish that such policy is adequate. Adequacy is **UNVERIFIED; a data-flow threat model plus seeded-secret leakage test would settle it**.
