# I04 — Initiative / anticipation calibration

## Executive answer: the exact line

The line is not “do extras when they seem useful.” It is:

> **Execute an unasked action only when it is closure-adjacent to the authorized objective, stays inside the already-authorized action/resource class, is reversible or read-only, has bounded marginal cost, and produces an external receipt. Otherwise preserve it as a thread; ask only if the owner must make a real choice.**

This can be made testable. For candidate action `x`, define:

```text
JUST_DO(x) = A ∧ U ∧ R ∧ B ∧ V ∧ ¬D

A  adjacency: x is a necessary prerequisite of an explicit acceptance criterion,
              repairs a direct consequence of the requested change, or verifies a
              completion claim; “same topic” is not enough.
U  authority: x uses the same resource set and action class already authorized;
              no explicit negative constraint or out-of-scope item is crossed.
R  recoverability: x is read-only, or has a tested rollback/checkpoint; x does not
              spend money, expose secrets, contact a person, publish, merge/push,
              delete durable data, change security posture, or bind the owner legally.
B  budget: estimated marginal wall time <= min(10 minutes, 10% of the remaining
              task budget), and it does not delay the requested critical path >5 min.
V  verification: a different tool/context, executable test, second model, or owner
              can verify the result before “done” is claimed.
D  decision: reasonable alternatives differ in owner-visible outcome, risk, cost,
              or taste. If D is true, the choice belongs to the owner.
```

Routing is then deterministic:

```text
if JUST_DO(x):                    execute, verify externally, disclose materially
elif A ∧ U ∧ R ∧ V and D:         confirm-first with one bundled question
elif relevant_to_root_goal(x):    append a proposed thread; do not execute
else:                             stay silent
```

The numeric budget in `B` is an **UNVERIFIED starting operating point**; the experiment that settles it is the held-out replay plus four-week production A/B in Finding 3, stratified by task length. It is **likely (55-80%)** to be conservative enough for initial shadow evaluation because it caps both absolute delay and proportional effort, but there is no local acceptance-labelled dataset yet. No same-context self-score is an input: each boolean is backed by the objective/authority record, an action taxonomy, tool health, and an external receipt.

The predicate deliberately distinguishes *completion halo* from *feature halo*. Tests directly invalidated by an edit, a format check required to claim the edit works, or cleanup of a temporary file created by the task are closure-adjacent. A new UI control, repo-wide refactor, new integration, unrelated cleanup, public action, or “while here” feature is not closure-adjacent even if beneficial.

- **what it is:** A pure decision function returning `execute | confirm | park | silent` plus machine-readable reason codes (`adjacent_acceptance`, `new_resource`, `external_side_effect`, `owner_choice`, `no_external_verifier`, etc.). ## What not to build

Do not add an “initiative agent,” proactive daemon, new memory database, second event ledger, seventh hook, or LLM judge that grades its own choices. These all fail the anti-overfit gate. The necessary substrate already exists: shared dispatcher, selection events, event ledger, calibrated-silence, open loops, background digest, AskUserQuestion, truth verification, checkpoints, and MCP liveness. The design is a small policy function, schema extensions, and an offline evaluator riding those buses.

Do not infer permission from enthusiasm. “Proceed with everything” can widen effort inside the stated outcome; it does not authorize public communication, spending, secrets, deletion, security changes, or new deliverables. Do not infer annoyance from silence. Do not surface every parked idea. Do not allow an extra to delay the requested critical path merely because it has high speculative upside.

## Deployment sequence and hook-ceiling accounting

1. Implement the pure classifier and JSON taxonomy, but keep all decisions shadow-only.
2. Build the independent replay set and known-positive/known-negative controls.
3. Audit and relabel calibrated-silence reactions; migrate rather than duplicate it.
4. Extend open-loop records and prove lossless park/close/expiry with a separate process.
5. Canary only read/test/local-reversible tier-1 actions.
6. Widen one consequence tier only after predeclared thresholds pass and the owner approves the authority change.

Raw hook additions: **zero**. The classifier is imported by existing consumers; replay is a command/skill; schema changes use existing event/open-loop stores. Thus the design remains under the ~6-hook ceiling and every runtime component catches its own exceptions and exits 0. For an unasked mutation, “fail-open” at the hook/runtime level means the user's requested work continues, while the uncertain extra is parked—failure must not silently manufacture authority.
