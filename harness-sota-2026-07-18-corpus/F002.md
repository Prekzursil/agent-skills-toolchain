# F002 — Red-team: malicious-repo-config

Date: 2026-07-19  
Unit: F002  
Scope: defensive, read-only review of the owner's Claude Code, Codex, shared harness, and autonomous Codex runner  
Subject versions observed: Claude Code `2.1.215`; Codex CLI `0.144.6` locally; autonomous runner pins Codex `0.144.1`

## Executive verdict

The exact CVE-2026-47751 package is **not deployed in this repository's workflows**, but the local harness still has two members of the same malicious-repository threat class.

1. **VERIFIED, critical: Claude Code non-interactive startup is an untrusted-repository execution boundary failure by design unless the launcher removes project/local setting sources.** Installed help says `-p` and non-TTY output skip workspace trust. Anthropic's security documentation says trust verification is disabled with `-p`. Project `.claude/settings.json`, `.claude/settings.local.json`, and `.mcp.json` can contain pre-turn execution primitives. The owner's PowerShell `claude` wrapper adds `--permission-mode bypassPermissions` to ordinary invocations, while user settings grant `C:` and `D:` as additional directories and set `defaultMode` to `bypassPermissions`. This is the highest exploitability × impact path.

2. **VERIFIED exposure, high: Codex correctly trust-gates executable repo-local `.codex/` config, hooks, rules, and MCP definitions, but it loads `AGENTS.md`/`AGENTS.override.md` independently of that gate.** On this machine the local default is `approval_policy="never"`, `sandbox_mode="danger-full-access"`, and a 151,072-byte project-instruction budget. The autonomous runner strips the target `.codex/` before launching, but leaves target `AGENTS.md`, then launches with approvals and sandbox disabled and secret-bearing environment variables. That is prompt injection rather than pre-turn shell execution, but the privilege after a successful injection is equivalent.

3. **VERIFIED, high: the current safeguard is prose, not a pre-launch enforcement point.** The warning exists in `~/.claude/AGENTS.md`, but an auto-loaded file is parsed before an agent can obey a rule saying to inspect it first. The Codex copy of the shared contract omits the cloned-repository warning. The current ConfigChange detector watches only the user `~/.claude/settings.json` after startup and cannot detect initial project `.claude/`, `.mcp.json`, `.codex/`, or instruction-file loading.

The best replacement is not a new security runtime. It is a small, deterministic pre-launch provenance gate on the existing PowerShell/CI launcher bus, combined with native safe modes and explicit source selection. This passes the anti-overfit gate: it adds no second orchestration runtime, vector database, knowledge graph, durable-execution system, trained critic, observability SaaS, or guardrail framework.

## Threat model and terminology

The attacker can cause the owner or an automated job to clone/check out a repository and start an agent inside it. The attacker does not initially control the host account. Relevant outcomes are:

- **direct pre-turn execution:** a settings key, lifecycle hook, credential helper, status command, or stdio MCP process runs before the model's first turn or before normal tool approval;
- **model-mediated execution:** a repository instruction file enters the model context and persuades the model to use its already-authorized tools;
- **capability expansion:** repo config changes sandbox, approvals, environment, plugins, MCP servers, writable roots, or tool allowlists;
- **secret exposure:** a pre-turn process or persuaded model can read inherited environment variables, credential files, or network-accessible services.

CVE-2026-47751 is the concrete reference case. GitHub's reviewed advisory says `anthropics/claude-code-action` versions before `1.0.74` checked out attacker-controlled PR heads, read `.mcp.json` through default setting sources, and unconditionally enabled project MCP servers, enabling runner code execution and secret exfiltration. Anthropic's root-cause PR broadens the affected startup surface to `.claude/settings.json`, `.claude/settings.local.json`, hooks, `env`, credential helpers, and `.mcp.json`, all before turn 1. Sources: [GitHub advisory GHSA-8q5r-mmjf-575q / CVE-2026-47751](https://github.com/advisories/GHSA-8q5r-mmjf-575q), lines 154-174; [Anthropic fix PR #1066](https://github.com/anthropics/claude-code-action/pull/1066), lines 214-243.

The exact action is not installed: a workflow-scoped `rg` found a known-present `uses:` control at `.github/workflows/quality.yml:47` and no `anthropics/claude-code-action` reference in any workflow. Therefore the report calls the local weaknesses **CVE-2026-47751-class**, not the exact vulnerable dependency.

Confidence: **almost certain (90-99%)** that the exact action dependency is absent from the supplied repository workflows, based on the validated workflow detector plus the complete bounded workflow search. This does not prove that no other repository or remote workflow uses the action.

## Native gates, precisely characterized

### Claude workspace trust

Claude defines project trust as a one-time directory acceptance before project configuration takes effect. It gates project hooks and project MCP configuration. Current MCP behavior is stronger than the historical CVE path:

- `.mcp.json` servers awaiting approval show `Pending approval` in `claude mcp list` and `/mcp`;
- committed `.claude/settings.json` cannot approve its own `.mcp.json` servers in an untrusted folder;
- since 2.1.207, an untracked `.claude/settings.local.json` approval waits for folder or parent trust;
- since 2.1.211, local settings are resolved at the repository root and repository-supplied files still require workspace trust.

Evidence: [Claude MCP reference](https://code.claude.com/docs/en/mcp), lines 247-256; [Claude settings reference](https://code.claude.com/docs/en/configuration), lines 170-173. Installed version `2.1.215` is newer than each cited fix.

The gate is intentionally absent in non-interactive mode. Installed `claude --help` says:

> workspace trust dialog is skipped when Claude is run in non-interactive mode (via -p, or when stdout is not a TTY ...). Only use this in directories you trust.

Anthropic's security page independently says trust verification is disabled with `-p`: [Claude security](https://code.claude.com/docs/en/security), lines 160-166.

Confidence: **almost certain (90-99%)** that current non-interactive Claude does not provide the interactive workspace-trust stop, because installed help and the independent vendor security page say so, and the CVE fix PR describes the same startup ordering.

### Claude MCP approval

MCP approval is a separate gate from folder trust. A trusted folder can still present a new server for per-server approval, and a rejected server is persisted in `disabledMcpjsonServers`. User, managed, or explicit `--settings` sources can approve project servers; project settings cannot self-approve while untrusted in current versions. `--strict-mcp-config` ignores ambient MCP sources and uses only explicit `--mcp-config` inputs.

Confidence: **almost certain (90-99%)**, based on the current MCP documentation at lines 247-256, installed CLI help for `--strict-mcp-config`, and the local persisted `enabledMcpjsonServers`/`disabledMcpjsonServers` state shape at `C:\Users\Prekzursil\.claude.json:1131-1137`.

### Claude managed policy

Claude provides native managed controls:

- `allowManagedHooksOnly=true` blocks user, project, and ordinary plugin hooks;
- `allowManagedMcpServersOnly=true` confines MCP servers to an admin allowlist;
- `strictPluginOnlyCustomization` can independently lock `skills`, `agents`, `hooks`, and `mcp`, leaving only managed/plugin sources;
- `strictKnownMarketplaces` allowlists plugin sources.

Evidence: [Claude settings reference](https://code.claude.com/docs/en/configuration), lines 258-265, 598-605, and 1013-1025.

On this machine `C:\Program Files\ClaudeCode\managed-settings.json:1-4` exists but contains only `allowAllClaudeAiMcps=true` and an empty `deniedMcpServers`; it has no hook/MCP/customization lockdown. Independent registry checks found neither `HKLM:\SOFTWARE\Policies\ClaudeCode` nor `HKCU:\SOFTWARE\Policies\ClaudeCode`. The known-present detector control found the managed file and `~/.claude/settings.json`, so this is not a broken path detector. **UNVERIFIED whether server-managed remote policy adds a higher-priority restriction; the settling experiment is to inspect `/status` → `Setting sources` and effective managed keys in a normal trusted session.**

Confidence: **almost certain (90-99%)** that no local file/registry policy currently locks project hooks or MCP, based on two distinct local policy delivery surfaces. Confidence is only **roughly even (45-55%)** that no remote managed policy does so, because no server-side state was queried.

### Codex project trust and hook trust

Codex has two native gates:

1. project `.codex/` layers are disabled until the relevant project/directory is trusted;
2. every non-managed command-hook definition is hash-reviewed and skipped after any change until its exact new hash is trusted.

The local configuration records per-hook hashes at `C:\Users\Prekzursil\.codex\config.toml:422-455`. Official docs say untrusted project `.codex/` layers, including config, hooks, and rules, are skipped, while `/hooks` displays source and review state: [Codex config basics](https://developers.openai.com/codex/config-basic), lines 764-775; [Codex hooks](https://developers.openai.com/codex/hooks), lines 773-795.

Pinned source independently confirms exact-path behavior. `codex-rs/config/src/loader/mod.rs` at `rust-v0.144.0` computes a project root, looks up normalized keys for the current directory/project root/repository root, and disables each project layer unless that exact decision is trusted (source lines 814-904, 974-1073, 1189-1317). It does **not** grant descendant trust merely because `C:\Users\Prekzursil` is trusted.

This refutes an initially plausible but wrong hypothesis: `C:\Users\Prekzursil\.codex\config.toml:151-152` does **not** make every descendant clone trusted. It matters only when that path is itself the resolved project/directory key. The exact trust lookup is an important safety property.

Confidence: **almost certain (90-99%)**, based on official docs plus the independent pinned loader implementation. The remaining 1-10% accounts for possible drift between tag `rust-v0.144.0` and installed `0.144.6`; the public behavior documentation matches the source.

### Codex `AGENTS.md` is outside the trust gate

`AGENTS.md` follows a different code path. Codex builds an instruction chain from global Codex home and from the project root down to the working directory, with nearer files later and therefore overriding earlier guidance. `read_agents_md` returns early only when `project_doc_max_bytes == 0`; it reads project files without consulting project trust. Evidence: [Codex AGENTS.md documentation](https://developers.openai.com/codex/guides/agents-md), lines 753-760; [pinned `agents_md.rs`](https://raw.githubusercontent.com/openai/codex/rust-v0.144.0/codex-rs/core/src/agents_md.rs), lines 4-7.

Confidence: **almost certain (90-99%)** that project `AGENTS.md` loads even when `.codex/` is untrusted, because the official instruction-discovery algorithm contains no trust qualification and the mechanically independent reader source has no trust branch.

### F1 — Critical: Claude headless startup can execute repo configuration before turn 1

**Status: VERIFIED.**

The trigger is ordinary: run `claude -p`, pipe/redirect stdout, or use an automation host without a TTY inside an attacker-influenced checkout. Installed help says the trust dialog is skipped. Project settings are allowed to define command hooks, environment variables, credential helpers, plugins, and MCP approvals; `.mcp.json` can define a stdio process. Anthropic's own CVE fix PR says those paths act before tool-permission gating.

The machine magnifies impact: the wrapper adds bypass permissions, the user settings grant both drives, and dangerous-mode warnings are suppressed. Direct hook/MCP execution does not require the model to be persuaded.

Confidence: **almost certain (90-99%)**, based on installed help, current vendor docs, the CVE root-cause PR, and deterministic wrapper/settings inspection.

Detection signature:

- launch mode contains `-p`, stdout is not a TTY, or the debug log says non-interactive;
- `/status` (interactive reproduction only) lists `Project settings` or `Project local settings` unexpectedly;
- `/hooks` shows `[Project]` or `[Local]` SessionStart/Setup/PreToolUse commands;
- `claude mcp list` or `/mcp` shows a project server as connected rather than `Pending approval`;
- a debug trace contains a project setting path before the first model request;
- an unexpected child process starts with its working directory or `CLAUDE_PROJECT_DIR` set to the clone.

### F2 — High: Codex CI target `AGENTS.md` survives the executable-config scrub

Codex loads it after the global runner file and lets nearer project guidance override earlier guidance. The agent then has inherited credentials, network, full filesystem access, no approvals, and hook-trust bypass.

This is not direct config execution, so it is less deterministic than F1. It is still a high-impact boundary error: attacker-authored instructions are placed in the privileged control channel rather than in a quoted-data channel.

Confidence: **almost certain (90-99%)** that the target instruction loads; **likely (55-80%)** that a well-crafted instruction can induce a sensitive action, based on the precedence and capability evidence. No exploit code was produced and no attack was attempted.

Detection signature:

- target instruction SHA-256 is not in a runner-owned reviewed manifest;
- a target file appears after the runner-owned `CODEX_HOME/AGENTS.md` in prompt order.

Detection signature for the blind spot: provider `/status` or prompt provenance shows a project source, but the harness has no corresponding pre-launch inventory receipt and no ConfigChange event because the file did not change during the session.

## Remediation design, ordered

### R1 — NATIVE (Claude Code already does this; we just enable it): use `--safe-mode` for first-open and untrusted automation

For any new clone or attacker-influenced ref, the first provider invocation should be `claude --safe-mode` with an explicit conservative permission mode. Installed help says safe mode disables `CLAUDE.md`, skills, plugins, hooks, MCP servers, custom commands/agents, workflows, themes, and other customization. For the strictest credential-minimal diagnostic path, `--bare` additionally disables keychain reads and auto-discovery, but it requires explicit API-key authentication and may be operationally inconvenient.

Do not rely on interactive trust in `-p` or non-TTY execution; it is intentionally disabled there.

Expected outcome: **very likely (80-90%)** to eliminate direct repository-owned startup execution for the first inspection, based on installed flag semantics. The remaining 10-20% covers undocumented customization paths; the settling test is an inert matrix covering settings hooks, MCP, CLAUDE.md, skills, agents, and workflows under safe mode.

Bus/anti-overfit: native CLI flag on the existing launcher; no new component.

### R2 — NATIVE (Claude Code already does this; we just enable it): constrain automated setting and MCP sources explicitly

For headless work that needs user customizations, use `--setting-sources user` so project/local settings do not merge. When MCP is required, add `--strict-mcp-config` and pass only a runner-owned reviewed MCP file. Never combine ambient project sources with `enableAllProjectMcpServers` in headless mode.

Expected outcome: **almost certain (90-99%)** to exclude project/local settings and ambient MCP under documented CLI semantics. A credential-free matrix comparing `/status`/debug sources and MCP child processes settles end-to-end behavior.

Bus/anti-overfit: native CLI source-selection controls; no new component.

### R3 — CONFIG (settings/JSON only): stop making bypass permissions the unconditional Claude default

Change the default user permission mode from `bypassPermissions` to `default` or `plan`, remove the unconditional wrapper injection, and require an explicit reviewed-path opt-in for bypass mode. Do not grant whole `C:` and `D:` as additional directories to ordinary sessions; grant the actual workspace or named adjacent roots.

This does not fix pre-turn command hooks by itself, so it is defense in depth after R1/R2. It materially reduces what model-mediated `CLAUDE.md`/skill injection can do.

Expected outcome: **very likely (80-90%)** to reduce blast radius for prompt-mediated attacks, based on Claude's permission architecture. It will not contain a hook/MCP process that starts before tool permissions; that limitation is why R1/R2 precede it.

Bus/anti-overfit: settings and existing wrapper only.

### R4 — CONFIG (settings/JSON only): deploy managed customization restrictions after preserving the owner harness

Two viable managed-policy profiles exist:

1. Minimum: `allowManagedHooksOnly=true`, plus managed MCP allowlisting.
2. Stronger: `strictPluginOnlyCustomization=["hooks","mcp"]` plus `strictKnownMarketplaces`, after the owner's approved hooks/MCP are packaged as managed/plugin sources.

Do **not** flip these immediately without migration: current owner hooks are user-level and would be blocked. Stage with `/status`, `/hooks`, and `/mcp`, then promote only after the approved harness appears from managed/plugin provenance.

Expected outcome: **very likely (80-90%)** to make repo-owned hooks/MCP structurally impossible while preserving reviewed plugin/managed equivalents, based on the documented managed-policy semantics. **UNVERIFIED operational compatibility with every current owner hook/MCP; the settling experiment is a clean test profile that compares the current hook/MCP roster before and after policy.**

Bus/anti-overfit: native managed policy and existing plugin bus; no new security framework.

### R5 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): add one deterministic pre-launch provenance gate

Put the gate in the existing PowerShell `claude` function and CI launch steps, before provider startup. It should:

1. resolve the real repository root and current commit;
2. inventory only startup-relevant paths: `.claude/`, `.mcp.json`, `.codex/`, `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, and nested instruction overrides between repo root and working directory;
3. hash each file and classify provenance as owner-reviewed base, local-only owner file, or unreviewed target delta;
4. compare against a small review receipt keyed by repository identity + commit/base-ref + file hash;
5. for unreviewed input, choose a deterministic safe launch: Claude safe/source-restricted mode; Codex with project docs disabled and `.codex/` untrusted/removed in ephemeral CI;
6. print one terminal marker such as `SAFE-TO-START:<receipt-hash>` or `UNREVIEWED-CONFIG:<paths>` and then exec the provider with argv arrays, never shell interpolation.

Do not scan prose for “malicious” patterns. Provenance and startup capability are the discriminator. This avoids the known harness defect where guards confuse mention with use.

Expected outcome: **very likely (80-90%)** to close the timing gap because the control runs before either provider parses target config; evidence is the successful existing CI `.codex/` scrub and Anthropic's own PR-base restoration fix. The settling test is a credential-free inert matrix for each loader path and launch mode.

Bus/anti-overfit: this extends the existing PowerShell/CI launcher and emits into the existing harness event/receipt stream. It adds no daemon, database, durable executor, trained critic, SaaS, or second orchestrator.

### R6 — NATIVE (Claude Code already does this; we just enable it): reset broad trust choices and approve exact repositories

Use `claude mcp reset-project-choices` for MCP approvals and remove stale/broad accepted project records through the supported trust UI/command where available. Re-accept exact repositories only after the preflight receipt succeeds. Avoid using a shared clone parent as the accepted project when child inheritance is possible.

Expected outcome: **likely (55-80%)** to restore meaningful prompts for new descendants, based on persisted per-path state and documented parent trust for local settings. **UNVERIFIED whether removing the parent record alone resets every descendant trust cache; the settling experiment is a disposable child before/after state comparison.**

Bus/anti-overfit: native trust/MCP state, no new component.

### R7 — CONFIG (settings/JSON only): disable project docs in privileged Codex automation

Add a runner-owned CLI override `-c project_doc_max_bytes=0` to `codex exec` for jobs that operate on unreviewed repositories, and pass the task only through the runner-owned prompt. Keep stripping target `.codex/`. If project guidance is legitimately needed, copy a maintainer-reviewed base-branch instruction file to a runner-owned location and include it explicitly; do not consume the PR/target delta.

This uses the native early return in `agents_md.rs` and avoids deleting user files in local workflows. In CI, restoring configuration from a reviewed base ref is also valid and mirrors Anthropic's fix.

Expected outcome: **almost certain (90-99%)** to prevent Codex project `AGENTS.md` ingestion because pinned source returns before discovery when the byte budget is zero. End-to-end confirmation requires the inert marker CI job described under F2.

Bus/anti-overfit: one CLI config override on the existing runner.

### R8 — CONFIG (settings/JSON only): reduce the local Codex project-document budget

Return the global `project_doc_max_bytes` from 151,072 to the native 32 KiB default, or use zero in explicitly untrusted profiles. This is not a trust control—the first malicious bytes can still matter—but it reduces prompt surface and prevents a local preference from magnifying a repo injection.

Expected outcome: **likely (55-80%)** to reduce attack surface and context pressure; it is **unlikely (20-45%)** to prevent a concise malicious instruction by itself. Evidence is the current 4.6× budget and Codex's deterministic truncation behavior.

Bus/anti-overfit: one config value.

### R9 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): record source-level startup telemetry, not content heuristics

Extend the existing event ledger with one pre-launch/startup receipt containing:

- provider/version/mode and TTY state;
- resolved repo root/commit/base ref;
- setting sources selected;
- startup-relevant file paths and SHA-256 hashes;
- trust decision key, without secrets;
- hook sources and review hashes;
- MCP names/transports/approval status, without args/env values;
- instruction source paths and byte counts;
- final safe/blocked mode.

At SessionStart, reconcile the provider-reported sources against the pre-launch receipt. An unexpected source is the detection signature. Never log file bodies, MCP arguments, environment values, headers, or credentials.

Expected outcome: **very likely (80-90%)** to make unexpected auto-load mechanically visible, based on native `/status`, `/hooks`, `/mcp`, Codex hook hashes, and instruction provenance. **UNVERIFIED whether every Claude source is available non-interactively without a debug trace; the settling experiment is to enumerate the installed debug/InstructionsLoaded schema in a credential-free session.**

Bus/anti-overfit: the existing ledger and hook events only; no observability SaaS or new daemon.

- Then allow normal user harness hooks/plugins and explicitly approved MCP.

## Detection playbook for an unexpected auto-load

An incident is “unexpected auto-load” when the provider consumes a source absent from the pre-launch receipt, or consumes a reviewed path at a different hash.

### Claude signatures

1. `/status` → `Setting sources` unexpectedly includes Project or Project local. Vendor docs say this line reports loaded sources: [Claude settings](https://code.claude.com/docs/en/configuration), lines 674-676.
2. `/hooks` shows a `[Project]` or `[Local]` command/prompt/HTTP/MCP hook not in the receipt. The hook UI displays source and full definition.
3. `/mcp` or `claude mcp list` shows a project server as connected instead of `Pending approval`.
4. `InstructionsLoaded` reports an unexpected `CLAUDE.md`/rule path, or debug logs show project instruction load before the first request.
5. A process-tree event shows a child whose executable/working directory derives from `.mcp.json` or a project hook before turn 1.
6. `ConfigChange` without an operator edit indicates live reload, but absence of ConfigChange does not clear startup files.

### Codex signatures

1. Startup warning: “project-local config, hooks, and exec policies” disabled/untrusted. This is a safe negative signal for `.codex/`, not for `AGENTS.md`.
2. `/hooks` shows a project source, new hash, changed hash, or `needs review` state.
3. Model prompt input/rollout provenance contains an unexpected project `AGENTS.md`/`AGENTS.override.md` path or hash.
4. `codex debug prompt-input` in a credential-free diagnostic run shows a project instruction when the launch profile required zero project docs.
5. `/status` alone is insufficient on Windows because upstream reports false `Agents.md: <none>`; validate against rollout/prompt provenance.

### Immediate containment

Stop the session before any tool call, preserve the startup receipt/debug log/process tree, terminate unexpected child MCP/hook processes, relaunch in safe/zero-project-doc mode, and review the diff against the trusted base. Do not run the suspicious hook or MCP “to see what it does” on the owner host.

## Alternatives considered and rejected

### A second orchestration/security runtime

Rejected. The loader boundary occurs before the agent runtime; another agent/daemon would add complexity and could itself parse the repository too late. Native source selection plus a deterministic launcher gate is smaller and earlier.

### Pattern-scanning config or instruction prose for malicious strings

Rejected. It is bypassable, invites the known use-vs-mention false positives, and cannot establish provenance. Hash/review the startup-capable source instead.

### Rely only on sandbox/tool approvals

Rejected. Direct hooks, environment helpers, and stdio MCP startup occur outside or before the model's normal tool approval. Sandbox/permissions remain valuable for model-mediated instruction injection.

### Delete every repo config before every local run

Rejected for local use because legitimate reviewed project configuration would be destroyed and the user forbids destructive handling. In ephemeral CI, restoring from a reviewed base or deleting the target delta is appropriate and already demonstrated.

### Trust the containing directory for convenience

Rejected. It weakens the “new clone” decision boundary and may confer parent-derived approval. Exact repository trust after a receipt is safer.

### Treat `AGENTS.md` and executable hooks as the same severity

Rejected. Hooks/MCP can execute deterministically before turn 1; `AGENTS.md` must persuade the model. Both deserve controls, but conflating them overstates one path and obscures the correct gate.
