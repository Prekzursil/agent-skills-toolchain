# X132 — Cross-domain borrow: systems safety → agent memory

**Unit:** X132  
**Source field:** systems safety (STAMP/STPA, Swiss-cheese defences, normal-accident theory, safety cases)  
**Target:** what an agent should remember across sessions, when it should forget, and how it should notice that a memory is stale  
**Scope discipline:** external research and design only. I did not inspect the local harness or repeat repository grounding assigned to other units. Consequently, this unit does **not** claim that any proposed mechanism is present or absent in the current harness.

## Executive conclusion

One systems-safety mechanism transfers unusually well: **STPA's controller process model, combined with a living assurance case**. In STPA, a controller chooses control actions using an internal model of the controlled process. Unsafe action can result even when the control algorithm is correct if its model is wrong, incomplete, or updated by delayed/inaccurate feedback. Cross-session agent memory occupies the same structural position: it is retained state used by a controller (the agent) to select actions. The transfer is therefore functional, not merely metaphorical.

The concrete borrow is a **memory control case**: each consequential persistent memory is a scoped claim with evidence, assumptions, invalidation conditions, feedback obligations, and a retirement rule. At retrieval, the harness treats memory as a fallible input, not as truth. It checks whether the current context satisfies the memory's scope, whether an invalidator has fired, and whether a high-consequence action requires fresh evidence. The lifecycle is analyzed using STPA's four unsafe-control-action forms: required memory not provided; unsafe memory provided; memory provided too early/late or in the wrong order; and memory retained too long or stopped too soon.

The transfer is **very likely (80-90%)** to expose useful failure scenarios that a timestamp-plus-similarity memory design misses. Evidence: STPA explicitly analyzes stale feedback and flawed process models as causes of unsafe control actions, while a memory record can directly represent the affected model variables and feedback dependencies ([Leveson & Thomas, *STPA Handbook*, pp. 25-27, 45-48, 180-183](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). Whether a lightweight gate measurably improves this owner's real sessions is **UNVERIFIED**; the settling experiment is the **Memory Hazard Replay** defined below, run against corrected historical episodes and prospective shadow traffic.

The other three mechanisms are supporting constraints, not equal co-designs:

- Reason's Swiss-cheese model says independent barriers can prevent propagation, but the analogy warns that several LLM-based checks are often one correlated barrier, not several.
- Perrow's normal-accident theory says interactive complexity plus tight coupling makes unexpected cascades more likely; this argues for *lowering memory's authority and coupling*, not for building a more elaborate memory runtime.
- Safety-case practice contributes explicit claims, evidence, context, assumptions, counterevidence, and event-triggered revision. It does **not** justify numeric “memory confidence.” NASA researchers found proposed quantitative assurance-confidence techniques capable of implausible results and insufficiently validated for critical decisions ([Graydon & Holloway, NASA/TM-2016-219195](https://ntrs.nasa.gov/api/citations/20160006526/downloads/20160006526.pdf?attachment=true)).

## 1. The source mechanisms in their own field

### 1.1 STAMP/STPA: unsafe control can arise from a wrong process model

STAMP models safety as a control problem. A controller issues actions to a controlled process through actuators and receives feedback through sensors. The controller's algorithm maintains a **process model**—its belief about the state of the controlled process and relevant environment—and uses that model to decide what action to issue. The model need not fail like a physical component: it can become inconsistent with reality because feedback is missing, inaccurate, delayed, not processed, or because the controller assumes that a commanded action actually occurred.

The STPA Handbook makes the relevant mechanism explicit:

1. Control action and feedback are separate paths; delay or distortion on either path can make an otherwise valid control structure unsafe (Handbook pp. 26-27, 180).
2. The controller must both generate control actions and maintain accurate information about the controlled process and environment; flaws in either function can produce unsafe control actions (p. 180).
3. Delayed data may no longer reflect the current state, causing action on incorrect information; the analyst must not stop at “flawed process model” but identify *why* the model became flawed (p. 180).
4. A controller may update its model merely because it issued a command, even if the actuator never executed it; missing feedback about non-execution is a causal scenario (pp. 181-182).
5. STPA classifies unsafe control actions by whether a required action is not provided, an unsafe action is provided, timing/order or duration is unsafe, or an action is stopped too soon/applied too long (pp. 35-36 and 45-48).

These are all statements of the method in its native field, supported by the definitive handbook hosted by MIT's Partnership for Systems Approaches to Safety and Security ([MIT PSASS handbook index](https://psas.scripts.mit.edu/home/books-and-handbooks/); [direct handbook PDF](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)).

### 1.2 Swiss cheese: accidents penetrate aligned weaknesses in layered defences

Reason's organizational-accident model represents defences, barriers, and safeguards as layers whose weaknesses (“holes”) are created by active failures and latent organizational conditions. Harm occurs when weaknesses align and a hazard passes through all layers. The important lesson is not simply “add checks”; it is that no layer is perfect and latent conditions can create common failure modes across layers. Reason contrasts a person-blame model with a systems approach concerned with the conditions that shape error ([Reason, 2000, *BMJ* 320:768-770, DOI 10.1136/bmj.320.7237.768](https://pmc.ncbi.nlm.nih.gov/articles/PMC1117770/)). FAA maintenance guidance independently operationalizes the same distinction: latent failures set the stage, active failures catalyze an accident, and aligned failures in multiple defences open an accident path ([FAA AC 120-72, §7e(4)-(5)](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-72.pdf)).

A crucial qualification comes from AHRQ's patient-safety explanation: barriers that look separate may share a common failure mode and disappear together in an emergency. Independence cannot be inferred from the number of checks ([AHRQ PSNet, “Swiss Cheese Model”](https://psnet.ahrq.gov/glossary/swiss-cheese-model)).

### 1.3 Normal accidents: complexity and coupling create unanticipated cascades

Perrow distinguishes **interactive complexity**—components can interact in unanticipated ways—from **tight coupling**—a disturbance cannot be isolated and cascades quickly. The National Academies applies this analysis to software: individually conforming components can interact through unanticipated but permissible values; software-heavy systems exhibit both properties, while modularity can reduce coupling and complexity ([National Research Council, *Software for Dependable Systems: Sufficient Evidence?*, “Complexity, Coupling, and Catastrophe”](https://www.nationalacademies.org/read/11923/chapter/3)). Perrow's own later summary argues that complex, tightly coupled systems are inherently vulnerable and warns that safety add-ons can themselves be accident sources ([Perrow, 1999, “Organizing to Reduce the Vulnerabilities of Complexity”](https://doi.org/10.1111/1468-5973.00108)).

Normal-accident theory does not supply a memory schema. It supplies a design test: does persistent memory create hidden interactions and immediate cascades, or does the architecture isolate and slow them?

### 1.4 Safety cases: claims remain valid only within context, assumptions, and live evidence

A safety/assurance case links a top-level claim to a reasoned argument and supporting evidence for a defined application and environment. Goal Structuring Notation (GSN) makes goals/claims, strategies, evidence (“solutions”), contexts, assumptions, and justifications explicit. The current GSN Community Standard describes itself as the authoritative notation and best-practice guide for developing and evaluating engineering arguments ([SCSC, GSN Community Standard v3](https://scsc.uk/gsn-standard)). A UK Ministry of Defence systems-assurance guide likewise describes progressively supporting a top-level claim with arguments and evidence and documenting cross-system assumptions/configurations ([ASEMS, “Goal Structuring Notation and Claim Trees”](https://www.asems.mod.uk/toolkit/goal-structuring-notation-and-claim-trees)).

The “living” property is operational, not decorative. UK HSE guidance says an offshore safety case must remain current and reflect operational reality; changes in environment, activities, or risk factors trigger limited, frequent revision, in addition to periodic thorough review. The thorough review examines the case's **basic assumptions**, not just its text ([HSE, *A guide to the Offshore Installations (Safety Case) Regulations*, paras. 15, 185, 187-190](https://www.hse.gov.uk/pubns/priced/l30.pdf)). HSE also stresses that acceptance does not guarantee safety and that post-acceptance inspection is still required (paras. 11-12). This blocks a dangerous translation: “the memory was once accepted, therefore it remains true.”

Safety-case reasoning is defeasible. NASA's survey describes assurance arguments as claims, evidence, and reasoning within a defined application/environment, and notes explicit treatment of uncertainty. It also shows why a computed confidence number must not substitute for review: proposed quantitative techniques lacked adequate empirical validation and sometimes produced implausible answers ([Graydon & Holloway, NASA/TM-2016-219195, pp. 1-4](https://ntrs.nasa.gov/api/citations/20160006526/downloads/20160006526.pdf?attachment=true)).

## 2. Structural mapping to agent memory

### 2.1 The mapping

| Systems-safety element | Agent-harness counterpart | Concrete implication |
|---|---|---|
| Controller | Agent/model plus harness policy | Chooses tool calls, edits, messages, and plans. |
| Controlled process | Workspace, services, owner workflow, and external world | Reality can change between sessions without the memory store observing it. |
| Process model | Current prompt state plus retrieved persistent memories | A remembered claim can be internally coherent yet false now. |
| Sensor/feedback | File reads, API responses, tests, owner corrections, outcomes | Retrieval is not feedback; a fresh observation is feedback. |
| Control action | Tool call, mutation, recommendation, or external communication | Consequence determines how much revalidation is needed. |
| Unsafe control action | Action hazardous in a particular context | The same remembered instruction can be safe in one repo/account/time and unsafe in another. |
| Safety constraint | Rule that bounds use of memory | Example: do not use a mutable infrastructure fact for an irreversible action without live validation. |
| Safety case | Structured justification for retaining and using a claim | Provenance alone is insufficient; scope, assumptions, invalidators, and counterevidence matter. |
| Review/revision trigger | Dependency change, contradiction, failed action, owner correction, elapsed review horizon | Staleness is event- and context-sensitive, not merely age-sensitive. |

The key structural identity is: **persistent memory is a component of the controller's process model**. Both systems make decisions under partial observation; both can act on delayed feedback; both can mistakenly infer that a requested state transition occurred; and in both, the hazard depends on context, timing, and control authority. That is why this analogy transfers.

### 2.2 STPA's four unsafe-action categories become a complete first-pass memory checklist

For every class of consequential action, ask:

1. **Required memory not provided.** What loss occurs if the agent fails to retrieve a still-valid constraint, owner decision, security boundary, or unresolved obligation?
2. **Unsafe memory provided.** What loss occurs if the agent retrieves an incorrect, poisoned, superseded, cross-project, or privacy-inappropriate claim?
3. **Wrong timing or order.** What loss occurs if a memory is injected before current context is established, after an irreversible action, or before a higher-priority correction?
4. **Applied too long or stopped too soon.** What loss occurs if a temporary workaround persists after the cause is fixed, or if a durable owner preference is forgotten merely because a time-to-live elapsed?

This checklist corrects a conceptual blind spot in generic “remember/retrieve/forget” designs: **forgetting can itself be unsafe**, and retention duration has two-sided risk. A universal TTL optimizes only one side.

### 2.3 Memory classes are control classes, not file formats

The harness should distinguish at least:

- **Owner directives and durable preferences:** high authority, explicitly owner-sourced, changed only by owner correction or scoped supersession. Their hazard is premature forgetting or scope leakage.
- **Mutable world facts:** low default authority, evidence-linked, aggressively revalidated when consequence is high. Their hazard is staleness.
- **Episode outcomes:** observations of what was attempted and what happened, including failed attempts. Their hazard is confusing an issued action with a successful result.
- **Derived hypotheses:** explicitly uncertain and never promoted to fact merely by repetition. Their hazard is self-confirmation.
- **Secrets and sensitive personal data:** retention-minimized with policy-driven deletion, not “useful forever.” Their hazard includes the retention itself.
- **Open commitments:** retained until independently observed complete or explicitly cancelled. Their hazard is both dropping an obligation and falsely marking it done.

This taxonomy is a design deduction, not an empirical finding about this harness. It is **likely (55-80%)** to reduce category errors because each class has a distinct authority, invalidation, and retention rule; evidence is the STPA requirement to analyze context-specific unsafe control actions rather than assigning safety to a component in isolation ([STPA Handbook, pp. 35-48](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). The size of the benefit is **UNVERIFIED**; the settling experiment is the **Memory Hazard Replay**, stratified by these six classes.

## 3. Recommendation — UNVERIFIED: a Memory Control Case on the existing bus

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Build a deliberately small ledger-and-gate mechanism, not a memory service. A JSONL ledger stores consequential memory claims; a pre-action or retrieval hook evaluates simple deterministic invalidation rules and emits a compact “memory use card.” Existing file/API/test tools supply live feedback. The model remains responsible for reasoning, but the harness makes the evidence boundary visible and blocks silent elevation of stale memory for high-consequence actions.

This recommendation inherits **UNVERIFIED** because this unit did not test whether the target harness exposes the required pre-action/retrieval hook or whether the added friction improves end-to-end owner outcomes. The settling experiment is: first run the **Hook Feasibility Probe** (a no-op hook proves it sees a known injected memory and a known high-consequence tool call), then run the **Memory Hazard Replay**. Until both pass, this is a design candidate, not a deployment conclusion.

### 3.1 Minimal record (“micro assurance case”)

Each record should contain only fields with a control purpose:

```json
{
  "id": "mem-...",
  "claim": "Plain-language proposition, not a document chunk",
  "class": "owner_directive|mutable_fact|episode_outcome|hypothesis|sensitive|commitment",
  "scope": {"workspace": "...", "account": "...", "branch": "...", "task_kind": ["..."]},
  "authority": "owner|observed|derived|external",
  "evidence": [{"locator": "...", "observed_at": "...", "digest_or_version": "..."}],
  "assumptions": ["Conditions required for the claim to remain applicable"],
  "invalidators": ["owner_supersedes", "dependency_digest_changes", "contradictory_live_read", "deadline_passes"],
  "negative_evidence": ["Known facts that weaken or conflict with the claim"],
  "feedback_due": "What observation would confirm the claimed outcome",
  "review": {"on_use_after": "...", "absolute_by": "..."},
  "retention": "retain|quarantine_after|delete_after",
  "sensitivity": "public|private|secret",
  "status": "provisional|active|challenged|superseded|quarantined",
  "supersedes": ["mem-..."],
  "created_from_session": "..."
}
```

Notably absent is `confidence: 0.87`. Evidence strength and applicability are multidimensional; collapsing them into a scalar creates false precision. This exclusion is **very likely (80-90%)** to avoid misleading assurance because NASA's review demonstrated that proposed quantitative confidence methods can return implausible results and lack sufficient validation for critical decisions ([NASA/TM-2016-219195](https://ntrs.nasa.gov/api/citations/20160006526/downloads/20160006526.pdf?attachment=true)). Whether qualitative states (`provisional`, `challenged`) are calibrated consistently by an agent is **UNVERIFIED**; settle it with blinded inter-run agreement on the replay set.

### 3.2 The retrieval-time memory use card

The hook should not dump the ledger into context. It should emit, for each selected consequential claim:

```text
MEMORY mem-123 — CHALLENGED
Claim: production deploys use region X
Applies only if: account=A; workspace=W; deployment config digest=D
Evidence observed: timestamp T; source S
Invalidator: current config digest != D (fired)
Required before destructive/external action: live config read from an independent source
```

Deterministic checks should include exact scope mismatch, source digest/version change, passed deadline, explicit supersession, unresolved contradiction, and missing required feedback. Semantic judgments remain visible as assumptions for the agent or owner; they are not hidden behind a score.

The gate has three consequence levels:

1. **Reversible/read-only:** permit use, label provenance and status.
2. **Material but recoverable:** require the agent to cite the memory and state the assumption it is relying on.
3. **Irreversible, external, privileged, destructive, financial, privacy-sensitive, or security-sensitive:** challenged/provisional mutable facts cannot authorize the action. Require a live observation from a source independent of the memory's production path, or explicit owner confirmation.

This gate is **likely (55-80%)** to catch scope leakage, stale infrastructure facts, remembered-but-never-completed actions, and superseded constraints before consequence. Evidence: those are direct instances of STPA's incorrect process model, missing feedback, and unsafe timing/context scenarios ([STPA Handbook, pp. 180-183](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). Actual precision and recall are **UNVERIFIED**; settle them with the replay experiment and report false-block and escaped-hazard rates separately.

### 3.3 Write, challenge, revise, retire

The lifecycle should be:

1. **Capture selectively.** Persist propositions that change future decisions, not transcripts or generic summaries. Record origin and scope at capture time.
2. **Challenge before promotion.** Derived claims begin `provisional`. Owner directives can begin `active` only when their source is an actual owner message. A successful outcome becomes active only after outcome feedback, not after issuing the command.
3. **Monitor cheap invalidators.** Compare known versions/digests and explicit supersession links when the record is retrieved; do not run a background crawler.
4. **Revalidate by consequence.** Age is a prompt to review, not proof of falsity. A high-consequence use requires fresher evidence than a reversible one.
5. **Preserve counterevidence.** Contradiction changes status to `challenged`; it must not be overwritten by the newest fluent summary.
6. **Supersede without erasing lineage.** New claims point to old records; retrieval returns the live successor and a conflict notice.
7. **Quarantine before ordinary deletion.** Quarantined records are excluded from retrieval but retained briefly for rollback/audit. Secrets and policy-mandated data bypass ordinary quarantine when deletion is required.
8. **Close the loop.** When an action relies on a memory, record the observed result. If the result conflicts, challenge both the claim and any derived records.

Event-triggered review is more important than uniform expiry. The translation from HSE's living safety-case practice is direct: material environment/operation changes trigger revision, and periodic review separately tests whether the whole argument remains sound ([HSE L30, paras. 185-190](https://www.hse.gov.uk/pubns/priced/l30.pdf)). It is **very likely (80-90%)** that change-triggered invalidation identifies some stale memories earlier than TTL alone, because a dependency change can occur immediately after capture while an unchanged fact may remain valid for years. The net benefit and correct trigger set are **UNVERIFIED**; settle them by replaying known corrections with event logs, comparing first-detection time against TTL baselines.

### 3.4 Independent barriers, not repeated LLM opinions

Apply the Swiss-cheese lesson as a barrier-diversity requirement:

- **Capture barrier:** structured scope/evidence required to persist a consequential claim.
- **Store barrier:** contradictions and supersession are preserved; they cannot be silently overwritten.
- **Retrieve barrier:** deterministic scope/invalidation checks run before injection.
- **Action barrier:** high-consequence actions require current independent feedback or owner confirmation.
- **Outcome barrier:** action completion is established by observed postcondition, not the agent's intent or tool invocation.

Five prompts to the same model over the same stale context are one barrier with one common failure mode. A model-generated summary and a model-generated “verification” of that summary are also correlated. Independence requires a different evidence path: current file digest, API response, test result, versioned authoritative document, or owner statement.

Barrier diversity is **likely (55-80%)** to reduce correlated escapes relative to repeated same-model review. Evidence: Reason's system model distinguishes latent conditions across defences, and AHRQ documents that nominally separate checks can share a common failure mode ([Reason 2000](https://pmc.ncbi.nlm.nih.gov/articles/PMC1117770/); [AHRQ Swiss Cheese Model](https://psnet.ahrq.gov/glossary/swiss-cheese-model)). The agent-specific effect is **UNVERIFIED**; settle it by injecting stale memories and comparing same-model self-review against deterministic digest/API/human barriers at equal latency budget.

## 5. Adversarial transfer analysis

### 5.1 Why STPA transfers

The essential assumptions match:

1. **A controller acts on a model, not direct reality.** An agent acts on prompt/context and retrieved memory.
2. **Feedback is partial and delayed.** Sessions end; repositories, services, people, and policies change while the agent is absent.
3. **Actions change state.** Tool calls and communications can alter the workspace or external world.
4. **Safety is contextual.** A memory is not globally safe/unsafe; using it for a particular action under particular conditions is.
5. **Non-failure interactions matter.** A perfectly stored and accurately retrieved old fact may still be unsafe because the environment changed.

These are structural correspondences, not surface resemblance. The confidence that the *analysis vocabulary* transfers is **almost certain (90-99%)**, supported by the STPA handbook's explicit definition of controller, process model, feedback, context, and unsafe control action, each of which has an operational agent analogue ([STPA Handbook, chapters 2-4 and Appendix G](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)). This does not imply that any particular implementation works.

### 5.2 Where STPA does not transfer cleanly

- **Loss severity is not always agreed.** Industrial safety often has defined unacceptable losses and regulated duty holders. General-purpose agent tasks have changing values and an owner who may trade speed against caution. Therefore the harness should apply the strongest gate only to recognizable consequence classes and owner-designated invariants.
- **The controlled-process boundary is porous.** The agent may not observe remote services, human decisions, or activity between sessions. A ledger cannot make an unobservable world current; it can only mark the epistemic gap and require a new observation.
- **Language is not a finite control alphabet.** STPA often enumerates control actions and contexts; an agent's natural-language actions and memories are combinatorial. Exhaustive UCA enumeration is infeasible. The four-category checklist should be applied to *classes of consequential action*, not every utterance.
- **Memory changes the controller itself.** In engineered control systems the process model is usually a designed state representation. LLM context changes reasoning in opaque ways, so injection can have nonlocal effects. This strengthens the case for sparse, scoped memory but weakens formal completeness claims.
- **“Safety” is only one objective.** Remembering everything may improve task continuity but violate privacy; forgetting may protect privacy but lose obligations. The memory control case must represent plural losses rather than optimize a single correctness metric.

Because of these disanalogies, it is **almost certainly not (1-5%)** plausible that a full formal STPA over every agent utterance would be cost-effective; evidence is the unbounded natural-language action/context space versus STPA's finite, analyst-defined control-action analysis. A narrowly scoped STPA over memory lifecycle actions remains **likely (55-80%)** to be tractable; this is **UNVERIFIED**, settled by timing analysts on a representative set and measuring uncovered scenario yield per hour.

### 5.3 Why naive Swiss cheese fails

The source model is explanatory and organizational; it does not prove that adding slices monotonically improves safety. Agent harness checks frequently share model, prompt, retrieval context, and upstream evidence. Common-mode hallucination or stale context can align all holes. Extra layers also increase latency and interaction complexity.

Therefore “three agent critics validate each memory” is rejected. It resembles independence while using the same failure substrate. The Swiss-cheese borrow is retained only as **barrier diversity and common-cause analysis**.

### 5.4 Why normal-accident theory argues against ambitious memory infrastructure

Persistent memory can couple past sessions to future actions. Automatic extraction, entity resolution, consolidation, decay, contradiction resolution, planning, and tool authorization create nonlinear interactions. If retrieval directly triggers action, coupling is tight: one corrupted record can cascade before observation or intervention.

Normal-accident theory therefore inverts the tempting conclusion. Do not answer memory risk with more autonomous memory machinery. Keep memories low-authority, retrieval sparse, invalidation legible, and consequence boundaries slow enough for fresh feedback. It is **likely (55-80%)** that this reduces cascade severity because modularity and reduced coupling are the source theory's prescribed structural mitigations ([National Academies](https://www.nationalacademies.org/read/11923/chapter/3)). Whether it improves aggregate productivity is **UNVERIFIED**; settle with the pilot's latency and task-success metrics.

### 5.5 Why a micro safety case can also fail

Safety cases can become paperwork that rationalizes a desired conclusion. A record with a source link can project rigor without establishing truth or current applicability. The same agent may invent the claim, assumptions, evidence description, and review result. A large argument graph can become an unauditable end in itself.

Mitigations are deliberately austere:

- retain raw evidence locators/digests, not just prose about evidence;
- preserve counterevidence and unresolved assumptions;
- never infer independent confirmation from model repetition;
- review at actual action boundaries;
- cap the schema and avoid recursive argument graphs;
- measure escaped hazards and false blocks, not ledger completeness.

## 6. Forgetting policy derived from safety constraints

“When to forget” is not answered by age alone. The safe operation is one of four distinct transitions:

1. **Supersede:** a newer authoritative claim replaces an old one, while lineage remains for conflict explanation.
2. **Challenge/quarantine:** evidence is stale, assumptions are false, or contradiction exists. Exclude from normal retrieval but retain briefly for audit and recovery.
3. **Delete:** retention itself is hazardous or prohibited (secret, sensitive personal data, explicit owner request, policy deadline). Delete according to storage semantics and independently verify deletion.
4. **Retain:** the claim remains both useful and supported, or forgetting it would create a larger hazard (durable directive, unresolved commitment, known failed approach).

A review deadline means “do not rely without review,” not “the proposition becomes false.” An invalidator is preferable when available: branch changes, dependency version changes, owner supersession, account changes, deadline passes, source digest changes, a test begins failing, or the expected postcondition is absent.

The dual-risk formulation is important:

| Memory class | Hazard of retaining too long | Hazard of forgetting too soon | Default transition |
|---|---|---|---|
| Mutable fact | Stale action | Re-read cost | Challenge on invalidator; re-observe on consequential use |
| Owner directive | Scope leakage or obsolete preference | Violate owner intent | Retain until scoped supersession/cancellation |
| Failed attempt | Anchor on obsolete workaround | Repeat costly/dangerous failure | Retain outcome and conditions; challenge when conditions change |
| Open commitment | Act on cancelled work | Drop obligation | Retain until observed completion or explicit cancellation |
| Secret/sensitive data | Privacy/security loss | Reduced convenience | Minimize and delete by policy; do not preserve merely for audit |
| Hypothesis | Self-confirming fiction | Lose useful lead | Quarantine/provisional; promote only with independent evidence |

These defaults are **likely (55-80%)** to dominate a single global TTL on safety-relevant errors because they address both “applied too long” and “stopped too soon,” the two duration forms in STPA. The operational trade-off is **UNVERIFIED**; settle it with class-stratified replay plus prospective retrieval/latency measurements.

## 7. Experiments required before adoption

### 7.1 Hook Feasibility Probe

Purpose: establish that the existing bus can implement the gate without a new runtime.

1. Inject a known-present synthetic memory with a known scope and expired invalidator.
2. Invoke one known read-only tool and one sandboxed high-consequence canary action.
3. Signal A: hook log shows the exact memory ID, fired invalidator, and consequence class.
4. Signal B, mechanically independent: the tool-facing prompt/result contains the expected challenge card or the canary action is blocked.
5. Negative test: unrelated memory is not surfaced.

Do not conclude the hook is absent or broken from one zero result. First prove the detector finds a known-present benign hook event through both the hook log and tool-facing effect. If the bus cannot expose these points, the BUILD-SMALL proposal is blocked rather than silently expanded into a daemon.

### 7.2 Memory Hazard Replay

Construct a labeled evaluation set from episodes with known later correction or ground truth, plus synthetic cases:

- stale mutable fact;
- wrong scope/account/repository;
- command issued but outcome absent;
- old claim superseded by owner correction;
- workaround retained after fix;
- durable directive aged beyond TTL;
- repeated hypothesis with no new evidence;
- paired individually safe memories with hazardous interaction;
- sensitive-data retention deadline.

Compare four arms under equal context/latency budgets:

1. no persistent memory;
2. summary plus TTL;
3. provenance-only memory;
4. Memory Control Case with consequence gate.

Primary measures: hazardous action rate, missed-obligation rate, stale-memory acceptance, scope leakage, privacy-retention violation, false blocks, unnecessary live reads, latency, and task success. Label outcomes from observed tool/postcondition evidence, not the tested agent's own narrative. Use an owner/human adjudicator or deterministic oracle where possible.

Before claiming a class “caught,” require two mechanically independent signals: the gate's structured decision and the downstream tool/postcondition trace. Before claiming a defect absent, validate both detectors on a known-present injected case.

### 7.3 Prospective shadow pilot

Run the gate in shadow mode on consequential actions. It emits cards but does not block. Pre-register thresholds, then inspect:

- how often challenged memories would have authorized action;
- how often fresh evidence agrees/disagrees;
- false challenge rate;
- latency/context overhead;
- which invalidators actually predict correction;
- whether the same model generated both the memory and all supposed corroboration.

Only enable blocking for consequence classes where shadow precision and recall justify it. The threshold is an owner policy choice, not something systems-safety theory supplies.

## 8. Anti-overfit gate and rejected alternatives

The recommendation passes the stated anti-overfit gate in design:

- it rides the existing hook/skill/MCP/file bus;
- it adds one small deterministic gate and a JSONL record convention;
- it introduces no second orchestration runtime;
- it introduces no vector database or knowledge graph;
- it introduces no durable-execution engine;
- it introduces no trained critic;
- it introduces no observability SaaS;
- it introduces no guardrail framework.

This “passes” statement concerns the architecture as specified, not implementation status. Feasibility on the actual bus is **UNVERIFIED** and is settled by the Hook Feasibility Probe.

Rejected alternatives:

1. **Full GSN graph for every memory.** Rejected as disproportionate and likely to become assurance theatre. The useful elements fit in one record.
2. **Numeric confidence decay.** Rejected because age, source strength, scope fit, contradiction, and consequence are not one scalar; NASA's critique supplies direct evidence against trusting superficially plausible quantitative assurance.
3. **More model critics.** Rejected because common-model/common-context checks are correlated Swiss-cheese layers.
4. **Background agent continuously reconciling memory.** Rejected because it adds coupling, cost, and unobserved autonomous mutation. Check cheap invalidators on retrieval and require live evidence at consequence boundaries.
5. **Universal TTL.** Rejected because it forgets durable directives and commitments while allowing a freshly captured but already-invalid fact.
6. **Automatic deletion on contradiction.** Rejected because contradictory evidence is diagnostically important and the newest source may be wrong. Challenge/quarantine first, except where retention policy mandates deletion.
7. **Vector similarity as authority.** Rejected because relevance is not applicability or truth. Similarity may nominate a record, but scope/evidence/invalidation govern use.

## 9. Implementation boundary for a later BUILD unit

If the two feasibility signals pass, the smallest implementable slice is:

- one documented JSONL schema;
- one deterministic hook under roughly 200 lines for scope, deadline, digest/version, supersession, contradiction, sensitivity, and consequence checks;
- one compact memory-use-card renderer;
- one append-only action/outcome link;
- test fixtures for each STPA unsafe-memory category and each consequence level.

Do not add semantic consolidation, embeddings, automatic entity graphs, background refresh, or confidence arithmetic in the first slice. Those features must earn inclusion by improving replay outcomes without raising common-mode failure or coupling.

The likely highest-value initial rule is: **a mutable cross-session claim may inform planning, but cannot by itself authorize an irreversible/external/privileged action; obtain current independent feedback first.** Its value is **likely (55-80%)**, based on the direct STPA mapping and the limited scope of the intervention. It remains **UNVERIFIED** until the replay and shadow pilot show fewer hazardous actions without unacceptable false blocks.

## 10. Gaps and evidence limits

- This unit did not inspect the subject tree by instruction. It therefore makes no finding about current memory mechanisms, hooks, schemas, or missing capabilities.
- No cited source evaluates this exact design in an agent harness. The transfer claim is grounded in structural correspondence; implementation efficacy is marked **UNVERIFIED** at every recommendation that depends on it.
- STPA provides a disciplined hazard-discovery method, not probabilities. The confidence bands here describe this unit's epistemic judgment, not STPA output.
- Swiss cheese is useful for common-cause thinking but does not quantify barrier independence.
- Normal-accident theory warns about unanticipated interactions; it cannot enumerate them. Paired-memory fault injection samples the space but cannot prove absence.
- Safety cases can document bad arguments as neatly as good ones. Independent live evidence and outcome measurement remain necessary.
- Deletion guarantees depend on storage, backups, logs, and provider semantics. A ledger `deleted` flag is not deletion. Any future claim of erasure requires a storage-level audit and an independent retrieval/canary check.
