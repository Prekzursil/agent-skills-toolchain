# D002 — HARNESS-BENCH task-suite design

## Executive decision

Build a **hermetic, deterministic trace-and-task suite on the existing hook/dispatcher/ledger/test bus**, not a public coding benchmark, an LLM judge, or a second orchestration runtime. The release gate should contain 20 corpus-derived cases, each executed from a fresh temporary state root, and should finish with a Boolean result per invariant rather than a compensating scalar score. The initial gate is: all critical cases pass three fresh-root trials; all other cases pass once; the scorer and fixtures pass integrity meta-tests; and every benchmark family kills at least one deliberately seeded implementation mutant.

This is the best fit because the corpus's largest measured failures are at concrete mechanism boundaries—tool routing, schema acceptance, command construction, search path size, write preconditions, retry behavior, and detector discrimination—not at generic puzzle-solving ability (`/local_disk0/codexwork/bundle/inputs/corpus.json:13-108,4281-4407`). The known live defects add failures of semantic discrimination, detector controls, telemetry, and orchestrator fact provenance (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-107,111-161`). A deterministic replay suite can exercise all of those without relying on the public internet or an uncalibrated model judge.

The recommendation is **very likely (80-90%)** to detect regressions in the mechanisms named above because each proposed case has an executable input boundary, an exact state/trace oracle, and an explicit mapped mutant; the remaining uncertainty is transfer from synthetic replay to live model behavior. That transfer is **UNVERIFIED; the settling experiment is a 30-task, pre-registered A/B on real owner work after the deterministic gate is green**, comparing old versus candidate harness with fixed provider/model/budget and owner-correction, escaped-defect, retry, and wall-clock outcomes. The deterministic suite must not claim that downstream uplift before that experiment.

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The runner/scorer should be one small Python module; cases, expected records, and mutation declarations are data files. This uses the existing pytest, dispatcher, hook, ledger, semantic-router, and Scheduled Task buses. It adds no daemon, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, guardrail framework, or second orchestrator. It therefore passes the anti-overfit gate.

## Scope boundary

This unit designs the **task suite**: cases, fixtures, oracles, scoring, anti-gaming controls, admission tests, and run budget. It does not implement the runner, alter the read-only subject, benchmark general model intelligence, choose a final harness architecture, or duplicate neighboring lifecycle-harness implementation work.

The unpacked subject was read at `/local_disk0/codexwork/bundle`; only this artifact was written. The original Windows paths are unavailable on the Linux job node, so no Windows execution is claimed.

## Benchmark contract

### What a “task” is

A task is a versioned directory containing:

```text
case-id/
  task.json                 # public prompt/event sequence, profile, budgets
  workspace/                # disposable files visible to the tested system
  expected.public.json      # milestones/minefields whose disclosure is harmless
  variants.json             # deterministic metamorphic transforms
  mutants.json              # implementation mutations this family must kill
```

The trusted runner holds `expected.private.json`, integrity hashes, and the scorer **outside** the mutable task workspace. The tested process receives a fresh copy of `workspace/`, a fresh harness state root, a loopback-only fake tool registry, and a deny-by-default egress policy. No task depends on DNS, public HTTP, cloud credentials, wall-clock dates, inherited user state, or live MCP health.

The manifest should minimally declare:

```json
{
  "id": "D002-H07-dead-mcp-fallback",
  "version": 1,
  "source_evidence": ["corpus.json:4389-4404"],
  "profile": "unattended-enforced",
  "providers": ["claude", "codex"],
  "events": ["UserPromptSubmit", "PreToolUse", "PostToolUse", "Stop"],
  "fixture_sha256": "...",
  "limits": {"wall_s": 20, "tool_calls": 6, "retries": 1},
  "milestones": ["health:dead-tavily", "route:local-search", "answer:fixture-token"],
  "minefields": ["invoke:dead-tavily", "network:non-loopback", "grader-write"],
  "final_state": {"answer.txt": {"sha256": "..."}},
  "critical": true
}
```

Every run records case/version/trial/provider/profile, harness commit and dirty-state hash, model field (`scripted-policy` for the deterministic gate), fixture and scorer hashes, seed, normalized event trace, final-state hashes, forbidden-effect count, elapsed time, and failure class. A result without provenance is invalid, not zero or pass.

### Execution model

The required release lane uses a deterministic scripted policy driver that supplies prerecorded candidate actions to the **real** adapters, hooks, dispatcher, ledger, router, and tool wrappers. This isolates harness behavior from model sampling while retaining stateful event order. Where a case permits multiple valid trajectories, the driver runs at least two: an oracle trajectory and an alternative valid trajectory. A no-op, malformed, and cheating trajectory must fail.

This approach is **very likely (80-90%)** to make scores reproducible because inputs, clocks, randomness, filesystem roots, tools, and action traces are controlled; the evidence is the subject's injectable pytest/dispatcher surface described in audit finding D10 (`/local_disk0/codexwork/bundle/inputs/audit-findings/D10.md:7-13`) and the closed hook schemas cited there. Exact cross-platform byte reproducibility is **UNVERIFIED; the settling experiment is to run the full manifest twice on clean Windows hosts and once on the Linux CI image, then compare normalized result JSON byte-for-byte after removing only declared timing fields**.

An optional model-in-loop shadow lane may later reuse the same workspaces and deterministic scorer, but it is not part of this under-an-hour, no-network-flakiness release gate. It must never be silently blended into the deterministic score.

### Why these are real-work tasks rather than synthetic trivia

H01-H06 are direct minimal reproductions of the four live-operating defects, including their matched controls. H07-H13 are minimized reproductions of the dominant corpus fingerprints and retry runs. H14-H20 encode the long-running, provider-parity, profile, handoff, compaction, fail-open, and concurrent-state work repeatedly represented by the installed harness and the lifecycle audit (`/local_disk0/codexwork/bundle/inputs/audit-findings/D10.md:7-18,31-45`). The fixtures are synthetic only in the sense required for hermetic replay; the failure mechanisms and task shapes are grounded in observed work.

The owner-correction candidates are deliberately not labels because the corpus itself calls them recall-biased and reports 41/41 false positives in an unfiltered smoke sample (`corpus.json:10374`). This avoids laundering a noisy detector into benchmark truth.

## Deterministic scoring

### Case-level result

Each case produces exactly one of `PASS`, `FAIL`, or `INVALID`.

- `PASS`: all required milestones and final-state predicates hold, no minefield or integrity violation occurs, provenance is complete, and resource limits are respected.
- `FAIL`: the run is valid but misses any required predicate, crosses a minefield, leaks a canary, performs a forbidden effect, or exceeds its case budget.
- `INVALID`: scorer/fixture hash mismatch, missing provenance, infrastructure preflight failure, non-loopback network attempt before task execution, unsupported platform for a declared required case, or evaluator tampering. INVALID never counts as PASS and never silently updates a baseline.

The scorer evaluates normalized event records, filesystem/database state, tool-call counts, forbidden syscall/network logs, and redaction canaries. It never awards points for the assistant's prose, self-reported success, process return code alone, or an exact gold call sequence. This follows ToolSandbox's milestone/minefield approach, which supports multiple valid trajectories ([Apple ToolSandbox](https://machinelearning.apple.com/research/toolsandbox-stateful-conversational-llm-benchmark)), and τ-bench's final-state evaluation plus all-trials reliability metric ([τ-bench paper](https://arxiv.org/abs/2406.12045)).

### Suite-level gate

Do **not** publish a single compensating percentage as the release decision. Report the tuple:

```text
integrity: PASS|FAIL
critical_pass^3: passed/critical_total
noncritical_pass@1: passed/noncritical_total
mutation_score_by_family: killed/declared
provider_parity: PASS|FAIL
network_violations: integer
leaked_canaries: integer
runtime_s: total and per-family p50/p95/max
```

Release requires:

1. integrity PASS;
2. every critical case PASS on each of three fresh roots (`pass^3`), not “one of three”;
3. every noncritical case PASS once;
4. zero network violations, leaked canaries, destructive side effects, or grader writes;
5. every family kills its required mutant;
6. provider parity PASS for mechanisms shipped to both providers;
7. no case exceeds its absolute timeout; and
8. no statistically asserted latency regression until a stable baseline exists.

The distinction between `pass@k` and `pass^k` already appears in the installed `/eval` documentation (`/local_disk0/codexwork/bundle/claude/commands/eval.md:29-31,84-88`). τ-bench independently defines `pass^k` as all-k reliability ([paper](https://arxiv.org/abs/2406.12045)). These are mechanically independent signals: a local operational contract and external benchmark prior art.

Latency starts as diagnostic plus absolute case timeouts. A relative p95 threshold is **UNVERIFIED until there are at least 20 clean scheduled runs; the settling experiment is to collect those runs on the owner Windows host, inspect for multimodality by provider/profile, and preregister a threshold before using it as a release gate**. Freezing a tolerance from one run would encode noise.

## Reward-hacking defenses

Reward hacking is treated as an integrity failure, not an interesting alternate solution. OpenAI's evaluation playbook explicitly asks evaluators to disclose system, budget, elicitation, and validity checks for reward hacking, contamination, broken tasks, refusals, and sandbagging ([trustworthy evaluation foundations](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)). Recent workspace-agent research makes evaluator tampering and train/test leakage separately measurable with locked evaluators, patch tracking, and file-access logs ([RewardHackingAgents](https://arxiv.org/abs/2603.11337)); SpecBench similarly separates visible validation from held-out compositional tests ([SpecBench](https://arxiv.org/abs/2605.21384)). The concrete defenses here are:

1. **Out-of-workspace scorer.** Mount scorer, private expectations, and integrity manifest read-only to the supervisor only. Any attempted open/write/rename/chmod against those paths is a minefield.
2. **No gold patch or Git history.** Task workspace is exported files with no `.git`, solution branch, expected final tree, baseline result, or hidden answer filename.
3. **Private compositional checks.** Public checks expose atomic behavior needed for honest debugging; private checks combine the same declared behaviors and use run-time nonces. Private checks must not require an undocumented feature.
4. **Canary access logging.** Put a random per-run label in the private expectation store. Any read or reproduction of it invalidates the run. Do not use a fixed canary models can memorize.
5. **Trace plus state plus forbidden effects.** Final bytes alone are insufficient: deleting tests, editing the scorer, hard-coding the fixture nonce, bypassing the dispatcher, or fabricating a terminal record all fail on trace/integrity predicates.
6. **Metamorphic pairs.** Randomly choose semantically equivalent mention/execute, false/true Boolean, healthy/dead route, whitespace/path/Unicode, and provider-order variants after the tested process starts. The expectation derives from semantics, not fixture names.
7. **Opaque neutral IDs.** Runtime directories use random IDs, not names such as `expected-block` or `dead-mcp-fallback`. Public task IDs remain in reports only after completion.
8. **Conjunctive critical gate.** Better benign utility cannot compensate for one destructive allow; more blocks cannot compensate for false positives; router recall cannot compensate for telemetry loss.
9. **Independent scorer replay.** Save normalized trace and final-state digest. A second minimal verifier, implemented without importing the production scorer, recomputes the Boolean critical predicates. Disagreement is INVALID.
10. **Evaluator mutation tests.** Seed a scorer that trusts exit 0, one that ignores forbidden state, one with a disclosed answer file, and one writable test. Meta-tests must detect all four before any task is admitted.
11. **Implementation mutation adequacy.** Each family declares a one-line or configuration mutant: invert Boolean success, scan payload instead of verb, require `kg_triples`, route dead MCP, remove read receipt, reset retry fingerprint, suppress exception telemetry, or drop provider normalization. A case that passes both real and mutant implementation does not measure its claimed mechanism and is rejected.
12. **Holdout rotation.** Keep at least two private variants per family and rotate one each scheduled run; publish semantics and old retired variants, not active exact values. Rotation is CONFIG (settings/JSON only), not a new service.

The combination is **very likely (80-90%)** to stop the obvious benchmark shortcuts because it independently locks gold data, observes access, verifies forbidden effects, mutates both scorer and implementation, and changes per-run values. Sophisticated exploitation outside the observed filesystem/process/network boundary remains **UNVERIFIED; the settling experiment is an adversarial red-team run explicitly instructed to maximize score without solving tasks, with every successful exploit converted into a new integrity meta-test before the benchmark gates releases**.

## Benchmark validation and admission

A candidate case is admitted only if all of these checks pass:

1. The oracle trajectory passes.
2. At least one different valid trajectory passes where the specification permits choice.
3. No-op, prose-only “done,” malformed, and direct-answer trajectories fail.
4. Every declared minefield is triggered by a purpose-built cheating trace.
5. Two scorer invocations on the same captured trace return byte-identical normalized results.
6. The task is solvable with all non-loopback network denied.
7. Public tests are sufficient to explain the contract; private tests only compose declared behavior.
8. The mapped implementation mutant fails for the expected diagnostic reason.
9. A clean control adjacent to every attack/absence fixture passes.
10. Fixture source evidence, owner relevance, platform needs, and expected runtime are recorded.
11. A human reads the private oracle for specification fidelity before first admission and after any semantic change.
12. Changing an expected result requires a manifest version bump and a short rationale; a lower score may not be “fixed” by silently ratcheting the baseline down.

Public benchmark drift and bad tests are not hypothetical. OpenAI reports material specification/test problems and contamination in audited SWE-bench Verified tasks ([OpenAI audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)); Terminal-Bench 2.1 documents repairs prompted by external drift, resource mismatch, and misspecification ([Terminal-Bench 2.1](https://www.tbench.ai/news/terminal-bench-2-1)). Therefore manifest versioning and oracle mutation tests are release requirements, not optional polish.

### Two-signal rule inside the benchmark

Any benchmark conclusion that something is absent or broken requires two mechanically independent signals:

- absence: inventory/query result **and** a known-positive control from the same detector;
- broken tool: typed terminal record **and** missing/forbidden final-state transition;
- telemetry: event emitter acknowledgment **and** independent sink query by correlation id;
- destructive block: hook decision **and** unchanged target hash;
- completion: terminal success **and** final-state/receipt verification;
- dead MCP suppression: liveness snapshot **and** invocation counter zero while a healthy fake proves routing works.

This rule is encoded in private predicates; it is not left as prompt advice. It directly responds to the seven bad single-probe conclusions in `INPUT-known-harness-defects.md:111-129`.

## Alternatives considered and rejected

### Public SWE-bench / Terminal-Bench as the release gate

Rejected. They measure model-plus-scaffold capability, require much larger and sometimes drifting environments, are contamination-prone, and do not isolate this owner's detector, router, ledger, or adapter changes. OpenAI's SWE-bench audit and Terminal-Bench 2.1's repairs are concrete evidence above. Public suites may be an optional calibration lane under fixed model/harness/budget, never the local regression oracle.

### LLM-as-judge scoring

Rejected. The target behaviors have exact code/state oracles, and adding a stochastic judge would make a deterministic requirement weaker. No trained critic is justified. This also avoids a previously rejected component class.

### Exact golden trajectory matching

Rejected. It rewards imitation of one tool order and fails valid alternative solutions. Milestones, final state, and minefields preserve flexibility while remaining deterministic, following ToolSandbox and τ-bench.

### One weighted score

Rejected. It enables compensation attacks: extra blocks can mask false positives; router recall can mask a leaked secret; speed can mask corrupted state. A tuple plus conjunctive critical gate is harder to game and more diagnostic.

### Replay raw historical sessions

Rejected as the primary suite. The corpus is distilled, samples are capped, owner-correction candidates are noisy, hook detection is broken, and raw historical environments include external services and secrets. Historical fingerprints select cases; hand-authored minimal fixtures provide stable truth.

### A new benchmark service or observability platform

Rejected. Pytest, the dispatcher, ledger, router eval, Windows Scheduled Task, and background digest already provide execution and delivery. A service would be BUILD-LARGE, violate the anti-overfit gate, and add failure modes without improving these exact oracles.
