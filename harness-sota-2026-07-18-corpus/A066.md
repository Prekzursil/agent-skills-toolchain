## Collision register

### C01 — Common absolute immutability versus Swift actor mutation

**Class:** CONTRADICTION  
**Artifacts:** `claude/rules/swift/coding-style.md` ↔ `claude/rules/common/coding-style.md`

**Exact conflicting lines**

- `swift/coding-style.md:8`: “This file extends common/coding-style.md.”
- `swift/coding-style.md:17-18`: prefer `let`, but permit `var` when required; prefer value-semantic structs, but permit classes for identity/reference semantics.
- `swift/coding-style.md:43-47`: “Enable Swift 6 strict concurrency checking” and prefer “Actors for shared mutable state.”
- `common/coding-style.md:23-33`: “ALWAYS create new objects, NEVER mutate existing ones.”
- `common/coding-style.md:59-68`: completion requires “No mutation (immutable patterns used).”
- Corroborating sibling example: `swift/patterns.md:36-46` explicitly implements an actor with `private var storage` and mutating `set`.

**Why this is a real collision**

Actor isolation makes controlled mutation race-safe; it does not make mutation cease to exist. Likewise, an identity-bearing class may legitimately mutate internal state while preserving an external invariant. The common absolute would reject the exact actor pattern the Swift layer recommends. `rules/README.md:93-104` resolves execution in favor of Swift specificity, but AGENTS §10 does not itself resolve this same-level rule collision.

**Diagnosis:** the common rule is badly written: it turns a useful default (“prefer value semantics and avoid uncontrolled shared mutation”) into an impossible universal. The Swift rule is the more precise instruction on this point.

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace `ALWAYS/NEVER` in `common/coding-style.md:23-33,68` with: “Prefer immutable value transformations. Permit narrowly scoped mutation when the language idiom or required identity demands it; encapsulate shared mutation behind synchronization/isolation, and do not expose uncontrolled mutable state.” Add a Swift note pointing to actors. This is **almost certain (90-99%) to remove the textual contradiction**, because the proposed exception exactly covers `swift/coding-style.md:17-18,46` and the concrete actor at `swift/patterns.md:41-46`; the remaining uncertainty is whether another omitted consumer depends on literal `NEVER mutation` wording.

### C02 — Typed-throws example silently erases and misclassifies errors

**Class:** CONTRADICTION  
**Artifacts:** `claude/rules/swift/coding-style.md` ↔ `claude/rules/common/coding-style.md`

**Exact conflicting lines**

- `swift/coding-style.md:28-39` says “Use typed throws … and pattern matching,” but its example performs `guard let data = try? read(from: path) else { throw .fileNotFound(id) }`.
- `common/coding-style.md:43-49` requires explicit handling at every level and says “Never silently swallow errors.”

**Why this is a real collision**

`try?` converts every thrown read error into `nil`. The branch then reports every failure as `.fileNotFound(id)`, including permission, corruption, I/O, cancellation, or other errors the read API may produce. The official Swift Error Handling chapter documents `try?` as optional-value handling, while typed throws restricts which concrete error type may escape. The example therefore demonstrates error erasure, not comprehensive pattern matching.

**Diagnosis:** this target example is wrong/underspecified. Typed throws itself is current; the defect is the example's blanket remapping and the unexplained assumption that `decode(data)` throws a compatible `LoadError` (`swift/coding-style.md:33-37`).

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Rewrite the example with `do/catch`, catch only the concrete not-found error and map that to `.fileNotFound(id)`, map or propagate every other read/decode case explicitly as members of `LoadError`, and show an exhaustive `switch` at the caller. This is **almost certain (90-99%) to reconcile the rule**, because it directly satisfies `common/coding-style.md:45-49` and Swift's typed-throws constraint; the residual uncertainty is the omitted signatures of the fictional `read` and `decode` functions.
