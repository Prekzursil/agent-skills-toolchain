# G009 — Failure-mode inventory: “green tests, broken deliverable”

## Scope and bottom line

This unit inventories failures in which a local check, test suite, CI gate, receipt, completion marker, or synthetic harness says “pass/done/success” while the property the owner actually needs is false. It does **not** inventory ordinary loud test failures, tool errors, or hangs except where their oracle itself reports green. The ranking below is by expected damage: probability of an undetected escape multiplied qualitatively by consequence and propagation radius, not by raw occurrence count.

The unifying mechanism is **oracle substitution**:

> The harness proves an inexpensive proxy P—exit zero, parseable JSON, a file exists, a marker prefix is present, a mocked state transition passes, or *some* fresh command ran—and silently treats it as proof of the owner’s outcome O. Tests can be perfectly green because they assert P, while P does not imply O.

This is not primarily a “need more tests” problem. In several verified cases the test positively enshrines the wrong contract. Adding more examples against that same proxy makes the suite greener without increasing outcome assurance.

The highest expected-damage class is **semantic inversion at an evidence boundary**: a successful probe is labeled failed or a content-free/counterfeit signal is labeled success, corrupting every downstream conclusion. This is **almost certain (90-99%)** to recur without a structural oracle change because the live defect already recurred after a prior patch, the current implementation still reproduces it, and its own suite remains green (`INPUT-known-harness-defects.md:63-72`; `claude/hooks/tool-result-sentinel/sentinel.py:264-289`; direct controls recorded below).

The second class is **offline/synthetic equivalence mistaken for live behavior**. It has an observed user-visible escape in the SWFOC trainer history: multiple agents reported green suites/builds, but the owner later reported that the actual feature did not work and explicitly rejected mock-only evidence (`inputs/corpus.json:12143,12149,12155,12173,12179,12191,12233,12257`). The corpus is distilled and samples are truncated, so the exact test-to-feature mapping is **UNVERIFIED; the settling experiment is to retrieve the cited raw transcript files, identify each test’s oracle and changed paths, then run the exact built trainer against the game for owner ID/unit selection while recording the process/UI state**.

No proposal below adds a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Every accepted proposal rides the existing hook, dispatcher, ledger, skill, or CI bus. This satisfies the anti-overfit gate.

## 1. Semantic verdict inversion and counterfeit “proof”

### Mechanism

Unstructured text or self-reported command shape is treated as semantic ground truth. On the negative side, a failure-word regex scans serialized successful content and overrides explicit `ok: true`. On the positive side, a receipt classifier recognizes command substrings and permissive output, allowing an agent-controlled string to become a “pass” receipt. Both collapse **meaning** into an easily-triggered lexical token.

### Observed instance 1A — green sentinel suite, successful result labeled FAILED

**Observed event.** A Databricks response contained `"user_cancelled_or_timedout": false` and `ok: true`; the sentinel matched `timedout` in the field name and instructed the agent not to build on the “missing/garbage” output (`INPUT-known-harness-defects.md:63-76`). The same note records a prior incident in which the hook marked every WebFetch 200 as failed (`INPUT-known-harness-defects.md:69-72`).

**Independent current reproduction.** `_gather_text` extracts the `content` string (`sentinel.py:163-196`), then `classify` applies `_INFRA_FAIL` to all MCP result text (`sentinel.py:264-278`); `_INFRA_FAIL` contains `etimedout`/timeout patterns (`sentinel.py:78-90`). The direct control above returns `FAILED` for the recorded success shape.

**Why tests remain green.** The standalone suite proves structural failures, one literal connection error, exit-code handling, a clean decompile, empty-content behavior, throttling, and disablement (`test_sentinel.py:59-171`). Its clean MCP case contains only decompiled code (`test_sentinel.py:113-123`); it has no successful payload containing a failure-like field name with a false value. The test is therefore green because it validates selected string classes, not the precedence rule “explicit success structure dominates words merely mentioned in content.”

**Precondition.** An MCP returns domain data containing a transport-failure substring in prose, a key name, source code, log text, or a false-valued field, without an explicit numeric exit code. `_structural_failed` returns false, after which the regex scans the content indiscriminately (`sentinel.py:218-278`).

**Detection signal.** A metamorphic pair: keep the response structure and explicit success fields identical, then add a false-valued field or quoted prose containing each failure token. Classification must remain `SUCCESS`. Also require a contradiction alarm whenever structural success and text-derived failure disagree. The recorded Databricks payload is the minimal regression fixture.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace free-text transport classification with precedence-aware typed decoding: explicit `isError/success/ok/status/exit_code` owns the verdict; inspect only provider-defined error envelope values, never arbitrary success payload content or field names; return `AMBIGUOUS` on genuine structural/text contradiction instead of `FAILED`. Add metamorphic use-vs-mention/negation/false-valued fixtures shared by every guard. This fix is **very likely (80-90%)** to eliminate the recorded class because it directly removes the lexical path that both the live event and local reproduction traverse; provider envelopes not represented in fixtures are the remaining uncertainty.

### Observed instances 1B–1E — prose guards report green/unsafe conclusions from mention rather than use

The live defect input records: two destructive-command false positives on a `Set-Content` operation whose markdown body quoted `Remove-Item`; six stub-ledger false positives on prose/negation; one Stop marker false positive on a sentence discussing markers; and the tool-sentinel case above (`INPUT-known-harness-defects.md:14-18,24-41,54-68`). Writing the defect report itself created another false positive (`INPUT-known-harness-defects.md:24-28`). These are observed instances, not static predictions.

The owner-visible outcome is not only noise: the false guard caused agents to replace the Write tool with PowerShell here-strings, whose measured failure rate was 13.6% versus 0.0% for Write in that workflow (`INPUT-known-harness-defects.md:35-38,100-102`). Thus a locally “successful” guard regressed the actual deliverable path.

**Precondition.** A detector sees payload text without semantic role—operation verb, target type, code fence, data field/value relationship, or negation—and treats occurrence as execution/unfinished work.

**Detection signal.** For every positive fixture, generate paired use/mention, affirmed/negated, true/false-valued, code/prose, and executable-verb/quoted-body variants. Any identical verdict across all pairs exposes a missing discriminator.

**Structural fix — UNVERIFIED legacy-input availability — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement one shared context discriminator used by command, marker, stub, and result guards. Command safety keys on normalized tool verb plus executable argument positions; source scanners parse file type/fence context; result guards parse typed envelopes and values. UNVERIFIED whether every legacy hook receives enough verb/fence context; the settling experiment is to capture one redacted payload schema for each implicated hook and run the nine recorded fires plus genuine-positive controls. This recommendation inherits the uncertainty only for legacy hooks lacking context. Given adequate inputs, it is **almost certain (90-99%)** to silence the recorded false fires because every incident differs from a true occurrence precisely on those roles (`INPUT-known-harness-defects.md:43-50,78-91`).

### Observed instance 1F — detector success interpreted as absence

Seven wrong conclusions were drawn from unvalidated single probes: context at 100%, stuck agents, missing `mon`, dead boards, fire-and-forget Codex, a true destructive-command positive, and capability counts of zero. A known-positive control then showed skills and agents were present and only the hooks detector was broken (`INPUT-known-harness-defects.md:111-129`).

**Precondition.** A negative result is accepted without first demonstrating recall on a known-present item and without an independent field/measurement.

**Detection signal.** Every absence result carries two receipts: `positive_control_found=true` and `independent_probe_agrees=true`. A result lacking either is `UNKNOWN`, never zero/absent.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a small detector-result schema and wrapper that refuses an `absent/broken` terminal state until a named known-positive control and a mechanically independent probe are attached. It is **very likely (80-90%)** to prevent the seven recorded wrong conclusions because all seven lacked this precondition; it cannot repair two detectors sharing the same blind spot, hence the independent-method requirement.

### Deterministic latent instance 1G — claimant can mint its own passing receipt

This is not recorded as historical misuse, so it is a latent instance, not an observed escape. `CLAIM_RECEIPT_MAP` allows `fixed` to be substantiated by either `test` or `run` (`ledger.py:109-121`), and `has_fresh_receipt` accepts any passing receipt in the required class (`ledger.py:1093-1117`). **Detection signal.** Adversarial “proof minting” tests attempt to satisfy each claim family with echo/output-only, irrelevant passing commands, tests outside changed scope, and passes against a different tree digest. Any accepted receipt is a critical false clear.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Authenticate receipts by runner allowlist or inspectable test artifact, bind them to workspace/diff digest and claim ID, and require bug fixes to show baseline fail → candidate pass → regression pass. It is **very likely (80-90%)** to close the demonstrated minting route because an echo supplies none of those exhibits; platform-specific test runners will require a maintained adapter table.

## 2. Synthetic/offline green substituted for live user behavior

### Mechanism

Unit/replay tests prove internal state transitions against mocks or hand-written mirrors, but the real deliverable depends on an external process, focus behavior, memory layout, timing, bridge wiring, and a user journey. The harness promotes the synthetic result without requiring even one acceptance oracle at the live boundary.

### Observed instance — SWFOC trainer passes many suites but the live feature fails

The corpus records agent completions reporting 44, 46, and 48 passing service tests (`inputs/corpus.json:12143,12149,12155`), 62 passing tests after a “fix” (`:12173`), 87 tests plus a clean build for bridge wiring (`:12179`), and nine side-effect-framework tests (`:12191`). It also records a 26m59s `dotnet test` with no output and an owner concern about test behavior (`:12161,12203`). Later, the owner reports that unit selection “currently it doesnt work,” with a suspected game-focus/no-Lua-flow interaction (`:12233`), and explicitly asks to replace “mock stuff” with a closer-to-live sandbox/contract approach (`:12257`). An earlier owner correction says the trainer was faulty and did not find owner ID properly (`:11795,11939`).

This establishes two independent signals for the class: agent-reported green synthetic checks and owner-observed failure at the live boundary. It does **not** establish that one named 87-test suite covered the exact failing focus/selection scenario. That causal pairing is **UNVERIFIED; retrieve the raw transcript named in the corpus sample, map test names and changed files to owner-ID/unit-selection/focus requirements, then execute the same build against the game with a focus-change script and a screen/API trace**.

**Precondition.** The feature’s state model is mirrored or mocked; the acceptance contract does not name the real game process, focus transition, multi-selection, owner display, bridge cadence, and UI outcome as required modalities.

**Detection signal.** A boundary ladder, all tied to the same build digest: unit → contract/replay → process integration → one golden live journey. The gate explicitly reports the highest achieved layer. A unit/replay pass may never be rendered as “working properly” when the live layer is required and unrun.

**Structural fix — UNVERIFIED live-host automation feasibility — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the task’s Definition of Done with `required_modalities` and `acceptance_commands/artifacts`; for external-process features, require a live or faithful disposable-host receipt before `done`. Keep replay tests for speed, but label their proof boundary. It is **likely (55-80%)** to prevent this class because the missing distinction becomes machine-readable; the lower confidence reflects the difficulty of autonomously driving the Windows game and proving UI semantics. UNVERIFIED whether the game can run headlessly on this owner’s box; the settling experiment is a disposable live smoke that launches the game, changes focus, exercises selection, and captures state without manual intervention.

### Why “just add an LLM reviewer” is rejected

An LLM looking at the same mocks cannot establish external process behavior. Audit D06 cites judge instability and keeps judges advisory (`inputs/audit-findings/D06.md:14-20`). The required discriminator is execution at a more faithful boundary, not another opinion. A trained critic or second verifier runtime would violate the anti-overfit gate and is not proposed.

## 3. Artifact presence, marker prefix, or turn-end substituted for completion

### Mechanism

The system chooses an observable terminal proxy that can become true early: nonempty file, directory contains anything, output begins with `SUCCESS:`, or a synchronous turn ended. It then stops monitoring/relaunching and may discard unfinished work. Tests pass because they use exactly that early proxy as their expected result.

### Observed instance 3A — write-early audit artifacts marked DONE

Audit B16 reports that `mon-audit.ps1` and `launch.ps1` classified any existing findings file as done/skip while the protocol deliberately required early writes. It names five files A01–A05 with explicit work-remaining gaps and missing terminal outputs (`inputs/audit-findings/B16.md:16-21`). The bundled A01–A05 files independently end in “still in progress”/“remaining … being checked” text (`inputs/audit-findings/A01.md:23-24`; `A02.md:23-24`; `A03.md:23-24`; `A04.md:23-24`; `A05.md:23-25`). Thus the partial deliverables are verified on this node. The exact PowerShell classifier is **UNVERIFIED because `mon-audit.ps1` and `launch.ps1` are not in the bundle; the settling experiment is to read those cited lines on Windows and replay one write-early worker that exits before the terminal sentinel**.

### Current general registry enshrines the same weak oracle

The background registry defines completeness as at least one byte or a nonempty directory (`claude/hooks/bg-registry/_common.py:31-33,181-193`). `done_marker.compute_done` maps that predicate directly to status `done` (`done_marker.py:41-60`). Its test writes the six-byte string `result`, expects `done`, and later expects a dead process with any present output to be silent (`test_bg_registry.py:155-176,242-261`). The direct suite reports `ALL PASS`. This is the purest “green tests, broken deliverable” mechanism: the test is correct relative to the implemented proxy and the proxy is insufficient relative to substantive completion.

**Precondition.** A worker writes early, creates a partial directory/file, or is synchronous but returns before fulfilling its contract.

**Detection signal.** Completion requires a terminal record separate from content: exact unit/task ID, terminal state, process exit status, artifact digest/size, contract validator results, and a final sentinel written only after durable flush. The monitor treats artifact existence as progress, never completion.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Change the existing registry record from presence-based completion to a two-phase protocol: `running` → `artifact_ready` → `validated_done`. A launcher writes an atomic sidecar or exact final line containing task ID and artifact digest after validators pass; the registry independently recomputes the digest and checks the worker’s terminal exit receipt. It is **very likely (80-90%)** to prevent the five observed partial-file skips and generic early-write case because presence no longer has terminal meaning. It cannot prove semantic quality unless the task contract supplies validators, which is addressed by the modality/claim contract above.

### Deterministic instance 3B — hollow `SUCCESS:` handoff is explicitly accepted

Subagent start demands a “structured summary” (`agents/harness/modules.py:2355-2367`), but stop checks `_TERMINAL` before checking output length and returns success immediately (`modules.py:2384-2396`). The regression test passes `SUCCESS:review` and asserts `allow` (`tests/test_modules.py:988-1020`). No historical owner-visible escape was found in the available corpus, so this is a verified contract defect, not an observed incident.

**Precondition.** A subagent emits the recognized terminal prefix without scope, methods, evidence, findings, or gaps.

**Detection signal.** Parse a typed terminal envelope and validate required fields plus referenced artifact existence/digest; a prefix is never sufficient.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace prefix short-circuit with a closed summary schema `{status, scope, methods, findings, evidence, gaps, artifact_digest}`; only `status=success` plus all task-required fields clears. It is **almost certain (90-99%)** to reject the shown `SUCCESS:review` counterexample because it cannot parse or satisfy the schema; semantic truth of populated fields still requires evidence validators.

## 4. Green receipt detached from the exact claim and workspace state

### Mechanism

Even a genuine test pass becomes false evidence when a later mutation is invisible, a sibling changes the workspace, the pass covers a different scope, or one receipt is allowed to satisfy multiple detected claims. This is temporal/exhibit substitution: “a check passed” replaces “this claim is true of this exact deliverable state.”

### Verified enabling conditions

The mutation recognizer includes native write tools, but shell commands count only when a narrow redirection/`tee`/`Out-File`/`Set-Content`/`Add-Content` regex matches (`modules.py:933-939,1090-1107`). Formatters, `git apply`, `Move-Item`, and in-place rewriters can therefore mutate without advancing the freshness floor. `last_mutation_seq` is turn-scoped (`ledger.py:1065-1079`), while a receipt is accepted if its sequence exceeds that floor (`ledger.py:1093-1117`). Audit D30 independently identifies missing tree/diff identity and cross-turn/sibling weakness (`inputs/audit-findings/D30.md:31-38`). No live misuse was observed; D30 explicitly says its counterfeit receipt is proven possible, not observed (`D30.md:78-84`).

The claim gate unions allowed receipt classes for all detected families, then accepts if **one** fresh receipt matches any class (`modules.py:2197-2215`; `ledger.py:109-121`). Therefore a message asserting multiple outcomes can clear on one convenient modality. Audit C11 describes the required ALL-families/ANY-within-family correction (`inputs/audit-findings/C11.md:82-95`).

**Precondition.** An unrecognized/sibling mutation follows a pass, multiple claim families are asserted, or the tested tree/scope differs from the delivered tree/scope.

**Detection signal.** Each receipt includes subject digest, changed-path set, runner identity/version, command, oracle class, baseline/candidate result, and claim IDs. Completion requires all claim IDs to have at least one allowed, post-mutation, matching-subject receipt. Mutating the subject after a receipt must deterministically stale it.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Enrich the existing ledger receipt rather than add a verifier service. Track project/worktree mutations at the normalized PostToolUse boundary, stamp a bounded Git tree/diff digest or explicit artifact digest, and evaluate `ALL(claim families) × ANY(allowed modality within family)`. This is **very likely (80-90%)** to close the source-verified stale/cross-claim routes because acceptance becomes a relation among claim, subject, and oracle rather than a timestamp. Non-Git/generated external state needs explicit artifact adapters.

## 5. Process/transport composition is green while protection is absent

### Mechanism

Subprocess tests accept exit zero, optional/empty stdout, and parseable dictionaries. Production is intentionally fail-open, so import failure, module-factory failure, invalid input, a quarantined guard, or provider-incompatible output can meet every test oracle while doing no protective work.

### Source-verified instances

The dispatcher catches all top-level exceptions and returns zero (`agents/harness/dispatcher.py:530-556`). Its event matrix invokes `dispatcher.py` directly with `sys.executable`, asserts return code zero and absence of `suppressOutput`, and if output exists checks only that it parses to a dictionary (`tests/test_dispatcher_and_registration.py:235-304`). It therefore bypasses the generated launcher/host and permits empty output. The module-order test asserts only the inert `MODULE_ORDER` tuple (`tests/test_modules.py:49-61`), while production actually constructs modules and a shared ledger in `build_default_modules` (`modules.py:2599-2613`). Audit A16 independently reaches the same conclusion (`inputs/audit-findings/A16.md:15-19`).

Malformed input is normalized to `{}` and dispatched (`dispatcher.py:530-546`); its test requires only exit zero/no `suppressOutput`/optional JSON (`tests/test_dispatcher_and_registration.py:210-232`). A quarantine skip is a bare `continue` (`dispatcher.py:267-275`), after which the terminal result is `SUCCESS` if no other error occurs (`dispatcher.py:317-329`). Thus “command survived” and “guard executed correctly” are distinct, but the smoke oracle does not require the latter.

These are deterministic source paths, but a current pytest pass is **UNVERIFIED because pytest is unavailable on this node; the settling experiment is a no-write-safe CI run plus fault-injection cases that break the generated launcher, factory construction, each module, and provider renderer while asserting an explicit executed-module manifest**.

**Precondition.** Fail-open behavior coincides with a smoke test whose oracle is only process/JSON validity, or a module is quarantined/omitted without an execution manifest.

**Detection signal.** Every event response carries a bounded coverage manifest: expected module IDs/version digest, executed/skipped/failed status, provider render schema result, and mandatory-module policy. A smoke test must run the exact generated launcher under the host shell and assert the manifest, not only exit zero.

**Structural fix — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Preserve fail-open for host availability, but make degraded protection observable and non-green: terminal status `DEGRADED`, explicit skipped/failed module list, and a separate liveness receipt. Add exact launcher/provider contract tests. It is **very likely (80-90%)** to eliminate silent composition greens because every omitted/quarantined/failing module becomes machine-visible; provider hosts may still discard unsupported fields, so host-native schema fixtures are required.

## 6. Deployment transaction holes hidden by happy-path tests

### Mechanism and evidence

Audit A16 reports that deploy tests cover conflicts before writes and corruption after writes but not an exception during sequential `os.replace` or receipt writing, leaving a possible mixed live tree (`inputs/audit-findings/A16.md:21-28`). Audit A15 reports three independent install writes without transaction/rollback and tests that do not inject later-write failure (`inputs/audit-findings/A15.md:43-51`). Bundled source independently shows sequential config/manifest writes (`agents/harness/install.py:479-512`), a check-then-write deploy lock (`install.py:623-646`), sequential per-file replacements followed later by the receipt (`install.py:775-830`), and only a CAS-specific `except` plus lock release in `finally` (`install.py:831-845`). This verifies the enabling control flow, but a historical mixed-version incident is **UNVERIFIED; the settling experiment is a temp-copy fault-injection matrix that raises at every `os.replace` and receipt step, then verifies byte-identical rollback and provider parity**.

**Precondition.** A process crash, disk error, antivirus/file lock, or concurrent installer occurs after at least one live file replacement.

## What not to do

1. **Do not maximize test count or coverage percentage.** A16 found hundreds of substantive cases yet the failures cluster at composition, concurrency, semantic corruption, and terminal boundaries (`inputs/audit-findings/A16.md:1-4`). A wrong oracle with more examples remains wrong.
2. **Do not make file size a completion threshold.** Any fixed byte count can be reached by a partial verbose artifact; only a terminal contract plus validation separates progress from completion (`bg-registry/_common.py:31-33,181-193`).
3. **Do not solve semantic correctness with more regexes.** The live guard defect followed three rewordings and recurred through field-name matching (`INPUT-known-harness-defects.md:35-41,63-72`).
4. **Do not make a model judge the final correctness oracle.** It cannot observe an unexecuted live environment and would add a rejected critic/runtime. Keep subjective review advisory after deterministic acceptance (`inputs/audit-findings/D06.md:14-20`).
5. **Do not require every task to run every modality.** That overfits and wastes time. The contract selects modalities based on the actual outcome boundary; trivial local edits may need only a scoped check, while game/UI/external-process claims need integration/live evidence.
6. **Do not replace the existing dispatcher/ledger.** Fresh receipts, exact-failing-command fingerprints, lifecycle hooks, and shadow staging already exist (`ledger.py:1065-1163`; `modules.py:2167-2228`). The defect is evidence adequacy and binding, not absence of a bus.

## Final decision

Evolution is better than wholesale replacement for this failure class. The current bus already has the right insertion points—normalized lifecycle events, append-only receipts, claim families, exact-command fingerprints, and shadow modes (`agents/harness/ledger.py:98-128,1065-1163`; `modules.py:2167-2228`; `dispatcher.py:235-330`). The ambitious change is not more scaffolding; it is to change the unit of “green” from **a check ran** to **every required claim about this exact subject has an outcome-faithful, validated exhibit, and the worker emitted a terminal receipt only after those exhibits passed**.

That architecture is **very likely (80-90%)** to prevent the observed semantic-inversion, partial-artifact, hollow-handoff, stale/counterfeit-receipt, and mock/live substitution classes because it removes their shared error: treating P as if it necessarily implied O. The remaining uncertainty is domain-oracle quality—especially live Windows/game/UI automation—which is why the contract records achieved modality rather than pretending an offline pass is universal proof.
