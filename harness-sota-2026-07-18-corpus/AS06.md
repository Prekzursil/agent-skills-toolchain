# AS06 — coherence sweep: MCP fleet versus skill assumptions

Date: 2026-07-19  
Scope: read-only analysis of the unpacked bundle at `/local_disk0/codexwork/bundle`; the only write is this artifact.

## Executive verdict

No enforced skill-to-MCP dependency contract is visible in the supplied bundle. Skills and adjacent specialist agents can name exact MCP tools, while routing suggests static MCP families without checking whether those names exist in the current provider session. The only concrete liveness policy shipped in the bundle covers `basic-memory` plus registered reverse-engineering daemons, not the general fleet. This is visible directly in `claude/hooks/skill-router/route.py:157-215`, which builds MCP suggestions from regex matches, and `claude/hooks/mcp-liveness/critical.json:6-20`, whose only critical server is `basic-memory`; the search detector's known-positive is Codex's native `skill_mcp_dependency_install` setting at `codex/config.toml:87`.

This is not merely theoretical. The corpus records one obsolete connector namespace, `claude_ai_Tavily`, being called 738 times. Its `tavily_extract` tool failed 137/532 calls, including 135 exact `not connected` failures, while `tavily_search` failed 139/194 calls, all with the same message. The prompt's pinned summary mentions only the 532-call extract row; the full corpus therefore reveals a larger aggregate: 276 errors across 726 search/extract calls, plus 12 crawl/map calls with no failure row. Evidence: `/local_disk0/codexwork/bundle/inputs/corpus.json:1`; reproduced by the command in Evidence Appendix E1.

The most directly evidenced skill collisions are:

1. `codex-consult`: **UNVERIFIED from this bundle; settle by reading both Windows manifests and invoking the two mounted Codex tools once.** Prior audits report that a live Claude-facing copy directs callers to nonexistent tool families even though the real `mcp__codex__codex` and `mcp__codex__codex-reply` surface is mounted. This is a stale-name collision candidate, not a dead-server claim.
2. `multi-ai-mingle`: **UNVERIFIED current state; settle with the supervisor, MCP protocol, and Claude registry probes in C2.** Its advertised Claude/Codex peer-mail rail reportedly had neither a Claude MCP registration nor a responsive daemon during the prior live audit, even though Codex still declared the endpoint enabled.
3. Research routing: `deep-research` advertises Tavily among several provider routes, and the router separately recommends Tavily by static label. The corpus proves repeated selection of a dead Tavily connector namespace. The exact causal attribution from skill invocation to the 276 failures is **UNVERIFIED; the settling experiment is to join each raw transcript's nearest preceding `Skill` invocation/router injection to the failed `mcp__claude_ai_Tavily__*` call** because the corpus aggregates skills and tools independently.

Several other apparent conflicts are intentional and safe only when a live alternative is actually available: disabled duplicate plugins with a separate connected MCP, and heavy RE servers parked off-default with an explicit on-demand bring-up path. A disabled entry by itself is not a defect.

**NATIVE-vs-BUILD: BUILD-SMALL.** The minimal repair is a declared `requires_mcp`/`fallback` contract in skill frontmatter plus invocation-time intersection with the host's actual tool inventory. It belongs on the existing skill validation/router/hook bus; it does not justify another orchestrator, gateway, registry service, vector database, durable runtime, trained critic, observability SaaS, or guardrail framework.

## 2. The architectural collision

### 2.1 Static routing claims “registered MCP” without registration evidence

`skill-router/capabilities.py` describes itself as covering “all ~48 connected MCP servers” (`:1-9`) and emits literal families including Firecrawl/Tavily (`:24-32`), disabled RE servers (`:34-39`), Context7 (`:48-51`), PDF/OCR/MarkItDown (`:57-64`), Semgrep (`:75-76`), Playwright (`:79-83`), and GitHub CLI (`:89-90`). The data module performs no I/O; `match()` only regex-matches text (`:104-117`).

`skill-router/route.py` calls that static matcher at `:165-169` and injects the results at `:190-215`. It never reads the effective MCP registry, `disabledMcpServers`, plugin state, native `tools/list`, or a liveness snapshot. Its skill catalog is likewise harvested from every manifest it finds (`:91-120`) and cached for 24 hours (`:123-136`) without validating declared tools.

The command-time nudge repeats the same false premise. `strong-tool-nudge/check.py:43-63` detects hand-rolled alternatives and tells the model that “a registered MCP already provides” the feature, but its only input is the same static capability table. It has no inventory check.

This creates two distinct failure modes:

* **Hard-name failure:** a skill instructs an exact `mcp__server__tool` name that is absent in the current host.
* **Soft-route failure:** the router says a family exists; the model chooses a stale alias or disabled provider even when another alias is healthy.

The corpus's `claude_ai_Tavily` failures are the observed soft-route/hard-alias outcome. The exact percentage of those calls caused by router text rather than a skill or model recollection is **UNVERIFIED; the settling experiment is the transcript join described in §1.3**.

### 2.2 Liveness does not close the gap

`mcp-liveness/critical.json:6-15` declares only `basic-memory`; `:16-20` handles RE daemons only if registered. `liveness.py:9-25` confirms that intended boundary. It does not cover Tavily, Firecrawl, Context7, Codex, Figma, scholarly access, Playwright, agent-mail, or the rest of the fleet.

Even for `basic-memory`, the probe accepts any JSON-RPC `error` envelope as healthy (`liveness.py:151-164`) and never calls `tools/list`. Prior audit A26 independently reproduced that false-positive class with synthetic error and plaintext bodies (`inputs/audit-findings/A26.md:64-70`). Thus “server answered” is not the same as “skill's required tool exists.”

## 5. Recommended design

### R1 — UNVERIFIED host schema tolerance: declare skill dependencies and fallbacks

**NATIVE-vs-BUILD: CONFIG**

Add provider-neutral metadata to each MCP-dependent skill, for example:

```yaml
requires_mcp:
  mode: any
  capabilities: [web.search, web.extract]
  preferred:
    claude: [search-hub.tavily_search, tavily.tavily_search]
    codex: [tavily_search]
fallback:
  kind: explicit-degrade
  route: WebSearch
```

For strict skills, use `mode: all` and `fallback: fail-visible`. For setup-only skills, use `activation: setup`; for RE, use `activation: on-demand` and a preflight. Never put secrets or credential values in the manifest.

This design is **likely (55-80%)** to fit within existing skill frontmatter because the skill validator already parses manifests (prior E01 at `inputs/audit-findings/E01.md:71-77`), but schema tolerance in both hosts is **UNVERIFIED; settle by validating one no-op metadata field in disposable Claude and Codex skill catalogs**.

### R2 — UNVERIFIED host inventory API: resolve against the effective live tool catalog at invocation

**NATIVE-vs-BUILD: BUILD-SMALL**

Extend the existing router/validator bus with one resolver:

1. Read the host-provided effective tool inventory, not raw config files.
2. Intersect a skill's capability requirements with exact available tools.
3. Probe a minimal data operation when mere `tools/list` is insufficient.
4. Return `READY`, `DEGRADED(alternative)`, `ON_DEMAND(preflight)`, or `UNAVAILABLE(reason)`.
5. On `not connected`, missing-tool, or auth failure, invalidate the session cache and try one declared alternative; never retry the same dead alias in a loop.

The code can ride `skill-router` plus the existing MCP liveness/ledger path; it needs no daemon. The <~200-line estimate is **roughly even (45-55%)** because provider tool-inventory access is not present in the bundle. The settling experiment is a 30-line prototype that captures available tool identifiers from both native hosts; if host APIs cannot expose them, the design may need separate provider adapters but still not a new runtime.

### R3 — Make routing availability-aware and truthful

**NATIVE-vs-BUILD: BUILD-SMALL**

Replace static labels such as `mcp__firecrawl__* / tavily / scrapegraph` with capability IDs resolved at runtime. If no tool is live, the router must say `MCP unavailable; use declared fallback`, not “a registered MCP already provides” it. `strong-tool-nudge` must not discourage a working CLI/library fallback unless the resolver returns `READY`.

This is **very likely (80-90%)** to prevent the exact false nudge because the current false assertion is emitted directly at `strong-tool-nudge/check.py:61-63` from a no-I/O table.

### R4 — Quarantine stale aliases immediately after a connection error

**NATIVE-vs-BUILD: BUILD-SMALL**

Use the existing hook/ledger bus to store a session-scoped `(server, failure_class, timestamp)` quarantine. One `not connected` error suppresses that exact alias for the rest of the session unless a fresh liveness probe succeeds. Alternatives remain eligible. Do not create durable global health state from one transient error.

This is **likely (55-80%)** to cut repeated dead calls because the corpus has 274 identical Tavily connection errors across two tools; precise savings are **UNVERIFIED; settle by replaying the relevant transcript sequences against the quarantine rule and counting avoided retries**.

### R5 — UNVERIFIED fleet-generator integration: generate provider/tier compatibility tests from the same manifest

**NATIVE-vs-BUILD: BUILD-SMALL**

At skill sync and MCP projection generation, assert:

* every strict skill has at least one satisfiable provider projection;
* every off-default skill has an explicit activation/fallback path;
* every hard-coded `mcp__server__tool` exists in a captured `tools/list` fixture;
* every replacement/alias is tested in the provider where the skill is published;
* no stale alias remains in router caches after a sync.

This is **likely (55-80%)** to remain small if implemented as schema checks plus set arithmetic on fixtures. It reuses the current validator and proposed fleet SSOT; the exact fleet generator is **UNVERIFIED in this bundle, and the settling experiment is to inspect the Windows repo paths cited by A29 and run its projection tests in an isolated copy**.
