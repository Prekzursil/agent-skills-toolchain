# A052 — coherence audit of `~/.claude/rules/php/hooks.md`

## Scope, method, and verdict

This unit audited the complete 24-line subject file at
`/local_disk0/codexwork/bundle/claude/rules/php/hooks.md`, then compared it with the unpacked
rules, active hook wiring and implementations, `settings.json`, `CLAUDE.md`, both available
`AGENTS.md` copies, and the distilled corpus. The subject applies to PHP source plus
`composer.json`, PHPStan configuration, and Psalm configuration (`php/hooks.md:1-8`). Its operative
requirements are:

1. auto-format edited PHP with Pint or PHP-CS-Fixer (`php/hooks.md:15-17`);
2. run PHPStan or Psalm after PHP edits in “typed codebases” (`php/hooks.md:18`);
3. run targeted PHPUnit or Pest tests after behavior-affecting edits (`php/hooks.md:19`);
4. warn on debug/termination calls (`php/hooks.md:21-23`); and
5. warn on raw SQL or disabled CSRF/session protection (`php/hooks.md:24`).

**Verdict:** the rule is documentation, not an implemented PHP hook contract. Four rule families
(formatter, analyzer, targeted tests, and warning scans) are **UNENFORCED**. The only wired
per-edit validator explicitly has no PHP branch. The rule also contains one same-level policy
collision around “raw SQL,” one higher-precedence contradiction exposed when `composer.json` is
edited, several redundant restatements, an obsolete hook taxonomy inherited from its common base,
and applicability globs that load the rule for configuration edits without specifying what those
edits require.

I am **almost certain (90-99%)** that the active unpacked configuration does not implement the four
PHP-specific hook families: signal 1 is the concrete `PostToolUse` wiring at
`claude/settings.json:310-354`; signal 2 is the complete extension dispatch in
`claude/hooks/per-edit-check/check.py:151-170`, which handles Python, JS, JSON, YAML, TS (skip), and
Rust (skip), then silently skips every other extension. A third independent configuration signal is
the local dispatch manifest, whose complete `PostToolUse` check list contains only memory-spool,
tool-result-sentinel, and stub-ledger (`claude/hooks/_dispatch/manifest.json:144-180`). This is not a
claim about the live Windows filesystem beyond the supplied snapshot.

## Precedence applied

The applicable precedence is explicit at `claude/AGENTS.md:115-131`: user/permissions first,
security and safety second, the cross-tool contract third, project governance fourth, and
third-party skills fifth. Lower layers may add restriction but may not relax the safety floor;
same-level conflicts must be surfaced rather than silently resolved (`AGENTS.md:129-131`).

The rules package separately claims that language-specific rules override common rules
(`claude/rules/README.md:93-98`). That statement cannot override the higher-precedence cross-tool
contract. It can resolve a PHP-vs-common language-idiom collision only where the cross-tool contract
is silent. No PHP-specific rule is entitled to weaken `AGENTS.md` section 6.

### C05 — “Raw SQL” warning conflicts with the PHP security rule’s allowed safe SQL

**Class: CONTRADICTION**

**Artifacts and exact lines:**

* `claude/rules/php/hooks.md:24`: warn whenever edited PHP files “add raw SQL.”
* `claude/rules/php/security.md:17-21`: require prepared statements for dynamic queries and avoid
  string-building SQL in controllers/views; this permits parameterized SQL through PDO/Doctrine.
* `claude/rules/common/code-review.md:102-110`: the defect to catch is SQL injection through string
  concatenation, not SQL text categorically.

**Precedence result:** both PHP files are same-level language-specific rules. `AGENTS.md:129-131`
therefore does **not** authorize silently choosing one. The package’s “specific overrides general”
rule (`rules/README.md:93-98`) cannot resolve a collision between two equally specific PHP files.

**Why this is a defect:** a compliant prepared PDO query contains SQL text and is “raw SQL” under a
common interpretation, so the hook clause is broader than the actual security invariant. I am
**very likely (80-90%)** that this produces false warnings if implemented literally, based on the
explicit permission for prepared PDO/Doctrine statements at `php/security.md:19`; the remaining
uncertainty is the undefined phrase “raw SQL.”

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace “add raw SQL” with
“introduce dynamically constructed or interpolated SQL that is not parameterized; warn on SQL in
controllers/views and point to the exact concatenation/interpolation.” This makes the hook rule
identical to the security invariant rather than stricter by accident.
