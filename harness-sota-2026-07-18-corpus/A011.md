# A011 — coherence audit of `~/.claude/rules/common/security.md`

## Executive verdict

The file is not coherent enough to remain the security policy's detailed source of truth. Its always-on pointer to `AGENTS.md` is sound, but the detailed rule has four kinds of drift:

1. absolute wording conflicts with the higher-precedence boundary-based security floor and with platform-specific secret storage;
2. the security-response and severity thresholds disagree with peer rules and with the `security-reviewer` agent;
3. active settings enforce credential-read and force-push policies that the rule does not state, including a force-push scope stricter than `AGENTS.md`;
4. the one active post-edit hook whose tests claim to enforce hardcoded-secret writes no longer contains the scanner those tests require.

The most important concrete defect is the stale write-path secret gate. `settings.json:334-340` invokes `per-edit-check/check.py` after edits; `per-edit-check/test_secrets.py:136-151` requires it to block a real-shaped key and honor `PER_EDIT_SECRETS=off`; but the complete 251-line deployed `check.py` only performs syntax/lint dispatch (`check.py:42-170`) and its `main()` only calls `_run_check` (`check.py:176-247`). A read-only runtime import independently returned `has_scan_secrets=False` and `main_names_secret=False`. Thus the secret-write requirement is **UNENFORCED**, not merely undocumented.

Confidence: **almost certain (90-99%)**, because the conclusion is supported by the active settings entry, the deployed implementation, the contrary test contract, and an independent runtime import. The remaining 1-10% covers the possibility that an external, unpacked plugin adds an additional secret scanner; that premise is **UNVERIFIED — experiment to settle it:** on the Windows owner machine, run `Get-Content ~/.claude/settings.json | ConvertFrom-Json` to enumerate all effective hooks including managed/project settings, then perform a synthetic canary edit in a disposable repo with a generated fake provider-key shape and record every hook decision.

## Scope, evidence discipline, and precedence

The audited subject is the read-only unpack at `/local_disk0/codexwork/bundle`; paths below are relative to that bundle unless shown otherwise. I wrote only this artifact.

I read `claude/rules/common/security.md` in full (52 lines). Its frontmatter covers common source extensions at lines 1-20; it explicitly delegates the always-on floor to `AGENTS.md §9` at lines 23-24; its commit checklist is lines 26-36; secret management is lines 38-43; and incident response is lines 45-52.

Precedence is not discretionary. `claude/AGENTS.md:115-131` orders: explicit user instruction and permission system; security/safety non-negotiables; the cross-tool contract; project governance; third-party skill/plugin defaults. It also says same-level conflicts must be surfaced, not silently chosen (`AGENTS.md:129-131`). I apply that order below. In particular:

- `AGENTS.md §9` wins over `common/security.md` when the latter says “all” but the floor says “at system boundaries” (`AGENTS.md:93-106`).
- Language rules and common rules are peer rule files. Their “extends” language does not define override semantics, so `AGENTS.md §10` does **not** resolve their same-level contradictions.
- A source comment claiming a past “owner directive” is evidence about design intent, not proof of a current explicit in-session instruction. I do not silently elevate such comments to precedence level 1.

## Collision register

### A011-C01 — boundary validation versus “all user inputs”

**Class: CONTRADICTION**

**Artifacts and exact lines**

- `claude/rules/common/security.md:28-30`: “Before ANY commit” and “All user inputs validated.”
- `claude/AGENTS.md:95-98`: “Validate all user inputs at system boundaries; sanitize before HTML output.”
- `claude/rules/common/coding-style.md:51-57`: validation is “at system boundaries,” while external data includes API responses, user input, and file content.
- `claude/agents/security-reviewer.md:68-72`: “Validate and sanitize everything,” reintroducing the unbounded shorthand.

**Why this collides**

“All user inputs before processing” demands repeated validation inside already-typed/trusted internal layers; the higher-precedence floor requires validation at trust boundaries. The higher-precedence `AGENTS.md` resolves actual behavior in favor of boundary validation, but the stale lower wording remains a coherence defect and encourages redundant validation.

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing rule bus).** Replace `security.md:30` with “Untrusted input is parsed/validated once at every system boundary; downstream code preserves the validated type/invariant.” Change the reviewer shorthand at `security-reviewer.md:71` to the same trust-boundary formulation. This is **very likely (80-90%)** to reduce contradictory review findings because both currently conflicting phrases are direct prompt inputs; evidence is the exact same concept stated with two scopes in the cited files.

## Consolidated resolution design

The minimal coherent architecture is:

1. `AGENTS.md §9/§9b` remains the always-on security floor and highest lower-than-user authority.
2. `common/security.md` becomes the single definitions file for trust boundaries, accepted secret-injection/storage classes, proactive reviewer triggers, severity disposition, and incident response.

Every component rides an existing rule, agent, settings, or hook bus. No second orchestration runtime, vector/KG memory, durable execution engine, trained critic, observability SaaS, or guardrail framework is proposed. This passes the anti-overfit gate.
