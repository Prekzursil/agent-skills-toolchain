# X057 — Cross-domain borrow: control theory → tool design

**Unit:** X057  
**Lens:** observability/controllability, feedback stability, anti-windup, and dead-band design  
**Target:** tool interfaces and error feedback that induce repeated agent misuse, especially the measured 1,631 unmatched-quote EOF failures  
**Scope discipline:** ideation and external research only. Per the unit brief, I did not inspect or infer the local harness implementation.

## Executive result

The borrow **does transfer, but narrowly**. The useful control-theory mechanism is not “put a PID controller around an LLM.” It is the combination of:

1. expose both the controller's requested actuation and the actuator's realized actuation;
2. detect saturation or rejection at the actuator boundary;
3. stop accumulating correction in a channel that currently cannot produce more actuation;
4. feed the realization error back into a small recovery controller; and
5. add hysteresis so recovery does not chatter between equivalent failing modes.

In control engineering, anti-windup back-calculation feeds the difference between unsaturated controller output and saturated actuator input back to the integrator. Conditional integration instead freezes the integrator while the controller is pushing farther into saturation. MathWorks' implementation documentation states both mechanisms explicitly and also states their key preconditions: the actuator limits must be known and, for the built-in technique, the controller output must be the only signal feeding the actuator ([anti-windup example](https://www.mathworks.com/help/simulink/slref/anti-windup-control-using-a-pid-controller.html); [PID controller reference](https://www.mathworks.com/help/simulink/slref/pidcontroller.html)).

For an agent tool call, the analogous “actuator” is the entire command-realization chain: tool schema → harness serialization → selected shell parser → expansions → native-process argument passing → process. A raw command string is merely the requested actuation. The actual shell dialect, parse stage, tokenization, expanded arguments, and launched `argv` are the realized actuation. An unmatched quote is actuator rejection: no intended process action occurs, yet an agent may keep adding corrective text. The measured 1,631 unmatched-quote EOF failures are therefore a plausible retry-windup population, not proof that all 1,631 are retry windup.

It is **very likely (80-90%)**, based on the direct structural match between “requested output differs from realized actuator input” in anti-windup and “requested command differs from parsed/launched action” in a shell boundary, that exposing realization feedback and clamping same-mode retries would prevent a material subset of repeated quoting failures. This effectiveness estimate is **UNVERIFIED; the settling experiment is the paired, held-out replay described under Evaluation**. The claim is deliberately “material subset,” not “most failures,” because the corpus count establishes syntax failures but does not, in this unit, identify how many were repeated attempts for the same semantic action.

The analogy does **not** justify numeric PID gains, a learned process model, formal observability-rank claims, or a second orchestration runtime. An LLM-agent loop is nonlinear, history-dependent, partly stochastic, and changes its policy after reading natural-language errors. Those disanalogies block formal control guarantees. What survives is a small, explicit interface state machine operating on observable events.

## 1. What control theory solved in its own field

### 1.1 Observability: control cannot rely on hidden state

Åström and Murray define a linear system as observable when its state at time `T` can be determined from its measured input and output history on `[0,T]`. They explain the practical consequence: an observable system has no hidden dynamics, and sensors plus a model can serve as a virtual sensor ([Feedback Systems, Chapter 7 PDF](https://www.cds.caltech.edu/~murray/books/AM08/pdf/am08-outputfbk_28Sep12.pdf); [Caltech chapter page](https://www.cds.caltech.edu/~murray/FBS/Output_Feedback.html)). In its own field, an observer combines known control input `u`, measured process output `y`, and a model to estimate unmeasured state `x̂`. The estimate can then drive output-feedback control.

This is not a generic exhortation to “log more.” The mechanism asks a sharper question: can two internal states that require different corrective actions be distinguished from available input/output histories? If not, no feedback policy using those measurements can reliably choose the correct action.

For shell tooling, the materially different hidden states include:

- Bash waiting for a closing single quote;
- PowerShell parsing an expandable double-quoted string;
- a command that parsed successfully but whose quotes were removed before native argument passing;
- a wrapper layer consuming a quote before the selected shell sees it;
- the intended executable launching with the wrong argument boundaries; and
- the executable launching correctly and rejecting an application-level value.

These are not interchangeable. POSIX specifies several distinct quoting mechanisms and processing phases, including token recognition, expansion, field splitting, and quote removal ([POSIX Shell Command Language §2.2 and §2.6](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)). Microsoft documents another boundary: PowerShell interprets quoted strings before passing them to a native command, removing the outer quote characters; its parser also changes from expression mode to argument mode for command invocation ([PowerShell quoting rules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-7.5); [PowerShell parsing rules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5)). Thus “shell command failed” is an under-observed output for choosing a repair.

### 1.2 Controllability/reachability: diagnosis without an effective lever is insufficient

In state-space control, reachability asks whether an input can move the system from one state to another in finite time. For a reachable linear system, state feedback can place closed-loop eigenvalues under the standard assumptions; unreachable modes cannot be reshaped by the available input ([Caltech State Feedback chapter](https://www.cds.caltech.edu/~murray/FBS/State_Feedback.html); [Chapter 6 PDF](https://www.cds.caltech.edu/~murray/books/AM08/pdf/am08-statefbk_22Feb09.pdf)).

The tool-design translation is operational rather than algebraic: an error interface is not useful merely because it names the state. It must expose a control input that can leave that state. “Unexpected EOF while looking for matching quote” improves observation but often leaves the agent actuating through the same raw-string channel. A typed `executable + argv[] + stdin` route, or a shell-specific syntax-check route with exact span data, creates a different control direction. Without such a route, the tool can diagnose quote saturation while leaving the agent unable to bypass it.

I do **not** claim that the harness is mathematically controllable. That would require a defined state model and input matrix, neither of which this ideation unit establishes. The useful design test is weaker: for each error state emitted by the interface, is there at least one machine-invocable recovery action that avoids the failed transformation stage?

### 1.3 Saturation and integrator windup: bounded output can hide unbounded internal demand

In a PID loop, actuator saturation clips the plant input even while the integral term continues accumulating error. The controller's internal requested output can grow far outside actuator limits, so when the error reverses the controller takes a long time to unwind. MathWorks explicitly notes that internal signals can be unbounded while the block output appears bounded, and documents two remedies ([PID controller reference, anti-windup section](https://www.mathworks.com/help/simulink/slref/pidcontroller.html)):

- **Back-calculation:** feed the difference between the saturated and unsaturated control signals back to the integrator, with a gain controlling the unwinding time constant.
- **Clamping/conditional integration:** stop integration when output is beyond a limit and the integrator input would push farther into saturation; resume when those conditions cease.

The crucial insight is not simply “retry less.” It is that a controller must receive the **real actuator output**, not assume its requested output was applied. For downstream saturation or cascaded actuator dynamics, the reference implementation exposes an external tracking input and feeds the actuator's output back to it; the documentation says built-in methods are insufficient when limits occur downstream ([anti-windup example, tracking mode](https://www.mathworks.com/help/simulink/slref/anti-windup-control-using-a-pid-controller.html)).

That is the most exact borrow for nested shell tooling. A command can traverse multiple downstream transformations. Pre-validating the agent's original string alone does not reveal what a wrapper or shell ultimately launched. The recovery loop needs both the requested form and a safe representation of the realized form.

### 1.4 Dead-band and hysteresis: prevent high-frequency corrective chatter

A dead-band defines an error interval within which the controller output does not change. Rockwell Automation documents an adjustable PID dead-band around the setpoint and a zero-crossing variant that continues control until the process crosses the setpoint, then holds output while it remains inside the band. Its purpose includes reducing final-control-element wear ([Rockwell Automation, “Setting the Deadband (PID)”](https://www.rockwellautomation.com/en-id/docs/studio-5000-logix-designer/37-00/contents-ditamap/instruction-set/special-instructions/proportional-integral-derivative--pid-/setting-the-deadband--pid-.html)). The zero-crossing rule supplies state/history: behavior inside the same numeric band depends on which boundary was crossed. That is hysteresis, not merely a symmetric threshold.

The trade-off is intrinsic. A wider dead-band reduces switching but permits a larger deviation from setpoint; a narrow band tracks closely but can chatter. Therefore the correct agent analogue is not “ignore small errors.” It is “once the loop has switched to a recovery actuator, do not switch back on a nearly identical observation.”

### 1.5 Feedback stability: delay and loop gain constrain correction speed

Feedback can amplify rather than suppress error when correction arrives late or is too aggressive. Åström and Murray describe gain margin, phase margin, stability margin, and delay margin as measures of how much loop variation or time delay can be tolerated before instability ([Caltech Frequency Domain Analysis chapter](https://www.cds.caltech.edu/~murray/FBS/Frequency_Domain_Analysis.html)).

The shell loop has an important delay: the agent proposes a full command, serialization and parsing occur, a process may or may not launch, an error is rendered, and only then can the model update. Natural-language error text can also omit the failed stage. A large “gain” correction—rewriting the whole command, switching shells, changing escaping, and adding wrappers at once—makes attribution harder on the next sample. This is a qualitative stability analogy only. There is no identified linear transfer function, and the model's context update is not a fixed controller.

## 2. Concrete translation: the interface-level control loop

The proposed correspondence is:

| Control-system concept | Tool-system counterpart | Required interface signal or action |
|---|---|---|
| Setpoint `r` | Semantic action requested by the agent | Stable `action_id` plus declared intent such as `run executable X with arguments A` |
| Controller output `u_req` | Raw tool payload produced by the model | Exact submitted payload and declared shell dialect |
| Actuator realization `u_act` | Parsed command / launched process input | Parse stage, executable, redacted `argv`, stdin mode, and whether launch occurred |
| Plant output `y` | Exit status, stdout/stderr, filesystem-visible result | Structured outcome envelope plus ordinary streams |
| Saturation | Parser rejection, policy rejection, length limit, or schema refusal before intended action | Stable error class, `actuation_applied=false`, stage, span, and limit |
| Windup state | Repeated same-semantic-action attempts that add quoting/wrapper complexity without actuation | Per-action retry count, normalized error fingerprint, recovery mode |
| Back-calculation error `u_act-u_req` | Difference between requested and realized command | Safe token/argument diff and transformation trace |
| Conditional integration | Refuse another same-mode retry while it pushes into the same rejection | Retry latch with an explicit bypass route |
| Dead-band/hysteresis | Hold the chosen recovery route until a meaningful state transition | Exit recovery only after successful launch or a different classified error |
| Observer | Derive actionable failure state from requested payload plus realization telemetry | Small deterministic classifier, not an LLM critic |

The interface must distinguish three events that are commonly collapsed into “command failed”:

1. **Not actuated:** schema or parser rejected the request; no target process launched.
2. **Actuated differently:** a process launched, but realized `argv` differs from the declared semantic arguments.
3. **Actuated as requested:** the intended process and arguments launched; failure belongs to the target program or environment.

This distinction catches errors a plain exit code cannot: quote consumption in a wrapper, wrong shell selection, accidental field splitting, unintended expansion, and false retries against a command that never launched. It also prevents a dangerous inference: exit code `2` is not universally a syntax error, because meanings differ by program and stage.

## 3. Proposals

Every proposal below rides the existing tool/hook/MCP bus and avoids a second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, and guardrail framework. The anti-overfit gate therefore passes at the architectural level. ### Proposal A — UNVERIFIED: typed process actuator with realization receipt

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a bus-local tool adapter whose primary interface is structured data, not a shell program string:

```json
{
  "action_id": "stable-within-task",
  "executable": "git",
  "argv": ["show", "origin/main:path with spaces/file.md"],
  "stdin": {"kind": "none"},
  "cwd": "...",
  "env_delta": {},
  "timeout_ms": 30000
}
```

Return a realization receipt alongside stdout/stderr:

```json
{
  "stage": "process_exit",
  "actuation_applied": true,
  "resolved_executable": "...",
  "argv_count": 2,
  "argv_digest": "...",
  "exit_code": 0,
  "error_class": null,
  "recovery": null
}
```

For privacy and secret safety, the receipt need not echo full arguments. It can return argument count, lengths, types, a keyed digest, and selectively reveal non-sensitive tokens. When a mismatch is detected before launch, it can emit token spans without copying values.

Raw Bash and PowerShell remain escape hatches for pipelines, redirection, compound statements, and shell built-ins. The adapter is the default for single-process calls. This division follows the actual language boundary: POSIX shells assign special meaning to numerous metacharacters and apply multiple expansion phases ([POSIX Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)); avoiding that language when no shell feature is requested removes an entire actuator nonlinearity.

It is **very likely (80-90%)**, because `argv[]` does not require the model to encode argument boundaries through shell quoting and because the official shell specifications identify quoting as the mechanism that controls those boundaries, that this adapter would eliminate unmatched-shell-quote failures for eligible single-process calls. This is **UNVERIFIED; settle it by classifying and replaying the 1,631 failures, first determining which commands require shell grammar, then comparing eligible cases through raw-string and typed-argv paths**.

The `<~200 lines` estimate is **likely (55-80%)**, based on the narrow adapter and receipt described above, but is **UNVERIFIED; settle it with a spike against the actual tool SDK and count non-generated source lines including redaction and Windows process-launch handling**. If correct Windows `CreateProcess` quoting, secret redaction, and lifecycle integration exceed that bound, reclassify this exact proposal as BUILD-LARGE or split it into platform-native adapters; do not retain a false BUILD-SMALL label.

What it catches that a raw shell result misses:

- whether the intended executable launched at all;
- whether argument boundaries survived serialization;
- whether a wrapper changed the requested arguments;
- native-process quoting errors that occur after PowerShell has parsed its own string;
- command-length or argument-count saturation before launch; and
- mismatches between declared semantic intent and realized actuation.

### Proposal B — UNVERIFIED: anti-windup error envelope and conditional retry clamp

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a deterministic pre/post-tool hook keyed by `(session_id, action_id, tool_family, normalized_error_class)`. It maintains only ephemeral retry state:

```text
NORMAL
  parse/quote rejection, no actuation -> SATURATED_ONCE

SATURATED_ONCE
  materially different payload or typed route -> allow
  same action + same raw mode + same error direction -> clamp and prescribe bypass
  successful launch -> NORMAL

RECOVERY_TYPED
  successful launch -> NORMAL
  different process-level error -> NORMAL with new classification
  request to return to raw shell before launch -> hold recovery mode
```

“Same error direction” must be strict and mechanical: for example, unmatched delimiter at the same parser stage plus `actuation_applied=false`. The hook must not infer semantic equivalence from embeddings or a learned critic. A stable `action_id` is preferable; when missing, a conservative digest of executable intent and target paths can be advisory only.

On the first failure, the error envelope reports:

- `stage`: schema, wrapper serialization, shell parse, expansion, native launch, or process exit;
- `dialect` and version;
- `actuation_applied`;
- `error_class`, e.g. `UNTERMINATED_SINGLE_QUOTE`;
- source span and expected closing token when the parser exposes them;
- safe alternate call, preferably a structured-tool payload with values separated from syntax; and
- `retry_policy`: `raw_retry_remaining=1`, `typed_fallback_available=true`.

On a repeated same-direction failure, conditional integration clamps raw retry and returns the bypass payload. This is the direct anti-windup borrow: while the actuator is rejecting input and the correction still pushes into the same rejected channel, do not accumulate another raw command. Back-calculation appears as the realization diff: tell the controller what was applied (`nothing`, or a specific realized `argv`) versus what it requested.

It is **likely (55-80%)**, based on anti-windup's exact saturation logic but reduced by uncertainty about semantic-action identification and agent adaptation, that a one-retry clamp would reduce quote-error loops without materially reducing completion. This is **UNVERIFIED; settle it with the paired replay plus a false-clamp review on successful second-attempt repairs**.

The hook-state and interception premise is **UNVERIFIED; settle it by a capability spike that emits a known-present synthetic quote error, proves the post-tool hook observes it, proves a pre-tool hook can identify the next call, and proves session-local state survives between the two events**. This requires two mechanically independent signals before concluding the hook is absent or broken: hook telemetry containing the synthetic marker and the next tool's externally visible allow/deny behavior. Re-running the same log query is not a second signal.

What it catches that current single-call error prose misses:

- a loop of parser-rejected commands in which no process ever launches;
- increasing payload length or wrapper depth while realized actuation remains zero;
- repeated switching among quote spellings without a change in parser stage;
- downstream saturation invisible to a pre-parser check; and
- recovery suggestions that are not invocable through a distinct actuator.

### Proposal C — UNVERIFIED: hysteretic recovery mode, not a generic “three strikes” breaker

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Configure tool guidance and structured error metadata so that, after the retry controller enters typed recovery for an action, it stays there until one of two meaningful transitions occurs: the target process launches, or the classified failure moves to a different stage. Do not exit recovery merely because the model emits a cosmetically different raw string.

This is dead-band/hysteresis translated correctly: the threshold for entering recovery differs from the threshold for leaving it, and state history matters. It avoids chatter such as Bash → PowerShell → Bash while the semantic action and non-actuation result remain unchanged.

It is **likely (55-80%)**, based on Rockwell's documented use of dead-band/zero-crossing behavior to reduce unnecessary output changes and on the exact repeated-mode-switching structure targeted here, that hysteresis would reduce oscillatory repair sequences. This is **UNVERIFIED; settle it by measuring mode switches per action and task completion in paired replays**.

The CONFIG classification is **roughly even (45-55%)**, because the policy can be expressed in settings/JSON only if Proposal B supplies a stateful enforcement primitive; otherwise configuration text alone is advisory. This is **UNVERIFIED; settle it by inspecting the eventual Proposal B interface schema**. If no enforcement field exists, merge C into B rather than pretending prose configuration is a controller.

### Proposal D — UNVERIFIED: shell-native syntax observer for irreducibly shell-shaped actions

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For commands that genuinely require pipelines, redirection, compound statements, or built-ins, run a no-execution syntax observer in the declared dialect before execution where the shell supports it. Return the parser's exact stage and span, then execute the exact validated bytes rather than reconstructing the command from a normalized representation. The control role is an observer: improve state estimation without pretending the syntax check has actuated the process.

The observer must report its limits inline. Syntax validity does not establish expansion safety, command existence, permissions, native argument correctness, or runtime success. In particular, PowerShell-to-native argument transformation is a later boundary documented separately by Microsoft ([PowerShell quoting rules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-7.5)).

It is **very likely (80-90%)**, because unmatched quotes are parser-level defects and a matching-dialect parser is the authoritative detector, that syntax preflight would catch unmatched delimiters before process execution for supported dialects. This is **UNVERIFIED; settle it by replaying known unmatched-quote fingerprints through the exact installed shell versions and checking parser rejection plus zero target-process launches**.

It is only **likely (55-80%)** that the full cross-shell observer stays under 200 lines, because dialect invocation, byte preservation, diagnostics normalization, and Windows behavior add complexity. This is **UNVERIFIED; settle it with separate Bash and PowerShell spikes and count all adapter code**.

## 4. Why this analogy could fail

### Disanalogy 1: there is no literal integral state in the model

A PID integrator sums numeric error over time. An LLM does not expose a scalar integral term; its next action is generated from a context-conditioned policy. Calling every retry “windup” would be metaphor laundering.

**Resolution:** build the accumulating state explicitly and minimally: same-action retry count, error fingerprint, actuation flag, and recovery mode. The anti-windup claim then applies to this harness-owned retry controller, not to hidden neural dynamics. This structural repair is why the borrow survives.

### Disanalogy 2: saturation boundaries are not all known

Classical anti-windup works best when limits and actuator structure are known. MathWorks says its built-in scheme requires known saturation limits and a specific actuator feed arrangement; cascaded dynamics require external tracking feedback ([anti-windup example](https://www.mathworks.com/help/simulink/slref/anti-windup-control-using-a-pid-controller.html)). Tool chains contain undocumented wrappers, version differences, policy gates, and remote executors.

**Resolution:** never infer successful actuation from a submitted string. Require a receipt from the nearest realizable boundary and classify unknown stages as `REALIZATION_UNKNOWN`, not as success or parser failure. The approach becomes less powerful when the receipt cannot be obtained, but it remains honest.

### Disanalogy 3: observability is not equivalent to verbose telemetry

More logs do not guarantee that relevant internal states are distinguishable, and observability of a nonlinear stochastic agent cannot be established by listing fields.

**Resolution:** use discriminating tests rather than a formal claim. Construct paired commands that differ at exactly one stage—wrapper quote consumption versus shell parse failure, for example—and require the envelope to classify them differently. If it cannot, that boundary remains unobservable to the recovery controller.

### Disanalogy 4: a dead-band can hide real failure

Suppressing “small” errors is unsafe in software because a one-character difference can change command meaning. A numeric tolerance on command strings would be indefensible.

**Resolution:** apply hysteresis to **mode transitions**, never to command semantics or error severity. No error is suppressed. The same complete error remains visible; only the permitted recovery actuator is held until a meaningful transition.

### Disanalogy 5: delay-margin language does not create a stability proof

The agent, parser, operating system, and external program do not form a known linear time-invariant plant. There is no validated frequency response or phase margin.

**Resolution:** borrow only conservative design consequences: minimize feedback delay, change one actuator dimension at a time, emit stage-specific feedback, cap same-mode retries, and measure oscillatory sequences. Do not claim Lyapunov, Nyquist, gain-margin, or delay-margin guarantees.

### Disanalogy 6: blocking a retry can block a legitimate repair

Many unmatched quotes are fixed correctly on the next attempt. An immediate hard breaker could reduce task completion even as it lowers the error count.

**Resolution:** permit one raw correction by default, clamp only a second same-direction/non-actuated attempt, and always provide an invocable bypass. Tune against task completion and false-clamp rate, not error count alone. The exact threshold is **UNVERIFIED; the paired replay and live canary described below settle it**.

## 5. Evaluation plan that would settle the UNVERIFIED premises

### 5.1 Detector validation before any absence/broken claim

The evaluation must honor the two-signal rule.

1. Create known-present fixtures for Bash unmatched single quote, Bash unmatched double quote, PowerShell unterminated string, successful quoted argument with spaces, successful pipeline, and native program rejection after a successful launch.
2. Prove the detector finds each known-present fixture before using it to report an absence.
3. For “no target process launched,” require two mechanically independent signals: the tool receipt says `actuation_applied=false`, and a target-side marker (unique process-side file/event/nonce acknowledgement in an isolated test) is absent while the same detector proves it sees the marker in the success control.
4. For “hook did not observe/intercept,” require both hook telemetry with a unique nonce and externally visible next-call behavior. A second read of the same telemetry store is not independent.

### 5.2 Offline paired replay

From the measured 1,631 unmatched-quote fingerprints, form semantic-action groups without using the evaluation outcome. Stratify by shell, quote type, nesting depth, presence of pipeline/redirection, native executable, wrapper count, and whether a later retry succeeded. Keep a held-out group split so near-duplicate commands do not cross train/tune and test partitions.

Compare:

- baseline raw shell and current error;
- structured realization receipt only;
- receipt plus one-retry anti-windup clamp;
- receipt, clamp, and hysteretic typed fallback;
- syntax observer for irreducibly shell-shaped calls.

Primary metrics:

- semantic task success within two and within five tool calls;
- unmatched-quote failures per semantic action;
- fraction of actions with zero realized actuation across repeated attempts;
- false clamps: a blocked raw retry that would have succeeded and was safer/faster than fallback;
- time and tokens to first successful actuation;
- mode switches per action;
- realized-argument mismatch rate; and
- unsafe or meaning-changing fallback rate, reviewed separately from syntax success.

The key acceptance condition must be task-level: lower quoting failure is insufficient if completion falls. A reasonable initial decision rule is **UNVERIFIED**: ship only if the held-out set shows a reduction in quote-error attempts with a non-inferior semantic completion rate and no increase in unsafe realization. The precise non-inferiority margin must be chosen from baseline variance before examining treatment outcomes.

### 5.3 Live canary

After offline success, canary the receipt first in observe-only mode, then enable typed suggestions, then enforce the second same-direction retry clamp for a small fraction of sessions. Roll back enforcement automatically on a predeclared completion or false-clamp regression. It is **likely (55-80%)**, based on distribution shift between recorded and live agent behavior, that live observe-only data will reveal error states absent from the replay taxonomy. This is **UNVERIFIED; the canary's `REALIZATION_UNKNOWN` and unclassified-stage rates settle it**.

### 5.4 Ablations

Run ablations to establish which borrowed mechanism contributes value:

- remove realized-actuation receipt but retain better prose;
- retain receipt but remove clamp;
- retain clamp but remove typed bypass;
- retain fallback but remove hysteresis;
- use syntax checking without post-parse launch receipt;
- use an immediate clamp versus one permitted same-mode repair.

If better prose alone matches the stateful controller, prefer prose/configuration because it is simpler. If typed invocation alone removes eligible failures, omit the retry controller for that class. This is the anti-overfit gate applied experimentally rather than rhetorically.

## 6. Recommended sequence

1. **Receipt schema and known-present fixtures first.** Without realized-actuation feedback, downstream saturation remains hidden and all later classification is suspect.
2. **Typed single-process path second.** It supplies a genuinely different control input instead of another instruction about quoting.
3. **Observe-only retry state third.** Measure same-action repetition and false-equivalence before enforcement.
4. **One-retry conditional clamp fourth.** Enable only for exact, non-actuated, same-direction parser failures with an available bypass.
5. **Hysteresis last.** Hold recovery mode only after data show chattering between modes.

This order is **very likely (80-90%)**, based on the dependency graph—observer signals are needed by the clamp, and a distinct fallback actuator is needed before clamping can preserve controllability—to minimize implementation ambiguity. The operational benefit is **UNVERIFIED; the staged ablation sequence above settles whether later stages add measurable value**.

## 7. What not to build

- Do not build a general control-theory daemon or model the LLM with a transfer function.
- Do not add a second orchestration runtime, durable workflow engine, learned critic, vector memory, knowledge graph, guardrail framework, or observability SaaS.
- Do not compute string edit distance and call it a dead-band.
- Do not hide repeated errors; expose them and constrain only the recovery mode.
- Do not auto-rewrite a command and then execute bytes different from those validated.
- Do not treat parser success as process success.
- Do not call the system “observable,” “controllable,” or “stable” in the formal control-theory sense without an identified model and proof.
- Do not optimize the measured 1,631 count in isolation; optimize semantic completion, safe realization, and recovery cost on held-out tasks.

These exclusions keep the borrow on the existing bus and prevent an analogy-driven architecture from outrunning its evidence.

## 8. Gaps and bounded claims

- This unit intentionally did not inspect the local harness. Therefore current tool schemas, hook mutation capability, session-state support, shell versions, and whether a typed execution path already exists are not conclusions here.
- The 1,631 figure is accepted from the pinned measured ground truth. This unit did not independently inspect the corpus and does not claim how many fingerprints form retry loops.
- No claim is made that current error messages omit all realization data. The proposal states the information required by the translated mechanism; local grounding units must compare it with what exists.
- No claim is made that Bash and PowerShell expose equally precise parser spans or no-execution modes. Proposal D is **UNVERIFIED; the exact installed-version fixture experiment settles support and diagnostic fidelity per dialect**.
- Secret-safe realized-argument telemetry may require more than hashing because low-entropy values can be guessed. A keyed digest plus aggressive selective disclosure is a design direction, not a completed security design. It is **likely (55-80%)**, based on standard low-entropy guessing risk, that plain unsalted argument hashes would leak information; a security review with a dictionary attack against representative redacted values settles the implementation choice.
- Formal feedback-stability analysis is out of scope and structurally unsupported. The recommended state machine is finite and testable, but that does not prove task-level convergence.

## Final judgment

Control theory contributes one high-value tool-design principle: **close the loop around what the actuator actually did, not what the controller asked it to do**.
