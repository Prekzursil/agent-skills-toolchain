# F018 — Frontier research: cost/latency engineering and model routing

**Unit:** F018  
**Research date:** 2026-07-19 UTC  
**Scope:** cost/latency engineering and model routing for the owner's Claude Code + Codex harness  
**Operating constraint:** subject trees were read-only. The only write is this artifact.  
**Evidence standard:** primary papers, official product documentation, real repositories, and the supplied local evidence. Audit findings are treated as claims unless independently supported.

## Executive verdict

The frontier does **not** justify putting a learned “AI router” or a new routing proxy in front of this harness. Published routing work establishes that query-dependent model selection is possible and can generate attractive cost/quality frontiers on particular benchmarks. It does not establish that a trained router will preserve outcome quality on this owner's long-horizon, tool-using, rapidly changing coding workload. The most recent large unified evaluation is actively cautionary: it finds strong model complementarity, but several sophisticated—including commercial—routers do not reliably beat a simple best-single-model baseline, and larger model pools show diminishing returns ([LLMRouterBench paper](https://arxiv.org/abs/2601.07206), [ACL 2026 paper PDF](https://aclanthology.org/2026.findings-acl.1881.pdf)).

This harness nevertheless has a large and unusually credible optimization opportunity. Its current defaults pin Claude to `opus[1m]` at `xhigh` effort (`/local_disk0/codexwork/bundle/claude/settings.json:77,685`) and Codex to `gpt-5.6-sol`, `ultra` reasoning, and `priority` service (`/local_disk0/codexwork/bundle/codex/config.toml:3-5,17-19`). Codex recursive agent depth is set to 8 (`config.toml:77-80`), even though current official guidance says the default depth is 1 and warns that deeper recursion increases tokens, latency, and local resource use ([Codex manual, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)). Those are blanket maximum-like choices, not task-conditioned allocation.

The immediate design should therefore be the sequence below. **Confidence: very likely (80-90%)**, because it starts with directly observed blanket maximum-like settings and deterministic waste, uses native controls documented by both providers, and postpones the learned-router component that the unified benchmark does not support. The remaining uncertainty is the local cost/quality curve; the §4.9 paired shadow benchmark would settle it.

1. remove deterministic waste before “smart” routing;
2. meter end-to-end task economics and latency on the existing receipt/benchmark bus;
3. use native, explicit per-role model and effort controls;
4. escalate on **observable task evidence**, not a model's unsupported self-confidence;
5. preserve stable prompt prefixes and use provider-native caching;
6. send only genuinely delay-tolerant, independent offline work to native batch lanes;
7. test all routing changes in shadow against fixed, stratified local tasks before promotion.

This is an evolution of the existing native buses, not a replacement runtime. Full replacement was considered. It loses the anti-overfit gate because it adds a second orchestration/routing service before this harness even records task-level token cost or can demonstrate that a two-tier native policy is inadequate.

# 1. Established

## 1.1 The objective is constrained outcome cost, not cheapest tokens

For an agent harness, the useful objective is something like:

`minimize E[dollar cost + latency penalty + retry cost + human-intervention cost]`

subject to task success, safety, and reliability constraints. Token price alone is not the objective. A cheaper call that triggers more retries, loses a lens, or creates human repair work can be more expensive end-to-end. This is not theoretical in the supplied evidence: the known-defects file records a safety workaround that moved work to a tool path with a 13.6% failure rate (`INPUT-known-harness-defects.md:100-107`), while audit C05 reports retained workflow traces in which schema validation retries consumed 101,378 tokens in one failed reviewer and 161,289 tokens in another workflow with 68 validation errors (`/local_disk0/codexwork/bundle/inputs/audit-findings/C05.md:3-15`). C05 is an audit claim because those source transcripts were not bundled here, but it identifies the exact experiment and records needed for replay.

Consequently, routing must be scored at the terminal task/receipt boundary, not at an individual request. τ-bench introduced `pass^k` specifically to measure repeated reliability rather than lucky capability, and grades final environment state rather than prose ([τ-bench](https://arxiv.org/abs/2406.12045)). ToolSandbox similarly uses required milestones and prohibited minefields across multiple valid trajectories ([ToolSandbox](https://arxiv.org/abs/2408.04682)). These are evaluation precedents, not proof that either benchmark transfers to this harness.

## 1.2 Native model and effort routing already exists

Claude Code custom subagents can select `haiku`, `sonnet`, `opus`, a full model ID, or `inherit`; the built-in read-only Explore agent already uses Haiku for fast, low-latency exploration. Subagents can also set effort and a maximum turn count ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents), [Agent SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents)). Claude’s official model configuration says lower effort is faster and cheaper, `medium` is the cost-sensitive trade-off, `xhigh` is a high-quality default for supported Opus, and `max` can show diminishing returns and should be tested before broad use ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)).

Codex custom agents likewise accept `model` and `model_reasoning_effort`. Current official guidance says unpinned agents may balance intelligence, speed, and price; it positions `gpt-5.6-terra` for fast/lower-cost scans and supporting work and higher-effort `gpt-5.6` for demanding reasoning. It also explicitly says higher reasoning effort increases response time and token usage ([Codex manual, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)).

This matters architecturally: the harness does not need a routing daemon to assign a cheaper model to exploration, summarization, log classification, or document triage. The routing control plane is native on both primary providers.

## 1.3 Learned routing is feasible, but its established scope is narrow

FrugalGPT demonstrated learned cascades over API models and reported benchmark-specific cost reductions, including up to 98% in one reported comparison ([FrugalGPT](https://arxiv.org/abs/2305.05176)). Hybrid LLM reported up to 40% fewer calls to the large model without an observed quality drop in its evaluated tasks ([Hybrid LLM](https://arxiv.org/abs/2404.14618)). RouteLLM, published at ICLR 2025, trained two-model routers on preference data and reported more than 2× cost reduction in some benchmark settings without reducing its selected quality measure ([RouteLLM paper](https://proceedings.iclr.cc/paper_files/paper/2025/hash/5503a7c69d48a2f86fc00b3dc09de686-Abstract-Conference.html)). Its real repository exposes serving, evaluation, threshold calibration, and four trained router types ([RouteLLM repository](https://github.com/lm-sys/RouteLLM)).

What is established is **feasibility on evaluated distributions**. These papers do not establish automatic transfer to evolving coding agents, multi-turn tool trajectories, rare safety failures, or this owner's model pair. RouteLLM’s shipped routers were trained on `gpt-4-1106-preview` and `mixtral-8x7b-instruct-v0.1`; its repository says thresholds should be calibrated for the queries and model pair in use ([RouteLLM repository](https://github.com/lm-sys/RouteLLM)).

The 2026 LLMRouterBench result materially narrows the claim. Across more than 400,000 instances, 21 datasets, and 33 models, it confirms complementarity but finds many routing methods similar under unified evaluation, several sophisticated/commercial routers unable to reliably beat a best-single-model baseline, and diminishing returns from larger ensembles ([LLMRouterBench](https://arxiv.org/abs/2601.07206)). Thus, “routing can work” is established; “a learned router is generally better than a simple baseline” is not.

## 1.4 Prompt/prefix caching is deployed and measurable

Provider-native prefix caching is real infrastructure, not a proposed research mechanism:

- OpenAI automatically caches eligible repeated prompt prefixes and exposes cached-token counts in response usage. The original product documentation explains that shared prefixes improve latency and reduce cached-input price, and that static content must come before dynamic content to maximize reuse ([OpenAI prompt caching](https://openai.com/index/api-prompt-caching/)).
- Anthropic supports automatic and explicit prompt caching, 5-minute and 1-hour TTLs, usage fields for cache read/write tokens, and explicit caching of tool-definition prefixes. It documents that changing server-tool availability can invalidate system/message caches and that tool search can preserve prefixes by deferring tool loading ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)).
- Gemini 2.5-and-newer models have automatic implicit caching, expose cached tokens, and recommend placing common content first; explicit caching is available on its legacy Generate Content path for recurring large contexts ([Gemini context caching](https://ai.google.dev/gemini-api/docs/caching), [explicit caching](https://ai.google.dev/gemini-api/docs/generate-content/caching)).
- For self-hosted serving, vLLM Automatic Prefix Caching reuses KV blocks for shared prefixes. Its own documentation is precise about the boundary: it speeds prefill/TTFT, not decoding, and provides little benefit when outputs dominate or prefixes do not repeat ([vLLM APC](https://docs.vllm.ai/usage/automatic_prefix_caching/)).

Caching therefore belongs in the design, but cache **hit rate and amortized charge** must be measured. A cache write can cost more than ordinary input, an entry can expire before reuse, and a reordered/dynamic prefix can miss. “Caching enabled” is not equivalent to “caching saved money.”

## 1.5 Async batch pricing is deployed, but it exchanges latency for cost

OpenAI’s Batch API processes asynchronous requests in a 24-hour completion window at a 50% discount ([OpenAI Batch API](https://platform.openai.com/docs/api-reference/batch/object?api-mode=responses)). Anthropic’s Message Batches API charges 50% of standard input/output pricing and says most batches finish in less than one hour, while retaining a 24-hour processing window ([Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)). Gemini advertises 50% Batch API pricing and separate batch rate limits ([Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing), [Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)).

This is established for offline evals, bulk classification, corpus distillation, or independent research lenses whose consumer can wait. It is not a latency optimization for an interactive critical path. It may improve throughput and cost while making wall-clock completion slower.

## 1.6 Output length, reasoning effort, and unnecessary serial work are first-order controls

Autoregressive generation requires serial token production; speculative decoding’s original ICML paper formalizes this and shows exact-distribution acceleration by drafting and verifying multiple tokens in parallel, with 2–3× acceleration in its T5-XXL experiments ([Leviathan, Kalman & Matias 2023](https://proceedings.mlr.press/v202/leviathan23a)). For hosted APIs the harness generally cannot choose the server’s decoding implementation, but it can reduce requested output, avoid repeated prose, lower reasoning effort on simple work, and parallelize genuinely independent calls.

Streaming improves time-to-first-visible-result, not total compute or total token cost. Prefix caching reduces prefill, not long-output decode ([vLLM APC](https://docs.vllm.ai/usage/automatic_prefix_caching/)). Codex’s current official Fast mode makes the explicit trade: roughly 1.5× model speed for higher credit/API consumption, and API Priority has its own premium ([Codex Speed](https://learn.chatgpt.com/docs/agent-configuration/speed.md)). This establishes that latency tiers buy speed; it does not establish that paying for Priority on every harness task is economically rational.

## 1.7 Tail latency and fan-out must be treated as critical-path economics

If a synthesis waits for every independent branch, completion time is governed by the slowest branch plus orchestration overhead. More fan-out can reduce elapsed time when work is truly independent, but it raises token use and the probability that at least one branch is slow or fails. Codex documentation explicitly warns that subagents consume more tokens than comparable single-agent work and that recursive delegation increases token usage, latency, and local resource consumption ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)).

The local configuration enables fan-out and sets depth 8 (`/local_disk0/codexwork/bundle/codex/config.toml:77-106`). The bundled A07 audit claims that a session-start plugin had p50 50.970 s and max 82.729 s, local Stop p50 10.422 s and max 22.759 s, and an estimated ordinary two-hook warm floor near 422 ms (`/local_disk0/codexwork/bundle/inputs/audit-findings/A07.md:1-10,39-47`). These measurements were not reproduced because their Windows transcripts are absent. If replayed, they would show why end-to-end latency engineering must include local hooks, process startup, tool retries, and fan-in—not just model TTFT.

# 2. Promising but unproven

## 2.1 Outcome-gated two-stage escalation

**Confidence: likely (55-80%)**, because cascade/routing papers show model complementarity and cost-quality trade-offs on several distributions ([FrugalGPT](https://arxiv.org/abs/2305.05176), [RouteLLM](https://proceedings.iclr.cc/paper_files/paper/2025/hash/5503a7c69d48a2f86fc00b3dc09de686-Abstract-Conference.html)), and both Claude and Codex expose native per-agent models. The evidence is reduced by LLMRouterBench’s finding that learned routers often fail to beat a simple baseline ([LLMRouterBench](https://arxiv.org/abs/2601.07206)). A local stratified shadow A/B—cheap-first with deterministic verification/escalation versus always-frontier—would settle it.

The promising form is not “ask the small model whether it is confident.” It is:

- cheap/fast model handles a bounded, reversible unit;
- machine-checkable or human-grounded evidence determines acceptance;
- failed tests, schema failure, missing citations, forbidden side effects, changed assumptions, or explicit uncertainty escalate to the stronger lane;
- safety-critical and high-blast-radius tasks bypass the cheap lane.

This makes escalation depend on observable outcomes. It also prevents double-paying on tasks where verification is impossible: those route strong initially.

## 2.2 Deterministic role routing before semantic routing

**Confidence: very likely (80-90%)**, because official Claude and Codex products already assign/encourage fast models for exploration and supporting scans, while preserving stronger models for demanding work ([Claude subagents](https://code.claude.com/docs/en/sub-agents), [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)). The uncertainty is local: this owner's custom roles, hidden task mix, and quality tolerance have not been benchmarked. A task-family A/B with fixed models, budgets, terminal oracles, and owner review would settle it.

Role routing is deliberately coarse: explorer/log triage/document slicer/format normalizer on the efficient tier; implementer/reviewer/security/root synthesizer on stronger tiers unless a local benchmark promotes a narrower role. Coarse policies are auditable and survive model churn better than an opaque query classifier.

## 2.3 Cache-aware prompt assembly for agent loops

**Confidence: very likely (80-90%)**, because all three major API providers expose cache usage and document stable-prefix rules, and this harness repeatedly sends large instructions/tool schemas. The precise local savings are **UNVERIFIED; experiment: record cache-read, cache-write, uncached-input tokens, TTL, and TTFT per turn for one week, then replay a fixed task set with stable instructions/tools first and dynamic state last**. Provider docs establish mechanics, not this workload’s hit rate ([OpenAI caching](https://openai.com/index/api-prompt-caching/), [Anthropic caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Gemini caching](https://ai.google.dev/gemini-api/docs/caching)).

The 2026 paper “Don't Break the Cache” is promising but post-cutoff research rather than established production evidence. It reports that selective cache-breakpoint control was more consistent than naïvely caching full agent contexts and that naïve full-context caching could increase latency ([paper](https://arxiv.org/abs/2601.06007)). Its exact gains are **UNVERIFIED for this harness; experiment: the same paired replay above with full-context, stable-prefix-only, and provider-default variants**.

## 2.4 Budget-aware reasoning effort

**Confidence: very likely (80-90%)**, because both current products explicitly expose effort as a latency/token trade-off and recommend lower levels for simpler work ([Claude model configuration](https://code.claude.com/docs/en/model-config), [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)). The exact thresholds are **UNVERIFIED; experiment: run low/medium/high/xhigh on a versioned local set stratified by trivial edit, exploration, coupled edit, debugging, review, and security, with pass^3, tokens, elapsed time, and interventions**.

The especially plausible win is removing blanket `ultra`/`xhigh` from small subagents and leaving high effort available to the root, reviewers, security work, and escalation paths. There is no evidence supporting “ultra everywhere” as the cost/quality optimum.

## 2.5 Latency-aware provider failover based on health, not quality prediction

**Confidence: likely (55-80%)**, because the corpus measured 135 “not connected” errors from the dead Tavily MCP and 232 WebFetch `ECONNREFUSED` errors in the pinned ground truth, and retry storms directly waste wall time. The uncertainty is whether native provider fallback and current hook payloads expose sufficiently fresh health/usage signals. **UNVERIFIED; experiment: replay known failure fingerprints through a shadow circuit breaker, measuring avoided retries, false bypasses, and recovery after a half-open probe.**

This is routing, but it is deterministic availability routing: disable a known-dead destination; open a circuit after repeated transport-class failures; use a known healthy equivalent; probe recovery. It does not predict model quality.

## 2.6 Delayed offline fan-out through batch APIs

**Confidence: likely (55-80%)**, because provider-native batch APIs reliably advertise a 50% token discount and separate batch capacity, and this owner runs large audit/research fan-outs ([OpenAI Batch](https://platform.openai.com/docs/api-reference/batch/object?api-mode=responses), [Anthropic Batch](https://platform.claude.com/docs/en/build-with-claude/batch-processing), [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)). Local applicability is **UNVERIFIED; experiment: inventory workflows whose declared deadline is at least one hour and whose units have no interactive dependency, then shadow one 20-item research/eval job through synchronous and batch lanes, comparing completed units, makespan, cost, retries, privacy/retention eligibility, and operator wait**.

This should never silently move an interactive task to a 24-hour SLA. Deadline and retention policy are part of the routing key.

## 2.7 Conformal or uncertainty-bounded routing

**Confidence: unlikely (20-45%)** for near-term harness adoption, despite interesting research. A 2026 ACL student-research paper reports conformal bounds for routing between Mixtral and GPT-4 on GSM8K/MMLU ([Conformal LLM Routing](https://aclanthology.org/2026.acl-srw.70/)). That is promising evidence for calibrated abstention, but it is a small task/model regime and does not cover long-horizon agent trajectories or shifting hosted model snapshots. **UNVERIFIED; experiment: only after local task labels exist, test whether conformal coverage remains calibrated under time-split model/version drift and rare safety-critical cases.** Without that data, this is research, not a harness component.

## 2.8 Speculative decoding and semantic KV-cache systems

**Confidence: likely (55-80%)** that these continue improving self-hosted inference latency, based on exact-distribution speculative decoding and deployed vLLM prefix caching ([speculative decoding](https://proceedings.mlr.press/v202/leviathan23a), [vLLM APC](https://docs.vllm.ai/usage/automatic_prefix_caching/)). **Confidence: very unlikely (5-20%)** that building them in this harness is worthwhile, because hosted Claude/Codex clients do not expose server decoding internals, the owner has rejected a second inference runtime, and provider-native caching already exists. An experiment would require a representative self-hosted model to match frontier task quality after including GPU, operations, cold-start, and maintenance cost; no such evidence is present.

# 3. Hype, and the tell that gives it away

## 3.1 “Up to 98% cost reduction with no quality loss” as a portable promise

The underlying FrugalGPT result is a legitimate paper result ([FrugalGPT](https://arxiv.org/abs/2305.05176)). The hype begins when its maximum benchmark result is presented as an expected production saving for a different model pool and agent workload.

**Tell:** “up to” is paired with no workload distribution, model/version pair, quality constraint, retry cost, or confidence interval. The claimed saving is per call, while task completion and human repair are unreported.

## 3.2 A universal “best model” router

Model complementarity is real, but the newest unified benchmark finds several recent routers cannot reliably beat best-single-model and that pool expansion has diminishing returns ([LLMRouterBench](https://arxiv.org/abs/2601.07206)).

**Tell:** the product advertises hundreds of models, but publishes no always-cheapest, always-strongest, best-single-model, random, and oracle baselines on the customer's task mix. A large catalog is marketed as intelligence even though model curation can matter more than router complexity.

## 3.3 “Self-confidence” as an escalation oracle

An LLM saying it is confident is not a machine-verifiable success signal. No primary evidence found here establishes that uncalibrated self-confidence is reliable enough for safety- or correctness-critical coding routing.

**Tell:** there is no calibration curve, selective-risk curve, abstention rate, or time-split evaluation after model updates. The router accepts “looks good” without tests, receipts, citation checks, or final-state validation.

## 3.4 LLM-as-judge savings that omit judge cost and shared bias

Learned routers often rely on preference or judge labels. Those can be useful for research, but a judge adds tokens/latency and can share blind spots with the candidates.

**Tell:** quality plots omit judge call cost, judge-model version, agreement with human/task oracles, and false-accept cost. The same model family grades itself, and disagreements are not adjudicated.

## 3.5 “Zero latency” through streaming or parallelism

Streaming improves perceived latency, not total completion cost. Parallel fan-out shortens the critical path only for independent work and can increase token consumption, tail exposure, and merge conflict. Codex explicitly says subagent workflows consume more tokens ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)).

**Tell:** only TTFT or average branch latency is reported. End-to-end makespan, p95/p99, slowest-branch wait, cancellation waste, and time to verified artifact are absent.

## 3.6 “90% cache savings” without amortization

Anthropic legitimately reports cache-hit economics and documents cache-write premiums/TTLs ([Anthropic caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). A headline that multiplies all input by the cache-read discount is hype if the prompt changes, expires, or is never reused.

**Tell:** no cache-read/write token split, prefix hash/hit rate, reuse interval, TTL, invalidation reason, or amortized charge. Cache warming and storage are counted as free.

## 3.7 A routing control plane disguised as a lightweight library

RouteLLM is a real repository, but deploying its OpenAI-compatible server still creates another online hop, configuration, credentials, training/calibration lifecycle, and failure domain ([RouteLLM repository](https://github.com/lm-sys/RouteLLM)).

**Tell:** the architecture diagram labels the router “one line of code” while omitting the service process, embeddings/API dependency, model registry drift, threshold calibration, telemetry, rollback, and privacy boundary.

## 3.8 Benchmark leaderboards with no temporal holdout

Hosted models and prices change. A router fitted to model A/B outputs can become stale when either endpoint changes.

**Tell:** train/test examples are randomly split from the same period; model IDs are aliases rather than pinned snapshots; no time-split, replacement-model, or distribution-shift result exists. A static benchmark is presented as future-proofing.

## 3.9 More agents as automatic latency optimization

The local config’s depth 8 makes recursive fan-out possible (`/local_disk0/codexwork/bundle/codex/config.toml:77-80`). Current Codex guidance warns that deeper recursion raises token use, latency, and resource consumption ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)).

**Tell:** agent count is the independent variable and “coverage” the narrative outcome, but marginal unique findings per token, completion rate, overlap, coordination time, and slowest-worker latency are missing.

# 4. Specific things this harness should adopt

Every proposal below includes the required implementation tag and an explicit anti-overfit decision.

## 4.1 Adopt an end-to-end economics envelope before changing routing

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing benchmark/receipt output—not the hot-path production schema initially—with:

- task/run ID, task family, provider, model snapshot/alias, effort, service tier;
- input, output, reasoning, cache-read, and cache-write tokens where exposed;
- provider request count, retries, tool calls, subagent calls, and schema repair count;
- TTFT if exposed, model wall time, tool wall time, hook wall time, end-to-end makespan;
- terminal success oracle, `pass@1`, reliability `pass^k`, owner intervention, and failure class;
- computed dollar cost from a **versioned price table plus raw usage**, never price alone.

**Confidence: almost certain (90-99%)** that this is necessary, because the supplied corpus retains 4,000 session summaries with timestamps/sizes but no tokens, dollars, models, TTFT, or task outcomes, and D10 independently reports no model-in-loop cost A/B (`D10.md:80-86`). The remaining uncertainty is which host APIs expose all usage fields. **UNVERIFIED fields must be nullable; experiment: capture one harmless Claude root call, Claude subagent, Codex root call, and Codex subagent and enumerate their native usage/receipt payloads before fixing the schema.**

**Anti-overfit gate:** PASS. It rides the existing benchmark, hook, and receipt buses. It adds no SaaS, trained critic, vector store, or runtime. It grades deterministic outcomes where available and leaves missing usage explicit.

## 4.2 Replace blanket maximum settings with three native role lanes — UNVERIFIED until local A/B

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Define:

- **fast/read lane:** exploration, file inventory, log clustering, document slicing, formatting, and bounded extraction; efficient model, low/medium effort, read-only tools, finite turns;
- **standard/action lane:** normal scoped edits and tests; balanced frontier model/effort;
- **deep/critical lane:** ambiguous cross-repo work, root synthesis, security, architecture, destructive/high-blast-radius actions, and escalation; strongest model with high/xhigh/ultra only when justified.

Claude supports model and effort per subagent ([Claude subagents](https://code.claude.com/docs/en/sub-agents), [model config](https://code.claude.com/docs/en/model-config)); Codex supports the same in custom-agent config ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)). Current blanket defaults are directly visible at `claude/settings.json:77,685` and `codex/config.toml:3-5,17-19`.

**Confidence: very likely (80-90%)** that role routing will reduce tokens/latency without harming simple tasks, because it is the native product design and avoids an added router call. The recommendation is **UNVERIFIED; experiment: shadow 10+ tasks in each family with current versus role-routed settings, report paired pass^3, cost, p50/p95 makespan, interventions, and safety misses before changing defaults.**

**Anti-overfit gate:** PASS. Native agent definitions and config only. No second router. Do not hard-code current model aliases permanently; version the policy and reevaluate after provider model changes.

## 4.3 Add deterministic escalation rules, not learned confidence routing — UNVERIFIED until replay

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add an optional `route_lane`, `budget`, and `escalation_reason` to the existing task/receipt state. Escalate when any of these occur:

- declared high-risk task class;
- test/typecheck/lint or final-state oracle failure;
- required evidence/citation absent;
- tool/MCP transport failure after one policy-compliant retry;
- schema failure where the field is machine-critical;
- invalidated plan assumption;
- budget exhaustion without a terminal artifact;
- explicit uncertainty on a load-bearing fact.

No fixed local task suite with task-family labels, pinned models, budgets, deterministic terminal oracles, owner interventions, and repeated trials was available. Public routing and coding benchmarks cannot settle transfer to this harness. The §4.9 benchmark is the required experiment.

## 5.7 Whether batch API retention is acceptable

Anthropic documents that Message Batches is not eligible for Zero Data Retention ([Anthropic Batch](https://platform.claude.com/docs/en/build-with-claude/batch-processing)). ## 5.8 Whether native clients expose enough knobs to implement deadline-tier routing per task

Official products expose models, effort, and service tiers, but this bundle does not prove every saved workflow can override them per invocation without restart or config mutation. ## 5.9 Provider/model drift behavior

Aliases such as `opus`, `sonnet`, or product-specific GPT slugs can resolve differently over time or platform. No time-split local evaluation exists. Store resolved model IDs/fingerprints with each benchmark record and rerun the promotion gate after an alias changes.

## 5.10 Owner utility function for latency

It is unknown how the owner values one minute of interactive waiting versus API/credit premiums, or how that differs for unattended overnight work. Without that value, there is no single mathematically correct cost/latency frontier. The harness should expose profiles and raw Pareto curves rather than silently collapsing them into one score.

## 5.11 Marginal value of the third and later model/provider

The local audits mention cross-provider review, but no retained task-level A/B establishes unique defects found, success uplift, or cost for adding another provider. LLMRouterBench suggests larger pools have diminishing returns ([LLMRouterBench](https://arxiv.org/abs/2601.07206)); this harness still needs its own marginal-value experiment.

## 5.12 Exact safe concurrency ceiling

The bundle does not contain a controlled launch matrix correlating model concurrency, MCP memory, Windows process limits, provider rate limits, p95 latency, and completion rate. The pinned orphan-directory/command-line-cap defect also means local process failures can masquerade as an inference concurrency limit. Fix or isolate that defect, then increase concurrency stepwise on a fixed workload.

# Final architectural decision

Use a **small, native, evidence-gated allocation layer**, not a learned router service:

`task family + risk + deadline -> native role/model/effort/tier -> execute -> deterministic receipt/oracle -> accept or escalate -> record economics`

The decision is **very likely (80-90%)** to dominate a new learned router for the next harness iteration because it uses controls already shipped by both providers, is auditable, has no extra online hop, and can generate the local labels a future router would require. Evidence: official native agent controls ([Claude](https://code.claude.com/docs/en/sub-agents), [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)), current blanket local configuration (`claude/settings.json:77,685`; `codex/config.toml:3-5,17-19`), and the cautionary unified router benchmark ([LLMRouterBench](https://arxiv.org/abs/2601.07206)). The remaining uncertainty is local task transfer; the §4.9 shadow experiment settles it.

The radical replacement option remains available but has not earned its complexity. The trigger to revisit it is concrete: after instrumentation and deterministic native routing, a candidate learned router must beat best-single-model and native role/escalation baselines on time-split local tasks, reduce verified-task cost or owner-weighted latency materially, preserve pass^k and all critical strata, survive model replacement, and justify its new failure domain. Until then, building it would be frontier theater rather than frontier engineering.
