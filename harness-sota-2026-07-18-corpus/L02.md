# L02 — Anti-slop / quality-perfection: wiring verification that proves the built thing runs

## Verdict

The harness has useful pieces of a wiring-verification system, but its evidence layers are currently conflated. In the unpacked snapshot, `wire-check` detects static zero-reference smells, `journey-coverage` looks for declared E2E specs and successful commands, the shared harness records typed receipts with mutation freshness, and a Stop dispatcher is registered. Those facts do **not** establish that a feature works end-to-end or even that the Windows Claude host invoked the hook in a real session.

The best replacement for “the agent says it checked” is a small, proof-carrying commissioning protocol on the buses that already exist:

1. each promised outcome has a machine-readable acceptance claim;
2. each claim is bound to a post-mutation external observation from the actual runtime boundary;
3. the observation must be shown capable of failing through a bounded counterfactual control;
4. an independent process/context reconciles claims, receipts, and open threads;
5. the owner sees one quiet certificate or one actionable exception, never a stream of reminders.

This is **very likely (80-90%)** to reduce “looks wired but dead” completions, because the local failures are specifically missing/invalid external observations, while current agent benchmarks grade final environment state rather than model-authored explanations. Evidence: the owner says lengthy repairs “barely moves an inch” and “almost nothing works properly” (`/local_disk0/codexwork/bundle/inputs/corpus.json:11297`); the built wire-check only proves references (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/check.py:4-17`); τ-bench grades final database state ([ICLR 2025 paper](https://proceedings.iclr.cc/paper_files/paper/2025/hash/1b126cc38b8638e07bef37e7b2bb72bf-Abstract-Conference.html)); and TUA-Bench uses execution-based scoring in a real terminal ([arXiv:2606.28480](https://arxiv.org/abs/2606.28480)). The settling experiment is a shadow A/B over 30 comparable owner tasks: existing completion policy versus the protocol below, labeled by post-completion owner correction or independently reproduced outcome.

No proposal below adds a seventh hook. All proposals fold into the existing local dispatcher, shared harness dispatcher, event ledger, Workflow/Task, OPEN-THREADS/open-loops, or the already scheduled harness-bench. No proposal introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Findings — inferred surprises first

### 1. Counterfactual seam-kill: a green journey is valid only if disconnecting its claimed wire makes it red

- **Improvement:** Add a bounded counterfactual “seam-kill” proof to verification. This tests the test: temporarily disconnect one changed integration seam in a disposable worktree or injectable fixture, run the exact acceptance probe and require failure; restore the seam and require success. Examples are removing a route registration, replacing a handler with a no-op, pointing an MCP health fixture at a closed port, or removing a UI-to-command mapping. Never mutate live state.
- **What it is:** A two-receipt pair `{control: expected_fail, restored: pass}` tied to the same acceptance claim and source hash. Static reference checks answer “something names it”; seam-kill answers “the claimed observer depends on it.” It directly detects hollow tests, dead buttons behind a green build, and assertions that only inspect a success banner.
- **Why inferred:** The owner’s strongest complaint is not lack of code but code that exists without behavior. The corpus contains a direct instruction to click every button/toggle and record actual results (`/local_disk0/codexwork/bundle/inputs/corpus.json:11993`), while current `wire-check` explicitly counts non-definition references and literal route appearances (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/check.py:218-236,251-318`). A reference can exist while the path never executes.
- **How to build:** Extend the existing Workflow verification phase with a `wire_proof` record: `claim_id`, `seam`, `probe_argv`, `baseline_sha`, `mutation_patch_sha`, `expected_control_status=fail`, `restored_status=pass`, `artifact_paths`. Prefer project-native mutation facilities; otherwise use an allowlisted set of reversible AST/text mutations in a temporary worktree. Start with only changed registration/handler files and at most one mutant per claim. Append both executions through the existing typed-receipt ledger; `run`, `e2e`, and `health` already exist as receipt classes (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:98-120`). Fold the scorer into the existing weekly `harness-bench` bus, which already runs a background regression net and reports only drops (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/bench.py:2-20`).
- **External signal that verifies it:** The unchanged independent E2E/health probe must fail against the temporary broken seam and pass after restoration; a separate ledger reconciler verifies distinct source hashes and statuses. Neither the implementing context nor prose decides the result.
- **SOTA:** Mutation-score research finds mutation score among the strongest metrics for test effectiveness against real faults, while warning that mutant-derived evaluations can overestimate effectiveness ([Zhang et al., 2022](https://arxiv.org/abs/2204.09165)). This proposal therefore uses one targeted integration mutant as a control, not a universal quality score. Metamorphic testing likewise verifies relations across executions when a direct oracle is hard to define ([Liu et al., IEEE TSE](https://vuir.vu.edu.au/33046/1/TSEmt.pdf)).
- **Confidence:** **likely (55-80%)** to catch a valuable class beyond the static wire-check, because mutation/metamorphic testing and the owner’s button-level failure signal align; heterogeneous repos may lack safely injectable seams. The settling experiment is shadow execution on 20 recent feature diffs, measuring killed controls, equivalent/unsafe mutants, added minutes, and unique defects beyond existing E2E.
- **Value × effort:** transformative × medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it for reversible temp-worktree controls; confirm-first for any control that touches a live service, device, account, or paid API.
- **Native-vs-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — a Workflow/receipt adapter and allowlisted seam mutators, not another test runtime.
- **Anti-overfit:** Runs only on changed, contract-declared seams; one mutant is the minimum falsifiability check. It uses repo-native tests plus existing receipts and does not add any rejected component.

### 2. [UNVERIFIED live-host premise — settle with a real Windows Stop canary] Challenge/response receipts for the hook bus itself

- **Improvement:** Make “hook is registered” and “hook ran” different states. Each dispatcher event writes a tiny nonce-bearing execution receipt; an independent process checks that the expected event, module selection, output delivery, and terminal state all occurred.
- **What it is:** A hook flight receipt `{nonce, provider, event, module_manifest_hash, selected_modules, started, terminal, output_hash, elapsed_ms}`. For a canary session, the dispatcher includes `CANARY:<nonce>` in `additionalContext`; a transcript-side observer records whether the host delivered it. The verifier accepts only a pair: dispatcher receipt plus host-observed nonce. Exit 0 is never treated as pass because fail-open intentionally returns 0 on caught failure (`/local_disk0/codexwork/bundle/agents/harness/dispatcher.py:530-556`).
- **Why inferred:** The corpus cannot measure hooks at all (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13264`); the live-defects file says hook telemetry across 1,964 sessions is unmeasurable and prescribes checking both ledger and transcript channels (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:133-147`). Locally, a single dispatcher command can look healthy while 14 required handlers are absent. The owner wants autonomous reliability, so the system must detect its own silent loss before they encounter a dead guard.
- **How to build:** Extend `_dispatch/dispatch.py` and the shared dispatcher’s existing terminal recorder, not settings.json. Reuse the append-only event ledger and redact payloads; persist only identities/hashes/timing. The already scheduled `ClaudeHarnessBench` task sends one synthetic, non-mutating fixture per provider/event weekly and compares the receipt with a captured native output. Surface one digest item only for missing/mismatched pairs. Fold this into the existing `harness-bench`; no seventh hook. Maintain fail-open behavior: receipt errors are swallowed and the hook exits 0.
- **External signal that verifies it:** Signal A is an out-of-context dispatcher receipt; signal B is the host/transcript observer finding the matching nonce. A known-positive canary validates both detectors before any absence claim. A missing pair is “UNVERIFIED,” not “broken,” until a second real canary reproduces it.
- **SOTA:** NIST says independent review can mitigate internal bias, deployed functionality should be monitored, and measurements should be demonstrated under deployment-like conditions ([AI RMF Core, Measure 2.3–2.5](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). TUA-Bench’s deterministic setups and execution-based scoring reinforce testing the actual runtime rather than configuration text ([arXiv:2606.28480](https://arxiv.org/abs/2606.28480)).
- **Confidence:** **very likely (80-90%)** to detect silent registration/dispatch loss, supported by the confirmed 14-route registration regression and the invalid corpus hook detector. **UNVERIFIED whether Claude’s Windows transcript exposes injected hook context in a stable machine-readable form; the settling experiment is the nonce canary above, with event-ledger-only liveness as the fallback if transcript capture is unavailable.**
- **Value × effort:** transformative × low.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it; it is redacted, non-mutating telemetry on an existing scheduled bus.
- **Native-vs-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — dispatcher receipt fields plus a harness-bench comparison.
- **Anti-overfit:** No daemon or SaaS. The scheduled process already exists; receipts are bounded JSONL and can be pruned with the existing ledger.

### 3. Commissioning, not completion: actual-platform proof before the word “working”

- **Improvement:** Split completion into `built`, `verified-in-sandbox`, and `commissioned-on-target`. Only the last permits “working” for environment-sensitive work.
- **What it is:** A target-profile receipt containing provider/OS/shell/runtime versions, resolved executable paths, active configuration hash, command, exit/result digest, and observed state. A Linux CI pass cannot commission a Windows PowerShell hook; a mocked MCP test cannot commission a live MCP; a DOM unit test cannot commission the browser journey.
- **Why inferred:** The subject is Windows, and the defect record includes wrong conclusions caused by Git Bash `which`, PowerShell regex semantics, and cached files (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-124`). The corpus shows PowerShell at 10.59% errors (`/local_disk0/codexwork/bundle/inputs/corpus.json:37-43`). This remote unit itself could prove component and dispatcher behavior on Linux but cannot prove a real Windows Stop event; hiding that distinction would reproduce the owner’s complaint.
- **How to build:** Add `target_profile` and `commissioning_status` to existing receipt metadata. Extend the current Windows Scheduled Task behind `harness-bench` to run a small catalog of target probes: Claude Stop canary, Codex lifecycle canary, PowerShell/Git-Bash command resolution, critical MCP `tools/list` plus benign call, and a repo-selected E2E smoke. Hash the effective config and refuse reuse after config/code mutation. The shared receipt freshness rule already requires a pass after the last mutation (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:1093-1117`).
- **External signal that verifies it:** A result produced by the target Windows host, plus an independent reconciler matching the receipt’s code/config hashes to the artifact being claimed. For GUI/device features, the target observer is the real UI/device state, not stdout alone.
- **SOTA:** NIST requires assurance criteria under conditions similar to deployment and documentation of limits beyond tested conditions ([AI RMF Core, Measure 2.3 and 2.5](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). OSWorld 2.0 shows long-horizon agents particularly fail on hidden state and skipped verification ([arXiv:2606.29537](https://arxiv.org/abs/2606.29537)).
- **Confidence:** **very likely (80-90%)** to prevent cross-environment overclaims, based on the concrete Windows-shell misdiagnoses and deployment-context guidance. The settling experiment is ten paired tasks where Linux/mock checks are green but target commissioning is run; count unique target-only failures and latency.
- **Value × effort:** high × medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it for local read-only probes; confirm-first for live accounts, devices, purchases, deployments, or disruptive service restarts.
- **Native-vs-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — receipt schema fields and scheduled probe adapters.
- **Anti-overfit:** Reuses native commands and the existing scheduled task. It is not a durable execution service.

### 4. Two-boundary journey contracts: interaction success plus downstream state

- **Improvement:** Upgrade golden journeys from “a command named this spec returned 0” to “the user action occurred and the authoritative downstream state changed.”
- **What it is:** Each critical journey declares two mechanically independent observers. Examples: clicking “Save” + reading the persisted record after reload; toggling a trainer control + reading game memory/behavior; invoking an MCP + observing the backend state or a known response; clicking a route + seeing both rendered UI and network/database consequence. For read-only journeys, use output plus an independent invariant/source.
- **Why inferred:** Current `journey-coverage` treats a successful broad E2E command or a command naming the spec as coverage (`/local_disk0/codexwork/bundle/claude/hooks/journey-coverage/check.py:119-162`), and only gates on a textual done claim (`:204-247`). That is useful but cannot tell whether an assertion inspects the wrong layer. The owner explicitly asked to click every control and report expected versus actual (`/local_disk0/codexwork/bundle/inputs/corpus.json:11993`).
- **How to build:** Extend journey specs with a small sidecar/front matter: `action`, `observer_a`, `observer_b`, `required_state_delta`, `forbidden_delta`, `cleanup`, `risk`. The Workflow invokes the project’s existing Playwright/Cypress/pytest/CLI runner, then runs the second observer with read-only credentials where possible. Store hashes/sanitized values in one `e2e` receipt. For risky actions, dry-run or ask once through AskUserQuestion. Fold validation into `journey-coverage`; do not add a hook.
- **External signal that verifies it:** Both observers must pass after the last mutation, and at least one must be outside the implementation surface. A UI’s own success toast cannot be both observers.
- **SOTA:** τ-bench compares final database state with the annotated goal state and uses `pass^k` for reliability ([ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/1b126cc38b8638e07bef37e7b2bb72bf-Abstract-Conference.html)). TUA-Bench evaluates complete terminal tasks with execution-based scoring ([arXiv:2606.28480](https://arxiv.org/abs/2606.28480)).
- **Confidence:** **likely (55-80%)** to catch green-but-dead user paths missed by command-level coverage, because final-state scoring directly targets the gap; writing robust second observers is domain-dependent. The settling experiment is five repos, three critical journeys each, comparing current command coverage against two-boundary outcomes.
- **Value × effort:** transformative × high.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it for reversible local state; confirm-first for external side effects or cleanup that is not guaranteed.
- **Native-vs-build:** **CONFIG (settings/JSON only)** for repos whose E2E runner already supports setup/action/assert/cleanup; where an adapter is missing, use the finding 3 adapter rather than creating another subsystem.
- **Anti-overfit:** The contract names outcomes and delegates execution to repo-native tests. No universal browser/runtime wrapper is proposed.

### 5. Proof-carrying Definition of Done: AND across claims, ANY only within one claim’s acceptable modalities

- **Improvement:** Bind every completion claim and open-thread obligation to its own acceptance predicate and fresh receipt. “Builds and tests and E2E” requires all three families; a build receipt cannot clear the compound statement.
- **What it is:** A task-local acceptance manifest generated at planning time and updated only by explicit scope changes: `claim_id`, `owner_wording`, `required_receipt_family`, `acceptable_modalities`, `minimum_target_profile`, `status`, `evidence_seq`, `deferred_by`. The completion certificate is the reconciliation result, not a self-review paragraph.
- **Why inferred:** The shared harness already defines typed test/build/lint/typecheck/coverage/run/e2e/health receipts (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:98-120`) and freshness after mutation (`:1093-1117`), but `ClaimWarningModule` unions all detected families into one class set and accepts any fresh member (`/local_disk0/codexwork/bundle/agents/harness/modules.py:2092-2109,2197-2228`). The audit independently identifies that a single build can clear “build and coverage” (`/local_disk0/codexwork/bundle/inputs/audit-findings/C11.md:10-26`).
- **How to build:** In `ClaimWarningModule`, evaluate `all(any(fresh(modality) for modality in claim.acceptable_modalities) for claim in claims)`. Add missing `lint_clean` and `e2e_pass` textual families already present in the receipt map; do not infer broad semantic completeness from arbitrary prose. Workflow writes the initial manifest; TaskCompleted/Stop reconciles it; explicit owner deferral closes a claim with `deferred_by=owner` but does not label it verified. Emit only `missing_claim_ids` and the next cheapest verifier.
- **External signal that verifies it:** Each claim points to a post-mutation ledger receipt created by an execution/tool result. The reconciler is deterministic and runs in the shared harness context, not the implementing model’s narrative context.
- **SOTA:** NIST recommends objective, repeatable, scalable TEVV, documented test methods, independent assessment, and measurement under deployment conditions ([AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). τ-bench’s final-goal-state grading is the analogous agent-evaluation contract ([arXiv:2406.12045](https://arxiv.org/abs/2406.12045)).
- **Confidence:** **almost certain (90-99%)** to eliminate the specific single-receipt/compound-claim false clear, because the current ANY-over-union logic is explicit and the proposed boolean semantics is deterministic. The remaining 1-10% uncertainty concerns claim extraction, settled by requiring the Workflow to declare claims explicitly and replaying 100 redacted historical Stop messages in shadow.
- **Value × effort:** transformative × low.
- **Novelty:** user-asked.
- **Autonomy:** just-do-it for deterministic receipt semantics; confirm-first only when changing the owner’s accepted scope.
- **Native-vs-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — a localized ClaimWarning/Workflow schema change.
- **Anti-overfit:** No model judge. Explicit claims and typed receipts are smaller and more stable as models improve.

### 6. Blind verifier lane: fresh context receives the contract and artifact, never the implementation story

- **Improvement:** For high-risk or semantically ambiguous claims, invoke a fresh verifier that sees the owner’s goal, acceptance manifest, changed artifact, and raw external receipts—but not the builder’s reasoning or conclusion.
- **What it is:** A black-box reproduction lane. Its output is constrained to `SUPPORTED`, `REFUTED`, or `NOT_ENOUGH_EVIDENCE`, plus executed probe receipts. An opinion without a different tool/result is invalid. This honors the law that intrinsic same-context self-correction fails.
- **Why inferred:** The cross-tool contract currently asks for an “internal generator-critic pass” (`/local_disk0/codexwork/bundle/claude/AGENTS.md:72-83`), but that is rejected by this unit’s law unless it closes on an external signal. The existing ecosystem already has fresh-context verification and Workflow/Task, so the improvement is strict evidence isolation rather than another critic.
- **How to build:** Enable a Workflow verification step when any of these hold: multifile/target-sensitive change, failed seam-kill, missing second observer, owner-disputed completion, or low-confidence acceptance mapping. Give the verifier a minimal typed packet. Require it to run/reproduce the acceptance probe in a fresh workspace/context and write receipts through the same ledger. Do not spawn it for routine green single-file work. If it disagrees, reopen the claim in OPEN-THREADS and return one compact exception.
- **External signal that verifies it:** A genuinely different model/context executes a different-context probe against the artifact; deterministic receipt reconciliation—not the verifier’s prose—settles completion.
- **SOTA:** NIST states independent review can improve testing effectiveness and mitigate internal bias ([AI RMF Core, lines summarized under Measure](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). OSWorld 2.0 reports that frontier agents lose constraints, guess rather than ask, and skip verification on long workflows ([arXiv:2606.29537](https://arxiv.org/abs/2606.29537)).
- **Confidence:** **likely (55-80%)** to catch semantic mismatches that deterministic wiring probes miss, because context isolation reduces shared rationalization but second models can share errors. The settling experiment is a blinded replay of 30 owner-disputed completions, comparing same-context review, blind review without execution, and blind review with execution receipts.
- **Value × effort:** high × medium.
- **Novelty:** user-asked.
- **Autonomy:** just-do-it when it uses local/reversible probes; confirm-first when verification itself would cause an external side effect.
- **Native-vs-build:** **NATIVE (Claude Code already does this; we just enable it)** — use existing Workflow/Task/fresh-context capability with a stricter packet and execution requirement.
- **Anti-overfit:** Risk-triggered, not universal multi-agent fan-out; no trained critic or second orchestrator.

### 7. Thread escrow: no claim can disappear between discussion, implementation, verification, and handoff

- **Improvement:** Turn every discussed obligation into an escrowed thread with a falsifiable closure predicate. Completion is a set reconciliation: promised thread IDs minus verified/deferred/rejected thread IDs must be empty.
- **What it is:** An extension of OPEN-THREADS/open-loops and the event ledger, not a new task manager. Each record carries `thread_id`, source turn, exact promise, acceptance claim IDs, owner, dependency, status, evidence refs, and explicit close reason. “Discussed” is not “done”; “code written” is not “verified.”
- **Why inferred:** “Never drop a thread” is a hard constraint. The corpus’s repeated “why did you stop” pattern (`/local_disk0/codexwork/bundle/inputs/corpus.json:10425-10428`) and the owner’s instruction to proceed until everything works (`:10389`) show that forgotten residue imposes real cognitive cost. The built open-loops store already models durable triggers and derives unresolved failures/goals from the event ledger (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/_common.py:2-26,110-198`), but its predicates do not bind obligations to acceptance receipts.
- **How to build:** Add `acceptance_claim_ids` and terminal states to open-loop records. Workflow creates/updates threads; event-ledger receipts automatically satisfy linked predicates; owner deferral is recorded, never silently inferred. SessionStart injects only a count and the highest-priority next action, not the whole backlog. Stop returns one bounded missing-thread list only when a completion claim is made. Reuse the existing manifest’s `open-loops/resurface` SessionStart entry (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:53-60`).
- **External signal that verifies it:** A deterministic ledger/open-loop reconciliation in a separate process shows zero unaccounted thread IDs and verifies each “closed” thread has either external receipts or explicit owner disposition.
- **SOTA:** OSWorld 2.0 specifically targets long-horizon hidden/implicit state and reports agents losing constraints and missing changing information ([arXiv:2606.29537](https://arxiv.org/abs/2606.29537)). Amershi et al.’s human-AI guidelines emphasize supporting efficient correction and maintaining user control across interaction ([CHI 2019](https://doi.org/10.1145/3290605.3300233)).
- **Confidence:** **very likely (80-90%)** to prevent mechanically representable threads from vanishing, supported by the existing durable store and deterministic set reconciliation. It cannot capture a promise never extracted; the settling experiment is shadow extraction on 50 sessions with owner review of false-missing and missed-thread rates.
- **Value × effort:** high × low.
- **Novelty:** user-asked.
- **Autonomy:** just-do-it for recording/reconciling explicit promises; confirm-first to reinterpret, reject, or defer owner scope.
- **Native-vs-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — additive open-loop fields and a reconciler.
- **Anti-overfit:** Uses the existing append-only ledger/open-loop files; no vector memory, knowledge graph, or durable workflow engine.

### 8. [UNVERIFIED personalization premise — settle with shadow utility labels] Quiet, evidence-calibrated proactivity instead of more prompts

- **Improvement:** Personalize *which verification runs automatically* and *when the owner is interrupted*, using observed utility rather than another reminder. Default to autonomous, reversible checks; ask once only when the missing evidence requires authority or a material choice.
