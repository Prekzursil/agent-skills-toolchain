# L01 — The Completeness Critic: external negative-space verification

## Executive verdict

Build the Completeness Critic as a **fresh-context, read-only negative-space auditor** whose sole question is: **“Which obligation, connection, verification modality, or previously opened thread lacks external closure evidence?”** It must not be another same-context reflection prompt, another regex scanner, another hook, or another authority that can declare work complete.

The best fit is a selective acceptance phase on the existing Workflow / agent and shared-dispatcher buses. The builder produces artifacts; deterministic tools produce receipts; a newly launched critic independently reconstructs the obligation set from immutable task sources and compares it with those receipts, the current diff, repository reachability, runtime behavior, and durable open-thread state. A critic finding is advisory until a different tool reproduces it. A critic can request a repair, but only an external receipt can close the finding. This obeys the unit's governing law: the generator never certifies its own work inside the context that created it.

This design is **very likely (80-90%)** to find more genuinely unfinished work than the current completion-language gate alone, because it checks obligation coverage and artifact connectivity rather than merely whether a “done” phrase has some evidence; the evidence is the current gate's phrase-trigger and any-of receipt logic at `/local_disk0/codexwork/bundle/agents/harness/modules.py:2000-2040,2092-2115,2197-2228`, while the proposed local held-out evaluation in Finding 7 is the experiment that must measure the actual gain. It is **likely (55-80%)** to reduce owner-visible “continue/finish it” interventions without increasing prompt fatigue, because only changed, externally reproduced gaps are surfaced and proactive-computing studies favor intervention at task breakpoints; the exact local effect is **UNVERIFIED — experiment L01-E7 (paired shadow deployment with owner-interruption counts) settles it**.

The proposal adds **zero hook registrations**. All lifecycle activation is folded into the already registered shared dispatcher / Workflow acceptance phase. It therefore remains under the approximately-six-hook ceiling. Every implementation path below is fail-open: catch its own exception, record `critic_status=unavailable`, and return/exit 0. A missing critic is never silently interpreted as a green critic.

## Proposed operating contract

The critic receives no builder chain-of-thought and no raw downstream report prefix. Its bounded input is:

```text
CRITIC-BUNDLE v1
task_source: immutable transcript/issue/spec pointer + sha256
root_goal: pointer, never a rewritten substitute
declared_scope: paths/authority/destructive limits
acceptance_sources: ordered pointers
artifact_manifest: changed paths + hashes + build/package outputs
receipt_index: ledger seq, class, argv hash, status, mutation seq
thread_index: open/deferred/superseded/closed records
detector_results: wire, stub, journey, truth, liveness, capability
builder_summary: optional five-field handoff; untrusted claim, not ground truth
```

It emits one permissive JSON object per gap. Required fields are deliberately few to avoid the measured strict-schema failure mode:

```json
{"gap_id":"g1","obligation_id":"o3","state":"missing|unwired|unfinished|unverified|conflict|unknown","claim":"...","external_evidence":["ledger#81","sha256:..."],"settling_probe":"exact command or owner decision","owner_visibility":"silent|digest|interrupt","repair_authority":"just-do-it|confirm-first","confidence_band":"likely (55-80%)"}
```

Unknown fields are allowed; invalid JSON is stored as `critic_status=malformed` plus the raw bounded text. There is no recursively nested schema and no schema-driven retry fan-out.

The lifecycle is:

```text
immutable task sources ──> independent obligation reconstruction
                                  │
current artifacts + receipts ─────┼──> fresh-context critic gap list
open-thread state + detectors ────┘              │
                                                 ├─ no external probe -> advisory/unknown
                                                 ├─ probe contradicts -> close critic finding
                                                 └─ probe reproduces -> repair or owner decision
                                                                  │
                                           fresh receipt + critic re-check closes obligation
```

The critic never emits `DONE`. Its terminal states are `NO-GAPS-FOUND-WITH-COVERAGE:<n>/<n>`, `GAPS:<n>`, or `CRITIC-UNAVAILABLE:<reason>`. `NO-GAPS-FOUND` is explicitly not proof that no gap exists.

## Findings (inferred-surprise first)

### Finding 1 — Compile the negative space, not another review prompt [UNVERIFIED BUILD SIZE]

**Improvement — Obligation-difference compiler.**

**What it is.** On acceptance, a fresh critic independently decomposes the immutable task prompt, issue/spec, plan, and explicit owner amendments into atomic obligations. It then performs a set difference against evidence-backed closures. The unit of analysis is not “is this answer good?” but `(obligation, required artifact, required connection, required verification, thread state)`. Compound requirements split into separate records; explicit deferrals remain visible and are not failures; contradictions become `conflict`, not silently resolved assumptions.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement `completeness_bundle.py` as a small adapter around the existing event ledger and task/Workflow envelope, plus a narrow prompt mode for the existing `agent-as-judge` role. Do not create a daemon, vector store, knowledge graph, or guardrail framework. Add no hook: Workflow calls it in its acceptance phase, while the existing dispatcher may enqueue it through the background registry for shadow review.

**Why inferred.** The owner did not merely request test verification; they explicitly named “missing, unwired, or unfinished,” banned built-but-not-wired and duplicate-v2 artifacts, and made thread loss unacceptable. The current completion gate detects a fixed set of claim phrases (`/local_disk0/codexwork/bundle/agents/harness/modules.py:2000-2049`) and can answer whether some verification exists, but it has no representation of each source obligation. The live defect where an orchestrator-authored false constraint propagated to roughly 15 prompts shows why the critic must reread immutable sources rather than accept a builder's summarized contract (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160`).

**How to build.** 

1. Persist only source pointers/hashes at task start: original user turn, issue/spec, plan, and amendment turns. Keep `root_goal` separate from `current_turn_intent`.
2. At acceptance, launch a new agent context with the pointers and ask it to emit atomic obligation JSONL. It must quote a source locator for each item.
3. A deterministic join maps each obligation to artifact hashes, receipt classes, reachability records, and thread state. A missing join becomes a candidate gap; it never becomes a defect solely because the LLM says so.
4. Send candidates back to the critic for a bounded alternative-explanation pass: explicit deferral, out-of-scope, superseded requirement, generated artifact, or genuinely absent.
5. Record the result in the existing ledger as `critic_gap`, keyed by source hash + obligation id, so reruns supersede rather than duplicate it.

**External signal that verifies it.** The source pointer/hash is one external signal; repository/artifact state or a deterministic receipt is the second. For an “absent” claim, the critic must first demonstrate that the selected detector finds a seeded known-present obligation, then show two mechanically independent misses—for example, no route reference in static reachability **and** a browser navigation that cannot reach the route. A different fresh context performs the source extraction, satisfying the governing law.

**SOTA citation.** Anthropic reports that separating generator and evaluator is a strong lever because agents grading their own work skew positive, while concrete criteria make evaluation tractable: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps). OpenAI treats active plans, completed plans, technical debt, verification status, and mechanical cross-link checks as first-class repository artifacts: [Harness engineering](https://openai.com/index/harness-engineering/). Horvitz's mixed-initiative work frames effective collaboration as coupling automation with direct human control rather than choosing one exclusively: [Principles of Mixed-Initiative User Interfaces](https://erichorvitz.com/uiact.htm).

**Confidence.** **Very likely (80-90%)**, based on the explicit mismatch between phrase/receipt checking and obligation coverage plus the externally reported benefit of evaluator separation. The size estimate is **UNVERIFIED — experiment L01-E1 (prototype against 20 held-out task artifacts, recording changed lines and runtime) settles whether it stays below 200 lines**.

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it. Scope expansion or changing an explicit owner deferral is outside this proposal's autonomous authority and remains an owner decision.

### Finding 2 — Make silence a product feature: an attention-budgeted critic

**Improvement — Delta-only, breakpoint-timed surfacing.**

**What it is.** The critic runs proactively but usually says nothing to the owner. It surfaces only a state transition: a newly reproduced high-impact gap, a previously open obligation that became closable, a conflict requiring owner authority, or a critic outage on a release-critical acceptance. Repeated unchanged gaps remain in the ledger/open-thread view and are not re-prompted. Low/medium findings appear in one terminal digest at the natural task boundary; only irreversible scope/intent conflicts interrupt.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Add policy fields to the critic mode/Workflow configuration: `surface=new_delta`, `digest_at=acceptance_boundary`, `repeat_suppression_by=gap_id+evidence_hash`, `owner_interrupt=authority_conflict|irreversible`, and `max_visible=3`. Fold any generic completion reminder it subsumes into the existing Stop dispatcher; do not add a seventh hook.

**Why inferred.** Prompt fatigue is a hard constraint, not a secondary optimization. The local open-loop resurface already caps visible items at three (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:38-40,69-95`), which is a reusable presentation precedent. The Stop dispatcher already aggregates seven internal checks behind one invocation (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:72-141`); duplicating their prose would multiply attention cost. The owner wants the system to remember everything, not to recite everything every turn.

**How to build.** Store `first_seen_evidence_hash`, `last_seen_evidence_hash`, `last_surfaced_at`, and `owner_disposition` on each critic gap in the existing ledger. The digest algorithm selects only records whose state or evidence hash changed. Auto-close a surfaced gap only on a matching external receipt; do not close merely because it aged. The UI text is one compact line per gap: `impact · missing thing · proof/probe · action`. Details remain behind the ledger/artifact pointer.

**External signal that verifies it.** Compare two objective streams in a shadow A/B: (a) injected-context characters and owner question/correction turns per task, and (b) seeded-gap recall. A deterministic event counter—not the critic—computes both. The owner adjudicates only sampled false-positive/false-negative pairs. Promotion requires non-inferior seeded-gap recall with fewer visible repeated messages; the exact threshold is set in Finding 7.

**SOTA citation.** Proactive notification research warns that ill-timed alerts decrease performance and increase frustration, and reports better results when notifications are deferred to meaningful task breakpoints: [Paying Attention to Interruption](https://www.microsoft.com/en-us/research/video/paying-attention-to-interruption-a-human-centered-approach-to-intelligent-interruption-management/). Attention-sensitive alerting explicitly balances deferral cost against interruption cost: [Attention-Sensitive Alerting](https://arxiv.org/abs/1301.6707). Microsoft's Human-AI guidance was validated through multiple rounds including 49 practitioners and 20 products: [Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/).

**Confidence.** **Likely (55-80%)** to lower owner cognitive load, based on interruption research and the existing three-item local cap; local task-flow benefit is **UNVERIFIED — experiment L01-E7 (shadow A/B of visible characters, repeated notices, and owner interventions) settles it**.

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it.

### Finding 3 — Use two acceptance lanes, not a critic on every turn

**Improvement — Selective synchronous acceptance plus asynchronous shadow coverage.**

**What it is.** There are two routes:

- **Acceptance lane:** for explicit Definition-of-Done tasks, multi-file/build/package work, owner “finish everything” instructions, destructive/irreversible operations, or release/merge requests, Workflow waits for deterministic checks, launches a fresh critic, allows at most two builder→critic repair rounds, and then returns a terminal state.
- **Shadow lane:** ordinary tasks enqueue a read-only critic job at Stop/TaskCompleted through the existing background registry. The session may end. Any later reproduced gap becomes an open-thread delta, surfaced at the next natural boundary.

The risk router is deterministic and conservative. It uses task metadata and mutation/artifact counts, not the builder's self-assessed confidence.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Configure the existing Workflow acceptance phase and background registry. The dispatcher manifest already demonstrates a SessionStart check with `side_effect: spawn+replay` (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:20-28`), so the shadow route reuses an existing bus. The existing `TaskCompleted` registration already reaches the shared dispatcher (`/local_disk0/codexwork/bundle/claude/settings.json:458-468`). No new hook or orchestration runtime is permitted.

**Why inferred.** Always-on synchronous review would violate prompt-fatigue and latency constraints, while a purely passive role leaves high-stakes completion unchecked. The corpus shows `StructuredOutput` at 22.9% errors (`/local_disk0/codexwork/bundle/inputs/corpus.json:103-108`) and identified retry loops across Read, Bash, TaskOutput and other tools (`/local_disk0/codexwork/bundle/inputs/corpus.json:10297-10369`); bounded rounds and fallback transport prevent the critic from becoming another grind loop. The current judge is explicitly advisory and read-only (`/local_disk0/codexwork/bundle/claude/agents/agent-as-judge.md:15-41`), which is a sound base for both lanes.

**How to build.** Add `acceptance_risk` to the task envelope: `routine|contracted|release-critical`. Contracted/release-critical tasks call `Workflow.acceptance(critic_mode="completeness")`; routine tasks append a bounded job record to the background registry. A breaker stops after two identical critic fingerprints and emits `CRITIC-STALLED`, never a third repair loop. Critic failure returns `unavailable`, exits 0, and cannot be represented as green. If a cross-vendor model is available in the B1 catalog, prefer it; otherwise use a fresh same-vendor context but never let its opinion gate without an executable external receipt.

**External signal that verifies it.** The acceptance lane must produce four independent records: task-source hash, critic run id/context id, deterministic receipt ids, and final obligation-state counts. The shadow lane must produce a background-registry terminal record and later ledger join. A test fixture kills the critic process; success is that the parent finishes, `critic_status=unavailable` persists, and no `closed` obligation is minted.

**SOTA citation.** OpenAI describes agent-to-agent review loops and application-legibility tooling that lets agents reproduce and validate behavior directly: [Harness engineering](https://openai.com/index/harness-engineering/). Anthropic distinguishes the final environment outcome from what an agent says happened and recommends isolated trials and thoughtful graders: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Anthropic also cautions that evaluator separation does not itself eliminate LLM leniency: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps).

**Confidence.** **Likely (55-80%)** to preserve routine-task latency while improving contracted-task scrutiny, based on selective routing and existing background/Workflow primitives. Cross-vendor availability and spawn latency on the Windows host are **UNVERIFIED — experiment L01-E3 runs 30 routine and 30 contracted disposable tasks with catalog availability, wall time, and failure injection**.

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first. Enabling a synchronous acceptance lane changes completion latency; once enabled, its read-only routing may run autonomously, while destructive repair and scope expansion remain outside its authority.

### Finding 4 — Require one fresh external closure per obligation, including runtime “dark surfaces” [UNVERIFIED DOMAIN COVERAGE]

**Improvement — Per-obligation evidence matrix and modality planner.**

**What it is.** Every obligation gets its own closure row; no single green test clears a bundle of unrelated claims. The critic asks which modality can falsify the obligation: static reference, unit test, build/package, API/DB state, browser/UI journey, source entailment, external service probe, or owner acceptance for irreducibly subjective intent. “Source exists,” “wired,” “built,” “deployed,” and “usable” are different states.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing receipt map/join to require coverage per obligation and to consume existing wire-check, journey-coverage, truth-verify, UI-drive/Playwright, package smoke, and research-claim receipts. This is a mapping and freshness join, not a new test framework.

**Why inferred.** The quality bar explicitly bans dead buttons, built-but-not-wired work, and reimplementation. Locally, wire-check already identifies zero-reference symbols and unlinked routes (`/local_disk0/codexwork/bundle/claude/hooks/wire-check/check.py:259-318`), while journey-coverage compares declared E2E files to successful commands (`/local_disk0/codexwork/bundle/claude/hooks/journey-coverage/check.py:1-21,105-162`). The shared claim gate currently flattens requested receipt classes and calls `has_fresh_receipt` over the combined set (`/local_disk0/codexwork/bundle/agents/harness/modules.py:2092-2107,2197-2228`); it does not establish a separate receipt for every semantic obligation. The corpus's 939 read-before-write errors and 709 `ENAMETOOLONG` fingerprints (`/local_disk0/codexwork/bundle/inputs/corpus.json:4298-4318`) further show that “attempted” and “artifact reached the intended state” must remain distinct.

**How to build.** Define a small table mapping obligation predicates to acceptable receipt classes, for example:

| Obligation predicate | Required external closure |
|---|---|
| file/code created | fresh hash/diff after last mutation |
| symbol/route wired | static reachability **and**, when user-facing, runtime navigation |
| package/build delivered | build exit + artifact existence/hash + packaged smoke |
| bug fixed | exact failing argv/input fingerprint rerun green after mutation |
| research claim supported | independent claim-source entailment record |
| external service working | liveness probe from B1 catalog, not prose |
| owner-taste/intent match | owner decision or calibrated independent judge, never builder self-score |

If no acceptable probe exists, state `unknown/unverified`; never improvise a weak proxy and call it closure. Receipts must post-date the last relevant mutation. A model finding can select a probe, but the tool result decides pass/fail.

**External signal that verifies it.** Each matrix row names the different tool or owner action that closes it. For runtime claims, compare static reachability with browser/API/DB outcome. For research, use a separately launched claim verifier that reads the source. For subjective residue, keep the existing judge advisory until owner-labeled calibration exists. A fresh source/artifact hash prevents reuse of stale receipts.

**SOTA citation.** Anthropic's eval guidance makes the distinction explicit: a booking claim is not the outcome; the reservation's presence in the database is the outcome: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). OpenAI reports making UI, logs, metrics, and traces directly legible so agents can validate critical journeys rather than infer them from code: [Harness engineering](https://openai.com/index/harness-engineering/). Research on LLM judges finds significant self-preference bias, supporting executable receipts over model style judgments: [Self-Preference Bias in LLM-as-a-Judge](https://arxiv.org/abs/2410.21819).

**Confidence.** **Very likely (80-90%)** to prevent a single irrelevant green signal from clearing multi-part completion, because closure becomes a deterministic one-to-one join. The coverage taxonomy is **UNVERIFIED for all owner domains — experiment L01-E4 runs the matrix against held-out coding, reverse-engineering, research, UI, and computational-chemistry tasks and records unmapped obligations**.

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it. This proposal covers cheap read-only probes and already-authorized in-scope tests only; costly jobs, destructive probes, production actions, and owner-taste judgments remain outside its autonomous authority.

### Finding 5 — Reconcile threads as durable obligations; never expire a commitment silently

**Improvement — Thread-to-obligation reconciliation over existing stores.**

**What it is.** The critic treats every discussed commitment as a state machine: `open → in_progress → externally_closed`, or `open → explicitly_deferred`, or `open → superseded(by id)`. It joins the task obligation set with the event ledger, open-loop triggers, and the canonical OPEN-THREADS document. A session can stop with open work, but it cannot erase or silently age it out. The critic reports “remaining” as a terminal fact, not as a nag.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a reconciliation projection to the existing event-ledger/open-loop code and extend the typed task handoff with obligation ids. Do not add a memory store. Basic-memory remains semantic memory; the event ledger remains objective state; OPEN-THREADS remains the human-readable cross-project register.

**Why inferred.** “Never drop a thread” is a direct owner hard constraint. Existing open-loops already derives unresolved failures and dangling goals from the ledger (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/_common.py:15-26`) and suppresses duplicate replay on recovery (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:10-25,83-95`). However, its trigger records default to a 30-day TTL (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/_common.py:41-48`) and expired records are removed during load/GC (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/_common.py:112-150`). That TTL is appropriate for prospective reminders but not for owner commitments. The distinction—not a replacement store—is the missing design move.

**How to build.** Add `record_kind=reminder|commitment`; only reminders may have TTL. Commitments require `source_pointer`, `obligation_id`, `status`, and for closure `receipt_id|owner_decision_id`; for deferral/supersession they require reason and target id. At Stop/TaskCompleted, the critic diffs source obligations against terminal records. The existing SessionStart resurfacer continues selecting at most three context-relevant items, but the complete count and artifact pointer remain visible. Compaction and provider handoff carry ids, not copied prose.

**External signal that verifies it.** A deterministic reconciliation command asserts that every source obligation has exactly one current state and that no `open` commitment disappeared between snapshots. A fixture advances time beyond 30 days: a reminder may GC, a commitment must remain. A second fresh-context critic reconstructs obligations from the original prompt and detects any ledger omission. Owner disposition is the only signal allowed to mark an unwanted but valid commitment deferred.

**SOTA citation.** OpenAI describes versioned, co-located active plans, completed plans, and known technical debt so agents do not rely on hidden external context: [Harness engineering](https://openai.com/index/harness-engineering/). Anthropic emphasizes structured artifacts for context handoff across long sessions: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps). Mixed-initiative research emphasizes user guidance and refinement of automated results: [Principles of Mixed-Initiative User Interfaces](https://erichorvitz.com/chi99horvitz.pdf).

**Confidence.** **Almost certain (90-99%)** that non-expiring, source-linked commitment records prevent TTL-based silent loss by construction; evidence is the current explicit TTL/GC implementation and deterministic state invariant. It is **likely (55-80%)** to reduce felt thread-loss stress, based on the owner's direct requirement; the human effect is **UNVERIFIED — experiment L01-E7 correlates reconciliation misses and owner “continue/forgot” adjudications over a prospective sample**.

**Value × effort:** transformative × low.  
**Novelty:** inferred-surprise.

### Finding 6 — Personalize interruption and repair authority, never truth

**Improvement — Bounded owner policy for critic behavior plus calibrated trust labels.**

**What it is.** Personalization controls **when to speak, how much detail to show, and which reversible repairs may proceed**. It never changes what counts as evidence or lowers a quality criterion. The policy begins with explicit owner instructions: preserve threads, minimize cognitive load, finish in-scope work, and ask before meaningful scope/authority changes. Learned preferences enter only after owner-confirmed dispositions; contaminated heuristic “correction candidates” cannot train it.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Store a small, owner-editable policy record in the existing semantic-memory/config layer, with provenance per field: `explicit`, `owner_confirmed`, or `default`. Example fields: `digest_size=3`, `repeat_unchanged=false`, `auto_repair=reversible_in_scope`, `confirm=scope|destructive|preference_conflict`, `critic_detail=summary_then_pointer`. Do not train a preference model and do not build a personalization service.

**Why inferred.** The corpus's correction detector is recall-biased and its smoke sample was 41/41 false positives (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10375`), so using it directly would personalize to agent-authored noise. The known false constraint propagated through fan-out demonstrates the danger of treating inferred preferences as ground truth (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160`). At the same time, the owner has supplied unusually clear explicit preferences in this unit, so ignoring them would waste high-confidence personalization signal.

**How to build.** Attach provenance and a revocable id to each policy field. A critic gap carries both an evidence confidence and a separate action policy. Confidence uses the mandated bands and cites receipts; action is `just-do-it` or `confirm-first`. Never infer “owner accepts lower quality” from prior behavior. Sample disputed/low-confidence findings for owner adjudication at a breakpoint, update only the relevant presentation/action field, and retain the objective record even if the owner chooses not to act.

**External signal that verifies it.** A config parser—not the critic—shows which explicit policy selected the surfacing/repair action. Owner disposition is the only label for a preference update. Evidence thresholds remain identical in paired tests with personalization on/off. An audit fixture injects a false “owner likes X” correction candidate and verifies that it cannot mutate policy without an owner-confirmed id.

**SOTA citation.** Personalized alignment may improve usefulness but unbounded personalization risks profiling, privacy infringement, bias reinforcement, and exploitation: [The benefits, risks and bounds of personalizing alignment](https://www.nature.com/articles/s42256-024-00820-y). Microsoft's synthesis defines appropriate reliance as accepting correct output and rejecting incorrect output and warns that both under- and over-reliance harm team performance: [Appropriate reliance on Generative AI](https://www.microsoft.com/en-us/research/publication/appropriate-reliance-on-generative-ai-research-synthesis/). Anthropic found five assistants showed sycophancy and that preference data can reward responses matching user views: [Towards Understanding Sycophancy](https://www.anthropic.com/research/towards-understanding-sycophancy-in-language-models).

**Confidence.** **Very likely (80-90%)** that provenance-gated policy prevents the measured candidate-detector contamination from directly changing behavior, because unconfirmed records are mechanically excluded. It is **roughly even (45-55%)** that inferred presentation preferences beyond the explicit unit instructions will add value; evidence is limited, so those preferences remain disabled until experiment L01-E6 collects prospective owner-confirmed dispositions.

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first. Applying already-explicit policy needs no repeated confirmation, but adding an inferred preference—the actual personalization change—requires owner confirmation.

### Finding 7 — Externally verify the critic with omission mutations, paired near-misses, and owner-load metrics [UNVERIFIED PROMOTION THRESHOLDS]

**Improvement — A held-out CompletenessCriticBench and shadow promotion gate.**

**What it is.** The critic is itself untrusted. A deterministic mutation harness creates paired tasks: one complete and one with exactly one seeded omission. It measures whether the critic names the correct obligation and settling probe without flagging the complete twin. Separate categories prevent high performance on easy TODO markers from hiding failure on dead UI, stale evidence, or dropped threads.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add pytest fixtures and a scoring script alongside existing harness tests. Use temporary repos/state roots and existing detectors. No trained critic, evaluation SaaS, durable-execution engine, or second orchestration runtime.

**Why inferred.** The local defects show why unvalidated detectors cannot be trusted: six wrong conclusions from single probes and a seventh corrected by a known-positive control (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`). Four detector implementations also confused mention with use and produced 9+ documented false signals (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-22,52-82`). The corpus hooks detector itself failed its positive control (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13264`). A critic deployed without an external test oracle would repeat the exact class of mistake it is meant to prevent.

**How to build.** Seed at least these paired cases:

1. one acceptance criterion omitted / its complete twin;
2. added function with zero callers / intentionally public extension point;
3. route exists but no navigation / route reachable through dynamic registry;
4. visible control with no action / deliberately disabled control with explained state;
5. source changed but package artifact not rebuilt / fresh packaged smoke;
6. green receipt older than last mutation / fresh post-mutation receipt;
7. open commitment absent from handoff / explicitly deferred commitment;
8. duplicate `v2` reimplementation / legitimate versioned protocol;
9. prose that mentions TODO/destructive terms / executable occurrence;
10. detector returns no hits while a known-positive is present / valid empty set after the control passes;
11. external verifier process dies / parent succeeds fail-open with `unavailable`;
12. critic disagrees with deterministic runtime outcome / runtime outcome wins and critic is logged wrong.

Run multiple fresh-context trials because model outputs vary. Score per category: seeded-gap recall, complete-twin false-positive rate, settling-probe validity, externally reproduced precision, abstention quality, stale-receipt acceptance, thread-loss rate, added wall time, owner-visible characters, repeated notifications, and owner adjudication burden. Never average a critical thread-loss or false-closure case away inside one quality score.

The following promotion numbers are **UNVERIFIED — the experiment is two prospective shadow windows of at least 50 paired cases plus 30 natural tasks, with confidence intervals and category breakdown**: consider moving from shadow to selective acceptance only if every critical seeded omission is caught in all clean reruns, reproduced precision is at least 90%, complete-twin false positives are at most 5%, and median owner-visible additions do not increase. These are initial safety targets, not evidence that the critic currently meets them.

**External signal that verifies it.** The mutation manifest is hidden from the critic and acts as the oracle. Deterministic file/runtime assertions grade each case. A different process launches each critic in a fresh context. Owner labels are used only for subjective intent and interruption burden, never to overwrite deterministic results. Release reports include invalid/missing trial counts; missing trials are not green.

**SOTA citation.** Anthropic recommends defined success criteria, multiple trials, multiple grader assertions, clean isolated environments, and grading final environment state rather than transcript claims: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Microsoft HAX guidance was validated across multiple evaluation rounds and product scenarios rather than accepted as intuition: [Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/). Model-written evaluations can scale evaluation discovery, but human agreement and external labels remain the validating signal: [Discovering Language Model Behaviors with Model-Written Evaluations](https://www.anthropic.com/research/discovering-language-model-behaviors-with-model-written-evaluations).

**Confidence.** **Almost certain (90-99%)** that the paired mutation suite detects detector classes represented by its fixtures, because the oracle controls the single changed variable. Generalization from fixtures to natural owner work is **likely (55-80%)** only after category-balanced prospective results; the cited shadow experiment settles promotion.

**Value × effort:** transformative × medium.  
**Novelty:** user-asked (external verification), with inferred-surprise paired near-miss and owner-load dimensions.  
**Autonomy:** just-do-it. This proposal is limited to disposable copies and shadow mode; promotion is a separate owner decision.
