# A021 — Coherence audit: `~/.claude/rules/**` versus `~/.claude/commands/**`

**Unit:** A021  
**Date:** 2026-07-19  
**Subject snapshot:** `/local_disk0/codexwork/bundle/claude` (read-only)  
**Question:** find **silent override** between rules and commands: at the concrete runtime decision point, one side is unavailable or shadowed, so the other side wins and the losing text cannot affect the decision.

## Executive result

I found **two verified silent-override defects**, both caused by putting globally timed policy inside path-scoped rules:

1. `/model-route` can recommend Sonnet for implementation before the Opus-only substantive-subagent rule has loaded.
2. `/checkpoint create` can make a commit after `/verify quick` while all three pre-commit rule files—tests/coverage, code review, and security—remain unloaded.

I also found **five genuine textual conflict families** (model routing in `/start-task`; hard-coded 80% coverage; test-after implementation flows; the old background cross-vendor transport; and HIGH review severity). These are not reported as verified silent overrides: once their relevant rules load, Claude Code supplies both texts to the model and explicitly documents that contradictory instructions may be reconciled arbitrarily. Treating “the later command always wins” as fact would be unsupported. The live Windows Claude executable and interactive transcript were not included on this Linux worker, so an empirical A/B outcome test is **UNVERIFIED; the experiment is the fresh-profile `InstructionsLoaded` + `UserPromptExpansion` trace described under GAPS**.

This distinction matters. A path-scoped rule that has not loaded is mechanically dead at the decision point; a loaded rule that competes with a command is unreliable, but it is not dead text in the strict sense requested.

### Runtime model used for this audit

The following are primary-source runtime facts, rather than assumptions:

* Rules without `paths` load at launch; path-scoped rules load when Claude reads a matching file. Anthropic's current [memory/rules documentation](https://code.claude.com/docs/en/memory#organize-rules-with-claude-rules) says this directly.
* A custom command is now the legacy form of a skill; invoking it loads its body as instructions/prompt. Anthropic's current [skills/custom-command documentation](https://code.claude.com/docs/en/slash-commands) states that `.claude/commands/*.md` still works and uses the same mechanism.
* `UserPromptExpansion` occurs when a typed command expands, before the expanded prompt reaches Claude, while `InstructionsLoaded` fires when a rule is actually loaded. Anthropic's current [hooks reference](https://code.claude.com/docs/en/hooks) documents both events.
* Loaded CLAUDE/rule instructions are additive rather than an enforced override stack. When loaded instructions conflict, Claude uses judgment and more-specific instructions only **typically** take precedence; the outcome is not guaranteed. See Anthropic's [feature-layering documentation](https://code.claude.com/docs/en/features-overview#understand-how-features-layer) and [memory troubleshooting](https://code.claude.com/docs/en/memory#claude-isnt-following-my-claudemd).
* The local contract also says same-level conflicts must be surfaced rather than silently selected (`/local_disk0/codexwork/bundle/claude/AGENTS.md:118-132`), but that is behavioral prompt text, not deterministic loader enforcement.

Therefore, I used this strict test:

1. The two texts prescribe incompatible behavior in one concrete situation.
2. At that decision point, loader/dispatch mechanics make one side unavailable or select a same-name definition deterministically.
3. The winner is established by a primary runtime contract or an executable local mechanism, not by guessing what the model will prefer.

If both texts are loaded, I report the conflict separately but do **not** call it a verified silent override.

### Concrete collision

Start a fresh Claude session in a repository and enter:

```text
/model-route implement a bounded API endpoint with tests
```

The command requires an immediate recommendation and says Sonnet is the default for implementation. No source file needs to be read to produce that recommendation. The contrary rule applies only after Claude reads one of its listed source extensions. Markdown task text, `package.json`, a GitHub issue, or the command itself does not match that frontmatter.

### Runtime winner

**The command wins at the routing decision point.** This is a loader result, not a model-preference inference: the command body is expanded for the turn, while `performance.md` has not yet met its documented path trigger. The Opus rule cannot participate in the first recommendation and is dead text for that decision. It may load later after a source read, but that does not retroactively change a recommendation or already-spawned worker.

Confidence: **almost certain (90-99%)**, supported by the exact `paths` guard, the command requiring output before any file operation, and Anthropic's documented lazy-load behavior. The residual uncertainty is that an already-running session may previously have read matching source and retained the rule; that does not affect the fresh-session collision above.

The corpus independently makes the conflict operational rather than hypothetical: `corpus.json:capability_use.skills_invoked` records one `start-task` invocation and the prior audit's bounded session evidence records model fragmentation; however, the corpus does not expose enough raw turn content to prove that `/model-route` itself was invoked. I therefore do not claim historical frequency for this exact command.

### Minimal resolution

#### BUILD-SMALL — make model routing unconditional and single-source

Move `performance.md:23-35` into a new unscoped `rules/common/model-routing.md` (or remove only the `paths` frontmatter from `performance.md`), then replace `commands/model-route.md:9-14` with a pointer/summary that exactly matches it: Opus for substantive implementation/refactor/review/research/orchestration; Haiku only for trivial mechanical work; named Sonnet exceptions only if the owner actually wants them.

This is **very likely (80-90%)** to eliminate the silent override because both entry paths would carry one identical policy before routing; evidence is the native unconditional-rule loader. It is under 200 lines and rides the existing rules/command bus. It introduces none of the rejected architectures.

Why not merely change Sonnet to Opus in the command? That fixes this one command but leaves the same policy path-scoped for every other early router. Making the timing-correct rule unconditional is the smaller systemic repair.

This is **almost certain (90-99%)** to close the demonstrated route because the gate becomes present before any command and the committing branch invokes the proper verification mode. Evidence is the unconditional loader plus the command's explicit branch. It is a small prompt/config edit on the existing bus and does not add a runtime.

## Design conclusion

The radical-but-supported conclusion is not to add an instruction-precedence engine. The current native bus already provides the missing deterministic boundary:

* Unconditional rules for policy that must exist before a task reads files.
* Path rules for language/file idioms only.
* Commands/skills for procedures, with their thresholds and routes resolved from the unconditional policy rather than duplicated.
* Hooks only for actions that truly must be enforced every time.

That architecture satisfies the anti-overfit gate. It uses Claude Code's existing rule/skill/hook mechanisms and does not introduce a second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

The minimal coherent edit set is therefore:

1. Unscope global-timing policy: model routing and pre-commit gates.
2. Remove duplicate policy tables from `/model-route` and `/start-task`.
3. Parameterize `/test-coverage` from `.coverage-thresholds.json`.
4. Make all behavior-changing command flows state test-before-code explicitly.
5. Retire or rewrite the five stale cross-vendor wrapper commands after the named Windows dependency probe.
6. Normalize HIGH severity to one action.

Implementing those edits is **very likely (80-90%)** to remove the two proven silent paths and the five nondeterministic collision families, based on direct elimination of duplicated or mistimed instructions. End-to-end adherence remains **UNVERIFIED; the settling experiment is the fixture suite below**, because prompt consistency improves model behavior but is not enforcement.
