# T004 — Competitive teardown: Roo Code

**Unit:** T004  
**Date:** 2026-07-19  
**Subject version researched:** Roo Code repository final commit `b867ec9145750d0ae1ff7f02d35406e9bf2a0b16` (2026-05-15); Roo Code Docs commit `a676c4173ae60348095efaebfd1292a9617622c0` (2026-04-21).  
**Scope:** agent loop, context management, memory, tools/MCP, permissions, customization, multi-agent behavior, verification/self-check, and concrete port recommendations.

## Executive verdict

Do **not** replace the owner's Claude/Codex harness with Roo Code. Roo Code was shut down on 2026-05-15 and its main repository is archived/read-only; the final README explicitly directs users to community alternatives. This is not merely a stale-doc inference: the [final source README says the extension was shut down](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/README.md#L87-L94), and GitHub marks the repository archived. A discontinued IDE extension cannot be the foundation of a frontier 2026 harness.

Mine Roo for mechanisms instead. Four are worth porting in bounded form:

1. **Pre-edit recoverability:** task-scoped shadow-Git checkpoints, with diff plus separate “files only” and “files + conversation” rewind semantics.
2. **Visible context economics:** explicit input/reserved-output/safety-budget telemetry, user-triggered condensation, before/after token counts, and a visible retained summary.
3. **Edit feedback:** capture VS Code diagnostics before an edit, wait briefly, and report only newly introduced errors.
4. **Capability-local permissions:** separate workspace/outside-workspace reads and writes; longest-prefix command allow/deny rules; per-MCP-tool grants; explicit disabled servers/tools.

Roo is worse than this harness in three strategically important ways:

* It has no native cross-task semantic memory comparable to the owner's `basic-memory` plus objective event ledger.
* Its Orchestrator is a paused-parent, isolated-child, summary-return tree—not a live peer team. It is principally sequential, while the owner's harness has parallel Codex fan-out and a live mailbox.
* It exposes no public agent-lifecycle hook bus comparable to the owner's SessionStart/UserPromptSubmit/PreToolUse/PostToolUse/Stop/compaction/subagent/task events. Its experimental custom tools are always auto-approved, which is actively unsafe to copy.

The final Roo release is still useful evidence because it captures a mature Cline-derived agent design immediately before shutdown. It is **almost certain (90-99%)** that selective adoption is better than product replacement: evidence is the shutdown/archive, plus the direct feature-by-feature comparison below. The remaining 1-10% covers a maintained community fork becoming materially better; that possibility was not evaluated because this unit is specifically Roo Code.

## 1. Agent loop

### Roo mechanism

Roo uses a conventional model/tool/result loop inside a VS Code extension:

1. Start a task and initialize checkpointing in the background.
2. Dynamically construct the system prompt from mode, available tools, MCP state, environment, and custom instructions.
3. Add user content plus fresh environment details.
4. Call the selected model/provider and stream text, reasoning, and native tool calls.
5. Validate and dispatch each tool call; append a structured `tool_result` carrying the same tool-use ID.
6. Call the model again with results.
7. Continue until `attempt_completion`, user abort, or request/error policy ends the loop. If the model emits no tool, Roo explicitly prompts it to complete or continue.

This is source-grounded. [`Task.initiateTaskLoop`](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2425-L2458) documents and implements the loop. [`recursivelyMakeClineRequests`](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2461-L2525) is actually an explicit stack/while loop despite the legacy name. Native tool-call parsing and ID de-duplication occur in [`Task.ts`](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2802-L2920), while validation and dispatch begin in [`presentAssistantMessage.ts`](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/assistant-message/presentAssistantMessage.ts#L295-L440).

Roo added parallel tool calling in v3.46: a model response can batch independent reads/searches/edits rather than spending one model round trip per tool. The immutable [v3.46 release notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.46.0.mdx#L14-L18) are the primary release evidence. This is tool concurrency, not concurrent agents.

Roo also has a configurable consecutive-mistake limit. When exceeded, it asks the user for guidance and resets the counter ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2483-L2501)). Empty responses get bounded retry/backoff and then a user decision ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L3550-L3617)).

### Comparison

Roo's loop is deliberately small and legible. That aligns with the anti-overfit gate: model → tools → results → model, with a few bounded recovery controls. The owner's harness already rides Claude/Codex native loops and has a two-strike pivot rule (`AGENTS.md:51-57`). Replacing the loop would add a second runtime and violate the anti-overfit gate.

Roo's native parallel tool batching is useful only where the active provider/runtime does not already offer it. The owner already uses parallel tool orchestration and Codex fan-out (`CLAUDE.md:19-42`), so this is not a clear gap.

### Port decision

**NATIVE (Claude Code already does this; we just enable it):** retain the native Claude/Codex agent loops and their native parallel tool/subagent APIs. Do not port Roo's TypeScript loop. It is **almost certain (90-99%)** that a second loop would reduce reliability: evidence is the owner's explicit anti-overfit constraint, the already-operational native tool buses, and Roo's own large provider/streaming compatibility surface.

**CONFIG (settings/JSON only):** set finite retry/mistake ceilings where the native provider exposes them, and preserve the owner's existing two-strike pivot. Do not create a learned critic or durable-execution layer.

## 2. Context management

### Roo mechanism

Roo builds context dynamically on every interaction. Its system prompt includes current mode, available tools, operational rules, and custom instructions; user messages are enriched with open tabs/files, cursor state, active terminals/output, modified files, time, mode, and an initial file listing. See the official [prompt structure](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/advanced-usage/prompt-structure.md#L26-L83).

Its strongest context features are:

* **Intelligent condensation:** summarize earlier conversation rather than abruptly drop it; preserve a first-message slash command; keep original history for rewind but use the summary in subsequent model calls ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/intelligent-context-condensing.mdx#L36-L47)).
* **Control and audit:** automatic threshold, custom condensation prompt, manual trigger, token counts before/after, cost, expandable retained summary, and a context bar showing used/reserved/available tokens ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/intelligent-context-condensing.mdx#L51-L92)).
* **Fallback recovery:** on a context-window error, truncate 25% and retry within the built-in retry limit ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/intelligent-context-condensing.mdx#L117-L140)).
* **Budget reservation:** documentation states a default reservation of 20% for model output and 10% safety, leaving 70% for history ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/intelligent-context-condensing.mdx#L144-L166)).
* **Bounded reads:** v3.46 defaults file reads to 2,000 lines, supports offset/limit paging, and can retrieve an indentation-bounded containing function/class. Large terminal output is clipped in context but stored as a searchable/pageable artifact ([v3.46 notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.46.0.mdx#L20-L27)).
* **Semantic code retrieval:** optional Tree-sitter chunking, embeddings, and Qdrant-backed `codebase_search` ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/codebase-indexing.mdx#L28-L43)).

### What is better than ours

The owner's harness has an auto-compaction threshold and PreCompact/PostCompact hooks (`settings.json:18`, `:380-404`) plus semantic memory, but the supplied bundle does not demonstrate Roo-like user-visible context accounting, a manual condense control, or an inspectable before/after summary. Roo's observability is the real gap—not generic summarization.

Roo's bounded file reads and output artifacts directly target context blowups. They are attractive given the corpus's high Glob and shell failure rates, although they do not solve the measured orphan-plugin `ENAMETOOLONG` root cause.

### What is worse than ours

Condensation is lossy and self-referential. Roo's docs admit only the summary proceeds, and its release history contains repeated condensation fixes: duplicate condensed content, silent zero-token failure, and summary loss on resume ([v3.44 notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.44.0.mdx#L29-L35), [v3.48 notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.48.0.mdx#L41-L46)). The owner's objective event ledger explicitly treats replayed events—not an in-context summary—as ground truth (`AGENTS.md:28-34`). That is stronger continuity.

Roo's Qdrant code index is exactly the kind of vector-DB component the anti-overfit gate rejects. It also requires an embedding provider plus Qdrant. Do not copy it; native `rg`, code search, MCP retrieval, and fresh file reads are simpler.

### Port decisions

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): context-compaction receipt.** Extend the existing PreCompact/PostCompact path to record: pre/post estimated tokens, active goal, files changed, unresolved errors, decisions, and the exact retained summary permalink in the event ledger. Expose it through a small slash command/skill. It is **very likely (80-90%)** to improve recoverability because Roo demonstrates the value of visible condensation receipts and the owner already has both event-ledger and compaction hook buses. Exact pre/post token fields are **roughly even (45-55%)** to be present in both hook payloads: the config proves both events exist but the payload schema was unavailable. If absent, store provider-reported fields plus an explicit “unavailable,” not an estimate presented as fact.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): output artifact pointer.** For shell outputs above a conservative threshold, retain head/tail in context and write the full output to the existing run log/artifact path, returning a stable path and search command. It is **very likely (80-90%)** to reduce context waste: evidence is Roo's production mechanism and the owner's existing `longrun` terminal-state contract (`AGENTS.md:36-49`).

**NATIVE (Claude Code already does this; we just enable it):** prefer native bounded reads and tool-search/progressive disclosure where present; do not layer a Qdrant index.

## 3. Memory and persistence

### Roo mechanism

Roo persists per-task conversation history and can reopen it. v3.49 moved each task to its own file with cross-process locking to prevent multi-window overwrite ([release notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.49.0.mdx#L31-L34)). It also persists task todo state into environment details, retains condensation summaries, and stores checkpoints per task.

That is **task persistence**, not durable semantic memory. Roo has no native store for owner preferences, decisions, supersession, failures, and recall across unrelated tasks. “Codebase indexing” retrieves code, not episodic/semantic user memory. “Checkpoint” snapshots files, not knowledge.

### Comparison

The owner is materially ahead: `basic-memory` provides durable semantic recall/capture with temporal supersession (`CLAUDE.md:5-11`), and the event ledger provides objective replay (`AGENTS.md:28-34`, `:85-91`). Roo's isolated subtask only returns a summary and does not share memory with siblings.

### Port decision

**NATIVE (Claude Code already does this; we just enable it):** keep `basic-memory` and the event ledger; make their use reliable rather than adding Roo-style task files as a competing memory authority. No vector DB/KG memory proposal is made; the existing semantic memory is already in scope and Roo contributes nothing better here.

## 4. Tools and MCP

### Roo mechanism

Roo exposes native file, search, command, mode, subtask, todo, skill, image, and MCP tools. By the end it had fully native tool calling; malformed/missing tool IDs become structured errors rather than executions ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/assistant-message/presentAssistantMessage.ts#L295-L318)). Duplicate results are guarded, and a tool failure is tracked for completion gating.

MCP configuration is global (`mcp_settings.json`) or project-local (`.roo/mcp.json`), with project names overriding global names. Each server can specify transport, command/URL, environment, working directory, timeout, watch paths, automatic grants, disabled status, and disabled tools. Roo supports stdio, Streamable HTTP, and legacy SSE; see [official configuration](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/mcp/using-mcp-in-roo.mdx#L25-L110) and [transport details](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/mcp/server-transports.md#L15-L107).

Roo can globally disable MCP, removing MCP logic and definitions from the system prompt. It can disable individual tools and remembers per-tool allow grants. Later releases warned when too many MCP tools were enabled ([v3.42 notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.42.0.mdx#L18-L22)). v3.48.1 fixed first-turn MCP availability by awaiting server connections before returning the hub ([release notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.48.1.mdx#L12-L18)); final source awaits the MCP hub and connection state before system-prompt generation ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L3633-L3653)).

Roo also offered experimental in-process TypeScript/JavaScript custom tools from `.roo/tools` and `~/.roo/tools`, dynamically transpiled and Zod-validated. Critically, they run **without approval** whenever enabled, return strings only, cannot interactively prompt, and have unreliable hot reload ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/experimental/custom-tools.md#L13-L35), [limits](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/experimental/custom-tools.md#L132-L141)).

### What is better than ours

The corpus records a dead Tavily MCP still being called 135 times as “not connected.” Roo's explicit `disabled`, `disabledTools`, prompt removal, tool-count warning, and connection-await behavior form a concrete capability hygiene pattern. The owner has broad MCP allow entries (`settings.json:47-60`), but a permission allow is not a health signal.

Per-server timeouts, watch-path restart, and project override are also clean mechanisms. However, “restart when watched files change” is not health-based restart and would not alone solve a remote dead service.

### What is worse than ours

Roo's custom tool execution model bypasses approvals and executes repository-supplied code inside the extension host. Combined with Roo's support for project-local configuration, that increases untrusted-repository risk. The owner's contract explicitly warns that cloned repo agent configuration and hooks are untrusted (`AGENTS.md:99-106`). Do not copy Roo custom tools.

Roo's UI/catalog breadth does not establish runtime reliability. Its own release notes repeatedly fix MCP schema, first-turn availability, tool naming, image results, and config serialization. The owner's corpus provides actual call/error rates; Roo offers no comparable local historical evidence in this unit.

### Port decisions

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): MCP capability admission.** At session start, enumerate configured servers, perform protocol-level initialization/list-tools with a short deadline, and create a session-local allow roster containing only responsive servers/tools. A failed server is removed from model-visible routing for the session and reported once with the exact failure. It is **very likely (80-90%)** to eliminate repeated “not connected” calls because the measured Tavily defect is precisely continued routing to an unavailable server, and Roo demonstrates prompt-level disabling and readiness gating. This must be a thin dispatcher/hook change, not an MCP supervisor daemon.

**CONFIG (settings/JSON only):** immediately disable/remove the known-dead `claude_ai_Tavily` route and configure per-server/per-tool timeouts and grants using the existing provider's native controls. This is an evidence-backed repair, not a Roo dependency.

**NATIVE (Claude Code already does this; we just enable it):** use MCP tool search/progressive disclosure rather than injecting all 93 touched servers/tools into every prompt. `ENABLE_TOOL_SEARCH=auto:5` is already present at `settings.json:17`; verify its effective roster in a separate build/verification unit.

## 5. Permission model

### Roo mechanism

Roo asks for approvals by default and exposes separate automatic grants for reads, writes, commands, MCP, mode switches, subtasks, and follow-up default answers. Reads and writes outside the workspace need additional switches. Writes to `.roo/` and `.rooignore` are protected unless separately enabled. MCP auto-approval requires both a global setting and per-tool `alwaysAllow`. The [permission matrix and workspace controls](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/auto-approving-actions.mdx#L55-L151) are unusually clear.

For commands, Roo uses prefix allow and deny lists with longest-prefix resolution; an equally or more specific deny wins. It also blocks dangerous parameter/process substitutions even under an allowed prefix. The docs recommend narrow prefixes such as `python -m pytest`, not `python` ([command policy](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/auto-approving-actions.mdx#L256-L299)).

`.rooignore` applies gitignore-like patterns to file tools, mentions, listing, and a predefined set of command-line readers, but the docs explicitly say it is workspace-only and **not a full sandbox**; its command inspection does not comprehensively cover uncommon utilities or custom scripts ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/rooignore.md#L72-L112)).

Custom modes additionally restrict tool groups (`read`, `edit`, `command`, `mcp`) and can constrain edits with a file regex ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/custom-modes.mdx#L268-L306)).

### Comparison

Roo's granularity and UI are better than the owner's current broad `bypassPermissions` setting (`settings.json:71`) plus a small deny list (`:64-69`). Particularly valuable are separate outside-workspace flags, longest-specific-prefix command rules, and two-level MCP grants.

The owner's semantic guards can be stronger in principle because PreToolUse sees structured calls, but current live defects show some guards scan prose/payload rather than the operation and generate false verdicts (`INPUT-known-harness-defects.md:9-107`). Roo's prefix matching is also lexical, but it is at least scoped to the command field rather than arbitrary prose.

Roo remains weaker than a true sandbox, and custom tools defeat its otherwise granular approval story.

### Port decisions

**CONFIG (settings/JSON only):** replace broad automatic execution with capability-local native grants: workspace read, workspace edit, narrow test/build command prefixes, explicit MCP tools, and separate approval for outside-workspace access. It is **very likely (80-90%)** to reduce blast radius; evidence is Roo's mature split and the owner's present `bypassPermissions` configuration. Preserve usability by auto-approving low-risk reads and known test commands rather than prompting for everything.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): structured command policy.** Normalize the actual tool verb and command AST/tokens, then apply longest-specific allow/deny rules plus substitution detection. Never scan markdown payload prose. It is **very likely (80-90%)** to reduce both false positives and dangerous over-broad grants because the known defect directly identifies use-vs-mention failure and Roo supplies a concrete specificity mechanism. This should share the discriminator requested by known defect D1, not create another guard.

## 6. Customization surface: modes, rules, skills, commands, tools, hooks

### Roo mechanisms

**Modes.** Global or project `.roomodes` define name, description, role, `whenToUse`, custom instructions, tool groups, and edit-path regex. Project modes fully override a global/default mode of the same slug. Modes remember the last model used (“Sticky Models”). Modes and their rule files can be exported/imported as one YAML bundle ([custom mode overview](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/custom-modes.mdx#L31-L80), [import/export](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/custom-modes.mdx#L83-L153)).

**Rules.** Roo aggregates global and workspace rules, generic and mode-specific. Directories are recursive and alphabetically ordered; workspace rules follow global rules. It supports root `AGENTS.md`/`AGENT.md` and, in v3.47, `AGENTS.local.md` personal overrides. Exact prompt order is documented in [Custom Instructions](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/custom-instructions.md#L189-L260).

**Skills.** Roo implements Agent Skills-style progressive disclosure: index only name/description, load full `SKILL.md` when selected, then load bundled resources on demand. It supports global/project, Roo-specific/cross-agent `.agents`, generic/mode-specific directories, explicit precedence, symlinks, and watchers ([skills mechanism](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/skills.mdx#L25-L70), [precedence](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/skills.mdx#L149-L190)).

**Slash commands.** Markdown files in `.roo/commands` or `~/.roo/commands` are reusable prompt workflows; project overrides global, and frontmatter can describe arguments and select a mode ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/slash-commands.mdx#L24-L105)).

**Custom tools.** In-process TS/JS, Zod schema, global/project override, no approval; discussed above.

**Hooks.** Roo has no public pre/post-tool/session/stop hook equivalent. Internal event emitters are not a user customization surface.

### Comparison

The owner already has the important parts and often more: specialized agents with per-agent tools/models/memory, cross-agent rules, hundreds of installed skills, slash workflows/plugins, MCP, and a much richer lifecycle hook bus. Roo's portable mode packaging and deterministic precedence are cleaner ergonomics, but not a missing execution capability.

Roo's progressive disclosure is directly relevant to the measured 78-used-of-~355-installed skill distribution. Yet the owner already sets `skillListingBudgetFraction=0.02` and enables tool search (`settings.json:2-17`), so the need is to verify and tune existing discovery—not clone Roo.

### Port decisions

**CONFIG (settings/JSON only):** standardize specialist agents on the existing frontmatter fields already demonstrated by `code-reviewer.md` and `architect.md`; add a deterministic precedence document and collision check for global/project rules and skills. Roo's YAML import/export is unnecessary if these remain versioned files.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): capability collision linter.** At startup/config change, detect duplicate agent/skill/command identifiers, show which layer wins, and flag invalid frontmatter without loading full skill bodies. It is **likely (55-80%)** to reduce silent shadowing and prompt bloat: Roo's explicit eight-level skill precedence demonstrates the mechanism, while the owner's installed/used disparity shows discovery pressure. The confidence is lower because the corpus does not quantify collision failures.

**Do not port:** Roo custom tools. Their automatic approval and repo-local code loading conflict with the owner's untrusted-repo rule and would enlarge the attack surface.

## 7. Multi-agent support

### Roo mechanism

Roo's built-in Orchestrator/Boomerang mode decomposes a task, invokes `new_task` in a chosen mode, pauses the parent, gives the child a fresh isolated history, and resumes the parent with only the child's `attempt_completion.result`. Context travels down in the new-task message and up in the completion summary. Approval is required at create/complete unless auto-approved ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/boomerang-tasks.mdx#L34-L67)). Source confirms child completion reopens the parent with `completionResultSummary` ([AttemptCompletionTool](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/tools/AttemptCompletionTool.ts#L82-L128), [delegation](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/tools/AttemptCompletionTool.ts#L148-L177)).

The Orchestrator intentionally lacks file, command, and MCP tools by default to keep its context clean; a user may override the mode ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/boomerang-tasks.mdx#L77-L113)). v3.48 added an arbitrary-depth task tree UI but also fixed multiple parent-history/status race conditions ([release notes](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/update-notes/v3.48.0.mdx#L24-L43)).

Roo did not ship parallel specialist agents. The design pauses the parent for the child, and a still-open enhancement at shutdown requested parallel specialized agents. This is a product limitation, not the same thing as parallel tool calls.

### Comparison

The owner is substantially ahead: parallel cross-vendor Codex fan-out returns native tool results (`CLAUDE.md:19-42`), while live peer messaging provides mid-turn dialogue and file leases (`:44-67`). The owner's structured-handoff rule (`AGENTS.md:59-62`) has the same good isolation principle without Roo's sequential-only constraint.

Roo's one-summary return is brittle: omitted child facts disappear. The owner's D4 shows a different orchestration risk—fabricated constraints propagated to ~15 prompts (`INPUT-known-harness-defects.md:151-160`). Roo does not solve provenance or challengeability; its example even says parent-specific instructions supersede a child's general instructions.

### Port decision

**NATIVE (Claude Code already does this; we just enable it):** retain native subagents/agent teams and existing Codex MCP fan-out. Adopt only Roo's typed handoff shape: goal, scope, supplied evidence, permissions, completion criteria, and concise result with artifact paths. Do not build another orchestrator.

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): provenance-bearing delegation envelope.** Every orchestrator-supplied “fact” should carry `observed | inferred | user-specified`, evidence path/probe ID, and freshness; children must re-probe load-bearing observed claims when cheap. It is **very likely (80-90%)** to prevent recurrence of D4 because D4's failure was an untraceable fabricated constraint, and Roo's isolated context makes explicit handoff metadata the natural control point.

## 8. Verification and self-check

### Roo mechanisms

Roo has several useful local checks:

* **Diagnostics delta:** capture diagnostics before an edit, wait for VS Code diagnostics after the edit, and surface only new errors. Users can inject all workspace errors/warnings via `@problems` ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/diagnostics-integration.md#L20-L69)).
* **Completion gate:** `attempt_completion` refuses to complete if any tool failed in the current turn. Optionally it also blocks while todos remain incomplete ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/tools/AttemptCompletionTool.ts#L38-L68)).
* **Mistake counter:** repeated invalid/missing tool parameters increase a counter; reaching the configured limit asks for user guidance.
* **Todo gate:** `roo-cline.preventCompletionWithOpenTodos` is opt-in; default false ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/task-todo-list.mdx#L166-L201)).
* **Checkpoints:** enabled by default, use a separate shadow Git repository, snapshot at task start and before file modification, show diffs, and restore files alone or files plus subsequent task conversation ([docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/checkpoints.mdx#L40-L75), [restore semantics](https://github.com/RooCodeInc/Roo-Code-Docs/blob/a676c4173ae60348095efaebfd1292a9617622c0/docs/features/checkpoints.mdx#L118-L143)). They are not created before command execution, ignore some large/sensitive/build files, disable on nested repos, and can overwrite unsaved work.
* **Human acceptance:** top-level `attempt_completion` asks the user to accept or provide feedback; feedback returns to the loop ([source](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/tools/AttemptCompletionTool.ts#L131-L143)).

### What is better than ours

Diagnostics delta and automatic pre-edit snapshots are concrete, low-friction checks not demonstrated in the supplied owner bundle. The checkpoint UI also binds code state to conversational state, which makes alternate implementations and rollback understandable.

### What is worse than ours

Roo does not provide an independent verifier, fresh-context review, required test execution, or evidence-backed done criterion. “No tool failed in the current turn” is much weaker than “the requested behavior was verified.” Open todos are self-reported and the completion gate is off by default. Diagnostics cover only language-server-visible errors, not behavioral regressions.

The owner's contract demands a generator/critic pass (`AGENTS.md:72-83`) and terminal-state outputs (`:36-39`), though these are prompt rules rather than independently proven enforcement. Roo's checks are complementary controls, not replacements for actual tests.

### Port decisions

**UNVERIFIED — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): diagnostics delta hook.** On an edit, snapshot relevant VS Code/language-server diagnostics, wait a configurable short interval, then inject only newly introduced errors with file/line. It is **likely (55-80%)** to catch cheap regressions without large prompt cost; evidence is Roo's mature mechanism. Direct diagnostic access through the current Claude/IDE bus is **roughly even (45-55%)**: VS Code is present, but no diagnostic endpoint was demonstrated in the supplied bundle. The settling experiment is a deliberate one-line type error, capturing hook payloads and configured language-server/MCP results. Use the existing endpoint only if that experiment finds one; otherwise omit rather than build a daemon.

**UNVERIFIED — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): bounded pre-edit safety snapshot.** Before the first write in a task and before high-risk multi-file edits, create a task-scoped Git object/ref or patch bundle outside the working tree; return diff and explicit restore commands. It is **likely (55-80%)** to improve recoverability because Roo's mechanism is mature and the owner has pre-tool/worktree buses. Safe behavior across the owner's Windows paths, nested repositories, and concurrent agent edits is **roughly even (45-55%)** because those topologies were not runnable on this Linux node. The settling experiment is a disposable Windows worktree test covering untracked files, nested repos, concurrent writers, and restore without disturbing the user's index.

**CONFIG (settings/JSON only):** require incomplete todos to block declared completion only for tasks that actually created a plan; pair it with real test/verification evidence. Do not equate checklist completion with correctness.

## Priority order

1. **MCP admission and dead-route suppression.** It directly addresses the top measured reliability defect (dead Tavily still called).
2. **Structured command policy shared by all guards.** It directly addresses D1's confirmed use-vs-mention correctness defect and Bash quoting pressure without adding another independent guard.
3. **Context-compaction receipts and output artifact pointers.** These ride current hooks/logs and improve long-run auditability.
4. **Diagnostics delta.** Cheap, local verification if the existing IDE/MCP bus exposes diagnostics.
5. **Bounded pre-edit snapshot.** Valuable, but test carefully on Windows, worktrees, untracked files, and concurrent agents.
6. **Capability collision linter and delegation provenance.** Useful hygiene after the measured reliability failures are addressed.

## Anti-overfit gate

Every positive proposal above rides an existing native configuration, hook, skill, MCP, event-ledger, or worktree bus. None introduces a second orchestration runtime, vector-DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Roo's Qdrant code index would violate the vector-DB rejection and is explicitly rejected. Porting Roo's TypeScript agent loop would create a second orchestration runtime and is explicitly rejected. A permanent checkpoint daemon would be BUILD-LARGE and is not proposed; the bounded snapshot proposal is a hook-invoked Git/patch operation only.

## Gaps and limits

* The Windows-only live subject paths do not exist on this Linux worker. Comparisons use the supplied unpacked bundle. It is **roughly even (45-55%)** that at least one feature absent from this intentionally bounded bundle exists elsewhere on the Windows host; evidence is that the bundle is a curated subject snapshot rather than a disk image. Such features are not claimed absent globally.
* Roo was not run interactively against a live provider. Product behavior is grounded in final official docs, final source, and changelogs; latency, approval UX, and empirical error rates were not benchmarked.
* Roo's own production telemetry and private cloud behavior were unavailable. No claim is made that documented features were reliable at corpus scale.
* The official docs repository's last commit predates the code shutdown by several weeks, but it contains release notes through v3.50 and the shutdown notice. Source claims use the final code commit where material.
* The corpus's hooks section is detector-broken and was treated as no data. Hook comparisons use concrete configuration/source, not corpus hook counts.
* **UNVERIFIED:** exact Claude/Codex availability of pre/post token fields needed for a precise compaction receipt is **roughly even (45-55%)**; both hooks are configured but their payload schema was unavailable. The settling experiment is one controlled compaction that captures native hook payloads before and after and compares them with the UI/API usage fields.
* **UNVERIFIED:** the existing Claude/IDE bus exposing diagnostic deltas without a new service is **roughly even (45-55%)**; VS Code is present but no endpoint was demonstrated. ## Bottom line

Roo Code's enduring lesson is not “build a bigger agent platform.” Its best mechanisms are small boundaries around a simple loop: visible context budgets, bounded inputs, explicit tool permissions, responsive-only capability rosters, diagnostic deltas, and recoverable edits. Those fit the owner's minimal-architecture principle.

The owner already surpasses Roo in the harder architecture: durable semantic plus objective memory, rich lifecycle hooks, native specialist agents, parallel cross-vendor fan-out, and live agent messaging. The right outcome is selective transplantation of four bounded controls—not Roo replacement, not a fork, and not another runtime.
