# P2A14 — Planning and decomposition: hierarchical planning, plan repair, and when explicit plans beat reactive loops

**Unit:** P2A14  
**Lens:** external research only  
**Research date:** 2026-07-18  
**Question:** What does the external evidence actually establish about hierarchical planning, plan repair, and the conditions under which explicit plans outperform reactive agent loops—and what should this owner's harness adopt?

## Executive conclusion

The evidence does **not** support a universal “plan first, then execute the whole plan” architecture. It supports a hybrid controller:

1. keep short, observable, reversible work in a reactive reason–act–observe loop;
2. require a small explicit plan for tasks with multiple dependent deliverables, interacting constraints, expensive actions, or work that must be handed off;
3. decompose **as needed**, especially after an executor demonstrates that a subgoal is too hard, rather than recursively expanding every task at the outset;
4. execute only the next plan frontier, then compare real tool/environment evidence with the expected postcondition;
5. repair the smallest invalid suffix of the plan while preserving achieved and still-valid work;
6. treat tests, tool results, file state, and user feedback as repair signals; do not treat ungrounded self-critique as a verifier;
7. impose depth, retry, and search budgets.

That conclusion is supported by four independent evidence families. ReAct demonstrates the strength of interleaving reasoning and environmental observations rather than committing to a closed-loop-free plan ([ReAct project and paper](https://react-lm.github.io/)). Plan-and-Solve shows that an explicit decomposition phase can reduce missing-step errors on bounded reasoning tasks ([ACL 2023 paper](https://aclanthology.org/2023.acl-long.147/)). ADAPT shows, under call-budget-matched interactive experiments, that recursive decomposition invoked after executor failure can substantially outperform flat ReAct and fixed plan-and-execute baselines ([NAACL 2024 paper](https://aclanthology.org/2024.findings-naacl.264.pdf)). Meanwhile, PlanBench and TravelPlanner show that fluent natural-language plans are frequently infeasible or constraint-violating and therefore cannot be trusted merely because they look coherent ([PlanBench](https://arxiv.org/abs/2206.10498), [TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe)).

The harness implication is deliberately small. Use native plan surfaces where they already exist; add a thin complexity gate, a compact plan contract, postcondition-based progress checks, and bounded local repair on the existing hook/tool bus. Do **not** add a second orchestration runtime, a general planner daemon, a tree-search service, a multi-agent hierarchy, or a learned critic.

## Method and evidence discipline

This unit intentionally did not inspect or infer from the local harness. The assigned value of this lens is external evidence. Sources were prioritized in this order: peer-reviewed conference proceedings; official project papers and repositories; official vendor engineering documentation; then recent preprints only for frontier hypotheses. Product documentation is treated as evidence that a mechanism exists, not as controlled evidence that it improves task success.

“Planning” is overloaded, so this report separates four mechanisms:

- **Planning surface:** an explicit, user-visible checklist or implementation plan.
- **Task decomposition:** splitting a goal into subgoals or easier calls.
- **Action planning/search:** selecting a sequence or tree of actions under an environment model.
- **Plan repair:** modifying a plan after observations invalidate an assumption, action, ordering, or constraint.

These mechanisms have different evidence. A checklist can improve coordination without establishing that an LLM can solve formal planning problems. A classical planner can guarantee a valid sequence in a correct symbolic model without solving perception, tool grounding, or model-construction errors. A search method can improve a benchmark while being uneconomical for routine coding. Conflating them is a major source of hype.

## 1. What is actually established

### 1.1 Reactive interleaving is a strong baseline when action reveals necessary state

ReAct interleaves reasoning traces, actions, and observations. Its stated purpose is not merely to “think step by step”: observations let the model update plans, handle exceptions, and acquire information that was unavailable before acting. On ALFWorld and WebShop, the paper reports absolute success-rate gains of 34 and 10 percentage points over the imitation/RL baselines used there, with one or two in-context examples ([ReAct project page](https://react-lm.github.io/); [official repository](https://github.com/ysymyth/ReAct)).

This establishes a narrow but important fact: for interactive tasks where tool calls disclose state, a loop that incorporates observations can be much better than generating an answer or action sequence without those observations. It does **not** establish that ReAct is always better than explicit planning. The relevant ADAPT experiments later beat ReAct on compositional tasks, and tree search improves over reactive baselines in some difficult web tasks ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf); [Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476)).

Practical boundary: when the next correct action depends primarily on the immediately preceding observation—search result, compiler error, test output, page state, filesystem discovery—a reactive step is information-efficient. A detailed action sequence written before that observation necessarily embeds guesses.

### 1.2 Explicit decomposition can improve bounded multi-step reasoning

Plan-and-Solve first asks the model to divide a task into subtasks and then execute them. Across ten datasets in arithmetic, commonsense, and symbolic reasoning, its GPT-3 experiments consistently outperformed the paper’s zero-shot chain-of-thought baseline and were comparable to or better than the evaluated zero-shot program-of-thought baseline; on mathematical reasoning they were comparable to eight-shot chain-of-thought ([ACL 2023 abstract and paper](https://aclanthology.org/2023.acl-long.147/)). The authors specifically target missing-step errors, while acknowledging that calculation and semantic errors require additional instruction.

This establishes that explicit planning can help when the problem is already specified, the decomposition is meaningful, and the output can be obtained by completing a bounded sequence of reasoning subtasks. It does not establish reliable long-horizon agency, tool selection, or recovery under changing state.

### 1.3 As-needed hierarchical decomposition can beat both flat reaction and a fixed up-front plan

ADAPT is the most directly relevant controlled result found. Its executor first attempts the current task. If execution fails, a planner decomposes the failed task, and the same controller recursively handles the subtasks up to a depth limit. Thus decomposition is conditional rather than mandatory ([NAACL 2024 paper, methodology](https://aclanthology.org/2024.findings-naacl.264.pdf)).

Using GPT-3.5-family models, ADAPT reported:

- WebShop success of 44%, versus ReAct 32%, fixed Plan-and-Execute 17%, Reflexion 35%, and the paper’s cited LATS result 38%;
- TextCraft success of 52%, versus ReAct 19%, fixed Plan-and-Execute 27%, and Reflexion 32%;
- up to 28.3 percentage-point improvement over ReAct on ALFWorld;
- larger gains on more compositionally difficult TextCraft recipes; and
- comparisons in which iteration budgets were increased for the executor-only baseline to keep LLM-call budgets comparable.

The tables, budget controls, and ablations are in the [ADAPT paper](https://aclanthology.org/2024.findings-naacl.264.pdf). The important mechanism is not “more hierarchy.” It is **selective escalation**: attempt an executable unit, decompose only the unit that fails, recurse only while useful, and cap depth.

This finding is bounded by old model families, three textual environments, task-specific demonstrations, and model-generated success heuristics. It is nevertheless stronger evidence for harness design than an architectural diagram or an uncontrolled agent demo.

### 1.4 Hierarchical decomposition is not synonymous with multi-agent delegation

Agentless applies a simple three-stage workflow—localization, repair, validation—and its localization is itself hierarchical: file, then class/function, then edit location. Its official repository reports 50.8% on SWE-bench Verified with Claude 3.5 Sonnet and exposes artifacts for reproduction ([Agentless repository](https://github.com/OpenAutoCoder/Agentless)). Regardless of later leaderboard movement, this is a concrete counterexample to the claim that hierarchy requires a supervisor and a team of agents.

Anthropic’s production guidance makes the same architectural distinction. Fixed prompt chains are recommended when a task decomposes cleanly into known subtasks; dynamic orchestrator–worker decomposition is positioned for cases where required subtasks cannot be predicted in advance; and agents are recommended only when flexibility justifies extra latency and cost ([Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents)). This is vendor experience rather than a controlled trial, but it is consistent with Agentless and the controlled task-decomposition literature.

### 1.5 Natural-language plan fluency is not plan validity

PlanBench was created because commonsense planning prompts make it difficult to distinguish actual planning from retrieval of familiar scripts. On formal planning domains, the evaluated LLMs fell short on plan generation and reasoning about action and change ([PlanBench paper and benchmark](https://arxiv.org/abs/2206.10498)).

TravelPlanner adds real-world information collection and interacting constraints. Its ICML 2024 evaluation reported only 0.6% success for GPT-4 under its strict final-pass criteria and attributed failures to losing task focus, incorrect tool use, and failure to track constraints ([TravelPlanner paper](https://openreview.net/forum?id=l5XQzNkAOe)). The absolute number is benchmark- and model-era-specific, but the failure mode is directly relevant: a plan can read plausibly while violating one constraint or omitting one dependency.

Therefore an explicit plan is an **editable hypothesis and coordination artifact**, not evidence of feasibility. Each material step needs an externally observable completion condition.

### 1.6 External solvers and verifiers help when the world can be represented faithfully

LLM+P converts natural-language planning problems to PDDL, invokes a classical planner, and translates the solution back. On the authors’ benchmark, it generated correct or optimal solutions for most problems while direct LLM baselines often failed to produce feasible plans ([LLM+P paper](https://arxiv.org/abs/2304.11477); [official code](https://github.com/Cranial-XIX/llm-pddl)). This establishes that delegating constrained search to a purpose-built solver can outperform asking an LLM to simulate that solver.

The limitation is equally important: correctness depends on the generated domain/problem representation matching reality. Coding and tool-use tasks rarely arrive with a complete action model, deterministic transitions, or a trustworthy PDDL translation. A classical planner is compelling for scheduling, dependency resolution, or formally modeled workflows; it is not a generic replacement for an interactive coding loop.

### 1.7 Plan repair works best when triggered by external evidence

Two peer-reviewed ICLR 2024 results delimit self-repair. “Large Language Models Cannot Self-Correct Reasoning Yet” found that intrinsic self-correction—asking a model to improve its reasoning without external feedback—generally failed and could degrade performance ([ICLR 2024 paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)). CRITIC, by contrast, lets models consult external tools while critiquing and reports gains from tool-interactive correction ([ICLR 2024 paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)).

The studies do not prove a universal law, but together with ReAct and ADAPT they establish the right default: repair from test failures, command results, observed state, constraint violations, or explicit user feedback. “Reflect again” without new evidence is not a reliable repair trigger.

### 1.8 Search can beat greedy reaction, but it spends test-time compute and needs a useful evaluator

Tree of Thoughts explores multiple reasoning paths, evaluates intermediate states, and backtracks. It improved results on Game of 24, Mini Crosswords, and a constrained creative-writing task relative to the paper’s prompting baselines ([NeurIPS 2023 paper](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html); [official repository](https://github.com/princeton-nlp/tree-of-thought-llm)). LATS combines tree search, an LM value function, environment feedback, and reflection; it reports gains in programming, QA, WebShop, and mathematics ([ICML 2024 paper](https://arxiv.org/abs/2310.04406); [official repository](https://github.com/lapisrocks/LanguageAgentTreeSearch)). A separate best-first search method applied to GPT-4o web agents reported relative success improvements of 39.7% on VisualWebArena and 28.0% on WebArena over the same agent without search ([Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476)).

What is established is conditional: branching search can improve difficult tasks with recoverable branches, a discriminative evaluator, and enough budget. These studies do not establish that tree search is cost-effective for ordinary code editing, nor that an LM’s self-score is reliable when no environment feedback exists.

### 1.9 Native planning surfaces already cover much of the coordination need

Claude Code’s official Plan mode is read-only: it explores with reads and commands, proposes a plan, accepts review/edits, and transitions to execution only after approval ([Claude Code permission-mode documentation](https://code.claude.com/docs/en/permission-modes)). Claude Code also exposes an `opusplan` alias that uses a more capable model during planning and a cheaper model during execution ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)).

Codex’s open-source base instructions expose `update_plan` as a short, status-bearing checklist and explicitly say plans help with complex, ambiguous, or multi-phase work but should not pad simple tasks ([OpenAI Codex source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)). Codex’s separate conversational Plan mode is explicitly distinguished from the `update_plan` progress checklist ([OpenAI Codex Plan-mode template](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md)).

This establishes that the harness need not build a new plan UI, plan store, or execution engine merely to obtain explicit plans and progress states.

## 2. What is promising but unproven

### 2.1 Complexity-gated planning is very likely to dominate “always plan” and “never plan”

**Confidence: very likely (80-90%).** Evidence: Plan-and-Solve and ADAPT show benefits on multi-step/compositional tasks; ReAct shows the value of observation-driven action; Anthropic recommends selecting workflows by task predictability and complexity; Codex’s own instructions warn against plans for simple work ([Plan-and-Solve](https://aclanthology.org/2023.acl-long.147/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [ReAct](https://react-lm.github.io/), [Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents), [Codex source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)).

UNVERIFIED for this owner: no external study tests the proposed gate against this owner’s task distribution and current model mix. The settling experiment is a randomized replay on a stratified sample of owner tasks comparing (a) reactive-only, (b) always-plan, and (c) the proposed gated policy on verified completion, cost, latency, intervention count, and repeated-action loops.

### 2.2 Repairing only the invalid suffix is likely better than wholesale replanning

**Confidence: likely (55-80%).** Evidence: ADAPT localizes additional decomposition to the failed subtask rather than restarting the whole trajectory; Microsoft’s Magentic mechanism tracks progress and replans after stalls; classical plan-repair research distinguishes repair from replanning and shows value in preserving commitments in shared settings ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [Microsoft Magentic orchestration](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic), [plan commitment and repair study](https://www.sciencedirect.com/science/article/pii/S0952197623004591)).

UNVERIFIED for coding/tool agents: the cited commitment study is not a coding-agent evaluation, and Magentic’s documentation explicitly says performance outside its original specialized design is untested. The settling experiment is to inject a controlled failure at plan steps 2, 4, and 6 and compare suffix repair versus full replan on preservation of completed work, redundant tool calls, constraint retention, and final success.

### 2.3 A two-level plan is likely enough for most harness tasks

**Confidence: likely (55-80%).** Evidence: ADAPT’s benefits increase with recursive depth on its environments, but it caps recursion; Agentless obtains strong coding results with a simple stage hierarchy and hierarchical localization; increasingly deep plans also create more generated assumptions and coordination overhead ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [Agentless](https://github.com/OpenAutoCoder/Agentless)).

UNVERIFIED: external work does not identify a universal optimal depth for heterogeneous desktop and coding tasks. The settling experiment is a depth ablation—flat, depth 2, depth 3, and unrestricted—measuring success, token/tool cost, stale-plan edits, and abandoned branches. Until then, depth 2 by default and depth 3 only after a demonstrated executor failure is a conservative hypothesis, not a fact.

### 2.4 Expected-postcondition checks are very likely more useful than prose status updates

**Confidence: very likely (80-90%).** Evidence: ReAct obtains ground truth from observations; Anthropic says agents should assess progress from environment ground truth such as tool or code-execution results; CRITIC’s gains rely on tool-interactive critique; TravelPlanner demonstrates how omitted constraints defeat otherwise plausible plans ([ReAct](https://react-lm.github.io/), [Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html), [TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe)).

UNVERIFIED: the best compact schema and model adherence rate for this harness are unknown. The settling experiment is a schema ablation comparing status-only steps against steps containing `deliverable`, `success_check`, and `evidence`, with machine scoring of false completion claims.

### 2.5 Search-on-failure is promising for high-value branches, not as the default controller

**Confidence: likely (55-80%).** Evidence: ToT, LATS, and web-agent best-first search improve hard benchmark performance, while each adds multiple candidates, scoring, and test-time computation ([Tree of Thoughts](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html), [LATS](https://arxiv.org/abs/2310.04406), [Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476)).

UNVERIFIED: no located study shows a favorable cost/success tradeoff for general owner workflows or compares bounded two-candidate branching against current frontier reasoning models on this task mix. The settling experiment is to invoke two-branch search only after a falsified step or repeated failure and compare marginal verified successes per extra model/tool call with a single evidence-grounded repair.

### 2.6 Planning/execution model specialization may be economical

**Confidence: likely (55-80%).** Evidence: Claude Code officially exposes `opusplan`, explicitly assigning a stronger model to plan mode and a cheaper model to execution; ADAPT reports gains when a stronger planner is paired with a weaker executor in one ALFWorld setting ([Claude model configuration](https://code.claude.com/docs/en/model-config), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf)).

UNVERIFIED: those results do not establish the optimal model routing for this owner, and stronger planners can still produce invalid plans. The settling experiment is a matrix of planner/executor model pairs on multi-phase tasks, scored on total verified success per dollar and repair count—not plan aesthetics.

### 2.7 Progress-ledger stall detection is promising as a small mechanism

**Confidence: likely (55-80%).** Evidence: Microsoft’s Magentic orchestration maintains a progress ledger, increments a stall counter for non-progressing rounds, and replans after a configured limit; its documentation exposes plan-created, replan, and progress events ([Microsoft Agent Framework documentation](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)).

UNVERIFIED outside Magentic-One: Microsoft explicitly states that the orchestration is untested outside the original specialized design. The settling experiment is a replay over known retry-loop trajectories comparing deterministic fingerprints plus evidence deltas against an LLM-only “are we making progress?” judgment.

## 3. What is hype, and how to tell

### 3.1 “Every nontrivial task should begin with a complete plan”

This is hype because it ignores information arrival. ReAct’s design and results show that actions and observations can be part of reasoning, while ADAPT’s fixed Plan-and-Execute baseline underperformed conditional decomposition on all three reported environments ([ReAct](https://react-lm.github.io/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf)). A complete plan created before repository exploration, test execution, search, or tool discovery encodes unknowns as facts.

Diagnostic: ask whether step 4 can be chosen correctly before seeing the output of step 1. If not, the appropriate artifact is a goal, constraints, and a short frontier—not a detailed end-to-end action script.

### 3.2 “A coherent natural-language plan proves the model can plan”

PlanBench was explicitly designed to separate script-like world knowledge from planning, and TravelPlanner shows near-total failure under strict interacting constraints despite models’ ability to produce fluent itineraries ([PlanBench](https://arxiv.org/abs/2206.10498), [TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe)).

Diagnostic: remove stylistic scoring. Check preconditions, constraint coverage, ordering, feasibility, and final state. If the plan has no mechanically or externally checkable postconditions, “plan quality” is mostly presentation quality.

### 3.3 “More hierarchy is more intelligence”

ADAPT supports bounded, failure-triggered hierarchy, not unrestricted recursive bureaucracy. Agentless shows hierarchy can be a small deterministic workflow rather than a hierarchy of personas ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [Agentless](https://github.com/OpenAutoCoder/Agentless)). Anthropic reports that its most successful customer implementations use simple, composable patterns rather than complex frameworks ([Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents)).

Diagnostic: count new failure surfaces—handoffs, duplicated context, synthesizers, role prompts, shared-state writes—and demand an ablation against one agent plus a checklist. If hierarchy has no measured marginal gain after equalizing model calls and tokens, it is architecture theater.

### 3.4 “Replanning means ask the same model to reflect”

Intrinsic self-correction frequently fails without external information, whereas tool-interactive correction has positive evidence ([ICLR intrinsic self-correction study](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)).

Diagnostic: identify what new falsifying information entered the repair prompt. If the answer is “none,” the loop is resampling, not evidence-based repair. It may help by luck, but it should not be described as verification.

### 3.5 “Tree search is a general agent upgrade”

ToT, LATS, and web-agent search demonstrate benchmark gains, but their gains rely on branching, evaluation, environment interaction, and increased inference. Their reported domains are selected precisely because search or planning is useful ([ToT](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html), [LATS](https://arxiv.org/abs/2310.04406), [web-agent tree search](https://arxiv.org/abs/2407.01476)).

Diagnostic: require a cost-normalized comparison against (a) one stronger model call, (b) one reactive loop with external validation, and (c) two candidate repairs. Also require an evaluator with demonstrated discrimination. Without those, a large search tree can multiply confident mistakes.

### 3.6 “A symbolic planner solves agent planning”

LLM+P is strong evidence for solver delegation **after** correct formalization. It is not evidence that an LLM reliably creates a faithful domain model from an open-ended repository, GUI, or web task ([LLM+P](https://arxiv.org/abs/2304.11477)).

Diagnostic: separate translation accuracy, planner validity, execution grounding, and outcome success. A valid plan over a wrong model is still wrong in the world.

### 3.7 “The leaderboard winner reveals the best harness architecture”

SWE-bench’s maintainers identified repository-state loopholes in which agents could inspect future commits that disclose solutions, demonstrating that end scores can be confounded by environment construction ([SWE-bench issue #465](https://github.com/SWE-bench/SWE-bench/issues/465)). Agentless’s simple pipeline also reached competitive results without a general autonomous planner ([Agentless](https://github.com/OpenAutoCoder/Agentless)).

Diagnostic: demand trajectories, equalized budgets, contamination controls, current model baselines, and ablations of the planning component. Do not infer architectural causality from an aggregate score.

## 4. Specific things this owner’s harness should adopt

Every recommendation below includes the required implementation classification and anti-overfit decision. Confidence describes the forward-looking expectation for this owner; each recommendation whose premise remains untested locally is marked UNVERIFIED in its heading.

### 4.1 Adopt a complexity-and-risk plan gate — UNVERIFIED

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Route a task to an explicit plan when **any** of these is true:

- three or more dependent deliverables are visible;
- success requires satisfying multiple interacting constraints;
- work spans distinct phases such as research → design → build → verify;
- an action is costly, externally consequential, hard to reverse, or requires approval;
- the result will be handed to another agent/person;
- estimated execution exceeds roughly five meaningful tool actions;
- the user explicitly requests a plan.

Stay reactive when all of these are true: one local outcome, next action is obvious, immediate tool feedback is available, actions are reversible, and there is a direct verifier.

**Confidence: very likely (80-90%).** Evidence: conditional decomposition outperforms fixed planning in ADAPT; reactive interleaving is strong in ReAct; official Anthropic and Codex guidance both select planning by task characteristics rather than universally ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [ReAct](https://react-lm.github.io/), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [Codex](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)).

UNVERIFIED: thresholds are heuristic. Settle with the randomized three-policy replay described in §2.1 and tune from false-plan and missed-plan cases.

**Anti-overfit gate:** passes. This is a small router on the existing instruction/hook bus, not a new runtime or learned classifier. Start as deterministic rules; do not train a plan router.

### 4.2 Use native plan surfaces, not a new plan subsystem

**Tag: NATIVE (Claude Code already does this; we just enable it).**

For complex or high-consequence Claude work, use native read-only Plan mode and its review/approval transition. For tasks where planning deserves a stronger model, evaluate native `opusplan`. The existence and behavior of both are official ([Plan mode](https://code.claude.com/docs/en/permission-modes), [`opusplan`](https://code.claude.com/docs/en/model-config)).

For Codex, use its native conversational Plan mode when collaborative design is required and its native `update_plan` checklist during execution. Do not confuse the two; OpenAI’s own template distinguishes them ([Codex Plan mode](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md), [`update_plan`](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)).

**Confidence: almost certain (90-99%).** Evidence: these features exist in official documentation/source and directly supply read-only planning, review, and status tracking. The remaining uncertainty is operational fit, not feature existence.

**Anti-overfit gate:** passes. This removes pressure to build a plan database, UI, daemon, or orchestration engine.

### 4.3 Standardize a compact executable plan contract — UNVERIFIED

**Tag: CONFIG (settings/JSON only).**

Plans should contain no more structure than:

```text
goal: one falsifiable terminal outcome
constraints: facts that every revision must preserve
steps:
  - id
  - deliverable
  - depends_on
  - success_check
  - status: pending | in_progress | complete | blocked | invalidated
  - evidence: empty until observed
assumptions: explicitly labeled, each with a probe
next_frontier: exactly one step, or independent steps if parallel-safe
revision_reason: evidence that changed the plan
```

Do not store hidden reasoning, verbose rationales, speculative future commands, or duplicate conversation summaries in the plan. A plan is a control surface and state summary.

**Confidence: very likely (80-90%).** Evidence: TravelPlanner exposes constraint-tracking failure; Anthropic emphasizes environment ground truth and visible planning; Codex’s native checklist uses concise steps and explicit statuses ([TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [Codex source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)).

UNVERIFIED: this exact schema has not been evaluated. Settle with the false-completion and adherence experiment in §2.4.

**Anti-overfit gate:** passes. It is a small data contract using native plan/checklist surfaces, with no durable-execution engine.

### 4.4 Plan at the goal level; choose actions at the observation frontier — UNVERIFIED

**Tag: CONFIG (settings/JSON only).**

Write stable subgoals and success checks up front. Detail only the next executable frontier. After each tool call, update evidence and select the next action from current state. Example: plan “identify failing boundary and reproduce it,” not six speculative shell commands whose validity depends on the first output.

**Confidence: very likely (80-90%).** Evidence: ReAct’s gains come from observation-interleaved reasoning; ADAPT conditionally decomposes only after a task proves difficult; PlanBench warns against treating generated action sequences as reliable plans ([ReAct](https://react-lm.github.io/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [PlanBench](https://arxiv.org/abs/2206.10498)).

UNVERIFIED: the ideal frontier width for this owner is unknown. Settle by comparing full action scripts, one-step frontiers, and subgoal frontiers on stale-step rate and success.

**Anti-overfit gate:** passes. This is an instruction-level policy on the existing tool loop.

### 4.5 Add bounded, evidence-triggered local plan repair — UNVERIFIED

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Trigger repair only when one of these occurs:

- the current step’s success check fails;
- a tool returns a terminal failure;
- an assumption is falsified;
- a new user constraint conflicts with the remaining plan;
- the same action/error fingerprint repeats without an evidence delta;
- the environment changes so a precondition no longer holds.

Repair protocol:

1. freeze completed steps whose postconditions still hold;
2. identify the earliest invalid step;
3. record the new evidence and violated assumption/constraint;
4. replace only the invalid step and dependent suffix;
5. re-check all global constraints;
6. permit at most two repairs at the same level before escalating, asking for authority, or stopping with evidence.

**Confidence: likely (55-80%).** Evidence: ADAPT redirects decomposition to failed subtasks; CRITIC supports tool-grounded correction; intrinsic self-correction evidence argues against evidence-free reflection; classical repair work supports preserving commitments ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html), [intrinsic self-correction study](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html), [plan-repair study](https://www.sciencedirect.com/science/article/pii/S0952197623004591)).

UNVERIFIED: suffix repair has not been tested on this owner’s trajectories. Settle with the controlled failure-injection experiment in §2.2.

**Anti-overfit gate:** passes. It is a bounded state transition on the existing hook/tool bus, not a durable-execution engine. The plan remains advisory and session-local.

### 4.6 Add deterministic progress and stall signals before LLM judgment — UNVERIFIED

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For each plan step, compute a small progress record from existing events:

- terminal tool result category;
- changed-file or changed-artifact set;
- test/check delta;
- new source/evidence count where relevant;
- repeated action/error fingerprint;
- plan step status transition.

Declare a stall only when two consecutive rounds show no new evidence or state delta, or when an identical terminal failure repeats. Then invoke repair, not blind retry. The LLM may explain the stall but should not be the sole detector.

**Confidence: very likely (80-90%).** Evidence: Microsoft’s Magentic design uses progress tracking and a stall threshold to trigger replanning, but its own documentation warns that generalization beyond the original design is untested; terminal environment evidence is also central in Anthropic’s agent guidance ([Microsoft documentation](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic), [Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents)).

UNVERIFIED: the two-round threshold and proposed signals need local calibration. Settle by replaying retry-loop and successful persistence trajectories and measuring precision/recall for harmful stalls.

**Anti-overfit gate:** passes only if implemented as deterministic event reduction. Do not import Magentic, create a supervisor agent, or add a monitoring service.

### 4.7 Use hierarchical decomposition as an escalation, capped at depth two by default — UNVERIFIED

**Tag: CONFIG (settings/JSON only).**

Attempt the current subgoal first when it is concrete and verifiable. If it fails because it is too broad—not merely because a command was mistyped—decompose into two to five child deliverables. Permit one further level only when a child again demonstrates compositional difficulty. Never expand a complete task tree speculatively.

**Confidence: likely (55-80%).** Evidence: ADAPT’s recursive, failure-triggered decomposition beats flat and fixed-plan baselines and shows gains with additional depth; its recursion is bounded. Agentless demonstrates useful hierarchy within a simple coding workflow ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [Agentless](https://github.com/OpenAutoCoder/Agentless)).

UNVERIFIED: depth two is a harness prior, not a research result. Settle with the depth ablation in §2.3.

**Anti-overfit gate:** passes. This is a bounded instruction rule; it does not introduce recursive agent spawning or a second orchestrator.

### 4.8 Separate decomposition from delegation

**Tag: CONFIG (settings/JSON only).**

A plan step should become a separate agent task only if it is genuinely independent, has a self-contained context package, and yields a mergeable artifact. Sequential dependencies remain in one agent loop. Parallelism is a scheduling decision, not proof of good decomposition.

**Confidence: very likely (80-90%).** Evidence: Agentless obtains hierarchical coding decomposition without multiple agents; Anthropic distinguishes fixed sectioning, parallelization, and dynamic orchestrator–workers and recommends each for different task topologies ([Agentless](https://github.com/OpenAutoCoder/Agentless), [Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents)).

**Anti-overfit gate:** passes. It explicitly prevents a default multi-agent hierarchy and second orchestration runtime.

### 4.9 Require external completion evidence for every material plan step

**Tag: CONFIG (settings/JSON only).**

Examples:

- code: relevant test, typecheck, build, or a minimal reproduction;
- research: primary-source citation supporting the claim;
- file operation: resolved target plus observed resulting state;
- configuration: parser/schema validation plus consumer recognition;
- deployment/external action: returned identifier and read-back where safe;
- analysis: explicit check against stated acceptance criteria.

Marking a step complete because the model says it “implemented” or “verified” it is insufficient.

**Confidence: almost certain (90-99%).** Evidence: Anthropic says agents need environment ground truth during execution; CRITIC finds value in tool-interactive correction; TravelPlanner and PlanBench show fluent plans can violate constraints or be infeasible ([Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html), [TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe), [PlanBench](https://arxiv.org/abs/2206.10498)).

**Anti-overfit gate:** passes. It uses existing tools and acceptance checks; no learned critic or guardrail framework is introduced.

### 4.10 Add a tiny planning evaluation slice before expanding architecture — UNVERIFIED

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Construct a replay suite containing at least:

- trivial one-step tasks where planning is overhead;
- multi-file coding changes with dependent edits;
- tasks with a hidden constraint revealed after the first tool call;
- tasks with a deliberately failing or missing tool;
- tasks where step 2 invalidates step 4;
- tasks with an irreversible action requiring approval;
- tasks whose correct response is “infeasible” or “need user input.”

Score: verified task completion, constraint preservation, false-complete rate, redundant calls, repeated-failure loops, plan revisions, latency, tokens/cost, and human interventions. Compare reactive-only, always-plan, and gated hybrid policies. Evaluate plans upstream as APB-style diagnostics only in addition to—not instead of—end-to-end execution ([Agent Planning Benchmark preprint](https://arxiv.org/abs/2606.04874)).

**Confidence: almost certain (90-99%).** Evidence: PlanBench exists because surface-level evaluation confounds planning with recall; TravelPlanner exposes constraint failures; the 2026 APB preprint explicitly separates plan diagnostics from execution and reports downstream gains from plan refinement, though that newest result remains preprint evidence ([PlanBench](https://arxiv.org/abs/2206.10498), [TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe), [APB](https://arxiv.org/abs/2606.04874)).

UNVERIFIED: the proposed slice size and composition are not calibrated to local frequencies. Settle by stratifying from the owner’s existing task corpus while keeping a held-out set.

**Anti-overfit gate:** passes. It is an evaluation fixture and scorer, not a trained critic or observability service.

### 4.11 Do not build a general tree-search/planner service now

**Tag: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).**

Recommendation: **reject at this stage.** Tree-search evidence is real but domain-bounded and compute-intensive; symbolic planning requires a faithful formal model; the owner’s anti-overfit gate explicitly rejects a second orchestration runtime and durable execution machinery. A daemon would duplicate native planning and tool-loop facilities before the small hybrid controller is evaluated ([ToT](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html), [LATS](https://arxiv.org/abs/2310.04406), [LLM+P](https://arxiv.org/abs/2304.11477), [Claude Plan mode](https://code.claude.com/docs/en/permission-modes), [Codex plan source](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md)).

**Confidence: very likely (80-90%).** Evidence: simpler conditional decomposition has direct positive results, native plan surfaces already exist, and no located external evidence demonstrates that a general planner daemon improves heterogeneous owner workflows after cost normalization.

This proposal fails the anti-overfit gate and is therefore rejected. Reconsider only if the evaluation slice shows a stable class of high-value failures where bounded two-branch search clearly outperforms stronger-model and local-repair baselines.

### 4.12 Do not build a learned critic, planning memory graph, or multi-agent planning hierarchy

**Tag: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).**

Recommendation: **reject.** A learned critic reintroduces a specifically excluded trained-critic component; a planning graph/vector store reintroduces excluded memory infrastructure; a multi-agent hierarchy adds coordination failure surfaces when decomposition alone is available. Intrinsic self-correction evidence also warns against assuming a model judge reliably repairs its own errors without external signals ([ICLR self-correction study](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html), [Agentless](https://github.com/OpenAutoCoder/Agentless), [Anthropic guidance](https://www.anthropic.com/engineering/building-effective-agents)).

**Confidence: very likely (80-90%).** Evidence: the excluded components add machinery without a demonstrated need, whereas existing tools, deterministic evidence, and bounded plan state implement the supported mechanisms.

These proposals fail the anti-overfit gate and are rejected.

## 5. Decision rule: when explicit plans beat reactive loops

The evidence supports this operational matrix. The matrix itself is a synthesis, not a directly tested universal law.

| Task property | Prefer reactive loop | Prefer explicit plan | Why / evidence |
|---|---:|---:|---|
| One obvious reversible action | Yes | No | Planning overhead has no demonstrated benefit; Codex explicitly discourages filler plans ([Codex source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)). |
| Next action depends on tool output | Yes | Plan only the goal/frontier | ReAct benefits from action–observation interleaving ([ReAct](https://react-lm.github.io/)). |
| Several dependent deliverables | Weak alone | Yes | Explicit decomposition helps bounded multi-step tasks; conditional hierarchy helps compositional environments ([Plan-and-Solve](https://aclanthology.org/2023.acl-long.147/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf)). |
| Fixed, known, cleanly separable stages | Deterministic workflow, not free agent | Yes, as workflow | Anthropic recommends prompt chaining for clean fixed decompositions ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). |
| Unknown subtasks discovered during execution | Yes at action level | Dynamic short plan at goal level | ReAct plus ADAPT supports observe, attempt, then selectively decompose ([ReAct](https://react-lm.github.io/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf)). |
| Many interacting constraints | Insufficient alone | Yes, with constraint ledger and checks | TravelPlanner demonstrates constraint-tracking failures ([TravelPlanner](https://openreview.net/forum?id=l5XQzNkAOe)). |
| Formal deterministic action model exists | Possibly | Solver-backed plan | LLM+P shows value from classical planning after PDDL translation ([LLM+P](https://arxiv.org/abs/2304.11477)). |
| Branching puzzle/search with cheap evaluation | Greedy loop may stall | Bounded search | ToT/LATS/web search-agent results support branching under these conditions ([ToT](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html), [LATS](https://arxiv.org/abs/2310.04406), [web-agent search](https://arxiv.org/abs/2407.01476)). |
| Expensive or irreversible external actions | No unreviewed reaction | Yes, with approval checkpoint | Native Claude Plan mode provides read-only review before execution ([Claude docs](https://code.claude.com/docs/en/permission-modes)). |
| Failure with new external evidence | Repair locally | Update invalid suffix | ADAPT and tool-interactive critique support evidence-based adaptation ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)). |
| Failure with no new evidence | One changed probe at most | Do not “replan” by prose alone | Intrinsic self-correction often fails without external feedback ([ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)). |

**Confidence: very likely (80-90%)** that this hybrid rule will outperform either extreme on a heterogeneous workload, based on convergence across controlled papers, benchmark failures, official production guidance, and native tool design. **UNVERIFIED:** it has not been tested on this owner’s workload. The decisive experiment remains the stratified randomized replay described in §4.10.

## 6. Minimal reference controller

The following is a design sketch, not a recommendation for a new runtime:

```text
classify(task):
  if simple + observable + reversible + direct verifier:
      mode = REACTIVE
  else:
      mode = PLANNED

PLANNED:
  explore enough to replace guesses with facts
  write goal + constraints + 2–7 deliverable steps + checks
  expose only next valid frontier

LOOP:
  execute one frontier step/action
  ingest terminal tool/environment evidence
  if success_check passes:
      attach evidence; mark complete; advance
  elif new evidence invalidates plan:
      preserve valid completed steps
      repair earliest invalid step and dependent suffix
  elif identical failure/no evidence delta repeats:
      trigger bounded decomposition or stop/escalate
  else:
      take one changed diagnostic action

  stop on verified goal, explicit blocker, authority boundary, or budget
```

**Confidence: very likely (80-90%)** that this controller captures the evidence-backed mechanisms without the rejected machinery. Evidence is the combination of ReAct’s observation loop, ADAPT’s failure-triggered recursive decomposition, external-feedback correction, and native plan/checklist interfaces ([ReAct](https://react-lm.github.io/), [ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html), [Claude Plan mode](https://code.claude.com/docs/en/permission-modes), [Codex update_plan](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)). **UNVERIFIED:** the combined controller has not been evaluated as a unit; the §4.10 experiment settles it.

## 7. What could not be determined (GAPS)

1. **No universal crossover threshold.** I found no controlled primary source that says, for example, “explicit planning wins after N tool calls” across models and domains. Any numeric gate is therefore UNVERIFIED; the stratified replay experiment in §4.10 is required.

2. **No current, apples-to-apples frontier-model comparison of always-plan versus reactive versus selectively planned coding agents.** Existing studies vary models, budgets, prompts, tools, environments, and success criteria. Agentless is a useful counterexample but not a controlled isolation of plan policy ([Agentless](https://github.com/OpenAutoCoder/Agentless)).

3. **No general optimum for decomposition depth or branching factor.** ADAPT gives domain-specific depth ablations, and search papers use domain-specific search configurations, but neither yields a universal setting ([ADAPT](https://aclanthology.org/2024.findings-naacl.264.pdf), [Tree of Thoughts](https://proceedings.neurips.cc/paper_files/paper/2023/hash/271db9922b8d1f4dd7aaef84ed5ac703-Abstract.html)).

4. **No proof that visible plans faithfully represent model reasoning.** This report treats visible plans as coordination/control artifacts, not mechanistic explanations. Their utility can be evaluated by constraint coverage, execution outcomes, and repairability; faithfulness was not established by the sources reviewed.

5. **Plan repair for open-ended coding remains under-isolated.** Relevant evidence comes from ADAPT’s failed-subtask decomposition, generic tool-interactive correction, classical plan repair, and production orchestrator designs. I found no mature benchmark that cleanly isolates minimal suffix repair against full replanning for repository-scale coding.

6. **Recent 2026 benchmarks remain preprint evidence.** APB, PlanBench-XL, and AdaPlanBench are potentially valuable because they isolate plan quality, broken-tool adaptation, and progressively revealed constraints, but peer review and independent replication were not determined ([APB](https://arxiv.org/abs/2606.04874), [PlanBench-XL](https://arxiv.org/abs/2606.22388), [AdaPlanBench](https://arxiv.org/abs/2606.05622)). Any recommendation relying on their numerical results would be UNVERIFIED until reproduction on released artifacts. This report uses APB only to motivate diagnostic evaluation, not as sole evidence for architecture.

7. **Cost-normalized tree-search value is unresolved for this owner.** Search improves selected hard benchmarks, but no located source compares it with current native extended reasoning and stronger-model calls across the owner’s heterogeneous work. The bounded search-on-failure experiment in §2.5 is required before adoption.

8. **Native feature behavior is documented, not outcome-validated.** Claude Plan mode, `opusplan`, and Codex planning tools demonstrably exist, but official documentation does not establish their causal effect on verified completion. Local evaluation must measure that effect ([Claude permission modes](https://code.claude.com/docs/en/permission-modes), [Claude model configuration](https://code.claude.com/docs/en/model-config), [Codex source](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)).

## Final recommendation

Adopt **selective, shallow, executable planning**: native plan surfaces; a deterministic complexity gate; a compact goal/constraint/step/check contract; action selection at the observation frontier; external-evidence completion; bounded failed-subtask decomposition; and minimal-suffix repair after deterministic stall/failure signals. Evaluate it against both extremes before expanding it.

Do not equate a plan with correctness, hierarchy with multiple agents, reflection with repair, or search compute with general intelligence. The best-supported harness is a reactive loop with a small deliberative layer—not a planning bureaucracy.
