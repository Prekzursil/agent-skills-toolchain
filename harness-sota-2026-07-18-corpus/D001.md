# D001 — HARNESS-BENCH: why there is no baseline, and the smallest benchmark that can change that

Date: 2026-07-19  
Unit: D001 / P3-coverage / bench: why-no-baseline  
Subject access: read-only Linux bundle at `/local_disk0/codexwork/bundle`  
Artifact scope: diagnosis and design only; no subject/config/runtime mutation

## Executive verdict

The harness cannot presently measure whether it makes the owner's agents better. It can count some tool calls and errors, exercise unit tests, and score one semantic router, but it has no versioned task bank, no immutable minimal control, no paired runs, no end-state grader, no reliable hook-exposure join, and no promotion rule tying a harness change to task success, safety, latency, or cost. Therefore a change can be shown to exist and a bug can sometimes be shown to disappear, but the central statement — **“this change improves the harness”** — has no operational truth condition.

This is not an abstract concern. The 136 supplied audit artifacts contain 1,154 finding-level claims: 614 `FIX`, 108 `BUILD`, 119 `NATIVE-ENABLE`, 87 `PRUNE`, 191 `ALREADY-BUILT`, and 35 `RESEARCH-ONLY`. Thus 928 findings explicitly recommend changing the system. **All 928 improvement-outcome claims are currently unfalsifiable as harness-level uplift.** Many have excellent static evidence and some have deterministic reproductions, so their *mechanism* claims are testable; none is backed here by an executed, same-model, same-task, with/without-harness counterfactual. The 191 `ALREADY-BUILT` findings can establish existence, but their implied claim that the retained mechanism earns its cost is also currently unfalsifiable. Only the 35 research-only findings make no implementation-uplift claim.

Confidence: **almost certain (90-99%)**, because two mechanically independent local signals agree: (1) the supplied corpus explicitly marks its hook detector `BROKEN` and therefore supplies no hook behavior data (`/local_disk0/codexwork/bundle/inputs/corpus.json`, `hooks.DETECTOR_STATUS`), while retaining exact tool/error counts in different fields; and (2) the live-defects input independently reports zero hook-name records across the transcript corpus and specifies a separate event-ledger/transcript experiment still required to locate durable hook telemetry (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:133-147`). The installed `/eval` is a prose workflow that tells an agent to “attempt to verify” checkboxes and append a log, not a deterministic batch runner (`/local_disk0/codexwork/bundle/claude/commands/eval.md:36-59`), and the installed `harness-bench` explicitly covers only semantic-router skill/MCP recall (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:1-9`).

The recommendation is a one-week **Minimum Viable Harness Benchmark (MVHB)** that rides the existing `/eval`, dispatcher mode ladder, hook event model, and ledger. It consists of versioned JSONL task/claim manifests, a small paired runner, deterministic graders, and an append-only result record. It does **not** install mini-SWE-agent, Inspect, an observability service, a vector store, a critic, or another orchestration runtime.

Proposal tag: **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for the runner; **CONFIG (settings/JSON only)** for claims/tasks; **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for event-to-trial receipt joining. It passes the anti-overfit gate because execution remains the native Claude/Codex agent, ablation uses the already-built OFF→SHADOW→ADVISE→ENFORCE bus, and scoring is an offline script rather than a new agent runtime.

Expected result: it is **very likely (80-90%)** that this design can produce the first valid deterministic replay baseline within one working week, because the hook event dataclasses, provider adapter, gate overrides, typed receipts, and `/eval` entry point already exist (`/local_disk0/codexwork/bundle/agents/harness/models.py`; `/local_disk0/codexwork/bundle/agents/harness/adapters.py`; `/local_disk0/codexwork/bundle/agents/harness/modules.py:311-417,1048-1077`; `/local_disk0/codexwork/bundle/claude/commands/eval.md:1-7`). It is only **likely (55-80%)** that the same week can yield a credible agent-level paired pilot, because native noninteractive CLI invocation, token/cost receipt completeness, and disposable Windows worktree setup are **UNVERIFIED — experiment `E0-runner-canary` below runs one no-op task twice under each arm and validates all required fields before the pilot**.

## 1. Precise problem statement

A harness improvement claim needs five bound objects:

1. a frozen task or event input;
2. an immutable control configuration;
3. one isolated candidate difference;
4. a grader that observes the environment outcome rather than trusting the agent's completion prose; and
5. a decision rule declared before results are seen.

The subject has none of these as a joined end-to-end contract.

What it does have is useful but narrower:

- The corpus measured 10.62 GB / 11,633 transcript files with zero file failures and one bad line, making its tool-call/error counts strong retrospective operational evidence (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-12`). It is not a controlled before/after experiment.
- The corpus's owner-correction detector is explicitly recall-biased and reports 41/41 false positives in an unfiltered smoke sample (`/local_disk0/codexwork/bundle/inputs/corpus.json`, `owner_correction_candidates.precision_warning`). It cannot presently grade user satisfaction.
- The corpus hook section is no data, not evidence of no hook fires (`/local_disk0/codexwork/bundle/inputs/corpus.json`, `hooks.DETECTOR_STATUS`).
- The local `/eval` document defines capability/regression checklists and pass@3/pass^3 reporting (`/local_disk0/codexwork/bundle/claude/commands/eval.md:9-32,61-97`) but does not freeze model/scaffold/environment hashes, run paired arms, record complete trajectories, or implement graders.
- The current `harness-bench` invokes one router evaluator, reads four recall counts, and ratchets a baseline upward (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/bench.py:55-129,150-184`). It explicitly returns zero on broken, garbage, or non-JSON eval output (`bench.py:150-160`) and on a corrupt present baseline (`bench.py:162-170`). This makes scheduler green non-evidence of a completed measurement. Audit F08 independently traced an actual caller/callee format mismatch and a green scheduled result (`/local_disk0/codexwork/bundle/inputs/audit-findings/F08.md:23-29`).
- The current router README says a green recall net “licenses” skill pruning (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:8-9`). Router recall is not end-task success: a skill can be selected and still harm the task, or not be selected and be irrelevant. That licensing claim is currently unfalsifiable at the outcome layer.
- The shared harness already has a per-gate mode ladder and environment/file overrides (`/local_disk0/codexwork/bundle/agents/harness/modules.py:119-143,311-333,389-417`). This is the correct ablation seam, but no supplied runner uses it to compare end-task outcomes.

The last absence statement has two mechanically independent signals with known-present controls. A filename inventory found the known-present `harness-bench/bench.py` and both router `eval.py` files, but no other filename containing `eval`, `bench`, `baseline`, or `grader` implements a paired agent runner. Separately, a content search that successfully found paired-control language in the known-present audit D08 found no `task_hash`, `grader_hash`, `harness_tree_hash`, paired-arm runner, or paired-statistics implementation outside audit inputs. Audit E02 independently reports that no versioned capability manifest, grader set, or blessed baseline was found in the live Windows subject and that the observed ledger had no `eval_start`/`eval_result` kinds (`/local_disk0/codexwork/bundle/inputs/audit-findings/E02.md:79-84`). The live-Windows portion remains an audit claim rather than a fact re-probed on this Linux node; the supplied-tree absence is directly verified.

The practical consequence is harsh: a false-positive guard can be “more active,” a recall injector can retrieve “more context,” a review agent can find “more findings,” and an orchestrator can launch “more specialists,” while owner outcomes get worse. Without a control, all four look like progress.

### 2.3 What “unfalsifiable” means here

It does not mean “impossible to test.” It means the present program has not bound the claim to a test that could make it lose.

Examples:

- “Fix explicit-failure precedence” can lose a deterministic replay test if a contradictory envelope is still stamped pass. That is a **mechanism claim** and is easy to falsify (`F08.md:7-21`). “This improves completed-task correctness without unacceptable false failures” additionally needs negative controls and paired tasks; that is absent.
- “Prune unused skills” can lose a routing recall test, but the current router net cannot detect a selected skill becoming worse, an unselected skill being irrelevant, or downstream task success changing (`harness-bench/README.md:8-9`).
- “Enable review/subagents” can be shown to launch, yet the benefit claim requires matched tasks, constant tests, escaped-defect grading, and full cost. Audit B12 itself says no A/B outcome counter was found and proposes such a pilot (`B12.md:66-67`).
- “Add memory scaffolds” cites external benchmark deltas, but local rankings reverse across published datasets and audit D01 correctly asks for a local architecture gate (`D01.md:74-80`). Until then the local uplift is unverified.
- “Promote shadow gates” proves a detector is active, not that it is precise or beneficial. Known defect D1 shows four detector implementations confusing use with mention and even treating a successful result as failed (`INPUT-known-harness-defects.md:9-87`). Activity without labels can make the harness worse.

## 3. Prior art and what transfers

### 3.1 Agent evals require outcomes, trajectories, and repeated trials

Anthropic's agent-eval guide defines a task, trial, grader, complete transcript, environment outcome, eval harness, and agent harness separately. It explicitly distinguishes what an agent *says* from the environment state and recommends multiple trials because outputs vary: <https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>. This maps directly to the subject's gap: ledger receipts can contribute trajectory data, but a completion sentence cannot be the grader.

The same guide says 20–50 tasks drawn from real failures are a useful first set, requires reference solutions/known-pass controls, and requires balanced positive and negative behavior cases. That supports a 24-task week-one bank rather than waiting for a grand universal benchmark. Confidence: **very likely (80-90%)** that 24 high-signal tasks will expose gross regressions, based on Anthropic's 20–50 recommendation and this corpus's concentrated recurrent failures; it is **unlikely (20-45%)** that 24 tasks can resolve small (<10 percentage-point) aggregate quality differences, because binary agent outcomes have high variance. ### 4.5 Metrics

No single scalar “harness score” in v1. A weighted composite would hide a safety regression behind a speed gain and invite weight tuning after results.

Primary by claim class:

- deterministic detector/adapter fix: verdict accuracy over balanced fixtures;
- coding task: objective end-state pass rate, including fail-to-pass and pass-to-pass tests;
- research task: claim coverage, citation entailment, source authority, and unsupported-claim count, with deterministic checks where possible and blinded human adjudication for residuals;
- routing: correct tool/capability selection *and end-task pass*;
- memory/continuity: required-fact recall and end-task pass, with poison/superseded negative controls;
- multi-agent/review: unique valid defects fixed or found, escaped defects, and end-task pass.

Universal secondary metrics:

- wall time, tool calls, tokens, cost, process count;
- tool-error count and errors per 100 calls;
- repeated identical actions and A-B-A-B cycles (the current harness already detects these at `modules.py:1848-1908`);
- false block/injection/nag rate;
- hook expected/observed/applied counts and join completeness;
- owner intervention/correction only after a correction detector passes a labeled precision audit.

Universal vetoes:

- credential exposure, out-of-scope mutation, or sandbox escape;
- previously passing regression task fails;
- benchmark-invalid rate above 0;
- missing required receipt;
- negative-control false-positive rate beyond the claim-card bound.

### 4.6 Statistics and decision rule

The unit of analysis is the task, not the raw tool call. Pair control and candidate on the same task/repetition block.

- Report raw numerator/denominator and per-task outcomes.
- Report pass@1 as all first trials, pass@3 only as “at least one of three,” and pass^3 as “all three.”
- For paired binary success, report the discordant-pair table and an exact McNemar test; use a task-clustered paired bootstrap 95% interval for the success-rate difference.
- For latency/calls/tokens/cost, report median paired difference plus a task-clustered bootstrap interval. Failed trials retain their consumed cost/time; do not condition efficiency on success alone. Also report cost per successful task.
- Run A/A before A/B. If identical arms produce systematic differences beyond sampling noise or receipt completeness differs, the runner is invalid.
- Freeze N before the run. Do not stop when the candidate looks good.

Week-one promotion rule:

1. deterministic claims may move from shadow to advise only if every positive and negative L1 fixture passes, the reference solution passes, malformed benchmark inputs exit 2, and existing harness tests remain green;
2. no heuristic gate moves to enforce on the 24-task pilot alone;
3. L2 results are reported with intervals and can justify a larger confirmatory run, not an unqualified “improved” label;
4. a candidate with a safety veto loses regardless of aggregate quality;
5. a candidate with no primary benefit and positive cost is retired or remains off.

Confidence: **very likely (80-90%)** that this rule prevents the most serious false promotions, because deterministic gates require exhaustive curated fixtures and heuristic gates cannot jump directly to enforcement. It is **roughly even (45-55%)** that a 24-task pilot will distinguish modest candidates, because the effect size and discordant-pair rate are unknown; `E4-power-refresh` settles the next sample size.
