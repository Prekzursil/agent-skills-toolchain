# I01 — Initiative / anticipation calibration: the EVPI/EIG attention gate

**Unit:** I01  
**Family:** initiative / anticipation calibration  
**Date:** 2026-07-19  
**Scope:** research and design only; the subject tree was read-only. The only written file is this artifact.

## Executive conclusion

The correct gate is not “is the prompt vague?” and not “is the model uncertain?” It is a constrained decision among **act, probe, ask, and defer**. The owner should be asked only when their answer is decision-changing, the information or authorization is uniquely theirs, and the expected reduction in decision loss exceeds both the best external probe and the full cost of interrupting them. Authorization boundaries override that economic comparison: an irreversible or externally consequential action that requires owner authority must be confirmed even when the agent is confident.

The existing harness contains valuable pieces but not that gate. The cross-tool contract says to ask only on material ambiguity and gate by EVPI (`/local_disk0/codexwork/bundle/claude/AGENTS.md:7-20`). An inquisitiveness implementation exists and is fail-open (`/local_disk0/codexwork/bundle/claude/hooks/inquisitiveness/prompt-guard.py:1-20,189-227`), while calibrated-silence learns from later user behavior (`/local_disk0/codexwork/bundle/claude/hooks/calibrated-silence/calibrated_silence.py:39-53`). However, neither `inquisitiveness` nor `calibrated-silence` appears in either of the two live wiring surfaces. This absence has two mechanically independent signals: the live `settings.json` UserPromptSubmit roster contains the shared dispatcher and selection-event emitter but neither candidate (`/local_disk0/codexwork/bundle/claude/settings.json:117-137`), and the local dispatcher manifest has no UserPromptSubmit event at all while demonstrably finding known-present SessionStart and PreToolUse checks (`/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:1-70,182-227`). The earlier audit independently made the same claim, but remains corroboration rather than ground truth (`/local_disk0/codexwork/bundle/inputs/audit-findings/A32.md:39-45`).

More importantly, simply wiring the existing code would be wrong. Its vagueness score treats a concrete token as sufficient reason for silence (`prompt-guard.py:108-144`), even though a perfectly concrete request can hide a high-impact preference or authority fork. Its calibrated-silence decision is `p_useful * fixed type value >= threshold + fatigue` (`calibrated_silence.py:381-428`); it does not price the best autonomous probe, reversibility, answer effort, delay, or downstream blast radius. Its reaction logger counts **any substantive answer of five or more words** as success for a question (`log_reaction.py:100-151`), regardless of whether the question changed the action or prevented an error. Optimizing that label would train the harness to elicit answers, not to save owner attention.

The recommended architecture is a small policy module folded into the **existing shared UserPromptSubmit dispatcher**, plus extensions to the existing calibrated-silence ledger, event ledger, open-loops store, AskUserQuestion, and Workflow checkpoint. It adds **zero hook invocations**, stays below the ~6-hook ceiling, is fail-open, and introduces none of the anti-overfit forbidden components: no second orchestrator, vector DB/KG, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Expected overall effect: **very likely (80-90%)**, because the proposal directly removes three locally evidenced failure modes—burden-shifting, premature action at decision forks, and optimizing a proxy label—while the exact magnitude is not known until the shadow replay and owner-attention A/B test in Finding 8.

## Evidence discipline and corpus limits

The corpus is unusually complete as a *distillation*: 11,633 files were seen, zero failed, one line was bad, and 32 oversized lines were separately recorded (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). It is not a turn-level dialogue dataset. The owner-correction detector reports 8,441 owner messages and 2,268 candidates, but explicitly warns that it is recall-biased and that 41/41 items in an unfiltered smoke sample were false positives caused by agent-authored prompts (`corpus.json:10371-10374`). Therefore **2,268/8,441 is not an owner-correction rate** and is not used as one here.

The supplied `owner_correction_candidates.samples` preserve owner text, time, source file, and an `after_tool_use` flag, but not the preceding assistant question/action. Consequently, the examples below are **UNVERIFIED candidate classifications; replaying the named raw JSONL and reading the immediately preceding assistant turn would settle each one**. The raw Windows transcript root is not present on this Linux job node, so that experiment cannot be run in this unit. This is a gap, not permission to reconstruct dialogue.

## Formal gate

Let the hidden task state be \(\theta\), candidate implementation actions be \(a\), an owner question be \(q\) with possible answers \(y\), and an autonomous external probe be \(z\) with observations \(o\). Utility \(U(a,\theta)\) includes task quality, time, resource cost, reversibility, safety, and owner burden.

Decision-weighted expected value of sample information from asking:

\[
EVSI(q)=\mathbb E_y\left[\max_a\mathbb E[U(a,\theta)\mid y]\right]-
\max_a\mathbb E[U(a,\theta)].
\]

Net value of asking:

\[
NVA(q)=EVSI(q)-C_{interrupt}(context)-C_{answer}(q)-C_{delay}(q)
-C_{trust}(false\ alarm)-C_{thread}(open\ dependency).
\]

Net value of probing:

\[
NVP(z)=EVSI(z)-C_{probe}(z)-C_{delay}(z)-R_{probe}(z).
\]

The policy is:

1. **Authority constraint first.** If an action is irreversible, meaningfully billable, credential/secret-bearing, external-facing, legally or reputationally consequential, or outside the granted scope, ask for confirmation. This is a permission boundary, not an information calculation.
2. **Owner-only test.** For other questions, ask only if the answer is a preference/fact the owner uniquely knows or if all safe external probes are exhausted.
3. **Decision-sensitivity test.** Enumerate at least two plausible answers. If they do not select different actions or materially different acceptance criteria, \(EVSI(q)=0\): do not ask.
4. **Comparator test.** Ask only when \(NVA(q)>\max(0,NVP(z))\). If a safe, cheaper deterministic probe or independent-context check can settle the fork, run it.
5. **Reversibility test.** Continue through reversible work and stop only immediately before the first irreversible or high-regret boundary. Do not interrupt merely because a later step may need a choice.
6. **Timing test.** Ask in the first 1-2 actions, as the existing contract requires (`AGENTS.md:7-12`), or at an explicitly declared terminal/checkpoint boundary; never spring a clarification mid-flow. Low-urgency questions are deferred into one checkpoint bundle.
7. **Loop closure.** Every question gets a decision receipt and a durable open-loop ID. It closes only on an external outcome: test result, tool result, independent reviewer verdict, or owner answer plus verified downstream result. Same-context “I think that helped” is invalid by construction.

Entropy/EIG is useful only as a candidate generator. A question can have high answer entropy but zero decision value if every answer leads to the same action. “Clarify When Necessary” uses intent entropy and reports better selection of clarification opportunities when only 10% of examples may be queried ([Zhang & Choi, 2023](https://arxiv.org/abs/2311.09469)); this harness should add the action-branch and cost comparator that entropy alone lacks. The decision-theoretic lineage is direct: Horvitz frames mixed initiative around uncertainty and expected utility ([Principles of Mixed-Initiative User Interfaces, CHI 1999](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/)), and Kamar & Grosz explicitly model the value an interruption provides against the human cost of responding ([2007 paper](https://www.microsoft.com/en-us/research/publication/applying-mdp-approaches-for-estimating-outcome-interaction-in-collaborative-human-computer-settings/)).

## Findings (inferred-surprise first)

### Finding 1 — Optimize verified regret avoided, not “the owner answered”

- **Improvement:** Replace the question learner’s `acted/ignored/annoyed` reward with an outcome-linked **ask receipt**.
- **What it is:** Each surfaced question records `question_id`, decision fork, candidate actions, predicted consequence, chosen answer, baseline action without asking, and verification target. After the answer, the record remains unresolved until an external signal reports whether the selected action passed, required rework, was reversed, or drew an owner correction. Score a question useful only when it changed the selected action/acceptance criterion *and* improved an external outcome relative to the recorded baseline. A substantive reply by itself is engagement, not value.
- **Why-inferred:** The existing classifier mechanically labels any non-dismissive reply of at least five words as `acted` (`log_reaction.py:100-151`). The owner’s attention is therefore optimized toward compliance. The correction candidates “I meant you should do that” and “you have to do that yourself” are UNVERIFIED examples of the exact behavior this proxy can reward; raw-turn replay is the settling experiment (`corpus.json:12227,12377`).
- **How-to-build:** Extend each calibrated-silence JSONL row with optional `decision_id`, `branches_hash`, `baseline_action`, and `verification_ref`. Add `decision_outcome` rows from the existing event-ledger Stop/note path; do not overwrite history. Join by `decision_id` in the existing reaction logger. Keep `answered` as a diagnostic field, but compute `useful` from `branch_changed && external_outcome_better`, and `harmful` from owner correction/reversal/rework. Unknown remains unknown rather than being coerced to ignored. Rough implementation size: 120-180 lines across the existing files.
- **External signal that verifies it:** A deterministic test result/tool result, independent-context reviewer verdict, or explicit owner correction/reversal linked to the decision ID. Same-context self-rating is prohibited. On a replay set, manually label whether each question changed the decision and compare the new score with observed downstream outcomes.
- **SOTA citation:** Appropriate reliance is measured by accepting correct advice and rejecting incorrect advice, not by trust or mere uptake ([Microsoft Research synthesis, 2024](https://www.microsoft.com/en-us/research/publication/appropriate-reliance-on-generative-ai-research-synthesis/)). Human-AI mitigations can backfire and therefore need user/outcome testing ([Microsoft Research, 2025](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-genai-lessons-learned-from-early-research/)).
- **Value x effort:** **transformative x medium**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **confirm-first** for adopting the reward semantics; the implementation can then run shadow-only without further attention.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.
- **Confidence:** Outcome-linked scoring is **very likely (80-90%)** to reject more nuisance questions than the current “five words = acted” proxy, because the code-level proxy defect is direct; the exact reduction is UNVERIFIED, and the held-out replay plus shadow A/B in Finding 8 would settle it.

### Finding 2 — Replace the vagueness detector with an act/probe/ask/defer comparator

- **Improvement:** Implement the formal NVA/NVP gate above as the single initiative policy.
- **What it is:** A compact decision card containing: `fork`, `best_default`, `answer_branches`, `owner_only`, `best_probe`, `reversible_until`, `authority_boundary`, `ask_cost`, and `deadline`. A question is emitted only when the card demonstrates decision sensitivity and beats the probe/default alternatives.
- **Why-inferred:** The contract already demands EVPI (`AGENTS.md:7-20`), but the existing implementation scores lexical vagueness and declares every prompt with any path, URL, code keyword, CamelCase, or ALL-CAPS target concrete (`prompt-guard.py:62-83,108-144`). The owner’s “do not disable; query the analysis results” candidate (`corpus.json:11897-11900`) shows why concreteness and decision risk are different dimensions, although the preceding turn remains UNVERIFIED until raw replay.
- **How-to-build:** Add one stdlib module to the existing shared `UserPromptSubmit` dispatcher. It consumes prompt, tool/capability catalog, current open loops, and durable preference summary. It emits only structured additionalContext instructing the model to either (a) execute a named probe, (b) use AskUserQuestion with a compiled question, (c) proceed with a named reversible default, or (d) register a bounded defer. Keep the existing `*` bypass. Fold/replace `inquisitiveness`; do not wire it separately. Wrap the module in try/except and return no guidance/exit 0 on any error.
- **External signal that verifies it:** For every emitted route, require one of: executed probe receipt, AskUserQuestion answer, tool/test result for the default, or open-loop closure at the declared deadline. A separate replay evaluator—not the generating model—compares chosen action with the answer-conditioned oracle action.
- **SOTA citation:** Mixed-initiative systems should allocate initiative to the party best positioned at the appropriate time ([Horvitz, 1999](https://www.microsoft.com/en-us/research/publication/mixed-initiative-interaction/)). Clarification needs three separable abilities—detect when, ask what, then use the answer—and intent-based utility beats generic uncertainty selection ([Zhang & Choi, 2023](https://arxiv.org/abs/2311.09469)).
- **Value x effort:** **transformative x medium**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **confirm-first** because it changes the global initiative policy; shadow mode is just-do-it after approval.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.
- **Confidence:** This comparator is **very likely (80-90%)** to dominate the lexical vagueness gate on decision relevance, based on the latter’s explicit hard gate and the decision-theoretic research; latency and calibration are UNVERIFIED until the replay evaluator measures precision, recall, and p95 dispatcher time.

### Finding 3 — Treat owner attention as a scarce, contextual budget with bounded deferral

- **Improvement:** Price interruption, answer effort, and cost of delay separately; batch low-urgency questions at a declared checkpoint.
- **What it is:** A session attention account, not a fixed question quota. It raises the ask threshold after recent interjections, during terse/focus signals, and for multi-part questions; it lowers the threshold as the cost of deferral approaches an irreversible boundary. Mandatory authorization prompts are exempt from suppression but are still compressed.
- **Why-inferred:** Prompt fatigue is a hard constraint in this unit. The existing calibrated-silence code already has useful proxies—recent correction, terse prompt, late hour, and session density (`calibrated_silence.py:289-378`)—but combines them only with a fixed per-type value, not delay or question effort (`calibrated_silence.py:414-426`). The corpus candidate “now? why would I want it later” (`corpus.json:11285`) is UNVERIFIED evidence that deferral itself can be the wrong choice; raw replay would settle it.
- **How-to-build:** Retain the existing fatigue features. Add `answer_effort` (number of independent fields/options), `deadline_event` (before write/deploy/external send), and `deferral_loss` (low/medium/high with evidence reference). Permit at most one question bundle at initial scoping and one at an explicit Workflow checkpoint; otherwise register it in open-loops. If three low-urgency questions accumulate, show one ranked bundle containing only the highest joint-value questions, never three separate interruptions.
- **External signal that verifies it:** User response latency, dismissal/rephrase, number of question turns, time-to-first-tool, and downstream correction rate from transcripts; task success from tests/tool receipts. Compare against matched shadow sessions. Do not infer fatigue from the agent’s prose.
- **SOTA citation:** BusyBody learned personalized interruption cost from activity and context and used it to mediate notifications ([Horvitz, Koch & Apacible, 2004](https://www.microsoft.com/en-us/research/publication/busybody-creating-fielding-personalized-models-cost-interruption/)); Bestcom balances interruption cost with cost of deferral ([Horvitz et al., 2003](https://www.microsoft.com/en-us/research/publication/considering-costs-interruption-deferral-routing-interpersonal-communications/)).
- **Value x effort:** **high x low**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **just-do-it** in shadow mode; confirm-first for changing visible timing.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.
- **Confidence:** Batching is **likely (55-80%)** to reduce interruption turns without increasing regret, based on the existing timing/fatigue signals and interruption literature; the owner-specific optimum is UNVERIFIED until the matched-session experiment above.

### Finding 4 — Learn a decision-rights matrix, not a generic “more/less proactive” preference

- **Improvement:** Personalize initiative by **decision class**: operate autonomously, verify autonomously, ask preference, or request authority.
- **What it is:** A small durable profile keyed by domain and consequence, for example: `redeploy/monitor/test -> agent operates`; `owner taste/product tradeoff -> ask when branch-changing`; `delete/disable/external-send/billable/credential -> confirm`; `live physical/UI observation unavailable to tools -> request minimal manual input`. Preferences decay or require reconfirmation when scope changes.
- **Why-inferred:** Multiple correction candidates across dates say the agent should restart, redeploy, monitor, use available reverse-engineering tools, and call the owner only for manual input (`corpus.json:12101-12104,12221-12230,12377-12384`). That makes the operational-autonomy preference **likely (55-80%)**, with evidence from several distinct turns; each causal interpretation remains UNVERIFIED until raw replay. The contrasting “do not disable” correction (`corpus.json:11897-11900`) argues against a blanket autonomy setting.
- **How-to-build:** Store owner-confirmed rules in basic-memory and a machine-readable `decision-rights.json` referenced by the existing behavior contract. Seed nothing from detector candidates automatically. Propose a rule only after two independent explicit owner corrections in the same class; ask once to ratify it, then apply it silently. Record every application with the matched rule ID. A conflicting owner instruction supersedes the old rule through the existing event-ledger decision mechanism.
- **External signal that verifies it:** Explicit owner ratification is signal one; later behavior is signal two—fewer burden-shift corrections without increased reversals/rollbacks in that class. A deterministic matcher test proves the intended class is selected. No same-context preference inference is accepted as truth.
- **SOTA citation:** Recent UserVille/PPP work explicitly separates productivity, proactivity, and personalization and evaluates preference adaptation in software-engineering and research tasks ([Sun et al., 2025 preprint](https://arxiv.org/abs/2511.02208)). The older HAI guidelines were validated through multiple rounds including 49 practitioners evaluating 20 products and include learning from user behavior over time ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).
- **Value x effort:** **high x low**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **confirm-first** to ratify each durable decision-right rule; applications are then just-do-it inside its scope.
- **NATIVE-vs-BUILD:** **CONFIG (settings/JSON only)**.
- **Confidence:** A class-specific profile is **very likely (80-90%)** to calibrate better than one global proactivity level, because local examples demand high operational autonomy and a conservative capability-reduction boundary; its generalization across new domains is **roughly even (45-55%)** until owner-ratified rules accumulate.

### Finding 5 — Compile one minimal sufficient question with an executable default

- **Improvement:** When asking wins, ask the smallest question that separates actions, with a recommended default and consequence.
- **What it is:** A question contract: `decision`, 2-3 mutually exclusive options, recommended option, one-sentence consequence per option, safe default if no answer, and deadline. Do not ask for information already in the repo, tools, memory, or prior owner decisions. Do not ask “is this okay?” when all answers lead to the same implementation.
- **Why-inferred:** The contract limits clarification to 1-3 focused questions (`AGENTS.md:7-12`), and the existing guidance correctly says not to ask about facts inferable from the codebase (`prompt-guard.py:147-160`). The missing step is proving that each question separates executable branches. This directly addresses prompt fatigue without suppressing high-value owner judgment.
- **How-to-build:** Update the existing `clarify-requirements` skill/AskUserQuestion template. Before emitting, require a machine-checkable `option -> action_id` map; reject duplicate action IDs and questions lacking a safe default or explicit “blocked pending authority.” Ask the highest-NVA question first; recompute after its answer instead of blindly asking the remaining list. Keep presentation to one UI interaction.
- **External signal that verifies it:** AskUserQuestion’s returned option is external. Then verify that the mapped action ID was executed and its acceptance test/tool receipt passed. Track re-asks and owner free-text corrections as failure signals. A separate schema test rejects non-discriminating option maps.
- **SOTA citation:** ClarifyCodeBench proposes Turn-discounted Key Question Rate and Optimal Round Adherence, explicitly penalizing inefficient questioning and measuring whether key ambiguities are resolved ([Fang et al., 2026 preprint](https://arxiv.org/abs/2607.00711)). “Clarify When Necessary” similarly separates question timing, question content, and answer use ([Zhang & Choi, 2023](https://arxiv.org/abs/2311.09469)).
- **Value x effort:** **high x low**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **just-do-it** after the global policy is approved.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. AskUserQuestion is native; only the decision-sensitive branch-map validator is built.
- **Confidence:** The branch-map constraint is **very likely (80-90%)** to eliminate rubber-stamp questions, because identical downstream actions mechanically imply zero decision value; owner-perceived improvement is UNVERIFIED until re-ask/dismissal rates are measured.

### Finding 6 — Put every unresolved question in “ask escrow” so no thread can disappear

- **Improvement:** Turn an unanswered/deferred question into a durable prospective-memory item with an automatic safe continuation rule.
- **What it is:** When a question cannot or should not interrupt now, create an open-loop record containing the decision ID, exact blocking boundary, reversible work still permitted, deadline/trigger, default, and closure evidence. The agent continues safe work and resurfaces the question only when its predicate matches or the boundary is reached.
- **Why-inferred:** Never dropping a discussed thread is a hard constraint. The infrastructure is already present: `open-loops/add.py` supports predicates, TTLs, recurrence, close/list, and a JSONL store (`open-loops/add.py:1-24,120-195`); SessionStart resurfaces at most three relevant loops and deliberately deduplicates event-ledger replay (`open-loops/resurface.py:1-25,39-107`). The proposal extends this system rather than inventing another tracker.
- **How-to-build:** Add optional fields to existing open-loop records: `decision_id`, `blocked_at`, `continue_until`, `default_action`, `evidence_required`, `question_payload`. The initiative gate calls `add.py` when it selects defer. Workflow checks the predicate at its existing checkpoints; SessionStart behavior remains unchanged. Closure requires the answer plus the external result, not the answer alone. On gate failure, fail open by continuing only reversible work and leaving the ledger item visible.
- **External signal that verifies it:** The open-loop JSONL record is signal one; a later matched trigger plus tool/test/owner outcome is signal two. A regression test simulates compact/resume and asserts the same decision ID resurfaces and closes exactly once.
- **SOTA citation:** Attention-sensitive systems explicitly balance the value of awareness with interruption cost ([Microsoft Research, Attention-Sensitive Alerting](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/)). The HAI guidelines emphasize support for efficient invocation, dismissal, correction, and learning over time ([Amershi et al., 2019](https://doi.org/10.1145/3290605.3300233)).
- **Value x effort:** **transformative x low**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **just-do-it**.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.
- **Confidence:** Ask escrow is **almost certain (90-99%)** to make deferred questions mechanically recoverable under the tested open-loop lifecycle, because durable creation and later trigger are separately observable; whether surfacing at most three items preserves the optimal priority is **likely (55-80%)** and requires the resume regression plus owner reaction data.

### Finding 7 — Separate epistemic questions from authority confirmations

- **Improvement:** Use tools for “what is true?” and the owner for “may I?” or “which consequence do you prefer?”
- **What it is:** A typed escalation policy:
  - `EPISTEMIC`: run a deterministic tool/test; if unavailable, use a fresh-context independent model or ask the owner only when they uniquely possess the observation.
  - `PREFERENCE`: ask only when plausible answers choose materially different outcomes.
  - `AUTHORITY`: always confirm before irreversible, external-facing, billable, secret-bearing, or scope-expanding action.
  - `EXECUTION`: act and verify; never ask the owner to run/redeploy/paste logs when the harness can observe them.
- **Why-inferred:** The law for this unit rejects same-context self-correction. The known-defects file records six wrong conclusions from single unvalidated probes and a seventh case where a known-positive control separated one broken detector from two working capabilities (`INPUT-known-harness-defects.md:111-129`). It also records a fabricated orchestrator constraint propagated to about 15 prompts (`INPUT-known-harness-defects.md:151-161`). Owner candidates repeatedly request autonomous tools/live probes (`corpus.json:12101-12104,12377-12384`), while the capability-reduction correction supplies the opposite authority signal (`corpus.json:11897-11900`); their exact antecedents remain UNVERIFIED pending replay.
- **How-to-build:** Add the four-valued `question_type` and `external_signal` fields to the decision card. Refuse to emit an epistemic question until a named probe has either produced a receipt or a recorded external failure. Route authority questions directly through AskUserQuestion. Route execution to Workflow plus truth-verify/edit-checkpoint receipts. A fresh model counts only if it lacks the generating context and produces a separately stored verdict; same-context reflection never counts.
- **External signal that verifies it:** Known-positive/known-negative controls for epistemic absence claims; execution/test results for operational choices; explicit owner response for preference/authority. For “absence/broken/done,” require two mechanically independent signals, one of which proves the detector on a known-present item.
- **SOTA citation:** Kamar & Grosz formalize interruption as valuable information purchased at a human response cost ([2007](https://www.microsoft.com/en-us/research/publication/applying-mdp-approaches-for-estimating-outcome-interaction-in-collaborative-human-computer-settings/)). Microsoft’s appropriate-reliance work warns that UX mitigations can backfire and calls for empirical testing rather than assumed trust gains ([2025](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-genai-lessons-learned-from-early-research/)).
- **Value x effort:** **transformative x low**.
- **Novelty:** **user-asked** (the external-signal law), extended here into a buildable decision taxonomy.
- **Autonomy:** **confirm-first** only for the authority class; all other classes follow the gate.
- **NATIVE-vs-BUILD:** **CONFIG (settings/JSON only)**.
- **Confidence:** Typed escalation is **very likely (80-90%)** to reduce owner-facing epistemic questions and unsafe silent authority assumptions, because the verification mechanism differs mechanically by uncertainty source; the classification error rate is UNVERIFIED until the replay benchmark in Finding 8.

### Finding 8 — Calibrate in shadow replay before one visible question is added

- **Improvement:** Build a counterfactual, owner-attention evaluation gate and require it to pass before enabling visible interjections.
- **What it is:** A replay dataset of real task openings and decision forks labeled with `ask/probe/act/defer`, minimal key question, authority requirement, and external outcome. Compare current policy, lexical inquisitiveness, and the proposed NVA policy under an explicit attention budget.
- **Why-inferred:** The correction-candidate detector’s own warning—41/41 smoke-sample false positives—proves that convenient labels are unsafe (`corpus.json:10371-10374`). Hook telemetry in the corpus is declared broken by the pinned input, and the defects file says the symptom is zero hook fields despite known firings; it names the event-ledger/system-reminder experiment needed to settle persistence (`INPUT-known-harness-defects.md:133-147`). Enabling another visible intervention without offline measurement would repeat the single-signal error class.
- **How-to-build:** Sample at least 100 replayable turns stratified by task type, correction candidate/non-candidate, long/terse prompt, and consequence class. Two independent annotators label each turn; disagreements go to the owner only as a compact adjudication batch of high-impact cases. Metrics: (1) unnecessary-question rate, (2) missed-key-question rate, (3) owner turns per successful task, (4) turn-discounted key-question rate, (5) external task success, (6) reversal/rework rate, (7) p50/p95 hook latency, and (8) dropped-decision count after resume. Start observe-only. Promote only if unnecessary questions fall without a statistically or practically meaningful increase in missed authority/key questions; retain a kill switch and rollback.
- **External signal that verifies it:** Independent annotations plus raw transcript/tool/test outcomes. Production verification is a randomized or stepped-wedge shadow comparison in which policy recommendations are logged but not shown, followed by a small visible canary only after the offline gate passes. The generating agent never judges its own recommendation.
- **SOTA citation:** ClarifyCodeBench’s turn-discounted question metrics provide a current benchmark model ([Fang et al., 2026](https://arxiv.org/abs/2607.00711)). The CHI HAI guidelines were themselves validated through multiple empirical rounds rather than treated as self-evident ([Amershi et al., 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). Recent proactive-personalized agent work jointly evaluates productivity, proactivity, and personalization rather than task success alone ([Sun et al., 2025](https://arxiv.org/abs/2511.02208)).
- **Value x effort:** **transformative x medium**.
- **Novelty:** **inferred-surprise**.
- **Autonomy:** **just-do-it** for read-only shadow evaluation; confirm-first before visible canary interjections.
- **NATIVE-vs-BUILD:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**.
- **Confidence:** Shadow replay is **almost certain (90-99%)** to catch gross label and routing defects before they consume owner attention, based on the detector’s measured 41/41 smoke failure and the known-positive-control incidents; its estimate of live causal benefit is **likely (55-80%)**, not certain, because replay cannot fully reproduce changing task context and must be followed by a canary.

## Concrete deployment sequence

1. **No visible behavior change:** create the typed decision-card schema and offline replay evaluator; recover raw transcripts for the eight candidate cases. This is Finding 8 and closes the largest current evidence gap.
2. **Repair the learning target:** add decision/outcome IDs and preserve `answered` separately from `useful`. Backfill only when a real external outcome can be joined; leave other historical rows unknown.
3. **Run three policies in shadow:** current implicit model behavior, existing lexical inquisitiveness, and NVA comparator. Include a known-positive control for every detector used to claim missing context or capability.
4. **Owner adjudication once:** present only high-impact policy disagreements, batched. Use those answers to ratify the first decision-rights rules.
5. **Visible canary:** enable minimal sufficient questions for one low-risk task class. Authority confirmations remain mandatory; no other class expands scope.
6. **Promote or roll back from external metrics:** promote only on fewer unnecessary questions with no meaningful rise in missed key/authority questions, task failure, reversal, or dropped decision IDs.

This sequence adds no hook. The policy module folds into the already registered shared UserPromptSubmit dispatcher (`settings.json:117-126`); outcome capture rides the existing event ledger; deferral rides open-loops; questioning rides AskUserQuestion; and consequence verification rides truth-verify/edit-checkpoints/Workflow. Every component is reversible and fail-open.

## Rejected alternatives and anti-overfit gate

1. **Wire the existing inquisitiveness hook unchanged — rejected.** It uses lexical vagueness rather than decision value, and any concrete token forces silence (`prompt-guard.py:108-144`). It also adds no proof that an answer changed the action.
2. **Ask whenever entropy/uncertainty is high — rejected.** Information gain without action sensitivity can purchase facts that do not change a decision. EIG is a feature, not the objective.
3. **Never ask; maximize autonomy — rejected.** Preference and authority are sometimes owner-only, and the `after_tool_use:true` “do not disable” correction candidate (`corpus.json:11897-11900`) is a warning against silent capability-reducing choices, though its antecedent remains UNVERIFIED until replay.
4. **Ask before every risky-looking action — rejected.** This makes the owner the guardrail runtime, violates prompt-fatigue, and trains indiscriminate confirmation behavior. Only typed authority boundaries mandate confirmation.
5. **Use a second orchestration/evaluation service or trained critic — rejected by the anti-overfit gate.** The existing dispatcher, event ledger, open-loops, AskUserQuestion, Workflow, truth-verify, and calibrated-silence stores are sufficient. A new daemon, vector/KG memory, durable engine, trained critic, observability SaaS, or guardrail framework adds coordination and failure surfaces without unique value.
6. **Let the same agent self-review the question — rejected by construction.** Every closure in this design comes from another tool/context/model or the owner. A same-context rationale may explain a proposal but never verifies it.

## Bottom line

The owner’s attention is worth spending at **preference forks, authority boundaries, and genuinely owner-only observations**—not on repository facts, tool choice, redeploy/monitoring, routine execution, or uncertainty that a safe external probe can settle. The gate should minimize verified downstream regret per unit of owner attention, not maximize answers or conversational engagement. The existing harness already has nearly every bus needed; the best design is a small, shadow-evaluated policy and outcome layer that folds into those buses, keeps every deferred decision durable, and refuses same-context self-certification.
