## Runtime model used to decide which text wins

Claude Code's current official subagent documentation states that a custom agent Markdown body becomes that subagent's **system prompt**, while the parent supplies a separate delegation/task message. It also states that automatic delegation is selected from the task, context, and the agent `description`, and that explicit naming can guarantee invocation. Source: <https://code.claude.com/docs/en/sub-agents>.

The official skills/commands documentation states that legacy `.claude/commands/<name>.md` files remain supported and create slash-command workflows like skills. Source: <https://code.claude.com/docs/en/slash-commands>.

Consequences:

- A command executes in the **parent** context.
- If that parent delegates, the child gets its own agent body as system instructions plus a delegation task message; it does not inherit the parent's full conversation/system prompt.
- Inside the child, the agent body is the higher-level instruction and therefore wins over an opposing delegation request.
- After the child returns, the parent still owns the user-visible response and can apply the command's instruction to the returned result.

This creates a particularly dangerous split: an agent may already take an action under its system prompt before the parent can re-apply a command-side stop rule.

The structural precedence above is very likely (80-90%) because it is stated by current official documentation and matches the files' use of agent frontmatter/body. The exact behavior of the owner's installed Claude Code build is **UNVERIFIED; settle it with the paired runtime experiments specified under each finding**, because the Linux bundle does not include the live Windows executable/session and automatic delegation is model-mediated.

### Opposing texts, verbatim

Command side, `/local_disk0/codexwork/bundle/claude/commands/code-review.md:38`:

>
> - **Approve**: No CRITICAL or HIGH issues

The agent's own sample reinforces the non-blocking classification at `/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:196-206`:

> | LOW      | 1     | note   |

### Concrete collision

A user runs `/code-review` on uncommitted changes. The review finds one genuine HIGH maintainability or error-handling defect and zero CRITICAL defects. The command requires a blocking result. The matching agent, whose description says it “MUST BE USED for all code changes” (`agents/code-reviewer.md:3`), requires `WARNING` and explicitly permits merge with caution.

This is a true contradiction for the same severity state; it is not merely a difference in detail.

### Runtime winner

- If the parent delegates the review to `code-reviewer`, the **agent wins inside the child** and emits WARNING/can-merge; the parent can then reclassify that output as blocking because it still has the command text.
- The final user-visible classification is likely (55-80%) to be **BLOCK**, because the command contains an unqualified direct instruction in the parent context. Evidence: `commands/code-review.md:38` plus the official parent/subagent context model above.
- Whether the current owner build automatically delegates this exact slash command is **UNVERIFIED; settle it by creating a fixture diff with one deterministic HIGH and no CRITICAL issue, running `/code-review` with debug transcript logging, and checking for an `Agent`/legacy `Task` call naming `code-reviewer` plus the final verdict**.

Even if the parent ultimately says BLOCK, the run can contain two incompatible terminal classifications, which is itself a coherence defect for automation consuming the subagent envelope.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Change only `/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:212-213` to:

> - **Block**: CRITICAL or HIGH issues found — must fix before merge
> - **Warning**: MEDIUM issues only (can merge with caution)

> - Add type annotations where missing

> npx eslint . --fix

### Concrete collision

A user runs `/build-fix`; the build reports `Cannot find module 'x'`, and inspection proves `x` is absent from the manifest/install. The command requires stopping and asking before `npm install`/`cargo add`. The matching agent is automatically eligible by description (“Use PROACTIVELY when build fails”) and tells itself to add/install the missing dependency.

This collision matters even if the parent later asks: a delegated child has Bash, Write, and Edit tools (`agents/build-error-resolver.md:4`) and can mutate the manifest, lockfile, or installed dependency tree before returning.

### Runtime winner

- Without delegation, the **command wins**: stop and ask.
- With delegation, the **agent system prompt wins inside the child**, so installation/addition is permitted before the parent regains control.
- Automatic delegation is likely (55-80%) because the agent description exactly matches build failures and says “Use PROACTIVELY”; evidence is `agents/build-error-resolver.md:3` and official automatic-delegation documentation.
- Actual mutation on the owner build is **UNVERIFIED; settle it in a disposable repository whose build imports an absent package, invoke `/build-fix` with debug logging, deny no tools, and inspect the manifest, lockfile, dependency directory, and transcript before answering any question**.

Thus there is no single unconditional runtime winner. The parent command wins only if no delegation/action occurs; after delegation, the agent wins at the point where the consequential tool call is made.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Edit three small locations in `agents/build-error-resolver.md`:

1. Line 52: replace “install package” with “identify the missing package and ask the user before installing or adding it”.
2. Line 64: replace “Add missing dependencies” with “Ask before adding missing dependencies; after approval, add only the named dependency”.
3. Lines 90-91: label reinstall as approval-gated and remove lockfile deletion from the default recipe; for example, `# Only after explicit approval: npm install`.

This edit is very likely (80-90%) to make the command and child agree at the action boundary because both would require the same explicit pause. Evidence: the command's exact guardrail and the agent's three opposing action clauses. It uses the existing command/agent prompt bus, introduces no new framework, and passes the anti-overfit gate.
