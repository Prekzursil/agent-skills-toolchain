# C004 — Context lifecycle: memory staleness

**Unit:** C004  
**Date:** 2026-07-19  
**Scope:** Measure how the present PreCompact, basic-memory, lexical-recall, and event-ledger mechanisms represent facts that later become false; evaluate the `superseded_by` / `valid_as_of` convention; design a minimal detection and recall lifecycle.  
**Subject mode:** read-only. The only write made by this unit is this artifact at the remote override path.

## Executive verdict

The current convention is directionally sound but operationally incomplete. `superseded_by` is a useful tombstone edge and `valid_as_of` is useful provenance, but neither field lets a note *know* that it has become stale. A note becomes detectably non-current only when an external signal arrives: a successor explicitly retires it, its declared validity interval ends, or a source receipt no longer matches and forces revalidation. Age alone is not falsity.

The most urgent defect is not missing metadata. It is that the existing consumer interprets the metadata backwards. The indexer places `superseded_by` on the old note (`agents/harness/recall_index.py:283-314`), while automatic recall labels that old note a contradiction and applies a 1.6 multiplier (`agents/harness/modules.py:1660-1673,1693-1710`). A read-only dynamic probe reproduced `old_quality=1.12`, `plain_quality=0.7`, ratio `1.6`. A failure-tagged old note remains `is_failure_head=True` even when `superseded_by` is populated; the probe reproduced `failure_plus_superseded_is_failure_head=True`, matching `recall_index.py:222-248`.

The event ledger has the same lifecycle split in a second implementation. A milestone correctly removes named failures from projected `open_failures` (`claude/hooks/event-ledger/ledger.py:276-284`), yet SessionStart independently renders recent raw failures without subtracting retired sequence numbers (`claude/hooks/event-ledger/sessionstart-replay.py:39-56`). A temporary-directory reproduction produced `open_failures=[]` and still rendered `- [failure] old false claim` next to `- [milestone] new success`. Thus stale information can re-enter context through both semantic recall and objective recovery.

The corpus establishes that this is a material path, not a hypothetical unused feature: 408 `write_note`, 357 `search_notes`, 353 `read_note`, 156 `edit_note`, and 11 `build_context` calls appear in the distilled transcripts (`inputs/corpus.json:239-244,271-276,335-340,1359-1364`; capability counts repeat at `:13476-13485,13607`). It does **not** establish the prevalence of stale notes or bad stale recalls. The corpus contains no `superseded_by`, `valid_as_of`, PreCompact, or event-ledger fields in its distilled sections, and its hook detector is explicitly broken (`inputs/corpus.json:13260-13263`). Owner-correction candidates are also recall-biased and failed a 41/41 smoke sample (`inputs/corpus.json:10371-10374`). Evidence does not support inventing an incidence rate.

The best design is evolution, not replacement: keep basic-memory as semantic authority, keep the event ledger as objective history, and add a small deterministic “currentness resolver” to the existing index/recall bus. Make the successor's `supersedes` edge authoritative because it is written atomically with the new content; keep `superseded_by` on the predecessor as a reciprocal back-reference, not the only edge. Resolve chains before ranking. Treat source drift and elapsed revalidation dates as `NEEDS_REVALIDATION`, not “false.” Do not generalize the existing truth-maintenance graph into a universal memory knowledge graph; that fails the anti-overfit gate and duplicates a rejected component.

I am **very likely (80-90%)** that this resolver will materially reduce stale-note injection, because both bad consumers are deterministic and reproduced, the proposal removes their exact admission paths, and selective-forgetting research finds that prompt-only overwrite instructions barely improve the hard cases. The remaining uncertainty is live prevalence: the Windows vault and event-ledger data files were not included in the Linux bundle.

The lifecycle convention requires at least two semantic mutations when a correction is represented as “edit old note with `superseded_by`; write new note with `valid_as_of`.” The more fragile operation is the old-note edit: 11.54% errors in the corpus versus 4.41% for writes. The write-ahead spool does not make that two-write protocol atomic. Therefore a successor note can land while the predecessor remains unmarked, or the predecessor edit can land while a successor write fails. This is a verified architectural race, not a measured live corruption count.

I am **almost certain (90-99%)** that making the new note's `supersedes` edge authoritative is safer than relying only on a later edit to the old note, because the edge and corrected content then land in one `write_note` payload, while current edit/write operations are separate and the edit path has both a higher measured error rate and no automatic replay.

### 2.3 Current schema and recall behavior

The current builder declares schema version 2 and says each note carries `mtime`, `importance`, `superseded_by`, `is_failure_head`, and `poisoned` (`agents/harness/recall_index.py:40-46`). It parses frontmatter, derives recency/importance, copies `superseded_by`, and computes `is_failure_head` (`:117-131,192-248,283-314`). It does not emit `valid_as_of`, `supersedes`, a fact identity, an explicit validity interval, or a source receipt into the index.

`valid_as_of` is used only as a Boolean indicator that a note might be the current chain head (`recall_index.py:225-248`). No date parsing or comparison occurs. A date of 2024-01-01 and a date of 2026-07-19 have identical effect. Consequently `valid_as_of` is provenance, not a staleness detector.

The consumer:

- skips poisoned notes and excluded paths (`agents/harness/modules.py:1632-1645`);
- computes lexical relevance, then multiplies by quality (`:1646-1650`);
- labels any `superseded_by` note `*contradiction*` and injects its own summary (`:1656-1673`);
- applies a 1.6 boost when either `superseded_by` or `is_failure_head` is truthy (`:1693-1710`);
- never dereferences the `superseded_by` permalink.

This is precisely backward for the documented convention in `claude/CLAUDE.md:5-11`: the old note is the one carrying `superseded_by`, and recall is supposed to surface current truth.

## 3. What “stale” must mean

A single Boolean `stale` collapses four materially different states:

1. **RETIRED:** a later authoritative assertion explicitly supersedes this one. It is historical, not current.
2. **EXPIRED:** its declared effective interval has ended. It may still be historically true.
3. **NEEDS_REVALIDATION:** a dependency changed or a review deadline passed. The fact is unknown, not proven false.
4. **AMBIGUOUS:** two current-looking assertions conflict, a link is broken/cyclic, or scope differs. Neither can safely be admitted as current truth.

The current convention handles only the first state, and only if an agent remembers to edit the old note. `valid_as_of` records assertion time; it does not distinguish the other three.

The resolver should derive, not freely author, a state:

```text
RETIRED            if a valid successor edge targets this note
EXPIRED            if valid_until < query_time
NEEDS_REVALIDATION if revalidate_after < query_time OR a source receipt mismatches
AMBIGUOUS          if chain cycles/breaks OR >1 incompatible current head exists
CURRENT            otherwise
```

A source mismatch must never directly mean RETIRED. A changed file, branch, API response, or dependency can leave the assertion true. It is only a falsifier trigger.

## 4. Evaluation of the existing convention against alternatives

| Alternative | How it detects staleness | Strength | Failure mode | Fit here |
|---|---|---|---|---|
| Current `superseded_by` on old + `valid_as_of` on new | Manual correction only | Human-readable history; simple permalink edge | Two non-atomic mutations; old edge can fail; `valid_as_of` is never compared; consumer boosts old note | Keep, but reverse authority and add resolver |
| Overwrite old note in place | Latest content replaces old | One write; retrieval is simple | Erases history, rationale, and evidence; no as-of queries; overwrite can silently replace scoped truth | Reject as canonical policy |
| Delete old note | Absence | Removes retrieval hazard | Destructive, loses audit trail; deletion itself has 20% error in five corpus calls; cannot explain corrections | Reject |
| Timestamp recency / exponential decay | Age heuristic | Cheap ranking | Old stable facts become under-ranked; new false claims win; age is not validity | Use only after currentness filtering |
| Fixed TTL | Wall-clock expiry | Good for inherently volatile facts | Declares stable facts stale; a TTL expiry says “unchecked,” not “false” | Optional `revalidate_after`, never universal |
| `valid_from` / `valid_until` effective-time interval | Query time outside interval | Supports as-of questions and scheduled expiry | Requires author knowledge; many changes are not scheduled | Add optional fields |
| Append-only “latest timestamp wins” | Newer record with same key | Atomic successor write; simple materialized view | Chronology is not authority; concurrent scopes and corrections can be incomparable | Use only with stable `fact_key` and explicit edge/scope |
| Bidirectional supersession (`supersedes` + `superseded_by`) | Either edge proves correction; reconciliation checks reciprocity | Survives a failed back-edit; navigable both ways | Broken links/cycles require deterministic handling | Best minimal correction model |
| Source receipts (`git HEAD`, file hash, API version/ETag) | Dependency mismatch triggers revalidation | Mechanically detects change | Change is not falsity; remote checks can be slow/unavailable | Add bounded local receipts |
| Truth-maintenance / dependency graph | Premise retraction propagates OUT | Strong for derived technical anchors | Graph admission cost, universal ontology, new memory runtime; existing TMS is RE-specific | Do not generalize |
| LLM contradiction classifier over all notes | Semantic model judges conflict | Can discover unstructured contradictions | Expensive, nondeterministic, false positives, trained-critic/guardrail drift | Reject as gate; optional offline candidate miner only |
| Full replacement with a temporal KG/vector DB | Graph/time queries | Richest theoretical model | Reintroduces explicitly rejected KG/vector memory and second runtime; migration and operational surface dwarf evidence | Reject under anti-overfit gate |

### 4.1 Research grounding

LongMemEval evaluates knowledge updates and temporal reasoning as distinct abilities and reports that time-aware indexing/query expansion improves temporal-subset recall by 11.3% for round values and 6.8% for session values. It also sorts retrieved items by timestamp. Primary source: https://arxiv.org/html/2410.10813v2#S5.SS4 and abstract/API record https://arxiv.org/abs/2410.10813v2.

This supports indexing explicit time and filtering by query time. It does **not** prove that “newest always wins,” nor does it validate this harness's proposed field names.

MemoryAgentBench defines selective forgetting as revising, overwriting, or removing prior information under contradictory evidence. Its 2026 revision tests explicit overwrite prompts: GPT-4.1-mini baseline averaged 20.5% on the two FactConsolidation tasks; “always prefer later” reached 22.0% (+1.5), while a conservative explicit-negation policy fell to 16.0%. The paper says the aggressive prompt failed to generalize to multi-hop updates. Primary source: https://arxiv.org/html/2507.05257v4#A11.SS2; abstract/API record https://arxiv.org/abs/2507.05257v4.

This is direct evidence that a prose rule alone is weak. I am **very likely (80-90%)** that deterministic pre-ranking retirement will outperform merely strengthening the instruction, because the local defect occurs before the model sees context and the benchmark's prompt-only delta is small on the evaluated selective-forgetting tasks.

## 5. Recommended lifecycle architecture

### Proposal 1 — Correct chain resolution before any schema-v2 rebuild

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Change `RecallModule._composite_recall` so currentness is resolved before relevance/quality ranking:

1. Build a `permalink -> note` map from the already-loaded bounded lexical index.
2. If a note has `superseded_by`, follow at most eight hops with a visited set.
3. If the successor resolves, do not rank or emit the predecessor; rank the terminal successor once.
4. If it does not resolve or cycles, emit only a compact `AMBIGUOUS/BROKEN_CHAIN` pointer when relevant—never the old summary as fact.
5. Apply the 1.6 contradiction boost only to an unsuperseded `is_failure_head`.
6. In `_is_failure_head`, check `superseded_by` before failure tags/types. A retired failure is historical.
7. Validate `schema_version == 2` and freshness before automatic injection; otherwise inject nothing and route to explicit MCP recall/rebuild.

Acceptance fixtures:

- old -> new: only new content enters context;
- old failure -> new success: old gets no failure-head boost;
- old -> missing: warning/pointer, no old content;
- A -> B -> C: C once;
- A -> B -> A: ambiguity warning, no factual content;
- two unrelated notes: unchanged ranking;
- history/as-of query: old may be returned only as explicitly labeled historical evidence.

This fix is **almost certain (90-99%)** to remove the reproduced 1.6× promotion path because it directly changes the predicates that produced the probe output. Whether it materially changes owner-visible outcomes is **UNVERIFIED**; the settling experiment is the paired replay benchmark in §9.4.

### Proposal 2 — Make successor-owned supersession authoritative and add a currentness envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For durable factual/decision notes that can change, standardize this additive frontmatter:

```yaml
permalink: projects/reframe/runtime-choice-2026-07-19
fact_key: reframe/runtime-choice
scope: project/reframe
valid_from: 2026-07-19T00:00:00Z
valid_until: null
revalidate_after: 2026-08-19T00:00:00Z
supersedes:
  - projects/reframe/runtime-choice-2026-06-20
superseded_by: null
source_receipts:
  - kind: git
    locator: source/agent-skills-toolchain
    revision: 58686d3
  - kind: file
    locator: path/to/config
    sha256: "..."
```

Semantics:

- `fact_key` identifies a replaceable proposition family, not an entire document topic.
- `scope` prevents “same key, different environment” from becoming a false contradiction.
- `valid_from` replaces the underspecified temporal meaning of `valid_as_of` for new notes. Continue reading legacy `valid_as_of` as `valid_from` for compatibility.
- `valid_until` means the author knows the effective interval ends then.
- `revalidate_after` means “do not trust without checking after this time”; it is not expiry.
- `supersedes` on the new note is authoritative. It lands atomically with corrected content through one `write_note`.
- `superseded_by` on the old note is a reciprocal navigation aid. A PostToolUse reconciliation edit may add it, but failure does not hide the correction.
- `source_receipts` provide falsifiable dependencies. Mismatch yields `NEEDS_REVALIDATION`.

Admission behavior on the already-registered memory write path (`claude/hooks/_dispatch/manifest.json:182-204`):

- stable preference or immutable lesson: fields optional;
- volatile fact/decision tagged `current`, `decision`, `failure`, `api_behavior`, or `version`: require `fact_key`, scope, effective time, and either a receipt or `revalidate_after`;
- new note with same `(scope, fact_key)` but a different value/head: inject a non-blocking candidate-conflict reminder requiring `supersedes` or an explicit `coexists_with`/scope distinction;
- never let an LLM automatically retire a note merely from semantic similarity.

I am **very likely (80-90%)** that successor ownership reduces incomplete-chain failures because it turns the load-bearing direction into one idempotent write, supported by the measured edit/write error asymmetry and spool replay behavior. I am **likely (55-80%)** that the full envelope remains under ~200 implementation lines if parsing/reconciliation is added to the existing builder/dispatcher rather than a new service; evidence is the current compact indexer and hook manifest, but exact size is **UNVERIFIED** until a spike implements the six fixtures above.

### Proposal 3 — Add bounded currentness checks at recall, not universal background polling

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For the at-most-three candidates already selected by `RecallModule` (`agents/harness/modules.py:1575-1597`), run cheap checks before injection:

- compare `valid_until` / `revalidate_after` to current UTC;
- for local file receipts, compare size/mtime first and hash only on mismatch;
- for git receipts, compare the recorded revision to the repository HEAD already available through existing ledger/git helpers;
- do not make network calls inside UserPromptSubmit or PreCompact;
- remote/API receipts use `revalidate_after` and an explicit task-time check when the fact matters.

The result is one of `CURRENT`, `RETIRED`, `EXPIRED`, `NEEDS_REVALIDATION`, or `AMBIGUOUS`. Only `CURRENT` enters context as unqualified factual memory. `NEEDS_REVALIDATION` produces a one-line advisory with the exact check; `RETIRED` resolves to the successor; `EXPIRED` is available only for historical queries; `AMBIGUOUS` exposes links, not summaries.

This is **likely (55-80%)** to fit the hook latency budget because only up to three candidates receive local checks and no network operation is permitted; the evidence is `max_results <= 5` and the current five-second PreCompact registration. Latency is **UNVERIFIED**; the settling experiment is the p50/p95/p99 benchmark in §9.3 with cold Windows filesystem and Git worktrees.

### Proposal 4 — Filter event-ledger recovery through its own tombstones

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Before rendering `notable` events in `sessionstart-replay.py`:

1. collect every `supersedes_failures` sequence ID from the replay window;
2. exclude those failure events from “Recent decisions/notes”;
3. retain the milestone;
4. if a superseded failure falls outside the replay window but remains absent from projected `open_failures`, trust the projection and do not reconstruct it as active;
5. label the section “recent lifecycle events,” not undifferentiated ground truth.

Also allow decision/note supersession as an additive generic `supersedes_events` field rather than overloading failure-only semantics. The event ledger remains append-only; only the view changes.

This is **almost certain (90-99%)** to remove the reproduced stale-failure replay because the temporary fixture directly demonstrates the selection error and supplies an exact regression test.

### Proposal 5 — Keep PreCompact as a pointer capsule; do not perform stale-memory discovery there

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

PreCompact has a five-second host budget and basic-memory writes have real connection/transport failures. It should record a bounded continuation envelope containing:

- ledger sequence/pointer;
- active `fact_key -> terminal permalink` references actually used this session;
- each reference's derived currentness at last use;
- source-receipt fingerprints, not copied note prose;
- exact next action and verification condition;
- counts/checksums for omitted sections.

PostCompact/SessionStart should resolve those permalinks again before restoring their content. If a head moved during compaction, restore the successor; if a receipt drifted, inject `NEEDS_REVALIDATION`. Never snapshot a stale summary and then trust the snapshot because it is newer.

I am **very likely (80-90%)** that pointer-based recovery is safer than copying semantic prose because the current checkpoint already stores a ledger pointer, checkpoints are excluded from ordinary recall, and the resolver can validate the referenced head at restore time. The effect on recovery completeness is **UNVERIFIED**; the settling experiment is the forced-compaction sequence in §9.5.

### Proposal 6 — Rebuild the lexical index after successful memory mutations, with coalescing and validation

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

After a confirmed `write_note` or `edit_note` PostToolUse:

- mark the index dirty;
- coalesce multiple writes for 10-30 seconds;
- rebuild off the critical hook path;
- atomically publish only if schema, note count, skipped-file count, and vault fingerprint validate;

## 7. Detailed state and recall contract

### 7.1 Invariants

1. A note cannot declare itself current merely because it is newest.
2. A note with a resolved incoming successor edge cannot enter ordinary context as current.
3. A source change means revalidate, not false.
4. `valid_as_of` alone never expires a note.
5. A successor write is complete enough to retire predecessors even if reciprocal old-note edits fail.
6. Broken/cyclic chains fail closed for factual injection and fail open for tool execution: warn, never block normal work.
7. Historical/as-of queries may retrieve retired notes, explicitly labeled with their interval and successor.
8. Checkpoints carry references and receipts; they do not mint truth.
9. Event-ledger projections and rendered recovery views must use the same tombstone set.
10. No semantic classifier may autonomously change lifecycle state.

### 7.2 Resolution pseudocode

```python
def resolve(note, by_permalink, now):
    seen = set()
    cur = note
    for _ in range(8):
        if cur.permalink in seen:
            return AMBIGUOUS("cycle", seen)
        seen.add(cur.permalink)

        nxt = cur.superseded_by
        if nxt:
            if nxt not in by_permalink:
                return AMBIGUOUS("missing-successor", nxt)
            cur = by_permalink[nxt]
            continue

        incoming = terminal_successors_from_supersedes(cur.permalink)
        if len(incoming) > 1 and not scopes_are_disjoint(incoming):
            return AMBIGUOUS("multiple-heads", incoming)
        if len(incoming) == 1:
            cur = incoming[0]
            continue
        break
    else:
        return AMBIGUOUS("hop-limit", seen)

    if cur.valid_until and now >= cur.valid_until:
        return EXPIRED(cur)
    if cur.revalidate_after and now >= cur.revalidate_after:
        return NEEDS_REVALIDATION(cur, "deadline")
    mismatch = first_local_receipt_mismatch(cur)
    if mismatch:
        return NEEDS_REVALIDATION(cur, mismatch)
    return CURRENT(cur)
```

The actual implementation need not create a new class hierarchy; a small enum/string plus structured reason is enough.

### 7.3 Conflict admission

When a new note shares `(scope, fact_key)` with a current head:

- same normalized value/receipt: treat as a refresh; update `valid_from`/receipt only if intentional;
- different value and explicit `supersedes`: accept successor, reconcile back-reference;
- different value and disjoint scope: accept both;
- different value without relationship: accept the write fail-open but mark both `AMBIGUOUS` in the index and inject a reconciliation reminder;
- no `fact_key`: preserve legacy behavior; do not guess a collision.

Fail-open writing is important because memory availability defects are measured, and blocking a note on uncertain semantic policy can lose the correction itself. Admission enforcement can become blocking only for structurally malformed lifecycle metadata after the shadow benchmark proves safe; until then it is advisory.

## 8. Alternatives deliberately rejected

### 8.1 “Just strengthen the rule”

Rejected. The existing rule already says exactly what to do (`claude/CLAUDE.md:9-11`), yet the consumer reverses it. MemoryAgentBench's prompt-only overwrite improvement was +1.5 average points and did not help multi-hop updates. A rule is useful author guidance, not a retrieval invariant.

### 8.2 “Newest timestamp always wins”

Rejected as a general rule. A later note can be less authoritative, scoped to another branch/environment, or merely a hypothesis. Timestamp is one ordering dimension. Explicit edges and scopes decide replacement.

### 8.3 “Decay all old facts”

Rejected. The current exponential recency factor (`agents/harness/modules.py:1699-1710`) is reasonable only after removing retired/unknown notes. It cannot turn age into truth.

### 8.4 “Delete retired notes”

Rejected. Historical failures and decisions are valuable for as-of reasoning and avoiding repeated dead ends. The problem is context admission, not storage existence.

### 8.5 “Use the event ledger as the only memory”

Rejected. The ledger is project-local objective chronology plus annotations; basic-memory is cross-tool semantic knowledge. The source contract explicitly distinguishes these roles (`claude/AGENTS.md:24-36,114-120`; `codex/AGENTS.md` persistent-memory section). Collapsing them would weaken either semantics or objective provenance.

### 8.6 “Replace everything with TMS/temporal KG”

Rejected by the anti-overfit gate. The owner already has an RE-specific TMS, and its universal expansion would require fact extraction, dependency admission, ontology, reconciliation, migration, and a new canonical authority. No measured local benefit justifies that BUILD-LARGE surface.
