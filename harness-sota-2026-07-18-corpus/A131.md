## Runtime precedence: what can and cannot be established

The current official Claude Code MCP documentation establishes the general resolution rules:

* A deployed Windows `C:\Program Files\ClaudeCode\managed-mcp.json` is exclusive: Claude Code loads only its defined servers; user, project, plugin, and connector servers do not load. `allowedMcpServers`/`deniedMcpServers` may further filter that managed set. Source: <https://code.claude.com/docs/en/managed-mcp>.
* Without exclusive managed MCP, duplicate names resolve local > project > user > plugin > claude.ai connector; plugins/connectors are deduplicated by endpoint. Source: <https://code.claude.com/docs/en/mcp#scope-hierarchy-and-precedence>.
* Enabled plugin MCP servers start automatically, and `/reload-plugins` can connect or disconnect plugin MCP servers within a session. Source: <https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers>.

These rules explain how to determine a winner after the real definitions and launch context are known. They do **not** identify this owner’s effective runtime set. Runtime also depends on whether managed MCP exists, current working directory/local project entry, project approval, plugin state, environment expansion, authentication, and connection health. **UNVERIFIED:** the effective server for any candidate below remains unknown; the settling experiment is the read-only Windows capture listed later (`Test-Path`, safe JSON parse, `claude mcp list`, and `claude mcp get <name>` from both home and a representative repo).

There is also an important category boundary. A command markdown file is an instruction/prompt; MCP JSON is capability configuration. A command saying “call X if available” and config disabling or omitting X are not direct textual opposites because the condition handles absence. A command saying an endpoint is canonical while the effective same-named server is configured to a different endpoint *can* collide at runtime. This unit retained only the latter kind as a candidate.
