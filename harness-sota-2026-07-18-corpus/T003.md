# T003 — competitive teardown: Cline

**Research date:** 2026-07-19 UTC  
**Unit:** T003  
**Subject:** Cline (IDE extensions, CLI, SDK/ClineCore, experimental subagents/teams, and Kanban)  
**Owner baseline:** unpacked read-only harness at `/local_disk0/codexwork/bundle`

## Executive judgment

Cline is not a compelling full replacement for this owner's Claude Code harness. Its ordinary loop is the familiar minimal coding-agent loop—model request, tool calls, tool results, repeat until completion—and its most attractive user-facing facilities now have native Claude Code equivalents. Cline is nevertheless useful as a design reference in three areas: (1) explicit hook execution policies, (2) operator-friendly MCP lifecycle controls, and (3) conversation-linked project snapshots that include command effects. The third is also the most dangerous thing to copy indiscriminately.

The best near-term imports are therefore small and native-bus-aligned:

1. **CONFIG — stop exposing dead MCPs.** Cline makes enabled/disabled state, restart, timeout, and server status ordinary control-plane concepts. This owner has a measured dead Tavily endpoint still receiving 532 calls with 25.8% errors. Remove/disable it rather than teaching the model to route around it. This is **almost certain (90-99%)** to eliminate the 135 measured “not connected” calls from that endpoint because those calls require the dead tool to remain exposed; evidence is the pinned corpus measurement plus Cline's documented per-server `disabled` flag and enable/disable controls ([MCP overview](https://docs.cline.bot/mcp/mcp-overview)).
2. **BUILD-SMALL — add explicit hook policy metadata and durable outcomes.** Port only Cline's `mode`, timeout, retry, failure-mode, concurrency, and queue semantics into the existing dispatcher, not its SDK runtime. This is **very likely (80-90%)** to make hook behavior easier to reason about because the current `settings.json` expresses timeouts but not those other policies (`/local_disk0/codexwork/bundle/claude/settings.json:81-529`), while the known-defects file says hook behavior across 1,964 sessions is presently unmeasurable (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:131-147`). The remaining uncertainty is implementation fit, not whether explicit outcomes improve observability.
3. **NATIVE — use Claude Code's checkpoint/rewind and IDE diagnostic sharing before building Cline-like substitutes.** Claude Code already snapshots direct edits, rewinds files/conversation independently, persists checkpoints with sessions, and shares IDE diagnostics ([Claude checkpointing](https://code.claude.com/docs/en/checkpointing), [IDE integration](https://code.claude.com/docs/en/ide-integrations)). Cline's shadow-Git snapshot after every command covers more mutations, but its own docs warn of storage and performance costs on large repositories ([Cline checkpoints](https://docs.cline.bot/core-workflows/checkpoints)); public issues include task stalls and destructive restore reports ([#4578](https://github.com/cline/cline/issues/4578), [#1213](https://github.com/cline/cline/issues/1213)).

Do **not** import ClineCore's hub/spoke daemon, persistent team runtime, or Kanban as a second orchestration plane. Those are **BUILD-LARGE** and explicitly fail the owner's anti-overfit gate: they recreate a daemon/durable execution layer already rejected, while this harness already has native agent teams, worktree hooks, cross-vendor fan-out, and an existing local mailbox (`/local_disk0/codexwork/bundle/claude/settings.json:5-7,419-529`; `/local_disk0/codexwork/bundle/claude/CLAUDE.md:15-82`). It is **very likely (80-90%)** that adding ClineCore would increase operational surface more than capability because the overlap is concrete and the corpus already ties command-line inflation to roughly 1,293 orphaned plugin directories; the uncertainty is the value of Cline's multi-client UI, not the duplicated runtime.

## Scope and evidence discipline

## 1. Agent loop

### Cline mechanism

The SDK documentation states the loop directly:

```text
run() or continue()
  -> model request
  -> tool calls, if any
  -> tool results
  -> repeat until complete
```

`AgentRuntime` holds message state, emits streamed events, supports `abort`, `restore(messages)`, and `snapshot()`, and returns status, iteration count, output text, messages, usage, and error ([Agent reference](https://docs.cline.bot/sdk/reference/agent), [ClineCore loop](https://docs.cline.bot/sdk/clinecore)). The host-facing event surface includes content, iteration, usage, notice, done, and error categories; the low-level stream includes tool-started/tool-finished and usage-updated events ([events](https://docs.cline.bot/sdk/events)).

Completion can be made explicit in SDK agents: a custom tool can declare `lifecycle: { completesRun: true }`; without one, the example says the loop continues until `maxIterations` ([building an agent](https://docs.cline.bot/sdk/guides/building-an-agent)). In ordinary Cline, the historical `attempt_completion` tool serves the same model-facing “I am done” role; changelog entries show repeated fixes for duplicate completion rendering, which is evidence that the signal is operationally fallible rather than a proof of correctness ([CHANGELOG 3.25.x](https://github.com/cline/cline/blob/main/CHANGELOG.md)).

Plan/Act is a capability gate, not a second planner runtime. Plan reads and searches but cannot modify files or execute commands; Act keeps the same conversation and unlocks mutation. Users may select different models for the two modes ([Plan & Act](https://docs.cline.bot/core-workflows/plan-and-act)). `/deep-planning` is a prompt workflow: silent investigation, discussion, `implementation_plan.md`, then a new implementation task ([commands](https://docs.cline.bot/core-workflows/using-commands)).

### Comparison

The minimal loop is neither better nor meaningfully different from Claude Code. This owner's harness layers extensive behavior and hook policy over Claude's native loop: assumption ledger, goal reinjection, two-strikes pivot, terminal-state result markers, generator/critic check, and blast-radius tracing (`/local_disk0/codexwork/bundle/claude/AGENTS.md:7-113`). Cline's public docs do not document equivalents to those safeguards.

Cline's separate Plan/Act model selectors are a genuine ergonomic delta in the Cline UI. **UNVERIFIED:** no equivalent per-mode model mapping was found in the unpacked `settings.json` (which sets one `model` and a fallback at lines 77-80) or in current Claude Code Plan-mode docs; the settling experiment is to inspect `claude config` schema/help on the Windows host for mode-specific model keys. A text search that successfully found `useAutoModeDuringPlan` at `/local_disk0/codexwork/bundle/claude/settings.json:703` found no plan-model key, but that alone is not a second proof of product absence.

### Recommendation — do not add a second loop

There is no proposal to port `AgentRuntime`. It violates the anti-overfit gate by duplicating the native loop. Cline's clean interfaces are useful for tests and embedding, but the owner is optimizing an operating harness, not building an SDK product.

## 2. Context management

### Cline mechanism

Cline has four context controls:

1. **Selective acquisition:** tree/AST inspection, regex search, and relevant file reads rather than indiscriminate repository ingestion ([README](https://github.com/cline/cline/blob/main/README.md)).
2. **`.clineignore`:** gitignore-style patterns exclude files from the starting tree, automatic context gathering, and search, while explicit `@file` mentions can override the exclusion ([`.clineignore`](https://docs.cline.bot/customization/clineignore)).
3. **Auto Compact:** token monitoring triggers a model-generated comprehensive summary which replaces history; the task continues in place. The docs explicitly say unsupported models fall back to rule-based truncation ([Auto Compact](https://docs.cline.bot/features/auto-compact)).
4. **Manual boundaries:** `/smol` compacts the current task; `/newtask` distills plan, completed work, relevant files, and next steps into a fresh task ([commands](https://docs.cline.bot/core-workflows/using-commands)).

Checkpoints and message editing integrate with context: users may restore files only, task/messages only, or both ([checkpoints](https://docs.cline.bot/core-workflows/checkpoints)). Cline's changelog dates Auto Compact and Focus Chain to 3.25.0 and records later fixes around restored tasks, context warnings, and context-window handling ([CHANGELOG](https://github.com/cline/cline/blob/main/CHANGELOG.md)).

### Comparison

Claude Code already has `/compact`, `/clear`, `/context`, session resume/fork, automatic compaction, and targeted checkpoint summarization. Current checkpointing offers “summarize from here” and “summarize up to here,” preserving the untouched side of a selected message; Cline's public docs describe whole-history replacement rather than this targeted operation ([Claude sessions](https://code.claude.com/docs/en/sessions), [Claude checkpointing](https://code.claude.com/docs/en/checkpointing)). On this axis current Claude Code is better.

The owner also has more ambitious continuity than Cline's Memory Bank: a semantic `basic-memory` MCP, temporal supersession links, automatic PreCompact checkpointing, and an objective event ledger replayed at SessionStart (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13`; `/local_disk0/codexwork/bundle/claude/AGENTS.md:28-35,85-91`). The known defect is observability of hooks, not absence of continuity (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:131-147`).

### Recommendation — NATIVE (UNVERIFIED active-use): exercise targeted summarize/rewind

**NATIVE (Claude Code already does this; we just enable it).** Use Claude's targeted summarize/rewind for side investigations instead of adding Cline's `/newtask` clone. **UNVERIFIED:** active use on the owner host has not been observed; the settling experiment is the disposable-repository `/rewind` test specified above. It is **very likely (80-90%)** to reduce context loss compared with whole-session compact because the operator chooses which side of a concrete message is summarized, and the original transcript remains locally available; evidence is the documented mechanism, with uncertainty about owner workflow fit.

### What not to copy

Do not copy the claim that summaries preserve “all” technical decisions. That is marketing language, not a mechanically verified invariant. A public Cline discussion reports compaction firing both too late and too early under different versions; it is anecdotal, not a rate estimate, but enough to reject an infallibility claim ([discussion #3248](https://github.com/cline/cline/discussions/3248)). Cline also falls back to truncation on unsupported models. The owner's objective ledger is a stronger source-of-truth pattern than trusting any generated summary.

## 3. Memory

### Cline mechanism

Cline's documented Memory Bank is not native semantic memory. It is a rules-driven markdown convention:

```text
memory-bank/
  projectbrief.md
  productContext.md
  activeContext.md
  systemPatterns.md
  techContext.md
  progress.md
```

The agent is instructed to read all files after reset and update them after milestones. Continuity is manual: update the bank, start a new conversation, tell Cline to follow the custom instructions ([Memory Bank](https://docs.cline.bot/best-practices/memory-bank)). ClineCore separately persists complete session messages and metadata, and the hub stores a SQLite listing index plus authoritative JSON session records ([hub/spoke](https://docs.cline.bot/sdk/architecture/hub-spoke)). Those are session persistence, not learned-memory retrieval.

### Comparison: Cline is worse

The owner already separates semantic memory (`basic-memory`) from objective turn history (event ledger) and records temporal invalidation (`superseded_by`, `valid_as_of`) at `/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13` and `/local_disk0/codexwork/bundle/claude/AGENTS.md:85-91`. Cline's six always-read files have no documented relevance retrieval, provenance enforcement, supersession semantics, contradiction handling, or stale-fact detector. They consume prompt tokens and rely on the model to maintain them correctly.

There is no port proposal. A second markdown memory hierarchy would duplicate the owner's existing memory and violate the anti-overfit principle by creating another truth surface. Cline's best idea here is organizational legibility, which can be applied to existing memory notes without importing the structure.

## 4. Tools and MCP

### Built-in and custom tool flow

In ClineCore, built-ins cover editor/read/patch/search, Bash, web fetch, and user questions. MCP tools load alongside built-ins. The lightweight `Agent` has no built-ins; the embedding application supplies tools explicitly ([tools reference](https://docs.cline.bot/tools-reference/all-cline-tools)). SDK tools have type-safe schemas and can designate completion lifecycle. SDK/CLI/Kanban plugins can register custom tools; current VS Code and JetBrains extensions cannot use those plugin custom tools, an important scope limitation in Cline's own docs.

Cline's IDE agent monitors terminal output, including background dev-server output, and can react to new failures. It also uses an integrated browser that captures screenshots and console logs ([README](https://github.com/cline/cline/blob/main/README.md)).

### MCP lifecycle

Cline supports local STDIO and remote Streamable HTTP/SSE definitions. Each server has `disabled` and `autoApprove` fields. The CLI wizard can list, add, edit, enable/disable, and delete servers. The UI can enable/disable, restart unresponsive servers, set request timeouts, and remove them ([MCP overview](https://docs.cline.bot/mcp/mcp-overview)). The docs tell users to verify that tools appear and test one call; they do **not** document automatic health quarantine.

Claude Code already exposes `claude mcp list/get/remove` and an in-session `/mcp` status panel. The panel shows tool counts, flags servers that claim tool capability but expose none, and waits for still-connecting servers through ToolSearch ([Claude MCP](https://code.claude.com/docs/en/mcp)). The owner also enables ToolSearch and defines MCP timeouts at `/local_disk0/codexwork/bundle/claude/settings.json:12-17`.

### Recommendation — CONFIG: quarantine the measured dead MCP

**CONFIG (settings/JSON only).** Remove or disable the dead Tavily definition at its source, then verify it is absent from both `claude mcp list` and `/mcp`; retain a different known-live server as the detector control. Do not merely add a routing instruction—the tool must not be exposed. This is **almost certain (90-99%)** to prevent further calls specifically to that dead server because an undiscoverable tool cannot be selected; evidence is the measured 135 “not connected” failures and both products' config-driven tool discovery. This is ordinary configuration hygiene and passes the anti-overfit gate.

**UNVERIFIED:** the exact owning config for `claude_ai_Tavily` is not included in the Linux bundle. The settling experiment is `claude mcp get <exact-name>`, `/mcp`, and a search of the Windows user/project/managed MCP scopes before editing. This does not weaken the removal recommendation; it limits only the target file.

### Recommendation — BUILD-SMALL (UNVERIFIED): session-start MCP negative health gate

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** **UNVERIFIED:** whether Claude Code's hook input can mutate the active MCP exposure list mid-session is not established; the settling experiment is to disable a disposable MCP config entry during SessionStart, reload plugins if required, and confirm the tool vanishes from ToolSearch. If mutation is unavailable, the gate must fail fast with a specific config-removal instruction, not pretend to quarantine.

Port Cline's control-plane idea as a small preflight: enumerate configured servers, read product-native status, emit `CONNECTED`, `CONNECTING`, `DISABLED`, or `FAILED`, and refuse to label absence until a known-live control is detected. Do not probe every MCP tool and do not introduce a daemon. This is **likely (55-80%)** to prevent recurrence of stale dead-tool exposure because SessionStart is already wired and the defect is stable config, but the confidence is limited by the UNVERIFIED ability to remove tools from an already-built prompt.

### What not to copy

* Cline lets the model author the command's `requires_approval` classification ([Auto Approve](https://docs.cline.bot/features/auto-approve)). That places a security decision inside the untrusted planner. The owner has deterministic PreToolUse guards and explicit permission patterns, despite their current false-positive defects.
* “Ask Cline to add a tool” can generate and install an MCP server. This is convenient but couples code generation, installation, credential configuration, and trust. The owner's hard rule requires explicit build scope and read-only default; preserve that separation.
* Cline has manual restart and disable controls, not documented automatic dead-server quarantine. Do not credit it with self-healing it does not claim.

## 5. Permission model

### Cline mechanism

Cline's default interaction presents approvals for edits, commands, browser, and MCP. Auto Approve is evaluated per tool/category: project versus all-file read/edit, safe versus all commands, browser, MCP, and notifications. The model supplies a `requires_approval` flag for commands; Cline says this is not a fixed allowlist. YOLO mode approves everything, including all file operations, destructive commands, browser actions, MCP, and mode transitions ([Auto Approve](https://docs.cline.bot/features/auto-approve)). Plan mode is read/search-only and cannot execute commands ([Plan & Act](https://docs.cline.bot/core-workflows/plan-and-act)).

The SDK uses per-tool `enabled` and `autoApprove` policies plus an application callback that can inspect the actual request. A serious footgun is documented: omitted SDK policies default to **enabled and auto-approved** ([permission handling](https://docs.cline.bot/sdk/guides/permission-handling)).

### Comparison

Claude Code's permission engine is richer: allow/ask/deny rules, permission modes, protected paths, hooks, and auto mode. But this owner's effective configuration sets `defaultMode` to `bypassPermissions` at `/local_disk0/codexwork/bundle/claude/settings.json:26-75`, so the safer product capability is intentionally bypassed. Explicit deny entries for environment, PEM, and credentials remain configured at lines 64-68, while hooks add further policy.

Cline's ordinary human-in-the-loop default is safer than this owner's effective default; Cline's YOLO mode and model-self-classified “safe command” are not safer. Claude's documentation explicitly states that `bypassPermissions` offers no protection against prompt injection or unintended actions ([Claude permission modes](https://code.claude.com/docs/en/permission-modes)).

### Recommendation — CONFIG (UNVERIFIED workflow tolerance): retire default bypass

**CONFIG (settings/JSON only).** **UNVERIFIED:** the owner's tolerance for interactive prompts versus Claude auto mode is not in the corpus; the settling experiment is a one-week A/B on representative repositories, recording approvals, blocked safe actions, dangerous catches, and completion time. Set a non-bypass default (`auto`, `dontAsk`, or another owner-selected native mode), and reserve bypass for recognized disposable sandboxes. It is **almost certain (90-99%)** to reduce the blast radius of prompt injection because bypass explicitly removes permission protection; evidence is the current setting and Claude's official warning. The productivity effect is **roughly even (45-55%)** until the A/B, because this harness's noisy guards may offset fewer permission prompts.

### What not to copy

Do not copy SDK's “unspecified means enabled and auto-approved.” Secure defaults must fail closed for mutation and egress. Do not copy YOLO as a standing mode. Do not replace semantic command checks with the model's self-declared safety boolean; the known prose-versus-code guard defect should be repaired with structured tool fields, not by delegating the verdict to the same model proposing the action (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-107`).

## 6. Customization: rules, skills, hooks, plugins

### Rules and skills

Cline reads `.clinerules/`, `.cursorrules`, `.windsurfrules`, project `AGENTS.md`, and global `~/.agents/AGENTS.md`; rules have UI toggles and workspace-over-global precedence. Path-conditional rules use YAML `paths` globs and activate from mentioned paths, open/visible files, and edited files ([rules](https://docs.cline.bot/customization/cline-rules)).

Skills use the now-standard progressive disclosure design: about 100 tokens of name/description at startup, under 5k of SKILL.md instructions on `use_skill`, and resources read or executed only as needed. Skills can auto-trigger or be invoked as slash commands ([skills](https://docs.cline.bot/customization/skills)).

These are not owner gaps. The harness has path-scoped rule frontmatter, permits the Skill tool, sets a skill-listing budget, and has approximately 355 installed skills (`/local_disk0/codexwork/bundle/claude/settings.json:3,39-42`; pinned corpus; concrete Kotlin rule controls cited above). The problem is 78/355 use and orphaned plugin inflation, not missing skill packaging.

### Hooks and plugins

Cline's SDK plugin interface bundles tools, commands, rules, hooks, events, and configuration. Documented hook stages include input, runtime/session/run/iteration/turn boundaries, before-agent, before/after tool, stop/error, and shutdown. Hook policies include:

* `mode`: blocking or async;
* `timeoutMs`;
* `retries` and `retryDelayMs`;
* `failureMode`: fail-open or fail-closed;
* `maxConcurrency`;
* `queueLimit`.

Plugins can register `beforeRun`, `afterRun`, `beforeModel`, `afterModel`, `beforeTool`, `afterTool`, and `onEvent`; examples include custom compaction, metrics, policy guards, background jobs, and LSP tools ([plugins](https://docs.cline.bot/sdk/plugins), [plugin examples](https://docs.cline.bot/sdk/plugin-examples)).

Claude Code already has a broader native hook bus in this harness: SessionStart, prompt submit, Pre/PostToolUse, failure, Pre/PostCompact, config change, subagent/team lifecycle, Stop, and worktree lifecycle (`/local_disk0/codexwork/bundle/claude/settings.json:81-529`). Cline's edge is not event count; it is explicit, uniform execution-policy metadata.

### Recommendation — BUILD-SMALL: hook policy envelope and receipt

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing dispatcher contract with a small policy object and one append-only receipt per invocation:

```json
{
  "mode": "blocking|async",
  "timeout_ms": 5000,
  "retries": 0,
  "failure_mode": "fail_open|fail_closed",
  "max_concurrency": 1,
  "queue_limit": 20
}
```

Receipt fields: event ID, session ID, hook name/version, matcher, start/end monotonic timestamps, exit code, decision (`allow|block|inject|error|timeout|dropped`), retry count, and a content hash—not full sensitive payload. The dispatcher must validate a known-present hook receipt before any report that hooks are absent. Policy hooks protecting irreversible operations use fail-closed; telemetry/advice hooks use fail-open. Queue drops are outcomes, not silence.

This is **very likely (80-90%)** to close the present measurement gap because it creates direct hook-execution records rather than attempting to infer hooks from assistant transcripts. Evidence: known defect D3 found no `hookName` or `hook_event_name` across 12 GB and prescribes checking the event ledger (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:131-147`); Cline's documented policy fields supply the minimal control vocabulary. It does not solve false-positive guard semantics; D1 still requires the shared use-versus-mention discriminator.

The proposal passes the anti-overfit gate: no daemon, SaaS, vector store, or second runtime; it wraps the existing dispatcher and event ledger.

### What not to copy

Cline's npm/git/file plugin loading is precisely the kind of lifecycle that can reproduce this owner's orphan-directory failure if cache cleanup and reachability are weak. The corpus root cause—about 1,293 `.orphaned_at` plugin directories inflating Windows command lines—is direct evidence against expanding plugin supply before lifecycle hygiene. Also do not add Cline, Cursor, and Windsurf compatibility files merely because Cline accepts them; this owner's single cross-tool `AGENTS.md` contract already minimizes duplicated instruction surfaces.

## 7. Multi-agent support

### Cline subagents

Cline's experimental `use_subagents` launches parallel, separate-context research agents. They can read, list, search, inspect definitions, run restricted read-only commands, and use skills. They cannot edit, patch, browse, use MCP, web-search, spawn nested agents, or mutate system state. Their prompts require approval unless project reads are auto-approved; their token/cost totals are reported separately and rolled into task cost ([subagents](https://docs.cline.bot/features/subagents)).

This is an intentionally narrow context-isolation primitive. Claude Code's native subagents also start in fresh contexts and can be restricted by tool allowlists; they cannot spawn subagents. This harness has 22 used agent types, explicit SubagentStart/Stop hooks, structured handoff rules, and cross-vendor fan-out (`/local_disk0/codexwork/bundle/claude/settings.json:419-443`; `/local_disk0/codexwork/bundle/claude/AGENTS.md:59-63`; `/local_disk0/codexwork/bundle/claude/CLAUDE.md:19-42`; [Claude subagents](https://code.claude.com/docs/en/sub-agents)). Cline is not ahead here.

### Cline Teams and Kanban

Teams add coordinator tools for spawn, delegation, status, and result retrieval. State persists in `~/.cline/data/teams/<name>/` as task board, mailbox, and mission log. Cline's docs advise teams only when work decomposes, needs specialization, or spans sessions, and admit the overhead ([SDK teams](https://docs.cline.bot/sdk/guides/multi-agent-teams)).

Kanban gives each card a worktree and terminal, task dependencies, inline diff comments, optional auto-commit/PR, and sidebar decomposition. It is a research preview and a separate local web server ([Kanban](https://docs.cline.bot/usage/kanban)).

The owner already enables experimental Claude agent teams, has team/task lifecycle hooks, native worktree creation/removal, Codex MCP fan-out, and a persistent local peer mailbox (`/local_disk0/codexwork/bundle/claude/settings.json:5-7,445-529`; `/local_disk0/codexwork/bundle/claude/CLAUDE.md:15-82`). Cline's integrated board UI and dependency auto-start are narrower ergonomic deltas; they are not missing orchestration semantics.

### Rejected proposal — BUILD-LARGE: ClineCore teams/Kanban

**BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected. Porting the team board or Kanban would introduce the prohibited second orchestration runtime/durable execution layer. It is **very likely (80-90%)** to create more lifecycle and split-brain problems than value because native teams, worktrees, task events, mailbox, and remote fleet already cover the underlying mechanisms. The only unfilled value is a unified visual board, and that does not justify a daemon under the anti-overfit gate.

If a future measured workflow demonstrates board-specific value, the settling experiment is not an install: compare ten equivalent multi-worktree tasks using existing native team status versus a disposable Cline Kanban instance, measuring coordination errors, merge conflicts, human steering time, and orphan cleanup. Until then this remains rejected, not deferred by default.

## 8. Verification and self-checks

### What Cline actually verifies

Cline's strongest verification facilities are environmental feedback, not an independent critic:

* It monitors linter/compiler diagnostics after edits and feeds errors back into the loop ([README](https://github.com/cline/cline/blob/main/README.md)).
* It watches live/background terminal output and can react to build, test, server, or runtime failures.
* Its browser captures screenshots and console logs, enabling interactive E2E checks.

## 10. Where Cline is worse and what not to copy

1. **Memory is prompt-maintained documentation.** Memory Bank is legible but manual, stale-prone, and token-hungry. The owner's semantic/objective split is better.
2. **Security classification is partly model-authored.** `requires_approval` is supplied by the planner; unspecified SDK tool policy defaults to enabled/auto-approved. Preserve deterministic outer policy.
3. **YOLO is broader than this owner needs.** It approves all filesystem, terminal, browser, MCP, and mode actions. The owner's current bypass is already a problem to retire, not a precedent for copying Cline.
4. **Checkpoint breadth brings cost and risk.** Cline snapshots complete file state after every tool via shadow Git. Its docs warn of storage/latency for large repos, and issue history includes stalls and destructive restores. Prefer native checkpoint and worktree isolation.
5. **Auto Compact is not lossless.** Unsupported models truncate; generated summaries have no proof that every decision survived. Preserve the objective ledger and targeted native summarization.
6. **Teams/hub/Kanban are extra runtime planes.** They are coherent product engineering for Cline, but overfit this owner, who already operates native teams, worktrees, mailbox, and fleet.
7. **Plugin distribution can magnify lifecycle debt.** This owner has a measured orphan-plugin command-line failure. More npm/git plugin supply before cleanup correctness would worsen the known root cause.
8. **Completion is not verification.** A schema-valid completion call and a checked todo list do not prove test or runtime correctness.
9. **IDE custom tools lag SDK/CLI.** Cline's current tools docs explicitly say plugin custom tools do not apply to VS Code/JetBrains. MCP remains the cross-surface extension path.
10. **Ordinary Cline lacks the owner's epistemic contract.** No documented equivalents were found for known-positive controls before absence claims, confidence bands, anti-sycophancy, two independent signals, use-versus-mention discrimination, or blast-radius tracing. Absence here is limited to public documentation, not asserted as an internal-code fact.
