# P2A07 — External research: tool/function-calling design

**Unit:** P2A07  
**Date:** 2026-07-18  
**Question:** Tool/function-calling design: error-message design, idempotency, affordances, and why agents misuse tools, with special attention to shell quoting failures and read-before-write friction.  
**Scope discipline:** This is an external-research lens. I did not inspect or draw conclusions from the owner's local repository, configuration, audit findings, or corpus. The owner's prompt supplies the two target symptoms; all causal and design claims below are supported from external standards, official documentation, papers, or public implementation evidence.

## Executive conclusion

The best-supported design is not a smarter orchestration layer. It is a better tool boundary.

At that boundary, the model needs: (a) a small, distinct, well-documented action surface; (b) schemas that constrain syntax without pretending to prove semantic correctness; (c) outputs and errors containing stable machine-readable state plus a concise human-readable repair; (d) explicit mutability, destructive, idempotency, and open-world semantics; (e) safe handling of ambiguous outcomes; and (f) interfaces that return the changed state immediately. This is consistent across the MCP specification, HTTP/API standards, Anthropic's tool-design guidance, AWS and Stripe's idempotency contracts, and agent-interface experiments [S1][S2][S3][S4][S5][S6][S7].

The two target symptoms are interface failures, not merely prompting failures:

* A raw shell command is a string that crosses JSON, host-shell, child-shell, and native-program parsers. Bash itself has multiple quoting modes, word splitting, glob expansion, command substitution, and here-document rules; PowerShell adds its own expression/argument modes and native-argument translation [S8][S9][S10][S11]. Asking a model to repeatedly synthesize this nested language is an avoidable affordance tax.
* A blanket read-before-write rule protects against stale or blind overwrites, but a separate mandatory read call is not the only way to obtain that protection. HTTP `If-Match`/ETag and Google AIP freshness validation establish conditional mutation as a standard lost-update defense, while SWE-agent demonstrates an agent-facing editor that couples view, edit, lint feedback, and the updated view [S12][S13][S14]. A conditional patch with an expected anchor/hash can preserve the safety invariant while removing redundant interaction.

My highest-value recommendations are therefore: a uniform actionable error envelope, a structured script runner for quote-heavy commands, a compare-and-swap patch primitive that returns the updated hunk, idempotency keys plus explicit `outcome: unknown`, native deferred tool loading, and a small execution-based conformance suite. Every one can ride the existing hook/skill/MCP/tool buses. None requires a second orchestrator, vector database, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## Research method and source quality

I decomposed the question into six searches: tool affordances and selection; error response design; idempotency and ambiguous outcomes; shell parsing; file mutation/concurrency; and empirical agent recovery. I searched variants across standards bodies, official vendor documentation, proceedings/anthologies, arXiv/OpenReview, and public repositories/issues. I deep-read the load-bearing sources rather than relying only on snippets.

The final evidence set contains 24 primary or near-primary sources:

* standards and approved API guidance: IETF RFC 9457, RFC 9110, Google AIP-193/134/154, MCP specification;
* official engineering documentation: Anthropic/Claude, OpenAI, AWS, Stripe, GNU Bash, Microsoft PowerShell, ShellCheck, Kubernetes;
* peer-reviewed papers: BFCL (ICML 2025), SWE-agent (NeurIPS 2024), ToolSandbox (NAACL 2025), API-Bank (EMNLP 2023), guided structured function calling (EMNLP 2025), ReflecTool-Bench (ACL Findings 2026), ToolReflection (REALM 2025);
* recent preprints are used only in the "promising but unproven" section or as negative evidence against hype;
* one real repository issue is used as an implementation failure specimen, not as population-level evidence.

Only the built-in web research provider was available in this unit. Cross-corroboration therefore comes from independent publishers and evidence types, not independent search indexes. I did not use vendor benchmark claims as proof of local lift.

## 1. What is actually established

### 1.1 Tool design is part of model performance, not neutral plumbing

Tool definitions are placed in model context and influence both selection and argument generation. Anthropic's current tool-definition documentation explicitly says the description should cover what a tool does, when to use or not use it, parameter semantics, behavior, caveats, and limitations; it calls detailed descriptions the most important factor in tool performance. It recommends meaningful namespacing, fewer related tools, examples for complex inputs, and high-signal responses [S1]. Google Research found on six tasks across vision and language that tool documentation alone could match few-shot demonstrations, and that documentation beat demonstrations-without-documentation in a setting with hundreds of APIs [S15]. This does not prove that “more description is always better”; it establishes that documentation is part of the executable interface rather than decorative prose.

The action interface itself measurably changes agent performance. SWE-agent held the model fixed and designed an Agent-Computer Interface with bounded search, an integrated viewer/editor, immediate post-edit display, and lint feedback; its paper reports that alternative interfaces materially changed behavior and performance [S14]. Anthropic's internal engineering account similarly reports that overlapping tools, opaque identifiers, bloated responses, and vague parameters confuse agents, while namespacing and meaningful context help; it explicitly recommends evaluation against held-out tasks because optimal names and formats vary by model and task [S2].

The external evidence therefore supports this causal account of misuse:

1. The model is a nondeterministic consumer of what ordinary API designers often treat as a deterministic developer contract [S2].
2. Tool names, descriptions, schemas, examples, and returned context jointly define the model's perceived affordances [S1][S2][S15].
3. Overlap and tool-count increase the selection problem, while state dependency and insufficient information create multi-turn failures that a single-call schema benchmark misses [S7][S16].
4. A syntactically valid call can still select the wrong tool, use a plausible but wrong value, ignore a result, or act on stale state. BFCL therefore evaluates abstention and stateful multi-step behavior as distinct capabilities, and finds memory, dynamic decision-making, and long-horizon reasoning remain challenges even when single-turn calls are strong [S16].

### 1.2 Strict structured output solves a narrow problem

Constrained decoding can enforce that generated arguments conform to a supported JSON Schema. OpenAI reports that `strict: true` constrains tool-call output to the supplied schema [S17], and Anthropic documents strict tool use for schema-valid inputs [S1]. This is valuable: malformed JSON and missing required fields can be rejected before execution.

But OpenAI's own limitations are decisive. Structured Outputs does not prevent mistakes inside field values, can fail on refusal or truncation, supports only a subset of JSON Schema, and in the cited release was incompatible with parallel function calls unless parallel calls were disabled [S17]. MCP likewise distinguishes protocol/schema failures from tool execution and business-logic failures [S3]. Therefore “schema-valid” is not equivalent to “correct,” “safe,” “complete,” or “retryable.”

This distinction matters for fan-out. A single large schema that tries to encode every branch shifts complexity into a constrained generation problem and can reject otherwise recoverable partial work. The established part is that strict decoding guarantees structural membership, not semantic success [S17]. The claim that any particular schema should be simplified is local and must be measured; it is not established by the standard alone.

### 1.3 Errors need separate machine and repair channels

There is unusually strong agreement across standards:

* RFC 9457 defines a machine-readable problem type, status, occurrence identifier, human title/detail, and extensible fields. Its validation example uses a list of field-specific errors with JSON Pointers. It says `detail` should help the client correct the problem and should not be parsed for machine logic [S4].
* Google AIP-193 requires a stable machine-readable `ErrorInfo` reason/metadata alongside a simple, descriptive, actionable developer-facing message. Dynamic values belong in metadata, and additional help should supplement rather than replace a clear resolution [S5].
* MCP separates JSON-RPC protocol errors from execution errors returned with `isError: true`; its specification explicitly says execution errors should contain actionable feedback that models can use to self-correct and that clients should pass them to the model [S3].
* Anthropic recommends errors that state specific, actionable improvements rather than opaque codes or tracebacks, and says examples of correctly formatted inputs can steer repair [S2].

These sources independently establish a dual-channel design: stable fields for control flow and concise prose for model/human repair. Raw stderr is useful evidence, but it is not a complete error contract. A good tool error says what failed, where, whether anything changed, whether and when retry is safe, and what minimally different action can succeed.

The converse also follows from the standards: clients should not parse variable prose to decide whether to retry. AIP-193 warns about breaking clients that had to depend on message strings [S5]; RFC 9457 says consumers should not parse `detail` for machine information [S4].

### 1.4 Error feedback helps, but self-reflection is not reliable enough to be the control plane

Interactive error feedback can improve recovery. ToolReflection trained models on generated error/correction trajectories and reported gains ranging from 4% to 56.2% across its evaluated datasets, with 10.5% in its named real-world ToolAlpaca scenario [S18]. An EMNLP 2025 study reported 3–12% relative gains from guided structured reasoning templates and found free-form chain-of-thought sometimes counterproductive for structured function calling [S19]. These are evidence that feedback format matters.

They do not justify relying on a model to notice its own mistake. ReflecTool-Bench evaluated 12 models across 968 dialogues and found that models handled user-originated errors better than assistant-originated ones, with a sharp drop from critiquing another trace to reflecting on their own trace [S20]. ToolSandbox independently identifies state dependency, canonicalization, and insufficient information as difficult for capable models [S7]. Deterministic preconditions and explicit tool state are therefore more defensible than “let the model critique itself.”

### 1.5 Idempotency is a server contract, not a retry prompt

AWS's Builders' Library defines the core failure: after a timeout, the client may not know whether a side effect occurred. Blind retry can create duplicates. AWS's preferred solution is a caller-provided request identifier, atomic association between that identifier and the mutation, parameter-equivalence checking, retention for a defined interval, and a semantically equivalent replay response [S6]. Stripe implements the same broad pattern: an idempotency key lets a client safely retry a `POST`; the service stores or reconciles the operation, compares parameters on key reuse, and documents retention semantics [S21].

Three operational consequences are established:

* “retryable” is not a property of an error code alone; it depends on operation semantics and whether the same intent can be recognized [S6][S21].
* Hashing identical arguments is not always a valid proxy for caller intent—two identical creates may be deliberately distinct. AWS therefore prefers a caller-generated token [S6].
* A useful replay response is semantically equivalent, not merely “already exists,” because the latter pushes uncertainty back to the client [S6].

MCP has `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`, but its specification labels them hints and tells clients not to trust annotations from untrusted servers [S22]. An annotation can drive UX or retry policy for trusted local servers; it cannot manufacture idempotency or enforce safety.

### 1.6 Read-before-write is one implementation of freshness control, not the invariant itself

The invariant is “do not unintentionally overwrite a state you did not base your decision on.” HTTP standardizes `If-Match` specifically to prevent lost updates when multiple actors modify a resource [S12]. Google AIP-134 and AIP-154 use opaque ETags to ensure an update applies only to the current resource version and require a conflict failure when the supplied version is stale [S13][S23]. Kubernetes server-side apply goes further by tracking field ownership and returning conflicts when one actor would overwrite another actor's managed field [S24].

For code editing, SWE-agent shows a complementary agent-facing pattern: edit only a known range in the open file, display the new contents immediately, run a linter, discard invalid edits, and provide the relevant before/after error snippet [S14]. This design couples observation and action instead of demanding that the model manually reconstruct state across separate calls.

Thus a safe editor can accept an expected old fragment and/or base content hash, atomically compare and patch, and return the changed hunk plus new hash. A stale mismatch should return the current nearby hunk and a stable precondition code. This preserves the safety reason for read-before-write while eliminating a separate read when the caller already has sufficient anchored context.

### 1.7 Raw shell strings are a hostile agent affordance

Bash quoting is not one rule. The GNU manual documents four quoting mechanisms and notes that a single quote cannot appear inside single quotes even when backslash-escaped [S8][S9]. Unquoted expansions undergo word splitting and glob expansion; ShellCheck's SC2086 explains why arrays and `"${args[@]}"` are the correct representation for argument vectors rather than a space-joined option string [S10]. PowerShell has expression mode, argument mode, metacharacters, native-program argument conversion, a stop-parsing token, and version-dependent native argument behavior [S11].

These are multiple parsers with different semantics. A command embedded in JSON and then passed through PowerShell to Bash or a native executable compounds them. An unmatched-quote EOF is therefore not adequately addressed by reminding the model to “quote carefully.” The interface should carry code and arguments separately whenever possible and should parse/lint source before execution.

The SWE-agent result reinforces the general principle: special-purpose editor/search actions with bounded, immediate feedback outperform forcing every operation through a raw shell [S14]. A public llama.cpp issue supplies a concrete failure specimen on the other side of the boundary: malformed/truncated tool-call JSON was converted into an HTTP 500 with no recoverable partial state, and the reporter explicitly requested a structured recovery surface [S25]. It is one implementation report, not a frequency estimate, but it demonstrates how a parser failure becomes unrecoverable when the boundary discards state.

## 2. What is promising but unproven

### 2.1 A uniform agent error envelope

It is **very likely (80-90%)**, based on the independent convergence of RFC 9457, AIP-193, MCP error guidance, and Anthropic's tool-design experience [S3][S4][S5][S2], that a stable error envelope would reduce blind retries and superficial parameter changes across heterogeneous tools. The exact effect size on this owner's model/tool mix is **UNVERIFIED; settle it with a replay A/B test that presents the same historical failures once with raw output and once with the normalized envelope, then scores successful repair, repeated identical calls, and unnecessary tool calls.**

A candidate envelope is:

```json
{
  "ok": false,
  "code": "SHELL_UNTERMINATED_QUOTE",
  "category": "invalid_input",
  "message": "Bash reached end of input while looking for a closing single quote.",
  "location": {"field": "/command", "line": 3, "column": 18},
  "observed": "single quote opened at line 3, column 18",
  "expected": "a closing single quote before end of input",
  "state_change": "none",
  "outcome": "not_started",
  "retry": {"safe": true, "class": "after_correction", "after_ms": 0},
  "repair": {
    "action": "fix_input",
    "hint": "For a literal single quote, end the quote, emit an escaped quote, and reopen it; for multi-line code prefer run_script with body and argv fields.",
    "example": {"tool": "run_script", "arguments": {"shell": "bash", "body": "printf '%s\\n' \"$1\"", "argv": ["value with ' quote"]}}
  },
  "invocation_id": "..."
}
```

`outcome` needs at least `not_started | committed | not_committed | partial | unknown`; `state_change` needs at least `none | changed | partial | unknown`. Those fields prevent a timeout from being misclassified as an ordinary validation failure.

### 2.2 Structured script execution instead of nested command strings

It is **likely (55-80%)**, based on the documented Bash/PowerShell parsing layers and ShellCheck's argument-array guidance [S8][S10][S11], that separating `{shell, body, argv, cwd, env_names}` will materially reduce unmatched-quote and interpolation failures. The magnitude is **UNVERIFIED; settle it with a paired execution test of at least 100 previously failing quote-heavy commands, preserving task intent while randomizing whether the model receives raw `command` or structured `body + argv`.**

This does not remove quoting inside the script language. It removes one or more outer quoting layers and gives the host a chance to pass `argv` without reparsing a joined string. It also makes a deterministic `bash -n` or PowerShell parser check possible before side effects.

### 2.3 Conditional patching as a replacement for mandatory separate reads

It is **very likely (80-90%)**, because compare-and-swap freshness is standardized in HTTP/Google APIs and integrated observation/editing worked in SWE-agent [S12][S13][S14], that an edit call carrying `expected_old` or `base_hash` can preserve conflict safety while reducing redundant read calls. Its compatibility with every current client is **UNVERIFIED; settle it with an execution test covering stale content, duplicate anchors, newline changes, encoding/BOM, symlinks, files larger than the context window, and concurrent edits.**

The tool should refuse ambiguous anchors, never silently choose the first match, and return the current local hunk on `PRECONDITION_FAILED`. On success it should return the applied diff, the updated hunk, and the new hash. That makes the next model state fresh without a follow-up read.

### 2.4 Model-facing retry classes

It is **likely (55-80%)**, based on AWS/Stripe's production contracts and MCP's idempotency vocabulary [S6][S21][S22], that explicitly separating `fix_input`, `retry_same_intent`, `reconcile`, `wait`, and `do_not_retry` will reduce unsafe and futile retries. Whether models will obey the field more reliably than concise prose is **UNVERIFIED; settle it by fault injection across validation errors, 429s, timeouts before execution, timeouts after commit, partial batch failures, and idempotency-key mismatch.**

### 2.5 Deferred tool loading

It is **very likely (80-90%)** that native deferred loading will reduce prompt-token load because Anthropic documents that it excludes deferred definitions from the initial context and reports over 85% reduction in a representative multiserver setup [S26]. It is **likely (55-80%)** to improve tool selection in this owner's harness because Anthropic reports degradation beyond 30–50 visible tools, while BFCL and Anthropic's engineering guidance independently identify selection/overlap as a real failure axis [S26][S16][S2]. The local accuracy gain is **UNVERIFIED; settle it with held-out task replay comparing the current visible set against 3–5 always-loaded tools plus native search, scoring correct selection, search misses, latency, and total tokens.**

### 2.6 Guided repair templates

It is **likely (55-80%)** that a short repair template can outperform free-form “try again” feedback for schema and parameter errors, based on the EMNLP guided-template result and ToolReflection's feedback training [S18][S19]. Generalization to closed frontier models and shell/edit errors is **UNVERIFIED; settle it with the same replay A/B test as the error envelope, without fine-tuning and with a hard cap of one corrected retry.**

## 3. What is hype, and how to tell

### 3.1 “Strict JSON means reliable tool use”

This is false by category error. Strict decoding proves that an output belongs to a schema. OpenAI explicitly says values can still be wrong and documents refusal, truncation, subset, and parallel-call limitations [S17]. MCP separately models execution and business errors [S3]. Any claim of “100% reliable tools” based only on schema conformance has changed the metric from task success to syntax success.

**Detection test:** ask whether evaluation executed the tool, verified state change, tested abstention, injected timeouts, and checked duplicate side effects. If it only parsed JSON or compared an AST, it does not establish operational reliability.

### 3.2 “A self-critic will catch and repair failures”

The positive studies are real but bounded. ToolReflection requires instruction tuning and reports widely varying gains across datasets [S18]. ReflecTool-Bench finds models are substantially worse at recognizing their own tool errors than critiquing others [S20]. A trained critic also reintroduces a specifically rejected harness component and adds latency, model/version coupling, and another nondeterministic failure surface.

**Detection test:** require held-out, execution-based results on assistant-originated failures; report critic false positives, extra calls, and failures where the critic agrees with the original mistake. A paper showing only synthetic correction accuracy does not justify a permanent critic runtime.

### 3.3 “More tools create more capability”

More installed capability is not the same as more usable capability. Anthropic says overlapping tools distract agents and documents native search precisely because selection degrades with large visible sets [S2][S26]. BFCL makes abstention and tool selection separate evaluation targets [S16].

**Detection test:** add semantically related distractor tools to held-out tasks. If success falls or calls rise without new task coverage, the extra surface is negative capability.

### 3.4 “Just retry transient failures”

Without an idempotency contract, a timeout is an ambiguous outcome, not evidence that nothing happened. AWS's canonical example is duplicate resource creation after a lost response [S6]. Stripe requires an idempotency key for safe `POST` replay [S21]. Backoff reduces load; it does not prevent duplicated side effects.

**Detection test:** inject a timeout after the server commits but before the response reaches the client. If the retry creates a second object or the harness cannot reconcile the original invocation, the claim fails.

### 3.5 “The raw shell is universal, so specialized tools are unnecessary”

Universality optimizes tool implementer convenience, not agent success. Bash and PowerShell have complex, different parsing rules [S8][S11], while the SWE-agent interface study shows model-fixed performance changes from specialized search/edit affordances and feedback [S14]. The raw shell remains an essential escape hatch; making it the only representation for structured actions is not minimalism, because complexity is merely exported into every generated command.

**Detection test:** compare equal tasks expressed as raw nested commands versus typed arguments and conditional edit primitives; measure syntax failures, tokens, retries, and side effects.

### 3.6 “A giant autonomous recovery framework is necessary”

Recent preprints propose planners, rollback graphs, fault-recovery training, and critic loops, but the strongest standards-based fixes are smaller: error fields, preconditions, request IDs, and focused tool surfaces. Anthropic's broad production guidance says successful implementations commonly use simple composable patterns and warns that frameworks obscure prompts and add unnecessary abstraction [S27].

**Detection test:** demand an ablation against a one-loop baseline equipped only with the same error envelope, idempotency, and conditional mutation. If the large framework has no held-out advantage after those controls, its orchestration is ceremony.

## 4. Specific, concrete things this owner's harness should adopt

Every recommendation below includes exactly one implementation classification and an explicit anti-overfit decision. “UNVERIFIED local effect” is in each heading because external evidence cannot establish the effect size in this owner's harness; the named experiment settles it.

### 4.1 UNVERIFIED local effect — Normalize failed tool results into one actionable envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Implement one normalizer invoked by the existing post-tool-failure path. Preserve the original stderr/response in a bounded `raw_excerpt`, but prepend the fields shown in §2.1. Minimum required fields:

* `code`, stable and enumerable;
* `category`: `invalid_input | precondition | unavailable | rate_limited | permission | conflict | internal`;
* `location`, using a JSON Pointer/field/line/column where possible;
* `outcome` and `state_change`;
* `retry.safe`, `retry.class`, and optional `after_ms`;
* one-sentence `message` and one concrete `repair` action;
* `invocation_id` and `idempotency_key` when applicable.

Do not let the normalizer infer `not_committed` from a timeout. Default ambiguous network/process termination to `outcome: unknown`, `retry.class: reconcile` unless the tool contract proves idempotency. That follows AWS's ambiguity analysis [S6].

**Expected result:** **very likely (80-90%)**, based on four independent standards/guidance sources [S2][S3][S4][S5], to improve repair direction; exact lift is **UNVERIFIED; run the historical-failure replay A/B described in §2.1.**

**Anti-overfit gate:** passes. This is a stateless adapter on an existing hook path. It adds no runtime, memory store, critic, SaaS, or orchestration layer.

### 4.2 UNVERIFIED local effect — Use native failure hooks to preserve and augment errors, never swallow them

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Enable `PostToolUseFailure` to add normalized `additionalContext`; use `PostToolUse.updatedToolOutput` only when the replacement preserves the built-in output shape. Claude Code's official hook reference documents both mechanisms and states that post-tool replacement changes only what Claude sees, not already-executed effects [S28]. Keep the original failure fingerprint and invocation ID in the augmented result.

Do not treat a nonblocking hook failure as successful normalization. Emit a terminal marker such as `FAILED:error-normalizer <reason>` and leave the raw tool failure visible.

**Expected result:** **likely (55-80%)** to reduce lost error context because the native hook injects context directly beside the failure [S28]; its behavioral benefit is **UNVERIFIED; settle it by checking repair success and whether raw errors remain observable in the replay suite.**

**Anti-overfit gate:** passes. It is native lifecycle plumbing, not a new component.

### 4.3 UNVERIFIED local effect — Add a structured `run_script` escape hatch for quote-heavy commands

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Expose:

```json
{
  "shell": "bash | pwsh",
  "body": "script source, not an outer shell command",
  "argv": ["each", "argument", "separate"],
  "cwd": "absolute or workspace-relative path",
  "timeout_ms": 10000,
  "env_names": ["names only; values inherited, never echoed"]
}
```

The implementation writes `body` to a uniquely created temporary file, runs a syntax-only parse first (`bash -n`; PowerShell parser API), and invokes the interpreter with an argument array rather than `bash -c "..."` or a space-joined command. It returns parse locations through the common envelope. It must clean up only its exact temp file and must never interpolate environment values into logs.

Keep the raw Bash tool for ordinary commands. Tool description guidance should say: use raw Bash for a simple command/pipeline; use `run_script` for multi-line bodies, nested JSON, embedded quotes, or cross-shell invocation. This is a focused alternative, not a replacement shell runtime.

**Expected result:** **likely (55-80%)**, from the parser and array evidence [S8][S10][S11], to reduce quote-layer failures; **UNVERIFIED; settle it with the 100-case paired execution test in §2.2.**

**Anti-overfit gate:** passes. One small tool on the existing bus; no daemon or durable executor. If implementation exceeds ~200 lines, cut features rather than promoting it to a service.

### 4.4 UNVERIFIED local effect — Replace “read token” gating with atomic conditional patching where possible

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Provide `patch_file(path, expected_old, replacement, expected_sha256?)`. Semantics:

1. Read and hash inside the tool.
2. Require `expected_old` to match exactly once; zero or multiple matches fail without mutation.
3. If supplied, require `expected_sha256` to match.
4. Apply atomically to the exact file.
5. Return unified diff, updated surrounding hunk, and new hash.
6. On mismatch, return `PRECONDITION_FAILED`, current hash, and bounded nearby/search results sufficient to rebase.

For whole-file overwrite, retain an explicit read/freshness precondition. For creation, require `must_not_exist: true`, analogous to `If-None-Match: *` [S12]. Do not silently downgrade a failed precondition to last-writer-wins.

**Expected result:** **very likely (80-90%)** to preserve lost-update safety and remove redundant read calls in anchored edits, based on standards and the integrated SWE-agent editor [S12][S13][S14]; **UNVERIFIED; settle it with the concurrency/encoding/ambiguity matrix in §2.3 plus a call-count comparison.**

**Anti-overfit gate:** passes. This is a local compare-and-swap primitive, not durable execution or a new state store.

### 4.5 UNVERIFIED local effect — Publish and consume MCP behavior annotations for trusted servers

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

For every trusted MCP tool, set all applicable native hints explicitly: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`. Do not rely on defaults. Use them to decide whether automatic retry is even eligible and to distinguish read-only parallelism from same-state mutations. For untrusted servers, treat hints as display information only, exactly as MCP requires [S22].

Add a conformance check that compares the annotation with fault-injected behavior: call an alleged idempotent test tool twice with the same arguments and confirm no second side effect; call a read-only test tool and diff its controlled state. An annotation is not proof.

**Expected result:** **likely (55-80%)** to improve retry/approval routing because the vocabulary directly maps to those decisions [S22]; **UNVERIFIED; settle it by measuring classification coverage and deliberately misannotated controls.**

**Anti-overfit gate:** passes. Native protocol metadata only.

### 4.6 UNVERIFIED local effect — Add caller-generated idempotency keys only to externally mutating operations

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Pilot this on one create/send/publish operation whose server can atomically bind a request key to the mutation. Generate the key once per user intent, reuse it on transport retry, reject the same key with different normalized parameters, retain it for a documented interval, and return the original/semantically equivalent result on replay [S6][S21]. Include the key in the tool result and ledger/fingerprint already used by the harness.

Do not add a client-only key to a server that ignores it; that produces the appearance of safety without the contract. For tools whose backend cannot support atomic idempotency, return `outcome: unknown` after ambiguous failure and require a read/reconcile operation before any retry.

**Expected result:** **almost certain (90-99%)** to prevent duplicate effects when the backend correctly implements the established idempotency contract [S6][S21]; correct backend support in the owner's specific tools is **UNVERIFIED; settle it with the post-commit/pre-response timeout injection in §3.4.**

**Anti-overfit gate:** passes for the one-tool pilot. It uses existing request/result paths. Do not build a general durable workflow engine.

### 4.7 UNVERIFIED local effect — Keep strict schemas small and move recoverable semantics into execution errors

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

For each tool schema:

* use precise names (`user_id`, not `user`), enums for true closed sets, and examples for format-sensitive nested inputs [S1][S2];
* keep structural validation strict at the call boundary;
* do not encode mutually unrelated fan-out branches into one enormous required object;
* execute independent items as separately identifiable items with per-item results, so one recoverable failure does not erase all successes;
* return semantic validation through field pointers and repair examples [S3][S4];
* disable parallel strict calls on provider/model combinations whose official documentation says the combination may violate schemas [S17].

The proposal is not “loosen validation.” It is “make the strict boundary correspond to one coherent action and report domain failures as data.”

**Expected result:** **likely (55-80%)** to reduce schema-only failure and make partial recovery possible, based on strict-output limitations and standardized field errors [S3][S4][S17]; which schemas need decomposition is **UNVERIFIED; settle it by mutation-testing required/optional fields and replaying multi-item calls against old and new schemas.**

## 5. Proposed contract details

This section makes the recommendations implementation-ready without claiming they are locally validated.

### 5.1 Retry decision table

| Category | Required outcome | Default model action | Same-call retry? |
|---|---:|---|---:|
| `invalid_input` | `not_started` | Correct the named field using pointer/example | Only after correction |
| `precondition` / `conflict` | `not_started` | Re-read/rebase from returned current state | No |
| `rate_limited` | `not_started` | Wait until `after_ms` | Yes if read-only or idempotent |
| `unavailable` before dispatch | `not_started` | Retry with bounded backoff | Yes if allowed by contract |
| timeout, commit status unknown | `unknown` | Reconcile by invocation/key/resource lookup | Never blindly |
| `partial` batch | `partial` | Retry only failed item IDs under their original intent keys | Never replay entire batch blindly |
| permission/policy | `not_started` | Ask for authority or choose a permitted path | No |
| permanent domain/business error | `not_started` | Change plan or report blocker | No |

The table's semantics follow MCP's error separation, RFC/AIP structured detail, and AWS/Stripe idempotency [S3][S4][S5][S6][S21]. The exact code mapping for each local tool is **UNVERIFIED; settle it through the conformance fixtures in §4.10.**


### 5.3 Tool description template

Each tool description should answer, in this order:

1. **Effect:** what state it reads or changes.
2. **Use when / do not use when:** distinct boundary against neighboring tools.
3. **Inputs:** units, formats, identifiers, defaults, mutually exclusive fields.
4. **Output:** what evidence/state comes back and what is deliberately omitted.
5. **Failure/retry:** whether it is read-only, destructive, idempotent, and how ambiguous outcomes are reconciled.
6. **One valid edge-case example:** especially for nested or quote-sensitive inputs.

This template is a direct operationalization of Anthropic's official description guidance and Google Research's documentation findings [S1][S15]. The ideal length and example count remain model/task dependent [S2].

## 6. Alternatives considered and rejected

### Train or deploy a separate tool critic

Rejected. Positive error-recovery training evidence exists [S18], but self-recognition remains weak [S20], and a trained critic is a previously rejected component under this program's anti-overfit gate. Deterministic validation, state preconditions, and actionable errors address the failure closer to its source.

### Add a durable workflow/retry engine

Rejected. Exactly-once behavior cannot be retrofitted solely by a client runtime; it requires server-side intent recognition and atomicity [S6]. A large durable executor would duplicate orchestration and still be unsafe for backends without idempotency. Pilot request keys on specific operations instead.

### Replace strict schemas with free-form text

Rejected. Strict schemas genuinely prevent structural failures [S17]. The problem is treating them as semantic proof or making one schema represent too many unrelated branches. Keep strictness at coherent action boundaries and return recoverable semantic errors.

### Auto-correct arbitrary shell commands in a pre-hook

Rejected. Deterministically parsing is safe; heuristically rewriting shell code can change intent or side effects. Use syntax errors to steer the model to a structured script tool. If a hook ever modifies input, Claude Code's native `updatedInput` mechanism makes the transformation visible, but the harness should restrict rewriting to provably semantics-preserving normalization [S28].

### Remove read-before-write safety entirely

Rejected. Lost updates are a standard concurrency problem [S12][S13][S23]. Replace the interaction pattern with atomic preconditions, not last-writer-wins.

### Build custom semantic/vector tool search immediately

Rejected. Native deferred loading and regex/BM25 search already exist [S26]. A new vector database or retrieval daemon is a prohibited overfit unless native search fails a held-out evaluation.

## 7. What I could not determine (GAPS)

1. **Cross-model quantitative effect of error envelope fields.** I found standards, official guidance, and recovery studies, but no controlled study isolating `retryable`, `state_change`, `outcome`, JSON Pointer, and repair example fields across current Claude, GPT, Gemini, and open models. This is **UNVERIFIED; the multi-model replay A/B in §2.1 would settle it.**
2. **Best error format for frontier models.** MCP structured content, JSON, Markdown, and concise prose are all plausible. Anthropic explicitly says response-format performance varies by task and model [S2]. It is **roughly even (45-55%)** whether JSON-only beats a short marker plus JSON in this harness, because no direct external comparison was found; **settle it with three-format randomization over identical failures.**
3. **Whether the owner's current hosts expose all native features uniformly.** Official Claude Code documentation exposes `PostToolUseFailure`, `additionalContext`, `updatedInput`, and output replacement [S28], and Claude API documents deferred tools [S26], but I did not inspect installed versions or Codex/other-host parity by instruction. Availability here is **UNVERIFIED; settle it with a read-only version/capability probe in the implementation unit.**
4. **Atomic file replacement details on Windows.** The concurrency semantics are established, but I did not verify the best cross-filesystem atomic replacement primitive for NTFS, symlinks, network drives, ACL preservation, or antivirus interference. A universal implementation claim would be **unlikely (20-45%)** without platform tests; **settle it with a Windows-specific filesystem test matrix before enabling whole-file writes.**
5. **Server support for request keys.** Stripe/AWS prove the pattern, not that the owner's MCP/API backends implement it. Support is **UNVERIFIED; settle it by inspecting each target tool's official contract and fault-injecting post-commit response loss.**
6. **Safety of parallel tool calls across providers.** OpenAI's cited Structured Outputs release documents a parallel-call limitation [S17], and OpenHands warns against parallel writes to shared state [S29], but provider/model behavior changes quickly. Any global rule beyond “parallelize independent read-only calls; serialize shared-state mutations” is **UNVERIFIED; settle it per provider/model with the conformance suite.**
7. **Optimal visible tool count.** Anthropic gives operational thresholds and reports degradation beyond 30–50 tools [S26], but those figures are model/vendor specific. A universal cutoff is **unlikely (20-45%)**; **settle it by adding distractors in increments on held-out tasks.**
8. **Long-term retention for local idempotency records.** AWS says retention is domain/resource dependent [S6], and Stripe documents service-specific windows [S21]. No externally justified universal TTL exists; **settle it per operation from maximum retry/reconciliation delay and resource lifetime.**
9. **Whether structured `run_script` will remain under 200 lines after Windows hardening.** The core is small, but cleanup, encoding, cancellation, and process-tree termination can expand it. It is **roughly even (45-55%)** that the complete cross-shell implementation remains under the BUILD-SMALL threshold; **settle it with a minimal spike restricted to syntax parse, temp file, argv, timeout, and exact cleanup. If it exceeds the threshold, keep it as a skill pattern rather than build a service.**

## Bottom line for the neighboring design/build units

Start with contracts, not cognition. Make every tool declare its effect and retry semantics; make every failure state what happened and what can safely happen next; represent arguments structurally; make mutations conditional; return the new state immediately; and test final state under injected failures. Use native deferred loading and hooks. Keep raw shell and raw stderr as escape hatches/evidence, not as the only interface. Do not add a critic, workflow engine, vector store, or second orchestrator unless the small boundary fixes lose a held-out execution comparison.
