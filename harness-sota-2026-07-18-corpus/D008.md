# D008 — HARNESS-BENCH design: recover after a mid-task session death

**Unit:** D008  
**Date:** 2026-07-19  
**Artifact type:** executable benchmark specification, not a harness patch  
**Primary case ID:** `recovery/session-death/itsdangerous-refresh/v1`  
**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The controller belongs behind the existing `/eval` entry point and writes typed `eval_start` / `eval_result` records to the existing ledger; it is not a new scheduler, daemon, database, memory system, or orchestration runtime.

## 1. Decision — UNVERIFIED until `D008-E0/E1/E1b/E2`

Build one two-process, two-epoch benchmark episode against a clean checkout of Pallets' real `itsdangerous` repository. The controller gives the agent a coding task, waits until the agent has correctly investigated the code, injects one load-bearing correction through the normal lifecycle bus, and then kills the agent's entire dedicated process group immediately before its first source mutation. It restarts the provider by the captured native session/thread ID and supplies only:

> Continue. Finish the task, run the required checks, and do not ask me to restate anything.

The grader ignores the agent's completion claim. It checks the repository by execution with upstream tests, held-out tests, diff-policy checks, and controller-integrity receipts.

This is a deliberately narrow benchmark. It measures whether the harness can preserve the correct objective, a late correction, exact session identity, and verified repository state across an ungraceful process death. It does **not** purport to measure reboot recovery, remote-side-effect idempotency, workflow fan-out recovery, or semantic memory quality in general.

The case is **very likely (80-90%)** to distinguish a functioning exact-session recovery path from “start a new chat and guess,” because the final public prompt omits the selected API name and the held-out tests require it; the evidence is the session-only correction protocol and the hidden test oracle specified below. That predictive claim is **UNVERIFIED** until experiment `D008-E2` runs at least five clean repetitions each for (a) native resume enabled and (b) a deliberately wrong/new session ID.

### 2.2 Recovery components exist, but the end-to-end death path has not been tested

The shared harness routes `SessionStart` to recovery replay only for `source in {resume, compact, clear}`, reads a strict per-session goal, and injects selected ledger entries (`/local_disk0/codexwork/bundle/agents/harness/modules.py:973-1003`). The goal is stored in a session-ID-derived file (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:996-1028`). The active goal is prefix-bounded to 500 characters at storage (`ledger.py:1019-1028`).

The ledger append itself flushes and calls `os.fsync` before updating its projected state (`ledger.py:868-880`). Its recovery replay, however, asks `replay(..., limit=20)` and only then selects decisions, failures, and milestones (`modules.py:979-987`); `replay` returns only the requested tail (`ledger.py:882-907`). Those are direct code facts. Whether they cause a failure in this case is an empirical question, not assumed.

The checkpoint writer runs only on `PreCompact`, not arbitrary process death (`/local_disk0/codexwork/bundle/agents/harness/modules.py:1458-1463`). Its stored content comprises a bounded goal, last ten decisions, last ten open failures, ledger pointer, and optional `.remember/now.md` (`modules.py:1475-1517`). The manual `/save-session` command explicitly targets planned end-of-session or pre-context-limit use and requires the agent to gather and write a session file (`/local_disk0/codexwork/bundle/claude/commands/save-session.md:9-16,18-64`); an abrupt kill gives it no opportunity to run.

The deployed Claude configuration registers the shared `SessionStart`, `PreCompact`, and `PostCompact` hooks (`/local_disk0/codexwork/bundle/claude/settings.json:81-103,380-403`). ### 2.3 Native resume is the correct first rail

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Claude's current official session documentation says sessions are continuously stored locally, `claude --resume <session-id>` can resume a programmatic session, and the resumed conversation stays under the same session ID: [Manage sessions](https://code.claude.com/docs/en/sessions), [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works), and [CLI reference](https://code.claude.com/docs/en/cli-usage). Its hook reference says `SessionStart` runs on resume with `source="resume"` and can add fresh context: [Hooks reference](https://code.claude.com/docs/en/hooks#sessionstart).

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** The fetched 2026-07-19 [official Codex manual](https://developers.openai.com/codex/codex-manual.md) labels both `codex resume` and `codex exec` stable (`/private/tmp/openai-docs-cache/codex-manual.md:5252-5278`; [CLI command reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli#cli-codex-resume)). The same manual documents `SessionStart` matcher values `startup`, `resume`, `clear`, and `compact` (`codex-manual.md:9441-9465`).

Native resume is therefore the benchmark transport. The benchmark does not propose a durable-execution engine.

## 4. Exact prompts and session-only correction

### 4.1 Initial user prompt (byte-for-byte after newline normalization)

```text
Work in this repository only. Do not commit, push, install global packages, or use the network.

We need an API on itsdangerous.signer.Signer that verifies a signed value and, when the value was signed with an older key, returns a replacement signed with the newest configured key. Preserve all existing Signer behavior and BadSignature payload semantics.

Before editing source, investigate the current implementation and write .bench/recovery-plan.json with exactly these keys:
  signing_key_position
  verification_order
  invalid_signature_payload
  source_file
  test_file
  next_action

Use factual values from the repository. `next_action` must describe the first source change you intend to make. Then implement the API, add focused tests to the existing signer test module, add a concise changelog entry, and run the focused tests followed by the full test suite. The public method name is intentionally pending; the harness will provide it after the investigation checkpoint. Do not invent a name before receiving that correction.

Success means the repository tests pass and the API handles bytes and str input, old-key refresh, newest-key no-op, missing separators, and invalid signatures. Keep the change minimal and compatible with the project's existing style.
```

### 4.2 Milestone predicate

The controller watches `.bench/recovery-plan.json`. It must parse as UTF-8 JSON, contain exactly the six requested keys, and satisfy:

```json
{
  "signing_key_position": "last",
  "verification_order": "newest-to-oldest",
  "invalid_signature_payload": "bytes-before-final-separator",
  "source_file": "src/itsdangerous/signer.py",
  "test_file": "tests/test_signer.py"
}
```

`next_action` must be a non-empty string containing `Signer`; its prose is not otherwise graded. The value comes from the real pinned implementation: `secret_key` returns `secret_keys[-1]`, verification iterates `reversed(self.secret_keys)`, and invalid signatures attach the bytes before the final separator as `BadSignature.payload` (`signer.py:175-180,227-256` in the fetched pinned source).

If the file is invalid, the controller does not reveal expected values. It returns the ordinary tool result and continues until the agent corrects it or times out.

### 4.3 Correction injected after a valid milestone

The controller's separate benchmark hook injects this exact context once:

```text
BENCHMARK CORRECTION (authoritative): Name the public method `refresh`, with signature `refresh(self, signed_value: str | bytes) -> tuple[bytes, bool]`. Return `(signed_bytes, False)` when the newest key already validates the value, and `(replacement_signed_with_newest_key, True)` when an older key validates it. ## 6. Executed success predicate
```

### 6.1 Authoritative binary result

`PASS` is true if and only if all of the following are true:

```text
controller_integrity
AND fixture_integrity
AND hard_death_integrity
AND exact_session_resume
AND correction_retained
AND focused_tests_exit_0
AND full_upstream_tests_exit_0
AND hidden_contract_tests_exit_0

AND no_forbidden_side_effect
```

Any controller/fixture/death-integrity failure produces `INVALID:<reason>`, never `FAIL` and never `PASS`. Any task oracle or budget failure after a valid controller sequence produces `FAIL:<reason>`.

The release metric is first-attempt pass rate. Run three independently materialized attempts and publish `pass^3` as well: all three must pass for this release-critical case. Do not choose the best retry.

### 6.2 Held-out executable contract

`test_refresh_contract.py` imports the changed checkout and executes at least these assertions:

1. `Signer` exposes callable `refresh`.
2. Its inspected signature is `(self, signed_value)`; return annotations may be resolved with `typing.get_type_hints` and must equal `tuple[bytes, bool]`.
3. A value signed by the newest of `[b"old", b"middle", b"new"]` returns equal bytes and `False`.
4. A value signed by `b"old"` is accepted by the rotating signer, returns `True`, preserves the payload bytes exactly, and the replacement validates with `Signer(b"new")`.
5. The replacement no longer validates with `Signer(b"old")` alone.
6. The same behavior holds for a `str` signed value.
7. Payloads containing the separator remain intact because splitting occurs at the final separator.
8. Missing separator raises `BadSignature` with the existing message shape and no invented payload.
9. Invalid signature raises `BadSignature` and exposes the bytes before the final separator as `.payload`.
10. Existing `sign`, `unsign`, `validate`, `get_signature`, and `verify_signature` behavior remains green through the upstream suite.
11. Empty, one-key, and three-key configurations follow existing constructor behavior; the new method does not silently change it.
12. Calling `refresh` twice is idempotent at the API level: the second call returns the same signed bytes and `False`.

The hidden suite uses grader-only randomized payloads and keys drawn from a recorded seed. Randomization varies data, not expected semantics. On failure, the scorer emits only assertion IDs during a scored run, not expected source code.

### 6.3 Diff-policy executable contract

`check_diff.py` fails unless all conditions hold:

- tracked changes are restricted to `src/itsdangerous/signer.py`, `tests/test_signer.py`, and the repository's existing changelog file;
- `.bench/recovery-plan.json` is the only permitted untracked benchmark file;
- the signer tests contain at least four new test functions whose bodies call `.refresh(`;
- the changelog contains the exact code token ``Signer.refresh``;
- no generated cache, virtual environment, credential file, controller file, hidden test, commit, tag, or Git config change exists;

The checker discovers the existing changelog filename from the pinned base manifest rather than accepting any newly invented changelog file.

## 7. Failure modes this case is designed to expose

1. **Wrong session selection.** Resuming “last” in a busy shared cwd can attach to another task. The scorer requires the captured ID, not recency.
2. **Fresh-session masquerading as recovery.** A new chat sees only “Continue” and lacks the corrected API name. Session identity is a controller gate.
3. **Late correction loss.** The original task deliberately withholds the method name; hidden tests require the injected `refresh` contract.
4. **Goal truncation or replacement.** A harness that persists only an early prefix or overwrites the root task with the resume prompt can lose late constraints. The current goal storage is bounded at 500 characters (`ledger.py:1019-1028`), so this is directly relevant without asserting that it will fail.
5. **Trusting a summary instead of repository state.** The worktree source is provably unchanged at death, while the plan is present. A resumed agent must inspect actual state rather than claim source work already landed.
6. **Graceful-stop-only checkpointing.** The controller kills the process group; no `/save-session`, Stop hook, or SessionEnd cleanup can manufacture a checkpoint after the fact.
7. **Surviving child process.** Job/process-group enumeration makes a hidden worker continuing after the “death” invalidate the run.
8. **Resume launched but work not completed.** Only executed task oracles pass; a successful resume command is not a success result.
9. **Repeated or conflicting implementation after resume.** The source is unchanged at the boundary, and final diff/test checks expose duplicate methods, conflicting names, or stale edits.
10. **Test-only gaming.** Hidden tests execute the public behavior; diff policy requires production code, public tests, and changelog.
11. **Narrative completion fraud.** The grader never reads the final assistant claim to determine status.
12. **Provider-hook schema drift.** Missing session ID, unrecognized mutation event, or absent kill boundary yields explicit `INVALID_*`, not a misleading regression.

## 8. Anti-gaming analysis

### Hole A: pass by saying “done”

Closed. The scorer runs code and ignores the final message.

### Hole B: pass by completing before the kill

Closed at the controller level. The public method name is withheld until after the validated investigation milestone. The controller kills immediately before the first requested source mutation after delivering the name, and verifies the source blob is still identical through both Git and SHA-256. If a provider bypasses the recognized mutation lane and modifies the file first, the episode is invalid, not passed.

### Hole C: reconstruct the answer from the workspace alone

Partially closed by design. The investigation plan is intentionally durable, but the method name and return contract are not written there. The final prompt does not repeat them. An agent can still rediscover its native transcript after resume; that is the capability under test.

### Hole D: read hidden tests or controller code

Closed by isolation. Neither is inside the worktree or the agent's readable sandbox during the episode. Hidden tests are mounted only after agent termination. The controller log contains event IDs and hashes, not test bodies or expected implementation.

### Hole E: change tests/config so a fake suite passes

Closed by running grader-owned hidden tests in a separate environment and by diff-policy restrictions. Upstream test edits are allowed only in the expected module and are supplemental, never authoritative.

### Hole F: replace the package/import path

Closed by checking the tracked diff, importing from the episode checkout with a sanitized `PYTHONPATH`, and asserting the imported module's resolved path is under the pinned checkout.

### Hole G: keep a helper alive so no death occurred

Closed with a dedicated Windows Job Object/POSIX process group and descendant enumeration. The process handle's forced-termination result and zero-descendant enumeration are mechanically independent signals.

### Hole H: exploit an invalid detector

Closed through known-positive controls. Before the episode, the event detector must identify a harmless known edit request and the file detector must find the known-present signer file through both Git and the blob manifest. Failure invalidates calibration.

### Hole I: memorize the benchmark patch

Not fully preventable in any public fixed coding benchmark. It is mitigated by grader-only randomized keys/payloads and by making recovery integrity independently mandatory. A memorized correct implementation still cannot pass under a new session ID or without a validated hard-death sequence. Dynamically changing semantics inside one suite version is forbidden.

### Hole J: ask the user to restate the task

Closed objectively: the controller sends no response after the fixed resume prompt. The episode eventually times out and fails. The benchmark does not judge whether the question was reasonable.

## 11. Rejected alternatives and why

1. **Graceful `/exit` then resume.** Rejected because Stop/SessionEnd/save-session behavior could run; it does not model abrupt death.
2. **Kill after a fixed number of seconds.** Rejected because model latency and tool ordering vary, so the semantic task point would not be repeatable.
3. **Kill after N tool calls.** Rejected because tool granularity differs across providers and harness versions; it measures tool packaging.
4. **Restate the full task after restart.** Rejected because an agent can pass without recovering any context.
5. **Score a recovery summary.** Rejected because wording requires human/model judgment and does not prove correct work.
6. **Use the assistant's `SUCCESS` marker.** Rejected because it is self-assertion, not an outcome label.
7. **Expose hidden tests before the run.** Rejected because the agent could target test syntax rather than the behavioral contract.
8. **Delete or corrupt the provider transcript.** Rejected for v1 because it turns native session recovery into disaster recovery and would confound the intended capability.
9. **Require basic-memory lookup.** Rejected because the benchmark scores outcome, not a preferred internal route; native transcript replay may be sufficient.
10. **Introduce a durable workflow engine.** Rejected by the anti-overfit gate and because native session IDs already supply the minimal continuation primitive.
11. **Use a synthetic toy repository.** Rejected because a real maintained package supplies authentic style, tests, exceptions, typing, and changelog constraints while remaining fast enough for repeated runs.
12. **Use the owner's live harness repository as the coding fixture.** Rejected to avoid benchmark contamination, subject writes, and self-referential fixes that know the scorer.

## 12. Validity limits and GAPS

1. **UNVERIFIED — native Windows kill boundary.** `D008-E1` must prove the controller can observe a post-correction mutation request and terminate the Job Object before the file changes, using both Git diff and blob SHA-256.
2. **UNVERIFIED — exact installed CLI command templates.** `D008-E1b` must run no-write two-turn canaries for every provider/version and capture identical IDs plus resume lifecycle events.
3. **UNVERIFIED — fixture dependency lock.** `D008-E0` must freeze the environment/archive/wheel digests and demonstrate an upstream green baseline before the case can yield scored results.
4. **UNVERIFIED — discrimination.** `D008-E2` must run no-death, exact-resume, and wrong-ID arms. The benchmark is accepted only if no-death is tractable and wrong-ID is materially worse than exact-resume.
5. This case does not test a power loss between filesystem write and `fsync`, corruption of the native transcript, reboot, user-profile loss, or expiration under the documented transcript-retention policy.
6. It does not test in-flight background agents or Workflow prefix-cache semantics. C06 already identifies those as a separate recovery surface (`/local_disk0/codexwork/bundle/inputs/audit-findings/C06.md:15-45`); another unit should own that neighboring benchmark.
7. It does not test external non-idempotent side effects; that neighboring benchmark is outside D008.
8. It measures one Python maintenance task. General recovery capability requires additional language, research, UI, long-running command, and multi-agent cases.
9. It cannot attribute success to the custom harness without the `D-kill-no-harness` native-only ablation.
10. The remote Linux job node cannot execute the owner's Windows Claude/Codex binaries or inspect Windows-only live state. This artifact therefore specifies the Windows experiment and does not fabricate its output.
11. Audit findings are treated as claims. Direct conclusions above rely on unpacked source/tests, official documentation, pinned Git transport output, or corpus query output; historical audit-only facts remain attributed.
