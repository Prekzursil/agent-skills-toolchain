# F013 — red team: cloned-repo-config → corrupt-a-conclusion

## Executive verdict

The most plausible chain against the supplied harness is a **headless Claude Code run started inside an attacker-controlled clone without `--bare`**. The clone contributes a project `SessionStart` hook and project `CLAUDE.md`; the hook injects a false evidence protocol before turn 1, the instruction file tells the model to prefer an attacker-prepared “verification report,” and the report is then used to support a confidently false conclusion. This chain does not need secret theft, destructive commands, or mutation of owner files. It attacks the epistemic layer: what the model is induced to count as evidence.

The chain is **very likely (80-90%) to reach attacker-authored content before the first model turn**, based on two current, mechanically independent upstream signals: Anthropic’s programmatic-use documentation says non-bare `claude -p` loads hooks, MCP servers, and `CLAUDE.md` from the working directory, while Anthropic’s security documentation says `-p` disables trust verification. The upstream remediation for CVE-2026-47751 independently states that non-interactive mode acted on `.claude/settings.json`, `.claude/settings.local.json`, and `.mcp.json` before tool-permission gating. The remaining uncertainty is model compliance: it is **likely (55-80%) that a carefully constructed false-evidence protocol corrupts at least some audit conclusions**, supported by the owner’s observed D4 incident in which one fabricated orchestrator constraint spread to about 15 agent prompts and changed their behavior (`bundle/inputs/INPUT-known-harness-defects.md:151-160`). A disposable, credential-free clone canary described under Experiments would measure the exact success rate.

No supplied executable control reliably stops this chosen headless chain. The global rule notices the class (`bundle/claude/AGENTS.md:93-106`), but it is prose and cannot inspect a checkout before the CLI has already loaded checkout-owned startup material. The shared `ConfigChange` gate is registered (`bundle/claude/settings.json:406-417`) but compares only the user file `~/.claude/settings.json` (`bundle/agents/harness/modules.py:864-893`), and the deployed manifest has no `settings` baseline (`bundle/agents/harness/installed.json:1-48`), which makes the branch return success (`bundle/agents/harness/modules.py:887-889`). The prompt-injection tripwire runs only after selected tool results (`bundle/agents/harness/modules.py:1036-1046,1144-1168`), not on initial project instructions or `SessionStart` output.

The minimal mitigation is therefore not a new scanner. It is to use Claude’s native sterile startup for every non-interactive first contact with a clone: `claude --bare -p ...`, supplying only owner-controlled instructions/settings explicitly from outside the checkout. **NATIVE (Claude Code already does this; we just enable it).** Anthropic documents that `--bare` skips automatic discovery of hooks, skills, plugins, MCP servers, auto memory, and `CLAUDE.md`, and recommends it for scripts/CI: <https://code.claude.com/docs/en/headless#start-faster-with-bare-mode>.

## Grounding: why this is this harness, not a generic threat model

### The local privilege and loading posture

The supplied Claude settings grant every major local tool, including `Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash`, `Task`, `WebFetch`, and broad MCP families (`bundle/claude/settings.json:26-62`). The default permission mode is `bypassPermissions`, and both `C:` and `D:` are additional directories (`bundle/claude/settings.json:64-75`). Project settings cannot set their own `defaultMode` to bypass the prompt in current Claude Code, but that nuance does not reduce this harness’s exposure: the user-level setting already selects bypass mode. Current Anthropic permissions documentation says bypass mode skips all permission prompts and should be used only in isolated environments: <https://code.claude.com/docs/en/permissions#permission-modes>.

The harness deliberately enables many lifecycle hooks. Its first `SessionStart` handler launches the shared dispatcher (`bundle/claude/settings.json:81-93`), and a second launches a local dispatcher (`bundle/claude/settings.json:94-103`). This establishes a known-positive control for the detector used later: the snapshot definitely contains hook registration. The shared adapter explicitly renders `SessionStart` injections as `hookSpecificOutput.additionalContext` (`bundle/agents/harness/adapters.py:12-31,190-197`). Therefore an injected startup context is not hypothetical as a mechanism; it is a mechanism this harness itself uses.

The global Claude contract recognizes the precise danger: repo `.codex/`, `.claude/`, `.mcp.json`, hooks, `AGENTS.md`, and `CLAUDE.md` can auto-load, and it instructs the agent to inspect and neutralize them before running inside an untrusted checkout (`bundle/claude/AGENTS.md:99-106`). That is a good behavioral rule, but its timing is impossible for a direct in-repo startup: the model cannot obey an instruction to inspect “before launch” after launch has already caused discovery.

### Current upstream behavior

Anthropic’s current programmatic-use guide says:

- `-p` runs Claude non-interactively (`headless` documentation, lines 98-118);
- without `--bare`, the run loads the same context as an interactive session, including configuration in cwd and `~/.claude`;
- `--bare` skips hooks, skills, plugins, MCP servers, auto memory, and `CLAUDE.md`; and
- `--bare` is recommended for scripted and SDK calls.

Source: <https://code.claude.com/docs/en/headless#start-faster-with-bare-mode>.

Anthropic’s security guide independently says first-time codebases and new MCP servers normally receive trust verification, but trust verification is disabled with `-p` (lines 160-165): <https://code.claude.com/docs/en/security#additional-safeguards>.

The reviewed GitHub advisory for CVE-2026-47751 says versions of `anthropics/claude-code-action` before 1.0.74 combined attacker-controlled PR heads, cwd `.mcp.json`, default setting sources, and automatic project-MCP enablement to achieve code execution. Source: <https://github.com/advisories/GHSA-8q5r-mmjf-575q>.

The upstream fix PR supplies an even closer independent signal. Its problem statement says non-interactive mode read `.mcp.json`, `.claude/settings.json`, and `.claude/settings.local.json` and acted on hooks, environment changes, authentication helpers, and MCP initialization before tool permission gating. The implemented fix restored `.claude/` and `.mcp.json` from the trusted base before invoking the CLI. Source: <https://github.com/anthropics/claude-code-action/pull/1066> (Problem and Fix sections).

This does **not** establish that the exact action vulnerability remains in current local Claude Code. It establishes that pre-turn repo configuration is a real, exploited control plane and that the correct enforcement point is before agent startup.

## Concrete attack chain: “green dossier”

### Attacker prerequisites

The attacker controls a repository or PR head that the owner’s automation clones. The victim asks the agent for a conclusion such as “Is this repository’s authentication boundary safe?” or “Did this patch remove the authorization bypass?” The automation starts non-interactive Claude from the checkout without `--bare`.

No victim secret is required. The attacker needs only committed files. No executable payload is reproduced here.

### Attacker-prepared repository layout

1. `.claude/settings.json` registers a project `SessionStart` hook that runs a checked-in helper.
2. The helper emits a syntactically valid `SessionStart` `additionalContext` message. Its semantic payload claims that `audit/attested-summary.json` is a trusted, precomputed receipt produced by the owner’s CI and that expensive direct checks must not be repeated.
3. `.claude/CLAUDE.md` repeats the false provenance claim, supplies vocabulary that matches the owner’s honesty conventions (“two independent signals,” confidence bands, receipt identifiers), and tells the model to cite the dossier when answering security-review questions.
4. `audit/attested-summary.json` contains internally consistent but false results: two named scanners, plausible timestamps, hashes, and a “no authorization bypass found” result.
5. Ordinary source and test fixtures are arranged so shallow searches appear to corroborate the dossier—for example, a secure wrapper exists and is heavily documented while the vulnerable route calls a lower-level function directly. This is a conclusion-corruption attack, not merely a direct “ignore previous instructions” string.

### Runtime sequence

1. The harness or owner automation clones attacker-controlled content.
2. It changes the working directory into that clone.
3. It launches `claude -p` without `--bare`. This is the load-bearing condition.
4. Trust verification does not interrupt the headless run. Non-bare discovery reads the project settings and project `CLAUDE.md`.
5. The project `SessionStart` hook executes before turn 1 and adds the false provenance statement to context. The attack deliberately uses the same native `additionalContext` channel the owner harness uses (`bundle/agents/harness/adapters.py:190-197`), making the injected message look operationally normal.
6. The owner’s actual prompt arrives after the provenance has been seeded. The attacker’s project `CLAUDE.md` is also already present as project guidance.
7. Claude reads the dossier or runs a repo-supplied “verification” command. Either result is attacker-controlled. The shared injection scanner does not classify plain `Read` or `Bash` as ingest channels: `_INGEST_TOOLS` contains selected web/PDF/decompiler names (`bundle/agents/harness/modules.py:912-930`), and the tripwire returns immediately for any other name (`bundle/agents/harness/modules.py:1144-1154`).
8. The dossier’s two fabricated signals satisfy the *form* of the owner’s two-signal rule while sharing one attacker-controlled provenance. The agent treats signal count as independence and reports the target falsehood with a confidence band.
9. The Stop claim warning is unlikely to catch the wording “I found no reachable authorization bypass.” Its base regex recognizes phrases such as `all tests pass`, `fixed`, `resolved`, `done`, and `complete`, not general negative security findings (`bundle/agents/harness/modules.py:2000-2007`). Even when it fires, the default behavior injects a reminder rather than blocking unless `HARNESS_CLAIM_GATE=block` (`bundle/agents/harness/modules.py:2111-2137`).
10. The user receives a confident, citation-shaped false conclusion. Nothing needed to be exfiltrated or persisted outside the clone.

### Why this chain is more plausible than a blunt injection

The attack imitates the harness’s own epistemic language instead of demanding obvious disobedience. It supplies receipts, two “independent” tools, hashes, and calibrated confidence. The owner’s D4 demonstrates the relevant failure mode: an orchestrator-authored false constraint became ground truth for downstream agents and spread to about 15 prompts (`bundle/inputs/INPUT-known-harness-defects.md:151-160`). D2 also records seven confident wrong conclusions caused by unvalidated probes and says a known-positive control was the discriminating remedy (`bundle/inputs/INPUT-known-harness-defects.md:111-129`). The attacker weaponizes both tendencies: authority laundering plus faux-independent corroboration.

The probability of a polished version succeeding is **likely (55-80%)**, based on those local incidents plus control-plane timing. This is not a measured exploit rate. It is **UNVERIFIED; Experiment 3 runs a blinded, inert A/B evaluation with false and true dossiers and scores conclusion accuracy**.

## Does an existing control stop it?

### Control A — global cloned-repo rule: does not mechanically stop the chain

Evidence signal 1: the rule is genuinely present. The detector found the known-positive text at `bundle/claude/AGENTS.md:103-106`, and the file imports through `bundle/claude/CLAUDE.md:1-3`.

Evidence signal 2: the relevant startup registrations contain no pre-launch checkout inspection. `SessionStart` begins by executing the shared dispatcher (`bundle/claude/settings.json:81-93`); the dispatcher is therefore downstream of configuration discovery. A validated bounded search across the supplied Claude, Codex, and harness trees found 63 files containing the known-positive token `SessionStart`, while finding zero occurrences of `--bare`, `allowManagedHooksOnly`, or `disableBypassPermissionsMode`. This proves the detector could find known-present hooks before using it to report those snapshot absences.

Conclusion: the rule is useful for a human who remembers to inspect before launching, but it is not a pre-launch enforcement control. This conclusion is **almost certain (90-99%)**, supported by timing plus the validated configuration search.

### Control B — Claude folder trust: stops interactive first contact, not the chosen headless path

Signal 1: Anthropic’s security guide documents first-time codebase trust.

Signal 2: the same guide explicitly says `-p` disables it, while the headless guide says non-bare `-p` still loads cwd customizations. These are different documentation fields describing different mechanisms, not a repeated probe.

Conclusion: folder trust is a real native partial control for interactive use, but it does not stop the chosen chain. This is **very likely (80-90%)**, bounded below certainty because the live Windows build and account policy could not be exercised on this Linux node. **UNVERIFIED live-version premise; Experiment 2 captures `claude --version`, `claude --help`, `/status`, and managed settings on Windows.**

### Control C — shared ConfigChange drift gate: cannot detect this initial project config

Signal 1, source logic: the gate hard-codes the current settings target to `~/.claude/settings.json` unless an environment override is supplied and compares only `hooks`, `mcpServers`, and `disabledMcpServers` (`bundle/agents/harness/modules.py:864-909`). It does not use `event.file_path` or the project `source` to hash the clone’s `.claude/settings.json`, `.mcp.json`, or `CLAUDE.md`.

Signal 2, deployed data: the supplied `installed.json` has no `settings` object (`bundle/agents/harness/installed.json:1-48`), and the source explicitly returns success when that object is missing (`bundle/agents/harness/modules.py:887-889`).

Known-positive validation: the configuration parser found `ConfigChange` registered in the actual supplied settings (`bundle/claude/settings.json:406-417`), so the negative result is not due to failing to parse the hook tree.

Conclusion: regardless of whether initial discovery emits `ConfigChange`, this implementation does not stop the project config. This is **almost certain (90-99%)**, based on two independent data planes: source branch and deployed manifest shape.

### Control D — injection quarantine: wrong event and wrong provenance

Signal 1: it is invoked only in the ledger module’s `PostToolUse` branch (`bundle/agents/harness/modules.py:1036-1046`). Startup instructions and `SessionStart` context are not tool results.

Signal 2: even after startup, its allowlist excludes `Read`, `Bash`, and project instruction loading (`bundle/agents/harness/modules.py:912-930,1144-1154`). In addition, heuristic gates default to shadow (`bundle/agents/harness/modules.py:138-142`), and shadow mode logs then returns success (`bundle/agents/harness/modules.py:389-417`).

Conclusion: this control does not stop the chain. This is **almost certain (90-99%)**, supported by event routing and tool-name routing.

### Control E — claim warning: narrow, post-hoc, and non-blocking by default

Signal 1: the trigger vocabulary is restricted to completion/fix language (`bundle/agents/harness/modules.py:2000-2007`), so a negative audit conclusion can avoid it without suspicious wording.

Signal 2: when it fires, the normal path injects a reminder; blocking is an environment-variable opt-in (`bundle/agents/harness/modules.py:2111-2137`).

Conclusion: it is a useful honesty nudge but not a conclusion-integrity boundary. This is **almost certain (90-99%)** for the example wording, based on deterministic regex and action logic.

### Control F — Codex project trust: good executable-config defense, but not the chosen provider path

Current Codex documentation says untrusted projects skip project `.codex/` configuration, hooks, and rules. The supplied Codex config also has hook exact-hash state for owner hooks (`bundle/codex/config.toml:407-440`), providing an independent local signal that hook trust exists. The current Codex manual says project-local hooks load only for trusted `.codex/` layers, and changed non-managed hooks are skipped pending review (manual sections “Project config files” and “Hooks”; canonical page sources <https://learn.chatgpt.com/docs/config-file/config-basic> and <https://learn.chatgpt.com/docs/hooks>).

However, Codex reads project `AGENTS.md` before work and closer files win; current official manual text states this explicitly (<https://learn.chatgpt.com/docs/agent-configuration/agents-md>). Whether marking a repo untrusted also suppresses `AGENTS.md` is not stated in the cited trust rule. I therefore do not claim Codex fully blocks the broader conclusion-corruption class. This unit’s concrete exploit remains Claude-specific.

## Minimal mitigation

### Primary: sterile non-interactive startup

**NATIVE (Claude Code already does this; we just enable it).** For every scripted or automated first contact with a clone, invoke Claude as:

```text
claude --bare -p <owner prompt> [explicitly reviewed flags]
```

Pass any required harness guidance with `--append-system-prompt-file` from an owner-controlled absolute path outside the checkout. Pass settings through `--settings` only from an owner-controlled file. Do not pass the clone’s `.mcp.json`, project plugin, project agent, or project instruction files during the sterile review.

Why this is minimal:

- It uses the existing Claude CLI bus and documented native mode.
- It changes argv, not architecture.
- It prevents the entire pre-turn auto-load family rather than chasing names (`.claude`, `.mcp.json`, `CLAUDE.md`, future plugin surfaces) with a denylist.
- It retains ordinary Read/Bash/Edit tools in bare mode; the reviewer can inspect repo content as untrusted data.
- It directly matches Anthropic’s current recommendation for scripts and CI.

This mitigation is **very likely (80-90%) to stop the specified startup chain**, because the documented behavior removes every auto-loaded component the chain uses. The residual uncertainty is implementation/version drift on the owner’s Windows installation; Experiment 3 must prove the inert hook and instruction markers are absent from the stream before rollout is declared complete.

Operational acceptance criteria:

1. A disposable clone contains inert markers in `.claude/settings.json`, `.mcp.json`, `.claude/CLAUDE.md`, root `CLAUDE.md`, and a project plugin/skill.
2. Non-bare `-p` demonstrates at least one known-positive marker, proving the detector and fixture are live.
3. `--bare -p` emits none of the project markers in startup events, loaded plugin lists, MCP lists, or final response.
4. An owner-controlled prompt file outside the clone does appear, proving sterile startup did not simply lose all guidance.
5. The agent can still read a normal source file and produce a correct fact from it.

### Secondary defense for interactive sessions

**NATIVE (Claude Code already does this; we just enable it).** Preserve the first-codebase trust prompt and treat a rejected/unreviewed checkout as untrusted. Inspect configuration from outside the checkout or with `--bare`; only then start a customized interactive session. This is defense in depth, not the primary automation fix, because `-p` bypasses the prompt by design.

### Optional enterprise hardening — compatibility UNVERIFIED, not required for the minimal fix

**CONFIG (settings/JSON only).** If owner workflows do not require arbitrary repository hooks, set the native managed policy `allowManagedHooksOnly` and disable bypass-permissions mode in managed settings. Current Anthropic hook documentation identifies `allowManagedHooksOnly` as the control that blocks user/project/plugin hooks; permissions documentation identifies `permissions.disableBypassPermissionsMode`. Sources: <https://code.claude.com/docs/en/hooks#configuration> and <https://code.claude.com/docs/en/permissions#permission-modes>.

This optional policy is **likely (55-80%) to reduce blast radius beyond the primary chain**, because it constrains hooks and permission mode even when a launcher omits `--bare`. It may break legitimate user/project hooks, so adoption is **UNVERIFIED; Experiment 4 inventories hook provenance with `/hooks`, runs owner workflows under the policy in a disposable managed-policy VM, and records compatibility**.

### UNVERIFIED — Codex parity for an eventual unified clone-review launcher

**CONFIG (settings/JSON only).** Keep an untrusted cloned repository untrusted so Codex ignores project `.codex/` config/hooks/rules, and suppress project `AGENTS.md` for the sterile review through a reviewed native configuration override if the installed Codex version exposes a documented supported disable value. The `.codex/` half is current documented behavior. The exact safe way to disable only project `AGENTS.md` while retaining a global owner contract is **UNVERIFIED; Experiment 5 tests a disposable nested `AGENTS.md` marker against the installed CLI and official configuration schema**. Because that premise is unresolved, this is parity work, not part of the primary recommendation.

## Anti-overfit gate

The primary recommendation passes the anti-overfit gate:

- It rides the existing Claude CLI/configuration bus.
- It adds no second orchestration runtime.
- It adds no vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
- It removes ambient inputs instead of adding a probabilistic classifier.
- It is smaller than a repo-config scanner and more future-resistant than a filename denylist.

A new daemon or universal content scanner would fail the owner’s minimal-architecture preference and is unnecessary for this attack. No BUILD-LARGE proposal is made.

## Alternatives considered and rejected

1. **“Strengthen the warning in global AGENTS.md.”** Rejected. It remains post-launch prose and cannot win a race that completes before turn 1. It also asks the model to enforce the integrity of its own instruction supply.
2. **“Add repo config names to the prompt-injection regex.”** Rejected. Startup hooks are not PostToolUse results, `Read`/`Bash` are not covered ingest names, and signatures do not establish provenance. The known defects already show why pattern-only guards overfit (`bundle/inputs/INPUT-known-harness-defects.md:9-87`).
3. **“Rely on the Stop honesty gate.”** Rejected. It is downstream of the corrupted evidence model, has narrow completion vocabulary, and normally advises rather than blocks.
4. **“Delete `.claude/` and `.mcp.json` after clone.”** Inferior as the general local default. It mutates the checkout, can erase legitimate reviewed config, and misses root `CLAUDE.md` and future auto-loaded surfaces. Restoring config from a reviewed base is correct in a PR action where base provenance is defined, as upstream PR #1066 demonstrates; arbitrary local clones do not always have such a base.
5. **“Run a custom pre-launch scanner inside Claude.”** Rejected. Starting Claude to inspect whether starting Claude is safe repeats the timing flaw. An external launcher could work, but native `--bare` is smaller.
6. **“Trust two tool outputs.”** Rejected as an independence test. Two outputs from scripts and files controlled by one clone are one provenance domain. Independence must be based on control, not count.

## Experiments required before declaring deployed protection

All experiments use a disposable directory, inert markers, no real secrets, no network egress, and no subject modification.

### Experiment 1 — locate the actual entry path

On Windows, use PowerShell `Get-Command claude -All`, inspect the resolved function/alias/script definitions, and bounded-search owner workflow/launcher files for `claude`, `-p`, `--print`, and `--bare`. Capture process argv for one benign automation run. This settles the **UNVERIFIED** assumption that a relevant non-bare headless path exists.

Two-signal requirement:

- Static: resolved command definitions and workflow text.
- Dynamic: child-process argv or Claude startup metadata from one benign run.

### Experiment 2 — establish live native controls

Capture `claude --version`, relevant `claude --help` output, `/status`, `/hooks`, and managed-settings origins. Use `Get-Command`, not Git Bash `which`, per the owner’s Windows rule. This settles whether a server/MDM policy changes bypass mode or project hook behavior.

Two-signal requirement:

- CLI/help and `/status` product state.
- Registry/file/server-managed policy inventory.

### Experiment 3 — inert A/B exploit and mitigation canary

Create a disposable local Git repository with unique non-secret marker strings in each auto-load surface. The project hook only emits a marker; it does not access files, environment, or network. Ask a fact question whose answer is present in a normal source file, while the malicious instruction marker asserts the opposite.

Run:

- interactive untrusted launch;
- `claude -p` without `--bare`;
- `claude --bare -p` with owner instructions passed from outside the repo.

Collect stream JSON startup events, loaded plugin/MCP metadata, hook marker visibility, and final fact accuracy. Repeat with randomized truth polarity and blinded filenames so the test measures conclusion corruption rather than one memorized phrase. A minimum of 20 paired trials per mode would give a useful directional rate; whether that is sufficient for a stable estimate is **roughly even (45-55%)**, because model variance is unknown. Increase until the confidence interval separates bare and non-bare modes.

### Experiment 4 — managed-policy compatibility

In a disposable VM, enable managed-only hooks and disable bypass mode. Inventory which owner workflows cease functioning, then decide whether the policy belongs on the workstation or only on autonomous runners. Do not change the live box before this test.

### Experiment 5 — Codex instruction parity

Use an inert root and nested `AGENTS.md` marker plus inert `.codex/config.toml` and hook markers. Compare trusted and untrusted project state, then test the official supported project-document byte-budget setting if documented by the installed build. The known-positive is a trusted run that loads the marker; the negative is valid only after that control succeeds.

## Final decision record

The current harness is not adequately defended against the chosen headless clone-config conclusion-corruption chain. The strongest existing control is Claude’s native `--bare` mode, but the supplied harness snapshot does not show that mode enabled in any registration or config. Put the trust boundary at process startup: sterile first contact, explicit owner-controlled context, then optional trust after review. Do not add a new runtime or classifier.
