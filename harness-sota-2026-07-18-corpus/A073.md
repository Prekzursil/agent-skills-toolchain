# A073 — coherence audit of `~/.claude/rules/typescript/patterns.md`

## Executive verdict

The 52-line target is not a coherent enforceable rule. It is three unexplained TypeScript examples, path-scoped to four TypeScript **and JavaScript** extensions, while its declared common parent contains the actual normative language. I confirmed six collisions/defects:

1. **CONTRADICTION:** the common response contract requires nullable `data` and `error`; the TypeScript child makes both optional, admitting invalid states.
2. **REDUNDANCY:** the repository example repeats the common repository operation list without adding applicability or semantics.
3. **STALE / badly written:** a file that the harness defines as a broad standard contains only “how” examples, contradicting the harness's own rules-versus-skills division and applying TypeScript-only syntax to `.js`/`.jsx`.
4. **UNENFORCED:** no active hook checks any of the three advertised patterns; the active per-edit checker explicitly skips `.ts`/`.tsx`, and the native TypeScript LSP plugin is disabled.
5. **UNRULED + CONTRADICTION:** that same active checker sends `.jsx` to `node --check` and hard-blocks the resulting error. A known-valid JSX control was blocked solely because Node 22 does not accept the `.jsx` extension.
6. **STALE:** the TypeScript hook rule and a dormant `hooks.json` advertise formatter/typecheck/console checks that are not wired by current `settings.json`; this makes the nearby documentation look like enforcement for the target rule when it is not.

The most important remedy is not to build an architectural-policy hook. It is to replace the globally prescriptive examples with a short, project-contract-first rule, correct the response type to a discriminated union **only where a project already uses an envelope**, and use project-native contract tests/lint/typecheck for actual enforcement. This is **very likely (80-90%)** to reduce false architectural steering without losing useful guidance, because the target has no applicability gates (`patterns.md:12-51`), the rules README says configuration is reference-only and must follow actual project requirements (`rules/README.md:66`), and the existing generic hook already demonstrably false-blocks valid JSX.

No replacement runtime, vector store, critic, durable engine, SaaS, or guardrail framework is proposed. Every resolution rides the existing rule/settings/hook/project-test buses.

## Collision register

### C1 — API response nullability and valid-state collision

**Class:** CONTRADICTION

**Artifact A:** `~/.claude/rules/common/patterns.md:45-51`

> “Use a consistent envelope for all API responses”; include a data payload “nullable on error,” an error field “nullable on success,” and pagination metadata.

**Artifact B:** `~/.claude/rules/typescript/patterns.md:12-25`

> `data?: T`, `error?: string`, and optional `meta` are independent properties alongside `success: boolean`.

**Conflict.** Nullable and optional are different contracts. The child permits `{success: true}`, `{success: false}`, `{success: true, error: "bad"}`, and `{success: false, data: value}`. It also makes `meta.total/page/limit` all mandatory whenever `meta` exists, without saying whether cursor pagination or non-paginated responses are allowed. The language-specific priority rule (`rules/README.md:93-98`) technically selects the TypeScript form over the common form, but AGENTS §10 does not resolve this rule-vs-rule collision, and “specific wins” does not explain why the child weakens the invariant.

**Diagnosis:** the rule is **wrong**, not merely unenforced. A hook that perfectly enforced this interface would faithfully enforce invalid states.

**Resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the example with a project-contract-first statement and, only as an example, a discriminated union such as success `{ success: true; data: T; error?: never; meta?: PageMeta }` versus failure `{ success: false; data?: never; error: ApiError; meta?: never }`. State that existing OpenAPI/GraphQL/tRPC/framework conventions win. Change the common rule from “all API responses” to “when the project uses an envelope, preserve its schema.” It is **very likely (80-90%)** that this eliminates impossible response states because TypeScript discriminated unions narrow on the literal `success` field, while the evidence for the present impossible states is directly visible at target lines 15-23.

**Anti-overfit gate:** pass. This is a small rule-bus edit and adds no runtime. Do not add a universal response-shape hook.
