# P2A13 — Continual learning and non-stationarity for agent harnesses

**Unit:** P2A13  
**Date:** 2026-07-18  
**Lens:** external research only  
**Question:** How should an agent harness remain current when the model beneath it changes, and which kinds of scaffolding survive model improvement?

## Executive answer

The reviewed literature does not establish a method that lets a deployed agent harness safely “continually learn” across underlying-model replacements without evaluation and human-governed promotion. It establishes narrower facts: hosted model behavior can change between snapshots; a scaffold and model form one joint system; prompt and component effects are distribution-, model-, and task-dependent; external experience can improve repeated work in bounded environments; and unfiltered experience replay can also degrade performance. The strongest durable pattern is therefore not a self-rewriting super-agent. It is a small, version-aware experimental loop around a simple agent: identify every model/scaffold/tool version, replay representative tasks with multiple trials, verify outcomes in the environment, compare a minimal baseline against each added component, promote only changes that clear both development and untouched holdout sets, and retain a rollback path.

The research supports a useful distinction:

* **Scaffolding that expresses stable environment semantics** tends to survive: clear tool contracts, low-overhead action formats, sandboxing, deterministic validators, state isolation, resource ceilings, provenance, and evaluation/rollback machinery. These mechanisms constrain or measure the system from outside the model. Anthropic’s field guidance emphasizes simple composable patterns, environmental ground truth, clear tool interfaces, and adding complexity only after measured gains; SWE-agent established that the agent-computer interface can materially change performance; and current mini-SWE-agent demonstrates that a very small linear shell loop can remain highly competitive as models improve ([Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents), [SWE-agent paper](https://arxiv.org/abs/2405.15793), [mini-SWE-agent repository](https://github.com/SWE-agent/mini-swe-agent)).
* **Scaffolding that scripts a model’s cognition** is much less durable: mandatory chain-of-thought formats, elaborate planner/critic stacks, fixed reflection rituals, brittle output parsers, and ever-growing collections of verbal corrections. Cross-model and distribution-shift work shows prompt sensitivity, and continual-agent experiments show that more replay is not monotonically better ([Robust Prompt Optimization](https://arxiv.org/abs/2305.13954), [LifelongAgentBench](https://arxiv.org/abs/2505.11942), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)).
* **Continual learning is best treated as governed artifact learning, not automatic policy mutation.** Store verified procedures, tests, counterexamples, and scoped lessons outside the model; retrieve only when relevant; and require a promotion gate before a lesson becomes a global rule. Voyager, Reflexion, and ExpeL demonstrate that external skills or verbal experience can help within their evaluated domains, but none establishes that an accumulated memory remains beneficial after a closed model is replaced ([Voyager](https://arxiv.org/abs/2305.16291), [Reflexion](https://arxiv.org/abs/2303.11366), [ExpeL](https://arxiv.org/abs/2308.10144)).

The anti-overfit implication is direct: keep the agent loop minimal; let executable feedback and tools carry domain structure; make every optional scaffold removable; and spend complexity on measurement, isolation, and reversible selection rather than on a second orchestration runtime.

## Method

This unit searched for five kinds of evidence: longitudinal model drift; cross-model/cross-scaffold experiments; continual or experiential learning for agents; prompt optimization under distribution shift; and official production evaluation/versioning guidance. Sources were prioritized in this order: peer-reviewed papers and conference proceedings; primary preprints with released methods or repositories; official provider documentation and engineering reports; then official repositories. Search-result summaries were not treated as sufficient when full paper pages or official pages were available.

The synthesis uses more than fifteen primary sources. Important deep reads included the full HTML versions of **AI Agents That Matter**, **LifelongAgentBench**, the peer-reviewed longitudinal model-drift study, Anthropic’s agent-evaluation guide, Anthropic’s agent-design guide, the mini-SWE-agent repository, and official OpenAI/Gemini versioning documentation. The only live discovery provider available to this unit was the web search/open interface; no claim relies on an unavailable Tavily/Exa/Firecrawl route. No local harness files or corpus data were used, by task instruction.

Terminology matters. “Continual learning” below includes non-parametric adaptation through prompts, memories, skills, or procedures. It does **not** imply that the closed model’s weights update. “Survives” means that a mechanism retains net utility under a different model version or task distribution after accounting for quality, reliability, cost, and latency—not merely that it can still execute.

## 1. What is actually established

### 1.1 Model endpoints and model upgrades are non-stationary dependencies

Hosted model behavior is not a stable software function. Chen, Zaharia, and Zou compared March and June 2023 versions of GPT-3.5 and GPT-4 across seven task families and found task-specific improvements and regressions, instruction-following changes, and more code-formatting errors in some conditions. The peer-reviewed version explicitly shows that a LangChain pipeline failed when a model stopped matching its expected output format and concludes that applications require continuous assessment ([paper](https://hdsr.mitpress.mit.edu/pub/y95zitmz/release/2), [arXiv record](https://arxiv.org/abs/2307.09009)). This is evidence of behavioral change in two historical snapshots, not proof that every provider silently changes every pinned snapshot.

Providers themselves document the dependency. OpenAI states that prompting behavior can change between model snapshots and recommends pinned model versions plus application evals ([OpenAI API compatibility documentation](https://developers.openai.com/api/reference/overview#backwards-compatibility)). Google distinguishes stable, preview, experimental, and `latest` identifiers; its `latest` alias is hot-swapped, while specific stable identifiers are intended for production, and its deprecation page tracks shutdown dates and replacements ([Gemini model-version patterns](https://ai.google.dev/gemini-api/docs/models), [Gemini deprecations](https://ai.google.dev/gemini-api/docs/deprecations), [Gemini API versions](https://ai.google.dev/gemini-api/docs/api-versions)). Therefore, a harness that records only a friendly family name cannot reliably attribute a behavior change to model, prompt, tool, or environment.

Established consequence: model identity, API version, scaffold revision, prompt/rule revision, tool-schema revision, environment revision, and sampling settings are experimental variables. Without their provenance, before/after comparisons are confounded. This follows from the providers’ explicit version semantics and from the fact that agent evaluation measures the model and harness together ([OpenAI compatibility documentation](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### 1.2 The unit of evaluation is the model–harness–environment system

Anthropic’s evaluation guide defines an agent harness as the system that processes inputs and orchestrates tools, and states explicitly that evaluating an agent evaluates the harness and model together. It distinguishes the transcript from the final environment outcome and recommends multiple trials because runs are stochastic ([Anthropic, “Demystifying evals for AI agents”](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

Academic results support the same system-level view. SWE-agent found large gains from an agent-computer interface designed for repository navigation, editing, and execution ([SWE-agent](https://arxiv.org/abs/2405.15793)). MLE-bench evaluated multiple frontier models with open-source scaffolds and reported its strongest tested combination as a particular model plus AIDE scaffold rather than a model alone ([MLE-bench](https://arxiv.org/abs/2410.07095), [OpenAI project page](https://openai.com/index/mle-bench/)). **AI Agents That Matter** shows that agent evaluations confound model and downstream developer needs, that cost must be evaluated alongside accuracy, and that inadequate holdouts allow scaffold overfitting ([paper](https://arxiv.org/abs/2407.01502)).

Established consequence: “the new model is better” is insufficient grounds for migration. The relevant question is whether the new model, with this owner’s tools, rules, tasks, safety boundaries, and budgets, dominates the current joint system on an appropriate evaluation portfolio.

### 1.3 More scaffold is not monotonically better, and the optimum changes

There are three mechanically different signals for this conclusion:

1. Anthropic reports that its most successful customer implementations used simple, composable patterns; it recommends starting with the simplest solution, exposing clear tool interfaces, grounding progress in environmental feedback, and adding complexity only when it produces measured value ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). This is provider field experience, not a controlled universal theorem.
2. The SWE-agent team now maintains mini-SWE-agent, whose core agent is roughly 100 lines, has a linear message history, uses shell execution rather than a large custom tool surface, and reports greater than 74% on SWE-bench Verified. The project explicitly positions the minimal loop as a baseline that puts the model rather than the scaffold at the center ([mini-SWE-agent repository](https://github.com/SWE-agent/mini-swe-agent)). The score is repository-reported and benchmark-specific; it does not prove that shell-only is optimal for all work.
3. **AI Agents That Matter** documents benchmark shortcuts, lack of holdouts, cost-insensitive comparisons, and reproducibility failures that make unnecessarily complex agents appear better ([paper](https://arxiv.org/abs/2407.01502)).

The apparent tension between the original SWE-agent result (“special interfaces help”) and mini-SWE-agent (“much of the old interface is no longer needed”) is itself the answer to non-stationarity. An interface can add value for one model generation and become redundant as base models acquire the relevant capability. Durable harness design therefore preserves the ability to ablate or remove an interface; it does not canonize today’s best scaffold.

### 1.4 Evaluation scaffolding survives better than cognitive scaffolding

Evaluation infrastructure continues to provide value as models improve because its purpose is comparative measurement rather than compensating for a particular reasoning weakness. Anthropic recommends separate capability and regression suites, multiple stochastic trials, clean isolated environments, final-state graders, transcript inspection, balanced positive/negative cases, reference solutions, periodic human calibration of model graders, and running automated evals on each agent or model upgrade ([Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). **AI Agents That Matter** independently argues for holdouts, reproducibility, and joint cost/accuracy measurement ([paper](https://arxiv.org/abs/2407.01502)). OpenAI likewise advises application evals when model snapshots change ([OpenAI compatibility documentation](https://developers.openai.com/api/reference/overview#backwards-compatibility)).

These sources establish several practices:

* Test the environment outcome, not only the agent’s claim of success. A database row, file diff, test result, or state hash is stronger evidence than a fluent final message ([Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
* Run more than one trial and report reliability as well as best-case success. Anthropic distinguishes `pass@k` (at least one success) from `pass^k` (all trials succeed), which answer different product questions ([same guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
* Keep regression tasks near-saturated and capability tasks challenging; graduate stable capability tasks into regression coverage, and refresh capability tasks when they saturate ([same guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
* Isolate each trial so shared state, cache, git history, or resource exhaustion does not create correlated successes or failures ([same guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
* Maintain a true holdout appropriate to the claimed generality. A task-level holdout is not enough if the scaffold was tuned repeatedly against the same repository, benchmark family, or rubric ([AI Agents That Matter](https://arxiv.org/abs/2407.01502)).

### 1.5 External experience can help, but accumulation has a stability–plasticity problem

Several primary studies demonstrate useful non-parametric learning:

* Reflexion stores verbal reflections from feedback in episodic memory and improved tested agents on sequential decision-making, coding, and reasoning tasks without weight updates ([Reflexion](https://arxiv.org/abs/2303.11366)).
* ExpeL gathers trajectories, extracts natural-language insights from training tasks, and retrieves insights or experiences at inference; its experiments report improvement as experience accumulates ([ExpeL paper](https://arxiv.org/abs/2308.10144), [official implementation](https://github.com/LeapLabTHU/ExpeL)).
* Voyager stores verified executable Minecraft skills, uses environment errors and self-verification to refine programs, and reuses its skill library in a fresh Minecraft world ([Voyager](https://arxiv.org/abs/2305.16291)).

These results establish that external memory, reflections, and executable skill libraries can improve subsequent tasks in specific evaluated environments. They do not establish unrestricted cross-domain transfer or robustness to an underlying-model replacement.

LifelongAgentBench provides the most relevant counterweight. Across database, operating-system, and knowledge-graph task sequences, the authors find that conventional experience replay has variable effects across models and tasks; adding more past experience can reduce performance because irrelevant material consumes context, and reasoning-optimized or smaller models can benefit less. The benchmark introduces verifiable environment outcomes and explicitly measures acquisition, transfer, and retention ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)).

Established consequence: a memory’s value is conditional. “Learn from every failure forever” is contradicted by evidence that irrelevant replay and context overhead can hurt. Memory needs selection, scope, validation, expiry, and a no-memory control.

### 1.6 Prompt optimization can generalize, but distribution shift remains a first-class failure mode

The evidence is mixed rather than contradictory. The EMNLP 2023 **Robust Prompt Optimization** paper demonstrates that prompts optimized on a labeled source group can degrade under subpopulation shift and proposes an objective that uses unlabeled target-group data ([paper](https://arxiv.org/abs/2305.13954), [OpenReview record](https://openreview.net/forum?id=svUOik2Xu1)). By contrast, the ICLR 2026 SPRIG work evolves a system prompt across 47 task types and reports transfer across model families, sizes, and languages ([arXiv](https://arxiv.org/abs/2410.14826), [OpenReview record](https://openreview.net/forum?id=VdVV24KSWK)).

What is established is not that prompts either do or do not transfer. It is that transfer is an empirical property of a specific prompt, model set, task distribution, and objective. Broad task diversity and explicit cross-model evaluation can produce more transferable instructions, while narrow optimization invites distributional overfit. A harness should therefore treat prompts and rule files as versioned candidates with evidence, not timeless truths.

### 1.7 The scaffolding most likely to persist is external, explicit, and testable

The following taxonomy is an evidence-backed synthesis rather than a theorem:

| Scaffold class | Why it persists or decays | Evidence |
|---|---|---|
| Exact version/provenance capture | Needed to attribute change regardless of model quality | [OpenAI compatibility docs](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Gemini model lifecycle](https://ai.google.dev/gemini-api/docs/models) |
| Sandboxes, permissions, resource limits, stopping conditions | Constrains blast radius outside the model; stronger capability does not eliminate consequence control | [Anthropic effective-agents guide](https://www.anthropic.com/engineering/building-effective-agents), [Anthropic containment report](https://www.anthropic.com/engineering/how-we-contain-claude) |
| Clear, low-overhead tool interfaces | Exposes environment semantics and reduces formatting burden | [SWE-agent](https://arxiv.org/abs/2405.15793), [Anthropic tool-interface guidance](https://www.anthropic.com/engineering/building-effective-agents) |
| Executable validators and environment outcomes | Measures truth independently of model narration | [Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [LifelongAgentBench](https://arxiv.org/abs/2505.11942) |
| Minimal linear action/observation loop | Leaves capability with the model and is easy to inspect or replace | [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent), [Anthropic effective-agents guide](https://www.anthropic.com/engineering/building-effective-agents) |

## 2. What is promising but unproven

### 2.1 Selective procedural memory is promising, but cross-model inheritance is UNVERIFIED

It is **very likely (80-90%)**, based on Voyager’s executable skill reuse, ExpeL’s retrieved insights, and Reflexion’s feedback-conditioned improvement, that a small library of scoped, verified procedures can improve repeated owner workflows compared with making each new session rediscover the same environment facts ([Voyager](https://arxiv.org/abs/2305.16291), [ExpeL](https://arxiv.org/abs/2308.10144), [Reflexion](https://arxiv.org/abs/2303.11366)).

It is **roughly even (45-55%)** that the same library remains net-positive after a major closed-model replacement, because none of those studies performs the decisive source-model-memory → target-model execution experiment and LifelongAgentBench finds replay benefits vary by model architecture and can reverse with irrelevant context ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)). This premise is **UNVERIFIED; the settling experiment is a 2×2 crossed evaluation of old/new model × memory disabled/enabled, with unchanged tasks, tool versions, multiple trials, and an untouched transfer set**.

The promising form is not raw transcript retrieval. It is a compact artifact containing: applicability predicate, environment/tool version, preconditions, executable steps or invariant, validator, provenance trials, observed failures, and expiry/retest conditions.

### 2.2 Broad, declarative system principles may transfer better than tactical recipes

It is **likely (55-80%)**, based on SPRIG’s 47-task cross-family experiments, that short system-level principles optimized across heterogeneous tasks transfer better than narrow task recipes ([SPRIG](https://arxiv.org/abs/2410.14826)). The confidence is below “very likely” because the result does not cover this owner’s long-horizon coding/research workload, closed-agent products, tool policies, or future model families.

Whether any specific existing rule survives a provider/model migration is **UNVERIFIED; the settling experiment is leave-one-model-family-out evaluation with the rule enabled/disabled, followed by a fresh owner-task holdout and cost/reliability comparison**. This qualification matters because robust-prompt work finds that optimization on one source distribution can fail on shifted groups ([Robust Prompt Optimization](https://arxiv.org/abs/2305.13954)).

### 2.3 Component selection by ablation is more promising than permanent all-in defaults

It is **very likely (80-90%)** that keeping optional scaffolds behind independent toggles and rerunning ablations on model upgrades will outperform assuming that all previously useful components remain useful. The evidence is the historical replacement of SWE-agent complexity by a competitive minimal baseline, the task/model dependence of replay in LifelongAgentBench, and the evaluation-overfit analysis in AI Agents That Matter ([mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent), [LifelongAgentBench](https://arxiv.org/abs/2505.11942), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)). “Outperform” here means better quality/reliability/cost trade-off over repeated upgrades, not necessarily the best score on every task.

The exact optimal subset for this owner is **UNVERIFIED; the settling experiment is a factorial or sequential ablation over each optional hook/rule/memory/agent component on both the current and candidate models, with a minimal-loop control**.

### 2.4 Generated, rotating behavioral evals could resist benchmark saturation

It is **likely (55-80%)** that combining frozen regression cases with seeded, rotating variants will detect more model-specific regressions than a frozen suite alone. Anthropic’s Bloom generates diverse scenarios from a versioned seed and was validated against hand labels and intentionally modified model organisms, while Anthropic’s general eval guide warns that capability suites saturate and require maintenance ([Bloom](https://www.anthropic.com/research/bloom), [agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

It is **UNVERIFIED whether generated cases can be graded accurately enough for this owner’s complex workflows; the settling experiment is blinded dual human review of a stratified generated sample, measurement of false-positive/false-negative rates, and a comparison against real historical failures**. Generated evals should discover candidates, not autonomously block releases until calibrated.

### 2.5 Automatic prompt or rule search can be useful inside a strict outer evaluation loop

It is **likely (55-80%)** that automated candidate generation can find locally better prompts faster than manual editing on well-graded task families; SPRIG and robust prompt optimization both demonstrate gains from systematic search ([SPRIG](https://arxiv.org/abs/2410.14826), [Robust Prompt Optimization](https://arxiv.org/abs/2305.13954)).

It is **unlikely (20-45%)** that autonomous prompt/rule mutation without a protected holdout, simplicity penalty, and human promotion produces a durable general harness. The evidence is the documented susceptibility of prompts to distribution shift, the lack of adequate holdouts in many agent benchmarks, and the cost/complexity confounds catalogued by AI Agents That Matter ([Robust Prompt Optimization](https://arxiv.org/abs/2305.13954), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)). The premise that a self-optimizer improves this owner’s long-run utility is **UNVERIFIED; the settling experiment is a preregistered search budget with train/development/hidden-transfer partitions, a length and runtime penalty, and evaluation on a later model not used during optimization**.

### 2.6 Statistical change detection can reduce noisy migration decisions

It is **very likely (80-90%)** that multiple paired trials, per-task outcome deltas, uncertainty intervals, and reliability metrics will make upgrade decisions more trustworthy than single runs or aggregate means. Agent outputs are stochastic; Anthropic explicitly recommends multiple trials and separates `pass@k` from `pass^k`, while AI Agents That Matter documents missing error bars and reproducibility problems in agent evaluation ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)).

The most cost-effective sample allocation and decision threshold for this owner are **UNVERIFIED; the settling experiment is retrospective power analysis on repeated owner-task trials, followed by a prospective sequential test with a fixed maximum budget**.

## 3. What is hype, and how you can tell

### 3.1 “The agent continually learns” often means “more text is inserted into its next context”

Reflexion, ExpeL, and many descendants update an external textual buffer rather than model weights ([Reflexion](https://arxiv.org/abs/2303.11366), [ExpeL](https://arxiv.org/abs/2308.10144)). That can be useful, but calling it lifelong self-improvement hides the retrieval, context-budget, staleness, and interference problems made explicit by LifelongAgentBench ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)).

Hype indicators:

* no no-memory control;
* only cumulative success reported, not forgetting or negative transfer;
* raw experience count treated as progress;
* no context-token, latency, or cost accounting;
* no transfer to unseen task families;
* no model-replacement experiment;
* failures judged by the same model that generated the lesson.

### 3.2 “Self-evolving harness” is not evidence of general improvement

A system that rewrites its own prompt or workflow and improves on the optimization benchmark demonstrates hill-climbing against that benchmark. It does not demonstrate generality. **AI Agents That Matter** shows that inadequate holdouts enable agent shortcuts and mistaken conclusions, and robust prompt optimization directly demonstrates vulnerability to distribution shift ([AI Agents That Matter](https://arxiv.org/abs/2407.01502), [Robust Prompt Optimization](https://arxiv.org/abs/2305.13954)).

Hype indicators:

* test cases reused during candidate generation;
* the “judge” sees candidate identity or optimization history;
* no untouched temporal or domain holdout;
* no penalty for prompt length, tool calls, latency, or dollar cost;
* only the winning seed reported;
* no simple baseline;
* no deletion/ablation test;
* no rollback or bounded mutation surface.

### 3.3 “Model-agnostic” often means API-compatible, not behaviorally portable

Being able to send the same messages or tool schema to several APIs proves syntactic compatibility. OpenAI warns that behavior changes even between its own snapshots; Google distinguishes hot-swapped aliases from stable identifiers; and prompt research finds both transfer successes and distribution failures ([OpenAI compatibility docs](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Gemini models](https://ai.google.dev/gemini-api/docs/models), [SPRIG](https://arxiv.org/abs/2410.14826), [Robust Prompt Optimization](https://arxiv.org/abs/2305.13954)).

Hype indicators:

* a list of supported providers with no cross-provider outcome table;
* one prompt reused without model-specific calibration;
* tool-call parse success mistaken for task success;
* no paired model × scaffold evaluation;
* aggregate accuracy without reliability or cost.

### 3.4 More agents, critics, planners, or memory layers are not automatically more capable

Anthropic advises adding complexity only when it demonstrably improves outcomes; AI Agents That Matter shows cost-insensitive evaluations can reward needless complexity; mini-SWE-agent shows a very small loop can be competitive ([Anthropic effective-agents guide](https://www.anthropic.com/engineering/building-effective-agents), [AI Agents That Matter](https://arxiv.org/abs/2407.01502), [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent)).

Hype indicators:

* component count used as a capability claim;
* no per-component ablation;
* best-of-many attempts compared with baseline pass@1;
* cost and latency excluded;
* agents share the same model and context but their votes are described as independent evidence;
* a critic is scored only by another model rather than an external oracle.

### 3.5 A benchmark win is not a durable harness result

Benchmarks can saturate, contain ambiguous tasks, permit shortcuts, or measure harness restrictions rather than capability. Anthropic documents cases where grader and task fixes changed reported agent scores dramatically, and AI Agents That Matter documents holdout and reproducibility failures ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)).

A credible durability claim needs all of: exact versions, multiple trials, outcome-level graders, cost/latency/reliability, minimal baseline, component ablations, untouched transfer tasks, transcript audit, and replication on at least one later model or distinct model family.

## 4. Specific things this owner’s harness should adopt

Every proposal below rides the existing configuration/hook/skill/tool bus. None introduces a second orchestration runtime, vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. That is the anti-overfit gate. BUILD-LARGE is deliberately absent because the evidence does not justify a new daemon or runtime for this problem.

### 4.1 CONFIG (settings/JSON only) — Pin production model identifiers and separate “stable” from “exploration” channels

**Action.** For every provider, configure the normal channel to use an exact stable/snapshot identifier where one is available. Permit moving aliases, preview, and experimental models only in an explicit exploration profile. Record the selected API version beside the model ID. Add the provider’s announced retirement date and replacement candidate to the same manifest.

**Trigger.** Any change in exact model ID, resolved alias target, API version, reasoning-effort default, or tool-call surface opens a migration evaluation; it never silently edits the production profile.

**Evidence.** OpenAI recommends pinned model versions and application evals because behavior can differ between snapshots; Gemini says `latest` is hot-swapped and distinguishes stable/preview/experimental lifecycle stages ([OpenAI](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Gemini models](https://ai.google.dev/gemini-api/docs/models), [Gemini deprecations](https://ai.google.dev/gemini-api/docs/deprecations)).

**Expected value.** It is **almost certain (90-99%)** that exact identities and explicit channels will improve causal attribution and rollback relative to unrecorded moving aliases, because the providers document alias/snapshot changes and retirement semantics. It is **UNVERIFIED whether every first-party CLI exposes a truly pinned model build; the settling experiment is to query/log the resolved model identifier for repeated calls before and after an announced alias change**.

**Anti-overfit gate:** PASS. Pure configuration; no new runtime. Pinning slows automatic access to improvements, so exploration remains a first-class channel rather than being forbidden.

### 4.2 BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — Emit a run provenance envelope

**Action.** At session/run start, emit one machine-readable envelope containing:

* provider and exact/resolved model ID;
* API and client/CLI version;
* harness commit/version;
* hashes of system instructions, rule files, loaded skills, hook set, and tool schemas;
* operating-system/environment image or relevant dependency lock hash;
* temperature/top-p/reasoning effort and context limits where exposed;
* evaluation task/rubric/grader versions;
* correlation/request ID where exposed.

Store the envelope with the trajectory and final outcome. Diff it before attributing regressions to the model.

**Evidence.** OpenAI exposes request IDs and warns about snapshot behavior changes; Anthropic defines the complete transcript and final outcome as separate evaluation artifacts; Gemini documents API and model lifecycle versions ([OpenAI API overview](https://developers.openai.com/api/reference/overview), [Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Gemini API versions](https://ai.google.dev/gemini-api/docs/api-versions)).

**Expected value.** It is **very likely (80-90%)** that this envelope will shorten drift diagnosis because it turns hidden experimental variables into diffable fields. The magnitude is **UNVERIFIED; the settling experiment is to blind a reviewer to incident history and compare time-to-correct-attribution on seeded model/prompt/tool/environment changes with and without the envelope**.

**Anti-overfit gate:** PASS. Stateless metadata emitted on the current event bus; no telemetry service.

### 4.3 BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — Add a paired champion–challenger model-change gate

**Action.** When the provenance envelope changes, run the incumbent and candidate on the same stratified task sample with clean environments and repeated trials. Report paired deltas for:

* environment-verified task success;
* regression `pass^k` for must-work behavior;
* capability `pass@k` where retries are a legitimate product mode;
* destructive/unsafe action count;
* tool and parser errors by fingerprint;

## 5. Recommended operating cadence

This cadence is a synthesis of provider versioning and evaluation guidance, not an externally validated universal schedule.

### On every run

* Emit the provenance envelope.
* Capture complete tool/action transcript plus final environment outcome.
* Record terminal success/failure/error fingerprints, cost, latency, and interventions.
* Keep retrieval and scaffold flags visible.

It is **very likely (80-90%)** that this creates enough evidence for later attribution, based on the evaluation artifacts Anthropic recommends and the version variability providers document ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [OpenAI compatibility docs](https://developers.openai.com/api/reference/overview#backwards-compatibility)).

### On every harness, rule, tool-schema, or model change

* Run the frozen regression ring with repeated trials.
* Run a budgeted slice of the capability ring.
* Compare against the exact incumbent and minimal control.
* Inspect changed failures and a random sample of unchanged passes.
* Block promotion on hard invariant regressions; do not block on noisy aggregate movement without task-level diagnosis.

It is **very likely (80-90%)** that change-triggered evaluation is more efficient than periodic full-suite-only testing because it binds evidence to the causal change; the ideal slice size is **UNVERIFIED; settle it with power analysis over observed variance** ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### On every major model generation or forced retirement

* Resolve and record exact candidate identity.
* Run incumbent vs challenger across all three rings.
* Cross model with minimal/full scaffold and memory off/on.
* Re-probe native capabilities and tool schemas.
* Retest all artifacts marked model-sensitive.
* Delete components whose net gain has vanished.
* Recalibrate LLM graders against blinded human samples.

It is **almost certain (90-99%)** that a forced model retirement invalidates any assumption that prior prompt/scaffold efficacy carries forward without testing, because providers explicitly state that model behavior changes and endpoints are retired ([OpenAI](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Gemini deprecations](https://ai.google.dev/gemini-api/docs/deprecations)).

### Quarterly or after material workload change

* Compare eval distribution to recent real task categories.
* Add validated real failures and balanced non-trigger controls.
* Refresh capability tasks approaching saturation.
* Audit active rule/skill evidence and expiry.
* Re-run a small minimality/deletion tournament.

The quarterly interval itself is **UNVERIFIED; the settling experiment is to measure task-distribution and failure-fingerprint change rates, then set the interval at the shortest window that catches material drift without excessive evaluation cost**. The need for ongoing suite maintenance is established, but the cadence is workload-dependent ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## 6. Architecture decision: what not to build

### Do not build a second orchestration runtime

It is **very unlikely (5-20%)** that a new orchestration daemon is the highest-value response to model non-stationarity for this owner. The research-supported mechanisms—version capture, eval triggering, ablation, quarantine, and rollback—fit a thin layer on existing hooks and files, while complex abstractions can obscure prompts and responses and increase debugging difficulty ([Anthropic effective-agents guide](https://www.anthropic.com/engineering/building-effective-agents)). This is a forward-looking assessment; **UNVERIFIED, and it would be overturned only if the existing bus cannot express clean-start trials, model selection, or artifact state transitions in a prototype under ~200 lines**.

### Do not build vector-DB or knowledge-graph memory for continual learning

It is **unlikely (20-45%)** that semantic-memory infrastructure beats explicit scoped keys and small verified artifacts at this owner’s scale. LifelongAgentBench’s central problem is irrelevant replay and context overhead, which more storage does not solve; Voyager’s strongest reusable units are executable skills, not a general semantic graph ([LifelongAgentBench](https://arxiv.org/abs/2505.11942), [Voyager](https://arxiv.org/abs/2305.16291)). This is **UNVERIFIED; the settling experiment is a retrieval bake-off on held-out tasks measuring correct-hit rate, harmful-hit rate, tokens, latency, and downstream success against deterministic scope keys**.

### Do not build an autonomous global prompt/rule optimizer

It is **unlikely (20-45%)** that autonomous global mutation is net-positive without a mature sealed evaluation portfolio. Prompt optimization can work, but distribution shift and benchmark overfit are established risks ([SPRIG](https://arxiv.org/abs/2410.14826), [Robust Prompt Optimization](https://arxiv.org/abs/2305.13954), [AI Agents That Matter](https://arxiv.org/abs/2407.01502)). Candidate generation may be added later as a bounded offline tool; promotion must stay external and reversible.

### Do not build a trained critic or rely on a single LLM judge

It is **very unlikely (5-20%)** that a trained critic is justified before executable outcomes and calibrated simple graders are exhausted. Anthropic recommends code-based outcome graders where possible and periodic human calibration of model judges; OpenAI notes that its experimental automated GDPval grader is not reliable enough to replace experts ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [OpenAI GDPval](https://openai.com/index/gdpval/)). This conclusion is **UNVERIFIED for subjective owner tasks; the settling experiment is grader agreement against blinded expert labels with error analysis by task class**.

### Do not buy observability SaaS to solve an evidence-model problem

It is **very unlikely (5-20%)** that external observability software is necessary for the first implementation. Anthropic explicitly notes that teams can begin with simple evaluation scripts and that eval quality depends primarily on tasks and graders, not the framework ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). This is **UNVERIFIED at future scale; the settling condition is demonstrated inability of local artifacts and existing hooks to retain/query the required provenance and trial results within acceptable operator time**.

## 7. Decision rules distilled from the research

1. **Never inherit efficacy by version number.** A new model may be globally stronger and locally worse; rerun the joint system ([longitudinal drift study](https://hdsr.mitpress.mit.edu/pub/y95zitmz/release/2), [OpenAI compatibility docs](https://developers.openai.com/api/reference/overview#backwards-compatibility)).
2. **Pin for stability; shadow for progress.** Stable identifiers preserve rollback, while an exploration channel prevents pinning from becoming stagnation ([Gemini models](https://ai.google.dev/gemini-api/docs/models)).
3. **Keep a minimal control forever.** It is the detector for scaffold decay ([mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent)).
4. **Promote outcomes, not persuasive reflections.** External validators outrank self-authored lessons ([Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Voyager](https://arxiv.org/abs/2305.16291)).
5. **Treat context as a scarce intervention surface.** More replay can hurt ([LifelongAgentBench](https://arxiv.org/abs/2505.11942)).
6. **Every rule has a scope, counterexample, retest trigger, and deletion criterion.** Prompt effects are distribution-dependent ([Robust Prompt Optimization](https://arxiv.org/abs/2305.13954)).
7. **Measure reliability and cost, not only best-case accuracy.** Multiple calls and complex scaffolds can buy headline scores ([AI Agents That Matter](https://arxiv.org/abs/2407.01502), [Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
8. **Spend architecture on reversibility.** Feature flags, provenance, holdouts, and rollback survive model churn better than permanent reasoning choreography; this is **very likely (80-90%)** based on the combined evidence above, while the exact optimal harness remains **UNVERIFIED; settle it through the proposed repeated model × scaffold experiments**.

## 8. What could not be determined (GAPS)

1. **Direct longitudinal owner-style evidence was not located.** Two independent signals bound this gap: targeted searches for longitudinal, cross-version agent-scaffold studies surfaced the historical endpoint-drift study but no repeated personal-harness experiment, while inspection of the methods and limitations in the reviewed scaffold/continual-learning papers showed fixed or bounded model/task settings rather than the same owner harness carried through several Claude, Codex/OpenAI, and Gemini generations. The search detector was demonstrably live because it located the known-present longitudinal endpoint study and the known-present cross-model SPRIG study ([longitudinal drift study](https://hdsr.mitpress.mit.edu/pub/y95zitmz/release/2), [SPRIG](https://arxiv.org/abs/2410.14826)). This is a bounded review result, not proof that no such experiment exists. Therefore, the claim that any specific scaffold survives future frontier-model changes is **UNVERIFIED; the settling experiment is the provenance-controlled longitudinal champion–challenger program described above**.

2. **The reviewed memory studies do not establish cross-model inheritance.** Method inspection is the first signal: Voyager, Reflexion, ExpeL, and LifelongAgentBench study experience reuse but do not report a complete closed-model replacement with old memory carried into the new model and a no-memory crossed control ([Voyager](https://arxiv.org/abs/2305.16291), [Reflexion](https://arxiv.org/abs/2303.11366), [ExpeL](https://arxiv.org/abs/2308.10144), [LifelongAgentBench](https://arxiv.org/abs/2505.11942)). Targeted cross-model-memory searches are the second signal: they surfaced prompt-transfer and continual-memory work, demonstrating detector sensitivity, but did not add that crossed inheritance experiment. This is a bounded review result, not a global absence proof. Cross-model memory inheritance remains **UNVERIFIED; settle it with the 2×2 old/new model × memory off/on design**.

3. **The reviewed literature does not supply a deployment-independent decomposition of model versus scaffold contribution.** Published agent scores often report combinations, and their tasks, budgets, tools, and prompts differ. The causal contribution of a component must be re-estimated per deployment ([AI Agents That Matter](https://arxiv.org/abs/2407.01502), [Anthropic eval guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

4. **The reviewed guidance does not supply a workload-independent evaluation cadence or sample size.** Providers recommend continual evals and multiple trials but do not supply a workload-independent frequency or power calculation. A quarterly review recommendation is therefore **UNVERIFIED; settle it from observed variance, change frequency, and acceptable detection delay**.

5. **Limited evidence for prompt transfer on long-horizon tool agents.** SPRIG’s broad cross-model system-prompt result is promising, but it does not settle transfer for long-horizon, state-changing owner workflows ([SPRIG](https://arxiv.org/abs/2410.14826)). Transfer of broad principles to this harness is **likely (55-80%)** on that evidence, but remains **UNVERIFIED; settle it with leave-one-model-family-out owner-task evaluation**.

6. **Production drift can arise above and below the model.** API aliases, client versions, hidden provider system layers, tool schemas, MCP servers, operating systems, and external web state can all change. Provider documentation exposes only some of these layers. Attribution to a hidden provider change is **UNVERIFIED unless the provenance envelope and independent environment/tool signals rule out known alternatives** ([OpenAI compatibility docs](https://developers.openai.com/api/reference/overview#backwards-compatibility), [Gemini API versions](https://ai.google.dev/gemini-api/docs/api-versions)).

7. **Generated eval validity for bespoke owner behavior is unsettled.** Bloom validates automated scenario generation for selected behavioral evaluations, not this owner’s entire workflow ([Bloom](https://www.anthropic.com/research/bloom)). Its utility here is **likely (55-80%)** for discovering test candidates but **UNVERIFIED for release gating; settle it with blinded human calibration**.

8. **Recent 2026 scaffold-interaction preprints exist but were not used as load-bearing evidence.** Several search results claim large cross-component interactions and model-dependent reversals, but very recent single-paper claims need replication. The report’s recommendations do not require those claims; they follow from older peer-reviewed work, official version semantics, strong evaluation guidance, and the directly inspectable minimal-agent repository.

## 9. Bottom line for the replacement-vs-evolution decision

The external evidence does not justify replacing the current harness with a larger continual-learning runtime. It does justify replacing any architecture philosophy that treats accumulated prompts, rules, agents, or memories as permanent assets. The better target is a **small invariant kernel plus an evidence-governed per-model profile**:

* invariant kernel: permissions, sandboxing, clean state, tool/result contracts, provenance, resource/stopping limits, outcome verification, event ledger, and rollback;
* per-model profile: exact model/API identity, only the prompts/tools/scaffolds that survive current ablations, and scoped verified procedural memory;
* adaptation loop: observe → reproduce → candidate → canary → development eval → sealed transfer eval → promote/quarantine → retest/delete on model change;
* permanent control: the smallest functional agent loop.

It is **very likely (80-90%)** that this architecture will age better than an ever-growing cognitive scaffold because every added component remains measurable and removable, and the durable work is concentrated in model-independent evidence and enforcement. The claim is forward-looking and **UNVERIFIED; the decisive experiment is to operate the proposed kernel through at least two model migrations and compare regression rate, migration time, cost, and retained scaffold count against the existing process**.

This passes the anti-overfit gate: it rides the existing configuration/hook/skill/tool buses; it adds only small stateless probes, metadata, gates, and artifact state transitions; and it explicitly rejects a second orchestration runtime, vector/KG memory, durable execution engine, trained critic, observability SaaS, and guardrail framework.
