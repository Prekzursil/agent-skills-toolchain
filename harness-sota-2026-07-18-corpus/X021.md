# X021 — Cross-domain borrow: intelligence tradecraft → shell-tool design

## Executive judgment

The borrow transfers, but only in a deliberately narrow form.

The useful mechanism is not “make the agent perform intelligence analysis before every command.” It is the combination of three separations that intelligence tradecraft already institutionalizes:

1. **Separate the reliability of a source from the credibility of a particular report.** The NATO/Admiralty grading system gives these independent axes; a historically unreliable source can report independently confirmed information, and a reliable source can make an improbable report.
2. **Compare competing explanations using diagnostic, especially inconsistent, evidence.** Analysis of Competing Hypotheses (ACH) asks which evidence distinguishes hypotheses and tries to reject explanations rather than merely accumulating support for the first plausible one.
3. **Separate likelihood from confidence and use a controlled probability vocabulary.** Sherman Kent’s problem was that ordinary probability words communicated radically different odds to different readers. Modern US Intelligence Community practice likewise distinguishes a likelihood judgment from confidence in the sources and reasoning behind it.

Translated to shell-tool design, this becomes a **dialect-aware execution envelope plus discriminating error packet**: identify the parser chain before execution; represent argument intent separately from shell source text; run cheap, deterministic checks for known parse contradictions; and, when execution still fails ambiguously, return ranked alternative failure explanations with the observation that supports or contradicts each one and the next probe that would distinguish them.

This is a **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** proposal, not a second orchestration runtime. It is **likely (55-80%)** to materially reduce the measured 1,631 unmatched-quote EOF failures because an unmatched delimiter is statically observable before process launch and because an explicit dialect prevents Bash and PowerShell escaping advice from being interchanged; the evidence is the POSIX/Bash grammar’s explicit delimiter rules, Microsoft’s distinct PowerShell parsing model, and the supplied corpus count. The exact reduction is **UNVERIFIED; the experiment that would settle it is a shadow-mode replay of the 1,631 fingerprinted failures plus a stratified sample of successful commands, followed by an online A/B test measuring prevented failures, false blocks, and retries per task**.

The full intelligence workflow does **not** transfer. Running a human-style ACH matrix on every command would add latency and ceremony to a mostly deterministic parsing problem. ACH belongs only in the ambiguous tail—where several parser layers or failure causes remain plausible—not in the common preflight path.

## What intelligence tradecraft solved in its own field

### 1. The Admiralty/NATO two-axis grade prevents source reputation from swallowing report evaluation

The UK Ministry of Defence’s current public joint doctrine says collected information must be evaluated for both **source reliability** and **information credibility**. Table 3.1 encodes source reliability A-F and report credibility 1-6. Crucially, the doctrine says the axes need not “match”: a usually reliable source can provide improbable information (`B5`), while an unreliable source can provide independently confirmed information (`E1`). `F6` means there is insufficient evidence to judge, not that the information is worthless. See JDP 2-00 §3.39-3.40 and Table 3.1: <https://assets.publishing.service.gov.uk/media/653a4b0780884d0013f71bb0/JDP_2_00_Ed_4_web.pdf>.

That solves a recurrent reasoning error in the source field: treating “who said it?” and “is this particular claim supported?” as one variable. The split preserves two facts that otherwise get collapsed. A source’s reporting history is prior evidence about the channel; corroboration, plausibility, and internal evidence concern this report. It also provides an honest “cannot be judged” state instead of forcing false precision.

ODNI’s analytic standards express the broader rule: analytic products must describe the quality and credibility of sources, data, and methodologies; explain uncertainty; distinguish information from assumptions and judgments; and incorporate alternatives. See ICD 203, especially Analytic Tradecraft Standards 1-4: <https://www.dni.gov/files/documents/ICD/ICD-203.pdf>. ODNI’s source-citation specification gives the operational purpose: citations improve traceability from collected information to analytic judgments and help readers assess the quality and scope of the supporting sources: <https://www.dni.gov/index.php/who-we-are/organizations/ic-cio/ic-technical-specifications/source-citations?tmpl=component>.

### 2. ACH prioritizes diagnostic contradiction over generic consistency

Heuer’s ACH starts by generating a set of hypotheses, laying hypotheses against evidence in a matrix, and judging whether each item is consistent or inconsistent with each hypothesis. The key is **diagnosticity**: evidence matters to the extent that it changes the relative plausibility of alternatives. A fever is consistent with many illnesses and therefore does little to identify which illness is present. The analyst should focus on evidence that is inconsistent with one or more hypotheses, provisionally select the hypothesis with the fewest serious inconsistencies, test sensitivity to the most diagnostic evidence, report conclusions with rejected alternatives, and identify future observations that could change the judgment. See Heuer, Chapter 8: <https://www.cia.gov/resources/csi/static/9a5f1162fd0932c29bfed1c030edf4ae/Pyschology-of-Intelligence-Analysis.pdf>.

The mechanism addresses confirmation bias and premature closure. “The evidence fits my explanation” is weak when it fits every explanation. “This observation is impossible under explanation B but expected under A” is much stronger. ACH also makes assumptions inspectable: disagreement can be located in a cell or an implicit hypothesis rather than hidden inside prose.

ACH is not a truth machine. Its output depends on whether the hypothesis set contains the real explanation, whether evidence is independent, and whether matrix judgments are sound. Heuer explicitly treats hypothesis generation and sensitivity analysis as necessary because omitted hypotheses or a single questionable item can determine the result. That limitation matters directly to the translation below.

### 3. Sherman-Kent vocabulary prevents false agreement about uncertainty

Kent documented a communication failure: analysts used the same estimative phrase while attaching very different odds to it. In one poll, interpretations of a “serious possibility” ranged from roughly 20% to roughly 80%. His remedy was a small, consistently used vocabulary tied to probability bands, while reserving “possible” for cases where an event was neither impossible nor certain but odds could not responsibly be assigned. See Kent, “Words of Estimative Probability”: <https://www.cia.gov/resources/csi/studies-in-intelligence/archives/vol-8-no-4/words-of-estimative-probability/>.

Modern IC exposition separates **likelihood** from **confidence**. Likelihood describes the assessed chance of an event; confidence reflects the quality, consistency, corroboration, assumptions, information gaps, and reasoning behind that assessment. A high-confidence judgment is still not a fact or certainty. A declassified ODNI assessment illustrates both scales and their definitions on page 10: <https://www.dni.gov/files/ODNI/documents/assessments/ICA-declass-16MAR21.pdf>.

The relevant achievement is not the exact historic cut points. It is the interface contract: the producer cannot silently use “likely” to mean “I have good evidence,” and the consumer cannot silently read “high confidence” as “nearly certain outcome.” Distinct concepts get distinct fields.

## Structural mapping to tool design

| Intelligence object | Tool-design counterpart | Why the mapping is structural rather than decorative |
|---|---|---|
| Source | Diagnostic channel: static parser, shell stderr, child-process exit, prior fingerprint, agent self-explanation | Channels have different track records and visibility into the failure. |
| Report | A particular observation: “delimiter unclosed at byte 184,” “argv[3] received as two arguments,” “child exited 2” | A normally reliable channel can produce a non-diagnostic observation in a particular case. |
| Competing hypothesis | Candidate failure mechanism: unclosed Bash quote, PowerShell escape used in Bash, outer-shell expansion, inner-shell parse, argument-boundary loss, tool-not-found | Multiple causes often produce superficially similar stderr or nonzero exits. |
| Diagnostic evidence | Observation whose expected value differs between candidate causes | It reduces retries by selecting a discriminating correction or probe. |
| Likelihood | Relative probability that a candidate failure mechanism caused this incident | This is about the incident. |
| Confidence | Strength and independence of the diagnostic evidence | This is about the basis for the ranking. |
| Intelligence gap / collection requirement | Minimal next probe, such as syntax-only parse or argv echo | It states what evidence is missing and how to obtain it. |
| Disseminated assessment | Structured error packet shown to the agent | The consumer needs traceable facts, alternatives, uncertainty, and action. |

The mapping is strongest where the tool currently emits a low-information symptom. For example, “unexpected EOF” is compatible with several root causes: the model emitted an unclosed quote; a wrapper truncated the command; the command contains a nested `bash -c` whose inner program is malformed; or one shell’s escaping was applied under another shell. Repeating the same command with another guessed backslash is confirmatory behavior. Asking which parser layer found the EOF, at what span, under which dialect, and whether a syntax-only parse reproduces it is diagnostic behavior.

The target domain also supplies hard distinctions. POSIX specifies that quote characters affect token recognition until matching quoted text ends, and that single quotes cannot contain a single quote; Bash documents its own single-, double-, escape-, and dollar-single-quote behavior. See POSIX §§2.1-2.2 and GNU Bash §3.1.2 at the URLs above. PowerShell instead tokenizes through expression and argument modes, uses the backtick as escape, and parses arguments before forwarding them to native commands; Microsoft also documents version-dependent native argument passing and the Windows-only `--%` stop-parsing token. See Microsoft `about_Parsing`: <https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5>. Therefore “quote correctly” is not one operation. Dialect and parser chain are first-class evidence.

## Concrete harness translation

### Proposal 1 — Typed execution envelope — UNVERIFIED efficacy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Change the shell tool’s request schema so raw command text is no longer the only semantic input. Require or infer, then echo back, an execution envelope:

```json
{
  "dialect": "bash | powershell | cmd | direct",
  "program": "git",
  "argv": ["show", "origin/main:path with spaces/file.md"],
  "shell_required": false,
  "source": null,
  "interpolation": "none | environment | shell",
  "working_directory": "...",
  "expected_effect": "read-only",
  "sensitive_fields": []
}
```

For pipelines, redirections, compound statements, or shell built-ins, `shell_required` is true and `source` carries dialect-specific text. Otherwise the executor invokes a program with an argument vector and does not ask a shell to reconstruct boundaries from a string.

This borrows the Admiralty separation: **command intent** (`program`, `argv`, effect) is not the same thing as one **serialization of that intent** (`source` under a named parser). A malformed serialization must not erase the intended argument boundaries. The response should show a redacted `argv_preview` so the agent can compare intended and received structure.

It is **very likely (80-90%)** that explicitly naming the dialect will prevent some cross-shell escaping mistakes because Bash and PowerShell have authoritatively different escaping and native-argument rules; the evidence is GNU Bash §3.1.2 and Microsoft `about_Parsing`. The magnitude is **UNVERIFIED; the settling experiment is to label a random sample of quoting failures by actual dialect-confusion cause, then replay them through the proposed schema and compare first-attempt success**.

It is **likely (55-80%)** that direct `program`+`argv` execution will remove a substantial class of argument-boundary and interpolation errors for commands that do not need shell syntax because an argv API bypasses shell tokenization; the evidence is POSIX’s documented tokenize/parse/expand stages and PowerShell’s documented additional native-command argument handling. This is **UNVERIFIED; the settling experiment is to classify corpus commands for genuine shell-feature use, replay the no-shell subset through direct execution, and compare outputs and side effects against the originals**.

Compatibility rule: keep raw `source` available. Making `argv` mandatory for pipelines would falsely pretend that a pipeline is a single executable invocation. The schema should discriminate, not flatten.

### Proposal 2 — Dialect-aware contradiction preflight — UNVERIFIED efficacy

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a pre-tool hook that performs only cheap, high-specificity checks:

1. Validate the declared dialect against the actual executor.
2. For Bash/POSIX source, use the installed shell’s syntax-only mode where available and report the first parser span; supplement it with a delimiter-state scanner only to improve location/explanation, not to overrule the real parser.
3. For PowerShell source, use PowerShell’s parser API to collect parse errors without executing the script.
4. Reject only definite contradictions: unclosed delimiter, impossible escape for the declared dialect, missing here-document terminator, or schema inconsistency such as `shell_required:false` plus a pipeline operator in `source`.
5. Warn rather than block on contextual risks such as possible unwanted expansion, nested parser boundaries, or ambiguous native-argument forwarding.

The intelligence borrow is negative evidence: an unclosed quote is not merely “consistent with a future EOF”; it is a direct contradiction of the hypothesis “this source is syntactically complete.” This avoids an elaborate scoring system in the deterministic case.

It is **almost certain (90-99%)** that a dialect-correct syntax-only parser can detect syntactically unclosed quotes before execution when it receives the same complete source text the executor would receive; the evidence is the formal quote rules in POSIX §2.2 and Bash §3.1.2. The residual uncertainty covers wrapper truncation after preflight, dynamically generated source, parser-version mismatch, and nested commands not inspected. Whether the harness preflight sees exactly the executor’s bytes is **UNVERIFIED; the settling experiment is to hash the redacted byte stream at preflight and at the executor boundary during a shadow run and compare hashes without logging secrets**.

It is **very likely (80-90%)** that warning rather than blocking on non-syntax risks will have fewer false positives than a blanket “dangerous metacharacter” denylist because the official grammars make many metacharacters legitimate in context; the evidence is POSIX §2.2’s context-sensitive quoting rules and PowerShell’s expression/argument modes. The operational false-positive rate is **UNVERIFIED; the settling experiment is shadow-mode evaluation on at least a stratified week of successful commands, with review of every would-block and a sample of would-warn cases**.

### Proposal 3 — Competing-diagnosis error packet — UNVERIFIED efficacy

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace generic shell-failure prose with a stable, machine-readable response that separates observation, hypothesis, likelihood, and confidence:

```json
{
  "observed": [
    {"channel":"bash-parser", "reliability":"direct", "fact":"unclosed single quote", "span":[184,184]},
    {"channel":"child-process", "reliability":"not_observed", "fact":"not launched"}
  ],
  "diagnoses": [
    {
      "cause":"outer Bash source is incomplete",
      "likelihood":"almost certain (90-99%)",
      "confidence":"high",
      "supports":["syntax-only parser reproduced at byte 184"],
      "contradicts":[],
      "repair":"close or restructure the quote at the reported span"
    },
    {
      "cause":"child program rejected an argument",
      "likelihood":"almost certainly not (1-5%)",
      "confidence":"high",
      "supports":[],
      "contradicts":["child was not launched"]
    }
  ],
  "next_discriminator":null,
  "raw_stderr":"...",
  "retry_same_command":false
}
```

For ambiguous failures, populate two to four candidates from a small taxonomy and name one minimal next discriminator. Examples:

- Run syntax-only parsing on the outer source. If it fails, “child rejected argv” loses plausibility.
- If syntax passes but the child reports an unexpected operand count, use a safe argv-echo shim or tool-native dry run to inspect boundaries.
- If a nested `bash -c`, `pwsh -Command`, `cmd /c`, or remote shell exists, label the parser layers and locate which layer produced stderr.
- If the executable was never resolved, do not recommend quote changes.

This applies the Admiralty distinction at error time. The static parser has strong direct access to syntax but no access to the child program’s semantic expectations. The child’s stderr has direct access to its own rejection but may be a poor guide to how an outer shell transformed arguments. An agent-generated self-explanation has no independent evidentiary value unless tied to a parser span, exit phase, or observed argv. A reliable channel in general can still provide weakly diagnostic evidence in one incident.

The packet also applies the Sherman-Kent distinction: `likelihood` ranks the candidate cause; `confidence` describes the quality and independence of the evidence behind that rank. The exact mandatory confidence vocabulary in this unit can be used for likelihood, while confidence may be an explicit evidence grade (`high/moderate/low`) provided its meaning is documented. Do not turn an exit code into a pseudo-probability.

It is **likely (55-80%)** that showing contradictions and a next discriminator will reduce blind same-command retries because ACH’s structure directs attention to evidence that differs across causes rather than evidence compatible with all causes; the evidence is Heuer Chapter 8’s diagnosticity method. This behavioral transfer is **UNVERIFIED; the settling experiment is an A/B trial comparing same-fingerprint retry loops, tool calls to resolution, and task success between legacy stderr and the structured packet, with identical underlying failures**.

### Proposal 4 — Evidence-calibrated fingerprint registry, not a universal critic — UNVERIFIED efficacy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Maintain a small registry for recurring shell failure fingerprints. Each entry records:

- dialect and parser layer;
- matched observation, with capture fields;
- candidate causes and known contradictions;
- historical precision and sample count;
- whether the cause was parser-confirmed, child-confirmed, or only inferred;
- safe next discriminator;
- last validation date and applicable shell versions.

Historical precision is the counterpart of source reliability; the current incident’s direct observations are the counterpart of report credibility. A fingerprint with 98% historic precision may still be contradicted by “child never launched” or a different dialect. Conversely, a new fingerprint with no history is “cannot be judged,” not “bad.”

Do not automatically learn executable repairs from unreviewed agent retries. A retry that later succeeds can differ in several dimensions and is not independent proof of which change mattered. Promote a fingerprint only when a parser result, observed argv, execution phase, or controlled replay discriminates the cause.

It is **likely (55-80%)** that tracking per-fingerprint precision will prevent stale or overgeneralized error advice from being presented as fact because applicability and historical performance become explicit fields; the evidence is the Admiralty system’s independent source/report evaluation and ODNI’s traceability requirements. The practical benefit is **UNVERIFIED; the settling experiment is a retrospective calibration study comparing predicted causes to independently labeled causes across held-out fingerprints, followed by monitoring precision drift by shell version**.

## What this would catch that a raw shell interface misses

The following are design predictions, not claims about current repository behavior:

1. **Unclosed delimiters before launch.** **Almost certain (90-99%)** for static source under the declared matching dialect, because the actual parser can reject incomplete syntax without executing it; evidence: POSIX §2.2 and GNU Bash §3.1.2. Dynamic or post-hook truncation remains outside this guarantee.
2. **Wrong-dialect escape advice.** **Very likely (80-90%)** when a command declares Bash but contains a repair pattern specific to PowerShell, or vice versa, because the grammars and escape characters differ; evidence: GNU Bash §3.1.2 and Microsoft `about_Parsing`. Exact detection coverage is **UNVERIFIED; settle it with a labeled mutation suite containing cross-dialect escape substitutions**.
3. **Outer-parser versus inner-parser failure.** **Likely (55-80%)** when nested invocations are explicitly represented as parser layers and stderr/phase is attached to a layer; evidence: both POSIX and PowerShell document parsing before command invocation. Coverage is **UNVERIFIED; settle it with a conformance suite crossing Bash, PowerShell, `cmd`, and representative native programs with controlled failures at each layer**.
4. **Argument-boundary loss despite syntactically valid source.** **Likely (55-80%)** for direct-execution candidates because intended `argv` can be compared with an argv echo or tool-native dry run; evidence: Microsoft documents that PowerShell parses and forwards native arguments and that behavior changed in PowerShell 7.3. Whether safe introspection exists for each executable is **UNVERIFIED; settle it by inventorying supported dry-run/echo strategies and replaying space, quote, empty-string, trailing-backslash, and Unicode cases**.
5. **Misleading repair after a pre-launch failure.** **Very likely (80-90%)** if the executor records whether resolution, parsing, spawn, or child execution was reached: a child-semantic explanation is contradicted when no child started. Evidence is causal phase ordering in POSIX’s overview (tokenize, parse, execute) and Microsoft’s PowerShell parse-then-forward description.
6. **Low-information retry loops.** **Likely (55-80%)** when the response sets `retry_same_command:false` and provides a discriminating probe, because the next action gains information rather than repeating an unchanged experiment; evidence: ACH’s emphasis on diagnostic evidence. Actual agent compliance is **UNVERIFIED; settle it with the A/B retry-loop experiment specified above**.

## Adversarial analysis: where the analogy breaks

### Disanalogy 1: intelligence targets are epistemically open; parsers are mostly deterministic

An intelligence analyst often cannot query the target directly, observations may be deceptive, and ground truth may arrive years later or never. A shell grammar is specified and an installed parser can often answer the syntax question immediately. Therefore a full ACH matrix is wasteful for obvious syntax errors. The correct target-side move is deterministic parsing first, alternatives only after deterministic evidence is exhausted.

This is why Proposal 2 blocks only direct contradictions. “Unclosed quote at byte 184” should not be diluted into six equally formatted hypotheses. The analogy transfers at the boundary between multiple diagnostic channels, not at the level of pretending all errors are uncertain geopolitical estimates.

### Disanalogy 2: source intent and tool observation are not adversarial in the same way

Human sources can lie, lack access, or pass deliberate deception. Shell stderr is usually produced mechanically. Calling a parser “usually reliable” must not anthropomorphize it. Its limitations are scope and observability: the Bash parser is authoritative about Bash syntax under its version, but it cannot judge a child program’s semantics or source text it never received.

The transferable abstraction is independent axes and provenance, not spy-style suspicion. The registry should record parser version, layer, bytes observed, and historical precision—not vague trust scores.

### Disanalogy 3: ACH’s hypothesis completeness requirement is dangerous in an open tool ecosystem

No small taxonomy can enumerate every executable’s failure modes. If the harness ranks only known causes, it may confidently choose the least inconsistent wrong answer because the real cause is absent. Every packet therefore needs `unknown_or_other` when direct evidence does not settle the cause, and confidence must fall when the candidate set is incomplete.

It is **very likely (80-90%)** that an explicit unknown bucket will be necessary in real use because arbitrary native programs have unbounded domain-specific error semantics; the evidence is the target interface’s ability to invoke programs beyond the shell grammar and ACH’s dependence on adequate hypothesis generation. The appropriate unknown rate is **UNVERIFIED; settle it by holding out entire executable families during evaluation and measuring forced misclassification with and without the unknown bucket**.

### Disanalogy 4: intelligence confidence bands are not measured classifier calibration

Sherman-Kent language improves communication, but attaching `80-90%` to a diagnosis does not make it calibrated. Initially, deterministic diagnoses should use rule-derived language with an evidence explanation; probabilistic labels on ambiguous fingerprints should be withheld until held-out outcomes support calibration. A raw frequency from correlated retries is not independent evidence.

Thus the example’s “almost certain” is justified by a direct syntax-parser contradiction and documented scope, not by an invented model score. Where no defensible percentage exists, return `likelihood: unquantified` plus confidence and the next discriminator. The owner’s mandatory bands govern claims in this artifact; they should not force fabricated runtime probabilities.

### Disanalogy 5: human analytic ceremony can become interface noise

An analyst may spend hours building ACH. A tool error must help an agent recover in seconds. A many-row matrix, source-grade codes, and long prose on every failure would consume context and encourage the agent to reason about the diagnostic system instead of the task. The runtime packet should expose at most two to four alternatives, one decisive contradiction per rejected cause, and one next probe. Full trace detail can remain behind a debug field.

It is **likely (55-80%)** that a compact default packet will outperform a full matrix in task completion because tool consumers have finite context and most parser failures are locally decidable; the evidence is the deterministic grammar and the narrow information needed to discriminate the listed causes. This interface claim is **UNVERIFIED; settle it with a factorial evaluation varying packet length and alternative count while measuring resolution rate, tokens, and tool calls**.

## Anti-overfit gate

All four proposals ride the existing tool schema and pre/post execution hook bus. They require no second orchestration runtime, vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The fingerprint registry is a small versioned JSON/table, not “memory infrastructure.” The diagnostic logic is rules plus native parsers, not a learned evaluator.

The minimal architecture is deliberate:

```text
request schema
    → identify dialect / direct argv
    → native syntax-only parser (when shell source exists)
    → execute once
    → attach phase + observed argv/stderr
    → small fingerprint matcher
    → compact alternatives + discriminator
```

No proposal here reintroduces a previously rejected component. A BUILD-LARGE service is not justified: parsing occurs at the execution boundary, the state needed for calibration is small, and the useful feedback must be synchronous with the existing tool call.

## Evaluation plan and stop/go gates

### Phase A: offline replay

Build a frozen test set from the 1,631 supplied unmatched-quote fingerprints, deduplicated by normalized structure but retaining shell, wrapper, command length, and nesting. Add three independent controls:

- successful commands with heavy legitimate quoting;
- synthetic mutations covering one error at a time;
- held-out executable families to test the unknown bucket.

Two mechanically independent correctness signals are required for each labeled case before declaring the diagnosis correct: for example, native syntax-parser location plus controlled repair/replay; or observed argv plus the child program’s documented expected arguments. Two regexes over the same stderr do not qualify.

Metrics: definite-error recall, false-block rate, warning rate, diagnostic top-1 accuracy, unknown recall, calibration by band, and whether the proposed repair preserves intended argv/effect. Also record added latency and response tokens.

### Phase B: shadow deployment

Run the preflight and diagnosis without blocking or changing execution. Verify detector health with known-present controls in every shell/version cohort. Compare the bytes/dialect seen by preflight with the executor boundary using secret-safe hashes. Sample successful invocations, not only failures, to estimate false positives.

Promotion gate: block only categories with two independent signals and a reviewed near-zero false-block rate. The exact acceptable threshold is **UNVERIFIED; the experiment that settles it is owner selection based on the cost ratio between an extra agent turn and blocking a valid command**. Until that choice is made, warnings are safer than blocks for anything short of native-parser rejection.

### Phase C: randomized error-interface trial

Randomize eligible failures to legacy stderr versus the compact structured packet while keeping executor behavior identical. Primary outcomes: same-command retries, calls-to-resolution, task completion, and newly introduced command damage. Secondary outcomes: tokens and latency. Stratify by dialect, nesting, and whether the child launched.

The proposal earns permanent adoption only if it reduces recovery cost without increasing false blocks or destructive corrections. It is **roughly even (45-55%)** whether the ACH-style alternatives add value beyond the typed envelope plus native parser for simple unmatched-quote cases, because deterministic preflight may already solve most of that narrow class; the evidence is the direct observability of unmatched delimiters versus ACH’s benefit primarily under ambiguity. The randomized trial isolates that incremental value.

## Alternatives considered and rejected

### “Teach the model a longer shell-quoting rulebook” — rejected as the primary control

Documentation is useful, but the shell versions and parser chains remain contextual, and the model can still emit a malformed string. A native parser at the boundary observes the actual source and is causally closer to execution. Prompt guidance may supplement, not replace, the preflight.

### “Wrap every command in a universal escaping function” — rejected

There is no universal escaping transform across Bash, PowerShell, `cmd`, nested `-c`/`-Command` programs, and arbitrary native argument parsers. GNU and Microsoft’s official documentation demonstrate materially different rules. Such a wrapper would erase the parser-chain distinction that the design needs to preserve.

### “Run full ACH for every tool failure” — rejected

This forces an intelligence workflow onto deterministic syntax, adds latency/context, and risks false sophistication. Use native contradiction first; use a tiny alternatives structure only for the ambiguous remainder.

### “Train a critic on the 1,631 failures” — rejected

This violates the anti-overfit gate’s trained-critic exclusion and is unnecessary for formal delimiter errors. It would also risk learning correlated retry artifacts rather than causal parser rules. Native grammars and a small held-out-calibrated registry are simpler and more inspectable.

### “Adopt the A1-F6 codes verbatim in user-facing errors” — rejected

The two-axis concept transfers; the military shorthand does not. `B5` would require training, obscure which axis concerns channel scope versus incident evidence, and add ceremony. Use descriptive fields (`channel`, `observation`, `likelihood`, `confidence`, `contradicts`) and keep any numeric calibration in debug telemetry.

## Final recommendation — UNVERIFIED end-to-end efficacy

Adopt the narrow borrow in this order:

1. **CONFIG (settings/JSON only):** add explicit dialect, direct `program`+`argv`, shell-required, and interpolation fields while preserving raw source for genuine shell constructs.
