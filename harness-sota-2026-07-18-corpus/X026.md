# X026 — Aviation safety → use-versus-mention guards

## Executive judgment

The aviation analogy transfers, but only in a narrow and useful form: **transfer the clearance/checklist protocol, not aviation phraseology and not a generic “human factors” metaphor**.

Aviation does not make a safety-relevant utterance actionable merely because it contains words associated with an action. An air traffic clearance has an authorized source, an addressed aircraft, operational content, a phase in a transaction, an acknowledgement/readback, and a controller hearback. Likewise, a challenge–response checklist has an assigned initiator, an explicit cue that starts checklist mode, a responding crewmember, and verification of aircraft state. FAA Order JO 7110.65 requires controllers to ensure acknowledgement of clearances and instructions, check readbacks for correctness, and ensure that the aircraft call sign appears in an acknowledging readback; its note states that until acknowledgement, the controller cannot know whether the pilot will comply or remain on the prior clearance ([FAA JO 7110.65 §2-4-3](https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap2_section_4.html)). FAA AC 120-71B assigns the cue for initiating a normal checklist to a particular pilot and describes a challenge–response sequence in which the other pilot verifies that the item has actually been done before responding ([FAA AC 120-71B, §5.1.4](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-71B.pdf)). NASA’s checklist study calls the method more precisely “challenge-verification-response”: one pilot calls the item, both verify the aircraft configuration, and the other reports the verified status ([NASA CR-177549, pp. 18–19](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)).

The concrete harness translation is a **role-addressed action envelope**. A guard should primarily match a typed control-plane event—who/what requested which operation against which object, at what lifecycle phase—not scan arbitrary user, document, or tool-result text for an action-shaped string. For the small set of high-consequence actions, add a normalized readback and a permit bound to the exact structured arguments. Descriptive text remains cargo even when it contains a verbatim example of the forbidden operation.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The proposal is a thin event normalizer plus guard adapter on the existing hook bus, not a second orchestrator, policy daemon, classifier service, or new memory system. It passes the anti-overfit gate: it adds a stable boundary invariant and a small deterministic state transition, not elaborate scaffolding that competes with the agent.

My outcome forecast is **very likely (80-90%)**, based on the close structural match between (a) aviation’s need to distinguish addressed operational instructions from other speech on a shared channel and (b) the target defect’s need to distinguish executable control events from text that mentions them. The forecast is not “almost certain” because flight communications operate in a constrained, trained, standardized environment whereas agent payloads contain arbitrary prose, code, quoted transcripts, adversarial instructions, and nested serialization.

## 1. What aviation has actually solved

### 1.1 Clearance is a transaction, not a substring

The FAA Pilot/Controller Glossary defines an air traffic clearance as an authorization from ATC for a particular aircraft to proceed under specified traffic conditions. It separately defines ATC instructions as directives requiring a pilot to take specific actions ([FAA Pilot/Controller Glossary, “Air Traffic Clearance” and “ATC Instructions”](https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/glossary-a.html)). This distinction matters: information, a request, a clearance, and an instruction can discuss the same runway, altitude, or heading but do not have the same operational force.

The communications protocol supplies several independent discriminators:

1. **Authority/source.** A clearance is issued by an ATC unit, not made actionable by any speaker uttering clearance-like words.
2. **Address/addressee.** The FAA states that pilots should acknowledge each ATC communication with the appropriate aircraft call sign ([FAA AIP, Radio Communications Phraseology and Techniques §4-2](https://www.faa.gov/air_traffic/publications/atpubs/aip_html/chap4_section_2.html)). JO 7110.65 likewise requires a call sign or registration number in a readback acknowledging a clearance or instruction.
3. **Speech-act type.** The system distinguishes authorization, directive, request, advisory information, acknowledgement, and readback. “Stand by,” for example, is explicitly neither approval nor denial ([FAA Pilot/Controller Glossary, “Stand By”](https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/glossary-s.html)).
4. **Lifecycle.** Issue, acknowledgement/readback, correction if necessary, and execution are distinguishable phases. The FAA’s historical readback/hearback awareness order describes the safety purpose as detecting and correcting erroneous readbacks, and calls for records containing the clearance, readback, correction, and acknowledgement ([FAA Order SW 7210.24](https://www.faa.gov/documentLibrary/media/Order/sw7210.24.pdf)).
5. **Scope and validity.** Clearances have conditions and limits. The glossary defines a clearance limit and a clearance-void time; authority can expire rather than remaining latent forever ([FAA Pilot/Controller Glossary, “Clearance Limit” and “Clearance Void Time”](https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/glossary-c.html)).

This does not eliminate communication errors. It makes the intended act mechanically distinguishable from background discourse and creates places where a mismatch can be detected. That is precisely the useful property for use-versus-mention.

### 1.2 Challenge–verification–response checks state, not fluent recital

The normal-checklist mechanism adds a second lesson. NASA CR-177549 distinguishes:

- **Challenge-verification-response:** configure first, then use the checklist to verify critical items; one pilot calls the item, both verify configuration, and the other calls the verified status.
- **Call-do-response:** the checklist directs configuration step by step; after setting the item, the actor announces the new status.

The report warns that in the latter method a mistake can pass unnoticed after an interruption because configuration redundancy is removed ([NASA CR-177549, pp. 18–19](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). AC 120-71B adds that checklist initiation has a role-assigned cue such as “before start checklist”; only then does the other pilot retrieve it and the crew enter the challenge–response activity ([FAA AC 120-71B, §5.1.4](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-71B.pdf)).

The central safety invariant is therefore not “the expected words appeared.” It is:

> the authorized role initiated the applicable procedure at the applicable phase, the challenged party inspected or changed the relevant system, and the response reports verified state.

A crew can recite a checklist item in a training discussion without operating the aircraft because the discussion is not an initiated operational checklist, and a correct verbal response is unsafe if the physical configuration was not verified. Aviation’s solution is contextual role plus state verification.

### 1.3 Mode awareness addresses the adjacent automation-surprise failure

Automation research names lack of mode awareness—the current and future status and behavior of automation—as a major source of automation surprise ([Wiener-era Airbus A320 operational study, NASA NTRS 20040112190](https://ntrs.nasa.gov/citations/20040112190)). Current FAA flightpath-management guidance includes explicit considerations for autoflight mode awareness and calls for policies, procedures, and training covering automated systems and pilot monitoring ([FAA AC 120-123](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_120-123.pdf); [FAA document page](https://www.faa.gov/regulations_policies/advisory_circulars/index.cfm/go/document.information/documentID/1041433)).

For the target defect, a detector that silently treats document text as an operational event is in the wrong mode: it has confused “cargo inspection” with “control authorization.” Explicit detector mode and transition reason are therefore not cosmetic observability. They allow the agent and operator to see whether a guard is evaluating a tool invocation, a proposed invocation, a quoted example, or a result.

## 2. Concrete harness design

### Proposal A — role-addressed action envelope

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Normalize safety-relevant hook inputs to an envelope resembling:

```json
{
  "event_id": "...",
  "origin_role": "assistant",
  "channel_role": "control",
  "addressee": "tool:Bash",
  "speech_act": "invoke",
  "phase": "proposed",
  "operation": "process.exec",
  "arguments": {"command": "...", "cwd": "..."},
  "provenance": {"hook_event": "PreToolUse", "tool_call_id": "..."}
}
```

The exact field names are illustrative. The invariant is not:

```text
if payload contains risky_pattern: block
```

It is:

```text
if channel_role == control
   and speech_act == invoke
   and phase == proposed
   and operation is governed:
       inspect the typed operation and its typed arguments
else:
       do not interpret cargo text as an attempted operation
```

Documents, examples, pasted logs, tool results, and postmortems enter as `channel_role: cargo` or lifecycle phases such as `observed_result`. A document can be inspected for threats, but that is a different detector with a different outcome; it cannot masquerade as an invocation guard.

The envelope must be constructed from trusted runtime metadata already delivered to the hook, not inferred by an LLM from the text. If a hook point lacks trusted role/event metadata, the guard should report `not_applicable: untrusted_event_role` rather than guess intent from payload vocabulary.

This design is **very likely (80-90%)** to eliminate the described class of mention-only false fires when the five detectors receive reliable hook event and tool identity metadata. Evidence is the direct structural exclusion: cargo events do not reach invocation predicates, just as unaddressed informational speech does not itself complete an ATC clearance transaction. **UNVERIFIED — settle with a replay experiment:** run all 12+ known false-fire fixtures and matched true-positive tool-call fixtures through the adapter; require zero mention-only blocks and no loss of known true positives before rollout.

It is **likely (55-80%)** to catch some cases the current lexical guards miss: indirect or novel textual forms that nevertheless resolve to the same structured operation, wrong tool/addressee, checks applied at the wrong lifecycle phase, and results that are accidentally reinterpreted as new requests. Evidence is that the decision key moves from incidental spelling to stable runtime operation/phase fields. **UNVERIFIED — settle with a mutation test:** paraphrase, encode, split, and nest the risky command while preserving the same tool invocation, then mutate the same strings into documents and results; compare recall and false-positive rate with the five current detectors.

### Proposal B — normalized readback and argument-bound permit for high-consequence actions

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For only the highest-consequence actions, the guard should produce a canonical “readback” derived from typed arguments:

```text
operation=filesystem.delete
target=/resolved/absolute/path
recursive=true
scope_count=137
authority=user_request:event-123
```

A separate deterministic verifier compares the canonical form against policy and explicit authority. Approval produces a short-lived permit bound to `(event_id, operation, canonical_argument_hash, expiry)`. Execution accepts only the matching permit. Any changed target, widened recursion, different addressee/tool, or stale event requires a new check.

This copies the useful logic of readback/hearback: the receiver returns its understood instruction, the issuer/verifier checks it, and mismatches are corrected before action. It also copies clearance limits and expiry. It does **not** ask a model to repeat arbitrary prose and call that confirmation.

The mechanism is **likely (55-80%)** to catch parameter substitution between authorization and execution, stale approvals reused on a new action, and a guard approving a human-readable summary that differs from actual tool arguments. Evidence is the cryptographic binding of permission to normalized executable parameters and aviation’s independent readback/hearback stage. **UNVERIFIED — settle with a time-of-check/time-of-use fault-injection test:** approve an action, mutate one parameter at a time before execution, and verify rejection; also test canonicalization collisions, path aliases, case behavior, symlinks, and platform-specific quoting.

Apply this only to a small risk tier. Requiring a two-phase permit for every read, search, or harmless write would reproduce checklist overload and add fragile ceremony. The anti-overfit gate therefore rejects a universal transaction manager.

### Proposal C — explicit detector mode annunciation and reason codes

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)** if existing hook results already accept structured metadata; otherwise **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for a small result wrapper. The implementation must choose one value after checking the native result schema; this ideation unit intentionally does not inspect the local harness.

Every guard decision should expose at least:

```json
{
  "detector": "destructive-action",
  "mode": "control.invoke.proposed",
  "decision": "block",
  "reason_code": "target_scope_too_broad",
  "evidence_fields": ["operation", "arguments.target", "arguments.recursive"]
}
```

For a mention-only event it should return, if logging is warranted:

```json
{
  "mode": "cargo.document",
  "decision": "not_applicable",
  "reason_code": "non_control_role"
}
```

Visible mode is the automation-surprise control: it exposes what the detector believes is happening now and why. It is **likely (55-80%)** to shorten diagnosis of residual false fires and mode confusion, based on aviation research identifying current/future automation status as the missing information in mode-awareness failures. **UNVERIFIED — settle with an operator study:** seed role-confusion failures with and without the mode field, then compare correct root-cause identification and time-to-diagnosis.

### Proposal D — non-punitive false-fire capture, deliberately secondary

**NATIVE-vs-BUILD: CONFIG (settings/JSON only)** if existing logs can accept `false_fire`, expected role, detector, and reason fields. Do not build a reporting service.

NASA’s Aviation Safety Reporting System is voluntary, confidential, and non-punitive; NASA de-identifies reports, and qualifying reports receive limited protection from FAA enforcement ([NASA ASRS confidentiality and incentives](https://asrs.arc.nasa.gov/overview/confidentiality.html); [FAA AC 00-46F / ASRS immunity policy](https://asrs.arc.nasa.gov/overview/immunity.html)). Its design encourages reporting of close calls and system contributors rather than suppressing evidence through fear of punishment.

The transferable fragment is a one-action “wrong mode / false fire” annotation that preserves the triggering event envelope and expected semantic role for later fixture generation. For a single-owner harness, confidentiality and legal immunity mostly do not transfer; the value is blameless capture of weak signals and near misses. This proposal does not fix use-versus-mention and must not be sold as doing so.

It is **roughly even (45-55%)** that an annotation control would yield enough additional high-quality examples to justify even its small maintenance cost, because the corpus already contains owner corrections and automated event data. Evidence for the upside is ASRS’s explicit reliance on free information flow to identify system deficiencies; evidence against is the much smaller social and organizational barrier in a personal harness. **UNVERIFIED — settle with a four-week A/B trial:** measure annotation usage, unique new fingerprints, time to convert reports into regression fixtures, and repeat-failure reduction. If reports merely duplicate existing logs, remove the control.

## 3. What this catches—and what it intentionally does not

### Expected catches

Subject to the replay and mutation experiments above, the design targets:

- A document that says “never run `rm -rf …`” triggering the destructive-action guard merely because the example contains the command.
- A postmortem containing a credential-like or exfiltration-like example triggering a live egress guard.
- Tool output echoing dangerous syntax being treated as a new action request.
- A quoted user/assistant transcript containing action language being mistaken for the current assistant’s proposed action.
- An encoded, paraphrased, or constructed operation evading a keyword detector even though the runtime tool and typed arguments reveal the governed action.
- Approval for target A being applied to target B, or an old approval being replayed after its event expires.
- A detector inspecting the wrong lifecycle phase, such as blocking an already-completed result as if it were a pre-action proposal.

The first four are **very likely (80-90%)** to be prevented once role metadata is trustworthy, because the adapter rejects the entire non-control class before examining action predicates. **UNVERIFIED — settle with the known false-fire replay suite plus newly generated quoted/nested fixtures.** The latter three are **likely (55-80%)**, because success depends on complete event normalization and robust argument canonicalization. **UNVERIFIED — settle with property-based event mutations and time-of-check/time-of-use injection.**

### Explicit non-goals

This design does not determine whether arbitrary document content is malicious, whether an instruction inside retrieved content is prompt injection, or whether a seemingly benign tool call has a dangerous emergent effect. Those are separate policies. Role gating answers “is this event an operational use or cargo that mentions a use?” It must not become a universal semantic safety classifier.

It also does not make every operational call safe. An addressed, correctly read-back clearance can still be unsafe, and a control-plane tool invocation can still be harmful. Existing action-specific guards remain necessary; they simply operate on the correct semantic object.

## 4. Adversarial analysis of the analogy

### Where the structures genuinely match

The transfer is **very likely (80-90%)** to be structurally valid at the transaction boundary. Evidence:

- Both domains multiplex operational and non-operational information through communication channels.
- Both need to bind authority to a source, a recipient, an action, and a time/phase.
- Both suffer if an observer confuses a representation of an action with the action transaction itself.
- Both have a second, more reliable object to inspect: aircraft/system state in aviation; typed runtime event and arguments in the harness.
- Both benefit from an explicit acknowledgement that exposes how the receiver interpreted the instruction.

The claim stops there. Aviation has not “solved” philosophical use-versus-mention for arbitrary language. It has engineered constrained protocols that avoid needing to solve it in safety-critical paths.

### Where it fails if copied literally

1. **Controlled language versus arbitrary content.** Aviation phraseology is standardized and participants are trained. Agent payloads can contain any natural language, programming language, quoting layer, encoding, or adversarial instruction. A larger keyword list modeled on standard phraseology would fail.
2. **Human shared world versus software metadata.** Pilots and controllers use situational awareness, physical state, and institutional roles. A hook sees only the fields delivered to it. If origin/role metadata is untrusted or absent, assigning a role from prose recreates the defect one layer lower.
3. **Readback is not proof.** A receiver can faithfully repeat an instruction and still misunderstand or execute it incorrectly. Readback/hearback errors remain a recognized aviation hazard; FAA’s program exists precisely because erroneous readbacks can go undetected ([FAA Order SW 7210.24](https://www.faa.gov/documentLibrary/media/Order/sw7210.24.pdf)). Hence the harness permit must derive from and bind to actual typed arguments, not a generated verbal summary.
4. **Call signs are not security principals.** Radio call signs identify conversational addressees but are not cryptographic authentication. Harness provenance and permits require trusted runtime identifiers and hashes. Copying only a textual `tool:Bash` label would be security theater.
5. **Checklist ceremony can overload.** Aviation literature itself notes interruption and checklist-method tradeoffs ([NASA CR-177549](https://www.faa.gov/sites/faa.gov/files/2022-11/NASA%20Ames%20Rpt%20CR%20177549%20.pdf)). Requiring challenge–response for every tool call would slow the agent, habituate bypasses, and violate the minimal-architecture constraint.
6. **The cost model differs.** Aviation optimizes rare catastrophic outcomes with trained crews and regulated procedures. Agent harnesses also face high-volume low-risk calls, latency costs, and rapidly improving models. Risk tiering is mandatory.

### Rejected borrows

- **Sterile-cockpit-style suppression of documents while guards run:** rejected. It would avoid false fires by hiding evidence and would make tools less composable.
- **An LLM “controller” that classifies every utterance as use or mention:** rejected. This is a second semantic authority, adds nondeterminism, and approaches the previously rejected second orchestration/guardrail runtime.
- **Full incident-reporting platform modeled on ASRS:** rejected. Confidentiality and cross-organization reporting incentives do not justify a daemon or service in a personal harness.
- **Universal two-person/challenge confirmation:** rejected. It transfers aviation staffing assumptions that do not exist here and adds ritual rather than independent evidence.
- **A new policy DSL for clearance grammar:** rejected. Typed hook events and existing configuration are enough; a new language increases surface area and overfits the current detector set.

## 5. Minimal experiment and acceptance plan

No performance claim above should graduate from forecast to fact without the following mechanically checkable experiment:

1. Build a fixture matrix with each of the five affected detectors crossed against semantic roles: live proposed invocation, user request, quoted transcript, document, source code, tool result, error log, and postmortem.
2. Include every known false fire and at least one known true positive per detector. Add paired fixtures where byte-identical risky text appears once as cargo and once as the typed argument of a live tool invocation.
3. Validate the detector on a known-present control: demonstrate that the harness identifies a real pre-tool event and its tool identity. Independently validate role using a second field or event boundary, not the same parser twice.
4. Replay baseline and adapter versions. Primary acceptance: all known mention-only false fires become `not_applicable/non_control_role`; all known true positives retain their expected decision.
5. Mutation-test spellings, quoting, encoding, nested JSON, multiline strings, and result echoes. The tool operation should dominate incidental wording.
6. For permit-bound actions, inject post-approval changes to target, cwd, recursion, environment, tool identity, event ID, and time. Every meaning-changing mutation must invalidate the permit.
7. Shadow-log mode decisions before enforcement. Sample both `not_applicable` and `block` cases manually; do not inspect only failures.

The design is ready for a build trial if and only if trusted runtime role, event phase, tool identity, and typed arguments are available at the affected hook points. **UNVERIFIED — the settling experiment is a native hook-schema inspection plus one captured known-present event for each relevant hook.** If those fields are not available, the honest result is not to infer them from payload text. The fallback is to move each guard to the nearest runtime boundary that does provide them, even if that means some detectors cannot run at their present location.

## 6. Final recommendation

Adopt the aviation clearance/checklist invariant as follows:

> **Only an authenticated, role-addressed control event can enter an action guard; high-consequence authorization is acknowledged in canonical form and bound to the exact executable state. Textual cargo is never promoted to an operational act by lexical resemblance.**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Start with the event normalizer and the five affected detector adapters. Add argument-bound permits only for the highest-consequence tier. Emit explicit mode/reason metadata. Use false-fire annotation only if a short trial proves it contributes unique regression cases.

This recommendation does not reintroduce a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. It is deliberately smaller: establish semantic role once at a trusted boundary, then let existing guards inspect the correct object.
