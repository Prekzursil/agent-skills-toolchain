# A019 — Coherence audit of `~/.claude/rules/cpp/security.md`

## Executive result

This audit found **seven actionable coherence collisions** around the C++ security rule: one path-scope contradiction, two same-level rule redundancies, one same-level static-analysis threshold contradiction, two independent enforcement gaps, and one stale/misleading “hooks” recipe. It also found one material skill-audit gap that cannot honestly be converted into a collision finding on this Linux job node.

The most consequential result is not that the C++ safety policy is too weak. It is that the policy has **no C++ enforcement path**. The live PostToolUse validator is wired for edits but its language dispatcher returns no checker for C/C++ files (`bundle/claude/hooks/per-edit-check/check.py:151-170`); the dispatcher manifest contains only generic Write/Task/memory checks (`bundle/claude/hooks/_dispatch/manifest.json:182-226`); no unpacked hook source contains `clang-tidy`, `cppcheck`, `fsanitize`, `strcpy`, or `reinterpret_cast`; and the clangd plugin is disabled (`bundle/claude/settings.json:562`). These are mechanically independent signals: executable source/manifest behavior and settings state. The positive controls succeeded: the same hook-source detector found 11 `ruff` occurrences, including the implemented Python checker at `per-edit-check/check.py:45-90`, and settings actually wire that checker at `settings.json:333-342`.

Therefore the rule is **unenforced**, not proven “ignored.” It is **almost certain (90-99%)** that edits made through `Edit`/`Write` can introduce the forbidden C++ constructs without any target-specific hook warning, because the configured PostToolUse path calls a dispatcher whose unknown-extension branch returns no issues (`per-edit-check/check.py:151-170`) and no other unpacked hook implements the named checks. This claim is deliberately limited to target-specific automatic enforcement; compiler/CI checks inside an individual project could still catch defects.

The measured corpus cannot settle whether agents usually follow the prose. It proves C++ work occurred—two retained compile-error fingerprints concern `lua_bridge.cpp` (`bundle/inputs/corpus.json:7345` and `:7651`)—but its retained fields contain no `clang-tidy`, `cppcheck`, `fsanitize`, or target forbidden-API evidence. The corpus is a distillation whose samples are capped (`bundle/inputs/corpus.json:3-11`), raw transcripts are absent from this bundle, and its hook detector explicitly says its entire hook section is NO DATA (`bundle/inputs/corpus.json:13261`). Calling this behavioral silence “compliance” or “noncompliance” would be invalid.

## Collision register

### A019-C01 — `.h` is claimed simultaneously as generic C and C++ policy scope

**Class:** CONTRADICTION  
**Artifacts:** `rules/cpp/security.md` and `rules/common/security.md` (with the package priority declaration in `rules/README.md`)

**Exact conflicting lines**

* C++ security applies to every `"**/*.h"`: `bundle/claude/rules/cpp/security.md:2-9`, specifically `:8`.
* Common security treats `.c`, `.cpp`, and `.h` as shared code scope: `bundle/claude/rules/common/security.md:13-16`.
* The package says the language-specific rule wins over common policy: `bundle/claude/rules/README.md:93-98`.
* Once loaded, the C++ rule forbids C allocation and C arrays: `bundle/claude/rules/cpp/security.md:17-19`.

**Collision mechanics**

A `.h` suffix does not by itself distinguish a C header from a C++ header. Under the current frontmatter, editing a C header loads C++-only instructions such as “Never use `malloc`/`free`” and “Never use C-style arrays.” The common file’s inclusion of `.c` and `.h` in the same universal scope makes the ambiguity concrete; it is not merely hypothetical naming trivia. Applying `rules/README.md` specificity literally would let the C++ rule override the common policy even when the header belongs to C.

`AGENTS.md` §10 does not resolve this collision. Both rule files are harness policy below the cross-tool security floor, and the collision is about erroneous applicability, not permission to weaken §9.

**Specific resolution — CONFIG:** Remove `"**/*.h"` from the unconditional C++ rule scope, or generate project-local scope that includes `.h` only after a C++ project signal such as `CMakeLists.txt` plus C++ translation units. Do not attempt content guessing in a blocking hook. It is **very likely (80-90%)** that project-level scoping eliminates false C-header guidance without reducing coverage of `.cpp/.hpp/.cc/.hh/.cxx`, because those unambiguous suffixes remain covered; the evidence is the current explicit suffix list at `cpp/security.md:3-9`. UNVERIFIED whether this owner has C projects whose public headers use `.h`; the settling experiment is a Windows inventory of repositories containing both `*.c` and `*.h`, followed by inspection of their build-language declarations.

It is **almost certain (90-99%)** this removes semantic drift without losing policy content, because the current strict prohibition already exists at `security.md:17` and the ownership details remain at `coding-style.md:25-27`.

### A019-C04 — `clang-tidy` has two incompatible effective check-selection recipes

**Class:** CONTRADICTION  
**Artifacts:** `rules/cpp/security.md` and `rules/cpp/hooks.md`

**Exact conflicting lines**

* Security explicitly forces all checks: `clang-tidy --checks='*' src/*.cpp` (`bundle/claude/rules/cpp/security.md:38-43`).
* The C++ hooks recipe runs `clang-tidy src/*.cpp -- -std=c++17` with no `--checks` override (`bundle/claude/rules/cpp/hooks.md:17-25`).
* The same hooks file calls clang-tidy a recommended CI stage but specifies no common configuration (`:33-39`).

**Collision mechanics**

These commands need not run the same checks. Official clang-tidy documentation says `-checks=` selects checks, no `-checks` uses the default/configured set, and a closest-parent `.clang-tidy` file supplies configuration; it also recommends a compilation database and documents `-p <build-path>` ([LLVM clang-tidy documentation](https://clang.llvm.org/extra/clang-tidy/index.html)). Thus `security.md` overrides project/default selection with `*`, while `hooks.md` relies on default/project selection and hardcodes only C++17 compiler arguments.

The files are peers, so `AGENTS.md` §10 explicitly declines a silent choice. The present harness has no declared winner.

**Specific resolution — CONFIG:** Delete both ad-hoc recipes and establish one project-owned `.clang-tidy` check set plus `compile_commands.json`; rules should invoke `run-clang-tidy.py -p <build-dir>` or the project’s existing wrapper. A security-oriented baseline can enable `clang-analyzer-*`, `bugprone-*`, `cert-*`, selected `cppcoreguidelines-*`, `performance-*`, and `portability-*`, with explicit project exclusions rather than `*`. It is **very likely (80-90%)** that a single configured invocation produces more coherent results than the two current commands, because official semantics confirm that the existing commands select different effective configurations. UNVERIFIED which exact check families fit the owner’s C++ projects; the settling experiment is to run `clang-tidy --list-checks` and `--explain-config` in each active C++ repo, then compare a baseline run’s actionable/false-positive counts before adopting the list.
