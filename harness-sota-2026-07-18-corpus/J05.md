# J05 — external background health monitoring for basic-memory

## Executive verdict

The missing signal is not another in-session hook. It is a **synthetic memory transaction driven by an independent Windows Task Scheduler clock, with its result written to a non-memory receipt and routed to an out-of-band desktop notification**. The existing B1 `mcp-liveness` and `memory-spool` mechanisms remain the request-path recovery layer; the proposed monitor is their external control plane. It folds into the already-existing `BasicMemory-Watchdog` scheduled task and the already-existing notification/background-digest/event-ledger buses, so it adds **zero hooks** and does not approach the approximately-six-hook ceiling.

The design would have detected the reported continuous four-hour daemon death. With a five-minute schedule and a two-consecutive-failure debounce, the first failed probe occurs within five minutes and the second within ten minutes. A 240-minute continuous outage therefore contains at least 48 failed scheduled probes and must reach `FIRING` within `(5,10]` minutes. This counterfactual is **almost certain (90-99%)**, because it follows from the schedule/state-machine arithmetic and the existing detector correctly classified both a closed port and a non-MCP HTTP listener in executed tests. The remaining one-percent-class uncertainty is environmental: **UNVERIFIED on the Windows owner box; the experiment that settles it is the controlled kill/corpse drill in Finding 8, including observation of the actual Windows toast and persisted receipt**.

This is deliberately not a second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. It is a small scheduled probe riding the Windows scheduler and the harness's current state/notification/ledger buses.

## Grounding and detector controls

### What the corpus establishes

The corpus is a high-coverage distillation: its metadata reports 11,633 files seen, zero failed files, 1,564,084 parsed lines, one bad line, and 32 oversized lines (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-10`). It does not directly timestamp the reported four-hour incident, so the duration comes from the unit's pinned incident statement, not a reconstructed transcript.

Basic-memory is both heavily used and fallible:

* `write_note`: 408 calls, 18 errors, 4.41% (`corpus.json:239-244`).
* `search_notes`: 357 calls, 13 errors, 3.64% (`corpus.json:271-276`).
* `read_note`: 353 calls, 3 errors, 0.85% (`corpus.json:279-284`).
* `edit_note`: 156 calls, 18 errors, 11.54% (`corpus.json:335-340`).

The failure shapes show why a process/port check is insufficient. The corpus contains five explicit `basic-memory is not connected` errors (`corpus.json:7490-7494`), three lost `edit_note` responses after the transport dropped (`corpus.json:8660-8665`), and three lost `write_note` responses after a mid-call transport drop (`corpus.json:8718-8724`). The per-tool breakdown adds six connection failures and three dropped-transport writes among the 18 `write_note` errors (`corpus.json:9592-9607`), while `edit_note` has six connection failures, five not-connected failures, and three dropped transports (`corpus.json:9623-9638`). This is direct evidence of user-visible memory transaction failures, not merely internal health noise.

The corpus's `hooks` section is **NO DATA**, not evidence of no hook activity: its own known-positive control failed and it explicitly labels the detector broken (`corpus.json:13260-13263`). No finding below uses that section. Likewise, the 2,268 owner-correction candidates are recall-biased and an unfiltered control found 41/41 false positives (`corpus.json:10371-10374`); I do not infer alert preferences from those candidates.

### What already exists and must not be duplicated

The canonical contract assigns semantic memory to basic-memory and objective history to the event ledger (`/local_disk0/codexwork/bundle/claude/AGENTS.md:87-91`). The current B1 liveness code already:

* probes on `SessionStart` and before basic-memory calls (`hooks/mcp-liveness/liveness.py:4-16`);
* checks TCP plus an MCP `initialize` exchange rather than only a port (`liveness.py:18-21`, `:100-193`);
* launches the restart helper and injects a same-session warning (`liveness.py:377-400`);
* catches all top-level exceptions and exits zero (`liveness.py:404-440`).

The B1 memory spool already writes intended `write_note`/`edit_note` payloads before the MCP call (`hooks/memory-spool/spool.py:2-12`, `:37-60`), retains failed writes and emits a loud failure alert (`hooks/memory-spool/flush_check.py:43-88`), and resurfaces unconfirmed writes at the next session (`flush_check.py:91-130`). The local dispatcher folds spool replay/checks, open-loop resurfacing, heartbeat, and background digest into a single SessionStart invocation (`hooks/_dispatch/manifest.json:6-70`); it also folds spooling into the existing PreToolUse dispatcher (`manifest.json:182-227`). Therefore this unit does not propose another hook, another spool, another open-thread file, or another memory store.

The audit's B14 claim—treated as a claim, not re-derived fact—says Claude and Codex reach the same vault through different processes/transports, and reports the HTTP daemon, MCP handshake, tools list, and scheduled launcher/watchdog as live during that audit (`inputs/audit-findings/B14.md:18-32`, `:66-72`). This matters because the new monitor must label transport planes rather than pronounce all memory healthy from one daemon check.

I also executed `test_memory_spool.py`: failed writes stayed spooled and alerted; successful writes cleared; SessionStart resurfaced an unflushed entry once; tool-use-ID fallback cleared a payload-drifted entry; all tests passed. Those behaviors are mechanically separate from liveness classification and support the continuity design, but they do not prove live MCP replay.

The timing proof was executed as a deterministic schedule calculation:

```text
interval=5m consecutive_failures=2 outage=240m guaranteed_failed_probes>=48 alert_window=(5,10]m
known-present control: PASS,PASS,PASS => HEALTHY, alerts=0
transient control: PASS,FAIL,PASS => RECOVERED-before-fire, alerts=0
four-hour incident prefix: FAIL,FAIL => FIRING no later than 10m; >=48 failed scheduled probes over 240m
```

This proves the state machine against the incident duration; it does not substitute for a Windows integration drill.

## Findings (inferred-surprise first)

### Finding 1 — **UNVERIFIED production drill: monitor the promise, not the process**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing `BasicMemory-Watchdog` scheduled task into a two-cadence black-box monitor: five-minute protocol checks and a fifteen-minute synthetic write/read/disk canary. This is not a new hook and not a new service.

**What it is.** The fast check performs an MCP `ping`, then `tools/list`, and asserts the expected `write_note` and `read_note` tools. The MCP specification defines `ping` specifically as a liveness request requiring a prompt response ([MCP schema, PingRequest](https://modelcontextprotocol.io/specification/2025-06-18/schema)). Every third tick, the transaction check overwrites one fixed note such as `harness-health/basic-memory-liveness-canary` with `{nonce, issued_at_utc, monitor_version}`, reads it back through MCP, and then independently reads the expected file under the configured `D:\basic-memory` vault and compares the nonce. Basic Memory documents `write_note(..., overwrite=true)` and `read_note(identifier)` as its supported interfaces ([Basic Memory MCP tools reference](https://docs.basicmemory.com/reference/mcp-tools-reference)). One fixed note prevents unbounded junk; the timestamp/nonce prevents a stale cached response from passing.

**Why-inferred.** The owner asked that basic-memory “always” work after a silent four-hour loss (recorded in the existing B1 source at `mcp-liveness/liveness.py:2-16`), while the corpus shows lost writes and dropped responses. The surprise is that a listening process is not the promise the owner cares about; *durable round-trip capture* is.

**How-to-build.** Add `memory-health.py` beside the current B1 liveness code and call it from the existing scheduled watchdog—not from Claude/Codex. Keep the script stdlib-only. Persist one atomic state document outside basic-memory, e.g. `~\.agents\state\harness\memory-health-state.json`, and append one bounded JSONL receipt per tick with `tick_id`, start/end UTC, phase results, latency, nonce hash, state transition, restart action, and notification result. State is `HEALTHY`, `SUSPECT` after one failure, `FIRING` after two, and `RECOVERING` until two full transaction successes. Use the current restart helper, whose safety check only kills a positively identified basic-memory owner of port 8765 (`restart-basic-memory.ps1:35-53`, `:71-86`). Always catch the monitor's own exception, record `monitor_error` if possible, and exit 0 to preserve the fail-open contract.

**External signal that verifies it.** Signal A is the actual MCP response/nonce returned by a process started by Task Scheduler, outside the agent session. Signal B is the nonce in the vault file read directly from disk, outside MCP. A closed-port control, a non-MCP listener control, a known-good canary round trip, and a stale-old-nonce control prove the detector discriminates rather than merely returning “down.” Google SRE explicitly distinguishes black-box symptom checks from white-box internal checks and says black-box checks are the paging signal for ongoing user-visible failures ([Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)).

**Proof and confidence.** For the reported continuous daemon death, the five-minute protocol path would reach `FIRING` within ten minutes: **almost certain (90-99%)**, based on the executed schedule proof and the two executed negative controls. **UNVERIFIED that the synthetic transaction works against the owner's installed Basic Memory version and exact Streamable HTTP session behavior; the experiment is the Finding 8 live canary followed by controlled clean-death and corpse tests.** A partial failure in which `ping` works but writes disappear is **very likely (80-90%)** to be caught within 30 minutes, based on two fifteen-minute failed transactions and independent MCP/disk nonce comparison; the same live fault-injection experiment settles it.

**SOTA citation.** Google SRE recommends critical black-box monitoring for symptoms, while retaining white-box signals for diagnosis ([Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)); NIST AI RMF Measure 2.4/2.6 calls for production component monitoring, safe failure, reliability metrics, and response-time measurement ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first, because the canary writes a fixed note and modifies the existing scheduled task; show the exact note path, cadence, and task diff before enabling it.

### Finding 2 — **UNVERIFIED client-plane probes: report a health vector, never a green blob**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Emit separately named results for `vault_disk`, `basic_memory_cli`, `http_mcp`, `claude_stdio_config`, and `codex_http_config`; do not collapse them into “basic-memory is healthy.”

**What it is.** The transaction in Finding 1 establishes the HTTP daemon/vault path. A slower hourly plane audit runs `basic-memory status`/`doctor` read-only, resolves `claude mcp get basic-memory` and `codex mcp get basic-memory`, and records transport/target drift. It does not invoke an LLM. It labels `HTTP_DOWN_VAULT_OK`, `VAULT_WRITE_FAILED`, `CLIENT_CONFIG_DRIFT`, `INDEX_STALE`, or `MONITOR_UNKNOWN` rather than one Boolean.

**Why-inferred.** B14's audit claim says Claude uses stdio while Codex uses the shared HTTP daemon (`B14.md:26-32`). The corpus also separates “no such tool,” “not connected,” socket closure, and dropped-mid-call errors (`corpus.json:9598-9615`, `:9629-9646`). An all-green result from one endpoint could therefore miscalibrate the owner's trust in another client plane.

**How-to-build.** Put the plane checks behind subcommands in the same `memory-health.py`, with per-phase hard timeouts and sanitized command outputs. Validate the detector first against known-present config: both CLI resolvers must name `basic-memory`; then mutate only disposable fixture configs to prove missing/wrong URLs are found. The scheduled task writes the vector into the same JSONL receipt. `doctor` remains diagnostic/ticket-level; only a failed user-promise transaction pages.

**External signal that verifies it.** Independent command exit/results from Basic Memory CLI, Claude CLI, Codex CLI, MCP, and direct filesystem content. No model judges its own configuration. Two signals are required before saying a plane is absent: the native resolver result and parsed configured target, after both find a known-present fixture.

**Proof and confidence.** The vector will distinguish HTTP-daemon death from vault failure **very likely (80-90%)**, because the MCP and direct-disk nonce signals differ mechanically. **UNVERIFIED whether `claude mcp get` and `codex mcp get` return usable connectivity information in a noninteractive scheduled-task account; the experiment is to run both under the task's exact principal and compare with their interactive output.** Until that experiment, `CLIENT_CONFIG_DRIFT` must not be paged—only logged.

**SOTA citation.** Google SRE notes that in multilayer systems one layer's symptom is another's cause and recommends observing both sides to distinguish service failure from the path to it ([Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)).

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for receipt schema/fixture tests; confirm-first before registering the hourly commands under the owner's task principal.

### Finding 3 — **UNVERIFIED observer-of-observer: detect a watchdog that silently stopped running**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Fold a freshness check for the memory monitor receipt into an already-scheduled background producer (prefer the existing background-digest/world-watch producer), rather than creating another hook or daemon.

**What it is.** The memory monitor writes `last_started`, `last_finished`, `tick_id`, and `monitor_version` to a non-memory atomic receipt. A mechanically separate scheduled task checks both (1) receipt age and monotonic `tick_id`, and (2) Task Scheduler's `LastRunTime`/`LastTaskResult`. If the receipt is older than 15 minutes while the machine is awake, it emits `MEMORY_MONITOR_BLIND`, not “basic-memory down.” It also knows a positive control: the current task definition and a recent intentionally generated receipt.

**Why-inferred.** The owner's incident was silent. A health checker that can disappear silently merely moves the same defect outward one layer. Existing audit findings include a memory regression suite that returns zero despite failed probes (`inputs/audit-findings/F08.md:79-85`), reinforcing that scheduler green and semantic green are different claims.

**How-to-build.** Add a small `check-memory-monitor-receipt` function to the existing hourly producer. Do not call basic-memory. Read the receipt, query `Get-ScheduledTaskInfo`, append one digest incident on transition, and clear it after two fresh ticks. Account for sleep/resume by comparing Windows boot/resume evidence: if the scheduler could not run, classify `HOST_ASLEEP_GAP` as informational and immediately request a fresh monitor tick on resume. All branches exit 0 on their own errors.

**External signal that verifies it.** The second scheduled task's execution result plus the first task's receipt. Known-present control: start the monitor manually and prove the checker sees a new `tick_id`. Negative control: point the checker at a frozen fixture receipt while keeping a fixture task “successful”; it must report blind. These are different data fields and different executions.

**Proof and confidence.** This catches a running scheduler whose monitor code hangs or no longer updates receipts **very likely (80-90%)**, based on independent freshness and scheduler fields. **UNVERIFIED whether the named background producer is registered at a suitable hourly cadence on the live Windows box; the experiment is `Get-ScheduledTask` plus a 70-minute frozen-receipt drill under the real task.** If the producer is not present, fold this check into the existing weekly `harness-bench` only as a weaker backstop, not as the primary ten-minute outage detector.

**SOTA citation.** Microsoft documents that scheduled tasks can repeat at fixed intervals and persist executions/results ([Task Scheduler repetition](https://learn.microsoft.com/en-us/windows/win32/taskschd/repeating-a-task)); NIST recommends regular in-operation testing and tracking of existing and emergent risks ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it if folded into a confirmed existing background producer; confirm-first if a new scheduled task would be required.

### Finding 4 — **UNVERIFIED end-to-end loss envelope: make “memory down” create a durable unresolved thread automatically**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On the external state transition to `FIRING`, append one failure to the existing event ledger and one line to the existing background digest; keep it unresolved until the recovered canary and spool reconciliation both prove closure.

**What it is.** An incident record contains episode ID, `first_failed_at`, `last_known_good_at`, affected planes, restart attempts, and the count/IDs of currently pending memory-spool records. It never stores the spooled note contents in the alert. On recovery, it records `recovered_at`, the successful canary nonce, and `pending_spool_count`. It tombstones the failure only when `pending_spool_count=0` or the owner explicitly discards the entries.

**Why-inferred.** “Never drop a thread” is a hard constraint, and the current spool intentionally resurfaces a write only once (`flush_check.py:91-130`). Audit E08 reports a pending spool entry already present in the reported set, meaning “alerted once” is not equivalent to “resolved” (`inputs/audit-findings/E08.md:65`). The event-ledger CLI already supports failures with preconditions and later milestones that supersede them (`hooks/event-ledger/note.py:2-12`, `:25-43`).

**How-to-build.** Invoke `event-ledger/note.py --kind failure` once per episode using an episode-key sidecar, and append an actionable, date-prefixed line to `BACKGROUND-DIGEST.md`. Do not create another `OPEN-THREADS` implementation: the existing SessionStart `open-loops/resurface` derives unresolved failures from the ledger (`hooks/open-loops/_common.py:5-23`, `:469`), and the existing background reader archives before truncation and only truncates after successful archive (`hooks/background-digest/reader.py:2-10`, `:161-220`). Recovery writes a milestone with `--supersedes` only after both external signals pass.

**External signal that verifies it.** Signal A: the external canary's recovered transaction receipt. Signal B: filesystem enumeration of spool sidecars and their confirmed/failed status, not an agent's recollection. A third owner signal—explicit discard—may close intentionally unreplayed items.

**Proof and confidence.** This prevents the incident thread from disappearing at the next session **very likely (80-90%)**, because unresolved ledger failures already feed the existing resurface path and digest consumption is archive-before-truncate. **UNVERIFIED end-to-end across a real incident because this unit did not mutate the subject; the experiment is a disposable episode fixture that fires, survives a SessionStart read, recovers with one spool pending, and closes only after that spool is cleared.**

**SOTA citation.** The Microsoft human-AI guidelines call for maintaining recent interactions, efficient correction/recovery, explanations of why the system acted, and cautious adaptation ([Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).

**Value × effort:** transformative × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it; it uses existing durable buses and performs no destructive action.

### Finding 5 — **UNVERIFIED scheduled-principal delivery: attention-aware alert contract with no prompt tax**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Reuse the existing desktop-notification implementation and background digest to issue one actionable alert per outage episode, plus one recovery notification; never inject repeated warnings into every agent turn.

**What it is.** Severity policy:

* first failure: silent `SUSPECT` receipt;
* second consecutive fast-check failure or one failed durable-write canary: one Windows desktop toast, one event-ledger failure, one digest line;
* continued failure: no additional owner interruption for six hours, but receipts continue;
* recovery: one compact resolution toast only if an outage alert fired;
* unresolved spools: shown in the next main SessionStart digest/open-loop surface, not as repeated desktop pages.

The alert body is factual and bounded: `Memory capture degraded since 14:05Z; HTTP MCP failed twice; restart attempted; 3 writes safely spooled; next automatic probe 14:15Z; open receipt …`. It never says “memory lost” unless an intended write has no spool and no successful transaction receipt.

**Why-inferred.** Prompt fatigue is a hard constraint. The current liveness code injects same-context warnings (`liveness.py:298-339`), while the current notification code already supports a detached Windows desktop balloon and terminal bell (`hooks/notify-idle/notify.py:2-24`, `:87-110`). The existing background digest is expressly designed to surface away-time notices once without adding another raw hook (`background-digest/reader.py:2-10`).

**How-to-build.** Extract or expose a tiny generic CLI entry point from the existing notifier instead of copying its PowerShell. Episode-dedup uses the monitor state file, not an LLM. Acknowledge/snooze is global configuration (`off`, quiet hours, repeat interval) and never hides the durable ledger record. Retain “resolved” in the same episode receipt. Do not install Prometheus/Alertmanager: copy only the state-machine semantics.

**External signal that verifies it.** The detached Windows notification process exit marker/callback plus the non-memory incident receipt. The owner sees the toast outside Claude/Codex; the next session sees the independently persisted digest. A notification fixture proves a known-present toast before a suppressed-toast conclusion is allowed.

**Proof and confidence.** Episode dedup will substantially reduce repeated prompts **very likely (80-90%)**, because notifications are keyed to state transitions rather than probe count. The alert will reach the owner while the desktop session is active **likely (55-80%)**, based on the shipped detached NotifyIcon pattern; **UNVERIFIED under the real scheduled-task principal and Windows notification settings, settled by the Finding 8 visible-toast/receipt drill**. If the toast control fails, the monitor must label `notification_delivery_unknown` and rely on the digest—never report “owner alerted.”

**SOTA citation.** IBM Research's proactive-notification work motivates issuing, suppressing, and aggregating by severity/preferences/schedule to reduce fatigue ([IBM Research](https://research.ibm.com/publications/a-snooze-less-user-aware-notification-system-for-proactive-conversational-agents)). Microsoft HAX calls for efficient dismissal, efficient correction, explanations, and global controls over what is monitored ([HAX paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Prometheus Alertmanager similarly deduplicates, groups, routes, silences, and inhibits alerts ([Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)); those semantics are copied locally without deploying that service.

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first for default quiet hours/repeat interval; just-do-it for episode dedup and factual receipt content.

### Finding 6 — **UNVERIFIED wedge drill: recovery is a read-after-write fact, not “restart launched”**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Keep an incident open after the restart helper launches; declare recovery only after two successful full canary transactions and a direct-disk nonce match.

**What it is.** `restart_attempted=true` is an action receipt, never a success receipt. The state transitions `FIRING -> RECOVERING` after launch and `RECOVERING -> HEALTHY` only after two spaced successful transaction cycles. If TCP returns but the nonce does not, state stays degraded. The resolution message includes exact MTTD, MTTR, and pending-spool count.

**Why-inferred.** The existing B1 code sets `restart_attempted` when the helper is launched (`liveness.py:377-400`), and its alert explicitly tells the agent to verify afterward (`liveness.py:307-316`). The restart helper's own confirmation is best-effort and checks only the port owner after two seconds (`restart-basic-memory.ps1:128-131`). The corpus's dropped-mid-call responses prove that “process exists” and “write durably completed” are different states.

**How-to-build.** Reuse Finding 1's canary; do not add another verifier. Persist action and outcome as separate receipt fields. Require two successes to avoid flapping and retain `keep_firing` semantics for one interval after a single apparent recovery. If auto-restart exhausts two attempts in one episode, stop thrashing, retain fail-open agent behavior/spooling, and page once with the manual scheduled-task command.

**External signal that verifies it.** Restart process launch/exit is signal A; later MCP read-back plus direct-disk nonce is signal B. Only signal B closes. The agent never certifies its own fix.

**Proof and confidence.** This prevents false “recovered” claims from a port-only comeback **almost certain (90-99%)**, because the close predicate structurally requires two independent observed outcomes. **UNVERIFIED against a real wedged-but-listening Basic Memory process; the experiment is the corpse/wedge scenario in Finding 8.**

**SOTA citation.** Prometheus supports a pending duration and `keep_firing_for` to avoid transient/flapping state changes ([Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)); Google SRE recommends at least two evaluation cycles to avoid missed-collection false alerts ([Practical Alerting](https://sre.google/sre-book/practical-alerting/)).

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it.

### Finding 7 — **UNVERIFIED owner-focus effect: publish evidence and loss exposure, not “always works”**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Derive a compact local SLO/status report from monitor receipts: availability by phase, MTTD, MTTR, transaction latency, monitor blind time, restart outcomes, pending-spool age, and the exact last-known-good durable-write timestamp.

**What it is.** A command/read-only status file answers: `Can I reach it? Can I write and read? Did disk contain the nonce? When was that last proven? Is the monitor itself fresh? How many intended writes are awaiting replay?` The owner-facing claim is `durable round trip last proven 7m ago`, never `memory is healthy` without scope. Weekly digest reports only threshold breaches or trend changes; raw ticks remain in bounded JSONL.

**Why-inferred.** The owner needs trust calibration after a silent loss. The corpus shows different failure rates for write, edit, search, and read, so one availability percentage would hide the riskier edit path. NIST says production monitoring, response times, limitations, and measurement effectiveness should be documented (`AI RMF Core`, Measure 2.4-2.6 and 2.13).

**How-to-build.** Add a pure reducer over the receipt JSONL; no database. Retain 30 days or a bounded number of records. Use explicit denominators and label scheduled-host-sleep gaps separately. Alert threshold starts fixed from the incident (`2 consecutive fast failures`), not learned. After 30 days, owner feedback may adjust quiet hours/repeats, but never the correctness predicate.

**External signal that verifies it.** The report is derived from execution receipts and disk/MCP comparisons, and a fixture independently recomputes totals from raw JSONL. The report generator must find a known-present seeded failure and seeded success before any “zero incidents” claim.

**Proof and confidence.** Evidence-scoped status is **very likely (80-90%)** to reduce overtrust compared with an unqualified green label, based on the explicit transport/transaction timestamps and HAI trust-calibration literature. **UNVERIFIED that weekly summaries improve this owner's focus; the experiment is a four-week A/B of raw per-incident alerts versus incident alerts plus one weekly threshold-only summary, using owner dismiss/acknowledge behavior as the outcome.** Do not personalize automatically before that evidence exists.

**SOTA citation.** NIST requires documented production monitoring and reliability/response-time metrics ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). Microsoft HAX recommends making clear why the system acted, learning preferences over time, adapting cautiously, and offering global controls ([HAX paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). A 2024 systematic review defines trust calibration as adjustment of expectations to actual reliability and reviews confidence/explanation/reliability cues ([ACM Journal on Responsible Computing](https://doi.org/10.1145/3696449)).

**Value × effort:** medium × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for factual local metrics; confirm-first before changing alert cadence based on inferred preferences.

### Finding 8 — **UNVERIFIED until executed: a five-fault live acceptance drill is the installation gate**

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Refuse to label the external monitor deployed until an isolated acceptance drill exercises five distinct failures and observes both detection and recovery through external receipts.

**What it is.** The matrix:

1. **Known-good control:** live MCP `ping` + tools list + nonce write/read + direct file nonce; zero alert.
2. **Clean death:** stop the daemon through its supported scheduled-task path; after two ticks, one `FIRING` incident and one visible toast; spool a disposable fixture payload, not owner data.
3. **Dead-but-listening:** bind a disposable non-MCP HTTP fixture port and point a temporary monitor config at it; classify `PROTOCOL_CORPSE`, never kill an unrelated PID.
4. **Semantic failure:** fixture returns valid MCP/ping but stale/wrong canary content; classify `TRANSACTION_FAILED` despite liveness.
5. **Observer failure:** freeze the monitor receipt while its fixture scheduler result remains success; the independent freshness checker reports `MEMORY_MONITOR_BLIND`.

Then restore the real daemon, require two full transaction successes, confirm one recovery notification, and prove the ledger thread remains open until the fixture spool is cleared.

**Why-inferred.** The known-defects input records six wrong conclusions from single unvalidated probes and a seventh detector that reported three absent capability classes until a known-positive control showed only hooks detection was broken (`INPUT-known-harness-defects.md:111-129`). This monitor protects the system's memory of truth; accepting it on source review would repeat the exact failure class.

**How-to-build.** Put fixtures in the existing `mcp-liveness/test_liveness.py` family and extend it with an MCP success server, stale nonce response, state-transition reducer, notification sink fixture, and frozen receipt. For the one live clean-death test, obtain owner confirmation, capture pre-state (`Get-ScheduledTask`, port owner, successful canary), stop/restart only the positively identified basic-memory task/process, and capture post-state. Never use an unbounded kill. The acceptance artifact records commands, UTC timestamps, task result, monitor receipts, toast acknowledgement, canary nonce hash, ledger episode ID, and restored healthy result.

**External signal that verifies it.** Every verdict has at least two mechanically independent signals: process/task status plus MCP; MCP nonce plus disk nonce; monitor receipt plus separate freshness task; notification sink/owner observation plus incident receipt. Known-positive controls precede every absence conclusion.

**Proof and confidence.** The existing test suite already passes clean closed-port, non-MCP listener, alert, state, throttle, and dedup cases (`test_liveness.py:66-208`), so the proposed expanded fixture suite is **very likely (80-90%)** to cover those logic paths. **UNVERIFIED—and intentionally not called done—until the real Windows clean-death, visible notification, recovery canary, and task-principal checks pass.** Once all five scenarios pass with restored pre-state, it is **very likely (80-90%)** that the exact reported four-hour continuous daemon death would alert inside ten minutes; evidence would then include both mathematical timing and live task execution.

## Minimal architecture and exact loop closure

```text
Existing BasicMemory-Watchdog scheduled task (different process + independent clock)
  every 5m: MCP ping -> tools/list
  every 15m: overwrite fixed canary nonce -> MCP read nonce -> direct disk read nonce
       |
       +--> bounded non-memory JSONL receipts + atomic episode state
       +--> existing restart-basic-memory helper (action only, not recovery proof)
       +--> existing generic Windows notification path (one per transition)
       +--> existing event-ledger failure + background digest line

Existing independent background producer
  receipt freshness + Task Scheduler LastRunTime/LastTaskResult
       |
       +--> MEMORY_MONITOR_BLIND (not BASIC_MEMORY_DOWN)

Existing session buses (no new hook)
  memory-spool preserves intended writes
  open-loops derives unresolved ledger failure
  background-digest surfaces incident once
       |
       +--> close only after 2 transaction successes AND zero/owner-discarded spools
```

|---|---|---|
| daemon alive | scheduled MCP response | no |
| memory capture works | scheduled nonce write/read + direct disk nonce | no |
| restart worked | later full transaction successes | no |
| monitor ran | independent receipt-freshness task + scheduler result | no |
| owner alerted | notification delivery control/owner observation + receipt | no |
| no thread lost | ledger unresolved state + spool inventory | no |
| incident closed | two recovered transactions + spool cleared/discarded | no |

## Anti-overfit gate and alternatives rejected

1. **Add another SessionStart/PreToolUse hook — rejected.** B1 already owns request-path liveness and spooling. Another hook would duplicate it, stay silent while no session is active, and consume hook/latency budget.
2. **Port/PID-only watchdog — rejected.** The corpus contains dropped mid-call responses, and the existing code already recognizes dead-but-listening as distinct (`liveness.py:109-193`). A process is not durable capture.
3. **Agent asks itself whether memory worked — rejected by construction.** It violates this unit's law and cannot catch an outage while no agent is running.
4. **Prometheus/Alertmanager/Sentry/PagerDuty daemon stack — rejected.** Their alert-state ideas are useful, but deploying them would be BUILD-LARGE/observability SaaS for a single local keystone. The local JSONL/state machine is enough.
5. **Second memory store/vector DB/KG as failover — rejected.** It reintroduces explicitly rejected architecture and creates reconciliation/split-brain risk. The existing spool is the bounded outage buffer.
6. **Model-based anomaly detector or trained critic — rejected.** The incident predicate is deterministic; a learned classifier would add calibration burden and false alerts without evidence.
7. **Email/chat alert by default — rejected for initial build.** It requires credentials/connectors and expands external state. The existing desktop notification plus digest is sufficient to validate the loop. If the owner later requires off-machine alerting, that is a separate confirm-first design.
8. **Every-tick owner notification — rejected.** It directly violates prompt-fatigue and alert-quality constraints. State-transition dedup retains evidence without attention spam.
