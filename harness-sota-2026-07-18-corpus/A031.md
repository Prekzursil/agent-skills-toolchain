# A031 — Coherence audit: `rules/golang/coding-style.md`

## Scope and verdict

This unit read the complete 32-line target at
`/local_disk0/codexwork/bundle/claude/rules/golang/coding-style.md`, the applicable common rules,
the Go sibling rules, the supplied Claude settings and instruction files, the hook wiring and
implementations, and the measured corpus. The subject was read-only. The only write is this artifact.

The target is not coherent enough to remain unchanged. It has four policy defects and two enforcement
defects:

1. It imports an absolute, language-agnostic ban on mutation that contradicts both idiomatic Go and
   the harness's own Go patterns.
2. “Return structs” contradicts the sibling Go example's pointer return and is narrower than the Go
   project's actual “return concrete types” guidance.
3. “Always wrap errors” conflates adding human context with exposing an underlying error through
   `%w`; the latter is an API decision and is not always correct.
4. Requiring both `gofmt` and `goimports` duplicates work because `goimports` is a superset of
   `gofmt`.
5. The live PostToolUse path does not format or even syntax-check Go.
6. The sibling Go hook rule advertises `go vet` and `staticcheck`, but neither is wired.

It is **almost certain (90-99%)**, based on the literal rule text, the live settings-to-handler call
path, the controlled malformed-file probe, and primary Go documentation cited below, that a small
replacement of this rule plus a small extension of the existing PostToolUse/Stop validation bus is
better than preserving the current text. This is an evolution of the existing native rules/hooks
bus, not a second runtime.

## Collision register

### C1 — Imported “never mutate” versus the harness's own mutating Go pattern

**Class: CONTRADICTION**

**Artifacts and exact lines**

- Target: `claude/rules/golang/coding-style.md:9` says it extends common coding style.
- Common rule: `claude/rules/common/coding-style.md:23-33` labels immutability “CRITICAL” and says
  “ALWAYS create new objects, NEVER mutate existing ones.” Its completion checklist repeats “No
  mutation” at `:59-68`.
- Go sibling: `claude/rules/golang/patterns.md:13-25` defines `Option func(*Server)`, mutates
  `s.port`, and applies options to `s`; `:38-40` returns a pointer to a constructed service.
- Rules governance: `claude/rules/README.md:102-104` explicitly anticipates a Go override allowing
  pointer-receiver mutation, but the target does not contain it.

**Why precedence does not silently fix it**

Go-specific rules could override common rules (`rules/README.md:93-99`), but the only Go-specific
text that would do so is an example in a never-loaded README (`rules/README.md:1-4`, `:100-104`), not
an operative rule. The loaded Go patterns demonstrate mutation but do not expressly resolve the
normative conflict. AGENTS §10 requires surfacing this same-level ambiguity.

**Diagnosis**

This is a wrong universal default for Go, not merely missing enforcement. The official Go review
guidance says a method that needs to mutate its receiver must use a pointer receiver and describes
several other cases requiring or preferring pointers ([Go Code Review Comments — Receiver Type](https://go.dev/wiki/CodeReviewComments#receiver-type)).

**Specific resolution**

[NATIVE (Claude Code already does this; we just enable it)] Replace the imported absolute with an
explicit Go override: “Prefer values when they naturally model immutable values; use pointer
receivers and deliberate mutation when identity, shared state, size, synchronization, or visible
updates require it. Do not copy types containing locks. Document concurrency and aliasing.” Also
change the common rule from an absolute to a default with the language-note mechanism promised at
`rules/README.md:106-110`. This is **almost certain (90-99%)** to eliminate the contradiction because
the replacement directly covers the sibling examples and follows the official receiver guidance.

### C2 — “Return structs” versus pointer returns and actual concrete-type guidance

**Class: CONTRADICTION**

**Artifacts and exact lines**

- Target: `claude/rules/golang/coding-style.md:15-18` says “Accept interfaces, return structs” and
  sets a 1–3-method interface threshold.
- Go sibling: `claude/rules/golang/patterns.md:35-40` accepts `UserRepository` and `Logger` but
  returns `*UserService`, not a struct value. Its functional-options constructor likewise returns
  `*Server` at `:20-25`.

Both are Go-specific rule files at the same precedence level. AGENTS §10 does not resolve the literal
struct-value versus pointer-to-struct mismatch.

**Diagnosis**

The phrase is badly written. It probably intends “return concrete types,” but “structs” literally
excludes pointers and other useful concrete types. That intended reading is **likely (55-80%)**, with
the sibling pointer-return examples and the Go project's wording as evidence. Official guidance says
interfaces normally belong to the consuming package and implementing packages should return
concrete, “usually pointer or struct,” types; it also warns against defining interfaces prematurely
or merely for mocks ([Go Code Review Comments — Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces)).

**Specific resolution**

[NATIVE (Claude Code already does this; we just enable it)] Replace the two bullets with: “Define an
interface in the consuming package when a real consumer needs an abstraction; accept the smallest
capability needed; return a concrete type (value or pointer as its semantics require). Do not create
implementor-side interfaces solely for mocking.” This is **very likely (80-90%)** to prevent the
current misreading because it names both permitted return forms and the placement rule.

### C4 — “Always wrap” wrongly makes `%w` exposure universal

**Class: STALE**

**Artifacts and exact lines**

- Target: `claude/rules/golang/coding-style.md:20-28` says “Always wrap errors with context” and its
  sole example uses `%w`.
- Common rule: `claude/rules/common/coding-style.md:43-49` requires explicit handling, user-friendly
  UI errors, detailed server context, and no silent swallowing. It does not require preservation of
  every underlying error as public API.

The target's word “wrap,” combined with only `%w`, collapses two decisions: add context for humans,
and expose the underlying error to `errors.Is`/`errors.As`. The Go team says there is no single answer:
use `%w` when callers should inspect the cause, and do not wrap when that leaks implementation details;
wrapping makes the underlying error part of the API ([Go 1.13 errors — Whether to Wrap](https://go.dev/blog/go1.13-errors#whether-to-wrap)).

**Diagnosis**

This is both wrong as an absolute and badly written. It is **very likely (80-90%)** that agents will
infer `%w` is mandatory because it is the only example and the heading says “Always”; the textual
pairing is the evidence. It is not safely enforceable through a lexical hook because API boundaries
and abstraction intent are semantic.

**Specific resolution**

[NATIVE (Claude Code already does this; we just enable it)] Replace it with: “Handle every error.
Add operation/resource context once at a useful boundary. Use `%w` only when callers are intended to
inspect the underlying error and that exposure is part of the API; otherwise translate to a package
error or preserve text without exposing the cause. Test with `errors.Is`/`errors.As` when wrapping is
contractual. Keep error strings lowercase and punctuation-free.” The final string convention is also
official ([Go Code Review Comments — Error Strings](https://go.dev/wiki/CodeReviewComments#error-strings)).
This is **almost certain (90-99%)** to remove the false universal while preserving useful context,
based on the Go team's explicit API analysis.

## Recommended replacement rule

[NATIVE (Claude Code already does this; we just enable it)] The following is the minimal native-rule
replacement after the skill experiment reconciles any duplicated guidance:

```markdown
---
paths:
  - "**/*.go"
  - "**/go.mod"
  - "**/go.sum"
---
# Go Coding Style

> Extends common coding style. Where Go idioms differ, this file overrides the common default.

## Formatting

- All Go source must be gofmt-formatted. Prefer goimports when available; otherwise use gofmt.

## Values, mutation, and receivers

- Prefer values for natural value types. Use pointer receivers and deliberate mutation when identity,
  shared state, synchronization, size, or visible updates require it. Do not copy lock-bearing types.

## Interfaces

- Define interfaces at the consumer when a real abstraction is needed.
- Accept the smallest capability needed; return a concrete value or pointer as its semantics require.
- Do not introduce implementor-side interfaces solely for mocking; no universal method-count gate.

## Errors

- Handle every error and add useful operation/resource context once at an appropriate boundary.
- Use %w only when callers are intended to inspect the underlying cause as part of the API.
  Otherwise translate the error or preserve its text without exposing implementation details.
- Use errors.Is/errors.As for contractual wrapped errors. Keep error strings lowercase and
  punctuation-free.

## Verification

- Run the repository's configured Go checks. Baseline: formatter plus go vet; run staticcheck when
  installed/configured. Do not weaken repository-specific gates.

## Reference

- See `golang-patterns` only after the canonical skill and both router indexes are verified current.
```

This replacement is 35 lines of native path-scoped guidance. The accompanying hook work remains
BUILD-SMALL and rides existing PostToolUse/Stop dispatch. It does not add a second orchestration
runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail
framework, so it passes the anti-overfit gate.
