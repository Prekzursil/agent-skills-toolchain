# A153 — Coherence audit: settings vs. behavior contracts / duplicate authority

Date: 2026-07-19 (UTC)  
Unit: A153  
Mode: read-only audit of the unpacked subject; only this artifact was written.

## Executive result

I read the complete supplied `~/.claude/settings.json` (703 lines), the complete supplied
`~/.claude/CLAUDE.md` (121 lines), and the complete `AGENTS.md` that Claude actually imports
(140 lines). The imported contract is unambiguous: `CLAUDE.md:3` contains exactly
`@AGENTS.md`, and the official Claude Code memory documentation says a relative import is
resolved relative to the importing file. Thus the relevant file is the sibling
`bundle/claude/AGENTS.md`, not `bundle/codex/AGENTS.md`. The latter is a separate provider copy
and is outside this settings-to-Claude-contract comparison.

The supplied configuration contains **four runtime-relevant coherence conflicts**:

1. The force-push rule has independently drifted in both directions: the registered hook
   blocks a direct forced push to any branch, while valid Git spellings that rewrite
   `main` pass the hook.
2. The contract requires explicit user instruction for `git commit --no-verify`, but the
   settings authority has no `ask` rule or hook for it and runs Bash in
   `bypassPermissions` mode.
3. The contract says destructive Git operations are block-worthy, but settings run Bash in
   bypass mode while the shared lifecycle blocker is opt-in and not enabled by the supplied
   settings.
4. The contract says non-dangerous guidance must inject rather than block, but the registered
   reverse-engineering autolaunch hook issues a native PreToolUse deny while a backend is
   merely starting, low on RAM, or unavailable.

Confidence in this snapshot-level conclusion is **almost certain (90-99%)**. Evidence: full-file
line review; two independent JSON parsers accepted `settings.json`; direct safe stdin probes of
the registered force-push hook exercised both positive and negative paths; static control-flow
inspection established the lifecycle and RE-autolaunch decisions; and current official Claude
Code documentation defines the relevant enforcement precedence. The remaining uncertainty is
the live Windows process environment and higher/lower settings scopes, which are not present on
this Linux job node and are called out inline under GAPS.

No subject file was modified. The architecture recommendations below use the existing native
permission/hook bus, add no orchestration runtime, memory store, durable-execution engine,
trained critic, observability SaaS, or guardrail framework, and therefore pass the anti-overfit
gate.

### Runtime precedence verified, not assumed

The current official Claude Code permissions documentation states that permission rules are
enforced by Claude Code rather than by the model: instructions in a prompt or `CLAUDE.md` shape
what Claude attempts, while permissions determine what the client allows. It also states that:

* `bypassPermissions` skips permission prompts except explicit `ask` rules and a few managed
  connector cases;
* a matching `ask` rule still prompts in bypass mode;
* a blocking PreToolUse hook takes precedence over allow rules and stops the call before normal
  permission evaluation; and
* settings are technical enforcement whereas `CLAUDE.md` is behavioral guidance.

Sources: [Configure permissions](https://code.claude.com/docs/en/permissions),
[Hooks reference](https://code.claude.com/docs/en/hooks), and
[Manage Claude's memory / CLAUDE.md](https://code.claude.com/docs/en/memory).

Consequently, “which wins at runtime” has two layers. If the model follows the contract, it may
never propose the prohibited call. Once it does propose a call, however, the native permission
and hook decisions win. That distinction is central to Findings 1-4.

## Finding 1 — Force-push duplicate authority has drifted both over-broad and under-broad

Severity: **breaking safety/coherence**.  
Confidence: **almost certain (90-99%)**, supported by the quoted configuration and contract,
the hook predicate, six direct stdin probes, and official hook precedence.

### Both authorities, verbatim

Behavior contract:

> “**Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code,
> force-push to main without explicit approval.”  
> — `bundle/claude/AGENTS.md:64-67`

> “Never `git push --force` to main/master without explicit user approval.”  
> — `bundle/claude/AGENTS.md:93-97`

> “1. The user's explicit in-session instruction and the permission system.”  
> — `bundle/claude/AGENTS.md:115-123`

Settings authority:

> `"Bash",`  
> — `bundle/claude/settings.json:35`

> `"ask": [],`  
> `"defaultMode": "bypassPermissions",`  
> — `bundle/claude/settings.json:70-71`

> `"matcher": "Bash",`  
> ...  
> `"command": "python \"C:/Users/Prekzursil/.claude/hooks/no-force-push/hook.py\"",`  
> ...  
> `"statusMessage": "no-force-push: protect remote history"`  
> — `bundle/claude/settings.json:152-159`

The implementation registered by settings makes the independent rule explicit:

> `ACTION = "Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1."`  
> `_PATTERN = re.compile("git\\s+push\\b[^\\n]*(--force\\b|-f\\b)", re.IGNORECASE)`  
> — `bundle/claude/hooks/no-force-push/tripwire.py:15-18`

### Concrete collisions

The safe probe fed synthetic PreToolUse JSON to the exact registered hook with bytecode writes
disabled. It did not run Git or touch a remote:

```text
git push --force origin main        -> rc=2, blocked
git push --force origin topic       -> rc=2, blocked
git -C repo push --force origin main -> rc=0, silent
git.exe push --force origin main    -> rc=0, silent
git push origin +main               -> rc=0, silent
git commit --no-verify -m x         -> rc=0, silent
```

This yields three actual semantic collisions:

1. An unapproved direct forced push to `topic` is blocked even though the named protected-target
   rule is `main/master`. The settings implementation owns a broader “all branches” rule.
2. An unapproved forced push to `main` using a Git global option, the Windows executable name, or
   a force-refspec bypasses the settings implementation, despite the contract forbidding the
   operation.
3. Even after explicit approval, the first normal direct invocation remains blocked unless the
   caller also knows and sets the hook-specific `FORGE_NO_FORCE_PUSH_OFF=1` escape. That extra
   mechanism is documented only in the hook response, not in the authoritative contract.

`--mirror` is another valid history-rewrite form not recognized by the standalone regex; the
shared lifecycle parser recognizes `--mirror` at `bundle/agents/harness/modules.py:684-696`, but
that parser is disabled by default as shown in Finding 3.

### Which authority wins at runtime

For literal `git push ... --force/-f`, the PreToolUse exit-2 hook wins and blocks even though Bash
is allowed and bypass mode is active. For missed spellings, the hook returns 0 and the broad Bash
allow plus bypass mode permits execution without a prompt. These outcomes follow the direct probe
and the official hook precedence cited above.

The exact effective behavior on the owner's current Windows Claude process is **UNVERIFIED**;
the settling experiment is to run `/permissions`, capture the effective settings sources, inspect
`Get-ChildItem Env:FORGE_NO_FORCE_PUSH_OFF,Env:HARNESS_LIFECYCLE_GUARD`, and repeat these synthetic
stdin probes against the deployed hook without invoking Git. The snapshot behavior itself is
verified.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Replace only the standalone predicate with a token-aware Git invocation parser, retaining the
existing PreToolUse registration and exit-2 wrapper. It must recognize `git`/`git.exe`, skip Git
global options such as `-C`, identify force modes (`-f`, `--force`, `--force-with-lease`,
`--mirror`, and leading `+` refspecs), resolve whether the destination includes `main/master`,
and preserve the documented explicit-approval escape. Permit non-protected forced topic-branch
pushes unless another project policy names them.

It is **very likely (80-90%)** that this remains below 200 lines and removes the demonstrated
scope/syntax drift, because the current pure predicate/wrapper boundary already exists
(`tripwire.py:39-47`; `hook.py:35-59`) and only the predicate changes. A fixture matrix containing
the six probes above plus `--mirror`, `--force-with-lease`, explicit remote refspec mappings, and
approved opt-out settles the remaining parser risk. No second runtime is introduced.

## Finding 2 — `--no-verify` requires approval in prose but has no settings enforcement

Severity: **degrading safety/coherence**.  
Confidence: **almost certain (90-99%)** for the supplied snapshot, supported by structured settings
parsing, a validated bounded search, a direct hook probe, and official bypass/ask semantics.

### Both authorities, verbatim

Behavior contract:

> “Never `--no-verify` on commits without explicit user instruction.”  
> — `bundle/claude/AGENTS.md:93-97`

Settings authority:

> `"Bash",`  
> — `bundle/claude/settings.json:35`

> `"ask": [],`  
> `"defaultMode": "bypassPermissions",`  
> — `bundle/claude/settings.json:70-71`

### Concrete collision and two independent signals

If the model emits `git commit --no-verify -m x` without prior instruction, the behavioral
contract says not to do it, but the configured client supplies no prompt or deny.

Signal 1 was a bounded implementation search over all supplied Claude hooks and the shared
harness: `--no-verify` had **0** matches. The same detector found **40** `force-push`/`--force`
matches, proving the search could find a known-present safety mechanism. Signal 2 was the direct
synthetic call to the registered force-push hook: `git commit --no-verify -m x` returned rc 0 with
no output. Structured JSON parsing independently confirmed `ask_rules=0`, `Bash` allowed, and
`defaultMode=bypassPermissions`.

### Which authority wins at runtime

The model instruction wins only if the model obeys it and never proposes the command. If it does
propose the command, settings win at execution: there is no matching deny/ask or blocking hook,
and bypass mode skips the normal prompt. This is exactly the behavioral-guidance versus technical-
enforcement distinction in the official permissions documentation.

The owner's live Windows effective rule set is **UNVERIFIED**; the settling experiment is
`/permissions` plus a non-mutating permission-debug invocation for the literal command, checking
managed, user, project, local, and CLI-supplied settings sources. No commit should be created.

### Minimal resolution — CONFIG (settings/JSON only)

Add a narrow native `permissions.ask` rule that matches any Bash command containing
`--no-verify` (for example, the least-complex robust boundary is the flag itself rather than one
fragile Git prefix). The official docs state that an explicit ask rule still prompts in
`bypassPermissions`, so approval becomes client-enforced without a new hook.

It is **very likely (80-90%)** that one ask entry resolves the demonstrated path, based on the
vendor's documented ask-over-allow/bypass precedence. A permission-debug matrix must settle exact
wildcard syntax for `git`, `git.exe`, `git -C`, shell chaining, and quoted arguments before deploy.
The rule rides the native permission bus and adds no scaffolding.

Confidence: **very likely (80-90%)** for the supplied settings-derived environment. Evidence is
the contract, broad permission configuration, absent enable key in the complete settings `env`
object, and the shared module's explicit default-off implementation. The band is below “almost
certain” because an external Windows process/user/machine environment variable could enable the

> force-push to main without explicit approval.”

> “## 9. Security non-negotiables (all tools) — ALWAYS ON”  
> — `bundle/claude/AGENTS.md:93`

Settings authority:

> `"Bash",`  
> — `bundle/claude/settings.json:35`

> `"ask": [],`  
> `"defaultMode": "bypassPermissions",`  
> `"additionalDirectories": [`  
> `  "C:",`  
> `  "D:"`  
> `]`  
> — `bundle/claude/settings.json:70-75`

The complete settings environment at `settings.json:4-20` does not set
`HARNESS_LIFECYCLE_GUARD`. The registered shared PreToolUse dispatcher is present at
`settings.json:139-149`, but its implementation says:

> “the irreversible-op (disk-wipe / history-rewrite) REGEX block is OPT-IN and OFF by default in
> interactive sessions”  
> — `bundle/agents/harness/modules.py:65-74`

and gates the blocker on `_lifecycle_guard_enabled()` at
`bundle/agents/harness/modules.py:764-790`. The dormant parser recognizes destructive working-tree
and history operations including `git restore`, checkout-path replacement, stash clear/drop,
forced clean, recursive deletion, and forced/mirror pushes at
`bundle/agents/harness/modules.py:632-723`.

### Concrete collision

Consider a mistaken Bash call such as destructive `git clean -fd`, `git restore`/checkout-path
replacement of uncommitted work, or a force-refspec rewrite. The contract classifies destructive
Git operations as block-worthy. In the supplied configuration, Bash is allowed, there is no ask
rule, bypass mode is active, and the general lifecycle blocker defaults off. The narrow standalone
force-push hook catches only its literal regex subset (Finding 1), not the other operations.

This does not claim every `rm -r` or `git reset --hard` is necessarily irreversible; the shared
module itself deliberately excludes reset-hard at `modules.py:609-612`, and its comments document
prior false positives. The finding is the authority mismatch: the contract says the dangerous
class is a hard boundary while the configured host intentionally relies on model/operator judgment
for most of the class (`modules.py:764-775`).

### Which authority wins at runtime

If `HARNESS_LIFECYCLE_GUARD` is unset, the shared module returns no block and native bypass
permissions execute the call. Thus settings/runtime authority wins after proposal. If an external
environment sets the flag, the hook deny wins over the Bash allow.

Whether that variable is set on the live Windows process is **UNVERIFIED**; the settling experiment
is `Get-ChildItem Env:HARNESS_LIFECYCLE_GUARD`, followed by user- and machine-scope
`[Environment]::GetEnvironmentVariable(...)` checks and a pure `_lifecycle_guard_enabled()` probe
under the launcher environment. Re-running a grep of settings would not be an independent signal.

### Minimal resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Do not simply turn the old broad regex gate back on: its own lines 65-74 record why that produced
false positives. Narrow the existing shared PreToolUse module to a small token-aware list of
genuinely destructive operations with explicit target/scope predicates, enable only that narrowed
lane by default, and leave recoverable or ambiguous operations as additionalContext/ask. Reuse the
existing dispatcher, adapter-native deny shape, and tests.

It is **likely (55-80%)** that a safe narrow set fits below 200 changed lines, because the parser,
module, adapter, and registration already exist; the uncertainty is classification of Windows and
Git syntax, not architecture. Settle it with table-driven positive/negative fixtures drawn from
the module's current patterns and its documented false-positive examples (`grep` containing
`rm -rf`, scratch-directory cleanup, legitimate text mentions). This satisfies the anti-overfit
gate.

## Finding 4 — RE backend availability hard-denies non-dangerous work despite inject-only rule

Severity: **degrading coherence/availability**.  
Confidence: **almost certain (90-99%)** when a matched backend is down/starting/low-RAM, supported
by the registered matcher, JSON defaults, explicit deny branches, and official PreToolUse deny
semantics. No claim is made that a backend was down at artifact time.

### Both authorities, verbatim

Behavior contract:

> “**Exit 0 + additionalContext (inject):** all other guidance (routing, reminders, goal
> injection). Never block on ambiguity; inject a clarifying route instead.”  
> — `bundle/claude/AGENTS.md:64-70`

Settings authority:

> `"matcher": "mcp__ida-pro-mcp__.*|mcp__ghidra-mcp__.*|mcp__binary-ninja-mcp__.*",`  
> ...  
> `"command": "python \"C:/Users/Prekzursil/.claude/hooks/re-autolaunch/autolaunch.py\" pretool",`  
> ...  
> `"statusMessage": "RE tool auto-launch"`  
> — `bundle/claude/settings.json:196-203`

The settings-referenced JSON says:

> `"deny_while_starting": true,`  
> `"deny_when_unlaunchable": true,`  
> — `bundle/claude/hooks/re-autolaunch/backends.json:11-13`

The hook emits `hookSpecificOutput.permissionDecision = "deny"` at
`autolaunch.py:397-408`. It uses the two true defaults at `autolaunch.py:456-457` to deny while a
cold start is pending, when RAM is low, when the launcher fails, and when a backend requires manual
startup (`autolaunch.py:465-539`). The hook itself acknowledges the duplicate-authority issue by
calling these “controlled” denies and suggesting both booleans be false for inject-only behavior
(`autolaunch.py:28-33`). That exception does not exist in the authoritative AGENTS contract.

### Concrete collision

An agent calls a decompiler MCP while its local backend is cold-starting or below the RAM launch
threshold. The action is read/analysis work, not irreversible or dangerous. The contract requires
an actionable injected route. The registered hook instead returns a native deny, preventing the
tool call. Denying a call guaranteed to fail may be operationally reasonable, but that is a policy
exception and therefore belongs in the single behavior authority if retained.

### Which authority wins at runtime

The PreToolUse `permissionDecision: deny` wins and stops the tool call even under the broad MCP/Bash
permission posture. The official permissions documentation explicitly gives a blocking hook
precedence over allow rules. The contract remains advisory context.

Historical firing on the Windows box is **UNVERIFIED** because the corpus hooks section is marked
`DETECTOR_STATUS: BROKEN` and therefore supplies no usable firing data. The settling experiment is
to use the hook's documented `probe` mode, stop or substitute a loopback test backend, redirect its
state directory to a temporary location, feed a synthetic PreToolUse event, and inspect the JSON
decision without invoking the real MCP operation.

### Minimal resolution — CONFIG (settings/JSON only)

Set `deny_while_starting` and `deny_when_unlaunchable` to `false` in the existing
`backends.json`. The same hook then emits actionable `additionalContext` rather than a deny, exactly
matching §6, while preserving probing, on-demand launch, RAM checks, and retry guidance.

It is **almost certain (90-99%)** that these two JSON flips change deny to inject on the named
branches because `_disposition` directly selects `emit_deny` versus `emit_context` from those
booleans (`autolaunch.py:411-412,456-457,481-539`). A synthetic down/starting/manual fixture settles
the final integration detail. This is existing-bus configuration, not new scaffolding.

## Recommended order

1. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** make the force-push
   predicate match the contract's protected-target and approval semantics across valid Git syntax.
2. **CONFIG (settings/JSON only):** add a native `ask` rule for `--no-verify`.
3. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** replace the dormant noisy

4. **CONFIG (settings/JSON only):** flip the two RE-autolaunch deny booleans to inject-only, or—if
   the owner deliberately wants availability precondition denies—make that exception explicit in
   the single AGENTS authority before retaining it.

This order is **likely (55-80%)** to yield the best risk reduction per change: Findings 1-3 affect
permission/safety boundaries, while Finding 4 mainly avoids a policy/availability mismatch. The
evidence is the documented runtime precedence and the direct predicate results; the uncertainty is
real production frequency because hook telemetry is NO DATA. Each change is independently
