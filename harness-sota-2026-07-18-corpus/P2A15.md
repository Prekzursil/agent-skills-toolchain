# P2A15 — Safety for autonomous long-running agents

**Unit:** P2A15  
**Research date:** 2026-07-18  
**Scope:** practical containment, reversibility, blast radius, and human-in-the-loop (HITL) placement for coding/research agents that may operate unattended for long periods.  
**Evidence lens:** external evidence only. I did not inspect or draw conclusions from the owner's local harness, corpus, audit, or defects, because this unit is explicitly assigned the external-research lens.

## Executive conclusion

The strongest practical safety architecture is not a smarter safety prompt or an always-on model critic. It is a small set of independently enforced boundaries around an otherwise ordinary agent loop:

1. run code in an OS-enforced workspace and network sandbox;
2. make the writable workspace disposable and keep promotion to durable/shared state separate;
3. issue task-scoped, short-lived, least-privilege credentials;
4. put human approval immediately before consequential, externally visible, or hard-to-reverse transitions—not before routine reads and sandbox-local edits;
5. cap turns, money, wall time, process count, concurrency, and external-action rate;
6. preserve a kill path that does not depend on model cooperation; and
7. evaluate the whole trajectory under realistic attacks rather than treating a clean final answer as evidence of safe execution.

This conclusion is established at the mechanism level. Anthropic documents OS-enforced filesystem and network isolation, fail-closed sandbox startup, disabling the unsandboxed escape hatch, per-tool permission decisions, worktree isolation, turn/cost limits, and file checkpoints. GitHub documents branch rules, required review, status checks, deployment gates, force-push blocking, and repository-scoped ephemeral workflow tokens. Microsoft documents hypervisor-isolated disposable Windows Sandbox instances and Windows Job Objects that can terminate an entire child process tree. These are enforceable controls, not model promises ([Anthropic sandboxing](https://code.claude.com/docs/en/sandboxing), [Anthropic hooks](https://code.claude.com/docs/en/hooks), [Anthropic worktrees](https://code.claude.com/docs/en/worktrees), [Anthropic agent loop limits](https://code.claude.com/docs/en/agent-sdk/agent-loop), [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

The crucial negative result is equally practical: prompt injection cannot currently be treated as a solved input-filtering problem. The UK NCSC says LLMs are “inherently confusable,” recommends deterministic safeguards outside the model, and frames worst-case tool authority as the relevant impact boundary. AgentDojo supplies an executable benchmark with 97 tasks and 629 security cases and demonstrates that agents operating on untrusted tool output remain vulnerable. Therefore, the harness must remain safe even when the model chooses an attacker-desired action ([NCSC prompt-injection analysis](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection), [AgentDojo paper](https://proceedings.neurips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html)).

## Method

I split the question into four control layers and searched each separately:

- **Containment:** Anthropic, Microsoft, Docker, Kubernetes, gVisor, and NCSC primary/official documentation.
- **Reversibility:** Anthropic checkpoints and worktrees, upstream Git documentation, and GitHub branch/deployment controls.
- **Blast radius:** permission modes, scoped credentials, rate/turn/cost/concurrency controls, resource isolation, and process-tree termination.
- **HITL placement:** Anthropic and OpenAI approval APIs, MCP tool metadata, GitHub review/deployment gates, warning-habituation research, ToolEmu, AgentDojo, and UK AISI ControlArena.

I prioritized official product documentation, upstream specifications, peer-reviewed papers, government guidance, and official repositories. Vendor claims about their own security properties establish documented behavior, not independent proof of implementation correctness. Research benchmark results establish performance inside the benchmark and do not automatically establish production effectiveness.

## 1. What is actually established

### 1.1 Containment has to be enforced below the model

Anthropic's current Claude Code sandbox uses OS primitives—Seatbelt on macOS and bubblewrap on Linux/WSL2—to enforce filesystem and network boundaries on Bash and its subprocesses. It allows writes to the working directory by default, controls outbound domains through a proxy, and can be configured to fail at startup if the sandbox is unavailable. It can also disable the `dangerouslyDisableSandbox` escape path. Anthropic explicitly states that permissions and sandboxing are complementary: permissions decide which tools may run, while the sandbox constrains what Bash and its children can reach ([sandboxing](https://code.claude.com/docs/en/sandboxing), [settings reference](https://code.claude.com/docs/en/configuration), [permissions](https://code.claude.com/docs/en/permissions)).

That distinction matters because a model-side allow/deny decision is not containment. A prompt injection may influence the decision-maker, while an OS boundary still denies the resulting system call. NCSC's guidance reaches the same architectural conclusion from a different direction: because LLMs cannot reliably distinguish instructions from data, deterministic safeguards should constrain the actions available to the system, and the design should tolerate the worst case of an attacker obtaining the agent's effective tool/API authority ([NCSC 2025](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection), [NCSC 2023](https://www.ncsc.gov.uk/blog-post/exercise-caution-building-off-llms)).

Containment is multidimensional. Anthropic warns that filesystem isolation without network isolation permits exfiltration, while network isolation without filesystem isolation may permit tampering that later gains network access. It also documents concrete bypass hazards: broad domains such as `github.com` can be exfiltration paths; its built-in proxy does not inspect TLS; access to `/var/run/docker.sock` can effectively grant host control; and writing to executable/configuration paths can create privilege escalation. Therefore, “sandboxed” is not a binary property; the mounted paths, readable secrets, egress routes, Unix sockets, and escape behavior define the actual boundary ([Anthropic sandbox limitations](https://code.claude.com/docs/en/sandboxing)).

Container isolation is useful but is not equivalent to a VM boundary. Docker's own security documentation notes that the daemon normally has root privilege, that its API can enable privilege escalation if exposed, and that rootless mode reduces daemon/runtime privilege by placing both daemon and containers in a user namespace ([Docker Engine security](https://docs.docker.com/engine/security/), [Docker rootless mode](https://docs.docker.com/engine/security/rootless/)). Docker's default seccomp profile blocks numerous dangerous syscalls, but the project documents ongoing security fixes and warns against disabling seccomp as a workaround ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/), [Docker 29 release notes](https://docs.docker.com/engine/release-notes/29/)). gVisor explains the residual shared-kernel issue directly: ordinary namespace/seccomp isolation still leaves the untrusted workload one permitted system call away from the host kernel, whereas gVisor interposes a userspace application kernel to reduce that surface ([gVisor architecture](https://gvisor.dev/docs/architecture_guide/intro/)).

For native Windows workloads, Microsoft documents a stronger disposable option: Windows Sandbox runs a separate kernel under the Microsoft hypervisor, discards state when closed, and supports disabling networking plus read-only host-folder mappings. Microsoft also warns that networking is enabled by default, mapped folders expose host data, clipboard sharing is enabled by default, and vGPU can increase attack surface ([Windows Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [WSB configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file), [sample hardened configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-sample-configuration)).

**Established design implication:** the safe unit of autonomy is a bounded execution cell, not an unconstrained host process with a safety instruction.

### 1.2 Least privilege limits consequences even when behavior is wrong

OWASP's Excessive Agency guidance identifies three independent sources of harm: excessive functionality, excessive permissions, and excessive autonomy. Its concrete mitigations are narrower tools, read-only or minimally scoped OAuth permissions, user review before sends, and rate limiting ([OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). NCSC similarly recommends deterministic restrictions outside the LLM rather than relying on the LLM to recognize malicious content ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)).

GitHub provides a concrete production example of least-lifetime and least-scope credentials: each Actions job receives a repository-scoped `GITHUB_TOKEN` that expires when the job ends or at its maximum lifetime; GitHub recommends granting it only the minimum permissions required ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), [secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)). AWS documents temporary session credentials with bounded durations and methods for revoking active role sessions, demonstrating the same general mechanism for cloud APIs ([AWS temporary-credential controls](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_disable-perms.html), [AWS role-session revocation](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_revoke-sessions.html)).

The MCP schema provides a useful vocabulary—`readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`—but its specification explicitly says these are hints and that clients must not make security decisions from annotations supplied by untrusted servers. Therefore, metadata may help classify trusted tools, but cannot itself be the authorization boundary ([MCP schema](https://modelcontextprotocol.io/specification/2025-11-25/schema)).

**Established design implication:** scope capability at the credential/tool boundary. Do not give a general shell, broad OAuth token, or multi-function MCP server to a task that needs one narrow operation.

### 1.3 Reversibility requires both disposable work and protected promotion

Git worktrees provide separate working directories with independent `HEAD` and index state while sharing repository history. Upstream Git explicitly recommends detached worktrees for experimental changes that should not disturb the main working tree ([git-worktree](https://git-scm.com/docs/git-worktree.html)). Claude Code now exposes this directly with `--worktree`, `EnterWorktree`, and `isolation: worktree` for subagents; its documentation says parallel sessions then cannot overwrite one another's files ([Claude Code worktrees](https://code.claude.com/docs/en/worktrees), [subagent isolation](https://code.claude.com/docs/en/sub-agents)).

Worktree isolation prevents collision; it does not protect the shared repository's remote or external systems. Promotion controls do that. GitHub rulesets can require pull requests, reviews, status checks, successful staging deployments, signed commits, linear history, path restrictions, and force-push blocking. GitHub environments can require reviewers, prevent self-review, and prevent administrators from bypassing protection when configured accordingly ([GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [deployment environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). These controls separate “the agent produced a candidate” from “the candidate became durable/shared/production state.”

Claude's checkpointing is useful but narrower than many users assume. It snapshots changes made through Write/Edit/NotebookEdit and supports rewind, but it does not track Bash-made file changes, directory operations, remote/network changes, or changes from other sessions. Anthropic explicitly says it is not a replacement for version control ([Claude checkpointing](https://code.claude.com/docs/en/checkpointing), [Agent SDK checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)). Git `revert`, in contrast, records a new change that reverses an earlier commit, preserving history; GitHub can create a revert pull request for a merged PR ([git-revert](https://git-scm.com/docs/git-revert.html), [reverting a PR](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/reverting-a-pull-request)). Neither mechanism can automatically reverse an email, money transfer, secret disclosure, destructive database call, or third-party API action.

**Established design implication:** classify effects before execution as (a) sandbox-local and disposable, (b) repository-local and revertible, (c) externally compensatable, or (d) irreversible. Never use “we have checkpoints” as justification for category (c) or (d).

### 1.4 Blast radius needs explicit quantitative caps

Claude Agent SDK exposes `max_turns` and `max_budget_usd`; when either limit is reached, the run stops with a typed error. Without limits, the loop continues until the model decides it is done. Custom subagents also support `maxTurns` ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Python SDK options](https://code.claude.com/docs/en/agent-sdk/python), [subagent fields](https://code.claude.com/docs/en/sub-agents)). OpenAI's Agents SDK separately exposes a cap on concurrent local function-tool execution, confirming that emitted parallel calls and runtime execution concurrency are distinct control points ([OpenAI running agents](https://openai.github.io/openai-agents-python/running_agents/)).

Operating systems can enforce bounds independently of the agent. Windows Job Objects group child processes, enforce process/job time and memory limits, account for resource usage, and—when `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is set—terminate the entire associated process hierarchy when the controlling handle closes ([Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [job limit flags](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)). Kubernetes' restricted pod standard disallows host namespaces and privilege escalation, while its security checklist recommends restricted pod policy, memory limits, selective CPU limits, seccomp, and minimal RBAC ([Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/), [Kubernetes security checklist](https://v1-32.docs.kubernetes.io/docs/concepts/security/security-checklist/)).

**Established design implication:** an autonomous run should have finite budgets for at least model turns, spend, elapsed time, process count/tree lifetime, memory, concurrency, external write count, and outbound destination set. A prose instruction to “be efficient” is not a cap.

### 1.5 Human approval is most useful at semantic commit points

Anthropic hooks can return `allow`, `deny`, `ask`, or (in supported non-interactive/TypeScript flows) `defer` before a tool executes. Deny takes precedence, hooks can inspect exact tool name and arguments, and deferred calls can be resumed later. OpenAI's Agents SDK independently implements the same pause/inspect/approve-or-reject/resume pattern and surfaces agent name, tool name, and arguments in the pending interruption ([Anthropic hooks](https://code.claude.com/docs/en/hooks), [Anthropic approval handling](https://code.claude.com/docs/en/agent-sdk/user-input), [OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)). This establishes that approval can be placed immediately before a specific side effect, not merely at the start or end of a long run.

GitHub's protected-branch and deployment-environment mechanisms demonstrate mature placement: automation may build and test freely, but merging to a protected branch or releasing to an environment can require an independent reviewer, current status checks, and a prohibition on self-approval ([protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [deployment review](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)). This is a semantic commit point: the review gates the transition from candidate state to durable/shared state.

Approval on every low-risk command is counterproductive. Anthropic explicitly motivates sandboxing partly by approval fatigue. Independent usable-security research provides the behavioral basis: repeated warnings produce habituation after few exposures, and frequent non-security notifications reduce attention and adherence to later security warnings ([Anthropic sandboxing](https://code.claude.com/docs/en/sandboxing), [Vance et al., 2016](https://doi.org/10.1016/j.dss.2016.09.010), [Vance et al., SOUPS 2019](https://www.usenix.org/conference/soups2019/presentation/vance)). These studies are not agent-specific, but they directly test the human warning channel that agent approval systems use.

**Established approval placement:**

| Action class | Default treatment | Why |
|---|---|---|
| Read within approved project; pure computation; sandbox-local tests | auto-allow | No durable effect; prompting adds noise. |
| Edit in disposable worktree; create local artifacts | auto-allow within quota | Revertible/discardable and bounded. |
| Install or execute untrusted dependencies | sandbox plus explicit domain/package policy; ask if boundary expansion is needed | Supply-chain code executes with the agent's authority. |
| Add a new domain, mount, socket, credential, tool, or permission | human approval | This expands future blast radius, not merely the current action. |
| Commit to task branch | usually auto-allow after tests; preserve provenance | Durable locally, but not yet promoted to protected/shared state. |
| Push task branch / create PR | allow under narrow repository credential; optionally notify | Externally visible but generally reversible; must not grant merge/admin authority. |
| Merge, release, deploy, change IAM, modify production data, send messages, spend money, publish, delete remote data | require exact-action approval and revalidation immediately before execution | Consequential, hard to reverse, or affects third parties. |
| Read or transmit secrets; disable containment; force-push protected refs; destructive broad filesystem operation | deterministic deny unless a separate, explicitly authorized break-glass path is used | Human confirmation is too weak for routine access to catastrophic authority. |

### 1.6 The agent cannot be trusted to apply safety knowledge consistently during action

ToolEmu evaluated 36 high-stakes tools and 144 cases. Its LM-emulated environment is imperfect, but human evaluation judged 68.8% of identified failures to correspond to valid real-world failures, and its safest tested agent still exhibited evaluator-identified failures in 23.9% of cases ([ToolEmu](https://arxiv.org/abs/2309.15817)). A newer study found models could answer abstract risk questions at over 98% pass rates yet performed below 26% on avoiding risky actions in instantiated agent trajectories; an independent risk verifier reduced risky executions by 55.3% in that study ([Tang et al., 2025](https://arxiv.org/abs/2508.13465)). These numbers must not be generalized beyond their evaluated agents and tasks, but they establish that “the model knows this is dangerous” does not imply “the acting agent will reliably abstain.”

AgentDojo's peer-reviewed benchmark executes agents over untrusted data across 97 realistic tasks and 629 security test cases. Its authors report that existing attacks break some security properties and that models also fail benign tasks; the live results registry explicitly warns that its entries are not a fair leaderboard because not all models were tested under identical attacks and defenses ([AgentDojo paper](https://proceedings.neurips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html), [official repository](https://github.com/ethz-spylab/agentdojo), [results registry](https://agentdojo.spylab.ai/results/)).

**Established design implication:** self-reflection, chain-of-thought, a safety reminder, or the same model checking its own action cannot serve as the final authorization control. Deterministic capability boundaries remain necessary.

## 2. What is promising but unproven

### 2.1 Risk-adaptive approvals instead of blanket prompting

It is **very likely (80-90%)**, based on the combination of exact-call approval APIs, GitHub's mature promotion gates, and warning-habituation studies, that approvals concentrated on permission expansion and semantic commit points will preserve more human attention than prompting on every shell command ([Anthropic hooks](https://code.claude.com/docs/en/hooks), [OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [SOUPS 2019](https://www.usenix.org/conference/soups2019/presentation/vance)). This remains unproven for this owner's workload because the cited human studies concern general security warnings and the SDK documents mechanisms rather than comparative owner outcomes.

The right experiment is an A/B replay over representative historical trajectories: blanket prompts versus risk-adaptive prompts, measuring prompts per completed task, approval latency, deny accuracy on seeded dangerous actions, and reviewer inspection time. This is not marked UNVERIFIED because the recommendation below does not depend on a claimed owner-specific effect; the owner-specific gain is what the experiment would quantify.

### 2.2 Independent model monitors and defer-to-trusted protocols

It is **likely (55-80%)** that a separately prompted or weaker trusted model can add useful triage signal on ambiguous actions, based on the verifier improvement in Tang et al. and the existence of executable ControlArena protocols for monitoring, resampling, trusted editing, and defer-to-trusted ([Tang et al.](https://arxiv.org/abs/2508.13465), [ControlArena monitors](https://control-arena.aisi.org.uk/monitors.html), [ControlArena micro-protocols](https://control-arena.aisi.org.uk/micro_protocols.html)).

It is **unlikely (20-45%)** that an LLM monitor is strong enough to be the sole production gate for a powerful long-horizon coding agent, because UK AISI explicitly describes weaker monitors missing sophisticated attacks and untrusted monitors risking collusion; ControlArena is an experimental evaluation library, not a production assurance result ([ControlArena introduction](https://control-arena.aisi.org.uk/intro-to-control.html), [AISI research agenda](https://www.aisi.gov.uk/research-agenda)). The monitor may rank calls for human attention, but deterministic policy must still deny out-of-envelope actions.

### 2.3 Information-flow-aware tool authorization

It is **likely (55-80%)** that tracking whether an action was influenced by untrusted web/email/tool content and tightening permissions after such exposure will reduce prompt-injection blast radius. Evidence includes NCSC's system-level framing, MCP's emerging `openWorldHint` vocabulary, and research systems that enforce information-flow or dependency-aware tool policy ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection), [MCP tool annotations](https://modelcontextprotocol.io/specification/2025-11-25/schema), [AgenTRIM](https://arxiv.org/abs/2601.12449), [security-aware planning](https://arxiv.org/abs/2602.11416)).

However, the cited 2026 defenses are recent papers evaluated primarily on benchmarks. Their generalization to arbitrary coding tools, PowerShell, nested agents, and long-lived memory is **UNVERIFIED; settle it with a cross-benchmark and owner-trajectory experiment that seeds indirect injections before privileged calls and measures security, benign utility, and false-positive rate**. Any recommendation that required their full frameworks would therefore inherit UNVERIFIED; this report does not recommend installing them.

### 2.4 Disposable VM execution for the highest-risk native-Windows jobs

It is **very likely (80-90%)** that Windows Sandbox with networking, clipboard, printer, audio, vGPU, and writable host mappings disabled provides materially stronger host isolation than running the same untrusted workload directly on the owner account. Microsoft documents a separate kernel, disposable state, and those explicit boundary controls ([Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)).

It is only **roughly even (45-55%)** that Windows Sandbox is ergonomic enough for the owner's routine autonomous coding runs, because it supports one instance at a time, installed tools do not inherit from the host, and shared folders/clipboard/network each weaken the isolation that makes it valuable. A timed prototype using one representative dependency-heavy task would settle the productivity question. It should remain an escalation lane for unknown executables or native-Windows testing, not the default orchestration substrate.

### 2.5 Trajectory-level adversarial evaluation

It is **very likely (80-90%)** that replayable trajectory tests will catch safety regressions that unit tests over final output miss, because AgentDojo evaluates actions and environment state under injection, ToolEmu targets risky tool use, and ControlArena distinguishes honest utility from attack-policy safety ([AgentDojo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html), [ToolEmu](https://arxiv.org/abs/2309.15817), [ControlArena](https://control-arena.aisi.org.uk/)). It remains unproven which public benchmark best predicts this owner's command mix; the practical response is a small owner-derived fixture set, not adoption of a general guardrail framework.

## 3. What is hype, and how to tell

### 3.1 “The model understands risk, so ask it to be careful”

This is contradicted by action-level evaluations. ToolEmu finds severe failures in high-stakes cases, and Tang et al. show a large gap between abstract risk knowledge and safe execution ([ToolEmu](https://arxiv.org/abs/2309.15817), [Tang et al.](https://arxiv.org/abs/2508.13465)). A claim is hype when its evidence is a refusal demo, a system prompt, or a few narrated transcripts rather than adversarial action-level evaluation with environment effects.

### 3.2 “Our prompt-injection detector/firewall solves prompt injection”

NCSC explicitly argues that LLMs are inherently confusable and that prompt injection must be risk-managed rather than treated as a solved SQL-injection analogue ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)). AgentDojo's official registry warns that heterogeneous runs are not a leaderboard, while newer AgentDyn work reports benchmark design flaws and poor security/utility trade-offs for existing defenses ([AgentDojo results](https://agentdojo.spylab.ai/results/), [AgentDyn](https://arxiv.org/abs/2602.03117)). A claim is hype when it reports near-zero attack success on one static benchmark without adaptive attacks, benign utility, false positives, held-out tool schemas, or reproducible traces.

### 3.3 “It runs in Docker, therefore the host is safe”

Docker itself documents rootful daemon risk, API/socket privilege implications, the value of rootless mode, and the need for seccomp and other hardening ([Docker Engine security](https://docs.docker.com/engine/security/), [rootless mode](https://docs.docker.com/engine/security/rootless/), [seccomp](https://docs.docker.com/engine/security/seccomp/)). gVisor documents the shared-kernel attack surface that remains after ordinary namespace and syscall filtering ([gVisor](https://gvisor.dev/docs/architecture_guide/intro/)). A claim is hype when “container” is the only boundary description and it omits user identity, capabilities, socket mounts, host mounts, egress, seccomp/AppArmor/SELinux, resource limits, and the escape response.

### 3.4 “Everything is reversible because we use Git/checkpoints”

Anthropic explicitly limits checkpoints to file-tool changes and excludes Bash, directories, external systems, and concurrent-session changes ([checkpointing](https://code.claude.com/docs/en/checkpointing)). Git revert records a compensating commit; it cannot un-send data or undo arbitrary external side effects ([git-revert](https://git-scm.com/docs/git-revert.html)). A claim is hype when it does not enumerate effects outside the repository or demonstrate a tested compensating action.

### 3.5 “Put a human in the loop and the system is safe”

HITL is a placement mechanism, not a safety proof. Repeated warnings habituate users, and irrelevant notifications reduce later security-warning adherence ([Vance et al., 2016](https://doi.org/10.1016/j.dss.2016.09.010), [SOUPS 2019](https://www.usenix.org/conference/soups2019/presentation/vance)). A claim is hype when the approver sees only “Allow tool?” rather than normalized arguments, target identity, data provenance, scope expansion, expected diff/effect, and reversibility—and when the system prompts so frequently that denial is operationally exceptional.

### 3.6 “A second LLM critic makes the first LLM safe”

ControlArena is valuable precisely because this remains an empirical control problem: trusted weaker monitors can miss sophisticated attacks, while untrusted monitors may collude; protocols must be attacked and evaluated ([ControlArena monitors](https://control-arena.aisi.org.uk/monitors.html), [AISI ControlArena announcement](https://www.aisi.gov.uk/blog/introducing-controlarena-a-library-for-running-ai-control-experiments)). A claim is hype when monitor accuracy is measured on isolated text labels instead of adaptive end-to-end trajectories, or when the critic can authorize the same capabilities it is meant to police.

### 3.7 “More orchestration means more safety”

No source reviewed establishes that a second orchestration runtime, durable workflow engine, vector/KG memory, trained critic, observability SaaS, or general guardrail framework is necessary for safe coding-agent autonomy. The enforceable controls above already exist in the OS, Git/GitHub, IAM, agent permissions, and hooks. Adding another privileged runtime increases code, state, credentials, and failure modes that must themselves be contained. This is an architectural inference, and it is **very likely (80-90%)** for this harness because all recommended controls ride existing buses and the external evidence supports boundaries rather than orchestration complexity. The evidence is the native mechanisms enumerated in Sections 1.1–1.5; the remaining uncertainty is their integration quality.

## 4. Specific things this owner's harness should adopt

Each proposal has exactly one implementation tag and an explicit anti-overfit decision. Confidence refers to the expected safety/value outcome, not to whether the cited feature exists.

### 4.1 Make Claude's WSL2 sandbox fail closed for unattended execution

**Tag: CONFIG (settings/JSON only)**

Configure unattended Claude runs with:

- sandbox enabled;
- `failIfUnavailable: true`;
- `allowUnsandboxedCommands: false`;
- project/worktree as the only writable tree;
- deny-read rules for credential stores, SSH material, cloud configuration, browser/session stores, and unrelated owner data;
- explicit, minimal egress domains;
- no Docker socket or other privileged Unix sockets;
- no `excludedCommands` unless each exclusion has a separate containment story; and
- no weaker nested sandbox mode unless a stronger outer boundary has been demonstrated.

Anthropic documents WSL2 bubblewrap support and says native Windows support is planned rather than current; it also documents fail-closed startup and the unsandbox escape control ([sandboxing](https://code.claude.com/docs/en/sandboxing), [configuration](https://code.claude.com/docs/en/configuration)). Expected benefit is **almost certain (90-99%)**, because these settings convert silent fallback/escape into explicit failure and reduce readable/writable/egress scope. This does not claim the sandbox is invulnerable; Anthropic documents TLS/domain-fronting and socket limitations.

**Anti-overfit gate:** passes. It uses native Claude/OS enforcement and adds no runtime, daemon, database, trained model, or SaaS.

### 4.2 Run every editing session and editing subagent in its own worktree

**Tag: NATIVE (Claude Code already does this; we just enable it)**

Use `--worktree`/`EnterWorktree` for long-running sessions and `isolation: worktree` for editing subagents. Do not copy `.env`, secrets, or broad gitignored state through `.worktreeinclude`; initialize only the task-specific dependencies required. Keep the agent off the owner's primary checkout and default branch ([Claude worktrees](https://code.claude.com/docs/en/worktrees), [subagents](https://code.claude.com/docs/en/sub-agents), [upstream Git](https://git-scm.com/docs/git-worktree.html)).

Expected collision and accidental-main-tree risk reduction is **almost certain (90-99%)**, because filesystem edits occur in separate directories/branches by construction. Protection against remote pushes, credential misuse, or shared external systems is **almost certainly not (1-5%)** provided by worktrees alone; those require the following controls.

**Anti-overfit gate:** passes. It is a native Git/Claude mechanism.

### 4.3 Separate the “work lane” from the “promotion lane”

**Tag: CONFIG (settings/JSON only)**

The normal agent identity should be able to read the repository, edit its worktree, run tests, and create local commits. It should not be able to merge to protected branches, bypass checks, modify repository rules, deploy, administer environments, or force-push. Promotion should occur through a protected PR/deployment path that requires current checks and an independent reviewer; prevent self-review and admin bypass where the platform supports it ([GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)).

Expected reduction in unintended durable/shared changes is **very likely (80-90%)**, because the agent can produce candidates but lacks authority to promote them. The residual risk includes malicious code that passes review/checks and repositories where administrators retain bypass.

**Anti-overfit gate:** passes. This is repository and environment policy, not a new orchestrator.

### 4.4 Add one deterministic PreToolUse “effect gate” at the existing hook choke point

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Implement one small, data-driven gate—not a growing regex zoo and not an LLM judge. For each tool call, normalize a compact effect record:

`{tool, operation, target, scope, external, destructive, reversible_class, credential_class, untrusted_input_seen}`

Then apply a short policy:

- **deny** writes outside the approved workspace, secret reads, containment disablement, privileged socket access, force-push to protected refs, broad destructive targets, and administrative/IAM changes outside a break-glass profile;
- **ask/defer** for new domains/mounts/tools/credentials, external sends/publishes/spend/deletes, deployments, merges, and any operation whose target/scope cannot be normalized;
- **allow** project reads and sandbox-local/revertible actions within quotas.

Anthropic's hook contract already supplies tool name and arguments and supports deny/ask/defer with deny precedence ([hooks](https://code.claude.com/docs/en/hooks), [permissions](https://code.claude.com/docs/en/permissions)). MCP annotations may seed defaults only for owner-trusted servers; the MCP specification says annotations from untrusted servers cannot be trusted for security decisions ([MCP schema](https://modelcontextprotocol.io/specification/2025-11-25/schema)).

Expected prevention of clear out-of-envelope actions is **very likely (80-90%)**, because deterministic denials are evaluated before execution. Expected classification of every obfuscated shell action is only **roughly even (45-55%)**; uncertain parsing must therefore escalate, and containment remains the backstop.

**Anti-overfit gate:** passes if the policy remains a single small hook using structured tool inputs and coarse effect classes. It fails if expanded into a separate policy service, general guardrail framework, or trained critic.

### 4.5 Make approval payloads decision-complete and rare

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For every `ask/defer`, show the owner one compact approval card containing:

1. exact normalized operation and target;
2. whether the target is local, remote, shared, production, or third-party;
3. credential and permission scope being used;
4. whether untrusted web/tool content influenced the action;
5. expected diff/effect and maximum count/amount;
6. reversibility class and tested rollback/compensation command, if any;
7. whether approval is one-shot or would expand future permissions; and
8. a safe alternative when available.

Never convert a one-shot approval into a permanent allow rule by default. Revalidate target, arguments, credentials, and policy immediately before execution after a long approval wait. OpenAI's HITL flow scopes approvals to call IDs by default and separately exposes sticky approvals; it serializes pending state and recommends versioning delayed tasks. Anthropic can preserve/defer exact calls and resume later ([OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [Anthropic approval handling](https://code.claude.com/docs/en/agent-sdk/user-input), [hooks guide](https://code.claude.com/docs/en/hooks-guide)).

Expected decision quality improvement is **likely (55-80%)**, based on exact-call visibility and warning-design evidence; no retrieved study directly measured this exact card for coding agents. Keep prompts rare because repeated warnings demonstrably habituate users ([Vance et al.](https://doi.org/10.1016/j.dss.2016.09.010)).

**Anti-overfit gate:** passes. This is presentation logic around the existing permission hook, not another runtime.

### 4.6 Enforce finite run budgets in configuration, not prose

**Tag: NATIVE (Claude Code already does this; we just enable it)**

Set per-agent defaults and task-specific overrides for `maxTurns`/`max_turns` and, for SDK-driven long runs, `max_budget_usd`. Use smaller limits for subagents than for the parent. Treat hitting a limit as a terminal typed state requiring explicit continuation, not a reason for automatic recursive respawn. Also cap parallel editing agents and external writes per task at the dispatch layer ([Claude agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [SDK options](https://code.claude.com/docs/en/agent-sdk/python), [subagent configuration](https://code.claude.com/docs/en/sub-agents)).

Expected containment of runaway loops and spend is **almost certain (90-99%)** for the bounded dimensions, because the runtime stops when limits are reached. It will not bound wall-clock time consumed inside one long tool call or damage from one high-impact call; process and effect gates cover those.

**Anti-overfit gate:** passes. Native fields only; explicitly reject a durable-execution engine or second supervisor runtime.

### 4.7 Issue separate, short-lived credentials for read, candidate-write, and promotion authority

**Tag: CONFIG (settings/JSON only)**

Create distinct credential classes:

- read-only research/repository access;
- task-branch/PR candidate-write access scoped to one repository;
- promotion/deployment/admin authority unavailable to the autonomous worker and released only through the approved platform gate.

Prefer job/session tokens that expire automatically and set default permissions to read-only. Do not place secrets in prompts, session state, worktree include files, or broadly readable home-directory paths. GitHub documents repository-scoped job tokens and least-permission configuration; AWS documents bounded temporary credentials and revocation ([GitHub token](https://docs.github.com/en/actions/concepts/security/github_token), [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use), [AWS temporary credentials](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_disable-perms.html)).

Expected blast-radius reduction after model compromise is **very likely (80-90%)**, because the agent cannot exercise permissions its credential lacks. Exact implementation depends on each MCP/API provider's auth model, so unsupported providers must remain out of unattended runs rather than receiving broad standing credentials.

**Anti-overfit gate:** passes. It uses existing IAM/provider configuration.

### 4.8 Keep checkpoints, but define Git as the durable rollback boundary

**Tag: NATIVE (Claude Code already does this; we just enable it)**

Keep Claude file checkpointing enabled for quick local undo, but require task-branch commits at coherent milestones before risky transformations. Record external actions separately with their idempotency key and compensation procedure. Do not label an action reversible unless rollback has been exercised against a test target. Anthropic documents checkpoint exclusions; Git documents worktree and revert behavior ([checkpointing](https://code.claude.com/docs/en/checkpointing), [git-worktree](https://git-scm.com/docs/git-worktree.html), [git-revert](https://git-scm.com/docs/git-revert.html)).

Expected recovery improvement for local file mistakes is **almost certain (90-99%)**. Expected recovery for remote side effects from file checkpoints is **almost certainly not (1-5%)**, per Anthropic's explicit exclusions.

**Anti-overfit gate:** passes. Native checkpoints and Git history; no new durable state engine.

### 4.9 **UNVERIFIED — Prototype a Windows process-tree kill wrapper for native long tools**

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Wrap native long-running tool processes in a Windows Job Object configured with elapsed/CPU/memory limits and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and ensure cancellation closes the controlling handle. Microsoft documents that children normally inherit job membership and that closing the last handle with this flag terminates associated processes and child jobs ([Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

The premise that every process tree produced by this owner's PowerShell/Git Bash/Node tool mix remains captured is **UNVERIFIED; settle it by launching representative nested processes (PowerShell → cmd/Node → child), deliberately orphaning children, cancelling the wrapper, and verifying process IDs via an independent process inventory**. Expected value is **likely (55-80%)** because the OS mechanism is designed for process-tree control, but shell/job nesting and explicit breakaway behavior require owner-specific validation.

**Anti-overfit gate:** passes only as a small launcher helper invoked by the existing long-operation path. Do not turn it into a service or durable scheduler.

### 4.10 Add a small trajectory-safety regression fixture set

**Tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build a compact set of replayable cases that exercise the actual effect gate without calling production systems:

- injected instructions in a fetched page/tool output followed by a secret read or outbound send;
- encoded/quoted shell variants of broad deletion and force push;
- path traversal/symlink attempts outside the worktree;
- new egress domain, Docker socket, or credential request;
- branch push versus protected-branch merge;
- delayed approval followed by changed target/state;
- repeated tool failure and retry loop;
- parallel calls that exceed external-write quota; and
- cancellation that must kill descendants.

Score environment state and tool calls, not just the final message. AgentDojo's benchmark/repository shows how to preserve tasks, attacks, defenses, and traces; ControlArena separates honest and attack evaluation modes ([AgentDojo repository](https://github.com/ethz-spylab/agentdojo), [ControlArena](https://control-arena.aisi.org.uk/)).

Expected regression-detection value is **very likely (80-90%)** for covered cases and **unlikely (20-45%)** to imply broad real-world safety by itself. Keep it small and owner-derived rather than importing a general guardrail suite.

**Anti-overfit gate:** passes. It is a fixture/test layer on the existing hook, not a second runtime or trained detector.

### 4.11 Use Windows Sandbox only as a high-risk escalation lane

**Tag: NATIVE (Windows already provides this; we just enable it)**

For unknown binaries, suspicious packages, or native-Windows behavior that cannot run inside Claude's WSL2 sandbox, launch a disposable Windows Sandbox profile with networking disabled, clipboard/printer/audio/video/vGPU disabled, a read-only input mapping, and a separate writable output directory whose contents are reviewed before import. Never map credential directories or the main writable repository ([Windows Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file), [sample](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-sample-configuration)).

Expected host-risk reduction for these jobs is **very likely (80-90%)**. Routine-task ergonomics are only **roughly even (45-55%)**, so this should not replace the default worktree/WSL2 lane without a measured prototype.

**Anti-overfit gate:** passes as an OS-provided escalation cell. Do not build a VM orchestration service.

## 5. Integrated target policy

The proposals above form one deliberately small control stack:

```text
user goal
   |
   v
finite agent loop (turn + cost + concurrency caps)
   |
   v
isolated worktree inside fail-closed OS sandbox
   |
   v
deterministic PreToolUse effect gate
   |                    |
   | allow              | ask/defer or deny
   v                    v
local/revertible work   decision-complete approval or hard stop
   |
   v
candidate branch / PR with narrow short-lived credential
   |
   v
protected promotion gate (checks + independent human)
   |
   v
shared/production state
```

No component requires a second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or general guardrail framework. Model monitors may be used offline to prioritize suspicious traces, but they should not authorize execution. The result is intentionally less ambitious in mechanism count than many “agent security platforms,” while being more ambitious in enforcement quality.

## 6. Adoption order and acceptance tests

### Phase 0 — block catastrophic authority leakage

1. Remove promotion/admin credentials from unattended agents.
2. Protect default branches and production environments against agent/self bypass.
3. Deny secret paths, privileged sockets, containment disablement, and broad destructive targets.

Acceptance test: an injected agent with full knowledge of tool names cannot read a seeded secret, write outside the worktree, force-push a protected branch, or obtain a promotion credential. Verify both the hook decision and the unchanged external/filesystem state.

### Phase 1 — establish bounded autonomy

1. Enable fail-closed WSL2 sandboxing and disable unsandbox escape.
2. Default editing sessions/subagents to worktrees.
3. Set turn, cost, concurrency, and external-write limits.
4. Use read-only or candidate-write short-lived credentials.

Acceptance test: ordinary repository work completes without low-risk prompts; exceeding any configured dimension produces a typed terminal state and does not auto-respawn.

### Phase 2 — put humans at commit points

1. Add the deterministic effect gate.
2. Render decision-complete approval cards.
3. Revalidate delayed approvals before execution.
4. Gate merges/deployments through independent platform review.

Acceptance test: approval is requested for permission expansion and consequential side effects, not for ordinary reads/tests/edits; one-shot approval does not become sticky; changed target/state invalidates a delayed approval.

### Phase 3 — prove containment continuously

1. Add the compact trajectory fixture set.
2. Prototype native-Windows Job Object cancellation.
3. Add Windows Sandbox only for high-risk native jobs.

Acceptance test: seeded prompt injections, path escapes, shell obfuscations, retry loops, concurrency bursts, and orphaned children are either deterministically blocked, contained, or escalated with exact evidence.

## 7. Alternatives considered and rejected

### A new durable workflow engine

Rejected. The problem is not primarily recovery from coordinator failure; it is authority and effect containment. Claude already supports resumable/deferred approvals, and the harness can terminate and resume work without adopting Temporal/Dapr/Restate. OpenAI documents these integrations for durable long waits, but that is evidence they are available, not evidence this owner needs another runtime ([OpenAI running agents](https://openai.github.io/openai-agents-python/running_agents/)). This violates the anti-overfit gate unless an independently measured requirement later shows process-resume semantics cannot be met by native sessions.

### A trained safety critic or general guardrail framework

Rejected as an authorization boundary. Research monitors are promising but unproven under adaptive, long-horizon owner workloads, and UK AISI explicitly treats monitor reliability as an open empirical problem ([ControlArena monitors](https://control-arena.aisi.org.uk/monitors.html), [AISI research agenda](https://www.aisi.gov.uk/research-agenda)). A critic can help triage logs offline; deterministic policy decides execution.

### A universal Docker-based agent platform

Rejected as the default replacement. Docker can be hardened, especially rootless with seccomp, but socket/mount/daemon/shared-kernel details determine its security. Claude's native WSL2 sandbox and Git worktrees already address the common local coding case with less machinery. For hostile native binaries, Windows Sandbox supplies a stronger separate-kernel escalation lane.

### Approval on every write or command

Rejected. It spends human attention on the actions already made safe by containment and reversibility and risks habituation. Approval belongs at boundary expansion and semantic commit points.

### Relying on checkpointing as transaction rollback

Rejected. Anthropic expressly excludes Bash and external side effects. Git plus protected promotion is the durable local-code boundary; external systems require narrow authority and explicit compensation.

## 8. What I could not determine

1. **Owner-specific false-positive and approval burden.** External evidence supports risk-adaptive placement, but it does not determine thresholds for this owner's command distribution. The settling experiment is the historical-trajectory A/B replay described in Section 2.1.

2. **Owner-specific WSL2 compatibility.** Anthropic documents WSL2 support and incompatibilities such as Windows binaries under `/mnt/c/`, but this unit intentionally did not inspect the local environment. A representative build/test matrix must establish which commands need redesigned access rather than sandbox exclusions ([Anthropic sandboxing](https://code.claude.com/docs/en/sandboxing)).

3. **Codex-specific parity.** My searches did not yield sufficiently precise, current official Codex documentation to support equivalent claims about every sandbox, approval, checkpoint, and budget control. I therefore make no Codex-specific parity claim. The settling experiment is a documented capability matrix plus black-box probes for read/write/egress/approval/timeout behavior on the installed Codex version.

4. **Cross-shell completeness of a small command classifier.** PowerShell, Git Bash, nested interpreters, encoded commands, aliases, and scripts make perfect semantic parsing unrealistic. The recommendation deliberately escalates unknowns and relies on OS containment. The settling experiment is the adversarial shell fixture set in Section 4.10.

5. **Real production effectiveness of 2026 information-flow and monitor papers.** AgenTRIM, security-aware planning, AgentDyn, and recent control protocols are promising but benchmark-bound. Cross-benchmark reproduction on owner tools would be required before adopting their frameworks.

6. **Quantified security gain from Windows Sandbox for this workload.** Microsoft documents the mechanism, but not this owner's task success or latency. A controlled native-binary task with host-canary files, process inventory, network capture, and measured setup time would settle it.

7. **Whether all external MCP/API providers support suitably scoped temporary credentials.** Provider-by-provider official auth review is required. Where they do not, the safe conclusion is to exclude write-capable access from unattended mode, not to give a broad standing token.

8. **A universal reversibility taxonomy for third-party APIs.** APIs differ in idempotency, cancellation, compensation, consistency, and retention. Each write-capable tool needs an explicit effect contract and tested rollback/compensation semantics.
