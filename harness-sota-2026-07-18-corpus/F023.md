# F023 — Frontier research: codebase-scale understanding, repository maps, and symbol graphs

**Research date:** 2026-07-19  
**Unit:** F023  
**Scope:** What is established, what remains experimental, and what this owner's agent harness should adopt. This is research and design only; the subject harness was kept read-only.

## Bottom line

The strongest evidence supports a deliberately small stack: a compact, token-budgeted repository map for orientation; native language-server operations for definitions, references, types, implementations, diagnostics, and call hierarchy; ordinary lexical search as the universal fallback; and progressive, task-conditioned expansion of context. These are complementary instruments, not a single magical “codebase understanding” layer.

The evidence does **not** support adding a graph database, vector database, knowledge graph, or second navigation runtime to this harness. Graph-guided research systems have produced real benchmark gains, but the gains are generally modest end-to-end, concentrated in Python and SWE-bench-family evaluations, and coupled to indexing, token, workflow, and freshness costs. The best immediate move is to enable the code-intelligence machinery Claude Code already supplies, repair the harness's contradictory routing, and evaluate a compact map on the owner's own historical tasks before building anything larger.

This conclusion is unusually well aligned with the anti-overfit gate: the useful frontier ideas can ride the existing LSP, hook, skill, and shell buses. A graph database would reintroduce a specifically rejected component and is not justified by the evidence reviewed here.

## Method, evidence standard, and terminology

I prioritized peer-reviewed papers, official protocol/product documentation, and live official repositories. I treated a paper's reported result as evidence that the result was reported—not as independent proof that it will transfer to this owner's repositories. Current 2026 product documentation and papers appearing after the model's usual knowledge cutoff are marked as lower-confidence where they affect a conclusion.

The following terms are easy to blur and should remain separate:

1. A **repository inventory/tree** lists paths and containment. It answers “what exists?”
2. A **repository map** is a compact prompt artifact: paths plus selected symbols, signatures, and occasionally important source lines. It answers “where might I look?” Aider's documented map is the clearest deployed example: it lists files and key definitions, then graph-ranks the portions that fit a token budget ([Aider repository-map documentation](https://aider.chat/docs/repomap.html)).
3. A **symbol index** resolves definitions, references, implementations, types, and sometimes call hierarchy with language semantics. LSP standardizes the editor/server interface ([LSP overview](https://microsoft.github.io/language-server-protocol/)); SCIP is a language-agnostic persisted indexing protocol used by multiple language indexers ([SCIP repository](https://github.com/scip-code/scip)).
4. A **syntactic graph** derives approximate relationships from parsed source: containment, imports, identifier references, and sometimes calls. Tree-sitter queries are structural pattern matches over concrete syntax, and explicitly represent parse errors and missing nodes rather than supplying type semantics ([Tree-sitter query syntax](https://tree-sitter.github.io/tree-sitter/using-parsers/queries/1-syntax.html)).
5. A **semantic dependency/call graph** attempts language-resolved edges. Its accuracy depends on language-server/compiler knowledge, build configuration, generated code, dynamic dispatch, and runtime behavior.
6. An **execution trace** reports what actually ran for a particular input. It is not interchangeable with any static graph. The post-cutoff Gistify work explicitly frames codebase understanding as requiring execution-flow modeling as well as structure ([Gistify paper](https://microsoft.github.io/debug-gym/static/papers/Gistify_arxiv.pdf)); this is a primary but post-cutoff source and is therefore lower-confidence as a frontier signal).

The phrase “understands the whole codebase” is not an operational metric. The measurable targets are localization recall, navigation precision, tokens read before the decisive edit, stale-index rate, wall time, end-to-end task success, and regressions introduced.

## 1. Established

### 1.1 Symbol navigation is established infrastructure

Language-aware definition/reference navigation is mature engineering infrastructure, not speculative AI research. LSP exists to reuse language-specific intelligence across tools and exposes the standardized editor-to-language-server boundary ([official LSP overview](https://microsoft.github.io/language-server-protocol/)). SCIP persists language-agnostic symbol occurrences and relationships, and its official repository lists indexers for Java/Scala/Kotlin, TypeScript/JavaScript, Rust, C/C++, Ruby, Python, .NET, Dart, and PHP ([SCIP README](https://github.com/scip-code/scip)). GitHub's production code navigation exposes symbols, definitions, and references over many languages using Tree-sitter-based extraction, with a documented repository-size limit of fewer than 100,000 files ([GitHub code-navigation documentation](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github)).

What this establishes is narrower and more valuable than “understanding”: definitions, references, types, implementations, symbols, and call relationships are useful structured navigation primitives. It does not establish that a serialized whole-repository graph improves an LLM's end-to-end coding rate.

Current Claude Code has a built-in LSP tool which can jump to definitions, find references, show type information, list symbols, find implementations, trace call hierarchies, and automatically return diagnostics after edits once a language plugin and server binary are present ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)). This is current 2026 official product documentation, hence a primary but post-cutoff source; the capability claim is **almost certain (90-99%)** because both the tools reference and the independent plugin reference describe the same interface, while runtime behavior on this Windows installation has not yet been exercised ([Claude Code plugin reference](https://code.claude.com/docs/en/plugins-reference)).

### 1.2 Compact repository maps are an established context-shaping pattern

Aider documents and ships a repository map containing files, key classes/functions, signatures, and selected defining lines. It graph-ranks source-file dependencies and selects the highest-value pieces under a configurable token budget, normally around 1,000 tokens ([Aider repository-map documentation](https://aider.chat/docs/repomap.html)). The live implementation imports Tree-sitter queries and computes PageRank over a weighted graph ([Aider `repomap.py`](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py)). The map is refreshed according to an explicit policy and has controls for token budget and no-file expansion ([Aider options reference](https://aider.chat/docs/config/options.html)).

This establishes that a compact map is deployable, bounded, and compatible with a small agent loop. It does not establish that Aider's exact PageRank heuristic is optimal. Aider's own FAQ says weaker models may be confused by the map and sometimes try to edit its rendered contents; that is direct adverse evidence against unconditional injection ([Aider FAQ](https://aider.chat/docs/faq.html)).

The stable design lesson is therefore: maps are prompt-budgeted orientation artifacts, not databases and not authorities. They should identify likely places to inspect; the agent must still read the real source before editing.

### 1.3 Repository context and retrieval help on tasks that need cross-file information

RepoCoder reported that iterative similarity retrieval plus generation improved its in-file repository-level completion baseline by more than 10% across its tested settings and outperformed one-shot retrieval on RepoEval ([RepoCoder paper](https://aclanthology.org/2023.emnlp-main.151/)). This is evidence for iterative retrieval, not for graphs specifically.

Agentless uses a simple hierarchical localization procedure—repository structure to files, classes/functions, then edit locations—and released its preprocessed repository structures and complete run artifacts ([Agentless repository](https://github.com/OpenAutoCoder/Agentless)). Its significance for this unit is architectural: a simple structure-first funnel can support competitive end-to-end work without a persistent graph service.

SWE-bench itself contains 2,294 issues from 12 Python repositories and was designed because repository tasks require coordinating changes across functions, classes, and files ([ICLR 2024 SWE-bench paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/edac78c3e300629acfe6cbe9ca88fb84-Abstract-Conference.html)). That establishes the need to navigate beyond one file. It does not establish any particular navigation representation.

### 1.4 Query-conditioned selection beats indiscriminate whole-repository dumping

Aider explicitly warns that adding all files can distract the model, worsen editing, and increase token cost, while its map selectively adds context ([Aider FAQ](https://aider.chat/docs/faq.html)). RepoGraph likewise retrieves and flattens a task-conditioned one- or two-hop ego graph rather than injecting its complete graph ([ICLR 2025 RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)). The common established mechanism is selection under a budget, not total serialization.

### 1.5 Graph edges can improve localization, but localization is only an intermediate result

The peer-reviewed RepoGraph study added a code-line graph retrieval tool to several existing systems. On SWE-bench Lite it reported absolute end-to-end resolve-rate gains of 2.00–2.66 percentage points: Agentless 27.33% to 29.67%, AutoCodeRover 19.00% to 21.33%, and SWE-agent 18.33% to 20.33% ([RepoGraph paper, Table 2](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)). The same paper reports that file-level localization improved more than line-level localization, and explicitly says localization is necessary but insufficient because downstream patching still depends on the model and iterative agents accumulate errors ([RepoGraph paper, localization analysis](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)).

That result is established as a published, peer-reviewed observation on that evaluation. A claim that the same graph will improve this harness is not established.

### 1.6 The owner's harness already names code intelligence, but the runtime configuration contradicts the routing

Two independent local signals establish a configuration/routing mismatch without claiming that the underlying binary is absent:

* The capability catalog tells agents to prefer Serena's symbol operations over grep (`/local_disk0/codexwork/bundle/claude/hooks/capability-catalog/catalog.json:9-12`), and the semantic router independently recommends Serena on symbol/navigation prompts (`/local_disk0/codexwork/bundle/claude/hooks/skill-router/capabilities.py:43-49`). This proves the detector can find a known-present routing declaration.
* The unpacked settings explicitly set Serena false (`/local_disk0/codexwork/bundle/claude/settings.json:635`) and set all inspected official language plugins false, including TypeScript, Pyright, Go, Rust, Java, C/C++, Swift, Kotlin, Lua, and Ruby (`/local_disk0/codexwork/bundle/claude/settings.json:552-568`).

A separately validated corpus probe found four Repomix tool keys and eight Repomix server uses (known-positive control), but no Serena server or tool key across 11,633 parsed transcript files, with zero failed files and one bad line. Command used:

```text
python: load corpus.json; search capability_use.mcp_servers_used and
capability_use.mcp_tools_used case-insensitively for repomix and serena

control: repomix server count=8, repomix tool keys=4
target:  serena server keys=[], serena tool keys=[]
coverage: files_seen=11633, files_failed=0, lines_bad=1, 10.62 GB
```

Source: `/local_disk0/codexwork/bundle/inputs/corpus.json`, `_meta` and `capability_use`. These are mechanically independent signals: static enablement state and transcript use. The warranted conclusion is only that official LSP/Serena navigation was disabled or unobserved in the captured harness—not that no other symbol facility existed.

## 2. Promising but unproven

### 2.1 Lightweight heterogeneous graphs with agent-directed multi-hop expansion

LocAgent represents directories, files, classes, and functions with containment, import, invocation, and inheritance edges, then lets an agent search and expand multiple hops. Its ACL 2025 paper reports file-level Acc@5 of 83.39% and function-level Acc@15 of 60.71% on LocBench using Claude 3.5, versus OpenHands at 79.82% and 59.29%; on a downstream repair experiment, Pass@1 moved from Agentless's 26.31% to 27.92%, while Pass@10 moved from 33.58% to 37.59% ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)). The ablation reports that removing relationship tools, restricting to containment, fixing exploration to one hop, or removing sparse search reduces localization performance ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)).

Transfer to this harness is **likely (55-80%)**, evidence: peer-reviewed ablations indicate that non-containment edges and multi-hop traversal add localization signal, but the study focuses on Python, filters out SWE-bench cases without modified existing functions, and LocBench excludes patches touching more than five Python files or ten functions ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)). The end-to-end Pass@1 gain is much smaller than the localization headline.

### 2.2 Hybrid lexical + structural retrieval

Using lexical search to seed candidates and structure only to expand around them is **very likely (80-90%)** to outperform either a static full map or graph-only querying for at least some owner tasks. Evidence: RepoCoder reports benefits from iterative similarity retrieval ([RepoCoder paper](https://aclanthology.org/2023.emnlp-main.151/)); LocAgent reports sparse search is essential even when a graph is present ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)); RepoGraph uses textual search terms to retrieve bounded ego graphs ([RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)). This is not yet verified on the owner's polyglot, Windows-heavy workload.

### 2.3 Precise semantic edges from LSP/SCIP instead of parser guesses

Using an already-running language server's definition/reference/call-hierarchy results as on-demand edges is **very likely (80-90%)** to be more precise than inferring all edges by identifier names in supported, correctly configured languages. Evidence: the current Claude Code LSP interface exposes those semantic operations ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)); SCIP's purpose is precise language-agnostic code navigation and it has compiler/language-specific indexers ([SCIP repository](https://github.com/scip-code/scip)); Tree-sitter itself exposes syntax-tree query matching, including error recovery, rather than type resolution ([Tree-sitter query documentation](https://tree-sitter.github.io/tree-sitter/using-parsers/queries/1-syntax.html)). The proposition remains unverified on the owner machine because all inspected language plugins are disabled and the required binaries/PATH state were not probed.

### 2.4 Runtime-guided slices for behavior questions

For tasks framed by a failing test, CLI entry point, or reproducible command, augmenting static navigation with a narrow runtime trace is **likely (55-80%)** to locate behavior that static graphs miss. Evidence: the post-cutoff Gistify paper deliberately evaluates reproducing a command's behavior and reports that current models struggle particularly with long execution paths ([Gistify paper](https://microsoft.github.io/debug-gym/static/papers/Gistify_arxiv.pdf)); Debug-gym provides a concrete execution/debugging environment over repositories ([Debug-gym repository](https://github.com/microsoft/debug-gym)). Confidence is capped because Gistify is post-cutoff, its task is not ordinary patching, and no owner-specific comparison exists.

### 2.5 Better exploration-specific evaluation

Evaluating navigation separately from final patch success is **likely (55-80%)** to produce a faster and less noisy optimization loop. Evidence: LocAgent and RepoGraph separately score file/function/line localization and show that localization and repair gains diverge ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf); [RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)). The post-cutoff SWE-Explore paper is explicitly designed to isolate repository exploration, but it is new and not independently established ([SWE-Explore paper](https://arxiv.org/abs/2606.07297)); therefore it is a lower-confidence design reference, not a benchmark to adopt blindly.

### 2.6 Graph databases as a universal code interface

CodexGraph stores symbols and edges in Neo4j and has an LLM translate natural-language intent into Cypher. It reports competitive results across CrossCodeEval, SWE-bench Lite, and EvoCodeBench, but the same paper reports 102.25k average tokens on SWE-bench versus 76.01k for AutoCodeRover and 14.76k for BM25, roughly 5 hours 12 minutes to build a graph for an average 312-file SWE-bench repository, Python-only evaluation, and severe degradation with Qwen2-72B where its SWE-bench Pass@1 was 1.95% versus AutoCodeRover's 9.34% ([CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf)).

The proposition that a graph database is a good universal interface for this harness is **unlikely (20-45%)**, evidence: the primary paper's own cost, indexing, language, and small-model fragility results; plus this harness's anti-overfit gate explicitly rejects a vector-DB/KG memory or second orchestration runtime. Graph traversal is promising; the database/service embodiment is not.

## 3. Hype, and the tell that gives it away

### 3.1 “The agent understands the entire codebase”

**Tell:** no operational definition of “understands,” no held-out questions, no localization recall, no token/read budget, and no end-to-end patches. A generated architecture narrative or pretty dependency diagram demonstrates summarization, not verified understanding. Even the purpose-built Gistify evaluation argues that common repository benchmarks can be solved through localized shortcuts and then shows frontier models struggling with full execution behavior ([Gistify paper](https://microsoft.github.io/debug-gym/static/papers/Gistify_arxiv.pdf)).

### 3.2 “Knowledge graph” as a synonym for parsed symbols

**Tell:** nodes are functions/classes and edges are imports/calls, but marketing implies learned semantics, intent, business rules, or runtime truth. LocAgent's honest schema is only directory/file/class/function plus contain/import/invoke/inherit, and it explicitly limits the study to Python ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)). That can be useful, but it is a static index, not organizational knowledge.

### 3.3 Benchmark gains reported only at file Acc@5 or Pass@10

**Tell:** the headline is coarse localization or many-sample success while single-attempt end-to-end repair barely moves. LocAgent's reported downstream numbers illustrate the gap: stronger localization changes Pass@1 from 26.31% to 27.92%, while the larger gain appears at Pass@10 ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)). RepoGraph likewise reports larger coarse file-localization gains than fine line-localization gains ([RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)).

### 3.4 “Graph beats RAG” without a matched simple baseline

**Tell:** the comparison changes model, prompt budget, number of queries, sampling count, or task-specific pipeline; there is no same-model/same-token comparison against `rg`/BM25 plus repository structure plus native LSP. CodexGraph's own table shows that the winner varies by task/model, and its token use exceeds both BM25 and AutoCodeRover ([CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf)). RepoGraph is stronger evidence because it plugs into matched baselines, yet its end-to-end gains are only about 2–2.66 absolute points ([RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)).

### 3.5 “Production scale” demonstrated on SWE-bench alone

**Tell:** Python-only evaluation over the SWE-bench family's 12 popular repositories is described as general codebase-scale evidence. The original benchmark has 12 repositories ([SWE-bench paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/edac78c3e300629acfe6cbe9ca88fb84-Abstract-Conference.html)). A broader 2025 ICML study constructed benchmarks across hundreds of repositories and found distributional differences and up to 60% lower agent success than SWE-bench-family measurements ([SWEE-bench/SWA-bench paper](https://proceedings.mlr.press/v267/vergopoulos25a.html)).

Post-cutoff evidence makes old SWE-bench headline comparisons still less reliable: OpenAI reports training contamination in frontier models and stopped treating SWE-bench Verified as a meaningful frontier measure ([OpenAI, “Why SWE-bench Verified no longer measures frontier coding capabilities”](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). This is an official primary audit but post-cutoff and not an independent academic reproduction, so the claim that older graph rankings no longer predict frontier performance is **likely (55-80%)**, not certain.

### 3.6 “Always-fresh repository brain” without dirty-worktree semantics

**Tell:** no declared cache key, invalidation rule, worktree overlay, generated-file policy, branch/submodule behavior, or parse-error telemetry. CodexGraph reports that first indexing can take hours and proposes incremental re-indexing, while acknowledging static-analysis scalability challenges ([CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf)). A repository map that cannot state the commit and dirty-file versions it represents is an attractive stale cache.

### 3.7 Infrastructure magnitude hidden behind “lightweight”

**Tell:** the architecture diagram omits a graph database, embedding service, indexer farm, or trained retriever, while the setup requires them. LocAgent's released instructions include prebuilt graph and BM25 indexes and show a 50-process batch generation example ([LocAgent repository](https://github.com/gersteinlab/LocAgent)). CodexGraph uses Neo4j/Cypher and reports multi-hour indexing on larger repositories ([CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf)). A small serialized adjacency list can be lightweight; a service stack is not made lightweight by naming it so.

## 4. Specific things this harness should adopt

### Priority 0 — UNVERIFIED: enable native, project-scoped LSP code intelligence

**NATIVE (Claude Code already does this; we just enable it)**

Enable only the official language plugin(s) relevant to the active repository after verifying the corresponding server binary with PowerShell `Get-Command`. Start with the owner's highest-volume languages, not all eleven plugins globally. The agent should use native LSP for definition, references, hover/type, symbols, implementations, call hierarchy, and post-edit diagnostics; retain `rg` as fallback. Claude Code officially documents exactly these operations and warns that language servers can consume significant memory or produce monorepo false positives when misconfigured ([Claude Code marketplace/code-intelligence documentation](https://code.claude.com/docs/en/discover-plugins)).

Why this harness specifically: settings currently disable the inspected official language plugins (`settings.json:552-568`), while two routing surfaces direct the model to Serena (`capability-catalog/catalog.json:9-12`; `skill-router/capabilities.py:43-49`). The corpus detector, validated on known-present Repomix calls, found no Serena use. That is a high-value contradiction: the model is prompted toward a path the captured runtime did not exercise even though a native path now exists.

Expected benefit is **very likely (80-90%)**, evidence: mature LSP/SCIP navigation primitives, Claude's native tool support, and the current disabled/routed mismatch. **UNVERIFIED premise:** the required language-server binaries are installed and work in the owner's real monorepos. **Settling experiment:** for Python and TypeScript controls, (1) prove `Get-Command pyright-langserver` / `Get-Command typescript-language-server`; (2) enable one plugin in a disposable project scope; (3) use known symbols to verify definition and references; (4) introduce a temporary type error and verify automatic diagnostics; (5) record startup time and peak memory; (6) disable/revert the project setting. Do not claim success until both a known-positive symbol and a known-negative symbol behave correctly.

**Anti-overfit gate:** passes. It enables an existing Claude Code bus, adds no orchestration runtime, database, memory system, critic, SaaS, or guardrail framework.

### Priority 0 — UNVERIFIED: repair the routing contract to prefer native LSP and state fallbacks

**CONFIG (settings/JSON only)**

After the Priority 0 experiment succeeds, replace the unconditional Serena guidance with a capability-checked order:

```text
symbol/type/reference task:
  native LSP when active and known-positive control passes
  -> rg/git grep for exact text and strings
  -> repository inventory/map for discovery
  -> read real source before editing
```

If the LSP experiment fails, the router must say it is unavailable and fall back rather than repeatedly suggest a disabled endpoint. This directly addresses the measured dead-MCP pattern in the owner brief without assuming Serena itself produced those errors.

Improvement is **very likely (80-90%)**, evidence: the local static contradiction and the validated absence of recorded Serena calls; the owner's measured ground truth shows a different dead MCP was nevertheless called 532 times with a 25.8% error rate, including 135 “not connected” errors. **UNVERIFIED premise:** native LSP outperforms Serena on the owner's repositories. **Settling experiment:** replay 20 historical symbol-navigation prompts with identical model and repository state, randomized between native LSP, Serena (only if actually active), and `rg`; score correct definition/reference recall, tool errors, calls, wall time, and tokens read.

**Anti-overfit gate:** passes. This is routing configuration on the existing tool bus and removes a contradictory path.

### Priority 1 — UNVERIFIED: add a compact, task-conditioned repository map, not an always-on dump

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build one local command/skill that emits a deterministic, bounded Markdown map. It should contain:

* repository root, current commit, dirty-file list, and map-generation timestamp;
* top-level tree with generated/vendor/cache directories excluded by existing ignore files;
* build/test/entry-point files and manifests;
* selected symbols and signatures from native LSP when available, with a Tree-sitter/ctags/regex fallback clearly labeled approximate;
* query-conditioned ranking from task words, mentioned paths/symbols, import/reference neighbors, and changed files;
* a hard default budget around 1,000–2,000 tokens, with deterministic truncation and an explicit “omitted” count;
* provenance per section and the rule “orientation only; read the real file before any edit.”

Do not inject it into every turn. Generate it at the start of unfamiliar-repository work, after compaction when repository orientation is lost, or when localization stalls. Refresh only when `HEAD`, dirty-file hashes, task query, or relevant build configuration changes. Aider supplies the deployed precedent for symbol/signature maps, token budgets, graph ranking, and refresh controls ([Aider repository-map documentation](https://aider.chat/docs/repomap.html); [Aider options](https://aider.chat/docs/config/options.html)).

Benefit is **likely (55-80%)**, evidence: Aider deployment, Agentless's structure-first localization, RepoCoder iterative retrieval, and graph-paper localization gains. **UNVERIFIED premise:** the map adds enough information beyond native LSP plus `rg` to justify its tokens on this owner's tasks. **Settling experiment:** replay at least 50 historical tasks stratified by repository size, language, bug/feature/review, and whether the final patch crossed files. A/B no map versus bounded map with the same model and tool budget. Primary metrics: all-ground-truth-files read before first edit, end-to-end verification pass, unnecessary files read, input tokens, wall time, map stale/missing-symbol incidents. Adopt only if the confidence interval excludes material harm and at least one of localization recall or end-to-end pass improves without a disproportionate token/latency increase.

**Anti-overfit gate:** passes only if implemented as one small local command/skill using existing parsers/tools. It fails the gate if it grows a daemon, graph store, embedding index, or second orchestration loop.

### Priority 1 — UNVERIFIED: enforce progressive disclosure as a navigation rule

**CONFIG (settings/JSON only)**

Add a short rule for codebase tasks:

1. Begin with issue text, manifests/entry points, `git status`/diff, a bounded tree/map, and exact lexical matches.
2. Use native LSP on named symbols.
3. Expand only one relationship hop at a time: definition → references/callers, import → imported symbol, test → production target.
4. Read source slices, then full files only when necessary.
5. For behavioral failures, prefer the failing test/stack trace/runtime observation over graph centrality.
6. Before editing, cite the exact source definition and at least one independent signal linking it to the task (test/trace/reference/config).

The rule should not mandate a fixed sequence when evidence already identifies the file. The purpose is bounded expansion, not ritual.

Benefit is **very likely (80-90%)**, evidence: Aider's warning against indiscriminate context ([Aider FAQ](https://aider.chat/docs/faq.html)), RepoGraph's bounded ego-graph retrieval ([RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)), and LocAgent's multi-hop result ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)). **UNVERIFIED premise:** the rule is followed rather than ignored or over-applied. **Settling experiment:** instrument 30 replay tasks and compare unnecessary file reads, maximum context, localization recall, and correction rate; manually classify whether rule deviations were justified.

**Anti-overfit gate:** passes. It is a compact rule over existing tools, with no new component.

### Priority 2 — UNVERIFIED: expose a tiny “neighbor expansion” view over LSP results

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Only if native LSP is reliable, add a formatter that turns on-demand results into a compact local adjacency view:

```text
symbol: package.module.Class.method  [definition path:line]
contains: ...
calls/called-by: top N resolved symbols
references: N total; top N paths by task relevance
implements/overrides: ...
tests mentioning symbol/path: ...
confidence: semantic-LSP | syntactic-fallback
```

Do not persist a global graph. Construct the view from the current query, cap each edge class, and include the underlying locations so the agent can verify them. This captures the useful LocAgent/RepoGraph operation—bounded multi-hop exploration—without copying their runtime ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf); [RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)).

Benefit is **roughly even (45-55%)**, evidence: graph ablations support relationship edges, but Claude can already invoke LSP operations directly and a formatter may add little. **UNVERIFIED premise:** compact aggregation reduces calls/tokens without hiding decisive references. **Settling experiment:** matched replay of 20 multi-hop tasks, direct LSP versus formatted one-hop view, measuring correct dependency chain, calls, tokens, latency, and omitted decisive edges.

**Anti-overfit gate:** passes if it remains a stateless formatter. Any persistent index or service changes this to BUILD-LARGE and fails the current gate.

### Priority 2 — UNVERIFIED: add a localization evaluation slice to the existing eval bus

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

For tasks with known human patches, derive file and symbol targets from the patch, then score the agent trace before its first edit:

* file recall: did it inspect every human-modified file?
* symbol recall: did it inspect a containing modified symbol where such a symbol exists?
* read efficiency: relevant source lines / total source lines returned;
* navigation cost: tool calls, errors, tokens, wall time;
* stale-map incidents: map/index points to content not matching the worktree;
* final verification: tests or deterministic acceptance checks, kept separate from localization.

Do not treat the human patch as the only valid solution; file/symbol misses are diagnostic, while executable verification remains the terminal measure. LocAgent's strict all-target top-k metrics and RepoGraph's file/function/line measures provide precedents, while both papers show localization does not equal repair ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf); [RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf)).

Value is **very likely (80-90%)**, evidence: it makes the precise design choice measurable on owner data and does not depend on public-benchmark transfer. **UNVERIFIED premise:** sufficient historical traces preserve read/tool events and resolvable worktree revisions. **Settling experiment:** sample 30 successfully completed historical tasks, attempt reconstruction, and report the fraction with usable revision, patch, tool trace, and verification receipt before building the full slice.

**Anti-overfit gate:** passes. This extends the existing eval/trace bus; it is not a trained critic or observability SaaS.

### Priority 3 — UNVERIFIED: runtime slices only on reproducible behavior tasks

**CONFIG (settings/JSON only)**

When a task supplies a failing test, stack trace, CLI command, or HTTP reproduction, route the agent to execute that narrow reproduction and follow observed frames/imports before asking for broader graph expansion. Never run broad tracing by default. Static maps describe possible structure; runtime evidence identifies one realized path. Debug-gym and Gistify are research evidence for this distinction ([Debug-gym repository](https://github.com/microsoft/debug-gym); [Gistify paper](https://microsoft.github.io/debug-gym/static/papers/Gistify_arxiv.pdf)).

Benefit is **likely (55-80%)**, evidence: execution directly observes the failing behavior, but many tasks lack a reproduction and tracing can perturb or omit behavior. **UNVERIFIED premise:** current harness execution tools provide sufficient trace/stack data without new instrumentation. **Settling experiment:** 20 historical tasks with reproductions; compare structure-first and execution-first localization under identical budgets.

**Anti-overfit gate:** passes because it changes routing over existing shell/test/debug tools. A tracing daemon would not pass.

### Explicit rejection: do not add a graph database, vector DB, or repository knowledge graph

No adoption tag is assigned because this is a rejected alternative, not a proposal. CodexGraph's own primary evidence shows Python-only evaluation, larger token consumption, multi-hour initial indexing for its larger repositories, and agent fragility on a weaker model ([CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf)). RepoGraph and LocAgent show that the valuable operation is bounded relationship expansion, which can be reproduced over native LSP and small local structures without a database ([RepoGraph paper](https://proceedings.iclr.cc/paper_files/paper/2025/file/4a4a3c197deac042461c677219efd36c-Paper-Conference.pdf); [LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf)).

The anti-overfit gate independently rejects this component: it would be a second code-navigation runtime and, if used as memory, a vector-DB/KG system explicitly rejected by the brief. Reconsider only if owner-specific A/B evidence first shows native LSP + lexical search + compact map missing a material class of tasks, and a stateless adjacency formatter fails to close that gap.

## Recommended sequence and stop conditions

1. Run the binary/PATH and disposable-project LSP controls. Stop if known-positive definitions/references fail or memory/diagnostic noise is unacceptable.

4. Prototype the bounded map behind an explicit command/skill. Do not auto-inject until the 50-task A/B shows net value.
5. Only after those results, test the stateless adjacency formatter on tasks proven to require multi-hop navigation.
6. Do not begin graph-database work without a written owner-data failure analysis and an exception to the anti-overfit gate.

The likely best architecture is still the smallest one: **native semantic primitives + lexical fallback + bounded map + execution evidence when available**. This is **very likely (80-90%)**, evidence: established tooling, matched graph-paper gains that are real but modest, and the local harness's currently disabled native capabilities. The remaining uncertainty is owner-specific transfer, which the proposed replay experiments directly settle.

Experiment: inspect live `claude mcp list`, plugin list, and tool inventory; invoke a known-positive symbol in a disposable repository. I therefore do not claim Serena is absent.
3. **Which programming languages dominate successful and failed owner code tasks.** The pinned corpus exposes capability/tool aggregates but this unit did not have a validated language classifier over task worktrees. Experiment: classify repository manifests/extensions from a stratified session sample with known-positive controls for Python and TypeScript.
4. **Map benefit on owner tasks.** No owner-specific A/B exists. Experiment: the 50-task stratified replay described under Priority 1. Any adoption recommendation for automatic map injection remains UNVERIFIED until that run.
5. **Whether Repomix helped or hurt.** The corpus records eight server uses and several tool calls, but tool invocation is not outcome attribution. Experiment: locate those sessions, compare intended task, returned context, downstream reads/edits, token cost, and owner corrections. No effectiveness conclusion was drawn.
6. **Map construction dependencies.** I did not determine whether Aider, universal-ctags, Tree-sitter language packs, or SCIP indexers are already installed on Windows. Experiment: `Get-Command` plus version probes; never install as part of the probe.
7. **Dirty-worktree and monorepo behavior of current Claude LSP plugins.** Official docs warn about monorepo false positives and resource use but do not establish this owner's behavior ([Claude Code plugin discovery documentation](https://code.claude.com/docs/en/discover-plugins)). Experiment: disposable dirty edits in a representative monorepo, known-positive/negative symbols, memory and startup measurements.
8. **Cross-language graph quality.** LocAgent is Python-focused, CodexGraph evaluates Python indexing, and SWE-bench's original suite is 12 Python repositories ([LocAgent paper](https://aclanthology.org/2025.acl-long.426.pdf); [CodexGraph paper](https://aclanthology.org/2025.naacl-long.7.pdf); [SWE-bench paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/edac78c3e300629acfe6cbe9ca88fb84-Abstract-Conference.html)). 9. **Current frontier benchmark stability.** Post-cutoff sources suggest SWE-bench Verified is contaminated and exploration-specific benchmarks are emerging ([OpenAI benchmark audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); [SWE-Explore](https://arxiv.org/abs/2606.07297)). These are important but recent. A current benchmark recommendation would require a separate evaluation unit comparing live, contamination-resistant, multilingual, and private owner-task suites.
10. **Repository-map failure cases at scale.** Aider documents model confusion and GitHub documents a 100,000-file navigation limit, but I did not locate a controlled multi-language study of map staleness, generated code, duplicate symbols, submodules, or monorepo workspaces ([Aider FAQ](https://aider.chat/docs/faq.html); [GitHub code-navigation documentation](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github)).
