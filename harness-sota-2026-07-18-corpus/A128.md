# A128 — coherence audit: commands versus settings / silent override

## Executive result

I found **zero fully runtime-verified silent overrides** and **two high-confidence static candidates that require a Windows Claude Code run before promotion to findings**:

1. `/pm2` says `.env` has second priority for port discovery, but the user settings deny reads of root and nested `.env` files. The native deny is almost certain (90-99%) to win when Claude uses `Read` or a recognized shell file-read command; the evidence is the exact local texts plus two independent official permission descriptions. This remains **UNVERIFIED** at the owner's runtime because this Linux job node has no `claude` executable and no Windows paths. The named settling experiment is **E-PM2-ENV** below.
2. `/skill-create` uses the unsupported frontmatter spelling `allowed_tools`, while settings independently pre-approve those tools and select `bypassPermissions`. The frontmatter is very likely (80-90%) dead metadata; the evidence is the exact local text and Claude Code's official frontmatter schema, but the schema does not explicitly say how this particular unknown key is reported. This remains **UNVERIFIED** at runtime; the named settling experiment is **E-SKILL-CREATE-METADATA** below.

This distinction is deliberate. The unit requires runtime verification, but the remote override supplies a read-only unpacked tree rather than the Windows host. I do not convert documented semantics into a fabricated live observation.

The audit also found one material **non-silent coherence defect**: `/context-budget` assumes 200K although settings select `opus[1m]`, a 1,000,000-token auto-compact window, and a 1,000,000-token compact override. Both texts still fire, so this is not a silent override under the unit definition; it is recorded under non-findings rather than inflated into the headline.

## Method

For every command I checked these collision axes against settings:

1. Tool requests and file reads versus `permissions.allow`, `permissions.ask`, `permissions.deny`, `defaultMode`, and additional directories.
2. Command frontmatter tool/model/invocation metadata versus global permission and model settings.
3. Named plugin/skill/agent/MCP dependencies versus `enabledPlugins` and the permitted MCP/tool surface.
4. Unqualified command names versus enabled or disabled plugin names, accounting for Claude Code's namespace rules.
5. Context/model assumptions versus `model`, `fallbackModel`, `effortLevel`, `autoCompactWindow`, and the environment compact override.
6. Plan/team/background behavior versus `useAutoModeDuringPlan`, experimental agent teams, and teammate mode.

A candidate was retained only when there is a concrete invocation state in which both texts address the same operation and one can prevent or bypass the other. Mere thematic overlap was rejected.

## Candidate finding 1 — `/pm2` `.env` priority is blocked by settings deny **[UNVERIFIED: E-PM2-ENV]**

### Both texts, verbatim

Command side, `/local_disk0/codexwork/bundle/claude/commands/pm2.md:29`:

```text
**Port Detection Priority**: User specified > .env > config file > scripts args > default port
```

Settings side, `/local_disk0/codexwork/bundle/claude/settings.json:64-71`:

```json
"deny": [
  "Read(./.env)",
  "Read(**/.env)",
  "Read(**/*.pem)",
  "Read(**/*.credentials*)"
],
"ask": [],
"defaultMode": "bypassPermissions",
```

The broad allow on the other side is also explicit at `settings.json:27-35`:

```json
"allow": [
  "mcp__codex__codex",
  "mcp__codex__codex-reply",
  "Read",
  "Edit",
  "Write",
  "Glob",
  "Grep",
  "Bash",
```

### Concrete collision

Invoke `/pm2` in a project where no port is supplied in the prompt and `.env` contains the only non-default port. To obey `pm2.md:29`, Claude must inspect `.env` before config files, script arguments, or defaults. A `Read` call on root `.env` matches `Read(./.env)`; a nested service `.env` matches `Read(**/.env)`.

This is not a collision merely because `.env` appears in prose. `/metaswarm-setup` only writes literal `.env` patterns into `.gitignore` (`commands/metaswarm-setup.md:351-408`), so it need not read the secret-bearing file. `/update-docs` explicitly reads `.env.example` (`commands/update-docs.md:10,31`), which is not the exact `.env` target of either deny rule. Those candidates were rejected.

### Which wins at runtime

The native deny is **almost certain (90-99%)** to win for `Read` and Claude Code-recognized shell reads. Evidence:

1. Claude Code's permissions documentation says rules are evaluated deny → ask → allow and that deny has precedence across settings scopes. It also says `Read` deny rules cover built-in read tools and recognized Bash reads such as `cat`, `head`, `tail`, and `sed`: https://code.claude.com/docs/en/permissions.
2. The independently documented Agent SDK evaluation order checks deny before permission mode and explicitly says a matching deny is blocked even in `bypassPermissions`: https://code.claude.com/docs/en/agent-sdk/permissions.
3. The local settings contain both exact root and recursive `.env` patterns, so this is not an inference from a generic credentials policy (`settings.json:64-68`).

The runtime outcome on the owner's Windows CLI is nevertheless **UNVERIFIED**. Experiment **E-PM2-ENV** settles it:

1. In a disposable trusted repo, create `package.json`, an otherwise port-free service, `.env` containing `PORT=4317`, and a non-secret `.env.example` containing `PORT=4318` as a detector control.
2. Start the owner's normal Claude Code CLI with `--debug`, confirm `/permissions` attributes both deny rules to `~/.claude/settings.json`, and invoke `/pm2` without a port argument.
3. Capture two mechanically independent signals: the debug permission decision for the `.env` access and the port written to the generated `ecosystem.config.cjs`.
4. Positive detector control: ask `Read .env.example`; it must succeed and return `4318` before interpreting a missing `.env` value as a deny.
5. Repeat with a temporary `--settings` copy whose only change is removal of the two `.env` deny rules. A generated port of `4317` in the control and a deny/fallback in the subject run verifies the collision.

There is an important escape path: official docs say arbitrary subprocesses that open files themselves are not covered by `Read` deny. Therefore a generated Python/Node reader could make the command “win” by bypassing the intended settings policy. This is **likely (55-80%)** to be avoided by Claude because the command gives no such implementation and native `Read` is the direct operation; evidence is the command's absence of a prescribed reader and the availability of `Read` at `settings.json:30`. E-PM2-ENV must record the actual tool call, not only the final port.

### Minimal resolution proposal **[UNVERIFIED premise: E-PM2-ENV]**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Edit only `commands/pm2.md:29` to:

```text
**Port Detection Priority**: User specified > .env.example > config file > scripts args > default port. Never read .env; if the only configured port may be there, ask the user for the port.
```

This preserves the settings security boundary and removes any incentive to bypass it through an arbitrary subprocess. It is **very likely (80-90%)** to resolve the collision because every path then either uses a readable non-secret template, another already-listed source, or explicit user input; evidence is the revised deterministic priority and the unchanged deny. E-PM2-ENV plus a rerun after this one-line edit is the acceptance test.

Deleting or weakening the global `.env` deny was rejected: it is **almost certain (90-99%)** to broaden access for all 71 commands to fix one command, because the rule is user-global and every command is user-global. Adding an allow exception also cannot beat a deny under the documented permission order.

Anti-overfit gate: pass. This is one command-text edit on the existing command/permission bus. It adds no orchestration runtime, vector DB/KG, durable execution, trained critic, observability SaaS, or guardrail framework.

## Candidate finding 2 — `/skill-create` tool metadata is misspelled and settings mask it **[UNVERIFIED: E-SKILL-CREATE-METADATA]**

### Both texts, verbatim

Command side, `/local_disk0/codexwork/bundle/claude/commands/skill-create.md:1-5`:

```yaml
---
name: skill-create
description: Analyze local git history to extract coding patterns and generate SKILL.md files. Local version of the Skill Creator GitHub App.
allowed_tools: ["Bash", "Read", "Write", "Grep", "Glob"]
---
```

Settings side, `/local_disk0/codexwork/bundle/claude/settings.json:30-35,71`:

```json
"Read",
"Edit",
"Write",
"Glob",
"Grep",
"Bash",
```

```json
"defaultMode": "bypassPermissions",
```

### Concrete collision

Invoke `/skill-create` and let it analyze history and write a `SKILL.md`, as instructed at `commands/skill-create.md:7-9`. The command **very likely (80-90%)** attempts to declare a per-invocation grant for Bash/Read/Write/Grep/Glob—the evidence is the five tool names under the near-identical key—but the supported key is `allowed-tools` with a hyphen. The global settings independently permit all five and `bypassPermissions` approves anything that reaches the mode evaluation. Thus normal execution can look healthy while the command's own metadata contributes nothing.

This matters as a silent override rather than a cosmetic typo only under a profile where `/skill-create` must carry its tool grant portably; the current profile makes the grant redundant. Correct `allowed-tools` is not a restriction: official docs explicitly say every other tool remains callable and settings still govern unlisted tools. Therefore this line never created a five-tool sandbox, even if spelled correctly.

### Which wins at runtime

Settings are **very likely (80-90%)** to be the effective approval source and `allowed_tools` is very likely ignored. Evidence:

1. The official frontmatter table lists `allowed-tools` and not `allowed_tools`, and says files under `.claude/commands/` support the same frontmatter: https://code.claude.com/docs/en/slash-commands.
2. The exhaustive local frontmatter inventory found `allowed_tools` only once and found zero `allowed-tools` keys, eliminating the possibility that this repository consistently uses a documented alternative spelling.
3. All five tools are independently present in `permissions.allow` and the selected default mode is `bypassPermissions` (`settings.json:30-35,71`).

The exact unknown-key behavior is **UNVERIFIED** because the authoritative page specifies malformed-YAML behavior but does not explicitly state whether an otherwise valid unknown underscore key produces a debug warning. Experiment **E-SKILL-CREATE-METADATA** settles it:

1. On Windows, start Claude Code with `--debug` in a disposable repo and invoke `/skill-create`.
2. Record the parsed metadata/debug output and the permission provenance for its first Bash and Write calls.
3. In a disposable copy—not the subject—change only `allowed_tools` to `allowed-tools`, run under `dontAsk` with the global allow entries removed, and repeat.
4. Independent signals: debug metadata must show the grant only in the corrected copy, and the corrected copy's listed tool call must execute while an unlisted mutating tool remains denied. Use a known-present `description` field as the parser control.

### Minimal resolution proposal **[UNVERIFIED premise: E-SKILL-CREATE-METADATA]**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** If E-SKILL-CREATE-METADATA confirms the key is ignored, rename `allowed_tools` to `allowed-tools` at `commands/skill-create.md:4`. This is **almost certain (90-99%)** to make the command metadata schema-valid because it is the exact documented field spelling; for the same reason, it is **almost certain (90-99%)** not to narrow the tool pool, and must not be represented as a security boundary.

If portability is not intended, deletion of line 4 is an even smaller coherent edit: settings already grant the tools. Rename is preferred because the command is described as a local version of a distributable skill generator and a turn-scoped grant remains useful outside this permissive user profile. That preference is **likely (55-80%)** to match owner intent; evidence is the command's explicit self-contained frontmatter and write workflow, but owner intent is not directly recorded. E-SKILL-CREATE-METADATA settles mechanics, not that product choice.

Anti-overfit gate: pass. This is a one-token metadata correction on the native command bus and introduces none of the rejected architecture classes.

## Gaps and limits

1. **Windows runtime unavailable.** `command -v claude` found no executable and `claude --version` returned `command not found`. The remote override explicitly says Windows-only paths do not exist. Therefore neither candidate is promoted to a runtime-verified finding.
2. **Plugin cache unavailable.** The unpacked `claude` tree contains no plugin cache or plugin manifests. Official namespace semantics are sufficient to reject obvious unqualified-name conflicts, but installed-version-specific plugin contents remain uninspected. Experiment **E-PLUGIN-NAMES**: on Windows run `/reload-plugins`, capture its counts, and export `/skills` names; compare qualified names against all 71 filenames.
3. **Full skill roots unavailable.** The semantic-router index proves known-present skills such as `brainstorming` and `prompt-optimizer`, but it is dated 2026-06-29 and contains 240 skills, while pinned inputs describe roughly 355 installed. It cannot prove current absence. No absence conclusion uses it alone.
4. **No historical `/pm2` invocation evidence.** The corpus search found no specific `/pm2` execution or `.env` permission rejection. The semantic index proves cataloguing, not use. The candidate is based on a concrete reproducible state, not a claim that the owner already encountered it.
5. **Corpus limits honored.** The corpus contains a generic OS `Permission denied` fingerprint at `corpus.json:7441`, but it is not tied to Claude permissions or `.env`, so it was not used. The broken corpus hook detector was not used at all.
