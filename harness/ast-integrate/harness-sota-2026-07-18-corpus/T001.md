# T001 — Competitive teardown: Cursor

**Research snapshot:** 2026-07-19 UTC  
**Unit:** T001  
**Subject:** Cursor, compared with the owner’s Claude Code + Codex shared harness  
**Mode:** research/design only. I made no changes to the unpacked subject tree.

## 0. Executive verdict

Cursor is currently the best evidence in this teardown for a **file-native, progressively disclosed agent harness**: long tool results become files, terminal sessions become searchable files, pre-compaction history remains available as a file, skills are discovered from files, and MCP schemas are synchronized into per-server folders rather than permanently occupying the prompt. Cursor reports a 46.9% total-token reduction on runs that used MCP after adopting its lazy MCP mechanism, although it also says variance was high ([Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)). This is the most valuable mechanism to port.

Cursor is also ahead in **operator experience for parallel work**: visible async subagents, worktree/branch isolation, one-click foreground handoff, local-to-cloud continuation, cross-repository workspaces, side chats, searchable transcripts, and artifact-rich cloud-agent review. Its April 2026 `/multitask` feature decomposes work into async subagents; each background task can run on its own branch/worktree ([Cursor 3.2 changelog](https://cursor.com/changelog/04-24-26)). The owner already has stronger raw multi-agent depth and strong handoff controls, but not this coherent operator surface.

Cursor is **not a full replacement candidate** for this owner. It is worse on the dimensions that the measured defects make load-bearing:

1. Cursor’s automatic memory is a sidecar model that proposes project-scoped rules for user approval; the owner already separates explicit semantic memory from an objective event ledger and compaction checkpoints (`bundle/claude/AGENTS.md:28-34,85-91`; `bundle/agents/harness/README.md:21-29`). Cursor’s mechanism is easier, but less provenance-rich and less suited to falsifiable failure history.
2. Cursor’s foreground `beforeSubmitPrompt` hook cannot inject prompt-specific context; it can only allow/block and show a user message. Cursor staff confirmed this in April 2026, and unknown output fields are silently ignored ([staff response and reproducer](https://forum.cursor.com/t/bug-beforesubmitprompt-hook-updated-input-is-silently-stripped-modified-prompt-never-reaches-the-model/158883/6)). The owner’s shared hook result explicitly supports `additional_context` (`bundle/agents/harness/models.py:45-73`), and its `UserPromptSubmit` recall path injects bounded context (`bundle/agents/harness/modules.py:1572-1621`).
3. Cursor staff also confirmed that a prompt blocked by `beforeSubmitPrompt` remained in history and could reach the model on the next turn; the published workaround was to start a new chat ([known blocked-prompt history leak](https://forum.cursor.com/t/blocked-messages-beforesubmitprompt-hook-returns-continue-false-are-still-included-in-later-llm-context-history/153318)). UNVERIFIED whether Cursor 3.11 fixed this; the settlement experiment is a two-turn canary on the exact installed Cursor build, then inspection of the local agent transcript. Until that passes, Cursor’s prompt hook is unsuitable as a confidentiality boundary.
4. Cursor foreground rules/skills/hooks and cloud hooks have evolved quickly, but public documentation is partially lagging product behavior. The July 2026 changelog advertises new cloud conversation hooks, while some stable payload fields were acknowledged as undocumented by staff in May 2026 ([3.11 changelog](https://cursor.com/changelog), [payload discussion](https://forum.cursor.com/t/beforesubmitprompt-hook-lacks-reliable-current-mode-signal-ask-vs-agent-making-mode-based-command-safety-gates-unreliable/159905)). The owner’s hook bus is imperfect, but its provider-neutral schema and test suite are inspectable (`bundle/agents/harness/README.md:1-29`).

**Bottom line:** evolve the owner’s existing bus with Cursor’s file-backed dynamic-discovery mechanisms and selected control-plane UX; do not replace the owner’s memory, receipt, verification, or safety semantics with Cursor’s. It is **very likely (80-90%)** that this selective port yields more reliability per line than adopting Cursor as a fourth orchestration runtime, because the highest-value ports are file adapters or configuration, while the local harness already has the lifecycle, ledger, compaction, recall, and subagent modules they need (`bundle/agents/harness/README.md:1-29`; Cursor’s own research argues that files are the simpler abstraction). This is a forward-looking assessment; the evidence is architectural fit, not an A/B result.

## 3. Agent loop

### 3.1 What Cursor does

Cursor’s foreground loop is conventional but polished: Agent searches, reads, edits, executes terminal commands, consumes errors, and continues. Its official tools page states that Agent has no tool-call count limit and continues as needed; modes select tool subsets and capabilities ([Agent tools](https://docs.cursor.com/en/agent/tools), [Modes](https://docs.cursor.com/agent)). The editor presents Agent, read-only Ask, edit-only Manual, and configurable Custom modes. Auto-run and auto-fix are mode options.

Plan Mode is a first-class pre-build loop: research the codebase, ask clarifying questions, write a detailed plan with file paths/code references, and wait for approval. Plans are editable Markdown and can be persisted in `.cursor/plans/` ([Cursor agent best practices](https://cursor.com/blog/agent-best-practices)). Cursor 1.2 added structured to-do lists with dependencies and visible progress, including Slack streaming ([1.2 changelog](https://cursor.com/changelog/1-2)).

Cursor explicitly tunes its harness instructions and tools for each frontier model using internal evaluations ([agent best practices](https://cursor.com/blog/agent-best-practices)). Its Composer 2 technical report describes a production-like harness with a system message, tool specifications, recent-file information, an isolated codebase environment, and training/evaluation over agent rollouts ([Composer 2 technical report](https://cursor.com/resources/Composer2.pdf)).

### 3.2 Where Cursor is better

- The visible plan artifact creates an inspectable contract before mutation. The owner has plan-mode reasoning configured in Codex and an assumption ledger in the behavior contract, but no single cross-provider plan artifact is proven by the inspected baseline.
- Mode-specific tool bundles make the permission/tool boundary visible to the operator. The owner’s effective configuration is powerful but permissive: Claude defaults to `bypassPermissions` (`bundle/claude/settings.json:64-75`) and Codex to `approval_policy="never"` plus `danger-full-access` (`bundle/codex/config.toml:6-7`).
- Cursor exposes change review, checkpoint restore, current todos, command-block state, agent status, and parallel agents in one UI ([Agent overview](https://docs.cursor.com/en/agent/overview)).

### 3.3 Where Cursor is worse

- “No tool-call limit” is not a reliability mechanism. The owner has a two-strikes pivot rule, terminal-state outputs, a long-run wrapper requirement, and failure fingerprints (`bundle/claude/AGENTS.md:36-57`). Cursor’s bounded stop-loop example uses a maximum iteration count, but the general agent loop documentation does not establish a hypothesis-aware anti-grind gate.
- Cursor’s `stop`-hook recipe can keep sending `followup_message` until a scratchpad says `DONE` or five iterations pass ([agent best practices, lines 168-210](https://cursor.com/blog/agent-best-practices)). That is convenient, but string-based self-declaration is weaker than the owner’s fresh receipt after the last mutation (`bundle/agents/harness/modules.py:2092-2228`).
- Cursor’s per-model harness tuning is proprietary. It cannot be inspected or regression-tested by the owner; the shared harness source can.

### 3.4 Port

#### CONFIG — reviewable plan contract

For plan-shaped mutating tasks, persist one small Markdown/JSON plan containing: objective hash, assumptions, scoped roots/files, steps, validation receipts expected, permission mode, and owner approval state. Use native plan approval where available; the file is an artifact, not a scheduler.

It is **likely (55-80%)** this reduces orchestrator-fabricated constraints because the plan exposes asserted facts before fan-out and can link each nontrivial premise to a probe; evidence is defect D4 (`INPUT-known-harness-defects.md:151-160`) and Cursor’s editable plan. UNVERIFIED impact size; settle with 50 comparable long tasks randomized between current plan UI and the persisted contract, scoring owner corrections and rework.

#### CONFIG — task-class mode profiles

Define four provider-neutral profiles on native controls: `research-readonly`, `plan`, `local-mutate-sandboxed`, and `isolated-worker`. Each specifies tools, directories, network, approval, and required receipts. This is not a new mode engine.

It is **very likely (80-90%)** that explicit profiles reduce accidental use of blanket bypass modes because the current configurations demonstrably select full bypass (`settings.json:71`; `config.toml:6-7`) and Cursor demonstrates that mode/tool bundles are operable. UNVERIFIED behavioral compliance on this host; settle with policy canaries across both providers.

## 4. Context management

### 4.1 Dynamic discovery is Cursor’s strongest contribution

Cursor’s January 2026 research post describes five file-based mechanisms ([Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)):

1. Long shell/MCP results are written to a file rather than truncated. The agent receives a pointer and can `tail` or read selectively.
2. When context fills and summarization runs, the agent receives a reference to the history file so it can recover details omitted by the lossy summary.
3. `SKILL.md` names/descriptions form a small discovery catalog; full instructions/scripts are loaded only when relevant.
4. MCP tool descriptions are synchronized into one folder per server. The static prompt carries only small discovery information. Cursor reports a 46.9% total-agent-token reduction in MCP-using runs.
5. Integrated terminal sessions are synchronized to files, enabling targeted grep over prior output.

This is deliberately anti-overfit: filesystem primitives and existing search/read tools, not another retrieval daemon.

Cursor also offers explicit `@Files`, `@Folders`, `@Code`, `@Docs`, `@Git`, `@Past Chats`, `@Recent Changes`, `@Lint Errors`, and rules context ([context symbols](https://docs.cursor.com/context/%40-symbols/overview)). Full-folder content may include all files when possible; large files/folders are condensed and the UI indicates inclusion ([files and folders](https://docs.cursor.com/context/%40-symbols/%40-files-and-folders)).

For codebase search, Cursor builds a Merkle tree, detects changed branches, syntactically chunks files, caches embeddings by chunk content, and can reuse a teammate’s similar index after cryptographic content proofs. Cursor reports median time-to-first-query improving from 7.87 seconds to 525 ms, p90 from 2.82 minutes to 1.87 seconds, and p99 from 4.03 hours to 21 seconds ([Secure codebase indexing](https://cursor.com/blog/secure-codebase-indexing)). These are Cursor’s own measurements, not independently replicated here.

### 4.2 What to port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — content-addressed result spill

Mechanism:

1. In the provider adapter, after redaction and before model injection, measure serialized result bytes/lines.
2. Below a conservative threshold, return inline as today.
3. Above threshold, atomically store the complete redacted output under an existing state directory using `sha256(content)` plus a short metadata sidecar: tool, session hash, timestamp, byte count, exit/status, MIME/encoding, and expiry.
4. Return a terminal-state receipt: `SUCCESS:<id> output_spilled=<path> bytes=N preview=<head/tail>`, or a failure receipt if writing fails. Never report success with a missing file.
5. Let the existing Read/`rg` tools retrieve slices. Do not auto-inject the full file later.
6. Garbage-collect by TTL and size cap; never include secrets or unredacted absolute paths.

This directly addresses long MCP/shell output without changing orchestration. It is **very likely (80-90%)** to reduce context consumption on high-volume outputs because Cursor reports a measured reduction from the same pattern and the owner’s corpus includes extensive Bash/WebFetch/MCP usage. UNVERIFIED local magnitude; settle by replaying 200 high-output calls and comparing tokens, summarizations, lost-result corrections, and spill read-back success.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — post-compaction history pointer — UNVERIFIED pending payload/path canary

The owner’s sanitized checkpoint is a strong state summary, but the inspected module writes selected goal/decisions/failures and `.remember/now.md`, not a searchable transcript reference (`modules.py:1440-1515`). Add a redacted, read-only history locator to `PostCompact` context: session-hashed path, index byte range, and a suggested `rg` command. The history itself remains native transcript storage; the hook adds only a pointer.

It is **likely (55-80%)** this improves recovery of exact omitted facts because Cursor identifies lossy summaries as the failure mode and lets the agent consult history, while the owner already sees compaction as a goal-loss boundary (`modules.py:1362-1378`). UNVERIFIED whether both installed providers expose stable transcript paths at the required event; settle by dumping known-positive `PreCompact`/`PostCompact` payloads on both providers and then running a needle-recovery test after forced compaction.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — terminal logs as discoverable files

First prefer native terminal transcript/log paths. If unavailable, extend the result-spill sidecar with `stream_id`, command fingerprint, and process lifecycle so longrun logs are searchable. Avoid duplicating full command output in the event ledger.

It is **likely (55-80%)** this reduces re-runs caused by forgotten terminal output because Cursor uses the mechanism for precisely that purpose and the owner’s contract already says status checks must re-read logs rather than re-run (`AGENTS.md:41-49`). UNVERIFIED effect; settle by mining repeated identical commands after long outputs before/after rollout.

### 4.3 What not to port

Do not build Cursor’s server-side embedding/vector index. That would reintroduce a specifically rejected vector-DB/KG component, expand privacy surface, and duplicate strong native `rg`, language tooling, provider code search, and the owner’s bounded lexical recall. Cursor’s security page says indexing uploads a Merkle tree, stores embeddings in Turbopuffer, stores obfuscated paths/line ranges, and acknowledges both hierarchy leakage and possible embedding reversal ([Cursor security](https://www.cursor.com/security)). Cursor itself also states indexing can experience heavy load and repeat uploads.

**ANTI-OVERFIT GATE:** the accepted ports are files plus existing tools. The vector retrieval stack fails the gate and is rejected.

## 5. Memory and continuity

### 5.1 Cursor memory

Cursor memories are project-scoped rules derived from Chat. A sidecar model passively observes conversations and proposes relevant memories; background-created memories require user approval. The Agent can also create a memory with a tool call when asked or when it notices an important fact. Memories are managed in Cursor Settings → Rules ([Memories docs](https://docs.cursor.com/en/context/memories); GA/approval details in [1.2 changelog](https://cursor.com/changelog/1-2)).

Past conversations can be resumed, referenced through `@Past Chats`, searched, and—since Cursor 3.11—forked into durable side chats that inherit main-chat context and can be mentioned back into the main thread. Transcript search uses a local index designed to scale to thousands of conversations ([3.11 changelog](https://cursor.com/changelog)).

### 5.2 Comparative judgment

Cursor wins on friction: it notices candidate knowledge without requiring the agent to remember a memory-write workflow. It also keeps promotion human-approved.

The owner wins on epistemic structure:

- Semantic memory and objective event history are explicitly distinct (`bundle/claude/AGENTS.md:85-91`).
- Failures have falsifiable preconditions and can be superseded by later milestones (`AGENTS.md:28-34`).
- The shared harness sanitizes and replays objective events and writes compaction checkpoints (`README.md:21-29`; `modules.py:933-1003,1440-1515`).

Cursor’s public memory docs do not describe source-message provenance, contradiction/supersession, validity dates, confidence, or an objective receipt link. This is an **absence from the public docs, not a proven product absence**: one known-present control is that the docs do describe project scope, sidecar generation, approval, direct tool creation, and management UI. A mechanically independent second signal is the 1.2 changelog, which adds memory quality and approval but likewise does not describe provenance. Still, UNVERIFIED whether private/internal memory records carry provenance; settle by exporting or inspecting a created memory record and tracing it back to its source messages.

### 5.3 Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — candidate-memory inbox

At `Stop`, `TaskCompleted`, explicit owner correction, or PR review feedback, produce a **candidate**, never a canonical memory. Candidate fields: proposed fact/rule, project, source event IDs, supporting and contradicting receipts, validity start, expiry/review date, sensitivity label, and action `accept/edit/reject`. Promotion uses the existing basic-memory write tool; rejection is recorded to avoid repeated suggestions. No sidecar model is required initially: use explicit corrections and high-confidence terminal events.

It is **likely (55-80%)** this captures corrections now being lost because the corpus contains 2,268 owner-correction candidates and only 78 of roughly 355 skills were invoked (pinned prompt), while Cursor demonstrates that approval-gated candidate extraction is usable. UNVERIFIED precision and annoyance rate; settle with shadow-mode extraction over 100 sessions, human-label candidates, require ≥70% precision before surfacing, and never auto-promote.

Do not replace basic-memory with Cursor-style generated rules. The recommendation inherits no unverified premise: it preserves the proven canonical stores and adds only an inbox.

## 6. Tool and MCP handling

### 6.1 Cursor mechanism

Cursor supports project `.cursor/mcp.json` and global `~/.cursor/mcp.json`, stdio and remote servers, OAuth, per-tool toggles, approvals by default, and auto-run when explicitly enabled. The IDE displays expandable arguments/results ([MCP docs](https://docs.cursor.com/context/model-context-protocol)). The CLI reads the same MCP configuration as the IDE ([CLI using Agent](https://docs.cursor.com/en/cli/using)). Cursor also supports MCP elicitation for structured user input ([1.5 changelog](https://cursor.com/changelog/1-5)).

The frontier feature is dynamic MCP discovery: server definitions and tools live as JSON under `.cursor`; agents discover/load them only when needed ([2.4 changelog](https://cursor.com/changelog/2-4)). Cursor’s research explains that tool descriptions are synchronized to one folder per server, only names/small hints are static, and status such as re-authentication can be communicated to the agent ([Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)).

### 6.2 Why it matters here

The corpus records 93 MCP servers touched and the worst named integration is a dead Tavily lane repeatedly called (pinned ground truth). The owner already has extremely reliable ToolSearch—5,091 calls with four errors / 0.08% (`corpus.json:87-92`)—so the right design is to feed ToolSearch a healthy, compact catalog, not to statically expose every schema.

### 6.3 Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — server-grouped MCP capability manifests

For each configured MCP server, generate one compact local manifest during existing registration/health checks:

```text
server-id/
  STATUS.json       # enabled, connected, auth-required, last-success, last-error fingerprint
  INDEX.md          # tool names + one-line capability hints only
  tools/
    tool-name.json  # full schema and description, loaded on demand
```

Static context contains only server names, high-level capability tags, and status. The agent searches manifests when relevant. A call router rejects `dead`, `disabled`, or `auth-required` candidates before schema load and proposes a healthy equivalent. A probe can transition status back only after a known-positive handshake/tool-list control.

It is **very likely (80-90%)** this prevents the known dead-MCP retry class because the Tavily failures are specifically “not connected,” the owner’s ToolSearch is already highly reliable, and Cursor’s file-grouped discovery carries liveness/auth state. UNVERIFIED exact prevention rate; settle by replaying all 135 not-connected Tavily fingerprints against a shadow router and requiring zero attempted dead calls plus correct recovery after a canary server is restored.

It is **likely (55-80%)** this reduces prompt tokens because Cursor measured 46.9% reduction on MCP-using runs, but the owner’s providers may already lazy-load some tools (`ENABLE_TOOL_SEARCH=auto:5` at `settings.json:17`). Settlement: capture static tool-schema tokens and total tokens on matched workloads before/after manifest routing.

#### CONFIG — approval by risk, not by tool family

Keep read-only/search MCP calls auto-runnable only when the server is healthy and results are treated as untrusted data. Require approval for mutations, egress with sensitive context, credential changes, and cross-system messages. Cursor’s default per-call MCP approval is safer than blanket auto-run; its one-click toggles are useful UX. The owner’s fetch/MCP prompt-injection rule already supplies the semantic policy (`AGENTS.md:99-106`).

It is **almost certain (90-99%)** that requiring approval for state-changing/egressing calls reduces their unauthorized blast radius relative to blanket auto-run, because the action cannot proceed without an additional authority decision. ## 7. Permission model and isolation

### 7.1 Cursor foreground and CLI

Cursor foreground Agent can require terminal confirmation or auto-run. The CLI supports global `~/.cursor/cli-config.json` and project `.cursor/cli.json` permissions for `Shell(commandBase)`, `Read(pathOrGlob)`, and `Write(pathOrGlob)`; deny takes precedence ([CLI permissions](https://docs.cursor.com/cli/reference/permissions)). Non-interactive mode has write access, and the docs caution that print-mode writing requires force in the permission reference, while the older CLI usage page says non-interactive mode has full write access ([CLI usage](https://docs.cursor.com/en/cli/using)). Treat version-specific behavior as needing a live canary.

Cursor 2.0 introduced kernel-backed sandboxing for supported systems/models: workspace and `/tmp` writes, filesystem reads, no network, and no `.cursorignore` access; escaping the sandbox requires approval. Cursor’s announcement says unsupported models fall back to the prior allowlist ([sandbox announcement](https://forum.cursor.com/t/agent-sandboxing-available-in-cursor-2-0/139449)). This is an official announcement in Cursor’s forum, not independent source inspection.

### 7.2 Cursor cloud

Background/cloud agents run in isolated Ubuntu VMs, clone repositories onto separate branches, can install packages, and auto-run terminal commands. Cursor explicitly warns that internet access plus auto-run creates prompt-injection/exfiltration risk. Secrets are encrypted at rest and injected into the environment; code persists on VM disks while accessible; background agents require retention for days ([Background Agents docs](https://docs.cursor.com/background-agent)).

As of March 2026 Cursor also offers self-hosted cloud-agent workers. Tool execution/code remain in the customer network, while inference/planning stay in Cursor’s cloud; workers connect outbound over HTTPS ([self-hosted cloud agents](https://cursor.com/blog/self-hosted-cloud-agents)). This is a large runtime product from Cursor’s side and would be a **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** proposal for us. It fails this program’s anti-overfit gate because it creates a second runtime/durable execution plane. Reject it for the personal harness unless a future requirement demands always-on remote execution that native Claude/Codex and existing `codex exec` cannot meet.

### 7.3 Comparative judgment and port

Cursor’s foreground sandbox policy is better than the owner’s current blanket bypass defaults. Cursor’s CLI `Shell(git)`-style command-base permission is worse than the owner’s need: it cannot distinguish `git status` from destructive subcommands. The owner’s known D1 defect proves naive payload regexes are also unsafe (`INPUT-known-harness-defects.md:9-107`). The right port is native sandbox isolation plus semantic argv parsing for the small dangerous set, not broader regexes.

#### CONFIG — safe default profiles

- Untrusted/new repo: read-only or sandboxed; network off; no repo-local hooks/MCP until inspected.
- Trusted local mutation: workspace writes, tests/build, network by explicit domain/capability.
- Parallel mutation: worktree/branch required.
- Cloud/remote: no broad secrets; outbound network allowlist; ephemeral task credentials.

It is **almost certain (90-99%)** these profiles reduce blast radius relative to `bypassPermissions` and `danger-full-access`, because they remove permissions by construction and the current full-access settings are directly observed (`settings.json:64-75`; `config.toml:6-7`). The remaining uncertainty is adoption/escape frequency, not direction of risk reduction.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — typed command discriminator — UNVERIFIED pending native payload-schema dump

Parse the actual tool verb/argv and target path before applying dangerous-operation policy. Never scan prose bodies for command words. Reuse one shared discriminator across guards and regression-test the nine recorded false fires plus real dangerous commands. This is already the live defect’s prescribed direction (`INPUT-known-harness-defects.md:78-91`).

UNVERIFIED whether every provider hook payload contains lossless argv/verb/path at the needed pre-action event; settle by dumping native payload schemas with a known-positive safe command and a known-positive dangerous fixture before implementation. If payloads are insufficient, do not silently fall back to prose regexes.

It is **likely (55-80%)** that the discriminator remains a small shared-bus change because the normalized envelope already carries tool name and input (`models.py:10-39`), but lossless provider-specific argv/path coverage is the unresolved evidence named above.

## 9. Multi-agent support

### 9.1 Cursor mechanism

Cursor 2.4 introduced default and custom subagents. They have separate context and can be configured with prompts, models, and tool access; defaults specialize in research, terminal work, and parallel streams ([2.4 changelog](https://cursor.com/changelog/2-4)). Cursor 3.2 added `/multitask`, which decomposes requests or queued messages across async subagents. Worktrees isolate background branches, and results can move into the foreground ([3.2 changelog](https://cursor.com/changelog/04-24-26)).

Cloud subagents can run in their own VMs/branches with `/in-cloud`; `/babysit` iterates on a PR toward merge readiness while the parent continues. Sessions can move local → cloud → local, and many cloud agents can run in parallel ([Cloud environment/subagents changelog](https://cursor.com/changelog/cloud-in-agents-window)). Background Agents API supports up to 256 active agents per API key ([API overview](https://docs.cursor.com/background-agent/api/overview)).

## 10. Verification and self-check

### 10.1 Cursor mechanisms

- Agent can auto-run commands and auto-fix errors ([Modes](https://docs.cursor.com/agent)).
- Plan Mode exposes a reviewable plan before building ([agent best practices](https://cursor.com/blog/agent-best-practices)).
- Review Changes shows diffs; checkpoints restore agent-created edits but are not version control and do not track manual edits ([Agent overview](https://docs.cursor.com/en/agent/overview); [Checkpoints](https://docs.cursor.com/en/agent/chat/checkpoints)).
- Cloud agents run applications and produce videos, screenshots, logs, and merge-ready PRs for review ([computer-use changelog](https://cursor.com/changelog/02-24-26)).
- Bugbot reviews PR diffs automatically or on command, leaves inline explanations/fix suggestions, and supports nested `.cursor/BUGBOT.md` based on changed-file ancestry ([Bugbot docs](https://docs.cursor.com/bugbot)).
- Cursor says Bugbot’s resolution rate rose through experiments and parallel bug-finding passes combined by majority vote; its January 2026 post reports improvement from 52% to over 70% resolution ([Building a better Bugbot](https://cursor.com/blog/building-bugbot)). April 2026 added feedback-learned rules and reported 78% resolution ([Bugbot changelog](https://cursor.com/changelog/04-08-26)). These are vendor measurements and use “resolved by merge” as a proxy, not ground-truth precision.

### 10.2 Where the owner is better

The owner’s completion gate links claim families to fresh, typed receipts after the last mutation, detects zero-diff “fixed” claims, and requires a green rerun of the exact failing fingerprint (`modules.py:2092-2228`). Cursor’s public general-agent docs do not establish an equivalent receipt invariant. This is an absence-from-docs claim supported by two mechanically independent documents: the Agent tools/modes docs describe auto-fix but no receipt gate, and the checkpoint docs explicitly scope rollback rather than verification. Detector control: both documents do identify known-present verification-adjacent mechanisms (auto-fix and checkpoints). UNVERIFIED whether Cursor’s proprietary system prompt internally enforces a stronger test-after-edit policy; settle with controlled tasks where a stale pre-edit test pass exists and observe whether Cursor accepts it as completion evidence.

Cursor’s automatic checkpoints are also weaker than a transactional rollback: only Agent changes are tracked, manual edits are excluded, storage is local, cleanup is automatic, and Cursor says they are not version control ([Checkpoints](https://docs.cursor.com/en/agent/chat/checkpoints)). Do not treat checkpoint restore as proof that external effects, generated artifacts, databases, or git operations were reversed.

### 10.3 What to port

#### CONFIG — separate implementation from independent review

After a meaningful mutation, invoke the existing reviewer model/agent with the original objective, diff, changed-file rules, and fresh receipts—not the implementer’s narrative. Trigger at PR/CI boundaries rather than every edit. Preserve the owner’s no-raw-output handoff.

It is **likely (55-80%)** this catches defects the implementer misses because Cursor’s Bugbot is deployed at PR boundaries and its own experiment history reports improved resolution, but vendor “resolved by merge” is an imperfect proxy. UNVERIFIED local yield/cost; settle with shadow reviews over 100 PRs and human adjudication.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — learned review-rule candidates

From explicit reviewer feedback, accepted/rejected findings, and later superseding receipts, generate candidate rules with support count, last-hit date, counterexamples, scope glob, and expiry. Promote only after human review or a conservative threshold plus no contradictory evidence; automatically demote stale rules to candidate status. This ports Cursor’s feedback-learning idea without a trained critic or auto-editing the canonical rules.

It is **likely (55-80%)** this reduces repeat review misses because Cursor reports learned rules from reactions/replies and the owner has 2,268 correction candidates. UNVERIFIED precision and gaming resistance; settle with offline backfill and holdout PRs, measuring false-positive change and avoided repeat findings.

#### CONFIG — artifact-backed completion

For UI/browser tasks, require screenshot/video/log artifacts plus tests where appropriate. For code tasks, require diff + fresh typed receipt. A screenshot is evidence of appearance, not of internal correctness; a passing unit test is not evidence of visual fidelity.

It is **very likely (80-90%)** that modality-matched artifacts make completion claims more auditable because the owner’s fresh-receipt gate already ties evidence to post-mutation state (`modules.py:2092-2228`) and Cursor’s cloud review exposes screenshots/videos/logs. ### 10.4 What not to copy

- Do not adopt majority vote as truth. Correlated agents can agree on the same wrong claim; use it only for candidate ranking, followed by objective checks.
- Do not run a blind “grind until DONE” stop loop. Require changed evidence or a discriminating check after failure, retain the two-strikes pivot, and cap continuations.
- Do not buy an observability SaaS or trained critic to emulate Bugbot. Existing hooks, receipts, reviewer agents, PR/CI, and local ledgers are enough.
- Do not treat checkpoint rollback as durable execution or external-effect reversal.

## 12. Explicit anti-overfit gate

Accepted recommendations ride existing buses:

- Hook adapter/dispatcher.
