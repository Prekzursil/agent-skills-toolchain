## Severity-ranked defects

### B1 — False-valued results mint passing verification receipts — **BREAKING**

Mechanism:

* `_receipt_command` explicitly discards `tool_name` (`ledger.py:262-280`), so any tool input containing `command`, including a non-shell MCP tool, can be classified as an executed command.
* `_receipt_status` serializes the whole result and regex-matches positive words including `ok` and `passed` without testing their values (`ledger.py:354-371`). A JSON key is enough.
* `ClaimWarningModule` trusts a fresh passing receipt to substantiate completion (`modules.py:2092-2137`).

Independent executable signal:

```json
classify_receipt("mcp_fake", {"command":"pytest"}, {"ok":false})
=> {"receipt_class":"test","status":"pass","passed":0,"failed":0}
```

Impact: a failed/false tool response can suppress the completion warning and allow “tests pass” or “fixed” to be presented as verified. This directly corrupts factual state, so the grade is breaking rather than noisy.

Test gap: no test contains `ok: False` or `passed: False`; `rg` found no such receipt case across `tests/`.

### B2 — Failure classification treats `error: false` as a failure — **BREAKING**

Mechanism: `_result_is_failure` calls `str(result.get(key))` and tests truthiness (`modules.py:521-539`). `str(False)` is the non-empty string `"False"`, so `{"error": false, "ok": true}` becomes a failure. It then also regex-scans serialized field names (`modules.py:540-545`), the same use-vs-mention class as pinned defect D1.

Independent executable signal:

```text
_result_is_failure({"error": False, "ok": True}) => True
```

Impact: anti-degeneration can treat a successful result as a failure, contaminating post-error-haste and loop decisions. This reproduces the pinned “field name whose value was false” correctness class in the shared harness code.

### B3 — Completion claim detector is negation/use-vs-mention blind — **BREAKING**

Mechanism: `_CLAIM` and `_FAMILIES` are word regexes with no negation or quotation parsing (`modules.py:2000-2041`). `_base_gate` injects whenever the word class matches without evidence (`modules.py:2111-2137`).

Independent executable signal:

```text
last_assistant_message = "This is not fixed; the tests did not pass."
ClaimWarningModule.run(...) => action=inject, reason=unverified_completion_claim
```

Impact: truthful denial of completion is itself flagged as a completion claim. This is self-amplifying when documenting failures and is the exact architectural class in pinned defect D1/D1a. The test suite has no `not fixed` or `did not pass` claim case.

### B4 — Deploy is not a full replacement; obsolete live files survive success — **BREAKING**

Mechanism:

* Candidate and live hashes are enumerated separately (`install.py:742-745`), but CAS and writes iterate only `candidate` (`install.py:770-787`).
* Parity checks only candidate paths (`install.py:794-805`). There is no `live - candidate` deletion or mismatch set.
* Receipt hashes list only candidate files (`install.py:683-702`), hiding survivors.

Independent temp-tree experiment:

```json
{"source":{"a.txt":"new"},"live_before":{"a.txt":"old","stale.txt":"stale"},
 "deploy_rc":0,"stale_survived":true}
```

Impact: removed hooks, tests, or modules remain executable in the deployed tree even after a reported successful “full” deploy. This matters directly to replacement architecture and can preserve dead or vulnerable code.

### B5 — Missing-file parity failure raises and does not restore — **BREAKING**

Mechanism: parity computes `_hash_file(dst / rel)` without an existence/error guard (`install.py:801-805`). Only `DeployCASConflict` is caught (`install.py:829-843`); other exceptions escape. `_restore_tree` runs only inside the ordinary mismatch branch (`install.py:806-818`).

Independent temp-tree experiment deleted the candidate in `_after_write`:

```json
{"exception":"FileNotFoundError","restored_content":null}
```

Impact: an integrity failure can leave the live target missing and return by exception rather than the documented status-1 fail-closed restore. `tests/test_install_deploy.py:130-156` covers content corruption, not disappearance.

### B6 — Deploy lock acquisition is check-then-replace, not exclusive — **BREAKING**

Mechanism: `_acquire_deploy_lock` tests `lock.exists()` and then uses `atomic_write_json`, which ends in `os.replace` (`install.py:623-647`, `storage.py:10-24`). It does not use `O_CREAT|O_EXCL`, unlike the ledger lock (`ledger.py:431-466`).

Independent synchronized two-thread experiment forced both callers past the existence check. On Windows, one acquired and the other raised uncaught `PermissionError` during `os.replace`, rather than receiving `DeployLockError`/structured contention. This demonstrates the race even though both did not enter the critical section.

Impact: concurrent deployment can crash outside the documented contention path. The held-lock unit test writes a lock before the call (`tests/test_install_deploy.py:164-187`); it does not test simultaneous acquisition.

### B7 — Runtime config drift gate is currently inert — **BREAKING for the claimed gate**

Mechanism: `_config_drift` returns allow unless `installed.json["settings"]` is a dict (`modules.py:874-897`). The deployed `installed.json` has no `settings` key. A live `ConfigChange` probe returned `SUCCESS:hook`, `action=allow`, `reason_code=ok`.

Independent operational signals:

* The exact deployed receipt lacks the required snapshot.
* All 107 accumulated Claude `ConfigChange` terminal records were allow; current live settings are independently reported drifted by the reconciler.

Root lifecycle: default `install()` writes `settings` (`install.py:479-528`), while deployment excludes source `installed.json` and merge-preserves only whatever is already live (`install.py:76-89`, `install.py:683-702`). The current receipt proves deployment occurred without a preserved installer snapshot. The code-level gate works only after the separate registration installer has seeded that key.

## Architecture trace: what actually runs

1. `registration.build_hooks` generates command hooks for 16 shared event names, with extra Claude-only local-TUI, workflow-monitor, and worktree hooks (`registration.py:15-54`, `registration.py:98-174`). Current live registrations do not match this generated set.
2. `dispatcher.main` reads stdin JSON, normalizes it, runs ten ordered modules, renders native output, and always exits 0 on internal failure (`dispatcher.py:518-556`).
3. `normalize_event` maps aliases into the closed event envelope (`adapters.py:73-146`). `render_output` emits denial, continuation, context, or empty JSON (`adapters.py:149-207`).
4. The dispatcher stops module execution at the first block to prevent later persistence of blocked payloads (`dispatcher.py:304-309`). This ordering is correct and tested at `tests/test_dispatcher_and_registration.py:96-132`.
5. Module order is secret guard → ledger → goal → checkpoint → recall → anti-degeneration → claim warning → design reminder → subagent lifecycle → BC offset (`modules.py:421-433`, `modules.py:2599-2613`).
6. New heuristic gates normally route through `stage()`; safety and deterministic tiers default enforce, heuristic defaults shadow, advisory defaults advise (`modules.py:120-136`, `modules.py:389-420`). Several established gates bypass staging: goal reinjection, base claim warning, design intent reminder, subagent handoff/hollow output.
7. The ledger uses an exclusive file lock and fsyncs appended event lines (`ledger.py:431-466`, `ledger.py:817-881`). State JSON is a projection/cache and legacy Claude ledger is read through (`ledger.py:909-942`, `ledger.py:1217-1280`).
8. Recall is lexical/local only: index build reads Markdown, stores redacted summaries/keywords, and runtime requires a high overlap threshold before injecting (`recall_index.py:251-326`, `modules.py:1608-1683`). No vector DB, KG, model, or network search exists in this subsystem.
9. Checkpoints are secret/path-redacted, bounded, and contain hashed session/project identifiers (`modules.py:1440-1554`).
10. Terminal and shadow telemetry are local files. Terminal records every dispatch; shadow samples Pre/PostToolUse 1-in-5 using a time-dependent hash and records all other events (`modules.py:342-387`, `dispatcher.py:485-515`).

## Coverage quality and dead-path assessment

The suite is unusually large—9,113 test lines for 6,478 production lines—and achieves real branch reach. It successfully covers malformed JSON, provider aliases, concurrency in ledger append, state-write crashes, stale locks, security redaction, receipt freshness, mutation ordering, gate modes, mixer priority, breaker quarantine, install reconciliation, and deploy corruption. This is valuable.

The weakness is **oracle coupling**: many `test_cov_*` cases force exceptions and assert the current branch return, while cross-component reachability and negative truth semantics are under-tested. Three concrete manifestations:

* A dead event handler is 100% covered because a unit test calls it directly.
* A deployer is 100% covered while a source-deleted file survives success and a missing parity file escapes restore.
* Receipt lines are 100% covered while `ok:false` becomes pass.

Thus “100% production statement coverage” is a milestone, not a correctness verdict.
