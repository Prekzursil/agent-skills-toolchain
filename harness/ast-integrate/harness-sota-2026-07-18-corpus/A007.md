# A007 — Coherence audit of `~/.claude/rules/common/git-workflow.md`

## Scope and verdict

This unit audited the unpacked, read-only subject at `/local_disk0/codexwork/bundle`; it wrote only this artifact. The target file was read in full: `/local_disk0/codexwork/bundle/claude/rules/common/git-workflow.md:1-38`.

The target is not a coherent git-workflow single source of truth. It is a 38-line, source-extension-scoped rule that (a) specifies a Conventional-Commit-like subject, (b) makes a global attribution claim, and (c) delegates PR work to a command whose implementation does not do what the rule says. The most consequential verified defects are:

1. `git-workflow.md:36-38` says `/pr-shepherd` analyzes the branch history, drafts the PR summary/test plan, and pushes with `-u`; the command requires an existing PR and only monitors it (`commands/pr-shepherd.md:15,28-54`). This is **STALE**.
2. The commit subject convention at `git-workflow.md:23-30` has no validator in the active hook wiring (`settings.json:139-283,310-355`; `_dispatch/manifest.json:144-225`). This is **UNENFORCED**.
3. The rule is scoped only to listed source extensions (`git-workflow.md:1-20`) even though its commit, attribution, and PR policy is not language-specific. Markdown-, JSON/YAML-, PowerShell-, and other nonmatching maintenance turns can miss the rule. This is **STALE** scope.
4. The command reached through `/pr-shepherd` mandates a foreground `gh pr checks ... --watch` (`commands/handle-pr-comments.md:495-505`), while the higher-precedence behavior contract requires every operation expected to exceed 60 seconds to use `longrun` plus background monitoring (`AGENTS.md:41-49`). This is a **CONTRADICTION** resolved by AGENTS precedence.
5. Active git safety enforcement is not documented in this canonical-looking file: a Bash-only force-push gate and a Bash-only test-tamper gate are wired at `settings.json:151-171`, while the rule says nothing about either. These are **UNRULED** here; the force-push policy is instead in `AGENTS.md:93-98`.

It is **almost certain (90-99%)**, based on the target text, active hook registration, hook manifest, and command definitions cited above, that editing this rule plus the existing command/hook bus is enough to repair the static coherence defects without adding a service or orchestration runtime. This confidence does not assert that the edited behavior would be live-loaded correctly; that runtime premise is **UNVERIFIED — the settling experiment is a disposable Claude session that performs one matching source commit, one Markdown-only commit, one PowerShell-tool commit, and one synthetic PR lifecycle while capturing loaded rules and hook receipts**.

## Expanded analysis and remedies

### GW-01 — Universal policy hidden behind source-file paths

The frontmatter at `git-workflow.md:1-20` covers `.py`, JS/TS variants, Go, Rust, Java, Ruby, PHP, C/C++, C#, Swift, Kotlin, and shell. It excludes at least Markdown, JSON, YAML, TOML, XML, PowerShell, and plain-text-only turns. Yet the rule's entire substantive content concerns a commit message, attribution, and PR procedure (`:21-38`), none of which is language-specific.

This is not merely theoretical scope nitpicking. The harness itself is maintained heavily through Markdown, JSON, and PowerShell: the inspected subject contains `settings.json`, dozens of `.md` rules/commands, and `hooks/create-worktree.ps1`. The earlier audit claim in `inputs/audit-findings/A31.md:68-70` noticed the same issue, but that prior finding was treated only as a claim; this unit independently verified the target frontmatter and the unpacked file types.

Resolution: **CONFIG**. Remove path scoping from the git policy. It is **very likely (80-90%)**, based on `rules/README.md:12-29` calling common rules universal and on the target containing no language-specific content, that unconditional loading is the intended design. Runtime load behavior is **UNVERIFIED — settle it by launching disposable sessions whose only changed files are `README.md`, `settings.json`, `workflow.yml`, and `script.ps1`, then inspect the loaded-rule diagnostic before any commit**.

### GW-02/GW-03 — Commit grammar is duplicated and underspecified

The target shows `<type>: <description>` and an optional body (`git-workflow.md:23-30`). It omits scope syntax, breaking-change notation, footers, subject-length rules, issue references, fixup/revert handling, generated/checkpoint commits, and repository-specific overrides. This unit does not assume all of those are needed; their omission matters because other bundled instructions already demand “detailed” messages (`development-workflow.md:55-58`) and checkpoint-name commits (`commands/checkpoint.md:11-18`).

The checkpoint command can satisfy both instructions only if the model invents a compliant mapping, such as `chore: checkpoint core-done`. That silent reconciliation is exactly what a coherence audit should remove.

Resolution: **CONFIG**. Put the full grammar in one rule and make all other files link to it. It is **very likely (80-90%)**, based on the direct ambiguity and the target's existing type list, that an explicit checkpoint template will reduce divergence. Whether a commit body should be mandatory for high-risk changes is **UNVERIFIED — settle it by sampling actual repository commit conventions and protected-branch/commitlint configuration, neither of which is included in this bundle**.

### GW-04 — Review severity has two incompatible gates

`development-workflow.md:50-58` instructs the agent to address both CRITICAL and HIGH issues before commit/push. `code-review.md:75-78` calls HIGH a warning, and `:129-133` says a HIGH-only review may merge with caution. Because both are common rule files, AGENTS §10 does not choose. The target imports this conflict by identifying development-workflow as the full pre-git process (`git-workflow.md:36-38`).

Resolution: **CONFIG**. Establish one review policy table and reference it. This unit deliberately does not decide whether HIGH blocks because §10 says not to silently select between same-level conflicts. A design owner must choose the risk posture and encode it once.

### GW-05/GW-12 — `/pr-shepherd` is described as a creator and a merger but implemented as a monitor

Three incompatible contracts coexist:

- Git rule: branch-history analysis, summary/test-plan drafting, upstream push (`git-workflow.md:36-38`).
- Command steps: find an existing PR and monitor it until all CI/threads are clear (`commands/pr-shepherd.md:28-54`).
- Command title/description: monitor “through merge” (`commands/pr-shepherd.md:2,7`), while its actual success condition is only ready-to-merge (`:52-54,73`).

The command also says to load separate `pr-shepherd` and `handling-pr-comments` skills (`commands/pr-shepherd.md:38-50`). Those installed skill definitions were not in the bundle, so they cannot repair the verified mismatch on the evidence available here.

Resolution: **CONFIG** for naming/terminal states, with **BUILD-SMALL** only if PR creation is added. A clean minimal decomposition is `pr-create` (base discovery, diff, draft, push, create) followed by `pr-monitor` (CI/review state). It is **likely (55-80%)**, based on the sharply different state machines, that two explicit commands would be clearer than one overloaded command. This forward-looking preference is **UNVERIFIED — settle it with a small evaluation over representative “open a PR,” “watch PR 123,” and “merge when green” prompts, scoring correct route and unauthorized mutation rate**.

### GW-06 — “Attribution disabled globally” is false as written

Settings do clear automatic commit and PR attribution (`settings.json:22-25`), so the narrow factual core of `git-workflow.md:32` is correct. But the word “globally” conflicts with the mandatory Claude attribution appended to every review reply (`commands/handle-pr-comments.md:484-493,507-515`).

Resolution: **CONFIG**. Say exactly which automatic surfaces are disabled. Then record a conscious, single policy for review-comment attribution. Precedence does not decide this because the command/rule relationship is not listed in AGENTS §10.

### GW-07 — PR monitoring violates the long-operation contract

The higher-level contract requires expected >60-second operations to run via `longrun` and background Monitor (`AGENTS.md:41-49`). The review-comment command calls `gh pr checks $PR_NUMBER --watch` directly (`commands/handle-pr-comments.md:495-503`). `/pr-shepherd` itself already describes a background 60-second poll (`commands/pr-shepherd.md:41-45`), so the harness has two monitoring approaches inside one lifecycle.

Resolution: **BUILD-SMALL**. Reuse one bounded poll on the existing command/hook bus; emit terminal receipts. It is **almost certain (90-99%)**, based on the direct textual contradiction and existing background-poll description, that removing the foreground watch restores static coherence. Runtime reliability is **UNVERIFIED — settle it with a synthetic PR whose checks transition pending→success and another pending→failure, verifying heartbeat, timeout, user status, and terminal receipt**.

### GW-08/GW-09 — Core demands are advisory but written as mandates

No bundled active hook validates the target's type list, and no hook routes PR work to `/pr-shepherd`. The settings grant Bash and PowerShell operation (`settings.json:26-75`) and wire many PreToolUse hooks (`:139-283`), proving the mechanism exists; the relevant validators simply are not in the active lists.

This makes the remedy depend on intent:

- If conventional commits are a preference, change imperative language to a preference and avoid a hook.
- If they are a harness invariant, add a small validator that honors stricter repository-native commitlint/commit-msg hooks.
- PR routing should remain a nonblocking injection; AGENTS §6 says only irreversible/dangerous conditions should block (`AGENTS.md:64-70`).

Resolution: **BUILD-SMALL** for a commit validator; **CONFIG** for nonblocking PR discovery. It is **likely (55-80%)**, based on repeated shell-quoting failures in the corpus and the low complexity of parsing a commit subject, that a structured argv-aware check will be more reliable than more prompt text. The precise false-positive rate is **UNVERIFIED — settle it with fixtures covering `-m`, multiple `-m`, `-F`, amend/no-edit, merge, revert, fixup/squash, `git -C`, `git.exe`, Bash, and PowerShell**.

### GW-10/GW-11/GW-13 — Git hooks and their companion skill enforce policies the git rule never states

The force-push gate is real and active for Bash (`settings.json:151-159`; `hook.py:52-58`; `tripwire.py:15-18,39-47`). Its regex blocks `-f/--force` on any branch, while the cross-tool contract only names main/master (`AGENTS.md:96-98`). This is allowed as a stricter lower layer under `AGENTS.md:129-130`, but it is invisible in the supposed git workflow and is asymmetric because the active matcher is only `Bash`, despite PowerShell being enabled (`settings.json:5-7,141,151-159`).

The test-tamper gate is also active only for Bash (`settings.json:162-170`). It scans staged test diffs on `git commit` (`guard.py:224-275`), can block high-confidence weakening depending on mode (`:295-313`), and otherwise tells the model to put an explanation in the commit message (`:315-320`). The canonical commit grammar never defines such an explanation.

The only bundled companion skill adds another mismatch. It reproduces the hook's message that explicit approval permits re-running with `FORGE_NO_FORCE_PUSH_OFF=1` (`hooks/no-force-push/SKILL.md:13-17`), then says the opt-out is permitted only for a confirmed false positive (`:19-25`). A genuinely approved force-push is not necessarily a false positive. The skill therefore leaves the operator without a coherent allowed path for the very approval state its quoted message recognizes.

Resolution proposal 1: **CONFIG** — document the policies and one approval/override procedure in the canonical git rule and companion skill. Resolution proposal 2: **BUILD-SMALL** — normalize parsing and coverage across shell tools. The no-force predicate's broader blind spots are outside this unit's primary target, but `tripwire.py:18` visibly requires literal `git push`; therefore variants such as global git options are not covered by that regex. A complete parser change is **UNVERIFIED — settle it with a nonexecuting fixture matrix for `git -C repo push`, `git.exe push`, `--force-with-lease`, `--mirror`, force refspecs, aliases, chained commands, quoted prose, Bash payloads, and PowerShell payloads**.

## Corpus: is the rule actually followed?

### What the corpus can establish

The corpus is high-coverage for its designed fields: `corpus.json:_meta` reports 11,633 files, 10.62 GB, 1,564,084 lines, zero failed files, one bad line, and 32 oversized lines. Its note says counts are exact and samples capped.

It establishes one concrete operational failure relevant to git workflow execution: `corpus.json:error_fingerprints` contains a PowerShell `ParserError` fingerprint with count 3 where a commit used Bash command substitution/heredoc syntax inside PowerShell: `git -C ... commit -m "$(cat <<'EOF' ...)"`; the fingerprint was seen in `agent-a34a09f457e613a69.jsonl`, `agent-a3a3ccaa99bb4b244.jsonl`, and `agent-a959ca0d32a9d8da6.jsonl`. This does not prove the commit subject violated the eight-type grammar. It proves the documented git workflow does not prevent a recurrent platform-invalid way of trying to supply a multiline message.

Classification: **badly written/incomplete for this Windows owner**, not “wrong.” The format may be desirable, but the rule provides no PowerShell-safe invocation and does not point to the Windows-shell rule from its commit section. Resolution: **CONFIG** — link `windows-shell.md`, show native PowerShell-safe examples using separate `-m` arguments or a temporary message file, and avoid Bash heredoc/substitution syntax in PowerShell.

### What the corpus cannot establish

The distilled corpus does not retain successful Bash/PowerShell command payloads or commit subjects as a dedicated field. Its `tool_usage` provides aggregate counts/error rates; `error_fingerprints` provides normalized failures; `sessions` provides file/time/size metadata; and capability use provides invocation names/counts. Therefore it cannot calculate:

- the percentage of successful commits using one of the eight types;
- the percentage of PRs created through `/pr-shepherd`;
- whether automatic attribution was absent from produced commits/PR bodies;
- whether the force-push or test-tamper hooks fired in production.

The last point is especially constrained: `corpus.json:hooks.DETECTOR_STATUS` explicitly says the hook detector is broken because it observed zero fires on a known-positive control and orders consumers to treat the entire hooks section as no data. This unit does so. Empty `hooks.fires` and `hooks.blocks` are not evidence of non-use.

The absence of `pr-shepherd` from `corpus.json:capability_use.skills_invoked` is also not enough to claim the slash command was unused: the command may load a skill through a path the capability detector does not label with the command name. A second independent signal is unavailable in the distilled data.

## Recommended coherent replacement shape

This is not a proposal for a second runtime. It keeps the existing rules, commands, native repository hooks, and Claude hook bus; it passes the anti-overfit gate.

1. **CONFIG — unconditional `git-policy.md`**: allowed commit grammar; repository-native override rule; no-verify and force-push safety floor; precise attribution scope; safe Bash/PowerShell examples; explicit pointer to `windows-shell.md`.
2. **CONFIG — `development-workflow.md` becomes pointers**: retain research/TDD/review ordering but delete duplicate commit and severity semantics.
3. **CONFIG — explicit PR terminal states**: `PR_CREATED`, `READY_TO_MERGE`, and `MERGED`; user authorization required where appropriate.
4. **BUILD-SMALL — argv-aware git preflight**: one existing-bus check shared by Bash and PowerShell; prefer native `commit-msg`/commitlint when a repo supplies one; only block truly invalid commit subjects or safety events.
5. **BUILD-SMALL — bounded PR state poll**: one background/`longrun` implementation with heartbeat and terminal receipts; no bare foreground `--watch`.

It is **very likely (80-90%)**, based on the fact that every proposed mechanism maps to an already-present rule, command, hook matcher, or repository-native hook surface, that this shape reduces contradiction without adding orchestration complexity. The net behavior improvement is **UNVERIFIED — settle it with an evaluation suite measuring route accuracy, false blocks, shell parity, successful PR creation, bounded monitoring, and correct terminal-state reporting before deployment**.

No proposal introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
