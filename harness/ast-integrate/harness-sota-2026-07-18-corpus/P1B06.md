## Executive verdict

The JSON is syntactically accepted and most UI/model settings are valid, but the subsystem as a whole is **DEGRADING with two BREAKING control-plane defects**.

1. **BREAKING — permissions describe protections that the selected mode bypasses.** The file grants `C:` and `D:` as additional directories and starts every session in `bypassPermissions` (`settings.json:26-75`), then separately lists allow/deny rules (`:27-69`). Official documentation says bypass mode skips the permission layer and is only for isolated containers/VMs without internet access; this is a native Windows host with network enabled. The direct evidence (configured mode and full-drive scope) plus the mechanically independent official runtime semantics support an **almost certain (90-99%)** conclusion that the declarative allow/deny arrays do not provide their apparent protection in ordinary sessions. A separate credential hook may catch a subset of reads, so this report does not claim that every credential read is unguarded.

2. **BREAKING — custom worktree creation defeats `worktree.baseRef: "fresh"` and expects an obsolete payload.** `settings.json:506-533` installs a `WorktreeCreate` command and sets `baseRef` to `fresh`. The official hook reference says configuring this hook replaces native git worktree behavior and the current input provides `name`; `create-worktree.ps1:114-139` instead reads `worktree_config`, invents a random name when it is absent, and converts missing/`fresh` to `HEAD`. These are independent configuration, implementation, and API signals. It is **almost certain (90-99%)** that current worktrees branch from local `HEAD`, not `origin/<default-branch>`, unless an undocumented compatibility payload is also supplied. UNVERIFIED compatibility detail: capture one live `WorktreeCreate` stdin payload to settle whether `worktree_config` is still included in addition to documented `name`; the mismatch and `fresh -> HEAD` behavior remain defects either way.

3. **BREAKING management/observability, not proven activation failure — plugin registry is all NULs.** The eight true switches are at `settings.json:572,589,600-607,621`. `C:\Users\Prekzursil\.claude\plugins\installed_plugins.json` is exactly 38,989 NUL bytes and cannot parse; `claude plugin list --json` returns `[]`. The detector has known-positive controls: `known_marketplaces.json` parses nine registered marketplaces, all eight enabled plugin cache roots exist, `~/.claude.json:763-831` records recent usage for enabled plugins, the corpus records multiple plugin skills, and audit unit A07 measured five live metaswarm hook executions. Therefore it would be false to say the plugins are inactive. The correct conclusion is that installed-plugin inventory, versions, and native management are **breaking**, while activation is independently proven for several plugins and otherwise itemized below.

4. **DEGRADING — hooks are broad, duplicated, and measurably expensive/noisy.** The file has 18 events, 38 groups, 38 command handlers, 19 unique command targets (`settings.json:81-529`). All targets exist and all 17 Python files parse with `ast.parse`; both PowerShell scripts parse with zero parser errors. Those are wiring/syntax signals only. Live evidence is worse: `INPUT-known-harness-defects.md:9-107` confirms false positives across PreToolUse, PostToolUse, and Stop; A07 reports metaswarm SessionStart p50 50.970 s, local Stop p50 10.422 s, and an estimated shared Pre+Post warm floor near 0.42 s (`findings/A07.md:3-5,7-21,39-53`).

5. **DEGRADING — one top-level key is obsolete/unknown.** `autoCompactWindow: 1000000` (`settings.json:686`) is absent from both current official settings documentation and the published JSON schema; the supported control is environment variable `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. The schema allows extra properties, so its absence does not make the whole file invalid. It is **very likely (80-90%)** inert in 2.1.214; experiment: launch once with debug logging and compare the resolved auto-compact capacity with and without only this key. The active `model: opus[1m]` already supplies a real 1M window, so current behavior may accidentally match the intended value.

`claude doctor` found no installation issue and did not reject this settings file. It did report missing environment variables for optional MCP groups `cloud-hub`, `social-hub`, and `search-hub`; those originate outside this file, so they are a cross-subsystem gap rather than a `settings.json` defect.
