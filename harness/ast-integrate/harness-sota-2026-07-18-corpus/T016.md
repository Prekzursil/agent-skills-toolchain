# T016 — Competitive teardown: Continue

**Unit:** T016  
**Research date:** 2026-07-19 UTC  
**Subject:** Continue, specifically the final Continue 2.0.0 code line and current official documentation  
**Comparison target:** the owner's Claude Code + Codex + shared-harness installation represented in the unpacked read-only bundle  
**Disposition:** borrow four small mechanisms; do not adopt Continue as a replacement runtime

## Executive verdict

Continue is no longer a frontier harness to replace ours with. Its own current landing page says that the repository is no longer actively maintained, calls 2.0.0 the final release, and says the final release removed authentication and anonymous telemetry ([official announcement](https://docs.continue.dev/), lines 15–27 in the rendered page). GitHub published `v2.0.0-vscode` on 2026-06-19 ([release](https://github.com/continuedev/continue/releases/tag/v2.0.0-vscode)). The repository UI is not marked GitHub-archived, so “read-only” here is the maintainer's stated project status rather than the GitHub archive bit. It would be a category error to replace an actively evolving Claude/Codex-native harness with this frozen second runtime.

The useful Continue ideas are much smaller and fit the existing buses:

1. **Restore native, least-privilege permission defaults.** Continue defaults reads to allow and writes/shell to ask, makes headless `ask` tools unavailable unless explicitly granted, and supports tool-plus-argument patterns. Our live setup does the opposite: Claude uses `bypassPermissions`; Codex uses `approval_policy = "never"`, `danger-full-access`, and an elevated Windows sandbox (`/local_disk0/codexwork/bundle/inputs/audit-findings/F05.md:8-14`).
2. **Advertise only connected MCP tools and quarantine dead servers before the first model turn.** Continue constructs its tool list only from connected servers and, in headless mode, reports initialization failures before work begins. This directly targets the measured dead-Tavily pattern without copying Continue's overly harsh “one dead server aborts the run” behavior.
3. **Use one lazy skills loader across compatible roots.** Continue discovers `SKILL.md` packages in workspace `.continue/skills`, workspace `.claude/skills`, and global Continue skills, exposes only name/description initially, and reads the selected body through a tool. This is a compact answer to our split-brain skill roots and high catalog cost, not a new router or store.
4. **Promote the already-built post-compaction goal re-anchor.** Continue auto-compacts near its context threshold and automatically continues the interrupted turn. We already have the more trustworthy half—the objective ledger and a post-compact re-anchor—but the re-anchor is shadow-only (`/local_disk0/codexwork/bundle/inputs/audit-findings/E05.md:66-80`). Enable that existing control; do not copy Continue's summary-only continuity as ground truth.

Continue is materially worse in the other load-bearing areas. It has no semantic cross-session memory system, no typed evidence receipts, no artifact/postcondition completion gate, and no reliable multi-agent supervision. Its beta `Subagent` implementation temporarily changes the shared permission service to `* = allow`, disables child history persistence, and returns the child's last message as success. Its hook package declares Claude-compatible event schemas, but prompt and agent hooks explicitly skip execution, and a source import/call-site audit found no production callers of its hook fire wrappers. The latter is **UNVERIFIED at packaged-binary runtime; an instrumented 2.0.0 CLI smoke run with one `PreToolUse` and one `SessionStart` hook would settle it**.

**Replacement decision:** almost certainly not (90–99%). Evidence: Continue declares its final release and cessation of active maintenance; its subagent safety and result contract are visibly weaker than our existing native multi-agent/shared-lifecycle plane; and replacing would violate the anti-overfit gate by introducing a second orchestration runtime. The residual 1–10% is the possibility of maintaining a private fork as a local-model IDE client, not evidence that it is a better owner harness.

## 1. Agent loop

### Concrete mechanism

Continue's core loop is admirably small. `streamChatResponse` recomputes the system message and available tools each iteration, runs a pre-request compaction checkpoint, streams the model response, executes tool calls, validates post-tool context size, optionally compacts, and breaks only when neither a tool call nor post-compaction continuation remains ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/stream/streamChatResponse.ts#L429-L581)). Official docs describe the same six-step handshake: tools are sent, the model calls one, permission is obtained, Continue executes built-in/MCP code, the result is sent back, and the cycle repeats ([docs](https://docs.continue.dev/ide-extensions/agent/how-it-works), lines 47–59).

Within one model response, Continue checks permissions sequentially and starts approved calls immediately, then awaits all executions together. It preserves result order and passes `parallelToolCallCount` so Bash/Read can reduce their per-call output limits ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/stream/streamChatResponse.helpers.ts#L463-L648)). This is a useful minimal design: concurrency is local to one tool batch rather than a durable workflow engine.

### What is better

- The loop recomputes tools after mode changes instead of assuming the initial capability map remains valid.
- Tool execution errors become tool results, allowing the same model loop to diagnose them; official Agent docs explicitly say most errors are returned to the model ([quick start](https://docs.continue.dev/ide-extensions/agent/quick-start)).
- Parallel-call output budgeting attacks context overflow at the source rather than compressing an already enormous aggregate result.

Our corpus says Bash has 108,121 calls at 6.0% errors and Glob has 6,222 calls at 13.3% errors; a per-batch output budget does not solve quoting or orphan-directory `ENAMETOOLONG`, but it is a sensible observation-shaping primitive.

### What is worse

- “No tool call” is treated as terminal. There is no deterministic check that requested files exist, tests passed, or the stated done signal holds.
- The loop has no explicit turn/tool budget in the cited control flow. Abort is user/controller-driven; repeated novel failures can continue until the model stops or context forces compaction.
- Tool errors are observations, not typed failure classes or breaker inputs.
- `--format json` formats output but does not validate the model's final object against a caller-supplied JSON Schema ([headless docs](https://docs.continue.dev/cli/headless-mode), lines 31–37). Our Codex paths already have native schema-validated output; Continue would be a regression.

### Port decision

Do not port the loop. Its useful parallel batch execution already exists natively in modern agents, and a second loop violates the anti-overfit gate. **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** would be required to install or fork Continue as the orchestrator, and there is no justification after the final-release announcement.

**Confidence:** almost certain (90–99%) that replacement would reduce reliability, based on the final-maintenance status, lack of a completion contract, and visible beta-subagent defects. The remaining uncertainty would be settled by a representative A/B task suite, but it does not justify deployment first.

## 2. Context management

### Concrete mechanism

Continue has four context lanes:

1. explicit `@file`/`@directory` context in the TUI ([docs](https://docs.continue.dev/cli/tui-mode), lines 19–27);
2. agent-selected file/search/repo-map tools and IDE signals; the docs name file content, language-server definitions, imports, and recent file history ([context selection](https://docs.continue.dev/ide-extensions/agent/context-selection), lines 43–51);
3. automatic inclusion of tool results as context items;
4. local session JSON, `/resume`, `/fork`, `/compact`, and automatic compaction.

The CLI assigns each new chat a UUID, stores sessions under `~/.continue/sessions`, removes system messages before persistence, and loads the most recently modified session for `--resume` ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/session.ts#L28-L67), [persistence](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/session.ts#L207-L357)). `/fork` begins a new session from current history, while `/resume` restores full history ([TUI docs](https://docs.continue.dev/cli/tui-mode), lines 28–61).

Automatic compaction reserves output/system budget, prunes messages until the summarization request fits, asks the current model for one comprehensive summary, and replaces prior history with system message + summary ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/compaction.ts#L18-L166)). The trigger uses an 0.8 buffer ratio capped at 15,000 tokens, not a fixed “80% of window” rule for every model. If compaction interrupts a turn, the outer loop inserts a continuation and keeps working.

### What is better

The visible `/info`, `/compact`, `/resume`, and `/fork` controls make session state legible and operator-steerable. The auto-continuation after compaction is particularly useful: a long tool-driven task does not silently end just because the model produced no new tool call immediately after summarization.

### What is worse

The summary is generated by the same model from a history that may first have had messages pruned. It is not checked against an immutable root contract, artifact state, ledger decisions, or receipts. Our pinned audit correctly calls the immediate owner defect a mutable 500-character active-goal prefix and recommends an immutable root contract plus typed checkpoints (`E05.md` verdict and findings); Continue has neither.

Continue's old `@Codebase` and `@Docs` retrieval providers are deprecated. Current guidance is file exploration, rules, and MCP (including external Context7/DeepWiki) rather than a built-in durable knowledge layer ([migration guide](https://docs.continue.dev/guides/codebase-documentation-awareness), lines 177–195). This is appropriately minimal, but it means the advertised context system is session/repository context, not long-horizon memory.

### Adopt enforced post-compact re-anchor — UNVERIFIED event ordering

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Set the existing shared harness `postcompact_reanchor` module to enforce, keyed once per `(session, ledger sequence)` as the local audit specifies; leave the provider's native compactor in place. Do not create a Continue-style second compactor.

Mechanism to port: on `PostCompact` or `SessionStart(source=compact)`, inject the immutable root objective, current done signal, open blockers, last verified mutation receipt, and artifact pointers from the existing ledger; deduplicate the paired events. If the provider stopped because compaction consumed the turn, emit one bounded continuation instruction.

**Confidence:** very likely (80–90%) to reduce post-compaction drift, because implementation and tests already exist and the only verified missing step is enforcement (`E05.md:66-72`). **UNVERIFIED whether Claude and Codex emit both compact-related events in the same order; a disposable long-context session capturing both event IDs settles deduplication before enablement.**

### Do not import IDE-context runtime

Continue's LSP/import/recent-file context is attractive, but **UNVERIFIED whether our current IDE/MCP surfaces already provide equivalent signals; capture one Claude and one Codex IDE-context/tool inventory while a symbol definition and recent edit are open to settle the premise**. A recommendation to add it would inherit that uncertainty, so none is made here.

## 4. Tool and MCP handling

### Concrete mechanism

Continue supports built-in file/search/edit/shell tools and MCP. The config schema covers command/args/env/cwd plus SSE and streamable-HTTP request options ([reference](https://docs.continue.dev/reference), lines 296–306). The CLI connects configured MCP servers concurrently, retains connection status, and exposes tools/prompts only from connections whose state is `connected` ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/services/MCPService.ts#L59-L125)). It also contains OAuth/token-refresh paths for remote servers.

In headless mode, initialization waits for MCP connections and throws a named aggregate error if any connection failed. In interactive mode without an agent file, initialization may proceed while connections update asynchronously. This is a real health boundary, but the headless policy is coarse.

### What is better

- Dead servers do not contribute tools to the model-visible action space.
- Headless automation gets a pre-turn error naming failed mounts instead of allowing the model to repeatedly call a dead tool.
- Agent files can compile a least-capability tool set: all tools from one MCP, one named tool from another, selected built-ins, or no unmentioned tools ([agent parser](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/packages/config-yaml/src/markdown/agentFiles.ts#L22-L41), [permission compiler](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/services/ToolPermissionService.ts#L79-L164)).

The first point directly answers the measured `claude_ai_Tavily` failure: 135 “not connected” errors came from a dead MCP still being callable. Continue's connected-only advertisement would remove that invalid action.

### What is worse

- A single optional MCP failure aborts every headless task. On this owner's heterogeneous 93-server history, that turns a peripheral outage into global unavailability.
- Connections are launched from one assistant config as an eager batch. This does not solve the owner's RAM fan-out or domain-loadout problem.
- Continue has no evidence here of a circuit breaker based on repeated runtime tool failure, no retirement/quarantine ledger, and no task-scoped on-demand server admission.
- Tool argument schemas remain whatever providers/MCPs declare; Continue does not address the corpus's 22.9% `StructuredOutput` error rate or over-strict fan-out schemas.

### Adopt connected-only advertisement with degraded health

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add an MCP-health projection to the existing MCP manager/SessionStart bus, not a new daemon.

Concrete mechanism:

1. Resolve the task loadout's configured servers.
2. Probe initialization with a strict per-server timeout and record `CONNECTED | AUTH_REQUIRED | DEAD | DEGRADED` plus a stable error fingerprint.
3. Generate the provider-visible allowlist only from `CONNECTED`; hide `DEAD`; keep `AUTH_REQUIRED` visible to the operator but not the model.
4. Abort only if a server marked `required_for_task` is unavailable. Otherwise start degraded and inject one compact availability note.
5. After N identical runtime transport failures, quarantine that tool/server for the session and stop retrying it; do not mutate global config automatically.

This rides the existing MCP manager, configuration projection, hook, and ledger buses. It introduces none of the rejected components.

**Confidence:** very likely (80–90%) to eliminate dead-server retry waste, based on the measured dead Tavily calls and Continue's source-verified connected-only tool construction. **UNVERIFIED how quickly every account connector exposes a reliable initialization state; a shadow run over DAILY servers comparing preflight state to the first real call settles timeout/status policy.**

## 5. Permission model

### Concrete mechanism

Continue's CLI has three outcomes: `allow`, `ask`, and `exclude`. Defaults allow read-only tools, ask for Write/Edit/Bash/MCP in the TUI, and in headless mode prevent ordinary `ask` tools from running unless explicitly granted ([docs](https://docs.continue.dev/cli/tool-permissions), lines 22–38). Policies match tools and primary arguments, including file globs and Bash command prefixes; persisted choices live in `~/.continue/permissions.yaml`. Precedence is mode, CLI flags, personal YAML, then defaults ([docs](https://docs.continue.dev/cli/tool-permissions), lines 39–86).

The implementation is first-match-wins and supports both tool patterns and argument maps ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/permissions/permissionChecker.ts#L12-L60), [evaluation](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/permissions/permissionChecker.ts#L124-L180)). Dynamic tool policy can hard-disable a call even when static policy allows it.

### What is better

This is Continue's clearest win. It makes least privilege the ordinary state and forces automation to name write capabilities. Our live host suppresses prompts at Administrator authority, and even the existing catastrophic guard is opt-in/off (`F05.md:8-22`).

### What is worse

- Continue's plan policy explicitly allows Bash and then allows wildcard MCP tools; its source contains a TODO acknowledging Bash read-only concerns ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/permissions/defaultPolicies.ts#L42-L66)). The official Plan guide says terminal execution is unavailable, so docs and source disagree. Do not copy that ambiguity.
- Headless defaults in source allow Bash and then `*`, whereas the current docs say `ask` tools are excluded unless explicitly allowed ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/permissions/defaultPolicies.ts#L7-L39)). The source/docs mismatch is itself a reason to test effective policy, not trust prose.
- The beta child agent deliberately overrides the service with `{ "*": "allow" }`, so parent least privilege does not survive delegation.
- Glob/prefix matching is syntax-level and can share our “mention versus use” class if applied to an entire command string without parsing. Continue does not solve shell aliases, wrappers, `git -C`, or semantic cloud operations.

### Restore native approval boundaries

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Remove `bypassPermissions` as the default Claude mode and stop launching Codex with `approval_policy = "never"` plus `danger-full-access` for ordinary work. Use native plan/read-only profiles for research and an explicit task-scoped write profile for builds.

**Confidence:** almost certain (90–99%) to reduce destructive blast radius, based on verified Administrator execution and disabled native boundaries (`F05.md:8-14`). The exact productivity cost is **UNVERIFIED; a two-week shadow log of calls that would prompt, followed by a one-week task-profile pilot, settles prompt volume and allowlist granularity**.

### Compile a shared least-capability task profile — UNVERIFIED Codex projection parity

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** For each existing role/loadout, declare `read`, `write(paths)`, `shell(command families)`, and named MCP tools; project those declarations into Claude/Codex native settings/profiles. Deny or hide unmentioned MCP tools for delegated read-only roles. This is configuration projection through the existing reconciler, not a new policy runtime.

**Confidence:** very likely (80–90%) to reduce accidental capability exposure, because Continue's compiler is concrete and our role agents/loadouts already exist. **UNVERIFIED which Codex per-agent overlay fields enforce individual MCP-tool exclusions in the installed binary; a read-only researcher versus write-capable worker smoke test settles projection parity.**

## 6. Customisation: rules, skills, hooks, agents, prompts

### Rules

Continue rules can be Markdown or YAML and carry `globs`, content `regex`, `description`, and `alwaysApply`. `alwaysApply: false` allows file-context matching or model-requested retrieval from the description; files load lexicographically ([rules docs](https://docs.continue.dev/customize/deep-dives/rules), lines 87–123). The system joins admitted rules into the system message. The agent can also create a project rule with a built-in tool.

Our path-scoped rules already cover the common glob case, and adding another rule directory/runtime would worsen drift. The useful missing idea is an admission contract that makes applicability explicit and testable.

### Conditional rule admission — UNVERIFIED gap

Do not let the agent rewrite rules without an explicit owner-authorized config change.

It is not yet an implementation recommendation because the local capability premise remains UNVERIFIED.

The IDE loader likewise consumes `.claude/skills` ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/core/config/markdown/loadMarkdownSkills.ts#L20-L67)).

This is cleaner than our split-brain delivery, although Continue still exposes every skill name/description and therefore does not by itself solve the 292-skill metadata ceiling.

### Adopt one canonical compatible skill-root projection

Preserve explicit invocation for the long tail. Validate name/description and auxiliary paths before projection; emit drift, never silently choose the newest duplicate.

**Confidence:** very likely (80–90%) to eliminate root drift and improve routing, based on Continue's working multi-root loader and our measured split/catalog problems (`A24.md:7-29`). **UNVERIFIED whether Windows junctions or generated copies are more robust across both installed clients; a 20-skill disposable projection with restart and explicit/implicit invocation tests settles the transport.**

### Hooks

Continue's source defines 17 Claude-shaped event names and compatible payloads, including `PreToolUse`, `PostToolUseFailure`, `PermissionRequest`, `SessionStart/End`, `Stop`, subagent/task/team, compact, config, and worktree events ([types](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/hooks/types.ts#L1-L30)). It loads both `.continue/settings*.json` and `.claude/settings*.json`, merging all hook groups ([loader](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/hooks/hookConfig.ts#L1-L15), [paths](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/hooks/hookConfig.ts#L69-L122)). Command and HTTP handlers execute with timeouts; synchronous handlers run in parallel and aggregate blocks/context.

But prompt and agent hook types are declared and explicitly skipped as “not yet supported” ([runner](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/hooks/hookRunner.ts#L210-L242)). HTTP failures and command-spawn errors fail open. The production-wiring result remains the inline UNVERIFIED finding above. Continue therefore offers no hook capability worth porting. Its one good design choice—typed verb, input, response, and tool-use ID in separate fields—already exists in Claude's hook payload and is exactly what our shared discriminator should consume (`INPUT-known-harness-defects.md:43-50,78-87`).

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Reuse the existing Claude/Codex hook events and shared dispatcher; do not install Continue's hook engine. Enable/repair registrations through the canonical manifest after the dedicated hook audit settles drift.

**Confidence:** almost certain (90–99%) that a second hook engine would be harmful, based on duplicate lifecycle ownership, incomplete handler types, and unverified call sites.

## 7. Multi-agent support

Continue's final source contains a beta `Subagent` tool, gated by a feature flag. Subagents are models whose role includes `subagent` and that have a base system message ([model selection](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/services/ModelService.ts#L309-L328)). The parent supplies a description, prompt, and subagent name. Multiple subagent tool calls can run in the general parallel tool batch.

The implementation is unsafe and shallow:

- it saves the parent's permission state, then globally replaces it with `* = allow` “for now” ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/subagent/executor.ts#L55-L89));
- it globally overrides the system-message function and disables the shared ChatHistoryService while the child runs;
- the child begins with only the delegated prompt, has no durable child session/transcript, and returns the last message as `success: true` ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/subagent/executor.ts#L91-L179));
- the parent receives free text plus `<task_metadata>status: completed|failed</task_metadata>`, with no artifacts, hashes, evidence, postconditions, or receipt validation ([tool](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/tools/subagent.ts#L63-L114));
- because permission and system-message services are process-global, parallel subagent calls can interleave save/override/restore operations. **very likely (80–90%) this creates race-prone authority/system-prompt state, based on the global mutable service code plus parallel tool execution; UNVERIFIED until a two-child concurrency test records effective permissions and system messages per call.**

This is worse than ours. The owner already has native fan-out, up to eight Codex threads, Claude role agents, shared `SubagentStart/Stop`/`TaskCompleted` hooks, monitoring, and an almost-complete `HandoffEnvelope` (`D16.md:6-18,62-69`). Our remaining gap is enforcing the existing typed handoff/result contract, not acquiring another spawner.

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Keep native Claude/Codex multi-agent and require delegated authority to be the intersection of parent authority and role profile. Do not use Continue subagents or copy its global override pattern.

**Confidence:** almost certain (90–99%) that Continue's subagent plane is a regression, based on source-visible privilege widening, ephemeral child state, and last-message acceptance.

## 8. Verification and self-check

Continue provides useful but advisory primitives:

- a `Checklist` tool lets the model maintain markdown checkboxes;
- tool failures are returned to the model;
- `ReportFailure` can mark a hosted agent `FAILED`, though it requires an agent ID and remote API ([source](https://github.com/continuedev/continue/blob/d0a3c0b626b5bebc3bef4742eec05a0242be0bab/extensions/cli/src/tools/reportFailure.ts#L25-L78));
- repository `.continue/checks` and PR-review workflows can run prompt-based checks in CI; the current official guide's review bot is an ordinary GitHub Actions job that asks `cn` to review a diff and posts its prose ([guide](https://docs.continue.dev/guides/github-pr-review-bot)).

These are not an evidence gate. Checklist completion is self-asserted. `ReportFailure` authenticates a declared failure but does not prove success. A review comment is not a typed, deterministic postcondition. The generic agent file has no result schema. Continue therefore cannot prevent the exact owner failure class in which agents produce plausible digests for nonexistent artifacts.

Our harness is better in design—typed receipts, mutation freshness, claim warnings, review lanes—but not yet trustworthy enough. Local audits show stale-receipt fallback, weak receipt authentication, ANY-of multi-claim semantics, and session/task scoping defects. Continue supplies no remedy for those.

### Enforce the existing WorkUnit/Handoff result contract

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Attach the already-defined strict `HandoffEnvelope`/WorkUnit result schema to every native delegation, and validate at `SubagentStop`/`TaskCompleted`: task ID, terminal status, artifact manifest with hash/bytes, evidence anchors, deterministic postconditions, fresh task-scoped receipts, and gaps. Reject “completed” when schema, artifact existence, or receipts fail.

This is not copied from Continue; it is the explicit conclusion from Continue's deficiency and the owner's evidence. It rides native output schemas and the shared dispatcher/ledger. It adds no trained critic, durable engine, or second runtime.

**Confidence:** very likely (80–90%) to reduce false completion at fan-in, based on the existing strict schema, local nonexistent-artifact incidents, and Continue's demonstrably weak last-message result. **UNVERIFIED absolute task-success uplift; an A/B suite of 30 representative delegated tasks with artifact validity, retries, tokens, and elapsed time settles magnitude.**
