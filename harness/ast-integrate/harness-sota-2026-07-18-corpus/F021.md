# F021 — Frontier research: distillation of agent trajectories into reusable skills

**Unit:** F021  
**Date:** 2026-07-19  
**Scope:** Research and design only. I did not modify the unpacked harness subject.  
**Question:** What is actually established, merely promising, or hype in converting agent execution trajectories into reusable procedural skills, and what should this harness adopt?

## Executive verdict

Trajectory-to-skill distillation is real, but the established result is narrow: **selected experience can improve later agents when the experience is compressed into a task-relevant workflow or an executable, environment-verified action, and when evaluation is performed on later tasks rather than on the source trace.** Peer-reviewed AWM, ExpeL, ASI, CRAFT, and Voyager establish versions of that statement in web navigation, reasoning/embodied environments, and tool-amenable tasks ([AWM, ICML 2025](https://proceedings.mlr.press/v267/wang25bx.html), [ExpeL, AAAI 2024](https://ojs.aaai.org/index.php/AAAI/article/view/29936), [ASI, COLM 2025](https://arxiv.org/pdf/2504.06821), [CRAFT, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/af31604708f3e44b4de9fdfa6dcaa9d1-Abstract-Conference.html), [Voyager project/paper](https://voyager.minedojo.org/)). These works do **not** establish that arbitrary coding transcripts can be summarized once into `SKILL.md`, automatically activated, and expected to compound safely.

The best current counterweight is unusually relevant to this owner. SkillsBench runs current filesystem skills in Claude Code, Codex, and Gemini CLI. Curated skills improve mean pass rate from 24.3% to 40.6% across seven model/harness configurations, but 16 of 84 tasks regress; its self-generated condition averages 21.0% versus 24.3% without skills and was run only on four Claude models plus Codex, not Gemini ([paper pp. 1, 5, 26](https://www.skillsbench.ai/skillsbench.pdf)). SkillEvolBench goes closer to this unit's exact question: across ten model configurations and three harnesses, agents often improve acquisition/replay yet fail context-shift, adversarial-shortcut, composition, and frozen-deployment tests; raw trajectories often beat their distilled skills ([project results](https://skillevolbench.github.io/)). Both are 2026 preprints, so they are lower evidence-tier than peer-reviewed AWM/ASI, but their negative controls are more directly matched to contemporary coding-agent skill files.

Therefore the harness should **not** create a self-installing skill factory. It should add a small, evaluator-led **candidate distillation lane** on the existing ledger/hook/skill/deploy bus:

`verified repeated traces -> candidate abstraction -> explicit-only quarantined SKILL.md -> paired held-out replay -> human review -> shadow/canary -> active or deprecated`

This is **likely (55-80%)** to yield a small number of useful owner-specific skills because AWM/ASI show transfer after selection and verification, SkillsBench shows curated skills work, and this corpus contains repeated failure fingerprints; it is not a higher confidence claim because no experiment has linked this owner's traces to held-out task improvement. The recommendation is **UNVERIFIED; the settling experiment is the paired 30-task pilot specified in §4.8**.

The anti-overfit gate rejects a second orchestrator, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, and guardrail framework. None is needed. The useful mechanism is a file candidate, a small manifest, deterministic receipts, and the existing promotion ladder.

## Definitions and evidence standard

“Trajectory distillation” is overloaded. I use it only for a pipeline with all of these stages:

1. **Evidence:** one or more executions containing observations, actions/tool calls, results, and preferably environment or verifier outcomes.
2. **Selection:** deciding which executions or fragments are trustworthy and recurrent.
3. **Abstraction:** removing instance constants and compressing common control flow, preconditions, parameters, exceptions, and stopping criteria.
4. **Packaging:** producing declarative instructions, a workflow, a callable program, or a hybrid skill directory.
5. **Routing:** deciding whether the later task should receive or invoke the skill.
6. **Validation:** testing on a different instance, context, or distribution and accounting for authoring/invocation cost.
7. **Lifecycle:** revision, conflict handling, provenance, rollback, and retirement.

A paper that measures only source-task replay establishes memorization or local repair, not reusable skill formation. A system that emits syntactically valid `SKILL.md` establishes packaging, not utility. A successful later task establishes correlation unless a same-task no-skill/raw-trajectory/curated baseline isolates the skill's causal contribution.

I classify evidence as follows:

- **Established:** peer-reviewed primary work with executable or deterministic task outcomes and relevant ablations, or convergent primary measurements across materially different systems. “Established” remains scoped to the tested domains.
- **Promising but unproven:** primary preprint/repository with nontrivial held-out evaluation but no independent replication, or a result whose transfer to this harness is uncertain.
- **Hype:** claims whose evaluation cannot distinguish reusable abstraction from source-task leakage, extra inference compute, latent model knowledge, direct raw-trace replay, or cherry-picked demos.

The unpacked corpus is suitable for discovering repeated candidates, not for labeling them correct. Its parser covered 11,633 files / 10.62 GB with one bad line and says counts are exact but samples capped (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). Crucially, its 2,268 “owner correction candidates” are recall-biased and all 41 items in an unfiltered smoke sample were false positives (`corpus.json:10371-10374`). Any design that trains or promotes directly from that field is invalid.

## 1. What is established

### 1.1 Reusable natural-language workflows can improve later tasks in a bounded domain

Agent Workflow Memory (AWM) induces common routines from successful web-navigation trajectories, retrieves relevant routines later, and supports offline and online induction. On Mind2Web and WebArena it reports relative success improvements of 24.6% and 51.1%, while online AWM retains 8.9–14.0 absolute-point gains as train/test gaps widen ([ICML 2025 primary page and abstract](https://proceedings.mlr.press/v267/wang25bx.html)). The peer-reviewed venue, 1,000+ tasks across 200+ domains, cross-task/site/domain tests, and step-efficiency result make this more than a demo.

What it establishes: compact textual procedural memory can outperform solving every related task from scratch in web navigation. What it does not establish: arbitrary free-form transcript summaries work; the method induces routines from selected trajectories and selectively supplies them in a benchmark with a repeatable action vocabulary.

ExpeL independently supports the broader “externalized experience helps” direction. It collects task experiences, contrasts successes/failures into natural-language insights, and recalls both insights and examples at inference; AAAI 2024 reports improvement as experience accumulates and publishes reproduction code ([paper](https://ojs.aaai.org/index.php/AAAI/article/view/29936), [official repository](https://github.com/LeapLabTHU/ExpeL)). ExpeL is closer to reusable heuristics than callable skills, so it establishes non-parametric experiential learning, not the modern skill-directory lifecycle.

### 1.2 Verification and representation matter at least as much as the distiller

ASI is the cleanest peer-reviewed causal evidence for this design choice. It filters candidate episodes, induces callable Python programs, rewrites a trajectory to force use of the new call, and admits a skill only if the later execution passes correctness, actually calls the skill, and changes environment state ([COLM 2025 paper, §§2.2–2.3](https://arxiv.org/pdf/2504.06821)). On WebArena, Claude 3.5 Sonnet rises from 32.7% static to 36.3% with textual AWM and 40.4% with ASI; successful solutions use 5.0 versus 5.6–5.9 steps ([Table 1](https://arxiv.org/pdf/2504.06821)).

Its ablation is especially important. On the shopping slice, unverified text in memory scores 32.6, verified programs rendered in memory 36.4, verified text in memory 39.0, and verified programs installed as actions 40.1 ([Table 3](https://arxiv.org/pdf/2504.06821)). Only 15.6% of program-induction turns pass verification, versus AWM adding a text skill 31.4% of the time. The lesson is not “code always beats prose.” It is: strict rejection is normal; executable skills are valuable when the execution surface and evaluator match them; prose can be better when the artifact is advisory memory.

This result converges with CRAFT, which creates specialized code toolsets from solved training examples and retrieves them later. Its ICLR 2024 experiments and ablations support atomicity, retrieval, and executable offloading in tasks with checkable code/API operations ([primary conference page](https://proceedings.iclr.cc/paper_files/paper/2024/hash/af31604708f3e44b4de9fdfa6dcaa9d1-Abstract-Conference.html)). CRAFT is offline tool induction rather than lifelong trajectory learning, but it independently supports the representation-and-retrieval mechanism.

### 1.3 Executable skill libraries work in stable, simulator-like action spaces

Voyager uses an automatic curriculum, an ever-growing executable JavaScript skill library, and iterative program repair driven by Minecraft feedback and self-verification. It transfers the library into a new world for novel tasks and includes component ablations ([project and paper](https://voyager.minedojo.org/), [official repository](https://github.com/MineDojo/Voyager)). It establishes that verified code fragments can serve as compositional procedural memory in a stable API-mediated environment.

The boundary matters: Minecraft/Mineflayer offers a controlled API and cheap repeated execution. It does not establish that generated PowerShell/Bash helpers should run with the owner's full Windows credentials, or that a successful one-off repository edit is a stable reusable program.

### 1.4 Curated skills help contemporary coding harnesses, but not uniformly

SkillsBench is a preprint, not peer-reviewed, but its breadth and deterministic verifiers make two observations strong enough to treat as established operational constraints pending reproduction:

- Across 84 tasks, 11 domains, seven model/harness combinations, five main-condition trials per task, and 7,308 total trajectories, curated skills improve mean pass rate by 16.2 percentage points. Every tested model/harness aggregate improves, but effects range from +13.6 to +23.3 points and 16/84 individual tasks regress ([paper pp. 1, 4–5, 17, 26](https://www.skillsbench.ai/skillsbench.pdf)).
- Focus and routing matter: the benchmark exposes only skill metadata first; Claude Code and Codex use name/description for relevance and load the body on demand, while deterministic pytest grades the final task ([paper Appendix C](https://www.skillsbench.ai/skillsbench.pdf)). Native Claude Code likewise discovers metadata then loads full content only on invocation, and supports explicit invocation control and supporting resources ([official skills documentation](https://code.claude.com/docs/en/slash-commands)).

The scoped conclusion is that a good skill can add substantial procedural competence, not that more skills are better. Only 78 distinct skill names appear in the corpus capability-use map (`corpus.json:13265-13345`), making routing and retirement first-order concerns; the corpus has no task-opportunity denominator, so it cannot establish that an unobserved installed skill is useless.

### 1.5 Self-generated skills are not automatically beneficial

The primary SkillsBench result corrects an overstatement in local audit finding E09. The current paper does **not** report self-generated skills for Gemini CLI, and it does **not** show 8.1–11.5 absolute-point degradation across all three harnesses. It reports self-generation on four Claude Code models and Codex GPT-5.2: −5.6 points for Codex, −2.1 for Sonnet 4.5, −0.4 for Opus 4.5, 0.0 for Haiku 4.5, and +1.4 for Opus 4.6, averaging −1.3 points ([Table 3 and Appendix Table 8](https://www.skillsbench.ai/skillsbench.pdf)). This is a one-shot generate-before-solving condition, not multi-trajectory verified distillation.

That narrower negative result still establishes an important control: formatting latent model knowledge as a skill does not itself create value, and the authoring step can add timeout and distraction costs. It refutes “ask the same solver to write a skill, then immediately trust it” more directly than it refutes AWM/ASI-style learning from a pool of grounded trajectories.

SkillEvolBench supplies a second, mechanically different signal: it separates acquisition, replay, frozen deployment, context shift, adversarial shortcuts, composition, raw-trajectory reuse, and curated-start evolution. Its published project results say distilled skills often lose information preserved by raw trajectories and that more updates are not monotonically better ([result analysis](https://skillevolbench.github.io/)). It is a recent preprint and thus a lower evidence tier than the peer-reviewed positive studies, but its controls target the exact abstraction claim.

### 1.6 Outcome selection must precede abstraction

Across AWM, ASI, Voyager, CRAFT, and ExpeL, useful artifacts are not distilled indiscriminately from all text. Systems use solved examples, successful/environment-filtered episodes, contrastive success/failure evidence, or iterative execution feedback. ASI explicitly removes error steps, compresses verbose thoughts, filters predicted-correct episodes, and then independently tests the induced skill ([ASI §§2.2–2.3](https://arxiv.org/pdf/2504.06821)).

This harness already has part of the required evidence plane: typed tool-result receipts record receipt class, status, pass/fail counts, and argv fingerprint (`/local_disk0/codexwork/bundle/agents/harness/modules.py:1048-1077`); freshness requires a pass after the latest mutation (`ledger.py:1065-1117`); and an exact failing command can be paired with a later green rerun (`ledger.py:1119-1163`). It does not yet make a task outcome visible in the task record, which stores provider, turn, agent type, and output hash only (`modules.py:1218-1238`). Thus tool-level evidence is available, but trajectory-level labels must not be inferred from “assistant stopped” or “command returned zero.”

## 2. Promising but unproven

Every item here is recent primary work but is not yet established for this harness.

### 2.1 Multi-trajectory, hierarchical consolidation

Trace2Skill analyzes a diverse pool in parallel, extracts trajectory-local lessons, and hierarchically consolidates them into one conflict-resolved skill directory. It reports held-out spreadsheet, VisionQA, and math gains, including cross-scale transfer, and reports that parallel pool analysis beats sequential online mutation ([paper](https://arxiv.org/abs/2603.25158), [official repository](https://github.com/Qwen-Applications/Trace2Skill)).

It is **likely (55-80%)** that pool-level consolidation is safer than editing a canonical skill after every session, because SkillEvolBench finds update frequency non-monotonic and Trace2Skill reports parallel consolidation outperforming sequential updates. This is still **UNVERIFIED; the settling experiment is to compare per-trace mutation, clustered batch induction, and raw-trace retrieval on the same held-out owner tasks**. Trace2Skill is a March 2026 preprint with author-reported results and a complex fan-out distiller; no independent replication was determined.

### 2.2 Parameterized finite-state/control-flow fragments

Skill-DisCo normalizes successful traces into intermediate programs, segments subgoals, clusters fragments by parameterized control-flow structure, and compiles verified callable skills. It reports lower execution-error rates and fewer turns on ALFWorld and WebArena ([June 2026 preprint](https://arxiv.org/abs/2606.26669)).

It is **likely (55-80%)** that explicit preconditions, parameters, transitions, and postconditions are more reusable than narrative summaries for repetitive CLI/browser flows, because ASI's callable boundaries already outperform fuzzy textual boundaries and Skill-DisCo directly tests structured fragments. It is **UNVERIFIED; settle it by mining only deterministic command sequences, then compare a parameterized checklist, a callable helper, and a prose summary on unseen repositories**. The PFSM assumption fits finite-state environments better than open-ended software work, and the paper is very recent and unreviewed.

### 2.3 Diverse model traces as a hedge against model-specific habits

AFTER evaluates 382 enterprise tasks, six professional roles, and 22 procedural skills. It reports one refinement round improving aggregate performance by 3.7–6.7 points and skills evolved from diverse multi-model traces achieving 73.1% cross-model test accuracy, above any single-model source ([June 2026 preprint](https://arxiv.org/abs/2606.23127)).

It is **roughly even (45-55%)** that mixing Claude, Codex, and Gemini traces would improve this owner's skill portability. Evidence supports diversity, but provider tool schemas, prompt policies, and available actions differ; mixing may erase provider-specific constraints. This is **UNVERIFIED; settle it with a 2x2 author-source/consumer-provider matrix on the same task families and inspect whether normalized action semantics preserve or corrupt key steps**.

### 2.4 Closed-loop benchmarks that charge authoring cost

EvoClawBench asks whether a runtime's own runs yield skills that improve fresh executions after authoring cost, and reports selective, cost-sensitive, non-monotonic behavior rather than automatic gains ([July 2026 arXiv paper](https://arxiv.org/abs/2607.09711)). This is post-cutoff/recent primary evidence and remains a lower evidence tier pending review and reproduction.

It is **very likely (80-90%)** that a harness evaluation must charge extraction tokens, verification runs, routing overhead, and maintenance—not merely final pass rate—because ASI reports step savings, SkillsBench reports extra self-generation timeouts, and EvoClawBench makes net benefit the target. The exact accounting scheme for this owner is **UNVERIFIED; settle it by recording wall time, tokens, tool calls, and reviewer minutes for both authoring and all later uses until break-even**.

### 2.5 SkillWeaver-style autonomous practice before promotion

SkillWeaver explores websites, synthesizes APIs, practices them, and refines them; it reports 31.8% and 39.8% relative success gains on WebArena and real sites and transfer from stronger to weaker agents ([paper](https://arxiv.org/abs/2504.07079), [official repository](https://github.com/OSU-NLP-Group/SkillWeaver)).

It is **unlikely (20-45%)** that autonomous practice is worth enabling broadly on this owner's coding harness. The evidence is good for sandboxed web sites with repeated actions, but repository tasks can mutate consequential state and lack cheap reset/oracles. This is **UNVERIFIED; settle it only in disposable fixture repositories with no credentials/network and deterministic reset, comparing practice cost to later saved work**. Website-specific API practice should not be generalized into host-wide self-modification.

### 2.6 RL-coupled evolving skill banks

SkillRL distills successful trajectories and failure lessons into a hierarchical skill bank while jointly training a policy and evolving skills; code and model artifacts are public ([paper/repository](https://github.com/aiming-lab/SkillRL)).

It is **very unlikely (5-20%)** that importing this architecture would beat file skills plus held-out evaluation for this owner, because it requires policy training, a teacher, RL infrastructure, and a new runtime while the owner uses proprietary fast-moving models. I make no determination about the research claim outside its reported training setup; the harness fit is poor. A settling experiment would require a fixed open model, task distribution, compute budget, and comparison against the file-only candidate lane—far beyond the value justified here.

## 3. Hype, and the tell that gives it away

### 3.1 “The agent wrote a skill, therefore it learned”

**Tell:** success is syntax validity, file creation, or a persuasive retrospective. No later held-out task is run. Structural validators can show a directory is loadable; they cannot show routing, factual correctness, safety, or utility. SkillsBench's one-shot self-generation result is the direct falsifier ([paper](https://www.skillsbench.ai/skillsbench.pdf)).

### 3.2 “It improves after learning” with no raw-trajectory control

**Tell:** the learned condition receives more tokens or the original solution while the baseline does not. SkillEvolBench observes that raw successful traces often outperform their distilled abstractions, making the raw-trajectory arm a required control ([results](https://skillevolbench.github.io/)).

### 3.3 Source-task replay presented as transfer

**Tell:** the generated artifact is tested on the same task, same constants, same webpage/repository, or a paraphrase with identical state. ASI explicitly truncates answer-bearing trailing actions to prevent spurious verification and then requires a new skill call plus environment change ([ASI §2.3](https://arxiv.org/pdf/2504.06821)). Any paper or product without an equivalent anti-leakage measure has not established reuse.

### 3.4 Success-only distillation presented as robust learning

**Tell:** failures, exceptions, contraindications, version drift, and negative routing examples are discarded rather than represented. A skill needs “when not to use,” failure modes, and invalidation conditions. Success traces reveal a path; contrastive failures reveal its boundary. ExpeL's success/failure comparison and ASI's rejection rate are evidence that selection is substantive, not housekeeping ([ExpeL](https://ojs.aaai.org/index.php/AAAI/article/view/29936), [ASI](https://arxiv.org/pdf/2504.06821)).

### 3.5 Ever-growing libraries presented as compounding intelligence

**Tell:** the graph shows skill count, not downstream invocation precision, marginal pass-rate delta, context cost, contradiction rate, or retirement. This owner's corpus records only 78 distinct invoked skill names (`corpus.json:13265-13345`); that does not prove other installed skills are useless, but it makes catalogue growth alone an invalid success metric. Native Claude loads full bodies on demand, yet descriptions are the discovery surface ([official docs](https://code.claude.com/docs/en/slash-commands)).

### 3.6 Same-model reflection presented as verification

**Tell:** the authoring model also decides whether its skill is correct, with no environment state, deterministic verifier, or independent outcome. ASI's neural episode filter is followed by execution checks; SkillsBench uses deterministic pytest. Model critique is useful for proposing abstractions, not certifying them.

### 3.7 A production “self-improving” claim without causal linkage

**Tell:** a failure happens, a memory is written, aggregate performance later rises, and the narrative attributes the rise to the memory without linking source failure -> candidate version -> invocation -> fresh receipt -> held-out outcome. The current local task event contains only an output hash (`modules.py:1218-1238`) and shadow records contain gate/reason/session metadata but no candidate or outcome (`modules.py:357-384`). A dashboard over these fields would produce activity, not learning evidence.

### 3.8 “Universal transferable skill” without context-shift and shortcut tests

**Tell:** transfer means only a larger model on the same benchmark or a nearby template. Robust claims need new repositories/sites, renamed identifiers, irrelevant distractors, adversarial shortcuts, composition, and a consumer model different from the author. SkillEvolBench makes these axes explicit ([benchmark](https://skillevolbench.github.io/)).

## 4. Specific adoption for this harness

### 4.1 Keep the native filesystem skill substrate; do not add a skill runtime

**Tag — NATIVE (Claude Code already does this; we just enable it).** Use ordinary project/global `SKILL.md` directories with metadata-first, body-on-demand loading, supporting files, explicit invocation control, and native live discovery ([Claude Code official documentation](https://code.claude.com/docs/en/slash-commands)). Preserve the cross-provider skill-directory convention already used by the owner; provider-specific metadata may be generated at deploy time.

**Anti-overfit gate:** passes. It rides the existing native skill bus and adds no orchestrator, memory service, vector/KG store, or framework.

It is **almost certain (90-99%)** that this is lower-risk than a new runtime because the subject already has hundreds of filesystem skills and all candidate output can remain reviewable text/files. This confidence concerns integration risk, not whether any particular distilled skill improves outcomes.

### 4.2 Add a typed `trajectory-candidate.json` manifest beside quarantined drafts — UNVERIFIED

**Tag — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** An offline command should accept explicit source event IDs and emit a candidate directory under the existing incubation area, never an active skill root. Minimum manifest:

- candidate ID/version/digest and creation time;
- source project/session hashes and event/receipt IDs, without copying secrets or full private bodies;
- task-family hypothesis and recurrence count;
- positive trace IDs and contrastive failure IDs;
- parameterized preconditions, inputs, expected postconditions, exceptions, and “do not use when” cases;
- artifact type: `declarative`, `resource`, or `executable`;
- author model/version and normalizer version;
- proposed routing description and explicit-only default;
- evaluation fixture IDs, baseline, trials, cost, result, reviewer, activation/deprecation state.

The current bus already stamps typed receipts and fingerprints (`modules.py:1048-1077`) and supports off/shadow/advise/enforce (`modules.py:118-149,389-417`). **UNVERIFIED whether a complete trajectory can be reconstructed from the live ledger because task records omit outcome and full trajectories; the settling experiment is to choose ten known completed sessions and join tool events, mutations, receipts, and final environment outcomes by session/turn IDs without transcript text.**

**Anti-overfit gate:** passes if implemented as one schema plus one small offline command. If reconstruction needs a new daemon or durable execution system, stop; that would become BUILD-LARGE and fails this unit's evidence threshold.

It is **likely (55-80%)** that a manifest prevents untraceable promotion because provenance/lifecycle fields make each claim inspectable; it is **roughly even (45-55%)** that the first implementation stays under 200 lines because the missing outcome join may expand scope. The experiment above settles sizing before build.

### 4.3 Candidate detection: recurrence plus evidence, never the correction-candidate field

**Tag — CONFIG (settings/JSON only).** Configure an offline report, not an enforcing hook, to nominate clusters only when one of these holds:

- the same normalized failing receipt fingerprint later has a green exact rerun in at least two independent sessions;
- the same multi-step tool pattern succeeds on at least three task instances with the same postcondition class;
- the owner explicitly nominates a trajectory;
- a reviewed audit finding provides source IDs plus a deterministic reproducer.

Exclude `owner_correction_candidates` from automatic labels: its own precision warning says 41/41 unfiltered examples were false positives (`corpus.json:10371-10374`). Use the 5,692 error fingerprints as discovery leads, then require underlying receipts/reproduction; counts alone are not correctness labels.

**Anti-overfit gate:** passes. This is a report configuration over existing corpus/ledger data, not online learning infrastructure.

It is **very likely (80-90%)** that this reduces noisy candidates relative to summary-every-session because the corpus provides direct evidence of a catastrophic correction-detector precision problem and ASI admits only a small verified fraction. It is **UNVERIFIED whether two/three recurrences are the right thresholds; settle with a blinded review of 100 nominated and 100 rejected clusters, measuring precision and missed useful procedures before enabling generation**.

### 4.4 Distill batches, not single sessions; preserve raw evidence pointers

**Tag — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one native skill/prompt used explicitly by the offline command. It should receive a bounded candidate bundle, not the full 10.62 GB corpus, and produce:

1. invariants common to multiple successes;
2. instance constants that must become parameters or be removed;
3. contrasting failure conditions;
4. minimal ordered steps and stopping rule;
5. verification commands/postconditions;
6. unresolved conflicts, which block promotion rather than being silently “merged”;
7. links back to raw evidence spans.

No recursive agent team is needed. A single strong model can draft, followed by deterministic evaluation and human review. Trace2Skill makes hierarchical multi-trajectory consolidation promising, but SkillsBench/SkillEvolBench make autonomous activation unjustified.

**Anti-overfit gate:** passes. It is a prompt/skill on the existing bus; no trained critic, retrieval database, or second runtime.

It is **likely (55-80%)** that batching improves abstraction over one-session summaries, based on Trace2Skill's pool analysis and SkillEvolBench's update-drift result. This recommendation is **UNVERIFIED; settle with the three-arm per-trace vs batch vs raw-trajectory experiment in §4.8**.

### 4.5 Quarantine every generated skill as explicit-only

**Tag — CONFIG (settings/JSON only).** Generated candidates must live outside auto-discovered active roots. When staged for canary, disable model invocation / allow only explicit invocation using the provider's native metadata, and scope to the smallest relevant project. Do not put executable scripts in v0. Human-written curated skills remain unchanged.

**Anti-overfit gate:** passes. This is native discovery configuration and existing incubation/deploy discipline.

It is **very likely (80-90%)** that quarantine prevents the main measured failure—confidently wrong or distracting self-authored material—from affecting unrelated work, because SkillsBench observes net-negative one-shot self-generation and native descriptions control routing. It is **UNVERIFIED whether explicit-only canaries adequately predict automatic routing; settle by running both explicit and shadow-routing trials before model invocation is enabled**.

### 4.6 Promotion requires paired, held-out outcome evaluation and negative routing tests — UNVERIFIED

**Tag — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing receipt/promotion surface, not a new eval framework. For each candidate:

- freeze at least five unseen task instances across two repositories/sites where possible;
- compare `no skill`, `raw evidence`, and `candidate skill`; add `existing curated skill` where relevant;
- use at least three trials per arm for stochastic tasks;
- grade final environment state/deterministic verifier first, fresh-context review only for irreducibly semantic output;
- require no regression on negative-routing tasks where the skill is discoverable but irrelevant;
- record pass rate, process violations, wall time, tokens/tool calls, reviewer time, and break-even reuse count;
- reject leakage by renaming identifiers, changing paths/order, and removing answer-bearing trailing actions;
- promote only a predeclared delta; do not choose the threshold after seeing results.

The harness already rejects stale greens and can require an exact failing-command rerun (`ledger.py:1065-1163`), but trajectory-level outcome and candidate linkage are **UNVERIFIED; the settling experiment is to implement one fixture family end to end and confirm every promoted result can be joined from candidate to invocation to final state with no transcript interpretation**.

**Anti-overfit gate:** passes if fixtures call existing commands and write ordinary JSON/Markdown receipts. A learned judge or durable workflow engine fails the gate.

It is **very likely (80-90%)** that this is necessary for trustworthy promotion because every strong positive study uses later-task/environment evaluation and both 2026 negative benchmarks expose local-replay and abstraction failures. It is **roughly even (45-55%)** that five instances x three trials is sufficient for stable thresholds; bootstrap intervals and the pilot variance should determine the production sample size.

### 4.7 Separate declarative and executable tiers

**Tag — CONFIG (settings/JSON only).** v0 candidates may contain instructions, checklists, examples, templates, and commands to be selected by the agent, but no newly generated executable. An executable tier may later be allowed only when:

- the action API is stable and allowlisted;
- all inputs/outputs and side effects are explicit;
- tests execute in a resettable, credential-free fixture;
- the program is forced into the verification path, not merely present;
- a human approves the exact code and deployment scope.

**Anti-overfit gate:** passes for the declarative tier. A generic sandbox/daemon would be BUILD-LARGE and is not justified; reuse an existing restricted runner if later verified by another unit.

It is **very likely (80-90%)** that declarative-first is the correct initial risk boundary because ASI's executable success depends on a controlled browser action space, whereas this owner runs PowerShell/Bash with host authority and already has substantial quoting/process failures (`corpus.json:13-20,39-44,79-84`). ## Final decision

Adopt the **small causal learning loop**, not the grand self-improving system. Filesystem skills, selective loading, typed receipts, exact reruns, and staged enforcement already provide almost all substrate. The missing value is disciplined conversion of repeated verified evidence into a quarantined candidate and a held-out causal test.

The frontier's most important lesson is negative and constructive: trajectory distillation fails when “summarize” substitutes for selection, abstraction, routing, and verification. It succeeds most convincingly when the environment provides a stable action vocabulary and objective postconditions, the candidate is aggressively rejected, and later tasks—not the originating trace—decide whether it becomes a skill.
