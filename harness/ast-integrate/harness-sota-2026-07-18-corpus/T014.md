# T014 — Competitive teardown: Amp

Date researched: 2026-07-19 UTC  
Subject: the current Amp product (the 2026 “Neo” rebuild), compared with the unpacked owner harness  
Unit scope: agent loop, context, memory, tools/MCP, permissions, customization, multi-agent, verification/self-check

## Executive finding

Amp is not a better whole-harness replacement for this owner. Its strongest ideas are narrow and portable: skill-scoped MCP exposure, argument-aware policy decisions, a typed in-process lifecycle bus that can transform both tool inputs and results, first-class hierarchical review checks, and a deliberately different-model “oracle.” Its weaker defaults are consequential: tools run without approval, subagents cannot be steered or communicate, thread data is cloud-synchronized, the client is not self-hostable, and Amp documents no ambient semantic memory comparable to the owner’s basic-memory plus event-ledger split.

The best direction is therefore evolution, not replacement. This judgment is **very likely (80-90%)**, based on (1) Amp’s current official manual and security architecture, and (2) the owner harness’s actual settings and behavior contract. It is not “safe incrementalism”: the recommended port replaces globally exposed MCP sprawl with capability-scoped exposure and consolidates policy/result transformation behind one typed adapter. Full replacement loses mechanisms the owner already has and uses: cross-tool semantic memory, objective event-ledger replay, steerable communicating agent teams, provider independence, and local control. Evidence: [Amp manual, Tools/Skills/MCP/Permissions](https://ampcode.com/manual#tools); [Amp security, System Components](https://ampcode.com/security#system-components); `/local_disk0/codexwork/bundle/codex/AGENTS.md:20-26,43-46,62-85`; `/local_disk0/codexwork/bundle/codex/config.toml:77-80,101-109,125-130`.

The highest-value port is the MCP exposure design. Amp starts skill-bundled servers but hides their tools until the skill loads, and recommends `includeTools` filters. The owner’s corpus instead records a dead Tavily MCP repeatedly being called (532 calls, 25.8% error, including 135 “not connected”), while the configured Claude allowlist exposes many broad MCP namespaces (`settings.json:47-60`). A capability-scoped exposure layer is **almost certain (90-99%)** to reduce invitations to dead/irrelevant tools; the evidence is the direct causal mechanism (unavailable tools cease to be model choices) plus Amp’s documented context-bloat rationale. The exact error-rate reduction is **UNVERIFIED**; settle it with an A/B replay of the corpus’s Tavily-triggering prompts, measuring selection rate, task success, latency, and token count with global versus skill-scoped exposure.

## 1. Agent loop

### What Amp does

Amp’s unit of execution is a thread: any number of user/LLM/tool turns. The client gathers local/editor context, sends it through Amp Server to a model, executes requested local tools, returns results, and repeats ([security, User Interaction Example](https://ampcode.com/security#user-interaction-example)). Its plugin lifecycle makes the loop unusually explicit:

`session.start → agent.start → (tool.call → tool.result)* → agent.end`

`tool.call` can allow, reject-and-continue, modify input, or synthesize a result without execution. `tool.result` can replace status/output before the model sees it. `agent.end` can append a guarded synthetic user message and continue another turn ([manual, Plugin Event Examples](https://ampcode.com/manual#event-examples)). The official example uses `agent.end` to request tests before finishing, with a marker to prevent an infinite continuation loop.

Agent “modes” are bundles of system prompt, tool selection, model and reasoning effort—not merely model aliases. As of the research date, Low uses GLM-5.2, Medium/High use GPT-5.6 Sol at different effort, and Ultra uses Claude Fable 5; task-specific system models handle media, compaction and titles ([Amp Models](https://ampcode.com/modes)). These identities are temporally unstable; the cited page is the evidence as of 2026-07-19.

### Comparison

The owner already has an eventful agent loop through Claude/Codex hook buses, goal reinjection, long-operation monitoring, terminal-state output conventions and provider-specific agent controls (`codex/AGENTS.md:14-60`; `claude/settings.json:81-523`; `codex/config.toml:82-130`). Amp’s improvement is not “having hooks”; it is a single typed, introspectable, in-process transformation surface with input modification, result replacement, result synthesis, UI and live reload/listing. The owner’s current design fans behavior across an external shared dispatcher and 71 local hook directories (filesystem count), and live defects show four detectors independently repeating the same use-versus-mention error (`INPUT-known-harness-defects.md:52-87`).

Amp is worse in two respects. First, its plugin docs explicitly say there is no `session.end` event, leaving cleanup semantics incomplete ([manual, `session.start`](https://ampcode.com/manual#event-examples)). Second, execute mode can start before plugins finish and skip `agent.start`/`agent.end` unless `--plugin-ready-timeout` is used ([manual, Non-Interactive Environments](https://ampcode.com/manual#cli-non-interactive-environments)). Do not copy lifecycle races or require every caller to remember a readiness flag.

### Port decision

#### Typed hook adapter with transform semantics — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Put one schema-normalizing adapter in front of the shared dispatcher. It should expose five decisions: `allow`, `reject_continue`, `modify_input`, `replace_result`, `inject_followup`; stamp event/session/tool IDs; validate returned shape; and log both original and transformed status. Existing Python hooks remain modules behind it. This does not add a second runtime.

This consolidation is **very likely (80-90%)** to prevent inconsistent per-hook interpretations, because D1 records four independent implementations sharing one discriminator flaw and D3 records missing durable hook telemetry (`INPUT-known-harness-defects.md:52-87,133-147`). Whether Claude and Codex hook payloads permit true pre-model result replacement is **UNVERIFIED**; settle it by capturing a known-safe `PostToolUse` payload and running a canary hook that replaces a unique result token, then verify the next model turn sees only the replacement. If either provider cannot replace, degrade that provider to annotation rather than pretending equivalence.

Anti-overfit gate: passes. It is a thin adapter on the existing dispatcher/hook bus, not a second orchestration runtime, memory database, critic service, durable engine, SaaS or guardrail framework.

## 2. Context management

Amp automatically compacts at 90%: summarize current context, start a fresh window with the summary, continue. It also uses isolated subagent contexts to keep verbose search/retry work out of the parent, lazy-loads skill bodies, dynamically includes subtree `AGENTS.md` guidance when a file is read, accepts glob-conditioned referenced guidance, filters MCP tools, and lets users reference prior threads for task-relevant extraction ([Amp rebuilt](https://ampcode.com/news/neo); [manual, AGENTS.md](https://ampcode.com/manual#AGENTS.md); [manual, Skills](https://ampcode.com/manual#agent-skills); [manual, Subagents](https://ampcode.com/manual#subagents)).

The owner already configures Claude auto-compaction at the same 90% (`claude/settings.json:18`), Codex local thread compression (`codex/config.toml:115`), structured subagent handoffs (`codex/AGENTS.md:43-46`), and a stronger post-compaction objective recovery rule: SessionStart replays objective ledger ground truth rather than trusting only a lossy summary (`codex/AGENTS.md:20-26`). Amp’s auto-compaction is parity, not an acquisition target.

Amp’s one-thread-per-task advice is sensible but deliberately rejects sprawling “forever threads.” Its earlier handoff experiment was removed in favor of compaction. Do not copy that historical oscillation as machinery. Focused threads plus ledger checkpoints is better than stacking summaries, while automatic compaction remains a safety net.

### Port decision

#### Conditional guidance inclusion by file globs — **NATIVE (Claude Code already does this; we just enable it)**

Preserve global rules as a small root contract; attach language/subtree rules only when matching files are read. Amp implements this with YAML `globs` on files referenced from `AGENTS.md`; closer subtree guidance wins. Claude already supports scoped rules/guidance mechanisms, so the mechanism is native and the work is content reorganization, not a new service.

It is **likely (55-80%)** to reduce irrelevant instruction load, based on Amp’s documented conditional inclusion and the owner’s very broad rule/skill surface. Token savings and compliance improvement are **UNVERIFIED**; settle with 30 representative tasks, recording injected rule tokens and rule-following errors before/after. Do not migrate all rules until the known-positive test proves at least one matching and one nonmatching file behave correctly.

## 3. Memory and continuity

Amp persists threads locally and synchronizes/stores them on Amp Server. A user can mention a thread ID/URL and Amp extracts relevant information; users can search personal and workspace threads by keyword, file, repo, author, date and task. Threads contain prompts, responses, tool calls/results and attachments and can be private, unlisted, workspace or group visible ([manual, Finding Threads](https://ampcode.com/manual#finding-threads); [manual, Thread Sharing](https://ampcode.com/manual#thread-sharing); [security, Thread Data](https://ampcode.com/security#thread-data)).

That is searchable episodic history, not documented ambient semantic memory. It is useful for provenance and team reuse, but Amp provides no documented equivalent of the owner’s explicit two-store distinction: objective event history versus curated semantic memory with temporal validity and supersession (`codex/AGENTS.md:62-85`). The owner is better here conceptually. The caveat is operational: basic-memory “does NOT auto-load” and relies on proactive queries (`codex/AGENTS.md:79-83`), while Amp makes shared thread search a first-class product surface.

Amp is worse for control/privacy: Amp Server stores thread data in multi-tenant GCP; private workspace threads remain visible to admins; deletion completes within 30 days; there is no self-hosted deployment ([security, Thread Data and System Components](https://ampcode.com/security)). The owner’s local/cross-tool store avoids making a vendor cloud the canonical memory. Do not copy Amp’s server merely to gain a feed.

### Port decision

#### Thread-to-memory provenance links — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

When writing a basic-memory note, store provider thread/session ID, repo/ref, changed files, timestamp, and a permalink/local transcript pointer. Add one existing-memory tool command that searches those fields and renders a compact provenance result. This ports Amp’s useful “find the work that touched this file” behavior without cloud thread centralization.

This is **likely (55-80%)** to improve recovery and auditability, based on Amp’s concrete search fields and the owner’s already canonical note store. Actual retrieval benefit is **UNVERIFIED**; settle with 20 historical questions whose answer lives in known sessions, comparing success@5 and time-to-answer before/after. Anti-overfit gate: passes because it extends the existing basic-memory MCP schema/index; it does not add a vector DB/KG or new durable runtime.

## 4. Tools and MCP

Amp provides built-in file/shell/search/media tools, custom plugin tools with JSON input schemas, MCP local/remote servers, OAuth, environment expansion, precedence rules, per-server tool filters, and `amp mcp doctor`. Workspace MCP definitions require explicit approval before execution. Most importantly, a skill can carry `mcp.json`; servers start with Amp but tools stay hidden until the skill is loaded, and `includeTools` narrows exposure ([manual, MCP Servers in Skills](https://ampcode.com/manual#agent-skills); [manual, MCP](https://ampcode.com/manual#mcp)). Tool names can be globally disabled by exact name or glob, and enterprise administrators can allow/block matching MCP server command/args or URL patterns (current manual configuration section).

The owner’s harness has much greater breadth—355-ish installed skills, 93 MCP servers touched and 78 skills actually invoked per the pinned corpus—but breadth is not the same as usable capability. The corpus’s dead Tavily calls and orphaned-plugin command-line inflation are direct counterexamples. Amp’s restrained exposure philosophy is better than the current “installed means ambient candidate” tendency. Amp also offers Librarian as a read-oriented cross-repository research subagent and Oracle as a reasoning tool, preventing every integration from becoming a globally advertised MCP namespace ([manual, Librarian/Oracle](https://ampcode.com/manual#oracle)).

Amp is worse where it starts skill MCP processes at launch even though their tools remain hidden. On this Windows owner machine, process/plugin enumeration already hits the 32,767-character CreateProcess boundary due to orphaned plugin directories. Do not port eager server startup; port lazy process start **and** lazy tool exposure. Amp’s official wording proves hidden exposure, not zero startup cost.

### Port decisions

#### Capability-scoped MCP registry and lazy activation — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Define for each skill: server ID, health command/endpoint, included tool globs, startup policy, cooldown and last-known state. At skill activation: validate executable/URL, start only then, run one bounded health probe, expose only included tools. On “not connected” or repeated transport failure: quarantine the server for the thread and inject one concise alternative, not another retry. On thread end: stop only processes this activation owns.

It is **almost certain (90-99%)** to stop calls to a server proven dead before exposure; the evidence is mechanical and the corpus records 135 “not connected” Tavily failures. It is **very likely (80-90%)** to reduce context/tool-choice clutter, supported by Amp’s design rationale. Overall task-quality effect is **UNVERIFIED**; settle with replay and measure tool-choice precision, completion rate and p95 latency. Anti-overfit gate: passes; registry metadata and activation live on the existing skill/MCP bus.

#### MCP trust-on-first-use for repository config — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Hash normalized server name + command/args/env-key names or URL/headers-key names from project config. Unknown/changed hashes require approval; user-global config remains governed by its own policy. Persist approval by project and hash so changing a command invalidates it. Amp’s `amp mcp approve` and `doctor` status provide the concrete precedent.

This is **very likely (80-90%)** to reduce repository-supplied code-execution risk, because it turns an untrusted config change into an explicit boundary. UX cost is **likely (55-80%)** low if approvals are hash-stable. **UNVERIFIED** whether current Claude project-MCP approval already covers every configured path; settle by creating a harmless project MCP canary in an isolated fixture and observing first-open behavior in Claude and Codex separately. If both natively gate and invalidate changed commands, classify the final implementation as `NATIVE (Claude Code already does this; we just enable it)` instead and do not duplicate it.

## 5. Permission model

Amp’s default is permissive: it does not ask before tools run and tells users of untrusted repos/MCP to add a policy plugin or isolate the environment. Its SDK/plugin permission rules support tool globs, nested argument matching, regex, arrays, main-thread versus subagent context, and actions `allow`, `reject`, `ask`, or `delegate` to an external command ([manual, Permissions](https://ampcode.com/manual#permissions); [TypeScript SDK, `createPermission`](https://ampcode.com/manual/sdk/typescript#createpermission)). Plugins can also use thread-scoped AI classification before prompting.

The owner is also permissive in practice: Claude `defaultMode` is `bypassPermissions`, with broad tool namespaces allowed and only credential-file patterns denied (`claude/settings.json:26-75`). However, the owner has explicit irreversible-action rules, a credential-read hook, test-tamper guard, no-force-push guard, and provider permission hooks (`settings.json:142-285`). Amp’s rule language is better than scattered regex guards; Amp’s default posture is not.

Do not copy AI-as-policy for irreversible actions. Amp’s example asks a model whether a git command is destructive. That creates a nondeterministic control exactly where the owner contract says block only dangerous/irreversible actions (`codex/AGENTS.md:48-54`). AI classification is acceptable only as a route to “ask,” never as sole authority to “allow.”

### Port decision

#### Structured argument/context permission rules — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Compile a small declarative rule set into the shared PreToolUse dispatcher: `{tool, argument predicates, context, action, reason}`. Match parsed tool fields—not serialized payload prose. First-match semantics must be explicit; startup validation rejects overlapping/invalid destructive rules. Support only `allow`, `deny`, `ask`; “delegate” is an implementation detail calling a deterministic helper. Feed every rule known-positive and known-negative fixtures.

This is **almost certain (90-99%)** to eliminate the recorded payload-versus-verb false positives for migrated rules, because the discriminator operates on parsed verb/target fields and D1’s nine false fires are fixtures (`INPUT-known-harness-defects.md:9-107`). Whether every provider supplies adequate structured fields is **UNVERIFIED**; settle with schema dumps from a harmless read, markdown write containing a quoted destructive command, and real blocked destructive canary. Anti-overfit gate: passes; it consolidates existing hook logic.

## 6. Customization surface

Amp has four clean layers:

1. `AGENTS.md`: durable always/conditionally loaded guidance, hierarchical by directory, compatible fallback to `AGENT.md`/`CLAUDE.md`.
2. Skills: on-demand instruction/resource packages with small always-visible name/description and optional MCP metadata.
3. Checks: scoped review criteria run in independent review subagents.
4. Plugins: TypeScript event handlers, commands, tools, UI, AI helper, custom agent modes and subagent tools; project/system/global locations; live reload and introspection ([manual, AGENTS.md](https://ampcode.com/manual#AGENTS.md); [manual, Plugins](https://ampcode.com/manual#plugins)).

This division is better articulated than the owner’s overlapping rules/commands/skills/hooks/plugins. The owner’s operational correction D4 shows why: a fabricated constraint in one launcher propagated to ~15 agent prompts and forced a more failure-prone write path (`INPUT-known-harness-defects.md:151-160`). Amp’s `plugins: list` and `agents-md list` are small but valuable provenance/introspection features.

Amp is worse on stability. It explicitly promises no backwards compatibility, killed legacy Toolboxes, and custom agent modes are experimental ([manual, Why Amp/Legacy Toolboxes/Custom Agent Mode](https://ampcode.com/manual)). That is acceptable for Amp’s managed product, not for an owner harness whose durable rules span providers. Do not bind the canonical contract to Amp plugin types.

### Port decision

#### Unified “why is this active?” inspection command — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Return, for the current repo/file/task: loaded rule files and precedence, matched hooks/policies, visible skills, visible MCP tools and owning skill, disabled/quarantined servers, and source hashes. Include a known-present control in each category and label detector failure separately from zero results. This directly operationalizes the mandatory two-signal discipline and Amp’s list/doctor affordances.

This is **very likely (80-90%)** to prevent false absence conclusions, because D2 documents seven such failures and the exact known-positive remedy (`INPUT-known-harness-defects.md:111-129`). Completeness across providers is **UNVERIFIED**; settle with a fixture containing one known rule, skill, hook, agent and MCP tool and require all five plus their origins. Anti-overfit gate: passes; this is a read-only view over existing registries, not observability SaaS.

## 7. Multi-agent support

Amp automatically spawns generic subagents for suitable tasks, especially in Medium mode. Each gets a fresh context and file/terminal access; multiple can run in parallel. It also has specialized Search, Review, Oracle, Librarian, Read Thread and media agents, and plugins can expose a custom agent as a tool ([manual, Subagents](https://ampcode.com/manual#subagents); [Amp Models, Subagents](https://ampcode.com/modes#subagents)). The Oracle deliberately uses a different frontier model from the main model in High mode, giving real architectural diversity rather than same-model self-consistency.

The hard limitation is explicit: subagents cannot communicate with each other, cannot be guided mid-task, start without accumulated conversation context, and the main agent sees only final summaries. This is materially worse than the owner’s Codex configuration (`interrupt_message=true`, depth 8, eight concurrent threads; `codex/config.toml:77-80,125-130`) and Claude agent-team hooks (`claude/settings.json:419-489`) plus structured handoffs (`codex/AGENTS.md:43-46`). Amp’s isolation is excellent for context hygiene but weak for coordination and correction.

### Port decisions

#### Different-model oracle for high-risk review — **CONFIG (settings/JSON only)**

The owner already exposes Claude and Codex and has multi-backend commands; define one routing rule: for high-risk design/security/debug review, request a fresh-context review from a model family different from the implementer, returning evidence and dissent rather than edits. Do not force it on routine tasks.

This is **likely (55-80%)** to find correlated blind spots better than same-model reflection, based on Amp’s deliberate cross-model Oracle design and the owner contract’s generator-critic requirement (`codex/AGENTS.md:56-60`). Net quality/cost is **UNVERIFIED**; settle with a blinded set of 30 known-defect patches, comparing unique true defects, false positives, latency and cost against same-model critic. This rides existing model/agent buses and introduces no trained critic.

#### Amp-style isolated subagent semantics — **NATIVE (Claude Code already does this; we just enable it)**

Use ordinary Task/subagent execution for independent, high-output retrieval or per-file work, with structured final summaries. This is already enabled (`CLAUDE_CODE_FORK_SUBAGENT=1`, `settings.json:5`; Task allowed at line 40). Do **not** replace agent teams with Amp’s non-steerable subagents when agents must coordinate, share ownership, or receive corrections.

## 8. Verification and self-check

Amp has three verification mechanisms:

* Prompt-driven iteration: its own prompting guide tells users to specify tests/logs/URLs and frequently screenshot UI work.
* Oracle: a distinct reasoning model can review a commit, proposed solution or bug analysis.
* `amp review` plus hierarchical Checks: Markdown criteria in `.agents/checks/`, subtree/global precedence, tool allowlists and severity; each check gets a separate subagent ([manual, Code Review/Checks](https://ampcode.com/manual#code-review)).

The check fan-out is Amp’s best verification feature because criteria are executable review units rather than one giant checklist. The independent contexts avoid one reviewer anchoring every criterion on its first theory. But Amp does not document a default universal “tests must pass before done” gate; its plugin example demonstrates how users can add one. The evidence is twofold: the manual’s known-present Checks section describes review invocation, while the known-present plugin lifecycle example implements tests via optional `agent.end` continuation. Therefore absence is scoped: **no documented always-on completion gate**, not proof about internal system prompts.

The owner already has `/verify`, `/quality-gate`, per-edit checks, test-tamper guard, Stop hooks and generator-critic guidance. It is stronger on available verification breadth but weaker on reliable signal quality: D1 records false detector verdicts, and corpus StructuredOutput schema mismatch is 22.9%. Amp’s lightweight Markdown check contracts avoid the owner’s over-strict fan-out schemas, but unstructured review output must still be normalized cautiously.

### Port decision

#### Hierarchical review checks with one fresh subagent each — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add `.agents/checks/*.md` discovery to the existing review skill/command. Frontmatter: `name`, `description`, `severity-default`, `tools`, optional file globs. Resolve nearest-file scope first, deduplicate by name, spawn one read-only subagent per applicable check, and merge findings by stable fingerprint `(check, path, line, normalized claim)`. Require evidence path/line and confidence; allow “no finding.” Do not require a brittle global StructuredOutput schema from every subagent—parse a minimal envelope and preserve raw Markdown when parsing fails.

This is **very likely (80-90%)** to improve criterion coverage over a single monolithic review, based on independent context per check and the owner’s existing parallel agents. It is **likely (55-80%)** to reduce schema-related failures if the envelope is deliberately minimal, based on the corpus’s 294 schema mismatches. Both quality claims are **UNVERIFIED**; settle with seeded-defect repositories and compare recall, precision, schema failure and tokens against `/quality-gate`. Anti-overfit gate: passes. This uses existing subagents and Markdown; it is not a trained critic or second orchestrator.

## 10. Recommended sequence

1. Build the read-only “why active?” command with known-positive controls. This prevents another detector-driven redesign from false zeroes.
2. Introduce structured permission/tool-result adapter and migrate only the four D1 detector classes, replaying all recorded false fires plus genuine positives.
3. Implement skill-scoped MCP activation with health/quarantine; A/B replay Tavily failures. Do not touch orphan directories as part of this unit—the pinned evidence says bulk deletion was stopped because many have no live sibling and one orphan was read by a live skill.
