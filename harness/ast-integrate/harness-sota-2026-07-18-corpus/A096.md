## Finding 1 — force-push hook overrides explicit user approval and over-broadly gates branches

### Contract text, verbatim

`/local_disk0/codexwork/bundle/claude/AGENTS.md:121-127`:

> 1. The user's explicit in-session instruction and the permission system.

`/local_disk0/codexwork/bundle/claude/AGENTS.md:64-70`:

> - **Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code, force-push to main without explicit approval.  
> - **Exit 0 + additionalContext (inject):** all other guidance (routing, reminders, goal injection). Never block on ambiguity; inject a clarifying route instead.

`/local_disk0/codexwork/bundle/claude/AGENTS.md:95-97`:

> - Never `--no-verify` on commits without explicit user instruction.  
> - Never `git push --force` to main/master without explicit user approval.

### Hook text, verbatim

The hook claims blocking authority at `/local_disk0/codexwork/bundle/claude/hooks/no-force-push/hook.py:2-15`:

> no-force-push/hook.py - FORGED tripwire discipline (PreToolUse, BLOCKING).  
> Generated by forge-discipline. This is a GATE: on a positive predicate it BLOCKS  
> the operation via the exit-2 path …

The predicate's authoritative action and match are `/local_disk0/codexwork/bundle/claude/hooks/no-force-push/tripwire.py:15-18`:

> ACTION = "Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1."  
> _PATTERN = re.compile("git\\s+push\\b[^\\n]*(--force\\b|-f\\b)", re.IGNORECASE)

On every match, `hook.py:52-56` writes that reason and returns 2. It is wired for every Bash call at `/local_disk0/codexwork/bundle/claude/settings.json:152-160`.

### Concrete collision

The owner explicitly approves `git push --force origin main`, or asks for `git push --force-with-lease origin feature/topic`. The contract puts the explicit instruction first and only states a mandatory approval gate for force-pushing `main/master`. The hook does not receive or inspect an approval fact and its regex neither distinguishes branch nor distinguishes `--force` from `--force-with-lease`.

The advertised command-local override is internally incoherent: `FORGE_NO_FORCE_PUSH_OFF=1 git push --force origin main` sets the variable only inside the Bash command that has not yet run. The hook is a separate PreToolUse process and reads its own pre-existing environment at `hook.py:29-32`; therefore the inline assignment cannot disable that already-running hook.

### Runtime winner — verified

The hook wins mechanically. I directly invoked the current hook with five JSON payloads, with `PYTHONDONTWRITEBYTECODE=1` to preserve the subject. Results:

```text

git push --force origin feature/topic                   -> rc 2
git push --force-with-lease origin feature/topic        -> rc 2
FORGE_NO_FORCE_PUSH_OFF=1 git push --force origin main  -> rc 2
git push origin main                                    -> rc 0
```

Each rc 2 emitted the action string above. This agrees with the shipped chaos evidence at `no-force-push/SELFTEST-RESULT.txt:8-18`, the end-to-end test at `no-force-push/chaos_no_force_push.py:53-70,113-158`, and Anthropic's official PreToolUse exit-code semantics. The direct probe proves the detector on a known-present case and its benign control; static settings wiring is the independent signal that the process is actually on the event path.

**Confidence:** **almost certain (90-99%)** that the configured hook overrides an explicit approval when enabled, based on the current regex, direct process outcomes, current settings registration, and official runtime semantics. **UNVERIFIED live Windows enablement — settle with `Get-ChildItem Env:FORGE_NO_FORCE_PUSH_OFF` in the Claude parent process plus one benign synthetic PreToolUse invocation:** the bundle cannot reveal an environment variable inherited by the owner's currently running Windows process.

Keep the predicate, but on a match return exit 0 with a structured PreToolUse `permissionDecision: "ask"` and a reason naming the remote/branch and force mode. ## Finding 2 — WorktreeCreate contradicts the universal fail-open rule

### Contract text, verbatim

`/local_disk0/codexwork/bundle/claude/AGENTS.md:64-70`:

> - **Exit 2 (block):** irreversible/dangerous only …  
> - **Exit 0 + additionalContext (inject):** all other guidance …  
> - All hook code wrapped in try/except; any hook error exits 0 (fail-open).

The last sentence is universal: it does not carve out lifecycle-provider hooks whose successful output is required to continue.

### Hook text, verbatim

`/local_disk0/codexwork/bundle/claude/hooks/create-worktree.ps1:1-5`:

> # Claude Code WorktreeCreate hook.  
> # stdin: JSON { cwd, worktree_config: { base_directory, worktree_name, source_ref } }  
> # stdout (on exit 0): absolute path of the created worktree. Non-zero exit aborts creation.

The hook deliberately exits 1 when no repository resolves (`create-worktree.ps1:118-130`), when `git worktree add` fails (`147-149`), or when an unexpected exception reaches the outer catch (`157-159`). It is wired at `settings.json:506-515`.

### Concrete collision

A WorktreeCreate request arrives with malformed JSON, no candidate Git repository, an invalid source ref, or a genuine `git worktree add` failure. The contract commands the hook error to exit 0. But an exit-0 WorktreeCreate hook must emit the created path; pretending success without a worktree would be false and unusable. The hook instead claims that non-zero is the required abort protocol.

This is not a hypothetical dormant branch: the no-repo and git-failure branches are ordinary reachable operational outcomes, and the outer catch handles malformed input.

### Runtime winner — verified

The WorktreeCreate hook wins. Current code returns 1, current settings invoke it, and Anthropic's official hook reference says WorktreeCreate is the exception where **any non-zero exit aborts worktree creation**. I did not execute the hook because a successful probe would create a real worktree and violate this unit's read-only scope; the code branch plus independently documented host protocol are sufficient to determine the runtime outcome without mutation.

**Confidence:** **almost certain (90-99%)** that a qualifying WorktreeCreate failure aborts creation rather than failing open, based on `create-worktree.ps1:130,149,157-159`, `settings.json:506-515`, and the official event-specific semantics.

### Minimal resolution

#### Proposal 2 — narrow the fail-open sentence to policy/observer hooks

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Edit `AGENTS.md:70` minimally:

> Policy, advisory, and observer hooks are wrapped in try/except; internal errors exit 0 (fail-open). Lifecycle implementation hooks whose successful output creates the requested resource (currently WorktreeCreate) must return the event's native failure status rather than fabricate success.
