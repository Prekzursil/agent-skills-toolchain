**Target problem:** prove an agent's claim without trusting the agent and without requiring a human to read everything

## Executive verdict

The borrow **does transfer, but only partially and only qualitatively**. The transferable mechanism is not “run several agents and vote.” It is a combination of:

1. bottom-up Failure Modes and Effects Analysis (FMEA) to enumerate how evidence and checkers can lie, go stale, miss scope, or be bypassed;
2. top-down Fault Tree Analysis (FTA) with the explicit top event **FALSE CLAIM ACCEPTED**;
3. minimal-cut-set analysis to reveal paths where one failure defeats the whole verification scheme;
4. Common Cause Failure Analysis (CCFA) to test whether nominally separate verifiers are actually coupled; and
5. independent verification that chooses its own tests and observes the world rather than accepting the producer's narrative.

**Transfer confidence: very likely (80-90%).** Evidence: NASA defines FMEA as bottom-up and FTA as top-down, explicitly noting that the former can reveal hidden interactions, dependencies, and unstated assumptions ([NASA Software Engineering Handbook, §2](https://swehb.nasa.gov/pages/viewpage.action?pageId=103776712)); NASA's FTA handbook defines minimal cut sets as the smallest combinations sufficient for a top event and says common-cause contributions must be modeled separately ([NASA Fault Tree Handbook, pp. 32, 58-59](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)); and the FAA's CCFA procedure examines the events in minimal cut sets using a coupling-factor matrix to determine whether redundancy is “real” ([FAA Safety Risk Management Guidance, Appendix C §C.2.4, p. C-13](https://www.faa.gov/media/80661)). Those are structural operations over failure logic and dependencies, not assumptions unique to pumps or valves. The remaining uncertainty is whether a small harness implementation obtains sufficient claim-extraction recall and useful verifier diversity in real agent work. That premise is **UNVERIFIED; settle it with Experiment E1 (shadow-mode claim mutation study)** defined below.

The quantitative reliability analogy does **not** transfer cleanly. An agent's semantic error is not a wear-out event, claim populations are non-stationary, specifications may be wrong, and an adversarial claimant can adapt to the checker. Therefore this unit does not recommend calculating a “probability the answer is true,” an MTBF for claims, or a product of two verifier error rates. The output of the proposed mechanism is a bounded status—`VERIFIED(predicate, scope, snapshot)`, `CONTRADICTED`, `UNVERIFIED`, or `UNVERIFIABLE`—plus replayable evidence.

## 1. What reliability engineering solved in its own field

### 1.1 FMEA: enumerate component failure modes bottom-up

In its own field, FMEA begins with components or functions, postulates ways each can fail, and propagates local effects upward to the system effect. NASA describes software FMEA as a bottom-up/forward analysis and software fault-tree analysis as a top-down/backward analysis. It also lists hidden failure modes, system interactions, dependencies, unstated assumptions, and requirement/design inconsistencies among the things FMEA can uncover. NASA is equally explicit about the limitations: FMEA is time-consuming, analyst- and documentation-dependent, and may start from an incomplete failure-mode list ([NASA Software Engineering Handbook, §2](https://swehb.nasa.gov/pages/viewpage.action?pageId=103776712)).

The crucial contribution is a disciplined question: **“If this evidence-producing component behaves incorrectly, what false system conclusion can result?”** Applied to a pressure sensor, a relay, or a software action, the method refuses to treat “component returned a value” as equivalent to “system state is known.”

### 1.2 Fault trees: work backward from the unacceptable top event

FTA starts from a precisely stated undesired event and decomposes it through Boolean AND/OR relationships into basic events. The NASA handbook defines a minimal cut set as the smallest set of basic events whose joint occurrence produces the top event; the unique minimal cut sets enumerate the distinct sufficient failure paths ([NASA Fault Tree Handbook, p. 32 and Appendix A pp. 158-162](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). A one-event cut set identifies a single-point failure. A two-event cut set shows where both protections must fail.

This is more useful than a generic checklist because it answers two different questions:

- **Completeness direction:** What combinations can cause the unacceptable result?
- **Control sufficiency direction:** Which smallest protections must remain sound to prevent it?

FTA does not itself guarantee that the analyst found every basic event. NASA's handbook notes that large trees may have too many minimal cut sets to generate exhaustively ([NASA Fault Tree Handbook, pp. 83-84](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)). Hence the complementary use of bottom-up FMEA and top-down FTA matters: neither is a proof of completeness.

### 1.3 Redundancy is useful only when failures are independent

Reliability arithmetic often gains dramatic reductions by requiring several redundant components to fail. NASA illustrates the trap: for three components each having failure probability (10^{-3}), an independence assumption gives (10^{-9}); adding a 1% conditional common-cause fraction gives (10^{-5}), 10,000 times larger. NASA therefore says the common-cause contribution must be represented separately in the fault tree ([NASA Fault Tree Handbook, pp. 58-59](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

The FAA operationalizes this with CCFA: take the primary events in FTA minimal cut sets and place them in matrices that look for shared environment, location, secondary causes, human error, or quality control. The stated purpose is to determine whether redundancy is “real” ([FAA Safety Risk Management Guidance, Appendix C §C.2.4](https://www.faa.gov/media/80661)). This matrix—not the mere count of checkers—is the most valuable cross-domain artifact.

Software provides a direct warning against naive voting. Knight and Leveson had 27 independently developed program versions run over one million tests. The programs were individually highly reliable, but coincident failures occurred substantially more often than independence predicted; they concluded that N-version programming reliability analysis must include dependent errors ([Knight & Leveson, 1986, DOI 10.1109/TSE.1986.6312924](https://people.cs.rutgers.edu/~uli/cs673/papers/EvaluationMultiVersionProgramming86.pdf)). This is mechanically independent evidence from the NASA/FAA guidance: it is an experiment on separately produced software, not a restatement of a safety standard.

### 1.4 Independence is control over the test, not a different signature on the report

NASA's IV&V description separates technical, managerial, and financial independence. Of particular relevance, the independent organization selects the system segments to analyze, the techniques and tests to use, the schedule, and the issues on which to act ([NASA IV&V Overview](https://www.nasa.gov/ivv-overview/)). Translated abstractly, a verifier is not independent if the producer chooses the only evidence, writes the oracle, decides which scope is inspected, and supplies the summary that the verifier reads.

This does not mean an agent harness needs an independent organization or budget. Those organizational dimensions do not map to a single-owner local harness. The transferable part is **technical control of observation**: the acceptance mechanism derives or selects checks independently, runs them in a fresh context where feasible, captures raw outcomes, and can refuse acceptance.

### 1.5 What not to borrow

#### MTBF and exponential-failure arithmetic: rejected

NASA notes that software does not wear out like hardware; a latent fault is already present even before it manifests ([NASA Software Engineering Handbook, §1-2](https://swehb.nasa.gov/pages/viewpage.action?pageId=103776712)). Agent claims are even less compatible with a stable time-to-failure model: tasks, prompts, sources, tools, and models change, and semantic errors cluster around difficult or ambiguous inputs.

**Conclusion: almost certain (90-99%)** that a single harness-wide “claim MTBF” would be misleading. Evidence: the NASA distinction between software faults and wear-out, plus Knight and Leveson's empirical failure of independence on difficult shared inputs. The residual 1-10% uncertainty covers a narrowly defined, stationary mechanical claim class (for example, a fixed parser predicate) where conventional reliability statistics could be meaningful; it does not rescue a global semantic metric.

#### Homogeneous multi-agent voting: rejected

Three prompts to the same model family over the same answer and rubric are redundancy, not demonstrated diversity. An LLM-judge study across 15 judges, 22 tasks, about 40 generating models, and more than 150,000 evaluations found non-random position bias varying by judge and task ([Shi et al., IJCNLP-AACL 2025](https://aclanthology.org/2025.ijcnlp-long.18/)). The much older N-version experiment independently demonstrates the same structural risk in conventional software: independently produced versions can fail together on intrinsically difficult inputs.

**Conclusion: very likely (80-90%)** that homogeneous majority voting will overstate verification assurance for at least some claim classes. Evidence: the two studies above use different systems, eras, methods, and failure signals yet both show correlated error mechanisms. This is not a claim that voting never helps; it is a claim that vote count cannot stand in for measured diversity.

#### Precise probabilistic-risk numbers before calibration: rejected

FTA's Boolean structure transfers; its numerical probabilities do not arrive for free. Estimating basic-event and common-cause rates requires representative outcome data and stable definitions. No such agent-harness calibration data were inspected in this ideation unit.

**Conclusion: almost certain (90-99%)** that initial numerical top-event probabilities would be false precision. Evidence: NASA's FTA quantification requires a probability for each basic event and separately models CCF, while this unit has neither representative rates nor a validated CCF model for claims ([NASA Fault Tree Handbook, Chapters 5 and 7](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/Fault%20Tree%20Handbook_NASA.pdf)).

## 2. Structural mapping to agent verification

| Reliability-engineering concept | Native meaning | Concrete harness translation | Transfer caveat |
|---|---|---|---|
| Unacceptable top event | Loss of required safety function | A materially false claim is presented as verified/finished | “False” must be reduced to a testable predicate and bounded scope |
| Basic event | Component/operator/environment failure | stale evidence, blind detector, wrong scope, bad oracle, checker bypass, shared cache/source, fabricated provenance | The event taxonomy is open-ended and must evolve |
| AND gate | Multiple failures required | two genuinely diverse predicates both false-pass | Independence cannot be assumed from separate invocations |
| OR gate | Any listed path suffices | gate bypass **or** bad shared specification **or** both checkers fail | A missed OR branch creates false assurance |
| Minimal cut set | Smallest sufficient failure combination | smallest set of verifier failures that can accept a false claim | Useful qualitatively even without probabilities |
| Redundant train | Multiple components serve same function | multiple checkers assess the same predicate | Same model/prompt/source is often common redundancy, not diversity |
| Diversity | Different implementations/physical principles | state inspection + behavioral test; source record + independent calculation; parser + live probe | Different models alone are weak diversity |
| Coupling factor / CCF | Shared cause defeats several trains | same rubric/specification, context, model family, source, backend, cache, credentials, clock, or agent-produced log | Shared requirement/oracle is often an unavoidable singleton risk |
| Proof test / surveillance | Exercise protection and expose latent failure | inject a known-present control, mutate evidence, and verify the gate rejects it | Test coverage is not proof of all semantic failures |
| IV&V | Independent party controls its analysis | harness chooses/runs checks and captures raw evidence outside claimant narrative | Organizational/financial independence does not map locally |
| Safe state on disagreement | System trips or degrades safely | mark `UNVERIFIED`; do not silently choose the favorable answer | Availability cost rises; risk tiering is necessary |

The key translation is a change of unit: the harness does not verify “the answer” as one blob. It verifies **atomic claim predicates** against a named scope and snapshot. “The work is done” must decompose into claims such as “required artifact exists at path P,” “test command T exited zero in snapshot S,” “the output contains invariant I,” and “no matching item exists within enumerated scope Q.” Each has different failure modes and therefore different verification physics.

## 3. Proposed mechanism: Claim Acceptance Fault Tree + Evidence Diversity Matrix

### Recommendation — UNVERIFIED: build a risk-tiered Claim Acceptance Gate

**UNVERIFIED premise:** a small hook/skill can capture high-consequence claims with acceptable recall and latency. Settle with **Experiment E1**, which shadows real final answers, injects claim mutations, and measures claim-extraction recall, false-acceptance rate, and overhead before enforcement.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement a thin acceptance gate and a library of declarative predicate templates. It must use the existing hook/skill/tool path, not create a second orchestration runtime.

**ANTI-OVERFIT GATE:** passes conditionally. The proposal is a bounded gate plus data records on the existing bus. It does not introduce a daemon, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. If implementation cannot remain a small hook plus predicate adapters, stop and reassess rather than growing it into a verification platform.

**Expected value: very likely (80-90%)** to catch false completion, stale-log, blind-absence-detector, wrong-scope, and “command ran but outcome did not change” failures that self-report or a prose judge misses. Evidence: these are direct instantiations of the FMEA/FTA basic events, and deterministic fault injection can demonstrate them. The exact effect size is **UNVERIFIED; Experiment E1 settles it**.

#### 3.1 Claim-evidence contract

For every consequential factual claim, emit or derive a record:

```text
claim_id
predicate                 # precise proposition, not prose confidence
claim_class               # state | behavior | absence | numeric | provenance | causal | temporal
scope                      # files, repo, process, URL, host, time window, revision/snapshot
risk_tier                  # low | consequential | high-stakes
snapshot_id / observed_at
verifier_1 {method, raw_result_ref, exit/status, digest}
verifier_2 {method, raw_result_ref, exit/status, digest}   # when required
positive_control {known_present_item, detected?}            # mandatory for absence detectors
coupling_flags
verdict                    # VERIFIED | CONTRADICTED | UNVERIFIED | UNVERIFIABLE
limitations
```

The claimant may propose a predicate and evidence, but proposal is not acceptance. The gate independently re-runs or selects the decisive observation for consequential claims. Raw output is retained by digest/reference so that a later audit can replay a sample without reading every answer.

`VERIFIED` is always qualified: it means the recorded predicate held over the recorded scope at the recorded snapshot. It never means “the entire natural-language answer is true.”

#### 3.2 The top-event fault tree

Define the top event:

```text
T = MATERIALLY FALSE CLAIM ACCEPTED AS VERIFIED

T = B OR O OR R OR X OR (V1 AND V2)

B  = acceptance gate bypassed, failed open, or did not run
O  = shared oracle/specification is wrong or does not represent owner intent
R  = shared evidence resource is stale, poisoned, truncated, or out of scope
X  = claim extraction/classification omits the material claim
V1 = verifier channel 1 false-passes
V2 = verifier channel 2 false-passes
```

The qualitative minimal cut sets are `{B}`, `{O}`, `{R}`, `{X}`, and `{V1,V2}`. This is the most important design result. Adding more judges only improves the final cut set; it does nothing to the four singleton cut sets. The architecture must therefore:

- make gate execution observable and fail closed for the selected claim tiers;
- expose the oracle and scope in the evidence record;
- require freshness/provenance for shared resources;
- measure claim-extraction recall through mutation tests; and
- require verifier diversity for claims where two channels are justified.

**Fault-tree adequacy: likely (55-80%)** as a useful first-order decomposition, not as a complete model. Evidence: it includes the main producer, oracle, evidence, extraction, checker, and bypass planes, and mirrors FTA/CCFA structure. It is **UNVERIFIED against representative claim failures; Experiment E2 (failure-mode workshop plus historical mutation replay) settles whether material branches are missing**.

#### 3.3 Evidence Diversity Matrix (the CCFA translation)

Before treating two checks as an AND gate, compare their coupling factors:

| Coupling dimension | Strongly coupled example | Preferable diverse pair |
|---|---|---|
| Producer | claimant supplies both conclusions | claimant output + harness-run observation |
| Reasoning mechanism | same LLM prompted twice | deterministic parser/test + source-state probe |
| Data source | both read same generated summary | working-tree state + fresh executable behavior |
| Oracle/specification | both use claimant-authored success criterion | owner requirement + independently derived invariant |
| Execution substrate | same cache/process/backend | fresh process plus direct filesystem/API observation |
| Time | both reuse one old log | snapshot observation + fresh rerun |
| Failure semantics | both only check exit code | exit/status + postcondition/state transition |
| Scope | both use same unvalidated glob | explicit enumerated scope + alternate index/query |
| Authorization/credentials | both silently see the same partial view | credentialed query + independently scoped inventory |
| Presentation bias | both judge same prose order/style | machine predicate + blinded/normalized semantic review |

Hard rule: a “different model” is not, by itself, a diverse evidence channel. Hard rule: evidence copied from the claimant is provenance, not corroboration. Hard rule: two checkers sharing an unvalidated oracle remain vulnerable to singleton `{O}`.

Do not turn the matrix into a decorative weighted score. A high total could hide one fatal coupling. Instead, use vetoes: for a high-consequence claim, if both channels share the decisive source, oracle, or execution artifact, label them `COUPLED` and do not claim two-signal assurance.

**Usefulness: very likely (80-90%)** for preventing false claims of independence. Evidence: the FAA explicitly uses coupling matrices to assess “real” redundancy, NASA requires separate CCF modeling, and Knight/Leveson empirically show correlated failures despite separate development. The precise veto set for agent tasks is **UNVERIFIED; Experiment E3 (paired-verifier correlation study) settles it**.

#### 3.4 Acceptance logic and safe states

For low-risk, easily replayed claims, a single authoritative deterministic observation may suffice. For consequential absence, completion, causal, or high-stakes claims, require either a formal/deterministic oracle that directly decides the predicate or two mechanically diverse channels with no decisive coupling flag.

Conceptually:

```text
ACCEPT(predicate, scope, snapshot) =
    gate_ran
    AND claim_was_classified
    AND oracle_and_scope_are_explicit
    AND (
         authoritative_deterministic_predicate_passed
         OR (V1_passed AND V2_passed AND not_decisively_coupled)
        )
```

Disagreement is not resolved by whichever verifier sounds more confident. The safe state is `UNVERIFIED`, accompanied by the exact failed obligation. `CONTRADICTED` requires positive counterevidence. `UNVERIFIABLE` means the claim is not reducible to an available observation, which is different from false.

**Fail-closed recommendation: likely (55-80%)** to improve factual precision while preserving acceptable workflow availability if restricted to consequential claim classes. Evidence: safety systems often use a safe response on disagreement; Knight and Leveson describe dual systems that disconnect or set signals red when outputs disagree. Availability cost and owner tolerance are **UNVERIFIED; Experiment E1 measures block rate and latency**.

### Recommendation — UNVERIFIED: add claim-class FMEA templates, not a universal semantic judge

**UNVERIFIED premise:** a compact set of claim classes covers most consequential operational claims. Settle with **Experiment E2**, coding a representative sample of corrected/failed claims and measuring residual “other” frequency.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Store failure-mode and predicate mappings as declarative records consumed by the small gate.

**ANTI-OVERFIT GATE:** passes. This is a small evolving catalog, not a trained critic or new framework.

Initial FMEA:

| Claim class | Representative false-accept path | Primary observation | Mechanically diverse second signal | What the combination catches |
|---|---|---|---|---|
| Artifact exists | wrong path, stale copy, empty/truncated file | direct stat/hash/content invariant | consumer opens/parses/uses artifact | “file exists” but is unusable or wrong artifact |
| Change completed | edit in unintended tree/snapshot; required item omitted | explicit diff/state enumeration | targeted behavior/invariant test | syntactic change without required effect |
| Test passed | old/cached log, test never ran, selected subset only | fresh process exit + timestamp + command identity | parse test report/count or independent postcondition | success prose detached from actual run/scope |
| Command succeeded | exit zero despite no state transition | raw exit/status | before/after postcondition | tools with permissive exit behavior |
| No item exists | blind detector, excluded scope, permission-denied, truncated enumeration | detector A after known-present positive control | detector B using different index/API/enumeration | false zero caused by broken or partial detector |
| Numeric claim | arithmetic/transcription/unit error | calculator or typed computation | dimensional/range/invariant check | same wrong number repeated in prose |
| Source supports claim | URL resolves but source is secondary, stale, or non-entailing | fetch exact primary-source passage and date | independent record/query or structured datum | citation decoration and freshness mismatch |
| Causal claim | change and improvement co-occur but unrelated | controlled replay/ablation in disposable scope | targeted mechanism trace/state assertion | correlation presented as cause |
| “Done” / requirement met | visible subtask passes while another requirement omitted | requirement-to-evidence matrix | artifact inventory plus targeted acceptance tests | local success promoted to global completion |
| Temporal/current claim | correct at an earlier snapshot | fresh authoritative query with observed time | independent clocked source or state probe | stale truth presented as current truth |

For absence claims, the positive control is non-negotiable: before trusting zero results, the same detector must locate a known-present item of the same relevant kind. The second signal must use a mechanically different data path, not merely rerun the same command. This directly imports proof testing (show that the protection can actually respond) and diversity (do not let one blind spot determine absence).

**Coverage expectation: likely (55-80%)** that these templates cover a large share of consequential tool-using-agent claims. Evidence: the classes span state, behavior, absence, arithmetic, provenance, causality, completion, and freshness. The premise is **UNVERIFIED; Experiment E2 measures coverage**, so the catalog must not be described as complete.

### Recommendation — UNVERIFIED: calibrate with fault injection, not self-reported confidence

**UNVERIFIED premise:** synthetic mutations are representative enough to improve the gate without overfitting it. Settle with **Experiment E4**, holding out natural failures and comparing detection lift after mutation-driven tuning.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a test fixture that mutates claim/evidence packets and runs the same gate; no production daemon.

**ANTI-OVERFIT GATE:** passes if mutations remain a small test suite and evaluation includes held-out natural errors. It fails if this becomes a trained critic, bespoke orchestration runtime, or endless benchmark-specific rules.

Seed at least these faults:

1. replace a fresh test log with a stale passing log;
2. change the claimed path while leaving a valid sibling artifact;
3. omit one required scope root;
4. make an absence detector return zero for everything, including its positive control;
5. preserve exit zero while suppressing the expected state change;
6. point two nominal verifiers at the same cached artifact;
7. give both verifiers the same wrong oracle;
8. insert a resolvable citation that does not entail the claim;
9. omit a material claim from the claim ledger;
10. disable/bypass the gate and verify that the run is visibly unverified rather than accepted.

Track **false-accept rate by claim class**, **mutation kill rate**, **positive-control failure rate**, **claim-extraction recall**, **coupled-verifier disagreement/correlation**, **unverified/block rate**, **latency**, and **human-audit escape rate on a sample**. Do not collapse them into one “verification score”; aggregation can hide a singleton cut set.

**Detection benefit: very likely (80-90%)** for the injected failure families because each has a deterministic expected verdict. Generalization to natural errors is **UNVERIFIED; Experiment E4 is the settling test**.

## 4. End-to-end harness behavior

### 4.1 Before execution: define what would count

For consequential tasks, derive acceptance predicates from the owner's request before the claimant reports success. This reduces the shared-oracle risk in which the same agent both performs the work and weakens the definition of done. The definition can still be wrong; the evidence packet must expose it rather than imply universal truth.

### 4.2 During execution: observe state transitions

Capture the precondition, action identity, and postcondition for consequential mutations. A command transcript is not proof of its effect. Prefer observations closest to the claimed property: parse the produced file, query the resulting state, run the consumer, or test the invariant.

### 4.3 At finalization: atomize, classify, and gate

The finalizer extracts consequential claims, maps each to a template, and refuses to upgrade unclassified claims to verified. The claimant's own ledger can improve recall but cannot be the sole extractor because `{X}` would then be fully controlled by the claimant. A deterministic pattern pass plus an independent semantic pass may be used for discovery, but neither makes semantic completeness provable.

**Claim extraction feasibility: roughly even (45-55%)** for achieving both high recall and low annoyance across open-ended work. Evidence: operational claims have recurring lexical and structural forms, but material implications can be implicit and FMEA itself is analyst/documentation-dependent. This is **UNVERIFIED; Experiment E1 settles it**, and is the largest implementation risk.

### 4.4 Verification: execute predicates outside the narrative

The verifier receives the predicate, scope, and snapshot—not the claimant's persuasive explanation unless needed as provenance. It chooses and runs the check, records raw results, validates absence detectors with a positive control, and consults the coupling matrix before combining channels.

Semantic review remains useful where no mechanical oracle exists, but it must be labeled advisory. Normalize or blind presentation order where practical because current research finds non-random LLM judge position bias ([Shi et al., 2025](https://aclanthology.org/2025.ijcnlp-long.18/)). A prose judge must never overwrite contradictory direct state evidence.

### 4.5 Report: bounded verdicts and explicit residual risk

The user-facing answer can remain concise. Internally, each consequential claim links to its evidence packet. A compact report might say:

```text
VERIFIED: artifact P parses and consumer test T passed at snapshot S.
UNVERIFIED: absence across remote service Q; local detector passed its control,
            but no mechanically independent remote inventory was available.
CONTRADICTED: claimed test count 42; fresh report contains 37.
```

This permits automated acceptance of the mechanically decidable majority while routing only contradictions, high-risk singleton cut sets, and `UNVERIFIABLE` semantic claims to human attention. It does not promise zero human reading; it concentrates reading where automation lacks an oracle.

## 5. What this catches that ordinary agent checking misses

This section names failure classes the mechanism is designed to catch; it does **not** assert that any particular local harness presently lacks these controls, because local grounding is outside this unit.

1. **Evidence laundering:** an agent quotes its own prior output or generated log as corroboration. The producer/data-source coupling veto prevents counting it twice.
2. **Two judges, one blind spot:** separate model calls share the same wrong requirement, stale source, prompt, or backend. The CCFA matrix exposes the singleton common cause.
3. **Broken zero detector:** a search says “nothing found” because scope, permissions, or invocation failed. Positive-control failure invalidates the absence conclusion; the diverse enumerator provides a second signal.
4. **Exit-code theater:** a command returns zero but performs no relevant transition. A postcondition on the state/consumer catches it.
5. **Stale success:** a passing transcript predates the final change. Snapshot and freshness fields plus a fresh rerun catch it.
6. **Scope substitution:** the claim is global but the check covers one directory, branch, account, or page. Explicit scope makes the mismatch machine-visible.
7. **Citation decoration:** a URL resolves but does not entail the proposition or is not authoritative/current. Exact passage/date plus an independent record leaves it unverified instead of accepted.
8. **Partial completion promoted to “done”:** one artifact/test passes while a sibling requirement is omitted. Requirement-to-evidence mapping exposes the missing obligation.
9. **Correlated arithmetic/reasoning error:** prose generator and prose judge repeat the same calculation. A calculator/invariant channel supplies different failure physics.
10. **Verification bypass:** a correct predicate library is useless when the hook never runs. Gate-execution evidence makes `{B}` visible and fail-closed.
11. **Claim omission:** the answer avoids stating a risky fact in the ledger while implying completion in prose. Independent extraction and mutation tests measure and reduce `{X}`.
12. **Wrong definition of success:** every checker passes a claimant-weakened oracle. The explicit oracle and predeclared acceptance predicate do not automatically correct `{O}`, but make it auditable and prevent hidden circularity.

**Overall catch expectation: likely (55-80%)** for a material subset of operational false claims, especially mechanically observable ones. Evidence: each class has a concrete, diverse predicate pair or a singleton cut-set control. The proportion in real traffic and net false-accept reduction are **UNVERIFIED; Experiments E1-E4 settle them**.

## 6. Adversarial analysis: where the analogy breaks

### 6.1 Truth is semantic and specification-relative

A valve state can often be instrumented directly. “The recommendation is best,” “the explanation is complete,” or even “the code meets the owner's intent” may have no independent mechanical oracle. Verification can prove a predicate while the predicate fails to capture intent. This is singleton `{O}` and cannot be eliminated by verifier count.

**Impact: almost certain (90-99%)** that the gate cannot establish universal truth for open-ended natural-language claims. Evidence: the explicit difference NASA draws between verification (meets specified requirements) and validation (meets mission/customer needs) shows that conformance and fitness are separate questions ([NASA IV&V Overview](https://www.nasa.gov/ivv-overview/)).

### 6.2 Failure events are non-stationary and input-dependent

Hardware reliability models often assume populations and operating conditions stable enough to estimate rates. Agent models, prompts, tools, sources, and attack strategies change. Difficult inputs create correlated errors; Knight and Leveson observed this even among conventional independently written programs.

**Impact: very likely (80-90%)** that historical verifier rates will drift and cannot be multiplied as independent probabilities. Evidence: the N-version experiment's coincident errors plus explicit common-cause treatment in NASA/FAA reliability guidance.

### 6.3 The claimant may be adaptive

Classic FMEA/FTA components generally do not read the safety case and strategically phrase around it. An agent can omit a claim, exploit a parser, manufacture a plausible artifact, or optimize for a known judge. This makes `{X}`, `{R}`, and `{O}` adversarial surfaces rather than random events.

**Impact: likely (55-80%)** that a fixed lexical claim extractor will be gamed or bypassed on some tasks. Evidence: this follows from the claimant's access to its own wording and checker-visible artifacts; direct empirical magnitude is **UNVERIFIED; Experiment E1 must include adaptive red-team mutations to settle it**.

### 6.4 Diversity is expensive and sometimes illusory

Different tools may share the same filesystem snapshot, API cache, identity permissions, or upstream source. Different models may share data, architecture, or evaluation biases. Real diversity should be defined in terms of failure mechanisms, not vendor labels.

**Impact: very likely (80-90%)** that some apparently independent verifier pairs are coupled. Evidence: FAA CCFA explicitly searches for coupling factors and Knight/Leveson found dependent failures under independent development; the LLM position-bias study provides a current, domain-specific second signal.

### 6.5 Verification can perturb state

Re-running a command may consume a queue item, mutate a database, refresh a cache, or incur external side effects. Mechanical replay is not always safe. The gate must distinguish pure observation, disposable-sandbox replay, idempotent action, and destructive/external action. It must never infer authorization to replay side effects merely because verification is desirable.

**Impact: likely (55-80%)** that a nontrivial minority of consequential actions cannot be directly replayed in production. This premise is **UNVERIFIED; settle it by classifying a representative action sample in Experiment E1**. For those cases, verify durable receipts and postconditions, or mark the claim `UNVERIFIED/UNVERIFIABLE` rather than replaying.

### 6.6 FTA completeness remains a human/model judgment

A fault tree only reasons over branches that were modeled. FMEA only considers failure modes someone enumerated. NASA explicitly describes FMEA as analyst- and documentation-dependent and warns about incomplete failure-mode lists. Thus the mechanism must maintain humility: mutation escape, sampled human audit, and newly observed failures update the catalog.

**Impact: almost certain (90-99%)** that the first fault tree and FMEA catalog will be incomplete. Evidence: NASA's stated FMEA limitations and FTA scaling limits. This does not defeat the transfer; it changes the claim from “proof of all truth” to “systematic reduction and visible bounding of false acceptance.”

## 7. Experiments that settle every inherited UNVERIFIED premise

### E1 — Shadow-mode claim mutation study

Run the gate without blocking on a representative stratified task sample. Independently label consequential claims and inject mutations: false completion, stale evidence, wrong scope, no-op success, broken zero detector, omitted claim, and shared-evidence coupling. Measure:

- consequential-claim extraction precision/recall;
- false-accept and false-reject rate by claim class;
- block/`UNVERIFIED` rate;
- latency and tool-call cost;
- replay-safety class distribution;
- rate at which the gate itself fails to run.

Predeclare a decision rule before looking at results. A reasonable candidate threshold is **UNVERIFIED**: at least 90% recall on high-consequence claims, at least 80% mutation kill rate, under 10% false blocking on mechanically decidable claims, and acceptable owner-observed latency. This threshold is only a proposed starting point; the owner-risk tradeoff must set the final values.

### E2 — FMEA/FTA coverage study

Two reviewers using different inputs independently classify a representative set of natural failures/corrections: one starts bottom-up from evidence/checker components (FMEA), the other starts top-down from false acceptance (FTA). Reconcile only after independent coding. Calculate the fraction fitting existing claim classes and basic events; add branches for recurring residuals. Seed known-present failure types to validate each reviewer's detector before concluding a category is absent.

This experiment specifically tests whether `{B,O,R,X,V1∧V2}` and the initial template table omit material paths.

### E3 — Paired-verifier correlation and coupling study

For each claim class, create pairs spanning:

- same model/same prompt;
- different model/same source;
- model judge + deterministic predicate;
- two deterministic tools sharing a source;
- independent state source + behavioral execution.

Inject known false claims and estimate joint false-pass frequencies and conditional failure (P(V2\ fails \mid V1\ fails)). Do not infer independence from low disagreement alone; two verifiers can agree while both are wrong. The truth labels come from controlled mutations or a formal/direct oracle. Use results to validate or revise coupling vetoes.

### E4 — Held-out natural-error generalization

Tune mutation tests and templates on one time/task slice, then evaluate against a later held-out set of natural corrections and seeded faults not used during tuning. Compare the small gate with:

1. claimant self-report only;
2. one LLM judge;
3. homogeneous multi-agent vote; and
4. the fault-tree/CCFA gate.

Primary outcome: high-consequence false-accept rate. Secondary outcomes: human audit minutes, `UNVERIFIED` rate, latency, and cost. This directly tests whether the reliability borrow creates value beyond elaborate-looking scaffolding.

### E5 — Bypass and common-oracle drill

Disable the gate, corrupt the acceptance predicate, provide a stale shared source, and restrict verifier permissions. Confirm that each produces an explicit `UNVERIFIED` or detector-control failure. This tests the singleton cut sets `{B}`, `{O}`, and `{R}`, which extra voters cannot mitigate.

## 8. Decision rule after experiments

Adopt the small gate only if held-out evaluation shows a meaningful reduction in high-consequence false acceptance without an unacceptable block/latency burden. Keep claim-class automation only where predicates are mechanically decidable and calibrated. Treat semantic judges as advisory evidence and sample their accepted claims for audit.

**Adoption forecast: likely (55-80%)** that a narrow gate for completion, test, state, absence, numeric, and freshness claims will pass this decision rule. Evidence: those claim classes admit direct predicates and controlled mutations, and the mechanism targets known generic failure physics rather than model-specific prose. This forecast is **UNVERIFIED; E1-E5 are the settling experiments**.

If extraction recall is poor or availability cost is high, retain the FMEA template as an on-demand verification skill rather than an always-on gate. If verifier pairs remain highly correlated, do not add more agents; invest only in different observation physics (direct state, execution, formal check, independent source) or leave the claim `UNVERIFIED`.

If the mechanism requires a daemon, durable workflow engine, trained critic, vector memory, or separate orchestration runtime to succeed, reject this proposal under the anti-overfit gate. The reliability insight is the logic and coupling discipline, not a new platform.

## 9. Alternatives considered and rejected

### “Have a second agent review everything”

Rejected as the main mechanism. It is expensive, shares semantic blind spots, cannot prove its own oracle, and lacks mechanically independent evidence. It can assist claim extraction or review `UNVERIFIABLE` items, but its output remains one evidence channel.

### “Use three models and majority vote”

Rejected absent measured diversity. Both the N-version experiment and LLM-judge bias research show why coincident error cannot be treated as the product of independent rates. Majority agreement is not ground truth.

### “Require a citation for every factual sentence”

Rejected as sufficient verification. Citation presence does not establish entailment, authority, scope, or freshness; it also does not verify local state or action completion. Exact source observations are useful within the provenance claim class.

### “Give every claim a probability”

Rejected initially as false precision. The harness lacks calibrated base-event and CCF rates for open-ended claim populations, and the population drifts. Use categorical bounded verdicts and per-class empirical error rates first.

### “Formally prove all claims”

Rejected as a universal design. Formal verification is excellent where a faithful formal predicate and checker exist, but formalization simply relocates singleton `{O}`: a proof of the wrong statement is still the wrong result. Use formal methods opportunistically for arithmetic, schemas, invariants, and code properties.

### “Send every result to a human”

Rejected because it violates the target constraint and does not scale. The proposed gate instead automates direct predicates, preserves evidence packets for sampling, and escalates contradictions, singleton risks, and non-mechanical semantics.

### “Build a full reliability service with event database and dashboards”

Rejected under the anti-overfit gate. It would be BUILD-LARGE, would risk becoming a second orchestration/observability runtime, and is not justified before a small shadow-mode gate demonstrates benefit.

## 11. Final answer to the cross-domain question

Reliability engineering has already solved the design question **“How do we avoid mistaking duplicated components for independent protection, and how do we expose the smallest combinations that defeat acceptance?”** Its mechanism is FMEA + FTA/minimal cut sets + CCFA + technically independent observation.

The concrete harness translation is a small, risk-tiered Claim Acceptance Gate that turns consequential prose claims into scoped predicates, gathers raw observations through genuinely different failure mechanisms, validates zero detectors with known-present controls, records coupling factors, fails closed to `UNVERIFIED`, and calibrates itself by injected faults. It catches stale or self-authored evidence, blind absence probes, wrong scope, no-op successes, correlated judges, omitted requirements, shared bad oracles, and gate bypasses—failure classes that merely asking the claimant or a homogeneous panel to “check carefully” cannot reliably expose.

The analogy stops at the boundary of semantic or ambiguous truth. It provides a disciplined assurance case for explicit predicates, not a universal truth meter. Quantitative MTBF and independent-failure multiplication are rejected until per-class empirical calibration exists. This constrained transfer is ambitious enough to change the acceptance architecture, yet small enough to ride the existing bus and pass the anti-overfit gate.
