# X140 — Systems-safety → trust calibration

## Executive verdict

The cross-domain borrow transfers, but only in a narrower form than the slogan “treat agent outputs like safety-critical systems” suggests. The useful mechanism is a **task-scoped assurance case with explicit defeaters, populated by a STPA-style analysis of unsafe control actions**. The output is not a universal reputation score for an agent. It is a compact, inspectable argument that a particular output is fit for a particular use, in a stated context, supported by evidence whose applicability and independence are visible.

This is **very likely (80-90%)** to improve trust calibration for consequential, objectively checkable agent work because (1) safety cases make the claim/context/evidence chain reviewable, (2) STPA searches for harmful interactions and control failures rather than only component failures, and (3) NASA's assurance-case work specifically recommends searching for defeaters rather than merely accumulating confirming evidence. Those are direct structural matches to agent-output assessment: the same output can be trustworthy for one use and unsafe for another; individually plausible steps can interact badly; and self-reported confidence is supporting rhetoric rather than independent evidence. Sources: the [GSN Community Standard v3](https://scsc.uk/r1386.pdf), the [STPA Handbook](https://www.flighttestsafety.setp.org/images/STPA_Handbook.pdf), and NASA's report on [assurance arguments and defeaters](https://ntrs.nasa.gov/api/citations/20160000772/downloads/20160000772.pdf).

It is **unlikely (20-45%)** that a full graphical GSN authoring environment or mandatory case for every response would improve the harness overall. That would add friction, encourage ceremonial paperwork, and tightly couple ordinary work to an elaborate assurance layer. The [GSN standard](https://scsc.uk/r1386.pdf) defines a notation, not proof that every task benefits from it; NASA describes safety cases as comprehensive arguments used in safety-critical certification contexts, not as a universal per-message protocol ([Denney and Pai](https://www.nasa.gov/wp-content/uploads/2022/07/tool_support_for_assurance_case_development.pdf)). The appropriate borrow is therefore a small data contract and a risk-triggered runtime gate, not a second orchestration runtime.

The central design principle is:

> Calibrate belief in a claim, for a use and context, from auditable evidence and unresolved defeaters—not belief in an agent as a stable personality.

I used four related systems-safety traditions, but only two supply the positive mechanism:

1. STAMP/STPA supplies the control-theoretic hazard search.
2. Safety/assurance cases supply claim–argument–evidence structure and explicit defeaters.

4. Normal Accident Theory supplies a warning against increasing interactive complexity and tight coupling in the name of safety.

The last two constrain the design; they are not presented as quantitative trust estimators.

## 1. What the source field actually solved

### 1.1 STAMP/STPA: safety is a control problem, not merely a component-reliability problem

In STAMP, losses can arise when interactions among otherwise functioning components violate system-level safety constraints. STPA operationalizes that view. The handbook's basic procedure is to define losses and hazards, model the control structure, identify unsafe control actions, and construct loss scenarios explaining why unsafe control could occur or why a safe command might not be executed ([Leveson and Thomas, *STPA Handbook*](https://www.flighttestsafety.setp.org/images/STPA_Handbook.pdf); MIT's [books and handbooks index](https://psas.scripts.mit.edu/home/books-and-handbooks/) describes the handbook as proactive analysis of hazards and future loss scenarios).

For each control action, STPA systematically asks four guideword questions:

1. Is not providing the control action hazardous?
2. Is providing it hazardous?
3. Is providing it too early, too late, or out of order hazardous?
4. Is stopping it too soon or applying it too long hazardous?

That four-way scheme appears in the handbook and is independently summarized in this [STPA method guide](https://octo.org.uk/posts/stpa_method/) and John Thomas's [STPA workshop material](https://indico.cern.ch/event/402151/attachments/1130843/1616245/STPA_Day_2_v2_san.pdf).

The important source-field accomplishment is not a numeric probability. It is a repeatable way to expose hazards caused by missing, inappropriate, mistimed, or overlong control—especially hazards invisible to a component-by-component fault checklist.

### 1.2 Assurance cases: confidence is an argument with bounded scope, not a badge

A safety case is a structured, defensible justification that risks for a specified system and context are understood and controlled, with evidence and monitoring of the controls. NASA describes it as an audit trail from concept through operation and emphasizes both control of identified risks and monitoring control effectiveness ([Denney and Pai](https://www.nasa.gov/wp-content/uploads/2022/07/tool_support_for_assurance_case_development.pdf)).

Goal Structuring Notation (GSN) makes the structure visible through:

- a top claim;
- context and assumptions that bound that claim;
- argument strategies and subclaims;
- evidence (“solutions”);
- explicit markings for undeveloped or uninstantiated claims.

The authoritative syntax and best-practice guidance are in the [GSN Community Standard v3](https://scsc.uk/r1386.pdf). A UK government example shows how undeveloped goals expose missing credible argument or evidence and how hierarchical numbering provides traceability ([Tornado Safety Case, Annex A](https://assets.publishing.service.gov.uk/media/5a804d6940f0b62305b8a5b1/20040220_Annex_A_-_Tornado_SC__v1_U_0__-_Baseline.pdf)).

The stronger modern refinement is **defeater-centered assurance**. Rather than asking only “what evidence supports the claim?”, reviewers ask “what plausible fact or reasoning defect would defeat this step?” NASA's Assurance 2.0 report recommends conscious search for defeaters at each argument step and warns that the limited independence of bespoke review remains a concern ([Rushby et al., NASA/CR-2015-218802](https://ntrs.nasa.gov/api/citations/20160000772/downloads/20160000772.pdf)). Assurance 2.0 further argues that uncertainty should be localized in evidential steps while interior reasoning should be deductive where feasible; the authors explicitly label feasibility a question, not a settled fact.

This is the source field's closest answer to trust calibration: confidence is justified only to the extent that a contextualized claim is supported by applicable evidence and survives active attempts to defeat it.

### 1.3 Swiss cheese: independent-looking barriers may share holes

Reason's model treats defenses, barriers, and safeguards as imperfect layers. Harm occurs when their holes align; the holes include active failures and latent conditions. The original concise account is [Reason, “Human error: models and management,” BMJ 2000](https://www.bmj.com/content/bmj/320/7237/768.full.pdf). The model's useful lesson here is that adding a checker does not automatically create an independent layer. If generator and checker share the same model family, prompt assumptions, retrieved source, or malformed intermediate representation, their errors can align.

The analogy has limits. Swiss cheese is a causal metaphor, not a method for calculating posterior confidence. Later analysis notes that the graphical metaphor can bias reasoning and that its changing visual interpretations are not a full sociotechnical model ([Larouzée and Le Coze 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10607274/)). Therefore the proposal below records evidence dependence explicitly; it does not multiply nominal “layers” and pretend their error probabilities are independent.

### 1.4 Normal accidents: added safety machinery can make the system less governable

Perrow's mechanism is the conjunction of interactive complexity—failures interacting in unexpected or opaque ways—and tight coupling—little slack or opportunity to isolate a disturbance before it cascades. The primary book chapter is [Perrow, “Complexity, Coupling, and Catastrophe”](https://www.degruyterbrill.com/document/doi/10.1515/9781400828494-005/html). A National Academies treatment applies the distinction to software and recommends attention to modularity, buffering, and redundancy ([*Software for Dependable Systems*, Observation 4](https://www.nationalacademies.org/read/11923/chapter/3)). Perrow later recommends decomposition into units joined by monitored links and warns that after-the-fact safety add-ons are disproportionately accident sources ([“Organizing to Reduce the Vulnerabilities of Complexity”](https://onlinelibrary.wiley.com/doi/abs/10.1111/1468-5973.00108)).

This constrains the borrow: an assurance mechanism that introduces a new orchestration service, hidden state, synchronous reviewer fan-out, or a long chain of mandatory agents can create the very coupling it is meant to control.

## 2. Structural mapping to agent trust

| Systems-safety construct | Agent-harness analogue | Concrete meaning |
|---|---|---|
| Loss | Owner-visible bad outcome | Wrong external action, corrupted artifact, false high-stakes advice, secret disclosure, irreversible change |
| Hazard | System state that can lead to loss | Output accepted despite stale evidence; write authorized on an unresolved target; summary omits a decisive exception |
| Controller | Agent, tool gate, reviewer, or human approver | Entity deciding whether to answer, act, verify, abstain, or escalate |
| Control action | Answer, tool call, approval request, acceptance/rejection | A consequential transition, not merely generated text |
| Process model | Agent's beliefs about task, environment, permissions, freshness, and evidence | Often incomplete or stale; disagreement with reality is a major hazard source |
| Feedback | Tool results, tests, external sources, user correction, downstream outcome | Evidence that should update the process model |
| Safety constraint | Trust rule tied to a hazard | “Do not assert current fact without fresh authoritative evidence”; “do not mutate until target identity is resolved” |
| Assurance-case top claim | Fitness-for-use claim | “Output O is fit to support decision D under context C” |
| Evidence | Artifact with provenance | Test output, cited source, independent calculation, diff, schema validation, owner confirmation |
| Defeater | Plausible reason claim/evidence/inference fails | Stale source, shared generator/checker blind spot, test did not exercise changed path, task outside agent's measured slice |
| Defense-layer dependence | Correlated evaluator failures | Same model, same prompt, same source, same cached state, or one output paraphrased by several reviewers |
| Coupling/slack | Ease of stopping and isolating bad output | Preview before execution, reversible staging, async review, scoped permissions, explicit abstention |

The mapping is **very likely (80-90%)** structurally sound for consequential tool-using agents because both domains contain controllers acting from imperfect internal models, feedback delays, contextual constraints, and losses produced by interactions rather than only broken components. The evidence is the STPA control-loop formulation in the [handbook](https://www.flighttestsafety.setp.org/images/STPA_Handbook.pdf) and the National Academies' observation that software components can operate within specification while unanticipated interactions still cause failure ([source](https://www.nationalacademies.org/read/11923/chapter/3)).

The mapping is only **roughly even (45-55%)** for open-ended creative or taste-based tasks because “loss,” “hazard,” and objective evidence may not be stable enough to define without collapsing owner preference into a false engineering constraint. Evidence: assurance-case guidance depends on a clearly scoped claim and context ([GSN standard](https://scsc.uk/r1386.pdf)); subjective quality often lacks that condition. The harness should therefore use ordinary conversational judgment for low-stakes subjective tasks, not manufacture a safety case.

## 3. Proposed harness mechanism — UNVERIFIED: Task Trust Case (settle with the phased experiment in §7)

### Proposal A — UNVERIFIED: risk-triggered Trust Contract (settle with §7 replay and shadow mode)

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Before a consequential task begins, attach a small `trust_contract` to the run:

```json
{
  "use": "basis for merging a code change",
  "losses": ["regression", "unintended file mutation"],
  "task_slice": ["language", "framework", "operation"],
  "required_claims": ["requested behavior implemented", "unrelated behavior preserved"],
  "required_evidence_kinds": ["targeted test", "diff inspection"],
  "max_evidence_age": "this workspace state",
  "disposition_if_open_defeater": "hold-for-review"
}
```

Activation should be driven by consequence and reversibility, not verbose taxonomies: external side effects, secrets, financial/legal/medical content, destructive operations, publishing/merging, or an owner-marked high-stakes task. All other tasks bypass the mechanism.

This is **likely (55-80%)** to prevent category errors such as treating an agent's strong coding history as evidence for current legal research, because it binds acceptance to a use and task slice. Evidence for the design principle is GSN's explicit context around top-level claims ([GSN standard](https://scsc.uk/r1386.pdf)); the harness-specific effect is **UNVERIFIED — settle by replaying a stratified sample of 100 cross-domain tasks and measuring how often global-agent reputation would accept while the contract lacks task-applicable evidence**.

### Proposal B — UNVERIFIED: STPA-derived unsafe-action template (settle with §7 seeded tests)

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

At design time, generate a short hazard table for each consequential action class using the four STPA guidewords:

| Action | Not provided | Provided when unsafe | Wrong time/order | Too long/too short |
|---|---|---|---|---|
| Verify freshness | Current claim remains unchecked | Needless browsing leaks context/cost | Verification occurs after action | Cache accepted beyond validity |
| Ask owner approval | Irreversible action proceeds | Low-risk work stalls | Approval obtained before target resolves, then context changes | Old approval treated as perpetual |
| Publish/merge/write | Needed result withheld | Wrong or unverified result escapes | Side effect precedes tests/review | Mutation scope continues beyond requested target |
| Abstain/escalate | Agent fabricates certainty | Agent refuses routine work | Escalation comes after harm | Run remains indefinitely blocked |

Each cell yields a safety constraint and, where detectable, a hook assertion. This catches omission and timing failures that a final-answer fact checker cannot: verification performed after an external action; an initially valid approval reused after target drift; a reviewer invoked but given an already-truncated artifact; or an agent continuing mutations after the requested bounded change.

This is **very likely (80-90%)** to broaden hazard discovery beyond “answer is factually wrong,” because the four guidewords explicitly cover omission, commission, sequence, and duration ([STPA guide](https://octo.org.uk/posts/stpa_method/)). Whether fewer than 200 lines suffice for this harness is **UNVERIFIED — settle by implementing one action class as a throwaway branch prototype and counting non-generated executable lines plus integration adapters**.

### Proposal C — UNVERIFIED: claim/evidence/defeater ledger (settle with §7 blinded replay)

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For each required claim, store:

```yaml
claim: "changed behavior is correct for parser v4"
context: "repository state <digest>; Windows PowerShell 7"
evidence:
  - ref: "test-result://..."
    supports: "new branch handles quoted refs"
    provenance: "command + exit + captured output"
    freshness: "after final edit"
    applicability: "exercises changed branch"
    independence_group: "runtime-test-A"
defeaters:
  - statement: "test fixture omits non-ASCII paths"
    status: open
    severity: material
disposition: hold-for-review
```

The gate should distinguish at least four dispositions: `supported`, `supported-with-caveat`, `hold-for-review`, and `unsupported`. It should never derive a high-precision universal score such as “Agent X = 87% trustworthy.” A scalar hides claim scope, evidence dependence, and catastrophic open defeaters. Counts or rates may be displayed as historical context, but acceptance is controlled by required evidence and material defeaters.

This is **likely (55-80%)** to catch “evidence-shaped” failures: a passing test that predates the last edit; citations that support background but not the asserted conclusion; two reviewers dependent on the same flawed source; or a result verified only on a different OS. The source-field support is that assurance cases expose claims, contexts, evidence, and undeveloped nodes ([GSN standard](https://scsc.uk/r1386.pdf)) and that defeater search is a systematic evaluation method ([NASA Assurance 2.0](https://ntrs.nasa.gov/api/citations/20160000772/downloads/20160000772.pdf)). The harness effect is **UNVERIFIED — settle with blinded adjudication of 300 completed outputs, comparing defect yield and false holds against the current acceptance path**.

### Proposal D — UNVERIFIED: independence labels for defensive layers (settle with §7 correlated-error tests)

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Every evidence item records a coarse `independence_group`: same-generation trace, same-model review, different-model review, deterministic tool, authoritative external source, owner observation, or downstream outcome. The gate does not assume two items are independent merely because two agents produced them. For high-consequence claims, require either one direct deterministic observation or two genuinely different evidence paths; exact policy depends on loss severity.

This is **likely (55-80%)** to expose correlated “Swiss cheese” holes because provenance makes shared inputs visible. Reason's model establishes that multiple imperfect defenses fail when holes align ([BMJ](https://www.bmj.com/content/bmj/320/7237/768.full.pdf)); NASA separately flags limited independent review of bespoke assurance cases ([NASA Assurance 2.0](https://ntrs.nasa.gov/api/citations/20160000772/downloads/20160000772.pdf)). It is **UNVERIFIED — settle by seeding 50 defects whose misleading premise is shared across generator and reviewer, then compare detection with and without independence labels**.

### Proposal E — UNVERIFIED: per-agent × task-slice outcome cards (settle with §7 held-out prediction study)


This is **likely (55-80%)** to calibrate users better than a global agent leaderboard because the card exposes applicability and unknown outcomes, mirroring assurance cases' scoped contexts. It is **UNVERIFIED — settle with a preregistered user study comparing prediction of held-out task correctness from global scores versus slice cards**. Stable “agent identity” across model, prompt, tool, and policy updates is **unlikely (20-45%)**; evidence is conceptual rather than empirical here, so this claim is **UNVERIFIED — settle by change-point analysis across known runtime/configuration revisions**.

## 5. Adversarial transfer analysis

### Where the analogy holds

1. **Context changes whether an action is safe.** A control action can be required in one state and hazardous in another; likewise, an answer can be fit for brainstorming and unfit for executing a medical or financial decision. This match is **almost certain (90-99%)** because both STPA's unsafe-control-action definition and GSN top claims explicitly include context ([STPA guide](https://octo.org.uk/posts/stpa_method/), [UK GSN guidance](https://www.asems.mod.uk/printpdf/toolkit/goal-structuring-notation-and-claim-trees)).

2. **Failures are interactional.** A model, retriever, shell, and reviewer can each behave as designed while their composition produces an unsafe result. This match is **very likely (80-90%)**; the National Academies gives the analogous software case where components operate within specification but unanticipated values at their interface cause failure ([source](https://www.nationalacademies.org/read/11923/chapter/3)).

3. **Evidence does not speak for itself.** Applicability, freshness, scope, and inference determine what evidence supports. This match is **almost certain (90-99%)** because assurance cases explicitly separate claims, context, argument, and solutions rather than treating evidence attachment as proof ([GSN standard](https://scsc.uk/r1386.pdf)).

4. **Counterevidence search is different from confirmation.** A second agent asked “is this good?” can rationalize the first answer; a defeater prompt asks what observation would make a specific inference fail. This match is **very likely (80-90%)**, supported directly by NASA's recommended conscious search for plausible defeaters ([report](https://ntrs.nasa.gov/api/citations/20160000772/downloads/20160000772.pdf)).

### Where it breaks

1. **Safety has engineered boundaries; general agency often does not.** Aircraft and medical devices usually have specified operating concepts, hazards, and accountable operators. An open-ended assistant faces shifting goals and ambiguous preference. A complete safety-case analogue for arbitrary conversation is **very unlikely (5-20%)** to remain honest and usable; evidence is the dependence of GSN claims on explicit context and the absence of such context in many subjective prompts. The latter premise is **UNVERIFIED — settle by coding 500 real prompts for whether loss, context, and adjudicable fitness criteria can be specified without additional owner input**.

2. **Agent competence is nonstationary.** Model versions, system prompts, tools, retrieved context, and environment change. Treating “the agent” like a manufactured component with a stable failure rate is **unlikely (20-45%)** to be valid. This is **UNVERIFIED — settle by longitudinal change-point analysis as described in Proposal E**. Therefore the mechanism scopes evidence to runtime/configuration and task slice.

3. **Agent outputs can shape their own evaluation.** The generator may select tests, summarize logs, choose citations, and frame the review prompt. That endogeneity is stronger than in many independently regulated safety cases. It makes self-produced confidence and same-trace review weak evidence. The disanalogy is **very likely (80-90%)** because the same causal actor controls both claim and evidence selection by construction; independence labels and deterministic/raw evidence reduce but do not eliminate it.

4. **Catastrophic thresholds differ from everyday utility.** Safety cases often justify “acceptably safe,” whereas trust calibration needs graded behavior across trivial, reversible, and catastrophic tasks. A binary case gate for every response is **very unlikely (5-20%)** to be proportionate. Risk-triggered activation is necessary.

5. **Unknown unknowns remain.** STPA is a disciplined search, not completeness proof; assurance cases can contain fallacies and omitted evidence. A published taxonomy documents recurring fallacies in system safety arguments ([Greenwell et al.](https://citeseerx.ist.psu.edu/document?doi=fe28dce0dc1bb4920b437adbf43f214e0cc28437&repid=rep1&type=pdf)). It is **almost certainly not (1-5%)** the case that a Trust Case can certify truth in the general case. The output must say “supported under these assumptions,” never “guaranteed.”

6. **The Swiss-cheese metaphor can invite false multiplication.** Adding three same-model reviewers is not equivalent to three independent physical barriers. The claim that nominal reviewer count alone materially increases reliability is **unlikely (20-45%)**; evidence is Reason's requirement that layer holes not align and NASA's warning about independence, but the exact correlation in an agent fleet is **UNVERIFIED — settle with paired seeded-error experiments across same-model and genuinely heterogeneous evidence paths**.

### Bottom line on transfer

The analogy survives only if the unit of trust is a **claim-in-context**, not an agent; if counterevidence is first-class; and if the mechanism preserves slack and inspectability. It fails when converted into a universal score, a claim of certification, or a large mandatory review bureaucracy.

## 6. Anti-overfit gate and rejected alternatives

The proposed mechanism rides the existing hook/skill/MCP bus as a small record, a template generator, and a gate. It does not require a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### Rejected: assurance-case daemon

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** This option is rejected.

A service that maintains live argument graphs, schedules reviewer agents, and blocks every action would increase interactive complexity and tight coupling. It would also reintroduce a second orchestration runtime, explicitly disallowed by the anti-overfit gate absent extraordinary evidence. Rejection is **very likely (80-90%)** correct because Perrow specifically recommends decomposition through monitored links and warns about safety add-ons ([source](https://onlinelibrary.wiley.com/doi/abs/10.1111/1468-5973.00108)); no evidence here shows a daemon's marginal benefit.

### Rejected: universal trust number

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** This option is rejected despite cheap implementation.

One number pooled across agent and task type destroys context, hides unknown outcomes, and makes correlated evidence appear additive. Rejection is **very likely (80-90%)** correct from the assurance-case requirement that claims be contextualized ([GSN standard](https://scsc.uk/r1386.pdf)).

### Rejected: mandatory multi-agent jury

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** This option is rejected as a default.

Same-model juries can share holes; synchronous fan-out adds cost and coupling; majority vote cannot repair a shared false premise. Rejection as a universal default is **likely (55-80%)**, based on Swiss-cheese dependence and NASA's independence concern. Whether heterogeneous juries help selected task slices is **UNVERIFIED — settle with the seeded correlated-error experiment in §7**.

### Retained minimal architecture

The retained design is deliberately small:

```text
risk trigger
    ↓
trust contract (claim + context + required evidence)
    ↓
normal agent/tool execution on existing bus
    ↓
evidence + provenance + independence labels
    ↓
defeater check
    ↓
supported | caveat | hold | unsupported
    ↓
optional outcome update to task-slice card
```

This architecture is **likely (55-80%)** to preserve most of the source-field value without overfitting because it adds structured metadata at existing boundaries rather than a new controller. That remains **UNVERIFIED — settle by measuring task latency, block rate, defect yield, and maintenance burden in the phased experiment**.

## 7. Experiments required before adoption

All recommendations above inherit the following empirical gate. No production claim should be made from analogy alone.

### Phase 0 — detector controls

Before measuring defects, prove the evaluator detects known-present conditions:

- positive control: a claim with a valid post-edit deterministic test;
- negative control: a test from before the final edit;
- dependence control: two reviewer outputs derived from the same seeded false source;
- context control: valid approval whose target digest then changes;
- open-defeater control: applicable evidence plus one material counterexample.

Use two mechanically independent outcome signals for every “caught” claim: (1) the structured gate disposition and reason code, and (2) an independent raw-event audit comparing timestamps/digests/source lineage. A pass from the same gate run twice is not independence.

### Phase 1 — offline replay

Stratify at least 300 completed tasks across coding, research, summarization, external-action, and high-stakes advice slices. Blind adjudicators to baseline versus Trust Case. Measure:

- material defects caught before acceptance;
- false holds on correct work;
- added wall-clock and token cost;
- fraction of cases with unresolvable context;
- defect yield by defeater type;
- performance separately for deterministic versus judgment-heavy tasks.

Adoption threshold proposed for offline evaluation: at least a 25% relative increase in pre-acceptance detection of material defects, no more than 10% absolute false-hold rate on triggered tasks, and median added latency below 15% when no extra reviewer is required. These thresholds are policy suggestions, **roughly even (45-55%)** to be the right tradeoff because no owner utility curve is available; they are **UNVERIFIED — settle by owner review of replay examples and explicit valuation of false holds versus escaped defects**.

### Phase 2 — seeded causal tests

Inject paired failures:

1. stale but otherwise valid evidence;
2. correct source with non-entailing claim;
3. same-model reviewers sharing a seeded premise;
4. different-model reviewer with the same source versus deterministic independent evidence;
5. approval followed by target drift;
6. verification after irreversible action;
7. task-domain shift with strong global agent history;
8. missing feedback mislabeled as success.

The causal question is whether each metadata field changes disposition, not merely whether an evaluator can explain the defect after disclosure.

### Phase 3 — shadow mode, then narrow enforcement

Run the mechanism without blocking for two weeks or a fixed 200 triggered tasks. Compare warnings with downstream corrections and owner overrides. Enable blocking only for the task slices where replay and shadow mode both show net benefit. Require an escape hatch that records the owner override as context, not as proof the claim was true.

A narrow production rollout after these phases is **likely (55-80%)** to be safer than immediate universal enforcement because it preserves slack, reveals false-hold costs, and avoids coupling all work to an unvalidated mechanism. Evidence is the Normal Accident Theory emphasis on coupling and monitored decomposition ([Perrow](https://onlinelibrary.wiley.com/doi/abs/10.1111/1468-5973.00108)); the exact rollout benefit is **UNVERIFIED — settle by randomized shadow-mode comparison where operationally safe**.
