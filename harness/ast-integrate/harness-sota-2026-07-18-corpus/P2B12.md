**Local versions observed:** Gemini CLI `0.45.2`; Claude Code `2.1.214`. Gemini's documented latest stable is `0.50.0` (2026-07-08), so this teardown uses the current published product/source rather than treating the locally installed Gemini binary as the frontier ([Gemini v0.50.0 release notes](https://geminicli.com/docs/changelogs/latest/)).

## Executive verdict

Gemini CLI is not a better wholesale architecture for this owner. Its core is a conventional but well-factored streaming agent loop: model turn, typed tool-call scheduling, policy/confirmation, concurrent execution, tool results back to the model, repetition until a terminal answer, with automatic compression and loop recovery in the loop itself. The most important conclusion is that **the current Claude Code substrate has caught up with, or surpassed, most features that superficially look like Gemini deltas**: lazy subdirectory rules, automatic tool-output eviction and compaction, project trust, file checkpoints and conversation rewind, resumable/forkable sessions, skills, plugins, OAuth MCP, isolated background subagents, and communicating agent teams are all native Claude Code capabilities now. Rebuilding them in the shared hook harness would be duplication.

The genuinely useful Gemini ideas are smaller:

1. an operator-facing hook panel with execution counts, last results, errors, and timing;
2. a review inbox for proposed memory changes (but **not** autonomous skill activation);
3. explicit pre-registration MCP/tool allowlists with restrictive merge semantics;
4. one bounded, result-aware loop-recovery feedback turn before escalation;
5. transparent capability discovery in the workspace trust dialog.

The first and fourth are already partly present locally: the shared dispatcher records provider/event/result/elapsed time in `terminal.jsonl` (`C:\Users\Prekzursil\.agents\harness\dispatcher.py:487-513`), and the existing loop stack fingerprints `(tool, args, output)` rather than merely `(tool, args)` (`C:\Users\Prekzursil\.claude\hooks\anti-degen\fingerprint.py:2-16`). The right move is to finish and expose those primitives, not import Gemini's runtime.

**Overall confidence: very likely (80-90%).** Evidence: current official Gemini docs and main-branch source, current official Claude Code docs, the live local configuration/version probes, and the pinned corpus/defect inputs agree on the major surfaces. The remaining uncertainty is product behavior not exercised locally on Gemini `0.50.0`, especially experimental Auto Memory, Context Manager, remote A2A agents, and Windows tool sandboxing.

## 1. Agent loop

### 1.1 What Gemini does

Gemini's current `GeminiClient.sendMessageStream()` bounds a request to at most 100 internal turns, invokes `BeforeAgent`, manages/compresses context, selects a model, streams a `Turn`, watches every stream event for looping, returns pending tool calls to the scheduler, and invokes `AfterAgent` when no tools remain. If `AfterAgent` denies completion, the reason becomes a continuation request and the loop retries. The source also performs availability fallback and optionally asks a small “next speaker” check whether the model should continue after an apparently terminal response ([`client.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/client.ts)).

The scheduler is an explicit state machine—validating, scheduled, executing, awaiting approval, success/error/cancelled—with a queue, policy evaluation, confirmation bus, live output updates, and cancellation ([`coreToolScheduler.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/coreToolScheduler.ts)). Multiple model-requested tools in a batch can execute concurrently once validated/approved.

This is sound engineering, but not a second-order orchestration breakthrough. The loop remains model → tools → observations → model, with native lifecycle interception.

### 1.2 What is genuinely different

#### Streaming content-loop detector and one-shot recovery — **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Gemini detects five identical consecutive tool calls (hash of name plus JSON arguments), repeated 50-character output chunks, and—after 30 turns—semantic looping via a utility-model check over 20 recent turns. The semantic check requires 0.9 confidence and, when another model is available, a second model confirmation. On the first detection it injects a “step back and rethink” message; a second detection terminates ([`loopDetectionService.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts); [`client.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/client.ts)).

Our harness already has the stronger detector for the dominant tool-spin case: it hashes tool, normalized arguments, **and result**, warns at three unchanged results, and explicitly treats changed output as progress (`C:\Users\Prekzursil\.claude\hooks\anti-degen\fingerprint.py:2-16`, `:35-37`, `:46-70`). Its recovery verdict also combines repeated tool results with recurring falsifiable failure preconditions and milestone/decision absence (`C:\Users\Prekzursil\.claude\hooks\loop-recovery\verdict.py:2-17`, `:28-39`). Gemini's immediate tool detector can false-positive legitimate identical polling because it does not inspect the result; the local detector was specifically designed around that failure.

The only missing piece is streamed prose “chanting” detection. Claude hooks do not receive partial model tokens at the necessary point, so a faithful port needs a client/runtime modification, hence BUILD-LARGE. **Recommendation: do not port it.** It violates the anti-overfit gate by pushing logic into a second runtime/fork for a low-frequency failure that is not ranked in the corpus. Confidence: very likely (80-90%), because the event schema and local detector source are concrete; the frequency of prose chanting in this owner's history is **UNVERIFIED — settle by mining assistant text for repeated 50-character periods with a known-positive synthetic transcript**.

#### After-agent forced retry — **NATIVE (Claude Code already does this; we just enable it)**

Gemini's `AfterAgent` can reject a proposed stop and force a continuation ([hooks reference](https://geminicli.com/docs/hooks/reference/)). Claude's `Stop` hook already prevents stopping on exit 2, and current Claude also provides prompt/agent hook types and the `/goal` wrapper for evaluator-driven continuation ([Claude hooks](https://code.claude.com/docs/en/hooks), [Claude goal](https://code.claude.com/docs/en/goal)). The local harness already wires Stop and has anti-loop guards. There is no build gap.

Confidence: almost certain (90-99%), from both products' current hook contracts and the local settings' Stop registration.

#### Built-in task DAG/tracker — no gap worth porting

Gemini exposes `write_todos` and an experimental task tracker with epics, tasks, dependencies, statuses, and ASCII visualization; state is session-scoped under `.gemini/tmp/tracker/<session-id>` ([tracker docs](https://geminicli.com/docs/tools/tracker/)). Claude Code has native task tools and agent-team shared task lists; Codex has plan/goal tools. The owner's harness additionally has a durable event ledger and goal reinjection. Gemini's tracker is experimental and explicitly does not persist across sessions, so it is worse than the owner's durable goal/ledger path for long work.

Confidence: very likely (80-90%), based on the tracker docs and local ledger implementation; UI ergonomics were not compared in a live Gemini 0.50 session.

## 2. Context management

### 2.1 Gemini mechanisms

Gemini composes global, workspace/ancestor, and just-in-time subdirectory `GEMINI.md` files; when a tool enters a directory, it discovers relevant local instructions up to a trust boundary. `/memory show` displays the exact concatenated instruction context and `/memory reload` refreshes it. Imports use `@file.md` ([GEMINI.md docs](https://geminicli.com/docs/cli/gemini-md/)).

For long conversations, Gemini automatically compresses history near the context limit, masks bulky older tool outputs, checks request size before sending, and has an experimental `ContextManager`/history provider path. Session recording includes prompts, model output, tool inputs/results, token usage, and reasoning summaries when available; resume, named checkpoints, search, fork-like branch points, retention, and max-turn limits are built in ([session docs](https://geminicli.com/docs/cli/session-management/), [`client.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/client.ts)).

### 2.2 Comparison

There is no material port target here. Claude Code now lazy-loads nested `CLAUDE.md` and path-scoped `.claude/rules/` when matching files are opened, reloads them after compaction when the path is touched again, imports files, shows active memory via `/memory`, shows context allocation via `/context`, clears older tool outputs before summarizing, and re-injects root rules/auto-memory/invoked skill bodies after compaction ([Claude memory](https://code.claude.com/docs/en/memory), [context window](https://code.claude.com/docs/en/context-window), [how Claude works](https://code.claude.com/docs/en/how-claude-code-works)). Local `autoCompactEnabled: true` confirms it is enabled (`C:\Users\Prekzursil\.claude\settings.json:697`).

Claude's MCP Tool Search is arguably better for this owner's oversized tool surface: it defers full MCP schemas and loads them only on demand, while Gemini still registers discovered tool declarations into its registry. Claude also persists oversized tool results to disk and replaces them with references ([Claude MCP](https://code.claude.com/docs/en/mcp)). Given the corpus's 93 touched MCP servers and only 78 used skills out of roughly 355, eager capability text is a real tax; deferred schemas are the correct direction.

Confidence: almost certain (90-99%) for feature parity, supported by the current docs and enabled local setting. Relative token efficiency is likely (55-80%), because no matched trace measured the same tool catalog on both CLIs.

### 2.3 Context features Gemini has but ours does not

#### Session export **and import** — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Gemini 0.43 added session export/import portability ([release notes](https://geminicli.com/docs/changelogs/)). Claude exports and resumes/forks local JSONL sessions but does not document importing a foreign/exported session as a native resumable conversation ([Claude sessions](https://code.claude.com/docs/en/sessions)). A small, safe port would **not** rewrite Claude transcripts. It would be a skill that converts an exported Gemini/Claude session into a bounded Markdown handoff with goal, decisions, open failures, changed files, verification receipts, and source provenance, then starts a fresh session with that file.

Recommendation priority: low. The existing handoff and compaction-checkpoint mechanisms already cover the operational need. Confidence: likely (55-80%); **UNVERIFIED whether native Claude 2.1.214 accepts any undocumented import format — settle with `claude --help`, `/help`, and a disposable exported-session round trip**.

## 3. Memory

### 3.1 Explicit and automatic memory

Gemini routes facts among shared project `GEMINI.md`, private per-project memory, and global `~/.gemini/GEMINI.md`; storage is plain Markdown and the active hierarchy is inspectable ([memory tool](https://geminicli.com/docs/tools/memory/)). Claude Code now has the same broad pattern: checked-in CLAUDE.md/rules plus per-repository auto memory with a bounded `MEMORY.md` index and on-demand topic files ([Claude memory](https://code.claude.com/docs/en/memory)). The owner's canonical cross-tool semantic memory remains Basic Memory on `D:` with a local lexical recall index and sanitized compaction checkpoints (`C:\Users\Prekzursil\.agents\harness\README.md:19-28`). Gemini's Markdown-only memory is simpler but not a replacement for the owner's deliberately cross-provider store.

### 3.2 Review-gated transcript mining — capability gap

#### **UNVERIFIED benefit: Auto Memory inbox — BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Gemini's experimental Auto Memory starts a background extractor at session startup, scans transcripts idle for at least three hours and containing at least ten user messages, locks/throttles per project, and proposes memory patches and new/updated skills into a local inbox. It cannot directly modify active memory or settings; `/memory inbox` lets the user inspect, promote/apply, or discard candidates, and patches are parsed/dry-run/allowlisted before approval ([Auto Memory docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/auto-memory.md)).

The owner lacks this exact retrospective, review-gated mining loop. A faithful port is BUILD-LARGE because it needs a background extractor, transcript index/state/locking, model calls, patch validation, and review UI. It also reintroduces a rejected self-improving runtime unless strictly bounded.

**Do not port the skill-generation half.** SkillsBench v4 evaluated 87 tasks with deterministic verifiers: self-generated skills fell below the no-skill baseline by 8.1 points on Claude Code, 11.3 on Codex, and 11.5 on Gemini CLI, while curated skills improved all three. Its trajectory audit found unused packs, authoring displacing solving, confidently wrong pack content, and instance leakage ([SkillsBench PDF, pp. 6 and 21-22](https://arxiv.org/pdf/2602.12670)). That is direct evidence against autonomous session-to-skill promotion.

A reduced proposal is acceptable: **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for a **memory-only candidate inbox**. Reuse the existing memory spool/event ledger and forge queue; create a command that renders unapplied candidate notes/diffs, requires explicit approval, and never creates skills. No background daemon: mine only when invoked or during an already-authorized research/audit unit. This rides the current buses and passes the anti-overfit gate.

Confidence that review-gated memory diffs would reduce accidental memory pollution: likely (55-80%), because review and target allowlists reduce direct-write risk. **UNVERIFIED whether they improve task outcomes for this owner — settle with a paired 30-session trial measuring accepted-candidate precision, later recall utility, correction rate, and time cost.**

## 4. Tool and MCP handling

### 4.1 Gemini's stack

Gemini's registry combines built-ins, discovery-command tools, MCP tools/resources/prompts, and extension contributions. MCP discovery connects over stdio, SSE, or Streamable HTTP, fetches tools and resources, sanitizes schemas, registers conflicts, and wraps calls with confirmation and timeout state. Resources are available through `@server://resource/path`. It supports OAuth discovery, browser authorization, refresh, token storage, server allow/exclude lists, per-server `includeTools`/`excludeTools`, and strict fully-qualified names `mcp_<server>_<tool>` ([MCP docs](https://geminicli.com/docs/tools/mcp-server/)).

When extension and local MCP settings merge, exclusions are unioned, inclusions intersect, and exclusion wins. This “most restrictive source wins” rule is the best part of Gemini's MCP design.

Claude already provides stdio/HTTP/SSE, resources, OAuth discovery and pinned scopes, namespaced `mcp__server__tool` names, project-server approval, managed allow/deny lists, output limits, plugin-bundled servers, and deferred schema search ([Claude MCP](https://code.claude.com/docs/en/mcp), [Claude settings](https://code.claude.com/docs/en/configuration)). The local profile already refuses blanket project-MCP enablement (`settings.local.json:40-41`). Most of Gemini's mechanism is parity, not a gap.

### 4.2 Measured local failure and what Gemini would change

The corpus records the dead Claude.ai Tavily path as the worst named integration: `mcp__claude_ai_Tavily__tavily_extract` has 532 calls and 137 errors (25.75%), with “MCP server \"claude.ai Tavily\" is not connected” as the dominant fingerprint (`corpus/corpus.json:175-178`, `:4389`, `:9130-9147`). A local Tavily server also exists and is explicitly allowed, so name similarity does not establish that the healthy local server and dead Claude.ai connector are the same endpoint (`C:\Users\Prekzursil\.claude\settings.json:54`; `settings.local.json:46`).

Gemini's `/mcp` status and allowlist would make the dead connection visible, but visibility alone does not stop the model from selecting a disconnected tool. The owner already has a real-handshake liveness hook for **critical** MCPs and a SessionStart preflight (`C:\Users\Prekzursil\.claude\hooks\mcp-liveness\liveness.py:2-32`; `C:\Users\Prekzursil\.claude\hooks\tool-preflight\README.md:1-3`), but its scope is not the full cloud/local MCP catalog. Two independent signals establish the remaining gap: the live code's critical-only scope and the corpus's repeated calls to a disconnected noncritical connector.

#### Disconnected-tool quarantine at discovery — **CONFIG (settings/JSON only)**

Use the existing `enabledMcpjsonServers`/permissions controls to disable the specific dead Claude.ai Tavily tool family and retain the healthy local provider. Do not build another liveness daemon. Add a generated **candidate** config diff from the existing preflight, require review, and only then update the allow/deny list. Confidence: very likely (80-90%) that removing the dead FQN stops this exact 25.8% error family, because the corpus fingerprint names that FQN and Claude permissions match namespaced tools. **UNVERIFIED which current config source owns the Claude.ai connector — settle by `/mcp`, `/permissions`, and one attempted tool call in a disposable session before changing settings.**

Port Gemini's algebra into the canonical config compiler: `effective_include = intersection(all declared includes)`; `effective_exclude = union(all excludes)`; exclude wins; emit server-qualified tool names; refuse ambiguous duplicate aliases. The output remains ordinary Claude/Codex settings, so this is a validator/compiler pass on the existing deploy bus, not a runtime.

Confidence: likely (55-80%) that it reduces accidental capability expansion, based on deterministic set semantics and the owner's large catalog. **UNVERIFIED impact on task success — settle by compiling the current catalog in report-only mode and counting tools removed, collisions found, and historical successful calls that would have been denied.**

## 5. Permission and sandbox model

### 5.1 Gemini

Gemini applies user confirmation to mutating tools, offers default/auto-edit/YOLO/plan modes, supports tool-level sandboxing and per-run sandbox expansion requests, and has a TOML policy engine with `allow`, `deny`, or `ask_user`; tool/MCP matching; stable-JSON `argsPattern`; shell command prefix/regex; interactive/headless predicates; and ordered user/admin tiers ([tools](https://geminicli.com/docs/reference/tools/), [sandbox](https://geminicli.com/docs/cli/sandbox/), [policy engine](https://geminicli.com/docs/reference/policy-engine/)).

Folder trust scans a workspace before loading it and shows discovered commands, MCP servers, hooks, skills, overrides, and dangerous settings. In untrusted mode it ignores workspace settings and `.env`, disables MCP and custom commands, restricts extension management, disables auto-accept, and avoids automatic memory loading ([trusted folders](https://geminicli.com/docs/cli/trusted-folders/)).

### 5.2 Claude parity and local posture

Claude now has a one-time project trust dialog, project MCP approval, permission allow/ask/deny rules, managed settings, plan/auto/dontAsk/bypass modes, OS-enforced sandboxing, dynamic prompts for blocked path/network expansion, symlink-aware path checks, and admin-only restrictions ([permissions](https://code.claude.com/docs/en/permissions), [sandbox](https://code.claude.com/docs/en/sandboxing), [glossary/project trust](https://code.claude.com/docs/en/glossary)). Thus folder trust, plan mode, and sandbox expansion are **NATIVE (Claude Code already does this; we just enable it)**, not build targets.

The owner's actual posture is much weaker than either product's recommended default: `defaultMode` is `bypassPermissions` (`settings.json:71`), while Codex is `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`C:\Users\Prekzursil\.codex\config.toml:6-7`). This is an enablement/configuration problem, not a missing harness feature.

#### Native sandbox and non-bypass default — **NATIVE (Claude Code already does this; we just enable it)**

Enable Claude sandboxing with `failIfUnavailable: true`, change the default permission mode away from bypass, and use explicit path/domain grants. On this native Windows workflow, Claude's documented OS sandbox supports macOS, Linux, and WSL2, not native Windows. Therefore the secure native route is WSL2. **UNVERIFIED compatibility of all owner-specific GUI/reverse-engineering MCPs with a WSL2-hosted Claude session — settle with a disposable WSL2 acceptance run across basic-memory, Git, PowerShell bridge, and one GUI MCP before migration.**

Confidence that sandboxing reduces filesystem/network blast radius: almost certain (90-99%), because enforcement is at the OS boundary. Confidence that switching the entire owner workflow to WSL2 is net-positive: roughly even (45-55%), due to Windows GUI/pipe/path interoperability risk.

#### Generic stable-JSON policy matcher — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Claude permissions are tool-specific; Gemini can apply one stable-JSON regex across arbitrary tool arguments with numeric priority. A small evaluator could run in PreToolUse and compile a narrow TOML/JSON policy file to allow/ask/deny.

**Recommendation: do not copy it generically.** D1 proves this owner's guards already misclassify payload prose, negation, and field names/values (`INPUT-known-harness-defects.md:9-108`). A general regex-over-serialized-JSON engine reproduces the same semantic-role defect. Only port typed matchers that bind explicit fields (tool verb, target path, command AST/prefix) and include known-positive/known-negative tests. Gemini itself warns that its workspace policy tier is currently nonfunctional ([policy engine](https://geminicli.com/docs/reference/policy-engine/)), another reason not to adopt the subsystem wholesale.

Confidence: almost certain (90-99%) that a generic regex matcher would recreate D1's failure class, because both mechanisms inspect serialized payload text without semantic role. Typed field matchers are likely (55-80%) to be safer; **UNVERIFIED until the nine recorded D1 fires and genuine destructive controls are replayed against the candidate evaluator.**
