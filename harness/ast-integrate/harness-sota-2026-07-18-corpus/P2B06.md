# P2B06 — Competitive teardown: Zed

**Unit:** P2B06  
**Date:** 2026-07-18  
**Subject:** Zed's native agent, Agent Panel, ACP integrations, and surrounding control surfaces  
**Comparator:** the installed Claude/Codex/shared harness on this owner’s Windows machine, not an abstract stock Claude Code installation

## Executive verdict

Zed is not a stronger autonomous harness than this one. It is a much cleaner **agent workbench**. Its advantage is that tool selection, approval, sandbox escalation, context, diffs, checkpoints, MCP health, multiple agents, worktrees, and thread history are visible and composable in one editor surface. The installed harness has substantially deeper hooks, durable semantic memory, specialized agents, skills, monitoring, and cross-tool continuity, but it frequently hides those mechanisms behind configuration and prose—and the measured corpus shows that several hidden mechanisms are unreliable.

The highest-value lesson is therefore not “replace Claude Code with Zed.” It is: **make the existing native Claude capabilities real and observable before building more orchestration.** In particular, this installation globally enables `bypassPermissions` and blanket-allows `Bash`, `PowerShell`, `Edit`, `Write`, `Task`, and many MCPs (`C:\Users\Prekzursil\.claude\settings.json:26-71`), disables every listed LSP integration (`settings.json:552-567`), and has no `sandbox` block. Zed exposes safer defaults and better status surfaces for precisely these areas.

The recommendation to keep Claude Code as the execution harness is **very likely (80-90%)** to be better than full replacement. Evidence: Claude already natively supplies checkpoint/rewind, auto-compaction, LSP diagnostics, granular permission parsing, OS sandboxing in WSL2, subagents, worktree isolation, hooks, MCP resources, monitors, and notifications; the installed corpus also records 1,745 `Agent` calls at only 1.15% error, 22 invoked agent types, 78 invoked skills, 93 used MCP servers, and hundreds of successful basic-memory operations (`corpus/corpus.json`, `tool_usage` and `capability_use`). Zed would improve the interface but would remove or fragment several of those harness mechanisms.

The recommendation to adopt a small subset of Zed’s control-plane ideas is **almost certain (90-99%)** to improve this harness. Evidence: the corpus records a dead Tavily MCP still being called 532 times with 135 “not connected” errors, 592 `Glob` failures caused by `ENAMETOOLONG`, and 846/3,694 StructuredOutput failures; Zed directly surfaces MCP running state, tool availability by profile, model/tool incompatibility, and rule decisions. These are visibility and catalog-control remedies aimed at measured failures, not speculative agent scaffolding.

## Method and evidence discipline

I decomposed the teardown into the requested subsystems: agent loop, context, memory, tools/MCP, permissions, customization, multi-agent operation, and verification. Current official Zed documentation and current Zed release notes are the primary sources. Current official Claude Code documentation and the installed configuration are the comparison controls. The pinned corpus is used for incidence and capability-use claims; its `hooks` section is not used because the brief marks that detector broken.

The research provider preflight found no deep-research MCP provider exposed in this Codex session. Official web search was live and was used for all web research. This limits provider diversity, but the central feature claims are taken from first-party Zed and Anthropic pages rather than search snippets or third-party commentary.

Absence claims use two independent signals. For example, the conclusion that Zed lacks a first-party durable semantic memory facility rests on (1) Zed’s exhaustive “What Zed Agent Uses” source-of-truth table, which names models, panel, profiles, permissions, tools, MCP, skills, and instructions but no memory, and (2) the official AI documentation search, whose known-positive control finds Skills and Instructions pages but finds no agent-memory page. This establishes only the documented product surface, not every possible internal cache.

## 1. Agent loop

### What Zed does

Zed’s first-party agent is a conventional model/tool loop embedded in the Agent Panel. A thread binds a model, an Agent Profile, built-in tools, selected MCP tools, Skills, and Instructions. The model reads/searches, edits, invokes terminal or MCP tools, receives results, and continues until it returns a response. The current built-in tools are `diagnostics`, `fetch`, `find_path`, `grep`, `list_directory`, `read_file`, `search_web`, file operation tools, `terminal`, `skill`, and `spawn_agent` ([Tools](https://zed.dev/docs/ai/tools)). Zed explicitly warns in the model selector when a model cannot use tools or cannot represent an MCP server’s tool set ([Agent Panel](https://zed.dev/docs/ai/agent-panel)).

The interaction loop has several useful human-control mechanics:

- Messages sent while generation is active are queued. “Steer” delivers a queued message at the next step boundary, normally between a tool call and the next response; immediate interruption remains available ([Agent Panel, Editing/Queueing](https://zed.dev/docs/ai/agent-panel)).
- Every edit produces a checkpoint at the user-message boundary, even if the thread is interrupted mid-edit ([Agent Panel, Checkpoints](https://zed.dev/docs/ai/agent-panel)).
- The user can follow files as the agent touches them, receive completion/waiting notifications, and review the aggregate diff ([Agent Panel](https://zed.dev/docs/ai/agent-panel)).
- A native `spawn_agent` tool creates a same-toolset subagent with an independent context while the parent continues. Zed added this in stable 0.227.1 in March 2026 ([0.227.1 release](https://zed.dev/releases/stable?b=71); [Tools](https://zed.dev/docs/ai/tools)).

### Comparison

The fundamental loop is parity, not a gap. Claude Code’s `Agent` tool also spawns independent-context subagents, and the installed corpus demonstrates it at scale. Claude can receive user steering and messages from asynchronous agents, has automatic checkpoints and rewind, can monitor background work, and already exposes hook events around the loop.

Zed’s real advantage is legibility. The model/profile/tool combination, tool-call cards, approval state, subagent status, context use, diff, and thread state are visible together. Our loop has more lifecycle instrumentation, but the known-defects report shows that invisible hook verdicts can be wrong and the transcript miner cannot measure them.

### Port decision

**Atomic named thread profiles — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The missing capability is not tool restriction itself; Claude already has permission modes, agent tool lists, `--allowedTools`, `--disallowedTools`, and model selection. The gap is a named, auditable bundle such as `ask`, `write`, `research`, or `reverse-engineering` that selects model, allowed tools, MCP server set, permission mode, and sandbox policy together. Port as a thin PowerShell launcher plus a generated manifest shown at session start. Do not introduce a new runtime. The prediction that this will reduce accidental over-capability is **very likely (80-90%)**, because the current single profile blanket-allows powerful tools while Zed’s Ask and Minimal profiles remove them from model context altogether.

**Queued step-boundary steering — NATIVE (Claude Code already does this; we just enable it).** No new component is warranted. Preserve the product’s native user-steering and async-message path; document it in the launcher/profile help. A custom message bus would violate the anti-overfit gate.

**Zed-style agent-loop UI — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Do not build it. Reproducing the Agent Panel, thread database, diff cards, live tool status, and editor integration is an editor product, not a hook. It would become a second orchestration runtime, one of the explicitly rejected components. If the owner wants this UI, run Claude/Codex as Zed External Agents over ACP rather than cloning it.

## 2. Context management

### What Zed does

Zed combines model-managed search with explicit context selection. `@` mentions can attach files, directories, symbols, old threads, Skills, language-server diagnostics, branch diffs, and URLs. Selected editor or terminal text can be attached with a shortcut; multiline copied code is automatically converted to a file-context mention; images can be attached for vision-capable models ([Agent Panel, Adding Context](https://zed.dev/docs/ai/agent-panel)). This is a strong editor-native affordance: the user can see exactly what was intentionally attached while the agent retains its own search tools.

Zed displays token consumption next to the profile selector. For models with at least an 80,000-token window, it automatically compacts a long thread near the configured threshold, replaces earlier messages with a summary, and inserts an expandable “Context Compacted” entry. `/compact` invokes the same path manually. Below 80,000 tokens, it instead warns and offers “New From Summary”; a new thread may also `@`-mention an old thread ([Agent Panel, Token Usage and Compaction](https://zed.dev/docs/ai/agent-panel)). Automatic compaction shipped in stable 1.7.2 on June 17, 2026 ([stable releases](https://zed.dev/releases/stable)).

Each thread has its own context window and history. Thread History persists, searches, archives, and restores threads. Zed can import supported External Agent sessions into the same history ([Parallel Agents](https://zed.dev/docs/ai/parallel-agents); [External Agents](https://zed.dev/docs/ai/external-agents)).

### Comparison

Claude Code already auto-compacts, supports `/compact`, `/context`, `/clear`, resumable/named/forked sessions, and selective checkpoint summarization. Its rewind menu can “Summarize from here” or “Summarize up to here,” which is more precise than Zed’s documented whole-history compaction ([Claude Code Checkpointing](https://code.claude.com/docs/en/checkpointing); [Sessions](https://code.claude.com/docs/en/sessions)). The shared harness adds sanitized pre-compaction checkpoints and cross-session semantic recall.

Zed is better at showing user-provided context and making diagnostics/diffs/threads attachable with one gesture. Claude is better at semantic continuity beyond a thread. Zed’s “New From Summary” is useful but summary-based continuity can lose falsifiers and provenance; our ledger/basic-memory split is designed specifically to retain objective history separately from semantic memory.

### Port decision

**Automatic and selective compaction — NATIVE (Claude Code already does this; we just enable it).** Keep Claude’s native auto-compaction and rewind summarization. Remove duplicate custom summarization behavior unless it adds redaction or durable checkpointing. This is an anti-overfit simplification, not a new feature.

**Visible compacted-summary audit — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The installed harness writes pre/post-compaction events but does not give the owner a concise, discoverable diff of “what survived.” Extend the existing compaction checkpoint artifact with a bounded summary manifest: active goal, decisions, failures, open loops, and sources, each with origin. The prediction that this will catch lossy compaction is **likely (55-80%)**, based on the present event-ledger design and Zed’s expandable compaction entry; it remains uncertain because the corpus’s hook detector is broken. Verification experiment: compact a synthetic thread containing seeded decisions/failures, then mechanically compare the post-compaction manifest against the seeds.

**Editor-native context palette — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Do not port into the harness. Claude’s IDE integrations and native `@`/LSP facilities should be used; otherwise Zed itself can be the front end. A new context UI would be a second orchestration surface and fail the anti-overfit gate.

## 3. Memory

### What Zed does—and does not do

Zed persists conversation threads and supports user/project Instructions. A user can archive, search, restore, or import thread history, and can seed a new thread from a generated summary or mention a past thread. Those are session persistence and instruction mechanisms, not autonomous durable memory.

I found no documented first-party Zed mechanism equivalent to basic-memory: no semantic note store, proactive cross-project recall, temporal validity/supersession, or objective event ledger. This absence conclusion has two independent signals: the official Zed Agent source-of-truth table enumerates its configuration sources and omits memory ([Zed Agent](https://zed.dev/docs/ai/zed-agent)); and the official AI docs return dedicated pages for Instructions, Skills, MCP, profiles, tools, and threads but no memory facility, while the known-positive searches successfully find those pages. The conclusion is **very likely (80-90%)**, not almost certain, because an undocumented internal implementation could exist. **UNVERIFIED** beyond the documented surface; the settling experiment is to build current Zed from source and trace serialization/restore plus search the source tree for user-facing memory schemas and commands.

### Comparison

This harness is materially ahead. `basic-memory` is canonical cross-tool semantic memory; the event ledger separately records objective milestones/failures. The corpus shows real basic-memory usage and generally low failure rates for its dominant operations. Zed thread history is convenient, but it does not replace curated, supersedable knowledge.

Zed is also less likely to suffer a bad semantic recall, precisely because it does less. Our memory’s downside is complexity and dependency health: the corpus contains “not connected,” lost-response, and no-such-tool failures for basic-memory. That argues for better liveness gating, not for deleting durable memory.

### Port decision

There is no Zed memory capability to port. **Do not replace basic-memory with thread history.** A thread archive is not a semantic memory system, and adding a second store modeled on Zed would directly violate the rejected vector-DB/KG-memory component gate. The best Zed-derived change is presentation only: make the existing ledger/memory provenance visible at compaction and recall time via the small manifest proposal above.

## 4. Tools and MCP handling

### What Zed does

Zed separates tool availability from tool permission:

- Agent Profiles decide which built-in and MCP tools are present in a thread and may bind a default model ([Agent Profiles](https://zed.dev/docs/ai/agent-profiles)).
- Tool Permissions decide whether an available call is allowed, denied, or confirmed ([Tool Permissions](https://zed.dev/docs/ai/tool-permissions)).
- The model selector warns when a model cannot call tools or cannot represent all tools exposed by an MCP server ([Agent Panel](https://zed.dev/docs/ai/agent-panel)).

MCP servers can be installed as Zed extensions or configured as local command servers and remote URL servers. Remote servers without a static Authorization header use standard MCP OAuth. The settings UI displays a status dot and tooltip such as “Server is active.” Zed handles `notifications/tools/list_changed`, automatically refreshing the available tool list when a server changes it at runtime. It supports MCP Tools and Prompts; its docs explicitly invite contributions for broader feature coverage ([MCP](https://zed.dev/docs/ai/mcp)). Zed-configured MCP servers can be forwarded to ACP External Agents.

Zed’s built-in `diagnostics` tool reads language-server errors/warnings at file or project scope. The terminal tool creates a fresh shell process per call. `fetch` is governed by permissions but is outside the OS terminal sandbox. `search_web` is limited to Zed Pro with Zed-hosted models; other users must supply an MCP server ([Tools](https://zed.dev/docs/ai/tools)).

### Comparison

Our raw capability breadth is larger. Claude Code exposes MCP tools plus `ListMcpResourcesTool` and `ReadMcpResourceTool`, whereas Zed currently documents only Tools and Prompts. This harness has touched 93 MCP servers and 400 MCP tools. It also has a tool-search mechanism and specialized MCP routing.

Our lifecycle reliability is worse. The dead `claude.ai Tavily` extractor alone was called 532 times with 135 “not connected” failures; the Tavily search variant failed 139/194 times. A liveness gate exists in the installed hooks, but dead tools still reached the model often enough to dominate the ranking. Zed’s status indicator, per-profile tool exclusion, and list-change refresh make deadness visible and keep capability selection closer to current server state.

Zed is not immune to MCP defects. Its docs say server errors simply flow to the agent and the operation fails. It provides no documented circuit breaker, retry budget, schema relaxation, or provider router. Its MCP protocol coverage is narrower than Claude’s resource support. The current stable changelog also records a recent fix for servers using Zod/Pydantic-generated schemas, evidence that schema interoperability remains an active compatibility surface ([latest stable release](https://zed.dev/releases/stable/latest)).

### Port decision

**Live MCP capability catalog and circuit breaker — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At SessionStart, probe configured servers cheaply, write a timestamped health cache, and emit permission `deny` entries or a tool-selection injection for tools on servers that are down/auth-expired/quota-exhausted. On a definitive “not connected” result, open a bounded circuit for that server; one successful independent probe closes it. `notifications/tools/list_changed` should invalidate the cache where the host exposes it. This rides the existing MCP liveness hook and `mcp-health-cache.json`; it is not a daemon. It is **almost certain (90-99%)** to prevent the exact 135 repeated Tavily extractor failures because the terminal condition is the same error fingerprint. It will not fix schema mismatches.

**MCP status surface — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one `/mcp-health` skill/command that reports active, down, auth-required, quota-exhausted, stale, and circuit-open servers with last probe time and tool count. Use terminal-state markers. This is **very likely (80-90%)** to improve operator decisions because the current defect is repeated use of known-dead endpoints, while Zed makes state visible before prompting.

**UNVERIFIED — Dynamic tool-list refresh — NATIVE (Claude Code already does this; we just enable it) where supported; otherwise BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** First verify Claude’s current MCP client behavior with a synthetic server that emits `notifications/tools/list_changed`. The settling experiment is to add/remove a harmless synthetic tool at runtime and observe `/mcp` plus the model tool catalog without restarting. If native refresh works, delete custom refresh logic. If not, invalidate the existing health/catalog cache and request a session restart rather than hot-patching the runtime.

**Model/tool compatibility warning — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At profile activation, compare declared provider capabilities with required tool schemas and print a warning before the first prompt. Do not transform schemas automatically. This is **likely (55-80%)** to reduce first-message tool failures; evidence is Zed’s warning UI and the corpus’s high StructuredOutput failure rate, but StructuredOutput is not identical to MCP model compatibility. A synthetic matrix of installed models versus representative schemas is the settling experiment.

## 5. Permission model and sandbox

### What Zed does

Zed layers three controls:

1. **Profile availability:** an unavailable tool cannot be selected.
2. **Tool Permissions:** global and per-tool defaults plus case-insensitive Rust regex `always_allow`, `always_confirm`, and `always_deny` rules. Precedence is built-in security, deny, confirm, allow, tool default, global default. For terminal calls Zed parses chained commands and checks subcommands; the settings UI includes a rule tester. MCP permissions are per server/tool, though pattern matching is effectively tool-level because MCP input is matched against an empty string ([Tool Permissions](https://zed.dev/docs/ai/tool-permissions)).
3. **OS sandbox:** terminal commands get filesystem/network enforcement. Project writes are allowed by default except Git metadata; network is denied until a host or all-host grant is approved; broader write or unsandboxed execution can be granted once, for a thread, or persistently. Zed uses Seatbelt on macOS, Bubblewrap on Linux, and Bubblewrap inside WSL on Windows. Native Windows is not sandboxed. Only `terminal` is sandboxed; `fetch`, other tools, Zed, extensions, language servers, External Agents, and Terminal Threads are outside that boundary ([Sandboxing](https://zed.dev/docs/ai/sandboxing)).

Zed hard-blocks a small set of destructive recursive deletions of root/home/current/parent directories. The docs explicitly say there are no other built-in hardcoded rules. Skills from untrusted projects are excluded until project trust is granted, and skill source cannot be edited by the agent without explicit authorization ([Skills](https://zed.dev/docs/ai/skills)).

### Comparison

Current Claude Code’s native permission engine is at least as capable. It separates allow/ask/deny, understands Bash separators, parses the PowerShell AST, canonicalizes PowerShell aliases, checks compound subcommands independently, controls MCP and subagent types, merges policy scopes with deny precedence, and supports workspace trust ([Claude Permissions](https://code.claude.com/docs/en/permissions)). It also has OS sandboxing on macOS/Linux/WSL2 with filesystem and network policy; native Windows is unsupported, just like Zed ([Claude Sandboxing](https://code.claude.com/docs/en/sandboxing)).

The installed configuration defeats most of that native protection: blanket tool allow plus `defaultMode: bypassPermissions` (`settings.json:26-71`). Ad hoc PreToolUse guards then try to reconstruct safety and have confirmed semantic false positives. Zed’s simpler visible layering is better than this deployed state, even though Claude’s underlying native engine is stronger.

Zed’s sandbox is not a full answer for this owner. On Windows it requires WSL; host-specific network grants become all-or-nothing in Zed’s WSL implementation; native reverse-engineering and PowerShell tooling would frequently need escape. Claude has the same native-Windows limitation and additionally cannot invoke Windows executables from inside its WSL2 sandbox unless excluded ([Claude Sandboxing, WSL2 notes](https://code.claude.com/docs/en/sandboxing)).

### Port decision

**Retire blanket bypass as the default — CONFIG (settings/JSON only).** Replace global `bypassPermissions` with normal/auto mode, retain explicit deny rules for credentials and destructive git operations, and move narrowly safe commands into allow rules. Claude’s native parser already handles Bash compound commands and PowerShell AST subcommands. This is **almost certain (90-99%)** to restore meaningful enforcement because current settings explicitly bypass it. Roll out with a one-week shadow log of would-prompt/would-deny decisions before making prompts blocking, because this owner runs many automation-heavy tasks.

**OS sandbox for portable projects — NATIVE (Claude Code already does this; we just enable it).** Enable Claude’s sandbox in WSL2 for repositories whose toolchain is Linux-compatible; set `failIfUnavailable: true` and `allowUnsandboxedCommands: false` only in that profile. Do not enable globally for native Windows reversing/science workloads. It is **very likely (80-90%)** to contain arbitrary shell writes and network access inside compatible projects, based on OS enforcement documented by both products. It is **unlikely (20-45%)** to cover the owner’s entire workload because native Windows binaries cannot run inside the sandbox and many subject tools are Windows-only.

**Permission rule test harness — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Build a pure command that reads the configured rules and evaluates a fixture matrix of safe, dangerous, chained, quoted, PowerShell-alias, and prose-mention inputs using Claude’s documented semantics. It must include known-positive and known-negative controls. This directly addresses D1/D2 and copies Zed’s “Test Your Rules” affordance without another guard framework. It is **very likely (80-90%)** to prevent rule regressions because the recorded failures arose from untested matcher semantics.

## 6. Customization: instructions, skills, hooks, tasks, external agents

### Instructions and skills

Zed uses personal `AGENTS.md` plus the first matching project instruction file from a compatibility list that includes `.rules`, `.cursorrules`, `.windsurfrules`, `.clinerules`, Copilot instructions, `AGENT.md`, `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`. Project instructions override personal instructions ([Instructions](https://zed.dev/docs/ai/instructions)). This broad compatibility is convenient but “first matching file” means multiple policy files are not composed.

Zed’s Skills follow the open `SKILL.md` package shape with optional scripts/references/assets. Skills can be model-invoked or explicitly invoked with `/name` or `@skill`; `disable-model-invocation: true` makes a dangerous workflow manual-only. Zed provides a creator/manager, imports from a GitHub Markdown URL, and shares a self-contained `zed://skill` link that requires review and Save before installation. It live-reloads skill changes. Project skills are trust-gated and cannot be edited by the agent without authorization. Limits include flat roots only, no custom search paths, no runtime remote registry, and a 50 KB total catalog budget; overflow is dropped with a UI warning ([Skills](https://zed.dev/docs/ai/skills)).

Our harness is stronger in skill depth, routing, reference layouts, and cross-tool sharing, but weaker in governance and catalog hygiene. Roughly 355 are installed and only 78 were invoked in the corpus; the orphaned-plugin path explosion is the root cause of Windows process-launch failures. Zed’s hard catalog budget and visible warnings are a useful constraint, while its flat-only skill layout is too limiting for this estate.

### Hooks and tasks

Zed’s native hook equivalent is extremely narrow. Tasks are global or project-local commands with editor variables, rerun/concurrency behavior, and terminal presentation. The only documented automatic Task hook is `create_worktree`, which runs after a linked worktree is created ([Tasks](https://zed.dev/docs/tasks)).

Our harness is far ahead: PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Pre/PostCompact, ConfigChange, SubagentStart/Stop, Task lifecycle, Session lifecycle, Stop, WorktreeCreate/Remove, and more are wired. The problem is correctness and telemetry, not missing hook points. Replacing this with Zed Tasks would lose essential enforcement and continuity.

### External agents and ACP

Zed has three agent paths: native Zed Agent, ACP External Agents, and terminal-backed threads. The ACP Registry installs Claude, Codex, OpenCode, Copilot, Cursor, Pi, and others. Zed hosts their thread UI, while the external process generally owns auth, models, native tools, Skills, Instructions, MCP, and permissions. Zed may forward its MCP servers over ACP, can import supported external sessions, and exposes ACP logs ([Agents](https://zed.dev/docs/ai/agents); [External Agents](https://zed.dev/docs/ai/external-agents); [ACP Registry](https://zed.dev/blog/acp-registry)).

This is excellent interoperability but not policy unification. Zed explicitly warns that profiles and Skills do not automatically apply to External Agents or Terminal Threads. A user can see everything in one sidebar while still having three independent security/configuration domains.

### Port decision

**Skill catalog budget, trust, and overflow report — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a deterministic catalog compiler that counts description bytes, reports dropped/shadowed/duplicate skills, validates one known-present control, and emits a small active catalog per profile. Do not delete orphan directories automatically; the pinned evidence proves some orphan-marked directories are live and 110/169 plugins lack live siblings. This is **very likely (80-90%)** to reduce prompt/catalog bloat and discovery ambiguity; it is only **likely (55-80%)** to reduce `os error 206`/ENAMETOOLONG because process argv composition, not catalog tokens alone, is the immediate cause. The settling experiment is an argv-length measurement before and after catalog generation.

**Manual-only dangerous Skills — CONFIG (settings/JSON only).** Adopt the `disable-model-invocation` convention where supported and enforce equivalent `Skill(name)` permission asks for deploy/release/destructive workflows. Claude natively supports Skill permission rules. This is **very likely (80-90%)** to prevent unintended autonomous invocation because the tool is removed from autonomous selection or forced through an approval boundary.

**Self-contained skill share links — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus), but low priority.** A signed local bundle/manifest with hashes and an explicit review/install command would reproduce the safety property without a URL protocol handler. It is **unlikely (20-45%)** to materially improve harness reliability; the owner’s bottleneck is catalog quality and dead plugins, not sharing UX. Defer until catalog hygiene is solved.

**Broader Zed-style hook replacement — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Reject. Zed has fewer hooks, not better hooks. Fix the shared discriminator and telemetry on the existing hook bus.

**ACP registry/orchestrator inside the harness — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Reject as a port. It would be a second orchestration runtime. Zed can be used optionally as the existing ACP presentation client without making it canonical. Zed’s explicit configuration boundaries mean it cannot replace the shared cross-tool behavior contract.

## 7. Multi-agent support

### What Zed does

Zed has two distinct forms of parallelism:

1. The model may call `spawn_agent`; each subagent receives its own context window and the same tools as the parent. The parent continues and later reviews the result ([Tools](https://zed.dev/docs/ai/tools)).
2. The human may run multiple independent Zed Agent, External Agent, or Terminal threads from the Threads Sidebar. Each has independent context/history and may target a different project. Potentially conflicting edits can be isolated in linked Git worktrees. Zed creates new worktrees detached, exposes setup through `create_worktree`, and on archival can save Git state, remove the worktree from disk, and restore it with the thread later ([Parallel Agents](https://zed.dev/docs/ai/parallel-agents)).

The latter is Zed’s standout design: it treats parallel work as inspectable threads rather than an opaque fan-out. Status, agent type, project, history, and worktree are visible. It does not, however, document a dependency DAG, typed handoff contract, shared task board, conflict arbitration protocol, or parent-enforced file ownership for native `spawn_agent`.

### Comparison

Our harness has functional parity and more orchestration semantics: custom agent types, structured handoff rules, subagent lifecycle hooks, file-scope enforcement, worktree isolation, task status, and cross-agent messaging. The corpus proves substantial successful use. Zed is better at operator visibility and thread/worktree cleanup. Our known defect D4—an orchestrator-fabricated constraint propagated to ~15 agents—also shows that stronger orchestration can amplify false premises. Zed’s independent threads reduce that particular propagation path, but do not solve premise verification.

### Port decision

**Native subagents and worktree isolation — NATIVE (Claude Code already does this; we just enable it).** Keep Claude’s Agent tool and `isolation: worktree`; the installed configuration already registers subagent and worktree lifecycle. Do not create another dispatcher.

**Parallel-thread/worktree status board — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing background registry/status line to show task, agent type, project, worktree, state, last terminal marker, and age. Data must come from lifecycle events; no polling daemon. It is **very likely (80-90%)** to improve supervision because Zed’s advantage is visibility and the corpus contains TaskStop failures such as unknown/stale task IDs. It is **likely (55-80%)** to reduce those failures if IDs are taken from the registry rather than memory; verify with a synthetic spawn/wait/stop matrix.

**Archive-and-rehydrate worktrees — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus), conditional.** Persist a manifest and Git status/branch pointers before cleanup; restore only from validated explicit paths. Do not serialize untracked secrets. This is **roughly even (45-55%)** in value because current Claude worktrees already clean themselves and the owner has not supplied measured worktree-loss incidence. Build only if a corpus query finds repeated manual recovery or disk-bloat evidence.

## 8. Verification and self-check

### What Zed provides

Zed has four verification-adjacent mechanisms:

- `diagnostics` gives current language-server errors/warnings for a file or the whole project ([Tools](https://zed.dev/docs/ai/tools)).
- Agent edits appear in an aggregate multi-buffer diff; the user can accept/reject each hunk or all changes. Optional single-file review overlays the hunk controls inline ([Agent Panel, Reviewing Changes](https://zed.dev/docs/ai/agent-panel)).
- Per-message checkpoints allow rollback after a bad edit, including interrupted edits ([Agent Panel, Checkpoints](https://zed.dev/docs/ai/agent-panel)).
- Tool permission patterns have an interactive rule tester ([Tool Permissions](https://zed.dev/docs/ai/tool-permissions)).

These are not an autonomous completion proof. Zed’s terminal documentation merely gives `cargo test` and `git diff --stat` as examples; it does not document a mandatory test-after-edit policy, post-edit hook, acceptance contract, or independent critic. The conclusion that Zed lacks a built-in mandatory verifier is **very likely (80-90%)**, based on two signals: the exhaustive built-in tool list contains diagnostics/terminal but no verifier, and the only documented Task hook is `create_worktree`. **UNVERIFIED** against runtime behavior; the settling experiment is a controlled edit that introduces a compiler error and observes whether Zed automatically invokes diagnostics/tests before declaring completion.

### Comparison

Claude’s current LSP tool automatically reports type errors/warnings after each edit and can navigate symbols, but all listed language LSP plugins are disabled here (`settings.json:552-567`). The installed harness also has a PostToolUse per-edit validator (`settings.json:333-342`) and Stop-time checks. Those are more automatic than Zed’s UI, but D1 shows that some validators misclassify prose/data and D3 says hook effectiveness is not measurable.

Claude’s native checkpoints are also stronger than Zed’s documented checkpoint UI: checkpoint rewind can independently restore code, conversation, both, or summarize either side of a selected message, and can fork instead of destructively rewriting history ([Claude Checkpointing](https://code.claude.com/docs/en/checkpointing)). Zed has a historically reported irreversible checkpoint-restore issue, so its rollback UX should not be copied without branching/undo; the current docs do not promise a post-restore undo.

### Port decision

**Enable native LSP diagnostics — NATIVE (Claude Code already does this; we just enable it).** Activate language-specific code-intelligence plugins for the owner’s actual high-use languages, beginning with a small pilot. Claude’s LSP automatically reports errors after edits ([Claude Tools Reference](https://code.claude.com/docs/en/tools-reference)); all corresponding installed toggles are currently false. This is **very likely (80-90%)** to catch type/syntax regressions earlier. Measure added latency and false/stale diagnostics per language before broad rollout.

**Human hunk-review UI — BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Do not build. Use the owner’s IDE/git diff or Zed as an ACP front end. A diff review GUI does not belong in the harness.

**Checkpointing — NATIVE (Claude Code already does this; we just enable it).** Prefer native `/rewind` over duplicate edit snapshot hooks for direct Edit/Write operations. Retain a custom snapshot only where it covers shell-mediated changes that native checkpoints explicitly do not track. The simplification is **very likely (80-90%)** to reduce hook complexity because native checkpoints persist with sessions and offer more restore modes. Verify coverage with one Edit mutation and one shell mutation before removing any hook.

**Mandatory evidence-before-done contract — CONFIG (settings/JSON only), not copied from Zed.** Preserve our stronger rule that completion claims need relevant diagnostics/tests/diff evidence, but route it through trustworthy terminal outputs and LSP rather than prose-scanning Stop hooks. This is **very likely (80-90%)** to outperform Zed’s optional review-only approach because it checks execution, not just edit shape. The D1 shared-discriminator regression suite is a prerequisite for any remaining automatic guard.

## Where Zed is worse—and what not to copy

### 1. No durable semantic memory

Zed’s thread persistence, summaries, and Instructions are not equivalent to a cross-tool semantic store plus objective event ledger. Do not downscope basic-memory to chat history. Zed’s simpler system reduces recall risk but loses durable, structured continuity.

### 2. Hook surface is drastically weaker

Only `create_worktree` is documented as an automatic Task hook. There is no Zed equivalent to our PreToolUse, PermissionRequest, PostToolUseFailure, Pre/PostCompact, Subagent lifecycle, ConfigChange, or Stop hooks. Our implementation is defective in places, but Zed’s answer is omission rather than a better hook model.

### 3. MCP coverage is narrower

Zed documents Tools and Prompts, not Resources, Sampling, or Elicitation. Claude already exposes MCP resources. Zed’s status and OAuth UX are worth copying; its protocol ceiling is not.

### 4. Permission patterns are less expressive for MCP inputs

Zed’s MCP pattern rules match an empty input, so practical control is per server/tool default. Claude can match MCP tool names and supports richer top-level input-parameter gating for tools. Do not flatten our permissions to Zed’s MCP model.

### 5. Sandboxing has broad exclusions and Windows limits

Only Zed Agent’s terminal tool is sandboxed; `fetch`, extensions, language servers, ACP agents, and terminal threads are outside it. Native Windows is unsupported. The UI is excellent, but the security boundary must not be overstated.

### 6. Parallel agents are visible but weakly coordinated

Zed provides independent threads and same-toolset subagents, not a typed task graph, shared acceptance contract, file ownership protocol, or premise-challenge mechanism. Our structured handoffs and file scopes remain valuable after their defects are fixed.

### 7. Skill layout is too restrictive

Flat direct-child skills, no custom search paths, and a 50 KB catalog cap are excellent hygiene constraints for a normal user but cannot directly host this owner’s large hierarchical capability estate. Copy the budget and warnings, not the topology.

### 8. First-matching instruction file can hide policy

Zed uses only the first match among multiple compatibility filenames. This avoids conflicting instruction piles but can silently ignore a lower-priority file. Our authoritative cross-tool contract is explicit; do not replace it with compatibility precedence.

### 9. Verification is optional and user-facing, not completion-enforcing

Diagnostics, diffs, checkpoints, and a rule tester help humans catch errors, but Zed does not document automatic tests or an evidence-required completion gate. Keep our stronger verification objective while simplifying its unreliable detectors.

### 10. ACP unifies display, not governance

External agents retain their own auth, model, tools, instructions, skills, MCP, and permissions. Zed’s sidebar can create an illusion of one harness while policy remains fragmented. Do not treat ACP presentation as a replacement for the shared behavior contract.
