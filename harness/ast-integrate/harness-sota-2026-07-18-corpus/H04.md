# H04 — Admitting mistakes cleanly: correction that adds information, not apology that spends a turn

## Executive verdict

The harness should treat a mistake admission as a **correction transaction**, not as a social preamble. The compact human-facing form is:

> **I got X wrong.** External signal Y establishes Z. This affects A (and does not affect B). I have corrected C; receipt D verifies the repair. Thread E remains open and is next.

The regret clause is useful when the agent created real owner cost, but it is not the payload. “Sorry” alone changes no belief, repairs no artifact, bounds no blast radius, and preserves no thread. The transaction above does all four. This conclusion is **very likely (80-90%)**, based on (a) a human-agent experiment in which regret plus explanation repaired trust better than either alone, while explanation alone did not repair trust, (b) repeated-violation evidence that communicative strategies do not restore perceived ability, and (c) this workspace’s executable-receipt and correction-first evidence ([Kox et al. 2021](https://link.springer.com/article/10.1007/s10458-021-09515-9); [Esterwood & Robert 2023](https://www.sciencedirect.com/science/article/pii/S0747563223000092); `claude/rules/common/fan-out-contract.md:41-43`; `agents/harness/ledger.py:98-121`).

This is not a proposal for another agent runtime, memory store, critic, observability product, or guardrail framework. Every mechanism below rides the existing response/rule, dispatcher, event-ledger, typed-receipt, truth-verify, calibrated-silence, and OPEN-THREADS buses. It adds **zero hooks**. Where runtime code is useful, it is folded into an existing consumer; therefore the approximately-six-hook ceiling is untouched. All runtime paths must catch their own exceptions and return/exit successfully: correction guidance may disappear on infrastructure failure, but work must never be blocked by a broken communication aid.

## Grounding and evidence boundary

The supplied corpus is a 10.62 GB, 11,633-file distillation with zero failed files, one malformed line, and 32 oversized lines; it explicitly says samples are capped (`inputs/corpus.json:2-13`). Its owner-correction field contains 8,441 owner messages and 2,268 candidates, but its own precision warning says a smoke sample was **41/41 false positives**, mostly agent-authored prompts (`inputs/corpus.json:10371-10374`). Consequently, I do not use 2,268 as a count of genuine corrections.

The distilled artifact preserves several high-information owner corrections:

* “nope still doesnt work, try again, **no resets**, it worked very well before” changes the recovery constraint and supplies a prior working-state fact (`inputs/corpus.json:11219`).
* “no it doesnt work properly [it] **copies only 1 file not 2** … the clipboard problem hasn’t been solved” supplies an observable postcondition and preserves a second open defect (`inputs/corpus.json:11447`).
* “why did you stop? **ralph loop shouldn’t allow you to do that**, make sure you properly executed it” identifies both the visible failure and the violated persistence mechanism (`inputs/corpus.json:12251`).
* “no wrong, **I’m in galactic view**” is short but information-dense: it replaces the agent’s false UI-state anchor (`inputs/corpus.json:10573`).

The contrast class is also real, but it is a **low-information correction trigger**, not a verified assistant apology: “why did you stop proceed until you finish everything” says the terminal state is wrong but does not identify which assumption or artifact failed (`inputs/corpus.json:10425-10426`). That same normalized stop feedback appears 12 times, while a more specific “do it … and do not stop” stop-loop pattern appears 524 times (`inputs/corpus.json:10375-10379`, `:10421-10426`). These repetitions establish owner effort and loop persistence; they do not establish what the assistant said between prompts.

**UNVERIFIED:** the raw-transcript corpus contains real assistant-authored examples of apology-only replies that waste a turn. The supplied `corpus.json` does not retain assistant prose: session rows contain only file/kind/size/timestamps, and correction samples contain owner text/file/time/after-tool-use. I validated the text detector against the known-present third-party Firecrawl string “We apologize…” (`inputs/corpus.json:9737`), then used both `rg` and an independent recursive JSON-string scan; neither found an assistant apology. The settling experiment is to run a role-aware join on the Windows raw JSONL: select genuine owner correction turns, extract the immediately preceding and following assistant text plus tool receipts, and have two independent labelers classify `apology-only`, `informational-unverified`, and `externally-verified correction`. Until that experiment, I will not fabricate a negative example. The strongest positive local behavioral example available is aggregate but measured: **4/4 correcting fan-out agents led their capped digest with the correction** (`claude/rules/common/fan-out-contract.md:41-43`).

## Inferred-surprise findings (lead set)

### Finding 1 — Make a correction invalidate its descendants, not merely replace one sentence

**improvement / NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a `correction` event adapter to the existing ledger API. A correction carries `wrong_ref`, `corrected_claim`, `external_signal_ref`, `affected_seqs`, `unaffected_threads`, and `receipt_seq`. The surprise is that the socially clean sentence is downstream of a data-integrity operation: before speaking, invalidate conclusions derived from the wrong premise.

**what it is.** The current ledger already has typed receipts and claim families (`agents/harness/ledger.py:88-121`), and `taint_dependents()` already finds `derived_from` dependents and writes a fail-open taint marker (`agents/harness/ledger.py:1186-1215`). Do not build a new graph. Add a thin orchestration function that accepts an **external falsification**—owner correction, failing execution result, independent tool disagreement, or fresh-context verifier result—then calls the existing one-level taint function transitively with a bounded queue. Render the affected/unaffected summary into the correction transaction.

**why-inferred.** The owner’s “copies only 1 file not 2” correction also says the clipboard defect remains unresolved (`inputs/corpus.json:11447`): they are not merely asking for the local sentence to change; they need the agent to understand which downstream claims are now unsafe while not dropping the parallel clipboard thread. The live D4 incident shows the cost of failing to invalidate descendants: one fabricated constraint propagated into roughly 15 prompts and routed writes onto a 13.6%-failure path (`inputs/INPUT-known-harness-defects.md:151-160`).

**how-to-build.** Extend `note.py` with `--kind correction --wrong-ref --signal-ref --corrected --receipt-seq`; its current CLI already writes decisions, failures, milestones, and supersession (`claude/hooks/event-ledger/note.py:2-12`, `:25-42`). In the ledger module, traverse at most 200 events, cap depth, deduplicate sequence numbers, and write one correction event plus existing taint markers. Render at most three affected items inline and put the rest behind a count/path to avoid prompt fatigue. Wrap parsing, traversal, append, and rendering in `try/except`; return an empty advisory on error. This folds into the existing ledger/dispatcher path and adds no hook.

**the EXTERNAL signal that verifies it.** Unit fixture: create claim A from a tool receipt, claims B/C `derived_from=A`, and unrelated thread D. Inject a second-tool result that falsifies A. Assert the ledger externally contains a correction event, B/C taint markers, D remains open, and the rendered response names A→B/C plus D. End-to-end replay the fabricated Write-constraint incident: the independent Write-tool success/error record must taint every prompt-derived claim that cites the false constraint. Same-context prose review is not acceptance evidence.

**SOTA citation with URL.** Repeated trust violations are not repaired by words alone: apologies, explanations, and promises did not restore ability or integrity perceptions after repeated failures ([Esterwood & Robert 2023](https://www.sciencedirect.com/science/article/pii/S0747563223000092)). This supports making demonstrated correction and blast-radius control the competence signal.

**value x effort.** **transformative x medium.** It is **very likely (80-90%)** to prevent a corrected premise from continuing to poison later work because the existing provenance and taint operations already encode the necessary relation; the remaining uncertainty is how consistently current events populate `derived_from` (`agents/harness/ledger.py:1186-1203`).

**novelty.** inferred-surprise.

**autonomy.** just-do-it; it is advisory, bounded, reversible, and fail-open.

### Finding 2 — Use the repair receipt as the competence-bearing part of the apology

**improvement / NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Add a response-contract rule: an agent may say “corrected”, “fixed”, or “now works” only after a fresh external receipt; otherwise it must say “the corrected hypothesis is …; verification is pending” and keep the thread open.

**what it is.** Separate three states that fluent language currently blurs: `ADMITTED` (the old claim is false), `REPAIRED` (a change was made), and `VERIFIED` (an independent execution/postcondition passed after the change). The visible correction packet includes the strongest achieved state and the receipt, never a promise that substitutes for it.

**why-inferred.** The owner repeatedly reports behavioral postconditions, not hurt feelings: one file copied instead of two (`inputs/corpus.json:11447`), a loop stopped when it should persist (`inputs/corpus.json:12251`), and a previously working path still fails without resets (`inputs/corpus.json:11219`). The harness already recognizes executable receipt classes—test, build, lint, typecheck, coverage, run, e2e, health—and maps “fixed” to test/run (`agents/harness/ledger.py:98-121`). The missing partner behavior is to expose that state cleanly in the response.

**how-to-build.** Amend the common communication rule and fan-out preamble with a five-line renderer specification: `wrong claim`, `external contradiction`, `scope`, `action`, `receipt/open status`. Reuse `has_fresh_receipt()` and the existing `fixed -> (test, run)` mapping; do not add a checker. High-stakes factual corrections use a mechanically different source/tool/second model or owner confirmation rather than a same-context re-read. If no valid receipt class exists, report the exact external experiment still required. Limit normal repairs to three sentences; expand only for blast radius or owner harm.

**the EXTERNAL signal that verifies it.** A fixture matrix feeds responses paired with ledger state: no receipt, stale receipt before mutation, fresh failing receipt, fresh passing receipt. Only the last may render `VERIFIED`. A second integration test mutates after a green test and confirms the earlier receipt becomes stale. The current local rule independently requires receipt plus postcondition for DONE (`claude/rules/common/single-signal-verification.md:20-37`).

**SOTA citation with URL.** Kox et al.’s human-agent experiment found the strongest trust recovery from regret plus information, while explanation without regret did not repair trust ([Kox et al. 2021](https://link.springer.com/article/10.1007/s10458-021-09515-9)). The receipt is stronger than a self-authored explanation because it is an execution result outside the speaking context.

**value x effort.** **high x low.** It is **almost certain (90-99%)** to prevent unsupported “fixed” language when the renderer consults the already-recorded receipt, because the state transition is deterministic; evidence is the explicit receipt map and freshness API (`agents/harness/ledger.py:109-121`, `:1178-1184`).

**novelty.** inferred-surprise.

**autonomy.** just-do-it.

### Finding 3 — Preserve the untouched threads explicitly during a correction splice

**improvement / NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing OPEN-THREADS/event-ledger integration so a correction updates one thread and emits a compact “still open” tail for every sibling commitment that could otherwise be displaced.

**what it is.** A correction is a splice, not a reset. Its record has `replaces`, `affected`, `unchanged`, and `next`. The human-facing response ends with one continuity clause: “Clipboard remains open; next after copy-path verification.” It does not dump the whole backlog into the prompt.

**why-inferred.** The owner’s copy-path correction explicitly carries two threads in one sentence—the one-file/two-file defect and the still-unsolved clipboard defect (`inputs/corpus.json:11447`). Their “no resets” instruction similarly says the recovery must preserve existing state (`inputs/corpus.json:11219`). A design that responds deeply to the corrected item while forgetting its sibling would satisfy local error repair and violate the owner’s stronger continuity need.

**how-to-build.** On externally triggered correction, load the current goal/open-thread snapshot through the existing ledger/OPEN-THREADS reader; attach the wrong thread’s stable ID to the correction event; leave siblings unchanged; render only (a) the corrected thread, (b) any tainted dependents, and (c) the highest-priority untouched sibling. If correction work spans compaction, session-start replay restores the event rather than regenerating it. Do not introduce a second task manager or memory store. Fail open: if the thread file cannot be parsed, continue the repair and state “continuity ledger unavailable” only in debug telemetry, not as an owner interruption.

**the EXTERNAL signal that verifies it.** Before/after snapshot test on a fixture containing threads A/B/C: correct A; compare stable IDs and hashes to prove B/C survived; compact/replay in a fresh process and verify A’s replacement plus B/C. Then simulate an owner follow-up about B; the recalled thread must point to the pre-correction B record, not a self-generated summary. A file snapshot and a separate fresh-process replay are mechanically independent signals.

**SOTA citation with URL.** Microsoft’s validated human-AI guidelines include supporting efficient correction and learning from user behavior across time; the 18 guidelines were evaluated with 49 practitioners against 20 products ([Amershi et al. 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**value x effort.** **transformative x medium.** It is **likely (55-80%)** to reduce discussed-then-forgotten stress because it mechanically preserves sibling IDs and makes one sibling visible; the causal effect on stress remains uncertain until owner follow-up rates are compared in an A/B shadow run. Evidence for the need is the owner’s multi-thread correction at `inputs/corpus.json:11447`.

**novelty.** inferred-surprise.

**autonomy.** just-do-it for the ledger splice; confirm-first only if the correction changes priority among unaffected threads.

### Finding 4 — After the same mistake twice, the admission must name the changed tactic

**improvement / NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Amend the existing two-strikes pivot so the second correction packet must include `repeated fingerprint`, `discarded tactic`, and `new externally testable tactic`. An additional apology is optional; repeating the same approach is forbidden.

**what it is.** First occurrence: “I got X wrong; here is the corrected result and receipt.” Recurrence: “This is the same fingerprint as attempt 1. The prior tactic Y is discarded. I am switching to Z; signal Q will decide it.” The pattern prevents apology language from laundering an unchanged retry.

**why-inferred.** A normalized “do it … and do not stop” stop-feedback loop appears 524 times (`inputs/corpus.json:10375-10379`), and “why did you stop…” appears repeatedly (`inputs/corpus.json:10421-10426`). Those counts include hook feedback and are not 524 independent owner judgments, but they establish a real repeated loop. The harness already says that two consecutive failures on one fingerprint require alternatives or escalation (`claude/AGENTS.md:51-57`); the communication layer should reveal the pivot rather than emit fresh-sounding remorse around the same attempt.

**how-to-build.** Add three required fields to the response rule when the event ledger reports the same failed fingerprint twice. Reuse existing error fingerprints and terminal `FAILED:<id>` markers (`claude/AGENTS.md:36-39`, `:51-57`). No runtime or hook is added. The new tactic’s settling signal must be a different tool, different measurement, execution outcome, second model, or owner decision. A third attempt without a changed tactic must escalate, not self-review.

**the EXTERNAL signal that verifies it.** Replay a fixture with two identical failed fingerprints and inspect the third tool call: its normalized approach signature must differ, and an external result must accept/refute it. Negative control: two failures with different fingerprints must not trigger the pivot text. Acceptance is based on tool-call signature plus tool result, not the agent’s claim that it pivoted.

**SOTA citation with URL.** In repeated human-robot violations, none of apology, explanation, promise, or denial fully restored overall trustworthiness/ability/integrity; denial was consistently least effective ([Esterwood & Robert 2023](https://www.sciencedirect.com/science/article/pii/S0747563223000092)). Changed behavior is therefore the necessary competence evidence after recurrence.

**value x effort.** **high x low.** It is **very likely (80-90%)** to reduce apology-wrapped retry loops because the current fingerprint trigger and pivot rule already exist; the change makes their consequence explicit in the next action (`claude/AGENTS.md:51-57`).

**novelty.** inferred-surprise.

**autonomy.** just-do-it; confirm-first only when every alternative materially expands scope or risk.

### Finding 6 — Deliver correction at the next natural breakpoint, except when continued action compounds harm

**improvement / NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Add timing policy to the response contract: queue a non-compounding correction for the next tool/result boundary; interrupt immediately only if the false premise is about to cause another mutation, unsafe action, or owner decision.

**what it is.** This is not concealment. The correction is mandatory; only delivery timing varies. `IMMEDIATE` applies before a dependent mutation or irreversible decision. `NEXT_BOUNDARY` applies while an independent long tool is already running or the owner is in a focused flow. The queued item is written to the existing event ledger/open-thread state first, so it cannot be forgotten.

**why-inferred.** Prompt fatigue is a hard constraint, while “never drop a thread” forbids silent deferral. The owner’s corpus contains focus-restoring prompts such as “now? why would I want it later” (`inputs/corpus.json:11285`) and stop-loop corrections (`inputs/corpus.json:10425-10426`), implying that mistimed or deferred communication itself can become work. A durable queue plus breakpoint delivery satisfies both pressures.

**how-to-build.** Add two enum values and a deterministic rule table to the communication rule; do not add a scheduler. Before any deferral, append the correction event with `deliver=next_boundary`. Existing PostToolUse/Stop response assembly consumes it at the next terminal tool result. If ledger append fails, fail open by delivering immediately. Never defer owner-authored corrections, safety-relevant corrections, or anything with tainted downstream mutations.

**the EXTERNAL signal that verifies it.** Instrument timestamps around tool start/result and correction delivery. In a replay suite, inject contradictions during (a) a read-only long operation and (b) immediately before a write. Assert boundary delivery for (a), pre-write delivery for (b), and durable survival across process restart. Then measure owner interruption/dismissal in shadow mode through the existing reaction logger. Tool boundaries, mutation ordering, and next-turn owner behavior are external signals.

**SOTA citation with URL.** A three-week field study modeled opportune work transitions and users rated recommendations 86%/77% accurate for transitions/breaks, supporting delivery at task breakpoints rather than arbitrary moments ([Kaur et al., CHI 2020](https://www.microsoft.com/en-us/research/publication/optimizing-for-happiness-and-productivity-modeling-opportune-moments-for-transitions-and-breaks-at-work/)).

**value x effort.** **medium x low.** It is **likely (55-80%)** to reduce interruption cost while preserving corrections, based on breakpoint-timing evidence and the durable-before-defer rule; transfer from workplace recommendations to coding-agent corrections is imperfect, so shadow measurement is required.

**novelty.** inferred-surprise.

**autonomy.** just-do-it in shadow mode; confirm-first before active deferral.

### Finding 7 — Standardize the “delta-first correction packet”; ban apology-only turns

**improvement / NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Install one compact communication pattern in the common response rules and every fan-out prompt that can speak to the owner:

1. **Delta:** “I got `<specific claim/action>` wrong.”
2. **Ground:** “`<external signal>` establishes `<corrected truth>`.”
3. **Scope:** “Affected: `<items>`; unaffected/open: `<threads>`.”
4. **Repair:** “I `<action already taken>`; `<receipt>` verifies it.”
5. **Continuation:** “Next: `<preserved next thread/action>`.”

Optional, only after owner cost: “I’m sorry—I made you `<repeat/re-check/lose work>`.” It must share a turn with the delta and repair; it never stands alone.

**what it is.** The pattern makes an admission human without making it theatrical. It names responsibility, teaches the corrected model, exposes uncertainty/blast radius, demonstrates changed behavior, and maintains continuity. If repair is not yet verified, line 4 becomes “Verification pending: `<external experiment>`”; no false closure.

**why-inferred.** The owner asks for the difference explicitly. Local evidence shows correction-first prioritization is compatible with tight communication: all four correcting fan-out agents led with the correction under a 350/400-word cap (`claude/rules/common/fan-out-contract.md:41-43`). The corpus’s strongest owner corrections themselves follow delta-plus-information: UI state (`inputs/corpus.json:10573`), observable copy cardinality plus an open sibling defect (`:11447`), and recovery constraints (`:11219`).

**how-to-build.** Add this 5-field template to the common communication rule and frozen fan-out preamble. Include two tests in the rule’s fixture suite: (a) apology-only and apology+promise are rejected as nonterminal; (b) delta+external signal+scope+receipt+next passes. Keep the normal renderer to at most 70 words; exceptions are safety incidents and multi-claim blast radii. The template must be explicit in each fan-out prompt because measured prompt elements predict compliance while global inheritance failed (`claude/rules/common/fan-out-contract.md:3-15`). No hook is added.

**the EXTERNAL signal that verifies it.** On a held-out set of real correction episodes, a deterministic schema checker validates field presence, then a separate tool/ledger join validates every cited signal and receipt. Success metric: lower owner re-correction within two turns and no increase in owner words spent. A same-context model rating “good apology” is explicitly inadmissible.

**SOTA citation with URL.** Kox et al. experimentally separated regret and explanation and found their combination most effective in the tested human-agent task ([Kox et al. 2021](https://link.springer.com/article/10.1007/s10458-021-09515-9)). Microsoft’s validated guideline set says systems should support efficient correction when wrong ([Amershi et al. 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**value x effort.** **high x low.** It is **very likely (80-90%)** to make correction turns more informative because the required fields are directly observable and the local 4/4 sample shows agents prioritize corrections under a cap; whether the owner prefers the optional regret clause in practice is UNVERIFIED and is settled by the reaction experiment in Finding 5.

## Alternatives considered and rejected

* **A seventh “apology checker” hook:** rejected. It breaches the hook ceiling, scans prose (the exact class already known to false-fire), and can only judge form, not whether a correction is true. The live defect record shows three prose/payload scanners confusing mention with use and causing 8+ false fires (`inputs/INPUT-known-harness-defects.md:95-107`).
* **A second orchestration runtime or durable correction service:** rejected by the anti-overfit gate. The existing ledger has receipts, provenance taint, supersession, and fail-open semantics; the missing work is a thin adapter and renderer (`agents/harness/ledger.py:88-121`, `:1186-1215`; `claude/hooks/event-ledger/note.py:2-12`).
* **A same-model “reflect before replying” critic:** rejected by construction under this unit’s law. It can improve prose while preserving the wrong anchor. Every acceptance path above terminates in an owner event, independent tool/result, fresh process/context, second model, or durable state comparison.
* **Always-long explanations:** rejected for prompt fatigue and because always-on supporting explanations worsened decision accuracy in one condition in the 2026 trust-adaptation study ([Srinivasan & Thomason](https://arxiv.org/abs/2502.13321)).
* **Always terse “you’re right” corrections:** rejected because they hide blast radius, receipt status, and preserved threads. The local fabricated-constraint incident demonstrates that a one-line false premise can propagate into roughly 15 prompts (`inputs/INPUT-known-harness-defects.md:151-160`).
