# T018 — Competitive teardown: Bolt.new

**Research date:** 2026-07-19 UTC  
**Unit scope:** Bolt.new only: agent loop, context, memory, tools/MCP, permissions, customisation, multi-agent, verification/self-check, and concrete ports into the owner's Claude/Codex harness.  
**Subject-write policy:** read-only. I wrote only this artifact.

## Executive verdict

Bolt.new is not a better general agent harness than the owner's system. It is a sharply narrower, much more productised agent appliance: one hosted coding agent, one browser-contained JavaScript development environment, an app preview, an editor, a terminal, deployment, and a small set of highly legible controls. Its strongest ideas are not frontier orchestration ideas. They are **control-plane ergonomics** around an intentionally constrained loop:

1. the preview or a code selection can be turned directly into context;
2. a user can visibly target or lock files;
3. persistent instructions have explicit account, team, project, and package-conditioned scopes;
4. MCP servers and individual MCP tools have visible enable/disable state;
5. execution occurs in a browser sandbox rather than on the owner's machine;
6. each change has a previewable, restorable history;
7. Plan mode is a first-class read-only state with a deliberate “Implement plan” transition.

Those are real advantages in discoverability and boundedness. The owner's harness is dramatically stronger in cross-domain reach, native filesystem/tool coverage, hooks, programmable skills, explicit verification commands, durable semantic memory, and multi-agent execution. The owner's local evidence shows those strengths also create its main liability: excessive and unreliable surface area. The corpus records a dead Tavily MCP still being called, over-strict structured-output failures, and a catastrophically inflated plugin path; the live-defect input records false-positive guards and missing hook telemetry. Bolt's small, visible control plane is therefore worth copying selectively, while Bolt's narrow runtime, shallow documented verification, manual context hygiene, and single-agent serialization are not.

**Bottom line:** preserve our existing Claude/Codex buses. Do not replace them with Bolt or a Bolt-like second runtime. Port five small control mechanisms—ephemeral scope locks, connector/tool activation state, hierarchical knowledge routing, read-only-plan enforcement, and a preview-to-evidence adapter—onto the existing hook/skill/MCP bus. This is **very likely (80-90%)** to improve reliability without overfitting, because each port reduces the active surface or makes intent mechanically explicit, and each maps to an existing bus already evidenced in `/local_disk0/codexwork/bundle/claude/settings.json:81-150`, `/local_disk0/codexwork/bundle/codex/config.toml:77-130`, and `/local_disk0/codexwork/bundle/agents/harness/README.md:1-29`.

## 1. Agent loop

### What Bolt exposes now

Bolt presents two current agents, **Standard** and **Max**, while hiding specific model selection behind the product. Standard is the fast/token-efficient default for well-defined work; Max spends more reasoning on large codebases, interconnected features, refactors, and open-ended tasks. Agent choice persists per project, and a default can be set for new projects. Source: [Choose an agent](https://support.bolt.new/building/using-bolt/agents).

The externally visible loop has two operator states:

1. **Plan Mode** reads the project and recent messages, can inspect the codebase and search the web, and is intended not to change code.
2. It emits a plan/explanation and contextual quick actions such as **Implement this plan**.
3. The user crosses an explicit boundary into **Build Mode**.
4. Build Mode changes files, installs packages, runs the app in the integrated environment, and shows the preview.
5. Errors may surface an **Attempt fix** action; users are warned not to repeat it blindly.
6. The user verifies through preview/build output or restores a prior version.

Sources: [Plan Mode](https://support.bolt.new/best-practices/discussion-mode), [token-efficiency guidance](https://support.bolt.new/best-practices/maximizing-token-efficiency), and [troubleshooting](https://support.bolt.new/troubleshooting/issues).

The public v1 source shows why Bolt felt coherent even before these newer controls. The server supplied one fixed system prompt, streamed one model response, and explicitly set `toolChoice: 'none'`; instead of model-native tool calls, the model emitted `<boltArtifact>` / `<boltAction>` markup. A streaming parser recognized `file` and `shell` actions, and a single `ActionRunner` serialised them through a promise chain. File actions wrote complete files; shell actions spawned `jsh -c` in a WebContainer. Long responses hitting the token ceiling were continued by appending the partial assistant response plus a synthetic “continue” user message. Evidence: [v1 chat route](https://github.com/stackblitz/bolt.new/blob/eda10b121221b30825a4c16eec5da1fd3eb1eb99/app/routes/api.chat.ts), [v1 stream setup](https://github.com/stackblitz/bolt.new/blob/eda10b121221b30825a4c16eec5da1fd3eb1eb99/app/lib/.server/llm/stream-text.ts), [v1 action runner](https://github.com/stackblitz/bolt.new/blob/eda10b121221b30825a4c16eec5da1fd3eb1eb99/app/lib/runtime/action-runner.ts), and [v1 system/action protocol](https://github.com/stackblitz/bolt.new/blob/eda10b121221b30825a4c16eec5da1fd3eb1eb99/app/lib/.server/llm/prompts.ts).

That historical loop is not ReAct in the broad tool-using sense. It is closer to **plan once in the model response, emit an ordered transaction, execute it serially, then let the next user turn carry feedback**. Current Standard/Max may be more iterative internally, but that is **UNVERIFIED; an authorised trace of one successful build and one failing build would settle whether tool results are fed back within the same turn**.

### Better than ours

Bolt's strongest loop feature is the explicit Plan→Implement state transition. Our Codex has plan mode and the local harness has commands, but Claude's settings grant broad edit/shell rights with `defaultMode: "bypassPermissions"` (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`), and Codex is configured `approval_policy = "never"`, `sandbox_mode = "danger-full-access"` (`/local_disk0/codexwork/bundle/codex/config.toml:6-8`). Bolt's mode is visible and comprehensible to a non-expert.

### Worse than ours

- Bolt does not expose a programmable task loop, custom agent types, model routing policy, lifecycle hooks, or a subagent graph. Our Codex config explicitly enables multi-agent, fan-out, hooks, goals, memories, and eight concurrent threads (`/local_disk0/codexwork/bundle/codex/config.toml:77-130`).
- Bolt's environment is deliberately web-centric. The public system prompt documents no native binaries, no C/C++ compiler, limited Python, and historically no Git inside WebContainers. That is excellent containment and poor generality. Our owner routinely uses reverse engineering, scientific tooling, Windows automation, notebooks, and native binaries.
- The v1 full-file action protocol was token-expensive and overwrote whole files. The current mechanism is **UNVERIFIED; the settling experiment is an authorised edit trace comparing wire payload size with changed-line count**.
- Bolt's own guidance tells users to split work into one change at a time, copy console errors into chat, and avoid repeated auto-fix attempts. That is honest, but it shows the loop is not a robust autonomous verifier. [Troubleshooting](https://support.bolt.new/troubleshooting/issues).

### Port decision

#### **CONFIG — enforce an explicit read-only Plan state**

Map Plan state to existing native plan modes and permissions: no Edit/Write/apply_patch/shell mutation while plan is active; a single explicit user action or command transitions to execution. Preserve web/search/read tools. This is **very likely (80-90%)** to reduce accidental mutation because Bolt's current product demonstrates the understandable state boundary, while our local settings show mutation is presently broadly pre-authorised. This is settings/policy work, not a second runtime.

Do not copy v1's XML-ish action language or build another action executor. Our native tool protocols already return typed results, and the corpus shows StructuredOutput is already the second-worst major surface at 22.9% error. Adding another bespoke schema would compound the measured problem.

## 2. Context management

### Bolt's mechanisms

Bolt defines context as project files, chat history, user prompts, and uploaded files—even uploads not stored in the project. Current agents have large windows but limit active history to recent messages. Earlier details must be restated or placed in persistent Knowledge. `/clear` discards conversational working memory while retaining access to the codebase. Source: [Manage project context](https://support.bolt.new/best-practices/manage-context).

Context can be focused through several concrete controls:

- `@` tags attach a file or folder to a prompt.
- **Select** in Preview targets a rendered UI element; **Pick from layers** disambiguates nested elements.
- In Code View, **Target file** focuses Bolt, **Lock file/Lock all** excludes a file/directory from changes, and highlighted source can be sent via **Ask Bolt**.
- `agents.md` is automatically discovered as an instruction entry point and may reference additional files.
- Current Bolt agents no longer support the legacy `.bolt/ignore`; context exclusion moved to UI locking/targeting.

Sources: [Chat tools](https://support.bolt.new/building/chat-tools), [Code View](https://support.bolt.new/building/using-bolt/code-view), and [Manage context](https://support.bolt.new/best-practices/manage-context).

This is a direct-manipulation context model: the human can point to the rendered object, source span, file, or directory instead of describing it in prose. That is Bolt's clearest advantage over a terminal-first harness.

Bolt's context management is otherwise manual and blunt. The docs recommend shorter prompts as projects grow, proactive `/clear`, deleting unused Markdown, removing unused files, splitting files around 500–700 lines, and restating old details. The troubleshooting guide even recommends maintaining a README and asking Bolt to reread it after a clear. These are workarounds, not automatic semantic context selection.

### Better than ours

The owner's harness has sophisticated context machinery, but no single, universally visible “these files are targeted; these files are locked” state. The local system does have a PreToolUse file-scope ownership guard (`/local_disk0/codexwork/bundle/claude/settings.json:218-225`) and a large skill router, yet the user's intent is inferred through hooks rather than represented as a small editable set. Bolt's control is simpler to inspect and challenge.

Preview element/layer selection is also materially better for UI work. Our harness has Playwright and image/visual skills, but those are separate capabilities, not a direct element→source→prompt interaction.

### Worse than ours

- Bolt's current-history truncation has no documented summary/checkpoint contract. The owner has sanitized PreCompact checkpoints and bounded recall in the shared lifecycle (`/local_disk0/codexwork/bundle/agents/harness/README.md:17-29`).
- Bolt makes the user manage context by deletion and repeated `/clear`; our system can retrieve prior work from Basic Memory and proactively inject bounded recall (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13`).
- Bolt's file-size heuristics are language-agnostic. A 700-line generated file and a 700-line handwritten god object are not equivalent.
- Connector data is said to be “added to context,” but the docs do not expose token estimates, selection rationale, provenance per retrieved item, or a context manifest. Exact connector-context loading is **UNVERIFIED; the settling experiment is to enable one MCP with two tools and compare an authorised request trace and token meter before/after**.

### Ports

#### **BUILD-SMALL — add an ephemeral scope manifest (<~200 lines)**

Add a per-session JSON or TOML record with `target`, `allow_edit`, and `deny_edit` path sets. A UserPromptSubmit hook injects the short manifest; the existing PreToolUse file-scope hook enforces only edit denial. Commands such as `/scope target src/auth`, `/scope lock migrations`, `/scope clear` update it atomically. The state must be printed in the status line and expire with the session unless promoted into project rules.

This is **very likely (80-90%)** to port Bolt's useful mechanism without its UI because `/local_disk0/codexwork/bundle/claude/settings.json:117-150` and `:218-225` prove the needed prompt and pretool hook points already exist. It rides the existing bus and does not require a daemon.

#### **BUILD-SMALL — preview/DOM selection adapter (<~200 lines plus existing browser tool)**

Have the existing browser/Playwright surface return a compact selection capsule: URL, stable selector, accessible role/name, bounding box, nearest source-map location when available, and screenshot crop. Attach that capsule to the next prompt and optionally translate source-map hits into the scope manifest. This is **likely (55-80%)** to improve UI edit precision, based on Bolt's first-class element/layer control and our existing Playwright MCP allow-list at `/local_disk0/codexwork/bundle/claude/settings.json:60`. Source-map availability across the owner's projects is **UNVERIFIED; the settling experiment is a five-project spike measuring selector-to-source resolution accuracy**. The recommendation does not depend on source maps because role/selector/screenshot remain useful.

Do not port “delete Markdown to save context” as an automated policy. The owner's durable instructions and evidence artifacts often are Markdown; automatic deletion would repeat the harness's existing use-vs-mention mistakes documented in `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-82`.

## 3. Memory and persistent knowledge

### Bolt's memory hierarchy

Bolt distinguishes recent conversational context from persistent **Knowledge**:

- **Account Knowledge:** instructions across all personal projects.
- **Project Knowledge:** goals, style, terminology, constraints, and workflow habits for one project.
- **Team Knowledge:** shared context for all team projects.
- **Packages Knowledge:** team-admin instructions keyed to an exact package name; Bolt applies them whenever that package appears in `package.json`.
- **`agents.md`:** repository-resident entry point automatically found by the agent, able to link to other files.
- **Design-system knowledge:** a design document plus a Project Knowledge rule can force reference to it on new UI work.

Sources: [Account settings](https://support.bolt.new/settings/account-settings), [Project settings](https://support.bolt.new/settings/project-settings), [Workspace settings](https://support.bolt.new/settings/workspace-settings), [context guide](https://support.bolt.new/best-practices/manage-context), and [design-system best practices](https://support.bolt.new/building/design-system/best-practices).

This is persistent instruction memory, not episodic or semantic autobiographical memory. There is no documented embedding search, entity store, temporal validity, contradiction handling, memory approval queue, or learned user preference extraction.

### Better than ours

Package-conditioned instructions are unusually concrete and low-noise: exact `package.json` membership is the trigger, not semantic guesswork. The owner has path-scoped rules and a skill router, but the local evidence does not show an equally simple package-name→instruction registry. Two independent local signals support that narrow gap: a controlled `rg` found known-present `skill-router` and `AGENTS.md` machinery but no `Packages Knowledge`/package-keyed instruction registry; the shared lifecycle's fixed module list contains bounded recall but no package-conditioned module (`/local_disk0/codexwork/bundle/agents/harness/README.md:17-27`).

Bolt also makes memory scope legible to non-experts. Our memory is more capable but spread across `CLAUDE.md`, `AGENTS.md`, skills, hooks, Basic Memory, compaction checkpoints, and recall injectors.

### Worse than ours

The owner has durable semantic Markdown memory with proactive recall after compaction, supersession metadata, and a local lexical fallback (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13`; `/local_disk0/codexwork/bundle/agents/harness/README.md:21-29`). Bolt documents only persistent instructions. For long-running research, reverse engineering, or cross-project operational knowledge, Bolt is substantially weaker.

Bolt's knowledge precedence and conflict resolution are **UNVERIFIED; the settling experiment is an authorised project with contradictory account, team, project, package, and `agents.md` instructions, then observe which wins**. Do not copy a hierarchy without explicit precedence.

### Port

#### **BUILD-SMALL — package-conditioned knowledge router (<~200 lines)**

Add a declarative registry mapping exact ecosystem coordinates to short instruction files: npm package names initially, later Python distributions, .NET packages, Cargo crates, and toolchain markers. On SessionStart or manifest change, detect exact dependencies and inject only matching snippets, with source path and precedence shown. The first version should be exact-match only; no embedding model or vector store.

This is **very likely (80-90%)** to reduce irrelevant skill injection because Bolt's exact package trigger is mechanically narrow and the owner already has a skill/context injection bus. It passes the anti-overfit gate: it is a deterministic lookup riding existing hooks, not a new memory runtime.

Keep Basic Memory. Replacing it with Bolt-style Knowledge would discard temporal, episodic, and cross-project recall for a simpler instruction box.

## 4. Tool and MCP handling

### Bolt's current mechanism

Bolt provides built-in connectors and custom remote MCP servers. A custom connection records name, URL, HTTP or SSE transport, and authentication (`API key`, MCP OAuth, or none). Credentials are verified at setup; connected/offline state is visible. Each connector can be auto-enabled for new projects or toggled per project. Individual tools can be disabled globally for that connector—e.g. keep create/read, disable delete. A refresh re-discovers tools and can confirm whether an offline server recovered. Source: [Connect to an MCP server](https://support.bolt.new/building/using-bolt/connect-mcp).

Important limitations:

- The documented custom transport is remote HTTP/SSE, not local stdio.
- Tool enablement is connector-global; tools cannot be varied per project.
- All tools default on when a connector is first added.
- Connector data increases context and token use; Bolt explicitly recommends enabling only what the current project needs.
- Only the project owner can connect MCP servers or prompt Bolt to use them; collaborators cannot. [Collaboration](https://support.bolt.new/building/using-bolt/collaborate).

### Better than ours

Bolt's activation UX directly addresses our worst measured MCP defect. The pinned corpus records `claude_ai_Tavily` at 532 calls and 25.8% error, including 135 “not connected” calls. Our settings statically allow Tavily and many other MCPs (`/local_disk0/codexwork/bundle/claude/settings.json:47-60`) and broad MCP pretool dispatch (`:139-150`). Bolt's visible Connected/Offline state, refresh, per-project connector toggle, and per-tool disabling are exactly the control plane a 93-server harness needs.

The local hook bundle contains a claimed “MCP health check” hook, but the measured dead-Tavily calls prove that the installed system did not reliably prevent this failure class. I do not infer whether the hook was disabled, bypassed, or miswired; hook telemetry is explicitly unmeasurable in `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:133-147`.

### Worse than ours

- Remote HTTP/SSE only is inadequate for the owner's many local stdio and native-tool servers.
- Default-all-tools-on is poor least privilege.
- Connector-global tool policy is too coarse for a project portfolio.
- Bolt documents no latency/error-rate routing, circuit breaker threshold, fallback provider, result schema validation, or tool-call provenance ledger.
- Bolt's connector context warning is manual rather than an automatic context budget.

### Ports

#### **BUILD-SMALL — MCP activation registry and circuit breaker (<~200 lines for first slice)**

Put every server/tool in one generated registry with `enabled`, `scope`, `health`, `last_success`, `consecutive_failures`, and `cooldown_until`. Tool discovery exposes only active tools where the provider permits it; otherwise PreToolUse blocks known-offline calls with one compact alternative. Three transport failures inside a bounded window should open the circuit; one explicit health probe after cooldown may close it. A `/mcp status|enable|disable|refresh` command is the operator surface.

This is **almost certain (90-99%)** to eliminate repeated calls to a deterministically disconnected server because the defect is measured and the mechanism prevents selection/call rather than merely warning after failure. Threshold quality is **UNVERIFIED; replaying the corpus's 5,692 error fingerprints through candidate thresholds settles false-open and missed-open rates**. The proposal rides the current MCP/tool-search/pretool bus and needs no daemon.

#### **CONFIG — default new MCP tools off pending review**

Invert Bolt's weakest default: newly discovered tools enter `pending`, display their descriptions and destructive verbs, and require explicit approval before entering the active set. This is **very likely (80-90%)** to reduce surprise capability and context inflation, based on Bolt's own warning that more tools slow output and increase tokens plus our installed-versus-used ratio (78 of roughly 355 skills invoked). It is configuration/state, not a guardrail framework.

Do not replace local stdio MCP with Bolt-style remote-only connectors. That would remove native and offline capability while adding network and authentication failure modes.

## 5. Permission and security model

### Bolt's layers

Bolt's most important security property is architectural: project code executes in StackBlitz WebContainers inside the browser security sandbox, not as arbitrary local binaries. StackBlitz says code execution occurs inside the browser sandbox and cannot break out to the local machine. [Introducing WebContainers](https://blog.stackblitz.com/posts/introducing-webcontainers/). The historical Bolt prompt explicitly constrained the agent to browser-compatible JavaScript/WebAssembly, limited Python, and no native compilation. [v1 system prompt](https://github.com/stackblitz/bolt.new/blob/eda10b121221b30825a4c16eec5da1fd3eb1eb99/app/lib/.server/llm/prompts.ts).

Other permission layers are:

- **File scope:** Target and Lock controls guide or forbid edits in Code View.
- **MCP least capability:** connector tools can be individually disabled.
- **Human RBAC:** Viewer, Editor, and Co-owner roles govern code visibility, prompting/editing, environment-variable visibility, invitations, and publishing.
- **Ownership boundaries:** only the owner connects GitHub/MCP; collaborator GitHub changes do not sync until the owner returns.
- **Database security:** a Security Audit identifies missing/insecure RLS and other warnings and provides “Ask Bolt to fix.”
- **Secrets UI:** database/project secrets are managed outside ordinary source; Viewers cannot see environment variables.

Sources: [Code View](https://support.bolt.new/building/using-bolt/code-view), [MCP](https://support.bolt.new/building/using-bolt/connect-mcp), [sharing roles](https://support.bolt.new/building/using-bolt/sharing), [collaboration](https://support.bolt.new/building/using-bolt/collaborate), and [database security](https://support.bolt.new/cloud/database/security).

### Better than ours

The browser sandbox gives Bolt an intrinsically smaller blast radius. The owner's Claude configuration allows Bash, Read/Edit/Write and broad drive access, defaults to bypass permissions, and adds `C:` and `D:` (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`). Codex is danger-full-access with no approvals (`/local_disk0/codexwork/bundle/codex/config.toml:6-8`). Our guard layer is more expressive, but live defects show four detectors confusing mention with use and sometimes instructing the agent to discard successful results (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-82`). Architectural isolation beats a regex guard for untrusted web-app execution.

Bolt's explicit Viewer/Editor/Co-owner model is also clearer for human collaboration than a local single-owner harness.

### Worse than ours

- WebContainer confinement obtains safety by excluding most native workloads. It cannot replace the owner's Windows/native harness.
- Bolt docs do not expose per-command approval, command allow/deny patterns, write-root restrictions, network egress policy, or hookable policy decisions.
- File Lock appears to constrain the agent editor, not necessarily every terminal command or MCP side effect. Enforcement breadth is **UNVERIFIED; an authorised test should lock a file, then ask the agent to overwrite it via shell and via a connector**.
- Editors can view environment variables. That is a broad collaboration trust grant, not fine-grained secret brokerage.
- Database “Ask Bolt to fix” is a convenience action, not proof that generated RLS is semantically correct.

### Port decision

#### **NATIVE — use existing native sandbox/approval modes by risk tier**

Enable workspace-write or read-only sandboxes and approvals for untrusted repositories, dependency-install experiments, downloaded code, and web-generated projects; reserve danger-full-access for explicit native tasks. This is **very likely (80-90%)** to reduce host risk because Bolt demonstrates the value of construction-level containment and our config proves native sandbox/approval features exist even though the current defaults disable them (`/local_disk0/codexwork/bundle/codex/config.toml:6-8`, `:95-99`).

Do not build a WebContainer clone. That would be a second execution runtime—explicitly rejected by the anti-overfit gate—and would still not support the owner's native work.

## 7. Multi-agent support

It deliberately processes one prompt at a time; others cannot submit while Bolt is working. Only one agent selection (Standard or Max) is active for the project. This is not multi-agent execution. No current public docs describe subagents, parallel tasks, isolated worktrees, delegation, agent-to-agent messages, independent critics, or result synthesis. The public v1 source likewise has one chat stream and one serial action chain. Current hidden orchestration remains **UNVERIFIED; an authorised trace or vendor disclosure would settle it**.

This is **very likely (80-90%)** to preserve throughput while preventing the class Bolt avoids, because the local harness already has a file-scope ownership guard (`/local_disk0/codexwork/bundle/claude/settings.json:218-225`) and documented file leases (`/local_disk0/codexwork/bundle/claude/CLAUDE.md:44-47`).

Do not copy Bolt's global single-prompt queue. Do not add a second orchestrator, durable-execution engine, or agent daemon.

## 8. Verification and self-check

### Bolt's verification surfaces

Bolt provides several useful but uneven checks:

1. **Live preview:** the app is built automatically after edits and rendered beside chat/code.
2. **Build/runtime output:** the Bolt/Terminal/Publish Output panes expose errors; docs recommend `npm run build` to reveal compile failures.
3. **Automatic error action:** detected errors can offer **Attempt fix**, but docs warn against repeating it.
4. **Plan diagnosis:** users can ask Plan Mode to inspect code and propose a fix before applying it.
5. **Version history:** automatic versions can be previewed, renamed, bookmarked, restored, or selected from chat; backups can be forked.
6. **GitHub:** Bolt automatically commits changes that do not break the project and polls GitHub every 30 seconds. It does not merge branches in-app, and rare concurrent updates may overwrite the GitHub version. [GitHub integration](https://support.bolt.new/integrations/git).
7. **Database audit/logs:** the Security tab flags issues such as permissive RLS, mutable search paths, and leaked-password protection; logs expose auth, PostgreSQL, storage, server function, PostgREST, realtime, and other events.

Sources: [troubleshooting](https://support.bolt.new/troubleshooting/issues), [version history](https://support.bolt.new/building/using-bolt/rollback-backup), [GitHub](https://support.bolt.new/integrations/git), [database security](https://support.bolt.new/cloud/database/security), and [database logs](https://support.bolt.new/cloud/database/logs).

### Better than ours

Bolt's version timeline is excellent recovery UX: preview before restore, bookmark known-good points, and restore without spending model tokens. Our harness has stronger mechanics—automatic edit checkpoints and `/rollback` instructions—but they are command/file based. Local evidence: `/local_disk0/codexwork/bundle/claude/commands/rollback.md:1-43` describes per-turn snapshots and preview-before-restore; `/local_disk0/codexwork/bundle/claude/commands/checkpoint.md:9-50` defines named verification checkpoints. Bolt wins presentation, not underlying capability.

The integrated preview and security/log panels also shorten the loop for the narrow web/database domain.

### Worse than ours

- Bolt does not document an invariant that tests, typecheck, lint, security scan, or browser assertions must run before claiming completion.
- Its own troubleshooting asks users to copy browser-console or terminal errors back into chat. The agent is not always observing its own runtime.
- `Attempt fix` can loop and consumes tokens; Bolt explicitly tells users to stop retrying.
- A rendered preview is not a functional test. It does not prove accessibility, data integrity, authorization, or edge cases.
- Database auto-fixes are not independent verification.

Our `/verify` command explicitly orders build, types, lint, tests, coverage, console-log audit, and git status and produces PASS/FAIL (`/local_disk0/codexwork/bundle/claude/commands/verify.md:1-51`). `/quality-gate` detects tooling and runs formatter/lint/type checks (`/local_disk0/codexwork/bundle/claude/commands/quality-gate.md:1-22`). Post-edit hooks also claim format/type/quality checks. Our problem is reliability and observability, not absence.

### Port decisions

#### **NATIVE — surface existing edit checkpoints as a compact timeline**

Use the existing checkpoint index and native UI/artifact rendering to list turn, files, verification status, and preview diff; retain the current explicit user confirmation before restore. This is **likely (55-80%)** to improve recovery use because Bolt shows the value of preview/bookmark UX and our checkpoint data already exists. Native artifact/UI support availability across both Claude and Codex is **UNVERIFIED; a one-session rendering spike settles it**. If unavailable, keep `/rollback`; do not build a web dashboard.

#### **BUILD-SMALL — evidence capsule after web-app edits (<~200 lines, rides existing browser/quality bus)**

After a web-app edit, collect only existing signals: build exit, type/lint/test summary, preview URL, console errors, one screenshot, and changed files. Inject the capsule into the agent's next reasoning step and require claims to cite it. This is **very likely (80-90%)** to outperform Bolt's preview-only loop because our native `/verify` already specifies the checks and Bolt shows the ergonomic value of colocated preview/errors. Do not add an observability SaaS or trained critic.

#### **CONFIG — cap automatic repair attempts at two per fingerprint**

Hash normalized error class plus command/tool and changed scope. After two materially identical failures, stop auto-repair and switch to diagnosis/Plan mode with the evidence capsule. This is **almost certain (90-99%)** to prevent blind retry loops by construction, and Bolt's own documentation independently recommends no repeated Attempt-fix clicking. Use the existing anti-degeneration/loop-recovery bus; do not create durable execution infrastructure.

## Final synthesis

Bolt.new's core lesson is not “use WebContainers” or “build a no-code web IDE.” It is that a strong model benefits from a **small, visible, reversible control plane**. Bolt makes focus, mode, connector state, knowledge scope, preview, and rollback tangible. The owner's harness has better primitives and much wider reach, but those primitives are hidden behind hundreds of capabilities and fallible detectors.

The ambitious move is therefore not replacement. It is a selective control-plane inversion: keep the powerful Claude/Codex runtime, but make the active subset explicit and tiny per task. Only the selected files, selected tools, selected knowledge, selected writer, and selected evidence should enter the loop. That design is **very likely (80-90%)** to capture Bolt's advantage while avoiding its severe domain and concurrency limits, because it directly addresses the owner's measured dead-tool, context, retry, and guard-reliability failures without adding any prohibited architecture.
