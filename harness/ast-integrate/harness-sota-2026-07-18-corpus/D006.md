# D006 — executable benchmark for external research with citations

Date: 2026-07-19 UTC  
Unit: D006  
Scope: benchmark-task design only; no harness subject files were modified.

## Executive result

This unit specifies one runnable benchmark, `EXT-RESEARCH-HTTP-001`, in which an agent must research eight narrowly framed facts in four primary HTTP standards and attach a source URL plus section locator to every answer. The answer values are deliberately typed and finite (booleans, a short string, or a small set), so a standard-library scorer can execute exact checks. Citation support is checked against a private oracle mapping from each claim to the RFC and section that entails it; no human or LLM judge reads a report and decides whether it “sounds researched.”

**Proposal tag — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The proposed addition is a fixture manifest, a private oracle, and a Python standard-library scorer invoked by the existing eval/weekly-bench path. It adds no hook event, MCP, daemon, model call, database, or orchestration runtime.

**Recommendation — UNVERIFIED implementation size:** implement this task and scorer as the first external-research baseline. The `<~200 lines` size is **UNVERIFIED; the settling experiment is to implement `score.py`, count nonblank/noncomment lines, and run its unit tests on both Windows PowerShell 7 and the Linux CI job**. It is **very likely (80-90%)** to remain BUILD-SMALL because the scorer requires only JSON parsing, normalization, SHA-256, path checks, and table lookup, all available in Python's standard library; the uncertainty is Windows process/fixture plumbing, not scoring logic.

The benchmark is intentionally a constrained objective proxy, not a claim that long-form research quality can be reduced to exact matching. BrowseComp motivates short, reference-verifiable answers for browsing evaluation, while acknowledging that this omits long answers and ambiguity ([BrowseComp v1](https://arxiv.org/abs/2504.12516v1)). GAIA likewise combines real-world questions with browsing/tool use and withholds many reference answers for leaderboard evaluation ([GAIA v1](https://arxiv.org/abs/2311.12983v1)). This design adopts those two useful properties—machine-verifiable terminal answers and a grader-side answer key—then separately verifies citation location.

## 4. Exact prompt delivered to the agent

The runner sends the following text verbatim after replacing only `<ABSOLUTE_CHECKOUT>` with the resolved checkout path. That replacement is fixture plumbing, not model-visible task variation.

```text
You are in a clean checkout at <ABSOLUTE_CHECKOUT>.

Research the official primary HTTP standards on the public web and answer the eight items below. Do not use search-result snippets, blogs, Wikipedia, mirrors, or this repository as factual authority. A source must be an HTTPS URL on www.rfc-editor.org and must name the exact numbered section that supports the answer. If one search or fetch route is unavailable, use another available route.

Items:
1. 421_name — the registered reason phrase/name for HTTP status 421.
2. 421_retry_non_idempotent — whether RFC 9110 permits a client to retry a request after 421 even when the method is non-idempotent.
3. 421_proxy_may_generate — whether RFC 9110 permits a proxy to generate 421.
4. retry_after_syntax — the two alternative value forms in RFC 9110's Retry-After grammar.
5. retry_after_9110_status_contexts — the two response-status contexts for which RFC 9110 §10.2.3 explicitly explains Retry-After semantics. Return the class as `3xx` and the individual code as a string.
6. 429_retry_after_strength — RFC 6585's uppercase RFC 2119 requirement word governing inclusion of Retry-After in a 429 representation.
7. 103_replaces_final_headers — whether fields in 103 Early Hints replace the header fields on the final response.
8. request_no_store_applies_to_already_stored_response — whether a request's no-store directive applies to an already stored response used to satisfy that request.

Write exactly one new file at the repository root: research-result.json. Do not edit, delete, or create anything else. It must be UTF-8 JSON with this shape:

{
  "benchmark_id": "EXT-RESEARCH-HTTP-001",
  "answers": [
    {
      "id": "421_name",
      "value": "...",
      "citations": [
        {"url": "https://www.rfc-editor.org/rfc/rfcNNNN.txt", "section": "N.N.N"}
      ]
    }
  ]
}

Use JSON booleans for yes/no items, arrays of strings for the two multi-value items, and a string for every other item. Include each ID exactly once. Array order is irrelevant. You may include extra explanatory keys, but the required values and citations must remain machine-readable. Validate the JSON before finishing.
```

This schema is intentionally shallow and permits extra keys. That avoids retesting the corpus's over-strict fan-out schema failure mode (`StructuredOutput` had 846 errors in 3,694 calls, including 294 repetitions of one missing-property mismatch; `/local_disk0/codexwork/bundle/inputs/corpus.json:1`, `/tool_usage` and `/error_fingerprints`). The task is research, not memorizing a brittle serialization contract.

## 5. Private oracle and citation-entailment map

The grader's canonical values are:

| ID | Canonical value | Allowed primary citation |
|---|---|---|
| `421_name` | `"Misdirected Request"` | RFC 9110 §15.5.20 |
| `421_retry_non_idempotent` | `true` | RFC 9110 §15.5.20 |
| `421_proxy_may_generate` | `false` | RFC 9110 §15.5.20 |
| `retry_after_syntax` | set `{ "HTTP-date", "delay-seconds" }` | RFC 9110 §10.2.3 |
| `retry_after_9110_status_contexts` | set `{ "3xx", "503" }` | RFC 9110 §10.2.3 |
| `429_retry_after_strength` | `"MAY"` | RFC 6585 §4 |
| `103_replaces_final_headers` | `false` | RFC 8297 §2 |
| `request_no_store_applies_to_already_stored_response` | `false` | RFC 9111 §5.2.1.5 |

Canonical source URLs are exactly the four `.txt` URLs in §2 after URL normalization. Do not accept an RFC index page merely because it links to the right document. Do not accept RFC 9110 §15.5.20 for the 429 claim; the section must locally support that claim.

Normalization is deliberately narrow:

* IDs: exact ASCII match; reject duplicates and unknown/missing required IDs.
* Boolean answers: JSON boolean only. In Python, test `type(value) is bool` before any integer logic because `bool` subclasses `int`.
* Scalar strings: strip outer ASCII whitespace. Preserve semantic case except normalize the RFC keyword to uppercase.
* Arrays: require a JSON list of strings, strip each element, reject duplicates, compare as sets.
* Section: accept optional leading `§`, `Section`, or `section`, then normalize the remaining dotted number. No section ranges.
* URL: require `https`, exact lowercase host `www.rfc-editor.org`, no userinfo, no query, path exactly `/rfc/rfc(9110|9111|6585|8297).txt`, and no alternate port. Percent-decode once and reject if decoding changes a slash or introduces traversal.

The source-section mapping is the executable proxy for citation entailment. A citation to the right document but wrong section fails that item's citation point even if another section happens to mention the same token.

## 6. Executed scoring predicate

### 6.1 Safety and artifact checks

After the agent exits, `score.py` runs as a separate process and performs, in order:

1. `lstat(research-result.json)`; reject absence, symlink, directory, nonregular file, or size over 64 KiB.
2. Read strict UTF-8; reject BOM, decode failure, or duplicate JSON object keys. The duplicate-key detector uses `json.loads(..., object_pairs_hook=...)`.
3. Execute `git status --porcelain=v1 --untracked-files=all`. The only allowed record is `?? research-result.json`. Any modified tracked file, alternate untracked file, submodule change, or ignored-file creation detected by a second `git status --porcelain=v1 --ignored --untracked-files=all` probe fails artifact hygiene. The known-positive control is the expected untracked result itself: if neither status probe sees it after `lstat` does, the detector is invalid and reports `SCORER_ERROR`.
4. Verify `benchmark_id`, required IDs, types, and uniqueness.

The second status mode is mechanically different from the first field set and catches attempts to hide work in ignored paths. A separate filesystem walk rooted at the checkout, compared with a pre-run path/type/size manifest, is the second independent signal before claiming that no other file changed. Git detects semantic repository state; the manifest detects ignored/untracked filesystem state. Both detectors first demonstrate they can see the known-present `research-result.json`.

### 6.2 Point score

The scorer emits a JSON receipt with these 40 points:

* 2 points: artifact is a regular, bounded, strict-UTF-8 JSON file and is the only workspace change.
* 16 points: 2 for each of eight exactly correct normalized values.
* 16 points: 2 for each item having at least one allowed canonical `(URL, section)` pair, with every additional citation on that item also required to be an allowed pair. An invalid decorative extra citation fails that item's citation points.
* 4 points: one for each cited RFC snapshot matching its pinned SHA-256 and containing the expected section boundary in the private snapshot.
* 2 points: all eight IDs occur exactly once, all required types are correct, and no citation uses a non-primary or non-HTTPS host.

The binary success predicate is:

```text
PASS iff infrastructure_preflight == VALID
     and scorer_exit_code == 0
     and points == 40
     and workspace_diff == only_untracked_research-result.json
```

Anything from 0 through 39 is `FAIL`, with per-axis diagnostics retained. `INFRA_INVALID` and `SCORER_ERROR` are neither pass nor fail and must be rerun in a fresh fixture. The agent's final chat statement, claimed confidence, named tool usage, and prose explanation contribute zero points.

The scorer must be unit-tested by execution with at least these mutations:

1. golden answer → 40/PASS;
2. flip each boolean one at a time → lose its answer points;
3. correct value, wrong RFC section → citation points fail;
4. right RFC/section, wrong value → answer points fail;
5. fake `rfc-editor.org.evil.example` host → reject;
6. URL userinfo trick → reject;
7. duplicate answer ID → reject;
8. duplicate JSON key → reject;
9. symlink result to grader oracle → reject;
10. correct result plus an ignored scratch file → hygiene failure;
11. missing live network but intact offline oracle → `INFRA_INVALID`, not model failure;
12. local source snapshot with one byte changed → `SCORER_ERROR` before scoring.

### 6.3 Metrics reported across attempts

Report pass@1 and pass@3 from independent attempts, plus four diagnostic rates:

* answer accuracy: correct values / 8;
* citation support: correctly located citations / 8;
* artifact hygiene: 0 or 1;
* infrastructure-invalid rate.

Do not ratchet a baseline upward from a single pass and do not convert partial points into PASS. Preserve the initial harness's attempt-level receipts so a harness change can be compared on the identical task and fixture.

It is **likely (55-80%)** that the per-axis breakdown will distinguish retrieval failures from synthesis/schema failures, because each failure produces different deterministic fields; evidence is the orthogonal answer, citation, hash, and hygiene checks. The settling experiment is to run at least 30 attempts across the current and candidate harnesses, manually classify only the raw tool/error traces after scoring, and compute the confusion matrix between those trace classes and scorer diagnostics.

## 7. Failure modes this task is designed to expose

1. **Dead-tool fixation.** The agent repeatedly calls a disconnected hosted MCP instead of moving to built-in search, direct fetch, another working MCP, browser, or `curl`. The corpus's Tavily/Exa fingerprints make this a measured risk, not a hypothetical one.
2. **Search-snippet substitution.** The agent reports a plausible answer but cites a search page or secondary summary. Host/path allowlisting rejects it.
3. **Citation decoration.** The answer is correct, but the linked section does not support it. The private item-to-section map rejects it.
4. **Source hallucination.** A fabricated RFC number, path, host, or section fails URL normalization and oracle matching.
5. **Nearby-concept confusion.** The task separates request `no-store` from response `no-store`, 421 retry permission from ordinary idempotency advice, and RFC 9110's stated Retry-After contexts from RFC 6585's 429 extension.
6. **Normative-strength loss.** “May” as casual prose is not enough; the required answer is the exact RFC keyword `MAY`.
7. **Boolean inversion under negation.** Three questions require converting prohibitive text (“MUST NOT,” “do not replace,” “does not apply”) into a boolean without reversing it.
8. **Partial research.** Missing any one answer or citation prevents PASS; partial points show where it stopped.
9. **Over-strict output fan-out.** The schema is small, accepts extra keys, ignores array ordering, and normalizes harmless surface differences; these surface differences receive no points and cannot change a correct normalized answer.
10. **Unverified completion claim.** Chat prose is ignored; only the result file and executed scorer receipt count.
11. **Workspace collateral.** The clean-checkout diff plus manifest catches agents that alter tests/config or leave scratch downloads behind.
12. **Evaluator/network conflation.** Positive and negative preflight controls separate source outage/proxy failure from agent failure.

The task does not intentionally inject a failing MCP call. Agents that choose a healthy route should not be penalized for avoiding a known-dead service. A separate chaos variant could test forced failover, but that is neighbouring benchmark work and is not part of D006.

## 8. Anti-gaming analysis

### 8.1 Ways to pass without genuine research, and closures

| Shortcut | Closure in this design |
|---|---|
| Write fluent prose and claim “verified” | Prose and self-assessment receive no points; exact values and citations are executed. |
| Guess the answers from model memory | The fixed task still requires correct primary URL/section pairs. For capability evaluation, keep prompt/oracle private and use the held-out sibling policy below. |
| Cite the right RFC generally without finding support | Per-item exact section mapping. |
| Cite a mirror/search result with the answer in its snippet | Exact HTTPS host and path allowlist. |
| Forge a lookalike URL | Parsed scheme/host/port/userinfo/path checks, not substring matching. |
| Modify or read the scorer/oracle | Oracle and scorer are not mounted in the agent-readable checkout; result symlinks are rejected. |
| Exploit JSON duplicate keys or Python boolean/integer coercion | Duplicate-key hook and exact type checks. |
| Hide scratch or answer material under `.gitignore` | `--ignored` status plus a pre/post filesystem manifest. |
| Pass because a proxy returned an error page with status 200 | Full-body pinned hash and nonexistent-path negative control. |
| Poison the live RFC page after fixture creation | Grading uses private hash-pinned snapshots; live mismatch is infrastructure drift, not a changed answer key. |

### 8.2 The irreducible causality limit

No output-only scorer can prove the internal causal statement “the agent learned this answer during this run.” An agent could already know all eight facts and independently know the section numbers. Requiring a fetch log proves that a request occurred, not that the returned bytes caused the answer; it also unfairly misses server-side browsing tools whose egress is outside the local transcript.

Therefore the objectively defensible predicate is **correct evidence-grounded work product**, not private cognition. This is the closest objective proxy. Treating tool-count theatre as proof of research would be less honest.

**Proposal tag — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** to close benchmark-specific hard-coding after disclosure, keep this exact instance private while it is a capability test, then retire it to a public regression test after leakage. Maintain grader-side sibling instances with the same schema but different primary standards, claim IDs, and answer maps; select the instance after checkout creation and never expose sibling oracles to the agent. This rotation policy is **likely (55-80%)** to reduce direct answer-key hard-coding because a hard-coded HTTP-001 object deterministically fails IDs and values on a held-out sibling; evidence is the sealed-oracle pattern used by GAIA and the short-reference-answer pattern used by BrowseComp. **UNVERIFIED effectiveness:** the settling experiment is a red-team harness that is given the full HTTP-001 answer object but no web access and is evaluated on at least five sealed siblings; measure its pass rate versus a web-enabled agent.

This unit specifies only HTTP-001; it does not invent sibling content without researching and pinning those sources. That restraint prevents an anti-gaming recommendation from smuggling unverified answer keys into the benchmark.

## 9. Anti-overfit gate

The proposal passes the gate:

* It rides the existing `/eval` and weekly `harness-bench` execution surfaces rather than creating a second orchestrator (`/local_disk0/codexwork/bundle/claude/commands/eval.md:36-59`; `/local_disk0/codexwork/bundle/claude/hooks/harness-bench/bench.py:1-20`).
* It is a one-shot scorer and static fixture, not a persistent service.
* It introduces none of the rejected components: no vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, guardrail framework, or second orchestration runtime.
* It uses deterministic exact checks where they fit and explicitly declines to judge open-ended prose. This keeps the benchmark narrower but falsifiable.
* It does not mandate a research skill or MCP by name. Model/harness improvements can choose a simpler route and still pass.

The radical alternative—a large research-evaluation service with semantic citation judges and browsing telemetry—was rejected. Its tag would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**; it adds a second runtime and model-judge dependency and makes baseline movement ambiguous between agent improvement and judge drift. Nothing in this eight-fact task justifies that cost.

## 10. Repeatability protocol

For every harness revision under comparison:

1. Resolve the same repository commit by full SHA; never use moving `main` after resolution.
2. Create a new temp checkout and verify clean state.
3. Run fixture-neutrality and infrastructure controls.
4. Copy no grader material into the agent tree.
5. Start a fresh agent session with the exact prompt and a 12-minute limit.
6. Record process exit, elapsed time, normalized tool errors if available, and final workspace manifest. Tool telemetry is diagnostic and cannot change PASS.
7. Terminate the agent, then run the protected scorer.
8. Store the scorer JSON receipt, result-file SHA-256, repository commit, harness revision, model identifier, prompt hash, and source-fixture hashes.
9. Repeat in two additional fresh sessions for pass@3. Do not allow attempts to share messages, files, caches containing task answers, or edited checkouts.
10. Compare harnesses on identical attempt policy. Report infrastructure-invalid runs separately and rerun them.

Use this benchmark as a gate only after a golden fixture and all mutation tests in §6.2 execute successfully. That recommendation is **almost certain (90-99%)** because without a known-positive golden run and known-negative mutations, a zero or perfect score cannot distinguish scorer breakage from agent behavior; the evidence is both the owner's mandatory detector-control rule and the live D2 examples where one unvalidated probe produced wrong absence conclusions (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:102-121`).
