### Contract text, verbatim

>
> - Use **Keychain Services** for sensitive data (tokens, passwords, keys) — never `UserDefaults`
> - Use environment variables or `.xcconfig` files for build-time secrets
> - Never hardcode secrets in source — decompilation tools extract them trivially

### Concrete collision

That conflicts with the contract's runtime acquisition rule and with the Swift rule's own warning that decompilation extracts embedded secrets.

This finding does not claim every `.xcconfig` value is shipped. Signing credentials and build-tool-only settings can remain on the build host. The conflict arises because the rule calls `.xcconfig` a location for “build-time secrets” without making that critical distinction.

### Runtime winner

**Neither prompt instruction wins deterministically** when a Swift file activates this path-scoped rule. If an app-consumed secret has already been substituted into the product, the build artifact wins physically. If the `.xcconfig` value is build-tool-only and never enters an output, no collision arises.

### Minimal resolving edit — BUILD-SMALL

**BUILD-SMALL (<~200 lines, rides the existing rule/hook bus).** Replace `swift/security.md:13` with:

> Use environment variables or secret files for build-host-only credentials (signing, upload, CI authentication), and verify they are not copied or substituted into the product. This recommendation is **very likely (80-90%)** to resolve the ambiguity because it separates host-only build credentials from distributed app values, supported by Apple's documented build-setting and bundle-substitution mechanisms. Complete remediation is **UNVERIFIED; a canary-secret build followed by scans of the `.app` bundle, Info.plist, strings, and binary would settle whether each project-specific path leaks the setting.**
