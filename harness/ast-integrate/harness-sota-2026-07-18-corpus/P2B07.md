## Executive verdict

Goose is not a better wholesale replacement for this owner's harness. It is a coherent, provider-neutral agent product with a compact core and a notably good declarative workflow feature: a recipe can declare deterministic shell success checks, bounded retries, cleanup, model/provider settings, extensions, and a structured response. Its context compaction, session UX, on-demand MCP virtualization, and subagents are also cleanly productized. However, almost all of those latter capabilities already exist here natively or in stronger form. This harness has a broader lifecycle hook surface, cross-provider semantic memory with temporal validity, richer native multi-agent coordination, and much deeper domain tooling.

The highest-value port is Goose's deterministic recipe acceptance loop, not Goose itself. **It is very likely (80-90%) that a small, opt-in acceptance-contract layer would reduce false “done” claims without creating a second runtime**, because Goose's documentation and source independently show that it runs explicit exit-code checks and resets only message state before a bounded retry, while this harness already has the hook, skill, `longrun`, event-ledger, and terminal-marker buses needed to host the same mechanism ([recipe reference, lines 448-470](https://goose-docs.ai/docs/guides/recipes/recipe-reference/#retry); [Goose retry source, lines 99-161](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/retry.rs#L99-L161); local `C:\Users\Prekzursil\.codex\AGENTS.md:20-39`; local `C:\Users\Prekzursil\.agents\harness\README.md:12-28`).

The second useful port is session-local, liveness-aware MCP exposure. The corpus records a dead Tavily connector still receiving calls and the current configuration exposes a large static MCP fleet (`corpus/corpus.json:175,319,4389`; `C:\Users\Prekzursil\.codex\config.toml:480-629`). Goose can hide the fleet behind three Code Mode meta-tools and enable or disable extensions inside a session ([Code Mode, lines 81-119](https://goose-docs.ai/docs/guides/managing-tools/code-mode/); [in-session changes, lines 253-264](https://goose-docs.ai/docs/guides/sessions/in-session-actions/#mid-session-changes)). This harness already has Codex Code Mode and a nested execution meta-tool (`C:\Users\Prekzursil\.codex\config.toml:82-116`), so the missing part is not a new runtime; it is making liveness and session scope authoritative for tool exposure.

Do **not** copy Goose's default autonomous permissions, its LLM-based read/write classifier, its optional second-model security critic, its “load every memory into every prompt” policy, or its strict JSON final-output tool. Those mechanisms align badly with the owner's measured false-positive detectors, over-strict schema failures, MCP fleet bloat, and anti-overfit ban on trained critics (`INPUT-known-harness-defects.md:9-87,111-145`; `corpus/corpus.json:103,5135,6351,7197`; local `C:\Users\Prekzursil\.codex\AGENTS.md:47-54`).

## Scope and method

This teardown covers only the requested harness dimensions: agent loop, context management, memory, tool/MCP handling, permissions, rules/skills/hooks equivalents, multi-agent support, and verification/self-checking. It is not a general feature comparison of the two desktop products.

Primary evidence was preferred in this order:

1. Goose source pinned to the inspected commit.
2. Current official Goose docs and release notes.
3. Current local harness/config files.
4. The pinned corpus and live-operation defects.
5. Earlier audit findings only as leads, never as sole proof.

The Goose docs and source are mechanically independent signals: documentation describes intended public behavior; pinned Rust source shows implemented structures and control flow. For local absence claims, searches were first validated against a known-present `goal_reinjection` module, then corroborated against a second surface such as settings, registration, or corpus behavior. The corpus `_meta` says 11,633 files were seen, zero failed, one JSONL line was bad, and its absence claims are corpus-scoped (`corpus/corpus.json:2-11`). Its `hooks` section was not used because the prompt marks that detector broken.

## 1. Agent loop

### Goose mechanism

Goose implements the familiar provider/tool loop directly in Rust. The inspected agent initializes an extension manager, permission manager, retry manager, final-output tool, hook manager, and tool-result channel ([`agent.rs`, lines 243-260](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L243-L260)). `reply_internal` establishes a turn counter, defaults the main loop to 1,000 turns, injects MOIM before each provider call, streams the model response, categorizes tool requests, obtains approvals where required, dispatches tools, appends results, and continues until no tools/final output, cancellation, max turns, or a stop decision ([`agent.rs`, lines 1929-2037](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L1929-L2037); [`agent.rs`, lines 2161-2259](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L2161-L2259)).

Tool calls emitted together can be executed concurrently. The tool execution path accumulates futures after permission decisions and sends results back through a channel ([`tool_execution.rs`, lines 92-188](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/tool_execution.rs#L92-L188)). Empty provider turns are retried rather than silently terminating as of v1.43.0 ([v1.43.0 bug fix #10360](https://github.com/aaif-goose/goose/releases/tag/v1.43.0)). Stop hooks can force the loop to continue, but Goose caps consecutive Stop blocks at eight by default to avoid an infinite policy loop ([`agent.rs`, lines 69-132](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/agent.rs#L69-L132)).

### Comparison

The loop itself is simpler than this harness because Goose owns the whole runtime. That unity avoids the adapter drift seen in a cross-provider harness, but replacing Claude/Codex with Goose would also discard native provider behavior, current plugins, and first-party multi-agent features. **It is unlikely (20-45%) that a Goose replacement would improve end-to-end task quality for this owner**, because the evidence supports cleaner integration but provides no owner-specific benchmark showing Goose beats the current Claude/Codex models, while the corpus demonstrates extensive use of capabilities Goose would have to re-integrate (`corpus/corpus.json` capability-use section; Goose README provider/extension claims).

The explicit turn ceiling and Stop-block ceiling are good defensive details. Our behavior contract has a three-repeat blocked threshold and anti-degeneration machinery, but no single provider-neutral main-turn budget is visible in the shared registration or live harness modules; the known-positive `goal_reinjection` search succeeded while searches for `GOOSE_MAX_TURNS`-like main-loop controls did not (`C:\Users\Prekzursil\.agents\harness\dispatcher.py:70`; `C:\Users\Prekzursil\.agents\harness\modules.py:1280-1356`).

#### Capability gap — provider-neutral turn/Stop-loop budgets

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add optional `max_tool_turns` and `max_stop_denials` to the goal/event-ledger state. Increment on PostToolUse/Stop, reset on new user input, inject a terminal warning at the threshold, and permit termination after the Stop-denial cap. This is a counter in the existing shared dispatcher, not a scheduler. **It is likely (55-80%) to prevent a narrow class of runaway loops**, based on Goose's explicit cap and this corpus's retry-loop evidence, but UNVERIFIED for net owner value; settle it with a 30-session shadow run measuring loops stopped, false stops, and extra tokens.

### What not to copy

- Do not copy the 1,000-turn default. It is a safety ceiling too high to be operationally meaningful for most interactive work ([environment variables, lines 358-365](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/environment-variables.md#L358-L365)).
- Do not add Goose as a second orchestration runtime merely to obtain its loop. That violates the anti-overfit gate's rejection of a second runtime and would be **very unlikely (5-20%) to repay its integration cost**, because every valuable loop control identified here fits an existing hook or skill.

## 2. Context management

### Goose mechanism

Goose uses two levels:

1. Proactive auto-compaction, defaulting to 80% of the model context.
2. A backup limit strategy: summarize, truncate, clear, or prompt; interactive CLI defaults to prompt, headless defaults to summarize, and Desktop always summarizes ([Smart Context Management](https://goose-docs.ai/docs/guides/sessions/smart-context-management/); [`context_mgmt/mod.rs`, lines 21-36 and 173-224](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L21-L36)).

Compaction formats the visible history, calls the provider with a customizable `compaction.md` prompt, inserts the summary as an agent-only message, preserves the current user message, and adds a continuation instruction ([`context_mgmt/mod.rs`, lines 67-168](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L67-L168); [`context_mgmt/mod.rs`, lines 277-339](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L277-L339)). Separately, it summarizes old tool-call/result pairs in batches while protecting recent pairs; source computes the cutoff from context size and threshold ([`context_mgmt/mod.rs`, lines 432-589](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/context_mgmt/mod.rs#L432-L589)).

MOIM (Model-Observed Internal Memory) is transient turn context, not durable memory. It injects current session facts such as time, working directory, turn budget, compaction status, todos, extension-provided context, and optional persistent text/file instructions before every model turn ([`moim.rs`, lines 1-19 and 42-161](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/moim.rs#L1-L19); [Persistent Instructions](https://goose-docs.ai/docs/guides/using-persistent-instructions/)). The configured file is re-read each turn and capped at 64 KiB.

### Comparison

Our providers already compact and the harness has PreCompact/PostCompact events, goal re-injection, checkpoints, request compression, and strategic-compaction guidance (`C:\Users\Prekzursil\.claude\settings.json:18,380-405`; `C:\Users\Prekzursil\.codex\config.toml:82-116`; `C:\Users\Prekzursil\.codex\AGENTS.md:18-26`). Goose's visible strategy selector and editable compaction prompt are cleaner controls, while our objective ledger is stronger than trusting a model-generated summary.

The per-tool-pair summary is attractive but risky here. The corpus's core problem includes tool-result misunderstanding and failed writes, and the Stop hook already receives false “discard successful result” signals (`INPUT-known-harness-defects.md:54-81`). Summarizing old results introduces another lossy transformation. **It is roughly even (45-55%) whether Goose-style pair summarization would help this owner**, because it reduces tokens in source, but no owner-specific experiment measures whether it loses terminal markers, error codes, paths, or evidence.

#### Capability gap — live, per-turn operational context file

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A bounded UserPromptSubmit/PreToolUse hook could re-read one small operational file and inject only changed, validated fields such as current goal ID, dangerous-action policy, and active acceptance checks. Do not inject arbitrary prose or the whole rules tree. **It is likely (55-80%) that a typed, sub-4-KiB variant would improve mid-session policy updates**, based on Goose's MOIM mechanism and this harness's need for goal re-injection, but UNVERIFIED; settle it with an A/B test that changes one canary instruction mid-session and measures adherence plus token cost. This recommendation inherits the known defect's requirement for code/prose discrimination.

#### Capability gap — user-selectable fallback after compaction failure — UNVERIFIED

**NATIVE (Claude Code already does this; we just enable it).** Claude already exposes `/compact [instructions]`, session checkpoint/rewind controls, and PreCompact/PostCompact hooks; the local harness registers both compact events ([Claude session docs](https://code.claude.com/docs/en/sessions); [Claude hooks reference](https://code.claude.com/docs/en/hooks#precompact); `C:\Users\Prekzursil\.claude\settings.json:380-405`). The port is a compact policy rule: automatic summary for headless work; ask before destructive clear/truncate in interactive work; persist the objective ledger before either. **It is very likely (80-90%) that no custom runtime is required**, based on those native controls; the remaining UNVERIFIED item is exact current CLI choice parity across both providers, settled by forcing a tiny-context canary session in each.

### What not to copy

- Never make model summary the ground truth. Keep the event ledger authoritative and treat summary as navigation.
- Do not enable tool-pair summarization until a golden test proves exact preservation of `SUCCESS:/FAILED:` markers, exit codes, error fingerprints, file paths, and source citations.
- Goose's “truncate” and “clear” strategies intentionally lose history. They are emergency options, not normal policy.

## 3. Durable memory and session continuity

### Goose mechanism

Goose has three distinct persistence surfaces:

- Sessions: all messages, tool calls/results, metadata, provider/model, extensions, and recipes are saved in local SQLite. Sessions can be resumed, duplicated, forked, exported, imported, searched, and—since v1.43.0—edited before a fork ([Session Management, lines 176-187, 282-368](https://goose-docs.ai/docs/guides/sessions/session-management/); [v1.43.0 release](https://github.com/aaif-goose/goose/releases/tag/v1.43.0)).
- Chat Recall: a built-in platform extension searches across session history by keyword/recency or loads a session summary and is automatically selected when the user references prior work ([Chat Recall Extension](https://goose-docs.ai/docs/mcp/chatrecall-mcp/)).
- Memory extension: project-local `.goose/memory/` and global config-directory files store categorized memories. Goose loads **all** saved memories at session start and includes them in every model prompt; tools remember, retrieve, or remove categories/items ([Memory Extension, lines 157-197](https://goose-docs.ai/docs/mcp/memory-mcp/)).

### Comparison

Our semantic memory is materially stronger in provenance and lifecycle: it is cross-tool, supports semantic lookup, compaction checkpoints, and explicit supersession/valid-as-of fields (`C:\Users\Prekzursil\.codex\AGENTS.md:62-85`; `C:\Users\Prekzursil\.claude\CLAUDE.md:5-11`). Goose's memory is simpler and more automatic, but loading all memory into every prompt scales with the vault and risks stale facts. Goose's own docs give no temporal supersession protocol.

Goose's raw transcript search and first-class fork/edit UX are better product surfaces than our offline corpus miner and manually triggered semantic recall. Codex saves all history and has a dense session picker, but no inspected local file establishes agent-callable cross-session transcript search (`C:\Users\Prekzursil\.codex\config.toml:39-50`). A known-positive local search found goal reinjection; separate searches across the live harness and settings found no Chat Recall-equivalent transcript tool. This supports the bounded gap without claiming that no uninspected native UI search exists.

#### Capability gap — agent-callable exact transcript search

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Expose a read-only tool over the existing Claude JSONL/Codex history stores: `search_sessions(query, cwd?, since?, limit=10)` and `read_session_excerpt(session_id, around_message_id, radius)`. Use lexical/SQLite search, return paths and message IDs, redact secrets, and never auto-load whole transcripts. This does not add a vector DB or daemon. **It is likely (55-80%) to improve recovery of exact prior commands and errors**, because Goose documents this workflow and the owner already mines 10.62 GB of transcripts, but UNVERIFIED for interactive frequency; settle it by replaying 50 owner-correction prompts that reference earlier work and comparing retrieval precision against `basic-memory` alone.

#### Capability gap — automatic, selective prior-session recall

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On UserPromptSubmit phrases that refer to prior work, query the existing bounded lexical index and inject at most three provenance-bearing snippets; if confidence is low, inject only the tool suggestion. The live harness already has bounded recall infrastructure, so this is activation/routing rather than a new memory system (`C:\Users\Prekzursil\.agents\harness\README.md:21-28,40-43`). **It is very likely (80-90%) to be cheaper and safer than Goose's load-all policy**, based on bounded retrieval and the size of this owner's vault, but UNVERIFIED for recall quality; settle it with known-note and stale-note controls.

### What not to copy

- Do not load all durable memory into every prompt. That is the opposite of bounded context engineering.
- Do not replace `basic-memory` with Goose's file categories. That would lose cross-tool canonicality and temporal validity.
- Do not add a knowledge graph memory extension. The anti-overfit gate explicitly rejects vector-DB/KG replacement; our existing store is sufficient.

## 4. Tool and MCP handling

### Goose mechanism

Goose treats extensions as MCP servers. Built-ins include Developer, Computer Controller, Memory, Chat Recall, Code Mode, Extension Manager, Summon, Todo, and Top of Mind. External stdio/HTTP extensions are managed by the same extension manager ([Using Extensions](https://goose-docs.ai/docs/mcp/filesystem-mcp/); [`extension_manager.rs`](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/extension_manager.rs)). The MCP client carries session ID, working directory, and tool-call request ID through MCP extensions/metadata and supports MCP Apps UI capabilities ([`mcp_client.rs`, lines 222-304 and 881-889](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/agents/mcp_client.rs#L222-L304)).

Code Mode virtualizes a large fleet behind `list_functions`, `get_function_details`, and `execute_typescript`. Tools are discovered on demand; multiple calls and intermediate transformations run inside a bounded Deno-based execution ([Code Mode, lines 81-122](https://goose-docs.ai/docs/guides/managing-tools/code-mode/)). Goose also lets the agent discover/enable/disable extensions during a session. v1.43.0 added timeouts/cancellation for Code Mode and fixed several MCP/tool-shape failures ([v1.43.0 release](https://github.com/aaif-goose/goose/releases/tag/v1.43.0)).

Supply-chain controls are concrete: administrators can publish a command-exact YAML allowlist fetched from `GOOSE_ALLOWLIST`, and Goose checks locally executed `uvx`/`npx` extensions against known malware before activation ([Extension Allowlist](https://goose-docs.ai/docs/guides/allowlist/); [Known Issues, malware scope](https://goose-docs.ai/docs/troubleshooting/known-issues/)).

### Comparison

Code Mode is not a gap. Codex already enables `code_mode`, unified execution, MCP Apps, and plugin gateways (`C:\Users\Prekzursil\.codex\config.toml:82-116`). The active execution API similarly exposes a small JavaScript orchestration surface and dynamically available tools. Goose's documented text-only limitation is worse for image/binary MCP results ([Code Mode, lines 120-122](https://goose-docs.ai/docs/guides/managing-tools/code-mode/)).

The material gap is session-local liveness and supply-chain admission. The current fleet still calls a dead MCP, and the owner has 1,293 orphaned plugin directories whose unsafe bulk deletion was correctly stopped. Goose does not solve orphan cleanup, but it demonstrates that extension discovery, enablement, timeouts, and admission can be one coherent boundary.

#### Capability gap — session-local, liveness-aware tool exposure

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing MCP manager/preflight path to publish only live capabilities to ToolSearch/Code Mode for the session. Cache `initialize + tools/list` health by server/config hash with short TTL; distinguish DOWN, AUTH, QUOTA, and LIVE; never mutate global configuration during a task; expose an explicit `enable_for_session(name)` only after a healthy probe. Feed terminal `FAILED:mcp-<name> <class>` results to the breaker. **It is very likely (80-90%) to reduce dead-connector calls**, because the corpus has 135 “not connected” Tavily failures and Goose's session-local extension state is implemented, but UNVERIFIED for startup latency; settle it with a shadow preflight over the current daily tier and measure latency, false DOWN classifications, and avoided calls.

#### Capability gap — MCP installation allowlist and malware admission

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a ConfigChange/PreToolUse gate for extension installation: normalize command plus package identity/version, require an owner-maintained allowlist or explicit approval, query the native package ecosystem's advisory/integrity signals, and write a receipt containing package, version, digest, decision, and evidence. Fail closed only on a positive known-malware match or unverifiable binary provenance; otherwise ask/inject according to the behavior contract. **It is likely (55-80%) to reduce supply-chain risk**, based on Goose's implemented admission boundary and this fleet's scale, but UNVERIFIED for false positives; settle it against known-clean `npx`/`uvx`, a benign unpublished local MCP, and a controlled known-malicious package fixture. A command-string-only allowlist is insufficient because shims and mutable tags can resolve different code.

#### Capability gap — MCP session context headers — UNVERIFIED

**CONFIG (settings/JSON only).** Standardize `session_id`, `working_dir`, and `tool_call_request_id` metadata for MCPs that support it, using existing client metadata/config rather than another service. **It is likely (55-80%) to improve attribution in concurrent runs**, because Goose source propagates those fields and this harness has documented sibling-agent scoping defects, but UNVERIFIED across the current MCP fleet; settle it by probing five representative stdio/HTTP servers and confirming round-trip visibility without schema breakage.

### What not to copy

- Do not dynamically install whatever the model discovers. Discovery and execution are distinct authority boundaries.
- Do not expose tool enable/disable as persistent global mutation from a subagent. Goose correctly blocks subagents from extension management ([Subagents, Security Constraints](https://goose-docs.ai/docs/guides/context-engineering/subagents/#security-constraints)).
- Do not adopt Code Mode's text-only result loss for visual/RE/scientific tools.

## 5. Permission and security model

### Goose mechanism

Goose offers Autonomous, Manual Approval, Smart Approval, and Chat Only. Autonomous is the default. Manual and Smart modes prompt for operations classified as writes; Smart uses a provider/model judgment to classify requests, while persistent per-tool permissions override with Always Allow, Ask Before, or Never Allow ([Permission Modes](https://goose-docs.ai/docs/guides/goose-permissions/); [Tool Permissions, lines 97-117](https://goose-docs.ai/docs/guides/managing-tools/tool-permissions/)). The permission judge's source explicitly treats tool names and arguments as untrusted, asks the model to return only IDs that are strictly read-only, and defaults uncertainty to not read-only ([`permission_judge.rs`, lines 40-88](https://github.com/aaif-goose/goose/blob/8e78960e535ab7f34630e7c5921a42f146cbc9f4/crates/goose/src/permission/permission_judge.rs#L40-L88)).

`.gooseignore` denies Developer-extension reads, writes, deletes, and shell access for matching paths, using global then project patterns. It does not constrain other extensions, and a local negation can re-include a globally ignored path. Default secret patterns exist only when no ignore file exists ([`.gooseignore`, lines 88-106 and 149-191](https://goose-docs.ai/docs/guides/context-engineering/using-gooseignore/)).

Optional prompt-injection detection pattern-matches tool-call text and can call a configured ML classifier; alerts carry confidence/finding IDs and decisions are logged ([Prompt Injection Detection](https://goose-docs.ai/docs/guides/security/prompt-injection-detection/)). Optional Adversary Mode calls the same provider/model before selected tools, supplies task/recent messages/rules, and accepts ALLOW/BLOCK. It fails open if the reviewer fails ([Adversary Mode, lines 82-131](https://goose-docs.ai/docs/guides/security/adversary-mode/)).

### Comparison

Our configured permission posture is worse than either product's available safe mode: both providers are effectively unrestricted. Goose's per-tool tri-state UI is clearer than the current giant allowlist. However, Claude already supports allow/deny/ask patterns and currently denies several credential reads (`C:\Users\Prekzursil\.claude\settings.json:26-71`), so this is configuration debt, not missing machinery.

Goose's controls are not a Windows OS sandbox. The docs explicitly scope `.gooseignore` to Developer and describe Smart Approval as model interpretation; the security index documents a macOS sandbox, not a Windows equivalent ([security index](https://goose-docs.ai/docs/guides/security/)). **It is likely (55-80%) that an arbitrary third-party MCP can bypass `.gooseignore` by design**, because the docs explicitly exclude other extensions, but whether current Goose Windows has another containment layer is UNVERIFIED; settle it by running a test MCP that attempts to read a blocked canary and write outside the workspace under each mode.

#### Capability gap — safer configured default permission profile

**CONFIG (settings/JSON only).** Move ordinary sessions from universal bypass to a native approval/sandbox profile; retain an explicit owner-selected high-autonomy profile for scoped tasks.
