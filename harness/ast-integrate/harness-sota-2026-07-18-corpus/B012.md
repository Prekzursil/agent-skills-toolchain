# B012 — Groundedness engineering: fabrication postmortem

## Executive verdict

The measured incident is a **provenance failure amplified by fan-out**, not a special defect in the Write tool. The orchestrator converted an unsupported belief—“The Write tool is blocked for `~/.claude`”—into authoritative prompt text, duplicated that text into approximately 15 child prompts, and thereby made a less reliable PowerShell here-string transport look mandatory. The pinned live-defects record says the constraint appears in no skill, rule, or setting and records the incident-specific failure rates as 13.6% for the workaround versus 0.0% for Write (`bundle/inputs/INPUT-known-harness-defects.md:151-160`). The broader corpus independently records PowerShell at 2,031 errors / 19,181 calls (10.59%) and Write at 439 / 12,845 (3.42%); those global rates corroborate the direction of harm but must not be substituted for the incident-specific 13.6%/0.0% comparison (`bundle/inputs/corpus.json`, `tool_usage` entries for `PowerShell` and `Write`).

Hallucination cannot be eliminated. Any harness design that promises elimination is false. The achievable target is narrower: make **unsupported operational constraints** mechanically identifiable before they are multiplied, then make challenging them cheaper than obeying an expensive workaround.

The recommended design is one small addition to the existing hook bus: a structured **Constraint Provenance Gate** on fan-out launch. It does not decide whether arbitrary prose is true. It checks whether a statement that changes tool choice, access, permissions, path scope, or required workaround has a typed source and a resolvable receipt. User directives are authority, not factual claims; host-capability claims require host evidence; inferences cannot be rendered as ground truth. A protected launcher renders the factual preamble only from validated records, and the existing Claude `PreToolUse` Task seam checks the manifest before dispatch. This would have made the measured unsupported sentence cheap to catch at the one producer boundary instead of after approximately 15 consumers had acted on it.

**Expected performance is UNVERIFIED.** It is **likely (55-80%)** that the protected rail catches most unsupported operational constraints in migrated batch launchers because it deterministically rejects missing provenance, but the actual fraction is unknown until the experiment “replay a labeled set of historical launcher prompts, including this incident and legitimate directives, through the new gate” is run. It catches no arbitrary hallucination outside the protected constraint fields, and that limitation is deliberate.

## Incident reconstruction

### 1. The normal capability was available

The current unpacked settings allow the native Write tool and do not define a blanket Write deny (`bundle/claude/settings.json`, `permissions`). The file-scope gate is explicitly fail-open when no sidecar exists and makes decisions from the concrete target path and allow-list (`bundle/claude/hooks/file-scope/check.py:4-10,98-136`). The corpus also contains 12,845 successful-or-attempted Write calls, so Write was plainly an active capability rather than an absent interface (`bundle/inputs/corpus.json`, `tool_usage[tool=Write]`).

This does **not** mean every Write call to every path must succeed: the corpus records 439 Write errors, dominated by 366 “File has not been read yet” errors, plus worktree and user-rejection cases (`bundle/inputs/corpus.json`, `failures_by_tool.Write`). It means the categorical claim “Write is blocked for `~/.claude`” required evidence about that path and enforcement context; generic knowledge about permissions was insufficient.

### 2. An internal belief was promoted to an instruction

The pinned incident record says the sentence originated “in one of my own workflow launchers” (`bundle/inputs/INPUT-known-harness-defects.md:153-155`). The exact first model turn, launcher filename, and surrounding reasoning are **UNVERIFIED because the raw launcher/transcript is not present in the bundle; the experiment that would settle them is to open the originating launcher and parent transcript from the Windows history and identify the first occurrence plus its immediately preceding tool results**.

What can be reconstructed without that missing material is the type transition:

```text
unsupported internal belief
        ↓ (no provenance/type boundary)
launcher preamble presented as ground truth
        ↓ (copy/fan-out)
~15 child prompts inherit the same constraint
        ↓ (instruction hierarchy)
children choose a workaround rather than challenge authority
        ↓
PowerShell here-string quoting/transport failures
```

The load-bearing transition is “belief → launcher preamble.” Once the sentence was in the task contract, a child was not merely evaluating an ordinary factual answer. It was following an instruction from its orchestrator. D4 states that this made the false constraint invisible to receiving agents and calls orchestrator-authored ground truth an attack surface (`bundle/inputs/INPUT-known-harness-defects.md:157-160`).

### 3. Fan-out laundered repetition into apparent authority

Approximately 15 children received the same false premise (`bundle/inputs/INPUT-known-harness-defects.md:153-155`). This was duplication, not 15 independent observations. The installed fan-out contract now records the general mechanism: prompt elements predict child compliance almost perfectly and global rules are not inherited reliably (`bundle/claude/rules/common/fan-out-contract.md:3-15`). It also records four briefed “VERIFIED GROUND TRUTH” facts being false in one run and two children reproducing the orchestrator’s broken detector rather than independently checking it (`:25-31`).

It is **very likely (80-90%)** that authoritative placement plus prompt duplication, rather than independent child discovery, was the dominant propagation mechanism because D4 names the launcher and ~15 prompts while the fan-out contract independently measures prompt-content compliance; exact child-by-child causal attribution remains **UNVERIFIED until the experiment “diff all affected child prompts and transcripts, then classify whether each workaround cites the preamble, a direct tool failure, or another source” is run**.

### 4. The workaround converted epistemic error into execution error

The affected children routed writes through PowerShell here-strings, measured at 13.6% failure in that workflow, instead of Write, measured at 0.0% there (`bundle/inputs/INPUT-known-harness-defects.md:153-155`). The broader corpus shows why this substitution is directionally dangerous: PowerShell’s aggregate error rate is 10.59%, versus 3.42% for Write, and Bash has 1,631 unmatched-single-quote EOF fingerprints (`bundle/inputs/corpus.json`, `tool_usage`; `failures_by_tool.Bash`). The fan-out contract independently identifies a PowerShell here-string output contract as vendor-fragile and a direct contributor to transport failure (`bundle/claude/rules/common/fan-out-contract.md:37-39`).

The 13.6% incident rate must not be generalized to all PowerShell operations, and the 0.0% incident rate must not be generalized to all Write calls. The corpus’s global rates demonstrate precisely why per-workflow and global rates must stay separate.

### 5. The failure survived because existing checks were downstream or category-narrow

The current claim guard records Bash results and scans the final answer for a closed list of success phrases such as tests/build/lint/fixed/functional claims (`bundle/claude/hooks/claim-guard/README.md:3-15,26-55`). It does not inspect Task launch premises, does not cover permission/capability assertions, and accepts any successful command for several broad claim classes (`:41-50`). The truth-verify hook is intentionally restricted to reverse-engineering anchors such as hex addresses and offsets (`bundle/claude/hooks/truth-verify/check.py:2-22,37-65`). Neither could catch “Write is blocked” at launch.

The prose single-signal rule does cover the epistemic principle: a load-bearing subagent finding is a single signal; absence/broken/done claims need mechanically independent corroboration; and the detector must first find a known-present control (`bundle/claude/rules/common/single-signal-verification.md:20-37`). But a rule is remembered behavior, not a producer-side type check. The live-defects record explicitly identifies that enforcement gap (`bundle/inputs/INPUT-known-harness-defects.md:126-129`).

The fan-out contract now requires a briefed fact to carry a probe tag, timestamp, and mechanically different re-probe rule (`bundle/claude/rules/common/fan-out-contract.md:25-31`). This is the correct policy direction, but D4 notes the residual hole: it covers only facts explicitly tagged with a probe ID (`bundle/inputs/INPUT-known-harness-defects.md:157-160`). An invented fact left untagged can still look authoritative.

## Root cause and contributing conditions

### Root cause: no type boundary between authority, evidence, inference, and instruction

The launcher accepted a natural-language preamble in which four epistemically different objects were representable by the same string:

- an owner directive (“do not write the subject”),
- a host capability fact (“Write is denied for this target”),
- an observation (“a Write call returned a denial”), and
- an inference (“therefore all `~/.claude` Write calls are blocked”).

Only the first is authoritative without empirical proof. The second and third require receipts and scope. The fourth must remain an inference until tested. The launcher had no mechanical distinction, so an inference acquired the force of a directive.

### Amplifier: one-to-many epistemic blast radius

The error was introduced once and paid approximately 15 times. The fan-out contract’s finding that prompt elements predict compliance and that four correcting agents led with their corrections demonstrates both sides of this channel: prompt content propagates, and correction content can propagate too (`bundle/claude/rules/common/fan-out-contract.md:3-15,41-43`). Therefore the economical interception point is the producer boundary before dispatch, not 15 independent Stop hooks after work.

### Contributing condition: consumers lacked cheap contradiction protocol

D4 says receiving agents had no way to falsify an orchestrator instruction (`bundle/inputs/INPUT-known-harness-defects.md:157-160`). More precisely, they had tools that could inspect settings or attempt a bounded probe, but the contract did not make such a challenge legitimate or cheap. The single-signal rule says a subagent finding remains one signal and instructs raw-source verification (`bundle/claude/rules/common/single-signal-verification.md:34-37`), while the fan-out contract now requires an independent re-probe (`bundle/claude/rules/common/fan-out-contract.md:25-31`). The missing piece is attaching that requirement to every operational constraint automatically.

### Contributing condition: the workaround was not decision-linked to the claim

The corpus can count tool errors, but the broken hook detector means hook behavior is no data, and the distilled corpus does not retain a typed edge saying “PowerShell call X was selected because constraint C said Write was unavailable.” D3 explicitly says hook behavior across sessions is currently unmeasurable and names experiments to locate any durable hook output (`bundle/inputs/INPUT-known-harness-defects.md:133-147`). Without a decision-to-constraint edge, postmortem attribution requires reading prose and is easy to miss.

## The guard that would have caught it

## Proposal 1 — Constraint Provenance Gate — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Add one deterministic module to the existing shared dispatcher and one tiny launcher-side renderer. Do not add an MCP server, daemon, model call, vector store, knowledge graph, trained critic, or second orchestration runtime.

### Protected object

The gate protects **operational constraints**, not all factual prose. An operational constraint is a claim whose truth changes any of:

- whether a tool or server is available;
- whether a tool is permitted for a path/scope;
- which shell/transport must be used;
- whether a path/file/service exists or is reachable;
- whether a required workaround is necessary;
- whether an action is prohibited by user authority or host policy.

That narrow target is intentional. It captures this incident while avoiding a text classifier over every sentence.

### Typed record

Protected batch launchers should render a compact, machine-readable block before the natural-language unit task:

```json
{
  "grounding_contract": 1,
  "launcher_id": "...",
  "run_id": "...",
  "constraints": [
    {
      "id": "C-001",
      "kind": "USER_DIRECTIVE | HOST_FACT | OBSERVATION | INFERENCE",
      "proposition": "...",
      "effect": "DENY_TOOL | REQUIRE_TOOL | PATH_SCOPE | REQUIRE_WORKAROUND | OTHER",
      "subject": {"tool": "Write", "path": "C:/Users/.../.claude/**"},
      "source": [{"type": "user_turn | config_span | tool_receipt", "ref": "...", "sha256": "..."}],
      "observed_at": "RFC3339 timestamp",
      "expires_at": "RFC3339 timestamp or null",
      "independent_probe": {"method": "...", "ref": "..."},
      "on_conflict": "REPORT_AND_USE_OBSERVED_HOST_STATE"
    }
  ]
}
```

The prompt’s operational-facts section is generated from these records. It is not a second free-form string maintained beside them. The natural-language task may describe the unit objective, but protected launchers do not accept an additional free-form “ground truth” preamble. A hash over the rendered block and launcher template makes accidental post-render edits detectable.

### Validation rules

1. `USER_DIRECTIVE` is valid with a pointer/hash to the current owner instruction. It does not need a tool probe because authority and truth are different questions. For example, “READ-ONLY on the subject” is a directive even if Write is technically available.
2. `HOST_FACT` that asserts unavailable, denied, absent, broken, or unreachable requires two mechanically independent signals when load-bearing: for this incident, either an actual scoped denial receipt plus a config/hook evaluation, or two different host measurements. Repeating the same rejected call is not independent. A negative search must include a known-positive control, matching the installed verification rule (`bundle/claude/rules/common/single-signal-verification.md:25-30`).
3. `OBSERVATION` can report exactly what a receipt showed, with timestamp and scope, but cannot be generalized. “Write to path X was denied at time T” is not “Write is blocked for all `~/.claude`.”
4. `INFERENCE` may be included only as inline `UNVERIFIED`, with the experiment that would settle it. It cannot carry `DENY_TOOL` or `REQUIRE_WORKAROUND` effect until promoted by evidence.
5. Evidence references must resolve. Config spans are re-read and hashed; tool receipts must exist in the current ledger and match tool, target, result, and time scope. A bare prose citation is not a receipt.
6. Expired evidence is `UNKNOWN`, not false. The gate asks for a refresh or renders the claim as unverified; it does not silently invert it.
7. A malformed or unsupported constraint in a protected fan-out blocks the **launch**, not the underlying tool. The diagnostic names the constraint ID and missing evidence. This prevents multiplying an unsupported premise while leaving ordinary single-agent work unaffected.

The existing harness already has most plumbing. Claude registers the shared dispatcher on `PreToolUse` with `Task` in the matcher (`bundle/agents/harness/registration.py:64-72`; `bundle/claude/settings.json`, first `PreToolUse` matcher). The adapter preserves `tool.name`, the entire `tool.input`, prompt, session, turn, and agent fields (`bundle/agents/harness/adapters.py:116-145`). The provider-neutral result can deny a PreToolUse action with a reason (`bundle/agents/harness/adapters.py:159-185`). The hook bus already has OFF → SHADOW → ADVISE → ENFORCE staging and defaults new heuristic gates to shadow (`bundle/agents/harness/modules.py:118-143,389-417`). The ledger already provides command fingerprints and bounded fresh-receipt queries (`bundle/agents/harness/ledger.py:374-403,1093-1133`).

Receipt validation must not reuse the ledger’s permissive generic-positive-text fallback: `_receipt_status` can treat words such as “success,” “ready,” or “ok” as pass without an exit code (`bundle/agents/harness/ledger.py:354-371`). For provenance, accept structured host decisions, exact config spans, explicit exit/status fields, or known typed results only. An arbitrary green receipt of the right broad class is also insufficient; it must bind to the claimed tool, target, and invariant.

### How it catches the measured incident

If the launcher attempted to emit:

```json
{
  "kind": "HOST_FACT",
  "proposition": "The Write tool is blocked for ~/.claude",
  "effect": "REQUIRE_WORKAROUND",
  "source": []
}
```

the launch would remain shadow-only during burn-in and later be denied in enforce mode because the fact has no resolvable host receipt and no independent probe. If the author marked it `INFERENCE`, the renderer would label it inline `UNVERIFIED` and forbid the workaround effect. If the author tried to mark it `USER_DIRECTIVE`, the referenced user-turn hash would fail to resolve to that directive. The sentence therefore could not become authoritative protected preamble merely by being typed confidently.

This catches unsupported provenance, not metaphysical falsity. A claim with two genuine but misleading signals can pass. A false owner directive remains an owner directive and is followed as authority. A free-form unprotected prompt can bypass the rail. Those are explicit boundaries, not hidden failure modes.

It is **almost certain (90-99%)** that a unit test containing the exact empty-source record above will be caught because schema validation is deterministic; runtime interception of the historical launcher is **UNVERIFIED until the experiment “implement the module in a copied harness, replay the original Task payload, and observe the staged verdict” is run**.

The implementation size is **likely (55-80%)** to remain below approximately 200 lines because parsing, receipt lookup, and staging primitives already exist at the cited seams; this estimate is **UNVERIFIED until the experiment “implement and count non-test source lines” is run**. If it exceeds that bound because a new service or semantic model is introduced, reject the implementation rather than silently relabel it BUILD-SMALL.

## Proposal 2 — Consumer challenge receipt and contradiction return — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Extend the same record, not a second component, so every child receives constraint IDs and a challenge rule:

> Before taking a materially costlier workaround because of `HOST_FACT` C-n, perform its named mechanically independent probe if the receipt is expired or not reproducible. If observed host state contradicts C-n, do not vote or silently comply; return `CONSTRAINT-CONFLICT C-n` with the new receipt and continue only when the action is safe and within the owner directive.

At `SubagentStart`, the existing lifecycle module already injects a handoff and an I-PASS read-back request (`bundle/agents/harness/modules.py:2331-2382`). Add the active constraint IDs and their probe methods to that injection. At `SubagentStop`, accept an optional structured conflict record alongside the existing terminal handoff, instead of burying contradictions in prose. The current lifecycle gate already treats empty or too-brief output as incomplete (`:2384-2396`).

This consumer path matters when a fact was supported at launch but becomes stale, or when receipts disagree. It must not cause every child to repeat every probe. Re-probe only when the constraint is about to change the child’s tool/transport choice, when evidence is expired, or when the child sees a direct contradiction. A single producer receipt can otherwise be shared.

It is **likely (55-80%)** that this keeps average probe cost low because most constraints will either be directives or carry fresh shared receipts and therefore trigger no child probe; the actual cost is **UNVERIFIED until the experiment “instrument protected launches and report probes triggered per constraint, added wall time, and tokens over at least 100 launches” is run**.

Do not hard-block a child merely for disagreeing with a factual constraint. A contradiction is a first-class result. The fan-in rule already says a specific probe beats agent count and that split verdicts must be resolved from probes rather than votes (`bundle/claude/rules/common/fan-out-contract.md:76-83`).

## Proposal 3 — Shadow-first rollout modes — CONFIG (settings/JSON only)

Configure the Proposal 1 module `off | shadow | advise | enforce` using the existing staging mechanism rather than enabling a fresh block immediately (`bundle/agents/harness/modules.py:118-143,389-417`). Start in shadow. The event fields below belong to the Proposal 1 BUILD-SMALL implementation; this CONFIG proposal only selects its mode and promotion state. Every would-fire event records only:

- launcher/run/constraint IDs and hashes, not raw sensitive prompt text;
- constraint kind/effect;
- missing/invalid evidence reason;
- whether the launch later used a workaround;
- human label: true unsupported claim, legitimate directive, valid but stale fact, parser error, or false fire;
- cost: parse time, probe count, tokens added, downstream tool failures avoided or introduced.

Promotion must be based on labeled precision, not the number of warnings. The exact promotion threshold is a policy choice, not an empirical fact. A conservative owner-selectable rule is: do not enter enforce mode until the known incident is caught, every known-present legitimate directive/control passes, and a labeled shadow set contains no high-impact false block. This workspace has measured more than 12 false fires from text-without-meaning guards, including one that told an agent to discard a successful result (`bundle/inputs/INPUT-known-harness-defects.md:9-22,52-82`). That history makes zero observed high-impact false blocks more important than high nominal recall.

The configuration-only rollout is **very likely (80-90%)** to avoid new user-visible false blocks during shadow mode because the installed `stage()` implementation logs shadow verdicts and returns success (`bundle/agents/harness/modules.py:389-417`); effective live-mode resolution is **UNVERIFIED until the experiment “launch one synthetic unsupported constraint under each configured mode and inspect both host verdict and shadow sink” is run**.

## Anti-overfit gate

The design passes the anti-overfit gate:

- It rides the installed `PreToolUse` Task, `SubagentStart`, `SubagentStop`, dispatcher, ledger, and staging buses (`bundle/agents/harness/registration.py:17-53,64-72`; `bundle/agents/harness/adapters.py:116-145`; `bundle/agents/harness/modules.py:389-417,2331-2396`).
- It adds no second orchestration runtime.
- It adds no vector database or knowledge graph.
- It adds no durable-execution engine.
- It adds no trained critic or general LLM judge.
- It adds no observability SaaS or guardrail framework.
- It verifies a small, high-blast-radius boundary once at fan-out producer time.
- It deliberately abstains on arbitrary prose truth.

The radical alternative—replacing free-form launcher preambles with a typed renderer—is justified because evolution by adding another regex hook would reproduce the measured architectural defect. This is radical only at the prompt-construction boundary; operationally it remains a small module on the existing bus.

## Alternatives considered and rejected

### Regex for “blocked,” “unavailable,” “must use PowerShell,” or similar phrases

Rejected. Four independent guards in this workspace have already confused use with mention, ignored negation, and matched failure-looking field names inside successful results (`bundle/inputs/INPUT-known-harness-defects.md:9-22,52-82`). A bug report about this incident would self-trigger. Pattern tuning cannot fix a missing semantic role discriminator (`:39-50`).

### LLM critic over every launcher prompt

Rejected. It adds cost per prompt, produces another fallible prose verdict, and offers no calibrated false-positive rate. The D02 audit claim warns that autonomous critics can hallucinate bugs and that acceptance should remain executable or human-grounded (`bundle/inputs/audit-findings/D02.md:47-53`). Even if a model critic caught this example, it would not provide the low false-positive deterministic boundary required here.

### Majority vote among children

Rejected. All children share the same prompt lineage, so repetition is correlated. The single-signal rule explicitly says N subagents reading the same stale input remain one lens (`bundle/claude/rules/common/single-signal-verification.md:34-37`). The fan-in contract says specific probes beat agent count (`bundle/claude/rules/common/fan-out-contract.md:76-77`).

### Probe every factual sentence

Rejected. It is expensive, often impossible, and would cause side effects. The narrow design probes only operational facts at the moment they change action. Arbitrary prose remains outside scope and must use task-native evidence mechanisms.

### Ban PowerShell here-strings

## Failure modes of the proposed guard

1. **Bypass:** a manual or unmigrated launcher can send free-form facts. Mitigation: protect registered high-fan-out launchers first and report migration coverage; do not claim global coverage.
2. **Misclassification:** an author can label a host fact as a user directive. Mitigation: resolve the referenced current user-turn span/hash; no source, no directive authority.
3. **Receipt laundering:** an unrelated green command can be cited. Mitigation: bind tool, target, decision, timestamp, and invariant; do not accept broad receipt class or positive prose.
4. **Misleading real evidence:** two independent detectors can still share a hidden failure or both be wrong. Mitigation: preserve scope and contradiction path; never promise truth.
5. **Staleness:** a formerly correct constraint changes. Mitigation: explicit observation/expiry time and decision-time re-probe.
6. **Prompt injection into task prose:** an external document can claim a tool is blocked. Mitigation: only the generated constraint block has operational authority; ordinary task/source prose cannot mint an effect.
7. **Fail-open ambiguity:** hook crashes could allow an unsupported launch. Mitigation: shadow telemetry first; in enforce mode, protected launcher schema validation may fail closed at the launcher boundary while the shared generic dispatcher remains fail-open. This policy choice requires owner approval because it changes availability.
8. **False blocks from missing telemetry:** a true fact with an unavailable receipt is still unsupported. The correct verdict is `UNKNOWN/NEEDS_EVIDENCE`, not “false.” The UI/message must say that precisely.
9. **Over-instrumentation:** manifests grow into bureaucracy. Mitigation: only operational constraints, compact IDs, shared receipts, and no re-probe unless action changes.

## What “done” means for this guard

The guard is not done when code exists or tests pass. It is done only when all of the following have receipts:

- the historical incident payload is caught before fan-out;
- quoted/negated prose controls remain silent;
- legitimate owner directives and real scoped denials pass;
- a 15-child replay produces one producer verdict and preserves a child contradiction;
- shadow precision, accepted-case error, cost per claim, and catch fraction are reported on a holdout set;
- enforcement is enabled only after the owner-selected precision threshold is met;
- bypass/migration coverage is displayed so protected coverage is not mistaken for universal truth detection.

Claiming that this eliminates fabrication would remain prohibited even after all checks pass.
