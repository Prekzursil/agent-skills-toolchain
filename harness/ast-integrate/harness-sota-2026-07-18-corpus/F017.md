# F017 — Frontier research: sandboxing and containment for autonomous agents

Date: 2026-07-19  
Unit: F017  
Scope: containment of autonomous coding/research agents on the owner's Windows 11 / PowerShell 7 / Git Bash harness, including Claude Code, Codex, child processes, MCP servers, credentials, network, resource exhaustion, and the harness control plane. This is research and design, not a configuration change.

## Bottom line

The frontier does **not** support replacing this harness with an elaborate “agent security platform.” The best-supported architecture is much smaller: put every model-generated process inside an OS-enforced, default-deny boundary; keep the control plane and credentials outside its writable/readable set; default network to off; expose narrow capabilities only for the duration of the task; bound the whole process tree; and continuously execute known escape canaries. This is the 2026 agent-specific form of fail-safe defaults, complete mediation, least privilege, and economy of mechanism from Saltzer and Schroeder’s original protection principles ([paper text](https://denali.cs.washington.edu/relwork/papers/saltzer.html), [DOI metadata](https://www.ojp.gov/ncjrs/virtual-library/abstracts/protection-information-computer-systems)).

The harness’s checked-in/unpacked configuration points in the opposite direction:

* Claude user settings allow the general `Bash`, file, web, task, and many MCP tool families (`/local_disk0/codexwork/bundle/claude/settings.json:26-63`), set `defaultMode` to `bypassPermissions` (`:70-71`), and add both entire `C:` and `D:` drives (`:72-75`). This establishes configuration intent, not effective runtime enforcement. Whether Claude’s separate Bash sandbox is enabled in a local or managed scope is **UNVERIFIED; the experiment that settles it is `/sandbox` → resolved Config plus filesystem/network/Unix-socket canaries in a disposable repository**.
* Codex explicitly sets `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`/local_disk0/codexwork/bundle/codex/config.toml:6-8`). The same file selects the preferred native Windows sandbox implementation, `elevated` (`:459-460`), but `danger-full-access` removes the sandbox boundary. Effective runtime behavior is **UNVERIFIED; the experiment that settles it is `codex /status`, `codex sandbox windows` canaries, and an independent check of `CODEX_HOME/.sandbox/sandbox.log`**.
* This is a high-exposure harness: the distilled corpus records 108,121 Bash calls, 19,181 PowerShell calls, and 6,222 Glob calls (`/local_disk0/codexwork/bundle/inputs/corpus.json:12-20`, `:36-44`, `:76 onward`). Its `_meta` says 10.62 GB and 1,564,084 transcript lines were processed with zero files failed and one bad line (`:2-10`). Containment therefore covers a materially exercised attack surface, rather than a hypothetical capability.

The most valuable immediate move is a controlled conversion from “model judgment is the boundary” to “the kernel is the boundary.” It is **very likely (80-90%)** to reduce the blast radius of accidental or injected commands because both vendors document OS enforcement across spawned commands, the current bundle requests full access, and the established security mechanisms deny operations independently of the model ([Claude sandbox](https://code.claude.com/docs/en/sandboxing), [Codex approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)). The range is not higher because native-Windows compatibility with this owner’s PowerShell-heavy toolchain and broad MCP estate (`/local_disk0/codexwork/bundle/claude/settings.json:47-60`) has not been measured.

## Method and evidence standard

I prioritized kernel/vendor documentation, standards, peer-reviewed papers, maintained repositories, and reviewed advisories. Vendor architecture claims establish what a mechanism is designed to do; they do not establish that this particular installation is configured correctly or that the mechanism has no escape. A repository README labeled alpha/beta/research preview is evidence of publication, not operational proof.

The research distinguishes:

* **Containment**: what a compromised or mistaken process is technically able to read, write, signal, execute, connect to, or exhaust.
* **Authorization**: whether a requested action is within the owner’s intent. A sandbox can allow an out-of-scope deletion inside the workspace; an approval classifier can approve a command that then escapes a weak sandbox. Both layers matter, but they solve different problems.
* **Isolation strength**: application sandbox / OS primitives, shared-kernel container, application kernel (gVisor), and hardware-virtualized VM are not interchangeable boundaries.
* **Data plane versus control plane**: repository source and generated output are data; hooks, settings, skills, MCP definitions, credentials, shell startup, executable search paths, and Git metadata can change what later runs execute and therefore belong to the control plane.

A local tooling dead end is relevant to reproducibility: `jq` was unavailable on this Linux job node (`/bin/bash: jq: command not found`), so corpus facts used here were read directly from the formatted JSON with `head`/line inspection. I did not install anything. The Windows subject was read only from `/local_disk0/codexwork/bundle`; no claim below depends on probing the unavailable live Windows host.

# 1. Established

## 1.1 Model instructions and command-pattern guards are not security boundaries

The established security properties come from mediation outside the potentially compromised program. Saltzer and Schroeder define fail-safe defaults, complete mediation, separation of privilege, and least privilege; a prompt that says “do not read secrets” is none of those because the same agent interpreting untrusted input also decides whether to comply ([original paper text](https://denali.cs.washington.edu/relwork/papers/saltzer.html)). Linux’s seccomp documentation is equally explicit: syscall filtering reduces kernel surface but “isn’t a sandbox”; policy and information flow require other hardening and an LSM ([kernel seccomp documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html)).

The owner’s live defects provide unusually direct local evidence against lexical command guards. Four independent detectors confused mentions with uses, including a tool sentinel that interpreted a successful result’s field name as failure (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:9-22`, `:54-82`). A command denylist therefore must not be promoted into the containment boundary. It remains useful as defense-in-depth and UX, but OS access control must decide whether the operation succeeds.

Agent-specific empirical work points the same way, but newer preprints belong below the “established” threshold. The settled point does not require those papers: discretionary model behavior and string matching cannot provide complete mediation; an OS boundary can.

## 1.2 Filesystem and network controls are jointly necessary

A filesystem-only sandbox can still exfiltrate every readable secret. A network-only sandbox can still plant persistence in shell startup, an executable on `PATH`, agent settings, hooks, or source that a later trusted process executes. Anthropic’s current documentation explicitly states this two-sided dependency and warns that widening an `allowWrite`, domain, or excluded-command exception can undo the other side ([Claude sandbox scope and limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)).

The established safe default is therefore:

1. deny reads outside task inputs and required system/runtime libraries;
2. deny writes outside a disposable workspace and session temp;
3. deny outbound and inbound network;
4. add the narrowest exception only when the task cannot proceed;
5. remove it after the phase that needs it.

Codex implements this separation directly: `workspace-write` limits writes to the workspace and keeps command network off unless enabled; network policy is a separate control applying to spawned programs and subprocesses ([Codex network access](https://learn.chatgpt.com/docs/agent-approvals-security#network-access)). Claude’s Bash sandbox similarly applies the OS boundary to the command and children, while permission rules decide whether each tool is invoked ([Claude sandbox](https://code.claude.com/docs/en/sandboxing)).

## 1.3 The boundary must cover descendants and non-shell capability paths

Wrapping only the visible shell executable is insufficient if grandchildren, service brokers, Unix sockets, COM/Apple Events, Docker, or a tool server act outside the boundary. Windows Job Objects manage a process group as a unit, normally inherit children, impose process/time/memory/CPU limits, and can kill the tree when the final job handle closes ([Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)). Linux Landlock restrictions and seccomp filters inherit to descendants; Landlock restrictions can only become tighter after enforcement ([kernel Landlock userspace API](https://docs.kernel.org/userspace-api/landlock.html)).

Vendor documentation also establishes important coverage gaps:

* Claude’s OS sandbox covers Bash subprocesses. Built-in Read/Edit/Write use Claude’s permission system, computer use controls the real desktop, and environment variables are inherited unless scrubbed ([Claude sandbox scope](https://code.claude.com/docs/en/sandboxing#scope)).
* The optional Linux seccomp layer is required to block Unix-domain sockets; allowing Docker’s socket effectively grants host control ([Claude sandbox limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)).
* MCP tools are arbitrary external actions, not shell children. The MCP specification says tool annotations are untrusted hints unless the server is trusted and clients must not base tool-use security decisions on annotations from untrusted servers ([MCP schema](https://modelcontextprotocol.io/specification/2025-11-25/schema), [tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)).

Consequently, “Bash is sandboxed” does not establish “the agent is contained.” Every capability path needs its own hard boundary or a least-privilege credential/API boundary.

## 1.4 Control-plane files must be immutable to the workload

A sandbox that can modify its next-run policy is not durable containment. This is not theoretical: reviewed advisory CVE-2026-25725 documents that Claude Code versions before 2.1.2 allowed code inside the bubblewrap sandbox to create a missing `.claude/settings.json`, injecting persistent `SessionStart` hooks that later ran with host privilege ([GitHub reviewed advisory GHSA-ff64-7w26-62rf](https://github.com/advisories/GHSA-ff64-7w26-62rf)). The fixed Claude sandbox now protects settings at every scope and resolves symlink targets in v2.1.210+ ([Claude limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)). Codex `workspace-write` recursively protects `.git`, `.agents`, and `.codex`, including a resolved Git-dir pointer ([Codex protected paths](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)).

The general, established rule is broader than those product-specific lists: agent settings, hooks, skills, MCP launch definitions, shell profiles, credential stores, executable directories, package-manager configuration, Git metadata, and trusted caches must be read-only or absent. A repository-local configuration supplied by untrusted source must never be allowed to widen its own sandbox. Anthropic explicitly warns that writable shell configuration or `PATH` executables create cross-context code execution and that project-local configuration must not enable Apple Events ([Claude security limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)).

## 1.5 Credentials should be absent, not merely “protected by policy”

If a token is in a process environment, readable file, credential helper, browser profile, or reachable broker socket, it is inside the blast radius. Claude documents that Bash children inherit the parent environment by default and provides credential masking/unsetting plus `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` ([Claude scope](https://code.claude.com/docs/en/sandboxing#scope)). Codex cloud’s two-phase model gives setup access to secrets, then removes them before the agent phase, which is offline by default ([Codex approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)). GitHub similarly withholds secrets and gives a read-only token to untrusted fork PR workflows; it warns that executing untrusted checked-out code with privileged secrets produces “pwn requests” ([GitHub `pull_request_target` security](https://docs.github.com/en/actions/reference/security/securely-using-pull-request-target)).

For MCP, token passthrough is explicitly forbidden; servers must validate audience and use a distinct downstream token, because passthrough enables confused-deputy attacks and erases accountability ([MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization), [MCP security practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)).

This establishes a robust ordering: no credential; then short-lived, audience-bound, minimum-scope credential; then a broker that attaches the credential only to an approved destination; ambient long-lived credentials last and unsuitable for untrusted execution.

## 1.6 Domain allowlists are useful but are not general information-flow control

Outbound deny-all is a strong and simple control. A domain allowlist is weaker: an allowed multi-tenant service can itself be an exfiltration sink, and hostname-based proxy decisions do not necessarily authenticate the ultimate destination. Anthropic explicitly warns that allowing broad `github.com` creates exfiltration paths and that its non-terminating TLS proxy can be susceptible to domain fronting; stronger requirements need a TLS-terminating inspecting proxy ([Claude network limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)).

This does not make allowlists useless. It means their guarantee is “traffic is limited to these destinations under the proxy’s resolution semantics,” not “private data cannot leave.” A package registry, Git host, paste endpoint, issue API, DNS, localhost daemon, or shared cloud domain may be both legitimate and an exfiltration channel. Separate setup/offline phases remove much of this ambiguity.

## 1.7 Shared-kernel containers reduce risk but are not the strongest hostile-code boundary

Namespaces, capabilities, seccomp, AppArmor/SELinux, read-only mounts, a non-root UID, and cgroups are established container hardening layers. Docker’s default seccomp profile blocks roughly 44 of 300+ syscalls and its documentation advises not disabling it ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)). NIST SP 800-190 catalogs container-image, registry, orchestrator, container, and host risks and recommends container-specific hardening ([NIST SP 800-190](https://csrc.nist.gov/pubs/sp/800/190/final)).

But a conventional container still shares the host kernel. Microsoft explicitly does not treat process-isolated Windows or Linux containers as a robust security boundary for hostile multi-tenant workloads and recommends hypervisor-isolated containers/dedicated VMs for that threat model ([Microsoft container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security)). The Linux kernel also warns that untrusted user namespaces expose resource-abuse surface and recommends memory cgroups ([kernel user namespaces and resource control](https://docs.kernel.org/admin-guide/namespaces/resource-control.html)). “Runs in Docker” is therefore not synonymous with “safe to execute adversarial native code.”

For this single-owner local harness, a correctly configured native application sandbox can be a proportionate first boundary. For hostile third-party binaries, multi-tenant service workloads, kernel-exploit research, or malware analysis, a hardware-virtualized boundary is the established stronger tier.

## 1.8 VM/microVM isolation is established; universal superiority is not

Windows Sandbox uses Hyper-V hardware virtualization and a separate kernel, is disposable, and can disable networking and mount a host folder read-only ([Microsoft Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)). Firecracker combines KVM microVMs with a reduced device model and a host-side jailer; its NSDI 2020 paper reports production use in AWS Lambda/Fargate at millions of workloads and trillions of requests per month ([USENIX paper](https://www.usenix.org/conference/nsdi20/presentation/agache), [Firecracker project](https://firecracker-microvm.github.io/)). Kata Containers similarly puts an OCI workload in a lightweight VM as a second isolation layer ([Kata architecture](https://github.com/kata-containers/kata-containers/blob/main/docs/design/architecture/README.md)).

What is established is the stronger separation from the host kernel. What is not established is that a microVM is always safer in every deployment: device emulation, host brokers, shared folders, vsock, image supply chain, and hypervisor bugs remain attack paths. gVisor’s security model correctly cautions that virtualization hardware alone does not prove security and that side channels remain ([gVisor security model](https://gvisor.dev/docs/architecture_guide/security/)).

## 1.9 Application kernels and capability runtimes are real, bounded tools

gVisor interposes a memory-safe Go application kernel (Sentry) between workload and Linux, using host namespaces/seccomp as a second layer. Its goal is to require compromise of both disjoint layers for a host escape; it is deployed in services including Google Cloud Run, but has syscall, device, `io_uring`, and in-sandbox resource-limit compatibility gaps ([gVisor introduction](https://gvisor.dev/docs/architecture_guide/intro/), [compatibility](https://gvisor.dev/docs/user_guide/compatibility/)). That is established engineering, not merely a paper, but it still requires task-specific compatibility testing.

WebAssembly provides language-level memory isolation, and WASI supplies I/O only through capabilities imported by the host ([WebAssembly security](https://webassembly.org/docs/security/), [WASI capabilities](https://github.com/WebAssembly/WASI/blob/main/docs/Capabilities.md)). It is a strong fit for narrow, portable plugin computations. It is not a drop-in replacement for an unrestricted coding agent that must run arbitrary native compilers, package scripts, browsers, Git, PowerShell, and OS tooling.

## 1.10 Resource containment is part of containment

Filesystem and network policies do not stop fork bombs, memory exhaustion, disk fill, endless subprocesses, or runaway CPU. Windows Job Objects can cap process count, memory/working set, CPU/time, and terminate a tree ([Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [limit structure](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)). Linux cgroup v2 provides CPU, memory, PID, and I/O controllers ([kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)). Firecracker also exposes storage/network rate limiting ([Firecracker](https://firecracker-microvm.github.io/)).

Timeout alone is incomplete: a parent may exit while descendants persist, and wall-clock time does not constrain memory, process count, or disk. Whole-tree termination and quotas are established containment controls.

# 2. Promising but unproven

Items in this section are published or deployed somewhere, but their agent-specific benefit, compatibility, or security property is not established for this owner. Each claim carries the required confidence band and the experiment that would move it.

## 2.1 Native Claude sandbox on WSL2 as the default Claude execution lane

It is **likely (55-80%)** that running Claude Code inside WSL2 with strict built-in sandboxing would provide the best near-term Claude boundary on this Windows host. Evidence: Anthropic officially supports macOS, Linux, and WSL2, uses bubblewrap plus a proxy and optional seccomp, can fail closed, and does not support native Windows in Claude Code’s integrated sandbox ([Claude docs](https://code.claude.com/docs/en/sandboxing)). The confidence is capped because this harness deliberately enables a PowerShell tool and Windows paths (`settings.json:5-7`), while Anthropic documents that sandboxed WSL2 commands cannot launch Windows binaries through `/mnt/c/` because the host-interop Unix socket is blocked.

**UNVERIFIED; experiment:** clone three representative tasks into WSL2-native ext4 storage: a pure code task, a PowerShell-heavy Windows task, and an MCP-heavy task. Enable `sandbox.enabled`, `failIfUnavailable`, and `allowUnsandboxedCommands: false`; run correctness, latency, tool-error, and containment canaries. Compare against the current lane. A single happy-path demo is not sufficient.

## 2.2 Anthropic Sandbox Runtime’s native Windows alpha

It is **roughly even (45-55%)** that `@anthropic-ai/sandbox-runtime`’s Windows alpha can become a practical containment wrapper for selected local tools or MCP servers before Claude itself ships native integration. Evidence: the maintained research-preview repository describes a dedicated local SID, restricted token, Job Object, NTFS ACEs, and WFP egress fence, including crash recovery and explicit limitations ([repository Windows model](https://github.com/anthropic-experimental/sandbox-runtime#Windows-alpha)). Counter-evidence: it is explicitly alpha/research preview; glob protection is expanded only at initialization, newly created matching paths are not covered; user-profile tools often become unreadable; and the separate account changes compatibility semantics.

**UNVERIFIED; experiment:** in a disposable Windows VM, execute a canary matrix for ACL rename/delete bypass, symlinks/junctions, new-path-after-init behavior, alternate data streams, task scheduler/COM/BITS surrogate spawning, WFP direct-connect bypass, IPv6, localhost brokers, child trees, and crash recovery. Then run 100 real corpus-derived commands. Do not install it on the owner’s live machine before this experiment.

## 2.3 gVisor for remote/high-risk agent jobs

It is **likely (55-80%)** that a gVisor-backed remote sandbox is a useful middle tier between a shared-kernel container and a microVM for Linux-native coding jobs. Evidence: gVisor adds a disjoint application-kernel layer and is production-deployed, while documenting compatibility gaps and host-cgroup requirements ([security introduction](https://gvisor.dev/docs/architecture_guide/intro/), [compatibility](https://gvisor.dev/docs/user_guide/compatibility/)). The confidence is capped because this owner’s dominant environment is native Windows/PowerShell and no representative workload benchmark exists.

**UNVERIFIED; experiment:** replay a stratified set of Bash/PowerShell-equivalent, browser, compiler, package-manager, Git, test, and MCP subprocess workloads under `runsc`; measure success delta, p50/p95 latency, syscall failures, and containment canaries. Compare to a hardened runc container and a microVM.

## 2.4 Firecracker/Kata or Hyper-V microVM per high-risk task

It is **very likely (80-90%)** that a correctly configured per-task microVM would reduce host-kernel escape exposure relative to a shared-kernel container for intentionally hostile native code. Evidence: independent-kernel isolation is the explicit Microsoft recommendation for hostile multi-tenancy, and Firecracker has peer-reviewed production evidence ([Microsoft container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security), [Firecracker NSDI](https://www.usenix.org/conference/nsdi20/presentation/agache)).

It is only **unlikely (20-45%)** that building a per-task microVM service is currently the best default for this personal harness. Evidence: native Codex/Claude boundaries already ride existing execution paths; Windows Sandbox permits only one instance at a time; microVM orchestration adds images, patching, file transfer, state, credential brokerage, and diagnostics. No measured adversarial workload or sandbox escape rate justifies that operational surface yet.

**UNVERIFIED; experiment:** first classify workloads. Only if native canaries fail or the owner intentionally runs hostile binaries should a disposable Hyper-V/Firecracker proof compare boot time, parallel density, Windows tool compatibility, file-sync correctness, and recovery with the native profile.

## 2.5 WASI for third-party skill helper code

It is **likely (55-80%)** that WASI components could safely host a narrow future class of deterministic skill helpers—parsers, format converters, validators—using explicit preopened files and no ambient network. Evidence: Wasm memory isolation and WASI capability imports are designed for precisely this narrow authority model ([WebAssembly security](https://webassembly.org/docs/security/), [WASI capabilities](https://github.com/WebAssembly/WASI/blob/main/docs/Capabilities.md)).

It is **very unlikely (5-20%)** that WASI can replace the general harness execution lane in the near term. Evidence: the harness uses PowerShell, Bash, browsers, Git, native package managers, arbitrary language runtimes, and MCP servers, which depend on broad POSIX/Windows behavior not provided by portable WASI.

**UNVERIFIED; experiment:** select one dependency-free validation helper and one filesystem parser, compile to a pinned Wasmtime/WASI target, grant one input and one output directory, and compare compatibility/latency plus host-read/network canaries. Do not port orchestration logic.

## 2.6 Destination-scoped credential injection

It is **likely (55-80%)** that a trusted egress broker which injects a short-lived credential only for a specific host/path/method would materially reduce token theft compared with inherited environment variables. Evidence: the MCP spec forbids token passthrough and requires audience binding; Claude’s experimental TLS termination supports credential masking/substitution; Codex cloud removes setup secrets before the agent phase ([MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization), [Claude sandbox](https://code.claude.com/docs/en/sandboxing), [Codex approvals](https://learn.chatgpt.com/docs/agent-approvals-security)).

It remains unproven here because a TLS-terminating broker adds certificate management, protocol compatibility, logging sensitivity, and a valuable privileged component. **UNVERIFIED; experiment:** test one low-risk read-only API with a five-minute audience-scoped token; attempt to read it from environment/files/process listings and replay it to another audience; inspect logs for leakage. This is not an immediate harness-wide build recommendation.

## 2.7 Taint-aware capability reduction after reading untrusted content

It is **roughly even (45-55%)** that dynamically removing write/network capabilities after an agent consumes untrusted web, issue, email, or repository instructions will reduce prompt-injection impact without unacceptable task breakage. Evidence: MCP maintainers describe session-level risk as the composition of private-data access, untrusted content, and exfiltration-capable tools, and note that annotations could inform host-layer restrictions but are not enforcement ([MCP tool-annotation analysis](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)). Modal exposes an alpha API for tightening a running sandbox’s egress, showing feasibility but not efficacy ([Modal sandbox networking](https://modal.com/docs/guide/sandbox-networking)).

This is a post-cutoff 2026 frontier idea, not established practice. **UNVERIFIED; experiment:** replay prompt-injection cases with a deterministic host state machine: after first untrusted-source read, remove side-effecting MCP tools and outbound shell network; measure attack success and legitimate-task completion. Do not ask the model to self-label taint.

## 2.8 New agent-security benchmarks

It is **likely (55-80%)** that realistic, runtime-observed benchmarks will reveal authorization/containment failures missed by static command rules. Evidence: the May 2026 OverEager-Gen preprint reports paired consent variants, dual-channel tool-call observation, and framework-level differences; the June 2026 GitInject preprint executes real CI workflows rather than simulating tools ([OverEager preprint](https://arxiv.org/abs/2605.18583), [GitInject preprint](https://arxiv.org/abs/2606.09935)). These are post-cutoff preprints and therefore lower-confidence than peer-reviewed or independently replicated work.

**UNVERIFIED; experiment:** import only their public scenarios relevant to filesystem scope, credentials, persistent config, and network exfiltration; reproduce results on pinned Claude/Codex versions; manually inspect a stratified sample and require two independent observation channels. Do not adopt headline rates as facts about this harness.

# 3. Hype, and the tell that gives it away

## 3.1 “Secure AI sandbox” with no threat model

**Tell:** the page says “enterprise-grade,” “secure,” or “zero trust” but does not name the attacker, kernel/hypervisor boundary, mount semantics, network enforcement point, credentials, escape path, resource limits, or update process. A GitHub README and star count demonstrate availability and interest, not containment. E2B and numerous 2026 “agent sandbox” repositories publish useful APIs, but their top-level claims alone do not establish an independently evaluated boundary ([E2B repository](https://github.com/e2b-dev/E2B), [Agent-Sandbox repository](https://github.com/agent-sandbox/agent-sandbox)).

## 3.2 “It runs in Docker, therefore it is safe”

**Tell:** `--privileged`, host PID/network, broad bind mounts, root, the Docker socket, or `seccomp=unconfined` appears in the quickstart. The AgencyBench repository, for example, launches its visual sandbox with `--security-opt seccomp=unconfined`; that may be acceptable for benchmark automation but voids a key hardening layer and cannot substantiate hostile-code containment ([AgencyBench repository](https://github.com/GAIR-NLP/AgencyBench)). Microsoft explicitly rejects a shared-kernel container as the robust boundary for hostile multi-tenancy ([container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security)).

## 3.3 “A command denylist prevents dangerous actions”

**Tell:** the policy reasons over command strings, shell tokens, or regexes without controlling syscalls/objects and every alternate interpreter. The kernel’s own documentation says seccomp alone is not a sandbox; a shell denylist is weaker still ([seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)). The local live defect where prose mentions triggered destructive-command guards is a direct harness-specific falsification (`INPUT-known-harness-defects.md:9-50`).

## 3.4 “Human approval makes it safe” or “an AI reviewer makes it autonomous and safe”

**Tell:** the reviewer sees a friendly command summary but not effective paths, inherited credentials, child behavior, network destinations, or persistent effects. Approval is authorization UX, not containment. Codex’s own documentation says auto-review does not change the sandbox boundary; it only reviews actions that already require escalation ([Codex auto-review](https://learn.chatgpt.com/docs/agent-approvals-security#automatic-approval-reviews)). Approval fatigue is a reason to make safe in-boundary actions automatic, not a reason to remove the boundary.

## 3.5 “Domain allowlist means no exfiltration”

**Tell:** the allowlist contains multi-tenant wildcard domains, permits raw IP/UDP/DNS, trusts client-supplied hostnames without TLS termination, or leaves localhost/Unix sockets open. Anthropic expressly documents domain-fronting and broad-GitHub risks ([Claude limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)). The honest claim is bounded egress, not noninterference.

## 3.6 “Ephemeral means nothing persists”

**Tell:** the system omits host bind mounts, shared caches, Git credentials, package caches, volumes, control-plane files, artifact upload, and external APIs from the persistence story. The Claude settings injection advisory demonstrates persistence through a configuration file even when the immediate command was sandboxed ([GHSA-ff64-7w26-62rf](https://github.com/advisories/GHSA-ff64-7w26-62rf)). A disposable VM with a writable host share is not disposable from the host’s perspective.

## 3.7 “MicroVM” as a magic word

**Tell:** no account of the host-side VMM, device emulation, vsock/9p/shared folders, image provenance, metadata service, or jailer. Firecracker’s credibility comes from its deliberately reduced devices, jailer, peer-reviewed paper, and production history—not the substring “microVM” ([Firecracker](https://firecracker-microvm.github.io/), [NSDI paper](https://www.usenix.org/conference/nsdi20/presentation/agache)).

## 3.8 “Wasm can sandbox the whole coding agent”

**Tell:** a diagram shows capability-safe Wasm but silently moves native compilers, browsers, Git, package scripts, or host calls into a privileged embedding API. Wasm protects the module only relative to what the embedder imports; the host API remains the authority ([WebAssembly security](https://webassembly.org/docs/security/), [WASI capabilities](https://github.com/WebAssembly/WASI/blob/main/docs/Capabilities.md)).

## 3.9 Security-by-telemetry

**Tell:** extensive dashboards are offered without a deterministic blocking boundary, known-positive detector controls, or escape tests. Telemetry can diagnose a breach; it does not prevent one. This harness’s hook telemetry is itself currently unmeasurable in transcripts and its root cause is explicitly UNVERIFIED (`INPUT-known-harness-defects.md:133-147`). Adding observability SaaS would violate the anti-overfit gate and would not repair containment.

It cannot prevent malicious changes to ordinary source inside the authorized workspace, so review remains required.

## A4 — make offline execution the default and split dependency acquisition — CONFIG (settings/JSON only)

Use a two-phase workflow already demonstrated by Codex cloud:

1. trusted setup obtains pinned dependencies with network and no production/user secrets;
2. autonomous execution begins from the prepared environment with outbound network off;
3. publishing, pushing, emailing, issue creation, deployment, or other external mutation happens through a separate, explicit capability after review.

Where live research is the task, prefer built-in web/search tools that return data without granting arbitrary child-process egress, and keep side-effecting MCP/app tools unavailable. Exact-domain proxies are an exception for tasks whose command genuinely needs a remote host, not the baseline.

Expected effect is **very likely (80-90%)** to eliminate simple shell exfiltration during ordinary coding runs because no route exists, while preserving builds from a prepared cache. It is **likely (55-80%)** to reduce task success for dependency-discovery work unless setup inputs are well prepared; corpus replay will determine the trade.

**Verification:** known-allowed offline build/test; blocked HTTPS, raw TCP, UDP/DNS, IPv4/IPv6, localhost, named pipe/Unix socket; no proxy variables or credentials in execution environment; independent packet/firewall log plus client failure. A domain allowlist test must include an allowed host, forbidden host, direct IP, and allowed multi-tenant upload attempt.

**Anti-overfit gate: PASS.** It is configuration and task phasing on the existing tool bus, not a broker daemon.

## A5 — remove ambient credentials from agent processes and narrow MCP authority — CONFIG (settings/JSON only)

For Bash/PowerShell children, start from a minimal allowlisted environment; explicitly unset cloud, GitHub, package registry, SSH agent, browser, database, and vendor tokens. Do not mount `.ssh`, `.aws`, `.azure`, `.config/gh`, browser profiles, DPAPI-exported secrets, or credential-helper sockets. Give each MCP server its own minimum-scope identity and tool allowlist; disable dead servers rather than letting the model retry them. Treat MCP annotations as UI hints, never as the authorization boundary.

The corpus records 532 Tavily extract calls with a 25.75% error rate and 135 “not connected” failures (`/local_disk0/codexwork/bundle/inputs/corpus.json:174-180`, `:9141-9148`); credential and capability pruning therefore also removes demonstrably useless attack surface. The MCP standard requires audience binding and forbids token passthrough ([MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)).

Expected effect is **very likely (80-90%)** to reduce credential theft blast radius because absent credentials cannot be exfiltrated. Compatibility impact is **likely (55-80%)** to be manageable with per-task capability enablement; the broad 93-server estate makes exact migration cost uncertain.

**Verification:** a secret-canary matrix across environment, filesystem, process command lines, Git credential helper, SSH agent/named pipes, browser stores, and MCP logs. Include a legitimate short-lived read-only MCP call as known-positive. Attempt token replay against a different audience. Never use real secrets in the test.

**Anti-overfit gate: PASS.** It is environment/MCP configuration on existing buses. It explicitly avoids building a secrets broker in the first phase.

## A6 — add a mechanically independent containment conformance suite — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Build a small, provider-neutral script invoked at session start after upgrades/config changes and on demand. It should generate disposable canaries, run a fixed matrix, and emit machine-readable pass/fail evidence. Minimum dimensions:

* allowed workspace read/write/execute (known-positive detector controls);
* denied host/control-plane read/write/rename/delete and symlink/junction aliases;
* child and grandchild inheritance;
* IPv4, IPv6, DNS/UDP, direct IP, forbidden hostname, localhost, named pipe/Unix socket;
* environment and credential-helper absence;
* process-count, memory, wall-time, and tree-kill behavior;
* policy self-modification and next-session persistence;
* built-in file tools and local MCP process coverage, not only shell.

For every “blocked” verdict require two mechanically independent signals: e.g. operation error plus unchanged hash/ACL, client failure plus firewall/packet log, timeout plus empty descendant-process query. Each detector first proves it can observe a known-present/allowed control. This directly incorporates the owner’s D2 lesson (`INPUT-known-harness-defects.md:111-129`).

It is **very likely (80-90%)** that this suite will catch fail-open, partial-upgrade, path-alias, and missing-dependency regressions earlier than documentation review, because the Codex Windows docs themselves describe partial/broken sandbox state and sandbox logs, and Claude defaults to fail-open unless configured otherwise ([Codex Windows troubleshooting](https://learn.chatgpt.com/docs/windows/windows-sandbox), [Claude failIfUnavailable](https://code.claude.com/docs/en/sandboxing)).

**Anti-overfit gate: PASS.** One small test script rides SessionStart/skill hooks, stores local evidence, and adds no runtime. It tests the kernel boundary instead of adding a second guard framework.

## A7 — bound every agent process tree — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Wrap provider-launched shell/MCP subprocess trees in Windows Job Objects with `KILL_ON_JOB_CLOSE`, active-process, memory, CPU/time limits, and accounting; use cgroup v2 equivalents in WSL2/Linux. Add a per-task disk quota or a disposable volume with a maximum size. Limits should be profile-specific—build/test tasks need more than read-only research—but finite.

It is **likely (55-80%)** that a small launcher can cover shell and stdio MCP child trees without breaking the harness because both are ordinary process launches and Job Objects inherit children by default. It is only **roughly even (45-55%)** that all current launchers can be nested without compatibility work: Windows documents nested-job/breakaway semantics, and some software already places itself in a Job Object ([Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

**UNVERIFIED experiment:** inventory which Claude/Codex/terminal processes are already in jobs with `IsProcessInJob`; run fork-bomb, memory, disk, and orphan-child canaries in a disposable VM; confirm a normal compiler/browser test still passes. If nested-job conflicts occur, prefer provider-native limits or outer VM quotas rather than expanding the wrapper beyond ~200 lines.

**Anti-overfit gate: PASS CONDITIONALLY.** It is a small process launcher on the existing execution bus. If compatibility requires a resident scheduler/daemon, stop: that becomes BUILD-LARGE and fails the current evidence threshold.

## A8 — quarantine untrusted third-party skill/plugin helper execution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Do not allow an installed skill/plugin to confer ambient authority merely because its Markdown was loaded. Treat executable helper scripts and local MCP servers as untrusted dependencies: pin source/version, run helpers through the same sandbox profile, expose only declared task paths, scrub credentials, and deny network unless explicitly required. It will not neutralize malicious natural-language instructions consumed by the model; containment limits what those instructions can accomplish. New June 2026 MalSkillBench results support the hybrid code/instruction risk but are post-cutoff preprints and **UNVERIFIED here; reproduce a small public sample to settle relevance** ([MalSkillBench preprint](https://arxiv.org/abs/2606.07131)).

**Verification:** one benign helper control; malicious fixtures attempting secret read, egress, control-plane write, path escape, and MCP tool escalation; observe both tool result and OS state. Pin fixtures and never execute them outside a disposable sandbox.

**Anti-overfit gate: PASS.** It reuses the sandbox and hook/skill launch bus. No scanner platform, trained critic, or package-security service is introduced.

## Explicit non-adoptions

These are design decisions, not omissions:

* Do **not** add a second agent orchestration runtime merely to obtain sandbox APIs. Existing Claude/Codex native buses can enforce the first boundary.
* Do **not** add a vector DB/KG, durable execution engine, trained security critic, observability SaaS, or general guardrail framework. None is needed for kernel mediation, and all are on the anti-overfit rejection list.
* Do **not** make Docker the default hostile-code boundary, expose `docker.sock`, use `--privileged`, or disable seccomp.
* Do **not** build a TLS credential-injection proxy now. The benefit is promising (§2.6), but BUILD-LARGE would create a privileged service before a single-API experiment establishes need.
* Do **not** build a microVM fleet now. Use an existing managed/Hyper-V isolation tier only for intentionally hostile workloads or after native conformance tests demonstrate a material gap. A new microVM control plane would be BUILD-LARGE and is not justified by current measurements.
* Do **not** use an LLM reviewer as the containment boundary. It can remain an authorization aid inside a kernel boundary.

This sequence is **very likely (80-90%)** to produce actionable evidence with lower overfit risk because every stage changes one boundary, runs known-positive and negative controls, and retains the existing execution bus.
