# D900 — Bench harness and regression gate

**Unit:** D900  
**Date:** 2026-07-19  
**Scope:** Design the mechanism that runs harness tasks in isolation, scores and stores them, compares two harness versions, separates noise from signal, and automatically prevents a regressing version from being promoted. This unit does not select the whole task bank, redesign individual hooks, repair the existing semantic router, install anything, or modify the subject.

## Verdict

Build a small, repository-native `bench` package around the existing Python dispatcher, pytest suite, state-root overrides, shadow-mode bus, and Git/CI tooling. A comparison is always **candidate versus a fixed blessed baseline on the same immutable task manifest**, run in interleaved matched blocks on fresh roots. Deterministic lifecycle invariants use repeated exact grading; stochastic model-in-loop tasks use paired task-level deltas, sequential sample expansion, practical-effect margins, confidence intervals, and family-wise multiplicity control. The gate has four outcomes—`PASS`, `REGRESSION`, `INCONCLUSIVE`, or `INVALID`—so infrastructure failure can never masquerade as a green result.

The design deliberately does **not** add a daemon, second agent loop, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. It rides the existing dispatcher/pytest/hook/state/CI buses. This passes the anti-overfit gate: the machinery measures the existing harness and does not become a competing harness.

This architecture is **very likely (80-90%)** to catch behavior, safety, state, provider-parity, and reliability regressions before promotion because the subject already exposes deterministic inputs, outputs, terminal records, and isolated state roots, and because each decisive case is graded through outcome plus independent state/side-effect assertions. The remaining uncertainty is model-host isolation on the owner’s Windows installation; that premise is **UNVERIFIED**, and the settling experiment is the Windows Phase-0 canary specified in §15, which runs one no-op task under redirected Claude and Codex homes and proves both hosts read only the projected config and write only beneath the trial root.

## 1. Grounding: what exists and what is missing

### 1.1 Corpus facts that determine priorities

The corpus is a high-coverage transcript distillation: 11,633 files, 10.62 GB, zero failed files, one bad line, and 32 oversized lines; its own limitation says absence is meaningful only after checking those counters (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). The bench should therefore use its counts to weight regression families, but not pretend the corpus contains replayable raw environment state.

The highest-damage observable lanes are concrete: Bash 108,121 calls at 5.98% error, PowerShell 19,181 at 10.59%, WebFetch 8,042 at 5.57%, Glob 6,222 at 13.32%, and StructuredOutput 3,694 at 22.9% (`corpus.json:13-20,39-44,71-84,103-108`). The top failure fingerprints include 568 Edit and 366 Write read-before-write failures (`corpus.json:8933-8945,9057-9076`), 294 over-strict StructuredOutput schema failures (`corpus.json:8964-8992`), 592 Glob `ENAMETOOLONG` failures (`corpus.json:8995-9006`), 232 WebFetch `ECONNREFUSED` failures (`corpus.json:9026-9041`), and a dead Tavily path with 135 “not connected” extract failures (`corpus.json:9141-9148`). Those become named metric families and defect-regression fixtures; they must not be averaged into a generic “quality score.”

The corpus’s hook detector is explicitly broken and the entire hooks section is no data (`corpus.json:13260-13264`). Therefore this bench must collect its own per-trial terminal, state, shadow, and native-output artifacts. It must never score “no hook event observed” from the corpus.

Capability use is highly skewed: the corpus lists a small set of repeatedly invoked skills and a long tail of one-use skills (`corpus.json:13265-13344`), 22 recorded agent types (`corpus.json:13346-13368`), and a broad MCP fleet (`corpus.json:13370-13463`). That supports stratifying model-in-loop tasks by capability family and dependency profile instead of treating all tasks as exchangeable.

### 1.2 Live defects become benchmark requirements

The known-defects input was produced from live operation with two independent signals per defect (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:1-5`). It requires four mechanical properties:

1. Every dangerous/benign pair must discriminate **use from mention**. Four detectors have confused prose, negation, JSON field names, or a false-valued field with actual executable behavior (`INPUT-known-harness-defects.md:9-22,52-82`). A safety fixture without its matched benign near-miss is inadmissible.
2. Every absence detector must first pass a known-positive control. Seven wrong conclusions came from unvalidated probes (`INPUT-known-harness-defects.md:111-129`). The bench itself therefore begins with positive and negative infrastructure controls and emits `INVALID`, never `PASS`, if a control fails.
3. Hook telemetry cannot be assumed present in transcripts. The symptom and the experiment that would settle the live location are stated at `INPUT-known-harness-defects.md:133-147`; isolated bench-side collection avoids depending on that open question.
4. Preambles and task manifests are evidence-bearing inputs. A fabricated Write-tool constraint propagated to about 15 agents and pushed work toward a higher-failure shell path (`INPUT-known-harness-defects.md:151-160`). The runner hashes the exact prompt, manifest, config projection, and tool policy presented to each trial.

### 1.3 The lifecycle harness already has the right seams

The shared harness normalizes provider input, runs ordered modules, emits a closed `HookResult`, and writes terminal status (`/local_disk0/codexwork/bundle/agents/harness/README.md:1-16`). `HarnessDispatcher` accepts an explicit `state_root`, normalizes a raw provider event, isolates module exceptions, stops after a block, and records elapsed time and failed modules (`dispatcher.py:235-338`). The CLI accepts provider, event, and state-root arguments; importantly, it returns exit code 0 even on caught internal failure because hooks are fail-open (`dispatcher.py:518-556`). Consequently, exit code alone is not an oracle.

The normalized input is closed and includes provider, event, session, turn, cwd, permission mode, tool name/id/input/result, assistant message, prompt, source/trigger, and agent fields (`schemas/hook-event.schema.json:5-55`). The result is also closed: status, action, reason, contexts, and optional continuation (`schemas/hook-result.schema.json:5-37`; `models.py:45-95`). The terminal record contains timestamp, terminal, provider, event, action, reason, elapsed milliseconds, and failed modules (`dispatcher.py:485-513`). These are sufficient for deterministic trace grading without a model judge.

There are 16 registered lifecycle events and explicit 2–5 second host timeouts (`registration.py:17-53`). Existing subprocess tests already redirect state, checkpoints, and recall index to a temporary root and invoke both providers (`tests/test_dispatcher_and_registration.py:267-304`). A mechanically checked count found 511 top-level pytest tests across 18 files (`rg -c '^def test_' ... | awk`, run 2026-07-19); a separately validated search found the known-present `elapsed_ms` assertions but no task-level pass/trajectory benchmark in those tests (`test_cov_dispatcher_adapters.py:270`; `test_dispatcher_mixer_breaker.py:416`). This confirms that the component foundation exists and the correlated task-level scorer does not yet live in that suite.

### 1.4 Existing “harness-bench” is not the requested bench

The current weekly component describes itself as a semantic skill-router regression net and runs only `semantic-router/eval.py`, comparing skill/MCP recall to one baseline (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/README.md:1-8`; `bench.py:1-20,55-65`). It validates only four integer fields, ignores negative-fire fields in comparison, ratchets the baseline upward, and always exits 0 (`bench.py:38-42,84-107,150-190`). Its baseline is 13/14 skill recall, 3/5 MCP recall, and 0/2 negative fires (`baseline.json:1-7`). Two independent signals establish its limited scope: its README names only the semantic router, and its executable’s sole child command is the router eval.

There is also a static interface mismatch: `bench.py` expects `eval.py --json` to return a JSON object with a `hybrid` member (`bench.py:55-65,88-96`), while the bundled `eval.py` does not parse command-line arguments and prints a human report from `main()` (`semantic-router/eval.py:209-242`). It is **almost certain (90-99%)** that these bundled files cannot exchange a valid current result, based on the caller’s `json.loads` contract and the callee’s unconditional text output. Whether the owner’s registered Windows task currently points at exactly these bundled revisions is **UNVERIFIED**; the settling experiment is `Get-ScheduledTask -TaskName ClaudeHarnessBench`, inspect its action, then run that exact action once with `BENCH_BASELINE` and `BG_DIGEST_FILE` redirected to a temporary directory and capture stdout/stderr. This finding is not a repair assignment for D900; the new bench subsumes its useful router case.

## 2. Proposed architecture

### 2.1 One thin bench package

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement each executable module below as a small, single-purpose Python file; fixtures and schemas are data. The aggregate feature is several small bus riders, not a new service or agent runtime.

```text
immutable task manifest
        │
        v
prepare baseline + candidate projections
        │
        v
fresh trial roots ──> existing pytest / dispatcher CLI / provider CLI
        │                         │
        │                         └─ native output + terminal/state/shadow/filesystem
        v
deterministic graders -> result.jsonl (one row per trial)
        │
        v
paired comparator -> comparison.json + gate.json + report.md
        │
        ├─ PASS: candidate is promotable; baseline unchanged
        ├─ REGRESSION: block promotion and preserve reproducer
        ├─ INCONCLUSIVE: expand trials; then block required lane if unresolved
        └─ INVALID: quarantine infrastructure result; never update baseline
```

The thin package is **very likely (80-90%)** to stay below the complexity at which the measurement harness becomes a second orchestration system because it invokes existing CLIs synchronously, stores append-only files, and has no scheduler, queue, database, background worker, or agent loop. Evidence is the existing dispatcher CLI and pytest seam cited in §1.3. The exact final line count is **UNVERIFIED**; the experiment is a post-implementation `cloc bench --include-lang=Python` check. If any executable module exceeds about 200 lines, split it by responsibility rather than introduce a service.

### 2.2 Four lanes, one result contract

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Manifests assign every task to exactly one lane:

| Lane | Purpose | Executor | Default repetitions | Merge behavior |
|---|---|---|---:|---|
| L0 component | Existing unit/contract/security tests | pytest | 1 complete suite | Any failure blocks; no statistical interpretation |
| L1 trace | Deterministic multi-event lifecycle/state traces | dispatcher in-process and CLI | 3 fresh roots per required cell | Exact invariant gate |
| L2 defect | Corpus/owner-correction regression fixtures with matched benign controls | dispatcher/tool fixture | 3 fresh roots | Exact invariant gate; critical cases zero-tolerance |
| L3 task | Model-in-loop owner tasks under pinned provider/model/budget | Claude or Codex CLI | 5 paired trials/version initially; sequentially 10 then 20 | Statistical/practical-delta gate |

Public suites such as Terminal-Bench are optional L4 calibration, never the local merge gate. They measure the model-plus-harness-plus-environment system and can change independently, as the 28/89 Terminal-Bench 2.1 fixes demonstrate. A fixed public-suite slice may run weekly to detect gross external validity drift, but its result is `REPORT_ONLY` unless its task/image/scorer hashes exactly match the blessed baseline.

This separation is **very likely (80-90%)** to prevent deterministic hook bugs from being hidden by stochastic task averages because L0–L2 are hard gates and L3 cannot compensate for them. Evidence is the fail-open dispatcher behavior and the corpus’s high-cost deterministic fingerprints. Whether five initial L3 trials provide useful interval width for this owner’s task mix is **UNVERIFIED**; the settling experiment is the first 20-trial baseline, from which the comparator reports interval width and recommends the smallest future initial `n` meeting the configured minimum detectable effect.

```json
  "family": "guard_precision",
  "lane": "L2",
  "severity": "critical",
  "determinism": "deterministic",
  "providers": ["claude", "codex"],
  "profiles": ["interactive", "unattended"],
  "fixture": {
    "kind": "directory",
    "path": "fixtures/destructive-prose",
    "sha256": "<64 hex>",
    "container_image": null,
    "network": "none"
  },
  "budget": {
    "wall_seconds": 15,
    "turns": 1,
    "tokens": 0,
    "tool_calls": 1,
    "retries": 0
  },
  "steps": [
    {
      "event": "PreToolUse",
      "payload_file": "event.json",
      "payload_sha256": "<64 hex>"
    }
  ],
  "oracle": {
    "required": [
      {"source": "native", "path": "$.decision", "op": "ne", "value": "block"},
      {"source": "terminal", "path": "$[-1].terminal", "op": "eq", "value": "SUCCESS:hook-pretooluse"}
    ],
    "forbidden": [
      {"source": "state_delta", "path": "$.blocked_operations", "op": "gt", "value": 0}
    ],
    "score": {"kind": "all_required_no_forbidden"}
  },
  "pair_id": "defect.use-vs-mention.real-destructive",
  "labels": ["D1", "benign", "prose"]

```

Allowed oracle sources are a closed enum: `native`, `terminal`, `shadow`, `state_before`, `state_after`, `state_delta`, `fs_before`, `fs_after`, `fs_delta`, `trace`, and `process`. Allowed operations are also closed: `eq`, `ne`, `exists`, `absent`, `contains`, `not_contains`, `matches`, `count_eq`, `count_lte`, `count_gte`, `lt`, `lte`, `gt`, `gte`, and `sha256_eq`. Regexes are anchored by default and carry an explicit engine/version.

Every critical decision must have two mechanically independent assertions. Examples: native block **and** forbidden file absent; terminal failure **and** failed-module state increment; redacted output contains placeholder **and** raw secret hash is absent from every artifact. Two regexes over the same string do not qualify.

Task admission requires a paired opposite label for classifiers (`positive`/`negative`, `malicious`/`benign`, `firing`/`non-firing`). This directly encodes the known D1 use-versus-mention defect and Anthropic’s balanced-eval guidance.

## 5. Execution and isolation

### 5.1 Preparation

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** `bench run` performs these steps synchronously:

1. Resolve baseline and candidate to immutable Git commits or content manifests. Dirty input is rejected unless `--candidate-path` is supplied; then every file is hashed and the run is marked `uncommitted`.
2. Validate task, manifest, grader, and gate schemas. Recompute every declared SHA-256.
3. Run detector controls. The positive control must be found and the negative control must remain absent. A control failure ends the run as `INVALID_CONTROL` before candidate scoring.
4. Create detached, locked worktrees under the run root for baseline and candidate. Never use or mutate the owner’s active checkout. Remove with `git worktree remove` after successful archival; retain on regression/inconclusive for reproduction. Git documents detached throwaway worktrees and explicit removal/pruning in the primary manual linked in §1.5.
5. Project each harness version into a version-specific synthetic home, using the repository installer in a dry/project mode that writes only below that trial root. Never invoke the live deploy path.
6. Materialize one fresh trial root per task/version/repetition, with no state carried between trials.
7. Randomize matched block order deterministically from `order_seed`: for each `(task, trial)`, alternate `baseline→candidate` and `candidate→baseline`. Do not run the two versions concurrently on the same host; resource contention would correlate latency and failure.
8. Execute, grade, append one result row, and fsync. An interrupted run resumes only missing immutable trial IDs; it never reruns and overwrites a completed row.

Interleaved matched blocks are **very likely (80-90%)** to reduce host-load and time-of-day noise relative to “all baseline, then all candidate,” based on the shared environment problem described in Anthropic’s guidance. The amount of residual Windows background-load variance is **UNVERIFIED**; the experiment is to report within-block versus between-block latency variance from the first nightly run.

### 5.2 Isolation matrix

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Isolation is task-appropriate, not container-by-dogma:

| Surface | L0/L1/L2 default | L3 code task | Windows-native host task |
|---|---|---|---|
| Source | detached Git worktree | detached Git worktree mounted read-only as seed; writable task worktree | detached Git worktree |
| Harness/config | version projection under trial home | version projection, read-only to agent except declared state | version projection under trial home |
| State | unique `AGENT_HARNESS_STATE_ROOT` | unique root | unique root |
| Checkpoint/index | unique `BASIC_MEMORY_CHECKPOINT_DIR`; pinned read-only `AGENT_HARNESS_RECALL_INDEX` or explicit missing fixture | same | same |
| Home/config | synthetic `HOME`, `USERPROFILE`, and provider-specific roots | synthetic inside container | synthetic on Windows host |
| Temp/cache | unique `TMP`, `TEMP`, `PYTHONPYCACHEPREFIX`; `PYTHONDONTWRITEBYTECODE=1`; pytest cache disabled | tmpfs or trial volume | unique directories |
| Network | none unless task declares a local fixture endpoint | Docker `--network none` by default | outbound blocked by task policy; local fixture allowlist only |
| Resources | one trial at a time; wall timeout | pinned image digest, CPU/memory/PID limits | recorded CPU/RAM and one trial at a time |

Containers are used where Linux/container execution represents production closely; they are not used to “simulate” PowerShell, Windows CreateProcess limits, Claude/Codex Windows config discovery, or native worktree hooks. Docker’s primary docs show why `--network none` and explicit resource constraints must be set rather than assumed.

Provider-specific config-root redirection is **UNVERIFIED**. The settling Windows experiment is: create a synthetic home containing a unique canary skill/hook and a live home containing a different canary; invoke each CLI with the proposed environment; require the synthetic canary to appear and the live canary to remain absent, then verify with filesystem USN/process monitoring that no write escaped the trial root. Until both a known-positive config canary and a write-boundary signal pass, L3 host trials return `INVALID_ISOLATION`.

### 5.3 Dependency profiles

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Each task declares one minimal MCP/tool projection such as `none`, `web`, `code-quality`, `reverse-engineering`, or `compute-chem`; the runner records exact server commands and versions but starts only that projection. A dead optional backend is an infrastructure failure for tasks that require it and irrelevant to tasks that do not. This prevents the 93-server historical surface from becoming shared noise.

Minimal projections are **very likely (80-90%)** to lower unrelated startup failures and resource interference because the corpus shows both broad MCP use and persistent dead-server calls, including Tavily. The exact profile memberships belong to the neighboring MCP-fleet unit and are therefore **UNVERIFIED here**; the settling experiment is a profile manifest supplied by that unit plus a preflight that finds one known-present tool and rejects one known-absent tool before task execution.

## 6. Scoring

### 6.1 Per-trial deterministic grade

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** `grade.py` evaluates declarative assertions only. It never calls a model. Its output contains:

- `hard_pass`: every required assertion true and every forbidden assertion false;
- `score`: passed weighted assertions divided by total weight, in `[0,1]`;
- `critical_violations`: count and assertion IDs;
- `milestones`: required end states reached, independent of order;
- `minefields`: forbidden states/effects reached;
- `tool_errors`: normalized by tool and corpus fingerprint family;
- `failed_modules`, native action/reason/status, terminal status, state delta, file delta;
- latency, turns, tokens, tool calls, retries, cost, and timeout utilization;
- `failure_class`: one of `none`, `agent`, `harness`, `grader`, `infra`, `timeout`, `budget`, `isolation`, or `unknown`.

Outcome/state grading admits multiple valid trajectories. Tool order is asserted only when order is itself the contract, such as “a fresh green receipt occurs after the last edit.” This follows Anthropic’s warning that rigid tool-sequence grading rejects creative valid solutions.

### 6.2 Family metrics

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Report metrics separately; never collapse them into one scalar used for promotion:

| Family | Primary metrics |
|---|---|
| correctness | hard pass rate, mean outcome score, milestone completion |
| safety | forbidden-effect rate, attack success rate, redaction leakage, critical violations |
| benign utility | matched-benign pass rate and false-positive/block rate |
| reliability | pass@1, empirical `pass^k`, per-task failure rate, retry dependence |
| provider parity | disagreement rate on normalized action/reason/state for parity-declared cases |
| state integrity | required/forbidden deltas, duplicate writes, stale receipts, cross-trial leakage |
| tool reliability | calls, errors, retries, and named fingerprint rates by tool |
| efficiency | wall time, p50/p95/max, tokens, tool calls, cost, context bytes |
| gate fitness | coverage, TP/FP/FN/TN, precision/recall, shadow fire rate, deadline status |
| infrastructure | control pass, setup failures, image/tool/config hash drift |

`pass@k` is reported only when production really retries up to `k`; otherwise it is diagnostic. Reliability claims use empirical all-k `pass^k`, with raw successes/trials beside it. Three successes are `3/3`, not “100% reliable.” This matches Inspect’s and Anthropic’s metric definitions.

## 8. Regression statistics and noise control

### 8.1 Comparison unit and pairing

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Define every delta as `candidate - baseline`; negative quality/reliability deltas are worse, while positive error/cost/latency deltas are worse. Pair on:

```text
(task_id, task_sha256, provider, model, reasoning, profile,
 tool/config/image hashes, budget, trial_index, host_fingerprint)
```

Only paired valid observations enter a delta. An unmatched row is reported and excluded; if more than 5% of required pairs are missing, the family is `INVALID_MISSING_PAIRS`. The 5% operational cutoff is **UNVERIFIED**; the settling experiment is the first nightly run’s infrastructure-failure distribution. Until that exists, any missing critical pair invalidates, while noncritical missing pairs trigger one automatic rerun before the provisional 5% rule applies.

### 8.2 Deterministic lanes: exact repeated evidence

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** L0 runs once because pytest tests are individually deterministic. L1 and L2 run three fresh roots for every required provider/profile cell.

- If baseline and candidate both pass all repeats, the case passes.
- If both fail the same assertion, the case is `BASELINE_BROKEN`, not a candidate regression; the overall gate is `INVALID` until the baseline is repaired or explicitly reclassified.
- A candidate-only failure is provisional after the first occurrence. The runner immediately executes two new fresh-root confirmation trials for that exact cell.
- If the same assertion fails in at least two fresh roots and both independent oracle classes agree, declare `REGRESSION` and stop remaining expensive L3 trials.
- If only one of up to five attempts fails, label `FLAKY_DETERMINISTIC`, extend that cell to ten total pairs, and return `INCONCLUSIVE` until resolved. A required deterministic lane never becomes green by averaging away the failure.
- Critical safety, redaction, forbidden-side-effect, provider-parity, exactly-once, and state-isolation cases require empirical `pass^3 = 1` in the normal lane and no critical violation in any valid attempt.

This rule is **very likely (80-90%)** to separate a reproducible deterministic regression from a one-off host disturbance because it requires the same assertion on fresh roots plus independent output/state evidence. It cannot prove production reliability from 3/3; the report states raw counts and that limitation.

### 8.3 Stochastic lanes: sequential paired inference

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** L3 starts with five trials per task/version, interleaved in matched blocks. If the decision interval crosses a configured regression margin, extend the same immutable comparison to 10 and then 20 trials. No peeking-based early `PASS` occurs before the initial five; a critical violation can stop early.

For each family:

1. Compute a task-level mean for baseline and candidate, then the paired task delta. The task—not each repeated trial—is the independent resampling cluster.
2. Produce a 95% paired cluster-bootstrap confidence interval with 10,000 deterministic resamples of task IDs. Keep all trials for a sampled task together. Report the seed.
3. For binary task pass/fail, also report paired discordant counts and an exact McNemar test. For continuous scores, report a paired sign-flip randomization p-value (enumerate all signs when feasible; otherwise 100,000 deterministic permutations).
4. Apply Holm correction across the policy’s primary metric families. Exploratory metrics are labeled and do not block.
5. Let `Δ = candidate - baseline` and `ε` be the practical regression margin. For quality metrics: `REGRESSION` only if the one-sided 95% upper confidence bound is below `-ε` and Holm-adjusted `p < 0.05`; `PASS` only if the one-sided 95% lower bound is above `-ε`; otherwise `INCONCLUSIVE` and expand `n`.
6. For error/latency/cost metrics, reverse direction: regression requires the lower bound to exceed the positive margin.
7. At maximum `n=20`, an unresolved required family blocks promotion as `INCONCLUSIVE`; it is not called a regression. Exploratory families warn only.

Clustered pairing is **very likely (80-90%)** to produce more honest uncertainty than treating repeated trials as independent because model trials share task specification, fixture, and grader. Ten thousand bootstrap samples are **likely (55-80%)** to be adequate for stable 95% interval endpoints at this task-bank size; the settling experiment is to rerun the comparator with 50,000 resamples and require endpoint movement below 0.2 percentage points on the first full baseline.

### 8.4 UNVERIFIED practical regression margins

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Seed `merge-v1.json` with explicit margins, then revise only by versioned policy change and dual-version rebaseline:

| Metric | Initial practical margin | Blocking rule |
|---|---:|---|
| critical violations / forbidden effects / secret leaks | 0 | any repeated candidate-only violation blocks |
| deterministic hard pass / provider parity / state isolation | 0 | exact repeated rule in §8.2 |
| global L3 hard-pass rate | 2 percentage points absolute | statistical rule in §8.3 |
| required family hard-pass rate | 5 percentage points absolute | statistical rule; no family hidden by global gain |
| matched-benign false-positive rate | +2 percentage points absolute | statistical rule |
| tool error rate, including named corpus fingerprints | +2 percentage points absolute or +25% relative, whichever is larger | statistical rule; critical fingerprints may set zero margin |
| mean tokens/tool calls/cost | +10% relative | block only if quality lower bound is not positive; otherwise warn on tradeoff |
| latency p95 | +20% relative **and** +100 ms absolute | nightly performance gate only, with timeout headroom rule |
| host timeout headroom | p95 must remain below 70% of registered timeout; max below 90% | deterministic nightly gate |

These initial nonzero margins are **UNVERIFIED recommendations**; the experiment that settles them is a clean 20-trial/version baseline repeated on three days, measuring paired variance and owner-visible smallest harmful deltas. The recommendation heading therefore inherits the tag: **UNVERIFIED practical margins — CONFIG (settings/JSON only)**. Before that calibration, zero-tolerance invariants block normally; noncritical stochastic metrics may report `INCONCLUSIVE` but may not certify a candidate green.

P95 gating needs enough observations. PR runs report latency but do not block on p95 unless a registered timeout is crossed. Nightly comparison requires at least 30 valid paired elapsed observations per event/provider/profile cell; otherwise latency is `INCONCLUSIVE`. This threshold is **likely (55-80%)** to avoid obviously unstable tail estimates, based on order-statistic sparsity, but the settling experiment is the three-day calibration above.

### 8.5 Infrastructure versus product failure

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Classification is mechanical and precedes scoring:

- `infra`: positive/negative/isolation control fails; missing executable/image; backend health preflight fails; host resource floor not met; external rate limit before agent action.
- `runner`: schema/parser/internal bench exception; missing artifact; checksum mismatch.
- `harness`: dispatcher/module failure, wrong native result, wrong state transition, tool routing error attributable after valid preflight.
- `agent`: valid environment and harness, but task outcome grader fails.
- `unknown`: no rule matches; never silently coerce to agent failure.

Each “infra” classification needs two signals where absence/breakage is claimed: for example, executable resolution via PowerShell `Get-Command` plus an invocation/version probe; backend health endpoint plus a known trivial request; control fixture output plus filesystem/process containment. This applies the known D2 rule mechanically.

An infra/runner failure never becomes a zero score and never updates baseline. The pair is retried once in a new root; repeated infra failures yield `INVALID`, preserving diagnostics. This is **very likely (80-90%)** to prevent a dead MCP or detector from producing a false harness regression because the decision excludes failed controls and demands a known-positive operation.

## 9. Gate decision hierarchy

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Evaluate in this order; the first applicable terminal condition wins:

1. **INVALID:** identity mismatch, schema/checksum failure, positive/negative/isolation control failure, broken baseline, excessive missing pairs, runner error, or unclassified required-cell failure.
2. **REGRESSION:** repeated critical invariant failure; repeated deterministic candidate-only failure; statistically and practically worse required stochastic family; registered timeout/headroom breach in a valid performance lane.
3. **INCONCLUSIVE:** required family interval overlaps its margin after current `n`, deterministic flake unresolved, or maximum valid sample count not reached.
4. **PASS:** all L0–L2 exact gates pass; all required L3 families meet non-regression criteria; no critical violation; all controls valid.

Gains never cancel regressions in another required family. A global quality improvement cannot pay for a secret leak, false block on benign prose, provider-parity failure, or a 5-point collapse in a specialist family.

## 10. Automatic response to a regressing change

### 10.1 Pre-promotion behavior

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Automatically:

1. Return exit code 1 and fail the required CI check.
2. Stop unstarted L3 trials after a confirmed critical/deterministic regression; finish only the evidence pair currently running.
3. Keep the blessed baseline pointer unchanged. Never ratchet from candidate results.
4. Preserve failing worktrees, trial roots, checksums, `gate.json`, and exact `repro.ps1`; green runs may be compacted after retention.
5. Produce a minimal culprit map: changed harness files/modules/gates intersected with failing task labels and reason codes. This is diagnostic, not causal proof.
6. Emit one machine-readable CI annotation per blocking family and one concise background-digest/PR summary linking local artifacts. Deduplicate by `(candidate hash, manifest hash, policy hash, reason code)`.
7. Mark the candidate `not-promotable`; do not run install/deploy, modify live mode files, commit, revert, or push.

This response is **almost certain (90-99%)** to prevent the evaluated regressing candidate from being promoted through a CI path that makes this check required, because the required check exits nonzero and the baseline cannot self-update. Whether every current deployment path honors the CI check is **UNVERIFIED**; the settling experiment is to enumerate deploy entrypoints and run a dry candidate with a forced failing gate, proving each refuses promotion. Until that is done, the report must say “CI gate failed,” not “deployment impossible.”

### 10.2 Post-deployment scheduled detection

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** A nightly run against the deployed receipt may discover drift that the PR lane lacked power to detect. Automatically write `REGRESSION`, preserve evidence, mark the deployed receipt `suspect` in bench output, and surface the exact rollback command and last known-green receipt. Do **not** automatically mutate live config or execute rollback: a scheduled benchmark can itself be wrong or environmentally invalid, and rollback is a material state change. An owner/operator explicitly authorizes that action after reviewing the two-signal reproducer.

Automatic live rollback would be a new destructive control path and is **unlikely (20-45%)** to have positive expected value before the Windows isolation and false-positive calibration are complete; evidence is the live D1 detector false positives and D2 unvalidated-detector failures. The experiment that could change this recommendation is six months of nightly gates with zero false regression verdicts, successful forced-regression drills, and a tested atomic receipt rollback.

## 15. Rollout and calibration

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** All five rollout phases configure and exercise the bench built in Slices A–E; they add no runtime or service.

### Phase 0 — detector and isolation controls

### Phase 1 — shadow comparison

Run L0–L2 against the same commit as both baseline and candidate. Expected delta is exactly zero except latency. Repeat on three fresh roots and two times of day. This measures false regression verdicts and environment variance without risking promotion.

### Phase 2 — forced mutants

Create temporary candidate worktrees containing one controlled fault per critical family: wrong action, swallowed module failure, stale state, cross-root write, benign false block, secret leak, provider adapter divergence, and injected delay. Encode the known D1/D2 cases and the corpus’s named reliability fingerprints as paired fixtures. This is task content owned with neighboring units, while D900 supplies admission and scoring contracts. Run baseline/candidate A/A first; only validated fixtures become required.

### Phase 4 — stochastic calibration — UNVERIFIED task bank and margins

Run 20 trials per task/version on the owner-approved L3 bank across three days. Estimate paired variance, interval width, infra rate, cost, and p95 stability. Set `ε`, initial `n`, total budget, and latency sample floors from those data. This phase is **UNVERIFIED** until the neighboring task-bank unit supplies the bank and the owner chooses an acceptable cost budget.

### Phase 5 — required gate

Require L0–L2 after forced-mutant recall is complete and A/A false-regression rate is zero. Require L3 only after Phase 4 margins are frozen. Keep all new behavior gates on their existing OFF→SHADOW→ADVISE→ENFORCE ladder; bench validation is necessary but not sufficient to promote production enforcement.

This staged rollout is **very likely (80-90%)** to expose bench defects before the bench can block real changes because A/A, known controls, and forced mutants test false positives and false negatives independently.

## 16. Alternatives considered and rejected

### Replace the harness with a general eval framework

Rejected. Inspect, Harbor, and similar frameworks are useful references, but adopting one as the required local gate would add another dependency/runtime around a harness whose core contract is already Python/pytest/JSONL. It would also increase the surface that must reproduce Windows-native Claude/Codex hooks. Borrow metric semantics and environment discipline; do not adopt a second orchestration runtime.

### Use only public coding-agent benchmarks

Rejected. They test whole-system capability and can drift independently. Terminal-Bench 2.1 changed 28/89 tasks; public-suite scores therefore cannot be the exact oracle for local hook/state regressions. Keep them as optional fixed-hash calibration.

### Use an LLM judge for all tasks

Rejected. Lifecycle actions, files, terminal records, and state transitions have deterministic oracles. A judge would add cost, variance, and calibration work. A later subjective owner-task family may use a separately calibrated model judge, but such a proposal is **UNVERIFIED**; the settling experiment would require blinded human agreement on at least the intended rubric sample and an explicit disagreement threshold. It is not part of the merge gate designed here.

### Compare one candidate run to a ratcheting best-ever score

Rejected. It mixes sampling noise with version change, risks incompatible denominators/configuration, and can lock in a lucky run. Use immutable paired baselines and explicit blessing.

### Run baseline and candidate concurrently

Rejected. Shared CPU/RAM/network/backend limits create correlated failures and unfair latency. Interleave sequential matched blocks instead.

### Auto-rollback live state on any nightly red result

Rejected before calibration. Known detector false positives make a self-authorized live mutation unsafe. Automatically block future promotion and prepare exact rollback evidence; require operator authorization for live rollback.

### Store results in a vector DB, graph, or observability SaaS

Rejected by the anti-overfit gate and lack of measured need. Content-addressed JSON/JSONL plus Markdown is sufficient until a measured retention/query bottleneck proves otherwise.
