# J01 — Between-session consolidation: what the harness should distill while idle

## Executive decision

Build a **single, one-shot consolidation worker**, launched by the operating system on a schedule and exiting after one bounded incremental pass. It is not a second agent runtime and not a seventh hook. It consumes only sessions that have reached an existing terminal checkpoint and then been quiet for a debounce interval. It writes an append-only evidence journal plus four small derived views: a scoped user model, a strategy candidate book, a lossless thread register/rank view, and a terse “what changed” digest. The existing `background-digest/reader.py` remains the only presentation path.

The key architectural distinction is **extract, verify, promote, present**. A fresh-context model may propose a memory, preference, strategy, or thread transition, but it cannot validate its own proposal. Promotion requires an external signal: a source-span re-read by a deterministic tool, an execution/test result, a different model context, or an owner action. This directly implements this unit's law that intrinsic same-context self-correction fails.

This is **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** for the first useful version: one incremental worker, one schema, atomic materialized views, and registration as a scheduled one-shot task. It folds into the existing SessionEnd cursor and SessionStart dispatcher; it adds **zero raw hooks**. It does not add a daemon, vector database, knowledge graph, trained critic, durable-execution engine, observability SaaS, or guardrail framework. That passes the anti-overfit gate.

Expected outcome: **very likely (80-90%)**, because the harness already has the required storage and presentation buses, the corpus documents repeated continuation pressure, and the remaining implementation is bounded glue. The uncertainty is whether Windows Task Scheduler and transcript paths expose all required session metadata; that premise is **UNVERIFIED — run `consolidate.py --dry-run --session <known-session-id>` under the intended scheduled-task account and compare its discovered transcript/cursor against the SessionEnd ledger entry** before enabling writes.

## Grounding and detector discipline

The supplied corpus is a high-coverage distillation: 11,633 files, 10.62 GB, 1,564,084 lines, zero failed files, one bad line, and 32 oversized lines. Its own note says samples are capped at 12 and qualifies absence claims (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). I therefore use its counts as measured ground truth but do not infer fine-grained semantics from capped samples.

The most tempting input for a user model is also the most dangerous. The corpus labels 2,268 of 8,441 owner messages as correction candidates, but explicitly says the detector is recall-biased and that an unfiltered smoke sample produced 41/41 false positives because agent-authored prompts were misclassified (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10374`). Its top patterns include hook feedback and internal teammate/task notifications (`/local_disk0/codexwork/bundle/inputs/corpus.json:10375-10414`). Therefore, **no candidate from this field may directly update the user model**. It is an acquisition queue only.

There is real owner signal for continuity: “why did you stop proceed until you finish everything” appears as a repeated normalized pattern (`/local_disk0/codexwork/bundle/inputs/corpus.json:10424-10426`), while retry-loop data separately records 53 repeated Read runs and 14 Bash runs (`/local_disk0/codexwork/bundle/inputs/corpus.json:10297-10323`). These are different data fields and support, respectively, the owner’s aversion to premature stopping and the need to extract reusable recovery strategies. They do not prove that every repeated stop message was human-authored; that finer claim is not made.

The corpus’s hooks section is unusable by declaration: its known-positive control observed zero fires and the section says to treat it as no data (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13263`). All hook-effect claims below instead cite static wiring plus runnable external tests. ## Exact run contract

**When it runs.** A Task Scheduler entry invokes `python .../consolidation/consolidate.py --budget-seconds 120` every 15 minutes, but the process immediately exits 0 unless: (a) the existing ledger has a terminal SessionEnd cursor; (b) the transcript mtime is at least 20 minutes old; (c) no newer non-subagent turn exists; and (d) that session ID is not already recorded in `processed.jsonl`. A nightly invocation may compact only derived views, never the append-only journal. The 15/20-minute numbers are initial conservative defaults, not evidence-backed optima. Their suitability is **UNVERIFIED — A/B 10 vs 20 vs 45 minutes for two weeks using collision count (a session resumes while being processed), missed-session count, and owner-visible stale-thread rate**.

**What it reads.** Incremental transcript tail/full session as required; correlated event-ledger shard; existing OPEN-THREADS.md; open-loop trigger store; selection-event outcomes; continuous-learning-v2/instinct candidate state; basic-memory note metadata; repository state only for paths already named in thread evidence. It never crawls all 10.62 GB on the hot path.

**What it writes.** All files are local, reviewable text/JSONL and written temp-plus-`os.replace` except append journals:

```
~/.claude/consolidation/
  processed.jsonl                 # session id/hash, cursor, extractor version, status
  evidence.jsonl                  # immutable source anchors and verifier outcomes
  preference-candidates.jsonl     # scoped, revocable hypotheses; never direct prompt rules
  strategy-candidates.jsonl       # condition/action/evidence/held-out score/lifecycle
  thread-events.jsonl             # opened/advanced/blocked/deferred/resolved/tombstoned
  eval.jsonl                      # shadow decisions, external outcomes, promotion decisions
  views/user-model.md             # generated, bounded, only promoted preferences
  views/strategies.md             # generated, only promoted strategies
  views/thread-ranks.json          # generated rank; source register remains lossless
~/.claude/BACKGROUND-DIGEST.md     # append <=3 genuinely new, actionable deltas
```

Every record has `id`, `kind`, `project_id`, `scope`, `claim`, `source_session`, `source_event_id`, `source_span_hash`, `observed_at`, `valid_from`, `valid_until`, `extractor_version`, `status`, `confidence_band`, `verifiers[]`, `supersedes[]`, and `reversible_by`. Secret-shaped material is redacted before model input and never persisted, reusing the selection-event redactor.

**Failure semantics.** Outer `try/except`, per-session exception isolation, bounded input/output, lock with stale-lock recovery, atomic derived views, and unconditional exit 0. A failed extraction leaves the session unprocessed for retry; a failed verification leaves a candidate quarantined; a failed digest append changes no promoted state. The worker must first pass a known-positive fixture containing one explicit preference, one unresolved thread, one resolved thread with a test result, and one tool failure/recovery. A second fixture contains only agent-authored prompts and tool results and must yield no owner preference. Those controls are mechanically independent of live data.

## Findings (inferred-surprise first)

### 1. **INFERRED-SURPRISE — Make consolidation a provenance compiler, not a nightly summary**

* **Improvement:** Compile each ended session into independently addressable evidence atoms and materialized views. Never overwrite “what happened” with a prose summary.
* **What it is:** A four-stage pipeline: fresh-context extractor proposes atoms; a deterministic source re-reader validates role/event/span hashes; a separate verifier context checks entailment and contradiction; a promoter updates derived views only when policy permits. Old claims are superseded/tombstoned, never silently edited away. This goes beyond `/self-reflect`: reflection creates candidates; evidence lifecycle determines what may affect future work.
* **Why-inferred:** The owner asked for between-session distillation, but the stronger latent need is resistance to confidently propagated falsehoods. The correction queue’s 41/41 smoke failure (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10374`) and the known fabricated orchestrator constraint in `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160` show that compression without provenance can amplify error. Existing `note.py` already models falsifiable failures and supersession (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/note.py:2-12`, `:25-42`), so provenance compilation is the natural next layer.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement the schema above, reuse event-ledger IDs and the selection-event human-role discriminator, hash exact source spans, and generate views from the journal. Candidate lifecycle is `quarantined -> corroborated -> promoted -> superseded|expired`; no model writes `promoted` directly.
* **EXTERNAL signal that verifies it:** (1) deterministic re-open of the source event reproduces the hash and human/system role; (2) a separately launched model, receiving the candidate plus adjacent source events but not the extractor’s reasoning, labels entailed/contradicted/ambiguous; (3) a mutation test changes the source after extraction and must quarantine the atom. This is outside the originating context.
* **SOTA:** Generative Agents separates observation, reflection, and planning and reports ablations showing each matters ([Park et al., 2023](https://arxiv.org/abs/2304.03442)); LongMemEval decomposes memory into indexing, retrieval, and reading and explicitly tests knowledge updates and abstention ([Wu et al., ICLR 2025](https://arxiv.org/abs/2410.10813)). This finding adds promotion governance, which those architectures do not supply for this harness.
* **Value × effort:** transformative × medium.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it for journaling/quarantine; confirm-first for any promoted consequential owner preference.
* **Confidence:** **very likely (80-90%)** to reduce propagated false memories, because every promoted atom is source-addressable and the highest-risk corpus detector is demonstrably low precision. **UNVERIFIED — replay 200 stratified candidate atoms through summary-only versus provenance-compiler variants and have a blinded fresh model plus owner spot-check score false promotion and missed promotion**.

### 2. **INFERRED-SURPRISE — Learn strategies in shadow mode before letting them steer work**

* **Improvement:** Convert successful/failed trajectories into conditional strategy candidates, but require held-out external outcomes before promotion to continuous-learning-v2/instincts.
* **What it is:** Each candidate is `when <observable preconditions>, prefer <action> over <alternative>, because <external result>`. Initial status is shadow: the harness logs whether it would have recommended the strategy, while the live agent behaves normally. Promotion requires improvement on later, non-source sessions.
* **Why-inferred:** The corpus records retry loops across tools, including 53 Read and 14 Bash runs (`/local_disk0/codexwork/bundle/inputs/corpus.json:10297-10323`), while continuous-learning-v2 appears only twice (`/local_disk0/codexwork/bundle/inputs/corpus.json:13299-13303`). The owner likely wants the harness to stop re-walking expensive dead ends, but same-session self-congratulation cannot establish a reusable strategy.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extract precondition/action/outcome triples from event-ledger selection/failure/milestone events; deduplicate by normalized precondition/action hash; store in `strategy-candidates.jsonl`; have the semantic router consult only `promoted` entries. Fold promotion export into the existing continuous-learning-v2/instinct format; do not create v3.
* **EXTERNAL signal that verifies it:** On the next three eligible sessions, correlate shadow recommendation with independent execution results: command exit code, test suite, artifact existence plus parser/validator, or owner acceptance/correction. Promote only with at least two successes from distinct sessions and no contradictory result; high-impact/destructive strategies require owner confirmation. A fresh verifier process recomputes the outcome from raw tool events.
* **SOTA:** ProactiveBench labels proactive suggestions accepted/rejected by humans and evaluates proactive assistance with an F1 operating point rather than raw suggestion volume ([Lu et al., 2024](https://arxiv.org/abs/2410.12361)). The proposed shadow phase imports that acceptance/rejection discipline without a trained reward model.
* **Value × effort:** high × medium.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it for candidate extraction and shadow evaluation; confirm-first for promotion of strategies that broaden authority or change safety posture.
* **Confidence:** **likely (55-80%)** to reduce repeat failures without overfitting, because later-session execution is independent of the source reflection, but sparse recurrence may delay promotion. **UNVERIFIED — run a 30-day shadow evaluation and compare retry-run rate and task success on eligible versus ineligible sessions, stratified by tool and project**.

### 3. **INFERRED-SURPRISE — Treat “never drop a thread” as a conservation invariant, not a ranking goal**

* **Improvement:** Maintain an append-only thread event stream in which ranking can hide nothing and resolution cannot erase history.
* **What it is:** Every discussed commitment becomes a thread with lifecycle `open -> active|blocked|deferred -> resolved -> tombstoned`. `thread-ranks.json` is disposable presentation; `thread-events.jsonl`, OPEN-THREADS.md, and the event-ledger are the conserved source set. Low-ranked means quiet, never deleted.
* **Why-inferred:** Repeated “why did you stop” continuation language is present in corpus patterns (`/local_disk0/codexwork/bundle/inputs/corpus.json:10424-10426`). Existing resurfacing deliberately caps presentation at three (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:38-40`, `:69-95`), which protects focus but makes a separate lossless conservation layer essential.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** A fresh extractor emits `opened/advanced/blocked/deferred/resolution_candidate`. A deterministic reconciler set-compares IDs across the new events, OPEN-THREADS.md, open-loop triggers, ledger dangling goals/failures, and prior thread journal. Any item present before but absent from extraction is carried forward with `unseen_this_session=true`; absence never closes it. Reuse project IDs and open-loop predicates.
* **EXTERNAL signal that verifies it:** For every proposed resolution require one of: owner says done; referenced commit/artifact exists **and** its relevant test/validator passes; external task/workflow status reports success. A separate known-positive conservation test seeds 100 threads, resolves 10 with test receipts, hides 20 from the next transcript, and asserts 90 remain unresolved. A second set-difference check compares journal IDs with rendered OPEN-THREADS IDs; discrepancies fail the worker pass but exit 0.
* **SOTA:** LongMemEval explicitly includes temporal reasoning, knowledge updates, and abstention, and finds a 30% accuracy drop in sustained interactions ([Wu et al., 2025](https://arxiv.org/abs/2410.10813)). The conservation invariant is the harness-specific response: defer retrieval optimization until losslessness is proven.
* **Value × effort:** transformative × medium.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it for opening/carry-forward/ranking; confirm-first to close owner-level goals when no executable completion receipt exists.
* **Confidence:** **almost certain (90-99%)** that set-conservation prevents extraction omissions from deleting threads, because the property is mechanically testable. It is **likely (55-80%)** to reduce owner stress; evidence is repeated continuation pressure, but causal stress reduction is **UNVERIFIED — track owner “forgot/stopped/missed” corrections per 100 sessions before and after, with a manual audit that excludes hook-authored messages**.

### 4. **INFERRED-SURPRISE — Add contradiction and expiry as first-class memory operations**

* **Improvement:** Make time, scope, and supersession mandatory for user preferences, facts, constraints, and strategies.
* **What it is:** “The owner prefers X” is never global by default. It carries project/task/audience scope, evidence kind (`explicit`, `behavioral`, `inferred`), valid-from/valid-until, contradicts/supersedes links, and a confidence band. Conflicts retrieve together; the system abstains instead of selecting the newest prose blindly.
* **Why-inferred:** A fabricated constraint propagated to about 15 prompts in the live-defects input (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-155`). The corpus’s candidate detector also confounds internal events with human speech (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10414`). The unasked need is not more memory volume but safe updating and selective application.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add lifecycle fields to the common journal; render only promoted, in-scope entries into `user-model.md`; make retrieval return `{current, conflicting, expired}`; keep explicit owner statements indefinitely until superseded, decay behavioral hypotheses after 30 days or five contradictory observations, and never turn silence into a preference.
* **EXTERNAL signal that verifies it:** Deterministic temporal tests replay an explicit preference, a later scoped exception, and a later reversal; a fresh-context query suite must select the right statement by date/scope and abstain on conflict. For real use, owner correction/acceptance and downstream artifact choices update the hypothesis; the originating model never grades itself.
* **SOTA:** LongMemEval makes knowledge update and time-aware query expansion core memory capabilities ([Wu et al., 2025](https://arxiv.org/abs/2410.10813)). BenchPreS finds that stronger preference adherence can increase misapplication when a remembered preference is inappropriate in a new context ([Yoon et al., 2026](https://arxiv.org/abs/2603.16557)).
* **Value × effort:** high × low.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it for schema, conflict detection, expiry, and abstention; confirm-first for a new global preference inferred from behavior.
* **Confidence:** **very likely (80-90%)** to prevent stale/global preference misapplication because applicability becomes explicit and conflicting evidence is preserved. **UNVERIFIED — run a harness-specific BenchPreS-style suite of 100 project/audience exceptions and measure appropriate-application and misapplication separately**.

### 5. **INFERRED-SURPRISE — Evaluate retrieval and consolidation with prospective “memory unit tests”**

* **Improvement:** Turn future questions into an external test set at the moment a memory is created.
* **What it is:** For each promoted atom, a different context generates one or two future probes: direct recall, temporal update, scope exception, or abstention. The answer key is the source anchor, not another model’s summary. Nightly evaluation asks these probes against the derived views and records retrieval/answer/abstention separately.
* **Why-inferred:** Corpus counts prove extensive memory use—408 writes, 357 searches, 353 reads (`/local_disk0/codexwork/bundle/inputs/corpus.json:13465-13479`)—but do not establish memory quality. The hooks telemetry detector is broken (`/local_disk0/codexwork/bundle/inputs/corpus.json:13260-13263`), so a purpose-built external evaluation signal is required before calling consolidation effective.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Store probes in `eval.jsonl`; use existing keyword/content-hash recall, not a vector DB; run a bounded sample nightly; classify failure stage as indexing, retrieval, reading, update, or abstention. Keep model-generated probes quarantined until a deterministic source-span checker verifies that the answer exists and a second model rejects ambiguous questions.
* **EXTERNAL signal that verifies it:** Exact source-span answers plus deterministic retrieval IDs are one signal; a different-context judge is the second. Weekly report only aggregate deltas and top three regressions through the existing background digest. A known-present canary must be retrieved before any “memory absent” diagnosis.
* **SOTA:** LongMemEval provides 500 questions across information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention, and decomposes failure into indexing/retrieval/reading ([Wu et al., 2025](https://arxiv.org/abs/2410.10813)). PrefEval reports preference-following below 10% for most evaluated models at only about ten turns in zero-shot settings, motivating explicit longitudinal tests rather than assumed personalization ([Zhao et al., 2025](https://arxiv.org/abs/2502.09597)).
* **Value × effort:** high × medium.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it.
* **Confidence:** **very likely (80-90%)** to expose silent memory regressions because the probes target specific stored atoms and stages. Whether those synthetic probes predict owner-perceived continuity is **UNVERIFIED — correlate weekly test accuracy with audited owner corrections and reopened-thread incidents for at least 30 days**.

### 6. **INFERRED-SURPRISE — Budget proactive attention like a scarce resource**

* **Improvement:** Present a change digest, not a recap, and charge every surfaced item against an attention budget.
* **What it is:** Consolidation may write many internal records but surface at most three deltas: one urgent thread, one newly verified strategy/gem, and one decision requiring owner input. Each line says `what changed | why now | evidence | proposed next action`; unchanged facts stay silent. Owner can dismiss once, snooze, inspect evidence, or change global controls.
* **Why-inferred:** The owner explicitly makes prompt fatigue a hard constraint. Existing reader defaults to 12 entries (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:67-68`, `:138-158`), while open loops and recall cap at three (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:38-40`; `/local_disk0/codexwork/bundle/claude/hooks/recall-inject/inject.py:44-50`). Consolidated output should follow the smaller attention budget, not the background reader’s legacy maximum.
* **How-to-build:** **CONFIG (settings/JSON only)** for the initial cap: set `BG_DIGEST_MAX=3`; producers append only state transitions whose expected value clears the existing calibrated-silence gate. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** only for adding stable IDs/action receipts to digest entries and feeding owner reactions to the existing interjection ledger. This is not a new hook.
* **EXTERNAL signal that verifies it:** The existing reaction logger records acted/ignored/annoyed next-turn behavior; selection events correlate subsequent tool action to real user prompts. Evaluate acted rate, annoyance rate, and time-to-reopen urgent threads, not volume. A separate digest archive proves what was shown; owner action proves usefulness.
* **SOTA:** The validated human-AI guidelines say to time services based on context, show contextually relevant information, support dismissal/correction, provide global controls, and notify users about changes ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). The paper specifically warns that proactive filtering can hide costly information and conflict with user goals.
* **Value × effort:** high × low.
* **Novelty:** inferred-surprise.
* **Autonomy:** just-do-it for reducing/capping background output and logging reactions; confirm-first before changing global notification policy if current owner settings are explicit.
* **Confidence:** **very likely (80-90%)** to lower prompt fatigue because output volume is capped and unchanged material is silent. The exact cap of three is **UNVERIFIED — compare caps 1/3/5 in alternating weeks using acted-per-surfaced, annoyed-per-surfaced, and missed-urgent-thread audits**.

### 7. **USER-ASKED — Build a scoped, inspectable user model from explicit speech and behavior receipts**

* **Improvement:** Distill stable working preferences, boundaries, collaboration style, and recurring goals without treating agent text, one-off constraints, or silence as owner intent.
* **What it is:** A compact `user-model.md` with sections `explicit`, `observed`, `hypotheses awaiting confirmation`, `exceptions`, and `superseded`. Each item carries scope and evidence links. Explicit owner directives can promote automatically when low-risk; behavioral patterns need repeated receipts; sensitive/high-impact inferences remain candidates.
* **Why-inferred:** The owner asked directly for user-model updates. The corpus contains abundant candidate material but explicitly invalidates naive harvesting (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10374`). Selection-event code already solves the crucial human-vs-tool/system distinction (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:131-162`, `:165-212`), so the correct expansion is evidence-backed personalization rather than a new classifier.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extract only from events validated as real user speech or from owner-linked action receipts. Promotion rules: explicit + source-verified + low-risk -> promoted; behavioral -> at least three distinct sessions and two distinct task contexts; inferred sensitive/global -> AskUserQuestion batch, never individual nag. Render maximum 25 active items, with older detail reachable by ID in basic-memory.
* **EXTERNAL signal that verifies it:** (1) deterministic role/source validation; (2) later owner behavior, explicit correction, or batched confirmation; (3) fresh-context preference application tests. A false-positive fixture made entirely of tool results, stop-hook messages, and agent prompts must yield zero preferences.
* **SOTA:** PrefEval distinguishes explicit and implicit preferences and shows severe degradation across multi-session contexts ([Zhao et al., 2025](https://arxiv.org/abs/2502.09597)). Amershi et al. recommend learning from user behavior while also making adaptation consequences visible and providing controls ([CHI 2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). BenchPreS adds the necessary warning that preferences must be selectively applied by context ([Yoon et al., 2026](https://arxiv.org/abs/2603.16557)).
* **Value × effort:** transformative × medium.
* **Novelty:** user-asked.
* **Autonomy:** just-do-it for evidence collection and low-risk explicit preferences; confirm-first for sensitive, global, or consequential inferred preferences.
* **Confidence:** **likely (55-80%)** to improve felt personalization without a large false-profile tax, because the design filters human speech and scopes every item. The three-session behavioral threshold is **UNVERIFIED — use a blinded owner audit of 50 promoted/candidate preferences and tune for precision before recall**.

### 8. **USER-ASKED — Re-rank threads by context and urgency, with anti-starvation and owner-cost terms**

* **Improvement:** Compute a disposable next-session priority view while preserving every unresolved thread.
* **What it is:** A transparent score, not an opaque model rank:

  `score = 3*explicit_owner_priority + 2*deadline + 2*currently_unblocked + 2*cwd/branch/file_match + downstream_dependents + age_credit - interruption_cost - needs_missing_authority`

  Hard rules override score: explicit owner pin first; safety/expiry deadlines next; at least one oldest unresolved thread enters every fifth digest (“fairness slot”); blocked threads remain visible in the register but do not displace executable work unless owner action is required.
* **Why-inferred:** The owner explicitly asked for thread re-ranking and forbids dropping threads. Existing open-loops already evaluates cwd/branch/file/prompt predicates and carries TTL/recurrence (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/_common.py:8-16`, `:41-58`, `:112-175`), so a deterministic re-ranker builds beyond it without duplicating retrieval.
* **How-to-build:** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Read conserved thread events, calculate features with stdlib predicates, write atomic `thread-ranks.json`, and let the existing resurface/background digest select from it. Include a score explanation and source IDs. Never mutate the underlying thread lifecycle from rank output.
* **EXTERNAL signal that verifies it:** Offline replay: hide the next real owner action, rank threads using only prior state, then measure reciprocal rank of the thread the owner actually advances. ## Rollout and mechanical acceptance gates

1. **Dry-run / no influence (week 1):** worker writes only `processed/evidence/*-candidates/eval`; compare source hashes and owner-role classifications on stratified samples. Acceptance: zero false owner classifications in the known-negative fixture; 100% retrieval of the known-positive fixture; no subject/config writes.
2. **Shadow ranking and strategy (weeks 2-3):** compute user-model, strategy, and thread-rank views but do not inject them. Backtest against later owner actions and execution outcomes. Acceptance: thread conservation set equality; no auto-resolution without receipt; shadow top-3 recall beats FIFO on held-out transitions. “Beats” is **UNVERIFIED until this experiment runs**.
3. **Low-volume presentation (week 4):** allow at most three digest deltas through existing reader and calibrated-silence. Acceptance: no additional raw hook; scheduled process exits 0 on malformed input; archive retains every surfaced entry; acted/ignored/annoyed is measured externally.
4. **Promotion enablement:** enable low-risk explicit preferences and strategies meeting held-out criteria. Global/sensitive preferences remain AskUserQuestion-confirmed. Acceptance: fresh-context test applies scope/temporal exceptions and abstains on contradiction.
5. **Quarterly prune:** prune only derived views, caches, expired probes, and fully receipted/tombstoned presentation entries. Append-only evidence and unresolved threads are retained or explicitly archived, never silently dropped.

The worker is “done” only when two mechanically independent signals agree: its isolated fixture suite passes, and a real scheduled-account dry run produces the expected cursor/view/digest artifacts with source hashes that re-open correctly. Static presence of files alone is not completion.
