# P2A01 — Agent-harness state of the art, 2026-07-18

## Executive answer

There is no defensible single “best agent harness” independent of model, task, budget, and evaluator. The best-supported unit of capability is the **model–harness–environment–budget configuration**, not the model or harness alone. Terminal-Bench 2.0 makes the size of the interaction visible: with the nominally same Claude Opus 4.6 model, published harness configurations range from 58.0% for Claude Code to 76.4% for Meta-Harness, an 18.4-point spread; however, dates, model aliases, effort settings, and implementation details are not fully locked, so this is strong evidence of harness sensitivity rather than a clean component-level causal estimate ([Terminal-Bench 2.0 leaderboard](https://www.tbench.ai/leaderboard/terminal-bench/2.0); [Harness-Bench’s own interpretation rule](https://arxiv.org/abs/2605.27922)).

The frontier’s common shape is **very likely (80-90%)** a thin, adaptable execution waist rather than a universal, elaborate orchestration runtime. Evidence: mini-SWE-agent exceeds 74% on SWE-bench Verified with roughly 100 lines of agent code, one bash tool, independent subprocess actions, and linear history; the official SWE-bench site explicitly maintains a bash-only mini-SWE-agent lane for model comparison; Agentless reached then-leading SWE-bench Lite results with a deterministic localization–repair–validation pipeline; and Anthropic’s production guidance says to start with simple loops and add complexity only when measured value requires it ([mini-SWE-agent documentation](https://mini-swe-agent.com/latest/); [SWE-bench Verified methodology](https://www.swebench.com/verified.html); [Agentless paper](https://arxiv.org/abs/2407.01489); [Anthropic, Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)).

That thin waist is surrounded by six load-bearing systems:

1. **A model-compatible agent-computer interface:** a small, unambiguous action surface, ergonomic editing and search, bounded high-signal observations, and model-specific adapters. SWE-agent established that interface design changes agent performance; Anthropic reports spending more time optimizing tools than the overall SWE-bench prompt; VS Code uses different prompts, edit tools, and history handling for different model families ([SWE-agent paper](https://arxiv.org/abs/2405.15793); [Anthropic tool guidance](https://www.anthropic.com/engineering/building-effective-agents); [VS Code coding harness](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)).
2. **Selective context, not maximal context:** just-in-time discovery, output filtering/truncation, compaction, and durable structured state. Anthropic’s context-engineering guidance defines the target as the smallest high-signal token set; Live-SWE-agent truncates long command results; VS Code now defers tool schemas and optimizes prompt caching ([Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Live-SWE-agent config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml); [VS Code token-efficiency work](https://code.visualstudio.com/blogs/2026/06/17/improving-token-efficiency-in-github-copilot)).
3. **Environment-grounded verification:** reproducible sandboxes, real execution, focused tests during work, broad regression tests at completion, and graders that inspect final state rather than self-report. Terminal-Bench, Harbor, PaperBench, and Anthropic’s eval guidance all make the environment outcome the scoring object ([Terminal-Bench paper](https://arxiv.org/abs/2601.11868); [Harbor task format](https://www.harborframework.com/docs/tasks/task-difference); [PaperBench](https://openai.com/index/paperbench/); [Anthropic eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
4. **Durable, inspectable task state:** versioned specs, progress artifacts, git history, and explicit completion criteria that survive compaction or a fresh session. Anthropic’s long-running harness used an initializer, feature-list JSON, progress file, startup script, git history, incremental work, and end-to-end checks ([effective long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
5. **Complete trajectory observability and regression gates:** record tool calls, outputs, artifacts, costs, failures, and outcome checks; require held-out evaluation before accepting harness changes. Meta-Harness’s ablation found raw traces far more useful to its proposer than scores or generated summaries; Anthropic and VS Code both require evals for harness/tool changes ([Meta-Harness](https://arxiv.org/abs/2603.28052); [Anthropic tool evaluation](https://www.anthropic.com/engineering/writing-tools-for-agents); [VS Code eval assessment](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)).
6. **Containment at the environment boundary:** filesystem, process, network, permission, and workspace isolation. Anthropic reports a controlled prompt-exfiltration test succeeding 24/25 times and concludes that egress controls and filesystem boundaries, rather than intent classifiers alone, are the defense that holds ([Anthropic containment report](https://www.anthropic.com/engineering/how-we-contain-claude)).

The frontier is not “more agents, more memory, more prompts.” Multi-agent research can outperform a single agent, but Anthropic reports roughly 15× chat token use and explicitly says many coding tasks have fewer truly parallelizable components. Automated harness evolution has striking same-benchmark results, but a July 2026 continual-learning study reports that GEPA transferred below the unoptimized baseline and Meta-Harness failed to improve on a second optimization phase; only the regression-controlled method continued improving ([Anthropic multi-agent system](https://www.anthropic.com/engineering/multi-agent-research-system); [continual harness-optimization study](https://arxiv.org/abs/2607.14004)). The default should therefore remain single-agent and minimal, with parallel workers and outer-loop optimization admitted only through evidence-bearing gates.

## Scope, definitions, and method

This unit uses external evidence only. It did not inspect or characterize the owner’s local harness; other units own that lens.

I use **agent harness** to mean the system around model weights that assembles context, exposes and executes tools, maintains state, controls the loop, applies permissions, records traces, handles recovery, and returns artifacts. This matches VS Code’s decomposition into context assembly, tool exposure/execution, and loop control, and Anthropic’s distinction between an agent harness and an evaluation harness ([VS Code coding harness](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode); [Anthropic eval definitions](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). An **evaluation harness** runs tasks, fixes budgets/environments, records trajectories, grades outcomes, and aggregates results. Confusing the two is a common source of false attribution.

Research was conducted on 2026-07-18 with primary sources prioritized: official leaderboard data and policies, benchmark papers, official repositories/configurations, and vendor engineering reports that disclose methods. I deep-read more than five key sources and cross-checked current leaderboard pages against their underlying official repositories where available. For the SWE-bench snapshot, I queried the official site’s source data at [`data/leaderboards.json`](https://raw.githubusercontent.com/swe-bench/swe-bench.github.io/master/data/leaderboards.json), rather than relying on search snippets. Search discovery used the available web-search provider; direct official GitHub HTTP reads were used for repository data. Vendor results are treated as first-party evidence, not independent replication.

Confidence language follows the owner’s required bands. `UNVERIFIED` appears inline whenever a premise still needs a settling experiment.

# 1. What is actually established

## 1.1 The score belongs to a configuration, not to a model

Anthropic’s eval taxonomy explicitly states that evaluating an agent evaluates the model and harness together. It defines the transcript as the complete trial record and the outcome as the final environment state, which may disagree with what the agent says it accomplished ([Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Harness-Bench independently frames the measured object as a model–harness configuration and warns that preserving native execution behavior supports configuration-level diagnosis, not causal decomposition of individual mechanisms ([Harness-Bench](https://arxiv.org/abs/2605.27922)). SWE-rebench reaches the complementary conclusion: to compare models, it fixes a minimal ReAct scaffold, prompt, environment, and 128K context across models ([SWE-rebench methodology](https://swe-rebench.com/about)).

This distinction gives two valid but different leaderboard questions:

| Question | Correct protocol | What can be attributed |
|---|---|---|
| Which complete agent system solves most tasks? | Allow arbitrary harnesses, but disclose model, budget, attempts, tools, and trajectories. | The complete submitted system only. |
| Which model is stronger in a common execution setting? | Lock harness, task image, context/budget, tool surface, and evaluator. | Relative model performance in that locked harness only. |
| Which harness is stronger? | Full-factorial model × harness matrix, locked environment and budget, multiple trials, held-out tasks. | Configuration effects and interactions; component causality still needs ablations. |

Terminal-Bench 2.0 is direct empirical evidence that harness choice is material. The official leaderboard was run and verified by the Terminal-Bench team and forbids changing timeouts/resources. Same-model comparisons include:

| Nominal model | Higher configuration | Lower configuration | Spread | Source |
|---|---:|---:|---:|---|
| Claude Opus 4.6 | Meta-Harness 76.4% | Claude Code 58.0% | 18.4 points | [Official TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0) |
| GPT-5 | Codex CLI 49.6% | mini-SWE-agent 33.9% | 15.7 points | [Official TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0) |
| Gemini 2.5 Pro | Terminus 2 32.6% | OpenHands 16.4% | 16.2 points | [Official TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0) |
| Claude Opus 4.5 | Droid 63.1% | OpenCode 51.7% | 11.4 points | [Official TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0) |

These are not clean randomized ablations: release dates, hidden provider changes behind aliases, effort controls, and agent implementation details can differ. They establish that a published agent score cannot be assigned to model weights alone. They do not establish that Meta-Harness’s named mechanism causes exactly 18.4 points.

Infrastructure is itself part of the measured configuration. Holding the model, harness, and task set constant, Anthropic measured a six-point Terminal-Bench 2.0 swing between resource setups and found pod errors unrelated to model ability in as many as 6% of tasks ([Anthropic infrastructure-noise study](https://www.anthropic.com/engineering/infrastructure-noise)). Differences smaller than infrastructure variance, run variance, or confidence intervals are not meaningful rank evidence.

## 1.2 Current benchmark-leader snapshot—and what it does not prove

### SWE-bench Verified

The official leaderboard source currently lists two systems tied at 79.2%: open-system Live-SWE-agent + Claude 4.5 Opus and closed-system Sonar Foundation Agent + Claude 4.5 Opus. The same official metadata marks each `checked: false`; it also records one attempt per instance for both ([official leaderboard JSON](https://raw.githubusercontent.com/swe-bench/swe-bench.github.io/master/data/leaderboards.json)). This is a leaderboard top, not an independently reproduced harness ranking.

The leaderboard itself mixes simple loops, retrieval systems, multiple attempts, and review/selection systems. SWE-bench therefore created a separate bash-only lane: all models use mini-SWE-agent with a minimal shell and ReAct loop, specifically to make model comparison more apples-to-apples. It warns that mini-SWE-agent 1.x and 2.x are not necessarily comparable because 2.x changed from parsed text actions to tool calling ([SWE-bench Verified methodology](https://www.swebench.com/verified.html)).

The official data also illustrates why “leader” is underspecified:

* Live-SWE-agent is open-system and uses Claude Opus 4.5; Sonar uses the same model family but does not publish the full system in the leaderboard metadata ([official leaderboard JSON](https://raw.githubusercontent.com/swe-bench/swe-bench.github.io/master/data/leaderboards.json)).
* The top fixed minimal-harness row shown in that same data is mini-SWE-agent + Claude 4.5 Opus at 76.8%, only 2.4 points below the unrestricted top; mini-SWE-agent + Claude Opus 4.6 is 75.6% ([official leaderboard JSON](https://raw.githubusercontent.com/swe-bench/swe-bench.github.io/master/data/leaderboards.json)).
* Live-SWE-agent’s repository says it is built on mini-SWE-agent with minimal modifications; its configuration adds a recommended inspect–reproduce–edit–verify workflow, asks the model to create task-specific Python tools, limits cost, executes actions in fresh subshells, and truncates observations above 10,000 characters ([Live-SWE-agent repository](https://github.com/OpenAutoCoder/live-swe-agent); [exact config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml)).

The benchmark no longer supports frontier capability claims without qualification. OpenAI stopped reporting SWE-bench Verified after finding contamination and test-design problems. Its audit reviewed 138 hard problems with at least six experienced engineers per case and found material test/specification issues in 59.4% of that audited subset; this is not 59.4% of all 500 tasks, but it is enough to compromise interpretation at the frontier ([OpenAI SWE-bench Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)).

### Terminal-Bench 2.0 and 2.1

The current official Terminal-Bench 2.0 top is NexAU-AHE + GPT-5.5 at 84.7% ±2.1, followed by LemonHarness with multiple models at 84.5% ±2.6 and Capy + GPT-5.5 at 83.1% ±2.1. The Terminal-Bench team runs and verifies submissions ([official TB 2.0 leaderboard](https://www.tbench.ai/leaderboard/terminal-bench/2.0)). NexAU-AHE’s paper holds a base model fixed during ten evolve–evaluate iterations and reports 69.7%→77.0% with GPT-5.4, with a frozen-harness transfer experiment; the 84.7% leaderboard row uses the newer GPT-5.5, so it still combines model and harness gains ([AHE paper](https://arxiv.org/abs/2604.25850); [AHE repository](https://github.com/china-qijizhifeng/agentic-harness-engineering)).

Terminal-Bench 2.1 is the stronger current benchmark version because it repairs 28 of 89 tasks and adds continuous validation. The official page reports that nine tasks had drifted external dependencies and shows score shifts as large as +12.1 points for Claude Code + Opus 4.6 after correction ([Terminal-Bench 2.1 release](https://www.tbench.ai/news/terminal-bench-2-1)). Its current official leader is Claude Code + Fable 5 at 83.8% ±1.2, narrowly ahead of Codex + GPT-5.5 at 83.1% ±1.1; both are closed model-bound systems, and the confidence intervals overlap ([official TB 2.1 leaderboard](https://www.tbench.ai/leaderboard/terminal-bench/2.1)). The leaderboard prohibits resource/timeout modification and links the run artifacts, but these rows do not isolate harness from model.

Terminal-Bench’s integrity update documents why team-run evaluation is necessary but insufficient: the maintainers removed submissions that changed timeouts, embedded encrypted solutions, or uploaded tests; they also rescored trials where an agent fetched online solutions. Passing trials now require standardized ATIF trajectories and an agent judge, with challenges permitted ([Terminal-Bench integrity update](https://www.tbench.ai/news/leaderboard-integrity-update)).

### Successors and complementary evaluations

No single successor solves all validity problems:

* **SWE-bench Pro** increased task length, repository diversity, private-code coverage, and environment work. Scale describes 731 public, 276 private, and 858 held-out tasks with human augmentation and Docker environments ([Scale methodology](https://labs.scale.com/leaderboard/swe_bench_pro_public)). However, OpenAI’s July 2026 audit flagged 200/731 tasks through its pipeline and 249/731 through human annotation, estimating about 30% broken due to overly strict/weak tests and under/mis-specified prompts. OpenAI retracted its prior recommendation ([OpenAI SWE-bench Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)). Pro is therefore not a clean replacement.
* **SWE-bench Live** continuously mines newer GitHub activity. Its first release contained 1,319 tasks across 93 repositories, and the paper reports a gap versus static SWE-bench under controlled evaluation ([SWE-bench Live paper](https://arxiv.org/abs/2505.23419); [live leaderboard](https://swe-bench-live.github.io/)). Freshness reduces training-contamination risk but does not by itself validate prompts, tests, or future-commit leakage.
* **SWE-rebench** runs models centrally with the same minimal scaffold, prompt, context, and environment and allows time-window slicing of fresh tasks. Its April–May 2026 page currently covers 110 problems from 86 repositories ([methodology](https://swe-rebench.com/about); [leaderboard](https://swe-rebench.com/)). This is useful for model comparison; by design, it does not rank full harness capability.
* **Terminal-Bench 2.1** repairs benchmark drift and continuous-validation issues while retaining 89 terminal tasks. Its own revisions changed representative agent-model scores by 1.3 to 12.1 points, demonstrating that task validity is load-bearing ([release details](https://www.tbench.ai/news/terminal-bench-2-1)). Terminal-Bench 3.0 is only listed as “coming soon”; no design or results are public on the official leaderboard index ([leaderboard index](https://www.tbench.ai/leaderboard)).
* **CodeClash** changes the object from a specified patch to multi-round goal-oriented development. Across 1,680 tournaments and six arenas, the paper reports that top models lost every round to expert human programmers and accumulated maintenance problems, exposing strategic and long-term weaknesses hidden by issue-resolution tests ([CodeClash paper](https://arxiv.org/abs/2511.00839); [repository](https://github.com/CodeClash-ai/CodeClash)).
* **PaperBench** tests full research replication and decomposes 20 ICML papers into 8,316 rubric items co-developed with paper authors. Its judge is itself evaluated on a separate judge benchmark. The best tested 2025 configuration scored 21.0%, leaving substantial headroom ([OpenAI PaperBench](https://openai.com/index/paperbench/)).
* **TheAgentCompany** supplies a self-contained software-company environment with web, code, programs, file sharing, and coworker communication; its original best baseline completed 24% ([paper](https://arxiv.org/abs/2412.14161); [official site](https://the-agent-company.com/)). It tests cross-tool workplace behavior absent from SWE-bench.
* **Harness-Bench** is the first recent benchmark explicitly organized as a model × harness matrix: 106 offline sandboxed tasks, six configurable harnesses, eight model backends, and 5,194 reported trajectories. It reports a 23.8-point aggregate gap between NanoBot and OpenClaw over the same backend pool, but correctly labels this configuration-level and partly LLM-judged rather than causal ([Harness-Bench](https://arxiv.org/abs/2605.27922)).

The established lesson is to use a **portfolio**: fixed-harness fresh tasks for model comparison, arbitrary-harness tasks for system ceilings, product-specific end-to-end regression tasks for deployment relevance, and audited trajectory/outcome checks for integrity. VS Code publicly follows this pattern: public benchmarks plus VSC-Bench, a containerized suite covering editor, terminal, browser, MCP, multi-turn, multilingual, correctness, effort, token, and latency behavior ([VS Code harness and VSC-Bench](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)).

## 1.3 What successful harnesses contribute

### The simple executable loop

mini-SWE-agent is the clearest anti-overfit baseline. It exposes only bash, runs each action independently via `subprocess.run`, and keeps linear message history. Its authors explicitly argue that the independent shell improves stability and that linear history improves debugging. It scores above 74% on SWE-bench Verified with current models ([mini-SWE-agent docs](https://mini-swe-agent.com/latest/)). The official SWE-bench model lane adopts it precisely because its scaffold contributes little task-specific structure ([SWE-bench Verified](https://www.swebench.com/verified.html)).

This does **not** prove bash is always the optimal interface. It establishes that any richer harness must beat a very strong, cheap baseline and justify its complexity.

### Agent-computer interface engineering

SWE-agent’s central result was that interfaces designed for models—repository navigation, file editing, execution, and observation—could materially improve performance over non-interactive generation ([SWE-agent paper](https://arxiv.org/abs/2405.15793)). Anthropic’s later guidance generalizes this:

* avoid formats with unnecessary escaping or bookkeeping;
* use clear parameter names and examples;
* make invalid actions hard;
* require absolute paths when relative paths cause errors;
* test tool use over many realistic examples ([Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)).

Anthropic’s tool-evaluation report adds held-out tasks, full-transcript review, tool-error/redundancy metrics, selective high-impact tools, namespacing, pagination/filtering/truncation, and high-signal responses. It reports that small tool-description changes fixed systematic search-query behavior and that agent-optimized tools beat expert implementations on held-out internal tests ([Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)).

VS Code demonstrates model–interface interaction in production. Claude models receive `replace_string_in_file`, GPT models receive `apply_patch`, Gemini needs specific tool-use/history treatment, and each model family gets a tuned system prompt and tool set ([VS Code coding harness](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)). A universal adapter is not neutral; it can privilege the model whose training/API conventions it matches.

### Context construction and progressive disclosure

Anthropic frames context as a finite attention budget with diminishing returns and recommends the smallest high-signal set at each step ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Three concrete mechanisms recur:

1. **Just-in-time discovery.** Anthropic’s Tool Search loads names/descriptions first and full schemas only when selected; programmatic tool calling keeps loops and intermediate data out of the model context ([advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)).
2. **Bounded observations.** Live-SWE-agent caps normal command output and returns head/tail plus an elision count when over limit ([config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml)). Anthropic’s parallel-compiler harness prints compact status and writes details to grep-friendly logs ([parallel compiler report](https://www.anthropic.com/engineering/building-c-compiler)).
3. **Cache-stable prompt construction.** VS Code preserves repeated prompt prefixes, defers heavy tool schemas, and measures cache, token, latency, and success tradeoffs ([token-efficiency report](https://code.visualstudio.com/blogs/2026/06/17/improving-token-efficiency-in-github-copilot)).

### Durable state for long horizons

Compaction alone does not reliably carry operational state. Anthropic observed agents attempting to one-shot applications, leaving half-complete work, or declaring completion early. Its remedy was deliberately ordinary engineering state: an initializer, startup script, structured feature list initially marked failing, progress log, git commits, one-feature-at-a-time execution, and end-to-end testing before marking a feature passed ([long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

OpenAI’s agent-first engineering report gives the repository-scale analogue: repository-local versioned knowledge, agent-legible UI/logs/metrics, executable skills, structural tests, custom linters, and mechanically enforced architectural dependency directions. The reported million-line project and 1,500 PRs are a first-party case study, not a controlled benchmark, but the mechanisms are concrete and inspectable ([OpenAI harness engineering](https://openai.com/index/harness-engineering/)).

### Verification and feedback

The best harnesses do not ask the model whether it is done; they inspect the world. Anthropic distinguishes the transcript from outcome and recommends multiple graders and multiple trials ([eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Terminal-Bench supplies an instruction, environment, reference solution, and tests; Harbor structurally separates tests from the agent container and supports richer rewards ([Terminal-Bench paper](https://arxiv.org/abs/2601.11868); [Harbor format](https://www.harborframework.com/docs/tasks/task-difference)).

For long work, targeted tests enable fast iteration while broad tests protect against regressions. Anthropic’s compiler harness used deterministic per-agent test subsamples during work and a stricter CI gate when late-stage regressions became common ([compiler harness](https://www.anthropic.com/engineering/building-c-compiler)). OpenAI’s repository enforced architectural and “taste” invariants mechanically rather than relying on prose ([OpenAI harness engineering](https://openai.com/index/harness-engineering/)).

### Trajectory observability and evidence-driven improvement

Meta-Harness stores each candidate’s source, score, and full traces in a filesystem that the proposer can inspect with ordinary file operations. In its text-classification ablation, score-only reached 34.6 median/41.3 best, score-plus-summary 34.9/38.7, and full trace access 50.0/56.7; the authors interpret raw traces as the key ingredient ([Meta-Harness](https://arxiv.org/abs/2603.28052)). This is one-domain ablation, but it is the clearest evidence against replacing raw evidence with only generated summaries.

AHE makes each component file-level and revertible, distills trace evidence but preserves drill-down, and requires the evolving agent to predict the effect of each edit before the next evaluation falsifies or supports it. Its paper reports that ablated gains localized to tools, middleware, and long-term memory rather than system-prompt prose ([AHE paper](https://arxiv.org/abs/2604.25850); [repository](https://github.com/china-qijizhifeng/agentic-harness-engineering)). This supports change manifests and granular rollback more strongly than it supports adopting AHE’s entire runtime.

## 1.4 Architectural archetypes and their evidence

| Archetype | Harness contribution | Best-supported use | Principal risk | Evidence |
|---|---|---|---|---|
| Minimal ReAct/bash loop | Lets a strong model inspect, act, observe, and self-correct with minimal mediation. | General coding baseline; model comparison. | Shell quoting, huge output, unsafe breadth, weak affordances for some models. | [mini-SWE-agent](https://mini-swe-agent.com/latest/) |
| Curated ACI / CodeAct | Ergonomic search/edit/execute operations or one unified executable action space. | Repository work where interface errors dominate. | Too many overlapping tools; model-specific mismatch. | [SWE-agent](https://arxiv.org/abs/2405.15793); [OpenHands CodeAct docs](https://docs.openhands.dev/openhands/usage/agents) |
| Deterministic pipeline | Predefined localization, candidate generation, validation, selection. | Narrow, verifiable repair tasks. | Brittle outside known task topology; less adaptive. | [Agentless](https://arxiv.org/abs/2407.01489) |
| Runtime self-extension | Agent writes task-specific tools during a run. | Repeated or awkward task-local operations. | Self-authored-tool bugs and benchmark-specific tricks. | [Live-SWE-agent](https://arxiv.org/abs/2511.13646); [config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml) |
| Generator/evaluator loop | Separate production and grading roles with executable criteria. | Outputs with reliable acceptance tests or calibrated rubrics. | Judge bias, cost, convergence to rubric artifacts. | [Anthropic long-running app harness](https://www.anthropic.com/engineering/harness-design-long-running-apps) |
| Parallel worker team | Separate contexts and workspaces increase throughput on independent branches. | Research and genuinely separable failures/tasks. | 15× token use, merge/coordination costs, duplicated work. | [Anthropic research system](https://www.anthropic.com/engineering/multi-agent-research-system); [compiler team](https://www.anthropic.com/engineering/building-c-compiler) |
| Offline harness evolution | Search over prompts/tools/middleware/memory using traces and scores. | Measured improvement on a stable task family. | Benchmark overfit, costly search, regression on new phases. | [Meta-Harness](https://arxiv.org/abs/2603.28052); [AHE](https://arxiv.org/abs/2604.25850); [continual study](https://arxiv.org/abs/2607.14004) |

The archetypes are composable, but composition is not automatically beneficial. Anthropic’s 2026 long-running-app work explicitly removed components one by one after a bulky three-agent planner/generator/evaluator harness became slow and expensive, because newer models could natively handle some decomposition work ([long-running app harness](https://www.anthropic.com/engineering/harness-design-long-running-apps)). This is direct support for a recurring complexity audit.

# 2. Promising but not yet proved

## 2.1 Runtime self-authored tools

Runtime task-specific tool creation is **likely (55-80%)** useful when an agent encounters repeated high-friction operations. Evidence: Live-SWE-agent’s public configuration explicitly prompts tool creation and the open system ties the official SWE-bench Verified top at 79.2% with Opus 4.5 ([config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml); [official leaderboard data](https://raw.githubusercontent.com/swe-bench/swe-bench.github.io/master/data/leaderboards.json)).

The mechanism-level gain is **UNVERIFIED**: the settling experiment is a preregistered A/B test on fresh SWE-bench Live or private owner tasks, same model/seed/budget, with only self-tool creation enabled or disabled, measuring resolve rate, tool failures, tokens, and unsafe actions. The current paper compares complete configurations and static benchmarks rather than isolating tool synthesis ([Live-SWE-agent paper](https://arxiv.org/abs/2511.13646)).

## 2.2 Automated harness evolution with full trace access

Trace-informed harness search is **likely (55-80%)** to find useful local improvements when objective evaluators and held-out tasks exist. Evidence: Meta-Harness’s raw-trace ablation, its cross-model math transfer, and AHE’s fixed-model 69.7%→77.0% Terminal-Bench 2 result plus reported frozen-harness transfer ([Meta-Harness](https://arxiv.org/abs/2603.28052); [AHE](https://arxiv.org/abs/2604.25850)).

Long-term compounding is **UNVERIFIED and roughly even (45-55%)**. The settling experiment is repeated chronological optimization over at least three disjoint owner-task cohorts, with a frozen permanent regression suite, no access to future cohorts, and rollback on any protected regression. A three-day-old preprint reports that GEPA transferred below baseline and Meta-Harness transferred but regressed after second-phase re-optimization, while RELAI-VCL’s regression-controlled loop continued improving ([continual study](https://arxiv.org/abs/2607.14004)). Until independently reproduced, it is evidence for regression control, not a production-ready optimizer.

## 2.3 Regression-controlled continual harness learning

Regression-controlled evolution is **likely (55-80%)** safer than unconstrained prompt/harness optimization. Evidence: in the published two-phase Terminal-Bench experiment, RELAI-VCL achieved a 76.4% lifelong average versus 66.0% GEPA, 64.6% Meta-Harness, and 58.7% baseline, and was the only evaluated optimizer with both positive transfer and second-phase improvement ([paper and released artifacts](https://arxiv.org/abs/2607.14004)).

The result is **UNVERIFIED** outside that authors’ benchmark. The settling experiment is an independent reproduction using owner correction cases in chronological order, with exact optimizer budgets and a hidden final cohort. Do not infer that RELAI’s runtime or algorithm should be installed from one new preprint.

## 2.4 Model-specific harness profiles

Per-model prompt/tool/history profiles are **very likely (80-90%)** beneficial. Evidence: VS Code discloses different edit tools and prompt/history handling by model family; SWE-bench warns that even action-parsing versus native tool calling changes comparability; Harness-Bench reports stronger models are less harness-sensitive while weaker models vary more ([VS Code](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode); [SWE-bench Verified](https://www.swebench.com/verified.html); [Harness-Bench](https://arxiv.org/abs/2605.27922)).

The owner-specific optimum is **UNVERIFIED**: settle it with a small factorial matrix of 2-3 model families × current profile versus one tuned profile on the same 30-50 tasks, preserving budgets and running multiple trials.

## 2.5 Selective multi-agent execution

Parallel subagents are **likely (55-80%)** valuable for high-value, genuinely independent work such as broad external research, many unrelated failures, or isolated worktree changes. Evidence: Anthropic reports a 90.2% internal research-eval gain for its multi-agent research system, up to 90% lower wall-clock time from parallel search, and successful compiler work partitioned by failing tests/files ([research system](https://www.anthropic.com/engineering/multi-agent-research-system); [compiler harness](https://www.anthropic.com/engineering/building-c-compiler)).

They are **unlikely (20-45%)** to improve the median tightly coupled coding task enough to justify default use. Evidence: Anthropic reports approximately 15× chat token use, says coding has fewer parallelizable tasks, and documents 16 compiler agents duplicating the same Linux-kernel failure until the harness created separable oracles ([research system](https://www.anthropic.com/engineering/multi-agent-research-system); [compiler harness](https://www.anthropic.com/engineering/building-c-compiler)).

## 2.6 Harness-Bench as a diagnostic standard

Harness-Bench is **likely (55-80%)** directionally useful because it fixes external tasks/budgets across a full model × harness matrix and retains artifacts and traces. Evidence: 106 tasks, six harnesses, eight backends, and 5,194 trajectories with reported completion/process/efficiency differences ([Harness-Bench](https://arxiv.org/abs/2605.27922)).

Its exact ranking is **UNVERIFIED**: the settling experiment is independent reruns of a sampled factorial block, replacement of the LLM process judge with blind human review, and publication of trial variance. The paper itself says its aggregate scores partly use an LLM judge and are descriptive, not deployment guarantees.

## 2.7 Fresh, goal-oriented, and product-specific eval portfolios

A mixed eval portfolio is **very likely (80-90%)** more informative than another static issue-resolution score. Evidence: static SWE-bench contamination, SWE-bench Pro’s estimated ~30% broken tasks, Terminal-Bench 2.1’s 28 repaired tasks, CodeClash’s exposure of long-term strategy/maintenance failures, and VS Code’s decision to supplement public tests with product workflows ([OpenAI Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); [OpenAI Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/); [TB 2.1](https://www.tbench.ai/news/terminal-bench-2-1); [CodeClash](https://arxiv.org/abs/2511.00839); [VSC-Bench](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)).

The best weighting of public, fresh, product, adversarial, and longitudinal tasks is **UNVERIFIED**: settle it by correlating each suite with blinded owner acceptance on real tasks over a quarter.

# 3. What is hype, and how to tell

## 3.1 “Our agent tops benchmark X, therefore our harness is best”

This inference is invalid when model, attempts, effort, tools, internet, resource budget, or evaluator differ. SWE-bench’s unrestricted leaderboard explicitly mixes simple loops, retrieval, multiple rollout, and review systems, while its bash-only lane exists to separate model comparison ([SWE-bench Verified](https://www.swebench.com/verified.html)). Terminal-Bench rows label both agent and model and show same-model spreads ([TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0)).

**Detection rule:** reject any harness-superiority claim lacking (a) a same-model comparison, (b) locked budget/environment, (c) attempt count, (d) trajectories, (e) uncertainty, and (f) held-out or fresh transfer.

## 3.2 “Verified” means clean

Verification usually means the submitted system was run as claimed, not that the task set is unbroken or uncontaminated. Terminal-Bench later found altered timeouts, embedded solutions, uploaded tests, and online solution retrieval despite prior submission processes ([integrity update](https://www.tbench.ai/news/leaderboard-integrity-update)). Terminal-Bench 2.1 repaired 28/89 tasks ([release](https://www.tbench.ai/news/terminal-bench-2-1)). OpenAI found major residual issues in its audited SWE-bench Verified subset and about 30% broken tasks in SWE-bench Pro ([Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); [Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)).

**Detection rule:** demand independent task audits, final-state graders, solution-leak checks, task-version pinning, and sensitivity analysis after removing disputed items.

## 3.3 “Self-improving” means generally improving

An optimizer can exploit a fixed benchmark, learn a brittle prompt, or erase prior gains. The new continual study found all three optimizers improved in a conventional static phase, yet GEPA transferred below baseline and Meta-Harness failed to improve after another phase ([continual study](https://arxiv.org/abs/2607.14004)).

**Detection rule:** require chronological cohorts, hidden transfer, a protected regression set, frozen-harness evaluation on different models/tasks, and explicit rollback. Same-split curves are optimization evidence, not generality evidence.

## 3.4 “More context/memory/tools is better”

Anthropic describes context rot and diminishing returns, recommends the smallest high-signal context, and warns that overlapping tools distract agents ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [tool design](https://www.anthropic.com/engineering/writing-tools-for-agents)). VS Code reports tool schemas historically consuming fixed context on every turn and now defers them ([token efficiency](https://code.visualstudio.com/blogs/2026/06/17/improving-token-efficiency-in-github-copilot)).

**Detection rule:** require accuracy-versus-token and accuracy-versus-tool-count curves, retrieval precision, cache hit rate, and ablations. A feature list is not a benefit measurement.

## 3.5 “More agents is better”

Multi-agent research gains are partly compute scaling: Anthropic says token use alone explained 80% of performance variance in its BrowseComp analysis, while the system used roughly 15× chat tokens. It also says dependent tasks are poor fits ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)).

**Detection rule:** compare against a token- and tool-call-matched single agent, report wall time and merge/rework, and demonstrate task separability before adding workers.

## 3.6 “Long autonomous run” equals completed work

Agents may stop early, loop, pass weak tests, or produce outputs no human has validated. Anthropic’s long-running work documents premature victory and half-implemented states; its compiler report warns that passing tests does not make unreviewed software safe ([long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [compiler report](https://www.anthropic.com/engineering/building-c-compiler)).

**Detection rule:** grade the final artifact and environment, not duration or narration; use independent acceptance checks and explicit residual-risk reporting.

## 3.7 “A large framework is production readiness”

Harness-Bench’s lightweight NanoBot outscored broader runtimes in its configuration matrix, while mini-SWE-agent remains competitive with about 100 lines. Those results do not prove “small always wins,” but they invalidate framework size as a quality proxy ([Harness-Bench](https://arxiv.org/abs/2605.27922); [mini-SWE-agent](https://mini-swe-agent.com/latest/)).

**Detection rule:** ask which measured failure each subsystem removes, its regression cost, token cost, and deletion ablation. Complexity without a failure-linked benefit is liability.

# 4. Specific things this owner’s harness should adopt

The recommendations below are external-design inputs, not claims about what the owner already has. Every proposal rides existing hooks, skills, MCP, shell, git, and native agent primitives. None requires a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 4.1 Make “model + harness profile + environment + budget” the run identity

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Every run/eval record should include: provider/model/version or snapshot, reasoning/effort, harness version, active instruction bundle, tool catalog hash, environment image/OS, permissions/network policy, token/cost/step/time budgets, attempt index, and evaluator version. Never publish or compare a bare model score.

This is **very likely (80-90%)** to prevent false attribution because Terminal-Bench, SWE-rebench, Anthropic’s eval definitions, and Harness-Bench independently treat configuration as the measured unit ([TB 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0); [SWE-rebench](https://swe-rebench.com/about); [Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [Harness-Bench](https://arxiv.org/abs/2605.27922)).

**Acceptance test:** two runs that differ in any listed field receive different immutable IDs; a report cannot render without these fields.

**Anti-overfit gate:** metadata only, on the existing run/log bus. No runtime added.

## 4.2 Set a minimal single-agent loop as the control and complexity budget

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Define a control profile with one model, one inspect–act–observe loop, shell plus the smallest safe file-edit/search surface, linear history, native compaction, and explicit completion. Every extra planner, reviewer, memory layer, router, or worker must name the observed failure it addresses and beat this control on held-out owner tasks at matched budget.

This is **very likely (80-90%)** to avoid harness overfit. Evidence: mini-SWE-agent’s strong result, Agentless’s competitive deterministic pipeline, and Anthropic’s repeated “simplest solution”/component-removal guidance ([mini-SWE-agent](https://mini-swe-agent.com/latest/); [Agentless](https://arxiv.org/abs/2407.01489); [Anthropic long-running app harness](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

**Acceptance test:** every enabled non-control component has an owner, target failure fingerprint, before/after metrics, and deletion date/review. Components without evidence default off.

**Anti-overfit gate:** explicitly makes the ~100-line pattern the control; adds no architecture.

## 4.3 Add model-specific adapter profiles, not model-specific policy forks

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Maintain small per-model profiles for edit interface, tool-call mode, reasoning effort, history normalization, output cap, and prompt verbosity. Keep safety, task semantics, and completion criteria shared. Version every profile and test each model on both the generic control and its profile.

Expected benefit is **very likely (80-90%)**, based on VS Code’s disclosed Claude/GPT/Gemini differences and SWE-bench’s 1.x/2.x comparability warning ([VS Code](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode); [SWE-bench Verified](https://www.swebench.com/verified.html)).

**Acceptance test:** profile wins on a prespecified metric across at least two held-out task categories without increasing unsafe or malformed calls; otherwise use generic.

**Anti-overfit gate:** configuration on the existing loop; no provider router daemon.

## 4.4 Use progressive disclosure for skills and tools

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Expose a compact core—shell, read/search, patch, test, and completion—then make specialized skills/MCP tools discoverable by name/description and load full instructions/schema only after selection. Namespace by service/resource, remove redundant wrappers, and keep destructive/open-world annotations visible.

This is **very likely (80-90%)** to reduce context and selection errors. Anthropic documents tool search, programmatic calls, examples, namespacing, selective tools, and high-signal outputs; VS Code reports the context/caching benefit of deferred schemas ([advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); [tool design](https://www.anthropic.com/engineering/writing-tools-for-agents); [VS Code token efficiency](https://code.visualstudio.com/blogs/2026/06/17/improving-token-efficiency-in-github-copilot)).

**Acceptance test:** measure schema tokens, irrelevant tool calls, invalid parameters, cache hit rate, task success, and discovery misses before/after. Roll back if discovery misses erase token gains.

**Anti-overfit gate:** uses native skill/MCP discovery; no registry service or vector index.

## 4.5 Build a tool-contract linter and executable smoke-test hook

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For every tool, statically check unique names, clear side-effect annotations, bounded output behavior, required/optional arguments, examples, absolute-path policy where relevant, timeout/cancellation, and a terminal success/failure envelope. Run one known-good and one known-bad invocation in preflight. Store the exact schema hash in the run identity.

This is **very likely (80-90%)** to reduce interface failures because Anthropic reports invalid parameters, redundant calls, ambiguous names, relative-path mistakes, and oversized responses as concrete tool defects, and recommends programmatic held-out tool evals ([Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents); [Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)).

**Acceptance test:** the linter detects seeded ambiguous names, missing timeout, unbounded output, and invalid example; preflight proves the detector with a known-present good tool before reporting absence.

**Anti-overfit gate:** one deterministic hook/script; no guardrail framework.

## 4.6 Standardize bounded, terminal-state tool observations

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Wrap long/noisy outputs into: terminal status (`SUCCESS:<id>` or `FAILED:<id> reason`), concise head/tail, byte/token counts, artifact/log path, elapsed time, and next diagnostic handle. Preserve full raw output outside model context. Add pagination/range/filter controls rather than silently truncating with no recovery route.

Expected benefit is **very likely (80-90%)**. Live-SWE-agent’s public config caps results; Anthropic’s compiler harness uses grep-friendly terminal markers and detailed log files; Anthropic’s tool guidance recommends pagination/filtering/truncation ([Live-SWE config](https://raw.githubusercontent.com/OpenAutoCoder/live-swe-agent/main/config/livesweagent.yaml); [compiler harness](https://www.anthropic.com/engineering/building-c-compiler); [tool design](https://www.anthropic.com/engineering/writing-tools-for-agents)).

**Acceptance test:** a 100MB output does not enter context, remains retrievable, carries a terminal status, and does not provoke an identical retry in a replay eval.

**Anti-overfit gate:** result adapter on existing tool bus; raw logs remain filesystem artifacts, not a new telemetry service.

## 4.7 Add a fingerprinted retry budget and circuit breaker

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Hash normalized tool name + error class + salient arguments. On the first failure, return a specific recovery hint; on the second identical failure, inject prior attempts and force a changed precondition; on the third, stop that route and require an alternate tool, reduced scope, or explicit blocked outcome. Provider-not-connected and deterministic schema errors should open the circuit immediately after preflight confirmation.

This is **likely (55-80%)** to reduce wasted loops. The external basis is that observable tool errors/redundant calls are actionable eval metrics, and long-running harnesses need explicit loop control/cancellation ([Anthropic tool evaluation](https://www.anthropic.com/engineering/writing-tools-for-agents); [VS Code loop controls](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)). The magnitude for this owner is **UNVERIFIED**; settle it by replaying historical repeated-failure trajectories through the wrapper and measuring avoided calls without lost recoveries.

**Acceptance test:** seeded deterministic failure produces at most the configured attempts; a transient failure followed by success does not trip permanently; the full raw failure remains linked.

**Anti-overfit gate:** small hook state for the current run, not durable execution infrastructure.

## 4.8 Make long-horizon state explicit and versioned

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For tasks likely to cross compaction/session boundaries, create one machine-readable task-state artifact containing objective, acceptance checks, completed/remaining items, current hypothesis, changed artifacts, verification evidence, failed approaches with preconditions, and next action. Start/resume hooks read it plus git/diff; stop/compaction hooks update it. Treat status changes as append-only events or versioned diffs, not free-form overwrite.

Expected benefit is **very likely (80-90%)** for multi-context work. Anthropic’s initializer/progress/feature-list/git design directly addresses half-implemented work and premature completion; OpenAI emphasizes repository-local, versioned, agent-legible knowledge ([Anthropic long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [OpenAI harness engineering](https://openai.com/index/harness-engineering/)).

**Acceptance test:** a fresh agent with no conversation receives only the objective, state artifact, and repository and correctly identifies last verified state, next action, and retired dead ends in a blinded test.

**Anti-overfit gate:** a file plus hooks on the existing bus; no vector DB, knowledge graph, or durable-execution engine.

## 4.9 Gate “done” on outcome evidence, not narration

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Define completion contracts by task class. Code change: diff exists, requested behavior test passes, relevant regressions pass, no forbidden files changed, and residual failures are enumerated. Research: required artifact exists, every factual claim maps to a source, requested sections and uncertainty labels exist. Operations: verify external state through a read-after-write. A stop hook may push the agent back only when a declared mandatory check is missing; it must not loop on subjective dissatisfaction.

This is **very likely (80-90%)** to reduce false completion. Anthropic distinguishes claimed completion from environment outcome, and its long-running harness only marks features passed after end-to-end checks ([eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

**Acceptance test:** seeded “I’m done” with no artifact is rejected; a valid alternative implementation is accepted; evaluator errors fail visibly rather than being treated as task failure.

**Anti-overfit gate:** deterministic task contracts and hook checks; no trained critic or general guardrail framework.

## 4.10 Establish a three-lane harness eval, with full trajectories

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Maintain:

1. **Frozen regression lane:** owner corrections and severe failures; never optimize only for aggregate score—protected items are hard gates.
2. **Fresh chronological lane:** newly observed tasks unavailable to prior harness edits; measures transfer.
3. **Capability-expansion lane:** new domains/tool combinations, including long-horizon and cross-tool tasks; measures ambition rather than only repair.

Record final artifacts, full trajectories, tool errors, retries, tokens, cost, elapsed time, environment failures, and multiple trials for stochastic tasks. Compare both fixed-model harness variants and fixed-harness model variants.

This is **very likely (80-90%)** the highest-leverage improvement process. Evidence: VS Code’s public+product benchmark portfolio and per-PR eval assessment, Anthropic’s lifecycle eval guidance, fresh benchmark motivation, and continual optimizer regression results ([VS Code](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode); [Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [SWE-bench Live](https://arxiv.org/abs/2505.23419); [continual study](https://arxiv.org/abs/2607.14004)).

**Acceptance test:** a proposed harness change must state the target cohort before evaluation, pass protected items, improve a prespecified metric with uncertainty, and produce inspectable traces. A change selected on fresh results moves those tasks into regression; the next fresh cohort remains hidden.

**Anti-overfit gate:** manifests plus a runner/reporter over existing CLI/hooks. Do not create an eval platform or observability SaaS.

## 4.11 Require falsifiable change manifests and granular rollback

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Each harness edit should declare: target failure fingerprint, causal hypothesis, files/components changed, predicted task-level flips, possible regressions, evaluation cohort, rollback command, and expiration/review date. Prefer one mechanism change per candidate. Store raw traces and summaries; summaries never replace evidence.

This is **likely (55-80%)** to improve learning efficiency. AHE’s decision observability makes edits falsifiable and file-revertible; Meta-Harness’s ablation supports raw trace access; VS Code gates core harness PRs on evals ([AHE](https://arxiv.org/abs/2604.25850); [Meta-Harness](https://arxiv.org/abs/2603.28052); [VS Code](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)).

**Acceptance test:** an auditor can identify why a component exists, the evidence that admitted it, and the exact protected regression set; an ineffective change is reverted without unrelated rollback.

**Anti-overfit gate:** documentation schema and git discipline on the existing bus. This imports AHE’s useful epistemic mechanism, not its optimizer/runtime.

## 4.12 Use selective parallelism with explicit separability and isolation

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Default to one agent. Permit parallel workers only when tasks have disjoint evidence targets or isolated worktrees/artifacts, a merge owner, and sufficient value to justify cost. Good cases: independent research questions, unrelated failing tests, platform-specific investigations, or alternative solution candidates. Bad cases: one serial failure frontier, shared mutable files, or undefined ownership.

Selective value is **likely (55-80%)**; default universal value is **unlikely (20-45%)**, based on Anthropic’s research gain/cost and compiler duplicate-work findings ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system); [compiler team](https://www.anthropic.com/engineering/building-c-compiler)).

**Acceptance test:** compare to a token-matched single agent; record duplicate work, conflicts, merge/review time, total tokens, wall time, and accepted output. Disable parallelism for task classes without net value.

**Anti-overfit gate:** native subagents/worktrees only; no second orchestration runtime.

## 4.13 Put containment below the model

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Use least-privilege filesystem roots, sandboxed process execution, explicit network/egress policy, secret-path denial, read-only defaults for unfamiliar repositories, separate worktrees/containers for parallel agents, and human approval for irreversible or externally consequential actions. Treat web/tool content as untrusted. Do not rely on a prompt or classifier to protect credentials.

This is **almost certain (90-99%)** to reduce blast radius, based on Anthropic’s 24/25 controlled exfiltration result and its conclusion that filesystem and egress boundaries are the defense that holds ([containment report](https://www.anthropic.com/engineering/how-we-contain-claude)).

**Acceptance test:** canary credentials outside the allowed root cannot be read; denied egress cannot be bypassed by shell or generated code; allowed build/test/network flows remain usable; destructive calls require the expected approval.

**Anti-overfit gate:** native sandbox/permission configuration, not a guardrail framework.

## 4.14 Keep prompt caching and tool/context cost visible

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Keep stable prompt prefixes stable, put volatile state later, track cached/uncached tokens, avoid injecting full catalogs or histories by default, and compact around explicit task state. Show cost/latency/cache changes beside success rate in every harness comparison.

This is **very likely (80-90%)** to reduce cost and latency without degrading quality when validated. VS Code reports exact mechanisms—extended prefix caching, deliberate cache breakpoints, deferred tools, and persistent transport—and evaluates success alongside token use ([VS Code token efficiency](https://code.visualstudio.com/blogs/2026/06/17/improving-token-efficiency-in-github-copilot)).

**Acceptance test:** held-out success is non-inferior; uncached tokens, time-to-first-action, total latency, and cost fall; no stale-state bug is introduced.

**Anti-overfit gate:** native caching/context settings; no cache daemon.

## 4.15 Do not adopt an autonomous harness-optimization runtime yet — UNVERIFIED

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).**

Full AHE/Meta-Harness/RELAI-style autonomous evolution would introduce an additional optimization runtime and, depending on implementation, separate analyzers/evolvers and large evaluation infrastructure. That conflicts with the anti-overfit gate’s rejection of a second orchestration runtime unless evidence is exceptional.

Adopting it now is **unlikely (20-45%)** to beat disciplined small-bus iteration on net for this owner. Evidence: high same-benchmark gains exist, but continual results show negative transfer or second-phase regression for two optimizers; AHE’s full stack is materially larger than the owner’s allowed thin-bus pattern ([AHE](https://github.com/china-qijizhifeng/agentic-harness-engineering); [Meta-Harness](https://arxiv.org/abs/2603.28052); [continual study](https://arxiv.org/abs/2607.14004)). This owner-specific net assessment is **UNVERIFIED**; settle it only after the three-lane eval exists, by comparing a bounded optimizer pilot against manual evidence-driven edits at equal rollout/token/human-review budgets over three chronological cohorts.

Adopt the small mechanisms now—raw trace retention, change manifests, predicted flips, protected regressions, granular rollback—not the runtime.

## 4.16 Explicitly reject the previously rejected architecture classes

The external frontier does not justify adding a second orchestration runtime, vector-DB/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework to the default harness:

* **Second orchestration runtime:** rejected by 4.2/4.15; minimal native loop is the control.
* **Vector-DB/KG memory:** context guidance supports just-in-time retrieval and structured durable artifacts, but no surveyed leaderboard establishes that a new semantic-memory service beats filesystem/git/task state at matched budget ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Meta-Harness filesystem design](https://arxiv.org/abs/2603.28052)).
* **Durable-execution engine:** long-run evidence supports explicit state, restart scripts, git, and clean sessions; a new workflow engine is not required ([long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
* **Trained critic:** executable outcome checks and calibrated rubrics are better grounded; LLM judges require separate validation ([PaperBench](https://openai.com/index/paperbench/); [Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
* **Observability SaaS:** filesystem trajectories, manifests, and local summaries supply the load-bearing evidence in Meta-Harness/AHE; no SaaS is necessary ([Meta-Harness](https://arxiv.org/abs/2603.28052); [AHE](https://arxiv.org/abs/2604.25850)).
* **Guardrail framework:** security evidence says environment containment is decisive; use native sandbox, filesystem, egress, and approval boundaries ([Anthropic containment](https://www.anthropic.com/engineering/how-we-contain-claude)).

This rejection is **very likely (80-90%)** correct for a minimal cross-tool owner harness because every desired function has a smaller implementation on the existing bus and the surveyed evidence does not show incremental value from those architecture classes at matched cost.

## Bottom line for the program

The best-known harness is not a named framework. It is an evidence discipline embodied in a small execution loop:

> Give a capable model a small, model-compatible action surface; reveal context and tools just in time; keep execution isolated and observations bounded; persist objective state in versioned artifacts; make success executable; record every trajectory; and admit every added mechanism only after it beats the minimal control on protected and fresh tasks.

That conclusion is **very likely (80-90%)** to survive model improvement because its components address persistent system boundaries—attention, tool contracts, external state, nondeterminism, security, and evaluation validity—rather than simulating reasoning the model may soon perform natively. The evidence is the convergence of minimal-agent results, agent-computer-interface research, production context/tool reports, benchmark integrity failures, and regression-controlled harness studies cited throughout this artifact.
