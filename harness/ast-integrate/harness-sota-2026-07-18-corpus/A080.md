## Executive result

I found **two direct contradictions, both conditional on an opt-in hook mode**:

1. `/update-docs` positively requires reading `.env.example` / `.env.template` / `.env.sample`, while the credential-read hook classifies all `.env.*` names as sensitive and denies the Read call when `HARNESS_CREDENTIAL_GUARD=1`.

Neither contradiction is active **by default in the unpacked configuration**: the credential hook is off unless explicitly enabled, and test-tamper defaults to warning rather than blocking. The actual Windows process environment is **UNVERIFIED — inspect it with `Get-ChildItem Env:HARNESS_CREDENTIAL_GUARD,Env:TEST_TAMPER_MODE -ErrorAction SilentlyContinue` in the Claude Code parent process, then run `/hooks`; that experiment settles whether either opt-in is active on the owner’s live box.** The unpacked `settings.json` sets neither variable (complete search for both names returned no match), but a parent-process environment variable would not need to appear there.

The two runtime outcomes are not inferred from names or comments. I invoked the real hook entry points with controlled payloads. The credential hook emitted `hookSpecificOutput.permissionDecision: "deny"`; the test-tamper hook returned exit code 2 and named the exact production-only `test.skip(...)` line. Claude Code’s official hook contract says a PreToolUse `deny` prevents the tool call, and exit 2 on PreToolUse blocks it; a deny also wins over sibling allow/ask results and applies even in bypass-permissions mode ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks), [hook workflow guide](https://code.claude.com/docs/en/hooks-guide)).

I found **no unconditional/default-mode direct contradiction**. This conclusion is **very likely (80-90%)**, supported by the exhaustive full-file scan, AST extraction of every Python string literal, complete runtime-wiring trace, and controlled positive/negative probes described below. The residual uncertainty is that this Linux bundle cannot expose Windows-only parent environment, per-project settings, plugin hooks, or a live `/hooks` rendering; those are explicitly outside the supplied unpacked trees and are not silently treated as absent.

### Concrete collision

The operator enables `HARNESS_CREDENTIAL_GUARD=1`, invokes `/update-docs`, and the command follows its mandatory first step by attempting `Read` on `C:/repo/.env.example`. `is_sensitive()` reduces the path to basename `.env.example`; `fnmatch('.env.example', '.env.*')` succeeds; the hook returns a PreToolUse deny. The same occurs for `.env.template` and `.env.sample` because all match `.env.*`.

This is direct X versus NOT-X for the same event:

* command: **Read `.env.example`**;
* hook: **credential files must not be read**, and `.env.example` is classified as one.

### Which wins at runtime

**The hook wins.** Controlled invocation:

```text
payload: {"tool_name":"Read","tool_input":{"file_path":"C:/repo/.env.example"}}
env: HARNESS_CREDENTIAL_GUARD=1
exit: 0
stdout: {"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny",...}}
```

Independent negative/default controls:

```text
same payload, HARNESS_CREDENTIAL_GUARD unset -> exit 0, stdout 0 bytes
Read C:/repo/package.json, guard enabled       -> exit 0, stdout 0 bytes
```

Claude Code documents that `permissionDecision: "deny"` prevents the PreToolUse call, that `deny` has the highest merged precedence, and that hooks run before permission-mode checks ([hooks reference](https://code.claude.com/docs/en/hooks), [hooks guide](https://code.claude.com/docs/en/hooks-guide)). `settings.json:71` uses `bypassPermissions`, but the documented ordering means bypass mode does not defeat this deny.

The live-box activation is **UNVERIFIED — the settling experiment is the parent-process environment plus `/hooks` check stated in the executive result.** The conditional behavior itself is verified.

### Minimal edit that resolves it — UNVERIFIED template-safety premise

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a narrow public-template allowlist in `is_sensitive()` before applying `SENSITIVE_GLOBS`:

```python

# after `base = os.path.basename(p).lower()`

    return False
```

Also add three predicate tests proving those exact public template names are allowed while `.env`, `.env.local`, `.env.production`, `service.env`, PEM/key files, and credential files remain denied. This is the smallest semantic repair because it reconciles the command’s exact three inputs without weakening the guard for real environment variants.

**UNVERIFIED security premise:** a file named `.env.example`, `.env.template`, or `.env.sample` contains placeholders rather than live secrets. A filename alone cannot prove that. The experiment that settles the safe implementation is a corpus scan of those three basenames for high-entropy values and known token formats, followed by a fixture in which an accidentally populated template remains blocked or is redacted. Therefore the narrow allowlist is **likely (55-80%)** to resolve the workflow without material regression, based on the conventional role of those filenames and the exact command contract. On the same evidence, adding a content check rather than trusting names alone is **very likely (80-90%)** to be the safer shipping choice if any populated templates are found.
