## Executive verdict

I found **five runtime-relevant coherence conflicts**:

1. The rules forbid bypassing permissions and instruct the harness to use `permissions.allow`, while settings start every session in `bypassPermissions` and suppress its warning. At runtime, bypass mode wins and the allow/deny permission layer does not provide the control the rule promises.
2. The rules instruct agents to use `TodoWrite`, and settings allow `TodoWrite`, but current Claude Code disables that tool by default in favor of the native task tools. The settings do not carry the compatibility flag that would re-enable it.
3. The rules require subagent orchestration, but settings still name the old `Task` tool in the allowlist and two `PreToolUse` matchers. Current Claude Code names the subagent launcher `Agent`; therefore those matcher alternatives do not observe agent launches.
4. The Dart hook rule supplies a matcher object and `$CLAUDE_FILE_PATHS`. Current hook settings require a string matcher and deliver the edited path in JSON on stdin; the example cannot register as written.
5. All six web hook examples place handler fields directly in the matcher group, and three additionally use `$FILE_PATH`. Current hook settings require an inner `hooks` handler array and deliver the path in `tool_input.file_path`; the examples cannot register as written.

The first three are active conflicts between always-loaded behavior/rules and active settings/runtime. The last two are dormant until an owner or agent follows the rule's explicit configuration example; that is still a concrete collision because copying the recommended text produces a dropped hook rather than the advertised formatter, linter, guard, or build check.

I did **not** promote mere non-installation of recommended language hooks, disabled plugins, named skills, or optional thinking configuration into findings. Those cases either do not assert that a capability is currently installed or cannot be decided from settings alone.
