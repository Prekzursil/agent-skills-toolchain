**Unit:** A140

## Executive result

I found **nine genuine command/contract collision families**:

1. three mutually competing “canonical” continuity stores;
2. elicitation commands that require questions after the contract’s first-two-action window;
3. a three-attempt build-fix threshold against the contract’s two-strikes threshold;
4. 10-minute blocking waits against the contract’s non-blocking `longrun` rule;
5. MCP prompt-enhancement output promoted from untrusted data to the replacement task;
6. external model opinions declared “trustworthy” or “authority” against the mandatory generator-critic pass;
7. shell-wrapper Codex fan-out against the global contract’s native-MCP fan-out;
8. `high|medium|low` confidence against the contract’s Sherman-Kent/WEP lexicon;
9. an unconditional command-level ban on `--no-verify` against the contract’s explicit-user-instruction exception.

The most important meta-finding is that the declared precedence ladder is **not runtime enforcement**. `CLAUDE.md` imports `AGENTS.md` at `/local_disk0/codexwork/bundle/claude/CLAUDE.md:3`, while custom command Markdown becomes prompt instructions when invoked. Anthropic documents that imported files are expanded into startup context, that command/skill bodies are instructions Claude follows, and that conflicting `CLAUDE.md` instructions may be chosen arbitrarily. Therefore, for every semantic collision below, the verified runtime answer is: **there is no product-guaranteed winner**. The contract states which text *ought* to win, but both sides remain model-followed prompt text unless an independent hook or permission enforces the behavior. Sources: [Claude Code memory and imports](https://code.claude.com/docs/en/memory), especially the “Import additional files” and “Claude isn’t following my CLAUDE.md” sections; [Claude Code skills/custom commands](https://code.claude.com/docs/en/slash-commands), especially lines describing `.claude/commands/` equivalence and skill contents as instructions.

I could not run a live Windows Claude Code A/B invocation from this Linux job node. **UNVERIFIED: which side this owner’s installed Claude build follows more often in each conflict.** The settling experiment is specified under “Runtime-verification gap.” This does not make the collision unverified: both texts and the absence of a deterministic semantic precedence guarantee are verified. It limits only an empirical adherence-rate claim, which I do not make.

## Duplicate-authority design conclusion

The problem is not merely “some stale commands.” Authority is copied into task prompts in four forms:

- **canonical-store declarations** (`save-session`, `prime`, contract);
- **global behavioral thresholds** (question timing, retries, confidence labels);
- **security/trust policy** (MCP results, model authority, `--no-verify`);
- **transport architecture** (native MCP versus wrapper).

The design recommendation is to make task commands point to one shared behavioral authority for cross-cutting rules. A command would then own only what is unique to that command: inputs, task steps, outputs, and command-specific safety boundaries. The contract would own shared thresholds, trust rules, precedence, and canonical stores.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** The recommended overall edit is a narrow “contract pointers” pass, not a second orchestration runtime: remove or qualify the nine duplicated authorities in the cited command lines and point them to the relevant `AGENTS.md` sections. This is **very likely (80-90%)** to reduce future drift because each conflicting value would have one editable source.
