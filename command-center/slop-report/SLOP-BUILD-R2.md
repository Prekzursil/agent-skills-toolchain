## D2 — the control receipt that refuted itself. Fixed in code.

**Reproduced first, and pinned so it stays reproduced.** The first version of this probe ran
the *live* `_b1_control.py` — which meant that the moment the fix landed, the receipt would
stop reproducing its own verdict: the exact defect class this round exists to close, rebuilt by
me, inside the fix for it. Rewritten to execute the **historical blob** at `fa87d1a2`
(materialised, sha256 asserted equal to the blob, run byte-unmodified). A commit is immutable,
so this reproduction re-runs forever.

`_r2_d2_reproduce.out.json`, verdict `D2-REPRODUCED`, 9/9 checks, grep controlled both ways
(1 hit on a known-present needle, 0 on a random one):

| probe | result |
|---|---|
| sentinel `_zzz_control_no_such_probe_9f3a17.py` in HEAD blobs | **2 files** — `_b1_control.py` and `_b1_control.out.json` |
| what the committed receipt asserts | `quiet_citer_count: 0`, `fire: 248`, `PASS` |
| executing the published command | `rc 1`, `quiet: 2`, `fire: 256`, **`FAIL`** |
| side effect | dirties the tracked receipt (restored with `git checkout --`; verified clean) |

Cause: committing the detector **and** its receipt put the "name that exists nowhere" into the
corpus `citations()` greps. The negative control found itself. It does not self-heal — every
clone re-running the lane's primary detector control got `FAIL`.

**Fix, three lines of substance in `_b1_control.py`:**

1. `--sentinel random` (**default**) generates the absent name at runtime (`uuid4`), so no
   committed byte can contain it.
2. `--sentinel legacy` reproduces the round-1 fixed name and is **required to FAIL** — the
   permanent negative control for this fix. It cannot silently start passing: the legacy literal
   lives in `_b1_control.py` forever, so the grep will always find ≥1.
3. The receipt records the sentinel's **shape**, never the literal, so the receipt can never
   re-poison the corpus. Writing it is now opt-in (`--write`), so the default invocation — the
   one published as the bucket-(c) regenerator — is read-only and exits 0.

**Verified both states** (`_r2_fix_verify.out.json`, verdict `FIX-VERIFIED`, 12/12 checks):

| invocation | rc | verdict | quiet | tracked receipt |
|---|---|---|---|---|
| `_b1_control.py` (default, random) | **0** | PASS | 0 | byte-unchanged, tree clean |
| `_b1_control.py --sentinel legacy` | **1** | **FAIL** | 2 | — |
| `_b1_control.py --write` | 0 | PASS | 0 | refreshed, no literal inside |
| default again, after the write | 0 | PASS | — | byte-unchanged (idempotent) |

Also de-rotted: `fire_citer_count` grows with the repo (248 → 256 in two commits). The checks now
assert **relations** — `fire ≥ 1`, `quiet == 0`, `fire > quiet` — never a pinned number, and the
receipt carries `measured_at_rev` and `counts_drift_with_tree: true`.

**Falsifiable prediction — I made one, and it was REFUTED. The refutation is the best argument
for the fix.**

I predicted the legacy sentinel's citer count would drop **2 → 1** after this round's commits,
reasoning that the receipt no longer carries the literal while the script still does. Measured
at `43cb7a62`: **6**.

```
SLOP-BUILD-R2.md · _VERIFY-SLOP-R1.json · _b1_control.py
_r2_d2_reproduce.py · _r2_fix_verify.py · _r2_msg_a.txt
```

Every one of those is a file that *talks about* the sentinel — this document, the probes that
reference it, my own commit message, the verifier's report. **Use-vs-mention: to a fixed-string
grep there is no difference between using a name and discussing it.** The corpus of citers grows
monotonically with every word written about the bug, so a hardcoded sentinel cannot be rescued
by being careful about what you commit — *writing the bug report poisons it*. That is not a
side-effect of the fix; it is the reason the fix has to be runtime generation rather than
discipline. Round 1's mistake was structural, not careless.

The invariant that actually matters is unaffected and verified at `43cb7a62`:
`--sentinel legacy` → **rc 1** (armed, still correctly failing), default random → **rc 0**.
The number is free to grow; if it ever reaches **0**, the negative control has died.

## O3 — the regeneration hash. Property CONFIRMED, value REFUTED. Sentence split.

- **Round-1 wording (kept, refuted):** *"regenerated byte-identically (sha256-16
  `9ef271460a07b5f4` before and after)"* — one sentence carrying two claims of very different
  durability.
- **Property — CONFIRMED, re-executed** (`_r2_bucket_c.out.json`, 9/9): deleted → **verified
  absent** → ran the published command → came back byte-identical, `rc 0`, and the command now
  leaves the tracked tree clean (it did neither before the D2 fix).
- **Value — REFUTED, and I proved the mechanism instead of conceding it.** The auditor measured
  `fced1207f66487e1`, not `9ef2…`. Control: bump the source's **mtime only** (bytes verified
  unchanged, `b0321b32190fbbf8` before and after; mtime restored) → the regenerated hash becomes
  `a7a2f6388326965b`. A `.pyc` header embeds the source's mtime and size, so the value tracks
  *when the source was last written*, not what it contains. `_b1_cited_probes.py` was
  ruff-formatted before commit, which is exactly why the published value went stale.
- **Correctly scoped:** *the artifact regenerates byte-identically within a run — delete, assert
  absence, regenerate, compare — and that property is what makes it bucket (c). The hash VALUE
  is not a durable receipt and must not be quoted as one.*
- Without the mtime control, "byte-identical" and "the hash is 9ef2…" read as the same claim.
  That conflation is the whole defect.
