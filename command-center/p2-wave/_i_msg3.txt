fix(measure-guard): the charter promised a two-directional ratchet; the code only printed

`.quality/charter.yml` was read rather than assumed, and its `p2-delivery` entry -- added by a
sibling lane when it found main charter-red -- says of this gate:

    "Ratchets on a two-directional baseline (vacuous_declarations 3,
     units_declaring_a_vacuous_contract 23): it fails if the count RISES, and equally if it FALLS
     without the baseline being lowered, so the gate cannot silently loosen."

The gate did not do the second half. `improvements()` printed `IMPROVED ...` and returned; only
`regressions()` fed the failure list, matching `wudeps`. So a governing document made a promise
about this code that the code did not keep.

Two ways to reconcile that, and only one is right here. Weakening the charter sentence would have
made the document true and the estate no safer, and this session has already found the opposite
shape three times: a generated "## Verdict:" line that outlived the hazard it warned about, a
doctor printing a PASS over a file it could not find, and a build wave reporting delivered_verified
from a filter that never read the status field. The promise is also simply correct -- a baseline
left high after the badness is gone keeps authorising it, which is how a ratchet drifts into slack.
So the CODE was brought up to the CHARTER.

`ratchet_findings()` now returns both directions, and the falling message says what to edit rather
than only that something moved. `regressions()` and `improvements()` keep their existing meanings
so the two directions stay separately assertable, which is what let the new test pin them apart.
