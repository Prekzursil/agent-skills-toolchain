## Collision register

### C1 — Formatter wording disagrees within the same Go rule layer

- Artifacts: `claude/rules/golang/hooks.md:15` and `claude/rules/golang/coding-style.md:11-14`.
- Exact lines:
  - `hooks.md:15`: `**gofmt/goimports**: Auto-format .go files after edit`
  - `coding-style.md:13`: `**gofmt** and **goimports** are mandatory — no style debates`
- Class: **CONTRADICTION** (also duplicated policy).
- Why: slash notation conventionally leaves “one of / combined choice” ambiguous, whereas “and” demands both. The first adds an after-every-edit timing requirement; the second only defines mandatory final style. Precedence does not resolve same-level Go rules (`AGENTS.md:129-131`).
- Specific resolution — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**: choose one canonical command sequence and state it literally in both rule files and the existing hook configuration. If both executables are truly required, say “run `gofmt`, then `goimports`”; if one is the canonical formatter, name only that one and make the other an explicit fallback. Keep the operational timing solely in `hooks.md` and link to it from `coding-style.md` to remove duplicate modality.
- Expected effect is **very likely (80-90%)**, because literal command wording removes the observed syntactic ambiguity; evidence is the current slash-versus-`and` mismatch. Which formatter policy the owner actually intends is **UNVERIFIED — run a repository-wide Go formatting comparison and ask the owner to select the canonical diff/command to settle it**.

### C2 — “Extends common/hooks.md” is not an actual load relationship

- Artifacts: `claude/rules/golang/hooks.md:1-9` and `claude/rules/common/hooks.md:1-6`.
- Exact lines:
  - Go rule paths: `**/*.go`, `**/go.mod`, `**/go.sum` (`golang/hooks.md:2-5`).
  - Common hook paths: `**/hooks/**`, `**/settings*.json`, `**/.claude/**` (`common/hooks.md:2-5`).
  - Claim: `This file extends [common/hooks.md]...` (`golang/hooks.md:9`).
- Class: **STALE**.
- Why: the path scopes do not overlap for an ordinary Go source read. Claude Code’s current official documentation says path-scoped rules load when a matching file is read, while unscoped rules load unconditionally: <https://code.claude.com/docs/en/memory>. A Markdown link is not an import directive. ## Coherent resolution design

### R1 — One serialized Go edit handler

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing `per-edit-check` PostToolUse handler rather than creating another runtime. For `.go` Edit/Write/MultiEdit events:

1. Resolve and validate the edited path.
2. Run the explicitly selected formatter sequence.
3. Resolve the owning Go package/module.
4. Run time-boxed `go vet` and `staticcheck` serially against the intended changed scope.
5. Emit terminal-state results that distinguish PASS, FINDINGS, TOOL-MISSING, TIMEOUT, and INTERNAL-ERROR. Findings inject context; hook failure remains fail-open; only AGENTS security classes may block.
6. Feed analyzer outcomes into the existing shared receipt ledger.

This rides the already-wired settings entry at `settings.json:333-342`, satisfies the anti-overfit gate, and adds no second orchestrator, vector/KG memory, durable engine, trained critic, observability SaaS, or guardrail framework. It is **very likely (80-90%)** to close C3-C5, based on the active matcher and deterministic extension dispatch. The experiment named under C3-C5 is required before claiming completion.

If p95 analyzer time exceeds the existing 12-second hook timeout, synchronous per-edit analysis becomes **UNVERIFIED — benchmark the owner’s Go repositories with cold and warm caches to settle it**.
