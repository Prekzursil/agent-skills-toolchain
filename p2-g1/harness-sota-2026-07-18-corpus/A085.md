# A085 — coherence audit: hooks versus settings (`direct-contradiction`)

Date: 2026-07-19  
Subject mirror: `/local_disk0/codexwork/bundle/claude` (read-only unpack of `C:\Users\Prekzursil\.claude`)  
Artifact scope: all 164 `~/.claude/hooks/**/*.py` files versus all 704 physical lines of `~/.claude/settings.json`, including `permissions`, `enabledPlugins`, environment settings, direct hook registration, and the local dispatch manifest.

## Executive result

I found **five configured direct-contradiction classes**. In each, settings broadly pre-authorizes a tool (or globally bypasses its permission check), while a reachable `PreToolUse` hook says **do not execute this particular call**. The five are:

1. allowed `Bash` versus the force-push block;
2. allowed edit/shell tools versus an armed Ulysses HALT tripwire;
3. allowed edit tools versus a file-scope sidecar;
4. globally bypassed RE MCP calls versus re-autolaunch's backend-down deny;
5. globally bypassed RE mutation calls versus the TMS stale-anchor hard block.

At runtime, **the hook wins in all five classes**. This is almost certain (90-99%): the local implementations return exit code 2 or structured `permissionDecision: "deny"`; focused shipped tests exercised four deny paths, while the file-scope path was independently confirmed by AST and direct branch inspection; and Claude Code's official hook reference says `PreToolUse` exit 2 blocks a call, structured `deny` prevents it, and multiple hook decisions use `deny > defer > ask > allow`. The Agent SDK permission documentation independently states that deny rules, explicit ask rules, and hooks are evaluated before permission mode and can still block a tool. Evidence: `~/.claude/hooks/no-force-push/hook.py:52-56`, `ulysses/enforce.py:57-68`, `file-scope/check.py:119-136`, `re-autolaunch/autolaunch.py:397-412`, `tms/stale_anchor.py:280-289`; <https://code.claude.com/docs/en/hooks#pretooluse-decision-control>; <https://code.claude.com/docs/en/agent-sdk/permissions>.

These are not nondeterministic races. They are contradictory policy declarations with a defined winner. `permissions.allow` means “skip normal manual approval”; it does **not** grant immunity from a later hook veto. `bypassPermissions` skips permission prompts but does not suppress `PreToolUse` hooks. That distinction explains runtime behavior but does not make the two source texts coherent: a reader of settings sees unconditional pre-approval, while the hooks implement conditional prohibition for the same call.

I found **no direct contradiction involving `enabledPlugins`**. Several hook files mention capabilities whose official plugins are disabled, but none creates a reachable same-situation “use X / X is disabled” collision: the relevant routers/mirror code is not registered in live settings or the dispatch manifest, and an MCP capability name is not proof that the identically named official plugin is its provider. Treating those mentions as contradictions would conflate independent installation surfaces.

## Runtime precedence, verified rather than assumed

There are two local blocking mechanisms:

* Exit 2: `no-force-push`, Ulysses, file-scope, and TMS write a reason to stderr and return 2.
* Structured JSON deny: re-autolaunch exits 0 but prints `hookSpecificOutput.permissionDecision = "deny"`.

Claude Code's official hook contract says:

* `PreToolUse` runs before permission processing and can allow, deny, ask, or defer: <https://code.claude.com/docs/en/hooks#pretooluse>.
* Exit code 2 on `PreToolUse` blocks the tool call: <https://code.claude.com/docs/en/hooks#exit-code-2-behavior-per-event>.
* Structured `permissionDecision: "deny"` prevents execution, and conflicting hook results resolve `deny > defer > ask > allow`: <https://code.claude.com/docs/en/hooks#pretooluse-decision-control>.
* Permission rules use deny-before-ask-before-allow ordering, while `bypassPermissions` skips prompts: <https://code.claude.com/docs/en/permissions>.
* Most directly, hooks are evaluated before permission-mode handling and can still block a pre-approved or bypassed tool: <https://code.claude.com/docs/en/agent-sdk/permissions>.

The local `cmd-rewrite` hook's structured `allow` does not overturn any deny. Its own code returns `permissionDecision: "allow"` at `hooks/cmd-rewrite/inject-nopager.py:203-211`; official precedence makes every matching deny stronger. Thus there is no last-writer ambiguity for permission decisions, even though the file's comments correctly warn that multiple `updatedInput` writers would be a different kind of conflict (`inject-nopager.py:26-32`).

## Recommended resolution strategy

### Preferred: make conditional hooks explicit exceptions to prompt-bypass policy

CONFIG (settings/JSON only).

The owner must choose which policy is authoritative. The current runtime clearly treats the hooks as authoritative, and the five vetoes are narrow, evidenced safety/reliability mechanisms. The least behaviorally destructive resolution is therefore to retain the hooks and stop presenting settings as unconditional authorization.

One unified edit can resolve Findings 2-5 and most of Finding 1's ambiguity:

1. Change `permissions.defaultMode` from `bypassPermissions` to `default` (or `dontAsk` only if every desired capability is explicitly allow-listed).
2. Replace broad `"Bash"`, `"Edit"`, `"Write"`, and `"NotebookEdit"` allow entries with the narrow permission rules the owner truly intends to pre-approve.
3. Add static deny rules for static invariants such as force push and credential-file Read. Keep stateful decisions (Ulysses, file scope, backend liveness, stale anchors) in hooks because settings cannot express them.

This is likely (55-80%) to improve policy comprehensibility because both source layers then say “normal calls may proceed; these specific hooks retain veto authority,” based on the documented permission model and the five concrete ambiguities above. The workflow-friction impact is **UNVERIFIED; the settling experiment is a one-week shadow inventory of permission decisions followed by an A/B smoke suite measuring prompt count, denied-call precision, task completion time, and owner overrides under current versus proposed settings**.

The alternative is to keep `bypassPermissions` and declare hook vetoes as intentional exceptions in an adjacent machine-checked policy manifest. That would explain the layering but would not literally remove the contradictory settings values. Building such a manifest is unnecessary for this unit and risks adding scaffolding without runtime value.

### Anti-overfit gate

All proposed changes are CONFIG (settings/JSON only) and ride Claude Code's native permission/hook bus. No second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is proposed. The existing hooks already implement the dynamic predicates; replacement with a larger policy service would fail the anti-overfit gate.
