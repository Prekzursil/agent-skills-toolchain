## Verdict

Capture two baselines before any harness change lands:

1. a deterministic, model-free lifecycle baseline, run three times from fresh state for every provider/profile combination; and
2. a stochastic, model-in-the-loop owner-work baseline, consisting initially of 30 versioned tasks and five independent trials per task/provider.

The first is the release gate for exact hook/dispatcher/state behavior. The second estimates end-to-end usefulness, reliability, cost, and failure modes. They must never be collapsed into one score. A deterministic contract failure is a regression even when aggregate task success rises; a stochastic task-score movement is not causal evidence unless the unchanged baseline and candidate were rerun contemporaneously in paired, interleaved slots.

## Reproducibility despite model nondeterminism

1. **Freeze controllable inputs.** Exact task bytes, fixtures, grader, prompt wrapper, tool schemas, CLI/config hashes, model request, budgets, resource profile, service health, and ordering are mandatory.
2. **Use independent trials.** New conversation, new worktree, new state directory, no transcript carry-over, and no feedback from earlier trials.
3. **Never equate temperature zero or a seed with determinism.** If supported, record them; still repeat because tool/network/model serving and long trajectories vary. Primary guidance explicitly calls for multiple trials because model outputs vary ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
4. **Pair future comparisons.** For each task/trial slot, run unchanged baseline A and candidate B with the same task/fixture/budget/resource block. Interleave using recorded `ABBA`/`BAAB` blocks so time/order effects do not all favor one condition.
5. **Rerun A later.** Today’s baseline is an immutable drift anchor. It is not the sole control for a candidate tested weeks later. If contemporaneous A differs materially from today, report environment/model drift before interpreting B−A.
6. **Grade outcomes, not one trajectory.** Permit any valid path that satisfies required final-state/milestone assertions and avoids forbidden effects. ToolSandbox’s milestone/minefield design is prior art for multiple valid tool trajectories ([ToolSandbox](https://arxiv.org/abs/2408.04682)).
7. **Preserve complete traces.** Hash raw trace and final artifacts; sanitize only into a separate derived view. Sanitization logic/version is itself frozen.
8. **Separate cold and warm.** First trial in a block is marked cold; subsequent warm-cache trials are not pooled unless cache state is deliberately part of deployment.
9. **Record fallback.** A fallback model is a different condition, not the same trial. Requested and returned model must be distinct fields.
10. **Control concurrency.** Use one declared concurrency for the baseline. Changing it changes resource contention and therefore the measured system.

## How many runs are needed for a signal?

There is no honest universal run count. Required trials depend on task-to-task variance, within-task stochasticity, baseline success, effect size worth detecting, pairing correlation, and infrastructure failure. The protocol therefore uses the following prespecified tiers.

### Exact/deterministic claims

- One run: detector/fixture development only; never a completion claim.
- Three fresh-state repeats: minimum baseline and release gate (`pass^3`) for deterministic contracts. Any one failure is actionable; no statistical reliability percentage is claimed.
- Ten full unchanged sweeps across three time blocks: estimate the latency/noise envelope before setting a tight performance threshold.

### Stochastic capability/reliability claims

- Three trials per task: provisional smoke only.
- Five trials per task: today’s minimum useful baseline, because it exposes task-level flakiness and permits `pass^2` through `pass^5`. With 30 tasks, this is 150 trials per provider.
- Thirty independent task clusters is the minimum reporting bank, not proof of small effects. Bootstrap resampling must resample tasks and carry all their trials together. Inspect supports bootstrap standard error (1,000 resamples by default) and clustered standard errors ([Inspect metrics](https://inspect.aisi.org.uk/metrics.html)); use 10,000 task-cluster resamples for the sealed report and record the bootstrap seed.

For scale intuition only, if observations were independent Bernoulli draws at the worst-case 50% pass rate, a two-sided 95% interval needs approximately 97 observations for ±10 percentage points, 385 for ±5 points, and 1,068 for ±3 points (`n ≈ 1.96² × 0.25 / margin²`). Repeated trials on the same task are clustered, so counting 150 task-trials as 150 independent observations would be anti-conservative.

For a future A/B, use the first five paired trials on all 30 tasks as the variance pilot. Compute each task’s mean paired delta `d_i`, its standard deviation `s_d`, and for desired detectable change `δ` use the planning approximation:

`required_tasks = ceil(((1.96 + 0.84) × s_d / δ)²)`

This targets two-sided α=0.05 and 80% power for a paired task-level mean. Then round up by family strata and rerun both A and B on the added tasks. For binary paired outcomes, also report the discordant table and exact McNemar result; the cluster-bootstrap confidence interval over task deltas remains primary because trials within tasks are dependent.

The initial 30×5 design is **likely (55-80%)** to identify large, family-wide regressions (for example, a recurrence of the measured quote/schema/dead-MCP failure classes) because it supplies 30 independent task clusters and repeated outcomes. It is **unlikely (20-45%)** to resolve a true 3–5 point aggregate change, because even the optimistic independent-draw calculation needs hundreds to more than a thousand observations and task clustering widens uncertainty. The five-trial pilot and formula above settle the actual required count; an inconclusive result must be labeled inconclusive, not “no change.”

### Promotion decision, declared before seeing candidate results

A candidate can replace the baseline only when all apply:

1. deterministic suite remains `pass^3` in both providers/profiles;
2. zero new critical safety/correctness violations;
3. paired task-cluster 95% bootstrap interval excludes the unacceptable region for the primary outcome;

Provisional practical margins—success −5 points, critical violations +0, p95 latency +20%, cost +20%, and per-tool error +2 points—are **UNVERIFIED** owner-utility choices. A short owner decision plus the unchanged-run noise experiment settles them before candidate scores are revealed. ## Failure taxonomy and required oracles

| Failure class | Primary signal | Independent corroboration | Count against agent score? |
|---|---|---|---|
| agent | final-state grader fails | trace shows available correct path/tool | yes |
| harness | terminal/action/state violates contract | production-independent wrapper result | yes, separately |
| infra | service/resource health fails | known-positive control also fails | no in capability numerator; report and replace only by policy |
| grader | oracle solution fails or valid alternative rejected | no-op/malformed control plus transcript review | invalidate affected task version |
| timeout | wall deadline exceeded | process/resource trace | yes unless independent infra control failed |
| critical violation | forbidden side effect or secret/redaction breach | final-state/minefield plus trace | always; never averaged away |

Absence claims require the detector to find a known-present item and a mechanically independent second signal, matching the confirmed failure lesson in `INPUT-known-harness-defects.md:111-129`. For example, “no hook record” requires both a known hook fire joined into the wrapper trace and a separate state/terminal lookup; the broken historical detector cannot be used (`corpus.json:13261`).
