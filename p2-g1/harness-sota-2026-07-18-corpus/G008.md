# G008 — Blind-spot analysis: unknown unknowns

## Executive verdict

The program is broad in *agent-harness mechanisms* and narrow in *what success is for*. Its supplied catalog decomposes tools, hooks, memory, orchestration, safety, and competing coding agents in detail, but it does not establish an owner-task outcome baseline, a task/modality distribution, or causal evidence that the harness layers improve results. The strongest next round is therefore not another mechanism survey. It is a coverage-and-outcome round that joins interventions to verified work outcomes and deliberately samples task modalities that the current catalogs never assigned.

Three findings dominate:

1. **Thirteen supplied audit artifacts fall through the current normalization fan-in.** E14, E15, and F01–F11 exist in the bundle but occur in neither the structured titles nor the unit-specific prompts of any P1C normalization unit. This is an observed catalog defect, not an inference about content. E14 contains the audit's claimed highest-leverage outcome contract; F01–F11 contain the concentrated red-team findings, including confirmed credential persistence, untrusted-repository loading, destructive-operation exposure, silent-success paths, configuration drift, and real resource exhaustion (`inputs/audit-findings/E14.md:1-35`; `F01.md:1-33`; `F03.md:1-19`; `F05.md:1-24`; `F08.md:1-34`; `F09.md:1-26`; `F10.md:1-18`).
2. **The supplied history has no outcome variable.** It can say which tools errored, what was invoked, and how long transcript files were; it cannot say whether the owner's task was correct, useful, complete, or cheaper because a hook/skill fired. That is independently corroborated by E14's live snapshot reporting `RecordsWithOutcomeField=0` (`inputs/audit-findings/E14.md:28-35`). Any design ranking based only on present telemetry is therefore correlational.
3. **The current catalog has no dedicated work on multimodal inputs/outputs, computer-use/browser work, accessibility, internationalization, human factors, onboarding, or non-coding knowledge work.** This is a claim about dedicated assignments, not about incidental mentions or installed capability. The prior audit proves several such capabilities are present—audio and UI skills, OCR, browser automation, voice/audio, Android tooling (`inputs/audit-findings/A22.md:6,48,79`; `A25.md:43,84,94-105`; `B03.md:25-49`)—which makes the absence of outcome evaluation a live blind spot rather than a speculative market checklist.

It is **very likely (80-90%)** that fixing the catalog/fan-in holes before synthesis will change the program's security and architecture priorities: the omitted set contains the audit's explicit top-ranked proposal plus the entire F-series red-team tranche, and those claims are otherwise not normalized. The confidence is below “almost certain” because subsystem units can independently rediscover some of the same facts.

It is **likely (55-80%)** that outcome linkage and modality-stratified evaluation will prune more harness code than another broad research wave would add. Evidence: E14 reports no outcome field despite 106,054 terminal records and 2,576 shadow records, while E15 argues that multiple duplicate runtimes are still live (`E14.md:28-35`; `E15.md:1-24`). The magnitude is UNVERIFIED; a prospective matched-task ablation, described below, is the experiment that settles it.

## Blind spot 2 — no owner-task outcome baseline

The corpus is excellent failure telemetry and poor fitness telemetry. Its top-level schema contains `_meta`, tool usage, error fingerprints, failures by tool, retry loops, owner-correction candidates, hooks, capability use, and sessions. `_meta` says counts are exact but samples are capped at 12 and bounds absence claims (`inputs/corpus.json:2-11`). `tool_usage` records calls/errors/rates (`:13-28`); session records begin at `:13868` and contain file kind, lines, MB, and timestamps. There is no task identifier, task class, requested deliverable, acceptance test, artifact validity, user rating, abandonment reason, cost, or outcome label.

Two mechanically independent signals support the finding:

1. The corpus schema has no outcome field, while its known-positive error fields are populated. This is a detector against structured data, not prose.
2. E14's independent live-ledger inspection reports `RecordsWithOutcomeField=0` across 106,054 terminal records, 93 task-completed records, and 1,478 stop records (`inputs/audit-findings/E14.md:28-35`).

The supplied catalog's nine P1 corpus axes cover tool reliability, quoting, read-before-write, structured output, retry grind, capability use, owner corrections, session shape, and MCP reality (`inputs/catalog.json:3-75`). None reconstructs task outcomes. P2A09 researches evaluation generally, but external eval research is not a baseline of what this owner actually asks or whether those tasks succeeded.

Consequences:

- Error-rate reduction cannot be translated into owner value. A noisy tool can still enable unique successful work; a zero-error no-op can be worthless.
- KEEP/PRUNE decisions based on invocation frequency risk confusing rare/high-value capabilities with dead weight. P1A06 partially guards against this by asking seasonal/dependency checks, but it still has no observed task-value join.
- Hook and skill effectiveness cannot be ranked causally. “Fired before success” and “caused success” are different claims.
- Full replacement cannot be evaluated. A replacement decision needs matched task quality, reliability, time, cost, and operator burden, not feature count.
