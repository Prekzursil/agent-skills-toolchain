# I05 — Initiative / anticipation calibration: pre-fetching and preparing

## Executive verdict

The harness should not become an agent that guesses a future task and starts doing it. It should become an **option factory**: while there is slack, prepare small, reversible, independently verifiable artifacts at the dependency frontier of already-evidenced goals; keep them out of the working tree; expire them aggressively; and surface them only when a different signal proves relevance. This is **very likely (80-90%)** to reduce restart and setup friction without increasing owner fatigue, because the workspace already has the continuity, routing, digest, and calibration rails, while the corpus shows expensive failures clustered in predictable setup operations. Evidence: the event-ledger/basic-memory roles are already explicit at `/local_disk0/codexwork/bundle/claude/AGENTS.md:28-34,85-91`; open-loop matching and bounded resurfacing already exist at `/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:2-25,38-95`; background notices are already folded into the existing dispatcher at `/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:6-69`; and the corpus records 1,631 unmatched-quote failures, 939 read-before-edit failures, 709 `ENAMETOOLONG` failures, and 232 `ECONNREFUSED` failures at `/local_disk0/codexwork/bundle/inputs/corpus.json:4279-4330,4406-4420`.

The correct unit of anticipation is therefore **a prepared option with a receipt**, not an autonomous action. “Receipt” means an execution result, filesystem/hash observation, second-model verdict, or owner action produced outside the context that proposed the option. Same-context self-review is rejected throughout this design.

No new orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is proposed. All accepted proposals ride the existing event-ledger, open-loop, scheduled-task/background-digest, skill-router, basic-memory, and shared dispatcher buses. No proposal adds a raw Claude hook: scheduled producers write artifacts/receipts, and existing SessionStart/UserPromptSubmit surfaces consume them. This respects the approximately-six-hook ceiling.

## Findings — inferred surprises first

### 1. Preparation escrow: compile options, do not execute guesses

**Improvement — Prepared-option escrow.** Extend each open-loop record with an optional `prepare` object whose lifecycle is `candidate -> prepared -> validated -> activated | expired | invalidated`. A prepared item is a disposable directory containing only read-only research, a command argv, a patch file that has **not** been applied, a test-selection list, cached documentation, or a decision packet. It may not modify the subject worktree, install packages, send messages, create PRs, launch paid jobs, or alter live configuration.

**What it is.** This separates “work that is cheap to ready” from “work that changes the world.” The agent can pre-read likely files, resolve authoritative docs, calculate dependency order, draft a patch outside the repo, or stage a safe command array. Activation remains a normal future task action under existing permissions. Each escrow item stores: `id`, `goal_id`, `thread_id`, `hypothesis`, `source_evidence[]`, `artifact_paths[]`, `external_receipts[]`, `cost_actual`, `created_at`, `expires_at`, `invalidation_predicates[]`, `activation_class`, and `status`.

**Why inferred.** The owner wants initiative and full completion but explicitly treats dropped threads and prompt fatigue as harms. Existing open loops preserve intentions, yet they store only a condition and action (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/add.py:177-189`); the digest stores notices/proposed commands, not reusable prepared work (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:12-18`). Escrow is the missing middle between remembering and acting. It is **very likely (80-90%)** that this will avoid more wrong-work harm than direct speculative execution, because every wrong guess is deletable and no guessed action reaches the live workspace; evidence is the design’s enforced artifact boundary plus CHI guidance to scope service when uncertain and support efficient correction.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add an `escrow.py` CLI beside `open-loops/add.py`, backed by append-only JSONL under the existing open-loop data directory and artifact subdirectories under a bounded temp/cache root. Commands: `propose`, `attach`, `validate`, `activate`, `invalidate`, `expire`, `list --ready`. Use atomic rename and a per-item maximum byte/token/currency budget. Fold a three-line “N prepared / M validated / K expired” reader into the existing `open-loops/resurface` SessionStart check; do not add a hook. Activation only returns paths and the exact receipt—it never applies a patch itself. Wrap the whole CLI and reader in `try/except`; any producer failure writes no item and exits 0 when called from a hook/scheduled path.

**External signal that verifies it.** A prepared item becomes `validated` only after a different tool/process produces a receipt: e.g. `git hash-object`/file stat from a later process matches its source hash, a parser accepts the staged argv/schema, a test collector confirms named tests exist, or a fresh model independently marks the packet relevant to the still-open goal. Usefulness closes only when a later owner request or accepted task consumes the artifact. `prepared` without a receipt is never reported as ready. This obeys the law because neither the proposing context nor its own prose can validate the item.

**SOTA.** Horvitz’s mixed-initiative principles frame automation as decision-making under uncertainty and emphasize timing/user control ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/)). Amershi et al.’s independently practitioner-tested guidelines say to support correction, scope services under uncertainty, learn from behavior, and update cautiously ([CHI 2019 paper](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). The 2026 idle-compute ProAct preprint explicitly separates anticipation and evidence acquisition, but its reported 14.8% fewer turns, 11.7% less user effort, and 28.1% fewer hallucinations are **UNVERIFIED** here; a matched local prepared-vs-reactive trial described in Finding 6 would settle transfer ([paper](https://arxiv.org/abs/2605.25971)).

**Value x effort:** transformative x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for read-only/cache/patch-file preparation; confirm-first for activation whenever activation changes persistent or external state.

### 2. Prepare the dependency frontier, not the predicted final answer

**Improvement — Frontier packets from open threads.** For each active goal, prepare only prerequisites that are (a) dependency-free now, (b) useful across at least two plausible next branches, and (c) invalidated by explicit state changes. Examples: authoritative API contracts, repo map of the files implicated by an open defect, exact failing-test selectors, environment/tool availability receipts, and a comparison table for a pending choice. Do not draft the whole feature or final recommendation merely because it appears probable.

**What it is.** Model each goal as a tiny DAG of observed commitments and prerequisites. Calculate a frontier score:

`option_score = P(any live branch uses artifact) * reuse_value - compute_cost - invalidation_risk - attention_cost`.

Only frontier nodes with positive score enter escrow. `P` is an auditable frequency bucket (`seen once`, `repeated`, `standing contract`), not an opaque learned model. If branches disagree, prepare the common evidence, not either branch’s implementation.

**Why inferred.** “Never drop a thread” can tempt a harness to advance every thread. That would amplify cost and cognitive load. Existing open loops already give contextual predicates and cap resurfacing at three (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:38-81`), so the surprising improvement is to deepen a few relevant loops invisibly rather than show more loops. It is **likely (55-80%)** that dependency-frontier preparation will transfer better than next-task prediction, because common prerequisites retain value when the chosen branch changes; evidence is the explicit reuse criterion and ProAct-75’s task-graph/parallel-action benchmark, but local effect size is not yet measured.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add optional `depends_on`, `branches`, `reuse_count`, and `invalidates_on` fields to escrow records. A scheduled producer reads the existing open-loop/event-ledger projection, selects at most two frontier candidates, and writes only proposal records. The next ordinary agent session performs the actual bounded reads using native tools and attaches external receipts. No daemon and no seventh hook. Default limits: two candidates/project, one artifact/candidate, 15 minutes or 20k tokens total per idle window, TTL 72 hours unless the source is version-pinned.

**External signal that verifies it.** A separate ledger consumer joins each prepared artifact to the next accepted task: did the later task reference the artifact hash/path, did it reduce pre-first-edit setup turns, and was its source hash still valid? The experiment compares frontier packets against “predict one next task” packets on 30 chronological sessions. The different future session and its tool trace are the verifying context.

**SOTA.** ProAct-75 supplies explicit task graphs with dependencies and parallel possibilities and reports improved trigger detection/parallel action from structure-aware selection; those 2026 benchmark results are **UNVERIFIED** for this software harness, and the 30-session chronological replay above would settle transfer ([paper](https://arxiv.org/abs/2602.03430)). ProAgentBench separates **when** to assist from **what** assistance to generate and uses 500+ hours of real work events; its claim that real history and long-term context beat synthetic alternatives is **UNVERIFIED** locally, settled by the same chronological replay using this owner’s real ledger rather than generated sessions ([paper](https://arxiv.org/abs/2602.04482)).

**Value x effort:** high x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it, because only evidence packets enter escrow; any implementation branch remains confirm-first unless already authorized by the active task.

### 3. Reliability-weighted readiness: preflight the likely failure, not just the likely task

**Improvement — Corpus-conditioned readiness packets.** When an open thread is likely to require a risky tool class, prepare the safer invocation and an independent known-positive control in advance. This is not a new liveness hook or edit guard; it is task-specific setup attached to an escrow item.

**What it is.** A readiness packet contains the selected tool route, exact argv/JSON schema, a fallback route, a known-positive detector control, and the last external receipt. Concrete initial policies from measured local data:

* prefer the plugin Exa route (562 calls, zero errors) over the disconnected `claude_ai_Tavily` routes when both satisfy the request; evidence at `/local_disk0/codexwork/bundle/inputs/corpus.json:165-180` versus Tavily search’s 139/194 errors at `:319-324` and “not connected” fingerprint at `:9130-9149`;
* prepare argv arrays or script files instead of nested shell strings for quote-heavy work, because Bash has 1,631 unmatched-single-quote failures (`/local_disk0/codexwork/bundle/inputs/corpus.json:8840-8855`);
* pre-read and hash edit targets immediately before the authorized edit, because 568 Edit failures were “file has not been read” and 125 were “modified since read” (`/local_disk0/codexwork/bundle/inputs/corpus.json:8933-8948`);
* use minimal/flexible fan-out contracts rather than speculative maximal schemas, because StructuredOutput fails 22.9% and 294 errors require missing `kg_triples` plus `confidence` (`/local_disk0/codexwork/bundle/inputs/corpus.json:8964-8987`);
* use scoped `rg --files`/explicit roots rather than Glob in inflated plugin trees, because Glob records 592 `ENAMETOOLONG` and 175 timeouts (`/local_disk0/codexwork/bundle/inputs/corpus.json:8995-9006`).

**Why inferred.** The obvious notion of anticipation is “guess content.” The corpus says a large share of preventable friction happens earlier: connection, quoting, read state, schema, and path expansion. It is **almost certain (90-99%)** that preparing syntactically validated argv/schema and known-positive controls can detect those exact setup defects before expensive work, because each check is executed by a parser/tool that directly exercises the failure boundary; evidence is the corresponding high-count fingerprints and confirmed detector-control defect at `/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`.

**How to build.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Add `readiness_templates` to the existing capability catalog/semantic router data: tool family, preferred live route, fallback, preflight command, positive control, TTL, and corpus error fingerprint. The skill-router can attach the matching readiness-template ID to its existing route; the active agent executes the preflight when preparing the escrow artifact. No additional hook, guard, or self-heal service. Keep B1 mcp-liveness authoritative for fleet healing; this packet only records task-local readiness.

**External signal that verifies it.** Each readiness claim requires two mechanically independent receipts: the route’s own safe probe plus a known-positive control proving the detector/probe can see a known-live item. For edits, target hash/read receipt plus the later Edit result; for schemas, local JSON Schema validation plus StructuredOutput acceptance; for commands, shell parser/dry-run plus actual exit status. The packet fails open: missing/errored preflight means “unready,” not a block, and normal reactive work remains available.

**SOTA.** The CHI 2019 guidelines explicitly recommend making capability/error boundaries clear and scoping service under uncertainty ([paper](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). Horvitz’s mixed-initiative work treats uncertainty and expected costs as inputs to whether/when automation acts ([Mixed-Initiative Interaction](https://www.microsoft.com/en-us/research/publication/mixed-initiative-interaction/)).

**Value x effort:** transformative x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for safe probes and local validation; confirm-first if a preflight would incur material cost, authenticate a new service, mutate remote state, or expose secrets.

### 4. Freshness contracts: a prepared artifact must prove it is still about the same world

**Improvement — Invalidation manifests and activation-time receipts.** Every prepared artifact declares which observations make it stale: file hashes, branch/HEAD, lockfile hash, API/version, MCP route identity, date horizon, goal/thread status, and owner choice. Activation rechecks them with a different tool/process. A stale artifact is retained as evidence but never silently reused.

**What it is.** This converts prefetching from “cached answer” into “cached answer plus validity envelope.” The envelope can be tiny: `{inputs:[{path,sha256}], repo_head, external_as_of, tool_route, goal_id, ttl, invalidators}`. The user sees only “ready / stale / expired” and one reason, not the manifest.

**Why inferred.** Preparation increases the time between evidence collection and use. This workspace already records a fabricated constraint propagated to about 15 prompts and a 13.6%-failure workaround (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:151-160`), showing the cost of letting unverified premises travel. Edit failures also include 125 files modified since read (`/local_disk0/codexwork/bundle/inputs/corpus.json:8941-8944`). It is **very likely (80-90%)** that explicit invalidation prevents a meaningful class of stale-preparation errors, because the activating process compares the actual load-bearing inputs rather than trusting the preparing context; evidence is those observed stale/propagated-premise failures.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Put a `manifest.json` beside each escrow artifact. Implement `escrow validate <id>` using native `git rev-parse`, file hashing/stat, version probes, and ledger goal status. The validator runs in a fresh process and emits machine-readable receipts. Fold stale/expired garbage collection into the existing scheduled background producer or open-loop GC; do not add a hook. Archive metadata, delete only disposable cache payloads, and never delete user work.

**External signal that verifies it.** Validation is solely external observation. A later activation succeeds only when the fresh-process receipt matches the manifest. Test the detector with a known-present invalidator: create a temporary fixture, validate it, modify it using a second process, and require `stale`; also validate an unchanged control. This supplies the mandatory known-positive control and an independent negative.

**SOTA.** Amershi et al. recommend remembering recent interactions, updating cautiously, conveying consequences, and notifying about changes ([guidelines and validation](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). The 2026 PersonalAgent paper reports cross-session preference consistency under noisy dialogues, but that result and its lifelong profile mechanism are **UNVERIFIED** for this owner; a chronological preference replay with superseded constraints would settle whether any of its inference machinery adds value beyond explicit manifests ([paper](https://aclanthology.org/2026.findings-acl.159/)). No PersonalAgent runtime is recommended.

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for validation and cache expiry; confirm-first before deleting any artifact outside the dedicated disposable cache.

### 5. A portfolio budget with a “wrong-work tax” and reserved continuity lane

**Improvement — Bounded speculative portfolio.** Allocate idle preparation by cost and reversibility, not by enthusiasm. Reserve one slot for continuity/open-thread protection, one for high-reuse readiness, and at most one for a surprising exploratory option. Charge expired or unused artifacts a wrong-work tax that raises their future threshold.

**What it is.** Default portfolio per project: maximum three live candidates, 20k model tokens, 15 wall-clock minutes, zero paid external jobs, 50 MB disposable storage, and no more than one owner-facing digest line. A candidate’s priority is `expected reuse value - compute - invalidation - attention - wrong_work_tax`. Safety/continuity items bypass the learned interjection hit rate but not the artifact/receipt rules; this prevents a bad calibration episode from suppressing “do not drop this thread.”

**Why inferred.** The harness has hundreds of installed capabilities but the corpus records only 78 skill names used, with a long tail of one- and two-use skills (`/local_disk0/codexwork/bundle/inputs/corpus.json:13265-13320`). This does not prove unused skills lack value, but it does show a broad anticipator could cheaply over-prepare across a huge surface. The corpus also records 53-run Read and 14-run Bash retry loops (`/local_disk0/codexwork/bundle/inputs/corpus.json:10297-10324`), demonstrating that unbounded persistence can consume slack without progress. It is **likely (55-80%)** that a hard portfolio cap prevents preparation sprawl while preserving the highest-option-value items; evidence is the existing long-tail capability surface, observed retry runs, and bounded-three precedent in open-loop resurfacing. Exact thresholds are **UNVERIFIED**; a four-week shadow budget sweep (1/3/5 candidates and 5k/20k/50k tokens) would settle them.

**How to build.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Put limits and type weights in the escrow config. Use the existing scheduled producer and ledger to account actual elapsed/tokens/bytes. Do not use a learned router or trained critic. Update candidate-type weights only from external consumption/expiry outcomes, require 20 samples before a threshold change, cap changes at 10% per review period, and retain a global off switch. This specifically goes beyond calibrated-silence: it budgets invisible preparation, while calibrated-silence budgets interjections.

**External signal that verifies it.** The next-session/event-ledger join records `consumed`, `expired_unused`, `invalidated`, setup-turns saved, and owner dismissal. Weekly deterministic aggregation—not an LLM self-rating—computes yield per cost. Promotion requires the capped policy to beat reactive-only on accepted-task latency without increasing owner-facing interjections. The owner is the signal for explicit dismissal; tool traces are the signal for time and reuse.

**SOTA.** BusyBody learned personalized interruption cost from users’ assessments plus activity/context and used expected cost to mediate notifications ([Microsoft Research publication](https://www.microsoft.com/en-us/research/?p=316172)). LlamaPIE’s two-stage small-model “when” / larger-model “what” design supports separating cheap gating from expensive generation, although its user study concerns in-ear conversations rather than software work ([ACL 2025 paper](https://aclanthology.org/2025.findings-acl.710/)).

**Value x effort:** high x low. **Novelty:** inferred-surprise. **Autonomy:** just-do-it within the hard free/read-only budget; confirm-first to exceed any wall-clock, token, storage, paid-service, or external-action cap.

### 6. Shadow evaluation must score anticipation against “wait and react,” including wrong preparations

**Improvement — Chronological prefetch evaluation.** Before enabling automatic preparation, replay historical goal/open-thread states in chronological order. At each cutoff, generate up to three candidate packets without seeing the future; reveal the next task/session; score usefulness, invalidation, setup turns, cost, and interruption. Then run a live alternating-week or randomized candidate-level shadow trial.

**What it is.** Required metrics: precision@prepared (consumed before expiry), coverage of next-task prerequisites, median setup turns saved, time-to-first-verified-action, wrong-work token/minute cost, stale activation rate, owner-facing prompts, and thread-drop rate. The reactive baseline gets the same model/tools after the future task arrives. A candidate that was plausible but unused counts as cost, not success.

**Why inferred.** Proactive systems can look impressive by grading only their hits. The local owner-correction detector demonstrates the danger: 2,268 candidates collapsed to 41/41 false positives in one smoke sample (`/local_disk0/codexwork/bundle/inputs/corpus.json:10371-10375`). The installed weekly semantic-router bench has also been claimed in the audit to treat an interface parse failure as success; that audit claim is not promoted to fact here, but its exact settling experiment is to run the real evaluator and assert nonzero parsed cases (`/local_disk0/codexwork/bundle/inputs/audit-findings/E01.md:48-49`). It is **almost certain (90-99%)** that a chronological reactive control is necessary to tell useful anticipation from cheap hindsight, because it mechanically withholds future state and prices unused outputs; evidence is the correction-detector control failure and standard randomized evaluation in the CHI 2025 programming-assistant study.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing harness-bench scheduled path, not its live hooks. Write JSONL cases from sanitized event-ledger/open-loop snapshots; call the same candidate generator with a cutoff timestamp; join later sessions by project/goal/thread; emit one aggregate JSON and one digest line only on regression/promotion. Use the corpus only for aggregate priors because raw future session content is not present on this job node. Promotion gate: zero subject mutations, stale activation rate 0, owner-interjection count no higher than baseline, and positive setup-turn savings with bootstrap intervals. The exact sample/power threshold is **UNVERIFIED**; a pilot variance estimate over the first 30 eligible chronological cases would settle it.

**External signal that verifies it.** Future transcript/tool events are the independent ground truth. Live evaluation uses actual later owner tasks and execution receipts. A held-out evaluator process computes metrics from immutable JSONL; no candidate-generating context sees or grades its own future match.

**SOTA.** Chen et al. evaluate proactive programming assistance with a randomized experiment and shared programming context rather than relying only on model judgment ([CHI 2025 publication](https://www.microsoft.com/en-us/research/publication/need-help-designing-proactive-ai-assistants-for-programming/)). ProAgentBench’s timing/content split and real-session emphasis further motivate chronological evaluation, but its numeric transfer is **UNVERIFIED** here; the proposed replay is the settling experiment ([paper](https://arxiv.org/abs/2602.04482)).

**Value x effort:** transformative x medium. **Novelty:** inferred-surprise. **Autonomy:** just-do-it for redacted read-only shadow evaluation; confirm-first before enabling automatic producers based on the result.

### 7. Ask now, use later—but only at a natural decision boundary and only once

**Improvement — Deferred preference acquisition queue.** When preparation is blocked by a reusable preference (e.g. preferred test depth, whether read-only web prefetch is welcome, cost ceiling, or which branch of an explicitly recurring workflow matters), store one typed question with expected reuse and expiry. Ask it only when the owner is already making a related choice, never as a standalone proactive interruption.

**What it is.** A queued question requires: `preference_key`, `future_tasks_supported >= 2`, `why_current_task_does_not_need_it`, `ask_at` predicate, `default_if_unasked`, `expiry`, and `sensitivity`. The default must keep work moving. Answers go through the existing basic-memory/ledger path with provenance and supersession; inferred answers are not silently promoted to durable preferences.

**Why inferred.** The natural response to uncertainty is more questions, but prompt fatigue is a first-class constraint. Existing `AskUserQuestion` is already heavily used—1,329 calls, 39 errors (`/local_disk0/codexwork/bundle/inputs/corpus.json:135-139`)—so a new question surface would be duplication and likely fatigue. The better surprise is to prepare the question and piggyback it on a future decision point. It is **likely (55-80%)** that boundary-timed acquisition improves future preparation without raising prompt count, because questions replace or enrich an already-required choice rather than create a new interruption; evidence is the no-new-prompt construction and ATRBench’s measured acquisition gap. Local benefit remains unmeasured.

**How to build.** **NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).** Use existing AskUserQuestion only when the active task already requires confirmation. Store deferred questions as a new open-loop predicate (`decision_key`) and surface at most one in the existing choice. Configure “never ask proactively just to improve a profile,” “never infer sensitive preferences,” and “expire after 30 days or goal closure.” No new hook or UI.

**External signal that verifies it.** The owner’s explicit selection is the only preference truth. Later tasks verify reuse by referencing the preference record and observing whether the owner keeps or overrides it. Silence, terse replies, or lack of correction are not consent. A 20-question cohort compares later reuse and override rate against questions asked only when immediately necessary.

**SOTA.** ATRBench reports that eight frontier long-lived agents remain at least 62 points below an oracle given the relevant preference and identifies acquisition as the bottleneck; this May 2026 preprint result is **UNVERIFIED** for this owner, and the 20-question reuse/override cohort would settle transfer ([paper](https://arxiv.org/abs/2605.28108)). The CHI 2019 guidelines support granular feedback during regular interaction and cautious adaptation ([paper](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)).

**Value x effort:** medium x low. **Novelty:** inferred-surprise. **Autonomy:** confirm-first—the preference itself always comes from the owner; queuing the question is just-do-it.

### 8. Progressive autonomy by reversibility, with one calm readiness surface

**Improvement — Four preparation classes and a single digest line.** Class 0 may be prepared automatically: hashes, repo maps, authoritative docs, test discovery, liveness receipts. Class 1 may create disposable artifacts: summaries, patch files, command plans, schemas. Class 2 needs confirmation before spending material compute or touching authenticated/paid services. Class 3 needs confirmation before any persistent/external mutation. Surface only validated Class 0/1 items, grouped into one “Prepared for likely next steps” digest line with `use`, `inspect`, and `dismiss/expire` semantics expressed as ordinary commands/paths—not new buttons.

**What it is.** This calibrates trust through observable consequences rather than claims of confidence. Every item shows why it exists, what it cost, as-of time, and what activation would do. Dismissal raises only that candidate type’s threshold; it never suppresses safety or continuity records. No dead UI is introduced.

**Why inferred.** The existing digest already emits up to 12 lines and then archives/truncates (`/local_disk0/codexwork/bundle/claude/hooks/background-digest/reader.py:67-68,138-180`), while open-loop resurfacing caps items at three (`/local_disk0/codexwork/bundle/claude/hooks/open-loops/resurface.py:38-40`). A separate proactive panel would violate dedup and quality constraints. It is **very likely (80-90%)** that one existing surface with explicit reversibility costs less attention than another notification channel, because it adds zero new interjection events and reuses bounded, surface-once behavior; evidence is the exact existing wiring at `/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:53-69`.
