# X142 — Cross-domain borrow: cartography → use-versus-mention guards

## Scope and evidence discipline

This is an ideation unit, not a local harness audit. Per the unit instruction, I did not inspect the subject repository, corpus, defects file, prior audit, or Windows-only paths. The target premise—five detectors and at least twelve false fires caused by matching payload text that merely describes a guarded thing—is supplied by the unit brief and is not independently re-measured here. Conclusions below therefore concern whether a cartographic mechanism transfers and what an implementation experiment should test; they do not claim that any named local detector has a particular implementation.

External research was limited to cartography/generalisation sources and standards. No local harness change was made. The only file written is this artifact.

## Verdict

The analogy transfers, but only partially and with a sharp boundary.

The useful cartographic mechanism is **semantic-feature/portrayal separation plus scale- and purpose-conditioned selection, followed by constraint checks**. A map renderer does not infer that a road-name label *is* a road merely because the label contains the road's name. It maintains a geographic feature model, applies rules to feature types/properties at an appropriate map scale, and separately renders symbols or labels. Generalisation may deliberately eliminate, reclassify, aggregate, or alter attributes, but checks the result against thematic, topological, and legibility constraints. In harness terms: classify the semantic role of each input region before applying a guard, evaluate the guard against action-bearing roles at the narrowest adequate “scale,” and retain omitted mention-only material for audit rather than treating every matching token as an action.

This is a **very likely (80-90%)** structurally valid transfer because two independent cartographic sources explicitly separate (1) geographic layers/features from styles/rendering rules and (2) semantic generalisation from cartographic portrayal, while the target failure is exactly a collapse of represented object and surface representation: the OGC SymCore standard defines a layer as an abstraction of reality and a style as instructions applied to that layer, while its rules may be conditioned on feature properties or map scale ([OGC SymCore §§4.2–4.5, 6.2–6.3](https://docs.ogc.org/is/18-067r3/18-067r3.html)); Blana, Kavadas, and Tsoulos separately model semantic generalisation and cartographic generalisation, including feature reclassification/elimination before portrayal and post-transformation quality checks ([Geographies 2023, §§2.2–2.3](https://www.mdpi.com/2673-7086/3/2/17)). The confidence is below “almost certain” because natural-language/code role recovery is less explicit and less stable than a GIS feature schema.

It is **almost certainly not (1-5%)** valid to borrow “deliberate omission” as “strip quoted text/comments, then run the old regex,” because executable languages can embed effects in quoted strings, heredocs, templates, generated code, and data consumed by an interpreter. That disanalogy follows from the target domain’s executable representations, not from a cartographic source; the settling experiment is the adversarial executable-carrier suite specified below.

## What cartography solved in its own field

### 1. Keep the phenomenon, the model, and the portrayal distinct

The OGC Symbology Conceptual Core Model gives the cleanest formal mechanism. It defines:

- a **layer** as an abstraction of reality specified by a geographic data model;
- a **style** as rules of symbolising instructions applied to a layer of geographic features;
- a **rendering engine** as a process taking layers and styles as inputs;
- a **rule** as an organiser of symbolising instructions whose application may depend on feature properties or map scale.

These are not informal analogies: they are distinct concepts/classes in the standard ([OGC SymCore §§4.2–4.5 and 6.2–6.3](https://docs.ogc.org/is/18-067r3/18-067r3.html)). The standard further describes a concrete feature-type style as applying to one feature type, and separately identifies the geometry property to style ([OGC SymCore Annex B](https://docs.ogc.org/is/18-067r3/18-067r3.html)). OGC’s Testbed-13 portrayal model states the design principle even more directly: portrayal ontologies relate feature types, portrayal rules, symbols, and symbolizers while separating data content from its portrayal ([OGC Testbed-13 Portrayal Engineering Report, Appendix A](https://docs.ogc.org/per/17-045.html)).

How it works in cartography: the database object “road segment” has identity, geometry, class, and properties. A portrayal rule can select that feature based on properties and scale, then render it as a line and perhaps derive a text label. The painted line and label are presentations of the feature; neither is used as the sole evidence that the feature exists or has a particular semantic class. This is what prevents an annotation saying “hospital” from automatically becoming a hospital feature.

### 2. Generalise semantics before graphics

Blana et al. model a transition from a geographic/spatial database to a cartographic database in separate semantic and cartographic phases. Their semantic operators include class abstraction, elimination and composition; attribute elimination and aggregation; and instance-level feature elimination, reclassification, aggregation, merging, and attribute modification ([Geographies 2023, §2.2](https://www.mdpi.com/2673-7086/3/2/17)). Relations between source and target feature classes are made explicit rather than guessed from how something looks. Only after that semantic transformation does graphic simplification select a portrayal, and the result is checked for topology, conceptual consistency, relative position, and legibility ([Geographies 2023, §§2.2–2.3](https://www.mdpi.com/2673-7086/3/2/17)).

This matters because omission is not arbitrary deletion. It is a declared source-to-target relation—one-to-one, many-to-one, or one-to-none—under constraints and conformance checks. A small-scale map can omit individual buildings while preserving the settlement pattern or aggregate them into a built-up area. The cartographic database is a purpose-specific abstraction, not a claim that omitted phenomena do not exist.

### 3. Change detail with scale and purpose, but preserve context

Map generalisation is not one universal simplifier. ICA work identifies map usage, scale, and feature distribution as determinants and lists selection, simplification, combination, smoothing, enhancement, displacement, exaggeration, and aggregation as distinct operators ([Luo et al., ICA Proceedings 2019](https://ica-proc.copernicus.org/articles/2/80/2019/)). OGC SymCore likewise permits rule conditions based on feature properties or map scales ([OGC SymCore §6.3](https://docs.ogc.org/is/18-067r3/18-067r3.html)).

Context is not optional. Experiments on distributed generalisation found that regular partitioning was fastest but least effective at incorporating geographic context; geographic partitioning better preserved that context ([Berli et al., ICA Proceedings 2018](https://ica-proc.copernicus.org/articles/1/8/2018/)). Thus the borrow is not “inspect less text.” It is “inspect the representation appropriate to the decision while retaining enough neighbourhood context to preserve relationships.”

### 4. Quality constraints accompany omission

Constraint-based cartographic generalisation measures candidate results before, during, and after transformation. The cited model ties constraints to measures, changes calibration or algorithm on non-compliance, and performs final quality checks; its requirements span thematic classification, completeness, conceptual consistency, topology, relative position, and legibility ([Blana et al., §§1.1 and 2](https://www.mdpi.com/2673-7086/3/2/17)). This is essential to the transfer: role-aware omission needs invariants, not trust in a new classifier.

## Concrete translation to an agent harness

### Proposal — UNVERIFIED: semantic portrayal boundary for guards

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Build one shared, deterministic adapter on the existing guard-hook path. It converts each hook event into a tiny **semantic event map** before any detector runs. It does not add an orchestrator, daemon, database, model call, or second policy engine.

The event map should expose spans/fields with these roles:

```text
ACT          the requested operation (tool identity + operation kind)
EFFECTOR     syntax/field that can cause an effect (command, URL fetch, write mode)
TARGET       resource the effect reaches (path, host, ref, recipient)
DATA         inert payload for that operation
MENTION      quoted/example/documentary description with no effect in this event
META         provenance, labels, logs, diagnostics
UNKNOWN      role could not be established
```

These are deliberately operational roles, not open-ended natural-language “understanding.” The map is constructed first from the trusted event envelope—hook event type, tool name, named JSON field, content type, and producer—and only then, where necessary, from a language-aware parser for an executable field. Raw substring matching becomes a fallback signal, never the primary classification.

The adapter should emit both the full input and a role-indexed view. Each existing guard declares the roles and scale it is allowed to inspect, for example:

```text
destructive-shell guard: ACT + EFFECTOR + TARGET; parse command AST
protected-path guard:    TARGET; canonical path tokens
secret-egress guard:     EFFECTOR + TARGET + DATA-flow flag; never arbitrary prose alone
policy-doc guard:        MENTION + META; observe/report, never action-block merely for terms
prompt-injection guard:  DATA from untrusted producer + consumer boundary; not all DATA globally
```

The predicted reduction of mention-triggered false fires is **very likely (80-90%)**, because the adapter directly removes the causal equivalence “token appears anywhere ⇒ prohibited act” and the unit brief says that equivalence caused the observed class; the magnitude is **UNVERIFIED—settling experiment: replay the twelve-plus known false-fire events and a matched set of true-positive events through old and new paths, with event IDs blinded during rule tuning**.

The implementation remaining under roughly 200 lines is **likely (55-80%)**, based on the small role vocabulary, use of existing structured envelopes, and absence of a new runtime; it is **UNVERIFIED—settling experiment: implement one vertical slice for one structured tool event and one shell event, count non-generated source lines including tests separately, and reject BUILD-SMALL if production code exceeds 200 lines**. Parser libraries already available on the hook bus may keep the adapter small, but their availability is **UNVERIFIED—settling experiment: inventory the runtime and dependency lockfiles on the actual Windows host**.

### Scale ladder — UNVERIFIED: inspect at the narrowest adequate semantic resolution

Borrow cartographic scale as a decision ladder, not as a metaphorical “zoom” control:

1. **Event scale:** determine whether this is a request to act, an observation result, a document read, or a diagnostic. A PostToolUse result mentioning `rm -rf` is not the same feature class as a PreToolUse shell request containing it.
2. **Operation scale:** use the tool name and typed argument schema. A path in a read call and the same path in a delete call have different ACT/EFFECTOR roles.
3. **Syntax scale:** only for executable fields, parse shell/PowerShell/SQL/templating syntax and identify command, redirection, expansion, and target nodes.
4. **Lexeme scale:** use regex/substring signals inside the eligible nodes. Lexemes contribute evidence; they do not assign role.
5. **Fallback scale:** if parsing or schema recognition fails, mark UNKNOWN and apply a detector-specific conservative policy.

This ladder will **very likely (80-90%)** distinguish documentary mentions from structured actions when the hook supplies a typed tool envelope, because tool identity and field role are mechanically available before text inspection; evidence is the direct correspondence to OGC rules conditioned on feature properties rather than rendered labels ([OGC SymCore §6.3](https://docs.ogc.org/is/18-067r3/18-067r3.html)). Its performance on free-form natural-language instructions is **roughly even (45-55%)**, because role boundaries may not be explicit; this is **UNVERIFIED—settling experiment: annotate and evaluate a held-out free-form set containing quotation, negation, examples, reported speech, and indirect requests**.

### Deliberate omission — UNVERIFIED: omit only from the decision view

For a decision at event/operation scale, MENTION and META are omitted from the *blocking predicate* but retained unchanged in the audit record. This is the cartographic one-to-none relation applied to a purpose-specific derived view, not deletion of source material. Every omission record should include `(guard_id, source_span_or_field, assigned_role, reason, classifier_version)` so a false negative can be reconstructed.

Omission must be asymmetric:

- In a non-executable documentation field, fenced examples, quotations, and prose can be MENTION.
- In a shell `command` field, quotes, heredocs, substitutions, and comments remain inside an executable-language parse; quotation alone never grants MENTION.
- In data handed to an interpreter/compiler/template engine in the same event chain, DATA may become EFFECTOR at the consumer boundary. Role is attached to an event edge, not permanently to bytes.
- UNKNOWN is never silently omitted. High-impact guards retain the current conservative behavior or request review; lower-impact guards may log only, according to existing policy.

This asymmetric omission is **very likely (80-90%)** to preserve obvious executable carriers while suppressing pure-document false fires, because it keys omission to the consumer boundary rather than punctuation; the residual safety claim is **UNVERIFIED—settling experiment: run the executable-carrier suite below and require zero regressions against the current true-positive baseline before enabling blocking decisions**.

### Constraint checks — UNVERIFIED: cartographic quality control translated

Add four invariants to the adapter’s test contract:

1. **Thematic/classification consistency:** the same field path under the same event/tool schema receives the same base role; changes require a versioned rule change.
2. **Topology/data-flow preservation:** if DATA is passed to a known executable consumer, the consumer edge reclassifies it to EFFECTOR before the relevant guard.
3. **Completeness:** every payload field is assigned exactly one base role, including UNKNOWN; no field disappears from both decision and audit views.
4. **Relative-context preservation:** a span classifier receives its containing field, event type, tool name, provenance, and immediate consumer; it is not run on isolated regex captures.

The invariants are **likely (55-80%)** to catch classifier regressions that a false-positive-only test set would miss, because they cover classification, consumer relationships, coverage, and neighbourhood context—the same distinct dimensions used in cartographic quality control ([Blana et al., §§2.2–2.3](https://www.mdpi.com/2673-7086/3/2/17)) and the context failure demonstrated by Berli et al. ([ICA Proceedings 2018](https://ica-proc.copernicus.org/articles/1/8/2018/)); harness effectiveness is **UNVERIFIED—settling experiment: mutation-test role rules by deleting field mappings, breaking a consumer edge, and stripping event context, and confirm that separate invariants fail**.

## What this catches that payload-text matching misses

The translated design is not merely a false-positive filter. It adds detections unavailable to a flat lexical scan:

1. **Semantically dangerous actions without the detector’s keyword.** A structured delete operation can be detected from ACT plus TARGET even if its payload never contains `delete`, `remove`, or `rm`. This is **very likely (80-90%)** for typed tool calls because operation identity is explicit in the envelope; breadth across actual tools is **UNVERIFIED—settling experiment: enumerate supported tool schemas and replay synonym-free destructive calls**.
2. **Dangerous targets split across syntax nodes.** A shell parser can join redirection/operator/expansion structure that flat matching treats as unrelated text. Detection improvement is **likely (55-80%)** because syntax supplies relations absent from substrings; it is **UNVERIFIED—settling experiment: compare against generated shell and PowerShell cases with concatenation, variables, pipelines, and redirections on both Windows shells**.
3. **Role changes across consumer boundaries.** Text read from a document is DATA at the read event but becomes EFFECTOR if later executed. A static “document = safe mention” mask misses this transition. Capturing it is **likely (55-80%)** if the existing hook events expose producer/consumer correlation; that premise is **UNVERIFIED—settling experiment: trace a read→transform→execute replay and test whether a stable correlation key exists**.
4. **Uncertainty itself.** UNKNOWN becomes an explicit, measurable state instead of accidental non-match. It is **almost certain (90-99%)** that this will expose unsupported schemas in adapter telemetry because total role coverage is an invariant; evidence is mechanical exhaustiveness of the role assignment, and the settling experiment is a property test asserting that each input field maps to one role.
5. **True mention/action contrasts with identical surface text.** The same dangerous string in a documentation result and an executable argument produces different decisions for a stated reason. It is **almost certain (90-99%)** that this will catch the supplied use-versus-mention defect class in typed events because the pair differs in event/tool/field roles even when bytes are identical; the settling experiment is a metamorphic test that moves identical text between MENTION and EFFECTOR fixtures and requires opposite decisions.

## Evaluation design and enablement gate

### Gold set

Build paired, provenance-preserving fixtures rather than a random corpus sample:

- all twelve-plus supplied false fires;
- an equal or larger set of known true fires for the same five detectors;
- minimal pairs with identical dangerous substrings in documentation, quoted report, log output, inert data, command argument, path target, and interpreter input;
- keyword-free typed dangerous operations;
- UNKNOWN schemas and malformed payloads.

Do not tune on all known incidents. Blind at least one third of each detector’s positive and negative cases until the role rules freeze. A held-out split reducing overfit is **very likely (80-90%)** relative to tuning on every incident because it prevents direct fixture memorisation; generalisation to future traffic remains **UNVERIFIED—settling experiment: shadow the frozen adapter on subsequent live events and adjudicate disagreements**.

### Adversarial executable-carrier suite

Include, at minimum:

- Bash and PowerShell quoting, escaped quotes, variables, aliases, command substitution, pipelines, redirection, heredocs/here-strings, and `eval`/`Invoke-Expression`-like consumers;
- JSON fields that are inert for one tool but executable for another;
- Markdown fences nested in an executable field;
- a document that describes a command, a request to write that document, and a request to execute its fenced block;
- generated scripts and template expansion;
- encoded/obfuscated targets sufficient to test UNKNOWN/fallback behavior, without pretending the adapter solves general deobfuscation.

### Acceptance criteria

Enable the adapter first in shadow mode. For each old/new disagreement, record old decision, new decision, semantic map, and adjudication. Promotion to blocking should require:

- all known false-fire fixtures corrected;
- zero loss on the known true-positive fixtures;
- zero loss on the adversarial executable-carrier suite;
- 100% field coverage by a role or UNKNOWN;
- explicit fallback behavior tested for every detector;
- no material latency regression at the selected hook.

Meeting these criteria would make successful deployment **likely (55-80%)**, not certain, because a finite suite cannot cover all composed interpreters and provenance chains; evidence would be the paired replay, adversarial suite, coverage invariant, and shadow adjudication. The deployment claim remains **UNVERIFIED—settling experiment: run the complete staged evaluation above and publish the confusion matrix per detector, including UNKNOWN and latency percentiles**.

## Adversarial analysis: where the analogy fails

### Disanalogy 1: maps start from typed features; harnesses often receive ambiguous text

A geographic database commonly supplies explicit feature types, attributes, and geometry. A harness may see prose that simultaneously quotes, requests, negates, and embeds code. Cartography’s portrayal boundary does not supply the missing parser. Therefore this borrow justifies using trusted structural metadata first; it does not justify claiming reliable semantic-role labelling from arbitrary prose.

Result: use deterministic envelope/schema roles where present. Leave free-form ambiguity as UNKNOWN or pass it to an already-authorised existing mechanism. Adding an LLM role classifier solely for this adapter is **unlikely (20-45%)** to satisfy the reliability and minimality requirements, because it would add nondeterminism, latency, and a new prompt-injection surface without a typed ground truth; this is **UNVERIFIED—settling experiment: benchmark a frozen classifier against the blinded contrast set and compare calibration, latency, and adversarial stability to deterministic rules**.

### Disanalogy 2: omission from a map is representational; omission from a guard changes safety

A small-scale map can omit a shed while the shed still exists in the source database. A guard that omits a dangerous executable span can permit an irreversible effect. The costs are asymmetric. Hence omission applies only to the decision view when a non-effect role is established; source bytes remain available, UNKNOWN is explicit, and high-impact fallback stays conservative.

### Disanalogy 3: “scale” does not monotonically map to safety

More textual detail is not always safer. Event-level structure can reveal an operation that token-level inspection misses, while syntax-level structure can reveal an injection hidden by the event schema. The appropriate resolution depends on the guard. There is no universal zoom threshold.

### Disanalogy 4: portrayal can itself be executable

In cartography a painted label normally does not turn back into a road. In agent systems, a document, log, or model output can later be interpreted as commands. The representation can become an effector across an event boundary. This is the strongest limitation and the reason for edge-relative roles and data-flow preservation.

### Disanalogy 5: hostile inputs exploit the classifier

Cartographic generalisation usually optimises legibility and fidelity over non-adversarial data. Guard inputs may be crafted specifically to obtain MENTION status. Surface devices—quotation marks, “example,” Markdown fences, comments—must never be trusted as sufficient proof of non-execution.

## Alternatives considered and rejected

### “Just improve the five regexes”

Rejected as the primary design. Negative lookarounds for quotes, fences, or words such as “example” encode portrayal conventions into every detector and cannot represent consumer-boundary role changes. Local regex tightening may still be useful after role selection, but it does not establish use versus mention.

### Strip comments/quotes/document blocks globally

Rejected. It confuses typography with semantics and is unsafe in executable fields. It would also erase evidence needed for audit and debugging.

### LLM classifier on every payload

Rejected for the initial design. It violates the small deterministic adapter goal and makes the guard depend on another model judgment. A later experiment may compare it only on UNKNOWN cases; it must not become a prerequisite for the core mechanism without evidence.

### New policy daemon, provenance database, or orchestration runtime

Rejected by the anti-overfit gate. The useful mechanism fits the existing hook/skill/MCP bus as a small adapter plus declarative detector role lists. A second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is neither required nor proposed.

## Anti-overfit gate result

The proposal **passes the architecture gate conditionally**:

- it rides the existing hook bus;
- it centralises only a small role vocabulary and event-map adapter;
- existing guards retain their policy logic;
- it adds no daemon, model, durable state, external observability, trained critic, or guardrail framework;
- it can be deleted or bypassed without replacing the harness runtime;
- it is promoted only after paired replay and shadow evidence.

The “under 200 production lines” condition is **likely (55-80%)**, not established, for the reasons and line-count experiment stated above. If typed-envelope handling plus one necessary parser cannot remain BUILD-SMALL, stop and reassess rather than silently growing a second policy runtime.

## Recommended decision — UNVERIFIED pending paired replay

Adopt the cartographic mechanism, not the cartographic vocabulary: **feature before portrayal; semantic selection before token matching; resolution chosen per decision; omission only in a derived decision view; constraint checks after transformation**.

Proceed with one BUILD-SMALL vertical slice for a single high-false-fire guard and two event classes: one typed non-executable/document event and one typed executable/action event. The slice is **very likely (80-90%)** to determine whether the supplied false-fire class is structurally removable without weakening known positives, because the minimal-pair replay directly tests the role boundary; this is **UNVERIFIED—settling experiment: implement the shadow adapter, run blinded paired fixtures, and publish per-detector confusion matrices and disagreement adjudications before any enforcement change**.

Do not generalise the result to arbitrary prose, do not use quotation as a trust signal, and do not build a new runtime. If the slice cannot distinguish the paired fixtures using trusted event/tool/field structure, the analogy has reached its limit and should be abandoned for that detector rather than forced.
