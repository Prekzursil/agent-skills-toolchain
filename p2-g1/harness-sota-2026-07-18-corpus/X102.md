# X102 — Cross-domain borrow: metrology → tool design

**Unit:** X102  
**Source field:** metrology (calibration, traceability, measurement uncertainty, reference standards)  
**Target:** agent tool interfaces and diagnostics that induce shell misuse  
**Scope boundary:** ideation and external research only. I did not inspect or characterize the local harness or repository. The sole harness datum used is the task's pinned measured ground truth: **1,631 Bash failures fingerprinted as unmatched-quote EOF**. The prompt states that this datum comes from the distilled 10.62 GB session corpus; I treat it as an input measurement, not as a result independently reproduced by this unit.

## Executive judgment

The borrow is valid, but narrower than the slogan “apply metrology to tools.” The transferable mechanism is a **reference-backed calibration and measurement-assurance loop around every text-to-process-boundary transformation**:

1. define the property being checked (the exact argument vector or exact parse result intended by the caller);
2. realize stable reference cases (“check standards”) whose correct outputs are known;
3. compare each supported renderer/parser path against those references under a recorded shell, version, host, and mode;
4. keep an unbroken provenance record for the transformations; and
5. re-run a small check set when an influence condition changes.

This maps well because both physical measurement and command invocation have a chain of intermediate transformations, environment-dependent behavior, reference inputs, and downstream decisions that are unsafe when the intermediate indication is mistaken for the desired property. The mechanism is **very likely (80-90%)** to expose renderer/dialect regressions that ordinary happy-path tool tests miss, because Bash performs multiple ordered expansions and quote removal, while PowerShell has distinct expression and argument modes and version-dependent native argument passing; stable adversarial input/output comparisons exercise the entire transform rather than only the front-end schema ([GNU Bash, “Shell Expansions”](https://www.gnu.org/software/bash/manual/html_node/Shell-Expansions.html); [Microsoft, `about_Parsing`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.6)).

The borrow does **not** justify attaching a made-up numerical “uncertainty” to a command. Shell parsing is normally deterministic for a fixed byte/string input, dialect, version, mode, environment, and filesystem state. There is no SI-like universal reference for “what the agent meant.” The correct translation of an uncertainty budget is therefore a **coverage and residual-risk statement**, not a probability distribution pretending to measure intent. This limitation is decisive: adopt calibration, reference standards, traceability discipline, and check standards; reject pseudo-metrological scoring.

The most valuable concrete change is to make a structured, shell-free process invocation the default and retain raw shell text as an explicit language-mode escape hatch. A calibrated conformance probe then verifies that the structured call reaches the child process as the intended argument vector, while dialect-native parse-only validation gives raw scripts precise pre-execution diagnostics. This is **likely (55-80%)** to reduce the measured unmatched-quote class materially, based on the pinned count of 1,631 failures and the fact that a structured argument list removes the agent's need to synthesize shell quoting for the common “launch one program with arguments” case; the range is broad because this unit was intentionally prohibited from reclassifying those 1,631 instances by intent.

## 1. What metrology actually solved

### 1.1 Calibration is a relation under specified conditions, not a sticker

The International Vocabulary of Metrology (VIM), as reproduced by NIST, defines calibration as a two-step operation under specified conditions: first establish the relation between reference values (with uncertainties) and instrument indications (with uncertainties), then use that relation to obtain a measurement result from an indication ([NIST, “Metrological Traceability,” definition section](https://www.nist.gov/metrology/metrological-traceability), lines 311-312 in the web edition). Calibration is not merely “the instrument once passed a test.” It connects an indication to a reference under stated conditions.

That distinction matters here. A unit test that a command renderer once emitted a plausible string is analogous to looking at an instrument's display. A useful calibration exercises the transformation under a specified shell/version/mode and compares the **received child-process arguments** to a reference argument vector. The output string is only an intermediate indication.

### 1.2 Traceability belongs to the result and requires an unbroken chain

VIM 2.41 defines metrological traceability as a property of a measurement result by which it is related to a reference through a documented, unbroken chain of calibrations, each contributing to measurement uncertainty. It requires an established calibration hierarchy and the time and other relevant information for the reference ([BIPM/JCGM, VIM 2.41](https://jcgm.bipm.org/vim/en/2.41.html)). VIM explicitly warns that traceability does not guarantee fitness for purpose or the absence of mistakes.

NIST emphasizes two points that tool design routinely gets wrong:

- Traceability is a property of the **result**, not the instrument, report, or organization.
- Merely owning or using a calibrated artifact does not establish traceability; the process and chain must be documented and controlled.

NIST lists the practical elements: a clearly defined property, a complete measurement-system description, a result and associated uncertainty, a contemporaneous reference specification, and measurement-assurance programs for both system and reference ([NIST, “What do I need to do to support a claim of traceability?”](https://www.nist.gov/metrology/metrological-traceability), §5.1.7).

For tools, the faithful borrow is not to claim “this shell tool is traceable.” It is to make a narrower claim about an individual result: “for adapter version A, runtime B, shell mode C, and reference-suite version D, the observed child argument vector matched reference vector R.” I call this an **invocation provenance chain**, not metrological traceability, to avoid appropriating a term whose uncertainty and calibration requirements are not fully satisfied.

### 1.3 Check standards make calibration a continuing process

NIST's process-control handbook describes a check standard as a stable artifact treated as a test item in every calibration design. Repeated measurements of it control bias and long-term variability; there should be a check standard at each critical measurement level, and results should be recorded with the standard, design, instrument, operator, out-of-control flag, and relevant environmental readings ([NIST/SEMATECH e-Handbook, “Control of artifact calibration”](https://www.itl.nist.gov/div898/handbook/mpc/section3/mpc35.htm)). A check standard can even be a mathematical construction rather than a physical artifact.

NIST does not prescribe a universal recalibration interval. It recommends that intervals depend on required accuracy, stability, and environment, and that cross-comparisons and control-chart data inform the interval ([NIST, “Recommended Calibration Interval”](https://www.nist.gov/calibrations/recommended-calibration-interval)). This is a strong fit for software: checking on a shell/runtime/adapter/configuration transition is more meaningful than an arbitrary weekly timer.

### 1.4 Uncertainty makes residual doubt explicit—but must not be cargo-culted

The GUM states that a measurement result needs a quantitative indication of quality so users can assess reliability and compare it with other results or reference values. It also states that even after known or suspected error components are evaluated and corrections applied, doubt remains about how well the result represents the measurand ([JCGM 100:2008, GUM, Introduction §§0.1-0.2](https://www.bipm.org/documents/20126/2071204/JCGM_100_2008_E.pdf)). NIST requires uncertainty reports to identify components, distinguish statistically evaluated from otherwise evaluated components, explain their evaluation, and state the basis of a confidence interpretation ([NIST TN 1297, §7](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-7-reporting-uncertainty)).

The general lesson transfers: report what the check establishes, what contributes residual doubt, and what lies outside the validated domain. The numerical machinery generally does not. For a fixed parser, unmatched quotation is a discrete syntactic fact, not a noisy estimate of a continuous measurand. “97% calibrated” would obscure rather than clarify unless it names a population and sampling design.

## 2. Structural mapping—and where it breaks

| Metrology element | Tool-design translation | Validity of translation |
|---|---|---|
| Measurand | Exact `argv`, executable, environment/cwd contract, or raw-script parse outcome intended by a structured request | Valid only when intent is represented structurally; prose intent has no objective reference value. |
| Instrument indication | Rendered command string, parser token stream, or adapter success status | Strong mapping: these are intermediate outputs often mistaken for correct execution. |
| Reference standard | A versioned set of input requests with exact expected child-observed values | Strong mapping for argument transport and syntax; weak for business semantics or side effects. |
| Calibration | Run the real adapter/runtime/shell path with reference cases; compare child-observed output to expected output | Strong mapping because the transform is reproducible under recorded conditions. |
| Traceability chain | Request → schema validation → renderer/serializer → shell/runtime → OS process API → child-observed `argv`, with versions and modes | Useful provenance analogy, but not literal metrological traceability because there is no SI hierarchy and no defensible numeric uncertainty chain. |
| Check standard | A small permanent set of hostile argument and syntax cases run on change/startup | Strong mapping for drift/regression detection. |
| Influence quantity | OS, shell executable/version, PowerShell native-argument mode, locale/encoding, cwd, environment, filesystem/globbing state | Strong mapping: official shell documentation shows that modes and expansions alter interpretation. |
| Uncertainty budget | Supported-domain statement, reference-case coverage, untested strata, and observed failure rate with denominator | Partial mapping only. Do not combine unlike residual risks into a synthetic scalar. |
| Calibration interval | Event-based check on adapter, runtime, shell, policy, or host-image change | Strong mapping; deterministic software favors change-triggered checks over elapsed time. |

### Why the analogy transfers

1. **There is a chain, not one parser.** Bash tokenization is followed by ordered brace, variable, command, arithmetic, word-splitting, filename, and quote-removal stages ([GNU Bash manual](https://www.gnu.org/software/bash/manual/html_node/Shell-Expansions.html)). PowerShell separately parses commands, shifts between expression and argument modes, and has special metacharacters and native-command behavior ([Microsoft, `about_Parsing`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.6)). A reference checked only before those transformations cannot certify the result after them.

2. **Conditions matter.** Microsoft documents `Legacy`, `Standard`, and `Windows` native argument-passing modes and notes a behavior change beginning with PowerShell 7.3 ([Microsoft, “Passing arguments to native commands”](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5)). Recording “PowerShell” without version and mode is like recording a measurement without an influence condition.

3. **A known stimulus can produce an independently inspectable result.** A tiny probe child can encode the argument count and each received argument independently of the renderer being tested. This creates a practical reference comparison at the boundary that matters.

4. **Passing once is insufficient.** A runtime or shell update can change the transformation without a tool-schema change. Continuing check standards specifically address that drift class.

### Why the analogy does not fully transfer

1. **Intent is not an SI quantity.** There is no universal standard that maps an English request to one command. The reference can certify transport of a structured value, not that the value fulfills the owner's goal.

2. **Most parser behavior is deterministic, not stochastic.** Repeated trials under identical conditions do not estimate a useful standard deviation. Control charts are appropriate for field failure rates or changing environments, but are gratuitous for a pure parser conformance result.

3. **Shell scripts are programs, not argument vectors.** Pipes, redirections, conditionals, substitutions, loops, and shell built-ins cannot all be reduced to `program + argv`. Forcing them into a typed process tool would destroy legitimate expressiveness.

4. **The observer can perturb semantics.** Executing a command merely to discover how it parses can cause side effects. Calibration must use an inert probe executable or parse-only API, never substitute the real target command.

5. **Reference-suite coverage is not correctness.** A renderer can pass every check and fail on a novel string. VIM's own warning that traceability does not ensure adequate uncertainty or absence of mistakes is directly applicable ([BIPM/JCGM, VIM 2.41 note 5](https://jcgm.bipm.org/vim/en/2.41.html)).

The transfer therefore survives adversarial review only as a discipline for **boundary conformance, provenance, and drift detection**. It does not solve intent inference, command semantics, or arbitrary program correctness.

## 3. Concrete harness design

## Proposal A — Calibrated structured process tool [UNVERIFIED BUILD-SMALL sizing; settle with a two-platform executable-line-count spike]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a default tool mode whose request is data, not shell source:

```json
{
  "program": "git",
  "args": ["show", "origin/main:path with spaces/file.txt", "--"],
  "cwd": "C:\\work tree",
  "env_delta": {},
  "stdin": {"kind": "none"},
  "timeout_ms": 10000
}
```

Required contract:

- `program` and every `args[i]` are separate values. The agent never supplies quoting around an argument.
- `args` preserves empty arguments, embedded whitespace, quotes, and leading hyphens.
- no shell is created; redirection, expansion, pipes, `&&`, and substitutions are impossible in this mode;
- the implementation uses the platform's argument-list process API rather than concatenating the array back into a command string. On .NET, `ProcessStartInfo.ArgumentList` is explicitly documented to escape supplied arguments and is recommended over the string `Arguments` property when escaping is uncertain ([Microsoft .NET API, `ProcessStartInfo.ArgumentList`](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist));
- the result reports executable identity, argument count, process creation stage, exit status, and whether a shell was involved, while redacting values marked secret.

This is calibration-inspired design at the source: expose the desired property directly instead of asking the caller to manipulate the instrument's display until it happens to imply that property.

**Expected catch:** unmatched quotation cannot occur at a shell grammar layer because there is no shell grammar layer. Lost empty arguments, accidental word splitting, glob expansion, variable expansion, command substitution, and quote removal are also structurally excluded for calls expressible in this mode.

The statement that those latter categories are material in the current harness is **UNVERIFIED**; settle it by sampling the existing failure corpus for child-argument mismatches and shell-expansion fingerprints, then replay the sampled intended invocations through both interfaces. This uncertainty does not affect the recommendation's foundation: the 1,631 unmatched-quote failures are pinned ground truth, and the interface removes the relevant grammar for single-process launches.

It is **almost certain (90-99%)** that the structured mode will prevent syntactically unmatched shell quotations for invocations that stay within its `program + args` contract, because no command string is parsed by a shell; the residual 1-10% covers implementation violations such as an adapter secretly joining arguments or routing `.cmd`/batch targets through `cmd.exe`, a path Microsoft warns receives raw command-line strings ([Microsoft, `about_Quoting_Rules`, native-command warning](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-7.6)). The calibration suite below is specifically designed to catch such violations.

## Proposal B — Raw shell as a declared dialect with native parse diagnostics [UNVERIFIED BUILD-SMALL sizing; settle with a two-platform executable-line-count spike]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Retain shell power explicitly:

```json
{
  "dialect": "bash",
  "script": "git show 'origin/main:path with spaces/file.txt' --",
  "cwd": "/work tree",
  "validation": "parse-before-execute"
}
```

Do not accept an unlabelled field named only `command`. Require a dialect (`bash`, `pwsh`, or another deliberately supported parser), resolve the actual executable/version before validation, and run that dialect's own parse-only mechanism before execution. The validator must not execute substitutions or the target command. A parse failure returns a structured diagnostic:

```json
{
  "error_code": "SHELL_PARSE_UNCLOSED_QUOTE",
  "stage": "parse",
  "dialect": "bash",
  "parser_version": "<resolved version>",
  "span": {"start_line": 1, "start_column": 10, "end_line": 1, "end_column": 48},
  "construct": "single_quoted_word",
  "executed": false,
  "safe_summary": "A single-quoted word reaches end of input.",
  "recovery": [
    "Close the quote at the indicated construct.",
    "Use process(program,args) if no shell operators are required."
  ],
  "calibration_status": "reference-suite <id> passed for this parser identity"
}
```

The diagnostic should identify **stage, dialect, construct, location, and non-execution**, not merely echo the shell's EOF text. Do not echo the full command by default: if a secret literal is present, full echo reproduces it in the diagnostic. Preserve an access-controlled raw diagnostic for debugging only when policy permits.

It is **almost certain (90-99%)** that native parse validation will detect ordinary unmatched single- or double-quote syntax before side effects when the validator is the same shell executable/version/mode that will execute the script; the evidence is that quote characters participate directly in Bash quoting and PowerShell tokenization ([GNU Bash, “Quoting”](https://www.gnu.org/software/bash/manual/html_node/Quoting.html); [Microsoft, `about_Parsing`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.6)). It will not establish semantic correctness and must say so.

It is **roughly even (45-55%)** that native parsers across the supported dialect/version matrix will consistently emit the exact location of the opening unmatched quote; this is **UNVERIFIED**, because the official syntax sources establish parsing rules but not uniform diagnostic-span contracts. Settle it with a dialect/version matrix of malformed scripts and compare reported spans to human-labelled opening delimiters. A small wrapper may infer a candidate span, but that inference is also **UNVERIFIED** and is settled by the same experiment. Until it passes, return `span: null` rather than fabricate precision.

## Proposal C — Reference suite, calibration manifest, and change-triggered check standards [UNVERIFIED BUILD-SMALL sizing; settle with a two-platform executable-line-count spike]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Build an inert `argv-probe` and a versioned reference-suite runner. The probe must serialize what the child actually received without ambiguous delimiter parsing: argument count plus a length-prefixed or base64 representation of each argument, with platform encoding named. Do not use a space-joined `echo` as the oracle.

The full reference suite should stratify at least:

- zero arguments, one empty argument, and adjacent empty arguments;
- spaces, tabs, and embedded newlines;
- single quote, double quote, backslash, and backslash-before-quote runs;
- `$`, backtick, semicolon, ampersand, pipe, parentheses, braces, wildcard characters, and leading `-`;
- trailing backslash and paths with spaces;
- non-ASCII BMP and supplementary Unicode characters;
- arguments near configured size limits and a deliberately over-limit request;
- supported target classes: native executable, script with shebang where applicable, and any Windows `.cmd`/`.bat` behavior the harness elects to support.

For each case, compare the structured request's expected vector to the probe's child-observed vector. Store a compact calibration manifest:

```text
reference_suite_id
reference_suite_hash
adapter_build_id
host_os_build
runtime_identity_and_version
shell_identity_version_and_mode (if any)
process_api_path
encoding
timestamp
case_count / pass / fail / skipped
first divergent transform stage
```

This is the invocation-provenance analogue of documenting the measurement system, reference, conditions, result, and time. A pass claim applies only to that result and recorded domain, not to “the tool” forever.

Use two levels:

1. **Full calibration:** on adapter/runtime implementation change and host-image qualification.
2. **Check standards:** a small permanent subset at harness startup after a shell/runtime/config identity change, not on every user command. Include at least an empty argument, whitespace, embedded quotes/backslashes, a shell metacharacter, Unicode, and a near-limit size case.

Event-triggered checks will **very likely (80-90%)** detect environment or version drift before it affects production calls, because the official PowerShell documentation records version- and mode-dependent native argument behavior and NIST's check-standard mechanism is explicitly designed to reveal changing bias/variability. The remaining uncertainty covers unrepresented input classes and changes that do not affect the selected sentinels. Settle the residual with mutation testing: deliberately swap renderer modes or inject escaping defects and measure sentinel detection by defect stratum.

Do not use a Shewhart chart for Boolean deterministic conformance. Do track the operational error rate per 1,000 eligible calls over time, with numerator, denominator, tool mode, and shell dialect. A chart is meaningful there because workloads and environments vary; it is not meaningful as decoration around a fixed parser test.

## Proposal D — “Calibration certificate” attached to diagnostics, not marketing [UNVERIFIED BUILD-SMALL sizing; settle with a two-platform executable-line-count spike]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Every parse or process-creation result should carry machine-readable provenance sufficient to answer:

- What mode was requested: structured process or raw shell?
- Which executable/parser actually handled it?
- Which version and argument-passing mode applied?
- At which stage did it fail: schema, policy, parse, rendering, OS process creation, child startup, or child exit?
- Did execution begin?
- Which reference/check suite last passed under the same identity?
- What is explicitly outside that suite's domain?

This catches a diagnostic failure that ordinary shell error text leaves unresolved: “unexpected EOF” says what the parser noticed, not which tool transformation, dialect assumption, or adapter mode produced it. Provenance does not automatically find the responsible character, but it makes responsibility mechanically localizable.

It is **likely (55-80%)** that an unqualified “certificate” label will be read as broader assurance than reference-case conformance, because VIM itself warns that traceability does not imply fitness or absence of mistakes ([BIPM/JCGM VIM 2.41, note 5](https://jcgm.bipm.org/vim/en/2.41.html)). The UI should therefore label it **conformance evidence** or **calibration manifest**, and state “reference cases passed; semantic intent not assessed.”

## 4. What this would catch that the present symptom does not

The task's only established present symptom is 1,631 unmatched-quote EOF failures. On that evidence, the design catches or prevents:

1. **Unclosed quotation before execution:** raw-shell native parse validation returns a structured parse-stage error and `executed:false`.
2. **Needless quotation generation:** structured process calls do not ask the model to quote individual arguments.
3. **Adapter regressions that reintroduce quoting:** the child-observed reference suite detects divergence even if the rendered string looks plausible.
4. **Dialect mismatch:** a request declaring `bash` cannot silently be calibrated or diagnosed as `pwsh`; parser identity is part of the result.
5. **Mode/version drift:** a previously passing check case fails after the actual shell/runtime/PowerShell native-argument mode changes.
6. **Failure-stage ambiguity:** a parse failure is separated from OS process-creation failure and from non-zero child exit.

The design is **very likely (80-90%)** to catch seeded lost-empty-argument, unintended-expansion, Unicode/encoding-transform, and argument-size-boundary defects when each defect's stratum is represented in the reference suite, because it compares separately encoded child-observed arguments to exact expected values. Their presence or damage in this harness is **UNVERIFIED**; settle it by (a) searching the corpus fingerprints for those independently defined signatures and (b) replaying a stratified sample through the child-observed probe. Both signals are required before claiming a current defect: the fingerprint detector must first demonstrate it finds a seeded known-positive case, and replay must independently reproduce the mismatch.

No claim is made that the present harness lacks typed invocation or parse validation. This unit was explicitly told not to ground in the local repository, and absence requires two mechanically independent signals. The proposed experiment to establish presence/absence is: (1) schema/static discovery, validated against a known-present tool field; and (2) black-box invocation with an empty argument and an unmatched raw quote, observing whether a shell is bypassed and whether execution is blocked before side effects.

## 5. Verification plan and success criteria

### 5.1 Conformance experiment

Create a frozen reference vector for each case and run it through every supported adapter × OS × runtime × shell-mode path into the inert probe. The primary result is exact equality of argument count and encoded values. Report every skipped cell; a skipped platform is not a pass.

Success criterion: 100% exact equality in the declared supported domain, zero target-command execution on malformed raw-script cases, and explicit rejection of over-limit requests before the OS process call. This is a conformance threshold, not a statistical claim.

### 5.2 Mutation experiment

Seed independent defects: remove escaping around whitespace, collapse an empty argument, alter backslash-before-quote behavior, switch PowerShell native argument mode, route through an unintended shell, truncate a long argument, and change encoding. Record which full-suite and check-standard cases detect each mutation.

The check subset is adequate only if every mutation in its declared threat model is detected. A missed mutation expands the check set; it must not be averaged away into a high pass percentage.

### 5.3 Corpus replay experiment

Sample the 1,631 unmatched-quote fingerprints by command shape, shell dialect, and retry-loop membership. Human-label whether each intent is:

- a single executable invocation expressible as structured `program + args`;
- a genuine shell program requiring raw mode; or
- indeterminate from retained data.

Replay sanitized representatives with an inert target. Report prevention/detection by stratum. The structured mode's real-world impact is **roughly even (45-55%)** to exceed half of all 1,631 cases absent this classification; this is deliberately low-confidence because the pinned aggregate gives no distribution of single-process versus genuine shell-program intents. The experiment above settles it.

### 5.4 Operational outcome experiment

Roll out by eligible-call cohort and compare:

- unmatched-quote parse errors per 1,000 raw-shell calls;
- percentage of eligible single-process calls using structured mode;
- retry-loop rate following a parse error;
- false rejection rate of valid raw scripts;
- renderer/calibration divergence events by environment identity;
- time from error to corrected call.

Use denominators and confidence intervals for observed rates. Do not claim causality from an unadjusted before/after count if workload composition changes. A randomized or stepped-wedge exposure over comparable tasks would give stronger evidence.

The combined design is **likely (55-80%)** to reduce quote-error retry loops, because it prevents quoting in eligible calls and gives a localized pre-execution error in the remainder; this forecast is constrained by the absence of corpus-level intent labels and should be replaced by the replay and cohort measurements.

## 6. Alternatives considered and rejected

### Prompt-only quoting guidance — rejected as primary control

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

A rule reminding agents to quote carefully is **unlikely (20-45%)** to remove most quote failures by itself: it leaves the caller responsible for dialect-specific serialization, while Bash has four quoting mechanisms and ordered expansion/quote-removal stages and PowerShell uses different metacharacters, modes, and native-command behavior ([GNU Bash quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html); [Microsoft PowerShell parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.6)). It supplies neither a boundary oracle nor drift detection. Keep concise routing guidance (“prefer structured process mode”), but do not call prose a calibration. Settle the forecast by randomizing the guidance over comparable eligible calls and measuring quote failures per 1,000 calls.

### Universal command AST — rejected

**NATIVE-vs-BUILD: BUILD-LARGE (new runtime; not justified).**

A cross-shell AST would require modeling multiple programming languages, built-ins, expansions, redirections, and platform process semantics. It would become a second orchestration/runtime layer, one of the anti-overfit gate's explicitly rejected components. The small split—typed one-process calls plus native raw-shell parsing—gets the high-value boundary without reimplementing shells.

### Learned quoting critic — rejected

**NATIVE-vs-BUILD: BUILD-LARGE (trained critic; not justified).**

This directly reintroduces a previously rejected trained critic and provides a probabilistic opinion where the actual parser can supply a deterministic syntax result. It also adds training drift and an opaque failure surface. Native parser validation and a child-observed conformance oracle are stronger and smaller.

### Retry with automatically modified quotes — rejected

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook bus), but unsafe.**

Blindly adding or deleting a quote can change command boundaries, expansion, or redirection. An EOF symptom does not uniquely determine intent. Return a localized diagnosis or route to structured arguments; do not execute a guessed repair.

### Numeric “command uncertainty score” — rejected

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines), but conceptually invalid.**

There is no justified measurement model that combines syntax coverage, semantic ambiguity, environment drift, and model intent into one number. NIST requires uncertainty components and evaluation methods to be stated, not hidden behind a scalar ([NIST TN 1297 §7](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-7-reporting-uncertainty)). Report separate facts: exact conformance, supported domain, skipped strata, observed rates, and unresolved intent.

## 7. Anti-overfit gate

The counted proposals pass the gate:

- They ride the existing tool/hook/skill/MCP bus: one structured tool shape, one raw-shell validation path, a small inert probe, and result metadata.
- They do not introduce a second orchestration runtime, vector database or knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
- Full calibration runs on relevant changes; a tiny sentinel set runs only when environment identity changes. There is no always-on daemon.
- The design reduces surface area for common calls by bypassing shell syntax rather than creating a richer planner.
- Raw shell remains available for real shell programs, so the harness does not overfit all execution to a single-process abstraction.

The BUILD-SMALL sizing is **likely (55-80%)** for an MVP limited to an existing process API, native parse-only calls, a compact probe, and manifest emission; this estimate is based on the small number of transformations and reuse of platform parsers, but is **UNVERIFIED** until a spike counts executable lines for one Windows and one POSIX path. If the spike exceeds roughly 200 lines because the existing bus lacks a process API or safe parse hook, reclassify honestly rather than splitting files to game the threshold.

## 8. Recommended sequence

1. Specify the two-mode contract: `process(program,args,...)` and `shell(dialect,script,...)`.
2. Build the inert child-observed probe and full adversarial reference suite before trusting the renderer.
3. Implement the structured path with the platform argument-list API and forbid silent fallback to string joining.
4. Add dialect-native parse-only validation and the structured diagnostic schema.
5. Produce a calibration manifest bound to adapter/runtime/shell/config identities.
6. Select check standards by mutation coverage, not intuition.
7. Classify and replay a stratified sample of the 1,631 measured failures.
8. Roll out to eligible calls and measure error and retry rates with denominators.

This sequence is **very likely (80-90%)** to falsify a bad implementation before broad rollout because the oracle and seeded mutations precede production use, and because the actual child boundary—not merely the rendered string—is compared. ## Bottom line

Metrology's useful contribution is not a metaphorical confidence gauge. Applied narrowly, that gives the harness a calibrated **argument transport boundary** and a truthful **raw-language boundary**.
