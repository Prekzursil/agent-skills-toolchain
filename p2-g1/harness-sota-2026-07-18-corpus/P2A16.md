# P2A16 — Windows agents: what breaks, what assumes POSIX, and what to adopt

**Unit:** P2A16  
**Research date:** 2026-07-18  
**Lens:** external evidence only. This unit intentionally does not inspect or draw conclusions from the owner's local harness, corpus files, audit output, or repositories. The owner's supplied measurements (PowerShell 10.6% errors; 1,631 unmatched-quote Bash failures) are treated only as the motivation for the external question.  
**Source policy:** primary vendor documentation, language/runtime documentation, official project documentation, public source repositories, and issue trackers. Issue reports are treated as reports and reproductions, not as proof that every installation is affected.

## Executive conclusion

Windows agent execution is not one compatibility problem. It is a stack of incompatible contracts: Win32 creates a process from one command-line string; the child chooses how to recover `argv`; `cmd.exe`, PowerShell, C runtimes, Rust, Node, Python, and MSYS/Git Bash do not all recover it the same way; and WSL introduces a second path and filesystem namespace. The Win32 `CreateProcessW` command line is capped at 32,767 characters, while `cmd.exe` has an 8,191-character command-line and inherited-variable limit ([Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Microsoft: cmd.exe limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)). PowerShell 7.3 deliberately changed native argument passing and retains a legacy path for `.bat`, `.cmd`, `cmd.exe`, and several script hosts; Microsoft calls that a breaking change ([Microsoft: about_Parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5)). Git Bash adds automatic POSIX-to-Windows rewriting of arguments and environment variables, which MSYS2 itself says is imperfect and best avoided by not mixing Unix/Cygwin and native tools ([MSYS2: Filesystem Paths](https://www.msys2.org/docs/filesystem-paths/)).

The ecosystem's own Windows posture corroborates the structural mismatch. Claude Code now supports a native PowerShell tool, but its documentation still describes it as a preview, says profiles are not loaded, and says sandboxing is unavailable on native Windows; Git Bash remains available for POSIX scripts ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). OpenHands requires WSL and explicitly says native Windows is not officially supported ([OpenHands CLI quick start](https://docs.openhands.dev/openhands/usage/cli/quick-start)). SWE-agent defaults to a Docker backend and its own release history includes a Windows path fix that replaced host `Path` handling with `PurePosixPath`/strings ([SWE-agent installation](https://swe-agent.com/latest/installation/source/), [SWE-agent releases](https://github.com/SWE-agent/SWE-agent/releases)). Even the reference MCP server documents a Windows-only `cmd /c npx ...` launch form, exposing the `.cmd` shim boundary in nominally portable JSON configuration ([MCP servers: everything](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md)).

The best response is not a second orchestrator, a universal escaping library, or blanket migration to WSL. It is a small execution contract on the existing hook/tool bus: declare the dialect and path namespace, prefer direct executable plus argument-vector invocation, materialize complex commands as short temporary scripts, keep native and WSL workspaces in their matching filesystems, preflight MCP executable resolution, test a small adversarial fixture suite, and use Windows Job Objects for reliable process-tree cleanup. This passes the anti-overfit gate: each measure is local, deterministic, and removable as native agents improve.

## Method and evidence grading

The research was split into five questions:

1. What does Windows itself guarantee about process creation, quoting, paths, files, encodings, and process termination?
2. What extra translation does PowerShell, Git Bash/MSYS2, WSL, Node, Python, Rust, and .NET add?
3. What do leading coding-agent projects officially support on Windows?
4. Which Windows failures recur in official project issue trackers with concrete reproductions?
5. Which countermeasures are native capabilities versus small harness additions?

Sources were deep-read from Microsoft, Python, Node.js, Rust, MSYS2, Git for Windows, Anthropic, OpenHands, SWE-agent, MCP, and Aider documentation. GitHub issues were used only where the issue contains a concrete environment, command, result, and workaround or linked duplicate cluster. A single issue never establishes prevalence.

Evidence grades used below:

- **Established:** normative platform/runtime documentation, or official product behavior explicitly documented.
- **Corroborated field evidence:** multiple independent project docs or reproducible issue reports consistent with the normative mechanism.
- **Promising but unproven:** a mechanism is technically grounded, but no owner-specific controlled trial has measured its effect.
- **Hype / overclaim:** a claim is stronger than the cited evidence permits, or erases a documented boundary.

## 1. What is actually established

### 1.1 Windows passes a command-line string, not a POSIX `argv[]`

`CreateProcessW` accepts a mutable command-line string whose maximum is 32,767 characters including the terminating null. If `lpApplicationName` is null, Windows derives the executable from the first whitespace-delimited token, making quoting of executable paths with spaces significant ([Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)). This is a different primitive from Unix process creation, where arguments are already an array.

Rust's standard library states the consequence directly: Unix passes arguments as an array of strings, while Windows passes one command-line string and leaves parsing to the child. Rust warns that programs with custom parsers may see a different array than the parent intended; it singles out `cmd.exe` and batch files as non-standard and especially vulnerable to malicious input ([Rust `std::process`](https://doc.rust-lang.org/std/process/index.html)). Python likewise documents the Microsoft C runtime conversion rules it uses when turning an argument sequence into a Windows command string ([Python `subprocess`](https://docs.python.org/3/library/subprocess.html#converting-an-argument-sequence-to-a-string-on-windows)).

Therefore, “the argument was already quoted” is not a stable property across layers. Quoting is a transformation relative to a specific next parser. An agent command embedded as JSON, then in PowerShell, then in `cmd /c`, then in a batch shim can be parsed several times under different grammars.

### 1.2 There are two important length ceilings, and response files are Microsoft's documented workaround

The Win32 `CreateProcessW` ceiling is 32,767 characters ([Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)). `cmd.exe` is stricter: Microsoft documents 8,191 characters for the command line, inherited individual environment variables such as `PATH`, and expansions in batch processing ([Microsoft: command prompt line limitation](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)). Microsoft recommends changing programs with long argument sets to accept a parameter/response file, and shortening large inherited environment variables.

These limits are independent of filesystem `MAX_PATH`. Enabling long paths can help file APIs, but cannot increase `CreateProcessW`'s command-line limit. Microsoft's long-path documentation says long paths require both a registry setting and an application manifest opt-in; it lists file APIs affected, not process-command-line capacity ([Microsoft: Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)).

### 1.3 PowerShell is a distinct language and adds a native-command compatibility boundary

PowerShell has expression and argument parsing modes, its escape character is the backtick, and its quoting/interpolation rules differ from Bash ([Microsoft: about_Parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5), [Microsoft: about_Quoting_Rules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-7.6)). Bash instead uses backslash, single quotes, double quotes, and dollar-single quotes, with `$`, backticks, backslash, and sometimes `!` retaining special behavior inside double quotes ([GNU Bash: Quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html), [GNU Bash: Double Quotes](https://www.gnu.org/software/bash/manual/html_node/Double-Quotes.html)). Text valid and literal in one dialect can be executable syntax in the other.

PowerShell 7.3 changed native argument passing. `$PSNativeCommandArgumentPassing` has `Legacy`, `Standard`, and `Windows` modes; on Windows the default `Windows` mode automatically uses legacy behavior for `cmd.exe`, `.bat`, `.cmd`, Windows Script Host files, and related hosts. Microsoft explicitly calls the change breaking for automation with previous workarounds ([Microsoft: about_Parsing, native arguments](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5#passing-arguments-to-native-commands)). The `--%` stop-parsing token is Windows-only and still performs `%ENVVAR%` substitution; it is not a general data-safe parameter API ([same source](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.5#the-stop-parsing-token)).

PowerShell's `Start-Process -ArgumentList` is also not an argument-vector escape hatch: its documentation says an array is joined into one string and that values containing spaces or quotes still require escaped double quotes ([Microsoft: Start-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process)). By contrast, .NET's `ProcessStartInfo.ArgumentList` says individual strings do not need to be pre-escaped and recommends it over the string `Arguments` property when escaping is uncertain ([Microsoft: ProcessStartInfo.ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)).

### 1.4 “Use a list of arguments” is the stable default, with a `.cmd`/`.bat` caveat

Node's `child_process.execFile(file, args)` does not spawn a shell by default; Node documents that `.bat` and `.cmd` files cannot be launched directly on Windows and instead require a shell, `cmd.exe`, or `exec()` ([Node.js child process](https://nodejs.org/api/child_process.html)). Python recommends argument sequences and `shell=False`; it warns that Windows may launch `.bat`/`.cmd` through a system shell regardless, so batch arguments can receive shell parsing without Python escaping ([Python `subprocess`: Security Considerations](https://docs.python.org/3/library/subprocess.html#security-considerations)). Python separately warns that `shlex.quote()` is only designed for Unix shells and can enable command injection if treated as a Windows quoting function ([Python `shlex`](https://docs.python.org/3/library/shlex.html)).

This establishes a practical hierarchy:

1. Direct native executable + structured argument list is the least ambiguous form.
2. A known shell + a script file is preferable when shell syntax is actually required.
3. A nested command string (`pwsh -Command "..."`, `bash -lc '...'`, `cmd /c "..."`) is the most fragile form and should be reserved for genuinely dynamic shell operations.
4. `.cmd`/`.bat` and npm shims require explicit handling because direct-spawn semantics do not port cleanly.

### 1.5 Git Bash is a compatibility environment, not native POSIX behavior

MSYS2 documents automatic Unix-to-Windows conversion of both process arguments and environment variables when a native Windows program is launched. It gives examples where `--dir=/foo` becomes a Windows path and `/foo:/bla` becomes a semicolon-separated Windows path list. It also states that the conversion is imperfect and recommends avoiding mixed Unix/Cygwin and native tools or converting paths deliberately ([MSYS2: Filesystem Paths](https://www.msys2.org/docs/filesystem-paths/)). `MSYS2_ARG_CONV_EXCL`, `MSYS2_ENV_CONV_EXCL`, and `cygpath` exist as targeted escapes, not proof of transparent compatibility.

Git for Windows publishes the same limitation in its release notes: slash-prefixed options can trigger POSIX-to-Windows conversion; `MSYS_NO_PATHCONV=1` or a doubled leading slash can suppress it. The release notes also state that symlink support is disabled by default when Developer Mode is off because special permission is otherwise required, and warn about deeply nested directory trees ([Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md)).

Terminal behavior is a separate seam. GitHub CLI documents known input-prompt problems under Git Bash's MinTTY and offers Windows Terminal, experimental pseudoconsole support, or `winpty` as workarounds ([GitHub CLI: `gh help mintty`](https://cli.github.com/manual/gh_help_mintty)). An agent that runs non-interactively avoids some prompt issues but still inherits MSYS path conversion and process-launch semantics.

### 1.6 WSL is a real Linux environment, but crossing its filesystem boundary has costs and semantic changes

Microsoft describes WSL 2 as a Linux environment with full system-call compatibility relative to WSL 1 ([Microsoft: What is WSL](https://learn.microsoft.com/en-us/windows/wsl/about), [Microsoft: Compare WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions)). It is the cleanest way on a Windows host to obtain Linux process, shell, case-sensitivity, and sandbox primitives.

Microsoft also recommends not working across operating systems' filesystems without a specific reason: keep Linux-command-line projects in the WSL filesystem and Windows-command-line projects in the Windows filesystem. `/mnt/c/...` is supported, but slower for a WSL 2 Linux workload than the WSL filesystem ([Microsoft: Working across file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)). Windows paths are case-insensitive by default, Linux paths are case-sensitive, and NTFS case sensitivity can be enabled per directory; Microsoft warns that Windows applications may fail in case-sensitive directories because they assume case insensitivity ([Microsoft: WSL case sensitivity](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)).

WSL is therefore an execution lane, not a transparent shell swap for the same workspace. A harness must know whether its current path is `C:\...`, `/mnt/c/...`, or `/home/...`, which side owns the toolchain, and which side is authoritative for file mutations.

### 1.7 Windows filesystem semantics affect agent cleanup and patch workflows

Windows normally treats file names case-insensitively; Linux normally treats them case-sensitively, with per-directory NTFS case sensitivity adding a mixed mode ([Microsoft: WSL case sensitivity](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)). This can turn case-only renames, case-colliding generated files, and allowlist comparisons into platform-specific failures.

Open file handles also matter. Microsoft states that a file cannot be deleted until all handles that deny delete sharing are closed and its name cannot be reused until deletion completes; renaming is the documented way to reuse a name immediately in some cases ([Microsoft: Closing and Deleting Files](https://learn.microsoft.com/en-us/windows/win32/fileio/closing-and-deleting-files)). This explains why Unix-style “unlink now, process can keep reading” assumptions are unsafe on Windows and why agents encounter transient sharing violations from test runners, antivirus, language servers, or dev servers.

Symlink creation is conditional. Win32 exposes `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE`, but the documentation notes Developer Mode requirements for the relevant app context and long-path details ([Microsoft: CreateSymbolicLink](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw)). Git for Windows accordingly disables symlinks by default in common configurations ([Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md)).

### 1.8 Encoding behavior has improved, but version drift remains real

Windows PowerShell 5.1 uses inconsistent defaults across cmdlets and commonly writes UTF-16LE or active-code-page text. PowerShell 7 defaults to UTF-8 without BOM for output, and PowerShell 7.4 changed native stdout redirection to preserve byte streams ([Microsoft: about_Character_Encoding](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding), [Microsoft: about_Redirection](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_redirection)). Therefore `powershell.exe` and `pwsh.exe` are not interchangeable execution targets for artifact generation, log parsing, or patch inputs.

An agent harness must record the actual shell executable and version. Merely labelling both “PowerShell” erases encoding and argument-passing differences that Microsoft documents as behavior changes.

### 1.9 Killing a shell process does not kill its child tree on Windows

Microsoft states that terminating a process does not terminate child processes it created ([Microsoft: Terminating a Process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)). Windows Job Objects are the native unit for grouping processes; children join the job by default, `TerminateJobObject` ends associated processes and nested child jobs, and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` can clean up the group when the final handle closes ([Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Microsoft: TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)). Breakaway flags and nested jobs require explicit handling, so `taskkill` or killing only `pwsh.exe` is not equivalent.

For agent harnesses, this is not cosmetic. A timed-out test runner or development server can retain file locks, ports, watchers, and inherited pipes after its parent shell is gone, causing later steps to fail for reasons detached from the original timeout.

### 1.10 Coding-agent ecosystems still expose POSIX assumptions

The strongest evidence is official support posture, not anecdotes:

- Claude Code's current Windows setup supports native Windows and WSL. Git for Windows enables the Bash tool; without it, Claude uses the PowerShell tool. The PowerShell tool is rolling out, is primary when enabled, does not load profiles, and has no native-Windows sandbox support ([Anthropic getting started](https://code.claude.com/docs/en/getting-started), [Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). Anthropic's sandbox documentation says OS-level sandboxing uses Seatbelt on macOS, bubblewrap on Linux and WSL 2, and does not run on native Windows ([Anthropic sandboxing](https://code.claude.com/docs/en/sandboxing)).
- OpenHands says its CLI requires WSL and native Windows is not officially supported; its local Windows setup requires WSL 2 and Docker Desktop integration and tells users to run commands inside WSL ([OpenHands CLI quick start](https://docs.openhands.dev/openhands/usage/cli/quick-start), [OpenHands local setup](https://docs.openhands.dev/openhands/usage/run-openhands/local-setup)).
- SWE-agent recommends Docker as its default backend; its documentation examples use `which python`, and its release notes record a Windows path fix involving `PurePosixPath`, showing host/container path-domain leakage is a maintained concern ([SWE-agent source install](https://swe-agent.com/latest/installation/source/), [SWE-agent releases](https://github.com/SWE-agent/SWE-agent/releases)).
- Aider is a useful counterexample: it ships a PowerShell installer, documents Windows-specific command discovery (`python -m aider`), has platform-specific editor and notification behavior, and exposes explicit `--encoding` and `--line-endings` options ([Aider install](https://aider.chat/docs/install.html), [Aider not found](https://aider.chat/docs/troubleshooting/aider-not-found.html), [Aider options](https://aider.chat/docs/config/options.html)). Portability is possible, but it requires explicit OS branches.
- The MCP reference “everything” server changes its launch configuration on Windows from direct `npx` to `cmd /c npx`, because npm's Windows entry point is a command shim rather than a directly executable binary ([MCP servers: everything](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md)).

The ecosystem does not uniformly assume POSIX, but the most execution-heavy agents often either require WSL/Docker or maintain distinct Windows paths. That is evidence against treating one free-form `shell_command: string` as a portable abstraction.

### 1.11 Concrete issue reports align with the documented mechanisms

These are field signals, not prevalence estimates:

- Anthropic's tracker contains a detailed Windows report where a correctly reachable Git Bash path was rejected and a duplicate bot linked several related Git Bash detection reports ([anthropics/claude-code #47923](https://github.com/anthropics/claude-code/issues/47923)). Another report documents paths with spaces being truncated in a shell-mediated setting ([#1726](https://github.com/anthropics/claude-code/issues/1726)). These are consistent with executable discovery and string-quoting boundaries documented by Node and Win32.
- OpenAI's tracker contains a Windows MCP report where `corepack`/`npx` failed but an absolute `node.exe` plus script path worked; the reporter also verified the server with the official MCP SDK client ([openai/codex #16229](https://github.com/openai/codex/issues/16229)). The MCP reference server independently documents `cmd /c npx` for Windows, providing a mechanically independent signal for the shim boundary ([MCP server README](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md)).
- The MCP filesystem tracker has Windows reports involving drive-letter case and allowlist/path normalization inconsistencies ([modelcontextprotocol/servers #1838](https://github.com/modelcontextprotocol/servers/issues/1838)). Microsoft's case-sensitivity documentation independently establishes that Windows, Linux, and per-directory NTFS modes differ ([Microsoft: WSL case sensitivity](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)).
- OpenAI's Codex tracker includes recent Windows reports where native sandbox setup or WSL/Windows runner selection failed before the user's command executed ([openai/codex #26158](https://github.com/openai/codex/issues/26158), [#22185](https://github.com/openai/codex/issues/22185), [#21147](https://github.com/openai/codex/issues/21147)). These reports are version-specific and do not establish that current Codex is generally unusable; they do establish that execution-lane identity and sandbox setup need direct health probes rather than inference from a successful CLI launch.

## 2. What is promising but unproven

Every claim in this section is forward-looking and therefore carries the required confidence band.

### 2.1 Structured execution will reduce quoting failures — **very likely (80-90%)**

It is **very likely (80-90%)** that moving deterministic invocations from model-generated shell strings to `{executable, args[], cwd, env}` will materially reduce quoting and injection failures. Evidence: Node `execFile`, Python `subprocess` with `shell=False`, Rust `Command`, and .NET `ProcessStartInfo.ArgumentList` all expose structured argument APIs specifically to avoid shell parsing; Python explicitly warns that Unix `shlex.quote` is not correct for Windows ([Node](https://nodejs.org/api/child_process.html), [Python subprocess](https://docs.python.org/3/library/subprocess.html), [Python shlex](https://docs.python.org/3/library/shlex.html), [Rust](https://doc.rust-lang.org/std/process/index.html), [.NET](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)). The uncertainty is the fraction of the owner's failures that come from commands which genuinely require pipelines, redirection, shell expansion, or compound control flow.

This is not a claim that Windows has a true kernel-level `argv[]`; the runtime still serializes to a string. It is a claim that one trusted runtime serializer is safer than asking a model to hand-compose every quoting layer.

### 2.2 Script-file materialization will help long and nested commands — **very likely (80-90%)**

It is **very likely (80-90%)** that writing complex PowerShell/Bash programs to a temporary `.ps1`/`.sh` file and invoking the shell with a short file path will reduce unmatched-quote and command-length failures. Evidence: Microsoft recommends parameter files for long command lines; a script file removes at least one outer quoting grammar and keeps the launch line short ([Microsoft command-line limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)). Bash and PowerShell have materially different quoting grammars, so avoiding embedding one program inside another string removes a documented parser boundary ([GNU Bash quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html), [PowerShell quoting](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules)).

The unproven part is the exact error-rate reduction and whether temporary-file lifecycle introduces meaningful antivirus/file-lock latency in this owner's environment.

### 2.3 A typed Windows execution preflight will prevent false retries — **likely (55-80%)**

It is **likely (55-80%)** that a preflight which resolves the actual executable, records shell/version/path namespace, and runs an adversarial argument echo before long work will prevent retry loops caused by misidentified execution lanes. Evidence: official Claude documentation exposes separate Bash and PowerShell tools with distinct availability and limitations, MCP's reference configuration has a Windows-only launch form, and multiple Codex issue reports fail before the requested command executes ([Anthropic tools](https://code.claude.com/docs/en/tools-reference), [MCP README](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md), [Codex #26158](https://github.com/openai/codex/issues/26158)).

The uncertainty is whether startup checks become stale after upgrades, environment mutation, or a long-lived process retaining old state. The check must be cheap enough to run per session and on first failure, not only at install time.

### 2.4 Windows Job Objects will improve timeout cleanup — **very likely (80-90%)**

It is **very likely (80-90%)** that assigning each long-running tool call to a Job Object with `KILL_ON_JOB_CLOSE` will reduce orphaned children, retained ports, and file locks after timeout. Evidence: Microsoft explicitly states that ordinary process termination does not terminate children and that Job Objects manage and terminate a process group ([Terminating a Process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

The residual uncertainty comes from processes that deliberately break away, nested job constraints imposed by an outer sandbox/IDE, and commands that must survive the parent by design.

### 2.5 Lane-aligned workspace placement will improve WSL reliability and speed — **very likely (80-90%)**

It is **very likely (80-90%)** that keeping Linux-agent workspaces under the WSL filesystem and native-agent workspaces on NTFS will reduce performance and semantic surprises. Evidence: Microsoft directly recommends this alignment and warns against cross-OS filesystem work without a specific reason ([Microsoft WSL filesystems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)).

It is only **likely (55-80%)** that this should become the owner's default for all projects, because Windows-native projects may require Visual Studio, Windows SDKs, PowerShell modules, COM, or native test runners that cannot operate wholly from a Linux-owned workspace. The correct unit is per-project lane selection, not fleet-wide migration.

### 2.6 Shell-dialect linting can catch obvious cross-language errors — **likely (55-80%)**

It is **likely (55-80%)** that a small pre-execution detector can catch high-signal mistakes such as Bash process substitution in PowerShell, PowerShell `$env:NAME` in Bash, `^` used as a PowerShell escape, `which` used where a Windows `.cmd` shim must be resolved, or raw `cmd /c` nesting with metacharacters. Evidence: the grammars and metacharacters are explicitly documented by PowerShell and Bash, and PSScriptAnalyzer emits parse errors and supports CI exit codes ([PowerShell parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing), [Bash quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html), [PSScriptAnalyzer overview](https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/overview), [Invoke-ScriptAnalyzer](https://learn.microsoft.com/en-us/powershell/module/psscriptanalyzer/invoke-scriptanalyzer)).

It is **unlikely (20-45%)** that static linting alone will catch most native-argument corruption, because many failures are syntactically valid and arise only after the next parser or MSYS path converter runs. A conformance execution fixture is necessary.

### 2.7 Native PowerShell as Claude's primary Windows shell is promising — **likely (55-80%)**

It is **likely (55-80%)** that enabling Claude Code's native PowerShell tool as primary on Windows-native repositories will outperform routing Windows-native work through Git Bash. Evidence: Anthropic now provides a distinct native PowerShell tool, makes it primary when enabled, and keeps Bash for POSIX scripts; MSYS2 recommends avoiding mixed Unix/native tool chains ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference), [MSYS2 paths](https://www.msys2.org/docs/filesystem-paths/)).

It is not yet established as an across-the-board default because Anthropic labels limitations: profiles are not loaded and native-Windows sandboxing is unsupported ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). Security-sensitive unattended execution may therefore favor WSL 2 even if PowerShell syntax reliability improves.

### 2.8 Absolute MCP executable paths will improve startup determinism — **likely (55-80%)**

It is **likely (55-80%)** that resolving MCP launchers to an absolute real executable plus script path at configuration-generation time will reduce Windows startup failures compared with relying on `npx`, `uvx`, `corepack`, or `.cmd` discovery inside a different host environment. Evidence: the MCP reference server documents `cmd /c npx` on Windows, Node documents that `.cmd` is not directly executable through `execFile`, and a Codex issue reports an absolute `node.exe` plus JS entry point working where common shims failed ([MCP README](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md), [Node child process](https://nodejs.org/api/child_process.html), [Codex #16229](https://github.com/openai/codex/issues/16229)).

The tradeoff is upgrade drift: absolute package entry points can change. The preflight must validate and regenerate them rather than freezing paths forever.

## 3. What is hype, and how to tell

### 3.1 “WSL solves Windows compatibility”

This is an overclaim. WSL supplies genuine Linux semantics, but Microsoft explicitly distinguishes the WSL and Windows filesystems, recommends lane-aligned storage, and documents case-sensitivity differences ([Microsoft WSL filesystems](https://learn.microsoft.com/en-us/windows/wsl/filesystems), [case sensitivity](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)). Agent projects can still misroute a Windows executable into WSL or map a WSL workspace to an invalid Windows path, as concrete Codex reports illustrate ([Codex #21147](https://github.com/openai/codex/issues/21147), [#22185](https://github.com/openai/codex/issues/22185)).

**How to tell:** a proposal says “run it in WSL” but does not specify workspace location, path conversion, executable ownership, credential location, IDE boundary, or Windows-native tool requirements.

### 3.2 “Git Bash makes Windows POSIX-compatible”

This is false as a general statement. MSYS2 documents automatic path and environment rewriting, ambiguous meanings for `/foo`, differing path-list separators, and imperfect conversion; Git for Windows publishes opt-outs for false conversions ([MSYS2 paths](https://www.msys2.org/docs/filesystem-paths/), [Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md)).

**How to tell:** the proposal cites successful `ls`/`grep` usage but has no adversarial test involving a native Windows executable, a slash-prefixed non-path argument, a path with spaces, a drive letter, or a colon-separated value.

### 3.3 “One quoting helper can make every Windows command safe”

This is incompatible with the documented model. Windows passes one string and children choose their parsers; Rust explicitly warns that custom parsers differ, Python says `shlex` is Unix-only, and PowerShell retains legacy handling for `cmd`/batch programs ([Rust process](https://doc.rust-lang.org/std/process/index.html), [Python shlex](https://docs.python.org/3/library/shlex.html), [PowerShell parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing)).

**How to tell:** the helper accepts only a string and no target parser/executable type. Correct escaping is a function of the next parser, not a property of text in isolation.

### 3.4 “Switching every command to PowerShell eliminates quoting bugs”

PowerShell removes the Git Bash/MSYS layer for native Windows work, which is useful, but it still parses its own language and then serializes arguments for native applications. Microsoft documents a breaking change in 7.3 and special legacy behavior for batch/cmd targets ([PowerShell parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing)). `Start-Process -ArgumentList` itself joins arrays into a string ([Start-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process)).

**How to tell:** the proposal changes the shell name but preserves model-generated nested command strings and does not pin `pwsh` versus `powershell.exe`.

### 3.5 “Enable long paths and error 206/ENAMETOOLONG is solved”

This conflates filesystem path limits with process command-line length. Long-path opt-in affects file APIs; `CreateProcessW` retains its 32,767-character command-line ceiling and `cmd.exe` retains 8,191 characters ([Microsoft long paths](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [cmd limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)).

**How to tell:** the proposed fix never measures the final expanded command line and environment, and never uses a response file or short manifest.

### 3.6 “Containerize every agent action”

Containers provide a coherent Linux environment and can be appropriate for Linux-targeted code, as OpenHands and SWE-agent demonstrate ([OpenHands local setup](https://docs.openhands.dev/openhands/usage/run-openhands/local-setup), [SWE-agent install](https://swe-agent.com/latest/installation/source/)). They do not automatically support Windows-native toolchains, COM, desktop applications, Windows services, or the exact host environment; mounted workspaces remain mutable and OpenHands explicitly warns about that ([OpenHands FAQ](https://docs.openhands.dev/overview/faqs)).

**How to tell:** the proposal offers isolation as proof of semantic compatibility, or omits the host/container filesystem and credential boundaries. For this owner it would also risk becoming a previously rejected second runtime if installed as the universal path rather than a project-selected lane.

### 3.7 “More orchestration will route around platform defects”

No external evidence reviewed here shows that another durable runtime, agent router, knowledge graph, trained critic, or observability service is necessary to address shell grammar, argument serialization, path namespace, or process-tree cleanup. These are local deterministic execution concerns with native APIs and existing hook points.

**How to tell:** the proposal adds a daemon before it can state the next parser, actual executable, final command length, workspace namespace, or cancellation unit. Complexity is being used in place of an execution contract.

## 4. Specific, concrete things this owner's harness should adopt

All proposals include the required NATIVE-vs-BUILD value and an explicit anti-overfit decision. Confidence describes expected benefit, not implementation certainty.

### 4.1 Make PowerShell primary for Windows-native Claude work, keep Bash explicit — **NATIVE (Claude Code already does this; we just enable it)**

Enable `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` and set `defaultShell` to `powershell` for Windows-native repositories. Require skills and command hooks to state `shell: powershell` or Bash explicitly instead of inheriting an ambiguous default. Anthropic documents all three controls and says PowerShell becomes primary while Bash remains for POSIX scripts ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). Pin and report the actual executable/version; prefer PowerShell 7 (`pwsh.exe`) because PowerShell 5.1 has materially different encoding defaults ([Microsoft encoding](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding)).

Expected benefit is **likely (55-80%)**, based on removing the MSYS rewrite layer from Windows-native commands while retaining a POSIX lane when genuinely required ([MSYS2 paths](https://www.msys2.org/docs/filesystem-paths/)).

Security condition: do not interpret this as enabling unattended native-Windows sandboxing. Anthropic states that the PowerShell preview and native Windows do not support its sandbox ([Anthropic tools](https://code.claude.com/docs/en/tools-reference), [sandboxing](https://code.claude.com/docs/en/sandboxing)). Use WSL 2 for tasks whose authorization depends on OS-enforced sandbox containment.

**Anti-overfit gate:** passes. This enables a native tool and adds no runtime.

### 4.2 Add a per-command execution contract — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Define a small JSON envelope accepted by the existing execution hook/wrapper:

```json
{
  "executor": "pwsh|git-bash|wsl|direct",
  "mode": "script|argv",
  "program": "absolute executable for argv mode",
  "args": ["one", "element", "per", "argument"],
  "cwd_namespace": "windows|wsl",
  "cwd": "absolute path in that namespace",
  "encoding": "utf-8",
  "timeout_ms": 60000,
  "kill_tree": true
}
```

Reject only impossible combinations (for example `cwd_namespace=wsl` with a raw `C:\...` cwd sent to Linux). Otherwise inject a correction describing the mismatch. Direct mode must use an argument-list API; script mode materializes a file as described next.

Expected benefit is **very likely (80-90%)** because every cited runtime distinguishes direct structured invocation from shell-string invocation ([Node](https://nodejs.org/api/child_process.html), [Python](https://docs.python.org/3/library/subprocess.html), [Rust](https://doc.rust-lang.org/std/process/index.html), [.NET](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)).

**Anti-overfit gate:** passes. It is a schema plus a thin adapter on the current tool bus, not a scheduler or orchestrator. Keep free-form shell tools available for exploratory commands; do not force every one-liner through the envelope.

### 4.3 Materialize complex shell programs to temporary files — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

When a command contains a newline, nested shell call, here-document/here-string, more than one quoting layer, or approaches a conservative length threshold, write it to a session-temp file and execute:

- PowerShell: `pwsh.exe -NoLogo -NoProfile -NonInteractive -File <absolute.ps1>`
- Git Bash: absolute `bash.exe --noprofile --norc <posix-or-converted-path.sh>`; write LF line endings
- WSL: `wsl.exe -d <distro> --cd <linux-path> -- /usr/bin/bash <linux-path.sh>`

Pass dynamic data via environment variables, stdin, JSON files, or typed arguments rather than interpolating it into the script source. Record the temp path and content hash in the tool result, then delete it after all associated process handles close.

Expected benefit is **very likely (80-90%)**, grounded in Microsoft's response-file workaround and the documented grammar differences ([Microsoft command limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation), [PowerShell quoting](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules), [Bash quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html)).

**Anti-overfit gate:** passes. It is a local transformation inside the executor. It removes complexity from command strings.

### 4.4 Add an adversarial execution conformance fixture and run it at session start/on executor change — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Use a tiny argument-echo program (PowerShell/.NET or Node) and assert round trips for:

- empty argument;
- spaces and tabs;
- trailing backslashes before quotes;
- literal single quote and double quote;
- `& | < > ^ % ! $ ` ; ( ) [ ] { }`;
- Unicode outside the active legacy code page;
- `C:\Program Files\x\`, UNC path, and `\\?\` path;
- `/foo`, `--regex=/a/b/`, and colon/semicolon path-list shapes under Git Bash;
- command lengths below/above 8,191 and near 32,767 without actually launching an unsafe payload;
- `.exe`, `.cmd`, and direct JS/Python entry-point launch.

The detector control is built in: first assert that the fixture catches a deliberately corrupted known-present argument, then run the real executor. Emit a terminal result such as `SUCCESS:exec-contract-pwsh-7.6` or `FAILED:exec-contract-git-bash slash-argument-rewritten`.

Expected value is **likely (55-80%)**: the fixture directly exercises the runtime boundary, unlike static lint alone. The exact correlation with real task success is unmeasured.

**Anti-overfit gate:** passes. This is a deterministic smoke test, not an eval service or trained critic.

### 4.5 Pre-resolve MCP commands to real executables and health-check them — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

At config generation or session preflight:

1. Resolve the launcher with Windows-aware command discovery, including `PATHEXT` and `.cmd` shims.
2. Prefer a real executable plus entry script (`node.exe`, `python.exe`, `uv.exe`) and argument array.
3. If a `.cmd` shim is unavoidable, represent `cmd.exe`, `/d`, `/s`, `/c`, and the shim invocation explicitly; never pretend the shim is a directly executable binary.
4. Capture executable path, version, cwd, sanitized environment fingerprint, and a protocol initialize/handshake result.
5. On failure, do not retry the same launch string; fail with the layer (`resolve`, `spawn`, `protocol-init`, or `server-method`).

This follows the MCP project's Windows-specific `cmd /c npx` documentation and Node's `.cmd` behavior ([MCP README](https://github.com/modelcontextprotocol/servers/blob/main/src/everything/README.md), [Node child process](https://nodejs.org/api/child_process.html)). Expected benefit is **likely (55-80%)**, with public Codex field evidence that absolute `node.exe` plus script can succeed where shims fail ([Codex #16229](https://github.com/openai/codex/issues/16229)).

**Anti-overfit gate:** passes. It improves existing MCP stdio launch and adds no MCP proxy or daemon.

### 4.6 Select one execution/filesystem lane per project — **CONFIG (settings/JSON only)**

Declare one of:

- `windows-native`: NTFS workspace; PowerShell/direct Windows executables; no implicit WSL path conversion.
- `wsl-linux`: workspace under `/home/...`; Linux tools and WSL 2 sandbox; Windows GUI access only through explicit interoperability.
- `mixed-required`: exception with named boundary conversions and tests.

Do not default Linux commands to `/mnt/c` merely because the path is visible. Microsoft recommends matching workspace storage to the command-line environment ([Microsoft WSL filesystems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)). Expected benefit is **very likely (80-90%)** for WSL-heavy work and **likely (55-80%)** across the owner's heterogeneous projects.

For a mixed project, convert paths only at the boundary (`wslpath`, `cygpath`, or a documented mapping) and keep both native and Linux forms in structured fields. Never mutate a single path string in place and then guess which namespace it represents.

**Anti-overfit gate:** passes. This is project metadata on the existing runtime, not another runtime.

### 4.7 Add a Windows filesystem capability preflight — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Before a project enables autonomous mutation, test in a disposable directory inside that project volume:

- case-only rename and case-collision behavior;
- symlink creation and read-back;
- long nested path creation through the same runtime that will edit files;
- rename/delete while a handle is open;
- UTF-8 no-BOM round trip;
- executable discovery for `.exe` and `.cmd`;
- actual temp directory path and free space.

Prove the detector with known-present controls (ordinary file create/read/delete, deliberate case mismatch, deliberate locked file) before reporting a capability absent or broken. Cache by volume + executor version, but rerun after toolchain upgrades.

Expected benefit is **likely (55-80%)**, grounded in documented case sensitivity, symlink permissions, long-path opt-in, and deletion semantics ([case sensitivity](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity), [CreateSymbolicLink](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw), [long paths](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), [deleting files](https://learn.microsoft.com/en-us/windows/win32/fileio/closing-and-deleting-files)).

**Anti-overfit gate:** passes. It is a disposable probe through existing hooks.

### 4.8 Use response files/manifests before the command line becomes long — **CONFIG (settings/JSON only)**

Set conservative launch budgets: treat 7,500 characters as a `cmd.exe` danger threshold and 28,000 characters as a `CreateProcessW` danger threshold, leaving headroom for executable names, wrappers, and quoting expansion. These exact thresholds are policy margins, not Windows guarantees. For supported tools, use response files (`@file`), file lists, test manifests, or input JSON. For enumeration, stream via stdin or a file instead of expanding thousands of paths into one command.

Expected benefit is **very likely (80-90%)** when large fan-outs are present because Microsoft's documented workaround is a parameter file ([Microsoft cmd limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)). The remaining uncertainty is tool-specific response-file syntax.

**Anti-overfit gate:** passes. This reduces command size and uses existing tool features.

### 4.9 Put each long-running Windows command in a Job Object — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Extend the existing long-operation wrapper, not the agent orchestrator. On Windows:

1. create a Job Object;
2. set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
3. start the child suspended when necessary, assign it to the job, then resume;
4. on timeout/cancel, terminate the job and wait for closure;
5. report breakaway/assignment failure explicitly;
6. verify that the port, file handle, and child PID are gone before `SUCCESS:cleanup`.

Expected benefit is **very likely (80-90%)** because normal process termination does not kill children and Job Objects are Microsoft's process-group mechanism ([Microsoft process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

**Anti-overfit gate:** passes if implemented inside the existing longrun wrapper. A new resident process supervisor would fail the gate as a second orchestration runtime.

### 4.10 Pin shell identity and normalize encoding — **CONFIG (settings/JSON only)**

For reproducible PowerShell scripts, invoke `pwsh.exe` explicitly, record `$PSVersionTable.PSVersion` and `$PSNativeCommandArgumentPassing`, use `-NoProfile -NonInteractive`, and write artifacts with explicit UTF-8 encoding. Treat Windows PowerShell 5.1 as a separate executor rather than a fallback with identical semantics. PowerShell's own documentation establishes the encoding and native-argument differences ([encoding](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding), [parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing)).

Expected benefit is **likely (55-80%)** for text corruption and version-dependent quoting; it will not address MSYS or `cmd` issues by itself.

**Anti-overfit gate:** passes. Pure configuration and provenance.

### 4.11 Add high-signal shell mismatch rules, but inject rather than broadly block — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Pre-execution hook rules should recognize a short, falsifiable set:

- PowerShell target containing Bash-only `<(...)`, `source`, `export NAME=`, or unquoted `$(...)` intended as Bash command substitution;
- Bash target containing `$env:NAME`, `Get-ChildItem`, PowerShell here-strings, or backtick escaping;
- PowerShell target using `^` as if it were the shell escape;
- use of `which` to establish that a Windows command/shim exists; require Windows-aware resolution or an absolute path;
- any shell string that embeds a second shell and contains untrusted/dynamic data;
- Git Bash launching a native executable with slash-prefixed non-path arguments without an explicit MSYS conversion policy.

Use the real parser where available: PowerShell AST/PSScriptAnalyzer for `.ps1`; `bash -n` for `.sh`. PSScriptAnalyzer includes parse errors and CI exit behavior ([PSScriptAnalyzer usage](https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/using-scriptanalyzer), [Invoke-ScriptAnalyzer](https://learn.microsoft.com/en-us/powershell/module/psscriptanalyzer/invoke-scriptanalyzer)). Inject a corrected route for non-dangerous mismatches; block only when quoting corruption could change the destructive target or permit injection.

Expected benefit is **likely (55-80%)** for obvious dialect errors and **unlikely (20-45%)** for syntactically valid native-argument corruption, hence the separate conformance fixture.

**Anti-overfit gate:** passes. A compact rule set on the existing PreToolUse bus; do not grow it into a general guardrail framework.

### 4.12 Test Windows behavior on Windows, not only in a Linux container — **CONFIG (settings/JSON only)**

For the harness/toolchain itself, add a small Windows CI lane covering execution-contract fixtures, MCP spawn, path normalization, encoding, timeout cleanup, and file-lock cleanup. Keep Linux CI for WSL/Linux lanes. A Linux container cannot validate `CreateProcessW`, `cmd.exe`, PowerShell Windows mode, PATHEXT, NTFS case mode, or Job Objects; those are documented Windows mechanisms in the sources above.

Expected benefit is **very likely (80-90%)** for preventing regressions in the compatibility layer, though the effect on end-task agent success remains **likely (55-80%)** until measured.

**Anti-overfit gate:** passes. A CI matrix is validation, not runtime scaffolding.

## Recommended adoption order and stop conditions

1. **Immediately, configuration only:** enable/pin native PowerShell for Windows-native Claude work; declare project lane; pin `pwsh`; use explicit MCP launch commands; set command-length budgets.
2. **First small build:** execution envelope + temp-script materializer + argument-echo conformance fixture. These target the quoting and length layers directly.
3. **Second small build:** MCP resolver/health check and filesystem capability probe.
4. **Third small build:** Job Object integration in the existing longrun wrapper.
5. **Then measure:** compare failures per 1,000 commands by executor, failure stage, nested-shell depth, command length, and whether the command used structured argv or a script file.

Stop or roll back a measure if it does not lower its targeted failure class in a controlled A/B or before/after window. Do not retain a wrapper merely because it is architecturally tidy. The minimal-harness principle requires each addition to earn its place through observed error reduction.

## 5. What I could not determine

### 5.1 Comparative agent success rates by Windows executor

I could not determine a credible benchmark comparing the same modern coding agent on native PowerShell, Git Bash, WSL 2, and Linux with identical repositories and tasks. The research found official support statements and issue reproductions, but those do not measure task success. I am not claiming such a benchmark is absent. The settling experiment is a stratified replay of representative owner tasks across the four executors with fixed model/version, measuring command success, retries, wall time, and final acceptance.

### 5.2 The fraction of quote failures attributable to the model versus the launcher

External documentation establishes multiple parser layers but cannot allocate the owner's failures among model syntax generation, JSON serialization, hook rewriting, shell parsing, MSYS conversion, and child parsing. The settling experiment is to log the original tool payload, materialized script or argv vector, final executable, final command-line length, and an argument-echo reconstruction at each boundary for a sampled set of failures.

### 5.3 Current Codex native-Windows sandbox reliability across installations

Official source and issue trackers show an evolving implementation and recent version-specific failures, but this unit did not establish the reliability of the exact currently installed Codex build. I therefore do not conclude that Codex's Windows sandbox is broken or complete. The settling experiment is a pinned-version matrix on clean Windows VMs: sandbox setup, workspace write, outside-workspace denial, environment inheritance, process-tree cleanup, restart recovery, and WSL workspace execution, each with known-allowed and known-denied controls.

### 5.4 Whether Claude's PowerShell preview outperforms Git Bash for this owner

Anthropic's current documentation makes native PowerShell available and identifies preview limitations, but provides no owner-specific error data ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). The recommendation to enable it for Windows-native projects is therefore based on removing a documented translation layer, not on a measured local win. The settling experiment is a two-week routing A/B with comparable tasks and failure fingerprints.

### 5.5 Enterprise policy interactions

I could not determine whether this machine's Group Policy, antivirus/EDR, Controlled Folder Access, AppLocker/WDAC, Developer Mode, or WSL policy affects process launch, scripts, symlinks, or file locking. Anthropic notes that process-scope execution-policy bypass does not override machine/user Group Policy ([Anthropic tools reference](https://code.claude.com/docs/en/tools-reference)). The settling experiment is a read-only capability preflight plus Windows Event Log/EDR correlation for a deliberately blocked harmless script and symlink probe, performed with owner authorization.

### 5.6 Antivirus impact on temporary-script materialization

The temp-script proposal is mechanically grounded, but I did not find evidence quantifying Defender/EDR latency or false positives for this exact workload. The settling experiment is to execute hashed harmless `.ps1`/`.sh` fixtures from the intended session temp directory 1,000 times, measure spawn latency and scan events, and compare with `-Command` strings. If materialization causes material delay, retain it only for complex/long commands.

### 5.7 Safe universal thresholds below Windows ceilings

Windows documents hard ceilings, not a universal safe budget after every wrapper adds quoting and executable prefixes. The proposed 7,500/28,000 warning thresholds are conservative policy margins, not externally verified optima. The settling experiment is to measure the actual final command line produced by each executor and find its failure boundary with inert generated arguments.
