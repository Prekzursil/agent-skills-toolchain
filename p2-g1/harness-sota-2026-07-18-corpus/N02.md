## Executive verdict

The body-level semantic router is not a sketch that needs replacing. It already contains the right small-system primitives: a 360-row local body index (240 skills, 39 MCP servers, 16 agents, 65 commands), asymmetric retrieval embeddings, lexical precision patches, an adaptive similarity threshold, per-kind caps, per-session deduplication, calibrated silence, fail-open behavior, a probe mode, and a nominal outcome store (`bundle/claude/hooks/semantic-router/route.py:1-22,89-109,164-200,248-358,361-419`; `bundle/claude/hooks/semantic-router/index/meta.json:1`). The correct architecture is therefore **extend, repair, and reconnect this router**, not build a second selector.

The live-state audit has two decisive findings:

1. **The router is off the prompt path.** Its own comment says it is registered as the sole `UserPromptSubmit` router (`bundle/claude/hooks/semantic-router/route.py:10-16`), but the live settings snapshot registers only the shared harness dispatcher and `selection-events/emitter.py` for that event (`bundle/claude/settings.json:117-138`). Independently, the local dispatcher manifest has no `UserPromptSubmit` event at all (`bundle/claude/hooks/_dispatch/manifest.json:5-228`). The detector was controlled: the same exact searches found the known-present `selection-events` registration at settings line 132 and the expected-but-missing `semantic-router/observe` entry in the wiring test at `bundle/claude/hooks/_dispatch/test_wiring.py:53-63,99-124`. Thus this is an **almost certain (90-99%)** wiring defect, supported by two mechanically independent registries plus a known-positive control—not an inference from missing telemetry.
2. **The weekly regression signal is false-green.** `bench.py` invokes `eval.py --json` and requires a JSON `hybrid` object (`bundle/claude/hooks/harness-bench/bench.py:55-96,150-184`), while `eval.py` ignores command-line arguments and prints a text table (`bundle/claude/hooks/semantic-router/eval.py:209-242`). A second signal is that the bench silently returns 0 when parsing fails (`bench.py:157-160`), and a third is that its tests inject fake evaluator JSON rather than exercise the real producer (prior audit claim, independently consistent with `bundle/inputs/audit-findings/E01.md:48-53`). The interface defect is **almost certain (90-99%)**, based on producer, consumer, and failure-path code.

The router must ride an existing hook carrier. Every proposal below uses the already registered `selection-events/emitter.py` at `UserPromptSubmit`, `PostToolUse`, and `PostToolUseFailure`; the event ledger; native skill/tool invocation; or offline sync/evaluation. **No seventh hook is added. No hook is added at all.** If implementers prefer the shared harness dispatcher as carrier, the semantic routing function must be folded into its existing `UserPromptSubmit` pass, not registered separately.

## Grounding: what the owner’s history actually says

The corpus is a high-coverage distillation: 11,633 files seen, zero file failures, one bad line across 1,564,084 lines, with samples capped at 12 (`bundle/inputs/corpus.json:2-11`). Its hook section is explicitly unusable and is treated as no data (`bundle/inputs/corpus.json:13260-13264`). I did not infer any hook behavior from it.

Capability use is extremely concentrated. Only 78 skills are observed as explicitly invoked; `deep-research` leads at 70, while a long tail appears once or twice (`bundle/inputs/corpus.json:13265-13344`). Agent routing is more concentrated still: `general-purpose` appears 1,158 times, versus 29 `code-reviewer`, 28 `planner`, 18 `architect`, and 18 `security-reviewer` invocations (`bundle/inputs/corpus.json:13346-13369`). This does not prove that every unobserved capability was useless—native implicit loads may not be recorded—but it is strong evidence that the owner is currently required to name a small familiar subset while specialist discoverability is weak.

The owner also explicitly asks for low-friction companionship: one retained sample asks the agent to “probe live instead of me having to paste you the log” and to be “a companion ... that's easier” (`bundle/inputs/corpus.json:12383`). Another asks the harness to remember to use “all information ... tools, research, mcps, plugins” (`bundle/inputs/corpus.json:10745`), and another challenges under-use of ToolUniverse (`bundle/inputs/corpus.json:10801`). These are direct owner-language signals for automatic capability choice, not speculative preference mining.

The correction detector is recall-biased: it reports 2,268 candidates but says 41/41 in an unfiltered smoke sample were false positives (`bundle/inputs/corpus.json:10371-10375`). I therefore use its repeated “why did you stop” and “do not stop” entries only as corroboration, not as exact owner-correction counts (`bundle/inputs/corpus.json:10425-10427,10569,12359,12413-12419`). The hard requirement to never drop a thread comes from this unit’s owner brief and the existing open-loop implementation, which explicitly describes forgotten-thread recovery (`bundle/claude/hooks/open-loops/resurface.py:2-25`), not from treating all 2,268 candidates as ground truth.

The old router’s `success.json` is not a quality measure. A read-only calculation over that file produced `180 rows; 4,885 suggested; 5 used`; its largest rows are `systematic-debugging 1,038/1`, `parallel-execution-optimizer 787/0`, `benchmark-optimization-loop 787/0`, and `make-interfaces-feel-better 551/0`. More importantly, the code defines “used” only as “suggested in this session, then invoked” (`bundle/claude/hooks/semantic-router/success.py:66-107`; `observe.py:20-64`). It does not observe whether the invocation succeeded, solved the task, preserved the thread, or was corrected by the owner. That proxy must not drive personalization.

## Research principles applied

- Amershi et al.’s human-AI interaction guidelines say to time services from context, show contextually relevant information, make invocation/dismissal/correction efficient, scope service when uncertain, explain why, remember recent interactions, learn from behavior, and adapt cautiously: https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/ (guidelines 3–17).
- The accepted ICLR 2025 Proactive Agent work separates proactive offers from ordinary reactive response and evaluates accepted versus rejected interventions over 6,790 events: https://proceedings.iclr.cc/paper_files/paper/2025/hash/75c37811e830bf029584b1c6fac17726-Abstract-Conference.html. Its trained reward model is **not** adopted here because a trained critic/reward model violates the anti-overfit gate; the useful lesson is the accepted/rejected intervention outcome.
- ProMemAssist reports that badly timed proactive interventions can harm ongoing task execution and frames timing as benefit versus disruption: https://kevinpjk.github.io/assets/pdf/promemassist_uist_2025.pdf (pp. 1–2). The wearable setting is not identical to coding; the transfer is the timing objective, not its cognitive model.
- ToolRet contains 7,600 retrieval tasks and 43,000 tools; strong generic retrievers still perform poorly, and retrieval errors reduce downstream task pass rate: https://aclanthology.org/2025.findings-acl.1258/. This supports end-to-end route evaluation, not importing a trained retriever.
- A CHI 2025 preregistered experiment (N=308) found that explanations increased reliance on both correct and incorrect LLM answers, while sources and visible inconsistencies reduced reliance on incorrect answers: https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies/. Therefore “show more rationale” is not automatically a trust fix.
- Microsoft’s appropriate-reliance synthesis defines the target as accepting correct outputs and rejecting incorrect ones, and warns that both over- and under-reliance hurt human+AI performance: https://www.microsoft.com/en-us/research/publication/appropriate-reliance-on-generative-ai-research-synthesis/.

## Findings — inferred-surprise items first

### Finding 1 — Route *whether and how to intervene*, not only *which capability* (inferred-surprise)

**Improvement.** Add an intervention policy to the existing router: `silent-execute`, `silent-context`, `one-line-nudge`, `ask-one-choice`, or `abstain`. Relevance score and interruption policy are separate outputs.

**What it is.** The present router calculates semantic relevance and then emits up to six suggestions whenever content and threshold gates pass (`route.py:89-105,164-200,305-345,361-402`). That conflates “this capability is related” with “interrupt the current task with this routing information.” The replacement decision object is small and typed:

```json
{"primary":"skill:ui-audit","alternate":"skill:design-studio","mode":"silent-context",
 "confidence_band":"likely","basis":["semantic","project-card"],"thread_ids":[17]}
```

The object stays internal unless the route is ambiguous and consequential. High-margin, reversible choices are injected as a direct instruction to invoke the primary capability. Low-margin but reversible choices provide one primary and one alternate without asking the owner. Only low-margin choices that change scope, spend money, contact a person, or mutate external state call the already-native `AskUserQuestion` path.

**Why inferred.** The owner asks to avoid remembering names and explicitly wants the agent to probe live rather than asking them to transport logs (`corpus.json:12383`). The present “skills: A, B, C, D | MCP: ...” list transfers selection work back to the owner/model and can increase prompt fatigue. The hard prompt-fatigue constraint means correctness must include interruption cost.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `assemble()` to return top-1/top-2 margin, evidence lanes, and action-risk metadata. Replace the multi-item prose renderer with the five-mode policy. Reuse `calibrated-silence` already called at `route.py:44-68,384-402`; do not add a timing hook or cognitive-load model. Put thresholds in the existing router environment/config. Fail-open means a policy error returns the current prompt untouched and exit 0.

**External signal that verifies it.** A frozen replay set is evaluated in a fresh process/context. Metrics are route success, unnecessary-intervention rate, owner-question count, and end-to-end task pass—not the router’s own explanation. A canary compares 50 matched real prompts under old renderer versus intervention policy, with owner dismissals/redirects and real execution receipts as outcomes.

**SOTA citation.** Amershi guidelines 3, 8, and 10: https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/; ProMemAssist timing tradeoff: https://kevinpjk.github.io/assets/pdf/promemassist_uist_2025.pdf.

**Value x effort.** transformative x medium. **Novelty.** inferred-surprise. **Autonomy.** just-do-it for shadow/replay; confirm-first before changing the live ask threshold. **Confidence.** **very likely (80-90%)** to reduce irrelevant routing prose because current output can list six candidates and the proposed test directly measures intervention/dismissal; impact on total session focus is **likely (55-80%)**, because the local canary has not yet run.

### Finding 2 — Replace “invoked after suggestion” with an execution-grounded route-outcome join (inferred-surprise)

**Improvement.** Make routing learn from external results, not from the model accepting its own suggestion.

**What it is.** Join a prompt-time `route_decision` event to the existing `selection.v1` event. The latter already correlates genuine user text to an exact `tool_use_id`, writes chosen tool and `success`, redacts secrets, bounds storage, and records PostToolUse versus PostToolUseFailure (`bundle/claude/hooks/selection-events/emitter.py:2-29,541-606,609-645`). A route is positive only when a distinct execution signal succeeds; stronger credit requires a subsequent milestone/test receipt or no owner redirect before closure. Invocation alone is neutral. Tool failure, replacement within the same intent, owner correction, or abandoned thread is negative/unknown according to an explicit table.

**Why inferred.** The current outcome store has only five invocation credits after 4,885 suggestions and no task-success field. The owner’s history contains a dead Tavily surface still called hundreds of times, while capability use shows many competing provider aliases (`corpus.json:13265-13344` and the pinned measured truth). A selection learner that rewards invocation can reinforce a dead or merely familiar route.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** At `UserPromptSubmit`, append a bounded `route_decision.v1` record to the existing event ledger, keyed by query hash/session hash and candidate IDs. Extend the current OATS/selection consumer to join the next selected tool and success/failure. Store only counts by `(intent-cluster, capability-id, inventory-hash)`: success, failure, corrected, unknown. Use conservative Beta-smoothed nudges capped below semantic score; never train a critic. Retire `semantic-router/observe.py` and `success.json` from authority rather than run two learning loops.

**External signal that verifies it.** Replay ledger joins must reproduce known successful and failed tool calls; a separate test process injects a known failed MCP call and proves its route weight cannot increase. Promotion requires better held-out end-to-end pass rate with no increase in owner redirects. Actual command/test/tool results—not same-context model judgment—close every label.

**SOTA citation.** Proactive Agent’s accepted/rejected event framing: https://proceedings.iclr.cc/paper_files/paper/2025/hash/75c37811e830bf029584b1c6fac17726-Abstract-Conference.html; cautious behavioral learning is guideline 13–15: https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/.

**Value x effort.** transformative x medium. **Novelty.** inferred-surprise. **Autonomy.** just-do-it in shadow, confirm-first for learned-weight promotion. **Confidence.** **almost certain (90-99%)** that this produces a more valid label than invocation because PostToolUseFailure is mechanically distinct and already recorded; whether the sparse local outcome volume is sufficient to improve ranking is **roughly even (45-55%)**, settled by the held-out replay.

### Finding 3 — Make open threads hard routing constraints, not extra reminder prose (inferred-surprise)

**Improvement.** Route the terse prompt together with unresolved obligations, so “continue,” “fix that,” or “do the rest” selects capabilities consistent with the standing goal and never drops a discussed item.

**What it is.** Before embedding, form a bounded query capsule from the prompt plus project identity, current goal, up to two open failures, and matching prospective-memory triggers. The event ledger already stores a standing goal and open failures (`bundle/claude/hooks/event-ledger/ledger.py:61-65,119-130`); open-loops already derives and bounds these (`bundle/claude/hooks/open-loops/_common.py:465-494`) and surfaces at most three on session start (`resurface.py:38-95`). The router should consume those same projections as constraints and attach their sequence IDs to the route decision. It must not create another memory store or repeat the full reminder to the owner.

**Why inferred.** The owner explicitly imposes “never drop a thread.” Corpus samples repeatedly refer to persistent loop state and ask why execution stopped (`corpus.json:10413-10427,12269-12365`), but the correction detector’s warning prevents treating their count as exact. The local system already recognized the need; the missing step is to make thread state affect selection rather than sit beside it as prose.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Import only the read-only ledger state projection. Add at most 500 bounded characters of goal/failure labels to the embedding query, while the raw user prompt retains greater weight. Add `thread_ids` and `thread_coverage` to `route_decision.v1`. If ledger read fails, route on the raw prompt and exit 0. Do not scrape transcripts or query basic-memory on every turn.

**External signal that verifies it.** Create paired fresh-process cases: identical “continue/fix that” prompt with two different ledger states must route to different expected capabilities; a known closed/superseded failure must not affect the result. End-to-end thread coverage is verified by ledger milestone/supersession IDs, not by the model saying it remembered.

**SOTA citation.** Remember recent interactions and time from context: https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/ (12 and 3).

**Value x effort.** transformative x low. **Novelty.** inferred-surprise. **Autonomy.** just-do-it. **Confidence.** **very likely (80-90%)** to improve pronoun/continuation routing because the same prompt is otherwise underdetermined and the required state is already typed; the exact capsule weighting is **UNVERIFIED—run the paired ledger-state experiment above to settle it**, so tuning remains shadow-only until green.

### Finding 4 — Add live availability, replacement, and contraindication before semantic rank (inferred-surprise)

**Improvement.** Never recommend a semantically ideal capability that is dead, retired, wrong for the provider, or superseded; route to the live replacement or degrade honestly.

**What it is.** The current index is positive-only and static. MCP rows are built from `.mcp.json` server names plus hand-written hints (`bundle/claude/hooks/semantic-router/build_index.py:196-225`), and the capability catalog still names direct Tavily/Exa routes and tells the model to start absent daemons (`bundle/claude/hooks/capability-catalog/catalog.json:19-23`). Introduce simple metadata—not a graph database—on each candidate: `providers`, `availability_probe`, `replaces`, `requires`, `not_for`, `side_effect`, and `risk`. A pre-rank filter consumes the already-built B1 MCP-liveness state and current native capability inventory. A dead `claude_ai_Tavily` candidate maps to a live search-hub/Tavily replacement only if that replacement passes a real probe.

**Why inferred.** The pinned corpus truth records 135 “not connected” errors for the dead Tavily MCP, while the capability corpus shows many aliases for Tavily, Exa, and local bridges (`corpus.json:13265-13344`). Discoverability without invocability is worse than silence because it consumes the shortlist and causes retries.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing catalog/index metadata and filter candidates before success boosts. Read B1 liveness/cache output; never start a daemon inside the prompt hook. For skills/agents/commands, validate the invocation ID against the provider’s current enumerated catalog hash. On missing/unknown liveness, keep the candidate only as `unverified` and do not auto-execute it. Fold this into the existing router; no liveness hook is added.

**External signal that verifies it.** A real `tools/list` plus minimum data probe is the availability signal. Test fixtures include one known-live tool and one intentionally unreachable tool; the detector must find the known-live control before exclusion is accepted. PostToolUseFailure verifies fallback behavior. Two signals—inventory presence and data probe—are required before “live” or “absent” is claimed.

**SOTA citation.** ToolRet shows retrieval quality affects task pass rate: https://aclanthology.org/2025.findings-acl.1258/; HAX guideline 2 requires communicating how well a system can do what it claims: https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/.

**Value x effort.** transformative x medium. **Novelty.** inferred-surprise. **Autonomy.** just-do-it for filtering confirmed-dead candidates; confirm-first before auto-starting any backend (this proposal does not auto-start). **Confidence.** **almost certain (90-99%)** to prevent the recorded dead-Tavily class when both probes fail, because exclusion precedes rank; replacement accuracy is **likely (55-80%)**, settled by the live two-probe fixture and end-to-end call.

### Finding 8 — UNVERIFIED: Split the routing surface: semantic router for capabilities; native deferred search for tool schemas (user-asked)

**Improvement.** Keep one semantic chooser for skill/command/agent intent and server-level capability families, while delegating individual MCP tool-schema search to the provider-native deferred search already enabled.

**What it is.** Claude settings already enable `ENABLE_TOOL_SEARCH=auto:5` (`bundle/claude/settings.json:4-20`). The semantic router currently ranks MCP servers alongside skills (`route.py:273-345`). Use it to choose a live server/family only when that adds information; let native Tool Search retrieve the concrete tool schema. Do not emit four skills plus three MCPs. This is progressive disclosure, not removal of the existing router.

**Why inferred.** The corpus spans 93 MCP servers and 400 recorded MCP tool names, with multiple provider aliases (`bundle/inputs/corpus.json:13265-13867`). Loading or hand-routing every concrete tool duplicates native discovery and increases overlap. The owner wants not to remember names, not to see a bigger catalog.

**How to build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Preserve the already-enabled native deferred-search setting, and limit semantic MCP output to one live family/server. Add server summaries and `when_not` boundaries to the existing catalog. The semantic router never becomes an MCP executor.

**External signal that verifies it.** On a held-out suite requiring one or multiple tools, record native search candidates and final calls. Require completeness@5/10, final-call accuracy, task pass, prompt tokens, and latency to be non-inferior to full semantic MCP suggestions. ## Alternatives considered and rejected

- **Replace with a new LLM router or trained reward model:** rejected. It violates the trained-critic/second-runtime anti-overfit gate, adds latency, and still requires the same outcome/evaluation work. The ICLR reward model is research evidence for accepted/rejected interventions, not an architecture to import.
- **Let the model check whether its own route was good:** rejected by the unit law. Same-context self-certification is not an outcome.
- **Reconnect `semantic-router/observe.py` as-is:** rejected. It credits invocation rather than success and duplicates the richer selection ledger.
- **Add a seventh/new hook:** rejected. The existing selection emitter already owns the required three lifecycle events.
- **Put every skill/tool body into the prompt:** rejected. It worsens prompt fatigue and ignores native deferred discovery.
- **Use raw corpus correction candidates as personalization labels:** rejected. The corpus itself reports 41/41 false positives in its smoke sample (`corpus.json:10371-10375`).
- **Build vector/KG memory for aliases and threads:** rejected. Typed ledger projections and the current flat index already carry the necessary bounded state.
- **Prune the router in favor of native tool search alone:** rejected for this unit. Native MCP Tool Search does not cover the full local skill/agent/command semantics requested here, and the owner explicitly requires extending the body-level router rather than rebuilding or discarding it.
