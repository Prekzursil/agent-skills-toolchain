# A143 — coherence audit: `~/.claude/settings.json` internal duplicate authority

## Executive result

I found **two genuine internal duplicate-authority pairs** in the supplied user settings snapshot:

1. the bare allow rule `WebFetch` subsumes both domain-specific WebFetch allow rules; and
2. the deny rule `Read(**/.env)` subsumes the narrower current-directory rule `Read(./.env)`.

Both are same-outcome duplicates rather than contradictory policies. Each duplicate can drift independently: deleting or changing only the narrower rule does not change the effective runtime decision because the broader rule still matches. The minimal resolution is therefore deletion of the narrower duplicate, not a new mechanism.

I found **no duplicate JSON keys, no exact duplicate permission-array elements, no duplicate plugin IDs, no same plugin name declared from two marketplaces, and no exact hook command repeated within one event**. Those absence statements have two mechanically independent, known-positive-controlled detectors described below.

The two edits proposed here are **almost certain (90-99%)** to preserve current and alternate-mode permission outcomes, because the current official Claude Code contract explicitly defines the relevant bare-tool, WebFetch-domain, `Read`/gitignore, and permission-mode semantics. A live replay with the owner's installed Windows binary is **UNVERIFIED**; the settling experiment is specified in “Runtime-verification boundary.”

## Method and detector controls

### Structural pass

A JSON parser using `object_pairs_hook` examined every object before conversion to a dictionary, so overwritten duplicate keys could not disappear silently. Before use, the detector was run on the known-positive control `{"known":1,"known":2}` and returned `['known']`. It returned `[]` for the subject. Standard JSON parsing independently succeeded and produced 29 top-level keys.

### Independent lexical pass

A line-oriented extraction over the complete `enabledPlugins` block (`settings.json:539-637`) and the complete permission allow block (`settings.json:28-62`) was sorted and passed through `uniq -d`. Its known-positive controls each returned the duplicated token (`known@market` and `KnownRule`); the subject blocks returned no duplicate. This is mechanically independent of JSON object construction: it operates on source lines and Unix sort/duplicate detection.

### Semantic containment pass

For permission entries, a structural containment check paired every scoped rule with a bare allow of the same tool. It reported exactly:

```text
WebFetch SUBSUMES WebFetch(domain:code.claude.com)
WebFetch SUBSUMES WebFetch(domain:docs.anthropic.com)
```

It separately reported the four broad-allow/narrow-deny overlaps for `Read`; these were then evaluated using Claude Code's documented deny-before-ask-before-allow runtime order rather than mislabeled as duplicates.

For hooks, the pass compared command strings within each event. It found no command repeated within the same event. The only command reused across events was `selection-events/emitter.py`, once at `UserPromptSubmit` and once at `PostToolUseFailure`; direct source inspection proves these are separate branches with separate behavior (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:4-10` and `:627-638`), so this is not duplicate authority.

### Normative runtime sources

Runtime precedence was checked against current first-party documentation retrieved on 2026-07-19:

* [Configure permissions](https://code.claude.com/docs/en/permissions), especially “Manage permissions,” “Match all uses of a tool,” “Read and Edit,” and “WebFetch.” The retrieved Markdown states that deny is evaluated before ask before allow; a bare `WebFetch` matches all WebFetch requests; `Read` rules follow gitignore semantics; `Read(.env)` and `Read(**/.env)` are equivalent for any `.env` at or below the current directory; and a bare WebFetch rule is the all-domain equivalent.
* [Choose a permission mode](https://code.claude.com/docs/en/permission-modes), especially lines 26-28 of the retrieved Markdown. It states that deny and explicit ask rules apply even in bypass mode, while allow rules have no effect in bypass mode because other calls are already approved.
* [Settings](https://code.claude.com/docs/en/settings), especially “Permission settings” and “Plugin configuration.” It documents `defaultMode`, distinguishes `skipDangerousModePermissionPrompt` from the mode itself, and defines `enabledPlugins` as one Boolean enablement value per `plugin@marketplace` identity.

These sources verify the evaluator's rule, mode, and identity semantics rather than inferring them from key names.

## Finding 1 — duplicate WebFetch allow authority

**Severity:** low coherence defect; current behavior is permissive under either copy.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

### Both authorities, verbatim

Broad authority:

> `"WebFetch",`

— `C:\Users\Prekzursil\.claude\settings.json:38` (bundle: `/local_disk0/codexwork/bundle/claude/settings.json:38`)

Narrow authorities:

> `"WebFetch(domain:code.claude.com)",`
>
> `"WebFetch(domain:docs.anthropic.com)"`

— `C:\Users\Prekzursil\.claude\settings.json:61-62` (bundle: `/local_disk0/codexwork/bundle/claude/settings.json:61-62`)

### Concrete collision

For a fetch to `https://code.claude.com/...`, both line 38 and line 61 match. For a fetch to `https://docs.anthropic.com/...`, both line 38 and line 62 match. If an operator later removes the domain-specific entry intending to revoke that domain, line 38 continues to allow it in any mode that evaluates allow rules. Conversely, if the operator keeps the narrow entries but removes the broad rule, all other domains stop being pre-approved. The two representations therefore expose one policy surface through independently editable broad and narrow declarations.

This is not a merely hypothetical overlap: those two named-domain requests satisfy both predicates under the official matching contract. It is also not a deny/allow exception; all three rules live in the same `allow` array.

### Runtime winner

There are two runtime contexts, both deterministic:

1. **Current default startup context.** `"defaultMode": "bypassPermissions"` at `settings.json:71` establishes bypass mode. In that mode, the mode baseline is the effective winner: current official documentation says allow rules have no effect because calls are already approved. A matching deny or explicit ask would still take precedence, but this settings file has no WebFetch deny and its ask array is empty (`settings.json:64-70`).
2. **Any active mode in which allow rules matter.** The bare rule at line 38 is the effective surviving authority. Official documentation defines a bare tool rule as matching every use and specifically defines bare `WebFetch` as all fetch requests. The two domain rules cannot narrow a simultaneous broad allow; removing either domain rule alone changes nothing.

There is no meaningful “first array element wins” dispute here because all matching entries return the same `allow` outcome. The broad rule wins in the operational sense required by this audit: it alone preserves the outcome after either narrow rule is removed.

### Minimal edit

Delete only lines 61-62:

```json
"WebFetch(domain:code.claude.com)",
"WebFetch(domain:docs.anthropic.com)"
```

Keep the bare `"WebFetch"` rule if the intended policy is unrestricted WebFetch. This is **almost certain (90-99%)** to preserve the runtime decision in every permission mode, based on the official bare-tool and domain matching rules plus the explicit statement that allow rules are inert in bypass mode. It reduces three independently editable declarations to one.

If the intended policy is actually “only these two documentation domains,” the correct edit is instead to remove line 38 and keep lines 61-62. That intent is **UNVERIFIED**; the settling experiment is an owner policy choice, not a technical probe: answer whether arbitrary WebFetch domains are intentionally pre-approved. I do not recommend silently choosing that stricter policy in a coherence-only unit.

## Finding 2 — duplicate `.env` deny authority

**Severity:** low coherence defect; current behavior is deny under either copy.

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

### Both authorities, verbatim

Narrow authority:

> `"Read(./.env)",`

— `C:\Users\Prekzursil\.claude\settings.json:65` (bundle: `/local_disk0/codexwork/bundle/claude/settings.json:65`)

Broader authority:

> `"Read(**/.env)",`

— `C:\Users\Prekzursil\.claude\settings.json:66` (bundle: `/local_disk0/codexwork/bundle/claude/settings.json:66`)

### Concrete collision

For `Read(<current-working-directory>/.env)`, both deny patterns match. The first is explicitly current-directory-relative; the second matches `.env` at the current directory and at every descendant depth. If line 65 is deleted or changed, line 66 still denies the current-directory file. If line 66 is deleted, line 65 preserves only the root case and silently loses descendant coverage. Thus one protected path is governed twice and only the broader declaration captures the complete apparent policy.

The current official Read/Edit documentation directly settles the wildcard point: relative `path` and `./path` rules anchor at the current directory, and `Read(.env)` / `Read(**/.env)` are equivalent for `.env` at any depth under that anchor. Therefore `Read(./.env)` is a strict subset of `Read(**/.env)`.

### Runtime winner

For a current-directory `.env`, the deny category wins over the broad `"Read"` allow at `settings.json:30`, because runtime evaluation is deny, then ask, then allow, with specificity unable to reverse that order. Denies also remain active in `bypassPermissions` mode.

Between lines 65 and 66, both return the same deny outcome, so array order does not create a different result. Line 66 is the effective surviving authority because it continues to block the same root `.env` if line 65 disappears and additionally blocks descendant `.env` files.

### Minimal edit

Delete only line 65:

```json
"Read(./.env)",
```

Keep `"Read(**/.env)"`. This is **almost certain (90-99%)** to preserve all existing deny decisions while eliminating the independently editable subset, based on the official anchor and `**/.env` semantics and the deny-first runtime order.

This edit does **not** broaden the rule to parent directories, other projects, or all drives. Official documentation says the relative `**/.env` rule covers only the current-directory anchor and descendants; on Windows, all-drive coverage would require `Read(//**/.env)`. Whether broader coverage is desired is outside this internal-duplication unit and is **UNVERIFIED**; the settling experiment is a separate credential-policy review of intended filesystem scope.
