**Unit:** E007  
**Scope:** What consumes time and context in the first 30 seconds of a Claude Code or Codex session: hooks, continuity/memory replay, skill discovery, and MCP connection.  
**Run date:** 2026-07-19  
**Subject policy:** read-only. This unit wrote only this artifact.  

## Executive verdict

The honest answer is not a single startup-latency number. The supplied distillation cannot measure one: all 533 `tool_usage` rows have `p50_ms=0` and `p95_ms=0`, its 4,000 `sessions` rows retain only file-level first/last timestamps, the corpus hook detector is explicitly broken, and the Linux bundle contains no raw `.jsonl` transcripts. The exact Windows first-prompt latency, per-hook elapsed time, live MCP connect timeline, and model-visible prompt bytes are therefore **UNVERIFIED; the experiment that settles them is the cold/warm startup benchmark in Recommendation 1**. Treating configured timeouts or whole-session duration as observed startup time would manufacture precision.

What is measurable establishes four strong findings:

1. **Startup is doing real executable work before the first prompt.** Claude has three matching `SessionStart` command groups with 5 s, 20 s, and 5 s timeout ceilings (`bundle/claude/settings.json:82-115`). Claude’s official lifecycle says matching hooks run in parallel, so the registered ceilings are not additive; the **likely (55-80%)** configured outer blocking envelope is approximately 20 seconds, not 30 seconds, because the three groups can overlap, but actual host scheduling on this Windows installation is **UNVERIFIED; `claude --debug hooks,mcp` with process timestamps settles it**. The local 20-second group serially imports six Python modules and then runs six checks in threads (`bundle/claude/hooks/_dispatch/dispatch.py:242-283`; manifest `:6-70`). This is startup computation, not evidence that 20 seconds is routinely consumed.

2. **Fresh-start semantic-memory replay is not the principal shared-harness tax.** The shared ledger deliberately injects nothing on a new session; it replays only on `resume|compact|clear`, reads at most 20 ledger entries, retains at most 12 decision/failure/milestone rows, and caps the injected block at 4,000 characters (`bundle/agents/harness/modules.py:964-1003`). Basic Memory is also declared pull-only rather than auto-loaded (`bundle/claude/CLAUDE.md:5-11`). However, Claude’s second, local dispatcher independently scans background work, memory spools, heartbeat state, project-global open loops, and a background digest on every `SessionStart` (`bundle/claude/hooks/_dispatch/manifest.json:6-70`). Thus “memory replay” is small and source-gated in the shared bus but broader and partly duplicative in the Claude-only bus.

3. **The recurring context tax is large before task text.** Static text eligible for global Claude loading is 8,121 characters of `CLAUDE.md`, its 8,624-character imported `AGENTS.md`, and 19,949 characters across five unscoped rules: 36,694 characters, approximately 9,174 tokens using the explicit chars/4 estimate. The configured skill-list reservation adds up to 2% of the 1M model window, nominally as much as 20,000 tokens (`bundle/claude/settings.json:3,77`; official settings documentation below). The exact model-visible total is **UNVERIFIED; a fresh `/context` plus `/doctor` capture settles imports, deduplication, plugin/bundled skills, and tokenizer cost**. An earlier audit claim measured Claude skill/command descriptions at roughly 11.6k-12.5k estimated tokens and Codex’s rendered skill catalog at roughly 5.6k tokens (`bundle/inputs/audit-findings/A24.md:3-83`); those are useful hypotheses, not reclassified as facts here because their cited raw prompt traces are absent from the bundle.

4. **MCP tool-search saves schemas, not processes.** Claude has `ENABLE_TOOL_SEARCH="auto:5"` and a 120-second MCP startup timeout (`bundle/claude/settings.json:12,17`). Official Claude documentation says `auto:5` loads schemas up front when they fit within 5% of context and defers only overflow; it also says enabled plugin MCP servers connect automatically at session startup. Therefore, **almost certain (90-99%)**, supported by the configuration plus official semantics, `auto:5` does not provide lazy process spawning and can still spend first-30-second CPU/RAM on connections. The corpus records 14,809 MCP calls, 1,211 errors (8.18%), 93 MCP server names used, and 489 distinct MCP tool names; non-MCP tools were 5.11% error over 284,915 calls. Startup ordering of those failures is **UNVERIFIED; raw ordered transcripts or native MCP debug logs settle whether failures cluster in the first 30 seconds**.

The best target is not a new orchestration runtime. It is a **measured, source-gated startup cockpit on the existing hook bus; true all-deferred tool search; a small task-profile MCP set; and corpus-driven skill visibility**. Every proposal below rides an existing bus and avoids a second runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 2. What is on the first-30-second path

### 2.1 Claude startup hooks

The live-copy settings in the bundle register three `SessionStart` groups, all matching `.*`:

| Group | Outer timeout | Synchronous work visible in bundle | Potential startup context |
|---|---:|---|---|
| Shared harness dispatcher | 5 s | Constructs ten default modules and invokes them sequentially (`bundle/agents/harness/modules.py:2599-2613`; `bundle/agents/harness/dispatcher.py:267-312`) | Fresh-session sibling hazard; recovery-only ledger replay |
| Claude-local dispatcher | 20 s | Serial import of six modules, then thread-per-check execution (`bundle/claude/hooks/_dispatch/dispatch.py:242-283`) | Orphans, unflushed memory, heartbeat, open loops, background digest |
| Local TUI reminder | 5 s | Date marker scan/write (`bundle/claude/hooks/local-tui-reminder/check.py:31-64`) | One 266-character daily reminder |

Official Claude docs say all matching hooks for an event run in parallel and identical commands are deduplicated. They also say `SessionStart` runs on every new/resumed session, stdout becomes model context before the first prompt, and such hooks should be fast: [Hooks guide](https://code.claude.com/docs/en/hooks-guide), [Hooks reference](https://code.claude.com/docs/en/hooks).

Inside the Claude-local dispatcher, six checks start concurrently only **after** serial import. Its join loop uses a common start time and absolute per-check budgets (`bundle/claude/hooks/_dispatch/dispatch.py:267-277`), so check execution is intended to stay near the largest relevant deadline rather than sum all six. Imports have no inner timeout, although the outer 20-second host timeout applies. The first check has a 10-second budget and the others have 6-8 seconds (`bundle/claude/hooks/_dispatch/manifest.json:10-68`).

The checks are not all cheap no-ops:

- `open-loops` runs `git rev-parse` with a 4-second timeout and can read the last 2,000 transcript lines when a transcript path exists (`bundle/claude/hooks/open-loops/_common.py:324-368`). It caps user triggers at three and ledger-derived output at two failure summaries plus one goal (`resurface.py:39,69-95`; `_common.py:468-494`).
- `bg-registry` scans every `*.ndjson` registry file and folds its records, with no explicit file/record cap (`bundle/claude/hooks/bg-registry/reconcile.py:48-74`). Its emitted orphan list is also uncapped (`:77-92`).
- `memory-spool/replay --spawn` checks whether work exists and detaches the slow Basic Memory CLI path; its comment says the CLI is approximately six seconds per write and deliberately keeps that cost off the critical path (`bundle/claude/hooks/memory-spool/replay.py:43-45,83-107,136-177`). This is a good existing pattern.
- `background-digest` can surface up to 12 lines, archives with `flush` and `fsync`, then rewrites the queue (`bundle/claude/hooks/background-digest/reader.py:67-68,138-180,205-220`). The number of lines is bounded but individual line length is not.

The shared dispatcher records one aggregate `elapsed_ms` per event in `terminal.jsonl` (`bundle/agents/harness/dispatcher.py:483-515`). This is useful existing instrumentation, but it does not break elapsed time down by module and no live `terminal.jsonl` was bundled. The Claude-local dispatcher records no per-check elapsed receipts in the inspected implementation.

### 2.2 Startup context injected by hooks

The shared dispatcher redacts each injected context to 4,000 characters (`bundle/agents/harness/dispatcher.py:281-285`). It has a deterministic 6,000-character total mixer, but the mixer defaults to shadow and returns uncapped raw contexts until explicitly enforced (`:342-372`; cap definition `:59-60`). Therefore the 6,000-character value is not a live hard cap.

The Claude-local dispatcher concatenates every emitted `additionalContext` with newlines and applies no total-character cap (`bundle/claude/hooks/_dispatch/dispatch.py:267-283`). This matters because `bg-registry` emits every orphan and the digest bounds only line count. The **likely (55-80%)** consequence is occasional startup-context spikes when state backlogs accumulate, supported by the unbounded formatters and startup wiring; prevalence is **UNVERIFIED, and logging `input_count/output_chars` per check for 30 days settles it**.

Fresh shared-ledger behavior is clean: it injects no old project history on `startup`; recovery-only replay is same-session scoped and bounded (`bundle/agents/harness/modules.py:973-1003`). The local `open-loops` path deliberately does the opposite on a fresh start: it adds project-ledger failures and a standing goal (`bundle/claude/hooks/open-loops/resurface.py:83-95`; `_common.py:468-494`). This is a verified cross-bus policy asymmetry. Whether it has ever caused an incorrect first-turn goal is **UNVERIFIED; correlate injected goal hashes with current session IDs and owner corrections to settle it**.

Build one bounded Windows benchmark/receipt script, not a daemon. It should launch 30 cold and 30 warm disposable Claude sessions plus equivalent Codex sessions, with no project mutation, and emit one JSON record per run:

Acceptance gates:

**Confidence:** **very likely (80-90%)** this will locate the dominant startup lane because it measures host, hook, context, and OS process planes independently; evidence is the existing aggregate timer, official debug surfaces, and the current absence of ordered telemetry. **Anti-overfit gate:** passes. It is a finite benchmark and a few receipt fields on existing hooks, not an always-on service or new orchestration layer.

### Recommendation 5 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): collapse Claude startup to one synchronous cockpit and async maintenance

Port or retire the second dispatcher’s checks behind the provider-neutral shared dispatcher, then leave exactly one synchronous `SessionStart` command per provider. Before deletion, build a parity table for all six current startup checks.

Synchronous, source-gated cockpit:

- on `startup`: only sibling-session hazard and genuinely current, bounded critical alerts;
- on `resume|compact|clear`: same-session goal + bounded decisions/failures/milestones;
- hard total: 4,000 startup characters, with item caps and per-item truncation;
- never replay a project-global standing goal into a fresh session without session ownership.

Async or deferred maintenance:

- heartbeat/state writes;
- memory-spool replay (already detached—retain this pattern);
- digest archival/truncation;
- garbage collection and registry reconciliation that does not need to steer the first response.

Claude natively supports `async: true` for command hooks, immediately continues, and delivers eventual context on a later turn; async hooks cannot block or control the triggering action ([Hooks reference](https://code.claude.com/docs/en/hooks)). Use it only for side effects or later-turn notices. Critical recovery context must remain synchronous.

**Confidence:** **very likely (80-90%)** one dispatcher reduces Python process/import duplication and makes startup context enforceably bounded because the current two buses and uncapped local concatenation are directly visible (`bundle/claude/settings.json:82-115`; local dispatcher `:242-283`). The exact latency reduction is **UNVERIFIED; the hook-on/off and pre/post A/B benchmark settles it**.

**Anti-overfit gate:** passes. This removes a composition bus and consolidates on the existing shared lifecycle bus.

## 6. Alternatives rejected

### A second startup supervisor/daemon — rejected

It would be BUILD-LARGE, violate the anti-overfit gate, and duplicate lifecycle authority. The current hook bus already exposes startup, async execution, context injection, and elapsed receipts. The missing component is measurement and consolidation, not another runtime.

### Vector/knowledge-graph startup memory — rejected

The shared ledger already gives bounded objective continuity and Basic Memory already owns semantic recall. Adding a new index would not measure startup and would add another connection/storage plane. No recall@k evidence in this unit justifies it.

### Increase skill-list budget — rejected

At 2% of a 1M window, the nominal reservation is already large. Corpus use is sparse relative to installed supply. Increasing the budget spends more recurring context while leaving overlap and dead descriptions intact.

### Treat tool search as lazy MCP startup — rejected

Official docs explicitly separate schema deferral from enabled plugin MCP automatic startup. Tool search is valuable for context, but it is not a process/RAM solution.

### Delete all orphaned plugin directories to improve startup — out of scope and unsafe

The pinned ground truth says one orphan-marked directory was being read by a live skill and 110/169 plugins lacked a live sibling. This unit proposes no deletion. A content-addressed reachability/lease analysis belongs to the plugin-cleanup unit, not startup ergonomics.
