# A142 — coherence audit: `~/.claude/settings.json` internal stale references

## Executive result

This unit found **two runtime-relevant stale-reference conflicts** in the single supplied settings document:

1. The two `PreToolUse` dispatcher matchers still name the former subagent tool as `Task`, while the current runtime emits the tool name `Agent`. The current corpus contains 1,745 `Agent` calls and no `Task` row. Consequently those two matcher branches do not run for current subagent launches. Severity: **degrading**.
2. The permission allow list still names `TodoWrite`, while current interactive Claude Code supplies `TaskCreate`, `TaskUpdate`, `TaskGet`, and `TaskList` instead. The corpus contains one `TodoWrite` attempt and it failed, versus thousands of successful structured-task calls. The permission rule is inert in the configured `bypassPermissions` default mode, but it is misleading dead configuration. Severity: **cosmetic configuration drift with one observed failed use**, not a demonstrated cause of that failed use.

The findings are deliberately narrow. `MultiEdit`, `apply_patch`, disabled-plugin entries, and the two ECC environment variables look old or disconnected, but no concrete runtime collision was established for them. Per the unit contract, they are recorded as non-findings rather than promoted to defects.

The task text names the same source on both sides: **settings (`~/.claude/settings.json`) versus settings (`~/.claude/settings.json`)**. There is no second settings file in the unpacked subject. I therefore treated the assignment as an *internal* coherence comparison: references in permissions and hook matchers versus the capabilities/tool names that the same configuration activates or expects. I used the corpus and current official runtime documentation to settle which name wins at runtime. I did not silently substitute `~/.claude.json`, `.mcp.json`, Codex config, the local-dispatch manifest, or an earlier audit for the missing second side.

## Finding 1 — `Task` hook matchers are stale against current `Agent` calls

**Severity: degrading.**

### Both sides, verbatim

Settings side A, the shared dispatcher:

> `"matcher": "Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit|apply_patch|Task|WebFetch|mcp__.*",`

— `/local_disk0/codexwork/bundle/claude/settings.json:141`

Settings side A again, the local dispatcher:

> `"matcher": "Task|Bash|PowerShell|Edit|Write|MultiEdit|mcp__basic-memory__.*|mcp__schrodinger__glide_dock|mcp__schrodinger__prime_mmgbsa|mcp__cheatengine__.*|mcp__frida-mcp__.*",`

— `/local_disk0/codexwork/bundle/claude/settings.json:251`

Runtime/provider side B, distilled from the complete transcript corpus:

> `"tool": "Agent",`
>
> `"calls": 1745,`
>
> `"errors": 20,`

— `/local_disk0/codexwork/bundle/inputs/corpus.json:119-123`

Current official contract side B: the Agent SDK reference says the tool name is **`Agent`**, “previously `Task`, which is still accepted as an alias”; the current built-in tool inventory likewise lists `Agent` as the orchestration tool. Sources: <https://code.claude.com/docs/en/agent-sdk/typescript#agent> and <https://code.claude.com/docs/en/tools-reference>.

### Concrete collision

When current interactive Claude Code launches a subagent, the tool event reaches `PreToolUse` with `tool_name: "Agent"`. The two groups at settings lines 141 and 251 compare that event against an exact `Task` alternative. Current hook documentation states that tool-event matchers run against `tool_name`, and a matcher consisting of letters/digits/underscores and `|` alternatives performs exact matching. `Agent` is not equal to `Task`.

This collision actually arises: the corpus records 1,745 `Agent` calls (`corpus.json:119-126`). By contrast, the complete `tool_usage` list contains no `Task` entry. The corpus detector's reliability control passes because it found `Agent`, `TaskCreate`, and `TaskUpdate`; corpus metadata reports 11,633 files seen, 0 failed, and only 1 bad line (`corpus.json:2-11`).

The result is **almost certain (90-99%)** to be that neither of these two dispatcher handlers executes for current `Agent` tool calls. Evidence: exact-match semantics in the official hooks reference, the literal settings matchers at lines 141 and 251, and 1,745 observed `Agent` event names in the corpus. The residual uncertainty is that this remote bundle does not include the Windows `claude.exe`, so I could not run a fresh instrumented `Agent` call and inspect a sanitized hook receipt.

This does not mean *all* subagent lifecycle processing is absent. Separate `SubagentStart` and `SubagentStop` shared-dispatcher hooks are configured at settings lines 419-443. The finding is specifically that the two **PreToolUse** dispatcher branches named above miss the parent-side launch call. That distinction matters because the hook bus receives different payloads and can make a pre-call decision only at `PreToolUse`.

### Which text wins at runtime

The provider-emitted `tool_name` wins. The runtime does not rewrite `Agent` to `Task` for hook matching: current hook matching is against the emitted `tool_name`, while the SDK's statement that `Task` remains an accepted alias concerns invocation compatibility, not a promise that hook events are emitted under the alias. The observed transcript field is `Agent`, not `Task` (`corpus.json:119-126`). Therefore the `Task` alternatives in settings are skipped.

The permission entry `"Task",` at `/local_disk0/codexwork/bundle/claude/settings.json:40` does **not** establish that hook events are called `Task`. Permissions and hooks are separate consumers. Moreover, the configured permission mode is `"defaultMode": "bypassPermissions"` at settings line 71; official permission documentation says this mode skips ordinary prompts, so the stale permission spelling does not rescue the hook matcher.

### Minimal resolution — CONFIG (settings/JSON only)

Change the two hook matcher alternatives from `Task` to `Agent`:

- settings line 141: replace `...|Task|...` with `...|Agent|...`;
- settings line 251: replace leading `Task|...` with `Agent|...`.

This proposal rides the existing settings/hook bus, adds no component, and does not reintroduce any rejected orchestration, memory, durability, critic, observability, or guardrail system. It passes the anti-overfit gate.

After editing, the required verification is a disposable current-version call whose hook receipt proves both dispatchers receive `tool_name=Agent`. Static JSON equality alone is not a completion signal.

## Finding 2 — `TodoWrite` permission names a tool interactive Claude Code no longer provides

**Severity: cosmetic configuration drift; one observed failed call, but causation by this permission entry is not established.**

### Both sides, verbatim

Settings side A:

> `"TodoWrite",`

— `/local_disk0/codexwork/bundle/claude/settings.json:39`

Runtime/provider side B:

> `"tool": "TodoWrite",`
>
> `"calls": 1,`
>
> `"errors": 1,`
>
> `"error_rate": 1.0,`

— `/local_disk0/codexwork/bundle/inputs/corpus.json:3631-3635`

The same provider side supplies the replacement tools:

> `"tool": "TaskUpdate",` / `"calls": 3710,`

— `/local_disk0/codexwork/bundle/inputs/corpus.json:95-99`

> `"tool": "TaskCreate",` / `"calls": 2181,`

— `/local_disk0/codexwork/bundle/inputs/corpus.json:111-115`

Current official contract side B says `TodoWrite` is available in non-interactive mode and the Agent SDK, while **interactive sessions use `TaskCreate`, `TaskGet`, `TaskList`, and `TaskUpdate` instead**. The task migration documentation states that structured Task tools became the default in Claude Code v2.1.142. Sources: <https://code.claude.com/docs/en/tools-reference> and <https://code.claude.com/docs/en/agent-sdk/todo-tracking>.

### Concrete collision

The settings pre-approves `TodoWrite` globally, but in an interactive session there is no current `TodoWrite` capability for that rule to approve. The only recorded corpus attempt failed. Meanwhile, the replacement task system is heavily active: 3,710 `TaskUpdate` calls (`corpus.json:95-100`), 2,181 `TaskCreate` calls (`corpus.json:111-116`), 72 `TaskList` calls (`corpus.json:471-476`), and 22 `TaskGet` calls (`corpus.json:959-964`).

It is **very likely (80-90%)** that the allow-list entry is stale for the owner's ordinary interactive Claude Code sessions. Evidence: the current first-party tools reference explicitly distinguishes interactive from non-interactive availability, the migration reference gives the version boundary, and the corpus shows one failed legacy call versus 5,985 structured-task calls across the four replacement tools. Residual uncertainty remains because the corpus aggregates interactive, SDK, and possibly print-mode sessions; it does not label the single failed `TodoWrite` call's host mode.

I do **not** claim the settings entry caused the failed call. Permission allow rules authorize offered tools; they do not themselves add a missing tool to the model's action space. The corpus fingerprint for this one failure is not retained in the supplied distilled data, so its exact error text is unavailable.

### Which text wins at runtime

Runtime tool availability wins over a permission allow rule. In interactive sessions the structured Task tools are offered and `TodoWrite` is not. Additionally, settings line 71 selects `bypassPermissions`; official docs state that this mode skips ordinary permission prompts. Therefore `"TodoWrite"` neither makes the tool available nor materially changes current interactive approval behavior.

### Minimal resolution — CONFIG (settings/JSON only)

Delete `"TodoWrite",` from the allow array at settings line 39. Do not add a compatibility daemon, shim, alias hook, or second task system.

Adding `TaskCreate`, `TaskUpdate`, `TaskGet`, and `TaskList` to `permissions.allow` is **unlikely (20-45%)** to provide value under the present configuration. Evidence: `bypassPermissions` already skips ordinary prompts, and the task tools are demonstrably callable thousands of times without those allow entries. If the owner intends to replace bypass mode later, the settling experiment is to start a disposable session in the intended permission mode and observe whether each structured Task tool prompts; add only the rules that suppress a real unwanted prompt.

This proposal is a deletion on the existing settings bus and passes the anti-overfit gate.

### Permission `mcp__basic-memory`

Current official permission documentation explicitly says a server-only rule such as `mcp__puppeteer` matches every tool from that server; hook matchers use different syntax and require `mcp__server__.*`. Sources: <https://code.claude.com/docs/en/permissions#mcp> and <https://code.claude.com/docs/en/hooks#match-mcp-tools>.

### Catch-all matcher `.*`

Seventeen groups use `"matcher": ".*"`. Current hook documentation recognizes regex-style patterns and explicitly documents `.*` for MCP prefixes; it also states that several lifecycle events ignore matchers and always fire. I found no stale-provider collision caused by these catch-alls. Where the event does not support matchers (for example `TaskCreated`, `TaskCompleted`, `TeammateIdle`), `.*` is silently ignored rather than breaking dispatch: <https://code.claude.com/docs/en/hooks#matcher-patterns>.

## Gaps and limits

1. **UNVERIFIED live effective settings:** this Linux job node contains only the unpacked user settings, not the Windows executable, managed settings, per-project `.claude/settings.json`, or `.claude/settings.local.json`. A Windows `claude --version`, `/status`, and `/hooks` capture in a disposable trusted project would settle effective precedence. Official precedence says managed > CLI > local project > shared project > user; therefore another scope can override plugin booleans and other scalar settings: <https://code.claude.com/docs/en/permissions#settings-precedence>.
2. **UNVERIFIED MCP-provider reconciliation:** the task's pinned `C:\Users\Prekzursil\.mcp.json` and `C:\Users\Prekzursil\.claude.json` do not exist in the remote bundle. A sanitized Windows enumeration of configured server keys from both files, followed by `/mcp` connection status, would settle which MCP permission entries are truly stale. I did not fabricate their contents.
3. **UNVERIFIED plugin cache/install state:** the bundle does not include `~/.claude/plugins/cache` or installed-plugin metadata. `claude plugin list`, `claude plugin details <id>`, and `/doctor` on Windows would settle whether each of the eight enabled plugins resolves and loads. Internal marketplace coherence alone does not prove installation.
4. **UNVERIFIED status-line path:** settings lines 534-537 name `C:/Users/Prekzursil/.claude/statusline-command.sh`, but that file was not included in the unpacked `claude` tree. I do not claim it is absent on Windows. Two independent Windows signals are required: `Test-Path -LiteralPath C:\Users\Prekzursil\.claude\statusline-command.sh` and a live status-line/debug invocation after `Get-Command bash` confirms the interpreter.
5. **UNVERIFIED fresh hook receipt:** corpus tool names establish that `Agent` calls occur, but the corpus hooks detector is explicitly broken and was not used. A disposable `Agent` call with sanitized shared/local dispatcher receipts is the experiment needed to upgrade Finding 1 from almost-certain static/runtime-name reasoning to observed end-to-end proof.

## Final disposition

The minimal coherent correction is two settings-only changes: route current subagent launches as `Agent` in both PreToolUse dispatcher matchers, and remove the obsolete interactive `TodoWrite` allow entry. No replacement runtime, shim, daemon, memory store, critic, observability service, or guardrail framework is justified. The other examined candidates either have an explicit live consumer, cannot collide while dormant, or lack the second independent signal required for an absence claim.
