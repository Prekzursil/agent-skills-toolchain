## Executive verdict

Aider is a focused pair-programming loop, not a general agent harness. Its center of gravity is unusually disciplined: assemble a deliberately small code context; ask a model for edits in a model-specific textual format; apply the edits; feed precise format/match failures back to the same model; lint changed files; optionally test; and make each accepted change recoverable through Git. The implementation is a bounded interactive loop rather than a tool-using autonomous runtime. The core loop is directly visible in `Coder.run_one` and `Coder.send_message`: at most three internal “reflections,” followed by edit application, commit, lint, suggested shell commands, and optional tests ([source, `base_coder.py` lines 924–944 and 1419–1623](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L924-L944)).

The best thing to port is not Aider itself. It is the combination of:

1. a hard-budgeted, task-conditioned repository symbol map;
2. edit errors that carry repair context and preserve already-successful edit units;
3. a tight edit → lint → repair loop with bounded retries;
4. explicit separation between editable files, read-only files, repository-map context, and conversation history;
5. evaluation reports that distinguish task correctness from edit-format correctness.

It is **very likely (80-90%)** that importing those mechanics on the existing Claude/Codex hook, native-tool, and Repomix buses would improve file selection and reduce repeated edit failures; evidence is Aider’s concrete implementation, the local corpus’s 1,066 read-before-write/stale-read edit errors and 20+ exact/multiplicity edit failures, and the already-mounted Repomix MCP. This is not causal proof of a local outcome. The settling experiment is the held-out A/B suite specified in “Experiments before adoption.”

It is **almost certain (90-99%)** that installing Aider as another editing/orchestration runtime would make this owner’s harness broader but not better; evidence is that the local harness already has native file tools, MCP, hooks, durable semantic memory, custom agents, agent teams, cross-vendor delegation, credential guards, and checkpoint rollback, whereas Aider lacks comparable general tool/MCP, policy-hook, durable-memory, and multi-agent surfaces. The remaining 1-10% uncertainty is compatibility and usability under real owner tasks; a disposable, no-write Aider session against a representative repository would settle that narrow usability question.

This recommendation passes the anti-overfit gate. Every proposed adoption below rides an existing native tool, hook, skill, or MCP bus. No proposal introduces a second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 1. Agent loop

### What Aider actually does

`Coder.run` is an ordinary terminal read/evaluate loop. `run_one` preprocesses slash commands, file mentions, and URLs, then repeatedly calls `send_message` while a reflected repair message exists. It stops after three reflections (`max_reflections = 3`) ([pinned source, lines 859-944](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L859-L944)). This is a crucial distinction: Aider is not giving the model a general set of tools and letting it decide among them. The model emits a response in a selected edit format; Aider interprets that response.

The message path is:

1. append user input;
2. build system/examples/repository/read-only/editable/history chunks;
3. warn or ask before exceeding the known context window;
4. call the LLM with bounded provider retry/backoff;
5. check model-mentioned files and optionally add them;
6. parse edits and dry-run them;
7. request permission for files outside the edit set;
8. apply edits;
9. auto-commit;
10. auto-lint edited files;
11. offer to feed lint errors back as the next reflection;
12. run explicitly suggested shell commands after confirmation;
13. optionally run tests and offer another repair reflection.

The implementation order is explicit at [pinned `base_coder.py` lines 1419-1623](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1419-L1623). Provider errors get exponential backoff from 0.125 seconds until a retry timeout, and output-limit continuation is supported for models with assistant prefill (lines 1449-1505). Format, lint, and test repair share the same three-reflection ceiling, which prevents an unbounded repair loop.

### Architect mode

Architect mode is a sequential two-model specialization. The architect produces prose. With user confirmation unless auto-accept is configured, Aider creates a fresh editor coder, disables shell suggestions and repository-map regeneration for it, clears its current/done message histories, and gives the architect’s prose directly to the editor ([pinned `architect_coder.py` lines 6-48](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/architect_coder.py#L6-L48); [official mode documentation](https://aider.chat/docs/usage/modes.html)).

This is attention separation, not a multi-agent system. There is no task delegation, parallelism, mailbox, shared work board, worktree lease, hierarchical agent spawning, or independent reviewer in the Aider path examined.

### Better than ours

- Aider’s loop has one explicit, source-enforced bounded retry count. The local contract has a two-strikes pivot at `/local_disk0/codexwork/bundle/claude/AGENTS.md:51-57`, but it depends partly on agent behavior and hook detection.
- Aider’s edit/lint/test stages have a deterministic order and carry machine-produced failure text into the next model call. The local harness has more verification components, but the corpus shows substantial tool-level failure and the detector record shows enforcement can misclassify success.
- The model is not exposed to an enormous generic tool schema, avoiding this harness’s measured StructuredOutput fan-out mismatch class (846/3,694 errors, including 294 identical missing-field failures).

### Worse than ours / do not copy

- Do not replace native tool calling with Aider’s text-protocol loop. Native Edit/apply-patch operations are already typed, scoped, and visible to the permission/hook bus.
- Do not copy the raw architect-prose handoff. The local contract explicitly forbids raw-output-prefix handoffs at `/local_disk0/codexwork/bundle/claude/AGENTS.md:59-62`; a typed plan packet with acceptance criteria is safer.
- Do not copy the single-session, single-repository control plane. Aider’s FAQ says it works on one Git repository at a time and suggests manually sharing read-only files/maps across repositories ([official FAQ](https://aider.chat/docs/faq.html)).

## 2. Context management

### Repository map

Aider’s repository map is its clearest structural advantage. It parses files with Tree-sitter queries into definition/reference tags; uses Pygments to backfill references where a grammar supplies definitions only; builds a directed file dependency graph; boosts identifiers mentioned in the task, long structured identifiers, and references from files already in chat; downweights private and over-common identifiers; and applies weighted PageRank ([pinned `repomap.py` lines 279-574](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L279-L574)).

The output side is equally important: cache keys include chat files, other files, token budget, and—under automatic refresh—mentioned files/identifiers; the map is regenerated or reused according to `auto|always|files|manual`; important root files are prepended; and a binary search chooses the richest rendered tree near the token cap ([pinned source, lines 576-706](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L576-L706)). Rendered trees cache by file, lines of interest, and modification time (lines 708-746).

The default map budget is 1,024 tokens in the pinned constructor, with a multiplier when no files are in chat; Aider warns when excessive map context may confuse the model ([pinned `base_coder.py` lines 250-275 and 299-340](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L250-L340); [repository-map docs](https://aider.chat/docs/repomap.html)).

This is not vector retrieval or durable graph memory. It is a transient, deterministic graph calculation over current source, which satisfies the owner’s anti-overfit gate.

### Layered prompt chunks

Aider keeps distinct chunks for system instructions, examples, summarized old conversation, repository map, read-only files, editable files, current turns, and a final reminder. It can add provider cache-control headers to the stable chunks ([pinned `base_coder.py` lines 1226-1338](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1226-L1338); [prompt-caching docs](https://aider.chat/docs/usage/caching.html)). Read-only files are explicitly acknowledged as references, while repository-map files are acknowledged as non-editable unless added ([pinned source, lines 709-815](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L709-L815)).

Conversation history is summarized asynchronously by a configured summarizer when the done-message soft limit is exceeded; the old messages are replaced only if they have not changed during summarization ([pinned source, lines 1002-1046](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1002-L1046)). Users can inspect tokens and manually `/drop`, `/clear`, or `/reset`; Aider warns at the model limit but can proceed after confirmation ([options reference](https://aider.chat/docs/config/options.html); [pinned source, lines 1396-1417](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1396-L1417)).

### Comparative judgment

The local harness has Repomix mounted at `/local_disk0/codexwork/bundle/codex/config.toml:524-526` and allowlisted for Claude at `/local_disk0/codexwork/bundle/claude/settings.json:47-51`, but the corpus records only 8 Repomix-server uses. When its repository map is enabled, Aider automatically conditions that map on current chat/task state. Whether the local harness already performs equivalent automatic map injection is **UNVERIFIED** because the hook telemetry detector is broken and a complete dispatcher-path audit is outside this unit; the settling experiment is a controlled fresh-agent task with debug prompt capture, proving whether a task-conditioned symbol map appears before the first file-selection action.

The local harness is better at open-ended context acquisition: native search, Serena/Repomix, many MCPs, web tools, skills, and delegated exploration. Aider is better at giving every coding turn a compact, predictable structural baseline.

## 3. Memory

Aider has three continuity mechanisms, none equivalent to durable semantic memory:

- in-process current and completed message arrays;
- model-generated summarization of completed history;
- optional file logs and `--restore-chat-history`, with `.aider.chat.history.md` as the default transcript file ([official options, History Files](https://aider.chat/docs/config/options.html)).

Git commits also form an objective edit history, but they record code state, not user preferences, decisions, failed hypotheses, or temporal supersession.

The local harness is stronger. `/local_disk0/codexwork/bundle/claude/CLAUDE.md:5-13` defines proactive recall and temporal validity through basic-memory; `/local_disk0/codexwork/bundle/claude/AGENTS.md:28-34,85-91` distinguishes objective event-ledger memory from semantic memory; the corpus records 1,332 basic-memory MCP calls. Aider’s transcript restore is simpler and less failure-prone, but it cannot selectively retrieve a past decision across projects.

Do not port a second Aider-style transcript memory system. The useful idea is only the separation between objective edit history, active chat, summarized old chat, and semantic memory; the local architecture already has those roles.

## 4. Tool and MCP handling

Aider’s “tools” are mostly host-side affordances, not LLM tool calls:

- file mutation via edit-format parsers;
- optional shell commands encoded in edit responses;
- slash commands such as `/run`, `/test`, `/git`, `/add`, `/read-only`, `/drop`, `/tokens`, and `/undo`;
- URL detection and optional fetching into context;
- images/PDFs for capable models;
- built-in/per-language/custom lint commands;
- a test command;
- Git operations.

Suggested shell commands are extracted from response blocks and run only after an explicit-yes confirmation; `--yes` deliberately answers “no” to commands marked `explicit_yes_required`, a subtle safety property in `InputOutput.confirm_ask` ([pinned `base_coder.py` lines 2434-2475](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2434-L2475); [pinned `io.py` lines 807-925](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/io.py#L807-L925)). Direct user `/run` and `/git` commands execute as user commands, which is appropriate for an interactive pair programmer but not a policy boundary.

Aider CLI has no native MCP or general Agent Mode in the checked evidence. That is **almost certain (90-99%)**, based on the controlled pinned-source probes, the official options surface, and the explicit open upstream request for native MCP/Agent Mode. The residual uncertainty is undocumented or newly merged behavior after the pinned commit; the settling experiment is the authenticated tree/source scan described above plus `aider --help | rg -i 'mcp|agent'` on the exact release.

The local harness is vastly more capable here: 93 MCP servers were touched in the corpus, 5,091 ToolSearch calls had a 0.08% error rate, and settings expose tool search and MCP namespaces. Aider’s narrow tool surface, however, avoids dead-server selection and complex schema fan-out. That lesson is to prune and health-gate our fleet, not to remove MCP.

## 5. Permission model

Aider’s permission model is an edit scope plus confirmations:

- files explicitly added to chat are editable;
- files passed with `--read` or `/read-only` are context-only;
- creating a new file requires confirmation;
- editing an existing file not added to chat requires confirmation;
- `.aiderignore` and Git ignore rules constrain visibility/editing;
- suggested shell commands require confirmation;
- URL ingestion requires confirmation;
- `--dry-run` suppresses writes;
- `--yes-always`/`--yes` can broadly automate confirmations;
- Git dirty-file commits and per-edit commits provide recovery.

The exact file gate is in [pinned `base_coder.py` lines 2191-2240](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2191-L2240). Confirmation supports yes/no, group all/skip-all, and “don’t ask again” choices ([pinned `io.py` lines 807-925](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/io.py#L807-L925)).

This is more legible than the local harness’s current effective policy. Local settings allow most high-impact tools, set an empty ask list, use `defaultMode: bypassPermissions`, and grant `C:` and `D:` additional directories at `/local_disk0/codexwork/bundle/claude/settings.json:26-75`. The local hook/rule layer is more expressive—credential reads, force pushes, test tampering, untrusted input, and semantic tool context—but the live defect record proves some guards confuse mention with use.

Aider is worse for security boundaries:

- no per-command/path capability grammar comparable to native tool permission rules was found;
- no sandbox or network egress policy is documented in the checked surface;
- read-only is a chat/edit affordance, not an OS filesystem sandbox;
- a global automation switch is coarse;
- project-local `.aider.conf.yml` and `.env` are configuration/secret-loading surfaces ([configuration docs](https://aider.chat/docs/config.html); [API-key docs](https://aider.chat/docs/config/api-keys.html)).

Do not copy Aider’s coarse global-yes model. Do copy the visible, per-file distinction among editable, read-only, ignored, and not-yet-authorized files.

## 6. Customization: rules, skills, hooks equivalents

### Configuration

Aider has a coherent four-way configuration surface: CLI switches, `.aider.conf.yml`, `AIDER_*` environment variables, and `.env` ([official configuration docs](https://aider.chat/docs/config.html)). It separately supports model aliases, model metadata, and per-model settings such as edit format, repository-map use, weak/editor model, prompt caching, reminder placement, reasoning tags, and accepted reasoning controls ([advanced model settings](https://aider.chat/docs/config/adv-model-settings.html)). This is excellent product configuration, but not an extensible harness bus.

### Rules equivalent

Coding conventions are ordinary files added read-only with `/read` or always loaded through configuration ([conventions docs](https://aider.chat/docs/usage/conventions.html)). That is roughly analogous to a project rule file, with two strengths: it is explicit context and can be placed in a cacheable read-only chunk. It lacks rule scoping, precedence, mandatory trigger semantics, and mechanical enforcement.

### Skills equivalent

No packaged, discoverable, triggerable skill system was found in the controlled source/options/doc evidence. Aider can load a file of slash commands at startup (`--load`) and users can script single messages via CLI or instantiate `Coder` in Python, but the scripting docs explicitly say the Python API is unofficial and provide no backwards-compatibility promise ([scripting docs](https://aider.chat/docs/scripting.html)). Conventions and command files are not equivalent to this harness’s skill metadata, trigger rules, referenced assets, and tool access.

### Hooks equivalent

The only user-facing hook option found is whether Aider-created Git commits run repository pre-commit hooks; the default skips them with `--no-verify`, and `--git-commit-verify` opts in ([Git integration docs](https://aider.chat/docs/git.html)). There is no comparable SessionStart/UserPromptSubmit/PreToolUse/PostToolUse/PostToolUseFailure/PreCompact/SubagentStop/Stop bus in the checked Aider surface.

This is a major area where Aider is worse. It cannot host the owner’s telemetry, semantic guard, routing, memory, and lifecycle mechanisms without source modification or an external wrapper. A wrapper would be a second runtime and fails the anti-overfit gate.

## 7. Multi-agent support

Aider’s architect/editor mode uses two model calls and two coder instances, sequentially. It is useful specialization, but the editor receives the architect’s free-form content directly and there is no independent validation of the handoff before editing ([pinned source](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/architect_coder.py#L11-L48)). The official docs recommend Ask → Code as a conversational alternative and describe Architect → Editor as a two-model workflow ([chat modes](https://aider.chat/docs/usage/modes.html)).

No parallel subagents, agent teams, mailbox, steering, role tool restrictions, lease coordination, or reviewer agent were found. That absence is **almost certain (90-99%)** for the pinned CLI, based on the controlled source probes and the explicit Agent Mode feature request. The same authenticated full-tree scan settles the residual uncertainty.

The local harness is categorically stronger: native experimental agent teams and forked subagents are enabled, custom architect/implementer/reviewer roles have different tool grants, and the corpus records 1,745 Agent calls across 22 agent types. The local problem is wiring quality and utilization, not missing multi-agent machinery.

Do not call Aider architect mode “multi-agent” in future design documents. Call it a two-stage model pipeline.

## 8. Verification and self-check

### Edit-format and match verification

Aider dry-runs parsed edits before permission and application. On malformed output it tells the model that the edit format was violated and reflects the concrete parser error ([pinned `base_coder.py` lines 2296-2328](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L2296-L2328)).

Its SEARCH/REPLACE coder is particularly good at repair semantics. It applies every block independently, keeps successful blocks, detects failures, returns nearby similar lines, detects when replacement text is already present, and instructs the model to resend only failed blocks ([pinned `editblock_coder.py` lines 41-124](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/editblock_coder.py#L41-L124)). It also permits leading-whitespace flexibility after an exact-match attempt (lines 134-143), which is convenient but can be unsafe if it turns an ambiguous match into an unintended edit.

### Lint and test verification

Auto-lint defaults on; built-in or configured linters run only on edited files. If lint errors occur, Aider asks whether to repair them and reflects the output. Auto-test defaults off; a configured test command can run after edits and likewise feed failure output back ([lint/test docs](https://aider.chat/docs/usage/lint-test.html); [options reference](https://aider.chat/docs/config/options.html); [pinned loop lines 1599-1623](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1599-L1623)).

This is not an independent self-review. The same conversation/model repairs parser, lint, and test failures. Architect mode separates reasoning and editing, but it does not add a post-edit reviewer. Aider can therefore converge on tests while missing requirements, security, or unrelated-diff problems.

### Git verification and rollback

Aider auto-commits edits by default, protects dirty files by committing pre-existing changes first, shows diffs, and offers `/undo` only for a commit made by Aider in the current chat. Undo refuses the first commit, merge commits, dirty changed files, and already-pushed commits, then checks out only files from the prior commit ([Git docs](https://aider.chat/docs/git.html); [pinned `commands.py` lines 553-640](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/commands.py#L553-L640)).

The local rollback is more general: it snapshots before Edit/Write/MultiEdit, supports non-Git copies, retains GC-safe refs, previews restore actions, and requires user choice. Aider’s UX is simpler, but its default auto-commit behavior changes repository history and its default skipping of pre-commit hooks is inappropriate for this owner’s `never --no-verify` contract at `/local_disk0/codexwork/bundle/claude/AGENTS.md:93-97`.

### Evaluation

Aider’s public polyglot leaderboard runs 225 Exercism tasks across six languages and reports task correctness, pass 1/pass 2, edit-format compliance, malformed responses, error outputs, context exhaustion, tokens, cost, test timeouts, source commit, versions, and wall time ([leaderboard](https://aider.chat/docs/leaderboards/); [benchmark README](https://github.com/Aider-AI/aider/blob/main/benchmark/README.md)). This distinction between “the task passed” and “the model obeyed the edit protocol” is worth copying.

The leaderboard is self-published, uses public exercises, mixes model generations and harness versions, and does not isolate the causal contribution of the repository map. Its numbers are evidence that Aider measures itself, not proof that a specific Aider feature will improve this owner’s current models. This decomposition motivates proposal P4.

## Capabilities not to port

### Aider as a second editing runtime

Do not install Aider into the harness. It would duplicate native file mutation, conversation, model routing, Git, context, and retry machinery while lacking the local lifecycle bus. This explicitly avoids a previously rejected second orchestration runtime.

### Textual edit-format zoo

Aider supports whole-file, SEARCH/REPLACE, unified-diff-like, editor-diff, and other model-specific formats ([edit-format docs](https://aider.chat/docs/more/edit-formats.html)). These are adaptations for models without reliable native mutation tools. Copying them would add parsing and fuzzy-application risk to a harness that already has native typed tools.

### Flexible whitespace matching

Do not port Aider’s whitespace-flexible fallback. In the local system, ambiguous/multiple matches are explicit errors. Maintain exact, unique target semantics and offer nearby context to the model instead.

### Default auto-commit and skipped commit hooks

Do not auto-commit every edit and do not skip pre-commit verification. The local checkpoint system provides recovery without polluting history; the global contract forbids `--no-verify` absent explicit user instruction.

### Global yes/automation switch

Do not collapse permission decisions into “yes to everything.” Preserve typed tool/path permissions and explicit approval for destructive or externally visible operations.

### Raw architect → editor prose

Do not forward free-form architecture prose as an editor’s sole instruction. Use the local structured handoff contract: original goal, decision, files, acceptance tests, constraints/non-goals, risks, and evidence.

### Session transcript as semantic memory

Do not treat restored chat history or a model summary as durable knowledge. Keep semantic memory, objective event history, and active conversation separate.

### Public benchmark scores as local causal proof

Do not select architecture based on Aider leaderboard rank or old architect-mode uplift alone. The 2024 architect study reported 82.7% for one architect/editor pairing and 85.0% for another ([Aider architect study](https://aider.chat/2024/09/26/architect.html)), but models, tasks, edit formats, and costs differ from this owner’s present setup.

## Where Aider is worse than this harness

1. **General action space:** no native MCP/general tool ecosystem versus 93 MCP servers touched locally.
2. **Multi-agent:** no teams, subagents, fan-out, steering, mailbox, or role-specific tool grants.
3. **Lifecycle customization:** no general hook bus.
4. **Durable memory:** no semantic cross-project recall or temporal supersession.
5. **Security policy:** coarse edit scope and prompts rather than tool/path/egress/credential policy.
6. **Independent review:** same-loop repair, no mandatory fresh reviewer.
7. **Cross-repository operation:** officially one repository at a time.
8. **Extensibility stability:** Python API explicitly unofficial; new coder formats require implementation work.
9. **Pre-commit posture:** verification hooks are skipped by default.
10. **Git side effects:** auto-commits are default, which is convenient for pair programming but inappropriate as a universal agent-harness policy.
11. **Telemetry integration:** it has optional analytics and logs, but not this owner’s objective event ledger and lifecycle receipts.
12. **Prompt-injection controls:** no source-map/content quarantine comparable to the local untrusted-data contract was found. This last absence is **very likely (80-90%)**, supported by the checked options/docs/source and absence of a lifecycle policy bus; the authenticated full-tree search for `prompt injection|untrusted|quarantine` would settle it.

## Where Aider is better than this harness

1. **Automatic structural context:** every coding request can receive a compact, task-conditioned repository map.
2. **Editing focus:** the entire runtime is optimized around applying code changes reliably.
3. **Repair feedback:** failed edit blocks get precise, actionable context; successful blocks are retained.
4. **Bounded reflection:** three internal repairs maximum in source.
5. **Stage order:** edit, commit, lint, shell suggestions, optional test is explicit and inspectable.
6. **Context legibility:** users can see/edit/drop read-only and editable sets and inspect token allocation.
7. **Evaluation transparency:** task correctness and protocol compliance are reported separately with provenance and cost.
8. **Configuration coherence:** CLI/env/YAML options map cleanly and are documented in one reference.
9. **Undo UX:** `/undo` is simple and safety-checks provenance, dirty files, merge commits, and pushes.

Items 1-5 describe upstream mechanisms, not proven local superiority on end-task success. Their end-task benefit here remains **UNVERIFIED** until the experiments below.

## Experiments before adoption

### E1 — Repomix structural-map A/B

Use 20-30 held-out owner-representative multi-file tasks across at least three repositories. Randomize fresh agents to:

- A: current harness;
- B: current harness + 1,024-token compressed Repomix map before first file choice.

Measure first-file precision, required-file recall, exploratory tool calls, time to first correct edit, task pass, unrelated diff, tokens, and total wall time. Run at least three independent trials per task/model. The CONFIG proposal passes only if B improves task pass or file-selection recall without a material unrelated-diff or latency regression.

### E2 — Edit repair replay

Build fixtures from the corpus’s top edit fingerprints: unread file, stale read, no exact match, duplicate match, already-applied change, and a two-block edit with one success/one failure. Compare current native error text against typed contextual repair. Require fewer repeated identical errors, no additional unintended diff, and no retry of successful units.

### E3 — Verification-hook known-positive control

Create a disposable fixture with one deterministic lint failure and one deterministic targeted-test failure. Capture hook input schema, hook ledger/event output, and transcript injection through mechanically separate channels. First prove the detector sees a known successful hook and known failing fixture. This settles whether P3 is new work or existing-but-unmeasured behavior.

### E4 — Architect/editor/reviewer ablation

Compare direct native coding, same-model plan→edit, specialist architect→editor, and architect→editor→fresh reviewer. Use current models, fixed tasks, held-out tests, total cost, wall time, and independent trials. Do not use Aider’s historical uplift as the expected answer.

### E5 — Cache-prefix measurement

On a stable large rule/conventions context, repeat the same class of request with native cache fields captured. Compare cache-hit/write tokens, cost, first-token latency, and output quality. Disable keepalive pings; this experiment is about layout, not synthetic cache retention.
