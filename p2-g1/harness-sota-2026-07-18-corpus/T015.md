# T015 — Competitive teardown: Factory

**Unit:** T015  
**Research date:** 2026-07-19 UTC  
**Subject:** Factory Droid CLI, Factory App, Factory Missions, and the public Droid SDK surface  
**Purpose:** identify mechanisms worth porting into the owner's Claude/Codex harness, mechanisms already present, and mechanisms that would be harmful to copy.

## Executive verdict

Factory is not a compelling full replacement for this owner's harness. Its ordinary single-agent surface—AGENTS.md, skills, hooks, MCP, custom commands, subagents, planning mode, approvals—substantially overlaps what the owner already operates. The owner's harness is materially ahead in durable cross-session memory: Factory's own memory guide says Droid has no built-in memory between sessions and recommends hand-maintained Markdown plus hooks, whereas this harness has a cross-tool `basic-memory` store, temporal supersession, an objective event ledger, Stop capture, and SessionStart replay (`/local_disk0/codexwork/bundle/codex/AGENTS.md:20-26,62-68,79-85`; [Factory memory guide](https://docs.factory.ai/guides/power-user/memory-management)).

Factory does, however, expose three mechanisms worth extracting:

1. **Deferred capability context:** keep only names/descriptions/input hints in the prompt; promote a complete tool schema or skill only on demand and keep it warm thereafter. Factory reports a 15.1% mean estimated input-token reduction in measured MCP-using sessions and 50.8% for sessions with 100+ hidden tools. This is unusually relevant here because the owner has roughly 355 installed skills but used 78, and 93 MCP servers were touched; the harness also continues to call a dead Tavily MCP. These are Factory production-telemetry claims, not an independent replication ([Deferred Context Engine](https://factory.ai/news/deferred-context-engine); pinned corpus summary in the unit brief).
2. **Validation-contract-first execution:** write finite behavioral assertions before feature decomposition; assign each feature to assertions; use fresh scrutiny and black-box user-testing agents at milestone boundaries; turn failures into narrowly scoped fix features; revalidate. Factory's published Slack-clone run says all six milestones needed 2–4 validation rounds, validators found 81 issues, and 21 of 61 implementation features were corrective. That is vendor-reported evidence from one run, but it is concrete enough to justify a bounded experiment ([Missions architecture](https://factory.ai/news/missions-architecture)).
3. **Per-subagent least privilege and model routing:** each subagent gets its own context, system prompt, model, autonomy, built-in-tool allowlist, and MCP-server allowlist; tasks can run in the background, be stopped, or be resumed with their prior transcript ([Subagents](https://docs.factory.ai/cli/configuration/custom-droids)).

The decisive architectural recommendation is **extract, do not adopt Missions wholesale**. Factory Missions is explicitly a separate orchestration layer, requires High autonomy or an unsafe permission bypass, and can be extremely expensive. Factory's showcased run used 185 agent runs, 778.5M total tokens, and 16.5 hours. A second orchestration runtime is on this program's rejected-components list and violates the anti-overfit gate. It is **very likely (80-90%)** that validation contracts plus fresh validators can capture most of the reliability benefit on the existing Agent Teams/subagent/skill bus; evidence is that the useful mechanism is expressed as shared Markdown/JSON artifacts and role separation, while the expensive runner is merely how Factory schedules it ([Missions architecture](https://factory.ai/news/missions-architecture); native multi-agent and fanout are already enabled at `/local_disk0/codexwork/bundle/codex/config.toml:77-80,101-106,125-130`). The settling experiment is a three-task A/B test described below.

## 1. Agent loop

### What Factory concretely exposes

The normal Droid experience is a standard conversational tool loop: take a prompt, inspect repository context, plan as needed, call read/edit/execute/web/MCP tools, observe results, and continue until it responds. Factory's AGENTS.md guide summarizes the intended trajectory as **Explore → Plan → Code → Verify**, and says AGENTS.md is loaded before planning ([AGENTS.md](https://docs.factory.ai/cli/configuration/agents-md)). The prompt guide repeatedly tells users to define success and give exact verification commands, which implies verification is goal-conditioned rather than a universal hard gate ([How to Talk to a Droid](https://docs.factory.ai/cli/getting-started/how-to-talk-to-a-droid)).

Specification Mode is a distinct read-only planning state. Droid examines the codebase, produces acceptance criteria, a file-level plan and verification strategy, then cannot edit until the user approves. Approval can also select the subsequent autonomy level ([Specification Mode](https://docs.factory.ai/cli/user-guides/specification-mode)). Mixed-model configuration can use a stronger model for planning and a cheaper model for implementation ([Mixed Models](https://docs.factory.ai/cli/configuration/mixed-models)).

`droid exec` turns the same surface into a non-interactive runner with text, JSON, or streaming JSON-RPC I/O; callers can initialize/load/fork/compact/interrupt sessions, handle permission requests, manage tools/MCP, and consume token/tool/turn events ([Droid Exec](https://docs.factory.ai/cli/droid-exec/overview); [TypeScript SDK](https://github.com/Factory-AI/droid-sdk-typescript)).

Factory Missions adds a second, explicit loop:

1. clarify the goal;
2. create a finite validation contract before features;
3. decompose assertions into bounded features and milestones;
4. create shared state artifacts;
5. run each feature in a fresh worker context, with tests before implementation;
6. at a milestone, launch fresh scrutiny and black-box user-testing validators;
7. convert actionable failures into fix features;
8. repeat validation until pass, or halt to the user if blocked.

That mechanism is described concretely in [How Missions Work](https://factory.ai/news/missions-architecture) and [Planning & Validation](https://docs.factory.ai/features/missions/planning).

### What is better

The validation contract is defined before implementation planning, reducing the chance that tests merely ratify the chosen design. Fresh validators also avoid the implementer's accumulated confirmation context. This is **very likely (80-90%)** to reduce false “done” declarations on tasks with externally testable behavior; evidence is the separation of incentives, Factory's reported 81 validator-found issues in one large run, and the owner's current critic being a prose instruction to imagine a fresh reviewer rather than actually spawning one (`AGENTS.md:56-60`). The A/B experiment below would settle owner-specific effect size.

Factory also added a repeated-identical-tool-call stop in v0.173.0, a direct response to loop failure ([release notes, July 15](https://docs.factory.ai/changelog/release-notes)). That aligns with the owner's measured retry-loop concern and terminal-state marker rule (`AGENTS.md:28-31`).

### What is worse

Missions is heavy. Factory itself calls it a research preview and lists unresolved questions about whether parallelism helps, how to maximize correctness, and cost/quality ([Missions overview](https://docs.factory.ai/features/missions/overview)). The showcased run spent 37.2% of 16.5 hours in validation and consumed 778.5M tokens. This is exactly the kind of elaborate scaffold that can overfit as base models improve.

Missions also requires High autonomy or `--skip-permissions-unsafe`; the latter bypasses all checks and is documented for isolated environments only ([Autonomy Level](https://docs.factory.ai/cli/user-guides/auto-run)). That coupling is worse than a least-authority validation workflow.

The normal loop has no documented universal proof gate. Factory tells the user to define success and review changes; that is good guidance, but not mechanical completion evidence ([How to Talk to a Droid](https://docs.factory.ai/cli/getting-started/how-to-talk-to-a-droid)).

### Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — validation-contract skill and two fresh validator roles

Create one skill/template that emits:

- `validation-contract.md`: stable assertion IDs, preconditions, user-visible behavior, tool, and required evidence;
- `features.json`: each bounded feature claims assertion IDs and allowed paths;
- a worker handoff containing only the feature, relevant contract assertions, known constraints, and existing evidence;
- a read-only scrutiny reviewer that checks diff, tests, and worker claims;
- a black-box validator that exercises the artifact without reading the worker's reasoning;
- an adjudication step that turns failed assertions into new bounded work, never lets validators implement their own fixes, and stops after an explicit retry budget.

Use native Agent Teams/subagents already enabled; do not create a daemon, durable-execution engine, or second scheduler. Apply only to high-risk/multi-surface tasks. This passes the anti-overfit gate.

It is **very likely (80-90%)** to fit within a small skill plus agent-definition change because the existing runtime already supports concurrent native agents and typed handoffs (`config.toml:77-80,101-106,125-130`; `AGENTS.md:43-46`). Experiment: replay three owner tasks with known corrections, alternating current flow versus contract + fresh validators; score missed acceptance criteria, owner corrections, wall time, and tokens. Promote only if correction reduction exceeds 25% without more than 2× tokens.

#### Do not port: BUILD-LARGE (new daemon/service/runtime -- needs its own justification) — Missions runner

This proposal is explicitly rejected. It reintroduces a second orchestration runtime and durable workflow state, both excluded by the anti-overfit gate. Factory has not shown that the runner itself—rather than contract quality and fresh validation—is the causal benefit.

## 2. Context management

### Anchored iterative compression

Factory maintains a persistent rolling summary anchored to a transcript message. When the prompt reaches a fill threshold, it keeps a recent suffix, summarizes only the newly dropped span, and merges that delta into the existing summary. The target structure preserves session intent, high-level play-by-play, artifact trail, and breadcrumbs such as paths/functions/identifiers. This avoids repeatedly re-summarizing the whole prefix ([Compressing Context](https://factory.ai/news/compressing-context)).

Factory evaluated compression with functional probes—recall, artifact, continuation, and decision questions—over 36,000+ production messages. It reports Factory structured summaries scoring 3.70/5 overall versus Anthropic 3.44 and OpenAI 3.35 at similar 98.6–99.3% token removal. Crucially, even Factory's artifact score was only 2.45/5, an admission that summaries are not reliable artifact ledgers ([Evaluating Context Compression](https://docs.factory.ai/guides/power-user/evaluating-context-compression)).

The owner's objective event ledger is therefore architecturally better for facts than asking a lossy summary to preserve them (`AGENTS.md:20-26,62-68`). Factory's probe methodology is the useful import, not replacing the ledger with a summary.

### Deferred Context Engine

Factory begins with compact discovery metadata for internal tools, MCP tools, skills, plugins and subagents. When relevant, a built-in loader promotes the full schema/instructions; promoted capabilities stay available for the rest of the work, while frequent tools remain warm in a cache across sessions. Factory says this reduces attention dilution, tool-selection noise, and earlier compaction ([Deferred Context Engine](https://factory.ai/news/deferred-context-engine)).

This directly targets the owner's sparse capability use and dead-MCP problem. It also avoids the unsafe response of deleting large catalogs solely to save context.

### Port

#### UNVERIFIED — NATIVE (Claude Code already does this; we just enable it) — provider-native deferred tool/skill discovery

**UNVERIFIED:** whether every active owner surface already exposes provider-native deferred loading for MCP schemas and skills. The Codex bundle enables code mode, apps gateway, plugins, and non-prefixed MCP names (`config.toml:82-123`), but those flags do not prove equivalent prompt-time deferral on Claude. The settling experiment is to capture per-turn request metadata/token counts in a disposable session with 0, 20, and 100 enabled-but-unused tools, then invoke one hidden tool and confirm discover → promote → reuse behavior.

If the control shows native deferral, enable it across providers and keep a compact index containing capability name, source, one-sentence trigger, risk class, and minimal input hints. Do not implement a wrapper runtime. It is **likely (55-80%)** to reduce tool-selection noise here because the owner's installed-to-used ratio is 355:78 and Factory's benefit rises sharply with hidden catalog size; uncertainty remains because Factory's telemetry cohort differs from this Windows harness.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — compaction continuation probes

Add a test harness, not a new compactor. Before and after a controlled compact, ask fixed probes for: original objective, last confirmed error, modified artifact list, rejected approaches, current next step, and governing constraints. Grade against the event ledger and git/file facts, not an LLM-only judge. Include a known-present control before any “lost” verdict.

It is **very likely (80-90%)** this will expose regressions more reliably than summary-length metrics because Factory's own evaluation found functional probes discriminated methods and its artifact score remained weak. This rides existing PreCompact/SessionStart/ledger hooks.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — proactive phase checkpoint

At a genuine phase boundary, write a structured checkpoint with objective, decisions, files, tests, failures, and next step to the existing event ledger/basic-memory path; re-inject it after compaction. Do not summarize every turn. This is **likely (55-80%)** to reduce re-reading after compaction because Factory identifies exactly those fields as continuation-critical and the owner's replay path already exists (`AGENTS.md:20-26,79-85`). Experiment: compare redundant reads/tool calls over ten long sessions with and without phase checkpoints.

## 3. Memory

### Factory mechanism

Factory explicitly says Droid has no built-in memory between sessions. Its recommended design is:

- `~/.factory/memories.md` for personal preferences;
- `.factory/memories.md` for project decisions/history;
- `.factory/rules/` for conventions;
- AGENTS.md references that instruct the model to read those files;
- optional `UserPromptSubmit` hooks, `/remember` commands, or skills to append entries;
- manual review/archive of stale memories.

See [Memory and Context Management](https://docs.factory.ai/guides/power-user/memory-management).

### Relative verdict: worse

This is flat-file prompt memory with manual curation, no demonstrated semantic retrieval, temporal validity, contradiction handling, cross-tool canonical store, or objective event capture. The owner's system explicitly distinguishes semantic memory from objective turn history and records supersession (`AGENTS.md:62-68,79-85`). Copying Factory would regress capability.

Factory Missions does externalize shared state into a validation contract, feature list, research notes, operational guidelines, and evolving knowledge base. That is useful **working state**, but it is not a replacement for durable personal/project memory ([Missions architecture](https://factory.ai/news/missions-architecture)).

### Port

No memory proposal qualifies. Preserve the current `basic-memory` + event-ledger split. Borrow only Factory's narrow shared artifacts inside a bounded multi-agent task.

## 4. Tool and MCP handling

### Factory mechanism

Factory supports stdio, Streamable HTTP, and legacy SSE MCP transports; OAuth discovery/dynamic registration, keyring storage, per-server timeouts, `enabledTools` allowlists, `disabledTools` blocklists, and user/folder/project configuration. `/mcp` shows connection status, tools, authentication, and enable/disable controls ([MCP configuration](https://docs.factory.ai/cli/configuration/mcp)). Org policy can restrict servers/tools. Custom droids can allowlist whole MCP servers or exact MCP tool IDs ([Subagents](https://docs.factory.ai/cli/configuration/custom-droids)).

The sandbox drops ambient environment variables for local MCP servers, keeping a safe allowlist plus explicitly configured keys, and mediates MCP filesystem/network requests ([Sandbox](https://docs.factory.ai/cli/configuration/sandbox)).

Recent release notes show active reliability work: stdio connect timeouts rather than hangs (July 13), silent token refresh and duplicate-auth prevention (July 14), explicit connection status (June 14), surfaced parse errors (June 25), and multiple OAuth fixes ([release notes](https://docs.factory.ai/changelog/release-notes)). This is meaningful because the owner's worst MCP has 135 “not connected” failures yet remains callable.

Factory's Deferred Context Engine is stronger than static schema injection. It does not, however, document an automatic error-rate circuit breaker that quarantines a repeatedly failing server. Do not infer one.

### What is worse

Factory's MCP examples include `npx -y` and warn users to pin versions. A live “latest” package install is a supply-chain risk and is inappropriate for this owner's high-trust harness ([MCP configuration](https://docs.factory.ai/cli/configuration/mcp)).

The SDK's structured output uses JSON Schema and leaves validation to the caller ([SDK README](https://github.com/Factory-AI/droid-sdk-typescript)). Nothing inspected demonstrates a lenient repair loop superior to the owner's 22.9% StructuredOutput error rate; do not credit Factory with one.

### Ports

#### CONFIG (settings/JSON only) — disable dead MCPs and expose only used tools

Immediately represent unavailable servers as disabled and apply per-server tool allowlists. Keep configuration entries for recoverability; do not delete them. This is **almost certain (90-99%)** to prevent calls to a known-disabled server because removal from the model's tool surface makes selection impossible; evidence is the pinned 135 Tavily “not connected” fingerprint and Factory's documented disabled/enabled-tool semantics. Validate with two signals: `/mcp` or provider status must show disabled, and a capability listing must omit the tool while a known-live MCP remains discoverable.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — health-driven MCP quarantine

Use the existing dispatcher/event ledger to count terminal connection/auth/timeout fingerprints per server. After a small threshold across distinct calls, inject “server unavailable; use fallback X” and suppress its routing hint for the session; restore only after a cheap explicit health probe succeeds. Do not silently delete config or retry indefinitely.

It is **very likely (80-90%)** to eliminate repeated dead-server calls because the failure is stable and explicit. Experiment: replay the 135 Tavily failure fingerprint stream and require one initial failure, one independent health check, zero later selections, and successful discovery of a known-live control. This directly follows the mandatory two-signal rule.

## 5. Permission model and sandbox

### Factory mechanism

Factory separates interaction mode from autonomy. Off permits reads/allowlisted commands; Low adds edits and low-risk commands/MCP; Medium adds reversible workspace changes such as installs/builds/local commits; High permits higher-risk actions unless a denylist or sandbox check intervenes. Denylisted commands require approval; blocklisted commands can never run, even through wrapper shells, absolute paths, quoting, command substitution, or unsafe skip flags. Org policy caps autonomy and accumulates non-weakening restrictions ([Autonomy Level](https://docs.factory.ai/cli/user-guides/auto-run); [Hierarchical Settings](https://docs.factory.ai/enterprise/hierarchical-settings-and-org-control)).

Its beta OS sandbox uses macOS Seatbelt or Linux/WSL2 bubblewrap+seccomp, plus a filtering proxy. Default write policy is CWD-only; network is deny-by-default except Factory domains; whole-process mode includes MCP, hooks, and subagents and refuses to start if isolation cannot be established. Interactive violations allow once/always/deny; headless violations auto-deny ([Sandbox](https://docs.factory.ai/cli/configuration/sandbox)). Native Windows—not WSL2—is not listed, a material limitation for this owner.

Droid Shield scans added diff lines before Droid-driven commits/pushes, with deterministic patterns plus randomness/context checks. Shield 2.0 is a research preview using a recall-oriented risk model and a downgrade model for false positives ([Droid Shield](https://docs.factory.ai/cli/account/droid-shield)). Shield only covers git operations performed through Droid, and manual git bypass remains possible.

### Relative verdict

Factory's layered mental model is cleaner than this job's Codex configuration, which is `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`config.toml:6-7`). Its command resolver is also a better discriminator than naive payload regex. That matters because the pinned D1 defect documents four guard implementations confusing mention with use, including a successful result marked failed.

Factory is worse for native Windows kernel isolation and potentially worse if Shield's learned models are treated as a guarantee; its own docs call them preview and retain manual bypass.

### Ports

#### UNVERIFIED — NATIVE (Claude Code already does this; we just enable it) — least-privilege native sandbox for risky sessions

**UNVERIFIED:** Claude Code's currently installed Windows build may not provide every filesystem/network control Factory documents; the settling experiment is the disposable allow/deny probe below. Enable the provider's existing sandbox/approval boundary for untrusted repositories and networked tool use, rather than building a guardrail framework. Use CWD-only writes, explicit secret-path read denies, and narrow network domains; keep whole-machine reverse engineering workflows on an explicit trusted profile. It is **very likely (80-90%)** to reduce blast radius because enforcement occurs below model reasoning, while uncertainty comes from Windows/provider-specific coverage. Settling experiment: in a disposable repo, verify a known-allowed CWD write and known-allowed domain, then independently verify denial of an out-of-scope write and disallowed domain.

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — semantic command discriminator shared by guards

Canonicalize the actual executable, arguments, target paths, tool verb, and result success fields before policy matching. Never scan Markdown prose as executable input. This proposal agrees with pinned defect D1 and copies Factory's useful “resolve actual program before blocklist” idea, not its product. It is **very likely (80-90%)** to eliminate the recorded use-versus-mention false positives because all recorded cases differ at exactly those typed fields. Re-run every recorded false fire plus known-dangerous positive controls before enabling.

## 6. Customization: rules, skills, hooks, commands, plugins

Factory's hierarchy is coherent:

- **AGENTS.md:** nearest applicable file wins, with personal `~/.factory/AGENTS.md`; loaded before planning ([AGENTS.md](https://docs.factory.ai/cli/configuration/agents-md)).
- **Skills:** `SKILL.md` plus supporting assets; user- and model-invocable by default; frontmatter can make a skill user-only (`disable-model-invocation`) or model-only (`user-invocable: false`); legacy commands are merged into skills ([Skills](https://docs.factory.ai/cli/configuration/skills)).
- **Commands:** Markdown prompt macros or shebang executables; executable output and source are added to the transcript, capped at 64 KB ([Custom Slash Commands](https://docs.factory.ai/cli/configuration/custom-slash-commands)).
- **Hooks:** Pre/PostToolUse, UserPromptSubmit, Notification, Stop, SubagentStop, PreCompact, SessionStart/End; JSON stdin includes tool verb/input/response and transcript path; hooks can allow/ask/deny, modify tool input, inject context, or force continuation. Multiple hooks run in parallel ([Hooks reference](https://docs.factory.ai/reference/hooks-reference)).
- **Plugins:** shareable bundles of skills, commands, tools and hooks; org policy can restrict marketplaces ([Factory 1.10](https://docs.factory.ai/changelog/1-10); [release notes](https://docs.factory.ai/changelog/release-notes)).
- **Custom droids:** Markdown system prompts with model, reasoning effort, tools, MCP servers, and autonomy; Factory can import Claude Code agents and commands ([Subagents](https://docs.factory.ai/cli/configuration/custom-droids)).

### Relative verdict

Capability breadth is mostly parity. Factory's best detail is invocation authority on skills and explicit MCP allowlists per subagent. Its hierarchy/UI/import experience is cleaner than a large manually accumulated tree.

Factory is not proven more reliable. Its July releases fixed hooks running more than once, plugin loading across scopes, stale concurrent settings writes, hung SessionStart behavior, hook merging, and Windows quoting ([release notes](https://docs.factory.ai/changelog/release-notes)). Those are warnings against copying implementation complexity. The owner's hook telemetry is currently unmeasurable because its detector is broken; no comparative hook reliability rate can be claimed.

### Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — capability manifest with invocation authority

Add normalized metadata to the existing catalog: `user_invocable`, `model_invocable`, side-effect class, required MCPs, known platform, and last validated date. Generate a compact discovery index and reject auto-invocation for deploy/send/destructive workflows. It is **likely (55-80%)** to reduce accidental or irrelevant capability selection because Factory's controls directly shrink who may invoke what, and the owner's corpus shows only 78/355 skills used. Experiment: compare tool/skill selection precision on 50 historical prompts before and after metadata filtering.

Do not import Factory's plugin marketplace or create another installer. The owner already has plugin-directory bloat severe enough to trigger Windows ENAMETOOLONG; copying another packaging layer would amplify a measured failure.

## 7. Multi-agent support

Factory's ordinary `Task` subagents are isolated and non-interactive. Built-ins include a read-only `explorer` and all-tool `worker`; custom agents can run foreground/background, be polled/stopped, and resumed with full prior context. A subagent cannot ask the user or spawn another subagent. Model selection resolves explicit model → complexity tier → parent; invalid/disallowed models fall back to parent. Autonomy is independently configured but clamped to the org maximum ([Subagents](https://docs.factory.ai/cli/configuration/custom-droids)).

This is a good bounded design. The inability to nest prevents uncontrolled recursive fanout, while resumption avoids restarting a focused investigation.

Missions sits above this with orchestrator/worker/validator roles and externalized shared state. It is sequential by feature according to the architecture post; Factory openly says whether parallelization is necessary remains an open question ([Missions overview](https://docs.factory.ai/features/missions/overview); [Missions architecture](https://factory.ai/news/missions-architecture)).

### Relative verdict

The owner's native multi-agent supports deeper nesting (depth eight) and eight concurrent threads (`config.toml:77-80,125-130`), so Factory's ordinary subagents are not a wholesale advantage. Factory is better in documented per-agent model/autonomy/MCP restriction and explicit implementer-versus-validator incentives. Factory is worse in nesting flexibility and Missions overhead.

### Port

#### BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — per-role least-privilege profiles

Define three profiles on the existing agent bus: explorer (read/search only), implementer (scoped edits/execute, no deployment MCP), validator (read/execute/browser, no edits). Pass only task-relevant MCPs. It is **very likely (80-90%)** to reduce blast radius and context noise because Factory's mechanism is a direct allowlist and this owner already has the agent runtime. Validate by known-present allowed tools and known-denied disallowed tools for each profile; do not infer from an empty detector result.

## 8. Verification and self-check mechanisms

## Bottom line

Factory's frontier contribution is disciplined **context shaping**: delay irrelevant capability schemas, constrain each agent to one incentive, externalize only the shared state each role needs, define correctness before implementation, and validate with fresh black-box agents. Those ideas are portable.

Its full product architecture is not. The owner already has richer durable memory, broader native multi-agent capability, extensive hooks/rules, and a provider-neutral contract. The correct move is a small extraction onto the existing bus: disable dead tools, measure compaction with functional probes, add validation contracts and genuinely fresh least-privilege validators, and test provider-native deferred loading. A Factory replacement or Missions clone would add cost and a second runtime without evidence that those additions cause the benefit.
