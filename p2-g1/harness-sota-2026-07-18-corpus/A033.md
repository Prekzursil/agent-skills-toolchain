## Collision register

### A033-C01 — `CONTRADICTION`: functional-options mutation versus universal immutability

**Artifacts and exact lines**

* `~/.claude/rules/golang/patterns.md:14-18`: `Option` receives `*Server`; `WithPort` executes `s.port = port`.
* `~/.claude/rules/golang/patterns.md:20-25`: `NewServer` creates `s`, then each option mutates it with `opt(s)`.
* `~/.claude/rules/common/coding-style.md:23-31`: “ALWAYS create new objects, NEVER mutate existing ones”; the stated correct form returns a new copy.
* The common rule applies to Go through its frontmatter at `common/coding-style.md:1-9`, specifically `**/*.go` at line 8.

**Why this collides**

The functional-option closure mutates the existing server object passed to it. The common rule says never to do exactly that. This is not a merely different threshold. Both files apply to the same `.go` edit, and section 10 supplies no same-level winner.

The common blanket is also at odds with ordinary Go pointer semantics. The official Go review guidance explicitly discusses cases in which a method that needs to mutate a receiver must use a pointer receiver. That does not mandate mutation, but it demonstrates that “never mutate” is not a coherent universal Go rule: <https://go.dev/wiki/CodeReviewComments#receiver-type>.

**Specific resolution — `NATIVE (Claude Code already does this; we just enable it)` value: use the existing path-scoped rule bus and edit rule text only.** Replace `common/coding-style.md:23-33` with a scoped policy such as: “Prefer immutable values at boundaries and for shared state. Controlled mutation during construction and methods on stateful Go pointer receivers are allowed; avoid hidden aliasing and document concurrency.” In the target, say explicitly that options mutate only a not-yet-published instance during construction. Do not create a hook for this semantic distinction.

**Confidence:** almost certain (90-99%), supported by the literal assignment at target line 17, the universal prohibition at common lines 25-30, and both files’ `.go` scope. The remaining 1-10% is only the possibility that Claude’s undocumented rule loader treats a language-specific file as an implicit override; `AGENTS.md` does not say that.

### A033-C02 — `REDUNDANCY`: interface policy is split across two Go rules with different precision

**Artifacts and exact lines**

* `~/.claude/rules/golang/patterns.md:29-31`: heading “Small Interfaces,” then consumer-side interface ownership.
* `~/.claude/rules/golang/coding-style.md:15-18`: “Accept interfaces, return structs” and “Keep interfaces small (1-3 methods).”

**Why this collides**

Both files govern interface design for the same Go paths (`patterns.md:1-5`; `coding-style.md:1-5`). One defines location but not a size threshold; the other defines a 1-3 method threshold and return-type policy but not location. They are compatible in a favorable case, yet the duplicated policy surface can drift and already answers “small” differently: qualitative in one place, hard numeric in another.

The official Go review guidance supports consumer ownership and concrete producer returns, but does not impose a universal 1-3 method cap: <https://go.dev/wiki/CodeReviewComments#interfaces>. This makes the numeric threshold a local heuristic, not an authoritative Go limit.

**Specific resolution — `NATIVE (Claude Code already does this; we just enable it)` value: consolidate all interface design guidance in the existing `golang/patterns.md` path-scoped rule and leave one pointer in `coding-style.md`.** Preferred canonical wording: “Define an interface only when a consumer needs one; keep it to the methods that consumer uses; producer packages return concrete types. Treat 1-3 methods as a review heuristic, not a validity gate.” This preserves useful specificity without falsely invalidating legitimate larger standard-library-style contracts.

**Confidence:** almost certain (90-99%), supported by the two quoted local rules and the official Go interface guidance. The proposed wording explicitly demotes the local “1-3” number to a heuristic because the cited official guidance supplies no universal numeric cap.

## Consolidated replacement text recommendation

The preferred resolution is evolution of the existing path-scoped rule, not a new framework. A compact replacement would say, in substance:

> Define interfaces in the consuming package, only when a consumer needs abstraction; producer packages return concrete types. Keep interfaces limited to consumer-used methods (1-3 is a heuristic, not a cap). Inject external collaborators through constructors. Use functional options for public constructors with a growing set of truly optional settings; for a small stable set, prefer explicit parameters or a config struct. Options may mutate the private instance during construction, before publication; validate invalid combinations and define duplicate-option behavior.

This replacement is aligned with the official Go interface guidance and module compatibility tradeoff discussion cited above. It also resolves C01-C03 without adding runtime complexity.
