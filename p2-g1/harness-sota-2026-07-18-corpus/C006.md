# C006 — Context lifecycle: semantic memory versus event ledger

## Executive verdict

The current *physical* split is directionally correct, but the stated *semantic* split is not.
Keeping two substrates is justified:

1. an append-only, bounded-replay evidence log for recent operations, receipts, active-session state,
   failures, and causal pointers; and
2. a cross-session, cross-provider, human-editable knowledge vault for curated facts, decisions,
   preferences, procedures, and synthesized lessons.

Calling the first “objective” and the second “semantic” hides the real defects. The event ledger is
not purely objective: its `decision`, `failure`, `goal`, and `milestone` records are prose supplied by
an agent or hook (`claude/hooks/event-ledger/note.py:2-12,25-42`), while its automatic Task/Stop
records retain hashes rather than the asserted content (`agents/harness/modules.py:1218-1255`). Basic
Memory is not purely semantic: the vault-derived index contains checkpoints, session handoffs,
failures, outcomes, and provider auto-memory mirrors in addition to durable facts. In the bundled
index, 106/621 entries match “compaction,” 116/621 match “checkpoint,” 17/621 match “decision,” and
8/621 match “failure” (command output, `python` bounded inventory of
`claude/hooks/recall-inject/index/recall_index.json`, 2026-07-19). Those categories overlap the
ledger directly.

The better boundary is therefore **evidence log versus curated knowledge**, with five explicit
dimensions on every record: **origin, authority, scope, temporal validity, and lineage**. Promotion
from evidence to knowledge must be explicit and receipt-linked. Retrieval must be query-specific.
Neither store should silently certify the other.

This conclusion is **very likely (80-90%)**, supported by the implemented writers/readers, the
vault-derived 621-note index, and corpus-wide Basic Memory use. It is not “almost certain” because
the current `D:\basic-memory` vault and live ledger data were not included on this Linux node; a
current content-level overlap/conflict audit on the Windows host is required to measure the true
duplicate and contradiction rates.

## What the two systems actually are

### Event ledger: a hybrid evidence/event stream plus narrative annotations

Automatic shared-ledger events include:

- `tool_result`: provider, turn ID, tool name, result hash, and a derived verification flag;
  receipt classification can add class/status/pass/fail/fingerprint
  (`agents/harness/modules.py:1048-1077`).
- `mutation`: provider, turn ID, redacted path, tool, and optional canonical-tree classification
  (`agents/harness/modules.py:1090-1142`).
- native tool failures: stored as negative `tool_result` events with `verified=False`
  (`agents/harness/modules.py:1171-1194`).
- instruction-load, task-completion, turn, and subagent lifecycle records, primarily as hashes and
  small enums (`agents/harness/modules.py:1196-1276`).
- append serialization with monotonic sequence, UTC timestamp, sanitization, file flush, and
  `fsync` (`agents/harness/ledger.py:817-880`).

Narrative ledger events include goals, decisions, failures with preconditions, and milestones with
superseded failure sequence numbers. They are explicitly entered through `note.py`
(`claude/hooks/event-ledger/note.py:25-42`) and projected into bounded current state
(`agents/harness/ledger.py:701-759`). Those strings are valuable, but they are propositions, not
objective ground truth. A milestone can tombstone a failure because an agent named its sequence;
that transition is mechanically recorded, but the truth of the milestone text is not mechanically
established by the annotation itself.

Recovery is bounded and selective. On `resume`, `compact`, or `clear`, the shared harness reads 20
recent project events, injects at most the last 12 decisions/failures/milestones, and obtains the
active goal from a session-specific sidecar (`agents/harness/modules.py:973-1003`). Fresh startup
does not replay this path. Reads are capped to at most 200 events
(`agents/harness/ledger.py:882-907`).

The ledger is thus best understood as a **recent, append-only evidence spine with mixed-authority
annotations and materialized state**, not a complete record of the conversation and not a truth
oracle.

### Basic Memory: a curated knowledge vault plus mixed-origin imports and checkpoints

Basic Memory's current official architecture is file-first Markdown, with a database as a secondary
query/index layer and MCP/CLI access; its files form a searchable linked knowledge format
([technical architecture](https://docs.basicmemory.com/reference/technical-information),
[knowledge format](https://docs.basicmemory.com/concepts/knowledge-format)). That makes it a good
human-auditable canonical knowledge surface.

Locally, however, “Basic Memory” is at least three operational layers:

1. the live MCP/CLI vault (not mounted here);
2. a separate automatic local lexical materialized view consumed by `RecallModule`; and
3. compaction checkpoint Markdown written under the vault or harness state directory.

The materialized view is not semantic search. It tokenizes prompt/title/permalink/keywords, applies
a high relevance threshold, returns at most five notes, suppresses repeat permalinks per session,
and caps injection to 2,400 characters (`agents/harness/modules.py:1572-1681`). This is a small,
automatic lexical hint cache over Basic Memory. On-demand MCP search is the deeper retrieval lane.

The checkpoint writer is also hybrid. At PreCompact it writes a redacted Markdown document with
ledger pointer, goal, last ten decisions, last ten unresolved failures, and `.remember/now.md`, then
retains at most 100 checkpoint files (`agents/harness/modules.py:1440-1528`). It therefore copies a
projection of ledger state into the memory/checkpoint surface. This overlap is intentional for
compaction recovery, but it needs lineage and retention semantics to avoid later being mistaken for
current knowledge.

## Where they overlap

### 1. Decisions, failures, and milestones

Both stores can hold the same semantic claim. The ledger's manual annotation CLI exists specifically
for decisions, failures, goals, and milestones. The vault-derived index contains notes matching
those concepts. The checkpoint writer copies ledger decisions/failures into Markdown. There is no
required stable identifier tying a memory note back to the ledger events and receipts that justify
it.

This overlap is useful only if it is a **projection/promotion relation**:

- ledger event = what was attempted/observed, by whom, in what scope, with what receipt;
- knowledge note = the current interpretation or reusable lesson, linked to its source events;
- superseding knowledge note = new current interpretation, without rewriting historical events.

Without that relation, the same prose can be edited in the vault, tombstoned in one ledger, remain
open in another ledger generation, and still surface from a stale lexical index.

### 2. Compaction checkpoints

The checkpoint is a recovery projection, not durable truth. It combines ledger state and a local
`.remember` file, labels the latter untrusted, and includes a ledger pointer
(`agents/harness/modules.py:1462-1517`). Yet the bundled legacy index contains 106 compaction-matching
entries and 116 checkpoint-matching entries. The current schema-2 builder excludes a directory named
`compaction-checkpoints` (`agents/harness/recall_index.py:46,260-266`), while the old snapshot also
contains checkpoint paths under other names such as `checkpoints/`; directory-name exclusion alone
does not express record semantics.

### 3. Provider-native auto-memory mirrored into the vault

The vault-derived index has 148/621 records whose serialized entry matches `claude-memory` (bounded
inventory, 2026-07-19). These include preferences, handoffs, lessons, and session state. Claude's
current official documentation says auto memory is model-written, per repository, loaded at every
conversation through a bounded `MEMORY.md`, and intended for discovered build commands, debugging
insights, architecture notes, and preferences
([Claude Code memory](https://code.claude.com/docs/en/memory)). Mirroring that leaf cache into the
cross-provider canonical vault, and then lexically reinjecting it, can duplicate and elevate
model-authored claims.

The index proves structural overlap, not semantic identity. **UNVERIFIED: the percentage of mirrored
notes that are exact or meaning-equivalent duplicates is unknown; the settling experiment is a
content-normalized hash plus blinded semantic-dedup pass over the live native memory directories and
their vault mirror before any deletion.**

### 4. “Current state”

The ledger materializes active goal, decisions, and open failures. Basic Memory supports durable
current facts and temporal metadata conventions. These are different time horizons, but no admission
rule prevents a volatile status (“server is down,” “branch is X,” “offset is Y”) from becoming an
unexpiring semantic note. Conversely, a durable project decision in the bounded ledger can age out
of replay before being promoted to memory.

## Where they disagree

### 1. The authority claim disagrees with the writers

The contract says “trust [ledger] replay as ground truth” and calls Basic Memory semantic
(`claude/AGENTS.md:20-25,64-68`). But manual ledger text is authored by the same model whose semantic
notes are treated as lower-authority narrative. Automatic Stop/Task entries store hashes, not the
content needed to independently reconstruct the assertion. “Append-only” proves that a claim was
recorded; it does not prove that the claim was true.

Correct authority rule:

- a typed, fresh receipt is high-authority evidence for the narrow predicate it measured;
- a tool call without a result is an attempt;
- a user instruction is high-authority intent, not proof of environmental state;
- an agent annotation is a hypothesis/interpretation until linked to evidence;
- a memory note is curated current knowledge only within its declared scope and validity window;
- a compacted summary or checkpoint is orientation, never certification.

### 2. Supersession semantics disagree

Ledger failures are retired when a milestone contains `supersedes_failures` sequence numbers
(`agents/harness/ledger.py:740-747`). The documented Basic Memory convention puts
`superseded_by: <new permalink>` on the old note (`codex/AGENTS.md:83-85`). But `RecallModule`
currently labels a note with `superseded_by` as a contradiction and multiplies its score by 1.6
(`agents/harness/modules.py:1666-1673,1693-1710`). Thus the documented old note is preferentially
ranked. The builder's comments define a *current head* as a note that supersedes older notes and is
not itself superseded (`agents/harness/recall_index.py:222-248`), so the ranker and builder encode
opposite meanings for the same field.

This defect is established by two mechanically independent signals: the contract's field direction
and the code's score direction. The bundled index cannot reveal live impact because it predates the
field and contains zero `superseded_by` entries.

### 3. Scope semantics disagree

The recovery replay draws durable annotations from the shared canonical project but gets the active
goal from a strict session sidecar (`agents/harness/modules.py:973-1003`). Basic Memory notes can be
global, project, folder, provider-mirror, or checkpoint records, but the local index flattens them
into one candidate list and relies on relevance/path exclusions rather than a required scope field
(`agents/harness/modules.py:1623-1650`). A valid decision from audit unit A can therefore be eligible
in unit B if they share project vocabulary, even if it was session-local.

The current shared ledger also uses `session_id` in dedupe keys but does not persist it in the
`tool_result` or `mutation` fields (`agents/harness/modules.py:1048-1077,1103-1142`). This is a direct
code-level loss of scope. Audit B15 reports live mixed-provider records with the same omission, but
that host measurement is treated here as corroborating audit evidence, not independently verified
fact.

### 4. Freshness semantics disagree

The event ledger is append-current and replay-bounded. The lexical view is an asynchronously built
snapshot. The bundled snapshot is eight days older than the corpus cutoff and lacks current schema
fields. `RecallModule._notes()` returns the first structurally valid index and performs no age,
schema, or vault-hash check (`agents/harness/modules.py:1600-1606`). A present stale index can
silently outrank a later canonical note.

Audit E04 claims the live deployed shared index was schema 1 from July 11 while the vault had July 18
notes. That specific Windows measurement is **UNVERIFIED here; the settling experiment is to compare
the live index `schema_version`, `built_at`, and `vault_hash` against the current builder version and
a fresh read-only vault fingerprint, then insert a disposable canary note and observe bounded
rebuild-to-recall latency.** The bundled snapshot plus missing runtime freshness check make the risk
real even without adopting the audit's live count.

### 5. Write success semantics disagree

The ledger can record a Basic Memory tool result, while the memory spool may later replay the
intended write directly. A lost response is ambiguous: the original write may have committed even
though the caller saw failure. `write_note --overwrite` is replayed as idempotent, but `edit_note` is
left pending because append/prepend can double-apply (`claude/hooks/memory-spool/replay.py:9-20`).
Neither substrate supplies one cross-store transaction saying “event E promoted note N at revision
R, and N's current content hash is H.”

## Gaps neither system covers

### Gap A — question-scoped access to original chronology

The ledger stores hashes and bounded receipts, not the underlying message/tool-result content. Basic
Memory stores selected syntheses, not a complete event sequence. When a later agent asks “what exact
command produced this conclusion, and was it later reverted?”, neither can answer reliably.

This is not an argument for copying transcripts into a new database. Native transcripts already
exist outside the two stores. The missing capability is a bounded, read-only, question-led resolver
that locates the native session, searches relevant slices, follows later revisions/reverts, and
returns redacted citations. Audit D17 independently identifies this gap, while the local shared
ledger's hash-only writers establish why it exists (`agents/harness/modules.py:1218-1255`).

### Gap B — causal promotion and invalidation

There is no required chain:

`failure event -> evidence/receipt -> candidate lesson -> promoted memory/rule -> later outcome -> supersession`.

The shared ledger accepts optional `derived_from` fields, but the ordinary append sites shown above
do not populate a lesson identity. Task/turn events hash output. Memory writes are not required to
carry source event IDs. As a result, the system cannot measure whether a remembered lesson reduced
recurrence or identify all downstream notes/rules when its source evidence is invalidated.

### Gap C — explicit authority and conflict resolution

Neither store requires `origin`, `authority`, `scope`, `valid_from`, `valid_until`, `status`, and
`source_refs` together. A stale model-authored auto-memory note, a user-approved decision, a tool
receipt, and a compacted checkpoint can all surface as prose without a common precedence resolver.
The local lexical banner correctly calls summaries untrusted historical context
(`agents/harness/modules.py:1656-1681`), but it does not show why a note is current or which receipt
supports it.

### Gap D — measured lifecycle policy

Neither live-store retention nor retrieval usage is represented in the supplied corpus. The ledger
operationally reads bounded tails, but append dedupe scans every compatible event file for matching
event IDs (`agents/harness/ledger.py:611-630,841-849`). Basic Memory notes are editable/deletable,
but no measured retention or archival policy is available here. Exact TTLs would be invented.

**UNVERIFIED: safe hot/warm/cold horizons are unknown; the settling experiment is a seven-day
read-only access trace recording event/note age at retrieval, query latency, bytes scanned, result
selection, and later use, followed by a replay test from proposed compacted state.**

### Gap E — outcome-level memory evaluation

Tool-call counts say that memory is used; they do not say it helps. No supplied evaluator labels a
retrieved note current, relevant, obeyed, or causally useful. The owner-correction field cannot fill
this gap: its own `precision_warning` says a smoke sample had 41/41 false positives. Any claim that
memory is improving outcomes would therefore be unevidenced.

### Gap F — procedural knowledge has no single owner

Current memory research distinguishes semantic facts, episodic experiences, and procedural rules;
LangGraph's official overview makes the same distinction and separately distinguishes thread state
from cross-thread stores ([memory overview](https://docs.langchain.com/oss/python/concepts/memory),
[persistence](https://docs.langchain.com/oss/python/langgraph/persistence)). Locally, procedures can
appear in Basic Memory, CLAUDE/AGENTS rules, skills, provider auto-memory, or ledger decisions.
Executable procedures should live in tested skills/rules; Basic Memory should hold rationale and
discovery pointers; the ledger should hold executions and receipts. The missing link is provenance,
not another procedural-memory service.

## Target architecture

### One evidence spine, one knowledge vault, native transcripts in place

```text
native hook/tool events
        |
        v
append-only evidence ledger  ----pointer----> native transcript slices (read in place)
  - attempt/result/receipt                         ^
  - session + project scope                        | question-scoped resolver
  - goal + annotations                             |
  - causal/source IDs                              |
        |
        | explicit reviewed or policy-gated promotion
        v
Basic Memory canonical knowledge vault
  - current facts / decisions / preferences
  - reusable lessons + rationale
  - validity + supersession + source_refs
        |
        +--> bounded lexical materialized view (automatic hints; rebuildable)
        +--> on-demand MCP search/read/build_context (semantic depth)

provider auto-memory = non-canonical leaf cache; never mirrored wholesale
compaction checkpoint = ephemeral recovery projection; never a current-fact head
skills/rules = tested procedural layer; link back to rationale/evidence
```

This design mirrors the useful part of current systems without importing their runtimes. LangGraph
separates thread checkpoints from cross-thread Store memory; Basic Memory is already a file-first
knowledge store; Microsoft's event-sourcing guidance treats append-only history and query-optimized
materialized views as distinct and explicitly warns that full event sourcing adds substantial
complexity. The local harness already has all three minimal buses: hooks, an append-only JSONL
ledger, and Basic Memory MCP/Markdown.

## Proposals, prioritized

### P0 — Correct the authority contract and record class taxonomy

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Configure the existing hook/module policy so each
injected record is labeled as one of `receipt`, `attempt`, `user_intent`, `annotation`,
`curated_knowledge`, or `checkpoint`, and stop presenting the whole ledger as “objective ground
truth.” The rendered replay should say “append-only evidence and annotations”; only fresh typed
receipts should use verification language. Documentation must mirror the configured taxonomy, but
no new runtime is required.

This is **almost certain (90-99%)** to reduce authority confusion because the contradiction is
field-level and deterministic: manual annotations and hash-only automatic events are currently
rendered under one ground-truth banner (`modules.py:991-1002`; `note.py:2-12`). It does not claim an
outcome effect; P8 measures that.

### P1 — Persist scope, origin, and lineage on the existing ledger bus

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add sanitized
fields to the existing normalized event and persisted record:

- `project_id`, hashed `session_id`, `provider`, `turn_id`;
- `origin` (`hook`, `user`, `agent`, `tool`, `import`);
- `scope` (`session`, `project`, `user`, `global`);
- stable `event_id`, `parent_event_id`, and `source_refs`;
- `authority_class` and `assertion_status` (`attempted`, `observed`, `verified`, `hypothesis`,
  `superseded`).

Default active goals and transient failures to session scope; require an explicit project scope for
cross-session replay. Keep secret/path redaction and the current lock/fsync append path.

This is **very likely (80-90%)** to eliminate the demonstrated structural ambiguity because
`session_id` is presently used for dedupe but omitted from stored result/mutation fields
(`modules.py:1048-1077,1103-1142`). Residual uncertainty is provider payload completeness; a
two-provider fixture with distinct sessions, conflicting goals, and independent receipts must prove
isolation before enforcement.

### P2 — Make promotion a link, not a copy

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the
existing Basic Memory write path with optional required metadata for durable operational notes:

- `source_refs: [ledger:event_id...]`;
- `origin` and `scope`;
- `valid_as_of` and, for volatile facts, `recheck_after` or `valid_until`;
- `supersedes` on the new note and `superseded_by` on the old note;
- `evidence_status` (`user-approved`, `receipt-backed`, `hypothesis`, `imported`).

Do not auto-summarize every event. Promote only user-requested facts, durable decisions, reviewed
repeated failures, and verified milestones. The ledger remains immutable; the note is the editable
current head; each can locate the other.

This is **likely (55-80%)** to reduce stale re-walking and make memory auditable, based on the
existing supersession convention, current ledger IDs/hashes, and the observed write volume. The
wide band reflects the unmeasured live note-quality baseline. The P8 A/B replay settles benefit and
false-promotion cost.

### P3 — Fix current-head recall before rebuilding the index

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** In the existing
lexical materialized view:

1. suppress notes with `superseded_by` from ordinary recall;
2. resolve and display the replacement permalink when available;
3. boost only unresolved failure heads or the newest unsuperseded note;
4. refuse an index whose schema is older than the consumer's minimum;
5. compare `vault_hash`/build timestamp to a cheap freshness marker and emit no recall rather than
   stale recall when invalid;
6. classify checkpoint records by `type`, not directory spelling, and exclude them from ordinary
   semantic recall.

This is **almost certain (90-99%)** to fix the direction error because the documented old-note field
currently receives a literal 1.6 multiplier (`modules.py:1693-1710`). It is **likely (55-80%)** to
improve live retrieval quality, conditional on live usage of schema-2 metadata; that premise is
UNVERIFIED and is settled by the disposable old/new-note recall test described in the freshness
section.

### P4 — Keep semantic recovery dual-mode, but make the checkpoint route deterministic

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On
resume/compact/clear:

- inject the scoped ledger tail and active goal synchronously;
- inject the exact latest session checkpoint pointer, not checkpoint prose selected by semantic
  similarity;
- perform Basic Memory search/build-context only when the resumed prompt or checkpoint identifies
  missing durable context;
- fall back to the fresh lexical view when the MCP is unavailable;
- display source, scope, validity, and permalink for every recalled note.

Do not call broad semantic search on every fresh startup. The corpus shows only 11 `build_context`
calls versus 357 `search_notes` calls, and search has observed connection/schema failures. Bounded
relevance-triggered recall preserves the minimal context path.

This is **likely (55-80%)** to improve post-compaction continuity because current recovery only
injects ledger annotations while Basic Memory is prose-advisory (`codex/AGENTS.md:81-85`;
`modules.py:973-1003`). The runtime rate of missed post-compaction recall is UNVERIFIED; a controlled
four-arm compact/resume test (ledger only, checkpoint pointer, lexical recall, MCP build-context)
must measure recovery correctness, latency, and tokens.

### P5 — Complete the Basic Memory write receipt/outbox

Idempotent create/overwrite can self-heal; append/prepend/edit remains pending until a compare-and-set

This is **very likely (80-90%)** to reduce ambiguous duplicate/lost memory updates because the corpus

## Anti-overfit gate

All proposals ride the existing hook, JSONL ledger, skill, native transcript, or Basic Memory MCP
bus. None adds:

- a second orchestration runtime;
- a new vector database or knowledge graph;
- a durable-execution engine;
- a trained critic;
- an observability SaaS; or
- a guardrail framework.

I explicitly reject replacing the two stores with LangGraph, Mem0, a new event-store service, or a
new transcript warehouse. LangGraph's Store/checkpointer split is useful evidence for *separation of
scope*, not a reason to import its runtime. Basic Memory already supplies the inspectable knowledge
store and secondary index. The existing ledger already supplies append-only events and projections.
Microsoft's current event-sourcing guidance warns that event sourcing changes concurrency, schema,
query, and migration complexity and is warranted only where reconstruction/audit benefit justifies
it ([Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)).
The newest directly relevant benchmark evidence also argues against architecture-by-fashion: the ACL
2026 paper [Does Memory Need Graphs?](https://aclanthology.org/2026.acl-long.1232.pdf) reports that
graph indexing can improve retrieval while failing to improve—and in some configurations reducing—
downstream answer accuracy because fragmented or temporally noisy context distracts the answerer
(paper pp. 7, 17-19). That is evidence for outcome evaluation and information-dense notes, not for
adding another graph layer.

Full replacement is therefore not supported by current evidence. This is **very likely (80-90%)**:
the observed failures are authority, scope, freshness, lineage, and evaluation failures at the seam,
not absence of storage/retrieval substrates. A replacement becomes justified only if P8 shows that
fresh, correctly scoped Basic Memory retrieval plus ledger evidence still underperforms a tested
alternative by a predeclared outcome margin after equal token/latency budgets.

## Direct answer to the unit question

**Is “Basic Memory is semantic; event ledger is objective” correct?** No. It is a useful mnemonic
for intended roles but an inaccurate system invariant. The ledger mixes objective-ish receipts with
agent-authored semantic annotations; Basic Memory mixes curated knowledge with episodic checkpoints,
failures, handoffs, and provider-generated notes.

**Where do they overlap?** Decisions, failures, milestones, current state, compaction checkpoints,
session handoffs, and learned procedures. The overlap currently behaves as duplication because it
lacks required cross-store lineage and one shared supersession model.

**Where do they disagree?** Authority language, scope, freshness, supersession direction, write
confirmation, and provider startup behavior. The most concrete contradiction is that an old Basic
Memory note carrying `superseded_by` is currently boosted by the lexical ranker.

**What does neither cover?** Exact question-scoped original chronology, causal promotion/invalidation,
uniform authority/conflict adjudication, measured retention, and outcome-level memory evaluation.

**What should replace the rule?** “The ledger is the append-only evidence spine; Basic Memory is the
curated current-knowledge vault; native transcripts remain the underlying session record; every
promotion is scoped, validity-bounded, and linked to evidence.”
