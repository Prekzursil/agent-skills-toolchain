# F031 — red team: shared secrets → execute code

## Executive verdict

The most plausible chain is an indirect-prompt-injection or compromised-agent turn in Claude Code reading an ambient cloud-compute credential (especially a `RUNPOD_API_KEY`/Modal-class credential) from the process environment, transmitting it through an already allowed network sink, and the external attacker then using that provider credential to start an attacker-controlled workload. This is an **arbitrary-code-execution outcome on owner-funded cloud compute**, not a claim of immediate code execution on the Windows workstation.

I assess this chain as **very likely (80-90%) conditional on one of the named cloud credentials still being provider-valid and authorized to create/submit compute**. Evidence for the reachable source and sink is strong: Claude allows Bash, WebFetch, and broad MCP access with `defaultMode: "bypassPermissions"` and adds both `C:` and `D:` to accessible directories (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`); the standalone and shared secret guards are opt-in (`/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:73-100`, `/local_disk0/codexwork/bundle/agents/harness/modules.py:50-99,746-798`); and safe synthetic probes in this unit demonstrated that both implementations allow a named environment read even when the credential guard is enabled. The remaining premise—current provider validity and create-compute scope—is **UNVERIFIED; a redaction-safe provider-side permissions/introspection call for each code-execution token, returning only account identity, expiry, and capability names, would settle it**. Because that premise is UNVERIFIED, the primary finding and recommendation heading below carry the tag.

An existing control does **not** stop the chain. More strongly, the credential-read controls are insufficient even if the deployment happens to enable them: neither catches named environment reads, both allow `accounts.json`, and the standalone hook also allows `auth.json`. The declarative Claude denies cover `.env`, PEM, and `*credentials*` only (`settings.json:64-69`); shell access is separately allowed, so those Read-tool patterns are not a complete source boundary.

The minimum durable mitigation is not a new secret manager or second runtime. It is to remove compute-capable credentials from the agent's ambient environment and enforce a narrowly typed secret-source boundary in the existing PreToolUse bus: exact protected store basenames/paths and exact secret-variable access as tool semantics, never arbitrary prose. That breaks the chain before a reusable credential enters model context while respecting the measured false-positive defect in prose/payload scanning.

## Scope and safety

This unit performed analysis only. It did not inspect credential values, contact a credentialed provider, test a token, exfiltrate data, change live configuration, or execute an attack. All dynamic probes used fake paths and variable names with no values. The unpacked subject remained the evidence source; the only authored artifact is this file.

The Windows paths named in the brief do not exist on this Linux job node. Consequently, live Windows ACLs, registry scopes, current environment-variable presence, current credential-store contents, and provider validity could not be freshly checked. Prior audit findings concerning those facts remain claims and are cited as leads, with UNVERIFIED stated inline where a conclusion depends on them.

The corpus hook section was not used: the brief marks its detector broken. Corpus `_meta` says 11,633 files and 10.62 GB were distilled with zero failed files, one malformed line, and 32 oversized lines (`/local_disk0/codexwork/bundle/inputs/corpus.json`, `_meta`), but that does not repair hook telemetry. The live-defects input independently states that hook behavior was unmeasurable in transcripts and prescribes a known-positive control (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-147`).

## Assets and trust boundaries actually present

### Credential stores and credential delivery

1. The bundled Codex config requests full host authority: `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`/local_disk0/codexwork/bundle/codex/config.toml:6-8`). It also persists all history (`config.toml:39-40`).

2. Codex narrows the ordinary shell environment with `[shell_environment_policy] inherit = "core"` (`config.toml:21-22`) and supplies selected variables to individual MCP servers, for example `FIRECRAWL_API_KEY`, `TAVILY_API_KEY`, and the disabled GitHub CLI server's `GITHUB_MCP_PAT`/`GH_TOKEN` (`config.toml:511-522,547-551`). This is a useful existing containment control for the Codex path.

3. The intended Codex keyring settings are under `[tui]` (`config.toml:42-49`). The current official Codex configuration reference lists `config.toml` keys and documents user-level configuration at `~/.codex/config.toml`: https://learn.chatgpt.com/docs/config-file/config-reference. Prior audit F01 claims those two credential-store keys are root keys and that plaintext `auth.json` remains; that runtime consequence is **UNVERIFIED on this job node; `codex debug config` (or an equivalent documented resolved-config command) plus metadata-only existence checks before and after a fresh login would settle whether the nested keys are ignored** (`/local_disk0/codexwork/bundle/inputs/audit-findings/F01.md:35-41,83-90`).

4. Prior audits report plaintext Claude OAuth/client-secret fields in `.claude/.credentials.json`, plaintext Codex OAuth/private-key fields in `.codex/auth.json`, literal values in hub `accounts.json`, and credential-rich user/machine environment scopes (`audit-findings/F01.md:27-41,67-73`; `audit-findings/A28.md:16-22,32-38`). Those are higher-detail audit claims, not reverified facts here. Their current presence is **UNVERIFIED; metadata-only field-name/type/nonempty checks plus Windows effective-ACL checks, without printing values, would settle store presence and sandbox readability**. Provider validity is a separate experiment.

5. The bundle deliberately excludes the live secret stores: a filename-only `find` found no `auth.json`, `.credentials.json`, or `accounts.json` beneath `/local_disk0/codexwork/bundle`. The detector's positive control succeeded by finding the known-present source file `claude/hooks/deny-credential-reads/deny.py`; the absence only establishes that these stores were not packaged, not that they are absent on Windows.

### Execution and egress capability

Claude globally allows `Read`, `Edit`, `Write`, `Grep`, `Bash`, WebSearch/WebFetch, Task, and numerous MCPs (`settings.json:26-63`), sets `defaultMode` to `bypassPermissions` (`:70-75`), suppresses the dangerous-mode warning (`:693`), and enables remote control at startup (`:700`). These are static configuration facts; no inference about an individual session is needed.

Codex similarly has no approval boundary and full host access (`config.toml:6-8`), while shell, apps/MCP gateway, hooks, plugins, and code mode are enabled (`:82-106`).

The official Claude hook guide states that PreToolUse hooks run before permission-mode checks and a JSON `permissionDecision: "deny"` blocks even in `bypassPermissions`: https://code.claude.com/docs/en/hooks-guide. Thus a correctly implemented and live PreToolUse deny could stop the chain. The issue is the deployed guard's coverage and default, not a native inability to enforce.

## Primary attack chain — UNVERIFIED current token validity

### Preconditions

- An attacker controls untrusted content that an agent ingests (for example, a poisoned fetched page or MCP result), or has otherwise steered an autonomous turn. This is **likely (55-80%) over long autonomous runs**, based on the broad web/MCP ingestion and no-approval configuration above; the corpus does not measure successful prompt injections, so no stronger frequency claim is made.

- A code-execution provider credential is readable from the Claude parent/child environment. Prior Windows audits name `RUNPOD_API_KEY`, Modal credentials, and other cloud credentials in the shared environment (`audit-findings/F01.md:27-33,67-73`; `audit-findings/A28.md:16-22`). Current readability is **UNVERIFIED; start a disposable Claude session after enabling subprocess scrubbing and run a name-only child-environment inventory that reports PRESENT/ABSENT but never values to settle it**.

- At least one stolen credential can create or submit compute. This is **UNVERIFIED; a provider-side capability/permissions introspection returning no secret and creating no resource would settle it**.

### Step-by-step chain

1. **Steer the agent into an authentication-diagnostic pretext.** Poisoned content tells the agent a cloud tool failed because its account configuration is stale and asks it to inspect whether the relevant named environment entry exists. This pretext fits this harness because it has many local MCPs and known liveness/reliability work. No secret value is needed in the injected text.

2. **Read the reusable credential through a gap that survives the advertised guard.** The agent uses PowerShell/Bash environment inspection for a specifically named compute credential. `deny.py` scans only read verbs near file fragments (`deny.py:27-31,47-55`) and has no environment-variable rule. The shared module scans `_CREDENTIAL_READ`, whose pattern only names `.env`, `auth.json`, credentials, SSH keys, and AWS credentials (`modules.py:641-643`); it also has no named-environment rule. Safe unit probes confirmed both allow `Get-ChildItem Env:GH_TOKEN` with `HARNESS_CREDENTIAL_GUARD=1`. A compute token name follows the same uninspected syntactic route.

3. **Place the credential in model/tool context.** The shell tool returns the environment value. Because the hard literal-secret block is also opt-in (`modules.py:84-99,748-762`) and the settings do not set `HARNESS_SECRET_GUARD`, no configured shared module is guaranteed to block the subsequent secret-bearing tool input. The settings-environment detector proved it could find known-present `CLAUDE_CODE_FORK_SUBAGENT` and found neither `HARNESS_CREDENTIAL_GUARD` nor `HARNESS_SECRET_GUARD`. This proves absence from the bundled `settings.env`, not absence from Windows Process/User/Machine scope.

4. **Transmit the credential.** The poisoned instruction causes a second tool call to an attacker-controlled HTTPS endpoint or another data-bearing outbound sink. Bash and WebFetch are allowlisted with bypass permissions (`settings.json:26-75`). The current harness has no demonstrated outbound data-flow gate in the files inspected. Claiming none exists anywhere on the Windows machine would require two independent live signals, so broader absence is **UNVERIFIED; enumerate effective PreToolUse registrations from the native `/hooks` view and send a synthetic canary—not a credential—through each outbound tool class to settle coverage**.

5. **Use the stolen provider authority outside the harness.** The attacker authenticates directly to the cloud provider and requests a workload/container/notebook under their control. If the token has create/submit scope, the provider runs arbitrary attacker code on owner-funded infrastructure. This is the execute-code terminal state. It does not depend on the model continuing to cooperate after exfiltration.

6. **Persistence/blast radius.** The raw secret is **likely (55-80%) to be duplicated into at least one transcript/history sink after it enters a tool result**, based on Codex being configured `save-all` (`config.toml:39-40`), Claude retaining sessions for 365 days (`settings.json:2`), and prior audit F01 claiming byte-equality matches in histories (`audit-findings/F01.md:19-25`). Current copies are **UNVERIFIED here; equality-only scans against current values, emitting only credential name and matching path, would settle it**.

### Why this is the most plausible chain

This route uses four capabilities already configured together: an untrusted-content input, a no-approval shell, ambient credentials, and an outbound network sink. It does not require exploiting memory corruption, guessing a token, defeating cryptography, changing a live config, waiting for an update, or persuading the owner to run a new file.

It is more plausible than the local-workstation PAT supply-chain alternative. A stolen GitHub PAT could plausibly modify a remote toolchain branch and later obtain host code execution when an owner update is pulled and a repo-hosted MCP entrypoint starts. However, that chain additionally depends on PAT repository scope, branch protection, a pull/update event, and the exact live launcher. I rate it **roughly even (45-55%) conditional on a valid write-capable PAT**, because the bundle proves repo-hosted executable entrypoints such as the scholarly MCP (`config.toml:535-538`) but does not prove an automatic pull of that repo. The premises are **UNVERIFIED; a scopes-only PAT introspection, branch-protection query, and update-path trace would settle them without pushing anything**.

## Existing controls: verified result

### Control 1: declarative Claude Read denies — partial only

`settings.json:64-69` denies Read for `.env`, PEM, and `*.credentials*`. It does not name `auth.json` or `accounts.json`. Separately, Bash and PowerShell are broadly allowed (`:26-36`) and the declarative deny is scoped to the Read tool syntax. Therefore it does not stop the environment-read primary chain and does not establish a shell-level file boundary.

### Control 2: standalone `deny-credential-reads` hook — present, default-off, incomplete

Wiring is present at `settings.json:239-248`, matching `Read|Edit|MultiEdit|Grep|Bash|PowerShell`. The detector control is therefore known-positive: the exact hook file exists and the exact registration is present.

The implementation returns immediately when `HARNESS_CREDENTIAL_GUARD` is not enabled (`deny.py:73-89`) and fails open on every exception (`:104-108`). Its sensitive globs include `.credentials.json` but not `auth.json` or `accounts.json` (`:19-25`); its shell fragments likewise omit those names (`:27-31`).

Safe synthetic execution results from this unit (fake paths, no secret values) were:

```text
off-auth-read: rc=0 decision=allow/no-decision
on-credentials-read: rc=0 decision=deny
on-auth-read: rc=0 decision=allow/no-decision
on-accounts-read: rc=0 decision=allow/no-decision
on-env-read: rc=0 decision=allow/no-decision
```

This both validates the detector with a known-positive block and demonstrates three relevant misses. The official Claude hook reference confirms that exit 0 with no deny allows the tool and that hook timeout/non-blocking failures proceed: https://code.claude.com/docs/en/hooks.

### Control 3: shared `SecretGuardModule` — default-off and incomplete

The shared guard is registered for Claude PreToolUse at `settings.json:139-149`. Its credential, lifecycle, and literal-secret hard blocks are independently opt-in (`modules.py:50-99`). Tests explicitly codify credential reads and literal secrets as allowed by default, and blocked only when flags are set (`agents/harness/tests/test_modules.py:266-340`).

The job node lacked `pytest`, so the selected test run ended with `No module named pytest`; no passing-suite claim is made. Instead, the deployed module was imported and called directly using normalized fake events. Results were:

```text
off-auth-shell: action=allow reason=ok
on-auth-shell: action=block reason=credential_read
on-accounts-shell: action=allow reason=ok
on-env-shell: action=allow reason=ok
```

This independent implementation does catch `auth.json` when enabled, but still misses both the hub store and named environment source used by the primary chain. The dispatcher itself also fails open on any exception (`agents/harness/dispatcher.py:530-556`).

### Control 4: keyring/environment isolation — useful but not established end-to-end

Codex's `inherit = "core"` plus per-MCP `env_vars` is a real least-ambient-authority configuration (`config.toml:21-22,511-551`). It is **likely (55-80%) to reduce the Codex variant of the chain**, based on that explicit narrowing and per-server delivery, but the exact contents of `core` and effective Windows inheritance are **UNVERIFIED; a name-only environment inventory from a Codex shell and from each credentialed MCP child would settle effectiveness**.

Claude's environment block does not set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (`settings.json:4-20`). The detector found the known-present `CLAUDE_CODE_FORK_SUBAGENT`, establishing that it can detect keys in this block. Current official documentation lists the subprocess scrub environment control: https://code.claude.com/docs/en/env-vars. Whether it covers every custom provider token, including RunPod/Modal, is **UNVERIFIED; a canary-valued, name-only child-environment matrix for known and custom secret names would settle exact coverage**.

### Overall answer

No verified existing control stops the primary chain. The hard finding is stronger than “the opt-in flag may be unset”: safe probes show the chain's environment source remains allowed even with the credential flag set. Therefore simply enabling `HARNESS_CREDENTIAL_GUARD=1` is not an adequate mitigation.

## Minimal mitigation — UNVERIFIED Windows deployment experiment

### 1. Remove ambient compute credentials from agent parents — NATIVE (Claude Code already does this; we just enable it)

Enable `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` for the no-approval/autonomous Claude profile and verify its exact coverage with canaries. This is the smallest immediate change that rides the native subprocess boundary. It is **likely (55-80%) to remove common provider credentials from shell/hook children**, based on the documented control and the current absence from `settings.env`; coverage of custom names is **UNVERIFIED; the canary child-environment matrix described above settles it**. If a compute token survives, do not call the step complete.

### 2. Make credential delivery per-server, never User/Machine ambient — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Retain Codex's existing `inherit = "core"` and per-server `env_vars` pattern. For Claude, launch each credentialed MCP with only the variables it needs, and remove compute-capable tokens from global `settings.env` and persistent User/Machine environments after coordinated rotation. The result should be that a general Bash/PowerShell child cannot see provider credentials, while a specific MCP server can use them without returning their values. This is **very likely (80-90%) to break step 2 if verified at the child-process boundary**, because the attack needs raw reusable bytes; evidence is the existing per-server Codex pattern (`config.toml:21-22,511-551`). Windows registry cleanup and live MCP startup are **UNVERIFIED; a before/after name-only process matrix plus one normal non-secret MCP health call per server settles deployment**.

Implement the one-time Windows environment cleanup and the name-only verification matrix as a bounded idempotent PowerShell script in the existing deployment/health-check bus. Server declarations remain ordinary configuration; the BUILD-SMALL tag accounts for the registry migration/verification portion and does not imply a daemon.

### 3. Correct Codex keyring placement and harden store ACLs — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Move `cli_auth_credentials_store = "keyring"` and `mcp_oauth_credentials_store = "keyring"` from `[tui]` to TOML root, then fresh-login and prove metadata-only that plaintext fallback stores are no longer used. Restrict any unavoidable `auth.json`, `.credentials.json`, and `accounts.json` working copies so agent sandbox identities cannot read or modify them. This is **likely (55-80%) to reduce reusable plaintext auth exposure**, based on TOML scope (`config.toml:42-49`) and the official config reference; effective migration is **UNVERIFIED; resolved-config output, store metadata, keyring target presence, and effective Windows ACLs would settle it**.

The TOML move itself is configuration, while the BUILD-SMALL tag accounts for an idempotent ACL verifier/remediator and metadata-only migration check in the existing deploy/health-check bus. No daemon is justified.

### 4. Replace the broad opt-in regex with a typed autonomous-profile source gate — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Modify the existing shared PreToolUse `SecretGuardModule`, not a second guard framework:

- Match semantic tool operations only: `Read/Edit/NotebookEdit/MultiEdit.file_path`, `Grep.path`, actual shell `command`, and MCP argument fields classified as local paths. Never scan Write/Edit body prose. This directly incorporates the live D1 defect (`INPUT-known-harness-defects.md:9-50`).
- Protect exact basenames and canonical locations: `auth.json`, `.credentials.json`, `accounts.json`, `.env*`, cloud CLI credential stores, SSH private keys, and the known transcript/history sinks that can contain current credential bytes. Normalize case, separators, quotes, and resolved paths before comparison.
- Detect actual environment-value access for secret-named variables and bulk environment enumeration. Do not block merely mentioning `GH_TOKEN` in Markdown.
- Enforce by default when the effective profile is no-approval/autonomous (`bypassPermissions`, `approval_policy=never`), while interactive/default profiles can return `ask`. This couples the policy to risk rather than a forgotten global flag.
- Fail closed for a matched secret source: malformed input, timeout, or internal error should deny/ask that single high-risk operation. Other tools remain fail-open. Native Claude documentation confirms a PreToolUse deny overrides bypass mode: https://code.claude.com/docs/en/hooks-guide.
- Add table-driven regression cases for both implementations: `.credentials.json`, `auth.json`, `accounts.json`, named env read, bulk env enumeration, case/slash/quote variants, and benign prose that only names them. Require one known-positive and one known-negative in the hook-health check.

This patch is **very likely (80-90%) to block raw secret acquisition through the enumerated Claude tool routes**, because the current misses were reproduced at that exact boundary. Completeness across every MCP path is **UNVERIFIED; replay the fixture matrix through the native Claude `/hooks` runtime and Codex hook adapter, plus synthetic canary calls for every source-capable tool, to settle it**.

### Ordered minimum

For immediate risk reduction, do 1 and 2 first; they remove the primary source without depending on model-visible regex. Do 3 for the on-disk auth stores. Do 4 to close explicit reads and prevent future ambient regressions. Enabling the old `HARNESS_CREDENTIAL_GUARD` alone is rejected because the direct probes prove it misses the selected path.

## Anti-overfit gate

All proposals ride existing native configuration, environment-delivery, OS ACL, and shared PreToolUse buses. None adds a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The only code proposal is a bounded extension/replacement inside the existing security module, targeted at a reproduced source-coverage defect.

A BUILD-LARGE secret broker is not justified at this stage. It would add an always-on security-critical service before native keyring, per-process environment, ACL, and current hook buses have been correctly configured and verified. Reconsider only if the canary matrix proves native/per-server delivery cannot keep raw credentials out of general agent children.

## Alternatives considered and rejected

1. **“Just enable `HARNESS_CREDENTIAL_GUARD`.”** Rejected: direct synthetic probes show both guards still allow environment reads and `accounts.json`; the standalone guard also allows `auth.json`.

2. **Add more secret-prefix regexes to the literal scanner.** Rejected: it operates after a secret can enter context, misses unknown formats, and the live D1 evidence shows payload/prose regexes create self-amplifying false positives (`INPUT-known-harness-defects.md:9-50`).

3. **Rely on git-crypt for `accounts.json`.** Rejected as a runtime control: git-crypt protects repository blobs, not an unlocked working-tree file needed by a running hub. Prior audit F01 explicitly distinguishes encrypted Git objects from readable working copies (`audit-findings/F01.md:67-81`). Current Windows readability is UNVERIFIED as described above.

4. **Disable all shell/network capability.** Rejected as disproportionate to this owner's high-autonomy intent. Per-server capability delivery and typed source denial preserve useful tools.

5. **Introduce Vault/a new broker daemon.** Rejected by the anti-overfit gate until native keyring, ACLs, and per-server environment delivery are proven insufficient.

6. **Treat the PAT supply-chain route as primary.** Rejected because it adds unverified write scope, branch-policy, pull, and launcher prerequisites. It remains a valuable second test case after the direct cloud-execution route.

## Verification plan / acceptance criteria

No mitigation should be called done until two mechanically independent signals agree for each boundary.

1. **Detector validity:** the config-key inventory must find known-present `CLAUDE_CODE_FORK_SUBAGENT`; the hook test must deny a fake `.credentials.json` read. Both controls succeeded in this unit.

2. **Ambient environment absence:** (a) metadata-only Windows Process/User/Machine inventory reports protected compute names absent from general agent parents; (b) a canary environment value is absent from a real Claude/Codex shell child while a designated MCP health call still succeeds. Registry enumeration and child observation are independent signals.

3. **Store isolation:** (a) Windows effective ACL calculation reports sandbox identities lack Read/Modify on each store; (b) an actual sandbox-identity metadata-only open attempt returns access denied while the designated client still authenticates. ACL text and behavioral open are independent.

4. **Hook enforcement:** (a) direct unit fixtures return block for exact source operations and allow for prose mentions; (b) native `/hooks` runtime with a fake canary source blocks before tool execution. Direct module and native host are independent.

5. **No credential persistence:** (a) equality-only scan of new transcripts/history finds zero matches to canary values; (b) ledger/log field inspection shows digests/redactions rather than bodies. Seed a canary, never a real token. A match scan and storage-shape inspection are independent.

6. **Provider authority:** for each surviving credential, use provider-side read-only introspection to record expiry and capability names. A credential that can create workloads must not be available to a general agent child. Do not create a workload as part of this verification.

7. **Failure behavior:** deliberately feed malformed fake hook JSON and force a test timeout. A matched protected-source operation must deny/ask; an unrelated operation must proceed. This settles the present fail-open bypass without risking a live secret.

## Gaps

- Current Windows secret-file existence, contents, ACLs, registry environment, and process inheritance could not be reverified because only the Linux bundle exists. Every conclusion depending on those is tagged UNVERIFIED inline with a settling experiment.
- Credential validity, expiry, and provider scope were intentionally not tested. Therefore the report claims a concrete reachable chain conditional on validity, not a confirmed live provider compromise.
- `.mcp.json`, `.claude.json`, managed MCP configuration, the toolchain repo, and the live hub source were not included in this bundle. Prior audit details about them remain leads rather than facts for this unit.
- The selected pytest cases could not run because this job environment has no `pytest`. Direct deployed-code probes replaced them for the narrow guard behavior, but the full suite remains unrun.
- The official Codex configuration reference was checked online, but a safe resolved-config diagnostic was not run on Windows. Keyring ineffectiveness remains UNVERIFIED until that experiment.
- No broad “no other control exists” claim is made. The report establishes that the visible registered controls and direct implementations do not stop the chosen source path. Native effective-hook enumeration plus canary replay is required to exclude an unbundled managed control.
