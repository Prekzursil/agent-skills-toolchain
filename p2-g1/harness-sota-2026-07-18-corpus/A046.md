## Collision register

### C1 — Claimed common inheritance is not loaded for Perl

**Class:** STALE  
**Artifacts:** `perl/coding-style.md` ↔ `common/coding-style.md` and `rules/README.md`

**Exact conflicting lines**

- `/local_disk0/codexwork/bundle/claude/rules/perl/coding-style.md:11`: “This file extends ... common/coding-style.md”.
- `/local_disk0/codexwork/bundle/claude/rules/common/coding-style.md:1-20`: the path frontmatter lists Python, TypeScript/JavaScript, Go, Rust, Java, Ruby, PHP, C/C++, C#, Swift, Kotlin, and shell extensions, but no `.pl`, `.pm`, `.t`, `.psgi`, or `.cgi`.
- `/local_disk0/codexwork/bundle/claude/rules/README.md:8-29`: common is described as the universal layer and language directories as extensions.
- `/local_disk0/codexwork/bundle/claude/rules/README.md:55-64`: installation calls common required, then adds language directories.

**Why this collides**

A Markdown link is not inheritance. For a Perl file, the Perl rule's own path filter matches while the alleged base rule's filter does not. Thus the common requirements for file size, function size, error handling, validation, and immutability (`common/coding-style.md:23-68`) are not supplied by that common file on Perl paths. The documentation describes an architecture that the frontmatter does not implement.

Precedence does not help: there is no simultaneously loaded common rule to override. This is a loading/scope defect, not a priority dispute.

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add the five Perl globs to the common rule's frontmatter. This is **almost certain (90-99%)** to restore the intended common-plus-Perl composition because the Perl file already uses those exact five globs at `perl/coding-style.md:2-7`; settle the residual loader uncertainty with a Claude Code instruction-load trace on a temporary `.pm` file. Add a fixture that asserts both rule IDs are loaded for each supported Perl extension and that a non-Perl control does not load the Perl rule.

Do not copy the common prose into the Perl file. That would hide the path bug and create another drifting duplicate.

### C2 — `perlcritic` security threshold is 3 in one rule and 4+ in another

Settle execution semantics by running both commands against fixtures containing one severity-3 security violation and one severity-4 security violation and asserting the intended results.

An alternative—raise the combined coding-style command to severity 4—would be simpler but would silently change the `core`/`pbp` threshold too. This unit does not recommend that unmeasured policy expansion.

**Why this is a defect**

Regex blocking is **very likely (80-90%)** to be brittle because absence of a text pattern is not proof of semantic absence and the rule names no AST-aware policy; settle this with a mutation suite covering comments, multiline declarations, generated accessors, and indirect imports.

**Specific resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

2. On `.pl` and `.pm`, run perltidy in check/diff mode using one checked-in configuration; do not silently rewrite user edits unless autoformat is an explicit owner choice.
3. On `.pm` (and optionally all five extensions after measured cost), run the two canonical perlcritic gates resolved in C2.

5. Add fixtures for every extension, missing tools, timeouts, syntax failure, formatting drift, severity-3 core/PBP, and severity-4 security.

This is **very likely (80-90%)** to close the observable formatter/linter gap because it extends the already wired edit hook (`settings.json:333-342`) and uses the exact tools demanded by the rules. It is **likely (55-80%)** to enforce the version/signature/attribute prose without false positives only if those prose requirements are mapped to tested compiler/perlcritic policies; settle that premise with a mutation suite containing compliant and intentionally noncompliant Perl fixtures. Missing tool binaries must fail open with a visible “validator unavailable” nudge, not a false clean result.

This proposal passes the anti-overfit gate: it adds one language lane to an existing hook bus and introduces no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.
