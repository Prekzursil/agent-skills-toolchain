## Collision register

### C1 — Required mutation is both permitted and absolutely forbidden

- **Class:** CONTRADICTION
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:17`: “Prefer `val` over `var` — default to `val` and only use `var` when mutation is required.”
  - `~/.claude/rules/common/coding-style.md:23-30`: “Immutability (CRITICAL)”; “ALWAYS create new objects, NEVER mutate existing ones”; only a new-copy operation is accepted.
  - The common checklist repeats the absolute at `common/coding-style.md:68`: “No mutation.”
- **Why this collides:** Kotlin explicitly permits `var` when mutation is required; the common rule prohibits that same operation for every `.kt` file because its frontmatter includes Kotlin at `common/coding-style.md:18`. This is not merely different emphasis. A required local mutation can comply with one or the other, not both.
- **Precedence:** unresolved. AGENTS.md §10 has no common-vs-language rule. The unloaded README cannot decide the live conflict.
- **Specific resolution:** Rewrite the common rule from an absolute object-mutation ban to a boundary/state rule: prefer immutable externally observable state and copy-on-write updates; allow encapsulated local mutation, builders, and performance-critical mutation when justified. Keep Kotlin line 17 as the language-specific spelling and line 19 for immutable state transitions. This is an editorial consolidation, not a new runtime mechanism.
- **Confidence:** **almost certain (90-99%)**, because both directives and the common `.kt` path scope are explicit at the cited lines.

### C2 — Extension files must be organized by receiver type and must not be organized by type

- **Class:** CONTRADICTION
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:60-62`: extensions must be discoverable, placed in receiver-named files such as `StringExt.kt` and `FlowExt.kt`.
  - `~/.claude/rules/common/coding-style.md:35-41`: “Organize by feature/domain, not by type.”
- **Why this collides:** A receiver-wide extension bucket is organization by type. For client-specific extensions, it also pulls behavior away from its feature/domain.
- **External freshness check:** Kotlin's current official coding conventions say universally relevant extensions belong with the class, client-specific extensions belong near the client, and one should avoid files created merely to hold all extensions of a class ([Kotlin coding conventions](https://kotlinlang.org/docs/coding-conventions.html)). That directly disfavors the blanket `StringExt.kt`/`FlowExt.kt` policy.
- **Precedence:** unresolved under AGENTS.md §10. If one imported the unloaded README's specificity rule, Kotlin would win, but that would silently select the less current convention.
- **Specific resolution:** Delete the receiver-filename mandate. Replace it with: keep universal extensions with/near the receiver when owned locally; keep client-specific extensions in the consuming feature; use a descriptive UpperCamelCase content name for top-level-only files. This makes the Kotlin rule agree with the common feature/domain rule and official Kotlin guidance.
- **Confidence:** **almost certain (90-99%)**, supported independently by the two harness texts and the primary Kotlin convention.

### C3 — `runCatching` contradicts the cancellation rule immediately below it

- **Class:** CONTRADICTION
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:76`: “Use `runCatching {}` for wrapping throwable code.”
  - `~/.claude/rules/kotlin/coding-style.md:77`: “Never catch `CancellationException` — always rethrow it.”
- **Why this collides:** The Kotlin standard library specifies that `runCatching` catches **any `Throwable`** and stores it as `Result.failure` ([`runCatching` API](https://kotlinlang.org/api/latest/jvm/stdlib/kotlin/run-catching.html)). Coroutine cancellation throws `CancellationException`, and the coroutine documentation requires it to be rethrown when caught because catching it can break propagation ([Kotlin cancellation documentation](https://kotlinlang.org/docs/cancellation-and-timeouts.html)). An unqualified `runCatching` around suspending/cancellation-capable work therefore violates line 77 without an explicit rethrow step.
- **Precedence:** not applicable; this is an internal contradiction in one same-level artifact. AGENTS.md §10 provides no line-order tie-break.
- **Specific resolution:** Replace line 76 with a cancellation-safe rule: do not use bare `runCatching` around suspending or cancellation-capable code; use explicit `try/catch`, rethrow `CancellationException`, and convert only expected non-cancellation failures. If a project supplies a tested `runSuspendCatching`/`coRunCatching` helper that rethrows cancellation, name that helper rather than generic `runCatching`.
- **Confidence:** **almost certain (90-99%)**, from the stdlib's catch-all contract plus the coroutine cancellation contract.

### C4 — General nesting cap 4 versus scope-function nesting cap 2

- **Class:** REDUNDANCY
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:64-71`: scope-function guidance and “max 2 levels.”
  - `~/.claude/rules/common/coding-style.md:59-65`: completion checklist with no deep nesting above 4 levels.
  - `~/.claude/rules/common/code-review.md:47-53` and `:113-119`: independently repeat the 4-level threshold.
- **Why this is defective:** The caps can be jointly satisfied, so this is not a logical contradiction. It is threshold duplication without a declared counting model: the Kotlin text does not say whether two scope-function levels nested inside other control flow are acceptable under the global four-level cap. The common threshold is itself duplicated in two files.
- **Precedence:** AGENTS.md §10 does not resolve same-level thresholds. The strictest interpretation (two for scope functions, four overall) is **likely (55-80%)** to be the author's intent because it satisfies both numeric caps, but it is not stated and therefore must not be silently assumed.
- **Specific resolution:** Make `common/coding-style.md` the sole global nesting threshold. In Kotlin, state only the specialization: “Scope-function nesting counts toward the global nesting depth and must not exceed two consecutive scope-function receivers.” Make `common/code-review.md` link to that threshold instead of copying it.
- **Confidence:** **very likely (80-90%)** that this wording removes reviewer disagreement, because all three current thresholds become one global definition plus one Kotlin subtype; the evidence is the three duplicated lines above.

### C5 — Error-return policy is duplicated with different scope

- **Class:** REDUNDANCY
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:73-78`: broadly says use `Result<T>` or custom sealed types.
  - `~/.claude/rules/kotlin/patterns.md:52-63`: says `suspend` repository functions return `Result<T>` or a custom error type and gives repository signatures.
- **Why this is defective:** The texts agree on the alternatives but disagree on declared scope: one reads as a general error-handling policy, the other as a mandatory repository/suspend signature. Future edits can change one without the other, and the general line provides no boundary for when nullable, exception, or domain error results are appropriate.
- **Precedence:** unresolved same-level duplication; neither artifact outranks the other under AGENTS.md §10.
- **Specific resolution:** Keep the decision rule in `coding-style.md` and make `patterns.md` reference it. Narrow the decision rule: nullable for legitimate absence; domain sealed errors/typed result at recoverable boundaries; exceptions for programmer/invariant failures; never encode cancellation as an ordinary failure. Do not require Kotlin `Result` for every suspend function.
- **Confidence:** **very likely (80-90%)** that consolidation prevents drift, based on the verbatim duplicated alternatives and their different scopes.

### C7 — `List`/`Map`/`Set` are called immutable although the interfaces are only read-only

- **Class:** STALE
- **Artifacts and exact lines:**
  - `~/.claude/rules/kotlin/coding-style.md:18`: “use immutable collections (`List`, `Map`, `Set`) in public APIs.”
  - `~/.claude/rules/common/coding-style.md:23-33` requires actual immutability to prevent hidden side effects.
- **Why this collides:** Kotlin's standard collection pairs are read-only and mutable interfaces; a mutable implementation can be exposed through a read-only `List` reference, and contained elements can themselves mutate. The official collection documentation explicitly describes `List`/`Set`/`Map` as read-only interfaces, not deep immutable values ([Kotlin collections overview](https://kotlinlang.org/docs/collections-overview.html)). Thus line 18 can falsely certify compliance with the common rule's actual immutability objective.
- **Precedence:** No order fixes a semantic type error. AGENTS.md §10 is inapplicable.
- **Specific resolution:** Say “expose read-only collection interfaces in public APIs; defensively copy mutable inputs/outputs when ownership crosses a boundary; use persistent immutable collections when the contract requires structural immutability.” Do not equate `val` or `List<T>` with deep immutability.
- **Confidence:** **almost certain (90-99%)**, supported by the primary collection-interface documentation and the common rule's stated rationale.
