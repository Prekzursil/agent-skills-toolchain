# AS05 — coherence sweep: precedence collisions

## Verdict

This unit verified **three genuine same-level collisions** in the supplied live-harness subset, plus one intentionally resolved same-level exception family. Two of the three genuine collisions need an owner policy decision: the `/start-task` command has two incompatible routing contracts, and the `no-force-push` companion tells an agent both to use and not to use the same override after approval. The third is a narrower authoring collision: Python cleanup code is told both never to swallow errors and to use `except ...: pass`.

This is **not an exhaustive verdict over the Windows harness**. The remote bundle omits nearly the entire level-5 skill/plugin surface and the repository tree. That limitation is load-bearing because the bundled audit claims identify several candidate collisions precisely in those omitted roots. I therefore report them as **UNVERIFIED** inline and name the source-export experiment that would settle each one; I do not promote audit claims to facts.

Confidence in the three verified collision classifications is **almost certain (90-99%)**, based on direct, line-level incompatible imperatives in the unpacked source and, for the force-push case, separately visible runtime predicate/registration evidence. Confidence that the list is complete for the full Windows harness is **almost certainly not (1-5%)**, because the supplied tree has no ordinary live skill catalog, no plugin directory, and no `agent-skills-toolchain` checkout, while 52 audit reports cite skill paths, 20 cite plugin paths, and 82 cite the repository.

## Scope and method

Section 10 defines the five levels and explicitly says same-level conflicts must be surfaced rather than silently resolved: `/local_disk0/codexwork/bundle/claude/AGENTS.md:115-131`. I used these operational buckets:

1. explicit user instruction / permission system;
2. safety non-negotiables (§6, §9, §9b);
3. the cross-tool `AGENTS.md` contract;
4. project/repo governance, including the loaded global/project rules surface;
5. third-party skill/plugin/command defaults.

I searched the provided Markdown instruction surfaces (`AGENTS.md`, `CLAUDE.md`, rules, commands, agents, and the one supplied companion `SKILL.md`), then compared imperative pairs only when their activation scopes overlap and obeying one would violate the other. Repetition, stale factual prose, enforcement drift, different-provider behavior, and different-level disagreements were not counted as same-level instruction collisions.

Absence checks were detector-controlled. The same `find` detector found two known-present `AGENTS.md` files and one known-present `SKILL.md` (`claude/hooks/no-force-push/SKILL.md`), but found zero `plugins` directories and zero `agent-skills-toolchain` directories. A mechanically different signal—the audit-reference index—found 52 reports citing Windows skill paths, 20 citing plugin paths, and 82 citing the repository, proving that the missing roots are relevant rather than that the live harness has no such instructions. ## Owner-decision queue

### C1 — Level 5: `/start-task` says both “route without asking” and “always ask”

**Collision.** The command begins with a deterministic first-match router, says never to make the user choose, gives T0 a “just-do-it (no gates)” route, limits asking to an ABSTAIN fork, and says reversible/obvious steps are automatic (`/local_disk0/codexwork/bundle/claude/commands/start-task.md:11-27`). The same command then applies a checklist “before starting any new task,” runs BEADS priming, asks whether to inspect PR comments, and always asks the user to confirm the simple/complex assessment (`start-task.md:33-55,76-90`). For a trivial read-only request, the first contract requires no gate and no choice; the second requires at least the PR question and complexity confirmation. Both cannot be followed.

This is not resolved by specificity: both branches live in the same command and the later checklist never says it applies only to selected tiers. It also creates a direct practical collision with the `*` bypass at `start-task.md:13`: “skip to the work” versus the universal questions below.

**Specific resolution — owner decision recommended:** make the router the sole entry contract. T0 must skip all gates, BEADS, PR checks, and assessment confirmation. T1 may enter native Plan Mode without a confirmation round. Apply recovery/PR/issue/design gates only to the explicitly named tiers that need them, and ask only at the tier-2-or-higher material fork already defined at line 27. Remove the second simple/complex classifier rather than maintaining two routing taxonomies.

**NATIVE-vs-BUILD: CONFIG (Markdown command/routing text only).** This rides the existing command and native Plan Mode bus. It introduces none of the anti-overfit rejected components.

Confidence that this resolution will remove the contradictory behavior is **almost certain (90-99%)**, because it deletes one of two explicit classifiers and preserves the already-written tier router. Whether the owner prefers the tier router over the legacy universal checklist is a policy choice, not something source evidence can decide.

### C2 — Level 5: `no-force-push` gives opposite conditions for its override

**Collision.** The companion skill says its purpose is to confirm explicit approval before overriding (`/local_disk0/codexwork/bundle/claude/hooks/no-force-push/SKILL.md:1-4`), and quotes the hook instruction “If approved, re-run with `FORGE_NO_FORCE_PUSH_OFF=1`” (`SKILL.md:13-18`). Its procedure then says the override may be used **only** for a confirmed false positive (`SKILL.md:19-25`). An approved, accurately detected force-push is not a false positive, so the same component both instructs and forbids the override.

This reaches the live path rather than being inert prose. The predicate matches every `git push` containing `--force` or `-f`, without branch or approval state (`/local_disk0/codexwork/bundle/claude/hooks/no-force-push/tripwire.py:15-18,39-47`); the wrapper honors `FORGE_NO_FORCE_PUSH_OFF` and exits 2 on a match (`hook.py:29-32,35-58`); and settings register that wrapper (`/local_disk0/codexwork/bundle/claude/settings.json:156-158`). These are mechanically distinct instruction and runtime signals.

**Specific resolution — owner decision recommended:** choose explicit approval as the legitimate bypass condition, because the level-2 contract already permits a force-push to main/master with explicit approval (`/local_disk0/codexwork/bundle/claude/AGENTS.md:93-98`). Rewrite the companion procedure to require (a) explicit in-session approval for the exact remote/ref and (b) a one-command-scoped bypass; reserve “false positive” for fixing the predicate, not as the only override case. At the same time, narrow the predicate to the protected target ref or make its message honestly state that local policy is stricter than the shared floor. Do not retain the `.disabled`-file escape as an unbounded alternative.

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** This is a bounded edit to the existing predicate/wrapper/companion, not a new guardrail framework or runtime.

Confidence that this is a genuine instruction collision is **almost certain (90-99%)**, based on the opposite “if approved” and “only false positive” conditions plus the registered bypass implementation. Confidence that protected-ref narrowing is preferable to blocking all branches is **likely (55-80%)**, based on the shared contract's explicit main/master scope; the remaining uncertainty is the owner's possible intent to impose a deliberately stricter all-branch policy.

## Verified collision with a low-risk editorial resolution

### C3 — Level 4: “never silently swallow errors” versus prescribed `except ...: pass`

**Collision.** The common coding rule says to handle errors explicitly at every level and “Never silently swallow errors” (`/local_disk0/codexwork/bundle/claude/rules/common/coding-style.md:43-49`). The simultaneously path-matching static-analyzer rule tells Python authors to replace `suppress(...)` with an explicit `try/except ExceptionType: pass` (`/local_disk0/codexwork/bundle/claude/rules/common/static-analyzer.md:1-16`). A bare `pass` is the exact silent swallowing forbidden by the sibling common rule. Both files match `*.py`, and the rules README only defines a specificity override between common and language-specific directories, not between two common rules (`/local_disk0/codexwork/bundle/claude/rules/README.md:93-110`).

The intended cleanup exception is understandable—the static rule explains that the caller is the cancellation originator—but intent does not remove the incompatible literal instructions.

**Specific resolution:** change the general rule to “never silently swallow an **unexpected** error”; require every expected suppression to name the narrow exception and carry a one-line invariant/comment (and logging only where it adds a real signal). Change the static-analyzer example to an explicit narrow `except` with that invariant comment, or prefer the already-listed `gather(..., return_exceptions=True)` form when returned exceptions are subsequently inspected.

**NATIVE-vs-BUILD: CONFIG (two Markdown rule edits).** No new mechanism is needed.

Confidence that the textual collision is real is **almost certain (90-99%)**, based on two directly opposite common-rule imperatives with overlapping Python scope. Confidence that mandatory logging on every expected cancellation would help is **unlikely (20-45%)**, because it could create shutdown noise; that is why the proposed resolution requires explicitness, not unconditional logging.

## Intentional same-level conflict that is already resolved safely

### I1 — Level 4: universal immutability versus language-required mutation

The common coding rule says “ALWAYS create new objects, NEVER mutate existing ones” and repeats “No mutation” in its completion checklist (`/local_disk0/codexwork/bundle/claude/rules/common/coding-style.md:23-33,59-68`). Language rules explicitly permit mutation when required: Kotlin `var` (`rules/kotlin/coding-style.md:15-19`), Rust `let mut` (`rules/rust/coding-style.md:16-22`), Swift `var` (`rules/swift/coding-style.md:15-18`), and Java mutable state (`rules/java/coding-style.md:16-21`). These are literal same-level differences.

This family is intentional and safe because the rules system explicitly defines the missing sub-precedence: language-specific rules override common defaults and even gives mutation as its example (`/local_disk0/codexwork/bundle/claude/rules/README.md:93-110`). The exceptions are narrow (“when required” / compiler-required) and retain immutability as the default. No owner decision is needed.

**Specific resolution:** retain the language-specific override, but replace the common rule's absolute “ALWAYS/NEVER” with “default to immutable values; language-specific rules may permit scoped mutation.” This makes the already-defined resolution visible at the point of use.

**NATIVE-vs-BUILD: CONFIG (wording alignment only).** Confidence that the current exception is intentional is **almost certain (90-99%)**, based on the explicit priority section and its mutation example. Confidence that the behavior is safe when mutation remains scoped is **very likely (80-90%)**, based on all four language rules retaining immutability as the default and limiting the exception to necessity.

## Examined pairs that are not same-level unresolved collisions

- The level-2 safety text says hook errors fail open (`AGENTS.md:64-70`) while security remains always on (`AGENTS.md:93-106`). These govern failure handling and the normative agent prohibition, respectively; a hook crash does not instruct the agent to perform the forbidden action. The `no-force-push` wrapper also explicitly calls the human procedure a backstop (`no-force-push/SKILL.md:27-32`). This is defense-in-depth tension, not two mutually exclusive agent actions. It would become a real collision only if the harness claimed that the hook alone guarantees “always on.”
- Section 10 places explicit user instruction above safety while also calls safety non-negotiable (`AGENTS.md:121-126`). That is a cross-level precedence ambiguity, not a same-level pair, so it is outside this unit. The explicit approval exceptions for `--no-verify` and force-pushing main (`AGENTS.md:95-97`) further show that some user-authorized exceptions are intentional.
- `code-review.md` labels HIGH findings a warning and says “merge with caution,” while approval requires no HIGH findings (`rules/common/code-review.md:71-78,129-133`). These are different verdict states, not opposite instructions: a warning is expressly not approval. The wording is permissive, but it does not simultaneously require and forbid merge.
- Static named agent references do not by themselves violate the instruction not to keep a static **roster** (`rules/common/agents.md:3`). A fixed specialist reference can be routed through `/start-task`; the sources do not require bypassing that router. This is duplication/drift risk, not a mechanically unavoidable instruction conflict.
- Claude's and Codex's `AGENTS.md` files differ in size and hash, but provider divergence alone is not a same-session instruction collision. The Claude file is 8,704 bytes / SHA-256 `b252150e...a89`; the Codex file is 5,281 bytes / `ef717cb2...a6`. The Codex copy omits newer rules; it does not contain an opposite instruction pair on the verified lines.
