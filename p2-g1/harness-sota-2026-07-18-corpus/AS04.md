# AS04 — coherence sweep: `~/.claude/settings.json` versus observed reality

## Executive verdict

The file is syntactically valid JSON and contains 29 top-level keys, 18 hook event keys, 38 command-hook registrations, 99 `enabledPlugins` entries (8 `true`, 91 `false`), and 383 scalar leaves. Those are direct counts from `/local_disk0/codexwork/bundle/claude/settings.json`; the relevant source ranges are lines 1-704.

The effective runtime is not coherent with that desired-state document in four important ways.

1. **Plugin booleans are not an effective-state inventory.** The eight `true` values are at settings lines 572, 589-607, and 621, but a same-day operational audit found the installed-plugin registry to be 38,989 NUL bytes and `claude plugin list` to return `No plugins installed` (`inputs/audit-findings/B11.md:47-53`). Independently, historical corpus capability telemetry proves that six of the eight enabled plugin namespaces had run before the snapshot—Codex 2 invocations, Ralph 11, Remember 4, Superpowers 50, Claude Reflect 1, and Metaswarm 3 (`inputs/corpus.json:13266-13345`; individual examples at lines 13272, 13281, 13292, 13318, and 13338). A separate native host trace proves Metaswarm's plugin hook executed five times, with p50 50.970 s (`inputs/audit-findings/A07.md:7-13`). The evidence is temporally inconsistent, not contradictory: plugin functionality existed in retained sessions, while discovery was broken at the later live probe. It is **almost certain (90-99%)** that `enabledPlugins` currently expresses intent rather than trustworthy effective state, because the config, registry bytes, CLI result, corpus history, and host trace are mechanically different signals.
2. **The hook document is broad, duplicated, and partly schema-stale.** The same four lifecycle events launch both the shared harness dispatcher and the local `_dispatch` runtime (settings lines 82-103, 139-260, 310-354, and 484-504). The second dispatcher explicitly describes itself as an in-process threaded dispatcher (`claude/hooks/_dispatch/dispatch.py:1-45`) and hosts 17 checks (`claude/hooks/_dispatch/manifest.json:5-228`). Operational timing found a roughly 0.42 s estimated warm Python/import floor around ordinary successful PreToolUse+PostToolUse, a 10.422 s local Stop p50, and a 50.970 s Metaswarm SessionStart p50 (`inputs/audit-findings/A07.md:1-5,7-21,39-53`). The corpus hook detector is broken and must not be used (`inputs/corpus.json:13261`); these claims instead use native host traces, source registrations, and implementation structure.
3. **Several settings are overridden, redundant, undocumented, or not measurable from transcripts.** The most consequential examples are global `bypassPermissions` plus an empty `ask` list (settings lines 64-75), a ten-minute MCP tool timeout that is stricter than the audited native default (`inputs/audit-findings/B11.md:15-21`), three competing compaction controls (settings lines 18, 686, and 697), a `fresh` worktree base ignored by the custom hook (`inputs/audit-findings/C18.md:40-46`), and two ECC environment toggles while the ECC plugin is false (settings lines 15-16 and 608).
4. **The corpus can prove use, failure, and historical reach, but not current setting causality.** It processed 11,633 files with zero file failures and one bad line (`inputs/corpus.json:5-10`), so positive observations are strong: 108,121 Bash calls, 19,181 PowerShell calls, 6,222 Glob calls, 5,091 ToolSearch calls, 1,745 Agent calls, and 500 SendMessage calls (`inputs/corpus.json:15-126,191-205`). It does not record model selection, UI state, update channel, voice, notification state, configuration precedence, or reliable hook events. A historical call does not prove the July 18 settings value caused it.

The best resolution is evolution on the native settings/hook/plugin buses, not replacement with another runtime. Every proposal below is `CONFIG`, `NATIVE`, or `BUILD-SMALL`; none introduces a second orchestration runtime, vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework. This passes the anti-overfit gate.

## Method and detector validation

I parsed the unpacked settings directly with Python's standard JSON parser; it succeeded. A second structural walk counted 29 top-level keys, 99 plugin booleans, 18 hook event arrays, and 38 command handlers. For corpus reliability, `_meta.files_failed=0` and `_meta.lines_bad=1` are the completeness controls (`inputs/corpus.json:2-11`). For capability-detector validation, known-present `deep-research`, `general-purpose`, Bash, and ToolSearch are all returned nonzero (`inputs/corpus.json:13266-13369` and `:15-94`). For hooks, the known-positive control failed and the corpus itself marks the detector broken (`inputs/corpus.json:13261`); therefore no empty `hooks.fires` or `hooks.blocks` value is used.

The audit findings are claims produced by other units, not automatically promoted to fact. Where this unit cites an audit's live Windows command output, it labels it as operational audit evidence and pairs it with an independent bundled source/config/corpus signal wherever making an absence, breakage, or completion claim. The Linux bundle does not contain the live Windows plugin cache/registry, raw transcripts, `.claude.json`, or status-line script, so those cannot be re-probed here.
