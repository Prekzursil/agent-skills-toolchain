# A150 — coherence audit: `settings.json` versus `CLAUDE.md` / `AGENTS.md`

## Executive result

I found **four reachable precedence/coherence defects** in the unpacked Claude harness:

1. The behavior contract puts “the user's explicit in-session instruction” and “the permission system” at the same precedence rank, but the configured deny rules can reject a user-explicit request. Claude Code resolves this operationally in favor of the deny rule; the contract does not say so.
2. The settings wire a reverse-engineering auto-launch hook that emits a native deny while a backend starts, is down, or is low on RAM. Those are availability conditions, not irreversible/dangerous actions, while the contract says all non-dangerous guidance must inject rather than block.
3. The settings wire a file-scope hook that exits 2 for an ordinary, reversible edit outside an agent's declared glob. That is useful concurrency governance, but it contradicts the contract's exhaustive “block only dangerous” rule.
4. The settings wire a force-push hook that blocks every matching force-push even after the user gives the approval required by the contract. Runtime offers no in-session approval tie-break: the process must already have an opt-out environment variable or disabled marker.

The first finding is the requested pure precedence ambiguity. Findings 2–4 are stronger than ambiguity: settings-activated enforcement and the behavior text prescribe different outcomes, and Claude Code's native hook machinery silently chooses enforcement.

The conclusion is **almost certain (90-99%)** for this unpacked snapshot: every finding has (a) exact settings/contract wiring, (b) the invoked implementation's decision path, and (c) official Claude Code runtime semantics or an executable self-test. The residual 1–10% is snapshot-to-live drift: this Linux job cannot inspect the owner's current Windows files. The live-equivalence experiment is `Get-FileHash $HOME\.claude\settings.json,$HOME\.claude\CLAUDE.md,$HOME\.claude\AGENTS.md -Algorithm SHA256` on the Windows box and comparison with the hashes in “Coverage and method.”

## Finding 1 — permission system and user instruction are co-ranked without a tie-break

### Both texts verbatim

Settings, `/local_disk0/codexwork/bundle/claude/settings.json:64-71`:

```json
    "deny": [
      "Read(./.env)",
      "Read(**/.env)",
      "Read(**/*.pem)",
      "Read(**/*.credentials*)"
    ],
    "ask": [],
    "defaultMode": "bypassPermissions",
```

Contract, `/local_disk0/codexwork/bundle/claude/AGENTS.md:115-123`:

```markdown
## 10. Instruction precedence (resolve collisions explicitly)

This contract's header says "provider addenda defer to it"; the metaswarm project `CLAUDE.md` says
its workflow-enforcement rules "override conflicting instructions from third-party skills/plugins."
These do NOT truly collide — they govern different axes. Precedence, highest first:

1. The user's explicit in-session instruction and the permission system.
2. **Security & safety non-negotiables** (§6, §9, §9b) — never overridden by any lower layer.
3. This cross-tool behavior contract (AGENTS.md §1-§11) — the shared floor all three tools read.
```

### Concrete collision

The user explicitly says, “Read `./.env` and tell me which variable names are present.” The user instruction and the permission system both apply and both occupy rank 1. The settings deny the Read call; the contract provides no ordering between the two rank-1 authorities and does not say that a user instruction is bounded by permissions.

This is not hypothetical unreachable syntax. `Read(./.env)` is an exact configured deny rule, and an explicit request to inspect one's own `.env` is an ordinary interactive situation. The separate credential hook even records that such workflows occurred: `/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:73-80` says the credential-read block “created setbacks in interactive sessions (inspecting one's OWN ~/.ssh keys / .env / config...)” and is therefore opt-in. That hook is not used as proof of current live frequency; it is evidence that the collision situation exists in this harness's operating domain.

### Runtime winner, verified

**The settings deny wins.** The official permission documentation says deny rules are evaluated before ask and allow and always take precedence. The same page says `bypassPermissions` skips prompts but does not move an allow above a deny. Therefore the native Read tool is rejected even though the request is user-explicit. A Bash subprocess is a separate loophole—official docs say Read/Edit deny patterns do not constrain Bash—but that does not resolve the precedence of the attempted Read call and must not be treated as the tie-break.

### Minimal edit

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Split rank 1 in `AGENTS.md` and make the capability ceiling explicit:

```markdown
1. The permission system and native safety enforcement: a deny/block is a hard capability ceiling.
2. The user's explicit in-session instruction, within that permitted capability set.
```

Renumber the remaining layers. Add one sentence: “An explicit user request does not override a native deny; change the permission rule through the normal permission/configuration path if the owner intends to authorize it.” This is a two-line contract correction; no new runtime exists. It is **almost certain (90-99%)** to remove this ambiguity because it states the already-documented runtime result; evidence is the configured deny and official deny-first rule.

### Concrete collision

An orchestrator gives agent `coder-1` scope `src/feature_a/**`; the agent attempts to edit `src/feature_b/impl.py`. The write is out of assigned scope but is still an ordinary reversible file edit. The settings-activated hook exits 2.

The invoked implementation states the behavior verbatim at `/local_disk0/codexwork/bundle/claude/hooks/file-scope/check.py:4-10`: “BLOCK (exit 2): a sidecar exists for this agent AND the target file_path does NOT match any allowed glob.” Lines 119-136 load a matching sidecar, compare the path, write `FILE-SCOPE BLOCK`, and return 2. The no-sidecar control is present and expected to allow at `test_file_scope.py:194-222`, demonstrating that the detector distinguishes known allow and block states rather than reporting every edit as blocked.

### Runtime winner, verified

**The hook wins:** a PreToolUse exit 2 stops the edit before permission evaluation, including in `bypassPermissions`, per official permission documentation. The implementation's `return 2` is at `check.py:127-136`; the settings matcher includes all four write tools.

Active Windows sidecars are **UNVERIFIED; run `python $HOME/.claude/hooks/file-scope/set_scope.py --list` on Windows to settle whether any scope is active now.** The unpacked snapshot contains the hook code but not mutable live state. The finding is the reachable policy contradiction created whenever the documented orchestrator feature is used, not a claim that a particular agent is blocked at this instant.

### Minimal edit

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Preserve the scope comparison and message, but return exit 0 with `hookSpecificOutput.additionalContext` for an out-of-scope path, matching §6. If file ownership must remain a hard concurrency lease, the alternative minimal edit is to amend §6 explicitly: “Deterministic cross-agent ownership leases may also block while a live lease exists,” and place that exception in the security/safety layer. Do not leave the exception implicit.

The inject-only change is **likely (55-80%)** to retain adequate practical isolation: evidence is that the agent receives an actionable scope correction, but model compliance is softer than a native deny. The contract-exception alternative is **very likely (80-90%)** to preserve isolation because it retains the deterministic exit-2 gate; evidence is the direct hook path and integration assertions. The owner must choose which invariant is load-bearing—§6's narrow blocking rule or hard multi-agent write leases—because no wording can make both current absolutes true.

## Finding 4 — explicit force-push approval still cannot win in-session

### Both texts verbatim

Settings, `/local_disk0/codexwork/bundle/claude/settings.json:151-160`:

```json
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python \"C:/Users/Prekzursil/.claude/hooks/no-force-push/hook.py\"",
            "timeout": 8,
            "statusMessage": "no-force-push: protect remote history"
          }
        ]
      },
```

Contract, `/local_disk0/codexwork/bundle/claude/AGENTS.md:93-98`:

```markdown
## 9. Security non-negotiables (all tools) — ALWAYS ON

- Never hardcode secrets; use environment variables and validate presence at startup.
- Never `--no-verify` on commits without explicit user instruction.
- Never `git push --force` to main/master without explicit user approval.
- Validate all user inputs at system boundaries; sanitize before HTML output.
```

The contract forbids the action **without** approval, which necessarily defines approval as the exception. Its precedence list also puts the user's explicit in-session instruction at rank 1 (`AGENTS.md:121`).

### Concrete collision

The owner explicitly approves `git push --force` to `main`, and Claude then issues the exact approved command. The activated hook's predicate matches any `git push ... --force` without checking branch or conversation approval (`/local_disk0/codexwork/bundle/claude/hooks/no-force-push/tripwire.py:15-18,39-47`). The hook returns exit 2 (`hook.py:45-56`).

The gate's message says, verbatim, “If approved, re-run with `FORGE_NO_FORCE_PUSH_OFF=1`” (`tripwire.py:17`), but the companion procedure says an opt-out is only for a confirmed false positive (`/local_disk0/codexwork/bundle/claude/hooks/no-force-push/SKILL.md:19-25`). More importantly, putting `FORGE_NO_FORCE_PUSH_OFF=1` inside the pending Bash command does not change the already-running hook process's environment. The opt-out must exist in Claude Code's process environment or a `.disabled` file before PreToolUse. Thus the settings have no in-session path by which the explicit approval itself wins.

### Runtime winner, verified

**The hook wins and blocks the approved command.** Official docs say PreToolUse exit 2 runs before permission evaluation and stops the tool call. Two executable checks passed on the job node:

- `python .../no-force-push/test_no_force_push.py` → `UNIT-PASS: no-force-push halts on trigger ... and allows otherwise`.
- `python .../no-force-push/chaos_no_force_push.py` → `CHAOS-PASS: gate blocks the dangerous op, allows benign ops, and fails open`.

These are mechanically different predicate/unit and subprocess/exit-code paths; the chaos test describes the exit-2 proof at `/local_disk0/codexwork/bundle/claude/hooks/no-force-push/chaos_no_force_push.py:2-8,116-127`. Neither test models conversation approval because neither runtime input contains such a field—which is exactly the missing tie-break.

### Minimal edit

**Proposal tag: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Replace the unconditional exit-2 response with native PreToolUse `permissionDecision: "ask"` for matched force-pushes. Claude Code evaluates hook asks even when the default mode is bypass; the permission page states explicit ask rules and hooks are evaluated before the mode check, and the hooks reference defines the native `ask` outcome. This makes a fresh, operation-specific human approval the runtime tie-break and removes the unverifiable conversation-state assumption.

This is **very likely (80-90%)** to resolve the contradiction while retaining protection: evidence is the native hook decision ordering and prompt behavior in official docs. The uncertainty is UX/version behavior on the owner's Windows build; settle it with a disposable bare remote and a harmless non-main test ref, verifying that a matched call opens a prompt, cancellation blocks, and approval executes exactly once. Never use `main` or a valuable remote for that experiment.

## Examined apparent conflicts that are not findings

### `bypassPermissions` versus behavioral prohibitions

Settings allow broad tool access (`settings.json:26-63`) and set `defaultMode` to `bypassPermissions` (`:71`), while the contract prohibits particular actions. Broad capability is not itself an instruction to perform every capable action. The stricter behavior rule can prevent the model from attempting an allowed call. This only becomes a true collision where a native deny/block and another authority prescribe opposite outcomes; those concrete cases are Findings 1 and 4. I therefore do not report every `allow` entry as a conflict.

### Credential denies versus security non-negotiables

The settings deny `.env`, PEM, and credential-file Reads (`settings.json:64-69`). §9 protects secrets and untrusted-content boundaries (`AGENTS.md:93-106`). Although reading one's own credential file can be reversible, model-context exposure is plausibly dangerous, and the contract's word “dangerous” is intentionally broader than its examples. There is no pair of texts explicitly requiring such reads. This is overbreadth/coverage territory, not a precedence ambiguity, so it is not a finding here.

### Plugin enablement versus plugin precedence

Eight plugins are enabled at `settings.json:572,589,600-607,621`: Codex, hookify, ralph-loop, remember, skill-creator, superpowers, claude-reflect, and metaswarm. Enabling a plugin is not itself a behavioral directive. The contract supplies an explicit ordering: project governance may add stricter process and overrides third-party defaults, while third-party defaults are rank 5 (`AGENTS.md:117-131`). Therefore “enabled” alone does not collide.

The installed/cached bodies of those eight plugins are **UNVERIFIED; inspect each live plugin's manifest, hooks, and instruction files on Windows to settle whether a plugin hook creates an additional native-enforcement conflict.** This gap does not justify inventing one from an enablement boolean.

### Codex collaboration layers

`CLAUDE.md:17` says, “DO NOT use both simultaneously — they serve different use cases.” Settings enable the Codex plugin (`settings.json:572`), but no settings key says to invoke both the Codex MCP and `multi-ai-mingle` in the same operation. Simultaneous availability is not simultaneous use. No collision.

### AgentBridge retirement

`CLAUDE.md:94-100` says AgentBridge budget enforcement is retired and no hooks enforce it. Settings explicitly disable `agentbridge@agentbridge` at `settings.json:637`. These agree.

### Auto-compaction and memory

Settings enable auto-compaction and define its window (`settings.json:686,697`); the contracts require memory pull/replay after compaction (`CLAUDE.md:5-11`; `AGENTS.md:28-34,85-91`). One configures when compaction occurs and the other governs recovery. They are complementary.

### Default test-tamper behavior

The test-tamper hook is wired at `settings.json:162-171`, but its block branch requires `TEST_TAMPER_MODE=block`; the implementation defaults to `warn` (`test-tamper-guard/guard.py:9,38,295-313`). That environment variable is not present in the complete settings `env` object (`settings.json:4-20`). In this snapshot the configured default is inject/warn, so it does not contradict §6. A live external environment override is **UNVERIFIED; run `Get-ChildItem Env:TEST_TAMPER_MODE` in the Claude-launch environment to settle it.** I do not promote that unverified possibility to a finding.

### Ulysses and stale-anchor blocks

Ulysses says its hard case is a genuinely dangerous irreversible live-memory action (`ulysses/enforce.py:4-13,53-73`). The stale-anchor gate blocks only a live write/patch to a retracted address/offset (`tms/stale_anchor.py:10-21,152-169,280-289`). Those fit §6's dangerous-action exception. Their state stores are not needed to establish coherence, and no contradiction was found.

## Final adjudication

This is not a “nothing found” audit. The contract does contain a precedence section, and it correctly orders third-party plugins, project governance, and safety in the abstract. It fails at the exact settings/runtime seams: co-ranking user intent with the permission system, and declaring inject-only behavior while settings activate native denials for availability and file ownership. The force-push seam is the most safety-sensitive: the prose defines approval as the exception, but the configured hook cannot observe or solicit that exception.

The smallest coherent target is: **native enforcement is the hard ceiling; user instructions operate inside it; every deliberate hard hook has an explicit named exception in §6; and operations requiring user approval use native `ask`, not an out-of-band environment escape hatch.**
