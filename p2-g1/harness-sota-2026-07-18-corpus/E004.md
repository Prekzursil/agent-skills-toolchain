# E004 — ecosystem survey: MCP security and prompt-injection surface

**Unit:** E004  
**Research date:** 2026-07-19 UTC  
**Scope:** What exists in the MCP-security ecosystem, which projects are high quality or dormant, and which ideas or implementations are worth adopting in this owner's Claude/Codex harness under the stated anti-overfit gate.  
**Mutation boundary:** Read-only on the unpacked subject. This file is the only artifact written.

## Executive verdict

The ecosystem has matured into four distinct layers: (1) protocol and host-native consent/authorization controls; (2) pre-deployment inventory and scanners; (3) runtime wrappers/gateways; and (4) attack benchmarks. The frontier is not “find the best prompt-injection regex.” The strongest current evidence says scanner signals are noisy and inconsistent: the July 2026 MCPZoo study dynamically assembled 64,611 unique servers, found existing scanners labeling 96.89% risky, and manually validated fewer than half of sampled alerts as true positives ([paper](https://arxiv.org/abs/2607.11086)). At the same time, the MCP specification explicitly says tool metadata is untrusted and clients should show tool inputs, confirm sensitive operations, validate results, and log use ([MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)).

For this owner, **full replacement with an MCP gateway is not justified**. It duplicates a shared hook/dispatcher that already sees Claude and Codex tool calls, and it violates the explicit rejection of a second orchestration runtime or guardrail framework. The best architecture is a small strengthening of the existing bus:

1. retain native host trust, permission, and output-replacement controls;
2. pin the MCP launch artifact and the canonical advertised tool surface;
3. classify external-content sources and consequential sinks deterministically, independent of English injection signatures;
4. carry a short-lived untrusted-provenance bit from source to sink and force a native approval at the sink;
5. run one pinned scanner only at admission/change time, as advisory evidence after a local bake-off; and
6. evaluate the mechanism with a small, attributed subset of the ICLR 2026 MCP Security Bench rather than installing its second agent runtime.

This six-part design is **very likely (80-90%)** to reduce the materially dangerous MCP injection chains without recreating a security platform: evidence is the existing cross-provider PreToolUse/PostToolUse dispatcher, Claude's documented hook decisions, the specification's explicit source/result/sensitive-call boundary, and the subject's broad no-approval surface. The exact precision and operator-friction improvement is **UNVERIFIED; the settling experiment is the 30-day shadow run and source→sink canary suite specified in §8**.

The highest-value ecosystem adoption is therefore **ideas and test data, not another always-on product**. Snyk Agent Scan and Cisco MCP Scanner are high-quality active scanner candidates; Trail of Bits' exact tool-surface pinning is the strongest deterministic design to borrow. ToolHive, IBM ContextForge, Lasso MCP Gateway, Trail of Bits' complete wrapper, and runtime “firewalls” fail the anti-overfit gate here even where their engineering is sound.

### 2.2 Both hosts suppress the ordinary human boundary

Claude settings broadly allow `Read`, shell, web, task, and many MCP namespaces, set an empty `ask` list, use `defaultMode: bypassPermissions`, and add the whole C: and D: drives (`claude/settings.json:26-75`). This is the exact “toxic flow” Snyk's issue model names: untrusted content, sensitive/private data, and destructive or outward authority ([Snyk issue-code reference](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md)). More importantly, the flow is visible directly in local policy, so the conclusion does not depend on Snyk's classifier.

The “incomplete” conclusion has two mechanically independent signals: branch-level source and a purpose-built behavior test. It also matches, but does not rely upon, audit F04.

The content classifier inherits the known live defect D1: regex scanners confuse use with mention. The mandatory defect input records false positives across destructive-command, marker, stub, and result sentinels, including a successful JSON result misclassified from a field name (`inputs/INPUT-known-harness-defects.md:1-101`). Promoting the English signature scanner directly from shadow to hard block is **very likely (80-90%)** to create harmful false blocks because four independently placed regex detectors already produced this semantic-role failure; **UNVERIFIED for this specific scanner mode, settle by replaying all recorded D1 benign cases with enforcement forced on before any promotion**.

### 2.4 The existing bus is the right integration point

Claude registers the shared dispatcher on `PreToolUse` for shell, writes, Task, WebFetch, and every `mcp__.*` name (`claude/settings.json:139-149`), and the local source proves a shared PostToolUse result path. Official Claude documentation says MCP tools appear in normal tool hooks, a PreToolUse hook may deny or force a prompt, and PostToolUse can replace output via `updatedToolOutput`/`updatedMCPToolOutput` ([hooks reference](https://code.claude.com/docs/en/hooks), [permissions](https://code.claude.com/docs/en/permissions)). This is a native enforcement bus, not a speculative extension.

The MCP specification independently says clients should prompt on sensitive operations, display tool inputs, validate results, use timeouts, and log tool use ([tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). The proposed architecture follows the protocol boundary and host bus rather than inserting a new protocol runtime.

## 3. Threat model: what a serious MCP security layer must cover

A useful survey must not collapse all MCP risk into prompt text. The applicable classes are:

1. **Admission/supply chain:** malicious or typosquatted package, unpinned `latest`, compromised release, unsafe launch command, hardcoded credentials.
2. **Tool-surface poisoning:** hostile instructions in server instructions, tool names/descriptions, parameter descriptions, or annotations before the first call.
3. **Rug pull / `list_changed`:** trusted metadata later changes after update or remote-server mutation. Claude explicitly supports dynamic `list_changed` refresh ([Claude MCP docs](https://code.claude.com/docs/en/mcp)).
4. **Indirect result injection:** web, email, document, repository, debugger, browser, or MCP result contains agent-steering text.
5. **Cross-server shadowing/composition:** a malicious tool description alters selection or invocation of a second trusted tool.
6. **Confused deputy and token abuse:** wrong-audience tokens, passthrough tokens, OAuth redirect/SSRF/session attacks. The official authorization specification requires resource/audience binding, validation, PKCE, secure redirects, and forbids passthrough ([authorization specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)); the security guide expands confused-deputy, SSRF, and session-hijack mitigations ([security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)).
7. **Excessive capability / toxic flow:** untrusted source plus sensitive read plus outward/mutating sink.
8. **Implementation vulnerability:** command injection, path traversal, SSRF, missing access control, vulnerable dependency, or unsafe Docker/RE bridge code.
9. **Deceptive presentation:** ANSI/control characters, user impersonation, false errors, and response replacement.
10. **Availability and stale surface:** dead servers, retry storms, overlarge outputs, and unused high-risk tools that enlarge the selection space.

No one surveyed tool covers all ten credibly. Semantic scanners mainly address 1, 2, 5, 7, and portions of 8; surface pinning addresses 3 deterministically; authorization libraries address 6; host hooks and permissions address 4, 7, and 9; dependency/version controls address 1 and 8. Defense must be compositional but minimal.

The exact file/commit license must therefore be checked before copying ([repository LICENSE](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/LICENSE)).
- **Fit here:** excellent as policy and test requirements. It cannot by itself enforce the owner's local no-approval configuration.

## 5. Adoption recommendations

Every proposal below passes the anti-overfit gate: it rides the existing config/hook/skill/MCP bus and does not add a second orchestrator, vector memory, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

### R1 — Native permission profiles for MCP sources and consequential sinks

**NATIVE-vs-BUILD: NATIVE (Claude Code already does this; we just enable it).**

Create explicit interactive and autonomous permission profiles. Auto-allow read-only, owner-reviewed MCP tools; require `ask` for outbound messages/posts/uploads, arbitrary URLs, financial/spend operations, cloud mutation, repository mutation, local-path upload, credential reads, and execution tools. Disable blanket `bypassPermissions` for the autonomous profile, or at minimum make the consequential MCP namespaces/tool names `ask` despite broad defaults. Preserve the owner's fast path for deterministic reads.

This is **almost certain (90-99%)** to restore a human boundary for calls matched by the profile because Claude documents deny/ask precedence over allow and PreToolUse decisions, while current settings explicitly have empty `ask` and `bypassPermissions` (`claude/settings.json:26-75`; [permissions docs](https://code.claude.com/docs/en/permissions)). Its exact productivity cost is **UNVERIFIED; settle with a one-week prompt-count/approval-acceptance shadow report before switching the default interactive profile**.

Why this beats scanner-only protection: it operates at the sink even when the injected content is paraphrased, multilingual, Unicode-obfuscated, or not recognized. It also covers accidental/hallucinated calls.

### R2 — Deterministic source→sink taint on the existing dispatcher

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add a small session-state record: when a result comes from any externally controlled source class—web/search/browser, email/social, public repository/docs, remote MCP resource, PDF, debugger/decompiler strings, or a subagent that consumed one—mark `untrusted_since=<tool_use_id>`. Do this unconditionally by capability classification; do not require an English signature. Before a consequential sink, attach the provenance chain and return native `ask`/deny unless the current user request explicitly authorized that exact target and effect. Clear or narrow the taint after the model summarizes into a data-only artifact or the user approves the sink.

This is **very likely (80-90%)** to block the canonical indirect-injection exfiltration chain because the source and sink are deterministic hook events and Claude supports PreToolUse decisions. Evidence: broad local source/sink capability, existing dispatcher registration, MCP spec confirmation guidance, and the current scanner's name-gated/shadow behavior. Precision is **UNVERIFIED; settle with the §8 canaries plus 30-day shadow telemetry, requiring ≥95% correct source classification and <1% unnecessary sink prompts on sampled ordinary turns**.

## 7. Architecture: minimal end state

The smallest useful flow is:

```text
admission/config change
  -> exact package/digest check
  -> capture canonical advertised tool surface
  -> optional one-shot advisory scan
  -> human approves surface digest

normal tool loop (existing host + dispatcher)
  source result -> unconditional source-class taint
                -> optional signature raises severity/quarantine
  next sink     -> deterministic source-to-sink check
                -> native allow / ask / deny
  all decisions -> existing event ledger receipt

surface/list_changed
  -> new canonical digest != approved digest
  -> changed tools unavailable pending review
```

This architecture separates questions that scanners often conflate:

- **Is this content externally controlled?** Deterministic capability/provenance classification.
- **Does it resemble a known attack?** Advisory signature/scanner evidence.
- **Did the server surface change?** Deterministic canonical hash/diff.
- **May this exact consequential effect occur now?** Native permission decision tied to current user authorization.

It also handles the known D1 defect: prose about attacks can trigger a signature, as the mandatory defect input directly records, but under this architecture it cannot manufacture untrusted provenance or a consequential sink. A false signature becomes an advisory/quarantine-review cost, not a false claim that a successful call failed and not an automatic denial of harmless documentation.

## 8. Verification program and acceptance gates

### 8.1 Detector controls first

Every probe must demonstrate a known-positive control before an absence claim:

1. Hook schema detector finds a known `WebFetch` PostToolUse event before judging `list_changed` absent.
2. Surface detector finds a known tool name/description/schema from a toy MCP before judging host metadata unavailable.
3. Config inventory finds the known `tavily` and disabled `semgrep` entries before reporting a missing server.
4. Scanner fixture detects its own documented canonical injection before reporting an attack category uncovered.
5. Sink classifier finds a known `send_message`/upload fixture before claiming a namespace contains no sinks.

### 8.2 Inert end-to-end canaries

Build a toy MCP with no external side effects and the following surfaces:

- clean read tool;
- malicious tool description instructing use of another server;
- changed description after `list_changed`;
- out-of-scope parameter request;
- result containing canonical, paraphrased, full-width, zero-width, multilingual, ANSI, and bidi attacks;
- result falsely claiming user authorization;
- false-error escalation;
- read of a canary local file followed by POST to an owned loopback-only sink; and
- benign security documentation mentioning every attack phrase.

Run it under both Claude and Codex in interactive and autonomous profiles. No live credential, third-party message, cloud mutation, or internet egress is necessary.

### 8.3 Promotion thresholds

- Source classification: ≥95% recall on known external sources and ≥95% precision on trusted/local deterministic results.
- Sink classification: 100% recall on the enumerated irreversible/outbound/credential/spend fixtures.
- Surface drift: 100% detection of semantic tool metadata/schema changes; zero alerts for property/tool ordering only.
- Signature/quarantine: ≥90% attack recall, ≥80% precision, and zero D1 self-documentation hard blocks.
- Operator friction: <1% unnecessary sink prompts over a manually sampled ordinary-work shadow window.
- Scanner: the R5 thresholds; no scanner hard-blocks on its own.
- Reliability: hook timeout/error must not silently allow a high-risk sink. Exact fail-closed behavior is **UNVERIFIED; settle with a synthetic timeout/exception canary before promotion**.

### 8.4 Rollout ladder

1. Offline fixtures only.
2. Shadow decisions in the existing event ledger.
3. Advise on surface changes and source→sink chains.
4. Ask on enumerated sinks; keep read-only sources automatic.
5. Deny only deterministic invariants: unapproved changed surface, explicitly denied credential path, invalid package digest, or exact user-scope mismatch.

The 30-day rollout is **likely (55-80%)** to produce enough ordinary-work samples for a stable prompt-friction estimate because corpus tool volume is high; the exact number depends on current use and is **UNVERIFIED; settle by predeclaring a minimum of 200 classified source/sink events rather than relying on elapsed time alone**.

## 9. Alternatives considered and dead ends

### “Turn the existing regex quarantine to enforce”

Rejected. It is cheap but directly conflicts with live D1 evidence that scanners treat prose and JSON field names as executable facts. It also misses unrecognized tool names, Unicode, paraphrases, and non-English content. Promote provenance and sink decisions; keep signatures as severity evidence.

### “Put every MCP behind Trail of Bits/ToolHive/Lasso/IBM”

Rejected under the explicit gate. Trail of Bits offers the best deterministic surface mechanism, but its wrapper duplicates the existing cross-provider bus. ToolHive and IBM are credible for multi-tenant enterprises, not minimal single-owner harnesses. A proxy also creates a new liveness and quoting layer on a Windows fleet already suffering spawn/path and orphan-inflated command-line failures.

The assertion that another wrapper would worsen observed Windows spawn reliability is **likely (55-80%)** because it adds processes/commands to a fleet with measured ENAMETOOLONG/os-error-206 and quote failures; **UNVERIFIED, settle only with a cold-start/error-rate comparison in a disposable profile**.

### “Use an LLM judge on every response”

Rejected. It is a trained-critic/guardrail framework, adds cost/latency/data exposure, and current large-scale research finds scanner inconsistency and <50% true positives in sampled alerts. A learned score is permitted only as an offline advisory in the bake-off, never the trust boundary.

### “Install every scanner for defense in depth”

Rejected. Scanner disagreement is not automatically independent evidence; many tools inspect the same metadata with similar lexical/LLM heuristics. More scanners multiply false positives and supply-chain dependencies. The correct response to MCPZoo is calibration and one selected advisory scanner, not voting among noisy detectors.

### “Sandbox all MCPs in containers/microVMs”

Rejected here because the owner explicitly lists OS/microVM sandboxing among previously rejected/deferred components, and the local memory index independently records that decision (`claude/hooks/recall-inject/index/recall_index.json:6858-6889`). Native Claude sandbox profiles remain allowed because they are an existing host feature rather than a new runtime.

### “Rely on package version pinning alone”

Rejected as incomplete. Exact versions stop silent upgrades, but remote HTTP server metadata can change without local config change, and a pinned first version can already be malicious. Bind artifact identity to reviewed advertised surface and retain sink approval.

### “Treat MCP output as safe after sanitization”

Rejected. Output sanitization can remove control sequences and known signatures, but semantic adversarial instructions cannot be reliably transformed into trusted content. Provenance survives sanitization.
