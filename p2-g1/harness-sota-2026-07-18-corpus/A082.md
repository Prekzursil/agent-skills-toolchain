# A082 — Coherence audit of `~/.claude/rules/web/testing.md`

## Executive verdict

The rule has a useful web-verification checklist, but it is not a coherent executable contract. I found **eleven reportable collisions/defects** in the material available on the job node: one path-scope break that prevents the claimed common-rule inheritance for five of the target's nine extensions; three ambiguous/redundant rule overlaps; an active Stop hook that silently depends on an **unregistered** evidence producer; a Windows-primary shell blind spot; two non-dangerous block paths that violate the higher-precedence behavior contract; an unruled all-journeys requirement; and no active mechanism that checks most of the web rule's distinctive requirements. I also found a recurring corpus signal that the inherited 80% fallback is below this owner's repeatedly requested 100% bar, although turning that session-level preference into a global default remains **UNVERIFIED — ask the owner whether 100% is the universal fallback, then run the same representative repositories under 80% and 100% gates to measure feasibility**.

The required skills comparison could not be completed because the remote bundle contains neither `claude/skills/` nor `agents/skills/`. This is not evidence that those trees are absent on the Windows subject. It is a bundle gap, documented in §8.

The most urgent repair is the broken journey-evidence chain. `journey-coverage` is registered as an active Stop check (`claude/hooks/_dispatch/manifest.json:133-141`) and reads successful commands from the claim-guard ledger (`claude/hooks/journey-coverage/check.py:144-162,221-224`), but neither `claude/settings.json` nor the active dispatcher manifest registers `claim-guard/ledger-write.py`. The producer itself rejects every tool except `Bash` (`claude/hooks/claim-guard/ledger-write.py:174-179`), while the governing contract says this is a Windows box with PowerShell primary (`claude/AGENTS.md:133-140`). Thus the hook cannot reliably distinguish “journeys not run” from “evidence was never recorded.”

## 4. Rule-to-rule collisions

### C1 — Claimed common inheritance does not cover five web extensions

**Exact lines.** The target applies to TSX, JSX, TS, JS, CSS, SCSS, HTML, Vue, and Svelte (`web/testing.md:2-11`) and says it extends common testing (`:13`). The common testing rule's front matter covers executable-language extensions through `.sh` but not `.css`, `.scss`, `.html`, `.vue`, or `.svelte` (`common/testing.md:2-20`). The target later says visual regression does not replace “coverage targets” (`web/testing.md:67`), while those targets live in the common rule (`common/testing.md:23,38`).

**Why this is a collision.** A Markdown link is documentation, not evidence that Claude Code loads the linked rule for a path excluded by its front matter. For a pure `.css`, `.scss`, `.html`, `.vue`, or `.svelte` edit, the target claims an extension relationship that its path scopes do not implement. “Coverage targets” is also ill-defined for non-executable CSS/HTML.

**Class:** STALE / UNENFORCED.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Align front matter and semantics: include `.vue`/`.svelte` in common testing if their script blocks are expected to carry unit coverage; do not impose line coverage on CSS/HTML; replace target line 67 with an explicit rule such as “visual tests supplement, and do not replace, executable-code coverage or behavioral assertions.” This is **almost certain (90-99%)** to remove the load-scope ambiguity because both evidence-bearing path lists would then agree; evidence is the directly mismatched front matter above.

### C2 — Two unexplained breakpoint thresholds in one rule

**Exact lines.** Visual regression screenshots list 320, 768, 1024, and 1440 (`web/testing.md:19-24`). Responsive testing lists 320, 375, 768, 1024, 1440, and 1920 (`:43-47`).

**Why this is a collision.** These can coherently be a four-width screenshot smoke set and a six-width functional layout set, but the file never says that. An agent may either omit 375/1920 visual states or unnecessarily screenshot every state at all six widths. The differing thresholds are therefore redundant with an unstated distinction, not a direct logical contradiction.

**Class:** REDUNDANCY.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Define named matrices: `visual-smoke = [320,768,1024,1440]`; `responsive-functional = [320,375,768,1024,1440,1920]`. State whether key themes/states multiply each matrix. It is **very likely (80-90%)** that explicit matrix names reduce divergent interpretations; evidence is the current two unlabeled overlapping sets, while the residual uncertainty is that no behavioral trace links a mistake to these lines.

### C3 — “Priority Order” competes with mandatory test-first sequencing

**Exact lines.** The target declares “Priority Order” and makes visual regression item 1, accessibility item 2, and performance item 3 (`web/testing.md:17-36`). The common rule calls RED→GREEN→IMPROVE a mandatory workflow (`common/testing.md:30-38`); development workflow repeats test-first sequencing (`common/development-workflow.md:43-48`).

**Why this is a collision.** “Priority” could mean risk/investment priority, execution order, or what to omit first. If read as execution order, screenshot work precedes the common mandatory write-a-failing-test step. If read as risk priority, there is no conflict. The rule does not disambiguate.

**Class:** CONTRADICTION (ambiguous ordering).

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Rename the section “Web verification dimensions, in risk-prioritization order” and explicitly say that common RED→GREEN sequencing still governs behavior changes. This is **very likely (80-90%)** to preserve both intents because it assigns the two orderings to different axes; evidence is the otherwise incompatible use of “Priority Order” and “MANDATORY workflow.”

### C4 — Duplicate Playwright authority at the same precedence level

**Exact lines.** Web testing says to use Playwright screenshots and gives a Playwright test example (`web/testing.md:23,49-58`). TypeScript testing says “Use Playwright as the E2E testing framework” (`typescript/testing.md:12-14`). Both path scopes include `.ts/.tsx/.js/.jsx` (`web/testing.md:2-6`; `typescript/testing.md:2-6`).

**Class:** REDUNDANCY.

**Precedence.** `rules/README.md:93-98` only says specific beats common; it does not order `web/` against `typescript/`. AGENTS §10 says surface same-level conflicts. The statements agree today, but duplicate authority can drift.

**Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Keep framework selection in `typescript/testing.md` or a single shared browser-testing rule. Let `web/testing.md` specify web-only visual, accessibility, and matrix expectations. It is **likely (55-80%)** this prevents future drift; evidence is duplicate same-scope authority, but no current divergent value exists.

### C10 — Inherited 80% fallback versus repeated owner 100% requests — UNVERIFIED global recommendation

**Exact lines.** Common testing uses `.coverage-thresholds.json`, with “100% on metaswarm; 80%+ where none is defined” (`common/testing.md:23,38`); target inherits it and says visuals do not replace coverage (`web/testing.md:13,67`). It is potentially **wrong for this owner** because the fallback is lower than repeated explicit requests. It is **likely (55-80%)** that 100% is the desired default, based on the independent recurring correction samples and the quality-over-cost rule. **Resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only), UNVERIFIED premise.** Ask the owner whether 100% should be the default when no repository threshold exists; settle feasibility by running representative frontend repositories with line+branch thresholds at both 80 and 100 and recording mutation/defect yield. ## 7. Measured corpus: followed, contradicted, or unmeasurable?

### What is positively supported

- Playwright is genuinely used: the corpus records the server 194 times (`corpus.json:13383-13388`), `browser_evaluate` 49 calls with no errors (`:559-564`), screenshot 32 calls with 4 errors (`:719-724`), and resize 8 calls with no errors (`:1639-1644`). It is **likely (55-80%)** that a required visual gate needs retry/stability guidance or artifact-aware failure handling; evidence is 4/32 errors, but the sample is small and mixes unknown projects.
- The rule's web testing behavior is not broadly routed through a named specialist in the capability aggregate. The enumerated agents include code-reviewer/planner/etc. but no `e2e-runner` or `tdd-guide` (`corpus.json:13346-13368`), while the skills list includes `ui-audit` five times (`:13284-13296`). This does not prove the underlying behavior never happened manually.

### What the corpus cannot answer

The corpus distillation does not retain a general per-session command stream or associate web edits with subsequent verification commands. Therefore it cannot establish:

- whether screenshots used the mandated widths;
- whether both themes were tested;
- whether accessibility automation, keyboard navigation, reduced motion, or contrast were checked;
- whether Lighthouse/CWV targets were run/met;
- whether Chrome, Firefox, and Safari all ran;
- whether responsive overflow/touch behavior was verified;
- whether unit/integration/E2E tests and coverage followed each applicable web change;
- whether fixed-timeout assertions were avoided.

I found no `lighthouse`, `firefox`, or `safari` string in the distilled corpus, but I do **not** report those behaviors absent: shell command bodies are not comprehensively indexed, browser choice may not appear in tool names, and a zero string match is not a mechanically independent behavioral signal. The settling experiment is to re-mine raw transcripts into `(session, edited extensions, command, exit, browser/project, viewport, artifact)` records and compare web-edit sessions against the declared matrix.
