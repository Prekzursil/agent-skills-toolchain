**Unit:** P2B14

## Executive verdict

Amp is not a generally more capable harness than this one. Its strongest ideas are unusually coherent product integration: a thread is simultaneously the agent loop, the shareable/auditable record, the remotely controllable unit, and the execution handle; plugins expose one typed surface for lifecycle interception, tools, commands, UI, and custom agents; and code-review “checks” turn small Markdown policies into isolated review agents. Amp also makes raw prior threads directly searchable and referenceable by the agent. Those are real design wins.

Most of Amp's headline mechanisms are already available in the owner's current Claude Code build, often with better safety or control:

- automatic compaction, rewind/fork, file checkpoints, remote control, cloud tasks, deferred MCP tool search, project-MCP trust, skills, hooks, custom agents, agent teams, and cross-agent messaging are native Claude Code capabilities;
- the installed Claude Code is `2.1.214`, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` is enabled, and `ENABLE_TOOL_SEARCH=auto:5` is configured (`C:\Users\Prekzursil\.claude\settings.json:7,17`; probe: `claude --version` returned `2.1.214`);
- the owner already has stronger semantic memory than Amp documents: basic-memory recall/capture plus compaction checkpoints (`C:\Users\Prekzursil\.claude\CLAUDE.md:5-11`);
- the owner already has cross-vendor fan-out and live peer dialogue (`C:\Users\Prekzursil\.claude\CLAUDE.md:19-67`), while Amp subagents explicitly cannot talk to each other or be guided mid-task ([Amp manual, lines 388-395](https://ampcode.com/manual));
- the owner already has specialized review agents and completion-claim gates (`C:\Users\Prekzursil\.claude\agents\code-reviewer.md:3`, `python-reviewer.md:3`, `typescript-reviewer.md:3`; `C:\Users\Prekzursil\.agents\harness\modules.py:2000-2124`).

The short list worth borrowing is therefore:

1. **BUILD-SMALL:** agent-callable search and selective extraction over raw historical sessions, complementary to basic-memory rather than replacing it.
2. **BUILD-SMALL:** a declarative `.agents/checks/*.md` convention and one lightweight review skill that fans checks out to native subagents and merges findings.
3. **CONFIG:** make the existing native remote-control/cloud-task surfaces discoverable and use them before considering an Amp-like control plane.
4. **CONFIG:** use native MCP deferral, health state, approval, and explicit server disablement more aggressively; do not copy Amp's skill-coupled server startup literally.

Do **not** copy Amp's permissive default, removal of reliable rollback, cloud-first thread retention, or distributed durable runtime. The last item is a previously rejected durable-execution engine and fails this program's anti-overfit gate unless native Claude Code cloud execution proves insufficient in a measured owner workload.

## 1. Agent loop

### What Amp actually does

Amp defines an agent as model + system prompt + tools and exposes four modes: low, medium, high, and ultra ([manual, lines 127-138](https://ampcode.com/manual)). The current model page shows that a mode is a bundled system-prompt/tool/model choice, not merely a temperature knob: low uses GLM-5.2, medium/high use GPT-5.6 Sol at different reasoning levels, and ultra uses Claude Fable 5; Oracle is deliberately a second model, and in high mode it switches vendor/model so the second opinion differs from the main agent ([Amp models, lines 6-19](https://ampcode.com/modes)). Specialized models handle review, search, thread reading, media, image generation, titling, and compaction ([Amp models, lines 73-110](https://ampcode.com/modes)).

The visible turn lifecycle is simple and programmable:

```text
session.start -> agent.start -> (tool.call -> tool.result)* -> agent.end
```

Amp documents that multiple threads can continue in one CLI, and an `agent.end` handler can append a synthetic user message to continue the loop ([manual, lines 598-608 and 664-684](https://ampcode.com/manual)). A busy thread queues messages by default; the user can steer at the next step boundary or interrupt immediately ([Amp Rebuilt, lines 102-113](https://ampcode.com/news/neo)).

Since the 2026 rebuild, Amp describes the thread loop as durably executed in a distributed system and remotely controllable ([Agents, Everywhere, lines 4-14](https://ampcode.com/news/agents-everywhere)). Orbs provide one fresh remote machine per thread, while runners let the web create threads on an existing machine ([manual, lines 292-302](https://ampcode.com/manual); [Orbs, lines 43-74](https://ampcode.com/manual/orbs)).

### Comparison

The owner's harness already covers the effective model-routing and peer-review outcomes. Its documented Layer 1 can fan out native Codex MCP calls and its Layer 2 supports live Claude/Codex dialogue (`C:\Users\Prekzursil\.claude\CLAUDE.md:19-67`). Claude Code itself describes work as gather context, take action, verify results and automatically compacts when needed ([Claude Code “How it works”](https://code.claude.com/docs/en/how-claude-code-works)). Native web tasks run independently in cloud VMs and can be steered from web/mobile ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)); native Remote Control can serve up to 32 concurrent local sessions and optionally isolate them in worktrees ([Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)).

Amp's exact durable-thread actor is a real implementation difference, not a demonstrated owner-value gap.

### **BUILD-LARGE — Do not port Amp's durable distributed loop**

**Classification:** BUILD-LARGE (new daemon/service/runtime — needs its own justification).

This would reintroduce the explicitly rejected durable-execution engine. It fails the anti-overfit gate because Claude Code already supplies cloud tasks and remote control on its native bus. A local replacement would need durable queues, leases, cancellation, event ordering, resumable tool calls, workspace isolation, authentication, secret delivery, logs, UI, and recovery semantics.

It is **very unlikely (5-20%)** that a second durable runtime would improve this owner's aggregate harness reliability, because the measured failures are tool/configuration failures—dead MCP calls, schemas, Windows command length, and quoting—not turn-loss failures. The settling experiment is **EXPERIMENT LOOP-NEED-1**: sample 100 recent long tasks and count tasks lost solely because the native Claude process/cloud task could not resume, excluding tool failure and user cancellation. Do not revisit BUILD-LARGE unless that measured loss is material.

### **CONFIG — Expose native execution modes instead**

**Classification:** CONFIG (settings/JSON only).

Make a compact operator card that routes “continue this local session from phone” to native Remote Control and “run independently in a clean cloud VM” to native web tasks. Remote Control has already been used according to `.claude.json` (`remote-control` counters at lines 37 and 3448), but the harness rules do not make it a prominent route.

This is **very likely (80-90%)** to capture most of Amp's remote-loop value with almost no new failure surface, because the native product already supplies synchronized multi-device steering, worktree spawning, cloud execution, and task inspection; the remaining uncertainty is how often this owner wants mobile/web operation.

## 2. Context management

### Amp's mechanisms

Amp's context model is transparent: a thread roughly corresponds to the context window, containing messages, replies, tool calls, system prompt, tool definitions, AGENTS.md, and environment/editor state ([context guide, lines 41-56](https://ampcode.com/guides/context-management)). Files can be explicitly mentioned; text is truncated at 500 lines and 2 KB per line ([context guide, lines 70-79](https://ampcode.com/guides/context-management)).

The old context guide describes editing a prior message, restoring to an earlier point, handoff to a fresh thread, and using a second model to extract relevant material from a referenced thread ([context guide, lines 80-108](https://ampcode.com/guides/context-management)). The newer 2026 architecture supersedes part of that guide: Amp now compacts automatically at 90%, removed handoff, and no longer rolls back files when a message is edited or restored ([Amp Rebuilt, lines 28-43 and 146-160](https://ampcode.com/news/neo)). Referenced-thread extraction remains.

This documentation drift is important: do not design against the obsolete handoff behavior. The current Amp model page independently lists a “Read Thread” summarization model and a compaction model ([Amp models, lines 83-110](https://ampcode.com/modes)), corroborating the new architecture's two surviving mechanisms.

### Comparison

Claude Code already compacts automatically, clears old tool output first, then summarizes; it supports `/compact` instructions and a `Compact Instructions` section ([Claude context documentation](https://code.claude.com/docs/en/how-claude-code-works)). `/rewind` can restore conversation, code, or summarize from a selected point ([Claude best practices](https://code.claude.com/docs/en/best-practices)); native checkpointing is more reliable than Amp's current “ask the model to undo” posture ([Claude sessions](https://code.claude.com/docs/en/sessions)).

Therefore:

- **NATIVE (Claude Code already does this; we just enable it):** automatic compaction, manual focused compaction, rewind, fork, and checkpoints. No Amp port is needed.
- Amp is worse for recovery because it intentionally removed file rollback. Its explanation admits the prior rollback was best-effort and prefers model-authored undo ([Amp Rebuilt, lines 153-157](https://ampcode.com/news/neo)). Native Claude checkpoints should remain authoritative; a model cannot reliably undo an opaque generator, migration, remote API call, or shell redirect.
- Amp's fixed 90% compaction threshold is simple, but the owner already has compaction checkpoints plus semantic recall (`C:\Users\Prekzursil\.claude\CLAUDE.md:7-11`). Copying the number would be cargo culting without a controlled quality/cost comparison.

### **BUILD-SMALL — Raw-thread search and relevance extraction**

**Classification:** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).

Amp can search historical personal/team threads by keyword, file path, repository, author, date, task, and relatedness, then use `read_thread` to have a second model extract only prompt-relevant information ([manual, lines 229-251](https://ampcode.com/manual); [context guide, lines 103-108](https://ampcode.com/guides/context-management)).

The owner has adjacent but non-equivalent mechanisms:

- basic-memory semantically recalls deliberately persisted facts and checkpoints (`C:\Users\Prekzursil\.claude\CLAUDE.md:5-11`);
- `/sessions` lists/loads manually saved Markdown sessions, but its `--search` searches only session IDs (`C:\Users\Prekzursil\.claude\commands\sessions.md:2-7,59,297`);
- `/resume-session` reads an entire selected saved-session file (`C:\Users\Prekzursil\.claude\commands\resume-session.md:49`);
- native Claude transcripts exist as JSONL and the corpus miner has already parsed 11,633 of them.

Two independent local probes support the narrow gap: source search found the known-present basic-memory recall and session-management commands, while a separate search for Amp-like `.agents/checks`/thread-extraction conventions found no raw-session relevance extractor in the shared harness roots. This does **not** claim no such code exists anywhere on the machine.

Concrete port:

1. Add a `thread-recall` skill with a bundled read-only script, not a daemon and not a new vector database.
2. Scan native `~/.claude/projects/**/*.jsonl` incrementally by mtime; extract only metadata and normalized user/assistant text. Reuse the existing content-hash/cache patterns.
3. Support filters `q`, `file`, `project`, `repo`, `branch`, `after`, `before`, and `session_id`; return bounded snippets and transcript paths, never whole transcripts by default.
4. On selection, spawn one native read-only subagent with the current goal plus bounded transcript slices and request a structured handoff: decisions, evidence, failures/not-to-retry, changed files, and unresolved items.
5. Keep basic-memory canonical for durable facts. Raw-thread recall is provenance/recovery, not memory replacement.
6. Measure retrieval precision against owner-selected relevant sessions before routing automatically.

This is **likely (55-80%)** to save time on continuity failures, because the local command can only search IDs while Amp's filters include semantic work attributes, and the raw transcript corpus is already available. Confidence is not higher because basic-memory plus native `/resume` may already cover most real owner cases. **EXPERIMENT THREAD-RECALL-1** settles value: select 30 “where did we solve X?” owner queries, blind-compare basic-memory alone versus basic-memory + raw-thread retrieval on precision@5, time-to-evidence, and context tokens.

## 3. Memory

Amp does not document a separate fact/preference memory store comparable to basic-memory or Claude auto memory. What it documents is durable cloud thread storage, search, sharing, and referenced-thread extraction. The Amp Server stores conversations in PostgreSQL on Google Cloud to enable sharing and auditing ([Amp security reference, lines 145-152](https://ampcode.com/security)). Threads can be private, unlisted, workspace-shared, or group-shared, but workspace admins can view private threads ([manual, lines 1003-1020](https://ampcode.com/manual)).

The owner's memory architecture is stronger for an individual harness:

- basic-memory stores durable semantic notes and explicit temporal supersession (`C:\Users\Prekzursil\.claude\CLAUDE.md:5-11`);
- the shared harness has sanitized checkpoint and bounded recall modules (`C:\Users\Prekzursil\.agents\harness\modules.py:1440,1572`);
- the corpus observed 1,332 basic-memory calls, making it the second-most-used MCP server in the measured history;
- current Claude Code also has native plain-Markdown auto memory, loaded by project and editable by the user ([Claude memory documentation](https://code.claude.com/docs/en/memory)).

Amp is worse on privacy/control: cloud persistence is mandatory for its collaborative thread model, it offers no self-hosted deployment, and private workspace threads remain admin-visible ([Amp security reference, lines 145-152](https://ampcode.com/security)). The owner’s canonical vault is local and tool-independent.

### **BUILD-LARGE — Do not copy Amp's team thread feed**

**Classification:** BUILD-LARGE (new daemon/service/runtime — needs its own justification).

An organization-wide searchable feed with visibility ACLs, groups, mobile/web UI, audit logs, and live synchronization would require a service and database. That is unnecessary for a single owner and overlaps native Claude web/session UI.

It is **almost certainly not (1-5%)** worth building for this owner because the evidence shows a single-owner local vault and no measured collaboration-search failure, while Amp's implementation adds cloud retention and ACL complexity. The raw-thread BUILD-SMALL port above captures the useful retrieval behavior without copying the collaboration product.

## 4. Tools and MCP handling

### Amp's mechanisms

Amp supports local and remote MCP servers, OAuth, explicit workspace-server approval, precedence across CLI/user/workspace/skill sources, and an `amp mcp doctor` state for pending approval ([manual, lines 470-543](https://ampcode.com/manual)). Skills can bundle an `mcp.json`; the server starts with Amp, but its tools remain hidden until the skill loads. `includeTools` filters names/globs ([manual, lines 353-387](https://ampcode.com/manual)). Amp recommends this arrangement to reduce tool-list/context bloat.

### Comparison

Current Claude Code already does the important parts and in some respects goes further:

- MCP Tool Search is on by default; definitions are deferred and only selected tools enter context ([Claude MCP documentation](https://code.claude.com/docs/en/mcp)). The owner's explicit `ENABLE_TOOL_SEARCH=auto:5` appears at `C:\Users\Prekzursil\.claude\settings.json:17`.
- Project MCP servers require trust/approval, a cloned repository cannot approve its own server, and rejected servers can be disabled in settings ([Claude MCP docs, lines 249-270](https://code.claude.com/docs/en/mcp)).
- HTTP/SSE servers reconnect with exponential backoff and become failed after bounded retries ([same source, lines 263-270](https://code.claude.com/docs/en/mcp)).
- Claude supports dynamic MCP `list_changed`, resources, OAuth, and tool-specific mandatory human approval ([Claude MCP docs](https://code.claude.com/docs/en/mcp)).

The owner’s measured problem is deployment hygiene, not missing discovery: the corpus contains 93 distinct MCP servers and a dead Tavily path repeatedly called. Amp's advice to keep the exposed set small is sound, but Amp's skill-level server startup still starts every bundled server at launch and therefore does not eliminate process/connect overhead; it primarily hides tool definitions.

### **CONFIG — Adopt Amp's selective-exposure discipline on native Tool Search**

**Classification:** CONFIG (settings/JSON only).

1. Keep `ENABLE_TOOL_SEARCH=auto:5` or test the current native default against it; do not add a new router.
2. Disable/remove servers after a bounded failed-health threshold and require an explicit task route to re-enable heavy/domain-specific servers.
3. Prefer fewer high-level tools with good server instructions; use native Tool Search rather than copying skill-coupled MCP startup.
4. Use project scope for repo-specific MCP and retain native workspace trust.
5. Treat server names as capability identifiers and maintain one live provider per redundant capability unless measured fallback value exceeds its failure/context cost.

This is **very likely (80-90%)** to improve reliability because dead-MCP calls are measured, while Tool Search and approval are already working native mechanisms. The uncertainty is which redundant servers carry unique owner value. **EXPERIMENT MCP-CURATE-1**: replay 100 representative MCP intents against the curated set and compare success, latency, and missing-capability rate before deleting any configuration.

### Where Amp is worse

- Amp's public manual exposes `includeTools` but no documented per-tool result-size annotations comparable to Claude's MCP result-size controls and warnings.
- Starting skill-bundled servers at launch while hiding tools can still waste Windows processes and command-line budget. Given this machine's orphaned-plugin/Windows CreateProcess failures, “hidden” must not be conflated with “not started.”
- Amp's default execution posture trusts tools far more broadly than this harness should.

## 5. Permission and security model

Amp intentionally does not ask before tool calls. Its security warning tells users of untrusted repositories/MCPs to write a policy plugin or use isolation ([manual, lines 302-309](https://ampcode.com/manual)). The 2026 announcement explicitly made the former dangerous-allow-all behavior the default, arguing that static shell matching creates false confidence when models write scripts and chain commands ([Amp Rebuilt, lines 114-131](https://ampcode.com/news/neo)).

The plugin API can intercept `tool.call` and return allow, reject-and-continue, modify, or synthesize; `tool.result` can replace status/output before the model sees it ([manual, lines 616-650](https://ampcode.com/manual)). Plugins can also ask a small thread-scoped AI classifier and present a confirmation UI ([manual, lines 811-825 and 929-992](https://ampcode.com/manual)). Workspace-defined MCP servers require explicit approval, even though individual ordinary tool calls do not ([manual, lines 504-513](https://ampcode.com/manual)).

Amp also claims automatic secret detection/redaction at the lowest level, before a secret reaches the LLM, local cache, external service, or Amp cloud storage ([security reference, lines 162-172](https://ampcode.com/security)).

### Comparison

The owner's Claude configuration also currently uses `bypassPermissions` and skips its dangerous-mode prompt (`C:\Users\Prekzursil\.claude\settings.json:71,693`), but it adds structural PreToolUse guards and secret handling. `SecretGuardModule` begins at `C:\Users\Prekzursil\.agents\harness\modules.py:606`; the credential guard denies read-ish tools and shell reads of sensitive files (`C:\Users\Prekzursil\.claude\hooks\deny-credential-reads\deny.py:2-8,21-31,96-101`). The shared dispatcher redacts its own injected/logged text (`C:\Users\Prekzursil\.agents\harness\dispatcher.py:282,427,505`), but that is not the same as universal pre-transmission redaction of every prompt and tool result.

Claude Code natively supports permission modes, sandboxing, declarative deny rules, PreToolUse allow/deny/ask/updated input, and PostToolUse structured output replacement ([Claude permissions](https://code.claude.com/docs/en/permissions); [Claude hooks](https://code.claude.com/docs/en/hooks)). Thus Amp's generic policy-plugin behavior is **NATIVE (Claude Code already does this; we just enable it)**; no plugin runtime is needed.

The known defects strongly argue against copying Amp's “AI classify shell risk” example as a primary safety boundary. This harness already confirmed four use-vs-mention scanners that misclassified prose/JSON, including a successful result as failed (`INPUT-known-harness-defects.md:9-18,63-76`). An LLM classifier adds cost and nondeterminism without OS-level containment.

### **BUILD-LARGE — Exact universal secret redaction parity — UNVERIFIED**

**Classification:** BUILD-LARGE (new daemon/service/runtime — needs its own justification).

Exact Amp parity means redacting all ingress before model inference *and* before local transcript/cache/telemetry persistence. Current hooks can replace tool output before the next model call, but Claude's documentation says telemetry captures the original tool output before PostToolUse replacement ([Claude hooks](https://code.claude.com/docs/en/hooks)). User-prompt hooks can block but do not expose a documented universal rewrite path.

It is **likely (55-80%)** that exact parity cannot be achieved solely with the current hook bus, based on the documented hook ordering and telemetry behavior. This is **UNVERIFIED; EXPERIMENT SECRET-BOUNDARY-1** settles it: inject a synthetic canary matching a secret pattern through (a) user prompt, (b) built-in tool stdout, (c) MCP result, and (d) subagent result in an offline test profile, then inspect model-visible hook payloads, native JSONL transcript, debug logs, and telemetry export for the canary. No real secret may be used.

Do not build a proxy/guardrail framework to close this gap. That violates the anti-overfit ban on a new guardrail framework and creates a high-consequence parser in front of every model call. Retain and test the existing BUILD-SMALL credential-read denial and harness-log redaction; ask Anthropic for a native pre-persistence redaction boundary if the canary experiment demonstrates leakage.

### Where Amp is worse

- Default no-approval tool execution is a poor default for untrusted repositories and prompt-injectable MCP content.
- “Write your own policy plugin” transfers a security-critical responsibility to every user and makes policy quality uneven.
- Amp's own rationale correctly criticizes string-matching shell guards, but its answer is mostly permissiveness plus optional plugins, not sandbox-by-default containment.
- Cloud thread storage expands the consequence of a missed secret; the owner’s local-first memory is preferable.

## 6. Customization surface

Amp separates customization cleanly:

- `AGENTS.md` for durable instructions;
- skills for task-specific instructions/resources and optional MCP bundles;
- plugins for event behavior, tools, commands, UI, AI classification, custom modes, and custom subagents;
- MCP for external integrations ([manual, lines 557-570](https://ampcode.com/manual)).

Plugins are TypeScript files at project/system/global scopes, can be hot-reloaded, and expose a typed `PluginAPI` ([manual, lines 571-597](https://ampcode.com/manual)). A plugin can register a custom agent mode with its own model, instructions, tools, reasoning effort, and display metadata, or wrap an agent as a callable subagent tool linked by `parentThreadID` ([manual, lines 827-905](https://ampcode.com/manual)).

This is Amp's best architectural idea: one coherent SDK reduces glue and makes extension ownership visible. But this harness already has equivalent capabilities spread over native Claude surfaces:

- CLAUDE.md imports AGENTS.md and path-scoped rules;
- Agent Skills standard directories and lazy skill loading;
- native hooks for lifecycle policy and tool-result/input mutation;
- MCP/SDK tools for new callable capabilities;
- Markdown subagent definitions with tool/model restrictions;
- native commands/skills and `AskUserQuestion` UI;
- agent teams and worktrees.

### **BUILD-LARGE — Do not build an Amp-style universal plugin API**

**Classification:** BUILD-LARGE (new daemon/service/runtime — needs its own justification).

A compatibility SDK spanning TUI/web UI, event ordering, custom tools, commands, models, agents, and hot reload would become a second orchestration runtime. It is explicitly disallowed by the anti-overfit gate and would compete with rapidly evolving native Claude APIs.

It is **very likely (80-90%)** to increase maintenance cost more than task success because the corpus already shows only 78 of roughly 355 installed skills used and multiple hook detectors failing; another extension plane worsens discoverability and correctness. Port individual ideas to the existing bus instead.

### What to copy without a new runtime

- **CONFIG:** preserve the clear routing rule: instructions in AGENTS/CLAUDE, procedural knowledge in skills, deterministic interception in hooks, external services in MCP.
- **BUILD-SMALL:** when a missing UI choice is genuinely useful, expose it as a native `AskUserQuestion`/skill interaction rather than creating a UI SDK.
- **CONFIG:** keep project/user/managed scope and precedence explicit in every extension artifact.
- **BUILD-SMALL:** add a manifest command that lists loaded hooks, skills, agents, and MCP with owner/path/event—Amp's `plugins: list` is a good operator affordance. This harness has catalogs and manifests already, so the implementation should be an adapter/view, not a new registry.

The last item is **likely (55-80%)** to reduce configuration archaeology because Amp's single list shows events/commands/tools per plugin, while this harness currently spreads ownership across settings, manifests, catalogs, and provider config. **EXPERIMENT SURFACE-MAP-1**: time five “which artifact caused this behavior?” investigations with and without the unified read-only view.

## 7. Multi-agent support

Amp automatically spawns isolated subagents for decomposable work. Each has a fresh context and editing/terminal tools. The main agent receives only the final summary; subagents cannot communicate with each other, cannot be guided mid-task, and cannot be observed step-by-step ([manual, lines 388-395](https://ampcode.com/manual)).

The Oracle is a read-only second-opinion agent, deliberately optimized for review/debugging/planning rather than routine editing ([Oracle announcement, lines 4-17](https://ampcode.com/news/oracle)). Current Amp modes use a different frontier model for Oracle when possible ([Amp models, lines 13-19](https://ampcode.com/modes)). Custom plugin agents can be wrapped as tools and linked to the parent thread ([manual, lines 859-905](https://ampcode.com/manual)). Multiple top-level threads can run simultaneously and appear in a sidebar/web activity surface ([Agents, Everywhere, lines 7-21](https://ampcode.com/news/agents-everywhere)).

### Comparison

The owner's harness is better here:

- native Claude agent teams provide a shared task list, inter-agent messaging, and centralized management ([Claude agent teams](https://code.claude.com/docs/en/agent-teams));
- the local config enables teams (`C:\Users\Prekzursil\.claude\settings.json:7`);
- specialized agent definitions exist for code, Python, TypeScript, security, build errors, planning, and more (`C:\Users\Prekzursil\.claude\agents\code-reviewer.md:3`, `python-reviewer.md:3`, `typescript-reviewer.md:3`);
- cross-vendor Codex fan-out and a live local mailbox are documented (`C:\Users\Prekzursil\.claude\CLAUDE.md:19-67`);
- `SubagentLifecycleModule` rejects hollow handoffs (`C:\Users\Prekzursil\.agents\harness\modules.py:2331-2393`).

**NATIVE (Claude Code already does this; we just enable it):** isolated subagents, reusable agent definitions, background work, agent teams, shared tasks, messages, and worktree isolation. Agent teams are already enabled; no Amp port is justified.

Amp is worse because its subagents cannot communicate or be steered. Its isolation can be useful for independent review, but the owner's native team bus strictly subsumes that topology: choose subagents for isolation and teams for collaboration.

The one Amp detail worth retaining is “second opinion comes from a different model family.” The owner already has that capability through Codex MCP. It should remain an explicit uncertainty/cost gate, not an always-on Oracle call; Amp itself avoids pushing Oracle aggressively because of latency/cost ([Oracle announcement, lines 9-12](https://ampcode.com/news/oracle)).

## 8. Verification and self-checking

Amp provides three visible mechanisms:

1. The user can run `amp review` or ask the main agent to review changes.
2. `.agents/checks/*.md` files define named review criteria, optional default severity, and tool allowlists. During review, Amp spawns a separate subagent per check; closer directory checks override global/parent checks ([manual, lines 433-469](https://ampcode.com/manual)).
3. A plugin can intercept `agent.end` and continue with a guarded follow-up such as “run the most relevant tests” ([manual, lines 664-684](https://ampcode.com/manual)).

Amp's ordinary prompting guide still tells the user to specify how work should be reviewed and what command/test/URL/log should be used ([manual, lines 139-153](https://ampcode.com/manual)). The public docs therefore show strong opt-in review primitives, not a documented universal “no success claim without fresh evidence” invariant.

The owner already attempts a stronger invariant:

- review agents say they must be used for relevant changes (`C:\Users\Prekzursil\.claude\agents\code-reviewer.md:3`, `python-reviewer.md:3`, `typescript-reviewer.md:3`);
- verification-before-completion and verification-loop skills exist;
- `ClaimWarningModule` examines Stop/TaskCompleted (`C:\Users\Prekzursil\.agents\harness\modules.py:2000-2055`);
- anti-degeneration detects identical repeated no-progress calls (`C:\Users\Prekzursil\.agents\harness\modules.py:1783-1863`).

But the operating defects show why a small, explicit review-check format may outperform more clever global scanners: existing use-vs-mention heuristics generated false blocks and even told an agent to discard a successful result (`INPUT-known-harness-defects.md:9-18,63-76`). Amp checks run as bounded reviewers over code/diff scope rather than regexing every prose/tool payload.

### **BUILD-SMALL — Declarative review checks over native subagents**

**Classification:** BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).

Port the *format and routing*, not Amp's whole review product:

1. Recognize `.agents/checks/*.md`, ancestor directories, and a user-global check directory.
2. Frontmatter: `name`, `description`, `severity-default`, `tools`, and optional `globs`.
3. A `/review-checks` skill computes changed-file scope, resolves precedence, and spawns one read-only native subagent per applicable check. Cap concurrency and check count.
4. Every check receives the original goal, diff/file list, its own instruction, and a strict output shape: finding ID, severity, path:line, evidence, consequence, suggested fix, confidence.
5. A merge pass deduplicates findings by normalized path/line/rule and reports disagreements; it does not auto-fix.
6. Checks are invoked explicitly or by a simple existing Stop/TaskCompleted route only after actual code changes. Never scan Markdown discussion for code markers.
7. Start with 3-5 high-value checks extracted from already-used reviewer agents; do not create hundreds of policies.

The local absence claim is narrow and validated: a source probe found known-present review mechanisms, then the independent target probe found zero `.agents/checks`, `severity-default`, or “one subagent per check” conventions in the shared harness/hook/rule roots. This does not exclude an unrelated plugin cache artifact.

This is **very likely (80-90%)** to improve review composability because the owner already uses specialized reviewers, Claude already supplies parallel agents, and the new layer is only file discovery + routing. It is **likely (55-80%)** to improve defect detection, not almost certain, because LLM check quality and duplicate noise require measurement. **EXPERIMENT REVIEW-CHECKS-1**: seed 20 known defects across Python/TypeScript/security fixtures, compare current reviewer route versus checks fan-out on recall, precision, tokens, wall time, and duplicate findings.

### **CONFIG — Use native Stop continuation for evidence, not prose markers**

**Classification:** CONFIG (settings/JSON only).

Claude Stop hooks can already prevent stopping and continue the conversation ([Claude hooks](https://code.claude.com/docs/en/hooks)). Keep one guarded continuation keyed on typed evidence state—changed files plus absence of a fresh verification receipt—not keywords such as “verify,” “stub,” or “done.” Amp's example uses a marker to avoid infinite recursion; this harness already learned the same re-entrancy lesson in `ClaimWarningModule` (`C:\Users\Prekzursil\.agents\harness\modules.py:2055-2062`).

This is **very likely (80-90%)** to be safer than content scanning because the known false positives all arose from treating mentions as occurrences. The exact receipt schema belongs to the neighboring design unit; this teardown does not design it.

## 9. Remote environments, portals, and execution infrastructure

Amp Orbs are fresh Debian 12 machines with repo clone, up to 16 CPUs/32 GB RAM, preinstalled tooling, per-project environment/secrets, short-lived OIDC identity, setup/resume hooks, a shared tmux terminal, local sync, and authenticated dev-server portals ([Orbs manual, lines 43-62, 76-114, 120-147, 177-209](https://ampcode.com/manual/orbs)). This is materially more integrated than a generic remote shell.

Claude web tasks already cover clean cloud execution and parallel tasks, while Remote Control covers local environment access and multi-device steering ([Claude web](https://code.claude.com/docs/en/claude-code-on-the-web); [Claude Remote Control](https://code.claude.com/docs/en/remote-control)). The missing Amp-specific pieces are one-click portal exposure, shared agent/human tmux inside the cloud environment, `amp sync`, and Amp-issued OIDC identity.

### **BUILD-LARGE — Do not port Orb parity**

**Classification:** BUILD-LARGE (new daemon/service/runtime — needs its own justification).

Orb parity would require VM lifecycle, image supply chain, repository credentials, secret broker, workload identity, network proxying, authenticated portals, billing/quotas, pause/resume, diff synchronization, and a web terminal. It is a cloud platform, not a harness hook.

It is **very unlikely (5-20%)** to beat native Claude web tasks plus the owner's existing infrastructure for this single user, because there is no measured portal/OIDC bottleneck and the build would reintroduce durable execution and a second control plane. If a future workload repeatedly needs ephemeral preview environments, integrate an existing cloud provider through a skill/MCP rather than building Orbs.

## 10. What Amp is worse at — explicit do-not-copy list

1. **Tool permission default.** Amp runs tools without approval and pushes policy construction onto the user. Keep deterministic blocks for truly irreversible operations and native sandbox/permission modes.
2. **Rollback.** Amp removed automatic file rollback and relies on the model to undo. Keep Claude checkpoints and git/worktrees.
3. **Subagent collaboration.** Amp subagents cannot communicate, be steered, or expose intermediate progress. Native Claude teams are stronger.
4. **Memory ownership/privacy.** Amp stores threads in its multi-tenant cloud and has no self-hosted deployment; workspace admins can see private threads. Keep local canonical memory.
5. **Backwards compatibility and churn.** Amp publicly embraces removing features and no backwards compatibility. That can keep a product lean, but it is hazardous for an owner harness whose rules/skills must survive provider churn. Copy the willingness to delete unused mechanisms, not the compatibility posture.
6. **Verification is opt-in/productized, not a proven invariant.** `amp review` and checks are good, but the docs still tell the user to specify verification. Keep evidence receipts and completion gates.
7. **Skill-bundled MCP startup.** Hiding definitions reduces context but starting servers at launch can still consume processes and fail. Native Tool Search plus curated server enablement is a better fit for this Windows fleet.
8. **Cloud control-plane scope.** Threads, projects, Orbs, runners, portals, visibility ACLs, activity feeds, and billing form a large product surface. The owner does not need to own that surface.
9. **Plugin AI classifiers for policy.** They are useful advisory helpers, but should not decide high-consequence boundaries. The local detector history already demonstrates classification fragility.

## 12. Mechanism-level port sketches

### A. Thread recall data flow

```text
user asks about prior work
  -> thread-recall skill
  -> bounded metadata/text scan of native JSONL transcripts
  -> ranked session IDs + evidence snippets
  -> user/agent selects up to N sessions
  -> fresh read-only subagent extracts goal-relevant facts
  -> structured handoff with transcript path/message IDs
  -> optional explicit basic-memory capture
```

No automatic ingestion into basic-memory. No vector DB. No raw transcript dumped into the main context.

### B. Review checks data flow

```text
changed files + original goal
  -> resolve applicable check Markdown by directory/glob/precedence
  -> bounded parallel native subagents (one/check)
  -> typed evidence findings
  -> deterministic dedupe/sort
  -> report; main agent chooses fixes
  -> fresh tests/verification receipts
```

No trained critic. No separate orchestration runtime. No automatic write access for check agents.

### C. MCP curation data flow

```text
task intent
  -> native Tool Search over connected curated servers
  -> server health/approval state
  -> selected tool only enters context
  -> bounded retry/backoff
  -> terminal FAILED state disables route until explicit recovery
```

This directly serves the corpus's dead-server/retry failures without copying Amp's plugin runtime.

## Bottom line

Amp's lesson is not “replace the harness with Amp.” It is “make a few high-value behaviors first-class and delete redundant scaffolding.” The owner's stack already has more powerful memory, verification intent, multi-agent communication, and native safety primitives. Amp is ahead in raw-thread retrieval ergonomics and declarative review-check fan-out; both can be ported in small, reversible layers. Its distributed runtime, cloud feed, universal plugin API, and Orb platform are product infrastructure—not missing harness features—and would recreate precisely the complexity this program's anti-overfit gate rejects.
