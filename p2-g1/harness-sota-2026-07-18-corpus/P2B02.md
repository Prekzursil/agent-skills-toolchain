# P2B02 — Competitive teardown: GitHub Copilot / Copilot Workspace

**Unit:** P2B02  
**Research date:** 2026-07-18  
**Subject:** current GitHub Copilot cloud agent, Copilot CLI, editor agent mode, Copilot app, and the retired Copilot Workspace technical preview  
**Decision frame:** identify mechanisms worth porting into this owner's Claude/Codex harness, not features worth admiring in the abstract.

## Executive verdict

GitHub Copilot is no longer one agent. It is a product family sharing GitHub's repository, identity, Actions, pull-request, code-scanning, and billing control planes. The useful competitive lesson is therefore not a novel ReAct loop. Its basic loop—understand, plan, inspect, edit, execute, observe, repair, review—is conventional and already native to Claude Code and Codex. Copilot's advantage is that GitHub has turned several optional good practices into delivery invariants: repository-scoped credentials, an ephemeral firewalled worker for cloud tasks, automatic self-review, automatic security checks, a branch/PR as the durable unit of work, session-to-commit traceability, and repository memories whose citations are revalidated against the current branch.

The central conclusion is **very likely (80-90%)**: the best import is a thin set of gates and metadata conventions on the buses already present here, not replacement by a Copilot-like cloud runtime. Evidence: this harness already has native Claude/Codex agents, hooks, MCP, skills, worktrees, a basic-memory vault, and a structured event ledger (`C:\Users\Prekzursil\.claude\CLAUDE.md:5-22`; `C:\Users\Prekzursil\.agents\harness\README.md:20-29`), while the anti-overfit brief rejects a second orchestration runtime and durable-execution engine. The high-value Copilot mechanisms can mostly be expressed as CONFIG or BUILD-SMALL changes below. A full Copilot-style cloud control plane would be BUILD-LARGE, would reintroduce a rejected second runtime, and is not justified by the evidence.

Copilot is materially worse than this harness in other dimensions. It has a product-fragmented customization matrix, cloud hooks are non-interactive and ephemeral, repository MCP servers are autonomously callable without per-call approval, cloud custom agents omit some IDE handoff features, code review excludes important file classes, cloud sessions cannot be deleted, and Copilot Memory expires unused entries after 28 days. This harness has broader cross-vendor composition, owner-controlled durable memory, richer evidence and honesty rules, and much deeper domain specialization. The corpus records 78 skills actually invoked, 22 agent types, and 93 MCP servers touched; those numbers show under-utilization, but they also show a capability breadth Copilot's standard product does not document (`corpus/corpus.json:13266-13377`).

## Scope correction: Copilot Workspace is historical, not the current product

The phrase “Copilot Workspace” must not be used as shorthand for current Copilot agents. GitHub's own GitHub Next page says its technical preview was sunset on **2025-05-30**. The retired product remains relevant because its interaction design was unusually explicit: issue/repository → editable specification → editable plan → coordinated multi-file implementation → terminal/Codespace execution → repair agent on test failure → share/version/PR. GitHub described the specification and plan as user-editable steering points, and the GitHub Next page described automatic context/history versioning and a repair agent driven by the observed error ([GitHub Next: Copilot Workspace](https://githubnext.com/projects/copilot-workspace/); [2024 launch article](https://github.blog/news-insights/product-news/github-copilot-workspace/)).

Current equivalents are distributed across:

- **Copilot cloud agent:** asynchronous GitHub-hosted work in an ephemeral Actions environment, branch/commit/PR delivery, live logs, steering, self-review, and security scanning.
- **Copilot CLI:** local interactive/programmatic agent, plan mode, permission prompts, hooks, skills, MCP, plugins, subagents, `/fleet`, context compaction, checkpoints, and session history.
- **Editor agent mode:** synchronous IDE loop with code search, edits, terminal/tool calls, diagnostics, approvals, and editor context.
- **Copilot app:** a desktop session manager over local repositories, worktrees, and cloud sandboxes, with parallel sessions and the CLI/SDK safety model.

This report treats the old Workspace design as a source of mechanisms, not as an available competitor. Any proposal to “adopt Workspace” would be based on a false product premise.

## 1. Agent loop

### What Copilot does

Copilot exposes three related loops.

**Cloud loop.** The cloud agent accepts a prompt, issue, PR comment, or automation trigger; evaluates the task; researches the repository; can create a plan; edits a branch in an ephemeral Actions environment; runs tests and linters; commits changes; receives steering after the current tool call; self-reviews; performs security checks; then presents or opens a PR. GitHub documents repository research, planning, branch changes, automated tests/linters, and scheduled/event triggers ([cloud agent overview](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)). Session logs expose the tools used and validation performed, and commits link back to those logs ([session management](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)).

**CLI/editor loop.** Copilot CLI has an execute mode and a plan mode. Plan mode analyzes the request, asks clarifying questions, and builds a structured plan before code is written. Execute mode iterates through tool calls whose outputs become context for the next model step. The CLI can run interactively or as a one-shot programmatic process ([CLI overview](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli); [VS Code tools model](https://code.visualstudio.com/docs/copilot/concepts/tools)).

**Historical Workspace loop.** Workspace made intermediate intent artifacts first-class and editable: task → specification → plan → implementation. The user could revise or regenerate the spec/plan rather than steering only after code appeared. Its repair agent consumed concrete test errors and proposed repairs ([GitHub Next Workspace page](https://githubnext.com/projects/copilot-workspace/)).

### Comparison

The underlying loop is not a gap. Claude Code/Codex already plan, inspect, edit, execute, observe, and iterate. This harness adds goal reinjection, long-operation monitoring, event ledger, subagents, and evidence rules. Copilot's advantage is the **product boundary** around the loop: every cloud task is isolated, logged, branched, and reviewable.

Workspace's explicit editable specification is a useful interaction pattern, but making it mandatory would overfit routine work. The **likely (55-80%)** best use is an optional high-risk/ambiguous-task mode, because it catches misunderstandings before edits while preserving the minimal loop for ordinary tasks. Evidence: GitHub retained plan mode in the current CLI but sunset the dedicated Workspace wrapper, suggesting the planning primitive survived while the heavyweight environment did not.

### Capability delta: optional intent → specification → plan gate

**OUR-SIDE TAG: NATIVE (Claude Code already does this; we just enable it)**

Port mechanism: for high-EVPI tasks, enter native plan mode and require three editable fields before execution: objective/acceptance criteria, affected surfaces, and verification commands. Store the accepted plan in the native plan state, not a new database. Do not invoke the gate for prompts prefixed `*` or for obvious one-step work. This is **very likely (80-90%)** to improve ambiguous multi-file work without taxing small tasks, because it reuses native plan state and obeys the existing front-loaded clarification rule.

This proposal rides the native agent loop and does not add a rejected component.

## 2. Context management

### What Copilot does

Copilot combines explicit and automatic context:

- repository instructions, path-specific instruction files, agent instructions, skills, MCP results, attached files/folders/symbols, terminal output, source-control changes, and chat context;
- cross-surface chat→cloud handoff, with cloud status and follow-ups visible in the originating chat;
- a 20 KiB large-tool-output spill rule in CLI: store the full result in a temporary file and give the model a path plus preview;
- a `/context` view that breaks token usage into system prompt, custom instructions, system tools, MCP tools, messages, free space, and response buffer;
- automatic background compaction at about 80% capacity, a pause near 95% if compaction has not completed, a structured summary preserving goal, completed work, technical details, files and next steps, plus a checkpoint for every compaction.

These behaviors are documented in [Copilot CLI context management](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-cli/context-management) and [VS Code context management](https://code.visualstudio.com/docs/chat/copilot-chat-context).

### Comparison

This harness already has pre/post-compaction hooks, sanitized checkpoints, context meters, output compression, skills, MCP, and explicit recall. It is not missing compaction or checkpoints. In fact, its separate durable checkpoint and event-ledger layers can preserve objective facts better than a single model summary. Copilot is better at making context composition inspectable: `/context` reports where tokens went, including tool schemas and MCP tools. The current Codex status line shows aggregate context use (`C:\Users\Prekzursil\.codex\config.toml:49`), but the active harness evidence inspected for this unit does not show the same category breakdown.

### Capability delta — UNVERIFIED: context-budget attribution by source

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

UNVERIFIED whether Claude Code's current hook payload exposes exact per-category token counts; the settling experiment is to capture a known session's PreCompact and status payloads, compare the reported total with a known-present custom-instruction and MCP-schema contribution, and verify the components sum within documented rounding. If exposed, add a `/context-audit` skill that reports bytes/tokens for rules, skills, tool schemas, MCP schemas, messages, and tool outputs. If not exposed, report only byte estimates and label them estimates.

The recommendation is **likely (55-80%)** to help because this harness has hundreds of installed skills and many MCP servers, while only 78 skills were observed invoked; visibility can distinguish a routing problem from an instruction/schema tax. The evidence is indirect, hence the UNVERIFIED heading. It rides existing inspection APIs and does not create a new observability service.

### What not to copy

Do not replace the event ledger and basic-memory checkpoints with model-only compaction summaries. GitHub explicitly warns that compaction loses fine-grained details and cannot be reversed ([context management](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-cli/context-management)). The current harness deliberately separates objective event history from semantic memory; that is stronger.

### Capability delta — UNVERIFIED: natural-language query over complete prior sessions

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Copilot can query a user's synced past sessions over prompts, responses, file changes, and related context; examples in GitHub's documentation include finding the session where authentication was refactored and sessions where the agent struggled or needed repeated correction ([session management](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)). This harness has raw transcripts, a distilled corpus, a session picker, an event ledger, and selected semantic notes, but the bounded active-contract scan did not establish an equivalent one-command semantic query across complete prior sessions.

UNVERIFIED whether an installed session skill or provider-native session picker already exposes equivalent query coverage; the settling experiment is to ask the same five queries—by date, goal, changed file, error fingerprint, and owner correction—through every existing session/history command, and score recall against five known session IDs found by exact transcript search.

If the experiment confirms the gap, add a read-only `session-query` skill that searches a small metadata/term index and resolves results back to immutable raw transcript paths and ledger receipts. Use exact/FTS retrieval first and the existing model for query expansion; do not create another vector database or ingest transcript bodies into basic-memory. This is **likely (55-80%)** to reduce repeated investigations because the 10.62 GB history already contains the evidence, while the 1.3 MB corpus intentionally loses conversational detail. The confidence is bounded because the experiment may show native coverage is sufficient.

## 3. Memory

### What Copilot does

Copilot Memory, currently public preview, has two stores:

- repository facts: conventions, architectural decisions, build commands, and project rules shared with eligible users of that repository;
- user preferences: stated or inferred interaction preferences, scoped to that user across repositories.

The important mechanism is not merely persistence. Repository facts are stored with citations to supporting code. At retrieval time Copilot checks those citations against the **current branch** and uses only validated facts. Repository owners can inspect and delete facts. Memories can transfer between cloud agent, code review, and CLI. Unused facts/preferences are deleted after 28 days, with the timer potentially reset after successful validation and use ([Copilot Memory](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-memory); [administrator controls](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory/manage-as-administrator)).

### Comparison

This harness's basic-memory is broader and more durable. It is shared across Claude/Codex, semantically searchable, owner-controlled, and explicitly models supersession. The corpus records 1,332 basic-memory server uses and hundreds of write/search/read calls, so this is a live capability, not an installed-only claim (`corpus/corpus.json:13370` onward).

Copilot's advantage is freshness enforcement at the evidence boundary. Here, validity is maintained by authors adding `superseded_by` and `valid_as_of`, while recall scoring recognizes those fields (`C:\Users\Prekzursil\.claude\CLAUDE.md:11`; `C:\Users\Prekzursil\.agents\harness\recall_index.py:41,223-235`). A bounded scan of the active memory contract, recall index, and harness modules found the known-present supersession/checkpoint mechanisms but no code-to-current-branch citation validator. This is two mechanically distinct signals: the documented memory schema and the retrieval implementation. Therefore the gap is narrow: **automatic source revalidation**, not memory itself.

### Capability delta: source-cited, current-branch-validated repository facts

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Port mechanism:

1. Extend repository-fact notes with `repo`, `commit_or_branch`, `source_path`, `start_line`, `end_line`, and `source_hash` (or an array of citations).
2. At recall, resolve the current repository root and read only the cited ranges.
3. If the content hash still matches, mark the fact `validated` and allow normal ranking.
4. If the file moved, optionally use `git log --follow`/bounded symbol search once; otherwise mark stale and suppress injection.
5. Never delete the note automatically. Preserve it as history and point to a superseding fact when known. This improves on Copilot's 28-day deletion policy.
6. Facts without citations remain usable only when explicitly typed as owner preferences or decisions, not codebase facts.

This is **very likely (80-90%)** to reduce stale-memory errors because the current-branch content check is deterministic and Copilot deploys the same invariant. It uses the existing basic-memory and recall bus, adds no vector database/KG, and stays below BUILD-LARGE if implemented as a retrieval filter plus schema fields.

### What not to copy

Do not copy automatic 28-day deletion. A rarely used architectural constraint may remain correct and important. The better rule is “validate or suppress, retain for audit,” matching this harness's event-ledger philosophy. Do not copy inferred personal preferences without provenance; Copilot says it uses “best judgment” to confirm preferences, which is weaker than exact source validation.

## 4. Tools and MCP handling

### What Copilot does

Copilot agents have built-in file read/edit/search, shell, GitHub, and Playwright-style tools, plus MCP tools. Custom agents can name an exact tool allowlist and embed agent-specific MCP server configuration. The built-in GitHub MCP token is read-only and scoped to the source repository; built-in Playwright is limited to localhost. Repository MCP configuration is shared by cloud agent and code review. Agent secrets prefixed `COPILOT_MCP_` are made available only to MCP servers, not general agent scripts ([custom-agent reference](https://docs.github.com/en/copilot/reference/custom-agents-configuration); [repository MCP configuration](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers); [agent secrets](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables)).

The CLI can allow/deny individual tools and URLs, disable built-in or named MCP servers, and show loaded instructions/MCP/skills/agents/hooks/plugins through `/env` ([CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)). It also narrows tool sets to reduce decision space and context consumption.

There are important limitations: GitHub.com's cloud agent and code review support MCP **tools only**, not MCP resources or prompts, and do not support remote MCP OAuth. Once a repository MCP server is configured, Copilot may call it autonomously without asking for approval ([repository MCP configuration](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers)).

### Comparison

This harness has much greater MCP breadth but worse operational hygiene. The measured leader is a dead Tavily MCP still receiving calls; the corpus records dozens of servers and tools, while current settings broadly allow MCP families. Copilot's smaller default tool set, source-repository token, localhost browser restriction, and MCP-only secret namespace are safer defaults. Conversely, this harness can use MCP resources/prompts where clients support them, can route across many specialist providers, and is not tied to GitHub's supported authentication matrix.

### Capability delta: repository-scoped and component-scoped MCP credentials

**OUR-SIDE TAG: CONFIG (settings/JSON only)**

Port mechanism: replace broad personal tokens used by GitHub MCPs with fine-grained read-only tokens scoped to named repositories; create separate environment-variable namespaces for MCP child processes; do not inherit unrelated agent environment secrets; set an explicit per-server tool allowlist; default disabled when liveness preflight fails. For write operations, use a separate short-lived credential and a separate server/profile so a read-oriented agent cannot silently escalate.

This is **almost certain (90-99%)** to reduce blast radius because token scope and process environment boundaries are enforced independently of model behavior. Evidence: Copilot documents repository-scoped read-only built-ins and MCP-only secrets, while this harness currently permits broad MCP families and additional drive roots (`C:\Users\Prekzursil\.claude\settings.json:26-75`). It is configuration on existing MCP buses, not a guardrail framework.

### Capability delta: automatic liveness-based tool suppression

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

The harness already has liveness/preflight machinery, yet the measured dead Tavily calls prove it is not enforcing a reliable availability set end-to-end. Port the Copilot `/env` idea as a generated per-session capability manifest: configured, authenticated, live, permitted, and selected. A server that fails a cheap preflight becomes unavailable to the model for the session; it may be re-enabled only after an explicit successful probe. Emit `SUCCESS:capability-manifest` or `FAILED:capability-manifest <server>` terminal states.

This is **very likely (80-90%)** to eliminate the observed dead-server retry class because removing a dead tool schema prevents selection, rather than asking the model to remember a warning. Evidence is the pinned 135 “not connected” Tavily failures plus active preflight/liveness components. This reuses the hook/MCP configuration bus and does not add a router daemon.

### What not to copy

Do not copy autonomous no-prompt MCP invocation for all configured servers. That is acceptable only inside Copilot's isolated cloud worker and still creates external side-effect risk. Do not shrink this harness to GitHub/Playwright; its specialist tool breadth is a real advantage. Fix selection and liveness instead.

## 5. Permission and isolation model

### What Copilot does

Copilot has two sharply different models.

**Local CLI/editor:** starts with folder trust, asks before side-effecting tool use, supports per-use/session/future approvals, tool and URL allow/deny flags, and offers preview local/cloud sandboxes. GitHub explicitly warns that allowing a command family or all tools can permit more destructive variants than the originally proposed command ([CLI overview](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli)).

**Cloud agent:** runs in an ephemeral Actions environment with a firewall enabled by default. The default outbound set is restricted; additional hosts require firewall configuration. The agent works on its branch, while branch protection and human PR review remain downstream controls. Cloud jobs pre-grant tool permissions and show no approval dialogs. Cloud hook filesystem output is discarded unless sent externally, and hook HTTP egress needs firewall allowance ([agents application card](https://docs.github.com/en/copilot/responsible-use/agents); [hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference)).

### Comparison

The current harness posture is worse by default: `bypassPermissions`, empty `ask`, broad command/file/web tools, and access to both full drive roots (`C:\Users\Prekzursil\.claude\settings.json:26-75`). Deny rules protect a few credential patterns, and hooks add more checks, but the known defects show semantic guards can false-positive and can misclassify successful tools (`INPUT-known-harness-defects.md:9-109`). Copilot's OS/container and credential boundaries do not depend on interpreting prose.

Copilot's cloud no-prompt model is not inherently safer for external MCP side effects; it is safer for the filesystem/network only because the surrounding sandbox and scoped credentials are stronger. The security property comes from containment, not agent obedience.

### Capability delta: least-privilege default profile

**OUR-SIDE TAG: CONFIG (settings/JSON only)**

Port mechanism: change the default from bypass to normal permission prompts; remove drive-root additional directories; give each agent profile an explicit tool set; split read-only investigation, repository editing, external-write, and destructive-maintenance profiles; keep irreversible actions denied. Preserve one explicitly named owner-invoked bypass profile for controlled cases.

This is **almost certain (90-99%)** to reduce accidental blast radius because it removes ambient authority mechanically. The current configuration is direct evidence. It also reduces reliance on the prose-matching guards known to be defective.

### Capability delta: ephemeral, firewalled cloud worker

**OUR-SIDE TAG: BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

A faithful port would require a job scheduler, isolated image lifecycle, secrets broker, egress firewall, branch/worktree provisioning, log retention, cancellation, and cleanup. This reintroduces a second orchestration runtime and durable-execution engine—two components the anti-overfit gate explicitly rejects.

Recommendation: **do not build it**. It is **very likely (80-90%)** that the maintenance and failure surface would outweigh its value for this single-owner harness, because native Claude/Codex sandboxes, local worktrees, GitHub Actions, and hosted coding agents already provide execution isolation when needed. If remote isolation becomes a measured requirement, configure an existing native provider or one-shot GitHub Actions job; do not create a resident owner-built service.

## 7. Multi-agent and concurrency

### What Copilot does

Copilot supports multiple distinct forms:

- concurrent cloud sessions managed from one Agents panel;
- CLI subagents with separate context windows, used for exploration, complex commands, review, and specialist custom agents;
- `/fleet`, whose orchestrator decomposes an implementation plan, reasons about dependencies, and runs independent subtasks in parallel;
- sibling/child discovery and scoped messaging, with depth and concurrency limits;
- multiple model providers/third-party coding agents available in GitHub's agent control plane;
- separate worktrees/cloud sandboxes in the desktop app.

Sources: [CLI feature comparison](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/comparing-cli-features), [`/fleet`](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/fleet), [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), [agent management](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/agent-management), and [agents application card](https://docs.github.com/en/copilot/responsible-use/agents).

### Comparison

The harness is already stronger at cross-vendor composition: Claude subagents can call Codex, and agent-mail provides real-time cross-provider messaging/file leases. Copilot's `/fleet` is more productized: the user invokes one command, the orchestrator decides the decomposition and parallelism, and the UI shows sessions. Here, the owner or a skill often has to explicitly orchestrate.

Copilot is worse in one current boundary: steering is documented as unavailable for third-party coding agents in the GitHub session manager, whereas this harness's agent-mail is explicitly intended for cross-provider messages. GitHub's multi-agent advantage is therefore control-plane polish, not a more open communication topology.

### Capability delta: dependency-aware one-command fleet planning

**OUR-SIDE TAG: NATIVE (Claude Code already does this; we just enable it)**

Port mechanism: expose a `/fleet`-equivalent skill that asks the native model to produce a dependency DAG, launches only independent leaves with native subagents, limits depth/concurrency, and requires structured summaries before synthesis. Reuse native team mailboxes when available; retain agent-mail only as the current fallback. Do not create a new orchestrator process.

This is **likely (55-80%)** to improve large independent workloads because parallel fan-out is already proven usable here, while the corpus shows specialized agents are used. It will not help serial or tightly coupled tasks; the command must be opt-in, and the model must be allowed to choose “do not fan out.” It rides native subagents and does not reintroduce a second runtime.

## 8. Verification and self-checks

### What Copilot does

Copilot's verification stack is unusually well integrated:

1. the agent runs repository tests and linters in its environment;
2. before opening the PR, the coding agent invokes Copilot code review on its own changes, receives feedback, and iterates;
3. code scanning, secret scanning, and dependency vulnerability checks run inside the workflow;
4. the result is delivered as a diff/PR for human review, with CI, review activity, signed commits, and linked session logs;
5. automatic code review can run on PR open and optionally on new pushes.

GitHub documents the self-review/iteration and security scans in its [2026 coding-agent update](https://github.blog/ai-and-ml/github-copilot/whats-new-with-github-copilot-coding-agent/), and details CodeQL, secret scanning, and advisory checks for agent-generated code in [third-party agent security validation](https://docs.github.com/en/copilot/concepts/agents/about-third-party-coding-agents). It also warns that Copilot review is not guaranteed to find all problems and still requires human validation ([code review](https://docs.github.com/en/copilot/concepts/agents/code-review)).

### Comparison

This harness has reviewers, security-reviewer agents, verification rules, test hooks, GitHub tooling, and has used CodeQL. A corpus search found CodeQL-related session material, so **CodeQL is not absent**. The gap is automatic coupling: a bounded scan of the active settings/harness finds security guards and validation hooks but no universal CodeQL/dependency/self-review pipeline, while the corpus samples show CodeQL invoked as task/workflow work rather than evidence that every agent delivery traversed the same gate. The hooks detector is broken, so this report does not use hook telemetry to claim non-execution.

Copilot's pipeline is stronger because it makes heterogeneous checks a delivery prerequisite. The harness's generator-critic rule is prompt-level and its known false-positive guards can corrupt tool verdicts (`INPUT-known-harness-defects.md:9-109`). Independent scanners tied to the produced diff are less vulnerable to use/mention confusion than scanning prose payloads.

### Capability delta: automatic fresh-context diff review before delivery

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Port mechanism: on a development task with a non-empty diff, invoke one fresh-context reviewer with only the original acceptance criteria, diff, relevant tests, and changed-file context. The reviewer returns structured findings with file/line/evidence/severity; the main agent may fix them once, then rerun affected tests. Skip prose-only research artifacts and trivial user-approved edits. Record the review receipt in the event ledger.

This is **very likely (80-90%)** to catch a useful class of generator blind spots because the critic is context-independent and diff-scoped, and GitHub reports this exact pre-PR iteration as a product behavior. It remains a model review, not proof; test/scanner results outrank it. It uses native subagents and the ledger rather than a trained critic or new service.

### Capability delta: automatic security checks on agent-produced code

**OUR-SIDE TAG: CONFIG (settings/JSON only)**

Port mechanism: configure repository-native CI/branch protection so agent branches run secret scanning, dependency review/advisory checks, and language-appropriate static analysis before merge. The harness should read terminal conclusions from those existing checks and never parse prose for secret-looking words. For local handoff, add a small skill that launches the repository's existing security workflow; do not embed another scanner framework in hooks.

This is **very likely (80-90%)** to improve consistency because it converts ad hoc scanner availability into a repository invariant. Evidence: Copilot's integrated gate, plus corpus evidence that CodeQL exists here but is not shown as universally coupled. The tag is CONFIG because GitHub Actions/branch protection and existing scanners are the bus; creating a new guardrail framework is explicitly rejected.

### Capability delta: commit-to-session provenance receipt

**OUR-SIDE TAG: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Port mechanism: every agent-created commit or handoff report includes a non-secret receipt ID pointing to the event-ledger session, original goal hash, test commands/results, reviewer receipt, and security-check URLs/status. Do not put private transcript text in commit metadata. A verifier resolves the receipt and confirms the commit hash matches.

This is **likely (55-80%)** to improve auditability because GitHub's signed commits link directly to session logs, while this harness already has an event ledger and terminal-state output convention. The lower band reflects the risk that excessive provenance becomes noise for one-owner local work; make it automatic only for commits/PRs, not every edit.

## 10. Where Copilot is worse—and what not to copy

1. **Surface fragmentation.** Capabilities differ across GitHub.com, CLI, VS Code, JetBrains, Eclipse, Xcode, code review, and app. Custom-agent fields and instruction types are not uniformly supported. Our cross-tool contract is conceptually cleaner.

2. **Cloud MCP approval is too coarse.** A configured repository MCP can be used autonomously without per-call approval. This is worse than scoped, effect-aware approval for external writes.

3. **Cloud hook durability is weak.** Files are discarded at job end; durable output requires an HTTP hook and firewall allowance. This harness's local ledger is durable by default.

4. **Cloud hooks are Linux-biased.** PowerShell hook entries are ignored in cloud jobs. That is a significant mismatch for this Windows owner.

5. **Memory expires silently by policy.** Unused facts and preferences disappear after 28 days. The owner needs long-horizon research and failure memory; validate/suppress is safer than delete.

6. **Code review has blind file classes.** Dependency manifests/lockfiles, logs, and SVGs are among excluded classes in GitHub's documented review behavior. Those may contain security or correctness changes ([code review](https://docs.github.com/en/copilot/concepts/agents/code-review)).

7. **Agent review is not proof.** GitHub itself says Copilot reviews can miss problems. Copy the independent-check placement, not confidence in the reviewer.

8. **Cloud session deletion is restricted.** Cloud sessions can be archived but not deleted; this is worse for owner-controlled retention ([session management](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)).

9. **Workspace's dedicated environment failed the product-survival test.** Its best primitives survived elsewhere, but the preview wrapper was sunset. Building a local clone would ignore that evidence.

10. **Billing/control-plane coupling.** Agent work and code review consume AI credits and Actions minutes. The product can block work when budgets are reached. This harness can route among providers and local tools, which is strategically stronger even if operationally messier.

11. **Less owner-specific honesty instrumentation.** Copilot documentation emphasizes human review, but it does not expose an equivalent of this unit's confidence bands, inline UNVERIFIED experiments, known-positive absence controls, or anti-sycophancy contract. Those are worth retaining.

12. **Less specialist breadth.** Copilot can add MCP/skills, but its documented default developer focus does not match this owner's reverse engineering, life science, game, binary, and research skill inventory. Porting Copilot wholesale would risk a capability regression.

- Copilot Memory is public preview. Its documented citation validation is clear, but long-term precision/recall and false-memory rates are UNVERIFIED; the settling experiment is a benchmark of seeded true, stale, moved, conflicting, and uncited facts across branches.
- A live Copilot account was not used. UI behavior was derived from current official documentation and changelogs, not hands-on telemetry.

- The active local scan was bounded to the comparison-relevant contract, settings, harness code/README, and corpus. It did not treat 140 earlier audit-unit claims as facts.

1. **Memory citation validation:** the known-present detector found `superseded_by`/checkpoint semantics in the memory contract and recall implementation.
