# P2B01 — Competitive teardown: Cursor

**Unit:** P2B01  
**Date researched:** 2026-07-18  
**Scope:** Cursor's agent loop, context management, memory, tools/MCP, permissions, customization, multi-agent operation, and verification/self-checking, compared with this owner's Claude/Codex harness.

## Executive verdict

Cursor is ahead less because it has a fundamentally different ReAct loop and more because it has productized a small set of good harness primitives into one coherent surface: model-specific tool provisioning; dynamic, file-backed context discovery; an approval classifier layered over allowlists and sandboxes; isolated asynchronous agents whose work remains steerable and retrievable; explicit local and PR review passes; and bounded repeat-until-verified workflows. Its strongest design principle is to put less in the prompt and make the agent retrieve what it needs. Cursor reports a 46.9% token reduction in MCP-using runs from deferred tool-schema discovery, and it preserves full long outputs and conversation history as files rather than throwing them away ([Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)).

The owner's harness already has most of the underlying buses and, in several cases, stronger correctness machinery. Claude Code already provides deferred MCP Tool Search, auto memory, native snapshots/rewind, subagents, agent teams, worktrees, a classifier-backed Auto permission mode, and a large hook lifecycle. The live setup explicitly enables MCP Tool Search at a 5% threshold (`C:\Users\Prekzursil\.claude\settings.json:17`), has 18 registered hook event families (`C:\Users\Prekzursil\.claude\settings.json:81-528`), and owns typed freshness-aware execution receipts (`C:\Users\Prekzursil\.agents\harness\ledger.py:98-152`, `:1093-1163`). Rebuilding those features would be duplication.

The real gaps are four seams:

1. Long tool outputs are sometimes destructively summarized rather than losslessly spooled and dynamically re-read. The live `compress-output.py` explicitly truncates long `git status` paths and only strips ANSI for other noisy Bash output (`C:\Users\Prekzursil\.claude\hooks\cmd-rewrite\compress-output.py:1-39`, registered only for `Bash` at `settings.json:323-330`). Cursor's file-backed result approach is materially better.
2. Compaction continuity restores summaries/snapshots but does not give the continuing agent a first-class, searchable pointer to the complete pre-compaction transcript. Cursor does.
3. Asynchronous cross-vendor work is not uniformly addressable through completion. A locally recorded failure shows `sessionId:null` jobs hidden by session-scoped status lookup after their result had completed on disk (`C:\Users\Prekzursil\.claude\rules\common\cross-vendor-dispatch.md:7-30`). Cursor's agent/run lifecycle keeps status, follow-up, cancellation, and takeover attached to durable identities.
4. Verification is technically stronger here but less productized. Cursor exposes Agent Review, Bugbot, `/loop`, self-testing cloud agents, demos, and reviewable diffs in obvious places. This harness has stronger receipts and exact failing-command reruns, but many verification skills are rarely selected: the local router telemetry records `verification-loop` suggested three times/used zero and `fresh-context-verify` suggested four/used zero (`C:\Users\Prekzursil\.claude\hooks\semantic-router\success.json:1`).

The recommended direction is evolution on the existing native host + hook + skill + ledger buses. It is **very likely (80-90%)** to improve reliability and context efficiency because each recommendation below either activates a current Claude Code primitive or closes a locally observed failure with a small extension; the evidence is the live settings/code, corpus error distribution, and Cursor's published A/B result. Importing the Cursor SDK or cloning Cursor Cloud is **very unlikely (5-20%)** to outperform that approach for this owner because it would create a second runtime while duplicating native Claude/Codex capabilities; the evidence is the current native feature set and the anti-overfit constraint, not a live Cursor-versus-Claude benchmark.

## 3. Agent loop

### What Cursor does

Cursor Agent runs an open-ended search/edit/run loop and advertises no fixed tool-call limit. Tools include file/code search, web, reads, edits, terminal, MCP, guardrails, and error repair ([Agent tools](https://docs.cursor.com/en/agent/tools)). It separates Ask, Agent, and planning behaviors, can request a mode switch mid-conversation, and can ask a clarification while continuing useful file reads, edits, or commands rather than idling ([Cursor 2.4 changelog](https://cursor.com/changelog/2-4)).

The more distinctive mechanism is model-specific harnessing. Cursor says it provisions patch editing for OpenAI-style models and string replacement for Anthropic-style models, changes prompts and tools by model/version, and swaps the harness when a user switches models. It discourages mid-chat switching because histories and caches are model-specific; a fresh subagent is often safer ([Continually improving our agent harness](https://cursor.com/blog/continually-improving-agent-harness)). This is a good anti-abstraction lesson: normalize lifecycle policy, not the model's learned edit interface.

Composer adds trained self-summarization at a fixed context trigger. The summary retains conversation state such as plan and remaining tasks, and Cursor reports about 1,000-token learned summaries versus roughly 5,000-token prompted baselines, with compaction error reduced by 50% in its internal experiment ([Training Composer for longer horizons](https://cursor.com/blog/self-summarization)). These are vendor-reported model+harness results, not evidence that a self-summary model would improve this owner's workload independently.

### Where ours matches or is better

Claude Code's native loop already handles planning, tool use, compaction, sessions, snapshots, subagents, and Auto permission classification. The owner's cross-provider dispatcher adds objective receipt/freshness semantics that Cursor's public local-agent loop does not document: it classifies test/build/lint/typecheck/coverage/run/e2e/health and can require a passing execution after the last mutation plus a rerun of the exact command fingerprint that failed (`C:\Users\Prekzursil\.agents\harness\ledger.py:98-152`, `:1093-1163`; `modules.py:2167-2228`). That is a stronger completion primitive than “the model kept trying.”

Cursor's “no tool call limit” is worse for this owner. The corpus contains retry loops and expensive failures, and the earlier audit found inconsistent caps, including an enabled loop plugin capable of unlimited iterations. Open-ended autonomy without a terminal predicate amplifies tool errors and context rot. Cursor itself acknowledges that failed calls remain in context and can derail sessions; its production response is error classification, anomaly alerts, and online experiments, infrastructure this local harness does not need to clone ([Continually improving our agent harness](https://cursor.com/blog/continually-improving-agent-harness)).

### P1 — Bounded repeat-until-verified skill

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement Cursor's useful `/loop` behavior as a thin skill over `longrun` and the existing receipt ledger:

1. Require an explicit wake condition or verifier command, maximum iterations, wall-clock budget, and immutable task statement.
2. Run operations expected to exceed 60 seconds through `longrun`, emitting heartbeat and hang timeout.
3. After each iteration, evaluate the deterministic predicate from a fresh receipt; do not let prose “DONE” terminate a code task.
4. Exit only with `SUCCESS:<loop-id>` plus receipt identity or `FAILED:<loop-id> <terminal-reason>` plus diagnostic tail.
5. Persist loop count and last fingerprint in the existing event ledger; repeated identical failure triggers the existing escalation route, not more retries.

This is **very likely (80-90%)** to provide Cursor's useful persistence without its open-ended downside because the owner already mandates `longrun` and terminal outputs, and the receipt code already supplies the verifier. The remaining uncertainty is integration behavior, not architecture; a disposable acceptance experiment with “fail twice, repair, pass,” “same failure three times,” timeout, and cancellation would settle it.

Do not copy Composer training. A trained self-summarizer would be **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and would violate the anti-overfit gate. The existing provider compaction plus searchable history pointer in P3 captures the transferable mechanism.

## 4. Context management

### Cursor's strongest mechanism: files as lazy context

Cursor turns five context-heavy surfaces into dynamically discoverable files:

1. Oversized shell/MCP outputs are written in full to a file; the model sees a compact reference and can `tail`, read, `rg`, or `jq` the original.
2. After compaction, the agent receives a reference to the complete conversation-history file so it can recover details omitted by the summary.
3. Skill name/description remains small static context; full `SKILL.md` and bundled scripts load only when relevant.
4. MCP tool descriptions are synchronized into one folder per server, with only small routing context loaded initially.
5. Integrated terminal sessions are synchronized to files, making previous terminal logs searchable without injecting all output.

Cursor reports that its MCP file catalog reduced total tokens by 46.9% in runs that called MCP tools, with statistically significant but high-variance results ([Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)). This aligns unusually well with the local evidence: only a fraction of hundreds of skills/tools are used, and large catalogs contribute to Windows command-line failure.

Cursor also offers semantic codebase indexing. It uses a client Merkle tree to find changed files, syntactic chunks and cached embeddings, and teammate-index reuse through similarity hashes plus content proofs. Cursor reports semantic search raised response accuracy by 12.5% in its evaluation and reduced p99 time-to-first-query from 4.03 hours to 21 seconds when reusing a team index ([Securely indexing large codebases](https://cursor.com/blog/secure-codebase-indexing)). Cursor's security page says embeddings and obfuscated paths are stored in Turbopuffer, code transits Cursor's servers, directory hierarchy leaks, embedding reversal is possible in principle, and indexing has experienced load-related upload failures ([Cursor security](https://www.cursor.com/security)).

### Where ours matches or is worse

Skill and MCP progressive disclosure are already native. Claude Code defers MCP tools and loads only names/server instructions until Tool Search selects relevant schemas ([Claude Code MCP Tool Search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)); the live setting is `auto:5` (`settings.json:17`). Claude skills similarly expose descriptions and load bodies on demand ([Claude Code context behavior](https://code.claude.com/docs/en/how-claude-code-works)). Building Cursor's schema-folder router would duplicate the host.

Tool-result handling is worse. The live compression hook is Bash-only and says it may truncate paths; it does not preserve a lossless model-readable artifact (`compress-output.py:1-39`; `settings.json:323-330`). The shared dispatcher additionally caps injected contexts at 4,000 characters (`C:\Users\Prekzursil\.agents\harness\dispatcher.py:281-282`). Cursor's “spool, then point” avoids both context bloat and data loss.

Compaction recovery is mixed. Claude stores every message/tool/result in local JSONL and snapshots files before edits ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Locally, `harness-trim/compact-restore.ps1` reinjects a pre-compaction snapshot (`C:\Users\Prekzursil\.claude\hooks\harness-trim\compact-restore.ps1:1-21`), and the event ledger replays objective state. But those are summaries/snapshots, not an explicit retrieval handle to the full conversation.

### P2 — Lossless oversized-result spool

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing PostToolUse output hook rather than add a service:

- Trigger on normalized Bash, PowerShell, WebFetch, and MCP results above a measured byte threshold.
- Write the original bytes once under a session-scoped spool using SHA-256 content addressing and restrictive permissions.
- Replace the in-context result with exit/status fields, byte count, hash, path, first/last bounded chunks, and suggested `rg`/`jq` commands.
- Preserve typed receipt extraction before replacement, or record receipt fields alongside the spool metadata.
- Redact only the preview. Mark the file as potentially sensitive, expire it with session retention, and never persist it to Basic Memory automatically.
- Keep short outputs unchanged.

This is **very likely (80-90%)** to reduce context loss because Cursor reports a reduction in unnecessary summarization from the same mechanism and local code proves the present hook truncates. The exact size threshold and retention are **UNVERIFIED; a replay over the corpus's oversized tool results measuring tokens, retrieval rate, sensitive-data exposure, and task success would settle them**. The recommendation does not depend on a particular threshold.

### P3 — Searchable post-compaction history pointer — UNVERIFIED payload availability

**BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** On PostCompact, inject a bounded pointer to the native `transcript_path`, the pre-compaction byte offset, and a retrieval recipe. The agent should search the original JSONL only when summary details are insufficient. Record a retrieval receipt so the harness can measure whether the pointer was useful.

This is **likely (55-80%)** to prevent lost constraints with low context cost because Cursor uses the same file-reference strategy and Claude already supplies/stores the transcript path. **UNVERIFIED whether the current PostCompact payload on the installed version always includes `transcript_path`; capture one real PostCompact payload and a known-present SessionStart payload as control to settle it.** The implementation can fall back to the session ID → native transcript path mapping already used by Stop hooks.

### What not to copy: shared semantic index

A literal Cursor-style managed semantic index is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and reintroduces the explicitly rejected vector-DB/KG memory architecture. Do not build it. Cursor's own disclosures include remote embeddings, hierarchy leakage, potential inversion, and operational upload failures. A local benchmark would need to show that native `rg`/search plus bounded repo maps miss materially important relationships before revisiting this. It is **unlikely (20-45%)** that a new always-on index beats the simpler path for this owner because the audit already found no setup-specific evidence that reviving Serena/PageRank improves outcomes (`C:\Users\Prekzursil\.claude\harness-mega-audit-2026-07-18\findings\C16.md:1-12`).

## 5. Memory

Cursor memories are repository-scoped rules derived from chat. A sidecar model observes conversations and proposes relevant memories; background-generated candidates require user approval, while the agent can create a memory directly when asked ([Cursor Memories](https://docs.cursor.com/en/context/memories)). Cursor's product page also says Automations can use a memory tool to learn from past runs ([Cursor Cloud](https://cursor.com/en-US/cloud)). Privacy Mode historically restricted Cursor memories, and all AI requests route through Cursor's backend even when users provide their own API key ([Cursor privacy](https://docs.cursor.com/account/privacy)).

Our stack is stronger in breadth and provenance:

- Claude Code auto memory is on by default, repository-scoped, shared across worktrees, and loaded automatically; subagents can maintain separate memory ([Claude Code memory](https://code.claude.com/docs/en/memory)).
- Basic Memory is the owner's canonical cross-tool semantic store, with explicit temporal validity and supersession rules in the behavior contract.
- The event ledger stores objective failures, decisions, receipts, and milestones separately from semantic memory.

Cursor's user-approval step is a useful trust property, but adding another sidecar model would duplicate native auto memory and violate the anti-overfit preference for evaluator-led improvement. Cursor's memory is also only a generated rule, not enforced configuration; this is the same fundamental limitation Claude documents for CLAUDE.md/auto memory.

### P4 — Keep the two existing memory layers; add no third

**NATIVE (Claude Code already does this; we just enable it).** Keep Claude auto memory enabled for local repository learnings and Basic Memory as cross-tool canonical memory. Use the event ledger for objective history. If approval is desired for Basic Memory, expose a small pending-note review command over the existing MCP rather than run a passive model observer.

This is **very likely (80-90%)** to be safer than adopting Cursor's sidecar because it avoids a third store and preserves explicit supersession. The evidence is the existing three-role split and Claude's native default. The effectiveness of native auto memory on this owner's corrections is **UNVERIFIED; sample 50 correction candidates from `corpus.json`, check whether later sessions retrieve the correct current fact, and compare Basic Memory versus auto memory to settle it**. No recommendation to delete either store rests on that unknown.

## 6. Tools and MCP

Cursor supports stdio, SSE, and Streamable HTTP MCP servers; tools, prompts, roots, and elicitation; OAuth; project and global JSON config; an extension API for dynamic registration; per-tool toggles; default per-call approval; and image results ([Cursor MCP](https://docs.cursor.com/context/model-context-protocol)). Since 2.4, Cursor stores MCP definitions/tools as files and discovers them only when needed ([Cursor 2.4 changelog](https://cursor.com/changelog/2-4)). The file catalog can also tell the model that a server needs re-authentication instead of silently removing its tools from awareness.

Claude Code now matches the important parts. Tool Search is on by default, only used schemas enter context, `/mcp` shows server status/tool counts, and the host waits for a connecting relevant server inside Tool Search ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). The live owner setting uses the more aggressive documented `auto:5` threshold. Therefore Cursor's lazy MCP system is not a gap.

The owner's gap is fleet correctness. The known live defects and audit show drift among `.mcp.json`, `.claude.json`, intended managed files, and scheduled promotion jobs; the corpus proves a dead Tavily mount remained attractive enough to receive hundreds of calls. Cursor's one-click marketplace would not cure this and could worsen it: this machine already has roughly 1,293 orphaned plugin directories contributing to Windows argument limits, and one orphan-marked directory was still read by a live skill.

### P5 — MCP admission and health are configuration work, not a router

**CONFIG (settings/JSON only).** Preserve native Tool Search, establish one generated authoritative MCP manifest, disable/remove dead definitions only after live-sibling and active-path checks, and make preflight return a machine-readable connected/needs-auth/down state. Do not load all schemas eagerly. Use environment variables for credentials and validate presence without printing values.

This is **almost certain (90-99%)** to eliminate dead-route calls once the dead definition is removed from every authoritative source because the corpus names the exact server and the host can no longer select an absent tool. Safe orphan cleanup itself is **UNVERIFIED; a reachability graph from installed manifests, plugin metadata, and live file-open traces, followed by a quarantine-and-smoke experiment, would settle which directories are removable**. The recommendation is admission control, not immediate bulk deletion.

### Where Cursor is worse

- Default MCP approval is useful, but forum reports documented periods where hook `allow`/`ask` precedence was unreliable; Cursor acknowledged that only `deny` worked consistently in affected versions ([Cursor hook permission bug](https://forum.cursor.com/t/beforeshellexecution-returns-permission-ask-but-sandboxed-agent-shell-still-runs-the-command-sandbox-true/155438)). This is historical/community evidence, not proof of the July 2026 build.
- Marketplace abundance increases supply-chain and context-governance burden. Cursor plugins can bundle skills, agents, MCPs, hooks, and rules in one install ([Cursor 2.5 changelog](https://cursor.com/changelog/2-5)); that packaging convenience also concentrates authority.
- Cursor routes AI requests through its backend even with user API keys. This is a material privacy/availability tradeoff versus local-first Claude/Codex CLI configuration ([Cursor privacy](https://docs.cursor.com/account/privacy)).

## 7. Permission model and sandboxing

Cursor offers manual approval, allowlists, sandboxed command execution, and Auto-review. Auto-review applies to Shell, MCP, and Fetch: allowlisted calls run, sandboxable actions execute in the sandbox, and remaining calls go to a classifier subagent that can allow, request an alternative, or ask the user ([Auto-review Run Mode](https://cursor.com/changelog/auto-review)). Cursor 2.5 added domain allowlists, filesystem/directory controls, and enterprise egress policy ([Cursor 2.5 changelog](https://cursor.com/changelog/2-5)). Ask mode is enforced read-only even when broad execution is enabled.

This directly exposes the worst live local posture: `permissions.defaultMode` is `bypassPermissions` (`C:\Users\Prekzursil\.claude\settings.json:26-71`). The setting suppresses prompts across a large host surface, while known guards have false-positive/semantic-discrimination defects (`INPUT-known-harness-defects.md:5-93`). More regex hooks layered on bypass are not equivalent to containment.

Claude Code now has a native Auto mode with a separate classifier. It approves reads and workspace edits, classifies other actions, strips tool results from the classifier context, checks subagents at spawn/action/return, and falls back to prompting after repeated blocks ([Claude Code permission modes](https://code.claude.com/docs/en/permission-modes#eliminate-permission-prompts-with-auto-mode)). It also supports native sandboxing and protected paths. The correct port is therefore configuration, not Cursor's classifier.

### P6 — NATIVE Auto mode + sandbox — UNVERIFIED live eligibility

**NATIVE (Claude Code already does this; we just enable it).** Replace bypass as the default with native Auto mode for compatible models/accounts, keep explicit deny/ask rules for secrets, destructive Git operations, deployments, and credential boundaries, and route untrusted commands into the native sandbox.

**UNVERIFIED whether this signed-in account/model combination exposes Auto mode and whether the Windows sandbox contains filesystem/network writes correctly; run `claude --permission-mode auto` in a disposable repository, then attempt known-safe reads, a workspace edit, an external write, a blocked secret read, a domain allow/deny probe, and a subagent action to settle it.** If Auto is unavailable or containment fails, use Manual/Plan on the host and the existing WSL2/runner isolation lanes. It is **very likely (80-90%)** that Auto reduces routine prompts while improving on bypass when eligibility holds because Claude documents a classifier decision order and explicit blocked categories; it is not a safety proof.

### P7 — Enforced egress on remote runs

## 11. What Cursor does worse and should not be copied

1. **Backend dependence and privacy tradeoff.** All AI requests route through Cursor's backend, even with a user's API key; semantic indexing stores embeddings and obfuscated path metadata remotely ([Cursor privacy](https://docs.cursor.com/account/privacy), [Cursor security](https://www.cursor.com/security)). The owner values local tools and explicit data boundaries.
2. **Long chats still degrade.** Cursor advises starting a new conversation when long chats accumulate noise and lose focus, then referencing past chats selectively ([Agent best practices](https://cursor.com/blog/agent-best-practices)). Its trained Composer path improves this for one model but is not a universal cure.
3. **Verification claims are partly self-reported.** Token reductions, accuracy lifts, Keep Rate, Bugbot resolution, and Composer compaction gains are useful signals but come from Cursor's own telemetry/evals. They establish mechanisms worth testing, not guaranteed transfer.
4. **Hooks have had enforcement regressions.** Cursor forum reports include malformed hook JSON historically failing open and `ask`/`allow` precedence bugs; a later update reportedly fixed malformed JSON ([malformed hook response report and fix](https://forum.cursor.com/t/beforeshellexecution-hook-malformed-json-response-silently-allows-command-instead-of-blocking/152669)). Our hook bus also has defects, but Cursor is not evidence that more hooks are inherently safe.
5. **Unlimited loops and large fleets can amplify failure.** Cursor's no-tool-call-limit stance and “as many cloud agents” product framing need explicit budgets for this owner.
6. **Automatic memories and learned rules can entrench mistakes.** Cursor provides user approval for memory candidates, which is good; Bugbot's automatic rule promotion is less clearly grounded in falsifiable tests.
7. **Marketplace/plugin proliferation is dangerous on this Windows host.** The local orphan-plugin/argument-limit incident makes one-click expansion a liability unless installs are content-addressed, deduplicated, reversible, and admission-tested.
8. **Cursor checkpoints are narrower than version control.** They track agent edits, not manual edits, are local, and are cleaned automatically ([Cursor checkpoints](https://docs.cursor.com/en/agent/chat/checkpoints)). Claude's native session snapshots plus Git and the owner's full-tree receipt identity are at least as suitable.
9. **Cursor's semantic index is exactly the architecture this program rejected.** Its results may be excellent, but copying it means a new embedding/index service. The minimal architecture gate wins until a workload-specific eval proves otherwise.
