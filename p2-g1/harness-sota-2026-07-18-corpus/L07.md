# L07 — GREEN-TESTS-BROKEN-DELIVERABLE: a packaged-artifact golden-journey oracle

## Executive verdict

The missing control is not another test suite and not another hook. It is a **consumer-side release-candidate oracle**: build the exact distributable, bind the run to its SHA-256, install or unpack those bytes into a disposable environment that cannot import/read from the source checkout, perform one declared owner journey through the public entry point, and judge success from externally observed state. The release receipt is valid only when the artifact identity, journey identity, external observations, and changed-set identity all match.

This must **replace the semantics of the already-wired `journey-coverage` child check**, not add a seventh hook. The existing check already occupies the Stop dispatcher at `/local_disk0/codexwork/bundle/claude/hooks/_dispatch/manifest.json:72-141`, and its own contract says it closes the “golden-journey nobody ran” blind spot at `/local_disk0/codexwork/bundle/claude/hooks/journey-coverage/README.md:6-17`. But its definition of “covered” is only a successful command that names the spec or a broad E2E command (`README.md:19-23`); it does not bind evidence to packaged bytes, a clean install, or an observed product outcome. Its implementation also returns success when no matching spec is found (`check.py:218-224`) and catches every exception with exit 0 (`check.py:204-247`). That is useful fail-open prompting, not a release oracle.

The core recommendation is **very likely (80-90%)** to close the stated packaged-artifact gap because three independent foundations point to the same boundary: (1) Python packaging guidance warns that tests run from the working directory can exercise source instead of the installed package ([pyOpenSci, “src layout and testing”](https://www.pyopensci.org/python-package-guide/package-structure-code/python-package-structure.html)); (2) SLSA verification requires the provenance subject to match the digest of the artifact being verified and then checks expectations against that subject ([SLSA 1.2 artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts)); and (3) the local harness currently authenticates neither condition—receipt class comes from command text and positive output (`/local_disk0/codexwork/bundle/agents/harness/ledger.py:360-400`), while freshness is only sequence-after-mutation and ANY-of receipt class (`ledger.py:1093-1117`). The residual 10-20% is environment-specific packaging/install behavior; the settling experiment is the shadow canary in Finding 8 across at least one known-good and three seeded broken artifacts on Windows.

No proposal below adds a daemon, durable-execution engine, vector database, knowledge graph, trained critic, observability SaaS, guardrail framework, or second orchestrator. Every proposal rides the existing quality command, dispatcher, event ledger, Workflow/fresh-context verifier, and `journey-coverage` slot. This passes the anti-overfit gate.

## Grounding and detector discipline

The corpus is sufficiently complete for positive-count claims: it distilled 11,633 files / 10.62 GB with zero failed files, one bad line, and 32 oversized lines, and explicitly warns that absence claims require checking those limits (`/local_disk0/codexwork/bundle/inputs/corpus.json:2-11`). I treat its `hooks` section as no data, per the pinned warning, and make no inference about hook firing frequency.

The corpus shows why a prose or self-reported completion receipt is too weak:

* Structured output failed 846 of 3,694 calls (22.9%) (`corpus.json:103-108`), including 294 repetitions of one required-property schema mismatch (`corpus.json:4371-4385`). A large bespoke journey-result schema would therefore recreate a measured high-damage failure mode.
* Shell transport is not a neutral verifier: Bash has 1,631 unmatched-quote EOF fingerprints (`corpus.json:4280-4296`), PowerShell has 2,031 errors in 19,181 calls (`corpus.json:8871-8899`), and Glob has 592 `ENAMETOOLONG` failures plus 175 timeouts (`corpus.json:8995-9007`). The oracle should invoke a checked-in command by path and pass data through files/argv fields, not synthesize a long inline shell program or discover it through broad globs.
* Write/Edit collectively show 939 “file has not been read yet” failures in the cross-tool fingerprint (`corpus.json:4298-4314`), with 568 attributed to Edit (`corpus.json:8933-8944`) and 366 to Write (`corpus.json:9057-9076`). The probe therefore consumes the already-built artifact read-only; it does not patch the artifact during verification.
* The owner-correction detector is explicitly recall-biased and its unfiltered smoke sample was 41/41 false positive (`corpus.json:10371-10374`). I do not use its tempting “do not stop” counts as owner preference evidence. The owner signals used below are the explicit hard constraints in this unit and the higher-confidence live defects, especially the known-positive-control rule (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:111-129`).

The existing apparatus is real and must be extended rather than duplicated. Receipt classes already include build/run/E2E (`ledger.py:98-120`); a fresh receipt must post-date a mutation (`ledger.py:1065-1117`); `agent-as-judge` is deliberately advisory and says deterministic receipts carry blocking weight (`/local_disk0/codexwork/bundle/claude/agents/agent-as-judge.md:15-35`); and the Codex worker contract already says exit 0 alone is insufficient and requires claimed files plus captured test output (`/local_disk0/codexwork/bundle/claude/agents/codex.md:80-97`). The gap is artifact-bound behavioral proof, not a lack of verification vocabulary.

## Reference design: the one golden journey

The implementation target is a small checked-in `golden-journey.json` plus one thin runner invoked from the existing release/quality workflow. The manifest should remain intentionally boring:

```json
{
  "version": 1,
  "journey_id": "install-launch-primary-action",
  "artifact_glob": "dist/*.whl",
  "entry": ["mytool", "doctor", "--json"],
  "setup_adapter": "python-wheel",
  "timeout_seconds": 120,
  "preconditions": ["source_unreachable", "clean_user_config"],
  "postconditions": [
    {"id": "public-entry-ok", "observer": "process", "expect_exit": 0},
    {"id": "result-created", "observer": "filesystem", "path": "out/result.json", "json": {"status": "ready"}}
  ],
  "forbidden": ["source_checkout_import", "network_unless_declared"],
  "thread_ids": ["OT-123"]
}
```

The runner lifecycle is `resolve exactly one artifact -> hash -> create disposable consumer root -> install/unpack artifact -> make source checkout unreachable -> invoke public entry -> observe postconditions through independent channels -> run detector controls -> emit one compact receipt -> cleanup`. “Exactly one” matters: zero or multiple artifact candidates is `NOT_EVALUATED`, never green. A package-specific adapter may translate the setup step (`pip install wheel`, `npm install tarball`, unzip executable, install VSIX, load MCP server), but adapters all emit the same small receipt envelope.

A completion state is one of `VERIFIED`, `FAILED_PRODUCT`, or `NOT_EVALUATED`. `NOT_EVALUATED` covers probe crashes, missing dependencies, unsupported artifact types, unavailable external services, or ambiguous artifacts. Hooks themselves catch exceptions and exit 0 as required; the explicit release command, not the hook, returns nonzero for `FAILED_PRODUCT` and `NOT_EVALUATED`. Thus hook infrastructure fails open without turning “could not test” into “passed.”

## Findings (inferred-surprise first)

### Finding 1 — Test the consumer artifact, with the source checkout made unreachable

**Improvement.** Replace “E2E command ran” with “the exact release-candidate bytes were installed and exercised outside the authoring tree.”

**What it is.** The runner resolves exactly one packaged artifact, computes SHA-256, creates a disposable consumer environment, installs/unpacks only that artifact, changes cwd outside the repository, removes the repository from `PYTHONPATH`/`NODE_PATH` and equivalent search paths, and invokes the public command/API/UI entry point. For Python, use a non-editable wheel install; for Node, install the `.tgz`; for a binary, copy the packaged archive into a clean directory and launch that copy. The artifact is never rebuilt between hashing and running.

**Why-inferred (owner signal).** The owner named the defect as “packaged artifact fails though CI passed,” while the quality bar explicitly rejects built-but-not-wired and half-built deliverables. The current check can mark a journey covered merely because a successful command named the spec (`journey-coverage/README.md:19-23`), and the general quality command only formats/lints (`/local_disk0/codexwork/bundle/claude/commands/quality-gate.md:13-22`). The owner is asking for consumer reality, not a stronger source-tree proxy.

**How-to-build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Implement one stdlib-first runner with a tiny adapter table. Inputs are manifest path and artifact path; outputs are a compact JSON receipt plus stdout/stderr files. Invoke it as the R3/release command from the existing quality workflow. Replace the `journey-coverage` Stop child with a reader that asks only whether a current digest-bound receipt exists; do not add a hook. Use `tempfile`/`New-Item` for a specific disposable directory, never a broad recursive target. On Windows, resolve executables with `Get-Command`, not Git Bash `which`.

**EXTERNAL signal.** Signal A is the SHA-256 of the bytes installed; signal B is a process launched from the disposable install root whose resolved module/executable path is recorded and asserted not to lie under the source checkout. A product postcondition then comes from the public interface. These mechanisms are independent of the authoring model and distinguish “source works” from “package works.”

**SOTA citation.** pyOpenSci explains that working-directory tests can import source rather than the installed package and miss user installation failures ([package structure guidance](https://www.pyopensci.org/python-package-guide/package-structure-code/python-package-structure.html)). SLSA separately requires verification that the statement subject matches the artifact digest ([SLSA 1.2](https://slsa.dev/spec/v1.2/verifying-artifacts)).

**Value x effort.** transformative x medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **very likely (80-90%)** that this catches the named class, because source shadowing and artifact identity are directly removed; evidence is the packaging guidance, SLSA subject-binding rule, and local command-name-only coverage. UNVERIFIED whether all owner projects have a build artifact discoverable without project-specific configuration; the settling experiment is to inventory release outputs in a read-only sample of ten recent repos and measure how many resolve exactly one artifact.

### Finding 2 — Judge outcome state, not the agent’s trajectory or command vocabulary

**Improvement.** Express the golden journey as preconditions, actions through the public surface, externally observable postconditions, and forbidden state changes.

**What it is.** A journey is not “run Playwright” or “run a command containing E2E.” It is a contract such as “install -> launch -> create item -> reopen -> item persists,” with every terminal predicate machine-checkable. Each load-bearing outcome gets two mechanically independent observations where feasible: UI-visible state plus backend/API/file state; CLI JSON plus created file; MCP tool response plus server-side/readback state. A trace or screenshot is diagnostic evidence, not the sole pass oracle.

**Why-inferred (owner signal).** The owner’s law rejects same-context self-correction and requires a different tool/execution result/owner. The live defect D2 establishes the known-positive-control discipline after seven wrong conclusions from unvalidated probes (`INPUT-known-harness-defects.md:111-129`). Locally, the receipt classifier can call output “pass” from positive words (`ledger.py:360-400`), which is exactly a trajectory/text proxy.

**How-to-build.** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Put postconditions in the per-project manifest and reuse existing adapters. Allow only a small observer vocabulary (`process`, `filesystem`, `json`, `http`, `ui`, `mcp-readback`) rather than arbitrary shell. Composite product success is ALL-of. Unknown observer types and missing observations produce `NOT_EVALUATED`. Keep model judgment advisory for genuinely subjective residue, consistent with `agent-as-judge` (`agent-as-judge.md:15-35`).

**EXTERNAL signal.** The verifier queries state after the action through an observer different from the action channel. For a UI write, query the backing API or reopen in a new browser context; for a CLI write, parse the file/database with a separate tool. The receipt records observer type, normalized result hash, and timestamp.

**SOTA citation.** Agent-Diff’s 2026 benchmark defines success by expected environment state change rather than fuzzy trace/parameter matching ([Agent-Diff paper](https://arxiv.org/abs/2602.11224)). Playwright recommends web-first retrying assertions for asynchronous UI state and trace capture through its test runner ([assertions](https://playwright.dev/docs/test-assertions), [tracing](https://playwright.dev/docs/api/class-tracing)).

**Value x effort.** transformative x low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **very likely (80-90%)** that state contracts reduce false green relative to command-name matching; evidence is the direct local classifier weakness and the state-diff benchmark design. UNVERIFIED whether two independent observers exist for every deliverable class; the settling experiment is to draft manifests for one CLI, one web app, one MCP, and one desktop artifact and record which postconditions have only one observable channel. Single-channel cases stay explicitly single-signal and cannot support an absence/done claim without owner confirmation.

### Finding 3 — Seed a known-bad package to prove the oracle can detect the failure it claims to guard

**Improvement.** Make detector calibration part of every journey definition, not a one-time unit test of the runner.

**What it is.** Each journey carries a harmless, deterministic negative control that breaks packaging without breaking source tests—for example omit a required resource from a wheel/tarball fixture, remove an entry point in a copied fixture, or point an internal packaged path at a nonexistent file. It also carries a known-good artifact. A detector version is eligible to certify releases only after the known-good passes and the known-bad fails for the expected reason code.

**Why-inferred (owner signal).** The owner explicitly mandates proving a detector against a known-present item before reporting absence. D2 shows a detector reporting zero skills, agents, and hooks until a known-positive control proved only hooks were broken (`INPUT-known-harness-defects.md:120-129`). A golden journey that has never demonstrated sensitivity to a package-only defect is another unvalidated detector.

**How-to-build.** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add two tiny committed fixture artifacts or fixture build recipes per adapter and a `--self-test` mode to the same runner. Do not mutate the real candidate. Cache the detector-version calibration receipt by runner hash + adapter + platform so every release need not rebuild controls; invalidate it when the runner, adapter, package toolchain major version, or OS changes.

**EXTERNAL signal.** Independent signal A: known-good artifact reaches every postcondition. Independent signal B: seeded package-only defect yields the declared failure code while source-tree tests remain green. This is a different artifact and a different measurement, not a repeated probe.

**SOTA citation.** NIST AI RMF asks that AI systems be validated in context and that measurement include feedback and unanticipated impacts ([AI RMF Core, Measure/Map outcomes](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)). The local rule is stronger and directly evidenced by D2.

**Value x effort.** high x low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it.

**Confidence.** **almost certain (90-99%)** that a passing positive plus failing seeded negative establishes detector sensitivity to that seeded class; the evidence is mechanical. It does not establish sensitivity to all package failures, so the claim is deliberately bounded to the seeded class.

### Finding 4 — Bind the receipt to artifact digest, source/change digest, journey, platform, and observer evidence

## Hook-budget and failure semantics

No seventh hook is proposed. The existing local dispatcher has one Stop invocation whose manifest already contains `journey-coverage` (`_dispatch/manifest.json:72-141`). Replace that child’s implementation with a receipt reader/reconciler, or fold it into the shared dispatcher’s existing claim-warning/receipt gate. If the shared provider-neutral implementation becomes canonical, remove the local child entirely; do not run both “v1” and “v2.”

The latency-heavy operation never runs inside Stop. Build/install/journey execution runs as the explicit R3/release command, using the existing long-running workflow where needed. Stop only hashes/replays a bounded receipt and emits one line. This respects the ~6-hook ceiling and prompt-fatigue constraint.

Failure taxonomy is intentionally split:

* Product assertion fails against successfully installed artifact -> `FAILED_PRODUCT`, explicit release command nonzero.
* Artifact is absent/ambiguous, adapter unsupported, prerequisite unavailable, observer crashes, or timeout is infrastructure -> `NOT_EVALUATED`, explicit release command nonzero; hook catches its own error and exits 0.
* All postconditions and detector controls pass for the exact digest -> `VERIFIED`.
* Model/judge says “looks good” without deterministic proof -> advisory only; never `VERIFIED`.

This avoids the current dangerous equivalence between silence and green. The Stop wrapper may fail open operationally, but a missing digest-bound receipt cannot become a release receipt. Ordinary agent work continues; the harness merely withholds a verified/ship claim.

## Concrete acceptance tests for the implementation

1. Build source-tree-green fixture whose wheel omits a required data file. Source tests remain green; consumer journey must return `FAILED_PRODUCT:missing-resource`.
2. Build known-good fixture. Consumer journey must return `VERIFIED`, resolve imports/executable outside the repo, and record matching artifact hash.
3. Copy a valid old receipt beside a byte-modified artifact. Digest comparison must return `NOT_EVALUATED:artifact-mismatch` before execution.
4. Run from repository cwd with an installed artifact. The probe must move outside the repo and prove resolved module/executable is under the disposable root.
5. Make the observer throw. Hook invocation exits 0, explicit release command returns nonzero `NOT_EVALUATED:observer-error`, and no verified receipt is written.
6. Change one byte in `golden-journey.json` after a green run. Prior receipt must be stale by manifest hash.
7. Leave one manifest `thread_id` unresolved. Result must be `NOT_EVALUATED:open-thread`; explicitly deferred thread with owner/reason remains visible but does not masquerade as verified.
8. Route the same synthetic receipt through Claude and Codex adapters. Replayed normalized fields and terminal state must match.
9. Run a command merely containing `playwright`, `e2e`, `success`, or `golden` without a receipt. It must not satisfy the release claim. This directly regresses the lexical receipt weakness at `ledger.py:159-174,360-400`.
10. Confirm that the Stop hook count is unchanged and that the old journey child is replaced/removed, not duplicated.

The implementation is done only when all ten have captured external execution artifacts and the known-good/known-bad detector controls behave as specified. A same-context review is not an acceptance signal.

## Alternatives considered and rejected

**“Just run all CI tests after packaging.”** Rejected because it can still run against source, and it does not require installation through the consumer entry point. CI remains R2; this oracle is R3.

**Add another Stop hook.** Rejected by the ~6-hook ceiling and because `journey-coverage` already owns the slot. Replacement/folding is the only compliant topology.

**Use an LLM-as-judge on screenshots.** Rejected as terminal authority by the same-context law and by the already-built advisory judge contract (`agent-as-judge.md:15-35`). A fresh second model may annotate semantic residue but cannot grant done.

**Require SLSA signing before any local release.** Rejected as disproportionate for the first closure. Digest-binding and local provenance fields capture the relevant artifact-identity property now. GitHub/Sigstore attestation is a later supply-chain layer, not a prerequisite for detecting missing packaged resources.

**Build a generic declarative workflow engine.** Rejected by the anti-overfit gate. A small manifest plus adapter table is enough; the existing dispatcher/Workflow is the execution bus.

**Make every project define dozens of journeys.** Rejected for prompt fatigue and maintenance cost. Start with one highest-value owner journey per artifact class, plus any path that has already escaped green CI. Expand only from observed escapes or explicit release criticality.

**Let the probe repair the package and retry.** Rejected because it contaminates the subject under test and returns to same-context self-correction. The probe is read-only on candidate bytes; repair happens in a new authoring iteration and produces a new digest.

## Final recommendation

Build one consumer-side, digest-bound golden-journey runner; define one state-based journey manifest per shipped artifact; calibrate it with known-good and package-only known-bad controls; store the compact authenticated result in the existing ledger; and replace the existing `journey-coverage` child’s command-name logic with a bounded receipt/thread reconciler. Promote from shadow only after canaries and both provider adapters agree. This is the smallest architecture that actually changes the truth condition from **“tests/CI said green”** to **“the exact thing the owner will receive was installed and demonstrably completed the owner journey.”**
