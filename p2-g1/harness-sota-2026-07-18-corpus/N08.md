# N08 — Capability discoverability / auto-routing: the prune-versus-surface decision

**Unit:** N08, partner-dimension unit  
**Date:** 2026-07-19  
**Scope:** read-only analysis of the unpacked harness plus external research; the only write is this artifact.  
**Decision in one sentence:** replace the static “show the model a catalogue and hope” posture with an evidence-bearing lifecycle for each capability—canonicalize it, prove it is live, expose it only when a task makes it eligible, measure an external outcome, and prune only after a controlled opportunity test fails.

## Executive verdict

The correct answer is neither wholesale pruning nor wholesale surfacing. The portfolio contains at least four materially different cases:

1. **Live, valuable, already used:** keep discoverable on demand, but remove from the global SessionStart catalogue. ToolUniverse, basic-memory, the research stack, browser automation, reverse-engineering MCPs, and chemistry MCPs are in this class. The corpus records 1,864 ToolUniverse server uses, 1,332 basic-memory uses, 1,259 Firecrawl uses, 1,110 uses of the plugin-local Ghidra bridge, 194 Playwright uses, 150 Schrödinger uses, and 34 RDKit uses (`/local_disk0/codexwork/bundle/inputs/corpus.json:13370-13418`).
2. **Dark but plausibly relevant:** keep in an on-demand probation index and run task-matched exposure tests. APKTool/JADX, security-corpus lookup, LOLBin lookup, spreadsheet/document conversion, and OCR belong here. “Zero recorded use” alone is not evidence of zero value.
3. **Duplicate aliases and dead endpoints:** prune from the exposed choice set, retaining one canonical route and a searchable tombstone. The `claude_ai_Tavily` endpoint is the clearest instance: Tavily extract had 532 calls at 25.75% error, Tavily search had 194 calls at 71.65% error (`corpus.json:174-180`, `:318-324`), and “not connected” appears as a concrete failure fingerprint (`corpus.json:4388-4400`, `:9130-9148`). Working Tavily alternatives also appear in the same corpus (`corpus.json:13380-13386`, `:13473-13494`).
4. **Not measurable with the supplied detector:** do not decide. The corpus itself warns that its correction candidates are recall-biased and that 41/41 in one unfiltered smoke sample were false positives (`corpus.json:10371-10374`); its hook section explicitly says the detector is broken and must be treated as no data (`corpus.json:13260-13263`). The semantic-router index is a stale 2026-06-29 snapshot of 360 units, not a verified 2026-07-19 installed roster (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/index/meta.json:1`).

This lifecycle is **very likely (80-90%)** to reduce catalogue/context tax without hiding useful specialists, because (a) Anthropic reports that on-demand Tool Search cut tool-definition context by 85% and improved internal large-library MCP accuracy, and (b) this corpus already records 5,091 ToolSearch calls at only 0.08% error (`corpus.json:87-92`). The remaining uncertainty is transfer from Anthropic’s API evaluation to this owner’s Windows Claude Code workload; the settling experiment is the paired replay evaluation in Finding 8.

## Decision rule used for every item

Each capability gets one lifecycle state, not an undifferentiated “installed/unused” bit:

| State | Per-item evidence required | Exposure | Exit rule |
|---|---|---|---|
| **CORE** | frequent successful use or safety-critical universal need | native-loaded only if truly universal | demote if a canonical replacement wins paired executions |
| **ON-DEMAND** | at least one successful, task-matched execution | ToolSearch/router only | promote with repeat benefit; probation after 90 eligible tasks without success |
| **PROBATION** | plausible task fit but no verified successful use, or stale/uncertain installation | randomized, low-rate task-matched exposure; never global catalogue | promote on independently verified task success; retire after the minimum opportunity gate below |
| **QUARANTINE** | liveness/schema/permission failure | hidden from routing, searchable by tombstone | return only after liveness plus a real canary call succeeds |
| **RETIRED** | duplicate, superseded, or failed controlled opportunity test | not routable; alias resolves to canonical replacement | reversible reinstall/re-index if a real task later demands it |

**Minimum opportunity gate:** at least 20 *eligible* prompts, at least five actual surfaced exposures, zero successful executions attributable to the capability, and either (a) a canonical alternative succeeds on the same task class or (b) the owner dismisses it twice. This threshold is **roughly even (45-55%)** to be the optimal sample size; it is deliberately a starting policy, not a fact. **UNVERIFIED threshold premise:** the paired replay and live shadow trial in Finding 2 must estimate confidence intervals and tune it. The recommendation inherits that uncertainty only for the numeric threshold, not for the need to measure opportunity rather than raw non-use.

Every implementation rides the existing semantic-router / ToolSearch / liveness / event-ledger buses. None adds a seventh hook, second orchestrator, vector database, knowledge graph, durable-execution engine, trained critic, SaaS, or guardrail framework.

## Finding 1 — Inferred surprise: remove the SessionStart capability “homepage”; preserve the library behind native search

**Improvement — NATIVE (Claude Code already does this; we just enable it):** make native ToolSearch plus the existing semantic router the only normal discovery surfaces; stop injecting the global capability catalogue at every SessionStart. Fold the small project card into the existing SessionStart carrier, but do not emit the global list.

**What it is:** a sparse discovery architecture. Keep a tiny always-visible core consisting only of ToolSearch and truly universal primitives. Defer specialist schemas and names until the current prompt establishes a task match. The current catalogue explicitly injects all groups once per session (`capability-catalog/inject.py:42-52`, `:55-83`), while the router already bounds output to six semantic suggestions and per-kind caps (`semantic-router/route.py:89-105`, `:305-342`).

**Why-inferred:** the owner asked for expansion without prompt fatigue, and the local record shows both catalogue pressure and strong native discovery. ToolSearch was called 5,091 times with four errors (`corpus.json:87-92`). The owner also explicitly asked whether skills existed for app automation (`corpus.json:10492-10494`), indicating that *reachable recall* matters more than seeing a static list. A long list is also not functioning as reliable awareness: the catalogue advertises OCR/document routes (`capability-catalog/catalog.json:33-35`), yet the owner later asked why no OCR was found (`corpus.json:10712-10714`).

**How-to-build:**

1. Mark non-core MCP tools/servers for deferred loading where Claude Code exposes that configuration. Keep ToolSearch non-deferred.
2. In `capability-catalog/inject.py`, retain only the project-card block and a one-line “use ToolSearch for specialist capabilities” reminder. This replaces/folds the existing catalogue injection; it is not a new hook.
3. Keep the semantic index as a candidate generator, but emit at most one primary route plus one fallback. If confidence is low, emit a ToolSearch query suggestion rather than four skills + three MCPs.
4. Store the complete catalogue out of prompt context as a searchable manifest with lifecycle state and canonical alias.
5. Preserve fail-open behavior: any search/router failure yields no nudge and leaves native tools usable. The existing router already catches errors and exits zero (`semantic-router/route.py:361-405`).

**External signal that verifies it:** replay the same 200 held-out real prompts in fresh contexts under A/B conditions: current SessionStart catalogue versus sparse ToolSearch. An external evaluator checks (1) correct capability present in the retrieved shortlist, (2) successful real or sandbox execution, (3) task completion, (4) input tokens, and (5) latency. The implementing context does not grade itself.

**SOTA citation:** Anthropic’s Tool Search design defers tools until needed, reports roughly 85% context reduction, and reports internal MCP accuracy gains when large tool libraries are searched on demand: https://www.anthropic.com/engineering/advanced-tool-use . ToolRet independently shows that generic retrievers can perform poorly on tool retrieval and that poor retrieval degrades task pass rate, so the local router needs task-specific evaluation rather than trust by construction: https://aclanthology.org/2025.findings-acl.1258/ .

**Confidence:** **very likely (80-90%)** that sparse discovery beats the global catalogue on context and fatigue, supported by Anthropic’s measurements, this corpus’s reliable ToolSearch use, and the catalogue/OCR mismatch. **UNVERIFIED Claude-Code configuration detail:** whether every locally connected MCP supports deferred loading is settled by enumerating the live Claude Code tool configuration schema on Windows and running one deferred-server canary; unsupported servers remain behind the existing semantic router.

**Value × effort:** transformative × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first, because removing an always-visible catalogue changes global behavior even though it is reversible.

**Anti-overfit gate:** passes. It removes prompt scaffolding, uses native ToolSearch, and folds rather than adds a hook.

## Finding 2 — Inferred surprise — UNVERIFIED: give every dark capability a small “option budget,” not permanent shelf space

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** extend the existing semantic-router success ledger into a per-capability exposure ledger with eligible/surfaced/invoked/executed/succeeded/dismissed counters and a bounded exploration policy.

**What it is:** a contextual-bandit-like probation mechanism without a trained policy or new runtime. For each dark capability, detect only prompts for which it is plausibly eligible. On a small, deterministic sample (for example, hash(session, capability) modulo 20), surface the candidate. Compare its downstream externally observed outcome with unexposed eligible prompts. This buys evidence about latent utility while capping fatigue.

**Why-inferred:** raw non-use confounds “not useful,” “not discoverable,” “not installed,” and “suggested at the wrong time.” The current router ledger records `systematic-debugging` as suggested 1,038 times but credited once, `benchmark-optimization-loop` 787/0, and `parallel-execution-optimizer` 787/0 (`semantic-router/success.json:1`). Independently, the corpus records actual systematic-debugging skill invocations (`corpus.json:13289-13304`). This does not prove the observer is broken; it proves that the current suggested/used ratio is not sufficient evidence for pruning. **UNVERIFIED cause:** it may reflect bad routing, missed alias credit, suggestions emitted after the agent already chose, or genuine ignore. A timestamped replay of prompt → route emission → tool use settles the cause.

**How-to-build:**

1. Add fields to the existing `success.json` row schema: `eligible`, `surfaced`, `invoked`, `exec_ok`, `task_ok`, `dismissed`, `last_seen`, and `variant`.
2. Compute eligibility in `semantic-router/route.py`; log it even if calibrated silence suppresses output. Fix the current order where `record_suggested` occurs inside `assemble` before calibrated-silence suppression (`semantic-router/route.py:346-357`, `:384-387`), because it currently can count a non-visible suggestion.
3. Reuse `semantic-router/observe.py` for invocation and tool result fields. It is already wired on `Skill|Task|mcp__.*` in the existing PostToolUse route (`hooks/_dispatch/test_wiring.py:115-124`) and is fail-open (`semantic-router/observe.py:52-67`). No new hook is added.
4. Use execution success from the actual PostToolUse payload, not the agent’s narrative. Use the next owner turn only for dismiss/accept, through the existing reaction logger; that logger explicitly derives reactions from owner behavior and tool invocations (`calibrated-silence/log_reaction.py:2-28`, `:118-151`).
5. Surface at most one probation candidate per session and never during a high-fatigue period. The exploration budget is global so multiple capabilities cannot each consume one prompt.
6. Retire only after the minimum opportunity gate, never from calendar age or raw zero use.

**External signal that verifies it:** the actual next tool invocation and tool result, plus a different-context task-success evaluator. Owner dismissal is an additional independent signal, not the sole one.

**SOTA citation:** Microsoft’s validated human–AI guidelines say to time services based on current task/environment, support efficient dismissal, learn from user behavior, and update cautiously: https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf . Training Proactive and Personalized LLM Agents explicitly optimizes productivity, proactivity, and personalization jointly rather than treating proactivity alone as success: https://arxiv.org/abs/2511.02208 .

**Confidence:** **likely (55-80%)** that bounded, task-matched exploration identifies some valuable dark capabilities without material fatigue; evidence is the current ledger ambiguity, owner correction examples, and the cited human–AI work. The exact exploration rate is **UNVERIFIED**; the experiment is a two-week shadow trial followed by a maximum-five-exposure live trial, measuring acted/dismissed/task-success rates.

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** confirm-first for the first live exploration; shadow logging can be just-do-it.

**Anti-overfit gate:** passes. This is a few fields and policies inside the existing router/observer/reaction buses, not a new bandit service or trained critic.

## Finding 3 — Inferred surprise: retirement must leave a tombstone, or pruning recreates “missing skills” stress

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** add a searchable retirement/tombstone record for every pruned alias or capability and attach it to the event ledger / capability manifest.

**What it is:** pruning removes a capability from the routing index and prompt catalogue but writes a durable record: old name(s), canonical replacement, reason code, evidence window, date, reversible recovery command, and open-thread link. ToolSearch for the old name returns “retired → use X,” never a silent zero-result.

**Why-inferred:** the owner explicitly asked where previously created SWFOC, binary reverse-engineering, and Battle Cats skills had gone (`corpus.json:11158-11162`). “Never drop a thread” therefore applies to capability lifecycle as much as task tracking. Silent pruning is **very likely (80-90%)** to reduce catalogue tax while recreating a known stressor; the evidence is the owner’s direct missing-capability message, and the tombstone lookup experiment below measures whether the mitigation works.

**How-to-build:**

1. Add `state`, `aliases`, `canonical`, `reason`, `evidence`, `retired_at`, and `recovery` to the existing capability manifest generated alongside the semantic index.
2. Before index omission, append a `capability_retired` event through the existing event-ledger/note path and add or update the relevant OPEN-THREADS item if recovery/action remains.
3. Index tombstones as a separate `alias` kind that can return only one terse result and cannot be invoked.
4. The router resolves an old alias silently to the canonical live capability. It surfaces the retirement explanation only if the owner names the old item or asks where it went.
5. A restore operation first runs liveness and a canary; it never blindly reinstalls or re-enables.

**External signal that verifies it:** in a fresh context, query ToolSearch using each retired old name. A deterministic checker must observe exactly one tombstone pointing to a live canonical replacement, then execute the replacement’s read-only canary. Separately verify the corresponding ledger receipt exists. These are mechanically independent signals.

**SOTA citation:** Microsoft Guideline 12 recommends remembering recent interactions, Guideline 18 recommends notifying users about capability changes, and Guideline 11 recommends making system behavior explainable: https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf .

**Confidence:** **very likely (80-90%)** that tombstones reduce “where did it go?” failures while preserving pruning’s context benefit, supported by the direct owner message and the established explainability/change-notification guidelines. **UNVERIFIED** whether the existing ToolSearch index accepts a non-invokable alias kind; the settling experiment is a one-item tombstone canary. If it does not, keep tombstones in the semantic router manifest and expose them only through its existing response.

**Value × effort:** high × low.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it for recording tombstones; confirm-first before permanently deleting capability files.

**Anti-overfit gate:** passes. It uses the existing index, event ledger, and OPEN-THREADS mechanisms; no new memory system.

## Finding 4 — Inferred surprise — UNVERIFIED: route capability chains, not isolated names

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** enrich the semantic index with a small `precedes/follows/fallback` adjacency list and retrieve one task chain when the prompt implies a multi-step workflow.

**What it is:** capabilities are often useful as sequences: ToolUniverse `find_tools → execute_tool`; paper search `search → OA access/PDF → read`; Android RE `JADX/APKTool → static native RE → Frida/Cheat Engine`; browser diagnosis `navigate → console/network → trace`; chemistry `RDKit triage → Schrödinger/QDX escalation`. Showing isolated names forces the agent to rediscover the chain and makes low-frequency downstream tools look unused.

**Why-inferred:** the catalogue already encodes chains in prose—for example ToolUniverse says `find_tools then execute_tool` and QDX describes submit/status/collect (`capability-catalog/catalog.json:19-24`)—but the router indexes capabilities independently (`semantic-router/build_index.py:196-225`) and emits flat buckets (`semantic-router/route.py:334-345`). The corpus independently shows both ToolUniverse stages used heavily: 349 `find_tools` and 1,416 `execute_tool` calls (`corpus.json:13466-13480`).

**How-to-build:**

1. Add a hand-curated JSON adjacency file for only high-value proven chains; do not infer a graph automatically.
2. When the primary retrieved capability has a chain and the prompt has multi-step intent, emit one compact chain, maximum three stages. For a single-tool prompt, emit only the primary.
3. Health-gate every stage with the existing B1 MCP-liveness status. A dead stage resolves to its canonical fallback.
4. Credit each executed stage from PostToolUse and task completion from an external test. Never let the router self-certify that the chain helped.
5. Keep chains out of SessionStart context; they load only after a match.

**External signal that verifies it:** replay held-out multi-step prompts in fresh contexts against flat retrieval versus chain retrieval. Verify tool sequence from transcript events, real execution results, and end-task fixtures. A separate evaluator grades whether the required stages occurred in a valid order.

**SOTA citation:** ToolReAGt decomposes complex tasks and associates tools iteratively, reporting higher retrieval accuracy than a conventional one-shot RAG baseline: https://aclanthology.org/2025.knowllm-1.7/ . Re-Invoke reports that intent- and multi-view-based retrieval improves single- and multi-tool retrieval: https://aclanthology.org/2024.findings-emnlp.270/ .

**Confidence:** **likely (55-80%)** that explicit chains improve this owner’s repeated research/RE workflows, supported by local paired-stage usage and the cited retrieval results. **UNVERIFIED chain set and benefit:** the experiment is a 50-prompt fresh-context A/B replay covering the five candidate chains above; only chains with higher fixture completion and no material token/latency regression are retained.

**Value × effort:** high × medium.  
**Novelty:** inferred-surprise.  
**Autonomy:** just-do-it in shadow evaluation; confirm-first before live routing changes.

**Anti-overfit gate:** passes narrowly because the “graph” is a small JSON adjacency list consumed by the existing router, explicitly not a knowledge graph or orchestration runtime.

## Finding 5 — Canonicalize duplicates and quarantine dead routes before trying to surface anything more

**Improvement — CONFIG (settings/JSON only):** expose one canonical capability per function; hide duplicate aliases and health-failed endpoints from retrieval; retain fallbacks and tombstones.

**What it is:** a per-family canonical map. Duplicate MCP bridges and names remain available as fallbacks only when the canonical endpoint is unavailable. Skills with namespaced/bare duplicates resolve to one canonical skill. A failed liveness state removes a route from candidate generation until a canary passes.

**Why-inferred:** duplicates are not theoretical here. The corpus records `ida-pro-mcp` and `plugin_local-mcp-bridge_ida-pro-mcp`, `ghidra-mcp` and its plugin bridge, `frida-mcp` and its plugin bridge, multiple Exa/Tavily surfaces, and both namespaced and bare skill variants (`corpus.json:13276-13344`, `:13374-13423`). The corpus also records “Unknown skill” for `verification-before-completion`, `gcloud-auth-verification`, and `simplest-probe-first` while capability-use records those same names elsewhere (`corpus.json:9678-9688`, `:13296-13315`), showing that historical invocation is not proof of current routability.

**How-to-build:**

1. Add `canonical` and ordered `fallbacks` to the existing capability manifest.
2. Suggested initial canonical families, subject to canaries: working local Tavily over `claude_ai_Tavily`; working plugin-local Ghidra/IDA/Frida endpoints over duplicate bare endpoints when their loaded database/session is the same; one bare skill name over plugin/bare duplicates unless the bodies differ materially.
3. Feed B1 MCP-liveness state into router filtering. A route with `not_connected`, schema mismatch, or failed canary becomes QUARANTINE, not a suggestion.
4. Run an equivalence probe before alias merge: compare tool schema hash, backend identity, and a read-only result. If any differ, keep separate names with discriminative descriptions.
5. For every pruned alias, create Finding 3’s tombstone.

**External signal that verifies it:** two independent checks per alias: schema/backend equivalence plus the same read-only canary result. For dead-route quarantine: liveness status plus a real tool invocation. A later recovery requires both signals to turn green.

**SOTA citation:** Anthropic identifies similar tool names as a common source of wrong selection and incorrect parameters and recommends on-demand discovery: https://www.anthropic.com/engineering/advanced-tool-use . ToolScope reports that redundant overlapping tools introduce ambiguity and that merging plus context-aware filtering improves selection accuracy; this is a 2025 preprint/forthcoming work, so it is supporting rather than decisive evidence: https://arxiv.org/abs/2510.20036 .

**Confidence:** **almost certain (90-99%)** that `claude_ai_Tavily` should be removed from the active candidate set now, supported independently by high per-tool error rates and the not-connected fingerprint, while other working Tavily endpoints exist. It is **likely (55-80%)** that the other named duplicate families can be collapsed; **UNVERIFIED equivalence premise:** schema-hash/backend-ID/canary comparison settles each family separately, so there is no wholesale merge.

**Value × effort:** high × low.  
**Novelty:** user-asked.  
**Autonomy:** just-do-it for quarantine of an endpoint that fails current liveness plus canary; confirm-first for deleting files or credentials.

**Anti-overfit gate:** passes. Pure manifest/settings work, building on the existing B1 liveness healer and router.

## Finding 7 — Trust-calibrated autonomy must be attached to the capability, not guessed per turn

**Improvement — CONFIG (settings/JSON only):** add `risk`, `side_effect`, `requires_confirmation`, `data_boundary`, and `canary` metadata to each capability; use it both for routing and action authority.

**What it is:** discoverability and autonomy become separate decisions. A read-only symbol lookup, documentation query, or local OCR can be just-do-it. Installing software, sending messages, modifying cloud state, writing memory/process state, or destructive binary operations remain confirm-first unless already explicitly authorized. A high retrieval score never grants authority.

**Why-inferred:** surfacing more tools without action calibration is **likely (55-80%)** to increase interruptions or unsafe action, supported by Microsoft’s context-sensitive intervention guidance and NIST’s task-risk guidance cited below. The owner explicitly requires low prompt fatigue and autonomy, which implies asking only when authority or consequential ambiguity truly requires it. AskUserQuestion is already available and used 1,329 times with 2.93% error (`corpus.json:135-140`); the proposed policy reserves it for material choices, not every tool route.

**How-to-build:**

1. Add static metadata to the same capability manifest; defaults are conservative for external writes and permissive for local read-only operations.
2. Router output carries an internal `autonomy` value but does not show it unless a confirmation is needed.
3. Use existing AskUserQuestion for a maximum of one bundled decision when multiple consequential operations share the same boundary.
4. Record the real action result and owner correction/dismissal via the existing observer/reaction ledger.
5. Global controls allow the owner to override categories, satisfying preference stability without repeated prompts.

**External signal that verifies it:** a policy fixture suite calls representative read-only and side-effecting tools and checks actual permission/confirmation events. Owner corrections over subsequent sessions are the personalization signal. A separate test context evaluates false asks and missed asks.

**SOTA citation:** Microsoft recommends timing interventions to context, graceful disambiguation when uncertain, learning from behavior, updating cautiously, and providing global controls: https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf . **Confidence:** **very likely (80-90%)** that per-capability authority metadata reduces unnecessary questions without broadening permission, supported by existing native confirmation machinery and the cited context/risk guidance. **UNVERIFIED policy thresholds:** a 100-case permission fixture and two-week false-ask/missed-ask review settle category boundaries.

## Finding 8 — The release gate is a fresh-context capability benchmark, not the router’s own confidence

**Improvement — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** extend the existing harness-bench with a capability-discovery suite built from real prompts, known-present controls, distractors, and executable fixtures.

**What it is:** a standing offline gate for changes to the catalogue, router, aliases, thresholds, and lifecycle states. It measures Recall@k, wrong-route rate, dead-route rate, execution success, task completion, tokens, latency, and owner-interruption count. It includes no-tool prompts so “always suggest something” cannot win.

**Why-inferred:** the law for this unit rejects same-context self-correction. The local corpus demonstrates why: the correction detector itself carries a precision warning (`corpus.json:10371-10374`), the hook detector is broken (`corpus.json:13260-13263`), and the router success ledger’s suggestion/adoption numbers are ambiguous (`semantic-router/success.json:1`). ToolRet likewise reports that conventional retrieval strength does not guarantee tool-retrieval quality.

**How-to-build:**

1. Sample 200 owner prompts across code, RE, Android, research, chemistry, browser/UI, documents/OCR, security, cloud, and no-tool tasks. Remove agent-authored prompts using provenance, not text heuristics.
2. For each fixture, specify acceptable capability set, forbidden/dead aliases, whether a tool is needed, autonomy class, and an executable success oracle.
3. Run each variant in a fresh context. The router-under-test only returns candidates; a second context or deterministic fixture evaluates retrieval and execution.
4. Include known-positive controls (`deep-research`, ToolUniverse, basic-memory) and known-negative/dead controls (`claude_ai_Tavily`). A detector failing either control invalidates the run.
5. Gate live changes on no regression in task completion, dead-route rate, and owner interruptions; token/latency improvements cannot compensate for thread loss or lower completion.
6. Publish per-capability results into the lifecycle manifest. The benchmark never automatically deletes; it recommends a state change backed by receipts.

**External signal that verifies it:** fresh-context execution output, deterministic fixtures, and a separate evaluator. Owner reaction is used only for live fatigue calibration, not offline correctness. This is mechanically independent from the router context.

**SOTA citation:** ToolRet provides a heterogeneous 7.6k-task/43k-tool retrieval benchmark and reports that retrieval quality affects downstream task pass rate: https://aclanthology.org/2025.findings-acl.1258/ . Re-Invoke evaluates single- and multi-tool retrieval with nDCG and reports gains from query/intent rewriting: https://aclanthology.org/2024.findings-emnlp.270/ . NIST calls for representative realistic test sets and external validity: https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/ .

**Confidence:** **almost certain (90-99%)** that this gate is necessary before pruning or broad surfacing, supported by three independent local detector/ledger weaknesses and primary external retrieval research. It is **likely (55-80%)** that 200 prompts cover the owner’s major workload families; **UNVERIFIED coverage premise:** compare fixture topic distribution with corpus session/project distributions and add strata until every material family has known-positive and no-tool controls.

**Value × effort:** transformative × medium.  
**Novelty:** user-asked.  
**Autonomy:** just-do-it for offline construction and shadow runs; confirm-first for applying retirements.

**Anti-overfit gate:** passes. It extends the existing local `harness-bench`; it does not add a runtime, model critic, or SaaS.
