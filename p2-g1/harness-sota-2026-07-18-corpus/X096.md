# X096 — metrology → use-vs-mention

## Executive result [UNVERIFIED — settle the recommendation with the specified shadow replay and temporal canary]

The borrow transfers, but only in a constrained form. The useful metrology mechanism is **measurand specification → measurement model → calibration against reference materials → uncertainty-aware conformity decision rule**. Metrology does not treat an instrument indication as the property of interest. It first specifies the quantity intended to be measured, models how observable inputs produce an estimate of it, calibrates the measurement result to a stated reference, carries uncertainty, and only then makes a conformity decision. VIM defines a measurand as the “quantity intended to be measured” and explicitly warns that the quantity actually measured can differ from the intended quantity; correction belongs in the measurement model ([JCGM VIM 2.3](https://jcgm.bipm.org/vim/en/2.3.html)). JCGM GUM-6 makes “select and specify the measurand” the first model-building step, followed by modelling the measurement principle, identifying effects, extending the model, and assessing adequacy ([JCGM GUM-6:2020, §§5.1–5.8](https://www.bipm.org/documents/20126/50065290/JCGM_GUM_6_2020.pdf/d4e77d99-3870-0908-ff37-c1b6a230a337)).

Translated to the target problem: a literal payload match is only an **indication**. The intended qualitative measurand is something like “this occurrence plays an operative role that this particular guard is responsible for.” The current anti-pattern is equivalent to declaring a battery’s loaded terminal reading to be its open-circuit voltage without specifying or correcting for the measuring interaction. A document saying `never run rm -rf` and an execution-bound shell argument containing `rm -rf` share an indication but differ on the intended property: semantic role.

My recommendation is therefore a narrow replacement, not another orchestration layer: retain regexes as high-recall sensors, but replace their authority to fire with a role-aware measurement contract and a three-outcome decision rule (`FIRE`, `CLEAR`, `INDETERMINATE`). Calibrate each detector on separately held role-labelled reference cases, report stratum-specific false-fire/miss uncertainty, and use a detector-specific guard band around the fire threshold. This is **very likely (80-90%)** to eliminate the supplied class of mention-only false fires, because semantic role becomes a required input instead of an unobserved confounder; the evidence is the direct structural correspondence between VIM’s indication/measurand distinction and the supplied use/mention distinction, plus GUM-6’s requirement to model all effects known to affect the result. The exact reduction is **UNVERIFIED — settle it with the shadow-replay experiment specified in “Acceptance experiment,” using all 12+ supplied false-fire cases plus temporally held-out traffic**.

This result does **not** justify calling the resulting classifier “metrologically traceable” in the SI sense. There is no universal physical reference standard for “operative semantic role,” annotator judgements can change with policy, and the object can be adversarial. The honest borrow is the quality architecture and decision discipline, not metrology’s institutional authority.

## The specific mechanism in its own field

### 1. Specify the measurand; do not confuse it with an indication

VIM 2.3 defines the measurand as the quantity intended to be measured. Its notes require specification of the kind of quantity and the relevant state of the phenomenon or object. It further says that the measuring system and conditions can make the quantity actually measured differ from the defined measurand, in which case correction is necessary. The accompanying annotation states the key lesson plainly: distinguishing the actually measured quantity from the intended one allows corrections in the measurement model ([JCGM VIM 2.3](https://jcgm.bipm.org/vim/en/2.3.html)).

ILAC separately defines an **indication** as the quantity supplied by a measuring instrument or system ([ILAC-G8:09/2019, §1.10](https://ilac.org/?ddownload=122722)). An indication is evidence; it is not automatically the result for the intended measurand. VIM likewise defines a measurement result as values attributed to a measurand together with relevant information, generally including measurement uncertainty ([JCGM VIM 2.9](https://jcgm.bipm.org/vim/en/2.9.html)).

In a temperature calibration, for example, the displayed digits are the indication. The intended measurand must say what temperature, of what body, under what conditions. Loading, drift, environment, resolution, and calibration corrections separate the indication from a defensible result. Metrology has solved the general category error: **a sensor response is not self-interpreting**.

### 2. Make the relation explicit in a measurement model

GUM-6 describes a measurement model as a mathematical expression or algorithm relating all known input quantities to the output measurand and its associated uncertainty. Its prescribed development sequence is: specify the measurand; model the measurement principle; identify effects; add terms for those effects; assess model adequacy. It warns that omitting a known effect can yield unrealistically small uncertainty or even the wrong measured value, and it requires a stated domain of validity ([JCGM GUM-6:2020, §§5.1–5.9](https://www.bipm.org/documents/20126/50065290/JCGM_GUM_6_2020.pdf/d4e77d99-3870-0908-ff37-c1b6a230a337)).

This is more than “benchmark the regex.” Calibration cannot recover a property that the measurement model never observes. If the instrument sees only character bytes, while the measurand depends on event field, provenance, quote boundary, actor and execution binding, semantic role is a missing influence quantity. Re-tuning a keyword threshold may improve one sample while leaving the model structurally incapable of distinguishing identical text in different roles.

### 3. Relate results to declared references, with uncertainty

VIM/NIST define metrological traceability as a property of a **measurement result**, related to a reference through a documented unbroken calibration chain in which every link contributes uncertainty. NIST stresses that merely owning a calibrated instrument is insufficient; the measurement system, result, reference, uncertainty, and quality control must all be documented ([NIST, “Metrological Traceability: Frequently Asked Questions and NIST Policy”](https://www.nist.gov/metrology/metrological-traceability)).

Reference materials are relevant because the target property is qualitative. NIST defines a reference material as sufficiently homogeneous and stable for specified properties and fit for an intended measurement use. It explicitly allows qualitative properties. A certified reference material supplies the specified property value, uncertainty and traceability; for qualitative attributes, uncertainty may be expressed as probabilities. NIST also states that one reference material cannot be used for both calibration and validation in the same procedure ([NIST, “SRM Definitions”](https://www.nist.gov/srm/srm-definitions)). This prevents the circular practice of tuning and “proving” a detector on the same examples.

### 4. Separate the measured result from the conformity decision

ILAC defines a decision rule as the rule describing how uncertainty is accounted for when declaring conformity. A guard band is the interval between a tolerance limit and a stricter acceptance limit. Guard bands reduce incorrect conformity decisions by moving the acceptance boundary inward to account for uncertainty ([ILAC-G8:09/2019, §§1.7–1.8 and 4.1](https://ilac.org/?ddownload=122722)). ILAC also supports non-binary outcomes—pass, conditional pass, conditional fail, fail—rather than forcing every uncertain result into a binary answer ([ILAC-G8:09/2019, §4.2.3](https://ilac.org/?ddownload=122722)).

The decision rule is selected according to the cost and allocation of false acceptance and false rejection; no single rule fits every calibration or test context ([ILAC-G8:09/2019, preamble and §§3–5](https://ilac.org/?ddownload=122722)). JCGM 106 formalizes the four binary outcomes and names false acceptance/false positive risk ([JCGM 106:2012, §9.3.2](https://www.bipm.org/documents/20126/50065304/JCGM_106_2012_E.pdf/fe9537d2-e7d7-e146-5abb-2649c3450b25)). Thus metrology separates three things that payload guards often collapse: sensor indication, estimated property with uncertainty, and policy decision.

## Structural mapping

| Metrology element | Harness translation | Concrete failure prevented |
|---|---|---|
| Measurand | Per-guard definition of the semantic property that warrants intervention | A generic word such as “delete” cannot silently stand in for an operative deletion request |
| Indication | Literal match, token pattern, parser flag, or classifier score | A match is evidence, not permission to fire |
| Measurement system/model | Function over text plus event kind, structured field path, actor, provenance/trust, syntactic enclosure, and downstream action binding | Same bytes in documentation and executor arguments no longer have identical meaning |
| Influence quantities | Quotation/code fence, negation, example/test-fixture status, quoted tool output, generated-vs-user text, transformation stage, and policy scope | Known mention contexts are represented rather than left as unexplained “noise” |
| Qualitative reference material | Adjudicated role-labelled cases with stated intended use and ambiguity | Calibration uses stable examples of `USE`, `MENTION`, and `AMBIGUOUS` |
| Calibration/validation split | Tune on one set; evaluate on a disjoint, temporally later set | Prevents self-validation on the 12+ known incidents |
| Measurement uncertainty | Confidence interval/posterior over error rate per role stratum, plus case-level ambiguity | A 0/5 error count is not reported as “zero risk” |
| Decision rule and guard band | Detector-specific thresholds and `INDETERMINATE` zone based on false-fire/miss cost | Borderline examples do not become unconditional blocks |
| Traceability record | For every fire: detector/version, measurand contract, raw indications, role inputs, reference-set version, decision rule, result | A later audit can reproduce why the decision was made |
| Domain of validity | Explicit event types/fields/languages tested | A shell-command guard cannot silently claim validity on prose, JSON patches, or a new tool schema |

The mapping is **very likely (80-90%)** structurally sound for the narrow failure class, because both domains contain an observable signal whose interpretation depends on conditions and an intended property different from the raw indication. Evidence: VIM expressly distinguishes actual from intended quantity, while the supplied target distinguishes identical payload text by semantic role. The mapping is only **likely (55-80%)** to generalize across every one of the five detectors, because detector purposes may differ: a prompt-injection detector may correctly care about an instruction merely embedded in untrusted content, whereas a destructive-action detector may care only when an action is execution-bound. The evidence is the detector-dependent allocation of false-positive/false-negative cost required by ILAC; **UNVERIFIED — settle per detector by writing its measurand contract and adjudicating the same contrast set under that contract**.

## Proposed replacement design [UNVERIFIED — settle with shadow replay]

### Proposal A — replace “match means fire” with a measurand contract [UNVERIFIED — settle with five contract adjudications before code changes]

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Each detector gets a small declarative contract:

```yaml
detector: destructive_action
measurand: operative_destructive_action
unit_of_assessment: one structured event field
positive_roles:
  - tool_argument_bound_for_execution
  - user_request_authorizing_action
negative_roles:
  - quoted_documentation
  - detector_rule_definition
  - historical_tool_output
  - test_fixture_expected_text
ambiguous_roles:
  - assistant_plan_without_action_binding
  - untrusted_content_that_may_be_prompt_injection
required_inputs:
  - event_kind
  - field_path
  - actor
  - provenance
  - syntactic_enclosure
  - downstream_sink
decision_cost:
  false_clear: critical
  false_fire: high
domain_of_validity:
  - declared event kinds and field paths only
```

The names are illustrative, not a universal ontology. Every detector must define its own measurand; “use” is not globally synonymous with “execute.” A secrets detector may define use as “secret value is about to cross a trust boundary.” A policy detector may define use as “an instruction from an authorized actor changes planned behavior.” A prompt-injection detector may define the relevant property as “untrusted content contains an attempted instruction,” in which case textual mention can itself be a legitimate positive and the use/mention suppression must not apply.

This configuration change alone does not enforce anything. It makes the intended property inspectable and prevents five unrelated detectors from inheriting one implicit definition. It is **likely (55-80%)** that writing these contracts will expose at least one detector for which the metrology analogy must be applied differently; evidence is ILAC’s explicit warning that no single decision rule fits all testing/calibration contexts. **UNVERIFIED — settle by an owner review of the five completed contracts before code changes**.

### Proposal B — a role adapter on the existing hook bus [UNVERIFIED — settle with per-stratum shadow-replay confusion matrices]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Add one pure adapter before the five detector decisions. It receives the already-structured event and emits a compact `role_context`; it does not run another agent, daemon, queue, database, or orchestration loop.

Minimum inputs:

1. Event and field identity: user message, assistant output, tool call argument, tool result, file contents, hook metadata.
2. Actor and provenance: owner/user, assistant, tool, untrusted external content, generated fixture.
3. Syntactic enclosure: plain text, quoted text, fenced code, JSON string, diff deletion/addition, comment, test expectation.
4. Action binding: whether this exact field is destined for an executor or state-changing API, merely rendered, or only stored.
5. Detector scope: the measurand contract from Proposal A.

The adapter must prefer authoritative transport metadata over NLP guesses. For example, a shell tool’s `command` field has execution binding even if the string says it is “just an example”; a Markdown file body has documentation provenance even if it uses imperative grammar. Text heuristics handle only the residual cases and should lower confidence rather than override authoritative routing metadata.

The raw matcher still runs, but its output becomes one input to a measurement function:

```text
role_context = classify_role(event_metadata, field_path, enclosure, sink)
indication    = existing_matcher(payload)
estimate      = detector_model(indication, role_context, detector_contract)
decision      = apply_rule(estimate, calibration_uncertainty, cost_policy)
```

The adapter is **very likely (80-90%)** to distinguish literal text in a documented/file-content route from the same text in an execution-bound tool argument when those routes expose structured metadata; evidence is that field path and sink are direct, non-lexical signals of role. It is only **roughly even (45-55%)** to classify arbitrary prose correctly when metadata is absent and use must be inferred from language; evidence is that the proposed small adapter has no universal semantic reference and deliberately avoids a second model runtime. Both claims are **UNVERIFIED — settle with per-stratum confusion matrices in shadow replay**.

### Proposal C — qualitative reference set, uncertainty, and control cases [UNVERIFIED — settle on disjoint and temporal validation sets]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Create a versioned fixture set, not a service. Each case records:

- exact structured event envelope, not payload text alone;
- detector and measurand-contract version;
- adjudicated `USE`, `MENTION`, or `AMBIGUOUS` property;
- intended-use/domain tags;
- rationale and provenance;
- independent second adjudication for ambiguous/high-cost cases;
- whether the case is calibration, validation, or permanent control.

Seed it with every known false fire, then create **paired contrasts** that hold bytes constant and change only role: documentation body versus executor argument; quoted tool result versus new tool call; diff deletion versus diff addition; policy definition versus request to violate the policy; negative test expectation versus live payload. Include positive controls that the detector must find, negative mention controls that it must ignore, and adversarial controls with code fences, escaping, nested quotations, multilingual prose, split strings, and structured API calls without the historical keyword.

Do not use the same cases to tune and validate. NIST’s reference-material guidance explicitly disallows using one material for both calibration and validation in the same measurement procedure ([NIST, “SRM Definitions”](https://www.nist.gov/srm/srm-definitions)). Report per-stratum counts and interval estimates for false-fire and miss rates; do not collapse rare high-cost strata into one global accuracy number. “No observed errors” must retain non-zero uncertainty unless the sample supports a tighter bound.

This fixture approach is **very likely (80-90%)** to prevent regression on the already-known false-fire forms if they become permanent controls; evidence is deterministic replay of exact event envelopes. It is **likely (55-80%)** to improve novel-case performance only when the contrast set spans the relevant role factors; evidence is GUM-6’s domain-of-validity requirement and warning that omitted effects yield wrong results. **UNVERIFIED — settle novel-case performance on a temporally held-out set collected after all tuning is frozen**.

### Proposal D — uncertainty-aware, three-outcome decision rules [UNVERIFIED — settle with shadow indeterminate counts and canary confirmation burden]

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Each detector declares a decision rule before evaluation. A high-cost destructive action might require a conservative fire rule; a low-cost advisory detector can tolerate a wider `INDETERMINATE` band. One concrete form is:

```text
FIRE          if lower_confidence_bound(P(relevant-use)) >= fire_limit
CLEAR         if upper_confidence_bound(P(relevant-use)) <= clear_limit
INDETERMINATE otherwise
```

`INDETERMINATE` must have a bounded existing-bus behavior: request confirmation before a destructive sink, emit a non-blocking advisory for low-risk cases, or record the case for adjudication. It must not silently become either `FIRE` or `CLEAR`. The decision record includes the rule and which result it applies to, mirroring ILAC’s reporting requirement that a conformity statement identify the result, specification and decision rule ([ILAC-G8:09/2019, §§2.6–2.7](https://ilac.org/?ddownload=122722)).

A three-outcome rule is **likely (55-80%)** to reduce costly false fires without increasing silent misses when ambiguous cases are routed to confirmation at state-changing sinks; evidence is ILAC’s non-binary guard-band pattern and the fact that confirmation supplies an additional authoritative signal. It is **unlikely (20-45%)** to be acceptable on every event because confirmation can interrupt automation and no user may be present; evidence is the operational difference between interactive and unattended execution. Both are **UNVERIFIED — settle with shadow-mode counts of indeterminate frequency and a canary rollout measuring confirmation burden and escaped hazards**.

### Proposal E — traceability-style decision records and drift checks [UNVERIFIED — settle with independent record replay and injected drift]

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

For each actual intervention, append a compact record to the existing local hook log: detector/version, measurand-contract version, event/field role, indications, estimate/uncertainty, decision rule/version, result, and reference-set version. Periodically replay stable positive and negative controls before/after rule changes. NIST says traceability belongs to results, not instruments, and calls for a defined property, measurement-system description, stated result with uncertainty, specified reference, and measurement assurance program ([NIST traceability policy, §§5.1.1 and 5.1.7](https://www.nist.gov/metrology/metrological-traceability)).

This record is “traceability-style,” not a claim of formal metrological traceability. It is **very likely (80-90%)** to make a reported fire reproducible when all listed versions and structured inputs are retained; evidence is that those fields determine the proposed pure decision path. It is only **likely (55-80%)** to diagnose semantic drift, because replay detects drift on stable controls but cannot prove coverage of new roles; evidence is the fixed reference set’s limited domain. **UNVERIFIED — settle reproducibility by independently replaying sampled records and requiring exact decision agreement; settle drift sensitivity with injected mutations to role metadata and matcher versions**.

## What this would catch that payload matching misses

The design targets both false interventions and blind spots. The following are predicted capabilities, not observed current failures beyond the supplied false-fire class.

1. **Same bytes, different route.** It would distinguish a dangerous command in a shell executor argument from the identical command in documentation or historical tool output. This is **very likely (80-90%)** where the event schema preserves field and sink, because action binding is an independent signal from text. **UNVERIFIED — settle with byte-identical paired fixtures across routes**.
2. **Diff semantics.** It could distinguish removal of a prohibited line from addition of the same line when patch metadata is available. This is **likely (55-80%)**, because hunk direction is structured role evidence but surrounding patch transformations may obscure it. **UNVERIFIED — settle with added/deleted/context-line fixtures across supported patch formats**.
3. **Definitions and test expectations.** It could suppress matches inside detector definitions, rules, quoted error fingerprints, and negative tests while retaining matches in the executed subject. This is **likely (55-80%)**, because provenance and field path are usually stronger than lexical framing. **UNVERIFIED — settle with fixtures that carry explicit provenance through the actual hook envelope**.
4. **Keyword-free operative actions.** An action-bound structured API call such as `{operation: "delete", target: ...}` can be relevant even when it lacks a shell keyword expected by the old regex. This is **likely (55-80%)** for tool schemas enumerated in the contract and **very unlikely (5-20%)** for unseen schemas, because schema-aware sink metadata supplies the former signal but no universal semantic parser supplies the latter. **UNVERIFIED — settle with known-schema and unseen-schema positive controls**.
5. **Prompt injection as a detector-specific exception.** It would avoid globally suppressing “mere document text” when a prompt-injection detector’s measurand is the presence of an attempted instruction in untrusted content. This is **very likely (80-90%)** once the detector contract declares provenance-sensitive attempted instruction as positive; evidence is that per-detector measurands prevent a destructive-action rule from being reused as an injection rule. **UNVERIFIED — settle with paired benign quotation and adversarial instruction cases adjudicated under the injection contract**.
6. **Unknown role instead of false certainty.** New event types and unmodelled fields would become `INDETERMINATE` outside the declared domain rather than inheriting a global payload rule. This is **very likely (80-90%)** if the adapter defaults unknown fields to indeterminate; evidence is deterministic configuration behavior. **UNVERIFIED — settle with synthetic unknown event/field controls**.

## Adversarial examination of the analogy

### Where the structure transfers

The analogy transfers at four precise joints:

1. **Observable versus intended property.** A textual occurrence is an indication; operative semantic role is the intended qualitative property. VIM explicitly exists to prevent confusing the actually measured quantity with the intended measurand ([VIM 2.3](https://jcgm.bipm.org/vim/en/2.3.html)).
2. **Context as a model input.** Both problems require conditions and influence quantities. GUM-6 requires known effects and domain restrictions in the model ([GUM-6 §§5.6–5.9](https://www.bipm.org/documents/20126/50065290/JCGM_GUM_6_2020.pdf/d4e77d99-3870-0908-ff37-c1b6a230a337)).
3. **Reference cases and independent validation.** Qualitative reference values are legitimate in NIST’s reference-material framework, and probabilities can express their uncertainty ([NIST SRM definitions](https://www.nist.gov/srm/srm-definitions)).
4. **Decision risk.** A noisy estimate and a policy action are different objects. ILAC guard bands and non-binary outcomes explicitly allocate false acceptance/rejection risk ([ILAC-G8](https://ilac.org/?ddownload=122722)).

These are structural, not metaphorical similarities. They directly prescribe missing interfaces: measurand contract, role inputs, reference cases, uncertainty, and decision rule.

### Where it fails or must be weakened

1. **No natural invariant or SI chain.** Semantic role is policy-relative and conversational. There is no kilogram-like realization of “use.” The reference is an adjudicated operational definition, not nature. Therefore “traceable” must mean reproducible to a versioned adjudication set, not formal SI traceability.
2. **The object is adversarial and reflexive.** Text can discuss the detector, quote its trigger, or deliberately manipulate the classifier. Ordinary calibration artefacts do not usually read the calibration procedure and adapt. Static reference cases will age.
3. **Non-stationarity is semantic, not just instrumental drift.** New tools, schemas, quoting conventions, and policies can redefine the measurand’s realization. A control chart over yesterday’s cases cannot establish validity on tomorrow’s event type.
4. **Ground truth can be genuinely ambiguous.** Two competent reviewers may disagree whether an assistant plan is operative “use.” That disagreement is information about measurand definition, not merely annotator noise. The correct output can be `INDETERMINATE` or a revised contract.
5. **A guard band cannot repair a deficient sensor.** If only raw payload text is available, moving thresholds trades errors but does not identify role. The role adapter is a prerequisite. This is why a “calibrated regex” alone is rejected.
6. **Suppression can create security blind spots.** Treating all quoted/document content as mention is unsafe for prompt injection, malicious patches, or executable examples later copied into a sink. The detector-specific measurand and downstream binding are essential.

Because of these disanalogies, I reject a grand “semantic metrology platform,” formal certification language, or a universal use/mention score. The analogy earns a small decision architecture, not a new institution.

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected. The required evidence set is small, versioned, executable, and best represented as fixtures. This would reintroduce explicitly rejected vector-DB/KG memory with no demonstrated need.

**NATIVE-vs-BUILD: BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** Rejected as category inflation. The target has no SI reference, stable universal measurand, or accredited calibration hierarchy. Borrow the mechanisms; do not borrow unwarranted authority.

## Anti-overfit gate

All recommended components ride the existing configuration/hook/log/test buses. They add no daemon, second orchestration runtime, vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The only executable addition is a pure role adapter plus fixture/replay support, each constrained to **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. The existing literal detectors remain useful sensors; their direct authority to make the final decision is what gets replaced.

This is the smallest architecture that can address the structural defect. Configuration-only threshold changes cannot observe role; a model service is unnecessary before structured transport metadata and paired controls have been exploited.

## Acceptance experiment

This experiment settles every material UNVERIFIED recommendation above.

### Phase 0 — preregister

Before implementation, write each detector’s measurand, unit of assessment, positive/negative/ambiguous roles, domain, false-fire cost, miss cost, and decision rule. Freeze these contracts for the experiment. Independently adjudicate disagreements rather than resolving them by looking at detector output.

### Phase 1 — reference-set construction

1. Put all supplied false-fire incidents into a **calibration candidate** pool with their full event envelopes.
2. Construct at least one byte-identical role contrast for every incident.
3. Add independently sourced positive uses, including keyword-free structured actions.
4. Reserve disjoint validation cases. Do not tune on them.
5. Add known-present positive controls and known-absent/mention controls for every detector and role stratum. The positive control proves the detector path can observe the target before any “no fires” result is interpreted.

### Phase 2 — shadow replay

Run old and proposed decisions side by side without changing live behavior. Report, per detector and role stratum:

- false fires, misses, correct fires, correct clears, indeterminates;
- exact denominators and interval estimates;
- decision latency;
- disagreement cases with both rationales;
- behavior on known-present controls and paired mention controls;
- performance separately on calibration and untouched validation sets.

Success criterion: all supplied mention-only false fires become `CLEAR` or justified `INDETERMINATE`; all paired operative positives remain `FIRE` or confirmation-bound `INDETERMINATE`; no control-path failure; and validation uncertainty is reported rather than rounded to zero. The numeric tolerance must be set by the owner from detector-specific costs before results are revealed; inventing one here would be false precision.

### Phase 3 — temporal holdout and canary

Freeze implementation and collect later cases from normal traffic. Adjudicate them without showing reviewers either detector’s answer. Then canary the proposed rule only on the lowest-risk detector, with automatic fallback to the existing behavior for adapter errors or unknown event schemas. Promotion requires two mechanically independent signals: (1) replay metrics on the untouched temporal set and (2) live canary decision records plus owner-confirmed outcome sampling. These are different data sources and measurement modes, not two reruns of one probe.

The proposal will meet the supplied goal in live operation with a material false-fire reduction and no material miss increase only **likely (55-80%)**. Evidence: the architecture directly observes structured role and sink signals that payload matching omits, but semantic ambiguity, detector heterogeneity and unseen schemas remain. **UNVERIFIED — the temporal holdout plus canary is the settling experiment**.
