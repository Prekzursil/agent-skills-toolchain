# P2B10 — Competitive teardown: Devin / Cognition

**Unit:** P2B10  
**Date researched:** 2026-07-18  
**Subject compared:** Cognition's cloud Devin, Devin CLI / Devin Local, and the adjacent Devin Review surface versus this owner's Claude Code + Codex shared harness.  
**Decision frame:** identify mechanisms worth porting, including replacement when justified; do not mistake vendor behavior documentation for proof of comparative effectiveness.

## Executive verdict

Devin's durable advantage is not a novel ReAct loop, a better `AGENTS.md`, or MCP support. Those are now commodity surfaces, and this harness already has unusually deep versions of rules, skills, hooks, provider-neutral lifecycle normalization, lexical memory recall, worktree isolation, multi-agent coordination, and verification workflows. The local evidence is concrete: the shared dispatcher normalizes both Claude and Codex lifecycle events and emits a closed result contract (`C:\Users\Prekzursil\.agents\harness\README.md:3-14`); its fixed module chain includes secret protection, event logging, goal re-injection, sanitized checkpoints, bounded recall, and subagent lifecycle checks (`README.md:17-29`); and the toolchain advertises 169+ skills and cross-provider configuration (`C:\Users\Prekzursil\source\agent-skills-toolchain\README.md:1-3`).

The parts Cognition genuinely productizes better are the *joins* between existing mechanisms:

1. a reproducible, prewarmed, disposable VM substrate for every cloud session;
2. a managed-session control plane with child-specific budgets, searchable event histories, steering, and a one-call completion barrier;
3. post-session synthesis that turns retries and user corrections into a better prompt plus environment, Knowledge, and workflow actions;
4. reviewed Knowledge and Skill suggestions, rather than a reminder that the agent ought to remember something;
5. end-to-end browser testing that returns a short recording as human-verifiable proof;
6. a cloud/local handoff and a productized PR review loop.

The highest-value response is **not** to copy Devin wholesale. It is to enable Claude Code's native sandbox immediately, then add small teardown, promotion, proof-bundle, and fleet-state adapters to the existing dispatcher/ledger/skill buses. This is **very likely (80-90%)** to capture most of the locally relevant value because every proposed slice consumes evidence or control points that already exist in this harness (`ledger.py:468-490,882-907`; `modules.py:1572-1681,2267-2317,2331-2420`), while avoiding a second orchestration runtime. The remaining uncertainty is outcome effect, not implementability; the controlled shadow experiments in §11 settle it.

Full Devin parity—hosted snapshot builders, browser/desktop VMs, cloud resumability, enterprise RBAC, billing, searchable session storage, and multi-tenant secret management—is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)** and fails this program's anti-overfit gate for a single-owner local harness. It would reintroduce both a second orchestration runtime and durable-execution infrastructure. Do not build it unless a later requirement explicitly changes the deployment target from “owner workstation” to “multi-user hosted agent platform.”

## 2. Agent loop

### 2.1 Published cloud loop

Cognition does not publish the cloud agent's system prompt, model policy, planner implementation, scratchpad representation, retry controller, compaction algorithm, or termination policy. Any claim that Devin internally uses a particular ReAct/tree-search/planner architecture is **UNVERIFIED; capturing a complete session event export plus model metadata and comparing tool/plan transitions settles it**.

The observable product loop is nevertheless concrete:

1. **Interpret and retrieve.** At session start, Devin searches an index of the main branch for relevant files and snippets.
2. **Initial assessment.** It surfaces relevant files, key findings, questions, and sometimes inspectable code citations.
3. **Detailed plan.** It proposes a code-grounded plan, often with citations/snippets.
4. **Optional human gate.** The default is a 30-second feedback window before execution; the user can require explicit plan approval.
5. **Execute.** It edits in a hosted IDE, uses shell, browser/desktop, git, and configured MCP tools, while exposing progress/worklog state.
6. **Verify.** It can run tests and, for UI work, enter a structured test mode that plans an end-to-end flow, operates the desktop, records it, and returns the recording.
7. **Deliver.** It creates a PR and can route it through Devin Review.
8. **Learn after the run.** Session Insights classifies the session and can produce an issue timeline, improved prompt, action items, and Knowledge-use assessment.

Steps 1-4 are directly documented in [Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning): the initial search uses a main-branch index and can miss recent or non-main changes; the assessment returns relevant files/findings/questions; the detailed plan includes inspectable citations; and approval can be made mandatory. Steps 5-6 are documented in [Devin Session Tools](https://docs.devin.ai/work-with-devin/devin-session-tools) and [Testing & Video Recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings). Step 8 is documented in [Session Insights](https://docs.devin.ai/product-guides/session-insights).

### 2.2 CLI loop

Devin CLI is a conventional local tool-calling coding loop with a stronger-than-average native control surface. It loads project context/rules, selects a configured model or Cognition's Adaptive router, explores with built-in and MCP tools, requests permissions according to mode/rules, edits and executes, can delegate to foreground/background subagents, compacts context, and exposes lifecycle hooks before/after these transitions. The hook events are `PreToolUse`, `PostToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `PostCompaction`, `SessionStart`, and `SessionEnd`; `PreToolUse` can block, add context, or rewrite tool input, and `PostToolUse` receives an explicit `success`, `output`, and `error` object ([lifecycle hooks](https://docs.devin.ai/cli/extensibility/hooks/lifecycle-hooks)).

### 2.3 Comparison

Interactive planning is not a capability gap. Claude Code already has plan mode and plan approval; this installation additionally runs a deterministic plan lint and three typed adversarial reviewers in parallel (`C:\Users\Prekzursil\.claude\workflows\plan-gate.mjs:24-30,40-100`). Devin is better at the *presentation contract*—relevant files, questions, citations, and an explicit assessment-to-plan-to-mutation transition—but worse in one important way: its fast initial assessment knowingly searches a possibly stale main-branch index ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning)). The local harness's direct `rg`/read path sees the checked-out worktree. Copy the inspectable phase boundary, not the stale index.

The local harness is also stronger in goal continuity. Its goal module rejects injected/system-like prompts as new goals, stores a redacted authoritative goal, reinjects every configured interval, and reanchors after compaction (`modules.py:1279-1369`). Cognition publishes no equivalent invariant for cloud Devin.

## 3. Context management

### 3.1 What Devin does

- **Repository index for fast initial scoping.** Fast, citation-bearing, but explicitly main-branch-biased and potentially stale ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning)).
- **Rules with scope and lazy discovery.** Root `AGENTS.md`/`CLAUDE.md`-style files load at start; rule files in subdirectories are discovered when the agent accesses that directory. Imported Cursor/Windsurf rules can be always-on, glob-triggered, agent-decided, or manual ([Rules & AGENTS.md](https://docs.devin.ai/cli/extensibility/rules)).
- **Skills loaded only when relevant.** Cognition explicitly recommends skills over long rules to reduce context and cost ([Rules & AGENTS.md](https://docs.devin.ai/cli/extensibility/rules)).
- **Compaction lifecycle.** Devin CLI exposes `PostCompaction` with the compactor's summary so hooks can log or re-inject lost context ([lifecycle hooks](https://docs.devin.ai/cli/extensibility/hooks/lifecycle-hooks)).
- **Subagent context isolation.** A child shares tools and codebase access but receives its own conversation chain and does not inherit parent history; the parent receives a summarized result rather than raw child output ([Subagents](https://docs.devin.ai/cli/subagents)).
- **Local-to-cloud handoff.** `/handoff` packages conversation context and the current git branch into a cloud session with its own VM, shell, browser, and repo access ([handoff](https://docs.devin.ai/cli/handoff)).

### 3.2 Comparison

Most of this is already native or stronger here. Claude Code supports path-scoped rules, on-demand skills, `PostCompact`, custom subagents with independent contexts, worktree-isolated subagents, background/foreground execution, native agent teams, and Remote Control. The live shared harness adds sanitized pre-compaction checkpoints (`README.md:28-29`), post-compaction goal reanchor, and bounded ledger replay (`ledger.py:882-907`).

The only context-management gap with practical value is the seamless local-to-hosted handoff. A true transfer of the live conversation, branch, uncommitted changes, secrets, tools, and execution state to a fresh hosted environment is **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**. Claude Code Remote Control is **not** equivalent: it keeps execution on the local machine, although it can expose the session from web/mobile ([Remote Control](https://code.claude.com/docs/en/remote-control)). Claude Code on the web supplies managed cloud environments, but the inspected docs do not establish a one-command local-to-cloud transfer of the current dirty state. Do not build a bespoke handoff service; this would be a second durable execution runtime.

## 4. Memory

### 4.1 Cloud Knowledge and Skills

Cloud Devin's Knowledge is trigger-based organizational memory. Every item has a trigger description; items can be enabled/disabled per user, invoked by a macro, organized into nested folders, pinned to one repo or all repos, and scoped to organization or enterprise. Devin retrieves relevant items during work rather than loading all of them at session start. Most importantly, it suggests new or updated Knowledge from chat feedback and requires the user to edit/save or dismiss the suggestion ([Knowledge](https://docs.devin.ai/product-guides/knowledge)). Session Insights separately flags useful and misleading Knowledge and recommends trigger/content changes ([Session Insights](https://docs.devin.ai/product-guides/session-insights)).

Cloud Skills are repository-local `SKILL.md` procedures. After testing an application or learning setup details, Devin can propose new/updated skill contents and offer a “Create PR” action ([Skills](https://docs.devin.ai/product-guides/skills)). Playbooks are manually attached reusable prompts with procedures, specifications, advice, macros, organization/enterprise sharing, and version history/revert ([Creating Playbooks](https://docs.devin.ai/product-guides/creating-playbooks)).

### 4.2 Devin CLI limitation

Cognition explicitly documents that Devin Local/CLI **does not persist memories between sessions** and tells users to migrate critical memories to skills; it also lacks cloud Workflows, Fast Context UI, browser previews, complete analytics, and conversation sharing ([CLI controls](https://docs.devin.ai/cli/enterprise/controls)). This is worse than this harness. Here, Basic Memory is cross-tool canonical semantic memory, the local index injects at most 3-5 high-precision notes while suppressing poisoned or already-injected entries (`modules.py:1572-1681`), and the event ledger gives objective continuity (`ledger.py:468-490,882-907`).

### 4.3 The real gap

The missing piece is not storage or retrieval. It is *reviewed promotion*. The current `basic_memory_nudge` only notices that a canonical file changed without a Basic Memory write and injects a reminder (`modules.py:2267-2317`). It does not draft a new/superseding note, identify the evidence that motivated it, show retrieval scope, or present save/edit/dismiss choices. The validated bounded search found no Knowledge-suggestion contract in the authoritative harness/config files; direct inspection of the nudge is the independent second signal.

**Capability delta — reviewed memory and skill suggestions (UNVERIFIED outcome effect):** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. Concrete port: at `Stop` or explicit `/teardown`, replay the last 120 ledger events; extract only owner corrections, repeated failures with a later success, and canonical configuration changes; draft one of `{basic-memory note, superseding note, SKILL.md change}` with `evidence_event_ids`, repo scope, trigger text, `valid_as_of`, and `superseded_by`; render save/edit/dismiss; call the existing Basic Memory tool or create a skill PR only after affirmative review. Never autonomously promote. The mechanism is directly implementable on present buses; whether it improves later task outcomes is **UNVERIFIED, and the accepted-versus-dismissed suggestion experiment in §11.2 settles it**.

A disabled server is skipped during discovery and not started. ### 5.2 Comparison

Base MCP protocol support is not a gap. This corpus records 93 MCP servers touched, and current Claude/Codex configurations already expose a large MCP surface. **Capability delta — cross-tool configuration import (UNVERIFIED effectiveness): BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Port only a read-only `config-doctor` adapter that enumerates known Claude/Codex/MCP sources, normalizes them to the existing toolchain manifest, detects duplicate/dead definitions, and emits a proposed patch. Do not auto-merge configurations or copy secrets. This is **likely (55-80%)** to reduce drift because this workstation has separate `.mcp.json`, `.claude.json`, Claude settings, Codex TOML, and a 40+ MCP-config toolchain (`agent-skills-toolchain\README.md:1-3`); effectiveness is **UNVERIFIED, and a before/after count of duplicate endpoints, dead-server calls, and configuration parse errors settles it**.

MCP security remains a shared weakness. Devin's namespace permissions and enterprise registry constrain which tool may run, but the documentation does not state that tool outputs are taint-labeled, scanned for indirect prompt injection, capability-attested, or prevented from influencing other tools. Treat every MCP result as untrusted evidence. Do not infer safety from marketplace presence.

## 6. Permission and isolation model

### 6.1 Devin CLI

Devin CLI has four modes: Normal, Accept Edits, Bypass, and Autonomous. Rules are evaluated `deny` then `ask` then `allow`, with prompt as the default. Matchers cover read/write globs, command prefixes, fetch URL patterns, built-in tools, and namespaced MCP tools. Approvals can be once, session-persistent, or project-persistent ([permissions](https://docs.devin.ai/cli/reference/permissions)).

With `--sandbox`, filesystem Read/Write scopes are enforced at OS level. Network traffic can be restricted by domain and HTTP method. Excluded commands have separate `allow`/`ask`/`deny` rules, use most-specific matching, combine enterprise and user settings toward the more restrictive result, and fail closed when parsing/resolution fails. If sandbox setup fails, Devin CLI refuses to start rather than silently running unsandboxed. However, Cognition states that Windows OS sandboxing is not currently supported and that network filtering is currently unstable ([sandbox](https://docs.devin.ai/cli/sandbox)).

### 6.2 Cloud Devin

Cloud Devin adds two-tier organization/account RBAC for sessions, Playbooks, Secrets, Knowledge, snapshots, repositories, MCP, metrics, billing, and review; IdP groups can map to roles ([RBAC](https://docs.devin.ai/enterprise/security-access/custom-roles)). Secrets have organization, personal, repo, and session scopes. Cognition warns that organization secrets are usable in every future organization session by all members, although only admins can view/edit them ([Secrets](https://docs.devin.ai/product-guides/secrets)). Blueprint build secrets are re-injected and scrubbed from the snapshot unless a setup command writes them to disk; Cognition explicitly warns that such files persist in the image ([Blueprint reference](https://docs.devin.ai/onboard-devin/environment/blueprint-reference)).

### 6.3 Comparison and immediate delta

This deployed harness has strong prompt-time guards but weak runtime confinement. Claude settings allow nearly every built-in tool and many whole MCP servers, use `defaultMode: "bypassPermissions"`, grant `additionalDirectories: ["C:", "D:"]`, and have an empty `ask` list (`C:\Users\Prekzursil\.claude\settings.json:26-75`). Codex is `danger-full-access` with no approval (`C:\Users\Prekzursil\.codex\config.toml:6-7`). The local worktree hook isolates git files but not processes, credentials, network, package caches, or the rest of the host (`C:\Users\Prekzursil\.claude\hooks\create-worktree.ps1:133-149`).

**Capability delta — OS-enforced filesystem/network isolation in the deployed configuration:** **NATIVE (Claude Code already does this; we just enable it)**. Current Claude Code supports OS-level filesystem and network sandboxing, domain allowlists, denied paths, excluded commands, `allowUnsandboxedCommands: false`, and `sandbox.failIfUnavailable: true` ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). On Windows it requires WSL2. That prerequisite is present here by two mechanically independent signals: `Get-Command wsl.exe` resolved `C:\WINDOWS\system32\wsl.exe`, and `wsl.exe --status` exited 0 reporting default distribution Ubuntu and default version 2 (commands run 2026-07-18). Enable it for mutation-capable and untrusted-content sessions, narrow additional directories, retain explicit deny rules for secrets, and fail closed when the sandbox is required. This is **very likely (80-90%)** to reduce blast radius because enforcement occurs below the model and all subprocesses; the evidence is Claude's documented OS boundary plus the live `bypassPermissions`/`danger-full-access` configuration. It will not fix semantic authorization errors inside allowed paths or allowed domains.

**Capability delta — enterprise RBAC/audit governance:** **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**. It is irrelevant to a single owner and would add identity, policy distribution, audit retention, and multi-tenant secret services. Reject it. Preserve the simple local policy model.

## 8. Multi-agent support

### 8.1 Devin CLI subagents

Devin CLI can automatically or explicitly spawn focused foreground/background children. Foreground children pause the parent and can request permission. Background children inherit already granted permissions, auto-deny anything else, and notify the parent on completion. The UI shows profile, title, state, elapsed time, and tool-call count; users can move a child between foreground/background, cancel it, or resume completed/failed/cancelled work in the foreground. Custom `AGENT.md` profiles set model, allowed tools, permissions, and optional maximum nesting. Nesting is disabled by default and bounded when explicitly enabled ([Subagents](https://docs.devin.ai/cli/subagents)).

This is mostly native in Claude Code now: independent subagent contexts, custom prompts/models/tool restrictions, foreground/background tasks, auto-denied background prompts, resumption, worktree isolation, `/agents` and `/tasks` panels, and agent teams are documented in [custom subagents](https://code.claude.com/docs/en/sub-agents), [parallel agents](https://code.claude.com/docs/en/agents), and [agent teams](https://code.claude.com/docs/en/agent-teams). The live config already enables experimental agent teams (`settings.json:4-8`) and Codex multi-agent with eight concurrent threads (`config.toml:101,125-130`). Local subagent lifecycle is stronger on structured handoff and stall detection (`modules.py:2331-2420`).

### 8.2 Cloud Managed Devins

Cloud Devin goes further operationally. A coordinator can split work into child sessions, each in its own isolated VM; assign prompt, Playbook, tags, and ACU limit; message children; monitor ACU usage; sleep or terminate them; schedule reminders; compile results; search complete session event timelines; and wait for all launched sessions in one call ([Advanced Capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)). March 2026 release notes add structured output schemas and full event search across shell, file, browser, git, and MCP activity ([release notes](https://docs.devin.ai/release-notes/overview)).

**Capability delta — full managed-session control plane with isolated VMs:** **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**. True parity requires compute provisioning, snapshot lifecycle, secrets, billing/budgets, durable event storage, APIs, scheduler, and failure recovery. Reject full parity under the anti-overfit gate.

**Capability delta — thin fleet convergence contract (UNVERIFIED benefit):** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. Add fields to existing child ledger events: `task_id`, `parent_id`, `scope`, `budget`, `output_contract`, `status`, `receipt_ids`, `last_progress_ts`. Provide one pure `settle(children)` helper that returns only when every child is terminal, plus explicit `cancel`, `steer`, and `resume` mappings to native Claude/Codex controls. Synthesis must reject non-terminal, hollow, or schema-invalid children. This is **likely (55-80%)** to reduce premature synthesis because the current module records child starts/stops and detects hollow/stalled results but has no per-child budget or all-terminal barrier (`modules.py:2331-2420`); the benefit is **UNVERIFIED, and a shadow comparison of premature-parent-stop and missing-child-output rates settles it**.

Do not copy nested autonomous swarms by default. Claude's own agent-team docs warn of token overhead, lagging task state, shutdown problems, and missing in-process resumption ([agent teams](https://code.claude.com/docs/en/agent-teams)); Devin warns that nested subagents multiply independent context/inference cost ([Subagents](https://docs.devin.ai/cli/subagents)). The owner's corpus already shows over-strict fan-out schemas are a major failure class: StructuredOutput has a 22.9% error rate. Use a minimal terminal envelope, not a large recursive schema.

## 9. Verification and self-checking

### 9.1 What Devin provides

1. **Code-grounded plan review:** inspectable file/snippet citations before mutation.
2. **Conventional tests:** shell/IDE access and environment blueprints carrying lint/test/build commands.
3. **End-to-end proof workflow:** after a PR, setup → minimal test plan → desktop execution/recording → attachment. The plan is grounded in the diff/code path and sent before execution ([Testing & Video Recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings)).
4. **Independent PR review:** Devin Review groups diffs, detects moves/copies, flags bugs with confidence/severity, classifies security findings with CWE/severity, uses repository context, can trigger on PR events, and can propose/apply fixes ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review)).
5. **Post-session self-analysis:** issue timeline, repeated-error detection, prompt rewrite, environment actions, and useful/misleading Knowledge assessment ([Session Insights](https://docs.devin.ai/product-guides/session-insights)).
6. **Human verification affordances:** live IDE diff, readable shell history, browser takeover, screenshots/recordings.

Cognition itself cautions that Devin can hallucinate, introduce bugs, or suggest insecure code and recommends code review plus branch protection ([Security at Cognition](https://docs.devin.ai/admin/security)). Therefore none of these mechanisms is proof of correctness. The video proves only the recorded path, not unrecorded requirements or absence of regressions.

### 9.2 Comparison

This harness has deeper procedural verification assets: `verification-before-completion`, TDD, code review, e2e testing, plan gate, per-edit checks, cross-vendor review, terminal receipts, and event-ledger mutation freshness. The toolchain lists these workflows explicitly (`agent-skills-toolchain\README.md:274-279`). Its weakness is productization and evidence presentation. A user often receives prose saying tests passed rather than a compact bundle tying diff → commands → raw receipts → visual proof → unresolved risks.

**Capability delta — verification proof bundle (UNVERIFIED outcome effect):** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. Add a `proof-bundle` skill that reads the diff, chooses the narrowest behavior that demonstrates the acceptance criterion, runs deterministic checks, captures receipt hashes and exit status, uses existing Playwright/browser tooling for changed UI, stores screenshots or a short recording when appropriate, and emits a manifest:

```json
{
  "claim": "checkout succeeds with a valid card",
  "diff": "<commit-or-diff-hash>",
  "checks": [{"command": "...", "receipt": "...", "exit": 0}],
  "visual": [{"path": "...", "step": "..."}],
  "coverage": ["happy path"],
  "not_verified": ["declined card", "mobile Safari"]
}
```

Require a real deterministic check where one exists; video is supplemental. The recommendation is **very likely (80-90%)** to make review easier because it reduces verification from reproducing the entire environment to checking bounded receipts/artifacts, supported by Devin's workflow and Hamel Husain's verification-interface argument ([“It's Hard to Eval” Is a Product Smell](https://hamel.dev/blog/posts/eval-smell/)). Its effect on defect escape is **UNVERIFIED; randomize eligible UI changes to proof-bundle versus existing handoff and compare review time, reviewer reproduction rate, and post-merge defects**.

**Capability delta — repository-event PR reviewer (UNVERIFIED comparative accuracy):** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**. Reuse `requesting-code-review`, GitHub CLI/MCP, and a minimal CI/automation trigger to launch a read-only, worktree-isolated reviewer on PR open/update. Output only evidence-backed findings with file/line, severity, confidence band, and a falsification step; never auto-merge and do not auto-fix until the finding is confirmed. This is **likely (55-80%)** to catch additional defects because independent review already exists locally and automation closes the invocation gap, but reviewer precision/recall is **UNVERIFIED; run shadow reviews on 50 historical PRs with known review outcomes and score true/false positives before posting comments**.

## 11. Recommended experiments and adoption order

### 11.1 Live Devin falsification protocol

No recommendation should depend on vendor demos. **UNVERIFIED until this experiment runs:** obtain a trial/team account; use one fixed public repo and ten tasks spanning bug fix, refactor, frontend behavior, failing test, dependency setup, and multi-module change; export all session events; record initial/final commit, user interventions, ACUs, wall time, tests, plan citations, Knowledge/Skill suggestions, child-session state, and proof artifacts. Repeat the same task/spec on the local harness with the same model class where possible. Grade task acceptance, regression tests, reviewer time, intervention count, tool failures, cost, and recovery from one injected environment failure. This settles whether Cognition's productized joins outperform the local equivalents rather than merely looking better.

### 11.2 Adoption sequence

1. **Enable native sandbox in a canary profile.** **NATIVE (Claude Code already does this; we just enable it).** Start with mutation-capable and untrusted-content tasks under WSL2, `failIfUnavailable`, no unsandboxed escape, workspace-only write, denied credential reads, and a small domain allowlist. This is **very likely (80-90%)** to reduce host blast radius for the reasons in §6.3. Measure sandbox fallback attempts, blocked legitimate calls, and task success before widening rollout.
2. **Shadow Session Insights teardown — UNVERIFIED effect.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Generate but do not persist an issue timeline, better prompt, and action drafts for 30 completed sessions. This is **likely (55-80%)** to surface repeated local failure patterns because the corpus already contains 5,692 error fingerprints, retry loops, and 2,268 owner-correction candidates; acceptance and future-error reduction decide promotion.
3. **Add reviewed memory/skill promotion — UNVERIFIED effect.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Promotion stays human-gated. Track accept/edit/dismiss, later retrieval/invocation, staleness, and contradiction incidents.
4. **Add proof bundles — UNVERIFIED defect effect.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Start with UI changes where review reproduction is expensive. Do not claim a video proves more than its manifest coverage.
5. **Add the thin fleet barrier — UNVERIFIED convergence effect.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Shadow-log whether it would have prevented premature synthesis; avoid complex schemas because StructuredOutput is already the second-worst measured tool class.
6. **Only then test config import and PR review automation.** Both are **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** and should graduate only on measured duplicate/dead-server reduction or review precision.

### 11.3 Acceptance thresholds

- Sandbox canary: no silent unsandboxed fallback; zero secret-path reads; legitimate-task completion within 10 percentage points of baseline.
- Insights: at least 50% of drafts rated “useful with no more than minor edits”; at least 20% reduction in the targeted repeated-error fingerprint on matched later tasks. These thresholds are design choices, not predictions.
- Memory/Skill promotion: accepted item must be invoked/retrieved at least once within its next ten eligible sessions, with no contradiction incident.
- Fleet barrier: zero parent completions while a required child is non-terminal; schema rejection must stay below 5%, far below the current StructuredOutput error rate.
- PR reviewer: do not post automatically until precision exceeds 80% on the historical shadow set; recall must be reported separately.
- Proof bundle: median human verification time lower than baseline without increased post-merge defects.

## 12. What is worse in Devin / what not to copy

### 12.1 CLI memory and analytics are materially weaker

Devin Local has no persistent memories and incomplete tool/line/mode analytics ([CLI controls](https://docs.devin.ai/cli/enterprise/controls)). This harness has Basic Memory plus an append-only, secret-redacted, provider-neutral event ledger (`ledger.py:468-490`) and a 10.62 GB corpus distilled into exact tool/error/capability measurements. Do not replace this with CLI-local skills-as-memory.

### 12.2 Fast context trades freshness for speed

Devin's initial assessment may miss recent changes and non-main branches because it searches a main-branch index ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning)). That is an unacceptable default for dirty-worktree debugging. Prefer live file reads; use an index only as a candidate generator and verify every cited symbol against the checked-out tree.

### 12.3 Cloud snapshots discard task state

Every cloud session boots a fresh snapshot copy, and session changes are discarded rather than written back to the snapshot ([Declarative configuration](https://docs.devin.ai/onboard-devin/environment/blueprints)). This is excellent environment hygiene but not durable task recovery. Do not confuse snapshot reproducibility with semantic continuity. Keep the event ledger and sanitized compaction checkpoint.

### 12.4 Global secrets have a broad blast radius

All organization members can cause Global Secrets to be used in all future organization sessions, even though only admins can view/edit the values ([Secrets](https://docs.devin.ai/product-guides/secrets)). This is broader than least privilege. Prefer repo/session-scoped secrets, dedicated service identities, and runtime injection; never bake credentials into a snapshot or memory.

### 12.5 Windows sandbox support is worse

Devin CLI hard-fails sandboxed sessions on Windows because OS-level sandboxing is unsupported; its network filtering is documented as unstable ([sandbox](https://docs.devin.ai/cli/sandbox)). Claude Code supports sandboxing through WSL2 on Windows ([Claude sandboxing](https://code.claude.com/docs/en/sandboxing)). For this owner, Devin CLI is not a sandbox upgrade.

### 12.6 Default plan auto-proceed is too permissive for high-risk work

Cloud Devin waits only 30 seconds before proceeding unless the user explicitly requires approval ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning)). A time delay is not authorization. Keep this harness's rule: block only dangerous/irreversible or materially ambiguous actions; allow planning to remain advisory for ordinary work, but require an explicit semantic gate for high-risk mutation.

### 12.7 Adaptive is opaque and unproven

Cognition says Adaptive analyzes each request and dynamically selects an underlying model, considering cost and prompt caching ([Adaptive](https://docs.devin.ai/cli/adaptive)). It does not publish the routing policy, model-choice trace, controlled task-quality comparison, or failure fallback. Its quality/cost advantage for this owner's workloads is **UNVERIFIED; log chosen model, tokens, latency, outcome, and cache hit on a randomized matched-task evaluation to settle it**.

**Do-not-copy recommendation — Adaptive parity (UNVERIFIED benefit): BUILD-LARGE (new daemon/service/runtime -- needs its own justification).** A faithful router would require evaluation data, telemetry, provider normalization, per-turn switching, cache accounting, and continuous recalibration. This violates the anti-overfit gate and risks routing opacity. Use explicit task-class skills and native per-subagent model selection instead.

### 12.8 Automatic memory and skill suggestions can pollute

Devin offers review before saving, which is good, but its docs do not publish suggestion precision, contradiction handling, temporal validity, or poison resistance. Autonomous admission would be worse than the local contradiction-first, poison-filtered recall (`modules.py:1626-1680`). Copy the reviewed draft, not automatic persistence.

### 12.9 Video evidence can create false confidence

A short recording validates only the demonstrated path. It does not prove regression safety, security, accessibility, cross-browser behavior, or unshown acceptance criteria. Require receipt-backed deterministic tests and an explicit `not_verified` list alongside visual proof.

### 12.10 Product lock-in and duplicated registries

Cloud Knowledge, Playbooks, Skills, Secrets, snapshots, schedules, and session data live in Cognition-specific management surfaces. Although Devin MCP exposes them, the owner already has a cross-provider skill/toolchain and Basic Memory source of truth. Importing another registry would create drift. Keep canonical assets in git/Basic Memory and treat any vendor library as a projection.

## 13. Anti-overfit gate

Accepted proposals all ride existing buses:

- sandbox: native Claude Code;
- teardown and promotion: existing `Stop`, dispatcher, ledger, Basic Memory, and skill validator;
- proof bundle: existing verification skill, Playwright/browser tools, receipts, and artifact path;
- fleet barrier: existing native multi-agent controls plus child lifecycle ledger events;
- config doctor: existing manifest/install tooling;
- PR review: existing review skill plus GitHub CLI/MCP/CI trigger.

Rejected proposals explicitly reintroduce forbidden or unjustified classes:

- hosted snapshot/VM service → second orchestration runtime + durable execution infrastructure;
- Devin-equivalent management MCP → second orchestration/admin plane;
- Adaptive parity → routing service with continual eval/telemetry burden;
- enterprise RBAC/audit/billing → multi-tenant platform unrelated to the owner;
- vendor Knowledge/Playbook mirror → parallel memory/workflow registry.

No vector database, knowledge graph, trained critic, observability SaaS, or guardrail framework is proposed. The design preserves the deliberate small-loop architecture.
