# M06 — Dual-use judgement: authorised RE/security without rubber-stamping

## Executive conclusion

The right boundary is not a topic filter and not a standing presumption that the owner is harmless. It is an **evidence-bearing, target-specific capability lease**: establish who authorised which targets, actions, effects, and time window once; allow low-impact work inside that envelope without repeated questions; require a new external signal when the action crosses the envelope or becomes materially harder to reverse. This permits legitimate reverse engineering while refusing to treat familiarity, insistence, or an earlier broad “continue” as authority for a different target or effect.

This architecture is **very likely (80-90%)** to reduce both rubber-stamp risk and needless friction because (1) NIST's Rules of Engagement define pre-established constraints as authority to perform defined testing without repeated permission, (2) the owner's corpus contains explicit requests for autonomous RE but also corrections about real execution state, and (3) the existing harness already has the buses needed for scope, receipts, reaction learning, and replay. Evidence: [NIST ROE](https://csrc.nist.gov/glossary/term/rules_of_engagement); `/local_disk0/codexwork/bundle/inputs/corpus.json:12125-12128`, `:12137-12140`, `:12401-12404`; `/local_disk0/codexwork/bundle/agents/harness/README.md:1-29`. The exact operating-point improvement is **UNVERIFIED — settle it with the shadow-mode replay and 30-decision owner adjudication experiment specified under Finding 6**.

No seventh hook is proposed. Every mechanism below is a module or data extension on the existing shared dispatcher, event ledger, AskUserQuestion/permission surface, Ulysses tripwires, and calibrated-silence consumer. Hook delta: **0**. Every proposed check closes on an external signal: an owner-authored scope receipt, an independently observed target identity, a tool execution result, a fresh-context reviewer, or the owner's later reaction. Same-context self-critique is never accepted as proof.

## Boundary model

The proposed decision function is:

`decision = f(principal provenance, target identity, allowed action class, effect, reversibility, lease freshness, external receipts)`

It is deliberately **not** `f(words in prompt)`. A request to “write an exploit explanation into a markdown report” is a documentation write, not exploit execution. Conversely, a blandly worded request to “check this host” can be an unauthorised network action. The known defect report proves four detectors have confused payload prose with executable position and records a successful tool result being marked failed because a field name contained `timedout` while its value was false (`/local_disk0/codexwork/bundle/inputs/INPUT-known-harness-defects.md:52-82`).

The minimal action classes are:

| Class | Representative action | Default inside a valid lease | External closure |
|---|---|---|---|
| A0 | explain, search public material, static read | run | source/artifact receipt |
| A1 | decompile/trace owned local binary; offline PoC; fuzz isolated copy | run | binary hash + local process/file identity + tool receipt |
| A2 | mutate isolated copy, attach debugger to owner process, write reversible game memory | run only if explicitly included; checkpoint first | scope receipt + target identity + before/after receipt |
| A3 | interact with remote service, accounts, third-party data, credentials, persistence, exploit delivery | confirm unless an exact current ROE includes it | owner/signed ROE + independently observed endpoint/account identity |
| A4 | destructive, hard-to-reverse, broad propagation/exfiltration, safety-impacting act | confirm for the exact act; block if authority cannot be established | owner confirmation plus second independent signal; execution receipt afterward |

These are capability/effect tiers, not moral labels. The same technique can occupy different tiers depending on target and effect.

## Findings (inferred-surprise first)

### 1. Scope receipts, not trust scores: compile an ROE into a capability envelope

**Improvement.** Add a compact, owner-readable `scope_receipt` event to the existing ledger. This replaces “do I trust this user?” with “is this exact action authorised for this exact target now?”

**What it is.** A receipt contains: `receipt_id`, `principal=owner|signed_policy`, `source_event_id/hash`, `target selectors` (repo root, binary SHA-256, PID/executable path, hostname/CIDR, account/tenant), allowed action classes, explicit exclusions, data-handling constraints, expiry, and revocation status. Free-form intent is retained for display but never grants capability. One owner answer can create the receipt; later actions consume it.

**Why inferred.** The owner explicitly wants autonomous IDA work (`corpus.json:12401-12404`) and uses RE tooling heavily (`corpus.json:159-164`, `:183-185`), so asking “is this authorised?” on every step is prompt fatigue. Yet the owner's legitimate history cannot authorise a new third-party target. NIST defines Rules of Engagement as pre-established constraints that give a test team authority for defined activities without additional permissions ([NIST ROE](https://csrc.nist.gov/glossary/term/rules_of_engagement)). Anthropic's newest dual-use research frames the objective as surgical restriction while retaining capability for trusted beneficial deployments, not uniformly deleting capability ([Anthropic, 2026](https://www.anthropic.com/research/off-switch-dual-use)).

**How to build.** Add one `AuthorizationModule` to `build_default_modules()` before the event ledger consumes blocked payloads. Extend the existing ledger event schema with `scope_grant`, `scope_revoke`, and `scope_use`; add a tiny `scope.py grant|show|revoke` CLI analogous to existing `note.py` (`/local_disk0/codexwork/bundle/claude/hooks/event-ledger/note.py:1-43`). On the first material ambiguity, AskUserQuestion shows a single compact delta: target, action class, effect, expiry. Store the resulting owner event hash. Matching is exact/canonical: resolved repo root, normalized endpoint, or binary hash; no fuzzy semantic target match. Any parse/storage error returns “unknown”, does not manufacture authorisation, and the enclosing hook still exits 0. An unknown A0/A1 action degrades to analysis-only; unknown A3/A4 asks the owner.

**External signal that verifies it.** (1) owner-authored event or signed ROE is the authority signal; (2) actual target identity is independently read via binary hash, Git root/remote, PID executable path, TLS hostname, or tool-returned target metadata. Tests must include a known-positive exact match, known-negative adjacent target, expired lease, revoked lease, prompt text quoting an exploit, and target substitution after approval.

**Confidence.** **Very likely (80-90%)** to remove repeated approval prompts without widening authority, because the receipt reuses the existing permission/ledger buses and mirrors established ROE practice. Evidence: NIST ROE above; generic permission events already reach the dispatcher (`settings.json:284-318`). Production fit is **UNVERIFIED — settle it with a shadow run that compares 30 proposed decisions against owner labels before enforcement**.

**Implementation tag.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — one module, schema additions, and CLI; no new hook or runtime.

**Anti-overfit gate.** Passes: existing dispatcher + append-only ledger; no second orchestrator, vector DB/KG, durable-execution engine, trained critic, SaaS, or guardrail framework.

**Value × effort.** transformative × medium.

**Novelty.** inferred-surprise.

**Autonomy.** confirm-first (one explicit scope grant; matching work thereafter is autonomous).

### 2. Consent amortisation: time-bound capability leases with automatic narrowing

**Improvement.** Turn a scope receipt into a short, renewable capability lease so the owner is asked once per meaningful boundary, not once per command.

**What it is.** A lease is valid only while all immutable selectors still match. It narrows automatically on time expiry, repo/branch/remote change, binary hash change, PID replacement, endpoint redirect outside the allowed host set, or transition to a higher action class. It never broadens automatically. “Continue,” “do everything,” and “do not stop” can extend the task goal but cannot change target or action class unless the owner sees that delta.

**Why inferred.** The corpus has a direct “nope you can proceed” followed by a request for autonomous multi-agent loops (`corpus.json:12119-12128`), and repeated stop-feedback patterns appear in the recall-biased detector (`corpus.json:10377-10398`). Those patterns are not counted as verified corrections, but they motivate an experiment about repeated consent friction. Microsoft HAI guidelines call for efficient invocation, dismissal, correction, scoping under doubt, and global controls ([Microsoft HAI guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)).

**How to build.** On `scope_grant`, derive `lease_until` and immutable selector fingerprints. At each PreToolUse, compare the proposed action against the receipt and live selector; consume silently on match. At mismatch, generate a one-line permission delta, e.g. `Target changed: local SHA abc… → def…; requested A2 memory write; approve for 2h?` Provide `once / task / 2h / deny` options. Use the existing calibrated-silence gate only for optional explanation, never to suppress a required A3/A4 confirmation. Revocation is a single command/owner response and is replayed at SessionStart.

**External signal that verifies it.** The owner's explicit selection establishes duration; filesystem/process/network observations establish continued selector identity. A mutation receipt closes each A2+ action. Evaluation measures prompts per completed authorised task, stale-lease catches, and false grants on target-switch fixtures.

**Confidence.** **Likely (55-80%)** to materially reduce prompt fatigue because the corpus demonstrates a preference for sustained autonomy and HAI research recommends efficient interaction. The magnitude is **UNVERIFIED — settle it by A/B shadow replay measuring approval prompts per 100 security-tool calls and owner-rated interruption cost**.

**Implementation tag.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — fields and matching logic inside Finding 1's module, not a separate hook.

**Anti-overfit gate.** Passes: it is lease data in the existing ledger, not a durable-execution system.

**Value × effort.** high × low.

**Novelty.** inferred-surprise.

**Autonomy.** confirm-first (at lease creation or material delta only).

### 3. Effect-first judgement: classify the tool verb, target, and blast radius—not security vocabulary

**Improvement.** Make dual-use decisions on executable semantics. Security prose is unrestricted A0; a live side effect is judged from tool name, normalized arguments, target, and reversibility.

**What it is.** A deterministic `classify_effect(tool_name, input, resolved_target)` shared by all safety consumers. It emits `{action_class, effect, reversibility, externality, confidence_reason}`. Examples: writing a report that quotes `Remove-Item` is a documentation write; reading/decompiling an owned DLL is A1; attaching to a locally owned game process is A2 when it permits mutation; sending an exploit to an unscoped host is A3/A4.

**Why inferred.** Four independent detectors already confuse prose/field names with executable occurrences, including a detector that would discard a successful result (`INPUT-known-harness-defects.md:52-82`). This is directly dangerous for dual-use work: a keyword gate becomes both over-refusing and easy to evade. The latest agent-security SoK says tool-integrated agents introduce security challenges distinct from conventional components ([USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/kim-juhee-agentic)); NIST AI RMF says tasks/methods and human oversight should be explicitly defined ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**How to build.** Do not create a new scanner. Implement the shared discriminator already demanded by the known-defects report, then add a small table mapping high-signal tool verbs to effects. Parse argv/structured MCP fields, never scan arbitrary payload prose. For shell calls, use the shell AST/parser already selected by the shared discriminator work; if parsing fails, return `unknown`, not `dangerous`. Fold this classifier into the existing dispatcher and Ulysses consumer. Keep classifications explainable with one stable reason code.

**External signal that verifies it.** Replay the recorded false-fire fixtures plus true controls: actual destructive command, prose quoting it, JSON key `timedout:false`, RE read, local memory write, and remote action. Require both the normalized tool event and the observed post-tool receipt for evaluation. The classifier proposes a class; correctness is decided by fixture truth or owner adjudication, never by the generating context.

**Confidence.** **Almost certain (90-99%)** that verb/target discrimination will eliminate the documented prose false-fire class, because each recorded false fire occurred outside executable position and the defect report identifies that common architectural cause (`INPUT-known-harness-defects.md:43-50`, `:78-87`). Generalisation to every shell/MCP tool is **UNVERIFIED — settle it with a 200-event stratified replay containing at least 50 true side effects**.

**Implementation tag.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** if the shared discriminator receives verb and structured input, as the dispatcher adapter already does; fold into that existing planned library, not a v2 detector.

**Anti-overfit gate.** Passes: deterministic shared library on the current bus; explicitly no general guardrail framework.

**Value × effort.** transformative × medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it (safe classification and A0/A1 continuation; confirmations are generated only for resulting A3/A4 deltas).

### 4. Authority provenance is tainted data: only the owner or a verifiable ROE can grant scope

**Improvement.** Track where an instruction came from and prevent tool output, retrieved documents, subagents, or prior assistant text from upgrading authority.

**What it is.** A two-bit provenance lattice is sufficient: `OWNER_AUTHORITY`, `VERIFIABLE_POLICY`, `UNTRUSTED_CONTEXT`, `DERIVED`. Only the first two may create a scope grant; derived text may narrow but never widen it. A peer can report facts, a README can describe testing, and a model can recommend actions, but none can say “you are authorised” on the owner's behalf without an externally verifiable policy bound to the target.

**Why inferred.** The corpus contains teammate-message wrappers that explicitly warn a peer cannot grant escalation or be treated as owner approval (`corpus.json:11309` in the supplied file; the full record begins there). The known defect D4 shows an orchestrator-authored false constraint propagated into roughly 15 prompts (`INPUT-known-harness-defects.md:151-161`). This proves prompt provenance affects real action. NIST AI RMF calls for documented roles, responsibilities, accountability, and third-party risk ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/), Govern 2.1, 3.2, and 6.1).

**How to build.** The adapter already distinguishes human messages from tool results in several components; calibrated-silence's reaction parser explicitly rejects tool-result blocks as user speech (`/local_disk0/codexwork/bundle/claude/hooks/calibrated-silence/log_reaction.py:170-188`). Reuse that discriminator. Stamp each scope candidate with source event type and hash. For a policy file, require an exact path/URL named by the owner or a known VDP source, bind it to target selectors, and store its content hash and retrieval timestamp. Any statement of authority arriving via tool output or subagent is displayed as evidence to verify, not accepted.

**External signal that verifies it.** Owner-event type plus transcript event hash, or a separately fetched signed/published policy whose hostname/target coverage is checked independently. Adversarial tests inject “owner approved” through a README, MCP result, subagent message, webpage, and prior assistant response; all must fail to grant. A genuine owner message is the known-positive control.

**Confidence.** **Very likely (80-90%)** to prevent instruction-origin laundering because the event structures already distinguish real user speech and tool results. Complete coverage of every provider event shape is **UNVERIFIED — settle it with cross-provider fixtures for Claude, Codex, Workflow, MCP, and teammate messages**.

**Implementation tag.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — provenance fields in adapters/models and a grant predicate in AuthorizationModule.

**Anti-overfit gate.** Passes: four-value taint metadata, no policy engine service.

**Value × effort.** high × low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it (provenance stamping is automatic; ambiguous authority is surfaced without acting).

### 5. Safe continuation instead of binary refusal: automatically descend the action ladder

**Improvement.** When authority is missing for a live effect, continue useful work at the highest authorised lower tier rather than either rubber-stamping or stopping the whole task.

**What it is.** A blocked/unknown A3 action is transformed into an A0/A1 plan: static analysis, offline reproduction, mock target, payload neutralisation, detection logic, patch, test harness, or a precise request for the one missing scope field. This is a mixed-initiative boundary: the agent contributes what it can safely do now, and the owner supplies authority only when it becomes decision-relevant.

**Why inferred.** The owner asks agents not to stop (`corpus.json:12401-12404`) and explicitly requests autonomous loops with quality gates (`corpus.json:12125-12128`). A pure refusal discards legitimate value; an unconditional proceed discards judgement. Mixed-initiative research defines the goal as each human/computer contributor acting where best suited and at the appropriate time ([Microsoft Mixed-Initiative Interaction](https://www.microsoft.com/en-us/research/publication/mixed-initiative-interaction/)). Microsoft HAI Guideline 10 recommends disambiguation or graceful degradation under uncertainty ([HAI guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)).

**How to build.** Add `safe_alternative` to the effect table, not free-form policy generation. Examples: `remote_exploit → local container replay`; `credentialed scan → unauthenticated public-surface inventory`; `live patch → binary diff + patch plan`; `data export → schema/count-only preview`. When a class mismatch occurs, AuthorizationModule injects a compact structured continuation and records an `open_authorization_delta` in the ledger. The agent performs that alternative immediately if it is within the lease. No owner prompt is emitted until the missing authority blocks the next concrete step.

**External signal that verifies it.** The lower-tier tool execution produces a real artifact/receipt; the unresolved delta remains in the ledger until owner grant, revocation, or explicit abandonment. Tests assert that the proposed substitute has no network/live mutation using process/network logs or a sandbox trace—not the same model's description.

**Confidence.** **Likely (55-80%)** to preserve momentum while avoiding unauthorised effects, based on the owner's autonomy preference and mixed-initiative/graceful-degradation guidance. Whether the fixed alternative table covers the owner's main RE workflows is **UNVERIFIED — settle it with 20 historical blocked-or-ambiguous scenarios and owner ratings of usefulness**.

**Implementation tag.** **CONFIG (settings/JSON only)** for the action-to-safe-alternative mapping, consumed by the Finding 1 module; no separate implementation.

**Anti-overfit gate.** Passes: a small declarative mapping on the existing bus.

**Value × effort.** high × low.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it (perform the authorised lower-tier continuation; confirm only before the unresolved higher-tier effect).

### 6. Calibrate judgement on outcomes, not compliance: shadow-mode dual-error measurement

**Improvement.** Measure both unsafe over-grants and obstructive under-grants, then adjust thresholds only between sessions from external labels.

**What it is.** Every proposed dual-use decision is logged in shadow mode with class, matched receipt, reason code, whether the owner proceeded/rejected/corrected, and whether the external execution receipt showed the predicted target/effect. Report a two-dimensional score analogous to appropriate reliance: correct autonomy on authorised work and correct escalation on unauthorised/out-of-scope work. A system that merely refuses more does not score better.

**Why inferred.** The corpus's correction miner is demonstrably unsuitable as raw truth (`corpus.json:10371-10374`). The existing calibrated-silence mechanism already uses acted/ignored/annoyed reactions and explicitly grounds its signal in the user's next turn (`calibrated_silence.py:39-53`). Current appropriate-reliance research distinguishes subjective trust from objective discrimination of correct and incorrect advice and warns against conflating more reliance with better reliance ([Raees & Papangelis 2026](https://arxiv.org/abs/2604.23896); [Schemmer et al.](https://arxiv.org/abs/2204.06916)).

**How to build.** Extend the calibrated-silence ledger schema with `decision_id`, `proposed_class`, `grant_match`, `owner_label`, `observed_effect`, and `outcome`. Reuse its real-user-turn parser. Do not online-learn from the current turn. Once per SessionStart or explicit `/self-reflect`, compute a report from prior closed decisions; require minimum sample counts and show both false-grant and false-escalation rates. Threshold changes are proposed as a JSON diff and require owner confirmation. Start shadow-only for at least 30 adjudicated decisions.

**External signal that verifies it.** Owner adjudication plus an independent action receipt/process/network trace. Correct autonomy requires authorised target + expected bounded effect; correct escalation requires owner denial, target mismatch, or missing authority confirmed by policy inspection. Same-context explanations are not labels.

**Confidence.** **Very likely (80-90%)** that two-sided measurement will reveal failure modes hidden by a single “number of blocks” metric, because the research operationalises over- and under-reliance separately and the local correction detector has a measured precision failure. Whether 30 decisions suffice for stable per-class tuning is **UNVERIFIED — settle it with bootstrap confidence intervals; retain shadow mode until each enforced class meets a predeclared interval width**.

**Implementation tag.** **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)** — additive fields and an offline report in calibrated-silence/self-reflect, not a trained critic.

**Anti-overfit gate.** Passes: simple counts/intervals and owner labels; explicitly no learned classifier, observability SaaS, or second runtime.

**Value × effort.** high × medium.

**Novelty.** inferred-surprise.

**Autonomy.** just-do-it (shadow logging/reporting; confirm-first only for a threshold configuration change).

### 7. Replace the same-context critic with an external two-key gate for high-impact actions

**Improvement.** Delete the behavioral requirement for an “internal generator-critic pass” as a safety proof and require two independent keys for A4: valid authority plus an external reality check.

**What it is.** Key 1 is scope: owner receipt or verifiable ROE. Key 2 is independent evidence appropriate to the act: fresh-context model review, second disassembler, binary hash/version check, dry-run/sandbox trace, canary, or owner confirmation of the exact irreversible delta. Neither key substitutes for the other. For A0-A2, one external execution receipt is usually sufficient; risk—not scary vocabulary—sets burden.

**Why inferred.** The current cross-tool contract says to run an internal generator-critic pass (`/local_disk0/codexwork/bundle/claude/AGENTS.md:72-79`), but the law binding this unit rejects same-context self-correction. The same contract already contains the better pattern: after two failures, use a genuinely independent fresh-context re-derivation (`AGENTS.md:51-57`). `fresh-context-verify` was actually invoked five times (`corpus.json:13291`), and Ulysses describes external transcript/tool signals (`ulysses/_common.py:2-29`). NIST AI RMF calls for documented oversight and deactivation/recovery processes ([NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)).

**How to build.** Change AGENTS §7 from internal critic to: “For A3/A4 or a load-bearing disputed claim, obtain an external receipt; same-context reflection is brainstorming only.” Extend the existing stake-tier map (`ledger.py:123-131`) with dual-use action classes and acceptable second-key receipt types. Reuse fresh-context-verify, Ulysses, truth-verify, and tool receipts. For A4, AskUserQuestion presents the exact target/effect and the second-key result; approval is act-specific and one-shot.

**External signal that verifies it.** A receipt from a different tool/context plus the authorisation receipt. Example: IDA-derived patch location + Ghidra re-derivation on the same binary hash; proposed remote action + owner-confirmed exact hostname/action; destructive file operation + independently enumerated explicit targets and checkpoint receipt. A second prompt to the same context is invalid.

**Confidence.** **Almost certain (90-99%)** that the current internal-critic sentence fails this unit's external-signal law because it explicitly keeps the critic internal. **Very likely (80-90%)** that the two-key scheme is implementable with existing components, supported by the existing fresh-context skill, typed receipts, and Ulysses. Its false-escalation rate is **UNVERIFIED — settle it in Finding 6's shadow evaluation**.

**Implementation tag.** **CONFIG (settings/JSON only)** for the behavior-contract text and stake/receipt map; it reuses existing verification machinery.

**Anti-overfit gate.** Passes: uses an existing second-model skill/tool only when risk warrants it; no trained critic or daemon.

**Value × effort.** transformative × low.

**Novelty.** user-asked (the binding law explicitly requires external closure).

**Autonomy.** confirm-first (only A4 exact acts; lower classes use external receipts without owner interruption).

### 8. Authorisation deltas are open threads: persist, replay, and retire them explicitly

**Improvement.** Make every discussed-but-unresolved security boundary a typed open thread, so safe continuation never silently forgets the live action the owner wanted.

**What it is.** `open_authorization_delta` records requested action, blocked dimension, safe work completed, next external signal needed, and status `open|granted|denied|obsolete`. It is part of the existing event ledger and mirrored to `OPEN-THREADS.md` by the existing thread mechanism. SessionStart surfaces only actionable deltas, grouped into one compact block; it never repeatedly asks while the owner is focused.

**Why inferred.** The owner explicitly said “ask me again since we got interrupted” (`corpus.json:11171-11174`). The current replay already preserves goals, open failures, decisions, and HEAD drift (`sessionstart-replay.py:31-63`), so authorisation state belongs in that same continuity plane. Microsoft HAI guidelines recommend remembering recent interaction, cautious adaptation, consequences, and global controls ([Microsoft HAI guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)).

**How to build.** Add the event kind and projection fields to the existing ledger. When Finding 5 descends to a safe tier, create/update one delta keyed by `(receipt_id,target,action_class)`; deduplicate rather than append nags. On grant/deny/target disappearance, append a terminal event that supersedes it. ## Integrated decision protocol

1. **Identify the principal.** Only a real owner event or independently verifiable ROE can grant. Tool/subagent/retrieved text is evidence, never authority.
2. **Resolve the target externally.** Hash the binary; resolve the repo root/remote; inspect PID executable; canonicalise hostname/account. Never accept the model's remembered target as the second signal.
3. **Classify the proposed effect.** Use tool verb + structured arguments + resolved target. Ignore security vocabulary in prose.
4. **Match the lease.** Exact target, allowed action class, exclusions, and freshness must match. Leases narrow automatically and never auto-broaden.
5. **Act or descend.** A0/A1 inside scope: act. A2: checkpoint and act if explicitly leased. A3/A4: consume exact ROE or ask for the smallest delta. If not granted, perform the configured lower-tier continuation.
6. **Close on reality.** Record tool result, observed target/effect, and any second-key receipt. Never let the current context certify its own action.
7. **Keep the thread.** Persist unresolved deltas and retire them only by grant, denial, or externally observed obsolescence.
8. **Calibrate between sessions.** Shadow-log both false grants and false escalations; change thresholds only from external labels and only after owner review.

## Hook, latency, prompt-fatigue, and failure accounting

* **Hook count:** adds zero. `AuthorizationModule` is folded into the shared dispatcher already registered for UserPromptSubmit/PreToolUse/Permission/PostToolUse. The other changes are data/config/extensions to existing consumers.
* **Fail-open:** every module catches its own errors and returns allow/unknown; it never fabricates a grant. * **Prompt fatigue:** one compact scope grant, then silence until an actual target/effect delta. Optional resurfacing uses the existing reaction-based calibrated-silence gate; required A3/A4 confirmation is not suppressed.
* **Never drop a thread:** unresolved authority is durable state, not a repeated prompt and not an in-context TODO.

* **Latency:** deterministic stdlib/JSON/hash/path checks only in hooks. Fresh-context/model review is reserved for A3/A4 or disputed load-bearing claims and runs through existing skills/tools outside the hook hot path.
