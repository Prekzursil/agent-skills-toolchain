# G005 — failure-mode inventory: cross-vendor dispatch can report completion without delivering work

Date: 2026-07-19  
Unit: G005  
Scope: the observed `3 Codex-backed subagents → 0 production artifacts` incident, and the failure class that generalises beyond that adapter  
Subject access: read-only unpack at `/local_disk0/codexwork/bundle`; only this artifact was written

## Executive finding

The highest-damage failure is **phase confusion at an agent boundary**: the caller treats one of
“request accepted,” “process started,” “transport returned,” “agent emitted plausible prose,” or
“terminal marker present” as if it meant “the contracted work was durably delivered and its
postcondition holds.” The 2026-07-18 record says three Codex-backed subagents produced zero
production artifacts while two Claude peers produced 16 files; it explicitly says the adapter, not
Codex coding quality, failed (`/local_disk0/codexwork/bundle/claude/rules/common/cross-vendor-dispatch.md:3-5`).
The same run records three concrete boundary collapses: an asynchronous start receipt was returned
as the entire answer and the eventual result became unreachable; a foreground invocation returned
only progress while its job remained `running`; and two real-work invocations exceeded Windows'
argument limit because the prompt/config was marshalled onto the command line
(`/local_disk0/codexwork/bundle/claude/rules/common/cross-vendor-dispatch.md:7-17,19-40`).

This is **almost certain (90-99%)** to be an adapter/orchestration-contract failure rather than
evidence that Codex could not do the coding task. Evidence: the local incident record states that
Codex coding was never exercised (`cross-vendor-dispatch.md:3-5`); the recorded failures occur at
launch, addressing, stream classification, and prompt transport (`:7-40`); and the corpus independently
shows the Codex MCP boundary itself had 31 errors in 47 calls, including ten explicit 300/600-second
timeouts (`/local_disk0/codexwork/bundle/inputs/corpus.json:591-596,9400-9428`). “Almost certain,” not
“certain,” is appropriate because the raw `wf_82c5b350-9ba` workflow ledger and its three child
transcripts were not included in the Linux bundle, so this unit cannot independently replay each
child's complete timeline.

The general structural fix is not “be more careful” and not another runtime. It is a **fail-closed,
provider-neutral WorkUnit delivery reducer** on the existing Workflow/shared-dispatcher bus. Only the
reducer may turn a child into `DELIVERED`; it requires a correlated work-unit identity, a terminal
transport state, a schema-valid result envelope, a nonempty artifact manifest, and mechanically
independent postcondition receipts. Everything else remains `ACCEPTED`, `RUNNING`, `FAILED`,
`SEVERED`, or `PARTIAL`. The reducer makes it impossible for a job id, progress stream, bare
`SUCCESS:` prefix, or exit code by itself to satisfy fan-in.

## Mechanism: the state machine that was collapsed

A cross-agent call has at least six distinct phases:

| Phase | What it proves | What it does **not** prove | Observed false substitute |
|---|---|---|---|
| `ACCEPTED` | the adapter accepted a request | a worker started | job/task id |
| `RUNNING` | a worker/process emitted activity | the logical turn finished | `[codex] …` progress / stderr |
| `TRANSPORT_TERMINAL` | process or RPC ended | a valid final payload exists | exit code 0 or RPC return |
| `RESULT_READY` | final result channel exists and parses | claimed effects exist | plausible digest / `SUCCESS:` prefix |
| `ARTIFACT_READY` | declared paths/hashes/bytes exist | behavior is correct | file existence alone |
| `DELIVERED` | result is correlated, schema-valid, and postconditions pass | nothing further for this work unit | the only fan-in success state |

The incident became possible because the old boundary collapsed earlier phases into `DELIVERED`.
The evidence is unusually specific:

- A start receipt was accepted as a final answer even though the completed payload was elsewhere
  (`cross-vendor-dispatch.md:12-17`).
- A returning foreground call was accepted even though its record still said `running` and only a
  progress prefix was present (`:21-30`).
- A digest was accepted without checking that its named files existed
  (`fan-out-contract.md:70-75`).
- The generic shared lifecycle gate makes the same semantic mistake in code: the terminal lexical
  prefix short-circuits before length/substance validation (`modules.py:2384-2396`), and its test
  enshrines that result (`test_modules.py:1005-1020`).

This failure is **very likely (80-90%)** to recur at any adapter that exposes more than one result
channel—job receipt plus later result, progress plus final message, event JSONL plus final response,
or agent prose plus filesystem mutation—unless fan-in owns a phase-aware reducer. Evidence: all
three observed transport shapes failed at precisely that ambiguity (`cross-vendor-dispatch.md:7-40`),
and the provider-neutral lifecycle code accepts a lexical marker rather than a typed delivery object
(`modules.py:2331-2396`). The band is below “almost certain” because other adapters may already
enforce typed postconditions outside the supplied bundle.

## Preconditions: what must be true for the failure to occur

The failure requires a conjunction; removing any one of the load-bearing preconditions prevents or
at least loudly exposes it.

1. **There is a lossy boundary.** One agent shells to another runtime or invokes it through an MCP,
   wrapper, workflow, background registry, or job store. The cross-vendor rule explicitly scopes
   itself to Claude→Codex “and any agent that shells to another agent runtime”
   (`cross-vendor-dispatch.md:1`).
2. **The boundary has multiple channels or phases.** Codex alone has progress on stderr, final text
   on stdout or `-o`, and JSONL events under `--json`; official documentation states these are
   distinct channels. A generic async wrapper adds start receipt, status, and result channels.
3. **Fan-in trusts self-report or transport status.** The 3/3 plausible-but-nonexistent digest record
   demonstrates that a child summary was allowed to substitute for the artifact
   (`fan-out-contract.md:70-75`).
4. **No correlated durable result key spans launch through fan-in.** In the observed async route,
   child jobs were written with `sessionId:null`, while status filtered by a non-null session id,
   making completed results invisible (`cross-vendor-dispatch.md:15-17`).
5. **Prompt/result marshalling is vendor- or shell-specific.** An inline prompt exceeded the Windows
   32,767-character process limit, and the retained rule reports heredoc truncation between tested
   4,500-byte success and 13,650-byte failure (`:32-40`).
6. **The completion gate is lexical rather than semantic.** The shared gate accepts a terminal
   prefix without parsing any fields or validating a postcondition (`modules.py:2331-2396`).
7. **Failure may return no terminal object.** The retained rule says an older rescue definition
   instructed the adapter to return nothing after Bash failure, which creates an unrecoverable fan-in
   hole (`cross-vendor-dispatch.md:55-60`).

The model/vendor is not a precondition. A Claude→Gemini wrapper, a Codex→Claude child, a local
subprocess worker, a remote CI agent, or even a non-agent batch job can exhibit the same state
collapse. This generalisation is **very likely (80-90%)** because its premises are transport and
verification semantics rather than model behavior; evidence is the provider-neutral weak terminal
gate (`modules.py:2331-2396`) plus the rule's explicit cross-runtime scope
(`cross-vendor-dispatch.md:1`).

## Observed instances, ranked by expected damage

Ranking is by expected damage, not count. Silent false completion outranks loud launch failure even
when the latter is more common.

### Rank 1 — plausible result accepted while contracted artifacts do not exist

**Observed instance.** Three of three Codex agents returned plausible digests for nonexistent files
(`fan-out-contract.md:70-71`). The companion incident record reports zero production artifacts for
all three Codex-backed subagents versus 16 files from two Claude peers
(`cross-vendor-dispatch.md:3-5`). A newer synchronous adapter also records a prior agent claiming
three files when all three were absent
(`/local_disk0/codexwork/bundle/claude/agents/codex.md:80-85`).

**Mechanism.** Self-reported prose crossed fan-in without a filesystem/postcondition check. A
plausible digest can then be cited downstream as if the underlying analysis or implementation
exists. This silently corrupts the aggregate conclusion and is therefore the highest expected
damage.

**Detection signal.** For every manifest entry, resolve the path relative to an explicitly pinned
artifact root; verify existence, nonzero bytes, expected type, and digest; then run the class-specific
postcondition (test, parse, Git diff, query, or deterministic content assertion). File existence and
child prose are not independent; filesystem metadata plus a behavioral verifier are.

**Confidence.** **Almost certain (90-99%)** that the false-delivery symptom occurred, based on two
retained incident rules and the newer adapter's postcondition warning. The exact paths and contents
are UNVERIFIED as stated above; the raw-ledger/filesystem-manifest experiment settles them.

### Rank 2 — completed asynchronous work becomes unreachable and is silently discarded

**Observed instance.** One agent's entire answer was a background-start receipt. Its job later
completed on disk, but the real finding was never read. Jobs launched from a subagent carried
`sessionId:null`; status lookup filtered by session id, so comparison with the caller's non-null id
hid them (`cross-vendor-dispatch.md:12-17`).

**Mechanism.** The async identity domain at write time differed from the identity domain at lookup.
The barrier accepted `ACCEPTED` as `DELIVERED`, discarded its only handle, and never consumed the
terminal payload.

**Detection signal.** Reject terminal child text matching a start receipt (`started in the
background`, job id, or “check status”). Independently reconcile every launched `work_unit_id` to
exactly one durable terminal record and exactly one result path; any accepted unit without that join
is `ORPHANED`, never successful.

**Confidence.** **Almost certain (90-99%)**, because the retained rule names both the discarded
completed result and the exact null-versus-session filter (`:12-17`). The underlying job-control
source is absent from the bundle, so line-level re-verification of that implementation is
UNVERIFIED; inspect `lib/job-control.mjs` and replay a subagent-launched background fixture to settle
it.

### Rank 3 — progress/event stream is mistaken for the final result

**Observed instance.** A foreground invocation configured for 30 minutes returned after 6m59s with
only a progress prefix; the adapter forwarded raw stderr as its terminal result while the job record
still said `running` (`cross-vendor-dispatch.md:19-30`).

**Mechanism.** “The call returned” was taken as transport completion, and the available text channel
was assumed to be the semantic result. Current official Codex documentation confirms that progress
is streamed to stderr while the final message uses stdout/`-o`, and that JSONL is an event stream,
not merely the final response.

**Detection signal.** Never parse stderr/progress as result. Require both a terminal process/RPC
state and a nonempty final-message file; if JSONL is used, require a terminal `turn.completed` and
then consume the explicit final-result channel. Disagreement—transport returned but job says
running, or exit 0 but no final file—is `SEVERED`.

**Confidence.** **Almost certain (90-99%)** for the recorded instance, supported by elapsed time,
channel content, and the independently stored running status (`cross-vendor-dispatch.md:21-30`).

### Rank 4 — the generic lifecycle gate accepts a hollow terminal marker

**Observed instance.** This is a currently present structural instance, not merely historical: the
shared module's `_TERMINAL` regex accepts `SUCCESS:`/`FAILED:` plus one token and returns allow before
checking length (`modules.py:2331-2334,2384-2396`); the test asserts `SUCCESS:review` is sufficient
(`test_modules.py:1005-1020`).

**Mechanism.** A lexical marker is used as proof of a semantic result. A failed child can suppress
the hollow-output warning with a one-token prefix, and a malicious or confused child can place any
prose after it without schema validation.

**Detection signal.** A known-positive control is a schema-valid WorkUnit result with a real
artifact and passing postcondition; known negatives include `SUCCESS:review`, long unstructured
prose, schema-valid JSON naming a missing file, and a real artifact with a failing test. The current
detector must reject all four negatives before its silence can be trusted.

**Confidence.** **Almost certain (90-99%)** that the weak predicate exists and is intended behavior,
because implementation and explicit regression test are mechanically independent signals.

### Rank 5 — inline prompt/config exceeds Windows process arguments before work begins

**Observed instances.** An inline prompt produced `payload_len=34472` and `os error 206`, killing
both attempts that tried real work (`cross-vendor-dispatch.md:32-40`). The corpus separately records
Codex MCP failures for an unsupported model and incompatible agent settings
(`corpus.json:9421-9427`), illustrating that launch configuration can fail before model work.

**Mechanism.** A logically unbounded task payload and active configuration were serialized into a
bounded process argument vector. Retrying the same route cannot improve it.

**Detection signal.** Preflight the encoded argv length; stage prompt and schema in files; pass the
prompt by stdin/file; capture exit code plus the final output path. Classify `os error 206` or
`payload_len` as `TRANSPORT_REJECTED`, never model failure.

**Confidence.** **Almost certain (90-99%)** for the two recorded attempts because payload size,
specific OS error, and lack of model exercise align. The precise heredoc threshold is **UNVERIFIED**
in the retained rule (`:36-37`); a binary-search fixture through the exact Windows Git Bash/Claude
Bash transport would settle it, but the structural fix does not depend on that threshold.

### Rank 6 — timeout/default-policy failures encourage unsafe background escape hatches

**Observed instances.** The cross-vendor rule says a silent ten-minute default caused one agent to
rationalise `--background` (`cross-vendor-dispatch.md:62-66`). Across the broader transcript corpus,
the Codex MCP had 47 calls, 31 classified errors (65.96%), including seven 600-second and three
300-second timeouts (`corpus.json:591-596,9400-9415`). `mcp__codex__codex-reply` had five failures in
five calls, all retained fingerprints being thread-id parse/not-found failures
(`corpus.json:10145-10161`).

**Mechanism.** A call-level deadline is conflated with job-level completion. When the synchronous
wait is too short or opaque, an adapter changes execution semantics to background mode without also
adding durable addressing and fan-in pickup.

**Detection signal.** Emit separate timestamps/deadlines for launch, heartbeats, logical turn, and
overall work unit. A timeout produces a terminal `FAILED:timeout` envelope with the last known job
identity and partial result pointer; it never silently changes sync to async.

**Confidence.** **Almost certain (90-99%)** that timeout and thread-address failures occurred at the
reported corpus counts; the corpus coverage control is at `corpus.json:2-11`. It is **likely
(55-80%)** that opaque timeout behavior materially encouraged backgrounding beyond the one recorded
agent, based on the explicit incident note plus ten MCP timeout fingerprints, but a controlled
same-task timeout experiment would be required to measure that causal rate.

### Rank 7 — wrapper epilogue masks a nonzero child exit as success

**Observed instance.** During the newer rail smoke test, a runner ended with a bare `echo`; that
overwrote the child status and turned Codex exit 1 into apparent success after seven seconds, with no
`-o` result file (`/local_disk0/codexwork/bundle/claude/agents/codex.md:56-58`).

**Mechanism.** The wrapper reported its own last command's status rather than the delegated process's
status. This is a generic shell-adapter failure: logging or cleanup after the child can accidentally
become the authoritative exit.

**Detection signal.** Capture the child return immediately, run bounded logging, and explicitly
`exit "$rc"`; independently require the result file/schema/postconditions, so even a masked zero is
classified `SEVERED`. Add a fixture whose child exits 1 followed by successful logging.

**Confidence.** **Almost certain (90-99%)** for the recorded smoke-test instance because the retained
adapter gives the child exit, apparent success latency, missing output file, and exact masking
command (`codex.md:56-58`). The original runner script is not in the bundle, so its complete command
sequence is UNVERIFIED; replay an inert exit-1 child through the archived runner to settle it.

### Rank 8 — a backgrounding wrapper severs prompt stdin

**Observed instance.** The synchronous adapter records that wrapping `codex … - < prompt.txt` in the
existing `longrun` as-is backgrounds the child, so the redirect does not reach Codex and it exits
with “No prompt provided via stdin” (`claude/agents/codex.md:50-54`).

**Mechanism.** A wrapper changes file-descriptor ownership while preserving command-looking syntax.
The parent believes it staged a prompt correctly; the actual child receives an empty input channel.

**Detection signal.** The launcher fixture uses a nonce-bearing prompt and requires that nonce in a
captured invocation/result fixture; operationally, place the redirect inside the script executed by
the wrapper or invoke synchronously. Empty final file plus the exact diagnostic is
`TRANSPORT_REJECTED`, not an agent result.

**Confidence.** **Almost certain (90-99%)** for the retained rail test because the adapter records the
wrapper behavior and exact child diagnostic (`codex.md:50-54`). Whether a newer `longrun` version has
changed descriptor handling is UNVERIFIED; a no-model child process that echoes stdin through the
installed Windows wrapper settles current behavior.

### Rank 9 — provider/model/config admission rejects the request before reasoning

**Observed instances.** The corpus records one unsupported ChatGPT-account model error and one
`agents.max_threads`/`multi_agent_v2` incompatibility for `mcp__codex__codex`
(`corpus.json:9421-9427`). The newer adapter says `gpt-5.4-codex` returned HTTP 400 on this account and
records a configuration-selected replacement (`claude/agents/codex.md:38-43`).

**Mechanism.** A router treats a documented or guessed model/configuration as usable without an
account- and runtime-specific admission preflight. No model work occurs, but an untyped adapter can
surface this as empty or hollow output.

**Detection signal.** Before a production wave, run one bounded capability preflight through the
exact noninteractive route and persist the accepted model/config hash. Admission errors become typed
`TRANSPORT_REJECTED:model` or `TRANSPORT_REJECTED:config`; they never enter quality scoring.

**Confidence.** **Almost certain (90-99%)** for the two corpus fingerprints because the corpus parsed
11,633 files with zero file failures (`corpus.json:2-11`) and retains the exact error classes
(`:9421-9427`). The replacement model's continuing availability is temporally unstable and
UNVERIFIED; the settling experiment is a `codex exec` capability/admission smoke through the exact
account immediately before a wave, without hard-coding the historical slug.

## Structural fix

### Proposal 1 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): one fail-closed WorkUnit result schema and reducer

Add one provider-neutral result object and one deterministic validator/reducer to the existing
shared harness. Do not add another orchestration runtime.

Minimum envelope:

```json
{
  "schema_version": 1,
  "work_unit_id": "immutable caller-minted id",
  "attempt": 1,
  "provider": "claude|codex|gemini|local|ci",
  "state": "SUCCESS|FAILED|PARTIAL",
  "result_channel": "final-message-file|native-result|artifact",
  "artifacts": [
    {"path": "root-relative", "sha256": "...", "bytes": 123, "role": "deliverable"}
  ],
  "evidence": [
    {"kind": "file-line|url|command-receipt", "value": "..."}
  ],
  "postconditions": [
    {"id": "caller-declared", "receipt_path": "...", "status": "pass|fail"}
  ],
  "gaps": [],
  "diagnostic": null
}
```

Reducer invariant:

```text
DELIVERED = correlated terminal transport
         AND schema-valid final result
         AND artifact manifest nonempty when a deliverable was contracted
         AND every manifest entry resolves inside the pinned root
         AND every entry exists, is nonempty, and matches digest/bytes
         AND every caller-declared postcondition has a fresh passing receipt
```

The caller, not the child, computes or independently re-computes artifact digests and postconditions.
The child may propose paths and receipts, but cannot self-certify delivery. A `FAILED` envelope is a
valid terminal handoff, not a delivered success. Any raw string, job id, progress channel, missing
work-unit id, duplicate id, missing artifact, or invalid schema fails closed into a typed diagnostic.

This proposal is **very likely (80-90%)** to eliminate the observed false-success and lost-result
classes because every observed substitute—start receipt, progress prefix, exit code, digest prose,
and bare terminal marker—fails at least one reducer conjunct. Evidence: the local synchronous adapter
already implements the Codex-specific subset of exit-zero + output file + schema + postconditions
(`/local_disk0/codexwork/bundle/claude/agents/codex.md:63-97`), and the official CLI exposes explicit
final-file and schema channels. The remaining uncertainty is enforcement placement across every
provider boundary. **UNVERIFIED — whether all provider lifecycle events expose enough data to block
fan-in synchronously.** The settling experiment is an offline trace fixture for Claude, Codex, and
Workflow completion events followed by one live cache-disabled two-child workflow; if a hook cannot
block, put the same reducer in the Workflow fan-in function and use the hook only for ledgering.

### Proposal 2 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): replace lexical terminal acceptance with semantic validation

Change `SubagentLifecycleModule._on_stop` so `_TERMINAL` is only a parser entry condition, never an
allow condition. Parse the WorkUnit envelope; validate identity, state, manifest, and postconditions;
then allow. Keep a compatibility lane for explicitly non-artifact advisory tasks, but require their
schema to declare `deliverable_kind: advisory` plus evidence anchors and a caller-defined done signal.
Add negative fixtures for:

- `SUCCESS:review` only;
- long plausible prose naming nonexistent files;
- schema-valid result with the wrong `work_unit_id`;
- exit 0 with missing/empty final-message file;
- final message while job state remains running;
- duplicate/late result from attempt 1 after attempt 2 began;
- real file with wrong digest;
- real artifact with failing behavioral postcondition;
- `FAILED:` with diagnostics (terminal but not success).

This proposal is **almost certain (90-99%)** to close the currently tested bare-marker bypass because
the exact weak branch and test are visible (`modules.py:2384-2396`; `test_modules.py:1005-1020`). It
does not by itself fix wrappers that never reach `SubagentStop`; those must invoke the common reducer
at their own fan-in boundary.

### Proposal 3 — CONFIG (settings/JSON only): route critical-path Codex work away from the failing MCP/background path to the existing synchronous adapter

Where routing is expressible in the existing agent/workflow configuration, select the already-built
`claude/agents/codex.md` adapter for artifact-producing work units and reserve rescue/background/MCP
routes for advisory exploration until they emit the same WorkUnit envelope. The adapter already
blocks, stages prompt/schema on disk, writes a final-message file, validates the schema, verifies
postconditions, and returns a terminal taxonomy (`claude/agents/codex.md:8-36,63-109`). Current
official Codex guidance independently supports stdin, `-o`, `--output-schema`, and
`--ignore-user-config` for controlled automation.

This is **very likely (80-90%)** to reduce immediate cross-vendor delivery failures because it removes
the exact job-store/session-filter/progress-stream route implicated by the incident
(`cross-vendor-dispatch.md:7-30`) while reusing an existing adapter. **UNVERIFIED — whether every
current workflow can choose this agent through settings/JSON alone.** The settling experiment is a
read-only route inventory of all Codex launch call sites followed by configuration diff generation;
any call site requiring source edits moves from CONFIG to BUILD-SMALL rather than stretching this tag.

### Proposal 4 — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): task-scoped delivery ledger and orphan reconciliation

Persist one append-only transition per `work_unit_id`/attempt on the existing ledger:
`ACCEPTED → RUNNING → RESULT_READY → VALIDATING → DELIVERED`, with terminal alternatives
`FAILED`, `SEVERED`, `TIMEOUT`, `ORPHANED`, and `PARTIAL`. On fan-in, assert exactly one terminal
attempt, reject late superseded results, and reconcile every launch to a result/artifact. Use the
work-unit id as the address; session id is metadata, never the retrieval key. This directly prevents
the observed `sessionId:null` result loss (`cross-vendor-dispatch.md:15-17`).

This is **very likely (80-90%)** to make lost completed results detectable and retrievable because it
removes the mismatched session lookup from the identity invariant. **UNVERIFIED — the existing ledger's
current uniqueness/concurrency guarantees under cross-process writers.** The settling experiment is
a 50-way offline append/reconcile fixture with duplicate and out-of-order transitions using a
temporary state root, followed by one Windows two-process smoke test.

on the existing test bus should include:

| severed stream | exit 0 | no final file | none | none | `SEVERED` |
| progress masquerade | returned but stored running | stderr prefix | none | none | `SEVERED`/`RUNNING` |
| plausible digest | terminal 0 | schema-invalid prose | missing | none | `FAILED:schema-invalid` |

| stale prior attempt | terminal 0 | id attempt=1 | valid old artifact | pass | `SUPERSEDED`, not delivered |
| advisory result | terminal 0 | advisory schema valid | intentionally empty | evidence check passes | `DELIVERED` advisory |
| honest failure | terminal nonzero/failed | typed diagnostic | partial optional | fail | terminal `FAILED`, barrier releases as failure |

Acceptance is not “tests pass” alone. Require two mechanically independent signals for each golden
case: reducer state plus actual filesystem/postcondition state. For the historical regression, replay
the three raw `wf_82c5b350-9ba` child traces and require `0/3` false `DELIVERED`; then run a known-good
Codex fixture and require `1/1 DELIVERED` so a detector that rejects everything cannot pass.

## Expected-damage rationale

1. **False `DELIVERED` with missing artifacts** can silently contaminate synthesis, decisions, or
   code integration. It is ranked first even if rare.
2. **Completed but unreachable work** silently omits evidence while appearing dispatched; it can
   bias a cross-vendor comparison and waste the full run cost.
3. **Progress mistaken for final output** can inject incomplete or operational text into downstream
   reasoning and release a barrier early.
4. **Hollow terminal-prefix acceptance** is an always-present bypass that permits the first three
   classes to evade the generic lifecycle warning.
5. **Argument-limit/launch rejection** wastes time but is normally loud and leaves no false artifact;
   it ranks below silent corruption.
6. **Timeout and thread-address errors** are common and costly, but the retained corpus fingerprints
   are loud. Their highest damage occurs only when another defect converts them into false success or
   background result loss.
7. **Exit masking** can become false success, but the result-file AND-gate catches it cheaply and the
   retained instance failed in seven seconds.
8. **Prompt stdin loss** is a loud pre-reasoning rejection once stderr and final-file absence are
   classified correctly.
9. **Model/config admission rejection** is loud, fast, and capability-specific; it corrupts quality
   conclusions only if the harness mislabels it as model work.

The ranking is **very likely (80-90%)** to match expected damage in this harness because the owner
explicitly values correct autonomous conclusions and because missing work can be propagated without
an immediate error, whereas `os error 206`, timeout, and unsupported-model failures are explicit.
**UNVERIFIED — monetary/token/time loss per class.** The settling experiment is to join each
work-unit transition to elapsed time, tokens, retry count, downstream citations, and user correction,
then estimate `P(failure) × downstream blast radius × recovery cost`.

## Anti-overfit gate

All four proposals ride existing native CLI output, Agent/Workflow, shared dispatcher, ledger, hook,
skill, MCP, and test buses. They do **not** introduce a second orchestration runtime, vector database
or knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail
framework. The state reducer is a small validation function and ledger vocabulary, not a scheduler or
daemon. Provider-specific adapters remain thin marshalling layers; the delivery invariant is shared.

A BUILD-LARGE daemon/service/runtime is not justified by this evidence. The observed problems are
misclassified states, missing correlation, and missing postcondition checks—not lack of a scheduler.
The existing synchronous adapter demonstrates the core solution in one path
(`claude/agents/codex.md:63-97`), and current official Codex output channels supply the native raw
signals. Adding durable execution would multiply recovery and identity semantics before the current
ones are made correct.

## Alternatives rejected

1. **“Use only Claude.”** Rejected: it hides an adapter defect and discards cross-vendor value
   without testing model capability. The incident itself says Codex quality was never exercised
   (`cross-vendor-dispatch.md:3-5`).
2. **“Retry the same Codex call.”** Rejected: retries cannot make an overlong argv shorter, repair a
   null addressing key, or turn progress into a final result. They may duplicate writes.
3. **“Require `SUCCESS:`.”** Rejected: the current shared code already does that, and the test proves
   a hollow `SUCCESS:review` passes (`modules.py:2384-2396`; `test_modules.py:1005-1020`).
4. **“Check exit code 0.”** Rejected: the incident explicitly records foreground return/progress
   without logical completion (`cross-vendor-dispatch.md:19-30`).
5. **“Check file existence.”** Rejected as a sole gate: a write-early, stale, empty, or unrelated file
   can exist. Require identity, hash/bytes, freshness, and a behavioral postcondition.
6. **“Make everything synchronous forever.”** Rejected as the general solution: sync avoids one
   addressing failure but not severed streams, hollow results, lying manifests, or invalid artifacts.
   Synchronous direct execution is the immediate safe route; the WorkUnit reducer is the invariant.
7. **“Add a durable workflow service.”** Rejected by the anti-overfit gate. The existing buses already
   expose enough signals for a small reducer; no evidence shows a missing scheduler caused the
   incident.
8. **“Trust three agreeing agents.”** Rejected: the fan-out contract reports 3/3 plausible nonexistent
   artifacts (`fan-out-contract.md:70-71`), and the single-signal rule states N agents reading the same
   stale input remain one lens
   (`/local_disk0/codexwork/bundle/claude/rules/common/single-signal-verification.md:31-37`).

## Bottom line

The incident is not “three Codex agents were bad.” It is “three work units crossed a boundary whose
success type was weaker than its delivery obligation.” The adapter allowed acknowledgements,
progress, prose, or transport termination to impersonate verified delivery. The provider-neutral
harness still contains the same flaw in miniature by accepting a bare terminal prefix.

Make `DELIVERED` a computed state, never a child-authored word. Compute it once in a small shared
reducer from correlated terminal state + schema-valid final result + artifact manifest + independent
postcondition receipts, and make every fan-in path use it. That is the smallest mechanism that closes
all observed holes and generalises to every vendor, subprocess, MCP, workflow, and remote worker
without adding a second runtime.
