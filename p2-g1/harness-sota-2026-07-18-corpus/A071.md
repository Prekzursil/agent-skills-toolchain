### C01 — TypeScript syntax guidance leaks into JavaScript scope

**Class: STALE**

**Artifacts and exact lines**

* `claude/rules/typescript/coding-style.md:2-6`: the file applies to `*.js` and `*.jsx` as well as
  TypeScript.
* `claude/rules/typescript/coding-style.md:18-20`: “Add parameter and return types to exported
  functions…” without restricting that imperative to `.ts`/`.tsx`.
* `claude/rules/typescript/coding-style.md:23-37`: the only immediate example uses TypeScript
  annotations.
* `claude/rules/typescript/coding-style.md:101-104`: only 80 lines later does the JavaScript section
  say to use JSDoc when helpful.
* `inputs/corpus.json:5265-5276`: 15 observed workflow parse failures say plain JavaScript received
  TypeScript annotations/interfaces/generics.
* The same fingerprint accounts for 15 of 32 Workflow errors at
  `inputs/corpus.json:9369-9377`.

**Why this collides**

The file-level scope and early imperative make annotation syntax appear applicable to JavaScript;
the late JSDoc paragraph supplies a different mechanism but never explicitly retracts the earlier
instruction for `.js`/`.jsx`. The corpus does not prove this rule caused all 15 failures, because
workflow tool scripts are not necessarily file edits that loaded this path-scoped rule. It does prove
that this exact category error recurs in real harness behavior.

General causality is **UNVERIFIED; the settling experiment is an A/B replay of the 15 recorded
workflow prompts with the current combined rule versus split TS-only and JS-only rule text, measuring
parse failures**. It is **likely (55-80%)** that the ambiguous combined wording contributes to the
same model error elsewhere, because the rule applies to JS and leads with annotation-only examples,
while the corpus independently shows 15 instances of that confusion.

**Resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**
Split the obligation explicitly: `.ts/.tsx` exported APIs get TypeScript annotations; `.js/.jsx`
public APIs get JSDoc only when it adds value. Put that distinction before the first example, and use
one TS and one JS example. This is a small rule-bus edit, not a new runtime.

### C03 — immutability is duplicated at two strengths

**Resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

### C04 — error handling is duplicated, and the example discards causal structure

**Class: REDUNDANCY**

**Artifacts and exact lines**

* Target `claude/rules/typescript/coding-style.md:141-175`: prescribes async/await with try/catch,
  logs the caught value, then throws `new Error(getErrorMessage(error))`.
* `claude/rules/common/coding-style.md:43-49`: comprehensively handle errors, log detailed server
  context, and never swallow them.
* `claude/rules/common/code-review.md:49-55,113-119`: requires explicit error handling.

**Why this collides**

The obligations repeat, but the TS example replaces the original error and stack relationship
without `cause`. That is weaker than “detailed error context” once the error crosses the local logger
boundary. The higher-level text does not require try/catch around every awaited call. It is **likely
(55-80%)** that the target’s unqualified heading encourages catch-and-rethrow boilerplate, because
its sole directive says “Use async/await with try-catch” and its sole example catches and rethrows.

**Resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**
State when to catch: recover, translate at a boundary, or add context. Otherwise allow propagation.
When translating, use `new Error(message, { cause: error })` on supported targets or preserve the
cause equivalently. Cross-link the common rule. It is **very likely (80-90%)** this preserves more
diagnostic information, because the cause is explicitly retained instead of replaced; evidence is
the current throw at target line 173.

### C09 — the rule forbids the hook protocol’s documented output mechanism

**Class: CONTRADICTION**

**Artifacts and exact lines**

* Target `claude/rules/typescript/coding-style.md:195-199`: no production `console.log`; use a logging
  library instead.
* `claude/hooks/README.md:90-115`: the documented JavaScript hook protocol reads stdin, warns on
  stderr, and uses `console.log(data)` to emit protocol output on stdout.
* The same README says hooks receive JSON on stdin and output JSON on stdout (`:90-93`).

**Why this collides**

For a production hook, stdout is a machine protocol, not diagnostic logging. It is **very likely
(80-90%)** that blindly replacing it with a conventional logging library corrupts the hook channel
or sends output to the wrong sink, because the documented contract requires JSON on stdout while
logging libraries commonly target stderr or add formatting. Neither artifact states this exception,
so a literal style review flags the required protocol implementation.

**Resolution — NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**
Rename the rule section “Diagnostic console output” and exempt deliberate CLI/protocol stdout.
Recommend `process.stdout.write` for protocol payloads to separate semantics from logging. It is
**very likely (80-90%)** that the exception prevents incorrect autofixes because the README explicitly
requires stdout JSON and currently demonstrates `console.log` as that transport.
