# T013 — Competitive teardown: JetBrains Junie

**Research date:** 2026-07-19 UTC  
**Scope:** Junie IDE/AI Chat, Junie CLI, and the official GitHub automation surface, compared with the unpacked Claude/Codex harness.  
**Subject policy:** read-only. I wrote only this artifact.  
**Primary-source policy:** JetBrains product documentation, JetBrains release posts, and JetBrains Marketplace release notes. Junie's agent implementation is not published in the material reviewed, so product behavior that the documentation does not specify is not reverse-inferred.

## Executive verdict

Junie is no longer merely an IDE plug-in with a plan pane. As of the July 2026 documentation, it is one agent engine presented through IDE/AI Chat, a standalone CLI, headless CI, GitHub/GitLab, and remote control. Its competitive advantage is the *composition* of native IDE intelligence, plan approval, permission prompts, resumable sessions, debugger control, focused review, skills, hooks, MCP, subagents, and worktrees into one coherent operator surface. The June 2026 GA announcement says the IDE integration was rebuilt on ACP and that the same engine sits behind AI Chat, the Junie tool window, and CLI ([GA announcement](https://blog.jetbrains.com/junie/2026/06/junie-coding-agent-out-of-beta/)).

Our harness is broader and, in several places, more sophisticated. It already has hundreds of skills, custom agents with model/tool/memory declarations, command prompts, Claude and Codex hooks, plugins/marketplaces, MCP routing, persistent memory, review agents, fan-out, and worktree automation. The corpus measured 78 invoked skills, 22 invoked agent types, and 93 MCP servers touched; the live configuration enables Claude agent teams and Codex multi-agent operation (`/local_disk0/codexwork/bundle/claude/settings.json:4-18`; `/local_disk0/codexwork/bundle/codex/config.toml:77-127`). Junie therefore does **not** justify replacement of the harness.

The radical but evidence-backed conclusion is narrower: retain Claude/Codex as the agent runtimes and replace several fragile *cross-cutting wrappers* with native lifecycle mechanisms or small adapters patterned after Junie. In priority order:

1. Quarantine disconnected MCP servers from the model-visible tool surface, instead of merely warning after selection.
2. Replace the current global bypass/full-access defaults with narrow, persistent action rules and explicit escalation.
3. Expose the JetBrains IDE's semantic navigation, configured test runners, and debugger through the existing MCP bus where a compatible IDE is already running.
4. Replace the faulty machine-global worktree selector with session-scoped, repository-derived worktree selection and visible task state.
5. Turn completion checks into bounded Stop-gate retries with durable receipts.

Those ports ride existing MCP, hook, agent, and configuration buses. None requires a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 1. Agent loop

### What Junie concretely does

In IDE code mode, Junie breaks the task into a multistep plan, reports progress, runs terminal commands, creates/edits files, runs tests, and verifies changes. At completion the user can follow up, keep the changes, or roll everything back. Ask mode is read-only. Auto mode chooses between modes ([IDE plug-in documentation](https://junie.jetbrains.com/docs/junie-ide-plugin.html)).

CLI plan mode is a stronger, explicit state machine:

```text
prompt
  -> read-only repository/context exploration
  -> living Markdown plan
       requirements
       technical design
       testing
       delivery steps
  -> pause for human decision
       confirm and implement | revise | save and stop
  -> implementation
  -> tests/build/verification
  -> Stop gates
  -> completion/review
```

The official plan-mode page states that exploration is read-only, the plan is updated when requirements change, and implementation begins only after confirmation. It saves a plan file and provides a dedicated plan view ([Plan mode](https://junie.jetbrains.com/docs/junie-cli-plan-mode.html)). CLI also accepts real-time follow-up prompts while work is running, appending clarifications immediately rather than requiring a restart ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html)).

The exact inner loop—whether it is ReAct-like, plan-and-execute, a fixed controller, or model-dependent—is **UNVERIFIED; the settling experiment is the full trace capture described in the evidence boundary.** The *documented observable* controller has plan, execution, permission, tool, verification, stop, and resume phases; each has a documented operator or hook transition.

### Comparison with ours

Our Claude `/plan` is a prompt-level convention: it tells a planner agent to restate requirements, assess risks, write phases, and wait for confirmation (`/local_disk0/codexwork/bundle/claude/commands/plan.md:1-34,94-115`). Codex has native plan mode configured at ultra reasoning effort (`/local_disk0/codexwork/bundle/codex/config.toml:1-6`). Thus the underlying capability exists, but a shared cross-provider, durable plan artifact with explicit state transitions is **UNVERIFIED as absent; the settling experiment is to run one Claude and one Codex plan task, inspect session artifacts for a versioned plan file and enforced read-only-to-write transition, and then verify that a revised requirement mutates that same artifact.** Static evidence only establishes that Claude's checked-in command is prose while Junie's plan is a host-managed file and pause state.

### Port proposal — shared plan artifact and transition contract — **UNVERIFIED**

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Define one Markdown plan schema (`requirements`, `decisions`, `affected surfaces`, `tests`, `delivery`) and a tiny state receipt (`draft|approved|implementing|verified`). Use the existing plan modes for generation; a `PreToolUse` hook blocks writes only while state is `draft`; approval changes the receipt; `Stop` checks that required tests/verification receipts exist. Do not add an orchestrator.

This is **likely (55-80%)** to reduce implementation-before-alignment errors because Junie enforces a host pause and living artifact, while ours demonstrably relies on prompt wording on the Claude side. The evidence is Junie's plan transition documentation and our command at `commands/plan.md:94-101`; the uncertainty is whether Codex already provides enough shared artifact semantics. The settling experiment is the cross-provider plan test immediately above, followed by a 20-task A/B measuring user redirections after the first write.

## 2. Context management

### Junie's context surfaces

Junie combines several layers:

1. **Explicit attachment.** `@` attaches project files/directories; drag-and-drop supports files and images ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html)).
2. **IDE working context.** The IDE integration supplies the open file, selection, recent build/test activity, project structure, and configured run/test setup. Semantic navigation and refactoring use the IDE index rather than line-by-line scanning ([IDE connection announcement](https://blog.jetbrains.com/junie/2026/04/junie-cli-inside-your-jb-ide/)).
3. **Semantic indexing.** IDE project settings expose optional semantic indexing based on embeddings ([Project settings](https://junie.jetbrains.com/docs/junie-plugin-project-settings.html)).
4. **Persistent instructions.** Global and project AGENTS.md content is injected into every task, with project precedence and exact-content deduplication ([Guidelines and memory](https://junie.jetbrains.com/docs/guidelines-and-memory.html)).
5. **Progressive skills.** Junie exposes skill names/descriptions first and loads the full `SKILL.md` and referenced materials only when relevant ([Agent skills](https://junie.jetbrains.com/docs/agent-skills.html)).
6. **Session context and compaction.** CLI stores full session context and usage for the last ten sessions and exposes resumable history. Hooks reveal a `SessionStart(source=compact)` event, proving that history compaction occurs; the representation and selection policy are not documented ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html), [Hooks](https://junie.jetbrains.com/docs/junie-cli-hooks.html)).
7. **Subagent isolation.** A delegated subtask runs in its own context and returns a result, keeping its working context out of the main conversation ([Custom subagents](https://junie.jetbrains.com/docs/junie-cli-subagents.html)).

Junie's internal relevance ranking, token budget allocation, summary faithfulness, and compaction trigger are **UNVERIFIED; the settling experiment is a long-task trace with known planted constraints before and after compaction, measuring retention, selected files, and task success.**

### Comparison with ours

Our configuration already uses progressive skill discovery (`skillListingBudgetFraction: 0.02`, `/local_disk0/codexwork/bundle/claude/settings.json:1-4`), a 360-item local embedding router (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/index/meta.json:1`), native Codex history and compression (`/local_disk0/codexwork/bundle/codex/config.toml:39-50,115`), and a more elaborate recall/memory layer. Audit D05 claims the live recall index is stale schema v1, the 90% compaction cliff is not calibrated, and post-compact context is routed incorrectly (`/local_disk0/codexwork/bundle/inputs/audit-findings/D05.md:1-12,73-105`). Those are claims, but the explicit `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=90` is independently visible at `settings.json:18`.

Junie's IDE semantic index is a real advantage for symbol-aware rename, overload resolution, configured test selection, and navigation. It is not evidence that a new standalone embedding store improves this harness. In fact, the owner's anti-overfit gate rejects vector-DB/KG memory, and our local router already demonstrates that another index can become another lifecycle obligation.

### Port proposal — IDE intelligence as an optional tool provider

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** When a compatible JetBrains IDE is running, connect its bundled MCP server to the existing MCP configuration and expose only semantic navigation, refactoring preview, configured test/build execution, and debugger tools. Do not copy the IDE index into harness memory; query it as the authoritative live tool. The official setup uses a local streamable-HTTP MCP endpoint and selectable exposed tools ([Junie/AI Assistant documentation](https://www.jetbrains.com/help/ai-assistant/junie-agent.html)).

This is **very likely (80-90%)** to reduce text-search and guessed-test-command failures on IDE-managed JVM/.NET projects because JetBrains documents direct use of the same semantic index and run configurations the user uses. The local benefit outside supported JetBrains projects is **unlikely (20-45%)**, because there may be no compatible IDE/index. Evidence: JetBrains' IDE connection documentation; settling experiment: a symbol rename with overload/name collisions plus a monorepo test run, compared against current Glob/Grep/shell behavior.

### What not to copy: a second semantic memory/index service

There is no proposal tag because this is a rejection, not a proposal. A new vector database or KG would violate the anti-overfit gate and duplicate both the IDE index and existing recall infrastructure. Prefer live, authoritative IDE queries and repair the existing compact/recall path.

## 3. Memory

JetBrains labels its page “Guidelines and memory,” but the documented durable mechanism is instruction files, imported agent instruction/memory files, prompt history, and session resumption. Global `~/.junie/AGENTS.md` and project `.junie/AGENTS.md` are merged with project precedence and deduplicated when identical ([Guidelines and memory](https://junie.jetbrains.com/docs/guidelines-and-memory.html)). CLI preserves prompt history across runs and full context for the last ten sessions ([CLI quickstart](https://junie.jetbrains.com/docs/junie-cli.html)).

A distinct Junie mechanism that autonomously extracts learned facts/preferences into durable cross-project memory is **UNVERIFIED; the settling experiment is to teach a novel preference without editing AGENTS.md, exit, start an eleventh session and a different project, and inspect both behavior and new files under `~/.junie` while controlling for imported instructions.** Two documentation signals constrain the claim—the memory page describes AGENTS.md rather than learned records, and quickstart specifies a ten-session history window—but documentation silence is not proof of absence.

Our memory is more ambitious: the corpus records 1,332 `basic-memory` server uses, including hundreds of write/search/read operations, and Codex enables native memories (`/local_disk0/codexwork/bundle/codex/config.toml:101-115`; audit D05 points to the detailed memory settings at its lines 91-98). The price is more failure modes. The liveness hook itself says it was built after a documented four-hour silent memory loss and probes only configured critical services (`/local_disk0/codexwork/bundle/claude/hooks/mcp-liveness/liveness.py:1-28`).

### Verdict

Junie's conservative file/session memory is **worse for durable cross-project recall** than our intended design, but **likely (55-80%)** easier to reason about because its documented durable state is limited to inspectable instruction files and a bounded session history. Do not replace basic-memory with Junie-style “memory.” Repair provenance, liveness, compaction, and duplicate-writer policy. A recommendation to simplify to AGENTS.md plus session history alone would be **UNVERIFIED; the settling experiment is a 30-task cross-session recall evaluation comparing success, stale recall, provenance, and operator correction with basic-memory on versus off.**

## 4. Tool and MCP handling

### Junie

Junie can automatically select relevant tools from configured MCP servers or users can request them manually. IDE configuration shows server status and connection errors and lets the user expand a server to inspect available tools. It supports at most 100 tools across configured servers ([IDE plug-in documentation](https://junie.jetbrains.com/docs/junie-ide-plugin.html)). CLI provides `/mcp`, project/user MCP locations, imports configurations from other agents, and extensions can bundle MCP configs ([Slash commands](https://junie.jetbrains.com/docs/slash-commands.html), [Extensions](https://junie.jetbrains.com/docs/junie-cli-extensions.html)). GitHub Action exposes preconfigured MCP servers for failed checks and inline review comments and allows an explicit `allowed_mcp_servers` list ([GitHub Action](https://junie.jetbrains.com/docs/junie-on-github.html)).

Debugger mode is implemented through MCP toolsets: breakpoints, stepping, call stacks, threads/frames, runtime variables, and expression evaluation are exposed by the IDE's Debugger MCP Toolset ([Junie agent documentation](https://www.jetbrains.com/help/ai-assistant/junie-agent.html)). This is a strong mechanism: convert high-value structured IDE operations into normal tools instead of teaching the model to synthesize brittle shell/debugger commands.

### Local gap: a dead MCP remains model-visible

This is established by two mechanically independent signals:

1. Corpus execution data: `mcp__claude_ai_Tavily__tavily_search` made 194 calls and failed 139 times (71.65%), all top failures saying the server was not connected; Tavily extract made 532 calls with 137 errors. The pinned aggregate combines these into the stated 532-call/25.8% family ranking.
2. Configuration/source scope: the MCP liveness config contains only `basic-memory` under `critical` and registered reverse-engineering daemons (`/local_disk0/codexwork/bundle/claude/hooks/mcp-liveness/critical.json:1-20`). Its implementation is deliberately inject-only/fail-open and warns the agent rather than removing a server from the tool surface (`liveness.py:9-28`).

The detector control is known-present: the same source search found `basic-memory`, and the corpus found extensive healthy basic-memory calls, so this is not a zero-result detector.

### Port proposal — MCP health quarantine and circuit breaker

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing liveness registry from “critical daemons only” to every enabled MCP transport. At session start perform a protocol-level initialize/list-tools probe. Maintain a small session-scoped state table: `healthy`, `open` (quarantined), `half-open`, `disabled`. After a connection-class failure, hide or deny that server's tools and inject one terse alternative; after a cooldown, perform one half-open probe. Re-enable only on a successful handshake. Never retry a disconnected server 135 times.

This is **almost certain (90-99%)** to eliminate repeated “not connected” calls for servers the preflight correctly identifies because quarantine removes the failed choice from the action surface. Evidence is the 139 identical Tavily search failures plus Junie's visible connection-status mechanism. It is **likely (55-80%)** to reduce overall MCP error rate because non-connection errors remain. Settling experiment: replay a task with one deliberately dead and one healthy MCP, verify zero model calls to the dead server after one probe, and prove the detector can still list/call the healthy control.

### What is worse in Junie MCP handling

* The 100-tool maximum is an arbitrary product ceiling, not semantic routing. Blindly copying the cap is **likely (55-80%)** to hide at least some needed specialized tools in MCP-heavy tasks while still permitting many irrelevant ones, because our corpus touched 93 servers and tool relevance varies by task. The settling experiment is a stratified task replay comparing fixed-cap, health-filtered, and relevance-scoped exposure. Prefer health plus task-scoped exposure.
* The IDE Action Allowlist documentation says one MCP rule currently authorizes **all** MCP tools; server/tool-specific approval is not possible there ([Action Allowlist](https://junie.jetbrains.com/docs/action-allowlist.html)). CLI `allowlist.json` is finer and can match MCP server prefixes ([CLI Action Allowlist](https://junie.jetbrains.com/docs/action-allowlist-junie-cli.html)). This IDE/CLI policy split is a weakness.
* The older dedicated plug-in documentation says secrets in MCP configs are unsupported and suggests environment-file wrappers ([IDE plug-in documentation](https://junie.jetbrains.com/docs/junie-ide-plugin.html)). Secret handling across newer AI Chat/CLI is **UNVERIFIED; the settling experiment is to configure OAuth and environment-backed servers on each surface and inspect persisted config/logs without exposing secret values.**

## 5. Permission model

### Junie

Junie classifies actions as safe or sensitive. Project reads/edits are generally safe; most terminal commands, MCP calls, outside-project reads/writes, build-script edits, builds/tests/previews can require approval. Brave mode has Off, Auto (classifies safe terminal commands), and On (all sensitive actions execute). “Always allow” persists a rule. CLI rules are ordered first-match `prefix` or glob `pattern` entries with `allow|ask` actions for file editing, executables, MCP tools, and reads outside project ([CLI Action Allowlist](https://junie.jetbrains.com/docs/action-allowlist-junie-cli.html)). IDE rules support exact or regex terminal commands and action types ([Action Allowlist](https://junie.jetbrains.com/docs/action-allowlist.html)).

Project-local hook commands are ignored by default; only user hooks or explicitly passed config files run. This is an excellent trust-boundary decision because a checked-out repository cannot silently install executable lifecycle code ([Hooks](https://junie.jetbrains.com/docs/junie-cli-hooks.html)).

`.aiignore` is not a sandbox. Junie asks before reading/editing matched content, but filenames remain visible; Brave mode and an allowed command can still access ignored files ([IDE plug-in documentation](https://junie.jetbrains.com/docs/junie-ide-plugin.html)).

### Our current defaults are materially worse

Two independent provider configurations establish the condition:

* Claude sets a broad allowlist including `Bash`, writes, web, tasks, and many MCP namespaces, has an empty ask list, uses `defaultMode: bypassPermissions`, and adds entire `C:` and `D:` drives (`/local_disk0/codexwork/bundle/claude/settings.json:26-75`).
* Codex sets `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`/local_disk0/codexwork/bundle/codex/config.toml:1-8`).

The known-present control succeeds: both configurations contain explicit permission/sandbox keys, so the finding is not based on a detector that failed to locate policy.

### Port proposal — least-authority defaults with persistent narrow rules

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Set default execution to workspace-scoped writes and approval for commands with external effects, credentials, outside-project access, package installation, deployment, destructive Git, and consequential MCP calls. Preserve exact read-only commands as native allow rules. Separate research/web lanes from write/PR lanes. Use existing provider-native permission configuration; do not create a guardrail framework.

This is **almost certain (90-99%)** to reduce the blast radius of a mistaken or prompt-injected action because both current providers are explicitly unrestricted and the proposed controls are enforced by their native permission/sandbox layers. It is **likely (55-80%)** to add approval friction until the narrow allowlist is tuned. Settling experiment: a canary week measuring prompt count and denied/allowed actions, with fixtures for safe reads, project edits, outside-project writes, chained shell commands, credential reads, package installs, and destructive Git.

### Port proposal — repository hooks remain inert unless explicitly trusted

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** During config reconciliation, refuse to execute hook commands sourced from a repository unless the user explicitly activates that exact config path or hash. User-owned hooks continue normally. Record source and hash in hook telemetry.

This is **very likely (80-90%)** to close a repository-to-host code-execution path without a new runtime because Junie already demonstrates the policy and our hook dispatcher already knows registration sources. Settling experiment: clone a fixture repo containing a project hook; prove it is visible but inert, then explicitly trust its hash and prove a known-safe marker hook fires.

### What not to copy

Do not treat `.aiignore` as confidentiality enforcement, do not copy Brave On as a normal operating default, and do not copy the IDE's “all MCP tools” approval granularity. Native OS/workspace restriction and server/tool-specific rules are stronger.

## 6. Customisation surface: rules, skills, hooks, commands, extensions

### Rules/guidelines

Junie reads `.junie/AGENTS.md`, root `AGENTS.md`, and legacy guidelines, plus global `~/.junie/AGENTS.md`. Project rules override global conflicts; identical content is deduplicated ([Guidelines and memory](https://junie.jetbrains.com/docs/guidelines-and-memory.html)). This is cleaner than silently concatenating everything, but narrower than our existing rules and injection machinery.

### Skills

Junie uses the open Agent Skills folder format: YAML-frontmatter `SKILL.md`, referenced files, templates, scripts, and progressive disclosure. It discovers project and user scopes and can import Cursor/Claude/Codex skills ([Agent skills](https://junie.jetbrains.com/docs/agent-skills.html)). We already have this primitive and substantially more inventory. The corpus finding—78 skills invoked out of roughly 355 installed—says our problem is selection, retirement, and measured utility, not lack of a skill format.

### Custom agents/subagents

Junie subagent Markdown supports name, description, allowed and disallowed tools, MCP server allowlist, model, reasoning level, max turns, skills, and prompt argument. The main agent automatically matches descriptions and delegates independent work; Auto can choose a cheaper capable model, while SameModelOnly permits only same-model parallelism. It imports agent files from `.cursor/agents`, `.claude/agents`, and `.codex/agents` ([Custom subagents](https://junie.jetbrains.com/docs/junie-cli-subagents.html)). The feature is EAP.

Our agents already specify tools, model, effort, and memory—for example the code reviewer uses read/search/shell/report tools, `opus`, `xhigh`, and user memory (`/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:1-20`). Codex already supports eight-deep/eight-wide multi-agent operation (`config.toml:77-80,125-130`). Junie's notable lead is a productized per-agent MCP allowlist, max-turn cap, and auto cost tier.

### Hooks

Junie EAP hooks support `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `Stop`, `StopFailure`, `PermissionRequest`, and `SessionEnd`. `PreToolUse` can allow/ask/block, rewrite input, or inject context. `Stop` can feed a failure back for retry, hard-halt, and caps consecutive blocks at eight. Async hooks are advisory and queue context for the next prompt. Hook configs merge additively across trusted files ([Hooks](https://junie.jetbrains.com/docs/junie-cli-hooks.html)).

Our shared registration is broader: 16 lifecycle events including post-tool success/failure, compaction, config change, subagent/task lifecycle, and teammate idle (`/local_disk0/codexwork/bundle/agents/harness/registration.py:7-53`). Junie explicitly lacks `PostToolUseFailure` today and does not run hooks in ACP/server hosts; project hooks are safer, but event coverage is worse.

### Commands/extensions

Junie custom slash commands coexist with built-ins. Extensions bundle skills, MCP servers, subagents, commands, and guidelines. Marketplaces may be Git repositories, local directories, or direct manifests; Junie accepts its own marketplace format and Claude plug-in manifests. Project activation is committed in `.junie/extensions.json`, while content is cached once at user scope and becomes available without restart ([Extensions](https://junie.jetbrains.com/docs/junie-cli-extensions.html)).

We already have many commands and both Claude and Codex marketplaces (`/local_disk0/codexwork/bundle/claude/settings.json:607-652`; `/local_disk0/codexwork/bundle/codex/config.toml:397-402`). Junie's value is migration/interoperability and coherent activation, not a new packaging concept.

### Port proposal — add max-turn and MCP-scope fields to shared agent definitions

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend the existing agent frontmatter/launcher adapter with `maxTurns` and `mcpServers`; hide unlisted servers for that subagent and terminate with a structured incomplete result at the cap. Do not create a second scheduler.

This is **very likely (80-90%)** to reduce runaway delegated loops and credential/tool overexposure because it bounds both action count and tool surface at the existing delegation boundary. Evidence: Junie's documented fields; our current code-reviewer frontmatter lacks both (`code-reviewer.md:1-8`); audit C17 claims retry budgets are inconsistent/dormant (`/local_disk0/codexwork/bundle/inputs/audit-findings/C17.md:31-42`). Settling experiment: a looping fixture subagent and a forbidden-MCP fixture, across Claude and Codex.

### Port proposal — automated model-tier routing — **UNVERIFIED**

The main agent chooses only among benchmarked installed models; receipts record chosen model, tokens/cost, latency, and outcome. Avoid a trained router.

Our lack of equivalent automatic cost routing is **UNVERIFIED; the settling experiment is to inspect native Claude/Codex delegation traces and model-selection events across ten heterogeneous subtasks.** If absent, this port is **likely (55-80%)** to reduce cost without quality loss on well-separated repetitive tasks, based on Junie's Auto/SameModelOnly policy, but only local evaluation can identify safe task classes.

## 7. Multi-agent and parallel work

Junie has two distinct concurrency mechanisms:

1. **Subagent delegation:** the main agent automatically launches focused workers in separate contexts and collects results. EAP policy permits parallel independent work and model-tier selection ([Custom subagents](https://junie.jetbrains.com/docs/junie-cli-subagents.html)).
2. **Parallel live sessions:** `/new` leaves existing work running, `/history` shows `Working`, `Awaiting input`, `Ready`, or saved state, and `/worktree` creates/switches isolated sibling Git worktrees. It prevents two TUI processes from controlling the same live session. Uncommitted changes may be moved with stash; conflicts remain in stash ([Parallel sessions and worktrees](https://junie.jetbrains.com/docs/junie-cli-worktrees.html)).

Our raw orchestration is more capable, but operator state and isolation are less reliable. Audit B16 supplies two independent signals for a concrete defect: the worktree selector source prioritizes a machine-global hint, and a real PrimariRo task reported being assigned a Reframe checkout with zero changes (`/local_disk0/codexwork/bundle/inputs/audit-findings/B16.md:8-14`). The same audit documents successful correctly targeted worktrees at lines 56-62. The local registration confirms custom WorktreeCreate/Remove hooks (`/local_disk0/codexwork/bundle/agents/harness/registration.py:122-140`). This is exactly the pattern the owner wants: keep the proven isolation primitive, replace the faulty target selection.

Junie is worse in one respect: parallel sessions that share a directory can overwrite each other's changes, and isolation requires the operator to choose a worktree. Its docs acknowledge this. Our desired harness can automatically isolate write-capable subagents.

### Port proposal — repository-derived worktree/session control

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Resolve repository identity from the current session's actual working directory and `git rev-parse --show-toplevel`; never consult a machine-global first-choice hint. Present existing worktrees and task owner/status, create a collision-resistant sibling worktree, bind the worker to its path, and emit a completion receipt. If the directory is not a Git repository, do not pretend isolation exists.

This is **almost certain (90-99%)** to prevent the documented cross-repository misrouting class because it removes the global selector that caused it and derives identity from the task session. Evidence: B16's source/runtime pair and Junie's repository-local worktree menu. Settling experiment: launch concurrent tasks from two repositories and one umbrella directory, then verify each worker's `git rev-parse`, branch, changed files, and cleanup receipt.

### Port proposal — compact session-state view

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Build a TUI/command view over existing native collaboration and ledger events: task, repository/worktree, agent/model, `working|awaiting input|ready|failed|complete`, last activity, and completion receipt. Do not add a daemon; compute from existing session/ledger files and native agent APIs.

This is **likely (55-80%)** to reduce false “stalled/done” operator decisions because Junie's status model is explicit and local audit A38/B16 claims current monitoring misclassifies terminal states. The uncertainty is whether all required events are durably present, especially given known defect D3. Settling experiment: known-state fixtures for live, input-waiting, successful, failed, superseded, and partial-artifact sessions, with two independent terminal signals for each.

## 8. Verification and self-check mechanisms

### Junie layers

* Code mode can run tests and verify changes; IDE integration uses configured runners rather than guessing shell commands ([IDE plug-in documentation](https://junie.jetbrains.com/docs/junie-ide-plugin.html), [IDE connection announcement](https://blog.jetbrains.com/junie/2026/04/junie-cli-inside-your-jb-ide/)).
* Plan mode requires a Testing section and explicit confirmation before implementation ([Plan mode](https://junie.jetbrains.com/docs/junie-cli-plan-mode.html)).
* The dedicated review agent is a focused read-only subagent. It loads the requested diff, can read/search context, cannot edit/run/commit, follows guidelines and review skills, supports follow-ups, and exposes per-suggestion accept/dismiss controls ([Code review agent](https://junie.jetbrains.com/docs/junie-review-agent.html)).
* IDE Done panels show changed files and allow file-by-file revert, but Marketplace known issues warn that shell-command file operations can be missing from Done and line counts can be wrong ([Marketplace May 2026 notes](https://plugins.jetbrains.com/plugin/26104-junie-the-ai-coding-agent-by-jetbrains/versions/stable/1048916)).
* Stop hooks can block completion, feed test/check output back to the model, retry, or hard-halt. The default eight-block cap prevents an unbounded stop loop ([Hooks](https://junie.jetbrains.com/docs/junie-cli-hooks.html)).
* Debug mode can inspect actual runtime state rather than infer only from logs ([Junie agent documentation](https://www.jetbrains.com/help/ai-assistant/junie-agent.html)).
* GitHub automation creates reviewable branches/PRs and can inspect failed checks through a preconfigured MCP ([GitHub Action](https://junie.jetbrains.com/docs/junie-on-github.html)).

Junie does not document independent test-oracle generation, mutation testing, proof that claimed tests actually ran, or calibration of review false positives. Any claim that its self-check is independent is **UNVERIFIED; the settling experiment is to seed known defects and test failures, capture whether the same model both writes and approves, and score precision/recall against a human-labeled set.**

### Comparison with ours

Our review agent is richer in static checklist content and confidence filtering (`/local_disk0/codexwork/bundle/claude/agents/code-reviewer.md:10-45`), and `/code-review` includes a severity report and nominal commit block (`commands/code-review.md:1-40`). However, those are prompt contracts, not proof of execution. The known defects show why proof matters: detectors misread prose as execution and can mark successful tool results failed (`INPUT-known-harness-defects.md:52-82`), and detector output was trusted without a known-positive control (lines 111-129).

### Port proposal — receipt-based Stop gate with bounded retry

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** For tasks that modify code, the Stop hook reads typed receipts emitted by actual tool results: command/runner identity, argv fingerprint, exit status, timestamp, repository/worktree, and tested revision. Missing or failing required receipts blocks completion with concise feedback. Cap repeated blocks per work unit; after cap, end as incomplete rather than claiming success. Treat mentions of “tests passed” in prose as non-evidence.

This is **very likely (80-90%)** to prevent unsupported “done” claims and prose-scanner false positives because it discriminates on tool-result structure and revision rather than text. Evidence: Junie's bounded Stop retry semantics and local defect D1/D2. Settling experiment: fixtures containing prose that mentions failure, a successful test, a failing test, a stale success from another revision, and a detector known-positive control.

### Port proposal — focused read-only review session with native diff scope

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Use the existing review model/agent and native Git diff selection to create a read-only review lane with explicit targets: unstaged, staged, last commit, or branch against base. Keep review tools read/search only and present findings by file with accept/dismiss state. This is configuration and command consolidation, not a trained critic.

This is **likely (55-80%)** to improve review signal and reduce accidental review-time edits because Junie's focused subagent narrows prompt and tools, while ours already has the necessary reviewer and `review_model` (`/local_disk0/codexwork/bundle/codex/config.toml:18-20`). The interaction UI parity is **UNVERIFIED; the settling experiment is a real diff review on both providers and inspection of tool permissions and durable disposition state.**

### Port proposal — debugger tools through existing MCP

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Enable the JetBrains Debugger MCP Toolset only for debugging tasks and expose it via the existing MCP bus. Require approval for expression evaluation or actions with side effects; allow state inspection by default. Keep log-based debugging available for unsupported projects.

This is **very likely (80-90%)** to improve diagnosis of runtime-only JVM/.NET defects because breakpoints, frames, threads, and expression values provide direct evidence. It is **unlikely (20-45%)** to help when no compatible IDE/debug session exists. Settling experiment: three defects whose cause depends on runtime state, comparing tool calls, time, owner corrections, and correct root cause.

## 9. Where Junie is worse, and what not to copy

1. **Closed inner loop.** The behavior is documented, but the controller and context algorithms are not inspectable. Our hooks and agent files are auditable.
2. **EAP fragmentation.** Hooks and custom subagents are EAP, and hooks do not run in ACP/server hosts. A “one engine” product claim does not imply lifecycle parity on every surface.
3. **Missing post-tool failure hook.** Junie explicitly says tool errors await a future `PostToolUseFailure`. Our shared registration already includes post-tool success/failure.
4. **Coarse IDE MCP approval.** One IDE MCP allow rule authorizes every MCP tool. CLI rules are better.
5. **Bypassable `.aiignore`.** Brave mode and allowed commands can cross it, and names remain visible.
6. **Tool ceiling instead of routing.** A hard 100-tool ceiling is not a substitute for health, relevance, and task-scoped tool exposure.
7. **Parallel sessions are not automatically isolated.** Same-directory sessions can overwrite each other until the user selects worktrees.
8. **Diff/revert incompleteness.** JetBrains' own release notes warn that Bash-made changes may not appear in Done and diff counts may be wrong. The filesystem/Git diff remains authoritative.
9. **Memory is shallow or undocumented.** AGENTS.md plus ten-session history is legible, but no verified learned-memory mechanism matches our intended cross-project recall.
10. **Review is not demonstrably independent.** A tailored prompt/toolset is useful but is not an independent oracle.
11. **IDE advantage is ecosystem-dependent.** Semantic navigation, debugger, and configured runners are strongest inside supported JetBrains IDEs; the general harness must retain editor-neutral fallbacks.
12. **Remote control increases external surface.** Whether Junie's web continuation meets this owner's credential, retention, and audit requirements is **UNVERIFIED; the settling experiment is a data-flow review plus a disposable remote session with network/log capture and account revocation.** Do not port a remote service merely for convenience.

## 11. Anti-overfit gate

All recommended mechanisms satisfy the gate:

* **Existing bus:** MCP health/debugger/IDE tools use MCP; plan/completion/trust checks use hooks; agent bounds use agent frontmatter; review uses existing review agents/models; worktree/session state uses native collaboration and Git.
* **No second runtime:** no new scheduler, daemon, durable engine, or remote control plane.
* **No new vector/KG memory:** semantic IDE queries remain inside the IDE; no index is copied into a new store.
* **No trained critic:** review remains a scoped existing model with read-only tools and typed dispositions.
* **No observability SaaS:** receipts and status are local files/native events.
* **No guardrail framework:** permission changes use provider-native sandbox/approval; small hooks enforce only missing cross-provider contracts.

The deliberately minimal architecture is: providers remain the loop; Git remains source-of-truth for changes; native permission layers remain the safety boundary; MCP remains the tool bus; hooks only quarantine, bind, and verify; local receipts make claims falsifiable.

## 12. Recommended experiments before build

These experiments are ordered to retire the highest-value uncertainty cheaply:

1. **MCP quarantine fixture:** one healthy known-present server and one dead server. Prove discovery of the control, one failure/probe maximum for dead, zero subsequent model-visible calls, and successful recovery after half-open.
2. **Permission canary:** safe project read/edit, outside-project read/write, chained shell, credential file, package install, networked deployment, consequential MCP. Measure prompts and correctness under native narrow rules.
3. **Two-repository worktree matrix:** concurrent tasks from repo A, repo B, and umbrella directory. Capture resolved root, worktree, branch, changed files, and cleanup.
4. **Plan parity probe:** one Claude and one Codex task; inspect whether a durable plan file and enforced transition already exist. Only build shared glue if the gap survives.
5. **Stop receipt regression:** prose mentions of commands/failures, actual passing/failing tests, stale receipts, wrong revision, and a known-present detector control.
6. **IDE-tool comparison:** overload-safe rename, configured monorepo test, and runtime-state debugger defect with and without JetBrains MCP tools.
7. **Subagent budget/scope fixture:** force a loop and forbidden MCP call; verify max-turn incomplete status and hidden server.
8. **Review calibration:** seeded issues and non-issues; compare focused reviewer precision/recall, tool writes, tokens, and follow-up usefulness.
9. **Compaction continuity:** plant constraints/identifiers/unresolved work, trigger compaction, and score retention and task completion. This evaluates both Junie and repaired local routing.
10. **Memory ablation:** 30 cross-session tasks with basic-memory on/off, scoring correct recall, stale recall, provenance, owner corrections, and latency.
