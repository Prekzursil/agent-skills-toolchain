# G007 — Blind spot: silent degradation

**Unit:** G007  
**Date:** 2026-07-19 (Europe/Bucharest)  
**Mode:** read-only on the subject; this file is the only artifact written  
**Question:** What could be getting worse without anyone noticing, and what detectors would notice it without mistaking detector blindness for system absence?

## Executive verdict

The harness does not mainly lack logs. It lacks **proof that its observers are still observing the intended surface**. The most important silent-degradation modes are:

1. an MCP alias remains exposed after its transport or credentials degrade, so agents repeatedly select it even though a healthy sibling exists;
2. plugin discovery inventory grows until Windows process creation fails, while different enumerators silently count different populations;
3. memory transport remains alive while the recall projection or supersession graph falls behind the vault;
4. canonical, deployed, and runtime-discovered skill sets diverge, while source validation continues to pass on a different tree;
5. the detectors themselves disappear from the active dispatcher or stop producing samples.

The strongest immediate finding is that the prompt's “dead MCP called 532 times” framing is false. `mcp__claude_ai_Tavily__tavily_extract` had 532 calls and 137 errors, hence 395 successes (`corpus/corpus.json:175-179`, `:9141-9152`). It was **degraded**, not dead. The sibling `mcp__plugin_local-mcp-bridge_tavily__tavily_extract` recorded 103/103 success and `mcp__tavily__tavily_extract` 40/40 (`corpus/corpus.json:407-411`, `:655-659`). A binary up/down detector would misdescribe this incident and miss the more useful fact: the router continued spending calls on a much worse alias.

It is **almost certain (90-99%)** that a small, typed detector contract on the existing hook/ledger bus will expose these failures earlier, because every proposed signal already exists as a file, hook event, protocol call, or native inventory command; the remaining uncertainty is alert thresholds and operational overhead, which require the shadow experiments specified below. No second orchestrator, daemon, vector store, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is justified.

## 1. Evidence discipline and corrections

### 1.1 Corpus limits

The corpus hook section is unusable by construction: `corpus/corpus.json:13260-13263` says `DETECTOR_STATUS: BROKEN` and explicitly forbids interpreting empty fires as hooks not firing. This report uses the corpus's tool and error-fingerprint sections, not its hook section.

The live-defects file later retracts the stronger claim that hook telemetry is absent: raw transcripts contain abundant `async_hook_response` records (`INPUT-known-harness-defects.md`, D3). The lesson is load-bearing: a broken parser was mistaken for a broken world. This unit therefore gives the detector itself a first-class state.

### 1.2 Required state machine

Every detector must return exactly one of:

- `OK`: known-positive control passed; both independent signals are within policy.
- `WATCH`: control passed; one signal moved adversely but corroboration is not yet sufficient.
- `DEGRADED`: control passed; two independent signals agree that service quality or freshness is materially worse.
- `OPEN`: control passed; a bounded circuit breaker should suppress further selection of the failing route for this session.
- `UNKNOWN`: there is insufficient traffic or the two signals disagree.
- `DETECTOR_FAILED`: the known-positive control failed, the probe scope changed unexpectedly, or the detector did not emit by its deadline.

`UNKNOWN` and `DETECTOR_FAILED` are never green. They also never authorize deletion, disabling, or a correctness claim.

### 1.3 Mechanical-independence rule

Two regexes over the same file are not independent. Acceptable pairs here are:

- configured inventory versus a protocol handshake or native runtime inventory;
- filesystem enumeration versus a captured vendor discovery argv;
- source/vault metadata versus a query/read outcome;
- canonical/deployed byte inventory versus a disposable runtime invocation;
- event receipt versus a separate deadman timestamp generated by the consumer.

Before any absence or “broken” verdict, the same probe must find a known-present item in the same scope. This directly applies the rule supported by seven wrong calls in `INPUT-known-harness-defects.md` D2.

## 3. Detector architecture

### P0 — Typed degradation envelope and deadman receipt

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add one shared helper that all silent-degradation checks use. It writes an atomic JSON snapshot under the existing harness state root and appends only state transitions to the existing event ledger. Suggested envelope:

```json
{
  "schema": 1,
  "detector": "mcp-route-health",
  "scope_hash": "sha256:...",
  "measured_at": "2026-07-19T00:00:00Z",
  "next_due_at": "2026-07-19T00:05:00Z",
  "control": {"id": "known-basic-memory", "expected": "present", "observed": "present", "pass": true},
  "signals": [
    {"kind": "protocol", "source": "initialize", "state": "ok"},
    {"kind": "outcome", "source": "PostToolUseFailure window", "state": "bad"}
  ],
  "state": "WATCH",
  "reason_code": "outcome-burn-short-only",
  "baseline_ref": "...",
  "evidence_refs": ["..."]
}
```

Rules:

1. `state` cannot be `OK`, `DEGRADED`, or `OPEN` if `control.pass != true`.
2. `DEGRADED`/`OPEN` require two signal kinds, not merely two samples.
3. Every snapshot exports `measured_at`, not “seconds since”; consumers compute age. Prometheus recommends event timestamps because a stuck update loop cannot keep making the age look current ([Instrumentation](https://prometheus.io/docs/practices/instrumentation/)).
4. A deadman check compares `now` with `next_due_at`; missing samples become `DETECTOR_FAILED`. This is the local equivalent of `absent_over_time`, which Prometheus documents specifically for alerting on missing series ([Query functions](https://prometheus.io/docs/prometheus/3.11/querying/functions/)).
5. The detector emits only `SUCCESS:<id>` or `FAILED:<id> reason` when run directly, matching the cross-tool behavior contract.
6. State changes are retained; repeated identical `OK` samples overwrite the snapshot rather than inflate the ledger.

It is **very likely (80-90%)** that this envelope prevents false-green absence conclusions because it makes control status, scope, freshness, and corroboration machine-required. Evidence: the live defect report documents seven wrong single-probe conclusions, and today's marker probe independently reproduced a 785/1,998/2,014 scope split. The remaining uncertainty is whether every current hook payload supplies enough tool identity and result-class data; schema-capture fixtures settle that before implementation.

### P0b — Cached producer, cheap consumer

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Synchronous hooks must never perform recursive plugin scans, full vault scans, or model calls. Use the already-supported lifecycle points as follows:

- SessionStart reads the last snapshot, checks its age, and launches a detached refresh only when due.
- `ConfigChange`/`FileChanged` invalidates the relevant scope hash.
- `PostToolUse` and `PostToolUseFailure` update O(1) counters for the exact tool route.
- Stop emits at most one concise digest if any detector changed state.
- a maintenance command runs the slow inventory under `longrun` if it can exceed 60 seconds.

Claude Code natively exposes SessionStart, PreToolUse, PostToolUse, PostToolUseFailure, ConfigChange, and FileChanged hook events ([hooks guide](https://code.claude.com/docs/en/hooks-guide)). The current harness already has a dispatcher, atomic-ish state patterns, and an event ledger; no service is needed.

It is **very likely (80-90%)** that cached production avoids material hook latency because steady-state hooks perform timestamp reads and counter appends, while full scans are detached. **UNVERIFIED p95 overhead** must be settled by a seven-day shadow run; promotion requires p95 added synchronous latency below 25 ms and no host-timeout increase.

### P1b — General MCP health must join three planes

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Build a route-health module around three planes:

1. **Exposure plane:** exact provider/server alias and tool are present in the host's current tool inventory. Configuration alone is insufficient because configs can be shadowed or fail to load.
2. **Protocol plane:** a bounded `initialize` handshake, capability negotiation, and—where safe—`tools/list` or `ping`. The current MCP specification requires initialization first, describes capability negotiation, and recommends configurable request timeouts ([MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)).
3. **Outcome plane:** counters from real calls keyed by `{provider, server alias, tool, error class}` with success, failure, latency, and fallback-used fields.

Known-positive controls:

- exposure: one exact tool the host just advertised;
- protocol: one critical local server expected to answer `initialize` (currently Basic Memory), plus a deliberately wrong port in test fixtures;
- outcomes: a synthetic success and failure event passed through the same classifier before interpreting a zero count.

State examples:

- protocol bad + real `not connected` failures -> `OPEN` for that alias/session;
- protocol good + high real failure rate -> `DEGRADED`, not `DOWN`;
- protocol bad + no traffic -> `WATCH` or `UNKNOWN`, never “unused”;
- outcome errors + healthy sibling success -> `DEGRADED_ROUTE`, with the sibling suggested;
- missing exposure + configuration present -> `LOAD_DRIFT` after the exposure control passes.

The circuit breaker suppresses **selection advice**, not the MCP process or config. It injects “route via sibling X for this session” and records how many calls were prevented after open. Recovery uses half-open probes after a cooldown; one passing protocol probe alone moves to `WATCH`, while a successful real call closes the episode.

It is **very likely (80-90%)** that this would have reduced wasted Tavily calls because the corpus contains an exact, repeated `not connected` fingerprint and simultaneously healthy sibling aliases. The number of preventable calls is **UNVERIFIED** until raw timestamps reconstruct episodes and routing opportunities.

### P1c — UNVERIFIED threshold calibration

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Thresholds belong in data, not code. Start in shadow mode with candidate rules, then set them from replay:

- immediate candidate: two consecutive protocol failures plus one real failure of the same class;
- rate candidate: both a short and a long window exceed the route's historical error budget with a minimum sample count;
- low-traffic candidate: one scheduled canary plus real-call evidence, not a percentage over one call;
- reset candidate: protocol success plus a successful real or safe canary operation.

Exact window lengths, minimum counts, and burn rates are **UNVERIFIED**. Settle them by replaying timestamped MCP calls and running a 14-day shadow evaluation scored on detection delay, false opens, calls wasted after first decisive signal, and healthy fallback availability. Multi-window/burn-rate alerting is preferred to one fixed percentage because it balances fast detection with precision; Google documents the approach and its low-traffic caveat ([Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)).
