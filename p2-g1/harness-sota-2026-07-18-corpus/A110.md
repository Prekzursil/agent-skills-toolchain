## Conflict tests and runtime disposition

### 1. Agent models versus global model — difference, not conflict

Texts:

- settings: `"model": "opus[1m]"` (`settings.json:77`)
- representative agent: `model: opus` (`agents/code-reviewer.md:5`); the three exceptions say `model: sonnet` (`agents/docs-lookup.md:5`, `agents/intent-drift-sentinel.md:5`, `agents/loop-operator.md:5`).

Concrete collision test: spawn one of these named agents while the main session is using the global `opus[1m]` setting.

Runtime winner: the agent's model frontmatter wins for that agent unless a higher-priority `CLAUDE_CODE_SUBAGENT_MODEL` or per-invocation model is supplied. The documented order is environment override, per-invocation model, agent frontmatter, then main-conversation model. No `CLAUDE_CODE_SUBAGENT_MODEL` is present in the complete settings `env` object (`settings.json:4-20`).

Why this is not a finding: the global model continues to govern the main conversation and any inheriting/built-in agent; it is not dead text. The named agent field governs only that named agent. The settings and agent texts have intentionally different scopes, so both fire.

### 2. Agent effort versus global effort — difference, not conflict

### 3. Agent `tools` allowlists versus settings permission allowlist — orthogonal layers, not conflict

Texts:

- agent example: `tools: ["Read", "Grep", "Glob"]` (`agents/architect.md:4`)
- settings examples: `"Read", "Edit", "Write", "Glob", "Grep", "Bash"` (`settings.json:30-35`) and `"Task", "Skill", "Monitor"` (`settings.json:40-42`).

Runtime winner: the agent tool allowlist. `Edit` never enters that agent's available capability pool. The global `permissions.allow` list only decides approval for a tool that is available; it does not add tools omitted by agent frontmatter. Conversely, a tool present in an agent's list is still subject to applicable global deny rules.

Why this is not a finding: no agent text promises that globally allowed tools will be injected. The restricted agents' bodies are analysis/planning/review roles consistent with their read-only allowlists: `architect.md:8-18`, `planner.md:8-16`, and the reviewer files' explicit report-only contracts (`typescript-reviewer.md:27`, with analogous reviewer contracts).
