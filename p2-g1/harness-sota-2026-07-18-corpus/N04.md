# N04 — Capability recommendation at the moment of need

## Verdict

The best trigger is **not** “a prompt is semantically similar to a skill.” It is a two-stage decision: (1) evidence that the current trajectory has an unmet capability need, followed by (2) evidence that one *live, invocable* capability has positive expected value after interruption, switching, execution-failure, and trust costs. The action then has three levels: silently route the agent for low-risk/reversible use; ask one compact question when authority or strategy changes; abstain when neither clears its threshold.

The false-positive cost is therefore not merely “the owner ignores a line.” It includes attention capture, task switching, anchoring the agent on the wrong method, tool failure/retry cost, displacement of an already-discussed thread, and cumulative loss of trust. The exact conversion of those components into a single time or money value is **UNVERIFIED; a shadow replay followed by a randomized within-owner crossover of the policy described in Finding 8 would settle the weights**. The corpus already proves that the execution term can be large: `mcp__claude_ai_Tavily__tavily_search` failed on 139/194 calls and every sampled top failure was “not connected” (`/local_disk0/codexwork/bundle/inputs/corpus.json:319-324,9130-9138`), while Tavily extract failed on 137/532 calls, including 135 “not connected” failures (`corpus.json:175-180,9141-9148`). A recommendation that steers work into that dead route has a materially different cost from a wrong suggestion for a local read-only skill.

I recommend **evolution, not replacement**: keep the capability catalog, semantic router, calibrated-silence gate, selection-event ledger, and open-loop store, but change the decision rule and learning labels. This is **very likely (80-90%)** to outperform another catalog or router because the bundle already contains candidate generation, reaction gating, outcome events, and prospective-memory rails; the missing value is their policy composition, evidenced at `capability-catalog/inject.py:2-13`, `semantic-router/route.py:2-22`, `calibrated-silence/calibrated_silence.py:2-53`, `selection-events/emitter.py:577-606`, and `open-loops/_common.py:2-18`. The remaining uncertainty is live Windows wiring and calibrated effect size, not architectural fit.

## Findings (inferred-surprise first)

### 1. Improvement: make capability recommendation agent-facing by default, owner-facing only at an authority boundary

- **What it is:** Replace “surface a list to the owner whenever there is a match” with a three-action policy: `ACT-SILENTLY`, `ASK-ONCE`, or `ABSTAIN`. A high-confidence, live, read-only/reversible capability is injected as agent routing context and used without a new owner prompt. `ASK-ONCE` is reserved for capabilities that add external side effects, material spend, credentials, destructive scope, or a genuine strategic fork. Everything else abstains. The final/status message may disclose the capability actually used, but discovery itself is not another decision the owner must service.
- **Why inferred:** The owner explicitly makes prompt fatigue and focus first-class, while the existing router can emit as many as four skills, three MCP labels, two agents, and two commands in a single bundle (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/route.py:97-105,334-344`). The corpus’s concentration on general-purpose agents (`corpus.json:13346-13368`) shows routing is often generic; it does **not** prove the owner wants more menus. The surprise is that better discoverability should usually create *less* visible UI.
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `interaction_class` to each indexed capability: `silent_safe`, `confirm_side_effect`, or `advisory_only`; derive defaults from tool permission/risk metadata and allow explicit manifest overrides. In the existing router assembly, choose only the top admitted candidate and output an internal directive for `silent_safe`; render a one-line `AskUserQuestion` option only for `confirm_side_effect`; emit nothing otherwise. This extends the semantic router and native `AskUserQuestion`; it does not create a second router.
- **External signal that verifies it:** A `selection.v1` event already records the real query, chosen tool, and PostTool success/failure (`/local_disk0/codexwork/bundle/claude/hooks/selection-events/emitter.py:577-606`). Join that with the next real owner turn: success plus continued task progress verifies silent routing; explicit approval/rejection verifies asked routing. A fresh-context reviewer audits a stratified sample of silent decisions against the task and tool receipt. Same-context agent approval never counts.
- **SOTA:** Horvitz models inaction, dialog, and action as separate expected-utility choices and derives two thresholds between them ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). Microsoft’s validated HAI guidelines say to time services from the current task/environment and make capability/error limits clear ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).
- **Value x effort:** transformative x medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it for `silent_safe`; confirm-first for any external, costly, destructive, credentialed, or strategy-changing route.
- **Confidence:** **very likely (80-90%)** to reduce owner interruption without reducing low-risk capability use, because it removes visible menus while retaining native agent execution and outcome logging. The live effect size is **UNVERIFIED; the Finding 8 crossover experiment would settle it**.
- **Anti-overfit gate:** passes. It uses native invocation, `AskUserQuestion`, the current router, and the current selection bus; no new runtime, model critic, vector store, or guardrail framework.

### 2. Improvement: trigger on a trajectory-level need event, not prompt similarity alone

- **What it is:** Candidate similarity answers “what resembles this text?” The trigger must answer “is assistance needed *now*?” Fire candidate evaluation only at one of five evidence-bearing events: a new task/phase boundary; an explicit capability gap (“how do I…”, “can we…”); a terminal tool failure or repeated route failure; a declared acceptance criterion that the current plan lacks a method to verify; or a stored open-loop precondition becoming true. A match without one of these need events remains in shadow.
- **Why inferred:** The semantic router currently gates mainly on prompt length/content then ranks semantic and regex matches (`semantic-router/route.py:89-105,164-200,361-387`). The newest proactive-agent benchmark explicitly separates *when to assist* from *what assistance to generate*, and real continuous workflows outperform isolated/synthetic contexts (`ProAgentBench`, below). This workspace also contains retry loops—53 Read runs, 14 Bash runs, and smaller ToolSearch/StructuredOutput loops (`corpus.json:10297-10369`)—which are stronger need signals than a fresh keyword match.
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add a deterministic `need_event` adapter inside the existing shared dispatcher. It reads only existing event type, terminal success/failure, goal/task state, and open-loop trigger state; it emits `{need_type, evidence_event_id, urgency}` into the router call. Do not add an LLM classifier. The router returns candidates only when `need_type != none`, except explicit user invocation which always passes.
- **External signal that verifies it:** The event ID and terminal tool result are external to the recommendation context. Offline, replay real prompt→tool sequences and have a fresh-context model plus an executable task receipt independently label whether assistance was needed at that point; disagreements go to owner adjudication. Online, compare interruption precision and missed-opportunity rate against the prompt-similarity baseline.
- **SOTA:** ProAgentBench decomposes proactive assistance into timing prediction and assistance generation and reports benefits from real historical context ([Tang et al., 2026](https://arxiv.org/abs/2602.04482)). The newer π-Bench separately measures task completion and proactivity across hidden intents, dependencies, and cross-session continuity ([Zhang et al., 2026](https://arxiv.org/abs/2605.14678)).
- **Value x effort:** transformative x medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it.
- **Confidence:** **very likely (80-90%)** that this yields higher precision than similarity-only firing, because timing and content are distinct benchmark tasks and local retry/terminal events supply independent need evidence. Its recall on implicit needs is **UNVERIFIED; a labeled replay of at least 200 real task boundaries would settle it**.
- **Anti-overfit gate:** passes; deterministic adapter on the existing event bus, no second orchestration runtime.

### 3. Improvement: charge each candidate its reliability-weighted false-positive cost before it can be recommended

- **What it is:** Use candidate-specific expected net value, not one global route threshold: `P(need) × P(success|task,capability) × benefit − interruption_cost − switch_cost − expected_failure_cost − thread_displacement_cost`. Exact currency is unnecessary initially: use ordinal risk tiers and hard admission rules. A currently dead/uninvocable capability has infinite admission cost; a historically unreliable or slow tool needs stronger evidence; a local reversible skill can pass a lower threshold.
- **Why inferred:** The current calibrated-silence gate learns one hit rate per broad interjection type (`route`, `question`, etc.) from `acted/(acted+ignored)` (`/local_disk0/codexwork/bundle/claude/hooks/calibrated-silence/calibrated_silence.py:75-107,226-266,381-428`). That makes a route to a dead Tavily server and a route to a local read-only skill share a criterion despite radically different execution costs. Corpus reliability demonstrates the difference: Tavily search is 71.65% error (`corpus.json:319-324`), whereas the Exa web-search tool shown nearby is 0/562 errors (`corpus.json:167-172`).
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Before ranking, join each candidate to the existing MCP-liveness state and a rolling selection-event outcome table. Reject `not_live`/`not_invocable`; apply a bounded penalty for recent failure rate and consecutive failures; add static side-effect/latency tiers. Keep semantic score solely as relevance evidence. Do not duplicate B1 mcp-liveness: consume its self-heal/alert state.
- **External signal that verifies it:** Provider `tools/list`/liveness is a different tool signal; PostToolUse/Failure is an execution result; terminal task tests are a third signal. A candidate is “good” only when it was live *and* its invocation succeeded *and* the task’s external receipt improved. Owner continuation alone is insufficient.
- **SOTA:** Horvitz explicitly makes the action threshold a function of utilities for desired and undesired service and notes that attention changes the cost of an unwanted action ([Horvitz 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)). The same paper recommends minimizing the cost of poor guesses and doing less under uncertainty to avoid backtracking.
- **Value x effort:** high x low.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it.
- **Confidence:** **almost certain (90-99%)** that live/invocable admission prevents the demonstrated class of dead-tool false positives, because the external liveness state directly contradicts admission. It is **likely (55-80%)** that reliability weighting improves overall task completion; a paired replay with terminal receipts would settle that broader claim.
- **Anti-overfit gate:** passes; consumes B1 liveness and existing outcome events.

### 4. Improvement: learn usefulness per capability × need type; stop treating “invoked” as “correct”

- **What it is:** Replace the router’s global `suggested`/`used` boost and the silence gate’s broad route hit-rate with a small contextual table keyed by `(capability_id, need_type, project_class)`. Labels are hierarchical: `exposed`, `invoked`, `tool_succeeded`, `task_receipt_passed`, `owner_rejected/corrected`. Ranking reward comes from the deepest externally observed label, not mere invocation.
- **Why inferred:** The current router explicitly calls acted-on suggestions “success”: it increments `used` when a suggested tool is invoked and boosts by `used/(suggested+2)` (`/local_disk0/codexwork/bundle/claude/hooks/semantic-router/success.py:1-14,90-124`). Its observer credits the first matching invocation without reading its result (`semantic-router/observe.py:52-66`). This can positively reinforce a wrong recommendation that the agent obediently tried and that then failed. The existing selection emitter already supplies a stronger `success` result (`selection-events/emitter.py:577-606`).
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Extend `selection.v1` additively (or emit `selection_outcome.v1`) with `recommendation_id`, `candidate_id`, `need_type`, `exposed`, and `rank`. The existing PostTool events set invocation outcome; a task-completion event or deterministic verifier attaches `receipt_passed`; the next genuine owner turn can attach explicit reject/correction only when provenance proves it is owner-authored. Use Beta-binomial smoothing per key and back off to capability family/global priors at low `n`; no trained critic.
- **External signal that verifies it:** Tool exit, deterministic acceptance receipt, fresh-context reviewer, and explicit owner reaction are all outside the recommending context. The corpus warning at `corpus.json:10371-10374` requires provenance filtering before any owner-correction label is admitted.
- **SOTA:** π-Bench finds a clear distinction between task completion and proactivity and benefits from prior interaction ([π-Bench](https://arxiv.org/abs/2605.14678)). Proactive Agent reports that reward feedback reduced false alarms but also sharply reduced recall, illustrating why “stay silent” and “was useful” must be measured separately ([Proactive Agent](https://arxiv.org/abs/2410.12361)).
- **Value x effort:** high x medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it.
- **Confidence:** **almost certain (90-99%)** that invocation is not a correctness label, because the observer never inspects the result and the corpus contains high-failure invoked tools. It is **very likely (80-90%)** that outcome labels calibrate better than uptake alone; the pre-registered replay in Finding 8 settles magnitude.
- **Anti-overfit gate:** passes; additive ledger events and simple counts only.

### 5. Improvement: discover cold/new capabilities in shadow, not by spending the owner’s attention

- **What it is:** New or rarely seen capabilities receive exploration opportunities, but their candidates are logged without being surfaced. When a shadow candidate is independently chosen by the agent or wins a fresh-context offline replay and produces a passing receipt, it earns promotion. Only high-value capabilities that cannot be safely tested without owner authority may request a single compact confirmation.
- **Why inferred:** The calibrated-silence gate deliberately allows every interjection type until five reacted samples exist (`calibrated-silence.py:94-107,407-418`). That avoids permanent suppression but spends the owner’s attention as the cold-start exploration budget. Meanwhile, the corpus records only 78 invoked skill IDs (`corpus.json:13265-13344`), making cold-start coverage important without proving any particular missing skill was needed.
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Add `shadow=true` and `policy_version` to candidate events. Reserve, for example, 10% of *internal* low-risk routes for a high-uncertainty candidate, never owner-visible; enforce one exploration per task phase. Promotion requires either two independent successful receipts or one owner-explicit invocation. Demotion requires repeated external failures, not same-context dislike.
- **External signal that verifies it:** Compare shadow candidate rank with the capability actually chosen, its tool result, and deterministic task receipt. A separate model judges counterfactual fit only on a frozen sample; it cannot update its own prompt or labels.
- **SOTA:** ProAgentBench reports that long-term history and real-world data improve timing prediction over synthetic data ([ProAgentBench](https://arxiv.org/abs/2602.04482)); Proactive Agent’s feedback experiment shows that aggressively reducing false alarms can collapse recall ([Proactive Agent](https://arxiv.org/abs/2410.12361)). Shadow exploration preserves recall learning without visible interruptions.
- **Value x effort:** high x medium.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it for read-only/reversible shadow trials; confirm-first otherwise.
- **Confidence:** **likely (55-80%)** to improve long-tail discovery without prompt fatigue, based on external-label collection without exposure. The exploration rate and promotion sample count are **UNVERIFIED; an offline replay grid followed by a four-week shadow run would settle them**.
- **Anti-overfit gate:** passes; a bounded exploration rule, not a contextual-bandit service or trained policy.

### 6. Improvement: if the owner must see it, show one falsifiable recommendation card—not a capability dump

- **What it is:** The owner-visible form is one line: `Use <capability> because <observed need>; expected gain <specific>; risk/uncertainty <specific>; [use] [skip]`. Never show more than one recommendation per task phase; alternatives stay behind the agent. “Because semantic score=.71” is not an explanation. The reason must cite task evidence (“two search calls failed because server unavailable; search-hub is live”).
- **Why inferred:** The current session catalog serializes every configured group item line-by-line (`capability-catalog/inject.py:42-52`), and the router emits multi-kind lists (`semantic-router/route.py:334-344,388-400`). More explanation is not automatically safer: human-AI research finds explanations can increase reliance even on wrong advice, while stronger cognitive forcing reduces overreliance at a usability cost.
- **How to build:** **NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Change router render configuration to `visible_top_k=1`, require `need_evidence` and `uncertainty_reason`, and map owner actions to native `AskUserQuestion` choices. Keep full candidate detail in the event ledger for audit, not the prompt. If those fields are absent, abstain.
- **External signal that verifies it:** Explicit `use/skip` is owner evidence; execution result and task receipt verify whether “use” was beneficial. Track visible recommendation lines per hour, skip/dismiss rate, time-to-next-task-action, and correction rate. A fresh-context rater checks that the stated reason is entailed by the cited event.
- **SOTA:** Microsoft’s guidelines pair “make clear how well” with “make clear why,” while timing services by the current task ([Amershi et al.](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Buçinca et al.’s N=199 study found cognitive forcing reduced overreliance but the most effective designs received the least favorable ratings, recommending adaptive use only when it can materially improve the decision ([Buçinca et al., 2021](https://zbucinca.github.io/assets/pdf/publications/bucinca2021trust.pdf)).
- **Value x effort:** high x low.
- **Novelty:** inferred-surprise.
- **Autonomy:** just-do-it.
- **Confidence:** **very likely (80-90%)** to reduce prompt fatigue because it strictly caps visible choices and tokens. Whether it preserves discovery recall is **UNVERIFIED; the Finding 8 crossover measures precision, recall, and interruption density together**.

### 8. Improvement: establish a cost-sensitive, externally labeled routing evaluation before enabling owner-visible proactivity

- **What it is:** Create a frozen evaluation set from real task boundaries and score the complete policy, not only retrieval. Required metrics: need-detection precision/recall; capability precision@1; invocability rate; successful-receipt rate; visible interruptions per hour; owner skip/dismiss/correction rate; thread-loss count; and cost-weighted regret. Report strata by need type, project class, capability risk, and cold/warm status. A wrong visible recommendation costs more than a wrong shadow candidate; a recommendation of an unavailable tool is an automatic severe false positive.
- **Why inferred:** The existing semantic eval has already been audited as coarse and tiny, but the stronger direct evidence here is that the corpus’s correction detector produced 41/41 false positives in its smoke sample (`corpus.json:10371-10374`). The corpus also shows that generic activity is not quality: 3,694 StructuredOutput calls had 846 errors, including 294 copies of one schema mismatch (`corpus.json:103-108,8964-8972`). A self-scored same-context eval would repeat the owner’s measured failure mode.
- **How to build:** **NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Export 200-300 provenance-clean task-boundary cases from `selection.v1` and corpus samples; freeze case IDs and policy version. Obtain labels from two mechanically independent channels: deterministic liveness/execution/task receipts, plus a fresh-context cross-provider model; send only disagreements and a small random audit sample to the owner. Run baseline and candidate policies on identical cases. Only after the lower confidence bound improves cost-weighted precision without materially worsening missed-need rate should owner-visible mode canary at 10% of eligible moments. No policy may grade its own generated recommendation in the same context.
- **External signal that verifies it:** This finding *is* the external loop: provider tool discovery, real exit codes, deterministic acceptance tests, a different-context/model label, and owner adjudication. Completion requires all seeded positive/negative detector controls to be found and a reproducible report with policy hash.
- **SOTA:** ProAgentBench uses real continuous-workflow events and explicitly separates timing from content ([ProAgentBench](https://arxiv.org/abs/2602.04482)); π-Bench jointly measures proactivity and task completion in long-horizon workflows ([π-Bench](https://arxiv.org/abs/2605.14678)). Buçinca et al. warn that proxy tasks can look more optimistic than actual decision-making and argue for adaptive interventions only on cases predicted to improve team decisions ([Buçinca et al.](https://zbucinca.github.io/assets/pdf/publications/bucinca2021trust.pdf)).
- **Value x effort:** transformative x medium.
- **Novelty:** user-asked.
- **Autonomy:** just-do-it for offline/shadow evaluation; confirm-first before owner-visible randomized canary.
- **Confidence:** **almost certain (90-99%)** that this is necessary for an honest go/no-go decision, because local correction labels demonstrably fail without provenance and the law rejects same-context self-correction. It is **likely (55-80%)** that 200-300 cases are enough for directional policy selection but **UNVERIFIED; bootstrap confidence intervals and power analysis on observed base rates would settle sample adequacy**.
- **Anti-overfit gate:** passes; offline script and existing events, no evaluation SaaS, trained critic, or second runtime.

## Concrete policy specification

The buildable decision is:

1. `need_event = detect(existing_event, task_state, open_loops)`.
2. If no need event, record shadow candidates only and return.
3. Generate candidates with the existing semantic/lexical router.
4. Admit only provider-valid, live/invocable candidates; attach risk and rolling external-outcome priors.
5. Compute ordinal expected net value. Similarity is relevance evidence, never the decision by itself.
6. If top candidate is `silent_safe` and clears the action threshold, inject one agent-facing route.
7. If it changes authority/risk/strategy and clears the dialog threshold, show one falsifiable `AskUserQuestion` card.
8. Otherwise abstain; if the need remains valuable but blocked/deferred, register a condition-bound open loop.
9. Learn only from external reactions/results: invocation, tool result, task receipt, fresh-context audit, or owner decision.

This exactly preserves the hook ceiling: candidate generation and gating fold into the existing shared `UserPromptSubmit` dispatcher; reactions/outcomes ride the current `PostToolUse`/`PostToolUseFailure` selection emitter; deferral rides open loops. All new code paths must be `try/except` wrapped and return/exit 0 on their own errors. If state is unreadable, recommendation admission fails open *operationally* by allowing normal agent work to continue, but fails silent for the optional recommendation so it cannot block the task.

## Rejected alternatives and dead ends

- **Another capability catalog:** rejected as duplication; the session-start catalog already exists (`capability-catalog/inject.py:2-13`).
- **Another semantic/vector router:** rejected as duplication and anti-overfit; repair/wire the existing semantic router. No vector DB or knowledge graph is proposed.
- **Always show top-k:** rejected because retrieval confidence does not price interruption or execution failure, and current top-k can generate a multi-line menu (`semantic-router/route.py:97-105,334-344`).
- **Use owner “continuation” as success:** rejected; the corpus’s correction detector confounded provenance (`corpus.json:10371-10374`), and invocation can be followed by failure.
- **Same-context LLM judge:** rejected by construction under the unit law. A different prompt in the same conversation is not independent.
- **Always ask before using any skill:** rejected as prompt-fatigue regression. Native/read-only/reversible routing should be silent.
- **Always stay silent after negative feedback:** rejected because Proactive Agent found reward feedback could reduce false alarms while sharply reducing recall; abstention and usefulness need separate labels ([paper](https://arxiv.org/abs/2410.12361)).
