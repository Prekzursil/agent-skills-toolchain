# P1A05 — Corpus axis: retry-grind

## Unit scope and bottom line

This unit analyzes only `corpus.json.retry_loops`: a detector intended to count a tool with the same input at least three consecutive times. I read the detector, resolved all 21 distinct sampled basenames to raw transcripts, inspected every small and medium sample, and used targeted extraction on the 4.39 GB outlier transcript. I did not modify the harness subject.

The plain result is that `retry_loops` is a useful **candidate generator**, but its 81 `runs` are not 81 proven agent retry loops. The raw samples show four materially different phenomena:

1. **Active polling of asynchronous state** is the dominant genuine pattern in the samples: background-output `Read`, shell status commands, blocking `TaskOutput`, research-status MCP calls, MCP availability search, and a PowerShell workflow-status command.
2. **Duplicate calls emitted inside one model response** occur independently of polling. The strongest examples are three identical `Read` calls and five identical `ToolSearch` calls carrying the same request ID.
3. **Unchanged retry after a deterministic rejection** occurs in the `StructuredOutput` sample: the agent explicitly says it will retry identical bytes until they pass, while the validator returns the same missing-properties error.
4. **Legitimate repeated probes across separate owner turns** can be mislabeled as a loop. The `hublive` sample is decisive: the owner separately asks for the same probe on lines 37 and 48, yet the miner retains its prior key and counts the three calls as one run.

It is **very likely (80-90%)** that active polling is the largest real retry-grind cause among the 81 candidates. Evidence: 11 of 12 sampled `Read` transcript files show background/status polling; all three sampled Bash files show progress polling; all six sampled `TaskOutput` episodes in the outlier use blocking status retrieval; all three deep-research files poll `status: running`; and the sole PowerShell episode polls workflow counts. The band is not higher because `seen_in` is a capped, scan-order sample of filenames rather than a random episode sample, and the corpus does not store episode line ranges or results.

The best harness response is not a universal “never repeat a call” prohibition. It is a small, result-aware repeat protocol on the existing hook/tool bus: distinguish same-response duplicates, active polling with changing state, polling with no change, deterministic unchanged errors, and deliberate cross-turn repetition; then select the corresponding breaker. A blind hard block would stop valid probes and long waits.

## Detector validity: what “consecutive identical” actually means

### 1. It is consecutive tool-use events, not uninterrupted assistant actions

Normal user records containing tool results occur between calls. The run key is updated only in the assistant tool-use branch (`mine.py:243-267`) and is not reset in the user/tool-result branch beginning at `mine.py:270`. This is appropriate for detecting call → result → same call, but has an important side effect described next.

### 2. The run crosses independent owner turns

There is no reset when a new user instruction arrives. The decisive control is:

- `...\06caca23-9880-42d6-9d81-b64842f170af.jsonl:28-29`: the assistant calls `mcp__hublive__b3_probe_gamma {}` and receives `B2-X-GAMMA-77bb21`.
- The assistant answers on line 32.
- Line 37 is a new owner instruction: **“Call the tool b3_probe_gamma with no arguments, then reply with ONLY the exact text it returned.”** The call/result occur on lines 40-41 and the answer on line 43.
- Line 48 repeats that owner instruction as another turn; the call/result occur on lines 51-52.

The corpus counts those calls as one three-call retry sequence even though each satisfies a separate request. Therefore the statement “81 retry loops occurred” is false as written. The defensible statement is “the miner found 81 same-key three-call sequence triggers.”

This false-positive mechanism is **almost certain (90-99%)** to affect more than the one proven `hublive` episode whenever an owner or orchestrator deliberately repeats a tool-only probe across turns. Evidence: the missing reset is unconditional in `mine.py:243-275`, and the raw control demonstrates the result. Its corpus-wide frequency is **UNVERIFIED;** settle it by replaying all 81 candidates with a reset at every genuine user-instruction boundary and comparing episode IDs.

### 3. “Identical input” means identical first 4,000 serialized characters

`mine.py:181-185` hashes `json.dumps(inp, sort_keys=True, default=str)[:4000]`. Two longer inputs with the same prefix collide by construction even before considering the 12-hex SHA-1 truncation. In the raw sampled sequences I extracted, the repeated serialized inputs were fully equal and short (from `{}` through a 1,069-character PowerShell input), so this defect did not invalidate those samples. Whether any of the unsampled 81 candidates are prefix-only matches is **UNVERIFIED;** settle it by recording a full canonical-input digest and comparing it with the existing prefix digest for every candidate.

### 4. Sample coverage is by filename, not by episode

The `Read` sample cap is exhausted at 12 transcript filenames for 53 candidate sequences. A file can contain several episodes: for example, `agent-aa10931ba79e0c4d4.jsonl` contains five observed `Read` runs, and `agent-a4cf6d37fd43c04b8.jsonl` contains four. The corpus does not say which episode in a sampled file caused the sample entry. Therefore exact cause proportions cannot be reconstructed from `corpus.json` alone.

The 32 oversized skipped lines are another narrow coverage gap. It is **unlikely (20-45%)** that they materially change the retry cause ranking, because only 32 of 1,564,084 lines were skipped and the observed dominant patterns recur across many independent small transcripts. Evidence for the band is the `_meta` line counts plus the repeated patterns below; this remains uncertain because a skipped line can contain many embedded tool blocks.

For these three observed calls, unchanged input deterministically reproduces the same validation error. Whether the validator had accepted byte-identical input earlier, as the agent claims, is **UNVERIFIED;** settle it by locating the alleged earlier successful tool call and byte-comparing its canonical JSON input and active schema. The recommendation to stop unchanged retries does not depend on that premise: once the same missing-property diagnostic repeats, the next action must change the root object or escalate the validator inconsistency, not submit the same string again.

## Cause D — intentional cross-turn repetition mislabeled as grind

The `hublive` probe described under detector validity is the sole corpus episode for that tool. It is a detector false positive, not agent retry-grind. A correct detector must reset at genuine user instruction boundaries or at least label this as `cross_turn_repeat` rather than `same_attempt_retry`.

Some repeated probes inside a single benchmark may also be intentional. Their frequency is **UNVERIFIED;** settle it by joining candidates to the initiating owner/orchestrator prompt and identifying explicit repetition counts or probe instructions.

## Cause-to-breaker map

| Cause | Observable signature | Mechanism that breaks the loop | Preserve / exemption |
|---|---|---|---|
| Background file polling with no new state | Same `Read`; result is `file_unchanged`, shorter-than-offset, or nonexistent; pending task/monitor exists | Register the pending operation once, wait for its terminal event, and make the next read eligible only on event or explicit deadline | Allow a bounded terminal-state read after notification/deadline |
| Progress polling with changing state | Same shell/PowerShell command; counters or log tail advance | Move the polling loop into one monitor process that emits heartbeats and one terminal marker; the model consumes notifications rather than launching each poll | Heartbeats are monitor output, not separate model tool calls |
| Blocking `TaskOutput` timeouts | `block:true`; result `timeout` + `running` | Keep one durable waiter/notification subscription rather than issuing another full block from the model | Reattach after session recovery only when no waiter is live |
| MCP status/connection polling | Result says `running` / `still connecting` / `try again` | Tool returns `next_poll_after_ms` plus terminal event/callback token; harness enforces monotonic backoff when no event interface exists | A user-requested explicit refresh bypasses the autonomous backoff |
| Same-response sibling duplicates | Same request ID, tool, and canonical input before any result | Deduplicate the planned tool batch by `(request_id, tool, canonical_input)` before dispatch, sharing one result with sibling consumers | Explicit test/probe repetitions require a declared distinct nonce or repetition index |
| Deterministic unchanged failure | Same canonical input and same normalized error fingerprint twice | Emit a terminal `FAILED:<fingerprint>` decision: mutate input/schema, choose another mechanism, or stop/report; never retry unchanged | A retry is allowed only after a falsifiable external-state change |
| Separate owner-turn repetition | New genuine user instruction between identical calls | Reset the autonomous retry run at the instruction boundary; classify separately | Owner-requested repetition remains valid |

## Harness proposals

### Proposal 1 — Repair the retry detector — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Change the existing miner rather than add a service:

1. Reset an autonomous run at every genuine user-instruction boundary, while not resetting on a tool-result record.
2. Hash the complete canonical input, not a 4,000-character prefix.
3. Emit episode records with start/end line, request IDs, tool-use IDs, actual call count, elapsed time, normalized result fingerprints, and whether state changed.
4. Label at least `same_response_duplicate`, `unchanged_result_poll`, `changing_result_poll`, `unchanged_error_retry`, and `cross_turn_repeat`.
5. Store a capped set of episode records, not only basenames.

This repair is **almost certain (90-99%)** to remove the proven `hublive` false positive and make future cause counts auditable. Evidence: the missing boundary reset directly causes that episode, and line ranges/request IDs separate both same-response duplicate examples. It is **very likely (80-90%)** to stay under roughly 200 lines because it extends `mine.py`'s existing state machine and output schema rather than introducing a runtime; settle the sizing uncertainty with a patch and line-count review.

### Proposal 2 — Use one terminal-state waiter for long work — NATIVE (Claude Code already does this; we just enable it)

For native background tasks, use the platform's background completion notification/one blocking waiter and do not re-read its output until notification or a declared deadline. The raw transcripts repeatedly refer to a “completion notification” and `TaskOutput` already supports `block:true` plus terminal/running status; the failure is that the agent continues to poll around those mechanisms.

This is **very likely (80-90%)** to eliminate most sampled `Read`-of-task-output loops and all six repeated `TaskOutput` sequences when a live waiter survives. Evidence: unchanged-output messages explicitly call the reads wasted, while later terminal reads become useful only after state changes. It will not handle process monitors that lack a native event, session loss, or a rejected waiter; those require Proposal 3.

### Proposal 3 — Result-aware repeat rail with terminal markers — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Extend the existing hook/event ledger with ephemeral per-session tuples `(tool, full_input_digest, result_fingerprint, pending_operation_id, last_change_time)`. On the second identical autonomous call:

- if result state changed, inject the next eligible poll time and require backoff;
- if result is unchanged, inject `REPEAT_WITHOUT_STATE_CHANGE` and route to the pending event;
- if the same error repeats, inject `FAILED:<fingerprint> unchanged input cannot change this result`; and
- reset on new owner instruction or a falsifiable external-state change.

Per the behavior contract, this should inject guidance rather than exit-2 block a nondangerous tool. This rail is **likely (55-80%)** to reduce repeated calls materially. Evidence: the sampled agents often state the correct intention (“stop polling”) yet immediately call again, so a result-tied reminder is better positioned than a static prose rule. The lower band reflects that prompt injection is not an execution hard stop and can be ignored.

### Proposal 4 — Same-response batch deduplication — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus) — UNVERIFIED

UNVERIFIED premise: the current Claude tool dispatch/hook surface permits one sibling tool call to be coalesced before execution and its result shared with duplicate siblings; settle it with a synthetic assistant response containing three identical harmless reads and observe PreToolUse ordering and result routing.

If the bus permits it, canonicalize the pending tool batch by `(request_id, tool, full_input_digest)`, dispatch the first, and return a cached/coalesced result to later siblings. If it does not, add a concise model rule requiring a deduplication pass before emitting parallel tool blocks and instrument violations; do not violate the behavior contract by hard-blocking nondangerous calls.

The dispatcher form is **very likely (80-90%)** to eliminate the two proven same-response examples because their request IDs and inputs are identical before any result. The prompt-only fallback is **roughly even (45-55%)** to prevent them reliably; evidence for caution is that these duplicates arose despite otherwise coherent plans, suggesting generation/streaming pathology rather than a deliberate policy choice.

### Proposal 5 — Make pollable MCP results schedule-aware — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Normalize pollable MCP outputs to include:

```json
{
  "status": "running",
  "next_poll_after_ms": 30000,
  "terminal_event_token": "...",
  "progress_version": 7
}
```

Where the underlying MCP cannot emit events, a small adapter can enforce `next_poll_after_ms` and increase it monotonically after unchanged `progress_version`. Do not tell the model merely “Continue polling... Call again” as the current deep-research results do.

This is **likely (55-80%)** to reduce the three research-status episodes and the `qlty` availability episode. Evidence: those tool results explicitly solicit another call without a delay. The effect depends on clients honoring the schedule; settle it with an A/B replay of the four sampled prompts against old and schedule-aware result text.

### Proposal 6 — Error-fingerprint transition rule — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

On `(same tool, same full input, same normalized error)` twice, require one of three terminal actions: mutate the input in a way that addresses the error, switch mechanism, or report `FAILED:<id>` with the falsifiable precondition for retry. The StructuredOutput example should route directly from “missing root properties” to constructing actual root properties, not resubmitting XML embedded in `summary`.

This is **very likely (80-90%)** to stop the sampled deterministic retry at two failures rather than three or more. Evidence: all three errors are byte-equivalent in meaning and explicitly identify the missing fields. It is **unlikely (20-45%)** to harm transient failures if the guard keys on the normalized error and allows retry after an external-state change; that risk must be tested with known transient connection failures.

## Anti-overfit gate

Every proposal above rides an existing bus: the corpus miner, native background-task semantics, hooks/event ledger, tool dispatch, or MCP result schema. None introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. The runtime rail stores only small ephemeral fingerprints and pending-operation state; it is not a new durable workflow engine. This preserves the deliberate minimal architecture while addressing failures demonstrated in raw transcripts.

A universal hard retry blocker is rejected. The evidence directly shows why: changing `Read` results can eventually reveal terminal state; Bash status outputs can progress; `TaskOutput` calls can be separated by ten-minute blocks; and the `hublive` calls satisfy distinct owner prompts. The smallest adequate intervention is classification plus the appropriate breaker.

## Expected priority and effect

1. Repair the detector first, because current aggregate counts mix false positives, same-response duplication, useful changing-state polls, and true unchanged grind.
2. Route long operations to one terminal-state waiter/monitor; this targets the largest sampled cause without new architecture.
3. Add the result-aware repeat rail for unchanged results/errors.
4. Experiment with same-response dedup because it requires confirmation of dispatch semantics.
5. Normalize pollable MCP result contracts with explicit scheduling.

It is **very likely (80-90%)** that steps 1-3 together address more sampled retry-grind than any static “do not retry” rule. Evidence: most sampled genuine loops arise after a result says running/unchanged or while progress is being watched, and assistant prose already contains repeated promises not to poll. The corpus cannot support a numeric effect-size estimate because it lacks episode results and the `Read` samples are capped.

## Alternatives considered and rejected

### Global ban after two identical calls

Rejected because it would mis-handle the cross-turn probe, changing progress results, and bounded terminal checks. It also conflicts with the requirement to block only dangerous actions.

### Fixed sleep instruction in the global prompt

Rejected as insufficient. A fixed sleep turns a fast polling loop into a slow polling loop, still consumes model/tool turns, and cannot distinguish a terminal event from unchanged state. The `TaskOutput` sample already waits five or ten minutes per call and still repeats.

### New durable workflow/orchestration service

Rejected by the anti-overfit gate. Existing native task waiting, monitor scripts, hooks, and MCP schemas are enough to express the required state transitions. No sampled cause justifies a new runtime.

### Treat every changing status call as harmless

Rejected. The 166-call Bash sequence does return progress, but it launches a new shell/tool turn for each observation. A single monitor can produce the same progress stream more cheaply and with a terminal marker.

8. **Oversized-line contribution.** Thirty-two lines were not parsed. Experiment: process them with a streaming/size-tolerant extractor and compare tool-event sequences around those boundaries.

## Final ruling

Retry-grind is real, but the current metric conflates three different harness responsibilities and one non-defect:

- **Harness/tool protocol defect:** async and MCP interfaces invite or permit repeated polling without an event or next-poll schedule.
- **Agent behavior defect:** the model actively polls despite stating it will wait, and retries deterministic errors unchanged.
- **Dispatch/generation defect:** one response emits duplicate sibling calls before results exist.
- **Detector defect / non-defect behavior:** deliberate repetitions across separate owner turns are counted as a loop.

The architecture should evolve through small changes on existing buses, not replacement with another orchestrator. First make the detector causally valid; then use native terminal notifications, a small result-aware repeat rail, and schedule-aware MCP results. Preserve explicit owner repetition and state-changing terminal checks.
