# A108 — coherence audit: `~/.claude/agents/**` versus `~/.claude/settings.json`

## Executive result

I found **three classes of direct configuration contradiction** in the unpacked subject:

1. **Model selection:** all 18 available agent definitions explicitly select `opus` or `sonnet`, while user settings select `opus[1m]`. In an ordinary named-agent invocation with no invocation-time model override, the agent frontmatter wins. This is 18 concrete agent/settings pairs, not one abstract possibility.
2. **Effort selection:** four agents explicitly select `medium`, while user settings select `xhigh`. The agent frontmatter wins for those four agent runs.
3. **Fallback selection:** `security-reviewer` declares `claude-opus-4-8` through frontmatter keys that are not in either current official subagent schema, while settings declare `claude-sonnet-5`. **UNVERIFIED** on the owner's Windows installation, the global settings fallback is the only documented effective fallback; the settling experiment is to invoke `security-reviewer` with a deliberately unavailable primary model under `claude --debug`, then inspect the selected fallback in the session/debug header.

I found **no direct permission or enabled-plugin contradiction that survives runtime semantics**. Several textual pairs look opposed, but they govern different things: a subagent `tools` allowlist controls tool availability; `permissions.allow` controls approval; an enabled/disabled plugin is not the same object as a separately configured MCP server. I enumerate these non-findings below rather than silently discarding them.

Confidence in the model and effort precedence result is **almost certain (90-99%)**, based on two independent official descriptions: the Claude Code subagent reference gives the model-resolution order and says agent `effort` overrides session effort, while the Agent SDK's independent `AgentDefinition` type describes both fields as per-agent overrides. The exact installed Windows binary was unavailable on this Linux job node, so the remaining 1-10% covers version drift and invocation-time overrides, not ambiguity in the inspected files. Sources: [Claude Code subagents](https://code.claude.com/docs/en/sub-agents), [Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript).

## Runtime rules used to decide winners

These are not assumptions about precedence:

1. The official subagent documentation says `tools` is an exclusive allowlist when present. It separately says a subagent `model` is resolved in this order: `CLAUDE_CODE_SUBAGENT_MODEL`, invocation parameter, agent frontmatter, then main-conversation model. It also says agent `effort` overrides session effort. [Claude Code subagent reference](https://code.claude.com/docs/en/sub-agents).
2. The independently published SDK type defines `AgentDefinition.model` as a model override and `AgentDefinition.effort` as the agent's reasoning-effort level; its type contains neither `fallbacks` nor `server-side-fallback`. [Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript).
3. The official permission documentation says allow rules permit use without approval; they are not a tool-availability allowlist. It gives deny → ask → allow evaluation and describes `bypassPermissions`. [Claude Code permissions](https://code.claude.com/docs/en/permissions).
4. The official tools reference states that tool names are shared across permission rules, subagent tool lists, and hook matchers, while disabling a tool is done through a deny rule. [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference).

The settings environment block at `settings.json:4-20` contains no `CLAUDE_CODE_SUBAGENT_MODEL`. Therefore the concrete runtime situations below explicitly assume the caller does not pass a per-invocation `model`. If it does, the caller's value wins; that is a third configuration surface unavailable in this bundle and is not silently assumed away.

## Permission and plugin pairs examined but rejected as findings

### 1. Global Write/Edit allow versus read-only agents — not a conflict that arises

Settings say:

> `"Edit",`
>
> `"Write",`

— `settings.json:31-32`

`agent-as-judge` says “Read-only on source. You NEVER edit, write, or refactor project code” (`agent-as-judge.md:40-41`) and omits Edit/Write from its tool allowlist (`agent-as-judge.md:4`). `intent-drift-sentinel` says “NEVER edit files, write code, or run non-read commands” (`intent-drift-sentinel.md:98`) and likewise omits Edit/Write (`intent-drift-sentinel.md:4`).

This looks contradictory only if `permissions.allow` is misread as a capability grant. Official runtime semantics distinguish the layers: agent `tools` is the availability allowlist; settings `allow` suppresses approval for an available tool. Therefore Edit and Write are not supplied to these agents, and the collision never arises. Their included Bash tool still creates a prompt-level policy risk because Bash can mutate, but settings do not say they **must** mutate and the agent does not claim Bash is technically sandboxed. That is not a direct X/NOT-X contradiction.

### 2. Global web permission versus sentinel's “NO web access” — not a conflict that arises

Settings allow `WebSearch` and `WebFetch` at `settings.json:37-38`. Sentinel says “NO web access” at `intent-drift-sentinel.md:10` and “NEVER call web search” at line 99. Its exclusive tools list at line 4 contains neither web tool. The agent allowlist wins availability, so the runtime never presents web tools to this agent under the documented semantics.

### 3. Broad MCP permission versus sentinel's basic-memory-only rule — not a conflict that arises
