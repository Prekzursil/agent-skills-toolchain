# X103 — Cross-domain borrow: metrology → observability without a baseline

**Unit:** X103  
**Source field:** metrology (calibration, traceability, measurement uncertainty, reference standards)  
**Target problem:** deciding whether a harness change helped when no trustworthy baseline exists  
**Research posture:** ideation lens only; no local repository or subject-tree inspection, as required  
**Date:** 2026-07-19

## Executive result

The useful borrow is not “calibrate the agent” in the loose machine-learning sense. It is a **measurement assurance program (MAP)**: define a narrow measurand, establish independently valued check standards, preserve an unbroken and versioned traceability chain, repeat the check standards through the same production measurement path, and report the result together with an uncertainty budget. In a harness, the “instrument” is the entire observation path—task fixture, harness, model, tools, environment capture, scorer, and aggregation—not merely the model.

**Transfer verdict — very likely (80-90%) for narrow operational claims, with evidence:** NIST explicitly designs check-standard methodology to expose time-dependent errors in a *whole measurement process*, and says the check standard can be an artifact **or a defined quantity/process characteristic**, not only a physical object ([NIST, “What is a check standard?”](https://itl.nist.gov/div898/handbook/mpc/section1/mpc12.htm)). NIST's Process Measurement Assurance Program likewise covers equipment, standards, personnel, procedure, and environment, and uses repeated control measurements to calculate uncertainty while production continues ([NISTIR 6176](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir6176.pdf), especially the PMAP description around p. 3). Those structures have direct analogues in an agent harness.

**Non-transfer verdict — almost certain (90-99%) for a universal claim such as “this harness is better,” with evidence:** metrological traceability relates a result to a specified reference; it does not prove that the chosen measurand or reference captures every value the owner cares about. The VIM defines a measurand as the “quantity intended to be measured” and requires its specification, including relevant state and conditions ([JCGM VIM 2.3](https://jcgm.bipm.org/vim/en/2.3.html)). “Agent quality” is neither a single stable quantity nor traceable to an SI realization. The borrow therefore supports statements such as “change B reduced schema-invalid outputs on reference task family R under environment E by Δ with uncertainty U,” not “B made the agent better.”

This result is ambitious in a different way from a replacement runtime: it replaces baseline-free dashboard storytelling with a **refusal-capable measurement contract**. If the reference, scorer, environment record, or statistical resolution is unfit, the correct output is `INDETERMINATE`, not an improvement percentage.

## 1. What metrology has already solved

### 1.1 Start by specifying the measurand, not by collecting convenient telemetry

In metrology, the measurand is the quantity intended to be measured. Its specification includes the kind of quantity and relevant state/conditions; the VIM also warns that the measuring system can alter the phenomenon, so the quantity actually measured can differ from the intended measurand ([JCGM VIM 2.3](https://jcgm.bipm.org/vim/en/2.3.html)).

That distinction is fundamental for harness observability. “Tool calls,” “tokens,” “judge score,” and “task completed” are indications. They are not automatically the owner-valued measurand. For example:

- Intended measurand: probability that a repository change satisfies a pinned test-and-review acceptance contract.
- Indications: exit status, tests passed, diff size, tool errors, elapsed time, and a reviewer rubric score.
- Influence quantities: model snapshot, prompt/context, seed or sampling behavior, tool versions, repository state, network state, credentials/permissions, task order, cache state, and scorer version.

The metrological lesson is that a dashboard cannot rescue an undefined measurand. It can only report indications more attractively.

### 1.2 Calibration establishes a relation; it is not adjustment and it is not verification

The VIM defines calibration as a two-step operation: under specified conditions, establish a relationship between values and uncertainties supplied by standards and the corresponding instrument indications; then use that relation to obtain a measurement result from an indication. It explicitly distinguishes calibration from adjustment and verification ([JCGM VIM 2.39](https://jcgm.bipm.org/vim/en/2.39.html)).

Applied here, running a known task through the observation path estimates how telemetry/scoring indications relate to an accepted task outcome. Changing prompts or hooks because the score looks wrong is **adjustment**, not calibration. Checking whether a predeclared release criterion is met is **verification**. Keeping these operations separate prevents a common circularity: tuning the evaluator and candidate on the same failures and then claiming that the candidate improved according to that evaluator.

### 1.3 Traceability is an auditable chain to a named reference, with uncertainty at every link

The VIM defines metrological traceability as the property by which a result can be related to a reference through a documented, unbroken chain of calibrations, each contributing to uncertainty. It requires an established calibration hierarchy and notes that the reference must be identified in time ([JCGM VIM 2.41](https://jcgm.bipm.org/vim/en/2.41.html)). This is more demanding than “we stored the metric.”

A physical chain might be working instrument → working standard → laboratory reference → national standard. A harness chain can only be conventional, but it can still be explicit:

`owner decision → acceptance contract → independently assigned reference outcome → executable scorer → raw run events → derived metric → release decision`

Every arrow needs an identity/version, procedure, and uncertainty or known limitation. The top reference is not SI; it is the owner's versioned operational definition. That weaker endpoint must be stated rather than disguised.

### 1.4 A check standard samples the total measurement process over time

NIST describes a check standard as a stable, repeatable artifact or defined process quantity measured over time to expose errors in the measurement process. The resulting database characterizes time-dependent error; regularly spaced measurements act as surrogates for production items that cannot all be repeatedly measured ([NIST, “What is a check standard?”](https://itl.nist.gov/div898/handbook/mpc/section1/mpc12.htm)). NIST also says check standards should resemble workload items in material and geometry and be present at critical measurement levels ([NIST, “Control of artifact calibration”](https://www.itl.nist.gov/div898/handbook/mpc/section3/mpc35.htm)).

PMAP goes beyond checking an instrument in isolation. It selects check standards representative of the calibration output, assigns their values with independent reference standards, duplicates the production procedure, and uses control measurements to evaluate equipment, standards, personnel, procedure, and environment ([NISTIR 6176](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir6176.pdf); [NIST SOP 30](https://www.nist.gov/system/files/documents/2019/05/13/sop-30-process-measurement-assurance-20190506.pdf)).

That is the strongest structural match. A fixed harness check task is not chiefly a benchmark for leaderboard quality; it is a travelling standard sent repeatedly through the *same end-to-end observation path* to reveal whether that path has drifted.

### 1.5 An uncertainty budget makes disagreement and resolution explicit

The VIM defines an uncertainty budget as a statement of uncertainty, its components, and how they are calculated and combined; it calls for the measurement model, component estimates, covariances, distributions, degrees of freedom, evaluation type, and coverage factor ([JCGM VIM 2.33](https://jcgm.bipm.org/vim/en/2.33.html)). NIST distinguishes statistically evaluated Type A components from other Type B components and combines standard uncertainties, including covariance where appropriate ([NIST TN 1297, §5](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-5-combined-standard-uncertainty)). NIST cautions that confidence interpretations depend on distributional conditions; an uncertainty interval is not automatically a classical confidence interval.

For a harness, uncertainty is not merely model sampling variance. A defensible budget must at least name:

- run-to-run stochasticity;
- task sampling/coverage uncertainty;
- scorer disagreement and scorer drift;
- flaky tests and external-service variability;
- environment/model/tool version variation;
- missing or censored telemetry;
- reference-outcome ambiguity;
- covariance caused by shared tasks, shared judges, shared caches, and paired runs.

The practical payoff is a detection limit: a change smaller than the measurement system's resolution is not “no effect”; it is unresolved.

### 1.6 Control charts distinguish ordinary variation from process change—but require commissioning

NIST's control procedure repeatedly measures a check standard and signals persistent changes in level or variability; candidate causes include damaged standards, procedural changes, lost environmental control, handling changes, and instrument degradation ([NIST, “How are bias and variability controlled?”](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc22.htm)). A Shewhart chart uses an accepted value and process standard deviation from historical check-standard data; NIST's example guidance says at least 100 check-standard values are required to establish that accepted value ([NIST, “Shewhart control chart”](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc221.htm)).

This is important to the target problem: metrology does **not** pretend that a process with no baseline is already controlled. It enters a commissioning period, establishes a reference relation, accumulates repeated control measurements, and only then uses historical control limits. Before that, the correct status is provisional.

## 2. Concrete translation: Harness Measurement Assurance Program (H-MAP)

### Mapping

| Metrology mechanism | Harness translation | What must be versioned |
|---|---|---|
| Measurand | One owner-relevant decision quantity, e.g. accepted completion rate for a named task stratum | prose definition, units/scale, exclusions, required conditions |
| Reference standard | Small suite of stable tasks with independently assigned outcomes; for deterministic properties, executable oracles | fixture commit/digest, oracle, assigned value, assignment evidence |
| Check standard | A hidden subset rerun unchanged through the production path | task ID, contamination status, last review date |
| Calibration hierarchy | Decision → contract → reference → scorer → event → aggregate → gate | all identities, hashes, timestamps, transformations |
| Control measurement | Full harness run on a check task, including hooks/tools/scorer | model, harness, environment, tool and scorer versions |
| Uncertainty budget | variance and bias components attached to every reported delta | method, sample, covariance, missingness, coverage statement |
| Intercomparison | Same sealed task/run bundle scored by independent mechanisms or executed on old and candidate harnesses | evaluator identities and blinded order |
| Out-of-control signal | Known check task shifts beyond commissioned limits or two independent detector signals disagree | raw evidence, alert rule, disposition |

### 2.1 Proposal — UNVERIFIED: versioned measurement contract and reference-task ledger

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Create a declarative ledger, not a new service. Each measurand record should include:

1. `decision`: the release/rollback decision the metric informs;
2. `measurand`: exact operational definition and direction of benefit;
3. `scope`: task strata and explicit non-covered workload;
4. `reference_id`: fixture/oracle/rubric digest and assigned outcome;
5. `assignment_method`: executable oracle, owner adjudication, or independent panel, with uncertainty/ambiguity;
6. `measurement_procedure`: exact harness path and aggregation;
7. `influence_quantities`: model, environment, tool, scorer, order, cache, permissions;
8. `target_uncertainty` and smallest owner-relevant effect;
9. `status`: `COMMISSIONING`, `CONTROLLED`, `OUT_OF_CONTROL`, or `INDETERMINATE`;
10. `trace_chain`: hashes/versions from owner contract to raw event bundle and decision.

**UNVERIFIED premise:** a representative, stable, independently assignable subset of this owner's work exists. The settling experiment is the “fitness-for-reference trial” in §5: independently re-adjudicate and rerun candidate standards across time and environments, then measure oracle agreement, stability, and coverage. Until it passes, the recommendation remains a ledger in `COMMISSIONING`, not a release gate.

**Expected value — very likely (80-90%), conditional on that trial, with evidence:** explicit reference identity, time, procedure, and uncertainty implement the structural requirements of VIM traceability ([JCGM VIM 2.41](https://jcgm.bipm.org/vim/en/2.41.html)). The ledger would make it mechanically difficult to compare incomparable score versions or silently move a rubric while preserving one metric name.

### 2.2 Proposal — UNVERIFIED: one hook-bus check-standard runner and append-only evidence record

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Build one thin runner/aggregator on the existing bus. It should:

- select a stratified handful of sealed check tasks;
- run them through exactly the production harness path, not a synthetic shortcut;
- emit append-only JSONL containing raw indications plus all influence-quantity versions;
- evaluate deterministic oracles locally and preserve raw artifacts for non-deterministic adjudication;
- validate detector health with a known-present positive control on every batch;
- require a second mechanically independent signal before declaring telemetry absent or a path broken (for example, hook event plus process exit/artifact existence, not the same parser run twice);
- calculate paired deltas and uncertainty components without overwriting raw observations;
- return `INDETERMINATE` if the positive control is unseen, required provenance is missing, the reference has changed, or uncertainty exceeds the target.

The runner should not auto-repair, prompt-route, or orchestrate work. It measures.

**UNVERIFIED premise:** the existing hook/skill/MCP bus exposes enough version and outcome data to construct the trace chain without invasive runtime changes. The settling experiment is a one-task vertical slice: inject a known event, run one deterministic reference task, and independently reconcile hook capture against process exit plus produced artifact. Failure means this proposal is not BUILD-SMALL and must be rejected or separately justified as BUILD-LARGE.

**Expected detection — likely (55-80%), conditional on the vertical slice, with evidence:** NIST says check standards expose errors that afflict a process over time and act as surrogates for otherwise-changing production items ([NIST check-standard methodology](https://itl.nist.gov/div898/handbook/mpc/section1/mpc12.htm)). The harness runner would detect observation-path drift that aggregate production success cannot separate from workload mix—such as a scorer version shift, event loss, environment change, or increased variability on an unchanged task.

### 2.3 Proposal — UNVERIFIED: paired, randomized change trials before historical control exists

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

For each meaningful harness change, run old/control and candidate on the same reference tasks in randomized order and in matched blocks of model snapshot, environment, repository fixture, and time window. Preserve per-task differences; do not compare two unpaired dashboard averages. Predeclare the primary contrast and smallest practically important effect. Report the paired effect, interval/uncertainty, failures by stratum, and a decision of `BETTER`, `WORSE`, `EQUIVALENT WITHIN PREDECLARED BOUNDS`, or `INDETERMINATE`.

NIST explains that paired observations compare two measurement systems or before/after treatments through within-item differences ([NIST, “Analysis of paired observations”](https://www.itl.nist.gov/div898/handbook/prc/section3/prc311.htm)). NIST also explains that randomized blocking holds controlled nuisance factors homogeneous while varying the factor of interest, and summarizes the rule “block what you can, randomize what you cannot” ([NIST, “Randomized block designs”](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)).

**UNVERIFIED premise:** an old/control harness remains executable under sufficiently matched conditions and there is no material carryover between runs. The settling experiment is an order-balanced A/A trial: run the unchanged control in both labelled arms, alternate order, and test whether the estimated “change” is centered near zero at the predeclared practical resolution. If A/A produces an apparent effect, diagnose order/cache/environment leakage before A/B.

**Expected value — very likely (80-90%) when matched execution is feasible, with evidence:** pairing removes task difficulty from the arm contrast, while blocking accounts for recorded nuisance shifts. This creates a contemporaneous reference when there is no historical baseline. It does not create an absolute baseline or prove generalization beyond the registered task strata.

### 2.4 Proposal — UNVERIFIED: commission control limits; do not backfill certainty

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

Start every check-standard series in `COMMISSIONING`. Accumulate unchanged-control runs across the influence conditions the claim is meant to cover. Estimate repeatability and longer-term reproducibility separately. Do not issue “out of control” from historical limits until the predeclared commissioning rule is met; NIST's cited Shewhart guidance uses at least 100 check-standard values for its accepted value ([NIST Shewhart guidance](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc221.htm)). Select sample size and chart type from false-alarm tolerance, effect size, autocorrelation, and operating conditions rather than copying “100” blindly.

**UNVERIFIED premise:** check-task outputs are sufficiently stationary within explicitly versioned regimes for a control model to be meaningful. The settling experiment is a stability study with frozen inputs and recorded influence quantities, followed by residual/autocorrelation checks and a deliberate small perturbation. If regime changes dominate, keep only paired trials and retire long-run control limits.

**Expected detection — likely (55-80%) if stationarity holds, with evidence:** NIST identifies persistent level shifts and changes in variability as signals of reference, procedure, environment, handling, or instrumentation changes ([NIST process-control guidance](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc22.htm)). A commissioned harness chart should similarly detect slow scorer drift, intermittent hook loss, or variance inflation even when mean success remains flat. “Should” here is conditional, not a claim of completed implementation.

## 3. What this would catch that baseline-free observability misses

The following are predictions, not observed local defects.

1. **False improvements caused by workload mix.** A production dashboard can rise because easier tasks arrived. Paired unchanged references hold task identity fixed. **Detection confidence: very likely (80-90%),** supported by the paired-comparison and blocking designs cited above.

2. **Evaluator or telemetry drift mistaken for agent drift.** A stable sealed task whose score changes after a scorer/hook version change exposes movement in the measurement path. **Detection confidence: likely (55-80%),** because it depends on preserved raw artifacts and an independently stable assigned value; NIST PMAP's whole-process scope is the supporting mechanism ([NISTIR 6176](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir6176.pdf)).

3. **Changes smaller than noise reported as wins.** An uncertainty budget and target resolution force `INDETERMINATE` when sampling, scorer, or environment uncertainty swamps the delta. **Detection confidence: very likely (80-90%),** provided uncertainty components are honestly estimated; the evidence is VIM's uncertainty-budget specification ([VIM 2.33](https://jcgm.bipm.org/vim/en/2.33.html)) and NIST's combination guidance ([TN 1297 §5](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-5-combined-standard-uncertainty)).

4. **Mean-preserving reliability degradation.** A change can leave mean score flat while increasing variance or intermittent failures. Repeated check measurements chart both level and variability. **Detection confidence: likely (55-80%),** supported by NIST's explicit treatment of changes in variability as process signals ([NIST process-control guidance](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc22.htm)).

5. **Broken detectors producing reassuring zeros.** Every batch includes a known-present positive control and reconciles it with an independent process/artifact signal. A missing positive control invalidates the batch rather than proving absence. **Detection confidence: very likely (80-90%)** for failures in the covered capture path; it cannot detect two independent channels that share an unrecognized common-mode failure.

6. **Reference or rubric movement hidden behind a stable metric name.** The trace chain binds each result to time-stamped reference/scorer identities. **Detection confidence: almost certain (90-99%)** for recorded version changes, because identity mismatch is deterministic; **UNVERIFIED** for semantic changes that retain identical bytes, settled by independent periodic re-adjudication of blinded raw outputs.

7. **Regressions concentrated in one critical operating range.** Metrology places check standards at critical levels, not only at one midpoint ([NIST artifact-calibration control](https://www.itl.nist.gov/div898/handbook/mpc/section3/mpc35.htm)). Stratified harness references—such as deterministic edits, long-context retrieval, tool recovery, and permission-constrained work—can expose a local regression hidden by an aggregate. **Detection confidence: likely (55-80%),** conditional on the strata actually representing owner-critical regimes.

## 4. Adversarial analysis: where the analogy breaks

### 4.1 There is no physical invariant or SI traceability

A calibrated mass standard embodies a quantity with a mature reference hierarchy. A coding or research task has multiple acceptable trajectories and often disputed utility. The harness chain terminates in a conventional owner contract, not a natural constant. Calling it “traceable” without naming that endpoint would borrow metrology's prestige without its epistemic foundation.

**Consequence — almost certain (90-99%), with evidence:** results must say “traceable to acceptance contract C,” never merely “traceable” or “ground truth.” VIM traceability is explicitly relation to a specified reference, not truth in the abstract ([VIM 2.41](https://jcgm.bipm.org/vim/en/2.41.html)).

### 4.2 Check tasks are not stable artifacts by default

Models can memorize public benchmarks; repositories and package ecosystems change; network tasks depend on live state; a task can become easier as tools acquire new capabilities. Repeating a prompt does not guarantee repeating the measurand.

**Consequence — very likely (80-90%), based on the task/environment dependence just enumerated:** reference tasks need sealed fixtures, pinned dependencies, contamination tracking, and expiration/review. Live-web tasks can be monitoring probes but are poor trueness standards unless their external state is captured. This is **UNVERIFIED** for the owner's actual workload; the §5 fitness trial settles it.

### 4.3 The scorer is often part of the same epistemic system

An LLM judge may share model-family biases with the agent, reward style over correctness, or drift when its provider updates it. Repeating a judge score can yield precision without trueness. Deterministic tests cover only properties that can be encoded.

**Consequence — likely (55-80%), based on shared-model and version-dependence mechanisms:** use independent executable oracles where possible; retain raw outputs; blind human or alternate-family adjudication for sampled ambiguous cases; report disagreement as uncertainty rather than majority-vote truth. This recommendation is **UNVERIFIED** until the scorer intercomparison in §5 measures disagreement and common-mode errors.

### 4.4 Production work is not an exchangeable population

Agent sessions vary in goals, risk, duration, and available context. A small reference suite can be stable yet unrepresentative. Metrology's check standard is useful because it resembles workload artifacts and the measurement process is expected to produce comparable results over time; NIST explicitly warns that the check artifact should be close to workload material/geometry ([NIST check-standard guidance](https://itl.nist.gov/div898/handbook/mpc/section1/mpc12.htm)). That assumption is weaker for open-ended knowledge work.

**Consequence — almost certain (90-99%), with the cited workload-similarity requirement as evidence:** H-MAP must report coverage by task stratum and cannot extrapolate to unseen work. Production outcome sampling remains necessary; check standards diagnose the measurement system, not the full future task distribution.

### 4.5 Intervention effects can depend on task, model, and order

A hook may help tool recovery but harm latency; a prompt rule may help one model snapshot and hurt another; cached artifacts or conversation state can carry over between arms. A single additive calibration curve is implausible.

**Consequence — very likely (80-90%), supported by the number of interacting influence quantities:** use per-stratum paired effects and explicit interaction checks. Do not collapse them into one score unless weights are declared by the owner. Order-balance and isolate caches where possible; otherwise widen uncertainty or declare the comparison indeterminate.

### 4.6 Control charts can industrialize Goodhart's law

Once check tasks become release gates, builders can optimize them, shrinking apparent uncertainty while missing novel work. Hidden tasks only delay this if the task family is static.

**Consequence — likely (55-80%), based on repeated exposure and optimization pressure:** separate measurement standards from development examples, rotate/refresh only through a versioned bridge study, and reserve periodically sampled real work for external-validity audits. A bridge study must run old and new reference panels together before changing the series; otherwise the historical chart is broken.

### Bottom line on transfer

The analogy **does transfer** to calibration and surveillance of a narrowly specified observation-and-decision process. It **does not transfer** to universal intelligence, utility, or future-work quality. This boundary is not a minor caveat; it is the design's central safety property.

## 5. Decisive experiments before adoption

### Experiment A — fitness-for-reference trial

Select candidate tasks across predeclared owner-critical strata. Freeze fixtures and dependencies. Obtain assigned outcomes using an executable oracle where possible and two blinded, mechanically independent adjudication routes where not. Rerun across times and the intended environment regimes; record all influence quantities.

Pass criteria must be set before seeing results and should include:

- assigned-outcome agreement sufficient for the intended release decision;
- within-reference variability below the target uncertainty;
- no unexplained time trend in the frozen regime;
- coverage explicitly mapped to, and limited to, named strata;
- known-present detector controls observed through two independent channels.

**Prediction — roughly even (45-55%), with evidence:** a mixed suite is likely to contain both fit deterministic references and unfit open-ended references. The uncertainty reflects the absence of local workload inspection by design. This experiment, not analogy, settles the premise.

### Experiment B — A/A false-improvement trial

Label identical harness configurations as control and candidate. Randomize order within matched blocks. Run the full proposed measurement path, including scoring and aggregation. The system must not declare either arm better at the predeclared practical resolution. Repeat after harmless metadata/version changes to ensure identity bookkeeping does not create a false effect.

**Prediction — likely (55-80%), with evidence:** A/A will expose at least one non-negligible nuisance component in a stochastic, tool-using harness; NIST's blocking guidance states that all experiments have nuisance factors ([NIST randomized blocks](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)). The exact component is UNVERIFIED; the A/A trial settles it.

### Experiment C — seeded-fault detection and localization

Inject individually identifiable perturbations into a disposable test path: drop one known hook event, alter scorer version, add a controlled tool failure, change fixture digest, and increase response variance without changing its mean. Keep a no-fault control. Require the program to (a) invalidate missing-detector batches, (b) attribute version/reference breaks, (c) flag level versus variability changes, and (d) avoid signaling in the control.

**Prediction — very likely (80-90%), conditional on raw event access, with evidence:** these perturbations directly target the whole-process and level/variability failure modes that NIST MAP/control-chart methods are designed to expose ([NISTIR 6176](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir6176.pdf); [NIST process control](https://www.itl.nist.gov/div898/handbook/mpc/section2/mpc22.htm)). Failure to localize is acceptable for the first small build; failure to detect or invalidate is not.

### Experiment D — scorer intercomparison

Create a blinded bundle containing clearly correct, clearly incorrect, and deliberately ambiguous outputs. Compare executable oracle results, current scorer, an independent scorer, and sampled owner adjudication. Estimate disagreement by stratum and inspect common-mode errors rather than only correlation.

**Prediction — likely (55-80%), based on scorer subjectivity for open-ended outputs:** disagreement will be materially larger on ambiguous research/design work than on executable coding outcomes. This remains UNVERIFIED until the intercomparison is run; its result supplies a Type A scorer component and identifies Type B limitations that cannot be averaged away.

### Stop conditions

Stop the transfer rather than forcing it if any of the following persists after one redesign:

- no candidate reference is stable and independently assignable at the owner's decision resolution;
- the full production path cannot be exercised by a check task;
- scorer/reference uncertainty is larger than the smallest owner-relevant change;
- A/A repeatedly reports improvement or regression;
- check-task coverage cannot be stated without claiming unseen-work generality;
- implementing trace capture requires a second orchestration runtime.

If stopped, retain only randomized paired experiments on freshly adjudicated real tasks. Do not call the result calibration or ongoing measurement assurance.

## 6. Anti-overfit gate and rejected expansions

The proposed architecture passes the stated anti-overfit gate **only if** it remains a declarative ledger plus a thin hook-bus recorder/evaluator. It rides the existing hook/skill/MCP bus and adds no second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

Rejected options:

- **Second evaluation/orchestration service:** unnecessary for replaying a small check suite; it creates another clock, queue, state store, and failure surface whose own traceability would need calibration.
- **Vector/KG “memory of baselines”:** similarity search does not establish comparability, assigned values, or uncertainty. It can retrieve precedents but cannot make them standards.
- **Trained critic:** it turns scorer calibration into a model-development program and risks common-mode bias. Independent executable and sampled human references are simpler and more falsifiable.
- **Observability SaaS:** useful display/storage does not solve measurand definition, reference assignment, detector controls, or uncertainty. Existing append-only artifacts are enough for the proposed experiment.
- **One composite quality score:** it hides non-compensable harms and owner weighting. Keep a small vector of predeclared decision quantities and stratum-specific effects.

**Complexity forecast — likely (55-80%), conditional on existing bus access:** the runner can remain below roughly 200 lines if task execution and raw event production already exist; the ledger and analysis formulas can be data/config. This is **UNVERIFIED** and the one-task vertical slice is the settling experiment. If the slice proves otherwise, do not smuggle a BUILD-LARGE system in under the same name.

## 7. Recommendation

### Recommended — UNVERIFIED: pilot H-MAP as a measurement layer, not as a new agent runtime

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Run Experiments A–D on a deliberately small, stratified reference panel. Until they pass, label all outputs `COMMISSIONING` or `INDETERMINATE`. If they pass, use paired randomized A/B trials immediately for change decisions and add historical control charts only after commissioning. Preserve raw evidence and uncertainty; never backfill a fictional baseline.

**Overall expected benefit — very likely (80-90%) for preventing unsupported “improved” claims, with evidence:** the proposal combines (1) explicit measurand specification, (2) reference-linked traceability, (3) whole-process check standards, (4) uncertainty budgets, and (5) paired/blocked comparisons, all supported by the primary JCGM/NIST sources above. Its strongest output is often a principled refusal to decide.

**Overall expected benefit — unlikely (20-45%) for predicting quality on novel, open-ended future work, with evidence:** check-standard validity depends on workload similarity and stable assigned values, conditions that NIST states for physical check artifacts and that agent work satisfies only imperfectly ([NIST check-standard guidance](https://itl.nist.gov/div898/handbook/mpc/section1/mpc12.htm)). Production sampling and owner judgment remain necessary.

## 8. Gaps and evidentiary limits

- No local subject, corpus, defects, or audit files were inspected. This is intentional under the unit's IDEATION instruction, so no claim is made about what the current harness already implements.
