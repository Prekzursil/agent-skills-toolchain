# A054 — coherence audit of `~/.claude/rules/php/security.md`

## Executive verdict

The PHP security overlay is directionally sound, but it is not coherent as an enforceable harness contract. I found **five rule-layer collisions** (four redundancies and one genuine output-safety contradiction), **four enforcement collisions** (three unenforced requirement groups and one unruled credential-read restriction), and **one stale/unactionable cross-reference risk that remains UNVERIFIED because the skill bodies were not included in the remote bundle**. The most consequential defect is not the prose itself: the wired per-edit hook has no PHP branch and the secret-scanner regression test expects functions that the live implementation does not contain.

The corpus cannot establish PHP compliance. Its hook detector explicitly failed a known-positive control (`inputs/corpus.json:13260-13263`), and the distilled behavioral sections contain no PHP/composer/CSRF/password/mass-assignment records. It does contain seven secret-bearing-input blocks and three no-raw-credentials blocks (`inputs/corpus.json:6743-6751`, `8166-8171`), but neither fingerprint identifies PHP or a committed PHP config. Treating those records as evidence that this PHP rule was followed—or violated—would overclaim.

The recommended architecture remains minimal: keep nuanced PHP obligations in the existing rule bus, repair and extend the already-wired per-edit hook, and route high-risk PHP edits to the existing reviewer/skill bus. No second orchestrator, vector store, durable runtime, trained critic, SaaS, or guardrail framework is proposed.

## Collision register

### C1 — Raw-HTML “justification” weakens the mandatory sanitization floor

**Class: CONTRADICTION**

**Artifacts and exact lines**

* `claude/rules/php/security.md:13-15`: validate at the framework boundary; escape templates by default; raw HTML is “an exception that must be justified”; validate query params, cookies, headers, and upload metadata.
* `claude/AGENTS.md:93-99`: security is always on; validate all user inputs at system boundaries and sanitize before HTML output.
* `claude/rules/common/security.md:28-33`: before any commit, all inputs must be validated and XSS prevention requires sanitized HTML.
* The analogous web rule is unambiguous: never inject unsanitized HTML, and raw HTML APIs are allowed only after sanitization (`claude/rules/web/security.md:40-45`).

**Collision**

“Justified” raw rendering is not the same control as sanitization. As written, PHP line 14 permits an agent to justify unsanitized raw HTML, while AGENTS line 98 and common line 32 do not. Escaping and sanitizing are also distinct operations: escaping converts data to safe text; sanitization permits a vetted subset of markup.

**Precedence**

Resolved by AGENTS §10: AGENTS §9 is a security non-negotiable and wins. The README’s language-specific-over-common rule (`rules/README.md:93-98`) cannot relax it. There is no unresolved choice about whether unsanitized raw HTML is permitted: it is not.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing rule/skill/hook bus)**

Replace PHP line 14 with: “Escape dynamic template values by default. Render raw HTML only from a typed/trusted-safe value produced by a vetted sanitizer; document the sanitizer and trust boundary.” Also use the same terminology in common security. It is **almost certain (90-99%)** this removes the loophole because the revised condition directly matches AGENTS `sanitize before HTML output` and web security’s `unless sanitized first` (`AGENTS.md:98`; `web/security.md:42-45`).

Some require semantic review rather than regex blocking; that is a harness design constraint, not proof the requirements themselves are unreasonable.

It is **very likely (80-90%)** that fixing routing and the existing per-edit hook will improve observability and compliance without a new runtime, because settings already invokes the hook and the security reviewer already exists (`settings.json:333-342`; `agents/security-reviewer.md:92-96`).
