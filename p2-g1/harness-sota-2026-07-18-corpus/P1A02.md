# P1A02 — corpus axis: quoting failures

## Executive finding

The 1,631 failures are **not a population of model-authored unmatched single quotes**. They
are one normalized error fingerprint emitted by the Windows Git Bash invocation boundary:

```text
Exit code 2
/usr/bin/bash: -c: line N: unexpected EOF while looking for matching `''
```

The pinned corpus records exactly 1,631 instances (`corpus/corpus.json:4281-4288`) and
attributes all 1,631 to Bash (`corpus/corpus.json:8841-8847`). Of the 1,630 raw calls that I
could join back to their originating command, **1,009 (61.9%) contain no single-quote
character at all**, and **135 (8.3%) contain neither a single nor a double quote**. A
one-line, quote-free `wc -l ... 2>/dev/null` call fails at Bash's reported **line 94** in a
real transcript (`...\agent-a06ea37553e085f77.jsonl:26-27`). That command cannot itself
open an unmatched single quote, and one authored line cannot itself account for a parser
location at line 94.

The strongest diagnosis is therefore: **very likely (80-90%) the unmatched quote is in
material inserted at or after Claude Code's Bash-tool boundary—most plausibly its generated
shell-state/bootstrap text or argument transport—not in the model-authored command.** The
evidence is (1) the 1,009 commands with no single quote, (2) the line-number displacement on
1,044 one-line commands, (3) all 1,631 errors naming the same `/usr/bin/bash -c` parser, and
(4) three structurally different recorded commands parsing successfully through a direct
Git Bash `-n -c` argv call. The exact corrupting component is **UNVERIFIED — the settling
experiment is a hooks-on/hooks-off canary that captures the final `argv` and/or generated
bootstrap bytes immediately before `exec`, then replays those exact bytes through Git Bash.**

This matters for the fix. “Escape quotes better,” “do not use quoted heredocs,” or “prefer
double quotes” attacks the wrong layer and cannot explain, let alone remove, the majority of
the fingerprint. The smallest robust design is a Windows Bash-script runner on the existing
tool bus that writes the exact script bytes to a temporary `.sh` and invokes Git Bash with an
argv array and `--noprofile --norc <script-file>`, avoiding `-c` and generated shell-state
text. A failure hook should route this exact fingerprint to that runner instead of inviting
another quote rewrite.

## Scope and evidence contract

This unit analyzes only the corpus fingerprint at `corpus/corpus.json:4281-4288`, not the
related 128 double-quote/eval fingerprint at `:8853` and not every possible Bash nonzero
exit. The denominator is the corpus's 108,121 Bash calls and 6,461 Bash errors
(`corpus/corpus.json:13-18`). The corpus states that counts are exact but samples are capped
at 12; it saw 11,633 files, failed to read zero, skipped one bad line and 32 oversized lines
(`corpus/corpus.json:2-11`). I therefore used the corpus for the count and the raw
transcripts for the command-shape join.

The raw tree was still being written after the corpus was produced, so substring counting
alone was unsafe. I reproduced the miner's normalization exactly from
`mine.py:73-89`, required `tool_result.is_error`, and accepted a raw result only if its
normalized full content equaled the pinned fingerprint. The miner itself counts errors by
flattening the error content, normalizing it, and joining `tool_use_id` to its tool
(`mine.py:205-210,243-287`). This detector reconciled to **exactly 1,631** records before the
corpus completion boundary. In contrast, a naive substring detector found 35 earlier
records whose larger/different messages merely contained the same phrase; they were
correctly excluded.

I joined each result's `tool_use_id` and `sourceToolAssistantUUID` to the originating Bash
tool call using 20 prior JSONL records. Coverage was **1,630/1,631 (99.94%)** across **672
transcript files**. The single unjoined call is at
`...\aeb94ff3-639d-48d8-b24a-6f3ee9650c46.jsonl:245172`; its source assistant record is
more than 20 JSONL records earlier, and a targeted scan of that very large transcript did
not complete within the bounded probe. Its construct is unknown and is not silently put in
any denominator below. Counts over command content therefore use 1,630 unless explicitly
stated otherwise; result-only facts use 1,631.

## Exact characterization

### Which shell?

All **1,631/1,631** normalized results name `/usr/bin/bash: -c`. There is no PowerShell,
WSL-shell, `sh`, `zsh`, or nested-`eval` result in this exact fingerprint. A live independent
mapping on this Windows host produced:

```text
Get-Command bash
Source: C:\Program Files\Git\usr\bin\bash.exe

bash -c 'printf ...; command -v bash; cygpath -w /usr/bin/bash'
argv0=/usr/bin/bash
version=5.2.37(1)-release
/usr/bin/bash
C:\Program Files\Git\usr\bin\bash.exe
```

Thus the observed `/usr/bin/bash` name maps to the installed Git for Windows Bash today.
It is **very likely (80-90%)** that this was also the executable family behind the historical
errors because the transcripts have Windows paths/cwds and the live Git Bash reports the
identical POSIX argv0; the exact historical Bash binary/version is **UNVERIFIED — settle it
by joining each call timestamp to retained Claude Code debug logs containing the resolved
executable path and version.** The only safe historical statement is the result's literal
`/usr/bin/bash -c` identity.

Of the 381 heredoc commands, 299 (78.5%) have at least one single-quoted delimiter such as
`<<'EOF'`, `<<'PYEOF'`, or `<<'PY'`; 82 do not. Delimiter occurrences (a command may have
more than one) were led by `<<'EOF'` 178 times, `<<'PYEOF'` 90, and `<<'PY'` 43. Quoted
heredoc delimiters are normal Bash syntax: they disable expansion in the body. A decisive
real command uses both `python - <<'PY'` and `git commit-tree ... <<'MSG'`; the transcript
records the tool call and failure at
`...\09158d9e-df69-4e33-8371-22a2963e3d7d.jsonl:14866-14868`.

I extracted that exact 2,998-character, 47-line command and ran:

```text
C:\Program Files\Git\bin\bash.exe -n -c <exact recorded command>
exit 0; stderr ''
```

That is a syntax-only check and executes none of the command. It proves this decisive
heredoc sample was valid before the Bash-tool boundary; it does not prove every one of the
381 heredoc commands was valid.

## What agent behavior produces and follows the failures?

The agents do use shell-dense composition: 381 heredocs, 345 commands containing Git, 325
containing `grep`/`rg`, 293 containing `echo`/`printf`, and 34 Python heredocs. Those choices
increase the amount of text passed through the boundary and make a transport bug costly.
However, the 1,044 one-line calls and 1,009 commands without single quotes prove that
complex composition is neither necessary nor the dominant causal condition.

The immediate post-error behavior is more revealing. Looking up to ten subsequent JSONL
records after each of the 1,630 paired failures, the next tool was:

| Immediate next tool/action | Count | Share |
|---|---:|---:|
| Bash again | 512 | 31.4% |
| PowerShell | 436 | 26.7% |
| Write | 301 | 18.5% |
| Glob | 163 | 10.0% |
| Read | 93 | 5.7% |
| Grep | 86 | 5.3% |
| No tool within ten records | 17 | 1.0% |
| Other tools | 22 | 1.3% |

Of the 512 immediate Bash retries, only **2** repeat the exact command; **510 (99.6%)**
change it, and 105 of those remove every single quote. Agents are therefore not mainly
blindly replaying unchanged input. They are reacting to a misleading parser message by
rewriting correct shell, changing quote style, decomposing work, or switching tools. The
raw quote-free control explicitly diagnoses a wrapper issue and successfully switches to
PowerShell (`...\agent-a06ea37553e085f77.jsonl:29-31`).

This recovery is locally rational but globally wasteful: the first call is already lost,
and all 510 rewritten Bash attempts still traverse the same native tool boundary. A quote-rule
prompt would reinforce the misdiagnosis. A terminal fingerprint route—“this is the known
Bash transport failure; do not repair command quoting; use the script runner”—matches the
actual evidence.

## Root cause statement

The proximate failure is exact: Git Bash's parser reaches EOF while it believes a single
quote is open, while processing a `-c` input. The authored-command cause is falsified for at
least 1,009/1,630 calls because their stored command contains no single quote. The most
plausible causal chain is:

```text
model emits Bash command
  -> Claude Code / hook invocation layer adds shell-state or transports `-c` text
  -> added/transformed text contains an unterminated single quote
  -> Git Bash parses the combined input
  -> EOF at a stable high line offset (often 94 or 99)
  -> agent sees a misleading quote error and rewrites/switches tools
```

It is **very likely (80-90%)** that corruption occurs after the recorded tool input and
before/during Bash parsing, supported by the quote-free majority, high line offsets, uniform
shell identity, and direct syntax checks. It is only **roughly even (45-55%)** whether the
responsible layer is Claude Code's native Bash bootstrap versus a user hook/environment
snapshot, because this unit did not capture final bytes with hooks disabled. The
hooks-versus-native attribution is **UNVERIFIED — run the byte-capture A/B described below.**

## Fix design

### Recommended fix — UNVERIFIED A/B required — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)

Add one Windows-specific `bash_script` tool on the existing MCP/tool bus, plus one tiny
failure-route hook:

1. Accept `{script, cwd, timeout_ms}` as structured inputs. Validate that `script` is a
   string under a configured size ceiling, `cwd` exists and is a directory, and timeout is
   bounded. Do not interpolate any field into a shell command.
2. Resolve the configured Git Bash executable once. Write `script` as UTF-8/LF to a uniquely
   created temporary `.sh` under a task-scoped temp directory.
3. Invoke it with an argv array equivalent to
   `[bash.exe, --noprofile, --norc, <literal-temp-path>]`, `cwd=<literal cwd>`, redirected
   stdout/stderr, and no intermediate `bash -c`, PowerShell string, or shell-state snapshot.
4. Return a typed terminal result: `SUCCESS:bash-script` plus stdout on exit 0, or
   `FAILED:bash-script exit=N` plus bounded stderr otherwise. Always remove the temp file in
   `finally`; never place secrets in command-line arguments or logs.
5. A `PostToolUseFailure` hook recognizes only this exact normalized Bash fingerprint and
   injects: `FAILED:bash-transport-singlequote; command text is not proven malformed. Route
   to bash_script; do not rewrite/retry native Bash.` Keep only a session-local circuit-breaker
   bit; do not add a new durable runtime.
6. While the native boundary remains unresolved, route **all Windows Bash work**, not only
   heredocs or commands containing `'`, through this runner. A content predicate would miss
   the 1,009 no-single-quote failures.

This proposal rides the existing tool and hook buses and adds no second orchestrator,
vector/KG memory, durable-execution engine, trained critic, observability SaaS, or guardrail
framework. It passes the anti-overfit gate: a small argv-safe adapter removes one measured
platform boundary rather than adding generalized agent scaffolding.

The recommendation is **UNVERIFIED — the settling experiment is a stratified replay of at
least 500 exact recorded commands (one-line/no quote, one-line/quoted, multiline/no heredoc,
quoted heredoc), with hooks on and off, through both native Bash and `bash_script`; capture
final bytes, exit status, stdout/stderr, and verify side-effect-free commands against expected
output.** The build should not be adopted as a universal replacement until that experiment
shows the fingerprint disappears without changing command semantics.

### Why not a rule or prompt-only fix?

- “Avoid single quotes” cannot touch the 1,009/1,630 commands with none. Even under the
  impossible assumption that it perfectly fixes every command that contains a single quote,
  its ceiling is 621 paired calls (38.1%).
- “Avoid heredocs” has a ceiling of 381/1,630 (23.4%) and ignores the 1,249 non-heredoc
  failures.
- “Use shorter/one-line commands” is contradicted by 1,044 one-line failures and a minimum
  command length of two characters.
- “Escape English apostrophes” addresses only 38 detected commands and mistakes comment or
  heredoc-body text for active Bash quoting.
- “Retry with modified quoting” describes what agents already do: 510/512 immediate Bash
  retries change the command, while only 105 remove all single quotes. It spends another
  call without bypassing the implicated boundary.
- “Always switch to PowerShell after failure” succeeds in the quoted raw control and is a
  useful emergency rule, but it does not prevent the first failure and moves work to a tool
  with its own measured 10.6% aggregate error rate. The typed Bash-script runner preserves
  Bash semantics and directly removes `-c`/bootstrap exposure.

### Native upstream alternative

The best long-term repair is for Claude Code's native Windows Bash tool to pass user script
bytes by stdin or a temporary script file and to make any shell-state bootstrap syntactically
safe. I do **not** tag this as `NATIVE` because I found no verified existing setting that
already enables such a path; claiming “we just enable it” would be unsupported. The local
BUILD-SMALL adapter is reversible and supplies the A/B evidence needed for an upstream bug
report.

The exact fingerprint is 1,631/6,461 = **25.2% of all Bash errors** and 1,631/108,121 =

|---|---:|---:|
| Ban heredocs | 381 (23.4% of target) | 5.62% |

| Proactive safe runner for all Windows Bash calls | 1,631 (100% ceiling) | 4.47% |

The reactive ceiling assumes each transcript file is an independent circuit-breaker scope
and the fallback always works; both premises are **UNVERIFIED — settle them by persisting a
session/runtime identifier in the replay and measuring fallback outcomes.** It is a ceiling,
not a forecast.

For the proactive runner, it is **likely (55-80%)** that the first implementation removes
**80-95% of this fingerprint (about 1,305-1,549 historical errors)**. The evidence for a
large effect is that 1,009 commands cannot themselves open a single quote, all 1,631 share
the `bash -c` boundary, and all three exact syntax controls pass direct Git Bash parsing.
The confidence is not higher because final corrupt bytes were not captured, only three
commands were parser-checked, and hooks-versus-native ownership remains unresolved. At 80%
removal the historical Bash error rate would fall from 5.98% to about **4.77%**; at 95%, to
about **4.54%**. These are counterfactual estimates holding all other calls/errors fixed,
not claims about future workload.

It is **very unlikely (5-20%)** that a quote-style prompt alone removes more than half of the
fingerprint, because 61.9% of paired failing commands have no single quote and 64.0% are
already one line. That confidence band is grounded in the exhaustive raw classification,
not an assumption about prompt compliance.

## Verification plan and acceptance criteria

1. **Detector control.** Feed the corpus miner one known target result and one `eval`/larger
   message containing the same substring. It must classify only the exact normalized target.
   The present analysis did this in situ: exact normalization reconciled to 1,631; naive
   substring matching overcounted by 35 before the corpus boundary.
2. **Byte capture.** Run a harmless quote-free canary (`printf ok`) and quoted/heredoc
   canaries with all hooks enabled, then disabled. Capture the exact native Bash executable,
   argv, stdin, generated bootstrap, cwd, and environment delta. This resolves the current
   native-versus-hook attribution.
3. **Replay strata.** Select at least 125 exact commands from each of four mutually useful
   strata: one-line/no quote, one-line/quoted, multiline/no heredoc, and heredoc. Use only
   syntax checks or commands proven side-effect-free for output comparisons.
4. **A/B.** Native Bash versus the BUILD-SMALL script runner, same Git Bash executable and
   cwd. Record parser fingerprint, exit status, stdout/stderr hash, elapsed time, temp cleanup,
   and Unicode/LF behavior.
5. **Pass gate.** Zero occurrences of this fingerprint in the safe-runner arm; at least 99%
   semantic agreement on commands where native Bash produces a non-fingerprint result; no
   temp-file residue; no secret-bearing argv/log output; timeout kills the child tree.
6. **Rollout.** Shadow-log routing decisions first, then route 10%, 50%, and 100% of Windows
   Bash calls. Compare target-fingerprint rate per 1,000 Bash calls, overall nonzero rate,
   latency, and mismatched output—not raw error counts alone.

It is **almost certain (90-99%)** that this experiment distinguishes authored-syntax failure
from invocation/bootstrap corruption because it captures the missing causal object—the
actual bytes Bash parses—and includes known-present controls. Evidence is that transcript
input and parser result are already joinable, while the only missing relation is the final
transport/bootstrap representation.

## Alternatives considered and dead ends

1. **Trust the corpus's 12 sample filenames as representative.** Rejected. The corpus
   explicitly caps samples (`corpus/corpus.json:11`); prevalence came from all 1,631 raw
   normalized results, not the capped list.
2. **Count raw substring matches.** Rejected after detector falsification. It included 35
   earlier messages with different normalized prefixes such as `eval` or larger child output.
3. **Scan all 10.62 GB with a Python full-file join.** Abandoned after a bounded 64-second
   attempt produced no counts. The successful method used ripgrep context and exact UUID/tool
   joins, then reported its 1/1,631 miss.
4. **Use the required `longrun.ps1` wrapper for that scan.** Two launch attempts yielded a
   running tool cell but, by independent process inspection and TEMP inspection, neither a
   labeled wrapper/child process nor any declared log file existed. This failure is recorded
   in the event ledger as #25 with the falsifiable precondition. Direct bounded `rg` completed
   in 8.1 seconds. This operational dead end does not affect the corpus conclusions.
5. **Target the single missing source call with another scan.** The targeted scan of the
   245k-line transcript did not finish promptly and was stopped. I leave the command shape
   as a one-record gap rather than infer it.
6. **Infer a bad Claude Code version from counts.** Rejected because failures lack successful
   per-version denominators.
7. **Claim every recorded command is valid Bash.** Rejected. Three decisive samples passed a
   real parser; the corpus cannot establish validity for every command without a full replay.

## Gaps — what the corpus cannot answer

- The corpus does not preserve the final bytes/argv/bootstrap presented to Bash. Therefore it
  cannot distinguish native Claude Code mutation from hook/environment snapshot mutation.
- It has no per-version, per-model, per-day, or per-command-shape Bash success denominators,
  so it cannot calculate relative risk for those strata.
- It does not retain an explicit command-to-fingerprint table; this unit reconstructed it from
  raw transcripts. One of 1,631 source calls remained beyond the bounded context join.
- It cannot tell whether a transcript file is the correct circuit-breaker scope or whether
  several subagents share one corrupted shell snapshot.
- It cannot predict safe-runner semantic compatibility for environment persistence, aliases,
  functions, interactive commands, signals, and child-tree termination. The A/B replay must
  measure these.
- It cannot establish the historical Git Bash patch version. The live executable mapping is a
  current control, not a historical version record.
- It cannot prove absence of additional quoting-related fingerprints outside the one assigned
  axis. This unit intentionally excludes the corpus's related `eval`/double-quote rows.

## Bottom line

The exact answer is counterintuitive but strong: **1,631 is a Bash invocation failure class,
not a count of agents forgetting to close quotes.** Heredocs account for 23.4%; one-line calls
account for 64.0%; 61.9% contain no single quote; all results come from `/usr/bin/bash -c`;
and the parser often reports line 94 or 99 for a one-line input. Agents then mostly rewrite
the command or switch tools, wasting a call in response to a misleading message.

Build the small argv-safe script runner, route this terminal fingerprint to it, and run the
byte-capture A/B before full rollout. Do not add a general orchestration layer, and do not
teach the model a quote superstition that the data directly falsifies.
