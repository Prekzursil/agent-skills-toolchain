## Executive conclusion

This snapshot has genuine duplicate-authority drift. I found **eight conflict families** that can
produce different behavior for the same operator intent depending on whether Claude follows the
slash-command prompt in the parent or delegates to the nominally corresponding custom agent. The
highest-impact conflicts are:

1. `/orchestrate` requires a Markdown handoff while the reviewer agents it explicitly invokes
   require their final message to be exactly one JSON envelope.
2. `/e2e` mandates Playwright while its explicitly named `e2e-runner` agent says to prefer Agent
   Browser and use Playwright only as fallback.
3. The `codex` agent prohibits the heredoc/wrapper transport that the multi-backend command family
   mandates.
4. `/code-review` blocks on HIGH findings while `code-reviewer` says HIGH findings are only a
   warning and may merge with caution.

These are not merely similar prose. Each has a concrete execution fork and incompatible operative
instructions. The runtime has **no global “agents beat commands” or “commands beat agents” rule**.
The command body is a prompt in the main conversation; a custom agent body becomes that agent's
system prompt. In a delegated run, the agent body governs the worker while the command continues to
govern the parent/orchestrator. That is exactly why the current arrangement produces split-brain
results rather than a stable winner.

I am **almost certain (90-99%)** about that loading model because Claude Code's current official
documentation states that legacy `.claude/commands/*.md` files work as prompt-based skills and that
a custom agent's Markdown body becomes its system prompt; it also states that a delegated agent
receives an agent system prompt plus a task message composed by the parent. Evidence:
<https://code.claude.com/docs/en/slash-commands> (lines 116-120 and 118 in the retrieved page) and
<https://code.claude.com/docs/en/sub-agents> (retrieved lines 290-305, 629-648, and 756-766).
The local snapshot independently enables fork subagents at
`/local_disk0/codexwork/bundle/claude/settings.json:4-7`, and its SubagentStart hook injects a
spawn-contract reminder at
`/local_disk0/codexwork/bundle/agents/harness/modules.py:2355-2367`.

## Runtime model: which text wins

The correct answer is contextual, not a single precedence list:

1. Invoking a legacy custom command expands/loads its Markdown as a prompt-based workflow in the
   **main conversation**. Official evidence:
   <https://code.claude.com/docs/en/slash-commands>, retrieved lines 116-124.
2. Delegating to a custom agent starts a worker whose Markdown body is its **system prompt**, plus a
   task message written by the parent. Official evidence:
   <https://code.claude.com/docs/en/sub-agents>, retrieved lines 290-305 and 756-766.
3. Therefore, inside the worker the agent body's mandatory instruction is the higher-authority
   instruction relative to an incompatible delegation/task message. In the parent, the command
   prompt still controls orchestration and interpretation of the returned report.
4. For command/agent pairs that do not explicitly delegate, the selected entry point wins simply
   because the other full body is not loaded. Claude sees agent descriptions for routing, not every
   agent body's entire procedure. This creates entrypoint-dependent behavior rather than an
   instruction-precedence resolution.
5. The local fork setting (`settings.json:5`) makes parent/worker coupling especially relevant, but
   it does not create a canonical source of truth. The lifecycle hook only asks for a structured
   summary (`modules.py:2362-2367`); it does not reconcile any of the substantive conflicts below.

Confidence is **very likely (80-90%)** for the precise parent/worker outcome on this owner's
installed build: official current docs and local settings agree, but the installed binary could not
be smoke-tested here. The exact experiment named in the preceding UNVERIFIED paragraph would settle
the remaining uncertainty.
