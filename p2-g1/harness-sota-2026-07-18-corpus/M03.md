# M03 — Calibrated escalation: when to stop and ask versus proceed

## Executive conclusion

The harness does not need another generic “ask more questions” rule. It needs one explicit, measurable decision policy that distinguishes (1) uncertainty the agent can cheaply resolve from external evidence, (2) owner-only intent or consent, (3) reversible preparation, (4) consequential commitment, and (5) runtime anomaly. The default should be: **continue gathering reversible external evidence; ask only when the owner’s answer can change a consequential next action or when independent runtime signals prove that autonomous progress has stopped; preserve every paused thread before asking.**

This recommendation is **very likely (80-90%)** to reduce both unnecessary interruptions and costly silent bets, because the corpus contains direct owner corrections on both sides: repeated “why did you stop / proceed” signals, explicit requests for autonomous loops, an after-tool-use “wait do not delete,” and owner-detected hung tests. The cited evidence is `corpus.json:10425-10426`, `:12119-12127`, `:11201-11204`, and `:12161-12164`. The range is not higher because the distilled corpus does not preserve complete preceding assistant turns for most sampled owner messages, and its correction miner explicitly warns that it is recall-biased (`corpus.json:10371-10374`).

All eight proposals below ride the existing shared dispatcher, event ledger, `note.py`, `AskUserQuestion`, `Workflow`, `longrun`, open-loop store, calibrated-silence code, or harness-bench. They add **zero raw hook surfaces**, so they remain under the ~6-hook ceiling by folding into an existing bus. None introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. All hooks remain fail-open: exceptions produce no block and exit 0. No same-context self-review is accepted as verification anywhere in this design.

## Grounding and method

### Corpus fitness and limits

The distillation covers 11,633 files and 10.62 GB, with zero failed files, one bad line, and 32 oversized lines; it says counts are exact while samples are capped (`corpus.json:2-11`). This is strong coverage for rates and repeated normalized patterns, but not for reconstructing complete conversational causality. The owner-correction detector found 2,268 candidates among 8,441 owner messages, yet explicitly says an unfiltered smoke sample was 41/41 false positives because agent-authored prompts leaked into the class (`corpus.json:10371-10374`). I therefore use only individually inspected, plainly owner-voiced samples as qualitative incidents; I do not report 2,268 as “mistakes.”

The corpus hook section is unusable: it explicitly says its known-positive control failed and the entire section is “NO DATA” (`corpus.json:13260-13263`). No finding below infers that a hook did not fire from that section.

### Observed over-escalation / premature stopping

* The normalized owner message “why did you stop proceed until you finish everything” occurs 12 times in stop-hook feedback (`corpus.json:10425-10426`), with a separate unprefixed pattern occurring twice (`corpus.json:10565-10570`). These are two mechanically different corpus fields—stop-feedback normalization and direct owner-pattern normalization—supporting the conclusion that premature stopping is a recurring owner pain, not a single quotation duplicated by my search.
* The owner explicitly said “nope you can proceed” and shortly afterward requested autonomous loops and multi-agent orchestration while retaining quality gates (`corpus.json:12119-12127`). This is direct evidence that autonomy is desired after scope is settled.
* “yeah ive already told you to do that, finish it” (`corpus.json:11339-11342`) is evidence of repeated authorization being forgotten. “ask me again since we got interrupted” (`corpus.json:11171-11174`) is the converse continuity failure: a warranted pending question was dropped.
* `AskUserQuestion` itself is a mature native capability—1,329 calls at 2.93% recorded tool error (`corpus.json:135-140`). The gap is selection and continuity, not lack of an asking actuator.

### Observed under-escalation / proceeding when intervention was due

* “wait do not delete the installers” arrived after tool use (`after_tool_use: true`) during disk cleanup (`corpus.json:11195-11204`). This is direct evidence that a broad cleanup instruction did not encode consent for every deletion target. It does not prove installers were deleted; it proves the owner needed to revoke/narrow the action after execution had begun.
* The owner noticed a test still running after 26m59s with no output and asked to review then proceed (`corpus.json:12161-12164`); later the owner again said the tests should not take that long and asked for verification before proceeding, also after tool use (`corpus.json:12203-12206`). Two temporally separate owner interventions support a runtime-anomaly escalation gap.
* The corpus independently records retry runs: 53 Read runs, 14 Bash runs, and six TaskOutput runs (`corpus.json:10297-10330`). These counts do not identify the hung-test incident, but they are an independent signal that repeated-action behavior exists and deserves a mechanical pivot path.
* Tool-use rejection has a normalized error fingerprint count of 533 across many sessions (`corpus.json:4335-4344`). A rejection is not always an autonomy mistake, but it is an external consent signal that must immediately override any cached permission.
* The live-defects report documents six wrong conclusions from single unvalidated probes and a seventh case where a known-positive control separated two working detectors from the actually broken hooks detector (`INPUT-known-harness-defects.md:111-129`). This is why every proposed uncertainty resolution below ends at an external signal, not an agent’s same-context confidence.

### Existing mechanisms and dedup boundary

The cross-tool contract already says to ask 1–3 questions only in the first 1–2 actions, never mid-task, and to use EVPI (`claude/AGENTS.md:7-12`); it also requires external fresh-context re-derivation after two strikes (`claude/AGENTS.md:51-57`), reserves blocking for irreversible/dangerous actions, and requires fail-open hooks (`claude/AGENTS.md:64-70`). The local inquisitiveness implementation is only a lexical vagueness scorer: concrete tokens force silence, vague verbs/pronouns raise a score, and the emitted text asks the same agent to decide whether material ambiguity remains (`claude/hooks/inquisitiveness/prompt-guard.py:52-82`, `:108-159`). That last step is rejected by this unit’s law when treated as a check, because it closes inside the same context.

The calibrated-silence module already models interjections as a signal-detection decision and claims to learn from next-turn behavior (`claude/hooks/calibrated-silence/calibrated_silence.py:2-25`, `:39-53`). Its reaction logger, however, classifies **any** non-dismissive reply of at least five words to a question as `acted`, and otherwise collapses outcomes to acted/annoyed/ignored (`claude/hooks/calibrated-silence/log_reaction.py:8-14`, `:100-151`). A five-word correction, revocation, or “you already asked this” can therefore reward the question.

In the unpacked bundle’s active Claude settings, `UserPromptSubmit` wires only the shared dispatcher and selection-event emitter (`claude/settings.json:117-138`). Neither `inquisitiveness` nor `calibrated-silence` appears there. As a detector control, the same settings probe successfully finds the known-present `loop-recovery` PreToolUse command (`claude/settings.json:228-237`); an independent manifest probe finds open-loop and background-digest entries but no inquisitiveness or calibrated-silence entry (`claude/hooks/_dispatch/manifest.json:53-63`). Thus it is **almost certain (90-99%)** that these two local scripts are not directly active in this bundle snapshot, based on two configuration surfaces plus the known-present control. This is not a claim about a running Windows process or environment overrides. **UNVERIFIED in the live Windows harness; the settling experiment is a fresh-session known-positive vague prompt plus inspection of the shared hook event ledger for the inquisitiveness marker.** Any recommendation depending on runtime activation is marked accordingly.

## Decision policy to implement

For each pending action, compute a small deterministic record, not an LLM self-score:

`decision = {owner_only, consequence, reversibility, scope_match, external_probe, anomaly_signals, lease_state, open_threads}`

Proceed when the action is in scope, reversible or checkpointed, and either its uncertain premise has an external probe or the uncertainty does not change the next action. Ask when an owner-only variable changes the consequential branch, consent is missing/revoked, or two mechanically independent anomaly signals show that autonomous progress has stopped. While waiting, continue independent, reversible lanes. Never interpret the same model restating the task as verification.

The precise thresholds below are initially shadow-evaluated. **UNVERIFIED whether the proposed policy beats the current behavior; the settling experiment is Finding 8’s replay plus a 30-session prospective shadow comparison of interruption regret and silent-bet regret.**

## Finding 1 — Consent leases, not repeated permission prompts

**Improvement — inferred surprise — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Add a scoped “autonomy lease” record to the existing event ledger. A lease captures the owner-authored objective, allowed mutation scope, explicitly excluded targets, external side effects, spending/credential bounds, destructive-action rule, and expiry conditions. It is not time-based by default: it remains valid until scope, consequence class, repository/worktree, or owner intent changes. A tool rejection or explicit stop/revoke invalidates the matching action family immediately.

**What it is:** This converts conversational permission into a structured capability envelope. “Proceed,” “do everything required,” and “still autonomous” authorize work inside the recorded objective; they do not authorize unrelated deletion, secret access, billing, publishing, or broader scope. The agent does not ask again for actions already inside the lease. It does ask at the first owner-only boundary outside it. Peer/subagent messages can supply evidence but can never widen the lease.

**Why inferred:** The owner repeatedly asks the system to continue (`corpus.json:10425-10426`) and explicitly requests autonomous loops (`corpus.json:12125-12127`), while also narrowing a cleanup after execution began (“do not delete the installers,” `corpus.json:11201-11204`). The desired behavior is neither blanket autonomy nor blanket confirmation; it is durable, scoped delegation.

**How to build:** Extend the existing ledger event schema with `autonomy_lease` and `lease_revocation` event types. On `UserPromptSubmit`, the shared dispatcher extracts only explicit owner phrases and scope objects into a proposed lease delta; the active agent writes the final lease through `note.py` after grounding targets from repository state. On `PreToolUse`, reuse the existing irreversible/action classifier to compare target and effect class against the lease. In-scope reversible actions inject nothing. Out-of-scope consequential actions inject one AskUserQuestion route. Rejection events append a revocation keyed by normalized target/effect, not a global “user dislikes autonomy.” Exceptions exit 0. This folds into the shared dispatcher; it does not activate the local inquisitiveness hook as a seventh surface.

**External signal that verifies it:** (1) the owner’s explicit prompt/reply or native tool-rejection event establishes consent/revocation; (2) the actual tool target/diff/API receipt establishes what the action did. Acceptance test: replay `proceed` followed by ordinary in-scope edits and observe zero repeated questions; replay cleanup plus an excluded installers target and observe a single question before the destructive call; replay a rejection and observe that the exact action family is not retried. The answer is never inferred from the agent’s own restatement.

**SOTA:** Horvitz’s mixed-initiative principles frame interaction as action under uncertainty and expected utility ([Principles of Mixed-Initiative User Interfaces](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz-1.pdf)). Amershi et al.’s validated human-AI guidelines include supporting efficient invocation, dismissal, correction, and learning from user behavior ([Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). NIST emphasizes real-time monitoring and the ability for humans to stop or modify systems that deviate from intended operation ([AI Risks and Trustworthiness](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).

**Value × effort:** transformative × medium.

**Novelty:** inferred-surprise.

**Autonomy:** just-do-it for schema/code in shadow mode; confirm-first before enabling enforcement because it changes when consequential actions pause.

**Confidence:** **very likely (80-90%)** to reduce repeated authorization burden while retaining narrow veto power, based on the paired corpus signals above and the existing ledger/PreToolUse bus. The benefit magnitude is **UNVERIFIED; the settling experiment is the replay and 30-session shadow evaluation in Finding 8.**

## Finding 2 — The reversible frontier: prepare autonomously, confirm only the commitment

**Improvement — inferred surprise — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Replace the binary ask/proceed rule with a “reversible frontier.” The agent advances through read-only discovery, dry-runs, isolated worktrees, checkpoints, local edits with rollback, tests, and draft artifacts without asking. It stops only at the first action whose consequences cannot be cheaply reversed or whose branch depends on owner-only preference.

**What it is:** A two-phase interaction contract: **prepare** and **commit**. Preparation gathers external evidence and reduces ambiguity. Commitment includes deletion without a verified recovery path, force/history rewrite, sending/publishing, purchases/billable compute above a bound, secrets/credentials, modifying live process/device state, or changing targets outside the autonomy lease. If a prepared diff makes both options equivalent, no question is needed. If two materially different owner-valued outcomes remain, show the evidence and ask once.

**Why inferred:** The owner wants uninterrupted autonomous work (`corpus.json:12125-12127`) but had to protect installer targets after a cleanup tool action (`corpus.json:11201-11204`). The existing contract’s absolute “Never ask mid-task” (`claude/AGENTS.md:7-12`) handles prompt fatigue but cannot safely represent newly discovered consequential forks or owner revocation. A phase boundary does.

**How to build:** Add a compact `effect_classes.json` consumed by the existing PreToolUse dispatcher: `read`, `reversible_write`, `checkpointed_write`, `external_side_effect`, `irreversible`, `owner_preference`. Map known tools/verbs to defaults; unknown tools default to advisory classification, not blocking, to preserve fail-open. Before any `external_side_effect`/`irreversible` class, require an external rollback receipt (checkpoint ID, backup path verified readable, dry-run output, transaction preview) and an in-scope lease. If either is missing, route to one confirmation. Modify AGENTS §1 from “never ask mid-task” to “never ask mid-task for resolvable implementation ambiguity; ask at a newly discovered owner-only or consequential commitment boundary.”

**External signal that verifies it:** Readability of the generated checkpoint/backup plus a dry-run/diff is the preparation signal; the owner’s answer is the commitment signal. After execution, a separate command/API read verifies the final state. A same-context “this is reversible” statement has no standing.

**SOTA:** The 2026 Value-of-Information framework explicitly balances expected utility from asking against cognitive cost and task stakes ([Value of Information: A Framework for Human–Agent Communication](https://aclanthology.org/2026.acl-long.1987/)). Horvitz’s mixed-initiative work similarly models whether to act or enter dialogue using expected utility ([Mixed-Initiative Interaction](https://www.microsoft.com/en-us/research/publication/mixed-initiative-interaction/)).

**Value × effort:** transformative × medium.

**Novelty:** inferred-surprise.

**Autonomy:** confirm-first for enabling the revised enforcement boundary; just-do-it for shadow classification and replay tests.

**Confidence:** **very likely (80-90%)** to dominate a blanket “ask early only” rule for this owner, because it directly fits both the autonomy and post-tool revocation evidence. **UNVERIFIED on the owner’s real task mix; the settling experiment is a shadow confusion matrix over 30 sessions, with owner corrections and tool rejections as labels.**

## Finding 3 — Interruption-budgeted escalation at natural breakpoints [UNVERIFIED live activation; run known-positive wiring probe]

**Improvement — inferred surprise — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Consolidate the dormant/partial inquisitiveness and calibrated-silence logic into the shared `UserPromptSubmit` dispatcher and add a bounded-deferral queue. Optional questions wait until a task breakpoint; safety/consent revocations surface immediately; multiple low-urgency questions are compressed into one decision packet.

**What it is:** Each proposed interjection receives `urgency`, `deadline`, `decision_key`, and `estimated_user_cost`. The queue emits at most one packet per natural breakpoint (tool failure terminal state, plan boundary, test completion, user status request, or before commitment). A mandatory consent boundary bypasses fatigue suppression. A suggestion or low-value clarification may be deferred, merged, or dropped. This uses the owner’s focus as a scarce resource without creating silence that loses urgent information.

**Why inferred:** Prompt fatigue is a hard constraint, while the owner also reports interrupted questions (`corpus.json:11171-11174`). Existing calibrated-silence explicitly models fatigue and next-turn reactions (`calibrated_silence.py:2-53`), but the bundle wiring evidence above indicates that the local scripts are not directly active, and the current reaction semantics reward any substantive reply (`log_reaction.py:100-151`). The right move is consolidation and corrected outcomes, not another hook.

**How to build:** Port `should_interject` as a library module under the shared harness; invoke it from the already-wired shared `UserPromptSubmit` and Stop/PreToolUse paths. Add an append-only `pending_interjections` ledger record keyed by decision. Flush only at breakpoints. Fold the open-loop trigger and background digest into the same packet renderer while preserving their separate stores. Cap the visible packet at one recommended choice plus two alternatives and “continue with safe default.” Remove or archive the unwired duplicate local entrypoints only after the known-positive live experiment proves shared parity. Failures leave items queued and exit 0.

**External signal that verifies it:** Breakpoint detection comes from terminal tool/Workflow/longrun status, not model prose. Use owner next-turn choice, explicit dismissal, repeated authorization complaint, and tool invocation to label usefulness. Measure questions per owner hour, repeated-question rate, unanswered-decision age, and corrections after silent proceeds. A pending item is “not dropped” only if its ledger key is later closed by an owner answer or external completion receipt.

**SOTA:** Bounded deferral balances awareness against interruption cost ([Balancing Awareness and Interruption](https://www.microsoft.com/en-us/research/?p=316112)); notifications are less disruptive when relevant or queued until key operations complete ([Instant Messaging: Effects of Relevance and Timing](https://www.microsoft.com/en-us/research/publication/instant-messaging-effects-of-relevance-and-timing/)); Oasis aligns delivery to task structure ([Oasis](https://www.microsoft.com/en-us/research/?p=161181)).

**Value × effort:** high × medium.

**Novelty:** inferred-surprise.

**Autonomy:** confirm-first before replacing live interjection wiring; just-do-it for parity tests and shadow queue logging.

**Confidence:** **likely (55-80%)** to reduce focus disruption without losing decisions, based on interruption research and the existing queue/ledger substrate. The lower band reflects **UNVERIFIED live activation and unknown breakpoint precision; settle with a known-positive vague prompt, event-ledger marker inspection, and a two-week shadow A/B by session.**

## Finding 4 — Escalation escrow: asking must never drop a thread

**Improvement — inferred surprise — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Make every blocking question atomically escrow the current work state into the existing event ledger/open-loop store before it is shown, then continue all independent reversible lanes.

**What it is:** An escalation record contains `decision_key`, exact owner question, recommended default, alternatives, evidence paths, blocked actions, still-runnable actions, active Workflow/task IDs, changed files/checkpoint ID, and resumption predicate. The question and escrow share an ID. On the next owner turn, the dispatcher matches the answer to that ID, closes it, and injects the exact resumption action. If the user changes subjects, the decision remains open and resurfaces at a low-cost breakpoint rather than disappearing.

**Why inferred:** “ask me again since we got interrupted” is a direct lost-question incident (`corpus.json:11171-11174`); “yeah ive already told you to do that, finish it” shows the reverse loss of an answered decision (`corpus.json:11339-11342`). The existing contract already makes the event ledger objective continuity ground truth (`claude/AGENTS.md:28-34`) and open-loop triggers already persist and fire user-authored intentions once (`claude/hooks/open-loops/trigger_match.py:2-20`, `:90-136`). This finding builds on those rather than creating memory v2.

**How to build:** Add `decision_opened`, `decision_answered`, and `decision_closed` ledger events and a renderer in `AskUserQuestion`. Before emitting, call existing `note.py` with the structured record and verify the append by reading back its ID. If append verification fails, fail-open: ask anyway, but include a compact inline resumption token. On reply, match explicit option ID first, then decision key; never use semantic similarity alone for consequential decisions. Register independent lanes as children and let Workflow continue them. At SessionStart/compaction, reuse open-loop replay to surface the oldest actionable unresolved decision, capped by the interruption budget.

**External signal that verifies it:** The independent signals are (1) the durable read-back of the decision record and (2) the actual task/Workflow/checkpoint status. Completion requires an owner answer event plus a tool/diff/test receipt closing every blocked child. The same agent saying “I’ll remember” is not evidence.

**SOTA:** Amershi et al. emphasize supporting correction, dismissal, and efficient interaction over time ([Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)). ProductAgent’s evaluated design maintains structured dialogue state and asks strategic clarification questions rather than treating each turn independently ([ProductAgent](https://aclanthology.org/2025.emnlp-industry.25/)).

**Value × effort:** high × low.

**Novelty:** inferred-surprise.

**Autonomy:** just-do-it.

**Confidence:** **almost certain (90-99%)** that durable question/answer IDs prevent the specific “asked then forgotten / answered then re-asked” class when the ledger is available, because closure is mechanically keyed and externally read back. End-to-end reliability is **very likely (80-90%)**, reduced by possible ledger/Workflow outages; fail-open inline tokens and replay tests are the evidence-backed mitigation.

## Finding 5 — Runtime anomaly escalation based on two independent signals

**Improvement — inferred surprise — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Extend existing `longrun`/loop-recovery behavior with a two-signal anomaly state machine. A long job does not ask merely because it is slow. It first probes; it asks only when progress is absent or a recovery choice genuinely belongs to the owner.

**What it is:** States: `healthy`, `slow-but-progressing`, `suspect`, `stalled`, `recovered`, `needs-owner`. Example independent signals: heartbeat age plus log-byte/mtime delta; process liveness plus child CPU/I/O delta; test runner state plus framework-specific hang/timeout artifact. Two observations from one file are not independent. On `suspect`, perform one bounded diagnostic/read-only recovery. On `stalled`, terminate only if the lease and longrun policy authorize it and the process has a recoverable checkpoint; otherwise escrow and ask with evidence.

**Why inferred:** The owner, not the harness, caught a test at 26m59s with no output (`corpus.json:12161-12164`) and later again asked to verify abnormally long tests (`corpus.json:12203-12206`). The contract already requires `longrun` for >60s work and heartbeat/hang timeouts (`claude/AGENTS.md:41-49`), while loop recovery currently asks after repeated action/failure (`claude/hooks/loop-recovery/handler.py:10-23`, `:169-181`). The missing piece is joining runtime signals to the escalation decision.

**How to build:** Add anomaly thresholds per operation class to existing longrun config, not a new monitor. Have longrun write heartbeat and progress counters. The existing loop-recovery/shared dispatcher reads both the longrun receipt and OS/process probe. At two-signal stall, it emits `FAILED:<id>` and an escalation escrow with: wait with new deadline, capture diagnostics/restart from checkpoint, or stop this lane and continue others. Fold taskwatch if/when its active wiring is separately verified; do not create a daemon.

**External signal that verifies it:** A controlled fixture runs (a) a quiet but CPU-progressing job, (b) a sleeping live process with no progress, (c) a dead child with stale heartbeat, and (d) a test producing periodic progress. Expected classifications require two independent probes. The owner is asked only for case (b) when stop/restart consent is absent; terminal process/test receipts verify recovery.

**SOTA:** Horvitz and Apacible model expected interruption cost from multiple event streams ([Learning and Reasoning About Interruption](https://www.microsoft.com/en-us/research/?p=166976)). NIST recommends real-time monitoring and human intervention for deviation from intended functionality ([AI Risks and Trustworthiness](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)).

**Value × effort:** high × low.

**Novelty:** inferred-surprise.

**Autonomy:** just-do-it for shadow classification and fixtures; confirm-first for auto-termination defaults.

**Confidence:** **very likely (80-90%)** to catch the observed no-output hang class before the owner does, because longrun already defines heartbeats and the second OS/process probe is independent. **UNVERIFIED for all Windows test runners; settle with the four controlled fixtures under PowerShell 7 and Git Bash plus one real `dotnet test` hang injection.**

## Finding 6 — Ask only questions with counterfactual action value

**Improvement — user-asked — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Replace lexical vagueness scoring with a structured question-worthiness contract. A question is eligible only if two plausible answers produce materially different next actions, the distinction cannot be resolved by an external probe, and the expected consequence of choosing wrong exceeds the interruption cost.

**What it is:** For every candidate question, produce machine fields: `unknown`, `answer_domain`, `action_if_A`, `action_if_B`, `external_probe`, `wrong-choice_cost`, `delay_cost`, `owner_only`. If `action_if_A == action_if_B`, proceed. If an external probe exists, run it. If the variable is aesthetic/product preference or consent, ask. If the question merely requests reassurance, suppress it. Ask no more than three mutually exclusive items, with the recommended default first and a statement of what safe work continues while waiting.

**Why inferred:** The current inquisitiveness code equates concrete paths/errors with clarity and vague verbs/pronouns with uncertainty (`prompt-guard.py:52-82`, `:108-144`), then asks the same agent to decide whether ambiguity remains (`:147-159`). A concrete command can still hide a dangerous target choice; a vague request can often be grounded by reading the repository. The owner’s “nope you can proceed” (`corpus.json:12119-12122`) is consistent with a question whose answer did not change the plan, while “do not delete the installers” (`:11201-11204`) is a branch-changing constraint.

**How to build:** Implement the record as a small pure function in the shared dispatcher. Populate tool parameters and effect classes deterministically. Query repository/tool schemas or run read-only discovery for resolvable fields. For borderline high-consequence cases, send only the structured record—without the current model’s rationale—to a fresh-context verifier or deterministic policy test; this satisfies the external-context law. The verifier may veto “proceed” but cannot grant consent. Log candidate, disposition, and later outcome for Finding 8.

**External signal that verifies it:** External schema/repository/tool output resolves non-owner fields; owner replies resolve preferences/consent; execution/test/API results reveal whether the selected branch worked. A replay suite checks that removing the owner answer would change the next action for every emitted question.

**SOTA:** SAGE-Agent separates specification uncertainty from model uncertainty and uses expected value of perfect information; it reports 7–39% higher coverage with 1.5–2.7× fewer questions than baselines ([Structured Uncertainty Guided Clarification](https://aclanthology.org/2026.findings-acl.2028/)). Earlier grounded-dialog work finds that well-calibrated predictive probabilities improve ambiguity detection ([Aligning Predictive Uncertainty with Clarification Questions](https://aclanthology.org/2023.findings-emnlp.999/)). Testoni and Fernández also show model uncertainty does not simply mirror human clarification behavior ([Asking the Right Question at the Right Time](https://aclanthology.org/2024.eacl-long.16/)).

**Value × effort:** high × medium.

**Novelty:** user-asked.

**Autonomy:** just-do-it in shadow; confirm-first before replacing live question selection.

**Confidence:** **very likely (80-90%)** that counterfactual action value is a better selector than the present word heuristic, based on the code inspection and controlled results from structured-uncertainty research. Transfer to this heterogeneous tool fleet is **UNVERIFIED; settle with Finding 8’s labeled replay and a prospective shadow run.**

## Finding 7 — Learn from corrections without teaching the wrong lesson

**Improvement — user-asked — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** Replace `acted/ignored/annoyed` as the sole learning target with outcome-specific reactions: `answered-usefully`, `confirmed-existing-lease`, `corrected-assumption`, `narrowed-scope`, `revoked-consent`, `message-mistake`, `ignored`, and `dismissed-no-value`.

**What it is:** Calibration must learn *why* the owner replied. “Nope, proceed” should lower the bar for repeated confirmation in that scope. “Wait, do not delete installers” should tighten target classification, not globally reduce autonomy. “I sent you the msg by mistake” should cancel that prompt’s policy effect entirely. A substantive correction must never count as proof that asking was useful unless the question actually preceded and elicited the missing fact.

**Why inferred:** The current logger marks any substantive response to a question as `acted` (`log_reaction.py:143-151`). The corpus contains an after-tool-use revocation (`corpus.json:11201-11204`), an after-tool-use mistaken message (`:11279-11282`), explicit proceed authorization (`:12119-12122`), and repeated authorization frustration (`:11339-11342`). Collapsing these into success/dismissal will move thresholds in contradictory directions.

**How to build:** Add deterministic high-precision phrase/event rules for explicit `stop`, tool rejection, `proceed`, `already told`, and `mistake`; leave ambiguous reactions `unknown`. Correlate by decision ID and chronology: a reply can be `answered-usefully` only when an open question record predates it. Use tool rejection as `revoked-consent` for the exact target/effect. Periodically sample `unknown` rows for a fresh-context second-model label, but never let that model widen authority. Update calibrated-silence separately by interjection type, project, and consequence class; require a minimum sample count before changing thresholds.

**External signal that verifies it:** Native rejection events, chronological decision IDs, subsequent tool calls, owner corrections, and actual diff/API effects are the labels. A blinded replay compares deterministic labels against a second-context reviewer; disagreements remain `unknown` until owner behavior or execution resolves them.
