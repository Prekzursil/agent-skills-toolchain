# A013 — Coherence audit: rules versus hooks / duplicate authority

Date: 2026-07-19 (UTC)  
Subject snapshot: `/local_disk0/codexwork/bundle/claude`  
Scope: every supplied file below `rules/**` and every supplied `hooks/**/*.py`; runtime registration was resolved through `settings.json` and `_dispatch/manifest.json`.

## Executive result

I found **six real duplicate-authority conflicts** in the supplied snapshot:

1. the general Python rule says to fail fast, log detailed context, and never silently swallow errors, while every one of the 34 snapshot-wired Python hook paths explicitly adopts silent fail-open behavior;
2. the behavioral rule limits the force-push prohibition to `main/master` without approval, while the blocking hook denies every `git push` containing `--force`, `--force-with-lease`, or `-f`, on every branch;
3. terminal-state discipline requires receipt **AND** postcondition, while `bg-registry/done_marker.py` records `done` from artifact alone **OR** synchronous turn-end alone;
4. two-signal verification requires independent corroboration before `up`/`DOWN`, while `heartbeat.py` emits either state from one TCP-connect observation;
5. the same verification rule rejects a one-signal persistence conclusion, while `memory-spool/flush_check.py` changes state to `failed` and tells Claude “Memory is NOT persisted” from one tool-response classification;
6. the same verification rule forbids a disruptive “down” conclusion from one probe, while `re-autolaunch/autolaunch.py` treats an empty TCP-port probe as “backend down,” may start a heavy backend, and may deny the pending tool call.

The first two are distinct policy-scope collisions. Findings 3–6 are four separate runtime manifestations of one duplicated authority: terminal/state truth is specified centrally in a rule but independently redefined in hook code.

Confidence in the six findings is **almost certain (90-99%)**. Evidence is: full source inspection, two independent wiring fields (`settings.json` command entries plus dispatcher-manifest membership where applicable), existing tests that encode the disputed behaviors, direct isolated executions of the relevant functions/scripts on this job node, and official Claude Code runtime semantics. The remaining uncertainty is platform/config activation: whether the supplied snapshot is byte-for-byte the live Windows configuration is **UNVERIFIED; settle it by running `claude --debug`, invoking one controlled trigger per hook on the Windows owner box, and comparing the loaded hook commands and `InstructionsLoaded` events with this snapshot**.

This is not a proposal for another runtime. Every minimal resolution below uses the existing `.claude/rules` and native hook buses. None introduces a second orchestrator, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework.

## 2. Finding 1 — global “never swallow/fail fast” rule versus universal hook fail-open

**Conflict confidence: almost certain (90-99%).** The rule is path-scoped to Python, every active hook is Python, all 34 reachable Python paths explicitly contain fail-open behavior, and representative outer handlers return success without diagnostics.

### Rule text, verbatim

`claude/rules/common/coding-style.md:43-57`:

> ## Error Handling  
>  
> ALWAYS handle errors comprehensively:  
> - Handle errors explicitly at every level  
> - Provide user-friendly error messages in UI-facing code  
> - Log detailed error context on the server side  
> - Never silently swallow errors  
>  
> ## Input Validation  
>  
> ALWAYS validate at system boundaries:  
> - Validate all user input before processing  
> - Use schema-based validation where available  
> - Fail fast with clear error messages  
> - Never trust external data (API responses, user input, file content)

The frontmatter explicitly includes `**/*.py` (`claude/rules/common/coding-style.md:1-20`). The Python extension does not create a hook exception; it says only “This file extends” the common file (`claude/rules/python/coding-style.md:1-8`).

### Hook text, verbatim

The registered dispatcher states at `claude/hooks/_dispatch/dispatch.py:41-45`:

> FAIL-OPEN at every level (try/except -> exit 0). Master opt-out: HOOK_DISPATCH=off in  
> env, or a _dispatch/.disabled file (disables the whole consolidated set; per-check  
> opt-outs still work individually). Pure stdlib. Never blocks (exit 0 only) — the  
> consolidated checks are all inject-only; none ever returned exit 2.

It implements that promise by swallowing every worker exception at `claude/hooks/_dispatch/dispatch.py:182-189` and every outer exception at `322-323`:

> except BaseException:  
> &nbsp;&nbsp;&nbsp;&nbsp;pass  # fail-open: a check must never crash the dispatcher

and:

> except BaseException:  
> &nbsp;&nbsp;&nbsp;&nbsp;pass  # fail-open: never crash a session

The direct blocking hook repeats the independent authority at `claude/hooks/no-force-push/hook.py:11-15`:

> FAIL-OPEN by design: malformed stdin, a predicate error, a MISSING OR BROKEN  
> tripwire.py, or the opt-out ... all -> exit 0  
> (allow). ... A crashing gate that blocked (or errored on) every command would be far worse than a silent one.

This is systemic, not two cherry-picked files. A full scan of the 34 unique registered Python paths found explicit `FAIL-OPEN`, “any error -> exit 0,” or silent-error language in **34/34** paths. Across all 164 Python files there are 574 `except Exception`/`except BaseException` sites and 1,020 obvious in-place mutation sites; the error-policy conflict alone is a finding because both sides state their policy explicitly.

### Concrete collision

Claude reads or edits `hooks/no-force-push/hook.py`. Both Python coding rules load because the path matches `**/*.py`. The rule requires a clear error and detailed logging. At runtime, malformed JSON, an import failure in `tripwire.py`, or an internal predicate exception returns 0 and produces no diagnostic (`claude/hooks/no-force-push/hook.py:35-59`). The same collision occurs inside the dispatcher if any imported check fails.

This is not merely “hooks have different needs.” The hook comments explicitly choose silence, while the scoped rule explicitly bans silence. That is duplicate authority capable of drifting: a maintainer following the coding rule could make an exception block every tool; a maintainer following the hook law can erase the only evidence of a broken guard.

### Runtime winner

The **hook implementation wins operationally**: Python catches the exception and exits 0. Claude Code sees neither an error nor a block. The coding rule can influence a future edit but cannot override executed exception handling. Official docs confirm that a successful/empty command-hook result lets the lifecycle continue ([hooks guide](https://code.claude.com/docs/en/hooks-guide)).

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Make `rules/common/hooks.md` the authority for hook error boundaries, and replace the absolute lines in `common/coding-style.md` with a one-line reference: normal application code must log/fail clearly; lifecycle hooks must fail open to Claude but append a bounded diagnostic to an existing local event-ledger/debug sink. Add one shared `fail_open_note(hook, exc)` helper and use it only in the outermost active-hook catches; stdout/stderr must remain protocol-clean.

This resolution is **very likely (80-90%)** to remove the conflict without wedging sessions because the dispatcher already has a shared import/execution boundary (`dispatch.py:182-189`) and the harness already has an append-only event-ledger bus. The residual risk is recursive logger failure; the helper must itself be best-effort and silent. Merely weakening the rule to “hooks may swallow everything” is smaller textually but preserves undetectable dead guards, so it is not the best minimal repair.

## 3. Finding 2 — force-push scope: protected branch versus every branch

**Conflict confidence: almost certain (90-99%).** Three rule/contract locations scope the prohibition to `main/master`; the hook regex has no branch test; direct execution blocked a feature-branch `--force-with-lease` command.

### Rule text, verbatim

`claude/rules/common/security.md:23-24`:

> AGENTS.md §9 is the always-on security floor (no secrets, no `--no-verify`, no  
> force-push to main, validate inputs). The detailed checklist below is code-turn-scoped.

The referenced contract is present in the supplied subject. `claude/AGENTS.md:64-69` says:

> **Exit 2 (block):** irreversible/dangerous only — destructive git ops, secrets in code,  
> force-push to main without explicit approval.  
> **Exit 0 + additionalContext (inject):** all other guidance ... Never block on ambiguity; inject a clarifying route instead.

and `claude/AGENTS.md:93-98` says:

> Never `git push --force` to main/master without explicit user approval.

### Hook text, verbatim

`claude/hooks/no-force-push/tripwire.py:15-18`:

> ACTION = "Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval. If approved, re-run with FORGE_NO_FORCE_PUSH_OFF=1."  
> _PATTERN = re.compile("git\\s+push\\b[^\\n]*(--force\\b|-f\\b)", re.IGNORECASE)

`hook.py` returns exit 2 for every positive match (`claude/hooks/no-force-push/hook.py:45-58`). The regex does not resolve the refspec, upstream, current branch, or protected branch. Because `\b` occurs before the hyphen, it also matches `--force-with-lease`.

### Concrete collision and direct result

For:

```text
git push --force-with-lease origin feature/a
```

the rule's protected-branch condition is false, but the hook blocks. Isolated execution returned:

```text
rc=2
Tripwire: refusing git push --force. Force-push can destroy remote history; AGENTS.md section 9 requires explicit user approval.
```

The direct wiring is at `claude/settings.json:152-160` with matcher `Bash`.

### Runtime winner

The **hook wins mechanically**. PreToolUse exit 2 blocks the pending Bash call before permission evaluation; prose cannot permit it ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks), [permissions documentation](https://code.claude.com/docs/en/permissions)).

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Keep native PreToolUse, but replace the text regex with a small Git-aware classifier: resolve explicit destination/refspec and, for implicit push, query the current branch/upstream. Deny only a force rewrite whose destination is `main` or `master` and lacks an explicit approval token; return `permissionDecision: ask` for an unresolved destination; allow or inject a warning for non-protected branches. Treat `--mirror` separately as dangerous. Do not require a global opt-out environment variable for a legitimate feature-branch lease rewrite.

This resolution is **very likely (80-90%)** to restore the stated owner policy because it implements the exact main/master condition found independently in the rule and AGENTS contract. Argument parsing across all Git push forms is the residual risk; fixture tests must cover explicit refspecs, implicit upstreams, `+src:dst`, `--mirror`, `--force-with-lease`, aliases, and shell chaining before replacement.

## 4. Finding 3 — background registry marks `done` with an OR-gate

**Conflict confidence: almost certain (90-99%).** The rule spells out an AND-gate; the active hook spells out and executes an OR-gate; direct pure-function calls produced `done` from each single branch.

### Rule text, verbatim

`claude/rules/common/single-signal-verification.md:20-33`:

> 1. **Absence/failure needs corroboration; success needs corroboration.** "Nothing there",  
>    "it crashed", "it's done" — each is a claim, not an observation, until a second independent  
>    probe agrees.  
> 2. **The two signals must be mechanically independent** — a different shell, a different data  
>    field, a different measurement ...  
> 4. **Terminal-state discipline (AGENTS.md §4):** `DONE` only on receipt **AND** postcondition;  
>    `FAILED`/`STALLED` only on an AND-gate of ≥2 signals ...

This file has no `paths` frontmatter, so it loads unconditionally under native rule semantics.

### Hook text, verbatim

`claude/hooks/bg-registry/done_marker.py:4-14`:

> appends a "done" status line for every still-"running" record that has demonstrably completed:  
>  
> * its declared artifact now exists and is non-trivial -> done (reason: artifact), or  
> * it is a synchronous sub-agent (sync=true) and the turn has ended -> done  
>   (reason: turn-ended; a Task() the orchestrator awaited is finished by Stop).

The implementation is the same OR at `claude/hooks/bg-registry/done_marker.py:41-61`: `if art and artifact_complete(...)` appends `status: done`; `elif rec.get("sync")` independently appends `status: done`.

The artifact postcondition is only “directory non-empty” or “file at least `MIN_ARTIFACT_BYTES`,” not schema/content validation (`claude/hooks/bg-registry/_common.py:181-197`). Task registration supplies no artifact and no receipt at all: `pid=None`, `expected_artifact=None`, `status=running`, `sync=not is_async` (`claude/hooks/bg-registry/register.py:85-99`).

### Concrete collisions and direct result

1. A stale/pre-existing 80-byte artifact exists before an async job runs. `compute_done` records `done` with reason `artifact`, without a process receipt.
2. A synchronous Task returns an empty/error-like result and creates no artifact. Stop records `done` with reason `turn-ended`, without a postcondition.

Direct pure-function probes returned:

```text
artifact-only = [{'id': 'a', 'status': 'done', 'reason': 'artifact', ...}]
turn-only     = [{'id': 's', 'status': 'done', 'reason': 'turn-ended', ...}]
```

The disputed hook is manifest-wired on Stop at `claude/hooks/_dispatch/manifest.json:76-83`; the dispatcher is Stop-wired at `claude/settings.json:495-503`. Existing tests intentionally lock in the same single-signal outcomes (`claude/hooks/bg-registry/test_bg_registry.py:153`, `175`).

### Runtime winner

The **hook wins for operational state**. It silently appends `status: done` (`done_marker.py:64-79`). The registry fold is last-write-wins (`_common.py:96-114`), and heartbeat/reconcile consume that status, so the prose rule cannot stop downstream readers from treating it as closed.

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Stop creating `done` in `Stop` from either single branch. Add a native PostToolUse `Task|Agent` receipt updater keyed by `tool_use_id`. Use explicit states: `running -> returned_unverified` on a Task receipt; `running/returned_unverified -> done` only when both `receipt_ok=true` and a declared postcondition validates. Jobs with no declared postcondition remain `returned_unverified`, not `done`. Include artifact creation timestamp/hash or schema validation so a stale non-empty file cannot satisfy the postcondition.

This is **very likely (80-90%)** to satisfy terminal-state discipline because it makes the code's state transition the same AND-gate as the rule and uses the existing native event/manifest bus. The exact provider shape of a successful Task PostToolUse payload on Windows is **UNVERIFIED; settle it with one controlled Task under `claude --debug`, capture the PostToolUse JSON, and fixture that shape before enabling the updater**. The recommendation does not depend on inventing a new runtime; if the payload lacks a receipt field, the safe state is `returned_unverified`.

## 5. Finding 4 — heartbeat claims `up` or `DOWN` from one socket

**Conflict confidence: almost certain (90-99%).** The unconditional rule requires independent probes and a known-present detector control; the wired hook returns both terminal labels from one `socket.create_connection` call; a live-listener control and closed-listener probe reproduced both labels.

### Rule text, verbatim

`claude/rules/common/single-signal-verification.md:22-30`:

> **Absence/failure needs corroboration; success needs corroboration.** ... until a second independent probe agrees.  
> **The two signals must be mechanically independent** — a different shell, a different data field, a different measurement ...  
> **Verify the detector before trusting the absence.** A "0 results / not found / 0 alive" reading is often a broken matcher ... check that the detector can find a known-present item before concluding nothing is present.

### Hook text, verbatim

The header advertises `mem:up|DOWN|?` (`claude/hooks/heartbeat/heartbeat.py:2-18`), but the current implementation has no `?` return. `claude/hooks/heartbeat/heartbeat.py:119-133` says:

> A live socket probe (~ms) instead of the mcp-liveness *last* probe ...  
> Listening => up; not => DOWN.

and executes:

> with socket.create_connection(("127.0.0.1", port), timeout=0.4):  
> &nbsp;&nbsp;&nbsp;&nbsp;return "up"  
> ...  
> return "DOWN"

This is also internal hook drift: line 10 still documents `mem:up|DOWN|?` as “last mcp-liveness probe result,” while lines 119-133 replaced it with one live TCP probe.

### Concrete collision and detector control

At SessionStart, the hook always emits the health banner (`heartbeat.py:201-208`). A process can listen on port 8765 without being the expected MCP service, yielding `up`; a service can be starting, overloaded, bound differently, or briefly slow beyond 0.4 seconds, yielding `DOWN`. Neither label has an independent handshake.

I validated the detector rather than trusting absence: with a temporary known-present listener, `mem_state` returned `up`; after closing the same listener, it returned `DOWN`. This proves the probe detects a listener, but it also proves the entire state label changes from one measurement only. Tests lock this in (`claude/hooks/heartbeat/test_heartbeat.py:124`, `151`).

Heartbeat is manifest-wired twice: SessionStart at `claude/hooks/_dispatch/manifest.json:42-50` and Stop at `86-94`.

### Runtime winner

There is **no deterministic instruction winner**. The dispatcher injects `[health] ... mem:DOWN` or `mem:up`; the unconditional rule is also in context. Official docs say Claude receives all `additionalContext` values and warn that contradictory rules may be chosen arbitrarily. Operationally, however, the hook's emitted state is the only freshly computed value, so downstream model behavior can be pulled toward it.

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Restore the documented tri-state. One successful TCP connect yields `reachable`, not `up`; one refusal/timeout yields `?`, not `DOWN`. Emit `up` only after TCP plus an application-level MCP/basic-memory health handshake. Emit `DOWN` only after the socket failure plus a mechanically independent process/service or MCP-handshake signal. Cache both signal timestamps and expose them in the banner, e.g. `mem:? tcp=refused mcp=stale`, so the model cannot mistake a single observation for a conclusion.

This is **very likely (80-90%)** to eliminate the duplicate authority because the hook already advertises a `?` state and the local `mcp-liveness` module provides an existing bus to reuse, although that module is not locally registered in this snapshot. Wiring that existing checker, rather than adding a daemon, passes the anti-overfit gate.

## 6. Finding 5 — memory spool turns “unconfirmed” into “NOT persisted”

**Conflict confidence: almost certain (90-99%).** The rule forbids a one-signal failure conclusion; the active hook's own docstring says it classifies one response and emits the stronger persistence claim; direct classifier execution reproduced the branch.

### Rule text, verbatim

The same unconditional text at `claude/rules/common/single-signal-verification.md:22-27` requires corroboration for failure and mechanically independent signals.

### Hook text, verbatim

`claude/hooks/memory-spool/flush_check.py:2-18`:

> Sees the tool_response. If the write SUCCEEDED, clear that spool entry  
> (it is safely persisted). If it FAILED/empty, KEEP the spool and inject a  
> LOUD alert that memory was NOT saved.

The runtime branch at `claude/hooks/memory-spool/flush_check.py:59-87` calls one `response_ok(tr)` and then says:

> Memory is NOT persisted. The payload is spooled at ...

It also mutates the spool record to `status = "failed"` (`flush_check.py:71-79`). The classifier itself says uncertainty is intentionally folded into not-ok: “ANY error envelope or empty result -> NOT ok” and “when uncertain we keep it” (`claude/hooks/memory-spool/_common.py:149-156`). Thus “unconfirmed” and “failed/not persisted” are explicitly conflated.

At the next session, the same authority becomes still stronger: `flush_check.py:123-128` says unflushed writes “were lost mid-write (likely a basic-memory outage).” A retained write-ahead spool proves only that success was not confirmed; it does not independently prove the remote write did not land.

### Concrete collision and direct result

An MCP write succeeds remotely but its response is lost or empty. The write-ahead spool remains. `response_ok("")` returned `False` in an isolated call, so the hook records `failed` and injects “Memory is NOT persisted,” while the central rule requires another independent read-back before that conclusion.

The hook is manifest-wired on PostToolUse at `claude/hooks/_dispatch/manifest.json:148-159` and on SessionStart at `20-39`.

### Runtime winner

The **hook wins for spool state** (`status=failed` persists on disk). For the textual conclusion there is **no deterministic winner**: both the unconditional rule and dispatched additional context reach Claude. The dispatcher itself always exits 0, so it cannot force reconciliation.

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Preserve the conservative spool, but change the state and words from `failed`/“NOT persisted”/“lost” to `unconfirmed`/“no success receipt was observed.” Before declaring loss, issue a read-back using note identifier plus expected content/version hash; only `write response not-ok AND read-back absent/mismatched` may become `failed`. If read-back finds the note, clear the spool as `confirmed_by_readback`.

The wording-only half is **almost certain (90-99%)** to remove the contradiction because it reports exactly what the spool proves. The read-back enhancement is **very likely (80-90%)** to distinguish lost acknowledgements from lost writes because it supplies the independent postcondition required by the rule; identifier/version behavior for every basic-memory edit mode is **UNVERIFIED; settle it with fixtures for write success + lost response, true failed write, idempotent overwrite, and edit-note version conflict against a disposable local basic-memory store**.

## 7. Finding 6 — re-autolaunch acts on a one-probe “backend down” conclusion

**Conflict confidence: almost certain (90-99%).** The central rule explicitly names disruptive action after a single signal as the expensive failure mode; the active hook derives `down` from empty TCP results and can both spawn a backend and deny the original call; direct decision execution reproduced the launch branch.

### Rule text, verbatim

`claude/rules/common/single-signal-verification.md:3-6`:

> A single tool's silence or single reading is NOT evidence. Before asserting that something  
> is absent, broken, stuck, or done — especially when the next action is disruptive (a  
> restart, a kill, a "re-fix", a rollback) — corroborate with a SECOND, mechanically-independent  
> probe.

Lines 28-30 additionally require proving that an absence detector can find a known-present item.

### Hook text, verbatim

`claude/hooks/re-autolaunch/autolaunch.py:14-31` says:

> For every RE MCP call it:  
> * probes ONLY the backend that tool needs ...  
> * if UP -> exits silently  
> * if DOWN and launchable -> cold-starts ONLY that backend ...  
> * if DOWN and NOT launchable ... reports the actionable manual-launch hint  
> ...  
> A deliberate deny on a confirmed-down backend ... is allowed.

The actual decision is one observation: `up_ports = probe_ports(...)` (`autolaunch.py:430-445`); an empty list flows into `decide`, which returns `manual`, `lowram`, `wait`, or `launch` with the reason “backend down” (`219-282`). On `launch`, it can spawn a detached process and deny the original tool while startup continues (`298-328`, `465-497`). On `manual`, it can directly emit `permissionDecision: deny` (`528-539`).

### Concrete collision and direct result

The RE backend is alive but its expected port is temporarily slow, moved, firewalled, or not yet bound. One probe yields no `up_ports`. A direct pure-decision call returned:

```text
Decision(action='launch', backend='ida', tool='ida', up_port=None,
         wait_port=12345, reason='backend down; cold-starting headless')
```

The hook is directly registered at `claude/settings.json:195-204` for IDA/Ghidra/Binary Ninja MCP calls.

The rule's “especially when disruptive” clause applies exactly: this branch starts a heavy process and can block the user's intended call. Repeating the same TCP connect during `brief_wait` is not mechanically independent; it is the same detector re-run (`autolaunch.py:339-352`).

### Runtime winner

The **hook wins mechanically** whenever it emits deny: native PreToolUse denial cancels the pending MCP call. It also wins operationally when it launches the process before emitting context. The rule can influence Claude's next response but cannot undo either action.

### Minimal resolution

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).** Split `UNREACHABLE` from `CONFIRMED_DOWN`.
