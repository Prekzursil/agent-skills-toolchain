# A055 — Coherence audit of `~/.claude/rules/php/testing.md`

## Executive verdict

The PHP testing rule is coherent in its testing advice, but it is not coherent with the mechanisms that are supposed to recognize and verify that advice. The most consequential confirmed defect is not PHPUnit-versus-Pest guidance itself; it is that the rule tells Claude to prefer Pest while two independent harness classifiers recognize `phpunit` and do not recognize `pest`. A successful Pest run can therefore fail to reset a test-frequency tripwire and can fail to create the typed `test` receipt used to substantiate a later “tests pass” claim.

I found **seven reportable collisions**:

1. one same-level coverage-source contradiction between the PHP rule and the common testing SSOT;
2. one confirmed shared-harness contradiction where Pest is not classified as a test receipt;
3. one confirmed hook contradiction where Pest is not recognized as a passing test;
4. one PHP hook promise that has no implementation in the active hook wire;
5. one reference whose live target (`laravel-tdd`) is **UNVERIFIED** because the two generated capability indexes disagree;
6. one behavioral enforcement failure: `tdd-workflow` was suggested 144 times and used zero times, independently matching the measured corpus's absence of a `tdd-workflow` invocation even when the owner explicitly requested it;
7. one conditional long-running-command collision, **UNVERIFIED** until representative PHP coverage timings are measured.

The first four are confirmed from the unpacked subject. Collision 5 is deliberately not promoted to “missing skill”: the Linux bundle does not include either live skills tree. Collision 6 is a measured routing/enforcement failure, not evidence that PHP projects themselves ignored PHPUnit/Pest. Collision 7 is conditional because command duration is project-dependent.

The highest-value repair is small: reconcile the coverage SSOT wording and add Pest to the existing receipt/test-command recognizers. These repairs are **very likely (80-90%)** to remove false “unverified tests” and false “too many calls since test” outcomes because the exact preferred command is absent from both classifiers, and the relevant code paths consume those classifier results. This confidence does not claim how often owners run Pest; the distilled corpus cannot answer that.

No proposal below introduces a second orchestration runtime, vector database/knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework. Every proposal edits the existing rule, hook, router, or shared-dispatch bus and therefore passes the anti-overfit gate.

## Collision register

### C1 — Coverage threshold location has two possible sources of truth

**Class:** CONTRADICTION

**Artifacts and exact conflicting lines**

1. `/local_disk0/codexwork/bundle/claude/rules/php/testing.md:24`:

   > Prefer **pcov** or **Xdebug** in CI, and keep coverage thresholds in CI rather than as tribal knowledge.

2. `/local_disk0/codexwork/bundle/claude/rules/common/testing.md:23` and `:38`:

   > Minimum Test Coverage: per `.coverage-thresholds.json` (100% on metaswarm; 80%+ where none is defined)

   > Verify coverage meets `.coverage-thresholds.json` (SSOT; 80%+ if none)

   The same SSOT is repeated at `/local_disk0/codexwork/bundle/claude/rules/common/code-review.md:56-58` and `:97-99`.

**Why this collides**

“Keep coverage thresholds in CI” can mean defining the number in a CI workflow or in `phpunit.xml`, while the common rule says the numeric policy lives in `.coverage-thresholds.json`. These are not guaranteed to be the same value. This is not mere prose duplication: it creates two plausible edit points.

The narrower rules-package precedence at `/local_disk0/codexwork/bundle/claude/rules/README.md:93-98` makes the PHP-specific wording win. AGENTS.md §10 does not independently resolve same-level global rule files. That means precedence selects the more ambiguous instruction; it does not remove the defect.

**Diagnosis:** badly written, not wrong in intent. Keeping enforcement in CI is compatible with keeping the value in a repository SSOT, but the present sentence conflates storage and enforcement.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** replace line 24 with: “Prefer pcov or Xdebug for CI coverage collection. Read the required threshold from `.coverage-thresholds.json` (80%+ only when it is absent), and make CI enforce that same value; do not duplicate a numeric threshold in workflow YAML or tribal knowledge.” Also remove repeated fallback prose from downstream checklists or make them pointers to `common/testing.md:23`.

This edit is **very likely (80-90%)** to eliminate threshold-source ambiguity because all four current references would name the same file and distinguish policy storage from CI enforcement. Evidence: the target's line 24 and three common-rule references quoted above.
