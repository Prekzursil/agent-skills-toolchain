# A141 — coherence audit: `~/.claude/settings.json` against itself / direct contradiction

## Executive result

I found **one direct, runtime-relevant contradiction** in the supplied user settings: four `Read(...)` rules say that credential-shaped files are denied, while the same permission object selects `bypassPermissions` as the default and the same file suppresses the bypass warning. Current Claude Code documentation says that `bypassPermissions` skips the permission layer entirely. In an ordinary interactive startup with no CLI mode override, the bypass mode wins and the four deny rules do not protect those files.

This conclusion is **almost certain (90-99%)**, based on (1) a complete, successful parse of the supplied JSON; (2) the exact local values at `settings.json:64-71` and `settings.json:693`; and (3) current official Claude Code permission-mode and settings documentation. A live invocation on the owner's Windows installation is **UNVERIFIED; the settling experiment is the four-case Windows smoke test specified under “Runtime verification boundary”** because this Linux job node contains no `claude` executable and does not contain the owner's Windows installation or session state.

No direct contradiction was found among the 99 `enabledPlugins` entries. In particular, a disabled plugin and an allowed MCP tool with a similar name are different runtime providers, not X versus NOT-X for the same situation.

## Finding 1 — credential-file denies are negated by the default bypass mode

### Both texts, verbatim

**Deny side** — `/local_disk0/codexwork/bundle/claude/settings.json:64-69`:

```json
    "deny": [
      "Read(./.env)",
      "Read(**/.env)",
      "Read(**/*.pem)",
      "Read(**/*.credentials*)"
    ],
```

The same permission object also broadly allows `Read` at `/local_disk0/codexwork/bundle/claude/settings.json:30`:

```json
      "Read",
```

**Bypass side** — `/local_disk0/codexwork/bundle/claude/settings.json:70-71`:

```json
    "ask": [],
    "defaultMode": "bypassPermissions",
```

The bypass confirmation is also suppressed at `/local_disk0/codexwork/bundle/claude/settings.json:693`:

```json
  "skipDangerousModePermissionPrompt": true,
```

### Concrete collision

Start a normal interactive Claude Code session without a `--permission-mode` override, with this file acting as the user settings, and ask the built-in `Read` tool to open any of these:

* `<current-directory>/.env` — matches `Read(./.env)`;
* a descendant `.env` — matches `Read(**/.env)`;
* a descendant PEM file — matches `Read(**/*.pem)`;
* a descendant filename matching `*.credentials*` — matches the fourth deny.

This is not a merely syntactic overlap. The official settings reference says `defaultMode` is the mode used when opening Claude Code and that `skipDangerousModePermissionPrompt` suppresses the confirmation for `defaultMode: "bypassPermissions"`. It also gives `Read(./.env)` as an exact permission-rule example: [Claude Code settings, permission settings](https://code.claude.com/docs/en/settings#permission-settings).

### Which text wins at runtime

**`bypassPermissions` wins in the stated default-startup situation.** The official permission-mode reference says that permission rules layer onto every mode *except* `bypassPermissions`, which “skips the permission layer entirely,” and further says bypass tool calls execute immediately: [Choose a permission mode](https://code.claude.com/docs/en/permission-modes#skip-all-checks-with-bypasspermissions-mode). Therefore the broad allow and the four denies are not ordered against one another at all in that session; the selected mode bypasses their evaluation.

There is an important conditional: if a CLI flag or in-session mode change selects a non-bypass mode, the deny side wins over the broad `Read` allow. The official rule order is deny, then ask, then allow, with first match winning regardless of specificity: [Claude Code settings, permission rule syntax](https://code.claude.com/docs/en/settings#permission-rule-syntax). Thus `Read` plus narrower `Read(...)` denies is a valid exception structure by itself and is **not** a separate contradiction. The contradiction is between retaining those denials as asserted policy and making the permission-bypassing mode the automatic startup state.

### Independent local evidence that no enabled credential hook restores the denied behavior by default

The file registers the local credential hook for `Read|Edit|MultiEdit|Grep|Bash|PowerShell` at `settings.json:239-248`, but that hook explicitly exits without a decision unless `HARNESS_CREDENTIAL_GUARD` is enabled. See `/local_disk0/codexwork/bundle/claude/hooks/deny-credential-reads/deny.py:73-89`; its decision branch is at `:92-100`. The settings environment contains all 16 values at `settings.json:4-20` and does not define `HARNESS_CREDENTIAL_GUARD`.

A mechanically different implementation path agrees: the shared harness module declares the credential-file block “OPT-IN and OFF by default” at `/local_disk0/codexwork/bundle/agents/harness/modules.py:50-61`, and its actual block is gated by `_credential_guard_enabled()` at `:791-798`. This is not evidence that no external process environment could set the variable; it shows that neither credential-hook path restores the block from the supplied settings alone.

### Minimal resolving edit

**Recommendation — remove the four deny strings, leaving `"deny": []`.**

**NATIVE-vs-BUILD: CONFIG (settings/JSON only).**

This is the minimal edit consistent with the locally recorded owner directive that credential-file reads are opt-in and off by default (`modules.py:50-56`; independently, `deny.py:73-80`) and with the file's deliberate bypass startup (`settings.json:71,693`). It removes four inert/misleading assertions without adding a hook, runtime, database, or framework. It rides the native settings bus and passes the anti-overfit gate; it introduces none of the previously rejected components.

Expected behavior after that edit is **almost certain (90-99%)**, because an empty deny array makes the declarative policy agree with bypass mode and both credential guards remain default-off by their source code. This claim concerns configuration coherence, not a promise that other settings scopes cannot add their own deny rules.

If the owner instead intends those four credential denials to be real protections, the alternative one-value edit is to change line 71 to a non-bypass mode (for example `"default"`). That alternative is **very likely (80-90%)** to make the four native denies effective, based on the official deny-first order and default-mode semantics, but it is not the preferred resolution because it conflicts with two local source comments recording the 2026-07-11 owner directive. The exact usability impact of changing the default mode is **UNVERIFIED; the settling experiment is a representative-session prompt-count A/B test on Windows**.

## Examined overlaps that are not findings

### Broad `Read` allow versus narrow `Read(...)` denies

Lines 30 and 65-68 overlap for four file classes, but in any mode where permission rules are evaluated, deny-first precedence resolves the overlap intentionally. In bypass mode, neither side is evaluated. There is no situation in which these two rules issue irreconcilable runtime decisions, so this pair is not an additional finding.

### Allowed MCP names versus disabled similarly named plugins

Examples include `"mcp__context7"` allowed at line 48 while `"context7@claude-plugins-official": false` appears at line 543, and `"mcp__playwright"` at line 60 while `"playwright@claude-plugins-official": false` appears at line 596. An MCP permission rule controls whether a tool may be called; an `enabledPlugins` boolean controls whether a particular marketplace plugin is enabled. They are not the same provider or the same predicate. A disabled plugin does not say that every independently configured MCP server with a similar name is disabled. No direct contradiction.

All 99 plugin identifiers are unique (duplicate-key detector result above), every plugin value is Boolean, and no identifier is simultaneously true and false. The eight enabled entries are at lines 572, 589, 600-601, 605-607, and 621; the other 91 are false. Marketplace declarations at lines 639-682 make sources known, but do not enable their plugins; the official settings reference explicitly says marketplace registration and plugin enablement are separate: [Plugin settings](https://code.claude.com/docs/en/settings#plugin-settings).

### Remote Control and bypass default

`remoteControlAtStartup: true` at line 700 enables a connectivity surface; it does not itself assert a permission mode. Official documentation says it connects Remote Control when each interactive session starts, while Remote Control keeps execution in the local process with its local tools and configuration: [Remote Control](https://code.claude.com/docs/en/remote-control#enable-remote-control-for-all-sessions). This pair therefore does not textually say X and NOT-X.

There is, however, a documentation ambiguity worth preserving as a gap: the permission-mode page says the remote client does not offer bypass mode, but the Remote Control page says it attaches to the local session. How an already-defaulted local bypass session is displayed or downgraded when auto-connect succeeds is **UNVERIFIED; the settling experiment is to start the Windows CLI with these settings, connect via Remote Control, run `/status` locally, inspect the remote mode selector, and attempt a harmless permission-sensitive write in a disposable directory**. Because runtime collision was not established, I do not promote this to a finding.

### Hooks and bypass mode

Bypass mode skips native permission evaluation; it does not imply “disable hooks.” The official hooks documentation says a blocking `PreToolUse` hook takes precedence over allow rules and can stop a call before permission rules are evaluated: [Configure permissions, extend permissions with hooks](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks). Thus the 38 registered hook commands do not directly contradict bypass mode merely by existing. Individual hook behavior is outside this settings-vs-settings unit, except for the credential-hook check needed to determine Finding 1's concrete winner.
