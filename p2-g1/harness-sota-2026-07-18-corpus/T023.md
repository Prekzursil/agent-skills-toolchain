# T023 — Competitive teardown: Augment Code

**Research date:** 2026-07-19 UTC  
**Unit remit:** agent loop, context management, memory, tools/MCP, permissions, customisation, multi-agent support, verification/self-check; identify portable advantages and non-examples.  
**Subject access:** read-only unpacked snapshot at `/local_disk0/codexwork/bundle`; the Windows source paths were not available on this Linux worker.  
**Source policy:** product facts below come from Augment's own current documentation and changelog. Those sources establish what Augment says the product does, not independent efficacy. Vendor benchmark claims are labelled as such. Local-harness comparisons cite the unpacked files or the pinned measured corpus/defects rather than earlier audit claims.

## Executive verdict

Augment's most differentiated component is not its agent loop. It is the **Context Engine**: a live semantic code index exposed both inside Augment and as an MCP service. The rest of local Auggie is now a broadly familiar harness: model loop, plan/task list, file and shell tools, MCP, rules, skills, commands, hooks, permissions, checkpoints, and parallel subagents. In several of those areas our harness is already equal or materially richer.

The best idea to import is therefore narrow and empirical: trial Augment's Context Engine MCP against our existing retrieval stack on held-out owner tasks. **It is likely (55-80%) to reduce exploratory searches on large or cross-repository tasks**, because Augment exposes task-ranked semantic retrieval and reports large controlled gains, but the evidence is vendor-run, the benchmark prompts and scoring are not fully reproduced here, and our owner workload is not Elasticsearch PR recreation. This is **UNVERIFIED; the settling experiment is the paired, blinded trial specified in Proposal P0**, including solution correctness, turns, retrieval calls, tokens, latency, and privacy/cost.

The second portable idea is **review-before-commit memory**: let automatic or agent-proposed durable memories enter a pending inbox, with approve/edit/discard actions, provenance, and supersession. The local harness has better semantic/objective memory separation than Augment documents, but Augment has a much better curation interaction. **A pending-memory gate is very likely (80-90%) to reduce silent memory contamination**, because it prevents an unreviewed candidate from becoming canonical while preserving the existing store. **It is also very likely (80-90%) to add some review friction**, because approve/edit/discard adds an explicit user action; therefore promotion should be selective rather than universal.

Do **not** replace our harness with Augment wholesale. Augment's documented IDE permission model is weaker than Auggie CLI's, its hook surface is narrower and internally inconsistent across docs/changelog, its automatic-memory selection policy is opaque, and its cloud Cosmos runtime is exactly the kind of second orchestration/runtime layer excluded by the owner's anti-overfit gate. **It is very unlikely (5-20%) that a Cosmos-style replacement would outperform a small set of MCP/hook-bus improvements per unit complexity on this owner**, because our current harness already has multi-agent dispatch, durable memory, lifecycle hooks, deterministic completion guards, and 108k+ observed Bash calls; no owner-specific head-to-head evidence supports migration.

### Bottom-line action

1. Run one bounded Context Engine MCP bake-off; adopt only on held-out owner-task evidence.
2. Add a small pending-memory review layer around `basic-memory`, not a second memory database.
3. Strengthen MCP discovery/health using the existing ToolSearch and hook buses; do not copy a new runtime.
4. Preserve our richer verification and hook mechanisms; borrow Augment's UI/operational ideas, not its thinner semantics.
5. Reject Cosmos replacement unless a future, separately authorised experiment demonstrates an order-of-magnitude benefit that cannot ride Claude/Codex's existing buses.

These signals establish **absence from this unpacked configuration snapshot**, not categorical absence from the Windows machine. Any recommendation that depends on actual full-machine absence is therefore marked **UNVERIFIED**, with a Windows experiment that settles it.

## 3. Agent loop teardown

### 3.1 Observable loop

The IDE Agent describes a conventional end-to-end loop: accept a natural-language goal, form a functional plan, implement it, expose actions/changes, and use terminal/MCP integrations where needed ([Using Agent](https://docs.augmentcode.com/using-augment/agent)). The user can:

* choose a model per workspace;
* attach files, folders, images, and other context;
* invoke a prompt enhancer that adds codebase references, structure, and conventions;
* inspect file diffs, full terminal commands/output, and integration results;
* interrupt and redirect mid-run;
* use normal Agent, which pauses before terminal/integration actions, Agent Auto, which proceeds automatically, or Quick Ask, which restricts the turn to read-only tools;
* restore automatically created workspace checkpoints.

The Tasklist is the explicit planning state. It can be agent-created or manual, supports nested subtasks and per-item states, can execute one task or all tasks sequentially, can move to another chat, and presents changes for each task ([Using Tasklist](https://docs.augmentcode.com/using-augment/tasklist)). The CLI has a separate persistent per-session task manager with nesting ([Using Task Manager](https://docs.augmentcode.com/cli/interactive/task-management)).

The message queue allows FIFO follow-ups while the agent works, with edit/delete/reorder/send-now/pause/resume controls and automatic pause on error ([Message Queue](https://docs.augmentcode.com/using-augment/message-queue)). Auggie additionally supports queued prompts in non-interactive mode, incremental session saving, transcript persistence options, and history summarisation; these evolved through releases ([Auggie 0.17.0](https://www.augmentcode.com/changelog/auggie-cli-0-17-0-release-notes), [Auggie 0.25.1](https://www.augmentcode.com/changelog/auggie-0-25-1-release-notes)).

The June 2026 changelog is unusually useful negative evidence: Auggie 0.30 fixed a loop that silently exited on an empty model response by retrying and surfacing an error, and “restored” context compression ([current changelog](https://www.augmentcode.com/changelog)). This demonstrates active reliability work but also shows these mechanisms have regressed in production.

### 3.2 What is not documented

The public sources do not specify the exact base model prompt, planning algorithm, termination policy, token budgeting algorithm, maximum retry count, checkpoint implementation, or how the model decides between grep, semantic retrieval, and MCP. Any stronger architectural account would be invented.

It is **roughly even (45-55%) whether Augment's local loop is intrinsically more reliable than ours once retrieval is held constant**. Evidence for Augment is polished task/queue/checkpoint UX and a vendor benchmark; evidence against is its changelog history of silent exits, stuck indexing, hanging MCP initialisation/subagents, queue stalls, and restored-after-regression compression. The settling experiment is a containerised, identical-model task suite with Context Engine alternately enabled/disabled and fault injection for empty responses, dead MCPs, tool timeouts, and interrupted queues.

### 3.3 Relative judgment

**Better than ours:** Tasklist portability, task-scoped diff review, editable queue controls, and automatic code checkpoints form a coherent operator experience. Our harness has plans, ledger state, worktrees, monitor controls, and mid-turn steering, but not that integrated presentation in the unpacked snapshot.

**Comparable:** interrupt/redirect, plan-execute flow, read-only mode, automatic execution mode, tool transparency, and terminal/file operations.

**Worse than ours:** the public local-Agent story does not expose our explicit objective-ledger/semantic-memory separation, terminal-state result contract, drift re-anchoring, or receipt-based done discipline. Task status “completed and ready for review” is workflow state, not proof of correctness.

## 4. Context management teardown

### 4.1 Context Engine mechanism

Augment's key mechanism is a live semantic index of a workspace (and, in hosted/cross-repo configurations, multiple repositories). The product claims it maps relationships and architectural patterns, ranks task-relevant slices, incorporates commit history/code patterns/external sources/tribal knowledge, and compresses context rather than replaying everything ([Context Engine product page](https://www.augmentcode.com/context-engine)). Users can also explicitly focus context with highlighted code, files/folders, or one of nearly 300 documentation sets ([Focusing Context](https://docs.augmentcode.com/using-augment/chat-context)). `auggie --add-workspace` indexes an additional workspace; `--wait-for-indexing` gates retrieval until indexing completes ([CLI reference](https://docs.augmentcode.com/cli/reference)).

The Context Engine is now independently exposed over MCP in two forms:

* **Local:** run Auggie as an MCP server over the current working tree, giving another agent a `codebase-retrieval` tool.
* **Remote:** connect to Augment's hosted endpoint for cross-repository context.

The official launch reports a 900-attempt Elasticsearch PR benchmark and claims improvements ranging from 30% to 80% across agent/model combinations, with fewer turns and tool calls ([Context Engine MCP launch](https://www.augmentcode.com/blog/context-engine-mcp-now-live)). Those numbers are **vendor claims, not independent ground truth**. The page describes the task count and evaluation dimensions, but the retrieved source does not provide enough artefacts here to reproduce its scoring.

Early Agent launch material advertised “up to 200K tokens” ([Meet Augment Agent](https://www.augmentcode.com/blog/meet-augment-agent)). That is not the principal advantage. Retrieval precision, context invalidation, and compression matter more than the nominal window; the 2026 changelog's “restored context compression” also proves the operational path can fail.

### 4.2 Comparison to ours

Our `basic-memory` is semantic durable knowledge, not a live semantic codebase graph/index (`bundle/codex/AGENTS.md:62-68`, `:79-85`). Our stack also has grep/glob, repo tools, rules, and numerous MCP sources, but the pinned corpus shows Glob at 13.3% error and broad tool/plugin surfaces have substantial reliability and Windows command-line costs. **It is likely (55-80%) that a single selective retrieval entry point would reduce exploration and up-front tool-schema load on large repositories**, because it replaces broad search/schema exposure with ranked slices; the owner-task bake-off below settles magnitude and transfer.

The snapshot contains no `codebase-retrieval` configuration under the validated probes. **UNVERIFIED whether the live Windows setup has an equivalent semantic code index; the settling experiment is to enumerate live Claude/Codex MCP servers with native config parsers, prove the parser finds known-present `basic-memory`, `context7`, and `repomix`, then query each server's tool schema for semantic code retrieval.**

### 4.3 Relative judgment

**Better than ours, if the live absence test confirms:** an integrated, task-ranked semantic code retrieval tool with explicit indexing state and local/remote modes. **Fewer fragile glob/search loops are likely (55-80%)**, based on the ranked-retrieval mechanism and our measured Glob error rate; Proposal P0 settles this on owner tasks.

**Worse or risky:** hosted indexing introduces vendor dependency, access-control, data-residency, freshness, cost, and outage questions. Augment says retrieval respects access permissions with proof of possession, but that is a product assertion on its marketing page, not a security design we verified. Local mode avoids hosted cross-repo exposure but still depends on a closed-source CLI/service.

**Do not copy:** a bespoke vector database or knowledge graph. Buying/trying the capability through MCP rides the existing bus; rebuilding an index runtime violates the anti-overfit gate and duplicates a fast-moving commodity.

## 5. Memory teardown

### 5.1 Augment's documented memory loop

Augment introduced memories that “automatically update as you work” and persist across conversations ([Meet Augment Agent](https://www.augmentcode.com/blog/meet-augment-agent)). The later Memory Review feature reveals the operational flow:

1. the agent proposes memories during a turn;
2. the chat summary shows an “X Pending Memory” affordance;
3. the user approves, edits, or discards each candidate;
4. the agent loop continues with curated memory context.

This is documented in both the [Memory Review changelog](https://www.augmentcode.com/changelog/memory-review) and the implementation narrative [How we built Memory Review](https://www.augmentcode.com/blog/how-we-built-memory-review). The latter admits that before review, automatic memories accumulated unnecessary/low-quality entries and users had to inspect a raw file. That admission is stronger evidence than generic “self-improving memory” marketing: uncontrolled automatic capture caused a real trust problem, and review was the remedy.

### 5.2 Unknowns

Public sources inspected here do not define the memory candidate schema, provenance fields, confidence, conflict resolution, retention/expiry, cross-workspace boundary, team visibility, retrieval ranking, deletion guarantees, encryption, or prompt-injection treatment. **UNVERIFIED whether pending memories record the evidence span that generated them; the settling experiment is to create a deliberately ambiguous and then contradictory convention in an isolated Augment workspace, inspect the pending/raw memory representations, approve one, edit one, reject one, restart, and measure exactly what is recalled.**

### 5.3 Comparison to ours

Our architecture is conceptually stronger in two ways: it separates objective event history from semantic memory and encodes supersession/temporal validity (`bundle/codex/AGENTS.md:20-26`, `:79-85`). Augment's public memory material does not show either. Our weakness is interaction and enforcement: `basic-memory` “does NOT auto-load” and depends on proactive query/capture instructions (`bundle/codex/AGENTS.md:81-84`). A user cannot see a compact pending-memory review affordance in the snapshot.

**Augment is better:** reviewability at the moment of capture.

**Ours is better:** cross-tool canonical storage, explicit objective-vs-semantic roles, temporal supersession, and no requirement to trust an opaque vendor memory store.

**Do not copy:** automatic write-through of every model-inferred preference. Augment's own history demonstrates why.

## 6. Tool and MCP teardown

### 6.1 Built-ins and integrations

Auggie exposes process management, file read/edit/save/delete, `codebase-retrieval`, grep, GitHub, Linear, Notion, Supabase, web search/fetch, and MCP tools ([Tool Permissions](https://docs.augmentcode.com/cli/permissions)). The IDE has OAuth/native integrations for GitHub, Linear, Jira, Confluence, Notion, Sentry, Stripe and others, selected automatically from request context ([Agent Integrations](https://docs.augmentcode.com/setup-augment/agent-integrations)). MCP configuration supports stdio and remote transports, environment/workspace variable expansion, OAuth, and CLI inspection ([Integrations and MCP](https://docs.augmentcode.com/cli/integrations)).

### 6.2 MCP Tool Search

By default Augment exposes every tool schema from every configured MCP server. Optional **MCP Tool Search** replaces that up-front list with two meta-tools:

* `find-tool`: a lightweight model selects the relevant underlying MCP tool from a natural-language need;
* `execute-tool`: invokes the selected tool.

Permission rules still apply to the underlying tool, not merely the meta-tool ([MCP setup — Tool Search](https://docs.augmentcode.com/setup-augment/mcp)). This is exactly the correct architectural shape for hundreds of tools: progressive discovery over the existing MCP bus, not a second orchestrator. It does add a model-mediated routing decision and a separately billed search activity.

### 6.3 Reliability operations

Recent releases added targeted MCP server restart, warnings for stale shared opt-ins, visibility for selected-but-dropped registry servers, more resilient OAuth refresh, and clearer failed-server connection status ([current changelog](https://www.augmentcode.com/changelog)). Those mechanisms directly address our highest measured tool defect: a dead Tavily MCP was called 135 times as “not connected.”

However, Augment's own changelog also records prior MCP initialisation hangs, non-conformant OAuth problems, subagents hanging during codebase retrieval, and schema compatibility fixes ([Auggie 0.16.0](https://www.augmentcode.com/changelog/auggie-cli-0-16-0-release-notes), [Auggie 0.21.0](https://www.augmentcode.com/changelog/auggie-cli-0-21-0-release-notes)). This is not a solved category; Augment has simply invested in better operator feedback and recovery.

### 6.4 Comparison

Our settings already permit `ToolSearch` (`bundle/claude/settings.json:40-47`) and include an `mcp-liveness` hook in the snapshot, so neither concept is truly novel. Yet the corpus proves the end-to-end policy failed to quarantine a known-dead server. Augment's useful delta is operational: discovery virtualization, explicit connection state, diagnostic reasons, and targeted restart.

**Better than ours:** current MCP failure visibility/restart ergonomics and a clearly documented two-meta-tool schema compression path.

**Comparable:** MCP transports, native/external integrations, tool permission matching, subagent inheritance.

**Worse/risky:** `find-tool` delegates routing to another model without a documented recall guarantee; it is separately billed, and it does not itself prove server health. Our harness must not confuse catalog discovery with liveness.

## 7. Permission model teardown

### 7.1 Auggie CLI

Auggie permissions are ordered, first-match rules in `~/.augment/settings.json`. Rules choose `allow`, `deny`, or interactive `ask-user`, can match a tool, can regex-filter shell input, and can apply at `tool-call` or `tool-response`. MCP tools are flattened to `{tool-name}_{server-name}` and truncated at 64 characters ([Tool Permissions](https://docs.augmentcode.com/cli/permissions)). Documented examples include read-only, development, and CI profiles.

This is concrete and automatable, but has sharp edges:

* unmatched tools fall back to implicit runtime behaviour rather than a documented deny-by-default;
* first-match ordering can shadow later rules;
* regex over a shell command string is not semantic command parsing;
* flattening/truncating MCP names maps distinct longer names onto the same 64-character prefix. **UNVERIFIED whether Auggie detects or disambiguates that collision; the settling experiment is to register two isolated dummy MCP tools with identical first 64 characters and inspect discovery, permission matching, and invocation.**
* most importantly, the documentation explicitly states CLI permission settings do not work in the extension.

### 7.2 IDE Agent

The IDE offers normal Agent (pauses before terminal/integration actions), Agent Auto (automatically edits/runs/accesses), and Quick Ask (read-only tools) ([Using Agent](https://docs.augmentcode.com/using-augment/agent)). This is understandable UX, but materially coarser than ordered CLI policy.

### 7.3 Comparison

Our current settings have explicit allow/deny lists but select `bypassPermissions` and very broad drive access (`bundle/claude/settings.json:26-75`). Our hook contract correctly reserves blocking for irreversible/dangerous operations (`bundle/codex/AGENTS.md:48-54`), yet the live defects show multiple guards confuse prose mentions with executable use (`bundle/inputs/INPUT-known-harness-defects.md:9-87`).

**Augment CLI is better:** one documented ordered policy language, explicit per-tool ask/allow/deny, shell regex examples, and post-response checks.

**Augment IDE is worse:** CLI policy does not carry over, leaving a coarse pause-all/auto/read-only choice.

**Do not copy:** raw regex command guards. Our measured payload-vs-verb failures show why semantic discrimination must occur on parsed tool input and target fields. Augment's regex documentation is a convenience, not a safe parser.

## 8. Customisation: rules, skills, commands, hooks, plugins

### 8.1 Rules and guidelines

Augment supports:

* user guidelines in `~/.augment/user-guidelines.md`;
* user rules in `~/.augment/rules/`, always applied;
* workspace rules in `.augment/rules/` with `always_apply`, manual IDE attachment, or agent-requested auto attachment based on a description;
* repository `.augment-guidelines`;
* hierarchical `AGENTS.md` and `CLAUDE.md` discovered from the target directory up to workspace root.

The docs disclose limits: 24,576 characters for user guidelines and 49,512 for workspace guidelines/rules, with a stated priority when over limit ([Rules & Guidelines](https://docs.augmentcode.com/setup-augment/guidelines)). Cross-tool `AGENTS.md`/`CLAUDE.md` compatibility is a strong choice and makes migration cheap.

### 8.2 Skills and commands

Auggie implements the agentskills.io `SKILL.md` convention and searches `.augment/skills`, `.claude/skills`, and `.agents/skills` at both user and workspace scope. Metadata remains discoverable; a `/skills` browser shows source, description, and estimated token cost; skill bodies can be lazy-loaded, including nested skill includes ([Agent Skills](https://docs.augmentcode.com/cli/skills), [current changelog](https://www.augmentcode.com/changelog)).

Custom Markdown slash commands support user/workspace scope, Claude and Cursor compatibility directories, YAML descriptions/argument hints/model override, `$ARGUMENTS`, prompted placeholders, and namespace subdirectories ([Custom Commands](https://docs.augmentcode.com/using-augment/custom-commands)). This is close to our commands/skills and is not a reason to migrate.

### 8.3 Hooks

Current hook documentation lists synchronous `PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, and `SessionEnd` command hooks. Hooks receive structured JSON; PreToolUse can deny, PostToolUse can inject context, Stop can prevent completion, and selected metadata is privacy-opt-in. Matchers understand an MCP namespace. Hooks are sequential and command-only ([Hooks](https://docs.augmentcode.com/cli/hooks)).

The same page says updated tool input is “not yet supported,” but the May 13 Auggie 0.27 changelog says “support for updating input from PreToolUse hooks” was added and PromptSubmit hooks were added ([Auggie 0.27](https://www.augmentcode.com/changelog/auggie-cli-0-27-0-release-notes)). This is a direct primary-source contradiction. **UNVERIFIED which statement matches Auggie 0.31; the settling experiment is a local 0.31 dummy PreToolUse hook returning a modified harmless `echo ORIGINAL` input plus a PromptSubmit hook, followed by transcript and process-output inspection.** Until then, do not port against `updatedInput`.

June 0.30 added PreToolUse/PostToolUse execution inside subagent sessions ([current changelog](https://www.augmentcode.com/changelog)). That is valuable inheritance but still narrower than our snapshot, which includes broader Claude/Codex lifecycle events and provider dispatch.

### 8.4 Plugins

Auggie can package commands, skills, agents, hooks, and MCP configuration as plugins/marketplaces ([Plugins and Marketplaces](https://docs.augmentcode.com/cli/plugins)). This is functionally familiar and is a cautionary comparison: our measured ~1,293 orphaned plugin directories already cause Windows command-line overflow. **It is very likely (80-90%) that copying more marketplace machinery without lifecycle garbage collection would worsen path/argument inflation**, because each retained plugin directory adds discovery/argument material to the already over-limit mechanism.

### 8.5 Relative judgment

**Better than ours:** clean cross-ecosystem discovery order, visible token estimates for skills, and description-driven auto rules are polished. These are configuration/UX improvements, not architectural gaps.

**Ours is better:** more lifecycle coverage, explicit shared dispatcher, provider-neutral cross-tool contract, and sophisticated verification hooks. Our problem is reliability and overgrowth, not lack of extension points.

## 9. Multi-agent support

Auggie CLI subagents have independent context windows, custom prompts, selectable models, tool allow/deny lists, user/workspace Markdown definitions, parallel execution, and progress summaries in the main thread. Auggie can suggest a relevant subagent; the user can invoke one explicitly ([Subagents](https://docs.augmentcode.com/cli/subagents)). Releases added MCP-tool inheritance, completion reporting, general-purpose and documentation-guide agents, subagent histories in session JSON, parent hook inheritance, and rolled-up cost display ([Auggie 0.17.0](https://www.augmentcode.com/changelog/auggie-cli-0-17-0-release-notes), [current changelog](https://www.augmentcode.com/changelog), [Auggie 0.25.0](https://www.augmentcode.com/changelog/cli-0-25-0-release-notes)).

Our baseline already has 22 used agent types in the pinned corpus, explicit Task/Monitor/TaskStop permissions (`bundle/claude/settings.json:39-46`), structured handoffs (`bundle/codex/AGENTS.md:43-46`), and specialised agent files. Augment is therefore not ahead in core multi-agent capability.

**Augment is better:** native progress summaries, cost roll-up, consistent per-agent model/tool frontmatter, and automatic suggestion UX.

**Ours is better:** cross-vendor agent use, explicit fresh-context critic independence, event-ledger integration, and owner-specific specialists. The large installed-but-unused capability surface remains a weakness: only 78 of roughly 355 installed skills were invoked, so adding more agents is not leverage by itself.

**Anti-overfit conclusion:** do not build a second agent scheduler. Normalise our existing agent metadata and surface progress/cost through current Task/Monitor hooks. **It is very likely (80-90%) that this captures Augment's useful local delta without runtime duplication**, because Task/TaskStop are configured, agent files declare models, and the contract already defines structured handoffs (`bundle/claude/settings.json:39-46`; `bundle/codex/AGENTS.md:43-46`). Cost-field parity remains UNVERIFIED; the settling experiment is to capture one Claude and one Codex subagent-start/stop payload and corroborate it with native session statistics before designing a display.

## 10. Verification and self-check

### 10.1 What local Agent actually provides

Local Agent can run tests/commands, display command output, checkpoint code, and show diffs. Tasklist marks items done and ready for review. Those are useful mechanisms, but the public Agent docs do not specify a mandatory plan-execute-verify state machine, evidence receipts, independent critique, mutation tests, acceptance tests, or a completion gate.

Augment publishes a guide advocating a Plan-Execute-Verify harness with explicit acceptance criteria and phase gates ([Harness Engineering guide](https://www.augmentcode.com/guides/harness-engineering-ai-coding-agents)). That is design guidance, not evidence the stock Agent enforces it.

### 10.2 Code review and cloud verification

Augment's code-review narrative describes semantic retrieval of related code plus repository/directory review guidelines ([High-quality code review agent](https://www.augmentcode.com/blog/how-we-built-high-quality-ai-code-review-agent)). This is a mechanism intended to improve contextual review, but the public blog does not establish independent calibration against escaped owner defects.

Augment also built an internal **Verifier** on Cosmos: a PR trigger provisions a VM/environment, deploys the change, exercises behaviour, and posts logs/API responses/screenshots to the PR ([Verification blog](https://www.augmentcode.com/blog/the-bottleneck-moved-to-verification-so-we-automated-that-too)). The article explicitly says “verification inside the coding loop” is a next step and that the system is not finished. Therefore it is inaccurate to credit stock Augment Agent with autonomous in-loop E2E proof.

### 10.3 Comparison

Our harness has a stronger documented epistemic boundary: terminal receipts, claim/evidence matching, an external bar for functional claims, deterministic gates before advisory judge opinion, and no judge-granted “done” (`bundle/claude/hooks/claim-guard/README.md:41-57`; `bundle/claude/agents/agent-as-judge.md:15-41`). Its weakness is implementation quality: known live guards misinterpret prose and tool fields, and hook telemetry is not currently measurable (`bundle/inputs/INPUT-known-harness-defects.md:9-87`, `:133-147`).

**Ours is conceptually better and currently operationally brittle.** Augment's local UX is better, while its strongest verifier requires a hosted BUILD-LARGE runtime and is not in the coding loop.

**Do not copy:** “agent verifies agent” as proof. Preserve executable, independently reproducible receipts; use an agent only to choose/exercise journeys and collect artefacts.

## 12. What not to copy

1. **Nominal context-window maximalism.** A 200K label does not establish retrieval precision or correctness; Augment's own compression regression shows the serving path matters.
2. **Unreviewed automatic memory.** Augment later built review specifically because low-quality memories accumulated.
3. **Permission policy split by surface.** CLI policies that do not govern IDE Agent create a false sense of uniform control.
4. **Regex-as-shell-security.** Our live detectors already demonstrate payload/semantic-role confusion. Parse structured tool inputs and command ASTs where possible.
5. **Implicit unmatched permission behaviour.** Explicit terminal defaults are safer and auditable.
6. **Marketplace expansion without garbage collection.** Our orphaned plugin directories already cause Windows CreateProcess overflow. Lifecycle correctness precedes more distribution surface.
7. **Agent status as evidence.** Task “done,” checkpoint creation, or a confident review comment does not prove the product works.
8. **Vendor benchmark adoption without owner-task replication.** Augment's gains are candidate hypotheses, not transfer guarantees.
9. **Cloud-runtime envy.** Cosmos solves a different organisational problem and violates this harness's minimal-architecture prior unless a workload proves necessity.
10. **Automatic updates in critical harness paths.** Auggie defaults to automatic interactive updates ([Configuration Wizard](https://docs.augmentcode.com/cli/config)); our owner needs pinned, tested changes because the Augment changelog itself records regressions.

## 15. Final assessment

Augment validates the owner's minimal-bus direction more than it argues against it. Its best local innovations—semantic retrieval over MCP, two-stage MCP tool discovery, reviewable memory, task envelopes, structured hooks, and subagents—ride exactly the same kinds of buses we already possess. The frontier move is not to reproduce Augment's portfolio. It is to isolate the two genuinely differentiated loops, retrieval and memory curation, and test/port them without weakening our evidence discipline.

The ranking is:

1. **Context Engine trial:** highest upside, evidence still owner-UNVERIFIED.
2. **MCP health quarantine/discovery:** highest confidence because it directly targets the top measured defect.
3. **Pending-memory review:** a small-scope candidate that is very likely (80-90%) to reduce silent memory contamination for the reasons in P1.
4. **Task evidence envelope and subagent roll-up:** useful operator polish on existing primitives.
5. **Everything Cosmos-like:** reject unless a future workload proves current buses structurally incapable.

This is an evolution recommendation, not incrementalism by reflex. Full replacement was considered and rejected because Augment's unique value can be consumed through MCP, while wholesale migration would discard stronger owner-specific verification/memory semantics and introduce a second closed runtime without comparative evidence.
