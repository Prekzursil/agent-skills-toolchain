### A058-C01 — Mutable DTO example versus mandatory/preferred immutability

**Class: CONTRADICTION**

**Artifact A:** `claude/rules/python/patterns.md:20-30`

```text
20 ## Dataclasses as DTOs

26 class CreateUserRequest:
27     name: str
28     email: str

```

**Artifact B1:** `claude/rules/python/coding-style.md:15-23`

```text
15 ## Immutability
17 Prefer immutable data structures:
20 from dataclasses import dataclass
22 @dataclass(frozen=True)
```

**Artifact B2:** `claude/rules/common/coding-style.md:23-33,59-68`

```text
23 ## Immutability (CRITICAL)
25 ALWAYS create new objects, NEVER mutate existing ones:
...
68 - [ ] No mutation (immutable patterns used)
```

The target's canonical DTO example is mutable, while the Python-specific style file demonstrates precisely the same construct as `@dataclass(frozen=True)`. The common rule is even stronger. `rules/README.md:93-104` would let an explicit Python exception override common immutability, but the Python patterns file does not state an exception or rationale; moreover it conflicts with another Python-specific rule at the same level. AGENTS §10 does not decide between these two Python files.

This is almost certain (90-99%) to produce inconsistent generated DTOs because the evidence is two directly copyable examples differing by a single `frozen=True` argument, coupled with a CRITICAL global immutability checklist. “Almost certain” describes the risk of inconsistent copying, not a claim that every generated DTO is mutable.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** change the target example to `@dataclass(frozen=True, slots=True)` or at minimum `@dataclass(frozen=True)`. Add one sentence allowing mutable dataclasses only when lifecycle/state mutation is an explicit requirement. This is a tiny rule-bus edit and adds no runtime. It is very likely (80-90%) to eliminate this instruction-level split because both Python examples would then demonstrate the same default; evidence is the exact one-token-option mismatch above. The residual uncertainty is whether the omitted skill teaches a different DTO policy.

It is very likely (80-90%) that the explicit “abbreviated” label will remove the collision without over-prescribing CRUD because it states the relationship instead of expanding architecture; evidence is that the collision currently depends entirely on whether the example is complete.

### A058-C06 — The harness itself documents a valid exception to the target's unconditional context-manager wording

**Class: CONTRADICTION**

**Artifact A:** `claude/rules/python/patterns.md:34`

```text
Use context managers (`with` statement) for resource management
```

**Artifact B:** `claude/hooks/re-autolaunch/autolaunch.py:298-325`

```text
298 def spawn_launch(cfg: dict, spec: dict) -> bool:
...
306     log_handle = None
307     try:
...
310         log_handle = open(log_path, "ab", buffering=0)  # noqa: SIM115 - spans child
319         subprocess.Popen(
...
322             stdout=log_handle,
323             stderr=log_handle,
```

The hook deliberately keeps the log handle alive across a spawned child's lifetime and suppresses the exact context-manager lint family. A lexical `with open(...)` around `Popen` would close the parent's handle at block exit; whether that is safe depends on platform handle inheritance and the intended ownership. The source comment explicitly says the lifetime spans the child. This is stronger evidence than merely finding a bare `open`: it records the intentional exception and its rationale.

This means the rule is **badly written**, not that context managers are wrong. The valid principle is deterministic ownership and cleanup; a lexical context manager is the default mechanism, not a universal form. It is almost certain (90-99%) that an unconditional mechanical ban on all non-`with` resource acquisition would false-flag this known case because the code carries `# noqa: SIM115 - spans child` at the acquisition site.

**Specific resolution — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** replace line 34 with: “Use context managers for resources whose lifetime is lexical. For resources intentionally transferred to or shared with a child/background owner, document ownership and close behavior explicitly.” Add the `Popen` log-handle case as the exception example. This is very likely (80-90%) to preserve the useful default while avoiding the demonstrated false positive; evidence is the explicit lifetime comment in the live hook source.

### Badly written, wrong, or unenforceable

- **Context-manager sentence: badly written.** It omits ownership/lifetime exceptions that the harness itself documents (`re-autolaunch/autolaunch.py:298-323`). The default is sound; the universal wording is not.
- **Generator sentence: unenforceable as written.** It does not define when lazy evaluation or memory efficiency is required, and that choice depends on consumption semantics and profiling. A mechanical style hook cannot infer the counterfactual without high false-positive risk. The conditional rewrite in A058-C05 is the remedy.
- **Mutable dataclass example: wrong relative to this harness's chosen policy.** The stronger same-language rule says to prefer frozen dataclasses (`python/coding-style.md:15-23`), while the common checklist labels immutability CRITICAL (`common/coding-style.md:23-33,59-68`). Fix the example.
- **Repository example: ambiguous/incomplete rather than proven wrong.** It needs an “abbreviated” marker or full alignment with the common operations list.
- **`id` parameter: wrong relative to the reviewer policy.** Rename it or explicitly exempt `id` from builtin-shadowing review.
