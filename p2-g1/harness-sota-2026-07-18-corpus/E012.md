## Executive verdict

The useful frontier is not “put the codebase in a knowledge graph.” It is two narrower capabilities:

1. **Exact, live, symbol-level lookup and refactoring through existing language servers.** Serena is the strongest ready-made implementation surveyed. It is a thin MCP toolkit over LSPs, not a replacement agent runtime, and its redundant shell/file/memory tools can be disabled. It is actively released (v1.6.0 on 2026-07-16), supports more than 40 languages, and is MIT-licensed ([Serena repository and release](https://github.com/oraios/serena); [documented retrieval/refactoring matrix](https://github.com/oraios/serena#features)).
2. **A small, answer-shaped structural map for orientation, impact, and cross-stack flow.** `James-Chahwan/repo-graph` is the cleanest architectural fit found: six budgeted MCP tools, a local tree-sitter/Rust engine, explicit blind-spot reporting, incremental refresh, no vector database, and MIT licensing. It is also very young—10 stars, zero forks, ten releases, and one published one-task comparison as of the research snapshot—so it is a benchmark candidate, not a production default ([repository](https://github.com/James-Chahwan/repo-graph); [tools and storage design](https://github.com/James-Chahwan/repo-graph#how-it-works)).

The leading proposal is therefore **not a replacement harness**. It is a pinned, retrieval-only Serena trial and a one-project Serena-versus-repo-graph bake-off on the current MCP/skill bus. This is **very likely (80-90%)** to expose useful signal without architectural overfit because both candidates attach through MCP, neither needs another agent loop, and their intended jobs are complementary; the uncertainty is actual benefit on this owner's repositories and Windows resource envelope, which the bake-off explicitly measures.

Do **not** adopt CodeGraphContext, codebase-memory-mcp, GitNexus, Joern, Glean, Kythe, Sourcegraph Enterprise, Augment Context Engine, or a full Aider runtime into the default harness. Some are high-quality tools in their own regimes, but here they either add a graph/vector persistence stack, a large service, a second orchestration runtime, a commercial remote index, an incompatible licence, or a resource footprint that conflicts with measured host failures. “Do not adopt here” is not a claim that those projects are poor.

Keep DeepWiki and Repomix for their existing, distinct jobs. DeepWiki provides remote, generated documentation and Q&A for public GitHub repositories; Repomix creates portable, token-counted repository snapshots. Neither is a live dependency graph, call graph, or exact symbol navigator. The current harness already has both enabled in Codex at `/local_disk0/codexwork/bundle/codex/config.toml:500-527`, and the corpus records 71 DeepWiki calls versus eight Repomix calls at `/local_disk0/codexwork/bundle/inputs/corpus.json:13400-13430`.

## Scope, definitions, and evidence discipline

### What counts as a repo map or code graph

I separated four mechanisms that are often marketed as one category:

* A **repository packer** serializes files and directory structure, optionally compressing bodies to signatures. Repomix is the exemplar.
* A **repo map** emits a bounded textual summary of important files/symbols, usually ranked against the active task. Aider's tree-sitter plus personalized PageRank map is the exemplar.
* A **semantic code navigator** delegates definitions, references, diagnostics, and refactors to compiler/LSP-quality indexes. Serena and SCIP-based systems are exemplars.
* A **code graph / code property graph** persists nodes and edges such as calls, imports, inheritance, control flow, data flow, routes, and services. The range runs from the lightweight repo-graph `.gmap` to Joern's full CPG.

A code graph is not automatically the forbidden “knowledge-graph memory.” A repository-scoped, reproducible index derived only from the current checkout can be treated like an LSP index: disposable acceleration over source-of-truth files. It crosses the anti-overfit line when it becomes durable agent memory, embeds conversations/decisions, adds vector retrieval as a new memory substrate, requires another daemon/service plane, or starts orchestrating work.

## Detailed assessment of the strongest candidates

### Serena: highest-quality practical fit

Serena exposes symbol lookup, file symbol overviews, references, declarations, implementations where the language server supports them, diagnostics, symbol renames, safe deletion, and symbol-body insertion/replacement. Its free default backend is existing language servers; a paid JetBrains plugin adds deeper dependency search, hierarchy, move/inline, inspections, and debugging. The project explicitly says its basic regex, file, and shell tools are normally disabled inside Claude Code or Codex because hosts already provide them ([feature matrix](https://github.com/oraios/serena#features)).

This matters because source-derived semantic navigation is different from generative memory. LSP answers are refreshed from the working tree and can degrade visibly by language/server; they do not require a graph database or embeddings. Serena is an MCP tool provider and leaves orchestration to the host ([architecture statement](https://github.com/oraios/serena#how-serena-works)). It therefore passes the bus and second-runtime gates.

Quality signals are unusually strong for this category: MIT licence, 26.6k stars, 1.8k forks, 14 releases, v1.6.0 three days before this survey, over 40 documented languages, and explicit per-backend capability limitations ([repository](https://github.com/oraios/serena)). Its published “evaluation” is an agent self-report over roughly 20 routine tasks, not an independent correctness benchmark; it is evidence of usability, not proof of task-success gain.

Risks:

* Serena includes its own memory. Enabling that would duplicate Basic Memory and fail the anti-overfit gate. Disable it.
* Its edit/refactor tools expand mutation authority. Initial evaluation must expose retrieval and diagnostics only; edits can be a later separately approved experiment.
* Language-server processes can be heavy. On this owner’s pressured Windows host, **likely (55-80%)** at least some multi-language projects will add noticeable commit charge because Serena launches or connects to per-language analyzers; evidence is Serena's dependency on language servers plus the owner's measured Python/Node/MCP process pressure, but no local Serena process measurement exists.
* The local snapshot sets the Serena official plugin false while retaining its permission namespace. The premise that a usable plugin payload is already installed is **UNVERIFIED; experiment: run `claude plugin list`, inspect the resolved plugin path, and query `/mcp` for Serena in a disposable read-only session**. This is why the recommendation below uses a pinned direct MCP command as the reproducible path instead of assuming plugin cache health.

### repo-graph: best lightweight structural-map design, immature evidence

`repo-graph` extracts modules, classes, functions, routes, services, components, imports, calls, handlers, cross-stack HTTP links, queue paths, and flows. It reduces an earlier 13-tool surface to six answer-shaped tools: `orient`, `find`, `impact`, `trace`, `read`, and `refresh`. Most accept a character budget. `orient` reports blind spots; `impact` emits reason-labelled closures; `trace` provides paths; `read` returns exact source slices. The Rust engine writes a local mmap-friendly `.gmap` plus JSON projections, not a server database ([README tools and implementation](https://github.com/James-Chahwan/repo-graph#how-it-works)).

That design directly addresses two harness defects: tool-schema overload and unnecessary context. Six simple schemas are less exposed to the corpus's 22.9% StructuredOutput failure than a 17- or 30-tool graph suite, although actual schema compatibility is **UNVERIFIED; experiment: initialize the pinned server through both Claude and Codex, enumerate schemas, and run 100 deterministic tool calls including malformed/ambiguous nodes**. Character budgets also avoid whole-repo payloads.

The project is admirably explicit that a small, clear repo may be cheaper to grep and that its value appears in large, cross-boundary code. It also emits blind-spot notes instead of pretending every edge is exact ([fit discussion](https://github.com/James-Chahwan/repo-graph#where-it-fits-best)). It is local, reports no telemetry, and is MIT-licensed.

Its weakness is maturity. The repository page showed only 10 stars, zero forks, 129 commits, ten releases, and v0.4.20. The public benchmark is one same-model task: 75,308 versus 29,838 tokens and the same correct fix. That is a controlled anecdote, not representative evaluation. It is **roughly even (45-55%)** whether repo-graph will beat Serena plus `rg` on this owner's typical work; evidence for upside is its targeted cross-stack map and budgeted tools, while evidence against is its very small adopter base, heuristic tree-sitter edges, and one-task self-benchmark.

The built-in `install` command writes multiple agents' configs/instructions and can add hooks. Do not use it here. Configure only the pinned MCP command manually through the canonical harness deploy path; do not add its generated CLAUDE/AGENTS block, pre-commit hook, or repository-committed graph.

### Aider repo map: best proven algorithmic reference, wrong runtime boundary

Aider builds a concise whole-repository map from tree-sitter tags. Files become graph nodes; dependencies become weighted edges; task/chat files personalize graph ranking; selected definitions are rendered within a dynamic token budget, normally about 1,000 tokens ([official repo-map documentation](https://aider.chat/docs/repomap.html)). Its `--show-repo-map` mode can emit the map without an interactive session ([options](https://aider.chat/docs/config/options.html)).

This pattern has better external task evidence than the young MCP graph tools. Aider reported correct edit-file localization on 70.3% of SWE-bench Lite tasks ([Aider SWE-bench analysis](https://aider.chat/2024/05/22/swe-bench-lite.html)). The ICLR 2025 RepoGraph paper independently found repository-graph augmentation improved multiple systems on SWE-bench and CrossCodeEval ([paper](https://openreview.net/pdf?id=dw9VUsSHGB)). CodeRAG-Bench provides counterweight: useful retrieved context helps, but current retrievers often miss it and generators do not always exploit it ([benchmark](https://code-rag-bench.github.io/)).

Do not install the full Aider agent as a harness component. That would create a second orchestration loop and fail the anti-overfit gate. Do not copy its roughly 700-line map subsystem into the harness either. Use its documented output as an offline benchmark baseline if a disposable environment is available. A tiny standalone Rust `repo-mapper` exists, but version 0.0.1 is too immature to prefer over the established implementation ([crate documentation](https://docs.rs/crate/repo-mapper/0.0.1/source/README.md)).

### Repomix and DeepWiki: useful complements, not competitors

Repomix is high quality for a different task. It respects ignore files, counts tokens, can include diffs/history, checks for secrets, and can use tree-sitter to compress code to key signatures ([current repository](https://github.com/yamadashy/repomix)). Its MCP packs local or remote code, after which the agent greps/reads the generated artifact. It does not maintain live symbol identity, callers, references, or blast radius. Keep it for bounded handoff, archival analysis, and remote repositories; do not use it as the default orientation step on every local coding task. Exact-version pinning is required because the local command is currently floating.

DeepWiki's official remote MCP is free and unauthenticated for public repositories and exposes `read_wiki_structure`, `read_wiki_contents`, and `ask_question`; private repositories require Devin credentials ([official DeepWiki MCP docs](https://docs.devin.ai/work-with-devin/deepwiki-mcp)). It provides generated explanations and citations to indexed source, not a live local working-tree graph. Keep it for public upstream architecture research. Do not send private or uncommitted code. The hosted service is proprietary; the MIT licence on the `seflless/deepwiki` wrapper covers the wrapper, not Cognition's service ([wrapper](https://www.deepwiki.sh/)).

## High-quality tools that fail the gate here

### codebase-memory-mcp — impressive engineering, prohibited architecture

This MIT project is active (v0.9.0 on 2026-07-08), ships a static Windows binary, exposes structural search, call graphs, impact, architecture, route linking, and watchers, and has a 2026 preprint. The paper reports 83% answer quality versus 92% for file exploration, with 10x fewer tokens and 2.1x fewer tool calls across 31 repositories ([paper](https://arxiv.org/abs/2603.27277)). That is a valuable result: efficiency improved while quality decreased nine points.

It fails this harness's gate because it explicitly persists a knowledge graph in SQLite, includes bundled Nomic vector embeddings and semantic search, auto-configures multiple agents' instructions/skills/hooks, and can commit a compressed database artifact ([repository persistence and search](https://github.com/DeusData/codebase-memory-mcp)). The vector/KG layer duplicates a rejected memory architecture even if the content is code-derived. Its claimed “99% fewer tokens” is a five-query project benchmark, not evidence of end-to-end patch success.

### CodeGraphContext — active and permissive, too much database surface

CodeGraphContext supports tree-sitter plus optional SCIP and offers call-chain querying through MCP/CLI. It is MIT-licensed and active. However, its supported backends include FalkorDB Lite, Kuzu/LadybugDB, Neo4j, remote FalkorDB, and Nornic; it also includes FastAPI/Uvicorn dependencies and an HTTP gateway ([repository prerequisites and backends](https://github.com/CodeGraphContext/CodeGraphContext)). This is precisely the graph-database/service expansion the anti-overfit rule rejects. Its own repository contains audit and inconsistency reports, which is healthy transparency but also a cue to demand local accuracy tests before relying on impact results.

### GitNexus — sophisticated, restrictive, and sprawling

GitNexus provides local tree-sitter indexing, persistent LadybugDB storage, embeddings, BM25+semantic+RRF search, clustering, execution flows, 17 MCP tools, code wiki, skills, and pre/post hooks. It even offers read-only MCP mode and signed container images ([repository](https://github.com/nxpatterns/gitnexus)). Those are strong engineering signals.

It fails on four independent grounds: (1) vector-enabled persistent graph storage; (2) an extra hook/instruction plane overlapping the owner’s dispatcher; (3) 17 tools, above the compact surface preferred after observed StructuredOutput failures; and (4) PolyForm Noncommercial 1.0.0, which is not a permissive open-source licence and requires separate commercial licensing for commercial use ([npm licence field](https://www.npmjs.com/package/gitnexus); [PolyForm description](https://polyformproject.org/licenses)). Do not adopt it merely because it can auto-configure every client.

### Joern / code property graphs — excellent security specialization, wrong default

Joern is a mature Apache-2.0 platform that builds AST, control-flow, and data-flow rich code property graphs in a custom database and exposes a Scala query DSL. It requires JDK 21 and releases daily; v4.0.583 appeared 2026-07-17 ([repository](https://github.com/joernio/joern)). The 2026 codebadger paper adds an MCP bridge over Joern ([paper](https://arxiv.org/abs/2603.24837)).

That depth is appropriate for vulnerability research, not everyday file localization. A JDK, graph database, language frontends, and MCP wrapper are a BUILD-LARGE analysis runtime. The harness already has specialist static-analysis surfaces and measured Semgrep memory pressure. Keep Joern as an explicitly invoked security tool if another unit demonstrates a need; do not preload it.

### Glean and Kythe — credible enterprise systems, BUILD-LARGE

Meta Glean stores and derives source facts at scale and queries them with Angle; its open repository supports several native languages plus SCIP/LSIF ingestion and uses a BSD licence ([Glean repository](https://github.com/facebookincubator/Glean)). Kythe provides schema, C++/Go/Java indexers, build extractors, a verifier, and a sample xref service; v0.0.76 released 2026-07-16 under Apache-2.0 ([Kythe repository](https://github.com/kythe/kythe)).

Both are high-quality foundations for organizations operating code-intelligence infrastructure. Neither is a small agent plug-in. Indexer orchestration, build extraction, fact storage, and query services make each BUILD-LARGE and outside this harness's bus/minimality envelope.

### Sourcegraph MCP — good cross-repo product, no demonstrated local need

The current Sourcegraph MCP provides keyword/semantic/regex search, exact files, SCIP-powered navigation, commit/diff history, ownership, and Deep Search across indexed repositories; it is available on Enterprise plans ([official MCP docs](https://sourcegraph.com/docs/api/mcp); [capability page](https://sourcegraph.com/mcp)). Sourcegraph moved its current monorepo private; the public snapshot says it is the last pre-migration snapshot and contains primarily non-OSS-licensed files ([public snapshot](https://github.com/sourcegraph/sourcegraph-public-snapshot)). SCIP itself remains Apache-2.0.

The local Sourcegraph plugin is disabled, and the corpus has four authentication calls but no substantive query. The combination of a paid indexed service, private-code trust boundary, and absent demonstrated usage makes adoption unjustified. Sourcegraph becomes **likely (55-80%)** the better option only if the owner's work shifts to many repositories/branches that cannot be indexed locally and an enterprise instance already exists; evidence is Sourcegraph's cross-repo/history/ownership surface, while the unresolved premises are organization scale, licence, data policy, and actual instance availability. **UNVERIFIED; experiment: inventory repository count/size and branch/history queries for 30 days, then run the same held-out retrieval set against an existing enterprise trial without changing the default harness.**

### Augment and Greptile — commercial context services, not local repo-map answers

Augment's Context Engine MCP indexes code, commit history, patterns, external docs, tickets, and tribal knowledge ([official docs](https://docs.augmentcode.com/context-services/mcp/overview)). That is a remote indexed knowledge service and duplicates memory/context authority. Greptile's current MCP exposes code-review comments, reports, and team custom context rather than repository symbol navigation ([official docs](https://www.greptile.com/docs/mcp/overview)). Both may be valuable products, but neither is the minimal local source index sought here.

No other candidate is called abandoned. A stale release alone is not proof of abandonment; for example, Aider's latest GitHub release field is 2025-08-09, but its repository remains large and is not archived.

## Proposals that pass the anti-overfit gate

### R1 — UNVERIFIED: retrieval-only Serena bake-off — **CONFIG (settings/JSON only)**

Add one exact-version, hash-reviewed Serena MCP definition in a disposable project scope. ## Adoption sequence and stop conditions

1. Fix/pin the existing MCP supply-chain and resource-admission defects before adding an always-on server. This ordering is **almost certain (90-99%)** to lower operational risk because the defects are measured on the actual host, while graph value is not yet locally measured.
2. Run R3 with built-ins only to establish baseline variance.
3. Run Serena retrieval-only on one Python or TypeScript project and one second-language project. Stop if cold start exceeds the project's test startup, steady commit exceeds an agreed host reservation, schema errors exceed built-in search errors, or required-file recall does not improve.
4. Run repo-graph on one polyglot/cross-stack project. Stop if edge precision is below 90% on labeled high-confidence edges, stale-answer rate is nonzero after the supported refresh window, or total task success does not beat built-ins at equal token budget. The 90% threshold is a design choice, **UNVERIFIED; experiment: calibrate the harm of false impact edges on ten owner corrections before promotion.**
5. Promote at most one structural graph default, and only for the task class it wins. Serena may coexist because it answers compiler/LSP questions rather than architectural heuristics.
6. Keep every new server disabled outside selected projects until the resource guard measures package identity and per-root commit correctly.

Full replacement of the harness is not justified by this ecosystem. The current bus already offers exactly the attachment points the strongest tools target. Replacement becomes **very unlikely (5-20%)** to outperform constrained evolution for this unit's problem because it would discard existing hooks, MCP, receipts, and memory while the missing feature is a narrow retrieval primitive; evidence is the direct MCP compatibility of Serena/repo-graph and the anti-overfit constraint. This conclusion is scoped only to repository context, not the entire harness program.

## Alternatives considered and dead ends

* **SCIP as the universal internal format:** technically attractive and Apache-2.0. It supports Java/Scala/Kotlin, TypeScript/JavaScript, Rust, C/C++, Ruby, Python, .NET, Dart, and PHP indexers ([SCIP repository](https://github.com/scip-code/scip)). But an agent still needs indexer orchestration, storage, freshness, query shaping, and MCP presentation. That is a platform project, not a <200-line integration.
* **Academic RepoGraph/CODEXGRAPH implementations:** strong evidence that graph augmentation can improve localization, especially in Python SWE-bench settings ([RepoGraph paper](https://arxiv.org/abs/2410.14684); [CODEXGRAPH paper](https://aclanthology.org/2025.naacl-long.7.pdf)). They are research systems, not the best maintained cross-platform MCP products. Their results motivate R3 rather than direct deployment.
* **GitHub-native navigation:** GitHub uses tree-sitter for symbols/definitions/references on supported languages ([GitHub docs](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github)). It is useful for hosted committed code but not a local dirty working tree and has no narrow local MCP advantage over Serena.
* **Raw tree-sitter or ast-grep:** excellent parsing/search substrates, but they do not resolve cross-file types/references by themselves. Building a new multi-language graph on them repeats work already packaged by the surveyed tools.
* **LSP plugins per language:** the local snapshot disables multiple official LSP plugins. Turning on only the needed native language plugin may be even lighter than Serena, but this unit could not verify their exact current tool schemas or whether they provide agent-callable references/refactors rather than background diagnostics. **UNVERIFIED; experiment: enable one project-scoped official LSP plugin in a disposable session and compare its discovered tools and process commit to Serena.** This is a valid additional baseline, not a conclusion.
* **REST metadata census:** GitHub API calls for 13 candidates returned HTTP 403 from the job node. No metadata was inferred from that failure. Archive and release conclusions instead use rendered repository fields.

## Final recommendation

Adopt no new default today. Authorize a read-only, exact-version bake-off:

* Serena retrieval/diagnostics only as the primary candidate;
* repo-graph's five read tools as the structural candidate on one polyglot repository;
* built-in `rg`/read as the mandatory baseline;
