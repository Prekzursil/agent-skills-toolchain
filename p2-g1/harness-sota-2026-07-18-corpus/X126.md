# X126 — Cross-domain borrow: forensic-science quality controls for agent tool design

## Executive determination

The borrow transfers, but only in a constrained form. The useful mechanism is **blind, casework-representative proficiency testing backed by boundary controls and chain-of-custody records**. It is not “make the agent act like a forensic scientist.” In forensic work, a blind proficiency item with known ground truth enters the ordinary case pipeline without being announced to the examiner; negative controls reveal contamination; chain-of-custody and elimination records help localize an introduced trace. Translated to tool design, a held-out command task should pass through the same model → tool schema → serializer → adapter → interpreter/OS path as ordinary work, while typed boundaries and stage hashes show exactly where quote-bearing text changed. The assigned measured symptom is 1,631 unmatched-quote EOF failures.

This transfer is **very likely (80-90%)** to expose failure modes that ordinary schema unit tests and declared demos miss. Evidence: blind forensic tests are designed to traverse the normal pipeline, and published comparisons cited in the primary review found higher error rates in blind than declared testing; the proposed harness cases exercise the exact production serialization and execution path rather than an isolated parser ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)). This is a prediction about an agent harness, not an observed harness result.

The prevention half is **likely (55-80%)** to materially reduce unmatched-quote parser failures if most such failures originate in shell-string construction. Evidence: an `executable + argv[]` process interface removes shell quote grammar from the default path, while exact-interpreter preflight catches unterminated syntax before execution. The residual uncertainty is causal: the supplied count identifies the error fingerprint, not what fraction genuinely requires shell syntax or arises inside nested `eval`, remote shells, generated scripts, or tool wrappers.

True double-blinding does **not** transfer to live command execution. The model necessarily sees the tool contract it must call, and the tool adapter necessarily knows which implementation it runs. Blinding belongs in the evaluation protocol: the agent is not told which tasks are scored proficiency cases, and the analyst reviewing outcomes is temporarily masked to interface variant. Calling the runtime itself “double blind” would be theatre.

## 1. The source-field mechanisms, in their own field

### 1.1 Blind proficiency testing

A proficiency sample has known ground truth. A declared test is labeled as a test and may cover only one analytical component. A **blind proficiency test** is submitted as ordinary casework; the examiner assumes it is real and learns its status only after completion. Done properly, it tests not merely the examiner's final comparison but evidence intake, routing, analysis, reporting, and other parts of the laboratory pipeline. It also limits the special-care/Hawthorne effect produced by knowing one is under test.

This is not merely conceptual. Koehler et al. report that blind tests must resemble actual cases, can exercise the entire pipeline, avoid behavior changes caused by announced testing, and are among the few mechanisms able to reveal misconduct. They also summarize drug-testing and blood-lead studies in which errors differed between blind and declared samples. Their account of Houston's program describes blind tests in biology, digital forensics, latent prints, toxicology, seized drugs, and other divisions, with a goal equivalent to 5% of casework. The same paper is candid about cost, realism, staff identifying implausible test artifacts, and the fact that blind proficiency results are not general error-rate studies ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)).

The crucial mechanics are therefore:

1. the test has externally known truth;
2. it is operationally indistinguishable enough from ordinary work that normal behavior is sampled;
3. it enters the ordinary end-to-end path;
4. ground truth is compared only after the work is frozen; and
5. failures feed process correction, not merely an individual score.

### 1.2 Blind verification is not ground-truth testing

The same source distinguishes blind verification from blind proficiency. In blind verification, a second examiner does not see the first examiner's conclusion. Agreement measures consistency, but because neither conclusion supplies ground truth, agreement does not establish accuracy ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)). This distinction matters directly for agent harnesses: two agents producing the same quoted command can share the same misconception. “A second model agreed” is not a substitute for an exact expected `argv`, filesystem delta, or exit classification.

### 1.3 Contamination control and elimination records

Forensic DNA contamination is foreign biological material introduced into, or detected alongside, evidentiary material. The controls are layered because prevention alone cannot prove cleanliness:

- manufacturing and handling are constrained to minimize introduction of human DNA; ISO 18385 is specifically a requirements standard for minimizing human-DNA contamination in products used to collect, store, and analyze forensic biological material ([ISO 18385:2016](https://www.iso.org/standard/62341.html));
- controls and process separation make an introduced trace observable and narrow where it entered; and
- elimination databases compare unexplained profiles with profiles of people who legitimately handled material, so a contaminant can be attributed rather than mistaken for probative evidence.

The attribution mechanism has operational evidence. Lapointe et al. describe a staff elimination database motivated by increasingly sensitive assays detecting DNA from crime-scene workers. In their reported deployment, 46 of 327 voluntarily submitted individual profiles (14%) matched 58 criminal cases. The authors also emphasize privacy safeguards and optional anonymity ([Lapointe et al., 2015](https://europepmc.org/article/MED/26117338)). The lesson is not “collect more identity data”; it is that a known-source reference can turn an unexplained artifact into an attributable process artifact.

### 1.4 Sequential unmasking: information order as a control

Linear Sequential Unmasking (LSU) requires the examiner to inspect and document questioned evidence before seeing the target/reference that could bias interpretation. LSU-Expanded generalizes the principle: start with raw data/evidence, then expose other information in an order chosen by relevance, objectivity, and biasing power, documenting revisions as each layer is disclosed. The authors explicitly argue that awareness and willpower alone are insufficient and that information flow must be structured ([Dror & Kukucka, 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8385162/)).

For tool errors, this is useful as an error-interface rule, not as a claim that shell parsing is a cognitive forensic judgment. The interface should first preserve the raw parser evidence and exact execution stage, then add diagnosis and suggested repair. Otherwise an early, overconfident explanation can anchor the agent into a retry loop.

## 2. Structural transfer test

### 2.1 What is genuinely isomorphic

| Forensic structure | Tool-design structure | Why the mapping holds |
|---|---|---|
| Known-truth proficiency item | Task with exact expected `argv`, exit class, stdout/stderr class, and sandbox delta | Both permit correctness to be checked independently of the operator's explanation. |
| Ordinary case pipeline | Production model → tool call → JSON transport → adapter → interpreter/OS → result formatter | Both contain boundary and routing failures that component-only tests omit. |
| Declared test changes examiner behavior | Prompted “quote this carefully” benchmark changes model behavior | Both can overestimate normal-work reliability when the operator recognizes the test. |
| Reagent/process control | Sentinel payload and stage-by-stage byte/argument digest | Both reveal that an artifact was introduced by the process, not the original item. |
| Elimination profile | Registry of known serializers/adapters plus their transformation fingerprints | Both can attribute a foreign artifact to a legitimate handling stage. |
| Blind verification | Independent agent/tool attempt with the first result hidden | Both measure consistency, not correctness, unless grounded by known truth. |
| Sequential unmasking | Raw failure record before diagnosis/remediation | Both prevent a contextual hypothesis from replacing primary evidence. |

The end-to-end testing analogy is **very likely (80-90%)** to hold. Evidence: both domains have a hidden internal pipeline, behavior can change under declared testing, and objective ground truth can be manufactured for selected cases; these are the causal preconditions identified in the blind-testing literature ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)).

The contamination analogy is only **likely (55-80%)** to be useful. Evidence: quote-bearing text can be altered at identifiable boundaries, and known sentinels can expose such alteration. Unlike DNA, however, a malformed command is usually not a mixture of independent physical traces. It is often a grammar or representation defect created by the author itself. “Contamination” should therefore name boundary corruption and attribution only, not every bad command.

### 2.2 Where the analogy breaks

1. **No persistent physical specimen.** DNA can be re-extracted or re-tested from retained material. A tool call may be transient unless the harness records the normalized request and stage representations. The design must create the equivalent record; the analogy does not supply it.

2. **The agent is generative, not an assay operator following a fixed method.** A proficiency case can alter subsequent model context, and the model may infer that unusual quoting cases are tests. Perfect concealment is **unlikely (20-45%)** because tool schemas and pathological fixtures are visible to the model; the evidence is the forensic paper's own examples of examiners detecting unrealistic crowbars and overly neat forms ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)).

3. **Agreement is cheap and correlated.** Two instances of the same model may share training and prompt-induced errors. Blind verification is not an accuracy oracle, exactly as examiner agreement without ground truth is not accuracy.

4. **Runtime double-blinding is impossible in the strict sense.** The agent must know field names and receives their errors; the adapter must know the implementation. An evaluator can mask variant labels from a human analyst, but an automated exact-match scorer has no expectancy bias to remove. Double-blinding adds value mainly where humans classify ambiguous outcomes.

5. **Negative controls do not prove production cleanliness.** A sentinel that survives unchanged demonstrates only that payload under that path. Dynamic shell expansion, remote quoting layers, locale, encoding, and nested interpreters can create other failures.

6. **An elimination database has a privacy inversion.** Human elimination profiles are sensitive identity records. Tool-stage fingerprints should contain implementation/version identifiers and cryptographic digests, not secrets or raw command contents. The forensic mechanism transfers; its data category does not.

The analogy passes only because the proposal uses these bounded correspondences. A program that injects fake user jobs into live owner work, calls majority vote “ground truth,” or labels every syntax error “contamination” would not pass.

## 3. Concrete harness translation

### Proposal A — UNVERIFIED: make process execution quote-free by default

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Experiment that settles the UNVERIFIED premise: replay a stratified sample of the unmatched-quote failures through both the current shell-string interface and a structured process interface, holding model, prompt, executable, and task constant; manually classify which cases truly require shell grammar.

Expose two deliberately different tools/contracts:

```json
{
  "tool": "exec_process",
  "executable": "git",
  "argv": ["show", "origin/main:path with spaces/file.txt"],
  "cwd": "...",
  "env_delta": {},
  "stdin": null
}
```

```json
{
  "tool": "exec_shell",
  "interpreter": "bash",
  "script": "...",
  "cwd": "...",
  "env_delta": {},
  "stdin": null,
  "reason_shell_required": "pipeline"
}
```

`exec_process` must call the OS process API with an argument vector and must not reconstruct a command line and send it through a shell. `exec_shell` is the explicit escape hatch for pipes, redirections, compound statements, parameter expansion, and shell built-ins. The error UI should recommend the process form when the attempted script is a simple command.

This catches or prevents:

- unmatched quoting used only to preserve spaces or punctuation in arguments;
- accidental expansion of `$`, backticks, glob characters, and command substitutions;
- cross-shell escape confusion where Bash quoting is sent to PowerShell or vice versa; and
- wrapper reconstruction bugs, if the stage record verifies the final `argv` rather than trusting the input JSON.

It does not catch quoting inside an argument intentionally passed to `bash -c`, `ssh host ...`, a database CLI, or another nested language. It also does not replace shell execution when the task actually needs shell composition.

The claim that this default would reduce the measured fingerprint is **likely (55-80%)**, supported by removal of the shell parser from simple process launches; the confidence is capped because no causal sample of the 1,631 events was examined in this ideation unit.

### Proposal B — UNVERIFIED: add forensic-style boundary controls and chain of custody

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Experiment that settles the UNVERIFIED premise: send a fixed sentinel corpus through every supported model/tool/transport/adapter/OS combination and compare captured representations at each boundary with the exact expected bytes and `argv` elements.

For each execution, record a compact, secret-safe stage ledger:

```text
request_id
tool schema version
model-emitted argument digest + length
post-JSON-decode argument digest + length
adapter-normalized argument digest + length
spawn target and argv-element digests + lengths
interpreter name/version, if any
parse phase / spawn phase / process phase
result formatter version
```

Use deterministic sentinels in the proficiency suite: spaces, single and double quotes, trailing backslashes, dollar signs, backticks, newlines, tabs, Unicode, empty arguments, Windows drive paths, UNC paths, glob characters, and shell metacharacters. For sensitive production calls, retain digests, lengths, types, and redacted spans by default; raw values require the existing secure trace policy.

This is the contamination-control translation:

- a **negative control** is a case expected to produce no shell parse at all under `exec_process`;
- a **positive control** is a deliberately malformed shell script that proves the parse-error detector fires and localizes the expected span;
- a **process blank** is a no-op payload sent through serialization and adaptation, then inspected before any user command runs;
- an **elimination registry** maps known adapter/version transformations to their signatures, allowing a changed length/digest to be attributed to a handling stage.

It would catch losses or insertions caused by JSON escaping, newline normalization, wrapper concatenation, an OS adapter, or result redaction—classes that a final `EOF` alone cannot localize. It would not explain a command that arrived intact but was grammatically wrong from the model.

This ledger is **likely (55-80%)** to localize boundary-induced failures with one recorded execution. Evidence: each proposed boundary has an independently captured digest/length, so the first divergence narrows the stage. It is only “likely,” not “almost certain,” because a wrapper could mutate data after the last instrumentation point, and digests without raw authorized inspection can establish difference but not its semantic cause.

### Proposal C — UNVERIFIED: return sequenced, typed parse evidence instead of generic stderr

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Experiment that settles the UNVERIFIED premise: randomized paired evaluation on held-out quoting failures, comparing retry success, repeated identical attempts, tool-call count, and token cost for raw stderr versus the typed diagnostic below.

Before executing `exec_shell`, invoke the exact selected interpreter's parser-only facility where one exists. A Bash implementation can use syntax checking; a PowerShell implementation can use its parser API. Return the evidence in this order:

```json
{
  "kind": "shell_parse_error",
  "phase": "preflight",
  "interpreter": {"name": "bash", "version": "..."},
  "source_digest": "...",
  "span": {"start_byte": 84, "end_byte": 85, "line": 2, "column": 19},
  "parser_evidence": "unexpected EOF while looking for matching quote",
  "diagnosis": "opening single quote has no closing delimiter",
  "retriable_unchanged": false,
  "safe_next_action": "use exec_process argv[] if shell composition is unnecessary"
}
```

Raw evidence comes first; diagnosis is explicitly a derived layer; remediation is last. This is the narrow LSU-E transfer. Preserve byte offsets against the exact parsed representation, not a prettified reconstruction. Never echo secrets merely to make the message friendly.

This would catch a malformed script before side effects begin, distinguish parse failure from spawn failure and process nonzero exit, identify the actual interpreter, and give the agent a machine-actionable reason not to repeat an unchanged request. It would miss runtime expansions, quote construction inside `eval`, strings parsed later by a nested interpreter, and semantically wrong but syntactically valid commands.

The typed error is **very likely (80-90%)** to classify ordinary unmatched-delimiter failures more accurately than a generic nonzero exit because it is emitted by the selected parser before execution. It is only **likely (55-80%)** to reduce retry loops; evidence from LSU-E supports the importance of information order in human expert decisions, but transfer to language-model repair behavior remains untested ([Dror & Kukucka, 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8385162/)).

### Proposal D — UNVERIFIED: run declared controls plus blind, production-shaped proficiency cases

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Experiment that settles the UNVERIFIED premise: pre-register and run a paired evaluation in an isolated sandbox, with an agent-blind mixture of ordinary tasks and held-out quoting cases, comparing the old and new interfaces on exact task success and pipeline-stage failures.

Build a versioned, held-out case bank from failure *shapes*, not copied secrets or paths. Each case contains:

- a natural task request;
- allowed side effects and sandbox boundary;
- exact expected executable and argument vector where applicable;
- acceptable shell ASTs where composition is genuinely required;
- expected stdout/stderr class, exit class, and filesystem delta;
- traps such as spaces, nested quotes, `$()`, backticks, multiline content, Windows paths, Unicode, and empty arguments; and
- a label hidden from the acting agent indicating ordinary case, negative control, positive control, or scored proficiency case.

Run two layers:

1. **Declared controls in CI.** Fast, obvious unit/property tests prove the detector recognizes known-present parse failures and does not reject known-valid cases. These are the forensic positive and negative controls.
2. **Blind end-to-end proficiency runs.** In an isolated evaluation session—not live owner work—mix held-out cases into realistic task sequences. Freeze the complete trace before revealing labels. Score exact effects, not the agent's self-report. Mask A/B implementation labels from any human adjudicator until ambiguous outcomes are classified; automated exact-match scoring needs no such masking.

Primary metrics should be task success, unmatched-quote parse failures per shell call, unintended expansion/side effect, repeated normalized request, calls-to-recovery, latency, and token/tool cost. Report results by shell-required versus shell-unnecessary tasks so a lower error rate cannot be purchased by refusing useful shell work.

Blind evaluation would catch:

- special-care performance that appears only when the prompt announces a quoting test;
- errors introduced outside the component under unit test;
- the agent ignoring a structured process tool and unnecessarily selecting a shell;
- an error message that is technically correct but fails to produce recovery; and
- correlated agreement between two agents when both differ from known ground truth.

It would not yield a universal model error rate. The case bank is intentionally targeted, and the source literature explicitly warns that proficiency tests are not general error-rate studies ([Koehler et al., 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7552087/)).

A blind suite is **very likely (80-90%)** to give a more realistic estimate for the selected quoting cases than declared “be careful with quotes” tests, supported by the forensic blind-versus-declared evidence and whole-pipeline design. It is only **roughly even (45-55%)** that the test label can remain concealed over repeated runs: pathological case distributions and stable fixture patterns can reveal the test, just as forensic examiners detected unrealistic submissions.

## 4. Combined operating design

The minimal architecture is:

```text
agent
  ├─ exec_process(executable, argv[]) ───────────────┐
  └─ exec_shell(interpreter, script)                 │
             │ exact-interpreter parse preflight    │
             └───────────────────────────────────────┤
                                                     v
                                      existing tool/process bus
                                                     │
                                      stage ledger + typed result
                                                     │
                       declared controls / isolated blind evaluator
```

No second orchestration runtime is needed. No vector database, knowledge graph, durable-execution engine, trained critic, observability SaaS, or guardrail framework is introduced. The proposals ride the existing tool/hook/evaluation bus and use a small adapter, structured errors, and data fixtures. This passes the anti-overfit gate: the intervention is at the narrow representation boundary implicated by the failure class, and the measurement suite can be removed without changing task orchestration.

An implementation sequence, conditional on experiments, is:

1. Capture a privacy-scrubbed, stratified causal sample of unmatched-quote events.
2. Create positive/negative parser controls and prove the detector finds a known-present error before using absence claims.
3. Add the stage ledger in shadow mode.
4. Add `exec_process` and explicit `exec_shell` without removing current behavior.
5. Run paired replay, then agent-blind sandbox proficiency testing.
6. Change the default only if task success improves without increased unintended effects or unacceptable cost.

This staged combination is **very likely (80-90%)** to distinguish model-authored syntax defects from transport/adapter corruption, because intact stage digests plus parser location provide mechanically independent signals. It is **likely (55-80%)** to reduce the target error count if simple commands comprise a material share, which the causal-sample experiment must establish.

## 5. Adversarial alternatives considered

### “Just improve the shell prompt”

Rejected as the primary intervention. It is a declared reminder, not an independent control; it leaves the ambiguous string interface and the complete transport pipeline untouched. It may still be a cheap experimental arm. Prompt-only improvement is **unlikely (20-45%)** to be as durable as removing unnecessary shell grammar, because it relies on the same generative operator remembering the instruction on every call; this is a structural inference, not an observed comparison.

### “Run a second model as verifier”

Rejected as ground truth. It maps only to blind verification and can measure disagreement. It cannot establish the correct command when errors are correlated. Exact `argv` or sandbox effects are independently checkable and therefore stronger.

### “Escape every argument automatically”

Rejected as a universal rule. Escaping is interpreter-specific, nesting-depth-specific, and context-specific. An adapter cannot safely decide whether a string is a literal argument, shell program, regular expression, JSON fragment, remote command, or template. Typed `argv` removes the ambiguity for the common simple-process case; explicit shell mode preserves power where grammar is intentional.

### “Inject blind tests into real owner sessions”

Rejected. Forensic laboratories can design test evidence with controlled downstream handling; a harness-injected fake command could consume time, mutate state, pollute context, or misrepresent owner intent. The valid borrow is isolated realistic evaluation or safe shadow transformation, not counterfeit live work.

### “Store every raw command for chain of custody”

Rejected. It would turn diagnostics into a secret-collection mechanism. Digests, lengths, typed metadata, and narrowly redacted spans are the default; authorized raw capture must follow the harness's existing security policy.

## 6. Decision gates and falsifiers

The recommendation should be abandoned or narrowed if any of the following experiments falsifies its premise:

- Causal sampling finds that **almost all** unmatched-quote events occur inside tasks that intrinsically require nested shell programs, so `argv[]` cannot remove the relevant grammar.
- Stage ledgers show end-to-end byte/argument identity in all sampled failures, eliminating transport contamination as a meaningful contributor. This would retain typed execution but drop the elimination-registry emphasis.
- Typed diagnostics do not improve recovery versus raw parser stderr in randomized paired tests, or increase harmful retries.
- Blind and declared results are indistinguishable at useful sample size, making ongoing concealment cost unjustified.
- The agent reliably identifies proficiency cases and changes strategy, invalidating the blind estimate.
- Added complexity reduces total task success, increases latency/tool cost beyond a pre-registered budget, or encourages unsafe fallback to nested `shell -c`.

Finding any of these would be a successful unit outcome, not a reason to preserve the analogy.

## 7. Gaps and precise next experiments

This was explicitly an external ideation lens and did not inspect the local harness or subject repository. Therefore:

- **UNVERIFIED — causal composition of the 1,631 failures.** Settle by manually classifying a random, privacy-scrubbed sample into model-authored delimiter error, transport/adapter mutation, wrong interpreter, nested-language failure, and misleading fingerprint.
- **UNVERIFIED — current availability of a structured process tool.** Settle by inspecting the actual tool schemas and adapter implementation. No NATIVE claim is made.
- **UNVERIFIED — parser-only support and span fidelity for every installed shell/version.** Settle with known-valid and known-invalid positive controls against the exact deployed Bash and PowerShell executables.
- **UNVERIFIED — safe hook size.** The BUILD-SMALL classification assumes the existing bus permits request/result interception and process spawning without runtime replacement. Settle with a read-only schema/hook capability inspection and a throwaway prototype line count.
- **UNVERIFIED — model response to sequenced diagnostics.** Settle with randomized paired repair trials, including misleading-location and nested-interpreter cases.
- **UNVERIFIED — blindness durability.** Settle by asking the agent after each run whether it believed the task was a test, then correlate belief with performance; rotate realistic templates and keep final labels inaccessible during action.

## 8. Bottom line

Borrow **blind proficiency testing as an evaluation discipline**, **contamination controls as boundary sentinels and provenance**, and **sequential unmasking as diagnostic ordering**. Do not borrow forensic terminology without its ground-truth and pipeline requirements. Do not claim double-blind live execution. Do not treat a second agent's agreement as correctness.

The best concrete design is a quote-free `exec_process(executable, argv[])` default, an explicit `exec_shell` escape hatch with exact-interpreter preflight, a secret-safe stage ledger, typed raw-first diagnostics, and an isolated blind proficiency suite scored on exact effects. It is small enough to ride the existing bus and strong enough to be falsified before rollout.
