# X054 — Cross-domain borrow: control theory → parallel-agent orchestration

## Executive result

The useful borrow is **not “put a PID on worker count.”** It is a smaller, more defensible package: treat parallelism as a bounded actuator; require an observability/controllability preflight; probe capacity with additive increase; retreat with multiplicative decrease on corroborated congestion; suppress reversals with a dead band and hold-down interval; and prevent scale-up state from accumulating while the worker cap is saturated.

This is the control logic behind congestion avoidance translated to a worker pool. In its native setting, Chiu and Jain formulate congestion avoidance as a feedback-control problem in which resources sense load, users change offered load, and the controller is judged on efficiency, fairness, convergence time, and oscillation size. Under their model, additive increase/multiplicative decrease (AIMD) converges toward an efficient and fair operating point ([paper, DOI 10.1016/0169-7552(89)90019-6](https://doi.org/10.1016/0169-7552(89)90019-6); [accessible paper copy](https://www.cs.cmu.edu/~srini/15-744/F02/readings/CJ89.pdf)). The Internet Engineering Task Force describes the operational form: increase cautiously in the absence of congestion, halve the congestion window on a congestion indication, and begin with a bounded slow-start phase ([RFC 2914, §9](https://datatracker.ietf.org/doc/html/rfc2914#section-9)).

The structural analogy is **likely (55-80%) to transfer as a conservative heuristic**, because both systems expose a discrete offered-load knob and both can enter a region where more offered work raises delay or failure without raising useful throughput. The evidence is the shared causal skeleton—bounded resource, delayed feedback, load actuator, congestion response—rather than similarity of vocabulary. It is **almost certainly not (1-5%) valid to transfer Chiu–Jain’s convergence guarantee**, because heterogeneous, dependency-constrained, finite agent tasks violate its shared-feedback, synchronized-update, and homogeneous-load abstractions; those assumptions are explicit in the paper’s model and summarized in its equations and convergence argument ([Chiu–Jain paper](https://www.cs.cmu.edu/~srini/15-744/F02/readings/CJ89.pdf)).

The proposal below is **UNVERIFIED for this harness; a shadow replay followed by a capped randomized canary, specified in “Experiments,” would settle it.** No local subject-tree claim is made: this unit is an ideation lens, as instructed.

## 1. What control theory has already solved

### 1.1 Observability before feedback

For a state-space system, observability asks whether internal state can be reconstructed from measured outputs over an interval. Åström and Murray define a linear system as observable when its state can be determined from the output history and give the observability-matrix rank test ([*Feedback Systems*, output-feedback chapter](https://www.cds.caltech.edu/~murray/books/AM08/pdf/am08-outputfbk_10Sep12.pdf)). This is not generic “monitoring.” It is an identifiability condition: a controller cannot reliably react to a latent condition if distinct internal conditions yield indistinguishable measurements.

The orchestration translation is concrete. “Workers are slow” can be produced by at least four different states:

1. a saturated shared resource;
2. harder tasks entering the ready queue;
3. workers blocked on the same prerequisite;
4. retries or tool failures consuming slots without useful completion.

If the harness observes only wall-clock completion rate, these states are aliased. A valid feedback input therefore needs separate measurements of ready backlog, active-worker age, useful completions, retry/failure work, and at least one resource-pressure signal. The proposed governor must refuse aggressive automatic scaling when these signals are missing or stale.

That gate would catch an **UNVERIFIED current blind spot: apparent “congestion” that is really workload-mix or dependency change; the stratified replay experiment in §6.1 would settle whether the present harness misclassifies it.** It is **very likely (80-90%) that the gate reduces false reactions in a heterogeneous workload**, because conditioning on task class and readiness separates causes that a single throughput series cannot; the evidence is the observability definition plus the explicitly different latent states above. The exact reduction is UNVERIFIED until replay.

### 1.2 Controllability before optimization

Controllability asks whether admissible inputs can drive the system state where desired; in the linear case it is tested by the controllability matrix. Åström and Murray present controllability and observability as the dual prerequisites for state-feedback and output-feedback design ([*Feedback Systems*, state-space/output-feedback material](https://www.cds.caltech.edu/~murray/books/AM08/pdf/am08-outputfbk_10Sep12.pdf)).

For orchestration, the actuator is the admitted worker count, not the nominal configured maximum. The system is locally controllable with respect to throughput only if changing admitted workers changes useful throughput or congestion on the timescale being controlled. A serial dependency chain, external API rate limit, single locked file, or empty ready queue makes worker count ineffective.

The harness translation is a perturbation test: after moving from `n` to `n+1`, ask whether a confidence interval for normalized useful throughput or congestion moves after the completion delay. If repeated perturbations have no detectable effect, mark the epoch **worker-count-uncontrollable**, stop scaling upward, and emit the likely bottleneck class instead of continuing to allocate workers.

This would catch an **UNVERIFIED current blind spot: paying for nominal parallelism when the ready-work graph or external bottleneck makes concurrency ineffective; the intervention test in §6.2 would settle it.** It is **likely (55-80%) to save wasted worker starts on dependency-heavy work**, because a no-effect intervention directly tests actuator authority; the wide confidence band reflects task heterogeneity and low sample sizes.

### 1.3 Negative feedback through AIMD

Chiu and Jain’s key mechanism is a distributed increase/decrease law driven by a congestion bit. Additive increase probes spare capacity without making the probe size grow with the current allocation. Multiplicative decrease retreats in proportion to how far the system may have overshot. Their analysis evaluates trajectories in efficiency/fairness space and derives AIMD as satisfying the relevant convergence conditions under the model ([Chiu–Jain](https://www.cs.cmu.edu/~srini/15-744/F02/readings/CJ89.pdf)). RFC 2914 records the production rule used by TCP: at most one-window-unit additive growth per round trip without congestion and a one-half reduction after congestion ([RFC 2914, §9.2](https://datatracker.ietf.org/doc/html/rfc2914#section-9.2)). RFC 5166 further makes explicit that congestion controllers trade responsiveness, smoothness, and aggressiveness rather than maximizing a single number ([RFC 5166, §2](https://datatracker.ietf.org/doc/html/rfc5166#section-2)).

The useful agent analogue is:

```text
if ready_backlog <= admitted_workers:
    hold                         # no demand for another worker
elif congestion_confirmed:
    n_next = max(n_min, floor(beta * n))
    enter_hold_down()
elif evidence_window_complete and not in_dead_band:
    n_next = min(n_cap, n + 1)  # probe capacity
else:
    hold
```

`beta` is a configuration value to tune in experiment, not a claimed universal `0.5`. An agent worker is far more expensive and less divisible than a packet window; aborting half of running tasks could destroy useful work. Multiplicative decrease therefore applies to **new admissions** and desired concurrency, while already-running non-preemptible work drains unless a separate cancellation policy authorizes cancellation.

It is **likely (55-80%) that asymmetric “+1, then proportional retreat” is safer than symmetric step-up/step-down for an unknown saturation knee**, because additive probing bounds each exploratory increase while multiplicative retreat exits overload quickly; Chiu–Jain and RFC 2914 establish that behavior for congestion windows. Agent-task nonstationarity prevents a stronger band.

### 1.4 Dead band, hysteresis, and sampled-data stability

On/off feedback changes its entire actuation for a small sign change and therefore tends to oscillate. Åström and Murray explicitly introduce a dead zone or hysteresis to modify such controllers and explain the overreaction mechanism ([*Feedback Systems*, simple forms of feedback, pp. 23–24](https://www.cds.caltech.edu/~murray/books/AM08/pdf/am08-hyperref_19Jul11.pdf)). A production analogue appears in Kubernetes’ autoscaler: it takes no action inside a configurable tolerance and uses a stabilization window to prevent replica-count flapping ([Kubernetes HPA algorithm](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#algorithm-details); [HPA v2 behavior API](https://kubernetes.io/docs/reference/kubernetes-api/autoscaling/horizontal-pod-autoscaler-v2/)).

Worker results are delayed measurements. Feedback delay can degrade performance or create instability; the open control-theory tutorial by Frank describes delay as reducing usable feedback and complicating dynamics ([“Time Delays,” *Control Theory Tutorial*](https://link.springer.com/chapter/10.1007/978-3-319-91707-8_13)). Consequently the controller must not reverse direction on every completion. It should use:

- a no-action band around zero estimated marginal benefit;
- separate enter/exit thresholds (hysteresis);
- a hold-down of at least one representative completion horizon after a scale change;
- a maximum change rate; and
- conservative “do not scale down” behavior when metrics are missing, analogous to HPA’s treatment of missing metrics ([Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#algorithm-details)).

It is **very likely (80-90%) that hysteresis plus a completion-aware hold-down reduces worker-count flapping**, because both the control text and the deployed HPA design use these mechanisms specifically to suppress oscillatory switching. Whether it improves total harness utility is **UNVERIFIED; the oscillation and utility endpoints in §6 would settle it.**

### 1.5 Saturation and anti-windup

An actuator saturates when the controller requests more than can physically be delivered. With integral action, error continues accumulating even though the actuator is pinned, causing overshoot and slow recovery when saturation clears. Åström and Murray describe this integrator-windup problem and the need to feed the saturated, actual actuation—not the impossible command—back into the controller/observer ([*Feedback Systems*, PID/implementation chapter](https://www.cds.caltech.edu/~murray/books/AM08/pdf/fbs-pid_17Aug2019.pdf)). The classical remedies are conditional integration (stop integrating in the direction of saturation) and back-calculation (drive internal controller state toward the realized actuator output).

Even an AIMD governor can accidentally recreate windup if it maintains `desired_workers` or a backlog-pressure accumulator above `n_cap`. The translation is:

```text
realized = clamp(requested, n_min, n_cap)
if realized != requested:
    pending_scale_up = 0
    demand_integral = back_calculate_toward(realized)
observer_input = realized_admissions   # never requested admissions
```

When capacity returns, the harness then resumes from realized state rather than releasing a stored burst of stale scale-up requests. This would catch an **UNVERIFIED current blind spot: scale-up debt accumulated at a cap and discharged after slots free; a forced-cap step test in §6.3 would settle whether that state exists today.** It is **very likely (80-90%) that explicit realized-versus-requested bookkeeping prevents this particular windup mechanism**, because the update removes the state that causes it; this does not imply a broad throughput improvement.

## 2. Proposed harness change — UNVERIFIED: saturation-aware concurrency governor

**NATIVE-vs-BUILD: BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus).**

Build one policy module on the existing orchestration event bus. It consumes task-ready, worker-start, worker-finish, retry/error, token/cost, and resource-pressure events and emits only an admission limit plus a reason code. It does not schedule tasks, create a second runtime, persist a knowledge graph, or judge semantic correctness.

The recommendation is **UNVERIFIED because the premise that the existing event bus exposes completion-correlated ready/backlog and realized-admission data has not been checked in this ideation unit; an event-schema inventory plus a known-present synthetic-event detector test would settle it.** If those fields are unavailable, the same design becomes BUILD-LARGE and fails the anti-overfit gate; in that case, do not build it as proposed.

### Inputs and derived signals

Use two families of mechanically independent congestion evidence before a multiplicative decrease:

1. **Work-output signal:** useful completions per elapsed minute, normalized within a task class or predicted-cost bucket; optionally useful completions per token/currency unit.
2. **Pressure/failure signal:** queueing delay, tool/API throttling, retry fraction, memory/CPU pressure, or worker-start latency.

A downshift requires one work-output degradation and one pressure/failure increase across a post-change evidence window. This protects against declaring overload from a single detector. Before enabling control, inject a known-present synthetic completion and a known-present synthetic pressure event and prove each detector sees its control; this satisfies the mechanical detector-validation requirement without assuming telemetry correctness.

“Useful completion” must initially be a narrow observable event: accepted artifact/check completion without immediate retry or owner reversal. Semantic quality is not observable at dispatch time. It is **unlikely (20-45%) that any cheap online metric fully captures semantic value**, because quality can be delayed, task-specific, and owner-dependent; no stronger claim is supported. The controller should therefore optimize a constrained proxy and report it plainly, not call it quality.

### State

Maintain only ephemeral per-run state:

- current realized admission limit `n`;
- hard bounds `n_min`, `n_cap`;
- previous scale direction and timestamp;
- rolling pre/post intervention windows;
- task-mix strata;
- congestion-evidence bits and freshness;
- saturation flag and last unsaturated `n`;
- reason code: `PROBE_UP`, `CONGESTION_DOWN`, `DEADBAND_HOLD`, `DELAY_HOLD`, `UNOBSERVABLE_HOLD`, `UNCONTROLLABLE_HOLD`, or `CAP_HOLD`.

No cross-run learned model is required. Ephemeral state is deliberate: workload regimes change, and durable estimates invite stale-policy overfit.

### Control epoch

An epoch ends only when either (a) enough post-intervention tasks have completed in comparable strata or (b) a safety congestion event fires. A wall-clock timer alone is invalid when tasks vary by orders of magnitude. Increase by one only when ready independent work exceeds admitted workers and the last probe is evaluable. Decrease desired admissions multiplicatively only on corroborated congestion. Hold inside the dead band. Freeze upward movement when observability or controllability checks fail.

The governor must log the counterfactual it is testing: “At comparable task mix, did `n+1` improve useful completion without crossing pressure bounds?” That record makes later replay possible.

### What it is designed to catch

The module is designed to surface:

- the saturation knee where `n+1` adds cost, latency, retries, or contention but no useful throughput;
- false demand when few tasks are dependency-ready;
- a shared external bottleneck that worker count cannot control;
- oscillation caused by reacting faster than task completion feedback arrives;
- stale scale-up debt at the worker cap;
- misleading aggregate throughput caused by task-mix changes; and
- telemetry states in which automatic control is not justified.

Whether these are **currently missed is UNVERIFIED; two independent signals are required before that absence can be claimed: (1) a static policy/event-path inventory that proves a known-present fixed-limit policy is detectable and finds no equivalent adaptive mechanism, and (2) a behavioral step-load trace showing the harness fails to hold or retreat at a measured knee. That paired audit would settle the claim.** This unit intentionally does not inspect the local repo.

## 3. Adversarial transfer analysis

### Structural correspondences that do transfer

| Control/congestion system | Agent orchestration |
|---|---|
| offered load/window | admitted parallel workers |
| bottleneck capacity | tool/API/CPU/memory/coordination capacity |
| delivered throughput | useful completed work per time |
| loss, marks, queue delay | retries/errors/resource pressure/completion delay |
| round-trip feedback delay | task start-to-evaluable-result delay |
| actuator saturation | hard worker/token/rate cap |
| congestion-window oscillation | worker-count flapping |

These correspondences are causal, not metaphorical: changing admissions changes offered work; shared constraints can saturate; measurements arrive after actuation; and actuation is bounded. That is enough to justify a guarded feedback experiment.

### Assumptions that do not transfer

1. **Packets are comparatively homogeneous; agent tasks are not.** One worker may perform a two-second lookup and another a forty-minute build. Raw completion rate is confounded by mix.
2. **Network demand is often treated as sustained; an agent task graph is finite and phase-changing.** The “optimal point” can move before the controller estimates it.
3. **TCP’s feedback and actuation are fine-grained; workers are lumpy and often non-preemptible.** A multiplicative decrease cannot safely mean killing half the tasks.
4. **Network success is mechanically observable as delivery; agent usefulness may require tests, review, or owner judgment.** Fast wrong work can look like throughput.
5. **Parallel workers may interfere semantically, not only through capacity.** Duplicate work, edit conflicts, and inconsistent assumptions are not well represented by queue pressure.
6. **The ready-work graph constrains parallelism.** More nominal workers do nothing when prerequisites serialize the work.
7. **Chiu–Jain’s convergence result assumes a simplified feedback/update model.** Asynchronous task finishes, changing capacity, multiple bottlenecks, and unequal workers invalidate direct theorem transfer ([Chiu–Jain](https://www.cs.cmu.edu/~srini/15-744/F02/readings/CJ89.pdf)).

Therefore the result is a policy heuristic with guardrails, not a stability proof. It is **very unlikely (5-20%) that a fixed globally tuned controller will remain near-optimal across all harness workloads**, because at least task duration, dependency width, and bottleneck capacity change by regime. The evidence is the seven violated assumptions above. Per-run probing and fail-safe hold are essential.

### Why not PID, model-predictive control, or extremum seeking?

- A PID needs a meaningful setpoint and sufficiently stable error dynamics. “Optimal useful parallelism” is neither directly measured nor stationary here. Its integral term also creates the exact saturation risk anti-windup must repair.
- Model-predictive control would require a predictive workload/resource model and constraint solver. That is disproportionate before the plant is shown observable and controllable.
- Extremum-seeking control can optimize an unknown response curve by deliberate perturbation, but persistent dither spends real agent work and assumes the objective can be measured on the adaptation timescale. Semantic utility violates that assumption.

It is **very likely (80-90%) that guarded AIMD is the better first experiment than those three mechanisms**, because it requires only a congestion classification and bounded probes, while the alternatives require a stable scalar objective or plant model. This is an engineering prior, UNVERIFIED for the harness; §6’s head-to-head replay would settle it.

## 5. Safety and failure policy

The default under uncertainty is hold, not scale up. Specifically:

- missing/stale output signal → `UNOBSERVABLE_HOLD`;
- conflicting congestion signals → `DEADBAND_HOLD` and gather another window;
- no ready independent tasks → reduce only future admissions, never cancel merely to meet the number;
- hard safety pressure → immediate admission decrease, independent of throughput estimate;
- cap reached → clear upward debt and observe realized admissions;
- task mix changes sharply → reset comparison windows;
- owner/manual override → bumpless transfer: initialize controller state from the realized override before resuming. Anti-windup and bumpless transfer are treated together in control practice because controller state must track actual actuation across saturation or mode changes ([Åström–Murray PID chapter](https://www.cds.caltech.edu/~murray/books/AM08/pdf/fbs-pid_17Aug2019.pdf)).

It is **almost certain (90-99%) that logging realized rather than requested admissions is necessary for valid causal evaluation**, because the intervention is what actually happened, not what the controller asked for; saturation makes the two observably different. This is a measurement-validity claim, not a performance prediction.

## 6. Experiments that settle the UNVERIFIED claims

### 6.1 Offline shadow replay

Replay historical run events without changing execution. First validate both detectors with injected known-present controls. Stratify tasks by available task type, predicted cost, and dependency readiness. Compare fixed concurrency with simulated AIMD decisions using:

- useful completions per wall-clock hour;
- useful completions per token/currency unit;
- p50/p90 time to accepted completion;
- retry/error work fraction;
- peak admitted and active workers;
- number and amplitude of direction reversals;
- time pinned at cap and accumulated requested-minus-realized debt; and
- fraction of epochs declared unobservable or uncontrollable.

Replay cannot establish causal effects when historical runs did not explore alternate concurrency. It can falsify the detector, reveal impossible telemetry requirements, and estimate how often the policy would act. A positive replay result remains insufficient for deployment.

### 6.2 Randomized capped canary

On low-risk, restartable workloads with at least several independent ready tasks, randomize eligible epochs between the fixed policy and a bounded `n→n+1` probe. Block by task class and ready-graph width. Do not kill running tasks on downshift. Pre-register safety limits and utility endpoints.

This intervention tests controllability: if `n+1` repeatedly changes neither useful throughput nor pressure, classify the regime as worker-count-uncontrollable. It also estimates the local marginal effect rather than inferring it from before/after workload drift.

Promotion criterion: non-inferior accepted completion time and semantic acceptance, lower or equal cost/error burden, materially fewer overload epochs, and no increase in owner reversals. Exact margins must be chosen from owner utility; choosing them here would be fabricated precision.

### 6.3 Forced-cap anti-windup step test

In a synthetic harness fixture, hold the cap below requested demand for several epochs, then release it. Assert mechanically that:

1. the requested-realized mismatch is recorded;
2. upward accumulator/debt stays zero or back-calculates to realized state;
3. release causes at most the configured slew-rate increase; and
4. the controller does not replay stale requests.

Use two independent verification signals before declaring done: controller-state inspection and observed worker-start count. Prove both detectors on known-present injected debt and worker-start events first.

### 6.4 Delay and oscillation test

Use synthetic task durations with fixed, heavy-tailed, and bimodal distributions. Sweep control epoch, hold-down, dead-band width, and `beta`. Compare reversal count, overshoot above the known synthetic capacity knee, settling time, and utility. This is the experiment that determines whether completion-aware epochs outperform wall-clock polling and whether the controller remains stable enough under delayed feedback.

### 6.5 Head-to-head policy test

Compare four policies under identical synthetic and canary regimes:

1. fixed worker count;
2. symmetric hill climb (`±1`);
3. guarded AIMD;
4. a minimal proportional controller without an integral term.

Do not add PID/MPC/extremum-seeking unless all four simpler policies fail and telemetry demonstrates a stable measurable objective. This preserves the anti-overfit gate.
