## Executive finding

`rules/dart/testing.md` is coherent as a short catalogue of Flutter test techniques, but it is not coherent as an enforceable rule. I found **eight collisions**: two contradictions/stale precedence defects, one redundancy, four substantive enforcement gaps, and one unruled enforcement. The highest-impact defect is the coverage contract: the rule says business logic must reach 80% and below-threshold CI must block, while the common rule declares `.coverage-thresholds.json` the single source of truth (100% on metaswarm, 80% only as a fallback), and the shared receipt hook accepts the mere success of a command containing `--coverage` as proof that a coverage claim is satisfied. Those are three different meanings of “coverage passed.”

The rule's claimed inheritance is also mechanically broken for Dart. `dart/testing.md:9` says it extends `common/testing.md`, but the common file's path frontmatter enumerates many languages and omits `.dart`, `pubspec.yaml`, and `analysis_options.yaml` (`common/testing.md:1-20`). Thus a Dart-only edit activates the specific file but not the common contract it claims to extend. This is a static wiring fact, not a conclusion from the corpus hook detector.

The measured corpus cannot establish whether Dart testing behavior followed this rule. Its raw-transcript ingestion is nearly complete (`corpus.json:2-10`: 11,633 files seen, zero failed, one bad line), but the distilled fields contain zero Dart/Flutter-specific strings while a known-positive testing control finds 170 `pytest|coverage` strings. The corpus records no commands or language labels per session, and its entire hook section explicitly says `DETECTOR_STATUS: BROKEN` (`corpus.json:13261`). Therefore a compliance rate is **UNVERIFIED; the settling experiment is a fresh raw-transcript pass that classifies Dart projects and extracts `flutter test`, `dart test`, golden-update, and coverage commands plus their exit results**. Treating the zero Dart strings as “the rule was never followed” would violate the required known-positive-control discipline.

**Collision**

This resolution is **very likely (80-90%)** to restore the intended common floor because the evidence is the direct mismatch between the two frontmatter lists; the residual uncertainty is the undocumented loader composition behavior. **UNVERIFIED: whether Claude Code follows links in rule prose and auto-loads the linked common file; settle with a disposable project and an instruction-debug/rule-load trace.** Until that experiment, do not rely on the prose link as inheritance.

### C02 — Coverage threshold has two authorities and two values

**Class:** CONTRADICTION

**Artifacts and exact lines**

- `~/.claude/rules/dart/testing.md:212` says “Target 80%+ line coverage for business logic.”
- `~/.claude/rules/dart/testing.md:215` says below-threshold coverage failures should block CI.
- `~/.claude/rules/common/testing.md:23` defines `.coverage-thresholds.json` as the threshold authority, specifies 100% on metaswarm, and uses 80% only where none is defined.
- `~/.claude/rules/common/testing.md:38` repeats that SSOT/fallback rule.
- `~/.claude/rules/common/code-review.md:56-57,97-98` repeats the same SSOT/fallback during completion review.
- `~/.claude/AGENTS.md:124-126` says project governance may add stricter process and must not be relaxed by a lower layer.
- `~/.claude/rules/README.md:95-98` says language-specific rules override common defaults where language idioms differ.

**Collision and precedence**

The Dart rule reads as a fixed 80% target, while the common rule says the checked-in threshold file wins and metaswarm is 100%. `rules/README.md` would normally let the Dart-specific rule override the common one, but coverage rigor is not a Dart idiom and `AGENTS.md` places stricter project governance above lower defaults. Therefore precedence resolves a metaswarm/project threshold in favor of the stricter project value, but it does **not** resolve the same-level wording defect for a non-metaswarm Dart project whose threshold file says, for example, 90%. The Dart sentence still advertises 80% as an independent target.

**Specific resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** Replace lines 212 and 215 with: “Coverage threshold is the value in the repository's `.coverage-thresholds.json`; if absent, use 80% line coverage for business logic. CI must enforce that same value.” Define whether the gate is line-only or line+branch and name the lcov parsing command. Remove duplicated numeric defaults from language files. This is **almost certain (90-99%)** to eliminate threshold drift because every cited rule already names the threshold file as SSOT; only the Dart wording fails to defer to it.

### C06 — Test-tamper policy is enforced without being stated in the Dart testing rule

**Class:** UNRULED

**Artifacts and exact lines**

- `~/.claude/rules/dart/testing.md:1-215` contains no rule against deleting test files, reducing assertions, adding skips, or adding trivial assertions.
- `~/.claude/settings.json:162-171` registers `test-tamper-guard` for Bash commands.

- `~/.claude/hooks/test-tamper-guard/guard.py:53-67` recognizes generic `test/` paths and `_test` names, so conventional Dart tests are in scope.
- `~/.claude/hooks/test-tamper-guard/README.md:32-38` says default behavior warns, while opt-in block mode exits 2 for three signals.
- `~/.claude/settings.json:4-20` does not set `TEST_TAMPER_MODE`, so the shipped configuration uses the hook's default warn mode.
- `~/.claude/AGENTS.md:64-70` permits blocking only irreversible/dangerous actions and requires other guidance to inject.

**Collision and precedence**

Conventional Dart test changes can trigger a policy the Dart testing rule never tells the agent about. In the shipped settings it is a warning, so it is consistent with `AGENTS.md`'s inject-not-block rule. If opt-in block mode is enabled, blocking a staged test deletion/assertion reduction is not necessarily irreversible or dangerous, so the higher-precedence `AGENTS.md §6` wins and that mode is contradictory unless a separate safety rationale applies to the exact action. The hook is also Bash-only while the box enables the PowerShell tool (`settings.json:5-6,141-169`), so its policy varies with shell choice.

**Specific resolution — NATIVE-vs-BUILD: CONFIG (settings/JSON only).** State the anti-tamper principle in common testing rules: test weakening requires an explicit rationale and equivalent/stronger replacement evidence. Keep enforcement advisory; remove or disable the non-dangerous exit-2 option. Register the same semantic pre-commit check for both Bash and PowerShell through the shared dispatcher, based on parsed command verb rather than shell-specific text. This is **likely (55-80%)** to make behavior shell-independent because both shell tools already traverse the shared PreToolUse dispatcher; exact command normalization is **UNVERIFIED: settle with paired Bash/PowerShell fixtures for commit, quoted prose mentioning commit, and non-commit commands.**
