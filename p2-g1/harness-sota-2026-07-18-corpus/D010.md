# D010 — Bench-first sequencing

## Question and verdict

**Verdict: build a minimum viable, trustworthy bench before promoting the other ~900 recommendations, but do not wait for a comprehensive benchmark platform before doing emergency containment or writing candidate patches.** The correct sequence is:

1. repair the existing false-green benchmark boundary;
2. freeze and run a small deterministic baseline against the unmodified harness;
3. require every recommendation tranche to add or select its own matched regression case before promotion;
4. grow stochastic model-in-loop and broad public-suite coverage alongside, rather than ahead of, implementation.

I assess this verdict as **very likely (80-90%)**, based on four concrete signals: (a) the corpus contains large, heterogeneous and repeated failure classes, so unmeasured interactions are not hypothetical (`/local_disk0/codexwork/bundle/inputs/corpus.json:13-109,8839-9065`); (b) the current weekly router bench is demonstrably false-green at its real subprocess boundary (`/local_disk0/codexwork/bundle/claude/hooks/harness-bench/bench.py:55-65,88-96,150-160`; `/local_disk0/codexwork/bundle/claude/hooks/semantic-router/eval.py:209-242`; disposable run recorded below); (c) the shared harness already exposes a deterministic dispatcher, isolated state roots, closed wire contracts, 16 lifecycle events, 511 component tests, and staging primitives, so the first useful bench is a thin addition rather than a new runtime (`/local_disk0/codexwork/bundle/agents/harness/registration.py:17-53`; `dispatcher.py:235-338,518-556`; `modules.py:119-149,303-417`; `tests/test_dispatcher_and_registration.py:267-304`); and (d) current agent-evaluation prior art recommends small failure-derived suites, clean trial isolation, final-state grading, positive and negative cases, and repeated trials [Anthropic, *Demystifying evals for AI agents*](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [tau-bench](https://arxiv.org/abs/2406.12045), and [ToolSandbox](https://arxiv.org/abs/2408.04682).

The remaining uncertainty is mainly schedule risk: **likely (55-80%)** that one owner plus agents can land the minimum gate in two to four working days, because the injectable boundaries and 511-test pytest substrate already exist; **UNVERIFIED — the experiment that settles this is a four-hour spike implementing the JSON contract repair and two end-to-end trace cases in a disposable worktree, followed by extrapolation from measured lines, fixture time, and runtime.** This estimate is not grounds for allowing a large bench build to become a prerequisite.

This answer deliberately separates three things that are often conflated:

- **containment:** reversible action that stops known ongoing damage;
- **promotion:** making a recommendation live or broadly enabled;
- **bench completion:** an evolving capability, not a one-time finished product.

Bench-first applies strictly to **promotion**. A dead MCP can be quarantined, an unsafe credential can be revoked, or an actively destructive operation can be stopped before the suite is complete. Those are break-glass containment actions and must be recorded as such, with a rollback path and a regression fixture added immediately afterward. Candidate design and implementation can also proceed in isolated branches/worktrees while the minimum bench is built; only promotion waits.

## The current bench is not a trustworthy gate

This is a scoped claim about the unpacked weekly semantic-router bench, not a claim that every benchmark on the Windows host is absent or broken.

### Signal 1: static contract contradiction

`harness-bench/bench.py` invokes `eval.py --json`, requires stdout to be a JSON object containing `hybrid`, and deliberately returns scheduler success with no report on empty, malformed, or non-JSON output (`bench.py:55-65,84-96,150-160`). But `semantic-router/eval.py` defines `main()` without argument parsing and always prints a human-readable table (`eval.py:209-242`). The `--json` token is ignored by Python because the program never reads `sys.argv`.

### Signal 2: independent disposable execution

On this Linux job node I ran the unpacked evaluator with writes redirected and bytecode disabled:

```text
PYTHONDONTWRITEBYTECODE=1 SEMROUTER_NO_RECORD=1 HOME=<mktemp> \
  timeout 45s python .../semantic-router/eval.py --json > <tmp>/out.txt

return code: 0
stdout prefix: "=== per-case skill recall (L=lexical S=pure-semantic H=hybrid; ..."
json.loads(stdout): JSONDecodeError at line 1 column 1
```

The detector control was known-positive: the same Python `json.loads` path accepts the JSON shapes fabricated by `_raw()` in the bench tests (`test_bench.py:26-37`). Thus the failure is not “the JSON detector cannot recognize JSON.” Static source structure and runtime output are mechanically independent signals.

### Signal 3: the tests bypass the failed boundary

The test module states that every test injects a fake `eval_runner`; no real evaluator subprocess runs (`test_bench.py:1-8`). Even its “default runner” success test replaces `subprocess.run` and returns a fabricated JSON string (`test_bench.py:234-250`). Those tests correctly exercise parsing, ratcheting, and digest behavior, but cannot validate producer-consumer compatibility.

Therefore, a scheduler result of 0 means only fail-open execution, not a green routing regression result. The source explicitly promises to return 0 on parse error (`bench.py:14-17,150-160`). This is a concrete example of why bench correctness must itself be tested before it is allowed to govern 900 recommendations.

The existing net is also intentionally narrow: it measures hybrid skill/MCP routing recall only (`bench.py:2-20`; `README.md:1-9`). It cannot establish hook correctness, cross-provider parity, final-state safety, edit reliability, shell quoting, latency headroom, or recommendation-level task success.

## Steelman: the case for bench-first

### 1. Without a baseline, “improved” is not a falsifiable claim

Nine hundred changes create a combinatorial attribution problem. If changes land first and an owner-visible regression appears later, neither a static audit nor a model review can reliably identify which change caused it. The current corpus proves that defects already cross layers: prose-scanning guards changed tool choice, which moved work to a higher-failure shell; a result scanner could discard a successful call; a false orchestrator fact propagated to many agents. Those are interaction effects, not isolated unit bugs (`INPUT-known-harness-defects.md`, D1-D4).

Anthropic describes the same operational failure mode: without evals, teams debug reactively, cannot distinguish regression from noise, and “fix the bug and hope nothing else regressed”; it recommends eval-driven development and says 20-50 real-failure tasks are enough to start ([source](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The local situation is past the early-prototype threshold: hundreds of skills, many MCPs, two provider adapters, 16 lifecycle events, and 10.62 GB of observed operation make manual intuition an inadequate promotion oracle.

### 2. The first bench can be small because most infrastructure already exists

The shared dispatcher takes raw event JSON plus provider/event selectors and accepts an isolated `state_root` (`dispatcher.py:235-252,518-547`). Existing subprocess tests redirect harness state, memory checkpoints, and recall index to temporary paths (`tests/test_dispatcher_and_registration.py:267-299`). The module bus already supplies OFF/SHADOW/ADVISE/ENFORCE modes, forced sampling, and gate contracts (`modules.py:119-149,303-417`). A mechanical count found 511 top-level pytest test functions across 19 test files in the unpacked harness. The missing keystone is a small cross-event trace manifest plus a scorer, not a second execution engine.

### 3. Known defects make high-signal cases available immediately

The common reason to delay evals—no curated tasks—does not apply. The corpus supplies high-frequency fingerprints; the known-defects file supplies diagnosed true/false pairs; current schemas and tests supply valid inputs; audit D10 supplies a proposed 12-trace skeleton. The suite can begin deterministic and synthetic. Historical raw replay is not required for the promotion gate.

### 4. A bench constrains radical replacement as well as incremental evolution

The owner explicitly permits full replacement. That strengthens the bench-first case: replacement and evolution need the same fixed tasks, environment, model/config, budget, and oracle. Otherwise the new architecture can “win” by silently dropping hard cases, changing tool access, or spending more tokens and time. A common suite makes radical alternatives easier to consider honestly rather than protecting the incumbent.

### 5. The bench creates a deletion license

Only 78 of roughly 355 installed skills were invoked according to the pinned measured ground truth, but unused-in-corpus is not equivalent to useless. A routing and task suite lets the owner prune, quarantine, or replace aggressively while checking positive triggers, negative triggers, final outcomes, and cost. This is particularly important because the orphaned-plugin cleanup has already shown that apparently dead directories can lack live siblings while still being read by a live skill. A benchmark cannot alone prove deletion safety, but it supplies one necessary signal alongside live-reference inventory and recoverable quarantine.

## Steelman: the case against bench-first

### 1. A comprehensive bench can become the largest recommendation of all

An outcome-level agent eval platform could require environment provisioning, transcript correlation, Windows isolation, cost accounting, stochastic repeats, graders, dashboards, task curation, and maintenance. Building that before any fix would delay obvious value and violate the anti-overfit gate. It would also be a **BUILD-LARGE** second runtime if implemented as a new daemon/service. That is not justified here.

### 2. The bench can encode today’s defects and preferences

If cases are harvested mechanically from noisy transcripts, the suite may reward workarounds rather than desired outcomes. The corpus itself warns that its correction detector produced 41/41 false positives in one unfiltered smoke sample (`corpus.json:10371-10375`). A brittle exact-trajectory grader could penalize a superior replacement architecture merely for using a different path. Anthropic likewise warns that rigid graders, ambiguous tasks, and environment defects can produce false failures, and recommends grading outcomes rather than prescribed steps ([source](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### 3. Some fixes do not need a population-level experiment

Removing a dead route from active selection after confirming the server is disconnected, correcting a producer-consumer schema mismatch, or preventing command-line overflow can be locally provable with contract tests and direct probes. Delaying containment while waiting for pass^k statistics would be process theater. The bench must match evidentiary burden to risk.

### 4. Small stochastic samples can manufacture confidence

Three passes do not establish production reliability. Model updates, network conditions, Windows process limits, and provider behavior can change. `pass^3` is a useful smoke measure of “all three succeeded,” not a confidence interval over the owner’s workload. tau-bench introduced `pass^k` precisely because one lucky success does not establish reliability ([paper](https://arxiv.org/abs/2406.12045)); Inspect provides repeated-epoch and pass-at-k/pass-k-k metrics for larger experiments ([documentation](https://inspect.aisi.org.uk/metrics.html)).

### 5. Bench maintenance competes with harness improvement

Every task needs an owner, reference solution, failure mutant, environment pin, and retirement rule. Public benchmarks drift too. A suite without maintenance becomes another false-green control plane. This is a real recurring cost, and the current broken weekly boundary shows that “a bench exists” can be worse than an explicit gap if scheduler success is mistaken for measurement success.

## Reconciliation: bench-first means gate-first, not platform-first

The strongest version of each side is simultaneously true. The owner needs measurement before promotion, and a large generalized evaluation platform would delay value. The resolution is to make the first bench a **thin promotion gate on the existing pytest/dispatcher/state bus**, time-box it, and deliberately leave broad model benchmarking for later.

The minimum gate answers only five questions:

1. Did the candidate fix the exact failure it claims to fix?
2. Did matched benign behavior remain working?
3. Did any critical safety, cross-provider, persistence, or fail-open invariant regress?
4. Is the result terminal state consistent with the process output, rather than merely exit code 0?
5. Is latency still below the host deadline with useful headroom?

It does not attempt to answer whether the harness is globally optimal, whether one model is universally better, or whether an open-ended research response is aesthetically superior.

### Phase 0 — Repair and self-test the existing router net — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Add a real `--json` branch to `semantic-router/eval.py` (or make the consumer invoke a supported structured entry point), then add one subprocess integration test that executes the real producer and validates the full required schema. This repair is **almost certain (90-99%)** to expose the currently silent incompatibility, because both source and disposable runtime independently reproduce it. ### Phase 1 — Add the deterministic trace gate — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Implement one parametrized pytest entry point and a versioned JSON/YAML manifest. Keep runner/scorer logic under roughly 200 lines by reusing `HarnessDispatcher`, adapters, schemas, pytest temporary directories, and existing helper fixtures. Data fixtures do not justify a daemon.

Each manifest row must include `case_id`, version, source evidence, profile, provider(s), initial state hash, ordered input events, required final-state predicates, forbidden final-state predicates, timeout, and fixture hash. The scorer should emit `run_id`, candidate hash, case/trial/profile/provider IDs, terminal/action/reason, required/forbidden deltas, failed modules, elapsed milliseconds, and deterministic grade. Store results as local JSONL plus a concise Markdown summary; do not add telemetry SaaS.

The initial 12-case choice is **likely (55-80%)** to catch the highest-risk cross-layer regressions because it maps directly to observed defects and core lifecycle invariants, but coverage sufficiency is **UNVERIFIED — mutation-test the suite by injecting one controlled defect per claimed invariant; any mutant that remains green requires a new or corrected case.**

### Phase 2 — Validate the bench before trusting it — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Every admitted case must pass four meta-tests:

1. a known-good reference trace passes;
2. a no-op or deliberately malformed implementation fails;
3. the grader is deterministic when rerun on the same recorded state;
4. at least one alternative valid trajectory passes when multiple paths are legitimate.

For every absence detector, run a known-present control first, following the live D2 lesson. For every safety attack, include a matched benign/near-miss control. AgentDojo reports user-task utility separately from security under attack, a useful precedent for not averaging safety and usefulness into one opaque score ([results](https://agentdojo.spylab.ai/results/)). ToolSandbox’s milestone/minefield formulation is the appropriate precedent for allowing multiple valid trajectories while rejecting forbidden state ([paper](https://arxiv.org/abs/2408.04682)).

Run all deterministic cases three times from fresh roots initially. Report raw `passed trials / total trials`, pass@1, and `pass^3`; require every repeat for safety, redaction, exactly-once, parity, and recovery invariants. Explicitly label 3/3 as smoke evidence, not a production reliability estimate.

### Phase 3 — Freeze the pre-change baseline — **CONFIG (settings/JSON only)**

Run the validated suite against the unmodified deployed-source candidate in disposable state. Record:

- provider versions and model identifiers where a model is involved;
- active gate/profile mode hash;
- fixture/manifest hash;
- Python/PowerShell/Windows versions;
- pass/fail by case and trial;
- failure fingerprints;
- p50/p95/max elapsed time against the 2-5 second hook deadlines defined in `registration.py:36-53`.

Do not ratchet away a known failure. A baseline is a comparison point, not a declaration that current behavior is acceptable.

Windows execution is required before promotion for Glob/PowerShell/Bash quoting, plugin-path length, task scheduler, and CreateProcess behavior. This Linux unit cannot validate those host-specific outcomes. **UNVERIFIED — the settling experiment is the same manifest executed on the Windows subject’s disposable copy under both PowerShell 7 and Git Bash, with all state/cache paths redirected outside the live subject.**

### Phase 4 — Promote recommendations in evidence-shaped tranches — **CONFIG (settings/JSON only)**

Classify the ~900 recommendations before implementation:

- duplicate or superseded;
- unsupported claim needing verification;
- containment-only;
- config change;
- small bus-native build;
- large architecture proposal;
- mutually exclusive alternative.

Then sequence by failure family, not audit-unit number. Each tranche should be small enough to attribute a score movement and must declare its target cases before implementation. A practical first order is:

1. measurement integrity: broken router bench boundary, hook telemetry experiment, terminal-vs-exit oracle;
2. reversible containment: dead MCP routing quarantine and path-length pressure mitigation, without deleting ambiguous orphan trees;
3. high-frequency deterministic reliability: StructuredOutput schema contracts, Glob/command construction, Bash/PowerShell quoting, read-before-write discipline;
4. guard precision: use-versus-mention discriminator and matched benign controls;
5. broader routing, memory, subagent, and autonomy changes;
6. replacement candidates tested against the same frozen suite.

The exact tranche order after measurement integrity is **likely (55-80%)** to maximize early value because it follows measured damage and reversibility; **UNVERIFIED — settle ties by estimating affected calls from the corpus, implementing one isolated candidate per tied family, and comparing targeted pass delta, critical regressions, elapsed time, and operator effort.**

Promotion rule:

- no new critical safety, state-corruption, cross-session leakage, or provider-parity failure;
- all cases targeted by the candidate pass all required repeats;
- benign paired controls do not regress;
- unrelated existing failures are not silently rebaselined;
- the result carries source, manifest, profile, and environment hashes;
- rollback is rehearsed or mechanically obvious.

For stochastic task-success changes, deterministic green is necessary but not sufficient. Add 20-50 adjudicated real-failure tasks over time, pin model/tools/prompt/budget, use multiple clean trials, and grade final state where possible. Anthropic explicitly recommends starting with 20-50 simple tasks from real failures and isolated clean environments ([source](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## What must not be built first

### General-purpose eval daemon — rejected — **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Do not create a scheduler daemon, distributed durable-execution engine, vector database, knowledge graph, trained critic, guardrail framework, or observability SaaS. This would reintroduce components explicitly rejected by the anti-overfit gate and duplicate native pytest, scheduled-task, provider, dispatcher, ledger, and worktree buses. No evidence in this unit justifies it.

### Model judge as promotion authority — rejected — **BUILD-LARGE (new daemon/service/runtime -- needs its own justification)**

Subjective model review can diagnose open-ended failures later, but it must not be the first gate. The local defects are mostly deterministically gradable, and a judge would require calibration data that this unit did not verify. Anthropic recommends deterministic graders where possible and human calibration for model graders ([source](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### Public benchmark as the local regression gate — rejected — **CONFIG (settings/JSON only)**

Terminal-Bench, SWE-bench, GAIA, AgentBench, and similar suites can compare model-plus-harness capability later, but they do not directly exercise this owner’s hook schemas, ledger states, Windows shell rules, MCP topology, or observed guard false positives. Public suites are secondary calibration, not the promotion oracle. The local suite should remain small, failure-derived, and final-state based.

### Exact-trajectory golden transcripts — rejected — **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus)**

Do not compare one canonical sequence of tool calls byte-for-byte. ToolSandbox and Anthropic’s guidance both favor required/forbidden outcomes over rigid path matching. Exact trajectories overfit the current harness and would unfairly block a better replacement.

## Stop conditions and ownership

The minimum bench is ready to gate promotion when all of these are true:

- the real router producer-consumer integration test is green and its failure mutant is red;
- all 12 trace manifests have known-good and known-bad controls;
- the scorer checks terminal record and final state, not exit code alone;
- three fresh-root runs are recorded for both providers where applicable;
- Windows-specific cases have run on Windows, not inferred from Linux;
- source, manifest, profile, and environment hashes make a result reproducible;
- one candidate change has demonstrated fail-before/pass-after without unrelated regression.

At that point, bench-first has served its sequencing purpose. Do not block all work until 20-50 stochastic tasks, dashboards, full cost accounting, or public benchmark integrations exist. Those are later maturity layers.

Every recommendation owner thereafter owns the cases for the behavior they change; a small central bench owner maintains runner integrity, schema, isolation, and meta-tests. This follows Anthropic’s reported pattern of central infrastructure ownership with domain experts contributing tasks ([source](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## Alternatives and dead ends considered

1. **Use the corpus as a replay suite.** Rejected for v0. The distilled corpus contains counts, capped samples, fingerprints, and recall-biased correction candidates, not complete deterministic environments or reliable hook telemetry (`corpus.json:2-11,10371-10375,13260-13264`). It is excellent for prioritization and fixture discovery, not direct pass/fail replay.
2. **Treat audit D10 as already settled design.** Rejected. Audit findings are claims. This unit independently verified the dispatcher/test substrate, 511-test count, staging primitives, and broken router boundary, but did not execute the full Windows harness.
3. **Fix all known defects, then baseline the improved system.** Rejected. That destroys the counterfactual and makes regressions or accidental wins unattributable.
4. **Freeze every change until a statistically powered stochastic suite exists.** Rejected. It delays containment and ignores that most first-wave invariants are deterministic.
5. **Measure only end-to-end owner satisfaction.** Rejected as the only oracle. It is important but too sparse and confounded for attribution; the corpus correction detector’s poor precision illustrates the danger of mechanical sentiment/correction inference.
6. **Measure only unit coverage.** Rejected as the only oracle. The weekly bench has extensive unit tests around fake JSON yet fails at the real subprocess boundary; this is the canonical counterexample.

## Final sequencing answer

Yes: **bench before promotion**, with a hard two-to-four-day minimum-gate time-box and explicit break-glass containment exception. No: **do not build the whole imagined bench before implementation work begins**. Repair the false-green boundary, establish a 12-trace deterministic baseline on both providers and Windows where required, then let every recommendation pay for its own evidence as it moves from candidate to live.

That sequence is **very likely (80-90%)** to produce more reliable net improvement than either “ship 900 changes and evaluate later” or “pause all value for a large eval platform,” because it directly addresses the demonstrated false-green boundary, reuses the existing bus and 511 tests, preserves attribution, and avoids a second runtime. The experiment that would move confidence above this band is three completed recommendation tranches showing repeatable fail-before/pass-after results with no critical regressions and lower rollback/reopen rates than comparable pre-gate work.
