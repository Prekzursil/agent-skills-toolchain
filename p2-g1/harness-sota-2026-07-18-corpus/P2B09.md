## Executive verdict

OpenHands is no longer primarily a monolithic Docker coding agent. The current V1 SDK is a composable Python agent runtime with a synchronous reasoning/action loop, typed append-only events, optional conversation persistence, condensers, MCP adaptation, Claude-compatible hooks, file-defined subagents, risk-based confirmation, and optional Docker/Kubernetes workspaces. The latest official SDK release visible during this unit is v1.23.1 (2026-05-25), and the official V1 documentation/source is therefore the relevant comparison target ([SDK repository and release](https://github.com/OpenHands/software-agent-sdk), [v1.23.1 release notes](https://github.com/OpenHands/software-agent-sdk/releases/tag/v1.23.1)). The older `OpenHands/OpenHands` V0 runtime remains useful only as migration evidence; OpenHands itself says the old asynchronous `EventStream` was confusing, caused thread/async problems, and had weak ordering guarantees ([Path to OpenHands v1](https://www.openhands.dev/blog/the-path-to-openhands-v1)).

The teardown result is not “import OpenHands.” Most of its attractive surfaces have converged on capabilities Claude Code already provides: AgentSkills, `AGENTS.md`, hooks, MCP, plugins, file-based agents, scoped tool/permission sets, conversation forks, compaction, background/parallel agents, and sandbox profiles. Importing the SDK or Agent Server would create the explicitly rejected second orchestration runtime.

The parts worth porting are smaller:

1. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** copy OpenHands’ action-boundary discrimination principle into one shared guard library: shell threat patterns inspect executable fields/segments, while prompt-injection patterns may inspect text fields. This directly addresses live defect D1, where four local detectors confuse prose or JSON field names with executable behavior (`INPUT-known-harness-defects.md`, D1–D1b).
2. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** complete the existing event spine with causal identifiers and durable hook-execution facts. OpenHands has event IDs, timestamps, sources, action/observation linkage, rejection source, and persistent hook execution events; the local normalized `HookEvent` has session/turn/tool fields but no timestamp, parent/action correlation, or origin enum (`C:\Users\Prekzursil\.agents\harness\models.py:26-39`), while `terminal.jsonl` drops even session/turn/tool identity (`dispatcher.py:485-507`). This is the strongest genuine architectural gap.
3. **BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus):** ledger the resolved plugin source/version/hash at session start and check it on resume. OpenHands persists resolved plugin sources so a resumed conversation can reuse the same extension version; the local plugin cache demonstrably contains versioned manifests, but a validated broad search of the shared harness found no plugin provenance/hash/ref field. This would turn the current orphan/plugin ambiguity into attributable state without deleting anything.
4. **NATIVE (Claude Code already does this; we just enable it):** stop granting every session full-host, no-confirmation access. The live defaults are `approval_policy = "never"` and `sandbox_mode = "danger-full-access"` (`C:\Users\Prekzursil\.codex\config.toml:6-7`) plus Claude `defaultMode: bypassPermissions`, empty `ask`, and both `C:` and `D:` as additional directories (`C:\Users\Prekzursil\.claude\settings.json:26-75`). OpenHands’ strongest lesson is to make isolation and risk-based confirmation the normal profile, but Claude Code already exposes native permission modes, per-agent permission settings, scoped MCP, hooks, and isolation ([Claude subagents](https://code.claude.com/docs/en/sub-agents), [Claude permissions](https://code.claude.com/docs/en/permissions)).

These four moves are **very likely (80-90%)** to capture nearly all useful OpenHands-specific value for this owner: evidence is the direct feature-to-local-surface mapping above, the current OpenHands/Claude primary documentation, and the anti-overfit rule that additions must ride the existing bus. The residual uncertainty is whether provider hook payloads expose every causal identifier needed; that premise is **UNVERIFIED — dump one real Claude and one real Codex hook payload for the same tool call and compare fields** before finalizing the causal schema.

## 1. Agent loop

### What OpenHands actually does

The V1 `Agent` is a stateless configuration object operating on a mutable `ConversationState`. One `step()` performs one bounded reasoning cycle: process pending confirmed actions; obtain a condensed event view; call the LLM; parse text or one/more tool calls into events; pause if confirmation is required; execute permitted actions; append observations; and return control to the conversation loop. Each step is intended to be interruptible and resumable ([Agent architecture](https://docs.openhands.dev/sdk/arch/agent), [Agent API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.agent), [Conversation architecture](https://docs.openhands.dev/sdk/arch/conversation)).

The loop has explicit lifecycle states (`idle`, `running`, `paused`, `waiting_for_confirmation`, `finished`, `error`, `stuck`) and a maximum-iteration bound. `Conversation.run()` repeats steps until a terminal state and can pause between steps; pending actions survive confirmation boundaries. The state implementation reconstructs unmatched actions by matching `ActionEvent.id`/`tool_call_id` against observations, rejection events, and errors ([conversation state source](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py)).

Multiple tool calls emitted in one LLM response are grouped by a shared `llm_response_id`. By default they execute sequentially (`tool_concurrency_limit=1`); increasing the limit uses a parallel executor. OpenHands calls this experimental and warns about shared-state races, ordering dependencies, deadlocks, and resource exhaustion ([Parallel Tool Execution](https://docs.openhands.dev/sdk/guides/parallel-tool-execution), [agent source](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/agent/agent.py)).

### Comparison

Claude Code and Codex already own their reasoning/action loops, retry behavior, interruption, compaction, and tool scheduling. The shared harness deliberately observes and constrains those loops through hooks. Using the OpenHands SDK as their controller would, by construction, add a Python orchestration runtime between the model and its native tools.

OpenHands’ maximum-iteration concept is not missing natively: current Claude agent definitions support `maxTurns`, background mode, effort, isolation, permission mode, skills, tools, hooks, and MCP servers ([Claude subagent schema](https://code.claude.com/docs/en/sub-agents)). Existing local agent files commonly specify `tools` and `model` (for example `C:\Users\Prekzursil\.claude\agents\architect.md:2-5`) but do not systematically use `maxTurns`, `permissionMode`, `isolation`, scoped `mcpServers`, or component-scoped `hooks`.

**Proposal — NATIVE (Claude Code already does this; we just enable it):** add explicit `maxTurns` and restricted `permissionMode`/`isolation` to autonomous or high-risk agent definitions, leaving ordinary interactive agents unconstrained unless evidence warrants a limit. This is **very likely (80-90%)** to reduce runaway cost/blast radius because OpenHands’ bounded loop and Claude’s native fields are both explicit, and the local corpus has real retry loops (`corpus/corpus.json`, `/retry_loops`). The appropriate numeric limits are **UNVERIFIED — replay a fixed local task set with 25/50/unbounded turns and compare completion, cost, and forced-stop rate**.

**Capability OpenHands has but we should not port — BUILD-LARGE (new daemon/service/runtime -- needs its own justification):** a user-configurable same-response tool scheduler with nested per-agent numeric concurrency. Implementing that below the provider loop would require owning dispatch or wrapping every tool, which is a second runtime. Native providers already parallelize independent calls and agents. OpenHands itself labels the feature experimental. A new scheduler is **unlikely (20-45%)** to beat native scheduling on this owner’s mixed Windows workloads; evidence is the documented race/deadlock/resource risks and the anti-overfit control, while no local same-model latency ablation exists. The experiment that could reverse this decision is a read-only I/O benchmark comparing native parallel calls against OpenHands at concurrency 1/4/8 with identical model, tools, and task.

### Worse than ours / do not copy

- Do not copy the V0 `EventStream`. OpenHands’ own migration account rejects it for confusing concurrency and weak ordering. The local dispatcher is synchronous and deterministic in module order, with a security block terminal at `C:\Users\Prekzursil\.agents\harness\dispatcher.py:267-302`.
- Do not place the provider behind OpenHands’ ACP agent merely to regain Claude/Codex. ACP is useful for an application embedding external agent servers ([ACP Agent](https://docs.openhands.dev/sdk/guides/agent-acp)); for this owner it would be provider → OpenHands → provider indirection with no missing outcome.

## 2. Context management

### OpenHands mechanisms

OpenHands stores the full event history and derives an LLM-facing `View`. A `Condensation` event names `forgotten_event_ids`, carries a summary, and specifies the insertion offset; the historical events remain in the event log while the view filters them. The rolling pattern preserves a head (system/initial instructions), preserves a recent tail, and summarizes the middle. `LLMSummarizingCondenser` is pluggable and can be forced through `Conversation.condense()` ([Condenser architecture](https://docs.openhands.dev/sdk/arch/condenser), [Context Condenser guide](https://docs.openhands.dev/sdk/guides/context-condenser)).

OpenHands also separates a cacheable static system prompt from per-conversation dynamic context (repository information, skills, runtime/workspace, secrets/settings, conversation instructions), allowing cross-conversation prompt caching without baking dynamic material into the cached prefix ([Agent API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.agent)). Skills follow progressive disclosure: the system prompt lists name/description/location and the agent reads full `SKILL.md` only when needed; keyword triggers may additionally auto-inject full content ([Agent Skills & Context](https://docs.openhands.dev/sdk/guides/skill)).

### Comparison

The owner already has native compaction, explicit goal re-injection, compaction checkpoints, on-demand AgentSkills, and semantic memory recall. The shared recall module injects a bounded lexical result set, suppresses duplicate permalinks, ranks by relevance/recency/importance, and marks contradiction heads (`C:\Users\Prekzursil\.agents\harness\modules.py:1608-1710`). OpenHands’ condenser is more explicit about which event IDs were elided; the local hook/event spine is more explicit about cross-session semantic recall and supersession.

OpenHands product documentation explicitly says previous sessions are not semantically remembered and recommends `AGENTS.md` as the workaround ([When to Use OpenHands](https://docs.openhands.dev/openhands/usage/essential-guidelines/when-to-use-openhands)). The owner’s canonical basic-memory store is therefore materially stronger for durable cross-project recall (`C:\Users\Prekzursil\.claude\AGENTS.md:85-91`).

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus), UNVERIFIED provider-field premise:** when provider compaction/resume signals are available, record a `compaction` event containing provider, pre/post context identifiers, checkpoint permalink, and explicit supersession relation. Do not build a condenser. This is **likely (55-80%)** to improve post-compaction auditability because OpenHands demonstrates that condensation provenance can coexist with an immutable log, and the local ledger already has event IDs. Provider availability of pre/post context identifiers is **UNVERIFIED — capture SessionStart(compact/resume) payloads from Claude and Codex plus the immediately preceding Stop payload**; if the fields are absent, retain the existing checkpoint only and do not synthesize IDs.

### Worse than ours / do not copy

- Do not make an auxiliary LLM summarizer the canonical memory. Summaries are lossy and can preserve the wrong detail. Keep raw provider transcripts/event facts plus basic-memory notes as the authoritative split.
- OpenHands documents “up to 2x” per-turn cost reduction and equivalent-or-better task performance for its condenser, but that vendor claim is **UNVERIFIED for this owner — run identical long local sessions with native compaction versus an OpenHands condenser and measure task correctness, retained facts, latency, and total tokens**. It is not a reason to add a second summarizer.
- Do not copy dynamic shell execution embedded in skill Markdown (`!`command``). OpenHands warns it executes with full shell privileges and only trusted skills are safe ([Agent Skills & Context](https://docs.openhands.dev/sdk/guides/skill)). Claude supports dynamic skill context natively, but the owner’s security model should keep executable behavior on explicit hook/tool buses. A synced global skill catalog plus implicit subprocess rendering is a supply-chain escalation.

## 3. Memory, persistence, and replay

### OpenHands mechanisms

With `persistence_dir`, OpenHands immediately autosaves public conversation-state mutations to `base_state.json` and appends each event as a separate file. Persisted state includes message/events, agent configuration, execution status/iteration/stuck settings, tool outputs, token/cost statistics, workspace context, activated skills, secrets, and custom `agent_state`. Restore verifies conversation ID plus agent class/tool compatibility; secrets are encrypted if a cipher is supplied, otherwise redacted and lost ([Persistence guide](https://docs.openhands.dev/sdk/guides/convo-persistence), [conversation state source](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py)).

`Conversation.fork()` deep-copies events and agent state under a new ID while leaving the source event history unchanged. It can swap the agent/model/tools and normally resets metrics, making forks suitable for A/B exploration ([Fork a Conversation](https://docs.openhands.dev/sdk/guides/convo-fork)).

This is trajectory memory, not semantic long-term memory. The public `agent-memory` extension writes repository knowledge into `AGENTS.md` ([OpenHands extensions registry](https://github.com/OpenHands/extensions)); it is not a cross-project semantic store with supersession semantics.

### Comparison

Claude already has session resume and `/fork`; its local changelog records conversation-copy semantics and later pointer-based hydration (`C:\Users\Prekzursil\.claude\cache\changelog.md:55,1908`). The shared append-only ledger records redacted event facts and typed receipts (`C:\Users\Prekzursil\.agents\harness\ledger.py:468-490,841-879`), while basic-memory handles durable semantics. We should not replace this two-store model with OpenHands’ per-conversation JSON files.

OpenHands does have a cleaner typed model for pending actions and crash recovery than the visible shared harness. Absence from provider internals is **UNVERIFIED — interrupt a disposable Claude and Codex session after an action is emitted but before its observation, resume, and inspect whether either repeats or reconciles the action**. Until that experiment, no new durable execution layer is justified.

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): plugin-resolution receipt.** At SessionStart, enumerate only active plugin components, record `{plugin_name, source, resolved_version/ref/hash, component paths}` as one redacted ledger event, and on resume emit a non-blocking warning if the resolved set changed. This is **very likely (80-90%)** to improve reproducibility because OpenHands persists `resolved_plugins` for exact resume behavior ([Conversation API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.conversation)), the local plugin cache is versioned, and the measured orphan condition proves “path exists” does not identify the intended live version. Keep it advisory: a changed plugin may be an intentional update.

### Worse than ours / do not copy

- `AGENTS.md` as a memory database scales poorly and pollutes every prompt. The owner explicitly caps always-on instruction files and routes durable knowledge to basic-memory.
- One JSON file per event is easy to inspect but can produce filesystem overhead at this owner’s scale. The current local corpus already covers 1,564,084 transcript lines and 11,633 files; no evidence shows that adding another trajectory copy improves recovery.
- OpenHands base state is overwritten on every public-field mutation. Its source raises on autosave failure. That is reasonable for an SDK owning state. Copying this into a provider hook is **likely (55-80%)** to make an advisory harness interfere with the native loop because a persistence exception would cross the hook boundary; keep hook telemetry append-only/fail-open.

## 4. Tools and MCP

### OpenHands mechanisms

Native tools are a typed quadruple: `Action` schema, `Observation` schema, executor, and `ToolDefinition`. This supports input validation, formatted results, reusable/shared executors, and programmatic registration ([Custom Tools](https://docs.openhands.dev/sdk/guides/custom-tools), [Tool System](https://docs.openhands.dev/sdk/arch/tool-system)).

MCP servers are configured on an agent. The client discovers tools, converts MCP JSON schemas to dynamic Pydantic action types, presents MCP and native tools uniformly, bridges async MCP calls into the synchronous loop, pools connections, applies timeouts, and cleans up servers with conversation lifecycle. MCP annotations such as read-only/destructive feed security analysis. OAuth remote servers and regex tool filtering are supported ([MCP guide](https://docs.openhands.dev/sdk/guides/mcp), [MCP architecture](https://docs.openhands.dev/sdk/arch/mcp)). File-based agents may embed MCP server definitions with environment-variable references; plugins may bundle `.mcp.json` ([File-Based Agents](https://docs.openhands.dev/sdk/guides/agent-file-based), [Plugins](https://docs.openhands.dev/sdk/guides/plugins)).

### Comparison

Claude Code already supports subagent-scoped inline MCP definitions, references to parent connections, automatic connect/disconnect, per-agent tool allow/deny lists, hooks, and permission modes ([Claude subagents](https://code.claude.com/docs/en/sub-agents)). Plugins already bundle agents, skills, hooks, MCP and other components ([Claude plugins](https://code.claude.com/docs/en/plugins)). Codex also has native MCP configuration. The correct move is to use those buses, not port OpenHands’ FastMCP client.

This matters empirically. The corpus records 93 MCP servers touched, but `mcp__claude_ai_Tavily__tavily_extract` made 532 calls with 137 errors (25.75%), including the measured dead “not connected” fingerprint (`corpus/corpus.json`, `/tool_usage` and `/failures_by_tool`). A globally advertised dead server is a selection failure. OpenHands’ per-agent/server scoping suggests the right remedy, and Claude already implements it.

**Proposal — NATIVE (Claude Code already does this; we just enable it):** move specialized MCP servers from the global catalog into the few agent/plugin definitions that need them; keep only reliable, broadly useful servers in the parent session. Configure read-only agents with read-only tools/MCPs. This is **very likely (80-90%)** to reduce dead-tool selection and prompt-schema load because the corpus shows a repeatedly selected dead endpoint and Claude documents that inline subagent MCP tools are absent from the parent context. Exact token savings are **UNVERIFIED — compare system/tool-schema token counts and selection errors across ten matched runs before and after scoping**.

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus), UNVERIFIED provider-field premise:** feed MCP annotations into the shared action discriminator only if the provider payload exposes them. This premise is **UNVERIFIED — call one known read-only and one known destructive annotated MCP tool and dump both PreToolUse payloads**. If annotations are present, treat them as one independent signal, never as sole authority; if absent, omit the feature rather than add another MCP client.

### Worse than ours / do not copy

- An SDK-side dynamic schema adapter cannot fix over-strict upstream tool schemas. The corpus’s `StructuredOutput` failure rate is 22.9%, including 294 schema mismatches. Adding another Pydantic conversion layer is **likely (55-80%)** to increase rather than reduce schema impedance; the evidence is the measured schema-mismatch class and the extra conversion boundary, while no same-schema local ablation exists.
- OpenHands direct `Conversation.execute_tool()` explicitly bypasses the normal confirmation policy and security analyzer; callers must protect it themselves ([Conversation API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.conversation)). The owner’s harness should not create an equivalent bypass.
- Do not auto-clone/update the entire public skill registry at session start. The owner already has ~355 installed skills but only 78 observed invocations; automatic catalog expansion without evaluation increases selection surface and plugin debris.

## 5. Permission model and sandboxing

### OpenHands mechanisms

OpenHands separates risk classification from confirmation policy:

- risk levels: LOW, MEDIUM, HIGH, UNKNOWN;
- policies: `AlwaysConfirm`, `NeverConfirm`, and thresholded `ConfirmRisky` (default threshold HIGH, confirm UNKNOWN by default);
- analyzers: LLM-supplied risk, no-op, deterministic pattern/rule analyzers, and ensembles;
- action events and rejection observations preserve the audit trail ([Security architecture](https://docs.openhands.dev/sdk/arch/security), [Security guide](https://docs.openhands.dev/sdk/guides/security), [event API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.event)).

The newest security guide is unusually relevant to live defect D1. Its deterministic `PatternSecurityAnalyzer` scans shell threat patterns only in executable fields while injection patterns scan all fields. `PolicyRailSecurityAnalyzer` evaluates composed threats within the same field/segment. The guide explicitly states limitations: classification is not hard deny by itself, direct tool execution bypasses it, the parser is incomplete, and the analyzers do not replace sandboxing.

Execution can use a local workspace or remote Agent Server. OpenHands recommends isolated Docker/Kubernetes workspaces for arbitrary code; the Agent Server manages per-conversation workspaces and production deployments can impose CPU/memory/storage limits ([Runtime Architecture](https://docs.openhands.dev/openhands/usage/architecture/runtime), [Agent Server](https://docs.openhands.dev/sdk/arch/agent-server), [resource limits](https://docs.openhands.dev/enterprise/k8s-install/resource-limits)). OpenHands also warns that mounted files, credentials, and egress remain exposed to the agent ([FAQ](https://docs.openhands.dev/overview/faqs)).

### Comparison and port

The local defaults are substantially less safe than either product’s recommended posture: Claude bypasses prompts and exposes both drives; Codex uses danger-full-access/no approvals. Local deny rules protect `.env`, PEM, and credential-like reads (`C:\Users\Prekzursil\.claude\settings.json:64-75`), and hooks can block irreversible commands, but D1 proves the current detectors classify strings without semantic role.

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus): shared `classify_occurrence(payload, context)` discriminator.** Parse the hook event first. For command guards, inspect the actual tool name and executable argument fields only; split shell commands into bounded segments using an existing safe parser where available; require composed threat tokens in the same segment; separately scan untrusted text fields only for injection indicators; preserve negation/code-fence/source-file context for prose scanners; return typed evidence `{field, segment, rule, confidence}`. Route all destructive-command, stub/marker, and tool-result sentinel checks through it. Test the nine recorded false fires plus known-positive executable/source fixtures. This is **almost certain (90-99%)** to eliminate the documented use-vs-mention false-positive class because the defect report supplies repeated false fixtures across four independent detectors and OpenHands implements the same executable-field distinction. It is not 100% because the exact hook input schemas are **UNVERIFIED — dump each implicated hook payload before implementation**.

**Proposal — NATIVE (Claude Code already does this; we just enable it):** make a restricted/sandboxed profile the default for untrusted repositories and autonomous agents; require an explicit trusted profile for full drive access. Use per-agent `permissionMode`, `isolation`, `tools`/`disallowedTools`, and scoped MCP. This is **almost certain (90-99%)** to reduce blast radius because current settings explicitly grant full-host access and both vendors document native isolation/permission mechanisms. Workflow friction is **UNVERIFIED — run a harmless canary suite under restricted and trusted profiles, measuring prompts, blocked legitimate operations, and escape attempts**.

**Capability OpenHands has but we should not port — BUILD-LARGE (new daemon/service/runtime -- needs its own justification):** a local Docker/Kubernetes Agent Server solely to wrap Claude/Codex. This reintroduces a second orchestration runtime and durable execution service. It is **unlikely (20-45%)** to outperform native restricted profiles for this single-owner Windows harness because setup, path translation, mounts, image lifecycle, and network policy add failure surfaces, while the desired isolation is already native. A container remains appropriate for benchmark fixtures or explicitly hostile repositories, but that is an execution environment selected by the task, not the harness control plane.

### Worse than ours / do not copy

- OpenHands’ LLM security analyzer can ask the same model to label its own action, or use another LLM. Model judgment is manipulable and adds latency/cost. Deterministic boundary rules plus native confirmation are preferable.
- `ConfirmRisky` is a confirmation policy, not a deny policy. Critical local non-negotiables should remain deterministic hard blocks.
- OpenHands’ default CLI local-workspace option trades away the Docker isolation its product historically advertised. “OpenHands is sandboxed” is configuration-dependent, not an invariant.

## 6. Customization: rules, skills, hooks, plugins

### OpenHands surface

- Permanent repo context: root `AGENTS.md` (plus model-specific `CLAUDE.md`/`GEMINI.md`).
- AgentSkills: standard `SKILL.md` directories with scripts/references/assets; descriptions are listed, full bodies are invoked progressively. OpenHands adds optional keyword triggers.
- Hooks: `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SessionStart`, `SessionEnd`; exit 2 blocks where supported; structured output can deny or inject context; async hooks cannot block. Hook execution events appear in the conversation log.

## 7. Multi-agent support

### OpenHands mechanisms

OpenHands registers programmatic or file-based agent factories in a global delegation registry. A parent equipped with `DelegateTool` or `TaskToolSet` selects an agent by name, supplies a task, starts a sub-conversation, and receives the result. Built-ins include general-purpose, read-only code explorer, bash runner, and web researcher. Agents may inherit or override model, tools, MCP, hooks, and permission mode. Registration precedence is programmatic → plugin → project files → user files ([File-Based Agents](https://docs.openhands.dev/sdk/guides/agent-file-based), [Sub-Agent Delegation](https://docs.openhands.dev/sdk/guides/agent-delegation), [Task Tool Set](https://docs.openhands.dev/sdk/guides/task-tool-set)).

Parallel delegation is implemented as parallel tool calls; the main agent and each subagent may have separate concurrency limits. A visualizer can create sub-visualizers and persisted events prove which actions shared an LLM response ([Parallel Tool Execution](https://docs.openhands.dev/sdk/guides/parallel-tool-execution)).

### Comparison

The corpus records 1,745 `Agent` calls at 1.15% error and 22 invoked agent types (`corpus/corpus.json`, `/tool_usage` and `/capability_use/agents_invoked`). The local lifecycle module injects structured handoff guidance, rejects hollow output, warns on stalled transcripts, and keeps each subagent anchored to its spawn objective (`C:\Users\Prekzursil\.agents\harness\modules.py:2331-2417`). The shared contract prohibits forwarding raw subagent output (`C:\Users\Prekzursil\.claude\AGENTS.md:59-62`). Those governance features are stronger than the base OpenHands delegation mechanism.

Claude Code also supports agent teams with independent sessions and peer messaging, while its ordinary subagents return summaries and cannot recursively spawn ordinary subagents ([Claude feature overview](https://code.claude.com/docs/en/features-overview), [Claude subagents](https://code.claude.com/docs/en/sub-agents)). OpenHands documentation shows two-level execution parallelism, but does not establish unbounded recursive delegation. Any claim that OpenHands is categorically “more multi-agent” is therefore **almost certainly not (1-5%)** supported; evidence is feature parity plus the lack of a documented comparative limit.

**Proposal — NATIVE (Claude Code already does this; we just enable it):** use native parallel agents only for independent, bounded units and keep the shared structured handoff/stall checks. This is **very likely (80-90%)** to preserve the useful throughput without adding a registry/runtime, based on measured local agent reliability and existing lifecycle code.

### Worse than ours / do not copy

- A global first-registration-wins agent registry creates hidden precedence and process-global state. File/plugin resolution should be explicit and receipted.
- Delegated agents share a workspace unless separately isolated. Parallel writes can race. OpenHands warns similarly for parallel tools; the owner’s current structured handoff alone does not prevent file races, so use worktrees or disjoint write scopes where native isolation supports it.
- Do not make multi-agent the default. The anti-overfit control remains a single native agent. OpenHands’ own V1 loop is deliberately simple; parallelism is experimental and workload-dependent.

## 8. Verification and self-check mechanisms

### OpenHands mechanisms

1. **Stuck detector (default on):** detects four repeated action/observation cycles, three repeated action/error cycles, three-message monologues, six alternating A/B cycles, and repeated context-window errors; it marks the conversation stuck and halts ([Stuck Detector](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)).
2. **Stop hooks:** a hook can deny finish and inject the missing completion requirement ([Hooks](https://docs.openhands.dev/sdk/guides/hooks)).
3. **Finish semantics:** default agents include an explicit finish tool; tool calls following finish in the same batch are discarded in current source ([agent source](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/agent/agent.py)).
4. **Experimental critic:** an API-based critic can score a completed task and automatically ask the agent to refine until a threshold is met ([Critic](https://docs.openhands.dev/sdk/guides/critic)).
5. **Events/metrics/tracing:** immutable events, token/cost statistics, callbacks, and optional OpenTelemetry/Laminar traces support after-the-fact analysis ([Events](https://docs.openhands.dev/sdk/arch/events), [Observability](https://docs.openhands.dev/sdk/guides/observability)).

### Comparison

The local harness already detects exact repetition and A-B-A-B cycles (`C:\Users\Prekzursil\.agents\harness\modules.py:1848-1905`). More importantly, it mints typed verification receipts from command/results, checks receipt freshness after mutations, ties “fixed” to a green rerun of the exact failing argv fingerprint, and injects a receipt gate for completion claims (`ledger.py:137-159,383-425,1093-1132`; `modules.py:2048-2225`). `/eval` already distinguishes pass@1 and pass@3 (`C:\Users\Prekzursil\.claude\commands\eval.md:30,74-87`). OpenHands’ base SDK does not provide this objective claim-to-receipt discipline.

**Proposal — CONFIG (settings/JSON only):** align repeat thresholds and terminal result markers across the existing local modules; do not add OpenHands’ detector as another scanner. OpenHands’ thresholds provide a useful external comparator, but local measured failures should determine final numbers. This is **likely (55-80%)** to simplify behavior without losing protection because both implementations cover exact and alternating loops, while the local detector also has tool-result memoization and typed receipts. The best thresholds are **UNVERIFIED — replay the corpus’s labeled retry-loop samples and plot false-stop versus wasted-call curves**.

**Proposal — BUILD-SMALL (<~200 lines, rides the existing hook/skill/MCP bus), UNVERIFIED premise:** join cost/token/latency fields to typed receipts and subagent lifecycle events if native hook payloads expose them. OpenHands aggregates multi-LLM statistics; the local harness search found no accumulated-cost/input/output-token fields, although provider status lines expose some usage. This is **likely (55-80%)** to improve ablation decisions because cost and wall time are required to judge whether scaffolding earns its keep. **UNVERIFIED — capture native hook payloads and status-line JSON, then prove a known token/cost field can be joined to a known tool event**; if no stable field exists, report the gap rather than scrape UI text.

### Worse than ours / do not copy

- **Reject the experimental critic.** It is exactly the previously rejected trained/hosted critic component. It depends on OpenHands’ provider in the documented form, adds another model judgment, and can generate self-reinforcing refinement loops. Deterministic tests and receipts are more falsifiable.
- **Reject observability SaaS as a harness dependency.** OpenHands’ OTEL support is useful for production applications, but this owner already has local transcripts and an append-only ledger. Port the missing causal fields, not Laminar/Honeycomb/Datadog.
- Stop hooks are only as sound as their detector. Local D1 shows that a finish gate that scans prose naively can block correct work and even flag its own bug report. Fix semantic discrimination before adding more completion checks.

## Anti-overfit gate

Every adopted item rides an existing bus:

- semantic discriminator → existing PreToolUse/PostToolUse/Stop modules;
- causal telemetry → existing `HookEvent`/`EventLedger`/terminal record;
- plugin receipt → existing SessionStart + ledger;
- restricted profiles and per-agent scoping → native Claude/Codex configuration;
- threshold tuning → existing repeat/cycle modules and `/eval`.

The rejected OpenHands elements are precisely the components the anti-overfit contract warns against: a second orchestration runtime (SDK/Agent Server), durable-execution service, hosted/trained critic, and observability SaaS. OpenHands is valuable here as a source of small mechanisms and negative architectural evidence, not as a replacement runtime.
