# search-hub — design & research rationale (2026-07-07)

**Why:** the search MCPs (exa/tavily/firecrawl) were single-key; when exa hit its credit limit mid-session there was no way to see remaining balance or fail over to a backup key. `search-hub` adds multi-key storage, labels, on-demand usage lookup, and reactive auto-rotation — reusing the cloud-hub `_shared/accounts.py` machinery.

## Grill decisions (grill-me-extensive)
- **SG-1 — architecture: front the official MCPs + lazy-spawn.** Keep the official exa/tavily/firecrawl tool surfaces verbatim (no reimplementation/drift); route each `tools/call` to a warm per-key child; **lazy-spawn** a backup key's child only when the primary cools, so RAM stays ~1 child/provider. (Alternatives rejected: a standalone REST hub — minimal RAM but reimplements ~30 tools and drifts; a full hybrid — two mechanisms.)
- **SG-2 — detection: reactive + on-demand usage tool.** Auto-rotate the moment a key returns its exhaustion error (402 / `NO_MORE_CREDITS`) — uniform incl. exa; plus a `search_usage` tool that reports remaining credits + label when asked. No background probing.
- **SG-3 — backup keys: paid/legitimate multi-key.** Cooldown a truly-exhausted key until the next UTC billing-period boundary; a rate-limit (429) never cools the key. (Free-tier multi-accounting to dodge limits is a ToS-risk and is *not* the design intent.)

## Provider facts (verified live 2026-07)
| Provider | Usage query | Exhaustion signal | Rotation strategy |
|---|---|---|---|
| **Firecrawl** | `GET /v2/team/credit-usage` (same key) → `remainingCredits` | **402** "insufficient credits" | reactive on 402; 429 = rate (no rotate) |
| **Tavily** | `GET /usage` (same key) → `plan_limit - plan_usage (+paygo)` | ambiguous — **429** may be rate *or* quota | on 429, probe `/usage`: no headroom ⇒ rotate; else back off |
| **Exa** | **no balance API** (usage lives on a separate admin host, needs a different service key, returns spend-USD) | **402** `NO_MORE_CREDITS` / `API_KEY_BUDGET_EXCEEDED` | **error-driven only**; 429 = pure rate (never rotate) |

## Architecture
A cloud-hub-style lazy stdio multiplexer (`hub.py`) fronting the **stdio** variants of the three MCPs (exa `exa-mcp-server`, tavily `tavily-mcp`, firecrawl `firecrawl-mcp`). `providers.py` holds the per-provider spec + error classifier; `usage.py` does the stdlib-urllib usage lookups; `rotation.py` owns per-key health (`cooldown_until`), `pick_active` (round-robin skipping cooled keys), and the per-call **rotate-retry-once** wrapper. Multi-key storage + the six `ex_`/`tv_`/`fc_` `*_account_*` tools (list/current/add/remove/switch/cycle) reuse `_shared/accounts.py`; the one additive shared helper is `AccountStore.env_for(platform, name)` (read-only named-key resolver). Rotation is **per-invocation** (route/retry a call), never a shared-child respawn — concurrency-safe. **52 tools exposed** (33 provider passthrough + 18 account + 1 `search_usage`).

## Live migration (user-approved)
Replace the three standalone `exa`/`tavily`/`firecrawl` entries in `~/.mcp.json` with the single `search-hub` entry from `canonical-mcp-servers.json` (stdio → `search-hub/hub.py`, env `EXA_API_KEY(+_2)`, `TAVILY_API_KEY(+_2)`, `FIRECRAWL_API_KEY(+_2)` as `${ENV}`), export any real backup keys, then `/mcp reconnect`. Tool names are unchanged so existing skills keep working; `search_usage` is additive. **Paid keys only.**
