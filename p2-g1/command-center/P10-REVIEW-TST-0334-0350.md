I extracted the tar member rather than reasoning about tar's layout:

| measurement | value |
|---|---|
| container bytes | 10,240 |
| container CRLF | 100 |
| **payload bytes (extracted)** | **3,837** |
| **payload CRLF (extracted)** | **100** |
| CRLF *outside* the payload | **0** |

So the receipt's claim — *"git archive's payload also carries 100 CRLF"* — is **CONFIRMED**, and the
payload matches the working tree (3,837/100) exactly. You are not inferring from padding: tar headers
are NUL-padded ASCII and the pad blocks are NUL, so no `\r\n` can originate outside the member. The
inference is **sound as measured**. Confidence **almost certain (90-99%)**.

Three problems remain:

1. **`blobread.py:112-113` is FALSE.** The comment says *"locate the member payload by tar's 512-byte
   header blocks"*. The code does no such thing — line 114 stores `archive.stdout` whole. A false
   comment in a module whose thesis is "verify the right bytes" is the same class the module indicts.
2. **The soundness is unasserted and format-dependent.** Measured: `--format=tar.gz` → **0 CRLF**,
   `--format=zip` → **0 CRLF**. If the format ever changes, the CRLF reading silently **inverts** to
   "git archive is LF-clean" — a false negative in the exact gate meant to catch this class. Since I
   extracted the member in four lines with stdlib `tarfile`, implementing what the comment already
   promises removes the fragility outright.
3. **`git_archive_tar_bytes` is excluded from the LF-normalisation control** (`blobread.py:128`), so
   the one route the module exists to indict is the only route with no content control.

Nit, not blocking: the second "verifier" probe for that claim greps `rules/common/windows-shell.md`,
which is the document those numbers came from — corroboration by citation, not a mechanically
independent re-measurement (`single-signal-verification.md` §2). My tar extraction now supplies a
genuine second signal, so the claim stands.
