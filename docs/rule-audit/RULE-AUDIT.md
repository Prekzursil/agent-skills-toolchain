## 1. Classification — every rule, always-on vs lazy (DoD item 1)

Measured by parsing frontmatter, not by assuming it. **254 rule files across three trees.** The
per-file table for all of them is in `RULE-AUDIT-TABLES.md` § "Full classification"; the totals:

| tree | root | files | always-on | fm-without-`paths` | lazy | always-on tok | lazy tok | all tok |
|---|---|---|---|---|---|---|---|---|
| repo | `rules/` | 88 | 8 | **0** | 80 | 17,107 | 46,187 | 63,294 |
| agent-self | `agent-self/config/rules/` | 78 | 4 | **0** | 74 | 1,201 | 36,807 | 38,008 |
| live | `~/.claude/rules/` | 88 | 8 | **0** | 80 | 15,141 | 39,285 | 54,426 |

**The always-on 8** (identical set in repo and live, all under `common/`): `agents.md`,
`bash-hud-and-terminal-emit.md`, `cross-vendor-dispatch.md`, `fan-out-contract.md`,
`harness-vcs-hygiene.md`, `single-signal-verification.md`, `stale-megapr-reconcile.md`,
`windows-shell.md`.

**agent-self's always-on 4** is a *different set*: `agents.md`, `git-workflow.md`, `hooks.md`,
`security.md`. Only `agents.md` overlaps. See §3.4.

**The third bucket is empty, and that is a measured result rather than an assumption.** The
classifier reports three buckets because "has frontmatter" and "has a `paths:` key" are different
predicates, and a file with frontmatter but no selector would load always-on while *looking*
scoped. Measured: **0 such files in all three trees**, so the binary no-frontmatter⇒always-on
shorthand is safe *on this tree today*. It is not safe as a general rule, and the classifier will
now surface the case the moment someone introduces one.

**Corroboration — two mechanically independent signals.** (A) measured frontmatter absence in
`~/.claude/rules/`; (B) this agent's own turn-0 system prompt, which lists exactly those 8 files
by absolute path and no others: 8/8, zero false positives across 88 candidates. Signal B is not a
re-run of A — it is the harness's own behaviour, read out of a different channel.

**Discriminating control (single-signal-verification rule 3c).** H1 "frontmatter presence gates
turn-0 injection" vs H2 "glob breadth gates it". `common/owner-ops-authorization.md` carries
`paths: ["**/*"]` — the broadest possible selector. Under H2 it would be at turn 0. It was **not**
in this agent's turn-0 context; it arrived only after a file was touched. The observation looks
different under the two hypotheses, so it is a real control, and H1 survives.

**The lazy half is CONFIRMED with a negative control that fires.** Mid-audit, after this lane read
two `.py` files, the harness injected 16 path-scoped user-level rules (11 `common/` + all 5
`python/`). `lazy_predict.py` scores the selector model against that observation:

```
candidate lazy rules in common/ + python/: 17
predicted injected: 16   observed injected: 16
negative control: PASS common/hooks.md selectors=['**/hooks/**','**/settings*.json','**/.claude/**'] predicted=False
SUCCESS:lazy_predict 16/16 injected reproduced, 1/1 withheld reproduced
```

17 candidates, 16 match a `.py` path, 16 injected; the one non-matching candidate was the one
withheld. That withholding is what separates "selectors are evaluated" from "everything loads
after the first touch" — without it the 16/16 would be unfalsifiable. This reproduces the
grounding lane's observation **in a different session**, which makes it a second signal for the
mechanism rather than a re-run of the first probe.

Confidence: **almost certain (90-99%)** for both clauses.

difference by one byte per line — the `windows-shell.md` §8b class. Any parity gate written for
§5.3 must normalise, or it will both understate deltas and manufacture phantom ones.
