## 2. agent-mail as the peer bus: registration, contact gating, leases

**Upstream state, checked 2026-09-02.**

- **[FACT, A, corroborated]** `Dicklesworthstone/mcp_agent_mail` describes itself as "Asynchronous coordination layer for AI coding agents: identities, inboxes, searchable threads, and advisory file leases over FastMCP + Git + SQLite"; supported agents "Claude Code, Codex CLI, Gemini CLI, GitHub Copilot CLI, any MCP client". Source: <https://github.com/Dicklesworthstone/mcp_agent_mail> (README), corroborated by `repo:skills/multi-ai-mingle/MCP_AGENT_MAIL.md` (author recorded 2021 stars, last push 2026-06-27, on 2026-07-11).
- **[FACT, A, corroborated by local doctrine]** The identity model is per-*program*: `register_agent(project_key, program, model, name?)`. `program` is free text (the estate uses the role there), `model` is free text. Nothing in the tool surface restricts `program` to a CLI - a value such as `program="hosted-model-adapter", model="Qwen3-Coder-480B@hf-router"` is legal. Source: `repo:skills/multi-ai-mingle/MCP_AGENT_MAIL.md` tool surface; README as above.
- **[FACT, A, local]** First contact is gated: `request_contact(from_agent, to_agent, registration_token)` then `respond_contact(to_agent, from_agent, accept=true, registration_token)`. Source: `repo:skills/multi-ai-mingle/SKILL.md` ("Real mcp_agent_mail API sequence, VERIFIED 2026-07-11").
- **[FACT, A, local]** Leases are **advisory**: `file_reservation_paths(... exclusive?, ttl_seconds?, reason?)`; nothing in the OS enforces them; `force_release_file_reservation` exists for stale holders. Source: `repo:skills/multi-ai-mingle/MCP_AGENT_MAIL.md`.
- **[FACT, B, UNVERIFIED this run]** A Rust rewrite `mcp_agent_mail_rust` (34 tools, TUI console) exists and was active on 2026-07-11; the estate decided to stay on the Python original. Source: `repo:skills/multi-ai-mingle/MCP_AGENT_MAIL.md` (recorded ~100 stars, pushed 2026-07-11). Not re-checked upstream in this run.

**[INFERENCE] What a hosted model needs to be a peer on this bus.** The bus is agent-agnostic by construction; the *only* thing missing for a hosted model is a long-lived local process that (1) holds one registration (codename + token) per hosted persona, (2) polls `fetch_inbox` (there is no push; `crcp/bus.py` polls), (3) turns each inbox message into a chat turn on the runtime (`/v1/chat/completions` with the profile's `tools`), (4) executes allowlisted tool calls locally, (5) replies with `reply_message` and takes/releases leases around any file it writes. That process is the adapter of section 6. It is a **client** of :8812 (owned port, unchanged), so it violates no lock.

**[INFERENCE] Contact gating is a feature, not friction, for hosted peers.** A hosted model that runs 24/7 on a Space could spam the inbox; the `request_contact`/`respond_contact` gate means the human's Claude or Codex session explicitly admits each hosted persona once. Keep it; do not auto-accept in the adapter.

**[RECOMMENDATION]** Register hosted personas with `program=<persona>` (e.g. `redteam-reporter`, `lit-learner`, `coder-worker`) and `model=<checkpoint@environment>` so `list_agents`/`whois` show at a glance which weights are behind a codename. Persist `(codename, token)` next to `.agents/local.json` by *name only* (the token is a secret; never in the repo), reusing `crcp/bus.py`'s sqlite read-only recovery when the tool result omits the token.

## 3. Codex `mcp-server` fan-out - and the fact that changes this section

**The fan-out rail's transport was deprecated on 2026-08-24.**

- **[FACT, A, corroborated]** OpenAI's Codex docs page "Running Codex as an MCP server" now opens: "`codex mcp-server` is deprecated. Use the Codex app server instead. To call Codex from Claude Code, use the Codex plugin for Claude Code, which uses the app server. This page documents the deprecated command for existing integrations." The deprecated server still lists two tools, `codex` (start; params `prompt`, `approval-policy` ∈ {`untrusted`,`on-request`,`never`}, `base-instructions`, `compact-prompt`, `config`, `cwd`, `developer-instructions`, `model`, `sandbox` ∈ {`read-only`,`workspace-write`,`danger-full-access`}) and `codex-reply` (`prompt`, `threadId`; `conversationId` deprecated alias). Sources: <https://learn.chatgpt.com/docs/mcp-server.md> (official mirror of developers.openai.com), <https://developers.openai.com/codex/cli/reference.md> ("`codex mcp-server` ... is deprecated. Use the Codex app server instead"), both read 2026-09-02; date of the change from <https://ccleaks.com/news/codex-mcp-server-deprecated-app-server-aug-2026> (tier C, "August 24") corroborated by a LinkedIn post dated 2026-08-26 <https://www.linkedin.com/posts/designly_openai-deprecated-codex-mcp-server-on-august-activity-7498439988993392640-OhVT> (tier C). No removal date is published.
- **[FACT, A, corroborated]** The replacement `codex app-server` speaks JSON-RPC 2.0 as JSONL over stdio by default (`codex app-server --listen stdio://`, alias `--stdio`), with `--listen ws://IP:PORT` (WebSocket, experimental) and `--listen unix:///absolute/path.sock`. Source: <https://learn.chatgpt.com/docs/developer-commands.md?surface=cli> (read 2026-09-02). The Claude Code plugin `openai/codex-plugin-cc` (`/plugin marketplace add openai/codex-plugin-cc`, `/plugin install codex@openai-codex`, `/codex:setup`) "delegates through the local Codex CLI and Codex app server ... same local auth, config, environment, and MCP setup ... not a separate runtime". Sources: <https://community.openai.com/t/introducing-codex-plugin-for-claude-code/1378186> (tier B, OpenAI staff post), <https://codex.danielvaughan.com/2026/04/18/codex-cli-claude-code-working-together/> (tier C, 2026-04-18).
- **[FACT, A]** Known defect in the deprecated path: `codex mcp-server` accepts `resources/list` / `resources/templates/list` and never replies, so any client that snapshots tools+resources together wedges until timeout. Source: <https://github.com/openai/codex/issues/6664> (maintainer-grade repro on codex-cli 0.114.0).

**[INFERENCE] Consequences for this estate.**
1. `CLAUDE.md` and `AGENTS.md` on main, and `multi-ai-mingle/SKILL.md` + `MOUNT.md` on live-capture, all describe the fan-out rail as "the official `codex mcp-server` mounted at user scope". That statement is now "a deprecated command kept for existing integrations". Nothing breaks today; the doc is stale and the migration target (app-server JSONL, or the `codex-plugin-cc` slash commands) is not the same shape: the plugin gives *slash commands*, not native tool calls a Claude subagent can invoke autonomously. The autonomous fan-out that `CODEX_FANOUT.md` depends on would need either the deprecated MCP surface (until removed) or a thin app-server client.
2. **Where a hosted model slots in.** The fan-out rail is command-and-control: orchestrator -> N worker threads -> push-watcher. A hosted model worker fits the *same* slot as a Codex thread if it is driven through a uniform protocol. That protocol should not be "one more bespoke MCP server per model" (rule 2 of `hosted-model-agents`), and it cannot be Codex's app-server (Codex-specific). The neutral candidate that already has an ecosystem is ACP (section 4): Codex itself is exposed as an ACP agent by Zed's `codex-acp`, Claude Code by `claude-code-acp`, so "N workers behind ACP" can mix Codex, Claude and a hosted model without the orchestrator caring.
3. The `CODEX_FANOUT.md` cap of 3 is a *Codex* cost (full MCP fleet + clone per thread). A hosted-model worker's per-process cost is a Python process with an HTTP client and a tool allowlist; its context window lives on the GPU box. **[INFERENCE, needs measurement]** several hosted workers should fit inside the RAM budget of one Codex thread; section 7 sizes this.

**[RECOMMENDATION]** Do not re-plumb the fan-out rail to the deprecated command in any new doc. Record the deprecation in `multi-ai-mingle` (a one-paragraph "as of 2026-08-24" note, no code change), keep the mounted server until OpenAI publishes a removal date (no feature removed for reliability - lock), and let the ACP adapter of section 6 be the *new* worker shape so Codex-vs-hosted becomes a per-worker choice.

## 4. ACP (Agent Client Protocol): v1 today, v2 draft, adapters

**Protocol state.**

- **[FACT, A, corroborated]** ACP v1 is stable; **v2 is published in Draft** ("various pieces can, and will, change before stabilization"). Version negotiation is unchanged: the client sends `protocolVersion: 2` in `initialize`; a v1-only agent answers `1` and the client decides. v2 changes that matter here: `session/prompt` becomes an acknowledgement and *all* output arrives as `session/update` notifications; `tool_call`+`tool_call_update` collapse into one upsert keyed by `toolCallId`; v1's client-side `fs/*` and `terminal/*` methods are **removed in favour of MCP**; `clientInfo`/`agentInfo` become one role-agnostic `info` so "agent-to-agent and other symmetric ACP connections do not need role-specific field names"; `session/new`'s `mcpServers` becomes optional; baseline lifecycle when `session` capability is present = `session/new`, `session/list`, `session/resume`, `session/close`, `session/prompt`, `session/cancel`, `session/update`; `_`-prefixed unknown enum variants are legal extensions. Sources: <https://agentclientprotocol.com/announcements/acp-v2-draft>, <https://agentclientprotocol.com/protocol/v2/migration>, <https://agentclientprotocol.com/rfds/v2/overview> (all read 2026-09-02; the migration page explicitly says "gate v2 support behind explicit version negotiation and feature flags until it stabilizes"). Secondary: <https://deepwiki.com/agentclientprotocol/agent-client-protocol/3-protocol-specification-v2-(draft)> (tier C).
- **[FACT, B, corroborated]** ACP is backed by Zed and JetBrains; Gemini CLI is the reference agent; the schema repo passed v0.11.0 on 2026-03-04. Clients: Zed, JetBrains, Neovim (CodeCompanion, avante), Emacs (agent-shell), Obsidian, **Toad** (Will McGugan's Python/Textual TUI), marimo. Source: <https://github.com/NousResearch/hermes-agent/issues/569> (tier C, community summary, read 2026-09-02) corroborated by <https://www.philschmid.de/acp-overview> (tier B).
- **[FACT, A/B, corroborated]** Agents already speaking ACP that are **installed on this box** (dedup-set #5): Claude Code via `@zed-industries/claude-agent-acp` (a.k.a. `claude-code-acp`), Codex via `npx @zed-industries/codex-acp`, Gemini CLI via `gemini --acp` (older: `--experimental-acp`), Goose via `goose acp`, OpenCode via `opencode acp`, GitHub Copilot via `copilot --acp`; roborev documents an `agy-acp` bridge for the `agy` CLI. Sources: <https://www.roborev.io/advanced/acp/> (tier B, table of wrappers + install commands), <https://github.com/NousResearch/hermes-agent/issues/569>, <https://agentclientprotocol.github.io/python-sdk/quickstart/> (Gemini `--acp` flag). Not re-verified per binary on the Windows box in this run (I have no access to it) -> **UNVERIFIED locally**.
- **[FACT, A]** Official **Python SDK** `agent-client-protocol` v0.12.1 on PyPI (Python >=3.10,<3.15; maintainers Chojan Shang, Frost Ming): generated Pydantic models tracking every ACP release, `acp.Agent` async base class, stdio JSON-RPC plumbing, `run_agent()`, `spawn_agent_process()` / `spawn_client_process()`, `acp.helpers` (`text_block`, `update_agent_message`, tool-call builders), `acp.contrib` (session accumulators, tool-call trackers, permission brokers), examples incl. `echo_agent.py`, `gemini.py`, `duet.py`. Sources: <https://pypi.org/project/agent-client-protocol/>, <https://agentclientprotocol.com/libraries/python>, <https://github.com/agentclientprotocol/python-sdk/blob/main/examples/echo_agent.py> (all read 2026-09-02). The echo agent is ~40 lines: `initialize` -> `new_session` -> `prompt` streaming `session_update`.
- **[FACT, B]** Third-party adapter toolkit `vcoderun/acpkit` (PyPI `acpkit`): `pydantic-acp` exposes a `pydantic_ai.Agent` as an ACP server (`run_acp(agent=Agent("openai:gpt-5"))`), supports model pickers (`AdapterModel(... override="openai:...")`), `FileSessionStore`, `NativeApprovalBridge`, slash-controls `/model`, `/thinking`, `/tools`, `/mcp-servers`; also the **inverse** (`create_acp_model` consumes an ACP agent as a model); `langchain-acp` targets LangChain/LangGraph; `acpremote` is a WebSocket transport to expose any ACP agent remotely; `codex-auth-helper` builds Codex-backed models from a local Codex login. Source: <https://github.com/vcoderun/acpkit>, <https://vcoderun.github.io/acpkit/pydantic-acp/>, <https://vcoderun.github.io/acpkit/pydantic-acp/adapter-config/> (read 2026-09-02).

**[INFERENCE] Lock check on the adapters.** `langchain-acp` is out (LangGraph lock). `pydantic-acp` drags in Pydantic AI v2 as an agent runtime - that is arguably "a second orchestration runtime" and definitely a new framework dependency; it buys a model picker and approval bridge we would otherwise write. The official SDK gives us the protocol with **zero** runtime opinions and lets the existing `hosted-model-agents/tool-loop.md` loop stay the loop. I rate the official SDK the lock-clean default and `pydantic-acp` a tradeoff row in the rubric, not a rejection (present tradeoffs, never remove options - lock).

**[INFERENCE] Why ACP is the right "agent shape" for a hosted model here.**
1. It is the one protocol under which Claude, Codex, Gemini, Goose and OpenCode on this box already present the same face (`initialize`/`session/new`/`session/prompt`/`session/update`). A hosted model behind the same face becomes interchangeable with them from any ACP client - Zed, Toad, or our own `spawn_agent_process` orchestrator.
2. v2's removal of `fs/*`/`terminal/*` in favour of MCP matches rule 3 of `hosted-model-agents` exactly ("the hosted model proposes; the harness executes"): the adapter passes the client's `mcpServers` (or its own allowlist) to the tool loop; nothing new is invented.
3. v2's symmetric `info` field is explicitly designed for **agent-to-agent** connections, i.e. an orchestrating agent can be an ACP *client* of N worker agents. That is the fan-out slot of section 3 without Codex's deprecated MCP surface.

**[RECOMMENDATION]** Implement v1 now (stable, every client speaks it), negotiate v2 behind a flag once the draft stabilises; the official Python SDK's generated models will carry both.

## 5. Parallel panes: dmux / Superset / tmux / Windows reality

- **[FACT, A]** **dmux** (`standardagents/dmux`, formerly `formkit/dmux`): Node.js CLI; "creates a tmux pane for each task. Every pane gets its own git worktree and branch"; requirements **tmux 3.0+**, Node 18+, Git 2.20+; supports Claude Code, Codex, OpenCode, Cline, Gemini, Qwen, Amp, pi, **Cursor CLI**, Copilot, Crush, Grok Build; pane menu Merge / Create GitHub PR; lifecycle hooks. Source: <https://github.com/standardagents/dmux/> (README, read 2026-09-02). Secondary: <https://nimbalyst.com/blog/best-tools-for-running-parallel-ai-coding-agents/> (tier C, "1K+ stars").
- **[FACT, A]** **Superset** (`superset-sh/superset`): Electron desktop IDE, "orchestrate 100+ coding agents in parallel", isolated worktrees, Cursor Agent / Claude Code / Codex / Gemini / Grok / Goose-class agents listed as "Fully supported"; **downloads: macOS primary, Linux AppImage experimental, "Windows: not yet available"**. Source: <https://github.com/superset-sh/superset> (README, read 2026-09-02). Its own guide says "At small scale, discipline and tmux can carry you" and that orchestration workspaces earn their keep only "once you are running parallel agents most days". Source: <https://superset.sh/parallel-coding-agents> (tier B).
- **[FACT, B, corroborated]** tmux on Windows runs only under WSL/MSYS2/Cygwin and "loses all Windows integration" (no toasts, no native paths). Sources: <https://github.com/amirlehmam/wmux> README ("tmux works in WSL but loses all Windows integration"), <https://www.wmux.app/en> FAQ ("Does wmux require WSL? No … There is no Linux VM in the path"), corroborating the brief's own statement.
- **[FACT, B/C, young projects]** Three unrelated projects named **wmux** target exactly "tmux for AI agents on native Windows": (a) `amirlehmam/wmux` - Electron + node-pty/ConPTY, 360 stars, created **2026-03-25**, named-pipe `\\.\pipe\wmux` JSON-RPC API (create workspaces, split panes, send keys, read pane text, CDP browser, spawn sub-agent terminals), PowerShell prompt hooks for working/done/interrupted state; (b) `openwong2kim/wmux` - Electron, "Windows & macOS", fan one prompt into **N isolated git worktrees** and "atomic adoption" of hunks, **agent-to-agent channels**, approval gates, survives full OS reboot via a daemon, "building in the open since March 2026"; (c) `Kazsuto/wmux` - **Rust + wgpu/Direct3D 12**, ConPTY, WebView2 browser panes, Named Pipes JSON-RPC v2 with HMAC auth, 80+ IPC handlers, `wmux-cli`. Sources: <https://github.com/amirlehmam/wmux>, <https://github.com/openwong2kim/wmux>, <https://www.wmux.app/en>, <https://github.com/Kazsuto/wmux>, <https://mcpmarket.com/server/wmux> (all read 2026-09-02; star counts and stability **UNVERIFIED** beyond the READMEs; all under six months old).

**[INFERENCE] The Windows reality for this box.**
1. dmux is the best-fit *pattern* (pane = worktree = branch = agent, merge from the pane) but its hard tmux dependency means WSL, and WSL on a 31.6 GB, chronically memory-starved box adds a Linux VM (`vmmem`) that competes with the Codex cap-of-3 for the same RAM. **Tradeoff, not a veto.**
2. Superset is not installable on Windows today.
3. The wmux family is native and scriptable (named-pipe JSON-RPC lets an orchestrator open panes and spawn agents programmatically - the same shape as dmux's `n` key), but two of three are Electron (each window carries a Chromium renderer; on this box that is the same RAM class as one more `cursor-agent`, which G-36 already caps at one), all three are pre-1.0, and they duplicate agent-to-agent messaging that agent-mail already provides. Their **genuinely new** capability for us is *persistence across reboot* and *atomic hunk adoption* from N worktrees.
4. **[INFERENCE, needs measurement]** For hosted-model workers specifically, panes are the wrong unit of parallelism: the worker is an HTTP client + tool executor, not an interactive TUI that needs a PTY. It can run as a headless process (PowerShell job, Scheduled Task, or child of the orchestrator) and report through agent-mail; a pane is only needed when a human wants to watch. That is the design choice section 7 makes.

## 6. Design: one hosted-model-agent adapter that speaks agent-mail and ACP

**[RECOMMENDATION - design, not built.]** Working name `hma` (hosted-model-agent). One Python process per *persona x runtime*, ~400-600 lines, three faces on one tool loop. It is the general integration layer the owner wants in place of `glm53-space`, but it is **not** an MCP server and adds **no row to `agents.json`** (rule 2 of `hosted-model-agents`; `mcp-fleet-curation`).

```
                 +---------------------------------------------------------+
  ACP client     |  hma  (one process = one persona on one runtime)        |
  (Zed / Toad /  |                                                         |
  orchestrator   |  face A: ACP agent (stdio)  <- agent-client-protocol    |
  spawn_agent_   |     initialize / session.new / session.prompt           |
  process) <---->|     session.update stream, request_permission            |
                 |                                                         |
  agent-mail     |  face B: agent-mail peer (HTTP MCP *client* of :8812)   |
  :8812 <------->|     ensure_project -> register_agent (codename+token)   |
  (owned port,   |     request_contact gate, fetch_inbox poll, reply,      |
   unchanged)    |     file_reservation_paths around every write           |
                 |                                                         |
  runtime /v1    |  core: tool loop  (hosted-model-agents/tool-loop.md)    |
  HF Router /    |     messages[0] = profile prompt (profiles.md)          |
  Endpoint /     |     tools = allowlist schema; validate name+args;       |
  Modal /        |     execute LOCALLY; role:tool round-trip; SSE stream  |
  Foundry /      |                                                         |
  llama-server   |  face C: CLI  `hma run --profile coder --runtime hf …`  |
  <------------->|     headless worker mode (no PTY), --watch for a pane   |
                 +---------------------------------------------------------+
```

**Face A - ACP agent (official Python SDK, v1 now, v2 flag later).** Subclass `acp.Agent`: `initialize` returns the negotiated version (accept 1; when `protocolVersion: 2` arrives and the flag is on, answer 2); `new_session(cwd, mcp_servers)` creates a session whose tool allowlist = profile tools ∩ (client-supplied `mcpServers` if any); `prompt()` runs the tool loop and streams `update_agent_message` / tool-call updates via `session_update`; any tool the profile marks `needs_permission` goes through `session/request_permission` so Zed/Toad show the same approval UI they show for Claude Code. **Sourced basis:** SDK surface in section 4 (`run_agent`, `session_update`, `acp.contrib` permission brokers). **[INFERENCE]** Because ACP v2 drops `fs/*`/`terminal/*`, the adapter should execute tools itself (v1 and v2 identical behaviour) and only *report* them - which is what `tool-loop.md` already prescribes.

**Face B - agent-mail peer.** Reuse `tools/crcp/crcp/bus.py` (`AgentMailRpc`, `load_or_register_bridge_agent`, `ensure_contact`, `publish_envelope`) as the client. Registration: `ensure_project(human_key=<repo abs path>)` once; `register_agent(project_key, program="hma:<profile>", model="<checkpoint>@<runtime>")`; store `(codename, registration_token)` in a per-user secret store outside the repo (name-only reference in `.agents/local.json`, matching dedup-set #4). Contact: **never auto-accept**; the human's Claude/Codex session accepts each hosted codename once. Work intake: poll `fetch_inbox(agent_name, registration_token)` on a backoff (there is no push; `crcp/bus.py` already polls); each message with `ack_required` becomes a `session/prompt` on an internal ACP session so *both faces share one code path*. Leases: before any local write the loop calls `file_reservation_paths(paths, exclusive=true, ttl_seconds=<turn budget>, reason=<thread id>)` and releases in `finally`; a lease conflict is surfaced to the model as a tool error, not silently overridden (`force_release` is a human tool). **License constraint carried from section 1:** if a persona is under evaluation (`evals.md`), the eval driver must not use agent-mail as its channel - use face A/C directly.

**Core - tool loop.** Unchanged from `hosted-model-agents/tool-loop.md`: OpenAI `tools` schema, `tool_choice`, allowlist + required-keys + JSON-parse checks before execution, unknown tool names treated as text, tool-call ids round-trip on `role: tool`, SSE streaming. Runtime is a plain OpenAI-compatible base URL + key name from the **profile**; HF Router, Endpoint, Modal, Foundry, `llama-server`, LM Studio and Ollama are all `/v1`-shaped (dedup-set #1 lists them). The Cursor quota via auth2api `:8317` is *also* a legal runtime for `hma` **only** when launched through the G-32 process-local wrapper pattern (`ai-mode`-style env for that process only; no global bridge env) - and it retires with auth2api within 7 days of a Cursor `/v1` GA (lock). OpenRouter is a legal runtime for the **CLI/Codex-sidecar** case only, spend-capped, never as a Cursor BYOK key (lock).

**Face C - CLI / headless worker.** `hma run --profile <p> --runtime <r> [--acp] [--mail] [--watch]`. `--acp` alone = pure ACP agent for Zed/Toad. `--mail` alone = headless peer polling :8812 (the "worker" role in section 7). `--watch` opens a read-only pane view (rich/Textual) for a human; not required for operation.

**What it deliberately does not do.** No new port, no new MCP server, no LiteLLM/LangGraph/second runtime, no vector memory (basic-memory :8765 stays the memory and is reachable to the *harness* as an ordinary allowlisted tool if a profile wants it), no credential rotation (uses existing `HF_TOKEN`/`HUGGINGFACE_TOKEN` names), no removal of `glm53-space` by itself (that is the owner's separate deprecation; `hma` is the replacement shape, and the `agents.json` row should be parked with `enabled: false` the way `markitdown`/`meta-tool` were).

**Build vs adopt per face.** Face A: **NATIVE** (official SDK; ~60 lines over the echo agent). Face B: **REUSE** (`crcp/bus.py`) + ~150 lines of poll/lease glue. Core: **REUSE** (`tool-loop.md` doctrine; `glm53_core.py`'s HTTP client if the owner keeps the file around during deprecation). Face C: **BUILD** (~100 lines, `argparse`/`typer`). Tradeoff option: **ADOPT `pydantic-acp`** for face A+core in exchange for a Pydantic-AI dependency (model picker, approval bridge, session store for free) - rejected as default on the "second runtime" lock, kept as a rubric row.

## 7. Parallelism pattern that fits this box

**Constraints (sourced):** 31.6 GB RAM, chronically memory-starved, no GPU assumed (brief); Codex fan-out cap = 3 and a 9-wide fan-out OOM'd all 9 (`repo:skills/multi-ai-mingle/CODEX_FANOUT.md`); G-36 = at most one `cursor-agent` process (`repo:skills/hosted-model-agents/SKILL.md`); tmux requires WSL (section 5); Superset has no Windows build (section 5).

**[RECOMMENDATION] "Headless hosted workers, one visible orchestrator, agent-mail as the pane."**

1. **Unit of parallelism = `hma --mail` headless process, not a pane.** Each worker is a Python process holding one HTTP connection to its runtime and one to :8812. Its context window is on the GPU box, so its resident footprint is a Python interpreter + httpx/urllib, not a Node MCP fleet. **[INFERENCE, needs measurement on the box]** expected order 60-150 MB RSS per worker vs. the multi-GB Codex thread; so **6-8 hosted workers ≈ one Codex slot**. Measure with `Get-Process -Name python | Measure-Object WorkingSet64 -Sum` before raising the cap; start at **4** hosted workers alongside **at most 2** Codex threads (leaving one Codex slot of headroom under the cap of 3) and adjust from measurement.
2. **Isolation = worktree per worker, exactly as `CODEX_FANOUT.md`**: `git -C <intended repo> worktree add` (CLAUDE.md rule), own branch `hma/wu-<n>`, push before exit, `git ls-remote` push-watcher is the done-signal, orchestrator verifies, never self-cert, two strikes -> split. Hosted workers inherit these rules unchanged.
3. **Coordination = agent-mail threads + leases, not shared panes.** The orchestrator (Claude or Codex, the human's visible session) sends one `send_message(ack_required=true)` per work unit to a worker codename; progress comes back as `reply_message` in the thread; leases make two workers touching the same file visible before the merge does. The inbox *is* the fleet view - `fetch_inbox` / `search_messages` replace "which pane is waiting?".
4. **Visibility for the human (optional, no new runtime):** Windows Terminal split panes (`wt -w 0 sp -d <worktree> hma run --watch …`) when watching is wanted; agent-mail's own web UI/TUI (Wave C, already planned) for the thread view. tmux/dmux only if the owner already keeps WSL running for other reasons (then `vmmem` RAM is a sunk cost and dmux's pane=worktree=branch flow is the best UX). wmux is a **watch item**: revisit when one of the three has a tagged 1.0 and a measured RSS; the Rust `Kazsuto/wmux` is the only one whose footprint is plausibly acceptable here.
5. **Stagger and failure semantics differ from Codex - in our favour.** No shared `auth.json` refresh race (each worker has its own runtime key by name); no shared app-server tree, so killing one hosted worker kills one. Keep the *stagger* anyway for HF Router / Endpoint rate limits, and give every worker a hard turn budget (tokens + wall clock) because a hosted model that loops costs money, not RAM.
6. **Where Codex and Claude still go:** anything needing the full local MCP fleet or the interactive approval UX stays a Codex/Claude thread (cap 3, section 3). Hosted workers take the *embarrassingly parallel* tail: red-team report drafting, literature learning, test-writing against a spec, doc lint - the `profiles.md` personas.
