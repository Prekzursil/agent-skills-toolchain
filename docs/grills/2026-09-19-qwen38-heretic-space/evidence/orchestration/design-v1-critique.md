## 9. Cost realism, the 1000-agent cap, per-invocation limits, resume

- Counts (§11, ≈ 270 R1 / ≈ 310-320 total, ≤ 110 per invocation) are consistent with the observed timings and fit the cap in either resume mode (`git` mode = one workflow per invocation; `cache` mode 4-5 × 110 ≪ 1000 even if replays count). The `agentsOk` reservation (`7 × chains + 4`) under-reserves a chain's worst case (2 authors + 2 reds + 3 builds + 3 verifies, each retried once = up to 20) — bounded by counters, but with C-8 an over-run parks progress instead of deferring it.
- Hidden cost as written: every confirmed local finding spawns a doomed fix chain (C-3, ≈ 5-6 agents); every clean gate is RED and triggers a revert (C-2, +1 agent and a lost merge per wave); the review loop runs on incomplete trees (C-5); the smoke run carries the full review loop (C-33). The "≈ 4 h more than A3" estimate is therefore not measurable until C-1..C-6 are fixed.
- Resume plan: `git` mode is the right default and `stale-launch-args` works (S9). What breaks it: reason-less rows, permanent parks after starvation, `next_args.stage` advancing after failure, no clean-gate re-run (C-8/C-9/C-10/C-22). `cache` mode is gated on the settling experiment — note `workflow-authoring/SKILL.md` L86-87: "`pipeline()` is not a cacheable resume unit — resuming a stopped pipeline re-runs its first stage"; the settling experiment should include a stopped-mid-pipeline resume, not only a completed one.
