## 3. Blocking defects per design (would make the run fail or lie)

### A2
1. **Null agent result crashes the run.** `safeAgent` calls `withTimeout` directly and then reads `r.status` (A2:L1168-1175). The H6 template's `withTimeout` returns the thunk's value unchanged (template L124-152); only `settle()` converts `null` to a receipt. `agent()` returns `null` on a user skip or a terminal API error (reference L15) → `TypeError` → caught by the stage `try` (L1620) → `RUN ABORTED` and the synthesizer runs on a dead run. F-41 is violated by the code that claims to guard it (L925).
2. **Ledger-hash equality is unsatisfiable.** The gate's hashed body includes `started_at`, `duration_s`, the worktree path and per-step seconds and log paths (L569-576), so two runs never share a `ledger_sha256`; `reduceVerdicts` requires `verify.ledger_hash_observed === impl.ledger_hash` (L1306) and `pVerify` tells the verifier to compare its own run's hash (L1261). Every task fails verification three times → `blocked:verify-exhausted`; if a verifier instead copies the implementer's file hash, the "two independent executions" signal (D/AP-3 row L939) is fake. Fix: A1's timestamp-free digest (A1:L272-277).
3. **Characterisation pins have no runnable mechanism.** T02a/b/c depend only on T01b and precede the T03 lift (L166-167); they are "test-only" (L854) yet must be "green-on-old" (L609) while `pTests` makes a test that passes on the base a failure (L1244) — and `app.py` at `f88b120` cannot be imported at all (model load at import + three undefined names), so pins written against it cannot run without AST extraction, which the design never mentions.
4. Composition root named both `main.py` (T04 L168, T10a L177) and `app.py` (T04c L169) — a card contradiction the plan critic must catch or two cards ship two roots.
5. `model:'fable'` overrides (L1173, L1334) with no `model` on the phase entry (contract nit, reference L10).

### A3
1. **F-11 guard exists only in the matrix.** The row says UNVERIFIED findings go to `verifier mode:'evidence'` before a card cites them (L810), but the plan stage (L1269-1281) only runs the planner and `verifier mode:'plan'`; critic-1..5 (all UNVERIFIED, incl. critic-2's blank user turn and critic-4's token-level continuation) can become cards unverified or be silently dropped. Not a crash; a "verified" the run cannot back.
2. **G-15 point (5) missing** — nothing says `python_eval` is enabled only by an operator secret flag; "absent from API/MCP toolsets" and "OFF on every surface" (L178, L587) leave the UI checkbox path unspecified. The decision is the build spec; a card built from this design could ship a checkbox-enabled tool.
3. **Continue mechanism contradicts the CORRECTED lines.** Lens-4 ships explicit Continue ON; A3's only resume path is chat-template `continue_final_message="reasoning_content"` (L181, L587). gpu-lease-3 CORRECTED and critic-4 (unverified, but the finding the pre-verifier would settle) say continuation must be at token level (`prefix_ids`/control record); the template `|trim`s content and closes `</think>` early, corrupting exactly the thinking presets.
4. **VLM class never stated.** Vision stays (G-16); a worker card built without "keep `AutoModelForImageTextToText`; no `prefill_chunk_size`; the checkpoint must carry `model.visual.*`" can pick a text-only checkpoint that cannot serve images (inference-perf-2 CORRECTED). Only the `prefill_chunk_size` idiom (L547) survives.
5. G-3 never named; Q4 (L1356) would defer gateway hardening to a second build run — contrary to "Both, equally" unless the owner explicitly re-decides.

### A1
1. **Null agent result crashes the run.** `safeAgent` reads `r.outward_actions_taken` on a `null` result (L736), the same class as A2's defect, while §10 asserts nulls become typed objects (L453).
2. **Transitively blocked dependents throw.** `build()` prunes only direct dependents of blocked cards after each wave (L993-994); a card depending on a pruned dependent stays in `queue`, `waves()` finds no ready card and throws `'no ready card'` (L705) → `RUN ENDED BY THROW` instead of a typed `dependency-blocked`.
3. **Approved plan hash not re-asserted.** The `build` stage re-runs `plan(pre)` expecting a cache replay (L1080) but compares only `OA.plan_hash === A.plan_hash` (two `args` values, L1079), never the recomputed `p.plan_hash`; on any cache miss the run builds a re-authored plan under the approved hash — the F-9 / D/AP-10 lie its matrix row (L570) says it prevents.
4. **No environment scrub in the gate.** `run_pytest` inherits the box environment (L240) and the secrets step scans only the diff range (L265), not `.gate/step-*.log`; the design's F-7 row (L515) relies on prompt rules for the part A2/A3 enforce mechanically.
5. **Agent budget at the edge.** ≈740 R1 agents vs an 800 soft cap (L479) and ≈41 h at cap 2 (L494); a 10 % higher fix rate parks the last cards as `agent-cap`.
6. (Program fit) The ship-but-flag list is not carried and Q9 re-opens the video default lens-4 already fixed (L1154).

## 5. Pairwise comparisons

**A1 vs A2.** The decisive difference is where verification truth lives and what it costs. A1's timestamp-free gate digest (A1:L272-277) makes "two independent gate runs at one sha agree" a real, cheap, machine signal, and its held-out seams H1-H7 turn the hard CORRECTED items (token-level Continue, `x-ip-token` inside the generator body, operator flag × every surface, TTL × no rmtree) into tests an implementer never sees; A2's equivalent signal is a self-hashed ledger whose body contains timestamps, so its equality check can never pass (A2:L569-576 vs L1306). Both crash on the first `null` agent result (the same `withTimeout` misuse). Where A2 wins is program carriage and cost: its decision sheet is in the design with a build consequence per id, its cards inline the CORRECTED text by finding id, its ship-but-flag list is complete, and it runs in roughly a third of A1's agents and wall-clock; A1 pays ≈740 agents and ≈41 h at cap 2 for probe agents, a 12-condition predicate and three-refuter panels, and still lets transitively blocked dependents throw and an unapproved plan slip past the hash check on a cache miss. Net: A2 ahead, because its two blocking code defects are one-line grafts (A1's digest; a null check), while A1's cost and structure are the design itself.

**A2 vs A3.** The decisive difference is replay determinism and null handling — the "would fail or lie" class. A3's waves are barrier-synchronised on purpose so the positional prefix cache holds (A3:L748), its `run()` converts null/timeout/throw into typed receipts (L1046-1058), its checkpoint object is computed in JS so no agent can add or remove an outward action (L1245-1257), its oracle lock is deterministic (L531-532), and its synthesizer rows are overwritten from the ledger on mismatch (L1305-1306). A2 is faster on paper (admission scheduler, ≈6.5 h at cap 14) and richer in program carriage, but it aborts on a null result, blocks every task on an unsatisfiable hash equality, and its call order depends on completion order under a prefix cache it admits it has not characterised. A3's weakness is exactly this judge's lens: it delegates the decision sheet and most CORRECTED specifics to the planner agent and omits several (token-level continuation, VLM class, the operator secret flag, the stop event, G-3 by name). Those are additions to a working skeleton; A2's defects are in the skeleton.

**A1 vs A3.** The decisive difference is mechanism count versus mechanism correctness. A1 has the richest guard set and the best carriage of the hard CORRECTED items (VLM class + Q6, token-level Continue, pre-verification of the UNVERIFIED critic findings, `against_recommendation` on every decision row); A3 has fewer mechanisms, all of them coherent, and the only skeleton of the three that survives a null result, keeps its call order replayable, and scrubs the test environment. A1 loses on C2/C3/C4/C6/C7 (null crash, transitive-block throw, un-asserted plan hash, inherited test environment, ≈740 agents); A3 loses on C5. A synthesis that takes A3's skeleton and grafts A1's §1.3/§4.6/pre-verifier/digest is stronger than either.

## 8. What none of them handles (common gaps)

1. **One token vs two backends.** G-15/G-24 says the only credential in the container is one narrowly scoped inference token. Under M-2 the CPU Space needs a credential for the HF router (hosted) *and* one that can reach the private worker Space via `gradio_client`. No design reconciles the count or names the scopes (fine-grained read on the worker Space + inference-provider permission), or says whether the worker Space is reached with the same token (A2:L176, A3:L1252, A1:L35 all speak of "the" token).
2. **`find_spec` probe and the kernels decision.** All three flag `__wrapped__` as a bad idiom; none names the positive boot probe (`importlib.util.find_spec('fla')`/`('causal_conv1d')`) or a card/runbook row for the inference-perf-4 CORRECTED plan (duplicate Space, Triton JIT budgeted in the first lease, no `kernels` without a matching build). It exists only as a staging keyword.
3. **`presence_penalty`.** inference-perf-3 CORRECTED requires either a LogitsProcessor with a CPU unit test or removing the placebo from UI/presets/API. None decides; all three only forbid passing it to `generate`. For the worker backend this is a real behaviour gap.
4. **lens-4 §C duplication list.** The ten collapse items (sampling kwargs in one place, one thinking split, one usage block, one error-to-content path, one stop normaliser, one tool dispatch, …) are not turned into DoD lines by any design; the layout is assumed to prevent the re-growth that produced the `images`/`videos` unbound names at HEAD.
5. **Persona absence test vs the boundary.** All three want a protected test that asserts the excluded clause is absent using "minimal normalised fragments", and none says how the test author obtains those fragments without reading `system_prompt.py` history or having the clause in a prompt. A hash of the normalised clause supplied by the owner (or a fragment list the owner writes) would resolve it; none proposes it.
6. **Fixture #1 ordering.** Lens-4 says the metered call must precede step 4's merge; all three make it an optional owner step before R1 and accept a synthetic fixture with a follow-up in R2 (A1 at least makes R2 depend on it). None makes step 4/T05/card 04 *unmergeable* without the recording, so the "seam shaped by whichever backend is built first" risk is accepted rather than closed.
7. **`/healthz` git sha on a Space.** Every canary rule compares the running sha with the pushed sha, and every thin-slice card says "`/healthz` with git sha"; none states how the sha reaches the running container (CI writes `GIT_SHA` into a file/env at deploy, or the runtime has `.git`). If the runtime lacks it, the canary's first check cannot be computed.
8. **Catalog entries that never pass the harness.** M-3 gates admission on the 12-prompt harness, which is paid and owner-run; with M-5 "everything in one release", the production catalog will carry `admission: pending`/`unverified` entries unless the harness ran on staging. None states the policy (hidden from the selector, shown with a badge, or promotion refused while any entry is pending).
9. **Worker checkpoint with visual tensors.** Only A1 asks whether the FP8 candidate carries `model.visual.*`; none budgets the case where neither the FP8 nor the GPTQ candidate does, which forces a VLM-class export HF Job before the staging worker can boot with vision on.
10. **Python patch level.** Only A3 notes 3.12.3 locally vs 3.12.12 in the Space image; none plans the one place it can matter (a `requirements` resolution that differs between the two), beyond "observed on staging".
