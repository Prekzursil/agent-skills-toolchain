# SYSTEMS-VERIFICATION Council — Six Harness Reliability Problems

**Date:** 28.08.2026  
**Mode:** discovery only; no implementation or configuration changes  
**Authority:** supersedes the Round-1 and Round-2 council assumptions for the claims tested here  
**Overall confidence:** **0.84 (high)** for platform/configuration facts; **0.48 (roughly even)** for the causal mechanism behind the observed Cursor mass-cancellation, because no incident-correlated process/ETW receipt exists.

## Method and verdict semantics

- `TRUE`: supported by at least two independent sources or one primary source plus a mechanically different local measurement.
- `FALSE`: contradicted by primary documentation, installed source, or a direct measurement.
- `UNVERIFIED`: plausible, but the available evidence does not discriminate it from alternatives. Each such row includes the settling experiment.
- Local file citations are disk evidence from this host. URLs are public sources.
- No absence is treated as proof unless the detector was shown to work.

## Claims that flipped from council assumptions

1. **“Windows OOM-killed the fleet” → UNVERIFIED; “Windows has an OOM killer” → FALSE.** Windows commit exhaustion fails allocations. At this council's measurement point, physical headroom was low but commit headroom was large, favoring thrash/timeout/index-loss hypotheses over current commit exhaustion.
2. **“WSL+systemd is an offload” → FALSE on-box.** WSL shares host RAM/commit. `vmmemWSL` itself occupied about 2.0 GiB resident memory during this run. WSL supports systemd, but the current Ubuntu instance reports PID 1 `init(Ubuntu)` and `systemctl` offline.
3. **“Disable Basic Memory reranker with `BASIC_MEMORY_RERANKER_ENABLED=false`” → FALSE for installed 0.22.1.** Reranking was added after this installed version. The variable is not an available installed field.
4. **“Basic Memory has a native >100 KB/entity cap” → FALSE.** `index_batch_max_bytes` is a batch shaper and explicitly still indexes an oversized file alone. The 100 KB rule is an external, provisional estate policy.
5. **“The 10-minute Basic Memory probe proves stability” → FALSE.** Later strikes/recoveries continued. Current health and semantics are confirmed only at a point in time.
6. **“Home-workspace duplicates halve MCP RAM” → UNVERIFIED.** Duplicate scope/UI representation is proven; per-scope duplicate process trees and the RAM delta are not. Moving the workspace is still low-risk hygiene.
7. **“The Claude local bridge can disappear while full sync stays green” → FALSE for the current wrapper.** Direct script exit is soft, but `sync_shared_state.ps1` rejects the missing `SUCCESS:` sentinel.
8. **“LockFileEx gives liveness truth for today's arbitrary agents” → FALSE.** It gives truth only for future cooperating holders and has delayed-release semantics under pressure.
9. **“Security words in titles are a proven trigger” → UNVERIFIED.** Content safeguards are proven; the title-only causal claim is not.

## Top five decisions

1. Move routine Cursor work from the home root to a normal single-project root, then measure—not assume—the RAM/process delta.
2. Ban relaunch based only on UI/composer state; keep one local writer and define a cooperating kernel writer lease.
3. Stay serial under current physical pressure; admission must inspect both free physical RAM and commit remaining, and account for `vmmemWSL`.
4. Preserve Basic Memory semantics, quarantine large generated artifacts via pointer notes, and stop relying on nonexistent 0.22.1 reranker/file-cap settings.
5. Extend the existing fail-closed sync contract across explicitly managed runtimes with one read-only drift sentinel; do not add a daemon.

## Single best experiment for the biggest UNVERIFIED

**Question:** Why do Cursor subagents become “canceled/dead” under pressure: process exit/allocation failure, scheduler/UI/composer-index loss, cyber-safeguard abort, or latency timeout while the worker remains alive?

**Experiment: one incident-correlated, read-only flight recorder during the next naturally occurring cancellation. Do not deliberately exhaust memory.**

Capture at 1–2 second cadence from before launch until five minutes after the first cancellation:

1. System: `Available MBytes`, `Committed Bytes`, `Commit Limit`, page reads/sec, hard faults/sec, pagefile usage.
2. Process tree: stable identity tuple `(PID, creation time, executable, parent PID, command line hash)`, private bytes, working set, CPU delta, I/O delta, and exit code where available for Cursor/agent descendants.
3. Agent artifact: subagent ID, transcript/output path, size and mtime growth, promised output existence/hash.
4. Product state: exact parent tool result and timestamp; exact “canceled,” “composer not found,” safeguard, timeout, or transport text; request ID if supplied.
5. Windows evidence: Event 2004 Resource-Exhaustion-Detector, Application Error 1000, WER 1001, and relevant Reliability Monitor/WER records for the same time window.
6. Safety: read-only subagents and one writer maximum; no automatic retry. If an apparently canceled worker's PID or artifact keeps progressing, wait and classify it alive instead of spawning a twin.

**Decision mapping:**

- Commit at limit + allocation/WER failure + process exit → application failure under Windows commit exhaustion.
- Commit headroom remains + hard faults/page reads spike + process/artifact continues → thrash/timeout plus false-dead UI.
- Process continues but composer lookup disappears → product index/control-plane loss.
- Explicit safeguard/request ID → classifier abort.
- Parent batch cancels siblings while their processes remain → orchestrator batch-abort/status reconciliation fault.

This single experiment has the highest expected information value because it selects among mutually different remedies: pagefile/commit work, physical-pressure admission, Cursor bug escalation, safeguard scoping, or retry/liveness control.
