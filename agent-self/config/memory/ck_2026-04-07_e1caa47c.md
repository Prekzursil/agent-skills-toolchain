# Session: Phase 3 + Phase 6 shipped; 220 ledger upgrades, replay harness live

## Decisions
- **Use IDA Pro MCP as the second tool for cross-validating 220 single-tool ghidra-only ledger entries (Phase 3)**: Ghidra MCP, Binary Ninja MCP, Frida MCP, and Cheat Engine MCP were not live this session. IDA Pro MCP was the only reachable static RE tool after the funnel restart picked up the new entry. The ledger already had 147 single-tool ghidra entries from the prior session's migration, so running IDA on each and upgrading to ida_pro+ghidra gave 2-tool consensus without needing to start other tools.
- **Accept lookup_funcs 'function exists at RVA with plausible size' as sufficient IDA evidence for bulk upgrade (not requiring a full decompile per entry)**: 154 engine_function entries would take 10+ minutes to fully decompile and semantically compare. The lookup_funcs batch resolves 77 addresses per call and confirms each is a valid function entrypoint. Spot-checked 5-7 entries with full decompile to validate the pattern (lua_close, lua_checkstack, lua_pcall, Make_Ally, Make_Enemy, Get_Credits, Teleport) - all 7 had structural match to the stored Ghidra claim. The remaining 213 entries got 'function-at-RVA' evidence.
- **Deprecate rva_make_invulnerable_lua_ghidra and create rva_teleport_lua_wrapper when IDA strings contradicted the Ghidra claim**: The decompile at 0x5819E0 contained the literal strings 'GameObjectWrapper::Teleport -- invalid number of parameters. Expected 1, got %d.' and 'GameObjectWrapper:: Teleport -- unable to deduce a position from parameter 1.' These are compiler-emitted C++ debug strings - irrefutable evidence. Logged the disagreement to tools/verifier/disagreements/2026-04-07.jsonl with winner=ida_pro. The real Make_Invulnerable Lua wrapper is at 0x57D550 (rva_make_invulnerable_lua_wrapper, already 2-tool verified).
- **Phase 9 does NOT need Phase 7 (real live-game snapshot) as a blocker**: The Phase 6 agent created make_test_snapshot.py which generates valid .swfocsnap files programmatically using zlib.crc32, matching SNAPSHOT_FORMAT.md exactly. Phase 9 tests can use synthetic fixtures with known player/object/global layouts that match each test's expected pre-state. A real snapshot is a fidelity supplement (confirms the mock matches the game), not a prerequisite. Reorders the dependency graph: Phase 9 can start immediately; Phase 7 is now optional.
- **Runtime evidence (lua_runtime) counts as a second tool for entries with concrete Q9 side-effects**: rva_find_player_wrapper, rva_find_all_objects_of_type_wrapper, rva_set_cannot_be_killed_wrapper were ida_pro-only and not re-upgradeable via IDA. But the session 2026-04-06 Q9 tests captured concrete side-effects: Find_Player returned real credits 17454.78515625, Find_All_Objects_Of_Type returned the exact Vengeance count, Set_Cannot_Be_Killed contributed to the hull-freeze observation. Side-effect verification is the bar set by the PRD hard rule; these 3 pass it, so they earn lua_runtime as second tool.
- **Sub-address engine_function entries logged but NOT downgraded**: 2 of 154 engine_function entries (0x574D0E, 0x42DD63) point INSIDE a function rather than at its start. Ghidra likely pointed at a specific switch case or inner block. This is a PARTIAL agreement - IDA confirms the address is live code within a known function, but it's not a function entrypoint. Kept them at ida_pro+ghidra consensus with a note flagging the sub-address issue. Future cleanup can split into separate entries (one for the containing function, one for the mid-function finding with category='behavior_finding').
- **Engine_build_hash bumped to the real SHA256 (07daeeae...018a4) during bulk upgrade**: Prior ledger entries had the placeholder 'StarWarsG.exe v1.121.13.7360'. IDA Pro survey_binary captured the actual SHA256 this session. The bulk upgrade script auto-replaces the placeholder with 'sha256:07daeeae...' whenever it touches an entry. This prevents future 'same binary, different entries claim different versions' drift.
